DMA Engine API Guide¶

Vinod Koul <vinod.koul@intel.com>

注意

async_txでのDMA Engineの使用については、以下をご参照ください: Documentation/crypto/async-tx-api.rst

DMA EngineのSlave-DMA APIを使用するデバイスドライバ開発者向けのガイドは以下の通りです。これはslave DMAの使用にのみ適用されます。

DMA 使用¶

Slave DMAの使用には以下の手順があります:

  • DMA slaveチャネルを割り当てる

  • slaveおよびコントローラー固有のパラメータを設定する

  • トランザクション用のディスクリプタを取得する

  • トランザクションを送信する

  • 未処理のリクエストを発行し、コールバック通知を待つ

これらの操作の詳細は以下の通りです:

  1. DMA slaveチャネルを割り当てる

    slave DMAコンテキストではチャネル割り当てがやや異なります。クライアントドライバは通常、特定のDMAコントローラーからのチャネルのみが必要であり、一部のケースでは特定のチャネルを指定することもあります。チャネルを要求するにはdma_request_chan() APIを使用します。

    インターフェース:

    struct dma_chan *dma_request_chan(struct device *dev, const char *name);

    ‘dev’デバイスに関連するDMAチャネルを検索し、返します。 name DMAチャネルは‘dev’デバイスに関連しています。関連付けはDT、ACPI、またはボードファイルベースのdma_slave_mapマッチングテーブルを通じて行われます。

    このインターフェースを通じて割り当てられたチャネルは、dma_release_channel()が呼ばれるまで呼び出し元専用です。

  2. slaveおよびコントローラー固有のパラメータを設定する

    次のステップは、DMAドライバに特定の情報を渡すことです。slave DMAが使用できる一般的な情報はstruct dma_slave_configに含まれています。これにより、クライアントはペリフェラルに対してDMA方向、DMAアドレス、バス幅、DMAバースト長などを指定できます。

    一部のDMAコントローラーがより多くのパラメータを送信する必要がある場合、そのコントローラー固有の構造体にstruct dma_slave_configを埋め込むべきです。これにより、クライアントが追加のパラメータを渡す必要がある場合に柔軟性が得られます。

    インターフェース:

    int dmaengine_slave_config(struct dma_chan *chan,
                  struct dma_slave_config *config)

    struct dma_slave_configの構造体定義については、dmaengine.hを参照してください。構造体メンバの詳細な説明が記載されています。注意点として、'direction'メンバはprepareコールで指定された方向と重複するため、将来的に削除される予定です。

  3. トランザクション用のディスクリプタを取得する

slave使用において、DMAエンジンがサポートするslave転送のさまざまなモードは以下の通りです:

  • slave_sg: ペリフェラルとscatter gatherバッファのリストをDMAする

  • dma_cyclic: ペリフェラルとのDMA操作を明示的に停止するまで繰り返します。

  • interleaved_dma: これはSlaveおよびM2Mクライアントにも共通です。デバイスのfifoアドレスがドライバに既知である場合があります。dma_interleaved_templateメンバに適切な値を設定することで、さまざまな操作を表現できます。チャネルがDMA_PREP_REPEAT転送フラグをサポートする場合、シクル型のinterleaved DMA転送も可能です。

この転送APIのNULLでない返却値は、指定されたトランザクションの「ディスクリプタ」を表します。

インターフェース:

struct dma_async_tx_descriptor *dmaengine_prep_slave_sg(
           struct dma_chan *chan, struct scatterlist *sgl,
           unsigned int sg_len, enum dma_data_direction direction,
           unsigned long flags);

struct dma_async_tx_descriptor *dmaengine_prep_dma_cyclic(
           struct dma_chan *chan, dma_addr_t buf_addr, size_t buf_len,
           size_t period_len, enum dma_data_direction direction);

struct dma_async_tx_descriptor *dmaengine_prep_interleaved_dma(
           struct dma_chan *chan, struct dma_interleaved_template *xt,
           unsigned long flags);

ペリフェラルドライバはdmaengine_prep_slave_sg()を呼び出す前に、DMA操作のためにスキャタリストリストをマッピングしておく必要があります。DMA操作が完了するまで、スキャタリストリストのマッピングを保持しなければなりません。スキャタリストリストはDMAを使用してマッピングする必要があります。 struct device後でマッピングの同期が必要な場合は、DMAを使用してdma_sync_*_for_*()を呼び出す必要があります。 struct device同様に、通常の設定は次のようになります。

nr_sg = dma_map_sg(chan->device->dev, sgl, sg_len);
   if (nr_sg == 0)
           /* error */

   desc = dmaengine_prep_slave_sg(chan, sgl, nr_sg, direction, flags);

ディスクリプタが取得された後、コールバック情報が追加され、その後ディスクリプタが送信される必要があります。一部のDMAエンジンドライバでは、準備成功と送信の間にスピンロックを保持する場合があります。そのため、これらの2つの操作は密接にペアリングされる必要があります。

注意

async_tx APIは完了コールバックルーチンが新しい操作を送信できないと指定していますが、これはslave/cyclic DMAでは当てはまりません。

slave DMAでは、コールバック関数が呼び出される前には次のトランザクションが送信不可となるため、slave DMAのコールバックは新しいトランザクションを準備・送信することが許可されます。

cyclic DMAでは、コールバック関数がdmaengine_terminate_async()を呼び出してDMAを終了したい場合があります。

そのため、DMAエンジンドライバはコールバック関数を呼び出す前に、ロックを解除しておくことが重要です。これによりデッドロックが発生しないようにします。

コールバックは常にDMAエンジンのタスケットから呼び出されるため、割り込みコンテキストではありません。

オプション: ディスクリプタごとのメタデータ

DMAengineはメタデータサポートのための2つの方法を提供します。

DESC_METADATA_CLIENT

メタデータバッファはクライアントドライバが割り当て/提供し、ディスクリプタにアタッチされます。

int dmaengine_desc_attach_metadata(struct dma_async_tx_descriptor *desc,
                              void *data, size_t len);

DESC_METADATA_ENGINE

メタデータバッファはDMAドライバが割り当て/管理します。クライアントドライバはポインタ、最大サイズ、現在の使用サイズを取得でき、メタデータを直接更新または読み取ることができます。

DMAドライバがメタデータを含むメモリ領域を管理しているため、クライアントは自分の転送完了コールバックが実行された後でメタデータにアクセスしたりポインタを取得したりしてはなりません。転送完了コールバックが定義されていない場合、issue_pendingの後でもメタデータにアクセスしてはなりません。言い換えれば、転送が完了した後でメタデータを読み戻したい場合は、クライアントは完了コールバックを使用しなければなりません。

void *dmaengine_desc_get_metadata_ptr(struct dma_async_tx_descriptor *desc,
           size_t *payload_len, size_t *max_len);

int dmaengine_desc_set_metadata_len(struct dma_async_tx_descriptor *desc,
           size_t payload_len);

クライアントドライバは、指定されたモードがサポートされているかを確認するには以下の通りです:

bool dmaengine_is_metadata_mode_supported(struct dma_chan *chan,
           enum dma_desc_metadata_mode mode);

使用するモードに応じて、クライアントドライバは異なるフローを実行する必要があります。

DESC_METADATA_CLIENT

  • DMA_MEM_TO_DEV / DEV_MEM_TO_MEM:

    1. ディスクリプタ（dmaengine_prep_*）を準備し、クライアントのバッファ内にメタデータを構築する

    2. dmaengine_desc_attach_metadata() を使用して、バッファをディスクリプタにアタッチする

    3. 転送を送信する

  • DMA_DEV_TO_MEM:

    1. ディスクリプタ（dmaengine_prep_*）を準備する

    2. dmaengine_desc_attach_metadata() を使用して、バッファをディスクリプタにアタッチする

    3. 転送を送信する

    4. 転送が完了した後、メタデータはアタッチされたバッファ内に利用可能となる

DESC_METADATA_ENGINE

  • DMA_MEM_TO_DEV / DEV_MEM_TO_MEM:

    1. ディスクリプタ（dmaengine_prep_*）を準備する

    2. dmaengine_desc_get_metadata_ptr() を使用して、エンジンのメタデータ領域へのポインタを取得する

    3. ポインタ先のメタデータを更新する

    4. dmaengine_desc_set_metadata_len() を使用して、クライアントがメタデータバッファに配置したデータ量をDMAエンジンに通知する

    5. 転送を送信する

  • DMA_DEV_TO_MEM:

    1. ディスクリプタ（dmaengine_prep_*）を準備する

    2. 転送を送信する

    3. 転送完了時に dmaengine_desc_get_metadata_ptr() を使用して、エンジンのメタデータ領域へのポインタを取得する

    4. ポインタからメタデータを読み出す

注意

DESC_METADATA_ENGINE モードを使用した場合、転送が完了した後からメタデータ領域はもはや有効でなくなる（completion callback が返る時点まで有効である場合もある）。

DESC_METADATA_CLIENT / DESC_METADATA_ENGINE の混用は許可されず、クライアントドライバは各ディスクリプタに対してどちらか一方のモードを使用しなければならない。

  1. トランザクションを送信する

    ディスクリプタが準備され、コールバック情報が追加された後、そのディスクリプタはDMAエンジンドライバの待機キューに配置しなければならない。

    インターフェース:

    dma_cookie_t dmaengine_submit(struct dma_async_tx_descriptor *desc)

    これは進捗状況を確認するために他のDMAエンジンコールを使用可能にするクッキーを返す。

    dmaengine_submit() はDMA操作を開始しない。単に待機キューに追加するのみであり、この処理はステップ5の dma_async_issue_pending を参照のこと。

    注意

    呼び出した後、 dmaengine_submit() 送信された転送ディスクリプタ（struct dma_async_tx_descriptor）はDMAエンジンに属するため、クライアントはそのディスクリプタへのポインタを無効とみなさなければならない。

  2. 待機中のDMAリクエストを実行し、コールバック通知を待機する

    待機キュー内のトランザクションは issue_pending API を呼び出すことで活性化される。チャネルがアイドル状態であれば、キュー内の最初のトランザクションが実行され、その後のものはキューに待機される。

    各DMA操作の完了時に次のキュー内のトランザクションが実行され、タスクレットがトリガーされる。タスクレットは、設定されている場合にクライアントドライバの完了コールバックルーチンを呼び出して通知を行う。

    インターフェース:

    void dma_async_issue_pending(struct dma_chan *chan);

その他のAPI¶

  1. 終了API

    int dmaengine_terminate_sync(struct dma_chan *chan)
int dmaengine_terminate_async(struct dma_chan *chan)
int dmaengine_terminate_all(struct dma_chan *chan) /* DEPRECATED */

    これにより、DMAチャネルのすべてのアクティビティが停止され、DMA FIFO内の未完全に転送されたデータは破棄される可能性がある。どの未完了トランザクションにもコールバック関数が呼ばれない。

    この関数には2つの変種が利用可能である。

    dmaengine_terminate_async()はDMAが完全に停止するのを待ったり、実行中の完了コールバックが終了するのを待ったりしない可能性があります。ただし、アトミックコンテキストからも、または完了コールバック内からもdmaengine_terminate_async()を呼び出すことは可能です。DMA転送でアクセスされたメモリや、完了コールバック内でアクセスされたリソースを安全に解放する前に、dmaengine_synchronize()を呼び出す必要があります。

    dmaengine_terminate_sync()は、転送および実行中の完了コールバックが終了するのを待ってから戻ります。ただし、この関数はアトミックコンテキストからも、または完了コールバック内からも呼び出すことはできません。

    dmaengine_terminate_all()は非推奨であり、新規のコードでは使用すべきではありません。

  2. 一時停止API

    int dmaengine_pause(struct dma_chan *chan)

    DMAチャネルの活動を停止しますが、データの喪失は発生しません。

  3. 再開API

    int dmaengine_resume(struct dma_chan *chan)

    以前に一時停止されたDMAチャネルを再開します。現在一時停止されていないチャネルを再開することはできません。

  4. トランザクション完了確認

    enum dma_status dma_async_is_tx_complete(struct dma_chan *chan,
          dma_cookie_t cookie, dma_cookie_t *last, dma_cookie_t *used)

    このAPIを使用してチャネルの状態を確認できます。より詳細な説明については、include/linux/dmaengine.hにあるドキュメンテーションを参照してください。

    このAPIはdma_async_is_complete()とdmaengine_submit()から取得したクッキーを組み合わせて使用し、特定のDMAトランザクションの完了を確認するために使用できます。

    注意

    すべてのDMAエンジンドライバが実行中のDMAチャネルに対して信頼できる情報を返すとは限りません。このAPIを使用する前に、チャネルを一時停止または停止（dmaengine_terminate_all()を介して）しておくことを推奨します。

  5. 終了同期API

    void dmaengine_synchronize(struct dma_chan *chan)

    DMAチャネルの終了を現在のコンテキストと同期します。

    dmaengine_terminate_async()の後にこの関数を使用する必要があります。DMAチャネルの終了を現在のコンテキストと同期するために使用します。この関数は転送および実行中の完了コールバックが終了するのを待ってから戻ります。

    dmaengine_terminate_async()を使用してDMAチャネルを停止した場合、この関数を呼び出す必要があります。以前に送信されたディスクリプタでアクセスされたメモリを安全に解放するか、以前に送信されたディスクリプタの完了コールバックでアクセスされたリソースを安全に解放する前に、この関数を呼び出す必要があります。

    dmaengine_terminate_async()とこの関数の間にdma_async_issue_pending()が呼び出された場合、この関数の動作は未定義です。

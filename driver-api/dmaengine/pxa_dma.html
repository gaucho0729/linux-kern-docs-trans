PXA/MMP - DMA Slave controller¶

制約¶

a) ホットキューイング ドライバが転送を送信し、実行を開始する際、DMAチャネルが動作中でも転送がキューイングされるべきです。これは、前の転送の終了を待たずにキューイングが行われ、転送終了時のIRQ/taskletコードによるディスクリプタのチェインングが行われるだけでなく、ディスクリプタのチェインングが行われるという意味です。物理チャネル上で送信・実行された転送は、物理チャネルが停止して再起動を待つことなく、「動作中のチャネル」上で送信されます。他のドライバ（特にmmp_pdma）は、物理チャネルが停止するのを待って新しい転送を再実行していました。

b) すべての確認を要求した転送は信号を送信する必要があります。DMA_PREP_INTERRUPTを指定した転送は、コールバック呼び出しをトリガーする必要があります。これは、転送tx1の終了によりIRQ/taskletがトリガーされたとしても、IRQ/DMA転送tx2がすでに終了している場合、tx1->complete()とtx2->complete()の両方が呼び出されるべきという意味です。

c) チャネルの動作状態 ドライバはチャネルが動作中かどうかを確認する必要があります。動画キャプチャなどのマルチメディア用途では、転送が送信された後、DMAチャネルの状態を確認した結果「停止中」である場合、次の「フレーム開始割込み」まで転送を実行しない必要があります。したがって、チャネルが動作中か停止中かを確認する必要があります。

d) バンド幅の保証 PXAアーキテクチャではDMAの優先度が4段階あります：high（高）、normal（通常）、low（低）。high優先度はnormalの2倍、normalはlowの2倍のバンド幅を確保します。ドライバは特にリアルタイム処理（例：pxa_camera）のような大容量のデータ転送を必要とする場合、優先度を指定できる必要があります。

設計¶

a) 仮想チャネル sa11x0ドライバと同じ概念です。つまり、ドライバに「仮想チャネル」が割り当てられ、リクエスターラインにリンクされ、転送が実行される際に物理DMAチャネルが動的に割り当てられます。

  1. スキャッターガather転送の転送構造

+------------+-----+---------------+----------------+-----------------+
| desc-sg[0] | ... | desc-sg[last] | status updater | finisher/linker |
+------------+-----+---------------+----------------+-----------------+

この構造はdma->sg_cpuによって指されます。ディスクリプタは以下のように使用されます：

  • desc-sg[i]: i番目のディスクリプタ、i番目のsg要素をビデオバッファスキャッターガatherに転送します

  • ステータスアップデーター 単一のu32を特定のDMAコンセントなメモリに転送し、この転送が完了したことをトレースするためのものです。この「特定の」は物理チャネルごとに一意であり、この値を読み取ることで、その時点での最後に完了した転送を確認できます。

  • フィニッシャー: ddadr=DADDR_STOP、dcmd=ENDIRQEN

  • リンカー: ddadr=次の転送のdesc-sg[0]、dcmd=0

c) ホットチェインの転送 進行中のチェインが以下のようだったと仮定します:

Buffer 1              Buffer 2
+---------+----+---+  +----+----+----+---+
| d0 | .. | dN | l |  | d0 | .. | dN | f |
+---------+----+-|-+  ^----+----+----+---+
                 |    |
                 +----+

dmaengine_submit(b3)の呼び出し後、チェインは以下のようになります:

Buffer 1              Buffer 2              Buffer 3
+---------+----+---+  +----+----+----+---+  +----+----+----+---+
| d0 | .. | dN | l |  | d0 | .. | dN | l |  | d0 | .. | dN | f |
+---------+----+-|-+  ^----+----+----+-|-+  ^----+----+----+---+
                 |    |                |    |
                 +----+                +----+
                                      new_link

new_linkが作成される際、DMAチャネルが停止していた場合、チャネルは再開されません。ホットチェインはdma_async_issue_pending()を用いて転送が実際に開始されるという前提を破らないため、この仮定は維持されます。

このルールの例外:

  • Buffer1とBuffer2のすべてのアドレスが8バイトアライメントされている場合

  • かつBuffer3の少なくとも1つのアドレスが4バイトアライメントされていない場合

  • ホットチェインは実行されません。なぜなら、チャネルは停止し、「アライメントビット」が設定され、チャネルが再開しなければならないからです。その結果、このような転送tx_submit()はサブミットキューにキューイングされ、DMAがすでにアライメントモードで動作している場合にこの特定のケースが発生します。

d) 転送完了アップデーター 毎回チャネルで転送が完了した際、クライアントの要請に応じて割り込みが発生する場合もあります。しかし、いずれの場合も転送の最後のディスクリプタ、「ステータスアップデーター」が物理チャネルの完了マーキングに最新の完了転送を書き込みます。

これはビデオバッファなどの大容量転送（約6,000ディスクリプタ以上を保持）の残量計算を高速化し、また、ロックを必要とせずに進行中のDMAチェインで最新の完了転送を特定できるようにします。

e) 転送完了、割り込みおよびタスクレット 転送が「DMA_PREP_INTERRUPT」フラグで指定されている場合、完了時にDMA割り込みが発生します。この割り込みにより、物理チャネルのタスクレットがスケジュールされます。

タスクレットの責任は以下の通り:

  • 物理チャネルの最後のアップデーターマーキングを読み込む

  • そのマーキングと各転送フラグに基づき、完了した転送のすべてのコールバックを呼び出す

この処理中に転送が完了した場合、DMA割り込みが発生し、タスクレットが再度スケジュールされ、新しいアップデーターマーキングを持つことになります。

f) 残量 残量の粒度はディスクリプタベースになります。発行済みだが完了していない転送は、現在進行中のディスクリプタとすべてのディスクリプタをスキャンします。

g) ドライバのtxキューの最も複雑なケース 最も複雑な状況は以下の通り:

  • 「アッカーデッド」されていない転送（tx0）が存在する場合

  • ドライバがアライメントされたtx1をサブミットし、チェインされていない場合

  • ドライバがアライメントされたtx2をサブミットし、tx2はtx1にコールドチェインされる場合

  • ドライバがtx1+tx2を発行し、チャネルがアライメントモードで動作している場合

  • ドライバがアライメントされたtx3をサブミットし、tx3はホットチェインされる場合

  • ドライバがアライメントされていないtx4をサブミットし、tx4はサブミットキューに配置され、チェインされない場合

  • ドライバがtx4を発行し、tx4は発行キューに配置され、チェインされない場合

  • ドライバーが一致したtx5を送信しました。tx5は送信キューに配置され、チェーンされません。

  • ドライバーが一致したtx6を送信しました。tx6は送信キューに配置され、tx5に冷蔵チェーンされています。

tx4が発行された後、これは以下のように表されます：

  • 発行キュー

+-----+ +-----+ +-----+ +-----+
| tx1 | | tx2 | | tx3 | | tx4 |
+---|-+ ^---|-+ ^-----+ +-----+
    |   |   |   |
    +---+   +---+
  - submitted queue
+-----+ +-----+
| tx5 | | tx6 |
+---|-+ ^-----+
    |   |
    +---+

  • 完了キュー : 空

  • 割り当てキュー : tx0

tx3が完了した後、チャネルが停止され、「非整列モード」で再起動され、tx4を処理します。

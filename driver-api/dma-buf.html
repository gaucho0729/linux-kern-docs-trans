バッファ共有と同期¶

dma-bufサブシステムは、複数のデバイスドライバおよびサブシステム間でハードウェア（DMA）アクセス用のバッファを共有するためのフレームワークを提供し、非同期ハードウェアアクセスの同期にも使用されます。

これは、たとえばdrm「prime」マルチGPUサポートなどで使用されますが、GPU用途に限定されるわけではありません。

このサブシステムの3つの主要なコンポーネントは以下の通りです：(1) dma-bufはsg_tableを表し、ユーザー空間にファイルディスクリプタとして公開され、デバイス間で渡すことができます。(2) フェンスは、1つのデバイスがアクセスを終えたことを信号として通知するメカニズムを提供します。(3) 予約は、バッファに関連する共有または排他的フェンスを管理します。

ユーザースペースインターフェースに関する注意事項¶

DMAバッファファイルディスクリプタは基本的にユーザースペースにとって不透明なオブジェクトであり、公開される汎用インターフェースは極めて最小です。ただし、いくつか考慮すべき点があります：

  • カーネル3.12以降、dma-buf FDはllseekシステムコールをサポートしますが、offset=0とwhence=SEEK_END|SEEK_SETのみです。SEEK_SETは通常のサイズ取得パターン（size = SEEK_END(0); SEEK_SET(0)）を許可するためサポートされています。他のすべてのllseek操作は-EINVALを報告します。

    dma-buf FDにおけるllseekがサポートされていない場合、カーネルはすべてのケースで-ESPIPEを報告します。ユーザースペースはこれを用いて、dma-bufサイズの検出がサポートされているかを検出できます。

  • exec時にfdリークを防ぐため、ファイルディスクリプタにFD_CLOEXECフラグを設定する必要があります。これは単なるリソースリークではなく、潜在的なセキュリティホールです。リークしたfdを通じて、新しいexec’dアプリケーションが本来アクセスすべきではないバッファにアクセスできる可能性があります。

    ファイルディスクリプタ作成時に原子的に処理するのではなく、別途fcntl()呼び出しで処理する場合の問題は、マルチスレッドアプリケーションでは本質的にレース条件を引き起こします。この問題は、ライブラリコードがファイルディスクリプタを開く/作成する場合にさらに悪化します。アプリケーションはそのfdを認識していない可能性があるからです。

    この問題を回避するため、ユーザースペースはdma-buf fd作成時にO_CLOEXECフラグを設定するよう明示的にリクエストする方法が必要です。したがって、エクスポートドライバが提供するAPIでdma-buf fdを作成する際には、ユーザースペースがO_CLO、EXECフラグを設定するのを制御できる手段を提供する必要があります。 dma_buf_fd().

  • DMAバッファの内容のメモリマッピングもサポートされています。詳細については、以下の CPUアクセスDMAバッファオブジェクト を参照してください。

  • DMAバッファFDはpoll可能であり、詳細は以下の 暗黙のフェンスpollサポート を参照してください。

CPUアクセスDMAバッファオブジェクト¶

複数の理由でDMAバッファオブジェクトへのCPUアクセスをサポートする必要があります：

  • カーネルのフォールバック操作、たとえばUSB経由でデバイスが接続され、カーネルがデータを転送する前にデータをシャッフルする場合など。キャッシュの整合性は、 dma_buf_begin_cpu_access() および dma_buf_end_cpu_access() を呼び出すことでトランザクションを囲みます。

    ほとんどのカーネル内部のdma-bufアクセスでは、全体のバッファが必要なため、vmapインターフェースが導入されました。注意点として、非常に古い32ビットアーキテクチャではvmalloc領域が制限され、vmap呼び出しが失敗する可能性があります。

    インターフェース:

    void *dma_buf_vmap(struct dma_buf *dmabuf) void dma_buf_vunmap(struct dma_buf *dmabuf, void *vaddr)

    vmap呼び出しが失敗する可能性は、エクスポーターにvmapサポートがなければ、またはvmalloc領域が不足している場合です。この場合、kmapへのフォールバックを実装する必要があります。注意点として、dma-bufレイヤーはすべてのvmapアクセスに対して参照カウントを保持しており、既にvmappingが存在しない場合にのみエクスポーターのvmap関数を呼び出し、解除も1回だけ行います。同時にvmap/vunmap呼び出しに対する保護は、dma_buf->lockミューテックスを取得することで提供されます。

  • 既存のユーザースペースインターフェースとの完全な互換性を確保するため、mmapでバッファをマッピングする機能をサポートしている場合があります。これは多くの処理パイプラインで必要です（例：ソフトウェアで描画した画像をハードウェアパイプラインに供給、サムネイル生成、スナップショットなど）。また、AndroidのIONフレームワークはすでにこの機能をサポートしており、DMAバッファファイルディスクリプタでIONバッファを置き換えるためにはmmapサポートが必要でした。

    特別なインターフェースは存在せず、ユーザースペースはdma-buf fdに対してmmapを呼び出します。CPUアクセス同様に、実際のアクセス範囲を括る必要がありますが、これはioctl（DMA_BUF_IOCTL_SYNC）で処理されます。注意点として、DMA_BUF_IOCTL_SYNCは-EAGAINまたは-EINTRで失敗する場合があり、その場合は再実行する必要があります。

    一部のシステムでは、CPUとGPUドメインがdma-bufを通じて同時にアクセスされる場合、キャッシュコヒーレンシー管理が必要になることがあります。このような問題を回避するため、begin/endコヒーレンシーマーカーが用意されており、これらは既存のdma-bufデバイスドライバのvfuncハンドラに直接転送されます。ユーザースペースはDMA_BUF_IOCTL_SYNC ioctlを通じてこれらのマーカーを使用できます。使用例は以下の通りです：

    • dma-buf fdのmmap

    • CPUでの各描画/アップロードサイクルに対して1. SYNC_START ioctl、2. mmap領域への読み込み/書き込み、3. SYNC_END ioctl。この操作は必要に応じて繰り返すことができます（新しいデータはGPUやスキャンアウトデバイスなどに消費されます）

    • バッファが不要になったらmunmapします

    正しさと最適なパフォーマンスのために、マッピングアドレスにアクセスする際には常にSYNC_STARTとSYNC_ENDをそれぞれ前後で使用する必要があります。ユーザースペースはこれらのioctlを呼び出さない場合でもコヒーレントなアクセスを保証できません。

  • ユーザースペース処理パイプラインにおけるCPUのフォールバックとして

    カーネルCPUアクセスの動機と同様に、特定のインポートサブシステムのユーザースペースコードが、インポートされたdma-bufバッファオブジェクトとネイティブなバッファオブジェクトの両方で同じインターフェースを使用できることが重要です。これは特にDRMにおいて重要で、現代のOpenGL、X、その他のドライバのユーザースペース部分は非常に大きく、それらを別の方法でバッファをmmapするように再構築するのは非常に侵襲的です。

    現在のdma-bufインターフェースの前提は、初期のmmapのリダイレクトがすべて必要なこととされています。いくつかの既存サブシステムの調査結果では、どのドライバもデバイス上の未処理の非同期処理と同期するなど、悪意のある動作を行っていないようです。したがって、ページフォールトをインターセプトし、pteのシャットダウンを許可するインターフェースを追加することで複雑さが大幅に増すため、これで十分であると期待されます。

    インターフェース:
    int dma_buf_mmap(struct dma_buf *, struct vm_area_struct *,

    unsigned long);

    インポートサブシステムがユーザースペースで特殊なmmap呼び出しを提供してマッピングを設定する場合、dma_buf->fileをdo_mmapに渡すことでdma-bufオブジェクトでも同様の結果を得られます。

DMAフェンス¶

DMAフェンスは、GPUレンダリング、ビデオエンコード/デコード、またはスクリーン上でのバッファ表示などのDMA操作のためのカーネル内部の同期プリミティブを表します。 struct dma_fence、これらはDMA操作のためのカーネル内部の同期プリミティブです。

フェンスは以下の関数を使用して初期化されます dma_fence_init() 、完了は以下の関数を使用して行われます dma_fence_signal()。フェンスはコンテキストに関連付けられ、以下の関数を通じて割り当てられます dma_fence_context_alloc()、かつ同じコンテキスト上のすべてのフェンスは完全に順序付けられます。

フェンスの目的はクロスデバイスおよびクロスアプリケーションの同期を促進することですが、使用方法は複数あります：

  • 個々のフェンスは sync_fileとして公開され、ユーザー空間からファイルディスクリプタとしてアクセスされ、以下の関数を呼び出すことで作成されます sync_file_create()。これは明示的なフェンスと呼ばれ、ユーザー空間が明示的な同期ポイントを扱います。

  • 一部のサブシステムは、以下の drm_syncobjなどの独自の明示的なフェンスプリミティブを持っています。これと比較して sync_file, a drm_syncobj は、下位のフェンスを更新できるようにします。

  • 次に、暗黙的なフェンスもあります。同期ポイントは共有された dma_buf インスタンスとして暗黙的にやり取りされます。このような暗黙的なフェンスは、以下の struct dma_resv を通じて dma_buf.resv ポインタを参照します。

DMAフェンスクロスドライバーコントラクト¶

なぜなら dma_fence クロスドライバーの契約を提供し、すべてのドライバが同じルールに従う必要があります：

  • フェンスは合理的な時間内で完了する必要があります。ユーザー空間から送信されたカーネルやシェーダーを表すフェンスは、永遠に実行される可能性があるため、タイムアウトとGPUハング回復コードでバックアップする必要があります。最小限のコードは、さらにコマンド送信を防ぎ、進行中のすべてのフェンスを強制的に完了する必要があります（ドライバーやハードウェアがGPUリセットをサポートしない場合、またはGPUリセットが失敗した場合など）。理想的には、ドライバがGPU回復をサポートし、これにより不正なユーザー空間コンテキストのみが影響を受け、他のユーザー空間送信には影響しないようにします。

  • ドライバは、他のドライバのフェンスのタイムアウト処理を推測してはいけません。ドライバは、他のドライバのタイムアウト処理を二重に推測してはいけません。

  • 以下の dma_fence_wait() のロックに対してデッドロックを防ぐために、ドライバはすべてのフェンス完了に必要なコードを以下の dma_fence_signal()で注釈付けする必要があります。 dma_fence_begin_signalling() および dma_fence_end_signalling().

  • ドライバは以下の dma_fence_wait() を保持しながら呼び出すことができます dma_resv_lock()これは、フェンス完了に必要なコードがロックを取得できないことを意味します。 dma_resv ロック。このことは、既存のロック階層全体を引き込むことにも注意してください。 dma_resv_lock() および dma_resv_unlock().

  • ドライバは以下の dma_fence_wait() 彼らのコールバックから shrinker コールバック。これは、フェンス完了に必要なコードがGFP_KERNELでメモリを割り当てることができないことを意味します。

  • ドライバは以下の dma_fence_wait() 彼らのコールバックから mmu_notifier それぞれ mmu_interval_notifier コールバック。これは、フェンス完了に必要なコードがGFP_NOFSまたはGFP_NOIOでメモリを割り当てることはできません。許可されるのはGFP_ATOMICのみで、これは失敗する可能性があります。

注意してください。GPUドライバ以外のドライバは、両方の要件を満たす理由がありません。 mmu_interval_notifier および shrinker コールバックを同時に要求する必要がありますが、非同期コンピュートワークを追跡するための dma_fence。drivers/gpu以外のドライバは、このような文脈で呼び出すべきではありません。 dma_fence_wait() このような文脈で呼び出すべきではありません。

DMA Fence Signalling Annotations¶

すべてのカーネルコードの正しさを証明するのはいくつかの理由で難しいです。 dma_fence コードレビューとテストを通じてはいくつかの理由で難しいです。

  • これはクロスドライバ契約であり、したがってすべてのドライバはロックネスティングの順序、さまざまな関数の呼び出しコンテキスト、およびカーネルインターフェースで重要なすべてのルールに従う必要があります。しかし、単一のマシンですべてのドライバをテストするのは不可能です。したがって、すべての組み合わせのブートフォースN対Nテストも不可能です。たとえ可能な組み合わせに限定しても、実行不可能です。

  • 関与するドライバコードは非常に多く、レンダードライバではフェンスが公開された後でのコマンド送信の末尾、スケジューラコード、ジョブ完了処理用の割り込みとワーカー、タイムアウト、GPUリセット、GPUハング回復コードがあります。さらにコアmmとの統合には、 mmu_notifierそれぞれ mmu_interval_notifier, and shrinker。モード設定ドライバでは、アトミックモードセットのフェンスが公開されたときと、対応するvblankが完了するときの間にコミット末尾関数があり、その間に割り込み処理や関連するワーカーも含まれます。すべてのドライバを横断してそのコードを監査するのは現実的ではありません。

  • 他のサブシステムの関与や引き込むロック階層のため、ドライバ固有の違いに許容される余地は非常に限られています。 dma_fence ページフォールハンドラを通じて、コアメモリ処理のほぼすべてと相互作用します。 dma_resv, dma_resv_lock() および dma_resv_unlock()。一方で、すべての割り当てサイトを通じて相互作用します。 mmu_notifier および shrinker.

さらに、lockdepはクロスリリース依存関係を処理しません。これは、任意のデッドロックが発生した場合、 dma_fence_wait() および dma_fence_signal() ランタイムで簡単なテストで検出できません。最も簡単な例は、1つのスレッドがロックを保持しながら別のロックを待っている場合です： dma_fence ロックを保持しながら待っている場合です：

lock(A);
dma_fence_wait(B);
unlock(A);

他のスレッドが同じロックを取得しようとして詰まっている間、前のスレッドが待っているフェンスをシグナルすることができないためです：

lock(A);
unlock(A);
dma_fence_signal(B);

signalling a に関連するすべてのコードを手動で注釈を付けることで dma_fence lockdep にこれらの依存関係を教えることができ、これにより検証の煩わしさも軽減されます。なぜなら、lockdep がすべてのルールを自動的にチェックできるからです：

cookie = dma_fence_begin_signalling();
lock(A);
unlock(A);
dma_fence_signal(B);
dma_fence_end_signalling(cookie);

For using dma_fence_begin_signalling() および dma_fence_end_signalling() critical sections を注釈するには、以下のルールを遵守する必要があります：

  • complete a に必要なすべてのコード dma_fence は、他のスレッドがフェンスにアクセスできるポイントから、 dma_fence_signal() が呼ばれるポイントまで注釈を付ける必要があります。注釈されていないコードにはデッドロックの可能性があり、非常に厳しいルールと多くの特殊なケースのため、レビューだけや通常のストレステストではこれらの問題を検出するのは現実的ではありません。

  • struct dma_resv は、読者を rcu でしか保護していないため、特別な注意が必要です。これは、新しいフェンスがインストールされた時点で直ちにシグナルングのクリティカルセクションが始まるためで、 dma_resv_unlock() polling間隔（ms）。0の場合はpollingを無効にします。

  • の呼び出しが行われる前からです。例外は高速パスと機会的シグナルングコードで、これらは dma_fence_signal() を最適化のために純粋に呼び出すだけで、の完了を保証する必要はありません。 dma_fenceの通常の例は、wait IOCTL が dma_fence_signal()を呼び出すことです。一方、必須完了パスはハードウェア割込みと可能であればジョブ完了ワーカーを通じて行われます。

  • コードの組み合わせ性を支援するため、注釈は全体的なロック階層が一貫している限り自由にネストできます。注釈は割込みコンテキストとプロセスコンテキストの両方で動作します。実装の詳細により、呼び出し元が dma_fence_begin_signalling() に（木の下から葉に向かって） dma_fence_end_signalling().

  • からオパケなクッキーを渡す必要があります。クロスドライバーコントラクトに対する検証は、起動時に関連する階層を lockdep に事前に設定することで実装されます。これにより、単一のデバイスでさえドライバの検証に十分であり、少なくとも dma_fence_wait() に対するデッドロックについては、 dma_fence_signal() と対応します。

不定期DMAフェンス¶

さまざまなタイミングで、不定期な時間まで続くdma_fenceが提案されています。例として以下があります： dma_fence_wait() 完了が提案されています。例として以下があります：

  • HWC1で使用され、バッファがディスプレイによってもはや使用されなくなったタイミングを信号として伝達する「未来フェンス（Future fences）」で、スクリーン更新によってバッファが表示されるよう作成されます。このフェンスが完了するタイミングはすべてユーザースペースの制御下にあります。

  • 「プロキシフェンス（Proxy fences）」は、drm_syncobjに対してフェンスがまだ設定されていない場合に使用される提案された方法で、コマンド送信を非同期的に遅延させるために使われます。

  • ユーザースペースで使用される「ユーザースペースフェンス（Userspace fences）」または「GPUファutex（gpu futexes）」は、コマンドバッファ内でエンジン間やCPUとの同期に使用される微細なロックで、DMAフェンスとしてインポートされて既存のwinsysプロトコルに統合されます。

  • 長時間実行されるコンピュートコマンドバッファは、コンピュートジョブが再スケジュールされるたびに再接続されるコンテキストプレエマプションDMAフェンスではなく、メモリ管理に従う伝統的なバッチ終了DMAフェンスを使用します。

これらのすべてのスキームに共通するのは、ユーザースペースがこれらのフェンスの依存関係を制御し、フェンスが発火するタイミングを制御していることです。無限フェンスと通常の内核DMAフェンスを混在させることは、フォールバックタイムアウトを含めても動作しません：

  • DMAフェンスの依存関係については、すべての内核が把握していますが、ユーザースペースはメモリ管理やスケジューラの決定によって注入された依存関係を把握していません。

  • 無限フェンスのすべての依存関係や、それらが正確にいつ完了するかについては、ユーザースペースのみが把握しており、内核はその情報にアクセスできません。

さらに、内核はメモリ管理の必要性のためにユーザースペースのコマンド送信を待機できる必要があります。つまり、無限フェンスがDMAフェンスに依存していることをサポートしなければなりません。内核がDMAフェンスのように無限フェンスをサポートする場合、例えば上記のどの提案でもそうであるように、デッドロックの可能性があります。

これは、ユーザースペースが把握していないメモリ管理の依存関係によって内核が誤ってデッドロックを生成し、ランダムにワークロードを停止する可能性があることを意味します。ユーザースペースの視点ではデッドロックが含まれていないワークロードです。このような混合フェンスアーキテクチャでは、すべての依存関係を把握するエンティティが存在しないため、内核内でこのようなデッドロックを防ぐことは不可能です。

依存関係のループを避ける唯一の解決策は、内核で無限フェンスを許可しないことです。これは以下の意味です：

  • 未来フェンス、プロキシフェンス、またはDMAフェンスとしてインポートされるユーザースペースフェンス（タイムアウトを含むか含まない場合も含む）は一切許可されません。

  • ユーザー空間がユーザー空間のフェンスを使用して許可されている場合や、長時間実行されるコンピュートワークロードを使用している場合、バッチバッファの終了を信号として示すDMAフェンスは使用されません。このような場合、共有バッファに対する暗黙のフェンスもありません。

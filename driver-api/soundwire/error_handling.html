SoundWireエラー処理¶

SoundWire PHY は丁寧に設計されており、バス上のエラーは非常にまれであり、発生した場合でも単一ビットエラーに限定されます。この設計の例は同期メカニズム（2つのエラー後に同期喪失）や Bulk Register Access に使用される短い CRC に見られます。

エラーは複数のメカニズムで検出できます:

  1. バスクラッシュまたはパリティエラー: このメカニズムは、ペイロードや用途に依存しない低レベルの検出器に依存しており、コントロールデータとオーディオデータの両方をカバーします。現在の実装ではこのようなエラーを記録するだけですが、改善策としてプログラミングシーケンス全体を無効化し、既知の位置から再開する方法が考えられます。コントロール/コマンドシーケンス外でのこのようなエラーの場合、SoundWire プロトコルでオーディオデータの隠蔽や復旧は行われず、エラーの位置が聴覚への影響（PCM では最上位ビットが最も影響を受けます）に影響します。このようなエラーが検出された後、バスがリセットされる可能性があります。注意点として、プログラミングエラー（2つのストリームが同じビットスロットを使用）や送受信遷移時の電気的問題によるバスクラッシュは区別ができないものの、オーディオが有効な状態で繰り返しバスクラッシュが発生する場合はバス割り当ての問題を示唆しています。割り込みメカニズムはバスクラッシュやパリティエラーを検出した Slave を特定するのに役立ちますが、エラーを引き起こした責任を負わない場合もあり、個別にリセットするという回復戦略は現実的ではありません。

  2. コマンドステータス: 各コマンのステータスは、デバイス間でのデータ送信をカバーします。ACK ステータスはコマンドが受信され、現在のフレームの終わりまでに実行されることを示します。NAK ステータスはコマンドにエラーがあり、適用されないことを示します。プログラミング不良（非存在する Slave または未実装レジスタへのコマンド送信）や電気的問題により、応答信号がなくコマンドが無視されたことを示します。一部のマスター実装ではコマンドを複数回再送信できる場合があり、再送信が失敗した場合はバックトラッキングし、プログラミングシーケンス全体を再開するという解決策が考えられます。代替案として一部の実装ではバスリセットを行い、すべてのデバイスを再検出する方法もあります。

  3. タイムアウト: チャネル準備やクロック停止準備などの複数のケースにおいて、バスドライバーはレジスタフィールドをポーリングし、それが「NotFinished」値のゼロに遷移するまで待つ必要があります。MIPI SoundWire仕様1.1ではタイムアウトが定義されていませんが、MIPI SoundWire DisCoドキュメントではタイムアウトに関する推奨事項が追加されています。このような設定が完了しなかった場合、ドライバーは-ETIMEOUTを返します。このようなタイムアウトは故障したスレーブデバイスの症状であり、復旧が困難な可能性があります。

グローバル再構成シーケンス中のエラーは極めて取り扱いが難しいです：

  1. バンクスイッチ: バンクスイッチコマンドの最後のエラーは逆引きが困難です。単一セグメント設定ではバンクスイッチコマンドの再送が可能ですが、複数のバスセグメントを有効化する際には同期問題が発生する可能性があります（フレーム再構成などの副作用を持つコマンドは異なるタイミングで処理されるため）。このような場合、グローバルハードリセットが最善の解決策となるかもしれません。

SoundWireは、有効なレジスタに不正な値が書き込まれたことを検出するメカニズムを提供していません。複数のケースにおいて、標準はスレーブデバイスが実装定義の方法で動作する可能性を明記しています。バス実装はこのようなエラーに対する回復メカニズムを提供せず、スレーブまたはマスタードライバーの実装者は有効なレジスタに有効な値を書き込み、必要に応じて追加の範囲チェックを実装する責任があります。

新しいドライバモデルへのドライバ移植¶

Patrick Mochel

2003年1月7日

概要

参照してください Documentation/driver-api/driver-model/*.rst さまざまなドライバの種類や概念の定義に使用されます。

新しいモデルへのデバイスドライバの移植の主な作業は、バスドライバ層で行われます。これは、カーネルドライバへの悪影響を最小限に抑え、バスドライバの段階的な移行を可能にするため、意図的に設計されています。

要約すると、ドライバモデルは、バス固有のオブジェクトに埋め込まれる複数のオブジェクトからなり、これらの汎用オブジェクトのフィールドはバス固有のオブジェクトのフィールドを置き換えることができます。

汎用オブジェクトはドライバモデルコアに登録する必要があります。これにより、sysfsファイルシステム経由でエクスポートされます。sysfsは以下のコマンドでマウントできます：

# mount -t sysfs sysfs /sys

プロセス

ステップ0: include/linux/device.h を読み込み、オブジェクトと関数の定義を確認します。

ステップ1: バスドライバの登録。

  • バスドライバ用の struct bus_type を定義します：

    struct bus_type pci_bus_type = {
      .name           = "pci",
};

  • バスタイプを登録します。

    これは、バスタイプの初期化関数で行われるべきです。通常は、 module_init()、または同等の関数:

    static int __init pci_driver_init(void)
{
        return bus_register(&pci_bus_type);
}

subsys_initcall(pci_driver_init);

    バスの種類が登録されていない可能性があります（バスドライバーがモジュールとしてコンパイルされる場合）。

    bus_unregister(&pci_bus_type);

  • 他の人が使用できるようにバスの種類をエクスポートします。

    他のコードがバスの種類を参照したい場合、共有ヘッダーファイルに宣言し、シンボルをエクスポートします。

include/linux/pci.h から:

extern struct bus_type pci_bus_type;

上記のコードが含まれているファイルから:

EXPORT_SYMBOL(pci_bus_type);

  • これにより、バスが /sys/bus/pci/ に表示され、'devices' と 'drivers' の2つのサブディレクトリが作成されます:

    # tree -d /sys/bus/pci/
/sys/bus/pci/
|-- devices
`-- drivers

ステップ2: デバイスの登録。

struct device これは単一のデバイスを表し、デバイスが他のエンティティと関連付けられている関係を記述するメタデータを主に含みます。

  • 埋め込む struct device バス固有のデバイスタイプ内に:

    struct pci_dev {
       ...
       struct  device  dev;            /* Generic device interface */
       ...
};

    構造体の最初の項目として一般的なデバイスを配置しないことが推奨されます。これにより、オブジェクトタイプ間での無駄なキャストをプログラマが行わないようにします。代わりに、マクロまたはインライン関数を作成して、一般的なオブジェクトタイプから変換する必要があります:

    #define to_pci_dev(n) container_of(n, struct pci_dev, dev)

or

static inline struct pci_dev * to_pci_dev(struct kobject * kobj)
{
    return container_of(n, struct pci_dev, dev);
}

    これにより、コンパイラが実行される操作の型安全性を検証できます（これは良いことです）。

  • 登録時にデバイスを初期化します。

    バスの種類にデバイスが検出されたり登録されたりする際、バスドライバーは一般的なデバイスを初期化する必要があります。初期化すべき重要な項目は、bus_id、parent、bus フィールドです。

    bus_id は、バス上のデバイスのアドレスを含む ASCII 文字列です。この文字列の形式はバス固有です。sysfs でデバイスを表すために必要です。

    parentはデバイスの物理的な親です。バスドライバーがこのフィールドを正しく設定することが重要です。

    ドライバーモデルは、電源管理のために使用するデバイスの順序付きリストを保持しています。このリストは、デバイスが物理的な親よりも先にシャットダウンされるように、また逆もまた真なり、順序を保つ必要があります。このリストの順序は登録されたデバイスの親によって決定されます。

    また、デバイスのsysfsディレクトリの位置もデバイスの親に依存します。sysfsはデバイス階層を反映するディレクトリ構造をエクスポートします。親を正しく設定することで、sysfsが階層を正確に表現できるようになります。

    デバイスのbusフィールドは、デバイスが属するバスタイプへのポインタです。これは、以前に宣言・初期化されたbus_typeに設定する必要があります。

    オプションで、バスドライバーがデバイスのnameとreleaseフィールドを設定することもできます。

    nameフィールドは、デバイスを記述するASCII文字列で、例えば

    「ATI Technologies Inc Radeon QD」

    releaseフィールドは、ドライバーモデルコアがデバイスが除去され、すべての参照が解放されたときに呼び出すコールバックです。この点については後ほど詳しく説明します。

  • デバイスを登録します。

    一般的なデバイスが初期化されると、ドライバーモデルコアに登録するために以下を行います:

    device_register(&dev->dev);

    その後、以下を行って登録を解除できます:

    device_unregister(&dev->dev);

    これはホットプラグ可能なデバイスをサポートするバスで行われるべきです。バスドライバーがデバイスを登録解除した場合、すぐに解放すべきではありません。代わりに、ドライバーモデルコアがデバイスのreleaseメソッドを呼び出すのを待ってから、バス固有のオブジェクトを解放する必要があります。(デバイス構造に参照している他のコードが存在する可能性があり、その間デバイスを解放するのは失礼です)。

    デバイスが登録されると、sysfsにディレクトリが作成されます。sysfs内のPCIツリーは以下のようになります:

    /sys/devices/pci0/
|-- 00:00.0
|-- 00:01.0
|   `-- 01:00.0
|-- 00:02.0
|   `-- 02:1f.0
|       `-- 03:00.0
|-- 00:1e.0
|   `-- 04:04.0
|-- 00:1f.0
|-- 00:1f.1
|   |-- ide0
|   |   |-- 0.0
|   |   `-- 0.1
|   `-- ide1
|       `-- 1.0
|-- 00:1f.2
|-- 00:1f.3
`-- 00:1f.5

    また、バスの「devices」ディレクトリ内にシンボリックリンクが作成され、物理階層内のデバイスディレクトリにポイントします:

    /sys/bus/pci/devices/
|-- 00:00.0 -> ../../../devices/pci0/00:00.0
|-- 00:01.0 -> ../../../devices/pci0/00:01.0
|-- 00:02.0 -> ../../../devices/pci0/00:02.0
|-- 00:1e.0 -> ../../../devices/pci0/00:1e.0
|-- 00:1f.0 -> ../../../devices/pci0/00:1f.0
|-- 00:1f.1 -> ../../../devices/pci0/00:1f.1
|-- 00:1f.2 -> ../../../devices/pci0/00:1f.2
|-- 00:1f.3 -> ../../../devices/pci0/00:1f.3
|-- 00:1f.5 -> ../../../devices/pci0/00:1f.5
|-- 01:00.0 -> ../../../devices/pci0/00:01.0/01:00.0
|-- 02:1f.0 -> ../../../devices/pci0/00:02.0/02:1f.0
|-- 03:00.0 -> ../../../devices/pci0/00:02.0/02:1f.0/03:00.0
`-- 04:04.0 -> ../../../devices/pci0/00:1e.0/04:04.0

ステップ3: ドライバの登録。

struct device_driverは、ドライバーモデルコアが呼び出す操作を含むシンプルなドライバ構造体です。

  • バス固有のドライバーにstruct device_driverを埋め込みます。

    デバイス同様に、以下のようにします:

    struct pci_driver {
       ...
       struct device_driver    driver;
};

  • 一般的なドライバ構造体を初期化します。

    ドライバーがバスに登録される際（例: pci_register_driver()を行う際）、ドライバーのnameとbusフィールドを必要に応じて初期化します。

  • ドライバーを登録します。

    一般的なドライバーが初期化されると、以下を行います:

    driver_register(&drv->driver);

    コアにドライバーを登録します。

    バスからドライバーがアンレジストレーションされた場合、コアからアンレジストレーションするには以下を行います:

    driver_unregister(&drv->driver);

    ドライバーへの参照がすべて解除されるまでブロックします。通常はこれはありません。

  • Sysfs表現。

    ドライバーは、バスの「driver」ディレクトリ内にsysfsを通じてエクスポートされます。例えば:

    /sys/bus/pci/drivers/
|-- 3c59x
|-- Ensoniq AudioPCI
|-- agpgart-amdk7
|-- e100
`-- serial

ステップ4: ドライバー用の汎用メソッドを定義する。

struct device_driverは、ドライバーモデルコアが呼び出す操作のセットを定義します。これらの操作の多くは、バスがすでにドライバーに対して定義している操作と似ていますが、異なるパラメータを取る場合があります。

バス上のすべてのドライバーを同時に汎用形式に変換するという作業は困難で煩雑です。代わりに、バスドライバーは、バス固有のドライバーに呼び出しが転送される汎用メソッドの単一インスタンスを定義すべきです。例えば:

static int pci_device_remove(struct device * dev)
{
        struct pci_dev * pci_dev = to_pci_dev(dev);
        struct pci_driver * drv = pci_dev->driver;

        if (drv) {
                if (drv->remove)
                        drv->remove(pci_dev);
                pci_dev->driver = NULL;
        }
        return 0;
}

汎用ドライバーは、登録される前にこれらのメソッドで初期化される必要があります:

/* initialize common driver fields */
drv->driver.name = drv->name;
drv->driver.bus = &pci_bus_type;
drv->driver.probe = pci_device_probe;
drv->driver.resume = pci_device_resume;
drv->driver.suspend = pci_device_suspend;
drv->driver.remove = pci_device_remove;

/* register with core */
driver_register(&drv->driver);

理想的には、バスはすでに設定されている場合を除き、フィールドを初期化する必要があります。これにより、ドライバーが独自の汎用メソッドを実装できるようになります。

ステップ5: 汎用ドライバーのバインディングをサポートする。

このモデルは、デバイスやドライバーがいつでもバスに動的に登録できると想定しています。登録が行われる際には、デバイスがドライバーにバインドされるか、またはドライバーがサポートするすべてのデバイスにバインドされる必要があります。

ドライバーは通常、サポートするデバイスIDの一覧を含みます。バスドライバーは、これらのIDを、自身に登録されたデバイスのIDと比較します。デバイスIDの形式や比較のセマンティクスはバス固有のため、汎用モデルはこれらを一般化しようとはしません。

代わりに、バスはstruct bus_typeにmatchメソッドを提供することで比較を行います:

int (*match)(struct device * dev, struct device_driver * drv);

matchは、ドライバーがデバイスをサポートする場合に正の値を返し、それ以外はゼロを返します。ドライバーがデバイスをサポートするかどうかを判断できない場合は、エラーコード（例えば-EPROBE_DEFER）を返すこともできます。

デバイスが登録されるとき、バスのドライバー一覧が繰り返されます。各ドライバーに対してbus->match()が呼び出され、マッチが見つかるまで続けられます。

ドライバーが登録されるとき、バスのデバイス一覧が繰り返されます。各デバイスに対してbus->match()が呼び出され、すでにドライバーによってclaimされているデバイスは除かれます。

デバイスがドライバーに成功裏にバインドされた場合、device->driverが設定され、デバイスがドライバーのデバイス一覧に追加され、ドライバーのsysfsディレクトリにデバイスの物理ディレクトリを指すシンリンクが作成されます:

/sys/bus/pci/drivers/
|-- 3c59x
|   `-- 00:0b.0 -> ../../../../devices/pci0/00:0b.0
|-- Ensoniq AudioPCI
|-- agpgart-amdk7
|   `-- 00:00.0 -> ../../../../devices/pci0/00:00.0
|-- e100
|   `-- 00:0c.0 -> ../../../../devices/pci0/00:0c.0
`-- serial

このドライバーのバインディングは、バスが現在使用している既存のドライバーのバインディングメカニズムを置き換えるべきです。

ステップ6: ホットプラグコールバックを提供します。

ドライバーモデルコアにデバイスが登録されるたびに、ユーザー空間のプログラム /sbin/hotplug が呼び出され、ユーザー空間に通知されます。ユーザーは、デバイスが挿入または除去されるときに実行するアクションを定義できます。

ドライバーモデルコアは、環境変数を介してユーザー空間に複数の引数を渡します。その中には、

  • ACTION: 'add' または 'remove' に設定します

  • DEVPATH: sysfs 内のデバイスの物理的なパスに設定します。

バスドライバは、ユーザー空間が使用できる追加のパラメータを提供することもできます。これを行うには、バスが struct bus_type 内の 'hotplug' メソッドを実装する必要があります:

int (*hotplug) (struct device *dev, char **envp,
                int num_envp, char *buffer, int buffer_size);

これは /sbin/hotplug が実行される直前に呼び出されます。

ステップ7: バスドライバのクリーンアップ。

汎用的なバス、デバイス、ドライバ構造体は、バスドライバが独自に定義したフィールドを置き換えることができるいくつかのフィールドを提供します。

  • デバイスリスト。

struct bus_type には、バスタイプに登録されたすべてのデバイスの一覧が含まれます。これは、そのバスタイプのすべてのインスタンスにあるデバイスを含みます。バスドライバが使用する内部リストは、この一覧を使用するように置き換えることができます。

コアはこれらのデバイスにアクセスするためのイテレータを提供します:

int bus_for_each_dev(struct bus_type * bus, struct device * start,
                     void * data, int (*fn)(struct device *, void *));

  • ドライバーリスト。

struct bus_type には、それに登録されたすべてのドライバの一覧も含まれます。バスドライバが保持するドライバの内部リストは、この汎用的なリストを使用するように置き換えることができます。

ドライバもデバイスと同様にイテレートできます:

int bus_for_each_drv(struct bus_type * bus, struct device_driver * start,
                     void * data, int (*fn)(struct device_driver *, void *));

詳しくは drivers/base/bus.c を参照してください。

  • rwsem

struct bus_type には、デバイスおよびドライバリストへのすべてのコアアクセスを保護する rwsem が含まれています。バスドライバは内部でこの rwsem を使用でき、バスが保持するデバイスまたはドライバリストにアクセスする際には使用する必要があります。

  • デバイスおよびドライバフィールド。

いくつかのフィールドは struct device struct device_driver にも含まれており、これらのオブジェクトのバス固有の表現に複製されています。バス固有のフィールドは削除して、汎用的なフィールドを優先してください。ただし、これによりバス固有のフィールドを参照するすべてのドライバを修正する必要があります（ただし、それらはすべて1行の変更で済むはずです）。

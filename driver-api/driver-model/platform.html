プラットフォームデバイスとドライバ¶

プラットフォームバスへのドライバーモデルインターフェースについては、<linux/platform_device.h>を参照してください: platform_deviceおよびplatform_driver。この擬似バスは、PCIやUSBなどの形式的に規定された大規模なバスと対照的に、最小限のインフラストラクチャで動作するバスに接続されたデバイスを扱います。これは、多くのシステムオンチッププロセッサで周辺機器を統合するためのバスや、一部の「レガシー」PCインターコネクトに使用されます。

プラットフォームデバイス¶

プラットフォームデバイスは、システム内で通常自律的なエントリティとして現れるデバイスです。これはレガシーのポートベースデバイスやペリフェラルバスへのホストブリッジ、システムオンチッププラットフォームに統合されたほとんどのコントローラーを含みます。これらが共通しているのは、CPUバスからの直接アドレッシングです。まれに、プラットフォームデバイスは他の種類のバスのセグメントを通じて接続されることがあります。しかし、レジスタは依然として直接アドレッシング可能です。

プラットフォームデバイスには名前が割り当てられ、ドライバーのバインディングに使用され、アドレスやIRQなどのリソースの一覧が含まれます:

struct platform_device {
      const char      *name;
      u32             id;
      struct device   dev;
      u32             num_resources;
      struct resource *resource;
};

プラットフォームドライバー¶

プラットフォームドライバーは標準的なドライバーモデルの規約に従い、発見/列挙はドライバー外で処理され、ドライザーはprobe()とremove()メソッドを提供します。電源管理およびシャットダウン通知には標準的な規約を使用します:

struct platform_driver {
      int (*probe)(struct platform_device *);
      int (*remove)(struct platform_device *);
      void (*shutdown)(struct platform_device *);
      int (*suspend)(struct platform_device *, pm_message_t state);
      int (*suspend_late)(struct platform_device *, pm_message_t state);
      int (*resume_early)(struct platform_device *);
      int (*resume)(struct platform_device *);
      struct device_driver driver;
};

probe()は一般的に指定されたデバイスハードウェアが実際に存在することを確認する必要があります。時折、プラットフォームのセットアップコードはその確認ができない場合があります。プローブはデバイスリソース（時計を含む）およびデバイスplatform_dataを使用します。

プラットフォームドライバーは通常の方法で自身を登録します:

int platform_driver_register(struct platform_driver *drv);

あるいは、デバイスがホットプラグ可能でないことがわかっている一般的な状況では、probe()ルーチンは初期化セクションに配置され、ドライバーの実行時メモリフットプリントを減らすことができます:

int platform_driver_probe(struct platform_driver *drv,
                  int (*probe)(struct platform_device *))

カーネルモジュールは複数のプラットフォームドライバーで構成できます。プラットフォームコアはドライバーの登録とアンレジスタを処理するためのヘルパを提供します:

int __platform_register_drivers(struct platform_driver * const *drivers,
                              unsigned int count, struct module *owner);
void platform_unregister_drivers(struct platform_driver * const *drivers,
                                 unsigned int count);

いずれかのドライバーが登録に失敗した場合、その時点までのすべてのドライバーが逆の順序で登録解除されます。注意点として、オーナーパラメータとしてTHIS_MODULEを渡すための便利なマクロがあります:

#define platform_register_drivers(drivers, count)

デバイスの列挙¶

一般的に、プラットフォーム固有（そしてしばしばボード固有）のセットアップコードがプラットフォームデバイスを登録します:

int platform_device_register(struct platform_device *pdev);

int platform_add_devices(struct platform_device **pdevs, int ndev);

一般的なルールは、実際に存在するデバイスのみを登録することですが、一部のケースでは余分なデバイスが登録されることがあります。例えば、カーネルが外部ネットワークアダプターと動作するように構成されている場合があり、そのアダプターがすべてのボードに搭載されていない可能性があります。あるいは、統合されたコントローラーと動作するように構成されていて、一部のボードがその周辺機器に接続していない場合もあります。

一部のケースでは、ブートファームウェアが特定のボードに搭載されているデバイスを記述するテーブルをエクスポートします。このようなテーブルがなければ、システム設定コードが正しいデバイスを設定する方法は、特定のターゲットボード用のカーネルをビルドする以外ありません。このようなボード固有のカーネルは、埋め込みシステムやカスタムシステム開発において一般的です。

多くのケースでは、プラットフォームデバイスに関連するメモリやIRQリソースは、ドライバが動作するのに十分ではありません。ボード設定コードは、通常、デバイスのplatform_dataフィールドを使用して追加情報を提供し、これによりドライバが正しく動作するようにします。

埋め込みシステムは、プラットフォームデバイスに1つまたは複数のクロックを必要とすることが多く、これらは必要になるまでオフに保たれています（電力消費を抑えるため）。システム設定コードはこれらのクロックをデバイスに関連付けるため、clk_get(&pdev->dev, clock_name)の呼び出しが必要に応じてクロックを返すようにします。

レガシドライバー: デバイスプロービング¶

一部のドライバーはドライバーモデルに完全に変換されていない場合があります。これは、ドライバーが非ドライバーの役割を担っているためです。このようなドライバーは、システムインフラストラクチャではなく、自身でプラットフォームデバイスを登録します。そのため、ホットプラグやコールドプラグが実行できません。これらのメカニズムは、ドライバーとデバイス作成が異なるシステムコンポーネントに存在する必要があります。

このようなドライバーの「良い」理由は、古いシステム設計を処理することです。このような設計は、元のIBM PCのように、ハードウェア構成に誤った「ハードウェアプローブ」モデルに依存しています。新しいシステムでは、このモデルをバスレベルでの動的構成サポート（PCI、USB）や、ブートファームウェアが提供するデバイステーブル（例: x86におけるPNPACPI）に置き換えています。どこに何があるかに関する選択肢は多く、OSが推測しても頻繁に誤りが生じるため、トラブルになる可能性があります。

このようなドライバーのスタイルは推奨されません。このようなドライバーを更新する場合は、デバイスの列挙をドライバーの外側に移動するように試してください。これは通常、クリーンアップになります。このようなドライバーはすでに「通常」モードを持っています。例えば、PNPやプラットフォームデバイス設定によって作成されたデバイスノードを使用するものです。

それでも、このようなレガシードライバをサポートするAPIはいくつかあります。これらの呼び出しは、ホットプラグができないドライバ以外では使用しないでください:

struct platform_device *platform_device_alloc(
                const char *name, int id);

使用できます platform_device_alloc() デバイスを動的に割り当て、その後リソースで初期化します。 platform_device_register()より良い解決策は通常、

struct platform_device *platform_device_register_simple(
                const char *name, int id,
                struct resource *res, unsigned int nres);

使用できます platform_device_register_simple() デバイスを割り当てて登録するワンステップの呼び出しとしてです。

デバイスの命名とドライバーバインディング¶

platform_device.dev.bus_idはデバイスの公式な名前です。これは二つのコンポーネントから構成されています:

  • platform_device.name … ドライバーマッチングにも使用されます。

  • platform_device.id … デバイスインスタンス番号、または「-1」で1つのみを示します。

これらは連結されるため、名前/id「serial」/0はbus_id「serial.0」、および「serial/3」はbus_id「serial.3」を示します。どちらもplatform_driver名「serial」を使用します。一方、「my_rtc」/-1はbus_id「my_rtc」（インスタンス番号なし）で、platform_driver名「my_rtc」を使用します。

ドライバーバインディングはドライバーコアが自動的に実行し、デバイスとドライバーのマッチングを確認した後、driver probe()を呼び出します。probe()が成功すれば、ドライバーとデバイスは通常通りバインドされます。このようなマッチングは以下の3つの方法があります:

  • デバイスが登録されるたびに、そのバスのドライバーがマッチングを確認します。プラットフォームデバイスはシステム起動の初期段階で登録する必要があります。

  • platform_driver_register()でドライバーを登録すると、そのバス上の未バインドのデバイスがマッチングを確認します。ドライバーは通常、起動の後半で登録するか、モジュールロードによって登録します。

  • platform_driver_probe()でドライバーを登録すると、platform_driver_register()と同様ですが、他のデバイスが登録された後でもプローブされません。(これは非ホットプラグ可能なデバイス専用のインターフェースであるため、問題ありません。)

早期プラットフォームデバイスとドライバー¶

早期プラットフォームインターフェースは、システム起動の初期段階でプラットフォームデバイスドライバーにプラットフォームデータを提供します。コードはearly_param()コマンドラインパースの上に構築されており、非常に早期に実行可能です。

例: 「earlyprintk」クラスの早期シリアルコンソールの6段階

1. 早期プラットフォームデバイスデータの登録¶

アーキテクチャコードはearly_platform_add_devices()関数を使用してプラットフォームデバイスデータを登録します。早期シリアルコンソールの場合、これはシリアルポートのハードウェア構成です。この時点で登録されたデバイスは、後続の早期プラットフォームドライバーとマッチングされます。

2. カーネルコマンドラインの解析¶

アーキテクチャコードは、カーネルコマンドラインを解析するためにparse_early_param()を呼び出します。これにより、すべての一致するearly_param()コールバックが実行されます。ユーザー指定の早期プラットフォームデバイスはこの時点で登録されます。早期シリアルコンソールのケースでは、ユーザーはカーネルコマンドラインでポートを「earlyprintk=serial.0」と指定できます。ここで「earlyprint,」はクラス文字列、「serial」はプラットフォームドライバーの名前、0はプラットフォームデバイスIDです。IDが-1の場合、ドットとIDは省略できます。

3. 特定のクラスに属する早期プラットフォームドライバーのインストール¶

アーキテクチャコードは、特定のクラスに属するすべての早期プラットフォームドライバーの登録をオプションで強制的に実行するため、early_platform_driver_register_all()関数を使用できます。ステップ2でユーザー指定されたデバイスはこれらを優先します。シリアルドライバーの例ではこのステップは省略されています。なぜなら、早期シリアルドライバーのコードはユーザーがカーネルコマンドラインでポートを指定していない限り無効にするべきだからです。

4. 早期プラットフォームドライバーの登録¶

early_platform_init()を使用するコンパイルインプラットフォームドライバーは、ステップ2または3で自動的に登録されます。シリアルドライバーの例ではearly_platform_init(「earlyprintk」, &platform_driver)を使用する必要があります。

5. 特定のクラスに属する早期プラットフォームドライバーのプローブ¶

アーキテクチャコードは、early_platform_driver_probe()を呼び出して、特定のクラスに関連する登録済み早期プラットフォームデバイスを登録済み早期プラットフォームドライバーとマッチングします。マッチしたデバイスはprobed()が実行されます。このステップは早期起動のどの段階でも実行可能です。シリアルポートのケースではなるべく早く実行するのが望ましいです。

6. 早期プラットフォームドライバーのprobe()内¶

ドライバコードは早期起動中に特にメモリ割当と割込み登録に注意を払う必要があります。probe()関数内のコードはis_early_platform_device()を使用して、早期プラットフォームデバイスのタイミングか通常のプラットフォームデバイスのタイミングかを確認できます。早期シリアルドライバーはこの時点でregister_console()を実行します。

詳細については<linux/platform_device.h>を参照してください。

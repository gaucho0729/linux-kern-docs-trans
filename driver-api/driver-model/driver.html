デバイスドライバ¶

struct device_driverに関するkerneldocを参照してください。

割当¶

デバイスドライバは静的に割り当てられた構造体です。ドライバがサポートするシステム内のデバイスが複数あっても、struct device_driverはそのドライバ全体を表します（特定のデバイスインスタンスではありません）。

初期化¶

ドライバは少なくともnameとbusフィールドを初期化する必要があります。また、devclassフィールド（到達時に）も初期化すべきです。これにより、内部で適切なリンクを取得できます。可能な限り多くのコールバックを初期化すべきですが、それぞれはオプションです。

宣言¶

上記のように、struct device_driverオブジェクトは静的に割り当てられます。以下はeepro100ドライバの例的な宣言です。これは仮想的な例であり、ドライバが新しいモデルに完全に変換されていることを前提としています：

static struct device_driver eepro100_driver = {
       .name          = "eepro100",
       .bus           = &pci_bus_type,

       .probe         = eepro100_probe,
       .remove                = eepro100_remove,
       .suspend               = eepro100_suspend,
       .resume                = eepro100_resume,
};

ほとんどのドライバは、所属するバスがバス固有の構造体を持ち、そのフィールドが一般化できないため、新しいモデルに完全に変換できません。

このような例として、デバイスID構造体があります。ドライバは通常、サポートするデバイスIDの配列を定義します。これらの構造体のフォーマットや、デバイスIDを比較するセマンティクスは完全にバス固有です。バス固有のエンティティとして定義すると型安全性が失われるため、バス固有の構造体は保持します。

バス固有のドライバは、バス固有のドライバ定義内で汎用的なstruct device_driverを含める必要があります。以下のように：

struct pci_driver {
       const struct pci_device_id *id_table;
       struct device_driver     driver;
};

バス固有のフィールドを含む定義は（再びeepro100ドライバを使用して）以下のようになります：

static struct pci_driver eepro100_driver = {
       .id_table       = eepro100_pci_tbl,
       .driver               = {
              .name           = "eepro100",
              .bus            = &pci_bus_type,
              .probe          = eepro100_probe,
              .remove         = eepro100_remove,
              .suspend        = eepro100_suspend,
              .resume         = eepro100_resume,
       },
};

一部の人にとっては、埋め込まれた構造体の初期化の構文が不自然に感じたり、少し醜く感じたりするかもしれません。現時点では、私たちが望むことを実現するための最良の方法です…

登録¶

int driver_register(struct device_driver *drv);

ドライバは起動時に構造体を登録します。バス固有のフィールドを持たないドライバ（つまり、バス固有のドライバ構造体を持たないドライバ）はdriver_registerを使用し、struct device_driverオブジェクトへのポインタを渡します。

しかし、ほとんどのドライバはバス固有の構造体を持ち、バスに登録するためにpci_driver_registerのような関数を使用する必要があります。

ドライバがドライバ構造体をできるだけ早く登録することが重要です。コアとの登録は、struct device_driverオブジェクト内のいくつかのフィールド（参照カウントとロックを含む）を初期化します。これらのフィールドは常に有効とみなされ、デバイスモデルコアやバスドライバによって使用される可能性があります。

バスドライバーの移行¶

ラッパー関数を定義することで、新しいモデルへの移行をより容易にできます。ドライバはジェネリックな構造を無視し、バスのラッパーがフィールドを埋めてくれるようすることで、コールバックについてはバスがジェネリックなコールバックを定義し、ドライバのバス固有のコールバックに呼び出すことができます。

この解決策は一時的なものとされています。ドライバにクラス情報が取得されるためには、ドライバ自体を修正する必要があります。ドライバを新しいモデルに変換することでインフラストラクチャの複雑さやコードサイズが削減されるため、クラス情報が追加されるにつれて変換することをお勧めします。

アクセス¶

オブジェクトが登録されると、そのオブジェクトの共通フィールド、例えばロックやデバイスの一覧にアクセスできます：

int driver_for_each_dev(struct device_driver *drv, void *data,
                        int (*callback)(struct device *dev, void *data));

デバイスフィールドは、ドライバにバインドされたすべてのデバイスの一覧です。LDMコアは、ドライバが制御するすべてのデバイスに対して操作を行うヘルパー関数を提供します。このヘルパー関数は、各ノードアクセスごとにドライバをロックし、デバイスにアクセスするたびに適切な参照カウントを管理します。

sysfs¶

ドライバが登録されると、そのバスのディレクトリ内にsysfsディレクトリが作成されます。このディレクトリ内では、ドライバがユーザースペースに対してドライバのグローバルな操作を制御するインターフェースをエクスポートできます。たとえば、ドライバ内のデバッグ出力のトグル操作などが挙げられます。

このディレクトリの今後の機能として、「デバイス」ディレクトリが追加される予定です。このディレクトリには、サポートしているデバイスのディレクトリへのシンボリックリンクが含まれます。

コールバック¶

int     (*probe)        (struct device *dev);

probe()エントリはタスクコンテキストで呼び出され、バスのrwsemがロックされ、ドライバがデバイスに部分的にバインドされている状態で呼び出されます。ドライバは通常、 container_of() を用いて「dev」をバス固有の型に変換します。probe()やその他のルーチンでも同様に使用されます。この型は、pci_dev.resource[]やplatform_device.resourcesなどのデバイスリソースデータを提供し、dev->platform_dataと併せてドライバの初期化に使用されます。

このコールバックは、ドライバを指定されたデバイスにバインドするドライバ固有のロジックを保持します。これは、デバイスが存在すること、ドライバが処理可能なバージョンであること、ドライバデータ構造が割り当てられ初期化できること、ハードウェアが初期化できることを確認します。ドライバは通常、dev_set_drvdata()を用いて自身の状態へのポインタを保存します。ドライバが指定されたデバイスに成功裏にバインドした場合、probe()はゼロを返し、ドライバモデルコードがドライバのそのデバイスへのバインドを完了します。

ドライバのprobe()は、ドライバがこのデバイスにバインドできなかった場合、負のerrno値を返してその旨を示すことができます。その場合、ドライバはすでに確保したすべてのリソースを解放しておく必要があります。

probe()は、ドライバがまだ利用できないリソースに依存している場合（例：まだ初期化されていないドライバが提供するリソースなど）、-EPROBE_DEFERを返すことができます。ドライバコアはこのデバイスをdeferred probeリストに登録し、後で再度呼び出します。ドライバがdeferを必要とする場合、deferをできるだけ早く-EPROBE_DEFERを返すことで、後で解除・再実行が必要なセットアップ作業の時間を減らすことができます。

警告

probe()がすでに子デバイスを生成している場合、-EPROBE_DEFERを返してはなりません。その子デバイスがクリーンアップパスで再び削除されたとしてもです。子デバイスが登録された後で-EPROBE_DEFERを返すと、同じドライバへの.probe()呼び出しの無限ループを引き起こす可能性があります。

void    (*sync_state)   (struct device *dev);

sync_stateはデバイスごとに1回だけ呼び出されます。このデバイスのすべての消費者デバイスが正常にprobeした後に呼び出されます。このデバイスの消費者デバイス一覧は、このデバイスと消費者デバイスを結ぶデバイスリンクを調べることで取得します。

sync_state()の最初の呼び出しはlate_initcall_sync()のタイミングで行われ、ファームウェアやドライバがデバイス同士をリンクする時間を作ります。最初のsync_state()呼び出し時に、このデバイスのすべての消費者デバイスがすでに正常にprobeした場合、sync_state()は即座に呼び出されます。最初の呼び出し時にこのデバイスに消費者デバイスが存在しない場合でも、「すべての消費者デバイスがprobeした」とみなされ、sync_state()は即座に呼び出されます。

デバイスのsync_state()呼び出しの最初の試行中に、まだprobeに成功していない消費者デバイスが存在する場合、sync_state()の呼び出しは延期され、将来、1つ以上の消費者デバイスが成功したときに再試行されます。再試行中にドライバコアが、まだprobeされていない消費者デバイスが存在することを発見した場合、sync_state()の呼び出しは再度延期されます。

sync_state()の典型的な使用例は、カーネルがブートロー�ーダーからデバイスの管理をスムーズに引き継ぐことです。たとえば、ブートローダーによってデバイスが特定のハードウェア構成で起動状態に残されている場合、そのデバイスのドライバーは、すべてのデバイス利用者（consumer）がプローブ（検出）を完了するまで、デバイスをブート時の構成状態に維持する必要があります。すべての利用者がプローブを終えたら、ドライバーはデバイスのハードウェア状態を、すべての利用者が要求したソフトウェア状態と同期させます。これがsync_state()という名前の由来です。

sync_state()が有効なリソースの例として明らかに挙げられるのは、レギュレータ（regulator）などのリソースですが、IOMMUなどの複雑なリソースにも有効です。たとえば、複数の利用者が存在するIOMMU（デバイスのアドレスがIOMMUによって再マッピングされるデバイス）は、すべての利用者がプローブを完了するまで、ブート時の構成状態にマッピングを固定（または追加）しておく必要があります。

sync_state()の典型的な使用例は、カーネルがブートローダーからデバイスの管理をスムーズに引き継ぐことです。ただし、sync_state()の使用はこの用途に限定されません。デバイスのすべての利用者がプローブを終えた後に行動を起こす必要がある場合は、いつでも使用してください。

int     (*remove)       (struct device *dev);

removeは、ドライバーをデバイスから解除するための関数です。これは、デバイスが物理的にシステムから外された場合、ドライバーモジュールがアンロードされる場合、再起動シーケンス中に呼び出される場合、またはその他の状況で呼び出されることがあります。

デバイスがまだ接続されているかどうかは、ドライバーが判断する必要があります。ドライバーは、デバイスに特有に割り当てられたリソースをすべて解放する必要があります。つまり、デバイスのdriver_dataフィールドに記録されているすべてのリソースを解放してください。

デバイスがまだ接続されている場合、ドライバーはデバイスを停止状態（クイエス）にし、サポートされている低電力状態に移行する必要があります。

int     (*suspend)      (struct device *dev, pm_message_t state);

suspendは、デバイスを低電力状態に移すための関数です。

int     (*resume)       (struct device *dev);

resumeは、デバイスを低電力状態から復元するための関数です。

属性¶

struct driver_attribute {
        struct attribute        attr;
        ssize_t (*show)(struct device_driver *driver, char *buf);
        ssize_t (*store)(struct device_driver *, const char *buf, size_t count);
};

デバイスドライバーは、sysfsディレクトリを通じて属性をエクスポートできます。ドライバーは、DEVICE_ATTR_RWとDEVICE_ATTR_ROマクロと同等の動作をするDRIVER_ATTR_RWとDRIVER_ATTR_ROマクロを使用して属性を宣言できます。

例:

DRIVER_ATTR_RW(debug);

これは次の宣言に等しいです：

struct driver_attribute driver_attr_debug;

これにより、ドライバーのディレクトリから属性を追加または削除できます。

int driver_create_file(struct device_driver *, const struct driver_attribute *);
void driver_remove_file(struct device_driver *, const struct driver_attribute *);

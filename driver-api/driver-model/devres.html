Devres - 管理されたデバイスリソース¶

Tejun Heo <teheo@suse.de>

初版 2007年1月10日

1. はじめに¶

devres は libata を iomap に変換しようとした際に登場しました。各 iomapped アドレスはドライバの接続解除時に保持され解放される必要があります。例えば、SFF ATA コントローラー（つまり、古き良き PCI IDE）はネイティブモードで5つのPCI BARを使用し、これらすべてを維持する必要があります。

多くのデバイスドライバと同様に、libata の低レベルドライバは ->remove および ->probe 失敗時の処理に十分なバグがあります。ええ、おそらくそれは libata の低レベルドライバ開発者たちが怠け者だからでしょうが、すべての低レベルドライバ開発者がそうなのでしょうか？一日中、ドキュメントもなければ壊れたハードウェアと戦って、それがようやく動くようになったら、動くのだからいいのです。

何かしらの理由で、低レベルドライバはコアコードほど注目やテストを受けていません。ドライバの接続解除や初期化失敗時のバグは頻繁に発生しないので気づきにくいです。初期化失敗時の処理はさらに悪化しています。それはあまり使われない経路であり、複数のエントリポイントを処理しなければならないからです。

そのため、多くの低レベルドライバはドライバ接続解除時にリソースをリークし、->probe() の半分だけ実装された失敗時の処理でリソースをリークしたり、エラーが発生した際にオプス（oops）を引き起こすことがあります。iomap はこの問題をさらに悪化させます。msi と msix も同様です。

2. Devres¶

devres は、任意のサイズのメモリ領域のリンクリストであり、 struct device各 devres エントリは解放関数と関連付けられています。devres はいくつかの方法で解放できます。どの方法でも、ドライバの接続解除時にすべての devres エントリが解放されます。解放時に関連する解放関数が呼び出され、その後 devres エントリが解放されます。

devres を使用して、デバイスドライバーでよく使用されるリソースの管理インターフェースが作成されています。例えば、コヒーレントDMAメモリは dma_alloc_coherent() で取得されますが、管理版は dmam_alloc_coherent() と呼ばれます。これは dma_alloc_coherent() とほぼ同じですが、DMAメモリは管理され、ドライバの接続解除時に自動的に解放されます。実装は以下のようになります：

struct dma_devres {
      size_t          size;
      void            *vaddr;
      dma_addr_t      dma_handle;
};

static void dmam_coherent_release(struct device *dev, void *res)
{
      struct dma_devres *this = res;

      dma_free_coherent(dev, this->size, this->vaddr, this->dma_handle);
}

dmam_alloc_coherent(dev, size, dma_handle, gfp)
{
      struct dma_devres *dr;
      void *vaddr;

      dr = devres_alloc(dmam_coherent_release, sizeof(*dr), gfp);
      ...

      /* alloc DMA memory as usual */
      vaddr = dma_alloc_coherent(...);
      ...

      /* record size, vaddr, dma_handle in dr */
      dr->vaddr = vaddr;
      ...

      devres_add(dev, dr);

      return vaddr;
}

ドライバーが dmam_alloc_coherent() を使用する場合、初期化が途中で失敗しても、デバイスが接続解除されても、領域が確実に解放されます。ほとんどのリソースを管理インターフェースで取得する場合、ドライバーは初期化と終了処理を大幅に簡略化できます。初期化処理は以下のようになります：

my_init_one()
{
      struct mydev *d;

      d = devm_kzalloc(dev, sizeof(*d), GFP_KERNEL);
      if (!d)
              return -ENOMEM;

      d->ring = dmam_alloc_coherent(...);
      if (!d->ring)
              return -ENOMEM;

      if (check something)
              return -EINVAL;
      ...

      return register_to_upper_layer(d);
}

そして、終了処理:

my_remove_one()
{
      unregister_from_upper_layer(d);
      shutdown_my_hardware();
}

上記のように、devresを使用することで低レベルドライバは大幅に簡略化できます。複雑さは、保守が不十分な低レベルドライバから、保守がより良い高層へと移されます。また、初期化失敗の処理と終了処理が共有されているため、両方の処理がより多くのテストを受けやすくなります。

ただし、現在の呼び出しや割り当てを管理されたdevm_*バージョンに変換する際には、メモの割り当てなどの内部操作が失敗したかどうかを確認するのはあなたの責任です。管理されたリソースとは、これらのリソースの解放に関連します。 のみ - 他の必要なチェックも依然としてあなたの責任です。一部のケースでは、管理されたdevm_*呼び出しに移行する前には必要なかったチェックを導入する必要があります。

3. Devresグループ¶

Devresエントリはdevresグループを使用してグループ化できます。グループが解放されると、含まれる通常のdevresエントリと適切にネストされたグループもすべて解放されます。1つの用途は、失敗時に一連の取得されたリソースをロールバックすることです。例えば：

 if (!devres_open_group(dev, NULL, GFP_KERNEL))
       return -ENOMEM;

 acquire A;
 if (failed)
       goto err;

 acquire B;
 if (failed)
       goto err;
 ...

 devres_remove_group(dev, NULL);
 return 0;

err:
 devres_release_group(dev, NULL);
 return err_code;

リソース取得失敗は通常プローブ失敗を意味するため、このような構造はmidlayerドライバ（例：libataコアレイヤー）で特に有用です。midlayerドライバではインターフェース関数が失敗時に副作用を起こすべきではありません。LLDsでは、ほとんどの場合エラーコードを返すだけで十分です。

各グループは void *idで識別されます。これは@id引数で明示的に指定するか、 devres_open_group() にNULLを渡して自動的に生成される場合があります（上記の例参照）。いずれの場合も、 devres_open_group() はグループのidを返します。返されたidは他のdevres関数に渡して対象グループを指定できます。これらの関数にNULLを渡すと、最新のオープングループが選択されます。

例えば、以下のようになります：

int my_midlayer_create_something()
{
      if (!devres_open_group(dev, my_midlayer_create_something, GFP_KERNEL))
              return -ENOMEM;

      ...

      devres_close_group(dev, my_midlayer_create_something);
      return 0;
}

void my_midlayer_destroy_something()
{
      devres_release_group(dev, my_midlayer_create_something);
}

4. 詳細¶

devresエントリのライフタイムはdevres割当から解放または破壊（削除と解放）まで続き、参照カウントは使用しません。

devresコアはすべての基本的なdevres操作に対してアトミック性を保証し、シングルインスタンスdevresタイプ（アトミックな検索と追加の組み合わせ）にも対応しています。それ以外の場合は、割り当てられたdevresデータへの並行アクセスの同期は呼び出し元の責任です。これはバス操作やリソース割当がすでに処理しているため、通常問題になりません。

シングルインスタンスdevresタイプの例として、lib/devres.c内のpcim_iomap_table()を参照してください。

すべてのdevresインターフェース関数は、適切なgfpマスクを指定すればコンテキストなしでも呼び出すことができます。

5. パフォーマンス影響¶

各devresブックキープ情報は要求されたデータエリアとともに割り当てられます。デバッグオプションがオフの場合、32ビットマシンではブックキープ情報が16バイト、64ビットマシンでは24バイトを占めます（3つのポインタをULLアライメントに四捨五入）。シングルリンクリストが使用される場合、これを2つのポインタ（32ビットでは8バイト、64ビットでは16バイト）に減らすことができます。

各devresグループは8つのポインタを占有します。シングルリンクリストが使用される場合、6つに減らすことができます。

AHCIコントローラーの2ポートで、32ビットマシンではナーフィー変換後、メモリ空間のオーバーヘッドは300〜400バイトです（libataコアレイヤーにはさらに効率的な方法があります）。

NAND エラー訂正コード¶

はじめに¶

Linux の mtd/nand ドライバを確認し、特に nand_ecc.c を詳しく見てみた結果、最適化の余地があることに気づきました。数時間かけてコードを吟味し、テーブル検索などの工夫や不要なコードの削除などを行いました。その結果、速度が35〜40％向上しましたが、それでも十分ではなかったと感じました。さらに改善の余地があると感じたからです。

悪い！私はハマってしまいました。このファイルに自分の手順を注釈として残すことにしました。誰かにとって参考になるかもしれないし、誰かが何かを学べるかもしれないからです。

問題¶

NANDフラッシュ（少なくともSLCの場合）は通常、256バイトのセクタを持ちます。しかしNANDフラッシュは極めて信頼性が低いので、エラー検出（および場合によっては訂正）が必要です。

これはハミング符号によって実現されます。私は素人向けに説明を試みますが（専門家の方には適切な用語を使えていない可能性があることをお許しください）、私の符号理論の授業は30年前にあり、あまり好きではなかったことを認めます。

先述した通り、ecc計算は256バイトのセクタに対して行われます。これは行と列ごとに複数のパリティビットを計算することによって実現されます。使用されるパリティは偶数パリティで、データの合計ビット数＋パリティビットが偶数になるようにします（理解できない場合はWikipediaを参照してください）。パリティ計算には排他的論理和（XOR）操作がよく用いられます。C言語では^がXOR演算子です。

この図は256バイトのセクタを表しています。cpは私の略で列パリティ、rpは行パリティを表します。

では、列パリティについて説明を始めましょう。

  • cp0はbit0、bit2、bit4、bit6のすべてに属するパリティです。

    したがって、bit0、bit2、bit4、bit6のすべての値の合計＋cp0自身は偶数になります。

同様にcp1はbit1、bit3、bit5、bit7のすべての合計です。

  • cp2はbit0、bit1、bit4、bit5のパリティです。

  • cp3はbit2、bit3、bit6、bit7のパリティです。

  • cp4はbit0、bit1、bit2、bit3のパリティです。

  • cp5はbit4、bit5、bit6、bit7のパリティです。

cp0〜cp5のそれぞれは、正確に1ビットです。

行パリティは実際にはほぼ同じように動作します。

  • rp0はすべての偶数バイト（0、2、4、6、… 252、254）のパリティです。

  • rp1はすべての奇数バイト（1、3、5、7、…、253、255）のパリティです。

  • rp2は0、1、4、5、8、9、…（2バイトを処理してから2バイトスキップ）のパリティです。

  • rp3はrp2がカバーしない部分（2、3、6、7、10、11、…）をカバーします。

  • rp4のルールは4バイトをカバーしてから4バイトスキップ、4バイトカバーしてから4バイトスキップと続きます。

    したがって、rp4は0、1、2、3、8、9、10、11、16、…のバイトのパリティを計算します。

  • rp5はもう一方の半分をカバーするので、4、5、6、7、12、13、14、15、20、…のバイトです。

この後は物語が非常に退屈になります。おそらくお分かりいただけたでしょう。

  • rp6は8バイトをカバーしてから8バイトスキップしますなど

  • rp7は8バイトスキップしてから8バイトカバーしますなど

  • rp8は16バイトをカバーしてから16バイトスキップしますなど

  • rp9は16バイトスキップしてから16バイトカバーしますなど

  • rp10は32バイトをカバーしてから32バイトスキップしますなど

  • rp11は32バイトスキップしてから32バイトカバーしますなど

  • rp12は64バイトをカバーしてから64バイトスキップしますなど

  • rp13は64バイトスキップしてから64バイトカバーしますなど

  • rp14は128バイトをカバーしてから128バイトスキップします

Analysis 0¶

Cにはビット演算子はあるものの、上記のような効率的な演算を行うための演算子は実際には存在せず（ほとんどのハードウェアも同様の命令を持っていません）、この実装を行わなければ、上のコードがノーベル賞をもたらすことは明らかでした :-)

幸いなことに排他的OR演算は可換性を持ち、値を任意の順序で結合できます。したがって、個別にすべてのビットを計算するのではなく、式を再配置してみましょう。列パリティの場合これは簡単です。単にバイトをXORし、最後に関連するビットのみをフィルタリングすればよいのです。これにより、ループ外でcp計算をすべて実行できるため、非常に効率的です。

同様に、各行のバイトをまずXORしてから処理することもできます。これにより以下のように導かれます:

void ecc1(const unsigned char *buf, unsigned char *code)
{
    int i;
    const unsigned char *bp = buf;
    unsigned char cur;
    unsigned char rp0, rp1, rp2, rp3, rp4, rp5, rp6, rp7;
    unsigned char rp8, rp9, rp10, rp11, rp12, rp13, rp14, rp15;
    unsigned char par;

    par = 0;
    rp0 = 0; rp1 = 0; rp2 = 0; rp3 = 0;
    rp4 = 0; rp5 = 0; rp6 = 0; rp7 = 0;
    rp8 = 0; rp9 = 0; rp10 = 0; rp11 = 0;
    rp12 = 0; rp13 = 0; rp14 = 0; rp15 = 0;

    for (i = 0; i < 256; i++)

        cur = *bp++;
        par ^= cur;
        if (i & 0x01) rp1 ^= cur; else rp0 ^= cur;

まだ比較的ストレートです。最後の3つの反転ステートメントは、空のフラッシュにおけるチェックサムが 0xff 0xff 0xff になるようにするためのものです。空のフラッシュではすべてのデータが 0xff なので、チェックサムは一致します。

また、パリティ検索を導入しました。この方法がパリティを計算する最も高速な方法だと予想していましたが、後で代替案を検討する予定です。

分析 1¶

コードは動作しますが、非常に効率的ではありません。私のシステムでは、Linux ドライバコードと比べてほぼ4倍の時間がかかりました。しかし、もし簡単だったなら、ずっと以前に実装されていたでしょう。痛みがないと得られないのです。 これ easy this would have been done long before. No pain. no gain.

幸いにも改善の余地は十分あります。

ステップ1ではビット単位の計算からバイト単位の計算に移行しました。しかしC言語では符号なしの long データ型を使用することもでき、ほぼすべての現代のマイクロプロセッサが32ビット演算をサポートしているため、なぜ32ビット単位でデータを処理するコードを書かないのか不思議です。

もちろん、行パリティがバイト単位で計算されるため、いくつかの修正が必要です。簡易な分析：列パリティには par 変数を使用します。32ビットに拡張する際、最終的に rp0 と rp1 を簡単に計算できます。(par は4バイトから成り、MSBからLSBへ rp1, rp0, rp1, rp0 にそれぞれ寄与します) また、rp2 と rp3 も par から簡単に取得できます。rp3 は最初の2つのMSBをカバーし、rp2 は最後の2つのLSBをカバーします。

ループが現在は64回しか実行されないことに注意してください（256/4）。また、バイトの順序に関する注意が必要です。long型のバイトの順序はマシン依存であり、私たちに影響を与える可能性があります。いずれにせよ、問題が生じた場合は、このコードはx86（正確にはDELL PCのD920 Intel CPU）で開発されています。

パフォーマンスはアライメントに依存するかもしれませんが、nandドライバのI/Oバッファが適切にアライメントされていると想定しています（そうでない場合は最大パフォーマンスを得るために修正する必要があります）。

extern const char parity[256];

void ecc2(const unsigned char *buf, unsigned char *code)
{
    int i;
    const unsigned long *bp = (unsigned long *)buf;
    unsigned long cur;
    unsigned long rp0, rp1, rp2, rp3, rp4, rp5, rp6, rp7;
    unsigned long rp8, rp9, rp10, rp11, rp12, rp13, rp14, rp15;
    unsigned long par;

    par = 0;
    rp0 = 0; rp1 = 0; rp2 = 0; rp3 = 0;
    rp4 = 0; rp5 = 0; rp6 = 0; rp7 = 0;
    rp8 = 0; rp9 = 0; rp10 = 0; rp11 = 0;
    rp12 = 0; rp13 = 0; rp14 = 0; rp15 = 0;

    for (i = 0; i < 64; i++)
    {
        cur = *bp++;
        par ^= cur;
        if (i & 0x01) rp5 ^= cur; else rp4 ^= cur;
        if (i & 0x02) rp7 ^= cur; else rp6 ^= cur;
        if (i & 0x04) rp9 ^= cur; else rp8 ^= cur;
        if (i & 0x08) rp11 ^= cur; else rp10 ^= cur;
        if (i & 0x10) rp13 ^= cur; else rp12 ^= cur;
        if (i & 0x20) rp15 ^= cur; else rp14 ^= cur;
    }
    /*
       we need to adapt the code generation for the fact that rp vars are now
       long; also the column parity calculation needs to be changed.
       we'll bring rp4 to 15 back to single byte entities by shifting and
       xoring
    */

    rp5 ^= (rp5 >> 16); rp5 ^= (rp5 >> 8); rp5 &= 0xff;
    rp6 ^= (rp6 >> 16); rp6 ^= (rp6 >> 8); rp6 &= 0xff;
    rp7 ^= (rp7 >> 16); rp7 ^= (rp7 >> 8); rp7 &= 0xff;
    rp8 ^= (rp8 >> 16); rp8 ^= (rp8 >> 8); rp8 &= 0xff;
    rp9 ^= (rp9 >> 16); rp9 ^= (rp9 >> 8); rp9 &= 0xff;
    rp10 ^= (rp10 >> 16); rp10 ^= (rp10 >> 8); rp10 &= 0xff;

    rp14 ^= (rp14 >> 16); rp14 ^= (rp14 >> 8); rp14 &= 0xff;
    rp15 ^= (rp15 >> 16); rp15 ^= (rp15 >> 8); rp15 &= 0xff;
    rp3 = (par >> 16); rp3 ^= (rp3 >> 8); rp3 &= 0xff;
    rp2 = par & 0xffff; rp2 ^= (rp2 >> 8); rp2 &= 0xff;
    par ^= (par >> 16);
    rp1 = (par >> 8); rp1 &= 0xff;
    rp0 = (par & 0xff);
    par ^= (par >> 8); par &= 0xff;

        (parity[rp6] << 6) |
        (parity[rp5] << 5) |
        (parity[rp4] << 4) |
        (parity[rp3] << 3) |
        (parity[rp2] << 2) |
        (parity[rp1] << 1) |
        (parity[rp0]);

        (parity[rp12] << 4) |

        (parity[rp10] << 2) |

パリティ配列はもう表示されません。また、これらの例では、通常のプログラミングスタイルから多少逸脱しています。1行に複数のステートメントを許可し、then/elseブロックで単一のステートメントのみを使用し、^=などの演算子を使用している点です。

分析2¶

コード（もちろん）は動作し、素晴らしい！私たちはLinuxドライバコードよりも少し速い（約15％）。しかし、待ってください、すぐに喜んではいけません。さらに改善の余地があります。rp14とrp15を見てみると、データをrp14またはrp15でXORしていることがわかります。しかし、parはすべてのデータをカバーしています。これはrp14を計算する必要がないことを意味します。なぜなら、par = rp14 ^ rp15であり、rp14 = par ^ rp15で計算できるからです（必要に応じてrp15を計算せず、rp14からrp15を計算することもできます）。これが逆パリティと呼ばれる理由です。もちろん、rp4/5、rp6/7、rp8/9、rp10/11、rp12/13にも同じことが適用されます。つまり、if文のelse句を削除できます。また、最終的な計算を少し最適化するためにlongからbyteに変換することもできます。実際にはテーブル参照を完全に回避することも可能です。

その後、コードはステートメント数が減少しているにもかかわらず、約30％時間が増えるようになりました。これはアセンブリコードにも反映されています。

分析3¶

非常に不思議です。キャッシュやインストラクション並列性などに原因があるのかもしれません。また、eeePC（Celeron、900 MHzで動作）でも試してみました。興味深い観察点は、このデバイスが私の3GHz D920プロセッサと比較して、時間にかかってコードを実行する際には30％遅いということです。

まあ、予想通り難しかったので、別のアプローチに移行するかもしれません。試行2のコードに戻り、ループ展開を行ってみましょう。これにより、いくつかのif文を削除できます。異なるループ展開量を試して、最も効果的なものを確認します。

試行4¶

ループを1回、2回、3回、4回展開しました。4回の場合はコードは以下のように始まります:

for (i = 0; i < 4; i++)
{
    cur = *bp++;
    par ^= cur;
    rp4 ^= cur;
    rp6 ^= cur;
    rp8 ^= cur;
    rp10 ^= cur;
    if (i & 0x1) rp13 ^= cur; else rp12 ^= cur;
    if (i & 0x2) rp15 ^= cur; else rp14 ^= cur;
    cur = *bp++;
    par ^= cur;
    rp5 ^= cur;
    rp6 ^= cur;
    ...

分析4¶

ループ展開を1回行うことで約15％の改善が得られます。

2回のアンロールにより、改善率は約15％に抑えられます

3回のアンロールにより、試行2と比較して改善率は30％になります

4回のアンロールにより、3回のアンロールと比較してわずかな改善があります

私は4回アンロールされたループを進める決断をしました。次のステップでさらに改善が得られるだろうという直感があったからです

parはすべてのバイトのXORを含み、rp4とrp5はそれぞれすべてのバイトの半分のXORを含みます。したがって、par = rp4 ^ rp5と表現できます。XORは可換なので、rp5 = par ^ rp4とも言えます。これによりrp4とrp5の両方を保持する必要はありません。rp5（またはrp4、ただしもう一つの最適化を予測していたため）を削除できます。rp6/7、rp8/9、rp10/11、rp12/13、rp14/15にも同様のことが適用されます

試行5¶

ループ内のすべての奇数番号のrp割当が削除されました。これはif文のelse句も含みます。もちろんループの後にはコードを追加して状態を修正する必要があります

rp5 = par ^ rp4;

初期割当（rp5 = 0; など）も削除できます。この辺りでrp0/1/2/3の初期化も削除しました

分析5¶

測定結果ではこの変更が良い選択だったことが分かりました。実行時間は試行4（4回アンロール）と比較してほぼ半分になり、現在のLinuxカーネルのコードと比較してプロセッサ時間は1/3程度に抑えられます

しかし、まだ何か改善の余地があると考えていました。すべてのif文を好きになれませんでした。なぜなら、継続的なパリティを保持し、最後のif文だけを残す方が良いからです。もう一つのバージョンを作成する時間です！

試行6¶

forループ内のコードは以下のようになりました：

for (i = 0; i < 4; i++)
{
    cur = *bp++; tmppar  = cur; rp4 ^= cur;
    cur = *bp++; tmppar ^= cur; rp6 ^= tmppar;
    cur = *bp++; tmppar ^= cur; rp4 ^= cur;
    cur = *bp++; tmppar ^= cur; rp8 ^= tmppar;

    cur = *bp++; tmppar ^= cur; rp4 ^= cur; rp6 ^= cur;
    cur = *bp++; tmppar ^= cur; rp6 ^= cur;
    cur = *bp++; tmppar ^= cur; rp4 ^= cur;
    cur = *bp++; tmppar ^= cur; rp10 ^= tmppar;

    cur = *bp++; tmppar ^= cur; rp4 ^= cur; rp6 ^= cur; rp8 ^= cur;
    cur = *bp++; tmppar ^= cur; rp6 ^= cur; rp8 ^= cur;
    cur = *bp++; tmppar ^= cur; rp4 ^= cur; rp8 ^= cur;
    cur = *bp++; tmppar ^= cur; rp8 ^= cur;

    cur = *bp++; tmppar ^= cur; rp4 ^= cur; rp6 ^= cur;
    cur = *bp++; tmppar ^= cur; rp6 ^= cur;
    cur = *bp++; tmppar ^= cur; rp4 ^= cur;
    cur = *bp++; tmppar ^= cur;

    par ^= tmppar;
    if ((i & 0x1) == 0) rp12 ^= tmppar;
    if ((i & 0x2) == 0) rp14 ^= tmppar;
}

tmpparはforループの各イテレーション内でパリティを累積するために使用されています。最後の3行ではparに加算され、必要に応じてrp12とrp14にも加算されます

変更を加える過程で、tmpparがこのイテレーションの継続的なパリティを含んでいることに気づきました。そのため、rp4 ^= cur; rp6 ^= cur; の代わりに、rp6 ^= cur; のステートメントを削除し、次のステートメントでrp6 ^= tmppar; としました。rp8とrp10にも同様の変更を行いました

分析6¶

このコードを再度測定した結果、大幅な改善が確認されました。元のLinuxコードを100万回実行するのに、私のシステムでは約1秒かかりました。（パフォーマンスを測定するためにtimeを使用）。このイテレーション後、0.075秒に戻りました。実際には、精度を失わないために1000万回以上のイテレーションから測定を開始する必要がありました。これは間違いなく大当たりです！

ただし、改善の余地はまだ少しあります。ステートメントがある場所は3か所あります：

rp4 ^= cur; rp6 ^= cur;

whileループ内で変数rp4_6も保持しておく方がより効率的です。これにより1回のループごとに3行分のステートメントを省略できます。もちろんループの後に修正を行う必要がありますので、以下のように加算します:

rp4 ^= rp4_6;
rp6 ^= rp4_6

さらにrp8への4回の連続割り当てがあります。これによりtmpparを4行の前後に保存し、後にrp8 = rp8 ^ tmppar ^ notrp8; とすることでより効率的にエンコードできます（notrp8は4行の前のrp8の値）。再びxorの可換性を活用しています。新しいテストの時間です！

試行7¶

新しいコードは以下のようになります:

for (i = 0; i < 4; i++)
{
    cur = *bp++; tmppar  = cur; rp4 ^= cur;
    cur = *bp++; tmppar ^= cur; rp6 ^= tmppar;
    cur = *bp++; tmppar ^= cur; rp4 ^= cur;
    cur = *bp++; tmppar ^= cur; rp8 ^= tmppar;

    cur = *bp++; tmppar ^= cur; rp4_6 ^= cur;
    cur = *bp++; tmppar ^= cur; rp6 ^= cur;
    cur = *bp++; tmppar ^= cur; rp4 ^= cur;
    cur = *bp++; tmppar ^= cur; rp10 ^= tmppar;

    notrp8 = tmppar;
    cur = *bp++; tmppar ^= cur; rp4_6 ^= cur;
    cur = *bp++; tmppar ^= cur; rp6 ^= cur;
    cur = *bp++; tmppar ^= cur; rp4 ^= cur;
    cur = *bp++; tmppar ^= cur;
    rp8 = rp8 ^ tmppar ^ notrp8;

    cur = *bp++; tmppar ^= cur; rp4_6 ^= cur;
    cur = *bp++; tmppar ^= cur; rp6 ^= cur;
    cur = *bp++; tmppar ^= cur; rp4 ^= cur;
    cur = *bp++; tmppar ^= cur;

    par ^= tmppar;
    if ((i & 0x1) == 0) rp12 ^= tmppar;
    if ((i & 0x2) == 0) rp14 ^= tmppar;
}
rp4 ^= rp4_6;
rp6 ^= rp4_6;

大きな変更ではありませんが、すべての1セントが大切です :-)

分析7¶

実際には状況が悪化しています。それほど大きくはないものの、誤った方向へ進まないよう気を付けたいです。後で調査するべきかもしれません。キャッシュ関連の問題かもしれません。

おそらくループ内で勝ち取るべきものはこれくらいです。もう一度ループを展開するだけで改善するかもしれません。まずは試行7の最適化を維持します。

試行8¶

ループをもう一度展開しました。

分析8¶

これにより状況が悪化しています。試行6に戻ってから進めます。ループ内のコードはもう最適化できないように見えますが、eccコードの生成を最適化する余地があります。単純に合計パリティを計算すればよいです。パリティが0であればrp4 = rp5など、パリティが1であればrp4 = !rp5; とします。

しかしrp4 = rp5であればrp5などは必要ありません。結果バイトに偶数ビットを直接書き込むだけで、その後以下のように処理できます:

code[0] |= (code[0] << 1);

これをテストしてみましょう。

試行9¶

コードを変更しましたが、再びパフォーマンスがわずかに低下しています。他の方法も試しました。たとえばparity配列を専用にしてparity[rp7] << 7; の後のシフトを避けるなど。しかし効果は見られませんでした。parity配列を使用する代わりにシフト演算子を使用する（例: parity[rp7] << 7 を以下のように置き換える）なども試しました。

rp7 ^= (rp7 << 4);
rp7 ^= (rp7 << 2);
rp7 ^= (rp7 << 1);
rp7 &= 0x80;

効果は見られませんでした。

唯一の微細な変更はパリティビットを反転させたことで、これにより最後の3つの反転ステートメントを削除できます。

残念ながらこれ以上改善は見られません。ただし、Linuxドライバコードで1000万回のイテレーションを実行すると13〜13.5秒かかりますが、私のコードでは約0.73秒で完了します。つまり私のシステムではパフォーマンスが18倍向上しています。それほど悪くありません。ただし、ハードウェアによって結果は異なります。保証は一切ありません！

ただし無料のランチはありません。コードサイズはほぼ3倍に（562バイトから1434バイト）増えました。ただし、それほど大きくはないです。

エラー訂正¶

エラー訂正については再度STのアプリケーションノートを参考にしましたが、既存のコードも確認しました。

アルゴリズム自体は非常にシンプルです。与えられたECCと計算されたECCをXORするだけでよいです。すべてのバイトが0であれば問題ありません。11ビットが1であれば1ビットの訂正可能なエラーがあります。1ビットが1であれば、与えられたECCコードにエラーがあります。

テーブルの参照を行うことで最も高速化できることが確認されました。私のシステムでは修理が必要な場合、性能向上は約2倍、修理が不要な場合は1％程度でした。

この関数のコードサイズは330バイトから686バイトに増加しました。(gcc 4.2, -O3)

結論¶

ECCの計算時の効果は非常に大きいです。私の開発ハードウェアではECC計算の高速化が18倍達成されました。MIPSコアを搭載した埋め込みシステムでのテストでは7倍の高速化が得られました。

Linksys NSLU2（ARMv5TEプロセッサ）でのテストでは、ビッグエンディアンモードでgcc 4.1.2、-O3で5倍の高速化が得られました。

訂正については、ビットフリップがまれなので大幅な効果は得られませんでした。ただし、処理にかかるサイクル数は大幅に少ないです。

C言語でプログラミングした場合、これ以上効果を引き出すことは難しいようです。もちろんアセンブリプログラムでさらに効果を引き出すことは可能かもしれませんが、パイプラインの動作などにより非常に困難です（少なくともインテルのハードウェアでは）。

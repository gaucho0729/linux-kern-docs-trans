struct usb_device_id¶

プロービングおよびホットプラグインのためのUSBデバイスを特定します

定義

struct usb_device_id {
  __u16 match_flags;
  __u16 idVendor;
  __u16 idProduct;
  __u16 bcdDevice_lo;
  __u16 bcdDevice_hi;
  __u8 bDeviceClass;
  __u8 bDeviceSubClass;
  __u8 bDeviceProtocol;
  __u8 bInterfaceClass;
  __u8 bInterfaceSubClass;
  __u8 bInterfaceProtocol;
  __u8 bInterfaceNumber;
  kernel_ulong_t driver_info ;
};

メンバ

match_flags

他のフィールドのうち、新しいデバイスとマッチングするための使用するフィールドを制御するビットマスクです。driver_info以外のどのフィールドも使用可能ですが、一部は他のフィールドと併せて意味があります。これは通常、USB_DEVICE_*()マクロによって設定され、この構造体の他のすべてのフィールドを設定します（driver_infoを除く）

idVendor

USBデバイスのベンダーID；数値はUSBフォーラムがそのメンバーに割り当てます。

idProduct

ベンダーが割り当てた製品ID。

bcdDevice_lo

ベンダーが割り当てた製品バージョン番号の範囲の下限。これは、単一のデバイスを含む範囲の個々の製品バージョンを特定するためにも使用されます。

bcdDevice_hi

バージョン番号範囲の上限。製品バージョンの範囲は包含されます。

bDeviceClass

デバイスのクラス；数値はUSBフォーラムが割り当てます。製品はクラスを実装することを選択するか、ベンダー固有にすることができます。デバイスクラスは、デバイス上のすべてのインターフェースの動作を指定します。

bDeviceSubClass

デバイスのサブクラス；bDeviceClassに関連しています。

bDeviceProtocol

デバイスのプロトコル；bDeviceClassに関連しています。

bInterfaceClass

インターフェースのクラス；数値はUSBフォーラムが割り当てます。製品はクラスを実装することを選択するか、ベンダー固有にすることができます。インターフェースクラスは、特定のインターフェースの動作のみを指定します。他のインターフェースは他のクラスをサポートする場合があります。

bInterfaceSubClass

インターフェースのサブクラス；bInterfaceClassに関連しています。

bInterfaceProtocol

インターフェースのプロトコル；bInterfaceClassに関連しています。

bInterfaceNumber

インターフェース番号；コンポジットデバイスは、ベンダー固有のインターフェースを区別するために固定されたインターフェース番号を使用する場合があります。

driver_info

ドライバが使用する情報を保持します。通常は、ドライバが理解するディスクリプタへのポインタまたはデバイスフラグを保持します。

説明

ほとんどの場合、ドライバは、以下のマクロなど、その目的のために設計されたマクロを使用してデバイスIDのテーブルを作成します。 USB_DEVICE()、またはその目的のために設計された他のマクロを使用します。その後、MODULE_DEVICE_TABLE()を使用してユーザー空間にエクスポートし、そのusb_driver構造体を通じてUSBコアに提供します。

を参照してください。 usb_match_id() マッチングがどのように行われるかに関する情報を提供する関数です。簡単に説明すると、通常はいくつかのマクロのうちの1つを使用してこれらのエントリを構築するのを助けることになります。提供する各エントリは、1つまたは複数の特定の製品を特定するか、または同じ動作を行う製品のクラスを特定します。ドライバ情報が特定製品の特徴を記録できるようにするため、テーブルの先頭により具体的なマッチングを配置してください。

struct util_est¶

FAIRタスクの推定利用率

定義

struct util_est {
  unsigned int                    enqueued;
  unsigned int                    ewma;
#define UTIL_EST_WEIGHT_SHIFT           2;
#define UTIL_AVG_UNCHANGED              0x80000000;
};

メンバ

enqueued

タスク/CPUの瞬間的な推定利用率

ewma

タスクの指数平滑移動平均 (EWMA) 利用率

説明

FAIRタスクの利用率の指数平滑移動平均 (EWMA) を追跡するサポートデータ構造。タスクがアクティベーションを完了するたびに新しいサンプルが移動平均に追加され、サンプルの重みはタスクのワークロードの一時的な変化に比較的不敏感になるように選択されます。

enqueued属性はタスクとCPUで意味がやや異なります：- タスク：タスクの最後のタスクデキュー時間におけるutil_avg - cfs_rq：そのCPU上の各RUNNABLEタスクのutil_est.enqueuedの合計値。したがって、タスクのutil_est.enqueuedは、そのタスクが現在登録されているCPUの推定利用率への貢献を表します。

タスクについては過去の瞬間的な推定利用率の移動平均を追跡します。これにより、ほぼ周期的なタスクの利用率の一時的な低下を吸収できます。

UTIL_AVG_UNCHANGED フラグは util_est と util_avg の更新を同期するために使用されます。タスクがデキューされる際、util_avg が更新されていない場合、util_est は更新されません。この情報はデキュー時間における util_est.enqueued の MSB ビットにマッピングされます。タスクの util_est.enqueued の最大値は1024（PELT util_avg）なので、MSBを使用するのは安全です。

__visible void notrace preempt_schedule_notrace(void)¶

トレースによって呼び出される preempt_schedule

パラメータ

void

説明

トレースインフラストラクチャは preempt_enable_notrace を使って再帰を防ぎ、トレースインフラストラクチャ自体による preempt 有効化を防ぎます。ただし、トレースはユーザー空間から発生する場合やユーザー空間に入る直前である場合もあり、user_exit() が呼ばれる前にも preempt 有効化が発生する可能性があります。これにより、システムがまだユーザーモードにある状態でスケジューラが呼ばれます。

これを防ぐため、preempt_enable_notrace は scheduler を呼び出す前に必要に応じてユーザーコンテキストを終了するためにこの関数を preempt_schedule() ではなく使用します。

void yield(void)¶

現在のプロセッサを他のスレッドに譲ります。

パラメータ

void

引数なし

説明

この関数は決して使用しないでください。99%の確率で間違っている可能性があります。

スケジューラは常に呼び出しタスクを最も適切なタスクとして選ぶことができます。もしコードから削除すると、 yield() コードからの呼び出しで壊れると、すでに壊れているのです。

典型的な不適切な使用例は:

while (!event)

yield();

ここで、以下を仮定しています yield() この処理は、'他'のプロセスがeventをtrueにするように実行します。ただし、現在のタスクがSCHED_FIFOタスクである場合、これは決して起こりません。決して使用しないでください。 yield() 進捗保証として!!

もしあなたが使用したい場合は yield() 何かを待つ場合は、 wait_event()。もしあなたが使用したい場合は yield() 他者に優しくするにはcond_resched()を使用してください。それでも使用したい場合は yield()、使用しないでください！

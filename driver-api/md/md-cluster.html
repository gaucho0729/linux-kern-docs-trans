MDクラスタ¶

クラスタMDは、クラスタ用の共有デバイスRAIDです。サポートしているレベルはraid1とraid10（制限付きサポート）です。

1. ディスク上の形式¶

各クラスタノードに対して個別のwrite-intent-bitmapが使用されます。これらのbitmapは、そのノードで開始されたがまだ完了していないすべての書き込みを記録します。ディスク上のレイアウトは以下の通りです：

0                    4k                     8k                    12k
-------------------------------------------------------------------
| idle                | md super            | bm super [0] + bits |
| bm bits[0, contd]   | bm super[1] + bits  | bm bits[1, contd]   |
| bm super[2] + bits  | bm bits [2, contd]  | bm super[3] + bits  |
| bm bits [3, contd]  |                     |                     |

「通常」動作中は、ファイルシステムが任意のブロックに対して同時に1つのノードのみが書き込みを行うことを保証すると仮定します。そのため、書き込み要求は

  • 適切なビットを設定します（すでに設定されている場合は除く）

  • すべてのミラーノードに書き込みをコミットします

  • タイムアウト後にビットをクリアするスケジュールを設定します。

読み取りは通常通り処理されます。ファイルシステムが、他のノード（または同じノード）が書き込み中の場所から読み取らないように保証する必要があります。

2. 管理用DLMロック¶

デバイスを管理するためのロックグループは3つあります：

2.1 ビットマップロックリソース（bm_lockres）¶

bm_lockresは個々のノードのビットマップを保護します。これらはbitmap000（ノード1）、bitmap001（ノード2）などと名付けられます。ノードがクラスタに参加する際には、PWモードでロックを取得し、クラスタに所属している間はその状態を維持します。ロックリソース番号はDLMサブシステムが返すスロット番号に基づいています。DLMはノードカウントを1から開始するのに対し、ビットマップスロットは0から開始するため、DLMスロット番号から1を引いた値がビットマップスロット番号になります。

特定のノードのビットマップロックのLVB（Lock Value Block）は、そのノードが再同期しているセクター範囲を記録します。他のノードはこれらのセクターに書き込みできません。これは新しいノードがクラスタに参加するときに使用されます。

2.2 メッセージ送信ロック¶

各ノードは、再同期の開始または終了、およびメタデータスーパーブロックの更新時に他のノードと通信する必要があります。この通信は、「token」、「message」、「ack」の3つのロックを通じて管理され、さらに「message」ロックの1つに属するLock Value Block（LVB）も使用されます。

2.3 新しいデバイスの管理¶

単一のロック「no-new-dev」が新しいデバイスの追加を調整するために使用されます。これは配列全体で同期する必要があります。通常、すべてのノードがこのデバイスに対してコンカレンテッドリードロックを保持します。

3. 通信¶

メッセージはすべてのノードにブロードキャストされ、送信者はすべての他のノードがメッセージを確認するのを待ってから進みます。一度に1つのメッセージのみを処理できます。

3.1 メッセージタイプ¶

6種類のメッセージが送信されます：

3.1.1 METADATA_UPDATED¶

他のノードにメタデータが更新されたことを通知し、ノードはmdスーパーブロックを再読み込む必要があります。これは同期的に実行されます。主にデバイス障害を通知するために使用されます。

3.1.2 リスynchronize¶

リスynchronizeの開始または終了を他のノードに通知し、各ノードが領域の停止または再開を可能にするためのメッセージです。各リスynchronizeメッセージは、送信ノードがリスynchronizeするデバイスの範囲を指定します。このメッセージは、そのノードからの以前の通知を上書きします。1つのノードあたり、一度に1つの範囲のみリスynchronizeできます。

3.1.3 NEWDISK¶

デバイスが配列に追加されていることを他のノードに通知します。メッセージにはそのデバイスの識別子が含まれます。詳細については下記を参照してください。

3.1.4 REMOVE¶

故障したか、代替として使用されていたデバイスが配列から削除されています。メッセージにはそのデバイスのスロット番号が含まれます。

3.1.5 RE_ADD:

故障したデバイスが再活性化されています。このデバイスが再び正常に動作していると判断されていることを前提としています。

3.1.6 BITMAP_NEEDS_SYNC:

ノードがローカルで停止しているが、ビットマップがクリーンでない場合、他のノードにリスynchronizeの所有権を取得するよう通知します。

3.2 通信メカニズム¶

DLM LVBはクラスタ内のノード間で通信するために使用されます。この目的で使用されるリソースは以下の3つです：

3.2.1 token¶

通信システム全体を保護するリソース。tokenリソースを持つノードのみ通信が許可されます。

3.2.2 message¶

通信に使用されるロックリソースで、データを運搬します。

3.2.3 ack¶

メッセージがクラスタ内のすべてのノードによって確認されたことを示すリソース。このリソースのBASTは、受信ノードにノードが通信を希望していることを通知します。

アルゴリズムは以下の通りです：

  1. ステータスを受信 - すべてのノードが「ack」にコンカレンタルリーダーロックを保持しています：

    sender                         receiver                 receiver
"ack":CR                       "ack":CR                 "ack":CR

  2. 送信者が「token」にEXを取得し、「message」にEXを取得します：

    sender                        receiver                 receiver
"token":EX                    "ack":CR                 "ack":CR
"message":EX
"ack":CR

    送信者がまだメッセージを送る必要があるかを確認します。トークンを待っている間受け取ったメッセージや他のイベントにより、このメッセージが不適切または冗長になる可能性があります。

  3. 送信者がLVBを書き込みます

    送信者が「message」をEXからCWに下位変換します

    送信者が「ack」のEXを取得しようとします

     [ wait until all receivers have *processed* the "message" ]

                                  [ triggered by bast of "ack" ]
                                  receiver get CR on "message"
                                  receiver read LVB
                                  receiver processes the message
                                  [ wait finish ]
                                  receiver releases "ack"
                                  receiver tries to get PR on "message"

sender                         receiver                  receiver
"token":EX                     "message":CR              "message":CR
"message":CW
"ack":EX

  4. 「ack」のEXが許可されたら（すべての受信者がメッセージを処理したことを示す）

    送信者が「ack」をEXからCRに下位変換します

    送信者が「message」を解放します

    送信者が「token」を解放します

                                receiver upconvert to PR on "message"
                            receiver get CR of "ack"
                            receiver release "message"

sender                      receiver                   receiver
"ack":CR                    "ack":CR                   "ack":CR

4. フェールオーバーの処理¶

4.1 ノードフェールオーバー¶

ノードが故障した場合、DLMはクラスタにスロット番号で通知します。ノードはクラスタ回復スレッドを開始します。クラスタ回復スレッドは以下の処理を行います：

  • 故障したノードのbitmap<number>ロックを取得します

  • bitmapを開きます

  • 故障したノードのbitmapを読み込みます

  • 設定されたbitmapをローカルノードにコピーします

  • 失敗したノードのビットマップをクリーンする

  • 失敗したノードのbitmap<number> ロックを解放する

  • 現在のノードでビットマップの再同期を開始します。recover_bitmaps内でmd_check_recoveryが呼び出され、md_check_recovery -> metadata_update_start/finishが実行されると、lock_commによって通信がロックされます。これは、1つのノードが再同期している間、配列全体のどこにも他のノードが書けないようにするためです。

再同期プロセスは通常のmd再同期です。ただしクラスタ環境では、再同期を実行する際には、他のノードに停止領域を通知する必要があります。再同期開始前に、ノードはRESYNCINGメッセージを送信し、停止する領域の(lo, hi)範囲を指定します。各ノードはsuspend_listを保持し、受信したRESYNCINGメッセージに応じて範囲を追加します。再同期が完了したノードは、空の範囲でRESYNCINGを送信し、他のノードがsuspend_listから該当のエントリを削除します。

area_resyncing()関数を使用して、特定のI/O範囲が停止すべきかどうかを確認できます。

4.2 デバイスの障害¶

デバイスの障害はメタデータ更新ルーチンで処理され通知されます。ノードがデバイス障害を検出すると、他のノードが承認するまでそのデバイスへの書き込みを禁止します。

5. 新しいデバイスの追加¶

新しいデバイスを追加するには、すべてのノードが新しいデバイスを認識する必要があります。そのため、以下のアルゴリズムが使用されます：

  1. ノード1はmdadm –manage /dev/mdX –add /dev/sdYYを実行し、ioctl(ADD_NEW_DISKでdisc.stateをMD_DISK_CLUSTER_ADDに設定)を発行します

  2. ノード1はuuidとスロット番号を含むNEWDISKメッセージを送信します

  3. 他のノードはuuidとスロット番号を用いてkobject_uevent_envを実行します（ステップ4、5はudevルールとして扱うこともできます）

  4. ユーザースペースでは、ノードはblkid -t SUB_UUID=””などを用いてディスクを検索します

  5. ディスクが見つかった場合、他のノードはioctl(ADD_NEW_DISKでdisc.stateをMD_DISK_CANDIDATEに設定し、disc.numberをスロット番号に設定)を実行するか、ioctl(CLUSTERED_DISK_NACK)を実行します

  6. ディスクが見つかった場合、他のノードは「no-new-devs」（CR）のロックを解除します

  7. ノード1は「no-new-dev」のEXロックを取得しようとします

  8. ノード1がロックを取得した場合、ディスクをSpareLocalから解除した後にMETADATA_UPDATEDを送信します

  9. ロックを取得できなかった場合（「no-new-dev」ロックを取得できなかった場合）、操作を失敗させMETADATA_UPDATEDを送信します

  10. 他のノードはMETADATA_UPDATEDを通じてディスクが追加されたかどうかの情報を取得します

6. モジュールインターフェース¶

mdコアがクラスターモジュールに対して行えるコールバックは17個あります。これらを理解することで、全体のプロセスについて良い概要を得ることができます。

6.1 join(nodes) および leave()¶

配列がクラスタービットマップで起動されるとき、または停止されるときに呼び出されます。join()はクラスタが利用可能になるようにし、各種リソースを初期化します。クラスタ内の最初の‘nodes’ノードのみが配列を使用できます。

6.2 slot_number()¶

クラスタインフラストラクチャが推奨するスロット番号を報告します。範囲は0からnodes-1です。

6.3 resync_info_update()¶

これはビットマップロックに保存されている再同期範囲を更新します。再同期が進むにつれて開始位置が更新され、終了位置は常に配列の終わりです。これにより、 ではありません RESYNCINGメッセージを送信します。

6.4 resync_start(), resync_finish()¶

再同期/回復/再構成が開始または停止するときに呼び出されます。これらはビットマップロック内の再同期範囲を更新し、RESYNCINGメッセージも送信します。resync_startは配列全体を再同期中と報告し、resync_finishはすべてを報告しません。

resync_finish()はさらにBITMAP_NEEDS_SYNCメッセージを送信し、他のノードが制御を引き継ぐことを可能にします。

6.5 metadata_update_start(), metadata_update_finish(), metadata_update_cancel()¶

metadata_update_startはメタデータへの排他アクセスを取得するために使用されます。そのアクセスを得た後でも変更が必要な場合は、metadata_update_finish()が他のノードにMETADATA_UPDATEメッセージを送信します。そうでない場合は、metadata_update_cancel()を使用してロックを解放できます。

6.6 area_resyncing()¶

これは2つの機能要素を統合しています。

まず、指定されたセクタ範囲内でどのノードが現在再同期しているかを確認します。再同期が見つかった場合、呼び出し元はその範囲での書き込みや読み込みバランスを避けることになります。

次に、ノード回復が進行中である場合、READリクエストに対してすべての領域が再同期中であると報告します。これにより、クラスタファイルシステムとクラスタRAIDがノード障害を処理する際の競合を回避します。

6.7 add_new_disk_start(), add_new_disk_finish(), new_disk_ack()¶

これは上記の新しいディスクプロトコルを管理するために使用されます。新しいデバイスが追加された場合、add_new_disk_start()がデバイスが配列にバインドされる前に呼び出され、成功した場合、デバイスが完全に追加された後にadd_new_disk_finish()が呼び出されます。

デバイスが以前のリクエストへの応答として追加された場合、またはデバイスが「利用不可」と宣言された場合、new_disk_ack()が呼び出されます。

6.8 remove_disk()¶

スパレや障害が発生したデバイスが配列から削除されるときに呼び出されます。これにより、他のノードにREMOVEメッセージが送信されます。

6.9 gather_bitmaps()¶

すべての他のノードにRE_ADDメッセージを送信し、その後すべてのビットマップからビットマップ情報を収集します。この結合されたビットマップは、再追加されたデバイスの復元に使用されます。

6.10 lock_all_bitmaps() および unlock_all_bitmaps()¶

ビットマップをnoneに変更する場合に呼び出されます。クラスタRAIDのビットマップをクリアするノードは、クラスタ内のすべてのビットマップロックをロックすることで他のノードがRAIDを使用していないことを確認する必要があります。その後、これらのロックは適切にアンロックされます。

7. 対応していない機能¶

クラスタMDではまだサポートされていない機能があります。

  • array_sectorsを変更する。

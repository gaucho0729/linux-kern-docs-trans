2.2. デジタルTVフロントエンド kABI¶

2.2.1. デジタルTV Frontend¶

デジタルTV Frontend kABIは、ハードウェアに依存しないフロントエンドレイヤーに、低レベルかつハードウェア固有のドライバを登録するドライバ内部のインターフェースを定義しています。これはデジタルTVデバイスドライバの作成者だけに関心があります。このAPIのヘッダーファイルは dvb_frontend.h および、以下に配置されています include/media/.

2.2.1.1. デモデュレータドライバ¶

デモデュレータドライバは、ハードウェアのデコード部分と通信する責任があります。このようなドライバは、 dvb_frontend_opsを実装すべきです。これはサポートするデジタルTV標準の種類を示し、DVBコアがコードの下でハードウェアを制御できる一連の関数を指します。 include/media/dvb_frontend.c.

ドライバ内でこのような構造体の典型的な例は foo は:

2.2.1.2. フロントエンドドライバをブリッジドライバに接続する¶

Digital TV frontend coreを使用する前に、ブリッジドライバーはfrontend demod、チューナーおよびSECデバイスをアタッチし、呼び出す必要があります。 dvb_register_frontend()サブシステムに新しいfrontendを登録するため。デバイスの接続解除/除去時に、ブリッジドライバーは呼び出して、 dvb_unregister_frontend() コアからfrontendを削除し、その後、 dvb_frontend_detach() フロントエンドドライバーによって割り当てられたメモリを解放します。

ドライバーはまた、 dvb_frontend_suspend() そのハンドラ内で、 device_driver.suspend(), and dvb_frontend_resume() そのハンドラ内で、 device_driver.resume().

いくつかの他のオプション機能が提供されており、一部の特殊なケースを処理するために使用されます。

2.2.2. デジタルTVフロントエンド統計¶

2.2.2.1. はじめに¶

デジタルTV frontendは、デバイスの調整やサービス品質の測定を支援するための 統計 を提供しています。

各統計測定において、ドライバーは使用するスケールの種類を設定する必要があります、または FE_SCALE_NOT_AVAILABLE 特定の時間に統計が利用できない場合。ドライバーはまた、各タイプの統計数を提供する必要があります。これは一般的にほとんどのビデオ標準で1です 1.

ドライバーは、各統計カウンターを初期化コードで長さとスケールを設定する必要があります。例えば、frontendが信号強度を提供する場合、初期化コードには以下のように設定する必要があります：

struct dtv_frontend_properties *c = &state->fe.dtv_property_cache;

c->strength.len = 1;
c->strength.stat[0].scale = FE_SCALE_NOT_AVAILABLE;

そして、統計が更新された場合、スケールを設定する必要があります：

c->strength.stat[0].scale = FE_SCALE_DECIBEL;
c->strength.stat[0].uvalue = strength;
1

ISDB-Tの場合、グローバル統計と各レイヤーの統計を提供する場合があります。そのような場合、lenは4に等しくなります。最初の値はグローバル統計に対応し、他の値は各レイヤーに対応します。例えば：

  • c->cnr.stat[0] はグローバルS/Nキャリア比に対応し、

  • c->cnr.stat[1] はレイヤーAのS/Nキャリア比に対応し、

  • c->cnr.stat[2] はレイヤーBのS/Nキャリア比に対応し、

  • c->cnr.stat[3] はレイヤーCのS/Nキャリア比に対応します。

注意

信号強度およびCNR測定には、 FE_SCALE_DECIBEL …の代わりに FE_SCALE_RELATIVE を推奨します。

2.2.2.2. 統計グループ¶

現在サポートされている統計グループはいくつかあります：

信号強度（DTV_STAT_SIGNAL_STRENGTH)

  • チューナーやデモッドのアナログ部分における信号強度レベルを測定します。

  • 通常はチューナーやフロントエンドに適用されるゲインから得られます。キャリアが検出されない場合、ゲインは最大値に設定され（強度は最小値になります）。

  • ゲインはゲインを調整するレジスタセットを通じて見えるため、通常この統計は常に利用可能です。 2.

  • ドライバーはこれらの統計を常に利用可能にする必要があります。これらの統計はアンテナ位置の調整やケーブルのトラブル確認に使用できます。

2

一部のデバイスではキャリアが存在しない場合、ゲインが浮遊します。このようなデバイスでは、強度レポートはまずチューナーでキャリアが検出されているか確認する必要があります（FE_HAS_CARRIER, 詳細は fe_status）、そうでない場合は最低限の値を返す必要があります。

キャリア信号対雑音比（DTV_STAT_CNR)

  • メインキャリアの信号対雑音比。

  • 信号対雑音比の測定はデバイスに依存します。一部のハードウェアでは、メインキャリアが検出されたときに利用可能です。このようなハードウェアでは、CNR測定はチューナーから通常取得されます（例：after FE_HAS_CARRIER, 詳細は fe_status).

    他のデバイスでは、内部FECデコードが必要です。フロントエンドは他のパラメータから間接的に測定します（例：after FE_HAS_VITERBI, 詳細は fe_status).

    内部FECの後に利用可能なことが一般的です。

FEC後のビットカウント（DTV_STAT_POST_ERROR_BIT_COUNT および DTV_STAT_POST_TOTAL_BIT_COUNT)

  • これらのカウンターは、内部コーディングブロック（Viterbi、LDPCやその他の内部コードの前）でのFEC後のビット数およびビットエラー数を測定します。

  • その性質上、これらの統計は完全なコーディングロックに依存します（例：after FE_HAS_SYNC またはafter FE_HAS_LOCK, 詳細は fe_status).

FEC前のビットカウント（DTV_STAT_PRE_ERROR_BIT_COUNT および DTV_STAT_PRE_TOTAL_BIT_COUNT)

  • これらのカウンターは、内部コーディングブロック（Viterbi、LDPCやその他の内部コードの前）でのFEC前のビット数およびビットエラー数を測定します。

  • すべてのフロントエンドがこの種の統計を提供するわけではありません。

  • その性質上、これらの統計は内部コーディングロックに依存します（例：after FE_HAS_VITERBI, 詳細は fe_status).

ブロックカウント（DTV_STAT_ERROR_BLOCK_COUNT および DTV-STAT_TOTAL_BLOCK_COUNT)

  • これらのカウンターは、内部コーディングブロック（Viterbi、LDPCやその他の内部コードの前）でのFEC後のブロック数およびブロックエラー数を測定します。

  • その性質上、これらの統計は完全なコーディングロックに依存します（例：after FE_HAS_SYNC またはafter FE_HAS_LOCK, 詳細は fe_status).

注意

すべてのカウンターはハードウェアから収集されるにつれて単調に増加する必要があります。

ステータスと統計を処理するロジックの典型的な例は次の通りです：

static int foo_get_status_and_stats(struct dvb_frontend *fe)
{
        struct foo_state *state = fe->demodulator_priv;
        struct dtv_frontend_properties *c = &fe->dtv_property_cache;

        int rc;
        enum fe_status *status;

        /* Both status and strength are always available */
        rc = foo_read_status(fe, &status);
        if (rc < 0)
                return rc;

        rc = foo_read_strength(fe);
        if (rc < 0)
                return rc;

        /* Check if CNR is available */
        if (!(fe->status & FE_HAS_CARRIER))
                return 0;

        rc = foo_read_cnr(fe);
        if (rc < 0)
                return rc;

        /* Check if pre-BER stats are available */
        if (!(fe->status & FE_HAS_VITERBI))
                return 0;

        rc = foo_get_pre_ber(fe);
        if (rc < 0)
                return rc;

        /* Check if post-BER stats are available */
        if (!(fe->status & FE_HAS_SYNC))
                return 0;

        rc = foo_get_post_ber(fe);
        if (rc < 0)
                return rc;
}

static const struct dvb_frontend_ops ops = {
        /* ... */
        .read_status = foo_get_status_and_stats,
};

2.2.2.3. 統計の収集¶

ほぼすべてのフロントエンドハードウェアでは、ビットおよびバイトカウントは特定の時間経過後、または総ビット/ブロックカウンターが特定の値に達したときにハードウェアによって保存されます（通常はプログラマブル）。たとえば、1000msごとまたは100万ビットを受信した後などです。

したがって、レジスタを早すぎるタイミングで読み取ると、前の読み取りと同じ値を読み取ることになり、単調増加の値が過度にインクリメントされる可能性があります。

ドライバーは、過度な読み取りを避ける責任を負う必要があります。これには2つのアプローチがあります：

2.2.2.3.1. ドライバーが収集データが準備完了であることを示すビットを持っている場合¶

ドライバーは、統計を提供する前にこのようなビットを確認する必要があります。

このような挙動の例は、次のコードスニペット（mb86a20sドライバーのロジックを基にした改訂版）にあります：

static int foo_get_pre_ber(struct dvb_frontend *fe)
{
        struct foo_state *state = fe->demodulator_priv;
        struct dtv_frontend_properties *c = &fe->dtv_property_cache;
        int rc, bit_error;

        /* Check if the BER measures are already available */
        rc = foo_read_u8(state, 0x54);
        if (rc < 0)
                return rc;

        if (!rc)
                return 0;

        /* Read Bit Error Count */
        bit_error = foo_read_u32(state, 0x55);
        if (bit_error < 0)
                return bit_error;

        /* Read Total Bit Count */
        rc = foo_read_u32(state, 0x51);
        if (rc < 0)
                return rc;

        c->pre_bit_error.stat[0].scale = FE_SCALE_COUNTER;
        c->pre_bit_error.stat[0].uvalue += bit_error;
        c->pre_bit_count.stat[0].scale = FE_SCALE_COUNTER;
        c->pre_bit_count.stat[0].uvalue += rc;

        return 0;
}

2.2.2.3.2. ドライバーが統計が利用可能であることを示すビットを提供しない場合¶

しかし、一部のデバイスでは、統計情報が利用可能かどうかを確認する方法が提供されていない（またはその確認方法が不明）場合があります。このようなデバイスでは、総ビット数やブロック数を直接読み取る方法すら提供されていない可能性もあります。

このようなデバイスでは、ドライバーがレジスタから読み込む頻度を減らす必要があり、または総ビット数/ブロック数を推定する必要があります。

このようなドライバーでは、統計情報を取得する典型的な手順は以下の通りです（dib8000ドライバーの論理を参考にしています）：

struct foo_state {
        /* ... */

        unsigned long per_jiffies_stats;
}

static int foo_get_pre_ber(struct dvb_frontend *fe)
{
        struct foo_state *state = fe->demodulator_priv;
        struct dtv_frontend_properties *c = &fe->dtv_property_cache;
        int rc, bit_error;
        u64 bits;

        /* Check if time for stats was elapsed */
        if (!time_after(jiffies, state->per_jiffies_stats))
                return 0;

        /* Next stat should be collected in 1000 ms */
        state->per_jiffies_stats = jiffies + msecs_to_jiffies(1000);

        /* Read Bit Error Count */
        bit_error = foo_read_u32(state, 0x55);
        if (bit_error < 0)
                return bit_error;

        /*
         * On this particular frontend, there's no register that
         * would provide the number of bits per 1000ms sample. So,
         * some function would calculate it based on DTV properties
         */
        bits = get_number_of_bits_per_1000ms(fe);

        c->pre_bit_error.stat[0].scale = FE_SCALE_COUNTER;
        c->pre_bit_error.stat[0].uvalue += bit_error;
        c->pre_bit_count.stat[0].scale = FE_SCALE_COUNTER;
        c->pre_bit_count.stat[0].uvalue += bits;

        return 0;
}

注意してください。どちらの場合も、統計情報は dvb_frontend_ops .read_status コールバック関数を介して取得しています。その理由は、フロントエンドコアがこの関数を定期的に呼び出すため（通常、フロントエンドがロックされているときに秒単位で3回程度）です。

これにより、カウンターを取得し、単調増加する統計情報を適切なタイミングでインクリメントしないことが防がれます。

enum dvbfe_algo¶

チャンネルにチューニングするためのアルゴリズムを定義します

定数

DVBFE_ALGO_HW

ハードウェアアルゴリズム - このアルゴリズムをサポートするデバイスでは、すべての処理がハードウェアで行われ、ソフトウェアでのサポートは必要ありません。このようなデバイスに対してLOCKを要求するだけで、デバイスがハードウェアですべての処理を行うことが期待されます。

DVBFE_ALGO_SW

ソフトウェアアルゴリズム - これらはソフトウェアですべての処理を必要とする単純なデバイスです

DVBFE_ALGO_CUSTOM

カスタマイズ可能なアルゴリズム - このアルゴリズムを持つデバイスは、フロントエンドドライバ内で特定のアルゴリズムをカスタマイズ可能であり、単純なソフトウェアのジグザグ処理を行うのではなく、これにより処理が可能になります。この場合、ジグザグ処理はハードウェアによって支援される可能性がありますし、あるいは完全にハードウェアで行われる可能性もあります。いずれの場合も、このアルゴリズムは検索およびトラックコールバックと併用することで、ドライバ固有のアルゴリズムを活用します。

DVBFE_ALGO_RECOVERY

回復アルゴリズム - これらのデバイスはLOCK失敗からの自動回復機能を持っています

int dvb_frontend_resume(struct dvb_frontend *fe)¶

デジタルTVフロントエンドを再開する

パラメータ

struct dvb_frontend *fe

ポインタ struct dvb_frontend

説明

デジタルTVフロントエンドを再開し、チューナーの通常動作を再開する。

フロントエンドを再開するには、デモッドの dvb_frontend_ops.init().

もし dvb_frontend_ops.tuner_ops。resume()が利用可能であればそれを呼び出す。そうでなければ、を呼び出す。 dvb_frontend_ops.tuner_ops。init()

ドライバーはまた、 dvb_frontend_resume() そのハンドラ内で、 device_driver.resume().

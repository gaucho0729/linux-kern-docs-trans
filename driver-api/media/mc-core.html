4. メディアコントローラーデバイス¶

4.1. メディアコントローラー¶

メディアコントローラー ユーザースペース API は メディアコントローラー uAPI 書籍でドキュメンテーションされています。このドキュメントはメディアフレームワークのカーネル側の実装に焦点を当てています。

4.1.1. 抽象メディアデバイスモデル¶

デバイスの内部トポロジーの発見および実行時での構成は、メディアフレームワークの目標の一つです。この目標を達成するため、ハードウェアデバイスは、エンティティと呼ばれる構築ブロックからなる有向グラフとしてモデル化され、パッドを通じて接続されます。

エンティティは基本的なメディアハードウェア構築ブロックです。これは、CMOS センサなどの物理ハードウェアデバイス、SoC イメージ処理パイプライン内の論理ハードウェアデバイス、DMA チャネル、物理コネクタなど、さまざまな論理ブロックに対応します。

パッドは、エンティティが他のエンティティと相互作用するための接続エンドポイントです。エンティティが生成するデータ（ビデオに限定されません）は、エンティティの出力から1つ以上のエンティティ入力へと流れます。パッドはチップ境界の物理ピンとは混同すべきではありません。

リンクは、2つのパッド間のポイントツーポイント有向接続です。これらは同じエンティティ上にあるか、異なるエンティティ上にあるかに関わらず、データはソースパッドからシンクパッドへと流れます。

4.1.6. リンク¶

4.1.7. グラフトラバーサル¶

メディアフレームワークは、グラフ内のエンティティを反復処理するためのAPIを提供します。

メディアデバイスに属するすべてのエンティティを反復処理するには、ドライバは以下のマクロを呼び出します： include/media/media-device.h.

struct media_entity *entity;

media_device_for_each_entity(entity, mdev) {
// entity will point to each entity in turn
...
}

ドライバは、指定されたエンティティから始まる有効なリンクを通じて到達可能なすべてのグラフ内のエンティティを反復処理する場合もあります。メディアフレームワークはその目的のために深さ優先グラフトラバーサルAPIを提供しています。

注意

サイクルを持つグラフ（有向または無向）は 禁止です グラフトラバーサルAPIでサポートされています。無限ループを防ぐため、グラフトラバーサルコードは最大深さを MEDIA_ENTITY_ENUM_MAX_DEPTHに制限します（現在は16として定義されています）。

ドライバは以下の関数を呼び出してグラフトラバーサルを開始します： media_graph_walk_start()

グラフ構造は呼び出し元によって初期化され、指定されたエンティティからグラフトラバーサルを開始します。

ドライバは以下の関数を呼び出して次のエンティティを取得します： media_graph_walk_next()

グラフトラバーサルが完了した場合、関数は NULL.

グラフトラバーサルはいつでも中断できます。クリーンアップ関数の呼び出しが必要なく、グラフ構造は通常の方法で解放できます。

2つのパッド間のリンクや、有効なリンクを通じて接続されたパッドを検索するための補助関数を使用できます。 media_entity_find_link() および media_entity_remote_pad().

4.1.8. 使用カウントと電源管理¶

電源管理のニーズに応じてドライバ間で大きな違いがあるため、メディアコントローラーは電源管理を実装していません。ただし、 struct media_entity には、メディアドライバが電源管理のニーズのためにすべてのエンティティのユーザー数を追跡するための use_count フィールドがあります。

以下の media_entity.use_count フィールドはメディアドライバが所有しており、エンティティドライバによっては変更してはなりません。このフィールドへのアクセスは、 media_device.graph_mutex ロックの下で取得できるようにする必要があります。

4.1.10. パイプラインとメディアストリーム¶

ストリーミングを開始する際、ドライバーはパイプライン内のすべてのエンティティに通知する必要があります。これにより、ストリーミング中にリンク状態が変更されることを防ぎます。 media_pipeline_start().

関数は、指定されたエンティティと有効なリンクを介して直接または間接的に接続されているすべてのエンティティをストリーミング状態としてマークします。

以下の struct media_pipeline パイプライン引数で示されるインスタンスは、パイプライン内のすべてのエンティティに保存されます。ドライバーは、 struct media_pipeline より上位のパイプライン構造に埋め込み、その後、 struct media_entity pipeフィールドを通じてパイプラインにアクセスできます。

呼び出しは media_pipeline_start() 入れ子になった呼び出しが可能です。すべての入れ子になった呼び出しでパイプラインポインタは同一でなければなりません。

media_pipeline_start() エラーを返す場合があります。その場合、自身が行った変更をすべてクリーンアップします。

ストリーム停止時にドライバーは、 media_pipeline_stop().

複数の呼び出しで media_pipeline_start() 同じ数の media_pipeline_stop() 呼び出しが必要です。最後の入れ子になった停止呼び出しで、 media_entity.pipe フィールドが NULL にリセットされます。

リンク構成は、リンクの両端がストリーミングエンティティである場合、デフォルトでは -EBUSY で失敗します。ストリーミング中に変更可能なリンクは、 MEDIA_LNK_FL_DYNAMIC フラグを設定します。

にマークする必要があります。ストリーミングエンティティに対して他の操作を禁止する必要がある場合（例：エンティティの構成パラメータの変更）、ドライバーはメディアエンティティのstream_countフィールドを確認してエンティティがストリーミングしているかを判定できます。この操作は、メディアデバイスのグラフミューテックスを保持した状態で行う必要があります。

4.1.11. リンク検証¶

リンク検証は、 media_pipeline_start() がパイプラインにsink padを持つすべてのエンティティに対して実行されます。この目的には、 media_entity.link_validate() コールバックが使用されます。 link_validate() コールバックでは、接続されたエンティティのsource padのプロパティと自身のsink padのプロパティが一致しているかをドライバーが確認する必要があります。エンティティの種類（最終的にはハードウェアのプロパティ）によって、一致の意味が異なります。

サブシステムは、サブシステム固有のヘルパーファンクションを提供して、よく使用される情報を簡単に取得できるようにし、最終的にはドライバーサービス固有のコールバックを使用できるようにする必要があります。

4.1.12. メディアコントローラーデバイスアロケータAPI¶

メディアデバイスが複数のドライバーに属する場合、共有メディアデバイスは共有 struct device をキーとしてして検索されます。

共有メディアデバイスは、最後のドライバが登録状態を解除するまで、常に登録状態を維持する必要があります。また、すべての参照が解放された時点でメディアデバイスは解放されるべきです。ドライバはプローブ時にメディアデバイスを割り当てることで参照を取得します。メディアデバイスがすでに割り当てられている場合、allocate APIは参照カウントを増やして既存のメディアデバイスを返します。ドライバは切断ルーチンで呼ばれるときに参照を再び解放します。 media_device_delete().

メディアデバイスはkref putハンドラによって解除されクリーンアップされるため、メディアデバイスは最後のドライバが解除するまで常に登録状態を維持します。

ドライバの使用方法

ドライバは、共有メディアデバイスのライフタイムを管理するため、適切なmedia-coreルーチンを使用する必要があります。管理する2つの状態は以下の通りです：1. 割り当て -> 登録 -> 削除 2. 既に登録済みのデバイスへの参照を取得 -> 削除

呼び出す media_device_delete() ルーチンを呼び出すことで、共有メディアデバイスの削除処理が正しく行われるようにします。

ドライバプローブ: を呼び出して、MMIOまたはIOポート範囲を利用可能にします。これを実施しないと、ドライバの再ロードができない状態になります。 media_device_usb_allocate() 割り当てまたは参照を取得するため、呼び出す media_device_register()、メディアデバイスノードが登録されていない場合

ドライバ切断: を呼び出して、MMIOまたはIOポート範囲を利用可能にします。これを実施しないと、ドライバの再ロードができない状態になります。 media_device_delete() メディアデバイスを解放します。解放処理はkref putハンドラによって行われます。

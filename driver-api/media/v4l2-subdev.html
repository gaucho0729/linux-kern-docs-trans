1.7. V4L2サブデバイス¶

多くのドライバがサブデバイスと通信する必要があります。これらのデバイスはさまざまなタスクを実行できますが、最も一般的にはオーディオおよび/またはビデオの多重化、符号化、復号化を処理します。ウェブカメラではセンサーとカメラコントローラーが典型的なサブデバイスです。

通常これらのデバイスはI2Cデバイスですが、必ずしもそうではありません。サブデバイスへのドライバのインターフェースを一貫して提供するため、 v4l2_subdev struct (v4l2-subdev.h) が作成されました。

各サブデバイスドライバは必ず v4l2_subdev struct を持つ必要があります。この構造体は単純なサブデバイスの場合にはスタンドアロンでよいですが、より多くの状態情報を保存する必要がある場合は、より大きな構造体に埋め込まれる場合があります。通常、デバイスデータをカーネルが設定する低レベルのデバイス構造（例： i2c_client) が存在し、そのポインタを v4l2_subdev を使用して v4l2_set_subdevdata()のプライベートデータに保存することをお勧めします。これにより、 v4l2_subdev から実際に低レベルのバス固有のデバイスデータへの移動が容易になります。

また、低レベルの構造体から v4l2_subdevへの移動方法も必要です。一般的なi2c_client構造体ではi2c_set_clientdata()関数呼び出しを使用してポインタを保存します。他のバスでは他の方法を使用する必要があります。 v4l2_subdev ブリッジもサブデバイスごとのプライベートデータを保存する必要があり、例えばブリッジ固有のサブデバイスプライベートデータへのポインタなどです。

構造体はその目的のためのホストプライベートデータを提供し、 v4l2_subdev でアクセスできます。 v4l2_get_subdev_hostdata() および v4l2_set_subdev_hostdata().

ブリッジドライバの観点からは、サブデバイスモジュールをロードし、どこかで v4l2_subdev ポインタを取得する必要があります。I2Cデバイスの場合これは簡単で、 i2c_get_clientdata()を呼び出します。他のバスでは類似の処理が必要です。I2Cバス上のサブデバイスにはヘルパー関数があり、この複雑な作業を自動的に実行します。

Each v4l2_subdev はサブデバイスドライバが実装できる（または実装しない場合がある）関数ポインタを含みます。 NULL サブデバイスは非常に多くの機能を持つため、すべての関数ポインタを含む巨大なops構造体になるのを防ぐため、関数ポインタはカテゴリごとに分類され、各カテゴリには独自のops構造体があります。

トップレベルのops構造体はカテゴリごとのops構造体へのポインタを含み、サブデバイスドライバがそのカテゴリの機能をサポートしない場合、NULLになることがあります。

これは以下のようになります：

struct v4l2_subdev_core_ops {
        int (*log_status)(struct v4l2_subdev *sd);
        int (*init)(struct v4l2_subdev *sd, u32 val);
        ...
};

struct v4l2_subdev_tuner_ops {
        ...
};

struct v4l2_subdev_audio_ops {
        ...
};

struct v4l2_subdev_video_ops {
        ...
};

struct v4l2_subdev_pad_ops {
        ...
};

struct v4l2_subdev_ops {
        const struct v4l2_subdev_core_ops  *core;
        const struct v4l2_subdev_tuner_ops *tuner;
        const struct v4l2_subdev_audio_ops *audio;
        const struct v4l2_subdev_video_ops *video;
        const struct v4l2_subdev_pad_ops *video;
};

コアのopsはすべてのサブデバイスに共通で、他のカテゴリはサブデバイスによって実装されます。例えば、ビデオデバイスはオーディオopsをサポートしない可能性があり、逆もしかりです。

この設定により関数ポインタの数を制限しながら、新しいopsやカテゴリの追加が容易になります。

サブデバイスドライバは以下のコードで v4l2_subdev 構造体を初期化します：

v4l2_subdev_init (sd, &ops).

その後、初期化が必要です sd一意の名前を設定し、モジュール所有者を設定します。i2c ヘルパ関数を使用する場合は、これは自動的に処理されます。

メディアフレームワークとの統合が必要な場合、 media_entity 構造体を初期化する必要があります。 v4l2_subdev （entityフィールド）を呼び出して media_entity_pads_init()エンティティがパッドを持つ場合:

struct media_pad *pads = &my_sd->pads;
int err;

err = media_entity_pads_init(&sd->entity, npads, pads);

pads配列は事前に初期化されている必要があります。 struct media_entity 関数と名前フィールドは必須ですが、リビジョンフィールドは必要に応じて初期化する必要があります。

サブデバイスデバイスノード（存在する場合）が開閉されるときに、エンティティへの参照が自動的に取得/解放されます。

サブデバイスが破壊される前に、メディアエンティティをクリーンアップしないと駄目です:

media_entity_cleanup(&sd->entity);

サブデバイスドライバーがビデオ処理を行い、メディアフレームワークと統合する場合、フォーマット関連の機能を v4l2_subdev_pad_ops …の代わりに v4l2_subdev_video_ops.

この場合、サブデバイスドライバーは link_validate フィールドを設定して、独自のリンク検証関数を提供できます。リンク検証関数は、パイプライン内のリンクごとに呼び出されます。リンクの両端が V4L2 サブデバイスである場合にのみ呼び出されます。ドライバーは、サブデバイス間およびビデオノード間のフォーマット設定の正しさを検証する責任があります。

link_validate 操作が設定されていない場合、デフォルト関数 v4l2_subdev_link_validate_default() が代わりに使用されます。この関数は、リンクのソースとシンクの両方で幅、高さ、およびメディアバスピクセルコードが等しいことを保証します。サブデバイスドライバーは、この関数を独自のチェックに加えて使用して、上記のチェックを実行することも自由です。

1.8. V4L2サブデバイスユーザースペースAPI¶

ブリッジドライバーは通常、ユーザー空間に1つまたは複数のビデオノードを公開し、ビデオノード操作を通じてサブデバイスを制御します v4l2_subdev_ops ビデオノード操作に応じて操作を実行します。これにより、アプリケーションから下位ハードウェアの複雑さが隠されます。複雑なデバイスでは、ビデオノードが提供するよりも細かい制御が必要な場合があります。その場合、 メディアコントローラーAPIを実装するブリッジドライバーは サブデバイス操作をユーザー空間から直接アクセス可能にする選択をします。

名前が v4l-subdevX は、 /dev サブデバイスを直接アクセスするためには、 V4L2_SUBDEV_FL_HAS_DEVNODE 登録前にフラグを設定しなければなりません。

サブデバイスを登録した後、 v4l2_device ドライバーは、すべての登録済みサブデバイスでマークされたものに対してデバイスノードを作成できます V4L2_SUBDEV_FL_HAS_DEVNODE を完了するために必要なコードセクションの開始をこの関数で注釈する必要があります。 v4l2_device_register_subdev_nodes()。これらのデバイスノードは、サブデバイスが登録解除されるときに自動的に削除されます。

デバイスノードはV4L2 APIの一部を処理します。

VIDIOC_QUERYCTRL, VIDIOC_QUERYMENU, VIDIOC_G_CTRL, VIDIOC_S_CTRL, VIDIOC_G_EXT_CTRLS, VIDIOC_S_EXT_CTRLS および VIDIOC_TRY_EXT_CTRLS:

コントロール ioctls は V4L2 で定義されたものと同一であり、動作も完全に一致しています。ただし、サブデバイスで実装されたコントロールのみを扱うという点が唯一の違いです。ドライバによっては、これらのコントロールは 1 つ（または複数）の V4L2 デバイスノードを通じてアクセスすることもできます。

VIDIOC_DQEVENT, VIDIOC_SUBSCRIBE_EVENT および VIDIOC_UNSUBSCRIBE_EVENT

イベント ioctls も V4L2 で定義されたものと同一であり、動作も完全に一致しています。ただし、サブデバイスによって生成されたイベントのみを扱うという点が唯一の違いです。ドライバによっては、これらのイベントが 1 つ（または複数）の V4L2 デバイスノードを通じて報告されることもあります。

イベントを使用したいサブデバイスドライバは、 V4L2_SUBDEV_FL_HAS_EVENTS v4l2_subdev.flags を設定してサブデバイスを登録する前に、 v4l2_subdev.devnode デバイスノードでイベントをキューイングできます。

イベントを適切にサポートするため、 poll() ファイル操作も実装されています。

プライベート ioctls

上記のリストにないすべての ioctls は、コア::ioctl 操作を通じてサブデバイスドライバに直接渡されます。

1.9. 読み取り専用サブデバイスユーザースペース API¶

コネクテッドサブデバイスを直接コアAPI（ v4l2_subdev_ops 構造体を通じて制御するブリッジドライバは、通常、ユーザースペースがサブデバイスデバイスノードを通じて同じパラメータを変更できるようにしたくないので、通常は登録しません。

ユーザースペースに現在のサブデバイス構成を報告する読み取り専用APIは、アプリケーションがデバイスパラメータを変更できないが、サブデバイスデバイスノードを通じてそれらを確認できるようにするため、有効です。

例えば、コンピューテーショナルフォトグラフィーに基づくカメラを実装するには、ユーザースペースがサポートされる各出力解像度ごとの詳細なカメラセンサ構成（スキップ、ビニング、クロッピング、スケーリング）を知る必要があります。このようなユースケースをサポートするため、ブリッジドライバは読み取り専用APIを通じてサブデバイス操作をユーザースペースに公開することがあります。

すべてのサブデバイスを V4L2_SUBDEV_FL_HAS_DEVNODE セットで登録した v4l2_device ドライバは v4l2_device_register_ro_subdev_nodes().

ユーザースペースアプリケーションがサブデバイスデバイスノードで以下の ioctls にアクセスすることを制限しています。 v4l2_device_register_ro_subdev_nodes().

VIDIOC_SUBDEV_S_FMT, VIDIOC_SUBDEV_S_CROP, VIDIOC_SUBDEV_S_SELECTION:

これらの ioctls は、 V4L2_SUBDEV_FORMAT_TRY フォーマットおよび選択矩形にのみ読み取り専用サブデバイスデバイスノードで許可されます。

VIDIOC_SUBDEV_S_FRAME_INTERVAL, VIDIOC_SUBDEV_S_DV_TIMINGS, VIDIOC_SUBDEV_S_STD:

これらの ioctls は読み取り専用サブデバイスノードでは許可されません。

ioctl が許可されない場合、または変更するフォーマットが V4L2_SUBDEV_FORMAT_ACTIVEに設定されている場合、コアは負のエラーコードを返し、errno 変数が -EPERM.

1.10. I2C サブデバイスドライバ¶

これらのドライバは非常に一般的なので、これらのドライバの使用を容易にする特別なヘルパーファンクションが利用可能です（v4l2-common.h).

I2Cドライバーへのサポートを追加する推奨方法は、 v4l2_subdev structを各I2Cデバイスインスタンスに作成されるstate structに埋め込むことです。非常に単純なデバイスはstate structを持っておらず、その場合、単に v4l2_subdev structを作成するだけでよいです。 v4l2_subdev 直接指定できます。

典型的なstate structは次のようになります（'chipname'はチップ名に置き換える）：

struct chipname_state {
        struct v4l2_subdev sd;
        ...  /* additional state fields */
};

を初期化するには、 v4l2_subdev structを以下のように初期化します：

v4l2_i2c_subdev_init(&state->sd, client, subdev_ops);

この関数は、 v4l2_subdev を確保し、 v4l2_subdev とi2c_clientがお互いにポインタを指すようにします。

また、 v4l2_subdev ポインタからchipname_state structへのヘルパーアクセサリーファンクションを追加する必要があります：

static inline struct chipname_state *to_state(struct v4l2_subdev *sd)
{
        return container_of(sd, struct chipname_state, sd);
}

を使用して、 v4l2_subdev structから i2c_client structへの移動を行います：

struct i2c_client *client = v4l2_get_subdevdata(sd);

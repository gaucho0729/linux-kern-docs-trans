8.1.3. cx2341xドライバー¶

8.1.3.1. cx2341xチップのメモリ¶

このセクションでは、cx2341xのメモリマップと、いくつかのレジスタ領域について説明します。

注意

メモリのロングワードはlittle-endian（'intel形式'）です。

警告

この情報は、メモリとレジスタを検索して得られました。この情報は正確でない可能性があり、間違いなく完全ではありません。また、より多くの情報は、コマンドのようなものでメモリ空間を検索することに過ぎません：

ivtvctl -O min=0x02000000,max=0x020000ff

この情報はそのまま受け入れてください。私は常にさらに多くの情報を探しています。レジスタ領域は非常に広いです :-）。

8.1.3.1.1. メモリマップ¶

cx2341xは、PCI BAR0（ベースアドレスレジスタ0）を介してPCIホストに全体の64Mメモリ空間を公開します。ここで示すアドレスは、BAR0に保持されているアドレスに対するオフセットです。

0x00000000-0x00ffffff Encoder memory space
0x00000000-0x0003ffff Encode.rom
???-???         MPEG buffer(s)
???-???         Raw video capture buffer(s)
???-???         Raw audio capture buffer(s)
???-???         Display buffers (6 or 9)

0x01000000-0x01ffffff Decoder memory space
0x01000000-0x0103ffff Decode.rom
???-???         MPEG buffers(s)
0x0114b000-0x0115afff Audio.rom (deprecated?)

0x02000000-0x0200ffff Register Space

8.1.3.1.2. Registers¶

レジスタは、BAR0からの0x02000000オフセットから始まる64kの領域を占めています。すべてのレジスタは32ビット幅です。

DMA Registers 0x000-0xff:

0x00 - Control:
        0=reset/cancel, 1=read, 2=write, 4=stop
0x04 - DMA status:
        1=read busy, 2=write busy, 4=read error, 8=write error, 16=link list error
0x08 - pci DMA pointer for read link list
0x0c - pci DMA pointer for write link list
0x10 - read/write DMA enable:
        1=read enable, 2=write enable
0x14 - always 0xffffffff, if set any lower instability occurs, 0x00 crashes
0x18 - ??
0x1c - always 0x20 or 32, smaller values slow down DMA transactions
0x20 - always value of 0x780a010a
0x24-0x3c - usually just random values???
0x40 - Interrupt status
0x44 - Write a bit here and shows up in Interrupt status 0x40
0x48 - Interrupt Mask
0x4C - always value of 0xfffdffff,
        if changed to 0xffffffff DMA write interrupts break.
0x50 - always 0xffffffff
0x54 - always 0xffffffff (0x4c, 0x50, 0x54 seem like interrupt masks, are
        3 processors on chip, Java ones, VPU, SPU, APU, maybe these are the
        interrupt masks???).
0x60-0x7C - random values
0x80 - first write linked list reg, for Encoder Memory addr
0x84 - first write linked list reg, for pci memory addr
0x88 - first write linked list reg, for length of buffer in memory addr
        (|0x80000000 or this for last link)
0x8c-0xdc - rest of write linked list reg, 8 sets of 3 total, DMA goes here
        from linked list addr in reg 0x0c, firmware must push through or
        something.
0xe0 - first (and only) read linked list reg, for pci memory addr
0xe4 - first (and only) read linked list reg, for Decoder memory addr
0xe8 - first (and only) read linked list reg, for length of buffer
0xec-0xff - Nothing seems to be in these registers, 0xec-f4 are 0x00000000.

エンコーダーバッファ用のメモリ位置 0x700-0x7ff:

これらのレジスタは、エンコーディングに使用される各バッファ領域に関連するメモリ位置のオフセットを示しています。最初に<<1シフトする必要があります。

  • 0x07F8: エンコーダーSDRAMリフレッシュ

  • 0x07FC: エンコーダーSDRAMプリチャージ

デコーダーバッファ用のメモリ位置 0x800-0x8ff:

これらのレジスタは、デコードに使用される各バッファ領域に関連するメモリ位置のオフセットを示しています。最初に<<1シフトする必要があります。

  • 0x08F8: デコーダーSDRAMリフレッシュ

  • 0x08FC: デコーダーSDRAMプリチャージ

その他のメモリ位置:

  • 0x2800: ビデオディスプレイモジュール制御

  • 0x2D00: AO（オーディオ出力？）制御

  • 0x2D24: バイトフラッシュ

  • 0x7000: LSB I2Cライトクロックビット（反転）

  • 0x7004: LSB I2Cライトデータビット（反転）

  • 0x7008: LSB I2Cリードクロックビット

  • 0x700c: LSB I2Cリードデータビット

  • 0x9008: GPIO入力状態取得

  • 0x900c: GPIO出力状態設定

  • 0x9020: GPIO方向（ビット7（GPIO 0..7）- 0:入力、1:出力）

  • 0x9050: SPU制御

  • 0x9054: HWブロックリセット

  • 0x9058: VPU制御

  • 0xA018: ビット6: インターナル待機？

  • 0xA064: APUコマンド

割込みステータスレジスタ0x0040および割込みマスク0x0048のビットの定義。マスクのビットがクリアされている場合、ISRを実行したいです。

  • ビット31 エンコーダー開始キャプチャ

  • ビット30 エンコーダーEOS

  • bit 22 デコーダーデータリクエスト

  • bit 20 デコーダーDMA完了

  • bit 19 デコーダーVBI再挿入

  • bit 18 デコーダーDMAエラー（リンクリスト不良）

8.1.3.3. cx2341xファームウェアのアップロード¶

このドキュメントは、cx2341xファームウェアをカードにアップロードする方法を説明しています。

8.1.3.3.1. 見つける方法¶

このチップを使用する各種プロジェクトのウェブページを参照し、ファームウェアを取得する方法について情報を得てください。

Windowsドライバに保存されたファームウェアは以下の手順で検出できます：

  • 各ファームウェアイメージは256KBバイトです。

  • エンコーダーイメージの1番目の32ビットワードは0x0000da7です

  • デコーダーイメージの1番目の32ビットワードは0x00003a7です

  • 両方のイメージの2番目の32ビットワードは0xaa55bb66です

8.1.3.3.2. ロード方法¶

  • エンコーダーが実行中である場合、FWapiコマンドを実行して停止します。コマンドの完了を待機してください。

  • デコーダーが実行中である場合、FWapiコマンドを実行して停止します。コマンドの完了を待機してください。

  • ディジタイザーにI2Cコマンドを実行してVSYNCイベントの発生を停止します。

  • エンコーダーのファームウェアを停止するFWapiコマンドを実行します。

  • 10ms待機します。

  • デコーダーのファームウェアを停止するFWapiコマンドを実行します。

  • 10ms待機します。

  • レジスタ0x2800に0x00000000を書き込み、ビデオディスプレイモジュールを停止します。

  • レジスタ0x2D00に0x00000005を書き込み、AO（オーディオ出力？）を停止します。

  • レジスタ0xA064に0x00000000を書き込み、APUをpingします。

  • レジスタ0x9058に0xFFFFFFFEを書き込み、VPUを停止します。

  • レジスタ0x9054に0xFFFFFFFFを書き込み、HWブロックをリセットします。

  • レジスタ0x9050に0x00000001を書き込み、SPUを停止します。

  • 10ms待機します。

  • レジスタ0x07FCに0x0000001Aを書き込み、エンコーダーSDRAMのプリチャージを初期化します。

  • レジスタ0x07F8に0x80000640を書き込み、エンコーダーSDRAMのリフレッシュを1μsに初期化します。

  • レジスタ0x08FCに0x0000001Aを書き込み、デコーダーSDRAMのプリチャージを初期化します。

  • レジスタ0x08F8に0x80000640を書き込み、デコーダーSDRAMのリフレッシュを1μsに初期化します。

  • 512ms待機します。（600msが推奨されます）

  • エンコーダーのファームウェアイメージをエンコーダーメモリ空間のオフセット0に転送します。

  • デコーダーのファームウェアイメージをデコーダーメモリ空間のオフセット0に転送します。

  • 読み込み-変更-書き込み操作を実行し、レジスタ0x9050のビット0をクリアしてSPUを再有効化します。

  • 1秒待機します。

  • レジスタ0x9058のビット3と0を読み込み-変更-書き込み操作でクリアし、VPUを再起動する。

  • 1秒待機します。

  • 両方のファームウェアイメージにステータスAPIコマンドを発行して確認する。

8.1.3.4. ファームウェアAPIを呼び出す方法¶

推奨される呼び出し規約はファームウェアメールボックスと呼ばれます。メールボックスは基本的に固定長の配列であり、コールスタックとして機能します。

ファームウェアメールボックスは、エンコーダーおよびデコーダーのメモリ内で16バイトのサインチャートを検索することで見つけることができます。このサインチャートは256バイト境界に位置しています。

サインチャート:

0x78, 0x56, 0x34, 0x12, 0x12, 0x78, 0x56, 0x34,
0x34, 0x12, 0x78, 0x56, 0x56, 0x34, 0x12, 0x78

ファームウェアは20のメールボックスを実装しており、それぞれ20の32ビットワードです。最初の10はAPI呼び出し用に予約されており、次の10はファームウェアがイベント通知に使用します。

コマンドは32ビットの列挙子です。APIの詳細はこの章に記載されています。

戻り値は32ビットの列挙子です。現在は2つの値のみが定義されています：

  • 0=成功

  • -1=コマンド未定義。

16のパラメータ/結果用32ビットフィールドがあります。ドライバーは、呼び出しに必要なすべてのパラメータの値でこれらのフィールドを埋めます。ドライバーは、呼び出しによって返された結果値でこれらのフィールドを上書きします。

タイムアウト値は、ドライバーのハングしたスレッドからカードを保護します。ドライバーが指定されたタイムアウト内に完了した呼び出しを処理しなかった場合、ファームウェアはそのメールボックスをリセットします。

API呼び出しを行うには、ドライバーは各メールボックスを繰り返し処理し、最初に利用可能なメールボックス（ビット0がクリアされているもの）を探します。ドライバーはそのビットを設定し、コマンド列挙子、タイムアウト値、および必要なパラメータを埋めます。その後、ドライバーはパラメータ準備ビット（ビット1）を設定します。ファームウェアは待機中のコマンドをメールボックスでスキャンし、それらを処理し、結果コードを設定します。呼び出しの戻り値を結果値配列に記録し、呼び出し完了ビット（ビット2）を設定します。ビット2が設定されたら、ドライバーは結果を取得し、すべてのフラグをクリアする必要があります。ドライバーがタイムアウトレジスタで設定された時間内にこのタスクを実行しなかった場合、ファームウェアはそのメールボックスをリセットします。

イベント通知はファームウェアからホストに送信されます。ホストはAPIコールを通じてファームウェアに興味のあるイベントを指定します。このコールにより、ファームウェアが使用する通知メールボックスが指定されます。ファームウェアは割込み信号でホストに通知します。使用されるのは16結果フィールドのみで、フラグ、コマンド、戻り値、タイムアウトワードは使用されません。

         output_pixel = destination_pixel
     if 256 > source_alpha > 1:

                         (255 - source_alpha)*destination_pixel)/256

         output_pixel = source_pixel
      if 255 > destination_alpha > 0:
         output_pixel = ((255 - destination_alpha)*source_pixel +
                         (destination_alpha + 1)*destination_pixel)/256

'11' if source_alpha=0:
         source_temp = 0
     if source_alpha=255:
         source_temp = source_pixel*256
     if 255 > source_alpha > 0:
         source_temp = source_pixel*(source_alpha + 1)
     if destination_alpha=0:
         destination_temp = 0
     if destination_alpha=255:
         destination_temp = destination_pixel*256
     if 255 > destination_alpha > 0:

8.1.3.9. cx231xx DMAエンジン¶

このページではcx2341x DMAエンジンが使用する構造と手順について説明します。

8.1.3.9.1. はじめに¶

cx2341x PCIインターフェースはバスマスター機能を備えています。これはカードと主記憶間で大容量のデータをCPUの助けなしに効率的に転送するDMAエンジンを持つことを意味します。ほとんどのハードウェア同様、連続した物理メモリ領域での動作が必須です。これは仮想メモリマシンでは大規模に入手するのが困難です。

そのため、『スキャッターガather』と呼ばれる技術もサポートしています。カードは1回の操作で複数のバッファを転送できます。1つの大容量連続バッファを割り当てる代わりに、ドライバは複数の小さなバッファを割り当てることができます。

実際には、平均的な転送量は約80KB程度でしたが、128KBを超える転送は特にスタートアップ時に頻繁に見られました。128KBという数字は重要で、これはカーネルが通常割り当てられる最大のブロックサイズです。それでも128KBのブロックは入手が難しいため、ドライバ開発者はより小さなブロックサイズを選択し、スキャッターギャッター技術を学ぶべきです。

メールボックス #10 は DMA 転送情報用に予約されています。

注意: ハードウェアはリトルエンディアンデータ（'intel フォーマット'）を期待しています。

8.1.3.9.2. フロー¶

このセクションでは、DMA 転送処理時のイベントの一般的な順序について説明します。詳細情報はこのセクションの後述部分にあります。

  • カードがエンコーダー割込みを発生させます。

  • ドライバがメールボックス #10 から転送タイプ、オフセット、サイズを読み取ります。

  • ドライバが十分な空き DMA バッファからスキャッターギャッター配列を構築します。

  • ドライバが ScheduleDMAtoHost API コールを通じて DMA 転送をスケジュールします。

  • カードが DMA 完了割込みを発生させます。

  • ドライバが DMA 状態レジスタを確認し、エラーをチェックします。

  • ドライバが新たに転送されたバッファを後処理します。

注意! エンコーダー割込みと DMA 完了割込みが同時に発生する可能性があります。(最後の終わりと次の始まりなど)

8.1.3.9.3. メールボックス #10¶

フラグ、コマンド、戻り値、タイムアウトフィールドは無視されます。

  • 名前: メールボックス #10

  • Results[0]: タイプ: 0: MPEG。

  • Results[1]: オフセット: カードのメモリ領域に対する相対位置。

  • Results[2]: サイズ: 転送するバイト数の正確な数値。

私の推測では、StartCapture API が「RAW」のキャプチャタイプを提供しているため、タイプフィールドには YUV および PCM データに対応する他の値が含まれる可能性があります。

8.1.3.9.4. スキャッターギャッター配列¶

スキャッターギャッター配列は、カードに各データブロックのソースと宛先を伝えるための連続的に割り当てられたメモリブロックです。カードの「アドレス」はメールボックス #10 から提供されるオフセットから導出され、ホストアドレスはターゲット DMA バッファの物理メモリ位置です。

各 S-G 配列要素は、3つの32ビットワードからなる構造体です。最初のワードはソースアドレス、2番目のワードは宛先アドレスです。どちらも32ビット全体を占めます。3番目のワードの下位18ビットは転送バイト数を示し、上位ビットは「最後」フラグです。「最後」フラグはカードに DMA_DONE 割込みを発生させる指示です。個人的な経験からすると、このビットを忘れてもカードは依然として「動作」しますが、ストリームがほぼ確実に破損します。

転送数は256の倍数でなければなりません。そのため、ドライバーはターゲットバッファ内の有効データ量を追跡し、それに応じて処理する必要があります。

配列要素:

  • 32ビットソースアドレス

  • 32ビット宛先アドレス

  • 14ビット予約済み（高位ビットは最後のフラグ）

  • 18ビットバイトカウント

8.1.3.9.5. DMA転送状態¶

レジスタ0x0004はDMA転送状態を保持しています:

  • ビット0: 読み込み完了

  • ビット1: 書き込み完了

  • ビット2: DMA読み込みエラー

  • ビット3: DMA書き込みエラー

  • ビット4: スキャッターガーディング配列エラー

8.1.14.3. 1.1 テレビデコーダーのできることとできないこと¶

よく知られているテレビ放送の標準はNTSC/PAL/SECAMです。しかし、フレームをデコードする際にはこの情報だけでは不十分です。テレビ放送の標準にはいくつかのフォーマットがあり、すべてのデコーダーがすべてのフォーマットを処理できるわけではありません。また、ドライバーがサポートする組み合わせもすべてではありません。現在、世界中で11種類のテレビ放送フォーマットが使われています。

CCIRは信号を放送するためのパラメータを定義しています。CCIRはいくつかの標準を定義しています: A,B,D,E,F,G,D,H,I,K,K1,L,M,N,…。CCIRはカラーシステムについてあまり述べていません！！！カラーシステムについて話すと、それがどのように放送されるかについての情報はあまりありません。

CCIR標準のA,E,Fはもう使われていません。

NTSCについて話すとき、通常はCCIR - Mを使用したNTSCカラーシステムを指します。これはアメリカ、日本、メキシコ、カナダ、いくつかの他の国で使われています。

PALについて話すとき、通常はCCIR - B/Gを使用したPALカラーシステムを指します。これは多くの国で使われています。

SECAMについて話すとき、通常はCCIR - Lを使用したSECAMカラーシステムを指します。これはフランスおよびいくつかの他の国で使われています。

他にもSECAMのバージョンとしてCCIR - D/Kがブルガリア、中国、スロバキア、ハンガリー、朝鮮民主主義人民共和国（旧称）、ポーランド、ルーマニア、いくつかの他の国で使われています。

CCIR - HはPALカラーシステム（ときにはSECAM）を使用し、エジプト、リビア、スリランカ、シリア民主主義人民共和国で使われています。

CCIR - IはPALカラーシステムを使用し、イギリス、香港、アイルランド、ナイジェリア、南アフリカ共和国で使われています。

CCIR - NはPALカラーシステムおよびPALフレームサイズを使用し、NTSCのフレームレートを使用します。これはアルゼンチン、ウルグアイ、いくつかの他の国で使われています。

オーディオの放送方法については話しません！

テレビ放送の標準についての良いウェブサイトは以下の通りです： http://www.sony.jp/support/ http://info.electronicwerkstatt.de/bereiche/fernsehtechnik/frequenzen_und_normen/Fernsehnormen/ および http://www.cabl.com/restaurant/channel.html

他にも奇妙なこと: NTSC 4.43 は修正された NTSC で、PAL VCR で NTSC を再生できるものに主に使用される。PAL 60 は NTSC 4.43 と同様のようだ。データシートも NTSC 44 を扱っているが、NTSC 4.43 と同様の可能性がある。NTSC Combs は、デコーダーがコンバーティングフィルタを用いてクロマとルミナを分離するデコードモードのようだ。

しかし、NTSC Combs について確実に確認できなかった。

8.1.14.5. この不機嫌なやつを動かすにはどうすればいいのか¶

zr36067.o をロード。自動検出ができない場合は、card=X insmod オプションを使用し、X は前のセクションで示したカード番号とする。複数のカードがある場合は、card=X1[,X2[,X3,[X4[..]]]] の形式で指定する。

この自動化を行うには、以下の内容を/etc/modprobe.d/zoran.confに追加してください：

options zr36067 card=X1[,X2[,X3[,X4[..]]]] alias char-major-81-0 zr36067

注意すべき点は、この設定がzr36067.o自体をロードするわけではなく、自動的にロードするようにするだけです。xawtvを開始使用する場合、一部のシステムではデバイスがロードされないことがあります。これはユーザーとしてモジュールをロードしようとしているため、権限が拒否される（「permission denied」）ためです。簡単な回避策として、Xをデフォルトで使用する際にはXF86Config-4に「Load "v4l"」を追加するか、起動スクリプト（通常はrc.local）で「v4l-conf -c <device>」を実行することで、起動時にrootアカウントでモジュールがロードされるようにできます。

8.1.14.9. バッファサイズ、品質、出力サイズなどに関する注意事項¶

zr36060は1:2のJPEG圧縮を実行できます。これはチップセットが到達できる理論的な最大値です。ただし、ドライバーは圧縮を最大（サイズ）1:4に制限することもできます。その理由は、一部のカード（例：Buz）が1:2の圧縮を処理できず、数分後にキャプチャを停止してしまうためです。1:4ではほぼ動作します。Buzを使用している場合は、「low_bitrate=1」を指定して1:4の最大圧縮モードに移行してください。

100%のJPEG品質は実際には1:2の圧縮です。フルPALフレーム（720x576）の場合、JPEGフィールドはYUY2形式で保存されるため、フィールドサイズは720x288x16/2ビット/フィールド（2フィールド/フレーム）= 207360バイト/フィールド x 2 = 414720バイト/フレーム（ヘッダーとDHT（ハフマン）、DQT（量子化）テーブルを含めると、1:2圧縮で1フレームあたり約512KBになります。1:4圧縮では、このサイズの半分になります。

マーティン・サミュエルソンによる追加の説明も含まれており、バッファサイズの重要性についても説明しています: – > うーん、本当にそのようには思わないな。現在のドライバ（月曜日の18:00にダウンロード）で得られる出力サイズは10秒あたり: > -q 50 -b 128 : 24.283.332 バイト > -q 50 -b 256 : 48.442.368 > -q 25 -b 128 : 24.655.992 > -q 25 -b 256 : 25.859.820

私は目を覚ましたが、もう一度眠ることができない。時間を潰すために、なぜこの現象が私には不思議に思えないのか説明します。

704ピクセルの幅を使って計算してみましょう。Buzが実際にこの数値を使用しているかどうかは私には重要ではありませんが、今はそれほど気にする必要はありません。

704x288ピクセル、1フィールドは202752ピクセルです。1ブロックあたり64ピクセルで割ると3168ブロックがフィールドあたりになります。1ピクセルは2バイトで構成されるため、1ブロックあたり128バイト、1ブロックあたり1024ビットです。新しいドライバで100%は1:2の圧縮を意味し、最大出力は1ブロックあたり512ビットになります。実際は510ビットですが、計算には512ビットの方が簡単です。

d1q50を指定すると、1ブロックあたり256ビットを望みます。3168ブロックを掛けると811008ビット、101376バイトがフィールドあたりになります。これは素直なビットとバイトの話なので、ビット-per-ピクセルなどの補正は必要ありません。1フィールドあたり101376バイトです。

d1ビデオは1フレームあたり2フィールドを含みます。それらの合計は1フレームあたり202752バイトとなり、それぞれのバッファに1フレームが入ります。

しかし、ちょっと待って！-b128は128KBのバッファを意味します！JPEGデータを202752バイト分詰め込むのは128KBでは不可能です！

ドライバはこの点を認識し、あなたの例で自動的に補正します。この情報をもとに計算してみましょう:

128KBは131072バイトです。このバッファには2フィールドを保存するため、各フィールドには65536バイトが残ります。フィールドあたり3168ブロックを考慮すると、各ブロックあたり20.68686868…バイトが利用可能で、165ビットになります。165ビットしか利用できないのに256ビットを要求するのは不可能です！-q50の指定は静かに無視され、-b128の指定が優先され、結果として-q32に相当します。

これにより、1ブロックあたりのデータレートが165ビットとなり、これを3168倍すると、フィールドあたり65340バイトとなり、許容される65536バイトの範囲内です。現在のドライバにはもう1段階のレート制限があります。指定されたバッファを6/8以上に満たす-q値は受け付けません。(なぜそのようにしているのかは私にはわかりません。「安全を優先する」のが安全な選択肢のように思えます。個人的には、requested-bits-per-blockを1つ減らすなどして、より安全にしていたのではないかと思います。) 165ビット毎ブロックを使用することはできませんが、再度下げて、利用可能なバッファスペースの6/8に合わせる必要があります。結果として1ブロックあたり124ビットとなり、-q24に相当します。128kBのバッファを使用する場合、-d1で-q24以上は使用できません。(PAL、704ピクセル幅…)

3番目の例も同じプロセスを通じて-q24に制限されています。2番目の例は非常に類似した計算を行い、-q48に制限されています。実際に指定した-q値を取得しているのは最後の例で、ファイルサイズを確認すると明確に見えます。

結論：生成された動画の品質はバッファサイズ、品質、zr36060.cモジュールにインスモッドオプションとして'low_bitrate=1'を使用して1:4の圧縮を行うか1:2の圧縮を行うかなど、さまざまな要因に依存します。

タイムアウトが発生する場合は、品質/バッファサイズを下げたり、zr36060.oに'low_bitrate=1'をインスモッドオプションとして使用したりするだけで、Buzによって実際に改善されることが証明されています。

8.1.14.10. ハング/クラッシュ/失敗/なんでも！助けて！¶

カードが独自の割込みを持つことを確認してください（/proc/interruptsを参照）、dmesgの出力を高verbosityで確認してください（zr36067.oをdebug=2でロードし、他のすべてのモジュールをdebug=1でロード）。メインボードが適切であることを確認してください（質問2を参照）、不適切な場合は別のコンピュータでカードをテストしてください。また質問3のノートを確認し、録画が一定時間後に失敗した場合は品質/バッファサイズ/キャプチャサイズを下げてみてください。

すべての対処法が効かない場合は、問題の詳細な説明を含むハードウェア情報（メモリ+ブランド、メインボード+チップセット+ブランド、どのMJPEGカードか、プロセッサ、他の関心のあるPCIカードなど）を明確に記載し、システムのPnP情報（/proc/interrupts、/proc/dma、/proc/devices）、カーネルバージョン、ドライババージョン、glibcバージョン、gccバージョン、および他の関心のある情報も提供してください。さらに高verbosityでのdmesg出力も提供してください。'Contacting'セクションで開発者に連絡する方法を参照してください。

1.13. V4L2 Controls¶

1.13.1. はじめに¶

V4L2コントロールAPIは見た目には単純に見えますが、ドライバで正しく実装するのは非常に難しくなります。しかし、コントロール処理に必要なコードの多くはドライバ固有ではなく、V4Lコアフレームワークに移すことができます。

結局、ドライバ開発者が関心を持つのは以下の部分だけです：

  1. コントロールを追加するにはどうすればよいですか？

  2. コントロールの値を設定するにはどうすればよいですか？（つまりs_ctrl）

そして偶発的に：

  1. コントロールの値を取得するにはどうすればよいですか？（つまりg_volatile_ctrl）

  2. ユーザーが提案したコントロール値を検証するにはどうすればよいですか？（つまりtry_ctrl）

それ以外の処理は中央で一括して行うことができます。

コントロールフレームワークは、V4L2仕様におけるコントロールに関するすべてのルールを中央で実装し、ドライバ開発者にとっての負担を最小限に抑えるために作成されました。

注意点として、コントロールフレームワークはV4L2ドライバ用のstruct v4l2_device と、 struct v4l2_subdev サブデバイスドライバ用のstruct

1.13.2. フレームワーク内のオブジェクト¶

主に2つのオブジェクトがあります：

以下の v4l2_ctrl コントロールのプロパティを記述し、現在値と提案された新しい値を追跡するオブジェクトです。

v4l2_ctrl_handler コントロールを管理するオブジェクトで、所有するv4l2_ctrlオブジェクトのリストと、他のハンドラが所有するコントロールへの参照リストを保持します。

1.13.3. V4L2およびサブデバイスドライバの基本的な使用方法¶

  1. ドライバの準備：

#include <media/v4l2-ctrls.h>

1.1) ドライバのトップレベルstructにハンドラを追加：

V4L2ドライバの場合：

struct foo_dev {
        ...
        struct v4l2_device v4l2_dev;
        ...
        struct v4l2_ctrl_handler ctrl_handler;
        ...
};

サブデバイスドライバの場合：

struct foo_dev {
        ...
        struct v4l2_subdev sd;
        ...
        struct v4l2_ctrl_handler ctrl_handler;
        ...
};

1.2) ハンドラを初期化：

v4l2_ctrl_handler_init(&foo->ctrl_handler, nr_of_controls);

第二引数は、このハンドラが処理する予想されるコントロール数を示すヒントです。これに基づいてハッシュテーブルが割り当てられます。ただし、ヒントに過ぎません。

1.3) コントロールハンドラをドライバに接続：

V4L2ドライバの場合：

foo->v4l2_dev.ctrl_handler = &foo->ctrl_handler;

サブデバイスドライバの場合：

foo->sd.ctrl_handler = &foo->ctrl_handler;

1.4) 最後にハンドラをクリーンアップ：

v4l2_ctrl_handler_free(&foo->ctrl_handler);

  1. コントロールを追加：

非メニュー型のコントロールは、 v4l2_ctrl_new_std():

struct v4l2_ctrl *v4l2_ctrl_new_std(struct v4l2_ctrl_handler *hdl,
                const struct v4l2_ctrl_ops *ops,
                u32 id, s32 min, s32 max, u32 step, s32 def);

メニューおよび整数メニュー型のコントロールは、 v4l2_ctrl_new_std_menu():

struct v4l2_ctrl *v4l2_ctrl_new_std_menu(struct v4l2_ctrl_handler *hdl,
                const struct v4l2_ctrl_ops *ops,
                u32 id, s32 max, s32 skip_mask, s32 def);

ドライバ固有のメニューを持つメニュー型のコントロールは、 v4l2_ctrl_new_std_menu_items():

struct v4l2_ctrl *v4l2_ctrl_new_std_menu_items(
                struct v4l2_ctrl_handler *hdl,
                const struct v4l2_ctrl_ops *ops, u32 id, s32 max,
                s32 skip_mask, s32 def, const char * const *qmenu);

標準の複合型コントロールは、 v4l2_ctrl_new_std_compound():

struct v4l2_ctrl *v4l2_ctrl_new_std_compound(struct v4l2_ctrl_handler *hdl,
                const struct v4l2_ctrl_ops *ops, u32 id,
                const union v4l2_ctrl_ptr p_def);

ドライバ固有のメニューを持つ整数メニュー型のコントロールは、 v4l2_ctrl_new_int_menu():

struct v4l2_ctrl *v4l2_ctrl_new_int_menu(struct v4l2_ctrl_handler *hdl,
                const struct v4l2_ctrl_ops *ops,
                u32 id, s32 max, s32 def, const s64 *qmenu_int);

これらの関数は通常、 v4l2_ctrl_handler_init():

static const s64 exp_bias_qmenu[] = {
       -2, -1, 0, 1, 2
};
static const char * const test_pattern[] = {
        "Disabled",
        "Vertical Bars",
        "Solid Black",
        "Solid White",
};

v4l2_ctrl_handler_init(&foo->ctrl_handler, nr_of_controls);
v4l2_ctrl_new_std(&foo->ctrl_handler, &foo_ctrl_ops,
                V4L2_CID_BRIGHTNESS, 0, 255, 1, 128);
v4l2_ctrl_new_std(&foo->ctrl_handler, &foo_ctrl_ops,
                V4L2_CID_CONTRAST, 0, 255, 1, 128);
v4l2_ctrl_new_std_menu(&foo->ctrl_handler, &foo_ctrl_ops,
                V4L2_CID_POWER_LINE_FREQUENCY,
                V4L2_CID_POWER_LINE_FREQUENCY_60HZ, 0,
                V4L2_CID_POWER_LINE_FREQUENCY_DISABLED);
v4l2_ctrl_new_int_menu(&foo->ctrl_handler, &foo_ctrl_ops,
                V4L2_CID_EXPOSURE_BIAS,
                ARRAY_SIZE(exp_bias_qmenu) - 1,
                ARRAY_SIZE(exp_bias_qmenu) / 2 - 1,
                exp_bias_qmenu);
v4l2_ctrl_new_std_menu_items(&foo->ctrl_handler, &foo_ctrl_ops,
                V4L2_CID_TEST_PATTERN, ARRAY_SIZE(test_pattern) - 1, 0,
                0, test_pattern);
...
if (foo->ctrl_handler.error) {
        int err = foo->ctrl_handler.error;

        v4l2_ctrl_handler_free(&foo->ctrl_handler);
        return err;
}

以下の v4l2_ctrl_new_std() 関数が新しいコントロールのv4l2_ctrlポインタを返す直後に呼び出されます。ただし、コントロールオプスの外でポインタを参照する必要がない場合は、ポインタを保持する必要はありません。

以下の v4l2_ctrl_new_std() 関数は制御IDに基づいてほとんどのフィールドを自動で埋めますが、min、max、step、およびデフォルト値は除きます。これらは最後の4つの引数として渡されます。これらの値はドライバ固有ですが、制御属性（type、name、flagsなど）はすべてグローバルです。制御の現在値はデフォルト値に設定されます。

以下の v4l2_ctrl_new_std_menu() この関数はメニュー制御用に使用され、前の関数と非常に似ています。メニュー制御ではmin引数が常に0であるため、存在しません。stepの代わりにskip_mask引数があります。bit Xが1の場合、メニュー項目Xはスキップされます。

以下の v4l2_ctrl_new_int_menu() 関数は新しい標準整数メニュー制御を作成し、メニュー内にドライバ固有の項目を含みます。v4l2_ctrl_new_std_menuとは異なり、mask引数を持たず、最後の引数として署名された64ビット整数の配列を渡します。この配列は正確なメニュー項目リストを形成します。

以下の v4l2_ctrl_new_std_menu_items() この関数はv4l2_ctrl_new_std_menuと非常に似ていますが、追加のパラメータqmenuを持ちます。qmenuは標準メニュー制御用のドライバ固有メニューです。例として、キャプチャ/ディスプレイ/センサー機器のテストパターン制御が挙げられます。これらのテストパターンはハードウェア固有のため、メニューの内容は機器によって異なります。

何かが失敗した場合、関数はNULLまたはエラーを返し、ctrl_handler->errorにエラーコードを設定します。ctrl_handler->errorがすでに設定されている場合は、何もせず終了します。これはv4l2_ctrl_handler_initが内部データ構造を確保できなかった場合にも同様です。

これにより、ハンドラの初期化と制御の追加を簡単に実行でき、最後にエラーコードのみを確認するだけで済みます。繰り返しのエラーチェックを大幅に省略できます。

制御IDの昇順で制御を追加することをお勧めします。これにより処理がやや速くなります。

  1. 初期設定を強制的に実行するオプション:

v4l2_ctrl_handler_setup(&foo->ctrl_handler);

これはすべての制御に対してs_ctrlを呼び出します。これによりハードウェアがデフォルトの制御値に初期化されます。この操作を行うことをお勧めします。これにより内部データ構造とハードウェアの同期が保証されます。

  1. 最後に: implement the v4l2_ctrl_ops

static const struct v4l2_ctrl_ops foo_ctrl_ops = {
        .s_ctrl = foo_s_ctrl,
};

通常はs_ctrlだけで十分です:

static int foo_s_ctrl(struct v4l2_ctrl *ctrl)
{
        struct foo *state = container_of(ctrl->handler, struct foo, ctrl_handler);

        switch (ctrl->id) {
        case V4L2_CID_BRIGHTNESS:
                write_reg(0x123, ctrl->val);
                break;
        case V4L2_CID_CONTRAST:
                write_reg(0x456, ctrl->val);
                break;
        }
        return 0;
}

制御操作はv4l2_ctrlポインタを引数として呼び出されます。新しい制御値はすでに検証済みなので、ハードウェアレジスタを実際に更新するだけで十分です。

完了です！これは私たちが持つドライバの大部分にとって十分です。コントロール値の検証やQUERYCTRL、QUERY_EXT_CTRLおよびQUERYMENUの実装は必要ありません。また、G/S_CTRLおよびG/TRY/S_EXT_CTRLSも自動的にサポートされます。

注意

残りのセクションではより高度なコントロールのトピックやシナリオについて説明します。実際には上記の基本的な使用方法がほとんどのドライバにとって十分です。

1.13.4. サブデバイスコントロールの継承¶

サブデバイスがV4L2ドライバに登録される際、v4l2_subdevとv4l2_deviceのctrl_handlerフィールドが設定されている場合、サブデバイスのコントロールが自動的にV4L2ドライバにも利用可能になります。サブデバイスドライバにV4L2ドライバに既存のコントロールが含まれている場合、それらはスキップされます（V4L2ドライバはサブデバイスのコントロールを常に上書きできます）。 v4l2_device_register_subdev() ここでは、サブデバイスのコントロールをv4l2_deviceのコントロールに追加する処理が行われます。

ここで起きていることは、 v4l2_device_register_subdev() 呼び出します v4l2_ctrl_add_handler() サブデバイスのコントロールをv4l2_deviceのコントロールに追加することです。

1.13.5. コントロール値の取得¶

制御フレームワーク内でコントロール値を取得するために以下のユニオンが使用されます：

union v4l2_ctrl_ptr {
        s32 *p_s32;
        s64 *p_s64;
        char *p_char;
        void *p;
};

v4l2_ctrl構造体には、現在値と新しい値の両方を取得するために使用できるフィールドが含まれています：

s32 val;
struct {
        s32 val;
} cur;


union v4l2_ctrl_ptr p_new;
union v4l2_ctrl_ptr p_cur;

コントロールが単純なs32型タイプの場合、

&ctrl->val == ctrl->p_new.p_s32
&ctrl->cur.val == ctrl->p_cur.p_s32

他のすべての型についてはctrl->p_cur.p<something>を使用してください。基本的にvalとcur.valフィールドは頻繁に使用されるため、アリアスとみなせます。

制御オプス内でこれらのフィールドを自由に使用できます。valとcur.valはそれ自体で説明がつきません。p_charポインタは、ctrl->maximum + 1長さの文字バッファを指し、常に0終端されています。

コントロールがvolatileフラグでマークされていない限り、p_curフィールドは現在キャッシュされたコントロール値を指します。新しいコントロールを作成する際、この値はデフォルト値と一致させられます。その後、 v4l2_ctrl_handler_setup() この値がハードウェアに渡されます。この関数を呼び出すことは一般的に良い考えです。

新しい値が設定されるたびに、その新しい値が自動的にキャッシュされます。これにより、ほとんどのドライバはg_volatile_ctrl()オプスの実装を必要としません。例外は、連続的に変化するような信号強度などのボルタイルレジスタを返すコントロールです。その場合、g_volatile_ctrlを次のように実装する必要があります：

static int foo_g_volatile_ctrl(struct v4l2_ctrl *ctrl)
{
        switch (ctrl->id) {
        case V4L2_CID_BRIGHTNESS:
                ctrl->val = read_reg(0x123);
                break;
        }
}

g_volatile_ctrlで「new value」ユニオンも使用してください。一般的に、g_volatile_ctrlを実装するコントロールは読み取り専用です。読み取り専用でない場合、コントロールが変化してもV4L2_EVENT_CTRL_CH_VALUEイベントは生成されません。

コントロールをボルタイルとしてマークするには、V4L2_CTRL_FLAG_VOLATILEを設定してください：

ctrl = v4l2_ctrl_new_std(&sd->ctrl_handler, ...);
if (ctrl)
        ctrl->flags |= V4L2_CTRL_FLAG_VOLATILE;

try/s_ctrlで新しい値（ユーザーが渡した値）が埋め込まれ、try_ctrlで編集したりs_ctrlで設定したりできます。'cur'のユニオンには現在の値が含まれており、これを（変更はしないで）使用できます。

s_ctrlが0（OK）を返す場合、制御フレームワークが新しい最終的な値を'cur'ユニオンにコピーします。

g_volatile/s/try_ctrl内では、同じハンドラが所有するすべてのコントロールの値にアクセスできます（ハンドラのロックが保持されているため）。他のハンドラが所有するコントロールの値にアクセスする場合は、デッドロックを引き起こさないよう注意が必要です。

制御操作の外では、ドライバで単一のコントロール値を安全に取得または設定するには、補助関数を通じて行います：

s32 v4l2_ctrl_g_ctrl(struct v4l2_ctrl *ctrl);
int v4l2_ctrl_s_ctrl(struct v4l2_ctrl *ctrl, s32 val);

これらの関数はVIDIOC_G/S_CTRL ioctlsと同様に制御フレームワークを通じて動作します。ただし、制御操作g_volatile/s/try_ctrl内でこれらを使用すると、補助関数がハンドラをロックするためデッドロックが発生します。

ハンドラのロックを自分で取得することもできます：

mutex_lock(&state->ctrl_handler.lock);
pr_info("String value is '%s'\n", ctrl1->p_cur.p_char);
pr_info("Integer value is '%s'\n", ctrl2->cur.val);
mutex_unlock(&state->ctrl_handler.lock);

1.13.6. メニュー コントロール¶

v4l2_ctrl構造体にはこのユニオンが含まれています：

union {
        u32 step;
        u32 menu_skip_mask;
};

メニュー コントロールではmenu_skip_maskが使用されます。これは特定のメニュー項目を簡単に除外できるようにするためのものです。これはVIDIOC_QUERYMENUの実装で使用され、特定のメニュー項目が存在しない場合に-EINVALを返すことができます。注意点として、VIDIOC_QUERYCTRLは常にメニュー コントロールに対してステップ値1を返します。

MPEG Audio Layer II Bitrateメニュー コントロールの例は、メニューが標準化された可能ビットレートの一覧である場合です。しかし実際のハードウェア実装では、これらの中から一部のみをサポートします。スキップマスクを設定することで、フレームワークにどのメニュー項目をスキップすべきかを指定できます。スキップマスクを0に設定すると、すべてのメニュー項目がサポートされます。

このマスクは、カスタムコントロール用のv4l2_ctrl_config構造体を通じて設定するか、以下のように呼び出すことで設定できます： v4l2_ctrl_new_std_menu().

1.13.7. カスタム コントロール¶

ドライバ固有のコントロールは、以下のように作成できます： v4l2_ctrl_new_custom():

static const struct v4l2_ctrl_config ctrl_filter = {
        .ops = &ctrl_custom_ops,
        .id = V4L2_CID_MPEG_CX2341X_VIDEO_SPATIAL_FILTER,
        .name = "Spatial Filter",
        .type = V4L2_CTRL_TYPE_INTEGER,
        .flags = V4L2_CTRL_FLAG_SLIDER,
        .max = 15,
        .step = 1,
};

ctrl = v4l2_ctrl_new_custom(&foo->ctrl_handler, &ctrl_filter, NULL);

最後の引数はprivポインタであり、ドライバ固有のプライベートデータを設定できます。

v4l2_ctrl_config構造体にもis_privateフラグを設定するためのフィールドがあります。

nameフィールドが設定されていない場合、フレームワークはこれを標準コントロールとみなし、name、type、flagsフィールドを適切に埋めます。

1.13.8. アクティブおよび取得中のコントロール¶

コントロール間の関係がより複雑になると、コントロールを有効または無効にする必要がある場合があります。たとえば、Chroma AGC コントロールがオンになっている場合、Chroma Gain コントロールは無効になります。つまり、値を設定することはできますが、自動ゲイン制御がオンになっている間はハードウェアによって使用されません。通常、ユーザーインターフェースはこのような入力フィールドを無効化できます。

「active」ステータスを設定するには v4l2_ctrl_activate()を使用します。デフォルトではすべてのコントロールが有効です。フレームワークがこのフラグをチェックしないことに注意してください。これはグラフィカルユーザーインターフェース（GUI）専用のものです。この関数は通常、s_ctrl 内から呼び出されます。

もう一つのフラグは「grabbed」フラグです。grabbed になっているコントロールは、他のリソースによって使用されているため、変更できません。典型的な例は、キャプチャが進行中である間変更できない MPEG ビットレートコントロールです。

コントロールを「grabbed」状態に設定する場合、 v4l2_ctrl_grab()でこのコントロールを設定しようとした際、フレームワークは -EBUSY を返します。この v4l2_ctrl_grab() 関数は通常、ドライバがストリーミングを開始または停止するときに呼び出されます。

1.13.9. コントロールクラスタ¶

デフォルトではすべてのコントロールは他のコントロールとは独立しています。しかし、より複雑なシナリオでは、あるコントロールが他のコントロールに依存する場合があります。その場合、これらを「クラスタ」にします:

struct foo {
        struct v4l2_ctrl_handler ctrl_handler;
#define AUDIO_CL_VOLUME (0)
#define AUDIO_CL_MUTE   (1)
        struct v4l2_ctrl *audio_cluster[2];
        ...
};

state->audio_cluster[AUDIO_CL_VOLUME] =
        v4l2_ctrl_new_std(&state->ctrl_handler, ...);
state->audio_cluster[AUDIO_CL_MUTE] =
        v4l2_ctrl_new_std(&state->ctrl_handler, ...);
v4l2_ctrl_cluster(ARRAY_SIZE(state->audio_cluster), state->audio_cluster);

以降、同じクラスタに属するコントロールのうち1つ以上が設定（または取得、または試行）されると、常に最初のコントロール（この例では「volume」）のコントロール操作のみが呼び出されます。これにより、新しい複合コントロールを有効にします。C言語の「struct」の仕組みに似ています。

したがって、s_ctrl が V4L2_CID_AUDIO_VOLUME を引数として呼ばれた場合、audio_cluster に属する2つのコントロールをすべて設定する必要があります:

static int foo_s_ctrl(struct v4l2_ctrl *ctrl)
{
        struct foo *state = container_of(ctrl->handler, struct foo, ctrl_handler);

        switch (ctrl->id) {
        case V4L2_CID_AUDIO_VOLUME: {
                struct v4l2_ctrl *mute = ctrl->cluster[AUDIO_CL_MUTE];

                write_reg(0x123, mute->val ? 0 : ctrl->val);
                break;
        }
        case V4L2_CID_CONTRAST:
                write_reg(0x456, ctrl->val);
                break;
        }
        return 0;
}

上記の例では、VOLUME の場合、以下のものが同等です:

ctrl == ctrl->cluster[AUDIO_CL_VOLUME] == state->audio_cluster[AUDIO_CL_VOLUME]
ctrl->cluster[AUDIO_CL_MUTE] == state->audio_cluster[AUDIO_CL_MUTE]

実際にはこのようなクラスタ配列を使用する作業は非常に手間がかかるため、代わりに以下の同等の方法が使われます:

struct {
        /* audio cluster */
        struct v4l2_ctrl *volume;
        struct v4l2_ctrl *mute;
};

匿名構造体を使用してこれらの2つのコントロールポインタを明確に「クラスタ」しますが、それ以外の用途はありません。効果は2つのコントロールポインタを持つ配列を作成するのと同じです。したがって、以下のようにできます:

state->volume = v4l2_ctrl_new_std(&state->ctrl_handler, ...);
state->mute = v4l2_ctrl_new_std(&state->ctrl_handler, ...);
v4l2_ctrl_cluster(2, &state->volume);

そして、foo_s_ctrl ではこれらのポインタを直接使用できます: state->mute->val.

クラスタ内のコントロールがNULLになる可能性があることに注意してください。たとえば、ミュートがハードウェアがその機能をサポートしていないため追加されなかった場合（その機能をサポートしていないため）、ミュートはNULLになります。このような場合、クラスタ内のコントロールは2つありますが、実際にインスタンス化されているのは1つだけです。唯一の制限は、クラスタの「マスターコントロール」である最初のコントロールが常に存在することです。マスターコントロールはクラスタを特定し、v4l2_ctrl_ops構造体へのポインタを提供します。

クラスタ配列内のすべてのコントロールは、有効なコントロールかNULLに初期化される必要があります。

まれなケースでは、ユーザーが明示的に設定したクラスタ内のどのコントロールかを知る必要があります。この場合、各コントロールの「is_new」フラグを確認してください。たとえば、ボリューム/ミュートクラスタの場合、ユーザーがVIDIOC_S_CTRLでミュートのみを呼び出した場合、ミュートコントロールの「is_new」フラグが設定されます。ユーザーがVIDIOC_S_EXT_CTRLSでミュートとボリュームの両方を呼び出した場合、両方のコントロールの「is_new」フラグが1になります。

「is_new」フラグは常に1になります v4l2_ctrl_handler_setup().

1.13.10. オートゲイン/ゲイン型コントロールの処理：オートクラスタ¶

コントロールクラスタの一般的なタイプは、「auto-foo/foo」型のコントロールを処理するものです。典型的な例はオートゲイン/ゲイン、オートエキスポージャー/エキスポージャー、オートホワイトバランス/レッドバランス/ブルーバランスです。すべての場合において、他のコントロールがハードウェアによって自動的に処理されるか、ユーザーによって手動で制御されるかを決定するコントロールが1つあります。

クラスタが自動モードの場合、手動コントロールは非アクティブかつボリューティルとしてマークされるべきです。ボリューティルコントロールが読み込まれる際には、g_volatile_ctrl操作がハードウェアの自動モードによって設定された値を返す必要があります。

クラスタが手動モードに設定された場合、手動コントロールは再びアクティブになり、ボリューティルフラグはクリアされます（手動モード中にg_volatile_ctrl操作は呼ばれません）。さらに手動モードに切り替える直前に、自動モードによって決定された現在の値が新しい手動値としてコピーされます。

最後に、オートコントロールにV4L2_CTRL_FLAG_UPDATEフラグを設定する必要があります。オートコントロールの変更は手動コントロールのフラグに影響を与えるためです。

この処理を簡略化するために、v4l2_ctrl_clusterの特別な変種が導入されました：

void v4l2_ctrl_auto_cluster(unsigned ncontrols, struct v4l2_ctrl **controls,
                            u8 manual_val, bool set_volatile);

最初の2つの引数はv4l2_ctrl_clusterと同一です。3番目の引数はフレームワークに、クラスタが手動モードに切り替わる値を指定します。最後の引数は、非自動制御に対してV4L2_CTRL_FLAG_VOLATILEフラグをオプションで設定します。falseの場合、手動制御は常に揮発性ではありません。ハードウェアが自動モードで決定された値を読み戻すオプションを提供しない場合（例: 自動ゲインが有効な場合、ハードウェアが現在のゲイン値を取得できない）に通常使用します。

クラスタの最初の制御は「auto」制御とみなされます。

この関数を使用することで、複雑なフラグや揮発性の処理をすべて扱う必要がありません。

1.13.11. VIDIOC_LOG_STATUSサポート¶

このioctlは、ドライバの現在状態をカーネルログにダンプできます。v4l2_ctrl_handler_log_status(ctrl_handler, prefix)は、指定されたハンドラが所有する制御の値をログにダンプします。プレフィックスを指定することも可能です。プレフィックスがスペースで終わっていなければ、自動的に「: 」が追加されます。

1.13.12. 異なるビデオノード用の異なるハンドラ¶

通常、V4L2ドライバはすべてのビデオノードに共通する1つの制御ハンドラを持ちます。ただし、異なるビデオノードに異なる制御ハンドラを指定することも可能です。これを実現するには、手動でctrl_handlerフィールドを設定します struct video_device.

サブデバイスが関与していない場合は問題ありませんが、サブデバイスが関与している場合は、サブデバイスの制御をグローバル制御ハンドラに自動的にマージするのをブロックする必要があります。これは、ctrl_handlerフィールドを struct v4l2_device NULLに設定することで実現します。これ以降、 v4l2_device_register_subdev() サブデバイスの制御をグローバル制御ハンドラにマージしなくなります。

各サブデバイスが追加された後、v4l2_ctrl_add_handlerを手動で呼び出して、サブデバイスの制御ハンドラ（sd->ctrl_handler）を目的の制御ハンドラに追加する必要があります。この制御ハンドラは、video_device固有のものであったり、video_deviceの一部に特化したものであったりします。たとえば、ラジオデバイスノードはオーディオ制御のみを持ち、ビデオおよびVBIデバイスノードはオーディオおよびビデオ制御に共通の制御ハンドラを持ちます。

あるハンドラ（例：ラジオデバイスノード用）が別のハンドラ（例：ビデオデバイスノード用）のサブセットである場合、まず最初のハンドラに制御を追加し、次に他のハンドラに制御を追加し、最後に最初のハンドラを二つ目のハンドラに追加する必要があります。たとえば：

v4l2_ctrl_new_std(&radio_ctrl_handler, &radio_ops, V4L2_CID_AUDIO_VOLUME, ...);
v4l2_ctrl_new_std(&radio_ctrl_handler, &radio_ops, V4L2_CID_AUDIO_MUTE, ...);
v4l2_ctrl_new_std(&video_ctrl_handler, &video_ops, V4L2_CID_BRIGHTNESS, ...);
v4l2_ctrl_new_std(&video_ctrl_handler, &video_ops, V4L2_CID_CONTRAST, ...);
v4l2_ctrl_add_handler(&video_ctrl_handler, &radio_ctrl_handler, NULL);

最後の引数は v4l2_ctrl_add_handler() フィルターファンクションであり、どの制御を追加するかをフィルタリングできます。すべての制御を追加したい場合はNULLに設定してください。

あるいは、特定の制御をハンドラに追加することもできます:

volume = v4l2_ctrl_new_std(&video_ctrl_handler, &ops, V4L2_CID_AUDIO_VOLUME, ...);
v4l2_ctrl_new_std(&video_ctrl_handler, &ops, V4L2_CID_BRIGHTNESS, ...);
v4l2_ctrl_new_std(&video_ctrl_handler, &ops, V4L2_CID_CONTRAST, ...);

行うべきではないことは、2つのハンドラに対して同じコントロールを2つ作成することです。例えば：

v4l2_ctrl_new_std(&radio_ctrl_handler, &radio_ops, V4L2_CID_AUDIO_MUTE, ...);
v4l2_ctrl_new_std(&video_ctrl_handler, &video_ops, V4L2_CID_AUDIO_MUTE, ...);

これは悪い例です。ラジオのミュートを有効にしても、ビデオのミュートコントロールは変更されません。ルールは、1つのコントロールを1つのハードウェアの「ノブ」に対して1つずつ持つことです。

1.13.13. コントロールの検出¶

通常は自分でコントロールを作成しており、そのポインタを自分の構造体に保存できます。 struct v4l2_ctrl pointer into your own struct.

しかし、他のハンドラからコントロールを検出する必要がある場合もあります。例えば、サブデバイスからボリュームコントロールを検出する必要がある場合です。

これを実行するには、v4l2_ctrl_findを呼び出します：

struct v4l2_ctrl *volume;

volume = v4l2_ctrl_find(sd->ctrl_handler, V4L2_CID_AUDIO_VOLUME);

v4l2_ctrl_findはハンドラをロックするため、使用場所に注意が必要です。例えば、これは良い例ではありません：

struct v4l2_ctrl_handler ctrl_handler;

v4l2_ctrl_new_std(&ctrl_handler, &video_ops, V4L2_CID_BRIGHTNESS, ...);
v4l2_ctrl_new_std(&ctrl_handler, &video_ops, V4L2_CID_CONTRAST, ...);

…そしてvideo_ops.s_ctrl:

case V4L2_CID_BRIGHTNESS:
        contrast = v4l2_find_ctrl(&ctrl_handler, V4L2_CID_CONTRAST);
        ...

s_ctrlがフレームワークによって呼び出される際、ctrl_handler.lockはすでに取得されているため、同じハンドラから別のコントロールを検出しようとするとデッドロックします。

コントロール操作内でこの関数を使用しないことが推奨されます。

1.13.14. コントロールの継承を防ぐ¶

1つのコントロールハンドラが別のハンドラにv4l2_ctrl_add_handlerで追加される場合、デフォルトでは1つのハンドラのすべてのコントロールがもう一方にマージされます。しかし、サブデバイスが低レベルのコントロールを含んでいて、一部の高度な埋め込みシステムでは必要ですが、消費者向けハードウェアでは不要な場合があります。その場合は、これらの低レベルのコントロールをサブデバイス内に局所的に保つ必要があります。これを実現するには、コントロールの'is_private'フラグを1に設定します：

static const struct v4l2_ctrl_config ctrl_private = {
        .ops = &ctrl_custom_ops,
        .id = V4L2_CID_...,
        .name = "Some Private Control",
        .type = V4L2_CTRL_TYPE_INTEGER,
        .max = 15,
        .step = 1,
        .is_private = 1,
};

ctrl = v4l2_ctrl_new_custom(&foo->ctrl_handler, &ctrl_private, NULL);

これにより、v4l2_ctrl_add_handlerが呼び出されるときにこれらのコントロールはスキップされます。

1.13.15. V4L2_CTRL_TYPE_CTRL_CLASS コントロール¶

このタイプのコントロールは、GUIがコントロールクラスの名前を取得するために使用できます。完全なGUIは、複数のタブを持つダイアログを作成でき、各タブに特定のコントロールクラスに属するコントロールを配置できます。各タブの名前は、ID <control class | 1> の特別なコントロールをクエリすることで取得できます。

ドライバはこれに気を配る必要はありません。フレームワークが自動的に、新しいコントロールクラスに属する最初のコントロールが追加されるたびに、このタイプのコントロールを追加します。

1.13.16. 通知コールバックの追加¶

ときどき、プラットフォームやブリッジドライバがサブデバイスドライバのコントロールが変化したときに通知される必要があります。これを実現するには、次の関数を呼び出します：

void v4l2_ctrl_notify(struct v4l2_ctrl *ctrl,
        void (*notify)(struct v4l2_ctrl *ctrl, void *priv), void *priv);

指定されたコントロールの値が変化するたびに、notifyコールバックが呼ばれます。コントロールのハンドラロックが保持されている状態でnotify関数が呼ばれます。

1つの制御ハンドラに対しては、通知関数は1つしか存在できません。他の通知関数を設定しようとするとWARN_ONが発生します。

1.14. Videobufフレームワーク¶

著者: Jonathan Corbet <corbet@lwn.net>

現在のバージョンは2.6.33です

注意

ビデオバッファはvideobuf2に置き換えられました。新規ドライバでは使用しないでください。

1.14.1. はじめに¶

ビデオバッファレイヤーは、V4L2ドライバとユーザー空間の間の一種の接着層として機能します。これはビデオフレームの保存に必要なバッファの割当および管理を担当します。read()、poll()、mmap()などの多くの標準的なPOSIX I/Oシステムコールを実装するための関数セットがあり、またV4L2 ioctl()コールの大部分に関連するストリーミングI/Oに関する関数セットもあります。ビデオバッファを使用するとドライバ作成者にいくつかの設計選択肢を課すものの、その結果としてドライバ内のコード量が減り、V4L2ユーザー空間APIの一貫した実装が得られます。

1.14.2. バッファの種類¶

すべてのビデオデバイスが同じ種類のバッファを使用するわけではありません。実際には、少なくとも3つの一般的な変種があります：

  • 物理的および（カーネル）仮想アドレス空間の両方で分散しているバッファ。ほぼすべてのユーザー空間バッファがこのように構成されていますが、可能であればカーネル空間のバッファも同様に割当てるのが合理的です。残念ながら常に可能ではありません。この種のバッファを処理するには、scatter/gather DMA操作を実行できるハードウェアが必要です。

  • 物理的に分散しているが、仮想的に連続しているバッファ。つまり、 vmalloc()関数で割当てるバッファです。これらのバッファはDMA操作には使いにくいですが、DMAが利用できない状況でも仮想的に連続したバッファが便利な場合に役立ちます。

  • 物理的に連続しているバッファ。このようなバッファの割当ては、フラグメンテーションのあるシステムでは信頼性が低く、単純なDMAコントローラーはこれ以外の処理はできません。

ビデオバッファはすべての3つの種類のバッファと対応できますが、ドライバ作成者は最初に1つを選択し、ドライバ設計に合わせる必要があります。

[4番目のバッファの種類があることに留意してください：システムのビデオメモリ内に配置される「オーバーレイ」バッファです。オーバーレイ機能はほとんどの用途では非推奨とされていますが、システムオンチップドライバではパフォーマンスの向上が理由でこの技術が使われることがあります。オーバーレイバッファは散在型バッファの一種として扱えますが、カーネル内での実装は極めて少なく、この技術の説明は本ドキュメントの範囲外です。]

1.14.3. データ構造、コールバック、および初期化¶

使用するバッファの種類によって、ドライバは以下のファイルのいずれかを含める必要があります:

<media/videobuf-dma-sg.h>           /* Physically scattered */
<media/videobuf-vmalloc.h>          /* vmalloc() buffers    */
<media/videobuf-dma-contig.h>       /* Physically contiguous */

V4L2デバイスを記述するドライバのデータ構造には、バッファキューの管理に使用するstruct videobuf_queueインスタンスと、利用可能なバッファのキューを管理するlist_headが必要です。また、キューを保護するための割り込み安全なスピンロックも用意する必要があります。

次に、videobufがバッファの管理を処理するのに役立つ4つのシンプルなコールバック関数を書く必要があります:

struct videobuf_queue_ops {
    int (*buf_setup)(struct videobuf_queue *q,
                     unsigned int *count, unsigned int *size);
    int (*buf_prepare)(struct videobuf_queue *q,
                       struct videobuf_buffer *vb,
                       enum v4l2_field field);
    void (*buf_queue)(struct videobuf_queue *q,
                      struct videobuf_buffer *vb);
    void (*buf_release)(struct videobuf_queue *q,
                        struct videobuf_buffer *vb);
};

buf_setup()はストリーミングを開始する際のI/Oプロセスの初期段階に呼び出され、I/Oストリームについてvideobufに情報を提供します。countパラメータは使用するバッファの推奨数を示しますが、ドライバはその有効性を確認し、必要に応じて調整する必要があります。実用上、適切なストリーミングには少なくとも2つのバッファが必要で、各デバイスごとに最大値（32を越えてはならない）が通常設定されます。sizeパラメータは各フレームデータの予想される（最大）サイズに設定する必要があります。

バッファ（struct videobuf_bufferポインタの形式）はbuf_prepare()に渡され、バッファのサイズ、幅、高さ、フィールドフィールドを適切に設定する必要があります。バッファのstateフィールドがVIDEOBUF_NEEDS_INITの場合、ドライバは以下の関数に渡す必要があります:

int videobuf_iolock(struct videobuf_queue* q, struct videobuf_buffer *vb,
                    struct v4l2_framebuffer *fbuf);

この呼び出しは通常、バッファのメモリを割り当てる処理を行います。最後に、buf_prepare()関数はバッファのstateをVIDEOBUF_PREPAREDに設定する必要があります。

バッファがI/Oキューに登録される際にはbuf_queue()に渡され、ドライバの利用可能なバッファリストに追加され、stateをVIDEOBUF_QUEUEDに設定する必要があります。注意点として、この関数はキューのスピンロックを保持した状態で呼び出されるため、再度取得しようとすると処理が停止します。これは経験からの忠告です。また、videobufはキュー内の最初のバッファを待機する可能性があるため、その前に他のバッファを追加すると処理が妨げられる可能性があります。そのため、 list_add_tail() を用いてバッファをキューに追加してください。

最後に、バッファがもはや使用されない場合、buf_release()が呼び出されます。ドライバはバッファにI/Oが進行していないことを確認した後、適切な解放処理を実行する必要があります:

/* Scatter/gather drivers */
int videobuf_dma_unmap(struct videobuf_queue *q,
                       struct videobuf_dmabuf *dma);
int videobuf_dma_free(struct videobuf_dmabuf *dma);

/* vmalloc drivers */
void videobuf_vmalloc_free (struct videobuf_buffer *buf);

/* Contiguous drivers */
void videobuf_dma_contig_free(struct videobuf_queue *q,
                              struct videobuf_buffer *buf);

バッファがI/O下でないことを確認するには、以下の関数に渡す必要があります:

int videobuf_waiton(struct videobuf_buffer *vb, int non_blocking, int intr);

ここで、vbはバッファ、non_blockingは非ブロッキングI/Oを使用するかどうかを示し（buf_release()の場合はゼロにする必要があります）、intrは割り込み可能な待機を使用するかどうかを制御します。

1.14.4. ファイル操作¶

この時点で、多くの作業はすでに完了しており、残りの多くは他のドライバコールバックの実装にvideobufコールを挿入する作業です。最初のステップはopen()関数で、この関数はvideobufキューを初期化する必要があります。使用する関数はバッファの種類により異なります:

void videobuf_queue_sg_init(struct videobuf_queue *q,
                            struct videobuf_queue_ops *ops,
                            struct device *dev,
                            spinlock_t *irqlock,
                            enum v4l2_buf_type type,
                            enum v4l2_field field,
                            unsigned int msize,
                            void *priv);

void videobuf_queue_vmalloc_init(struct videobuf_queue *q,
                            struct videobuf_queue_ops *ops,
                            struct device *dev,
                            spinlock_t *irqlock,
                            enum v4l2_buf_type type,
                            enum v4l2_field field,
                            unsigned int msize,
                            void *priv);

void videobuf_queue_dma_contig_init(struct videobuf_queue *q,
                                   struct videobuf_queue_ops *ops,
                                   struct device *dev,
                                   spinlock_t *irqlock,
                                   enum v4l2_buf_type type,
                                   enum v4l2_field field,
                                   unsigned int msize,
                                   void *priv);

いずれの場合もパラメータは同じです: qはデバイスのキュー構造体、opsは上記で説明したコールバックのセット、devはこのビデオデバイスのデバイス構造体、irqlockはデータ構造へのアクセスを保護する割り込み安全なスピンロック、typeはデバイスが使用するバッファの種類（カメラはV4L2_BUF_TYPE_VIDEO_CAPTUREを使用します）、fieldはキャプチャされるフィールドを示し（進捗デバイスでは通常V4L、msizeはstruct videobuf_buffer周辺の含む構造体のサイズ、privはプライベートデータポインタでstruct videobuf_queueのpriv_dataフィールドに表示されます。注意: これらはvoid関数であり、明らかに失敗には耐性があります。

V4L2キャプチャドライバは、read()システムコールとより複雑なストリーミングメカニズムの2つのAPIのいずれかをサポートできます。一般的には、すべてのアプリケーションがデバイスと動作できるようにするため、両方をサポートする必要があります。videobufは同じコードでこれを簡単に実現します。read()を実装するには、ドライバは以下のいずれかの関数を呼び出すだけで十分です:

ssize_t videobuf_read_one(struct videobuf_queue *q,
                          char __user *data, size_t count,
                          loff_t *ppos, int nonblocking);

ssize_t videobuf_read_stream(struct videobuf_queue *q,
                             char __user *data, size_t count,
                             loff_t *ppos, int vbihack, int nonblocking);

これらの関数のいずれもdataにフレームデータを読み込み、実際に読み込んだ量を返します。違いは、videobuf_read_one()は単一のフレームのみを読み込み、videobuf_read_stream()はアプリケーションが要求したcountに応じて複数のフレームを読み込むことです。典型的なドライバread()実装では、キャプチャエンジンを起動し、上記の関数のいずれかを呼び出し、その後エンジンを停止して戻ります（よりスマートな実装では、次のread()呼び出しが近い将来に来るのを予測してエンジンを一時的に動作させることもあります）。

poll()関数は通常、以下の直接呼び出しで実装できます:

unsigned int videobuf_poll_stream(struct file *file,
                                  struct videobuf_queue *q,
                                  poll_table *wait);

実際に使用される待機キューは、最初に利用可能なバッファに関連付けられたものです。

ストリーミングI/Oがカーネル空間バッファに行われる場合、ドライバはmmap()システムコールをサポートしなければなりません。多くのV4L2ドライバでは、複雑なmmap()実装は単一の呼び出しに簡略化されます:

int videobuf_mmap_mapper(struct videobuf_queue *q,
                         struct vm_area_struct *vma);

その他はvideobufコードが処理します。

release()関数には2つの別々のvideobufコールが必要です。

void videobuf_stop(struct videobuf_queue *q);
int videobuf_mmap_free(struct videobuf_queue *q);

videobuf_stop()の呼び出しは、進行中のI/Oを終了させます。ただし、キャプチャエンジンを停止するのはドライバの責任です。videobuf_mmap_free()の呼び出しは、すべてのバッファがアンマップされていることを保証します。そうであれば、すべてのバッファがbuf_release()コールバックに渡されます。バッファがマップされている場合、videobuf_mmap_free()はエラーコードを返します。目的は、バッファがマップされている場合にファイルディスクリプタのクローズが失敗するようにすることですが、2.6.32カーネルのすべてのドライバはその戻り値を無視しています。

1.14.5. ioctl()操作¶

V4L2 APIには、ユーザー空間から提供される多くのioctl()コマンドに対応するドライバコールバックの長リストが含まれています。そのうち、ストリーミングI/Oに関連するいくつかのコールバックは、ほぼ直接videobufの呼び出しに変換されます。関連するアシスタント関数は以下の通りです。

int videobuf_reqbufs(struct videobuf_queue *q,
                     struct v4l2_requestbuffers *req);
int videobuf_querybuf(struct videobuf_queue *q, struct v4l2_buffer *b);
int videobuf_qbuf(struct videobuf_queue *q, struct v4l2_buffer *b);
int videobuf_dqbuf(struct videobuf_queue *q, struct v4l2_buffer *b,
                   int nonblocking);
int videobuf_streamon(struct videobuf_queue *q);
int videobuf_streamoff(struct videobuf_queue *q);

例えば、VIDIOC_REQBUFS呼び出しは、ドライバのvidioc_reqbufs()コールバック呼び出しに変換され、これは通常、適切なstruct videobuf_queueポインタを特定し、videobuf_reqbufs()に渡すだけです。これらのサポート関数は、多くのV4L2ドライバでバッファ管理のボイラープレートを大幅に置き換えることができます。

vidioc_streamon()およびvidioc_streamoff()関数は、キャプチャエンジンの開始と停止を扱う必要があるため、やや複雑になります。

1.14.6. バッファの割り当て¶

これまでのところ、バッファについて話してきましたが、バッファの割当方法については見てきませんでした。割当に関しては、ドライバがvideobufレイヤーに完全にバッファ割当を委譲することも可能です。その場合、バッファは匿名ユーザー空間ページとして割当され、非常に散らばった状態になります。アプリケーションがユーザー空間バッファを使用している場合、割当は必要ありません。videobufレイヤーがget_user_pages()を呼び出し、scatterlist配列を埋めることを担当します。

ドライバが独自のメモリ割当を行う必要がある場合は、vidioc_reqbufs()関数内で行うべきです。 RCU保護データ構造からデータ要素を削除した後、 videobuf_reqbufs()を呼び出します。最初のステップは以下の呼び出しが必要です：

struct videobuf_dmabuf *videobuf_to_dma(struct videobuf_buffer *buf);

返されたvideobuf_dmabuf構造体（<media/videobuf-dma-sg.h>で定義）にはいくつかの関連するフィールドが含まれます：

struct scatterlist  *sglist;
int                 sglen;

ドライバは適切なサイズのscatterlist配列を確保し、割当されたバッファのピースへのポインタを埋め込む必要があります。sglenには配列の長さを設定します。

scatter/gatherを使用するドライバは vmalloc() メソッドはバッファの割当を一切気にする必要（そして不可能）ありません。videobufがその詳細を処理します。通常、contiguous-DMAドライバにも同様のことが言えます。videobufは必要に応じてdma_alloc_coherent()を呼び出してバッファを割り当てます。つまり、これらのドライバはいつでも高オーダーの割当を試みる可能性があり、その操作は常に成功するとは限りません。一部のドライバはシステム起動時にDMA領域を割り当てることでトリックをかけますが、videobufは現在、そのようなドライバとよく相性が悪いです。

2.6.31以降、contiguous-DMAドライバはユーザーが提供したバッファと動作できます。ただし、そのバッファが物理的に連続している必要があります。通常のユーザー空間の割り当てはこの条件を満たしませんが、他のカーネルドライバから取得したバッファや、ヒューゲンページ内に含まれるバッファはこれらのドライバと動作します。

1.14.7. バッファの埋め込み¶

videobufの実装の最終部分には直接のコールバックはありません。これは実際にフレームデータをバッファに書き込むコードの部分で、通常はデバイスからの割込みに応じて実行されます。すべてのドライバタイプにおいて、このプロセスは以下のようになります：

  • 次の利用可能なバッファを取得し、誰かが実際に待っていることを確認します。

  • メモリのポインタを取得し、その場所に動画データを書き込みます。

  • バッファを完了状態にマークし、待っているプロセスを起こします。

上記のステップ（1）はドライバが管理するlist_head構造体を確認することで実行されます。これはbuf_queue()コールバックで埋められる構造体です。エンジンの起動とバッファのキューイングは別々のステップで行われるため、エンジンが動作しているにもかかわらずバッファが利用できない状態になることがあります。特にそのケースでは、ドライバはリストが空であることを準備しておく必要があります。 vmalloc() 誰もまだバッファに興味を持っていない可能性もあります。ドライバはプロセスが待っているまでバッファをリストから削除したり、埋めたりすべきではありません。このテストは、バッファのdoneフィールド（wait_queue_head_t構造体）を確認することで行えます。 waitqueue_active().

DMAでマッピングされる前に、バッファの状態をVIDEOBUF_ACTIVEに設定しておく必要があります。これにより、デバイスがデータを転送している間、videobufレイヤーがそのバッファに対して何らかの処理を試みることを防ぎます。

scatter/gatherドライバでは、上記で説明したscatterlist構造体に必要なメモリポインタが含まれています。videobufメソッドを使用するドライバは、 vmalloc() メモリポインタを取得するには以下のようになります：

void *videobuf_to_vmalloc(struct videobuf_buffer *buf);

contiguous DMAドライバでは、以下の関数を使用します：

dma_addr_t videobuf_to_dma_contig(struct videobuf_buffer *buf);

contiguous DMA APIは、ドライバにカーネル空間のDMAバッファのアドレスを隠すように特別な配慮をしています。

最後のステップは、関連するvideobuf_buffer構造体のsizeフィールドを実際にキャプチャされた画像のサイズに設定し、ステートをVIDEOBUF_DONEに設定した後、doneキューでwake_up()を呼び出すことです。この時点で、バッファはvideobufレイヤーの所有となり、ドライバはこれ以降は触らないでください。

より詳しい情報が必要な開発者は、関連するヘッダーファイルを参照してください。そこにはここでは説明されていないいくつかの低レベルの関数が宣言されています。また、すべてのこれらの呼び出しはGPLのみでエクスポートされるため、非GPLカーネルモジュールには利用できません。

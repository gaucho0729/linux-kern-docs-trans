5. CECカーネルサポート¶

CECフレームワークはHDMI CECハードウェアと使用するための統一されたカーネルインターフェースを提供します。これは複数のハードウェアタイプ（受信機、送信機、USBドングルなど）を処理するように設計されており、カーネルドライバで実行すべき処理とユーザー空間アプリケーションで処理すべき処理を決定するオプションも提供します。さらに、リモコンパストスルー機能をカーネルのリモコンフレームワークに統合しています。

5.1. CECプロトコル¶

CECプロトコルは、HDMI接続を介して消費者電子機器同士が通信できるようにします。このプロトコルは論理アドレスを使用して通信を行います。論理アドレスはデバイスが提供する機能と厳密に関連しています。通信ハブとして機能するテレビは常にアドレス0が割り当てられます。物理アドレスはデバイス間の物理的な接続によって決定されます。

ここに説明するCECフレームワークはCEC 2.0仕様と最新です。これはHDMI 1.4仕様に記載されており、新しい2.0ビットはHDMI 2.0仕様に記載されています。ただし、ほとんどの機能には無料で利用可能なHDMI 1.3a仕様が十分です:

http://www.microprocessor.org/HDMISpecification13a.pdf

5.2. CECアダプタインターフェース¶

struct cec_adapterはCECアダプタハードウェアを表します。これは以下の関数を呼び出すことで作成されます cec_allocate_adapter() および以下の関数を呼び出すことで削除されます cec_delete_adapter():

struct cec_adapter *cec_allocate_adapter(const struct cec_adap_ops *ops, void *priv, const char *名前, u32 caps, u8 available_las);¶
void cec_delete_adapter(struct cec_adapter *adap);¶

アダプタを作成するには以下の情報を渡す必要があります:

ops:

CECフレームワークが呼び出すアダプタ操作で、実装しなければならないものです。

priv:

adap->privに保存され、アダプタ操作で使用できます。privポインタを取得するにはcec_get_drvdata(adap)を使用してください。

name:

CECアダプタの名前。注意: この名前はコピーされます。

caps:

CECアダプタの機能。これらの機能はハードウェアの機能を決定し、ユーザー空間とカーネル空間で処理すべき部分を指定します。機能はCEC_ADAP_G_CAPSで返されます。

available_las:

このアダプタが同時に処理できる論理アドレスの数。1 <= available_las <= CEC_MAX_LOG_ADDRSでなければなりません。

privポインタを取得するには次のヘルパー関数を使用してください:

void *cec_get_drvdata(const struct cec_adapter *adap);¶

/dev/cecXデバイスノードとリモコンデバイス（CEC_CAP_RCが設定されている場合）を登録するには以下の関数を呼び出してください:

int cec_register_adapter(struct cec_adapter *adap, struct デバイス *親);¶

parentは親デバイスです。

デバイスをアンレジストするには以下の関数を呼び出してください:

void cec_unregister_adapter(struct cec_adapter *adap);¶

注意: 以下の関数が失敗した場合、以下の関数を呼び出してクリーンアップしてください。しかし、以下の関数が成功した場合、以下の関数を呼び出してのみクリーンアップしてください、決して cec_register_adapter() が失敗した場合 cec_delete_adapter() を呼び出してクリーンアップしてください cec_register_adapter() が成功した場合 cec_unregister_adapter() を呼び出してクリーンアップしてください、決して cec_delete_adapter()unregister関数は、/dev/cecXデバイスの最後のユーザーがそのファイルハンドルを閉じた後、アダプタを自動的に削除します。

5.3. 低レベルCECアダプタの実装¶

以下の低レベルのアダプタ操作は、ドライバーで実装する必要があります：

struct cec_adap_ops¶
struct cec_adap_ops
{
        /* Low-level callbacks */
        int (*adap_enable)(struct cec_adapter *adap, bool enable);
        int (*adap_monitor_all_enable)(struct cec_adapter *adap, bool enable);
        int (*adap_monitor_pin_enable)(struct cec_adapter *adap, bool enable);
        int (*adap_log_addr)(struct cec_adapter *adap, u8 logical_addr);
        int (*adap_transmit)(struct cec_adapter *adap, u8 attempts,
                              u32 signal_free_time, struct cec_msg *msg);
        void (*adap_status)(struct cec_adapter *adap, struct seq_file *file);
        void (*adap_free)(struct cec_adapter *adap);

        /* Error injection callbacks */
        ...

        /* High-level callbacks */
        ...
};

7つの低レベルの操作は、CECアダプタハードウェアの制御に関するさまざまな側面を扱います：

ハードウェアを有効/無効にするには：

int (*adap_enable)(struct cec_adapter *adap, bool enable);

このコールバックはCECハードウェアを有効または無効にします。CECハードウェアを有効にするとは、論理アドレスが割り当てられていない状態で電源をオンにするということです。この操作は、enableがtrueの場合に物理アドレス(adap->phys_addr)が有効であると想定し、CECアダプタが有効な間は変更されません。呼び出し後のCECアダプタの初期状態は、 cec_allocate_adapter() 無効

enableがfalseの場合、adap_enableは0を返さなければなりません。

「モニタリングすべて」モードを有効/無効にするには：

int (*adap_monitor_all_enable)(struct cec_adapter *adap, bool enable);

有効にすると、アダプタは自分宛ではないメッセージもモニタリングするモードになります。すべてのハードウェアがこの機能をサポートするわけではなく、この関数はCEC_CAP_MONITOR_ALLの能力が設定されている場合にのみ呼び出されます。このコールバックはオプションです（一部のハードウェアは常に「モニタリングすべて」モードになっている場合があります）。

enableがfalseの場合、adap_monitor_all_enableは0を返さなければなりません。

「ピンモニタリング」モードを有効/無効にするには：

int (*adap_monitor_pin_enable)(struct cec_adapter *adap, bool enable);

有効にすると、アダプタはCECピンの変化をモニタリングするモードになります。すべてのハードウェアがこの機能をサポートするわけではなく、この関数はCEC_CAP_MONITOR_PINの能力が設定されている場合にのみ呼び出されます。このコールバックはオプションです（一部のハードウェアは常に「ピンモニタリング」モードになっている場合があります）。

enableがfalseの場合、adap_monitor_pin_enableは0を返さなければなりません。

新しい論理アドレスをプログラミングするには：

int (*adap_log_addr)(struct cec_adapter *adap, u8 logical_addr);

logical_addr == CEC_LOG_ADDR_INVALIDの場合、すべてのプログラミングされた論理アドレスを削除する必要があります。それ以外の場合、指定された論理アドレスをプログラミングする必要があります。利用可能な論理アドレスの最大数を超えた場合は、-ENXIOを返す必要があります。論理アドレスがプログラミングされると、CECハードウェアはそのアドレス宛のディレクトリメッセージを受信できるようになります。

logical_addrがCEC_LOG_ADDR_INVALIDの場合、adap_log_addrは0を返さなければなりません。

新しいメッセージを送信するには：

int (*adap_transmit)(struct cec_adapter *adap, u8 attempts,
                     u32 signal_free_time, struct cec_msg *msg);

この関数は新しいメッセージを送信します。attempts引数は送信の推奨される回数を示します。

signal_free_timeは、ラインが空いているときにアダプターがメッセージを送信する前に待機すべきデータビット周期の数を示します。この値は、送信が再試行、新しい初期化子からのメッセージ、もしくは同じ初期化子からの新しいメッセージであるかによって異なります。ほとんどのハードウェアでは自動的に処理されるため、一部のケースではこの情報が必要になります。

signal_free_timeをマイクロ秒に変換するには、CEC_FREE_TIME_TO_USECマクロを使用できます（1データビット周期は2.4msです）。

現在のCECハードウェアの状態をログに記録するには:

void (*adap_status)(struct cec_adapter *adap, struct seq_file *file);

オプションのコールバックを使用してCECハードウェアの状態を表示できます。状態はdebugfs経由で確認可能です: cat /sys/kernel/debug/cec/cecX/status

アダプターが削除されるときにリソースを解放するには:

void (*adap_free)(struct cec_adapter *adap);

オプションのコールバックを使用して、ドライバによって割り当てられたリソースを解放できます。cec_delete_adapterから呼び出されます。

アダプタードライバは、以下の状況でフレームワークに呼び出すことでイベント（通常は割り込み駆動型）に反応しなければなりません:

送信が完了した場合（成功してもしくはそうでない場合）:

void cec_transmit_done(struct cec_adapter *adap, u8 status,
                       u8 arb_lost_cnt,  u8 nack_cnt, u8 low_drive_cnt,
                       u8 error_cnt);

または:

void cec_transmit_attempt_done(struct cec_adapter *adap, u8 status);

ステータスは次のいずれかです:

CEC_TX_STATUS_OK:

送信が成功しました。

CEC_TX_STATUS_ARB_LOST:

仲裁が失われました: 他のCEC初期化子がCECラインを制御し、仲裁を失いました。

CEC_TX_STATUS_NACK:

メッセージがnacked（ダイレクトメッセージの場合）またはacked（ブロードキャストメッセージの場合）されました。再送が必要です。

CEC_TX_STATUS_LOW_DRIVE:

CECバスでロー駆動が検出されました。これはフォロワーがバスでエラーを検出し再送を要求したことを示します。

CEC_TX_STATUS_ERROR:

特定のエラーが発生しました: これはARB_LOSTまたはLOW_DRIVEのいずれかである可能性があります（ハードウェアが区別できない場合）。一部のハードウェアでは送信結果としてOKとFAILのみをサポートしており、異なるエラーを区別できません。その場合、FAILはCEC_TX_STATUS_NACKにマッピングし、CEC_TX_STATUS_ERRORにはマッピングしないでください。

CEC_TX_STATUS_MAX_RETRIES:

複数回試行してもメッセージを送信できませんでした。この値はドライバがハードウェアによる再送をサポートしている場合にのみ設定します。設定された場合、フレームワークはハードウェアが既に再送を実施したため、もう一度送信を試みる必要がないとみなします。

ハードウェアはOK、NACK、および「何か他のもの」を区別できる必要があります。

*_cnt引数は、観測されたエラー状態の数を表します。情報が利用できない場合は0になることがあります。ハードウェアのリトライをサポートしないドライバは、ハードウェアがリトライをサポートする場合に限り、送信エラーに対応するカウンターを1に設定します。ハードウェアがリトライをサポートしない場合は、エラーが発生した種類や回数をフィードバックしない場合はこれらのカウンターを0に設定し、ハードウェアが報告する正しい値を記録してください。

これらの関数を呼び出すと、キューに待機中の送信が存在する場合、すぐに新しい送信を開始する可能性があるため、ハードウェアが新しい送信を開始できる状態にあることを確認してください。 before これらの関数を呼び出す。

cec_transmit_attempt_done()関数は、ハードウェアがリトライをサポートしない場合に使用する補助関数であり、送信は常に単一の試行のみです。この関数はcec_transmit_done()を呼び出し、ステータスに応じてcount引数に対応する値を1に設定します。ステータスがOKだった場合はすべて0になります。

CECメッセージが受信された場合:

void cec_received_msg(struct cec_adapter *adap, struct cec_msg *msg);¶

説明不要。

5.4. 割込みハンドラの実装¶

通常、CECハードウェアは送信が完了したときに割込みを発生させ、送信が成功したかどうかを通知します。また、CECメッセージが受信されたときに割込みを発生させます。

CECドライバでは、送信割込みを処理した後で受信割込みを処理する必要があります。フレームワークはcec_transmit_doneの呼び出しがcec_received_msgの呼び出しより先に発生することを期待しており、受信メッセージが送信メッセージへの応答だった場合に混乱を防ぐためです。

5.5. オプション: エラー注入サポートの実装¶

CECアダプターがエラー注入機能をサポートする場合、その機能はエラー注入コールバックを通じて公開されます:

struct cec_adap_ops {
        /* Low-level callbacks */
        ...

        /* Error injection callbacks */
        int (*error_inj_show)(struct cec_adapter *adap, struct seq_file *sf);
        bool (*error_inj_parse_line)(struct cec_adapter *adap, char *line);

        /* High-level CEC message callback */
        ...
};

両方のコールバックが設定されている場合、 error-inj debugfsにファイルが表示されます。基本的な構文は以下の通りです:

先頭のスペース/タブは無視されます。次の文字が # であるか、行末に達した場合、その行は無視されます。それ以外の場合はコマンドが期待されます。

この基本的なパース処理はCECフレームワークで行われます。ドライバは実装するコマンドを決定する責任があります。唯一の要件は、引数を指定せずに実装されるコマンド clear が存在することです。このコマンドは現在のすべてのエラー注入コマンドを削除します。

これにより、ドライバ固有のコマンドの詳細を知る必要なく、いつでも echo clear >error-inj を実行してエラー注入をクリアできます。

注意: error-inj の出力は、 error-injの入力として有効です。したがって、この処理が正しく動作することを確認してください。

$ cat error-inj >einj.txt
$ cat einj.txt >error-inj

このファイルが読み込まれたときに呼ばれる最初のコールバックは、現在のエラー注入状態を表示する必要があります:

int (*error_inj_show)(struct cec_adapter *adap, struct seq_file *sf);

コメントブロックで基本的な使用法の情報から始めることが推奨されます。成功時は0を返し、エラー時はエラーを返します。

2番目のコールバックは、 error-inj ファイル：

bool (*error_inj_parse_line)(struct cec_adapter *adap, char *line);

以下の line 引数がコマンドの開始位置を指しており、先頭のスペースまたはタブはすでにスキップされています。これは単一行のみ（埋め込まれた改行はありません）で、0終端です。コールバックはバッファの内容を自由に変更できます。このコールバックはコマンドを含む行のみ呼び出されるため、空行やコメント行には呼ばされません。

コマンドが有効な場合はtrueを返し、構文エラーがある場合はfalseを返します。

5.6. ハイレベルCECアダプタの実装¶

ローコード操作がハードウェアを制御し、ハイレベル操作はCECプロトコルによって制御されます。以下のハイレベルコールバックが利用可能です:

struct cec_adap_ops {
        /* Low-level callbacks */
        ...

        /* Error injection callbacks */
        ...

        /* High-level CEC message callback */
        int (*received)(struct cec_adapter *adap, struct cec_msg *msg);
};

received()コールバックは、ドライバが新たに受信したCECメッセージをオプションで処理できるようにします:

int (*received)(struct cec_adapter *adap, struct cec_msg *msg);

ドライバがCECメッセージを処理したい場合は、このコールバックを実装できます。処理しない場合は-ENOMSGを返す必要があります。それ以外の場合、CECフレームワークはこのメッセージを処理したと想定し、何も処理しません。

5.7. CECフレームワーク関数¶

CECアダプタドライバは、以下のCECフレームワーク関数を呼び出すことができます:

int cec_transmit_msg(struct cec_adapter *adap, struct cec_msg *msg, bool block);¶

CECメッセージを送信します。blockがtrueの場合、メッセージの送信を待機します。それ以外の場合は、キューに追加して即座に返します。

void cec_s_phys_addr(struct cec_adapter *adap, u16 phys_addr, bool block);¶

物理アドレスを変更します。この関数はadap->phys_addrを設定し、変更された場合にイベントを送信します。もし cec_s_log_addrs() 呼び出されており、物理アドレスが有効になった場合、CECフレームワークは論理アドレスの取得を開始します。blockがtrueの場合、この処理が完了するまで関数は戻りません。

物理アドレスが有効な値に設定されると、CECアダプタは有効化されます（adap_enable opを参照）。物理アドレスがCEC_PHYS_ADDR_INVALIDに設定されると、CECアダプタは無効化されます。有効な物理アドレスを別の有効な物理アドレスに変更する場合、この関数はまずアドレスをCEC_PHYS_ADDR_INVALIDに設定し、その後新しい物理アドレスを有効化します。

void cec_s_phys_addr_from_edid(struct cec_adapter *adap, const struct edid *edid);¶

edid構造体から物理アドレスを抽出し、 cec_s_phys_addr() そのアドレスで呼び出します。EDIDに物理アドレスが含まれていなかった場合やedidがNULLポインタだった場合はCEC_PHYS_ADDR_INVALIDを返します。

int cec_s_log_addrs(struct cec_adapter *adap, struct cec_log_addrs *log_addrs, bool block);¶

CEC論理アドレスを取得します。CEC_CAP_LOG_ADDRSが設定されている場合は決して呼び出されません。ブロックがtrueの場合、論理アドレスが取得されるまで待機します。それ以外の場合は、キューイングして即座に返します。すべての論理アドレスをアンコンフィギアするには、log_addrsをNULLに設定するか、log_addrs->num_log_addrsを0に設定してこの関数を呼び出します。アンコンフィギアする際にはblock引数は無視されます。物理アドレスが無効な場合、この関数は即座に返します。物理アドレスが有効になった後、フレームワークがこれらの論理アドレスを取得しようとします。

5.8. CECピンフレームワーク¶

ほとんどのCECハードウェアは、ソフトウェアがメッセージを提供し、ハードウェアが低レベルのCECプロトコルを処理するフルなCECメッセージを処理します。しかし一部のハードウェアはCECピンを駆動するだけで、ソフトウェアが低レベルのCECプロトコルを処理する必要があります。CECピンフレームワークはこのようなデバイスを処理するために作成されました。

リアルタイムに近い要件のため、100%の動作を保証することはできません。このフレームワークは内部でハイレゾタイマを使用しますが、タイマが300マイクロ秒以上遅れた場合、誤った結果が発生する可能性があります。実際にはかなり信頼性が高いようです。

この低レベル実装の利点の一つは、割込みを用いてCECピンの電圧が低から高または逆に変化するのを検出できるため、安価なCECアナライザーとして利用できる点です。

オプション、ステータス情報をログ出力します。

5.9. CEC通知フレームワーク¶

ほとんどのDRM HDMI実装では統合されたCEC実装が含まれており、通知サポートは必要ありません。ただし一部の実装では独立したCEC実装が使用され、独自のドライバーを持つ場合があります。これはSoCのIPブロックや、CECピンを処理する完全に分離されたチップである可能性があります。そのような場合、DRMドライバーは通知を登録し、物理アドレスの変化をCECドライバーに通知するために通知を使用します。

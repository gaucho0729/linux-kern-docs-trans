struct dev_pm_ops¶

デバイスPMコールバック。

メンバ

prepare

このコールバックの主な役割は、このコールバックが返した後、デバイスの新しい子デバイスが登録されないようにすることです（ドライバのサブシステムおよび一般的にカーネルの他の部分は、プローブメソッドへの新しい呼び出しを防ぐことが予期されます）。もし prepare() が成功した場合、 prepare() が処理できない状況（例：すでに登録が進行中の子デバイス）を検出すると、-EAGAINを返してPMコアが再度実行されるようにします（例：新しい子デバイスが登録された後）。このメソッドはすべてのスリープ遷移に対して実行され、その後、次のスリープコールバックのいずれかが実行されます： suspend(), freeze()（sleepable RCU）が導入されました。 poweroff()。もし遷移がメモリへのスリープまたはスタンバイ（ヒーブリッドに関係しない）の場合、 prepare() の戻り値は、PMコアにデバイスをランタイムスリープ状態に残すことを示すために使用できます。つまり、 prepare() が正の数を返す場合、PMコアはそのデバイスがランタイムスリープ状態にあると理解し、その状態を遷移中およびその後の再起動中に維持する可能性があります（すべての子孫もランタイムスリープ状態に残る場合）。その場合、 complete() は prepare() の直後に実行され、システム再起動後にデバイスの適切な動作を保証する必要があります。PMコアは、すべてのデバイスに対してサブシステムレベルの prepare() を実行した後、それらのデバイスのスリープコールバックを呼び出します。そのため、通常、 prepare() が実行されている間、デバイスは機能しているか、ランタイム再起動リクエストに応答しているとみなされます。ただし、デバイスドライバはその時点でユーザー空間の利用可能性について何らかの仮定をすることはできませんし、 prepare() 内でファームウェアを要求することはできません（その時点ですでに遅すぎます）。また、 prepare() 内でGFP_KERNELモードで大量のメモリを割り当てるのも有効ではありません。[これらの制限を回避するため、ドライバはタスクの凍結前のスリープおよびヒーブリッド通知を登録して実行することが可能です。]

complete

によって行われた変更を元に戻す。 prepare()。このメソッドはすべてのリザーブ遷移に対して実行され、次のリザーブコールバックのいずれかの後に実行されます： resume(), thaw(), restore()。また、ドライバのスリープコールバックよりも前に状態遷移が失敗した場合にも呼び出されます： suspend(), freeze() または poweroff()、が実行される可能性があります（例：PMコアが以前にスリープを試みた他のデバイスのスリープコールバックが失敗した場合）。PMコアはサブシステムレベルの complete() すべてのデバイスに対して適切なresumeコールバックが実行された後。対応する prepare() スリープ遷移の開始時に正の数を返した場合、デバイスはランタイムスリープ状態に残され（スリープおよびリザーブコールバックが実行されないまま）、 complete() デバイスに対して実行される唯一のコールバックになります。その場合、 complete() システムの再起動後にデバイスが正しく動作するよう、必要なすべての準備を整える必要があります。このため、 complete() デバイスのpower.direct_completeフラグを確認し、以前のスリープおよびリザーブコールバックが実行済み（フラグが未設定）か否か（フラグが設定済み）を把握する必要があります。

suspend

メインメモリの内容が保持されたスリープ状態にシステムを移行する前に実行されます。具体的な動作はデバイスのサブシステム（PMドメイン、デバイスタイプ、クラスまたはバスタイプ）に依存しますが、一般的にはサブシステムレベルで suspend() 実行後、デバイスがI/OやDMAを行わないようにする必要があります。サブシステムレベルで suspend() すべてのデバイスに対して実行されます。すべてのデバイスに対して prepare() が実行されます。

resume

メインメモリの内容が保持されたスリープ状態からシステムを再起動した後に実行されます。具体的な動作はデバイスのサブシステムに依存しますが、一般的にはドライバーが再び動作を開始し、ハードウェアイベントやソフトウェアリクエストに応じる必要があります（デバイス自体は低電力状態に残され、ランタイムリザーブが発生するのを待つ場合があります）。デバイスのドライバーの resume() コールバックが実行される時点でのデバイスの状態は、デバイスが所属するプラットフォームおよびサブシステムに依存します。ほとんどのプラットフォームでは、 resume()の際、クロックなどのリソースの利用制限はありません。 resume() すべてのデバイスに対して実行されます。すべてのデバイスに対して サブシステムレベル が実行されます。

freeze

hibernation専用、hibernation画像の作成前に実行されます。 suspend()に類似していますが、デバイスがウェイクアップイベントをシグナルとして出力するのを有効にしたり、電源状態を変更するのを避ける必要があります。ほとんどのサブシステム（PCIバスタイプを除く）は、ドライバレベルの freeze() でデバイスの設定をメモリに保存し、 restore() がhibernationからの再起動時に使用します。サブシステムレベルの freeze() すべてのデバイスに対して実行されます。すべてのデバイスに対して prepare() が実行されます。

thaw

hibernation専用、hibernation画像の作成後または作成失敗後に実行されます。また、メインメモリの内容をその画像から復元する試みが失敗した場合にも実行されます。前の freeze()で行われた変更を元に戻すため、デバイスは freeze()の際、クロックなどのリソースの利用制限はありません。 thaw() すべてのデバイスに対して実行されます。すべてのデバイスに対して コールバック呼び出し前の状態と同じように操作可能になります。 すべてのデバイスに対して実行されます。また、遷移エラーの際にも、 freeze() 直後に直接実行されることがあります。

poweroff

ヒbernation固有の処理で、ヒbernationイメージを保存した後に実行されます。これは suspend()に類似していますが、デバイスの設定をメモリに保存する必要はありません。サブシステムレベルの poweroff() すべてのデバイスに対して実行されます。すべてのデバイスに対して prepare() が実行されます。

restore

ヒbernation固有の処理で、ヒbernationイメージからメインメモリの内容を復元した後に実行されます。これは resume().

runtime_suspend

電源管理により、CPU(s)およびRAMと通信できなくなる状態にデバイスを準備する必要があります。これはデバイスを低電力状態にすることを意味する必要はありません。たとえば、デバイスが直前に切断されるリンクの後にある場合、デバイスはフル電力状態のまま残ることができます。デバイスが低電力状態に移行し、ランタイムウェイクアップイベントを生成できる場合、リモートウェイクアップ（つまり、デバイスが割込みを通じて自身の電源状態を変更するよう要求するハードウェアメカニズム）を有効にする必要があります。

runtime_resume

ハードウェアによって生成されたウェイクアップイベントまたはソフトウェアのリクエストに応じて、デバイスを完全にアクティブな状態にします。必要に応じて、デバイスをフル電力状態にし、レジスタを復元して、デバイスが完全に動作可能になるようにします。

runtime_idle

デバイスが非アクティブに見える場合、すべての必要条件が満たされた場合、低電力状態に移行する可能性があります。これらの条件を確認し、PMコアがデバイスのスリープリクエストをキューイングするのに適切である場合、0を返します。

説明

いくつかのデバイス電源状態の遷移は外部から見えるため、保留中のI/Oキューの状態や（ハードウェアにアクセスするドライバの場合）割込み、ウェイクアップ、DMA、その他のハードウェア状態に影響を与えます。また、ドライバスタックの残りの部分には透明なさまざまな低電力モードへの内部遷移も発生する可能性があります（たとえば、ONゲートで使用されていないクロックをオフにしているドライバなど）。

外部から見える遷移は、この構造に含まれるコールバックを活用して処理され、通常、2段階のコールバックが関与します。まず、PMコアはPMドメイン、デバイスタイプ、クラス、バスタイプから提供されるコールバックを実行します。これらはサブシステムレベルのコールバックであり、デバイスドライバから提供されるコールバックを実行することが期待されていますが、ドライバがそれを選択的に実行しない場合もあります。ドライバコールバックが実行される場合、それらはサブシステムレベルのコールバックと協力して、与えられたシステム遷移、遷移フェーズ、およびデバイスが属するサブシステムに適した目標を達成する必要があります。

上記のすべてのコールバックは、 complete()を除き、エラーコードを返します。ただし、 resume(), thaw(), restore(), サブシステムレベル, コールバック呼び出し前の状態と同じように操作可能になります。, and が実行されている間、割込みハンドラが実行されないことが保証されています。これはPMコアがデバイスが復帰される過程で中止を引き起こさないようにする必要があります。そのような場合に返されるエラーコードは、デバッグ目的でシステムログにのみ出力されます。それでも、ドライバーはデバイスが復帰できず使用不能になった場合（つまり、処理対象のデバイスが復帰を拒否した場合）にのみ、resumeメソッドからエラーコードを返すことが推奨されます。これにより、今後PMコアを変更する際に、復帰に失敗したデバイスやその子デバイスを処理しようとするのを回避できるようになります。

上記のコールバックが実行されている間でもデバイスの登録解除は許可されています。ただし、コールバックルーチンは呼び出されたデバイスの登録解除を試もうとしてはいけません。ただし、そのデバイスの子デバイス（システムがスリープしている間、子デバイスが抜き取られたことを検出するなど）の登録解除は行うことができます。

デバイスのランタイム電源管理にも関連するコールバックがあります。同様に、これらのコールバックは通常、PMコアがサブシステム（PMドメイン、デバイスタイプ、クラス、バスタイプ）に対して実行し、サブシステムレベルのコールバックがドライバーコールバックを呼び出すことが期待されます。また、デバイスドライバーのコールバックが実行すべき具体的な動作は、デバイスが所属するプラットフォームやサブシステムによって異なります。

struct dev_pm_domain¶

電源管理ドメインの表現。

定義

struct dev_pm_domain {
  struct dev_pm_ops       ops;
  int (*start)(struct device *dev);
  void (*detach)(struct device *dev, bool power_off);
  int (*activate)(struct device *dev);
  void (*sync)(struct device *dev);
  void (*dismiss)(struct device *dev);
  ANDROID_KABI_RESERVE(1);
};

メンバ

ops

このドメインに関連する電源管理操作。

start

ユーザーがドメインを通じてデバイスを起動する必要があるときに呼び出されます。

detach

デバイスがドメインから削除されるときに呼び出されます。

activate

バスタイプやドライバーのプローブルーチンを実行する前に呼び出されます。

sync

ドライバーのプローブが成功した後に呼び出されます。

dismiss

ドライバーのプローブが失敗した後およびドライバーの削除後に呼び出されます。

説明

電源管理ドメインは、システムスリープ、ハイبرネーション、システム復帰、およびランタイムPM遷移中に実行されるコールバックを提供し、サブシステムレベルおよびドライバーレベルのコールバックの代わりに使用されます。

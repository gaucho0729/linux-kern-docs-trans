Legacy GPIOインターフェース¶

LinuxにおけるGPIOアクセスの慣例についての概要を提供します。

これらの関数はgpio_*という名前付けのプレフィックスを使用します。他の関数はこのプレフィックスや関連する__gpio_*プレフィックスを使用してはいけません。

GPIOとは何ですか？¶

「汎用入出力」（GPIO）は、柔軟にソフトウェア制御可能なデジタル信号であり、多くのチップから提供され、Linux開発者にとってエムベデッドやカスタムハードウェアの開発において親しみやすい要素です。各GPIOは特定のピン、またはボールグリッドアレイ（BGA）パッケージの「ボール」に接続されたビットを表します。基板回路図では、どの外部ハードウェアがどのGPIOに接続されているかを示します。ドライバーは汎用的に書くことができ、そのため基板設定コードがこのようなピン設定データをドライバーに渡します。

System-on-Chip (SOC)プロセッサはGPIOに大きく依存しています。一部のケースでは、すべての非専用ピンがGPIOとして設定可能であり、ほとんどのチップには少なくとも数十のGPIOが搭載されています。プログラマブル論理デバイス（例：FPGA）はGPIOを簡単に提供でき、電源管理チップやオーディオコーデックなどのマルチファンクションチップはSOCでのピン不足を補うため、いくつかのGPIOピンを備えています。また、「GPIO拡張チップ」もI2CやSPIなどのシリアルバスを介して接続されることがあります。ほとんどのPC southbridgeチップには数十のGPIO機能を持つピンが搭載されており（BIOSファームウェアのみがその用途を知っています）。

GPIOの正確な機能はシステムによって異なります。一般的なオプション:

  • 出力値は書き換え可能（高電圧=1、低電圧=0）です。一部のチップでは、この値の駆動方法についてのオプションが存在し、たとえば一方の値のみを駆動して「ワイヤーOR」や類似のスキームをサポートするなど、他方の値には「オープンドレイン」信号などの機能を提供します。

  • 入力値も同様に読み取れます（1、0）。一部のチップでは、出力として設定されたピンの読み戻しがサポートされており、このような「ワイヤーオア」ケースで双方向信号をサポートするために非常に役立ちます。GPIOコントローラーには入力デグリッチング/デブウンスロジックが含まれることがあり、場合によってはソフトウェア制御も可能です。

  • 入力はしばしばIRQ信号として使用でき、通常はエッジトリガーですが、場合によってはレベルトリガーもあります。このようなIRQは、システムの低電力状態からシステムを起動させるために設定可能であり、ウェイクアップイベントとして機能できます。

  • 一般的にGPIOは、製品ボードの必要に応じて入力または出力として設定可能ですが、単方向のものも存在します。

  • ほとんどのGPIOはスピンロックを保持しながらアクセス可能ですが、シリアルバスを通じてアクセスされるGPIOは通常アクセスできません。一部のシステムでは両方のタイプをサポートしています。

特定のボードでは、各GPIOはMMC/SDカードの挿抜検出、カードのライトプロテクト状態の検出、LEDの駆動、トランシーバーの設定、シリアルバスのビットバッキング、ハードウェアウォッチドッグの操作、スイッチの検出など、特定の用途にのみ使用されます。

GPIOの規約¶

このことが「慣例」と呼ばれるのは、この方法を採用する必要はなく、採用しなくても問題ないからです。 あります ポートabilityが主な問題ではないケースもあります。GPIOはしばしばボード固有のグルーブロジックとして使用され、ボードのリビジョンごとに変化する可能性があり、異なる配線で構成されたボードでは使用できません。最も汎用的な機能のみが非常に移植性が高いですが、他の機能はプラットフォーム固有であり、グルーブロジックにとっては重要な要素です。

さらに、この実装にはフレームワークを必要とせず、単なるインターフェースのみで十分です。あるプラットフォームではチップレジスタに直接アクセスするシンプルなインライン関数で実装され、別のプラットフォームでは複数の非常に異なるGPIOコントローラー用の抽象化を介して実装されることがあります。（この実装戦略をサポートするオプションのコードについてはこのドキュメントの後述部分に記載されていますが、GPIOインターフェースをクライアントとして動作するドライバーはその実装方法に依存してはいけません。）

ただし、プラットフォームでコンベンションがサポートされている場合、ドライバは可能な限りそれを使用すべきです。プラットフォームはGPIO機能が厳密に必要である場合にGPIOLIBを選択する必要があります。標準のGPIO呼び出しを必要とできないドライバは、KconfigエントリでGPIOLIBに依存する必要があります。ドライバがincludeファイルを使用する場合、GPIO呼び出しは「実際のコード」または最適化されたスタブとして利用可能です：

#include <linux/gpio.h>

このコンベンションに従うことで、他の開発者もあなたのコードの動作を理解し、メンテナンスを容易にすることができます。

これらの操作は、プラットフォームがそれらを使用する必要がある場合にI/Oバリアーを含みます。ドライバは明示的にそれらを追加する必要はありません。

GPIOの識別¶

GPIOは符号なし整数0..MAX_INTで識別されます。これは「負の」数を他の用途（例：信号が「このボードでは利用不可」であることを示す、またはエラーを示す）に予約しています。ハードウェアに直接アクセスしないコードでは、これらの整数をオパケなクッキーとして扱います。

プラットフォームはこれらの整数をどのように使用するかを定義し、通常はGPIOラインに# defineシンボルを定義して、ボード固有の設定コードが関連する回路図と直接対応するようにします。一方、ドライバは、その設定コードから渡されたGPIO番号のみを使用すべきで、プラットフォームデータを用いてボード固有のピン設定データ（およびその他の必要なボード固有データ）を保持します。これにより、移植性の問題を回避できます。

たとえば、あるプラットフォームはGPIOを32-159番を使用し、他のプラットフォームは0..63番のGPIOコントローラー、64-79番の別のタイプのGPIOコントローラー、そして特定のボードでは80-95番のFPGAを使用します。番号は連続する必要はありません。これらのプラットフォームのどちらも、I2C GPIO拡張デバイスのバンクを識別するために2000-2063番を使用する可能性があります。

無効なGPIO番号で構造体を初期化する場合は、負の数（例：「-EINVAL」）を使用してください。これは常に有効ではありません。このような構造体から得た番号がGPIOを参照する可能性があるかをテストするには、次の述語を使用できます：

int gpio_is_valid(int number);

有効でない番号は、GPIOを要求または解放する呼び出し（以下参照）で拒否されます。他の番号も拒否される場合があります。たとえば、あるボードでは特定の番号が有効ですが一時的に使用されていない可能性があります。

GPIOコントローラーが複数サポートされるかどうかは、プラットフォーム固有の実装問題であり、そのサポートがGPIO番号空間に「穴」を残す可能性があるかどうかも、ランタイムに新しいコントローラーを追加できるかどうかも、プラットフォーム固有の実装問題です。このような問題は、隣接するGPIO番号が有効であるかどうかに影響を与えることがあります。

GPIO の使用¶

システムがGPIOを処理する最初のステップは、gpio_request()関数を使用してGPIOを割り当てることです；後述します。

GPIOを処理する次のステップの一つで、ボード設定コードでプラットフォームデバイスを設定する際によく行われるのが、GPIOの方向を設定することです：

/* set as input or output, returning 0 or negative errno */
int gpio_direction_input(unsigned gpio);
int gpio_direction_output(unsigned gpio, int value);

返却値は成功時はゼロ、エラー時は負のerrnoです。これはget/set呼び出しにエラー戻りがなく、誤設定の可能性があるため、必ず確認する必要があります。通常はタスクコンテキストからこれらの呼び出しを実行すべきです。ただし、スピンロック安全なGPIOについては、タスクが有効化される前でも使用可能です（早期ボード設定の一部として）。

出力GPIOの場合、提供された値が初期出力値になります。これにより、システム起動時の信号のグルチングを回避できます。

GPIOの方向設定は、既にリクエストされていないGPIOに対しては、legacyインターフェースとの互換性のために暗黙にリクエストします（後述参照）。この互換性はオプションのgpiolibフレームワークから削除されています。

GPIO番号が無効な場合、またはその特定のGPIOがそのモードで使用できない場合、方向設定が失敗する可能性があります。ブートファームウェアが方向を正しく設定していると信頼するのは一般的には悪い考えです。なぜなら、ブートファームウェアはLinuxの起動を目的としており、それ以上の検証は行われていないからです。（同様に、そのボード設定コードはそのピンをGPIOとしてマルチプレックスし、プルアップ/プルダウンを適切に設定する必要があります。）

スピンロック安全なGPIOアクセス¶

ほとんどのGPIOコントローラーはメモリ読み書き命令でアクセス可能です。これらはスリープを必要とせず、ハードウェア（非スレッド）IRQハンドラや同様なコンテキストから安全に実行可能です。

gpio_cansleep()が常にfalseを返すGPIOにアクセスするための次の呼び出しを使用してください（後述参照）：

/* GPIO INPUT:  return zero or nonzero */
int gpio_get_value(unsigned gpio);

/* GPIO OUTPUT */
void gpio_set_value(unsigned gpio, int value);

値は論理値であり、ゼロはロー、ゼロ以外はハイです。出力ピンの値を読み込む際、返却される値はピンに実際に現れる値です…ただし、オープンドレイン信号や出力遅延などの問題により、指定された出力値と一致しない場合があります。

get/set呼び出しは「無効なGPIO」が以前のgpio_direction_*()から報告されていたべきであるため、エラー戻りを持ちません。ただし、すべてのプラットフォームが出力ピンの値を読み込むことができるわけではありません。読み込めないプラットフォームでは常にゼロを返す必要があります。また、スリープなしに安全にアクセスできないGPIO（後述参照）に対してこれらの呼び出しを行うことはエラーです。

プラットフォーム固有の実装では、GPIO番号（出力の場合は値）が一定の場合にGPIO値へのアクセスを2回呼び出す処理を最適化することが推奨されます。このような場合、通常は少数の命令（ハードウェアレジスタの読み書きなど）で済み、スピンロックを必要としません。このような最適化された呼び出しは、サブルーチン呼び出しに数十命令を使うよりも、スペースと時間の効率が大幅に向上します。

スリープ可能なGPIOアクセス¶

一部のGPIOコントローラはI2CやSPIなどのメッセージベースのバスを介してアクセスする必要があります。GPIO値の読み書きコマンドは、コマンドを送信し応答を受けるためにキューの先頭に到達するまで待機する必要があります。これはIRQハンドラ内では行えないスリープを必要とします。

この種のGPIOをサポートするプラットフォームでは、他のGPIOと区別するためにこの呼び出しでゼロ以外を返します（有効なGPIO番号を指定する必要があります。これはgpio_requestで事前に割り当てたGPIO番号であるべきです）：

int gpio_cansleep(unsigned gpio);

このようなGPIOをアクセスするため、異なるアクセッサが定義されています:

/* GPIO INPUT:  return zero or nonzero, might sleep */
int gpio_get_value_cansleep(unsigned gpio);

/* GPIO OUTPUT, might sleep */
void gpio_set_value_cansleep(unsigned gpio, int value);

このようなGPIOにアクセスするには、スリープする可能性のあるコンテキストが必要です（例えばスレッド化されたIRQハンドラ）、そしてこれらのアクセッサは、cansleep()名前接尾辞を含まないスピンロック安全なアクセッサではなく、代わりに使用する必要があります。

これらのアクセッサがスリープする可能性があること、およびハードIRQハンドラからアクセスできないGPIOにも動作することを除けば、これらの呼び出しはスピンロック安全な呼び出しと同様の動作を行います。

追加で このようなGPIOの設定と構成の呼び出しは、GPIOコントローラチップにもアクセスする可能性があるため、スリープ可能なコンテキストから行う必要があります（これらの設定呼び出しは通常ボード設定やドライバのプローブ/ teardownコードから行われるため、この制約は簡単に遵守できます）：

        gpio_direction_input()
        gpio_direction_output()
        gpio_request()

##      gpio_request_one()
##      gpio_request_array()
##      gpio_free_array()

        gpio_free()
        gpio_set_debounce()

GPIOの取得と解放¶

システム構成エラーを検出するために、2つの呼び出しを定義しています：

/* request GPIO, returning 0 or negative errno.
 * non-null labels may be useful for diagnostics.
 */
int gpio_request(unsigned gpio, const char *label);

/* release previously-claimed GPIO */
void gpio_free(unsigned gpio);

gpio_request()に無効なGPIO番号を渡すと失敗し、すでにgpio_request()で取得済みのGPIOを再取得しようとすると失敗します。gpio_request()の戻り値を必ず確認する必要があります。通常はタスクコンテキストからこれらの呼び出しを行います。ただし、スピンロック安全なGPIOについては、タスクが有効になる前からGPIOを取得することが可能です（これは早期ボード設定の一環として行われます）。

これらの呼び出しは2つの基本的な目的を持っています。1つ目は、実際に使用中の信号をGPIOとしてマークし、診断をより効率化することです。システムには数百の潜在的なGPIOがあるかもしれませんが、実際に使用されるのは数十程度です。もう1つは、競合を検出することです。例えば、複数のドライバが誤って特定の信号の排他アクセスを想定している場合、または何かが誤ってアクティブに使用中の信号を管理するドライバを削除するのを安全だと誤って認識している場合のエラーを検出します。つまり、GPIOを取得することは一種のロックとして機能します。

一部のプラットフォームでは、アクティブなGPIOに関する知識を電源管理に利用することもあります。例えば、未使用のチップセクションを電源を切る、あるいはより簡単に未使用のクロックを遮断するなどします。

pinctrlサブシステムがピンを認識しているGPIOを使用する場合、そのサブシステムに使用を通知する必要があります。gpiolibドライバーの.request()操作ではpinctrl_gpio_request()を呼び出し、.free()操作ではpinctrl_gpio_free()を呼び出すことができます。pinctrlサブシステムは、ピンまたはピングループがデバイスによってピン多重化のために「所有」されている状態でも、pinctrl_gpio_request()が成功するようにします。

GPIO信号を適切なピンにルーティングするために必要なピン多重化ハードウェアのプログラミングは、GPIOドライバーの.direction_input()または.direction_output()操作内で行われるべきです。また、出力GPIOの値の設定後に実行する必要があります。これにより、ピンの特殊な機能からGPIOへの切り替えがノイズを伴わずに実行できます。これは、非GPIOハードウェアブロックによって駆動される信号に対してGPIOを用いた回避策を実装する場合など、しばしば必要です。

一部のプラットフォームでは、一部またはすべてのGPIO信号を異なるピンにルーティングすることが可能です。同様に、GPIOやピンの他の設定も必要となることがあります（例：プルアップ/プルダウン）。プラットフォームソフトウェアは、これらの設定をgpio_request()が呼ばれる前に完了させる必要があります。たとえば、pinctrlサブシステムのマッピングテーブルを使用して、GPIOユーザーがこれらの詳細を意識する必要がありません。

また、GPIOを解放する前にその使用を停止している責任はあなたのものです。

ほとんどの場合、GPIOは実際に取得した後すぐに設定されるため、以下の3つの追加の呼び出しが定義されています。

/* request a single GPIO, with initial configuration specified by
 * 'flags', identical to gpio_request() wrt other arguments and
 * return value
 */
int gpio_request_one(unsigned gpio, unsigned long flags, const char *label);

/* request multiple GPIOs in a single call
 */
int gpio_request_array(struct gpio *array, size_t num);

/* release multiple GPIOs in a single call
 */
void gpio_free_array(struct gpio *array, size_t num);

ここで「flags」は現在、以下のプロパティを指定するために定義されています：

  • GPIOF_DIR_IN - 方向を入力に設定

  • GPIOF_DIR_OUT - 方向を出力に設定

  • GPIOF_INIT_LOW - 出力として初期レベルをLOWに設定

  • GPIOF_INIT_HIGH - 出力として初期レベルをHIGHに設定

  • GPIOF_OPEN_DRAIN - GPIOピンがオープンドレインタイプです。

  • GPIOF_OPEN_SOURCE - GPIOピンがオープンソースタイプです。

  • GPIOF_EXPORT_DIR_FIXED - sysfsにGPIOをエクスポートし、方向を固定します

  • GPIOF_EXPORT_DIR_CHANGEABLE - またエクスポートし、方向の変更を許可します

GPIOF_INIT_*は出力として設定された場合にのみ有効なので、有効な組み合わせを以下のようにグループ化します：

  • GPIOF_IN - 入力として設定

  • GPIOF_OUT_INIT_LOW - 出力として設定し、初期レベルをLOWに

  • GPIOF_OUT_INIT_HIGH - 出力として設定し、初期レベルをHIGHに

GPIOF_OPEN_DRAINフラグを設定すると、ピンがオープンドレイン型とみなされます。このようなピンは出力モードで1に駆動されません。このようなピンにはプルアップを接続する必要があります。このフラグを有効にすると、gpioライブラリは出力モードで値を1に設定する要求があった場合、ピンを入力方向にします。出力モードで値を0に駆動することでピンはLOWになります。

GPIOF_OPEN_SOURCEフラグを設定すると、ピンがオープンソース型とみなされます。このようなピンは出力モードで0に駆動されません。このようなピンにはプルダウンを接続する必要があります。このフラグを有効にすると、出力モードで値を0に設定する要求があった場合、ピンを入力方向にします。出力モードで値を1に駆動することでピンはHIGHになります。

今後、これらのフラグはより多くのプロパティをサポートする拡張が行われる予定です。

さらに、複数のGPIOを簡単に取得/解放できるようにするため、'struct gpio'が導入され、すべての3つのフィールドを以下のようにカプセル化します:

struct gpio {
        unsigned        gpio;
        unsigned long   flags;
        const char      *label;
};

使用例の一例:

static struct gpio leds_gpios[] = {
        { 32, GPIOF_OUT_INIT_HIGH, "Power LED" }, /* default to ON */
        { 33, GPIOF_OUT_INIT_LOW,  "Green LED" }, /* default to OFF */
        { 34, GPIOF_OUT_INIT_LOW,  "Red LED"   }, /* default to OFF */
        { 35, GPIOF_OUT_INIT_LOW,  "Blue LED"  }, /* default to OFF */
        { ... },
};

err = gpio_request_one(31, GPIOF_IN, "Reset Button");
if (err)
        ...

err = gpio_request_array(leds_gpios, ARRAY_SIZE(leds_gpios));
if (err)
        ...

gpio_free_array(leds_gpios, ARRAY_SIZE(leds_gpios));

GPIOが割り当てられたIRQ¶

GPIO番号は符号なし整数であり、IRQ番号も同様です。これらは論理的に異なる2つの名前空間を構成します（GPIO 0はIRQ 0を使用する必要はありません）。これらを相互にマッピングするには、次の関数呼び出しを使用できます:

/* map GPIO numbers to IRQ numbers */
int gpio_to_irq(unsigned gpio);

/* map IRQ numbers to GPIO numbers (avoid using this) */
int irq_to_gpio(unsigned irq);

これらは他の名前空間における対応する番号を返します。マッピングができない場合は負のエラー番号コードを返します。（例：一部のGPIOはIRQとして使用できません。）gpio_direction_input()で入力として設定されていないGPIO番号を使用する、またはgpio_to_irq()から得たIRQ番号を使用する場合、エラーが発生します。

これらの2つのマッピング関数は、単一の加算または減算に相当するコストがかかると期待されます。これらはスリープを許可しません。

gpio_to_irq()から返された非エラー値は、 request_irq() または free_irq(). They will often be stored into IRQ resources for platform devices, by the board-specific initialization code. Note that IRQ trigger options are part of the IRQ interface, e.g. IRQF_TRIGGER_FALLING, as are system wakeup capabilities.

irq_to_gpio()から返された非エラー値は、例えばIRQがエッジトリガーの場合、gpio_get_value()と組み合わせてドライバ状態の初期化や更新に最もよく使用されます。注意点として、一部のプラットフォームではこの逆マッピングをサポートしていないため、使用を避けるべきです。

オープンドレイン信号のエミュレーション¶

時折、共有信号は「オープンドレイン」信号を使用する必要があります。ここで実際に駆動されるのはロー信号レベルのみです。（この用語はCMOSトランジスタに適用され、「オープンコレクタ」はTTLに使用されます。）プルアップ抵抗器によりハイ信号レベルが生成されます。これはしばしば「ワイヤーアンド」と呼ばれることがあり、否定論理（ロー＝真）の観点から見ると「ワイヤーオア」とも呼ばれます。

オープン・ドレイン信号の一般的な例は、共有されたアクティブ・ローIRQラインです。また、双方向データバス信号も時折オープン・ドレイン信号を使用します。

一部のGPIOコントローラはオープンドレイン出力の直接的なサポートを行います。多くのコントローラはサポートしていません。オープンドレイン信号が必要な場合でも、ハードウェアが直接サポートしていない場合は、任意の入出力ピンを用いてエミュレートするための一般的な技法があります:

LOW: gpio_direction_output(gpio, 0) … この関数は信号を駆動します

およびプルアップを上書きします。

HIGH: gpio_direction_input(gpio) … この関数は出力をオフにします

したがって、プルアップ（または他のデバイス）が信号を制御します。

信号をハイレベルに駆動しているにもかかわらず、gpio_get_value(gpio)が適切な立ち上がり時間の後にロー値を報告する場合、他のコンポーネントが共有信号をローに駆動していることを知ることができます。これは必ずしもエラーではありません。一般的な例として、I2Cクロックはこのような仕組みでストレッチされます: スレーブが遅いクロックを必要とする場合、SCKの立ち上がりエッジを遅らせ、I2Cマスターはそれに応じてシグナル速度を調整します。

GPIOコントローラとピン制御サブシステム¶

SoC上のGPIOコントローラは、ピンが他の機能とオプションでGPIO機能を組み合わせて使用可能であるという意味で、ピン制御サブシステムと密接に関連している場合があります。すでにGPIOコントローラがピンを予約するか、ピンの方向を設定する必要がある場合に、以下の関数を呼び出すケースを説明してきました:

pinctrl_gpio_request()
pinctrl_gpio_free()
pinctrl_gpio_direction_input()
pinctrl_gpio_direction_output()

しかし、GPIO番号（グローバルな仕様）を特定のピンコントローラ上の特定のピンにマッピングするには、どのようにピン制御サブシステムがこれを関連付けるのでしょうか？

これは「ピン範囲」の登録によって実現されます。これは基本的にクロスリファレンステーブルです。これらは以下のドキュメンテーションで説明されています: PINCTRL (PIN CONTROL)サブシステム

ピン割当は完全にピン制御サブシステムによって管理されていますが、gpio（gpiolib下）は依然としてgpioドライバによって維持されています。SoC内の異なるピン範囲が異なるgpioドライバによって管理される可能性があります。

これにより、gpioドライバがピン制御サブシステムにピン範囲を宣言し、その後pinctrl_gpio_requestを呼び出してピン制御サブシステムがピンを準備するよう依頼する前に、gpioの使用を開始するという論理的な流れができます。

このため、gpioコントローラはpinctrlサブシステムにピン範囲を登録できます。現在ではDT（Device Tree）を用いる場合と用いない場合の2つの方法があります。

DTを用いる場合についてはDocumentation/devicetree/bindings/gpio/gpio.txtを参照してください。

DTを用いない場合、ユーザーは以下の関数を適切なパラメータとともに呼び出して、pinctrlドライバにgpioピンの範囲を登録できます。この正確なpinctrlデバイス名は、この関数の引数の一つとして必須です。 gpiochip_add_pin_range() with appropriate parameters to register a range of gpio pins with a pinctrl driver. For this exact name string of pinctrl device has to be passed as one of the argument to this routine.

これらの規約が省略しているのは何ですか？¶

これらのコンベンションが省略している最大の要素の一つはピン多重割当て（pin multiplexing）です。これは非常にチップ固有であり、移植性がありません。あるプラットフォームでは明示的な多重割当てが不要かもしれませんし、他のプラットフォームでは特定のピンの使用方法として最大2つのオプションしか提供されないかもしれません。また、他のプラットフォームではピンごとに8つのオプションが、さらに他のプラットフォームでは特定のGPIOを複数のピンのいずれかにルーティングできるかもしれません。（これらの例はすべて現在Linuxを実行しているシステムから来ています。）

多重割当てに関連して、一部のプラットフォームで内蔵されたプルアップまたはプルダウンの設定と有効化も挙げられます。すべてのプラットフォームがこれらをサポートしているわけではなく、サポート方法もプラットフォームによって異なります。また、特定のボードでは外部プルアップ（またはプルダウン）を用いるため、チップ内蔵のものを使用すべきではありません。（回路が5 kOhmを必要とする場合、チップ内蔵の100 kOhm抵抗では満たせません。）ドライブ強度（2 mA vs 20 mA）や電圧（1.8V vs 3.3V）もプラットフォーム固有の問題であり、設定可能なピンとGPIOの1対1対応が存在するかどうかなどのモデルも同様です。

他にもここでは説明されていないシステム固有のメカニズムがあります。例えば、前述した入力デグリッチングオプションやワイヤーオア出力などです。ハードウェアがGPIOをグループで読み書き可能である場合もありますが、これは通常GPIOが同じバンクを共有している場合の設定に依存します。（GPIOは16または32ピンのバンクにグループ化され、特定のSOCでは複数のこのようなバンクが存在します。）一部のシステムでは出力GPIOからIRQをトリガーしたり、GPIOとして管理されていないピンから値を読み取ったりできます。このようなメカニズムに依存するコードは必然的に移植性がありません。

GPIOの動的定義は現在標準化されていません。例えば、GPIO拡張子を搭載した拡張ボードの設定によって間接的に発生する場合もあります。

GPIO実装者のフレームワーク（オプション）¶

前述したように、プラットフォームが同一のプログラミングインターフェースを用いてさまざまなGPIOコントローラーをサポートするためのオプションの実装フレームワークがあります。このフレームワークは「gpiolib」と呼ばれます。

デバッグの補助として、debugfsが利用可能であれば、/sys/kernel/debug/gpioというファイルがその場所に存在します。これはこのフレームワークを通じて登録されたすべてのコントローラーと、現在使用中のGPIOの状態を一覧表示します。

コントローラードライバー: gpio_chip¶

このフレームワークでは、各GPIOコントローラーは「struct gpio_chip」としてパッケージ化され、そのタイプのコントローラーに共通する情報を含みます:

  • GPIO方向を設定するためのメソッド

  • GPIO値にアクセスするためのメソッド

  • そのメソッドの呼び出しがスリープ可能かどうかを示すフラグ

  • オプションのdebugfsダンプメソッド（プルアップ設定などの追加状態を表示）

  • 診断用ラベル

また、インスタンスごとのデータも存在し、これはdevice.platform_dataから来ることがあります。これはそのGPIOの最初の番号と、公開するGPIOの数です。

gpio_chipを実装するコードは、ドライバモデルを用いて複数のコントローラーインスタンスをサポートする必要があります。このコードは、各gpio_chipを設定し、gpiochip_add()を呼び出します。GPIOコントローラーの削除はまれであり、使用する場合は gpiochip_remove() devm_gpiochip_add_data()を使用してください。

通常、gpio_chipはインスタンス固有の構造体に含まれており、GPIOインターフェースで露出されない状態（アドレス指定、電源管理など）を持ちます。コーデックなどのチップは複雑な非GPIO状態を持ちます。

debugfsダンプメソッドは、GPIOとしてリクエストされていない信号を通常は無視する必要があります。これらは、 gpiochip_is_requested()を呼び出すことで、GPIOがリクエストされたときに関連付けられたラベルを返すか、NULLを返します。

プラットフォームサポート¶

このフレームワークを強制的に有効にするには、プラットフォームのKconfigが「GPIOLIB」を「選択」する必要があります。それ以外の場合は、ユーザーがGPIOのサポートを構成する責任があります。

また、ARCH_NR_GPIOSにカスタム値を提供する場合もあります。これにより、プラットフォームで実際に使用されているGPIOの数をより正確に反映でき、静的テーブル空間を無駄にしません。（これは、組み込み/SoCのGPIOとGPIO拡張子にあるGPIOの両方をカウントする必要があります）

これらのオプションのいずれも選択されない場合、プラットフォームはGPIO-libを通じてGPIOをサポートせず、ユーザーがコードを有効にすることができません。

これらの関数の単純な実装は、フレームワークコードを直接使用できます。フレームワークコードは常にgpio_chipを介してディスパッチします：

#define gpio_get_value        __gpio_get_value
#define gpio_set_value        __gpio_set_value
#define gpio_cansleep         __gpio_cansleep

より高度な実装では、これらの関数をインライン関数として定義し、特定のSoCベースのGPIOへのアクセスを最適化するロジックを組み込むことができます。たとえば、参照されるGPIOが定数「12」である場合、その値の取得または設定には最大で2〜3インストラクションで済み、待機せずに済みます。このような最適化が不可能な場合は、フレームワークコードにデリゲートする必要があります。これには少なくとも数十インストラクションがかかるため、ビットバッジI/Oではこのようなインストラクションの節約が非常に重要です。

SoCの場合、プラットフォーム固有のコードは、チップ内のGPIOバンクごとにgpio_chipインスタンスを定義し、登録します。これらのGPIOは、チップベンダーのドキュメンテーションとボード回路図に直接一致するように、番号/ラベルを割り当てます。これらは通常、ゼロからプラットフォーム固有の上限まで連続する可能性があります。このようなGPIOは、通常、プラットフォーム初期化に統合されて常に利用可能になります（arch_initcall()またはそれ以前の段階）。これらはしばしばIRQとして機能します。

ボードサポート¶

外部のGPIOコントローラー（I2CやSPIエクスパンダー、ASIC、マルチファンクションデバイス、FPGAやCPLDなど）については、通常、ボード固有のコードがコントローラーのデバイスを登録し、ドライバがgpiochip_add()で使用するGPIO番号を把握するようにします。これらの番号は、プラットフォーム固有のGPIOの後に続きます。

例えば、ボード設定コードがGPIOチップが公開するGPIO範囲を特定する構造体を作成し、platform_dataを通じて各GPIOエクスパンダーに渡すことができます。その後、チップドライバのprobe()ルーチンがそのデータをgpiochip_add()に渡すことで、設定を完了します。

初期化の順序は重要です。例えば、I2CベースのGPIOに依存するデバイスでは、そのGPIOが利用可能になるまでprobe()ルーチンを呼び出すべきです。これは、GPIOが動作するまでデバイスを登録しない必要があることを意味します。このような依存関係を解決するためには、gpio_chipコントローラーがボード固有コードにsetup()とteardown()コールバックを提供することで、必要なリソースが利用可能になったらデバイスを登録し、GPIOコントローラーが利用不可になったら削除します。

ユーザースペース用のSysfsインターフェース（オプション）¶

「gpiolib」実装フレームワークを使用するプラットフォームでは、GPIOに対するユーザースペースインターフェースを構成する選択肢があります。これはデバッグfsインターフェースとは異なり、GPIOの方向と値の制御を提供するため、単にGPIOの状態を表示するだけではありません。さらに、デバッグサポートがなくても製造環境で存在する可能性があります。

システムの適切なハードウェアドキュメンテーションが与えられた場合、ユーザースペースは例えばGPIO #23がフラッシュメモリ内のブートローダーセグメントを保護するライト保護ラインを制御していることを知ることができます。システムアップグレード手順では、まずGPIOをインポートし、その後出力状態を変更し、コードを更新してからライト保護を再び有効にする必要があります。通常の使用ではGPIO #23は一切操作されず、カーネルはその存在を知る必要がありません。

適切なハードウェアドキュメンテーションに依存しますが、一部のシステムではユーザースペースGPIOを使用して標準カーネルが知らないシステム構成データを特定することができ、一部のタスクでは単純なユーザースペースGPIOドライバがシステムのすべての必要条件を満たす場合もあります。

標準のカーネルドライバが「LEDとボタン」のGPIOタスクを扱っており、「leds-gpio」と「gpio_keys」があります。直接GPIOにアクセスする代わりにこれらのドライバを使用してください。これらはユーザー空間のコードよりもカーネルフレームワークとよりよく統合されます。

Sysfsのパス¶

/sys/class/gpioに存在するエントリは3種類あります。

  • GPIOをユーザースペース制御に導くためのコントロールインターフェース;

  • GPIO自体; そして

  • GPIOコントローラー（"gpio_chip"インスタンス）。

これは"device"シンボリックリンクなどの標準ファイルを除いて追加されます。

コントロールインターフェースは書き込み専用です:

/sys/class/gpio/

「エクスポート」… ユーザースペースがこのファイルにGPIO番号を書き込むことで、カーネルにGPIOの制御をユーザースペースにエクスポートするよう要求できます。

「アンエクスポート」… エクスポートを解除します。

例: 「echo 19 > export」は、カーネルコードが要求していない場合でもGPIO #19の「gpio19」ノードを作成します。

「ディレクション」… 読み取ると「in」または「out」のいずれかになります。この値は通常書き込み可能です。

例: 「echo 19 > unexport」は、「export」ファイルを使用してエクスポートされた「gpio19」ノードを削除します。

GPIO信号は、/sys/class/gpio/gpio42/（GPIO #42の場合）などのパスを持ち、以下の読み書き可能な属性を持ちます:

/sys/class/gpio/gpioN/

「値」… 読み取ると0（ロー）または1（ハイ）のいずれかになります。GPIOが出力に設定されている場合、この値を書き込むことができます。非ゼロの値はハイとして扱われます。

「値」… 読み取ると0（ロー）または1（ハイ）のいずれかになります。GPIOが出力に設定されている場合、この値を書き込むことができます。非ゼロの値はハイとして扱われます。

この属性について注意してください が存在しない場合 カーネルがGPIOの方向変更をサポートしていない、またはカーネルコードがユーザースペースにこのGPIOの方向再構成を明示的に許可していない場合です。

「値」… 読み取ると0（ロー）または1（ハイ）のいずれかになります。GPIOが出力に設定されている場合、この値を書き込むことができます。非ゼロの値はハイとして扱われます。

「値」… 読み取ると0（ロー）または1（ハイ）のいずれかになります。GPIOが出力に設定されている場合、この値を書き込むことができます。非ゼロの値はハイとして扱われます。

ピンが割り込みを生成する設定にでき、かつ割り込みを生成する設定にされている場合（「エッジ」の説明を参照）、そのファイルに対してpoll(2)を実行できます。割り込みがトリガーされたたびにpoll(2)が返ります。poll(2)を使用する場合は、POLLPRIイベントを設定してください。select(2)を使用する場合は、exceptfdsにファイル記述子を設定してください。poll(2)が返った後は、sysfsファイルの先頭にlseek(2)して新しい値を読み取るか、ファイルを閉じて再オープンして値を読み取る必要があります。

「エッジ」…「なし」「上昇」「下降」、または

「両方」を読み取ります。これらの文字列を書き込むことで、「value」ファイルに対するpoll(2)が返るエッジを指定できます。

このファイルは、ピンが割り込み生成入力ピンとして設定可能である場合にのみ存在します。

「アクティブロー」… 0（偽）または1（真）を読み取ります。書き込む

任意のゼロ以外の値を指定すると、読み取りおよび書き込み時の値属性が反転します。既存および後のpoll(2)のサポート設定は、「上昇」および「下降」エッジのエッジ属性を通じてこの設定に従います。

GPIOコントローラーは、/sys/class/gpio/gpiochip42/（GPIO #42から開始するGPIOを実装するコントローラー）などのパスを持ち、以下の読み取り専用属性を持ちます:

/sys/class/gpio/gpiochipN/

「ベース」… このチップが管理する最初のGPIO（N）と同じです

「ラベル」… デバッグ用に提供される（常に一意ではない）

「ngpio」… このGPIOが管理するGPIOの数（NからN + ngpio - 1）

ボードドキュメンテーションでは、GPIOがどの目的で使用されるかを記載することが一般的です。ただし、GPIO番号は常に安定しているわけではありません。daughter board（拡張ボード）のGPIOは、使用しているベースボードやスタックされている他のボードによって異なり得るため、このような場合ではgpiochipノード（回路図と併用して）を使用して、特定のシグナルに使用する正しいGPIO番号を特定する必要があります。

カーネルコードからのエクスポート¶

カーネルコードは、gpio_request()で既にリクエストされたGPIOのエクスポートを明示的に管理できます：

/* export the GPIO to userspace */
int gpio_export(unsigned gpio, bool direction_may_change);

/* reverse gpio_export() */
void gpio_unexport();

/* create a sysfs link to an exported GPIO node */
int gpio_export_link(struct device *dev, const char *name,
        unsigned gpio)

カーネルドライバがGPIOを要求した後、sysfsインターフェースでそのGPIOを有効にするにはgpio_export()を使用します。ドライバは信号の方向変更を制御できます。これにより、ユーザー空間のコードが重要なシステム状態を誤って上書きするのを防ぐことができます。

このような明示的なエクスポートはデバッグに役立ち（特定の実験をより容易にする）、またボードサポートパッケージの一部としてドキュメンテーションに適した常に利用可能なインターフェースを提供できます。

GPIOがエクスポートされた後、gpio_export_link()はsysfsの他の場所からGPIO sysfsノードへのシンボリックリンクを作成できます。ドライバはこれを活用して、sysfs内の自身のデバイス下で説明的な名前でインターフェースを提供できます。

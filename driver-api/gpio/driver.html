GPIO Driver Interface¶

このドキュメントはGPIOチップドライバーのライター向けのガイドです。

各GPIOコントローラードライバーは、GPIOドライバーを定義するための構造体を定義する以下のヘッダーファイルを含める必要があります:

#include <linux/gpio/driver.h>

GPIOの内部表現¶

GPIOチップは1つまたは複数のGPIOラインを処理します。GPIOチップとみなされるには、ラインは「General Purpose Input/Output（汎用入出力）」の定義に合致する必要があります。ラインが汎用でない場合、それはGPIOではなく、GPIOチップで処理すべきではありません。使用例として、システム内の特定のラインがGPIOと呼ばれるかもしれませんが、特定の用途にのみ使用されるため、汎用I/Oの基準を満たさない場合があります。一方、LEDドライバのラインはGPIOとして使用される可能性があり、そのためGPIOチップドライバーで処理する必要があります。

GPIOドライバー内では、個々のGPIOラインはハードウェア番号で識別され、これは offset、チップが管理するGPIOの数（n）を基に0からn-1までの一意の番号です。

ハードウェアGPIO番号はハードウェアにとって直感的なものであるべきです。例えば、システムがメモリマップされたI/Oレジスタを使用し、32ビットレジスタ内の1ビットで32ラインを処理する場合、これらのラインに0..31のハードウェアオフセットを使用し、レジスタ内のビット0..3、31に一致させるのは自然です。

この番号は純粋に内部用です。特定のGPIOラインのハードウェア番号はドライバーの外部に公開されることはありません。

この内部番号に加えて、各GPIOラインは整数GPIO名前空間内のグローバル番号を持つ必要があります。これにより、レガシーGPIOインターフェースで使用できます。そのため、各チップは「ベース」番号（自動的に割り当てられる場合もあります）を持ち、各GPIOラインのグローバル番号は（ベース + ハードウェア番号）になります。整数表現は非推奨とされていますが、多くのユーザーが使用しているため、維持する必要があります。

例えば、あるプラットフォームではGPIOにグローバル番号32-159を使用し、コントローラーが「ベース」32で128のGPIOを定義する場合があります。一方、他のプラットフォームでは0..63のグローバル番号を使用し、1つのGPIOコントローラーで64-79の別のタイプのGPIOコントローラーで、特定のボードでは80-95のFPGAで使用する場合もあります。レガシー番号は連続する必要はありません。これらのプラットフォームは2000-2063の番号を使用してI2C GPIO拡張子チップのバンクを識別することもできます。

コントローラードライバー: gpio_chip¶

gpiolibフレームワークでは、各GPIOコントローラーは「struct gpio_chip（<linux/gpio/driver.h>を参照）の完全な定義を持つ。これらは、そのタイプの各コントローラーに共通するメンバであり、ドライバコードによって割り当てられるべきです：

  • GPIOラインの方向を確立するメソッド

  • GPIOライン値にアクセスするメソッド

  • 特定のGPIOラインの電気的設定を設定するメソッド

  • 特定のGPIOラインに関連するIRQ番号を返すメソッド

  • そのメソッドの呼び出しがスリープ可能かどうかを示すフラグ

  • オプションのライン名配列を用いてラインを識別する

  • オプションのdebugfsダンプメソッド（追加の状態情報の表示）

  • オプションのベース番号（省略された場合は自動的に割り当てられる）

  • 診断およびGPIOチップマッピングに使用するオプションのラベル（プラットフォームデータを用いる場合）

gpio_chipを実装するコードは、複数のコントローラーインスタンスをサポートすべきです。 preferably using the driver model。 そのコードは各gpio_chipを設定し、gpiochip_add()を実行します、 gpiochip_add_data()、またはdevm_gpiochip_add_data()。 GPIOコントローラーの削除はまれですが、避けられない場合は、 gpiochip_remove() devm_gpiochip_add_data()を使用してください。

通常、gpio_chipはインスタンス固有の構造体の一部であり、GPIOインターフェースで露出されない状態（アドレス指定、電源管理など）を含みます。 音声コーデックなどのチップは複雑な非GPIO状態を持ちます。

任意のdebugfsダンプメソッドは、リクエストされていないラインを無視する必要があります。 それらは、 gpiochip_is_requested()NULLまたはそのGPIOラインがリクエストされたときに関連付けられたラベルを返す関数を用いることができます。

リアルタイム考慮事項：GPIOドライバは、リアルタイムカーネルでのアトミックコンテキストからのGPIOAPI呼び出しを想定している場合、gpio_chip実装（.get/.setおよび方向制御コールバック）ではspinlock_tやスリープ可能なAPI（PMランタイムなど）を使用すべきではありません。 通常はこれが必要ありません。

GPIO電気的設定¶

GPIOラインは、.set_config()コールバックを使用して複数の電気的動作モードに設定できます。 現在、このAPIはサポートしています：

  • デブッキング

  • シングルエンドモード（オープンドレイン/オープンソース）

  • プルアップおよびプルダウン抵抗の有効化

これらの設定は以下に説明します。

.set_config()コールバックは、一般的なピン制御ドライバと同じ列挙子と設定 semantics を使用します。 これは偶然ではありません：.set_config()を関数に割り当てることで、 gpiochip_generic_config() pinctrl_gpio_set_config()が呼び出され、最終的にGPIOコントローラー「後ろに」あるピン制御バックエンドに到達します。 このようにして、ピンコントローラーが以下に記載されたGPIO設定を管理できます。

ピンコントローラーのバックエンドが使用される場合、GPIOコントローラーまたはハードウェアの説明は、「GPIO範囲」としてGPIOラインのオフセットをピンコントローラー上のピン番号にマッピングし、それらが適切に相互参照できるようにする必要があります。

デバウンス機能付きのGPIOライン¶

デバウンスは、ピンに機械式スイッチやボタン、または類似の装置が接続されていることを示す設定です。バウンスとは、機械的な理由によりラインが短い間隔で高/低に引き起こされる現象を指します。これにより、値が不安定になるか、IRQが繰り返し発生する可能性があります。

実際のデバウンスでは、ラインに変化が生じた際にタイマーセットを行い、少し待ってからラインを再サンプリングします。これにより、値が依然として低または高であるかを確認します。また、状態機械を巧みに利用してラインが安定するのを待つことも可能です。いずれの場合もデバウンス時間（ミリ秒単位）を設定するか、設定不可の場合はオン/オフの切り替えを行うことができます。

オープンドレイン/ソース機能付きのGPIOライン¶

オープンドレイン（CMOS）またはオープンコレクタ（TTL）は、ラインが積極的に高レベルを駆動しないことを意味します。代わりに、ドレイン/コレクタを出力として提供し、トランジスタが閉じていない場合、外部電源ラインに対して高インピーダンス（トリステート）を示します。

CMOS CONFIGURATION      TTL CONFIGURATION

         ||--- out              +--- out
  in ----||                   |/
         ||--+         in ----|
             |                |\
            GND                 GND

この設定は、以下の2つの目的の一つを達成するための方法として通常使用されます。

  • レベルシフト：出力が存在するシリコンの論理レベルよりも高い論理レベルを達成するためのものです。

  • I/Oライン（例：GPIOライン）における逆ワイヤーオア接続。これにより、ライン上の任意の駆動段が他の出力が同時に高レベルを駆動している場合でも、ラインを低レベルに駆動できるようになります。これはI2CバスのSCLおよびSDAラインの駆動が、定義上ワイヤーオアバスであるための特例です。

いずれの場合もラインにプルアップ抵抗を搭載する必要があります。この抵抗により、ラインはプルアップ抵抗のVDDに傾向を示すが、ライン上のトランジスタがアクティブに低レベルに引き下げる場合を除きます。

ラインのレベルは、プルアップ抵抗のVDDに達する可能性があり、これはトランジスタがサポートするレベルよりも高いため、高VDDへのレベルシフトを実現します。

統合電子機器では、出力ドライバ段としてCMOSの「トゥモローポール」（N-MOSトランジスタとP-MOSトランジスタを組み合わせた構造）が使用されることがあり、一方のトランジスタがラインを高レベルに、もう一方が低レベルに駆動します。これを「プッシュプル出力」と呼び、その構造は以下のようになります。

                 VDD
                  |
        OD    ||--+
     +--/ ---o||     P-MOS-FET
     |        ||--+
IN --+            +----- out
     |        ||--+
     +--/ ----||     N-MOS-FET
        OS    ||--+
                  |
                 GND

望ましい出力信号（例：GPIO出力レジスタから直接来るもの）がINに到達します。ODおよびOSと呼ばれるスイッチは通常閉じており、プッシュ・プル回路を形成しています。

入力の分割直後にP-MOSまたはN-MOSトランジスタを有効/無効にする小さな「スイッチ」ODおよびOSを考慮してください。このスイッチが開いていると、どちらのトランジスタも完全に動作しなくなります。トーテムポールは半分になり、ラインを積極的に高/低に駆動する代わりに高インピーダンスになります。これは通常、ソフトウェア制御によるオープン・ドレイン/オープン・ソースの仕組みです。

一部のGPIOハードウェアはオープン・ドレイン/オープン・ソースの設定で提供されます。一部はハードウェアで固定され、オープン・ドレインまたはオープン・ソースのみをサポートします（トランジスタが1つしかありません）。一部はソフトウェアで設定可能で、レジスタのビットを反転させることで出力をオープン・ドレインまたはオープン・ソースに設定できます（上記の図におけるODおよびOSスイッチを切り替えることになります）。

P-MOSトランジスタを無効にすると、出力はGNDと高インピーダンス（オープン・ドレイン）の間で駆動できます。N-MOSトランジスタを無効にすると、出力はVDDと高インピーダンス（オープン・ソース）の間で駆動できます。前者の場合、出力ラインにプルアップ抵抗が必要です。後者の場合、出力ラインにプルダウン抵抗が必要です。

オープン・ドレインまたはオープン・ソース、または両方をサポートするハードウェアは、gpio_chipに特別なコールバック関数.set_config()を実装できます。これはジェネリックなピン設定パック値を受取り、ラインをオープン・ドレイン、オープン・ソース、またはプッシュ・プルとして設定します。これはGPIO_OPEN_DRAINまたはGPIO_OPEN_SOURCEフラグがマシンファイルに設定されているか、他のハードウェア記述から来ている場合に発生します。

この状態がハードウェアで設定できない場合（つまりGPIOハードウェアがオープン・ドレイン/オープン・ソースをサポートしていない場合）、GPIOライブラリはトリックを使います。ラインが出力モードに設定されている場合、ラインがオープン・ドレインフラグで指定されていて、IN出力値がローの場合、通常通りローに駆動します。IN出力値がハイの場合、代わりに 禁止です ハイに駆動する代わりに、入力モードに切り替えられます。入力モードは高インピーダンスなので、これにより「オープン・ドレインエミュレーション」が実現されます。電気的に動作は同じですが、ラインのモードを切り替える際のハードウェアのグリッチが発生する可能性があります。

オープンソースの設定においても同じ原則が使用されますが、ラインをアクティブに低電圧に駆動する代わりに、入力として設定されます。

プルアップ/プルダウン抵抗をサポートするGPIOライン¶

GPIOラインは.set_config()コールバックを使用してプルアップ/プルダウンをサポートできます。これはGPIOラインの出力にプルアップまたはプルダウン抵抗が搭載され、この抵抗はソフトウェアによって制御されるということを意味します。

ディスクリート設計では、回路板にプルアップまたはプルダウン抵抗が単純に実装されます。これはソフトウェアで扱うものではなくモデル化しません。これらのラインについて考える最も重要な点は、ほぼ確実にオープンドレインまたはオープンソースとして設定されていること（上記のセクションを参照）です。

.set_config()コールバックは、プルアップまたはプルダウンをオン/オフに切り替えるだけです。抵抗値の使用に関するセマンティックな知識は持ちません。単にレジスタ内のビットを切り替えることでプルアップまたはプルダウンを有効/無効にするだけです。

GPIOラインがプルアップまたはプルダウン抵抗の異なる抵抗値でシーティングをサポートする場合、GPIOチップの.set_config()コールバックだけでは不十分です。このような複雑な使用ケースでは、GPIOチップとピンコントローラーの組み合わせを実装する必要があります。ピンコントローラーのピン設定インターフェースは電気的特性のより柔軟な制御をサポートし、さまざまなプルアップまたはプルダウン抵抗値を処理できます。

割り込み（IRQ）を提供するGPIOドライバ¶

GPIOドライバ（GPIOチップ）は通常、割り込みを提供しており、最もよくあるのは親割り込みコントローラーからのカスケードです。一部の特殊なケースでは、GPIO論理がSoCのプライマリ割り込みコントローラーと統合されています。

GPIOブロックの割り込み部分は、ヘッダーファイル<linux/irq.h>を使用したirq_chipで実装されます。したがって、この組み合わせドライバはgpioとirqの2つのサブシステムを同時に利用しています。

任意のIRQ消費者が、組み合わせドライバであっても、任意のirqchipからIRQを要求することは法的に許可されています。基本的な前提は、gpio_chipとirq_chipが正規化されたサービスであり、お互いに依存せずに独立して提供されることです。

gpiod_to_irq() 特定のGPIOラインのIRQを特定するための便宜的な関数であり、IRQが使用される前にこの関数が呼び出されたことを依存すべきではありません。

GPIOおよびirq_chip APIからのそれぞれのコールバックでハードウェアを準備し、動作準備を整える必要があります。事前に呼び出しされたことを依存しないでください。 gpiod_to_irq() 呼び出しされたことが保証されているとは限りません。

GPIO割り込みチップは大きく2つのカテゴリに分類できます：

  • 連鎖型割り込みチップ: これはGPIOチップが1つの共通割り込み出力ラインを持ち、そのチップ上の任意の有効なGPIOラインがトリガーとなることを意味します。この割り込み出力ラインは、最も単純なケースではシステムの主な割り込み制御器にルーティングされます。これはGPIO制御器内のビットを検査してどのラインが発生したかを特定するirqchipによってモデル化されます。ドライバのirqchip部分はレジスタを検査してこれを特定し、通常は割り込みを処理していることを確認するためにいくつかのビットをクリアする必要があります（場合によってはステータスレジスタを読み込むだけで暗黙的に処理されます）。また、エッジ感度（上昇/下降エッジ、または高/低レベルの割り込みなど）などの設定を設定する必要があります。

  • 階層型割り込みチップ: これは各GPIOラインが親の割り込み制御器に割り当てられた専用の割り込みラインを持つことを意味します。GPIOハードウェアを確認する必要はなく、どのラインが発生したかを特定できますが、依然として割り込みを確認する必要があり、エッジ感度などの設定を設定する必要がある場合があります。

リアルタイム考慮事項: リアルタイム準拠のGPIOドライバは、irqchip実装内でspinlock_tや睡眠可能API（例: PMランタイム）を使用してはいけません。

  • spinlock_tはraw_spinlock_tに置き換えるべきです。[1]

  • 睡眠可能APIを使用する必要がある場合は、.irq_bus_lock()と.irq_bus_unlock()コールバックから実行できます。これらはirqchipでのみ存在する遅延処理コールバックです。必要に応じてコールバックを作成してください。[2]

連鎖型GPIO割り込みチップ¶

連鎖型GPIO割り込みチップは通常、以下の3つのカテゴリのいずれかに該当します:

  • チェイン型連鎖型GPIO割り込みチップ: これらは通常SoCに埋め込まれたタイプです。これはGPIOの高速割り込みハンドラがシステム割り込み制御器からのチェインで呼び出される事を意味します。これにより、GPIO割り込みチップハンドラは親割り込みチップから直ちに呼び出され、IRQを無効にした状態で実行されます。GPIO割り込みチップはその割り込みハンドラで以下のような処理を実行します:

    static irqreturn_t foo_gpio_irq(int irq, void *data)
    chained_irq_enter(...);
    generic_handle_irq(...);
    chained_irq_exit(...);

    連鎖型GPIO割り込みチップは通常、.can_sleepフラグを設定できません。 struct gpio_chipなぜならすべての処理が直接コールバック内で行われるため、I2Cなどの遅延のあるバス通信は使用できません。

    リアルタイム考慮事項: チェイン型割り込みハンドラは-RTで強制スレッド化されません。その結果、spinlock_tや睡眠可能API（例: PMランタイム）はチェイン型割り込みハンドラで使用できません。

    必要がある場合（nested threaded GPIO irqchipに変換できない場合、下記を参照）、chained IRQハンドラはgeneric IRQハンドラに変換可能であり、これにより-RTではthreaded IRQハンドラ、非-RTではhard IRQハンドラとして動作します（例として[3]を参照）。

    以下の generic_handle_irq() IRQが無効な状態で呼び出されることが期待されており、IRQコアはIRQハンドラから強制的にスレッドに移された状態で呼び出された場合に警告を出します。この問題を回避するには、「fake?」raw lockを使用できます：

    raw_spinlock_t wa_lock;
static irqreturn_t omap_gpio_irq_handler(int irq, void *gpiobank)
    unsigned long wa_lock_flags;
    raw_spin_lock_irqsave(&bank->wa_lock, wa_lock_flags);
    generic_handle_irq(irq_find_mapping(bank->chip.irq.domain, bit));
    raw_spin_unlock_irqrestore(&bank->wa_lock, wa_lock_flags);

  • GENERIC CHAINED GPIO IRQCHIPS: これは「CHAINED GPIO irqchips」と同じですが、chained IRQハンドラは使用されません。代わりに、generic IRQハンドラがGPIO IRQのディスパッチを処理し、以下のように設定されます： request_irq()GPIO irqchipはその割り込みハンドラで以下のようなシーケンスを呼び出します：

    static irqreturn_t gpio_rcar_irq_handler(int irq, void *dev_id)
    for each detected GPIO IRQ
        generic_handle_irq(...);

    リアルタイム考慮: この種のハンドラは-RTでは強制的にthreadedになります。その結果、IRQコアは generic_handle_irq() IRQが有効な状態で呼び出されたと警告を出し、"CHAINED GPIO irqchips"の場合と同じワークアラウンドが適用可能です。

  • NESTED THREADED GPIO IRQCHIPS: これはオフチップのGPIOエクスパンドャーや、I2CやSPIなどのスリープバスの他側に配置された他のGPIO irqchipです。

    もちろん、IRQステータスを読み出すなどの遅いバストラフィックを必要とするドライバは、IRQが無効な状態でクイックIRQハンドラで処理できません。代わりにスレッドを生成し、ドライバが割り込みを処理するまで親IRQラインをマスクする必要があります。このドライバの特徴は、割り込みハンドラで以下のような処理を呼び出すことです：

    static irqreturn_t foo_gpio_irq(int irq, void *data)
    ...
    handle_nested_irq(irq);

    threaded GPIO irqchipsの特徴は、GPIOラインにアクセスする際、.can_sleepフラグを struct gpio_chip trueに設定することです。これにより、このチップがGPIOにアクセスする際スリープ可能であることを示します。

    このようなirqchipsは本来リアルタイムに耐性があり、すでにスリープコンテキストを処理するように設定されています。

一部のGPIOラインが対応するIRQを持たない場合、gpio_irq_chip内のビットマスクvalid_maskとフラグneed_valid_maskを使用して、IRQと関連付けるために無効なラインをマスク処理することが可能です。

ヘルパーサポートの設定には、以下の通り struct gpio_irq_chip inside struct gpio_chip gpio_chipを追加する前に実施します。この方法を採用すると、gpiolibがGPIO機能の他の部分の設定と同時に追加のirq_chipを自動的に設定します。以下はgpio_irq_chipを使用した連鎖的な割り込みハンドラの典型的な例です：

/* Typical state container with dynamic irqchip */
struct my_gpio {
    struct gpio_chip gc;
    struct irq_chip irq;
};

int irq; /* from platform etc */
struct my_gpio *g;
struct gpio_irq_chip *girq;

/* Set up the irqchip dynamically */
g->irq.name = "my_gpio_irq";
g->irq.irq_ack = my_gpio_ack_irq;
g->irq.irq_mask = my_gpio_mask_irq;
g->irq.irq_unmask = my_gpio_unmask_irq;
g->irq.irq_set_type = my_gpio_set_irq_type;

/* Get a pointer to the gpio_irq_chip */
girq = &g->gc.irq;
girq->chip = &g->irq;
girq->parent_handler = ftgpio_gpio_irq_handler;
girq->num_parents = 1;
girq->parents = devm_kcalloc(dev, 1, sizeof(*girq->parents),
                             GFP_KERNEL);
if (!girq->parents)
    return -ENOMEM;
girq->default_type = IRQ_TYPE_NONE;
girq->handler = handle_bad_irq;
girq->parents[0] = irq;

return devm_gpiochip_add_data(dev, &g->gc, g);

階層的な割り込みコントローラーを用いたヘルパーサポートも可能です。この場合、典型的な設定は以下のようになります：

/* Typical state container with dynamic irqchip */
struct my_gpio {
    struct gpio_chip gc;
    struct irq_chip irq;
    struct fwnode_handle *fwnode;
};

int irq; /* from platform etc */
struct my_gpio *g;
struct gpio_irq_chip *girq;

/* Set up the irqchip dynamically */
g->irq.name = "my_gpio_irq";
g->irq.irq_ack = my_gpio_ack_irq;
g->irq.irq_mask = my_gpio_mask_irq;
g->irq.irq_unmask = my_gpio_unmask_irq;
g->irq.irq_set_type = my_gpio_set_irq_type;

/* Get a pointer to the gpio_irq_chip */
girq = &g->gc.irq;
girq->chip = &g->irq;
girq->default_type = IRQ_TYPE_NONE;
girq->handler = handle_bad_irq;
girq->fwnode = g->fwnode;
girq->parent_domain = parent;
girq->child_to_parent_hwirq = my_gpio_child_to_parent_hwirq;

return devm_gpiochip_add_data(dev, &g->gc, g);

見た目はほぼ同じですが、IRQに親ハンドラを指定するのではなく、親irqdomain、ハードウェア用のfwnode、および子（つまりこのGPIOチップ）のハードウェアIRQから親ハードウェアIRQを検索する目的を持つ.child_to_parent_hwirq()関数を指定します。いつも通り、カーネルツリー内の例を確認するのが良いです。

GPIOチップの登録後にirqchipを追加する古い方法もまだ利用可能です。ただし、この方法は徐々に廃止されていきます：

  • 非推奨：gpiochip_irqchip_add(): gpiochipに連鎖的な割り込みチップを追加します。これは struct gpio_chipチップにすべてのIRQコールバックに通知するため、コールバックはstate containerにgpio_chipを埋め込む必要があり、containerへのポインタを取得するために container_of()。 (参照 Device Driver Design Patterns)

  • gpiochip_irqchip_add_nested(): 上記で説明したように、異なる種類のカスケードIRQチップをgpiochipにネストしたカスケードIRQチップを追加します。カスケードIRQはスレッド型割込みハンドラで処理する必要があります。それ以外の動作はチェーンされたIRQチップとまったく同じです。

  • gpiochip_set_nested_irqchip()：親IRQからgpio_chip用のネストしたカスケードIRQハンドラを設定します。親IRQは通常ドライバによって明示的にリクエストされるため、この関数は子IRQを親IRQとしてマークする以外にほとんど何もしません。

これらのヘルパーで処理するIRQドメインから特定のGPIOラインを除外する必要がある場合、devm_gpiochip_add_data()またはgpiochip_irqchip_add()が呼ばれる前にgpiochipの.irq.need_valid_maskを設定できます。これにより、チップ内のGPIOライン数と同じ数のビットが設定された.irq.valid_maskが割り当てられます。各ビットはライン0..n-1を表します。ドライバはこのマスクからビットをクリアすることでGPIOラインを除外できます。マスクはgpiochip_irqchip_add()またはgpiochip_irqchip_add_nested()が呼ばれる前に埋め込む必要があります。 gpiochip_add_data() is called. This allocates an .irq.valid_mask with as many bits set as there are GPIO lines in the chip, each bit representing line 0..n-1. Drivers can exclude GPIO lines by clearing bits from this mask. The mask must be filled in before gpiochip_irqchip_add() or gpiochip_irqchip_add_nested() is called.

To use the helpers please keep the following in mind:

  • Make sure to assign all relevant members of the struct gpio_chip irqchipが初期化できるようにするため。例えば、.devと.can_sleepは適切に設定する必要があります。

  • 通常はすべてのハンドラを handle_bad_irq() setupコールバックで設定し、 handle_bad_irq() gpiochip_irqchip_add()のフローハンドラパラメータとして渡す必要があります。GPIOドライバがirqchipの.set_type()コールバックが各GPIO IRQの使用/有効化前に呼ばれることが予期される場合です。その後、ハンドラを handle_level_irq() および/または handle_edge_irq() irqchipの.set_type()コールバック内で、コントローラーがサポートするものと消費者が要求するものに応じて設定します。

IRQ使用のロック¶

GPIOとirq_chipは直交しているため、異なる使用ケース間で競合が発生する可能性があります。例えば、IRQとして使用されるGPIOラインは入力ラインでなければならず、出力GPIOで中断を発生させるのは意味がありません。

サブシステム内でリソース（特定のGPIOラインやレジスタなど）の使用競合がある場合、特定の操作を拒否し、gpiolibサブシステム内で使用状態を追跡する必要があります。

入力GPIOはIRQ信号として使用できます。このような場合、ドライバにGPIOをIRQとして使用しているとマークする必要があります：

int gpiochip_lock_as_irq(struct gpio_chip *chip, unsigned int offset)

これにより、GPIO IRQロックが解放されるまで、非IRQ関連のGPIO APIの使用が防がれます：

void gpiochip_unlock_as_irq(struct gpio_chip *chip, unsigned int offset)

GPIOドライバ内にirqchipを実装する場合、これらの2つの関数は通常、irqchipの.startup()と.shutdown()コールバックから呼び出されるべきです。

gpiolibのirqchipヘルパを使用する場合、これらのコールバックは自動的に割り当てられます。

IRQの無効化と有効化¶

一部の（特殊な）用途では、ドライバがGPIOラインをIRQの入力として使用しているが、たまにそのラインを出力駆動に切り替え、その後再度中断付き入力に戻すことがあります。これはCEC（Consumer Electronics Control）などの用途で発生します。

GPIOをIRQ信号として使用する場合、gpiolibにもIRQが有効か無効かを知らせる必要があります。この情報をgpiolibに伝えるには、irqchipドライバが以下のように呼び出す必要があります：

void gpiochip_disable_irq(struct gpio_chip *chip, unsigned int offset)

これにより、IRQが無効な状態でGPIOを出力として駆動できます。IRQが再び有効になったら、ドライバは以下のように呼び出します：

void gpiochip_enable_irq(struct gpio_chip *chip, unsigned int offset)

GPIOドライバ内にirqchipを実装する場合、これらの関数は通常、irqchipのirq_disable() と.irq_enable()コールバックから呼び出されるべきです。

gpiolibのirqchipヘルパを使用する場合、これらのコールバックは自動的に割り当てられます。

GPIO IRQチップのリアルタイム準拠¶

irqchipの提供者は、リアルタイムプリエンプションをサポートするように慎重に設計する必要があります。GPIOサブシステム内のすべてのirqchipはこの点を考慮し、適切なテストを行うことでリアルタイム動作を確保する必要があります。

したがって、ドキュメンテーションに上記のリアルタイムに関する考慮事項を注意深く記載してください。

リアルタイム準拠のドライバーを準備する際のチェックリストは以下の通りです:

  • spinlock_t を irq_chip の実装として使用しないようにしてください

  • sleepable APIs を irq_chip の実装として使用しないようにしてください。sleepable APIs を使用する必要がある場合は、これらは .irq_bus_lock() と .irq_bus_unlock() コールバックから実行できます

  • チェインされた GPIO irqchip: チェインされた IRQ ハンドラから spinlock_t や sleepable APIs を使用しないようにしてください

  • 汎用チェインされた GPIO irqchip: 注意が必要です generic_handle_irq() 呼び出しと、対応する回避策を適用してください

  • チェインされた GPIO irqchip: チェインされた IRQ ハンドラを削除し、可能な場合は汎用 IRQ ハンドラを使用してください

  • regmap_mmio: .disable_locking を設定し、GPIO ドライバーでロック処理を担当することで、regmap 内部のロックを無効にすることができます

  • レベルおよびエッジ IRQ に対応した適切な内蔵リアルタイムテストケースでドライバーをテストしてください

自己所有GPIOピンの要求¶

GPIOチップドライバーがgpiolib APIを通じて自身のGPIOディスクリプタを要求できるようにすることが有効な場合があります。GPIOドライバーは以下の関数を使用してディスクリプタを要求および解放できます:

struct gpio_desc *gpiochip_request_own_desc(struct gpio_desc *desc,
                                            u16 hwnum,
                                            const char *label,
                                            enum gpiod_flags flags)

void gpiochip_free_own_desc(struct gpio_desc *desc)

Descriptors requested with gpiochip_request_own_desc() must be released with gpiochip_free_own_desc().

これらの関数はモジュール使用カウントに影響しないため、注意して使用してください。呼び出し元のドライバーが所有していないGPIOディスクリプタの要求には使用しないでください

GPIOマッピング¶

このドキュメントでは、GPIOを特定のデバイスおよび機能に割り当てる方法について説明します。

注意: これは新しいディスクリプタベースのインターフェースにのみ適用されます。非推奨の整数ベースのGPIOインターフェースについての説明はgpio-legacy.txtを参照してください（実際には、古いインターフェースでは本当にマッピングが可能ではなく、どこかから整数を取得して対応するGPIOを要求するだけです）。

すべてのプラットフォームでGPIOライブラリを有効化できますが、プラットフォームがGPIO機能の存在を厳密に要求する場合、そのKconfigからGPIOLIBを選択する必要があります。その後、GPIOのマッピング方法は、プラットフォームがハードウェアレイアウトを記述するために使用する方法に依存します。現在、マッピングはデバイスツリー、ACPI、およびプラットフォームデータを通じて定義できます。

Device Tree¶

GPIOはデバイスツリー内でデバイスおよび機能に簡単にマッピングできます。正確なやり方は、GPIOを提供するGPIOコントローラーに依存します。お使いのコントローラーのデバイスツリーバインディングを参照してください。

GPIOマッピングは、消費者デバイスのノード内で定義され、<function>-gpiosという名前のプロパティに記述されます。ここで<function>はドライバが要求する機能です。 gpiod_get()。

foo_device {
        compatible = "acme,foo";
        ...
        led-gpios = <&gpio 15 GPIO_ACTIVE_HIGH>, /* red */
                    <&gpio 16 GPIO_ACTIVE_HIGH>, /* green */
                    <&gpio 17 GPIO_ACTIVE_HIGH>; /* blue */

        power-gpios = <&gpio 1 GPIO_ACTIVE_LOW>;
};

<function>-gpioという名前のプロパティも有効とみなされ、古いバインディングでは使用されていますが、互換性のためのみサポートされており、新しいバインディングでは使用すべきではありません（これは非推奨です）。

このプロパティにより、ドライバは「led」機能でGPIO 15、16、17を使用でき、GPIO 1は「power」GPIOとして利用できます：

struct gpio_desc *red, *green, *blue, *power;

red = gpiod_get_index(dev, "led", 0, GPIOD_OUT_HIGH);
green = gpiod_get_index(dev, "led", 1, GPIOD_OUT_HIGH);
blue = gpiod_get_index(dev, "led", 2, GPIOD_OUT_HIGH);

power = gpiod_get(dev, "power", GPIOD_OUT_HIGH);

led GPIOはアクティブハイで、power GPIOはアクティブローになります（つまり、gpiod_is_active_low(power)はtrueになります）。

第二パラメータの gpiod_get() 関数の第二パラメータであるcon_id文字列は、デバイスツリーで使用されるGPIOサフィックス（「gpios」または「gpio」、gpiod関数が内部的に自動的に検索）の<function>-プレフィックスでなければなりません。上記の「led-gpios」例では、文字列の「-」を除いたプレフィックスをcon_idパラメータとして使用します：「led」。

内部的には、GPIOサブシステムは、con_idで渡された文字列をGPIOサフィックス（「gpios」または「gpio」）の前に付けて結果の文字列を生成します（snprintf(... "%s-%s", con_id, gpio_suffixes[]).

ACPI¶

ACPIもDTと同様の方法でGPIOの機能名をサポートしています。上記のDT例は、_DSD（デバイス固有データ）を使用してACPI 5.1で導入された同等のACPI記述に変換できます：

Device (FOO) {
        Name (_CRS, ResourceTemplate () {
                GpioIo (Exclusive, ..., IoRestrictionOutputOnly,
                        "\\_SB.GPI0") {15} // red
                GpioIo (Exclusive, ..., IoRestrictionOutputOnly,
                        "\\_SB.GPI0") {16} // green
                GpioIo (Exclusive, ..., IoRestrictionOutputOnly,
                        "\\_SB.GPI0") {17} // blue
                GpioIo (Exclusive, ..., IoRestrictionOutputOnly,
                        "\\_SB.GPI0") {1} // power
        })

        Name (_DSD, Package () {
                ToUUID("daffd814-6eba-4d8c-8a91-bc9bbf4aa301"),
                Package () {
                        Package () {
                                "led-gpios",
                                Package () {
                                        ^FOO, 0, 0, 1,
                                        ^FOO, 1, 0, 1,
                                        ^FOO, 2, 0, 1,
                                }
                        },
                        Package () {
                                "power-gpios",
                                Package () {^FOO, 3, 0, 0},
                        },
                }
        })
}

ACPI GPIOバインディングについての詳細情報は _DSD デバイスプロパティ（GPIO関連）.

プラットフォームデータ¶

最後に、プラットフォームデータを使用してGPIOをデバイスおよび機能にバインドできます。これを実行したいボードファイルは、次のヘッダーを含める必要があります：

#include <linux/gpio/machine.h>

GPIOは、gpiod_lookup構造体のインスタンスを含む検索テーブルによってマッピングされます。このようなマッピングを宣言するのに役立つ2つのマクロが定義されています:

GPIO_LOOKUP(key, chip_hwnum, con_id, flags)
GPIO_LOOKUP_IDX(key, chip_hwnum, con_id, idx, flags)

オプションを指定する必要があります。形式は以下の通りです：

  • keyは、GPIOを提供するgpiod_chipインスタンスのラベルか、GPIOライン名のいずれかです

  • chip_hwnumは、チップ内のGPIOのハードウェア番号で、keyがGPIOライン名を示す場合はU16_MAXを使用します

  • con_idは、デバイスの観点からのGPIO機能名です。これは

    NULLの場合、任意の機能にマッチします

  • idxは、機能内のGPIOのインデックスです

  • flagsは、以下のプロパティを指定するために定義されています:

    • GPIO_ACTIVE_HIGH - GPIOラインはアクティブハイで設定されています

    • GPIO_ACTIVE_LOW - GPIOラインはアクティブロウで設定されています

    • GPIO_OPEN_DRAIN - GPIOラインはオープンドレインで設定されています

    • GPIO_OPEN_SOURCE - GPIOラインはオープンソースで設定されています

    • GPIO_PERSISTENT - GPIOラインは、

      スリープ/再起動中に永続的で、値を保持します

    • GPIO_TRANSITORY - GPIOラインは一時的で、スリープ/再起動中に電気的状態を失う可能性があります

      今後、これらのフラグはより多くのプロパティをサポートするために拡張される可能性があります

GPIOライン名はグローバルに一意であるとは限りませんので、最初に見つかったマッチが使用されます

注意:

  1. GPIO_LOOKUP()はidx=0の場合にGPIO_LOOKUP_IDX()のショートカットです

  2. lookupテーブルは次のようになります。空のエントリで終端を示します。テーブルの‘dev_id’フィールドは、これらのGPIOを使用するデバイスの識別子です。NULLの場合、NULLデバイスに対する呼び出しにマッチします

そして、テーブルはボードコードによって次のように追加されます: gpiod_get() ‘dev_id’フィールドのテーブルは、これらのGPIOを使用するデバイスの識別子です。NULLの場合、NULLデバイスに対する呼び出しにマッチします

struct gpiod_lookup_table gpios_table = {
        .dev_id = "foo.0",
        .table = {
                GPIO_LOOKUP_IDX("gpio.0", 15, "led", 0, GPIO_ACTIVE_HIGH),
                GPIO_LOOKUP_IDX("gpio.0", 16, "led", 1, GPIO_ACTIVE_HIGH),
                GPIO_LOOKUP_IDX("gpio.0", 17, "led", 2, GPIO_ACTIVE_HIGH),
                GPIO_LOOKUP("gpio.0", 1, "power", GPIO_ACTIVE_LOW),
                { },
        },
};

そして、ボードコードにテーブルを追加する方法は次の通りです:

gpiod_add_lookup_table(&gpios_table);

「foo.0」を制御するドライバーは、次のようになります:

struct gpio_desc *red, *green, *blue, *power;

red = gpiod_get_index(dev, "led", 0, GPIOD_OUT_HIGH);
green = gpiod_get_index(dev, "led", 1, GPIOD_OUT_HIGH);
blue = gpiod_get_index(dev, "led", 2, GPIOD_OUT_HIGH);

power = gpiod_get(dev, "power", GPIOD_OUT_HIGH);

「led」GPIOはアクティブハイでマッピングされているため、この例では信号を1に切り替えてLEDを有効にします。一方、「power」GPIOはアクティブロウでマッピングされており、このコードの後は信号が0になります。従来の整数GPIOインターフェースとは異なり、アクティブロウのプロパティはマッピング時に処理されるため、GPIO消費者には透明です

新しいディスクリプター指向インターフェースを操作するための関数セット、例えば gpiod_set_value() が利用可能です

プラットフォームデータを使用するボードは、GPIOhogテーブルを定義することでGPIOラインを占有できます

struct gpiod_hog gpio_hog_table[] = {
        GPIO_HOG("gpio.0", 10, "foo", GPIO_ACTIVE_LOW, GPIOD_OUT_HIGH),
        { }
};

そして、ボードコードにテーブルを追加する方法は次の通りです:

gpiod_add_hogs(gpio_hog_table);

gpiochipが作成されるか、チップが以前に作成されていた場合にhogテーブルが登録されるタイミングでラインが占有されます

ピンの配列¶

関数に属するピンを1つずつ要求するだけでなく、デバイスは関数に割り当てられたピンの配列を要求することもできます。これらのピンがデバイスにどのようにマッピングされているかによって、この配列が高速ビットマップ処理に適切かどうかが決まります。適切な場合、呼び出し元とGPIOチップの対応する.get/set_multiple()コールバック間でビットマップが直接get/set配列関数経由で渡されます。

高速ビットマップ処理に適切なためには、配列は以下の要件を満たす必要があります：

  • 配列の0番目のメンバーのピンハードウェア番号も0でなければなりません、

  • 0番目のメンバーと同じチップに属する連続する配列メンバーのピンハードウェア番号も、それぞれの配列インデックスと一致しなければなりません。

そうでない場合、高速ビットマップ処理パスは使用されません。これは、同じチップに属するがハードウェア順序でない連続するピンが別々に処理されるのを防ぐためです。

配列が高速ビットマップ処理パスに適用される場合、0番目のメンバーとは異なるチップに属するピン、およびハードウェアピン番号とインデックスが一致しないピンは、入力および出力の高速パスから除外されます。また、オープンドレインおよびオープンソースピンは高速ビットマップ出力処理から除外されます。

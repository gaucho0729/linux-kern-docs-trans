LIBNVDIMM: 非揮発性デバイス¶

libnvdimm - カーネル / libndctl - ユーザースペースの補助ライブラリ

linux-nvdimm@lists.01.org

バージョン13

用語集¶

PMEM:

システム物理アドレス範囲で、書き込みが永続的です。PMEMで構成されるブロックデバイスはDAXを実行可能です。PMEMアドレス範囲は複数のDIMMのインタレーブをまたがる場合があります。

BLK:

DIMMが提供する1つ以上のプログラマブルメモリマップアペルタの集合です。この間接性はインタレーブのパフォーマンスメリットを排除しますが、DIMM限定の失敗モードを可能にします。

DPA:

DIMM物理アドレスはDIMM相対オフセットです。システムに1つのDIMMがある場合、システム物理アドレス:DPAは1:1の関係になります。DIMMを追加すると、メモリコントローラーのインタレーブをデコードしてシステム物理アドレスに関連するDPAを特定する必要があります。BLK容量は常に単一DIMMのDPA範囲と1:1の関係を持ちます。

DAX:

ファイルシステム拡張機能で、ページキャッシュとブロックレイヤーをバイパスして、PMEMブロックデバイスからプロセスアドレス空間に直接マッピングするためのものです。

DSM:

デバイス固有メソッド: ACPIメソッドで特定のデバイスを制御します（この場合、ファームウェアを制御します）。

DCR:

ACPI 6セクション5.2.25.5で定義されたNVDIMM制御領域構造体です。これは特定のDIMMのベンダーアイデンティティ、デバイスID、インターフェースフォーマットを定義します。

BTT:

ブロック翻訳テーブル: 持続可能メモリはバイトアドレス可能です。既存のソフトウェアは、電源遮断時の書き込みの原子性が少なくとも1セクタ（512バイト）であることを期待しています。BTTは、PMEM/BLKブロックデバイスドライバを前面にし、任意の原子セクタサイズを提示するための間接テーブルで、原子的な更新セマンティクスを持ちます。

LABEL:

DIMMデバイスに保存されたメタデータで、PMEMとBLK間のストレージを分割し、識別（永続的に名前を付ける）します。また、BLKストレージをBLKパーティションごとに異なるパラメータを持つBTTにホストします。従来のパーティションテーブル（GPT/MBR）はBLKまたはPMEMデバイスの上にレイヤー化されています。

概要¶

LIBNVDIMMサブシステムは、PMEM、BLK、およびNVDIMMデバイスの3種類のサポートを提供します。これらは、PMEMモードとBLKモードの両方を同時にサポートできるデバイスです。この3つの動作モードは、ACPI 6における「NVDIMMファームウェアインターフェーステーブル」（NFIT）で記述されています。LIBNVDIMMの実装は汎用的であり、NFIT以前のプラットフォームにも対応していますが、ACPI 6で定義されたNVDIMMリソースのサポートに必要な機能のスーパーセットに基づいて設計されています。カーネルの実装の大部分は、PMEM経由でアクセス可能なDPA（Direct Physical Address）がBLK経由でアクセス可能なDPAとアリアス（同一のアドレス範囲）になっている場合の処理を担当しています。その場合、1つのモードごとにDPAを排他的にアクセスするためにLABELが必要です。

LIBNVDIMM PMEMおよびBLK¶

NFITが導入される前は、非揮発性メモリはシステムにさまざまな非公式な方法で記述されていました。通常は最低限の情報しか提供されず、システム電源喪失後に書き込みが永続的なシステム物理アドレス範囲のみが提供されていました。現在では、NFIT仕様によりPMEMだけでなく、BLKやプラットフォーム間メッセージ送信のエントリポイントも標準化され、制御と設定が可能になりました。

NVDIMMアクセス方法（PMEM、BLK）ごとにLIBNVDIMMはブロックデバイスドライバを提供します:

  1. PMEM（nd_pmem.ko）：システム物理アドレス範囲を駆動します。この範囲はシステムメモリ内で連続しており、複数のDIMMにハードウェアメモリコントローラーによってストライピング（分散）されることがあります。ストライピングされている場合、プラットフォームは参加しているDIMMの詳細をオプションで提供することがあります。

    LIBNVDIMMは、BLKアクセスとアリアスするシステム物理アドレス範囲をND_NAMESPACE_PMEM範囲として、アリアスしない範囲をND_NAMESPACE_IO範囲として記述しますが、nd_pmemドライバにはこの区別はありません。異なるデバイスタイプは実装の詳細であり、ユーザー空間は「特定のDIMMからのアドレス範囲のみをインターフェースする」などのポリシーを実装するために利用できます。注意すべきは、アリアスが存在し、DIMMにラベルがなければ、ユーザー空間が少なくともPMEM範囲にDPAを1回割り当てを行う必要があるため、ブロックデバイスはデフォルトで作成されないことです。一方、ND_NAMESPACE_IO範囲は登録後、すぐにnd_pmemに接続できます。

  2. BLK (nd_blk.ko): このドライバは、プラットフォームで定義されたアペラチャを用いてI/Oを実行します。アペラチャのセットは1つのDIMMにアクセスします。複数のウィンドウ（アペラチャ）は複数の同時アクセスを許可し、タグ付きコマンドキューイングと同様の動作をします。これにより、異なるスレッドや異なるCPUが使用する可能性があります。

    NFIT仕様ではBLKアペラチャの標準形式が定義されていますが、仕様はベンダー固有のレイアウトも許容しており、NFIT以外のBLK実装ではBLK I/Oに別の設計が採用される可能性があります。このため、「nd_blk」はプラットフォーム固有のコードに逆参照してI/Oを実行します。

    このような実装の一つは「ドライバライターズガイド」および「DSMインターフェース例」に定義されています。

なぜBLKなのか？¶

PMEMはNVDIMMストレージに直接バイトアドレス可能なCPUロード/ストアアクセスを提供しますが、システムRAS（回復、可用性、サービス性）モデルとしては最適ではありません。破損したシステム物理アドレスへのアクセスはCPU例外を発生させますが、BLKアペラチャ経由での破損アドレスアクセスは、そのブロックウィンドウがレジスタにエラー状態を報告します。後者はホストバスアダプター接続ディスクが提供する標準的なエラーモデルにより近いです。

また、管理者がメモリを交換する必要がある場合、DIMMモジュール境界でシステムをサービスするのはより簡単です。PMEMでは複数のDIMMに不透明なハードウェア固有の方法でデータがインターリーブされているため、比較対象になります。

PMEM vs BLK¶

BLKアペラチャはこれらのRAS問題を解決しますが、その存在はNDサブシステムの複雑さの主な要因となっています。PMEMとBLKがDPA領域でアリアス化されるため、実装が複雑になります。任意のDIMMのDPA範囲は、1つ以上のシステム物理アドレスのインターリーブDIMMセットに貢献する可能性があります。 および また、BLKアペラチャ経由で全体をアクセスすることも可能です。システム物理アドレス経由でDPAにアクセスしながら、同時にBLKアペラチャ経由で同じDPAにアクセスすると未定義の結果になります。このため、この二重インターフェース構成を持つDIMMには、LABELを保存/取得するDSM機能が含まれています。LABELはDPA領域をシステム物理アドレスとBLKアペラチャアクセス可能な領域に分離します。簡潔さのため、DIMMは所属するインターリーブセットごとにPMEM「領域」を1つずつ許可されます。残りのDPA領域は任意の数のBLKデバイスに不連続な領域として分割できます。

BLK-REGIONs, PMEM-REGIONs, Atomic Sectors, and DAX¶

複数のBLK名前空間を1つのREGIONごとに許可する理由は限られており、その1つは各BLK名前空間が一意のアトミックセクタサイズを持つBTT（Block Translation Table）で構成できるためです。PMEMデバイスはBTTをホストできますが、LABEL仕様ではPMEM名前空間のセクタサイズを指定する機能は提供されていません。

これはPMEMの主な使用モデルがDAX経由であるという期待に基づいています。BTTはDAXと互換性がありません。ただし、アプリケーションやファイルシステムが依然としてアトミックセクタ更新の保証を必要とする場合、PMEMデバイスまたはパーティションにBTTを登録できます。参照：LIBNVDIMM/NDCTL: Block Translation Table "btt"

NVDIMMプラットフォームの例¶

このドキュメントの残りの部分では、例のsysfsレイアウトを参照するために以下のダイアグラムが使用されます：

                             (a)               (b)           DIMM   BLK-REGION
          +-------------------+--------+--------+--------+
+------+  |       pm0.0       | blk2.0 | pm1.0  | blk2.1 |    0      region2
| imc0 +--+- - - region0- - - +--------+        +--------+
+--+---+  |       pm0.0       | blk3.0 | pm1.0  | blk3.1 |    1      region3
   |      +-------------------+--------v        v--------+
+--+---+                               |                 |
| cpu0 |                                     region1
+--+---+                               |                 |
   |      +----------------------------^        ^--------+
+--+---+  |           blk4.0           | pm1.0  | blk4.0 |    2      region4
| imc1 +--+----------------------------|        +--------+
+------+  |           blk5.0           | pm1.0  | blk5.0 |    3      region5
          +----------------------------+--------+--------+

このプラットフォームでは1つのソケットに4つのDIMMと2つのメモリコントローラーがあります。DPA領域への各一意なインターフェース（BLKまたはPMEM）は、動的に割り当てられたID（REGION0 - REGION5）を持つリージョンデバイスで識別されます。

  1. DIMM0とDIMM1の最初の部分はREGION0としてインターリーブされています。REGION0-SPA範囲内でユーザー指定の名前"pm0.0"で1つのPMEM名前空間が作成され、DIMM0とDIMM1の大部分をカバーします。そのインターリーブされたシステム物理アドレス範囲の一部は、DPAオフセット(a)から各DIMMにアクセス可能なBLK-aperture領域として再利用され、その領域内でREGION2とREGION3から2つのBLK-aperture "名前空間"が作成されます。"blk2.0"と"blk3.0"はユーザーが指定可能な任意の名前をLABELで設定できます。

  2. DIMM0とDIMM1の最後の部分には、REGION1としてインターリーブされたシステム物理アドレス範囲があり、この範囲はDIMM0とDIMM1だけでなくDIMM2とDIMM3もカバーします。REGION1の一部は"pm1.0"という名前でPMEM名前空間として割り当てられ、残りは4つのBLK-aperture名前空間（インターリーブセット内の各DIMMごと）として再利用されます。"blk2.1"、"blk3.1"、"blk4.0"、"blk5.0"がその例です。

  3. DIMM2とDIMM3のREGION1インターリーブされたシステム物理アドレス範囲に含まれない部分（つまりDPAオフセット(b)を超える領域）も"blk4.0"と"blk5.0"名前空間に含まれます。注意：この例ではBLK-aperture名前空間がDPA空間で連続する必要がないことが示されています。

このバスは、nfit_test.koモジュールをtools/testing/nvdimmからロードした際、カーネルが/sys/devices/platform/nfit_test.0で提供します。これによりLIBNVDIMMだけでなく、acpi_nfit.koドライバもテストできます。

LIBNVDIMM/LIBNDCTL: バス¶

バスはNFITと1対1の関係を持ちます。現在のACPIベースのシステムにおける期待される仕様は、プラットフォームグローバルに1つのNFITしか存在しないことです。ただし、複数のNFITを登録することは非常に簡単で、仕様はこれを禁止していません。インフラストラクチャは複数のバスをサポートしており、ユニットテストでは複数のNFIT構成をテストするためにこの機能を使用しています。

LIBNVDIMM/LIBNDCTL: DIMM (NMEM)¶

DIMMデバイスはハードウェアにコマンドを送信するためのキャラクターデバイスを提供し、LABELのコンテナとして機能します。DIMMがNFITで定義されている場合、NFIT固有の情報を追加するためのオプションの'nfit'属性サブディレクトリが利用可能です。

LIBNDCTL: DIMMの列挙例¶

この例では、NFITで定義されたDIMMを前提としており、識別には「nfit_handle」という32ビットの値を使用します。ここで:

  • ビット3:0 メモリチャネル内のDIMM番号

  • ビット7:4 メモリチャネル番号

  • ビット11:8 メモリコントローラーID

  • ビット15:12 スロットID（ノードコントローラーが存在する場合のノードコントローラーのスコープ内）

  • ビット27:16 ノードコントローラーID

  • ビット31:28 予約済み

static struct ndctl_dimm *get_dimm_by_handle(struct ndctl_bus *bus,
       unsigned int handle)
{
        struct ndctl_dimm *dimm;

        ndctl_dimm_foreach(bus, dimm)
                if (ndctl_dimm_get_handle(dimm) == handle)
                        return dimm;

        return NULL;
}

#define DIMM_HANDLE(n, s, i, c, d) \
        (((n & 0xfff) << 16) | ((s & 0xf) << 12) | ((i & 0xf) << 8) \
         | ((c & 0xf) << 4) | (d & 0xf))

dimm = get_dimm_by_handle(bus, DIMM_HANDLE(0, 0, 0, 0, 0));

LIBNVDIMM/LIBNDCTL: レギオン¶

PMEM範囲またはBLKアピターレットセットごとに一般的なREGIONデバイスが登録されます。例では6つのレギオンがあります：「nfit_test.0」バスには2つのPMEMと4つのBLKアピターレットセットがあります。レギオンの主な役割は「マッピング」を含むコンテナとしての役割を果たすことであり、マッピングは<DIMM、DPA開始オフセット、長さ>の組み合わせです。

LIBNVDIMMは、これらのREGIONデバイス用に組み込みドライバを提供しています。このドライバは、すべてのリージョンにおけるアリアスDPAマッピングを調整し、LABELが存在する場合はそれを解析した後、nd_pmemまたはnd_blkデバイスドライバが消費できるよう、解決済み/排他的なDPA境界を持つNAMESPACEデバイスを生成します。

「mapping」「interleave_ways」「size」などの汎用的な属性に加えて、REGIONデバイスはいくつかの便利な属性を公開します。「nstype」はこのリージョンが生成するnamespaceデバイスの整数型を示し、「devtype」はudevが「add」イベント時に保存したDEVTYPE変数を再現し、「modalias」はudevが「add」イベント時に保存したMODALIAS変数を再現します。最後に、リージョンがSPAで定義されている場合に限り、オプションの「spa_index」が提供されます。

LIBNDCTL: リージョンの列挙例¶

PMEM用の「spa_index」（interleaveセットID）やBLK用の「nfit_handle」（DIMM ID）などのNFIT一意データに基づくサンプルリージョン取得ルーチン:

static struct ndctl_region *get_pmem_region_by_spa_index(struct ndctl_bus *bus,
                unsigned int spa_index)
{
        struct ndctl_region *region;

        ndctl_region_foreach(bus, region) {
                if (ndctl_region_get_type(region) != ND_DEVICE_REGION_PMEM)
                        continue;
                if (ndctl_region_get_spa_index(region) == spa_index)
                        return region;
        }
        return NULL;
}

static struct ndctl_region *get_blk_region_by_dimm_handle(struct ndctl_bus *bus,
                unsigned int handle)
{
        struct ndctl_region *region;

        ndctl_region_foreach(bus, region) {
                struct ndctl_mapping *map;

                if (ndctl_region_get_type(region) != ND_DEVICE_REGION_BLOCK)
                        continue;
                ndctl_mapping_foreach(region, map) {
                        struct ndctl_dimm *dimm = ndctl_mapping_get_dimm(map);

                        if (ndctl_dimm_get_handle(dimm) == handle)
                                return region;
                }
        }
        return NULL;
}

なぜリージョンのタイプをリージョン名にエンコードしないのか？¶

一見すると、NFITがPMEMとBLKインターフェースタイプのみを定義しているため、REGIONデバイスの名前をそれらのタイプ名から派生した名前にするべきだと考えられます。しかし、NDサブシステムは明示的にリージョン名を汎用的とし、ユーザー空間が常にリージョン属性を考慮する必要があるため、以下の4つの理由でリージョン名にタイプをエンコードしないのです:

  1. すでにリージョンと「namespace」タイプは2種類以上存在しています。PMEMには2つのサブタイプがあります。前述したように、PMEMにはDIMMデバイスが判明しているPMEMと匿名PMEMがあります。BLKリージョンではNFIT仕様がすでにベンダー固有の実装を予期しています。リージョンが含む内容の正確な区別はリージョン属性ではなく、リージョン名やリージョンdevtypeではありません。

  2. 子namespaceを持たないリージョンは可能配置です。たとえば、NFITはBLKアプライアンスと対応しないDCRの公開を許可しており、これはDIMMがコントロール/設定メッセージのみを受け付けることができ、孫ブロックデバイスを通じたI/Oは行えないDIMMを表します。この「タイプ」は属性（'mappings' == 0）で宣伝され、名前はあまり意味を成しません。

  3. 今後、第三の主要なインターフェースタイプが登場する可能性はありますか？ベンダー固有の実装を除けば、BLKとPMEMを超えた第三のインターフェースタイプの存在を想像するのは難しくありません。デバイス階層のREGIONレベルに汎用的な名前を付けることで、古いユーザースペースの実装も新しいカーネルが宣伝するREGIONタイプを理解できます。ユーザースペースは「マッピング」「サイズ」などの汎用的な領域属性や、「namespace」と名付けられた予期される子デバイスに常に依存できます。この汎用的なデバイスモデル階層形式により、LIBNVDIMMとLIBNDCTLの実装がより統一的で将来性のあるものになります。

  4. 領域の主なタイプを特定するためには、デバイス名よりもより信頼性の高いメカニズムがあります。次のセクション「領域の主なタイプをどのように特定するか」を参照してください。

領域の主なタイプをどのように特定するか¶

「libndctl」を使用することを推奨する一般的なアドバイスや、カーネルヘッダー（/usr/include/linux/ndctl.h）を確認して「nstype」整数属性をデコードする以外にも、以下のようなオプションがあります。

1. モジュールアリアスの検索¶

領域/namespaceデバイスタイプの区別を行う目的は、どのLIBNVDIMM namespaceにブロックデバイスドライバーがアタッチするかを決定することです。このため、modaliasを用いて結果のモジュールを検索できます。この方法は、今後ベンダー固有ドライバーが登場しても信頼性があります。ベンダー固有の実装が標準のnd_blkドライバーを置き換える場合でも、LIBNVDIMMの他の部分への影響は最小限に抑えられます。

実際、ベンダーはnd_region以外のベンダー固有の領域ドライバーをもつ場合もあります。たとえば、ベンダーが独自のLABEL形式を定義した場合、そのLABELを解析してnamespaceを生成するための独自の領域ドライバーが必要です。モジュール解決の出力は、領域名や領域デバイスタイプよりも正確です。

2. udev¶

カーネルの「devtype」はudevデータベースに登録されています：

# udevadm info --path=/devices/platform/nfit_test.0/ndbus0/region0
P: /devices/platform/nfit_test.0/ndbus0/region0
E: DEVPATH=/devices/platform/nfit_test.0/ndbus0/region0
E: DEVTYPE=nd_pmem
E: MODALIAS=nd:t2
E: SUBSYSTEM=nd

# udevadm info --path=/devices/platform/nfit_test.0/ndbus0/region4
P: /devices/platform/nfit_test.0/ndbus0/region4
E: DEVPATH=/devices/platform/nfit_test.0/ndbus0/region4
E: DEVTYPE=nd_blk
E: MODALIAS=nd:t3
E: SUBSYSTEM=nd

…そして、領域属性として利用できますが、注意点として「devtype」はサブタイプの変化を示しません。スクリプトは他の属性を理解する必要があります。

3. タイプ固有の属性¶

現在のところ、BLKアプライド領域は「nfit/spa_index」属性を持たず、非NFIT PMEM領域も同様です。マッピング値が0のBLK領域は、前述の通りI/Oを許可しないDIMMです。マッピング値が0のPMEM領域は単純なシステム物理アドレス範囲です。

LIBNVDIMM/LIBNDCTL: Namespace¶

リージョンは、DPAのアリアス解決とLABEL指定境界を解決した後、1つ以上の「名前空間」デバイスを表面化します。現在、「名前空間」デバイスの到着は、nd_blkまたはnd_pmemドライバがロードされ、ディスク/ブロックデバイスを登録するようにトリガーされます。

LIBNDCTL: 名前空間列挙例¶

名前空間は、親リージョンに対してインデックス付けされます。以下の例をご覧ください。これらのインデックスは、起動ごとにほぼ静的なままですが、サブシステムはこの点について保証を提供しません。静的な名前空間識別子が必要な場合は、'uuid'属性を使用してください。

static struct ndctl_namespace
*get_namespace_by_id(struct ndctl_region *region, unsigned int id)
{
        struct ndctl_namespace *ndns;

        ndctl_namespace_foreach(region, ndns)
                if (ndctl_namespace_get_id(ndns) == id)
                        return ndns;

        return NULL;
}

LIBNDCTL: 名前空間作成例¶

アイドル状態の名前空間は、リージョンが新しい名前空間を作成するために十分な容量を持っている場合、カーネルによって自動的に作成されます。名前空間のインスタンス化には、アイドル状態の名前空間を検索し、設定を行う必要があります。名前空間属性の設定順序は基本的に自由ですが、'uuid'は'size'よりも前に設定する必要があります。これにより、カーネルが静的な識別子をもとにDPA割当を内部的に追跡できるようになります。

static int configure_namespace(struct ndctl_region *region,
                struct ndctl_namespace *ndns,
                struct namespace_parameters *parameters)
{
        char devname[50];

        snprintf(devname, sizeof(devname), "namespace%d.%d",
                        ndctl_region_get_id(region), paramaters->id);

        ndctl_namespace_set_alt_name(ndns, devname);
        /* 'uuid' must be set prior to setting size! */
        ndctl_namespace_set_uuid(ndns, paramaters->uuid);
        ndctl_namespace_set_size(ndns, paramaters->size);
        /* unlike pmem namespaces, blk namespaces have a sector size */
        if (parameters->lbasize)
                ndctl_namespace_set_sector_size(ndns, parameters->lbasize);
        ndctl_namespace_enable(ndns);
}

なぜ「名前空間」という用語を使うのか？¶

  1. なぜ「ボリューム」ではないのか？「ボリューム」はND（libnvdimmサブシステム）をデバイスマッパーやボリュームマネージャーと混同するリスクがありました。

  2. この用語は、NVMEコントローラー内で作成できるサブデバイスを説明するために起源を持ちます（nvme仕様: https://www.nvmexpress.org/specifications/)、そしてNFIT名前空間はNVME名前空間の機能と設定可能性を並行して表現することを目的としています。

LIBNVDIMM/LIBNDCTL: ブロック翻訳テーブル「btt」¶

BTT（設計ドキュメント: https://pmem.io/2014/09/23/btt.html)は、PMEMまたはBLK名前空間によって生成されたブロックデバイス全体またはそのパーティションを前面に据えるスタックされたブロックデバイスドライバーです。

LIBNVDIMM: bttレイアウト¶

すべてのリージョンは、少なくとも1つのBTTデバイス（種子デバイス）から始まります。これを有効化するには、「名前空間」、「uuid」、「sector_size」属性を設定し、リージョンタイプに応じてデバイスをnd_pmemまたはnd_blkドライバにバインドします。

|-- delete
|-- devtype
|-- modalias
|-- numa_node
|-- sector_size
|-- subsystem -> ../../../../../bus/nd
|-- uevent
`-- uuid

LIBNDCTL: btt作成例¶

名前空間と同様に、リージョンごとにアイドル状態の BTT デバイスが自動的に作成されます。この「シード」BTT デバイスが設定され有効化されるたびに新しいシードが作成されます。BTT の構成を作成するには、アイドル状態の BTT を見つけて PMEM または BLK 名前空間を消費するように割り当てる 2 つのステップが必要です：

static struct ndctl_btt *get_idle_btt(struct ndctl_region *region)
{
        struct ndctl_btt *btt;

        ndctl_btt_foreach(region, btt)
                if (!ndctl_btt_is_enabled(btt)
                                && !ndctl_btt_is_configured(btt))
                        return btt;

        return NULL;
}

static int configure_btt(struct ndctl_region *region,
                struct btt_parameters *parameters)
{
        btt = get_idle_btt(region);

        ndctl_btt_set_uuid(btt, parameters->uuid);
        ndctl_btt_set_sector_size(btt, parameters->sector_size);
        ndctl_btt_set_namespace(btt, parameters->ndns);
        /* turn off raw mode device */
        ndctl_namespace_disable(parameters->ndns);
        /* turn on btt access */
        ndctl_btt_enable(btt);
}

インスタンス化されると、該当のリージョンの下に新しい非アクティブな BTT シード デバイスが表示されます。

BTT から「名前空間」が削除されると、その BTT デバイスのインスタンスが削除されるか、またはデフォルト値に戻されます。この削除はデバイスモデルレベルでのみ行われます。BTT を破壊するには「情報ブロック」を破壊する必要があります。注意点として、BTT を破壊するにはメディアがrawモードで書き込まれる必要があります。デフォルトでは、カーネルが BTT の存在を自動検出し、rawモードを無効にします。この自動検出動作は、ndctl_namespace_set_raw_mode() API を使って名前空間の raw モードを有効にすることで抑制できます。

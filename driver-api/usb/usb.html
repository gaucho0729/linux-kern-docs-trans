Linux-USBホスト側API¶

LinuxにおけるUSBの概要¶

ユニバーサル・シリアル・バス（USB）は、PCやワークステーションなどのホスト機器を複数の外設機器に接続するためのインターフェースです。USBはツリー構造を採用しており、ホストがルート（システムのマスター）、ハブが内部ノード、外設機器が葉（スレーブ）となります。現代のPCは複数のUSBデバイスツリーをサポートしており、通常はいくつかのUSB 3.0（5 GBit/s）やUSB 3.1（10 GBit/s）のバスに加え、一部の遺産技術であるUSB 2.0（480 MBit/s）のバスもサポートしています。

このマスター/スレーブの非対称性は、使いやすさの観点から設計されています。物理的にアップストリームとダウンストリームを間違えることは不可能ですし、タイプCプラグ（または外設機器に組み込まれている）では問題になりません。また、ホストソフトウェアは分散型の自動設定を扱う必要がなく、事前に指定されたマスターノードがすべての設定を管理しています。

カーネル開発者は2.2シリーズのカーネル初期からUSBサポートを追加し、それ以降も継続的に開発を進めています。各世代のUSBへのサポートに加え、さまざまなホストコントローラーがサポートされるようになり、外設機器用のドライバーが追加され、レイテンシー測定や電力管理の改善といった高度な機能も導入されました。

LinuxはUSBデバイス内でもホスト機器上でも動作可能です。しかし、それらの外設機器内で動作するUSBドライバーはホスト内でのドライバーとは異なる機能を担うため、別名が与えられています： gadgetドライバー。このドキュメントではgadgetドライバーは扱いません。

USB ホスト側APIモデル¶

USBデバイスのホスト側ドライバーは「usbcore」APIと通信します。このAPIは2種類あります。1つは 汎用的 なドライバー（ドライバーフレームワークを通じて公開）用に設計されており、もう1つは コアの一部として実装されたドライバー用です。このようなコアドライバーには、ツリー構造のUSBデバイスを管理する ハブ ドライバーと、個々のバスを制御するさまざまな種類の ホストコントローラードライバーが含まれます。

USBドライバーが見られるデバイスモデルは相対的に複雑です。

  • USBは制御、バースト、割込み、等時の4種類のデータ転送をサポートしています。そのうち2種類（制御とバースト）は利用可能な帯域幅を即座に使用しますが、残りの2種類（割込みと等時）は予約された帯域幅を確保するためスケジュールされます。

  • デバイスの説明モデルには、デバイスごとに1つまたは複数の「構成」が含まれており、一度に有効なのはそのうちの1つです。デバイスは、最大速度よりも低い速度でも動作可能であり、最低限の動作速度を示すBOSディスクリプタを提供することが求められます。

  • USB 3.0の設定では、1つまたは複数の「機能（function）」が含まれており、これらは共通の機能を提供し、電源管理の目的でグループ化されています。

  • 設定または機能は、1つまたは複数の「インターフェース（interface）」を持ち、それぞれが「代替設定（alternate setting）」を持つ場合があります。インターフェースはUSBの「クラス（Class）」仕様によって標準化される場合もありますが、ベンダーまたはデバイス固有のものであることもあります。

    USBデバイスドライバーはインターフェースにバインドします。デバイスではなくインターフェースにバインドするので、「インターフェースドライバー」と考えてもよいでしょう。ただし、多くのデバイスではこの区別は重要ではありません。 ほとんどのUSBデバイスは単純で、1つの機能、1つの設定、1つのインターフェース、1つの代替設定しか持ちません。

  • インターフェースは1つまたは複数の「エンドポイント（endpoint）」を持ち、それぞれが「バースト出力」や「割込み入力」などのデータ転送の種類と方向をサポートします。全体の設定では、各方向に対して最大16つのエンドポイントが割り当てられ、必要に応じてすべてのインターフェース間で分配されます。

  • USBでのデータ転送はパケット化されています。各エンドポイントには最大パケットサイズが設定されています。ドライバーは、例としてバースト転送の終端を「短いパケット（ゼロ長さを含む）」で示すなどの慣例を理解する必要があります。

  • LinuxのUSB APIは制御メッセージやバーストメッセージの同期呼び出しをサポートしています。また、すべてのデータ転送に対して非同期呼び出しをサポートしており、これには「URB（USB Request Block）」と呼ばれるリクエスト構造を使用します。

このように、デバイスドライバーに公開されるUSBコアAPIは非常に幅広い範囲をカバーしています。USB 3.0仕様書を参照することをお勧めします。これはwww.usb.orgから無料でオンラインで入手可能です。また、クラスまたはデバイス仕様も参照する必要があります。

実際にハードウェア（レジスタの読み書き、IRQの処理など）に触れるホスト側ドライバーはHCD（Host Controller Driver）です。理論上、すべてのHCDは同じAPIを通じて同じ機能を提供します。実際にはこのことがより真実に近づいてきていますが、特にレアなコントローラーでのエラー処理ではまだ違いがあります。異なるコントローラーは同じエラーの側面を報告しない場合があり、エラーからの回復（ソフトウェアによるものも含む、URBのアンリーフィングなど）はまだ完全に一貫していません。デバイスドライバーの作成者は、それぞれのホストコントローラードライバーで切断テスト（デバイスがアクティブな状態で）を行うべきです。これにより、ドライバー自身のバグを確認し、HCD固有の動作に依存していないことを確認できます。

USB標準タイプ¶

In <linux/usb/ch9.h> USB仕様書の第9章にUSBデータ型が定義されています。これらのデータ型はUSB全体で使用され、このホスト側APIやギャッジAPI、USBキャラクターデバイス、デバッグfsインターフェースなどのAPIにも含まれています。

ホスト側データ型とマクロ¶

ホスト側APIはドライバに対していくつかのレイヤーを公開しており、これらは必要度によって異なります。これらはホスト側ドライバおよびデバイスのライフサイクルモデルをサポートし、usbcoreを介してHCDにバッファを渡す機能も提供します。

メンバ

altsetting

インターフェース構造体の配列、選択可能な代替設定ごとに1つずつ。それぞれにエンドポイント構成が含まれます。順序は特に指定ありません。

cur_altsetting

現在の代替設定

num_altsetting

定義された代替設定の数

intf_assoc

インターフェース関連記述子

minor

このインターフェースに割り当てられたマイノル番号（このインターフェースがUSBメジャーナンバーを使用するドライバにバインドされている場合）。このインターフェースがUSBメジャーナンバーを使用しない場合、このフィールドは無視されます。ドライバはUSBコアからマイノル番号を割り当てられた後、probe()関数内でこの値を設定する必要があります。 usb_register_dev().

condition

インターフェースのバインディング状態: バインドされていない、バインディング中（probe()中）、ドライバにバインド済み、またはアンバインド中（disconnect()中）

sysfs_files_created

sysfs属性が存在する

ep_devs_created

エンドポイント子仮デバイスが存在する

unregistering

インターフェースがアンレジストレーション中であるときに設定されるフラグ

needs_remote_wakeup

ドライバがオートスリープ中にリモートウェイクアップ機能を必要とするときに設定されるフラグ

needs_altsetting0

代替設定0に対するset-interfaceリクエストが遅延されたときに設定されるフラグ

needs_binding

リセットやサポートしないスリープ操作後にドライバを再プローブまたはアンバインドする必要があるときに設定されるフラグ

resetting_device

USBコアがデバイスをリセットしたため、現在の代替設定は0; リセット後に帯域幅割当が必要です。

authorized

これは、デバイス全体ではなく、個々のインターフェースを(解除して)認証する機能を提供します。これはデバイス認証とは対照的です。

dev

ドライバモデルにおけるこのデバイスのビュー

usb_dev

インターフェースがUSB majorにバインドされている場合、これはそのデバイスのsysfs表現を指します。

reset_ws

アトミックコンテキストからリセットをスケジュールするために使用されます。

説明

USBデバイスドライバーは物理デバイスにインターフェースにアタッチします。各インターフェースは、オーディオストリームをスピーカーに送信するか、ボリュームコントロールの変化を報告するなどの単一の高レベル機能をカプセル化します。多くのUSBデバイスは1つのインターフェースしか持ちません。インターフェースのエンドポイントと通信するプロトコルは、USBの「クラス」仕様で定義されるか、製品のベンダーによって定義されます。すべてのインターフェースには制御エンドポイントが含まれますが、インターフェースのディスクリプタにはリストされません。

インターフェースにバインドされたドライバーは、この構造体のdevメンバに対してdev_get_drvdata()などの標準ドライバーモデルコールを使用できます。

各インターフェースは代替設定を持つ場合があります。デバイスの初期設定ではaltsetting 0が設定されますが、デバイスドライバーはこの設定を変更できます。 usb_set_interface()代替設定は、周期的なエンドポイントの使用を制御するためによく使用されます。例えば、異なるエンドポイントが異なるUSB帯域幅を予約するようにする場合があります。すべての標準準拠USBデバイスが、等時通信エンドポイントを使用する場合、これらは非デフォルトの設定で使用されます。

USB仕様では、代替設定番号が0から総設定数より1少ない数まで連続する必要があります。しかし一部のデバイスはこのルールを破っており、構造体が数値順に保存されているとは限りません。使用 usb_altnum_to_altsetting() で、代替設定番号に基づいてaltsetting配列内の代替設定を検索できます。

定義された代替設定の数

ref

参照カウンタ。

struct usb_host_config¶

デバイスの設定の表現

定義

struct usb_host_config {
  struct usb_config_descriptor    desc;
  char *string;
  struct usb_interface_assoc_descriptor *intf_assoc[USB_MAXIADS];
  struct usb_interface *interface[USB_MAXINTERFACES];
  struct usb_interface_cache *intf_cache[USB_MAXINTERFACES];
  unsigned char *extra;
  int extralen;
};

メンバ

desc

デバイスの設定ディスクリプタ。

string

この設定に存在する場合のiConfiguration文字列のキャッシュバージョンへのポインタ。

intf_assoc

この設定に含まれるインターフェース関連ディスクリプタのリスト

interface

usb_interface構造体へのポインタの配列。この構成内の各インターフェースごとに1つずつ含まれます。インターフェースの数はdesc.bNumInterfacesに保存されています。これらのポインタは、構成がアクティブな間のみ有効です。

intf_cache

usb_interface_cache構造体へのポインタの配列。この構成内の各インターフェースごとに1つずつ含まれます。これらの構造体はデバイスの寿命を通じて存在します。

extra

この構成に関連するすべての追加ディスクリプタを含むバッファへのポインタ。これは最初のインターフェースディスクリプタの前後に配置されます。

extralen

追加ディスクリプタバッファの長さ。

説明

USBデバイスは複数の構成を持つことができますが、同時に有効なのは1つの構成だけです。それぞれが異なる運用環境を表します。例えば、デュアルスピードデバイスはフルスピードとハイスピードの運用にそれぞれ別な構成を持ちます。利用可能な構成数はデバイスディスクリプタのbNumConfigurationsに保存されています。

構成は複数のインターフェースを含むことができます。それぞれがUSBデバイスの異なる機能に対応し、構成がアクティブな間はすべて利用可能です。USB標準ではインターフェースが0からdesc.bNumInterfaces-1まで順番に番号付けされるべきですが、多くのデバイスがこの点を誤っています。さらに、インターフェース配列は数値順に並んでいない場合があります。使用 usb_ifnum_to_if() インターフェース番号を基にインターフェースエントリを検索するにはこちらを使用してください。

デバイスドライバーは構成をアクティブにするべきではありません。どの構成をインストールするかは、利用可能な電力、提供する機能、ユーザーの希望（ユーザー空間ツールを通じた表現）などの要素を考慮したポリシーディシジョンです。ただし、ドライバーは usb_reset_configuration() 現在の構成およびそのすべてのインターフェースを再初期化するために呼び出すことができます。

};

メンバ

name

ドライバ名はUSBドライバの中で一意でなければなりません。通常はモジュール名と一致する必要があります。

probe

ドライバがデバイスの特定のインターフェースを管理する意欲があるか確認するための関数です。管理可能な場合、プローブがゼロを返し、usb_set_intfdata()を用いてドライバ固有のデータをインターフェースと関連付けます。適切なaltsettingを指定する場合にも使用します。 usb_set_interface() インターフェースを管理しない場合は -ENODEV を返し、本質的なIOエラーが発生した場合は適切な負のエラノーラン値を返します。

disconnect

インターフェースがアクセスできなくなった場合、通常はそのデバイスが切断された（または切断中）か、ドライバモジュールがアンロードされているときに呼び出されます。

unlocked_ioctl

ユーザー空間とusbfsファイルシステムを通じて通信したいドライバに使用されます。これにより、デバイスはファイルシステム内の他の場所に表示されなくても、ユーザー空間に情報を公開する方法を提供できます。

suspend

デバイスがシステムスリープまたはランタイムスリープコンテキストからシステムによってスリープされるときに呼ばれます。システムスリープコンテキストでは返却値は無視されるため、スリープ失敗時はデバイスの使用を継続しないでください。代わりに、再起動またはリセット-再起動ルーチンで失敗を回復してください。

resume

デバイスがシステムによって再起動されるときに呼ばれます。

reset_resume

サスペンドされたデバイスが再起動された代わりにリセットされたときに呼び出されます。

pre_reset

が呼ばれるとき、デバイスが再設定される直前に呼ばれます。 usb_reset_device() このルーチンは、ドライバがデバイスに対してアクティブなURBを一切持たなくなった時点で戻らなければなりません。post_resetメソッドが呼ばれるまで、新たなURBの送信は許されません。

post_reset

が呼ばれるとき、デバイスが再設定される直前に呼ばれます。 usb_reset_device() デバイスが再設定された後

id_table

USBドライバはIDテーブルを使用してホットプラグをサポートします。MODULE_DEVICE_TABLE(usb,…)でこれをエクスポートしてください。この設定がなければ、ドライバのプローブ関数が呼び出されることはありません。

dev_groups

デバイスがドライバにバインドされたときに生成されるデバイスに付属する属性

dynids

このドライバに動的に追加されたデバイスIDの一覧を内部的に保持するためのもの

drvwrap

ドライバモデルコア構造体のラッパー

no_dynamic_id

この値が1に設定されている場合、USBコアはこのドライバに動的IDを追加することを防ぎ、sysfsファイルの作成を禁止します。

supports_autosuspend

0に設定すると、USBコアはこのドライバにバインドされたインターフェースのオートスリープを許可しません。

disable_hub_initiated_lpm

1に設定すると、USBコアはアイドルタイムアウトが発生した際にハブが低消費電力リンク状態の遷移を開始することを許可しません。ただし、デバイスが発起するUSB 3.0リンクPMは依然として許可されます。

soft_unbind

1に設定すると、USBコアはドライバのdisconnectメソッドを呼び出す前にURBを終了させたりエンドポイントを無効化したりしません。

説明

USBインターフェースドライバは、name、probe()およびdisconnect()メソッド、およびid_tableを提供する必要があります。他のドライバフィールドは任意です。

id_tableはホットプラグイン時に使用され、複数のデスクリプタのセットを保持します。各エントリには専用データが関連付けられることもあります。このテーブルはユーザーモードとカーネルモードのホットプラグインサポートの両方に使用されます。

probe()およびdisconnect()メソッドはスリープを許可するコンテキストで呼び出されますが、権限の濫用を避けるべきです。デバイスの接続に関するほとんどの処理はデバイスがオープンされたときに実行され、最後のクローズ時に解除されるべきです。disconnectコードではopen()およびclose()メソッドに関するコンカレンシー問題を扱う必要があります。また、すべての待機中のI/Oリクエストを完了させるために（必要に応じてリンクを解除し、解除が完了するまでブロックするなど）処理を実行する必要があります。

データ転送バッファ:

通常、ドライバは以下の関数で割り当てたI/Oバッファを提供します kmalloc() または、一般的なページプールから取得します。これはtransfer_buffer（コントロールリクエストではsetup_packetも使用）で提供され、ホストコントローラードライバは各バッファに対してDMAマッピング（およびアンマッピング）を行います。これらのマッピング操作は一部のプラットフォームではコストが高く（DMAバウンスバッファやIOMMUとの通信など）、ただしコンピューターモノリスのx86やppcハードウェアでは安価です。

代替として、ドライバーはURB_NO_TRANSFER_DMA_MAPという転送フラグを渡すこともできます。これはホストコントローラードライバーに、transfer_bufferに対してDMAマッピングが不要であることを伝えます。なぜなら、デバイスドライバーがDMAを認識しているからです。たとえば、デバイスドライバーはDMAバッファを割り当てたり、usb_buffer_map()を呼び出すことができます。 usb_alloc_coherent() この転送フラグが提供された場合、ホストコントローラードライバーはtransfer_dmaフィールドに含まれるDMAアドレスを使用しようとします。それ自体でDMAアドレスを決定するのではなく、そのアドレスを使用します。

注意: コントローラーがDMAをサポートしない場合（hcd_uses_dma()が示す通り）やルートハブとの通信時に、transfer_bufferは依然として設定する必要があります。highmemゾーンとデバイス間でデータを転送しなければならない場合、バウンスバッファを作成するかエラーで終了する必要があります。transfer_bufferが設定できない（highmemに存在する）場合、コントローラーがDMAをサポートする場合はNULLを割り当てて、usbmonがその値を使用しないようにします。setup_packetは常に設定する必要がありますので、highmemに配置されることはありません。

初期化:

すべてのURBはdev、pipe、transfer_flags（ゼロでも可）、completeフィールドを初期化する必要があります。すべてのURBはtransfer_bufferとtransfer_buffer_lengthも初期化する必要があります。URB_SHORT_NOT_OK転送フラグを提供することも可能ですが、これは読み込みが短い場合にエラーとして扱うことを示します。このフラグは書き込みリクエストには無効です。

バルクURBはURB_ZERO_PACKET転送フラグを使用できます。これは、バルクOUT転送が常に短いパケットで終了するようにするためのものです。これはゼロ長パケットを追加する必要がある場合でもです。

コントロールURBはsetup_packetフィールドに有効なポインタを提供する必要があります。transfer_bufferとは異なり、setup_packetはDMAマッピングの前にマッピングされることはできません。

インターポールURBは転送間隔を指定する必要があります。これはミリ秒単位で（高速デバイスでは125マイクロ秒単位で）転送をポーリングする頻度を示します。URBがサブミットされた後、intervalフィールドは実際にスケジュールされた転送の間隔を反映します。ポーリング間隔は要求されたよりも頻繁になる可能性があります。たとえば、一部のコントローラーでは最大32ミリ秒の間隔が設定されており、他のコントローラーでは最大1024ミリ秒の間隔がサポートされています。イソクロナスURBにも転送間隔があります。（イソクロナスエンドポイントや高速インターポールエンドポイントの場合、エンドポイント記述子での転送間隔は対数形式でエンコードされています。デバイスドライバーはこれを線形単位に変換する必要があります。）

アイソクロノスエンドポイントキューがすでに実行されていない場合、ホストコントローラーは帯域幅の利用が可能になったら新しいURBをスケジュールして実行を開始します。キューが実行中である場合は、前のURBの終了後に続く最初のトランスファースロットで新しいURBをスケジュールします（そのスロットがすでに期限切れになっていない場合）。スロットが期限切れになっている場合（IRQ配信が長時間遅延した場合など）、スケジュールの挙動はURB_ISO_ASAPフラグに依存します。フラグが未設定の場合、URBは期限切れしたスロットで実行されるため、一部のパケットが転送されない可能性があります。フラグが設定されている場合、URBは最初の未期限切れスロットで実行され、キューの同期が破られます。URB完了時にstart_frameフィールドは、転送がスケジュールされた（マイクロ）フレーム番号に設定されます。フレームカウンタ値の範囲はHC固有であり、最低256から最大65536フレームまで変化します。

アイソクロノスURBは、品質保証が「ベストエフォート」であるため、データ転送モデルが異なります。呼び出し元は特別に割り当てられたURBを提供し、その末尾にnumber_of_packets分のiso_frame_desc構造体を配置します。それぞれのパケットは個別のISO転送を表します。アイソクロノスURBは通常キューイングされ、ドライバがダブルバッファリングを確保するようにサブミットされ、完了ハンドラで明示的に再サブミットされるため、音声や動画などのデータストリームがホストコントローラーのスケジューラがサポートできる最大の定常的な速度で転送されます。

完了コールバック:

完了コールバックはin_interrupt()内で実行され、完了ハンドラが最初にすべきことはステータスフィールドを確認することです。ステータスフィールドはすべてのURBに提供され、未リンクURBの報告や非ISO転送のステータスを報告するために使用されます。URBが完了ハンドラに返される前にはステータスフィールドを確認しないでください。

コンテキストフィールドは通常、URBを関連するドライバやリクエスト状態に戻すために使用されます。

非アイソクロノスURBの完了コールバックが呼び出される際、actual_lengthフィールドは転送されたバイト数を示します。このフィールドは、URBがエラーで終了した場合や未リンクとなった場合でも更新されます。

ISO転送のステータスはiso_frame_desc配列のstatusおよびactual_lengthフィールドで報告され、エラー数はerror_countフィールドで報告されます。ISO転送の完了コールバックでは通常、URBを再サブミットして定常的な転送速度を維持します。

urbがhcdによって所有されている場合、すなわちcall toの呼び出し usb_submit_urb() 完了ルーチンへの移行まで、ドライバがpublicにマークされたフィールドを操作してはいけません。

USBコアAPI¶

USB APIには2つの基本的なI/Oモデルがあります。最も基本的なのは非同期です。ドライバがURBという形式でリクエストを送信し、URBの完了コールバックが次のステップを処理します。すべてのUSB転送タイプがこのモデルをサポートしていますが、コントロールURB（常にセットアップステージとステータスステージを持ち、データステージを持たない場合がある）やイソクロナスURB（大容量パケットを許容し、パケットごとのエラー報告を含む）には特別なケースがあります。

USBドライバはDMAを使用可能なバッファを提供する必要がありますが、DMAマッピング自体を提供する必要はありません。DMAバッファを割り当てる際のAPIを使用することで、一部のシステムではバウンスバッファの使用を防ぐことができます。一部のケースでは、64bit DMAを活用して別の種類のバウンスバッファを省略できる場合があります。

int usb_submit_urb(struct urb *urb, gfp_t mem_flags)¶

エンドポイントに対して非同期転送リクエストを発行します

パラメータ

struct urb *urb

リクエストを記述するURBへのポインタ

gfp_t mem_flags

割り当てるメモリのタイプ、詳細は kmalloc() この項目の有効なオプション一覧を参照してください。

説明

転送リクエストを送信し、そのリクエストを記述するURBの制御をUSBサブシステムに渡します。リクエストの完了は、後述の完了ハンドラを通じて非同期で通知されます。完了の種類は成功、エラー、およびアンリンク（ソフトウェアによって発生するエラー、また「リクエストのキャンセル」とも呼ばれます）の3種類です。

URBは割込みコンテキストからも送信可能です。

送信前にURBを正しく初期化しておく必要があります。関数 usb_fill_bulk_urb() および usb_fill_control_urb() は、特定の転送タイプに応じてほとんどのフィールドを正しく初期化するのに役立ちます。ただし、転送フラグは初期化しません。

送信が成功した場合、USBコアとホストコントローラードライバー（HCD）がURBの処理を終えた時点で、URBのcomplete()コールバックがちょうど1回呼び出されます。完了ハンドラが呼び出されると、リクエストを送信したデバイスドライバーにURBの制御が戻り、完了ハンドラはそのURBを即座に解放したり再利用したりできます。

例外を除き、USBデバイスドライバーはusbcoreまたはHCDが提供するURBフィールドにアクセスすべきではありません。そのアクセスは、complete()が呼ばれた後まで待つ必要があります。例外は周期的な転送スケジューリングに関連します。インタラプトおよびイソクロナスURBの双方において、成功したURBサブミットの一部として、urb->intervalは実際に使用される転送周期（通常は2のべき乗単位）を反映して変更されます。また、イソクロナスURBでは、urb->start_frameは転送がスケジュールで開始されるタイミングを反映して変更されます。

すべてのイソクロナス転送スケジューリングポリシーが動作するわけではありませんが、ほとんどのホストコントローラードライバーは、現在から10〜200ミリ秒先までのISOキューを処理できるはずです。ドライバーは少なくとも1〜2ミリ秒のデータをキューに保持する必要があります。多くのコントローラーでは、新しい転送が追加される際には、少なくとも1ミリ秒先のタイミングで開始する必要があります。ドライバーが追いつかずキューが空になると、新しいサブミットの挙動はURB_ISO_ASAPフラグによって制御されます。フラグが設定されているか、またはキューがアイドル状態であれば、URBはエンドポイントのスケジュール内で最初に空きがある（かつ期限切れしていない）スロットに常に割り当てられます。フラグが設定されていない場合かつキューがアクティブであれば、URBはエンドポイントの前のURBの終了後に続く次のスロットに常に割り当てられます（そのスロットが過去のものであっても）。このようにしてスロットに割り当てられたパケットがすでに期限切れしている場合、そのパケットは送信されず、対応するusb_iso_packet_descriptorのステータスフィールドには-EXDEVが返されます。URB内のすべてのパケットにこのようなことが起きた場合、サブミットは-EXDEVエラーで失敗します。

コントロールエンドポイントでは、同期 usb_control_msg() 呼び出しは（非インタラプトコンテキストで）この呼び出しの代わりによく使用されます。これはUSB 2.0仕様で標準化されたリクエストを処理するための利便性ラッパーとしてよく使用されます。バルクエンドポイントでは、同期 usb_bulk_msg() 呼び出しが利用可能です。

リクエストキュー:

URBは前のものに完了する前にエンドポイントにサブミットされ、割り込み遅延やシステムオーバーヘッドがデータ通信用に与える影響を最小限に抑えることができます。このようなキューイングポリシーにより、エンドポイントのキューは常に空ではありません。これは連続的なイソクロナスデータストリームには必須であり、一部のインタラプト転送にも適用される場合があります。このようなキューイングは、USBコントローラーがドライバソフトウェアが前の（成功した）リクエストの完了処理を終える前に後続のリクエストを開始できるようにすることで、帯域幅利用率を最大限に活用します。

Linux 2.6以降、すべてのUSBエンドポイント転送キューは、1より大きい深さをサポートしています。これは以前はHCD固有の挙動でしたが、ISO転送を除きます。非等時性エンドポイントキューは、エラーまたはキャンセル後のクリーンアップ中に無効になります。

予約帯域幅転送:

定期的な転送（割込みまたは等時性）は、urbに指定されたインターバルで繰り返し実行されます。最初のurbをエンドポイントにサブミットすることで、その転送に必要な帯域幅が予約されます。USBサブシステムが定期的なリクエストに十分な帯域幅を割り当てられなかった場合、そのリクエストは失敗する必要があります。

xHCIデバイスでは、設定時またはアリト設定が選択されたときに帯域幅が予約されます。バス帯域幅が不足している場合、設定/アリト設定リクエストは失敗します。したがって、xHCIデバイスの定期的なエンドポイントへのサブミットは、帯域幅制約により失敗することはありません。

デバイスドライバーは、エンドポイントのキューに常にURBが存在することを明示的に要求する必要があります（完了ハンドラでの短い期間を除く）。URBがキューにない場合、エンドポイントの帯域幅予約がキャンセルされます。これにより、ドライバーは完了ハンドラを使用して、必要な帯域幅を維持するために、完了したURBを再初期化して再サブミットし続けることができます。

メモリフラグ:

mem_flagsの使用方法に関する一般的なルールはkmallocと同じです。4つの可能な値があります：GFP_KERNEL、GFP_NOFS、GFP_NOIO、GFP_ATOMIC。

GFP_NOFSはまだ実装されていないため、使用されません。

GFP_ATOMICは、

  1. 完了ハンドラ、割込み、ボトムハーフ、タスクレット、タイマーや、

  2. スピンロックまたはrwロック（セマフォでは適用されません）を保持している場合、または、

  3. current->stateがTASK_RUNNINGでない場合（これはstateを変更した後のみ発生します）

ブロックIOパスおよびストレージデバイスのエラー処理で使用されます。

すべてのその他の状況ではGFP_KERNELが使用されます。

mem_flagsに関するより具体的なルールは以下のようになります、例えば

  1. ネットワークドライバーのstart_xmit、timeout、およびreceiveメソッドはGFP_ATOMICを使用する必要があります（これらはスピンロックを保持して呼び出されます）；

  2. SCSIドライバーのqueuecommandメソッドはGFP_ATOMICを使用する必要があります（これもスピンロックを保持して呼び出されます）；

  3. ネットワークドライバーでカーネルスレッドを使用する場合は、(b)または(c)が適用されない限りGFP_NOIOを使用する必要があります;

  4. down()を実行した後、GFP_KERNELを使用できます。ただし、(b)または(c)が適用される場合、またはストレージドライバーのブロックIOパス内である場合は除きます。

  5. USBプローブおよび切断はGFP_KERNELを使用します。ただし、(b)または(c)が適用される場合は除きます。

  6. 稼働中のストレージまたはネットワークデバイスのファームウェアを変更する際はGFP_NOIOを使用します。ただし、(b)または(c)が適用される場合は除きます。

戻り値

成功時のサブミッションでは0。エラーの場合には負のエラーナンバーが返されます。

int usb_unlink_urb(struct urb *urb)¶

エンドポイントの転送リクエストを中止/キャンセルする

パラメータ

struct urb *urb

以前にサブミットされたリクエストを記述するurbへのポインタ。NULLでも可

説明

このルーチンは進行中のリクエストをキャンセルします。URBは1回のサブミッションごとに完了し、1回のサブミッションごとにキャンセル可能であり、成功したキャンセルはリクエストの終了を意味します。 urb 完了ハンドラがステータスコードでリクエストがキャンセルされたことを示すコードとともに呼び出されます。

ドライバーは切断メソッドが返る後、このルーチンや関連ルーチン（例： usb_kill_urb() または usb_unlink_anchored_urbs()）を呼び出すべきではありません。切断関数はドライバーのI/Oルーチンと同期を取って、すべてのURB関連アクティビティが完了するのを待ってから返す必要があります。

このリクエストは非同期ですが、HCDはunlink中に->complete()コールバックを呼び出す可能性があります。そのため、ドライバーが usb_unlink_urb()を呼び出す際には、完了関数が取得する可能性のあるロックを保持してはいけません。成功は-EINPROGRESSを返すことで示され、その時点でURBはまだデバイスドライバーに返却されていない可能性があります。最終的に呼び出される際、完了関数は urb->status == -ECONNRESETを確認します。失敗は usb_unlink_urb() 他の値を返すことで示されます。 urb が現在「リンク」されていない場合（つまり、サブミットされていない、または以前にアンリンクされた、またはハードウェアがすでに処理を終えた場合）、完了ハンドラがまだ実行されていない場合でもアンリンクは失敗します。

このルーチンが実行中はURBを解放してはいけません。特に、ドライバーがこのルーチンを呼び出す際には、完了ハンドラがURBを解放しないように保証する必要があります。

アンリンクとエンドポイントキュー:

[以下の動作と保証は仮想ルートハブには適用されません。物理的なUSBデバイスのエンドポイントキューにのみ適用されます。]

ホストコントローラードライバ（HCD）は、特定のエンドポイントのすべてのURBをキューに配置します。通常、コントローラハードウェアが各リクエストを処理するにつれてキューは進みますが、URBがエラーで終了した場合、キューは一般的に停止します（以下参照）。少なくともそのURBの完了ルーチンが戻るまで、停止したキューは再開しません。元の完了ハンドラが戻る何時間後であろうと、すべての未リンクURBが完全に退役し、その完了ルーチンが実行された時点で、停止したキューが再開されることを保証します。URBがリンク解除されたため終了した場合でも、同じ挙動と保証が適用されます。

バーストおよび割込みエンドポイントのキューは、URBがいかなるエラーでも終了した場合、必ず停止します。これは-ECONNRESET、-ENOENT、-EREMOTEIOを含むすべてのエラーです。コントロールエンドポイントのキューは同様の挙動を示しますが、-EREMOTEIOエラーでは停止しないことが保証されません。イソクロノスエンドポイントのキューは異なる扱いを受けます。なぜなら、それらは固定のレートで進む必要があるからです。このようなキューは、URBがエラーを発生させた場合でも、またはリンク解除された場合でも停止しません。リンク解除されたイソクロノスURBは、パケットストリームにギャップを生じさせる可能性があります。このようなギャップが補填されるかどうかは未定義です。

URBが短いパケットを受信したため早期に終了した場合、URB_SHORT_NOT_OKフラグが設定されている場合に限り、-EREMOTEIOエラーが発生します。このフラグを設定することで、USBデバイスドライバは大容量または複雑なバースト転送用に深いキューを構築し、任意の中断転送後にすべての待機中のURBをリンク解除することで信頼性のあるクリーンアップが可能になります。

コントロールURBが-EREMOTEIO以外のエラーで終了した場合、転送のステータスステージが実行されない可能性が高いです。

戻り値

成功の場合-EINPROGRESS。失敗の場合の他の値については説明を参照してください。

一致する条件:

usb_device_idの「match_flags」要素は、どのメンバが使用されるかを制御します。対応するビットが設定されている場合、device_idの値はデバイスまたはインターフェース記述子の対応するメンバと一致しなければなりません。一致しない場合、device_idは一致しません。

優れたusb_device_idテーブルの特徴:

マッチアルゴリズムは非常に単純なので、ドライバ選択の知能はスマートなドライバIDレコードから来なければなりません。他の選択ポリシーを使用する明確な理由がない限り、関連するグループのみにマッチ要素を提供し、マッチ指定子を特定から一般の順に並べるべきです。目的に応じて提供されるマクロを使用してください。

最も特定のマッチ指定子はデバイス記述子データを使用します。これらは製品固有のマッチでよく使用されます。USB_DEVICEマクロはベンダーと製品IDを提供でき、また製品リビジョンの範囲にもマッチできます。これらはアプリケーションまたはベンダー固有のbDeviceClass値を持つデバイスで広く使用されています。

デバイスクラス/サブクラス/プロトコル仕様に基づくマッチはやや一般的です。USB_DEVICE_INFOマクロまたはその兄弟マクロを使用してください。これらは、bDeviceClassが各インターフェースに独自のクラスを指定しない単機能デバイスで使用されます。

インターフェースのクラス/サブクラス/プロトコルに基づくマッチングは最も一般的です。これにより、マルチファンクションデバイス上の任意のインターフェースにドライバをバインドできます。class-per-interfaceスタイルのデバイス（bInterfaceClassに記録されているもの）をマッチングするには、USB_INTERFACE_INFOマクロまたはその兄弟マクロを使用してください。

USB_INTERFACE_INFOで作成されたエントリは、デバイスクラスがVendor-Specificに設定されている場合、どのインターフェースにもマッチングしません。これは意図的な挙動です。USB仕様では、これらのデバイスのインターフェースクラス/サブクラス/プロトコルの意味もベンダー固有であり、標準的な製品クラスにマッチングすることができないためです。このようなデバイスでインターフェースベースのマッチングを使用したい場合は、ベンダーIDも指定したマッチングレコードを作成してください。（残念ながら、このようなレコードを作成する標準的なマクロはありません。）

そのグループ内で、すべての組み合わせが意味を持つわけではありません。たとえば、ベンダーIDと製品IDを指定せずに製品バージョンの範囲を指定したり、関連するクラスとサブクラスを指定せずにプロトコルを指定したりしないでください。

ホストコントローラーAPI¶

これらのAPIはホストコントローラードライバー専用で、ほとんどのドライバーがXHCI、EHCI、OHCI、またはUHCIなどの標準レジスタインターフェースを実装しています。UHCIは最初のインターフェースの一つで、インテルによって設計されVIAでも使用されました。ハードウェアではあまり処理を行いません。OHCIは後になって設計され、ハードウェアがより多くの処理を行うようにしました（より大きな転送、プロトコル状態の追跡など）。EHCIはUSB 2.0用に設計され、OHCI（ハードウェアが多くの処理を行う）とUHCI（一部のISOサポート、TDリスト処理など）の特徴を組み合わせています。XHCIはUSB 3.0用に設計され、機能のサポートをハードウェアに移行し続けています。

「大三」以外のホストコントローラーもありますが、ほとんどのPCIベースのコントローラー（一部の非PCIベースのコントローラーも含む）はこれらのインターフェースのいずれかを使用しています。すべてのホストコントローラーがDMAを使用するわけではなく、一部はPIOを使用し、シミュレータや仮想ホストコントローラーも存在し、ネットワーク経由でUSBをパイプするためのものです。

これらのコントローラーのドライバーにも同じ基本的なAPIが利用可能です。歴史的な理由により、2つのレイヤーに分かれています。 struct usb_bus 2.2カーネルで導入された薄いレイヤーで、 struct usb_hcd 機能豊富なレイヤーで、HCDが共通コードを共有できるようにし、ドライバーサイズを小さくし、HCD固有の動作を大幅に削減します。

「devtmpfs」に含まれるファイルは何か？¶

通常は /dev/bus/usb/にマウントされ、usbfsの特徴には以下のものが含まれます：

  • /dev/bus/usb/BBB/DDD …デバイスごとの設定記述子を公開するマジックファイル、およびデバイスリクエスト（含むデバイスへのI/O）を行うための複数のioctlをサポートしています。（プログラムからのアクセス専用です。）

各バスにはBBBという番号が割り当てられ、各バス内ではデバイスにも同様の番号DDDが割り当てられます。ただし、これらの BBB/DDD パスは「安定した」識別子ではありません。デバイスを常に同じハブポートに接続していても、変更される可能性があります。 アプリケーションの設定ファイルにこれらを保存するのは考えてもいけません。 安定した識別子は利用可能です。ユーザーモードアプリケーションで使用したい場合に有効です。HIDやネットワークデバイスはこれらの安定したIDを公開しており、たとえば正しいUPSを指定してセカンドサーバーを電源オフにするなど、確実な操作が可能です。注意点として、このドキュメンテーションではまだこれらのIDを公開していません。

/dev/bus/usb/BBB/DDD¶

これらのファイルは以下の基本的な方法で使用します：

  • これらは読み取れ、 まずデバイス記述子（18バイト）を生成し、その後現在の設定の記述子を出力します。USB 2.0仕様を参照してください。バイナリデータ形式についての詳細情報があります。ほとんどのマルチバイト値はリトルエンディアン形式からホストのネイティブバイト順に変換する必要がありますが、デバイス記述子内のフィールド（BCD符号化されたフィールド、ベンダーや製品IDを含む）は自動的にバイトオーダーが反転されます。注意点として、設定記述子にはインターフェース、アリトセッティング、エンドポイント、または追加のクラス記述子が含まれます。

  • USB操作 を使用して ioctl() を実行するリクエストでエンドポイントI/Oリクエスト（同期または非同期）やデバイス管理を行います。これらのリクエストには CAP_SYS_RAWIO の機能、およびファイルシステムアクセス権限が必要です。これらのデバイスファイルに対しては、一度に1つのioctlリクエストのみが可能です。これにより、1つのスレッドで同期的にエンドポイントを読み込んでいる間、別のスレッドで別のエンドポイントへの書き込みはできません。これは ハーフダブルックス プロトコルでは問題ありませんが、それ以外の場合は非同期I/Oリクエストを使用します。

接続されたすべてのUSBデバイスには1つのファイルがあります。 BBB はバス番号を示します。 DDD そのバス上のデバイスアドレスを示します。これらの番号は順番に割り当てられ、再利用可能なため、デバイスへの安定したアクセスには頼れません。たとえば、デバイスが接続されている間でも再登録されることが比較的よくあるため（たとえば、電源やハブ、USBケーブルが揺さぶられた可能性がある）、デバイスは 002/027 最初に接続したときと 002/048 ある程度の時間が経過した後、異なるアドレスを持つことがあります。

これらのファイルはバイナリデータとして読み込むことができます。バイナリデータはまずデバイス記述子、次にデバイスの各コンフィギュレーションの記述子で構成されます。デバイス記述子内のマルチバイトフィールドは、カーネルがホストのエンドイアンネスに変換します。コンフィギュレーション記述子はバスのエンドイアンネス形式で記述されています！コンフィギュレーション記述子はwTotalLengthバイトごとに配置されます。デバイスがwTotalLengthで示されるよりも少ないコンフィギュレーション記述子データを返す場合、その欠落したバイト分に穴ができます。この情報は後述する /sys/kernel/debug/usb/devices ファイルでテキスト形式でも表示されます。

これらのファイルは、USBデバイス用のユーザー空間ドライバを書くためにも利用できます。まず /dev/bus/usb/BBB/DDD ファイルを開き読み書き可能にし、その記述子を読み込んで期待するデバイスであることを確認し、その後、ioctlコールを使用してインターフェース（または複数のインターフェース）にバインドします。さらに、コントロール、バルク、またはその他の種類のUSB転送を使用してデバイスと通信するためには、デバイスに対してより多くのioctlコールを実行します。ioctlコールの一覧は <linux/usbdevice_fs.h> ファイルに記載されており、現在の時点ではソースコード（linux/drivers/usb/core/devio.c)がこれらのファイルを通じてデバイスにアクセスする方法の主要な参照資料です。

注意してください。これらの BBB/DDD ファイルはデフォルトではrootのみが書き込み可能であるため、ユーザー空間ドライバを書くにはrootのみが可能です。他のユーザーに読み取り/書き込み権限を特定的に付与するには、 chmodを使用できます。また、usbfsのマウントオプションなど、 devmode=0666 が役立つ場合があります。

ユーザーモードドライバのライフサイクル¶

このようなドライバはまず、処理可能なデバイスのデバイスファイルを特定する必要があります。それは、 /sbin/hotplug イベントハンドリングエージェントが新しいデバイスをこのドライバで処理するように選んだためかもしれません。あるいは、すべての /dev/bus/usb デバイスファイルをスキャンし、ほとんどのデバイスを無視するアプリケーションかもしれません。いずれにしても、そのドライバは read() デバイスファイルからすべての記述子を読み込み、それが処理可能なデバイスであるかを確認する必要があります。これは特定のベンダーと製品IDのみを許可する単純な拒否ポリシーかもしれないし、より複雑なポリシーが必要かもしれません。

いつでもシステムにこのようなデバイスが1つだけ存在するとは仮定しないでください！コードが同時に複数のデバイスを処理できない場合でも、複数のデバイスが存在する場合を検出するようにし、ユーザーがどのデバイスを使用するかを選べるようにしてください。

ユーザー モード ドライバーが使用するデバイスを特定した後、そのデバイスとやり取りするスタイルは2通りあります。シンプルなスタイルは制御要求のみを行うことであり、一部のデバイスはこれ以上の複雑なやり取りを必要としません。(例として、特定のベンダー向けの制御要求を使用して初期化や設定を行うソフトウェアがあり、その他の部分にはカーネル ドライバーを使用するというケースがあります。)

より複雑なスタイルのドライバーが必要なケースが一般的です。これは非制御エンドポイントを使用し、データの読み書きを行い、インターフェースの排他使用を主張するドライバーです。 バルク 転送は使いやすく、その兄弟 割り込み 転送は低速デバイスで動作します。割り込みと 等時性 転送は帯域幅が確保されているためサービスの保証が可能です。このような「周期的」な転送は usbfs を通して使用するのはやや複雑ですが、非同期コールを使用すれば問題ありません。ただし、割り込み転送も同期的な「ワンショット」スタイルで使用可能です。

ユーザー モード ドライバーはデバイスが切断された際のリクエスト状態のクリーンアップを心配する必要がありませんが、ENODEV エラーを開始してからすぐにオープンしているファイル記述子を閉じるべきです。

ドキュメントに記載されています）。各ファイルは複数の I/O ストリームを複数のエンドポイントごとに multiplex しており、各デバイスには制御エンドポイント（エンドポイントゼロ）があり、これは限定的な RPC スタイルのアクセスをサポートします。デバイスの設定は、カーネル内の hub_wq によってデバイス全体にわたる 構成 を設定することによって行われ、これは消費電力や基本的な機能などの項目に影響を与えます。エンドポイントは USB インターフェースに含まれており、これは複数の 代替設定 を持つ場合があり、これにより利用可能なエンドポイントなどの項目に影響を与えます。多くのデバイスは単一の設定とインターフェースしか持たないため、それらのドライバーは設定と代替設定を無視します。

管理/ステータスリクエスト¶

いくつかの usbfs リクエストはデバイス I/O と直接的な関係がありません。これらは主にデバイス管理やステータスに関するものであり、すべて同期リクエストです。

USBDEVFS_CLAIMINTERFACE

usbfsが特定のインターフェースを主張するように強制するために使用されます。このインターフェースは、以前にusbfsや他のカーネルドライバーによって主張されていません。ioctlパラメータは、インターフェース番号（ディスクリプタから取得したbInterfaceNumber）を保持する整数です。

ドライバがインターフェースのエンドポイントを使用する前にインターフェースを主張していない場合、かつ他のドライバがそのインターフェースにバインドしていない場合、usbfsが自動的にインターフェースを主張します。

この主張はRELEASEINTERFACE ioctlまたはファイル記述子の閉じる操作によって解放されます。このリクエストによってファイルの変更時刻は更新されません。

USBDEVFS_CONNECTINFO

デバイスがローレートかどうかを示します。ioctlパラメータは、次の構造に似た構造を指します：

struct usbdevfs_connectinfo {
        unsigned int   devnum;
        unsigned char  slow;
};

ファイルの変更時刻はこのリクエストによって更新されません。

「遅くない」デバイスがハイレート（480 MBit/sec）で接続されているか、フルレート（12 MBit/sec）で接続されているかは判別できません。 devnum値はすでに把握しているはずです。これはデバイスファイル名のDDD値です。

USBDEVFS_GETDRIVER

指定されたインターフェースにバインドされているカーネルドライバーの名前（文字列）を返します。パラメータはこの構造へのポインタで、この構造は変更されます：

struct usbdevfs_getdriver {
        unsigned int  interface;
        char          driver[USBDEVFS_MAXDRIVERNAME + 1];
};

ファイルの変更時刻はこのリクエストによって更新されません。

USBDEVFS_IOCTL

ユーザー空間からカーネルドライバーにリクエストを転送します。このドライバーがカーネルのioctlエントリを登録している場合、 struct usb_driver 登録済み:

struct usbdevfs_ioctl {
        int     ifno;
        int     ioctl_code;
        void    *data;
};

/* user mode call looks like this.
 * 'request' becomes the driver->ioctl() 'code' parameter.
 * the size of 'param' is encoded in 'request', and that data
 * is copied to or from the driver->ioctl() 'buf' parameter.
 */
static int
usbdev_ioctl (int fd, int ifno, unsigned request, void *param)
{
        struct usbdevfs_ioctl   wrapper;

        wrapper.ifno = ifno;
        wrapper.ioctl_code = request;
        wrapper.data = param;

        return ioctl (fd, USBDEVFS_IOCTL, &wrapper);
}

ファイルの変更時刻はこのリクエストによって更新されません。

このリクエストは、カーネルドライバーがキャラクターやブロック特殊デバイスを生成せずにユーザーモードコードとファイルシステム操作を通じて通信できるようにします。また、デバイスにどの特殊ファイルを使用すべきか尋ねるなどの操作にも使用されています。デバイスのバインドと構成をユーザーモードコードが完全に管理できるようにするため、2つの事前定義されたioctlが用意されています。

USBDEVFS_RELEASEINTERFACE

ファイル記述子が閉じる前に、usbfsがインターフェースを主張したことを解放するために使用されます（明示的にまたはUSBDEVFS_CLAIMINTERFACE呼び出しの結果）。ioctlパラメータはインターフェース番号（ディスクリプタから取得したbInterfaceNumber）を保持する整数です。ファイルの変更時刻はこのリクエストによって更新されません。

警告

主張をしたタスクが解放を実行しているかを確認するセキュリティチェックは行われません。これにより、ユーザーモードドライバーが他のドライバーに干渉する可能性があります。

USBDEVFS_RESETEP

エンドポイント（バーストまたは割り込み）のデータトグル値をDATA0にリセットします。ioctlパラメータはエンドポイント番号（エンドポイントディスクリプタで識別される1〜15）を保持する整数で、デバイスのエンドポイントがホストにデータを送信する場合、USB_DIR_INを追加します。

警告

このリクエストは使用しないでください。おそらく削除すべきです。 この機能を使用すると、デバイスとドライバーのトグル同期が失われる可能性があります。本当に同期を失った場合は、CLEAR_HALT や SET_INTERFACE などのリクエストを使用してデバイスと完全にハンドシェイクする必要があります。

USBDEVFS_DROP_PRIVILEGES

この機能は、usbfs ファイル記述子で特定された操作を実行する権限を放棄します。これは、任意のインターフェースを主張する、他のユーザーが主張しているインターフェースを持つデバイスをリセットする、または USBDEVFS_IOCTL コールを実行するなど、権限が付与された操作を含みます。ioctl パラメータは、このファイル記述子でユーザーが主張できるインターフェースの 32 ビットマスクです。この ioctl を複数回実行することで、マスクを狭めることができます。

同期I/Oサポート¶

同期リクエストは、ユーザー モードのリクエストが完了するまでカーネルがブロックします。これは、成功またはエラーを報告するまでです。ほとんどの場合、これは usbfs を使用する最も簡単な方法ですが、上記のように複数のエンドポイントへの I/O を同時に実行することはできません。

USBDEVFS_BULK

デバイスに対してバッキングリードまたはバッキングライトリクエストを実行します。ioctl パラメータは、次の構造へのポインタです：

struct usbdevfs_bulktransfer {
        unsigned int  ep;
        unsigned int  len;
        unsigned int  timeout; /* in milliseconds */
        void          *data;
};

以下の ep 値は、エンドポイント記述子で識別されるバッキングエンドポイント番号（1 〜 15）を示し、デバイスからホストへデータを送信するエンドポイントを参照する場合は USB_DIR_IN でマスクされます。データバッファの長さは、 len; 最近のカーネルでは、リクエストが 128KBytes までサポートされています。 FIXME 読み取り長さの返却方法や短い読み取りの処理方法を説明してください。.

USBDEVFS_CLEAR_HALT

エンドポイントのハルト（ストール）をクリアし、エンドポイントのトグルをリセットします。これは、バッキングまたは割込みエンドポイントにのみ意味があります。ioctl パラメータは、デバイスからホストへデータを送信するエンドポイントを参照する場合は USB_DIR_IN でマスクされ、エンドポイント番号（1 〜 15、エンドポイント記述子で識別される）を示します。

バッキングまたは割込みエンドポイントがストールしている場合、この機能を使用してデータ転送リクエストにステータスを返します。制御リクエストを直接実行しないでください。なぜなら、ホストのデータトグルの記録を無効にする可能性があるからです。 -EPIPE status to a data transfer request. Do not issue the control request directly, since that could invalidate the host’s record of the data toggle.

USBDEVFS_CONTROL

デバイスに対して制御リクエストを実行します。ioctl パラメータは、次の構造へのポインタです：

struct usbdevfs_ctrltransfer {
        __u8   bRequestType;
        __u8   bRequest;
        __u16  wValue;
        __u16  wIndex;
        __u16  wLength;
        __u32  timeout;  /* in milliseconds */
        void   *data;
};

この構造の最初の 8 バイトは、デバイスに送信する SETUP パケットの内容です。詳細は USB 2.0 指南を参照してください。bRequestType の値は、 USB_TYPE_* value, a USB_DIR_* value, and a USB_RECIP_* value (from linux/usb.hwLengthがゼロでない場合、その値はデータバッファの長さを示し、これはデバイスに書き込まれる（USB_DIR_OUT）か、デバイスから読み取られる（USB_DIR_IN）かを表します。

現在のところ、デバイスへまたはから転送できるデータ量は最大4 KBytesに制限されており、usbfsには制限があり、一部のホストコントローラードライバーにも制限があります。（これは通常問題にはなりません。） また デバイスから短い読み取りが返ってくることを許容するという表現はできません。

USBDEVFS_RESET

USBレベルでのデバイスリセットを行います。ioctlパラメータは無視されます。リセット後、すべてのデバイスインターフェースが再びバインドされます。ファイルの変更時刻はこのリクエストで更新されません。

警告

この呼び出しは使用を避けてください usbcoreのバグが修正されるまで、この呼び出しはデバイス、インターフェース、ドライバー（usbfsだけでなく）の状態を完全に同期しないので、使用を避けてください。

USBDEVFS_SETINTERFACE

インターフェースの代替設定を設定します。ioctlパラメータは、次の構造体へのポインタになります：

struct usbdevfs_setinterface {
        unsigned int  interface;
        unsigned int  altsetting;
};

ファイルの変更時刻はこのリクエストによって更新されません。

これらのstructメンバは、現在の設定に適用されるインターフェース記述子からのものです。インターフェース番号はbInterfaceNumberの値で、altsetting番号はbAlternateSettingの値です。（これによりインターフェース内の各エンドポイントがリセットされます。）

USBDEVFS_SETCONFIGURATION

デバイスに対して usb_set_configuration() 呼び出しを行います。パラメータは、設定番号（記述子からのbConfigurationValue）を保持する整数です。ファイルの変更時刻はこのリクエストで更新されません。

警告

この呼び出しは使用を避けてください usbcoreのバグが修正されるまで、この呼び出しはデバイス、インターフェース、ドライバー（usbfsだけでなく）の状態を完全に同期しないので、使用を避けてください。

非同期I/Oサポート¶

上記のように、ユーザーモードコードから並行操作を開始することが重要な状況があります。これは特に周期的な転送（割込みおよび等時性）において重要ですが、他の種類のUSBリクエストにも適用可能です。このような場合、ここに説明する非同期リクエストは不可欠です。カーネルが1つのリクエストを完了するまでブロックするのではなく、ブロッキングは別途行われます。

これらのリクエストは、カーネルデバイスドライバで使用されるURBに似た構造体にパッケージされます。（POSIX非同期I/Oのサポートはありません、ごめんなさい。）これはエンドポイントタイプ（USBDEVFS_URB_TYPE_*）、エンドポイント（番号、USB_DIR_INでマスク処理）、バッファおよび長さ、そしてユーザーの「コンテキスト」値（各リクエストを一意に識別するためのもの）を指定します。（これは通常、リクエストごとのデータへのポインタです。）フラグはリクエストを変更できます（カーネルドライバにサポートされているほど多くのフラグはありません）。

各リクエストは、完了時にリアルタイムシグナル番号（SIGRTMINからSIGRTMAXまでの範囲）を指定して、そのシグナルを送信するようにリクエストできます。

usbfsがこれらのURBを返す際、ステータス値が更新され、バッファが変更される可能性があります。等時性転送を除き、actual_lengthが転送されたバイト数を示すよう更新されます。USBDEVFS_URB_DISABLE_SPDフラグが設定されている場合（「短いパケットは許容されない」）、読み込まれたバイト数が要求されたよりも少ない場合はエラーレポートが返されます。

struct usbdevfs_iso_packet_desc {
        unsigned int                     length;
        unsigned int                     actual_length;
        unsigned int                     status;
};

struct usbdevfs_urb {
        unsigned char                    type;
        unsigned char                    endpoint;
        int                              status;
        unsigned int                     flags;
        void                             *buffer;
        int                              buffer_length;
        int                              actual_length;
        int                              start_frame;
        int                              number_of_packets;
        int                              error_count;
        unsigned int                     signr;
        void                             *usercontext;
        struct usbdevfs_iso_packet_desc  iso_frame_desc[];
};

これらの非同期リクエストでは、ファイルの変更日時がリクエストを開始したタイミングを反映します。これとは対照的に、同期リクエストではリクエストが完了したタイミングを反映します。

USBデバイス¶

USBデバイスは現在debugfs経由でエクスポートされています:

  • /sys/kernel/debug/usb/devices …これは、カーネルが認識しているすべてのUSBデバイスとその構成デスクリプタを示すテキストファイルです。このファイルはpoll()で監視することもできます。

/sys/kernel/debug/usb/devices¶

このファイルは、ユーザーモードでのステータス表示ツールにとって便利です。ツールはテキスト形式をスキャンして大部分を無視できます。より詳細なデバイスステータス（クラスやベンダーのステータスを含む）は、デバイス固有のファイルから取得可能です。このファイルの現在のフォーマットについての情報は下記をご参照ください。

このファイルは、poll()システムコールと組み合わせて使用することで、デバイスの追加・削除を検出することもできます:

int fd;
struct pollfd pfd;

fd = open("/sys/kernel/debug/usb/devices", O_RDONLY);
pfd = { fd, POLLIN, 0 };
for (;;) {
    /* The first time through, this call will return immediately. */
    poll(&pfd, 1, -1);

    /* To see what's changed, compare the file's previous and current
       contents or scan the filesystem.  (Scanning is more precise.) */
}

この挙動は情報表示やデバッグ目的にのみ意図されています。デバイスの初期化やユーザーモードのヘルパープログラムの起動などは、udevやHALなどのプログラムを使用するのが適切です。

このファイルでは、各デバイスの出力が複数行のASCII出力で表示されます。

ASCII形式にしたのは意図しており、補助プログラムを使わずに誰でも有用なデータを取得できるようにしています。ただし、補助プログラムを使用すれば、各行の最初の4列（トポロジー情報: Lev, Prnt, Port, Cnt）の数字を用いてUSBトポロジーダイアグラムを作成できます。 T: line（トポロジー情報: Lev, Prnt, Port, Cnt）

各行はその行に割り当てられた1文字のIDでラベル付けされています:

T = Topology (etc.)
B = Bandwidth (applies only to USB host controllers, which are
virtualized as root hubs)
D = Device descriptor info.
P = Product ID info. (from Device descriptor, but they won't fit
together on one line)
S = String descriptors.
C = Configuration descriptor info. (* = active configuration)
I = Interface descriptor info.
E = Endpoint descriptor info.

USBデバイスは複数の設定を持つことがあります。それぞれの設定は大きく異なります。たとえば、バス電源の設定は自己電源の設定よりもはるかに機能が制限されているかもしれません。一度に有効なデバイス設定は1つだけです。ほとんどのデバイスは1つの設定しか持ちません。

使用例¶

ユーザーまたはスクリプトがトポロジ情報にのみ興味がある場合、たとえば以下のようにします grep ^T: /sys/kernel/debug/usb/devices トポロジ行のみを表示します。『角括弧内にある文字で始まる行のみを表示する』には、 grep -i ^[tdp]: /sys/kernel/debug/usb/devices というコマンドを使用できます。やや複雑なスクリプトを使うと、選択した行（たとえばT、D、P行のみ）を表示したり、出力形式を変更したりできます。（The procusb Perlスクリプトはこのアイデアの始まりです。選択した行（TBDPSCIEから選択）または「すべて」の行を一覧表示します。 /sys/kernel/debug/usb/devices.)

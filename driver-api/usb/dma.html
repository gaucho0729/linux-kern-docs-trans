USB DMA¶

Linux 2.5カーネル（以降）では、USBデバイスドライバーがDMAを用いてI/O操作を行う方法に対して追加の制御を行うことができます。APIの詳細は、カーネルのusbプログラミングガイド（kerneldoc、ソースコードから参照）に記載されています。

API概要¶

全体像としては、USBドライバーはほとんどのDMAに関する問題を無視し続けることができますが、DMA用バッファを提供する必要があります（ 動的DMAマッピングガイド参照）。これは2.4（および以前）のカーネルでの動作と同様ですが、DMAを意識したドライバーとして動作することも可能です。

DMAを意識したUSBドライバー:

  • 新しい呼び出しによりDMAを意識したドライバーが可能となり、DMAバッファを割り当てたり、既存のDMA用バッファのDMAマッピングを管理したりできます（以下参照）。

  • URBには追加の「transfer_dma」フィールドがあり、その有効性を示すtransfer_flagsビットも存在します。（コントロールリクエストには「setup_dma」もありますが、ドライバーはこれを使用してはいけません。）

  • 「usbcore」は、DMAを意識したドライバーが最初にマッピングしなかった場合にDMAアドレスをマッピングします（ URB_NO_TRANSFER_DMA_MAPを設定した場合）。HCDはURBのDMAマッピングを管理しません。

  • 新しい「汎用DMA API」があり、その一部はUSBデバイスドライバーでも使用可能です。USBインターフェースやデバイスに対してdma_set_mask()を絶対に使用しないでください。これは共有しているバス上のすべてのデバイスに影響を及ぼす可能性があります。

不要なコピーの削減¶

CPUが不要にデータをコピーするのを避けることは望ましいです。コストは累積し、キャッシュの過剰な使用などの副作用は微妙なペナルティを課すことがあります。

  • 同じバッファから常に小さなデータを転送している場合、IOMMUでDMAマッピングを管理するシステムではリソースを大幅に消費します。各リクエストごとにIOMMUマッピングを設定・解除するコストは、I/O操作よりもはるかに高くなる可能性があります！

    このような特定のケースでは、USBは低コストのメモリを割り当てるプリミティブを提供しています。これらはkmallocとkfreeのバージョンに似ており、urb->transfer_bufferとurb->transfer_dmaに正しいアドレスを提供します。また、 URB_NO_TRANSFER_DMA_MAP にurb->transfer_flagsを設定します。

    void *usb_alloc_coherent (struct usb_device *dev, size_t size,
        int mem_flags, dma_addr_t *dma);

void usb_free_coherent (struct usb_device *dev, size_t size,
        void *addr, dma_addr_t dma);

    ほとんどのドライバーは 禁止です これらのプリミティブを使用すべきです。これらは「dma-coherent」タイプのメモリを使用する必要がなく、 kmalloc() から返されるメモリも問題なく動作します。

    返されるメモリバッファは「dma-coherent」です。場合によっては、メモリバリアを使用して一貫したメモリアクセスの順序を強制する必要があります。これはストリーミングDMAマッピングを使用していないため、IOMMUマッピングがI/Oで過剰に使用されるシステムでの小規模な転送に適しています。（「coherent」および「streaming」DMAマッピングの定義については 動的DMAマッピングガイド を参照してください。）

    ページの1/N分（およびNページの要求）を求めるのは空間効率が良いです。

    ほとんどのシステムでは、返されるメモリはキャッシュされていない状態になります。これは、dma-coherentメモリのセマンティクスがCPUキャッシュをバイパスするか、バススヌープをサポートするキャッシュハードウェアを使用する必要があるためです。x86ハードウェアではこのようなバススヌープがサポートされていますが、多くの他のシステムではソフトウェアでキャッシュラインをフラッシュしてDMAの競合を防ぐようにしています。

  • 一部のEHCIコントローラー上のデバイスは、DMAをhigh memoryとやり取りすることができました。

    残念ながら、現在のLinux DMAインフラストラクチャには、これらの機能を適切に公開する合理的な方法がありません…また、HIGHMEMは主にx86_32に特有の設計上の問題です。そのため、USBドライバにhighmemバッファを渡さないことが最善の選択です。これは簡単で、デフォルトの動作です。ただ、それを上書きしないようにしてください（例： NETIF_F_HIGHDMA.

    これにより、呼び出し元がhigh memoryから「通常の」DMAメモリにコピーするバウンスバッファリングを行う必要があるかもしれません。x86_32マシンで1GB以上メモリを持つ場合、この問題を改善する良い方法が見つかったら、パッチを送信してください。

既存のバッファの扱い¶

DMAに使用するには、まずデバイスのDMAアドレス空間にマッピングする必要があります。ただし、ドライバに渡されるほとんどのバッファは、このようなDMAマッピングで安全に使用できます。（『What memory is DMA-able?』（DMA可能メモリは何か？）というセクションを参照してください 動的DMAマッピングガイド）

  • スキャタリストリートを使用している場合、一度にすべてをマッピングできます。一部のシステムでは、これによりIOMMUが起動し、スキャタリストリートが単一のDMAトランザクションに変換されます：

    int usb_buffer_map_sg (struct usb_device *dev, unsigned pipe,
        struct scatterlist *sg, int nents);

void usb_buffer_dmasync_sg (struct usb_device *dev, unsigned pipe,
        struct scatterlist *sg, int n_hw_ents);

void usb_buffer_unmap_sg (struct usb_device *dev, unsigned pipe,
        struct scatterlist *sg, int n_hw_ents);

    スキャタリストリートでDMAを実行するよりも、新しい usb_sg_*() 関数呼び出しを使用する方が簡単です。これらはDMAマッピングを行い、スキャタリストリートI/Oを高速化する他の調整も行います。

  • 一部のドライバは、大容量バッファをマッピングし、安全に再利用するモデルを好む場合があります。（再利用がなければ、usbcoreにmap/unmapを任せましょう）大規模な周期的な転送はここで良い例です。なぜなら、バッファを同期する方が、毎回URBが完了するたびにアンマップし、再送信時にマッピングしなおすよりもコストが低いからです。

    これらの関数呼び出しは、初期化済みのURBと動作します： urb->dev, urb->pipe, urb->transfer_buffer, and urb->transfer_buffer_length これらが使用される際にはすべて有効でなければなりません（urb->setup_packet が制御リクエストのURBの場合でも有効です）：

    struct urb *usb_buffer_map (struct urb *urb);

void usb_buffer_dmasync (struct urb *urb);

void usb_buffer_unmap (struct urb *urb);

    これらの関数呼び出しは、 urb->transfer_dma を自動的に管理し、 URB_NO_TRANSFER_DMA_MAP を設定して、usbcoreがバッファをマッピングまたはアンマッピングしないようにします。これらは制御リクエストのsetup_packetバッファには使用できません。

いくつかのインターフェースは現在コメントアウトされています（現在のユーザーがいないため）。ソースコードを参照してください。dmasync関数呼び出し以外（その下にあるDMAプリミティブが変更されたため）、ほとんどのインターフェースは必要に応じてコメントアウトを解除できます。

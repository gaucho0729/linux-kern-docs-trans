MUSB Glue Layerの作成¶

著者

Apelete Seketeli

はじめに¶

Linux の MUSB サブシステムは、より大きな Linux USB サブシステムの一部です。これは、Universal Host Controller Interface (UHCI) または Open Host Controller Interface (OHCI) を使用しない埋め込み USB デバイスコントローラー (UDC) のサポートを提供します。

代わりに、これらの埋め込み UDC は USB On-the-Go (OTG) 標準に依存しており、少なくとも部分的にこの標準を実装しています。一般的なシリコンリファレンスデザインは、Mentor Graphics の Inventra™ デザインに含まれる Multipoint USB Highspeed Dual-Role Controller (MUSB HDRC) です。

自己学習のための練習として、Ingenic JZ4740 SoC 用の MUSB グリュー層を書きました。これは、カーネルソースツリー内の多くの MUSB グリュー層を模範としたものです。この層は以下にあります drivers/usb/musb/jz4740.c. このドキュメンテーションでは、 jz4740.c グリュー層の基本について説明し、自分のデバイスグリュー層を書くために必要なさまざまな要素と実施すべき手順を解説します。

Linux MUSB基礎¶

このトピックを始めるには、USB On-the-Go 基本事項 (リソースを参照) を読み、ハードウェアレベルでの USB OTG 操作の紹介を確認してください。Texas Instruments と Analog Devices のいくつかのウィキページも、Linux カーネル MUSB の構成についての概要を提供していますが、これらの会社が提供する特定のデバイスに焦点を当てています。最後に、USB ホームページで USB 標準に詳しくなれば、実際の例として Writing USB Device Drivers ドキュメンテーション（再度リソースを参照）が役立つかもしれません。

Linux USB スタックはレイヤードアーキテクチャであり、MUSB コントローラーハードウェアが最も下層に位置しています。MUSB コントローラードライバーは、Linux USB スタックに対して MUSB コントローラーハードウェアを抽象化します:

    ------------------------
    |                      | <------- drivers/usb/gadget
    | Linux USB Core Stack | <------- drivers/usb/host
    |                      | <------- drivers/usb/core
    ------------------------
               ⬍
   --------------------------
   |                        | <------ drivers/usb/musb/musb_gadget.c
   | MUSB Controller driver | <------ drivers/usb/musb/musb_host.c
   |                        | <------ drivers/usb/musb/musb_core.c
   --------------------------
               ⬍
---------------------------------
| MUSB Platform Specific Driver |
|                               | <-- drivers/usb/musb/jz4740.c
|       aka "Glue Layer"        |
---------------------------------
               ⬍
---------------------------------
|   MUSB Controller Hardware    |
---------------------------------

上記のように、グリュー層は実際にはコントローラードライバーとコントローラーハードウェアの間に位置するプラットフォーム固有のコードです。

Linux USB ドライバーが Linux USB サブシステムに自身を登録するのと同じように、MUSB グリュー層もまず MUSB コントローラードライバーに登録する必要があります。これにより、コントローラードライバーはグリュー層がサポートするデバイスを認識し、サポートされているデバイスが検出または解放されたときに呼び出す関数を把握できます。記憶してください、ここでの話題は埋め込みコントローラーチップなので、実行時での挿入や除去はありません。

すべての情報は、 platform_driver グリュー層で定義された構造体を通じて MUSB コントローラードライバーに渡されます:

static struct platform_driver jz4740_driver = {
    .probe      = jz4740_probe,
    .remove     = jz4740_remove,
    .driver     = {
        .name   = "musb-jz4740",
    },
};

プローブとリムーブ関数ポインタは、マッチングしたデバイスが検出されたときおよび解放されたときにそれぞれ呼ばれます。名前文字列は、このグルー層でサポートされるデバイスを記述します。現在のケースでは、このグルー層が宣言されたプラットフォームデバイス構造と一致します。 arch/mips/jz4740/platform.cここではデバイスツリーのバインディングを使用していません。

コントローラードライバーに自身を登録するためには、グルー層はいくつかのステップを経ます。基本的にはコントローラーハードウェアリソースを割り当て、いくつかの回路を初期化します。そのためには、これらのステップで使用される情報を追跡する必要があります。これはプライベートな jz4740_glue フィールドはRCU読み込み側クリティカルセクションのネストレベルを記録し、

struct jz4740_glue {
    struct device           *dev;
    struct platform_device  *musb;
    struct clk      *clk;
};

devとmusbメンバはどちらもデバイス構造変数です。前者は一般的なデバイス情報を持ち、基本的なデバイス構造であるため、後者はデバイスが登録されているサブシステムに密接に関連する情報を保持します。clk変数はデバイスクロック操作に関連する情報を保持します。

プローブ関数のステップを確認して、グルー層がコントローラードライバーに登録される流れを見てみましょう。

注意

読みやすさのため、各関数は論理的な部分に分割され、それぞれが他とは独立しているかのように表示されます。

static int jz4740_probe(struct platform_device *pdev)
{
    struct platform_device      *musb;
    struct jz4740_glue      *glue;
    struct clk                      *clk;
    int             ret;

    glue = devm_kzalloc(&pdev->dev, sizeof(*glue), GFP_KERNEL);
    if (!glue)
        return -ENOMEM;

    musb = platform_device_alloc("musb-hdrc", PLATFORM_DEVID_AUTO);
    if (!musb) {
        dev_err(&pdev->dev, "failed to allocate musb device\n");
        return -ENOMEM;
    }

    clk = devm_clk_get(&pdev->dev, "udc");
    if (IS_ERR(clk)) {
        dev_err(&pdev->dev, "failed to get clock\n");
        ret = PTR_ERR(clk);
        goto err_platform_device_put;
    }

    ret = clk_prepare_enable(clk);
    if (ret) {
        dev_err(&pdev->dev, "failed to enable clock\n");
        goto err_platform_device_put;
    }

    musb->dev.parent        = &pdev->dev;

    glue->dev           = &pdev->dev;
    glue->musb          = musb;
    glue->clk           = clk;

    return 0;

err_platform_device_put:
    platform_device_put(musb);
    return ret;
}

プローブ関数の最初のいくつかの行はグルー、musb、clk変数を割り当ておよび割り当てます。 GFP_KERNEL フラグ（行8）は割り当てプロセスでスリープし、メモリを待つことを許可するため、ロック状態でも使用可能です。 PLATFORM_DEVID_AUTO フラグ（行12）はデバイスIDの自動割り当てと管理を許可し、明示的なIDによるデバイス名空間の衝突を避けるためのものです。 devm_clk_get() （行18）でグルー層はクロックを割り当てます。この devm_ プレフィックスは clk_get() が管理されていることを示します。デバイスが解放されるときに自動的に割り当てられたクロックリソースデータを解放し、それを有効化します。

次に登録ステップが続きます：

static int jz4740_probe(struct platform_device *pdev)
{
    struct musb_hdrc_platform_data  *pdata = &jz4740_musb_platform_data;

    pdata->platform_ops     = &jz4740_musb_ops;

    platform_set_drvdata(pdev, glue);

    ret = platform_device_add_resources(musb, pdev->resource,
                        pdev->num_resources);
    if (ret) {
        dev_err(&pdev->dev, "failed to add resources\n");
        goto err_clk_disable;
    }

    ret = platform_device_add_data(musb, pdata, sizeof(*pdata));
    if (ret) {
        dev_err(&pdev->dev, "failed to add platform_data\n");
        goto err_clk_disable;

    return 0;

err_clk_disable:
    clk_disable_unprepare(clk);
err_platform_device_put:
    platform_device_put(musb);
    return ret;

最初のステップは、グルー層が保持しているデバイスデータをコントローラードライバーに通報することです。これは platform_set_drvdata() （行7）を通じて行われます。次に、デバイスリソース情報も、その時点でのプライベートな情報として platform_device_add_resources() （行9）を通じて通報します。

最後に、コントローラードライバーにプラットフォーム固有のデータを渡します（行16）。プラットフォームデータについては デバイスプラットフォームデータで説明しますが、ここでは platform_ops 関数ポインタ（行5）を musb_hdrc_platform_data 構造体（行3）内のものです。この関数ポインタは、MUSBコントローラードライバーがデバイス操作に呼び出すべき関数を示します：

static const struct musb_platform_ops jz4740_musb_ops = {
    .init       = jz4740_musb_init,

ここでは、コントローラードライバが必要に応じてのみinitおよびexit関数が呼び出される最小限のケースを示しています。事実、JZ4740 MUSBコントローラーは基本的なコントローラーであり、他のコントローラーに見られる一部の機能が欠如しているため、それ以外の場合は、電源管理関数やOTGモードと非OTGモードの切り替えを行う関数など、いくつかの他の関数へのポインタを持つことも考えられます。

IRQの処理¶

ここでは、glueレイヤーは関連するハードウェアレジスタを読み取り、コントローラー・ドライバにその値を渡す必要があります。コントローラー・ドライバが実際にIRQをトリガーしたイベントを処理します。

static irqreturn_t jz4740_musb_interrupt(int irq, void *__hci)
{
    unsigned long   flags;
    irqreturn_t     retval = IRQ_NONE;
    struct musb     *musb = __hci;

    spin_lock_irqsave(&musb->lock, flags);

    musb->int_usb = musb_readb(musb->mregs, MUSB_INTRUSB);
    musb->int_tx = musb_readw(musb->mregs, MUSB_INTRTX);
    musb->int_rx = musb_readw(musb->mregs, MUSB_INTRRX);

    /*
     * The controller is gadget only, the state of the host mode IRQ bits is
     * undefined. Mask them to make sure that the musb driver core will
     * never see them set
     */
    musb->int_usb &= MUSB_INTR_SUSPEND | MUSB_INTR_RESUME |
        MUSB_INTR_RESET | MUSB_INTR_SOF;

    if (musb->int_usb || musb->int_tx || musb->int_rx)
        retval = musb_interrupt(musb);

    spin_unlock_irqrestore(&musb->lock, flags);

    return retval;
}

デバイスプラットフォームデータ¶

MUSBグルー層を書くには、コントローラハードウェアのハードウェア能力を記述したデータが必要です。これをプラットフォームデータと呼びます。

プラットフォームデータはハードウェア固有ですが、幅広いデバイスをカバーする可能性があり、一般的には arch/ ディレクトリに存在します。これはデバイスアーキテクチャに応じて異なります。

例えば、JZ4740 SoCのプラットフォームデータは arch/mips/jz4740/platform.c。その中には platform.c ファイルに記述されています。JZ4740 SoCの各デバイスは、構造体のセットで記述されます。

ここに arch/mips/jz4740/platform.c が含むUSBデバイスコントローラ（UDC）に関する部分です：

/* USB Device Controller */
struct platform_device jz4740_udc_xceiv_device = {
    .name = "usb_phy_gen_xceiv",
    .id   = 0,
};

static struct resource jz4740_udc_resources[] = {
    [0] = {
        .start = JZ4740_UDC_BASE_ADDR,
        .end   = JZ4740_UDC_BASE_ADDR + 0x10000 - 1,
        .flags = IORESOURCE_MEM,
    },
    [1] = {
        .start = JZ4740_IRQ_UDC,
        .end   = JZ4740_IRQ_UDC,
        .flags = IORESOURCE_IRQ,
        .name  = "mc",
    },
};

struct platform_device jz4740_udc_device = {
    .name = "musb-jz4740",
    .id   = -1,
    .dev  = {
        .dma_mask          = &jz4740_udc_device.dev.coherent_dma_mask,
        .coherent_dma_mask = DMA_BIT_MASK(32),
    },
    .num_resources = ARRAY_SIZE(jz4740_udc_resources),
    .resource      = jz4740_udc_resources,

以下の jz4740_udc_xceiv_device プラットフォームデバイス構造（2行）は、UDCトランシーバーの名前とID番号でUDCトランシーバーを記述します。

執筆時点では、 usb_phy_gen_xceiv は、組み込みの参照USBIPまたは自律的なトランシーバー（PHYプログラミングを必要としない）に使用するための特定の名前です。対応するトランシーバードライバーを使用するには、 CONFIG_NOP_USB_XCEIV=y をカーネル構成に設定する必要があります。idフィールドは-1（ PLATFORM_DEVID_NONEに相当）または-2（ PLATFORM_DEVID_AUTOに相当）を設定するか、この種の最初のデバイスに0から始めて特定のID番号を割り当てることもできます。

以下の jz4740_udc_resources リソース構造（7行）はUDCレジスタベースアドレスを定義します。

最初の配列（9行から11行）はUDCレジスタベースメモリアドレスを定義します：startは最初のレジスタメモリアドレスを、endは最後のレジスタメモリアドレスを、flagsメンバは処理しているリソースの種類を示します。そのため IORESOURCE_MEM はレジスタメモリアドレスを定義するために使用されます。2番目の配列（行14〜17）はUDC IRQレジスタアドレスを定義します。JZ4740 UDCには1つのIRQレジスタのみが利用可能なので、startとendは同じアドレスを指します。The IORESOURCE_IRQ フラグはIRQリソースを扱っていることを示しており、name mc は実際にはMUSBコア内でハードコードされており、コントローラードライバーがこのIRQリソースを名前で照合して取得できるようにしています。

で行われます。コントローラーハードウェアのOTG機能を定義する際、multipointメンバ（行3）は0（つまりfalseに相当）に設定されています。JZ4740 UDCはOTG互換ではありませんので、このように設定しています。次に num_eps （行5）はコントローラーハードウェアのUSBエンドポイント数を定義します（エンドポイント0を含む）。ここでは3つのエンドポイント＋エンドポイント0があります。次に ram_bits （行7）はMUSBコントローラーハードウェアのRAMアドレスバス幅を示します。コントローラードライバーが関連するコントローラーハードウェアレジスタを読み取ることでエンドポイントを自動的に設定できない場合にこの情報が必要です。この問題については後述の デバイスの特殊な挙動で詳しく説明します。最後の2つのフィールド（行8と9）もデバイスクイックに関するものです： fifo_cfg はUSBエンドポイント構成テーブルを指し、 fifo_cfg_size はその構成テーブル内のエントリ数のサイズを記録しています。この点については後述の デバイスの特殊な挙動.

で詳しく説明します。この設定はその後 jz4740_musb_platform_data musb_hdrc_platform_data 構造体（行11）：configは構造体自体へのポインタであり、modeはコントローラードライバーにコントローラーハードウェアがどのように使用可能かを伝える情報です。 MUSB_HOST のみ、 MUSB_PERIPHERAL のみ、または MUSB_OTG これはデュアルモードです。

ご注意ください。 jz4740_musb_platform_data は、プローブ関数で見たようにプラットフォームデータ情報を伝達するために使用されます。 Linux MUSB基礎.

デバイスの特殊な挙動¶

デバイス固有のプラットフォームデータを完了する際には、USB On-the-Go仕様の実装が不完全だったり、ハードウェアのバグによって生じるデバイス固有の制限を回避するため、グルーブレイヤーで一部のコードを書く必要があるかもしれません。これらのクイックは、ハードウェアのバグが原因だったり、単にUSB On-the-Go仕様の実装が不完全だったりする可能性があります。

JZ4740 UDCはこのようなクイックを示しており、これらについて洞察のためここに説明しますが、実際に使用しているコントローラーハードウェアには含まれていない可能性もあります。

では、最初に初期化関数に戻りましょう：

static int jz4740_musb_init(struct musb *musb)
{
    musb->xceiv = usb_get_phy(USB_PHY_TYPE_USB2);
    if (!musb->xceiv) {
        pr_err("HS UDC: no transceiver configured\n");
        return -ENODEV;
    }

    /* Silicon does not implement ConfigData register.
     * Set dyn_fifo to avoid reading EP config from hardware.
     */
    musb->dyn_fifo = true;

    musb->isr = jz4740_musb_interrupt;

    return 0;
}

行12の指示は、コントローラーハードウェアにUSBエンドポイントの設定に使用されるレジスタが欠如しているという事実を回避するため、MUSBコントローラードライバーに役立ちます。

これらのレジスタがないため、コントローラードライバーはハードウェアからエンドポイントの設定を読み取ることができません。そのため、行12の指示を使用してシリコンから設定を読み取るのを回避し、代わりにエンドポイントの設定を記述したハードコーディングされたテーブルに依存します：

static struct musb_fifo_cfg jz4740_musb_fifo_cfg[] = {
    { .hw_ep_num = 1, .style = FIFO_TX, .maxpacket = 512, },
    { .hw_ep_num = 1, .style = FIFO_RX, .maxpacket = 512, },
    { .hw_ep_num = 2, .style = FIFO_TX, .maxpacket = 64, },
};

上記の構成テーブルを見てみると、各エンドポイントは3つのフィールドで記述されています： hw_ep_num はエンドポイント番号、styleは方向（コントローラードライバーがコントローラーハードウェアでパケットを送信するための FIFO_TX 、またはハードウェアからパケットを受信するための FIFO_RX ）、maxpacketはそのエンドポイントを介して送信可能な各データパケットの最大サイズを定義します。テーブルから読み取ると、コントローラードライバーはエンドポイント1が512バイトのUSBデータパケットを一度に送信および受信可能であることを知り（これは実際にはバースト入出力エンドポイントです）、エンドポイント2が64バイトのデータパケットを一度に送信可能であることを知ります（これは実際には割込みエンドポイントです）。

エンドポイント0に関する情報はここにはありません。これはすべてのシリコン設計でデフォルトで実装されており、USB仕様に基づいた事前に設定された構成が適用されます。エンドポイント構成テーブルの他の例については、 musb_core.c.

では、中断ハンドラ関数に戻りましょう：

static irqreturn_t jz4740_musb_interrupt(int irq, void *__hci)
{
    unsigned long   flags;
    irqreturn_t     retval = IRQ_NONE;
    struct musb     *musb = __hci;

    spin_lock_irqsave(&musb->lock, flags);

    musb->int_usb = musb_readb(musb->mregs, MUSB_INTRUSB);
    musb->int_tx = musb_readw(musb->mregs, MUSB_INTRTX);
    musb->int_rx = musb_readw(musb->mregs, MUSB_INTRRX);

    /*
     * The controller is gadget only, the state of the host mode IRQ bits is
     * undefined. Mask them to make sure that the musb driver core will
     * never see them set
     */
    musb->int_usb &= MUSB_INTR_SUSPEND | MUSB_INTR_RESUME |
        MUSB_INTR_RESET | MUSB_INTR_SOF;

    if (musb->int_usb || musb->int_tx || musb->int_rx)
        retval = musb_interrupt(musb);

    spin_unlock_irqrestore(&musb->lock, flags);

    return retval;
}

行18の指示は、USBホストモード操作に使用される割込みビットがシリコンに存在しないという事実を回避するため、コントローラードライバーが使用する方法です。 MUSB_INTRUSB 登録後、ハードウェア状態が未定義のままとなり、このMUSBコントローラーはペリフェラルモードのみで使用されるため、この状態は定義されていません。その結果、グルー層はこれらの欠損しているビットを論理積（AND）演算により読み取った値と実際に実装されているビットを比較することで、寄生割込みを防ぐようにマスク処理を行います。 MUSB_INTRUSB これらのビットは、登録から実際に実装されているビットと論理積（AND）演算により、寄生割込みを防ぐようにマスク処理を行います。

これらはJZ4740 USBデバイスコントローラーに見られる特異な挙動の一部にすぎません。他のいくつかの問題は、MUSBコアで直接対応されており、修正が汎用性が高く、他のコントローラーのハードウェアにも適用可能なため、より効果的な問題解決が可能になりました。

結論¶

Linux MUSBグルー層の実装は、このドキュメンテーションがこの作業の詳細を示すことでよりアクセスしやすいタスクになるでしょう。

JZ4740 USBデバイスコントローラーは比較的シンプルな設計であるため、このグルー層が探究心のある人にとって良い例になることを願っています。現在のMUSBグルー層と併用することで、このドキュメンテーションは開始するための十分なガイドを提供します。何か問題が発生した場合は、linux-usbメーリングリストアーカイブを参照すると役立ちます。

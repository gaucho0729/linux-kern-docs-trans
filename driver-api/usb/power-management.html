電源管理とは？¶

電源管理（PM）とは、コンピュータシステムの一部を使用していないときに停止させてエネルギーを節約する技術です。コンポーネントが suspended 非機能的な低電力状態にあり、完全にオフになることもあります。停止中のコンポーネントは、 resumed （カーネルが必要なときに機能するフル電力状態に戻すことができます）。（また、コンポーネントを停止状態からではなく、一部の機能を維持しながら使用可能な状態に置く形式のPMもあります。例えばCPUのクロック周波数を減らすなどです。このドキュメントではその他の形式については議論しません。）

CPUとシステムの大部分を停止する場合、これを「システムスリープ」と呼びます。システム全体が稼働している間、特定のデバイスがオフになる場合、これを「ダイナミックスリープ」（または「ランタイムスリープ」「選択的スリープ」とも呼ばれます）と呼びます。このドキュメントは主にダイナミックPMがUSBサブシステムでどのように実装されるかに焦点を当てていますが、システムPMについてはある程度扱っています（ Documentation/power/*.rst を参照してください。システムPMについての詳細情報については、

システムPMのサポートは、カーネルが CONFIG_SUSPEND または CONFIG_HIBERNATION が有効になっている場合にのみ存在します。USBのダイナミックPMサポート

は、カーネルが CONFIG_PM 有効にされています。

[歴史的に、USBのダイナミックPMサポートは、カーネルが CONFIG_USB_SUSPEND が有効になっている（これは CONFIG_PM_RUNTIMEに依存していました）場合にのみ存在しました。3.10カーネルリリース以降、USBのダイナミックPMサポートは、カーネルが CONFIG_PM_RUNTIME が有効になっている場合にのみ存在します。 CONFIG_USB_SUSPEND オプションは廃止されました。]

リモートウェイクアップとは？¶

デバイスが停止している場合、通常はコンピュータが指示するまで再開しません。同様に、全体が停止しているコンピュータも、ユーザーが電源ボタンを押すなどして指示するまで再開しません。

ただし、一部のデバイスは自動的に再開する能力や、カーネルに再開を依頼する能力、あるいは全体のコンピュータに再開を通知する能力を持っています。このような能力は「Wake On LAN」などと呼ばれることがありますが、ここでは一般的に「リモートウェイクアップ」と呼びます。リモートウェイクアップが有効なデバイスが停止している場合、外部イベントに応じて自動的に再開する（または再開を依頼する）ことができます。例えば、キーボードが停止している状態でキーが押されると再開する、またはUSBハブが停止している状態でデバイスが挿さると再開するなどです。

USBデバイスがアイドル状態になるのはいつ？¶

カーネルが重要な作業を行っていないと判断したデバイスは、アイドル状態にあるとみなされ、スリープ候補となる。正確な定義はデバイスのドライバに依存するが、ドライバは実際の通信が行われていない場合でもデバイスがアイドル状態でないことを宣言できる。例えば、ハブはそのハブに接続されたすべてのデバイスがすでにスリープしている場合に限りアイドル状態とみなされる。さらに、プログラムがusbfsファイルを開いている限り、デバイスはアイドル状態とみなされない。

USBデバイスにドライバがなく、usbfsファイルが開いておらず、sysfs経由でアクセスされていない場合、デバイスは確実にアイドル状態にある。

動的PMの形式¶

カーネルがアイドル状態のデバイスをスリープさせる場合、これは autosuspend と呼ばれる。一般的に、デバイスが一定期間のアイドル状態を経た後でなければ、自動スリープ（autosuspend）されない。この期間を「アイドル遅延時間（idle-delay time）」と呼ぶ。

もちろん、カーネルが自らの判断で行う操作は、コンピュータやそのデバイスの正常な動作を妨げてはならない。デバイスが自動スリープされ、プログラムがそれを使用しようとすると、カーネルが自動的にデバイスを再開する（autoresume）。同様の理由から、自動スリープ中のデバイスは、リモートウェイクアップをサポートしている場合、通常リモートウェイクアップが有効になっている。

多くのUSBドライバが自動スリープをサポートしていない点を強調しておく。実際、この執筆時点（Linux 2.6.23）では、サポートしているドライバはハブドライバ、kaweth、asix、usblp、usblcd、usb-skeleton（これはカウントしない）のみである。サポートしていないドライバがデバイスにバインドされている場合、そのデバイスは自動スリープされない。実質的に、カーネルはそのデバイスが常にアイドル状態でないと仮定する。

電源管理イベントは大きく分けて外部イベントと内部イベントの2つのクラスに分類できる。外部イベントはUSBスタックの外側からトリガーされるイベントで、システムのスリープ/再開（ユーザー空間からトリガー）、手動による動的再開（ユーザー空間からトリガー）、リモートウェイクアップ（デバイスからトリガー）が該当する。内部イベントはUSBスタック内でトリガーされるイベントで、自動スリープと自動再開が含まれる。注意点として、すべての動的スリープイベントは内部イベントであり、外部エージェントが動的スリープを発行することは許可されていない。

動的PMのユーザーインターフェース¶

動的電源管理（PM）を制御するユーザーインターフェースは、各USBデバイスのsysfsディレクトリの power/ サブディレクトリに位置する。つまり、 /sys/bus/usb/devices/.../power/ の場所にある。ここで「…」はデバイスのIDを表す。関連する属性ファイルは：wakeup、control、および autosuspend_delay_ms。（また、ファイル名が levelという名前のファイルも存在する可能性があるが、これは2.6.35カーネル以降で非推奨となり、 control ファイルに置き換えられた。2.6.38では autosuspend ファイルは非推奨となり、 autosuspend_delay_ms ファイルに置き換えられます。違いは、新しいファイルがミリ秒単位で遅延を表し、古いファイルは秒単位で表している点です。混乱を招くかもしれませんが、2.6.37では両方のファイルが存在しますが、のみ autosuspend 動作します。)

power/wakeup

デバイスがリモートウェイクアップをサポートしない場合、このファイルは空です。サポートしている場合は、このファイルに「 enabled 」または「 disabled」という単語が含まれており、これらの単語をファイルに書き込むことができます。設定により、デバイスが次にスリープ状態になったときにリモートウェイクアップが有効になるかどうかが決まります。(デバイスがスリープ中で設定を変更しても、次のスリープ時に変更が反映されます。)

power/control

このファイルには2つの単語のうちの1つが含まれています： on または auto。この単語をファイルに書き込むことで、デバイスの設定を変更できます。

  • on はデバイスが再開され、オートスリープが許可されないことを意味します。(もちろん、システムのスリープは依然として許可されます。)

  • auto は、カーネルがデバイスのオートスリープとオートリスローを許可する通常の状態です。

(2.6.32までのカーネルでは、「 suspend」を指定することもでき、これはデバイスがスリープ状態のままとなり、オートリスローが許可されないことを意味します。この設定はもはやサポートされていません。)

power/autosuspend_delay_ms

このファイルには、デバイスがオートスリープされるまでのアイドル時間（idle-delay時間）を表す整数値が含まれています。デフォルトは2000ミリ秒です。0はデバイスがアイドル状態になった直ちにオートスリープを開始し、負の値はオートスリープを決して行わないことを意味します。ファイルに数値を書き込むことで、オートスリープのアイドル時間（idle-delay時間）を変更できます。

書き込み -1 に（木の下から葉に向かって） power/autosuspend_delay_ms および「 on に（木の下から葉に向かって） power/control 」は基本的に同じ動作をします – どちらもデバイスがオートスリープされないようにします。はい、これはAPIの冗長性です。

(2.6.21では「 0 に（木の下から葉に向かって） power/autosuspend 」を書き込むことでデバイスがオートスリープされなくなりましたが、2.6.22で動作が変更されました。属性「 power/autosuspend 」は2.6.21以前には存在せず、属性「 power/level 」は2.6.22以前には存在しませんでした。 power/control は2.6.34で追加され、 power/autosuspend_delay_ms は2.6.37で追加されましたが、2.6.38になってから機能しました。)

デフォルトのアイドル遅延時間の変更¶

デフォルトのオートスリープアイドル時間（秒単位）は、usbcoreモジュールのパラメータで制御されます。usbcoreをロードする際に値を指定できます。たとえば、2秒から5秒に変更するには以下のようにします：

modprobe usbcore autosuspend=5

同様に、/etc/modprobe.dにある設定ファイルに以下のように追加することもできます：

options usbcore autosuspend=5

一部のディストリビューションでは、ブートプロセスの初期段階でinitramfsイメージから実行されるスクリプトやプログラムを通じてusbcoreモジュールを非常に早くロードします。パラメータ値を変更するには、そのイメージを再構築する必要があります。

usbcoreがカーネルに組み込まれている場合（ロード可能なモジュールとしてではなく）、以下のように追加できます：

usbcore.autosuspend=5

カーネルのブートコマンドラインに

最後に、システムが起動している間でもパラメータ値を変更できます。以下のように行うと:

echo 5 >/sys/module/usbcore/parameters/autosuspend

新しいUSBデバイスはすべて、自動スリープのアイドル遅延を5に初期化されます。(既に存在するデバイスのアイドル遅延値は影響を受けません。)

初期デフォルトのアイドル遅延を-1に設定すると、すべてのUSBデバイスの自動スリープを防ぐことができます。これにより、選択したデバイスに対して自動スリープを有効にすることができます。

警告¶

USB仕様では、すべてのUSBデバイスが電源管理をサポートしなければならないと規定されています。しかし、残念なことに多くのデバイスがこれに十分対応していないのが現状です。これらを一時的にスリープさせることはできますが、再開しようとするとUSBバスから切断されたり、完全に動作しなくなることがあります。これは特にプリンタやスキャナに見られる傾向ですが、他の種類のデバイスにも同様の問題があります。

このため、カーネルはデフォルトでは自動スリープを無効にします（ power/control 属性が初期化されます on）。ホストは少なくともこの点では比較的適切に動作するようです。

(2.6.21および2.6.22ではこのようにはなりませんでした。ほぼすべてのUSBデバイスで自動スリープがデフォルトで有効になっていました。その結果、多くの人が問題を経験しました。)

これは、ホスト以外のデバイスが自動スリープされるのはユーザーまたはプログラムが明示的に有効にした場合に限られます。執筆時点ではこのような動作を行う汎用的なプログラムは存在せず、今後HALなどのデバイスマネージャーがこの責任を引き受けることを期待しています。その間は手動で操作を行うか、udevスクリプトに追加することで対応可能です。アイドル遅延時間も変更可能です。2秒はすべてのデバイスにとって最適な選択ではありません。

ドライバーがそのデバイスが適切なスリープ/再開サポートを持っていることを知っている場合、自動スリープを自動的に有効にすることができます。たとえば、ノートPCのウェブカメラのビデオドライバーはこれを行うかもしれません（最近のカーネルではそうしています）。これらのデバイスはあまり使用されないため、通常は自動スリープされるべきです。

場合によっては、デバイスがオートスリープ機能で正常に動作するにもかかわらず、依然として問題が発生することがあります。たとえば、キーボードやマウスを管理するusbhidドライバーはオートスリープをサポートしています。複数のキーボードをテストした結果、スリープ状態のキーボードで入力を行うと、キーボードがリモートウェイクアップを適切に行うものの、頻繁にキーストロークが失われる現象が確認されました。マウスのテストでは、一部のマウスはボタン押下時にリモートウェイクアップリクエストを送るが、動きに対しては送らない場合があり、一部はどちらにも反応しない場合もあります。

カーネルは、オートスリープをサポートできないデバイスでも有効化を防ぐことはしません。理論上、適切なタイミングでスリープさせることでデバイスを破損させる可能性もあります。(非常にまれですが、あり得ます。) 注意が必要です。

電源管理用ドライバインターフェース¶

USBドライバーが外部電源管理をサポートするための要件は比較的控えめです。ドライバーは以下のメソッドを定義するだけで十分です：

.suspend
.resume
.reset_resume

構造体の usb_driver メソッド、および reset_resume メソッドはオプションです。メソッドの役割は非常に単純です：

  • 以下の suspend メソッドは、ドライバにデバイスがスリープ状態になることを通知するため呼び出されます。ドライバが負のエラーコードを返すと、スリープ処理が中止されます。通常はドライバが0を返すため、その場合、ドライバはすべての未完了のURB（usb_kill_urb()）をキャンセルし、これ以上送信しない必要があります。

  • 以下の resume メソッドは、ドライバにデバイスが再開され、通常の動作に戻ったことを通知するため呼び出されます。これ以降、URBを再び送信できます。

  • 以下の reset_resume メソッドは、ドライバにデバイスが再開され、リセットされたことを通知するため呼び出されます。ドライバはデバイスが以前のスリープ前の状態をほぼ失っている可能性があるため、必要な初期化を再実行する必要があります（インターフェースは以前と同じaltsettingsを維持している可能性があります）。

デバイスがスリープ状態のまま切断または電源を切られた場合、 disconnect メソッドが呼ばれる代わりに resume または reset_resume メソッドが呼ばれます。これは、ハibernationから目覚める際にも起こりやすいです。多くのシステムでは、ハibernation中にUSBホストコントローラーへのスリープ電流を維持しないからです。(USB Persist機能を使用することで、ハibernationによる強制切断の問題を回避できます。)

以下の reset_resume メソッドはUSB Persist機能（参照： システムスリープ時のUSBデバイスの永続性）で使用され、また CONFIG_USB_PERSIST が有効でない特定の状況でも使用可能です。現在、デバイスが再開中にリセットされ、ドライバが reset_resume メソッドを持っていない場合、ドライバは再開に関する通知を受けることができません。後続のカーネルではドライバの disconnect メソッドを呼び出しますが、2.6.23ではこの処理は行われません。

USBドライバーはインターフェースにバインドされるため、その suspend および resume インターフェースが一時停止または再開されるときに呼び出されるメソッドです。原則として、デバイスの一部のインターフェースを一時停止する（つまり、そのインターフェースのドライバがすべてのアクティビティを停止させる）一方で他のインターフェースを一時停止しないという状況を望むことはあります。しかし、USBコアはこのような動作を許可していません。デバイス自体が一時停止されるときにすべてのインターフェースが一時停止され、デバイスが再開されるときにすべてのインターフェースが再開されます。デバイスの一部のインターフェースだけを一時停止または再開することはできません。最も近い対応は、インターフェースのドライバをアンバインドするという方法です。

オートスリープとオートリザーブ用ドライバインターフェース¶

オートスリープとオートリザーブをサポートするためには、上記の3つのメソッドすべてを実装する必要があります。さらに、ドライバがオートスリープをサポートしていることを示すために、そのusb_driver構造体に .supports_autosuspend フラグを設定します。その後、ドライバは、自身のインターフェースがビジー（忙しい）状態またはアイドル（空闲）状態になったときにUSBコアに通知する責任があります。ドライバは、以下の6つの関数を呼び出すことでこれを実現します：

int  usb_autopm_get_interface(struct usb_interface *intf);
void usb_autopm_put_interface(struct usb_interface *intf);
int  usb_autopm_get_interface_async(struct usb_interface *intf);
void usb_autopm_put_interface_async(struct usb_interface *intf);
void usb_autopm_get_interface_no_resume(struct usb_interface *intf);
void usb_autopm_put_interface_no_suspend(struct usb_interface *intf);

これらの関数は、usb_interfaceの埋め込まれたデバイス構造体に使用カウンタを保持することで動作します。使用カウンタが0より大きい場合、インターフェースはビジー状態とみなされ、カーネルはインターフェースのデバイスを自動的に一時停止しません。使用カウンタが0の場合、インターフェースはアイドル状態とみなされ、カーネルがデバイスを自動的に一時停止できるようになります。

ドライバは、使用カウンタへの変更を全体的にバランスよく行う必要があります。ドライバがアンバインドされるときに、アンバランスな「get」操作が残ると、インターフェースが再度ドライバにバインドされた場合でもデバイスがランタイムスリープ状態に移行できなくなります。一方で、ドライバは、自身の usb_autopm_* ルーチンが戻った後でも、ワークキュー処理など内部で呼び出すことができます。ただし、インターフェースに有効な参照を保持している必要があります（経由して disconnect インターフェースへのアクティブな参照を保持しています）。 usb_get_intf および usb_put_intf).

非同期ルーチンを使用するドライバは、自身で同期と相互排他を管理する責任があります。

usb_autopm_get_interface() 使用カウンタをインクリメントし、デバイスが一時停止されている場合に自動的に再開します。自動再開に失敗した場合は、カウンタを再び減算します。

usb_autopm_put_interface() 使用カウンタをデクリメントし、新しい値が0になった場合に自動的に一時停止を試みます。

usb_autopm_get_interface_async() および usb_autopm_put_interface_async() 非同期 counterparts とほぼ同じ動作を行います。大きな違いは、再開または一時停止の処理をワークキューを使用して行うことです。その結果、URBの完了ハンドラなどのアトミックコンテキストで呼び出すことができますが、戻るときにはデバイスがまだ望ましい状態にないことが一般的です。

usb_autopm_get_interface_no_resume() および usb_autopm_put_interface_no_suspend() 使用カウンターを単にインクリメントまたはデクリメントするだけであり、オートリザーブやオートスリープを実行しようとはしません。そのため、アトミックコンテキストで呼び出すことができます。

最も簡単な使用パターンは、ドライバーが usb_autopm_get_interface() オープンルーチンおよび usb_autopm_put_interface() クローズまたはリリースルーチンで呼び出すことです。ただし、他のパターンも可能です。

上記のオートスリープ試行は、多くの場合、何かしらの理由で失敗します。たとえば、 power/control 属性が onに設定されている可能性があります。または、同じデバイス内の他のインターフェースがアイドル状態でない可能性があります。これは完全に正常なことです。失敗の理由がデバイスが十分にアイドル状態でなかった場合、タイマーがオートスリープアイドル遅延が経過したときに自動的に操作を実行します。

オートリザーブ試行も失敗することがあります。ただし、失敗はデバイスがもう存在しないか、正しく動作していないことを意味します。オートスリープとは異なり、オートリザーブにはアイドル遅延がありません。

ドライバインターフェースのその他の部分¶

ドライバーは、デバイスのオートスリープを有効にするために次のルーチンを呼び出します：

usb_enable_autosuspend(struct usb_device *udev);

彼らの probe() ルーチンを呼び出すことで、ドライバーがデバイスが正しくスリープおよび再開できることがわかっている場合です。これは、デバイスの auto 属性に値を書き込むことと完全に同等です。同様に、ドライバーは次のルーチンを呼び出すことでオートスリープを無効にできます： power/control これは、属性に値を書き込むことと完全に同等です。

usb_disable_autosuspend(struct usb_device *udev);

これは、属性に値を書き込むことと完全に同等です。 on から power/control 属性。

ドライバーは、オートスリープ中にリモートウェイクアップが有効になっていることを確認する必要があります。たとえば、ユーザーがキーボードをタイプすることでリモートウェイクアップを引き起こすことができない場合、オートスリープする意味はありません。ドライバーが intf->needs_remote_wakeup に1を設定すると、リモートウェイクアップが利用できない場合、カーネルがデバイスをオートスリープさせません。(ただし、デバイスがすでにオートスリープしている場合、このフラグを設定してもカーネルがオートリザーブを実行するわけではありません。通常、ドライバーはこのフラグを自身の probe メソッドで設定します。その時点で、デバイスがオートスリープされていないことが保証されます。)

ドライバーが割込みコンテキストでI/Oを非同期に実行する場合、 usb_autopm_get_interface_async() 出力開始前に呼び出さなければなりません。 usb_autopm_put_interface_async() 出力キューが空になるときに呼び出さなければなりません。入力イベントを受信した場合、

usb_mark_last_busy(struct usb_device *udev);

イベントハンドラ内で呼び出さなければなりません。これにより、PMコアにデバイスが先ほどまで忙しかったことを伝え、次のオートスリープアイドル遅延の期限を延期する必要があります。多くのusb_autopm_*ルーチンもこの呼び出しを行いますので、ドライバーは割込み駆動の入力が到達した場合のみ心配する必要があります。

非同期操作は常に競合条件に巻き込まれます。たとえば、ドライバーが usb_autopm_get_interface_async() ルーチンを呼び出すタイミングが、コアがデバイスが十分にアイドル状態だったと判断したところですが、まだドライバーの suspend メソッドを呼び出しているところです。 suspend メソッドは、I/OリクエストルーチンとURB完了ハンドラとを同期させる責任があり、ドライバがデバイスを使用する必要がある場合、自動スリープを-EBUSYで失敗させるべきです。

外部スリープ呼び出しは、このように失敗してはならない。自動スリープ呼び出しのみが例外です。ドライバは、メッセージ引数にマクロを適用することで、これらを区別できます。 PMSG_IS_AUTO() マクロをメッセージ引数に適用する suspend メソッドに適用します。これは内部PMイベント（自動スリープ）に対してTrueを、外部PMイベントに対してFalseを返します。

相互排他¶

外部イベントの場合、自動スリープまたは自動再開に関係なく、デバイスセマフォ（udev->dev.sem）が呼び出し時に保持されます。これは外部スリープ/再開イベントが、 suspend または resume メソッド呼び出しと排他的であることを意味します。USBコアは、自動スリープ/自動再開イベントにも同様にこのことが保証されています。 probe, disconnect, pre_reset, and post_reset；USBコアは、自動スリープ/自動再開イベントにも同様にこのことが保証されています。

ドライバがクリティカルセクション中にすべてのスリープ/再開呼び出しをブロックしたい場合、デバイスをロックし、 usb_autopm_get_interface() を呼び出すのが最善です（クリティカルセクション終了時に逆の操作を行う）。デバイスセマフォを保持することで、すべての外部PM呼び出しをブロックし、 usb_autopm_get_interface() は、すら失敗しても内部PM呼び出しを防ぎます。（演習：なぜ？）

動的PMとシステムPMの相互作用¶

ダイナミック電源管理とシステム電源管理は複数の方法で相互作用します。

まず、システムスリープが発生する際、デバイスがすでに自動スリープしている可能性があります。システムスリープはなるべく透明であるべきですが、システム再開後にデバイスがスリープしたままになるべきです。しかし実際にはこの理論がうまく機能しない場合があります。2.6.37以降、システム再開時にすべてのデバイスを再開し、それ以降はデバイス自身がランタイムスリープを処理するというポリシーが採用されています。

次に、システムスリープが進行中にダイナミック電源管理イベントが発生する可能性があります。この時間枠は短く、システムスリープは通常数秒程度しかかかりませんが、発生する場合があります。たとえば、スリープ中のデバイスがシステムスリープ中にリモートウェイクアップ信号を送信するかもしれません。リモートウェイクアップが成功すると、システムスリープが中止されます。リモートウェイクアップが失敗した場合でも、デバイスがアクティブなまま残っている可能性があり、システムスリープが完了した直後にシステムが再開されるかもしれません。リモートウェイクアップが失敗して信号が消失する場合もあります。どの結果が発生するかはタイミングやハードウェア、ファームウェアの設計に依存します。

xHCIハードウェアリンクPM¶

xHCIホストコントローラーは、USB2.0（xHCI 1.0の機能）およびリンクPMをサポートするUSB3.0デバイスにハードウェアリンク電源管理を提供します。ハードウェアLPMを有効にすると、ホストがデバイスを低電力状態（USB2.0デバイスではL1、USB3.0デバイスではU1/U2）に自動的に移行させることができ、この状態ではデバイスが非常に速く再起動できます。

ハードウェアLPMを制御するユーザーインターフェースは power/ サブディレクトリに位置する。つまり、 /sys/bus/usb/devices/.../power/ にあります。ここで「…」はデバイスのIDです。関連する属性ファイルは usb2_hardware_lpm および usb3_hardware_lpm.

power/usb2_hardware_lpm

USB2.0デバイスがLPMをサポートしており、xHCIホストルートハブがソフトウェアLPMをサポートしている場合、ホストはそのデバイスに対してソフトウェアLPMテストを実行します。デバイスがL1状態に移行し再起動に成功し、ホストがUSB2.0ハードウェアLPMをサポートしている場合、このファイルが表示され、ドライバーがデバイスにハードウェアLPMを有効にします。このファイルにy/Y/1またはn/N/0を書き込むことで、USB2.0ハードウェアLPMを手動で有効/無効にできます。これは主にテスト目的です。

power/usb3_hardware_lpm_u1 power/usb3_hardware_lpm_u2

USB3.0 LPMをサポートするデバイスがxHCIホストに接続され、ホストがリンクPMをサポートしている場合、BOSディスクリプターにU1およびU2の待機遅延が設定されているかを確認します。確認が成功し、ホストがUSB3.0ハードウェアLPMをサポートしている場合、USB3.0ハードウェアLPMがデバイスに有効になり、これらのファイルが作成されます。これらのファイルは、USB3.0ハードウェアLPM U1またはU2がデバイスに有効かどうかを示す文字列値（enableまたはdisable）を保持しています。

USBポート電源制御¶

エンドポイントデバイスのスリープとハードウェア制御されたリンク電源管理の有効化に加え、USBサブシステムは特定の条件下でポートの電源を無効にする機能も持っています。電源制御は Set/ClearPortFeature(PORT_POWER) ホストのリクエストを通じてハブに行われます。ルートまたはプラットフォーム内部のハブの場合、ホストコントローラードライバーは PORT_POWER リクエストをプラットフォームファームウェア（ACPI）メソッド呼び出しに変換し、ポートの電源状態を設定します。詳細については、Linux Plumbers Conference 2012のスライド 1 および動画 2:

を参照してください。リクエストを受信した ClearPortFeature(PORT_POWER) ポートは論理的にオフになり、ポートのVBUSの実際の喪失を引き起こす可能性があります。 3VBUSは、ハブが複数のポートを共有電源ウェルにグループ化し、すべてのポートがオフになるまで電源を維持する場合、または充電アプリケーションに設定されたハブポートによって維持される場合があります。いずれにしても、論理的にオフのポートはデバイスとの接続を失い、ホットプラグイベントやリモートウェイクアップイベントに応答しなくなります。

警告

ポートをオフにすると、デバイスをホットアドドすることができなくなる可能性があります。詳細については、「ポート電源制御のユーザーインターフェース」を参照してください。

デバイス自体への影響については、システムスリープ中にデバイスが経験するものと同様です。つまり、電源セッションが失われる状態になります。システムスリープ中にUSBデバイスやドライバーが不適切に動作する場合、ポート電源サイクルイベントによって同様に影響を受けることになります。このため、実装はハブのシステム再開処理と同様のデバイス回復処理（および同じクイック）を実行します。

ポート電源制御用ユーザーインターフェース¶

ポート電源制御メカニズムはPMランタイムシステムを使用します。電源を切る要求はポートデバイスの power/pm_qos_no_power_off フラグをクリアすることで行われます（デフォルトでは1）。ポートが切断されている場合、すぐに ClearPortFeature(PORT_POWER) リクエストが届きます。それ以外の場合は、PMランタイムルールに従い、接続されている子デバイスおよびそのすべての子孫をスリープ状態にします。このメカニズムは、ハブ記述子でポート電源スイッチングをアドバタイズしている（wHubCharacteristics論理電源スイッチングモードフィールド）ハブに依存します。

注意: 一部のインターフェースデバイス/ドライバーはオートスリープをサポートしていません。ユーザー空間では、 usb_device スリープする前にインターフェースドライバーをアンバインドする必要があります。アンバインドされたインターフェースデバイスはデフォルトでスリープ状態になります。アンバインドする際は、親USBデバイスのドライバーではなく、インターフェースドライバーをアンバインドするように注意してください。また、ハブインターフェースドライバーはアンバインドしないでください。USBデバイス（インターフェースではない）のドライバーをアンバインドすると、カーネルがデバイスを再開できなくなります。ハブインターフェースドライバーをアンバインドすると、その子ポートの制御が失われ、すべての接続された子デバイスが切断します。良いルールとして、デバイスの「ドライバ/モジュールリンク」が /sys/module/usbcore を指している場合、そのデバイスをアンバインドするとポート電源制御に干渉します。

ポート電源制御に関連するファイルの例。注意: この例では、これらのファイルはUSBハブデバイス（プレフィックス）に対して相対的に示しています。

prefix=/sys/devices/pci0000:00/0000:00:14.0/usb3/3-1

                 attached child device +
             hub port device +         |
hub interface device +       |         |
                     v       v         v
             $prefix/3-1:1.0/3-1-port1/device

$prefix/3-1:1.0/3-1-port1/power/pm_qos_no_power_off
$prefix/3-1:1.0/3-1-port1/device/power/control
$prefix/3-1:1.0/3-1-port1/device/3-1.1:<intf0>/driver/unbind
$prefix/3-1:1.0/3-1-port1/device/3-1.1:<intf1>/driver/unbind
...
$prefix/3-1:1.0/3-1-port1/device/3-1.1:<intfN>/driver/unbind

これらのファイルに加えて、一部のポートは別のハブのポートに接続する「ペアリンク」を持つ場合があります。期待されるのは、すべてのスーパースピードポートがハイスピードペアを持つことです:

$prefix/3-1:1.0/3-1-port1/peer -> ../../../../usb2/2-1/2-1:1.0/2-1-port1
../../../../usb2/2-1/2-1:1.0/2-1-port1/peer -> ../../../../usb3/3-1/3-1:1.0/3-1-port1

「コンパニオンポート」や「EHC/XHCI共有スイッチオーバーポート」とは異なり、ペアポートは単一のUSB3コネクタに組み合わされたハイスピードおよびスーパースピードインターフェースピンです。ペアポートは同じ祖先XHCIデバイスを共有します。

スーパースピードポートが電源を切られている間、デバイスが接続を下位互換性に変更し、ハイスピードピンに接続しようとする場合があります。この実装では、このような接続を防ぐための対策が講じられています:

  1. ポートのスリープは順序を保って行われ、高速ポートがスーパースピードのペアが電源を切る許可を受ける前に電源を切ることを保証します。これは、スーパースピードポートの設定をゼロにしても、高速ポートのペアがランタイムスリープ状態になるまでポートが電源を切らない可能性があることを意味します。 pm_qos_no_power_off ユーザー空間がスーパースピードポートが電源を切るのを確実にするためには、スリープの順序を正しく管理する必要があります。

  2. ポートのリザーブは、スーパースピードポートが高速ポートよりも先に電源をオンにするように強制されます。

  3. ポートのリザーブは、接続された子デバイスをリザーブします。電源セッションが失われた後、デバイスが削除されているか、リセットが必要な場合があります。親ポートが電源を取り戻すときに子デバイスをリザーブすることで、これらの状態を解決し、子デバイスがスリープ（autosuspend-delay）およびリザーブ（reset-resume latency）できる速度で最大ポート電源サイクル周波数を制限します。

ポート電源制御に関連するsysfsファイル:

<hubdev-portX>/power/pm_qos_no_power_off:

この書き込みフラグは、アイドルポートの状態を制御します。すべての子孫デバイスがスリープした後、pm_qos_no_power_offが「0」の場合に限りポートがスリープ/電源を切ることができます。pm_qos_no_power_offが「1」の場合、ポートは子孫デバイスの状態に関係なくアクティブ/電源が入ったままです。デフォルトは1です。

<hubdev-portX>/power/runtime_status:

このファイルは、ポートが「アクティブ」（電源が入っている）か「スリープ」（論理的にオフ）かを反映します。VBUSがまだ供給されているかどうかについてはユーザー空間に情報がありません。

<hubdev-portX>/connect_type:

ユーザー空間にポートの場所と接続タイプを示すアドバイザリーリードオンリーフラグです。このフラグは「hotplug」、「hardwired」、「not used」、「unknown」の4つの値のいずれかを返します。すべての値（unknownを除く）はプラットフォームファームウェアによって設定されます。

hotplug プラットフォーム上に外部から接続可能/表示されるポートを示します。通常、ユーザー空間はこのようなポートを電源を維持して新しいデバイス接続イベントを処理するために選ぶでしょう。

hardwired 表示されないが接続可能なポートを指します。例はUSBブルートゥースの内部ポートで、外部スイッチやハードワイヤードUSBカメラを介して切断可能なポートです。pm_qos_no_power_offがスイッチで接続を制御するものと調整されている限り、これらのポートをスリープさせるのは安全です。ユーザー空間はポートが電源を切る前にデバイスが接続されているように、またはスイッチで接続を有効にする前にポートをオンにする必要があります。

not used 常にデバイスが接続されない内部ポートを指します。これらは空の内部ポートか、プラットフォーム上に物理的に露出していないポートかもしれません。常に電源を切っても安全とされています。

unknown このポートに関する情報がプラットフォームファームウェアで提供されていないことを意味します。これは、ポリシー決定において「ホットプラグ」として扱われるべき外部ハブポートを最もよく指します。

注意

  • BIOSにACPI情報の正確性を依存しているため、USBポートの説明が不足しているか誤っている可能性があります。

  • クリアする際には注意が必要です pm_qos_no_power_off。電源がオフになると、このポートは新しい接続イベントに反応しなくなります。

子デバイスが接続された後、ポートを電源オフに許可する前に追加の制約が適用されます。

<child>/power/control:

必須です auto、そしてポートは <child>/power/runtime_status が「スリープ」状態を反映しています。デフォルト値は子デバイスドライバによって制御されます。

<child>/power/persist:

これはほとんどのデバイスでデフォルトで 1 であり、カーネルが電源セッションの喪失（スリープ／ポート電源イベント）時にデバイスの設定を維持できるかを示します。この値が 0 (特殊なデバイス)の場合、ポート電源オフが無効になります。

<child>/driver/unbind:

ウェイクアップ可能なデバイスはポート電源オフをブロックします。この時点では、インターフェースデバイスのusb-internalウェイクアップ能力をクリアする唯一のメカニズムはドライバをアンバインドすることです。

ポートデバイスに関する電源オフ前の必須設定のサマリー:

echo 0 > power/pm_qos_no_power_off
echo 0 > peer/power/pm_qos_no_power_off # if it exists
echo auto > power/control # this is the default value
echo auto > <child>/power/control
echo 1 > <child>/power/persist # this is the default value

推奨されるユーザー空間ポート電源ポリシー¶

上記のように、ユーザー空間は電源オフを許可するポートについて慎重かつ意図的に選択する必要があります。

デフォルトの設定では、すべてのポートが power/pm_qos_no_power_off 設定に設定する 1 で初期化され、ポートが常にアクティブな状態を維持します。

プラットフォームファームウェアがポートの説明（ポートのACPI _PLDレコードが「connect_type」を設定）を信頼できるとみなす場合、ユーザー空間はすべての「未使用」ポートに対してpm_qos_no_power_offをクリアできます。また、「ハードワイヤード」ポートについても、ポートの接続スイッチと電源オフを調整した上で同様の操作が可能です。

より積極的なユーザー空間ポリシーは、ユーザーがシステムと対話を停止したことを外部要因が示すときにすべてのポートでUSBポート電源オフを有効にします（ <hubdev-portX>/power/pm_qos_no_power_off に（木の下から葉に向かって） 0を設定）。

Synopsys DesignWare Core SuperSpeed USB 3.0 Controller¶

著者

フェリペ・バルビ <felipe.balbi@linux.intel.com>

日付

2017年4月

はじめに¶

以下の Synopsys DesignWare Core SuperSpeed USB 3.0 Controller （以下、 DWC3) は USB SuperSpeed 対応のコントローラーであり、4通りの設定のいずれかに構成できます：

  1. ペリフェラル専用構成

  2. ホスト専用構成

  3. ダブルロール構成

  4. ハブ構成

Linux はこのコントローラーのいくつかのバージョンをサポートしています。おそらく、あなたの SoC に搭載されているバージョンはすでにサポートされています。この執筆時点では、テスト済みのバージョンは 2.02a から 3.10a までです。一般的に、2.02a より上のバージョンは信頼性よく動作するはずです。

現在、このドライバーの多くのユーザーがいます。アルファベット順で：

  1. Cavium

  2. インテル コーポレーション

  3. クアルコム

  4. ロックピーク

  5. ST

  6. サムスン

  7. テキサス インスツルメンツ

  8. Xilinx

機能の概要¶

DWC3 のバージョンでサポートされている機能についての詳細は、IP チームと/or Synopsys DesignWare Core SuperSpeed USB 3.0 コントローラー データブック。この執筆時点でのドライバーがサポートしている機能の一覧は以下の通りです：

  1. 最大16の双方向エンドポイント（コントロールパイプを含む - ep0）

  2. 柔軟なエンドポイント構成

  3. IN と OUT 両方の転送を同時にサポート

  4. スキャッターリストのサポート

  5. 最大256 TRB 1 各エンドポイントあたり

  6. すべての転送タイプのサポート（コントロール, バルク, 割込み, and アイソクロナス)

  7. スーパースピード バルクストリーム

  8. リンク電源管理

  9. デバッグ用のトレースイベント

  10. DebugFS 3 インターフェース

これらの機能は、多くの in-tree gadget drivers. We have verified both ConfigFS 4 and legacy gadget drivers.

ドライバ設計¶

The DWC3 driver sits on the drivers/usb/dwc3/ directory. All files related to this driver are in this one directory. This makes it easy for new-comers to read the code and understand how it behaves.

Because of DWC3’s configuration flexibility, the driver is a little complex in some places but it should be rather straightforward to understand.

The biggest part of the driver refers to the Gadget API.

既知の制限事項¶

Like any other HW, DWC3 has its own set of limitations. To avoid constant questions about such problems, we decided to document them here and have a single location to where we could point users.

OUT転送サイズの要件¶

According to Synopsys Databook, all OUT transfer TRBs 1 must have their size field set to a value which is integer divisible by the endpoint’s wMaxPacketSize. This means that e.g. in order to receive a Mass Storage CBW 5, req->length must either be set to a value that’s divisible by wMaxPacketSize (1024 on SuperSpeed, 512 on HighSpeed, etc), or DWC3 driver must add a Chained TRB pointing to a throw-away buffer for the remaining length. Without this, OUT transfers will 禁止です start.

Note that as of this writing, this won’t be a problem because DWC3 is fully capable of appending a chained TRB for the remaining length and completely hide this detail from the gadget driver. It’s still worth mentioning because this seems to be the largest source of queries about DWC3 and non-working transfers.

TRBリングのサイズ制限¶

We, currently, have a hard limit of 256 TRBs 1 per endpoint, with the last TRB being a Link TRB 2 pointing back to the first. This limit is arbitrary but it has the benefit of adding up to exactly 4096 bytes, or 1 Page.

DWC3 driver will try its best to cope with more than 255 requests and, for the most part, it should work normally. However this is not something that has been exercised very frequently. If you experience any problems, see section バグの報告 も参照してください。

バグの報告¶

Whenever you encounter a problem with DWC3, first and foremost you should make sure that:

  1. You’re running latest tag from Linus’ tree

  2. You can reproduce the error without any out-of-tree changes to DWC3

  3. You have checked that it’s not a fault on the host machine

After all these are verified, then here’s how to capture enough information so we can be of any help to you.

必要な情報¶

DWC3 relies exclusively on Trace Events for debugging. Everything is exposed there, with some extra bits being exposed to DebugFS 3.

DWC3のトレースイベントをキャプチャするには、以下のコマンドを実行してください。 before USBケーブルをホストマシンに接続してください：

# mkdir -p /d
# mkdir -p /t
# mount -t debugfs none /d
# mount -t tracefs none /t
# echo 81920 > /t/buffer_size_kb
# echo 1 > /t/events/dwc3/enable

この操作が完了したら、USBケーブルを接続して問題を再現してください。問題が再現され次第、ファイルのコピーを取ってください trace および regdump、以下のようにしてください：

# cp /t/trace /root/trace.txt
# cat /d/*dwc3*/regdump > /root/regdump.txt

圧縮してください trace.txt および regdump.txt tarballに圧縮して、以下にメールで送ってください： chrisn with linux-usb Ccに記載してください。私が確実にご支援できるようにするには、件名を以下のように記載してください：

[BUG REPORT] usb: dwc3: Bug while doing XYZ

メール本文には、以下の情報を詳細に記載してください：問題の再現手順、使用しているギガントドライバー、使用しているSoC、ホストマシンで動作しているOS（バージョン含む）などを。

この情報があれば、問題の原因を特定し、ご支援できるでしょう。

以下の一覧から一つを表示します。 link_state このファイルは、上記の状態の一つに強制的にリンクさせるために書込み可能です。 U0, U1, U2, U3, SS.Disabled, RX.Detect, SS.Inactive, Polling, Recovery, Hot Reset, Compliance, Loopback, Reset, Resume または UNKNOWN link state.

regdump¶

DWC3のレジスタダンプを表示します。このファイルは、grepコマンドで必要な情報を検索できます。 regdump 指定されたUSB 2.0テストモード（）の一つの名前を表示します。テストが実行されていない場合は、文字列を表示します。

testmode¶

以下の一覧から一つを表示します。 testmode テストが実行されていない場合。test_j, test_k, test_se0_nak, test_packet, test_force_enable)または文字列 no test テストが実行されていない場合。

これらのテストモードを開始するには、同じ文字列をファイルに書込み、DWC3が要求されたテストモードに移行します。

ep[0..15]{in,out}¶

各エンドポイントに対して、以下の命名規則に従ったディレクトリを公開します ep$num$dir (ep0in, ep0out, ep1in, …)。これらのディレクトリには、以下のファイルがあります：

descriptor_fetch_queue event_queue rx_fifo_queue rx_info_queue rx_request_queue transfer_type trb_ring tx_fifo_queue tx_request_queue

Synopsys Databookにアクセスできると、これらの情報の解読が可能です。

トレースイベント¶

DWC3 は、ドライバの実行時の動作に関する情報を収集するのに役立つ複数のトレースイベントも提供しています。

これらを使用するには、有効にする必要があります CONFIG_FTRACE を有効にしておく必要があります。

DWC3 イベントを有効にする方法についての詳細は、セクション バグの報告.

以下のサブセクションでは、DWC3 で定義された各イベントクラスと各イベントについての詳細を説明します。

MMIO¶

バグの検出に際して、すべての MMIO アクセスを確認することが有用な場合があります。そのため、DWC3 は dwc3_readl() と dwc3_writel() それぞれに対応するトレースイベントを提供しています。 TP_printk 続きます:

TP_printk("addr %p value %08x", __entry->base + __entry->offset,
              __entry->value)

割込みイベント¶

すべての IRQ イベントはログとして記録され、人間が読みやすい文字列にデコードされます。すべてのイベントが異なりますので、例は以下のフォーマットのみを示します。 TP_printk 使用するフォーマット:

TP_printk("event (%08x): %s", __entry->event,
              dwc3_decode_event(__entry->event, __entry->ep0state))

コントロールリクエスト¶

すべての USB コントロールリクエストはトレースバッファにログとして記録されます。出力フォーマットは:

TP_printk("%s", dwc3_decode_ctrl(__entry->bRequestType,
                              __entry->bRequest, __entry->wValue,
                              __entry->wIndex, __entry->wLength)
)

標準コントロールリクエストは、それぞれの引数とともに人間が読みやすい文字列にデコードされます。クラスやベンダーのリクエストは、16進数で8バイトのシーケンスとして表示されます。

のライフタイム struct usb_request¶

のすべてのライフタイム struct usb_request トレースバッファで追跡できます。割り当て、解放、キューイング、デキューイング、giveback のそれぞれにイベントがあります。出力フォーマットは:

TP_printk("%s: req %p length %u/%u %s%s%s ==> %d",
      __get_str(name), __entry->req, __entry->actual, __entry->length,
      __entry->zero ? "Z" : "z",
      __entry->short_not_ok ? "S" : "s",
      __entry->no_interrupt ? "i" : "I",
      __entry->status
)

汎用コマンド¶

すべての汎用コマンドとその完了コードをログとして記録およびデコードできます。フォーマットは:

TP_printk("cmd '%s' [%x] param %08x --> status: %s",
      dwc3_gadget_generic_cmd_string(__entry->cmd),
      __entry->cmd, __entry->param,
      dwc3_gadget_generic_cmd_status_string(__entry->status)
)

エンドポイントコマンド¶

エンドポイントコマンドも完了コードとともにログとして記録できます。フォーマットは:

TP_printk("%s: cmd '%s' [%d] params %08x %08x %08x --> status: %s",
      __get_str(name), dwc3_gadget_ep_cmd_string(__entry->cmd),
      __entry->cmd, __entry->param0,
      __entry->param1, __entry->param2,
      dwc3_ep_cmd_status_string(__entry->cmd_status)
)

のライフタイム TRB¶

A TRB ライフタイムは単純です。準備中か、完了中かのいずれかです。この2つのイベントにより、が時間とともにどのように変化するかを確認できます。フォーマットは: TRB のライフタイム TRB が時間とともにどのように変化するかを確認できます。フォーマットは:

TP_printk("%s: %d/%d trb %p buf %08x%08x size %s%d ctrl %08x (%c%c%c%c:%c%c:%s)",
      __get_str(name), __entry->queued, __entry->allocated,
      __entry->trb, __entry->bph, __entry->bpl,
      ({char *s;
      int pcm = ((__entry->size >> 24) & 3) + 1;
      switch (__entry->type) {
      case USB_ENDPOINT_XFER_INT:
      case USB_ENDPOINT_XFER_ISOC:
              switch (pcm) {
              case 1:
                      s = "1x ";
                      break;
              case 2:
                      s = "2x ";
                      break;
              case 3:
                      s = "3x ";
                      break;
              }
      default:
              s = "";
      } s; }),
      DWC3_TRB_SIZE_LENGTH(__entry->size), __entry->ctrl,
      __entry->ctrl & DWC3_TRB_CTRL_HWO ? 'H' : 'h',
      __entry->ctrl & DWC3_TRB_CTRL_LST ? 'L' : 'l',
      __entry->ctrl & DWC3_TRB_CTRL_CHN ? 'C' : 'c',

      __entry->ctrl & DWC3_TRB_CTRL_IOC ? 'C' : 'c',

int dwc3_gadget_start_config(struct dwc3_ep *dep)¶

EPリソースを設定する

パラメータ

struct dwc3_ep *dep

有効化されているエンドポイント

説明

コマンドを DWC3_DEPCMD_DEPSTARTCFG 実行して dep。コマンドが完了した後、すべての利用可能なエンドポイントに対して転送リソースを設定します。

コントローラードライバーが事前にすべての設定情報を把握していないため、データブックに完全に従うことはできません。SET_CONFIGURATIONおよびSET_INTERFACEごとにコンポジットギアフレームワークから情報が断片的に提供されるため、このシナリオでデータブックのプログラミングモデルを従うとエラーが発生する可能性があります。その理由は以下の通りです：

1) データブックでは DWC3_DEPCMD_DEPSTARTCFG をすべて USB_REQ_SET_CONFIGURATION および USB_REQ_SET_INTERFACE (8.1.5)。これは複数のインターフェースのシナリオでは誤りです。

2) データブックでは新しいエンドポイントの DWC3_DEPCMD_DEPXFERCFG について記述されていません(8.1.6)。

代わりに以下の簡略化された方法が使用されます：

すべてのハードウェアエンドポイントに転送リソースを割り当てることができ、この設定はコアリセットまたは休止状態になるまで永続します。そのため、いつでも DWC3_DEPCMD_DEPSTARTCFG``(0) we can go ahead and do ``DWC3_DEPCMD_DEPXFERCFG をすべてのハードウェアエンドポイントにも適用します。これにより、エンドポイントと転送リソースの数が同じであることを保証します。

この関数は、エンドポイントが有効化されるときに呼び出されますが、EP0-outの呼び出しからのみトリガーされます。これは常に最初に発生し、上記の条件のいずれかでしか発生しないはずです。

DWC3リビジョン280A以前: fifo_size = mult * (max_packet / mdwidth) + 1;

DWC3リビジョン290A以降: fifo_size = mult * ((max_packet + mdwidth)/mdwidth + 1) + 1

最大パケットサイズはスーパースピードUSBの使用ケースに主に適用されるため、1024に設定されています。ただし、他のシナリオ（例：ハイスピードUSB）ではfifo割当を過剰に見積るのも安全です。

int dwc3_gadget_start_isoc_quirk(struct dwc3_ep *dep)¶

無効なフレーム番号のワークアロンド

パラメータ

struct dwc3_ep *dep

等時性エンドポイント

説明

この関数は、XferNotReadyイベントで報告された16ビットのマイクロフレーム番号のBIT[15:14]の正しい組み合わせをテストし、将来のフレーム番号に基づいてisoc転送を開始するための処理を行います。

DWC_usb31バージョン1.70a-ea06以前では、高速およびフルスピードのisochronous INにおいて、XferNotReadyイベントで報告された16ビットマイクロフレーム番号のBIT[15:14]は無効です。ドライバーはこの番号を使用してisochronous転送をスケジュールし、START TRANSFERコマンドに渡します。この番号が無効なため、コマンドが失敗する可能性があります。BIT[15:14]が内部の16ビットマイクロフレームと一致する場合、START TRANSFERコマンドは通過し、スケジュールされた時間に転送が開始されます。もし1ずれた場合でもコマンドは通過しますが、転送は2秒後に開始されます。他のすべての条件では、START TRANSFERコマンドはバスの期限切れで失敗します。

この問題を回避するには、BIT[15:14]の正しい組み合わせをテストするために、BIT[15:14]の異なる値（'b00、'b01、'b10、'b11）でSTART TRANSFERコマンドを送信します。各組み合わせは2^14 uframe（または2秒）の間隔があります。4秒先の場合はバスの期限切れステータスになります。結果として、BIT[15:14]の4つの可能な組み合わせの中で、2つの成功と2つの失敗のSTARTコマンドステータスがあります。成功した2つのコマンドステータスのうち1つは2秒の遅延で開始します。小さいBIT[15:14]値が正しい組み合わせです。

4つの結果があり、結果が順序付けられているため、BIT[15:14]の'b00と'b01の2つのSTART TRANSFERコマンドをテストするだけで、小さい成功組み合わせを推定できます。

test0 = 'b00の組み合わせのテストステータス、test1 = 'b01の組み合わせのテストステータスとします。正しい組み合わせは以下の通りです：

test0が失敗でtest1が成功の場合、BIT[15:14]は'b01です。test0が失敗でtest1も失敗の場合、BIT[15:14]は'b10です。test0が成功でtest1が失敗の場合、BIT[15:14]は'b11です。test0とtest1がともに成功の場合、BIT[15:14]は'b00です。

Synopsys STAR 9001202023: isochronous INエンドポイントの誤ったマイクロフレーム番号

void dwc3_gadget_setup_nump(struct dwc3 *dwc)¶

NUMPフィールドを計算および初期化する DWC3_DCFG

パラメータ

struct dwc3 *dwc

私たちのコンテキスト構造へのポインタ

説明

以下の説明は複雑に見えるかもしれませんが、実際には非常に簡単です。OUT転送で一度に送信できるパケット数を計算するには、RxFIFOサイズを使用します。

RxFIFOサイズを計算するには2つの数値が必要です：MDWIDTH = 内部メモリバスRAM2_DEPTH = 内部RAM2（RxFIFOが配置されている場所）の深さ（MDWIDTH単位）

これらの2つの数値をもとに、式はシンプルです：

RxFIFO サイズ = (RAM2_DEPTH * MDWIDTH / 8) - 24 - 16;

24 バイトは3つのSETUPパケット用で、16 バイトはクロックドメインクロス許容のため

RxFIFO サイズが与えられた場合、NUMP = RxFIFOSize / 1024;

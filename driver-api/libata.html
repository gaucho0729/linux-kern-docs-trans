はじめに¶

libATAはLinuxカーネル内でATAホストコントローラーおよびデバイスをサポートするためのライブラリです。libATAはATAドライバAPI、ATAおよびATAPIデバイス用のクラストランスポーテーション、およびT10 SAT仕様に従ったATAデバイスのSCSI<->ATA変換を提供します。

このガイドはlibATAドライバAPI、ライブラリ関数、ライブラリ内部構造、およびいくつかのサンプルATA低レベルドライバについてドキュメンテーションしています。

コマンドの起源¶

libataでは、コマンドは struct ata_queued_cmd or qcで表されます。qcはポート初期化時に事前に割り当てられ、コマンド実行時に繰り返し使用されます。現在は1ポートあたり1つのqcが割り当てられていますが、まだマージされていないNCQブランチではタグごとに1つ割り当てられ、各qcをNCQタグ1対1でマッピングします。

libataコマンドは2つのソースから発生します - libata自体とSCSIミドルレイヤーです。libata内部コマンドは初期化およびエラー処理に使用されます。すべての通常のblkリクエストおよびSCSIエミュレーション用のコマンドは、SCSIホストテンプレートのqueuecommandコールバックを通じてSCSIコマンドとして処理されます。

コマンドが発行される仕組み¶

内部コマンド

まず、qcは ata_qc_new_init()は ata_qc_new_init() qcが利用不可の場合、待機や再試行のメカニズムを実装していませんため、現在は初期化およびエラー回復中にのみ内部コマンドが発行され、他のコマンドがアクティブにならないため、割り当てが成功することを保証しています。

割り当てられたqcのタスクファイルが実行するコマンドに初期化されます。qcは現在、完了を通知する2つのメカニズムを持っています。1つは qc->complete_fn() コールバック経由で、もう1つは完了 qc->waiting. qc->complete_fn() コールバックは通常のSCSI変換コマンドに使用される非同期経路で、 qc->waiting は内部コマンドに使用される同期経路（発行者がプロセスコンテキストでスリープ）です。

初期化が完了すると、host_setロックを取得し、qcが発行されます。

SCSIコマンド

すべてのlibataドライバーは ata_scsi_queuecmd() as hostt->queuecommand コールバック。scmdはシミュレーションされるか翻訳されるかのいずれかです。シミュレーションされたscmdの処理にはqcは関与しません。結果は即座に計算され、scmdは完了します。

翻訳されたscmdの場合、 ata_qc_new_init() が呼び出されてqcが割り当てられ、scmdはqcに翻訳されます。SCSI midlayerの完了通知関数ポインタが qc->scsidone.

qc->complete_fn() コールバックが完了通知に使用されます。ATAコマンドは ata_scsi_qc_complete() を使用し、ATAPIコマンドは atapi_qc_complete()を使用します。どちらの関数も、qcが完了したときに上位レイヤーを通知するために qc->scsidone を呼び出します。翻訳が完了した後、qcは ata_qc_issue().

で実行されます。注意点として、SCSI midlayerはhost_setロックを保持しながらhostt->queuecommandを呼び出しますので、すべての処理はhost_setロックを保持しながら行われます。

コマンドの処理方法¶

使用するプロトコルやコントローラーによってコマンドの処理が異なります。議論の目的として、タスクファイルインターフェースとすべての標準コールバックを使用するコントローラーを想定します。

現在、6種類のATAコマンドプロトコルが使用されています。これらは処理方法によって以下の4つのカテゴリに分類されます。

ATAノーデータまたはDMA

ATA_PROT_NODATAおよびATA_PROT_DMAはこのカテゴリに属します。これらのコマンドは発行後、ソフトウェアの介入を必要としません。デバイスが完了時に割り込みを発生させます。

ATA PIO

ATA_PROT_PIOはこのカテゴリに属します。libataは現在、PIOをポーリングで実装しています。ATA_NIENビットを設定して割り込みを無効化し、ata_wqのpio_taskがポーリングとIOを実行します。

ATAPIノーデータまたはDMA

ATA_PROT_ATAPI_NODATAおよびATA_PROT_ATAPI_DMAはこのカテゴリに属します。PACKETコマンドを発行後にpacket_taskがBSYビットをポーリングします。デバイスがBSYをオフにした後、packet_taskがCDBを転送し、割り込みハンドラに処理を委譲します。

ATAPI PIO

ATA_PROT_ATAPIはこのカテゴリに属します。ATA_NIENビットが設定され、ATAPIノーデータまたはDMAと同様にpacket_taskがcdbを送信します。ただし、cdbを送信した後は、pio_taskにデータ転送の処理を委譲します。

コマンドの完了方法¶

発行後、すべてのqcは ata_qc_complete() で完了するか、タイムアウトします。割り込みで処理されるコマンドでは、 ata_host_intr() が呼び出されます。 ata_qc_complete()が呼び出され、PIOタスクではpio_taskが ata_qc_complete()を呼び出します。エラーケースでは、packet_taskもコマンドを完了することがあります。

ata_qc_complete() は以下の処理を行います。

  1. DMAメモリがマッピング解除されます。

  2. qc->flagsからATA_QCFLAG_ACTIVEがクリアされます。

  3. qc->complete_fn コールバックが呼び出されます。コールバックの戻り値がゼロでない場合、完了処理が短絡され、 ata_qc_complete() 戻ります。

  4. __ata_qc_complete() が呼び出され、その処理を行います。

    1. qc->flags がゼロにクリアされます。

    2. ap->active_tag および qc->tag が毒化されます。

    3. qc->waiting がクリアされ、完了します（この順序で）。

    4. は、適切なビットをクリアして解放されます ap->qactive.

したがって、上位レイヤーに通知し、qcを解放します。例外は#3の短絡パスで、これは atapi_qc_complete().

すべての非ATAPIコマンドについて、成功または失敗に関わらずほぼ同じコードパスが処理され、エラー処理はほとんど行われません。コマンドが成功した場合はqcが成功ステータスで完了し、失敗した場合は失敗ステータスで完了します。

しかし、失敗したATAPIコマンドはREQUEST SENSEを取得する必要があるため、より多くの処理が必要です。ATAPIコマンドが失敗した場合、 ata_qc_complete() エラー状態で呼び出され、これにより atapi_qc_complete() を qc->complete_fn() そのコールバックは、指定されたポリシーに属するすべてのオンラインCPUに対して、CPUスケジューラにパーセルCPUの利用率更新コールバックを登録する必要があります。

これにより atapi_qc_complete() set scmd->result SAM_STAT_CHECK_CONDITIONに移行し、scmdを完了して1を返します。センスデータが空ですが、 scmd->result CHECK CONDITIONであるため、SCSIミドルレイヤーはscmdに対してEHを呼び出し、1を返すことで ata_qc_complete() qcを解放せずに戻るようになります。これにより、 ata_scsi_error() 部分的に完了したqcが発生します。

ata_scsi_error()¶

ata_scsi_error() は現在の transportt->eh_strategy_handler() libataの処理です。上記のように、タイムアウトとATAPIエラー完了の2つのケースでこの関数が呼ばれます。この関数はlow level libataドライバの eng_timeout() コールバックを呼び出します。標準的なコールバックは ata_eng_timeout()です。qcがアクティブかどうかを確認し、アクティブな場合に ata_qc_timeout() をqcに呼び出します。実際のエラー処理は ata_qc_timeout().

タイムアウトでEHが呼び出された場合、 ata_qc_timeout() BMDMAを停止し、qcを完了します。注意点として、現在EH内にいるためscsi_doneを呼び出すことはできません。SCSI EHドキュメントで説明されている通り、回復可能なscmdは、 scsi_queue_insert() で再試行するか、 scsi_finish_command()で終了する必要があります。ここでは、 qc->scsidone with scsi_finish_command() で定義し、 ata_qc_complete().

ATAPI qcが失敗した場合にEHが呼び出された場合、qcは完了しますが解放されません。この半分の完了の目的は、EHコードがこの場所に到達するためのプレースホルダーとしてqcを使用することです。これはちょっとしたハックですが、機能します。

制御がここに到達した後、qcを解放するために __ata_qc_complete() を明示的に呼び出します。その後、内部でREQUEST SENSEを実行するqcが発行されます。センスデータを取得した後、scmdは直接 scsi_finish_command() をscmdに呼び出して完了します。注意点として、scmdに関連するqcがすでに完了・解放されているため、 ata_qc_complete() また。

現在のEHの問題点¶

  • エラー表現が粗すぎる。現在、すべてのエラー条件がATA STATUSおよびERRORレジスタで表されています。ATAデバイスエラーでないエラーもATA_ERRビットを設定してATAデバイスエラーとして扱われています。ATAおよび他のエラー/例外を適切に表現できるより良いエラーデスクリプターが必要です。

  • タイムアウト処理では、デバイスがタイムアウトしたコマンドを忘れ、新しいコマンドを受け入れる準備になるようにするためのアクションが行われていません。

  • EH処理を通じて ata_scsi_error() 通常のコマンド処理から適切に保護されていない。EH（エラー処理）のエントリ時にデバイスが静止状態でない。タイムアウトしたコマンドはいつでも成功または失敗する可能性がある。pio_task および atapi_task はまだ実行中である可能性がある。

  • エラー回復が十分に弱い。HSM不一致エラーなどのエラーを頻繁に発生させるデバイス/コントローラーは、知られている状態に戻すためにリセットが必要である。また、NCQやホットプラグなどの機能をサポートするためには、高度なエラー処理が必須である。

  • ATAエラーは割込みハンドラで直接処理され、PIOエラーはpio_taskで処理される。これは高度なエラー処理において問題となる以下の理由がある。

    まず、高度なエラー処理はコンテキストと内部qcの実行を必要とする。

    次に、単純な失敗（例: CRCエラー）でも情報収集が必要であり、複雑なエラー処理（例: リセットと再構成）をトリガーする可能性がある。情報収集、エラー処理への移行、アクションのトリガーに複数のコードパスを持つことは非常に煩雑である。

    第三に、散らばったエラー処理コードは低レベルドライバの実装を困難にする。低レベルドライバはlibataコールバックをオーバーライドする。エラー処理が複数の場所に散らばっている場合、各影響を受けるコールバックがそれぞれエラー処理の一部を実行しなければならない。これはエラーが発生しやすく、煩雑である。

unsigned int ata_eh_speed_down_verdict(struct ata_device *dev)¶

速度ダウンの判断を行う

パラメータ

struct ata_device *dev

関心のあるデバイス

この関数は、のエラー環を調べます dev NCQをオフにする必要があるか、転送速度を段階的に下げるべきか、またはPIOに戻る必要があるかを判断します。

ECAT_ATA_BUS : 任意のコマンドにおけるATA_BUSエラー

ECAT_TOUT_HSM任意のコマンドのタイムアウトまたはのHSM違反

IOコマンド

ECAT_UNK_DEV : IOコマンドにおける不明なDEVエラー

ECAT_DUBIOUS_*上記の3つと同様ですが、の際発生しました

データ転送が確認されていません

判断は以下の通りです

NCQ_OFF : NCQをオフにします

SPEED_DOWN転送速度を下げるが、戻らない

PIOに切り替えます。

FALLBACK_TO_PIO: PIOに切り替えます。

複数の判定結果が返された場合でも、各エラーごとに1つのアクションのみが実行されます。非DUBIOUSエラーによってトリガーされたアクションはエラーをクリアしますが、DUBIOUS_*エラーによってトリガーされたアクションはクリアしません。これは、デバイスが最初に設定された直後に迅速な速度ダウン決定を行うためです。

以下は速度ダウンのルールです。#1と#2はDUBIOUSエラーに関連します。

  1. 過去5分間にDUBIOUS_ATA_BUSまたはDUBIOUS_TOUT_HSMエラーが1つ以上発生した場合、SPEED_DOWNとFALLBACK_TO_PIOを行います。

  2. 過去5分間にDUBIOUS_TOUT_HSMまたはDUBIOUS_UNK_DEVエラーが1つ以上発生した場合、NCQ_OFFを行います。

  3. 過去5分間にATA_BUS、TOUT_HSM、またはUNK_DEVエラーが8つ以上発生した場合、FALLBACK_TO_PIOを行います。

  4. 過去10分間にTOUT_HSMまたはUNK_DEVエラーが3つ以上発生した場合、NCQ_OFFを行います。

  5. 過去10分間にATA_BUSまたはTOUT_HSMエラーが3つ以上、またはUNK_DEVエラーが6つ以上発生した場合、SPEED_DOWNを行います。

ロック: 呼び出し元から継承されます。

戻り値

ATA_EH_SPDN_*フラグのORです。

ATAエラーおよび例外¶

この章では、ATA/ATAPIデバイスで発生するエラー/例外条件を特定し、実装に依存しない方法でどのように処理すべきかを説明します

'エラー'という用語は、デバイスから明示的なエラー条件が報告されるか、コマンドがタイムアウトした場合に使用されます

「例外（exception）」という用語は、エラーではない例外的な状態（電源やホットプラグイベントなど）を表すか、またはエラーと非エラーの例外的な状態の両方を表す場合があります。エラーと例外の明確な区別が必要な場合は、「非エラー例外（non-error exception）」という用語を使用します。

例外カテゴリ¶

例外は、主に従来のタスクファイル＋バスマスターIDEインターフェースに関するものとして説明されます。コントローラーがエラー報告用に他のより優れたメカニズムを提供する場合、このセクションで説明するカテゴリにマッピングするのは難しくありません。

次のセクションでは、2つの回復アクション - リセットとトランスポートの再構成 - が言及されています。これらについては EH回復アクション.

HSM違反¶

ATA/ATAPIコマンドの発行または実行中にSTATUS値がHSMの要件と一致しない場合、このエラーが示されます。

  • ATA_STATUSがコマンドの発行中に!BSY && DRDY && !DRQを含まない場合、このエラーが発生します。

  • PIOデータ転送中に!BSY && !DRQが発生します。

  • コマンド完了時にDRQが立っています。

  • CDB転送が始まってから最後のバイトが転送される直前までに!BSY && ERRが発生します。ATA/ATAPI標準では、「デバイスはコマンドパケットの最後のバイトが書き込まれる前にPACKETコマンドをエラーで終了してはならない」と規定しており、エラーメッセージの説明と状態図にはこのような遷移は含まれていません。

このような場合、HSMが違反され、STATUSまたはERRORレジスタからエラーに関する情報が得られにくいです。つまり、このエラーはドライバのバグ、不良デバイス、コントローラーおよび/またはケーブルのいずれかの原因である可能性があります。

HSMが違反されているため、状態を再構築するためのリセットが必要です。また、伝送エラーが原因でこのようなエラーが発生する場合、低速でのトランスポートの再構成も有効かもしれません。

ATA/ATAPIデバイスエラー（NCQ/チェック条件以外）¶

これらはATA/ATAPIデバイスが検出・報告するデバイスの問題を示すエラーです。このようなエラーでは、STATUSおよびERRORレジスタの値が有効であり、エラー状態を説明しています。注意点として、一部のATAバスエラーもATA/ATAPIデバイスが検出し、デバイスエラーと同じメカニズムで報告されることがあります。このようなケースについては、このセクションの後半で説明します。

ATAコマンドでは、コマンド実行中に!BSY && ERRが発生し、完了時にも同様にこのタイプのエラーが示されます。

ATAPIコマンドでは、

  • !BSY && ERR && ABRTがPACKETコマンドの発行直後に発生すると、PACKETコマンドがサポートされていないことを示し、このカテゴリに該当します。

  • !BSY && ERR(==CHK) && !ABRT でCDBの最後のバイトが転送された後は、CHECK CONDITIONを示し、このカテゴリには該当しません。

  • !BSY && ERR(==CHK) && ABRT でCDBの最後のバイトが転送された後は、*おそらく* CHECK CONDITIONを示し、このカテゴリには該当しません。

上記で検出されたエラーの中には、ATA/ATAPIデバイスのエラーではなくATAバスエラーであり、以下に従って処理する必要があります。 ATAバスエラー.

データ転送中のCRCエラー

これはERRORレジスタのICRCビットによって示され、データ転送中に破損が発生したことを意味します。ATA/ATAPI-7までの標準ではこのビットはUDMA転送にのみ適用されるものと規定されていましたが、ATA/ATAPI-8ドラフトリビジョン1fでは、マルチワードDMAおよびPIOにも適用可能であると述べています。

データ転送中に発生したABRTエラーまたは完了時のABRTエラー

ATA/ATAPI-7までの標準では、ICRCエラーまたはデバイスがコマンドを完了できない場合でもABRTビットが設定されることが規定されていました。また、MWDMAおよびPIO転送エラーはATA/ATAPI-7まででICRCビットを使用できないため、ABRTビット単独で転送エラーを示しているように思われます。

ただし、ATA/ATAPI-8ドラフトリビジョン1fではICRCエラーがABRTビットを設定する可能性を削除しています。そのため、この領域はやや曖昧です。ここではヒューリスティクスが必要です。

ATA/ATAPIデバイスエラーはさらに以下のカテゴリに分類されます。

メディアエラー

これはERRORレジスタのUNCビットによって示されます。ATAデバイスは特定のリトライ回数が限界に達してデータを復旧できない場合にのみUNCエラーを報告するため、上位レイヤーに通知する以外にすることがありません。

READおよびWRITEコマンドは最初に失敗したセクタのCHSまたはLBAを報告しますが、ATA/ATAPI標準ではエラー完了時の転送データ量が不確定であるため、失敗セクタ前のセクタが転送されているとは断定できません。したがってSCSIのようにセクタを成功裏に完了させることが出来ません。

ATAPIデバイス CHECK CONDITION¶

ATAPIデバイス CHECK CONDITION エラーは、PACKETコマンドの最後のバイトが転送された後にステータスレジスタのCHKビット（ERRビット）が設定されることで示されます。このようなエラーについては、センスデータを取得してエラー情報を収集する必要があります。センスデータを取得するにはREQUEST SENSEパケットコマンドを使用します。

センスデータを取得した後、この種のエラーは他のSCSIエラーと同じように処理できます。注意点として、センスデータはATAバスエラー（例：Sense Key 04h HARDWARE ERROR && ASC/ASCQ 47h/00h SCSI PARITY ERROR）を示す可能性があります。このような場合、エラーはATAバスエラーとして扱い、以下の通り処理する必要があります。 ATAバスエラー.

ATAデバイスエラー（NCQ）¶

NCQコマンドフェーズ中にBSYがクリアされERRビットが設定された場合（1つ以上のNCQコマンドが未完了）、NCQコマンドエラーが発生しています。STATUSおよびERRORレジスタにはエラーを説明する有効な値が含まれますが、エラー状態をクリアし、失敗したコマンドを特定するにはREAD LOG EXTを使用する必要があります。

READ LOG EXTログページ10hは失敗したタグとエラーを説明するタスクファイルレジスタ値を報告します。この情報により、失敗したコマンドは通常のATAコマンドエラーとして処理できます。以下の通りです。 ATA/ATAPIデバイスエラー（NCQ/チェック条件以外） すべての未完了コマンドは再試行する必要があります。注意点として、この再試行はカウントされません。失敗したコマンドがなければ、このように再試行したコマンドは正常に完了する可能性が高いです。

ATAバスエラーはATAデバイスNCQエラーとして報告されることがあります。以下の通り処理する必要があります。 ATAバスエラー.

READ LOG EXTログページ10hが失敗したりNQを報告したりした場合、深刻な問題が発生します。以下の通り処理する必要があります。 HSM違反.

ATAバスエラー¶

ATAバスエラーとは、ATAバス（SATAまたはPATA）を介したデータ送信中にデータ破損が発生したことを示します。このようなエラーは以下の通り示されることがあります。

  • ICRCまたはABRTエラーとして説明されています。 ATA/ATAPIデバイスエラー（NCQ/チェック条件以外）.

  • コントローラー固有のエラー完了で、送信エラーを示すエラー情報が含まれています。

  • 一部のコントローラーではコマンドタイムアウトが発生します。この場合、タイムアウトが送信エラーによるものであるかを判定するメカニズムがある可能性があります。

  • 未知のランダムなエラー、タイムアウト、およびさまざまな不具合が含まれます。

上記のように、伝送エラーはデバイスのICRCエラーからランダムなデバイスロックアップまで幅広い症状を引き起こす可能性があり、多くの場合、エラー状態が伝送エラーによるものであるかを判断する方法がありません。そのため、エラーおよびタイムアウトの処理には、ある程度の推論を採用する必要があります。例えば、既知のサポートコマンドに対して繰り返しABRTエラーが発生する場合、ATAバスエラーを示唆しています。

ATAバスエラーが発生した可能性が判明した場合、ATAバスの伝送速度を下げるという対処が問題の緩和に有効です。参照してください トランスポートの再構成 詳しくは

PCIバスエラー¶

PCI（または他のシステムバス）を介した伝送中にデータの破損やその他の障害が発生した場合、標準のBMDMAではBMDMAステータスレジスタのエラービットがこの状態を示します。このようなエラーはシステムに重大な問題があることを示すため、記録する必要があります。ホストコントローラーのリセットが推奨されます。

遅延完了¶

タイムアウトが発生した際、タイムアウトハンドラがタイムアウトしたコマンドが成功またはエラーで完了していると判明した場合に発生します。これは通常、割り込みの喪失によって引き起こされます。このようなエラーは記録する必要があります。ホストコントローラーのリセットが推奨されます。

不明なエラー（タイムアウト）¶

タイムアウトが発生した際、コマンドがまだ処理中であるか、ホストとデバイスが未知の状態にある場合に発生します。このような状況ではHSMが有効または無効な状態にある可能性があります。デバイスを確実な状態に戻し、タイムアウトしたコマンドを忘れさせるためにはリセットが必要です。タイムアウトしたコマンドは再試行される可能性があります。

タイムアウトは伝送エラーによっても発生する可能性があります。参照してください ATAバスエラー 詳細についてはこちら。

EH回復アクション¶

このセクションではいくつかの重要な回復アクションについて説明します。

エラー状態のクリア¶

多くのコントローラーではエラー登録をエラー処理によってクリアする必要があります。コントローラーによっては異なる要件がある場合があります。

SATAでは、エラー処理中に少なくともSErrrorレジスタをクリアすることが強く推奨されます。

リセット¶

エラー処理（EH）中にリセットが必要なケースは以下の通りです。

  • HSMが未知または無効な状態にある

  • HBAが未知または無効な状態にある

  • EHがHBA/デバイスが進行中のコマンドを忘れることを目的としている

  • HBA/デバイスが不正な動作を示している

エラー状態に関係なく、EHの信頼性を高めるためにリセットを行うのが良い場合があります。HBAとデバイスのどちらか一方または両方をリセットするかどうかは状況によりますが、以下のスキームが推奨されます。

  • HBAが準備完了していることがわかっているが、ATA/ATAPIデバイスが未知の状態にある場合、デバイスのみをリセットしてください。

  • HBAが未知の状態にある場合、HBAとデバイスの両方をリセットする必要があります。

HBAのリセットは実装に依存します。タスクファイル/BMDMA PCI IDEコンプライアンスのコントローラーでは、アクティブなDMAトランザクションを停止するだけで十分な場合があります（BMDMAの状態がHBAのコンテキストの唯一の状態である場合）。しかし、ほとんどのタスクファイル/BMDMA PCI IDEコンプライアンスのコントローラーでも、実装に依存する要件や自己リセットメカニズムを持つ可能性があります。これは特定のドライバで対応する必要があります。

一方で、ATA/ATAPI標準ではATA/ATAPIデバイスのリセット方法を詳細に記述しています。

PATAハードウェアリセット

これはハードウェアがデバイスをリセットし、PATA RESET-信号がアサートされた状態で通知されるデバイスリセットです。ソフトウェアからハードウェアリセットを開始する標準的な方法は存在しませんが、一部のハードウェアではドライバがRESET-信号を直接操作できるレジスタが提供されることがあります。

ソフトウェアリセット

これはCONTROL SRSTビットを少なくとも5マイクロ秒間オンにすることで実現されます。PATAとSATAの両方がサポートしていますが、SATAの場合、コントローラー固有のサポートが必要となる可能性があります（BSYビットがセットされている間、セカンドレジスタFISでSRSTをクリアする必要があります）。PATAでは、この操作はチャネル上のマスターおよびスレーブデバイスの両方をリセットします。

EXECUTE DEVICE DIAGNOSTICコマンド

ATA/ATAPI標準では正確に記述されていませんが、EDDはある程度のリセットを意味し、ソフトウェアリセットと同様のレベルのリセットを含む可能性があります。ホスト側のEDDプロトコルは通常のコマンド処理で扱うことができ、ほとんどのSATAコントローラーは他のコマンドと同様にEDDを処理できます。ソフトウェアリセットと同様に、PATAバス上の両方のデバイスに影響を与えます。

EDDはデバイスをリセットしますが、エラー処理には不適切です。BSYがセットされている間EDDを実行することはできず、デバイスが未知/異常な状態にあるときにどのように動作するかは不明です。

ATAPI DEVICE RESETコマンド

これはソフトウェアリセットと非常に似ていますが、選択したデバイスだけをリセットし、ケーブルを共有する他のデバイスに影響を与えないようにできます。

SATA PHYリセット

これはSATAデバイスをリセットする推奨される方法です。実際にはPATAハードウェアリセットと同一です。この操作は標準SCRコントロールレジスタで実行できるため、ソフトウェアリセットより通常は実装が簡単です。

デバイスをリセットする際には、リセットによって特定の設定パラメータがクリアされるため、リセット後にそれらを以前の値または新たに調整した値に戻す必要があります。

影響を受けるパラメータは以下の通りです。

  • INITIALIZE DEVICE PARAMETERSで設定されたCHS（ほぼ使用されません）

  • SET FEATURESで設定されたパラメータ（転送モード設定を含む）

  • SET MULTIPLE MODEで設定されたブロック数

  • その他のパラメータ（SET MAX、MEDIA LOCK…）

ATA/ATAPI標準では、ハードウェアまたはソフトウェアのリセット時に一部のパラメータが保持されることが規定されていますが、すべてを厳密に規定していません。信頼性を確保するためには、リセット後に必要なパラメータを再構成する必要があります。なお、これはディープスリープ（電源オフ）からの復帰時にも同様に適用されます。

また、ATA/ATAPI標準では、設定パラメータが更新された後またはハードウェアリセット後にIDENTIFY DEVICE / IDENTIFY PACKET DEVICEコマンドを実行し、その結果を次の操作に使用する必要があります。OSドライバーはこの動作をサポートするため、再検証メカニズムを実装する必要があります。

トランスポートの再構成¶

PATAおよびSATAの両方において、安価なコネクタ、ケーブル、コントローラーのために多くの設計が省略されており、高伝達エラー率が見られることがよくあります。これは伝達速度を下げるにより緩和できます。

Jeff Garzikが提案した可能性のあるスキームは以下の通りです。

15分間に$N（3？）以上の伝達エラーが発生した場合、

  • SATAの場合、SATA PHY速度を下げる。速度を下げることが出来ない場合は、

  • UDMA転送速度を下げる。UDMA0の場合、PIO4に切り替える、

  • PIO転送速度を下げる。PIO3の場合、警告を出すが継続する

デバイス/ホスト固有のエラーフィックスアップを適用

パラメータ

struct ata_device *dev

検査対象のデバイス

IDENTIFY [PACKET] DEVICEステップが完了し、デバイスが存在していることが確認された後、この関数が呼び出されます。シリコンイメージ固有の2つのエラーフィックスアップを適用します。そのうち1つはシーゲート向け、もう1つはマクターボ向けです。

特定のシーゲートデバイスでは、最大セクタ数を8K未満に制限する必要があります。

特定のマクターボデバイスでは、ドライブをudma5を超えてプログラミングしてはいけません。

これらのフィックスアップはどちらも過度に慎重すぎます。これらのエラーフィックスアップに関する情報がさらに得られ次第、より詳細なリストを作成し、必要なデバイス/ホスト/ファームウェアにのみ適用します。

20040111 - Mod15Writeバグに影響を受けるシーゲートドライブはブラックリストに登録されています。マクターボのクイアはブラックリストに含まれていますが、以下の理由で元の慎重なフィックスアップを維持しています… - この情報は少なく、Windowsドライバから得られたデバイスは1つだけかもしれません。影響を受けるのはおそらく1台だけです。情報がもっとあれば大変助かります。- しかし、UDMA5自体はあまり気にする必要がないでしょう。

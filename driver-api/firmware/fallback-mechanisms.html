フェールバックメカニズム¶

ルートファイルシステムでの直接ファイルシステム検索に失敗する場合や、ファームウェアを実用上ルートファイルシステムにインストールできない場合にも、フォールバックメカニズムをサポートしています。ファームウェアフォールバックメカニズムをサポートするためのカーネル構成オプションは以下の通りです:

  • CONFIG_FW_LOADER_USER_HELPER: ファームウェアフォールバックメカニズムをビルドするためのオプションを有効にします。現在、ほとんどのディストリビューションがこのオプションを有効にしています。有効になっていてもCONFIG_FW_LOADER_USER_HELPER_FALLBACKが無効な場合、みずからカスタムフォールバックメカニズムのみが利用可能で、 request_firmware_nowait() 呼び出し時にkdumpが発生します。

  • CONFIG_FW_LOADER_USER_HELPER_FALLBACK: すべてのファームウェアAPI呼び出しにおいて、kobject ueventフォールバックメカニズムを強制的に有効にするオプションです。ただし、 request_firmware_direct()は除きます。現在、ほとんどのディストリビューションはこのオプションを無効にしています。呼び出し request_firmware_nowait() により、1つの代替フォールバックメカニズムが利用可能になります: このkconfigオプションが有効になっていて、あなたの第二引数を request_firmware_nowait()、uevent、をfalseに設定した場合、カーネルにカスタムフォールバックメカニズムを使用することを通知し、手動でファームウェアをロードします。詳細については下記を参照してください。

この構成を持つ場合、

CONFIG_FW_LOADER_USER_HELPER=y CONFIG_FW_LOADER_USER_HELPER_FALLBACK=n

のとき、kobject ueventフォールバックメカニズムは常に有効になりません。これは、ueventがtrueに設定されてもです。 request_firmware_nowait() 直接ファイルシステム検索が失敗する理由はいくつかあります。この理由を明記しておくことで、フォールバックメカニズムの必要性を説明できます:

ファームウェアのフォールバックメカニズムの正当性¶

起動時のルートファイルシステムへのアクセスとの競合。

  • スリープからの再開時の競合。これはファームウェアキャッシュで解決されますが、ファームウェアキャッシュはueventsを使用する場合にのみサポートされ、

  • にはサポートされていません。 request_firmware_into_buf().

  • ファームウェアが通常の手段でアクセスできない:

    • ルートファイルシステムにインストールできない

    • ファームウェアは、ユニット固有のデータをローカル情報とともに収集した非常にユニークなデバイス固有データを提供します。例はモバイルデバイス用のWiFiチップセットのカリブレーションデータです。このカリブレーションデータはすべてのユニットに共通ではなく、各ユニットごとにカスタマイズされています。このような情報は、ルートファイルシステムが提供される場所以外の別個のフラッシュパーティションにインストールされることがあります。

フォールバックメカニズムの種類¶

実際には、1つの共有sysfsインターフェースをロード用施設として使用して、2つのフォールバックメカニズムが利用可能です:

  • kobject ueventフォールバックメカニズム

  • カスタムフォールバックメカニズム

まず、共有sysfsロード施設をドキュメンテーションします。

ファームウェア sysfs ロード機能¶

デバイスドライバがフォールバックメカニズムを使用してファームウェアをアップロードするのを支援するために、ファームウェアインフラストラクチャはsysfsインターフェースを作成し、ユーザー空間がファームウェアをロードし、準備完了を示すことを可能にします。このsysfsディレクトリはfw_create_instance()によって作成されます。この呼び出しは、新しい struct device リクエストされたファームウェアに名前を付け、デバイス階層に組み込むために、リクエストを実行したデバイスをそのデバイスの親として関連付けています。sysfsディレクトリのファイル属性は、新しいデバイスのクラス（firmware_class）とグループ（fw_dev_attr_groups）を通じて定義され制御されます。これはもともとfirmware_classモジュール名の出所であり、もともと利用可能なファームウェアロードメカニズムは現在のフォールバックメカニズムとして使用されるものであり、これはstruct class firmware_classを登録するメカニズムでした。属性がモジュール名の一部であるため、将来モジュール名firmware_classを変更することはできません。これにより、古いユーザー空間との後方互換性が保証されます。

sysfsインターフェースを使用してファームウェアをロードするには、ロードインジケーターとファームウェアのアップロード先としてのファイルを提供します:

  • /sys/$DEVPATH/loading

  • /sys/$DEVPATH/data

ファームウェアをアップロードするには、loadingファイルに1をエコーバックしてファームウェアをロード中であることを示します。その後、dataファイルにファームウェアを書き込み、ロードが完了したことをカーネルに通知するために、loadingファイルに0をエコーバックします。

sysfsを使用してファームウェアをロードするためのファームウェアデバイスは、直接ファームウェアロードが失敗し、かつフォールバックメカニズムが有効化されている場合にのみ作成されます。これは firmware_fallback_sysfs()で設定されます。直接ファイルシステム検索が成功した場合、どのデバイスも作成されないことに再び強調します。

使用:

echo 1 > /sys/$DEVPATH/loading

これにより、以前の部分的なロードを一度にクリーンアップし、ファームウェアAPIがエラーを返すようになります。ファームウェアをロードする際、firmware_classはPAGE_SIZE単位でバッファを拡張し、画像を取得するたびに保持します。

firmware_data_read()とfirmware_loading_show()はテスト_firmwareドライバのテスト用に提供されており、通常の使用では呼び出されず、ユーザー空間が定期的に使用することを期待していません。

firmware_fallback_sysfs¶

int firmware_fallback_sysfs(struct firmware *fw, const char *名前, struct デバイス *デバイス, u32 opt_flags, int ret)¶

フォールバックメカニズムを使用してファームウェアを検索する

パラメータ

struct firmware *fw

ファームウェアイメージへのポインタ

const char *name

検索するファームウェアファイル名

struct device *device

ファームウェアをロードしているデバイス

u32 opt_flags

ファームウェアロード動作を制御するオプション、これは enum fw_opt

int ret

直接検索によってトリガーされたフォールバックメカニズムの戻り値

説明

ファームウェアの直接検索が失敗した場合にこの関数が呼び出されます。これは、ユーザー空間を通じてフェールバックメカニズムを有効にするため、sysfsロードインターフェースを公開します。ユーザー空間はsysfsロードインターフェースを通じてファームウェアをロードする責任があります。このsysfsのフェールバックメカニズムは、ignore_sysfs_fallbackをtrueに設定することでシステム全体で無効にすることができます。この値がfalseの場合、内部APIの呼び出し元がFW_OPT_NOFALLBACK_SYSFSフラグを設定したかどうかを確認します。 FW_OPT_NOFALLBACK_SYSFS 設定されている場合、フェールバックメカニズムも無効になります。システムが常にsysfsフェールバックメカニズムを強制的に有効にしたい場合、ignore_sysfs_fallbackをfalseに設定し、force_sysfs_fallbackをtrueに設定することで実現できます。force_sysまって_fallbackを有効にすることは、CONFIG_FW_LOADER_USER_HELPER_FALLBACKを含むカーネルをビルドすることと機能的に同等です。

ファームウェア kobject uevent フォールバックメカニズム¶

sysfsインターフェースを通じてファームウェアのフェールバックロードを支援するデバイスが作成されるため、ユーザー空間はkobject ueventsに依拠してデバイスの追加を通知されます。デバイスがデバイス階層に追加されることで、ファームウェアロードのフェールバックメカニズムが開始されます。実装の詳細についてはfw_load_sysfs_fallback()を参照してください。特にdev_set_uevent_suppress()とkobject_uevent()の使用について注目してください。

カーネルのkobject ueventメカニズムはlib/kobject_uevent.cで実装されており、ユーザー空間にueventsを発行します。kobject ueventsに加えて、LinuxディストリビューションはCONFIG_UEVENT_HELPER_PATHを有効化することで、カーネルのユーザー空間ヘルパ（UMH）機能を活用して、kobject uevents用のユーザー空間ヘルパを呼び出すことができます。実際には、どの標準ディストリビューションもCONFIG_UEVENT_HELPER_PATHを使用したことはありません。CONFIG_UEVENT_HELPER_PATHが有効な場合、このバイナリはカーネル内のkobject_uevent_env()が呼び出されるたびに実行されます。

ユーザースペースでさまざまな実装がサポートされており、このフォールバックメカニズムを活用しています。ファームウェアのロードは以前はsysfsメカニズムのみで可能でしたが、ユーザースペースのコンポーネント「hotplug」がkobjectイベントのモニタリング機能を提供していました。歴史的にこれはsystemdのudevによって置き換えられましたが、2014年8月にsystemdのコミットbe2ea723b1d0（「udev: userspace firmware loading supportの削除」）でudevからファームウェアロードサポートが削除されました。これにより、現在のほとんどのLinuxディストリビューションは、kobject ueventsによって提供されるファームウェアフォールバックメカニズムを利用していないことがわかります。これは、ほとんどのディストリビューションがCONFIG_FW_LOADER_USER_HELPER_FALLBACKを無効にしているためさらに悪化しています。

kobjectイベント変数の設定詳細についてはdo_firmware_uevent()を参照してください。現在、"kobject add"イベントでユーザースペースに渡される変数は以下の通りです。

  • FIRMWARE=ファームウェア名

  • TIMEOUT=タイムアウト値

  • ASYNC=APIリクエストが非同期かどうか

デフォルトではDEVPATHは内部のカーネルkobjectインフラストラクチャによって設定されます。以下に簡単なkobject ueventスクリプトの例を示します。

# Both $DEVPATH and $FIRMWARE are already provided in the environment.
MY_FW_DIR=/lib/firmware/
echo 1 > /sys/$DEVPATH/loading
cat $MY_FW_DIR/$FIRMWARE > /sys/$DEVPATH/data
echo 0 > /sys/$DEVPATH/loading

ファームウェアカスタムフォールバックメカニズム¶

の利用者は request_firmware_nowait() 呼び出しにはさらに別のオプションが利用可能です：sysfsフォールバックメカニズムに依存するが、ユーザースペースにkobject ueventsを発行しないようにリクエストします。このロジックの元々の目的は、udev以外のユーティリティが非伝統的なパス（セクション「直接ファイルシステム検索」に記載されたリスト外のパス）からファームウェアを検索する必要がある場合に備えていました。このオプションは、他のAPI呼び出しには利用できません（ueventsは常に強制されます）。

ueventsはフォールバックメカニズムがカーネルで有効になっている場合にのみ意味を持つため、フォールバックメカニズムが有効になっていないカーネルでueventsを有効にするのは奇妙に思えます。残念ながら、ueventフラグは無効にすることができます。 request_firmware_nowait() ファームウェアキャッシュの設定にも利用されます。上記のドキュメンテーションによると、API呼び出しでueventが有効になっている場合にのみファームウェアキャッシュが設定されます。これにより、 request_firmware_nowait() 呼び出しではファームウェアキャッシュが無効になりますが、このAPIの利用者はキャッシュの無効化の目的でこのフラグを使用すべきではありません（これはフラグの元々の目的ではありません）。ueventフラグを設定しないということは、ファームウェアフォールバックメカニズムに参加したいが、kobject ueventsを抑制したいことを意味します。なぜなら、カスタムの解決策があり、デバイスがデバイス階層に追加されるのを監視し、カスタムパスを通じてファームウェアをロードするからです。

ファームウェアフォールバックタイムアウト¶

ファームウェアのフォールバックメカニズムにはタイムアウトがあります。タイムアウト値までにsysfsインターフェースにファームウェアがロードされない場合、ドライバにエラーが送信されます。UEVENTが必要な場合、デフォルトでは60秒がタイムアウト値として設定されますが、それ以外の場合はMAX_JIFFY_OFFSET（最大のタイムアウト値）が使用されます。非UEVENTの場合にMAX_JIFFY_OFFSETを使用する理由は、カスタムソリューションがファームウェアをロードするのに必要なだけの時間を確保できるためです。

ファームウェアのタイムアウトをカスタマイズするには、次のファイルに望ましいタイムアウト値をechoコマンドで指定してください：

  • /sys/class/firmware/timeout

このファイルに0をechoするとMAX_JIFFY_OFFSETが使用されます。タイムアウト値のデータ型は整数型です。

EFI 埋め込まれたファームウェアフォールバックメカニズム¶

一部のデバイスでは、システムのEFIコード／ROMにシステムの統合周辺デバイス用のファームウェアの埋め込まれたコピーが含まれている場合があり、その周辺デバイスのLinuxドライバがこのファームウェアにアクセスする必要があります。

このようなファームウェアが必要なデバイスドライバは、 firmware_request_platform() 関数を使用できます。ただし、これは他のフォールバックメカニズムとは別のフォールバックメカニズムであり、sysfsインターフェースを使用していません。

この機能が必要なデバイスドライバは、efi_embedded_fw_desc構造体を使用して必要なファームウェアを記述できます：

struct efi_embedded_fw_desc¶

この構造体はEFI埋め込みファームウェアコードが埋め込まれたファームウェアを検索するために使用されます。

定義

struct efi_embedded_fw_desc {
  const char *name;
  u8 prefix[EFI_EMBEDDED_FW_PREFIX_LEN];
  u32 length;
  u8 sha256[32];
};

メンバ

name

見つかった場合にファームウェアを登録するための名前

prefix

ファームウェアの最初の8バイト

length

バイト数（プレフィックスを含む）

sha256

ファームウェアのSHA256ハッシュ

EFI埋め込みファームウェアコードは、EFI_BOOT_SERVICES_CODEメモリセグメントをスキャンし、prefixと一致する8バイトのシーケンスを検索します。prefixが見つかった場合、lengthバイトのSHA256を計算し、それが一致した場合、lengthバイトのコピーを作成して見つかったファームウェアの一覧に追加します。

すべてのシステムでこの少しコストのかかるスキャンを避けるために、DMIマッチングが使用されます。ドライバはdmi_system_id配列をエクスポートし、各エントリのdriver_dataがefi_embedded_fw_descを指す必要があります。

この配列をefi-embedded-fwコードに登録するには、ドライバは以下の手順を実行する必要があります：

  1. 常にカーネルに組み込まれるか、またはdmi_system_id配列を常に組み込まれる別のオブジェクトファイルに保存する必要があります。

  2. include/linux/efi_embedded_fw.hにdmi_system_id配列のextern宣言を追加します。

  3. drivers/firmware/efi/embedded-firmware.cのembedded_fw_tableにdmi_system_id配列を追加し、ドライバが組み込まれていることをテストする#ifdefで囲みます。

  4. Kconfigエントリに「select EFI_EMBEDDED_FIRMWARE if EFI_STUB」を追加します。

以下の firmware_request_platform() 関数は常に指定された名前でディスクから直接ファームウェアをロードしようとします。そのため、EFIに埋め込まれたファームウェアは常に/lib/firmware配下にファイルを置くことで上書きされます。

注意:

  1. EFIに埋め込まれたファームウェアのスキャンコードはstart_kernel()の終わり近くで実行され、rest_init()呼び出しの直前に位置します。通常のドライバやサブシステムがsubsys_initcall()で自身を登録する場合、これは問題になりません。これは、コードがより早く実行される場合、EFIに埋め込まれたファームウェアを使用できないことを意味します。

  2. 現在、EFIに埋め込まれたファームウェアコードはファームウェアが常に8バイトの倍数のオフセットから始まると仮定しています。これはご使用のケースで当てはまらない場合、修正するパッチを送ってください。

  3. 現在、EFIに埋め込まれたファームウェアコードはx86のみで動作します。他のアーキテクチャではEFI_BOOT_SERVICES_CODEがEFIに埋め込まれたファームウェアコードがスキャンする前に解放されるためです。

  4. 現在のEFI_BOOT_SERVICES_CODEの強引なスキャンは一時的な強引な解決策です。UEFI Platform Initialization (PI)仕様のFirmware Volumeプロトコルを使用する議論がありました。しかし、FVプロトコルは以下の理由で拒否されました: internal PI仕様の内部インターフェースに依存しており、1. PI仕様は周辺ファームウェアをまったく定義していません 2. PI仕様の内部インターフェースは後方互換性を保証しません。FVの実装詳細は変更される可能性があり、システムごとに異なります。FVプロトコルをサポートするのは困難です。これは意図的に曖昧にされているからです。

埋め込まれたファームウェアを確認し抽出する例¶

例えばSileadタッチスクリーンコントローラーの埋め込まれたファームウェアを確認するには、以下の手順を行います:

  1. カーネルコマンドラインにefi=debugを指定してシステムを起動します。

  2. cp /sys/kernel/debug/efi/boot_services_code?をホームディレクトリにコピーします。

  3. 16進数エディタでboot_services_code?ファイルを開き、Sileadファームウェアのマジックプレフィックス:F0 00 00 00 02 00 00 00を検索します。これにより、boot_services_code?ファイル内のファームウェアの開始アドレスが得られます。

  4. ファームウェアには特定のパターンがあります。これは8バイトのページアドレスで始まり、通常は最初のページにはF0 00 00 00 02 00 00 00が続き、その後32ビットワードアドレスと32ビット値のペアが続きます。ワードアドレスは各ペアごとに4バイト(1ワード)ずつ増加し、ページが完了するまで続きます。完了したページの後には新しいページアドレスが続き、さらにワードアドレスと値のペアが続きます。これにより非常に明確なパターンが形成されます。このパターンが途切れたら、boot_services_code?ファイル内のファームウェアの終端が得られます。

  5. 「dd if=boot_services_code? of=firmware bs=1 skip=<begin-addr> count=<len>」というコマンドでファームウェアを抽出できます。抽出したファームウェアファイルをhexエディタで確認し、ddパラメータが正しいことを確認してください。

  6. テストのために予期される名前で/lib/firmwareにコピーしてください。

  7. 抽出したファームウェアが動作する場合、得られた情報をefi_embedded_fw_desc構造体に記述し、『sha256sum firmware』を実行してsha256フィールドに使用するハッシュ値を取得してください。

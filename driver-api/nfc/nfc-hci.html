NFCコア用のHCIバックエンド¶

  • 著者: Eric Lapuyade, Samuel Ortiz

  • お問い合わせ: eric.lapuyade@intel.com, samuel.ortiz@intel.com

一般¶

HCIレイヤーはETSI TS 102 622 V10.2.0仕様の多くを実装しており、HCIベースのNFCドライバの簡単な作成を可能にします。HCIレイヤーはNFC Coreバックエンドとして動作し、抽象nfcデバイスを実装し、NFC Core APIをHCIコマンドおよびイベントに変換します。

HCI¶

HCIはNFC Coreにnfcデバイスとして登録されます。ユーザー空間からのリクエストはnetlinkソケットを経由してNFC Coreへ、そしてHCIへ送られます。この時点で、HCIコマンドの連続がホストコントローラー（チップ）内のHCIレイヤーに送信され、処理されます。コマンドは同期的に（送信コンテキストが応答を待つ状態で実行）または非同期的に（応答はHCI Rxコンテキストから返却）実行可能です。ホストコントローラーからHCIイベントも受信可能です。これらは処理され、必要に応じてNFC Coreへ変換して転送されます。HCIは独自イベントの処理や標準動作の上書きを可能にするハックを提供します。HCIは2つの実行コンテキストを使用します：

  • コマンド実行用：nfc_hci_msg_tx_work()。任意のタイミングで1つのコマンドのみが実行可能です。

  • 受信イベントおよびコマンドの配信用：nfc_hci_msg_rx_work()。

HCIセッション初期化¶

セッション初期化はHCI標準であり、残念ながら独自ゲートをサポートする必要があります。これはドライバがセッションに含まれるべき独自ゲートの一覧を渡すための理由です。HCIはhciデバイスが設定されるときにすべてのゲートにパイプが接続されていることを保証します。チップが事前にオープンされたゲートと擬似静的パイプをサポートする場合、ドライバはその情報をHCIコアに渡すことができます。

HCI ゲートとパイプ¶

ゲートはサービスが見つかる「ポート」を定義します。サービスにアクセスするには、そのゲートにパイプを作成してオープンする必要があります。この実装ではパイプは完全に非表示です。パブリックAPIはゲートのみを知っています。これはドライバがパイプに接続されているかを知らずに独自ゲートにコマンドを送信する必要があるためです。

ドライバインターフェース¶

ドライバは一般的に2つの部分から構成されます：物理リンク管理とHCI管理。これにより、i2c、spiなどさまざまなphyで接続可能なチップのドライバをより簡単に維持できます。

HCI管理¶

ドライバは通常、HCIに登録し、以下のエントリポイントを提供します：

struct nfc_hci_ops {
      int (*open)(struct nfc_hci_dev *hdev);
      void (*close)(struct nfc_hci_dev *hdev);
      int (*hci_ready) (struct nfc_hci_dev *hdev);
      int (*xmit) (struct nfc_hci_dev *hdev, struct sk_buff *skb);
      int (*start_poll) (struct nfc_hci_dev *hdev,
                         u32 im_protocols, u32 tm_protocols);
      int (*dep_link_up)(struct nfc_hci_dev *hdev, struct nfc_target *target,
                         u8 comm_mode, u8 *gb, size_t gb_len);
      int (*dep_link_down)(struct nfc_hci_dev *hdev);
      int (*target_from_gate) (struct nfc_hci_dev *hdev, u8 gate,
                               struct nfc_target *target);
      int (*complete_target_discovered) (struct nfc_hci_dev *hdev, u8 gate,
                                         struct nfc_target *target);
      int (*im_transceive) (struct nfc_hci_dev *hdev,
                            struct nfc_target *target, struct sk_buff *skb,
                            data_exchange_cb_t cb, void *cb_context);
      int (*tm_send)(struct nfc_hci_dev *hdev, struct sk_buff *skb);
      int (*check_presence)(struct nfc_hci_dev *hdev,
                            struct nfc_target *target);
      int (*event_received)(struct nfc_hci_dev *hdev, u8 gate, u8 event,
                            struct sk_buff *skb);
};

  • open()およびclose()はハードウェアのオン/オフを制御します。

  • hci_ready() は、HCI セッションが設定された後に呼び出されるオプションのエントリポイントです。ドライバーは HCI コマンドを使用して実行する必要のある追加の初期化処理を行うことができます。

  • xmit() は単にフレームを物理リンクに書き込むだけです。

  • start_poll() はハードウェアをポーリングモードに設定するオプションのエントリポイントです。ハードウェアが特許ゲートや HCI 標準と異なるメカニズムを使用する場合にのみ実装する必要があります。

  • dep_link_up() は P2P ターゲットが検出された後に呼び出され、ハードウェアパラメータを NFC コアに返すことで P2P 接続の設定を完了します。

  • dep_link_down() は P2P リンクを停止するため呼び出されます。

  • target_from_gate() は特許ゲートに対応する NFC プロトコルを返すオプションのエントリポイントです。

  • complete_target_discovered() はドライバーが発見したターゲットを自動起動するために必要な特許処理を実行するオプションのエントリポイントです。

  • im_transceive() は、特許 HCI コマンドを使用してデータをタグに送信する必要がある場合、ドライバーが実装する必要があります。一部のタグタイプはカスタムコマンドを必要とし、他のものは標準 HCI コマンドで書き込むことができます。ドライバーはタグタイプを確認し、特許処理を行うか、1 を返して標準処理を要求できます。データ交換コマンド自体は非同期で送信する必要があります。

  • tm_send() は P2P 接続の場合にデータを送信するため呼び出されます。

  • check_presence() は定期的にコアが呼び出して、アクティブなタグがまだフィールドにあるか確認するオプションのエントリポイントです。この関数が実装されていない場合、コアはユーザー空間に tag_lost イベントをプッシュできなくなります。

  • event_received() はチップから送信されたイベントを処理するため呼び出されます。ドライバーがイベントを処理するか、1 を返して HCI が標準処理を試みるよう指示できます。

RX パスでは、ドライバーは nfc_hci_recv_frame() を使用してチップから受信した HCP フレームを HCI にプッシュする責任があります。HCI は再集約と処理を担当します。この処理はスリープ可能なコンテキストから行う必要があります。

PHY 管理¶

物理リンク（I2C、…）の管理は以下の構造で定義されます：

struct nfc_phy_ops {
      int (*write)(void *dev_id, struct sk_buff *skb);
      int (*enable)(void *dev_id);
      void (*disable)(void *dev_id);
};
enable():

PHY をオン（電源投入）にして、データ転送に備える

disable():

PHY をオフにする

write():

データフレームをチップに送信します。注意点として、LLC などの上位レイヤーがフレームを再送信のために保存する場合、この関数は skb を変更してはいけません。また、成功時は 0 を、失敗時は負の値を返す必要があります。

チップから来るデータは直接 nfc_hci_recv_frame() に送信する必要があります。

LLC¶

CPUとチップ間の通信には、一般的にリンクレイヤープロトコルが必要です。これらはHCIレイヤーによって管理されるモジュールとして隔離されています。現在のモジュールは2つあります: nop（素直な転送）とshdlcです。新しいllcは以下の機能を実装しなければなりません:

struct nfc_llc_ops {
      void *(*init) (struct nfc_hci_dev *hdev, xmit_to_drv_t xmit_to_drv,
                     rcv_to_hci_t rcv_to_hci, int tx_headroom,
                     int tx_tailroom, int *rx_headroom, int *rx_tailroom,
                     llc_failure_t llc_failure);
      void (*deinit) (struct nfc_llc *llc);
      int (*start) (struct nfc_llc *llc);
      int (*stop) (struct nfc_llc *llc);
      void (*rcv_from_drv) (struct nfc_llc *llc, struct sk_buff *skb);
      int (*xmit_from_hci) (struct nfc_llc *llc, struct sk_buff *skb);
};
init():

プライベートストレージを割り当てて初期化する

deinit():

クリーンアップ

start():

論理的な接続を確立する

stop ():

論理的な接続を終了する

rcv_from_drv():

チップからHCIへ送られるデータを処理する

xmit_from_hci():

HCIからチップへ送られるデータを処理する

llcはnfcに登録されてから使用可能です。以下のように呼び出してください:

nfc_llc_register(const char *name, struct nfc_llc_ops *ops);

また、llcは物理的なリンクを処理しません。そのため、特定のチップドライバに対して、任意の物理リンクと任意のllcを混在させてしまうことが非常に簡単です。

インクルードされたドライバ¶

NXP PN544のHCIベースのドライバで、I2Cバスを介して接続し、shdlcを使用しています。

実行コンテキスト¶

実行コンテキストは以下の通りです: - IRQハンドラ（IRQH）: 高速で、スリープできません。受信フレームをHCIに送り、現在のllcに渡します。shdlcの場合、フレームはshdlcのrxキューにキューインされます。

  • SHDLCステートマシンワーカー（SMW）

    llc_shdlcが使用される場合のみ: shdlcのrxとtxキューを処理します。

    HCIコマンド応答を配信します。

  • HCI Tx Cmdワーカー（MSGTXWQ）

    HCIコマンドの実行をシリアル化します。

    応答タイムアウト時に実行を完了します。

  • HCI Rxワーカー（MSGRXWQ）

    受信したHCIコマンドまたはイベントを配信します。

  • ユーザースペースからのシステムコールコンテキスト（SYSCALL）

    NFCコアから呼び出されるHCIの任意のエントリポイント

SHDLCを使用したHCIコマンドの実行ワークフロー¶

HCIコマンドの実行は以下のAPIを使用して同期的に簡単に実行可能です:

int nfc_hci_send_cmd (struct nfc_hci_dev *hdev, u8 gate, u8 cmd,
                      const u8 *param, size_t param_len, struct sk_buff **skb)

このAPIはスリープ可能なコンテキストから呼び出さなければなりません。ほとんどの場合、これはシステムコールコンテキストです。skbは応答で受け取った結果を返します。

内部的には非同期で実行されます。このAPIは、HCIコマンドをキューイングし、スタック上のローカルな待機キューを設定し、 wait_event() 完了を待機します。待機は中断できません。これは、コマンドが短いタイムアウト後に必ず完了するという保証があるためです。

MSGTXWQコンテキストは次にスケジュールされ、nfc_hci_msg_tx_work()を呼び出します。この関数は次の待機中のコマンドをデキューイングし、shdlcである下層にそのHCPフラグメントを送信します。その後、タイムアウトエラーでコマンドを完了させるためのタイマを開始します。

SMWコンテキストがスケジュールされ、nfc_shdlc_sm_work()が呼び出されます。この関数はSHDLCフレームの送受信を処理します。ドライバのxmitを使用してフレームを送信し、ドライバのIRQハンドラからフィルルされたskbキューから受信フレームを取得します。SHDLCのI（情報）フレームのペイロードはHCPフラグメントです。これらは、応答、コマンド、イベントなどの完全なHCIフレームを形成するために集約されます。

HCI応答はこのコンテキストから即座にディスパッチされ、待機中のコマンド実行を解除します。応答処理では、nfc_hci_msg_tx_work()がコマンドを送信した際に提供された完了コールバックが呼び出されます。完了コールバックはその後、システムコールコンテキストを再開します。

このAPIを使用してコマンドを非同期的に実行することも可能です：

static int nfc_hci_execute_cmd_async(struct nfc_hci_dev *hdev, u8 pipe, u8 cmd,
                                     const u8 *param, size_t param_len,
                                     data_exchange_cb_t cb, void *cb_context)

ワークフローは同じですが、API呼び出しは即座に返却され、結果はSMWコンテキストからコールバックが呼び出されます。

HCIイベントまたはコマンドの受信ワークフロー¶

HCIコマンドまたはイベントはSMWコンテキストからディスパッチされません。代わりに、これらはHCI rx_queueにキューイングされ、HCI rxワーカーコンテキスト（MSGRXWQ）からディスパッチされます。この方法により、コマンドまたはイベントハンドラが他のコマンドを実行することも可能になります（例：PN544からNFC_HCI_EVT_TARGET_DISCOVEREDイベントを処理する際には、リーダーAゲートに対してANY_GET_PARAMETERを実行して、発見されたターゲットに関する情報を取得する必要があります）。

通常、このようなイベントはMSGRXWQコンテキストからNFCコアに伝播されます。

エラー管理¶

NFCコアリクエストの実行と同時に発生するエラーは、リクエストの実行結果として単純に返却されます。これらは扱いが簡単です。

非同期的に発生するエラー（例：バックグラウンドプロトコルハンドリングスレッド内で発生）は、上位レイヤーが下層で何かがうまくいかなかったことに気づかず、予期されるイベントがおそらく発生しないことを知る必要があります。このようなエラーの処理は以下の通りです：

  • ドライバ（pn544）が受信フレームを届けられなかった場合、エラーを記録し、その後のドライバ呼び出しでこのエラーが発生します。その後、標準のnfc_shdlc_recv_frame()関数にNULL引数を渡して上位に問題を報告します。shdlcはEREMOTEIOのスタイリッシュなステータスを記録し、これによりSMWが上位に報告します。

  • SMWは、受信および送信するshdlcフレームを処理するバックグラウンドスレッドであり、shdlcのsticky状態を確認し、shdlcまたはその下層で発生した回復不能なエラーにより動作できなくなった場合、HCIにその状態を報告します。shdlc接続中に問題が発生した場合は、接続完了を通じてエラーを報告します。

  • HCI: 内部のHCIエラー（フレームが失われた）が発生した場合、または下層からエラーが報告された場合、HCIは現在実行中のコマンドをそのエラーで終了させるか、コマンドが実行されていない場合はNFC Coreに直接通知します。

  • NFC Core: NFC Coreが下層からのエラーを通知され、ポーリングが有効な場合、タグが検出不可能であることをユーザー空間に通知するため、空のタグリストを伴うタグ発見イベントを送信します。ポーリングが無効でエラーがstickyな場合、下層は次回の呼び出し時にそのエラーを返します。

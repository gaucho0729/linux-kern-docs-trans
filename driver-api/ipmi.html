Linux IPMIドライバ¶

著者

Corey Minyard <minyard@mvista.com> / <minyard@acm.org>

Intelligent Platform Management Interface（IPMI）は、システムを監視する知能デバイスを制御するための標準インターフェースです。システム内のセンサーの動的発見を可能にし、センサーの監視やセンサー値の変化または特定の境界を超えた場合の通知を提供します。また、場所交換可能なユニット（FRU）用の標準化されたデータベースとウォッチドッグタイマーも備えています。

このドライバを使用するには、システム内にIPMIコントローラー（ベースボードマネジメントコントローラー（BMC）と呼ばれる）へのインターフェースと、IPMIシステムを使用できるマネジメントソフトウェアが必要です。

このドキュメントでは、Linux用IPMIドライバの使用方法について説明します。IPMI自体に詳しくない場合は、以下のウェブサイトをご覧ください https://www.intel.com/design/servers/ipmi/index.htm。IPMIは大規模なトピックであり、ここではすべてを網羅することはできません！

設定¶

Linux IPMIドライバはモジュール化されており、ハードウェアに応じていくつかの設定を選び、正しく動作させる必要があります。ほとんどの設定は「キャラクターデバイス」メニュー内のIPMIメニューで利用できます。

何をしても、「IPMIトップレベルメッセージハンドラ」を選択する必要があります。それ以降の選択肢は、必要条件やハードウェアに応じて異なります。

メッセージハンドラはユーザー層のインターフェースを提供しません。カーネルコード（例：ウォッチドッグ）は依然として使用可能です。ユーザー空間からアクセスが必要な場合は、「IPMIデバイスインターフェース」を選択する必要があります。

ドライバインターフェースはハードウェアに依存します。システムがIPMI用にSMBIOS情報を正しく提供する場合、ドライバが自動的に検出され、動作します。標準インターフェースを持つボード（これらは一般的に「KCS」、「SMIC」、「BT」のいずれか）の場合、「IPMI SIハンドラ」オプションを選択してください。また、IPMIマネジメントコントローラーへの直接I2Cアクセス用のドライバも存在します。一部のボードでサポートされていますが、すべてのボードで動作するかは不明です。この場合、「IPMI SMBusハンドラ」を選択してください。ただし、SMBIOS/APCI情報が誤っているか、存在しない場合、システムで動作するか試す準備が必要です。これらを有効にしてドライバが自動検出するのも安全です。

IPMIを持つシステムでは、一般的にACPIを有効にする必要があります。ACPIテーブルがシステムを記述している場合があります。

標準インターフェースを使用しており、ボードメーカーが正しく作業を実施した場合、IPMIコントローラーは自動的に検出される（ACPIまたはSMBIOSテーブル経由）ため、問題なく動作するはずです。残念ながら、多くのボードはこの情報を持っていません。ドライバーは標準的なデフォルト値を試みますが、これらが動作しない場合もあります。このような状況に陥った場合は、「SIドライバー」または「SMBusドライバー」セクションを参照し、手動でシステムを設定する方法を確認してください。

IPMIは標準的なウォッチドッグタイマを定義しています。この機能を有効にするには、「IPMI Watchdog Timer」のコンフィギュレーションオプションを使用してください。ドライバーをカーネルに組み込む場合、カーネルコマンドラインオプションを通じてタイマが初期化とともに起動するように設定できます。また、多くの他のオプションもあります。詳細については、「ウォッチドッグ」セクションを参照してください。注意点として、タイマが閉じた後でも動作を継続できるように設定することも可能です（デフォルトでは閉じた際に無効化されます）。'ウォッチドッグカード'メニューに移動し、「ウォッチドッグタイマサポート」を有効化し、「閉じてもウォッチドッグシャットダウンを無効化」オプションを有効にしてください。

IPMIコマンドを使用してIPMIシステムを電源を切ることも可能です。この操作を行うには、「IPMI Poweroff」を選択してください。ドライバーはシステムがIPMIで電源を切れるかどうか自動で検出します。システムがこの機能をサポートしない場合でも、この機能を有効にしても問題ありません。これはATCAシステム、Radisys CPI1カード、および標準のチャサジ管理コマンドをサポートするすべてのIPMIシステムで動作します。

ドライバーがパンク時にイベントログにイベントを記録するようにするには、「パンク時にすべてのBMCにパンクイベントを生成」オプションを有効にしてください。パンク文字列をOEMイベントを通じてイベントログに記録する場合は、「パンク文字列を含むOEMイベントを生成」オプションを有効にしてください。また、ipmi_msghandlerモジュールのパラメータ「panic_op」を「event」または「string」に設定することで、これらの機能を動的に有効化できます。このパラメータを「none」に設定すると、この機能は無効になります。

基本的な設計¶

Linux IPMIドライバーは非常にモジュール化されており柔軟に設計されており、必要な機能のみを組み合わせて使用できます。そのため、多くのコードの塊に分割されています。これらの塊（モジュール名ごと）は以下の通りです：

ipmi_msghandler - これはIPMIシステムの中心的なソフトウェアです。すべてのメッセージ、メッセージタイミング、および応答を処理します。IPMIユーザーはこのインターフェースに接続し、IPMI物理インターフェース（システム管理インターフェースと呼ばれるSMI）もここに接続されます。これにより、カーネル内でのIPMIインターフェースが提供されますが、アプリケーションプロセスが使用できるインターフェースは提供されません。

ipmi_devintf - これはIPMIドライバーのユーザーランド用IOCTLインターフェースを提供し、このデバイスの各オープンファイルはメッセージハンドラに接続され、IPMIユーザーとして動作します。

ipmi_si - 各種システムインターフェースをサポートするドライバーです。KCS、SMIC、BTインターフェースをサポートします。SMBusインターフェースまたはカスタムインターフェースを使用しない場合、このドライバーを使用する必要があります。

ipmi_ssif - SMBus経由でBMCにアクセスするドライバーです。これはI2CカーネルドライバーのSMBusインターフェースを使用してSMBus経由でIPMIメッセージを送受信します。

ipmi_powernv - POWERNVシステム上のBMCにアクセスするドライバーです。

ipmi_watchdog - IPMIはシステムに非常に機能的なウォッチドッグタイマが必要です。このドライバーはIPMIメッセージハンドラ上で標準的なLinuxウォッチドッグタイマインターフェースを実装します。

ipmi_poweroff - 一部のシステムではIPMIコマンドを介してオフにすることが可能です。

bt-bmc - これはメインドライバーの一部ではなく、BTインターフェースのBMC側インターフェースにアクセスするドライバーです。Linuxを実行しているBMCではホストへのインターフェースを提供するために使用されます。

これらはすべて構成オプションを通じて個別に選択可能です。

インターフェースに関する多くのドキュメンテーションはインクルードファイルに含まれています。IPMIのインクルードファイルは以下の通りです。

linux/ipmi.h - IPMIのユーザーランドインターフェースおよびIOCTLインターフェースを含みます。

linux/ipmi_smi.h - システム管理インターフェース（IPMIコントローラーに接続するもの）が使用するインターフェースを含みます。

linux/ipmi_msgdefs.h - 基盤となるIPMIメッセージングの一般的な定義を含みます。

アドレス指定¶

IPMIアドレッシングはIPアドレスとほぼ同じように動作し、異なるアドレスタイプを処理するオーバーレイがあります。オーバーレイは以下の通りです。

struct ipmi_addr
{
      int   addr_type;
      short channel;
      char  data[IPMI_MAX_ADDR_SIZE];
};

addr_typeはアドレスが実際に何であるかを決定します。ドライバーは現在、2種類のアドレスタイプを理解しています。

「システムインターフェース」アドレスは以下の通り定義されます：

struct ipmi_system_interface_addr
{
      int   addr_type;
      short channel;
};

タイプはIPMI_SYSTEM_INTERFACE_ADDR_TYPEです。これは現在のカード上のBMCに直接通信するためのもので、チャネルはIPMI_BMC_CHANNELでなければなりません。

IPMBバス経由で送信されるメッセージはIPMI_IPMB_ADDR_TYPEアドレスタイプを使用します。フォーマットは以下の通りです：

struct ipmi_ipmb_addr
{
      int           addr_type;
      short         channel;
      unsigned char slave_addr;
      unsigned char lun;
};

ここで「チャネル」は一般的にゼロですが、一部のデバイスでは複数のチャネルをサポートしており、これはIPMI仕様で定義されたチャネルに該当します。

メッセージ¶

メッセージは以下の通り定義されます：

struct ipmi_msg
{
      unsigned char netfn;
      unsigned char lun;
      unsigned char cmd;
      unsigned char *data;
      int           data_len;
};

ドライバはヘッダー情報の追加/削除を担当します。データ部分は送信するデータ（アドレス情報はここに含めないでください）または応答データです。応答の完了コードは「data」の最初の項目であり、これは仕様でメッセージが定義されているため、オフセットのカウントを少し簡単にするため、削除されません（:-）。

ユーザーランドからIOCTLインターフェースを使用する場合、"data"にデータブロックを提供し、それを埋め、data_lenにそのブロックの長さを設定する必要があります（メッセージを受信する場合も同様です）。そうでない場合、ドライバがメッセージを置く場所がありません。

カーネル空間のメッセージハンドラから届くメッセージは以下の形式で届きます:

struct ipmi_recv_msg
{
      struct list_head link;

      /* The type of message as defined in the "Receive Types"
         defines above. */
      int         recv_type;

      ipmi_user_t      *user;
      struct ipmi_addr addr;
      long             msgid;
      struct ipmi_msg  msg;

      /* Call this when done with the message.  It will presumably free
         the message and do any other necessary cleanup. */
      void (*done)(struct ipmi_recv_msg *msg);

      /* Place-holder for the data, don't make any assumptions about
         the size or existence of this, since it may change. */
      unsigned char   msg_data[IPMI_MAX_MSG_LENGTH];
};

受信タイプを確認し、メッセージを適切に処理する必要があります。

上位レイヤーインターフェース（メッセージハンドラ）¶

インターフェースの上位レイヤーはユーザーにIPMIインターフェースの一貫したビューを提供します。これにより複数のSMIインターフェースにアクセス可能（一部のボードには複数のBMCが存在するため）になり、ユーザーはSMIの種類を気にする必要がありません。

インターフェースの監視¶

コードが起動する際、IPMIドライバがIPMIデバイスの存在を検出しているかどうかは不明です。したがって、デバイスが検出されるまで設定を延期するか、即座に実行するかを選択する必要があります。これを処理し、発見を可能にするために、ipmi_smi_watcher_register()でSMIウォッチャーを登録し、インターフェースの変化を通知します。

ユーザーの作成¶

メッセージハンドラを使用するにはまずipmi_create_userでユーザーを作成します。インターフェース番号は接続したいSMIを指定し、データが届いた際に呼び出されるコールバック関数を提供する必要があります。コールバック関数は割込みレベルで実行されるため、注意が必要です。これにより、handler_dataというデータを渡すことができ、すべての呼び出しでこのデータが戻されます。

完了したらipmi_destroy_user()を呼び出してユーザーを削除します。

ユーザーランドでは、デバイスを開くと自動的にユーザーが作成され、閉じると自動的に削除されます。

メッセージング¶

カーネル空間からメッセージを送信する場合、ipmi_request_settime()呼び出しはほぼすべてのメッセージハンドリングを担当します。ほとんどのパラメータは自明ですが、"msgid"パラメータがあります。これはメッセージのシーケンス番号ではなく、メッセージ応答が返された際に戻される長値です。これを使用する用途は自由です。

応答は、ipmi_create_user()に渡した「handler」構造体のipmi_recv_hndlフィールドで指定された関数に返ってきます。再度お忘れしないでください、これらは割込みレベルで実行されている可能性があります。受信タイプも確認してください。

ユーザーランドでは、ipmi_req_t構造体を埋め込み、IPMICTL_SEND_COMMAND ioctlを使用してコマンドを送信します。受信データがあるのを待つにはselect()やpoll()を使用できます。ただし、read()関数は使用できません。メッセージを実際に取得するには、ipmi_recv_t構造体を用いてIPMICTL_RECEIVE_MSG ioctlを呼び出す必要があります。msg.dataフィールドにデータブロックへのポインタを指定し、msg.data_lenフィールドにデータのサイズを設定してください。これにより、受信側がメッセージを実際に格納できる場所を提供します。

メッセージが提供されたデータに収まらない場合、EMSGSIZEエラーが発生し、ドライバが受信キューにデータを残します。メッセージを取得し、メッセージをトリミングする場合はIPMICTL_RECEIVE_MSG_TRUNC ioctlを使用してください。

IPMBバス上でコマンドを送信する際（IPMI仕様に基づくnetfnの最下位ビットで定義）、ドライバが自動的にシーケンス番号を割り当て、コマンドを保存します。応答がIPMI仕様で指定された5秒以内に受信されない場合、ドライバが自動的にコマンドタイムアウトと通知する応答を生成します。5秒後に到着した不要な応答（例: 5秒後に到着した場合）は無視されます。

カーネル空間では、メッセージを受信し処理が終了した後、必ずipmi_free_recv_msg()を呼び出す必要があります。メッセージのリークを防ぐためです。メッセージの「done」フィールドを操作しないでください。これはメッセージの適切なクリーンアップに必要です。

送信時に、ipmi_request_supply_msgs()関数を使用してSMIと受信メッセージを提供できます。これはバッファが不足している場合でも動作するコードの実装に有用です（例: ワッチドッグタイマーやその他の用途）。自分でバッファと解放処理を提供しますが、通常の用途では推奨されません。自分のバッファ管理は複雑です。

イベントと受信コマンド¶

ドライバがIPMIイベントのポーリングとコマンド（他デバイスから送信されたメッセージ）の受信を担当します。これらを受信するには登録が必要です。自動的に通知されるわけではありません。

イベントを受信するには、ipmi_set_gets_events()を呼び出し、「val」をゼロ以外に設定する必要があります。ドライバ起動後でさえも受信されたイベントは、最初にイベントを登録したユーザーに即座に配信されます。その後、複数のユーザーがイベントを登録している場合、すべてのユーザーにすべてのイベントが届きます。

コマンドを受信するには、受信したいコマンドを個別に登録する必要があります。ipmi_register_for_cmd()を呼び出し、受信したい各コマンドのnetfnとコマンド名を指定してください。また、コマンドを受信したいチャネルのビットマスクも指定します（不要な場合はIPMI_CHAN_ALLを指定します）。netfn/cmd/チャネルごとに1つのユーザーのみが登録できますが、異なるコマンドや、チャネルビットマスクが重複しない同じコマンドを複数のユーザーが登録することも可能です。

ユーザーランドからも、これらの機能を行うための同等のIOCTLが提供されています。

下位レイヤー（SMI）インターフェース¶

前述の通り、複数のSMIインターフェースがメッセージハンドラに登録されることがあります。これらはメッセージハンドラに登録する際、インターフェース番号が割り当てられます。通常は登録順に割り当てられますが、SMIが登録を解除した後で再度登録する場合、すべての可能性が開きます。

ipmi_smi.hは管理インターフェースのインターフェースを定義しており、詳細はそちらをご確認ください。

SIドライバ¶

SIドライバは、システム内でKCS、BT、SMICインターフェースを構成できます。インターフェースはシステムに応じてさまざまな方法で検出されます。

モジュールロード時のラインで最大4つのインターフェースを指定でき、一部のモジュールパラメータを制御できます。

modprobe ipmi_si.o type=<type1>,<type2>....
     ports=<port1>,<port2>... addrs=<addr1>,<addr2>...
     irqs=<irq1>,<irq2>...
     regspacings=<sp1>,<sp2>,... regsizes=<size1>,<size2>,...
     regshifts=<shift1>,<shift2>,...
     slave_addrs=<addr1>,<addr2>,...
     force_kipmid=<enable1>,<enable2>,...
     kipmid_max_busy_us=<ustime1>,<ustime2>,...
     unload_when_empty=[0|1]
     trydmi=[0|1] tryacpi=[0|1]
     tryplatform=[0|1] trypci=[0|1]

これらの中ではtry…項目はリストであり、1番目の項目が1番目のインターフェース、2番目の項目が2番目のインターフェース、というように順番に割り当てられます。

si_typeは「kcs」「smic」「bt」のいずれかを指定できます。空白にするとデフォルトで「kcs」が選択されます。

インターフェースのaddrsをゼロ以外に指定した場合、ドライバは指定されたメモリアドレスをデバイスのアドレスとして使用します。これはsi_portsの設定を上書きします。

インターフェースのportsをゼロ以外に指定した場合、ドライバは指定されたI/Oポートをデバイスのアドレスとして使用します。

インターフェースのirqsをゼロ以外に指定した場合、ドライバは指定された割込みをデバイスに使用しようとします。

他のtry…項目は対応する名前で発見を無効にします。これらはすべてデフォルトで有効ですが、ゼロに設定して無効化できます。tryplatformはopenfirmwareの発見を無効にします。

次の3つのパラメータはレジスタレイアウトに関連しています。インターフェースで使用されるレジスタは連続する位置に配置されず、8ビットのレジスタである必要もありません。これらのパラメータは、レジスタ内のデータレイアウトをより正確に指定できるようにします。

regspacingsパラメータは、連続するレジスタ開始アドレス間のバイト数を指定します。例えば、regspacingが4に設定され、開始アドレスが0xca2の場合、2番目のレジスタのアドレスは0xca6になります。デフォルト値は1です。

regsizesパラメータは、レジスタのサイズをバイト単位で指定します。IPMIで使用されるデータは8ビット幅ですが、より大きなレジスタ内に含まれる場合があります。このパラメータは読み込みおよび書き込みタイプを指定します。値は1、2、4、または8のいずれかで、デフォルトは1です。

レジスタのサイズが32ビット以上である場合、IPMIデータが下位8ビットに配置されない可能性があります。regshiftsパラメータは、データをシフトして実際のIPMIデータにアクセスする量を指定します。

slave_addrsはローカルBMCのIPMIアドレスを指定します。通常は0x20で、ドライバーはこれをデフォルトとしていますが、その場合でない場合はドライバー起動時に指定できます。

force_ipmidパラメータは、1に設定するとカーネルIPMIデーモンを強制的に有効にし、0に設定すると無効にします。通常はドライバーが自動検出しますが、割り込みが破損しているシステムでは有効化が必要な場合があります。また、デーモンを必要としないユーザー（パフォーマンス不要、CPU負荷を避けたい）は無効化できます。

unload_when_emptyが1に設定されている場合、インターフェースが見つからないかすべてのインターフェースが動作しない場合、ドライバーがアンロードされます。デフォルトは1です。hotmodを使用する場合に0に設定するのが役立ちますが、モジュールでのみ有効です。

カーネルにコンパイルされた場合、パラメータはカーネルコマンドラインで指定できます:

ipmi_si.type=<type1>,<type2>...
     ipmi_si.ports=<port1>,<port2>... ipmi_si.addrs=<addr1>,<addr2>...
     ipmi_si.irqs=<irq1>,<irq2>...
     ipmi_si.regspacings=<sp1>,<sp2>,...
     ipmi_si.regsizes=<size1>,<size2>,...
     ipmi_si.regshifts=<shift1>,<shift2>,...
     ipmi_si.slave_addrs=<addr1>,<addr2>,...
     ipmi_si.force_kipmid=<enable1>,<enable2>,...
     ipmi_si.kipmid_max_busy_us=<ustime1>,<ustime2>,...

これは同じ名前のモジュールパラメータと同様の動作を行います。

IPMIインターフェースが割り込みをサポートせず、KCSまたはSMICインターフェースである場合、IPMIドライバーはインターフェース用にカーネルスレッドを起動して処理を高速化します。これは低優先度のカーネルスレッドで、IPMI操作中は常にIPMIドライバーをポーリングします。force_kipmidモジュールパラメータでこのスレッドを強制的に有効/無効にできます。割り込みがない状態で無効にするとドライバーが非常に遅くなります。これらのインターフェースのせいではありませんので、ご注意ください。

残念ながら、このスレッドはインターフェースの性能に応じてCPUを大量使用する可能性があります。これにより、CPUの無駄が生じ、アイドル状態のCPUの検出や余分な電力消費といったさまざまな問題が発生する可能性があります。これを避けるため、kipmid_max_busy_usはkipmidがスリープする前にスピンする最大時間をマイクロ秒単位で設定します。この値はパフォーマンスとCPUの無駄のバランスを調整するためのものであり、ユーザーのニーズに合わせて調整する必要があります。いつかは自動調整機能が追加されるかもしれませんが、それも簡単なことではなく、自動調整機能自体もユーザーの望むパフォーマンスに合わせて調整する必要があります。

ドライバーはインターフェースのホットアドとホットリムをサポートしています。これにより、カーネルが起動した後でもインターフェースを追加または削除できます。これは/sys/modules/ipmi_si/parameters/hotmodという書き込み専用パラメータを使用して行われ、このインターフェースに文字列を書き込みます。文字列の形式は以下の通りです：

<op1>[:op2[:op3...]]

「op」は以下の通りです：

add|remove,kcs|bt|smic,mem|i/o,<address>[,<opt1>[,<opt2>[,...]]]

1行に複数のインターフェースを指定できます。「opt」は以下の通りです：

rsp=<regspacing>
rsi=<regsize>
rsh=<regshift>
irq=<irq>
ipmb=<ipmb slave addr>

これらは上で説明した意味と同じです。注意点として、インターフェースを削除する際には、比較に使用されるのは最初の3つのパラメータ（siタイプ、アドレスタイプ、アドレス）のみであり、他のオプションは無視されます。また、インターフェースを指定する際には、カーネルコマンドラインでもよりコンパクトな形式で使用できます。

SMBusドライバ（SSIF）¶

SMBusドライバーはシステムに最大4つのSMBusデバイスを設定できます。デフォルトでは、ドライバーはDMIやACPIテーブルに記載されているデバイスのみに登録します。モジュールのロード時に以下のコマンドでこの挙動を変更できます：

modprobe ipmi_ssif.o
      addr=<i2caddr1>[,<i2caddr2>[,...]]
      adapter=<adapter1>[,<adapter2>[...]]
      dbg=<flags1>,<flags2>...
      slave_addrs=<addr1>,<addr2>,...
      tryacpi=[0|1] trydmi=[0|1]
      [dbg_probe=1]
      alerts_broken

アドレスは通常のI2Cアドレスです。アダプターはアダプターの文字列名で、/sys/class/i2c-adapter/i2c-<n>/nameに表示されている名前です。これは 禁止です i2c-<n>自身です。また、比較はスペースを無視して行われるため、名前が「This is an I2C chip」の場合、「adapter_name=ThisisanI2cchip」と指定できます。これはカーネルパラメータにスペースを渡すのが難しいためです。

デバッグフラグは各BMCに対してビットフラグで、以下の通りです：IPMIメッセージ: 1、ドライバーステート: 2、タイミング: 4、I2Cプローブ: 8

tryxxxパラメータは、さまざまなソースからのインターフェースの検出を無効にするために使用できます。

dbg_probeを1に設定すると、SMBus上のBMCのプローブと検出プロセスのデバッグが有効になります。

slave_addrsはローカルBMCのIPMIアドレスを指定します。通常は0x20で、ドライバーはこれをデフォルトとしていますが、その場合でない場合はドライバー起動時に指定できます。

alerts_brokenはSSIF用のSMBusアラートを有効にはしません。それ以外のサポートハードウェアではSMBusアラートが有効になります。

SMBus上でのIPMI準拠BMCの検出は、I2Cバス上のデバイスに障害を引き起こす可能性があります。SMBusドライバーはI2Cバスに対して「Get Device ID」IPMIメッセージをブロック書き込みとして送信し、応答を待機します。この動作は一部のI2Cデバイスにとって悪影響を及ぼす可能性があります。DMIまたはACPIデータでドライバーに使用するアドレスを指定できない限り、SMBusドライバーに既知のI2Cアドレスをsmb_addrパラメータで指定することをお勧めします。

カーネルに組み込まれた場合、カーネルコマンドラインでアドレスを指定できます。

ipmb_ssif.addr=<i2caddr1>[,<i2caddr2>[...]]
      ipmi_ssif.adapter=<adapter1>[,<adapter2>[...]]
      ipmi_ssif.dbg=<flags1>[,<flags2>[...]]
      ipmi_ssif.dbg_probe=1
      ipmi_ssif.slave_addrs=<addr1>[,<addr2>[...]]
      ipmi_ssif.tryacpi=[0|1] ipmi_ssif.trydmi=[0|1]

これらはモジュールコマンドラインと同じオプションです。

I2Cドライバーは非ブロッキングアクセスやポーリングをサポートしていないため、このドライバーは特別なカーネルパッチやドライバーモディファイを除き、IPMIパニックイベントの処理、パニック時のウォッチドッグの延長、またはその他のパニック関連のIPMI機能を実装できません。それらはopenipmiウェブページで入手できます。

このドライバーはI2C sysfsインターフェースを通じてインターフェースのホットアド/ホットレムをサポートしています。

その他の部品¶

IPMIデバイスに関する詳細情報を取得する¶

一部のユーザーは、デバイスの詳細な情報（アドレスの出所やIPMIインターフェースのrawベースデバイスなど）が必要な場合があります。IPMI smi_watcherを使用してIPMIインターフェースの出現・消失をキャッチし、情報の取得にはipmi_get_smi_info()関数を使用します。この関数は以下の構造体を返します：

struct ipmi_smi_info {
      enum ipmi_addr_src addr_src;
      struct device *dev;
      union {
              struct {
                      void *acpi_handle;
              } acpi_info;
      } addr_info;
};

現在はSI_ACPIアドレスソースに関する特別な情報のみが返されます。必要に応じて他のソースも追加される可能性があります。

上記構造体にはdevポインタが含まれており、ipmi_smi_get_infoが成功を返すと仮定する場合、devポインタに対してput_deviceを呼び出す必要があります。

ウォッチドッグ¶

Linux標準のウォッチドッグタイマーアクセスインターフェースを実装したウォッチドッグタイマが提供されています。このタイマは以下の3つのモジュールパラメータを使用して制御できます：

modprobe ipmi_watchdog timeout=<t> pretimeout=<t> action=<action type>
    preaction=<preaction type> preop=<preop type> start_now=x
    nowayout=x ifnum_to_use=n panic_wdt_timeout=<t>

ifnum_to_useはウォッチドッグタイマが使用するインターフェースを指定します。デフォルトは-1で、これは最初に登録されたインターフェースを選択することを意味します。

タイムアウトはアクションまでの秒数を表し、pretimeoutはリセット前のパニックが発生する秒数を表します（pretimeoutがゼロの場合、pretimeoutは無効になります）。注意点として、pretimeoutは最終タイムアウトの直前で発生します。タイムアウトが50秒でpretimeoutが10秒の場合、pretimeoutは40秒後に発生します（タイムアウトの10秒前）。panic_wdt_timeoutはカーネルパニック時に設定されるタイムアウト値で、パニック時のアクション（例：kdump）を実行できるようにします。

アクションは「reset」、「power_cycle」、「power_off」のいずれかであり、タイマがタイムアウトしたときに実行する操作を指定します。デフォルトは「reset」です。

プレアクションは「pre_smi」でSMIインターフェースを通じた指示、「pre_int」でSMIインターフェースを通じた割込みによる指示、「pre_nmi」でプレアクション時にNMIを発生させる場合を指定します。これはドライバがプレタイムアウトを通知される仕組みです。

プレオペレーションは「preop_none」でプレタイムアウト時に何も実行しない、「preop_panic」でプレオペレーションをパニック状態に設定、「preop_give_data」でプレタイムアウト発生時にウォッチドッグデバイスから読み取るデータを提供します。ただし、「pre_nmi」設定と「preop_give_data」は併用できません。NMIからデータ操作を行うことはできません。

プレオペレーションが「preop_give_data」に設定されている場合、プレタイムアウト発生時にデバイスから1バイトのデータが読み取れるようになります。デバイスのセレクトおよびfasync処理も行われます。

start_nowが1に設定されている場合、ドライバがロードされた直ちにウォッチドッグタイマが開始されます。

nowayoutが1に設定されている場合、ウォッチドッグデバイスが閉じてもタイマが停止しません。nowayoutのデフォルト値は、CONFIG_WATCHDOG_NOWAYOUTオプションが有効な場合はtrue、無効な場合はfalseです。

カーネルに組み込まれた場合、カーネルコマンドラインでウォッチドッグを設定できます:

ipmi_watchdog.timeout=<t> ipmi_watchdog.pretimeout=<t>
      ipmi_watchdog.action=<action type>
      ipmi_watchdog.preaction=<preaction type>
      ipmi_watchdog.preop=<preop type>
      ipmi_watchdog.start_now=x
      ipmi_watchdog.nowayout=x
      ipmi_watchdog.panic_wdt_timeout=<t>

オプションはモジュールパラメータのオプションと同一です。

プレアクションを受信した場合、ウォッチドッグはパニック状態になり、120秒のリセットタイマを開始します。パニックまたは再起動中にウォッチドッグが動作している場合、再起動が確実に実行されるよう120秒タイマを開始します。

NMIプレアクションを使用する場合、nmi watchdogを使用してはいけません。IPMIコントローラーからのNMIの出所を判断する合理的な方法が存在しないため、未処理のNMIが発生した場合はIPMIからのものとみなされ、即座にパニック状態になります。

ウォッチドッグタイマを開いた後は、デバイスに'V'文字を書き込む必要があります。それ以外の場合、タイマは停止しません。これはドライバの新しいセマンティクスですが、Linuxの他のウォッチドッグドライバと整合性を持たせています。

パニックタイムアウト¶

OpenIPMIドライバは、パニック発生時にシステムイベントログにセミカスタムおよびカスタムイベントを記録する機能をサポートしています。『パニック発生時にすべてのBMCにパニックイベントを生成』オプションを有効にすると、標準のIPMIイベント形式でパニックイベントが1つ生成されます。『パニック文字列を含むOEMイベントを生成』オプションを有効にすると、パニック文字列を保持するOEMイベントが複数生成されます。

イベントのフィールド設定は:

  • ジェネレータID: 0x21（カーネル）

  • EvM Rev: 0x03（このイベントはIPMI 1.0形式でフォーマットされています）

  • センサータイプ: 0x20（OSの緊急停止センサー）

  • センサーナンバー: パニック文字列の最初のバイト（パニック文字列がない場合は0）

  • イベントディレクション | イベントタイプ: 0x6f（アサーション、センサースペシフィックイベント情報）

  • イベントデータ1: 0xa1（OEMバイト2および3でのランタイム停止）

  • イベントデータ2: パニック文字列の2番目のバイト

  • イベントデータ3: パニック文字列の3番目のバイト

イベントレイアウトの詳細はIPMI仕様を参照してください。このイベントは常にローカルマネジメントコントローラーに送信されます。メッセージを適切な場所にルーティングする処理を行います

他のOEMイベントは次の形式を持ちます:

  • レコードID（バイト0-1）: SELによって設定されます

  • レコードタイプ（バイト2）: 0xf0（OEM非タイムスタンプ）

  • バイト3: パニックを保存したカードのスレーブアドレス

  • バイト4: シーケンス番号（ゼロから始まる）残りのバイト（11バイト）はパニック文字列です。パニック文字列が11バイト以上の場合、シーケンス番号を増やしながら複数のメッセージが送信されます

標準インターフェースでOEMイベントを送信することはできませんため、この機能はSELを探してそこでイベントを追加します。まずローカルマネジメントコントローラーの機能を照会します。SELがある場合、ローカルマネジメントコントローラーのSELに保存されます。なければ、ローカルマネジメントコントローラーがイベントジェネレータである場合、そのイベントレシーバーを照会し、デバイスのSELにイベントを送信します。それ以外の場合は、送信先が存在しないためイベントは送信されません

電源オフ¶

電源オフ機能を選択した場合、IPMIドライバは標準電源オフ関数ポインタにシャットダウン関数をインストールします。これはipmi_poweroffモジュール内にあります。システムが電源オフを要求した場合、適切なIPMIコマンドを送信して処理します。これは複数のプラットフォームでサポートされています

「poweroff_powercycle」パラメータはゼロ（電源オフ）または非ゼロ（電源サイクル、システムをオフにして数秒後に再起動）を指定できます。kernelコマンドラインでipmi_poweroff.poweroff_control=xと設定すると同じ動作になります。このパラメータは/proc/sys/dev/ipmi/poweroff_powercycleでも利用可能です。注意点として、システムが電源サイクルをサポートしない場合、常に電源オフが行われます

「ifnum_to_use」パラメータは電源オフコードが使用するインターフェースを指定します。デフォルトは-1で、最初に登録されたインターフェースを選択します

ACPIが有効になっている場合、システムはACPIを優先して電源オフを行います

共通のCLKフレームワーク¶

著者

マイク・ターキュート <mturquette@ti.com>

このドキュメントでは、共通のCLKフレームワークの詳細について説明し、プラットフォームをこのフレームワークに移植する方法についても述べます。現在は、include/linux/clk.hにあるクロックAPIの詳細な説明ではありませんが、いつかはその情報も含むかもしれません。

導入とインターフェースの分割¶

共通のCLKフレームワークは、現在のデバイスにあるクロックノードを制御するインターフェースです。これはクロックゲート、レート調整、MUXング、またはその他の操作の形で提供されることがあります。このフレームワークはCONFIG_COMMON_CLKオプションで有効になります。

インターフェース自体は2つの半分に分かれています。それぞれが対応する相手の詳細を遮蔽しています。まず、struct clkの共通定義があり、これはフレームワークレベルでのアカウントとインフラストラクチャを統合しており、これまで複数のプラットフォームで複製されていました。次に、clk.h APIの共通実装があり、drivers/clk/clk.cに定義されています。最後に、struct clk_opsがあり、その操作がclk APIの実装によって呼び出されます。

インターフェースの後半は、struct clk_opsに登録されたハードウェア固有のコールバックと、特定のクロックをモデル化するために必要なハードウェア固有の構造体で構成されています。このドキュメントの残りの部分では、struct clk_ops内のコールバック（例: .enableや.set_rate）への参照は、そのコードのハードウェア固有の実装を指します。同様に、struct clk_fooへの参照は、仮想の「foo」ハードウェアのハードウェア固有の実装を簡潔に表すための便宜的な略語です。

このインターフェースの2つの半分を結びつけるのはstruct clk_hwです。これはstruct clk_foo内で定義され、struct clk_core内にポインタとして指されます。これにより、共通クロックインターフェースの2つの離れた半分間の簡単な移動が可能になります。

共通データ構造とAPI¶

以下はdrivers/clk/clk.cから抜粋した共通struct clk_coreの定義で、簡潔にするために修正しています:

struct clk_core {
        const char              *name;
        const struct clk_ops    *ops;
        struct clk_hw           *hw;
        struct module           *owner;
        struct clk_core         *parent;
        const char              **parent_names;
        struct clk_core         **parents;
        u8                      num_parents;
        u8                      new_parent_index;
        ...
};

上記のメンバはclkツリーのトポロジーの中心を成しています。clk API自体は、struct clkを操作するドライバ向けの複数の関数を定義しており、そのAPIはinclude/linux/clk.hにドキュメンテーションされています。

共通struct clk_coreを採用しているプラットフォームやデバイスは、struct clk_core内のstruct clk_opsポインタを使用して、clk-provider.hで定義された操作のハードウェア固有の部分を実行します:

struct clk_ops {
        int             (*prepare)(struct clk_hw *hw);
        void            (*unprepare)(struct clk_hw *hw);
        int             (*is_prepared)(struct clk_hw *hw);
        void            (*unprepare_unused)(struct clk_hw *hw);
        int             (*enable)(struct clk_hw *hw);
        void            (*disable)(struct clk_hw *hw);
        int             (*is_enabled)(struct clk_hw *hw);
        void            (*disable_unused)(struct clk_hw *hw);
        unsigned long   (*recalc_rate)(struct clk_hw *hw,
                                        unsigned long parent_rate);
        long            (*round_rate)(struct clk_hw *hw,
                                        unsigned long rate,
                                        unsigned long *parent_rate);
        int             (*determine_rate)(struct clk_hw *hw,
                                          struct clk_rate_request *req);
        int             (*set_parent)(struct clk_hw *hw, u8 index);
        u8              (*get_parent)(struct clk_hw *hw);
        int             (*set_rate)(struct clk_hw *hw,
                                    unsigned long rate,
                                    unsigned long parent_rate);
        int             (*set_rate_and_parent)(struct clk_hw *hw,
                                    unsigned long rate,
                                    unsigned long parent_rate,
                                    u8 index);
        unsigned long   (*recalc_accuracy)(struct clk_hw *hw,
                                        unsigned long parent_accuracy);
        int             (*get_phase)(struct clk_hw *hw);
        int             (*set_phase)(struct clk_hw *hw, int degrees);
        void            (*init)(struct clk_hw *hw);
        void            (*debug_init)(struct clk_hw *hw,
                                      struct dentry *dentry);
};

ハードウェアCLK実装¶

共通のstruct clk_coreの強さは、.opsと.hwポインタによって得られます。これらはstruct clkの詳細をハードウェア固有の部分から抽象化し、逆もまた然りです。例を挙げて説明します。drivers/clk/clk-gate.cにある単純なゲート可能clkの実装をご覧ください:

struct clk_gate {
        struct clk_hw   hw;
        void __iomem    *reg;
        u8              bit_idx;
        ...
};

struct clk_gateはstruct clk_hw hwを含むだけでなく、ハードウェア固有の知識も持っています。これは、このclkのゲートを制御するレジスタとビットに関する情報です。クロックのトポロジーやアカウントに関する情報（enable_countやnotifier_countなど）はここには必要ありません。これらはすべて共通フレームワークコードとstruct clk_coreによって処理されます。

ドライバコードからこのclkを有効化する際の手順を確認しましょう:

struct clk *clk;
clk = clk_get(NULL, "my_gateable_clk");

clk_prepare(clk);
clk_enable(clk);

clk_enableの呼び出しグラフは非常にシンプルです:

clk_enable(clk);
        clk->ops->enable(clk->hw);
        [resolves to...]
                clk_gate_enable(hw);
                [resolves struct clk gate with to_clk_gate(hw)]
                        clk_gate_set_bit(gate);

clk_gate_set_bitの定義は以下の通りです:

static void clk_gate_set_bit(struct clk_gate *gate)
{
        u32 reg;

        reg = __raw_readl(gate->reg);
        reg |= BIT(gate->bit_idx);
        writel(reg, gate->reg);
}

to_clk_gateは以下のように定義されています:

#define to_clk_gate(_hw) container_of(_hw, struct clk_gate, hw)

この抽象化パターンはすべてのクロックハードウェア表現に適用されます。

独自のclkハードウェアのサポート¶

新しいタイプのクロックをサポートする際には、以下のヘッダーファイルを含むだけで十分です:

#include <linux/clk-provider.h>

プラットフォーム用のclkハードウェア構造体を構築するには、以下の定義が必要です:

struct clk_foo {
        struct clk_hw hw;
        ... hardware specific data goes here ...
};

データを活用するには、以下の操作をサポートする必要があります:

struct clk_ops clk_foo_ops = {
        .enable         = &clk_foo_enable,
        .disable        = &clk_foo_disable,
};

container_ofを使用して上述の関数を実装してください:

#define to_clk_foo(_hw) container_of(_hw, struct clk_foo, hw)

int clk_foo_enable(struct clk_hw *hw)
{
        struct clk_foo *foo;

        foo = to_clk_foo(hw);

        ... perform magic on foo ...

        return 0;
};

以下は、クロックのハードウェア能力に基づいた必須のclk_opsのマトリクスです。セルに「y」と記載されている場合は必須、「n」は無効または不要を意味します。空欄はケースバイケースで評価が必要です。

ロック¶

一般的なクロックフレームワークは、prepare lockとenable lockという2つのグローバルなロックを使用しています。

enable lockはスピンロックであり、.enableおよび.disable操作の呼び出し中に保持されます。したがって、これらの操作はスリープを許可されず、 clk_enable(), clk_disable() API関数はアトミックコンテキストで呼び出しが許可されています。

clk_is_enabled() APIについては、アトミックコンテキストでの使用も設計されています。ただし、コア内でenable lockを保持する必要性はほとんどありません。例外として、enable状態の情報をそのロックを保持しながら何か処理を行う場合を除けば、クロックが有効かどうかを確認する操作は単発の読み取りです。この関数が終了した後、ロックが解放されるため、有効状態が変化する可能性があります。したがって、このAPIのユーザーは、有効状態の読み取りとその用途との同期を確保する必要があります。

prepare lockはミューテックスであり、すべての他の操作呼び出し中に保持されます。これらの操作はすべてスリープが許可され、対応するAPI関数の呼び出しはアトミックコンテキストでは許可されません。

これにより、ロックの観点から操作を2つのグループに分けることが可能です。

ドライバは、1つのグループ内の操作間で共有されるリソースを手動で保護する必要はありません。ただし、2つのグループ間で共有されるリソースへのアクセスはドライバによって保護する必要があります。このようなリソースの例は、クロックレートとクロック有効/無効状態を制御するレジスタです。

クロックフレームワークは再入可能であり、ドライバがクロック操作の実装内でクロックフレームワーク関数を呼び出すことが許可されています。これは、あるクロックの.set_rate操作が別のクロックの.set_rate操作内で呼び出されるなどのケースを引き起こす可能性があります。このようなケースはドライバの実装で考慮する必要がありますが、通常ドライバがコードフローを制御します。

コードが一般的なクロックフレームワークの外側でクロック操作に使用されるリソースにアクセスする場合、ロックの考慮も必要です。これはこのドキュメントの範囲外とされています。

はじめに¶

RapidIO標準は、埋め込みシステムで使用されるパケットベースのファブリックインターコネクト標準です。RapidIO標準の開発はRapidIOトレード協会（RTA）が担当しています。現在のRapidIO仕様書はRTAウェブサイトからダウンロード可能です[1]。

このドキュメントではLinuxのRapidIOサブシステムの基本について説明し、主要なコンポーネントに関する情報を提供します。

1 概要¶

RapidIOサブシステムはLinuxデバイスモデルに準拠しているため、他のバスと同様にデバイスモデル内にRapidIO固有のデバイスおよびバスタイプを定義し、登録することでカーネルに統合されます。

Linux RapidIOサブシステムはアーキテクチャに依存せず、共通なRapidIOサブシステム操作をサポートするアーキテクチャ固有のインターフェースを定義しています。

2. コアコンポーネント¶

典型的なRapidIOネットワークはエンドポイントとスイッチの組み合わせです。これらの各コンポーネントはサブシステム内で関連するデータ構造として表されます。RapidIOサブシステムのコア論理コンポーネントはinclude/linux/rio.hファイルに定義されています。

2.1 マスターポート¶

マスターポート（またはmport）は、Linuxコードを実行しているプロセッサにローカルにあるRapidIOインターフェースコントローラーです。マスターポートはRapidIOパケット（トランザクション）を生成および受信します。RapidIOサブシステムにおいては、各マスターポートがrio_mportデータ構造体で表され、この構造体にはメールボックスやドアベルなどのマスターポート固有のリソースが含まれます。rio_mportには、マスターポートが列挙ホストとして構成されているときに有効な一意のホストデバイスIDも含まれています。

RapidIOマスターポートは、サブシステム固有のmportデバイスドライバーによってサービスされます。RapidIOサブシステム操作のハードウェアに依存しないインターフェースを提供するために、rio_mport構造体にはrio_opsデータ構造体が含まれており、これはハードウェア固有のRapidIO関数の実装ポインタを含みます。

2.2 デバイス¶

RapidIOデバイスはネットワーク内のエンドポイント（mportを除く）またはスイッチのいずれかです。すべてのデバイスはRapidIOサブシステムにおいて、対応するrio_devデータ構造体で表されます。デバイスはグローバルなデバイスリストおよびネットワークごとのデバイスリスト（利用可能なmportおよびネットワークの数に応じて）を形成します。

2.3 スイッチ¶

RapidIOスイッチは、ポート間でパケットを最終宛先へルーティングする特別なクラスのデバイスです。スイッチ内のパケット宛先ポートは内部ルーティングテーブルによって定義されます。RapidIOサブシステムでは、rio_devデータ構造体に追加されたrio_switchデータ構造体によってスイッチが表され、これはルーティングテーブルのコピーとスイッチ固有の関数へのポインタなど、スイッチ固有の情報を含みます。

RapidIOサブシステムは、サブシステム固有のスイッチドライバの形式と初期化方法を定義しており、これらはハードウェア固有の実装を提供する一般的なスイッチ管理ルーチンの実装を目的としています。

2.4 ネットワーク¶

RapidIOネットワークは、接続されたエンドポイントおよびスイッチデバイスの組み合わせです。システムが認識する各RapidIOネットワークは、対応するrio_netデータ構造体で表され、この構造体には同じネットワークを形成するすべてのデバイスとローカルマスターポートのリストが含まれます。また、ネットワーク内のデバイスと通信する際のデフォルトマスターポートへのポインタも含みます。

2.5 デバイスドライバ¶

RapidIOデバイス固有のドライバはLinuxカーネルドライバーモデルに従っており、RapidIOネットワークに接続された特定のRapidIOデバイスをサポートすることを目的としています。

2.6 サブシステムインターフェース¶

RapidIOインターコネクト仕様は、すべての参加RapidIOデバイスに共通サービスレイヤーを提供するための機能を定義しています。これらの共通サービスはデバイス固有のドライバとは別に動作するか、それらを介して利用されることがあります。このようなサービスプロバイダーの例としてRIONETドライバがあり、これはイーサネットオーバーRapidIOインターフェースを実装しています。1つのデバイスに対しては1つのドライバのみが登録可能であるため、すべての共通RapidIOサービスはサブシステムインターフェースとして登録する必要があります。これにより、複数の共通サービスが同じデバイスに接続されても、デバイス固有ドライバの接続を妨げることなく、それぞれが独立して動作できます。

3. サブシステム初期化¶

RapidIOサブシステムを初期化するには、プラットフォームがRapidIOネットワーク内で少なくとも1つのマスターポートを初期化し、登録する必要があります。サブシステムコントローラードライバの初期化コードでは、各利用可能なマスターポートに対してrio_register_mport()関数を呼び出してmportを登録します。

すべてのアクティブなマスターポートがRapidIOサブシステムに登録されると、自動的にもしくはユーザー空間コマンドによって列挙および/または発見ルーチンが呼び出されることがあります。

RapidIOサブシステムは、カーネルの静的リンクまたはモジュール型コンポーネントとして構築されることが可能です（以下に詳細を記載します）。

4. 列挙と発見¶

4.1 概要¶

RapidIOサブシステムの構成オプションにより、ユーザーは列挙および発見メソッドを静的リンクコンポーネントまたはロード可能なモジュールとして構築できます。列挙/発見メソッドの実装および利用可能な入力パラメータにより、任意のメソッドが利用可能なRapidIO mportsにどのように接続されるかが定義されます。つまり、すべての利用可能なmportsに単純に接続するか、指定されたmportデバイスに個別に接続するかです。

選択された列挙/発見ビルド構成に応じて、列挙および/または発見プロセスを開始する方法はいくつかあります：

(a) 静的リンクされた列挙および発見プロセスは、カーネル初期化時に対応するモジュールパラメータを使用して自動的に開始できます。これはRapidIOサブシステムの導入以来使用されてきた元の方法です。現在は、既存の基本的な列挙/発見メソッドに使用される「rio-scan.scan」 enumeratorモジュールパラメータに依存しています。自動的な列挙/発見開始を使用する場合、ユーザーはすべての発見エンドポイントが列挙エンドポイントよりも前に起動され、列挙完了を待機していることを確認する必要があります。構成オプションCONFIG_RAPIDIO_DISC_TIMEOUTは、発見エンドポイントが列挙完了を待つ時間を定義します。指定されたタイムアウトが切れると、発見プロセスはRapidIOネットワーク情報の取得せずに終了します。注意：タイムアウトした発見プロセスは、以下に記載されているユーザースペースコマンドを使用して後で再開できます（指定されたエンドポイントが成功裏に列挙された場合）。

(b) 静的リンクされた列挙および発, はユーザースペースからのコマンドで開始できます。この起動方法は、(a)のオプションに比べてシステム起動時の柔軟性が高くなります。すべての参加エンドポイントが成功裏に起動された後、ユーザースペースコマンドを実行してまず列挙プロセスを開始し、その後、残りのエンドポイントに対して発見プロセスを開始できます。

(c) モジュール化された列挙および発見プロセスはユーザースペースからのコマンドで開始できます。列挙/発見モジュールがロードされた後、ユーザースペースコマンドを実行してネットワークスキャンプロセスを開始できます。これは(b)のオプションと同様に、まずエナメーターアクセラレータを起動する必要があります。

(d) モジュール化された列挙および発見プロセスはモジュール初期化ルーチンから開始できます。この場合、まず列挙モジュールをロードする必要があります。

ネットワークスキャンプロセスが開始されると、マスターポートの設定された役割（ホストまたはエージェント）に応じて、一覧表示（enumeration）または発見（discovery）ルーチンが呼び出されます。

マスターポートがホストポートとして設定されている場合（ホスト宛先IDがゼロ以上である場合）、一覧表示が実行されます。ホスト宛先IDは、RapidIOサブシステムのビルド構成に応じてさまざまな方法でマスターポートに割り当てられます：

(a) 静的リンクされたRapidIOサブシステムコアを使用する場合、mportデバイス登録の順序に従って宛先IDの割り当てを指定するため、コマンドラインパラメータ「rapidio.hdid=」を使用します。たとえば、2つのRapidIOコントローラーを持つシステムでは、「rapidio.hdid=-1,7」というパラメータが指定されると、2番目のRapidIOコントローラーにホスト宛先ID=7が割り当てられ、1番目のコントローラーには宛先ID=-1が割り当てられます。

(b) RapidIOサブシステムコアがロード可能なモジュールとして構築されている場合、上記の方法に加えて、モジュールのロード時に伝統的な方法で「hdid=」パラメータを使用してホスト宛先IDを指定できます：

  • コマンドラインから：「modprobe rapidio hdid=-1,7」、または

  • modprobe設定ファイルで「options」コマンドを使用して指定します。例えば、「options rapidio hdid=-1,7」となります。以下にmodprobe設定ファイルの例を示します。

ノート：

(i) 「hdid=」パラメータを省略すると、すべてのmportに宛先ID=-1が割り当てられます。

(ii) 複数のmportを持つシステムでは、リストの末尾の宛先IDの割り当てを省略してもよい（デフォルト値=-1）。

特定のマスターポートのホストデバイスIDが-1に設定されている場合、発見プロセスが実行されます。

一覧表示および発見ルーチンは、RapidIOメンテナンストランザクションを使用してデバイスの設定領域にアクセスします。

ノート：RapidIOスイッチ固有のデバイスドライバーがロード可能なモジュールとして構築されている場合、一覧表示/発見プロセスが始まる前にこれらのモジュールをロードしておく必要があります。これは、一覧表示/発見メソッドが早期段階でベンダー固有のコールバックを呼び出すためです。

4.2 自動的な一覧表示および発見の開始¶

自動的な一覧表示/発見開始メソッドは、組み込みの一覧表示/発見RapidIO構成選択にのみ適用されます。既存の基本的なエナメーティングメソッドを使用して自動的な一覧表示/発見開始を有効にするには、ブートコマンドラインパラメータ「rio-scan.scan=1」を設定してください。

この設定では、ネットワークを形成するすべてのRapidIOエンドポイントの同期した起動が必要です。列挙/発見を行うエンドポイントは、列挙が開始される前に起動しておく必要があります。これにより、すべてのRapidIOコントローラーが初期化され、発見に準備が整っていることを保証します。設定パラメータCONFIG_RAPIDIO_DISC_TIMEOUTは、発見エンドポイントが列挙完了を待つ時間（秒単位）を定義します。

自動列挙/発見起動が選択された場合、基本的なメソッドの初期化ルーチンはrio_init_mports()を呼び出して、すべての既知のmportデバイスに対して列挙または発見を実行します。

RapidIOネットワークの規模や設定によっては、すべてのエンドポイントの同期した起動が必要であるため、この自動列挙/発見起動方法は使用が困難になる場合があります。

4.3 ユーザースペースでの列挙と発見の開始¶

ユーザースペースでの列挙と発見の開始は、組み込み型およびモジュール型の構成で使用できます。ユーザースペース制御による開始を行う場合、RapidIOサブシステムはsysfsの書き込み専用属性ファイル '/sys/bus/rapidio/scan' を作成します。特定のmportデバイスでの列挙または発見プロセスを開始するには、ユーザーがこのファイルにmport_ID（RapidIO宛先IDではなく）を書き込む必要があります。mport_IDはmportデバイス登録時に順番に割り当てられる番号（0 … RIO_MAX_MPORTS）です。たとえば、単一のRapidIOコントローラーを持つマシンでは、そのコントローラーのmport_IDは常に0になります。

すべての利用可能なmportでのRapidIO列挙/発見を開始するには、scan属性ファイルに'-1'（またはRIO_MPORT_ANY）を書き込むことができます。

4.4 基本的な列挙方法¶

これはRapidIOサブシステムコードの最初のリリースから利用可能なオリジナルの列挙/発見方法です。列挙プロセスは、RapidIOインターコネクト仕様: 付録I [1] に記載されている列挙アルゴリズムに従って実装されています。

この方法は静的リンク型またはロード可能なモジュールとして構成可能です。このメソッドの単一パラメータ「scan」は、モジュール初期化ルーチンから列挙/発見プロセスをトリガーできます。

この列挙/発見方法は一度しか開始できず、モジュールとして構築された場合、アンロードはサポートされていません。

エnumerationプロセスは、再帰的な深さ優先アルゴリズムを使用してネットワークをトラバースします。新しいデバイスが検出された場合、エnumeratorはHost Device ID Lock CSRに書き込みを行うことでそのデバイスを所有権を取得します。これにより、エnumeratorがデバイスのエnumerationに排他的な権限を持つことを保証します。デバイスの所有権が成功裏に取得された場合、エnumeratorは新しいrio_dev構造体を割り当て、デバイスの能力に応じて初期化します。

デバイスがエンドポイントである場合、一意のデバイスIDが割り当てられ、その値がデバイスのBase Device ID CSRに書き込まれます。

デバイスがスイッチである場合、エnumeratorはスイッチ固有の情報を保存するための追加のrio_switch構造体を割り当てます。次に、スイッチのベンダーデバイスIDが既知のRapidIOスイッチ一覧テーブルと照合されます。各スイッチテーブルエントリには、スイッチ固有の初期化ルーチンへのポインタが含まれており、これにより残りのスイッチ固有操作へのポインタを初期化し、必要に応じてハードウェアの初期化を行います。RapidIOスイッチは一意のデバイスIDを持たず、構成レジスタへのアクセスが必要な場合、接続されたエンドポイントのhopcountとルーティングをもってデバイスIDとして使用します。スイッチ（またはスイッチのチェーン）に接続されているエンドポイント（エnumeratorを除く）がなければ、ルート設定のために仮のデバイスIDが割り当てられます。スイッチのチェーンにエンドポイントが存在しない場合、1つの仮デバイスIDがチェーン全体を通じてルートを設定し、スイッチはhopcount値によって区別されます。

エンドポイントおよびスイッチの両方に対して、エnumeratorはデバイスのComponent Tag CSRに一意のコンポーネントタグを書き込みます。この一意な値は、エラー管理通知メカニズムがエラー管理イベントを報告しているデバイスを識別するために使用されます。

スイッチを経由したエnumerationは、スイッチの各アクティブなエグジットポートを反復処理することで完了します。各アクティブなリンクに対して、ルーティングテーブルにデフォルトデバイスID（8ビットシステムでは0xFF、16ビットシステムでは0xFFFF）へのルートが一時的に書き込まれます。アルゴリズムは、hopcount + 1とデフォルトデバイスIDを引数として自身を再帰的に呼び出して、アクティブなポート上のデバイスにアクセスします。

ホストがネットワーク全体のエnumerationを完了した後、デバイスの所有権を解放するためにデバイスIDロックをクリアします（呼び出し rio_clear_locks()）。システム内の各エンドポイントに対して、Port General Control CSRのDiscoveredビットを設定し、エnumerationが完了したことを示し、エージェントがネットワークのパッシブな発見を実行できるようにします。

発見プロセスはエージェントによって実行され、上記で説明した列挙プロセスと類似しています。ただし、発見プロセスは既存のルーティングを変更することなく実行されます。エージェントはRapidIOネットワーク構造に関する情報を収集し、内部で発見されたデバイスのマップを構築するためです。このように、RapidIOサブシステムのLinuxベースの各コンポーネントがネットワーク全体を完全に把握できます。発見プロセスは複数のエージェントが同時に実行可能です。各エージェントはRapidIOマスターポートを初期化した後、ホストによる列挙完了を待機します。設定された待機時間内に列挙が完了しなかった場合、エージェントはRapidIOの発見をスキップし、残りのカーネル初期化に進みます。

4.5 新しい列挙/発見方法の追加¶

RapidIOサブシステムのコード構成は、コアRapidIOコードへの大きな影響をかけずに新しい列挙/発見方法の追加を可能にします。

新しい列挙/発見方法は、列挙/発見プロセスを開始する前に、1つ以上のmportデバイスにアタッチする必要があります。通常、メソッドのモジュール初期化ルーチンは、 rio_register_scan() 指定されたmportデバイス（または複数のデバイス）にエナメータをアタッチするための呼び出しを行います。基本的なエナメータ実装はこのプロセスを示します。

4.6 ロード可能なRapidIOスイッチドライバーの使用¶

RapidIOスイッチドライバーがロード可能なモジュールとして構築されている場合、ユーザーは列挙/発見が始まる前にそれらをロードする必要があります。このプロセスは、RapidIO固有のmodprobe設定ファイルで事前または事後の依存関係を指定することで自動化できます。以下の例のように示されています。

ファイル /etc/modprobe.d/rapidio.conf:

# Configure RapidIO subsystem modules

# Set enumerator host destination ID (overrides kernel command line option)
options rapidio hdid=-1,2

# Load RapidIO switch drivers immediately after rapidio core module was loaded
softdep rapidio post: idt_gen2 idtcps tsi57x

# OR :

# Load RapidIO switch drivers just before rio-scan enumerator module is loaded
softdep rio-scan pre: idt_gen2 idtcps tsi57x

--------------------------
ノート:

上記の例では、一つの「softdep」コマンドを削除またはコメントアウトする必要があります。必要なモジュールロード順序を維持するためです。

VFIO - 「仮想ファンクション I/O」 1¶

多くの現代のシステムは、I/Oデバイスが割り当てられた境界内で動作することを保証するため、DMAおよび割込みリマッピング機能を提供しています。これはAMD-ViとIntel VT-dを搭載したx86ハードウェア、Partitionable Endpoints（PEs）を持つPOWERシステム、およびFreescale PAMUを含む埋め込まれたPowerPCシステムなどに該当します。VFIOドライバーは、セキュアなIOMMU保護環境においてユーザー空間に直接デバイスアクセスを提供する、IOMMU/デバイスに依存しないフレームワークです。言い換えれば、これは安全 2な非特権ユーザー空間ドライバーを可能にします。

なぜこのようなことが望まれるのでしょうか？仮想マシンは、最高のI/Oパフォーマンスを実現するため、デバイス割当（「デバイス割当」）を活用します。デバイスおよびホストの観点からすれば、これは仮想マシンをユーザー空間ドライバーに変換し、大幅なレイテンシー削減、高い帯域幅、および裸メタリックデバイスドライバーの直接利用といった利点をもたらします 3.

一部のアプリケーション、特に高性能コンピューティング分野では、ユーザー空間からの低オーバーヘッドで直接デバイスへのアクセスが恩恵を受けています。ネットワークアダプター（TCP/IPベースでない場合も含む）やコンピュートアクセラレータなどが該当します。VFIO導入以前には、これらのドライバーは、正しいアップストリームドライバーになるためにフルな開発サイクルを経る必要があったり、ツリー外でメンテナンスする必要があったり、UIOフレームワークを使用する必要があり、これはIOMMU保護の概念を持たず、制限された割込みサポートがあり、PCI構成空間などのアクセスにはroot特権が必要でした。

VFIOドライバーフレームワークはこれらを統合し、KVM PCI固有のデバイス割当コードを置き換え、UIOよりもセキュアで機能性の高いユーザー空間ドライバー環境を提供することを目的としています。

グループ、デバイス、およびIOMMUs¶

デバイスはどのI/Oドライバーの主な対象です。デバイスは、I/Oアクセス、割込み、DMAからなるプログラミングインターフェースを通常作成します。それぞれの詳細には立ち入らないとしても、DMAはセキュアな環境を維持する上で最も重要な要素です。なぜなら、デバイスがシステムメモリへの読み書きアクセスを許可することで、全体的なシステムの信頼性に最も大きなリスクを及ぼすからです。

このリスクを軽減するため、多くの現代のIOMMUは、以前はアドレス解決の問題を解決するためのインターフェースであったものが、今では隔離特性を組み込むようになりました。これにより、デバイス同士や任意のメモリアクセスから隔離されるようになり、仮想マシンへのセキュアな直接デバイス割当が可能になります。

この隔離は常に単一のデバイスレベルの粒度で行われるとは限りません。IOMMUがこの機能を備えている場合でも、デバイスの特性やインターコネクト、IOMMUのトポロジーなどの要素がこの隔離を低下させることがあります。たとえば、個々のデバイスがより大きなマルチファンクションエンクロージャーの一部である場合があります。IOMMUがエンクロージャー内のデバイスを区別できる場合でも、エンクロージャーはデバイス間のトランザクションがIOMMUに到達する必要がない場合があります。このような例としては、ファンクション間のバックドアを持つマルチファンクションPCIデバイスから、PCI-ACS（アクセス制御サービス）をサポートしていないブリッジがIOMMUを経由せずにリダイレクトを許可するものまで幅広いです。また、デバイスの隠蔽においてもトポロジーが影響を与えることがあります。PCIe-to-PCIブリッジはブリッジの後ろにあるデバイスをマスクし、トランザクションがブリッジ自体から発生しているように見えます。明らかにIOMMUの設計はこの分野において重要な要素です。

したがって、IOMMUは基本的にデバイスレベルの粒度で機能しますが、どのシステムも粒度が低下する可能性があります。このため、IOMMU APIはIOMMUグループという概念をサポートしています。グループとは、システム内の他のすべてのデバイスから隔離可能なデバイスの集合です。グループはしたがってVFIOが使用する所有権の単位です。

グループはセキュアなユーザーへのアクセスを確保するために使用する最小の粒度です。ただし、必ずしも最適な粒度ではありません。ページテーブルを使用するIOMMUでは、複数のグループで同じページテーブルを共有できる可能性があり、これによりプラットフォーム（TLBスラッシングの減少、複数のページテーブルの削減）およびユーザー（単一の翻訳セットのプログラミングのみ）へのオーバーヘッドを削減できます。このため、VFIOはコンテナクラスを活用しており、1つまたは複数のグループを保持できます。コンテナは単に/dev/vfio/vfioというキャラクタデバイスを開くことで作成されます。

単独ではコンテナは機能が限定されており、ほぼすべてのバージョンや拡張機能のクエリインターフェースはロックされています。ユーザーは次のレベルの機能を有効にするためにコンテナにグループを追加する必要があります。これを実行するには、まず対象のデバイスに関連するグループを特定する必要があります。これは下記の例に記載されているsysfsリンクを使用して行うことができます。デバイスをホストドライバーからアンバインドし、VFIOドライバーにバインドすることで、グループは/dev/vfio/$GROUP（$GROUPはデバイスが所属するIOMMUグループ番号）として新たにVFIOグループが出現します。IOMMUグループに複数のデバイスが含まれる場合、それぞれをVFIOドライバーにバインドする必要があります（VFIOドライバーが利用できない場合でも、ホストドライバーからデバイスをアンバインドするだけでグループは利用可能になりますが、特定のデバイスは利用できません）。TBD - ドライバーのプローブを無効化するインターフェース／デバイスのロック機能。

グループが準備完了したら、VFIOグループキャラクターデバイス（/dev/vfio/$GROUP）を開き、VFIO_GROUP_SET_CONTAINER ioctlを使用して以前に開いたコンテナファイルのファイル記述子を渡すことでコンテナに追加できます。必要があれば、IOMMUドライバーがグループ間でIOMMUコンテキストを共有可能である場合、複数のグループを同じコンテナに設定できます。グループが既存のグループを持つコンテナに設定できない場合、代わりに新しい空のコンテナを使用する必要があります。

グループ（または複数のグループ）がコンテナに接続されると、残りのioctlが利用可能になり、VFIO IOMMUインターフェースへのアクセスが可能になります。さらに、VFIOグループファイル記述子上でioctlを実行することで、グループ内の各デバイスのファイル記述子を取得できるようになります。

VFIOデバイスAPIには、デバイスの説明、デバイス記述子上のI/O領域およびその読み込み／書き込み／mmapオフセット、また中断通知の説明と登録メカニズムに関するioctlが含まれます。

VFIOの使用例¶

ユーザーがアクセスしたいPCIデバイスは0000:06:0d.0です：

$ readlink /sys/bus/pci/devices/0000:06:0d.0/iommu_group
../../../../kernel/iommu_groups/26

このデバイスはIOMMUグループ26に属しています。このデバイスはPCIバス上にあるため、ユーザーはvfio-pciを使用してグループを管理します：

# modprobe vfio-pci

このデバイスをvfio-pciドライバーにバインドすると、このグループ用のVFIOグループキャラクターデバイスが作成されます：

$ lspci -n -s 0000:06:0d.0
06:0d.0 0401: 1102:0002 (rev 08)
# echo 0000:06:0d.0 > /sys/bus/pci/devices/0000:06:0d.0/driver/unbind
# echo 1102 0002 > /sys/bus/pci/drivers/vfio-pci/new_id

次に、VFIO使用のためにグループ内の他のデバイスを確認する必要があります：

$ ls -l /sys/bus/pci/devices/0000:06:0d.0/iommu_group/devices
total 0
lrwxrwxrwx. 1 root root 0 Apr 23 16:13 0000:00:1e.0 ->
        ../../../../devices/pci0000:00/0000:00:1e.0
lrwxrwxrwx. 1 root root 0 Apr 23 16:13 0000:06:0d.0 ->
        ../../../../devices/pci0000:00/0000:00:1e.0/0000:06:0d.0
lrwxrwxrwx. 1 root root 0 Apr 23 16:13 0000:06:0d.1 ->
        ../../../../devices/pci0000:00/0000:00:1e.0/0000:06:0d.1

このデバイスはPCIe-to-PCIブリッジの後ろにあります 4したがって、同様の手順に従って、デバイス 0000:06:0d.1 もグループに追加する必要があります。デバイス 0000:00:1e.0 は、現在ホストドライバーを持っていないブリッジです。そのため、このデバイスを vfio-pci ドライバにバインドする必要はありません（vfio-pci は現在、PCI ブリッジをサポートしていません）。

非特権操作を希望する場合は、ユーザーにグループへのアクセス権を提供する必要があります（注意：/dev/vfio/vfio は単独では機能を持たず、システムがモード 0666 に設定されていることが期待されます）：

# chown user:user /dev/vfio/26

ユーザーは、このグループのすべてのデバイスおよび IOMMU に完全なアクセス権を持ち、以下のようにアクセスできます：

int container, group, device, i;
struct vfio_group_status group_status =
                                { .argsz = sizeof(group_status) };
struct vfio_iommu_type1_info iommu_info = { .argsz = sizeof(iommu_info) };
struct vfio_iommu_type1_dma_map dma_map = { .argsz = sizeof(dma_map) };
struct vfio_device_info device_info = { .argsz = sizeof(device_info) };

/* Create a new container */
container = open("/dev/vfio/vfio", O_RDWR);

if (ioctl(container, VFIO_GET_API_VERSION) != VFIO_API_VERSION)
        /* Unknown API version */

if (!ioctl(container, VFIO_CHECK_EXTENSION, VFIO_TYPE1_IOMMU))
        /* Doesn't support the IOMMU driver we want. */

/* Open the group */
group = open("/dev/vfio/26", O_RDWR);

/* Test the group is viable and available */
ioctl(group, VFIO_GROUP_GET_STATUS, &group_status);

if (!(group_status.flags & VFIO_GROUP_FLAGS_VIABLE))
        /* Group is not viable (ie, not all devices bound for vfio) */

/* Add the group to the container */
ioctl(group, VFIO_GROUP_SET_CONTAINER, &container);

/* Enable the IOMMU model we want */
ioctl(container, VFIO_SET_IOMMU, VFIO_TYPE1_IOMMU);

/* Get addition IOMMU info */
ioctl(container, VFIO_IOMMU_GET_INFO, &iommu_info);

/* Allocate some space and setup a DMA mapping */
dma_map.vaddr = mmap(0, 1024 * 1024, PROT_READ | PROT_WRITE,
                     MAP_PRIVATE | MAP_ANONYMOUS, 0, 0);
dma_map.size = 1024 * 1024;
dma_map.iova = 0; /* 1MB starting at 0x0 from device view */
dma_map.flags = VFIO_DMA_MAP_FLAG_READ | VFIO_DMA_MAP_FLAG_WRITE;

ioctl(container, VFIO_IOMMU_MAP_DMA, &dma_map);

/* Get a file descriptor for the device */
device = ioctl(group, VFIO_GROUP_GET_DEVICE_FD, "0000:06:0d.0");

/* Test and setup the device */
ioctl(device, VFIO_DEVICE_GET_INFO, &device_info);

for (i = 0; i < device_info.num_regions; i++) {
        struct vfio_region_info reg = { .argsz = sizeof(reg) };

        reg.index = i;

        ioctl(device, VFIO_DEVICE_GET_REGION_INFO, &reg);

        /* Setup mappings... read/write offsets, mmaps
         * For PCI devices, config space is a region */
}

for (i = 0; i < device_info.num_irqs; i++) {
        struct vfio_irq_info irq = { .argsz = sizeof(irq) };

        irq.index = i;

        ioctl(device, VFIO_DEVICE_GET_IRQ_INFO, &irq);

        /* Setup IRQs... eventfds, VFIO_DEVICE_SET_IRQS */
}

/* Gratuitous device reset and go... */
ioctl(device, VFIO_DEVICE_RESET);

VFIOバスドライバAPI¶

VFIO バスドライバ（例: vfio-pci）は、VFIO コアにのみ少数のインターフェースを使用します。デバイスがドライバにバインドされたり解除されたりする際、ドライバは vfio_add_group_dev() と vfio_del_group_dev() をそれぞれ呼び出します：

extern int vfio_add_group_dev(struct device *dev,
                              const struct vfio_device_ops *ops,
                              void *device_data);

extern void *vfio_del_group_dev(struct device *dev);

vfio_add_group_dev() は、指定された dev の iommu_group を追跡を開始し、VFIO バスドライバが所有していると登録するようにコアに指示します。ドライバは、ファイル操作構造体に似たコールバック用の ops 構造体を提供します：

struct vfio_device_ops {
        int     (*open)(void *device_data);
        void    (*release)(void *device_data);
        ssize_t (*read)(void *device_data, char __user *buf,
                        size_t count, loff_t *ppos);
        ssize_t (*write)(void *device_data, const char __user *buf,
                         size_t size, loff_t *ppos);
        long    (*ioctl)(void *device_data, unsigned int cmd,
                         unsigned long arg);
        int     (*mmap)(void *device_data, struct vm_area_struct *vma);
};

各関数には、上記 vfio_add_group_dev() 呼び出しで登録された device_data が渡されます。これにより、バスドライバがオパケなプライベートデータを簡単に保存できる場所が提供されます。open/release コールバックは、VFIO_GROUP_GET_DEVICE_FD を通じてデバイス用に新しいファイルディスクリプタが作成されるときに発生します。ioctl インターフェースは VFIO_DEVICE_* ioctl を直接透過的に処理します。read/write/mmap インターフェースは、デバイスごとの VFIO_DEVICE_GET_REGION_INFO ioctl で定義されたデバイス領域へのアクセスを実装します。

PPC64 sPAPR実装ノート¶

この実装にはいくつかの特異点があります：

  1. 古いシステム（POWER7 と P5IOC2/IODA1 を搭載）では、コンテナごとに1つの IOMMU グループのみがサポートされます。IOMMU テーブルは起動時に割り当てられ、各 IOMMU グループ（PE と呼ばれる）ごとに1つのテーブルが存在します（PE は通常 PCI ドメインですが、必ずしもそうではありません）。

    新しいシステム（POWER8 と IODA2 を搭載）では、ハードウェア設計が改善されており、複数の IOMMU グループを VFIO コンテナごとに持つことが可能になりました。

  2. ハードウェアは、いわゆる DMA ウィンドウをサポートしています。これは、DMA 送信が許可される PCI アドレス範囲であり、ウィンドウ外のアドレス空間へのアクセス試行は、全体の PE の隔離を引き起こします。

  3. PPC64ゲストはパラバーティザライズされていますが、完全なエミュレーションではありません。DMA用のページのマッピング/アンマッピングを行うAPIがあり、通常は1〜32ページを1回の呼び出しでマッピングします。現在、呼び出し回数を減らす方法はありません。処理を高速化するために、リアルモードでマッピング/アンマッピングの処理が実装されており、性能が非常に高いですが、リアルタイムでのロックページのアカウント処理ができないなどの制限があります。

  4. sPAPR仕様によると、パーティション可能エンドポイント（PE）は、パーティションおよびエラー回復の目的で扱う単位となるI/Oサブツリーです。PEは単一またはマルチファンクションIOA（IOアダプター）、マルチファンクションIOAのファンクション、複数のIOA（スイッチやブリッジ構造を含む可能性がある）を含むことができます。PPC64ゲストはEEH RTASサービスを用いてPCIエラーを検出・回復します。

    そのため、4つの追加のioctlが追加されました：

    VFIO_IOMMU_SPAPR_TCE_GET_INFO

    PCIバス上のDMAウィンドウのサイズと開始位置を返します。

    VFIO_IOMMU_ENABLE

    コンテナを有効化します。この時点でロックページのアカウント処理が行われます。これにより、ユーザーはDMAウィンドウを確認し、rlimitを調整した後で実際の作業を行えるようになります。

    VFIO_IOMMU_DISABLE

    コンテナを無効化します。

    VFIO_EEH_PE_OP

    EEHの設定、エラー検出、回復のためのAPIを提供します。

    上記の例からのコードフローはやや変更されます：

    struct vfio_eeh_pe_op pe_op = { .argsz = sizeof(pe_op), .flags = 0 };

.....
/* Add the group to the container */
ioctl(group, VFIO_GROUP_SET_CONTAINER, &container);

/* Enable the IOMMU model we want */
ioctl(container, VFIO_SET_IOMMU, VFIO_SPAPR_TCE_IOMMU)

/* Get addition sPAPR IOMMU info */
vfio_iommu_spapr_tce_info spapr_iommu_info;
ioctl(container, VFIO_IOMMU_SPAPR_TCE_GET_INFO, &spapr_iommu_info);

if (ioctl(container, VFIO_IOMMU_ENABLE))
        /* Cannot enable container, may be low rlimit */

/* Allocate some space and setup a DMA mapping */
dma_map.vaddr = mmap(0, 1024 * 1024, PROT_READ | PROT_WRITE,
                     MAP_PRIVATE | MAP_ANONYMOUS, 0, 0);

dma_map.size = 1024 * 1024;
dma_map.iova = 0; /* 1MB starting at 0x0 from device view */
dma_map.flags = VFIO_DMA_MAP_FLAG_READ | VFIO_DMA_MAP_FLAG_WRITE;

/* Check here is .iova/.size are within DMA window from spapr_iommu_info */
ioctl(container, VFIO_IOMMU_MAP_DMA, &dma_map);

/* Get a file descriptor for the device */
device = ioctl(group, VFIO_GROUP_GET_DEVICE_FD, "0000:06:0d.0");

....

/* Gratuitous device reset and go... */
ioctl(device, VFIO_DEVICE_RESET);

/* Make sure EEH is supported */
ioctl(container, VFIO_CHECK_EXTENSION, VFIO_EEH);

/* Enable the EEH functionality on the device */
pe_op.op = VFIO_EEH_PE_ENABLE;
ioctl(container, VFIO_EEH_PE_OP, &pe_op);

/* You're suggested to create additional data struct to represent
 * PE, and put child devices belonging to same IOMMU group to the

pe_op.op = VFIO_EEH_PE_GET_STATE;
ioctl(container, VFIO_EEH_PE_OP, &pe_op);

/* Save device state using pci_save_state().
 * EEH should be enabled on the specified device.

....

/* Inject EEH error, which is expected to be caused by 32-bits
 * config load.

pe_op.op = VFIO_EEH_PE_INJECT_ERR;
pe_op.err.type = EEH_ERR_TYPE_32;
pe_op.err.func = EEH_ERR_FUNC_LD_CFG_ADDR;
pe_op.err.addr = 0ul;
pe_op.err.mask = 0ul;
ioctl(container, VFIO_EEH_PE_OP, &pe_op);

....

/* When 0xFF's returned from reading PCI config space or IO BARs
 * of the PCI device. Check the PE's state to see if that has been
 * frozen.
 */
ioctl(container, VFIO_EEH_PE_OP, &pe_op);

/* Waiting for pending PCI transactions to be completed and don't
 * produce any more PCI traffic from/to the affected PE until
 * recovery is finished.

/* Enable IO for the affected PE and collect logs. Usually, the
 * standard part of PCI config space, AER registers are dumped
 * as logs for further analysis.

pe_op.op = VFIO_EEH_PE_UNFREEZE_IO;
ioctl(container, VFIO_EEH_PE_OP, &pe_op);

/*
 * Issue PE reset: hot or fundamental reset. Usually, hot reset
 * is enough. However, the firmware of some PCI adapters would
 * require fundamental reset.

ioctl(container, VFIO_EEH_PE_OP, &pe_op);
pe_op.op = VFIO_EEH_PE_RESET_DEACTIVATE;
ioctl(container, VFIO_EEH_PE_OP, &pe_op);

/* Configure the PCI bridges for the affected PE */
pe_op.op = VFIO_EEH_PE_CONFIGURE;
ioctl(container, VFIO_EEH_PE_OP, &pe_op);

/* Restored state we saved at initialization time. pci_restore_state()
 * is good enough as an example.
 */

/* Hopefully, error is recovered successfully. Now, you can resume to
 * start PCI traffic to/from the affected PE.
 */

....

  5. SPAPR TCE IOMMUのv2があります。これはVFIO_IOMMU_ENABLE/VFIO_IOMMU_DISABLEを非推奨にし、2つの新しいioctl（VFIO_IOMMU_SPAPR_REGISTER_MEMORYおよびVFIO_IOMMU_SPAPR_UNREGISTER_MEMORY）を実装します（これらはv1 IOMMUでは非対応です）。

    PPC64パラバーティザライズゲストは多くのマッピング/アンマッピングリクエストを生成し、その処理にはページのピンニング/アンピンニングとmm::locked_vmカウンターの更新が含まれます。v2 IOMMUはアカウント処理とピンニングを別個の操作に分離しています：

    • VFIO_IOMMU_SPAPR_REGISTER_MEMORY/VFIO_IOMMU_SPAPR_UNREGISTER_MEMORY ioctlはユーザー空間のアドレスとピンするブロックのサイズを受け取ります。バイセクティングはサポートされておらず、VFIO_IOMMU_UNREGISTER_MEMORYは登録したメモリブロックに使用した正確なアドレスとサイズで呼び出される必要があります。ユーザー空間ではこれらのioctlを頻繁に呼び出すことは期待されていません。範囲はVFIOコンテナ内のリンクリストに保存されます。

    • VFIO_IOMMU_MAP_DMA/VFIO_IOMMU_UNMAP_DMA ioctlは実際のIOMMUテーブルを更新するだけで、ピンニングは行いません。代わりに、ユーザー空間のアドレスが事前に登録された範囲から取得されているかを確認します。

    この分離により、ゲスト向けのDMAの最適化が可能になります。

  6. sPAPR仕様では、ゲストがPCIバス上で変更可能なページサイズを持つ追加DMAウィンドウを取得できるようになります。この機能をサポートするため、VFIO_IOMMU_SPAPR_TCE_CREATEおよびVFIO_IOMMU_SPAPR_TCE_REMOVEという2つのioctlが追加されました。プラットフォームがこの機能をサポートしない場合、ユーザースペースにエラーが返されます。既存のハードウェアは最大2つのDMAウィンドウをサポートしており、1つは2GBの長さで4Kページを使用する「デフォルト32bitウィンドウ」、もう1つは全体のRAMサイズまで拡張可能で、異なるページサイズを使用します。この後者はオプションであり、ゲストドライバが64bit DMAをサポートする場合、実行時にゲストが作成します。

    VFIO_IOMMU_SPAPR_TCE_CREATEは、ページシフト、DMAウィンドウサイズ、およびTCEテーブルレベル数（TCEテーブルが十分に大きく、カーネルが物理的に連続したメモリを確保できない場合）を受け取り、利用可能なスロットに新しいウィンドウを作成し、新しいウィンドウの開始バスアドレスを返します。ハードウェアの制限により、ユーザースペースはDMAウィンドウの位置を指定できません。

    VFIO_IOMMU_SPAPR_TCE_REMOVEは、DMAウィンドウのバス開始アドレスを受け取り、それを削除します。

1

VFIOは当初、トム・ライオン氏がシスコで実装した際には「Virtual Function I/O（仮想ファンクションI/O）」というイニシャルでしたが、その後はイニシャルを越えて使い続けています。

2

「安全（safe）」の概念もまた、デバイスが「適切な動作（well behaved）」をしているかどうかに依存します。複数ファンクションを持つデバイスがファンクション間でバックドアを持つ可能性があり、単一ファンクションのデバイスでもMMIOレジスタを通じてPCIコンフィグスペースへの代替アクセスを持つ可能性があります。前者については、IOMMUドライバに追加の注意点を加えることで、複数ファンクションPCIデバイスをグループ化（iommu=group_mf）して対策できます。後者は防げませんが、IOMMUは依然として隔離を提供すべきです。PCIではSR-IOV仮想ファンクションが「適切な動作」の最も信頼できる指標です。

3

常に、仮想マシンデバイス割当にはVFIOの範囲を超えたトレードオフがあります。今後、IOMMU技術が進化することでこれらのトレードオフは一部は解消されるかもしれませんが、すべてを解消するには至りません。

4

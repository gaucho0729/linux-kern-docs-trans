はじめに¶

このフレームワークは、電圧および電流レギュレータを制御するための標準的なカーネルインターフェースを提供することを目的としています。

システムがレギュレータの電力出力を動的に制御できるようにすることで、省電力化とバッテリー寿命の延長を目的としています。これは電圧レギュレータ（電圧出力が制御可能）および電流吸収器（電流制限が制御可能）の両方に適用されます。

追加の（現在はより完全な）ドキュメンテーションは、Linuxカーネルソースコード内の Documentation/power/regulator.

用語集¶

レギュレータAPIは、以下の用語を含むため、これらが不慣れな場合があります:

レギュレータ

他のデバイスに電源を供給する電子デバイス。ほとんどのレギュレータは出力の有効/無効を制御でき、一部は出力電圧または電流を制御できます。

コンシューマ

レギュレータによって供給される電力を消費する電子デバイス。これらは静的（固定電源のみが必要）または動的（実行時におけるレギュレータのアクティブな管理が必要）のいずれかです。

電源ドメイン

特定のレギュレータによって供給される電子回路（レギュレータおよびすべてのコンシューマデバイスを含む）。この回路内のすべてのコンポーネントは、レギュレータの設定を共有します。

電源管理統合回路 (PMIC)

多数のレギュレータを含むICで、しばしば他のサブシステムも含みます。埋め込みシステムでは、主なPMICはデスクトップシステムのPSUと南橋の組み合わせに相当します。

消費者ドライバインターフェース¶

これはカーネルクロックフレームワークと同様のAPIを提供します。コンシューマドライバーは 取得 および put 操作を使用してレギュレータを取得および解放します。レギュレータの設定およびランタイムパラメータの取得・設定に必要な関数が提供されます。 enable および 無効化 When requesting regulators consumers use symbolic names for their supplies, such as “Vcc”, which are mapped into actual regulator devices by the machine interface.

機械インターフェースによって、供給電源のシンボリック名（例: 「Vcc」など）が実際のレギュレータデバイスにマッピングされます。

レギュレータフレームワークが使用されていない場合でも、このAPIのスタブバージョンが提供されるため、ifdefの使用を最小限に抑えます。

有効化および無効化¶

レギュレータAPIは、レギュレータの参照カウントによる有効化および無効化を提供します。コンシューマデバイスは regulator_enable() および regulator_disable() 関数を使用してレギュレータを有効化および無効化します。この2つの関数の呼び出しはバランスを取る必要があります。

複数のコンシューマが同じレギュレータを使用している場合や、機械制約によりレギュレータを無効化できない場合があるため、呼び出しによってレギュレータの供給電源が必ず無効化されるとは限りません。 regulator_disable() コンシューマドライバーは、レギュレータが常に有効である可能性があると想定する必要があります。

設定¶

一部の消費者デバイスは、供給電源を動的に設定する必要がある場合があります。たとえば、MMCドライバーは、カードに適切な動作電圧を選択する必要があります。これは、レギュレータが有効になっているか無効になっているかに関係なく実行できます。

以下の regulator_set_voltage() および regulator_set_current_limit() これらの関数は、このインターフェースの主な手段です。どちらも電圧および電流の範囲をサポートし、特定の値を必要としないドライバー（例：CPUの周波数スケーリングは、CPUが低い周波数で幅広い供給電圧を使用できるようにするが、供給電圧を下げることを必要としない）をサポートします。正確な値が必要な場合は、最小値と最大値が一致する必要があります。

コールバック¶

レギュレータの故障などのイベントにもコールバックを登録できます。

レギュレータドライバインターフェース¶

レギュレータチップのドライバーは、レギュレータをレギュレータコアに登録し、コアに操作構造体を提供します。通知インターフェースは、エラー条件をコアに報告するためのものです。

登録は、プラットフォームによる明示的な設定によってトリガーされ、 struct regulator_init_data レギュレータの制約および供給情報が含まれる

マシンインターフェース¶

このインターフェースは、特定のシステムにおけるレギュレータが消費者にどのように接続されているかを定義し、システムの有効な動作パラメータを示します。

供給電源¶

レギュレータ供給電源は、struct regulator_consumer_supplyで指定されます。これはドライバー登録時にマシン制約の一部として行われます。

制約¶

接続の定義に加えて、マシンインターフェースはクライアントが実行できる操作と設定可能なパラメータを定義する制約も提供します。これは、一般的にレギュレータデバイスがシステムで安全に使用できるよりも多くの柔軟性を提供するためです（例：消費者が定格しているよりも高い供給電圧をサポートする場合）。

これは、ドライバー登録時に struct regulation_constraints.

制約に初期のレギュレータの設定を指定することもできます。これは静的消費者との使用に特に役立ちます。

int regulator_set_load(struct リゲュレータ *リゲュレータ, int uA_load)¶

レギュレータの負荷を設定します

パラメータ

struct regulator *regulator

リゲュレータソース

int uA_load

負荷電流

説明

新しいデバイスの負荷をレギュレータコアに通知します。DRMS（制約によって有効化されている場合）は、新しいレギュレータの負荷に最も効率的な運用モードを設定するためにこれを使用します。

消費者デバイスは、運用状態が変化し、結果として電力状態も変化する際に、そのデバイスが要求する最大電力を供給レギュレータに通知します（これはデバイスのデータシートの電力消費表から取得できます）。運用状態の変化で電力消費に影響を与える例は次のとおりです：-

・デバイスが開かれた/閉じられた。・デバイスのI/Oが開始されるか、完了した。・デバイスが作業の間隔でアイドル状態にある。

この情報はsysfsを介してユーザースペースにエクスポートされます。

DRMSは、プラットフォームの制約が許可する場合、レギュレータの合計リクエスト負荷を合計し、最も効率的な運用モードに切り替えます。

レギュレータが常にオンのレギュレータである場合、その消費者が完全に無効化された場合でも、個々の消費者の負荷は依然として削除されます。

エラーの場合、負のエラー番号が返されます。

注意

レギュレータ消費者がレギュレータの無効化を要求した場合、その消費者が要求した負荷は合計リクエスト負荷にカウントされなくなります。レギュレータが再有効化されると、以前に要求された負荷が再びカウントされます。

ioctlベースのインターフェース¶

ioctl()はアプリケーションがデバイスドライバとインターフェースする最も一般的な方法です。柔軟性があり、新しいコマンドを追加することで簡単に拡張可能です。キャラクターデバイス、ブロックデバイス、ソケットやその他の特殊なファイルディスクリプタを通じて使用可能です。

ただし、ioctlコマンドの定義を誤ることが非常に簡単で、後から修正しようとすると既存のアプリケーションを破壊してしまうため、このドキュメントは開発者が正しい方法で実装できるよう支援しています。

コマンド番号定義¶

コマンド番号、またはリクエスト番号は、ioctlシステムコールに2番目に渡される引数です。これは特定のドライバで動作を識別するための任意の32ビットの数値ですが、いくつかの慣例があります。

include/uapi/asm-generic/ioctl.h 現代の慣例に従うioctlコマンドを定義するための4つのマクロを提供しています。 _IO, _IOR, _IOW, and _IOWRこれらはすべての新しいコマンドに使用し、正しいパラメータを指定してください：

_IO/_IOR/_IOW/_IOWR

マクロ名は引数がどのように使用されるかを指定します。これはカーネルにデータを渡すポインタ(_IOW)、カーネルからデータを取得するポインタ(_IOR)、または両方(_IOWR)を示します。_IOは引数がなく、またはポインタではなく整数値を渡すコマンドを示すことができます。_IOは引数がなくても使用すべきですが、データを渡す場合はポインタを使用することをお勧めします。

type

8ビットの数値で、サブシステムやドライバに特有で、 Ioctl ナンバー

nr

「type」の特定の値に対応するコマンドを一意に識別する8ビットの数値

data_type

引数で指すデータ型の名前、コマンド番号はこのデータ型の sizeof(data_type) 値を13ビットまたは14ビットの整数にエンコードし、引数の最大サイズには8191バイトの制限があります。注意：_IOR/_IOW/IOWRにsizeof(data_type)を渡すと、sizeof(sizeof(data_type))つまりsizeof(size_t)をエンコードしてしまい、これは望ましくありません。_IOはdata_typeパラメータを持ちません。

インターフェースバージョン¶

一部のサブシステムでは、データ構造体にバージョン番号を含めることで、引数の解釈を変えてコマンドをオーバーロードしています。

これは一般的に悪い考えで、既存のコマンドの変更は既存のアプリケーションを破壊する傾向があります。

より良い方法は新しいioctlコマンドを追加することです。新しい番号で実装します。古いコマンドは互換性のためカーネルで引き続き実装する必要がありますが、これは新しい実装のラッパーとして扱うことができます。

戻りコード¶

ioctlコマンドは、errno(3)ドキュメントに記載されているように負のエラー コードを返すことができます。これらはユーザー空間でerrno値に変換されます。成功した場合、戻り値はゼロでなければなりません。正の「long」値を返すことは可能ですが、推奨されません。

ioctlコールバックが未知のコマンド番号で呼び出される場合、ハンドラは-ENOTTYまたは-ENOIOCTLCMDを返します。これによりシステムコールから-ENOTTYが返されます。一部のサブシステムでは歴史的要因により-ENOSYSまたは-EINVALを返すこともありますが、これは誤りです。

Linux 5.5以前では、互換モード用のioctlハンドラは-ENOIOCTLCMDを返す必要がありました。現在ではすべてのサブシステムが互換モードを自前で処理するため、これが必要ありません。ただし、古いバージョンのカーネルへのバグ修正のバックポーティングを考慮する際には重要かもしれません。

タイムスタンプ¶

タイムスタンプとタイムアウト値は伝統的に struct timespec または struct timevalとして渡されていましたが、64ビットtime_tへの移行後、ユーザー空間でのこれらの構造体の定義が互換性がないため問題があります。

以下の struct __kernel_timespec typeは、別個の秒/ナノ秒値を望む場合に他のデータ構造体に埋め込まれるか、またはユーザー空間に直接渡すために使用できます。ただし、この構造体はカーネルのtimespec64もしくはユーザー空間のtimespecと完全には一致せず、依然として理想的ではありません。get_timespec64()およびput_timespec32()のヘルパ関数を使用することで、ユーザー空間とのレイアウト互換性を維持し、パディングの処理を正しく行うことができます。

秒をナノ秒に変換するのはコストが低く、逆は64ビットの割り算が必要でコストが高いため、単純な__u64ナノ秒値がよりシンプルで効率的です。

タイムアウト値およびタイムスタンプは、 CLOCK_MONOTONIC時間、つまり ktime_get_ns() または ktime_get_ts64()で返される時間を使うのが理想的です。 CLOCK_REALTIMEとは異なり、これによりタイムスタンプがサーカディアン調整やclock_settime()呼び出しによる逆行や進みを防ぐことができます。

ktime_get_real_ns() CLOCK_REALTIMEタイムスタンプは、再起動や複数のマシン間で永続的な場合に使用できます。

32ビット互換モード¶

32ビットユーザー空間が64ビットマシン上で動作するようにサポートするため、各サブシステムまたはドライバがioctlコールバックハンドラを実装する場合、対応するcompat_ioctlハンドラも実装する必要があります。

データ構造のすべてのルールを遵守すれば、これはcompat_ptr_ioctl()やblkdev_compat_ptr_ioctl()などのヘルパ関数への.compat_ioctlポインタを設定するだけで完了します。

compat_ptr()¶

s390アーキテクチャでは、31ビットのユーザー空間においてデータポインタの表現が曖昧であり、上位ビットは無視されます。このようなプロセスを互換モードで実行する際には、compat_ptr()ヘルパ関数を使用して、compat_uptr_tの上位ビットをクリアし、有効な64ビットポインタに変換する必要があります。他のアーキテクチャでは、このマクロは単にキャストを行います。 void __user * ポインタを参照します。

compat_ioctl()コールバック関数において、最後の引数はunsigned long型であり、コマンドによってはポインタかスカラーとして解釈されます。スカラーの場合、compat_ptr()は使用しない必要があります。これにより、64ビットカーネルが32ビットカーネルと同様の挙動を示すようにします。

compat_ptr_ioctl()ヘルパ関数は、互換性のあるデータ構造へのポインタのみを引数として受け取るドライバにおいて、カスタムのcompat_ioctlファイル操作を置き換えることができます。

構造体レイアウト¶

互換性のあるデータ構造はすべてのアーキテクチャで同じレイアウトを維持しており、問題となるメンバは一切含まれていません。

  • long および unsigned long レジスタのサイズに一致するため、32ビットまたは64ビット幅を持つことができ、汎用的なデータ構造には使用できません。固定長の代替は __s32, __u32, __s64 および __u64.

  • ポインタにも同様の問題があり、compat_ptr()の使用が必須です。回避策として最も効果的なのは、 __u64 ポインタの代わりに使用することであり、これは uintptr_t ユーザー空間でのキャストが必要であり、カーネルではu64_to_user_ptr()関数を使用してユーザーポインタに戻す必要があります。

  • x86-32（i386）アーキテクチャでは、64ビット変数のアライメントは32ビットのみですが、x86-64を含む他のアーキテクチャでは自然にアライメントされます。これは、構造体のような:

    struct foo {
    __u32 a;
    __u64 b;
    __u32 c;
};

    x86-64ではaとbの間に4バイトのパディングがあり、末尾にも4バイトのパディングが追加されるのに対し、i386ではパディングがありません。このため、互換性のあるioctl変換ハンドラが必要です。

    この問題を回避するため、すべての構造体のメンバは自然にアライメントされるべきです。または、明示的なパディングの代わりに明示的な予約フィールドを追加する必要があります。この pahole ツールを使用してアライメントを確認できます。

  • ARM OABIユーザー空間では、構造体が32ビットの倍数にパディングされるため、32ビット境界にない場合、現代のEABIカーネルと互換性がありません。

  • m68kアーキテクチャでは、構造体メンバのアライメントが16ビットを超えることは保証されておらず、これは暗黙のパディングに依存する場合の問題です。

  • ビットフィールドとエナムは一般的に期待通り動作しますが、一部の特性は実装依存です。そのため、ioctlインターフェースでは完全に避けるのが望ましいです。

  • char メンバはアーキテクチャに応じて署名付きまたは署名なしのいずれかになります。そのため、8ビット整数値には__u8と__s8型を使用すべきですが、固定長の文字列にはchar配列の方が明確です。

情報漏洩¶

初期化されていないデータはユーザー空間にコピーしてはいけません。これは情報漏洩を引き起こす可能性があり、その結果、カーネルアドレス空間レイアウトランダム化（KASLR）を回避する攻撃に利用される可能性があります。

この理由（および互換性のサポートのため）データ構造に暗黙のパディングを避けるのが望ましいです。既存の構造体に暗黙のパディングがある場合、カーネルドライバはその構造体のインスタンスをユーザー空間にコピーする前に、完全に初期化する必要があります。これは通常、以下のように呼び出します memset() 個々のメンバに割り当てる前に。

サブシステム抽象化¶

一部のデバイスドライバは独自のioctl関数を実装していますが、ほとんどのサブシステムは複数のドライバで同じコマンドを実装しています。理想的にはサブシステムが.ioctl()ハンドラを持ち、ユーザー空間とデータ構造の引数をコピーし、サブシステム固有のコールバック関数に通常のカーネルポインタを通じて渡します。

これはさまざまな方法で役立ちます:

  • 同一サブシステム内の他のドライバでも動作する可能性が高いです。ユーザー空間ABIに微妙な違いがない場合、アプリケーションが1つのドライバで作成されても別のドライバで動作します。

  • ユーザー空間へのアクセスとデータ構造レイアウトの複雑さは1ヶ所で処理されるため、実装ミスの可能性が低くなります。

  • 複数のドライバでioctlが共有されている場合、インターフェースの問題を発見できる経験豊富な開発者がレビューする可能性が高くなります。単一のドライバでしか使用されない場合よりです。

ioctlの代替手段¶

ioctlが問題解決に最適なケースは多くあります。代替案には以下が挙げられます:

  • システム全体に影響を与える機能で、物理デバイスに依存せず、キャラクタデバイスノードのファイルシステムパーミッションに制約されない場合は、システムコールの方が良い選択です

  • ネットワーク関連のオブジェクトをソケットを通じて構成する場合はnetlinkが推奨されます。

  • デバッグ機能の即興インターフェースにはdebugfsが使用されます。これはアプリケーションに安定したインターフェースとして公開する必要がない場合です。

  • カーネル内オブジェクトの状態をファイルディスクリプタに依存しない形で公開するにはsysfsが適切です。

  • sysfsよりも複雑な設定にはconfigfsが使用できます

  • カスタムファイルシステムはシンプルなユーザーインターフェースで追加の柔軟性を提供できますが、実装には多くの複雑さを伴います。

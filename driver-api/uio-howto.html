はじめに¶

多くのデバイスではLinuxカーネルドライバを作成するのは過剰です。必要なのは、割り込みを処理し、デバイスのメモリ空間にアクセスする方法だけです。デバイスの制御ロジックは必ずしもカーネル内に必要ありません。なぜなら、デバイスがカーネルが提供する他のリソースを活用する必要がないからです。このような特徴を持つデバイスの典型的な例は産業用I/Oカードです。

このような状況に対応するため、ユーザー空間I/Oシステム（UIO）が設計されました。典型的な産業用I/Oカードでは、非常に小さなカーネルモジュールのみが必要です。ドライバの主な部分はユーザー空間で実行されます。これにより開発が簡単になり、カーネルモジュール内の重大なバグのリスクが低減されます。

UIOは万能のドライバインターフェースではありません。既に他のカーネルサブシステム（ネットワークやシリアル、USBなど）で十分に処理されているデバイスはUIOドライバの候補ではありません。UIOドライバに最適なハードウェアは以下の条件をすべて満たします：

  • デバイスはメモリマッピング可能なメモリを持ち、このメモリに書き込むことでデバイスを完全に制御できます。

  • デバイスは通常、割り込みを生成します。

  • デバイスはどの標準カーネルサブシステムにも該当しません。

UIOについて¶

UIOをカードのドライバに使用する場合、以下のようなメリットがあります：

  • ただ一つの小さなカーネルモジュールを書く必要があり、保守も簡単です。

  • ドライバの主な部分をユーザー空間で開発し、慣れ親しんだツールやライブラリを使用できます。

  • ドライバのバグがカーネルをクラッシュさせません。

  • ドライバの更新はカーネルの再コンパイルなしに実行できます。

UIOの仕組み¶

各UIOデバイスはデバイスファイルといくつかのsysfs属性ファイルを通じてアクセスされます。デバイスファイルは /dev/uio0 1番目のデバイスの場合、 /dev/uio1, /dev/uio2 2番目のデバイスの場合、

/dev/uioX カードのアドレス空間にアクセスするために使用されます。単に mmap() カードのレジスタやRAM領域にアクセスできます。

割り込みは /dev/uioX. ブロッキング read() from /dev/uioX 割り込みが発生した時点ですぐに返します。また、以下のように使用することもできます select() on /dev/uioX 割り込みを待機するための方法です。この整数値は /dev/uioX 割り込みの総数を表します。この数値を使用して、いくつかの割り込みを無視したかどうかを確認できます

複数の割り込みソースを持つが、個別にIRQマスクとステータスレジスタを持たないハードウェアでは、カーネルハンドラがチップのIRQレジスタに書き込みで割り込みを無効化した場合、ユーザースペースが割り込みの原因を特定できなくなる可能性があります。このような場合、カーネルはIRQを完全に無効化する必要があります。これによりチップのレジスタが変更されず、ユーザースペースが割り込みの原因を特定できますが、割り込みを再有効化することはできません。また、割り込みを再有効化する操作が統合されたIRQステータス/アサートレジスタへの読み取り-変更-書き込み操作であるチップでは、同時に新しい割り込みが発生した場合、競合状態が発生する可能性があります

これらの問題に対処するために、UIOはwrite()関数も実装しています。通常は使用されず、単一の割り込みソースを持つハードウェアや、個別にIRQマスクとステータスレジスタを持つハードウェアでは無視できます。ただし、必要とすれば、ドライバが実装するwrite()関数に書き込みます /dev/uioX は、 irqcontrol() ドライバがこの関数を実装していない場合、0または1の32ビット値を書き込むことで割り込みを無効化または有効化できます irqcontrol(), write() この関数は、0または1の32ビット値を書き込むことで割り込みを無効化または有効化できます -ENOSYS.

割り込みを適切に処理するには、カスタムカーネルモジュールが独自の割り込みハンドラを提供できます。これは組み込みハンドラによって自動的に呼び出されます

割り込みを生成しないがポーリングが必要なカードには、設定可能な時間間隔で割り込みハンドラをトリガーするタイマーセットが可能です。この割り込みシミュレーションは、タイマーイベントハンドラから uio_event_notify() 関数を呼び出すことで実行されます

各ドライバは変数を読み書きするための属性を提供します。これらの属性はsysfsファイルを通じてアクセス可能です。カスタムカーネルドライバモジュールは、uioドライバが所有するデバイスに独自の属性を追加できますが、現在はUIOデバイス自体には追加されていません。今後、これが有用であることが確認されれば変更される可能性があります

以下の標準的な属性がUIOフレームワークによって提供されます

  • name: デバイスの名前。この用途には、カーネルモジュールの名前を使用することをお勧めします

  • version: ドライバによって定義されたバージョン文字列。これにより、ドライバのユーザースペース部分がカーネルモジュールのさまざまなバージョンに対応できます

  • event: デバイスノードが読み取られた最後の時点でドライバが処理した割り込みの総数

これらの属性は /sys/class/uio/uioX ディレクトリの下に表示されます。このディレクトリがシンリンク（symlink）である可能性があり、実際のディレクトリではない場合があります。このディレクトリにアクセスするユーザースペースのコードは、シンリンクの可能性を考慮して動作する必要があります。

各UIOデバイスは、メモリマッピング可能なメモリ領域を1つまたは複数提供できます。これは、一部の産業用I/Oカードがドライバ内で複数のPCIメモリ領域にアクセスを必要とするためです。

各マッピングにはsysfs内に独自のディレクトリが作成され、最初のマッピングは /sys/class/uio/uioX/maps/map0/として表示されます。その後のマッピングは map1/, map2/というディレクトリを生成し、同様に続きます。これらのディレクトリは、マッピングのサイズが0でない場合にのみ表示されます。

Each mapX/ ディレクトリには、メモリの属性を示す読み取り専用ファイルが4つ含まれています。

  • name: このマッピングの文字列形式の識別子です。これはオプションで、空文字列でも可能です。ドライバがこれを設定することで、ユーザースペースが正しいマッピングを特定しやすくなります。

  • addr: マッピング可能なメモリのアドレスです。

  • size: addrで示されるメモリのバイト数です。

  • offset: ptrで取得されるポインタに加算する必要があるバイト数です。デバイスのメモリがページアライメントされていない場合、このオフセットの重要性が高まります。ptrで取得されるポインタは常にページアライメントされているため、このオフセットを常に加算するスタイルが推奨されます。 mmap() で取得されるポインタにこのオフセットを加算することで、実際のデバイスメモリにアクセスできます。 mmap() で取得されるポインタは常にページアライメントされているため、このオフセットを常に加算するスタイルが推奨されます。

ユーザースペースから異なるマッピングを区別するには、 offset コールの mmap() パラメータを調整します。マッピングNのメモリをマッピングするには、N倍のページサイズをオフセットとして使用する必要があります：

offset = N * getpagesize();

一部のハードウェアでは、メモリのような領域がこの技術でマッピングできない場合がありますが、ユーザースペースからアクセスする方法は依然として存在します。代表的な例はx86のioportsです。x86システムでは、ユーザースペースがこれらのioportsに ioperm(), iopl(), inb(), outb()関数などを使用してアクセスできます。

これらのioport領域はマッピングできないため、 /sys/class/uio/uioX/maps/ のように通常のメモリと同様に表示されません。ポート領域に関する情報がなければ、ドライバのユーザースペース部分がどのUIOデバイスにどのポートが属するかを特定するのは困難になります。

この状況に対応するため、新しいディレクトリ /sys/class/uio/uioX/portio/ が追加されました。このディレクトリは、ドライバがユーザースペースに1つ以上のポート領域に関する情報を渡したい場合にのみ存在します。その場合、 port0, port1というサブディレクトリが /sys/class/uio/uioX/portio/.

Each portX/ ディレクトリの下に表示され、このディレクトリにはポート領域の名前、開始アドレス、サイズ、およびタイプを示す読み取り専用ファイルが4つ含まれています。

  • name: このポート領域の文字列形式の識別子です。これはオプションで、空文字列でも可能です。ドライバがこれを設定することで、ユーザースペースが特定のポート領域を特定しやすくなります。

  • start: この領域の最初のポートです。

  • size: この領域のポート数。

  • porttype: ポートのタイプを記述する文字列。

割り込みハンドラの追加¶

あなたの割り込みハンドラで行うべきことは、ハードウェアの種類や、どのように処理するかによって異なります。カーネルの割り込みハンドラ内に書くコード量はできるだけ少なく保つべきです。あなたのハードウェアが、あなたが が 毎回の割り込み後に実行しなければならない動作を必要としない場合、ハンドラは空でも構いません。

一方で、あなたのハードウェアが が 毎回の割り込み後に実行する必要のある動作を必要とする場合、あなたは grace periodsを尊重しなければなりませんし、 カーネルモジュール内でこれを実行します。注意して下さい、ドライバのユーザースペース部分に頼ってはいけません。ユーザースペースのプログラムはいつでも終了する可能性があり、ハードウェアを適切な割り込み処理が必要な状態に残す可能性があります。

また、データをハードウェアから毎回の割り込み時に読み取ってカーネルメモリにバッファリングするアプリケーションも考えられます。この技術を使うことで、ユーザースペースのプログラムが割り込みを無視した場合でもデータの喪失を防ぐことができます。

共有割込みに関する注意点: ドライバーは、可能であれば割込み共有をサポートする必要があります。割込み共有が可能となるのは、ドライバーがハードウェアが割込みを発生させたかどうかを検出できる場合です。これは通常、割込みステータスレジスタを確認することで実現されます。ドライバーがIRQビットが実際に設定されていると検知した場合、その動作を実行し、ハンドラはIRQ_HANDLEDを返します。ドライバーが自分のハードウェアが割込みを発生させたとは判断しなかった場合、何もせずIRQ_NONEを返し、カーネルが次の可能な割込みハンドラを呼び出すのを許可します。

割込み共有をサポートしない場合、あなたのカードは空き割込みがないコンピュータでは動作しません。これはPCプラットフォームで頻繁に発生するため、割込み共有をサポートすることで多くの手間を省けます。

また、あなたのメモリマッピングのアドレスとサイズを含む配列を設定する必要があります。 struct resource この情報は、 .resource および .num_resources の struct platform_device.

を設定する必要があります。 .name の struct platform_device に（木の下から葉に向かって） "uio_pdrv" を汎用UIOプラットフォームデバイスドライバーを使用するように設定します。このドライバーは、与えられたリソースに基づいて mem[] 配列を埋め込み、デバイスを登録します。

汎用的な割込みハンドラの『 uio_pdrv_genirq は、『 disable_irq_nosync()』を使用して割込みラインを無効化します。作業を完了した後、ユーザー空間はUIOデバイスファイルに0x00000001を書き込むことで割込みを再有効化できます。ドライバーはすでに『 irq_control() 』を実装しているため、自前の実装は行わないでください。

Using uio_pdrv_genirq 割り込みハンドラのコードを数行節約するだけでなく、チップの内部レジスタについて何も知らない状態でも、ドライバのカーネル部分を作成できます。必要なのは、チップが接続されているピンの割り込み番号だけです。

デバイスツリーが有効なシステムで使用する場合、ドライバは "of_id" モジュールパラメータを "compatible" ドライバが処理すべきノードの文字列に設定してプローブする必要があります。デフォルトでは、ノード名（ユニットアドレスを除く）がユーザー空間のUIOデバイスの名前として公開されます。カスタム名を設定するには、DTノードで "linux,uio-name" というプロパティを指定できます。

プラットフォームデバイスでのuio_dmem_genirqの使用¶

静的割り当てのメモリ範囲に加えて、ユーザー空間ドライバで動的割り当ての領域を使用したい場合もあります。特にdma-mapping APIを通じてメモリにアクセスできるのは非常に有用です。 uio_dmem_genirq ドライバはこれを実現する方法を提供します。

このドライバは、割り込み設定とハンドリングに関して "uio_pdrv_genirq" ドライバと同様の方法で使用されます。

以下の .name の struct platform_device に（木の下から葉に向かって） "uio_dmem_genirq" このドライバーを使用するための設定を行います。

を埋め込む必要があります。 .platform_data の struct platform_device、これは struct uio_dmem_genirq_pdata 型であり、以下の要素を含みます：

  • struct uio_info uioinfo： uio_pdrv_genirq プラットフォームデータと同じ構造体を使用します

  • unsigned int *dynamic_region_sizes：ユーザー空間にマップする動的メモリ領域のサイズのポインタリスト

  • unsigned int num_dynamic_regions： dynamic_region_sizes 配列を表しています。

内の要素数。プラットフォームデータで定義された動的領域は、プラットフォームデバイスリソースの後に`` mem[] ``配列に追加されるため、静的と動的のメモリ領域の総数は MAX_UIO_MAPS.

を超えてはなりません。動的メモリ領域は、UIOデバイスファイル /dev/uioX が開かれたときに割り当てられます。静的メモリリソースと同様に、動的領域のメモリ情報はsysfsの /sys/class/uio/uioX/maps/mapY/*で確認できます。動的メモリ領域は、UIOデバイスファイルが閉じるときに解放されます。どのプロセスもデバイスファイルを開いていない場合、ユーザー空間に返されるアドレスは~0です。

ユーザー空間でドライバーを作成する¶

動作するカーネルモジュールがハードウェアに作成できた場合、ドライバのユーザー空間部分を記述できます。特別なライブラリは必要なく、ドライバは通常の言語で記述でき、浮動小数点数を使用することも可能です。要するに、通常のユーザー空間アプリケーションで使用するツールやライブラリをすべて利用できます。

必要なメモリマッピングが存在し、予期するサイズになっているか確認してください。

あるツールがあります。 lsuio UIOデバイスとその属性を一覧表示します。こちらから入手できます。

ユーザー空間ドライバコードで使用できる多くの関数を含んでいます。¶

mmap()デバイスメモリ mmap() 必要なメモリマッピングを持つ正しいデバイスを確認した後は、以下を呼び出すだけです。

パラメータ offset の mmap() 呼び出しではUIOデバイスでは特別な意味を持ちます。これは、デバイスのどのマッピングをマップするかを選択するために使用されます。マッピングNのメモリをマップするには、オフセットとしてN倍のページサイズを使用します：

offset = N * getpagesize();

Nはゼロから始まります。したがって、1つのメモリ範囲のみをマップする場合は、 offset = 0を設定してください。この技術の欠点は、メモリが常に開始アドレスからマップされるということです。

割込みを待機¶

デバイスのメモリを成功裏にマッピングした後は、通常の配列のようにアクセスできます。通常、初期化を行います。その後、ハードウェアが動作を開始し、完了、データが利用可能、またはエラーが発生した際に割込みを生成します。

/dev/uioX は読み取り専用ファイルです。A read() は常に割込みが発生するまでブロックします。 count パラメータの read()、その値は符号付き32ビット整数（4）のサイズです。 count がその値に下がります。ただし、 read() を指定すると失敗します。読み取った符号付き32ビット整数は、デバイスの割込みカウントです。最後に読み取った値よりも1大きい場合は問題ありません。差が1より大きい場合は、割込みを無視した可能性があります。

また、 select() on /dev/uioX.

汎用PCI UIOドライバー¶

汎用ドライバはカーネルモジュールuio_pci_genericです。これは、PCI 2.3（約2002年）に準拠したデバイスや、PCI Expressに準拠したデバイスと動作します。これを使用することで、ハードウェア固有のカーネルモジュールを書く必要はなく、ユーザー空間ドライバのみを書くだけで済みます。

ドライバがデバイスを認識するようにする¶

ドライバがデバイスIDを宣言していないため、自動的にロードされず、デバイスに自動的にバインドされることもありません。そのため、自分でロードし、ドライバにIDを割り当てなければなりません。例えば：

modprobe uio_pci_generic
echo "8086 10f5" > /sys/bus/pci/drivers/uio_pci_generic/new_id

すでにデバイス用のハードウェア固有のカーネルドライバーが存在する場合、汎用ドライバーもそのデバイスにバインドできません。このような場合、汎用ドライバーを使用したい（なぜでしょうか？）場合は、手動でハードウェア固有のドライバーをアンバインドし、汎用ドライバーをバインドする必要があります。以下のように行います：

echo -n 0000:00:19.0 > /sys/bus/pci/drivers/e1000e/unbind
echo -n 0000:00:19.0 > /sys/bus/pci/drivers/uio_pci_generic/bind

デバイスがドライバーにバインドされているかを確認するには、sysfsで確認できます。例えば以下のようにします：

ls -l /sys/bus/pci/devices/0000:00:19.0/driver

成功した場合、以下のように表示されます：

.../0000:00:19.0/driver -> ../../../bus/pci/drivers/uio_pci_generic

注意点として、汎用ドライバーは旧型のPCI 2.2デバイスにはバインドできません。デバイスのバインドに失敗した場合は、次のコマンドを実行してください：

dmesg

そして出力結果で失敗の原因を確認してください。

uio_pci_genericについての注意点¶

割込みは、PCIコマンドレジスタの割込み無効ビットと、PCIステータスレジスタの割込みステータスビットを使用して処理されます。すべてのPCI 2.3準拠デバイス（2002年頃）およびすべてのPCI Express準拠デバイスはこれらのビットをサポートする必要があります。uio_pci_genericはこのサポートを検出し、コマンドレジスタに割込み無効ビットが存在しないデバイスにはバインドしません。

各割込み発生時にuio_pci_genericは割込み無効ビットを設定します。これにより、ビットがクリアされるまでデバイスがさらに割込みを生成できなくなります。ユーザースペースドライバーは、ブロック処理を行い次の割込みを待機する前にこのビットをクリアする必要があります。

uio_pci_genericを使用したユーザースペースドライバーの作成¶

ユーザースペースドライバーは、pci sysfsインターフェースを使用するか、libpciライブラリ（インターフェースをラップしたもの）を使用してデバイスと通信し、コマンドレジスタに書き込むことで割込みを再有効化できます。

uio_pci_genericを使用したサンプルコード¶

以下はuio_pci_genericを使用したユーザースペースドライバーのサンプルコードです：

#include <stdlib.h>
#include <stdio.h>
#include <unistd.h>
#include <sys/types.h>
#include <sys/stat.h>
#include <fcntl.h>
#include <errno.h>

int main()
{
    int uiofd;
    int configfd;
    int err;
    int i;
    unsigned icount;
    unsigned char command_high;

    uiofd = open("/dev/uio0", O_RDONLY);
    if (uiofd < 0) {
        perror("uio open:");
        return errno;
    }
    configfd = open("/sys/class/uio/uio0/device/config", O_RDWR);
    if (configfd < 0) {
        perror("config open:");
        return errno;
    }

    /* Read and cache command value */
    err = pread(configfd, &command_high, 1, 5);
    if (err != 1) {
        perror("command config read:");
        return errno;
    }
    command_high &= ~0x4;

    for(i = 0;; ++i) {
        /* Print out a message, for debugging. */
        if (i == 0)
            fprintf(stderr, "Started uio test driver.\n");
        else
            fprintf(stderr, "Interrupts: %d\n", icount);

        /****************************************/
        /* Here we got an interrupt from the
           device. Do something to it. */
        /****************************************/

        /* Re-enable interrupts. */
        err = pwrite(configfd, &command_high, 1, 5);
        if (err != 1) {
            perror("config write:");
            break;
        }

        /* Wait for next interrupt. */
        err = read(uiofd, &icount, 4);
        if (err != 4) {
            perror("uio read:");
            break;
        }

    }
    return errno;
}

汎用Hyper-V UIOドライバー¶

汎用ドライバーはカーネルモジュールとしてuio_hv_genericと呼ばれ、Hyper-V VMBus上のデバイスをPCIバス上のuio_pci_genericと同様にサポートします。

ドライバがデバイスを認識するようにする¶

ドライバーはデバイスのGUIDを宣言していないため、自動的にロードされず、デバイスに自動的にバインドすることもありません。自分でドライバーをロードし、IDを割り当ててください。例えばネットワークデバイスクラスGUIDを使用する場合、以下のようにします：

modprobe uio_hv_generic
echo "f8615163-df3e-46c5-913f-f2d2f965ed0e" > /sys/bus/vmbus/drivers/uio_hv_generic/new_id

すでにデバイス用のハードウェア固有のカーネルドライバーが存在する場合、汎用ドライバーもそのデバイスにバインドできません。このような場合、ユーザースペースライブラリで汎用ドライバーを使用したい場合は、手動でハードウェア固有のドライバーをアンバインドし、汎用ドライバーをバインドする必要があります。デバイス固有のGUIDを使用して以下のように行います：

echo -n ed963694-e847-4b2a-85af-bc9cfc11d6f3 > /sys/bus/vmbus/drivers/hv_netvsc/unbind
echo -n ed963694-e847-4b2a-85af-bc9cfc11d6f3 > /sys/bus/vmbus/drivers/uio_hv_generic/bind

デバイスがドライバーにバインドされているかを確認するには、sysfsで確認できます。例えば以下のようにします：

ls -l /sys/bus/vmbus/devices/ed963694-e847-4b2a-85af-bc9cfc11d6f3/driver

成功した場合、以下のように表示されます：

.../ed963694-e847-4b2a-85af-bc9cfc11d6f3/driver -> ../../../bus/vmbus/drivers/uio_hv_generic

uio_hv_genericについての注意点¶

各割込みごとに、uio_hv_generic は割込み無効ビットを設定します。これにより、ビットがクリアされるまでデバイスがさらに割込みを生成できなくなります。ユーザースペースドライバーは、ブロッキングして割込みを待つ前にこのビットをクリアする必要があります。

ホストがデバイスを切断した場合、割込みファイル記述子は無効とされ、割込みファイル記述子の読み取りは -EIO を返します。これは閉じられたソケットや切断されたシリアルデバイスに似ています。

vmbus デバイス領域は uio デバイスリソースにマッピングされます:

  1. チャネルリングバッファ: ゲストからホストへ、ホストからゲストへ

  2. ゲストからホストへ向けた割込み通知ページ

  3. ゲストからホストへ向けたモニターページ

  4. ネットワーク受信バッファ領域

  5. ネットワーク送信バッファ領域

ホストへのリクエストによってサブチャネルが作成された場合、uio_hv_generic デバイスドライバーは、各チャネルリングバッファ用の sysfs バイナリファイルを作成します。例えば:

/sys/bus/vmbus/devices/3811fe4d-0fa0-4b62-981a-74fc1084c757/channels/21/ring

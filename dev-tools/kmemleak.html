Kernel Memory Leak Detector¶

Kmemleakは、トレースガベージコレクタと同様の方法でカーネルメモリリークを検出する方法を提供します トレースガベージコレクタ、ただしorphansオブジェクトは解放されず、/sys/kernel/debug/kmemleak経由でのみ報告されます。Valgrindツール（memcheck --leak-check)は、ユーザー空間アプリケーションにおけるメモリリークを検出するために同様の方法を使用します。

使い方¶

「Kernel hacking」のCONFIG_DEBUG_KMEMLEAKを有効にする必要があります。カーネルスレッドはデフォルトで10分ごとにメモリをスキャンし、新規に見つかった参照されていないオブジェクトの数を出力します。もし debugfs がまだマウントされていない場合は、以下でマウントしてください：

# mount -t debugfs nodev /sys/kernel/debug/

すべての可能なスキャンされたメモリリークの詳細を表示するには：

# cat /sys/kernel/debug/kmemleak

中間のメモリスキャンをトリガーするには：

# echo scan > /sys/kernel/debug/kmemleak

すべての現在の可能なメモリリークのリストをクリアするには：

# echo clear > /sys/kernel/debug/kmemleak

新しいリークは、読み込む際に表示されます /sys/kernel/debug/kmemleak また。

注意：orphansオブジェクトは割当順にリストされ、リストの先頭にあるオブジェクトが他の後続のオブジェクトをorphansとして報告する原因となることがあります。

メモリスキャンパラメータは、ファイルに書き込むことで実行時にも変更可能です。サポートされるパラメータは以下の通りです： /sys/kernel/debug/kmemleak file

  • off

    kmemleakを無効化 (不可逆的)

  • stack=on

    タスクスタックのスキャンを有効にする (デフォルト)

  • stack=off

    タスクスタックのスキャンを無効にする

  • scan=on

    自動メモリスキャンスレッドを開始する (デフォルト)

  • scan=off

    自動メモリスキャンスレッドを停止する

  • scan=<secs>

    自動メモリスキャンの周期を秒単位で設定 (デフォルト600秒、0で自動スキャンを停止)

  • スキャン

    メモリスキャンをトリガーする

  • クリア

    現在のメモリリークの疑いをクリアする (現在報告されている参照されていないオブジェクトを灰色にマークするか、kmemleakが無効化されている場合、すべてのkmemleakオブジェクトを解放する)

  • dump=<addr>

    <addr>に存在するオブジェクトに関する情報をダンプする

Kmemleakは、カーネル起動時に以下のパラメータを指定することで無効化することも可能です： kmemleak=off on

kmemleakが初期化される前にメモリが割当てられたり解放されたりする場合、これらの操作は早期ログバッファに保存されます。このバッファのサイズはCONFIG_DEBUG_KMEMLEAK_MEM_POOL_SIZEオプションで設定されます。

CONFIG_DEBUG_KMEMLEAK_DEFAULT_OFFが有効な場合、kmemleakはデフォルトで無効になります。以下のパラメータをカーネルコマンドラインに指定することで機能を有効化できます： kmemleak=on on

「Error while writing to stdout」や「write_loop: Invalid argument」などのエラーが発生している場合は、kmemleakが正しく有効になっているか確認してください。

基本アルゴリズム¶

メモリ割当ては kmalloc(), vmalloc(), kmem_cache_alloc() 関連するメモリブロックは追跡され、ポインタとともにサイズやスタックトレースなどの追加情報がrbtreeに保存されます。対応する解放関数呼び出しは追跡され、ポインタはkmemleakデータ構造から削除されます。

割当されたメモリブロックが、メモリ（保存されたレジスタを含む）をスキャンしてもその開始アドレスやブロック内のどこかへのポインタが見つからない場合、孤立した（orphan）とみなされます。これは、カーネルがこの割当ブロックのアドレスを解放関数に渡す方法が存在しない可能性があるため、このブロックがメモリリークとみなされる可能性があります。

スキャンアルゴリズムのステップ:

  1. すべてのオブジェクトを白（remaining white objectsは後に孤立したとみなされます）にマーク

  2. データセクションとスタックからメモリをスキャンし、rbtreeに保存されたアドレスと値を照合します。白オブジェクトへのポインタが見つかった場合、そのオブジェクトはグレーリストに追加されます

  3. グレーリストのオブジェクトを照合し、一致するアドレスを探します（一部の白オブジェクトはグレーリストの末尾に追加されることがあります）までグレーリストを完了します

  4. 残った白オブジェクトは孤立したとみなされ、/sys/kernel/debug/kmemleak経由で報告されます

一部の割当メモリブロックは、カーネルの内部データ構造にポインタが保存されているため、孤立したと検出されません。これを防ぐために、kmemleakはブロックアドレス範囲内に存在するアドレスへのポインタの数を保存することもできます。これにより、ブロックがメモのリークとみなされません。__vmalloc()はこのような例です。

kmemleak で特定のセクションをテストする¶

初期起動時に/sys/kernel/debug/kmemleakの出力ページは非常に長くなることがあります。開発中に非常に不具合のあるコードを実行している場合でも同様です。このような状況を回避するには、「clear」コマンドを使用して、/sys/kernel/debug/kmemleak出力からすべての参照されていないオブジェクトをクリアできます。その後、「scan」を実行して新しい参照されていないオブジェクトを検出することで、特定のコードセクションのテストに役立ちます。

クリーンなkmemleakで必要なときに重要なセクションをテストするには:

# echo clear > /sys/kernel/debug/kmemleak
... test your kernel or modules ...
# echo scan > /sys/kernel/debug/kmemleak

通常通りレポートを取得するには:

# cat /sys/kernel/debug/kmemleak

kmemleak 内部オブジェクトの解放¶

kmemleakがユーザーによって無効化された後や致命的なエラーにより無効化された場合、内部のkmemleakオブジェクトは無効化されず、それらのオブジェクトが物理メモリの大きな部分を占める可能性があります。

このような状況では、メモリを回収するには:

# echo clear > /sys/kernel/debug/kmemleak

kmemleak API¶

関数プロトタイプについては、include/linux/kmemleak.hヘッダーファイルを参照してください。

  • kmemleak_init - kmemleakを初期化する

  • kmemleak_alloc - メモリブロックの割当を通知する

  • kmemleak_alloc_percpu - percpuメモリブロックの割り当てを通知

  • kmemleak_vmalloc - 割り当てを通知 vmalloc() メモリ割り当て

  • kmemleak_free - メモリブロックの解放を通知

  • kmemleak_free_part - 部分的なメモリブロックの解放を通知

  • kmemleak_free_percpu - percpuメモリブロックの解放を通知

  • kmemleak_update_trace - オブジェクト割り当てのスタックトレースを更新

  • kmemleak_not_leak - オブジェクトをリークでないものとしてマーク

  • kmemleak_ignore - オブジェクトをリークとしてスキャンまたはレポートしない

  • kmemleak_scan_area - メモリブロック内にスキャン領域を追加

  • kmemleak_no_scan - メモリブロックをスキャンしない

  • kmemleak_erase - ポインタ変数の古い値を削除

  • kmemleak_alloc_recursive - kmemleak_allocと同様ですが、再帰性を確認

  • kmemleak_free_recursive - kmemleak_freeと同様ですが、再帰性を確認

次の関数は、オブジェクトポインタとして物理アドレスを受け取り、アドレスがlowmemマッピングを持つ場合にのみ対応するアクションを実行します:

  • kmemleak_alloc_phys

  • kmemleak_free_part_phys

  • kmemleak_not_leak_phys

  • kmemleak_ignore_phys

偽陽性/偽陰性の処理¶

偽陰性は実際のメモリリーク（orphans）ですが、kmemleakがメモリスキャン中に見つける値がそのオブジェクトを指しているため報告されません。偽陰性の数を減らすために、kmemleakはkmemleak_ignore、kmemleak_scan_area、kmemleak_no_scan、kmemleak_erase関数を提供しています（上記参照）。タスクスタックも偽陰性の数を増やす要因であり、デフォルトではスキャンが有効ではありません。

偽陽性は誤ってメモリリーク（orphans）として報告されるオブジェクトです。リークでないことが分かっているオブジェクトにはkmemleak_not_leak関数が提供されます。メモリブロックが他のポインタを含まないことが分かっている場合は、kmemleak_ignoreも使用可能です。これにより、それ以降スキャンされなくなります。

報告されたリークの一部は一時的であり、特にSMPシステムではCPUレジスタやスタックに一時的に保存されたポインタの影響で発生します。kmemleakはMSECS_MIN_AGE（デフォルトでは1000）を定義し、リークとして報告されるオブジェクトの最小年齢を表します。

制限と欠点¶

主なデメリットはメモリ割り当てと解放のパフォーマンス低下です。他のペナルティを回避するため、メモリスキャンは/sys/kernel/debug/kmemleakファイルが読み込まれるときにのみ実行されます。ただし、このツールはデバッグ目的で使用されるため、パフォーマンスが最も重要な要件ではないと想定されています。

アルゴリズムを単純にするため、kmemleakはブロックのアドレス範囲内の任意のアドレスにポインタを指している値を検索します。これにより偽陰性の数が増える可能性がありますが、実際のメモリリークは最終的に見つかる可能性が高いです。

偽陰性の他の原因はポインタ値以外のデータに保存されている情報です。今後のバージョンでは、割り当てられた構造体のポインタメンバのみをスキャンする機能が追加される予定です。この機能により、上述の多くの偽陰性ケースが解消される可能性があります。

このツールは偽陽性を報告することがあります。これは割り当てられたブロックが解放する必要がない場合（init_call関数の一部）や、通常のcontainer_ofマクロ以外の方法でポインタが計算される場合、またはkmemleakがスキャンしない場所にポインタが保存されている場合です。

ページの割り当てやioremapは追跡されません。

kmemleak-test でのテスト¶

kmemleakを正しく設定しているか確認するには、kmemleak-testモジュールを使用できます。このモジュールは意図的にメモリをリークさせるためのものです。CONFIG_DEBUG_KMEMLEAK_TESTをモジュールとして設定し（ビルトインでは使用できません）、kmemleakを有効にしてカーネルを起動します。モジュールをロードし、以下のコマンドでスキャンを行います:

# modprobe kmemleak-test
# echo scan > /sys/kernel/debug/kmemleak

結果がすぐに表示されない場合があります。kmemleakが結果を取得すると、ログに記録します kmemleak: <count of leaks> new suspected memory leaks。ファイルを読み込んで確認してください。

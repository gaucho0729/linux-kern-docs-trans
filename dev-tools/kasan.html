The Kernel Address Sanitizer (KASAN)¶

概要¶

カーネルアドレスサニタイザー (KASAN) は、バウンダリ外アクセスや使用後の解放エラーなどのメモリセキュリティエラーを検出する動的検出ツールです。KASAN は 3 種類のモードがあります:

  1. ジェネリック KASAN (ユーザー空間 ASan と似ています),

  2. ソフトウェアタグベース KASAN (ユーザー空間 HWASan と似ています),

  3. ハードウェアタグベース KASAN (ハードウェアメモリタギングに基づいています).

ソフトウェアベースの KASAN モード (1 と 2) は、コンパイル時にインストルメンテーションを挿入してメモリアクセスごとに有効性チェックを行います。そのため、サポートするコンパイラバージョンが必要です。

ジェネリック KASAN は GCC および Clang の両方でサポートされています。GCC ではバージョン 8.3.0 以上が必要です。サポートされている任意の Clang バージョンは互換性がありますが、グローバル変数のバウンダリ外アクセス検出は Clang 11 以降でのみサポートされています。

タグベースの KASAN は Clang でのみサポートされています。

現在、ジェネリック KASAN は x86_64、arm64、xtensa、s390 および riscv アーキテクチャでサポートされており、タグベースの KASAN モードは arm64 でのみサポートされています。

使い方¶

KASAN を有効にするには、カーネルを構築する際には以下の設定を行います:

CONFIG_KASAN = y

CONFIG_KASAN_GENERIC (ジェネリック KASAN を有効にする)、CONFIG_KASAN_SW_TAGS (ソフトウェアタグベース KASAN を有効にする)、および CONFIG_KASAN_HW_TAGS (ハードウェアタグベース KASAN を有効にする) のいずれかを選択します。

ソフトウェアベースのモードでは、CONFIG_KASAN_OUTLINE と CONFIG_KASAN_INLINE のどちらかを選択します。アウトラインとインラインはコンパイラインストルメンテーションの種類です。前者はより小さなバイナリを生成しますが、後者は 1.1〜2 倍高速です。

ソフトウェアベースの KASAN モードは SLUB および SLAB メモリアロケータとも動作しますが、ハードウェアタグベースの KASAN は現在 SLUB でのみサポートされています。

スタックトレースを含むより詳細なエラーレポートを取得するには、CONFIG_STACKTRACE を有効にしてください。

物理ページの最後の割り当てと解放スタックをレポートに追加するには、CONFIG_PAGE_OWNER も有効にして、page_owner=on で起動することを推奨します。

レポートのヘッダーには、発生したエラーの種類と原因となったアクセスの種類が簡潔にまとめられています。その後に、不正なアクセスのスタックトレース、アクセスされたメモリが割り当てられた場所のスタックトレース（スラブオブジェクトの場合）、およびオブジェクトが解放された場所のスタックトレース（使用後の解放エラーの場合）が続きます。次に、アクセスされたスラブオブジェクトの説明とアクセスされたメモリページに関する情報が続きます。

前のセクションでは、アクセスされたアドレス周辺のメモリ状態が報告されています。KASANは、メモリの粒度ごとにメモリ状態を別々に追跡しており、これはKASANモードによって8バイトまたは16バイトにアライメントされたメモリ粒度です。報告のメモリ状態セクションにある各数字は、アクセスされたアドレスを囲むメモリ粒度の状態を示します。

一般的なKASANでは、各メモリ粒度のサイズは8バイトです。各粒度の状態は1つのシャドウバイトで符号化されます。これらの8バイトは、アクセス可能、部分的にアクセス可能、解放済み、またはレッドゾーンの一部である可能性があります。KASANは、各シャドウバイトに対して次の符号化を使用します：0は、対応するメモリ領域のすべての8バイトがアクセス可能を意味します；数値N（1 <= N <= 7）は、最初のNバイトがアクセス可能で、他の（8 - N）バイトはアクセス不可能を意味します；負の値は、8バイトのワード全体がアクセス不可能を示します。KASANは、レッドゾーンや解放済みメモリなどの異なる種類のアクセス不可能メモリを区別するために異なる負の値を使用します（参照：mm/kasan/kasan.h）。

上の報告では、矢印はシャドウバイト03を指しており、これはアクセスされたアドレスが部分的にアクセス可能であることを示します。タグベースのKASANモードでは、この最後の報告セクションはアクセスされたアドレス周辺のメモリタグを表示します（参照： 実装詳細 セクション）。

ブートパラメータ¶

ハードウェアタグベースのKASANモード（下記のセクションで説明）は、セキュリティ対策として生産環境での使用を目的としています。そのため、KASANを完全に無効化したり、特定のKASAN機能を制御するためのブートパラメータをサポートしています。

  • kasan=off または =on KASANが有効かどうかを制御します（デフォルト： on).

  • kasan.mode=sync または =async KASANが同期モードまたは非同期モードで実行されるかを制御します（デフォルト： sync）。同期モード：タグチェックエラーが発生したときに即座に不正アクセスを検出します。非同期モード：不正アクセスの検出が遅延されます。タグチェックエラーが発生した際、情報はハードウェア（arm64ではTFSR_EL1レジスタ）に保存され、カーネルは定期的にハードウェアをチェックし、これらのチェック中にのみタグエラーを報告します。

  • kasan.stacktrace=off または =on アロケーションとフリースタックトレースの収集を無効化または有効化します（デフォルト： on).

  • kasan.fault=report または =panic KASANレポートのみを表示するか、カーネルをパニックにさせるかを制御します（デフォルト： report）。注意：タグチェックは最初のバグ報告後には無効になります。

開発者向け¶

ソフトウェア KASAN モードはコンパイラによるインストルメンテーションを使用して妥当性チェックを挿入します。このようなインストルメンテーションは一部のカーネルと互換性がなく、そのため無効にする必要があります。特定のファイルまたはディレクトリのインストルメンテーションを無効にするには、対応するカーネル Makefile に以下の例に類似した行を追加してください：

  • 特定のディレクトリ内のすべてのファイルの場合：

    KASAN_SANITIZE_main.o := n

  • CONFIG_GCOV_PROFILE_ALLが指定された場合でもプロファイリング対象から除外するには：

    KASAN_SANITIZE := n

実装詳細¶

ジェネリック KASAN¶

高レベルの観点から見ると、KASAN のメモリエラー検出アプローチは kmemcheck と同様で、シャドウメモリを使用して各バイトのメモリがアクセス可能かどうかを記録し、コンパイル時インストルメンテーションを使用して各メモリアクセス時にシャドウメモリをチェックします。

ジェネリック KASAN はカーネルメモリの 1/8 をシャドウメモリに割り当てます（例：x86_64 では 128TB のカバーに 16TB を使用）。メモリアドレスを対応するシャドウアドレスに変換するには、スケールとオフセットを用いた直接マッピングを使用します。

アドレスを対応するシャドウアドレスに変換する関数は次の通りです：

static inline void *kasan_mem_to_shadow(const void *addr)
{
    return ((unsigned long)addr >> KASAN_SHADOW_SCALE_SHIFT)
            + KASAN_SHADOW_OFFSET;
}

オプションを指定する必要があります。形式は以下の通りです： KASAN_SHADOW_SCALE_SHIFT = 3.

コンパイル時インストルメンテーションはメモリアクセスチェックを挿入します。コンパイラは 1、2、4、8、または 16 バイトのサイズの各メモリアクセスの前に __asan_load*(addr)、__asan_store*(addr) などの関数呼び出しを挿入します。これらの関数はシャドウメモリをチェックしてメモリアクセスが有効かどうかを確認します。

GCC 5.0 はインラインインストルメンテーションを実行する可能性があります。関数呼び出しではなく、コンパイラが直接シャドウメモリをチェックするコードを挿入します。このオプションはカーネルサイズを大幅に拡大しますが、アウトラインインストルメンテーションされたカーネルと比較して x1.1 〜 x2 のパフォーマンス向上をもたらします。

ジェネリック KASAN は、オブジェクトにアクセスする可能性のある作業の生成時に最後の 2 つのコールスタックを報告します。以下のコールスタックが表示されます： call_rcu() およびワークキューのキューイング。

ジェネリック KASAN は、クォラント（quarantine）を介して解放されたオブジェクトの再利用を遅延させる唯一のモードです（実装は mm/kasan/quarantine.c を参照してください）。

ソフトウェアタグベース KASAN¶

ソフトウェアタグベース KASAN は、HWASan に類似したコンパイラインストルメンテーション形式のソフトウェアメモリタグサポートを必要とします（詳細は HWASan ドキュメントを参照してください）。

ソフトウェアタグベース KASAN は現在、arm64 アーキテクチャのみで実装されています。

ソフトウェアタグベース KASAN は arm64 CPU のトップバイト無視（TBI）機能を使用して、カーネルポインタのトップバイトにポインタータグを保存します。ジェネリック KASAN と同様に、シャドウメモリを使用して各 16 バイトメモリセルに関連するメモリタグを保存します（そのためシャドウメモリにはカーネルメモリの 1/16 を割り当てます）。

メモリ割当ごとにソフトウェアタグベースのKASANはランダムなタグを生成し、そのタグで割当たったメモリをタグ付けし、このタグを返却されたポインタに埋め込みます。

ソフトウェアタグベースのKASANはコンパイル時にインストルメンテーションを挿入し、各メモリアクセスの前にチェックを行います。これらのチェックは、アクセスしているメモリのタグが、そのメモリにアクセスするポインタのタグと一致していることを確認します。タグ不一致の場合は、ソフトウェアタグベースのKASANはバグレポートを出力します。

ソフトウェアタグベースのKASANには2つのインストルメンテーションモードがあります（アウトラインモードはメモリアクセスをチェックするためのコールバックを発行するもの、インラインモードはシャドウメモリチェックをインラインで実行するもの）。アウトラインモードでは、アクセスチェックを実行する関数から単純にバグレポートが出力されます。インラインモードではコンパイラがbrk命令を発行し、専用のbrkハンドラを使用してバグレポートを出力します。

ソフトウェアタグベースのKASANは0xFFをすべてのポインタタグに一致するタグとして使用します（0xFFタグを持つポインタによるアクセスはチェックされません）。現在は0xFEが解放されたメモリ領域をタグ付けするための予約値です。

ソフトウェアタグベースのKASANは現在、kmem_cache_alloc/kmallocおよびpage_allocメモリのタグ付けのみをサポートしています。

ハードウェアタグベースのKASAN¶

ハードウェアタグベースのKASANは概念的にはソフトウェアモードと同様ですが、コンパイラインストルメンテーションとシャドウメモリではなく、ハードウェアメモリタグ付け機能を使用します。

ハードウェアタグベースのKASANは現在、arm64アーキテクチャにのみ実装されており、ARMv8.5インストラクションセットアーキテクチャで導入されたMemory Tagging Extension（MTE）とTop Byte Ignore（TBI）に基づいています。

特別なarm64命令が各割当に対してメモリタグを割り当てます。同じタグがこれらの割当のポインタにも割り当てられます。すべてのメモリアクセスにおいてハードウェアが、アクセスしているメモリのタグが、そのメモリにアクセスするポインタのタグと一致していることを確認します。タグ不一致の場合はエラーが発生し、レポートが出力されます。

ハードウェアタグベースのKASANは0xFFをすべてのポインタタグに一致するタグとして使用します（0xFFタグを持つポインタによるアクセスはチェックされません）。現在は0xFEが解放されたメモリ領域をタグ付けするための予約値です。

ハードウェアタグベースのKASANは現在、kmem_cache_alloc/kmallocおよびpage_allocメモリのタグ付けのみをサポートしています。

ハードウェアがMTE（ARMv8.5以前）をサポートしない場合、ハードウェアタグベースのKASANは有効になりません。この場合、すべてのブートパラメータは無視されます。

CONFIG_KASAN_HW_TAGSを有効にすると、常に内核のTBIが有効になります。kasan.mode=offを指定しても、またはハードウェアがMTEをサポートしないがTBIをサポートしている場合でも、この結果は変わりません。

ハードウェアタグベースのKASANは、最初に検出されたバグのみを報告します。その後、MTEタグのチェックは無効になります。

KASAN がサニタイズするメモリアクセスは何か？¶

カーネルはアドレス空間のさまざまな部分でメモリをマッピングします。これにより、KASANがインストルメントコードがアクセスするすべてのアドレスに有効なシャドウ領域があることを要求するという問題が生じます。

カーネルの仮想アドレス範囲は非常に広く、カーネルがアクセス可能なすべてのアドレスに実際のメモリでシャドウ領域を確保するには実際のメモリが不足しています。

デフォルトでは¶

デフォルトでは、アーキテクチャは線形マッピング（および他の小さな領域を含む）のシャドウ領域上に実メモリをマッピングします。その他の領域（vmallocやvmemmap領域など）では、シャドウ領域上に1つの読み取り専用ページをマッピングします。この読み取り専用シャドウページはすべてのメモリアクセスを許可と宣言します。

これはモジュールにとって問題になります。モジュールは線形マッピングではなく、専用のモジュール領域に存在します。モジュールアロケータにハックすることで、KASANは一時的に実際のシャドウメモリをマッピングしてモジュールをカバーできます。これにより、モジュールグローバル変数への無効なアクセスの検出が可能になります。

これにより、 VMAP_STACKスタックがvmalloc領域に存在する場合、読み取り専用ページによってシャドウされます。これにより、スタック変数のシャドウデータを設定しようとするとカーネルがフェールします。

CONFIG_KASAN_VMALLOC¶

With CONFIG_KASAN_VMALLOC、KASANはvmalloc領域をカバーできますが、メモリ使用量が増加します。現在はx86アーキテクチャでのみサポートされています。

これはvmallocとvmapにハックし、マッピングをバックする実際のシャドウメモリを動的に割り当てる仕組みで動作します。

vmalloc領域のほとんどのマッピングは小さく、1ページ分のシャドウ領域を必要としません。したがって、各マッピングに1ページのシャドウ領域を割り当てるには無駄です。さらに、異なるマッピングが異なるシャドウページを使用するようにするには、マッピングを KASAN_GRANULE_SIZE * PAGE_SIZE.

代わりに、KASANは複数のマッピングでバック領域を共有します。vmalloc領域のマッピングがシャドウ領域の特定のページを使用するときにバックページを割り当てます。このページは後続の他のvmallocマッピングでも共有できます。

KASANはvmapインフラストラクチャにハックし、未使用のシャドウメモリをラズィーにクリーンアップします。

マッピングの交換に関する困難を避けるため、KASANは、shadow領域のうちvmalloc領域をカバーする部分が初期shadowページによってカバーされず、未マッピングのままにされることが期待されています。これにより、アーキテクチャ固有のコードでの変更が必要になります。

これにより VMAP_STACK x86でのサポートが可能となり、固定されたモジュール領域を持たないアーキテクチャのサポートを簡略化できます。

CONFIG_KASAN_KUNIT_TEST および CONFIG_KASAN_MODULE_TEST¶

KASANのテストは2つの部分から構成されています：

1. KUnitテストフレームワークと統合されたテスト。有効化には CONFIG_KASAN_KUNIT_TEST。これらのテストは、いくつかの異なる方法で自動的に実行および部分的に検証できます。以下の指示を参照してください。

2. 現在KUnitと互換性がないテスト。有効化には CONFIG_KASAN_MODULE_TEST とし、モジュールとしてのみ実行できます。これらのテストは、カーネルモジュールをロードし、カーネルログでKASANレポートを確認することで手動で検証する必要があります。

各KUnit互換のKASANテストは、エラーが検出された場合にKASANレポートを出力します。その後、テストはその番号とステータスを出力します。

テストが成功した場合：

ok 28 - kmalloc_double_kzfree

not ok 4 - kmalloc_large_oob_right

Expected kasan_data->report_expected == kasan_data->report_found, but
kasan_data->report_expected == 1
kasan_data->report_found == 0
not ok 28 - kmalloc_double_kzfree

最後に、すべてのKASANテストの累積ステータスが表示されます。成功した場合：

ok 1 - kasan

または、1つのテストが失敗した場合：

not ok 1 - kasan

KUnit互換のKASANテストを実行する方法はいくつかあります。

1. ロード可能なモジュール¶

With CONFIG_KUNIT 有効化され、 CONFIG_KASAN_KUNIT_TEST insmodまたはmodprobeでモジュールをロードすることで、KASANをサポートするすべてのアーキテクチャで実行できます。このモジュールは test_kasan.

2. ビルトイン¶

With CONFIG_KUNIT ビルトインで、 CONFIG_KASAN_KUNIT_TEST KASANをサポートするすべてのアーキテクチャでビルトインできます。これらのテストおよび他のすべての有効化されたKUnitテストは、late-initコールとして起動時に実行され、結果を出力します。

3. kunit_toolを使用して¶

With CONFIG_KUNIT および CONFIG_KASAN_KUNIT_TEST ビルトインの場合でも、使用可能です kunit_tool これらのテストおよび他のKUnitテストの結果をより読みやすく表示できます。これは、通過したテストのKASANレポートを出力しません。使用するには KUnitドキュメンテーション に関する最新情報については kunit_tool.

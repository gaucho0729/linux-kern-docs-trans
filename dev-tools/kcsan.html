The Kernel Concurrency Sanitizer (KCSAN)¶

Kernel Concurrency Sanitizer (KCSAN) は、コンパイル時のインストルメンテーションに依存し、ウォッチポイントベースのサンプリングアプローチを用いてレースを検出する動的レース検出ツールです。KCSAN の主な目的は、 data races.

使い方¶

KCSAN は GCC および Clang の両方でサポートされています。GCC ではバージョン 11 以降、Clang でもバージョン 11 以降が必要です。

KCSAN を有効にするには、カーネルを以下の設定で構築してください:

CONFIG_KCSAN = y

KCSAN は、動作をカスタマイズするための他の設定オプションを提供しています（詳細は、関連するヘルプテキストを参照してください） lib/Kconfig.kcsan 詳しくは、以下を参照してください。

選択的な分析¶

特定のアクセス、関数、コンパイルユニット、または全体のサブシステムに対してデータレース検出を無効にするのは望ましい場合があります。静的ブラックリスト化については、以下のオプションが利用可能です:

  • KCSAN は、 data_race(expr) アノテーションを理解しており、これは KCSAN に、 expr アクセスによって発生するデータレースは無視され、データレースが発生した場合の結果が安全であるとみなされます。

  • 全体の関数に対してデータレース検出を無効にするには、関数属性 __no_kcsan:

    __no_kcsan
void foo(void) {
    ...

    動的にレポートを生成する関数を制限するには、 DebugFS インターフェース ブラックリスト/ホワイトリスト機能。

  • 特定のコンパイルユニットに対してデータレース検出を無効にするには、 Makefile:

    KCSAN_SANITIZE_file.o := n

  • 特定のコンパイルユニットリスト内のすべてのコンパイルユニットに対してデータレース検出を無効にするには、 Makefile、それぞれの Makefile:

    KCSAN_SANITIZE := n

さらに、KCSAN にデータレースのクラス全体を表示または非表示にするように指示することも可能です（好みに応じて）。これらは以下の Kconfig オプションを通じて変更できます:

  • CONFIG_KCSAN_REPORT_VALUE_CHANGE_ONLY：有効化されている場合、ウォッチポイントを通じて競合する書き込みが観測されたが、メモリ場所のデータ値が変化しなかった場合は、データレースをレポートしない。

  • CONFIG_KCSAN_ASSUME_PLAIN_WRITES_ATOMIC平らにアライメントされたワードサイズまでの書き込みがデフォルトでアトミックであると仮定します。このような書き込みがデータレースを引き起こす不安全なコンパイラ最適化の影響を受けないものと仮定します。このオプションにより、KCSANは、単に平らなアクセスのみが行われる場合の競合をレポートしません。

DebugFS インターフェース¶

ファイル /sys/kernel/debug/kcsan 以下のインターフェースを提供します:

  • 読み込み /sys/kernel/debug/kcsan さまざまなランタイム統計情報を返します。

  • 書き込み on または off に（木の下から葉に向かって） /sys/kernel/debug/kcsan KCSANを有効にするか無効にすることができます。

  • 書き込み !some_func_name に（木の下から葉に向かって） /sys/kernel/debug/kcsan リストに追加します some_func_name レポートフィルタリストに追加し、(デフォルトでは)リスト内の関数がスタックフレームのいずれかである場合のデータレースのレポートをブラックリストにします。

  • どちらか一方を書き込むと blacklist または whitelist に（木の下から葉に向かって） /sys/kernel/debug/kcsan レポートフィルタリングの挙動を変更します。たとえば、ブラックリスト機能は頻繁に発生するデータレースを静音化し、ホワイトリスト機能は修正の再現とテストに役立ちます。

パフォーマンスの調整¶

KCSANの全体的なパフォーマンスとバグ検出能力に影響を与えるコアパラメータは、カーネルコマンドライン引数として公開されており、対応するKconfigオプションを通じてデフォルト値を変更することもできます。

  • kcsan.skip_watch (CONFIG_KCSAN_SKIP_WATCH): 各CPUごとのメモリ操作をスキップする数。ウォッチポイントをより頻繁に設定することで、レースが観測される可能性が高まります。このパラメータは全体的なシステムパフォーマンスとレース検出能力に最も大きな影響を与えます。

  • kcsan.udelay_task (CONFIG_KCSAN_UDELAY_TASK): タスクの場合、ウォッチポイントが設定された後に実行を停止するマイクロ秒単位の遅延。値が大きいほど、レースを観測する窓のサイズが増加します。

  • kcsan.udelay_interrupt (CONFIG_KCSAN_UDELAY_INTERRUPT): インターナルの場合、ウォッチポイントが設定された後に実行を停止するマイクロ秒単位の遅延。インターナルにはより厳しいレイテンシ要件があり、タスク用に選ばれた遅延よりも一般的に小さい値を選択する必要があります。

実行時に、これらはを介して調整される可能性があります。 /sys/module/kcsan/parameters/.

データレース¶

実行中に、2つのメモリアクセスがデータレースを形成します。 データレース 彼らが競合する場合、 競合する、彼らは異なるスレッドで同時に発生し、少なくとも1つはplain accessです； plain access、彼らは 競合する 両方が同じメモリ位置にアクセスし、少なくとも1つが書き込みである場合。より詳細な説明と定義については、 「Plain Accesses and Data Races」を参照してください。.

Linux-Kernel Memory Consistency Model (LKMM)との関係¶

LKMMは、さまざまなメモリ操作の伝播と順序付けのルールを定義し、開発者に並行コードについて論理的に考える能力を提供します。最終的には、並行コードの可能な実行を特定し、そのコードがデータレースから解放されているかを判断するのに役立ちます。

KCSANは、 マーキングされたアトミック操作 (READ_ONCE, WRITE_ONCE, atomic_*など), ただし順序保証を考慮せず、メモリバリアが正しく配置されていると想定しています。言い換えれば、KCSANは、単純なアクセスが他の競合するアクセスと競合していると観測されない限り、メモリ操作が正しく順序付けられていると想定しています。

これは、KCSANが 潜在的な データ競合を、メモリ順序の不足により報告しないことを意味します。開発者は、未検出のメモリ順序の要件を慎重に検討する必要があります。ただし、特定のコンパイラとアーキテクチャで観測可能なメモリ順序の不足が、観測可能なデータ競合（例: クリティカルセクションに誤って進入するなど）を引き起こす場合、KCSANはその結果生じたデータ競合を報告します。

データレースを超えたレース検出¶

複雑な並行処理設計を持つコードでは、競争条件のバグが常にデータ競合として現れるとは限りません。競争条件は、並行して実行される操作が予期せぬシステム挙動を引き起こす場合に発生します。一方、データ競合はC言語レベルで定義されています。以下のマクロは、バグがデータ競合として現れない場合の並行コードのプロパティを検証するために使用できます。

ASSERT_EXCLUSIVE_WRITER¶

ASSERT_EXCLUSIVE_WRITER (var)

assert no concurrent writes to var

パラメータ

var

assertする変数

説明

が同時に書き込まれていないことをアサートします。 var; 他の読み込みは許容されます。このアサーションは、通常のデータ競合として検出できない並行コードのプロパティを指定するために使用できます。

たとえば、単一のライターしか存在しないが、複数の並行読み込みがある場合、データ競合を避けるためにはすべてのアクセスをマークする必要があります。ただし、マークされたため、それらの並行アクセスはもはやデータ競合とみなされません。このようなケースでは、以下のマクロを使用できます:

void writer(void) {
        spin_lock(&update_foo_lock);
        ASSERT_EXCLUSIVE_WRITER(shared_foo);
        WRITE_ONCE(shared_foo, ...);
        spin_unlock(&update_foo_lock);
}
void reader(void) {
        // update_foo_lock does not need to be held!
        ... = READ_ONCE(shared_foo);
}

注意

ASSERT_EXCLUSIVE_WRITER_SCOPED(), 必要に応じて、どのスコープでもないはずの同時書き込みが存在しない明確なスコープがあれば、より詳細なチェックを行います。

void writer(void) {

                ...

void buggy(void) {
        if (READ_ONCE(shared_foo) == 42)
                WRITE_ONCE(shared_foo, 1); // bug!
}

実装の詳細¶

KCSANは、2つのアクセスが同時に発生することを観測することに依存しています。重要なのは、(a)レース（特にまれにしか発生しないレース）を観測する機会を増やすこと、および(b)実際にそれらを観測できるようにすることです。この(a)はさまざまな遅延を挿入することで達成でき、(b)はアドレスウォッチポイント（またはブレイクポイント）を使用することで実現できます。

メモリアクセスを意図的にストールし、そのアドレスのウォッチポイントが設定されている状態で、ウォッチポイントが発火することを観測すると、同じアドレスへの2つのアクセスはレースを起こしたと判断できます。ハードウェアウォッチポイントを使用したこのアプローチは、 DataColliderで採用されています。DataColliderとは異なり、KCSANはハードウェアウォッチポイントを使用せず、代わりにコンパイラのインストルメンテーションと「ソフトウォッチポイント」に依存しています。

KCSANでは、ウォッチポイントはアクセスタイプ、サイズ、アドレスをlong型で効率的に符号化して実装しています。ソフトウォッチポイントを使用するメリットは移植性と柔軟性です。KCSANはコンパイラが通常のアクセスをインストルメンテーションするのを依頼し、各インストルメンテーションされた通常アクセスに対して以下の処理を行います。

  1. 一致するウォッチポイントが存在するか確認します。存在し、かつ少なくとも1つのアクセスが書き込みである場合、レースを検出しました。

  2. 定期的に、一致するウォッチポイントが存在しない場合、ウォッチポイントを設定し、短いランダムな遅延をかけてストールします。

  3. 遅延前のデータ値を確認し、遅延後のデータ値を再確認します。値が不一致である場合、原因不明のレースを推測します。

通常のアクセスとマーキングされたアクセス間のデータレースを検出するため、KCSANはマーキングされたアクセスにも注釈を追加しますが、ウォッチポイントの存在を確認するためだけです。つまり、KCSANはマーキングされたアクセスに対してウォッチポイントを設定しません。マーキングされた操作に対してウォッチポイントを設定しない限り、変数が同時にアクセスされる場合でもすべてのアクセスが適切にマーキングされている場合、KCSANはウォッチポイントをトリガーせず、アクセスをレポートしません。

主要な特性¶

  1. メモリのオーバーヘッド: 全体のメモリオーバーヘッドは設定に応じて数MB程度です。現在の実装ではウォッチポイント情報を符号化するための小さなlong型配列を使用しており、これは無視できるほどです。

  2. パフォーマンスのオーバーヘッド: KCSANの実行時間は最小限に抑えられ、高速パスで共有ロックを取得せずに効率的なウォッチポイント符号化を使用しています。8コアのシステムでのカーネル起動において:

    • デフォルトのKCSAN設定では5.0倍の遅延;

    • 高速パスのオーバーヘッドのみで2.8倍の遅延（非常に大きい KCSAN_SKIP_WATCH を設定し、解除 KCSAN_SKIP_WATCH_RANDOMIZE).

  3. アノテーションのオーバーヘッド: KCSAN実行時以外では最小限のアノテーションが必要です。結果として、カーネルの進化に伴うメンテナンスオーバーヘッドも最小限です。

  4. デバイスからのレース条件の書き込みを検出: ウォッチポイントの設定時にデータ値をチェックするため、デバイスからのレース条件の書き込みも検出可能です。

  5. メモリ順序: KCSANは ではありません LKMMの順序ルールを明示的に認識しており、これによりデータレースの検出が漏れ（偽陰性）になる可能性があります。

  6. 分析の正確性: 観測された実行に対して、サンプリング戦略を使用するため、分析は 不正確 （偽陰性の可能性あり）、ただし完全性を追求しています（偽陽性はなし）。

検討された代替案¶

カーネル用の代替データレース検出アプローチは以下の カーネルスレッドサニタイザー（KTSAN）にあります。KTSANはハッピントーバイフォアデータレース検出器であり、メモリ操作間のハッピントーバイフォア順序を明示的に確立します。これにより、LKMMで定義されたデータレースを検出できます。 データレース.

正しいハッピントーバイフォア関係を構築するため、KTSANはLKMMのすべての順序ルールと同期プリミティブを把握する必要があります。残念ながら、どの要素も欠けていた場合、多数の偽陽性が発生します。これは、多数のカスタム同期メカニズムを含むカーネルの文脈では特に深刻です。ハッピントーバイフォア関係を追跡するため、KTSANの実装は各メモリ場所（シャドウメモリ）にメタデータを必要とし、各ページに対して4ページのシャドウメモリに対応し、大規模なシステムでは数十ギガバイトのオーバーヘッドになる可能性があります。

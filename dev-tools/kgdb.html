Using kgdb, kdb and the kernel debugger internals¶

著者

Jason Wessel

はじめに¶

カーネルには、kdbとkgdbという2つの異なるデバッガーのフロントエンドがあり、これらはデバッグコアとインターフェースします。カーネルを適切にコンパイルおよび実行時設定することで、どちらかのデバッガーを用いたり、動的に切り替えることができます。

kdbはキーボードまたはシリアルコンソールで使用できるシンプルなシェルスタイルのインターフェースです。メモリやレジスタ、プロセスリスト、dmesg、さらには特定の場所で停止するためのブレイクポイントの設定が可能です。kdbはソースレベルデバッガーではありませんが、ブレイクポイントの設定や基本的なカーネル実行制御が可能です。kdbは主に開発支援やカーネル問題の診断に使用されるツールです。カーネルビルトインやカーネルモジュールでコードがビルドされた場合、一部のシンボルを名前で参照することが可能です。 CONFIG_KALLSYMS.

kgdbはLinuxカーネルのソースレベルデバッガーとして設計されています。kgdbはgdbと併用してカーネルのデバッグに使用されます。gdbを用いてカーネルに「ブレイクイン」し、メモリや変数を確認し、呼び出しスタック情報をアプリケーション開発者がアプリケーションをデバッグするようにするのと同様に確認できることが期待されます。カーネルコードにブレイクポイントを設定し、一部の制限付きの実行ステップを実行することが可能です。

kgdbを使用するには2台のマシンが必要です。そのうち1台は開発マシン、もう1台はターゲットマシンです。デバッグされるカーネルはターゲットマシン上で動作します。開発マシンではvmlinuxファイル（シンボルを含むファイル、bzImageやzImage、uImageなどのブートイメージではなく）に対してgdbのインスタンスを実行します。gdbでは開発者が接続パラメータを指定し、kgdbに接続します。開発者がgdbで使用する接続タイプは、kgdb I/Oモジュールがテストマシンのカーネルでコンパイルされたビルトインかロード可能なモジュールとして利用可能かどうかに依存します。

カーネルデバッガーのブート引数¶

このセクションでは、カーネルデバッガーの構成に影響を与えるさまざまなランタイムカーネルパラメータについて説明します。次の章では、kdbとkgdbの使用方法と、構成パラメータの例をいくつか紹介します。

カーネルパラメータ: kgdboc¶

kgdbocドライバはもともと「kgdb over console（コンソールを介したkgdb）」という略称でしたが、現在ではgdbとkgdbの通信方法を設定する主要なメカニズムであり、kdbシェルとやり取りするためのデバイスを指定する方法でもあります。

kgdb/gdbではkgdbocは単一のシリアルポートで動作設計されています。シリアルコンソールを主なコンソールとして使用し、かつカーネルデバッグにも利用する場合に使用することを意図しています。また、システムコンソールとして指定されていないシリアルポートでもkgdbを用いることが可能です。kgdbocはカーネルのビルトインまたはロード可能なモジュールとして構成可能です。kgdbocを有効にするには kgdbwait kgdbocをカーネルのビルトインとして構築する必要があります。

オプションでKMS（Kernel Mode Setting）統合を有効化できます。KMSとkgdbocを併用し、アトミックモード設定フックを持つビデオドライバを使用している場合、グラフィックコンソール上でデバッガーに移行することが可能です。カーネルの実行が再開されると、以前のグラフィックモードが復元されます。この統合は、kdbを使用してクラッシュの診断やメモリの分析を行う際に、フルグラフィックコンソールアプリケーションを実行できる有用なツールとして機能します。

kgdboc引数¶

使用方法:

kgdboc=[kms][[,]kbd][[,]serial_device][,baud]

オプションの構成を併用する場合、上記の順序を厳守する必要があります。

略称:

  • kms = Kernel Mode Setting

  • kbd = Keyboard

kdbおよび/またはkgdbを使用する場合、以下のシナリオのいずれかでkgdbocをキーボードおよび/またはシリアルデバイスを使用して構成できます。オプションの構成を併用する場合、上記の順序を厳守する必要があります。KMS＋のみgdbを使用する組み合わせは一般的に有用ではありません。

ロード可能なモジュールまたはビルトインを使用する¶

  1. カーネルのビルトインとして:

    カーネル起動引数を使用:

    kgdboc=<tty-device>,[baud]

  2. カーネルロード可能なモジュールとして:

    コマンドを使用:

    modprobe kgdboc kgdboc=<tty-device>,[baud]

    kgdboc文字列のフォーマット例を以下に示します。1つ目はx86ターゲットで最初のシリアルポートを使用する例、2つ目はARM Versatile ABで2番目のシリアルポートを使用する例です。

    1. kgdboc=ttyS0,115200

    2. kgdboc=ttyAMA1,115200

sysfs経由でkgdbocをランタイムで構成する¶

ランタイムでkgdbocを有効化または無効化するには、sysfsにパラメータをエコーバックします。以下に例を示します:

  1. ttyS0でkgdbocを有効化:

    echo ttyS0 > /sys/module/kgdboc/parameters/kgdboc

  2. kgdbocを無効化:

    echo "" > /sys/module/kgdboc/parameters/kgdboc

注意

ttyがすでに構成またはオープンされている場合、ボーレートを指定する必要はありません。

さらに多くの例¶

kdbおよび/またはkgdbを使用する場合、以下のシナリオのいずれかでkgdbocをキーボードおよび/またはシリアルデバイスを使用して構成できます。

  1. シリアルポートのみを介してkdbとkgdb:

    kgdboc=<serial_device>[,baud]

    例:

    kgdboc=ttyS0,115200

  2. キーボードとシリアルポートを介してkdbとkgdb:

    kgdboc=kbd,<serial_device>[,baud]

    例:

    kgdboc=kbd,ttyS0,115200

  3. キーボードを介してkdbを用いる場合:

    kgdboc=kbd

  4. カーネルモード設定を用いる場合:

    kgdboc=kms,kbd

  5. カーネルモード設定を用い、シリアルポートを介してkgdbを用いる場合:

    kgdboc=kms,kbd,ttyS0,115200

注意

kgdbocはgdb remoteプロトコルを介したターゲットの中断をサポートしていません。手動で送信する必要があります SysRq-G コンソールプロキシがなければなりません。コンソールプロキシはデバッガー用の別個のTCPポートと"人間"コンソール用の別個のTCPポートを持ち、プロキシがコンソール出力をターミナルプログラムに送信するのを担当します。 SysRq-G あなたの代わりに送信します。

kgdbocをプロキシなしで使用する場合、デバッガーが2つのエントリポイントのいずれかに接続されることがあります。kgdbocをロードした後で例外が発生した場合、コンソールにデバッガーを待機しているというメッセージが表示されます。この場合、ターミナルプログラムを切断し、デバッガーを接続します。ターゲットシステムを中断して強制的にデバッグセッションに入る場合は、シーケンスを発行し、その後文字 Sysrq をタイプします。 gその後、ターミナルセッションを切断し、gdbを接続します。この方法が気に入らない場合は、gdbをハックして、シーケンスを自動的に送信するように設定するか、または未変更のgdbでデバッグが可能なデバッガープロキシを使用します。 SysRq-G を自動的に送信するように設定します。また、初期接続時にも送信します。

カーネルパラメータ: kgdboc_earlycon¶

カーネルパラメータ kgdboc_earlycon を指定し、シリアルドライバーがポーリングをサポートするブートコンソールを登録している場合（割り込みを必要とせず、非ブロッキングread()関数を実装している）、kgdbはブートコンソールを使用して動作を試みます。その後、通常のttyドライバーに移行します。 kgdboc パラメータで指定されたものに。

通常はブートコンソールは1つだけ（read()関数を実装している）ので、単に kgdboc_earlycon を追加するだけで動作します。ブートコンソールが複数ある場合は、ブートコンソールの名前を追加して区別します。注意点として、ブートコンソールレイヤーとttyレイヤーで登録される名前は同じポートでも異なります。

例えば、あるボードでは明示的に以下のようにします:

kgdboc_earlycon=qcom_geni kgdboc=ttyMSM0

デバイスのブートコンソールが唯一「qcom_geni」だった場合、以下のように簡略化できます:

kgdboc_earlycon kgdboc=ttyMSM0

カーネルパラメータ: kgdbwait¶

カーネルコマンドラインオプション kgdbwait は、カーネルの起動中にkgdbがデバッガー接続を待機するようにします。このオプションは、kgdb I/Oドライバをカーネルに組み込んでおり、I/Oドライバの構成をカーネルコマンドラインオプションで指定した場合にのみ使用可能です。kgdbwaitパラメータは、カーネルコマンドラインにおいてkgdb I/Oドライバの構成パラメータの直後に常に追加する必要があります。そうでなければ、I/Oドライバが構成される前にカーネルに使用を依頼してしまうため、動作しません。

このオプションを使用すると、カーネルはI/Oドライバおよびアーキテクチャが許可する限り、できるだけ早く停止して待機します。kgdb I/Oドライバをロード可能なカーネルモジュールとしてビルドした場合、kgdbwaitは何も実行しません。

カーネルパラメータ: kgdbcon¶

以下の kgdbcon 機能により、 printk() gdbがカーネルに接続されているときにgdb内でのメッセージを確認できます。Kdbはkgdbcon機能を使用しません。

kgdbは、デバッガーが接続・実行しているときに、gdbシリアルプロトコルを使用してコンソールメッセージをデバッガーに送信する機能をサポートしています。この機能を有効にする方法は2通りあります。

  1. カーネルコマンドラインオプションで有効化:

    kgdbcon

  2. I/Oドライバを構成する前にsysfsを使用:

    echo 1 > /sys/module/kgdb/parameters/kgdb_use_con

注意

kgdb I/Oドライバを構成した後でこの操作を行った場合、設定は次のI/O再構成のタイミングまで有効になりません。

重要です。

kgdboc + kgdbconは、アクティブなシステムコンソールのttyでは使用できません。誤った使用例は:

console=ttyS0,115200 kgdboc=ttyS0 kgdbcon

システムコンソールでないttyでこのオプションとkgdbocを使用することは可能です。

ランタイムパラメータ: kgdbreboot¶

kgdbreboot機能により、デバッガーが再起動通知をどのように処理するかを変更できます。動作の選択肢は3つあり、デフォルトでは常に0が設定されています。

1

echo -1 > /sys/module/debug_core/parameters/kgdbreboot

再起動通知を完全に無視する。

2

echo 0 > /sys/module/debug_core/parameters/kgdbreboot

すべての接続されたデバッガークライアントに切断メッセージを送信する。

3

echo 1 > /sys/module/debug_core/parameters/kgdbreboot

再起動通知時にデバッガーに移行する。

カーネルパラメータ: nokaslr¶

使用しているアーキテクチャでKASLRがデフォルトで有効になっている場合、無効にすることを検討してください。KASLRはカーネルイメージの仮想アドレスをランダム化し、gdbがvmlinuxのシンボルテーブルからカーネルシンボルのアドレスを解決するのを混乱させます。

kgdb / gdb の使用¶

kgdbを使用するには、kgdb I/Oドライバの1つに構成情報を渡して有効化する必要があります。構成情報を渡さない場合、kgdbはまったく動作しません。kgdb I/Oドライバがロードされ構成されている場合に限り、kgdbがカーネルのトラップハンドラにアクティブに接続します。kgdb I/Oドライバを無効化すると、kgdbがすべてのカーネルハンドルポイントを登録解除します。

すべてのkgdb I/Oドライバは、以下の条件を満たす場合、実行時にも再構成できます CONFIG_SYSFS および CONFIG_MODULES が有効化されている場合、新しい設定文字列を /sys/module/<driver>/parameter/<option>にエコーします。ドライバを無効化するには、空文字列を渡してください。デバッグが接続されている間は設定を変更できません。デバッグを解除するには、 detach コマンドでデバッガーを分離してください。

シリアルポート経由でgdbに接続する¶

  1. kgdbocを設定

    カーネルパラメータを使用して起動時にkgdbocを構成:

    kgdboc=ttyS0,115200

    または

    カーネルが起動した後でkgdbocを設定してください：

    echo ttyS0 > /sys/module/kgdboc/parameters/kgdboc

  2. カーネルの実行を停止（デバッグにブレイクイン）

    kgdboc経由でgdbに接続するには、まずカーネルを停止する必要があります。カーネルを停止する方法には、ブート引数としてkgdbwaitを使用する方法、または SysRq-G、カーネルが例外を発生させ、デバッグを接続するのを待機するまで実行を続ける方法があります。

    • rootとしてログインしているか、スーパーユーザーセッションでログインしている場合、次を実行できます:

      echo g > /proc/sysrq-trigger

    • minicom 2.2を使用した例

      押してください: CTRL-A f g

    • telnetでターミナルサーバーに接続し、リモートブレイクを送信可能な場合、

      押してください: CTRL-]

      入力してください: send break

      押してください: Enter g

  3. gdbから接続

    直接接続されたポートを使用する例：

    % gdb ./vmlinux
(gdb) set remotebaud 115200
(gdb) target remote /dev/ttyS0

    例（TCPポート2012のテルミナルサーバーにkgdbを接続）：

    % gdb ./vmlinux
(gdb) target remote 192.168.2.2:2012

    接続後、アプリケーションプログラムをデバッグするようにカーネルをデバッグできます。

    接続に問題があるか、デバッグ中に重大な問題が発生している場合、gdbがターゲット通信について詳細に情報を出力するように有効化することが最も一般的です。これを実行する前に、 target remote コマンドを入力してください：

    set debug remote 1

gdbで継続して実行している場合、再度「ブレイクイン」する必要がある場合は、別の SysRq-Gを実行してください。ブレイクポイントを設定することで、簡単なエントリポイントを作成できます sys_sync に設定し、その後実行を開始してください。 sync シェルまたはスクリプトからデバッグモードに入るための方法です。

kgdb と kdb の相互運用性¶

kdbとkgdbの間で動的に切り替えることができます。デバッグコアは最後に使用したモードを記憶し、自動的に同じモードで起動します。

kdbとkgdbの切り替え¶

kgdbからkdbへの切り替え¶

kgdbからkdbへの切り替えには2つの方法があります。gdbを使用してメンテナンスパケットを送信するか、盲打でコマンドを入力するかです。 $3#33kgdbモードでカーネルデバッガーが停止すると、メッセージが表示されます。 KGDB or $3#33 for KDB重要ですが、正しい順序で一度に入力する必要があります。バックスペースや削除キーを入力することはできません。kgdbはそれらをデバッグストリームの一部として解釈します。

  1. 盲打で入力してkgdbからkdbに切り替えます:

    $3#33

  2. gdbを使用してkgdbからkdbに切り替えます:

    maintenance packet 3

    注意

    今すぐgdbを終了する必要があります。通常は CTRL-Z を押して、コマンドを実行します:

    kill -9 %

kdbからkgdbへの切り替え¶

kdbからkgdbへの切り替えには2つの方法があります。kdbシェルプロンプトからkgdbコマンドを実行して手動でkgdbモードに移行するか、kdbシェルプロンプトがアクティブなときにgdbを接続するかです。kdbシェルはgdbリモートプロトコルで通常最初に実行されるコマンドを検出し、そのコマンドを確認すると自動的にkgdbモードに切り替わります。

  1. kdbプロンプトからコマンドを実行します:

    kgdb

    今すぐターミナルプログラムを切断し、gdbに接続します

  2. kdbプロンプトでターミナルプログラムを切断し、gdbに接続します。

gdbからkdbコマンドを実行する¶

gdbモニタコマンドを使用して、限定されたkdbコマンドを実行できます。ランタイム制御やブレイクポイント操作は実行しないでください。それらはカーネルデバッガーの状態を妨げる可能性があります。gdbが接続されている場合は、ブレイクポイントやランタイム制御操作にはgdbを使用してください。より役に立つコマンドはlsmod、dmesg、ps、またはメモリ情報コマンドの一部かもしれません。すべての実行可能なkdbコマンドを確認するには monitor help.

kgdb テストスイート¶

カーネルコンフィギュレーションでkgdbが有効になっている場合、コンフィギュレーションパラメータを有効化することもできます KGDB_TESTS。この設定を有効にすると、kgdb内部関数をテストするための特別なkgdb I/Oモジュールが有効になります。

kgdbテストは主に開発者向けに設計されており、kgdb内部のテストや、新しいkgdbアーキテクチャ固有の実装を開発するためのツールとしても使用されます。これらはLinuxカーネルの一般ユーザーにはあまり適していません。主なドキュメンテーションは以下の場所を確認してください drivers/misc/kgdbts.c ファイル。

kgdbテストスイートは、コンパイル時にカーネルコンフィギュレーションパラメータを設定して、コアセットのテストを実行するように構成することもできます KGDB_TESTS_ON_BOOT. このオプションは自動化されたリグレッションテストを目的としており、カーネルのブート構成引数を変更する必要はありません。このオプションが有効になると、kgdbテストスイートは指定することで無効化できます kgdbts= カーネルのブート引数として。

カーネルデバッガーの内部構造¶

アーキテクチャ固有の仕様¶

カーネルデバッガーはいくつかのコンポーネントに分かれています:

  1. デバッグコア

    デバッグコアは kernel/debugger/debug_core.c. これは以下の要素を含みます:

    • 汎用的なOS例外ハンドラで、マルチCPUシステムにおいてプロセッサを停止状態に同期する機能を含みます。

    • kgdb I/Oドライバと通信するためのAPI

    • アーキテクチャ固有のkgdb実装に呼び出しを行うためのAPI

    • デバッガーを使用しながらメモリに安全な読み書きを行うロジック

    • アーキテクチャによって上書きされない限り、ソフトウェアブレイクポイントの完全な実装

    • kdbまたはkgdbフロントエンドをデバッグコアに呼び出すためのAPI

    • アトミックなカーネルモード設定用の構造体とコールバックAPI

      注意

      kgdbocはKMSコールバックが呼び出される場所です。

  2. kgdbのアーキテクチャ固有の実装

    この実装は通常 arch/*/kernel/kgdb.c. 例として、 arch/x86/kernel/kgdb.c は、このアーキテクチャにおけるHWブレイクポイントの実装 specifics およびトラップハンドラの動的登録・解除の初期化を含みます。アーキテクチャ固有の部分は以下の機能を実装します:

    • は、アーキテクチャ固有のトラップキャッチャーを含み、kgdb_handle_exception()を呼び出してkgdbの作業を開始します

    • gdb固有のパケット形式とstruct pt_regsの間の翻訳

    • アーキテクチャ固有のトラップハンドルの登録と解除

    • 特別な例外処理とクリーンアップ

    • NMI例外処理とクリーンアップ

    • (オプション) HWブレイクポイント

  3. gdbstubフロントエンド (別名kgdb)

    gdbstubは kernel/debug/gdbstub.c. これは以下の要素を含みます:

    • gdbシリアルプロトコルを実装するためのすべてのロジック

  4. kdbフロントエンド

    kdbデバッガーシェルはいくつかのコンポーネントに分かれています。kdbコアはkernel/debug/kdbに位置しています。他のカーネルコンポーネントには、ロックを取得することなくカーネルの情報を検査・報告できるようにするヘルパーファンクションが含まれています。kdbコアは以下の機能を実装しています。

    • シンプルなシェル

    • kdbコアコマンドセット

    • 追加のkdbシェルコマンドを登録するための登録API

      • self-containedなkdbモジュールの良い例は ftdump ftraceバッファのダンプコマンドです。参照: kernel/trace/trace_kdb.c

      • 動的登録を行う新しいkdbコマンドの例として、kdb_hello.koカーネルモジュールを構築できます samples/kdb/kdb_hello.c. この例を構築するには、 CONFIG_SAMPLES=y および CONFIG_SAMPLE_KDB=m カーネル構成に設定してください。後で実行してください modprobe kdb_hello kdbシェルに入ると、次のコマンドを実行できます hello Sometimes

    • kdb_printf()の実装は、メッセージを直接I/Oドライバに送信し、カーネルログを迂回します。

    • kdbシェルにおけるSW/ハードウェアブレイクポイント管理

  5. kgdb I/Oドライバ

    各kgdb I/Oドライバは、以下の実装を提供しなければなりません。

    • 組み込みまたはモジュールによる設定

    • 動的設定およびkgdbハックの登録呼び出し

    • 読み込みおよび書き込みキャラクタインターフェース

    • kgdbコアから解除する際のクリーンアップハンドラ

    • (オプション) 早期デバッグメソッド

    kgdb I/Oドライバはハードウェアと非常に密接に協働する必要があります。システムコンテキストを完全に復元せずに割込みを有効化したり、他のシステムコンテキストを変更したりしてはなりません。kgdbコアは入力が必要なときにkgdb I/Oドライバを繰り返し「ポーリング」します。データが利用できない場合、I/Oドライバはすぐに返す必要があります。これにより、今後、ウォッチドッグハードウェアを操作してターゲットシステムがリセットされない状態で実行できる可能性があります。

新しいアーキテクチャにkgdbアーキテクチャ固有のサポートを追加する場合、アーキテクチャは HAVE_ARCH_KGDB アーキテクチャ固有のKconfigファイルで定義する必要があります。これにより、アーキテクチャにkgdbが有効になり、その時点でアーキテクチャ固有のkgdb実装を作成しなければなりません。

すべてのアーキテクチャで設定する必要があるフラグがあります。これらは、 asm/kgdb.h ファイル。

  • NUMREGBYTES:

    すべてのレジスタのバイト数を設定し、これらがすべてパケットに収まるようにする必要があります。

  • BUFMAX:

    GDBが読み込むバッファのバイト数。これはNUMREGBYTESよりも大きくなければなりません。

  • CACHE_FLUSH_IS_SAFE:

    flush_cache_rangeまたはflush_icache_rangeを呼び出すことが常に安全である場合、1に設定します。一部のアーキテクチャでは、SMPでこれらの関数を呼び出すことが安全でない場合があります。

共有バックエンドに必要な以下の関数があります。これらは、 kernel/kgdb.cで定義されており、アーキテクチャ固有のバックエンドで提供する必要があります。ただし、(オプション)としてマークされている場合は、アーキテクチャが特定の実装を提供しなくてもデフォルト関数を使用できます。

kgdbocの内部構造¶

kgdbocとUART¶

kgdbocドライバは実際には非常に薄いドライバであり、ハードウェアドライバの下層にある「ポーリングハンドル」にttyドライバが接続されていることを前提としている。kgdbocの初期実装では、シリアルコアがポーリングモードでの1文字の読み書きを行うための低レベルUARTハンドルを公開するように変更され、kgdbがデバッグ機器にI/Oリクエストを送信する際、kgdbocはシリアルコア内のコールバックを呼び出し、そのコールバックはUARTドライバ内のコールバックを使用する。

kgdbocをUARTで使用する場合、UARTドライバはstruct uart_ops内の2つのコールバックを実装しなければならない。例は drivers/8250.c:

#ifdef CONFIG_CONSOLE_POLL
    .poll_get_char = serial8250_get_poll_char,
    .poll_put_char = serial8250_put_poll_char,
#endif

ポーリングドライバの作成に関する実装詳細は、 #ifdef CONFIG_CONSOLE_POLL、上記のように示されている。ポーリングハンドルはアトミックコンテキストから呼び出される必要があり、返却時にUARTチップの状態を復元する必要があるため、システムがデバッグ機器から接続を解除したときに正常に戻るよう確保しなければならない。ロックに関する考慮は非常に慎重に行う必要があり、ここでの失敗はリセットボタンを押す可能性が高い。

kgdbocとキーボード¶

kgdbocドライバは、接続されたキーボードとの通信設定を行うロジックを含んでいる。キーボードインフラストラクチャは、 CONFIG_KDB_KEYBOARD=y がカーネル構成に設定されているときにのみカーネルにコンパイルされる。

PS/2タイプのキーボード用のポーリング中心のキーボードドライバは、 drivers/char/kdb_keyboard.cに存在する。このドライバはkgdbocが配列内のコールバックを埋め込むときにデバッグコアに接続される。 kdb_poll_funcs[]。kdb_get_kbd_char()は、ハードウェアから単一の文字入力をポーリングするトップレベルの関数です。

kgdbocとKMS¶

kgdbocドライバは、使用時にグラフィックディスプレイがテキストコンテキストに切り替わるようリクエストするロジックを含んでいる。ただし、これはビデオドライバがフレームバッファコンソールとアトミックカーネルモード設定をサポートしている場合に限る。 kgdboc=kms,kbdを提供する

カーネルデバッガーが入力されるたびに、kgdboc_pre_exp_handler()が呼び出され、これは仮想コンソールレイヤー内のcon_debug_enter()を呼び出します。カーネルの実行を再開する際には、カーネルデバッガーがkgdb、post_exp_handler()を呼び出し、これはcon_debug_leave()を呼び出します。

カーネルデバッガーおよびアトミックKMSコールバックと互換性があるビデオドライバーは、 mode_set_base_atomic, fb_debug_enter および fb_debug_leave operationsを実装しなければなりません。For the fb_debug_enter および fb_debug_leave ハードウェア用にカスタムの実装を行うか、ジェネリックなDRM fbヘルパ関数を使用するという選択肢があります。以下の例は、drivers/gpu/drm/i915/intel_display.c における .mode_set_base_atomic 操作の初期化を示しています。

static const struct drm_crtc_helper_funcs intel_helper_funcs = {
[...]
        .mode_set_base_atomic = intel_pipe_set_base_atomic,
[...]
};

i915ドライバーがジェネリックなDRMヘルパ関数を使用して fb_debug_enter および fb_debug_leave 関数を初期化する方法の例です。 drivers/gpu/drm/i915/intel_fb.c:

static struct fb_ops intelfb_ops = {
[...]
       .fb_debug_enter = drm_fb_helper_debug_enter,
       .fb_debug_leave = drm_fb_helper_debug_leave,
[...]
};

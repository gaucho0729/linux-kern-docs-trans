Linux Kernel Selftests¶

カーネルにはtools/testing/selftests/ディレクトリに「自己テスト」としてのセットが含まれています。これはカーネル内の個々のコードパスをテストするための小さなテストを目的としています。テストはカーネルをビルド、インストール、起動した後に実行することを意図しています。

Kselftest フレームワークに関する追加情報や、フレームワークを使用した新しいテストの作成方法については、Kselftest ウィキをご覧ください:

https://kselftest.wiki.kernel.org/

一部のシステムでは、ホットプラグテストがCPUとメモリがオフラインになる準備ができたのを待っているうちに永遠に停止する可能性があります。すべてのホットプラグテストを実行するための特別なホットプラグターゲットが作成されています。デフォルトモードではホットプラグテストは安全モードで実行され、スコープは制限されています。制限モードではCPUホットプラグテストはすべてのホットプラグ可能なCPUではなく、単一のCPUで実行され、メモリホットプラグテストは10%ではなく2%のホットプラグ可能なメモリで実行されます。

kselftest はユーザー空間プロセスとして実行されます。ユーザー空間で実行可能なテストは、 テストハルネスカーネル空間で実行が必要なテストは、 テストモジュール.

selftests の実行（hotplug テストは制限されたモードで実行されます）¶

テストをビルドするには:

$ make -C tools/testing/selftests

テストを実行するには:

$ make -C tools/testing/selftests run_tests

テストを1つのコマンドでビルドして実行するには:

$ make kselftest

一部のテストはroot権限が必要です。

Kselftestは出力ファイルを別のディレクトリに保存してテストを実行することをサポートしています。出力ファイルを別のディレクトリに配置するには2つの構文がサポートされています。どちらの場合も作業ディレクトリはカーネルソースのルートである必要があります。これは以下の「自己テストのサブセットを実行する」セクションにも適用されます。

テストをビルドし、出力ファイルを別のディレクトリに保存するにはO=

$ make O=/tmp/kselftest kselftest

テストをビルドし、出力ファイルを別のディレクトリに保存するにはKBUILD_OUTPUT

$ export KBUILD_OUTPUT=/tmp/kselftest; make kselftest

O=の割当はKBUILD_OUTPUT環境変数よりも優先されます。

上記のコマンドはデフォルトでテストを実行し、完全なパス/失敗レポートを出力します。Kselftestはテスト結果を理解しやすくするため「サマリー」オプションをサポートしています。サマリーオプションを指定した場合、個々のテスト結果は/tmp/testnameファイルに保存されます。これは以下の「自己テストのサブセットを実行する」セクションにも適用されます。

サマリーオプションを有効にしてkselftestを実行するには

$ make summary=1 kselftest

selftests のサブセットの実行¶

makeコマンドラインにTARGETS変数を使用して実行するテストを指定したり、実行するテストの一覧を指定したりできます。

単一のサブシステムに特化したテストのみを実行するには:

$ make -C tools/testing/selftests TARGETS=ptrace run_tests

複数のテストをビルドして実行するには:

$  make TARGETS="size timers" kselftest

テストをビルドし、出力ファイルを別のディレクトリに保存するにはO=

$ make O=/tmp/kselftest TARGETS="size timers" kselftest

テストをビルドし、出力ファイルを別のディレクトリに保存するにはKBUILD_OUTPUT

$ export KBUILD_OUTPUT=/tmp/kselftest; make TARGETS="size timers" kselftest

さらにmakeコマンドラインにSKIP_TARGETS変数を使用して、TARGETSリストから除外する1つ以上のターゲットを指定できます。

すべてのテストを実行するが、単一のサブシステムを除くには:

$ make -C tools/testing/selftests SKIP_TARGETS=ptrace run_tests

複数のテストをスキップするには、指定できます:

$  make SKIP_TARGETS="size timers" kselftest

また、実行するテストの制限されたリストを指定し、専用のスキップリストを一緒に指定することもできます:

$  make TARGETS="bpf breakpoints size timers" SKIP_TARGETS=bpf kselftest

すべての可能なターゲットの一覧は、トップレベルの tools/testing/selftests/Makefile を参照してください。

フルレンジ hotplug selftests の実行¶

ホットプラグテストをビルドするには:

$ make -C tools/testing/selftests hotplug

ホットプラグテストを実行するには:

$ make -C tools/testing/selftests run_hotplug

一部のテストはroot権限が必要です。

selftests のインストール¶

「make」の「install」ターゲット（これは kselftest_install.sh ツールを呼び出します）を使用して、selftests をデフォルトの場所（tools/testing/selftests/kselftest_install）にインストールできます。または、 INSTALL_PATH 「make」変数を介してユーザー指定の場所にインストールすることもできます。

デフォルトの場所に selftests をインストールするには:

$ make -C tools/testing/selftests install

ユーザー指定の場所に selftests をインストールするには:

$ make -C tools/testing/selftests install INSTALL_PATH=/some/other/path

インストール済み selftests の実行¶

インストールディレクトリおよび Kselftest tarball には、テストを実行するためのスクリプト run_kselftest.sh が含まれています。

インストールされた Kselftests を実行するには、以下の手順を実行できます。ただし、一部のテストは root 権限が必要です:

$ cd kselftest_install
$ ./run_kselftest.sh

利用可能なテストの一覧を確認するには、 -l オプションを使用できます:

$ ./run_kselftest.sh -l

以下の -c オプションを使用して、テストコレクションからすべてのテストを実行するか、 -t オプションで特定の単一テストを実行できます。どちらも複数回使用できます:

$ ./run_kselftest.sh -c bpf -c seccomp -t timers:posix_timers -t timer:nanosleep

その他の機能については、スクリプトの使用法出力を確認してください。これは -h オプションの下に隠されています。

selftests のパッケージング¶

で確認できます。

$ make -C tools/testing/selftests gen_tar

テストが別のシステムで実行する必要があるなどの場合、パッケージ化が望まれます。selftests をパッケージ化するには、以下を実行してください: これにより、 INSTALL_PATH/kselftest-packages ディレクトリに tar ボールが生成されます。デフォルトでは、 .gz 形式が使用されます。tar の圧縮形式を上書きするには、 FORMAT make 変数を指定してください。tar の auto-compress オプションで認識される任意の値がサポートされています。たとえば: make gen_tar

$ make -C tools/testing/selftests gen_tar FORMAT=.xz

make install が呼び出されます。 を使用して、変数で指定されたテストのサブセットをパッケージ化できます。 セクションで指定された変数を使用して、 selftests のサブセットの実行 セクション:

$ make -C tools/testing/selftests gen_tar TARGETS="bpf" FORMAT=.xz

新しいテストの貢献¶

一般的な selftests のルールは

  • root でない場合はできるだけ行う;

  • あまり時間をかけすぎない;

  • どのアーキテクチャでもビルドを壊さないでください、そして

  • あなたの機能が未設定の場合でも、トップレベルの「make run_tests」が失敗しないようにしてください。

新しいテストの貢献（詳細）¶

  • コンパイル中にこのようなバイナリまたはファイルが生成される場合は、TEST_GEN_XXXを使用してください。

    TEST_PROGS、TEST_GEN_PROGSは、デフォルトでテストされる実行ファイルを示します。

    カスタムビルドルールが必要なテストではTEST_CUSTOM_PROGSを使用し、一般的なビルドルールの使用を防ぐ必要があります。

    TEST_PROGSはテストシェルスクリプト用です。シェルスクリプトの実行ビットが設定されていることを確認してください。それ以外の場合、lib.mkのrun_testsは警告を生成します。

    TEST_CUSTOM_PROGSとTEST_PROGSは共通のrun_testsによって実行されます。

    TEST_PROGS_EXTENDED、TEST_GEN_PROGS_EXTENDEDはデフォルトでテストされない実行ファイルを示し、TEST_FILES、TEST_GEN_FILESはテストで使用されるファイルを示します。

  • まず、カーネルソースおよび/またはgitリポジトリ内のヘッダーファイルを使用し、その後システムヘッダーを使用してください。システムにインストールされたディストロのヘッダーではなく、カーネルリリース用のヘッダーに重点を置くことで、リグレッションを検出できます。

  • テストで特定のカーネル構成オプションを有効にする必要がある場合は、テストディレクトリに構成ファイルを追加して有効にしてください。

    例: tools/testing/selftests/android/config

テストモジュール¶

Kselftestはユーザー空間からカーネルをテストします。場合によっては、カーネル内部からテストが必要なため、テストモジュールを作成する方法があります。シェルスクリプトのテストランナーを使用して、このモジュールをkselftestフレームワークに統合できます。 kselftest/module.sh このプロセスを簡素化するように設計されています。また、kselftestと使用するカーネルモジュールの作成を支援するヘッダーファイルも提供されています:

  • tools/testing/kselftest/kselftest_module.h

  • tools/testing/kselftest/kselftest/module.sh

使い方¶

ここでは、テストモジュールを作成し、kselftestに統合する典型的な手順を示します。例としてkselftests for lib/を使用します。

  1. テストモジュールを作成する

  2. モジュールを実行（ロード/アンロード）するテストスクリプトを作成してください。例: tools/testing/selftests/lib/printf.sh

  3. 構成ファイルに行を追加してください。例: tools/testing/selftests/lib/config

  4. makefileにテストスクリプトを追加してください。例: tools/testing/selftests/lib/Makefile

  5. 動作を確認する:

# Assumes you have booted a fresh build of this kernel tree
cd /path/to/linux/tree
make kselftest-merge
make modules
sudo make modules_install
make TARGETS=lib kselftest

例: モジュール¶

シンプルなテストモジュールの例は次の通りです:

// SPDX-License-Identifier: GPL-2.0+

#define pr_fmt(fmt) KBUILD_MODNAME ": " fmt

#include "../tools/testing/selftests/kselftest/module.h"

KSTM_MODULE_GLOBALS();

/*
 * Kernel module for testing the foobinator
 */

static int __init test_function()
{
        ...
}

static void __init selftest(void)
{
        KSTM_CHECK_ZERO(do_test_case("", 0));
}

KSTM_MODULE_LOADERS(test_foo);
MODULE_AUTHOR("John Developer <jd@fooman.org>");
MODULE_LICENSE("GPL");

例: テストスクリプト¶

#!/bin/bash
# SPDX-License-Identifier: GPL-2.0+
$(dirname $0)/../kselftest/module.sh "foo" test_foo

テストハルネス¶

kselftest_harness.hファイルにはテスト作成に役立つユーティリティが含まれています。テストハーケスはユーザー空間のテスト用であり、カーネル空間のテストについては テストモジュール 上記。

tools/testing/selftests/seccomp/seccomp_bpf.cのテストは例として使用できます。

例¶

#include "../kselftest_harness.h"

TEST(standalone_test) {
  do_some_stuff;
  EXPECT_GT(10, stuff) {
     stuff_state_t state;
     enumerate_stuff_state(&state);
     TH_LOG("expectation failed with state: %s", state.msg);
  }
  more_stuff;
  ASSERT_NE(some_stuff, NULL) TH_LOG("how did it happen?!");
  last_stuff;
  EXPECT_EQ(0, last_stuff);
}

FIXTURE(my_fixture) {
  mytype_t *data;
  int awesomeness_level;
};
FIXTURE_SETUP(my_fixture) {
  self->data = mytype_new();
  ASSERT_NE(NULL, self->data);
}
FIXTURE_TEARDOWN(my_fixture) {
  mytype_free(self->data);
}
TEST_F(my_fixture, data_is_good) {
  EXPECT_EQ(1, is_my_data_good(self->data));
}

ヘルパー¶

TH_LOG¶

TH_LOG (fmt, ...)

パラメータ

fmt

フォーマット文字列

...

オプション引数

説明

TH_LOG(format, ...)

テストで使用可能なオプションのデバッグログ関数です。TH_LOG_ENABLEDを定義することでログの有効/無効を切り替えられます。例: #define TH_LOG_ENABLED 1

定義が提供されていない場合、ログはデフォルトで有効になります。

テストを実行しているプロセスでエラーメッセージを印刷する方法がない場合（例: stderrへの書き込みが許可されていない場合）、テストが失敗したASSERT_*番号を取得することは依然として可能です。この挙動は以下のコードを実行することで有効化できます。 _metadata->no_print = true; 印刷できないチェックシーケンスの前に行う必要があります。エラーが発生した場合、エラーメッセージを印刷しabort(3)を呼び出す代わりに、 abort(3)ではなく、テストプロセスが _exit(2) を呼び出します。この際、アサート番号を引数として渡し、その後親プロセスがその番号を印刷します。

TEST (test_name)

テスト関数を定義し、登録スタブを作成します

パラメータ

test_name

テスト名

説明

TEST(name) { implementation }

名前でテストを定義します。名前は一意でなければなりませんし、テストは並列で実行してはいけません。実装ブロックは関数として扱い、スコープは関数として扱うべきです。早期リターンは「return;」ステートメントで行うことができます。

EXPECT_*およびASSERT_*は TEST() { }コンテキストで有効です。

FIXTURE¶

FIXTURE (fixture_name)

各fixtureに対してデータのセットアップと登録を行うために呼び出されます。

パラメータ

fixture_name

fixture名

説明

FIXTURE(fixture_name) {
  type property1;
  ...
};

テストに提供されるデータを定義します。 TEST_F()-定義されたテストとして 自身. これは populate および clean up するために使用されます FIXTURE_SETUP() および FIXTURE_TEARDOWN().

FIXTURE_SETUP¶

FIXTURE_SETUP (fixture_name)

fixture のセットアップ関数を準備します。 _metadata EXPECT_* および ASSERT_* が正しく動作するように含まれています。

パラメータ

fixture_name

fixture名

説明

FIXTURE_SETUP(fixture_name) { implementation }

fixture の必要な「setup」関数を埋め込みます。この datatype で定義されたインスタンスは、 FIXTURE_DATA() 実装のために 自身 として公開されます。

ASSERT_* はこのコンテキストで使用可能です。関連するfixtureテストの実行を中断します。

空の「return;」ステートメントを使用して早期に戻ることができます。

FIXTURE_TEARDOWN¶

FIXTURE_TEARDOWN (fixture_name)

パラメータ

fixture_name

fixture名

説明

_metadata EXPECT_* および ASSERT_* が正しく動作するように含まれています。

FIXTURE_TEARDOWN(fixture_name) { implementation }

fixture の必要な「teardown」関数を埋め込みます。この datatype で定義されたインスタンスは、実装のために FIXTURE_DATA() 実装のために 自身 をクリーンアップするために使用されます。

空の「return;」ステートメントを使用して早期に戻ることができます。

KUnitの使用方法¶

このドキュメントの目的は、KUnitとは何か、どのように動作するのか、どのように使用すべきか、そしてKUnitを理解するために必要な概念や用語について説明することです。このガイドではLinuxカーネルに関する実務レベルの知識と、テストに関する基本的な知識を前提としています。

KUnitの概要とプロジェクトでの設定方法については、以下を参照してください はじめに.

このドキュメントの構成¶

このドキュメントは「テスト」と「挙動の分離」の2つの主要セクションに分かれています。「テスト」セクションではユニットテストとは何か、そしてKUnitを使用してそれらをどのように書くかを説明します。「挙動の分離」セクションではKUnitを使用してコードを分離し、以前はユニットテストが困難だったコードをテスト可能にする方法を説明します。

テスト¶

KUnitとは？¶

「K」は「カーネル（kernel）」の略なので、「KUnit」は「（Linux）カーネル用ユニットテストフレームワーク」を指します。KUnitの主な目的はユニットテストの作成であり、汎用性が高くインテグレーションテストにも利用可能です。ただし、これは二次的な目的です。KUnitはカーネル用の唯一のテストフレームワークを目指すものではなく、例えばエンドツーエンドテストフレームワークを目指すものではありません。

ユニットテストとは何ですか？¶

A ユニットテスト コードの最小限のスコープでテストを行うテストです、つまり ユニット のコードです。C言語では関数です。

コンパイル単位で公開されているすべての関数にテストを書く必要があります。つまり、すべての関数が クラス （以下で定義）またはすべての ではありません static（キーワード）です。

テストの作成¶

テストケース¶

KUnitにおける基本単位はテストケースです。テストケースは、シグネチャを持つ関数です void (*)(struct kunit *test)。テスト対象の関数を呼び出し、次に設定します 期待値 例えば:

void example_test_success(struct kunit *test)
{
}

void example_test_failure(struct kunit *test)
{
        KUNIT_FAIL(test, "This test never passes.");
}

上記の例では example_test_success 常に成功します。なぜなら何もしないからで、期待値が設定されていないため、すべての期待値が成功します。一方で example_test_failure 常に失敗します。なぜなら、 KUNIT_FAILを呼び出しているからです。これはメッセージをログに記録し、テストケースを失敗させる特別な期待値です。

期待値¶

ある 期待値 は、テストで特定のコードが特定の動作を行うことを期待する方法です。期待値は関数のように呼び出されます。テストは、テスト対象のコードの動作について期待値を設定することで構成され、1つ以上の期待値が失敗すると、テストケースが失敗し、失敗に関する情報がログに記録されます。例えば:

void add_test_basic(struct kunit *test)
{
        KUNIT_EXPECT_EQ(test, 1, add(1, 0));
        KUNIT_EXPECT_EQ(test, 2, add(1, 1));
}

上記の例では add_test_basic 関数を呼び出すことで、その動作について複数のアサーションを行います；第一引数は常に add型です struct kunit *、現在のテストコンテキストに関する情報が含まれています。第二引数は、期待される値であり、最後の値は実際に取得された値です。もし add すべての期待条件を満たす場合、テストケース、 add_test_basic は通過します。どの期待条件も満たされない場合、テストケースは失敗します。

テストケースが 失敗する のは、どの期待条件も違反した場合です。ただし、テストは失敗しても実行を継続し、他の期待条件を試行し続ける可能性があります。これは アサーション とは異なり、後述します。

KUnitでサポートされている他の期待について学ぶには、 テストAPI.

注意

1つのテストケースは非常に短く、理解しやすく、単一の動作に焦点を当てたほうが良いです。

例えば、上で示したadd関数を適切にテストするには、それぞれがadd関数が持つべき性質をテストする別のテストケースを作成します。例えば、次のようにします：

void add_test_basic(struct kunit *test)
{
        KUNIT_EXPECT_EQ(test, 1, add(1, 0));
        KUNIT_EXPECT_EQ(test, 2, add(1, 1));
}

void add_test_negative(struct kunit *test)
{
        KUNIT_EXPECT_EQ(test, 0, add(-1, 1));
}

void add_test_max(struct kunit *test)
{
        KUNIT_EXPECT_EQ(test, INT_MAX, add(0, INT_MAX));
        KUNIT_EXPECT_EQ(test, -1, add(INT_MAX, INT_MIN));
}

void add_test_overflow(struct kunit *test)
{
        KUNIT_EXPECT_EQ(test, INT_MIN, add(INT_MAX, 1));
}

テスト対象のすべてのプロパティが一目でわかるようにしています。

アサーション¶

KUnitには アサーションという概念もあります。アサーションは、期待条件と同様ですが、条件が満たされない場合にテストケースを即座に終了させます。

例:

static void mock_test_do_expect_default_return(struct kunit *test)
{
        struct mock_test_context *ctx = test->priv;
        struct mock *mock = ctx->mock;
        int param0 = 5, param1 = -5;
        const char *two_param_types[] = {"int", "int"};
        const void *two_params[] = {&param0, &param1};
        const void *ret;

        ret = mock->do_expect(mock,
                              "test_printk", test_printk,
                              two_param_types, two_params,
                              ARRAY_SIZE(two_params));
        KUNIT_ASSERT_NOT_ERR_OR_NULL(test, ret);
        KUNIT_EXPECT_EQ(test, -4, *((int *) ret));
}

この例では、テスト対象のメソッドがポインタを返す必要があります。したがって、メソッドが返すポインタがNULLまたはerrnoだった場合、次の期待条件でテストケースがクラッシュする可能性があるため、テストを継続する必要はありません。 ASSERT_NOT_ERR_OR_NULL(…) は、テストケースを終了し、テストを完了させる条件が満たされていない場合に、テストを中断します。

テストスイート¶

明らかに1つのユニットテストだけでは役立ちません。多くのテストケースでユニットのすべての動作をカバーする力が重要です。そのため、多くの 類似 なテストが行われる場合があります。このような密接に関連したテストを減らすために、多くのユニットテストフレームワーク（KUnitを含む）では、 テストスイート. A テストスイート は、コードのユニットに対するテストケースのコレクションで、セットアップ関数が各テストケース実行前に呼び出され、ティアダウン関数が各テストケース終了後に呼び出される仕組みです。

例:

static struct kunit_case example_test_cases[] = {
        KUNIT_CASE(example_test_foo),
        KUNIT_CASE(example_test_bar),
        KUNIT_CASE(example_test_baz),
        {}
};

static struct kunit_suite example_test_suite = {
        .name = "example",
        .init = example_test_init,
        .exit = example_test_exit,
        .test_cases = example_test_cases,
};
kunit_test_suite(example_test_suite);

上の例では、テストスイート、 example_test_suiteはテストケース、 example_test_foo, example_test_bar, and example_test_bazを実行します。それぞれのテストケースは、実行前に example_test_init が呼び出され、実行後に example_test_exit が呼び出されます。 kunit_test_suite(example_test_suite) テストスイートをKUnitテストフレームワークに登録します。

注意

テストケースは、テストスイートに関連付けられている場合にのみ実行されます。

kunit_test_suite(...) は、リンカに指定されたテストスイートを特別なリンカセクションに配置させ、KUnitがlate_initの後に、またはテストモジュールがロードされるときに実行できるようにするマクロです（テストがビルドされたかどうかによって実行タイミングが異なります）。

これらの種類の詳細については、以下を参照してください。 テストAPI.

動作の分離¶

ユニットテストの他のテスト形式では提供されない最も重要な側面は、テスト対象コードの量を単一のユニットに限定できるという能力です。実際には、テスト対象ユニットが関数を呼び出すときにどのコードが実行されるかを制御できることが必要ですが、これは通常、関数をAPIとして公開し、その関数の定義を変更しても残りのコードベースに影響を与えないようにする間接的な方法で実現されます。カーネルでは、主に2つの構造からこの機能が得られます。1つは実装者が提供する関数ポインタを含む構造体（クラス）で、もう1つはコンパイル時に選択されるアーキテクチャ固有の関数です。

クラス¶

クラスはC言語の組み込み構造ではありませんが、簡単に導出可能な概念です。したがって、標準化されたオブジェクト指向ライブラリ（例：GNOMEのGObject）を使用していないほぼすべてのプロジェクトは、オブジェクト指向プログラミングを実装するための独自の方法を持っています。Linuxカーネルも例外ではありません。

カーネルのオブジェクト指向プログラミングの中心的な概念はクラスです。カーネルでは、 クラス は関数ポインタを含む構造体です。これにより、 実装者 および users が同じ関数シグネチャを使用するように強制されるため、関数を直接呼び出す必要がありません。クラスとしての真の機能を果たすためには、関数ポインタがクラスへのポインタ（これを クラスハンドルと呼ぶ）をパラメータの1つとして指定する必要があります。これにより、メンバ関数（もしくはクラスメソッド）が実行可能になります。 メソッド) メンバ変数（より一般的にフィールドと呼ばれる）にアクセスできるようにするため、 フィールド) 同じ実装が複数の インスタンス.

通常、クラスは オーバーライドされる によって 子クラスによって 親クラスを内包する 親クラス 子クラス内に含まれる親を指すポインタが渡されると、子の実装がそのポインタを自身のポインタに変換できる。これは、親のポインタが常に子のポインタから固定オフセットを引いたものであるためである。このオフセットは、子構造体に含まれる親のオフセットに等しい。例えば：

struct shape {
        int (*area)(struct shape *this);
};

struct rectangle {
        struct shape parent;
        int length;
        int width;
};

int rectangle_area(struct shape *this)
{
        struct rectangle *self = container_of(this, struct shape, parent);

        return self->length * self->width;
};

void rectangle_new(struct rectangle *self, int length, int width)
{
        self->parent.area = rectangle_area;
        self->length = length;
        self->width = width;
}

この例では（ほとんどのカーネルコードと同じように）親のポインタから子のポインタを計算する操作は、 container_of.

Faking Classes¶

クラスのメソッドを呼び出すコードをユニットテストするには、メソッドの挙動を制御可能にする必要があります。そうでなければ、テストはユニットテストではなく統合テストになります。

フェイクは、実行環境とは異なるコードの実装を提供しますが、呼び出し元から見れば同じ挙動をします。これは、扱いにくい依存関係や遅い処理を置き換えるために通常行われます。

このような例として、内部バッファに「コンテンツ」を保存するフェイクEEPROMを実装するかもしれません。例えば、EEPROMを表すクラスがあるとします:

struct eeprom {
        ssize_t (*read)(struct eeprom *this, size_t offset, char *buffer, size_t count);
        ssize_t (*write)(struct eeprom *this, size_t offset, const char *buffer, size_t count);
};

そして、EEPROMへの書き込みをバッファリングするコードをテストしたいとします:

struct eeprom_buffer {
        ssize_t (*write)(struct eeprom_buffer *this, const char *buffer, size_t count);
        int flush(struct eeprom_buffer *this);
        size_t flush_count; /* Flushes when buffer exceeds flush_count. */
};

struct eeprom_buffer *new_eeprom_buffer(struct eeprom *eeprom);
void destroy_eeprom_buffer(struct eeprom *eeprom);

このコードを簡単にテストするには、 フェイクアウト その下にあるEEPROM:

struct fake_eeprom {
        struct eeprom parent;
        char contents[FAKE_EEPROM_CONTENTS_SIZE];
};

ssize_t fake_eeprom_read(struct eeprom *parent, size_t offset, char *buffer, size_t count)
{
        struct fake_eeprom *this = container_of(parent, struct fake_eeprom, parent);

        count = min(count, FAKE_EEPROM_CONTENTS_SIZE - offset);
        memcpy(buffer, this->contents + offset, count);

        return count;
}

ssize_t fake_eeprom_write(struct eeprom *parent, size_t offset, const char *buffer, size_t count)
{
        struct fake_eeprom *this = container_of(parent, struct fake_eeprom, parent);

        count = min(count, FAKE_EEPROM_CONTENTS_SIZE - offset);
        memcpy(this->contents + offset, buffer, count);

        return count;
}

void fake_eeprom_init(struct fake_eeprom *this)
{
        this->parent.read = fake_eeprom_read;
        this->parent.write = fake_eeprom_write;
        memset(this->contents, 0, FAKE_EEPROM_CONTENTS_SIZE);
}

これを使ってテストを実行できます struct eeprom_buffer:

struct eeprom_buffer_test {
        struct fake_eeprom *fake_eeprom;
        struct eeprom_buffer *eeprom_buffer;
};

static void eeprom_buffer_test_does_not_write_until_flush(struct kunit *test)
{
        struct eeprom_buffer_test *ctx = test->priv;
        struct eeprom_buffer *eeprom_buffer = ctx->eeprom_buffer;
        struct fake_eeprom *fake_eeprom = ctx->fake_eeprom;
        char buffer[] = {0xff};

        eeprom_buffer->flush_count = SIZE_MAX;

        eeprom_buffer->write(eeprom_buffer, buffer, 1);
        KUNIT_EXPECT_EQ(test, fake_eeprom->contents[0], 0);

        eeprom_buffer->write(eeprom_buffer, buffer, 1);
        KUNIT_EXPECT_EQ(test, fake_eeprom->contents[1], 0);

        eeprom_buffer->flush(eeprom_buffer);
        KUNIT_EXPECT_EQ(test, fake_eeprom->contents[0], 0xff);
        KUNIT_EXPECT_EQ(test, fake_eeprom->contents[1], 0xff);
}

static void eeprom_buffer_test_flushes_after_flush_count_met(struct kunit *test)
{
        struct eeprom_buffer_test *ctx = test->priv;
        struct eeprom_buffer *eeprom_buffer = ctx->eeprom_buffer;
        struct fake_eeprom *fake_eeprom = ctx->fake_eeprom;
        char buffer[] = {0xff};

        eeprom_buffer->flush_count = 2;

        eeprom_buffer->write(eeprom_buffer, buffer, 1);
        KUNIT_EXPECT_EQ(test, fake_eeprom->contents[0], 0);

        eeprom_buffer->write(eeprom_buffer, buffer, 1);
        KUNIT_EXPECT_EQ(test, fake_eeprom->contents[0], 0xff);
        KUNIT_EXPECT_EQ(test, fake_eeprom->contents[1], 0xff);
}

static void eeprom_buffer_test_flushes_increments_of_flush_count(struct kunit *test)
{
        struct eeprom_buffer_test *ctx = test->priv;
        struct eeprom_buffer *eeprom_buffer = ctx->eeprom_buffer;
        struct fake_eeprom *fake_eeprom = ctx->fake_eeprom;
        char buffer[] = {0xff, 0xff};

        eeprom_buffer->flush_count = 2;

        eeprom_buffer->write(eeprom_buffer, buffer, 1);
        KUNIT_EXPECT_EQ(test, fake_eeprom->contents[0], 0);

        eeprom_buffer->write(eeprom_buffer, buffer, 2);
        KUNIT_EXPECT_EQ(test, fake_eeprom->contents[0], 0xff);
        KUNIT_EXPECT_EQ(test, fake_eeprom->contents[1], 0xff);
        /* Should have only flushed the first two bytes. */
        KUNIT_EXPECT_EQ(test, fake_eeprom->contents[2], 0);
}

static int eeprom_buffer_test_init(struct kunit *test)
{
        struct eeprom_buffer_test *ctx;

        ctx = kunit_kzalloc(test, sizeof(*ctx), GFP_KERNEL);
        KUNIT_ASSERT_NOT_ERR_OR_NULL(test, ctx);

        ctx->fake_eeprom = kunit_kzalloc(test, sizeof(*ctx->fake_eeprom), GFP_KERNEL);
        KUNIT_ASSERT_NOT_ERR_OR_NULL(test, ctx->fake_eeprom);
        fake_eeprom_init(ctx->fake_eeprom);

        ctx->eeprom_buffer = new_eeprom_buffer(&ctx->fake_eeprom->parent);
        KUNIT_ASSERT_NOT_ERR_OR_NULL(test, ctx->eeprom_buffer);

        test->priv = ctx;

        return 0;
}

static void eeprom_buffer_test_exit(struct kunit *test)
{
        struct eeprom_buffer_test *ctx = test->priv;

        destroy_eeprom_buffer(ctx->eeprom_buffer);
}

非UMLアーキテクチャでのKUnit¶

デフォルトでは、KUnitはテスト対象コードの依存関係を提供する方法としてUMLを使用します。ほとんどの場合、KUnitのUMLの使用は内部での実装詳細とみなされます。ただし、特定のアーキテクチャのコードを実行するか、実際のハードウェアでテストを行う必要がある場合があります。そのため、KUnitは他のアーキテクチャでの実行をサポートしています。

既存のKUnitテストを非UMLアーキテクチャで実行¶

非UMLアーキテクチャで既存のKUnitテストを実行する際には、いくつかの特別な考慮点があります:

  • ハードウェアは決定性が保証されないため、UMLで常に通過または失敗するテストが、実際のハードウェアでは常に同じ結果を返すとは限りません。

  • ハードウェアや仮想マシン環境はhermeticでない可能性があります。KUnitはテストを実行するためのhermeticな環境を提供しようとしますが、カーネルの外でKUnitが知らない状態を管理することはできません。そのため、UMLではhermeticなテストだったものが、他のアーキテクチャではhermeticでなくなる可能性があります。

  • 一部の機能やツールはUMLの外ではサポートされない可能性があります。

  • ハードウェアや仮想マシンはUMLよりも遅いです。

これらは、実際のハードウェアでKUnitテストを実行するのを避ける理由ではありません。これらは、実行する際の注意点に過ぎません。

最も大きな障害は、特定のKUnit機能やインフラストラクチャがターゲット環境をサポートしない可能性です。たとえば、現在のKUnit Wrapper (tools/testing/kunit/kunit.pyこれはUMLの外では動作しません。残念ながら、この問題を回避する方法はありません。UML（あるいは特定のアーキテクチャのみでも）を使用することで、多くの仮定を導入でき、それにより通常は不可能なことが実現可能になります。

ただし、すべてのコアKUnitフレームワーク機能はすべてのアーキテクチャで完全にサポートされており、使用方法は簡単です。必要なのは、実行したいテスト用のkunitconfigとKconfigオプションを、プラットフォーム用の設定にマージするだけです。それだけで完了です！

たとえば、以下のkunitconfigをもっているとします：

CONFIG_KUNIT=y
CONFIG_KUNIT_EXAMPLE_TEST=y

x86 VMでこのテストを実行したい場合、以下の設定オプションを、 .config:

CONFIG_KUNIT=y
CONFIG_KUNIT_EXAMPLE_TEST=y
CONFIG_SERIAL_8250=y
CONFIG_SERIAL_8250_CONSOLE=y

これらの新しいオプションは、ログ出力に必要な一般的なシリアルコンソールのサポートを有効にするだけです。

次に、これらのテストを含むカーネルを構築するには、以下のようになります：

make ARCH=x86 olddefconfig
make ARCH=x86

カーネルを構築したら、QEMUで実行するには以下のようになります：

qemu-system-x86_64 -enable-kvm \
                   -m 1024 \
                   -kernel arch/x86_64/boot/bzImage \
                   -append 'console=ttyS0' \
                   --nographic

カーネルのログに挟まれている可能性があります：

TAP version 14
        # Subtest: example
        1..1
        # example_simple_test: initializing
        ok 1 - example_simple_test
ok 1 - example

おめでとうございます！これでx86アーキテクチャでKUnitテストを実行しました！

同様に、kunitおよびkunitテストはモジュールとして構築することもできます。テストをこのように実行したい場合、以下の設定オプションを、 .config:

CONFIG_KUNIT=m
CONFIG_KUNIT_EXAMPLE_TEST=m

カーネルが構築・インストールされると、単純な

modprobe example-test

…でテストを実行できます。

他のアーキテクチャ向けの新しいテストの作成¶

最初にしなければならないのは、特定のアーキテクチャでKUnitテストを書く必要があるか、また特定のハードウェアでテストを書く必要があるかを自問することです。一般に、Linuxソースリポジトリに含まれていない特定のハードウェアやソフトウェアへのアクセスを前提としたテストは、極力避けるべきです。

たとえあなたがテストを常に自分のハードウェア構成で実行する予定であっても、他の人があなたのテストを実行したい場合があり、あなたのハードウェアにアクセスできないかもしれません。テストをUMLで実行するように書けば、誰でもあなたの特定のセットアップを知らずにテストを実行でき、あなたのハードウェアセットアップでテストを実行するには、あなたのアーキテクチャでコンパイルするだけで済みます。

重要です。

常にUMLで実行可能なテストを、特定のアーキテクチャのみで実行可能なテストよりも優先し、QEMUや他の入手が容易（金銭的に無料）なソフトウェア環境で実行可能なテストを、特定のハードウェアよりも優先してください。

ただし、アーキテクチャやハードウェアに特化したテストを書く理由は依然として有効です。たとえば、本当に属するコードをテストしたい場合があります。 arch/some-arch/*。ただし、物理的なハードウェアに依存しないテストを書くように努めてください。いくつかのテストケースがハードウェアを必要としない場合、実際に必要するテストケースだけにハードウェアを依存させるべきです。

ハードウェアに特化した部分を正確に限定した現在、テストの作成と実行の手順は通常のKUnitテストとほぼ同じです。特別な注意点は、テストケースの間にハードウェアの状態をリセットする必要があります。これが不可能な場合、呼び出しごとに1つのテストケースのみを実行できる可能性があります。

KUnit debugfs表現¶

KUnitテストスイートが初期化されるとき、それに関連するディレクトリが以下に作成されます。 /sys/kernel/debug/kunit/<test-suite>。このディレクトリには1つのファイルが含まれています。

  • results: 「cat results」コマンドは、最後のテスト実行における各テストケースの結果と全体スイートの結果を表示します。

debugfsの表現は、KUnitテストスイートがネイティブ環境で実行される場合（モジュールまたはビルトインとして）に主に役立ちます。このように結果を表示する方法は、それ以外の場合、dmesg出力と他のイベントが混在する可能性があるため、価値があります。各結果ファイルの最大サイズはKUNIT_LOG_SIZEバイト（定義は include/kunit/test.h).

テストスタイルと命名規則¶

KUnitテストの検索、作成、使用をできるだけ簡単にするため、以下のガイドラインに従って名前を付け、書くことが強く推奨されます。これらのルールに従わないKUnitテストを書くことは可能ですただし、ツールの動作を破壊する可能性があり、他のテストと競合する可能性があり、テストシステムが自動的に実行しない可能性があります。

以下のケースを除き、これらのガイドラインから逸脱しないことが推奨されます：

  1. 既存の名前を持つテストをKUnitに移植する場合、または

  2. 自動実行で重大な問題を引き起こす可能性があるテストを書く場合（例：非決定的な偽陽性または偽陰性を生じる、または非常に長い時間かかるテスト）。

サブシステム、スイート、テスト¶

テストをできるだけ簡単に見つけるため、テストはサブシステムごとにグループ化されています。テストサブシステムは、カーネルの関連する領域をテストするテストのグループであり、サブシステムは同じカーネルサブシステムまたはドライバの異なる部分をテストするテストサブシステムの集合です。

サブシステム¶

すべてのテストサブシステムはサブシステムに属さなければなりません。サブシステムは、同じドライバまたはカーネルの一部をテストする1つ以上のKUnitテストサブシステムのコレクションです。一般的なルールは、テストサブシステムが単一のカーネルモジュールに一致するべきです。テスト対象のコードがモジュールとしてコンパイルできない場合、多くの場合、ソースツリー内のディレクトリまたはMAINTAINERSファイルのエントリに該当するサブシステムにするべきです。不明な場合は、類似した領域のテストの慣例に従いましょう。

テストサブシステムはテスト対象のコードに名前を付けなければなりません。可能な限りモジュール名、またはテスト対象のディレクトリまたはファイル名に合わせるべきです。必要に応じて、誤解を招かないように名前を明確にする必要があります。

テストサブシステム名に複数のコンポーネントがある場合、アンダースコアで区切るべきです。 不要 サブシステム名に「test」や「kunit」を直接含めるのは、他のテストやkunitフレームワーク自体をテストする場合を除き、避けましょう。

例としてのサブシステムは以下の通りです：

ext4

モジュールとファイルシステム名に一致します。

apparmor

モジュール名とLSM名に一致します。

kasan

ツールの一般的な名前、パスの顕著な部分 mm/kasan

snd_hda_codec_hdmi

複数のコンポーネントを持ち（snd, hda, codec, hdmi)アンダースコアで区切られています。モジュール名に一致します。

避けるべき名前例：

linear-ranges

名前は単語を区切る際、アンダースコアを使用し、ハイフンは避けましょう。推奨されるのは linear_ranges.

qos-kunit-test

アンダースコアを使用するだけでなく、この名前には「kunit-test」のサフィックスを含めず、 qos サブシステム名として誤解を招く可能性があります。 power_qos より良い名前は

pc_parallel_port

対応するモジュール名は parport_pcなので、このサブシステムも同様に名前を parport_pc.

注意

KUnit API およびツールはサブシステムについて明示的に知っているわけではありません。単にテストスイートをカテゴリ化し、モジュールを名前付けるための簡単で一貫した方法を提供するものに過ぎません。今後は変更される可能性があります。

スイート¶

KUnit テストはテストスイートにグループ化され、特定の機能領域をテストします。テストスイートには、スイート内のすべてのテストで実行される共有初期化およびシャットダウンコードを含めることができます。すべてのサブシステムが複数のテストスイートに分割される必要はありません（例：シンプルなドライバ）。

テストスイートは所属するサブシステムの名前から命名されます。サブシステム内に複数のスイートがある場合、テスト対象の特定の領域をサブシステム名にアンダースコアで接続して追加します。

サブシステム内に複数のテストタイプ（例：ユニットテストと統合テスト）が存在する場合、それらは別のスイートに配置する必要があります。スイート名の最後にテストタイプを記載してください。これらのテストが実際に存在しない場合は、使用しないでください。 _test, _unittest または類似の語をスイート名に含めないでください。

サブシステム名を含むフルなテストスイート名は、 .name 構造体の kunit_suite メンバとして指定する必要があります。これはモジュール名のベースになります（以下を参照）。

例としてのテストスイートには次のものがあります：

ext4_inode

の ext4 サブシステムの inode 領域をテストしています。

kunit_try_catch

の kunit の実装自体をテストしています。 try_catch 領域をテストしています。

apparmor_property_entry

の apparmor サブシステムの property_entry 領域をテストしています。

kasan

以下の kasan サブシステムには1つのスイートしか存在しないため、スイート名はサブシステム名と一致します。

避けるべき名前例：

ext4_ext4_inode

サブシステムを2回記載する理由はありません。

property_entry

サブシステム名がないとスイート名は曖昧です。

kasan_integration_test

サブシステム内に1つのスイートしかない場合、スイートは単に kasan と呼ばれるべきです。サブシステム名を冗長に追加する必要はありません。 kasanを冗長に追加する必要はありません。 integration_test別のテストスイート（例：ユニットテスト）が追加された場合、そのスイートは kasan_unittest や同様の方法で処理しなければなりません。

テストケース¶

個々のテストは、制約されたコードパス、プロパティ、または関数をテストする単一の関数で構成されます。テスト出力では、個々のテスト結果がスイート結果のサブテストとして表示されます。

テストはテスト対象の名前で命名すべきです。これは通常、テストされる関数名で、テストされる入力またはコードパスの説明を含みます。テストはC関数であるため、カーネルのコーディングスタイルに従って命名および記述する必要があります。

注意

テスト自体が関数であるため、他のC識別子と名前が衝突する可能性があります。これには多少の工夫が必要かもしれません。テスト関数を static として定義することで、グローバル名前空間を汚染するのを避けるのが良いです。

テスト名の例には次のものがあります：

unpack_u32_with_null_name

をテストしています unpack_u32 NULL名が渡された場合の関数。

test_list_splice

をテストしています list_splice マクロ。これはマクロ自身と名前が衝突しないように接頭辞をもつ。 test_ テストスイートの名前をスイート名とテスト名をコロン（つまり

テストのテストスイートの文脈を超えて参照する必要がある場合、 完全修飾 テストの名前は、スイート名とテスト名をコロン（つまり suite:test).

テスト Kconfigエントリ¶

すべてのテストスイートはKconfigエントリに結びつけるべきです。

このKconfigエントリは以下を満たす必要があります：

  • 名前を CONFIG_<name>_KUNIT_TESTここで<name>はテストスイートの名前を表します。

  • テスト対象のドライバ/サブシステムの設定エントリと並べて表示するか、[Kernel Hacking]→[Kernel Testing and Coverage]の下に配置する必要があります。

  • 依存する CONFIG_KUNIT

  • 表示されるのは CONFIG_KUNIT_ALL_TESTS 有効になっていない場合のみ

  • デフォルト値を CONFIG_KUNIT_ALL_TESTS.

  • ヘルプテキストにKUnitの簡単な説明を記載する

特定の理由がない限り（例：テストがモジュールとしてビルドできない場合を除く）、テスト用のKconfigエントリはトリステートにするべきです。

例: Kconfigエントリ

config FOO_KUNIT_TEST
        tristate "KUnit test for foo" if !KUNIT_ALL_TESTS
        depends on KUNIT
        default KUNIT_ALL_TESTS
        help
          This builds unit tests for foo.

          For more information on KUnit and unit tests in general, please refer
          to the KUnit documentation in Documentation/dev-tools/kunit/.

          If unsure, say N.

テストファイルとモジュール名¶

KUnitテストは通常モジュールとしてコンパイルできます。これらのモジュールはテストスイートの名前を基に、 _testに名前を付けるべきです。これは非KUnitテストと衝突する可能性がある場合、サフィックス _kunit を使用することもできます。

この目的を達成する最も簡単な方法は、テストスイートを含むファイルに <suite>_test.c （または、上記のように <suite>_kunit.c）。このファイルはテスト対象のコードの隣に配置する必要があります。

テストスイートの名前がテストの親ディレクトリの一部またはすべてを含む場合、ソースファイル名を変更して冗長性を減らすのが意味があるかもしれません。例えば、 foo_firmware スイートは foo/firmware_test.c ファイル。

Linux Kernelのコーディングスタイル¶

これはLinuxカーネルのための好ましいコーディングスタイルを説明する短いドキュメントです。コーディングスタイルは非常に個人的で、私は誰かの意見を否定するつもりはありませんが、 force 私の意見を誰かに押し付けるつもりはありませんが、これは私がメンテナンスする必要があるものに適用されるべきものであり、他の多くのものにも適用したいと思っています。少なくともここに述べたポイントを考慮してください。

まず、GNUコーディング標準のコピーを印刷することをお勧めします。読むのはやめましょう。焼却するのは、非常に象徴的な行動です。

まあ、ここからいきます。

1) インデント¶

タブは8文字で、インデントも同様に8文字です。インデントを4（または2！）文字にしようと試みる異端的な動きがありますが、それはPIの値を3と定義しようとするのと同じです。

理由：インデントの目的は、制御ブロックがどこで始まり、どこで終わるかを明確にすることです。特に、画面を見続けて20時間経った後、大きなインデントがあると、インデントの仕組みがどれほど効果的かがはるかにわかりやすくなります。

では、一部の人々は8文字のインデントがコードを右にずらしすぎることを主張し、80文字のターミナル画面で読みにくくなると主張します。その答えは、インデントレベルが3を超える必要がある場合、プログラムを修正すべきであるということです。

まとめると、8文字のインデントは読みやすさを高め、関数を深くネストしているときに警告するという追加のメリットがあります。その警告に耳を傾けてください。

switch文で複数のインデントレベルを扱いやすくするための推奨方法は、 switch およびその下位 case 同じ列にラベルを配置するのではなく double-indenting 、そして case ラベル。例:

switch (suffix) {
case 'G':
case 'g':
        mem <<= 30;
        break;
case 'M':
case 'm':
        mem <<= 20;
        break;
case 'K':
case 'k':
        mem <<= 10;
        fallthrough;
default:
        break;
}

1行に複数のステートメントを書かないでください。隠す何かがある場合を除いて

if (condition) do_this;
  do_something_everytime;

1行に複数の代入を書かないでください。カーネルのコーディングスタイルは非常にシンプルです。複雑な式は避けてください。

コメント、ドキュメンテーション、およびKconfig以外では、インデントにスペースは使用されません。上記の例は意図的に破られています。

適切なエディタを取得し、行末のホワイトスペースを残さないでください。

2) 長い行と文字列の折り返し¶

コーディングスタイルは、一般的なツールを使用して読みやすく保守性を確保することです。

1行の長さの推奨制限は80カラムです。

80カラムを超えるステートメントは、読みやすく情報を隠さない場合を除き、合理的なブロックに分割する必要があります。

子要素は常に親要素よりも大幅に短く、右側に配置されます。非常に一般的なスタイルとして、子要素を関数のオープンパレットに揃える方法があります。

これらの同じルールは、長い引数リストを持つ関数ヘッダにも適用されます。

ただし、ユーザーが見ることができる文字列（例: printkメッセージ）を改行して分割しないでください。そうすると、grepで検索する能力を破壊してしまうからです。

3) ブラケットとスペースの配置¶

Cスタイルのもう一つの問題は、ブラケットの配置です。インデントサイズとは異なり、技術的な理由でどちらか一方の配置戦略を選ぶ理由はほとんどありませんが、KernighanとRitchieが示したように、行の最後にオープンブラケットを置き、次の行の最初にクローズブラケットを置くのが望ましいです。

if (x is true) {
        we do y
}

これは、関数以外のすべてのステートメントブロック（if、switch、for、while、do）にも適用されます。例:

switch (action) {
case KOBJ_ADD:
        return "add";
case KOBJ_REMOVE:
        return "remove";
case KOBJ_CHANGE:
        return "change";
default:
        return NULL;
}

ただし、関数は特別なケースです。オープンブラケットは次の行の先頭に置きます。以下のように:

int function(int x)
{
        body of function
}

世界中で異端者たちはこの不一致を…まあ…不一致だと主張していますが、正統派の人々は（a）K&Rが 右 正しいことを知っています。また、関数は本来特殊なのです（Cではネストできません）。

閉じるブラケットは1行で空であることに注意してください、 ただし 同じステートメントの続きがある場合、つまり while doステートメントや else ifステートメントの場合、以下のように:

do {
        body of do-loop
} while (condition);

および

if (x == y) {
        ..
} else if (x > y) {
        ...
} else {
        ....
}

理由: K&R。

また、このブラケットの配置は、空行（またはほぼ空行）の数を最小限に抑え、読みやすさを損なうことなく、画面の改行数（25行のターミナル画面を想定）が再生可能資源ではないため、コメントを書くための空行を多く確保します。

1行のステートメントで十分な場合は、不要なブラケットを使用しないでください。

if (condition)
        action();

および

if (condition)
        do_this();
else
        do_that();

条件ステートメントのどちらか一方のブランチが単一行のステートメントのみの場合、このルールは適用されません。後者の場合、両方のブランチでブラケットを使用してください：

if (condition) {
        do_this();
        do_that();
} else {
        otherwise();
}

また、ループが単一行のステートメントより多く含む場合、ブラケットを使用してください：

while (condition) {
        if (test)
                do_something();
}

3.1) スペース¶

Linuxカーネルのスタイルでは、スペースの使用は（主に）関数とキーワードの使い分けに依存します。キーワードの後にスペースを空けます。ただし、sizeof、typeof、alignof、および__attribute__は関数のように見え、Linuxでは通常括弧と一緒に使用されます（ただし、言語では括弧は必須ではありません）。例: sizeof info RCU保護データ構造からデータ要素を削除した後、 struct fileinfo info; 宣言されています。

したがって、これらのキーワードの後にスペースを空けてください：

if, switch, case, for, do, while

ただし、sizeof、typeof、alignof、または__attribute__にはスペースを空けません。例：

s = sizeof(struct file);

括弧内にスペースを追加しないでください。この例は 悪い:

s = sizeof( struct file );

ポインタ型のデータや、ポインタ型を返す関数を宣言する際、推奨される使用方法はデータ名や関数名に隣接し、型名には隣接しない。例: * データ名や関数名に隣接し、型名には隣接しない。例:

char *linux_banner;
unsigned long long memparse(char *ptr, char **retptr);
char *match_strdup(substring_t *s);

ほとんどの二項演算子および三項演算子の前後には1つのスペースを空ける。例えば、以下のいずれか:

=  +  -  <  >  *  /  %  |  &  ^  <=  >=  ==  !=  ?  :

ただし、単項演算子の後にはスペースを空けない:

&  *  +  -  ~  !  sizeof  typeof  alignof  __attribute__  defined

後置インクリメントおよびデクリメントの単項演算子の前にはスペースを空けない:

++  --

前置インクリメントおよびデクリメントの単項演算子の後にはスペースを空けない:

++  --

また、 . および -> 構造体メンバ演算子の前後にはスペースを空けない。

行末に余分な空白を残さないでください。一部のエディタでは、 smart インデントの設定により、新しい行の先頭に適切に空白を挿入するため、次の行のコードをすぐに入力できます。ただし、このようなエディタの一部では、コードの行を挿入しなかった場合（例えば、空白行を残した場合）、余分な空白を削除しないことがあります。その結果、行末に余分な空白を含む行が残ってしまいます。

Gitは、余分な空白を導入するパッチについて警告を発します。また、オプションで余分な空白を自動的に削除することもできます。ただし、複数のパッチを適用する場合、この処理により後続のパッチがコンテキストラインを変更して失敗する可能性があります。

4) ナメイング¶

Cはスパルタ式の言語であり、命名規則もそれに合わせるべきです。Modula-2やPascalのプログラマとは異なり、CのプログラマはThisVariableIsATemporaryCounterのようにかわいらしい名前を使いません。Cのプログラマはその変数を tmpと呼び、これは書くのがはるかに簡単で、理解するのに最も難しくない名前です。

HOWEVER、混在した大文字小文字の名前は好まれませんが、グローバル変数には説明的な名前が必須です。グローバル関数を呼び出す foo は重大な過ちです。

グローバル変数（必要がある場合のみ使用するため）には説明的な名前が必要です。同様にグローバル関数にも説明的な名前が必要です。アクティブなユーザー数をカウントする関数がある場合、その関数を 本当に と呼ぶべきです。 count_active_users() などは、あなたが ではありません それを呼び出すべきです cntusr().

関数の型を名前にエンコードする（いわゆるハンガリアン記法）は馬鹿げています - コンパイラはすでに型を知っているため、チェックは可能ですし、プログラマを混乱させるだけです。だからこそマイクロソフトがバグのあるプログラムを作っているのです。

ローカル変数名は短く、具体的にすべきです。ランダムな整数型のループカウンタであれば、おそらく iそれを呼び出すべきです loop_counter 誤解の可能性がない場合でも、非生産的です。同様に、 tmp 一時的な値を保持するために使用される変数であれば、ほぼどんな型でも可能です。

ローカル変数名を混同するのを恐れているなら、別の問題があります。それは「関数成長ホルモン不均衡症候群」と呼ばれるものです。第6章（関数）を参照してください。

シンボル名やドキュメンテーションでは、「マスター/スレーブ」（または「マスター」に依存しない「スレーブ」）や「ブラックリスト/ホワイトリスト」の新しい使用法を導入しないようにしてください。

「マスター/スレーブ」の代替案として推奨されるのは、

「{プライマリ、メイン} / {セカンドアリ、レプリカ、サブオーダー}」「{イニシエーター、リクエスター} / {ターゲット、レスポンダー}」「{コントローラー、ホスト} / {デバイス、ワーカー、プロキシ}」「リーダー / フォロワー」「ディレクター / パフォーマー」です。

「ブラックリスト/ホワイトリスト」の代替案として推奨されるのは、

「デニリスト / アローリスト」「ブロックリスト / パスリスト」です。

新しい使用法を導入する例外は、ユーザースペースABI/APIの維持、または2020年時点でのハードウェアやプロトコル仕様の更新でその用語が義務付けられている場合です。新しい仕様では、その用語の使用をカーネルコーディング標準に翻訳して使用してください。

5) ティプedef¶

構造体やポインタに対してティプedefを使用しないでください。 vps_t. これは 間違いです。 ソースコードで

vps_t a;

を見たとき、それは何を意味するのでしょうか？一方で、それが

struct virtual_container *a;

と書かれている場合、実際に a が指定された場所に存在しない場合

多くの人がティプedefが help readabilityと信じています。しかし、そうではありません。彼らは以下のケースにしか役立ちません：

  1. 完全に不透明なオブジェクト（typedefが積極的に使用されて hide オブジェクトの内容を隠す場合）。

    例: pte_t など、アクセッサ関数のみでアクセス可能な不透明なオブジェクト。

    注意

    不透明さと accessor functions は、それ自体では良いとは限りません。pte_tなどのようにこれらを使用する理由は、本当に絶対 ゼロ ポータブルにアクセス可能な情報があるからです。

  2. 明確な整数型で、抽象化が 役立ちます。 それが int または long.

    u8/u16/u32は完全に問題ありませんが、ここでは（d）のカテゴリに属する方が適切です。

    注意

    また、この用途には 理由 が必要です。何かが unsigned longであれば、

    typedef unsigned long myflags_t;

    の理由はありませんが、特定の状況でそれが unsigned int になる可能性があり、他の設定では unsigned longになる可能性がある場合、typedefを使用するのは全然問題ありません。

  3. sparseで実際に型チェック用の new 型を作成する場合。

  4. 標準C99型と同一の新しい型、特定の例外状況において。

    標準型のような uint32_tに慣れればそれほど時間がかかりませんが、一部の人にとってはその使用に反対する人もいます。

    そのため、Linux固有の u8/u16/u32/u64 型とその符号付きの同等型は標準型と同一ですが、新しいコードでは必須ではありません。

    既存のコードで既に使用されているタイプセットの一つを使用している場合、そのコード内の既存の選択に従うべきです。

  5. ユーザー空間で使用可能なタイプ。

    ユーザー空間に表示される特定の構造体では、C99型を要求したり、以下の形式を使用することはできません。 u32 そのため、ユーザー空間と共有されるすべての構造体で__u32や同様のタイプを使用します。

他のケースも存在するかもしれませんが、基本的なルールは、明確にこれらのルールのいずれにも該当しない限り、決してtypedefを使用しないことです。

一般的に、直接アクセス可能な要素を持つポインタや構造体は 更新処理が完了した後でも新しい読者が即座に開始する可能性があるため、以下のコードは読者がいないと信頼してはならない。 typedefとして定義すべきです。

6) 関数¶

関数は短く簡潔で、1つの目的だけを果たすべきです。1画面または2画面分のテキストに収まり、1つのことを行うことに特化すべきです（ISO/ANSIの画面サイズは80x24です）。

関数の最大長は、その関数の複雑さとインデントレベルに反比例します。したがって、概念的に単純なが、長く（ただし単純な）caseステートメントで、多くの異なるケースに対して多数の小さな処理を行う関数の場合、長めの関数を使用するのは問題ありません。

ただし、複雑な関数がある場合、1年生の高校生でも理解できない可能性があると懸念するなら、最大限の制限に厳密に従うべきです。説明的な名前を持つヘルパー関数を使用してください（パフォーマンスが重要と感じる場合はコンパイラにインライン化を依頼できます。コンパイラの方があなたよりも優れた結果を出してくれるでしょう）。

関数の別の指標はローカル変数の数です。5〜10を超えると何か間違いをしている可能性があります。関数を再考し、小さな部分に分割してください。人間の脳は通常、7つの異なることを簡単に把握できます。それ以上になると混乱します。あなたは優れていることはわかっていますが、2週間後には自分が何をしたか理解したいかもしれません。

ソースファイルでは、関数を1行の空白で区切ってください。関数がエクスポートされる場合、 EXPORT その関数のクロージングブレース行の直後にマクロを記述する必要があります。例：

int system_is_up(void)
{
        return system_state == SYSTEM_RUNNING;
}
EXPORT_SYMBOL(system_is_up);

関数プロトタイプでは、パラメータ名とデータ型を含めてください。これはC言語では必須ではありませんが、Linuxでは読者に有益な情報を簡単に追加できるため、推奨されます。

関数プロトタイプでキーワードを使用しないでください。 extern これは行を長くし、厳密には必要ありません。

7) 関数の統一的な終了処理¶

一部の人々によって非推奨とされるものの、コンパイラは条件を問わずジャンプする命令としてgotoステートメントの代替として頻繁に使用しています。

関数が複数の場所から終了する場合や、クリーンアップなどの共通処理が必要なときにgotoステートメントは役立ちます。クリーンアップが不要な場合は直接returnで終了させましょう。

ラベル名はgotoが行う動作や存在理由を示すように選ぶべきです。良い名前の例は out_free_buffer: gotoで解放 bufferです。GW-BASICのような名前（例： err1: および err2:）は避けてください。追加や削除を行うと再番号化が必要になり、また正しさを検証するのも困難です。

gotoを使用する理由は以下の通りです：

  • 条件を問わず実行するステートメントは理解しやすく追跡しやすい

  • ネストの深さが減らされる

  • 変更時に個々のエクスイットポイントを更新しないためのエラーを防ぐ

  • コンパイラが冗長なコードを最適化する作業を省略できるため

int fun(int a)
{
        int result = 0;
        char *buffer;

        buffer = kmalloc(SIZE, GFP_KERNEL);
        if (!buffer)
                return -ENOMEM;

        if (condition1) {
                while (loop1) {
                        ...
                }
                result = 1;
                goto out_free_buffer;
        }
        ...
out_free_buffer:
        kfree(buffer);
        return result;
}

注意すべき一般的なバグの一種は one err bugs で、以下のように見えます：

err:
        kfree(foo->bar);
        kfree(foo);
        return ret;

このコードのバグは、一部のエクスイットパスで foo がNULLであることです。通常の修正方法はこれを2つのエラーラベルに分けることです err_free_bar: および err_free_foo::

err_free_bar:
       kfree(foo->bar);
err_free_foo:
       kfree(foo);
       return ret;

理想的にはすべてのエクスイットパスをテストするためエラーをシミュレートすべきです。

8) コメント¶

コメントは良いですが、過剰なコメントは危険です。コードの動作方法をコメントで説明するのは絶対にしないでください：コードを書く際には、 動作 が明確であるようにする方がずっと良いです。下手に書いたコードを説明するのは時間の無駄です。

一般的には、コメントはコードが何をしているかを説明すべきで、どのように動作するかを説明すべきではありません。また、関数本体内にコメントを書くのは避けてください：関数が複雑すぎて一部を別途コメントする必要がある場合は、おそらく第6章に戻って見直すべきです。特に巧妙（または醜い）な部分には小さなコメントを加えるのは構いませんが、過剰なコメントは避けてください。代わりに関数の冒頭にコメントを加え、関数が何をするのか、なぜそうするのかを説明してください。

カーネルAPI関数をコメントする際は、kernel-doc形式を使用してください。以下のファイルを参照してください： Documentation/doc-guide/ および scripts/kernel-doc 詳しくは以下をご参照ください。

長い（複数行）コメントの推奨スタイルは：

/*
 * This is the preferred style for multi-line
 * comments in the Linux kernel source code.
 * Please use it consistently.
 *
 * Description:  A column of asterisks on the left side,
 * with beginning and ending almost-blank lines.
 */

net/ディレクトリおよびdrivers/net/ディレクトリ内のファイルでは、長いコメントのスタイルがやや異なります。

/* The preferred comment style for files in net/ and drivers/net
 * looks like this.
 *
 * It is nearly the same as the generally preferred comment style,
 * but there is no initial almost-blank line.
 */

基本型や派生型のデータについてもコメントすることが重要です。このため、1行に1つのデータ宣言（複数のデータ宣言にはコンマを使わない）を使用してください。これにより、各項目について小さなコメントを追加してその用途を説明できるスペースが確保されます。

9) あなたが大変な状況に陥った¶

それは大丈夫です、誰もがそうします。あなたの長期Unixユーザーのヘルパーから GNU emacs Cソースコードを自動的に整形してくれますが、そのデフォルトの設定は望ましくありません（実際にはランダムな入力よりも悪く、GNU emacsに無限のモンキーがタイプしても良いプログラムを作成できないほどです）。

そのため、GNU emacsを削除するか、より理にかなった設定を使用する必要があります。後者の場合は、.emacsファイルに以下の内容を追加してください：

(defun c-lineup-arglist-tabs-only (ignored)
  "Line up argument lists by tabs, not spaces"
  (let* ((anchor (c-langelem-pos c-syntactic-element))
         (column (c-langelem-2nd-pos c-syntactic-element))
         (offset (- (1+ column) anchor))
         (steps (floor offset c-basic-offset)))
    (* (max steps 1)
       c-basic-offset)))

(dir-locals-set-class-variables
 'linux-kernel
 '((c-mode . (
        (c-basic-offset . 8)
        (c-label-minimum-indentation . 0)

12) マクロ、列挙型およびRTL¶

定数や列挙型のラベルを定義するマクロの名前はキャピタル化されます

#define CONSTANT 0x12345

複数の関連する定数を定義する際には列挙型が好まれます

キャピタル化されたマクロ名は好まれますが、関数に似たマクロは小文字で名前を付けることができます

一般的に、インライン関数は関数に似たマクロよりも優れています

複数のステートメントを持つマクロはdo-whileブロックで囲みます

#define macrofun(a, b, c)                       \
        do {                                    \
                if (a == 5)                     \
                        do_this(b, c);          \
        } while (0)

マクロを使用する際は避けるべきこと：

  1. 制御フローに影響を与えるマクロ：

#define FOO(x)                                  \
        do {                                    \
                if (blah(x) < 0)                \
                        return -EBUGGERED;      \
        } while (0)

がブロックされるのは、 非常に 悪いアイデアです。関数呼び出しのように見えますが、関数を終了します。 calling コードを読む人の内部パーサーを壊さないでください。

  1. マクロがローカル変数にマジックな名前を持つことを依存している場合、

#define FOO(val) bar(index, val)

コードを読むと非常に混乱するだけでなく、見かけ上無害な変更でも壊れやすくなります。

3) l-valueとして使用される引数を持つマクロ: FOO(x) = y; が、誰かがFOOをインライン関数に変換した場合に問題を引き起こします。

4) 優先順位を忘れる: 表現式を使用して定数を定義するマクロは、表現式を括弧で囲む必要があります。パラメータを使用するマクロでも同様の問題に注意してください。

#define CONSTANT 0x4000
#define CONSTEXP (CONSTANT | 3)

5) 関数に似たマクロでローカル変数を定義する際の名前空間の衝突:

#define FOO(x)                          \
({                                      \
        typeof(x) ret;                  \
        ret = calc_ret(x);              \
        (ret);                          \
})

retはローカル変数の一般的な名前ですが、__foo_retは既存の変数と衝突する可能性が低くなります。

cppマニュアルではマクロについて詳しく説明しています。gcc内部マニュアルもRTLについて説明しており、これはカーネルのアセンブリ言語で頻繁に使用されます。

13) カーネルメッセージの出力¶

カーネル開発者は文章を読める人物として見られたいです。カーネルメッセージのスペルミスに注意し、良い印象を与えてください。誤った縮略語を使用しないでください。 dont；使用してください。 do not または don't 代わりに。メッセージは簡潔で明確で曖昧ではありません。

カーネルメッセージは句読点で終わらなくてもよいです。

括弧内に数字を表示する(%d)は価値がなく、避けるべきです。

linux/device.h には、メッセージが正しいデバイスとドライバーにマッチし、正しいレベルでタグ付けされるようにするためのドライバーモデル診断マクロがいくつかあります。dev_err()、dev_warn()、dev_info() などです。デバイスに関連付けられていないメッセージについては、<linux/printk.h> が定義しています。 pr_notice(), pr_info(), pr_warn(), pr_err()などの数値かもしれません。

良いデバッグメッセージを作成するのはかなりのチャレンジです。しかし、作成したメッセージはリモートでのトラブルシューティングに大変役立ちます。ただし、デバッグメッセージの出力は他の非デバッグメッセージの出力とは異なります。他の pr_XXX() 関数は条件に関係なく出力しますが、 pr_debug() デバッグメッセージはそれとは異なり、デフォルトではコンパイルアウトされます。DEBUG が定義されているか、CONFIG_DYNAMIC_DEBUG が設定されている場合を除いてです。dev_dbg() も同様で、関連する慣例では VERBOSE_DEBUG を使用して dev_vdbg() メッセージを既に DEBUG で有効化されたメッセージに追加します。

多くのサブシステムでは、対応する Makefile に -DDEBUG を有効にする Kconfig デバッグオプションがあります。他の場合では特定のファイルで #define DEBUG します。デバッグメッセージが条件に関係なく出力されるべき場合、たとえばすでにデバッグ関連の #ifdef セクション内にある場合は、printk(KERN_DEBUG …) を使用できます。

14) メモリの割り当て¶

カーネルは以下の一般的なメモリ割り当て機能を提供しています： kmalloc(), kzalloc(), kmalloc_array(), kcalloc(), vmalloc(), and vzalloc()詳しくは API ドキュメンテーションを参照してください。 メモリ割当ガイド

構造体のサイズを渡す際の推奨形式は以下の通りです：

p = kmalloc(sizeof(*p), ...);

構造体名を明示する形式は可読性を害し、ポインタ変数の型が変更された場合でもそれに応じて sizeof を渡す必要がないため、バグの機会を生じます。

void ポインタの戻り値をキャストするのは冗長です。C 言語では void ポインタを他のポインタ型に変換する動作は保証されています。

配列を割り当てる際の推奨形式は以下の通りです：

p = kmalloc_array(n, sizeof(...), ...);

ゼロ初期化された配列を割り当てる際の推奨形式は以下の通りです：

p = kcalloc(n, sizeof(...), ...);

どちらの形式も割り当てサイズ n * sizeof(…) でオーバーフローを検出し、発生した場合は NULL を返します。

これらの汎用割り当て関数は __GFP_NOWARN が指定されていない場合、失敗時にスタックダンプを出力します。したがって NULL を返した際に追加の失敗メッセージを出力する必要はありません。

15) インライン病¶

gcc に「make me faster」という特別な速度アップオプションがあるという誤解が一般的に見られます inlineインライン関数の使用は適切な場合もあります（マクロの置き換えなど、第12章を参照）、しかし多くの場合、適切ではありません。インラインキーワードを過度に使用すると、カーネルのサイズが大幅に増加し、結果としてCPUのicacheフットプリントが大きくなり、全体的なシステムの性能が低下します。また、ページキャッシュに使用できるメモリが少なくなるため、その影響も大きいです。考えてみれば、ページキャッシュのミスはディスクシークを引き起こし、それが5ミリ秒以上かかることがあります。これらの5ミリ秒には、多くのCPUサイクルが費やされています。

インラインを関数に適用する際の合理的なルールは、関数のコード行数が3行以上ある場合はインラインを避けることです。ただし、パラメータがコンパイル時定数であることが分かっている場合など、その定数性によりコンパイラがほとんどの関数をコンパイル時に最適化できる場合は、このルールの例外とします。 知っている コンパイラがコンパイル時にほとんどの関数を最適化できるため、このようなケースでは kmalloc() インライン関数

しばしば、静的で一度しか使われない関数にインラインを適用すると常にメリットがあると主張されることがあります。これは技術的に正しいですが、gccはこのような関数を自動的にインライン化できるため、2番目のユーザーが現れた際にインラインを削除するメンテナンスの手間が、インラインのヒントがgccに不要な動作をさせる可能性よりも重要です。

16) 関数の返却値と名前¶

関数はさまざまな種類の値を返すことができ、そのうち最も一般的なのは関数が成功したか失敗したかを示す値です。このような値は、エラーコード整数（-Exxx = 失敗、0 = 成功）または succeeded ブール値（0 = 失敗、非ゼロ = 成功）で表現できます。

これらの2つの表現方法を混同すると、見逃しやすいバグの原因になります。C言語が整数とブール値の明確な区別をもっていたら、コンパイラがこれらの間違いを検出してくれますが、現状ではそうではありません。このようなバグを防ぐために、常に次の規則に従ってください：

If the name of a function is an action or an imperative command,
the function should return an error-code integer.  If the name
is a predicate, the function should return a "succeeded" boolean.

例えば、 add work これはコマンドであり、add_work()関数は成功時は0、失敗時は-EBUSYを返します。同様に、 PCI device present これは述語であり、 pci_dev_present() 関数はマッチングするデバイスを見つけた場合1を、見つからなかった場合は0を返します。

すべてのEXPORTされた関数はこの規則を守るべきであり、すべてのパブリック関数も同様です。プライベート（スタティック）関数はこの規則を守る必要はありませんが、推奨されます。

計算の実際の結果を返す値を持つ関数は、このルールの対象外です。通常、失敗を示すために範囲外の結果を返します。典型的な例はポインタを返す関数で、NULLやERR_PTRメカニズムを使用して失敗を報告します。

17) boolの使用¶

Linuxカーネルのbool型はC99の_Bool型の別名です。bool値は0または1にしか評価されず、暗黙のまたは明示的なboolへの変換は値を自動的にtrueまたはfalseに変換します。bool型を使用する際は!!構造は必要なく、これによりバグのクラスを削減できます。

bool値を扱う際は、trueとfalseの定義を使用すべきで、1と0を使用しないでください。

bool型の関数戻り値やスタック変数は、適切な場面であれば常に使用可能です。読みやすさを高めるためboolの使用を推奨し、boolean値を保存する場合にintよりもしばしばより良い選択肢です。

キャッシュラインのレイアウトや値のサイズが重要である場合、boolの使用は避けるべきです。最適化されたアライメントとサイズの構造体ではboolを使用すべきではありません。

構造体に多数のtrue/false値がある場合、1ビットのメンバーを持つビットフィールドや、u8などの適切な固定幅型を使用して統合することを検討してください。

関数引数についても同様に、多数のtrue/false値は単一のビットフラグ引数に統合でき、呼び出し元が裸のtrue/false定数を持つ場合にflagsはしばしば読みやすい代替手段です。

それ以外の構造体や引数でのboolの限られた使用は読みやすさを向上させます。

18) カーネルマクロを再実装しないでください¶

include/linux/kernel.hヘッダーファイルには、自分で実装する代わりに使用すべきマクロが多数含まれています。例えば、配列の長さを計算する必要がある場合、マクロを活用してください

#define ARRAY_SIZE(x) (sizeof(x) / sizeof((x)[0]))

同様に、構造体メンバのサイズを計算する必要がある場合は、

#define sizeof_field(t, f) (sizeof(((t*)0)->f))

min()とmax()マクロも必要があれば厳密な型チェックを行います。このヘッダーファイルを確認して、コードに再実装しないでください。

20) インラインアセンブリ¶

アーキテクチャ固有のコードでは、CPUやプラットフォーム機能とインターフェースするためインラインアセンブリを使用する必要があります。必要に応じて躊躇せず使用してください。ただし、Cで実現可能であれば、インラインアセンブリを無駄に使用しないでください。可能な限りCからハードウェアを操作すべきです。

よく使うインラインアセンブリの部分をまとめた簡潔な補助関数を書くことを検討してください。繰り返し書くよりも、Cのパラメータを使用可能な形でまとめておくのが良いでしょう。

大規模で複雑なアセンブリ関数は.Sファイルに記述し、対応するCのプロトタイプはCヘッダーファイルで定義する必要があります。アセンブリ関数のCプロトタイプでは asmlinkage.

GCCが副作用を認識しなかった場合でもasmステートメントを削除しないようにvolatileとしてマークする必要があります。ただし常に必要とは限りません。無駄にvolatileを指定すると最適化の制限になる可能性があります。

複数の命令を含む単一のインラインアセンブリステートメントを書く場合、各命令を別の quoted string に分けて1行ずつ記述し、最後の文字列以外の各文字列の末尾に \n\t アセンブリ出力の次の命令のインデントを正しく行うために使用してください:

asm ("magic %reg1, #42\n\t"
     "more_magic %reg2, %reg3"
     : /* outputs */ : /* inputs */ : /* clobbers */);

21) 条件付きコンパイル¶

可能な限り.cファイルでプリプロセッサ条件式(#if, #ifdef)を使用しないでください。これによりコードの可読性が低下し、論理が追跡困難になります。代わりに、これらの.cファイルで使用する関数を定義するヘッダーファイルで条件式を使用し、#elseケースでは無操作のスタブバージョンを提供し、.cファイルでこれらの関数を条件に関係なく呼び出すようにしてください。コンパイラはスタブ呼び出しのコードを生成しないので、結果は同じですが論理は読みやすくなります。

関数全体をコンパイルアウトするのを好むべきです。関数の一部や式の一部をコンパイルアウトするのではなく、式の一部または全部を別個の補助関数に抽出し、その関数に条件を適用するようにしてください。

特定の構成で使用されない可能性のある関数や変数がある場合、コンパイラがその定義が使用されないことを警告する可能性があるため、__maybe_unusedとしてマークするのではなく、プリプロセッサ条件付きでラップするのではなく、__maybe_unusedとしてマークしてください。(ただし、関数や変数が実際に使用されない場合、削除する必要があります。) always コード内で可能であれば、IS_ENABLEDマクロを使用してKconfigシンボルをCの論理式に変換し、通常のC条件式として使用してください。

コンパイラが条件式を定数評価してブロックを含むか含まないかを判定し、#ifdefと同様にコードブロックを含むか含まないかを処理するため、この方法はランタイムオーバーヘッドを追加しません。ただし、このアプローチではCコンパイラがブロック内のコードを確認できるため、構文や型、シンボル参照などの正しさをチェックできます。したがって、ブロック内のコードが条件が満たされない場合に存在しないシンボルを参照する場合は、#ifdefを使用する必要があります。

if (IS_ENABLED(CONFIG_SOMETHING)) {
        ...
}

任意の複雑な#ifや#ifdefブロック（複数行以上）の終わりには、#endifの同じ行にコメントを追加し、使用した条件式を記載してください。例えば：

付録I) 参考文献

#ifdef CONFIG_SOMETHING
...
#endif /* CONFIG_SOMETHING */

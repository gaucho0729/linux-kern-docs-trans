変更内容を説明してください。¶

問題を説明してください。あなたのパッチが1行のバグ修正であれ、5000行の新機能の実装であれ、必ずしも背後にある問題が存在します。レビュアーに、修正すべき問題があることを説得し、彼らが最初の段落を読み終わって次の内容を読む価値があることを示してください。

ユーザーが見える影響を説明してください。明確なクラッシュやロックアップは説得力がありますが、すべてのバグがそのように明確ではありません。問題がコードレビュー中に見つかったとしても、ユーザーに与える影響を説明してください。多くのLinuxインストールは、セカンダリスターブルやベンダー/製品固有のツリーからカーネルを実行しており、アップストリームからの特定のパッチのみをピックアップしています。したがって、あなたの変更をダウンストリームにルーティングするのに役立つ情報を含めてください：誘因となる状況、dmesgからの抜粋、クラッシュの説明、パフォーマンスの低下、レイテンシーの急増、ロックアップなど。

最適化とトレードオフを明確に示してください。パフォーマンス、メモリ消費量、スタックの占有領域、またはバイナリサイズの改善を主張する場合は、その根拠となる数値を含めてください。ただし、明らかでないコストについても説明する必要があります。通常、最適化は無料ではありませんが、CPU、メモリ、可読性の間のトレードオフ、またはヒューリスティクスにおいては異なるワークロード間のトレードオフが生じます。最適化の予想されるデメリットを説明することで、レビュワーがコストと利益を比較できるようにしてください。

問題が明確になったら、技術的な詳細をもとに実際にどのような対処をしているかを英語で説明してください。レビュワーがコードが意図した通りに動作しているかを確認するためには、この説明が重要です。

Linuxのソースコード管理システムに簡単に取り込むことができる形式でパッチの説明を書くと、メンテナから感謝されます。 git「コミットログ」として。 明示的なIn-Reply-Toヘッダー.

1つの問題のみをパッチで解決してください。説明が長くなる場合、それはおそらくパッチを分割する必要があるサインです。参照： 変更点を分離してください.

パッチまたはパッチシリーズを送信または再送信する際には、完全なパッチの説明とその正当性を含めてください。パッチ（シリーズ）のバージョンN（シリーズ）であるとだけ述べるのではなく、サブシステムメンテナが以前のパッチバージョンや参照されたURLを参照してパッチの説明をパッチに含めるのを期待しないでください。つまり、パッチ（シリーズ）とその説明は自立している必要があります。これはメンテナとレビュワー双方にとって有益です。一部のレビュワーは以前のパッチバージョンをすら受け取っていない可能性があります。

変更点を命令形で説明してください。例：「xyzzyがfrotzを行うようにする」ではなく、「[このパッチ]がxyzzyをfrotzにする」や「[私は] xyzzyをfrotzにする」といった形で、コードベースに行動を指示するようにしてください。

ただし、外部リソースなしで説明が理解できるようにしてください。メーリングリストアーカイブやバグへのURLを提供するだけでなく、パッチが提出された際の議論の関連するポイントを要約してください。

特定のコミットを参照する場合、コミットのSHA-1 IDを参照するのではなく、コミットのワンライナー要約も含めてください。これにより、レビュワーがそのコミットについて何についてのものかを簡単に把握できます。例：

Bear in mind that, even if there is no collision with your six-character ID now, that condition may change five years from now.

If your patch fixes a bug in a specific commit, e.g. you found an issue using git bisect, please use the ‘Fixes:’ tag with the first 12 characters of the SHA-1 ID, and the one line summary. Do not split the tag across multiple lines, tags are exempt from the “wrap at 75 columns” rule in order to simplify parsing scripts. For example:

Fixes: 54a4f0239f2e ("KVM: MMU: make kvm_mmu_zap_page() return the number of pages it actually freed")

以下の git config settings can be used to add a pretty format for outputting the above style in the git log または git show commands:

[core]
        abbrev = 12
[pretty]
        fixes = Fixes: %h (\"%s\")

An example call:

$ git log -1 --pretty=fixes 54a4f0239f2e

変更点を分離してください¶

Separate each logical change into a separate patch.

For example, if your changes include both bug fixes and performance enhancements for a single driver, separate those changes into two or more patches. If your changes include an API update, and a new driver which uses that new API, separate those into two patches.

On the other hand, if you make a single change to numerous files, group those changes into a single patch. Thus a single logical change is contained within a single patch.

The point to remember is that each patch should make an easily understood change that can be verified by reviewers. Each patch should be justifiable on its own merits.

If one patch depends on another patch in order for a change to be complete, that is OK. Simply note “this patch depends on patch X” in your patch description.

When dividing your change into a series of patches, take special care to ensure that the kernel builds and runs properly after each patch in the series. Developers using git bisect to track down a problem can end up splitting your patch series at any point; they will not thank you if you introduce bugs in the middle.

If you cannot condense your patch set into a smaller set of patches, then only post say 15 or so at a time and wait for review and integration.

Style-check your changes¶

Check your patch for basic style violations, details of which can be found in Linux Kernelのコーディングスタイル. Failure to do so simply wastes the reviewers time and will get your patch rejected, probably without even being read.

レビューコメントに返信してください¶

レビュワーから、パッチを改善する方法についてのコメントが必ず入るでしょう。そのコメントは、あなたのメールに対する返信として届きます。これらのコメントに必ず返信しなければなりません。レビュワーを無視するのは、逆に無視される原因になります。コメントに直接、メールで返信するだけで十分です。コード変更に至らないコメントや質問については、次のレビュワーが状況を理解しやすくなるよう、コメントやチェンジログへの記載がほぼ確実に必要です。

レビュワーに変更内容を明確に伝え、時間の確保に感謝するようにしてください。コードレビューは消耗的な作業であり、レビュワーは時折イライラするかもしれません。それでも、問題点を丁寧に受け止め、丁寧に対応するようにしてください。

参照 Linux用メールクライアント情報 メールクライアントやメールリストのマナーについてのアドバイスがあります。

やる気を失わないで、焦らないでください¶

変更を送信した後は、忍耐強く待つようにしてください。レビュワーは忙しい人々であり、すぐにあなたのパッチに手を付けられない場合があります。

かつてはパッチがコメントなしに消え去ってしまうことがありましたが、現在では開発プロセスがよりスムーズに進んでいます。1週間程度でコメントが届くのが普通ですが、届かない場合は、正しい場所にパッチを送信したか確認してください。再送信またはレビュワーへのリマインドを行う際は、少なくとも1週間は待つようにしてください。繁忙期（マージウィンドウなど）にはさらに時間がかかる場合があります。

件名にPATCHを含める¶

Linusやlinux-kernelへのメールが多いため、件名に[PATCH]を付けるのが一般的な慣習です。これにより、Linusや他のカーネル開発者の方がパッチを他のメールディスカッションと区別しやすくなります。

git send-email 自動的にこれを実行します。

あなたの作業に署名する - 開発者認証書¶

特にパッチが複数のメンテナを通じてカーネルに吸収される場合、作業の追跡をより効率的に行うため、メールで回されるパッチに「署名」手続きを導入しました。

署名とは、パッチの説明の最後に記載されるシンプルな行で、そのパッチをあなたが作成したか、あるいはオープンソースパッチとして転送する権利があることを証明します。ルールは簡単です：以下の項目を認証できる場合は、署名を行ってください。

開発者認証書 1.1¶

このプロジェクトへの貢献を行うことで、私は以下を認証します：

  1. この貢献は私が作成したものであり、オープンソースライセンスに基づいて提出できる権利を持っています；または

  2. この貢献は、私が知る限り適切なオープンソースライセンスの下でカバーされており、そのライセンスに基づき、私がこの作業を変更して含む権利があることを示しています（私が異なるライセンスで提出を許可されている場合は除く）。その記載はファイル内で示されています；または

  3. この貢献は、他の人が（a）、（b）、または（c）を認証した上で私に直接提供されたものであり、私はこれを変更していません。

  4. 私はこのプロジェクトと貢献が公開されていることを理解し、同意します。貢献の記録（含む私が提出したすべての個人情報、包括して私の署名）は永久に保持され、このプロジェクトまたは関与するオープンソースライセンスに従って再配布されることがあります。

その場合は、以下の行を追加します：

Signed-off-by: Random J Developer <random@developer.example.org>

実名を使用してください（ペンネームや匿名での貢献はできません）。この処理は、以下のツールを使用すれば自動的に行われます： git commit -s.

一部の人々は、最後に追加タグを付けます。これらは現時点では無視されますが、内部の会社プロセスを示すか、署名に関する特別な詳細を指すためにこれを行うことができます。

Acked-by:、Cc:、Co-developed-by: の使用タイミング¶

Signed-off-by: ラベルは、署名者がパッチの開発に関与したか、またはパッチの配信経路に含まれていたことを示します。

パッチの準備または処理に直接関与していないが、その承認を示して記録したい人物は、パッチの変更履歴に Acked-by: 行を追加してもらうことができます。

メンテナは、そのコードを貢献したり転送したりしなかった場合でも、Acked-by: をよく使用します。

Acked-by: は Signed-off-by: ほど正式ではありません。これは、確認者がパッチを確認し承認したことを記録するものです。そのため、パッチマージャーは、確認者の「よろしいです」という確認を手動で Acked-by: に変換することがあります（ただし、明示的な確認を求めるのが通常より望ましいです）。

Acked-by: はパッチ全体の承認を必ずしも示しません。例えば、パッチが複数のサブシステムに影響し、一つのサブシステムメンテナから Acked-by: が得られた場合、これはそのメンテナのコードに影響する部分のみの承認を示します。ここでは判断が必要です。不明な点がある場合は、メールアーカイブの元の議論を参照してください。

ある人物がパッチのコメントを提示する機会があったが、実際にコメントを提供していない場合、オプションでパッチにタグを追加できます。これは、タグを追加する際に人物の明示的なアクションが不要な唯一のタグです。ただし、このタグはその人物がパッチにコピーされたことを示すものであり、関係者を議論に含めたことを記録します。 Cc: コラボレーションによる開発者: は、パッチが複数の開発者によって共同で作成されたことを示します。これは、From: タグで属性が割り当てられた著者以外にも、複数の人物が単一のパッチに貢献したことを記載するためのものです。コラボレーションによる開発者: は著者を示すため、必ず関連する共同著者のSigned-off-by: が直後に続きます。標準的なサインオフ手順が適用され、Signed-off-by: タグの順序はパッチの時系列的な履歴を可能な限り反映する必要があります（From: タグまたはコラボレーションによる開発者: タグを通じて著者が割り当てられた場合も含む）。特に、最後のSigned-off-by: はパッチを送信した開発者のものでなければなりません。

From: タグは、メールヘッダーのFrom: 行に記載された著者と同一の人物（およびメールアドレス）である場合、オプションです。

From: タグは、メールヘッダーのFrom: 行に記載された著者と同一の人物（およびメールアドレス）である場合、オプションです。

From: 著者によって送信されたパッチの例:

<changelog>

Co-developed-by: First Co-Author <first@coauthor.example.org>
Signed-off-by: First Co-Author <first@coauthor.example.org>
Co-developed-by: Second Co-Author <second@coauthor.example.org>
Signed-off-by: Second Co-Author <second@coauthor.example.org>
Signed-off-by: From Author <from@author.example.org>

Co-developed-by: 著者によって送信されたパッチの例:

From: From Author <from@author.example.org>

<changelog>

Co-developed-by: Random Co-Author <random@coauthor.example.org>
Signed-off-by: Random Co-Author <random@coauthor.example.org>
Signed-off-by: From Author <from@author.example.org>
Co-developed-by: Submitting Co-Author <sub@coauthor.example.org>
Signed-off-by: Submitting Co-Author <sub@coauthor.example.org>

Reported-by:、Tested-by:、Reviewed-by:、Suggested-by: および Fixes: の使用方法¶

Reported-by: タグは、バグを発見して報告した人物に貢献を記載し、今後も同様の支援を引き出すことを目指します。注意点として、バグがプライベートで報告された場合は、Reported-by: タグを使用する前に許可を得ることが必要です。

Tested-by: タグは、パッチが特定の環境で成功裏にテストされたことを示します。これはメンテナにテストが行われたことを通知し、今後のパッチのテスト者を特定する手段を提供し、テスト者に貢献を記載します。

Reviewed-by: は、レビューが行われ、レビューラーの声明に従ってパッチが受け入れ可能であることを示します。

レビューラーの監督声明¶

Reviewed-by: タグを提供することにより、私は以下を表明します:

  1. 私はこのパッチを技術的にレビューし、その適切性とメインラインカーネルへの導入準備状態を評価しました。

  2. パッチに関する問題、懸念、または質問はすべて送信者にフィードバックされ、私は私のコメントに対する送信者の応答に満足しています。

  3. この投稿には改善点があるかもしれませんが、現在のところ、(1) カーネルへの有益な変更であり、(2) 既知の問題が含まれていないため、採用に反対する理由がありません。

  4. 私はこのパッチを検討し、信頼できると判断していますが、（明示的に他で記載されていない限り）このパッチが目的を達成するか、特定の状況で正常に動作するかについての保証や保証は一切行いません。

Reviewed-by ラベルは、パッチがカーネルへの適切な変更であり、重大な技術的問題が残っていないと主張する意見表明です。関心のあるレビュワー（作業を実施した人）がパッチに Reviewed-by ラベルを付与できます。このラベルはレビュワーへの貢献を示し、メンテナにパッチのレビューアクセス度を伝えるためのものです。レビュワーが該当分野を理解し、丁寧なレビューアクセスを実施している場合、Reviewed-by ラベルはあなたのパッチがカーネルに採用される可能性を高める傾向があります。

Tested-by および Reviewed-by ラベルは、メールリストからテスト者またはレビュワーによって受け取った後、著者が次のバージョンを送信する際、該当するパッチに追加する必要があります。ただし、パッチが次のバージョンで大幅に変更された場合、これらのラベルはもはや適用されなくなり、削除する必要があります。通常、誰かの Tested-by または Reviewed-by ラベルを削除する際は、パッチの変更履歴にその削除を記載する必要があります（'—'セパレータの後ろに記載）。

Suggested-by: ラベルは、パッチのアイデアが特定の人物によって提案されたことを示し、その人物への貢献を記録します。注意点として、報告者の許可なしにこのラベルを追加しないでください。特に、アイデアが公開フォーラムで投稿されていない場合。ただし、アイデアの報告者に丁寧に貢献を記録すれば、彼らが今後また協力してくれる可能性があります。

Fixes: ラベルは、パッチが以前のコミットで発生した問題を修正していることを示します。これにより、バグの起源を簡単に特定でき、バグ修正のレビューを支援します。このラベルはまた、安定版カーネルチームがどの安定版カーネルにあなたの修正を適用すべきかを判断するのにも役立ちます。これは、パッチがバグを修正していることを示すための推奨方法です。参照 変更内容を説明してください。 詳細についてはこちら。

標準的なパッチフォーマット¶

このセクションでは、パッチ自体のフォーマットについて説明します。注意点として、パッチをリポジトリに保存している場合でも、 git 適切なパッチフォーマットを得るために git format-patchを使用できます。ただし、ツールが必要なテキストを自動生成することはできませんので、以下の指示を必ず読みましょう。

標準的なパッチの件名は次のとおりです:

Subject: [PATCH 001/123] subsystem: summary phrase

標準的なパッチの本文には以下の要素が含まれます:

  • A from パッチの著者を指定する行、その後に空行（パッチを送信する人物が著者でない場合にのみ必要）。

  • 説明の本文で、改行を75文字に制限して記述し、このパッチを説明するための永続的な変更履歴にコピーされます。

  • 空行。

  • 以下の Signed-off-by: 上記で説明した行が変更履歴にも含まれます。

  • パッチを識別するマーカー行で、単に ---.

  • 変更履歴に含めない追加コメント。

  • 実際のパッチ（diff 出力）。

件名のフォーマットにより、メールを件名でアルファベット順に並べる作業が非常に簡単です。ほぼすべてのメールリーダーがこの機能をサポートしており、シーケンス番号がゼロパディングされているため、数字とアルファベットの並べ順が一致します。

以下の subsystem メールの件名には、パッチが適用されるカーネルの特定の領域またはサブシステムを明示する必要があります。

以下の summary phrase メールの件名には、そのメールに含まれるパッチの内容を簡潔に説明する必要があります。ただし、 summary phrase ファイル名としては使用しないでください。同じ summary phrase をパッチシリーズ（複数の関連パッチを順序付きで含む系列）内のすべてのパッチで使用しないでください。 patch series 順序付きの系列は、複数の関連パッチを順序付きで含むものです。

あなたのメールの summary phrase は、そのパッチのグローバルに一意な識別子になります。これは永続的な変更履歴にまで伝播します。この git は、後述の開発者間の議論でパッチを参照する際に使用される可能性があります。人々はこの summary phrase を検索して、そのパッチに関する議論を読むでしょう。また、2〜3か月後、ツールなどを使って数千のパッチを確認する際、人々が最初に見る情報もこの summary phrase です。 gitk または git log --oneline.

これらの理由から、 summary は70〜75文字以内に抑え、パッチが変更する内容と、なぜ必要なのかを記述する必要があります。簡潔かつ説明的な表現をバランスよく行うのは難しいですが、これは良質なサマリーの役割です。

以下の summary phrase は角括弧で囲まれたタグで前につけることができます：「Subject: [PATCH <tag>…] <summary phrase>」。タグはサマリー表現の一部とは見なされず、パッチの扱い方を説明します。一般的なタグには、コメントへの応答で送信された複数バージョンのパッチを示すバージョン記述子（例：「v1, v2, v3」）や、コメントを求めるための「RFC」が含まれます。パッチシリーズに4つのパッチがある場合、個々のパッチは「1/4, 2/4, 3/4, 4/4」といった形式で番号付けされます。これにより、開発者がパッチの適用順序を理解し、シリーズ内のすべてのパッチを確認または適用したことを確認できます。

例としてのサブジェクトの例:

Subject: [PATCH 2/5] ext2: improve scalability of bitmap searching
Subject: [PATCH v2 01/27] x86: fix eflags tracking

以下の from メッセージ本文の最初の行にする必要があります。形式は以下の通りです:

From: パッチ作成者 <author@例.com>

以下の from 行は、パッチの著者として記載される人物を指定します。この from 行が存在しない場合、メールヘッダーから取得した From: 行が変更ログにおけるパッチ作成者を決定します。

説明本文は永続的なソースコード変更ログにコミットされるため、専門的な読者にとって意味のある内容にする必要があります。このパッチが解決する失敗の症状（カーネルログメッセージ、oopsメッセージなど）を含めると、コミットログを検索している人にとって非常に有用です。コンパイルエラーを修正するパッチの場合、すべてのコンパイルエラーを含む必要はありません。検索している人がパッチを見つけやすい程度の情報があれば十分です。 summary phrase同様に、簡潔かつ説明的であることが重要です。

以下の --- マーカー行はパッチ処理ツールに変更ログメッセージの終わりを示す重要な役割を果たします。

マーカー行の後の追加コメントは、パッチ処理ツールが変更ログメッセージの終わりを認識できるようにするためのものです。 --- マーカー行の後の追加コメントは、 diffstatを示すために用いられます。 diffstat は特に大規模なパッチに有用です。 patch changelogs その他のコメントは、特定の時点やメンテナ専用の情報であり、永続的な変更ログには不適切な場合もあります。このようなコメントの例は、

v1とv2のパッチバージョン間の変更点を説明するものです。 diffstat after the --- マーカーを含める場合は、 diffstat オプション -p 1 -w 70 を使用してください。これにより、ファイル名はカーネルソースツリーのトップから表示され、水平スペースを多く使用せず（80列以内に収まるように、インデントを加えることも可能）、ファイル名の一覧が表示されます。（git はデフォルトで適切なdiffstatsを生成します。）

正しいパッチ形式についての詳細は、以下の参考文献で説明しています。

明示的なIn-Reply-Toヘッダー¶

パッチにIn-Reply-To:ヘッダーを手動で追加する（例： git send-emailを使用する場合）ことで、パッチと過去の関連するディスカッションを関連付けることができます。例えば、バグ修正をバグレポートのメールと関連付けることができます。ただし、複数のパッチシリーズを扱う場合、In-Reply-To:でシリーズの古いバージョンをリンクするのは一般的に避けるべきです。これにより、メールクライアントでパッチの複数バージョンが管理不能な参照の森になってしまう可能性があります。リンクが必要な場合は、 https://lkml.kernel.org/ リダイレクター（例：カバーメール本文内で）を使用して、パッチシリーズの以前のバージョンにリンクできます。

ベースツリー情報の提供¶

他の開発者があなたのパッチを受け取りレビューを開始する際、彼らがツリーの履歴でどこにあなたの作業を配置すべきかを知ることはしばしば役立ちます。これは、マインテナーがレビューを開始する前に、あなたの提出物の品質を確認するために一連のテストを実行しようとする自動化されたCIプロセスにおいて特に役立ちます。

ゼロ長または1要素の配列を末尾メンバとして含む構造体で git format-patch パッチを生成する際には、 --base フラグを使用することで、自動的にベースツリーの情報をサブミッションに含めることができます。このオプションを最も簡単かつ便利に使用する方法はトピカルブランチを使用することです：

$ git checkout -t -b my-topical-branch master
Branch 'my-topical-branch' set up to track local branch 'master'.
Switched to a new branch 'my-topical-branch'

[perform your edits and commits]

$ git format-patch --base=auto --cover-letter -o outgoing/ master
outgoing/0000-cover-letter.patch
outgoing/0001-First-Commit.patch
outgoing/...

を編集モードで開くと、その下部に outgoing/0000-cover-letter.patch トラILERが表示され、レビュアーおよびCIツールに十分な情報を提供し、 base-commit: を適切に実行するための情報が得られます。これにより、コンフリクトについて心配する必要がありません： git am このオプションについての詳細情報については

$ git checkout -b patch-review [base-commit-id]
Switched to a new branch 'patch-review'
$ git am patches.mbox
Applying: First Commit
Applying: ...

詳しくは以下をご参照ください。 man git-format-patch をご覧ください。

注意

以下の --base この機能はgitバージョン2.9.0から導入されました。

gitを使用してパッチをフォーマットしていない場合でも、同じ base-commit トラILERを追加することで、あなたの作業がベースとなるツリーのコミットハッシュを示すことができます。これをカバー手紙またはシリーズの最初のパッチに追加し、 --- 行の下またはすべての他のコンテンツの一番最後、あなたのメール署名の直前に配置する必要があります。

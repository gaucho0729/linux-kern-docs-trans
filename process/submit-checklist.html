Linux Kernelパッチ提出チェックリスト¶

開発者が自分のカーネルパッチの送信がより速く受け入れられるようにするためには、以下の基本的なことを行ってください。

これらは、以下に記載されているドキュメンテーションに加えて、さらに追加されたものです。 パッチの送信: コードをカーネルに取り込むためのエッセンシャルガイド 他の場所でも、Linux Kernel パッチの送信に関するドキュメンテーションに加えて

  1. 必要な機能を使用する場合は、その機能を定義または宣言しているファイルを #include してください。他のヘッダーファイルが自動的に読み込むのを依存しないでください。

  2. クリーンにビルドされる：

  1. 適用可能なか、変更された CONFIG オプション =y, =m, and =n・なし gcc 警告/エラー、リンカーウォーニング/エラーがありません。

  2. パスします allnoconfig, allmodconfig

  3. 使用時にビルドが成功します O=builddir

  4. ドキュメンテーション/変更のすべてが新しい警告/エラーなしでビルド成功します。使用して make htmldocs または make pdfdocs ビルドを確認し、問題を修正してください。

  1. ローカルのクロスコンパイルツールや他のビルドファームを使用して、複数のCPUアーキテクチャでビルドされます。

  2. ppc64はクロスコンパイルの確認に適したアーキテクチャです。これは64ビットの量を扱う際に unsigned long 64ビットの量を扱う際に

  3. スタイルの詳細については、以下に記載されている通り、パッチをチェックしてください。 Linux Kernelのコーディングスタイル。提出前にパッチスタイルチェッカーで簡単な違反を確認してください（scripts/checkpatch.pl）。あなたのパッチに残るすべての違反について説明できる必要があります。

  4. 新しいか、変更された CONFIG オプションは設定メニューを混乱させず、ドキュメントに記載された例外基準に該当しない限りデフォルトでオフになります。 Documentation/kbuild/kconfig-language.rst メニュー属性: デフォルト値。

  5. すべての新しい Kconfig オプションにはヘルプテキストがあります。

  6. 関連する Kconfig 組み合わせについて慎重にレビューされています。テストで正しい結果を得るのは非常に困難です – ここで脳の力が重要です。

  7. sparseでクリーンにチェックしてください。

  8. Use make checkstack 見つかった問題を修正してください。

    注意

    checkstack 問題を明示的に指摘しませんが、スタックに512バイト以上使用する関数は変更の候補です。

  9. 含める kernel-doc グローバルなカーネルAPIをドキュメント化します。(静的関数には不要ですが、それもOKです。) 使用して make htmldocs または make pdfdocs をチェックして kernel-doc 問題を修正してください。

  10. テストされています CONFIG_PREEMPT, CONFIG_DEBUG_PREEMPT, CONFIG_DEBUG_SLAB, CONFIG_DEBUG_PAGEALLOC, CONFIG_DEBUG_MUTEXES, CONFIG_DEBUG_SPINLOCK, CONFIG_DEBUG_ATOMIC_SLEEP, CONFIG_PROVE_RCU および CONFIG_DEBUG_OBJECTS_RCU_HEAD すべて同時に有効化された場合

  11. ビルドおよび実行時テストが行われています。有効化と無効化の両方で CONFIG_SMP および CONFIG_PREEMPT.

  1. すべてのコードパスが、すべてのlockdep機能が有効な状態でテストされています。

  2. すべての新しい /proc エントリは以下に記載されています Documentation/

  3. すべての新しいカーネル起動パラメータは以下に記載されています Documentation/admin-guide/kernel-parameters.rst.

  4. すべての新しいモジュールパラメータは以下のようにドキュメントされています。 MODULE_PARM_DESC()

  5. すべての新しいユーザースペースインターフェースは以下のようにドキュメントされています。 Documentation/ABI/のみ Documentation/ABI/README 詳しくは。ユーザースペースインターフェースを変更するパッチは、CCで送信する必要があります。 linux-api@vger.kernel.org.

  6. すべてが通るか確認してください。 make headers_check.

  7. 少なくともslabおよびページ割当失敗のインジェクションによるチェックが行われています。詳しくは Documentation/fault-injection/.

    新しいコードが大幅な場合、サブシステム固有のフォールトインジェクションの追加が適切である可能性があります。

  8. 新たに追加されたコードは、コンパイルされており、 gcc -W (使用 make EXTRA_CFLAGS=-W)。これにより多くのノイズが発生しますが、警告「符号付きと符号なしの比較」などのバグを検出するのに役立ちます。

  9. マージ後、-mmパッチセット内の他のキューイングされたパッチやVM、VFS、その他のサブシステムにおける変更と依然として動作するかテストされています。

  10. すべてのメモリーバリアー {たとえば、 barrier(), rmb(), wmb()} は、ソースコード内でその動作と理由を説明するコメントが必要です。

  11. パッチで任意のioctlが追加された場合、同時に以下のファイルも更新する必要があります。 Documentation/userspace-api/ioctl/ioctl-number.rst.

  12. あなたの変更したソースコードが以下の関連するカーネルAPIや機能に依存しているか、使用している場合、 Kconfig シンボルを使用している場合、関連するシンボルを無効にして複数のビルドをテストする必要があります。 Kconfig シンボルを無効にして、 =m (そのオプションが利用可能であれば) [同時にすべてを無効にはしない、さまざまな/ランダムな組み合わせのみ]:

    CONFIG_SMP, CONFIG_SYSFS, CONFIG_PROC_FS, CONFIG_INPUT, CONFIG_PCI, CONFIG_BLOCK, CONFIG_PM, CONFIG_MAGIC_SYSRQ, CONFIG_NET, CONFIG_INET=n (ただし後述の CONFIG_NET=y).

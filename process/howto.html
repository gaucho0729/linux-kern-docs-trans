Linuxカーネル開発のHOWTO¶

これはこのトピックに関するすべてを網羅したドキュメントです。Linux kernel developerになる方法や、Linux kernel開発コミュニティと協力して作業する方法についての説明を含んでいます。技術的なkernelプログラミングの詳細については含んでいませんが、それに関する正しい方向へと導く情報を提供します。

このドキュメント内の情報が古くなってしまった場合は、このファイルのメンテナにパッチを送ってください。メンテナの名前はこのドキュメントの最後に記載されています。

はじめに¶

Linux kernel developerになることを学びたいですか？それともマネージャーから「このデバイス用のLinuxドライバを書け」と指示されたのでしょうか？このドキュメントの目的は、この目標を達成するために必要なすべての知識を教えることです。そのためには、必要なプロセスを説明し、コミュニティと協力するためのヒントも提供します。また、コミュニティがどのように動作するかについてもいくつかの理由を説明します。

カーネルは主にC言語で書かれ、一部のアーキテクチャ依存部分はアセンブリ言語で書かれています。カーネル開発にはC言語に関する深い理解が必要です。アセンブリ言語（どのアーキテクチャでも）は、低レベルの開発を行う予定がある場合を除けば必要ありません。これらは堅実なC言語の教育や経験とは置き換えられませんが、参考書として以下の本が役立ちます：

  • 「The C Programming Language」by Kernighan and Ritchie [Prentice Hall]

  • 「Practical C Programming」by Steve Oualline [O’Reilly]

  • 「C: A Reference Manual」by Harbison and Steele [Prentice Hall]

カーネルはGNU CとGNUツールチェーンを使用して書かれています。ISO C89標準に準拠していますが、標準には含まれていない拡張機能もいくつか使用しています。カーネルは標準Cライブラリに依存せず、スタンドアロンのC環境として構築されているため、一部のC標準はサポートされていません。任意の長整数の割り算や浮動小数点演算は許可されていません。カーネルがツールチェーンや使用する拡張機能について持つ仮定を理解するのは時折難しく、残念ながらこれらについての明確なリファレンスは存在しません。詳しくはgccのinfoページをご確認ください（info gcc)

既存の開発コミュニティとどのように協力するかを学ぶことを試みていることを忘れないでください。これは多様な人々のグループで、コーディング、スタイル、手順の高い基準を維持しています。これらの基準は、このような大規模で地理的に広範なチームが効果的に運用する方法を経年累積して作成されてきました。これらの基準はよく文書化されていますので、事前にできるだけ多くの情報を学ぶようにしてください。人々があなたの会社のやり方やあなたのスタイルに合わせて調整するのを期待しないでください。

法的問題¶

LinuxカーネルソースコードはGPLの下でリリースされています。詳しくはソースツリーのメインディレクトリにある COPYING ファイルをご覧ください。Linuxカーネルのライセンス規則と使用方法 SPDX ソースコード内の識別子は以下で説明されています Linuxカーネルライセンス規則。ライセンスに関する質問がさらにございましたら、弁護士にご相談ください。Linuxカーネルメーリングリストで質問しないでください。メーリングリストに登録されている人々は弁護士ではありませんので、法的問題に関するご意見には頼らないでください。

GPLに関する一般的な質問と回答については、以下をご覧ください:

https://www.gnu.org/licenses/gpl-faq.html

ドキュメンテーション¶

Linuxカーネルソースツリーには、カーネルコミュニティとやりとりするための非常に価値のあるドキュメントが多数含まれています。カーネルに新機能が追加される際には、その機能の使い方を説明する新しいドキュメントファイルも追加することをお勧めします。カーネットの変更がユーザー空間に公開するインターフェースを変更する場合、変更内容をマニュアルページのメンテナである mtk.manpages@gmail.comに情報やパッチを送信し、リストにCCしてください linux-api@vger.kernel.org.

カーネルソースツリーに含まれる、読み物として必須のファイルの一覧:

Documentation/admin-guide/README.rst

このファイルはLinuxカーネルの簡単な背景と、カーネルを構成・ビルドするための必要な手順を説明しています。カーネルに初めて触れる人々はここから始めるべきです。

Documentation/process/changes.rst

このファイルは、カーネルを成功裏に構築・実行するために必要なソフトウェアパッケージの最低限のバージョンを一覧しています。

Documentation/process/coding-style.rst

これはLinuxカーネルのコーディングスタイルと、その背景にある根拠を説明しています。すべての新規コードはこのドキュメントのガイドラインに従う必要があります。ほとんどのメンテナはこれらのルールに従っていない場合、パッチを受理しない傾向があります。また、多くの人々は正しいスタイルでないコードをレビューしません。

Documentation/process/submitting-patches.rst および Documentation/process/submitting-drivers.rst

これらのファイルは、パッチを作成し送信する方法を詳細に説明しており、以下のような内容を含みます（ただし、これらに限定されるわけではありません）:

  • メール本文

  • メールフォーマット

  • 送信先

これらのルールを守ることで成功を保証するわけではありません（すべてのパッチは内容やスタイルに対して厳格な検証を受けるため）が、ルールを守らないとほぼ常に失敗します。

適切なパッチ作成方法についての他の優れた説明は以下の通りです:

『The Perfect Patch』

https://www.ozlabs.org/~akpm/stuff/tpp.txt

『Linux kernel patch submission format』

https://web.archive.org/web/20180829112450/http://linux.yyz.us/patch-format.html

Documentation/process/stable-api-nonsense.rst

このファイルは、カーネル内に安定したAPIを持たないという意図的な決定の背景にある論理を説明しており、以下の内容を含みます:

  • サブシステムのシムレイヤー（互換性のため？）

  • ドライバのオペレーティングシステム間での移植性

  • カーネルソースツリー内の急速な変更を抑制する（または防止する）

このドキュメントはLinux開発の哲学を理解する上で極めて重要であり、他のオペレーティングシステムでの開発経験を持つ人々にとっても非常に重要です。

Documentation/admin-guide/security-bugs.rst

Linuxカーネル内でセキュリティ上の問題を発見した場合は、このドキュメントに記載されている手順に従ってカーネル開発者に通知し、問題を解決するお手伝いをしましょう。

Documentation/process/management-style.rst

このドキュメントはLinuxカーネルメンテナがどのように運用しているか、およびそのメソッド論理の共有される理念を説明しています。カーネル開発に初めて触れる人（または単に興味がある人）にとって非常に重要な読み物であり、カーネルメンテナの特異な行動に関する一般的な誤解や混乱を解消します。

Documentation/process/stable-kernel-rules.rst

このファイルは、安定版カーネルリリースのルールを説明し、これらのリリースに変更を含めるための手順を示しています。

Documentation/process/kernel-docs.rst

カーネル開発に関連する外部ドキュメントの一覧です。インカーネルドキュメント内で見つからない場合は、このリストをご参照ください。

Documentation/process/applying-patches.rst

パッチとは何か、そしてカーネルのさまざまな開発ブランチにパッチを適用する方法を説明する良い入門書です。

カーネルには、ソースコード自体やReStructuredTextマークアップ（ReST）から自動生成可能なドキュメントが多数存在します。このドキュメントには、インカーネルAPIの完全な説明と、ロック処理のルールが含まれます。

すべてのこのようなドキュメントは、以下のコマンドを実行することでPDFまたはHTML形式で生成できます:

make pdfdocs
make htmldocs

main kernel source directory（メインカーネルソースディレクトリ）からそれぞれ生成されます。

ReSTマーキアップを使用したドキュメントはDocumentation/outputに生成されます。また、LaTeXおよびePub形式にも生成可能です。

make latexdocs
make epubdocs

カーネル開発者になること¶

Linuxカーネル開発について何も知らない場合は、Linux KernelNewbiesプロジェクトをご覧ください：

https://kernelnewbies.org

これは、ほぼすべての基本的なカーネル開発に関する質問に答えてくれる有益なメーリングリストを含んでいます（過去にすでに答えが提供されている質問については、まずアーカイブを検索してください）。また、リアルタイムで質問を質問できるIRCチャネルや、Linuxカーネル開発を学ぶために役立つ多くの有益なドキュメントも含まれています。

このウェブサイトには、コードの構造、サブシステム、および現在のプロジェクト（インツリーおよびアウトツリーの両方）に関する基本的な情報が含まれています。また、カーネルのコンパイル方法やパッチの適用方法などの基本的なロジスティック情報も説明しています。

どの場所から始めるか分からないが、カーネル開発コミュニティに参加するために何かタスクを探している場合は、Linux Kernel Janitor’sプロジェクトをご覧ください：

https://kernelnewbies.org/KernelJanitors

これは、始めるのに適切な場所です。Linuxカーネルソースツリー内でクリーンアップおよび修正が必要な相対的に簡単な問題の一覧が記載されています。このプロジェクトを担当する開発者と協力しながら作業することで、自分のパッチをLinuxカーネルツリーに取り込む基本的な手順を学ぶことができ、既にアイデアがない場合でも、次に何をすべきかの方向を示される可能性があります。

Linuxカーネルコードに実際に変更を加える前に、そのコードがどのように動作するかを理解することが必須です。この目的には、直接コードを読むことが最も効果的です（ほとんどの複雑な部分はコメントで丁寧に説明されています）。専門的なツールを活用するのも良いでしょう。特に推奨されるツールの一つは、Linux Cross-Referenceプロジェクトで、ソースコードを自己参照型のインデックス付きウェブページ形式で表示できます。カーネルコードの最新のリポジトリは以下にあります：

https://elixir.bootlin.com/

開発プロセス¶

Linuxカーネル開発プロセスは現在、いくつかの異なるメインカーネル「ブランチ」および多くの異なるサブシステム固有のカーネルブランチから構成されています。これらの異なるブランチは：

  • Linusのメインラインツリー

  • 複数のメジャーバージョンを持つさまざまな安定ツリー

  • サブシステム固有のツリー

  • linux-next統合テストツリー

メインラインツリー¶

メインラインツリーはLinus Torvaldsによって維持されており、以下にあります https://kernel.org またはリポジトリ内にもあります。その開発プロセスは以下の通りです：

  • 新しいカーネルがリリースされると、2週間の期間が開かれ、この期間中、メンテナはLinusに大きな変更（diff）を提出できます。通常、これらのパッチはすでにlinux-nextに数週間含まれているものです。大きな変更を提出する推奨方法はgit（カーネルのソース管理ツール）ですが、情報は以下のURLで確認できます。 https://git-scm.com/) ただし、 plain patches（通常のパッチ）も問題ありません。

  • 2週間が経過した後、-rc1カーネルがリリースされ、新しいカーネルが可能な限り安定したものになるように焦点が当てられます。この時点でほとんどのパッチはリグレッション（不具合）の修正になります。常に存在していたバグはリグレッションとはみなされないため、重要性が高い場合のみこのような修正を推奨します。注意してください。-rc1以降でもgitを用いてLinusにパッチを送信できますが、パッチは公開メーリングリストにも送信してレビューを受ける必要があります。

  • Linusが現在のgitツリーがテストに適した状態にあると判断した時点で、新しい-rcがリリースされます。目標は毎週新しい-rcカーネルをリリースすることです。

  • プロセスはカーネルが「準備完了」とみなされるまで続き、このプロセスは約6週間かかるとされています。

Andrew Mortonがlinux-kernelメーリングリストで書いたコメントを紹介します。

「誰もカーネルのリリース時期を知り得ない。なぜなら、リリースは予定されたタイムラインではなく、不具合の状態によって決まるからである。」

複数のメジャーバージョンを持つさまざまな安定ツリー¶

3部バージョンを持つカーネルは-stableカーネルです。これらは、特定の主要なメインラインリリースで発見されたセキュリティ問題や重大なリグレッションに対する相対的に小さな修正を含みます。主要な安定版シリーズの各リリースでは、バージョン番号の3番目の部分がインクリメントされ、最初の2つの部分は変わりません。

最新の安定版カーネルを希望し、開発/実験版のテストに参加したくないユーザー向けに推奨されるブランチです。

安定ツリーは「安定」チーム <stable@vger.kernel.org＞ によって維持され、必要に応じてリリースされます。通常のリリース期間は約2週間ですが、緊急の問題がなければ長くなることがあります。セキュリティ関連の問題は、リリースをほぼ即座に引き起こすことがあります。

ファイル Linux -stableリリースについて知りたいすべての情報 カーネルツリーのドキュメントには、-stableツリーに許容される変更の種類やリリースプロセスについての詳細が記載されています。

サブシステム固有のツリー¶

さまざまなカーネルサブシステムのメンテナーや、多くのカーネルサブシステム開発者も、ソースリポジトリで現在の開発状況を公開しています。これにより、他の開発者もカーネルのさまざまな分野での進捗を確認できます。開発が急速に進む分野では、開発者にそのサブシステムのカーネルツリーをベースにした投稿を依頼し、投稿と既存の進行中の作業との間の競合を避けることが求められます。

これらのリポジトリの多くはgitツリーですが、他にもSCMが使用されている場合や、quiltシリーズとして公開されているパッチキューもあります。これらのサブシステムリポジトリのアドレスはMAINTAINERSファイルに記載されています。多くは以下のURLから閲覧可能です https://git.kernel.org/.

このようなサブシステムツリーにパッチがコミットされる前に、メールリストでのレビューが行われます（以下で説明します）。いくつかのカーネルサブシステムでは、このレビュープロセスをpatchworkというツールで追跡しています。patchworkはパッチ投稿やコメント、リビジョンの表示を行うウェブインターフェースを提供し、メンテナーや開発者はパッチをレビュー中、承認、却下としてマークできます。これらのpatchworkサイトの多くは以下のURLにリストされています https://patchwork.kernel.org/.

linux-next統合テストツリー¶

サブシステムツリーのアップデートがメインラインツリーにマージされる前に、統合テストが必要です。このため、ほぼ毎日サブシステムツリーが引き込まれる特別なテストリポジトリがあります:

https://git.kernel.org/?p=linux/kernel/git/next/linux-next.git

このように、linux-nextは次のマージ期間にメインラインカーネルに組み込まれる内容の概要を示しています。冒険心のあるテスト者は、linux-nextを実時間でテストすることを歓迎しています。

バグ報告¶

https://bugzilla.kernel.org Linuxカーネル開発者がカーネルのバグを追跡する場所です。ユーザーはこのツールで見つかったすべてのバグを報告することを推奨しています。カーネルバグザラの使用方法についての詳細は以下のURLをご覧ください:

https://bugzilla.kernel.org/page.cgi?id=faq.html

ファイル admin-guide/reporting-bugs.rst メインカーネルソースディレクトリ内には、カーネルバグを報告する際のテンプレートがあり、必要な情報の種類についても説明されています。

バグレポートの管理¶

他の人が報告したバグを修正することで、あなたのハッキングスキルを実践する最良の方法の一つです。これによりカーネルの安定性が向上し、現実世界の問題を解決するスキルを学ぶことができ、他の開発者もあなたの存在を認識します。バグ修正は他の開発者から評価されやすく、多くの人が他人のバグを修正する時間を使うことを好まないため、最も効果的な貢献方法の一つです。

既に報告されたバグレポートを処理するには、以下のURLにアクセスしてください https://bugzilla.kernel.org.

メールリスト¶

上記のいくつかのドキュメントで説明されているように、コアのカーネル開発者たちは多くがLinux Kernel Mailing listに参加しています。リストへの登録や解除方法については以下に記載されています:

http://vger.kernel.org/vger-lists.html#linux-kernel

メールリストのアーカイブは、ウェブ上のさまざまな場所で公開されています。これらのアーカイブを検索するには検索エンジンをご利用ください。例えば:

http://dir.gmane.org/gmane.linux.kernel

リストに投稿する前に、投稿したいトピックに関するアーカイブを検索することをお勧めします。多くの詳細な議論はメールリストのアーカイブにのみ記録されています。

ほとんどの個々のカーネルサブシステムも、それらの開発活動を行うための別個のメールリストを持っています。これらのリストの詳細についてはMAINTAINERSファイルをご参照ください。

多くのリストはkernel.orgでホストされています。それらに関する情報は以下に記載されています:

http://vger.kernel.org/vger-lists.html

リストを使用する際は、良い行動規範を守るようにしてください。ちょっと冗談ぽいですが、以下のURLにはリスト（またはどのリストにも共通する）簡単なガイドラインがあります:

http://www.albion.com/netiquette/

複数人があなたのメールに返信すると、CC:リストの受信者欄がかなり長くなることがあります。誰かをCC:リストから無理やり削除しないようにし、リストアドレスだけに返信しないようにしてください。送信者からのメールとリストからのメールの両方を受信することに慣れておき、複雑なメールヘッダーでそれを調整しようとするのは避けましょう。

返信内容の文脈と出典を保持し、返信先の上部に「ジョン・カーネルハッカーが…書いた：」などの行を残し、各引用セクションの間に自分の意見を追加してください。メールの上部に直接書くのではなく、各引用の間に自分のコメントを加えるようにしてください。

メールにパッチを追加する場合は、必ず読みやすい平文テキストにしてください。以下の パッチの送信: コードをカーネルに取り込むためのエッセンシャルガイドに記載されている通りです。カーネル開発者たちは添付ファイルや圧縮されたパッチを扱うのを避けたいので、パッチの個々の行にコメントを加えることが必要です。そのためには、スペースやタブ文字を壊さないメールソフトを使用してください。最初のテストとして、自分自身にメールを送って、自分のパッチを自分で適用できるか確認してください。うまくいかない場合は、メールソフトを修正または変更してから再度試してください。

すべてにおいて、他のサブスクライバーへの敬意を忘れないようにしてください。

コミュニティとの協力¶

カーネルコミュニティの目標は、最高品質のカーネルを提供することです。パッチを受理申請する際は、技術的な優位性のみに基づいてレビューされます。したがって、あなたが期待すべきことは何でしょうか？

  • 批判

  • comments

  • 変更の依頼

  • 正当性の求め

  • 沈黙

ご注意ください。これはパッチをカーネルに取り込む過程の一部です。あなたのパッチに対して批判やコメントを受け入れ、技術的なレベルで評価し、その変更が必要かどうかを再考するか、それらの変更がなぜ必要でないのかを明確かつ簡潔に説明する必要があります。あなたの投稿に返信がない場合は、数日待って再度投稿してください。時折、大量の投稿の中から見逃されることがあります。

避けなければならないことは何ですか？

  • あなたのパッチが疑問なく受け入れられることを期待しないでください

  • 防御的になる

  • コメントを無視する

  • 求められた変更を一切行わずパッチを再投稿する

技術的な最適解を求めているコミュニティでは、パッチの有益性について常に異なる意見があります。協力的で、アイデアをカーネルの枠組みに合わせて調整する姿勢が必要です。少なくとも、あなたのアイデアが価値があることを証明する準備があること。誤りを犯すことは問題ありませんが、正しい解決策に向かって努力する姿勢が求められます。

最初のパッチに対する返答が単に12項目の修正点のリストであることは普通のことです。これは ではありません あなたのパッチが受け入れられないことを意味せず、また ではありません あなた個人を対象としたものではありません。すべての指摘を受け入れ、問題を修正した上で再投稿してください。

カーネルコミュニティと企業構造の違い¶

カーネルコミュニティは、大多数の伝統的な企業開発環境とは働き方が異なります。以下の点を心がけることで問題を回避できます：

あなたの提案変更について良い表現は以下の通り：

  • 「複数の問題を解決します。」

  • 「2000行のコードを削除します。」

  • 「私が説明しようとしていることを説明するパッチです。」

  • 「5つの異なるアーキテクチャでテストしました…」

  • 「一連の小さなパッチです…」

  • 「典型的なマシンでのパフォーマンス向上…」

避けるべき悪い表現は以下の通り：

  • 「AIX/ptx/Solarisではこのように実施しており、だからこそ正しいのです…」

  • 「私は20年間このように実施しており、だからこそ…」

  • 「これは私の会社が利益を上げるために必要なものです」

  • 「これは私たちのエンタープライズ製品ラインのためにです」

  • 「私のアイデアを説明する1000ページの設計ドキュメントです」

  • 「私はこの作業に6か月間取り組んでいます…」

  • 「5000行のパッチです…」

  • 「現在の混乱をすべて再構築し、ここにあります…」

  • 「私は期限があり、このパッチを今すぐ適用する必要があります。」

カーネルコミュニティが伝統的なソフトウェアエンジニアリングの環境と異なる点の一つは、無顔なやり取りの性質です。メールやIRCを主なコミュニケーション手段として使用する利点の一つは、性別や人種に基づく差別が存在しないことです。Linuxカーネルの作業環境は、すべてがメールアドレスであるため、女性やマイノリティを歓迎しています。国際的な要素も公平性を高めるため、人物の名前から性別を推測することはできません。男性でもAndreaという名前で、女性でもPatという名前を持つことがあります。Linuxカーネルで働いた女性たちの多くは、ポジティブな経験を述べています。

英語に不慣れな人にとっては、言語の壁が問題になることがあります。メールリストでアイデアを適切に伝えられるには英語の習得が重要です。そのため、メールを送信前に英語として意味が通るか確認してください。

変更を分割してください¶

Linuxカーネルコミュニティは、一度に大量のコードを投下されることを喜んでいません。変更は適切に紹介され、議論され、小さな個々の部分に分割される必要があります。これは企業が通常行う作業とはほぼ逆のやり方です。提案は開発プロセスの早期段階で提示すべきです。これによりフィードバックを受けやすく、コミュニティが一緒に作業しているように感じさせ、単なる機能の受け皿として使われているわけではないと示せます。ただし、一度に50通のメールをメールリストに送信しないでください。パッチシリーズはほぼ常にその半分以下の規模に保つべきです。

変更を分割する理由は以下の通りです：

  1. 小さなパッチは、検証にかかる時間や労力が少なく、あなたのパッチが適用される可能性を高めます。5行程度のパッチは、管理者がほぼ一瞬で確認できます。しかし、500行のパッチは正しさを確認するのに数時間かかることがあります（パッチのサイズに比例して指数関数的に増加します）。

    小さなパッチは、何かがうまくいかなくなったときにデバッグを非常に容易にします。大きなパッチを適用後に壊れた場合を解釈するよりも、一つずつパッチを取り消す方がはるかに簡単です。

  2. 小さなパッチを送るだけでなく、送信前にパッチを再構成し、簡略化する（または単に順序を変える）ことも重要です。

カーネル開発者であるAl Viroからの比喩です：

数学の宿題を採点する教師を想像してみましょう。教師は、生徒が解決策に至るまでの試行錯誤を確認したくはなく、最も洗練された、最もエレガントな解答を確認したいのです。優れた生徒はこれを理解しており、最終的な解答が出るまで途中の作業を提出することはありません。

カーネル開発においても同じことが言えます。メンテナーやレビュワーは、問題解決の背後にある思考プロセスを確認したくはなく、シンプルでエレガントな解決策を確認したいのです。

エレガントな解決策を提示する一方で、コミュニティと協力して未完成の作業を議論するバランスを保つのは難しいかもしれません。そのため、作業の初期段階でフィードバックを得て改善を図るのも良いですが、変更を小さなブロックに分けて管理し、全体が完成していない現在でも受け入れられることを考慮する必要があります。

未完成のパッチを含めてインクルージョン（採用）を求めるのは受け入れられません。

変更の正当性を説明する¶

パッチを分割するだけでなく、Linuxコミュニティにこの変更を採用すべき理由を伝えることも非常に重要です。新機能は必要性と有用性が明確に示されなければなりません。

変更をドキュメント化する¶

パッチを送信する際は、メール本文に書かれた内容に特に注意を払ってください。この情報はパッチのChangeLog情報となり、すべての人にとって永久に公開されます。この本文はパッチを完全に説明し、以下の内容を含める必要があります：

  • 変更が必要な理由

  • パッチにおける全体的な設計アプローチ

  • 実装の詳細

  • テスト結果

これらすべての内容がどのように見えるべきかの詳細については、ドキュメントの「ChangeLog」セクションをご参照ください：

『The Perfect Patch』

https://www.ozlabs.org/~akpm/stuff/tpp.txt

Linuxカーネルへのパッチ適用¶

Original by:

Jesper Juhl, August 2005

注意

このドキュメントは非推奨です。ほとんどの場合、手動で適用するのではなく、Gitを使用する方が望ましいです。 patch manually

Linux Kernel Mailing Listでよく聞かれる質問の一つは、パッチをカーネルに適用する方法や、特定のツリー/ブランチ用のパッチを適用する際のベースとなるカーネルについてです。このドキュメントがこれを説明できるよう努めます。

パッチの適用と戻し方の説明に加え、さまざまなカーネルツリーについての簡単な説明（各ツリー用のパッチの適用方法の例も含む）も提供されています。

パッチとは何ですか？¶

パッチは、2つの異なるソースツリーのバージョン間の変更内容を表した小さなテキストドキュメントです。パッチは diff プログラム。

パッチを正しく適用するには、そのパッチが生成されたベースとなるバージョンと、パッチがソースツリーをどのバージョンに変更するかを知る必要があります。これらはパッチファイルのメタデータに含まれているか、ファイル名から推測可能でなければなりません。

パッチを適用または戻す方法は？¶

パッチを適用するには、 patch プログラムを使用します。patchプログラムは、diff（またはパッチ）ファイルを読み込み、そのファイルに記述された変更をソースツリーに適用します。

Linuxカーネル用のパッチは、カーネルソースディレクトリを含む親ディレクトリに対して生成されます。

これは、パッチファイル内のファイルへのパスが生成時に使用されたカーネルソースディレクトリ名（または「a/」や「b/」などの他のディレクトリ名）を含むことを意味します。

これは、あなたのローカルマシン上のカーネルソースディレクトリ名と一致しない可能性があります（ただし、無ラベルのパッチがどのバージョンに生成されたかを確認するための情報としてしばしば役立ちます）。そのため、パッチを適用する際には、カーネルソースディレクトリに移動し、パッチファイル内のファイル名からパスの最初の要素を削除する必要があります（ -p1 引数として patch patchコマンドがこれを処理します）。

以前に適用したパッチを戻すには、patchに-Rオプションを使用します。例えば、以下のようにパッチを適用した場合：

patch -p1 < ../patch-x.y.z

これを戻す（取り消す）には以下のようにします：

patch -R -p1 < ../patch-x.y.z

パッチ/diffファイルを patch?¶

この（Linuxや他のUNIX系オペレーティングシステムと同様に）複数の方法で行うことができます。

以下の例では、すべての例で圧縮されていない形式のファイルを標準入力（stdin）経由でpatchに渡しています。構文は以下の通り：

patch -p1 < path/to/patch-x.y.z

以下の例を追うだけであれば、patchの使用方法を1つの方法だけ知る必要があるだけなので、このセクションの読みをここで止めても構いません。

patchはまた、-iオプションで使用するファイル名を指定することもできます。例えば以下のように：

patch -p1 -i path/to/patch-x.y.z

パッチファイルがgzipまたはxzで圧縮されており、適用前に解凍したくない場合、patchに以下のように渡すことができます：

xzcat path/to/patch-x.y.z.xz | patch -p1
bzcat path/to/patch-x.y.z.gz | patch -p1

パッチファイルを手動で解凍してから適用する場合（以下の例では行ったと想定しています）、単にgunzipまたはxzコマンドをファイルに適用します。例えば以下のように：

gunzip patch-x.y.z.gz
xz -d patch-x.y.z.xz

これにより、通常のテキストファイルpatch-x.y.zが得られ、これを標準入力または -i 引数として指定することもできます。

patchの他の便利なオプションには、 -s があります。これはエラー以外は静かにします。これにより、エラーが画面からすぐにスクロールしていってしまうのを防ぐことができます。また、 --dry-run は、実際に変更を加えることなく、何が行われるかを一覧表示します。最後に、 --verbose は、処理中の詳細情報を表示します。

パッチ適用時の一般的なエラー¶

パッチを適用する際、patchはファイルの健全性を複数の方法で確認します。

ファイルが有効なパッチファイルであるかを確認し、変更対象の周辺コードがパッチで提供されたコンテキストと一致するかを確認するのは、patchが行う基本的な健全性チェックの例です。

patchが何かが正しくないものに遭遇した場合、2つの選択肢があります。変更を拒否して中断するか、あるいはいくつかの小さな変更を加えてパッチを適用できるように試みるかです。

patchが修正しようとする例として、コンテキストが一致していて変更対象の行も一致しているが、行番号が異なる場合があります。たとえば、パッチがファイルの中間部分で変更を加えるが、何らかの理由でファイルの先頭近くに数行が追加または削除された場合、すべてが正常に見えるが、行番号が少し上か下にずれている場合があります。このような場合、patchは通常、行番号を調整してパッチを適用します。

patchがパッチを適用するために少し修正した場合、以下のようにしてそのことを通知します： fuzz。このような変更には注意が必要です。なぜなら、patchが正しい結果を出している可能性が高いですが、常に正しいとは限りません。結果が間違っている場合があります。

patchがfuzzで修正できない変更に遭遇した場合、即座に拒否し、拡張子 .rej を持つファイル（拒否ファイル）を作成します。このファイルを読むことで、どの変更が適用できなかったかを確認できます。必要に応じて手動で修正することもできます。

カーネルソースにサードパーティのパッチを適用していないが、kernel.orgからのパッチのみを正しく順番に適用し、ソースファイルに自分で変更を加えていない場合、パッチがファジングや拒否メッセージを表示することはありません。それでもこのようなメッセージが表示される場合は、ローカルのソースツリーまたはパッチファイルが何らかの形で破損している可能性が非常に高いです。その場合は、パッチを再ダウンロードすることを試みるべきです。それでも問題が解決しない場合は、kernel.orgから完全にダウンロードした新しいツリーから再開することをお勧めします。

パッチが生成するメッセージについてもう少し詳しく見ていきましょう。

パッチが停止し、以下のプロンプトを表示した場合、パッチを適用するファイルが見つからなかった可能性があります。 File to patch: 最も可能性が高いのは、-p1を指定していないか、または正しいディレクトリにいないことです。まれに、パッチを適用する際には -p0 …の代わりに -p1 特定のオプションが必要なパッチもあります（パッチファイルを読み込むことでこの状況かどうか確認できます。もしこれが起きた場合は、パッチを作成した人の誤りですが、致命的なエラーではありません）。

ファジングや Hunk #2 succeeded at 1887 with fuzz 2 (offset 7 lines). のようなメッセージが表示された場合、パッチが変更の位置を調整したことを意味します（この例では、予期していた場所から7行移動させることで変更を適用しました）。

結果として得られたファイルが正常かどうかは、ファイルが予期せず異なる理由によります。

これは、パッチが生成されたカーネルバージョンと現在適用しようとしているカーネルバージョンが異なる場合によく起きます。

以下のメッセージが表示された場合、 Hunk #3 FAILED at 2387.パッチを正しく適用できず、ファジングで乗り越えることができなかったことを意味します。これにより、 .rej 変更が失敗した原因となった変更内容を含むファイルと、 .orig 変更できなかった元の内容を表示するファイルが生成されます。

ファジングや Reversed (or previously applied) patch detected!  Assume -R? [n] パッチが検出しました。このパッチに含まれる変更がすでに適用されている可能性があります。

もしこのパッチを以前に適用した後、誤って再度適用した場合、[n]oを選択してこのパッチを中止してください。以前に適用したパッチを元に戻すつもりだったが、-Rを指定しなかった場合、[y]esを選択してパッチを元に戻すことができます。y]esを選択することでパッチを元に戻すことができます。

これは、パッチを作成した人がソースと宛先ディレクトリを逆にした場合にも起こります。その場合、パッチを元に戻すことで実際にはパッチを適用することになります。

以下のメッセージに似たものが表示されることがあります patch: **** unexpected end of file in patch または patch unexpectedly ends in middle of line これは、パッチが提供されたファイルを正しく理解できなかったことを意味します。ダウンロードが破損している、またはパッチを適用する前に圧縮されたパッチファイルを解凍せずに処理した、もしくはメールクライアントやメール転送エージェントによってパッチファイルが途中で改変された（例えば、長い行を2行に分割された）可能性があります。これらの警告は、通常、分割された行を結合（連結）することで簡単に修正できます。

すでに上記で述べた通り、kernel.orgからパッチを適用する際には、修正されていないソースツリーの正しいバージョンを使用すればこれらのエラーは発生しません。そのため、kernel.orgのパッチでこのようなエラーが発生した場合は、おそらくパッチファイルまたはツリーが破損していると想定し、フルなカーネルツリーと適用したいパッチを新たにダウンロードしてからやり直すことをお勧めします。

代替案はありますか？ patch?¶

はい、代替案があります。

interdiffという interdiff プログラム（http://cyberelk.net/tim/patchutils/）を使用して、2つのパッチ間の差分を表すパッチを生成し、その後その結果を適用できます。

これにより、5.7.2から5.7.3へ一度のステップで移動できます。interdiffの-zフラグは、gzipまたはbzip2で圧縮されたパッチファイルを直接処理可能で、zcatやbzcatの使用や手動での圧縮解除を必要としません。

5.7.2から5.7.3へ一度のステップで移動する方法は以下の通りです：

interdiff -z ../patch-5.7.2.gz ../patch-5.7.3.gz | patch -p1

interdiffはステップを1つ減らすかもしれませんが、一般的には追加のステップを実行することを推奨します。interdiffは一部のケースで誤りを生じる可能性があるためです。

他の代替案として ketchupという、パッチの自動ダウンロードおよび適用を行うためのPythonスクリプト（https://www.selenic.com/ketchup/).

）があります。他にもdiffstatというパッチによる変更内容のサマリを表示するツール、lsdiffというパッチファイル内の影響を受けたファイルの一覧表示ツール（各パッチの開始行番号をオプションで表示可能）、grepdiffというパッチに特定の正規表現が含まれるファイルの一覧表示ツールがあります。

パッチはどこでダウンロードできますか？¶

パッチは以下のURLから入手できます： https://kernel.org/ 最新のパッチはフロントページからリンクされていますが、それぞれに特定のホームがあります。

5.x.y (-stable)および5.xのパッチは以下の場所にあります：

https://www.kernel.org/pub/linux/kernel/v5.x/

-rcパッチはウェブサーバーに保存されておらず、gitタグ（例：

https://git.kernel.org/torvalds/p/v5.1-rc1/v5.0

）から必要に応じて生成されます。安定版の-rcパッチは以下の場所にあります：

https://www.kernel.org/pub/linux/kernel/v5.x/stable-review/

5.xカーネル¶

これらはリナックスがリリースしたベースとなる安定版です。最も大きな番号のリリースが最新です。

リグレッションや他の深刻な欠陥が見つかった場合、このベースの上に「-stable」の修正パッチがリリースされます（以下を参照）。新しい5.xベースカーネルがリリースされた後、前の5.xカーネルと新しいカーネルの差分を反映したパッチが提供されます。

5.6から5.7へのパッチを適用するには、以下の手順を行います（このようなパッチは、5.x.yカーネルではなく、ベースの5.xカーネル上に適用されます。5.x.yから5.x+1へ移行する場合は、まず5.x.yのパッチを元に戻す必要があります）。 禁止です 5.x.yカーネル上ではなく、ベースの5.xカーネル上に適用されます。5.x.yから5.x+1へ移行する場合は、まず5.x.yのパッチを元に戻す必要があります。

以下に例を示します。

# moving from 5.6 to 5.7

$ cd ~/linux-5.6                # change to kernel source dir
$ patch -p1 < ../patch-5.7      # apply the 5.7 patch
$ cd ..
$ mv linux-5.6 linux-5.7        # rename source dir

# moving from 5.6.1 to 5.7

$ cd ~/linux-5.6.1              # change to kernel source dir
$ patch -p1 -R < ../patch-5.6.1 # revert the 5.6.1 patch
                                # source dir is now 5.6
$ patch -p1 < ../patch-5.7      # apply new 5.7 patch
$ cd ..
$ mv linux-5.6.1 linux-5.7      # rename source dir

5.x.y カーネル¶

3桁のバージョンを持つカーネルは「-stable」カーネルです。これらは、特定の5.xカーネル内で発見されたセキュリティ問題や重要なリグレッションに対する小さな（それなりの）重要な修正を含んでいます。

最新の安定版カーネルを希望し、開発/実験版のテストに参加したくないユーザー向けに推奨されるブランチです。

5.x.yカーネルが利用できない場合、最も高い番号を持つ5.xカーネルが現在の安定版カーネルです。

注意

-stableチームは通常、インクリメンタルなパッチや最新のメインラインリリースに対するパッチも提供しますが、ここでは非インクリメンタルなパッチのみを説明します。インクリメンタルなパッチは以下にあります https://www.kernel.org/pub/linux/kernel/v5.x/incr/

これらのパッチはインクリメンタルではありません。たとえば、5.7.3のパッチは5.7.2カーネルソースではなく、ベースの5.7カーネルソース上に適用されます。

したがって、既存の5.7.2カーネルソースに5.7.3パッチを適用するには、まず5.7.2パッチを元に戻してベースの5.7カーネルソースに戻し、その後で新しい5.7.3パッチを適用する必要があります。

小さな例を以下に示します。

$ cd ~/linux-5.7.2              # change to the kernel source dir
$ patch -p1 -R < ../patch-5.7.2 # revert the 5.7.2 patch
$ patch -p1 < ../patch-5.7.3    # apply the new 5.7.3 patch
$ cd ..
$ mv linux-5.7.2 linux-5.7.3    # rename the kernel source dir

「-rc」カーネル¶

これらはリリース候補カーネルです。これらは、Linusが現在のgit（カーネルのソース管理ツール）ツリーがテストに適した状態にあると判断したときにリリースされる開発用カーネルです。

これらのカーネルは安定していません。実行する場合はまれに破損する可能性があることをご了承ください。ただし、これは主要な開発ブランチの中で最も安定しており、最終的に次の安定版カーネルになるため、できるだけ多くの人々がテストを行うことが重要です。

開発用カーネルのテストに協力したいが、非常に実験的な内容を実行したくないユーザーには、このブランチが適しています（このようなユーザーは、以下の「-next」および「-mm」カーネルのセクションを参照してください）。

-rcパッチはインクリメンタルではありません。これらは5.xベースのカーネルに適用され、上記の5.x.yパッチと同様です。-rcNサフィックス前のカーネルバージョンは、この-rcカーネルが最終的に変換するバージョンを示します。

したがって、5.8-rc5は5.8カーネルの5番目のリリース候補を表し、このパッチは5.7カーネルソース上に適用されるべきです。

これらのパッチを適用する方法の例を3つ示します：

# first an example of moving from 5.7 to 5.8-rc3

$ cd ~/linux-5.7                        # change to the 5.7 source dir
$ patch -p1 < ../patch-5.8-rc3          # apply the 5.8-rc3 patch
$ cd ..
$ mv linux-5.7 linux-5.8-rc3            # rename the source dir

# now let's move from 5.8-rc3 to 5.8-rc5

$ cd ~/linux-5.8-rc3                    # change to the 5.8-rc3 dir
$ patch -p1 -R < ../patch-5.8-rc3       # revert the 5.8-rc3 patch
$ patch -p1 < ../patch-5.8-rc5          # apply the new 5.8-rc5 patch
$ cd ..
$ mv linux-5.8-rc3 linux-5.8-rc5        # rename the source dir

# finally let's try and move from 5.7.3 to 5.8-rc5

$ cd ~/linux-5.7.3                      # change to the kernel source dir
$ patch -p1 -R < ../patch-5.7.3         # revert the 5.7.3 patch
$ patch -p1 < ../patch-5.8-rc5          # apply new 5.8-rc5 patch
$ cd ..
$ mv linux-5.7.3 linux-5.8-rc5          # rename the kernel source dir

-mmパッチとlinux-nextツリー¶

-mmパッチはアンドリュー・モートンが公開する実験的なパッチです。

かつてはサブシステムパッチのテストにも使用されていましたが、現在は linux-next <https://www.kernel.org/doc/man-pages/linux-next.html> ツリーでこの機能が行われています。サブシステムメンテナはまずlinux-nextにパッチをプッシュし、マージウィンドウ期間中に直接リンスへ送信します。

-mmパッチはサブシステムツリーを通じてマージされない新機能や他の実験的パッチの検証場のような役割を果たします。このようなパッチが- mmで十分検証されると、アンドリューがメインラインのリンスツリーにマージするよう推進します。

linux-nextツリーは毎日更新され、-mmパッチを含みます。どちらも常に変化しており、多くの実験的機能やメインラインに適さないデバッグパッチ、その他多くの実験的要素を含み、このドキュメントで説明する分岐の中で最も実験的なものです。

これらは安定したシステムに使用すべきではなく、他の分岐よりもリスクが高いです（最新のバックアップを確保してください。これはどの実験的カーネルでも同様ですが、特に-mmパッチやlinux-nextツリーからのカーネルを使用する場合に注意が必要です）。

-mmパッチおよびlinux-nextのテストは非常に重要です。これらが主にメインラインのリンスツリーにマージする前にリグレッション、クラッシュ、データ腐敗のバグ、ビルドエラー（および一般的な他のバグ）を排除するためのものです。

ただし、-mmおよびlinux-nextをテストするユーザーは、他のツリーに比べてエラーがより頻繁に発生することを認識しておくべきです。

このドキュメントで説明したさまざまなカーネルツリーの説明はこれで終わります。今後、さまざまなパッチの適用方法やカーネルのテストへの協力を理解していただけたことを願っています。

7. 高度なトピック¶

この時点で、開発プロセスの仕組みについて理解できることを願っています。しかし、まだ学ぶべきことはたくさんあります！このセクションでは、Linux カーネル開発プロセスに定期的に参加したい開発者にとって役立つさまざまなトピックについて説明します。

7.1. git を用いたパッチの管理¶

カーネルの開発において分散型バージョン管理が導入されたのは、2002年初頭のことです。当時、リンスは専有型の BitKeeper アプリケーションを試していました。BitKeeper は議論を呼んだものの、その実装するソフトウェアバージョン管理のアプローチは間違いなかったのです。分散型バージョン管理は、カーネル開発プロジェクトの進捗を即座に加速させました。現在では、BitKeeper に代わる無料の代替ツールがいくつかあります。良いか悪いかに関わらず、カーネルプロジェクトは git を選択したツールとして定着させました。

git を用いたパッチの管理は、特にパッチの量が増えるにつれて開発者にとって非常に役立ちます。git は若いながらも力強いツールであり、まだ開発者によって「文明化」されている途中です。このドキュメントでは、読者に git の使い方を教えることはしません。それだけでも長編のドキュメントになるでしょう。代わりに、ここでは git がカーネル開発プロセスにどのように組み込まれているかに焦点を当てます。git の習熟を望む開発者は以下の情報にアクセスできます：

https://git-scm.com/

https://www.kernel.org/pub/software/scm/git/docs/user-manual.html

ウェブ上に存在するさまざまなチュートリアルでも確認できます。

最初のステップは、上記のサイトを読み、git の仕組みをしっかり理解した上で、他の人にパッチを提供するための準備を整えることです。git を使用する開発者は、メインラインリポジトリのコピーを取得し、変更履歴を調査し、ツリーに変更をコミットし、ブランチを使用するなど、基本的な操作を理解しておく必要があります。git の履歴再構築ツール（rebase など）の理解も役立ちます。git には独自の用語と概念があり、新規ユーザーは refs、リモートブランチ、インデックス、フォワードマージ、プッシュとプル、デタッチドヘッドなどについて知る必要があります。最初は少し怖く感じるかもしれませんが、ある程度の学習で概念はそれほど難しくありません。

メールで提出するパッチを生成するために git を使用する練習は、習熟するうえで良い方法です。

他人が確認できるようgitツリーを公開する準備ができたら、当然ながら、プルできるサーバーが必要になります。インターネットにアクセス可能なシステムであれば、git-daemonを使用したサーバーの設定は比較的簡単です。そうでない場合は、無料で公開されているホスティングサイト（例: GitHub）がネットワーク上に現れ始めています。確立された開発者であればkernel.orgにアカウントを取得できますが、それらは入手が難しいため、参照してください https://kernel.org/faq/ 詳しくは

gitの通常のワークフローでは、多くのブランチを使用します。各開発ラインは「トピックブランチ」として分離され、独立して管理されます。gitのブランチは簡単に作成できるため、自由に活用する理由はありません。また、他人からプルする予定があるブランチで開発を行うべきではありません。公開用のブランチは慎重に作成し、開発ブランチから完全に完成したパッチを導入した後で、それ以外のタイミングで公開しないようにしてください

gitは開発履歴を再構築するための強力なツールを提供しています。不都合なパッチ（バイセクションを破るなど、明らかにバグのあるもの）は場所を変えて修正したり、履歴から完全に消去することも可能です。パッチシリーズは、今月にわたって作業していたとしても、今日のメインライン上に書かれたもののように再構築できます。変更はブランチ間で透明に移動させることも可能です。このようなgitの履歴再構築機能を適切に活用すれば、問題が少ないクリーンなパッチセットを作成できます

この機能を過度に使用すると、単なる完璧なプロジェクト履歴へのこだわり以上の問題が生じます。履歴を再構築すると、その履歴に含まれる変更も再構築され、テスト済み（ hopefully）のカーネルツリーをテストされていないものに変えることになります。さらに、開発者同士がプロジェクト履歴の共有視点を持たなければ協力が難しくなります。他の開発者がプルした履歴を再構築すると、それらの開発者の作業が大幅に困難になります。したがって、シンプルなルールとして、他人に公開した履歴はその後変更不可とみなすべきです

したがって、自分の公開サーバーに変更をプッシュした後は、その変更は再構築されべきではありません。Gitは、変更がフォワードマージ（つまり、同じ履歴を持つ変更ではない）をもたらす場合にのみプッシュを許可しようとします。ただし、このチェックを上書きすることが可能です。また、エクスポートされたツリーの変更を再構築する必要がある場合もあります。linux-nextで変更セットをツリー間で移動して衝突を回避する例が挙げられます。しかし、このような操作はまれに限るべきです。これが、開発がプライベートブランチ（必要に応じて再構築可能な）で行われ、公開ブランチに移すのはある程度進化した状態のときに限るべきである理由の一つです。

メインライン（または他の変更がベースとなるツリー）が進化するにつれて、そのツリーとマージして先頭に立つことが誘惑されます。プライベートブランチでは、リベースすることで他のツリーに追いつくのが簡単ですが、ツリーが世界に公開されるとリベースは選択肢から外れます。その時点で、フルマージを行う必要があります。マージは時折有効ですが、過度に頻繁に行うと履歴を無駄に複雑にします。その場合の推奨テクニックは、マージをあまり頻繁に行わず、一般的には主要ラインの-rcリリースなどの特定のリリースポイントでのみ行うことです。特定の変更に不安がある場合は、プライベートブランチでテストマージを行うことも可能です。このような状況では、gitのrerereツールが役立ちます。このツールは、マージコンフリクトの解決方法を記憶するので、同じ作業を2度行う必要がありません。

gitなどのツールについて最もよくある不満の一つは、パッチの大量移動により、レビューの目から外れてしまう不適切な変更がメインラインに組み込まれる可能性があることです。カーネル開発者たちは、このようなことが起こると不満になります。未検証またはオフタピックのパッチを含むgitツリーを公開すると、今後ツリーが取り込まれる可能性に影響を与えることがあります。リンスの言葉を引用します：

You can send me patches, but for me to pull a git patch from you, I
need to know that you know what you're doing, and I need to be able
to trust things *without* then having to go and check every
individual change by hand.

(https://lwn.net/Articles/224135/).

このような状況を避けるためには、各ブランチ内のパッチが関連するトピックに密着していることを確認してください。たとえば、「ドライバ修正」ブランチはコアメモリ管理コードの変更を行ってはいけません。最も重要なのは、レビュープロセスをバイパスするためのgitツリーを使わないことです。定期的にツリーのサマリーを関連するリストに投稿し、タイミングが合えばlinux-nextにツリーを含めるよう依頼してください。

他の人があなたのツリーにパッチを送るようになっても、レビューを行うのを忘れないでください。また、正しい著作者情報を維持することも重要です。「git am」ツールはこの点で最大限の努力をしていますが、第三者を通じてあなたに届いたパッチには「From:」行を手動で追加する必要があるかもしれません。

プルリクエストを依頼する際は、以下の情報をすべて提供してください：あなたのツリーの場所、どのブランチからプルするか、そしてそのプルによって生じる変更内容です。「git request-pull」コマンドはこの作業を助けることができます。このコマンドは他の開発者に期待されるフォーマットでリクエストを生成し、またパブリックサーバーに変更をプッシュしたかを確認します。

7.2. パッチのレビュー¶

一部の読者の中には、このセクションを「高度なトピック」と一緒に掲載することに異論を唱える人もいます。理由は、初心者でもパッチのレビューを行うべきだという点です。確かに、他の人が投稿したコードを確認することで、カーネル環境でのプログラミングを学ぶには最善の方法です。さらに、レビュワーは常に不足しているため、コードを確認することで全体的なプロセスに大きな貢献ができるのです。

コードのレビューは特に新米カーネル開発者にとって不安を引き起こす可能性があります。経験豊富な開発者が投稿したコードをパブリックに質問するという行為に緊張を感じるかもしれません。しかし、最も経験のある開発者が書いたコードでも改善の余地はあります。レビュワー（すべてのレビュワー）にとって最も重要なアドバイスは、レビューのコメントを批判ではなく質問として表現することです。「このパスでロックが解放される仕組みはどのようになっていますか？」と尋ねる方が、「ここでのロック処理が間違っている」と指摘するより常に効果的です。

開発者はコードレビューを行う際、それぞれ異なる視点を持っています。一部はコーディングスタイルやコード行末のホワイトスペースに注目する人もいます。他には、パッチ全体としてカーネルにとって有益かどうかに焦点を当てます。また、一部は問題のあるロック処理、スタック使用量の過多、潜在的なセキュリティリスク、他の場所で見られるコードの重複、十分なドキュメンテーション、パフォーマンスへの悪影響、ユーザー空間のABI変更など、さまざまな点をチェックします。すべてのレビューは、より良いコードがカーネルに取り込まれることを目的としているため、歓迎されるし、価値のある作業です。

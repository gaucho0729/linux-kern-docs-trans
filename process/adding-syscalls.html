新しいシステムコールの追加¶

このドキュメントでは、Linux Kernel に新システムコールを追加する際に、通常のサブミッションアドバイスに加えて必要な手順について説明します。 パッチの送信: コードをカーネルに取り込むためのエッセンシャルガイド.

システムコールの代替案¶

新システムコールを追加する際には、まず代替案が適切かどうかを検討する必要があります。システムコールはユーザー空間とカーネル間のインターフェースポイントとして最も伝統的で明確ですが、他の選択肢もあります。インターフェースに最も合ったものを選ぶことが重要です。

  • 操作がファイルシステムのようなオブジェクトに見えるようにできる場合、新しいファイルシステムやデバイスを作成する方が適切です。これにより、カーネルモジュールで新機能をカプセル化し、メインカーネルに組み込む必要がなくなるため、実装が簡単になります。

    • カーネルがユーザー空間に何かが起きたことを通知する操作を含む新機能の場合、関連するオブジェクトに新しいファイル記述子を返すことで、ユーザー空間が poll/select/epoll その通知を受信できるようになります。

    • ただし、ファイルシステムのような操作にマッピングできない操作は、 read(2)/write(2)リクエストとして実装する必要があります。これにより、ある程度不透明なAPIが生じる可能性があります。 ioctl(2) ランタイムシステム情報のみを公開する場合は、sysfs（参照）に新しいノードを作成する方が適切です。または、

  • ) または Documentation/filesystems/sysfs.rstのいずれかを使用します。 /proc ファイルシステムの方が適切かもしれません。ただし、これらのメカニズムへのアクセスには、関連するファイルシステムがマウントされている必要がありますが、常にその状態にあるとは限りません（例: 名前空間/サンドボックス/チョート環境など）。debugfsにAPIを追加するのは避けてください。これはユーザー空間に対する「本番環境用」インターフェースと見なされないからです。

  • 操作が特定のファイルまたはファイル記述子に限定されている場合は、追加の fcntl(2) コマンドオプションを追加する方が適切かもしれません。ただし、 fcntl(2) は複雑な多重化システムコールであり、多くの複雑さを隠しています。そのため、このオプションは、新しい機能が既存の fcntl(2) 機能と非常に類似している場合、または新しい機能が非常に単純な場合（例: ファイル記述子に関連する単純なフラグの取得/設定など）に最適です。

  • 操作が特定のタスクまたはプロセスに限定されている場合は、追加の prctl(2) コマンドオプションを追加する方が適切かもしれません。既存の fcntl(2)システムコール同様に、複雑な多重化処理であり、既存の prctl() コマンドや、プロセスに関連する単純なフラグの取得/設定にのみ予約されています。

APIの設計: 拡張性の考慮¶

新しいシステムコールはカーネルのAPIの一部となり、無期限にサポートされる必要があります。そのため、カーネルのメーリングリストでインターフェースを明確に議論することが非常に良い考えです。また、インターフェースの今後の拡張を計画することも重要です。

(syscallテーブルには、この手順が行われなかった歴史的な例が散らばっており、それに伴う追加のシステムコールも含まれています— eventfd/eventfd2, dup2/dup3, inotify_init/inotify_init1, pipe/pipe2, renameat/renameat2 —そのため、カーネルの歴史から学び、拡張を最初から計画してください。)

シンプルなシステムコールで、数個の引数しか受け取らない場合、今後の拡張性を確保するためには、システムコールにフラグ引数を含めるのが望ましいです。ユーザースペースのプログラムがカーネルバージョン間でフラグを安全に使用できるようにするためには、フラグ値に未知のフラグが含まれていないか確認し、含まれている場合はシステムコールを拒否（ EINVAL)します：

if (flags & ~(THING_FLAG1 | THING_FLAG2 | THING_FLAG3))
    return -EINVAL;

(まだフラグ値が使用されていない場合、フラグ引数がゼロであることを確認してください。)

より複雑なシステムコールで、多数の引数を扱う場合、主な引数をポインタで渡される構造体にまとめることで拡張性を確保するのが望ましいです。このような構造体は、サイズ引数を含むことで今後の拡張に対応できます：

struct xyzzy_params {
    u32 size; /* userspace sets p->size = sizeof(struct xyzzy_params) */
    u32 param_1;
    u64 param_2;
    u64 param_3;
};

その後に追加されるフィールド、例えば param_4であれば、ゼロ値が以前の挙動を再現するように設計されている限り、この方法はバージョン不一致の両方向に対応できます：

  • 後続のユーザースペースプログラムが古いカーネルを呼び出す場合、カーネルコードは、構造体のサイズを超えたメモリがゼロであることを確認する必要があります（つまり、 param_4 == 0).

  • を確認するためのチェックです）。 param_4 = 0).

参照 perf_event_open(2) 2.5開発シリーズで導入された形式です。 perf_copy_attr() 関数（ kernel/events/core.c）はこのアプローチの例です。

APIの設計: その他の考慮事項¶

新しいシステムコールがユーザースペースにカーネルオブジェクトを参照させる場合、ファイルディスクリプタをそのオブジェクトのハンドルとして使用すべきです。カーネルが既にファイルディスクリプタの使用に明確なセマンティクスを持つメカニズムを持っているため、新しいユーザースペースオブジェクトハンドルを新たに作成しないでください。

新しい xyzzy(2) システムコールが新しいファイルディスクリプタを返す場合、フラグ引数には新しいFDで設定するオプションに相当する値を含めるべきです。これにより、ユーザースペースが O_CLOEXEC のタイミング窓を閉じる可能性が高まります。 xyzzy() を埋め込み、 fcntl(fd, F_SETFD, FD_CLOEXEC)で、別のスレッドからの予期せぬ fork() および execve() が実行されたプログラムにディスクリプタをリークさせる可能性があります。（ただし、実際の O_CLOEXEC 定数として扱うべきです。なぜなら、これはアーキテクチャ固有であり、番号空間の一部だからです。 O_* 比較的完全なフラグです。(。

システムコールが新しいファイル記述子を返す場合、そのファイル記述子を使用する意味についても考慮する必要があります。 poll(2) このファイル記述子を読み込みまたは書き込み用に準備する方法が、カーネルが対応するカーネルオブジェクト上でイベントが発生したことをユーザー空間に通知する通常の方法です。

新しい xyzzy(2) システムコールはファイル名引数を含みます:

int sys_xyzzy(const char __user *path, ..., unsigned int flags);

また、以下の xyzzyat(2) バージョンがより適切です:

int sys_xyzzyat(int dfd, const char __user *path, ..., unsigned int flags);

これにより、ユーザー空間が関係するファイルを指定する方法に柔軟性が生まれ、特に既にオープンされたファイル記述子に対してユーザー空間がフラグを使用して機能を要求できるため、 AT_EMPTY_PATH フラグを効果的に提供することになります。 fxyzzy(3) 操作を無料で実行できます:

- xyzzyat(AT_FDCWD, path, ..., 0) is equivalent to xyzzy(path,...)
- xyzzyat(fd, "", ..., AT_EMPTY_PATH) is equivalent to fxyzzy(fd, ...)

(※ *at()コールの根拠についての詳細は、 openat(2) man ページを参照してください。AT_EMPTY_PATHの例については、 fstatat(2) man ページを参照してください。)

新しい xyzzy(2) システムコールがファイル内のオフセットを表すパラメータを含む場合、その型を loff_t 64ビットオフセットを32ビットアーキテクチャでもサポートできるようにします。

新しい xyzzy(2) システムコールが特権機能を含む場合、適切なLinuxキャパビリティビットで制御する必要があります（call to capable()で確認されます）。 capabilities(7) man ページで説明されています。関連する機能を制御する既存のキャパビリティビットを選択してください。ただし、関連性のない機能を複数まとめて同じビットに配置するのは、キャパビリティの目的であるrootの権限を分割する目的に反するため、避けましょう。特に、既に過度に一般的な CAP_SYS_ADMIN capability.

新しい xyzzy(2) システムコールを操作する対象が呼び出し元プロセス以外のプロセスである場合、呼び出し元プロセスが対象プロセスと同じ権限を持つか、必要なキャパビリティを持つ場合にのみ操作を許可するよう制限する必要があります（call to ptrace_may_access()で制限します）。

最後に、一部の非x86アーキテクチャでは、システムコールパラメータが明示的に64ビットである場合、奇数番号の引数（つまり、引数1、3、5など）に配置することで、連続する32ビットレジスタのペアの使用が可能になります。（この懸念は、引数がポインタで渡される構造体の一部である場合には適用されません。）

APIの提案¶

新しいシステムコールのレビューを容易にするため、パッチセットを複数のチャンクに分けるのが望ましいです。これらには少なくとも以下の項目を個別のコミットとして含める必要があります（以下で詳しく説明します）:

  • システムコールのコア実装と、プロトタイプ、汎用的な番号付け、Kconfigの変更、およびフォールバックスタブの実装。

  • 特定のアーキテクチャ（通常はx86、x86_64、x86_32、x32を含む）向けに新しいシステムコールを接続する作業。

  • ユーザー空間での新しいシステムコールの使用例を、以下のselftestで示す。 tools/testing/selftests/.

  • 新しいシステムコール用のドラフトman-pageを、カバー手紙内のプレーンテキストとして、またはman-pagesリポジトリへのパッチとして提出。

カーネルのAPIへの変更（新しいシステムコールを含む）は常に linux-api@vger.kernel.org.

汎用システムコール実装¶

新しい xyzzy(2) システムコールのメインエントリポイントは sys_xyzzy()と呼ばれるが、適切な SYSCALL_DEFINEn() マクロでこのエントリポイントを追加する。'n'はシステムコールの引数の数を示し、マクロはシステムコール名に続いて（型、名前）のペアを引数として受け取る。このマクロを使用することで、他のツールが新しいシステムコールに関するメタデータを取得できるようになる。

新しいエントリポイントには、 include/linux/syscalls.hに記載される関数プロトタイプが必要で、asmlinkageとしてマークする必要がある。

asmlinkage long sys_xyzzy(...);

一部のアーキテクチャ（例: x86）は独自のアーキテクチャ固有のシステムコールテーブルを持つが、他のいくつかのアーキテクチャは汎用的なシステムコールテーブルを共有する。新しいシステムコールを汎用リストに追加するには、 include/uapi/asm-generic/unistd.h:

#define __NR_xyzzy 292
__SYSCALL(__NR_xyzzy, sys_xyzzy)

のリストにエントリを追加する。また、__NR_syscallsのカウントを更新し、複数の新しいシステムコールが同じマージウィンドウで追加される場合、新しいシステムコール番号が調整される可能性があることを留意する。

ファイル kernel/sys_ni.c はすべてのシステムコールのフォールバックスタブ実装を提供し、 -ENOSYSを返す。新しいシステムコールもここで追加する:

COND_SYSCALL(xyzzy);

新しいカーネル機能およびそれを制御するシステムコールは通常オプションとなるため、 CONFIG オプション（通常は init/Kconfigに）を追加する。新しい CONFIG オプション:

  • については、オプションで制御される新しい機能およびシステムコールの説明を含める。

  • オプションが通常ユーザーから隠されるべき場合は、EXPERTに依存させる。

  • 新しいソースファイルを実装する際、Makefile内のCONFIGオプションに依存させる（例: obj-$(CONFIG_XYZZY_SYSCALL) += xyzzy.o).

  • 新しいCONFIGオプションをオフにした状態でカーネルがビルド可能か再確認する。

要約すると、以下のコミットが必要となる:

  • CONFIG オプションで新しい機能を制御する、通常 init/Kconfig

  • SYSCALL_DEFINEn(xyzzy, ...) エントリポイントの

  • に該当するプロトタイプを include/linux/syscalls.h

  • 汎用テーブルのエントリを include/uapi/asm-generic/unistd.h

  • フォールバックスタブを kernel/sys_ni.c

x86システムコール実装¶

x86プラットフォームで新しいシステムコールを設定するには、マスターシステムコールテーブルを更新する必要があります。新しいシステムコールが特別なケースでない場合（以下を参照）、これはx86_64およびx32用の「一般的な」エントリをarch/x86/entry/syscalls/syscall_64.tblに追加することを意味します:

333   common   xyzzy     sys_xyzzy

および「i386」用のエントリを arch/x86/entry/syscalls/syscall_32.tbl:

380   i386     xyzzy     sys_xyzzy

また、これらの数字は、関連するマージウィンドウで競合が発生した場合、変更される可能性があります。

互換性システムコール（汎用）¶

ほとんどのシステムコールでは、ユーザースペースプログラムが32ビットであっても、同じ64ビットの実装を呼び出すことができます。システムコールのパラメータに明示的なポインタが含まれる場合でも、透明に処理されます。

ただし、32ビットと64ビットのサイズ差に対応するためには、互換性レイヤーが必要なケースもあります。

1つ目のケースは、64ビットのカーネルが32ビットのユーザースペースプログラムをサポートする場合で、（__user)メモリの領域を解析する必要があります。特に、システムコールの引数が以下のいずれかの場合に必要です:

  • ポインタへのポインタ

  • ポインタを含む構造体へのポインタ（例： struct iovec __user *)

  • 可変サイズの整数型へのポインタ（time_t, off_t, long, …)

  • 可変サイズの整数型を含む構造体へのポインタ。

2つ目のケースは、システムコールの引数のうち、32ビットアーキテクチャでも明示的に64ビット型である場合です。例えば、 loff_t または __u64。この場合、32ビットアプリケーションから64ビットカーネルに到達した値は、2つの32ビット値に分割され、互換性レイヤーで再構成する必要があります。

(システムコールの引数が明示的に64ビット型へのポインタである場合、 ではありません 互換性レイヤーが必要です。例えば、 splice(2)の引数の型 loff_t __user * は、システムコールの必要性を引き起こしません。 compat_ システムコールの互換性バージョンは

と呼ばれ、SYSCALL_DEFINEnに類似して compat_sys_xyzzy()マクロで追加されます。この実装は64ビットカーネル内で動作しますが、32ビットのパラメータ値を受け取り、それらを処理するために必要な処理を行います。（通常、 COMPAT_SYSCALL_DEFINEn() バージョンは値を64ビット版に変換し、 compat_sys_ バージョンに呼び出しますか、または両方のバージョンが共通の内部実装関数を呼び出します。） sys_ 互換性エントリポイントにも、対応する関数プロトタイプが必要です。

もしシステムコールが32ビットと64ビットで構造体のレイアウトが異なる場合、例えば、 include/linux/compat.hに記載される関数プロトタイプが必要で、asmlinkageとしてマークする必要がある。

asmlinkage long compat_sys_xyzzy(...);

の場合、include/linux/compat.hヘッダーファイルにも、可変サイズのフィールドが適切に struct xyzzy_argsの互換性バージョンの構造体を含める必要があります。struct compat_xyzzy_argsを指定します。 compat_ 型が対応する型は struct xyzzy_argsの部分で、 compat_sys_xyzzy() ルーチンはこの compat_ 構造体を使用して、32ビットの呼び出しからの引数を解析する

たとえば、フィールドがある場合、

struct xyzzy_args {
    const char __user *ptr;
    __kernel_long_t varying_val;
    u64 fixed_val;
    /* ... */
};

struct xyzzy_args にフィールドがある場合、struct compat_xyzzy_args には以下のようなフィールドがあります。

struct compat_xyzzy_args {
    compat_uptr_t ptr;
    compat_long_t varying_val;
    u64 fixed_val;
    /* ... */
};

#define __NR_xyzzy 292
__SC_COMP(__NR_xyzzy, sys_xyzzy, compat_sys_xyzzy)

  • a COMPAT_SYSCALL_DEFINEn(xyzzy, ...) 互換性エントリポイント用

  • に該当するプロトタイプを include/linux/compat.h

  • (必要に応じて) 32ビットマッピング構造体 include/linux/compat.h

  • インスタンス __SC_COMP ではありません __SYSCALL の include/uapi/asm-generic/unistd.h

互換性システムコール (x86)¶

x86アーキテクチャのシステムコールを互換性バージョンと接続するには、システムコールテーブルのエントリを調整する必要があります。

まず、以下のエントリに arch/x86/entry/syscalls/syscall_32.tbl 追加の列が追加され、64ビットカーネル上で実行される32ビットユーザースペースプログラムが互換性エントリポイントに到達するように示されます：

380   i386     xyzzy     sys_xyzzy    __ia32_compat_sys_xyzzy

次に、新しいシステムコールのx32 ABIバージョンで何が起こるかを確認する必要があります。ここで選択肢があります：引数のレイアウトは64ビットバージョンと一致するか、32ビットバージョンと一致するかのどちらかです。

ポインタのポインタが含まれる場合、決定は簡単です：x32はILP32なので、レイアウトは32ビットバージョンと一致するべきです。この場合、エントリの arch/x86/entry/syscalls/syscall_64.tbl x32プログラムが互換性ラッパーに到達するように分割されます：

333   64       xyzzy     sys_xyzzy
...
555   x32      xyzzy     __x32_compat_sys_xyzzy

ポインタが含まれていない場合、x32 ABI用に64ビットシステムコールを再利用することが望ましいです（結果として、arch/x86/entry/syscalls/syscall_64.tbl のエントリは変更されません）。

いずれの場合も、引数レイアウトに関与する型が実際にx32 (-mx32) から32ビット (-m32) または64ビット (-m64) に正確にマッピングしているかを確認する必要があります。

他の場所に戻るシステムコール¶

ほとんどのシステムコールでは、システムコールが完了した後、ユーザーのプログラムはちょうど中断した場所から再開します – 次の指令で、スタックは同じで、レジスタの多くも以前と変わりません。仮想メモリ空間も同じです。

ただし、いくつかのシステムコールは異なります。それらは異なる場所（rt_sigreturn）に戻るか、メモリ空間（fork/vfork/clone）を変更するか、あるいはアーキテクチャ（execve/execveat）を変更する可能性があります。

このような動作を許可するため、システムコールのカーネル実装では、カーネルスタックに追加のレジスタを保存・復元する必要があるかもしれません。これにより、システムコール後の実行の場所と方法を完全に制御できます。

これはアーキテクチャ固有ですが、通常はアセンブリのエントリポイントを定義し、追加のレジスタを保存・復元し、実際のシステムコールエントリポイントを呼び出すことになります。

x86_64では、これは stub_xyzzy エントリポイントとして実装され、 arch/x86/entry/entry_64.Sのシステムコールテーブルのエントリ（arch/x86/entry/syscalls/syscall_64.tbl）が調整されます：

333   common   xyzzy     stub_xyzzy

64ビットカーネル上で実行される32ビットプログラムの同等物は通常呼ばれます stub32_xyzzy および arch/x86/entry/entry_64_compat.S、対応するシステムコールテーブルの調整は arch/x86/entry/syscalls/syscall_32.tbl:

380   i386     xyzzy     sys_xyzzy    stub32_xyzzy

システムコールが互換性レイヤーを必要とする場合（前のセクションのように）であれば、 stub32_ バージョンは compat_sys_ バージョンのシステムコールに呼び出す必要があります。また、x32 ABIの実装がx86_64バージョンと異なれば、そのシステムコールテーブルもstubを呼び出す必要があり、そのstubは compat_sys_ バージョンに呼び出します。

完全性を保つために、ユーザーモードLinuxが動作するようにマッピングを設定しておくと良いです – そのシステムコールテーブルはstub_xyzzyを参照しますが、UMLビルドには arch/x86/entry/entry_64.S 実装（UMLはレジスタなどをシミュレートするため）は含まれていません。これを修正するには、#defineを追加するだけです。 arch/x86/um/sys_call_table_64.c:

#define stub_xyzzy sys_xyzzy

その他の詳細¶

カーネルの大部分はシステムコールを一般的な方法で処理しますが、特定のシステムコールに合わせて更新が必要な例外もあります。

監査サブシステムはそのような特別なケースの一つです。これは（アーキテクチャ固有の）関数を含み、特定のファイルオープン（open/openat）、プログラム実行（execve/exeveat）またはソケット多重化（socketcall）操作を分類します。新しいシステムコールがこれらに類似する場合、監査システムを更新する必要があります。

より一般的に、既存のシステムコールが新しいシステムコールに類似する場合、カーネル全体でgrepを実行して他の特別なケースがないか確認する価値があります。

テスト¶

新しいシステムコールは明らかにテストする必要があります。また、レビュワーにユーザー空間プログラムがシステムコールを使用する方法を示すデモンストレーションを提供することも役立ちます。これらの目的を組み合わせる良い方法は、新しいディレクトリの下に簡単な自己テストプログラムを含めることです。 tools/testing/selftests/.

新しいシステムコールの場合、libcのラッパー関数は存在しないため、テストは syscall()で呼び出す必要があります。また、システムコールが新しいユーザー空間可視構造を含む場合、テストをコンパイルするために対応するヘッダーをインストールする必要があります。

すべてのサポートされているアーキテクチャでselftestが成功するようにしてください。たとえば、x86_64 (-m64)、x86_32 (-m32)、x32 (-mx32) ABIプログラムとしてコンパイルした場合にも動作することを確認してください。

より広範かつ詳細な新しい機能のテストを行うためには、Linux Test Projectやファイルシステム関連の変更に使用するxfstestsプロジェクトにテストを追加することも検討してください。

  • https://linux-test-project.github.io/

  • git://git.kernel.org/pub/scm/fs/xfs/xfstests-dev.git

マニュアルページ¶

すべての新しいシステムコールは、完全なmanページを添付する必要があります。理想的にはgroffマーカップを使用しますが、プレーンテキストでも問題ありません。groffを使用する場合、パッチセットのカバーメールにmanページの事前にレンダリングされたASCII版を含めると、レビュアーの利便性に配慮できます。

manページは linux-man@vger.kernel.org 詳細は以下を参照してください https://www.kernel.org/doc/man-pages/patches.html

カーネル内でシステムコールを呼び出すことは禁止されています¶

システムコールは、上記のようにユーザー空間とカーネルの相互作用ポイントです。したがって、システムコール関数（例: sys_xyzzy() または compat_sys_xyzzy() ）は、ユーザー空間から syscall テーブルを介してのみ呼び出されるべきであり、カーネル内の他の場所から呼び出すべきではありません。システムコール機能がカーネル内で使用される必要がある場合、古いシステムコールと新しいシステムコールの間で共有される必要がある場合、またはシステムコールとその互換性バリアント間で共有される必要がある場合は、「ヘルパーファンクション」（例: kern_xyzzy()）を使用して実装する必要があります。このカーネル関数は、システムコールスタブ（sys_xyzzy()）、互換性システムコールスタブ（compat_sys_xyzzy()）、および/または他のカーネルコード内で呼び出すことができます。

少なくとも64ビットx86では、v4.17以降はカーネル内でシステムコール関数を呼び出すことは必須ではありません。システムコールの呼び出しには異なるコール・コンベンションが使用され、 struct pt_regs が即座にデコードされ、システムコール Wrapper が実際のシステムコール関数に処理を委譲します。これにより、特定のシステムコールに必要なパラメータのみがシステムコールエントリ時に渡され、常に6つのCPUレジスタにランダムなユーザー空間のコンテンツを詰め込むのではなく、呼び出しチェーンの下位で重大な問題を引き起こす可能性があります。

さらに、カーネルデータとユーザー空間データの間でデータのアクセス方法に関するルールが異なります。これがなぜ sys_xyzzy() を呼び出すことが一般的には悪いアイデアであるかのもう一つの理由です。

このルールの例外は、アーキテクチャ固有のオーバーライド、アーキテクチャ固有の互換性 Wrapper、またはarch/内の他のコードに限られます。

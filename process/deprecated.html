非推奨インターフェース、言語機能、属性、および慣例¶

理想的な世界では、非推奨APIのすべてのインスタンスを新しいAPIに変換し、1つの開発サイクルで古いAPIを完全に削除することが可能ですが、カーネルの規模、メンテナーシップ階層、タイミングの都合により、このような変換を一度に実施するのは常に現実的ではありません。これにより、古いAPIが削除される間、新しいインスタンスがカーネルに混入する可能性があり、APIを削除する作業量が増加します。開発者に非推奨のAPIについての情報を提供するため、このリストはカーネルに非推奨の要素を導入しようとする提案が行われた際の参照先として作成されました。

__deprecated¶

この属性はインターフェースを視覚的に非推奨としてマークしますが、 ビルド中に警告を出さなくなりました なぜなら、カーネルの一つの目標として、警告なしにビルドすることであり、誰もこれらの非推奨インターフェースを削除するための行動を実施していませんからです。ヘッダーファイルに古いAPIを記載するという点では良いですが、 __deprecated これは完全な解決策ではありません。このようなインターフェースは、カーネルから完全に削除するか、このファイルに追加して今後誰も使用しないように抑止する必要があります。

BUG() および BUG_ON()¶

WARN() と WARN_ON() を代わりに使用し、"不可能"なエラー状態をできるだけ穏やかに処理してください。BUG() ファミリのAPIは元々"不可能な状況"のアサーションとして設計され、カーネルスレッドを"安全に"終了させるためのものでしたが、実際にはあまりにもリスクが高すぎることが判明しました。(例: "ロックはどの順序で解放する必要がありますか？さまざまな状態は復元されていますか？") 通常、BUG() の使用はシステムを不安定にさせたり、完全に破壊したりするため、デバッグや信頼できるクラッシュレポートの取得が困難になります。Linus はこの点について 非常に強い 意見 この点について.

WARN() ファミリは"到達不可能と期待される"状況にのみ使用する必要があります。"到達可能だが不望な"状況を警告する場合は、 pr_warn()ファミリの関数を使用してください。システムオーナーは、"到達不可能"状態に遭遇してもシステムが動作を継続しないようにするため、 panic_on_warn sysctl を設定する場合があります。(例: このコミットを参照してください) このコミット.)

アロケータ引数におけるオープンコードされた算術¶

メモリ割当関数（または類似の）の引数で動的サイズ計算（特に乗算）を行うと、オーバーフローのリスクがあるため避けるべきです。これにより、値が巻き戻り、呼び出し元が予期していたよりも小さな割当が行われる可能性があります。このような割当を使用すると、ヒープメモリの線形的なオーバーフローなどの不具合が発生する可能性があります。（ただし、リテラル値の例外は、コンパイラがオーバーフローの可能性を警告できるため、この例外は存在します。以下の提案のようにリテラルを引数として使用しても問題ありません。）

例えば、以下のような引数を使用しないでください count * size という引数を、以下のように使用しないでください：

foo = kmalloc(count * size, GFP_KERNEL);

代わりに、割当関数の2因子形式を使用するべきです：

foo = kmalloc_array(count, size, GFP_KERNEL);

2因子形式が利用できない場合、オーバーフロー時に飽和する補助関数を使用するべきです：

bar = vmalloc(array_size(count, size));

回避すべきもう一つの一般的なケースは、末尾に他の構造体の配列を持つ構造体のサイズを計算する場合です。例えば：

header = kzalloc(sizeof(*header) + count * sizeof(*header->item),
                 GFP_KERNEL);

代わりに、次の補助関数を使用してください：

header = kzalloc(struct_size(header, item, count), GFP_KERNEL);

注意

ゼロ長または1要素の配列を末尾メンバとして含む構造体で struct_size() を使用している場合、このような配列の使用をリファクタリングし、柔軟な配列メンバに切り替えるべきです 柔軟な配列メンバ を呼び出してください。

参照 array_size(), array3_size(), and struct_size()の詳細情報および関連するcheck_add_overflow()とcheck_mul_overflow()関数ファミリについても参照してください。

simple_strtol(), simple_strtoll(), simple_strtoul(), simple_strtoull()¶

以下の simple_strtol(), simple_strtoll(), simple_strtoul(), and simple_strtoull() 関数はオーバーフローを明示的に無視しており、これにより呼び出し元で予期せぬ結果が発生する可能性があります。関連する kstrtol(), kstrtoll(), kstrtoul(), and kstrtoull() 関数は正しい置き換えとして一般的ですが、注意点としてそれらは文字列がNULLまたは改行で終端されている必要があります。

strcpy()¶

strcpy() 宛先バッファの境界チェックを行いません。これによりバッファの終端を超えた線形オーバーフローが発生し、さまざまな不具合が生じる可能性があります。一方で CONFIG_FORTIFY_SOURCE=y および各種コンパイラフラグはこの関数の使用リスクを減らすのに役立ちますが、この関数の新しい使用理由はまったくありません。安全な置き換えは strscpy()ただし、戻り値が使用されていた場合など、注意が必要です。 strcpy() が使用されていた場合、 strscpy() 宛先へのポインタを返すのではなく、コピーされた非NULLバイト数（または、切り捨てた場合の負のerrno）を返します。

NULL終端文字列に対してstrncpy()を使用する場合¶

の使用は strncpy() 宛先バッファがNULL終端されるとは保証しません。これは、終端が欠如しているため、さまざまな線形読み込みオーバーフローなどの問題を引き起こす可能性があります。また、ソースの内容が宛先バッファのサイズより短い場合、宛先バッファにNULLパディングを追加します。これは、NULL終端文字列のみを使用する呼び出し元にとっては不要なパフォーマンスのペナルティとなる可能性があります。安全な代替は strscpy()ただし、戻り値が使用されていた場合など、注意が必要です。 strncpy() が使用されていた場合、 strscpy() 宛先へのポインタを返すのではなく、コピーされたNULLでないバイト数（またはトリミング時に返す負のエラー番号）を返します。NULL埋めが必要なケースは、代わりに strscpy_pad().

呼び出し元がNULLでない終端の文字列を使用している場合、 strncpy() まだ使用できますが、宛先には __nonstring 属性を指定して、今後のコンパイラの警告を回避する必要があります。

strlcpy()¶

strlcpy() はソースバッファ全体を最初に読み込みます（返値が strlen()と一致するため）。この読み込みは宛先のサイズ制限を超える可能性があり、これは効率が悪く、ソース文字列がNULLでない終端でない場合、線形読み込みのオーバーフローを引き起こす可能性があります。安全な代替は strscpy()ただし、戻り値が使用されていた場合など、注意が必要です。 strlcpy() です。なぜなら strscpy() はトリミング時に負のエラー番号を返します。

%p フォーマット指定子¶

伝統的に、「%p」をフォーマット文字列で使用すると、dmesg、proc、sysfsなどにアドレス漏洩の脆弱性を引き起こしました。これらの脆弱性を悪用されないようにするため、カーネル内のすべての「%p」使用はハッシュ値として出力され、アドレスとして利用不可能にしています。新しい「%p」使用はカーネルに追加しないでください。テキストアドレスについては、「%pS」がより適切です（より有用なシンボル名を出力するため）。ほぼすべての他のケースでは、「%p」を追加しないでください。

リンスの現在の ガイドライン:

  • ハッシュされた「%p」値が意味がない場合、ポインタ自体が重要かどうかを問うべきです。完全に削除すべきかもしれませんか？

  • 本当に真のポインタ値が重要だと考えるなら、なぜ特定のシステム状態やユーザー特権レベルが「特別」とされるのでしょうか？もしコメントやコミットログで十分に正当化でき、リンスの厳格な検証に耐えられるなら、「%px」を使用し、適切な権限を確保することも可能です。

最後に、％pハッシュのトグルは 受け入れられません.

スタック上のVLAを使用すると、静的サイズのスタック配列よりも劣る機械コードを生成します。これらの非自明なパフォーマンス問題は、VLAを削除する理由になるだけでなく、セキュリティリスクにもなります。スタック配列の動的拡張がスタックセグメントの残りメモリを超える可能性があり、これによりクラッシュやスタックの終わりに配置されたセンシティブなコンテンツの上書き（CONFIG_THREAD_INFO_IN_TASK=yを無効にした場合） パフォーマンス問題 、スタックに隣接したメモリの上書き（CONFIG_VMAP_STACK=yを無効にした場合） CONFIG_THREAD_INFO_IN_TASK=y)、または CONFIG_VMAP_STACK=y)

暗黙のswitchケースのfall-through¶

C言語では、switch文のcaseブロックで「break」文が省略されている場合、次のcaseブロックに制御が移る（fall through）ことが許容されています。しかし、この仕様はコードに曖昧さを生じさせます。なぜなら、省略されたbreakが意図的なものであるか、バグであるかが明確でないからです。たとえば、コードを単に見ただけでは、 STATE_ONE が意図的に次の STATE_TWO:

switch (value) {
case STATE_ONE:
        do_something();
case STATE_TWO:
        do_other();
        break;
default:
        WARN("unknown state");
}

に制御が移るのか、それともバグなのかが明らかではありません。 これまでに多数の問題が、省略された「break」文によって引き起こされてきました。そのため、我々は明示的なfall throughを許可しなくなりました。意図的なfall throughを識別するため、擬似キーワードマクロ「fallthrough」を導入しました。このマクロはgccの拡張機能 __attribute__((__fallthrough__))に展開されます。(C17/C18 [[fallthrough]] 構文がCコンパイラ、静的解析ツール、IDEでより広くサポートされるようになった場合、このマクロ擬似キーワードの代わりにその構文を採用する予定です。)

すべてのswitch/caseブロックは次のいずれかで終了しなければなりません:

  • break;

  • fallthrough;

  • continue;

  • goto <label>;

  • return [expression];

ゼロ長と単一要素の配列¶

カーネルでは、構造体に動的にサイズが変化する末尾要素を宣言する必要がある場合があります。このようなケースでは常に 「flexible array members」 を使用する必要があります。古いスタイルの単一要素またはゼロ長配列はもはや使用すべきではありません。

古いCコードでは、動的にサイズが変化する末尾要素は構造体の最後に単一要素の配列を指定することで実現されていました:

struct something {
        size_t count;
        struct foo items[1];
};

これはsizeof()によるサイズ計算に脆弱性を生じさせました（正確な「ヘッダ」のサイズを得るために、単一要素のサイズを引く必要がありました）。そのため、 GNU C拡張機能 が導入され、ゼロ長配列を許可することで、このようなサイズ計算の問題を回避するようになりました:

struct something {
        size_t count;
        struct foo items[0];
};

しかし、これにより他の問題が生じ、両スタイルに共通する問題（例えば、このような配列が構造体の末尾でない場合に誤って使用されているかどうかの検出不能）は解決されませんでした。

C99では「flexible array members」が導入され、配列宣言に数値サイズを完全に省略しています:

struct something {
        size_t count;
        struct foo items[];
};

これはカーネルが動的にサイズが変化する末尾要素を宣言するための方法です。これは、柔軟な配列が構造体の最後にない場合にコンパイラがエラーを生成できるようにし、コードベースに意図せずに未定義動作のバグが導入されるのを防ぎます。また、コンパイラが配列サイズを正しく分析できるようにし（sizeof()を通じて、 未定義動作 のバグを防ぐとともに、 CONFIG_FORTIFY_SOURCE, and CONFIG_UBSAN_BOUNDS). 例えば、ゼロ長さの配列にsizeof()演算子を適用した際に常にゼロになるという事実を私たちに警告する仕組みは存在しません:

struct something {
        size_t count;
        struct foo items[0];
};

struct something *instance;

instance = kmalloc(struct_size(instance, items, count), GFP_KERNEL);
instance->count = count;

size = sizeof(instance->items) * instance->count;
memcpy(instance->items, source, size);

上記コードの最後の行で size 結果として zero、これは以前に割り当てられた末尾配列の動的メモリの総バイト数を表していると考えられていたにもかかわらず items. この問題の例をいくつか示します: link 1, link 2. 代わりに flexible array membersは不完全な型を持ち、sizeof()演算子を適用できないため、このような演算子の誤用はビルド時にすぐに検出されます。

1要素の配列については、以下の点に注意する必要があります 、このような配列は、その型の単一オブジェクトと同程度以上の空間を占有します、したがって、このような配列は包含構造体のサイズに寄与します。このため、このような配列をメンバーとして含む構造体の動的メモリを割り当てる際の総サイズを計算するたびにエラーが発生しやすくなります:

struct something {
        size_t count;
        struct foo items[1];
};

struct something *instance;

instance = kmalloc(struct_size(instance, items, count - 1), GFP_KERNEL);
instance->count = count;

size = sizeof(instance->items) * instance->count;
memcpy(instance->items, source, size);

上記の例では、計算を忘れないようにしなければなりませんでした count - 1 ヘルパーを使用する際には struct_size() 、ヘルパーを使用しないと、意図せず1つ多いオブジェクトのメモリを割り当ててしまう可能性があります items この実装の最も清潔でエラーの少ない方法は、 柔軟な配列メンバを一緒に使用することで struct_size() および flex_array_size() ヘルパー:

struct something {
        size_t count;
        struct foo items[];
};

struct something *instance;

instance = kmalloc(struct_size(instance, items, count), GFP_KERNEL);
instance->count = count;

memcpy(instance->items, source, flex_array_size(instance, items, instance->count));

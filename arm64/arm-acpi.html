ARMv8サーバーにおけるACPI¶

ACPI は ARMv8 サーバーで、ARM SBSA（Server Base System Architecture）[0] および SBBR（Server Base Boot Requirements）[1] の仕様に準拠した汎用サーバー向けに使用できます。注意点として、SBBR は [1] にアクセスするだけで取得可能です。ただし、SBSA は ARM ログインを持つユーザーのみが現在アクセスできるため、ARM IP ライセンスに関する制約があります。

ARMv8 カーネルは ACPI 版 5.1 またはそれ以降の簡略化されたハードウェアモデルを実装しています。仕様およびその参照するすべての外部ドキュメントへのリンクは UEFI Forum が管理しています。仕様は以下から確認できます。 http://www.uefi.org/specifications この仕様で参照されるドキュメントは、以下から確認できます http://www.uefi.org/acpi.

ARMv8 システムが SBSA および SBBR の要件を満たさない、または必要な ACPI 仕様で定義されたメカニズムで記述できない場合、ACPI はハードウェアにとって良い選択肢とは限りません。

上記のドキュメントは、産業標準の ARMv8 サーバーを構築するための要件を示していますが、それらは1つ以上のオペレーティングシステムにも適用されます。このドキュメントの目的は、ARMv8 システムにおける ACPI と Linux の相互作用についてのみ説明することです。つまり、Linux が ACPI から期待するものと、ACPI が Linux から期待するものです。

なぜ ARM に ACPI が必要なのか？¶

ACPI と Linux のインターフェースの詳細を検討する前に、なぜ ACPI が使用されるのか理解することが役立ちます。畢竟、Linux には非列挙ハードウェアを記述するための技術はすでに存在しています。このセクションでは、Grant Likely 氏が書いたブログ記事 [2] を要約した内容を紹介しています。実際には、この要約テキストの多くをほぼ直接的に引用しています。

ACPI が ARM で使用される理由の要約は以下の通りです：

  • ACPI のバイトコード（AML）はハードウェアの動作をエンコードできるのに対し、DT はこれをサポートしていません。ハードウェアベンダーにとって、動作をエンコードする機能は、新しいハードウェアでのOSリリースをサポートするための重要なツールです。

  • ACPI の OSPM は、プラットフォームが特定のモデルに制限されるようにする一方で、ハードウェア設計に柔軟性を提供する電源管理モデルを定義しています。

  • 企業向けサーバー環境では、ACPI は RAS（Reliability, Availability, and Serviceability）などのバインディングが確立されており、現在の生産環境で使用されています。DT にはこのようなバインディングは存在しません。このようなバインディングは DT で定義される可能性もありますが、そうすると ARM と x86 はファームウェアおよびカーネルの両方で完全に異なるコードパスを使用することになります。

  • プラットフォームとOS間の抽象化を記述するための単一インターフェースを採用することは重要です。ハードウェアベンダーが複数のオペレーティングシステムをサポートしたい場合、DTとACPIの両方を実装する必要はありません。また、OSごとのインターフェースに分断されるのではなく、単一インターフェースに合意することで、全体的な相互運用性が向上します。

  • 新しいACPIガバナンスプロセスはうまく機能しており、Linuxはハードウェアベンダーおよび他のOSベンダーと同様にテーブルに座っています。実際、ACPIがWindows専有であるという理由や、Linuxがマイクロソフトに対する二流であるという思いはもうありません。ACPIガバナンスがUEFIフォーラムに移管されたことで、仕様開発プロセスが大幅にオープンになり、現在、ACPIへの変更の多くはLinuxによって推進されています。

ACPIの利用において重要なのはサポートモデルです。一般的なサーバーでは、ハードウェアの動作責任をカーネルに一括して委ねるのではなく、プラットフォームとカーネルの間で分担する必要があります。これにより、時間とともに秩序ある変更が可能になります。ACPIはOSがハードウェアのすべての詳細を理解する必要がないようにし、OSが各デバイスごとに移植する必要がないようにします。これにより、ハードウェアベンダーがOSのリリースサイクルに依存することなく、電源管理の動作責任を引き受けることが可能になります。

ACPIはまた、ハードウェアベンダーとOSベンダーがすでに汎用コンピューティングエコシステムをサポートするためのメカニズムを整えているため重要です。インフラストラクチャ、バインディング、プロセスがすでに整っています。DTは垂直統合デバイスと作業する際、Linuxが求める機能を正確に果たしますが、サーバーベンダーが必要とするサポートプロセスは存在していません。LinuxはDTを通じてその目標に到達するかもしれませんが、これによりすでに機能しているものを単に複製するだけになります。ACPIはすでにハードウェアベンダーが必要とする機能を果たしており、マイクロソフトはDTに協力しないことから、ハードウェアベンダーは依然としてLinux用とWindows用の完全に分離されたファームウェアインターフェースを提供することになります。

カーネルの互換性¶

ACPIの主な動機の一つは標準化であり、これによりLinuxカーネルの後方互換性を提供することです。サーバー市場ではソフトウェアやハードウェアが長期間使用されることが多く、ACPIはカーネルとファームウェアが時間とともにハードウェアやソフトウェアが変化しても維持可能な一貫した抽象化を合意できるようにします。抽象化がサポートされている限り、システムの更新は必ずしもカーネルの置き換えを必要としません。

Linuxドライバやサブシステムが最初にACPIで実装される場合、それはACPI仕様の特定バージョンを前提としています。これはベースラインと定義されます。ACPIファームウェアは、そのベースラインバージョンのACPIをサポートする最初のカーネルバージョンと互換性を保ちながら動作しなければなりません。最適な性能を維持する必要はなく、古いカーネルバージョンでも動作する必要があります。さらに、ACPIファームウェアは最新のカーネルバージョンとも動作可能でなければなりません。

デバイスツリーとの関係¶

ARMv8向けドライバやサブシステムにおけるACPIサポートは、コンパイル時にデバイスツリー（DT）サポートと競合しないようにする必要があります。

ブート時にカーネルは、ブートローダーから渡されたパラメータ（含むカーネルのブート引数）に応じて1つの記述方法のみを使用します。

DTやACPIのどちらが使用されようとも、カーネルは常にどちらのスキーマでも起動可能でなければなりません（両方のスキーマがコンパイル時に有効化されている場合）。

ACPIテーブルを使用したブート¶

ARMv8でカーネルにACPIテーブルを渡す唯一の定義された方法はUEFIシステム構成テーブル経由です。明示的に述べるまでもありませんが、これはUEFIでブートするプラットフォームでのみACPIがサポートされることを意味します。

ARMv8システムがブートする際、DT情報、ACPIテーブル、または極めて特殊なケースでは両方を持つことができます。コマンドラインパラメータが使われない場合、カーネルはデバイスの列挙にDTを使用しようとします。DTが存在しない場合、カーネルはACPIテーブルを使用しようとしますが、それらが存在しなければなりません。どちらも存在しない場合、カーネルは起動しません。コマンドラインにacpi=forceが指定されている場合、カーネルはまずACPIテーブルを使用しようとしますが、ACPIテーブルが存在しない場合はDTにフォールバックします。基本的な考え方は、カーネルが起動失敗するのは、他の選択肢が全くない場合のみです。

カーネルコマンドラインにacpi=offを指定すると、ACPIテーブルの処理が無効になります。これはデフォルトの動作です。

カーネルがACPIテーブルをロードし使用するためには、UEFI実装はACPI_20_TABLE_GUIDをRSDPテーブル（ACPIサインナチュア「RSD PTR」を持つテーブル）にポインタを設定しなければなりません。このポインタが不正確でacpi=forceが使用された場合、カーネルはACPIを無効にしてDTを使用して起動を試みます。これにより、カーネルはその時点でACPIテーブルが存在しないと判断しています。

RSDPテーブルへのポインタが正しい場合、UEFIが提供するアドレスを使用してACPIコアがテーブルをカーネルにマッピングします。

次にACPIコアは、RSDPテーブル内のアドレスを使用してXSDT（eXtended System Description Table）を検索・マッピングします。XSDTはシステムファームウェアが提供する他のすべてのACPIテーブルのアドレスを提供し、ACPIコアはこのテーブルをトラバースしてリストに記載されたテーブルをマッピングします。

ACPIコアは提供されたRSDT（Root System Description Table）を無視します。RSDTはアーキテクチャごとのレガシハードウェアをサポートするためのものであり、arm64では廃止されており無視されます。

さらに、ACPIコアはFADT（Fixed ACPI Description Table）内の64ビットアドレスフィールドのみを使用します。arm64ではFADT内の32ビットアドレスフィールドは無視されます。

ハードウェア簡略モード（ACPI 6.1仕様の第4.1節参照）はarm64でACPIコアが強制されます。これにより、ACPIコアはレガシハードウェアのサポートを提供しなくても済むため、より簡潔なコードで動作できます。ハードウェア簡略モードで使用しないフィールドはすべてゼロに設定しなければなりません。

カーネルがデバイスを構成するために必要な情報を提供するため、ACPIコアは以下のテーブルを検出する必要があります（すべてのセクション番号はACPI 6.1仕様を参照）：

  • RSDP（Root System Description Pointer）、5.2.5節

  • XSDT（eXtended System Description Table）、5.2.8節

  • FADT（Fixed ACPI Description Table）、5.2.9節

  • DSDT（Differentiated System Description Table）、5.2.11.1節

  • MADT（Multiple APIC Description Table）、5.2.12節

  • GTDT（Generic Timer Description Table）、5.2.24節

  • PCIがサポートされている場合、MCFG（Memory mapped ConFiGuration Table）、5.2.6節、特に表5-31。

  • コンソール=<デバイス>を指定せずに起動がサポートされている場合、SPCR（Serial Port Console Redirection table）、5.2.6節、特に表5-31。

  • I/Oトポロジ、SMMUs、GIC ITSsを記述する必要がある場合、IORT（Input Output Remapping Table）、5.2.6節、特に表5-31。

  • NUMAがサポートされている場合、SRAT（System Resource Affinity Table）とSLIT（System Locality distance Information Table）がそれぞれ5.2.16節と5.2.17節に記載されています。

上記のテーブルがすべて存在しない場合、カーネルが正しく起動できるかどうかは不明です。すべてのデバイスを正しく設定できない可能性があるためです。このテーブルの一覧は完全ではありません。特定の機能をサポートするために、一部の環境では他のテーブル（例：18節にある任意のAPEIテーブル）が必要になる場合があります。

ACPIの検出¶

ドライバは、ACPI_HANDLEがNULL値であるか、.of_nodeを確認するか、デバイス構造体の他の情報を確認することでprobe()タイプを判定する必要があります。詳細については「ドライバの推奨事項」セクションで説明しています。

ドライバ以外のコードでは、実行時にACPIの存在を検出する必要がある場合、acpi_disabledの値を確認してください。CONFIG_ACPIが設定されていない場合、acpi_disabledは常に1になります。

デバイスの列挙¶

ACPIでのデバイス説明では、標準的な認識されているACPIインターフェースを使用する必要があります。これらには、同じデバイスに対してデバイスツリーの説明で通常提供される情報よりも少ない情報しか含まれていない場合があります。これはACPIが有用な理由の一つであり、ドライバはデバイスに関する詳細情報が不足している可能性を考慮し、合理的なデフォルト値を使用します。ドライバが適切に実装されている場合、ハードウェアは時間とともに変化・改善しても、ドライバを変更することなく動作できます。

クロックは良い例です。DTではクロックを明示的に指定し、ドライバがそれを考慮する必要があります。一方、ACPIではUEFIがデバイスを合理的なデフォルト状態（含むクロック設定）に残すと仮定しています。もしドライバがクロック値を変更する必要がある場合、ACPIメソッド内でこれを実行できます。ドライバはメソッドがクロックを変更する方法を気にせず、単にメソッドを呼び出すだけでよいです。時間とともにハードウェアの変更は、ACPIメソッドの内容を変更することで実現でき、ドライバを変更する必要はありません。

DTでは、ドライバがクロックを設定するために必要なパラメータは「バインディング」と呼ばれます。ACPIではこれらは「デバイスプロパティ」と呼ばれ、_DSDオブジェクトを通じてドライバに提供されます。

ACPIテーブルは、ACPIソース言語（ASL）という形式的な言語で記述されます（仕様書のセクション19）。これは、同じものを記述する方法が常に複数存在することを意味します。デバイスプロパティも同様で、例えばデバイスプロパティはASL構文で「Name(KEY0, "value0")」のように記述されることがあります。この場合、ACPIデバイスドライバーはKEY0オブジェクトを評価してプロパティの値を取得します。しかし、Name()をこのように使用するにはいくつかの問題があります：(1) ACPIは名前（"KEY0"）を4文字以内に制限しているのに対し、DTは制限がありません；(2) 名前の一覧を維持する業界標準の登録機関が存在しないため、再利用が困難です；(3) プロパティ値（"value0"）の定義に関する登録機関も存在しないため、再利用が困難です；(4) 新しいハードウェアが登場するたびに後方互換性を維持する方法は？この種の問題を解決するために_DSDメソッドが作成されました。Linuxドライバーは常に_DSDメソッドを使用してデバイスプロパティを記述し、他の方法は使用しないべきです。

_DSMオブジェクト（ACPIセクション9.14.1）もドライバーにデバイスプロパティを伝達するために使用できます。Linuxドライバーは、_DSDがデータを表現できない場合や、_DSDオブジェクト用に新しいUUIDを生成できない場合にのみ_DSMを使用するものと期待すべきです。注意点として、_DSMの使用に関する規制は_DSDよりさらに少なく、これにより_DSMオブジェクトの内容に依存するドライバーは時間とともにメンテナビリティが低下します。執筆時点では、_DSMの使用は多数のファームウェア問題を引き起こしており、推奨されません。

ドライバーは常に_DSDオブジェクトのみにデバイスプロパティを検索すべきです。_DSDオブジェクトはACPI仕様書のセクション6.2.5で記述されていますが、これは_DSDを介して返されるオブジェクトの構造を定義する方法や、特定UUIDで特定データ構造を定義する方法についてのみ説明しています。Linuxは常に_DSDデバイスプロパティUUID [5] を使用すべきです：

  • UUID: daffd814-6eba-4d8c-8a91-bc9bbf4aa301

  • https://www.uefi.org/sites/default/files/resources/_DSD-device-properties-UUID.pdf

UEFIフォーラムは、デバイスプロパティをすべてのACPIをサポートするオペレーティングシステムで使用できるようにするための登録メカニズムを提供しています [4]。UEFIフォーラムに登録されていないデバイスプロパティは使用すべきではありません。

新しいデバイスプロパティを作成する前に、すでに定義されていないかを確認してください。LinuxカーネルドキュメンテーションでのDTバインディングとして登録されているか、またはUEFIフォーラムでのデバイスプロパティとして登録されているかを確認してください。すべてのDTバインディングを単にACPIデバイスプロパティに移すことは望んでいませんが、これまでに定義された内容から学ぶことはできます。

新しいデバイスプロパティを定義する必要がある場合、またはバインディングの定義を合成して任意のファームウェアで使用可能にするのが合理的な場合、DTバインディングとACPIデバイスプロパティの両方がレビュープロセスを経ます。両方を活用してください。ドライバ自体がLinuxメーリングリストにレビュー対象として提出される際には、必要なデバイスプロパティの定義も同時に提出する必要があります。ACPIをサポートしデバイスプロパティを使用するドライバは、その定義がなければ完全とはみなされません。デバイスプロパティがLinuxコミュニティによって承認されると、UEFIフォーラム[4]に登録する必要があります。UEFIフォーラムは、登録されたプロパティがレジストリ内で整合性を保っているか再度レビューします。これは繰り返しの必要があるかもしれません。UEFIフォーラムは、デバイスプロパティ定義の公式なソースとなるでしょう。

以前に使用されていないデバイスプロパティ名を登録する意向があることをUEFIフォーラムに通知することが、今後の使用のために名前を確保する手段として意味があるかもしれません。他のOSベンダーも登録申請を提出するため、このプロセスをスムーズにする助けになります。

登録とレビューが完了した後、カーネルはDTやACPIを問わずデバイスプロパティを検索するためのインターフェースを提供します。このAPI[6]を使用すべきです。これによりドライバプローブ関数内のコードパスの重複を減らし、DTバインディングとACPIデバイスプロパティの分離を抑制できます。

プログラマブルな電源制御リソース¶

プログラマブルな電源制御リソースには、電圧/電流提供者（レギュレータ）やクロックソースなどのリソースが含まれます。

ACPIでは、カーネルのクロックおよびレギュレータフレームワークは一切使用されません。

カーネルは、これらのリソースの電源制御がPower Resource Objects（ACPIセクション7.1）で表現されていると想定しています。ACPIコアは、必要なときにリソースを正しく有効化および無効化します。この動作を実現するため、ACPIは各デバイスがD-statesを定義していると想定し、これらをオプションのACPIメソッド _PS0、_PS1、_PS2、_PS3を通じて制御できるとします。ACPIでは、_PS0はデバイスを完全にオンにし、_PS3は完全にオフにするメソッドです。

Power Resourcesの利用には2つのオプションがあります。これらは:

  • power state Dxに入る際に呼び出される_PSxメソッドで管理されます。

  • 電源リソースとして個別に宣言され、それぞれの_ONと_OFFメソッドを持つ。その後、_PRxを通じて特定のデバイスがD状態に接続され、そのデバイスがDx状態にあるときに必要な電源リソースが指定される。カーネルは電源リソースを使用するデバイスの数を追跡し、必要に応じて_ON/_OFFメソッドを呼び出す。

カーネルのACPIコードは、_PSxメソッドが通常のACPIルールに従うと仮定する。

  • _PS0または_PS3のいずれかが実装されている場合、もう一方のメソッドも必ず実装されている必要がある。

  • デバイスがON状態で電源リソースを使用する必要がある場合、ASLはそのリソースが_PS0メソッドを通じて割り当てられ/有効化されることを明示するべきである。

  • _PS0メソッドで割り当てられ/有効化されたリソースは、_PS3メソッドで無効化または解放されるべきである。

  • ファームウェアはカーネルに制御を委譲する前に、リソースを適切な状態に保つ。

_PSxメソッド内のコードはプラットフォーム固有になるが、これによりドライバーがデバイスのインターフェースを抽象化し、ACPIテーブルから非標準的な値を読み取る必要がなくなる。さらに、これらのリソースの使用を抽象化することで、ハードウェアが時間とともに変化してもドライバーの更新が不要になる。

クロック¶

ACPIは、制御をカーネルに委譲する前に、ファームウェア（ここではUEFI）がクロックをある動作可能な値に初期化していると仮定する。これはUARTやSoC駆動のLCDディスプレイなどのデバイスに影響を与える。

カーネルが起動する際、クロックは適切な動作値に設定されていると仮定される。もし何らかの理由で周波数が変更が必要な場合（例：電源管理用のスロットリング）、デバイスドライバーはそのプロセスがACPIメソッドを通じて抽象化されていることを期待する（詳細はACPI仕様を参照）。例外はCPUクロックで、CPPCがACPIメソッドよりも豊富なインターフェースを提供するためである。クロックが設定されていない場合、Linuxが直接制御する方法は存在しない。

SoCベンダーがシステムクロックの詳細な制御を提供したい場合、Linuxドライバーが呼び出せるACPIメソッドを提供することで実現できます。ただし、これは推奨されず、Linuxドライバーはこのようなメソッドを提供されても使用すべきではありません。このようなメソッドは現在のACPI仕様で標準化されておらず、使用するとカーネルを特定のSoCに、またはSoCを特定のカーネルバージョンに結びつける可能性があり、これらは避けようとしている問題です。

ドライバーに関する推奨事項¶

DTの処理を削除しないでください。同じデバイスがさまざまなシステムで使用される可能性があるからです。

ドライバーをデータ駆動型の構造にすることを試みてください。つまり、ドライバーのプローブ関数で発見する必要のある情報に基づき、デバイスごとの内部状態を含む構造体を設定し、その後のドライバー処理をこの構造体の内容に依存させるようにします。これにより、ACPIとDT機能の差異はプローブ関数内に局所化され、ドライバー全体に散らばることを防げます。例えば：

static int device_probe_dt(struct platform_device *pdev)
{
       /* DT specific functionality */
       ...
}

static int device_probe_acpi(struct platform_device *pdev)
{
       /* ACPI specific functionality */
       ...
}

static int device_probe(struct platform_device *pdev)
{
       ...
       struct device_node node = pdev->dev.of_node;
       ...

       if (node)
               ret = device_probe_dt(pdev);
       else if (ACPI_HANDLE(&pdev->dev))
               ret = device_probe_acpi(pdev);
       else
               /* other initialization */
               ...
       /* Continue with any generic probe operations */
       ...
}

DTおよびACPIからプローブされるデバイス名を明確にするため、ドライバー内でMODULE_DEVICE_TABLEのエントリをまとめてください：

static struct of_device_id virtio_mmio_match[] = {
        { .compatible = "virtio,mmio", },
        { }
};
MODULE_DEVICE_TABLE(of, virtio_mmio_match);

static const struct acpi_device_id virtio_mmio_acpi_match[] = {
        { "LNRO0005", },
        { }
};
MODULE_DEVICE_TABLE(acpi, virtio_mmio_acpi_match);

ASWG¶

ACPI仕様は定期的に変更されます。例えば2014年にはバージョン5.1がリリースされ、バージョン6.0はARM固有の要件によって大幅に完成しました。提案された変更はUEFIフォーラムのASWG（ACPI仕様作業グループ）で提示・議論され、現在のACPI仕様は2016年1月にバージョン6.1がリリースされました。

このグループへの参加はUEFI会員であれば誰でも可能です。詳細については http://www.uefi.org/workinggroup をご覧ください。

ARMv8 ACPIカーネルコードは、ACPI仕様にできるだけ忠実に従うことを意図しており、UEFI ASWGが公開した標準に準拠した機能のみを実装することを目的としています。実際の運用では、一部のベンダーが不良なACPIテーブルを提供したり、標準に違反する場合があります。これはエラーによるものである場合、クイックや修正が求められるかもしれませんが、可能な限り回避します。ACPIがプラットフォームで使用できない機能が欠如している場合、ASWGにECR（エンジニアリング・チェンジ・リクエスト）を提出し、通常の承認プロセスを経る必要があります。UEFI会員でない場合でも、Linuxコミュニティの多くのメンバーがECRの提出に協力してくれる可能性があります。

Linuxコード¶

ARM上でのLinux固有の項目は、以下のリストに含まれています：

ACPI_OS_NAME

このマクロは、ACPIメソッドが_OSメソッドを呼び出す際の返却文字列を定義します。ARM64システムではデフォルトで「Linux」となります。コマンドラインパラメータacpi_os=<string>を使用して他の値に設定できます。他のアーキテクチャではデフォルトで「Microsoft Windows NT」が設定されます（例）。

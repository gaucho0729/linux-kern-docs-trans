AArch64 Linuxの起動¶

著者: Will Deacon <will.deacon@arm.com>

日付: 2012年9月7日

このドキュメントはRussell KingによるARM起動ドキュメントに基づいており、AArch64 Linuxカーネルのすべてのパブリックリリースに関連しています。

AArch64例外モデルは、複数の例外レベル（EL0 - EL3）から構成され、EL0とEL1にはセキュアな counterpart と非セキュアな counterpart があります。EL2はハイパーバイザレベルで、非セキュアモードのみ存在します。EL3は最高優先度レベルで、セキュアモードのみ存在します。

このドキュメントでは、以下の用語を単に「ブートローダー」として使用します。 ブートローダー CPU上で制御がLinuxカーネルに渡る前に実行されるすべてのソフトウェアを指します。これにはセキュアモニターやハイパーバイザコードが含まれる場合もありますが、最小限のブート環境を準備するための少数の命令だけの場合もあります。

基本的に、ブートローダーは以下のものを提供する必要があります（最低限）:

  1. RAMの設定と初期化

  2. デバイスツリーの設定

  3. カーネルイメージの展開

  4. カーネルイメージの呼び出し

1. RAMの設定と初期化¶

要件: 必須

ブートローダーは、カーネルがシステムで揮発性データストレージとして使用するすべてのRAMを検出・初期化する必要があります。これは機種依存の方法で実行されます。（内部アルゴリズムを用いてすべてのRAMを自動的に検出・サイズ指定するか、機種のRAMに関する知識を使用するか、ブートローダー設計者に任せる他の方法を使用する可能性があります。）

2. デバイスツリーの設定¶

要件: 必須

デバイスツリーのblob（dtb）は8バイト境界に配置され、サイズは2メガバイトを超えてはなりません。dtbは2メガバイトのブロックでキャッシュ可能にマッピングされるため、特定の属性でマッピングされる2M領域内に配置してはなりません。

注意: v4.2以前のバージョンでは、dtbはkernel Imageのtext_offsetバイト下の512MB領域内に配置する必要があります。

3. カーネルイメージの展開¶

要件: オプション

AArch64カーネルは現在、デコンプレッサーを提供していないため、ブートローダーがgzipなどの展開を実行する必要があります。ブートローダーがこの要件を実装していない場合、展開されていないImageターゲットが代わりに利用できます。

4. カーネルイメージの呼び出し¶

要件: 必須

展開されたカーネルイメージには次の64バイトのヘッダーが含まれています。

u32 code0;                    /* Executable code */
u32 code1;                    /* Executable code */
u64 text_offset;              /* Image load offset, little endian */
u64 image_size;               /* Effective Image size, little endian */
u64 flags;                    /* kernel flags, little endian */
u64 res2      = 0;            /* reserved */
u64 res3      = 0;            /* reserved */
u64 res4      = 0;            /* reserved */
u32 magic     = 0x644d5241;   /* Magic number, little endian, "ARM\x64" */
u32 res5;                     /* reserved (used for PE COFF offset) */

ヘッダーに関する注意点:

  • v3.17以降、すべてのフィールドはリトルエンディアンです（特に記載がない限り）。

  • code0/code1はstextへのジャンプを担当します。

  • EFIでブートする場合、code0/code1は最初にスキップされます。res5はPEヘッダーへのオフセットで、PEヘッダーにはEFIエントリポイント（efi_stub_entry）が含まれています。スタブが作業を終えたら、code0にジャンプして通常のブートプロセスを再開します。

  • v3.17以前では、text_offsetのエンディアンは指定されていませんでした。このような場合、image_sizeはゼロであり、text_offsetはカーネルのエンディアンに基づいて0x80000です。image_sizeがゼロでない場合、image_sizeはリトルエンディアンであり、尊重する必要があります。image_sizeがゼロの場合、text_offsetは0x80000とみなせます。

  • フラグフィールド（v3.17で導入）は、リトルエンディアンの64ビットフィールドで、以下のようになります：

    ビット0

    カーネルのエンディアン。BEの場合は1、LEの場合は0。

    ビット1-2

    カーネルのページサイズ。

    • 0 - 指定なし。

    • 1 - 4K

    • 2 - 16K

    • 3 - 64K

    ビット3

    カーネルの物理配置

    0

    2MBアライメントされたベースはDRAMのベースにできるだけ近づけるべきです。なぜなら、その下のメモリは線形マッピングでアクセスできませんから。

    1

    2MBアライメントされたベースは物理メモリのどこでも可能です。

    ビット4-63

    予約済み。

  • image_sizeがゼロの場合、ブートローダーはカーネルイメージの終了直後にカーネルが使用できるように可能な限り多くのメモリを確保する必要があります。必要な領域のサイズは選択した機能により異なり、実質的に制限はありません。

イメージはシステムRAMのどこかにある2MBアライメントされたベースアドレスからtext_offsetバイトずれた場所に配置され、そこで呼ばれる必要があります。2MBアライメントされたベースアドレスとイメージの開始地点の間の領域はカーネルにとって特別な意味を持たず、他の用途に使用可能です。イメージの開始地点から少なくともimage_sizeバイトはカーネルが使用できるように確保しなければなりません。注意：v4.6以前のバージョンはイメージの物理オフセット以下のメモリを使用できませんので、システムRAMの開始にできるだけ近い場所にイメージを配置することをお勧めします。

起動時にカーネルにinitrd/initramfsが渡される場合、その全体が最大32GBのサイズの1GBアライメントされた物理メモリの窓内に配置され、カーネルイメージを完全にカバーする必要があります。

カーネルに記述されたすべてのメモリ（イメージの開始以下のメモリを含む）で、カーネルが予約されていない（例：デバイスツリーにmemreserve領域を指定していない）ものは、カーネルが使用可能なメモリとみなされます。

カーネルにジャンプする前に以下の条件を満たす必要があります：

  • DMAをサポートするすべてのデバイスを停止し、メモリが不正なネットワークパケットやディスクデータによって破損しないようにします。これにより、デバッグにかかる時間を大幅に短縮できます。

  • プライマリCPUの汎用レジスタの設定：

    • x0 = システムRAM内のデバイスツリーBLOB（dtb）の物理アドレス。

    • x1 = 0（今後の利用のために予約済み）

    • x2 = 0（今後の利用のために予約済み）

    • x3 = 0（今後の利用のために予約済み）

  • CPUモード

    すべての割込みはPSTATE.DAIF（デバッグ、SError、IRQ、FIQ）でマスクする必要があります。CPUはEL2（仮想化拡張機能へのアクセスを目的としたため推奨）またはセキュアでないEL1でなければなりません。

  • キャッシュ、MMU

    MMUはオフにする必要があります。

    インストラクションキャッシュはオンまたはオフのいずれかでなければならず、ロードされたカーネルイメージに対応する古いエントリを保持してはならない。

    ロードされたカーネルイメージに対応するアドレス範囲はPoCにクリーンアップしなければならない。システムキャッシュやその他のキャッシュを有効にしたコヒーレントマスターが存在する場合、これは通常VAによるキャッシュメンテナンスが必要となり、セット/ウェイ操作ではなくなる。アーキテクチャ定義のVAによるキャッシュメンテナンスを尊重するシステムキャッシュは設定され、有効化されるべきである。アーキテクチャ定義のVAによるキャッシュメンテナンスを尊重しないシステムキャッシュ（推奨されない）は設定され、無効化されるべきである。

  • アーキテクチャ定義のタイマ

    CNTFRQにはタイマ周波数を設定し、CNTVOFFにはすべてのCPUで一貫した値を設定しなければならない。EL1でカーネルに移行する場合、CNTHCTL_EL2にはEL1PCTEN（ビット0）を設定しなければならない。

  • コヒーレンシー

    カーネルに移行するすべてのCPUは、カーネルのエントリ時に同じコヒーレンシードメインに属している必要がある。これは、各CPUでメンテナンス操作を受けるためにIMPLEMENTATION DEFINED初期化が必要となる場合がある。

  • システムレジスタ

    カーネルイメージが移行される例外レベルにおけるすべての書き込み可能なアーキテクチャ定義システムレジスタは、より高い例外レベルでソフトウェアによって初期化されなければならない。これにより、UNKNOWN状態での実行を防ぐ。

    • SCR_EL3.FIQは、カーネルが実行されるすべてのCPUで同じ値を保持しなければならない。

    • カーネルが実行されるたびに、SCR_EL3.FIQの値は起動時と同じでなければならない。

    GICv3割り込みコントローラーをv3モードで使用するシステムの場合：

    • EL3が存在する場合、ICC_SRE_EL3.Enable（ビット3）は0b1に初期化しなければならない。

    • ICC_SRE_EL3.SRE（ビット0）は0b1に初期化しなければならない。

    • ICC_CTLR_EL3.PMHE（ビット6）は、カーネルが実行されるすべてのCPUで同じ値に設定され、カーネルの寿命を通じて変更してはならない。

    • カーネルがEL1で移行される場合：

      • ICC.SRE_EL2.Enable（ビット3）は0b1に初期化しなければならない。

      • ICC_SRE_EL2.SRE（ビット0）は0b1に初期化しなければならない。

    • DTまたはACPIテーブルはGICv3割り込みコントローラーを記述しなければならない。

    GICv3割り込みコントローラーを互換性（v2）モードで使用するシステムの場合：

    • EL3が存在する場合：

      ICC_SRE_EL3.SRE（ビット0）は0b0に初期化しなければならない。

    • カーネルがEL1で移行される場合：

      ICC_SRE_EL2.SRE（ビット0）は0b0に初期化しなければならない。

    • DTまたはACPIテーブルはGICv2割り込みコントローラーを記述しなければならない。

    ポインタ認証機能を持つCPUの場合：

    • EL3が存在する場合：

      • SCR_EL3.APK（ビット16）は0b1に初期化しなければならない。

      • SCR_EL3.API（ビット17）は0b1に初期化しなければならない。

    • カーネルがEL1で移行される場合：

      • HCR_EL2.APK（ビット40）は0b1に初期化しなければならない。

      • HCR_EL2.API (bit 41) は 0b1 に初期化する必要があります。

    AMUv1 拡張機能が存在する CPU については:

    • EL3が存在する場合：

      • CPTR_EL3.TAM (bit 30) は 0b0 に初期化する必要があります。

      • CPTR_EL2.TAM (bit 30) は 0b0 に初期化する必要があります。

      • AMCNTENSET0_EL0 は 0b1111 に初期化する必要があります。

      • AMCNTENSET1_EL0 は、存在する補助カウンターごとに該当ビットに 0b1 を設定したプラットフォーム固有の値に初期化する必要があります。

    • カーネルがEL1で移行される場合：

      • AMCNTENSET0_EL0 は 0b1111 に初期化する必要があります。

      • AMCNTENSET1_EL0 は、存在する補助カウンターごとに該当ビットに 0b1 を設定したプラットフォーム固有の値に初期化する必要があります。

上記の CPU モード、キャッシュ、MMU、アーキテクチャタイマ、コヒーレンシー、システムレジスタの要件はすべての CPU に適用されます。すべての CPU は同じ例外レベルでカーネルに移行する必要があります。

ブートローダーは、以下のように各 CPU でカーネルに移行する必要があります:

  • プライマリ CPU はカーネルイメージの最初の命令に直接ジャンプする必要があります。この CPU が渡すデバイスツリーの blob には、各 cpu ノードに対して 'enable-method' プロパティが含まれている必要があります。サポートされる enable-method は以下の通りです。

    ブートローダーは、カーネル移行前にこれらのデバイスツリーのプロパティを生成し、blob に挿入する必要があります。

  • 「spin-table」の enable-method を使用する CPU は、その cpu ノードに 'cpu-release-addr' プロパティを有する必要があります。このプロパティは、自然にアライメントされた 64 ビットゼロ初期化されたメモリ位置を識別します。

    これらの CPU は、カーネルの外側のメモリ領域（デバイスツリーの /memreserve/ リージョンでカーネルに通知された予約領域）でカーネルの外側に待機し、cpu-release-addr の位置をポーリングする必要があります。この位置は予約領域内に含まれている必要があります。忙しいループのオーバーヘッドを減らすために wfe 指令を挿入することができ、プライマリ CPU は sev を発行します。cpu-release-addr で指す位置の読み込みがゼロ以外の値を返すと、CPU はその値にジャンプする必要があります。この値は単一の 64 ビットリトルエンディアン値として書き込まれるため、CPU はジャンプ前に読み込んだ値を自身のネイティブエンディアンに変換する必要があります。

  • 「psci」の enable メソッドを使用する CPU は、カーネルの外側に残る必要があります（つまり、メモリノードでカーネルに記述されたメモリ領域の外側、またはデバイスツリーの /memreserve/ リージョンでカーネルに記述された予約メモリ領域内）。カーネルは、ARM ドキュメント番号 ARM DEN 0022A（「ARM プロセッサにおける電源状態調整インターフェースシステムソフトウェア」）に記載されている CPU_ON 呼び出しを実行して、CPU をカーネルに移行します。

    デバイスツリーには、Documentation/devicetree/bindings/arm/psci.yaml に記載されているように 'psci' ノードが含まれるべきです。

  • セカンダリ CPU の汎用レジスタ設定

    • x0 = 0 （今後の使用のために予約されています）

    • x1 = 0（今後の利用のために予約済み）

    • x2 = 0（今後の利用のために予約済み）

    • x3 = 0（今後の利用のために予約済み）

AArch64 Linuxにおけるスケーラブルベクターエクステンション（SVE）サポート¶

著者: Dave Martin <Dave.Martin@arm.com>

日付: 2017年8月4日

このドキュメントは、LinuxがARM Scalable Vector Extension (SVE)の使用をサポートするためにユーザー空間に提供するインターフェースについて簡潔に説明しています。

これは最も重要な機能と問題点のみを概説しており、網羅的な説明を目的としていません。

このドキュメントはSVEアーキテクチャやプログラマーモデルの説明を目的としていません。理解を助けるため、SVEの関連するプログラマーモデルの特徴についての最小限の説明がAppendix Aに含まれています。

1. 一般¶

  • SVEレジスタZ0..Z31、P0..P15およびFFRと現在のベクターレンジVLはスレッドごとに追跡されます。

  • SVEの存在は、aux vectorのAT_HWCAPエントリにおけるHWCAP_SVEを通じてユーザー空間に報告されます。このフラグの存在はSVE命令およびレジスタの存在を示し、このドキュメントで説明するLinux固有のシステムインターフェースの存在も示します。SVEは/proc/cpuinfoで「sve」として報告されます。

  • SVE命令の実行をユーザー空間でサポートしているかを検出するには、MRS命令でCPU IDレジスタID_AA64PFR0_EL1を読み取って、SVEフィールドの値がゼロでないことを確認します。[3]

    次のセクションで説明するシステムインターフェースの存在を保証しません。必要なソフトウェアはHWCAP_SVEを確認する必要があります。

  • SVE2拡張機能をサポートするハードウェアでは、AT_HWCAP2 aux vectorエントリでHWCAP2_SVE2も報告されます。さらに、以下のHWCAP2_SVE2 HWCAP2_SVEAES HWCAP2_SVEPMULL HWCAP2_SVEBITPERM HWCAP2_SVESHA3 HWCAP2_SVESM4の存在により、SVE2のオプション拡張機能が報告されることがあります。

    HWCAP2_SVE2 HWCAP2_SVEAES HWCAP2_SVEPMULL HWCAP2_SVEBITPERM HWCAP2_SVESHA3 HWCAP2_SVESM4

    このリストはSVEアーキテクチャが進化するにつれて拡充される可能性があります。

    これらの拡張機能は、ユーザー空間がMRS命令でID_AA64ZFR0_EL1レジスタを読み取ることで報告されます。詳細はelf_hwcaps.txtとcpu-feature-registers.txtを参照してください。

  • デバッガーはNT_ARM_SVE regsetを通じてターゲットとやり取りする必要があります。このregsetのサポートを検出する推奨方法は、まずターゲットプロセスに接続し、ptrace(PTRACE_GETREGSET, pid, NT_ARM_SVE, &iov)を試みることです。

  • ユーザー空間とカーネル間でSVEスケーラブルレジスタ値（Zn、Pn、FFR）がメモリで交換される際、レジスタ値はメモリ内でエンドイアンネスに依存しないレイアウトで符号化され、ビット[(8 * i + 7) : (8 * i)]はメモリ表現の開始位置からバイトオフセットiに配置される。これは例えばシグナルフレーム（struct sve_context）やptraceインターフェース（struct user_sve_header）および関連するデータに影響を与える。

    ビッグエンディアンシステムでは、FPSIMD Vレジスタ（128ビット単位でホストエンディアンとして保存される）とは異なるバイト順序が結果となることに注意せよ。FPSIMD Vレジスタのビット[(127 - 8 * i) : (120 - 8 * i)]はバイトオフセットiに配置される。（struct fpsimd_context、struct user_fpsimd_state）

2. ベクターレンジ用語¶

SVEベクタ（Z）レジスタのサイズは「ベクターレンジ」と呼ばれる。

ベクターレンジの単位に関する混乱を避けるため、カーネルは以下の規則を採用する：

  • ベクターレンジ（VL）＝ Zレジスタのバイト数

  • ベクターキュアワード（VQ）＝ Zレジスタの128ビット単位のサイズ

（したがって VL＝16 × VQ）

VQの規則は、データ構造定義など、基盤となる粒度が重要となる場面で使用される。ほとんどの他の状況ではVLの規則が使用される。これはSVEインストラクションセットアーキテクチャにおける「VL」擬似レジスタの意味と一致する。

3. システムコールの挙動¶

  • システムコール中にV0..V31は保持される（SVEなしの場合と同じ）。したがってZ0..Z31のビット[127:0]は保持される。システムコールからの戻り時にZ0..Z31の他のビット、およびP0..P15とFFRのすべては未定義となる。

  • SVEレジスタはどのシステムコールにも引数として使用されたり、結果として返されたりしない。

  • 実際には、影響を受けるレジスタ/ビットはシステムコールからの戻り時に保持されるかゼロに置き換えられるが、ユーザー空間はこれを前提にすべきではない。カーネルの挙動はケースバイケースで異なる可能性がある。

  • スレッドの他のすべてのSVE状態、包括して現在のベクターレンジ設定、PR_SVE_VL_INHERITフラグの状態、および遅延ベクターレンジ（存在する場合）は、section 6で説明するexecve()の特定の例外を除き、すべてのシステムコールで保持される。

    特に、fork()またはclone()からの戻り時に、親プロセスと新しい子プロセスまたはスレッドは、呼び出し前の親プロセスのSVE設定と一致する同じSVE設定を共有する。

4. シグナル処理¶

  • 新しいシグナルフレームレコード sve_context はシグナル送信時にSVEレジスタを符号化する。[1]

  • このレコードはfpsimd_contextに補足情報を提供します。FPSRおよびFPCRレジスタはfpsimd_contextにのみ存在します。便利のため、V0..V3、の内容はsve_contextとfpsimd_contextの両方に複製されています。

  • SVEのシグナルフレームレコードは常に基本的なメタデータを含み、特にスレッドのベクターレンジ（sve_context.vlに記録）を含みます。

  • SVEレジスタは、スレッドでレジスタが有効かどうかによってレコードに含まれるかどうか異なります。レジスタが存在するのは次の条件を満たすときのみです：sve_context.head.size >= SVE_SIG_CONTEXT_SIZE(sve_vq_from_vl(sve_context.vl))。

  • レジスタが存在する場合、レコードの残りの部分はベクターレンジに依存したサイズとレイアウトを持ちます。マクロSVE_SIG_*は[1]で定義されており、メンバへのアクセスを容易にします。

  • スケーラブルなレジスタ（Zn、Pn、FFR）は、エンドイアンネスに依存しないレイアウトで保存されます。ビット[(8 * i + 7) : (8 * i)]は、レジスタのメモリ表現の開始位置からのバイトオフセットiに格納されます。

  • SVEコンテキストがsigcontext.__reserved[]に収まりきらない場合、スタックに追加の領域を確保し、__reserved[]にextra_contextレコードを書き込み、この領域を参照させます。sve_contextはその後、この追加領域に書き込まれます。このメカニズムの詳細については[1]を参照してください。

5. シグナルリターン¶

シグナルハンドラから戻る場合:

  • シグナルフレームにsve_contextレコードが存在しない、または存在しても前記セクションで説明したようにレジスタデータを含まない場合、SVEレジスタ/ビットは非有効となり、未定義の値を取ります。

  • sve_contextがシグナルフレームに存在し、完全なレジスタデータを含んでいる場合、SVEレジスタは有効となり、指定されたデータで初期化されます。ただし、後方互換性のため、Z0..Z31のビット[127:0]はsve_contextからではなく、fpsimd_context.vregs[]の対応するメンバから常に復元されます。残りのビットはsve_contextから復元されます。

  • シグナルフレームにfpsimd_contextの包含は、sve_contextが存在するかどうかに関わらず必須です。

  • ベクターレンジはシグナルリターンで変更できません。シグナルフレームのsve_context.vlが現在のベクターレンジと一致しない場合、シグナルリターンの試行は不正とみなされ、強制的なSIGSEGVが発生します。

6. prctl拡張機能¶

新しいprctl()呼び出しを追加し、プログラムがSVEベクターレンジを管理できるようにします:

prctl(PR_SVE_SET_VL, unsigned long arg)

呼び出し元スレッドのベクターレンジおよび関連するフラグを設定します。arg == vl | flags。呼び出し元プロセスの他のスレッドは影響を受けません。

vlは望ましいベクターレンジで、sve_vl_valid(vl)が必須です。

フラグ:

PR_SVE_VL_INHERIT

execve()の実行中に現在のベクターレンジを継承します。それ以外の場合、ベクターレンジはexecve()の実行時にシステムのデフォルト値に戻されます。(第9節を参照してください。)

PR_SVE_SET_VL_ONEXEC

このスレッドが実行する次のexecve()の際に、要求されたベクターレンジの変更を延期します。

次のexecve()（ある場合）がスレッドによって実行された直後に、以下の呼び出しを暗黙的に実行する効果が等しいです：

prctl(PR_SVE_SET_VL, arg & ~PR_SVE_SET_VL_ONEXEC)

これにより、呼び出し元の実行時副作用を回避しながら、異なるベクターレンジで新しいプログラムを起動することが可能になります。

PR_SVE_SET_VL_ONEXECが指定されていない場合、要求された変更は即座に有効になります。

戻り値: 成功時は非負値、エラー時は負値:
EINVAL: SVEがサポートされていない、または無効なベクターレンジが要求された場合、または

無効なフラグです。

成功した場合:

  • 呼び出しスレッドのベクトル長または、次のexecve()で適用される遅延ベクトル長（PR_SVE_SET_VL_ONEXECフラグがargに存在するかどうかによります）が、vl以下のシステムでサポートされる最大値に設定されます。vlがSVE_VL_MAXの場合、設定される値はシステムがサポートする最大値です。

  • 呼び出しスレッドの未処理の遅延ベクトル長変更はキャンセルされます。

  • 返却値はPR_SVE_GET_VLと同様の形式で結果の構成を表します。この値のベクトル長は、argにPR_SVE_SET_VL_ONEXECフラグが存在しない場合、このスレッドの新しい現在ベクトル長を表します。存在する場合、報告されるベクトル長は、呼び出しスレッドが次のexecve()で適用する遅延ベクトル長を表します。

  • ベクトル長の変更により、P0..P15、FFRおよびZ0..Z31のすべてのビット（Z0の[127:0]ビットからZ31の[127:0]ビットを除く）は未定義になります。PR_SVE_SET_VLを呼び出してvlをスレッドの現在ベクトル長と等しくする、またはPR_SVE_SET_VL_ONEXECフラグを指定して呼び出すことは、この目的でのベクトル長の変更とはみなされません。

prctl(PR_SVE_GET_VL)

呼び出しスレッドのベクトル長を取得します。

次のフラグは結果にORで組み込むことができます:

PR_SVE_VL_INHERIT

ベクトル長はexecve()を跨って継承されます。

未処理の遅延ベクトル長変更があるかどうかを確認する方法はありません（通常の使用ではfork()またはvfork()と対応するexecve()の間のみが該当します）。

結果からベクトル長を抽出するには、PR_SVE_VL_LEN_MASKと論理積をとります。

戻り値: 成功した場合、非負の値を返します。エラーの場合、負の値を返します:

EINVAL: SVEがサポートされていません。

7. ptrace拡張¶

  • 新しいregset NT_ARM_SVEが定義され、PTRACE_GETREGSETとPTRACE_SETREGSETで使用されます。

    定義については[2]を参照してください。

regsetデータはstruct user_sve_headerから始まり、以下のフィールドを含みます:

size

完全なregsetのサイズ（バイト単位）。これはvlに依存し、今後他の要素にも依存する可能性があります。

PTRACE_GETREGSETの呼び出しがsizeの値よりも少ないデータを要求する場合、呼び出し元はより大きなバッファを割り当てて再試行することで、完全なregsetを読み取ることができます。

max_size

ターゲットスレッドのregsetが成長できる最大サイズ（バイト単位）。ターゲットスレッドがベクターレンジを変更しても、このサイズを超えることはありません。

vl

ターゲットスレッドの現在のベクターレンジ（バイト単位）。

max_vl

ターゲットスレッドの最大可能ベクターレンジ。

フラグ

どちらか一方

SVE_PT_REGS_FPSIMD

SVEレジスタは非アクティブ（GETREGSET）または非アクティブにされる（SETREGSET）。

ペイロードの型はstruct user_fpsimd_stateで、NT_PRFPREGと同じ意味を持ち、user_sve_headerの開始位置からのSVE_PT_FPSIMD_OFFSETオフセットから開始します。

今後、追加データが追加される可能性があります: ペイロードのサイズはSVE_PT_FPSIMD_SIZE(vq, flags)を使用して取得します。

vqはsve_vq_from_vl(vl)を使用して取得します。

または

SVE_PT_REGS_SVE

SVEレジスタはアクティブ（GETREGSET）またはアクティブにされる（SETREGSET）。

ペイロードにはSVEレジスタデータが含まれ、user_sve_headerの開始位置からのSVE_PT_SVE_OFFSETオフセットから開始し、サイズはSVE_PT_SVE_SIZE(vq, flags)です;

…以下のフラグのいずれか0個以上がORで組み合わされ、これらはPR_SET_VL_*フラグに対応するものと同じ意味と動作を持ちます:

SVE_PT_VL_INHERIT

SVE_PT_VL_ONEXEC (SETREGSET専用).

  • ベクターレンジおよび/またはフラグの変更効果は、PR_SVE_SET_VLに記載されているものと同等です。

    SETREGSETによって実際に設定されたVLを知る必要がある場合、呼び出し元はさらにGETREGSETを呼び出す必要があります。ただし、事前にリクエストされたVLがサポートされていることがわかっている場合は除きます。

  • SVE_PT_REGS_SVEの場合、ペイロードのサイズとレイアウトはヘッダーフィールドに依存します。SVE_PT_SVE_*()マクロが提供されており、メンバへのアクセスを容易にしています。

  • どちらの場合でも、SETREGSETではペイロードを省略することが許可されており、その場合、ベクターレンジとフラグのみが変更されます（その変更の結果も含む）。

  • SETREGSETの場合、SVE_PT_REGS_SVEペイロードが存在し、要求されたVLがサポートされていない場合、ペイロードが省略された場合と同じ効果が得られますが、EIOエラーが報告されます。ペイロードデータを実際に設定されたベクターレンジの正しいレイアウトに変換する試みは行われません。スレッドのFPSIMD状態は保持されますが、SVEレジスタの残りのビットは未指定になります。呼び出し元がペイロードレイアウトを実際のVLに変換し、再試行する必要があります。

  • 部分的な、不完全なペイロードの書き込みの効果は未定義です。

8. ELFコアダンプ拡張機能¶

  • ダンプされたプロセスの各スレッドに対してNT_ARM_SVEノートがコアダンプに追加されます。コンテンツは、コアダンプ生成時に各スレッドに対してNT_ARM_SVEのPTRACE_GETREGSETが実行された場合に読み取られたデータと同等になります。

9. システムランタイム構成¶

  • シグナルフレームの拡張によるABI影響を軽減するため、管理者、ディストリビューションメンテナ、開発者向けに、ユーザー空間プロセスのデフォルトベクターレンジを設定するポリシーメカニズムが提供されます:

/proc/sys/abi/sve_default_vector_length

このファイルに整数のテキスト表現を書き込むと、システムデフォルトベクターレンジが指定された値に設定されます。ただし、指定値がシステムがサポートする最大ベクターレンジより大きい場合、デフォルトベクターレンジはその最大値に設定されます。

結果はファイルを再開して内容を読み取ることで確認できます。

起動時にデフォルトベクターレンジは64またはサポートされる最大ベクターレンジのうち小さい方で初期化されます。これはinitプロセス（PID 1）の初期ベクターレンジを決定します。

このファイルを読み込むと、現在のシステムデフォルトベクターレンジが返されます。

  • execve()呼び出しのたびに、新しいプロセスのベクターレンジがシステムデフォルトベクターレンジに設定されます。ただし、

    • 呼び出しスレッドにPR_SVE_VL_INHERIT（または同等のSVE_PT_VL_INHERIT）が設定されている、または

    • PR_SVE_SET_VL_ONEXECフラグ（またはSVE_PT_VL_ONEXEC）で待機中のベクターレンジ変更がある場合を除きます。

  • システムデフォルトベクターレンジを変更しても、execve()呼び出しを行わない既存のプロセスまたはスレッドのベクターレンジには影響しません。

付録A. SVEプログラマーモデル（情報的）¶

このセクションでは、このドキュメントに関連するARMv8-AプログラマーモデルへのSVEの追加について簡潔な説明を提供します。

注意: このセクションは情報提供を目的としたものであり、完全性を保証するものではなく、アーキテクチャ仕様の代替ではありません。

A.1. レジスタ¶

A64状態では、SVEは以下の要素を追加します:

  • 32の8VLビットベクターレジスタ Z0..Z31。各Znについて、Znのビット[127:0]はARMv8-AベクターレジスタVnとアリアスします。

    Vnレジスタ名を使用してレジスタを書き込むと、対応するZnのすべてのビットをゼロにし、ビット[127:0]を除きます。

  • 16のVLビット述語レジスタ P0..P15

  • 1のVLビット専用述語レジスタ FFR（「最初のエラーレジスタ」）

  • VLの「擬似レジスタ」で、各ベクターレジスタのサイズを決定します。

    SVE命令セットアーキテクチャはVLを直接書き込む方法を提供していません。代わりに、EL1以上で適切なシステムレジスタに書き込むことでのみ変更可能です。

  • VLの値はEL1以上で実行時に行き、16 <= VL <= VLmaxの範囲で設定可能です。ただし、VLは16の倍数でなければなりません。

  • 最大ベクターレンジはハードウェアによって決定されます: 16 <= VLmax <= 256。

    (SVEアーキテクチャは256を指定していますが、今後のアーキテクチャの改訂によりこの制限を上げることが許可されています。)

  • FPSRおよびFPCRはARMv8-Aから保持され、SVE浮動小数点演算と同様にARMv8浮動小数点演算と相互作用します:

         8VL-1                       128               0  bit index
    +----          ////            -----------------+
 Z0 |                               :       V0      |
  :                                          :
 Z7 |                               :       V7      |
 Z8 |                               :     * V8      |
  :                                       :  :
Z15 |                               :     *V15      |
Z16 |                               :      V16      |
  :                                          :
Z31 |                               :      V31      |
    +----          ////            -----------------+
                                             31    0
     VL-1                  0                +-------+
    +----       ////      --+          FPSR |       |
 P0 |                       |               +-------+
  : |                       |         *FPCR |       |
P15 |                       |               +-------+
    +----       ////      --+
FFR |                       |               +-----+
    +----       ////      --+            VL |     |
                                            +-----+
(*) callee-save:

これはZ-/Vレジスタのビット[63:0]にのみ適用されます。FPCRにはcallee-saveおよびcaller-saveのビットが含まれます。詳細は[4]を参照してください。

A.2. プロシージャ呼び出し標準¶

ARMv8-Aベースのプロシージャ呼び出し標準は、追加されたSVEレジスタ状態に関して以下のようになります:

  • SVEレジスタのビットでFP/SIMDと共有されていないものはすべてcaller-saveです。

  • Z8のビット[63:0]～Z15のビット[63:0]はcallee-saveです。

    これはこれらのビットがベースプロシージャ呼び出し標準でcaller-saveであるためです。

付録B. ARMv8-A FP/SIMDプログラマーモデル¶

注意: このセクションは情報提供を目的としたものであり、完全性を保証するものではなく、アーキテクチャ仕様の代替ではありません。

詳細については[4]を参照してください。

ARMv8-Aは以下の浮動小数点/SIMDレジスタ状態を定義しています:

  • 32の128ビットベクターレジスタ V0..V31

  • 2の32ビットステータス/コントロールレジスタ FPSR, FPCR

      127           0  bit index
     +---------------+
  V0 |               |
   : :               :
  V7 |               |
* V8 |               |
:  : :               :
*V15 |               |
 V16 |               |
   : :               :
 V31 |               |
     +---------------+

              31    0
             +-------+
        FPSR |       |
             +-------+
       *FPCR |       |
             +-------+
(*) callee-save:

これはVレジスタのビット[63:0]にのみ適用されます。FPCRにはcallee-saveとcaller-saveのビットが混在しています。

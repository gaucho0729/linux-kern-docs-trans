BPF Type Format (BTF)¶

1. はじめに¶

BTF (BPF Type Format) は、BPF プログラム/マップに関連するデバッグ情報のメタデータ形式です。BTF という名前は最初、データ型を記述するために使用されました。その後、BTF は定義されたサブルーチンの関数情報やソース/行情報の記述にも拡張されました。

デバッグ情報はマップの見やすい表示、関数サインなどに使用されます。関数サインは、BPF プログラム/関数のカーネルシンボルをより正確に表示するのに役立ちます。行情報は、ソースコードに注釈を加えた変換済みバイトコードやジェイテッドコード、検証ログの生成に役立ちます。

BTF 指定書は2つの部分から構成されています。

  • BTF カーネル API

  • BTF ELF ファイル形式

カーネル API はユーザー空間とカーネルの間の契約です。カーネルは BTF 情報を使用する前にそれを検証します。ELF ファイル形式は ELF ファイルと libbpf ローダー間のユーザー空間での契約です。

型と文字列セクションは BTF カーネル API の一部であり、bpf プログラムが参照するデバッグ情報（主に型関連）を記述します。これらの2つのセクションについては 2. BTF 型と文字列の符号化.

2. BTF 型と文字列の符号化¶

ファイル include/uapi/linux/btf.h が、型/文字列の符号化方法を高レベルで定義しています。

データブロブの開始は以下の必要があります:

struct btf_header {
    __u16   magic;
    __u8    version;
    __u8    flags;
    __u32   hdr_len;

    /* All offsets are in bytes relative to the end of this header */
    __u32   type_off;       /* offset of type section       */
    __u32   type_len;       /* length of type section       */
    __u32   str_off;        /* offset of string section     */
    __u32   str_len;        /* length of string section     */
};

マジックは 0xeB9Fで、ビッグエンディアンとリトルエンディアンシステムで異なる符号化があり、ビッグエンディアンまたはリトルエンディアンのターゲットが生成されたかをテストするために使用できます。 btf_header はデータブロブが生成されるときに拡張性を持たせるように設計されています hdr_len ドライバを無効化し、 sizeof(struct btf_header) 。

2.1 文字列符号化¶

文字列セクションの最初の文字列は空文字列でなければなりません。文字列テーブルの残りの部分は、他のNULL終端文字列の連結です。

2.2 型符号化¶

型ID 0 は void 型に予約されています。型セクションは順次解析され、認識された各型にIDが割り当てられます。IDは 1から開始します。現在、サポートされている型は以下の通りです:

#define BTF_KIND_INT            1       /* Integer      */
#define BTF_KIND_PTR            2       /* Pointer      */
#define BTF_KIND_ARRAY          3       /* Array        */
#define BTF_KIND_STRUCT         4       /* Struct       */
#define BTF_KIND_UNION          5       /* Union        */
#define BTF_KIND_ENUM           6       /* Enumeration  */
#define BTF_KIND_FWD            7       /* Forward      */
#define BTF_KIND_TYPEDEF        8       /* Typedef      */
#define BTF_KIND_VOLATILE       9       /* Volatile     */
#define BTF_KIND_CONST          10      /* Const        */
#define BTF_KIND_RESTRICT       11      /* Restrict     */
#define BTF_KIND_FUNC           12      /* Function     */
#define BTF_KIND_FUNC_PROTO     13      /* Function Proto       */
#define BTF_KIND_VAR            14      /* Variable     */
#define BTF_KIND_DATASEC        15      /* Section      */

注意：型セクションはデバッグ情報のみを符号化しており、純粋な型を表していません。 BTF_KIND_FUNC は型ではなく、定義されたサブプログラムを表します。

各型は以下の共通データを含みます:

struct btf_type {
    __u32 name_off;
    /* "info" bits arrangement
     * bits  0-15: vlen (e.g. # of struct's members)
     * bits 16-23: unused
     * bits 24-27: kind (e.g. int, ptr, array...etc)
     * bits 28-30: unused
     * bit     31: kind_flag, currently used by
     *             struct, union and fwd
     */
    __u32 info;
    /* "size" is used by INT, ENUM, STRUCT and UNION.
     * "size" tells the size of the type it is describing.
     *
     * "type" is used by PTR, TYPEDEF, VOLATILE, CONST, RESTRICT,
     * FUNC and FUNC_PROTO.
     * "type" is a type_id referring to another type.
     */
    union {
            __u32 size;
            __u32 type;
    };
};

特定の種類については、共通データの後に種類固有のデータが続きます。 name_off の struct btf_type は文字列テーブル内のオフセットを指定します。以下のセクションでは各種類の符号化方法を詳しく説明します。

2.2.1 BTF_KIND_INT¶

struct btf_type 符号化要件:

  • name_off: 有効なオフセットのいずれか

  • info.kind_flag: 0

  • info.kind: BTF_KIND_INT

  • info.vlen: 0

  • size: int 型のバイト数。

btf_type は u32 の後に続き、以下のビット配置を持ちます:

#define BTF_INT_ENCODING(VAL)   (((VAL) & 0x0f000000) >> 24)
#define BTF_INT_OFFSET(VAL)     (((VAL) & 0x00ff0000) >> 16)
#define BTF_INT_BITS(VAL)       ((VAL)  & 0x000000ff)

以下の BTF_INT_ENCODING は以下の属性を持ちます:

#define BTF_INT_SIGNED  (1 << 0)
#define BTF_INT_CHAR    (1 << 1)
#define BTF_INT_BOOL    (1 << 2)

以下の BTF_INT_ENCODING() は int 型の符号性、char、または bool に関する追加情報を提供します。char と bool の符号化は見やすい表示に主に使用され、int 型には最大1つの符号化が指定できます。

以下の BTF_INT_BITS() このint型が実際に保持するビット数を指定します。たとえば、4ビットのビットフィールドは BTF_INT_BITS() 4に等しい。の btf_type.size * 8 は、の型のための値以上でなければなりません BTF_INT_BITS() 型のための。の最大値は BTF_INT_BITS() 128です。

以下の BTF_INT_OFFSET() 開始ビットオフセットを指定します。たとえば、ビットフィールド構造体メンバは:

  • btfメンバビットオフセット100、構造体の開始位置からの

  • int型を指すbtfメンバ、

  • int型は BTF_INT_OFFSET() = 2 および BTF_INT_BITS() = 4

その後、構造体のメモリレイアウトでは、このメンバが占有する 4 ビットから始まるビット 100 + 2 = 102.

代わりに、ビットフィールド構造体メンバは以下のようになります。上記と同じビットにアクセスする

  • btfメンバビットオフセット102、

  • int型を指すbtfメンバ、

  • int型は BTF_INT_OFFSET() = 0 および BTF_INT_BITS() = 4

元々の意図は BTF_INT_OFFSET() ビットフィールドの符号化の柔軟性を提供することです。現在、LLVMとpaholeの両方が生成しています BTF_INT_OFFSET() = 0 すべてのint型に対して

  • info.kind: BTF_KIND_ARRAY

  • info.vlen: 0

    __u32   type;

};
以下の struct btf_array 符号化:

  • type: 要素型

  • index_type: インデックス型

  • nelems: この配列の要素数（0 これも許可されます）。

以下の index_type 任意の通常のint型（u8, u16, u32, u64, unsigned __int128）。含む設計の元々の意図 index_type DWARFに従います。が持つ index_type 配列型に対して。現在、BTFでは型検証を超えて、 index_type 使用されません。

以下の struct btf_array 要素型を通じてチェインを許可します。たとえば、 int a[5][6]、以下の型情報がチェインを示しています：

  • [1]: int

  • [2]: array、 btf_array.type = [1], btf_array.nelems = 6

  • [3]: array、 btf_array.type = [2], btf_array.nelems = 5

現在、paholeとLLVMは多次元配列を1次元配列に圧縮します。例えば、 a[5][6]and wakes up processes waiting on the timerfd. While iterating the btf_array.nelems 等しい 30. この理由は、元のユースケースがマップ pretty print であり、配列全体がダンプされるため、一次元配列で十分なためです。BTF の利用がさらに進むにつれて、pahole と llvm は、多次元配列に対して正しいチェーン表現を生成するよう変更できます。

2.2.5 BTF_KIND_UNION¶

struct btf_type 符号化要件:

  • name_off: 0 または有効な C 識別子へのオフセット

  • info.kind_flag: 0 または 1

  • info.kind: BTF_KIND_STRUCT または BTF_KIND_UNION

  • info.vlen: struct/union のメンバ数

  • info.size: struct/union のバイト数

btf_type は続く info.vlen 構造体の数は struct btf_member.:

struct btf_member {
    __u32   name_off;
    __u32   type;
    __u32   offset;
};
struct btf_member 符号化:

  • name_off: 有効な C 識別子へのオフセット

  • type: メンバの型

  • offset: <以下参照>

型情報 kind_flag が設定されていない場合、オフセットにはメンバのビットオフセットのみが含まれます。注意点として、ビットフィールドのベース型は int または enum 型に限られます。ビットフィールドのサイズが 32 の場合、ベース型は int または enum 型のいずれかで構いません。ビットフィールドのサイズが 32 でない場合、ベース型は int でなければなりません。int 型 BTF_INT_BITS() ビットフィールドのサイズをエンコードします。

もし kind_flag が設定されている場合、 btf_member.offset にはメンバのビットフィールドサイズとビットオフセットの両方が含まれます。ビットフィールドサイズとビットオフセットの計算式は以下の通りです。:

#define BTF_MEMBER_BITFIELD_SIZE(val)   ((val) >> 24)
#define BTF_MEMBER_BIT_OFFSET(val)      ((val) & 0xffffff)

この場合、ベース型が int 型である場合、それは通常の int 型でなければなりません:

  • BTF_INT_OFFSET() は0でなければなりません。

  • BTF_INT_BITS() は等しい必要があります {1,2,4,8,16} * 8.

以下のカーネルパッチが導入され kind_flag 両方のモードが存在する理由が説明されています:

https://github.com/torvalds/linux/commit/9d5f9f701b1891466fb3dbb1806ad97716f95cc3#diff-fa650a64fdd3968396883d2fe8215ff3

3. BTFカーネルAPI¶

以下のbpfシスコールコマンドはBTFを関与しています：

  • BPF_BTF_LOAD: BTFデータをカーネルにロードする

  • BPF_MAP_CREATE: マップの作成で、BTFのキーおよび値の型情報を使用します。

  • BPF_PROG_LOAD: プログラムのロードで、BTFの関数および行情報を使用します。

  • BPF_BTF_GET_FD_BY_ID: BTFのファイル記述子を取得します。

  • BPF_OBJ_GET_INFO_BY_FD: BTF、func_info、line_info およびその他の BTF 関連情報が返されます。

ワークフローは通常、以下のようになります：

Application:
    BPF_BTF_LOAD
        |
        v
    BPF_MAP_CREATE and BPF_PROG_LOAD
        |
        V
    ......

Introspection tool:
    ......
    BPF_{PROG,MAP}_GET_NEXT_ID (get prog/map id's)
        |
        V
    BPF_{PROG,MAP}_GET_FD_BY_ID (get a prog/map fd)
        |
        V
    BPF_OBJ_GET_INFO_BY_FD (get bpf_prog_info/bpf_map_info with btf_id)
        |                                     |
        V                                     |
    BPF_BTF_GET_FD_BY_ID (get btf_fd)         |
        |                                     |
        V                                     |
    BPF_OBJ_GET_INFO_BY_FD (get btf)          |
        |                                     |
        V                                     V
    pretty print types, dump func signatures and line info, etc.

3.1 BPF_BTF_LOAD¶

BTF データのブロブをカーネルにロードします。記述されたデータブロブは、 2. BTF 型と文字列の符号化、カーネルに直接ロードできます。ユーザー空間に btf_fd ユーザー空間に返されます。

3.2 BPF_MAP_CREATE¶

マップは以下のように作成できます。 btf_fd 指定されたキー/値の型 ID を指定して。

__u32   btf_fd;         /* fd pointing to a BTF type data */
__u32   btf_key_type_id;        /* BTF type_id of the key */
__u32   btf_value_type_id;      /* BTF type_id of the value */

libbpfでは、以下のように追加の注釈を用いてマップを定義できます：

struct bpf_map_def SEC("maps") btf_map = {
    .type = BPF_MAP_TYPE_ARRAY,
    .key_size = sizeof(int),
    .value_size = sizeof(struct ipv_counts),
    .max_entries = 4,
};
BPF_ANNOTATE_KV_PAIR(btf_map, int, struct ipv_counts);

ここでは、マクロ BPF_ANNOTATE_KV_PAIR のパラメータはマップ名、キーおよび値の型です。ELF 解析中に、libbpf はキー/値の type_id を抽出し、BPF_MAP_CREATE 属性に自動的に割り当てます。

3.3 BPF_PROG_LOAD¶

prog_load では、以下の属性に適切な値を指定して、func_info および line_info をカーネルに渡せます：

__u32           insn_cnt;
__aligned_u64   insns;
......
__u32           prog_btf_fd;    /* fd pointing to BTF type data */
__u32           func_info_rec_size;     /* userspace bpf_func_info size */
__aligned_u64   func_info;      /* func info */
__u32           func_info_cnt;  /* number of bpf_func_info records */
__u32           line_info_rec_size;     /* userspace bpf_line_info size */
__aligned_u64   line_info;      /* line info */
__u32           line_info_cnt;  /* number of bpf_line_info records */

func_info および line_info はそれぞれ以下の配列です：

struct bpf_func_info {
    __u32   insn_off; /* [0, insn_cnt - 1] */
    __u32   type_id;  /* pointing to a BTF_KIND_FUNC type */
};
struct bpf_line_info {
    __u32   insn_off; /* [0, insn_cnt - 1] */
    __u32   file_name_off; /* offset to string table for the filename */
    __u32   line_off; /* offset to string table for the source line */
    __u32   line_col; /* line number and column number */
};

func_info_rec_size は各 func_info レコードのサイズで、line_info_rec_size は各 line_info レコードのサイズです。レコードサイズをカーネルに渡すことで、今後レコード自体を拡張することが可能になります。

func_info に関する要件は以下の通りです：

  • func_info[0].insn_off は 0 でなければなりません。

  • func_info の insn_off は厳密に増加し、bpf 関数の境界と一致する必要があります。

line_info に関する要件は以下の通りです：

  • 各関数の最初の insn には、その insn に指す line_info レコードが必要です。

  • line_info の insn_off は厳密に増加する必要があります。

line_info では、行番号と列番号は以下のように定義されます：

#define BPF_LINE_INFO_LINE_NUM(line_col)        ((line_col) >> 10)
#define BPF_LINE_INFO_LINE_COL(line_col)        ((line_col) & 0x3ff)

3.4 BPF_{PROG,MAP}_GET_NEXT_ID¶

カーネルでは、ロードされたすべてのプログラム、マップ、または BTF に一意の ID が割り当てられます。この ID はプログラム、マップ、または BTF の寿命中に変更されません。

bpf システムコールコマンド BPF_{PROG,MAP}_GET_NEXT_ID は、それぞれのコマンドに対してユーザー空間に ID を返します。これにより、検査ツールがすべてのプログラムとマップを検査できます。

3.5 BPF_{PROG,MAP}_GET_FD_BY_ID¶

検査ツールは ID を使ってプログラムまたはマップの詳細を取得できません。参照カウントの目的でまずファイル記述子を取得する必要があります。

3.6 BPF_OBJ_GET_INFO_BY_FD¶

プログラム/マップの fd を取得した後、検査ツールはその fd に関するカーネルからの詳細情報を取得できます。その一部は BTF 関連です。例えば、 bpf_map_info が返します btf_id およびキー/値の型 ID。 bpf_prog_info が返します btf_id、変換された BPF バイトコードの func_info および line info、および jited_line_info。

3.7 BPF_BTF_GET_FD_BY_ID¶

With btf_id obtained in bpf_map_info および bpf_prog_info、bpf システムコールコマンド BPF_BTF_GET_FD_BY_ID は btf fd を取得できます。その後、コマンド BPF_OBJ_GET_INFO_BY_FD を使用して、元々 BPF_BTF_LOAD でカーネルにロードされた btf blob を取得できます。

btf blob により、 bpf_map_info, and bpf_prog_info、インテロスペクションツールは完全な btf 知識を持ち、マップのキー/値を綺麗に表示したり、関数サインとライン情報、バイト/jit コードをダンプしたりできます。

4. ELF ファイル形式インターフェース¶

4.1 .BTF セクション¶

.BTF セクションには型と文字列データが含まれます。このセクションのフォーマットは、 2. BTF 型と文字列の符号化.

4.2 .BTF.extセクション¶

.BTF.ext セクションは func_info と line_info をエンコードしており、カーネルにロードする前にローダー処理が必要です。

.BTF.ext セクションの仕様は、 tools/lib/bpf/btf.h および tools/lib/bpf/btf.c.

.BTF.ext セクションの現在のヘッダー:

struct btf_ext_header {
    __u16   magic;
    __u8    version;
    __u8    flags;
    __u32   hdr_len;

    /* All offsets are in bytes relative to the end of this header */
    __u32   func_info_off;
    __u32   func_info_len;
    __u32   line_info_off;
    __u32   line_info_len;
};

これは .BTF セクションと非常に似ています。型/文字列セクションの代わりに、func_info と line_info セクションを含みます。参照 3.3 BPF_PROG_LOAD で func_info と line_info のレコードフォーマットについての詳細を確認してください。

func_info は以下のようになっています。：

func_info_rec_size
btf_ext_info_sec for section #1 /* func_info for section #1 */
btf_ext_info_sec for section #2 /* func_info for section #2 */
...

func_info_rec_size は .BTF.ext が生成される際の bpf_func_info 構造体のサイズを指定します。 btf_ext_info_sec、以下に定義されていますが、特定の ELF セクションごとの func_info のコレクションです：

struct btf_ext_info_sec {
   __u32   sec_name_off; /* offset to section name */
   __u32   num_info;
   /* Followed by num_info * record_size number of bytes */
   __u8    data[0];
};

ここで、num_info は 0 より大きくなければなりません。

line_info は以下のようになっています。：

line_info_rec_size
btf_ext_info_sec for section #1 /* line_info for section #1 */
btf_ext_info_sec for section #2 /* line_info for section #2 */
...

line_info_rec_size は .BTF.ext が生成される際の bpf_line_info 構造体のサイズを指定します。

の解釈は、カーネル API と ELF API で異なります。カーネル API では、 bpf_func_info->insn_off および bpf_line_info->insn_off は単位の insn_off の指令オフセットです。ELF API では、 struct bpf_insnはセクション（ insn_off ）の開始位置からのバイトオフセットです。btf_ext_info_sec->sec_name_off).

4.2 .BTF_ids セクション¶

.BTF_ids セクションはカーネル内で使用される BTF ID 値をエンコードします。

このセクションは、 include/linux/btf_ids.h ヘッダーファイルに定義されたマクロを活用してカーネルコンパイル中に作成されます。カーネルコードはこれらを用いて BTF ID 値のリストとセット（ソート済みリスト）を作成できます。

以下の BTF_ID_LIST および BTF_ID マクロは未ソートの BTF ID 値のリストを定義し、以下の構文を持ちます：

BTF_ID_LIST(list)
BTF_ID(type1, name1)
BTF_ID(type2, name2)

これにより、.BTF_ids セクション内でのレイアウトは以下のようになります：

__BTF_ID__type1__name1__1:
.zero 4
__BTF_ID__type2__name2__2:
.zero 4

以下の u32 list[]; 変数はリストにアクセスするための定義です。

以下の BTF_ID_UNUSED マクロは 4 バイトのゼロを定義します。BTF_ID_LIST に未使用のエントリを定義する際に使用します。例えば：

BTF_ID_LIST(bpf_skb_output_btf_ids)
BTF_ID(struct, sk_buff)
BTF_ID_UNUSED
BTF_ID(struct, task_struct)

以下の BTF_SET_START/END マクロペアは BTF ID 値とそのカウントのソート済みリストを定義し、以下の構文を持ちます：

BTF_SET_START(set)
BTF_ID(type1, name1)
BTF_ID(type2, name2)
BTF_SET_END(set)

これにより、.BTF_ids セクション内でのレイアウトは以下のようになります：

__BTF_ID__set__set:
.zero 4
__BTF_ID__type1__name1__3:
.zero 4
__BTF_ID__type2__name2__4:
.zero 4

以下の struct btf_id_set set; 変数はリストにアクセスするための定義です。

以下の typeX name は次のいずれかです：

struct, union, typedef, func

で、BTF ID 値を解決する際のフィルタとして使用されます。

すべての BTF ID リストとセットは .BTF_ids セクションにコンパイルされ、カーネルビルドのリンキングフェーズで resolve_btfids ツールによって解決されます。

5. BTF の使用¶

5.1 bpftool map 綺麗な表示¶

BTF を使用すると、マップのキー/値はフィールドに基づいて表示できます。これは特に大規模な構造体やビットフィールドを持つデータ構造の場合に価値があります。例えば、以下のマップに対して：

enum A { A1, A2, A3, A4, A5 };
typedef enum A ___A;
struct tmp_t {
     char a1:4;
     int  a2:4;
     int  :4;
     __u32 a3:4;
     int b;
     ___A b1:4;
     enum A b2:4;
};
struct bpf_map_def SEC("maps") tmpmap = {
     .type = BPF_MAP_TYPE_ARRAY,
     .key_size = sizeof(__u32),
     .value_size = sizeof(struct tmp_t),
     .max_entries = 1,
};
BPF_ANNOTATE_KV_PAIR(tmpmap, int, struct tmp_t);

bpftool は以下のように綺麗に表示できます：

[{
      "key": 0,
      "value": {
          "a1": 0x2,
          "a2": 0x4,
          "a3": 0x6,
          "b": 7,
          "b1": 0x8,
          "b2": 0xa
      }
  }
]

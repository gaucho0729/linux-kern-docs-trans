BPF_MAP_TYPE_CGROUP_STORAGE¶

以下の BPF_MAP_TYPE_CGROUP_STORAGE マップタイプはローカルな固定サイズのストレージを表します。これは CONFIG_CGROUP_BPFに限定され、cgroupにアタッチするプログラムにのみ利用可能です。これらのプログラムは同じKconfigによって提供されます。ストレージはプログラムがアタッチされているcgroupによって識別されます。

マップは、BPFプログラムがアタッチされているcgroupにローカルなストレージを提供します。これは一般的なハッシュテーブルよりも高速で簡単なアクセスを提供します。一般的なハッシュテーブルはハッシュテーブルの検索を実行し、ユーザーが自らライブなcgroupを追跡する必要があります。

このドキュメントは、以下のマップタイプの使用方法とセマンティクスについて説明します。 BPF_MAP_TYPE_CGROUP_STORAGE マップタイプ。Linux 5.9で一部の動作が変更され、このドキュメントではその違いについて説明します。

使い方¶

マップは、以下のタイプのキーを使用します __u64 cgroup_inode_id または struct bpf_cgroup_storage_key、が宣言されている linux/bpf.h:

struct bpf_cgroup_storage_key {
        __u64 cgroup_inode_id;
        __u32 attach_type;
};

cgroup_inode_id はcgroupディレクトリのインノデIDです。 attach_type はプログラムのアタッチタイプです。

Linux 5.9では、タイプ __u64 cgroup_inode_id をキーのタイプとしてサポートしました。このキーのタイプを使用すると、特定のcgroupおよびマップのすべてのアタッチタイプが同じストレージを共有します。それ以外の場合、タイプが struct bpf_cgroup_storage_keyの場合、異なるアタッチタイプのプログラムは隔離され、異なるストレージを参照します。

プログラム内のストレージにアクセスするには、 bpf_get_local_storage:

void *bpf_get_local_storage(void *map, u64 flags)

flags は今後の使用のために予約されており、0でなければなりません。

明示的な同期はありません。以下のストレージは BPF_MAP_TYPE_CGROUP_STORAGE 複数のCPUにまたがって複数のプログラムからアクセス可能で、ユーザー自身で同期を取る必要があります。BPFインフラストラクチャは struct bpf_spin_lock ストレージを同期するための機能を提供します。参照してください tools/testing/selftests/bpf/progs/test_spin_lock.c.

例¶

キーのタイプとしての使用方法 struct bpf_cgroup_storage_key:

#include <bpf/bpf.h>

struct {
        __uint(type, BPF_MAP_TYPE_CGROUP_STORAGE);
        __type(key, struct bpf_cgroup_storage_key);
        __type(value, __u32);
} cgroup_storage SEC(".maps");

int program(struct __sk_buff *skb)
{
        __u32 *ptr = bpf_get_local_storage(&cgroup_storage, 0);
        __sync_fetch_and_add(ptr, 1);

        return 0;
}

上記のマップをユーザー空間でアクセスする方法:

#include <linux/bpf.h>
#include <linux/libbpf.h>

__u32 map_lookup(struct bpf_map *map, __u64 cgrp, enum bpf_attach_type type)
{
        struct bpf_cgroup_storage_key = {
                .cgroup_inode_id = cgrp,
                .attach_type = type,
        };
        __u32 value;
        bpf_map_lookup_elem(bpf_map__fd(map), &key, &value);
        // error checking omitted
        return value;
}

代わりに、単に __u64 cgroup_inode_id をキーのタイプとして:

#include <bpf/bpf.h>

struct {
        __uint(type, BPF_MAP_TYPE_CGROUP_STORAGE);
        __type(key, __u64);
        __type(value, __u32);
} cgroup_storage SEC(".maps");

int program(struct __sk_buff *skb)
{
        __u32 *ptr = bpf_get_local_storage(&cgroup_storage, 0);
        __sync_fetch_and_add(ptr, 1);

        return 0;
}

ユーザー空間:

#include <linux/bpf.h>
#include <linux/libbpf.h>

__u32 map_lookup(struct bpf_map *map, __u64 cgrp, enum bpf_attach_type type)
{
        __u32 value;
        bpf_map_lookup_elem(bpf_map__fd(map), &cgrp, &value);
        // error checking omitted
        return value;
}

セマンティクス¶

BPF_MAP_TYPE_PERCPU_CGROUP_STORAGE はこのマップタイプの変種です。このper-CPU変種は、各ストレージに対して各CPUに異なるメモリ領域を持ちます。非per-CPUの場合は、各ストレージに対して同じメモリ領域を持ちます。

Linux 5.9以前では、ストレージのライフタイムは厳密にアタッチごとに制御され、単一の CGROUP_STORAGE マップに対して、最大で1つのプログラムのみがロード可能です。プログラムは複数のcgroupにアタッチされるか、複数のアタッチタイプを持つことができます。各アタッチはゼロ初期化された新しいストレージを作成し、アタッチ解除時にストレージが解放されます。

ロード検証時間において、各タイプのマップ（per-CPUおよび非per-CPU）とBPFプログラムは1対1の関連付けがあります。その結果、各マップは1つのBPFプログラムのみで使用可能であり、各BPFプログラムは各タイプごとに1つのストレージマップのみを使用できます。マップは1つのBPFプログラムのみで使用可能であるため、このcgroupのストレージを他のBPFプログラムと共有することは不可能でした。

Linux 5.9 以降、ストレージは複数のプログラムで共有可能になりました。プログラムが cgroup にアタッチされる際、カーネルはマップに cgroup とアタッチタイプのペアに関するエントリが既に存在しない場合にのみ新しいストレージを作成し、それ以外の場合は既存のストレージを再利用します。マップがアタッチタイプで共有されている場合、アタッチタイプは比較時に無視されます。ストレージは、マップまたはアタッチされた cgroup が解放されるときにのみ解放されます。アタッチ解除はストレージを直接解放しませんが、マップへの参照カウントがゼロになる可能性があり、間接的にマップ内のすべてのストレージを解放する原因になります。

マップはどの BPF プログラムとも関連付けられていませんので、共有が可能になります。ただし、BPF プログラムは各タイプ（per-CPU および non-per-CPU）ごとに1つのマップのみに関連付けることができます。BPF プログラムは1つ以上のマップを使用することはできません BPF_MAP_TYPE_CGROUP_STORAGE or more than one BPF_MAP_TYPE_PERCPU_CGROUP_STORAGE.

すべてのバージョンにおいて、ユーザースペースは cgroup のアタッチパラメータとアタッチタイプのペアを struct bpf_cgroup_storage_key BPF マップ API におけるキーとして使用し、特定のアタッチメントのストレージを読み取るか更新できます。Linux 5.9 のアタッチタイプで共有されるストレージでは、比較時に構造体の最初の値である cgroup inode ID が使用されるため、ユーザースペースは単に __u64 直接指定できます。

ストレージはアタッチ時にバインドされます。プログラムが親 cgroup にアタッチされ、子 cgroup でトリガーされる場合でも、ストレージは依然として親に属します。

ユーザースペースはマップに新しいエントリを追加したり、既存のエントリを削除したりすることはできません。プログラムのテスト実行では常に一時的なストレージが使用されます。

リモートプロセッサフレームワーク¶

はじめに¶

現代のSoCは、非対称マルチプロセッシング（AMP）構成で異質なリモートプロセッサデバイスを備えており、Linuxや他のリアルタイムOSのバリエーションを実行している可能性があります。

例としてOMAP4は、デュアルCortex-A9、デュアルCortex-M3、C64x+ DSPを備えています。典型的な構成では、デュアルCortex-A9はSMP構成でLinuxを実行し、他の3つのコア（2つのM3コアとDSP）はそれぞれAMP構成で独自のRTOSを実行しています。

remoteprocフレームワークは、ハードウェアの違いを抽象化しながら、さまざまなプラットフォーム/アーキテクチャがリモートプロセッサを制御（電源をオン、ファームウェアをロード、電源をオフ）できるようにします。これにより、ドライバ全体を複製する必要がありません。さらに、このフレームワークは、この種の通信をサポートするリモートプロセッサ用にrpmsg virtioデバイスを追加します。これにより、プラットフォーム固有のremoteprocドライバはいくつかの低レベルハンドラを提供するだけで、すべてのrpmsgドライバが動作します（virtioベースのrpmsgバスとそのドライバについての詳細情報については、 リモートプロセッサメッセージ(rpmsg)フレームワーク)。他のタイプのvirtioデバイスの登録も現在可能になりました。ファームウェアは、サポートするvirtioデバイスの種類を公開するだけで、remoteprocがそれらのデバイスを追加します。これにより、既存のvirtioドライバをリモートプロセッサバックエンドと組み合わせて再利用できるため、開発コストを最小限に抑えられます。

ユーザーAPI¶

int rproc_boot(struct rproc *rproc)

リモートプロセッサを起動する（つまり、ファームウェアをロードし、電源をオンにし、…）。

リモートプロセッサがすでに電源が入っている場合、この関数は即座に成功して返します。

成功した場合は0を返し、エラーの場合は適切なエラー値を返します。注意: この関数を使用するには、すでに有効なrprocハンドルが必要です。これを行う方法はいくつかあります（devres、pdata、remoteproc_rpmsg.cで行っている方法、または、これが一般的になる場合、dev_archdataを使用することも検討するかもしれません）。

void rproc_shutdown(struct rproc *rproc)

リモートプロセッサを電源を切る（以前にrproc_boot()で起動した場合）。@rprocが追加のユーザーによってまだ使用されている場合、この関数は電源の参照カウントを減らして終了し、実際にデバイスを電源を切らないままになります。

rproc_boot()のすべての呼び出しは（最終的には）rproc_shutdown()の呼び出しが伴う必要があります。rproc_shutdown()を冗長に呼び出すことはバグです。

注意

rprocの参照カウントをデクリメントしていない。ただのpower参照カウントのみを減らしている。これにより、rproc_shutdown()が返る後でも@rprocハンドルは有効なままとなり、必要に応じてその後のrproc_boot()で依然として使用できる。

struct rproc *rproc_get_by_phandle(phandle phandle)

デバイスツリーのphandleを使ってrprocハンドルを検索する。成功時はrprocハンドルを返し、失敗時はNULLを返す。この関数はリモートプロセッサの参照カウントをインクリメントするため、rprocがもはや必要なくなった時点で必ずrproc_put()を使って参照カウントをデクリメントする必要がある。

典型的な使用法¶

#include <linux/remoteproc.h>

/* in case we were given a valid 'rproc' handle */
int dummy_rproc_example(struct rproc *my_rproc)
{
      int ret;

      /* let's power on and boot our remote processor */
      ret = rproc_boot(my_rproc);
      if (ret) {
              /*
               * something went wrong. handle it and leave.
               */
      }

      /*
       * our remote processor is now powered on... give it some work
       */

      /* let's shut it down now */
      rproc_shutdown(my_rproc);
}

実装者向けAPI¶

struct rproc *rproc_alloc(struct device *dev, const char *name,
                              const struct rproc_ops *ops,
                              const char *firmware, int len)

新しいリモートプロセッサハンドルを割り当てますが、まだ登録は行わない。必要なパラメータは、基盤となるデバイス、このリモートプロセッサの名前、プラットフォーム固有のオペレーションハンドラ、このrprocを起動するためのファームウェア名、および割り当てたrprocドライバが使用するプライベートデータの長さ（バイト単位）である。

この関数はリモートプロセッサの初期化時に、rprocの実装によって使用されるべきである。

この関数でrprocハンドルを作成した後、準備ができたらrproc_add()を呼び出してリモートプロセッサの登録を完了するべきである。

成功時は新しいrprocが返され、失敗時はNULLが返される。

注意

更新処理が完了した後でも新しい読者が即座に開始する可能性があるため、以下のコードは読者がいないと信頼してはならない。 直接@rprocを解放してもよい。ただし、まだ登録されていない場合でも。代わりにrproc_alloc()を解除する必要がある場合はrproc_free()を使うべきである。

void rproc_free(struct rproc *rproc)

rproc_alloc()で割り当てたrprocハンドルを解放する。

この関数はrproc_alloc()を解除するため、rprocの参照カウントをデクリメントする。直接rprocを解放しない。参照カウントがゼロになるまで他の参照がなければ、その時だけrprocが解放される。

int rproc_add(struct rproc *rproc)

rproc_alloc()で割り当てた@rprocをremoteprocフレームワークに登録する。

プラットフォーム固有のrproc実装が、新しいリモートプロセッサデバイスがプローブされるたびにこの関数を呼び出す。

成功時は0を返し、それ以外の場合は適切なエラーコードを返す。注意: この関数は非同期のファームウェアロードコンテキストを開始し、rprocのファームウェアがサポートするvirtioデバイスを検索する。

見つかった場合は、それらのvirtioデバイスが作成され追加されるため、このリモートプロセッサの登録結果として、追加のvirtioドライバがプローブされる可能性がある。

int rproc_del(struct rproc *rproc)

rproc_add()を解除する。

プラットフォーム固有のrproc実装がrprocデバイスを削除する際にこの関数を呼び出すべきである。ただし、rproc_add()の以前の呼び出しが成功した場合にのみ呼び出すべきである。

rproc_del()が返る後も@rprocは依然として有効であり、最後の参照カウントを減らすためにrproc_free()を呼び出す必要がある。

成功時は0を返し、@rprocが有効でない場合は-EINVALを返す。

void rproc_report_crash(struct rproc *rproc, enum rproc_crash_type type)

remoteprocでのクラッシュを報告する

この関数は、プラットフォーム固有のrproc実装がクラッシュを検出するたびに呼び出す必要があります。この関数は非remoteprocドライバから呼び出さないでください。この関数はアトミック/割込みコンテキストから呼び出すことができます。

実装コールバック¶

これらのコールバックはプラットフォーム固有のremoteprocドライバによって提供されるべきです:

/**
 * struct rproc_ops - platform-specific device handlers
 * @start:    power on the device and boot it
 * @stop:     power off the device
 * @kick:     kick a virtqueue (virtqueue id given as a parameter)
 */
struct rproc_ops {
      int (*start)(struct rproc *rproc);
      int (*stop)(struct rproc *rproc);
      void (*kick)(struct rproc *rproc, int vqid);
};

すべてのremoteproc実装は少なくとも->startおよび->stopハンドラを提供する必要があります。rpmsg/virtio機能も望まれる場合、->kickハンドラも提供する必要があります。

The ->start() ハンドラはrprocハンドルを受け取り、デバイスを電源を入れて起動する必要があります（プラットフォーム固有のプライベートデータにアクセスするにはrproc->privを使用します）。起動アドレスが必要な場合は、rproc->bootaddrにあります（remoteprocコアがELFエントリポイントをそこに設定します）。成功時は0を返し、失敗時は適切なエラーコードを返す必要があります。

The ->stop() ハンドラはrprocハンドルを受け取り、デバイスを電源を切ります。成功時は0を返し、失敗時は適切なエラーコードを返す必要があります。

->kick()ハンドラはrprocハンドルと、新しいメッセージが配置されたvirtqueueのインデックスを受け取ります。実装では、リモートプロセッサを中断し、待機中のメッセージがあることを通知する必要があります。リモートプロセッサに正確なvirtqueueインデックスを通知するかどうかは任意です：既存のvirtqueueを走査してused ringsで新しいバッファを検索するのは簡単（かつコストがそれほど高くありません）。

バイナリファームウェア構造¶

現在、remoteprocはELF32およびELF64のファームウェアバイナリをサポートしています。ただし、このフレームワークでサポートしたい他のプラットフォーム/デバイスは、異なるバイナリ形式に基づいていることが予想されます。

このような使用例が現れた場合、バイナリ形式をフレームワークコアから分離する必要があります。これにより、共通コードを複製することなく複数のバイナリ形式をサポートできます。

ファームウェアが解析されるとき、そのさまざまなセグメントは指定されたデバイスアドレスに従ってメモリにロードされます（リモートプロセッサがメモリを直接アクセスする場合、物理アドレスになる可能性があります）。

標準のELFセグメントに加えて、ほとんどのリモートプロセッサは、私たちが「リソーステーブル」と呼ぶ特別なセクションも含みます。

リソーステーブルには、リモートプロセッサが電源を入れる前に必要なシステムリソースが含まれます。たとえば、物理的に連続したメモリの割当や、特定のオンチップパーセルのiommuマッピングなどです。Remotecoreは、リソーステーブルのすべての要件が満たされた後にのみデバイスを電源を入れます。

システムリソースに加えて、リソーステーブルには、リモートプロセッサがサポートする機能や設定の存在を発表するリソースエントリも含まれることがあります。たとえばトレースバッファやサポートされているvirtioデバイス（およびその設定）などが該当します。

リソーステーブルはこのヘッダーで始まります:

/**
 * struct resource_table - firmware resource table header
 * @ver: version number
 * @num: number of resource entries
 * @reserved: reserved (must be zero)
 * @offset: array of offsets pointing at the various resource entries
 *
 * The header of the resource table, as expressed by this structure,
 * contains a version number (should we need to change this format in the
 * future), the number of available resource entries, and their offsets
 * in the table.
 */
struct resource_table {
      u32 ver;
      u32 num;
      u32 reserved[2];
      u32 offset[0];
} __packed;

このヘッダーの直後にリソースエントリ自体が続き、それぞれが次のリソースエントリヘッダーで始まります:

/**
 * struct fw_rsc_hdr - firmware resource entry header
 * @type: resource type
 * @data: resource data
 *
 * Every resource entry begins with a 'struct fw_rsc_hdr' header providing
 * its @type. The content of the entry itself will immediately follow
 * this header, and it should be parsed according to the resource type.
 */
struct fw_rsc_hdr {
      u32 type;
      u8 data[0];
} __packed;

一部のリソースエントリは単なる発表であり、ホストに特定のremoteproc設定を通知するものもあります。他のエントリはホストに行動を求める（例：システムリソースの割り当て）ことがあります。また、ファームウェアがリソースを要求し、割り当てられたらホストがその詳細（例：割り当てられたメモリ領域のアドレス）を返すような交渉が求められることもあります。

現在サポートされているリソースタイプは以下の通りです:

/**
 * enum fw_resource_type - types of resource entries
 *
 * @RSC_CARVEOUT:   request for allocation of a physically contiguous
 *                memory region.
 * @RSC_DEVMEM:     request to iommu_map a memory-based peripheral.
 * @RSC_TRACE:            announces the availability of a trace buffer into which
 *                the remote processor will be writing logs.
 * @RSC_VDEV:       declare support for a virtio device, and serve as its
 *                virtio header.
 * @RSC_LAST:       just keep this one at the end
 * @RSC_VENDOR_START: start of the vendor specific resource types range
 * @RSC_VENDOR_END:   end of the vendor specific resource types range
 *
 * Please note that these values are used as indices to the rproc_handle_rsc
 * lookup table, so please keep them sane. Moreover, @RSC_LAST is used to
 * check the validity of an index before the lookup table is accessed, so
 * please update it as needed.
 */
enum fw_resource_type {
      RSC_CARVEOUT            = 0,
      RSC_DEVMEM              = 1,
      RSC_TRACE               = 2,
      RSC_VDEV                = 3,
      RSC_LAST                = 4,
      RSC_VENDOR_START        = 128,
      RSC_VENDOR_END          = 512,
};

特定のリソースタイプに関する詳細については、include/linux/remoteproc.hに記載されている専用構造体を参照してください。

また、プラットフォーム固有のリソースエントリがいつか現れる可能性もあります。その際には、新たにRSC_PLATFORMタイプを追加し、それらのリソースをプラットフォーム固有のrprocドライバに処理させることが容易です。

Virtio および remoteproc¶

ファームウェアはサポートするvirtioデバイスに関するremoteproc情報を提供すべきです。その設定も含め、RSC_VDEVリソースエントリはvirtioデバイスID（virtio_ids.hにあるもの）、virtio機能、virtioコンフィギュレーションスペース、vrings情報なども指定する必要があります。

新しいリモートプロセッサが登録されるとき、remoteprocフレームワークはそのリソーステーブルを検索し、サポートするvirtioデバイスを登録します。ファームウェアは任意の数のvirtioデバイスをサポートし、それらの種類も任意です（必要に応じて、単一のリモートプロセッサが複数のrpmsg virtioデバイスをサポートすることも容易です）。

もちろん、RSC_VDEVリソースエントリはvirtioデバイスの静的割り当てにしか対応しません。動的割り当てはrpmsgバスを使用して実現され、これはすでにrpmsgチャネルの動的割り当てを実施しているのと同様です（詳しくはrpmsg.txtを参照してください）。

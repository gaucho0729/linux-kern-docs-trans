CRC計算の簡単なチュートリアル¶

CRCは長除法の余りです。メッセージにCRCを追加すると、全体（メッセージ+CRC）は指定されたCRC多項式の倍数になります。CRCを確認するには、再計算された値とCRCが一致することを確認するか、 または メッセージ+CRCを処理した際の余りが0であることを確認できます。この後者のアプローチは多くのハードウェア実装で採用されており、そのため多くのプロトコルがCRCの後にフレーム終端フラグを配置しています。

これは学校で学ぶ通常の長除法と同じです。ただし、以下の点が異なります：

  • 2進数で計算するため、桁は0と1のみです。

  • 多項式を割る際には繰り上がりはありません。加算と減算ではなく、XORを使用します。そのため、加算と減算の違いについて少し手を抜く傾向があります。

すべての割り算と同じく、余りは常に除数よりも小さくなります。32ビットのCRCを生成するには、除数は実際には33ビットのCRC多項式です。33ビットの長さなので、ビット32は常に設定されています。そのため、通常CRCは16進数で表され、最上位ビットは省略されます。（IEEE 754浮動小数点形式に慣れている場合は、同じ考え方です。）

注意点として、CRCはビットの文字列に対して計算されますので、 ビット各バイト内のビットのエンドイアンネスを決める必要があります。エラー検出性能を最大にするには、実際に送信された順序と一致させる必要があります。たとえば、標準的なRS-232シリアル通信はリトルエンディアンです。最上位ビット（場合によってはパリティビットとして使用される）が最後に送信されます。CRCワードをメッセージに追加する際には、エンドイアンネスに合った正しい順序で行う必要があります。

通常の割り算と同様に、1桁（ビット）ずつ処理します。各ステップで、被除数の1つ次の桁（ビット）を取り、現在の余りに追加します。次に、余りを範囲内に戻すための適切な除数の倍数を選び、減算します。2進数では、この倍数は0または1のみで、XORをキャンセルさせるため、余りのビット32をコピーします。

CRCを計算する際には商は気にしないため、商のビットを無視できます。ただし、多項式の適切な倍数を余りから引くことで、再び最初に戻り、次のビットを処理できる状態になります。

ビッグエンディアンのCRCはこのようにコードされます：

for (i = 0; i < input_bits; i++) {
        multiple = remainder & 0x80000000 ? CRCPOLY : 0;
        remainder = (remainder << 1 | next_input_bit()) ^ multiple;
}

余りのシフト後のビット32を取得するには、余りのビット31を確認します before シフトします。

次に、next_input_bit()でシフトするビットが余りに影響を与えるのは32ビット先の処理になってからであることに注意してください。そのため、この処理の最初の32サイクルは非常に退屈です。また、メッセージにCRCを追加するには、最後に32ビットの空き領域が必要なので、各メッセージの末尾にゼロを32ビット分シフトする処理を追加する必要があります。

これらの詳細から、標準的なテクニックとして、next_input_bit()の統合を必要になるタイミングまで先延ばしにします。これにより、最初の32サイクルは事前に計算しておくことができ、CRCを確保するための最終的な32ビットのゼロの統合処理を完全に省略できます。これによりコードは以下のようになります:

for (i = 0; i < input_bits; i++) {
        remainder ^= next_input_bit() << 31;
        multiple = (remainder & 0x80000000) ? CRCPOLY : 0;
        remainder = (remainder << 1) ^ multiple;
}

この最適化により、little-endianのコードは特にシンプルになります:

for (i = 0; i < input_bits; i++) {
        remainder ^= next_input_bit();
        multiple = (remainder & 1) ? CRCPOLY : 0;
        remainder = (remainder >> 1) ^ multiple;
}

余り多項式の最上位係数は、二進数の「余り」変数の最下位ビットに格納されています。他のエンディアンに関する詳細はCRCPOLY（ビット逆転を必要とする）とnext_input_bit()に隠されています。

next_input_bitがビットを合理的な順序で返している限り、 が 追加ビットを統合するタイミングを最後まで待つ必要はありません。1ビットずつではなく、8ビットずつ処理できます:

for (i = 0; i < input_bytes; i++) {
        remainder ^= next_input_byte() << 24;
        for (j = 0; j < 8; j++) {
                multiple = (remainder & 0x80000000) ? CRCPOLY : 0;
                remainder = (remainder << 1) ^ multiple;
        }
}

あるいはlittle-endianの場合:

for (i = 0; i < input_bytes; i++) {
        remainder ^= next_input_byte();
        for (j = 0; j < 8; j++) {
                multiple = (remainder & 1) ? CRCPOLY : 0;
                remainder = (remainder >> 1) ^ multiple;
        }
}

入力が32ビットの倍数である場合、32ビットワードを1つずつXORで統合し、内側のループ回数を32に増やすこともできます。

また、2つのループスタイルを組み合わせることも可能です。例えば、メッセージの大部分をバイト単位で処理し、残りの小数点以下のバイトにはビット単位で処理するなど、柔軟に使い分けられます。

条件分岐の数を減らすために、ソフトウェアでは一般的にDilip V. Sarwate氏が提唱した「バイト単位でのテーブル参照法」が使われます。「Cyclic Redundancy Checksの計算におけるテーブル参照法」、Comm. ACM v.31 no.8 (1998年8月) p.1008-1013。

ここでは、余りを1ビットずつシフトして正しい倍数を減算するのではなく、1バイトずつシフトします。これにより、40ビット（33ビットではなく）の中間余りが生成され、多項式の正しい倍数を減算するためには、高8ビットをインデックスにした256エントリの参照表を使います。

(参照表のエントリは、与えられた1バイトメッセージのCRC-32です。)

スペースが制限されている場合、より小さなテーブルが使われます。例えば、4ビットずつシフトし、その後16エントリのテーブルを参照するなど。

この技術では、8ビット以上を処理するのは現実的ではありません。なぜなら、256エントリ以上のテーブルはメモリを多く消費し、さらに重要なのはL1キャッシュを多く消費するからです。

ソフトウェアのパフォーマンスを向上させるには、「スライシング（slicing）」という技術が利用できます。詳しくは「High Octane CRC Generation with the Intel Slicing-by-8 Algorithm」をご覧ください。 ftp://download.intel.com/technology/comms/perfnet/download/slicing-by-8.pdf

テーブルの検索回数は変わりませんが、並列性が向上します。伝統的なSarwateアルゴリズムでは、各テーブル検索が完了するまで次のインデックスの計算ができません。

「スライシング by 2」技術では、余りを16ビットずつシフトして48ビットの中間余りを生成します。65536エントリのテーブルで単一の検索を行う代わりに、2つの256エントリのテーブルで2つの高バイトを検索します。それぞれのテーブルは、対応するバイトをキャンセルする余りを含みます。テーブルは異なるのは、キャンセルする多項式が異なるためです。一方はx^32からx^39の係数が非ゼロで、もう一方はx^40からx^47の係数が非ゼロです。

現代のプロセッサは多くの並列メモリ操作を処理できるため、単一のテーブル検索にかかる時間とほぼ同じで、基本的なSarwateアルゴリズムのほぼ2倍の速度で動作します。

これは「スライシング by 4」に拡張可能です。4つの256エントリのテーブルを使用して、各ステップで32ビットのデータをフェッチし、CRCとXORして結果をバイトに分解しテーブルで検索します。32ビットシフトにより中間余りの低オーダービットがゼロになるため、最終的なCRCは4つのテーブル検索結果のXORです。

しかし、この方法でも順序的な実行を強制しているため、次のグループのテーブル検索が開始されるまで、前のグループの4つの検索が完了する必要があります。そのため、プロセッサのロード/ストアユニットが時折アイドル状態になることがあります。

プロセッサを最大限に活用するには、「スライシング by 8」が8つの検索を並列に実行します。各ステップで32ビットのCRCを64ビットシフトし、64ビットの入力データとXORします。重要なのは、8つのバイトのうち4つは入力データそのものであり、前のCRCに依存しません。そのため、それらの4つのテーブル検索は前のループイテレーションを待つことなく即座に開始できます。

現代のスーパースケーラープロセッサは常に4つのロードを処理中にしておくことで、L1キャッシュを十分に活用し、忙しい状態を維持できます。

実際の世界でのCRC実装に関するもう2点の詳細:

通常、メッセージが既に多項式の倍数である場合、ゼロビットを追加するとその多項式のより大きな倍数になります。したがって、基本的なCRCは追加されたゼロビット（またはバイト）を検出できません。CRCがこの状態を検出できるようにするため、一般的にCRCを追加する前に反転させます。これにより、メッセージ＋CRCの余りがゼロではなく、固定の非ゼロ値になります。（反転パターンのCRC値は0xffffffffです。）

ゼロビットがメッセージの先頭に追加される場合にも同様の問題が生じます。類似した解決策が採用されます。CRC計算を開始する際の初期余りを0ではなくすべて1に設定します。復号処理時に同じ方法で開始すれば、違いは生じません。

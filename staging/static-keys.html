スタティックキー¶

警告

非推奨のAPI:

‘struct static_key’の直接的な使用は現在非推奨とされています。また、static_key_{true,false}()も同様に非推奨とされています。つまり、以下のコードは使用しないでください:

struct static_key false = STATIC_KEY_INIT_FALSE;
struct static_key true = STATIC_KEY_INIT_TRUE;
static_key_true()
static_key_false()

更新されたAPIの置き換えは以下の通りです:

DEFINE_STATIC_KEY_TRUE(key);
DEFINE_STATIC_KEY_FALSE(key);
DEFINE_STATIC_KEY_ARRAY_TRUE(keys, count);
DEFINE_STATIC_KEY_ARRAY_FALSE(keys, count);
static_branch_likely()
static_branch_unlikely()

要約¶

Static keysは、GCCの機能とコードパッチング技術を活用して、パフォーマンスに敏感な高速パスのカーネルコードにまれに使用される機能を含めることができます。簡単な例:

DEFINE_STATIC_KEY_FALSE(key);

...

if (static_branch_unlikely(&key))
        do unlikely code
else
        do likely code

...
static_branch_enable(&key);
...
static_branch_disable(&key);
...

static_branch_unlikely()ブランチは、likelyなコードパスへの影響をできるだけ最小限に抑えながらコードに生成されます。

動機¶

現在、トレースポイントは条件分岐を用いて実装されています。条件チェックには各トレースポイントごとにグローバル変数を確認する必要があります。このチェックのオーバーヘッドは小さなものですが、メモリキャッシュが負担を受けると（これらのグローバル変数のメモリキャッシュラインが他のメモリアクセスと共有される可能性があるため）、オーバーヘッドが増加します。カーネル内のトレースポイント数を増やすにつれてこのオーバーヘッドが問題になる可能性があります。さらに、トレースポイントはしばしば非活性（無効）状態であり、直接のカーネル機能を提供しません。そのため、トレースポイントの影響をできるだけ減らすことが極めて望ましいです。トレースポイントがこの作業の元来の動機であるにもかかわらず、他のカーネルコードパスもstatic keysの機能を活用できるようにする必要があります。

解決策¶

gcc (v4.5)は新しい‘asm goto’ステートメントを追加し、ラベルへのジャンプを可能にします:

https://gcc.gnu.org/ml/gcc-patches/2009-07/msg01556.html

‘asm goto’を用いることで、メモリの確認を必要とせずにデフォルトでジャンプされるか、ジャンプされない分岐を作成できます。その後、実行時において、分岐ポイントをパッチングして分岐方向を変更できます。

例えば、以下のような単純な分岐があり、デフォルトでは無効になっています:

if (static_branch_unlikely(&key))
        printk("I am the true branch\n");

そのため、デフォルトでは‘printk’は出力されません。生成されるコードは、ストレートラインコードパスに単一のアトミックな‘no-op’命令（x86では5バイト）が含まれます。分岐が‘flipped’（反転）されると、ストレートラインコードパスの‘no-op’を‘jump’命令に置き換えて、オフラインの真の分岐先にジャンプします。つまり、分岐方向の変更にはコストがかかるものの、分岐選択は基本的に‘無料’です。これがこの最適化の基本的なトレードオフです。

この低レベルのパッチングメカニズムは‘jump label patching’と呼ばれ、static keysの機能の基盤となります。

Static key label API、使用方法および例¶

この最適化を活用するにはまずキーパラメータを定義する必要があります:

DEFINE_STATIC_KEY_TRUE(key);

または:

DEFINE_STATIC_KEY_FALSE(key);

キーパラメータはグローバルでなければなりません。つまり、スタック上に割り当てられたり、実行時において動的に割り当てられたりすることはできません。

キーパラメータはコード内で以下のように使用されます:

if (static_branch_unlikely(&key))
        do unlikely code
else
        do likely code

または：

if (static_branch_likely(&key))
        do likely code
else
        do unlikely code

DEFINE_STATIC_KEY_TRUE() または DEFINE_STATIC_KEY_FALSE で定義されたキーは、static_branch_likely() または static_branch_unlikely() のステートメントで使用可能です。

ブランチは以下の方法で true に設定できます:

static_branch_enable(&key);

または false に設定できます:

static_branch_disable(&key);

その後、参照カウントを介してブランチを切り替えることができます:

static_branch_inc(&key);
...
static_branch_dec(&key);

したがって、「static_branch_inc()」は「ブランチをtrueにする」を、「static_branch_dec()」は「ブランチをfalseにする」を表し、適切な参照カウント管理を行います。例えば、キーが初期化時にtrueの場合、static_branch_dec()はブランチをfalseに切り替え、その後のstatic_branch_inc()は再びtrueに戻します。同様に、キーが初期化時にfalseの場合、static_branch_inc()はブランチをtrueに変更し、その後のstaticのstatic_branch_dec()は再びfalseに戻します。

ブランチの状態と参照カウントは「static_key_enabled()」および「static_key_count()」で取得可能です。一般的に、これらの関数を使用する際は、有効/無効化や増減操作の関数で使用されるmutexと同じmutexで保護する必要があります。

ブランチの切り替えはいくつかのロックを取得することを引き起こします。特にCPUホットプラグロック（CPUがカーネルに追加される際の競合を防ぐため）が含まれます。したがって、ホットプラグノティファイア内から静的キーAPIを呼び出すことは確実なデッドロックの原因になります。この機能を依然として使用可能にするため、以下の関数が提供されています:

static_key_enable_cpuslocked() static_key_disable_cpuslocked() static_branch_enable_cpuslocked() static_branch_disable_cpuslocked()

これらは ではありません 汎用的な関数であり、本当に上記のコンテキスト内でかつ他のコンテキストと競合しない状況でのみ使用すべきです。

配列形式のキーが必要な場合は、以下のように定義できます:

DEFINE_STATIC_KEY_ARRAY_TRUE(keys, count);

または:

DEFINE_STATIC_KEY_ARRAY_FALSE(keys, count);

したがって、ジャンプラベル無効のケースでは「mov」「test」「jne」の3つの命令が追加されるのに対し、ジャンプラベル有効のケースでは「no-op（無操作命令）」または「jmp 0（ジャンプ先0）」が使用される。(「jmp 0」は起動時に5バイトのアトミックなno-op命令にパッチされる。) したがって、ジャンプラベル無効のケースでは以下のようになる:

6 (mov) + 2 (test) + 2 (jne) = 10 - 5 (5 byte jump 0) = 5 addition bytes.

パディングバイトを含めると、ジャンプラベルコードはこの小さな関数に対して合計16バイトの指令メモリを節約する。この場合、ジャンプラベルを用いない関数は80バイトの長さであるため、指令フットプリントの20%を節約できた。さらに改善が可能である。なぜなら、5バイトのno-opは2バイトのno-opに実質的に置き換えられるからである。2バイトのjmpで分岐先に到達できるためだ。ただし、現在は最適なno-opサイズの実装がされていない(現在はハードコードされている)。

リモートプロセッサメッセージ(rpmsg)フレームワーク¶

注意

このドキュメントではrpmsgバスとrpmsgドライバの作成方法について説明します。新しいプラットフォームへのrpmsgサポートの追加方法を学ぶには、remoteproc.txt（Documentation/に含まれています）をご参照ください。

はじめに¶

現代のSoCは、非対称マルチプロセッシング（AMP）構成で異質なリモートプロセッサデバイスを採用することが一般的です。これらはLinuxや他のリアルタイムOSのいずれかのインスタンスを実行している可能性があります。

例えばOMAP4は、双コアCortex-A9、双コアCortex-M3、C64x+ DSPを搭載しています。通常、双コアCortex-A9はSMP構成でLinuxを実行し、他の3つのコア（2つのM3コアとDSP）はそれぞれAMP構成でRTOSのインスタンスを実行しています。

通常、AMPリモートプロセッサは専用のDSPコーデックとマルチメディアハードウェアアクセラレータを採用しており、主なアプリケーションプロセッサからCPU重いマルチメディアタスクをオフロードするために使用されます。

これらのリモートプロセッサは、遅延敏感なセンサーの制御、ランダムなハードウェアブロックの駆動、または主なCPUがアイドルしている間のバックグラウンドタスクの実行にも利用できます。

これらのリモートプロセッサのユーザーは、ユーザーランドアプリケーション（例：マルチメディアフレームワークがリモートOMXコンポーネントと通信する場合）またはカーネルドライバ（リモートプロセッサのみがアクセス可能なハードウェアを制御し、リモートプロセッサの代わってカーネル制御のリソースを確保するなど）です。

Rpmsgはvirtioベースのメッセージングバスであり、カーネルドライバがシステム上のリモートプロセッサと通信できるようにします。必要に応じて、ドライバは適切なユーザースペースインターフェースを公開できます。

ユーザーランドにrpmsg通信を公開するドライバを作成する際は、リモートプロセッサがシステムの物理メモリや他のセンシティブなハードウェアリソース（例：OMAP4ではリモートコアやハードウェアアクセラレータが物理メモリ、GPIOバンク、DMAコントローラー、I2Cバス、GPTimers、メモリーメッセージングデバイス、HWSpinlocksなどに直接アクセスできる可能性があります）に直接アクセスできる点を考慮してください。さらに、リモートプロセッサがRTOSを実行している場合、すべてのタスクがプロセッサに露出されたメモリ/デバイス全体にアクセスできる可能性があります。不正な（またはバグのある）ユーザーランドコードがリモートのバグを悪用してシステムを制御するリスクを最小限に抑えるため、ユーザーランドがメッセージを送信できる特定のrpmsgチャネル（以下で定義）に制限し、メッセージコンテンツに対する制御をできるだけ最小限にすることが望ましいです。

すべてのrpmsgデバイスは、リモートプロセッサと通信するためのチャネルです（したがって、rpmsgデバイスはチャネルと呼ばれます）。チャネルはテキスト名で識別され、ローカル（「ソース」）のrpmsgアドレスと、リモート（「宛先」）のrpmsgアドレスを持ちます。

ドライバがチャネルでリスニングを開始すると、そのrxコールバックは一意なrpmsgローカルアドレス（32ビット整数）にバインドされます。このようにして、インバウンドメッセージが到着した際、rpmsgコアはその宛先アドレスに基づき適切なドライバにメッセージをディスパッチします（これは、ドライバのrxハンドラをインバウンドメッセージのペイロードとともに呼び出すことで実現されます）。

ユーザーAPI¶

int rpmsg_send(struct rpmsg_channel *rpdev, void *data, int len);

指定されたチャネルを介してリモートプロセッサにメッセージを送信します。呼び出し元はチャネル、送信したいデータ、およびデータの長さ（バイト単位）を指定します。メッセージは指定されたチャネルで送信され、そのソースおよび宛先アドレスフィールドがチャネルのsrcとdstアドレスに設定されます。

TXバッファが利用不可な場合、関数は15秒のタイムアウトが発生するまでブロックします（つまり、リモートプロセッサがTXバッファを消費してvirtioのusedディスクリプタリングに戻すまで待機します）。タイムアウトが発生した場合、-ERESTARTSYSが返されます。

この関数は現在、プロセスコンテキストからのみ呼び出すことができます。成功時は0を、失敗時は適切なエラーコードを返します。

int rpmsg_sendto(struct rpmsg_channel *rpdev, void *data, int len, u32 dst);

指定されたチャネルを介してリモートプロセッサにメッセージを送信します。呼び出し元は宛先アドレスを指定する必要があります。

呼び出し元はチャネル、送信したいデータ、データの長さ（バイト単位）、および明示的な宛先アドレスを指定する必要があります。

メッセージは、チャネルに属するリモートプロセッサに送信され、チャネルのsrcアドレスとユーザーが提供したdstアドレスを使用します（したがって、チャネルのdstアドレスは無視されます）。

TXバッファが利用不可な場合、関数は15秒のタイムアウトが発生するまでブロックします（つまり、リモートプロセッサがTXバッファを消費してvirtioのusedディスクリプタリングに戻すまで待機します）。タイムアウトが発生した場合、-ERESTARTSYSが返されます。

この関数は現在、プロセスコンテキストからのみ呼び出すことができます。成功時は0を、失敗時は適切なエラーコードを返します。

int rpmsg_send_offchannel(struct rpmsg_channel *rpdev, u32 src, u32 dst,
                                                      void *data, int len);

ユーザーが提供したsrcおよびdstアドレスを使用して、リモートプロセッサにメッセージを送信します。

呼び出し元はチャネル、送信したいデータ、データの長さ（バイト単位）、および明示的なソースおよび宛先アドレスを指定する必要があります。メッセージは、チャネルに属するリモートプロセッサに送信されますが、チャネルのsrcおよびdstアドレスは無視され、代わりにユーザーが提供したアドレスが使用されます。

TXバッファが利用不可な場合、関数は15秒のタイムアウトが発生するまでブロックします（つまり、リモートプロセッサがTXバッファを消費してvirtioのusedディスクリプタリングに戻すまで待機します）。タイムアウトが発生した場合、-ERESTARTSYSが返されます。

この関数は現在、プロセスコンテキストからのみ呼び出すことができます。成功時は0を、失敗時は適切なエラーコードを返します。

int rpmsg_trysend(struct rpmsg_channel *rpdev, void *data, int len);

指定されたチャネルを介してリモートプロセッサにメッセージを送信します。呼び出し元はチャネル、送信したいデータ、およびデータの長さ（バイト単位）を指定します。メッセージは指定されたチャネルで送信され、そのソースおよび宛先アドレスフィールドがチャネルのsrcとdstアドレスに設定されます。

TXバッファが利用不可な場合、関数は15秒待機することなく即座に-ENOMEMを返します。

この関数は現在、プロセスコンテキストからのみ呼び出すことができます。成功時は0を、失敗時は適切なエラーコードを返します。

int rpmsg_trysendto(struct rpmsg_channel *rpdev, void *data, int len, u32 dst)

指定されたチャネルを介してリモートプロセッサにメッセージを送信します。呼び出し元はユーザーが提供した宛先アドレスを指定する必要があります。

ユーザーは、送信したいデータ、その長さ（バイト数）、および明示的な宛先アドレスを指定する必要があります。

メッセージは、チャネルに属するリモートプロセッサに送信され、チャネルのsrcアドレスとユーザーが提供したdstアドレスを使用します（したがって、チャネルのdstアドレスは無視されます）。

TXバッファが利用不可な場合、関数は15秒待機することなく即座に-ENOMEMを返します。

この関数は現在、プロセスコンテキストからのみ呼び出すことができます。成功時は0を、失敗時は適切なエラーコードを返します。

int rpmsg_trysend_offchannel(struct rpmsg_channel *rpdev, u32 src, u32 dst,
                                                      void *data, int len);

ユーザーが提供したソースと宛先アドレスを使用して、リモートプロセッサにメッセージを送信します。

ユーザーは、送信したいデータ、その長さ（バイト数）、および明示的なソースと宛先アドレスを指定する必要があります。このメッセージは、チャネルが属するリモートプロセッサに送信されますが、チャネルのsrcとdstアドレスは無視され（ユーザーが提供したアドレスが代わりに使用されます）。

TXバッファが利用不可な場合、関数は15秒待機することなく即座に-ENOMEMを返します。

この関数は現在、プロセスコンテキストからのみ呼び出すことができます。成功時は0を、失敗時は適切なエラーコードを返します。

struct rpmsg_endpoint *rpmsg_create_ept(struct rpmsg_device *rpdev,
                                        rpmsg_rx_cb_t cb, void *priv,
                                        struct rpmsg_channel_info chinfo);

システム内のすべてのrpmsgアドレスは、rpmsg_endpoint構造体を介してrxコールバックにバインドされています（インバウンドメッセージが到着した際、rpmsgバスが適切なコールバックハンドラを使用してディスパッチされます）。

この関数は、ドライバがこのようなエンドポイントを作成し、コールバックをバインドし（必要に応じてプライベートデータも含め）、事前にわかっているrpmsgアドレスまたは動的に割り当てられるアドレスにバインドできるようにします。

シンプルなrpmsgドライバはrpmsg_create_eptを呼び出す必要がありません。rpmsgバスがドライバをプローブする際に（rpmsgバスに登録したrxコールバックを提供した場合）、すでにエンドポイントが作成されています。

したがって、シンプルなドライバには問題ありません。すでにエンドポイントが存在し、rxコールバックがrpmsgアドレスにバインドされています。関連するインバウンドメッセージが到着した場合（つまり、メッセージの宛先アドレスがドライバのrpmsgチャネルのソースアドレスと一致する場合）、ドライバのハンドラが呼び出されて処理されます。

ただし、複雑なドライバは追加のrpmsgアドレスを割り当て、それらを異なるrxコールバックにバインドする必要があります。これを実現するには、この関数を呼び出す必要があります。ドライバはチャネル（新しいエンドポイントが所属するリモートプロセッサにバインドされるように）、rxコールバック関数、オプションのプライベートデータ（rxコールバックが呼び出される際に戻される）、およびバインドしたいアドレスを提供する必要があります。addrがRPMSG_ADDR_ANYの場合、rpmsg_create_eptは動的に利用可能なrpmsgアドレスを割り当てます（ここでは常にRPMSG_ADDR_ANYを使用する理由が明確でなければなりません）。

成功した場合、エンドポイントへのポインタを返します。エラーの場合、NULLを返します。

void rpmsg_destroy_ept(struct rpmsg_endpoint *ept);

既存のrpmsgエンドポイントを破壊します。ユーザーは、rpmsg_create_ept()で以前に作成したrpmsgエンドポイントへのポインタを提供する必要があります。

int register_rpmsg_driver(struct rpmsg_driver *rpdrv);

rpmsgバスにrpmsgドライバを登録します。ユーザーは、ドライバの->probe()と->remove()関数、rxコールバック、およびこのドライバがプローブ対象とするチャネル名を指定するid_tableを持つrpmsg_driver構造体へのポインタを提供する必要があります。

void unregister_rpmsg_driver(struct rpmsg_driver *rpdrv);

rpmsgバスからrpmsgドライバを登録解除します。ユーザーは以前に登録したrpmsg_driver構造体へのポインタを提供します。成功時は0を、失敗時は適切なエラーコードを返します。

典型的な使用法¶

以下は、probe()時に「hello!」メッセージを送信し、受信メッセージをコンソールに出力するシンプルなrpmsgドライバの例です。

#include <linux/kernel.h>
#include <linux/module.h>
#include <linux/rpmsg.h>

static void rpmsg_sample_cb(struct rpmsg_channel *rpdev, void *data, int len,
                                              void *priv, u32 src)
{
      print_hex_dump(KERN_INFO, "incoming message:", DUMP_PREFIX_NONE,
                                              16, 1, data, len, true);
}

static int rpmsg_sample_probe(struct rpmsg_channel *rpdev)
{
      int err;

      dev_info(&rpdev->dev, "chnl: 0x%x -> 0x%x\n", rpdev->src, rpdev->dst);

      /* send a message on our channel */
      err = rpmsg_send(rpdev, "hello!", 6);
      if (err) {
              pr_err("rpmsg_send failed: %d\n", err);
              return err;
      }

      return 0;
}

static void rpmsg_sample_remove(struct rpmsg_channel *rpdev)
{
      dev_info(&rpdev->dev, "rpmsg sample client driver is removed\n");
}

static struct rpmsg_device_id rpmsg_driver_sample_id_table[] = {
      { .name = "rpmsg-client-sample" },
      { },
};
MODULE_DEVICE_TABLE(rpmsg, rpmsg_driver_sample_id_table);

static struct rpmsg_driver rpmsg_sample_client = {
      .drv.name       = KBUILD_MODNAME,
      .id_table       = rpmsg_driver_sample_id_table,
      .probe          = rpmsg_sample_probe,
      .callback       = rpmsg_sample_cb,
      .remove         = rpmsg_sample_remove,
};
module_rpmsg_driver(rpmsg_sample_client);

注意

同様のサンプルはsamples/rpmsg/に構築・ロード可能なものとして用意されています。

rpmsg チャネルの割当¶

現在はrpmsgチャネルの動的割当のみをサポートしています。

これは、VIRTIO_RPMSG_F_NSというvirtioデバイス機能セットを持つリモートプロセッサでのみ可能です。この機能ビットは、リモートプロセッサが動的名前サービスアノンシメントメッセージをサポートすることを示します。

この機能が有効になると、rpmsgデバイス（つまりチャネル）の作成は完全に動的になります。リモートプロセッサは、名前サービスメッセージ（名前とrpmsgアドレスを含み、struct rpmsg_ns_msgを参照）を送ることで、リモートrpmsgサービスの存在をアノンシメントします。

このメッセージはrpmsgバスによって処理され、これにより動的にrpmsgチャネルが作成され登録されます（これはリモートサービスを表します）。関連するrpmsgドライバが登録された場合、バスが即座にプローブを行い、リモートサービスへのメッセージ送信を開始できるようになります。

今後、virtioコンフィギュレーションスペースを介したrpmsgチャネルの静的作成も追加する予定ですが、現時点では実装されていません。

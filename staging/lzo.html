LinuxのLZOデコンプレッサーが理解するLZOストリーム形式¶

はじめに¶

これは仕様ではありません。LZOストリーム形式の仕様は公に公開されていないように見えます。このドキュメントは、Linuxカーネルに実装されたLZOデコンプレッサが理解する入力形式について説明しています。分析対象のファイルはlib/lzo/lzo1x_decompress_safe.cです。圧縮機や他の実装については分析は行われていませんが、形式が標準と一致している可能性が高いと考えられます。このドキュメントの目的は、コードの動作をよりよく理解し、今後のバグレポートに対するより効率的な修正を提案することです。

説明¶

ストリームは、複数の命令、オペランド、データから構成されています。命令は、オペコードを表す少数のビットと、その命令のオペランドを形成するビットからなり、オペコードや前命令でコピーされたリテラルの数に応じてサイズや位置が異なります。オペランドは以下の情報を示します：

  • 辞書（過去の出力バッファ）からデータをコピーする際の距離

  • 辞書からコピーするバイト数（長さ）

  • コピーするリテラルの数。これは次の命令のために保持される情報として変数「state」に保持されます。

オペコードとオペランドに応じて、追加データが続くことがあります。これらの追加データは、オペランドの補足（例: 大きな値で符号化された長さまたは距離）であるか、出力バッファにコピーされるリテラルである可能性があります。

ブロックの最初のバイトは、他のバイトとは異なる符号化方式を使用しており、そのバイト以前には辞書が存在しないため、リテラルの使用に最適化されているように見えます。

長さは常にオペランド内の少数のビットから始まる可変長で符号化されます。ビット数が長さを表すのに不十分な場合、最大で255の割合で1バイトごとに追加して、最大で255:1の圧縮率を達成できません。#bitsを使用した可変長符号化は常に同じです：

length = byte & ((1 << #bits) - 1)
if (!length) {
        length = ((1 << #bits) - 1)
        length += 255*(number of zero bytes)
        length += first-non-zero-byte
}
length += constant (generally 2 or 3)

辞書への参照では、距離は出力ポインタに対して相対的です。距離は特定の範囲に属する少数のビットで符号化され、これにより複数のコピー命令が異なる符号化方式を使用するようになります。一部の符号化方式では1つの追加バイトが使用され、他の場合は2つの追加バイトがリトルエンディアン16ビット量を形成します（下記でLE16とマークされます）。

大文字のコピー以外のすべての指示において、次の指示を開始する前に0、1、2、または3つのリテラルがコピーされます。コピーされたリテラルの数は次の指示の意味や動作に影響を与える可能性があります。実際には、0、4未満、または4以上がコピーされたかを知る必要があるのは1つの指示だけです。これはこの実装における<state>変数に保存されている情報です。このリテラルの数は通常、指令の最後の2ビットに符号化されますが、場合によっては追加のオペランド（例：距離）の最後の2ビットからも取得できます。

距離0のブロックコピーが見られるとストリームの終わりと宣言されます。この距離（0001HLLL）を符号化する指示は1つだけ存在し、距離には1つのLE16オペランドが必要なので3バイトが必要です。

重要です。

コード内では一部の長さのチェックが抜けている場合があります。これは、解析前にすでに確保されているバイト数に基づいて特定の指示が呼び出されるためです。それらは追加のバイトを消費した場合にのみ、このクレジットを補填する必要があります。これはアルゴリズムや符号化とは無関係な実装設計の選択肢です。

バージョン

0: オリジナルバージョン 1: LZO-RLE

LZOバージョン1はゼロの連続をランレングス符号化で符号化する拡張機能を実装しています。これはzramでよく見られるゼロが多いデータの処理速度を向上させます。これは後方互換性を保ちながらビットストリームを変更します（v1はv0で圧縮されたデータを正しく復号化できますが、v0はv1のデータを読み込めません）。

最大の互換性を確保するため、両方のバージョンは異なる名前（lzoとlzo-rle）で利用可能です。このドキュメントでは、符号化の違いはバージョン1のみなど、例を挙げて記載しています。

バイトシーケンス¶

最初のバイトの符号化:

0..16   : follow regular instruction encoding, see below. It is worth
          noting that code 16 will represent a block copy from the
          dictionary which is empty, and that it will always be
          invalid at this place.

17      : bitstream version. If the first byte is 17, and compressed
          stream length is at least 5 bytes (length of shortest possible
          versioned bitstream), the next byte gives the bitstream version
          (version 1 only).
          Otherwise, the bitstream version is 0.

18..21  : copy 0..3 literals
          state = (byte - 17) = 0..3  [ copy <state> literals ]
          skip byte

22..255 : copy literal string
          length = (byte - 17) = 4..238
          state = 4 [ don't copy extra literals ]
          skip byte

インストラクションの符号化:

0 0 0 0 X X X X  (0..15)
  Depends on the number of literals copied by the last instruction.
  If last instruction did not copy any literal (state == 0), this
  encoding will be a copy of 4 or more literal, and must be interpreted
  like this :

     0 0 0 0 L L L L  (0..15)  : copy long literal string
     length = 3 + (L ?: 15 + (zero_bytes * 255) + non_zero_byte)
     state = 4  (no extra literals are copied)

  If last instruction used to copy between 1 to 3 literals (encoded in
  the instruction's opcode or distance), the instruction is a copy of a
  2-byte block from the dictionary within a 1kB distance. It is worth
  noting that this instruction provides little savings since it uses 2
  bytes to encode a copy of 2 other bytes but it encodes the number of
  following literals for free. It must be interpreted like this :

     0 0 0 0 D D S S  (0..15)  : copy 2 bytes from <= 1kB distance
     length = 2
     state = S (copy S literals after this block)
   Always followed by exactly one byte : H H H H H H H H
     distance = (H << 2) + D + 1

  If last instruction used to copy 4 or more literals (as detected by
  state == 4), the instruction becomes a copy of a 3-byte block from the
  dictionary from a 2..3kB distance, and must be interpreted like this :

     0 0 0 0 D D S S  (0..15)  : copy 3 bytes from 2..3 kB distance
     length = 3
     state = S (copy S literals after this block)
   Always followed by exactly one byte : H H H H H H H H
     distance = (H << 2) + D + 2049

0 0 0 1 H L L L  (16..31)
     Copy of a block within 16..48kB distance (preferably less than 10B)
     length = 2 + (L ?: 7 + (zero_bytes * 255) + non_zero_byte)
  Always followed by exactly one LE16 :  D D D D D D D D : D D D D D D S S
     distance = 16384 + (H << 14) + D
     state = S (copy S literals after this block)
     End of stream is reached if distance == 16384
     In version 1 only, to prevent ambiguity with the RLE case when
     ((distance & 0x803f) == 0x803f) && (261 <= length <= 264), the
     compressor must not emit block copies where distance and length
     meet these conditions.

  In version 1 only, this instruction is also used to encode a run of
     zeros if distance = 0xbfff, i.e. H = 1 and the D bits are all 1.
     In this case, it is followed by a fourth byte, X.
     run length = ((X << 3) | (0 0 0 0 0 L L L)) + 4

0 0 1 L L L L L  (32..63)
     Copy of small block within 16kB distance (preferably less than 34B)
     length = 2 + (L ?: 31 + (zero_bytes * 255) + non_zero_byte)
  Always followed by exactly one LE16 :  D D D D D D D D : D D D D D D S S
     distance = D + 1
     state = S (copy S literals after this block)

0 1 L D D D S S  (64..127)
     Copy 3-4 bytes from block within 2kB distance
     state = S (copy S literals after this block)
     length = 3 + L
   Always followed by exactly one byte : H H H H H H H H
     distance = (H << 3) + D + 1

1 L L D D D S S  (128..255)
     Copy 5-8 bytes from block within 2kB distance
     state = S (copy S literals after this block)
     length = 5 + L
   Always followed by exactly one byte : H H H H H H H H
     distance = (H << 3) + D + 1

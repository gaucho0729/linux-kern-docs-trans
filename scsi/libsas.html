SASレイヤー¶

SASレイヤーはSAS LLDD（SAS Layer Device Driver）を管理するインフラストラクチャです。SCSIコアとSAS LLDDの間に位置し、レイアウトは以下の通りです：SCSIコアはSAM/SPCに関する問題を扱い、SAS LLDD＋シーケンサーはPHY/OOB/リンク管理を担当しますが、SASレイヤーは以下のことに責任を持ちます：

  • SAS_PHY/Port/HAイベント管理（LLDDが生成し、SASレイヤーが処理）、

  • SASポート管理（作成/破壊）、

  • SASドメインの発見と再検証、

  • SASドメインデバイス管理、

  • SCSIホストの登録/解除、

  • SCSIコア（SAS）またはlibata（SATA）へのデバイス登録、および

  • エクスパNDER管理とエクスパNDER制御のユーザー空間へのエクスポート。

SAS LLDDはPCIデバイスドライバーです。PHY/OOB管理とベンダー固有のタスクを担当し、イベントをSASレイヤーに生成します。

SASレイヤーはSAS 1.1仕様に記載されているほとんどのSASタスクを担当します。

sas_ha_structはSAS LLDDをSASレイヤーに説明する構造体です。ほとんどのフィールドはSASレイヤーで使用されますが、一部のフィールドはLLDDで初期化する必要があります。

ハードウェアを初期化した後、probe()関数からsas_register_ha()を呼び出します。これにより、LLDDがSCSIサブシステムに登録され、SCSIホストが作成され、SASドライバーがsysfsで作成されるSASツリーに登録されます。その後、関数は戻ります。次に、PHYを有効化してOOBを実際に開始し（この時点でドライバーがnotify_*イベントコールバックを呼び出すようになります）。

構造体の説明¶

struct sas_phy¶

通常、ドライバーのPHY構造体に静的に埋め込まれています：

struct my_phy {
        blah;
        struct sas_phy sas_phy;
        bleh;
};

そして、すべてのPHYは、以下のHA構造体にmy_phyの配列として含まれます。

PHYを初期化するにつれて、sas_phy構造体も自分のPHY構造体とともに初期化します。

一般的に、PHYはLLDDによって管理され、ポートはSASレイヤーによって管理されます。したがって、PHYはLLDDによって初期化・更新され、ポートはSASレイヤーによって初期化・更新されます。

LLDDが特定のフィールドを読み書きでき、SASレイヤーがそれらを読み込むだけできるというスキーマがあります。これは不要なロックを避けるための設計です。

enabled

  • 設定が必要（0/1）

id

  • 設定が必要 [0,MAX_PHYS)]

class, proto, type, role, oob_mode, linkrate

  • 設定が必要

oob_mode

  • OOBが完了したときにこの値を設定し、SASレイヤーに通知します。

sas_addr

  • これは通常、PHYのsasアドレスを保持する配列へのポインタで、my_phy構造体のどこかに存在します。

attached_sas_addr

  • LLDDがIDENTIFYフレームまたはFISフレームを受信した際に設定します。SASレイヤーに通知する前に設定する必要があります。この設定の目的は、LLDDが特定のphy/portで異なるSASアドレスを偽造または提供したい場合に、これを実現するためです。最善の方法は、IDENTIFYフレームまたはSATA直結デバイスに対して直接SASアドレスを生成することです。後続のDiscoverプロセスでこの設定が変更される可能性があります。

frame_rcvd

  • 受信したIDENTIFY/FISフレームをコピーする場所です。ロックを取得し、フレームをコピーしてframe_rcvd_sizeを設定し、ロックを解放した後、イベントを呼び出します。ハードウェアフレームサイズを正確に把握できないため、ポインタとして定義しています。phy構造体で実際の配列を定義し、このポインタがそれを指すようにします。DMA可能なメモリからフレームをコピーする際はロックを保持しながら行います。

sas_prim

  • 受信したプリミティブはここに格納されます。sas.hを参照してください。ロックを取得し、プリミティブを設定してロックを解放し、通知します。

port

  • phyが属するsas_portへのポインタです。LLDDはこのフィールドを読み込むだけです。このphyが属するsas_portを指します。SASレイヤーが設定します。

ha

  • 設定可能です。SASレイヤーが必ず設定します。

lldd_phy

  • このフィールドを自身のphyにポインタを設定してください。SASレイヤーがコールバックを呼び出し、phyを渡す際に自身の位置を素早く特定できるようにします。sas_phyが埋め込まれている場合でもcontainer_ofマクロを使用できます。どちらか好きな方で構いません。

struct sas_port¶

LLDDはこの構造体のどのフィールドも設定しません。読み取り専用です。説明は自明です。

phy_maskは32ビットです。現時点ではこれで十分です。HAが8以上のphyを持つことは聞いたことがありません。

lldd_port

  • このフィールドの使用例は見つけていません。他のLLDDが内部のポート表現を必要とする場合に利用できるかもしれません。

struct sas_ha_struct¶

通常、自身のLLDD構造体でアダプターを記述する際に静的に宣言されています:

struct my_sas_ha {
    blah;
    struct sas_ha_struct sas_ha;
    struct my_phy phys[MAX_PHYS];
    struct sas_port sas_ports[MAX_PHYS]; /* (1) */
    bleh;
};

(1) If your LLDD doesn't have its own port representation.

初期化が必要な項目（下記にサンプル関数を示します）。

pcidev¶

sas_addr

  • SASレイヤーがメモリ割当などの処理をやりたくないため、このフィールドは静的に割り当てられた配列（例：ホストアダプター構造体内のどこか）へのポインタです。ホストアダプターのSASアドレスは、ユーザーまたはメーカーが指定したものなどを保持します。

sas_port¶

sas_phy

  • 構造体へのポインタの配列です。（上記のsas_addrに関する注意を参照）。これらは必ず設定する必要があります。以下の注意を参照してください。

num_phys

  • sas_phy配列内のphysの数、およびsas_port配列内のportsの数です。最大num_physポート（各ポート1つずつ）があるため、num_portsは使用せずnum_physのみを使用します。

イベントインターフェース:

/* LLDD calls these to notify the class of an event. */
void sas_notify_port_event(struct sas_phy *, enum port_event);
void sas_notify_phy_event(struct sas_phy *, enum phy_event);
void sas_notify_port_event_gfp(struct sas_phy *, enum port_event, gfp_t);
void sas_notify_phy_event_gfp(struct sas_phy *, enum phy_event, gfp_t);

ポート通知:

/* The class calls these to notify the LLDD of an event. */
void (*lldd_port_formed)(struct sas_phy *);
void (*lldd_port_deformed)(struct sas_phy *);

LLDDがポートが形成または変形されたときに通知を受けたい場合、それらをタイプに合致する関数に設定します。

SAS LLDDは、SAMで記述されているタスク管理関数（TMFs）の少なくとも1つを実装する必要があります。

/* Task Management Functions. Must be called from process context. */
int (*lldd_abort_task)(struct sas_task *);
int (*lldd_abort_task_set)(struct domain_device *, u8 *lun);
int (*lldd_clear_aca)(struct domain_device *, u8 *lun);
int (*lldd_clear_task_set)(struct domain_device *, u8 *lun);
int (*lldd_I_T_nexus_reset)(struct domain_device *);
int (*lldd_lu_reset)(struct domain_device *, u8 *lun);
int (*lldd_query_task)(struct sas_task *);

詳細については、T10.orgからSAMを参照してください。

ポートとアダプタの管理:

/* Port and Adapter management */
int (*lldd_clear_nexus_port)(struct sas_port *);
int (*lldd_clear_nexus_ha)(struct sas_ha_struct *);

SAS LLDDは、それらの少なくとも1つを実装する必要があります。

PHY管理:

/* Phy management */
int (*lldd_control_phy)(struct sas_phy *, enum phy_func);
lldd_ha

  • これをあなたのHA構造体を指すように設定します。上記のように埋め込まれている場合は、container_ofを使用することもできます。

初期化および登録関数の例は次のようになります（probe()から最後に呼ばれる） ただし physをOOBを行うために有効にする前に:

static int register_sas_ha(struct my_sas_ha *my_ha)
{
        int i;
        static struct sas_phy   *sas_phys[MAX_PHYS];
        static struct sas_port  *sas_ports[MAX_PHYS];

        my_ha->sas_ha.sas_addr = &my_ha->sas_addr[0];

        for (i = 0; i < MAX_PHYS; i++) {
                sas_phys[i] = &my_ha->phys[i].sas_phy;
                sas_ports[i] = &my_ha->sas_ports[i];
        }

        my_ha->sas_ha.sas_phy  = sas_phys;
        my_ha->sas_ha.sas_port = sas_ports;
        my_ha->sas_ha.num_phys = MAX_PHYS;

        my_ha->sas_ha.lldd_port_formed = my_port_formed;

        my_ha->sas_ha.lldd_dev_found = my_dev_found;
        my_ha->sas_ha.lldd_dev_gone = my_dev_gone;

        my_ha->sas_ha.lldd_execute_task = my_execute_task;

        my_ha->sas_ha.lldd_abort_task     = my_abort_task;
        my_ha->sas_ha.lldd_abort_task_set = my_abort_task_set;
        my_ha->sas_ha.lldd_clear_aca      = my_clear_aca;
        my_ha->sas_ha.lldd_clear_task_set = my_clear_task_set;
        my_ha->sas_ha.lldd_I_T_nexus_reset= NULL; (2)
        my_ha->sas_ha.lldd_lu_reset       = my_lu_reset;
        my_ha->sas_ha.lldd_query_task     = my_query_task;

        my_ha->sas_ha.lldd_clear_nexus_port = my_clear_nexus_port;
        my_ha->sas_ha.lldd_clear_nexus_ha = my_clear_nexus_ha;

        my_ha->sas_ha.lldd_control_phy = my_control_phy;

        return sas_register_ha(&my_ha->sas_ha);

イベント¶

イベントは 唯一の方法 SAS LLDDがSASレイヤーに何が起きたかを通知する方法です。LLDDがSASレイヤーに内部またはSASドメインで起きたことについて通知する他の方法はありません。

PHYイベント:

PHYE_LOSS_OF_SIGNAL, (C)
PHYE_OOB_DONE,
PHYE_OOB_ERROR,      (C)
PHYE_SPINUP_HOLD.

ポートイベント、_phy_を介して伝達されます:

PORTE_BYTES_DMAED,      (M)
PORTE_BROADCAST_RCVD,   (E)
PORTE_LINK_RESET_ERR,   (C)
PORTE_TIMER_EVENT,      (C)
PORTE_HARD_RESET.
ホストアダプタイベント:

HAE_RESET

SAS LLDDは生成する必要があります

  • グループC（選択肢）からの少なくとも1つのイベント、

  • マーキングされたM（必須）イベントは必須です（1つのみ）

  • E（拡張子）イベントをマーキングし、SASレイヤーがドメイン再検証を処理するようにしたい場合（1つのみ）。

  • 未マーキングのイベントはオプションです。

意味:

HAE_RESET

  • あなたのHAが内部エラーが発生し、リセットされたとき。

PORTE_BYTES_DMAED

  • IDENTIFY/FISフレームを受信するとき

PORTE_BROADCAST_RCVD

  • primitiveを受信するとき

PORTE_LINK_RESET_ERR

  • タイマーエクスプロイア、信号の喪失、DWSの喪失など 1

PORTE_TIMER_EVENT

  • DWSリセットタイムアウトタイマーエクスプロイア 1

PORTE_HARD_RESET

  • Hard Reset primitiveを受信しました。

PHYE_LOSS_OF_SIGNAL

  • デバイスがなくなった 1

PHYE_OOB_DONE

  • OOBは正常に完了し、oob_modeが有効です

PHYE_OOB_ERROR

  • OOB処理中にエラーが発生し、デバイスがおそらく切断されました。 1

PHYE_SPINUP_HOLD

  • SATAが接続されており、COMWAKEが送信されていません。

1(1,2,3,4)

phyの適切なフィールドを設定またはクリアする必要があります。または、タスクレットから呼び出すことのできるinlined sas_phy_disconnected()関数を使用することもできます。

Execute Command SCSI RPC:

int (*lldd_execute_task)(struct sas_task *, gfp_t gfp_flags);

SAS LLDDにタスクをキューイングするためのものです。@taskは実行するタスクで、@gfp_maskは呼び出し元のコンテキストを定義するgfp_maskです。

この関数はExecute Command SCSI RPCを実装する必要があります。

つまり、lldd_execute_task()が呼ばれた場合、コマンドがトランスポート経由で送信されます。 即時。存在します no SAS LLDD内の任意のレベルで、任意の種類のキューイングが存在します。

戻り値:

  • -SAS_QUEUE_FULL、-ENOMEM、何もキューイングされませんでした；

  • 0、タスク（複数可）がキューイングされました。

Discovery¶

sysfsツリーは以下の目的を持っています：

  1. 現在のSASドメインの物理的なレイアウトを表示します。つまり、現在の物理世界でのドメインの状態を示します。

  2. 発見時のデバイスパラメータを表示します。

これはtree(1)プログラムへのリンクで、SASドメインを表示するのに非常に役立ちます： ftp://mama.indstate.edu/linux/tree/

ユーザー空間アプリケーションが実際にこのグラフィカルなインターフェースを作成することを期待しています。

つまり、READY LED MEANING設定の意味を変更した場合など、sysfsドメインツリーは状態を表示または保持しませんが、ドメインデバイスの現在の接続状態は表示します。

内部デバイス状態の変更の保持は上位レイヤー（コマンドセットドライバー）とユーザー空間の責任です。

デバイスがドメインから外されると、sysfsツリーに即座に反映され、デバイスがシステムから削除されます。

domain_device構造体はSASドメイン内のすべてのデバイスを記述します。これはSASレイヤーによって完全に管理されます。タスクはdomain_deviceにポイントし、SAS LLDDがタスクを送信する先を知る仕組みです。SAS LLDDはdomain_device構造体の内容を読み込むだけで、作成または破壊しません。

ユーザー空間からのExpander管理¶

sysfs内の各Expanderディレクトリには、「smp_portal」というファイルがあります。これはバイナリのsysfs属性ファイルで、SMPポート（注：これは 禁止です SMPポートで、ユーザー空間アプリケーションがSMPリクエストを送信し、SMPレスポンスを受信できます。

機能は見かけより単純です：

  1. 送信したいSMPフレームを構築してください。形式とレイアウトはSAS仕様に記載されています。CRCフィールドは0に設定してください。

open(2)

  1. ExpanderのSMPポートsysfsファイルを開き、RWモードで読み書きします。

write(2)

  1. 1で構築したフレームを書き込みます。

read(2)

  1. 構築したフレームに予期されるデータ量を確認してください。予期していたデータ量と異なる量を受信した場合、エラーが発生しています。

close(2)

このプロセスの詳細は、ファイル「expander_conf.c」内の関数 do_smp_func() およびその呼び出し元で確認できます。

カーネル機能はファイル「sas_expander.c」で実装されています。

「expander_conf.c」プログラムはこれを実装しています。1つの引数として、拡張子へのSMPポータルのsysfsファイル名を指定し、ルーティングテーブルを含む拡張子に関する情報を提供します。

SMPポータルは拡張子の完全な制御を提供するため、注意が必要です。

SCSI EH¶

このドキュメントはSCSIミドルレイヤーエラーハンドリングインフラストラクチャについて説明しています。詳しくは以下をご参照ください SCSI mid_level - lower_level ドライバインターフェース SCSIミドルレイヤーについての詳細情報については以下をご参照ください。

1. SCSIコマンドがミドルレイヤーを介してEHに到達する仕組み¶

1.1 struct scsi_cmnd¶

各SCSIコマンドはstruct scsi_cmnd (== scmd)で表されます。scmdは2つのlist_headを用いてリストにリンクされます。これらはscmd->listとscmd->eh_entryです。前者はフリーリストやデバイスごとのscmdリストに使用され、このEHの議論にはあまり関係ありません。後者は完了処理とEHリストに使用され、この議論では通常scmd->eh_entryを用いてscmdがリンクされています。

1.2 scmdが完了する仕組み¶

LLDDがscmdを取得した後、LLDDがmidlayerから渡されたscsi_doneコールバックを呼び出してコマンドを完了させるか、ブロックレイヤーがタイムアウトでコマンドを完了させます。

1.2.1 scsi_doneを用いたscmdの完了¶

すべての非EHコマンドではscsi_done()が完了コールバックになります。これはblk_complete_request()を呼び出してブロックレイヤーのタイマーやSCSI_SOFTIRQを生成します。

SCSI_SOFTIRQハンドラscsi_softirqはscsi_decide_disposition()を呼び出してコマンドの処理を決定します。scsi_decide_disposition()はscmd->result値やセンスデータを確認してコマンドの処理を決定します。

  • SUCCESS

    scsi_finish_command()がコマンドに呼び出されます。この関数はメンテナンス処理を行い、scsi_io_completion()を呼び出してI/Oを終了します。scsi_io_completion()はblk_end_requestや関連する関数を呼び出してブロックレイヤーに完了通知を行い、エラー時の残りデータの処理を判断します。

  • NEEDS_RETRY

  • ADD_TO_MLQUEUE

    scmdはblkキューに再キューイングされます。

  • それ以外の場合

    scsi_eh_scmd_add(scmd)がコマンドに呼び出されます。この関数の詳細については[1-3]をご参照ください。

1.2.2 タイムアウトによるscmdの完了¶

タイムアウトハンドラはscsi_times_out()です。タイムアウトが発生した場合、この関数は

  1. オプションのhostt->eh_timed_out()コールバックを呼び出します。戻り値は次のいずれかです

    • BLK_EH_RESET_TIMER

      コマンドの完了にさらに時間がかかることを示します。タイマが再起動されます。このアクションはリトライとしてカウントされ、scmd->allowed + 1(!)回まで許可されます。制限に達した場合はBLK_EH_DONEのアクションが実行されます。

    • BLK_EH_DONE

      eh_timed_out()コールバックがコマンドを処理できなかったため、ステップ#2が実行されます。

  2. scsi_abort_command()は非同期アービットをスケジュールするために呼び出されます。SCSI_EH_ABORT_SCHEDULEDフラグが設定されているコマンド（このフラグはコマンドがすでに一度アービットされ、これは失敗した再試行を示す）や、EH期限が切れた場合、非同期アービットは呼び出されません。このような場合、ステップ#3が実行されます。

  3. scsi_eh_scmd_add(scmd, SCSI_EH_CANCEL_CMD)がコマンドに対して呼び出されます。詳細については[1-4]を参照してください。

1.3 非同期コマンドアービット¶

タイムアウトが発生した後、scsi_abort_command()からコマンドアービットがスケジュールされます。アービットが成功した場合、コマンドは再試行（再試行回数が尽きた場合はない）が行われるか、DID_TIME_OUTで終了します。

それ以外の場合、scsi_eh_scmd_add()がコマンドに対して呼び出されます。詳細については[1-4]を参照してください。

1.4 EHが制御を取る仕組み¶

scmdはscsi_eh_scmd_add()を通じてEHに入るため、以下の処理を行います。

  1. scmd->eh_entryをshost->eh_cmd_qにリンクします

  2. shost->shost_stateのSHOST_RECOVERYビットを設定します

  3. shost->host_failedをインクリメントします

  4. shost->host_busy == shost->host_failedのときにSCSI EHスレッドを起動します

上記のように、scmdがshost->eh_cmd_qに追加されるとSHOST_RECOVERYビットが有効になります。これにより、blkキューからホストへの新たなscmdの送信が防がれます。最終的に、ホスト上のすべてのscmdは正常に完了するか、失敗してeh_cmd_qに追加されるか、タイムアウトしてeh_cmd_qに追加されます。

すべてのscmdが完了または失敗した場合、進行中のscmd数は失敗したscmd数と等しくなります（shost->host_busy == shost->host_failed）。これによりSCSI EHスレッドが起動します。起動後、SCSI EHスレッドはすべての進行中のコマンドが失敗し、shost->eh_cmd_qにリンクされていると期待できます。

ただし、下層が静止していることを意味するわけではありません。LLDDがエラー状態でscmdを完了した場合、LLDDおよび下層はそのscmdを忘れると仮定されます。しかし、scmdがタイムアウトした場合、hostt->eh_timed_out()が下層を忘れさせない限り（現在のLLDDではこの処理は行われていません）、下層にとってはコマンドがまだアクティブであり、いつでも完了する可能性があります。もちろん、タイマーがすでに切れているため、すべての完了は無視されます。

後述するように、SCSI EHがタイムアウトしたscmdに対してLLDDにアービットを実行し、LLDDがそのscmdを忘れさせる仕組みについて説明します。

2. SCSI EHの動作方法¶

LLDDはSCSI EHのアクションを以下の2つの方法のいずれかで実装できます。

  • 細かいEHコールバック

    LLDDは細かいレベルのEHコールバックを実装し、SCSI midlayerがエラー処理を駆動し、適切なコールバックを呼び出すことができます。これは[2-1]でさらに説明します。

  • eh_strategy_handler()コールバック

    これは全体のエラー処理を行う1つの大きなコールバックです。そのため、SCSI midlayerが回復時に実行するすべての処理を行う必要があります。これは[2-2]で詳しく説明します。

回復が完了した後、SCSI EHはscsi_restart_operations()を呼び出して通常の操作を再開します。これは

  1. ドアロックが必要かどうかを確認し、ドアをロックします。

  2. SHOST_RECOVERY shost_stateビットをクリアします

  3. shost->host_waitの待機中のプロセスを起こします。これは誰かが scsi_block_when_processing_errors() ホスト上で呼び出した場合に発生します。(なぜ必要なのでしょうか？すべての操作はblk queueに到達した後でもブロックされます。 Kicks queues in all devices on the host in the asses

  4. 2.1 細かいレベルのコールバックを通じたEH

2.1.1 概要¶

eh_strategy_handler()が存在しない場合、SCSI midlayerがエラー処理を担当します。EHの目標は2つで、LLDD、ホスト、デバイスがタイムアウトしたscmdを忘れ、新しいコマンドを受け入れる準備を整えることです。scmdが回復されたとは、下位レイヤーがscmdを忘れ、下位レイヤーが再び処理または失敗させる準備ができている状態を指します。¶

これらの目標を達成するため、EHは段階的に重みの高い回復アクションを実行します。一部のアクションはSCSIコマンドを送信して実行され、他のアクションは以下の細かいレベルのhostt EHコールバックのいずれかを呼び出して実行されます。コールバックは省略可能で、省略されたコールバックは常に失敗とみなされます。

下位の重みのアクションで一部の失敗したscmdを回復できない場合にのみ、より重みの高いアクションが実行されます。また、最も重みの高いアクションの失敗はEHの失敗を意味し、すべての未回復デバイスがオフラインになります。

int (* eh_abort_handler)(struct scsi_cmnd *);
int (* eh_device_reset_handler)(struct scsi_cmnd *);
int (* eh_bus_reset_handler)(struct scsi_cmnd *);
int (* eh_host_reset_handler)(struct scsi_cmnd *);

回復中に以下のルールが適用されます

回復アクションは、to doリストにある失敗したscmdに対してeh_work_qで実行されます。scmdの回復アクションが成功した場合、回復されたscmdはeh_work_qから削除されます。

  • 注意：scmdに対する単一の回復アクションで複数のscmdが回復されることがあります。例えば、デバイスのリセットはデバイス上のすべての失敗したscmdを回復します。

    より重みの高いアクションは、下位の重みのアクションが完了した後、eh_work_qが空でない場合にのみ実行されます。

  • EHは失敗したscmdを再利用して回復用のコマンドを送信します。タイムアウトしたscmdについては、SCSI EHはLLDDがscmdを忘れることを確認した後にEHコマンドで再利用します。

  • scmdが回復された場合、eh_work_qからEHローカルのeh_done_qに移動します。

。すべてのscmdが回復された後（eh_work_qが空になった後） scsi_eh_finish_cmd()Note that single recovery action on a scmd can recover multiple scmds. e.g. resetting a device recovers all failed scmds on the device. scsi_eh_flush_done_q() 再試行またはエラー終了（上層に失敗を通知）を行うため、復元されたscmdsに呼び出されます。

scmdsは、そのsdevがまだオンライン状態（EH中にオフラインになっていない）であり、REQ_FAILFASTが設定されていない場合、かつ++scmd->retriesがscmd->allowed未満の場合にのみ再試行されます。

2.1.2 EHを通じたscmdsのフロー¶

  1. エラー完了 / 時間切れ

    ACTION

    scsi_eh_scmd_add()がscmdに呼び出されます

    • scmdをshost->eh_cmd_qに追加します

    • SHOST_RECOVERYを設定します

    • shost->host_failed++

    ロック処理

    shost->host_lock

  2. EHが開始されます

    ACTION

    すべてのscmdsをEHのローカルeh_work_qに移動し、shost->eh_cmd_qはクリアされます

    ロック処理

    shost->host_lock（厳密には必要ではありませんが、一貫性のため）

  3. scmdが復元されました

    ACTION

    scsi_eh_finish_cmd() EH終了処理を行うためscmdに呼び出されます

    • scsi_setup_cmd_retry()

    • ローカルeh_work_qからローカルeh_done_qに移動します

    ロック処理

    none

    並行処理

    それぞれのeh_work_qに対して1つのスレッドのみを許可し、キュー操作をロックレスにします

  4. EHが完了します

    ACTION

    scsi_eh_flush_done_q() scmdsを再試行するか、上層に失敗を通知します。並行処理される可能性がありますが、それぞれのeh_work_qに対して1つのスレッドのみを許可し、キュー操作をロックレスにします

    • scmdがeh_done_qから削除され、scmd->eh_entryがクリアされます

    • 再試行が必要な場合、scsi_queue_insert()を使用して再キューされます

    • それ以外の場合、scsi_finish_command()がscmdに呼び出されます

    • shost->host_failedをゼロにします

    ロック処理

    キューまたは完了関数が適切なロック処理を行います

2.1.3 コントロールフロー¶

EHは細かいコールバックを通じてscsi_unjam_host()から開始されます

scsi_unjam_host

  1. shost->host_lockをロックし、shost->eh_cmd_qをローカルeh_work_qにスパインインイニシャライズし、host_lockをアンロックします。注意: この操作によりshost->eh_cmd_qはクリアされます

  2. scsi_eh_get_sense()を呼び出します

scsi_eh_get_sense

このアクションは、エラー完了（!SCSI_EH_CANCEL_CMD）かつ有効なセンスデータを持たないコマンドに対して行われます。ほとんどのSCSIトランスポート/LLDDはコマンド失敗時に自動的にセンスデータを取得します（自動センス）。パフォーマンスの観点から自動センスが推奨され、センス情報がCHECK CONDITIONの発生とこのアクションの間に同期を取らなくなる可能性があります。

自動センスがサポートされていない場合、scmd->sense_bufferには無効なセンスデータが含まれます。このような場合、scsi_decide_disposition()は常にFAILEDを返し、SCSI EHを呼び出します。scmdがここに到達した場合、センスデータが取得され、scsi_decide_disposition()が再度呼び出されます。

  1. scsi_request_sense()を呼び出し、REQUEST_SENSEコマンドを実行します。失敗した場合は何も処理しません。注意: 処理を行わないことで、scmdに対してより重い復旧処理が行われます。

  2. scmdに対してscsi_decide_disposition()を呼び出します

    • SUCCESS

      scmd->retriesがscmd->allowedに設定され、 scsi_eh_flush_done_q() scmdの再試行を防ぎ、 scsi_eh_finish_cmd() が呼び出された後です。

    • NEEDS_RETRY

      scsi_eh_finish_cmd() 呼び出される

    • それ以外の場合

      処理を行いません。

  1. もし!list_empty(&eh_work_q)であれば、scsi_eh_abort_cmds()を呼び出します。

scsi_eh_abort_cmds

no_async_abortがホストテンプレートで有効になっている場合、タイムアウトしたコマンドごとにこのアクションが実行されます。各scmdに対してhostt->eh_abort_handler()が呼び出され、LLDDおよび関連するハードウェアがscmdを忘れることに成功した場合にSUCCESSが返されます。

タイムアウトしたscmdが正常に中止され、sdevがオフラインまたは準備完了状態の場合、 scsi_eh_finish_cmd() scmdに対してこの関数が呼び出されます。それ以外の場合、scmdはeh_work_qに残され、より重いエラー処理が行われます。

オフラインおよび準備完了の状態は、sdevが新しいscmdを処理できる状態を意味します。処理は即時失敗を含むため、sdevがこれらのいずれかの状態にある場合、さらなる回復処理は必要ありません。

デバイスの準備状態はscsi_eh_tur()によってテストされ、TEST_UNIT_READYコマンドが送信されます。注意点として、scmdは成功した中止後にTEST_UNIT_READY用に再利用される必要があります。

  1. list_empty(&eh_work_q)がfalseの場合、invoke scsi_eh_ready_devs()

scsi_eh_ready_devs

この関数は、失敗したsdevが新しいコマンドを受け入れるようになるために、4段階のエラー回復処理を行います。

  1. scsi_eh_stu()を呼び出します

scsi_eh_stu

失敗したscmdに有効なセンスデータを持つsdevごとに、 scsi_check_sense()判定がFAILEDの場合、START_STOP_UNITコマンドをstart=1で送信します。注意点として、明示的にエラー完了したscmdを選択しているため、下層がscmdを忘れていることが分かっており、STU用に再利用可能です。

STUが成功し、sdevがオフラインまたは準備完了状態の場合、sdev上のすべての失敗したscmdがEH完了状態になります。 scsi_eh_finish_cmd().

注意 hostt->eh_abort_handler()が実装されていないか失敗した場合、この時点でタイムアウトしたscmdがまだ存在し、STUは下層がscmdを忘れることを保証しません。しかし、STUが成功した場合、下層が不整合な状態になる可能性があるため、この関数はsdev上のすべてのscmdをEH完了状態にします。STUのアクションは、sdevにタイムアウトしたscmdが存在しない場合にのみ実行すべきです。

  1. list_empty(&eh_work_q)がfalseの場合、scsi_eh_bus_device_reset()を呼び出します。

scsi_eh_bus_device_reset

このアクションはscsi_eh_stu()と非常に似ていますが、STUではなくhostt->eh_device_reset_handler()が使用されます。また、SCSIコマンドを送信せず、リセットによりsdev上のすべてのscmdがクリアされるため、エラー完了したscmdを選択する必要はありません。

  1. list_empty(&eh_work_q)がfalseの場合、scsi_eh_bus_reset()を呼び出します

scsi_eh_bus_reset

各チャネルの失敗したscmdを持つsdevに対してhostt->eh_bus_reset_handler()が呼び出されます。バスリセットが成功した場合、チャネル上のすべての準備完了またはオフライン状態のsdevの失敗したscmdがEH完了状態になります。

  1. list_empty(&eh_work_q)がfalseの場合、scsi_eh_host_reset()を呼び出します

scsi_eh_host_reset

これは最終手段です。hostt->eh_host_reset_handler()が呼び出されます。ホストリセットが成功した場合、ホスト上のすべての準備完了またはオフラインのsdevsに失敗したscmdsはEH処理が完了します。

  1. もし!list_empty(&eh_work_q)であれば、scsi_eh_offline_sdevs()を呼び出します

scsi_eh_offline_sdevs

まだ未解決のscmdsを持つsdevsをすべてオフラインにし、scmdsをEH処理完了します。

  1. 呼び出す scsi_eh_flush_done_q().

    scsi_eh_flush_done_q

    この時点ですべてのscmdsは回復（または放棄）され、eh_done_qに配置されます。 scsi_eh_finish_cmd()。この関数は、scmdsの再試行または上位レイヤーへの失敗通知によってeh_done_qをフラッシュします。

2.2 トランスポートt->eh_strategy_handler()を通じたEH¶

scsi_unjam_host()の代わりにtransportt->eh_strategy_handler()が呼び出され、全体の回復プロセスを担当します。完了時には、下位レイヤーがすべての失敗したscmdsを忘れ、新しいコマンドの準備ができているか、またはオフラインになるようにする必要があります。また、SCSI midlayerの整合性を維持するためのSCSI EHの保守作業も行う必要があります。つまり、[2-1-2]で説明した手順のうち、#1を除くすべての手順をeh_strategy_handler()が実装する必要があります。

2.2.1 transportt->eh_strategy_handler()前のSCSI midlayerの条件¶

ハンドラへの入力時点で以下の条件が成立しています。

  • 各失敗したscmdのeh_flagsフィールドが適切に設定されています。

  • 各失敗したscmdはscmd->eh_entryを通じてscmd->eh_cmd_qにリンクされています。

  • SHOST_RECOVERYが設定されています。

  • shost->host_failed == shost->host_busy

2.2.2 transportt->eh_strategy_handler()後のSCSI midlayerの条件¶

ハンドラからの退出時点で以下の条件が成立しなければなりません。

  • shost->host_failedはゼロです。

  • 各scmdはscsi_setup_cmd_retry()を実行しても変化がありません。

  • shost->eh_cmd_qはクリアされています。

  • 各scmd->eh_entryはクリアされています。

  • 各scmdに対してscsi_queue_insert()またはscsi_finish_command()が呼び出されます。注意として、ハンドラはscmd->retriesおよび->allowedを用いて再試行回数を制限できます。

2.2.3 考慮すべき点¶

  • タイムアウトしたscmdsは下位レイヤーでまだアクティブな状態です。それらのscmdsに対して何かを行う前に、下位レイヤーがそれらを忘れることを確認してください。

  • 一貫性を保つため、shostデータ構造をアクセス・変更する際はshost->host_lockを取得してください。

  • 完了時に、各失敗したsdevはすべてのアクティブなscmdsを忘れなければなりません。

  • 完了時に、各失敗したsdevは新しいコマンドの準備ができているか、またはオフラインにならなければなりません。

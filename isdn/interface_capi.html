ハードウェアドライバへのカーネルCAPIインターフェース¶

1. 概要¶

CAPI 2.0仕様書には、ISDN機器に接続された基本速度インターフェース（BRI）およびプライマリ速度インターフェース（PRI）をアクセスするためのアプリケーションプログラミングインターフェース（API）標準であるCOMMON-ISDN-API（CAPI）が記載されています。

カーネルCAPIは、CAPIアプリケーションとCAPIハードウェアドライバの間でディスパッチングレイヤーとして機能します。ハードウェアドライバは、CAPIアプリケーションにサービスを提供できる状態になったことを示すために、ISDNデバイス（CAPI用語ではコントローラー）をカーネルCAPIに登録します。CAPIアプリケーションもカーネルCAPIに登録し、CAPIデバイスとの関連付けを要求します。カーネルCAPIは、アプリケーションの登録を利用可能なデバイスにディスパッチし、対応するハードウェアドライバに転送します。その後、カーネルCAPIはアプリケーションとハードウェアドライバ間でCAPIメッセージを双方向に転送します。

CAPIメッセージの形式とセマンティクスはCAPI 2.0標準で定義されています。この標準は、以下から無料で入手できます。 https://www.capi.org.

2. ドライバとデバイスの登録¶

CAPIドライバは、制御するISDNデバイスをカーネルCAPIに登録するため、struct capi_ctrへのポインタを渡してKernel CAPI関数attach_capi_ctr()を呼び出す必要があります。この構造体にはドライバおよびコントローラーの名前、およびカーネルCAPIがドライバと通信するために後で使用するコールバック関数ポインタを記入する必要があります。登録は、同じstruct capi_ctrへのポインタを渡してdetach_capi_ctr()関数を呼び出すことで取り消すことができます。

デバイスが実際に使用可能になる前に、ドライバはデバイスのcapi_ctr構造体内の「manu」、「version」、「profile」、「serial」フィールドを埋め込み、capi_ctr_ready()を呼び出して使用準備を示す必要があります。それ以降、カーネルCAピはデバイスの登録されたコールバック関数を呼び出すことができます。

デバイスが何らかの理由で利用不能になった場合（シャットダウン、切断など）、ドライバはcapi_ctr_down()を呼び出す必要があります。これにより、カーネルCAPIからのコールバック関数の呼び出しが停止されます。

3. アプリケーション登録と通信¶

カーネルCAPIは、アプリケーションからの登録リクエスト（CAPI_REGISTER操作の呼び出し）を適切なハードウェアドライバに転送するために、そのregister_appl()コールバック関数を呼び出します。カーネルCAPIは一意のアプリケーションID（ApplID, u16）を割り当て、このIDをregister_appl()にパラメータ構造体とともに渡します。これは通常のファイルやキャラクタデバイスのopen()操作に類似しています。

register_appl()が成功して戻った後、アプリケーションからCAPIメッセージがドライバに送信され、send_message()コールバック関数を介してデバイスのドライバに渡されることがあります。逆に、ドライバはKernel CAPIのcapi_ctr_handle_message()関数を呼び出して、受信したCAPIメッセージをKernel CAPIに渡し、アプリケーションに転送することができ、その際ApplIDを指定します。

アプリケーションからの登録解除リクエスト（CAPI操作CAPI_RELEASE）は、release_appl()コールバック関数として転送され、register_appl()と同じApplIDが渡されます。release_appl()から戻った後、そのアプリケーションとの間でCAPIメッセージのやり取りは行われません。

4. データ構造¶

4.1 struct capi_driver¶

この構造体はKernel CAPIドライバ自身を記述しており、register_capi_driver()およびunregister_capi_driver()関数で使用されます。以下の非プライベートフィールドを含み、ドライバがregister_capi_driver()を呼び出す前にすべて設定する必要があります。

char name[32]

ドライバの名前をゼロ終端のASCII文字列で表します

char revision[32]

ドライバのバージョン番号をゼロ終端のASCII文字列で表します

4.2 struct capi_ctr¶

この構造体はKernel CAPIドライバによって処理されるISDNデバイス（コントローラー）を記述します。attach_capi_ctr()関数を通じて登録されると、すべてのコントローラー固有の下位レイヤーインターフェースおよびコールバック関数に渡され、操作対象のコントローラーを特定します。

以下の非プライベートフィールドを含みます：

ドライバがattach_capi_ctr()を呼び出す前に設定する必要があります：¶

struct module *owner

デバイスを所有するドライバモジュールへのポインタ

void *driverdata

Kernel CAPIが操作しないドライバ固有データへの不透明ポインタ

char name[32]

コントローラーの名前をゼロ終端のASCII文字列で表します

char *driver_name

ドライバの名前をゼロ終端のASCII文字列で表します

int (*load_firmware)(struct capi_ctr *ctrlr, capiloaddata *ldata)

(オプション) デバイスにファームウェアおよび設定データを送信するためのコールバック関数へのポインタ

この関数は操作が完了する前に戻ることがあります。

完了を示すにはcapi_ctr_ready()を呼び出す必要があります。

戻り値：成功時は0、エラー時はエラーコード。プロセスコンテキストで呼び出されます。

void (*reset_ctr)(struct capi_ctr *ctrlr)

(オプション) デバイスの停止とすべての登録アプリケーションの解放を行うためのコールバック関数へのポインタ

この関数は操作が完了する前に戻ることがあります。

完了を示すにはcapi_ctr_down()を呼び出す必要があります。

プロセスコンテキストで呼び出されます。

void (*register_appl)(struct capi_ctr *ctrlr, u16 applid, capi_register_params *rparam)

デバイスへのアプリケーション登録のためのコールバック関数へのポインタ

Kernel CAPIがこれらの関数呼び出しをシリアル化するため、同時に複数の呼び出しは行われません。

void (*release_appl)(struct capi_ctr *ctrlr, u16 applid)

デバイスからのアプリケーション登録解除のためのコールバック関数へのポインタ

Kernel CAPIがこれらの関数呼び出しをシリアル化するため、同時に複数の呼び出しは行われません。

u16  (*send_message)(struct capi_ctr *ctrlr, struct sk_buff *skb)

デバイスにCAPIメッセージを送信するためのコールバック関数へのポインタ

戻り値：CAPIエラーコード

メソッドが0（CAPI_NOERROR）を返す場合、ドライバがskbの所有権を取得しており、呼び出し元はこれにアクセスできなくなります。非ゼロ（エラー）値を返す場合、skbの所有権は呼び出し元に戻り、再利用または解放することが可能です。

返却値は、メッセージの受け入れまたはキューイングに関する問題を信号として使用する必要があります。メッセージの実際の処理中に発生したエラーは、適切な応答メッセージで信号を送る必要があります。

プロセスコンテキストまたは割込みコンテキストで呼び出すことができます。

この関数への呼び出しは、カーネルCAPIによってシリアル化されません。つまり、再入可能である必要があります。

char *(*procinfo)(struct capi_ctr *ctrlr)

CAPIコントローラー情報テーブル（/proc/capi/controller）にデバイスのエントリを返すコールバック関数へのポインタ

注意:

send_message()以外のコールバック関数は、割込みコンテキストで呼び出されることはありません。

capi_ctr_ready()を呼び出す前に埋め込むべき値：¶

u8 manu[CAPI_MANUFACTURER_LEN]

CAPI_GET_MANUFACTURERに返す値

capi_version version

CAPI_GET_VERSIONに返す値

capi_profile profile

CAPI_GET_PROFILEに返す値

u8 serial[CAPI_SERIAL_LEN]

CAPI_GET_SERIALに返す値

4.3 SKBs¶

CAPIメッセージは、Kernel CAPIとドライバ間でsend_message()およびcapi_ctr_handle_message()を通じてやりとりされ、ソケットバッファ（skb）のデータ部分に格納されます。各skbにはCAPI 2.0標準に従って1つのCAPIメッセージが含まれます。

データ転送メッセージ（DATA_B3_REQおよびDATA_B3_IND）では、CAPIメッセージそのものの直後にペイロードデータが続き、同じskb内に含まれます。DataおよびData64パラメータは処理には使用されません。Data64パラメータは、CAPIメッセージの長さフィールドを30から22に設定することで省略可能です。

4.4 _cmsg構造体¶

（<linux/isdn/capiutil.h>で宣言されています）

_cmsg構造体は、CAPI 2.0メッセージの内容を簡単にアクセス可能な形式で保存します。これはCAPI 2.0のすべてのパラメータ、包括してAdditional InfoおよびBプロトコル構造化パラメータのサブパラメータを含みますが、以下の例外を除きます：

  • 2番目の着信者番号（CONNECT_IND）

  • Data64（DATA_B3_REQおよびDATA_B3_IND）

  • 送信完了（Additional Infoのサブパラメータ、CONNECT_REQおよびINFO_REQ）

  • グローバル設定（Bプロトコルのサブパラメータ、CONNECT_REQ、CONNECT_RESPおよびSELECT_B_PROTOCOL_REQ）

現在処理中のメッセージタイプに出現するパラメータのみが実際に使用されます。未使用のメンバはゼロに設定する必要があります。

メンバは、それらが表すCAPI 2.0パラメータの標準名に基づいています。正確なスペルは<linux/isdn/capiutil.h>を参照してください。メンバデータ型は：

u8

CAPIパラメータのタイプが'byte'の場合

u16

type ‘word’のCAPIパラメータ

u32

type ‘dword’のCAPIパラメータ

_cstruct

type ‘struct’のCAPIパラメータ。メンバはCAPIエンコーディングでパラメータを含むバッファへのポインタです（長さ＋コンテンツ）。NULLの場合、空（ゼロ長）のパラメータとみなされます。サブパラメータはコンテンツ部分内で符号化された形式で格納されます。

_cmstruct

type ‘struct’のCAPIパラメータの代替表現（'Additional Info'および'B Protocol'パラメータのみ使用）表現は、CAPI_DEFAULT: パラメータが空/存在しない。CAPI_COMPOSE: パラメータが存在。サブパラメータ値は対応する_cmsg構造体メンバ内で個別に格納されます。

7. デバッグ¶

モジュールkernelcapiは、デバッグ出力に影響を与えるモジュールパラメータshowcapimsgsを持っています。このパラメータはモジュールがロードされる際のみ設定可能で、modprobeコマンドのパラメータ「showcapimsgs=<n>」で設定します（コマンドラインまたは設定ファイルで）。

showcapimsgsの最下位ビットが設定されている場合、kernelcapiはコントローラーおよびアプリケーションのアップ/ダウンイベントをログ出力します。

さらに、すべての登録済みCAPIコントローラーには、そのコントローラーから送信・受信されるCAPIメッセージのログ出力を制御するtraceflagパラメータが関連付けられています。traceflagパラメータは、コントローラーが登録される際にはshowcapimsgsパラメータの値で初期化されますが、後でMANUFACTURER_REQコマンド（KCAPI_CMD_TRACE）を介して変更することが可能です。

traceflagの値がゼロ以外の場合、CAPIメッセージがログ出力されます。DATA_B3メッセージはtraceflagの値が2より大きい場合にのみログ出力されます。

traceflagの最下位ビットが設定されている場合、のみコマンド/サブコマンドとメッセージ長がログ出力されます。それ以外の場合、kernelcapiはメッセージ全体を読みやすい形式でログ出力します。

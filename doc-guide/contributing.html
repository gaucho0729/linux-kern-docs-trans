カーネルドキュメンテーションの改善に貢献する方法¶

ドキュメンテーションはソフトウェア開発プロジェクトにおいて重要な要素です。良いドキュメンテーションは新規開発者を引きつけるだけでなく、既存の開発者もより効率的に作業できるようにします。高品質なドキュメンテーションがなければ、コードの逆工学に多くの時間を費やすことになり、避けられるべきミスを犯す可能性があります。

残念ながら、カーネルのドキュメンテーションは、この規模と重要性を持つプロジェクトを支えるために必要なレベルに大きく満たしていません。

このガイドは、状況を改善したい貢献者向けのものです。カーネルドキュメンテーションの改善は、さまざまなスキルレベルを持つ開発者でも行える比較的簡単な方法であり、コミュニティで活躍する場を手に入れることにもつながります。以下の内容の大部分は、ドキュメンテーションマインテナーが優先的に取り組むべきタスク一覧です。

ドキュメンテーション TODO リスト¶

ドキュメンテーションを目標の位置に導くためには、無限に続くタスクが待っています。このリストには重要な項目がいくつか含まれていますが、完全ではありません。ドキュメンテーションの改善方法が思いついた場合は遠慮しないでください！

警告の修正¶

現在のドキュメンテーションビルドでは、信じられないほどの多くの警告が出力されます。その数が多いと、実質的に警告がまったくないのと同様です。人々は無視してしまうため、自分の作業で新たな警告を追加しても気づかないでしょう。そのため、警告の削除はドキュメンテーション TODO リストで最も優先度の高いタスクの一つです。タスク自体は比較的簡単ですが、正しい方法で取り組まなければ成功できません。

Cコードのコンパイラが発行する警告は、偽陽性であることがよくあり、コンパイラを黙らせるためのパッチに発展します。一方、ドキュメンテーションビルドからの警告は常に実際の問題を指しており、警告を解消するには問題を理解し、その根源を修正する必要があります。そのため、ドキュメンテーション警告を修正するパッチは、変更履歴のタイトルに「警告を修正」という表現を避け、実際に修正された問題を示すべきです。

重要な点は、ドキュメンテーションの警告がCコードのkerneldocコメントの問題によってしばしば生成されるということです。ドキュメンテーションのメンテナは、これらの警告に対する修正のコピーを感謝しますが、ドキュメンテーションツリーは実際にそれらの修正を担当する適切な場所ではありません。修正は、関連するサブシステムのメンテナに届けるべきです。

たとえば、ドキュメンテーションビルド中に私はほぼランダムに選んだ警告のペアを拾いました:

./drivers/devfreq/devfreq.c:1818: warning: bad line:
      - Resource-managed devfreq_register_notifier()
./drivers/devfreq/devfreq.c:1854: warning: bad line:
      - Resource-managed devfreq_unregister_notifier()

(読みやすさのため、行が分割されています)。

上記のソースファイルを確認すると、以下のようないくつかのkerneldocコメントが見つかりました:

/**
 * devm_devfreq_register_notifier()
        - Resource-managed devfreq_register_notifier()
 * @dev:      The devfreq user device. (parent of devfreq)
 * @devfreq:  The devfreq object.
 * @nb:               The notifier block to be unregistered.
 * @list:     DEVFREQ_TRANSITION_NOTIFIER.
 */

問題は「*」が欠如していることで、ビルドシステムの単純なCコメントブロックの認識を混乱させています。この問題は、そのコメントが2016年に追加された以来、すでに4年間存在していました。修正は、欠如しているアスタリスクを追加するだけでした。そのファイルの履歴を確認すると、件名の通常のフォーマットがわかり、 scripts/get_maintainer.pl 誰に届けるべきかを教えてくれました。結果として作成されたパッチは以下のようになります:

Two kerneldoc comments in devfreq.c fail to adhere to the required format,
resulting in these doc-build warnings:

  ./drivers/devfreq/devfreq.c:1818: warning: bad line:
        - Resource-managed devfreq_register_notifier()
  ./drivers/devfreq/devfreq.c:1854: warning: bad line:
        - Resource-managed devfreq_unregister_notifier()

Add a couple of missing asterisks and make kerneldoc a little happier.

他の修正はより時間がかかります、特に構造体メンバーやドキュメントが不足している関数パラメータに関連する修正です。そのような場合、メンバーやパラメータの役割を明確にし、正しい方法で記述する必要があります。全体的にこの作業はときどき退屈ですが、非常に重要です。ドキュメンテーションビルドから警告を実際に削除できるようになれば、開発者に新しい警告を追加しないように期待できるようになります。

放置されたkerneldocコメント¶

開発者に自身のコードにkerneldocコメントを書くよう奨励されていますが、多くのコメントはドキュメンテーションビルドに引き込まれません。これにより情報が見つけにくくなり、たとえばSphinxがそのドキュメンテーションへのリンクを生成できなくなることがあります。このようなコメントをドキュメンテーションに引き込むためのディレクティブを追加することで、コミュニティがこれらの作業の価値を最大限に活用できるようになります。 kernel-doc ツールを使用することで、これらの見過ごされたコメントを見つけることができます。

以下の scripts/find-unused-docs.sh tool can be used to find these overlooked comments.

エクスポートされた関数やデータ構造のドキュメンテーションを取り込むことで最大の価値が得られます。多くのサブシステムでは内部使用のためにkerneldocコメントが用意されていますが、それらは関連するサブシステムの開発者を対象としたドキュメントにのみ含めるべきです。

スペルミスの修正¶

ドキュメンテーション内のスペルミスやフォーマットエラーを修正することは、パッチの作成と送信方法を学ぶための素早く効果的な方法であり、また有用なサービスです。私はこのようなパッチを常に受け入れます。ただし、いくつか修正した後は、より高度なタスクに進むことをお勧めします。次の初心者にスペルミスを残しておきましょう。

以下の点は ではありません スペルミスであり、「修正」すべきではありません:

  • カーネルドキュメンテーションではアメリカ英語とイギリス英語のスペルどちらも許容されています。どちらか一方に統一する必要はありません。

  • ドットの後に1スペースか2スペースを置くべきかという点については、カーネルドキュメンテーションの文脈では議論すべきではありません。他にも「オックスフォードコンマ」のような理性的な意見の相違は、ここではオフトピックです。

どのプロジェクトのパッチにも同様ですが、あなたの変更が本当に改善につながるかをよく考えましょう。

古びたドキュメンテーション¶

一部のカーネルドキュメンテーションは最新で維持されており、有用です。一方で、一部のドキュメンテーションは…そうではありません。埃っぽく古い、不正確なドキュメンテーションは読者を誤解させ、全体のドキュメンテーションの信頼性を損ないます。このような問題を改善するための取り組みは歓迎されます。

ドキュメントを扱っている際には、それが最新かどうか、更新が必要かどうか、あるいは完全に削除すべきかどうかをよく検討してください。以下のような警告サインに注意してください:

  • 2.xカーネルへの参照

  • SourceForgeリポジトリへのポインタ

  • 数年間の履歴に他に何もない

  • Git導入前のワークフローに関する議論

もちろん、ドキュメンテーションを最新にし、必要な情報を追加することが最も良い方法です。このような作業は、関連するサブシステムに精通した開発者の協力が必要な場合があります。開発者たちは、丁寧に依頼され、その意見が聞き取り・実行される場合、改善に取り組む人々と協力するためにはしばしば協力的です。

一部のドキュメンテーションは改善の余地が全くない状態です。たとえば、コードがカーネルから古くから削除されたにもかかわらず、それに関するドキュメントがまだ存在しているケースもあります。古くなったドキュメンテーションを削除する抵抗が意外と強いですが、それでも行うべきです。ドキュメンテーションに不要な余分な情報は誰も助かりません。

特に、古くなったドキュメントにまだある程度有用な情報が含まれている場合、更新が困難な場合は、そのドキュメントの冒頭に警告を追加するのが最善の対処法かもしれません。以下のテキストが推奨されます：

.. warning ::
      This document is outdated and in need of attention.  Please use
      this information with caution, and please consider sending patches
      to update it.

このようにすれば、少なくとも苦労している読者たちに、このドキュメントが誤った方向へ導く可能性があることを警告することができました。

ドキュメンテーションの整合性¶

ここにいるベテランたちは、1990年代に書店で見かけたLinux関連の本を覚えていらっしゃるでしょう。それらは単にネット上のさまざまな場所から集めたドキュメンテーションファイルをまとめたものです。それ以来、本は（ほぼ）改善されてきましたが、カーネルのドキュメンテーションはまだそのモデルに基づいて構築されています。それは数千ものファイルで構成されており、それぞれが他のファイルとは独立して書かれています。私たちは統合されたカーネルのドキュメンテーションを持っています。私たちは数千もの個別ドキュメントを持っています。

私たちは、特定の読者向けにドキュメンテーションをグループ化した「ブック」を作成することで状況を改善しようと努力しています。これらには以下のものがあります：

  • Linuxカーネルユーザーおよび管理者のガイド

  • コアAPIドキュメント

  • Linuxドライバ実装者向けAPIガイド

  • Linuxカーネルユーザー空間APIガイド

ドキュメンテーションそのものに関するこのブックも含まれます。

ドキュメントを適切なブックに移すことは重要なタスクであり、継続する必要があります。ただし、この作業にはいくつかの課題があります。ドキュメントファイルを移動させることで、そのファイルを扱う人々には短期的な負担が生じます。彼らはその変更に不満があるのは当然です。通常、ドキュメントを一度移動させることは可能ですが、頻繁に移動させたくないのです。

すべてのドキュメントが正しい場所に配置されたとしても、私たちは単に大きな山を小さな山に分けるだけです。これらのドキュメントを統合して一つの全体にする作業はまだ始まっていません。この点について、どのように進めるかのアイデアがありましたら、ぜひご意見をいただければ大変嬉しく思います。

スタイルシートの改善¶

Sphinxの採用により、HTML出力は以前より見やすくなりました。しかし、まだ大幅な改善の余地があります。ドナルド・クヌースやエドワード・トーフテが見ても驚かないレベルには程遠いです。これには、スタイルシートを調整して、よりtypographically sound（見やすく読みやすい）で、アクセシビリティが高く読みやすい出力を作成する必要があります。

注意してください：このタスクに取り組むと、典型的なビキシェッド領域に突入することになります。連想がなくても、比較的明白な変更でも多くの意見や議論が生まれるでしょう。これは、我々が生きている世界の性質なのです。

LaTeXを使わないPDFのビルド¶

Pythonスキルと多くの時間をもつ人にとって、これは非自明なタスクです。Sphinxツールチェーンは比較的小規模で、開発環境に組み込みやすいですが、PDFやEPUBの出力にはLaTeXのインストールが必要で、これは決して小規模や制限されていないわけではありません。これを削除できれば良いでしょう。

rst2pdfツール（https://rst2pdf.org/）をPDF生成に利用する予定でしたが、実際には期待に応えるほどではなかったようです。rst2pdfの開発は最近再び進んでいるようですが、これは希望の兆候です。もし適切に意欲のある開発者がこのプロジェクトと協力してrst2pdfをカーネルドキュメンテーションビルドと連携させることができれば、世界中が感謝するでしょう。

より多くのドキュメンテーションを書く¶

当然ながら、カーネルの多くの部分はドキュメント不足です。特定のカーネルサブシステムについて知識があり、それをドキュメンテーションする意欲があれば、すぐに執筆してカーネルに結果を寄稿してください。その結果、無数のカーネル開発者やユーザーが感謝するでしょう。

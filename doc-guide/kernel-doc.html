kernel-docコメントの作成¶

Linux カーネルのソースファイルには、関数、型、設計を説明するための kernel-doc フォーマットの構造化されたドキュメンテーションコメントが含まれている場合があります。ソースファイル内に埋め込まれているドキュメンテーションは、更新をより容易にします。

注意

kernel-doc フォーマットは、javadoc、gtk-doc または Doxygen に見かけ上似ていますが、歴史的な理由により大きく異なります。カーネルのソースコードには数万の kernel-doc コメントが含まれています。ここに記述されているスタイルに従ってください。

kernel-doc の構造はコメントから抽出され、適切な Sphinx C Domain 関数および型の説明とアンカーは、それらから生成されます。説明は特別なkernel-docのハイライトとクロスリファレンスのためにフィルタリングされます。詳細については下記を参照してください。

ロード可能なモジュールにエクスポートされるすべての関数は EXPORT_SYMBOL または EXPORT_SYMBOL_GPL kernel-docコメントを持つべきです。モジュールから使用される予定のヘッダーファイル内の関数およびデータ構造体にもkernel-docコメントを付与すべきです。

他のカーネルファイルから見える関数（マークされていない static）にもkernel-doc形式のドキュメンテーションを提供することも良い実践です。また、プライベート（ファイル static）ルーチンにもkernel-doc形式のドキュメンテーションを提供することを推奨します。これはカーネルソースコードレイアウトの整合性を保つためで、優先度は低く、そのカーネルソースファイルのメンテナの裁量に任されます。

kernel-docコメントの書式設定方法¶

開始コメント記号 /** kernel-docコメントに使用されます。The kernel-doc ツールはこのようにマークされたコメントを抽出します。コメントの残りの部分は、左側にアスタリスクの列を持つ通常のマルチラインコメントと同様にフォーマットされ、 */ 改行で1行に閉じます。

関数および型のkernel-docコメントは、記述されている関数または型の直前に配置すべきです。これにより、コードを変更する人がドキュメンテーションも同時に変更する可能性が高まります。概要のkernel-docコメントは、トップインデントレベルのどこにでも配置できます。

ツールを実行する際の kernel-doc ツールを増加した詳細度で実行し、実際の出力生成を行わずに、ドキュメンテーションコメントの正しい書式を確認するために使用できます。たとえば:

scripts/kernel-doc -v -none drivers/foo/bar.c

ドキュメンテーションの書式は、追加のgccチェックを実行するよう求められたときにカーネルビルドによって確認されます:

make W=n

関数ドキュメンテーション¶

関数および関数ライクマクロのkernel-docコメントの一般的な書式は:

/**
 * function_name() - Brief description of function.
 * @arg1: Describe the first argument.
 * @arg2: Describe the second argument.
 *        One can provide multiple line descriptions
 *        for arguments.
 *
 * A longer description, with more discussion of the function function_name()
 * that might be useful to those using or modifying it. Begins with an
 * empty comment line, and may include additional embedded empty
 * comment lines.
 *
 * The longer description may have multiple paragraphs.
 *
 * Context: Describes whether the function can sleep, what locks it takes,
 *          releases, or expects to be held. It can extend over multiple
 *          lines.
 * Return: Describe the return value of function_name.
 *
 * The return value description can also have multiple paragraphs, and should
 * be placed at the end of the comment block.
 */

関数名の後の簡潔な説明は複数行にわたる場合があり、引数の説明、空のコメント行、またはコメントブロックの終わりで終了します。

関数パラメータ¶

各関数引数は、短い関数説明の直後に順に記述する必要があります。関数説明と引数の間に空白行を空けないでください。また、引数同士の間に空白行も空けないでください。

Each @argument: 説明は複数行にわたることができます。

注意

もし @argument 説明が複数行にわたる場合、説明の続きは前の行と同じ列から開始する必要があります。

* @argument: some long description
*            that continues on next lines

または:

* @argument:
*         some long description
*         that continues on next lines

関数が可変数の引数を持つ場合、その説明はkernel-doc記法で以下のように記述する必要があります：

* @...: description

関数のコンテキスト¶

関数が呼び出せるコンテキストを記述する必要があります。 Contextこのセクションには、関数がスリープするかどうか、割り込みコンテキストから呼び出せるかどうか、取得するロック、解放するロック、および呼び出し元が保持するロックが記述される必要があります。

例:

* Context: Any context.
* Context: Any context. Takes and releases the RCU lock.
* Context: Any context. Expects <lock> to be held by caller.
* Context: Process context. May sleep if @gfp flags permit.
* Context: Process context. Takes and releases <mutex>.
* Context: Softirq or process context. Takes and releases <lock>, BH-safe.
* Context: Interrupt context.

構造体、共用体、列挙型のドキュメンテーション¶

構造体、共用体、列挙型のkernel-docコメントの一般的な形式は：

/**
 * struct struct_name - Brief description.
 * @member1: Description of member1.
 * @member2: Description of member2.
 *           One can provide multiple line descriptions
 *           for members.
 *
 * Description of the structure.
 */

以下のように置き換えることができます： struct 上記の例における union または enum 共用体または列挙型を記述するために使用します。 member は、構造体および共用体のメンバ名や列挙型内の列挙値を表します。

構造体名の後の簡潔な説明は複数行にわたることができ、メンバの説明、空のコメント行、またはコメントブロックの終わりで終了します。

メンバ¶

構造体、共用体、列挙型のメンバは、関数パラメータと同じようにドキュメンテーションする必要があります。短い説明の直後に記述し、複数行にわたることもできます。

構造体または共用体の説明内で、以下のようなコメントタグを使用できます： private: および public: コメントタグ。構造体のフィールドで、 private: 領域内にあるフィールドは、生成された出力ドキュメンテーションに表示されません。

以下の private: および public: タグは、 /* コメントマーカーの直後に開始する必要があります。 : と終了 */ マーカーの間にコメントを含めることができます。

例:

/**
 * struct my_struct - short description
 * @a: first member
 * @b: second member
 * @d: fourth member
 *
 * Longer description
 */
struct my_struct {
    int a;
    int b;
/* private: internal use only */
    int c;
/* public: the next one is public */
    int d;
};

ネストされた構造体/共用体¶

ネストされた構造体と共用体をドキュメンテーションできます。例えば：

/**
 * struct nested_foobar - a struct with nested unions and structs
 * @memb1: first member of anonymous union/anonymous struct
 * @memb2: second member of anonymous union/anonymous struct
 * @memb3: third member of anonymous union/anonymous struct
 * @memb4: fourth member of anonymous union/anonymous struct
 * @bar: non-anonymous union
 * @bar.st1: struct st1 inside @bar
 * @bar.st2: struct st2 inside @bar
 * @bar.st1.memb1: first member of struct st1 on union bar
 * @bar.st1.memb2: second member of struct st1 on union bar
 * @bar.st2.memb1: first member of struct st2 on union bar
 * @bar.st2.memb2: second member of struct st2 on union bar
 */
struct nested_foobar {
  /* Anonymous union/struct*/
  union {
    struct {
      int memb1;
      int memb2;
  }
    struct {
      void *memb3;
      int memb4;
    }
  }
  union {
    struct {
      int memb1;
      int memb2;
    } st1;
    struct {
      void *memb1;
      int memb2;
    } st2;
  } bar;
};

注意

  1. ネストされた構造体または共用体をドキュメンテーションする場合、構造体/共用体が foo 名前がついている場合、そのメンバ bar は以下のようにドキュメンテーションする必要があります： @foo.bar:

  2. ネストされた構造体/共用体が匿名の場合、そのメンバ bar は以下のようにドキュメンテーションする必要があります： @bar:

インラインメンバドキュメンテーションコメント¶

構造体メンバも、定義内にインラインでドキュメント化することも可能です。スタイルは2種類あり、オープンとクローズが同じ行に記述されるシングルラインコメントと、それぞれが別の行に記述されるマルチラインコメントがあります。すべての他のkernel-docコメントと同様に、以下のように記述します: /** and closing */ are on the same line, and multi-line comments where they are each on a line of their own, like all other kernel-doc comments:

/**
 * struct foo - Brief description.
 * @foo: The Foo member.
 */
struct foo {
      int foo;
      /**
       * @bar: The Bar member.
       */
      int bar;
      /**
       * @baz: The Baz member.
       *
       * Here, the member description may contain several paragraphs.
       */
      int baz;
      union {
              /** @foobar: Single line description. */
              int foobar;
      };
      /** @bar2: Description for struct @bar2 inside @foo */
      struct {
              /**
               * @bar2.barbar: Description for @barbar inside @foo.bar2
               */
              int barbar;
      } bar2;
};

Typedefドキュメント¶

typedef kernel-docコメントの一般的なフォーマットは以下の通りです:

/**
 * typedef type_name - Brief description.
 *
 * Description of the type.
 */

関数プロトタイプを持つtypedefもドキュメント化可能です:

/**
 * typedef type_name - Brief description.
 * @arg1: description of arg1
 * @arg2: description of arg2
 *
 * Description of the type.
 *
 * Context: Locking context.
 * Return: Meaning of the return value.
 */
 typedef void (*type_name)(struct v4l2_ctrl *arg1, void *arg2);

ハイライトとクロスリファレンス¶

kernel-docコメントの説明テキスト内で認識される特別なパターンは、適切なreStructuredTextマーキアップおよび Sphinx C Domain リファレンスに変換されます。

注意

以下は のみ kernel-docコメント内で認識されます、 ではありません 通常のreStructuredTextドキュメント内で認識されます。

funcname()

関数リファレンス。

@parameter

関数パラメータの名前。(クロスリファレンスは行わず、フォーマットのみ)

%CONST

定数の名前。(クロスリファレンスは行わず、フォーマットのみ)

``literal``

文字列ブロックとして扱うべきものです。出力では monospaced font.

使用する特殊文字がkernel-docスクリプトやreStructuredTextで特別な意味を持つ場合に役立ちます。

これは、関数説明内で %ph のようなものを使用する場合に特に役立ちます。

$ENVVAR

環境変数の名前。(クロスリファレンスは行わず、フォーマットのみ)

&struct name

構造体リファレンス。

&enum name

列挙型リファレンス。

&typedef name

typedefリファレンス。

&struct_name->member または &struct_name.member

構造体またはユニオンメンバリファレンス。クロスリファレンスは構造体またはユニオンの定義に向けられるため、メンバ自体にはなりません。

&name

汎用型リファレンス。上記のフルリファレンスを使用することを推奨します。これは主に legacy コメントのためのものです。

reStructuredTextからのクロスリファレンス¶

kernel-docコメントで定義された関数や型へのクロスリファレンスには、追加の構文は必要ありません。関数名の末尾に () を付けて、 struct, union, enum または typedef で型を指定します。例えば:

See foo().
See struct foo.
See union bar.
See enum baz.
See typedef meh.

ただし、クロスリファレンスリンクにカスタムテキストを指定したい場合は、以下の構文を使用できます:

See :c:func:`my custom link text for function foo <foo>`.
See :c:type:`my custom link text for struct bar <bar>`.

詳細については、以下の Sphinx C Domain ドキュメントを参照してください。

概要ドキュメントコメント¶

ソースコードとコメントを近接させることを支援するために、kernel-docドキュメントブロックを自由形式のコメントとして含めることができます。これは関数、構造体、ユニオン、列挙型、typedef用のkernel-docではなく、ドライバやライブラリコードの運用理論など、何か他の用途に使用できます。

これは、 DOC: セクションキーワードとセクションタイトルを使用することで実現されます。

概要または高レベルドキュメントコメントの一般的なフォーマットは以下の通りです:

/**
 * DOC: Theory of Operation
 *
 * The whizbang foobar is a dilly of a gizmo. It can do whatever you
 * want it to do, at any time. It reads your mind. Here's how it works.
 *
 * foo bar splat
 *
 * The only drawback to this gizmo is that is can sometimes damage
 * hardware, software, or its subject(s).
 */

タイトルの後ろに DOC: ソースファイル内で見出しとして機能し、ドキュメンテーションコメントを抽出するための識別子としても使用されます。したがって、タイトルはファイル内で一意である必要があります。

kernel-docコメントの含める¶

reStructuredTextドキュメントにドキュメンテーションコメントを含めるには、専用のkernel-doc Sphinxディレクティブ拡張機能を使用します。

kernel-docディレクティブの形式は次の通りです：

.. kernel-doc:: source
   :option:

以下の source ソースファイルへのパスは、カーネルソースツリーに対して相対パスで指定します。サポートされるディレクティブオプションは次の通りです：

エクスポート： [source-pattern …]

を含むすべての関数のドキュメンテーションを source でエクスポートされた EXPORT_SYMBOL または EXPORT_SYMBOL_GPL でエクスポートされた関数を source または、 で指定されたファイル内の関数を.

以下の で指定されたファイル内の関数を kernel-docコメントがヘッダーファイルに配置されている場合、 EXPORT_SYMBOL および EXPORT_SYMBOL_GPL 関数定義の隣に配置されている場合、

例:

.. kernel-doc:: lib/bitmap.c
   :export:

.. kernel-doc:: include/net/mac80211.h
   :export: net/mac80211/*.c
内部： [source-pattern …]

を含むすべての関数と型のドキュメンテーションを source でエクスポートされた ではありません でエクスポートされた関数と型を EXPORT_SYMBOL または EXPORT_SYMBOL_GPL でエクスポートされた関数を source または、 で指定されたファイル内の関数を.

例:

.. kernel-doc:: drivers/gpu/drm/i915/intel_audio.c
   :internal:
識別子： [ function/type …]

を含むそれぞれの ファンクション および type の sourceが指定されていない場合、 ファンクション 内のすべての関数と型のドキュメンテーションを含みます。 source 識別子を除外：

例:

.. kernel-doc:: lib/bitmap.c
   :identifiers: bitmap_parselist bitmap_parselist_user

.. kernel-doc:: lib/idr.c
   :identifiers:
を含むそれぞれの [ function/type …]

関数： ファンクション および type の source.

例:

.. kernel-doc:: lib/bitmap.c
   :no-identifiers: bitmap_parselist
これは「識別子」ディレクティブの別名であり、非推奨です。 [ function/type …]

ドキュメント：

を指定した title

の段落のドキュメンテーションを DOC: で指定した title の sourceにスペースを含めることができます。 titleを引用せずに記述してください。 titleの部分で、 title は段落の識別子としてのみ使用され、出力には含まれません。enclosing reStructuredTextドキュメントに適切な見出しを設ける必要があります。

例:

.. kernel-doc:: drivers/gpu/drm/i915/intel_audio.c
   :doc: High Definition Audio over HDMI and Display Port

オプションを指定しない場合、kernel-docディレクティブはソースファイル内のすべてのドキュメンテーションコメントを含みます。

kernel-doc拡張機能はカーネルソースツリー内の Documentation/sphinx/kerneldoc.pyに含まれています。内部的には、 scripts/kernel-doc スクリプトを使用してソースからドキュメンテーションコメントを抽出します。

kernel-docをmanページ生成に使用する方法¶

kernel-docをmanページ生成に使用するだけであれば、カーネルgitツリーから以下のように実行できます：

$ scripts/kernel-doc -man \
  $(git grep -l '/\*\*' -- :^Documentation :^tools) \
  | scripts/split-man.pl /tmp/man

古いバージョンのgitは、パス除外用の構文の一部をサポートしていない場合があります。そのようなバージョンでは、次のコマンドのいずれかが動作する可能性があります：

$ scripts/kernel-doc -man \
  $(git grep -l '/\*\*' -- . ':!Documentation' ':!tools') \
  | scripts/split-man.pl /tmp/man

$ scripts/kernel-doc -man \
  $(git grep -l '/\*\*' -- . ":(exclude)Documentation" ":(exclude)tools") \
  | scripts/split-man.pl /tmp/man

はじめに¶

2001年3月、国家安全保障局（NSA）は2.5版Linuxカーネルサミットでセキュリティ強化Linux（SELinux）についてプレゼンテーションを行いました。SELinuxはLinuxカーネル内で柔軟かつ細かい非任意アクセス制御を実装するための仕組みで、元々は独自のカーネルパッチとして実装されていました。他にもRSBAC、MedusaなどのセキュリティプロジェクトがLinuxカーネル向けに柔軟なアクセス制御アーキテクチャを開発しており、LIDS、DTE、SubDomainなどのプロジェクトもLinux向けに特定のアクセス制御モデルを開発しています。各プロジェクトは自社のセキュリティニーズをサポートするため、独自のカーネルパッチを開発・維持しています。

NSAのプレゼンテーションに応じて、リンス・トーバルズは主流のLinuxカーネルに組み込むためのセキュリティフレームワークについてコメントしました。彼は、カーネルオブジェクトの操作を制御するためのセキュリティフックのセットと、セキュリティ属性を保持するためのカーネルデータ構造内の不透明なセキュリティフィールドのセットを提供する一般的なフレームワークについて説明しました。このフレームワークは、ロード可能なカーネルモジュールが任意のセキュリティモデルを実装するために利用できます。また、リンスはLinuxのキャパビリティコードをこのようなモジュールに移行する可能性を提案しました。

WireXによってLinux Security Modules（LSM）プロジェクトが始まりました。LSMは、Immunix、SELinux、SGI、Janusなどのセキュリティプロジェクトと、グレッグ・クロアハートマン、ジェームズ・モリスなどの個人が共同で開発したLinuxカーネルパッチです。この作業は2003年12月にメインストリームに組み込まれました。この技術報告書では、このフレームワークとセキュリティキャパビリティモジュールについて概説します。

LSMフレームワーク¶

LSMフレームワークは、セキュリティモジュールをサポートする一般的なカーネルフレームワークを提供します。特に、LSMフレームワークはアクセス制御モジュールのサポートに主に焦点を当てていますが、今後はサンドボックスなどの他のセキュリティニーズにも対応する可能性があります。フレームワーク自体は追加のセキュリティを提供しません。単にセキュリティモジュールをサポートするインフラストラクチャを提供するだけです。LSMフレームワークはオプションであり、 CONFIG_SECURITY 有効化されます。この機能ロジックはセキュリティモジュールとして実装されています。この機能モジュールについては、以下の「LSM Capabilities Module」で詳しく説明します。 LSM Capabilities Module.

LSMフレームワークは、カーネルデータ構造にセキュリティフィールドを含め、カーネルコードの重要なポイントでハック関数を呼び出してセキュリティフィールドを管理し、アクセス制御を実行します。また、セキュリティモジュールの登録に使用する関数も追加しています。インターフェース /sys/kernel/security/lsm は、システム上でアクティブなセキュリティモジュールの一覧をコンマ区切りで報告します。

LSMセキュリティフィールドは単純に void* ポインタです。データは「blob」と呼ばれるもので、フレームワークによって管理されるか、それを使う個々のセキュリティモジュールによって管理されます。複数のセキュリティモジュールで使用されるセキュリティblobは通常フレームワークによって管理されます。プロセスおよびプログラム実行のセキュリティ情報については、セキュリティフィールドが含まれています struct task_struct および struct cred。ファイルシステムのセキュリティ情報については、セキュリティフィールドが含まれています struct super_block。パイプ、ファイル、ソケットのセキュリティ情報については、セキュリティフィールドが含まれています struct inode および struct file。System V IPCのセキュリティ情報については、セキュリティフィールドが追加されました struct kern_ipc_perm および struct msg_msg。さらに、 struct msg_msg、struct msg_queue、および struct shmid_kernel の定義はヘッダーファイル（include/linux/msg.h および include/linux/shm.h に適切に）に移動され、セキュリティモジュールがこれらの定義を使用できるようにしました。

パケットおよびネットワークデバイスのセキュリティ情報については、セキュリティフィールドが追加されました struct sk_buff および struct scm_cookie。他のセキュリティモジュールデータと異なり、ここでのデータは32ビット整数です。セキュリティモジュールはこれらの値を実際のセキュリティ属性と関連付ける必要があります。

LSMハックはリストに維持されています。各ハックに対してリストが維持され、CONFIG_LSMで指定された順序でハックが呼び出されます。各ハックの詳細なドキュメンテーションは、 include/linux/lsm_hooks.h ヘッダーファイルに含まれています。

LSMフレームワークは、一般的なセキュリティモジュールスタッキングの近似を提供します。これは、各セキュリティモジュールが security_add_hooks() に渡す struct security_hooks_listをリストに追加します。LSMフレームワークは、登録されたハックを削除するメカニズムを提供していません。SELinuxセキュリティモジュールは自身を削除する方法を実装していますが、この機能は非推奨とされています。

ハックは主に2つの主要なカテゴリに分類されます：セキュリティフィールドを管理するために使用されるハックと、アクセス制御を実行するために使用されるハックです。第一カテゴリのハックの例には、security_inode_alloc()とsecurity_inode_free()があります。これらはinodeオブジェクトのセキュリティ構造体を割り当てたり解放したりするために使用されます。第二カテゴリのハックの例はsecurity_inode_permission()ハックです。このハックはinodeにアクセスする際の権限をチェックします。

LSM Capabilities Module¶

POSIX.1eのcapabilitiesロジックは、ファイルに保存されたセキュリティモジュールとして維持されています security/commoncap.c。capabilitiesモジュールは、説明のorderフィールドを用いて、最初に登録されるセキュリティモジュールとして識別されます。 lsm_info capabilitiesセキュリティモジュールは、他のモジュールとは異なり一般的なセキュリティブロブを使用していません。その理由は歴史的であり、オーバーヘッド、複雑さ、パフォーマンスに関する懸念に基づいています。

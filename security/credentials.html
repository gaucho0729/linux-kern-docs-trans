概要¶

Linuxが一つのオブジェクトが別のオブジェクトに作用する際に行うセキュリティチェックにはいくつかの要素があります：

  1. オブジェクト。

    オブジェクトとは、ユーザー空間のプログラムが直接操作できるシステム内のものです。Linuxでは、タスク、ファイル/インODE、メッセージキュー、共有メモリセグメントなど、さまざまな操作可能なオブジェクトがあります：

    • タスク

    • ファイル/インODE

    • ソケット

    • メッセージキュー

    • 共有メモリセグメント

    • セマフォア

    • キー

    これらのすべてのオブジェクトの説明には、認証情報のセットが含まれています。セットに含まれる内容はオブジェクトの種類によって異なります。

  2. オブジェクトの所有権。

    ほとんどのオブジェクトの認証情報には、そのオブジェクトの所有権を示すサブセットが含まれます。これはリソースの会計と制限（ディスククォータやタスクのrlimitなど）に使用されます。

    標準的なUNIXファイルシステムでは、これはinodeに記録されたUIDによって定義されます。

  3. 目的のコンテキスト。

    これらのオブジェクトの認証情報にも、そのオブジェクトの「目的のコンテキスト」を示すサブセットが含まれます。これは(2)のセットと同一である場合もありますし、そうでない場合もあります。標準的なUNIXファイルでは、これはinodeに記録されたUIDとGIDによって定義されます。

    目的のコンテキストは、オブジェクトが操作される際に行われるセキュリティ計算の一部として使用されます。

  4. サブジェクト。

    サブジェクトとは、他のオブジェクトに対して行動を起こすオブジェクトです。

    システム内のほとんどのオブジェクトは非アクティブです。システム内で他のオブジェクトに対して行動を起こすことはありません。プロセスやタスクは明らかに例外です：これらは操作を行い、アクセスや操作を行います。

    タスク以外のオブジェクトも、特定の状況ではサブジェクトとなることがあります。例えば、オープンされたファイルがタスクにSIGIOを送信する際、タスクが呼び出した際に与えられたUIDとEUIDを使用します。 fcntl(F_SETOWN) このような場合、ファイル構造体には主観的コンテキストも含まれます。

  5. 主観的コンテキスト。

    サブジェクトは、自身の認証情報をさらに解釈します。その認証情報のサブセットが「主観的コンテキスト」となり、サブジェクトが行動する際のセキュリティ計算の一部として使用されます。

    例えばLinuxのタスクでは、ファイルに対して行動する際にはFSUID、FSGID、補助グループリストを使用します。これらは通常の目的のコンテキストとなるリアルUIDとGIDとは別です。

  6. アクション。

    Linuxには、主体が対象に対して実行できるアクションがいくつかあります。許可されるアクションの種類は、主体と対象の性質によって異なります。

    アクションには、ファイルの読み込み、書き込み、作成、削除、タスクのフォークやシグナル送信、トレースなどが含まれます。

  7. ルール、アクセス制御リスト、セキュリティ計算。

    主体が対象に対してアクションを実行する際、セキュリティ計算が行われます。これは、主観的なコンテキスト、客観的なコンテキスト、およびアクションを組み合わせて、複数のルールセットを検索し、そのコンテキスト下で主体が対象に対してそのアクションを許可されるか拒否されるかを判断します。

    ルールの主なソースは以下の2つです：

    1. 任意アクセス制御（DAC）：

      時折、対象自体がその説明の一部としてルールセットを含むことがあります。これは「アクセス制御リスト（ACL）」と呼ばれます。Linuxのファイルは1つ以上のACLを提供する場合があります。

      たとえば、伝統的なUNIXファイルは、ユーザー、グループ、およびその他の3つの固定クラスの主体（「user」「group」「other」）それぞれに特定の権限（「read」「write」「execute」など）を付与する簡略化されたACLとしてのパーミッションマスクを含みます。UNIXファイルのパーミッションは、任意の主体を指定することができないため、用途に制限されます。

      LinuxのファイルはまたPOSIX ACLを持つ場合もあります。これは、さまざまな主体にさまざまな権限を付与するルールのリストです。

    2. 強制アクセス制御（MAC）：

      システム全体がすべての主体と対象に適用される1つ以上のルールセットを持つ場合があります。SELinuxやSmackはその例です。

      SELinuxやSmackの場合、各対象はその認証情報にラベルが割り当てられます。アクションが要求される際、主体のラベル、対象のラベル、およびアクションを組み合わせて、そのアクションが許可されるか拒否されるかを規定するルールを探します。

資格情報の種類¶

Linuxカーネルがサポートする認証情報の種類は以下の通りです：

  1. 伝統的なUNIX認証情報。

    • 実際のユーザーID

    • 実際のグループID

    UIDとGIDは、ほとんどの場合、すべてのLinuxオブジェクトに含まれています（一部のケースでは自動的に生成される必要があります、たとえばFATやCIFSファイルなどWindowsから導出されたファイル）。これら（ほぼすべて）は、オブジェクトの客観的コンテキストを定義し、一部のケースではタスクが若干異なります。

    • 有効、保存、FSユーザーID

    • 有効、保存、FSグループID

    • 補助グループ

    これはタスク専用の追加の資格情報です。通常、EUID/EGID/GROUPSが主観的なコンテキストとして使用され、実際のUID/GIDが目的的な資格情報として使用されます。タスクに関しては、常にこのようにはならないことに注意する必要があります。

  2. 能力（Capabilities）。

    • 許可された能力のセット

    • 継承可能な能力のセット

    • 有効な能力のセット

    • 能力のバウンドイングセット

    これらはタスクのみが保持します。これは、通常のタスクが持たない能力を段階的に付与される形でタスクに与えられる上位の能力を示します。これらは伝統的なUNIX資格情報の変更によって暗黙的に操作されますが、また、 capset() システムコールで読み取ることができます。

    許可された能力は、プロセスが自身の有効なまたは許可されたセットに自身で能力を付与する際に使用可能な能力です。 capset()この継承可能なセットも同様に制約されることがあります。

    有効な能力は、タスクが実際に利用できる能力です。

    継承可能な能力は、他のタスクに渡される可能性のある能力です。 execve().

    バウンドイングセットは、継承される能力を制限します。 execve()特にバイナリがUID 0として実行される場合に適用されます。

  3. セキュアマネジメントフラグ（securebits）。

    これらはタスクのみが保持します。これらは、execve()などの特定の操作において上記の資格情報がどのように操作され継承されるかを制御します。これらは直接的な目的的または主観的な資格情報として使用されません。

  4. キーやキーライン。

    これらはタスクのみが保持します。これらは、他の標準UNIX資格情報に収まらないセキュリティトークンを保持しキャッシュします。これにより、プロセスが行うファイルアクセスにネットワークファイルシステムのキーやその他のセキュリティ詳細を知る必要なく、セキュリティ関連の情報が利用できるようになります。

    キーラインは特別な種類のキーラインです。他のキーラインのセットを保持し、必要なキーラインを検索できます。各プロセスは複数のキーラインに登録できます：

    スレッドごとのキーリング プロセスごとのキーリング セッションごとのキーリング

    プロセスがキーアクセスを行う際、既に存在しない場合は、今後アクセスする際に検索できるようにこれらのキーラインのいずれかにキャッシュされます。

    キーアクセスの使用方法については、 Documentation/security/keys/*.

  5. LSM

    Linuxセキュリティモジュール（Linux Security Module）は、タスクが行える操作に追加の制御を設けることができます。現在、LinuxはいくつかのLSMオプションをサポートしています。

    一部のモジュールでは、システム内のオブジェクトをラベル付けし、タスクが一つのラベルを持つオブジェクトに対して他のラベルを持つオブジェクトに行える操作を規定するルール（ポリシー）を適用します。

  6. AF_KEY

    これはネットワーキングスタックにおける資格情報管理のソケットベースのアプローチです[RFC 2367]。このドキュメントでは、タスクおよびファイル資格情報と直接的に相互作用しないので、論じられていません。むしろ、システムレベルの資格情報を保持しています。

ファイルを開く際、開くタスクの主観的コンテキストの一部が作成されたファイル構造体に記録されます。これにより、そのファイル構造体を使用する操作では、タスクが実行した操作の主観的コンテキストではなく、これらの資格情報を使用できるようになります。例えば、ネットワークファイルシステム上で開かれたファイルでは、読み取りまたは書き込みを行うユーザーに関係なく、サーバーに対してそのファイルの資格情報を提示する必要があります。

ファイルの属性¶

ディスク上にあるファイルまたはネットワーク経由で取得したファイルには、そのファイルの客観的セキュリティコンテキストを形成する注釈が含まれる場合があります。ファイルシステムの種類によっては、以下の一覧に示す1つまたは複数が含まれる場合があります：

  • UNIX UID、GID、mode;

  • WindowsユーザーID;

  • アクセス制御リスト;

  • LSMセキュリティラベル;

  • UNIX実行権限昇格ビット (SUID/SGID);

  • ファイルキャパビリティ実行権限昇格ビット。

これらはタスクの主観的なセキュリティコンテキストと比較され、その結果として特定の操作が許可または拒否されることがあります。execve()の場合、権限昇格ビットが有効となり、実行可能ファイルの注釈に基づいて生成されたプロセスに追加の権限が与えられることがあります。

タスクの資格情報¶

Linuxでは、タスクのすべての資格情報は(uid, gid)または(groups, keys, LSMセキュリティ)を通じて、参照カウントを持つ'struct cred'型の構造体に保持されます。各タスクは、task_struct内の'cred'というポインタを通じて自身の資格情報を参照します。

資格情報のセットが準備・コミットされると、以下の例外を除き変更できません：

  1. その参照カウントを変更できます；

  2. 参照しているgroup_info構造体の参照カウントを変更できます；

  3. 参照しているセキュリティデータの参照カウントを変更できます；

  4. 参照しているキーリングの参照カウントを変更できます；

  5. 参照しているキーリングを失効させたり、セキュリティ属性を変更したり、取り消すことができます；そして

  6. 参照しているキーリングの内容を変更できます（キーリングが共有された資格情報を変更可能な点がその目的です）。

cred構造体の内容を変更するには、コピーして置き換える原則に従う必要があります。まずコピーを取り、その後コピーを変更し、最後にRCUを用いてタスクポインタを新しいコピーに変更します。この作業を支援するラッパー関数があります（以下を参照してください）。

タスクは自身の_own_クレデンシャルのみを変更でき、他のタスクのクレデンシャルを変更することは許可されません。これは、 capset() システムコールが現在のプロセスのPID以外のPIDを指定することは許可されなくなったことを意味します。また、 keyctl_instantiate() および keyctl_negate() 関数は、要求プロセスのプロセス固有のkeyringへのアタッチメントを許可しなくなりました。インスタンス化プロセスがそれらを生成する必要があるためです。

タスクの資格情報を取得する¶

クレデンシャル構造体へのポインタを取得し、その後の解放は必要ありません。

const struct cred *current_cred()

を呼び出すだけでよいです。

タスクの資格情報の特定の側面を取得するための、便利なラッパーが用意されています（値は各場合で単純に返却されます）：

uid_t current_uid(void)         Current's real UID
gid_t current_gid(void)         Current's real GID
uid_t current_euid(void)        Current's effective UID
gid_t current_egid(void)        Current's effective GID
uid_t current_fsuid(void)       Current's file access UID
gid_t current_fsgid(void)       Current's file access GID
kernel_cap_t current_cap(void)  Current's effective capabilities
struct user_struct *current_user(void)  Current's user account

タスクの資格情報の特定の関連ペアを取得するための、便利なラッパーも用意されています：

void current_uid_gid(uid_t *, gid_t *);
void current_euid_egid(uid_t *, gid_t *);
void current_fsuid_fsgid(uid_t *, gid_t *);

これらは、現在のタスクの資格情報から取得した後、引数を通じてこれらの値のペアを返却します。

さらに、現在のプロセスの現在の資格情報セットへの参照を取得する関数もあります：

const struct cred *get_current_cred(void);

struct cred に実際に存在しない資格情報を参照するための関数も用意されています：

struct user_struct *get_current_user(void);
struct group_info *get_current_groups(void);

これらは、それぞれ現在のプロセスのユーザー会計構造と補助グループリストへの参照を取得します。

参照を取得した後は、以下のように解放する必要があります： put_cred(), free_uid() または put_group_info() 適切な処理を行ってください。

他のタスクの資格情報を取得する¶

タスクが自身の資格情報を取得する際はロックを必要としませんが、他のタスクの資格情報を取得する際にはそうではありません。RCU read lock を使用し、 rcu_dereference().

以下の rcu_dereference() ラッパーとしてラップされています：

const struct cred *__task_cred(struct task_struct *task);

RCU read lock 内で使用する必要があります。以下の例のように：

void foo(struct task_struct *t, struct foo_data *f)
{
        const struct cred *tcred;
        ...
        rcu_read_lock();
        tcred = __task_cred(t);
        f->uid = tcred->uid;
        f->gid = tcred->gid;
        f->groups = get_group_info(tcred->groups);
        rcu_read_unlock();
        ...
}

他のタスクの資格情報を長期間保持する必要がある場合、またはその間にスリープする必要がある場合は、呼び出し元は以下のように参照を取得する必要があります：

const struct cred *get_task_cred(struct task_struct *task);

これは内部でRCUのマジックをすべて処理します。呼び出し元は、取得したクレデンシャルを処理が終わったらput_cred()を呼び出す必要があります。

注意

の結果 __task_cred() を直接的に渡してはいけません get_cred() に渡すと、これは競合条件を引き起こす可能性があるため commit_cred().

他のタスクのクレデンシャルの一部にアクセスするためのいくつかのユーティリティ関数があります。これらはRCUのマジックを呼び出し元から隠します:

uid_t task_uid(task)            Task's real UID
uid_t task_euid(task)           Task's effective UID

呼び出し元がすでにRCU読み取りロックを保持している場合、以下のようにします:

__task_cred(task)->uid
__task_cred(task)->euid

を代わりに使用する必要があります。同様に、タスクのクレデンシャルの複数の側面にアクセスする必要がある場合、RCU読み取りロックを使用する必要があります、 __task_cred() を呼び出し、結果を一時ポインタに保存し、ロックを解除する前にそのクレデンシャルの側面を呼び出します。これにより、コストのかかるRCUマジックが複数回呼び出されることを防ぎます。

他のタスクのクレデンシャルの単一の側面にアクセスする必要がある場合、以下のように使用できます:

task_cred_xxx(task, member)

ここで'member'はcred構造体のポインタでないメンバです。例えば:

uid_t task_cred_xxx(task, suid);

はタスクから'struct cred::suid'を取得し、適切なRCUマジックを実行します。ポインタメンバについては使用できません。RCU読み取りロックが解除された瞬間にポインタが指すオブジェクトが消失する可能性があるためです。

資格情報を変更する¶

以前に述べたように、タスクは自身のクレデンシャルのみを変更でき、他のタスクのクレデンシャルを変更することはできません。これにより、自身のクレデンシャルを変更する際にはロックを使用する必要がありません。

現在のプロセスのクレデンシャルを変更するには、関数がまず以下の関数を呼び出して新しいクレデンシャルセットを準備する必要があります:

struct cred *prepare_creds(void);

この関数はcurrent->cred_replace_mutexをロックし、その後、現在のプロセスのクレデンシャルの複製を割り当てて構築します。成功した場合、ミューテックスを保持したまま戻します。失敗した場合（メモリ不足）、NULLを返します。

ミューテックスは ptrace() を、クレデンシャルの構築と変更に関するセキュリティチェックが行われている間、プロセスのptrace状態を変更することを防ぎます。ptrace状態は結果を変更する可能性があるため、特に以下のケースでは重要です: execve().

新しいクレデンシャルセットは適切に変更し、セキュリティチェックとフックを実行する必要があります。current_cred()はこの時点では現在のセットを返すため、現在のセットと提案されたセットの両方が利用可能です。

グループリストを置き換える際、新しいリストはクレデンシャルに追加される前にソートする必要があります。二分探索がメンバーシップのテストに使用されるためです。実際には、set_groups()またはset_current_groups()の前にgroups_sort()を呼び出す必要があります。groups_sort()は、共有されている構造体には呼び出すべきではありません struct group_list 共有されている構造体には呼び出すべきではありません。ソートプロセス中に要素の順序が変化する可能性があるためです。配列がすでにソートされている場合でもです。

資格情報セットが準備ができたら、現在のプロセスにコミットするために次の関数を呼び出す必要があります:

int commit_creds(struct cred *new);

この操作は、資格情報およびプロセスのさまざまな側面を変更し、LSMが同様に処理できるようにする機会を提供します。その後、 rcu_assign_pointer() 新しい資格情報を実際にコミットするために使用します。 current->credこの操作は、ロックを解放し、 current->cred_replace_mutex ドライバは、その変更に応じて動作します。その変更に応じて動作します。 ptrace() が実行され、スケジューラーや他の関係者に変更を通知します。

この関数は常に0を返すことが保証されており、このような関数の最後にテールコール可能として使用できます。 sys_setresuid().

この関数は呼び出し元の新しい資格情報への参照を消費します。呼び出し元はその後、 put_cred() 新しい資格情報に対して呼び出すべきではありません。

さらに、この関数が新しい資格情報セットに対して呼び出された後は、その資格情報は変更することはできません。

セキュリティチェックが失敗したり、他のエラーが発生した場合、以下の関数を呼び出す必要があります: prepare_creds() この関数は、

void abort_creds(struct cred *new);

のロックを解放します。 current->cred_replace_mutex これ prepare_creds() 取得したロックを解放し、新しい資格情報を解放します。

典型的な資格情報の変更関数は次のようになります:

int alter_suid(uid_t suid)
{
        struct cred *new;
        int ret;

        new = prepare_creds();
        if (!new)
                return -ENOMEM;

        new->suid = suid;
        ret = security_alter_suid(new);
        if (ret < 0) {
                abort_creds(new);
                return ret;
        }

        return commit_creds(new);
}

資格情報の管理¶

資格管理に役立つ関数は以下の通りです:

  • void put_cred(const struct cred *cred);

    指定された資格情報への参照を解放します。参照カウントがゼロになると、RCUシステムによって資格情報が破棄される予定になります。

  • const struct cred *get_cred(const struct cred *cred);

    アクティブな資格情報セットへの参照を取得し、その資格情報セットへのポインタを返します。

  • struct cred *get_new_cred(struct cred *cred);

    構築中の資格情報セットへの参照を取得し、その資格情報セットへのポインタを返します。

オープンファイルの資格情報¶

新しいファイルが開かれた場合、開くタスクの資格情報への参照が取得され、その参照がファイル構造体に f_cred の代わりに f_uid および f_gid。以前は file->f_uid および file->f_gid 現在は file->f_cred->fsuid および file->f_cred->fsgid.

アクセスは安全です。 f_cred RCUやロックを使用せずにアクセスできます。ファイル構造体の寿命を通じてポインタが変化せず、cred構造体の内容も変化しないからです（上記の例外を除く、タスク資格情報セクションを参照）。

「confused deputy」による権限昇格攻撃を防ぐため、開かれたファイルの後続操作におけるアクセス制御チェックでは、これらの資格情報を「current」の資格情報の代わりに使用する必要があります。ファイルがより権限の高いプロセスに渡されている可能性があるためです。

VFSが資格情報を使用するのを上書きする¶

特定の状況では、VFSが使用する資格情報を上書きすることが望ましく、これはのような関数を呼び出すことで実現できます。 vfs_mkdir() 異なる資格情報セットを使用して行われます。以下の場所で実行されます:

  • sys_faccessat().

  • do_coredump().

  • nfs4recover.c。

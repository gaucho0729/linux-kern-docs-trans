Key Request Service（キーリクエストサービス）¶

キーリクエストサービスは、キーリテンションサービス（参照 Kernel Key Retention Service）の一部です。このドキュメントでは、リクエストアルゴリズムの仕組みをより詳しく説明します。

プロセスは、カーネルがサービスをリクエストして呼び出すことによって開始されます。 request_key*():

struct key *request_key(const struct key_type *type,
                        const char *description,
                        const char *callout_info);

または:

struct key *request_key_tag(const struct key_type *type,
                            const char *description,
                            const struct key_tag *domain_tag,
                            const char *callout_info);

または:

struct key *request_key_with_auxdata(const struct key_type *type,
                                     const char *description,
                                     const struct key_tag *domain_tag,
                                     const char *callout_info,
                                     size_t callout_len,
                                     void *aux);

または:

struct key *request_key_rcu(const struct key_type *type,
                            const char *description,
                            const struct key_tag *domain_tag);

またはユーザースペースがrequest_keyシステムコールを呼び出すことによって開始されます：

key_serial_t request_key(const char *type,
                         const char *description,
                         const char *callout_info,
                         key_serial_t dest_keyring);

アクセスポイントの主な違いは、カーネルインターフェースがキーリングにキーリンクを張る必要がないため、キーリングにリンクせずに即座に破壊されることを防ぐことができます。カーネルインターフェースはキーポインタを直接返し、呼び出し元がキーリンクを破壊する責任を持ちます。

request_key_tag()コールは、カーネル内部のrequest_key()と同様ですが、ドメインタグを追加して、名前空間ごとにキーリングを分離し、グループ単位でキーリングを破壊できるようにします。

request_key_with_auxdata()コールは、request_key_tag()コールと同様ですが、アップコール側（デフォルトはNULL）に補助データを渡すことができます。これは、/sbin/request-keyを使用せず独自のアップコールメカニズムを定義したキーテイプにのみ有効です。

request_key_rcu()コールは、request_key_tag()コールと同様ですが、構築中のキーリングをチェックせず、構築不足のキーリングを構築試みません。

ユーザースペースインターフェースは、プロセスに関連するキーリングにキーリンクを張ることでキーリングが消失しないようにし、キーリングのシリアル番号を呼び出し元に返します。

以下の例は、キーテイプが独自のアップコールメカニズムを定義していないことを前提としています。もし独自のアップコールメカニズムを定義している場合は、/sbin/request-keyのフォークと実行に代わってそれらを適用する必要があります。

プロセス¶

リクエストは次の手順で進行します：

  1. プロセスAがrequest_key()を呼び出します（ユーザースペースのシステムコールはカーネルインターフェースを呼び出します）。

  2. request_key()は、プロセスのサブスクライブされたキーリングを検索して、適切なキーリングが存在するか確認します。存在する場合はキーリングを返します。存在しない場合でcallout_infoが設定されていない場合はエラーを返します。それ以外の場合は次のステップに進みます。

  3. request_key()は、Aがまだ必要なキーリングを持っていないことに気づき、以下の2つの要素を作成します：

    1. 要求されたタイプと説明の未インスタンス化キーコンテナU。

    2. キーコンテナUを参照し、プロセスAがキーコンテナUをインスタンス化・セキュリティ確保するコンテキストであり、関連するキーリクエストを満たすことができるキーコンテナV。

  4. request_key()は、認証キーコンテナVへのリンクを含む新しいセッションキーリングを持つプロセスをフォークして、/sbin/request-keyを実行します。

  5. /sbin/request-keyは、キーコンテナUに関連する権限を担います。

  6. /sbin/request-key は、実際にインスタンス化を行うための適切なプログラムを実行します。

  7. このプログラムは、A のコンテキストから別のキーや（例として Kerberos TGT キーなど）アクセスしたい場合があります。適切なキーリングを要求するだけで、キーリング検索はセッションキーリングが最下層に認証キー V を持っていることを記録します。

    これにより、プロセス A のキーリングを検索し、プロセス A の UID、GID、グループ、セキュリティ情報として検索を行い、プロセス A としての扱いを受けてキーワーク W を得ることができます。

  8. その後、プログラムはキーワーク W を参照として、キーワーク U をインスタンス化するために必要なデータを取得します（例として Kerberos サーバーに TGT を使って接続するなど）し、キーワーク U をインスタンス化します。

  9. キーワーク U をインスタンス化する際、認証キー V は自動的に失効させられ、再度使用できなくなります。

  10. その後、プログラムは 0 を返して終了し、request_key() はキー V を削除して、キー U を呼び出し元に返します。

これはさらに拡張されます。キーワーク W（上記のステップ 7）が存在しなかった場合、キーワーク W は未インスタンス化で作成され、別の認証キー（X）が作成され（ステップ 3 に従い）、別の /sbin/request-key のコピーが生成されます（ステップ 4 に従い）；ただし、認証キー X で指定されたコンテキストは、認証キー V の場合と同様にプロセス A です。

これは、プロセス A のキーリングを単純に /sbin/request-key にアタッチできない理由は、（a）execve が2つのキーリングを破棄し、（b）UID/GID/グループ情報が一貫して必要だからです。

否定的インスタンス化と拒否¶

認証キーの保有者であれば、構築中のキーよりも否定的インスタンス化を行うことが可能です。これは一時的なプレースホルダーであり、存在中にキーアクセスを試みると ENOKEY または指定されたエラーで失敗します。

これは、取得不可能なキーよりも /sbin/request-key プロセスを繰り返し生成しないことを防ぐための仕組みです。

/sbin/request-key プロセスが 0 以外で終了したり、シグナルで終了した場合、構築中のキーリングは短時間の間自動的に否定的インスタンス化されます。

検索アルゴリズム¶

特定のキーリングの検索は以下の手順で行われます：

  1. キーマネジメントコードがキーやキーリングを検索する際（keyring_search_rcu）、まず検索を開始するキーリングに対して key_permission(SEARCH) を呼び出します。この処理が権限を拒否した場合、それ以降の検索は行われません。

  2. そのキーリング内の非キーリングキーをすべて検討し、どのキーも指定された基準に合致する場合、そのキーに対してkey_permission(SEARCH)を呼び出して、キーが検索許可されているか確認します。許可されている場合はそのキーを返します。許可されていない場合は検索を継続し、現在のエラー設定よりも優先度が高い場合にエラーコードを保持します。

  3. 次に、現在検索中のキーリング内のキーリング型のキーを検討します。各キーリングに対してkey_permission(SEARCH)を呼び出し、許可が得られた場合、再帰的に実行し、そのキーリングに対してステップ(2)と(3)を実行します。

使用許可が与えられている有効なキーが見つかると、プロセスは即座に停止します。以前のマッチ試行からのエラーは破棄され、そのキーが返されます。

request_key()が呼び出される場合、CONFIG_KEYS_REQUEST_CACHE=yの場合は、まずタスクごとの1キーキャッシュを検索してマッチするキーを確認します。

search_process_keyrings()が呼び出される場合、以下の検索を実行し、成功するまで続けます。

  1. 存在する場合、プロセスのスレッドキーリングを検索します。

  2. 存在する場合、プロセスのプロセスキーリングを検索します。

  3. プロセスのセッションキーリングを検索します。

  4. プロセスがrequest_key()の認可キーに関連する権限を取得している場合、以下の検索が行われます。

    1. 存在する場合、呼び出し元プロセスのスレッドキーリングを検索します。

    2. 存在する場合、呼び出し元プロセスのプロセスキーリングを検索します。

    3. 呼び出し元プロセスのセッションキーリングを検索します。

どれかが成功すると、すべての待機中のエラーは破棄され、見つかったキーが返されます。CONFIG_KEYS_REQUEST_CACHE=yの場合は、そのキーがタスクごとのキャッシュに格納され、以前のキーは置き換えられます。キャッシュは終了時またはユーザースペースの再開直前にクリアされます。

すべての検索が失敗した場合、最高優先度のエラーで全体が失敗します。複数のエラーがLSMから発生している可能性があることに注意してください。

エラーの優先度は以下の通りです。

EKEYREVOKED > EKEYEXPIRED > ENOKEY

EACCES/EPERMは、特定のキーリングの直接検索時に、基盤のキーリングがSearch許可を提供していない場合にのみ返されます。

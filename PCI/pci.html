1. Linux PCIドライバの作成方法¶

著者

  • Martin Mares <mj@ucw.cz>

  • Grant Grundler <grundler@parisc-linux.org>

PCIの世界は広大で、（ほぼ）すべてが不快な驚きに満ちています。各CPUアーキテクチャが異なるチップセットを実装し、PCIデバイスごとに異なる要件（えむアール、『機能』）があるため、Linuxカーネル内のPCIサポートは、望むほど単純ではありません。この短い資料では、すべてのドライバ作成者にLinuxのPCIデバイスドライバAPIを紹介します。

より完全なリソースは、Jonathan Corbet、Alessandro Rubini、Greg Kroah-Hartmanによる『Linux Device Drivers』の第3版です。LDD3はクリエイティブ・コモンズライセンスの下で無料で入手可能です： https://lwn.net/Kernel/LDD3/.

ただし、すべてのドキュメントは「ビット腐敗」の影響を受ける可能性があります。記述と異なる場合は、ソースコードを参照してください。

Linux PCI APIに関する質問/コメント/パッチは、「Linux PCI」<linux-pci@atrey.karlin.mff.cuni.cz> メーリングリストに送信してください。

1.1. PCIドライバの構造¶

PCIドライバはpci_register_driver()を通じてシステム内のPCIデバイスを「発見」します。実際には逆です。PCI汎用コードが新しいデバイスを発見すると、マッチングした「説明」を持つドライバに通知されます。詳細は以下で説明します。

pci_register_driver()はデバイスのプローブを主にPCIレイヤーに任せ、オンラインでのデバイス挿抜をサポートするため、ホットプラグ可能なPCI、CardBus、Express-Cardを単一のドライバでサポートします。pci_register_driver()呼び出しには、関数ポインタのテーブルを渡す必要があり、これによりドライバの高レベルな構造が決まります。

ドライバがPCIデバイスを認識し、所有権を取得した後、以下の初期化を行う必要があります：

  • デバイスを有効にする

  • MMIO/IOPリソースを要求する

  • DMAマスクサイズを設定する（コヒーレントDMAおよびストリーミングDMAの両方について）

  • 共有制御データを割り当てて初期化する（pci_allocate_coherent()）

  • デバイス構成空間にアクセスする（必要に応じて）

  • IRQハンドラを登録する（request_irq())

  • 非PCI部分（LAN/SCSI/etc.のチップの一部）を初期化する

  • DMA/処理エンジンを有効にする

デバイスを使用が終了し、モジュールがアンロードされる場合、ドライバは以下の手順を実行する必要があります：

  • デバイスがIRQを生成しないように無効にする

  • IRQを解放する（free_irq())

  • すべてのDMA活動を停止する

  • DMAバッファ（ストリーミングおよびコヒーレント）を解放する

  • 他のサブシステム（例：scsiまたはnetdev）から登録を解除する

  • MMIO/IOPリソースを解放する

  • デバイスを無効にする

これらのトピックの多くは次のセクションで説明します。その他についてはLDD3または<linux/pci.h>を参照してください。

PCIサブシステムが構成されていない場合(CONFIG_PCIが設定されていない)、以下の説明するPCI関数は、ドライバ内での多くのifdefを避けるために、インライン関数として定義されるか、または適切なエラーコードを返すだけの空関数として定義されます。

1.2. pci_register_driver()呼び出し¶

PCIデバイスドライバが呼び出す pci_register_driver() 初期化時にドライバを記述する構造体へのポインタで、struct pci_driver):

struct pci_driver¶

PCIドライバ構造体

定義

struct pci_driver {
  struct list_head        node;
  const char              *name;
  const struct pci_device_id *id_table;
  int (*probe)(struct pci_dev *dev, const struct pci_device_id *id);
  void (*remove)(struct pci_dev *dev);
  int (*suspend)(struct pci_dev *dev, pm_message_t state);
  int (*resume)(struct pci_dev *dev);
  void (*shutdown)(struct pci_dev *dev);
  int (*sriov_configure)(struct pci_dev *dev, int num_vfs);
  const struct pci_error_handlers *err_handler;
  const struct attribute_group **groups;
  struct device_driver    driver;
  struct pci_dynids       dynids;
  ANDROID_KABI_RESERVE(1);
  ANDROID_KABI_RESERVE(2);
  ANDROID_KABI_RESERVE(3);
  ANDROID_KABI_RESERVE(4);
};

メンバ

node

ドライバ構造体の一覧。

name

ドライバ名。

id_table

ドライバが関心を持つデバイスIDのテーブルへのポインタ。ほとんどのドライバはMODULE_DEVICE_TABLE(pci,…)を使用してこのテーブルをエクスポートすべきです。

probe

このプローブ関数は、pci_register_driver()の実行中に既存のデバイスや、新しいデバイスが挿入された後に、IDテーブルに一致し、他のドライバによって「所有」されていないすべてのPCIデバイスに対して呼び出されます。この関数には、IDテーブルのエントリに一致する各デバイスの「struct pci_dev *」が渡されます。ドライバがデバイスの「所有権」を取得する場合、この関数はゼロを返します。それ以外の場合は、負の数のエラーコードを返します。プローブ関数は常にプロセスコンテキストから呼び出されるため、スリープが可能です。

remove

remove()関数は、このドライバが処理しているデバイスが除去されるたびに呼び出されます（ドライバの登録解除中に起きますか、またはホットプラグ可能なスロットから手動で抜き取った場合）。remove関数は常にプロセスコンテキストから呼び出されるため、スリープが可能です。

suspend

デバイスを低電力状態に設定する。

resume

低電力状態からデバイスを復元する。(PCI電源管理の説明と関連する関数については、 PCI Power Management を参照してください。)

shutdown

reboot_notifier_list（kernel/sys.c）にハックする。アイドル中のDMA操作を停止するためのものです。Wake-on-LAN（NIC）を有効化するのに有用で、再起動前にデバイスの電源状態を変更する場合にも使用されます。例: drivers/net/e100.c。

sriov_configure

sysfsの「sriov_numvfs」ファイルを介して有効にするVFの数を設定するオプションのドライバコールバック。

err_handler

参照 PCIエラー回復

groups

Sysfs属性グループ。

driver

ドライバモデル構造体。

dynids

動的に追加されたデバイスIDの一覧。

IDテーブルは、 struct pci_device_id すべてゼロのエントリで終わるエントリの配列です。静的const定義が一般的に推奨されます。

struct pci_device_id¶

PCIデバイスID構造体

定義

struct pci_device_id {
  __u32 vendor, device;
  __u32 subvendor, subdevice;
  __u32 class, class_mask;
  kernel_ulong_t driver_data;
};

メンバ

vendor

一致させるベンダID（またはPCI_ANY_ID）

device

一致させるデバイスID（またはPCI_ANY_ID）

subvendor

一致させるサブシステムベンダID（またはPCI_ANY_ID）

subdevice

一致させるサブシステムデバイスID（またはPCI_ANY_ID）

class

デバイスのクラス、サブクラス、および「インターフェース」を一致させる必要があります。PCIローカルバス仕様書の付録Dや、include/linux/pci_ids.hを参照してください。ほとんどのドライバでは、ベンダー/デバイスの指定だけで十分です。

class_mask

クラスフィールドのどのサブフィールドを比較するかを制限します。drivers/scsi/sym53c8xx_2/にある例を参照してください。

driver_data

ドライバ専用のデータ。ほとんどのドライバではdriver_dataフィールドを使用する必要はありません。ベストプラクティスは、driver_dataを静的リストのデバイスタイプのインデックスとして使用することです。ポインタとして使用するのではなく。

ほとんどのドライバでは PCI_DEVICE() または PCI_DEVICE_CLASS() pci_device_idテーブルを設定するだけで十分です。

新しいPCI IDは、以下のようにドライバのpci_idsテーブルにランタイムで追加できます:

echo "vendor device subvendor subdevice class class_mask driver_data" > \
/sys/bus/pci/drivers/{driver}/new_id

すべてのフィールドは16進数値として渡されます（0xの先頭は不要）。ベンダーとデバイスフィールドは必須で、他のフィールドは任意です。ユーザーは必要なだけの任意フィールドを渡すだけでよいです:

  • サブベンダーおよびサブデバイスフィールドはデフォルトでPCI_ANY_ID（FFFFFFFF）になります

  • クラスおよびクラスマスクフィールドはデフォルトで0になります

  • driver_dataはデフォルトで0ULになります。

driver_dataは、ドライバで定義されたすべてのpci_device_idエントリが使用する値と一致する必要があります。すべてのpci_device_idエントリが非ゼロのdriver_data値を持つ場合、driver_dataフィールドは必須になります。

追加後、ドライバのプローブルーチンが、その（新たに更新された）pci_idsリストに記載されている未割り当てのPCIデバイスに対して呼び出されます。

ドライバが終了する際には、単に pci_unregister_driver() を呼び出すだけで、PCIレイヤーがドライバが処理するすべてのデバイスのremoveハックを自動的に呼び出します。

1.2.1. ドライバ関数/データの「属性」¶

適切な場所で初期化およびクリーンアップ関数をマークしてください（対応するマクロは<linux/init.h>に定義されています）:

__init

初期化コード。ドライバが初期化した後は破棄されます。

__exit

終了コード。モジュールでないドライバでは無視されます。
上記の属性をいつどこで使用するかのヒント:

  • 以下の module_init()/module_exit() 関数（およびこれらの関数のみから呼び出されるすべての初期化関数）は__init/__exitとしてマークする必要があります。

  • マークしないでください struct pci_driver.

  • どのマーキングを使用するか不明な場合は、関数をマークしない方が良いです。関数を誤ってマークするより、関数をマークしない方が良いです。

1.3. PCIデバイスを手動で検出する方法¶

PCIドライバは、PCIデバイスを検出するためにpci_register_driver()インターフェースを使用しない理由が本当に強い必要があります。複数のドライバがPCIデバイスを制御する主な理由は、1つのPCIデバイスが複数の異なるハードウェアサービスを実装しているためです。例: シリアル/パラレルポート/フロッピードライブコントローラーの組み合わせ。

手動での検索は以下の構造を使用できます:

ベンダーおよびデバイスIDによる検索:

struct pci_dev *dev = NULL;
while (dev = pci_get_device(VENDOR_ID, DEVICE_ID, dev))
        configure_device(dev);

クラスIDで検索（同様の方法で反復処理）:

pci_get_class(CLASS_ID, dev)

ベンダー/デバイスとサブシステムベンダー/デバイスIDの両方で検索:

pci_get_subsys(VENDOR_ID,DEVICE_ID, SUBSYS_VENDOR_ID, SUBSYS_DEVICE_ID, dev).

VENDOR_IDまたはDEVICE_IDの代わりに、定数PCI_ANY_IDを使用できます。これにより、特定のベンダーからすべてのデバイスを検索できるようになります。

これらの関数はホットプラグ対応です。返すpci_devの参照カウントをインクリメントします。最終的に（モジュールのアンロード時に可能であれば）、これらのデバイスの参照カウントを減らすために pci_dev_put().

1.4. デバイス初期化手順¶

導入部で述べたように、ほとんどのPCIドライバーはデバイス初期化に以下の手順が必要です:

  • デバイスを有効にする

  • MMIO/IOPリソースを要求する

  • DMAマスクサイズを設定する（コヒーレントDMAおよびストリーミングDMAの両方について）

  • 共有制御データを割り当てて初期化する（pci_allocate_coherent()）

  • デバイス構成空間にアクセスする（必要に応じて）

  • IRQハンドラを登録する（request_irq())

  • 非PCI部分（LAN/SCSI/etc.のチップの一部）を初期化する

  • DMA/処理エンジンを有効化します。

ドライバーはいつでもPCIコンフィギュレーション空間レジスタにアクセスできます。（ほぼ常に。BISTを実行中はコンフィギュレーション空間が消失するかもしれませんが、その場合、PCIバスマスター_ABORTが発生し、コンフィギュレーション読み込みはゴミデータを返します）。

1.4.1. PCIデバイスを有効化します¶

デバイスレジスタにアクセスする前に、ドライバーは以下の関数を呼び出してPCIデバイスを有効化する必要があります pci_enable_device()。これは以下の処理を行います:

  • デバイスがスリープ状態だった場合、それを起動します。

  • BIOSが未設定の場合、デバイスのI/Oおよびメモリ領域を割り当てます。

  • BIOSが未設定の場合、IRQを割り当てます。

注意

pci_enable_device() 失敗する可能性があります！戻り値を確認してください。

警告

OSのバグ: リソースの割り当てを有効化する前に確認していません。より論理的な順序としては、pci_request_resources()を呼び出してから pci_enable_device()を呼び出すのが適切です。現在、デバイスドライバーは2つのデバイスが同じ範囲を割り当てられた場合のバグを検出できません。これは一般的な問題ではなく、近々修正される可能性は低いです。

この問題は以前から議論されてきましたが、2.6.19以降に変更されていません: https://lore.kernel.org/r/20060302180025.GC28895@flint.arm.linux.org.uk/

pci_set_master() PCI_COMMANDレジスタのバスマスタービットを設定してDMAを有効化します。BIOSが不正な値に設定した場合、レイテンシータイマービットも修正します。 pci_clear_master() バスマスタービットをクリアしてDMAを無効化します。

PCIデバイスがPCIメモリライトインバリデートトランザクションを使用できる場合、 pci_set_mwi()を呼び出してください。これにより、Mem-Wr-InvalのPCI_COMMANDビットが有効になり、キャッシュラインサイズレジスタも正しく設定されます。戻り値を確認してください。 pci_set_mwi() はすべてのアーキテクチャやチップセットがMemory-Write-Invalidateをサポートするとは限りません。代替として、Mem-Wr-Invalが望ましいが必須ではない場合、 pci_try_set_mwi() を呼び出して、システムがMem-Wr-Invalを有効化するよう最大限に努力します。

1.4.2. MMIO/IOPリソースを要求する¶

メモリ（MMIO）およびI/Oポートアドレスは、PCIデバイスのコンフィギュレーションスペースから直接読み取ってはいけません。pci_dev構造体の値を使用してください。PCI「バスアドレス」はアーキテクチャ/チップセット固有のカーネルサポートにより「ホスト物理」アドレスに再マッピングされる可能性があります。

参照 io_mapping関数 デバイスレジスタやデバイスメモリにアクセスする方法について。

デバイスドライバーは呼び出す必要があります pci_request_region() 他のデバイスが同じアドレスリソースを使用していないかを確認するために。逆に、ドライバーは呼び出す必要があります pci_release_region() 呼び出す後 pci_disable_device()2つのデバイスが同じアドレス範囲で衝突することを防ぐためのアイデアです。

ヒント

上記のOS BUGコメントを参照してください。現在（2.6.19）、ドライバーは呼び出す後でMMIOおよびIOポートリソースの利用可能性を確認できます pci_enable_device().

汎用的な pci_request_region() request_mem_region()（MMIO範囲用）とrequest_region()（IOポート範囲用）です。"通常"のPCI BARで記述されないアドレスリソースにはこれらを使用してください。

以下の pci_request_selected_regions() も参照してください。

1.4.3. DMAマスクサイズを設定する¶

注意

以下が意味不明な場合は、 汎用デバイスを使用した動的DMAマッピングをご参照ください。このセクションは、ドライバーがデバイスのDMA能力を示す必要があるという_reminder_であり、DMAインターフェースの公式な情報源ではありません。

すべてのドライバーは、PCIバスマスターのDMA能力（例：32ビットまたは64ビット）を明示的に示す必要があります。ストリーミングデータ用に32ビット以上のバスマスター能力を持つデバイスでは、pci_set_dma_mask()を適切なパラメータとともに呼び出してこの能力を「登録」する必要があります。これにより、システムRAMが4G物理アドレス以上にあるシステムでのDMA効率が向上します。

すべてのPCI-XおよびPCIe準拠デバイスのドライバーは、64ビットDMAデバイスであるため、pci_set_dma_mask()を呼び出す必要があります。

同様に、デバイスがシステムRAMの4G物理アドレス以上で「一貫したメモリ」を直接アドレス可能である場合、pci_set_consistent_dma_mask()を呼び出してこの能力を「登録」する必要があります。これには、すべてのPCI-XおよびPCIe準拠デバイスのドライバーが含まれます。多くの64ビット「PCI」デバイス（PCI-X以前）や一部のPCI-Xデバイスは、ストリーミングデータ用に64ビットDMAをサポートしていますが、制御用の「一貫した」データにはサポートしていない場合があります。

1.4.4. 共有制御データの設定¶

DMAマスクが設定されると、ドライバーは「一貫した」（つまり共有）メモリを割り当てることができます。詳細については、 汎用デバイスを使用した動的DMAマッピング をご参照ください。このセクションは、デバイスでDMAを有効にする前にこれを実行する必要があるという_reminder_です。

1.4.5. デバイスレジスタを初期化する¶

一部のドライバーでは、特定の「機能」フィールドをプログラミングするか、または他の「ベンダー固有」レジスタを初期化またはリセットする必要があります。例として、未処理の割り込みをクリアするなど。

1.4.6. IRQハンドラを登録する¶

呼び出す request_irq() はここでの最後のステップですが、これはしばしばデバイスの初期化の別の中間ステップに過ぎません。このステップは、デバイスが使用可能になるまでdeferred（遅延）されることがよくあります。

すべてのIRQライン用の割り込みハンドラはIRQF_SHAREDで登録し、devidを使用して割り込みをデバイスにマッピングする必要があります（すべてのPCI割り込みラインが共有可能であることを覚えておいてください）。

request_irq() 割り込みハンドラとデバイスハンドルを割り込み番号に関連付けます。歴史的に割り込み番号はPCIデバイスから割り込みコントローラーへ走るIRQラインを表します。MSIおよびMSI-X（以下で詳しく説明）では、割り込み番号はCPUの「ベクター」を表します。

request_irq() 割り込みを有効にもします。割り込みハンドラを登録する前に、デバイスが静止状態であり、待機中の割り込みがないことを確認してください。

MSIおよびMSI-XはPCIの機能です。どちらも「メッセージシグナリング割り込み（Message Signaled Interrupts）」であり、DMAによるローカルAPICへの書き込みを通じてCPUに割り込みを送信します。MSIとMSI-Xの根本的な違いは、複数の「ベクター」を割り当てる方法です。MSIは連続するベクターのブロックを必要としますが、MSI-Xは複数の個別のベクターを割り当てられます。

MSI機能を有効にするには、pci_alloc_irq_vectors()関数を呼び出す前にPCI_IRQ_MSIおよび/またはPCI_IRQ_MSIXフラグを指定します。 request_irq().これにより、PCIサポートがCPUベクター情報をPCIデバイスの機能レジスタに書き込みます。多くのアーキテクチャ、チップセット、またはBIOSはMSIまたはMSI-Xをサポートしていないため、PCI_IRQ_MSIとPCI_IRQ_MSIXフラグのみでpci_alloc_irq_vectorsを呼び出すと失敗する場合があります。そのため、常にPCI_IRQ_LEGACYフラグも指定することをお勧めします。

MSI/MSI-XとレガシINTxに異なる割り込みハンドラを持つドライバは、pci_dev構造体のmsi_enabledおよびmsix_enabledフラグに基づいて正しいハンドラを選択する必要があります。

MSIを使用する2つの主要な理由があります：

  1. MSIは定義上排他的な割り込みベクターです。これにより、割り込みハンドラはデバイスが割り込みを発生させたことを確認する必要がありません。

  2. MSIはDMA/IRQ競合条件を回避します。DMAがホストメモリに送信される際、MSIが届くとホストCPUがその内容を確実に確認できます。これはデータ整合性と古い制御データの回避に重要であり、この保証によりドライバはDMAストリームのMMIO読み込みを省略できます。

drivers/infiniband/hw/mthca/またはdrivers/net/tg3.cを参照してください。これらはMSI/MSI-Xの使用例です。

1.5. PCIデバイスのシャットダウン¶

PCIデバイスドライバがアンロードされる際には、以下のステップを実行する必要があります：

  • デバイスがIRQを生成しないように無効にする

  • IRQを解放する（free_irq())

  • すべてのDMA活動を停止する

  • DMAバッファ（ストリーミングおよび一貫性バッファ）を解放します

  • 他のサブシステム（例：scsiまたはnetdev）から登録を解除する

  • デバイスがMMIO/IOポートアドレスに応答しないようにします

  • MMIO/IOポートリソースを解放します

1.5.1. デバイス上の割り込みを停止します¶

この操作方法はチップ/デバイス固有です。実施しない場合、IRQが他のデバイスと共有されている場合（かつそれのみの場合）に、「スクリームインター ループ（screaming interrupt）」の可能性が生じます。

共有IRQハンドラが「解除」された後も、同じIRQラインを使用する他のデバイスはIRQを有効にしたままです。したがって、「解除」されたデバイスがIRQラインをアサートした場合、システムはそのIRQラインを残っているデバイスがアサートしたと誤って処理します。他のデバイスがIRQを処理しない場合、システムはIRQが処理されないことを認識するまで（10万回の反復後）「停止」状態に陥ります。共有IRQがマスクされると、残っているデバイスは正しく動作しなくなります。これは望ましくない状況です。

MSIまたはMSI-Xを使用するのがもう一つの選択肢です（利用可能であれば）。MSIおよびMSI-Xは排他的な割り込みとして定義されており、「スクリームインター ループ」問題には影響を受けません。

1.5.2. IRQを解放する¶

デバイスが静止状態になった（IRQがもう発生しない）後、以下を呼び出せます free_irq()。この関数は、すべての待機中のIRQが処理されたら制御を戻し、「解除」したドライバのIRQハンドラをそのIRQから分離し、他のデバイスが使用していない場合にIRQを解放します。

1.5.3. すべてのDMA活動を停止する¶

DMA操作を停止する前にDMA制御データの解放を試行するのは極めて重要です。これを実施しないとメモリ破壊、システム停止、一部のチップセットではハードウェアクラッシュを引き起こす可能性があります。

IRQを停止した後にDMAを停止するようにすることで、IRQハンドラがDMAエンジンを再起動する競合状態を回避できます。

このステップは見た目には明らかで簡単ですが、過去にはいくつかの「成熟した」ドライバがこのステップを正しく実装していませんでした。

1.5.4. DMAバッファを解放する¶

DMAが停止した後は、ストリーミングDMAをまずクリーンアップします。つまり、データバッファをアンマップし、アップストリーム所有者がある場合はバッファを返却します。

次に、制御データを含む「一貫性」バッファをクリーンアップします。

参照 汎用デバイスを使用した動的DMAマッピング アンマップインターフェースの詳細についてはこちら。

1.5.5. 他のサブシステムから登録を解除する¶

ほとんどの低レベルPCIデバイスドライバはUSB、ALSA、SCSI、NetDev、Infinibandなどの他のサブシステムをサポートしています。ドライバが他のサブシステムからリソースを失っている可能性を確認してください。このような場合、サブシステムがすでにロードされたドライバを呼び出す際に「Oops（パニック）」が発生します。

1.5.6. デバイスがMMIO/IOポートアドレスに応答しないようにする¶

io_unmap()でMMIOまたはIOポートリソースを解除し、その後 pci_disable_device()を呼び出します。これは pci_enable_device()の逆対応です。呼び出した後は、デバイスレジスタへのアクセスを行わないでください。 pci_disable_device().

1.5.7. MMIO/IOポートリソースを解放する¶

を呼び出して、MMIOまたはIOポート範囲を利用可能にします。これを実施しないと、ドライバの再ロードができない状態になります。 pci_release_region() 。

1.6. PCI構成領域にアクセスする方法¶

使用できます pci_(read|write)_config_(byte|word|dword) を、次の構造体で表されるデバイスの構成領域にアクセスするために使用できます struct pci_dev *これらの関数は、成功した場合は0を返し、エラー コード (PCIBIOS_…) でテキスト文字列に変換できます。ほとんどのドライバは、有効なPCIデバイスへのアクセスが失敗しないことを期待しています。

struct pci_devが利用できない場合は、次の関数を呼び出せます pci_bus_(read|write)_config_(byte|word|dword) を、そのバス上の指定されたデバイスとファンクションにアクセスします。

標準部分のフィールドにアクセスする場合は、<linux/pci.h>で宣言された場所とビットのシンボリック名を使用してください。

拡張PCIキャパビリティレジスタにアクセスする場合は、 pci_find_capability() 特定のキャパビリティを呼び出すだけで、対応するレジスタブロックを自動的に見つけてくれます。

1.9. ベンダーおよびデバイス識別¶

include/linux/pci_ids.hに新しいデバイスまたはベンダーIDを追加しないでください。これらが複数のドライバで共有されている場合に限り追加してください。役に立つ場合はドライバ内にプライベート定義を追加できますが、それ以外は単純な16進数定数を使用してください。

デバイスIDは、ベンダーが制御する任意の16進数であり、通常は単一の場所（pci_device_idテーブル）でのみ使用されます。

新しいベンダー/デバイスIDを提出する場合は、必ず https://pci-ids.ucw.cz/にご提出ください。pci.idsファイルのミラーリングがこちらにあります https://github.com/pciutils/pciids.

1.11. MMIO領域と「書き込みポスティング」¶

I/Oポート領域からMMIO領域へのドライバ変換には、いくつかの追加変更が必要です。特に「書き込みポスティング」の処理が必要です。多くのドライバー（例: tg3、acenic、sym53c8xx_2）はすでにこれを実装しています。I/Oポート領域では、CPUが処理を続ける前に書き込みトランザクションがPCIデバイスに到達することを保証しています。MMIO領域では、CPUがトランザクションがPCIデバイスに到達する前に処理を続けることができます。ハードウェアのエキスパートはこれを「書き込みポスティング」と呼び、CPUに書き込み完了が「ポスト」される状態を指します。

したがって、タイミングに敏感なコードでは、CPUが他の処理を実行する前に待機する必要がある場所にreadl()を追加する必要があります。I/Oポート領域では、古典的な「ビットバッキング」シーケンスがI/Oポート領域では十分に機能します。

for (i = 8; --i; val >>= 1) {
        outb(val & 1, ioport_reg);      /* write bit */
        udelay(10);
}

MMIO領域では同じシーケンスは以下のようになります：

for (i = 8; --i; val >>= 1) {
        writeb(val & 1, mmio_reg);      /* write bit */
        readb(safe_mmio_reg);           /* flush posted write */
        udelay(10);
}

「safe_mmio_reg」はデバイスの正しい動作に干渉しない副作用を持たないことが重要です。

注意すべきもう一つのケースはPCIデバイスのリセットです。PCIコンフィギュレーション領域の読み込みでwritel()をフラッシュしてください。これにより、すべてのプラットフォームでPCIマスター_ABORTを適切に処理できます。PCIデバイスがreadl()に応答しないと予想される場合です。ほとんどのx86プラットフォームではMMIO読み込みがマスター_ABORT（Soft Fail）を許容し、無効値（例: ~0）を返します。しかし多くのRISCプラットフォームではクラッシュ（Hard Fail）します。

7. PCIエラー回復¶

著者

  • Linas Vepstas <linasvepstas@gmail.com>

  • Richard Lary <rlary@us.ibm.com>

  • Mike Mason <mmlnx@us.ibm.com>

多くのPCIバス制御器は、バス上でさまざまなハードウェアPCIエラーを検出できます。例えばデータバスやアドレスバスのパリティエラー、SERRおよびPERRエラーなどです。一部の高度なチップセットはこれらのエラーを処理できます。これはPCI-Eチップセットや、IBM Power4、Power5、Power6ベースのpSeriesボックスに搭載されたPCIホストブリッジが含まれます。一般的な対処方法として、影響を受けたデバイスを切断し、すべてのI/Oを停止します。切断の目的はシステムの破壊を防ぐためで、たとえばDMAによる「ワイルドな」アドレスへのアクセスによるシステムメモリの破壊を回避します。通常、再接続メカニズムも提供されており、影響を受けたPCIデバイスをリセットして正常な状態に戻します。リセットフェーズでは、影響を受けたドライバとPCI制御器チップの間で協調が必要です。このドキュメントでは、バス切断をドライバに通知し、エラー回復を行うための汎用APIについて説明します。このAPIは現在、2.6.16以降のカーネルで実装されています。

報告および回復は複数のステップで行われます。まず、PCIハードウェアエラーによりバスが切断した場合、そのイベントはすぐにすべての影響を受けたドライバに報告されます。これはマルチファンクションカード上の複数のドライバインスタンスにも適用されます。これにより、ドライバがスピンロック内で死lockingを避けることができ、I/O空間レジスタの変化を待つことなく、必要なI/Oを遅延処理できます。また、ドライバが必要なI/Oをdeferする機会も与えます。

次に、回復は複数の段階で行われます。複数のファンクションを持つデバイスを処理する必要があるため、多くの複雑さが生じます。最初の段階では、各ドライバがどの種類のリセットを希望するかを示すことができます。選択肢は、I/Oの再有効化のシンプルな再起動か、スロットリセットを要求するかです。

もしあなどのドライバがスロットリセットを要求すれば、それが実行されます。

リセットおよび/またはI/Oの再有効化後、すべてのドライバに再び通知が送られ、必要なデバイスの設定/構成を行うことができます。これらの処理がすべて完了した後、最終的な「通常操作を再開」イベントが送信されます。

カーネルベースの実装を選択した最大の理由は、ストレージメディアに接続されたPCIデバイスのバス切断処理を扱う必要があったことです。特に、ルートファイルシステムを保持するデバイスからの切断処理が必要でした。ルートファイルシステムが切断された場合、ユーザー空間のメカニズムは復旧を完了するためには多くの手間をかける必要があります。現在のLinuxファイルシステムのほぼすべては、下位ブロックデバイスからの切断・再接続に対して耐性がありません。対照的に、バスエラーはデバイスドライバで簡単に管理できます。実際、ほとんどのデバイスドライバは類似の復旧手順をすでに処理しており、たとえばSCSIジェネリックレイヤーはSCSIバスエラーおよびSCSIバスリセットの処理にすでに多くのメカニズムを提供しています。

7.1. 詳細設計¶

Ben Herrenschmidtとの公開メールディスカッションに基づく設計および実装の詳細は、2005年4月5日頃にまとめられています。

エラー回復APIのサポートは、新しいフィールドを介してドライバに構造体形式で公開されます。 struct pci_driverドライバがこの構造体を提供しない場合、「非認識」ドライバとされ、実際の回復手順はプラットフォーム依存になります。arch/powerpcの実装ではPCIホットプラグの削除/追加をシミュレートします。

この構造体の形式は以下の通りです：

struct pci_error_handlers
{
        int (*error_detected)(struct pci_dev *dev, pci_channel_state_t);
        int (*mmio_enabled)(struct pci_dev *dev);
        int (*slot_reset)(struct pci_dev *dev);
        void (*resume)(struct pci_dev *dev);
};

可能なチャネル状態は以下の通りです：

typedef enum {
        pci_channel_io_normal,  /* I/O channel is in normal state */
        pci_channel_io_frozen,  /* I/O to channel is blocked */
        pci_channel_io_perm_failure, /* PCI card is dead */
} pci_channel_state_t;

可能な返却値は以下の通りです：

enum pci_ers_result {
        PCI_ERS_RESULT_NONE,        /* no result/none/not supported in device driver */
        PCI_ERS_RESULT_CAN_RECOVER, /* Device driver can recover without slot reset */
        PCI_ERS_RESULT_NEED_RESET,  /* Device driver wants slot to be reset. */
        PCI_ERS_RESULT_DISCONNECT,  /* Device has completely failed, is unrecoverable */
        PCI_ERS_RESULT_RECOVERED,   /* Device driver is fully recovered and operational */
};

ドライバはすべてのコールバックを実装する必要はありませんが、実装する場合はerror_detected()を必ず実装しなければなりません。コールバックが実装されていない場合、対応する機能はサポートされていないとみなされます。たとえば、mmio_enabled()とresume()が実装されていない場合、ドライバは直接的な回復を行わず、スロットリセットを必要とするものとみなされます。通常、ドライバはスロットリセットについて知る必要があります。

プラットフォームがPCIエラーイベントから回復する際の具体的な手順はプラットフォーム依存しますが、以下の一般的な手順に従います。

7.1.1. STEP 0: エラーイベント¶

PCIバスエラーがPCIハードウェアによって検出されます。powerpcでは、スロットが隔離され、すべてのI/Oがブロックされます。すべての読み取りは0xffffffffを返し、すべての書き込みは無視されます。

7.1.2. STEP 1: 通知¶

プラットフォームは、エラーに影響を受けたすべてのドライバの各インスタンスに対してerror_detected()コールバックを呼び出します。

この時点で、デバイスがもうアクセスできなくなる可能性があります（プラットフォームにより異なります。powerpcではスロットが電源投入時に隔離されます）。I/Oの失敗によりドライバーがすでにエラーを「認識」しているかもしれませんが、これは適切な「同期ポイント」です。つまり、ドライバーが未完了の処理（タイマーやなんでも）を完了するのを待つ機会を提供し、セマフォを取得したり、スケジュールを調整したりするなど、デバイスを操作しない限り何でもできます。この関数内で、および関数が戻る後、ドライバーは新しいIOを実行すべきではありません。タスクコンテキストで呼び出されます。これは「静止ポイント」のようなものです。このドキュメントの最後に記載されている割り込みに関する注意点も参照してください。

このシステムに参加するすべてのドライバーはこの呼び出しを実装しなければなりません。ドライバーは次の結果コードのいずれかを返さなければなりません：

  • PCI_ERS_RESULT_CAN_RECOVER

    ドライバーがハードウェアをIOを叩くことで回復できる可能性があると考える場合、または診断情報を取得する機会を求める場合にこのコードを返します（下記のmmio_enableを参照してください）。

  • PCI_ERS_RESULT_NEED_RESET

    スロットのリセットなしでは回復できないと判断した場合にこのコードを返します。

  • PCI_ERS_RESULT_DISCONNECT

    回復を一切行いたくない場合にこのコードを返します。

次のステップはドライバーが返す結果コードに依存します。

すべてのドライバーがPCI_ERS_RESULT_CAN_RECOVERを返した場合、プラットフォームはスロットのIOを再有効化する必要があります（プラットフォームがスロットを隔離しない場合は何も行いません）。回復はSTEP 2（MMIO有効化）に進みます。

どのドライバーもスロットリセットを要求した場合（PCI_ERS_RESULT_NEED_RESETを返した場合）、回復はSTEP 4（スロットリセット）に進みます。

プラットフォームがスロットを回復できない場合、次のステップはSTEP 6（永久的な失敗）です。

注意

現在のpowerpc実装は、デバイスドライバーがこのルーチン内でスケジュールまたはセマフォを取得することを前提としています。現在のpowerpc実装では、すべてのデバイスに通知するため1つのカーネルスレッドを使用しています。そのため、1つのデバイスがスリープまたはスケジュールする場合、すべてのデバイスに影響が出ます。より良い実装には、エラー回復実装内で複雑なマルチスレッドロジックが必要です（例：すべての通知スレッドが「join」するのを待つ）。これは非常に複雑で、実装する価値がないとされています。 ではありません このドキュメントの最後に記載されている割り込みに関する注意点も参照してください。

現在のpowerpc実装では、デバイスがこの時点でI/Oを試行するかどうかはあまり気にせず、I/Oは失敗して読み込み時に0xffを返し、書き込みは無視されます。凍結されたアダプターに対してEEH_MAX_FAILSを超えるI/Oが試行された場合、EEHはデバイスドライバーが無限ループに入ったと想定し、syslogにエラーを出力します。その後、デバイスを再び動作させるには再起動が必要です。

7.1.3. ステップ2: MMIOが有効化される¶

プラットフォームがデバイスにMMIOを再有効化し（DMAは通常有効化されません）、影響を受けるすべてのデバイスドライバーに対してmmio_enabled()コールバックを呼び出します。

これは「早期回復」コールバックです。I/Oは再び許可されますが、DMAは許可されません（一部の制限あり）。これはドライバーが操作を再開するためのコールバックではなく、デバイスを覗き見る・操作し、診断情報を取得し、最終的にデバイスローカルリセットなどの操作をトリガーするためのものです。このコールバックは、セグメント内のすべてのドライバーが回復を試みることを合意し、ハードウェアが自動的なリンクリセットを行わない場合に呼び出されます。プラットフォームがスロットリセットやリンクリセットなしにI/Oを再有効化できない場合、このコールバックは呼び出されず、直接ステップ3（リンクリセット）またはステップ4（スロットリセット）に移行します。

注意

以下の提案が行われています（現在どのプラットフォームも実装していません）：提案：すべてのI/Oはこのコールバック内で同期的に実行されるべきです。これにより発生するエラーは通常のpci_check_whatever() API経由で返されます。このコールバック内で発生したエラーにより、新たなerror_detected()コールバックは発行されません。ただし、このようなエラーはセグメント全体のI/Oを再ブロック化し、他のデバイスの回復を無効化する可能性があり、セグメント全体をリンクリセットまたはスロットリセットのいずれかの状態に強制します。

ドライバーは次の結果コードのいずれかを返すべきです：
  • PCI_ERS_RESULT_RECOVERED

    ドライバーがデバイスが完全に機能しており、正常なドライバー操作を再開できると判断した場合に返します。ただし、他のドライバーが失敗し、スロットリセットをトリガーした場合など、ドライバーが実際に進むことを許可される保証はありません。

  • PCI_ERS_RESULT_NEED_RESET

    ドライバーが現在の状態で回復不可能であり、スロットリセットが必要だと判断した場合に返します。

  • PCI_ERS_RESULT_DISCONNECT

    上記と同じです。完全な失敗、リセット後も回復が不可能でドライバーが完全に停止している状態。（より正確に定義する必要があります）

ドライバーが返す結果によって次のステップが決まります。すべてのドライバーがPCI_ERS_RESULT_RECOVEREDを返した場合、プラットフォームはSTEP3（リンクリセット）またはSTEP5（運用再開）に進みます。

どのドライバーもPCI_ERS_RESULT_NEED_RESETを返した場合、プラットフォームはSTEP4（スロットリセット）に進みます。

7.1.4. STEP 3: リンクリセット¶

プラットフォームがリンクをリセットします。これはPCI-Express固有のステップであり、致命的なエラーが検出された際にリンクをリセットすることで解決できる場合に実行されます。

7.1.5. STEP 4: スロットリセット¶

PCI_ERS_RESULT_NEED_RESETの返却値に対応して、プラットフォームはリクエストしているPCIデバイスに対してスロットリセットを行います。プラットフォームがスロットリセットを実行する際の具体的な手順はプラットフォーム依存します。スロットリセットが完了すると、プラットフォームはデバイスのslot_reset()コールバックを呼び出します。

PowerPCプラットフォームはスロットリセットを2段階に実装しています：ソフトリセット（デフォルト）と fundamentals（オプション）リセット。

PowerPCソフトリセットはアダプターの#RSTラインをアサートし、その後PCI BARおよびPCI構成ヘッダーを、システム電源投入後にBIOS/システムファームウェア初期化が完了した状態と同等の状態に戻します。ソフトリセットはホットリセットとしても知られています。

PowerPC fundamentalsリセットはPCI Expressカードのみでサポートされ、デバイスのステートマシン、ハードウェアロジック、ポート状態、構成レジスタが初期状態に戻ります。

ほとんどのPCIデバイスではソフトリセットで回復が可能です。オプションのfundamentalsリセットは、ソフトリセットでは回復できない少数のPCI Expressデバイスをサポートするために提供されています。

プラットフォームがPCIホットプラグをサポートしている場合、リセットはスロットの電気的電源をオフ/オンに切り替えることで実行されることがあります。

プラットフォームはPCI構成空間を「電源投入後の初期状態」に戻す必要があります。「最後の状態」ではなく。スロットリセット後、デバイスドライバーは通常の初期化手順をほぼ常に使用し、異常な構成空間の設定はデバイスの停止、カーネルのパニック、または静的なデータ破損を引き起こす可能性があります。

このコールはドライバーにハードウェアの再初期化（ファームウェアの再ダウンロードなど）を機会にします。この時点でドライバーはカードが初期状態に戻り、完全に機能していると仮定できます。スロットは解凍され、ドライバーはPCI構成空間、メモリマップドI/O空間、DMAに完全なアクセス権を持ち、割込み（レガシ、MSI、MSI-X）も利用可能です。

ドライバーはこの時点で通常のI/O処理を再開すべきではありません。すべてのデバイスドライバーがこのコールバックで成功を報告した場合、プラットフォームはresume()を呼び出して処理を完了し、ドライバーが通常のI/O処理を再開できるようにします。

ドライバーは、リセット後でもデバイスを動作させることができない場合、この関数に対してcritical failureを返すことができます。プラットフォームが以前にソフトリセットを試した場合、現在はハードリセット（電源サイクル）を試みる可能性があり、その後slot_reset()を再度呼び出します。デバイスが依然として回復できない場合、これ以上なにもできません。このような場合、プラットフォームは通常「永久的な失敗」と報告します。この場合、デバイスは「死んだ」とみなされます。

マルチファンクションカードのドライバーは、どのドライバーインスタンスが「ワンショット」またはグローバルなデバイス初期化を実行するかについて、お互いに調整する必要があります。たとえば、Symbios sym53cxx2ドライバーはPCI機能0のみからデバイス初期化を行います。

+       if (PCI_FUNC(pdev->devfn) == 0)
+               sym_reset_scsi_bus(np, 0);
結果コード:

  • PCI_ERS_RESULT_DISCONNECT 上記と同じ。

PCI Expressカードで根本的なリセットが必要な場合、ドライバーはprobe関数でpci_dev構造体のneeds_fresetビットを設定する必要があります。たとえば、QLogic qla2xxxドライバーは特定のPCIカードタイプに対してneeds_fresetビットを設定します。

+       /* Set EEH reset type to fundamental if required by hba  */
+       if (IS_QLA24XX(ha) || IS_QLA25XX(ha) || IS_QLA81XX(ha))
+               pdev->needs_freset = 1;
+

プラットフォームはステップ5（再開処理）またはステップ6（永久的な失敗）に進みます。

注意

現在のpowerpc実装では、ドライバーがPCI_ERS_RESULT_DISCONNECTを返した場合、電源サイクルリセットを試みません。しかし、おそらく試すべきです。

7.1.6. ステップ5: 再開処理¶

すべてのドライバーが前の3つのコールバックのいずれかからPCI_ERS_RESULT_RECOVEREDを返した場合、プラットフォームは影響を受けたすべてのデバイスドライバーにresume()コールバックを呼び出します。このコールバックの目的は、ドライバーに処理を再開させ、すべてが正常に戻ったことを通知することです。このコールバックは結果コードを返しません。

この時点で新たなエラーが発生した場合、プラットフォームは新しいエラー回復シーケンスを再開します。

7.1.7. ステップ6: 永久的な失敗¶

「永久的な失敗」が発生し、プラットフォームがデバイスを回復できなくなった場合、プラットフォームはpci_channel_state_t値としてpci_channel_io_perm_failureを指定してerror_detected()を呼び出します。

この時点で、ドライバーは最悪の事態を想定すべきです。すべての待機中のI/Oをキャンセルし、新しいI/Oを拒否して上位レイヤーに-EIOを返す必要があります。その後、ドライバーはすべてのメモリをクリーンアップし、カーネル操作から自身を削除する必要があります。システムシャットダウン時に同様の処理を行います。

プラットフォームは通常、システムオペレータに永続的な故障の発生を何らかの方法で通知します。デバイスがホットプラグ可能である場合、オペレータはおそらくデバイスを外して交換したいでしょう。ただし、注意すべきは、すべての故障が本当に「永続的」であるとは限らないということです。一部は過熱によって、一部は挿し込みが不完全なカードによって引き起こされます。多くのPCIエラーイベントはソフトウェアのバグによって引き起こされます。たとえば、DMAが不正なアドレスに送られるか、プログラミングエラーによる偽の分割トランザクションなどがその例です。詳細については、powerpc/eeh-pci-error-recovery.txtで議論されている内容を参照してください。

7.1.8. 結論；一般的な注意事項¶

コールバックが呼ばれる方法はプラットフォームのポリシーです。スロットリセット機能を持たないプラットフォームは、回復できないドライバー（接続を解除）を無視し、同一セグメントの他のカードが回復できるように試みるかもしれません。ただし、実際のケースでは、セグメントごとに1つのドライバーしか存在しないことが一般的です。

では、割り込みについての注意点を述べます。割り込みが発生し、デバイスが死んでいたり孤立している場合、問題があります :) 現在のポリシーはこれをプラットフォームのポリシーに依存させることです。つまり、回復APIは以下の点を要求します：

  • セグメント内のエラー検出から、スロットリセットコールバックが呼ばれるまで、どのデバイスからも割り込み配信が行われる保証はありません。スロットリセットコールバックが呼ばれた時点で、割り込みが完全に動作しているものと期待されます。

  • 割り込み配信が停止している保証はありません。つまり、エラーを検出した後で割り込みを受け取るドライバー、または割り込みハンドラ内でエラーを検出し、適切な割り込み確認（ACK）が行われず、その原因を除去できない場合、単にIRQ_NOTHANDLEDを返すべきです。この状態の処理はプラットフォームに依存します。通常は、エラー処理中にIRQソースをマスクします。プラットフォームは、エラー管理可能なスロットに割り当てられている割り込みを知っていると期待され、エラー処理中にそのIRQ番号を一時的に無効にする必要があります（これは非常に複雑ではありません）。これにより、他のデバイスが共有する割り込みに対して一時的な遅延が生じますが、これ以外の方法は存在しません。高品質なプラットフォームは本来、多数のデバイス間で割り込みを共有しないはずです :)

8.1. 概要¶

8.1.1. このガイドについて¶

このガイドでは、PCI Express Advanced Error Reporting (AER) ドライバーの基本的な仕組みを説明し、その使用方法やエンドポイントデバイスのドライバーをPCI Express AERドライバーに準拠させる方法についても解説します。

8.1.2. PCI Express AERドライバーとは何ですか？¶

PCI Expressリンク自体やリンク上で実行されるトランザクションの behalf でエラーが発生する場合があります。PCI Expressでは、ベースラインキャパビリティとAdvanced Error Reportingキャパビリティという2つのエラー報告パラダイムを定義しています。ベースラインキャパビリティは、最小限のエラー報告要件を提供するすべてのPCI Expressコンポーネントに必須です。Advanced Error Reportingキャパビリティは、PCI Express拡張キャパビリティ構造を用いて実装され、より堅牢なエラー報告が可能になります。

PCI Express AERドライバーは、PCI Express Advanced Error Reportingキャパビリティをサポートするインフラストラクチャを提供します。PCI Express AERドライバーは以下の3つの基本的な機能を提供します：

  • エラーが発生した場合、包括的なエラー情報を収集します。

  • エラーをユーザーに報告します。

  • エラー回復アクションを実行します。

AERドライバーは、PCI-Express AERキャパビリティをサポートするルートポートのみにアタッチします。

8.2. ユーザー向けガイド¶

8.2.1. PCI Express AER RootドライバーをLinuxカーネルに含める¶

PCI Express AER Rootドライバーは、PCI Expressポートバスドライバーにアタッチされたルートポートサービスドライバーです。ユーザーがこれを使用したい場合、ドライバーはコンパイルする必要があります。オプション CONFIG_PCIEAER がこの機能をサポートします。これは CONFIG_PCIEPORTBUS に依存するため、CONFIG_PCIEPORTBUS=y および CONFIG_PCIEAER=y を設定してください。

8.2.2. PCI Express AER Rootドライバーをロードする¶

一部のシステムではファームウェアにAERサポートが含まれています。ファームウェアがAERを処理している間、LinuxのAERサポートを同時に有効にすると予測できない挙動が発生する可能性があります。そのため、LinuxはファームウェアがACPI _OSCメソッドを通じてOSにAER制御を委譲するまで、AERイベントを処理しません。_OSCの使用に関する詳細はPCI FW 3.0仕様を参照してください。

8.2.3. AERエラー出力¶

PCIe AERエラーがキャプチャされた場合、コンソールにエラーメッセージが出力されます。正しいエラーの場合は警告として出力され、そうでない場合はエラーとして出力されます。そのため、ユーザーはログレベルを変更して正しいエラーのメッセージをフィルタリングできます。

以下に例を示します：

0000:50:00.0: PCIe Bus Error: severity=Uncorrected (Fatal), type=Transaction Layer, id=0500(Requester ID)
0000:50:00.0:   device [8086:0329] error status/mask=00100000/00000000
0000:50:00.0:    [20] Unsupported Request    (First)
0000:50:00.0:   TLP Header: 04000001 00200a03 05010000 00050100

例では、「Requester ID」は、エラー メッセージをルート ポートに送信するデバイスの ID を意味します。他のフィールドについては、PCI Express データシートを参照してください。

8.2.4. AER ステータス / カウンタ¶

PCIe AER エラーがキャプチャされた場合、カウンタ / ステータスは sysfs 属性として公開され、Documentation/ABI/testing/sysfs-bus-pci-devices-aer_stats にドキュメントされています。

8.3. 開発者向けガイド¶

AER 意識型サポートを有効にするには、ソフトウェア ドライバが自身のデバイス内で AER キャパビリティ構造を構成し、コールバックを提供する必要があります。

AER をよりよくサポートするには、まず AER の動作を理解する必要があります。

PCI Express エラーは、訂正可能なエラーと訂正不可能なエラーの 2 種類に分類されます。この分類は、エラーの影響に基づいており、パフォーマンスの低下や機能障害を引き起こす可能性があります。

訂正可能なエラーはインターフェースの機能に影響を与えません。PCI Express プロトコルはソフトウェアの介入やデータの喪失なくして復旧できます。ハードウェアがこれらのエラーを検出し訂正します。一方、訂正不可能なエラーはインターフェースの機能に影響を与えます。訂正不可能なエラーは特定のトランザクションや PCI Express リンクの信頼性を低下させる可能性があります。エラー条件に応じて、訂正不可能なエラーは非致命的エラーと致命的エラーに分類されます。非致命的エラーは特定のトランザクションの信頼性を低下させますが、PCI Express リンク自体は完全に機能します。致命的エラーは、リンクの信頼性を低下させます。

AER が有効な場合、PCI Express デバイスはエラーをキャプチャした際に、上位の PCIe ルート ポートにエラー メッセージを自動的に送信します。ルート ポートは、エラー報告メッセージを受信した際に、内部で処理し、PCI Express キャパビリティ構造内でエラー メッセージをログに記録します。ログに記録されるエラー情報には、エラー報告エージェントのリクエスター ID をエラー源識別レジスタに保存し、ルート エラー ステータス レジスタのエラー ビットを適切に設定します。ルート エラー コマンド レジスタで AER エラー レポートが有効な場合、エラーが検出されるとルート ポートが割込みを生成します。

上記のエラーは PCI Express ハイエラルチャイナとリンクに関連しています。これらはデバイス固有のエラーを含みません。デバイス固有のエラーは依然としてデバイス ドライバに直接送信されます。

8.3.1. AER キャパビリティ構造を構成する¶

PCI ExpressコンポーネントのAER（Advanced Error Reporting）を認識するドライバーは、AERを有効にするためにデバイス制御レジスタを変更する必要があります。また、マスクレジスタや深刻度レジスタなどのAERレジスタも変更する場合があります。Helper関数pci_enable_pcie_error_reportingを使用してAERを有効化できます。セクション3.3を参照してください。

8.3.2. コールバックの提供¶

8.3.2.1. reset_linkコールバックを用いてPCI Expressリンクをリセット¶

このコールバックは、致命的なエラーが発生した際にPCI Express物理リンクをリセットするために使用されます。ルートポートAERサービスドライバーはデフォルトのreset_link関数を提供していますが、異なる上流ポートはPCI Expressリンクのリセット仕様が異なるため、すべての上流ポートで独自のreset_link関数を提供する必要があります。

セクション3.2.2.2にはreset_linkを呼び出すタイミングに関する詳細情報が記載されています。

8.3.2.2. PCIエラー回復コールバック¶

PCI Express AERルートドライバーは、エラー回復アクションを実行する際、関連する階層の下流デバイスドライバーと連携するためにエラーコールバックを使用します。

データ struct pci_driver err_handlerポインタは、pci_error_handlersにポイントし、これは複数のコールバック関数ポインタから構成されます。AERドライバーはpci-error-recovery.txtに定義されたルールに従いますが、PCI Express固有の部分（例：reset_link）は除きます。詳細なコールバックの定義についてはpci-error-recovery.txtを参照してください。

8.3.2.3. 訂正可能なエラー¶

訂正可能なエラーはインターフェースの機能に影響を与えません。PCI Expressプロトコルはソフトウェアの介入やデータの喪失なくして回復できます。このようなエラーには回復アクションは必要ありません。AERドライバーはデバイスの訂正可能エラー状態レジスタをクリアし、これらのエラーをログに記録します。

8.3.2.4. 訂正不能な（非致命的および致命的）エラー¶

エラー情報が非致命的なエラーを示す場合、上流でのリンクリセットは不要です。AERドライバーは、関連する階層内のすべてのドライバーに対してerror_detected(dev, pci_channel_io_normal)を呼び出します。例えば：

EndPoint<==>DownstreamPort B<==>UpstreamPort A<==>RootPort

上流ポートAがAERエラーをキャプチャした場合、階層には下流ポートBとエンドポイントが含まれます。

ドライバーは、回復可能かどうかによってPCI_ERS_RESULT_CAN_RECOVER、PCI_ERS_RESULT_DISCONNECT、またはPCI_ERS_RESULT_NEED_RESETを返すことができます。AERドライバーが次にmmio_enabledを呼び出すかどうかに応じて異なります。

エラー メッセージが致命的なエラーを示している場合、カーネルは error_detected(dev, pci_channel_io_frozen) を関連する階層内のすべてのドライバにブロードキャストします。その後、上流デバイスでのリンク リセットが必要です。異なる種類のデバイスがリンク リセットに異なるアプローチを使用するため、AER ポート サービス ドライバは pcie_do_recovery() 関数のコールバックパラメータを通じてリンク リセットを実行する機能を提供する必要があります。reset_link が NULL でない場合、回復関数はそれを使用してリンクをリセットします。error_detected が PCI_ERS_RESULT_CAN_RECOVER を返し、reset_link が PCI_ERS_RESULT_RECOVERED を返す場合、エラー処理は mmio_enabled に移行します。

8.3.3. 補助関数¶

int pci_enable_pcie_error_reporting(struct pci_dev *dev);

pci_enable_pcie_error_reporting は、エラーが検出されたときにデバイスがエラー メッセージをルート ポートに送信できるようにします。注意点として、デバイスはデフォルトではエラー レポートを有効にしていないため、ドライバはこの関数を呼び出して有効化する必要があります。

int pci_disable_pcie_error_reporting(struct pci_dev *dev);

pci_disable_pcie_error_reporting は、エラーが検出されたときにデバイスがエラー メッセージをルート ポートに送信しないようにします。

int pci_aer_clear_nonfatal_status(struct pci_dev *dev);`

pci_aer_clear_nonfatal_status は、訂正不能エラー状態レジスタ内の非致命的なエラーをクリアします。

8.3.4. よくある質問¶

Q:

PCI Express デバイス ドライバがエラー回復ハンドラ（pci_driver->err_handler が NULL に等しい）を提供しない場合、何が起こりますか？

A:

そのドライバで接続されたデバイスは回復されません。エラーが致命的である場合、カーネルは警告メッセージを出力します。詳しくはセクション 3 を参照してください。

Q:

上流ポート サービス ドライバが callback reset_link を提供しない場合、何が起こりますか？

A:

上流ポートがサービス ドライバで接続されている場合、エラーが報告されると致命的なエラー回復が失敗します。

Q:

このインフラストラクチャが PCI Express に無知なドライバをどのように処理しますか？

A:

このインフラストラクチャはエラー発生時にドライバのエラー コールバック関数を呼び出します。ただし、ドライバが PCI Express を認識していない場合、デバイスが自身のエラーをルート ポートに報告しない可能性があります。

Q:

そのドライバが PCI Express AER ルート ドライバと互換性を持つために何を変更する必要がありますか？

A:

AER をデバイスで有効化し、訂正不能状態レジスタをクリアする補助関数を呼び出すことができます。詳しくはセクション 3.3 を参照してください。

8.4. ソフトウェア エラー注入¶

PCIe AER エラー回復コードのデバッグは、実際のハードウェア エラーをトリガーするのが難しいため非常に困難です。ソフトウェアベースのエラー注入を使用することで、さまざまな PCIe エラーを擬似的に発生させることができます。

まず、カーネル構成で PCIe AER ソフトウェア エラー注入を有効にする必要があります。つまり、.config に次の項目が含まれている必要があります。

CONFIG_PCIEAER_INJECT=y または CONFIG_PCIEAER_INJECT=m

新しいカーネルで再起動するか、モジュールを挿入した後、/dev/aer_inject という名前のデバイスファイルが作成される必要があります。

次に、aer-inject という名前のユーザー空間のツールが必要です。これは次のURLから取得できます：

https://git.kernel.org/cgit/linux/kernel/git/gong.chen/aer-inject.git/

aer-inject に関する詳しい情報は、そのソースコードに同梱されているドキュメントに記載されています。

Seccomp BPF (SECure COMPuting with filters)¶

はじめに¶

ユーザーランドプロセスに多くのシステムコールが公開され、そのうち多くのものはプロセスの寿命を通じて使用されません。システムコールが進化し成熟するにつれて、バグが発見され除去されていきます。特定のユーザーランドアプリケーションは、利用可能なシステムコールのセットを減らすことで恩恵を受けるため、システムコールフィルタリングはこのようなアプリケーションのために設計されています。

Seccompフィルタリングは、プロセスが受信するシステムコールにフィルターを指定する方法を提供します。このフィルターは、ソケットフィルタと同様にBerkeley Packet Filter (BPF) プログラムとして表現され、操作されるデータはシステムコール番号とその引数に関連しています。これにより、ユーザーランドで長年利用されてきたフィルタープログラム言語と、シンプルなデータセットを活用した表現力のあるシステムコールフィルタリングが可能になります。

さらに、BPFはseccompのユーザーがタイムオブチェックタイムオブユース（TOCTOU）攻撃に遭うことを防ぐための仕組みを提供します。これはシステムコールの間接実行フレームワークで一般的な攻撃です。BPFプログラムはポインタを解引用することを許可せず、すべてのフィルターがシステムコール引数を直接評価するものに制限されます。

これは何ではありません¶

システムコールフィルタリングはサンドボックスではありません。これは明確に定義されたメカニズムでカーネルの露出面を最小限に抑えるためのツールです。サンドボックス開発者向けのツールとして意図されています。それ以上は、論理的な動作と情報フローのポリシーを、他のセキュリティ強化技術と、選択したLSM（Linux Security Module）を組み合わせて管理する必要があります。表現力のある動的フィルターは、この道筋でさらに選択肢を提供します（例: 病的なサイズを回避するか、socketcall()内の多重化されたシステムコールのうちどれを許可するかを指定するなど）が、誤ってより完全なサンドボックス解決策とみなされる可能性があります。

使い方¶

追加のseccompモードが導入され、厳格なseccompと同じprctl(2)コールで有効化されます。もしアーキテクチャが CONFIG_HAVE_ARCH_SECCOMP_FILTER、以下のようになります:

PR_SET_SECCOMP:

現在はBPFプログラムで新しいフィルターを指定する追加引数を受け取ります。BPFプログラムはstruct seccomp_dataを処理し、システムコール番号、引数、その他のメタデータを反映します。BPFプログラムはその後、カーネルがどのアクションを実行すべきかを示す受け入れ可能な値のいずれかを返さなければなりません。

使用方法:

prctl(PR_SET_SECCOMP, SECCOMP_MODE_FILTER, prog);

‘prog’ 引数は、フィルタープログラムを含む struct sock_fprog へのポインタであり、プログラムが無効な場合、呼び出しは -1 を返し、 errno を設定します。 EINVAL.

もし fork/clone および execve @prog によって許可される限り、子プロセスは親と同じフィルターおよびシステムコール ABI に制限されます。

使用する前に、タスクは prctl(PR_SET_NO_NEW_PRIVS, 1) または、 CAP_SYS_ADMIN 名前空間内の権限を有している必要があります。これらが真でない場合、 -EACCES が返されます。この要件により、フィルタープログラムは、インストールしたタスクよりも高い権限を持つ子プロセスに適用されません。

さらに、 prctl(2) が、アタッチされたフィルターによって許可される場合、追加のフィルターが重ねられることもあり、評価時間が増加しますが、プロセス実行中の攻撃面をさらに削減できます。

上記の呼び出しは、成功時は 0 を、エラー時は非ゼロ値を返します。

返却値¶

セキュアコンパクトフィルタは、以下のいずれかの値を返すことができます。複数のフィルタが存在する場合、特定のシステムコールの評価において常に優先度の高い値が使用されます。(例えば、 SECCOMP_RET_KILL_PROCESS が常に優先されます。)

優先度順に、以下の通りです：

SECCOMP_RET_KILL_PROCESS:

プロセス全体がシステムコールを実行することなく即座に終了します。タスクの終了ステータス (status & 0x7f) は SIGSYS、ではなく SIGKILL.

SECCOMP_RET_KILL_THREAD:

タスクがシステムコールを実行することなく即座に終了します。タスクの終了ステータス (status & 0x7f) は SIGSYS、ではなく SIGKILL.

SECCOMP_RET_TRAP:

カーネルが信号を送信します。 SIGSYS トリガーとなったタスクに送信します。 siginfo->si_call_addr システムコール命令のアドレスを示します。また、 siginfo->si_syscall および siginfo->si_arch が試行されたシステムコールを示します。プログラムカウンタはシステムコールが実行されたかのように設定されます（つまり、システムコール命令を指さない）。戻り値レジスタにはアーキテクチャに依存する値が含まれます – 実行を再開する場合は、意味のある値に設定してください。（アーキテクチャ依存性は、 -ENOSYS を置き換えると有用な情報を上書きする可能性があるためです。）

以下の SECCOMP_RET_DATA 戻り値の一部が si_errno.

SIGSYS セキュアコンパクトによってトリガーされた場合、si_code は SYS_SECCOMP.

SECCOMP_RET_ERRNO:

戻り値の下位16ビットがシステムコールを実行することなくユーザー空間に errno として渡されます。

SECCOMP_RET_USER_NOTIF:

戻り値の一部が struct seccomp_notif ユーザー空間通知 fd に送信されるメッセージ、その fd が接続されている場合、または -ENOSYS 接続されていない場合です。ユーザー通知の処理方法については下記を参照してください。

SECCOMP_RET_TRACE:

この値が返された場合、カーネルが... ptrace()ベースのトレーサーに通知を試みます。トレーサーが存在しない場合、 -ENOSYS ユーザー空間に返され、システムコールは実行されません。

トレーサーがリクエストを送信した場合、通知されます。 PTRACE_O_TRACESECCOMP を使用して ptrace(PTRACE_SETOPTIONS)。トレーサーは... PTRACE_EVENT_SECCOMP 2.5開発シリーズで導入された形式です。 SECCOMP_RET_DATA BPFプログラムの一部の戻り値はトレーサーに介して利用可能になります PTRACE_GETEVENTMSG.

トレーサーはシステムコールをスキップするためにシステムコール番号を-1に変更できます。代替案として、トレーサーは有効なシステムコール番号にシステムコールを変更することで、システムコールをスキップできます。トレーサーがシステムコールをスキップするよう要求すると、システムコールはトレーサーが戻り値レジスタに設定した値として戻り値を返すように見えます

トレーサーに通知が送信された後ではseccompチェックが再度実行されません。(これはseccompベースのサンドボックスがptraceを使用することを許可する際、他のサンドボックスプロセスを含めて極めて注意が必要であることを意味します。ptraceを介してトレーサーはこのメカニズムを悪用してエスケープできるためです)

SECCOMP_RET_LOG:

システムコールがログに記録された後で実行される結果になります。アプリケーション開発者は、複数のテストと開発サイクルを経てリストを構築する必要なく、アプリケーションがどのシステムコールを必要とするかを学習するためにこの機能を使用すべきです

「log」がactions_logged sysctl文字列に存在する場合にのみこのアクションがログに記録されます

SECCOMP_RET_ALLOW:

システムコールが実行される結果になります

複数のフィルタが存在する場合、特定のシステムコールの評価における戻り値は常に最高の優先度を持つ値を使用します

優先度はのみマスクを使用して決定されます SECCOMP_RET_ACTION マスク。複数のフィルタが同じ優先度の戻り値を返す場合、のみ最新にインストールされたフィルタからの値が返されます SECCOMP_RET_DATA from the most recently installed filter will be returned.

陥りやすい罠¶

使用中に避けるべき最大の落とし穴は、アーキテクチャ値を確認せずにシステムコール番号でフィルタリングすることです。なぜなら、複数のシステムコール呼び出し規約をサポートするアーキテクチャでは、特定の呼び出し方法によってシステムコール番号が変化する可能性があるからです。異なる呼び出し規約間で番号が重なっている場合、フィルタのチェックが悪用される可能性があります。常にarch値を確認してください！

例¶

以下の samples/seccomp/ ディレクトリにはx86固有の例と、より一般的なマクロインターフェースの高レベル例が含まれています

ユーザースペース通知¶

以下の SECCOMP_RET_USER_NOTIF 戻りコードによりseccompフィルタは特定のシステムコールをユーザー空間に渡して処理させることができます。これはコンテナマネージャーなどのアプリケーションが特定のシステムコール（mount(), finit_module(), etc.)の挙動を変更したい場合に有用です

通知FDを取得するには、 SECCOMP_FILTER_FLAG_NEW_LISTENER 引数に複数のタグチェックエラー モード ビットを設定できます。 seccomp() システムコールを使用してください：

fd = seccomp(SECCOMP_SET_MODE_FILTER, SECCOMP_FILTER_FLAG_NEW_LISTENER, &prog);

（成功した場合）フィルタのリスナーFDを返します。その後、このFDは SCM_RIGHTS または類似のものです。注意点として、フィルタードス（filter fds）は特定のフィルターに該当し、特定のタスクとは関係ありません。したがって、このタスクがフォーク（fork）した場合、両方のタスクからの通知は同じフィルタードスに表示されます。フィルタードスへの読み込みと書き込みは同期されていますため、複数のリーダーがフィルタードスを使用しても安全です。

セックコンプ通知ドス（seccomp notification fd）のインターフェースは2つの構造体から成り立っています。

struct seccomp_notif_sizes {
    __u16 seccomp_notif;
    __u16 seccomp_notif_resp;
    __u16 seccomp_data;
};

struct seccomp_notif {
    __u64 id;
    __u32 pid;
    __u32 flags;
    struct seccomp_data data;
};

struct seccomp_notif_resp {
    __u64 id;
    __s64 val;
    __s32 error;
    __u32 flags;
};

以下の struct seccomp_notif_sizes 構造体は、セックコンプ通知で使用される各種構造体のサイズを決定するために使用できます。サイズは struct seccomp_data 今後変更される可能性があるため、コードでは以下のものを使用すべきです：

struct seccomp_notif_sizes sizes;
seccomp(SECCOMP_GET_NOTIF_SIZES, 0, &sizes);

を用いて、各種構造体のサイズを割り当てるために使用してください。例として、samples/seccomp/user-trap.cを参照してください。

ユーザーは、 ioctl(SECCOMP_IOCTL_NOTIF_RECV) (または poll())を介してセックコンプ通知ドスから読み取ることで、 struct seccomp_notifを受信できます。これは5つのメンバから成り、構造体の入力長、フィルターパーツごとの一意な識別子、 idand wakes up processes waiting on the timerfd. While iterating the pid このリクエストをトリガーしたタスクの識別子（タスクがリスナーのpid名前空間から見えないpid名前空間にいる場合、この値は0になる可能性があります）。通知にはさらに、 data セックコンプに渡された引数、およびフィルターフラグが含まれます。構造体をioctl呼び出し前にゼロ初期化する必要があります。

ユーザー空間は、この情報に基づき何を行うかの決定を行い、 ioctl(SECCOMP_IOCTL_NOTIF_SEND) 応答を送信することで、ユーザー空間に返すべき動作を示します。応答の id のメンバーです struct seccomp_notif_resp は、 id と同じ struct seccomp_notif.

注意すべき点は、 struct seccomp_data がシステムコールのレジスタ引数の値を含むものの、メモリへのポインタは含みません。タスクのメモリは、適切な権限を持つトレースによって ptrace() または /proc/pid/mem経由してアクセス可能です。ただし、上記のTOCTOU（タイムオブチェックとタイムオブ使用）の回避に注意する必要があります。トレース対象のメモリから読み取るすべての引数は、ポリシー決定を行う前にトレーサーのメモリに読み込む必要があります。これにより、システムコール引数の原子的な決定が可能になります。

Sysctls¶

セックコンプのsysctlファイルは、 /proc/sys/kernel/seccomp/ ディレクトリにあります。以下は、そのディレクトリ内の各ファイルの説明です：

actions_avail:

セックコンプの返却値の読み取り専用順序付きリスト（上記の SECCOMP_RET_* マクロを参照）を文字列形式で示しています。左から右への順序は、最も制限的な返却値から最も制限の少ない返却値までです。

このリストは、カーネルがサポートするセックコンプの返却値の集合を表しています。ユーザー空間のプログラムは、このリストを使用して、プログラムがビルドされた際のアクションと、現在実行中のカーネルがサポートするアクションの違いを確認できます。 seccomp.h、プログラムがビルドされた際のアクションが、現在実行中のカーネルがサポートするアクションと異なっているかを確認できます。

actions_logged:

セックコンプの返却値の読み取り書き込み可能な順序付きリスト（上記の SECCOMP_RET_* マクロを参照）で、ログに記録可能な値を示します。ファイルへの書き込みは順序を保つ必要はありませんが、読み取りはactions_avail sysctlと同じ順序で行われます。

以下の allow 文字列はsysctlに受け入れられません。ログ actions_logged を記録することができないためです。sysctlに書き込みを試みると、EINVALが返されます。 SECCOMP_RET_ALLOW アクション。sysctlへの書き込みは、EINVALが返されるためできません。 allow sysctlへの書き込みは、EINVALが返されるためできません。

x86-64では、vsyscallのエミュレーションがデフォルトで有効です。(vsyscallsはvDSOコールのレガシーな変体です。) 現在、エミュレートされたvsyscallsはseccompを尊重しますが、いくつかの特異な挙動があります:

  • 戻り値が SECCOMP_RET_TRAP が設定され、 si_call_addr がvsyscallコールのエントリーポイントを指すため、'syscall'命令後のアドレスにはなりません。再実行するコードは、(a) ret命令がエミュレートされたこと、(b) システムコールの再実行が標準のvsyscallエミュレーションセキュリティチェックを再度トリガーし、再実行はほぼ無意味であることを認識する必要があります。

  • 戻り値が SECCOMP_RET_TRACE トレーサーに通常通り通知しますが、orig_raxレジスタを使用してシステムコールを他のコールに変更できない場合があります。現在エミュレートされているコールをスキップするには、-1に変更する必要があります。他の変更はプロセスを終了させる可能性があります。トレーサーが見るのは、システムコールのエントリーポイントアドレスです。これは通常の挙動とは異なります。トレーサーはripやrspを変更してはなりません。(他の変更がプロセスを終了させるとは信頼してはなりません。動作する可能性があります。たとえば、一部のカーネルでは、今後のみ存在するシステムコールを選択すると、正しいエミュレーションが行われるため、 -ENOSYS).

この特異な挙動を検出するには、 addr & ~0x0C00 == 0xFFFFFFFFFF600000を確認してください。( SECCOMP_RET_TRACEの場合、ripを使用してください。 SECCOMP_RET_TRAPの場合、 siginfo->si_call_addrを使用してください。) 他の条件を確認しないでください: 今後のカーネルではvsyscallエミュレーションが改善される可能性があり、vsyscall=nativeモードの現在のカーネルでは挙動が異なりますが、 0xF...F600{0,4,8,C}00 の場所にある命令はこれらのケースではシステムコールではありません。

現代のシステムではvsyscallを使用しない可能性が高く、これはレガシー機能であり、標準のシステムコールよりもはるかに遅いです。新規コードはvDSOを使用し、vDSOによって発行されたシステムコールは通常のシステムコールと区別がつきません。

unshareシステムコール¶

このドキュメントは、新しいシステムコール unshare() について説明しています。ドキュメントでは、この機能の概要、なぜ必要なのか、どのように利用できるか、インターフェース仕様、設計、実装方法、およびテスト方法について述べています。

1) 概要¶

従来のオペレーティングシステムカーネルは、スレッドをプロセス内の複数の実行コンテキストとして抽象化しています。これらのカーネルは、これらの「スレッド」を維持するために特別なリソースやメカニズムを提供します。Linuxカーネルは、プロセスと「スレッド」を区別せず、シンプルかつ巧妙な方法で処理しています。カーネルはプロセス間でリソースを共有させることにより、追加のデータ構造やメカニズムを必要とせずに従来の「スレッド」の挙動を実現しています。このようにスレッドを実装する力は、単純さだけでなく、アプリケーションプログラマが従来のスレッドの「すべてまたはなし」の共有リソースの制約から外れて作業できる点にもあります。Linuxでは、cloneシステムコールを使用してスレッドを生成する際、アプリケーションは選択的にどのリソースをスレッド間で共有するかを指定できます。

unshare() システムコールは、Linuxスレッドモデルに「スレッドが生成時に共有していたリソースを選択的に共有を解除できる」という基本的な機能を追加します。unshare() は、2000年8月にLinux-KernelメーリングリストでPOSIXスレッドに関する議論の中で、Al Viroによって概念化されました。unshare() は、新しいプロセスを生成せずに共有リソースを制御したいアプリケーションにとってLinuxスレッドの有用性を拡張します。unshare() は、プロセス/スレッドを仮想マシンとして実装する概念を反映した利用可能なプリミティブの自然な拡張です。

2) メリット¶

unshare() は、PAMなどの大規模なアプリケーションフレームワークにおいても有用です。このようなフレームワークでは、新しいプロセスを生成してプロセスリソースの共有/非共有を制御することはできません。forkやcloneを使用して新しいプロセスを生成する際、ネームスペースはデフォルトで共有されるため、unshare() は非スレッドアプリケーションでも、デフォルトの共有ネームスペースから分離する必要がある場合に恩恵を受けることができます。以下に、unshare() が利用できる2つのユースケースを示します。

2.1 セキュリティコンテキストごとのネームスペース¶

unshare()は、カーネルのプロセスごとの名前空間メカニズムを使用して、ポリインスタンス化されたディレクトリを実装するために使用できます。ポリインスタンス化されたディレクトリ（例：/tmp、/var/tmp、またはユーザーのホームディレクトリのセキュリティコンテキストごとのインスタンスなど）は、ユーザーがこれらのディレクトリと作業を行う際、ユーザープロセスを分離します。unshare()を使用することで、PAMモジュールはログイン時にユーザーにプライベートな名前空間を簡単に設定できます。Common Criteria認証におけるラベリングされたシステム保護プロファイルではポリインスタンス化されたディレクトリが必要ですが、Linuxカーネルの共有ツリー機能が利用可能になったことにより、通常のLinuxシステムでもログイン時にプライベートな名前空間を設定し、/tmp、/var/tmpなどのディレクトリをポリインスタンス化することで恩恵を受けることができます。

2.2 仮想メモリおよび/またはオープンファイルのunsharing¶

クライアント/サーバーのアプリケーションを例にすると、サーバーがクライアントのリクエストを処理するために、仮想メモリやオープンファイルなどのリソースを共有するプロセスを作成します。unshare()が利用されていない場合、サーバーはリクエストを処理するプロセスを作成する際に何を共有するかを決定する必要があります。unshare()は、リクエストの処理中にコンテキストの一部を分離する機能をサーバーに提供します。大規模で複雑なミドルウェアアプリケーションフレームワークでは、プロセスが作成された後にunshare()を実行できるこの機能は非常に有用です。

3) コスト¶

コードの重複を防ぐため、unshare()はアクティブなタスク（clone/forkとは異なり、新たに割り当てられた非アクティブなタスクとは対照的）に対して動作するため、copy_*関数をわずかな再編成で変更しました。既存のテスト済みで安定したコードを変更して新機能を実装するには、初期には頻繁に使用されない可能性のある機能にもかかわらず、コストが伴います。しかし、変更内容の適切な設計とコードレビュー、およびLTP向けのunshare()テストの作成により、この新機能のメリットはコストを上回る可能性があります。

4) 要件¶

unshare()は、clone(2)システムコールで行われた共有を解除するために使用され、clone(2)と同様のインターフェースを持つべきです。つまり、clone(int flags, void *stack)のflagsは共有する内容を指定するため、unshare(int flags)のflagsも同様に共有を解除する内容を指定する必要があります。ただし、clone(2)でのflagsの使用方法とは意味が逆になるように見える可能性があります。しかし、ABI変更なしで今後のインクリメンタルなコンテキストの共有解除を可能にする簡単な解決策は存在しませんでした。

unshare()のインターフェースは、古いアプリケーションの再ビルドを必要とせずに将来の新しいコンテキストフラグの追加を可能にする必要があります。新しいコンテキストフラグが追加された場合、unshare()の設計はそれらのリソースを必要に応じてインクリメンタルに共有解除できるようにする必要があります。

5) 功能仕様¶

NAME

unshare - プロセス実行コンテキストの一部を分離する

SYNOPSIS

#include <sched.h>

int unshare(int flags);

DESCRIPTION

unshare()は、他のプロセスと共有している現在の実行コンテキストの一部をプロセスから分離するための機能です。fork(2)で新規プロセスが作成される際には、名前空間などの実行コンテキストの一部はデフォルトで共有されますが、仮想メモリやオープンファイルディスクリプタなどはclone(2)で明示的に共有を指定する必要があります。

unshare()の主な用途は、新規プロセスを作成することなく、プロセスが共有している実行コンテキストを制御することです。

flags引数は、以下の定数の1つまたは複数のビット論理和を指定します。

CLONE_FS

CLONE_FSが設定されている場合、呼び出し元のファイルシステム情報は共有ファイルシステム情報から分離されます。

CLONE_FILES

CLONE_FILESが設定されている場合、呼び出し元のファイルディスクリプタテーブルは共有ファイルディスクリプタテーブルから分離されます。

CLONE_NEWNS

CLONE_NEWNSが設定されている場合、呼び出し元の名前空間は共有名前空間から分離されます。

CLONE_VM

CLONE_VMが設定されている場合、呼び出し元の仮想メモリは共有仮想メモリから分離されます。

戻り値

成功時は0が返され、失敗時は-1が返されerrnoが

エラー
EPERM CLONE_NEWNSが非rootプロセス（プロセス

CAP_SYS_ADMINを指定せずに。

ENOMEM 呼び出し元のコンテキストの一部をコピーするために十分なメモリを確保できません

共有解除する必要がある部分。

EINVAL 無効なフラグが引数として指定されました。

準拠している

unshare()コールはLinux固有の機能であり、ポータブルなプログラムには使用すべきではありません。

関連項目

clone(2), fork(2)

6) 高レベル設計¶

flags引数によってunshare()システムコールは適切なプロセスコンテキスト構造体を割り当て、現在の共有バージョンから値を取得して初期化し、新たに複製した構造体を現在のタスク構造体に関連付け、対応する共有バージョンを解放します。cloneの補助関数(copy_*)は、以下の2つの理由によりunshare()が直接使用できないためです。

  1. cloneは新たに割り当てられたまだアクティブになっていないタスク構造体を操作しますが、unshare()は現在アクティブなタスク構造体を操作します。そのため、unshare()は新たに複製したコンテキスト構造体を関連付ける前に適切なtask_lock()を取得する必要があります。

  2. unshare()は、解放するコンテキスト構造体をすべて割り当てて複製する必要があります。それらを現在のタスク構造体に関連付け、古い共有構造体を解放する前に、この作業を実行しないと、エラー発生時にロールバック時にレースコンディションやクラッシュが発生します。例えば仮想メモリと名前空間の両方を解放する場合、仮想メモリの解放が成功した後、新しい名前空間構造体の割り当て中にエラーが発生した場合、エラーレターンコードで仮想メモリの解放を逆操作する必要があります。この逆操作では、古い共有の仮想メモリ構造体に戻る必要がありますが、その構造体がもう存在しない可能性があります。

そのため、copy_*>関数で実装されていたコンテキスト構造体の割り当てと複製のコードは、dup_*>関数に移動されました。現在、copy_*>関数はdup_*>関数を呼び出して適切なコンテキスト構造体を割り当て、複製し、それらを構築中のタスク構造体に関連付けます。一方unshare()システムコールは以下の手順を実行します。

  1. フラグを確認し、欠落しているが暗黙的に設定されるフラグを強制的に設定します。

  2. 各コンテキスト構造体について、flags引数に該当するビットが設定されている場合、対応するunshare()補助関数を呼び出して新しいコンテキスト構造体を割り当て、複製します。

  3. 割り当てと複製にエラーがなければ、新しいコンテキスト構造体がある場合、現在のタスク構造体をロックし、新しいコンテキスト構造体を現在のタスク構造体に関連付け、現在のタスク構造体のロックを解放します。

  4. 古い共有コンテキスト構造体を適切に解放します。

7) 低レベル設計¶

unshare()の実装は以下の4つの項目に分類できます。

  1. 既存のcopy_*関数の再編成

  2. unshare()システムコールのサービス関数

  3. 各プロセスコンテキストに対応するunshare()補助関数

  4. 各種アーキテクチャにおけるシステムコール番号の登録

7.1) 既存のcopy_*関数の再編成¶

copy_mm、copy_namespace、copy_filesなどのコピー関数は、それぞれ2つの主要なコンポーネントを持っていた。最初のコンポーネントは適切な構造体を確保し複製し、2番目のコンポーネントはコピー関数に渡されたタスク構造体にリンクする役割を果たした。最初のコンポーネントは別個の関数として分割された。これらのdup_*関数は適切なコンテキスト構造体を確保し複製する。再編成されたcopy_*関数は、対応するdup_*関数を呼び出し、その後、コピー関数が呼び出されたタスク構造体に新たに複製された構造体をリンクする。

7.2) unshare() システムコールサービス関数¶

  • フラグをチェックし、強制的に設定されるフラグを確認する。CLONE_THREADが設定されている場合、CLONE_VMを強制的に設定する。CLONE_VMが設定されている場合、CLONE_SIGHANDを強制的に設定する。CLONE_SIGH,ANDが設定されていてシグナルが共有されている場合、CLONE_THREADを強制的に設定する。CLONE_NEWNSが設定されている場合、CLONE_FSを強制的に設定する。

  • 各コンテキストフラグに対して、システムコールに渡されたフラグと、新しいアンシャアリング構造体を指すポインタへの参照を引数として、対応するunshare_*ヘルパ関数を呼び出す。

  • unshare_*ヘルパ関数が新しい構造体を生成する場合、現在のタスクのtask_lock()を取得し、適切なコンテキストポインタを修正し、タスクロックを解放する。

  • すべての新しいアンシャアリング構造体に対して、対応する古い共有構造体を解放する。

7.3) unshare_* ヘルパ関数¶

CLONE_SYSVSEM、CLONE_SIGHAND、CLONE_THREADに対応するunshare_*ヘルパ関数は、まだ実装されていないため-EINVALを返す。それ以外のフラグについては、フラグの値を確認し、その構造体のアンシャアリングが必要な場合、対応するdup_*関数を呼び出して構造体を確保・複製し、ポインタを返す。

7.4) 最後に¶

アーキテクチャ固有のコードを適切に修正し、新しいシステムコールを登録する。

8) テスト仕様¶

unshare()のテストでは以下の点を確認する必要がある:

  1. 有効なフラグ: シグナルやシグナルハンドラのクローンフラグで、未実装のため-EINVALを返すテスト。

  2. 欠落/強制フラグ: ファイルシステムのアンシャアリングを指定せずに名前空間をアンシャアリングする場合、正しい処理が行われるかテスト。

  3. 名前空間、ファイルシステム、ファイル、VMの4つのサポートされているアンシャアリングについて、システムコールが正しい構造体をアンシャアリングするか確認。個別にアンシャアリングする場合もしくは他の構造体と組み合わせてアンシャアリングする場合の動作が正しく行われるかを検証する。

  4. 並行実行: shmセグメント内のアドレスで共有メモリセグメントとfutexを使用して、約10スレッドの実行を同期します。いくつかのスレッドはexecveを実行し、いくつかは_exitを実行し、残りはさまざまなフラグの組み合わせでunshareを実行します。unshareが正しく行われることを確認し、クラッシュやフリーズなどの異常が発生しないことを検証してください。

9) 今後の作業¶

現在のunshare()の実装では、シグナルとシグナルハンドラのunshareはサポートされていません。シグナル自体が複雑であり、実行中のプロセスのシグナルやシグナルハンドラをunshareするのはさらに複雑です。今後、シグナルやシグナルハンドラのunshareを明示的に許可する必要がある場合でも、legacyアプリケーションに影響を与えることなくunshare()に段階的に追加することが可能です。

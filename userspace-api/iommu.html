IOMMUユーザー空間API¶

IOMMU UAPIは、物理的なIOMMUドライバーと仮想的なIOMMUドライバー間で通信が必要な仮想化ケースで使用されます。ベアメタルでの使用では、IOMMUはシステムデバイスであり、ユーザースペースと直接通信する必要はありません。

主な使用ケースはゲストの共有仮想アドレス（SVA）およびゲストIO仮想アドレス（IOVA）です。この場合、vIOMMUの実装は物理的なIOMMUに依存しており、そのためホストドライバーとの相互作用が必要です。

機能¶

ユーザーとカーネルの通信は双方向です。サポートされるユーザー・カーネルAPIは以下の通りです：

  1. ゲストPASIDのバインド/アンバインド（例：Intel VT-d）

  2. ゲストPASIDテーブルのバインド/アンバインド（例：ARM SMMU）

  3. ゲストからの要求に応じてIOMMUキャッシュを無効化

  4. ゲストにエラーを報告し、ページリクエストを処理

要件¶

IOMMU UAPIは汎用的で拡張可能であり、以下の要件を満たします：

  1. エミュレートおよびパラバーチャライズド vIOMMU

  2. 複数のベンダー（Intel VT-d、ARM SMMUなど）

  3. UAPIの拡張は既存のユーザースペースを破壊してはなりません

インターフェース¶

IOMMU UAPIで定義されたデータ構造は自立していますが、ユーザーアプリケーション用のAPI関数は導入されていません。代わりに、VFIOなどの既存ユーザードライバーフレームワークと連携して動作するよう設計されています。

拡張規則と注意事項¶

IOMMU UAPIが拡張される場合、データ構造は のみ 2つの方法で変更できます：

  1. padding[]フィールドを再利用して新しいフィールドを追加。サイズ変更なし。

  2. ユニオンの末尾に新しいメンバを追加。構造体サイズが増加する可能性あり。

新しいフィールドは追加できません RCU保護データ構造からデータ要素を削除した後、 変動サイズのユニオンであり、オフセットが移動すると後方互換性を破る可能性があります。どちらの方法でも構造体に影響を与える変更がある場合、新しいフラグを導入する必要があります。IOMMUドライバーはフラグに基づいてデータを処理し、後方互換性を確保します。

バージョンフィールドは、UAPI全体のアップグレードが極めてまれな場合にのみ予約されています。

It’s always 呼び出し元の責任は、構造体のサイズを適切に設定することです。ただし、argszはユーザーが提供するデータであり信頼できません。argszフィールドはユーザーアプリケーションが提供するデータ量を示しますが、正しいサイズが十分かどうかの検証はカーネルの責任です。

互換性確認¶

IOMMU UAPI拡張により構造体サイズが増加した場合、IOMMU UAPIコードは以下のケースを処理する必要があります：

  1. ユーザーとカーネルが正確なサイズを一致させている

  2. 古いユーザーで、古いカーネルヘッダー（UAPIサイズが小さい）を使用して新しいカーネル（UAPIサイズが大きい）上で動作しているケース

  3. 新しいユーザーで、新しいカーネルヘッダー（UAPIサイズが大きい）を使用して古いカーネル上で動作しているケース

  4. 悪意のある/不正なユーザーが範囲内に収まるが不正なサイズを渡す場合。データにはゴミデータが含まれる可能性があります

機能確認¶

vIOMMUでゲストを起動する際、事前に互換性を確認することをお勧めします。vIOMMUの操作中に発生する一部のエラー（例：キャッシュ無効化失敗など）は、IOMMU仕様の制約によりゲストに丁寧に伝達できないため、ユーザーにとって深刻な障害につながる可能性があります

QEMUなどのユーザーアプリケーションはカーネルUAPIヘッダーをインポートする必要があります。逆相容性は機能フラグごとにサポートされています。例えば、古いQEMU（古いカーネルヘッダー）は新しいカーネルでも動作しますが、新しいQEMU（新しいカーネルヘッダー）は古いカーネルで新しい機能フラグがサポートされていない場合、初期化を拒否する可能性があります。既存コードを新しいカーネルヘッダーで再コンパイルするだけであれば問題ありません。新しいフラグは使用されないためです

IOMMUベンダードライバーは以下の機能をIOMMU UAPI消費者（例：VFIOなど）に報告する必要があります

  1. IOMMU_NESTING_FEAT_SYSWIDE_PASID

  2. IOMMU_NESTING_FEAT_BIND_PGTBL

  3. IOMMU_NESTING_FEAT_BIND_PASID_TABLE

  4. IOMMU_NESTING_FEAT_CACHE_INVLD

  5. IOMMU_NESTING_FEAT_PAGE_REQUEST

VFIOを例にすると、VFIOユーザースペースからのリクエスト（例：QEMU）に対して、VFIOカーネルコードがIOMMUベンダードライバーが上記機能をサポートしているかを照会します。照会結果はユーザースペースの呼び出し元に報告されます。詳細は VFIO - 「仮想ファンクション I/O」 .

VFIOとのデータやり取り例¶

一般的なユーザースペースドライバーフレームワークであるVFIOはすでにIOMMUを意識しており、デバイスモデル、グループ、保護ドメインなどの多くの主要な概念を共有しています。他のユーザードライバーフレームワークもIOMMU UAPIをサポートするように拡張可能ですが、これは本ドキュメントの範囲外です

この密接なVFIO-IOMMUインターフェースでは、IOMMU UAPIデータの最終消費者はホストIOMMUドライバーです。VFIOはユーザーとカーネル間のデータ転送、機能確認、セキュリティ、プロセスアドレス空間ID（PASID）のライフサイクル管理を支援します

VFIOレイヤーはIOMMUドライバーにデータ構造を下位に伝えます。以下のパターンに従います

struct {
     __u32 argsz;
     __u32 flags;
     __u8  data[];
};

ここでdata[]にはIOMMU UAPIデータ構造が含まれています。VFIOは自身のフラグに基づいてデータを束ねたり、サイズを解析したりする自由があります

ユーザーデータのサイズと機能セットを決定するために、argszとflags（または同等のもの）もIOMMU UAPIデータ構造に埋め込まれています

「__u32 argsz」フィールドは always 各構造体の先頭に位置しています。

例:

struct iommu_cache_invalidate_info {
     __u32   argsz;
     #define IOMMU_CACHE_INVALIDATE_INFO_VERSION_1 1
     __u32   version;
     /* IOMMU paging structure cache */
     #define IOMMU_CACHE_INV_TYPE_IOTLB      (1 << 0) /* IOMMU IOTLB */
     #define IOMMU_CACHE_INV_TYPE_DEV_IOTLB  (1 << 1) /* Device IOTLB */
     #define IOMMU_CACHE_INV_TYPE_PASID      (1 << 2) /* PASID cache */
     #define IOMMU_CACHE_INV_TYPE_NR         (3)
     __u8    cache;
     __u8    granularity;
     __u8    padding[6];
     union {
             struct iommu_inv_pasid_info pasid_info;
             struct iommu_inv_addr_info addr_info;
     } granu;
};

VFIOは自身のargszとflagsを確認し、適切なIOMMU UAPI関数を呼び出します。ユーザーのポインタはIOMMUレイヤーに渡され、さらに処理されます。責任の分担は以下の通りです：

  • ジェネリックIOMMUレイヤーは、現在のカーネルバージョンのUAPIデータに基づいてargszの範囲を確認します。

  • ジェネリックIOMMUレイヤーは、フラグ内のゼロでない予約ビット、パディングフィールド、および非対応バージョンのUAPIデータの内容を確認します。これにより、今後これらのフィールドやフラグが使用される際にユーザー空間が破壊されることを防ぎます。

  • ベンダーベースのIOMMUドライバーは、ベンダーフラグに基づいてargszを確認します。UAPIデータはフラグに基づいて消費されます。ベンダースペシフィックな今後の拡張機能において、ベンダー独自の未加工のargsz値にアクセス可能です。現在は自身でcopy_from_user()を実行していません。今後の一部のシナリオでは、構造体定義外のベンダーデータを扱うために__userポインタが提供される可能性があります。

IOMMUコードはUAPIデータを2つのカテゴリに分類して処理します：

  • 構造体にベンダーデータが含まれる場合（例: iommu_uapi_cache_invalidate()）

  • 構造体にジェネリックデータのみが含まれる場合（例: iommu_uapi_sva_bind_gpasid()）

内核ユーザーとのUAPI共有¶

カーネル内ユーザーと共有されるUAPIについては、呼び出し元を区別するためラッパー関数が提供されています。例えば、

ユーザー空間からの呼び出し元

int iommu_uapi_sva_unbind_gpasid(struct iommu_domain *domain,
                                 struct device *dev,
                                 void __user *udata)

カーネル内からの呼び出し元

int iommu_sva_unbind_gpasid(struct iommu_domain *domain,
                            struct device *dev, ioasid_t ioasid);

概要の HDIO_ ioctlコール¶

  • Edward A. Falk <efalk@google.com>

2004年11月

このドキュメントでは、HD/IDEレイヤーでサポートされているioctl(2)コールを説明しています。これらはLinux 2.6以降主にdrivers/ide/ide.cとdrivers/block/scsi_ioctl.cで実装されています

ioctl値は<linux/hdreg.h>に記載されています。この執筆時点では以下の通りです：

以下に示す情報は、カーネルソースコードの読み込みから得られたものです。時間とともに修正される可能性があります。

一般:

指定がない限り、すべてのioctlコールは成功時に0を返し、エラー時にerrnoが適切な値に設定されて-1を返します。

指定がない限り、すべてのioctl呼び出しはデータのコピーに失敗した場合、ユーザーアドレス空間へのコピーに失敗した際に-1を返し、errnoにEFAULTを設定します。

指定がない限り、すべてのデータ構造と定数は<linux/hdreg.h>で定義されています。

HDIO_GETGEO

デバイスの幾何学的パラメータを取得

usage:

struct hd_geometry geom;

ioctl(fd, HDIO_GETGEO, &geom);
入力:

none

出力:

hd_geometry構造体に含まれる項目:

ヘッド数

ヘッド数

セクタ数

セクタ/トラック数

シリンダー数

シリンダー数（65536で割った余り）

start

このパーティションの開始セクタ。
エラー戻り:

  • EINVAL

    デバイスがディスクドライブまたはフロッピードライブでない場合、またはユーザーがNULLポインタを渡した場合

注:

現代のディスクドライブでは特に役立ちません。現代のドライブは、シリンダーゲオメトリーという抽象概念を用いず、セクタ番号で直接アドレス指定されています（LBAアドレス指定）。実際のドライブのゲオメトリーは変化する可能性があります。現在（2004年11月時点）では、ゲオメトリー値は「BIOS」の値です。これはLinuxが最初に起動した際のドライブの設定を示しています。

hd_geometry構造体のシリンダーフィールドは符号なしのshort型であり、これによりほとんどのアーキテクチャでは、65535トラックを超えるドライブでは意味のある値が返されません。

startフィールドは符号なしのlong型であり、219GBを超えるディスクでは意味のある値を含みません。

HDIO_GET_UNMASKINTR

現在のアンマスク設定を取得

usage:

long val;

ioctl(fd, HDIO_GET_UNMASKINTR, &val);
入力:

none

出力:

ドライブの現在のアンマスク設定の値

HDIO_SET_UNMASKINTR

I/O中でも他のIRQを許可

usage:

unsigned long val;

ioctl(fd, HDIO_SET_UNMASKINTR, val);
入力:

新しいアンマスクフラグの値

出力:

none

エラー戻り値:

  • パーティションではなく全体のディスクデバイスに対して呼び出された場合、EINVALが発生します

  • EACCES アクセス拒否：CAP_SYS_ADMINが必要

  • サポート範囲外の値[0 1]が指定された場合、EINVALが発生します

  • コントローラーがビジー状態です

HDIO_GET_MULTCOUNT

現在のIDEブロックモード設定を取得

usage:

long val;

ioctl(fd, HDIO_GET_MULTCOUNT, &val);
入力:

none

出力:

現在のIDEブロックモード設定の値。これはドライブが割り込みごとに転送するセクタ数を制御します。

HDIO_SET_MULTCOUNT

IDEブロックモードを変更

usage:

int val;

ioctl(fd, HDIO_SET_MULTCOUNT, val);
入力:

新しいIDEブロックモード設定の値。これはドライブが割り込みごとに転送するセクタ数を制御します。

出力:

none

エラー戻り値:

  • パーティションではなく全体のディスクデバイスに対して呼び出された場合、EINVALが発生します

  • EACCES アクセス拒否：CAP_SYS_ADMINが必要

  • サポートされていない値が指定された場合、EINVALが発生します

  • コントローラーがビジー状態またはブロックモードがすでに設定されている場合、EBUSYが発生します

  • ドライブが新しいブロックモードを受容しなかった場合、EIOが発生します

注:

ソースコードのコメント:

This is tightly woven into the driver->do_special cannot
touch.  DON'T do it again until a total personality rewrite
is committed.

ブロックモードがすでに設定されている場合、このioctlは-EBUSYで失敗します

HDIO_GET_QDMA

use-qdmaフラグを取得

2.6.8.1以降、実装されていない

HDIO_SET_XFER

proc経由で転送速度を設定

2.6.8.1以降、実装されていない

HDIO_OBSOLETE_IDENTITY

非推奨、使用しないでください

HDIO_GET_IDENTITY（以下参照）と同じですが、ドライブのアイデンティティ情報の最初の142バイトのみを返します。

HDIO_GET_IDENTITY

IDE識別情報の取得

usage:

unsigned char identity[512];

ioctl(fd, HDIO_GET_IDENTITY, identity);
入力:

none

出力:

ATAドライブのアイデンティティ情報。詳細についてはATA仕様のIDENTIFY DEVICEおよびIDENTIFY PACKET DEVICEコマンドを参照してください。

エラー戻り:

  • パーティションではなく全体のディスクデバイスに対して呼び出された場合、EINVALが発生します

  • IDENTIFY DEVICE情報が利用不可。ENOMSGが発生します

注:

ドライブがスキャンされた際の情報を返します。一部の情報は変更される可能性があり、このioctlはドライブを再スキャンして情報の更新を行いません。

この情報はまた/proc/ide/hdX/identifyからも取得可能です

HDIO_SET_NICE

niceフラグを設定

usage:

unsigned long nice;

...
ioctl(fd, HDIO_SET_NICE, nice);
入力:

nice フラグのビットマスク

出力:

none

エラー戻り:

  • EACCES アクセス拒否：CAP_SYS_ADMINが必要

  • DSC_OVERLAP と NICE_1 以外のフラグが設定されている

この ioctl はユーザーが提供した値から DSC_OVERLAP と NICE_1 フラグを設定します

nice フラグは linux/hdreg.h に記載されており、IDE_NICE_DSC_OVERLAP から始まります。これらの値はシフトを表します

HDIO_DRIVE_RESET

デバイスリセットを実行

usage:

int args[3]

...
ioctl(fd, HDIO_DRIVE_RESET, args);
入力:

none

出力:

none

エラー戻り:

  • EACCES アクセス拒否：CAP_SYS_ADMINが必要

  • ENXIO そのようなデバイスはありません: phy が死んでいたか ctl_addr == 0

HDIO_DRIVE_TASKFILE

rawタスクファイルを実行

注意:

ANSI ATA 仕様書を持っていない場合は、この ioctl を無視するべきです

  • ドライブの「タスクファイル」レジスタに直接 ATA ディスクコマンドを実行します。ADMIN および RAWIO アクセス権限が必要です

usage:

struct {

  ide_task_request_t req_task;
  u8 outbuf[OUTPUT_SIZE];
  u8 inbuf[INPUT_SIZE];
} task;
memset(&task.req_task, 0, sizeof(task.req_task));
task.req_task.out_size = sizeof(task.outbuf);
task.req_task.in_size = sizeof(task.inbuf);
...
ioctl(fd, HDIO_DRIVE_TASKFILE, &task);
...

入力:

(ioctl に渡されるメモリ領域の詳細については下記を参照)

io_ports[8]

タスクファイルレジスタに書き込む値

hob_ports[8]

拡張コマンド用の高オーダーバイト

out_flags

有効なレジスタを示すフラグ

in_flags

返却すべきレジスタを示すフラグ

data_phase

以下を参照

req_cmd

実行するコマンドの種類

out_size

出力バッファのサイズ

outbuf

ディスクに送信するデータのバッファ

inbuf

ディスクから受信するデータのバッファ (参照 [1])

出力:

io_ports[]

タスクファイルレジスタに返される値

hob_ports[]

拡張コマンド用の高オーダーバイト

out_flags

有効なレジスタを示すフラグ (参照 [2])

in_flags

返却すべきレジスタを示すフラグ

outbuf

ディスクに送信するデータのバッファ (参照 [1])

inbuf

ディスクから受信するデータのバッファ
エラー戻り:

  • EACCES CAP_SYS_ADMIN または CAP_SYS_RAWIO の権限が設定されていない。

  • ENOMSG デバイスがディスクドライブでない。

  • ENOMEM タスク用のメモリを確保できなかった。

  • EFAULT req_cmd == TASKFILE_IN_OUT (2.6.8 以降未実装)

  • EPERM

    req_cmd == TASKFILE_MULTI_OUT かつドライブのmulti-countが設定されていない。

  • EIO ドライブがコマンドを実行できなかった。

注:

[1] 以下の注意事項を読みましょう 注意深く. このIOCTLは多くの落とし穴があります。このIOCTLを使用する際には極めて注意が必要です。誤りは簡単にデータを破壊したりシステムを停止したりする可能性があります。

[2] 入力および出力バッファは、使用されていなくてもユーザーからコピーされ、ユーザーに戻して書き込まれます。

[3] out_flagsに1つ以上のビットが設定され、in_flagsがゼロの場合、in_flags.allに以下の値が使用され、完了時にin_flagsに戻して書き込まれます。

  • IDE_TASKFILE_STD_IN_FLAGS | (IDE_HOB_STD_IN_FLAGS << 8) がLBA48アドレッシングがドライブで有効な場合

  • IDE_TASKFILE_STD_IN_FLAGS がCHS/LBA28の場合

in_flags.allと各有効ビットフィールドの関係はエンドイアンネスに応じて反転します。幸いにも、TASKFILEはinflags.b.dataビットのみを使用し、他のビットは無視します。結果として、どのエンドイアンネスのマシンでも、完了時にin_flagsを変更する以外に影響はありません。

[4] SELECTのデフォルト値はポートチップセットごとに4つのドライブの場合を除き、(0xa0|DEV_bit|LBA_bit)です。4つのドライブをポートチップセットごとに使用する場合、最初のペアには(0xa0|DEV_bit|LBA_bit)、次のペアには(0x80|DEV_bit|LBA_bit)が使用されます。

[5] ioctlの引数は、ide_task_request_t構造体を含むメモリ領域へのポインタであり、その後に送信するデータのオプションバッファ、および受信するデータのオプションバッファが続きます。

in_flags

data_phase

  1. ドライブがコマンドを失敗しました (EIO)。

  2. out_flags の1つ以上のビットが設定されています。

  3. 要求された data_phase が TASKFILE_NO_DATA です。

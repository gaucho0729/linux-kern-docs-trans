3. CECピンフレームワークエラー注入¶

CEC Pin Frameworkは、CECバスに低レベルのサポートのみを持つCECハードウェア用のコアなCECフレームワークです。現在のほとんどのハードウェアでは、ハードウェアがCECバスを駆動する高レベルのCECサポートが提供されていますが、一部の古いデバイスはそれほど複雑ではありません。しかし、このフレームワークは、Raspberry PiなどのGPIOにCECピンを接続することで、CECアダプターを構築することも可能です。

このようにCECアダプターを構築する面白さは、バス全体を制御できるため、エラーの注入を簡単にサポートできる点にあります。これは、CECアダプターがエラー状態をどれだけ適切に処理できるかをテストするのに最適な環境です。

現在は、CECラインが直接プルアップGPIOラインに接続されている場合のcec-gpioドライバ（）と、AllWinner A10/A20 drmドライバのみがこのフレームワークをサポートしています。

もし CONFIG_CEC_PIN_ERROR_INJ 有効になっている場合、debugfsを通じてエラー注入が利用可能です。具体的には、 /sys/kernel/debug/cec/cecX/ に新たに error-inj ファイル。

注意

エラー注入コマンドは安定したABIではありませんので、今後変更される可能性があります。

With cat error-inj ここでは、可能なコマンドと現在のエラー注入状態を確認できます:

$ cat /sys/kernel/debug/cec/cec0/error-inj

#   <op> tx-clear  clear all tx error injections for <op>
#

#   <op>[,<mode>] rx-nack              NACK the message instead of sending an ACK
#   <op>[,<mode>] rx-low-drive <bit>   force a low-drive condition at this bit position
#   <op>[,<mode>] rx-add-byte          add a spurious byte to the received CEC message
#   <op>[,<mode>] rx-remove-byte       remove the last byte from the received CEC message
#   <op>[,<mode>] rx-arb-lost <poll>   generate a POLL message to trigger an arbitration lost
#

#   tx-ignore-nack-until-eom           ignore early NACKs until EOM
#   tx-custom-low-usecs <usecs>        define the 'low' time for the custom pulse
#   tx-custom-high-usecs <usecs>       define the 'high' time for the custom pulse
#   tx-custom-pulse                    transmit the custom pulse once the bus is idle
#

# <poll>     CEC poll message used to test arbitration lost (0x00-0xff, default 0x0f)
# <usecs>    microseconds (0-10000000, default 1000)

clear

エラー注入コマンドを error-inj を使用して echo 'cmd' >error-inj または cat cmd.txt >error-injの部分で、 cat error-inj の出力には現在のエラー注入コマンドが含まれています。出力結果をファイルに保存して、後の error-inj の入力として使用できます。

3.1. 基本的な構文¶

先頭のスペース/タブは無視されます。次の文字が # であるか、行末に達した場合、その行は無視されます。それ以外の場合はコマンドが期待されます。

エラー注入コマンドは、受信CECメッセージに関連するものと送信CECメッセージに関連するものの2つの主要なグループに分類されます。さらに、既存のエラー注入コマンドをクリアするコマンドや、CECバスにカスタムパルスを生成するコマンドもあります。

ほとんどのエラー注入コマンドは、特定のCECオペコードに対して実行可能です。また、すべてのオペコードに対して実行することも可能です（any）。各コマンドには「モード」と呼ばれる設定があり、 off （既存のエラー注入コマンドを無効化するために使用可能） once （デフォルト）は次の受信または送信メッセージに対してエラー注入を1回だけ実行します。 always を常に実行し、 toggle は送信または受信ごとにエラー注入をトグルします。

したがって、‘any rx-nack’は次の受信CECメッセージをNACKします。‘any,always rx-nack’はすべての受信CECメッセージをNACKします。‘0x82,toggle rx-nack’はアクティブソースメッセージが受信された場合のみNACKし、その実行は受信メッセージの間隔ごとに実行されます。

エラー注入モード once でエラーが注入された後、エラー注入コマンドは自動的にクリアされるため、 once は一時的な処理です。

すべての <op> とエラー注入コマンドの組み合わせは共存可能です。したがって、これは問題ありません:

0x9e tx-add-bytes 1
0x9e tx-early-eom
0x9f tx-add-bytes 2
any rx-nack

すべての4つのエラー注入コマンドが同時に有効になります。

ただし、同じ <op> とコマンドの組み合わせで異なる引数を指定した場合:

0x9e tx-add-bytes 1
0x9e tx-add-bytes 2

では、2番目のコマンドが1番目のコマンドを上書きします。

3.2. エラーインジェクションをクリア¶

clear

すべてのエラーインジェクションをクリア。

rx-clear

すべての受信エラーインジェクションをクリア

tx-clear

すべての送信エラーインジェクションをクリア

<op> clear

指定されたオペコードのすべてのエラーインジェクションをクリア

<op> rx-clear

指定されたオペコードのすべての受信エラーインジェクションをクリア

<op> tx-clear

指定されたオペコードのすべての送信エラーインジェクションをクリア

3.3. メッセージの受信¶

<op>[,<mode>] rx-nack

このCECアダプタに送信されるブロードキャストメッセージおよびメッセージをNACKします。送信者が最初のバイトをNACKした後でも送信を続けた場合、メッセージのすべてのバイトがNACKされます。

<op>[,<mode>] rx-low-drive <bit>

このビット位置でロー・ドライブ状態を強制します。<op>が特定のCECオペコードを指定している場合、ビット位置は18以上でなければなりません。それ以外の場合、オペコードはまだ受信されていません。これは送信機がロー・ドライブ状態を正しく処理できるかをテストし、エラーを正しく報告するためのものです。注意点として、最初の4ビットでのロー・ドライブは送信機によって仲裁失敗状態と解釈されることがあります。これは実装依存です。

<op>[,<mode>] rx-add-byte

受信したCECメッセージに不要な0x55バイトを追加します（メッセージが15バイト以下の場合）。これは、不要なバイトが無視されるようにしてハイレベルプロトコルをテストするためのものです。

<op>[,<mode>] rx-remove-byte

受信したCECメッセージから最後のバイトを削除します（メッセージが2バイト以上の場合）。これは、短すぎるメッセージが無視されるようにしてハイレベルプロトコルをテストするためのものです。

<op>[,<mode>] rx-arb-lost <poll>

仲裁失敗状態をトリガーするPOLLメッセージを生成します。このコマンドは、 <op> 値は next または all。開始ビットが受信されると、CECアダプタは送信モードに切り替えられ、POLLメッセージを送信します。デフォルトでは0x0fですが、 <poll> 引数。

このコマンドは、リモートのCEC送信機における仲裁失敗状態をテストするために使用できます。仲裁は、2つのCECアダプタが同時にメッセージを送信し始めたときに発生します。その場合、リーディングゼロが多い送信者が勝ち、もう一方の送信機は送信を停止する必要があります（‘仲裁失敗’）。このテストは非常に困難ですが、このエラーインジェクションコマンドを使用することで可能です。

リモートCEC送信機が論理アドレス0（‘TV’）を持つ場合、このコマンドは機能しません。なぜなら、そのアドレスは常に勝つからです。

3.4. メッセージの送信¶

tx-ignore-nack-until-eom

この設定はCECメッセージの送信動作を変更します。通常、受信側がバイトをNACKした時点で送信が停止しますが、仕様では全メッセージを送信した後でACKビットを確認する方法も許容されています。この動作は推奨されません。なぜなら、CECバスを必要以上に忙しくする意味がないからです。特にバスの速度が遅いためです。

この設定は、受信側が送信側がNACKを無視し、メッセージの終わりまで行う場合の挙動をテストするのに使用できます。

<op>[,<mode>] tx-no-eom

EOMビットを設定しないでください。通常、メッセージの最後のバイトにはEOM（End-Of-Message）ビットが設定されています。このコマンドでは送信が停止するだけで、EOMを送信しません。これにより、受信側がこのケースをどのように処理するかをテストできます。通常、受信側は一定時間後にアイドル状態に戻します。

<op>[,<mode>] tx-early-eom

EOMビットを1バイト早すぎたタイミングで設定します。これは明らかに2バイト以上のメッセージにのみ適用可能です。EOMビットは2番目に最後のバイトに設定され、最終バイトには設定されません。この場合、受信側は最後のバイトを無視すべきです。結果として生成されるメッセージがこの理由で十分に短いため、通常は全体が無視されます。受信側は最後のバイトが送信された後、アイドル状態にいるべきです。

<op>[,<mode>] tx-add-bytes <num>

追加 <num> (1-255)の誤ったバイトをメッセージに追加します。追加されたバイトはメッセージ内のバイト位置の値を持ちます。たとえば2バイトのメッセージ（例：Get CEC Versionメッセージ）を送信し、2バイトを追加すると、リモートCECアダプターが受信する完全なメッセージは 0x40 0x9f 0x02 0x03.

このコマンドは受信側のバッファオーバーフローをテストするために使用できます。たとえば、最大メッセージサイズ（16バイト）を超えて受信した場合の挙動を確認できます。

<op>[,<mode>] tx-remove-byte

メッセージが少なくとも2バイト以上である場合、最後のバイトを削除します。受信側は短すぎるメッセージを無視すべきです。

<op>[,<mode>] tx-short-bit <bit>

このビット周期を許容範囲より短くします。ビット位置はACKビットであってはなりません。<op>が特定のCECオペコードを指定している場合、ビット位置は少なくとも18に設定しなければなりません（それ以前にオペコードが受信されていないため）。通常、データビットの周期は2.05〜2.75ミリ秒です。このコマンドではこのビットの周期を1.8ミリ秒に設定します。これはCECバスが高電位になる時間を短縮することで実現されます。このビット周期は許容範囲を下回っており、受信側はロー駆動状態で応答すべきです。

ビット位置0〜3の0ビットについては、このコマンドは無視されます。これは、受信機がこれらの最初の4ビットで仲裁失敗状態を検出するためであり、長すぎる0ビットが検出された場合の動作は未定義です。

<op>[,<mode>] tx-long-bit <bit>

このビット周期を有効な範囲を超えて長くしてください。このビット位置はアサーションビット（Ackビット）であってはなりません。<op>が特定のCECオペコードを指定している場合、ビット位置は少なくとも18以上でなければなりません（それ以前にオペコードが受信されていないため）。通常、データビットの周期は2.05〜2.75ミリ秒です。このコマンドにより、このビットの周期は2.9ミリ秒になります。これはCECバスが高電位になる時間を長くすることで実現されます。

このビット周期が有効な範囲を超えて長くても、受信機がどのように反応するかは未定義です。受信機はこれを単に受け入れるかもしれませんが、タイムアウトしてアイドル状態に戻る可能性もあります。残念ながらCEC仕様書にはこの点について記載されていません。

ビット位置0〜3の0ビットについては、このコマンドは無視されます。これは、受信機がこれらの最初の4ビットで仲裁失敗状態を検出するためであり、長すぎる0ビットが検出された場合の動作は未定義です。

<op>[,<mode>] tx-short-start

このスタートビット周期を許容範囲より短くしてください。通常、スタートビットの周期は4.3〜4.7ミリ秒です。このコマンドにより、スタートビットの周期は4.1ミリ秒になります。これはCECバスが高電位になる時間を短くすることで実現されます。このスタートビット周期は許容範囲より短く、受信機はこの検出時にアイドル状態に戻るべきです。

<op>[,<mode>] tx-long-start

このスタートビット周期を許容範囲より長くしてください。通常、スタートビットの周期は4.3〜4.7ミリ秒です。このコマンドにより、スタートビットの周期は5ミリ秒になります。これはCECバスが高電位になる時間を長くすることで実現されます。このスタートビット周期は許容範囲より長く、受信機はこの検出時にアイドル状態に戻るべきです。

このスタートビット周期が許容範囲より長くても、受信機がどのように反応するかは未定義です。受信機はこれを単に受け入れるかもしれませんが、タイムアウトしてアイドル状態に戻る可能性もあります。残念ながらCEC仕様書にはこの点について記載されていません。

<op>[,<mode>] tx-last-bit <bit>

このビットの後で送信を停止してください。<op>が特定のCECオペコードを指定している場合、ビット位置は少なくとも18以上でなければなりません（それ以前にオペコードが受信されていないため）。このコマンドは、メッセージが突然停止した際の受信機の反応をテストするのに使用できます。受信機はタイムアウトしてアイドル状態に戻るべきです。

<op>[,<mode>] tx-low-drive <bit>

このビット位置でロー・ドライブ条件を強制します。<op>が特定のCECオペコードを指定している場合、ビット位置は少なくとも18以上でなければなりません。それ以外の場合、オペコードはまだ受信されていません。これは受信機がロー・ドライブ条件をどのように処理するかをテストするために使用できます。注意: ビット位置が0〜3の場合、受信機はこれを仲裁喪失条件と解釈する可能性があります。これは実装依存です。

3.5. カスタムパルス¶

tx-custom-low-usecs <usecs>

この値は、カスタムパルスがCECラインをローに引き下げる時間（マイクロ秒単位）を定義します。デフォルトは1000マイクロ秒です。

tx-custom-high-usecs <usecs>

この値は、カスタムパルスがCECラインをハイに保つ時間（マイクロ秒単位）を定義します。ただし、他のCECアダプターがその間にラインをローに引き下げる場合があります。デフォルトは1000マイクロ秒です。カスタムパルスのトータル周期は tx-custom-low-usecs + tx-custom-high-usecs.

<op>[,<mode>] tx-custom-bit <bit>

通常のデータビットの代わりにカスタムビットを送信します。ビット位置はアサーションビットであってはなりません。<op>が特定のCECオペコードを指定している場合、ビット位置は少なくとも18以上でなければなりません。それ以外の場合、オペコードはまだ受信されていません。

<op>[,<mode>] tx-custom-start

通常のスタートビットの代わりにカスタムビットを送信します。

tx-custom-pulse

CECバスがアイドル状態になった直ちに単一のカスタムパルスを送信します。

6. Linux USB Video Class (UVC) ドライバ¶

このファイルはUVCドライバーのドライバ固有の特徴、例えばドライバ固有のioctlや実装ノートなどについて記述しています。

質問やコメントはLinux UVC開発用メーリングリストに送信してください。メールアドレスは linux-uvc-devel@lists.berlios.de.

6.1. 拡張ユニット(XU)サポート¶

6.1.1. はじめに¶

UVC仕様では拡張ユニット(XU)を通じてベンダー固有の拡張が可能ですが、Linux UVCドライバーは2つのメカニズムを通じて拡張ユニット制御(XU制御)をサポートしています。

  • XU制御をV4L2制御にマッピングする方法

  • ドライバ固有のioctlインターフェースを通じた方法

最初の方法では、一般的なV4L2アプリケーションが特定のXU制御をV4L2制御にマッピングすることで使用可能となり、通常の制御列挙時に表示されます。

2番目のメカニズムではアプリケーションがXU制御にアクセスするにはuvcvideo固有の知識が必要ですが、ユーザー空間にUVC XU概念全体を公開して最大の柔軟性を提供します。

両方のメカニズムは補完し合い、以下でより詳しく説明します。

6.1.2. 制御マッピング¶

UVCドライバーはユーザー空間アプリケーションが実行時において「制御マッピング」と呼ばれるものを定義するためのAPIを提供しています。これにより、個々のXU制御またはバイト範囲が新しいV4L2制御にマッピングされ、通常のV4L2制御（例えば明るさ、コントラストなど）と同様に動作します。ただし、このようなV4L2制御の読み書きは関連するXU制御の読み書きをトリガーします。

これらの制御マッピングを作成するためのioctlはUVCIOC_CTRL_MAPと呼ばれます。以前のドライババージョン（0.2.0以前）では、XU制御情報をUVCドライバーに渡すために別のioctl（UVCIOC_CTRL_ADD）を使用していましたが、新しいuvcvideoバージョンではデバイスから直接情報を取得するため、これが必要ありません。

UVCIOC_CTRL_MAP ioctlの詳細については、以下の「IOCTLリファレンス」セクションを参照してください。

  1. ドライバ固有のXU制御インターフェース

テスト目的やファームウェアアップロード、バイナリ制御へのアクセスなど、XU制御を直接アクセスする必要があるアプリケーションには、ドライバ固有のioctlであるUVCIOC_CTRL_QUERYを通じたもう一つのメカニズムが提供されています。

このioctlの呼び出しにより、アプリケーションはUVCドライバーに直接マッピングされる低レベルのUVC制御リクエストにクエリを送信できます。

このようなリクエストを行うには、制御の拡張ユニットのUVCユニットIDと制御セレクターの情報が必要です。この情報はアプリケーション内でハードコードするか、UVCディスクリプタの解析など他の方法で取得する必要があります。また、メディアコントローラーAPIが利用可能な場合は、デバイスのエンティティを列挙するためのAPIを使用することもできます。

制御サイズが既知でない場合、まずUVC_GET_LENリクエストを実行して十分なサイズのバッファを確保し、正しい値にバッファサイズを設定する必要があります。同様に、特定の制御に対してUVC_GET_CURまたはUVC_SET_CURが有効なリクエストかどうかを確認するには、UVC_GET_INFOリクエストを実行する必要があります。結果のバイトのビット0（GETサポート）とビット1（SETサポート）が有効なリクエストを示します。

UVCIOC_CTRL_QUERY ioctlが追加されたため、UVCIOC_CTRL_GETとUVCIOC_CTRL_SET ioctlはその機能が前者のioctlのサブセットであるため非推奨となりました。現時点ではまだサポートされていますが、アプリケーション開発者にはUVCIOC_CTRL_QUERYの使用を推奨します。

UVCIOC_CTRL_QUERY ioctlの詳細については、以下に掲載されている「IOCTLリファレンス」セクションを参照してください。

6.1.3. セキュリティ¶

現在のAPIは、細かいアクセス制御機能を提供していません。UVCIOC_CTRL_ADDおよびUVCIOC_CTRL_MAP ioctlはスーパーユーザーの権限が必要です。

改善案は歓迎されます。

6.1.4. デバッグ¶

XU制御や一般的な制御に関する問題をデバッグする際には、モジュールパラメータ「trace」のUVC_TRACE_CONTROLビットを有効にすることを推奨します。これにより、システムログに追加の出力が記録されます。

6.1.5. IOCTLリファレンス¶

6.1.5.1. UVCIOC_CTRL_MAP - UVC制御をV4L2制御にマッピング¶

引数: struct uvc_xu_control_mapping

説明:

このioctlは、UVC制御またはUVC制御の一部をV4L2制御にマッピングします。マッピングが定義されると、ユーザー空間アプリケーションはV4L2制御APIを通じてベンダー定義のUVC制御にアクセスできます。

マッピングを作成するには、アプリケーションはuvc_xu_control_mapping構造体を既存のUVC制御（UVCIOC_CTRL_ADDで定義）と新しいV4L2制御に関する情報を埋め込みます。

UVC制御は複数のV4L2制御にマッピングできます。例えば、UVCパン/チルト制御は別個のパンとチルトのV4L2制御にマッピングされることがあります。UVC制御は'size'と'offset'フィールドを使用して非重複のフィールドに分割され、それぞれ独立してV4L2制御にマッピングされます。

符号付き整数V4L2制御の場合、data_typeフィールドをUVC_CTRL_DATA_TYPE_SIGNEDに設定する必要があります。他の値は現在無視されています。

戻り値:

成功時は0が返されます。エラー時は-1が返され、errnoが適切に設定されます。

ENOMEM

操作に必要なメモリが不足しています。

EPERM

十分な権限がありません（スーパーユーザーの権限が必要です）。

EINVAL

該当するUVC制御がありません。

EOVERFLOW

指定されたオフセットとサイズがUVC制御をオーバーフローします。

EEXIST

マッピングがすでに存在しています。

データタイプ:

* struct uvc_xu_control_mapping

__u32   id              V4L2 control identifier
__u8    name[32]        V4L2 control name
__u8    entity[16]      UVC extension unit GUID
__u8    selector        UVC control selector
__u8    size            V4L2 control size (in bits)
__u8    offset          V4L2 control offset (in bits)
enum v4l2_ctrl_type
        v4l2_type       V4L2 control type
enum uvc_control_data_type
        data_type       UVC control data type
struct uvc_menu_info
        *menu_info      Array of menu entries (for menu controls only)
__u32   menu_count      Number of menu entries (for menu controls only)

* struct uvc_menu_info

__u32   value           Menu entry value used by the device
__u8    name[32]        Menu entry name


* enum uvc_control_data_type

UVC_CTRL_DATA_TYPE_RAW          Raw control (byte array)
UVC_CTRL_DATA_TYPE_SIGNED       Signed integer
UVC_CTRL_DATA_TYPE_UNSIGNED     Unsigned integer
UVC_CTRL_DATA_TYPE_BOOLEAN      Boolean
UVC_CTRL_DATA_TYPE_ENUM         Enumeration
UVC_CTRL_DATA_TYPE_BITMASK      Bitmask

6.1.5.2. UVCIOC_CTRL_QUERY - UVC XU制御の照会¶

引数: struct uvc_xu_control_query

説明:

このioctlコマンドは、拡張ユニットIDと制御セレクタで指定されたUVC XU制御を照会します。

UVC仕様で記述されている低レベル制御リクエストに密接して対応する複数の照会が利用可能です。これらのリクエストは以下の通りです。

UVC_GET_CUR

制御の現在値を取得します。

UVC_GET_MIN

制御の最小値を取得します。

UVC_GET_MAX

制御の最大値を取得します。

UVC_GET_DEF

制御のデフォルト値を取得します。

UVC_GET_RES

制御の解像度（許容される制御値のステップサイズ）を照会します。

UVC_GET_LEN

制御のバイト数を照会します。

UVC_GET_INFO

制御情報ビットマップを照会します。これはget/setリクエストがサポートされているかを示します。

UVC_SET_CUR

制御の値を更新します。

アプリケーションは「size」フィールドを制御の正しい長さに設定する必要があります。例外はUVC_GET_LENおよびUVC_GET_INFOの照会で、それぞれ「size」は2および1に設定する必要があります。「data」フィールドは、指定されたデータバイト数を保持できる有効な書き込み可能なバッファを指さなければなりません。

デバイスから直接データがコピーされ、ドライバ側の処理は行われません。アプリケーションはデータバッファのフォーマット（リトルエンディアン/ビッグエンディアンの変換を含む）を責任を持って行う必要があります。これは特にUVC_GET_LENリクエストの結果に重要で、デバイスは常にリトルエンディアン16ビット整数として結果を返します。

戻り値:

成功時は0が返されます。エラー時は-1が返され、errnoが適切に設定されます。

ENOENT

デバイスが指定された制御をサポートしていないか、または指定された拡張ユニットが見つからない場合です。

ENOBUFS

指定されたバッファサイズが正しくありません（大きすぎるか小さすぎる）。

EINVAL

無効なリクエストコードが渡されました。

EBADRQC

指定されたリクエストは指定された制御によってサポートされていません。

EFAULT

データポインタがアクセスできないメモリ領域を参照しています。

データタイプ:

* struct uvc_xu_control_query

__u8    unit            Extension unit ID
__u8    selector        Control selector
__u8    query           Request code to send to the device
__u16   size            Control data size (in bytes)
__u8    *data           Control value

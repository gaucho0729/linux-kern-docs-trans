4. リクエストAPI¶

Request APIは、V4L2が現代のデバイス（ステートレスコーデック、複雑なカメラパイプライン、…）およびAPI（Android Codec v2）の要件に対応できるように設計されています。このような要件の一つは、同じパイプラインに属するデバイスがフレームごとに再構成し、密接に協働できるようにすることです。もう一つは、ステートレスコーデックをサポートすることであり、これには効率的に使用するため、特定のフレーム（いわゆる「フレームごとの制御」）に制御を適用する必要があります。

初期の使用例はV4L2でしたが、メディアコントローラーを使用する他のサブシステムにも拡張可能です。

Request APIなしでこれらの機能をサポートすることは常に不可能であり、可能であっても極めて効率が悪いです。ユーザー空間では、メディアパイプラインですべてのアクティビティをフラッシュし、次のフレームのために再構成し、その構成で処理するバッファをキューイングし、すべてがデキューイング可能になるのを待つ必要があります。これにより、バッファキューの目的が台無しになります。実際には一度に1つのバッファしかキューイングされません。

Request APIは、パイプライン（メディアコントローラーのトポロジー＋各メディアエンティティの構成）の特定の構成を特定のバッファに関連付けることができます。これにより、ユーザー空間は、必要なときに期待される結果を得るために、さまざまな構成を持つ複数のタスク（「リクエスト」）を事前にスケジュールできます。リクエスト完了時の構成値も読み取ることができます。

4.1. 一般的な使用法¶

Request APIはメディアコントローラーAPIを拡張し、サブシステム固有のAPIと協働してリクエストの使用をサポートします。メディアコントローラーレベルでは、リクエストはサポートするメディアコントローラーデバイスノードから割り当てられます。その後、リクエストファイル記述子を通じて不透明な方法でライフサイクルが管理されます。リクエストに保存された構成データ、バッファハンドル、処理結果は、リクエストサポートのために拡張されたサブシステム固有のAPI（V4L2 APIなど、明示的なパラメータを取る）を通じてアクセスされます。 request_fd パラメータで指定されたものに。

4.2. リクエストの割り当て¶

ユーザー空間は、 ioctl MEDIA_IOC_REQUEST_ALLOC メディアデバイスノードに対して使用してリクエストを割り当てます。これはリクエストを表すファイル記述子を返します。通常、複数のリクエストが割り当てられます。

4.3. リクエストの準備¶

標準のV4L2 ioctlsは、リクエストファイル記述子を受け取り、そのioctlが該当するリクエストに属し、即時実行されないことを示すことができます。参照してください ioctl MEDIA_IOC_REQUEST_ALLOC この機能をサポートするioctlの一覧については、Configurations set with a request_fd パラメータで設定された設定は即座に適用されるのではなく保存され、バッファがリクエストにキューイングされるまで通常のバッファキューに登録されません。

4.4. リクエストの送信¶

リクエストの設定とバッファが指定されたら、リクエストファイルディスクリプタ上で ioctl MEDIA_REQUEST_IOC_QUEUE を呼び出すことでキューイングできます。リクエストには少なくとも1つのバッファを含まなければなりません。そうでない場合、 ENOENT が返されます。キューイングされたリクエストはその後は変更できません。

注意

For メモリ間デバイス 出力バッファのみリクエストを使用できます。キャプチャバッファには使用できません。キャプチャバッファをリクエストに追加しようとすると、 EBADR エラーを返します。

リクエストが複数のエンティティの設定を含む場合、個々のドライバーが同期して、バッファが処理される前にリクエストパイプラインのトポロジーが適用されるようにします。メディアコントローラードライバーは、ハードウェアの制限により完全なアトミック性が不可能なため、ベストエフォートの実装を行います。

注意

キューイングリクエストと直接バッファキューイングを混在させることはできません。どちらか一方の方法が最初に使用されると、その状態が固定され、 VIDIOC_STREAMOFF が呼ばれるか、デバイスが オフされるまで変更できません。以前にリクエストまたはバッファでキューイングされたバッファを逆に直接キューイングしようとすると、 EBUSY エラーを返します。

制御はリクエストを介さずとも設定できます。設定された制御は、リクエストが使用されているかどうかに関係なく即座に適用されます。

注意

同じ制御をリクエストで設定し、同時に直接設定すると、未定義の挙動を引き起こす可能性があります！

ユーザー空間は poll() リクエストファイルディスクリプタを使用してリクエストが完了するのを待つことができます。リクエストが完了すると、すべての関連バッファがデキューイング可能になり、すべての関連制御が完了時の値に更新された時点でリクエストは完了とみなされます。ユーザー空間はリクエストが完了するのを待つ必要はありません。リクエストの途中で利用可能なバッファは、リクエストの状態とは独立してデキューイングできます。

完了したリクエストには、リクエストが実行された後のデバイスの状態が含まれます。ユーザー空間は、 ioctl VIDIOC_G_EXT_CTRLS を呼び出してリクエストファイルディスクリプタでその状態を照会できます。完了していないリクエストに対して ioctl VIDIOC_G_EXT_CTRLS を呼び出すと、 EBUSY が返されます。ドライバーがリクエストが進行中である間、制御値をいつでも変更する可能性があるためです。

4.5. 再利用と破棄¶

最後に、完了したリクエストは破棄するか再利用できます。呼び出す close() リクエストファイル記述子が要求された場合、そのファイル記述子は使用できなくなり、カーネルがもはや使用していないときにリクエストが解放されます。つまり、リクエストがキューイングされ、その後ファイル記述子が閉じられた場合、ドライバーがリクエストを完了するまで解放されません。

以下の ioctl MEDIA_REQUEST_IOC_REINIT リクエストの状態をクリアし、再度利用可能にします。この操作により状態は保持されず、リクエストは新たに割り当てられたかのように扱われます。

4.6. コーデックデバイスの例¶

使用例として コーデック、リクエストAPIを使用してOUTPUTバッファに適用される特定の制御を関連付けることができます。これにより、ユーザースペースは事前に多くのこのようなバッファをキューイングできます。また、リクエストが完了時に制御の状態をキャプチャできる機能を活用し、変化の可能性のある情報を読み戻すことができます。

コードにすると、リクエストを取得した後、ユーザースペースは制御を割り当て、それにOUTPUTバッファを割り当てることができます:

struct v4l2_buffer buf;
struct v4l2_ext_controls ctrls;
int req_fd;
...
if (ioctl(media_fd, MEDIA_IOC_REQUEST_ALLOC, &req_fd))
        return errno;
...
ctrls.which = V4L2_CTRL_WHICH_REQUEST_VAL;
ctrls.request_fd = req_fd;
if (ioctl(codec_fd, VIDIOC_S_EXT_CTRLS, &ctrls))
        return errno;
...
buf.type = V4L2_BUF_TYPE_VIDEO_OUTPUT;
buf.flags |= V4L2_BUF_FLAG_REQUEST_FD;
buf.request_fd = req_fd;
if (ioctl(codec_fd, VIDIOC_QBUF, &buf))
        return errno;

注意: CAPTUREバッファにはフレームごとの設定を報告するものがないため、リクエストAPIを使用することはできません。

リクエストが完全に準備できたら、ドライバーにキューイングできます:

if (ioctl(req_fd, MEDIA_REQUEST_IOC_QUEUE))
        return errno;

その後、ユーザースペースはpoll()関数を呼び出してリクエストの完了を待つか、CAPTUREバッファをデキューします。ほとんどの場合、CAPTUREバッファをできるだけ早く取得したいので、通常の VIDIOC_DQBUF:

struct v4l2_buffer buf;

memset(&buf, 0, sizeof(buf));
buf.type = V4L2_BUF_TYPE_VIDEO_CAPTURE;
if (ioctl(codec_fd, VIDIOC_DQBUF, &buf))
        return errno;

注意: この例では簡潔さのため、OUTPUTバッファごとに1つのCAPTUREバッファがあると仮定していますが、必ずしもそうする必要はありません。

リクエストが完了したことを確認するためにファイル記述子をポーリングした後、リクエストの完了時に制御値を取得するために呼び出します。 VIDIOC_G_EXT_CTRLSこれは、キャプチャバッファが生成された直ちに値を取得したい一時的な制御に特に役立ちます。

struct pollfd pfd = { .events = POLLPRI, .fd = req_fd };
poll(&pfd, 1, -1);
...
ctrls.which = V4L2_CTRL_WHICH_REQUEST_VAL;
ctrls.request_fd = req_fd;
if (ioctl(codec_fd, VIDIOC_G_EXT_CTRLS, &ctrls))
        return errno;

もはやリクエストが必要なくなった場合は、リクエストを再利用するために ioctl MEDIA_REQUEST_IOC_REINIT…

if (ioctl(req_fd, MEDIA_REQUEST_IOC_REINIT))
        return errno;

…またはファイル記述子を閉じて完全に廃棄できます。

close(req_fd);

4.7. シンプルなキャプチャデバイスの例¶

シンプルなキャプチャデバイスでは、リクエストを使用して特定のCAPTUREバッファに適用する制御を指定できます。

struct v4l2_buffer buf;
struct v4l2_ext_controls ctrls;
int req_fd;
...
if (ioctl(media_fd, MEDIA_IOC_REQUEST_ALLOC, &req_fd))
        return errno;
...
ctrls.which = V4L2_CTRL_WHICH_REQUEST_VAL;
ctrls.request_fd = req_fd;
if (ioctl(camera_fd, VIDIOC_S_EXT_CTRLS, &ctrls))
        return errno;
...
buf.type = V4L2_BUF_TYPE_VIDEO_CAPTURE;
buf.flags |= V4L2_BUF_FLAG_REQUEST_FD;
buf.request_fd = req_fd;
if (ioctl(camera_fd, VIDIOC_QBUF, &buf))
        return errno;

リクエストが完全に準備できたら、ドライバーにキューイングできます:

if (ioctl(req_fd, MEDIA_REQUEST_IOC_QUEUE))
        return errno;

その後、ユーザースペースはバッファをデキューし、リクエストの完了を待ち、制御を照会し、M2M例の上記のようにリクエストを再利用できます。

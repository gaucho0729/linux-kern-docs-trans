4.5.3. メモリ間無状態ビデオデコーダーインターフェース¶

ステートレスデコーダーは、処理されたフレーム間で状態を保持しないで動作するデコーダーです。これは、各フレームが前後のフレームとは無関係に独立してデコードされることを意味し、クライアントがデコード状態を維持し、各デコードリクエストごとにデコーダーに提供する責任があります。これは、ハードウェアとドライバーがデコード状態を維持し、クライアントが単に符号化されたストリームを提供してデコードされたフレームを表示順にデキューするだけでよいというステートフルビデオデコーダーインターフェースとは対照的です。

このセクションでは、ユーザースペース（「クライアント」）がステートレスデコーダーとどのように通信すべきかを説明します。ステートフルコーデックと比較して、デコーダー/クライアントのシーケンスはシンプルですが、このシンプルさの代償としてクライアント側でより多くの複雑さを負う必要があります。

ステートレスデコーダーは、 リクエストAPIを必要とします。 V4L2_BUF_CAP_SUPPORTS_REQUESTS をその OUTPUT キューで VIDIOC_REQBUFS() または VIDIOC_CREATE_BUFS() が呼び出されるときに公開しなければなりません。

デコーダーがサポートする符号化形式に応じて、1つのデコードされたフレームは複数のデコードリクエストの結果となる場合があります（例：1つのフレームに複数のスライスを持つH.264ストリーム）。このような形式をサポートするデコーダーは、また V4L2_BUF_CAP_SUPPORTS_M2M_HOLD_CAPTURE_BUF をその OUTPUT キュー。

4.5.3.3. 復号¶

各フレームに対して、クライアントは以下の情報を含む少なくとも1つのリクエストを送信する責任があります:

  • 現在の設定に応じてコーデックが期待する符号化データの量は、バッファとして送信された OUTPUT キューに送信されます。通常、これは1フレーム分の符号化データに相当しますが、一部の形式では1単位あたり異なる量を許可（または要求）する場合があります。

  • 符号化データをデコードするための必要なメタデータは、デコード対象形式に関連するコントロール形式で提供されます。

ソース OUTPUT バッファのデータ量および内容、およびリクエストに設定する必要のあるコントロールは、アクティブな符号化ピクセル形式に依存し、各形式のドキュメントで説明されているコーデック固有の拡張コントロールに影響される可能性があります。

デコードされたフレームが現在のリクエストの後で1つまたは複数のデコードリクエストを必要とする可能性がある場合、クライアントは V4L2_BUF_FLAG_M2M_HOLD_CAPTURE_BUF フラグを OUTPUT バッファに設定する必要があります。これにより、（部分的に）デコードされた CAPTURE バッファがデキューイング用に利用できなくなり、次のデコードリクエストで再利用されます（次の OUTPUT バッファのタイムスタンプが変化していない場合）。

通常のフレームは以下の手順でデコードされます:

  1. デコードリクエスト用に OUTPUT バッファをキューに登録し、そのバッファに含まれる符号化ビデオストリームデータの1単位を指定します。 VIDIOC_QBUF().

    • 必須フィールド:

      index

      キューに登録されているバッファのインデックス。

      type

      バッファのタイプ。

      bytesused

      バッファ内の符号化データフレームのバイト数。

      flags

      、そして V4L2_BUF_FLAG_REQUEST_FD フラグを設定する必要があります。さらに、現在のデコードリクエストが完全にデコードされたフレームを生成するために必要な最後のリクエストであるかどうかが不明な場合、 V4L2_BUF_FLAG_M2M_HOLD_CAPTURE_BUF フラグも設定する必要があります。

      request_fd

      フラグをデコードリクエストのファイルディスクリプタに設定する必要があります。

      timestamp

      フラグをフレームごとに一意の値に設定する必要があります。この値はデコードされたフレームのバッファに伝播され、このフレームを他のフレームの参照として使用することもできます。複数のデコードリクエストを1フレームに対して使用する場合、その OUTPUT バッファのタイムスタンプはすべて同一でなければなりません。タイムスタンプが変更された場合、現在保持している CAPTURE バッファはデキューイング用に利用可能になり、現在のリクエストは新しい CAPTURE バッファ。

  2. バッファを処理します。デコードリクエストのコントロールを設定するには、 VIDIOC_S_EXT_CTRLS().

      でなければなりません V4L2_CTRL_WHICH_REQUEST_VAL.

      フラグをデコードリクエストのファイルディスクリプタに設定する必要があります。

      その他のフィールド

      他のフィールドは通常通りコントロールを設定する際と同じように設定します。 controls 配列には、フレームをデコードするために必要なすべてのコーデック固有のコントロールを含める必要があります。

    注意

    異なる呼び出しで制御を指定することが可能です。 VIDIOC_S_EXT_CTRLS()、または以前に設定された制御を上書きすることが可能です。ただし、 request_fd および which が適切に設定されている必要があります。リクエストの送信時における制御の状態が考慮されます。

    ステップ1とステップ2の順序は交換可能です。

4.5.3.4. デコード中のバッファ管理¶

ステートフルなデコーダーとは異なり、ステートレスなデコーダーはバッファ管理を行いません。ただでさえキューから取得された CAPTURE バッファはキューに再度追加されるまでクライアントによって使用できます。「使用」とは、バッファをコンポジットや表示に使用することを含みます。

キューから取得されたキャプチャーバッファは、他のバッファの参照フレームとしても使用できます。

フレームは、そのタイムスタンプをナノ秒に変換し、コードック依存の制御構造体の関連するメンバに保存することで参照フレームとして指定されます。この v4l2_timeval_to_ns() 関数を使用してその変換を行います。フレームのタイムスタンプは、すべての符号化データ単位が成功裏にキューに送信された時点で、そのフレームを参照するために使用できます。 OUTPUT キュー。

参照フレームを含むデコードされたバッファは、すべての参照フレームがデコードされるまで再利用してはなりません。最も安全な方法は、すべてのデコードされた参照フレームがキューから取得されるまで参照バッファをキューに追加しないことです。ただし、ドライバがキューに追加されたバッファがキュー順に処理されることを保証できる場合、 CAPTURE キューに追加されたバッファがキュー順に処理されることを保証できる場合、ユーザー空間はこの保証を活用して、以下の条件が満たされたときに参照バッファをキューに追加できます：

  1. 参照フレームによって影響を受けるすべてのフレームのリクエストがキューに追加され、

  2. デコードされた参照フレームをカバーする十分な数の CAPTURE バッファがキューに追加されている必要があります。

デコード要求をキューイングする際、ドライバーはすべての参照フレームに関連するリソースの参照カウントを増加させます。これにより、クライアントはその後必要としなくなった場合、参照フレームバッファのDMABUFファイル記述子を閉じることができます。

4.5.3.5. シーク¶

シークを行うには、クライアントは新しいストリームポジションに対応する入力バッファを使用して要求を送信するだけで十分です。ただし、解像度が変更されている可能性があるため、その場合は動的解像度変更手順に従う必要があります。また、使用するコーデックによっては、ピクチャーパラメータ（例：H.264のSPS/PPS）が変更される場合があり、クライアントはデコーダーに有効な状態を送る責任があります。

クライアントはその後、シーク前のポジションから返却される CAPTURE バッファを無視することができます。

4.5.3.6. 一時停止¶

一時停止を行うには、クライアントは単に OUTPUT キューへのバッファキューイングを停止すればよいです。ソースバイナリストリームデータがなければ処理するデータがなく、コーデックはアイドル状態のままになります。

4.5.3.7. 動的解像度変更¶

クライアントがストリーム内で解像度変更を検出した場合、新しい解像度で初期化手順を再度実行する必要があります：

  1. 最後に送信した要求が CAPTURE フラグを使用してバッファを保持した結果となった場合、最後のフレームは V4L2_BUF_FLAG_M2M_HOLD_CAPTURE_BUF キューに存在しません。このような場合、 CAPTURE コマンドを送信する必要があります。これによりドライバーは保持している V4L2_DEC_CMD_FLUSH バッファをキューから外します。 CAPTURE バッファ。

  2. すべての送信要求が完了するのを待って、対応する出力バッファをキューから外します。

  3. を呼び出して、MMIOまたはIOポート範囲を利用可能にします。これを実施しないと、ドライバの再ロードができない状態になります。 VIDIOC_STREAMOFF() 両方の OUTPUT および CAPTURE キューにも適用します。

  4. すべての CAPTURE バッファを解放するには、 VIDIOC_REQBUFS() on the CAPTURE キューにバッファ数ゼロを指定して呼び出します。

  5. 新しい解像度で初期化手順を再度実行します（バッファの割当は除きます）。 OUTPUT キューに新しい解像度を設定します。解像度制約により、 OUTPUT キューで異なるフォーマットを選択する必要があります。 CAPTURE キュー。

4.5.3.8. シーケンスと同様です¶

最後に送信した要求が CAPTURE フラグを使用してバッファを保持した結果となった場合、最後のフレームは V4L2_BUF_FLAG_M2M_HOLD_CAPTURE_BUF キューに存在しません。このような場合、 CAPTURE コマンドを送信する必要があります。これによりドライバーは保持している V4L2_DEC_CMD_FLUSH バッファをキューから外します。 CAPTURE バッファ。

その後、ステートレスデコーダーでストリームをドレインするには、クライアントはすべての送信要求が完了するのを待つだけで十分です。

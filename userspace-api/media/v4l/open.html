1.1. デバイスのオープンとクローズ¶

1.1.1. V4L2を介してハードウェア外設機器を制御する¶

V4L2 uAPI を使用してサポートされるハードウェアは、複数のデバイスまたは周辺機器から構成されることが多く、それぞれが独自のドライバを持つ。

ブリッジドライバは、1つまたは複数の V4L2 デバイスノードを露出します（参照 V4L2デバイスノードの命名).

他のハードウェアコンポーネントをサポートする他のドライバも存在し、それらも V4L2 サブデバイスとしてデバイスノードを露出することがあります。

このような V4L2 サブデバイスが露出されている場合、それらは他のハードウェアコンポーネントの制御を可能にします（通常、シリアルバス（I²C、SMBus、SPI など）を介して接続されています）。ブリッジドライバによっては、サブデバイスを間接的に制御するか、明示的に制御するかが可能です。 メディアコントローラー および V4L2サブデバイス.

を介して制御されます。 メディアコントローラー を必要とするデバイスは、 MC中心的 デバイスと呼ばれます。V4L2 デバイスノードを介して完全に制御されるデバイスは、 video-node-centric.

ユーザースペースは、V4L2 ハードウェア周辺機器が MC-centric であるかを確認するには、 ioctl VIDIOC_QUERYCAP を呼び出し、 device_caps フィールドを確認します。.

デバイスが V4L2_CAP_IO_MC フラグを返す場合、MC-centric であり、そうでない場合は video-node-centric です。 device_capsflag at

MC-centric ドライバは、V4L2 サブデバイスを識別し、 media controller API を介してパイプラインを構成する必要があります。また、サブデバイスの設定は、 sub-device API.

注意

video-node-centric デバイスは、メディアコントローラーおよびサブデバイスインターフェースを提供することもあります。

ただし、その場合、メディアコントローラーおよびサブデバイスインターフェースは読み取り専用となり、デバイスに関する情報のみを提供します。実際の設定は V4L2 デバイスノードを通じて行われます。

1.1.2. V4L2デバイスノードの命名¶

V4L2 ドライバはカーネルモジュールとして実装され、システム管理者が手動でロードするか、デバイスが最初に検出されたときに自動的にロードされます。ドライバモジュールは、 videodev カーネルモジュールに接続され、このドキュメントで指定されたヘルパーファンクションと一般的なアプリケーションインターフェースを提供します。

各ロードされたドライバは、主装置番号 81 の1つまたは複数のデバイスノードを登録します。メジャーナンバーは動的に割り当てられます。ただし、カーネルが CONFIG_VIDEO_FIXED_MINOR_RANGES オプションでコンパイルされている場合、メジャーナンバーはデバイスノードタイプに応じて範囲で割り当てられます。

Video4Linux サブシステムでサポートされるデバイスノードは以下の通りです：

デフォルトのデバイスノード名

使い方

/dev/videoX

ビデオおよびメタデータの収録/出力デバイス

/dev/vbiX

垂直無効期間データ（閉じた字幕、テレックステ）

/dev/radioX

ラジオチューナーおよび変調器

/dev/swradioX

ソフトウェア定義ラジオチューナーおよび変調器

/dev/v4l-touchX

/dev/v4l-subdevX

ビデオサブデバイス（センサーおよびハードウェア周辺機器の他のコンポーネントで使用）1

ここで X は非負の整数です。

注意

  1. 実際のデバイスノード名はシステムに依存し、udevルールが適用される可能性があります。

  2. 保証はありませんが、 X 同じデバイスに対して同じ番号が続くとは限りません。番号はデバイスドライバのプローブ順に依存するためです。ユニークな名前が必要な場合は、udevのデフォルトルールが生成する /dev/v4l/by-id/ および /dev/v4l/by-path/ V4L2デバイスノードを一意に識別できるリンクを含むディレクトリ:

    $ tree /dev/v4l
/dev/v4l
├── by-id
│   └── usb-OmniVision._USB_Camera-B4.04.27.1-video-index0 -> ../../video0
└── by-path
    └── pci-0000:00:14.0-usb-0:2:1.0-video-index0 -> ../../video0
1

V4L2サブデバイスノード (e. g. /dev/v4l-subdevX) は、説明されているように、異なるシステムコールのセットを使用します。 サブデバイスインターフェース.

多くのドライバーは「video_nr」、「radio_nr」または「vbi_nr」のモジュールオプションをサポートし、特定のビデオ/ラジオ/VBIノード番号を選択できます。これにより、ユーザーがデバイスノードが例えば/dev/video5に名前を付けるように指定できるようになります。ドライバーが同じタイプの複数のデバイスをサポートする場合、複数のデバイスノード番号をコンマで区切って割り当てることができます。

# modprobe mydriver video_nr=0,1 radio_nr=0,1

In /etc/modules.conf これは次のように書かれます:

options mydriver video_nr=0,1 radio_nr=0,1

モジュールオプションとしてデバイスノード番号が指定されていない場合、ドライバーはデフォルトを提供します。

通常、udevは/devに自動的にデバイスノードを生成します。udevがインストールされていない場合、CONFIG_VIDEO_FIXED_MINOR_RANGESというカーネルオプションを有効にする必要があります。これにより、マイナーナンバーがデバイスノード番号と正しく関連付けられます。つまり、マイナーナンバー5がデバイスノード名video5にマッピングされていることを確認する必要があります。このカーネルオプションにより、異なるデバイスタイプが異なるマイナーナンバー範囲を使用します。これらの範囲は、 インターフェース.

キャラクタースペシャルファイル（mknodを使用して作成）の作成は特権操作であり、デバイスはメジャーナンバーとマイナーナンバーで開けません。そのため、アプリケーションは 信頼できる ロード済みまたはインストール済みドライバーをスキャンできません。ユーザーはデバイス名を入力する必要があります。それ以外の場合、アプリケーションは従来のデバイス名を試してみることができます。

1.1.3. で記載されているように、ドライバはすべてのマイノーデバイス番号で関連デバイス機能を提供しなければなりません。¶

デバイスは複数の機能をサポートできます。たとえばビデオキャプチャ、VBIキャプチャ、ラジオサポートなどです。

V4L2 APIは、これらの各機能に対して異なるV4L2デバイスノードを作成します。

V4L2 APIは、1つのデバイスノードがすべての機能をサポートするという設計に基づいていました。しかし、実際にはこれは機能しませんでした。この「機能」はアプリケーションによって使われず、多くのドライバーはこれをサポートしていません。サポートしている場合でも、テストは行われていません。さらに、デバイスノードを異なる機能間で切り替えるのは、ストリーミングI/O APIを使用する場合にのみ可能です。 read()/write() API。

現在、各V4L2デバイスノードは1つの機能のみをサポートしています。

ビデオ入力または出力に加えて、ハードウェアはオーディオサンプリングや再生をサポートすることもあります。その場合、これらの機能はALSA PCMデバイスとして実装され、オプションでALSAオーディオミキサーデバイスも使用されます。

これらのデバイスの1つ目の問題は、V4L2 APIが関連するV4L2デバイスノードを検出するための仕様を提供していないことです。非常に複雑なハードウェアはメディアコントローラー（参照 第 IV 章 - Media Controller API)を使用してこの目的を達成できます。しかし、いくつかのドライバはこれを使用していません。また、sysfsを使用して関連するV4L2デバイスノードを検出するコードが存在します（参照 libmedia_dev という名前の v4l-utils git リポジトリ内のファイル）。しかし、メディアコントローラーベースのデバイスとメディアコントローラーを使用しないデバイスの両方に対して単一のAPIを提供するライブラリはまだ存在しません。この作業に取り組みたい場合は、linux-media メーリングリストにご連絡ください： https://linuxtv.org/lists.php.

1.1.4. 複数のオープン¶

V4L2デバイスは1回以上オープンできます。 2 ドライバがこれをサポートする場合、ユーザーは例えば「パネル」アプリケーションを起動して明るさやオーディオボリュームなどの制御を変更しながら、別のアプリケーションがビデオとオーディオをキャプチャするなど、複数のアプリケーションが同時に動作できます。言い換えれば、パネルアプリケーションはALSAオーディオミキサーアプリケーションと同等です。単にV4L2デバイスを開くだけではデバイスの状態を変更しません。 3

1.1.5. 共有データストリーム¶

V4L2ドライバは、バッファのコピー、タイムマルチプレクシング、または類似の方法で複数のアプリケーションがデバイス上の同じデータストリームを読み書きするサポートをすべきではありません。これはユーザー空間のプロキシアプリケーションでより適切に処理されます。

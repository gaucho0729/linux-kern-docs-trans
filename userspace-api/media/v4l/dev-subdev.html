4.13. サブデバイスインターフェース¶

V4L2デバイスの複雑な性質は、ハードウェアがしばしば複数の統合回路から構成され、制御された方法で相互に通信する必要があるため、複雑なV4L2ドライバを生み出します。ドライバは通常、ハードウェアモデルをソフトウェアで反映し、異なるハードウェアコンポーネントを「サブデバイス」と呼ばれるソフトウェアブロックとしてモデル化します。

V4L2サブデバイスは通常、カーネル専用のオブジェクトです。V4L2ドライバがメディアデバイスAPIを実装する場合、自動的にメディアエンティティを継承します。アプリケーションはメディアエンティティ、パッドおよびリンクの列挙APIを通じてサブデバイスを列挙し、ハードウェアのトポロジーを発見できます。

サブデバイスの発見だけでなく、ドライバはアプリケーションが直接サブデバイスを設定できるようにすることも選択できます。サブデバイスドライバとV4L2デバイスドライバがこの機能をサポートする場合、サブデバイスはキャラクターデバイスノードを持つようになり、その上でioctlを呼び出して

  • サブデバイスのコントロールを照会・読み取り・書き込みできます

  • イベントのサブスクライブとアンサブスクライブを行い、イベントを取得できます

  • 個々のパッドでの画像フォーマットのネゴシエーションを行えます

サブデバイスキャラクターデバイスノードは、通常は /dev/v4l-subdev*という名前で、メジャーナンバー81を使用します。

ドライバは、サブデバイスキャラクターデバイスがデバイスの状態を変更しない操作のみを公開することを選択できます。このような場合、サブデバイスは read-only このドキュメンテーションの後半で参照され、関連する制限は個々のioctlで記載されています。

4.13.1. コントロール¶

ほとんどのV4L2コントロールはサブデバイスハードウェアによって実装されます。ドライバは通常、すべてのコントロールを統合し、ビデオデバイスノードを通じて公開します。アプリケーションは単一のインターフェースを通じてすべてのサブデバイスを制御できます。

複雑なデバイスでは、同じコントロールが異なるハードウェア部品で実装されることがあります。これは埋め込みプラットフォームでよく見られ、センサーや画像処理ハードウェアがコントラスト調整、ホワイトバランス、不良ピクセル補正などの同一機能を実装する場合です。V4L2コントロールAPIは単一のデバイス内で複数の同一コントロールをサポートしないため、すべての同一コントロールのうち1つは非表示になります。

アプリケーションは、サブデバイスノードを通じてV4L2コントロールAPIで記述されたAPIを使用して、それらの非表示コントロールにアクセスできます。 ユーザー制御ioctlはV4L2デバイスノードで呼び出されたときと同じように動作しますが、サブデバイスで実装されたコントロールのみを処理します。

ドライバによっては、これらのコントロールが1つ（または複数の）V4L2デバイスノードを通じて公開される可能性もあります。

4.13.2. イベント¶

V4L2 sub-devices can notify applications of events as described in イベントインターフェース. The API behaves identically as when used on V4L2 device nodes, with the exception that it only deals with events generated by the sub-device. Depending on the driver, those events might also be reported on one (or several) V4L2 device nodes.

4.13.3. Pad-level Formats¶

警告

Pad-level formats are only applicable to very complex devices that need to expose low-level format configuration to user space. Generic V4L2 applications do ではありません need to use the API described in this section.

注意

For the purpose of this section, the term format means the combination of media bus data format, frame width and frame height.

Image formats are typically negotiated on video capture and output devices using the format and selection ioctls. The driver is responsible for configuring every block in the video pipeline according to the requested format at the pipeline input and/or output.

For complex devices, such as often found in embedded systems, identical image sizes at the output of a pipeline can be achieved using different hardware configurations. One such example is shown on Image Format Negotiation on Pipelines, where image scaling can be performed on both the video sensor and the host image processing hardware.

The sensor scaler is usually of less quality than the host scaler, but scaling on the sensor is required to achieve higher frame rates. Depending on the use case (quality vs. speed), the pipeline must be configured differently. Applications need to configure the formats at every point in the pipeline explicitly.

Drivers that implement the media API can expose pad-level image format configuration to applications. When they do, applications can use the VIDIOC_SUBDEV_G_FMT および VIDIOC_SUBDEV_S_FMT ioctls. to negotiate formats on a per-pad basis.

Applications are responsible for configuring coherent parameters on the whole pipeline and making sure that connected pads have compatible formats. The pipeline is checked for formats mismatch at VIDIOC_STREAMON time, and an EPIPE error code is then returned if the configuration is invalid.

Pad-level image format configuration support can be tested by calling the ioctl VIDIOC_SUBDEV_G_FMT, VIDIOC_SUBDEV_S_FMT ioctl on pad 0. If the driver returns an EINVAL error code pad-level format configuration is not supported by the sub-device.

4.13.3.2. 選択肢: トリミング、スケーリング、コンポジション¶

多くのサブデバイスは、入力または出力パッド（あるいは両方）でフレームのクロッピングをサポートしています。クロッピングは、画像の興味領域を選択するために使用され、通常は画像センサーまたはビデオデコーダー上での操作です。また、デジタルズームの実装においても、拡大される画像領域を選択するために使用されます。

クロッピング設定は、クロッピング矩形によって定義され、構造体で表されます。 v4l2_rect この矩形は左上隅の座標と矩形のサイズによって表現され、座標とサイズはすべてピクセル単位で表されます。

パッドフォーマットと同様に、ドライバは選択対象のための試行およびアクティブな矩形を保存します。 一般的な選択定義.

スケーリング操作は画像のサイズを新しい寸法に変更します。スケーリング比率は明示的に指定されませんが、元の画像サイズとスケール後の画像サイズから推定されます。これらのサイズは構造体で表されます。 v4l2_rect.

スケーリングのサポートはオプションです。サブデバイスがサポートする場合、サブデバイスのシンクパッド上のクロッピ、ング矩形はVIDIOC_SUBDEV_S_SELECTION IOCTLを使用して設定されたサイズにスケーリングされます。 VIDIOC_SUBDEV_S_SELECTION IOCTLを使用して、同じパッド上の選択ターゲットを指定します。サブデバイスがスケーリングをサポートしているがコンポジットをサポートしていない場合、トップとレフトの値は使用されず、常にゼロに設定する必要があります。 V4L2_SEL_TGT_COMPOSE ソースパッドでは、シンクパッドと同様のクロッピングが行われますが、クロッピングが行われるソースサイズはシンクパッド上のコンポジット矩形です。シンクとソースの両方のパッドにおいて、クロッピング矩形はクロッピング操作のためにソース画像サイズの内部に完全に含まれている必要があります。

4.13.3.3.2. BOUNDSターゲット¶

BOUNDSターゲットは、すべての有効な実際の矩形を含む最小の矩形です。ただし、実際の矩形をBOUNDS矩形と同じくらい大きく設定できない場合もあります。これは、たとえばセンサーのピクセル配列が長方形ではなくクロス型や円形であるなどの理由による可能性があります。最大サイズもBOUNDS矩形よりも小さくなることがあります。

4.13.3.4. 設定の順序とフォーマットの伝播の順序¶

サブデバイス内では、画像処理ステップの順序は常にシンクパッドからソースパッドへと行われます。これはユーザーが設定を行う際の順序も反映されており、変更はその後のすべての段階に伝播します。この挙動が望ましくない場合は、ユーザーは V4L2_SEL_FLAG_KEEP_CONFIG フラグを設定する必要があります。このフラグにより、変更の伝播が常に禁止されます。これは、基盤となるハードウェアの特性により、アクセスされた矩形がドライバによって調整される可能性もあります。

ステップの座標は常に前段階の実際のサイズを参照します。このルールの例外はシンクコンポーズ矩形であり、これはシンクコンポーズバウンド矩形を参照します（ハードウェアがこれをサポートする場合）。

  1. シンクパッドフォーマット。ユーザーはシンクパッドフォーマットを設定します。このフォーマットは、エンティティがパッドを通じて受信する画像のパラメータを定義します。

  2. シンクパッド実際のクロップ選択。シンクパッドクロップは、シンクパッドフォーマットに対して行われるクロップを定義します。

  3. シンクパッド実際のコンポーズ選択。シンクパッドコンポーズ矩形のサイズは、シンクパッドクロップ矩形のサイズと比較したスケーリング比率を定義します。コンポーズ矩形の位置は、シンクコンポーズバウンド矩形内での実際のシンクコンポーズ矩形の位置を指定します。

  4. ソースパッド実際のクロップ選択。ソースパッドのクロップは、シンクコンポーズバウンド矩形内の画像に対して行われるクロップを定義します。

  5. ソースパッドフォーマット。ソースパッドフォーマットは、サブデバイスの出力ピクセルフォーマットおよびその他のパラメータを定義します（画像幅と高さを除く）。幅と高さは、ソースパッド実際のクロップ選択のサイズによって定義されます。

上記のサブデバイスがサポートしていない矩形をアクセスすると EINVALが返されます。以前のサポートされていない矩形の座標を参照する矩形は、代わりに以前のサポートされている矩形を参照します。たとえば、シンククロップがサポートされていない場合、コンポーズ選択はシンクパッドフォーマットの寸法を参照します。

上記の例では、サブデバイスがシンクパッドでクロッピングをサポートしています。設定を行うには、ユーザーがサブデバイスのシンクパッドにメディアバスフォーマットを設定します。これにより、実際にクロッピングする矩形をシンクパッドで設定できます。この矩形の位置とサイズは、シンクフォーマットからクロッピングする矩形の位置とサイズを反映します。また、シンククロッピング矩形のサイズは、サブデバイスのソースパッドのフォーマットのサイズにもなります。

この例では、サブデバイスはまずクロッピングし、その後スケーリングし、最終的に結果のスケーリング画像から2つのソースパッドそれぞれに対して個別にクロッピングします。スケーリング画像の位置はシンクコンポジットターゲットで無視されます。2つのソースクロッピング矩形の位置は、シンクスケーリング矩形を参照し、それぞれソースクロッピング矩形で指定された位置から独立して領域をクロッピングします。

サブデバイスドライバーは2つのシンクパッドと2つのソースパッドをサポートしています。2つのシンクパッドからの画像は個別にクロッピングされ、その後スケーリングされ、合成境界矩形でさらに合成されます。これにより、2つの独立したストリームがソースパッドからサブデバイスから送出されます。

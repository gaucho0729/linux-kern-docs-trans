7.29. ioctl VIDIOC_G_EXT_CTRLS, VIDIOC_S_EXT_CTRLS, VIDIOC_TRY_EXT_CTRLS¶

7.29.1. 名前¶

7.29.2. 概要¶

VIDIOC_S_EXT_CTRLS¶

__u32

error_idx

ドライバーがエラーを発生した場合に設定されます。エラーが特定の制御項目に関連している場合、 error_idx はその制御項目のインデックスに設定されます。エラーが特定の制御項目と関係なく、または検証ステップで失敗した場合（以下参照）、 error_idx が countが設定されます。ioctlが0（成功）を返した場合、値は未定義です。

制御項目がハードウェアから読み込まれたり書き込まれたりする前に検証ステップが実行されます。このステップでは、リスト内のすべての制御項目が有効な項目であるか、読み取り専用の制御項目に書き込まれようとする試みがないか、またはハードウェアにアクセスすることなく実行可能な他の初期チェックが行われます。このステップで実行される具体的な検証はドライバー依存です。なぜなら、一部のデバイスではハードウェアへのアクセスが必要なチェックが存在するため、事前に実行できない可能性があるからです。ただし、ドライバーは可能な限り多くの初期チェックを実行するように努めるべきです。

このチェックは、ハードウェアが簡単に回避可能な問題により不整合な状態に残らないようにするため行われます。しかし、これにより別の問題が生じます：アプリケーションは、エラーが検証ステップから発生した（つまりハードウェアが操作されていない）か、ハードウェアへの読み書き中に発生したかを知る必要があります。

hindsight から見ればかなり悪い、その問題に対する解決策は、検証が失敗した場合に error_idx に（木の下から葉に向かって） count を設定することです。これは、どの制御項目が検証に失敗したかを確認できないという不都合な副作用があります。検証が成功し、エラーがハードウェアへのアクセス中に発生した場合、 error_idx より小さい count が設定され、かつ、 error_idx-1 までの制御項目が正しく読み込まれたり書き込まれたりし、残りの制御項目の状態は未定義です。

なぜなら VIDIOC_TRY_EXT_CTRLS ハードウェアにアクセスしない場合、この特別な処理を行う必要もありませんので、 error_idx は検証ステップで失敗した制御項目に設定され、 countに設定されるのではなくなります。これは、 VIDIOC_S_EXT_CTRLS 失敗します error_idx 設定に設定する countが設定されている場合、 VIDIOC_TRY_EXT_CTRLS を呼び出して、実際に検証ステップで失敗した制御項目を特定できるようにします。残念なことに、 TRY には同等の関数がありません。 VIDIOC_G_EXT_CTRLS.

3.3. ストリーミングI/O（ユーザーポインタ）¶

入出力デバイスは、ioctlが設定されているときにこのI/Oメソッドをサポートします。 V4L2_CAP_STREAMING フラグを含めます。以下のようにします： capabilities 構造体の v4l2_capability は ioctl VIDIOC_QUERYCAP ioctlが設定されています。特定のユーザーポインタメソッド（メモリマッピングに限らず）がサポートされているかどうかは、呼び出すことによって確認する必要があります。 ioctl VIDIOC_REQBUFS ioctlを呼び出し、メモリタイプを V4L2_MEMORY_USERPTR.

このI/Oメソッドは、read/writeとメモリマッピングの両方の利点を組み合わせています。バッファ（プレーン）はアプリケーション自体が割り当て、仮想メモリや共有メモリなどに配置されることがあります。データへのポインタのみが交換され、これらのポインタとメタ情報はstruct内で渡されます。 v4l2_buffer (またはmulti-planar APIの場合、struct v4l2_plane マルチプレーンAPIの場合）。ドライバーは、呼び出すことによってユーザーポインタI/Oモードに切り替えなければなりません。 ioctl VIDIOC_REQBUFS 望ましいバッファタイプとともに。事前にバッファ（プレーン）が割り当てられず、結果としてインデックス付けされず、マッピングされたバッファのようにクエリできません。 VIDIOC_QUERYBUF ioctl.

3.3.1. 例: ユーザーポインタを使用したストリーミングI/Oの開始¶

struct v4l2_requestbuffers reqbuf;

memset (&reqbuf, 0, sizeof (reqbuf));
reqbuf.type = V4L2_BUF_TYPE_VIDEO_CAPTURE;
reqbuf.memory = V4L2_MEMORY_USERPTR;

if (ioctl (fd, VIDIOC_REQBUFS, &reqbuf) == -1) {
    if (errno == EINVAL)
        printf ("Video capturing or user pointer streaming is not supported\\n");
    else
        perror ("VIDIOC_REQBUFS");

    exit (EXIT_FAILURE);
}

バッファ（プレーン）のアドレスとサイズは、ioctlを通じて動的に渡されます。 VIDIOC_QBUF ioctl。バッファは通常サイクルしますが、アプリケーションは各呼び出しで異なるアドレスとサイズを渡すことができます。 VIDIOC_QBUF 呼び出し。ハードウェアが必要な場合、ドライバーは物理メモリ内でメモリページを交換し、連続したメモリ領域を作成します。これはカーネルの仮想メモリサブシステム内でアプリケーションに対して透過的に実行されます。バッファページがディスクに交換されると、それらは再び読み込まれ、最終的にDMA用に物理メモリでロックされます。 1

満タンまたは表示されたバッファは、ioctlを通じてデキューされます。 VIDIOC_DQBUF ioctl。DMAの完了とこのioctlの間に、ドライバーはメモリページをいつでもアンロックできます。メモリはまた、またはデバイスが閉じられたときにアンロックされます。 VIDIOC_STREAMOFF が呼ばれたとき、 ioctl VIDIOC_REQBUFS、またはデバイスが閉じられたときにアンロックされます。アプリケーションは、デキューせずにバッファを解放しないように注意する必要があります。まず、バッファはより長時間ロックされ、物理メモリを浪費します。次に、メモリがアプリケーションのフリーリストに戻され、他の用途に再利用されるときにドライバーに通知されません。これにより、要求されたDMAが完了し、貴重なデータを上書きする可能性があります。

キャプチャアプリケーションでは、通常、空のバッファを複数キューイングしてキャプチャを開始し、読み取りループに入ります。ここでアプリケーションは満たされたバッファがキューから dequeue できるのを待機し、データが不要になったらそのバッファを再キューイングします。出力アプリケーションでは、十分なバッファがスタックされたら出力が開始され、バッファを満たしてキューイングします。書き込みループでは、アプリケーションが空きバッファがなくなった場合、空きバッファがキューから dequeue できるのを待機する必要があります。アプリケーションの実行を一時停止するための2つの方法があります。デフォルトでは VIDIOC_DQBUF 出力キューにバッファがなければブロックします。flagが与えられた場合、 O_NONBLOCK 関数に与えられた場合、 open() 関数の場合、 VIDIOC_DQBUF エラー コードとともに即座に返します。 EAGAIN バッファが利用不可の場合のエラーコードです。The select() または poll() 関数は常に利用可能です。

キャプチャまたは出力アプリケーションを開始・停止するには VIDIOC_STREAMON および VIDIOC_STREAMOFF ioctl.

注意

VIDIOC_STREAMOFF 両方のキューからすべてのバッファを削除し、すべてのバッファをアンロックする副作用があります。マルチタスクシステムでは「即時実行」の概念がありませんため、アプリケーションが他のイベントと同期する必要がある場合は、キャプチャまたは出力されたバッファの構造体を確認する必要があります。 v4l2_buffer timestamp struct

ユーザーポインタI/Oを実装するドライバーは、をサポートしなければなりません。 VIDIOC_REQBUFS, VIDIOC_QBUF, VIDIOC_DQBUF, VIDIOC_STREAMON および VIDIOC_STREAMOFF ioctlに加えて、 select() および poll() function. 2

1

頻繁に使用されるバッファは通常スワップされないものと期待されます。しかし、スワップやロック、スキャッターガatherリストの生成といったプロセスは時間がかかることがあります。この遅延は入力バッファキューの深さによって補うことができ、またバッファが再びキューに追加されることが予想される場合にキャッシュを維持することでさらに軽減される可能性があります。一方で、メモリ使用量を最適化するためドライバーは事前にロックするバッファの数を制限し、最も最近使用されたバッファを優先的に再利用する方法が考えられます。もちろん、入力キューにある空バッファのページはディスクに保存する必要はありません。出力バッファは入力キューおよび出力キューに保存する必要があります。なぜなら、アプリケーションが他のプロセスと共有する可能性があるからです。

2

ドライバーレベルで select() および poll() 同じであり、 select() オプションとして扱うにはあまりにも重要です。残りは明らかでしょう。

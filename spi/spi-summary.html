LinuxカーネルSPIサポートの概要¶

2012年2月2日

SPIとは何か？¶

「シリアルペリフェラルインターフェース」（SPI）は、マイクロコントローラーをセンサー、メモリ、ペリフェラルに接続するための同期型4ワイヤーのシリアルリンクです。これはシンプルな「事実上の標準」であり、標準化機関に登録するほど複雑ではありません。SPIはマスターアンドスレーブの構成を採用しています。

3つの信号線にはクロック（SCK、通常10MHz程度）、および「マスターオアチップ、スレーブイン」（MOSI）または「マスターアイン、スレーブアウト」（MISO）の並列データラインが含まれます。（他の名称も使われます。）データのやり取りには4つのクロックモードがあり、モード0とモード3が最も一般的です。各クロックサイクルでデータが送信され、受信されます。クロックはデータビットをシフトする際以外はサイクルを繰り返しません。ただし、すべてのデータビットが使用されるわけではなく、すべてのプロトコルがフル duplexの機能を活用しているわけではありません。

SPIマスタは4番目の「チップセレクト」ラインを使用して特定のSPIスレーブデバイスをアクティブにします。そのため、これらの3つの信号線は複数のチップに並列で接続されることがあります。すべてのSPIスレーブはチップセレクトをサポートしており、通常はアクティブロー信号で、スレーブ「x」にラベルnCSx（例：nCS0）で表示されます。一部のデバイスには他の信号があり、マスタへの割り込み信号が含まれる場合もあります。

USBやSMBusなどのシリアルバスとは異なり、SPIスレーブ機能の低レベルプロトコルはベンダー間で通常は互換性がありません（例外はSPIメモリチップなどの汎用品です）。

  • SPIはタッチスクリーンセンサーなどのデバイスプロトコルのリクエスト/レスポンス形式にも利用されます。

  • また、データの片方向（半二重）でのストリーム送信や、両方向同時に（全二重）送信にも利用されます。

  • 一部のデバイスでは8ビットのワードが使用されることがあります。他には12ビットや20ビットのデジタルサンプルストリームなど、異なるワード長が使用される場合もあります。

  • ワードは通常、最高位ビット（MSB）から送信されますが、場合によっては最低位ビット（LSB）から送信されることがあります。

  • SPIはシフトレジスタなど、デバイスをダイズーチェーン接続する際にも使用されることがあります。

同様に、SPIスレーブは自動発見/エナメレーションプロトコルをサポートするケースはめったにありません。あるSPIマスタからアクセス可能なスレーブデバイスの木構造は通常、手動で設定し、コンフィギュレーションテーブルで構成されます。

SPIはこのような4ワイヤープロトコルの一つの名称であり、ほとんどのコントローラーは「マイクロワイヤー」（リクエスト/レスポンスプロトコル用の半二重SPIと考えてください）や「SSP（同期シリアルプロトコル）」、「PSP（プログラマブルシリアルプロトコル）」、その他の関連プロトコルを処理できます。

一部のチップはMOSIとMISOを統合して信号ラインを削減し、ハードウェアレベルでハーフドップルに限定されています。実際、一部のSPIチップではこの信号モードをストラッピングオプションとして提供しています。これらはSPIの同じプログラミングインターフェースでアクセス可能ですが、もちろんフルドップルの転送は処理できません。このようなチップは「スリーワイヤー」シグナルとして説明されることがあります：SCK、データ、nCSx。（このデータラインは時としてMOMIまたはSISOと呼ばれます。）

マイクロコントローラーは通常、SPIプロトコルのマスターおよびスレーブ側の両方をサポートしています。このドキュメント（およびLinux）はSPIインタラクションのマスターおよびスレーブ側の両方をサポートしています。

誰が使用するのか？どの種類のシステムで使用されるのか？¶

LinuxでSPIを使用する開発者はおそらく埋め込みシステムボード用のデバイスドライバを書いているでしょう。SPIは外部チップを制御するために使用され、またすべてのMMCまたはSDメモリカードがサポートするプロトコルでもあります。（古い「DataFlash」カードはMMCカードよりも前の時代に登場しましたが、同じコネクタとカード形状を使用しており、SPIのみをサポートしています。）一部のPCハードウェアではBIOSコードにSPIフラッシュを使用しています。

SPIスレーブチップはアナログセンサーやコーデック用のデジタル/アナログコンバーターから、メモリ、USBコントローラーやイーサネットアダプタなどのペリフェラルに至るまで幅広い用途があります。

SPIを使用するシステムでは、メインボードにいくつかのデバイスが統合されるのが一般的です。一部のシステムでは拡張コネクタにSPIリンクを提供しており、専用のSPIコントローラーが存在しない場合、GPIOピンを使用して低速の「ビットバッキング」アダプターを作成できます。SPIコントローラーを「ホットプラグ」するシステムは非常に少なく、SPIを使用する理由は低コストとシンプルな操作に焦点を当てており、動的リコンフィギュレーションが重要であればUSBがより適切な低ピンカウントのペリフェラルバスです。

Linuxを実行可能なマイクロコントローラーは通常、SPIモードを持つ1つ以上のI/Oインターフェースを統合しています。SPIサポートがあれば、専用のMMC/SD/SDIOコントローラーを必要とせずにMMCまたはSDカードを使用できます。

混乱しています。これら4つのSPI「クロックモード」は何ですか？¶

ここでは混乱しやすいため、見つかるベンダーのドキュメンテーションは必ずしも役立ちません。4つのモードは2つのモードビットを組み合わせたものです：

  • CPOLは初期クロック極性を示します。CPOL=0はクロックが低電圧で始まり、最初の（リードイン）エッジが上昇、次の（リードアウト）エッジが下降することを意味します。CPOL=1はクロックが高電圧で始まり、最初の（リードイン）エッジが下降することを意味します。

  • CPHAはデータをサンプリングするクロックフェーズを示します。CPHA=0はリードインエッジでサンプリングすることを意味し、CPHA=1はリードアウトエッジでサンプリングすることを意味します。

    信号がサンプリングされる前に安定する必要がありますが、CPHA=0は、データが最初のクロックエッジの半分前に書き込まれることを意味します。チップセレクトによってそのデータが利用可能になった可能性があります。

チップの仕様書では「SPIモードXを使用する」という表現は必ずしも使われませんが、タイミングチャートによってCPOLおよびCPHAのモードが明確になります。

SPIモード番号ではCPOLが高位ビット、CPHAが低位ビットです。チップのタイミングチャートがクロックが低レベルから始まり（CPOL=0）、データが後半のクロックエッジで安定してサンプリングされる（CPHA=1）場合、それはSPIモード1です。

クロックモードはチップセレクトがアクティブになる直後に重要になります。マスターはスレーブを選択する前にクロックを非アクティブに設定しなければなりません。スレーブは自身のセレクトラインがアクティブになるときにクロックレベルをサンプリングして選んだ極性を判別します。これが多くのデバイスがモード0とモード3の両方をサポートする理由です。極性に興味はなく、常にクロックの上昇エッジでデータをクロックイン/アウトするからです。

ドライバプログラミングインターフェースはどのように動作するのでしょうか？¶

<linux/spi/spi.h>ヘッダーファイルおよびメインソースコードはどちらもkerneldocを含んでおり、カーネルAPIドキュメントのこの章を必ず読みましょう。これは概要であり、詳細な情報よりも全体像を把握するためのものです。

SPIリクエストは常にI/Oキューに投入されます。特定のSPIデバイスのリクエストは常にFIFO順序で実行され、完了コールバックを通じて非同期的に完了します。また、これらの呼び出しには簡単な同期処理のラッパーも含まれており、コマンドを送信してその応答を読み取るなどの一般的なトランザクションタイプにも対応しています。

SPIドライバには2つのタイプがあります。ここでは以下のように呼びます：

コントローラードライバ …

コントローラーはシステムオンチッププロセッサに組み込まれることがあり、多くの場合マスターおよびスレーブの両方の役割をサポートします。これらのドライバはハードウェアレジスタにアクセスし、DMAを用いることも可能です。あるいは、GPIOピンのみで動作するPIOビットバンガーや、PIOビットバンガーとして動作するものもあります。

プロトコルドライバ …

これらはコントローラードライバを通じてメッセージを送り、SPIリンクの他端にあるスレーブまたはマスター機器と通信します。

たとえば、1つのプロトコルドライバはMTDレイヤーを通じてDataFlashなどのSPIフラッシュメモリに保存されたファイルシステムへのデータをエクスポートするかもしれません。また、他のドライバはオーディオインターフェースを制御したり、タッチスクリーンセンサーを入力インターフェースとして提示したり、産業プロセス中の温度や電圧レベルを監視したりするかもしれません。これらはすべて同じコントローラードライバを共有しているかもしれません。

A “struct spi_device「」はこの2種類のドライバ間のコントローラー側のインターフェースをまとめています。

SPIプログラミングインターフェースの最小限のコアがあり、ドライバーモデルを使用してコントローラーとプロトコルドライバを接続するためのデバイステーブルをボード固有の初期化コードが提供することに焦点を当てています。SPIはsysfsにおいて複数の場所に表示されます。

/sys/devices/.../CTLR ... physical node for a given SPI controller

/sys/devices/.../CTLR/spiB.C ... spi_device on bus "B",
     chipselect C, accessed through CTLR.

/sys/bus/spi/devices/spiB.C ... symlink to that physical
     .../CTLR/spiB.C device

/sys/devices/.../CTLR/spiB.C/modalias ... identifies the driver
     that should be used with this device (for hotplug/coldplug)

/sys/bus/spi/drivers/D ... driver for one or more spi*.* devices

/sys/class/spi_master/spiB ... symlink (or actual device node) to
     a logical node which could hold class related state for the SPI
     master controller managing bus "B".  All spiB.* devices share one
     physical SPI bus segment, with SCLK, MOSI, and MISO.

/sys/devices/.../CTLR/slave ... virtual file for (un)registering the
     slave device for an SPI slave controller.
     Writing the driver name of an SPI slave handler to this file
     registers the slave device; writing "(null)" unregisters the slave
     device.
     Reading from this file shows the name of the slave device ("(null)"
     if not registered).

/sys/class/spi_slave/spiB ... symlink (or actual device node) to
     a logical node which could hold class related state for the SPI
     slave controller on bus "B".  When registered, a single spiB.*
     device is present here, possible sharing the physical SPI bus
     segment with other SPI slave devices.

コントローラーのクラス状態の実際の場所は、CONFIG_SYSFS_DEPRECATEDが有効になっているかどうかにより異なります。現在、クラス固有の状態はバス番号（「B」が「spiB」の「B」）のみであり、そのため/sys/classのエントリはバスを素早く特定するためのものです。

ボード固有の初期化コードがSPIデバイスを宣言する方法は？¶

LinuxはSPIデバイスを正しく構成するためにいくつかの情報が必要です。通常、その情報はボード固有のコードによって提供され、一部の自動検出/列挙をサポートするチップであっても同様です。

コントローラーの宣言¶

最初の情報は、存在するSPIコントローラーの一覧です。SoC（システムオンチップ）ベースのボードでは、これらは通常プラットフォームデバイスであり、コントローラーは正しく動作するためにいくつかのプラットフォームデータが必要になる場合があります。"struct platform_device"には、コントローラーの最初のレジスタの物理アドレスやIRQなどのリソースが含まれます。

プラットフォームではしばしば"register SPI controller"操作を抽象化し、ピン設定の初期化コードと結合するため、arch/…/mach-/board-.cファイルで複数のボードが同じ基本的なコントローラー設定コードを共有できます。これは、ほとんどのSoCが複数のSPI対応コントローラーを備えているためで、実際に使用可能なコントローラーのみが設定および登録されるべきです。

したがって、例としてarch/…/mach-/board-.cファイルには次のようなコードが含まれるかもしれません：

#include <mach/spi.h>   /* for mysoc_spi_data */

/* if your mach-* infrastructure doesn't support kernels that can
 * run on multiple boards, pdata wouldn't benefit from "__init".
 */
static struct mysoc_spi_data pdata __initdata = { ... };

static __init board_init(void)
{
        ...
        /* this board only uses SPI controller #2 */
        mysoc_register_spi(2, &pdata);
        ...
}

そしてSoC固有のユーティリティコードは次のようになるかもしれません：

#include <mach/spi.h>

static struct platform_device spi2 = { ... };

void mysoc_register_spi(unsigned n, struct mysoc_spi_data *pdata)
{
        struct mysoc_spi_data *pdata2;

        pdata2 = kmalloc(sizeof *pdata2, GFP_KERNEL);
        *pdata2 = pdata;
        ...
        if (n == 2) {
                spi2->dev.platform_data = pdata2;
                register_platform_device(&spi2);

                /* also: set up pin modes so the spi2 signals are
                 * visible on the relevant pins ... bootloaders on
                 * production boards may already have done this, but
                 * developer boards will often need Linux to do it.
                 */
        }
        ...
}

ボードごとのplatform_dataが異なることに注意してください。たとえば、1つのボードではSPIが外部クロックを使用し、他のボードではマスタクロックの現在の設定からSPIクロックを導出する場合があります。

スレーブデバイスの宣言¶

2番目の情報は、ターゲットボード上の存在するSPIスレーブデバイスの一覧で、ドライバが正しく動作するためにボード固有のデータが含まれていることが通常です。

通常、arch/…/mach-/board-.cファイルは各ボードのSPIデバイスをリストする小さなテーブルを提供します。(これは通常非常に少数です。) それは次のようになるかもしれません：

static struct ads7846_platform_data ads_info = {
        .vref_delay_usecs       = 100,
        .x_plate_ohms           = 580,
        .y_plate_ohms           = 410,
};

static struct spi_board_info spi_board_info[] __initdata = {
{
        .modalias       = "ads7846",
        .platform_data  = &ads_info,
        .mode           = SPI_MODE_0,
        .irq            = GPIO_IRQ(31),
        .max_speed_hz   = 120000 /* max sample rate at 3V */ * 16,
        .bus_num        = 1,
        .chip_select    = 0,
},
};

また、ボード固有の情報が提供されていることに注意してください。チップごとに複数の種類が必要な場合があります。この例では、ボード電圧に依存する最高速SPIクロックや、IRQピンの配線方法などの汎用的な制約、またはチップ固有の制約（あるピンのキャパシタンスによって変化する重要な遅延など）が示されています。

(「controller_data」という情報もあります。これはコントローラードライバーにとって有用な情報です。例えば、ペリフェラル固有のDMAチューニングデータやチップセレクトコールバックなどが該当します。これは後述のspi_deviceに保存されます。)

board_infoは、チップのドライバーがロードされる前でもシステムが動作するための十分な情報を提供する必要があります。その中で最も問題になるのは、spi_device.modeフィールド内のSPI_CS_HIGHビットです。なぜなら、バスを共有するデバイスがチップセレクトを「逆に」解釈する場合、インフラストラクチャがチップセレクトを解除する方法を知るまでは動作が不可能だからです。

その後、ボード初期化コードではこのテーブルをSPIインフラストラクチャに登録し、SPIマスターコントローラードライバーが登録されるときに利用できるようにします。

spi_register_board_info(spi_board_info, ARRAY_SIZE(spi_board_info));

他の静的ボード固有の設定と同様に、これらはアンレジスタリングしません。

広く利用されている「カードスタイル」のコンピュータは、メモリ、CPU、それ以外の部品をほぼ30平方センチメートルのカードに集約しています。このようなシステムでは、あなたの arch/.../mach-.../board-*.c ファイルは、このようなカードが挿さるメインボード上のデバイスに関する情報を主に提供します。これはSPIデバイスがカードコネクタを通じて接続されている場合も当然含まれます。

非静的な設定¶

開発ボードは製品ボードと異なるルールに従うことが多く、ホットプラグ可能なSPIデバイスおよび/またはコントローラーが必要な場合があります。

そのようなケースでは、 spi_busnum_to_master() を用いてspiバスマスターを検索し、おそらく spi_new_device() を用いてホットプラグされたボードに基づいたボード情報の提供が必要です。もちろん、そのボードが除去された後には少なくとも spi_unregister_device() を呼び出します。

LinuxがSPIを通じてMMC/SD/SDIO/DataFlashカードのサポートを含む場合、これらの設定も動的になります。幸いなことに、このようなデバイスはすべて基本的なデバイス識別プローブをサポートしているため、ホットプラグが通常通り動作するはずです。

私はどのように「SPIプロトコルドライバー」を書くべきですか？¶

現在、ほとんどのSPIドライバーはカーネルドライバーですが、ユーザー空間ドライバーのサポートもあります。ここではカーネルドライバーについてのみ説明します。

SPIプロトコルドライバーはプラットフォームデバイスドライバーに若干似ています：

static struct spi_driver CHIP_driver = {
        .driver = {
                .name           = "CHIP",
                .owner          = THIS_MODULE,
                .pm             = &CHIP_pm_ops,
        },

        .probe          = CHIP_probe,
        .remove         = CHIP_remove,
};

ドライバコアは、ボード情報(board_info)が「CHIP」というmodaliasを指定したSPIデバイスに自動的にこのドライバをバインドしようとします。probe()関数のコードは、バスを管理しているデバイスを除いて、このように見えるでしょう。

static int CHIP_probe(struct spi_device *spi)
{
        struct CHIP                     *chip;
        struct CHIP_platform_data       *pdata;

        /* assuming the driver requires board-specific data: */
        pdata = &spi->dev.platform_data;
        if (!pdata)
                return -ENODEV;

        /* get memory for driver's per-chip state */
        chip = kzalloc(sizeof *chip, GFP_KERNEL);
        if (!chip)
                return -ENOMEM;
        spi_set_drvdata(spi, chip);

        ... etc
        return 0;
}

probe()関数に入った瞬間、ドライバはSPIデバイスに対してI/Oリクエストを送信できます。『struct spi_message』を使用します。remove()関数が返るか、probe()関数が失敗した後、ドライバはこのようなメッセージをもう送信しなくなります。

  • spi_messageは、プロトコル操作のシーケンスで、1つのアトミックなシーケンスとして実行されます。SPIドライバの制御には以下の項目があります：

    • 双方向の読み書きが開始するタイミング…spi_transferリクエストのシーケンスがどのように配置されるかによって決まります；

    • どのI/Oバッファが使用されるか…各spi_transferは、送信方向と受信方向それぞれにバッファをラップし、フルダプル（2つのポインタ、両方で同じポインタを用いる場合もあり）およびハーフダプル（1つのポインタがNULL）の転送をサポートします；

    • 転送後に短い遅延をオプションで定義…spi_transfer.delay_usecs設定を使用します（バッファ長がゼロの場合、この遅延がプロトコルの唯一の効果となることがあります）；

    • 転送後にチップセレクトが無効になるかどうかおよびその遅延…spi_transfer.cs_changeフラグを使用します；

    • 次のメッセージが同じデバイスに送られる可能性があるかどうかのヒント…そのアトミックなグループの最後の転送でspi_transfer.cs_changeフラグを使用し、チップのディセレクトおよびセレクト操作のコストを節約する可能性があります。

  • 標準のカーネルルールに従い、メッセージにDMAセーフなバッファを提供してください。これにより、DMAを使用するコントローラードライバは、ハードウェアが要求する場合を除き、余分なコピーを強制されません（例：ハードウェアのエラーラタを回避するためのバウンスバッファの使用を強制する場合）。

    標準のdma_map_single()処理がこれらのバッファに不適切な場合、spi_message.is_dma_mappedを使用してコントローラードライバに、関連するDMAアドレスをすでに提供したことを通知できます。

  • 基本的なI/Oの原始操作は spi_async()です。非同期リクエストは、任意のコンテキスト（割込みハンドラ、タスクなど）で発行でき、完了はメッセージとともに提供されるコールバックで報告されます。検出されたエラー後、チップはディセレクトされ、そのspi_messageの処理は中止されます。

  • 同期的なラッパーもあります、例えば spi_sync()、およびラッパーもあります、例えば spi_read(), spi_write(), and spi_write_then_read()。これらは、スリープ可能なコンテキストでのみ発行でき、すべてがクリーン（かつ小型で、「オプション」的な）レイヤーです。 spi_async().

  • 以下の spi_write_then_read() call, and convenience wrappers around it, should only be used with small amounts of data where the cost of an extra copy may be ignored. It’s designed to support common RPC-style requests, such as writing an eight bit command and reading a sixteen bit response – spi_w8r16() being one of its wrappers, doing exactly that.

Some drivers may need to modify spi_device characteristics like the transfer mode, wordsize, or clock rate. This is done with spi_setup(), which would normally be called from probe() before the first I/O is done to the device. However, that can also be called at any time that no message is pending for that device.

While “spi_device” would be the bottom boundary of the driver, the upper boundaries might include sysfs (especially for sensor readings), the input layer, ALSA, networking, MTD, the character device framework, or other Linux subsystems.

Note that there are two types of memory your driver must manage as part of interacting with SPI devices.

  • I/O buffers use the usual Linux rules, and must be DMA-safe. You’d normally allocate them from the heap or free page pool. Don’t use the stack, or anything that’s declared “static”.

  • The spi_message and spi_transfer metadata used to glue those I/O buffers into a group of protocol transactions. These can be allocated anywhere it’s convenient, including as part of other allocate-once driver data structures. Zero-init these.

If you like, spi_message_alloc() and spi_message_free() convenience routines are available to allocate and zero-initialize an spi_message with several transfers.

How do I write an “SPI Master Controller Driver”?¶

An SPI controller will probably be registered on the platform_bus; write a driver to bind to the device, whichever bus is involved.

The main task of this type of driver is to provide an “spi_master”. Use spi_alloc_master() to allocate the master, and spi_master_get_devdata() to get the driver-private data allocated for that device.

struct spi_master       *master;
struct CONTROLLER       *c;

master = spi_alloc_master(dev, sizeof *c);
if (!master)
        return -ENODEV;

c = spi_master_get_devdata(master);

The driver will initialize the fields of that spi_master, including the bus number (maybe the same as the platform device ID) and three methods used to interact with the SPI core and SPI protocol drivers. It will also initialize its own internal state. (See below about bus numbering and those methods.)

After you initialize the spi_master, then use spi_register_master() to publish it to the rest of the system. At that time, device nodes for the controller and any predeclared spi devices will be made available, and the driver model core will take care of binding them to drivers.

SPIコントローラードライバーを削除する必要がある場合、spi_unregister_master()はspi_register_master()の効果を逆にする。

バス番号付け¶

バス番号付けは重要です。これはLinuxが特定のSPIバス（共有SCK、MOSI、MISO）を識別する方法です。有効なバス番号はゼロから始まります。SoCシステムでは、バス番号はチップメーカーが定義した番号と一致させる必要があります。たとえば、ハードウェアコントローラーSPI2はバス番号2に、それに接続されたデバイスのspi_board_infoはこの番号を使用します。

ハードウェア割り当てられたバス番号を持っていない場合、または何らかの理由で番号を割り当てられない場合は、負のバス番号を提供してください。これにより、動的に割り当てられた番号に置き換えられます。この場合、非静的構成として扱う必要があります（上記参照）。

SPIマスターメソッド¶

master->setup(struct spi_device *spi)

この機能はデバイスのクロック周波数、SPIモード、ワードサイズを設定します。ドライバーはboard_infoで提供されるデフォルトを変更し、spi_setup(spi)を呼び出してこの手順を実行できます。この関数はスリープする可能性があります。

各SPIスレーブが独自の設定レジスタを持つ場合でない限り、すぐに変更しないでください…それ以外にドライバーが他のSPIデバイスの進行中のI/Oを破損させる可能性があります。

注意

BUGアラート：多くのspi_masterドライバーの最初のバージョンはなぜかこの処理を誤って実行しているようです。setup()をコードする際、コントローラーが他のデバイスの転送を処理中であると仮定してください。

master->cleanup(struct spi_device *spi)

コントローラードライバーはspi_device.controller_stateを使用して、そのデバイスに動的に関連付ける状態を保持できます。このような場合、状態を解放するcleanup()メソッドを提供する必要があります。

master->prepare_transfer_hardware(struct spi_master *master)

キュー機構がドライバーにメッセージが間もなく到着するという信号を送るため呼び出されます。この呼び出しにより、サブシステムがドライバーに転送ハードウェアの準備を求めるため、この関数を実行します。この関数はスリープする可能性があります。

master->unprepare_transfer_hardware(struct spi_master *master)

キュー機構がドライバーにキューに待機中のメッセージがなくなったことを通知するため呼び出されます。これにより、ドライバーはハードウェアをリラックスさせる（例：電源管理呼び出し）ことができます。この関数はスリープする可能性があります。

master->transfer_one_message(struct spi_master *master, struct spi_message *mesg)

サブシステムは、同時に到着する転送をキューに積みながら、単一のメッセージをドライバーに転送します。ドライバーがこのメッセージを完了した後、 spi_finalize_current_message() サブシステムが次のメッセージを送信できるようにするため、この関数を呼び出す必要があります。この関数はスリープする可能性があります。

master->transfer_one(struct spi_master *master, struct spi_device *spi, struct spi_transfer *transfer)

サブシステムは、同時に到着する転送をキューに積みながら、単一の転送をドライバーに転送します。ドライバーがこの転送を完了した後、 spi_finalize_current_transfer() したがってサブシステムは次のトランスファーを実行できます。これは待機する可能性があります。注意: transfer_one と transfer_one_message は排他的に使用され、両方が設定されている場合、汎用サブシステムは transfer_one コールバックを呼びません。

戻り値:

  • 負の errno: エラー

  • 0: トランスファーが完了しました

  • 1: トランスファーが進行中です

master->set_cs_timing(struct spi_device *spi, u8 setup_clk_cycles, u8 hold_clk_cycles, u8 inactive_clk_cycles)

このメソッドは、SPI クライアントドライバが SPI マスターコントローラーにデバイス固有の CS セットアップ、ホルド、非アクティブタイミングの要件を設定するようリクエストできます。

非推奨のメソッド¶

master->transfer(struct spi_device *spi, struct spi_message *message)

このメソッドは待機してはいけません。責任はトランスファーが実行され、complete() コールバックが発行されるようにすることです。通常、他のトランスファーが完了した後、またはコントローラーがアイドル状態であればキックスタートが必要です。このメソッドはキューイングされたコントローラーでは使用されず、transfer_one_message() および (un)prepare_transfer_hardware() が実装されている場合は NULL でなければなりません。

SPI メッセージキュー¶

SPI サブシステムが提供する標準的なキューイングメカニズムに満足している場合は、上記のキューイングメソッドを実装するだけでよいです。メッセージキューを使用すると、多くのコードを集中化し、純粋なプロセスコンテキストでのメソッド実行が可能になります。また、高優先度の SPI 通信ではメッセージキューをリアルタイム優先度に昇格させることも可能です。

SPI サブシステムのキューイングメカニズムが選択されていない場合、ドライバの大部分は現在非推奨の関数 transfer() で供給される I/O キューを管理することになります。

そのキューは純粋に概念的かもしれません。たとえば、低周波数センサーへのアクセス専用のドライバであれば、同期 PIO を使用しても問題ありません。

しかし、キューはおそらく現実的であり、message->queue、PIO、DMA（特にルートファイルシステムが SPI フラッシュメモリにある場合）、IRQ ハンドラ、タスケット、ワークキュー（keventd など）などの実行コンテキストを使用します。ドライバは必要に応じて複雑でも単純でも構いません。このような transfer() メソッドは通常、メッセージをキューに追加し、その後非同期トランスファーエンジンを開始します（既に実行中であれば除きます）。

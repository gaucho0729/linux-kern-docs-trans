SPIユーザースペースAPI¶

SPIデバイスは制限されたユーザースペースAPIを持ち、SPIスレーブデバイスへの基本的な半二重通信のread()およびwrite()アクセスをサポートしています。ioctl()リクエストを使用することで、フルダブルックス転送やデバイスI/O設定も利用可能です。

#include <fcntl.h>
#include <unistd.h>
#include <sys/ioctl.h>
#include <linux/types.h>
#include <linux/spi/spidev.h>

このプログラミングインターフェースを使用したい理由として考えられるのは次の通りです:

  • クラッシュしにくい環境でのプロトタイピング；ユーザースペースの不正なポインタがLinuxシステムを通常は停止させません。

  • マイクロコントローラーがSPIスレーブとして動作する際に使用するシンプルなプロトコルの開発。このプロトコルは頻繁に変更する必要がある場合があります。

もちろん、カーネルインターフェース（IRQハンドラーやドライバスタックの他のレイヤーなど）にアクセスする必要があるため、ユーザースペースで書くことができないドライバもあります。

デバイスの作成、ドライバのバインディング¶

このドライバを使用するための最も簡単な方法は、デバイスのspi_board_infoにこのドライバを指定することです。「modalias」エントリは「spidev」として、このAPIを提供するドライバの名前と一致します。他のデバイス特性（ワードあたりのビット数、SPIクロッキング、チップセレクトの極性など）は通常通り設定し、後で上書きする必要は常にありません。

(Sysfsはユーザースペース駆動のドライバとデバイスのバインディング/アンバインディングもサポートしています。このメカニズムは今後このドキュメントでサポートされる可能性があります。)

この操作を行うと、SPIデバイスのsysfsノードには「dev」属性を持つ子デバイスノードが含まれます。これはudevまたはmdevによって理解されます。(大規模なシステムでは「udev」が使用され、小規模なシステムではbusyboxに「mdev」を組み込むことがあり、機能は少なめですが十分な場合があります。) チップセレクトCを持つバスB上のSPIデバイスでは、以下を確認してください:

/dev/spidevB.C …

キャラクタースペシャルデバイスで、メジャーナンバー153で動的に選ばれたマイナーデバイス番号を持つ。これはudevまたはmdevによって作成され、ユーザースペースのプログラムがオープンするノードです。

/sys/devices/…/spiB.C …

通常、SPIデバイスノードはSPIマスターマネージャーの子ノードになります。

/sys/class/spidev/spidevB.C …

「spidev」ドライバがそのデバイスにバインドしたときに作成されます。(「deprecated sysfs files」Kconfigオプションを有効にした場合、ディレクトリまたはシンリンクになります。)

/devキャラクタースペシャルデバイスノードを手動で管理しないでください。これは誤りが生じやすく、システムセキュリティの問題に注意する必要があります。udev/mdevはすでにセキュアに設定されています。

そのデバイスから「spidev」ドライバをアンバインドすると、その2つの「spidev」ノード（sysfs内のものと/dev内のもの）は自動的に削除されます（それぞれカーネルとudev/mdevによって）。ドライバモジュール「spidev」を削除することでアンバインドできますが、これによりこのドライバを使用するすべてのデバイスに影響が出ます。また、カーネルコードがSPIデバイスを削除することでアンバインドすることも可能で、おそらくそのSPIコントローラーのドライバを削除することで、そのspi_masterが消えます。

これは標準的なLinuxデバイスドライバです – たとえユーザー空間に低レベルAPIを提供するだけでも – 一度に複数のデバイスと関連付けることができます。各SPIデバイスに対してspi_board_infoレコードを1つずつ提供すれば、各デバイスに対して/devデバイスノードが作成されます。

BASIC CHARACTER DEVICE API¶

/dev/spidevB.Dファイルの通常のオープン()およびクローズ()操作は、予想通りに動作します。

標準的なリード()およびライト()操作は明らかに半二重通信であり、これらの操作の間にチップセレクトが無効になります。全二重通信やチップセレクト無効化なしの複合操作は、SPI_IOC_MESSAGE(N)リクエストを使用して実行可能です。

いくつかのioctl()リクエストにより、ドライバがデバイスのデータ転送パラメータの現在の設定を読み取ったり上書きしたりできます:

SPI_IOC_RD_MODE, SPI_IOC_WR_MODE …

1バイトのポインタを渡して、(RD)読み取りまたは(WR)設定でSPI転送モードを取得または設定します。SPI_MODE_0〜SPI_MODE_3の定数を使用してください。またはSPI_CPOL（クロック極性、このフラグが設定されている場合、アイドル状態はハイ）またはSPI_CPHA（クロックフェーズ、このフラグが設定されている場合、サンプリングは降下エッジ）フラグを組み合わせて使用することも可能です。注意点として、このリクエストは1バイトに収まるSPIモードフラグに限定されます。

SPI_IOC_RD_MODE32, SPI_IOC_WR_MODE3, …

uin32_tのポインタを渡して、(RD)読み取りまたは(WR)設定でフルなSPI転送モードを取得または設定します。1バイトに収まるビットに限定されません。

SPI_IOC_RD_LSB_FIRST, SPI_IOC_WR_LSB_FIRST …

1バイトのポインタを渡して、(RD)読み取りまたは(WR)設定でSPIワードのビット正規化を取得または設定します。ゼロはMSB優先を示し、他の値はLSB優先のエンコーディングを示します。どちらの場合も、各ワード内で右に詰められており、未使用（TX）または未定義（RX）ビットはMSBに配置されます。

SPI_IOC_RD_BITS_PER_WORD, SPI_IOC_WR_BITS_PER_WORD …

1バイトのポインタを渡して、(RD)読み取りまたは(WR)設定でSPI転送ワードのビット数を取得または設定します。ゼロは8ビットを示します。

SPI_IOC_RD_MAX_SPEED_HZ, SPI_IOC_WR_MAX_SPEED_HZ …

u32型のポインタを渡して、最大SPI転送速度（Hz単位）をRDで返すかWRで設定するようにします。コントローラーがその特定のクロック速度を必ずしも設定できるとは限りません。

ノート：

  • 現在は非同期I/Oのサポートはありません。すべて同期処理です。

  • 特定のデバイスにデータをシフトする際の実際のビットレートを報告する方法はありません。

  • ユーザースペースから現在はチップセレクトの極性を変更できません。他のSPIバスを共有するデバイスへの転送を破壊する可能性があるためです。SPIデバイスがアクティブに使用されていないときは常に選択解除され、他のドライバーが他のデバイスと通信できるようになります。

  • 各I/OリクエストがSPIデバイスに転送できるバイト数には制限があります。デフォルトでは1ページですが、モジュールパラメータを変更することで変更可能です。

  • SPIは低レベルでの転送確認を提供しないため、非存在するデバイスと通信する際には通常I/Oエラーが表示されません。

フルダブルスルー文字デバイスAPI¶

spidev_fdx.cのサンプルプログラムはフルダブルスループログラミングインターフェースの使用例を示しています（ただし、実際にフルダブルスルー転送は行われません）。このモデルはカーネルで使用されているものと同じです。 spi_sync() リクエスト；個別転送はカーネルドライバーで利用可能な機能と同様の能力を提供します（非同期ではない点を除きます）。

例では半二重のRPCスタイルのリクエストと応答メッセージを示しています。このようなリクエストでは、リクエストと応答の間にチップが選択解除されないことが一般的です。複数のリクエストを1つのカーネルリクエストにチェーン化でき、各応答後にチップを選択解除することも可能です。（他のプロトコルオプションには、各転送セグメントごとにワードサイズやビットレートを変更することも含まれます。）

フルダブルスルーリクエストを行うには、同じ転送に対してrx_bufとtx_bufの両方を提供してください。これらが同じバッファでも問題ありません。

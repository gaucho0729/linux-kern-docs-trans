一般的な通知メカニズム¶

汎用通知メカニズムは標準のパイプドライバーに基づいて構築されており、これによりカーネル内の通知メッセージがユーザー空間で開かれたパイプに有効にスプライスされます。これは以下の項目と併用可能です:

* Key/keyring notifications

通知バッファは以下の方法で有効化できます:

「汎用設定」/「汎用通知キュー」(CONFIG_WATCH_QUEUE)

概要¶

この機能は特別なモードで開かれたパイプとして現れます。パイプの内部リングバッファはカーネルが生成するメッセージを保持します。これらのメッセージはread()によって読み出されます。このようなパイプではスプライスや類似の操作が無効化されており、特定の状況下でリングへの追加を元に戻す必要があるため、通知メッセージと混在する可能性があるためです。

パイプの所有者は、そのパイプを通じて監視したいソースをカーネルに指定する必要があります。接続されていないソースはパイプにメッセージを挿入しません。注意点として、1つのソースが複数のパイプにバインドされ、同時にすべてのパイプにメッセージを挿入することがあります。

パイプにフィルタも設定可能です。関心のないソースタイプやサブイベントは無視されます。

リングバッファに空きがない場合、または事前に割り当てられたメッセージバッファが利用できない場合、メッセージは破棄されます。このような場合、read()はバッファ内の最後のメッセージが読み出された後に、WATCH_META_LOSS_NOTIFICATIONメッセージを出力バッファに挿入します。

通知を生成する際、カーネルは消費者が通知を収集するのを待たず、ただ進み続けます。これはスピンロックを保持しながら通知を生成できるようにし、ユーザー空間の障害によってカーネルが無限に待機することを防ぎます。

メッセージ構造¶

通知メッセージは短いヘッダーで始まります:

struct watch_notification {
        __u32   type:24;
        __u32   subtype:8;
        __u32   info;
};

「type」は通知レコードのソースを示し、「subtype」はそのソースからのレコードタイプを示します（以下で説明するWatch Sourcesセクションを参照）。typeは「WATCH_TYPE_META」も可能で、これはwatchキュー自体が生成する特別なレコードタイプです。サブタイプは2種類あります:

  • WATCH_META_REMOVAL_NOTIFICATION

  • WATCH_META_LOSS_NOTIFICATION

前者はウォッチが設定されたオブジェクトが削除または破壊されたことを示し、後者はいくつかのメッセージが失われたことを示します。

「info」は以下の情報などを含みます:

  • メッセージのバイト数（ヘッダーを含む）。これは、マスク処理をWATCH_INFO_LENGTHとシフト処理をWATCH_INFO_LENGTH__SHIFTで行い、レコードのサイズを示します。このサイズは8〜127バイトの間です。

  • ウォッチID（マスク処理をWATCH_INFO_IDとシフト処理をWATCH_INFO_ID__SHIFTで行います）。これは、ウォッチの呼び出し元IDを示し、0〜255の間で設定可能です。複数のウォッチが同じキューを共有する場合があり、これにより区別を行います。

  • タイプ固有のフィールド（WATCH_INFO_TYPE_INFO）。通知の生成元がこのフィールドを設定し、タイプとサブタイプに固有の意味を示します。

infoの内容で長さを除くすべてはフィルタリングに使用可能です。

ヘッダーの後には補足情報が続くことがあります。この情報のフォーマットはタイプとサブタイプによって定義されます。

ウォッチリスト(通知ソース)API¶

「ウォッチリスト」は、通知のソースにサブスクライブしているウォッチャーのリストです。リストはオブジェクト（例えばキーまたはスーパーブロック）にアタッチされるか、グローバル（例えばデバイスイベント用）になることがあります。ユーザー空間から見ると、グローバルでないウォッチリストは、所属するオブジェクト（例えばKEYCTL_NOTIFYを使用してキーのシリアル番号を指定）を参照することで通常参照されます。

ウォッチリストを管理するための関数は以下の通りです：

  • void init_watch_list(struct watch_list *wlist,
                     void (*release_watch)(struct watch *wlist));

    ウォッチリストを初期化します。もし release_watch がNULLでない場合、この関数はウォッチリストオブジェクトが破棄されるときに呼び出され、ウォッチリストが保持しているウォッチされたオブジェクトへの参照を解放します。

  • void remove_watch_list(struct watch_list *wlist);

    ウォッチリストにサブスクライブされているすべてのウォッチを削除し、それらを解放した後、ウォッチリストオブジェクト自体を破棄します。

ウォッチキュー(通知出力)API¶

「ウォッチキュー」は、通知レコードが書き込まれるバッファで、アプリケーションが割り当てます。この動作はパイプデバイスドライバー内部で完全に隠蔽されていますが、ウォッチを設定するにはこの参照を取得する必要があります。これらは以下の通り管理できます：

  • struct watch_queue *get_watch_queue(int fd);

    ウォッチキューは、バッファを実装するパイプのfdでカーネルに示されます。ユーザー空間では、システムコールを通じてこのfdを渡す必要があります。これにより、システムコールからウォッチキューへのオパケなポインタを検索できます。

  • void put_watch_queue(struct watch_queue *wqueue);

    から取得した参照を破棄します get_watch_queue().

ウォッチサブスクリプションAPI¶

「ウォッチ」は、ウォッチリストへのサブスクライブであり、通知レコードが書き込まれるべきバッファ（ウォッチキュー）を示します。ウォッチキューオブジェクトは、ユーザー空間で設定されたフィルタリングルールも保持する場合があります。ウォッチ構造体の一部はドライバによって設定可能です：

struct watch {
        union {
                u32             info_id;        /* ID to be OR'd in to info field */
                ...
        };
        void                    *private;       /* Private data for the watched object */
        u64                     id;             /* Internal identifier */
        ...
};

以下の info_id 値はユーザー空間から取得した8ビットの数値で、WATCH_INFO_ID__SHIFTでシフトされ、通知が関連するウォッチキュー・バッファに書き込まれるときに、struct watch_notification::infoのWATCH_INFO_IDフィールドにOR操作で組み込まれます。

以下の private フィールドはドライバがウォッチリストに関連付けるデータで、 watch_list::release_watch() メソッドで報告する必要があります。

以下の id フィールドはソースのIDです。異なるIDでポストされた通知は無視されます。

以下の関数によりウォッチを管理できます:

  • void init_watch(struct watch *watch, struct watch_queue *wqueue);

    ウォッチオブジェクトを初期化し、そのポインターをウォッチキューに設定します。ロックデップの警告を回避するため、適切なバリアリングを用います。

  • int add_watch_to_object(struct watch *watch, struct watch_list *wlist);

    ウォッチをウォッチリスト（通知ソース）にサブスクライブします。この関数を呼び出す前に、ウォッチ構造体のドライバで設定可能なフィールドが設定されている必要があります。

  • int remove_watch_from_object(struct watch_list *wlist,
                             struct watch_queue *wqueue,
                             u64 id, false);

    ウォッチリストからウォッチを削除します。このウォッチは指定されたウォッチキュー（wqueue) およびオブジェクト識別子（id) と一致する必要があります。ウォッチキューに通知（WATCH_META_REMOVAL_NOTIFICATION) が送られ、ウォッチが削除されたことを示します。

  • int remove_watch_from_object(struct watch_list *wlist, NULL, 0, true);

    ウォッチリストからすべてのウォッチを削除します。これは破壊準備として呼び出されるものと想定され、この時点でウォッチリストは新しいウォッチからアクセスされないものとします。ウォッチキューの各サブスクライブウォッチに通知（WATCH_META_REMOVAL_NOTIFICATION) が送られ、ウォッチが削除されたことを示します。

通知投稿API¶

通知をウォッチリストにポストして、サブスクライブされたウォッチが確認できるようにするには、以下の関数を使用してください:

void post_watch_notification(struct watch_list *wlist,
                             struct watch_notification *n,
                             const struct cred *cred,
                             u64 id);

通知は事前にフォーマットされ、ヘッダー（n) へのポインターを渡してください。通知はこのサイズより大きく、バッファスロット単位のサイズは n->info & WATCH_INFO_LENGTH.

以下の cred structはソース（サブジェクト）の資格情報を示し、SELinuxなどのLSMに渡され、各キュー（オブジェクト）の資格情報に基づいてノートの記録を許可または抑制するかどうかを決定します。

以下の id ソースオブジェクトのID（例: キーのシリアル番号）です。この通知を確認するには、ウォッチに同じIDが設定されている必要があります。

ウォッチソース¶

任意のバッファは複数のソースから供給されることがあります。ソースには以下のものがあります:

  • WATCH_TYPE_KEY_NOTIFY

    このタイプの通知は、キーやキーリングの変更を示します。キーリングの内容やキーパラメータの変更も含まれます。

イベントフィルタリング¶

ウォッチキューが作成された後、以下の関数を使用してフィルタを適用して受信イベントを制限できます:

struct watch_notification_filter filter = {
        ...
};
ioctl(fd, IOC_WATCH_QUEUE_SET_FILTER, &filter)

フィルタの説明は次の型の変数です:

struct watch_notification_filter {
        __u32   nr_filters;
        __u32   __reserved;
        struct watch_notification_type_filter filters[];
};

ここで「nr_filters」はfilters[]内のフィルタ数で、「__reserved」は0にする必要があります。filters配列の要素は次の型を持ちます:

struct watch_notification_type_filter {
        __u32   type;
        __u32   info_filter;
        __u32   info_mask;
        __u32   subtype_filter[8];
};

以下では:

  • type フィルタリングするイベントタイプで、"WATCH_TYPE_KEY_NOTIFY"のような形式になります。

  • info_filter および info_mask 通知レコードのinfoフィールドにフィルタとして機能します。通知がバッファに書き込まれるのは次の条件を満たす場合です:

    (watch.info & info_mask) == info_filter

    たとえば、マウントツリー内の正確な監視ポイントでないイベントを無視するなど、このような用途に使用できます。

  • subtype_filter 関心のあるサブタイプを示すビットマスクです。subtype_filter[0]のビット0はサブタイプ0に対応し、ビット1はサブタイプ1に対応します。といった具合です。

ioctl()の引数がNULLの場合、フィルターが削除され、すべての監視ソースからのイベントが通過します。

ユーザースペースコード例¶

バッファは次の例のように作成されます:

pipe2(fds, O_TMPFILE);
ioctl(fds[1], IOC_WATCH_QUEUE_SET_SIZE, 256);

その後、キーリング変更通知を受信するように設定できます:

keyctl(KEYCTL_WATCH_KEY, KEY_SPEC_SESSION_KEYRING, fds[1], 0x01);

通知は次の例のように処理できます:

static void consumer(int rfd, struct watch_queue_buffer *buf)
{
        unsigned char buffer[128];
        ssize_t buf_len;

        while (buf_len = read(rfd, buffer, sizeof(buffer)),
               buf_len > 0
               ) {
                void *p = buffer;
                void *end = buffer + buf_len;
                while (p < end) {
                        union {
                                struct watch_notification n;
                                unsigned char buf1[128];
                        } n;
                        size_t largest, len;

                        largest = end - p;
                        if (largest > 128)
                                largest = 128;
                        memcpy(&n, p, largest);

                        len = (n->info & WATCH_INFO_LENGTH) >>
                                WATCH_INFO_LENGTH__SHIFT;
                        if (len == 0 || len > largest)
                                return;

                        switch (n.n.type) {
                        case WATCH_TYPE_META:
                                got_meta(&n.n);
                        case WATCH_TYPE_KEY_NOTIFY:
                                saw_key_change(&n.n);
                                break;
                        }

                        p += len;
                }
        }
}

ALSA PCM タイムスタンプ¶

ALSA APIは、2つの異なるシステムタイムスタンプを提供できます。

  • trigger_tstampは、.triggerコールバックが呼び出されるときに取得されるシステム時間のスナップショットです。通常はALSAコアがこのスナップショットを取得しますが、特定のハードウェアでは同期機能がある場合や、逆に遅延を伴って正確な推定値を提供できる場合があります。後者の2つのケースでは、低レベルドライバが最も適切かつ正確なタイミングでtrigger_tstampを更新する責任があります。アプリケーションは単に最初のtrigger_t3stampに依存するのではなく、ドライバが遅延を伴って精緻な推定値を提供する場合、内部計算を更新する必要があります。

  • tstampは、最後のイベントまたはアプリケーションのクエリ時に更新される現在のシステムタイムスタンプです。差分（tstamp - trigger_tstamp）は経過時間を定義します。

ALSA APIは、availとdelayという2つの基本的な情報を提供します。これらは、トリガーおよび現在のシステムタイムスタンプと組み合わせることで、アプリケーションがリングバッファの「満たさ」やキューイングされたサンプルの量を追跡できます。

これらの異なるポインタとタイムスタンプ情報の使用は、アプリケーションのニーズに依存します：

  • avail リングバッファに書き込める量を報告します

  • delay すべてのキューイングされたサンプルが再生された後、新しいサンプルを聞くのにかかる時間を報告します。

タイムスタンプが有効になっている場合、avail/delay情報はシステム時間のスナップショットとともに報告されます。アプリケーションは以下の選択肢から選ぶことができます： CLOCK_REALTIME (NTP補正を含む、戻る可能性あり） CLOCK_MONOTONIC (NTP補正を含むが戻らない） CLOCK_MONOTIC_RAW (NTP補正なし）およびsw_paramsでモードを動的に変更できます。

ALSA APIはまた、audio_tstampというタイムスタンプを提供します。これは、音声ハードウェアのさまざまなコンポーネントで測定される時間の経過を反映します。アスキーアートでこの場合を以下のように表現できます（再生の場合）：

--------------------------------------------------------------> time
  ^               ^              ^                ^           ^
  |               |              |                |           |
 analog         link            dma              app       FullBuffer
 time           time           time              time        time
  |               |              |                |           |
  |< codec delay >|<--hw delay-->|<queued samples>|<---avail->|
  |<----------------- delay---------------------->|           |
                                 |<----ring buffer length---->|

アナログ時間は、再生の最後の段階で取得され、実際のトランスデューサーに最も近い位置で測定されます。

リンク時間は、SoC/チップセットの出力で取得され、サンプルがリンクにプッシュされるタイミングです。ハードウェアがサンプルカウンターやウォールクロック（例：HDAudio 24MHzやネットワークソリューション用のPTPクロック）をサポートする場合、リンク時間は直接測定できます。逆に、フレームカウンタ（例：USB）を用いることで間接的に推定することもできます。

DMA時間はカウンタによって測定され、DMA転送のバースト性により、すべての測定の中で最も信頼性の低いものです。

アプリケーション時間は、リングバッファに書き込んだ後、アプリケーションが追跡する時間に対応します。

アプリケーションはハードウェアの能力を照会し、audio_tstamp_configフィールドで関連する設定を選択することで、希望する音声タイムスタンプの報告を定義し、タイムスタンプの精度の推定値を得ることができます。また、測定にアナログへの遅延を含めるようにリクエストすることも可能です。埋め込まれたDSPを提供するプラットフォームでは、リンクタイムへの直接アクセスは非常に重要です。専用ハードウェアでリンクタイムを直接測定し、システム時間と同期させることで、内部DSP処理時間や遅延を追跡する必要がなくなるためです。

アプリケーションがハードウェア/低レベルドライバでサポートされていない音声タイムスタンプをリクエストした場合、タイプはDEFAULTに上書きされ、タイムスタンプはhw_pointer値に基づいたDMA時間に基づいて報告されます。

以前の実装（タイムスタンプ選択を提供しなかったもの）との後方互換性を確保するため、ゼロ値のCOMPATタイムスタンプタイプで結果は、再生ストリームではHDAudioウォールクロック、その他の場合ではDMA時間（hw_ptr）にデフォルトで戻ります。

音声タイムスタンプの精度はユーザー空間に返されるため、適切な決定が可能です：

  • DMA時間（デフォルト）の場合、転送の粒度は更新間のステップから推定され、アプリケーションポインタが安全に巻き戻せる範囲に関する情報を提供します。

  • リンクタイムは、(tstamp-trigger_tstamp)/audio_tstampの比率を用いて、音声とシステム時間の長期的なずれを追跡するのに利用できます。精度は、平滑化/ローパスフィルタリングに必要な量を定義します。リンクタイムは起動時にリセットされるか、そのまま報告されるか選べます（後者は異なるストリームの進行を比較するのに有用ですが、ウォールクロックが常に動作し、アイドル期間中に巻き戻さないことを要件とします）。ハードウェアでサポートされている場合、絶対リンクタイムは正確な開始時間を定義するためにも利用できます（パッチWIP）

  • 音声タイムスタンプに遅延を含めても、直感的に精度が向上するとは限りません。たとえば、コーデックが変動する遅延DSP処理を含むか、ハードウェアコンポーネントのチェーンがある場合、遅延は正確に知られていません。

精度はナノ秒単位（符号なし32ビットワードを使用）で報告され、最大精度は4.29秒となり、音声アプリケーションには十分です…

タイムスタンピングのニーズは多様であり、単一のアプリケーションでも動的にaudio_tstamp_configを変更できます。In the STATUS ioctlでは、パラメータは読み取り専用であり、アプリケーション選択を許可しません。これにより、既存アプリケーションへの影響を最小限に抑えつつ制限を回避するため、新しい STATUS_EXT ioctlが導入され、読み取り/書き込み可能なパラメータが使用されます。ALSA-libはこの新しいioctlを活用するよう修正され、 STATUS_EXT および効果的に非推奨とされます STATUS.

ALSA APIは一度に1つのオーディオタイムスタンプのみを報告できます。これは意図的な設計です。ハードウェアレジスタやIPCからオーディオタイムスタンプを読み取るには時間がかかり、報告するタイムスタンプが増えるほど測定結果の精度が低下します。誤解を避けるため、一度に1つの（システム、オーディオ）タイムスタンプのみを報告します。異なるタイムスタンプが必要なアプリケーションは、複数のクエリを実行し、結果を補間する必要があります

一部のハードウェア固有の設定では、システムタイムスタンプが低レベルのオーディオサブシステムによってキャッチされ、ドライバに情報が返されます。ハードウェアとの通信に潜在的な遅延があるため、利用可能時間と遅延情報とのずれのリスクがあります。アプリケーションが混乱しないようにするため、snd_pcm_status構造体にdriver_timestampフィールドが追加されました。このタイムスタンプは、ドライバが情報の組み立てを完了してからioctlを終了するタイミングを示します。 STATUS および STATUS_EXT ほとんどの場合、このdriver_timestampは通常のシステムタイムスタンプと一致します。

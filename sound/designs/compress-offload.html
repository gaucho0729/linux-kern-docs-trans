ALSA Compress-Offload API¶

Pierre-Louis.Bossart <pierre-louis.bossart@linux.intel.com>

Vinod Koul <vinod.koul@linux.intel.com>

概要¶

初期の頃から、ALSA APIはPCMサポートや定常ビットレートのペイロード（例：IEC61937）を想定して設計されていました。フレーム内の引数と返却値が通常の形式であり、これにより既存のAPIを圧縮データストリームに拡張するには困難な状況でした。

近年、オーディオデジタル信号プロセッサ（DSP）がシステムオンチップ設計に統合され、DSPはオーディオコーデックにも統合されています。このようなDSPで圧縮データを処理すると、ホストベースの処理と比較して消費電力が大幅に削減されます。Linuxではこのようなハードウェアのサポートは十分ではありませんでした。これは、メインラインカーネルに存在する汎用的なAPIが不足しているためです。

ALSA PCMインターフェースのAPI変更による互換性破壊を必要とせず、新しい「圧縮データ」APIが導入され、オーディオDSP向けの制御およびデータストリーミングインターフェースを提供します。

このAPIの設計は、インテルのMoorestown SOCとの2年間の経験に基づいており、APIをメインラインカーネルにアップストリームするためにはステージングツリーではなく他のユーザーが使用できるようにするための多くの修正が必要でした。

要件¶

主な要件は以下の通りです：

  • バイト数と時間の分離。圧縮形式はファイルごとに、フレームごとに、またはヘッダーをまったく持たない場合があります。ペイロードのサイズはフレームごとに変化する可能性があります。その結果、圧縮データを処理する際、オーディオバッファの持続時間を正確に推定することは困難です。信頼性のあるオーディオ-ビデオ同期を実現するには、特定のメカニズムが必要であり、その際、任意の時点でのレンダリングされたサンプル数を正確に報告する必要があります。

  • 複数のフォーマットの処理。PCMデータにはサンプリングレート、チャンネル数、サンプルあたりのビット数の指定のみが必要です。一方、圧縮データは多様なフォーマットで提供されます。オーディオDSPは、ファームウェアに埋め込まれた制限された数のオーディオエンコーダーおよびデコーダーのサポートを提供する場合もあり、動的ダウンロードを通じてより多くの選択肢をサポートすることもあります。

  • 主なフォーマットに焦点を当てます。このAPIは、オーディオおよびビデオのキャプチャと再生に使用される最も一般的なフォーマットをサポートしています。オーディオ圧縮技術が進化するにつれて、新しいフォーマットが追加される可能性があります。

  • 複数の設定の処理。例えばAACという特定のフォーマットでも、一部の実装ではAACマルチチャンネルをサポートするがHE-AACステレオをサポートしない場合があります。同様に、WMA10レベルM3はメモリとCPUサイクルをあまり使わないかもしれません。新しいAPIはこれらのフォーマットを一覧表示するための汎用的な方法を提供する必要があります。

  • レンダリング/キャプチャ専用です。このAPIはハードウェアアクセラレーションを提供せず、PCMサンプルをユーザースペースに戻して追加処理を許可します。このAPIは代わりに圧縮データをDSPにストリーミングするに焦点を当てており、デコードされたサンプルが物理的な出力または論理的なバックエンドにルーティングされるものと仮定しています。

  • 複雑性の隠蔽。既存のユーザースペースマルチメディアフレームワークはすべて、各圧縮フォーマットごとにenums/structuresを持っています。この新しいAPIは、プラットフォーム固有の互換性レイヤーが存在することを前提とし、オーディオDSPの機能を露出・翻訳・利用するためのものです（例：Android HALやPulseAudioのシンク）。構造上、通常のアプリケーションはこのAPIを使用すべきではありません。

設計¶

この新しいAPIはPCM APIといくつかの概念を共有しています。開始、一時停止、再開、ドレイン、停止コマンドのセマンティクスはコンテンツの種類に関係なく同じです。

ALSA PCM APIから借用されたメモリリングバッファのフラグメント分割概念があります。ただし、バイト単位でのサイズ指定のみ可能です。

シーク/トリックモードはホストが処理します。

巻き戻し/早送りの概念はサポートされていません。リングバッファにコミットされたデータは、すべてのバッファをドロップする場合を除き無効化できません。

圧縮データAPIは、データがオーディオDSPにどのように送信されるかについて仮定しません。DMA転送はメインメモリから埋め込まれたオーディオクラスターまたは外部DSP用SPIインターフェースへ可能です。ALSA PCMの場合と同様に、コアなルーチンが公開され、ドライバ実装者は必須ルーチンのサポートを書く必要があります。オプションのルーチンも利用可能かもしれません。

主な追加機能は以下の通りです

get_caps

このルーチンはサポートするオーディオフォーマット一覧を返します。キャプチャストリームのコーデックを照会するとエンコーダーが返され、再生ストリームではデコーダーがリストされます。

get_codec_caps

各コーデックごとに、このルーチンは機能のリストを返します。目的は、すべての機能が有効な設定に対応していることを確認し、設定失敗のリスクを最小限に抑えることです。たとえば、AACなどの複雑なコーデックでは、サポートされるチャンネル数は特定のプロファイルに依存する場合があります。機能が単一のディスクリプタで公開されていた場合、特定のプロファイル/チャンネル/フォーマットの組み合わせがサポートされない可能性があります。同様に、埋め込まれたDSPはメモリやCPUサイクルが限られているため、一部の実装では機能リストを動的にし、実行中のワークロードに依存するようにする可能性があります。コーデック設定に加えて、このルーチンは実装が処理する最小バッファサイズも返します。この情報はDMAバッファサイズや同期に必要なバイト数などに依存し、ユーザー空間がリングバッファにどのくらい書き込む必要があるかを定義するのに利用できます。

set_params

このルーチンは、特定のコーデックに選択された設定を設定します。パラメータで最も重要なフィールドはコーデックタイプです。ほとんどの場合、デコーダーは他のフィールドを無視しますが、エンコーダーは設定に厳密に従います。

get_params

このルーチンはDSPが実際に使用している設定を返します。設定の変更は例外の範囲にとどめるべきです。

get_timestamp

タイムスタンプは複数のフィールド構造になります。転送されたバイト数、処理されたサンプル数、レンダリング/キャプチャされたサンプル数がリストされます。これらの値を用いることで、平均ビットレートを算出したり、リングバッファの再補給が必要かどうかを判断したり、DSPでのデコード/エンコード/ioによる遅延を確認できます。

コーデック/プロファイル/モードのリストはOpenMAX AL仕様から導出しており、再発明を避けています。変更点には次の通り:- FLACおよびIECフォーマットの追加 - エンコーダー/デコーダー機能の統合 - プロファイル/モードをビットマスクとしてリストし、ディスクリプタをコンパクトにする - デコーダー用set_paramsの追加（OpenMAX ALに存在しない） - AMR/AMR-WBエンコーディングモードの追加（OpenMAX ALに存在しない） - WMAのフォーマット情報の追加 - 必要に応じてエンコーディングオプションの追加（OpenMAX ILから導出） - rateControlSupportedの追加（OpenMAX ALに存在しない）

Gapless Playback¶

アルバムを再生する際、デコーダーはエンコーダーの遅延とパディングをスキップし、トラックのコンテンツを直接次のトラックに移行できる。最終ユーザーはこの処理を「ギャップレス再生」として認識する。トラック間の切り替え時に静かな空白が生じないためである。

また、エンコーディングによって低強度のノイズが発生する可能性がある。すべての圧縮データで完全なギャップレス再生は難しいが、ほとんどの音楽コンテンツでは問題ない。デコーダーはエンコーダーの遅延とパディングを知る必要があるため、このメタデータをDSPに伝達する必要がある。このメタデータはID3/MP4ヘッダーから抽出され、デフォルトではビットストリームに含まれていないため、DSPに情報を伝達するための新しいインターフェースが必要となる。またDSPとユーザースペースはトラックを切り替えて、次のトラックのデータを開始する必要がある。

主な追加機能は以下の通り:

set_metadata

このルーチンはエンコーダーの遅延とパディングを設定する。デコーダーはこの情報をもとに静かな空白を除去できる。トラックのデータが書き込まれる前にこの設定を行う必要がある。

set_next_track

このルーチンはDSPに、この操作以降に送信されるメタデータと書き込み操作が次のトラックに該当することを通知する。

partial drain

ファイルの終わりに達したときに呼ばれる。ユーザースペースはDSPにEOFが到達したことを通知し、DSPはパディング遅延をスキップしてから次のトラックのデータを開始できる。

ギャップレス再生のシーケンスフローは以下の通り: - 開く - キャップス/コーデックキャップス取得 - パラメータ設定 - 最初のトラックのメタデータ設定 - 最初のトラックのデータを埋める - スタートをトリガー - ユーザースペースがすべて送信を終了 - 次のトラックデータを通知するためset_next_trackを送信 - 次のトラックのメタデータ設定 - その後partial_drainを呼び出してDSP内のバッファを大部分空に - 次のトラックのデータを埋める - DSPが2番目のトラックに切り替わる

(注: partial_drainと次のトラックの書き込みの順序は逆転することも可能)

ギャップレス再生では、実行状態から部分的なドレイン状態へ移行し、メタデータの設定と次のトラックの信号を送る処理を行う。

  compr_drain_notify()    |          |
+------------------------>|  RUNNING |
|                         |          |
|                         +----------+
|                              |
|                              |
|                              | compr_next_track()
|                              |
|                              V

非対応¶

  • VoIP/回線交換通話のサポートはこのAPIの対象外である。動的ビットレート変更のサポートはDSPとホストスタックの緊密な連携を必要とし、電力節約を制限するため、実装は困難である。

  • パケットロスの補償はサポートされていない。これはデコーダーが送信中にフレームが失われた際にデータを合成するための追加インターフェースが必要となるためである。今後追加される可能性がある。

  • ボリューム制御/ルーティングはこのAPIで処理されません。圧縮データインターフェースを提供するデバイスは通常のALSAデバイスとみなされ、ボリューム変更やルーティング情報は通常のALSA kcontrolsを通じて提供されます。

  • 埋め込まれたオーディオ効果。入力がPCMまたは圧縮データであれ、同じように有効化する必要があります。

  • マルチチャネルIECエンコーディング。この要求が必須かどうかは不明です。

  • エンコーディング/デコーディングの加速は上記のようにサポートされません。デコーダーの出力をキャプチャストリームにルーティングするか、さらには変換処理の実装も可能です。このルーティングはALSA kcontrolsを通じて有効化されます。

  • オーディオポリシー/リソース管理。このAPIはオーディオDSPの利用状況を照会するためのハックや、プリエンプションメカニズムの提供を行いません。

  • アンダーラン/オーバーランの概念はありません。書き込まれるバイトが圧縮された性質を持ち、書き込まれた/読み取られたデータが時間的にレンダリングされた出力と直接関係しないため、このAPIはアンダーラン/オーバーランを扱わず、ユーザーのライブラリで処理される可能性があります。

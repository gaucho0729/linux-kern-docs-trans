ALSADriverの作成¶

著者

Takashi Iwai <tiwai@suse.de>

はじめに¶

このドキュメントは、以下を説明しています。 ALSA (Advanced Linux Sound Architecture) ドライバの作成方法を説明しています。このドキュメントは主にPCIサウンドカードに焦点を当てています。他のデバイスタイプの場合、APIが異なる可能性もあります。しかし、少なくともALSAカーネルAPIは一貫しており、そのため他のデバイスドライバの作成にもある程度役立ちます。

このドキュメントは、C言語のスキルがあり、Linuxカーネルプログラミングの基礎知識がある人を対象としています。このドキュメントはLinuxカーネルコーディングの一般的なトピックを説明しておらず、低レベルドライバの実装詳細についてはカバーしていません。ALSA上でのPCIサウンドドライバの標準的な作成方法のみを説明しています。

このドキュメントはまだドラフト版です。フィードバックや修正、お待ちしています！

coreディレクトリ¶

このディレクトリには、ALSAドライバの心臓となる中間レイヤーが含まれています。このディレクトリにはネイティブなALSAモジュールが格納されており、サブディレクトリには異なるモジュールが含まれており、カーネル構成に依存しています。

core/oss¶

PCMおよびミキサーOSSエミュレーションモジュールのコードがこのディレクトリに格納されています。rawmidi OSSエミュレーションはALSA rawmidiコードに含まれており、それほど小さいためです。シーケンサーのコードは core/seq/oss ディレクトリ（参照 に記載されています。).

core/seq¶

このディレクトリとそのサブディレクトリはALSAシーケンサー用です。このディレクトリにはシーケンサーのコアと主なシーケンサーモジュール（例：snd-seq-midi、snd-seq-virmidiなど）が含まれています。これらは、カーネル構成で CONFIG_SND_SEQUENCER が設定されている場合にのみコンパイルされます。

core/seq/oss¶

これはOSSシーケンサーエミュレーションコードを含んでいます。

includeディレクトリ¶

これはALSAドライバのパブリックヘッダーファイルの場所で、ユーザー空間にエクスポートされるか、複数のディレクトリからインクルードされるファイルです。基本的にプライベートヘッダーファイルはこのディレクトリに置かないべきですが、歴史的な理由によりここにファイルが見られることがあります：)

driversディレクトリ¶

このディレクトリには、異なるアーキテクチャの異なるドライバで共有されるコードが含まれています。そのため、アーキテクチャ固有のものではありません。例えば、ダミーPCMドライバとシリアルMIDIドライバはこのディレクトリにあります。サブディレクトリにはバスやCPUアーキテクチャに依存しないコンポーネントのコードが含まれています。

drivers/mpu401¶

MPU401およびMPU401-UARTモジュールがここに格納されています。

drivers/opl3 and opl4¶

OPL3およびOPL4 FMシンセの情報がここにあります。

i2cディレクトリ¶

これはALSA i2cコンポーネントを含んでいます。

Linuxには標準的なi2cレイヤーが存在しますが、ALSAは一部のサウンドカード用に独自のi2cコードを持っています。これは、サウンドカードが単純な操作で済むため、標準的なi2c APIはこのような用途には複雑すぎるからです。

synth directory¶

これはシンセの中間レベルのモジュールを含んでいます。

現在、以下のサブディレクトリにはEmu8000/Emu10k1のシンセドライバーのみが存在しています。 synth/emux sub-directory.

pci directory¶

このディレクトリおよびそのサブディレクトリは、PCIサウンドカード用のトップレベルのカードモジュールと、PCIバス固有のコードを保持しています。

単一ファイルからコンパイルされたドライバーはpciディレクトリ内に直接格納され、複数のソースファイルを持つドライバーはそれぞれのサブディレクトリに格納されます（例: emu10k1、ice1712）。

isa directory¶

このディレクトリおよびそのサブディレクトリは、ISAサウンドカード用のトップレベルのカードモジュールを保持しています。

arm, ppc, and sparc directories¶

これらは、これらのアーキテクチャに特化したトップレベルのカードモジュールに使用されます。

usb directory¶

このディレクトリにはUSBオーディオドライバーが含まれています。最新版では、USB MIDIドライバーがUSBオーディオドライバーに統合されています。

pcmcia directory¶

PCMCIA、特にPCCardドライバーはここに配置されます。CardBusドライバーはpciディレクトリに配置されます。なぜなら、そのAPIが標準的なPCIカードと同一だからです。

soc directory¶

このディレクトリにはASoC（ALSA System on Chip）レイヤーのコードが含まれています。ASoCコア、コーデック、マシンドライバーなどが含まれます。

oss directory¶

ここにはOSS/Liteのコードが含まれています。本書執筆時点では、m68k向けのdmasoundを除き、すべてのコードは非推奨となっています。

PCIドライバの基本フロー¶

Outline¶

PCIサウンドカードの最小フローは以下の通りです：

  • PCI IDテーブルを定義します（セクション PCI Entries).

  • create probe そのコールバックは、指定されたポリシーに属するすべてのオンラインCPUに対して、CPUスケジューラにパーセルCPUの利用率更新コールバックを登録する必要があります。

  • create remove そのコールバックは、指定されたポリシーに属するすべてのオンラインCPUに対して、CPUスケジューラにパーセルCPUの利用率更新コールバックを登録する必要があります。

  • を struct pci_driver 構造体を作成します。この構造体には上記の3つのポインタが含まれます。

  • 作成します init 関数は単に以下の pci_register_driver() を呼び出して、上記で定義したpci_driverテーブルを登録します。

  • 作成します exit 関数は以下の pci_unregister_driver() function.

/* constructor -- see "Driver Constructor" sub-section */
static int snd_mychip_probe(struct pci_dev *pci,
                            const struct pci_device_id *pci_id)
{
        static int dev;
        struct snd_card *card;
        struct mychip *chip;
        int err;

        /* (1) */
        if (dev >= SNDRV_CARDS)
                return -ENODEV;
        if (!enable[dev]) {
                dev++;
                return -ENOENT;
        }

        /* (2) */
        err = snd_card_new(&pci->dev, index[dev], id[dev], THIS_MODULE,
                           0, &card);
        if (err < 0)
                return err;

        /* (3) */
        err = snd_mychip_create(card, pci, &chip);
        if (err < 0)
                goto error;

        /* (4) */
        strcpy(card->driver, "My Chip");
        strcpy(card->shortname, "My Own Chip 123");
        sprintf(card->longname, "%s at 0x%lx irq %i",
                card->shortname, chip->port, chip->irq);

        /* (5) */
        .... /* implemented later */

        /* (6) */
        err = snd_card_register(card);
        if (err < 0)
                goto error;

        /* (7) */
        pci_set_drvdata(pci, card);
        dev++;
        return 0;

error:
        snd_card_free(card);
        return err;
}

/* destructor -- see the "Destructor" sub-section */
static void snd_mychip_remove(struct pci_dev *pci)
{
        snd_card_free(pci_get_drvdata(pci));
}

Driver Constructor¶

PCIドライバの実際のコンストラクタは以下の probe コールバックの直後に呼び出されます。The probe コールバックとその他のコンポーネントコンストラクタで、以下の probe コールバックは以下の __init プレフィックスを使用できません。なぜなら、どのPCIデバイスもホットプラグデバイスである可能性があるからです。

～において、クエリは probe コールバックでは、以下のスキームがよく使われます。

1) デバイスインデックスを確認し、インクリメントします。¶

static int dev;
....
if (dev >= SNDRV_CARDS)
        return -ENODEV;
if (!enable[dev]) {
        dev++;
        return -ENOENT;
}

オプションを指定する必要があります。形式は以下の通りです： enable[dev] はモジュールオプションです。

Each time the probe callback is called, check the availability of the device. If not available, simply increment the device index and returns. dev will be incremented also later (step 7).

2) Create a card instance¶

struct snd_card *card;
int err;
....
err = snd_card_new(&pci->dev, index[dev], id[dev], THIS_MODULE,
                   0, &card);

The details will be explained in the section カードおよびコンポーネントの管理.

3) Create a main component¶

In this part, the PCI resources are allocated.

struct mychip *chip;
....
err = snd_mychip_create(card, pci, &chip);
if (err < 0)
        goto error;

The details will be explained in the section PCIリソース管理.

When something goes wrong, the probe function needs to deal with the error. In this example, we have a single error handling path placed at the end of the function.

error:
        snd_card_free(card);
        return err;

Since each component can be properly freed, the single snd_card_free() call should suffice in most cases.

4) Set the driver ID and name strings.¶

strcpy(card->driver, "My Chip");
strcpy(card->shortname, "My Own Chip 123");
sprintf(card->longname, "%s at 0x%lx irq %i",
        card->shortname, chip->port, chip->irq);

The driver field holds the minimal ID string of the chip. This is used by alsa-lib’s configurator, so keep it simple but unique. Even the same driver can have different driver IDs to distinguish the functionality of each chip type.

The shortname field is a string shown as more verbose name. The longname field contains the information shown in /proc/asound/cards.

5) Create other components, such as mixer, MIDI, etc.¶

Here you define the basic components such as PCM, mixer (e.g. AC97), MIDI (e.g. MPU-401), and other interfaces. Also, if you want a proc file, define it here, too.

6) Register the card instance.¶

err = snd_card_register(card);
if (err < 0)
        goto error;

Will be explained in the section カードおよびコンポーネントの管理, too.

7) Set the PCI driver data and return zero.¶

pci_set_drvdata(pci, card);
dev++;
return 0;

In the above, the card record is stored. This pointer is used in the remove callback and power-management callbacks, too.

Destructor¶

The destructor, remove callback, simply releases the card instance. Then the ALSA middle layer will release all the attached components automatically.

It would be typically just calling snd_card_free():

static void snd_mychip_remove(struct pci_dev *pci)
{
        snd_card_free(pci_get_drvdata(pci));
}

The above code assumes that the card pointer is set to the PCI driver data.

Header Files¶

For the above example, at least the following include files are necessary.

#include <linux/init.h>
#include <linux/pci.h>
#include <linux/slab.h>
#include <sound/core.h>
#include <sound/initval.h>

where the last one is necessary only when module options are defined in the source file. If the code is split into several files, the files without module options don’t need them.

In addition to these headers, you’ll need <linux/interrupt.h> for interrupt handling, and <linux/io.h> for I/O access. If you use the mdelay() または udelay() functions, you’ll need to include <linux/delay.h> too.

The ALSA interfaces like the PCM and control APIs are defined in other <sound/xxx.h> header files. They have to be included after <sound/core.h>.

カードおよびコンポーネントの管理¶

カードインスタンス¶

各サウンドカードに対して、「カード」レコードを割り当てる必要があります。

カードレコードはサウンドカードの本部であり、PCM、ミキサー、MIDI、シンセサイザーなどのサウンドカード上のすべてのデバイス（コンポーネント）のリストを管理します。また、カードレコードはカードのIDと名前文字列を保持し、プロセスファイルのルートを管理し、電源管理状態とホットプラグ切断を制御します。カードレコード上のコンポーネントリストは、破棄時にリソースを正しく解放するために使用されます。

上記のように、カードインスタンスを作成するには、以下のように呼び出します。 snd_card_new().

struct snd_card *card;
int err;
err = snd_card_new(&pci->dev, index, id, module, extra_size, &card);

この関数は6つの引数を取ります：親デバイスポインタ、カードインデックス番号、ID文字列、モジュールポインタ（通常 THIS_MODULE）、追加データ領域のサイズ、およびカードインスタンスを返すポインタ。extra_size引数は、チップ固有データ用のcard->private_dataを割り当てるために使用されます。注意点として、これらのデータは snd_card_new().

によって割り当てられます。 struct device最初の引数である &pci-> ポインタは親デバイスを指定します。PCIデバイスの場合、通常

コンポーネント

カードが作成された後、コンポーネント（デバイス）をカードインスタンスにアタッチできます。ALSAドライバでは、コンポーネントはstruct snd_deviceオブジェクトとして表されます。コンポーネントはPCMインスタンス、コントロールインターフェース、RAW MIDIインターフェースなどです。このような各インスタンスには1つのコンポーネントエントリがあります。 snd_device_new() function.

snd_device_new(card, SNDRV_DEV_XXX, chip, &ops);

コンポーネントはSNDRV_DEV_XXXを介して作成できます。これはカードポインタ、デバイスレベル（&ops）、データポインタ、およびコールバックポインタ（ SNDRV_DEV_LOWLEVEL.

）を取ります。デバイスレベルはコンポーネントの種類と登録・解除の順序を定義します。ほとんどのコンポーネントではデバイスレベルはすでに定義されています。ユーザー定義のコンポーネントの場合は、chip を使用できます。この関数自体はデータ領域を割り当てません。データは事前に手動で割り当てられ、そのポインタが引数として渡されます。このポインタ（上記の例では

）はインスタンスの識別子として使用されます。 snd_device_new() 事前に定義されたALSAコンポーネント（例：ac97やpcm）は自身のコンストラクタ内で

を呼び出します。各コンポーネントのデストラクタはコールバックポインタで定義されるため、このようなコンポーネントのデストラクタを呼び出す必要はありません。 ops独自のコンポーネントを作成する場合は、 snd_card_free()のdev_freeコールバックにデストラクタ関数を設定する必要があります。これにより、自動的に解放されます。次の例ではチップ固有データの実装を示します。

チップ固有データ¶

チップ固有情報（例：I/Oポートアドレス、そのリソースポインタ、またはIRQ番号など）はチップ固有レコードに保存されます。

struct mychip {
        ....
};

一般的に、チップ記録の割り当て方法は2つの方法があります。

1. 割り当ては以下の通りです。 snd_card_new().¶

上記のように、extra-data-lengthを5番目の引数に渡すことができます。 snd_card_new(), i.e.

err = snd_card_new(&pci->dev, index[dev], id[dev], THIS_MODULE,
                   sizeof(struct mychip), &card);

struct mychipはチップ記録の型です。

その代わりに、割り当てられた記録は以下のようにアクセスできます。

struct mychip *chip = card->private_data;

この方法では、2回割り当てることはありません。記録はカードインスタンスとともに解放されます。

2. 追加のデバイスを割り当てます。¶

カードインスタンスを割り当てた後、以下のようにします。 snd_card_new() (with 0 4番目の引数で kzalloc().

struct snd_card *card;
struct mychip *chip;
err = snd_card_new(&pci->dev, index[dev], id[dev], THIS_MODULE,
                   0, &card);
.....
chip = kzalloc(sizeof(*chip), GFP_KERNEL);

チップ記録には少なくともカードポインタを保持するフィールドが必要です。

struct mychip {
        struct snd_card *card;
        ....
};

次に、返されたチップインスタンスにカードポインタを設定します。

chip->card = card;

次に、フィールドを初期化し、指定されたデバイスデストラクタ関数とともにこのチップ記録を低レベルデバイスとして登録します。 ops,

static const struct snd_device_ops ops = {
        .dev_free =        snd_mychip_dev_free,
};
....
snd_device_new(card, SNDRV_DEV_LOWLEVEL, chip, &ops);

snd_mychip_dev_free() はデバイスデストラクタ関数であり、実際のデストラクタを呼び出します。

static int snd_mychip_dev_free(struct snd_device *device)
{
        return snd_mychip_free(device->device_data);
}

オプションを指定する必要があります。形式は以下の通りです： snd_mychip_free() は実際のデストラクタです。

この方法の欠点はコード量が明らかに多いことです。ただし、利点はsnd_device_opsの設定を通じてカードの登録と切断時に独自のコールバックをトリガーできる点です。カードの登録と切断については、以下のサブセクションを参照してください。

登録と解放¶

すべてのコンポーネントが割り当てられた後、以下のようにカードインスタンスを登録します。 snd_card_register(). この時点でデバイスファイルへのアクセスが有効になります。つまり、 snd_card_register() が呼ばれる前には、コンポーネントは外部から安全にアクセスできません。この呼び出しが失敗した場合、カードを解放した後、probe関数を終了してください。 snd_card_free().

カードインスタンスを解放するには、単に以下のように呼び出してください。 snd_card_free(). 前述のように、すべてのコンポーネントはこの呼び出しで自動的に解放されます。

ホットプラグ可能なデバイスの場合、以下のように使用できます。 snd_card_free_when_closed(). これはすべてのデバイスが閉じるまで破壊を延期します。

PCIリソース管理¶

Full Code Example¶

このセクションでは、チップ固有のコンストラクタ、デストラクタ、PCIエントリを完了します。以下に例コードを示します。

struct mychip {
        struct snd_card *card;
        struct pci_dev *pci;

        unsigned long port;
        int irq;
};

static int snd_mychip_free(struct mychip *chip)
{
        /* disable hardware here if any */
        .... /* (not implemented in this document) */

        /* release the irq */
        if (chip->irq >= 0)
                free_irq(chip->irq, chip);
        /* release the I/O ports & memory */
        pci_release_regions(chip->pci);
        /* disable the PCI entry */
        pci_disable_device(chip->pci);
        /* release the data */
        kfree(chip);
        return 0;
}

/* chip-specific constructor */
static int snd_mychip_create(struct snd_card *card,
                             struct pci_dev *pci,
                             struct mychip **rchip)
{
        struct mychip *chip;
        int err;
        static const struct snd_device_ops ops = {
               .dev_free = snd_mychip_dev_free,
        };

        *rchip = NULL;

        /* initialize the PCI entry */
        err = pci_enable_device(pci);
        if (err < 0)
                return err;
        /* check PCI availability (28bit DMA) */
        if (pci_set_dma_mask(pci, DMA_BIT_MASK(28)) < 0 ||
            pci_set_consistent_dma_mask(pci, DMA_BIT_MASK(28)) < 0) {
                printk(KERN_ERR "error to set 28bit mask DMA\n");
                pci_disable_device(pci);
                return -ENXIO;
        }

        chip = kzalloc(sizeof(*chip), GFP_KERNEL);
        if (chip == NULL) {
                pci_disable_device(pci);
                return -ENOMEM;
        }

        /* initialize the stuff */
        chip->card = card;
        chip->pci = pci;
        chip->irq = -1;

        /* (1) PCI resource allocation */
        err = pci_request_regions(pci, "My Chip");
        if (err < 0) {
                kfree(chip);
                pci_disable_device(pci);
                return err;
        }
        chip->port = pci_resource_start(pci, 0);
        if (request_irq(pci->irq, snd_mychip_interrupt,
                        IRQF_SHARED, KBUILD_MODNAME, chip)) {
                printk(KERN_ERR "cannot grab irq %d\n", pci->irq);
                snd_mychip_free(chip);
                return -EBUSY;
        }
        chip->irq = pci->irq;
        card->sync_irq = chip->irq;

        /* (2) initialization of the chip hardware */

リソース割り当て¶

I/OポートとIRQの割り当ては標準のカーネル関数を通じて行われます。これらのリソースはデストラクタ関数で解放する必要があります（以下参照）。

PCIデバイスが8バイトのI/Oポートと割込みを持つと仮定します。この場合、struct mychipには以下のフィールドがあります：

struct mychip {
        struct snd_card *card;

        unsigned long port;
        int irq;
};

I/Oポート（およびメモリ領域）を割り当てるには、標準のリソース管理用のリソースポインタが必要です。割り込み（irq）については、irq番号（整数）のみを保持すればよいですが、実際の割り当て前にこの番号を-1に初期化する必要があります。なぜなら、irq 0は有効な値だからです。ポートアドレスとそのリソースポインタは、 kzalloc() 自動的に初期化されるため、手動でリセットする必要はありません。

I/Oポートの割り当ては以下のようになります：

err = pci_request_regions(pci, "My Chip");
if (err < 0) {
        kfree(chip);
        pci_disable_device(pci);
        return err;
}
chip->port = pci_resource_start(pci, 0);

指定されたPCIデバイスのI/Oポート領域8バイトを予約します。返却値、 chip->res_portは kmalloc() によって request_region()経由して割り当てられます。ポインタは kfree()経由して解放する必要がありますが、この方法には問題があります。この問題については後述します。

割り込みソースの割り当ては以下のようになります：

if (request_irq(pci->irq, snd_mychip_interrupt,
                IRQF_SHARED, KBUILD_MODNAME, chip)) {
        printk(KERN_ERR "cannot grab irq %d\n", pci->irq);
        snd_mychip_free(chip);
        return -EBUSY;
}
chip->irq = pci->irq;

オプションを指定する必要があります。形式は以下の通りです： snd_mychip_interrupt() は割り込みハンドラが 後述するように定義されています。。注意： chip->irq は、 request_irq() 成功しました。

が条件を満たす場合にのみ定義されるべきです。 IRQF_SHARED PCIバスでは割り込みが共有可能なので、 request_irq().

は request_irq() の割り込みフラグとして使用されます。

の最後の引数は、割り込みハンドラに渡されるデータポインタです。通常はチップ固有のレコードが使用されますが、好きなものでも構いません。

static irqreturn_t snd_mychip_interrupt(int irq, void *dev_id)
{
        struct mychip *chip = dev_id;
        ....
        return IRQ_HANDLED;
}

割り込みをリクエストした後、それを card->sync_irq フィールドに渡すことができます：

card->irq = chip->irq;

これにより、PCMコアが synchronize_irq() の必要タイミングで自動的に実行されます。詳しくは後述の hw_freesync_stopコールバック セクションを参照してください。 詳しくは以下をご参照ください。

以上で述べたリソースに対応するデストラクタを記述しましょう。デストラクタの役割は単純で、ハードウェアを無効化（すでに有効化されている場合）し、リソースを解放することです。これまでハードウェア部分は存在しなかったため、無効化コードはここには記述されていません。

リソースを解放するには、「チェックして解放」する方法がより安全です。割り込みについては以下のようにします：

if (chip->irq >= 0)
        free_irq(chip->irq, chip);

irq番号は0から始まるため、 chip->irq に負の値（例：-1）を初期化しておく必要があります。これにより、上で述べたirq番号の有効性を確認できます。

I/Oポートやメモリ領域を pci_request_region() または pci_request_regions() 経由してリクエストした場合、この例のように、対応する関数 pci_release_region() または pci_release_regions().

pci_release_regions(chip->pci);

経由してリソース（複数可）を解放します。 request_region() または request_mem_region()を手動でリクエストした場合、 release_resource()経由して解放できます。仮に request_region() から返却されたリソースポインタをchip->res_portに保持しているとすれば、解放手順は以下のようになります：

release_and_free_resource(chip->res_port);

終了前に必ず pci_disable_device() を呼び出してください。

最後に、チップ固有のレコードを解放してください。

kfree(chip);

上記ではハードウェアの無効化処理を実装していません。必要とされる場合は、チップの初期化が完了する前でもデストラクタが呼び出される可能性があるため、ハードウェアが初期化されていない場合にハードウェアの無効化をスキップするフラグを設けるのが望ましいです。

チップデータをカードに割り当てて使用する際 snd_device_new() with SNDRV_DEV_LOWLELVEL 、そのデストラクタは最後に呼び出されます。つまり、PCMsやコントロールなどの他のコンポーネントがすでに解放されていることを保証されています。PCMsなどは明示的に停止する必要はなく、低レベルのハードウェア停止処理を呼び出すだけでよいです。

メモリマッピング領域の管理はI/Oポートの管理とほぼ同じです。以下の3つのフィールドが必要です。

struct mychip {
        ....
        unsigned long iobase_phys;
        void __iomem *iobase_virt;
};

、割り当て方は以下のようにします。

err = pci_request_regions(pci, "My Chip");
if (err < 0) {
        kfree(chip);
        return err;
}
chip->iobase_phys = pci_resource_start(pci, 0);
chip->iobase_virt = ioremap(chip->iobase_phys,
                                    pci_resource_len(pci, 0));

、対応するデストラクタは以下のようになります。

static int snd_mychip_free(struct mychip *chip)
{
        ....
        if (chip->iobase_virt)
                iounmap(chip->iobase_virt);
        ....
        pci_release_regions(chip->pci);
        ....
}

もちろん、現代的な方法として pci_iomap() を使用すると、少し手間が省けます。

err = pci_request_regions(pci, "My Chip");
if (err < 0) {
        kfree(chip);
        return err;
}
chip->iobase_virt = pci_iomap(pci, 0, 0);

これはデストラクタでペアリングされます。 pci_iounmap() デストラクタでペアリングされます。

PCMインターフェース¶

一般¶

ALSAのPCMの中間レイヤーは非常に強力で、各ドライバは自身のハードウェアにアクセスするための低レベル関数を実装するだけで十分です。

PCMレイヤーにアクセスするには、まず <sound/pcm.h> をインクルードする必要があります。さらに、 <sound/pcm_params.h> hw_paramに関連する関数にアクセスする場合、これが必要となるかもしれません。

各カードデバイスは最大4つのPCMインスタンスを持つことができます。PCMインスタンスはPCMデバイスファイルに対応します。インスタンス数の制限はLinuxのデバイス番号のビットサイズに依存します。64ビットのデバイス番号が使用されると、より多くのPCMインスタンスが利用可能になります。

pcmインスタンスはpcm再生ストリームとキャプチャストリームから構成され、それぞれのpcmストリームは1つ以上のpcmサブストリームからなります。一部のサウンドカードは複数の再生機能をサポートしています。例えば、emu10k1は32つのステレオサブストリームを持つpcm再生を備えています。このような場合、各オープン時に空きサブストリームが（通常）自動的に選択され開かれます。一方、1つのサブストリームしか存在せずすでにオープンされている場合、成功したオープンはファイルオープンモードに応じてブロックするかエラーを返します。 EAGAIN ただし、ドライバではこのような詳細を気にする必要はありません。pcmの中間レイヤーがこのような作業を担当します。

PCMコンストラクタ¶

pcmインスタンスは snd_pcm_new() 関数によって割り当てられます。pcmのコンストラクタとして、

static int snd_mychip_new_pcm(struct mychip *chip)
{
        struct snd_pcm *pcm;
        int err;

        err = snd_pcm_new(chip->card, "My Chip", 0, 1, 1, &pcm);
        if (err < 0)
                return err;
        pcm->private_data = chip;
        strcpy(pcm->name, "My Chip");
        chip->pcm = pcm;
        ....
        return 0;
}

以下の snd_pcm_new() 関数は4つの引数を取ります。最初の引数はこのpcmが割り当てられたカードポインタで、2番目はID文字列です。

3番目の引数（index、上記では0）はこの新しいpcmのインデックスです。ゼロから始まります。複数のpcmインスタンスを生成する場合、この引数で異なる番号を指定します。例えば、 index = 1 は2番目のpcmデバイスを表します。

4番目と5番目の引数は再生と録音用のサブストリーム数をそれぞれ指定します。ここでは両方とも1が使用されます。再生または録音用のサブストリームが利用できない場合は、対応する引数に0を指定します。

チップが複数の再生または録音をサポートする場合、より多くの数値を指定できますが、オープン/クローズなどコールバック処理で適切に処理する必要があります。どのサブストリームを参照しているかを知る必要がある場合は、各コールバックに渡されるstruct snd_pcm_substreamデータから取得できます。

struct snd_pcm_substream *substream;
int index = substream->number;

pcmが作成された後、各pcmストリームにオペレータを設定する必要があります。

snd_pcm_set_ops(pcm, SNDRV_PCM_STREAM_PLAYBACK,
                &snd_mychip_playback_ops);
snd_pcm_set_ops(pcm, SNDRV_PCM_STREAM_CAPTURE,
                &snd_mychip_capture_ops);

オペレータは通常次のように定義されます：

static struct snd_pcm_ops snd_mychip_playback_ops = {
        .open =        snd_mychip_pcm_open,
        .close =       snd_mychip_pcm_close,
        .hw_params =   snd_mychip_pcm_hw_params,
        .hw_free =     snd_mychip_pcm_hw_free,
        .prepare =     snd_mychip_pcm_prepare,
        .trigger =     snd_mychip_pcm_trigger,
        .pointer =     snd_mychip_pcm_pointer,
};

すべてのコールバックは 演算子 サブセクションで説明されています。

オペレータを設定した後、バッファを事前に割り当てて管理された割当モードを設定したい場合、次の関数を呼び出します：

snd_pcm_set_managed_buffer_all(pcm, SNDRV_DMA_TYPE_DEV,
                               &chip->pci->dev,
                               64*1024, 64*1024);

これにより、デフォルトでは64kBまでのバッファが割り当てられます。バッファ管理の詳細は後述のセクションで説明します。 バッファとメモリ管理.

さらに、このpcmに追加情報を設定することもできます： pcm->info_flags。利用可能な値は SNDRV_PCM_INFO_XXX の <sound/asound.h>で定義されており、ハードウェア定義（後述）に使用されます。サウンドチップが半二重通信のみをサポートする場合、次のように指定します：

pcm->info_flags = SNDRV_PCM_INFO_HALF_DUPLEX;

pcmサブストリームがオープンされるとき、pcmランタイムインスタンスが割り当てられ、サブストリームに割り当てられます。このポインタは substream->runtime経由してアクセス可能です。このランタイムポインタは、pcmを制御するために必要なほとんどの情報を保持しています。hw_paramsとsw_paramsの設定のコピー、バッファポインタ、mmapレコード、スピノックロックなどです。

ハードウェアの説明¶

ハードウェアディスクリプタ（struct snd_pcm_hardware）には、基本的なハードウェア構成の定義が含まれています。最も重要に、これを PCMオープンコールバックで定義する必要があります。注意点として、ランタイムインスタンスはディスクリプタのコピーを保持しており、既存のディスクリプタへのポインタではありません。つまり、オープンコールバックでは必要に応じてコピーされたディスクリプタ（runtime->hw）を変更できます。例えば、一部のチップモデルでは最大チャンネル数が1のみの場合でも、同じハードウェアディスクリプタを使用し、後でchannels_maxを変更できます：

struct snd_pcm_runtime *runtime = substream->runtime;
...
runtime->hw = snd_mychip_playback_hw; /* common definition */
if (chip->model == VERY_OLD_ONE)
        runtime->hw.channels_max = 1;

通常、ハードウェアディスクリプタは以下のようになります：

static struct snd_pcm_hardware snd_mychip_playback_hw = {
        .info = (SNDRV_PCM_INFO_MMAP |
                 SNDRV_PCM_INFO_INTERLEAVED |
                 SNDRV_PCM_INFO_BLOCK_TRANSFER |
                 SNDRV_PCM_INFO_MMAP_VALID),
        .formats =          SNDRV_PCM_FMTBIT_S16_LE,
        .rates =            SNDRV_PCM_RATE_8000_48000,
        .rate_min =         8000,
        .rate_max =         48000,
        .channels_min =     2,
        .channels_max =     2,
        .buffer_bytes_max = 32768,
        .period_bytes_min = 4096,
        .period_bytes_max = 32768,
        .periods_min =      1,
        .periods_max =      1024,
};

  • 以下の info フィールドにはこのpcmのタイプと機能が含まれます。ビットフラグは <sound/asound.h> as SNDRV_PCM_INFO_XXXで定義されています。ここでは、少なくともmmapがサポートされているか、どのインターレーブ形式がサポートされているかを指定する必要があります。ハードウェアがmmapをサポートする場合、ここに SNDRV_PCM_INFO_MMAP フラグを追加してください。ハードウェアがインターレーブ形式またはノンインターレーブ形式をサポートする場合、それぞれ SNDRV_PCM_INFO_INTERLEAVED または SNDRV_PCM_INFO_NONINTERLEAVED フラグを設定する必要があります。両方をサポートする場合は、両方を設定することも可能です。

    上記の例では、 MMAP_VALID および BLOCK_TRANSFER がOSS mmapモードで指定されています。通常は両方設定されています。もちろん、 MMAP_VALID はmmapが実際にサポートされている場合にのみ設定されます。

    他の可能なフラグは SNDRV_PCM_INFO_PAUSE および SNDRV_PCM_INFO_RESUMEの部分で、 PAUSE ビットはpcmが「一時停止」操作をサポートすることを意味し、 RESUME ビットはpcmが「一時停止/再開」操作を完全にサポートすることを意味します。もし PAUSE フラグが設定されている場合、 trigger 以下のコールバックは対応する（一時停止プッシュ/リリース）コマンットを処理する必要があります。一時停止/再開トリガー コマンドは、フラグが設定されていない場合でも定義できます。See RESUME 以下のコールバックは対応する（一時停止プッシュ/リリース）コマンドを処理する必要があります。一時停止/再開トリガー コマンドは、フラグが設定されていない場合でも定義できます。See 電源管理 セクションをご参照ください。

    PCMサブストリームが同期可能である場合（通常は再生とキャプチャストリームの同期した開始/停止）、 SNDRV_PCM_INFO_SYNC_STARTこれも可能です。この場合、トリガー コールバックでPCMサブストリームのリンクリストを確認する必要があります。これは後述のセクションで説明します。

  • formats フィールドにはサポートされている形式のビットフラグ（SNDRV_PCM_FMTBIT_XXX）を含みます。ハードウェアが複数の形式をサポートする場合、すべてのビットをORで指定してください。上の例では符号付き16bit little-endian形式が指定されています。

  • rates フィールドにはサポートされているサンプリング周波数のビットフラグ（SNDRV_PCM_RATE_XXX）を含みます。チップが連続周波数をサポートする場合、 CONTINUOUS ビットを追加で指定してください。事前に定義された周波数ビットは典型的な周波数に限定されています。チップが非標準的な周波数をサポートする場合、 KNOT ビットを追加し、ハードウェア制約を手動で設定する必要があります（後述します）。

  • rate_min および rate_max 最小と最大のサンプリング周波数を定義します。これはある程度 rates ビットと対応する必要があります。

  • channel_min および channel_max 最小と最大のチャンネル数を定義します。これはすでに予想していた通りです。

  • buffer_bytes_max バッファの最大サイズ（バイト単位）を定義します。最小ピリオドサイズと最小ピリオド数から計算できるため、 buffer_bytes_min フィールドは存在しません。一方で、 period_bytes_min とがピリオドの最小と最大サイズ（バイト単位）を定義します。 periods_max および periods_min バッファ内のピリオドの最大と最小数を定義します。

    「ピリオド」はOSS世界における「フラグメント」に該当します。ピリオドはPCM割込みが発生するサイズを定義します。このサイズはハードウェアに強く依存します。一般的に、ピリオドサイズが小さいほど割込みが増えて、制御が細かくなります。キャプチャの場合、このサイズは入力遅延を定義します。一方、バッファ全体のサイズは再生方向の出力遅延を定義します。

  • また、 fifo_sizeフィールドもあります。これはハードウェアFIFOのサイズを指定しますが、現在のドライバやalsa-libでは使用されていません。そのため、このフィールドは無視できます。

PCM設定¶

では、PCMランタイムレコードに戻ります。ランタイムインスタンスで最もよく参照されるレコードはPCM設定です。PCM設定はアプリケーションがalsa-lib経由でデータを送信した後、ランタイムインスタンスに保存されます。多くのフィールドはhw_paramsとsw_params構造体からコピーされています。例えば、 hw_params はアプリケーションが選択した形式タイプを保持します。このフィールドには format のenum値を含みます SNDRV_PCM_FORMAT_XXX.

注意すべき点は、設定されたバッファおよび周期サイズが実行時において「フレーム（frames）」として保存されていることです。ALSAの世界では、 1 frame = channels \* samples-sizeフレームとバイトの変換には、以下のヘルパ関数を使用できます。 frames_to_bytes() および bytes_to_frames() helper functions.

period_bytes = frames_to_bytes(runtime, runtime->period_size);

また、多くのソフトウェアパラメータ（sw_params）もフレームとして保存されています。フィールドの型を確認してください。 snd_pcm_uframes_t はフレームを符号なし整数として扱い、 snd_pcm_sframes_t はフレームを符号付き整数として扱います。

アトミック性¶

カーネルプログラミングにおいて最も重要（そしてデバッグが難しい）な問題の一つがレースコンディションです。Linuxカーネルでは、通常スピンロック、ミューテックス、セマフォラを用いてこれを回避します。一般的に、割込みハンドラ内でレースコンディションが発生する場合、原子的（atomic）に処理する必要があります。この場合、クリティカルセクションを保護するためにスピンロックを使用する必要があります。クリティカルセクションが割込みハンドラコード内にない場合、かつ実行に相応に時間がかかることが許容される場合は、ミューテックスまたはセマフォラを使用するべきです。

すでに見たように、一部のpcmコールバックは原子的で、一部はそうではありません。例えば、 hw_params コールバックは非原子的ですが、 trigger コールバックは原子的です。これは、後者はPCMの中間レイヤーが保持するスピンロックの中ですでに呼び出されていることを意味します。コールバックでロックスキーマを選択する際には、この原子性を考慮してください。

原子的なコールバックでは、 schedule() を呼び出す可能性のある関数や、 sleep()に移動する関数を使用することはできません。セマフォやミューテックスはスリープすることが可能であり、そのため原子的なコールバック内では使用できません（例： trigger コールバック）。このようなコールバック内で遅延を実装する場合は、 udelay() または mdelay().

を用いてください。すべての原子的なコールバック（トリガー、ポインタ、ACK）はローカル割込みが無効になっている状態で呼び出されます。

最近のPCMコアコードの変更により、すべてのPCM操作が非原子的になることが可能になりました。これはすべての呼び出し側が非原子的コンテキストにあることを前提としています。例えば、関数 snd_pcm_period_elapsed() は通常割込みハンドラから呼ばれます。しかし、ドライバをスレッド型割込みハンドラを使用するように設定した場合、この呼び出しも非原子的コンテキストになることがあります。このような場合、 nonatomic 構造体snd_pcmオブジェクトを生成後にこのフラグを設定できます。このフラグが設定されている場合、PCMコア内部ではスピンロックやrwロックではなくミューテックスとrwセマフォを用いるため、非原子的コンテキストでもすべてのPCM関数を安全に呼び出すことができます。

                ch.min = ch.max = 1;
                ch.integer = 1;
                return snd_interval_refine(c, &ch);
        }
        return 0;
}

コントロールインターフェース¶

一般¶

コントロールインターフェースは、ユーザー空間からアクセスされるスイッチやスライダーなど多くの用途に広く使用されています。最も重要な用途はミキサーインターフェースです。言い換えれば、ALSA 0.9.x以降、すべてのミキサー機能はコントロールカーネルAPIで実装されています。

ALSAには明確に定義されたAC97コントロールモジュールがあります。チップがAC97のみをサポートし、他の機能は持たない場合であれば、このセクションはスキップできます。

コントロールAPIは <sound/control.h>に定義されています。自分のコントロールを追加したい場合は、このファイルをインクルードしてください。

コントロールの定義¶

新しいコントロールを作成するには、以下の3つのコールバックを定義する必要があります: info, get および put。次に、struct snd_kcontrol_newレコードを定義します、例えば:

static struct snd_kcontrol_new my_control = {
        .iface = SNDRV_CTL_ELEM_IFACE_MIXER,
        .name = "PCM Playback Switch",
        .index = 0,
        .access = SNDRV_CTL_ELEM_ACCESS_READWRITE,
        .private_value = 0xffff,
        .info = my_control_info,
        .get = my_control_get,
        .put = my_control_put
};

以下の iface フィールドはコントロールの種類を指定します、 SNDRV_CTL_ELEM_IFACE_XXX、これは通常 MIXER。使用してください CARD ミキサーに論理的に属さないグローバルなコントロールの場合です。コントロールがサウンドカード上の特定のデバイスと密接に関連している場合は、 HWDEP, PCM, RAWMIDI, TIMER（sleepable RCU）が導入されました。 SEQUENCERを使用し、デバイス番号を device および subdevice フィールド。

以下の name で指定します。これはコントロールの名前識別文字列です。ALSA 0.9.x以降、コントロール名は非常に重要です。なぜなら、名前からその役割が分類されるからです。事前に定義された標準的なコントロール名があります。詳細は コントロール名 サブセクションで説明されています。

以下の index フィールドはこのコントロールのインデックス番号を保持します。同じ名前の複数のコントロールがある場合、インデックス番号で区別します。これはカード上に複数のコーデックがある場合です。インデックスがゼロの場合は、上の定義を省略できます。

以下の access フィールドはこのコントロールのアクセスタイプを保持します。ビットマスクの組み合わせを SNDRV_CTL_ELEM_ACCESS_XXXに指定してください。詳細は アクセスフラグ サブセクションで説明されています。

ドライバでのレジスタの更新¶

ドライバからコーデックにアクセスする必要がある場合、以下の関数を呼び出せます： snd_ac97_write(), snd_ac97_read(), snd_ac97_update() および snd_ac97_update_bits().

FM OPL3¶

FM OPL3は多くのチップでまだ使用されており（主に後方互換性のため）、ALSAにもOPL3 FM制御レイヤーが用意されています。OPL3 APIは <sound/opl3.h>.

FMレジスタは直接-FM APIを通じてアクセス可能です。このAPIは <sound/asound_fm.h>で定義されています。ALSAネイティブモードでは、FMレジスタはハードウェア依存デバイスの直接-FM拡張APIを通じてアクセスされ、OSS互換モードではOSS直接-FM互換APIを通じてアクセス可能です。 /dev/dmfmX device.

OPL3コンポーネントを作成するには2つの関数を呼び出します。最初の関数は opl3_t インスタンスを生成する必要があります。

struct snd_opl3 *opl3;
snd_opl3_create(card, lport, rport, OPL3_HW_OPL3_XXX,
                integrated, &opl3);

のコンストラクタです。最初の引数はカードポインタ、2番目の引数は左ポートアドレス、3番目の引数は右ポートアドレスです。ほとんどの場合、右ポートは左ポート＋2に配置されます。

4番目の引数はハードウェアタイプです。

左ポートと右ポートがすでにカードドライバによって割り当てられている場合、5番目の引数（integrated）にゼロ以外の値を渡します。それ以外の場合、opl3モジュールが指定されたポートを自動的に割り当てます。

ハードウェアへのアクセスに標準のI/Oアクセスではなく特別な方法が必要な場合は、 snd_opl3_new().

struct snd_opl3 *opl3;
snd_opl3_new(card, OPL3_HW_OPL3_XXX, &opl3);

で別途opl3インスタンスを作成できます。その後、 command, private_data および private_free プライベートアクセス関数、プライベートデータ、およびデストラクタを設定します。 l_port および r_port は必ずしも設定する必要はありません。コマンドのみを適切に設定してください。データは opl3->private_data フィールドによって保護されています。

から取得できます。 snd_opl3_new()でopl3インスタンスを作成した後、 snd_opl3_init() を呼び出してチップを適切な状態に初期化します。注意点として、 snd_opl3_create() は常に内部でこれを呼び出します。

opl3インスタンスが正常に作成された場合、このopl3用にhwdepデバイスを作成してください。

struct snd_hwdep *opl3hwdep;
snd_opl3_hwdep_new(opl3, 0, 1, &opl3hwdep);

最初の引数はあなたが作成した opl3_t インスタンスで、2番目の引数はインデックス番号で通常0です。

3番目の引数はOPL3ポートに割り当てられたシーケンサクライアントのインデックスオフセットです。MPU401-UARTがある場合はここに1を指定します（UARTは常に0を取るため）。

ハードウェア依存デバイス¶

一部のチップは、特殊な制御やマイクロコードのロードにユーザー空間からのアクセスが必要です。このような場合、ハードウェア依存デバイス(hwdep)を作成できます。hwdep APIは <sound/hwdep.h>で定義されています。opl3ドライバや isa/sb/sb16_csp.c.

の作成は、 hwdep インスタンスは、 snd_hwdep_new().

struct snd_hwdep *hw;
snd_hwdep_new(card, "My HWDEP", 0, &hw);

で行われます。ここで3番目の引数はインデックス番号です。

その後、任意のポインタ値を private_dataに渡すことができます。プライベートデータを割り当てた場合は、デストラクタ関数も定義する必要があります。デストラクタ関数は private_free フィールドによって保護されています。

struct mydata *p = kmalloc(sizeof(*p), GFP_KERNEL);
hw->private_data = p;
hw->private_free = mydata_free;

で設定され、デストラクタの実装は以下のようになります：

static void mydata_free(struct snd_hwdep *hw)
{
        struct mydata *p = hw->private_data;
        kfree(p);
}

このインスタンスには、任意のファイル操作を定義できます。ファイル操作は ops テーブルで定義されています。例えば、このチップがioctlを必要とする場合、

hw->ops.open = mydata_open;
hw->ops.ioctl = mydata_ioctl;
hw->ops.release = mydata_release;

を好きなように実装してください。

ALSAは、バスやアーキテクチャに応じてさまざまなバッファ割当関数を提供しています。これらはすべて一貫したAPIを持っています。物理的に連続したページの割当は snd_malloc_xxx_pages() 関数で行われ、xxxはバスタイプです。

チップがホストメモリではなくPCIメモリマップ領域を使用する場合もあります。この場合、mmapはIntelなどの特定のアーキテクチャでのみ利用可能です。非mmapモードでは通常通りの方法でデータを転送できません。そのため、上記のケースと同様にコールバックを定義する必要があります。例は以下の通りです。 copy_user, copy_kernel および fill_silence コールバックの実装は、ハードウェアがインターレーブまたは非インターレーブサンプルをサポートするかにより異なります。コールバックは以下のように定義されます。 rme32.c および rme96.c.

コールバック copy_user, copy_kernel および silence コールバック copy_user コールバックは、方向が再生または録音であるかにより少し異なります。

static int playback_copy_user(struct snd_pcm_substream *substream,
             int channel, unsigned long pos,
             void __user *src, unsigned long count);
static int capture_copy_user(struct snd_pcm_substream *substream,
             int channel, unsigned long pos,
             void __user *dst, unsigned long count);

インターレーブサンプルの場合、第二引数（channel)は使用されません。第三引数（pos)は現在のポジションオフセットをバイト単位で示します。

第四引数の意味は再生と録音で異なります。再生ではソースデータポインタを保持し、録音では宛先データポインタになります。

最後の引数はコピーするバイト数です。

このコールバックで行うべきことは、再生とキャプチャの方向によって異なります。再生の場合、指定されたポインタ（count) にある指定された量のデータ（src) をハードウェアバッファの指定されたオフセット（pos) にコピーします。memcpyのようにコード化すると、コピーは以下のようになります：

my_memcpy_from_user(my_buffer + pos, src, count);

キャプチャ方向の場合、指定されたオフセット（count) にある指定された量のデータ（pos) をハードウェアバッファから指定されたポインタ（dst).

my_memcpy_to_user(dst, my_buffer + pos, count);

ここで関数は、 from_user および to_user と名付けられています。これはこれらのコールバックに渡されるユーザー領域のバッファであるためです。つまり、コールバックはユーザー領域のデータをハードウェアバッファに直接コピーする必要があります。

注意深く読まれた読者には、これらのコールバックが他のコールバックと異なり、バイト単位で引数を受け取る点に気づくかもしれません。これは上述のようにコードを簡潔にするため、またインターレーブと非インターレーブのケースを統一しやすくするためです。

非インターレーブされたサンプルの場合、実装はやや複雑になります。コールバックは第二引数で渡される各チャンネルごとに呼び出されるため、1回の転送ごとにNチャンネル分呼び出されます。

他の引数の意味はインターレースの場合とほぼ同じです。コールバックは、指定されたチャンネルに対して、指定されたユーザースペースバッファから/へデータをコピーする必要があります。詳細な実装については、 isa/gus/gus_pcm.c 「pci/rme9652/rme9652.c」などの例を確認してください。

上記のコールバックはユーザースペースバッファからの/へのコピーを処理します。ただし、カーネルスペースバッファからの/へのコピーが必要なケースもあります。その場合、 copy_kernel コールバックが呼ばれます。見た目は以下のようになります：

static int playback_copy_kernel(struct snd_pcm_substream *substream,
             int channel, unsigned long pos,
             void *src, unsigned long count);
static int capture_copy_kernel(struct snd_pcm_substream *substream,
             int channel, unsigned long pos,
             void *dst, unsigned long count);

簡単に確認できる通り、違いはバッファポインタに前缀が付いていないことだけです。つまり、第4引数にカーネルバッファポインタが渡されます。それに応じて、ユーザーコピーを含まないバージョンの実装になります。例えば、 __user のようなものです。

my_memcpy(my_buffer + pos, src, count);

通常、再生には別のコールバック fill_silence が定義されます。これは上記のコピーコールバックと同様の方法で実装されます：

static int silence(struct snd_pcm_substream *substream, int channel,
                   unsigned long pos, unsigned long count);

引数の意味は copy_user および copy_kernel コールバックと同様ですが、バッファポインタの引数はありません。インターレースサンプルの場合、チャンネル引数は意味を持たず、 copy_* コールバックによって実装されます。

の場合は同様です。 fill_silence コールバックの役割は、ハードウェアバッファの指定されたオフセット（count）に指定された量（pos）の静かなデータを設定することです。データ形式が符号付き（つまり静かなデータは0）であると仮定すると、memsetのような関数を用いた実装は以下のようになります：

my_memset(my_buffer + pos, 0, count);

インターレースでないサンプルの場合、また複数のチャンネルごとに転送ごとにN回呼ばれるため、実装がやや複雑になります。例として、 isa/gus/gus_pcm.c.

バッファは vmalloc()たとえば、中間バッファとして使用される。最近のカーネルバージョンでは、標準的な方法で割当てを行うことができる。 snd_pcm_lib_malloc_pages() バッファの事前割当てを設定した後、coを介して設定する。 SNDRV_DMA_TYPE_VMALLOC type。

snd_pcm_set_managed_buffer_all(pcm, SNDRV_DMA_TYPE_VMALLOC,

デバイスポインタ引数にNULLを渡すことで、デフォルトのページ（GFP_KERNELおよびGFP_HIGHMEM）が割当てられることを示す。

snd_pcm_set_managed_buffer_all(pcm, SNDRV_DMA_TYPE_VMALLOC,
        snd_dma_continuous_data(GFP_KERNEL | __GFP_DMA32), 0, 0);

プロックインターフェース¶

ALSAはprocfsに対して簡単なインターフェースを提供している。プロックファイルはデバッグに非常に有用である。ドライバを開発し、実行状態やレジスタダンプを取得したい場合は、プロックファイルを設定することをお勧めする。APIは以下の場所に存在する。 <sound/info.h>.

プロックファイルを作成するには、以下のように呼び出す。 snd_card_proc_new().

struct snd_info_entry *entry;
int err = snd_card_proc_new(card, "my-file", &entry);

第二引数は作成するプロックファイルの名前を指定する。上記の例では、以下のようにカードディレクトリ下にファイルが作成される。 my-file カードディレクトリ下、例えば /proc/asound/card0/my-file.

他のコンポーネント同様に、プロックエントリは snd_card_proc_new() で作成され、カード登録および解放関数内で自動的に登録および解放される。

作成が成功した場合、関数は第三引数で指定されたポインタに新しいインスタンスを格納する。これは読み取り専用のテキストプロックファイルとして初期化される。このプロックファイルをそのまま読み取り専用テキストファイルとして使用する場合は、プライベートデータを介して読み取りコールバックを設定する。 snd_info_set_text_ops().

snd_info_set_text_ops(entry, chip, my_proc_read);

第二引数（chip）はコールバックで使用するプライベートデータを指定し、第三パラメータは読み取りバッファサイズを指定し、第四（my_proc_read）はコールバック関数を指定する。この関数は以下のように定義される。

static void my_proc_read(struct snd_info_entry *entry,
                         struct snd_info_buffer *buffer);

読み取りコールバックでは、 snd_iprintf() で出力文字列を使用し、これは標準出力と同様に動作する。 printf()たとえば、

static void my_proc_read(struct snd_info_entry *entry,
                         struct snd_info_buffer *buffer)
{
        struct my_chip *chip = entry->private_data;

        snd_iprintf(buffer, "This is my chip!\n");
        snd_iprintf(buffer, "Port = %ld\n", chip->port);
}

ファイルのパーミッションはその後変更可能である。デフォルトでは全ユーザーに対して読み取り専用が設定されている。ユーザー（rootがデフォルト）に書き込み権限を追加したい場合は、以下のように行う。

entry->mode = S_IFREG | S_IRUGO | S_IWUSR;

書き込みバッファサイズとコールバックを設定する。

entry->c.text.write = my_proc_write;

書き込みコールバックでは、 snd_info_get_line() でテキスト行を取得し、 snd_info_get_str() で行から文字列を取得できる。いくつかの例は以下の場所に存在する。 core/oss/mixer_oss.c、core/oss/および pcm_oss.c.

rawデータ用のプロックファイルでは、属性を以下のように設定する。

static const struct snd_info_entry_ops my_file_io_ops = {
        .read = my_file_io_read,
};

entry->content = SNDRV_INFO_CONTENT_DATA;
entry->private_data = chip;
entry->c.ops = &my_file_io_ops;
entry->size = 4096;
entry->mode = S_IFREG | S_IRUGO;

rawデータの場合、 size フィールドを適切に設定する必要がある。これはプロックファイルアクセスの最大サイズを指定する。

rawモードの読み取り/書き込みコールバックはテキストモードより直接的である。低レベルのI/O関数（例： copy_from_user() および copy_to_user() ）を使用してデータを転送する必要がある。

static ssize_t my_file_io_read(struct snd_info_entry *entry,
                            void *file_private_data,
                            struct file *file,
                            char *buf,
                            size_t count,
                            loff_t pos)
{
        if (copy_to_user(buf, local_data + pos, count))
                return -EFAULT;
        return count;
}

情報エントリのサイズが適切に設定されている場合、 count および pos は0と指定されたサイズの範囲内に収まる。コールバック内で範囲を確認する必要はなく、他の条件が必要な場合を除けばよい。

電源管理¶

チップがスリープ/再起動機能と連携して動作する場合、ドライバに電源管理コードを追加する必要があります。電源管理用の追加コードは、 CONFIG_PMマクロで ifdef するか、__maybe_unused 属性で注釈を付ける必要があります。それ以外の場合、コンパイラがエラーを出力します。

ドライバが 完全に スリープ/再起動をサポートしている場合、つまりデバイスがスリープが呼ばれた際の状態を適切に再起動できる場合、pcm info フィールドに SNDRV_PCM_INFO_RESUME フラグを設定できます。通常、チップのレジスタがRAMに安全に保存・復元できる場合にこの操作が可能です。このフラグが設定されている場合、再起動コールバックが完了後に SNDRV_PCM_TRIGGER_RESUME トリガー コールバックが呼び出されます。

ドライバが完全なPMをサポートしていない場合でも、部分的なスリープ/再起動が可能であれば、スリープ/再起動コールバックの実装は依然として有益です。このような場合、アプリケーションは状態をリセットして、 snd_pcm_prepare() を呼び出してストリームを適切に再開します。そのため、以下のスリープ/再起動コールバックを定義できますが、 SNDRV_PCM_INFO_RESUME info フラグをPCMに設定しないでください。

SUSPEND 用のトリガーは、 snd_pcm_suspend_all() が呼ばれたときに常に呼び出せます。これは、 SNDRV_PCM_INFO_RESUME フラグとは関係ありません。 RESUME フラグは、 snd_pcm_resume()の動作にのみ影響します。(理論上、 SNDRV_PCM_TRIGGER_RESUME が設定されていない場合、トリガー コールバックで処理する必要はありません。ただし、互換性のためには残しておくのが良いでしょう。) SNDRV_PCM_INFO_RESUME 以前の ALSA ドライババージョンでは、共通の電源管理レイヤーが提供されていましたが、それらは削除されました。ドライバは、デバイスが接続されているバスに応じてスリープ/再起動のハンドラを定義する必要があります。PCI ドライバの場合、コールバックは以下のようになります:

{

        return 0;
}
static int __maybe_unused snd_my_resume(struct device *dev)

        return 0;
}

static int __maybe_unused mychip_resume(struct pci_dev *pci)
{

        struct snd_card *card = dev_get_drvdata(dev);
        struct mychip *chip = card->private_data;

        snd_mychip_reinit_chip(chip);
        /* (3) */
        snd_mychip_restore_registers(chip);
        /* (4) */
        snd_ac97_resume(chip->ac97);
        /* (5) */
        snd_mychip_restart_chip(chip);
        /* (6) */
        snd_power_change_state(card, SNDRV_CTL_POWER_D0);
        return 0;
}

モジュールパラメータ¶

ALSAには標準的なモジュールオプションがあります。少なくとも各モジュールは index, id および enable オプション。

モジュールが複数のカードをサポートする場合（通常は8台まで） SNDRV_CARDS カード）は配列で定義する必要があります。初期値はすでに定数として定義されており、プログラミングを容易にするためのものです:

static int index[SNDRV_CARDS] = SNDRV_DEFAULT_IDX;
static char *id[SNDRV_CARDS] = SNDRV_DEFAULT_STR;
static int enable[SNDRV_CARDS] = SNDRV_DEFAULT_ENABLE_PNP;

モジュールが単一のカードのみをサポートする場合、単一の変数で構いません。 enable この場合、optionは必ずしも必要ではありませんが、互換性のためダミーのオプションを設けるのが良いでしょう。

モジュールパラメータは標準の module_param(), module_param_array() および MODULE_PARM_DESC() は、複数の名前で1つの関数を表すために使用される。典型的な用途は:

典型的なコード例は以下の通りです:

#define CARD_NAME "My Chip"

module_param_array(index, int, NULL, 0444);
MODULE_PARM_DESC(index, "Index value for " CARD_NAME " soundcard.");
module_param_array(id, charp, NULL, 0444);
MODULE_PARM_DESC(id, "ID string for " CARD_NAME " soundcard.");
module_param_array(enable, bool, NULL, 0444);
MODULE_PARM_DESC(enable, "Enable " CARD_NAME " soundcard.");

また、モジュールの説明とライセンスの定義を忘れずにください。特に、最近のmodprobeはモジュールライセンスをGPLなどとして定義する必要があります。そうでないと、システムが「汚染された」状態として表示されます。

MODULE_DESCRIPTION("Sound driver for My Chip");
MODULE_LICENSE("GPL");

ドライバをALSAツリーに登録する方法¶

一般¶

これまで、ドライバコードの書き方を学んできました。そして、ここで疑問が生じるかもしれません：自分のドライバをALSAドライバツリーにどのように配置すればよいのでしょうか？ここ（ついに！）では標準的な手順を簡潔に説明します。

例えば、カード「xyz」用の新しいPCIドライバを作成したとします。カードモジュール名はsnd-xyzになります。新しいドライバは通常、alsa-driverツリーに配置され、 sound/pci PCIカードの場合、ディレクトリに配置されます。

以下のセクションでは、ドライバコードがLinuxカーネルツリーに配置される場合を想定しています。対象は、単一のソースファイルからなるドライバと、複数のソースファイルからなるドライバの2つのケースです。

単一のソースファイルからなるドライバ¶

  1. sound/pci/Makefileを編集

    xyz.cというファイルがあるとします。以下の2行を追加してください

snd-xyz-objs := xyz.o
obj-$(CONFIG_SND_XYZ) += snd-xyz.o

  1. Kconfigエントリを作成

    あなたのxyzドライバ用の新しいKconfigエントリを追加してください。config SND_XYZ tristate “Foobar XYZ” depends on SND select SND_PCM help ここにYを選択するとFoobar XYZサウンドカードのサポートを含みます。このドライバをモジュールとしてコンパイルする場合はMを選択してください。モジュール名はsnd-xyzになります。この行でselect SND_PCMを指定することで、ドライバxyzがPCMをサポートしていることを示します。selectコマンドでサポートするコンポーネントには、SND_RAWMIDI、SND_TIMER、SND_HWDEP、SND_MPU401_UART、SND_OPL3_LIB、SND_OPL4_LIB、SND_VX_LIB、SND_AC97_CODECが含まれます。各サポートコンポーネントについてselectコマンドを追加してください。

    一部の選択肢は低レベルの選択肢を含意します。例えば、PCMにはTIMERが含まれ、MPU401_UARTにはRAWMIDIが含まれ、AC97_CODECにはPCMが含まれ、OPL3_LIBにはHWDEPが含まれます。低レベルの選択肢は再度指定する必要がありません。

    Kconfigスクリプトの詳細については、kbuildドキュメンテーションを参照してください。

複数のソースファイルを持つドライバ¶

ドライバsnd-xyzが複数のソースファイルを持つ場合、それらは新しいサブディレクトリsound/pci/xyzに配置されています。

  1. 新しいディレクトリ（sound/pci/xyz) in sound/pci/Makefile 以下のように作成します

obj-$(CONFIG_SND) += sound/pci/xyz/

  1. ディレクトリ sound/pci/xyzの下にMakefileを作成します

snd-xyz-objs := xyz.o abc.o def.o
obj-$(CONFIG_SND_XYZ) += snd-xyz.o

  1. Kconfigエントリを作成

    この手順は前節と同じです。

役に立つ関数¶

snd_printk() および仲間¶

注意

このサブセクションでは、標準的な printk() の装飾をより一層行うためのいくつかの補助関数について説明します。ただし、一般的にはこのような補助関数の使用はもはや推奨されません。可能な限り、標準関数のように dev_err() または pr_err().

が提供する詳細なバージョンの printk() 関数を使用してください。カーネル構成 CONFIG_SND_VERBOSE_PRINTK が設定されている場合、この関数は呼び出し元のファイル名と行番号とともに指定されたメッセージを出力します。 KERN_XXX プレフィックスは printk() と同様に処理されるため、このプレフィックスを追加することをお勧めします。例えば、snd_printk(KERN_ERR "Oh my, sorry, it’s extremely bad!\n");のようにします。

また、 printk()にはデバッグ用の関数もあります。 snd_printd() は一般的なデバッグ目的に使用できます。 CONFIG_SND_DEBUG が設定されている場合、この関数はコンパイルされ、 snd_printk()と同様に動作します。ALSAがデバッグフラグなしでコンパイルされている場合、この関数は無視されます。

snd_printdd() はデバッグフラグが設定されている場合にのみコンパイルされます。 CONFIG_SND_DEBUG_VERBOSE が設定される前。

snd_BUG()¶

は BUG? メッセージおよびスタックトレースを、 snd_BUG_ON() の場所で表示します。致命的なエラーがその場所で発生していることを示すために役立ちます。

デバッグフラグが設定されていない場合、このマクロは無視されます。

snd_BUG_ON()¶

snd_BUG_ON() マクロは WARN_ON() マクロと似ています。例えば、snd_BUG_ON(!pointer); または条件式として使用できます。if (snd_BUG_ON(non_zero_is_bug)) return -EINVAL; など。

マクロは条件式を評価します。 CONFIG_SND_DEBUGが設定されている場合、式がゼロでない場合、警告メッセージ（例： BUG? (xxx) ）を表示します。通常、スタックトレースも続きます。どちらの場合も評価された値を返します。

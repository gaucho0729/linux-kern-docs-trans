HD-Audioドライバに関する補足情報¶

Takashi Iwai <tiwai@suse.de>

一般¶

HD-audioはAC97の後継として現代のPCに搭載されるオーディオコンポーネントの新規標準です。LinuxはHD-audioを長年サポートしてきましたが、新しいマシンではしばしば問題が発生します。問題の一部は破損したBIOS、もう一つはドライバの実装に起因しています。このドキュメントではHD-audioハードウェアのトラブルシューティングおよびデバッグ方法について簡潔に説明します。

HD-audioコンポーネントは2つの部分から構成されています：HD-audioバス上のコントローラーチップとコーデックチップです。Linuxはすべてのコントローラーチップをサポートする単一のドライバsnd-hda-intelを提供しています。ドライバ名に特定のハードウェアベンダーの名前が含まれているように見えますが、これは他のベンダーのコントローラーチップに適用される一般的なドライバです。HD-audioコントローラーは互換性が保証されているため、snd-hda-driverはほとんどの場合動作します。ただし、予想通り、各コントローラータイプに特有のバグや問題は存在します。snd-hda-intelドライバは以下の通り、これらの問題に対する対処方法を備えています。

コントローラーは複数のコーデックを持つ場合があります。通常は1つのオーディオコーデックと、オプションで1つのモデムコーデックを持ちます。理論上、複数のオーディオコーデックが存在する可能性もあります（アナログ出力とデジタル出力など）、そしてミキサー要素の競合によりドライバが正しく動作しない可能性があります。このようなハードウェアが実際に存在する場合、今後はこの問題が修正される予定です。

snd-hda-intelドライバはコーデックごとに異なるパーサーを提供しています。一般的なパーサーをフォールバックとして使用しますが、現在のところその機能は限定的です。代わりに、コーデック固有のパーサー（patch_*.cで実装）がコーデック固有の実装に使用されます。コーデック固有の問題の詳細は後述のセクションで説明します。

HD-audioの深く詳細なデバッグに興味がある場合は、まずHD-audio仕様書を読みましょう。仕様書はIntelのウェブページなどで確認できます、例えば：

  • https://www.intel.com/standards/hdaudio/

HD-Audioコントローラー¶

DMAポジションの問題¶

コントローラーで最も一般的な問題はDMAポインタの不正確な報告です。再生および録音用のDMAポインタは、LPIBレジスタ経由またはポジションバッファマップ経由の2つの方法で読み取れます。デフォルトではドライバはioマップされたポジションバッファから読み込み、ポジションバッファが動作しない場合にLPIの方法にフォールバックします。しかし、一部のデバイスではこの検出が正確ではありません。このような場合、デフォルトの方法を変更するには、 position_fix オプションの下に隠されています。

position_fix=1 LPIBメソッドを明示的に使用する方法を指定します。 position_fix=2 ポジションバッファを使用する方法を指定します。 position_fix=3 VIAコントローラーには必要となる両方の方法を組み合わせる方式を意味します。キャプチャストリームの位置はLPIBとポジションバッファの値を比較して補正されます。 position_fix=4 これはすべてのコントローラーで利用可能なもう一つの組み合わせ方式で、プレイバックにはLPIBを、キャプチャストリームにはポジションバッファを使用します。 position_fix=5 これはIntelプラットフォーム（Skylake以降）に特有の方式で、正確なポジション報告のために遅延計算を適用します。 position_fix=6 これは最近のAMDコントローラー向けに固定されたFIFOサイズで位置を補正する方式です。他のすべてのコントローラーでは0がデフォルト値で、上記の通り自動的にLPIBにフォールバックします。繰り返しの音声問題が発生した場合はこのオプションが役立つ可能性があります。

さらに、すべてのコントローラーがウェイクアップタイミングに関する問題を抱えていることがわかっています。バッファでデータを処理するよりも少し前からウェイクアップします。これはALSA dmixやJACKなど多くの問題を引き起こしました。2.6.27カーネル以降、ドライバはウェイクアップタイミングに人工的な遅延を導入しています。この遅延は bdl_pos_adj オプションの下に隠されています。

が呼ばれるとき、modprobeは bdl_pos_adj で制御されます。デフォルトでは負の値（-1）ですが、コントローラーのチップに応じて適切な値が割り当てられます。Intelチップでは1、他のチップでは32が設定されます。通常は問題ありませんが、動作しない場合や警告メッセージが表示される場合はこのパラメータを他の値に変更してください。

コーデックプローブの問題¶

まれですが深刻な問題としてコーデックプローブがあります。BIOSが利用可能なコーデックスロットを正しく報告しない場合、ドライバは非存在するスロットにアクセスしようとし、これにより全体的な破壊的なエラーが発生します。症状としてよく見られるエラーメッセージは以下の通りです：

hda_intel: azx_get_response timeout, switching to polling mode:
      last cmd=0x12345678
hda_intel: azx_get_response timeout, switching to single_cmd mode:
      last cmd=0x12345678

1行目の警告は通常比較的無害です。これはコーデック応答がIRQを介して通知されないことを意味します。ドライバは明示的にポーリング方式で応答を読み取ります。非常にわずかなCPUオーバーヘッドを生じますが、気づきにくいです。

2行目のエラーメッセージは致命的なエラーです。このようなエラーが発生した場合、通常何かが非常に間違っていることを意味します。最も可能性が高いのは非存在するコーデックスロットにアクセスしていることです。

したがって、2行目のエラーメッセージが表示された場合は、以下の probe_mask オプションでプローブするコーデックスロットを絞り込んでください。これはビットマスクで、各ビットがコーデックスロットに対応します。たとえば、1番目のスロットのみをプローブする場合は probe_mask=1を指定します。1番目と3番目のスロットをプローブする場合は probe_mask=5 (5 = 1 | 4)のように、それ以降も同様です。

2.6.29カーネル以降、ドライバーはより堅牢なプローブ方法を採用しており、このエラーはめったに起きない可能性があります。

BIOSが破損しているマシンでは、ハードウェアが使用していないと報告しているコーデックスロットを強制的にプローブする必要があります。このような場合、 probe_mask オプションのビット8（0x100）をオンにします。その後、残りの8ビットは無条件でプローブするコーデックスロットとして渡されます。例えば、 probe_mask=0x103 は、ハードウェアが報告する内容に関係なく、コーデックスロット0と1を強制的にプローブします。

割込み処理¶

HD-audioドライバーは2.6.33カーネル以降、MSIをデフォルト（利用可能であれば）としています。MSIは一部のマシンでは動作が良好で、パフォーマンス面でも一般的に優れています。しかし、NvidiaコントローラーではMSIと組み合わせた場合（特にAMDチップセットとの組み合わせで）不具合が発生するため、MSIを無効にしています。

MSIで動作しない他のデバイスもまだ存在するようです。最近のカーネルで音質の低下（ジャッキング、など）やロックアップが発生した場合は、 enable_msi=0 オプションを指定してMSIを無効にしてみてください。動作した場合は、hda_intel.cで定義されたブラックリストに既知の不具合デバイスを追加できます。このような場合、問題を報告し、アップストリームの開発者にパッチを戻してください。

HD-Audioコーデック¶

モデル オプション¶

HD-audioドライバーに関する最も一般的な問題は、サポートされていないコーデック機能やデバイス構成の不一致です。ほとんどのコーデック固有のコードには、BIOS設定を上書きするか、より包括的な機能を提供するためのいくつかのプリセットモデルが含まれています。

ドライバーはPCI SSIDを確認し、静的構成テーブルを検索して一致するエントリを見つけます。新しいマシンを使用している場合、以下のようなメッセージが表示されることがあります：

hda_codec: ALC880: BIOS auto-probing.

以前のバージョンでは、以下のようなメッセージが表示されました：

hda_codec: Unknown model for ALC880, trying auto-probe from BIOS...

このようなメッセージが表示されても、パニックにならないでください。深呼吸してタオルを手に取りましょう。これは情報メッセージであり、警告やエラーではありません。これは、あなたのデバイスのPCI SSIDが既知のプリセットモデル（ホワイトリスト）に記載されていないことを意味します。しかし、ドライバーが破損しているわけではありません。多くのコーデックドライバーはBIOS設定に基づいて自動構成メカニズムを提供しています。

HD-audioコーデックには通常「ピン」ウィジェットがあり、BIOSは各ピンのデフォルト構成を設定します。これは位置、接続タイプ、ジャックの色などを示します。HD-audioドライバーはこれらのデフォルト構成値から正しい接続を推測できます。ただし、一部のコーデックサポートコード（例：patch_analog.c）は自動プローブをサポートしていません（2.6.28時点では）。また、BIOSはしばしば、正しい値を設定せずドライバーを破損させます。

事前に設定されたモデル（最近では「fix-up」と呼ばれる）は、このような状況を克服するため基本的に提供されています。ホワイトリストにマッチする事前に設定されたモデルが見つかった場合、ドライバーはそのモデルの静的な設定（正しいピン設定など）を自動的に採用します。したがって、既存のものとやや異なるPCI SSID（またはコーデックSSID）を持つ新しいマシンを持っている場合、同じモデルを再利用する可能性があります。この場合、 model オプションを指定して、PCI（およびコーデック）SSIDの検索ではなく事前に設定されたモデルを指定できます。

何 model オプションの値は、コーデックチップによって異なります。コーデックプロシージャーファイル（以下で説明する「コーデックプロシージャーファイル」セクションを参照）から自分のコーデックチップを確認してください。これにより、あなたのコーデックチップのベンダー/製品名が表示されます。その後、 HD-Audio コーデック専用モデル ファイル、HD-audioドライバーのセクションを確認してください。ここでは、コーデックと、それぞれに属する model オプションの一覧が表示されます。たとえば、Realtek ALC269 codecチップの場合、 model=ultra Samsung Q1 Ultraと互換性のあるデバイスに渡すことができます。

したがって、サポートされていない非動作のHD-audioハードウェアの最初に実行すべきことは、HD-audioコーデックといくつかの異なる model オプション値を確認することです。幸運があれば、これらのうちいくつかがあなたのデバイスに合っている可能性があります。

いくつかの特別なモデルオプション値があります：

  • ‘nofixup’を渡すと、コーデックパーサー内のデバイス固有のfix-up処理がスキップされます。

  • when generic ‘noautoconfig’を渡すと、コーデック固有のパーサーがスキップされ、ジェネリックパーサーのみが使用されます。

スピーカーおよびヘッドホン出力¶

HD-audioで最も頻繁かつ明らかに発生するバグの一つは、内蔵スピーカーまたはヘッドホンジャックのいずれかまたは両方からの静かな出力です。一般的にはまずヘッドホン出力の確認を試すべきです。スピーカー出力には外部アンプビットなどの追加制御が必要となるため、ヘッドホン出力の方がやや確率が高いです。

バグレポートを提出する前に、ミキサーが正しく設定されているか確認してください。最新版のsnd-hda-intelドライバーは、「マスター」ボリューム制御だけでなく、「フロント」ボリューム（フロントはフロントチャネルを指します）も提供しています。また、個別に「ヘッドホン」や「スピーカー」の制御が存在する場合もあります。

スピーカー出力についても同様です。一部のコーデックでは「外部アンプ」スイッチが存在する場合があります。存在する場合はこれをオンにしてください。

別の関連する問題は、ヘッドホン挿入時にスピーカー出力が自動的にミュートされる機能です。この機能はほとんどの場合実装されていますが、すべての事前に設定されたモデルやコーデックサポートコードには含まれていません。

いずれにしても、このような問題がある場合は、別のモデルオプションを試してみてください。他のモデルはよりよくマッチし、より多くのマッチング機能を提供する可能性があります。どのモデルも動作しない場合は、バグレポートを送信してください。詳しくはバグレポートセクションをご参照ください。

ドライバの問題をデバッグするほどマゾヒストックなほど、以下の点に注意してください：

  • スピーカー（ヘッドホンも同様）の出力は通常、外部アンプが必要です。これは一般的にEAPDコマンドまたは特定のGPIO経由で設定されます。コーデックピンがEAPDをサポートする場合、SET_EAPD_BTLコマンド（0x70c）を用いることでより確率的に動作します。他はGPIOピン（主にGPIO0またはGPIO1）でEAPDをON/OFFできます。

  • 一部のRealtekコーデックは、アンプをオンにするために特別なベンダー固有の係数が必要です。詳しくはpatch_realtek.cをご参照ください。

  • IDTコーデックは、各アナログピンごとに追加の電源ON/OFF制御を持つ場合があります。詳しくはpatch_sigmatel.cをご参照ください。

  • 非常にまれですが、一部のデバイスはピン検出コマンドをトリガーされるまで受け付けないことがあります。GET_PIN_SENSEコマンド（0xf09）を発行すると、コーデック通信が停止する可能性があります。例はpatch_realtek.cに掲載されています。

キャプチャの問題¶

キャプチャの問題は、ミキサーの設定が不足していることが原因であることが多く、バグレポートを送信する前に、ミキサーを正しく設定しているか確認してください。例えば、「キャプチャボリューム」および「キャプチャスイッチ」を適切に設定し、「キャプチャソース」または「入力ソース」の選択も正しく行う必要があります。一部のデバイスでは「マイクブースト」ボリュームまたはスイッチが存在します。

PCMデバイスが「default」PCM（パルスオーディオプラグインなし）経由で開かれる場合、通常「デジタルキャプチャボリューム」コントロールが表示されます。これは、ハードウェアボリューム制御がない入力（デジタルマイクなど）の信号にソフトウェアで追加のゲイン/減衰を加えるためのものです。必要ない限り、このコントロールは正確に50%（0dB相当）に設定する必要があります。ゲインや減衰を加える必要がないためです。ただし、「hw」PCM（rawアクセスPCM）を使用する場合、このコントロールは影響を与えません。

一部のコーデック／デバイスではアナログ回路が非常に悪く、録音された音声に特定のDCオフセットが含まれることがわかっています。これはドライバのバグではありません。

現代のほとんどのノートPCはアナログCD入力接続を持たないため、CD入力からの録音は多くの場合動作しません。ただしドライバはキャプチャソースとして提供しています。CDDAを使用してください。

マイクの内蔵と外付けの自動切り替えは一部のコーデックモデルでは実装されていますが、すべてのモデルでは実装されていません。一部は私の怠さのためですが、主にテストケースが不足しているためです。改善のためのパッチを作者に送信してください。

直接デバッグ¶

どのモデルオプションも結果を改善しない場合、悪に立ち向かう強者であれば、デバイスにraw HD-audio コーデックコマンドを送ることでデバッグを試してください。利用可能なツールはhda-emuとhda-analyzerです。詳細は以下のセクションに記載されています。これらのツールを使用するにはhwdepを有効にする必要があります。詳しくは「カーネル設定」セクションをご参照ください。

その他の問題¶

カーネルの設定¶

一般的には、サウンドデバッグオプションを有効にしてください。 CONFIG_SND_DEBUG=yデバッグを行っているかどうかに関わらず、このオプションを有効にすると、 snd_printd() マクロや他の機能が有効になり、プローブ時に追加のカーネルメッセージが得られます。

さらに、有効化できます。 CONFIG_SND_DEBUG_VERBOSE=yただし、これにより非常に多くのメッセージが表示されます。必要に応じてのみ有効にしてください。

適切な CONFIG_SND_HDA_CODEC_* オプションを有効にしてください。注意点として、これらはコーデックチップに応じて設定されるため、lspciでNvidiaコントローラーが表示されても、他のベンダーのオプションを選択する必要があります。不明な場合はすべてのyesを選択してください。

CONFIG_SND_HDA_HWDEP ドライバのデバッグに有用なオプションです。このオプションが有効になると、ドライバがハードウェア依存デバイス（各コーデックごとに1つずつ）を作成し、これらのデバイスファイルを通じてデバイスに直接アクセスできます。例えば、 hwC0D2 は、最初のカード（#0）のコーデックスロット#2に作成されます。hda-verbやhda-analyzerなどのデバッグツールではhwdepデバイスを有効にする必要があります。そのため、常に有効にしておくのが望ましいです。

CONFIG_SND_HDA_RECONFIG は新しいオプションで、このオプションは上記のhwdepオプションに依存します。有効にすると、対応するhwdepディレクトリ下にsysfsファイルが生成されます。詳しくは以下の「HD-audio再構成」セクションをご参照ください。

CONFIG_SND_HDA_POWER_SAVE オプションは省電力機能を有効にします。詳しくは以下の「省電力」セクションをご参照ください。

コーデックプロシージャーファイル¶

コーデックプロシージャーファイルはHD-audioのデバッグに非常に有用です。これは各コーデックウィジェットの多くの有用な情報を表示します。

プロシージャーファイルは/proc/asound/card*/codec#*に位置し、各コーデックスロットごとに1ファイルあります。ここではコーデックベンダー、製品ID、名前、各ウィジェットのタイプ、機能などに関する情報を確認できます。ただし、ジャックセンシングの状態は表示されません。これはジャックセンシングがトリガー状態に依存するためです。

このファイルはデバッグツールによって読み込まれ、またエミュレータに主なコーデック情報として提供することもできます。詳しくは以下のデバッグツールセクションをご参照ください。

このprocファイルは、ジェネリックパーサーが使用されているかを確認する際にも使用できます。ジェネリックパーサーが使用されている場合、ベンダー/製品ID名は「Realtek ID 0262」と表示され、「Realtek ALC262」と表示されません。

HD-Audio 再構成¶

この機能は、ドライバを再起動することなくHD-audio コーデックを動的に再構成できるようにする実験的な機能です。以下のsysfsファイルは、各codec-hwdepデバイスディレクトリ（例：/sys/class/sound/hwC0D0）下にあります：

vendor_id

32ビットのコーデックベンダーIDの16進数を表示します。このファイルに書き込むことでベンダーIDの値を変更できます。

subsystem_id

32ビットのコーデックサブシステムIDの16進数を表示します。このファイルに書き込むことでサブシステムIDの値を変更できます。

revision_id

32ビットのコーデックリビジョンIDの16進数を表示します。このファイルに書き込むことでリビジョンIDの値を変更できます。

afg

AFG IDを表示します。これは読み取り専用です。

mfg

MFG IDを表示します。これは読み取り専用です。

名前

コーデック名文字列を表示します。このファイルに書き込むことで名前を変更できます。

modelname

現在設定されている model オプションを表示します。このファイルに書き込むことでオプションを変更できます。

init_verbs

初期化時に実行する追加のベロップです。このファイルに書き込むことでベロップを追加できます。3つの数値（nid、verb、パラメータ）をスペースで区切って渡してください。

hints

コーデックパーサーに任意の用途で使用するヒント文字列を表示・保存します。形式は key = valueです。例えば、 jack_detect = no とすることで、マシンのジャック検出を完全に無効化できます。

init_pin_configs

BIOSによって設定された初期ピンのデフォルトコンフィギュレーション値を表示します。

driver_pin_configs

コーデックパーサーが明示的に設定したピンのデフォルト値を表示します。これはすべてのピン値を表示するのではなく、パーサーによって変更された値のみを表示します。つまり、パーサーがピンのデフォルトコンフィギュレーション値を自分で変更しなければ、この項目には何も表示されません。

user_pin_configs

BIOS設定を上書きするピンのデフォルトコンフィギュレーション値を表示します。このファイルに書き込む（2つの数値、NIDと値）ことで新しい値を追加できます。次の再構成時に、この値が初期BIOS値の代わりに使用されます。注意点として、このコンフィギュレーションはドライバのピンコンフィギュレーションを上書きすることも含まれます。

reconfig

コーデックの再構成をトリガーします。このファイルに任意の値を書き込むと、ドライバが再初期化し、コーデックツリーを再解析します。すべてのsysfsエントリでの変更が考慮されます。

クリア

コーデックをリセットし、指定されたコーデックのミキサーエレメントとPCM情報を削除し、すべての初期ベロップとヒントをクリアします。

たとえば、ピンウィジェット0x14のピンのデフォルト設定値を0x9993013fに変更し、ドライバーがその状態に基づいて再構成する場合、以下のように実行します:

# echo 0x14 0x9993013f > /sys/class/sound/hwC0D0/user_pin_configs
# echo 1 > /sys/class/sound/hwC0D0/reconfig

ヒント文字列¶

コーデックパーサーには、実際のコーデックやデバイスの挙動に合わせてより正確に動作させるためのスイッチや調整用のコントロールがいくつかあります。これらは、上記セクションで説明した「ヒント」文字列を通じて動的に調整することが可能です。たとえば、sysfsやパッチファイルを通じて文字列を渡すことで、ジャック検出を無効化し、コーデックパーサーがオートミュートやマイクオートスイッチなどの機能をスキップします。ブール値として、以下いずれかを指定できます。 jack_detect = no を指定できます。 yes, no, true, false, 1 または 0 を指定できます。

ジェネリックパーサーがサポートするヒント:

このマシンでジャック検出が有効かどうかを指定します。デフォルトはtrueです

inv_jack_detect (ブール値)

ジャック検出論理が反転していることを示します

trigger_sense (ブール値)

ジャック検出にはAC_VERB_SET_PIN_SENSEという明示的なコマンド呼び出しが必要であることを示します

inv_eapd (ブール値)

EAPDが反転論理で実装されていることを示します

pcm_format_first (ブール値)

ストリームタグとチャンネルIDの前にPCMフォーマットを設定します

sticky_stream (ブール値)

PCMフォーマット、ストリームタグおよびIDを可能な限り保持します。デフォルトはtrueです

spdif_status_reset (ブール値)

SPDIFストリームが設定されるたびにSPDIFステータスビットをリセットします

pin_amp_workaround (ブール値)

出力ピンは複数のアンプ値を持つ可能性があります

single_adc_amp (ブール値)

ADCは単一の入力アンプのみを持つことができます

auto_mute (ブール値)

ヘッドホンオートミュート機能を有効/無効にします。デフォルトはtrueです

auto_mic (ブール値)

マイクロホンオートスイッチ機能を有効/無効にします。デフォルトはtrueです

line_in_auto_switch (ブール値)

ラインインオートスイッチ機能を有効/無効にします。デフォルトはfalseです

need_dac_fix (ブール値)

primary_hp (ブール値)

ヘッドホンジャックを主な出力として検出します。デフォルトはtrueです

multi_io (ブール値)

マルチI/O構成（例：共有ラインイン/サウンド、マイクロホン/CLFEジャック）を試して検出します

add_stereo_mix_input (ブール型)

ステレオミックス（アナログループバックミックス）を入力MUXに追加します（利用可能な場合）

add_jack_modes (ブール型)

各I/Oジャックに「xxx Jack Mode」エンコード制御を追加し、ヘッドホンアンプおよびマイクバイアスVREFの機能を変更できるようにします

各ウィジェットに対して高度な電源管理を行い、ピンおよびストリーム状態に応じて各ウィジェットノードの電源状態（D0/D3）を制御します

早期パッチング¶

が呼ばれるとき、modprobeは CONFIG_SND_HDA_PATCH_LOADER=y 設定されている場合、HDオーディオ設定を初期化する前にコーデックを変更するための「パッチ」ファイルをファームウェアとして渡すことができます。これは上記のsysfs経由での再構成と同様の動作をしますが、最初のコーデック構成よりも前に実行されます

パッチファイルは以下のように見える plain text ファイルです

[codec]
0x12345678 0xabcd1234 2

[model]
auto

[pincfg]
0x12 0x411111f0

[verb]
0x20 0x500 0x03
0x20 0x400 0xff

[hint]
jack_detect = no

ファイルには1行 [codec]が必要です。次の行には、コーデックベンダーID（例: 0x12345678）、コーデックサブシステムID（例: 0xabcd1234）およびコーデックのアドレス（例: 2）の3つの数値を記載します。後続のパッチエントリはこの指定されたコーデックに適用され、別のコーデックエントリが指定されるまで続きます。最初または第二の値に0または負数を渡すと、対応するフィールドのチェックがスキップされます。これはSSIDを適切に初期化しない非常に破損したデバイスに有効です

以下の [model] 行は各コーデックのモデル名を変更します。上記の例ではmodel=autoに変更されます。注意: この設定はモジュールオプションを上書きします

構造体が作成された後で、 [pincfg] 行では、以下の通りuser_pin_configs sysfsファイルで表示されるように、初期デフォルトピン構成が解析されます user_pin_configs sysfs 上記と同様に解析され、ユーザー_pin_configs sysfs ファイルでも表示されます

Similarly, the lines after [verb] は init_verbs sysfs エントリとして解析され、 [hint] は hints sysfs エントリとしてそれぞれ解析されます

コーデックベンダーIDを0x12345678から0xdeadbeefに上書きする例は以下の通りです

[codec]
0x12345678 0xabcd1234 2

[vendor_id]
0xdeadbeef

同様の方法で、コーデックサブシステムIDを [subsystem_id]経由して上書きできます。また、リビジョンIDは [revision_id] 行で、コーデックチップ名は [chip_name] 行で上書きできます

[codec]
0x12345678 0xabcd1234 2

[subsystem_id]
0xffff1111

[revision_id]
0x10

[chip_name]
My-own NEWS-0002

hd-audioドライバはファイルを request_firmware()したがって、パッチファイルは適切なファームウェアパスに配置する必要があります。通常は/lib/firmwareです。たとえば、オプションを渡す場合、 patch=hda-init.fwファイル/lib/firmware/hda-init.fwが存在している必要があります。

パッチモジュールオプションは各カードインスタンスごとに特定され、各インスタンスに対してファイル名をコンマで区切って指定する必要があります。たとえば、2つのカードがある場合、1つはオンボードアナログ用、もう1つはHDMIビデオボード用であれば、以下のようにパッチオプションを指定できます：

options snd-hda-intel patch=on-board-patch,hdmi-patch

電源節約¶

電源節約はデバイスの自動スリープの一種です。デバイスが一定時間アクティブでない場合、電源を自動的に切って電力を節約します。電源を切るまでの時間は power_save モジュールオプションで指定され、このオプションはsysfs経由で動的に変更可能です。

一部のコーデックでアナログループバックが有効になっている場合、電源節約は動作しません。電源節約を有効にする場合は、不要な信号ルートをすべてミュートしてください。

電源節約機能は、デバイスによっては電源ON/OFF時に音のクリック音を発生させる可能性があります。一部は解決可能ですが、一部は難しいかもしれません。openSUSEなどのディストロでは電源ケーブルを外したときに電源節約機能を自動的に有効にする場合があります。そのため、クリック音が聞こえる場合はまず電源節約機能を疑ってください。/sys/module/snd_hda_intel/parameters/power_saveで現在の値を確認してください。値がゼロでなければ機能が有効になっています。

最近のカーネルではHDオーディオコントローラーチップにもランタイムPMがサポートされています。これはHDオーディオコントローラーも動的に電源をON/OFFする機能を意味します。この機能はIntel LynxPointなどの特定のコントローラーチップにのみ有効です。この機能を強制的に有効/無効にするには、 power_save_controller オプションを設定します。これはまた/sys/module/snd_hda_intel/parametersディレクトリでも利用可能です。

トレースポイント¶

hd-audioドライバーはいくつかの基本的なトレースポイントを提供します。 hda:hda_send_cmd CORB書き込みをトレースしますながら hda:hda_get_response RIRBからの応答をトレースします（コーデックドライバーから読み取る場合のみ）。 hda:hda_bus_reset 致命的なエラーなどによるバスリセットをトレースしますなど、 hda:hda_unsol_event 非依頼イベントをトレースしますなど、 hda:hda_power_down および hda:hda_power_up 電源節約動作による電源ON/OFFをトレースします。

すべてのトレースポイントを有効にするには、

# echo 1 > /sys/kernel/debug/tracing/events/hda/enable

その後、いくつかのコマンドを実行した後、/sys/kernel/debug/tracing/traceファイルからトレースデータを取得できます。たとえば、どのコーデックコマンドが送信されるかをトレースする場合は、以下のようにトレースポイントを有効にします：

# cat /sys/kernel/debug/tracing/trace
# tracer: nop
#
#       TASK-PID    CPU#    TIMESTAMP  FUNCTION
#          | |       |          |         |
       <...>-7807  [002] 105147.774889: hda_send_cmd: [0:0] val=e3a019
       <...>-7807  [002] 105147.774893: hda_send_cmd: [0:0] val=e39019
       <...>-7807  [002] 105147.999542: hda_send_cmd: [0:0] val=e3a01a
       <...>-7807  [002] 105147.999543: hda_send_cmd: [0:0] val=e3901a
       <...>-26764 [001] 349222.837143: hda_send_cmd: [0:0] val=e3a019
       <...>-26764 [001] 349222.837148: hda_send_cmd: [0:0] val=e39019
       <...>-26764 [001] 349223.058539: hda_send_cmd: [0:0] val=e3a01a
       <...>-26764 [001] 349223.058541: hda_send_cmd: [0:0] val=e3901a

ここでは [0:0] カード番号とコーデックアドレスを示し、 val コードックに送信される値を示しています。この値はパックされた値であり、hda-emuパッケージに含まれるhda-decode-verbプログラムを用いてデコードできます。例えば、e3a019という値は左出力アンプの値を25に設定します。

% hda-decode-verb 0xe3a019
raw value = 0x00e3a019
cid = 0, nid = 0x0e, verb = 0x3a0, parm = 0x19
raw value: verb = 0x3a0, parm = 0x19
verbname = set_amp_gain_mute
amp raw val = 0xa019
output, left, idx=0, mute=0, val=25

デバッグツール¶

このセクションではHD-audioの問題をデバッグするためのツールについて説明します。

alsa-info¶

スクリプト alsa-info.sh オーディオデバイス情報を収集するための非常に役立つツールです。これはalsa-utilsパッケージに含まれています。最新バージョンはgitリポジトリにあります:

  • git://git.alsa-project.org/alsa-utils.git

スクリプトは以下のURLからも直接取得できます:

  • https://www.alsa-project.org/alsa-info.sh

このスクリプトをrootとして実行すると、モジュールリスト、モジュールパラメータ、プロシージャーファイルの内容（コードックプロシージャーファイルを含む）、ミキサー出力、コントロール要素などの重要な情報を収集します。デフォルトでは、これらの情報はalsa-project.orgのウェブサーバーに保存されます。ただし、バグレポートを送る場合は、 --no-upload オプションで実行し、生成されたファイルを添付するのが望ましいです。

他の有用なオプションもあります。詳細は --help オプション出力に記載しています。

プローブエラーが発生した場合、またはドライバが明らかに不一致なモデルを割り当てている場合、ドライバを probe_only=1 オプション（できれば冷起動後に）でロードし、この状態でalsa-infoを実行すると役立ちます。このオプションを使用すると、ドライバはミキサーおよびPCMを設定せず、コードックスロットのプローブにのみ焦点を当てます。プローブ後、プロシージャーファイルが利用可能になるため、ドライバによって変更される前のコードック情報が取得できます。もちろん、このオプションではドライバは使用できません。 probe_only=1ただし、hda-reconfig オプションが有効になっている場合、hwdep sysfs ファイルを介して設定を続行できます。Using probe_only mask 2 は HDA コーデックのリセットをスキップします（use probe_only=3 モジュールオプションとして使用

hda-verb¶

hda-verb は、HD-audio コーデックに直接アクセスできる小さなプログラムです。このプログラムを使用すると、raw HD-audio コーデックのバーブを実行できます。このプログラムは hwdep デバイスにアクセスするため、カーネルの設定を有効にする必要があります CONFIG_SND_HDA_HWDEP=y 事前に処理されます

hda-verb プログラムは4つの引数を取ります：hwdep デバイスファイル、ウィジェット NID、バーブ、およびパラメータ。カード0のスロット2にあるコーデックにアクセスする場合、通常は /dev/snd/hwC0D2 を1番目の引数として渡します（ただし、実際のパス名はシステムによって異なります）。

2番目の引数はアクセスするウィジェットの番号IDです。3番目の引数は、16進数/数字の数値か、バーブに対応する文字列のいずれかです。同様に、4番目の引数は書き込む値か、パラメータタイプに対応する文字列です。

% hda-verb /dev/snd/hwC0D0 0x12 0x701 2
nid = 0x12, verb = 0x701, param = 0x2
value = 0x0

% hda-verb /dev/snd/hwC0D0 0x0 PARAMETERS VENDOR_ID
nid = 0x0, verb = 0xf00, param = 0x0
value = 0x10ec0262

% hda-verb /dev/snd/hwC0D0 2 set_a 0xb080
nid = 0x2, verb = 0x300, param = 0xb080
value = 0x0

このプログラムで任意のバーブを実行できますが、ドライバの状態は常に更新されません。たとえば、ボリューム値は通常ドライバでキャッシュされており、hda-verb を使ってウィジェットのamp値を直接変更しても、ミキサーの値は変わりません。

hda-verb プログラムは現在 alsa-tools に含まれています：

  • git://git.alsa-project.org/alsa-tools.git

また、古いスタンドアロンパッケージは ftp ディレクトリにあります：

  • ftp://ftp.suse.com/pub/people/tiwai/misc/

また、Gitリポジトリも利用可能です：

  • git://git.kernel.org/pub/scm/linux/kernel/git/tiwai/hda-verb.git

tarball の README ファイルを参照すると、hda-verb プログラムに関する詳細情報が得られます。

hda-emu¶

hda-emuはHDオーディオエミュレータです。このプログラムの主な目的は、実際のハードウェアを使わずにHDオーディオコーデックをデバッグすることです。したがって、実際のオーディオ入出力の挙動をエミュレートするのではなく、HDオーディオドライバのプローブおよび運用中にコーデックレジスタの変化やALSAドライバ内部の変化をダンプします。

このプログラムはコーデックプロセスファイルをシミュレートするために必要です。対象のコーデック用のプロセスファイルを事前に取得するか、tarball内のコーデックプロセスコレクションから例を取得してから、プログラムをプロセスファイルとともに実行してください。これにより、hda-emuがコーデックファイルを解析し、HDオーディオドライバをシミュレートします。

% hda-emu codecs/stac9200-dell-d820-laptop
# Parsing..
hda_codec: Unknown model for STAC9200, using BIOS defaults
hda_codec: pin nid 08 bios pin config 40c003fa
....

このプログラムは非常にシンプルなコマンドラインインターフェースのみを提供します。現在の状態でのプロセスファイルダンプを取得したり、コントロール（ミキサー）要素の一覧を取得したり、コントロール要素の値を設定/取得したり、PCMの操作をシミュレートしたり、ジャック挿抜をシミュレートしたりできます。

このプログラムは以下のgitリポジトリにあります：

  • git://git.kernel.org/pub/scm/linux/kernel/git/tiwai/hda-emu.git

hda-emuプログラムについての詳細は、リポジトリ内のREADMEファイルを参照してください。

hda-jack-retask¶

hda-jack-retaskは、ジャックリタスク用にHDオーディオピンコントロールを操作するためのユーザー向けGUIプログラムです。ジャック割当に関する問題がある場合は、このプログラムを使用して有用な結果が得られるか確認してください。正しいピン割当を特定した後は、ドライバコード内で静的に修正するか、ファームウェアパッチファイルを渡すことで修正できます（「早期パッチング」セクションを参照）。

このプログラムは現在alsa-toolsに含まれています：

  • git://git.alsa-project.org/alsa-tools.git

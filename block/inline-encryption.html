インライン暗号化¶

背景¶

インライン暗号化ハードウェアはメモリとディスクの論理的な間に位置し、ディスクへのデータの入出時に暗号化・復号化を行うことができます。インライン暗号化ハードウェアには固定された「keyslot（鍵スロット）」の数があり、このスロットにカーネルがいつでも暗号化コンテキスト（つまり暗号化鍵、暗号アルゴリズム、データ単位サイズなど）を設定できます。ディスクへの要求にkeyslotのインデックス（および暗号化用のデータ単位番号を含む）を付与することで、インライン暗号化ハードウェアはそのkeyslotに設定された暗号化コンテキストで要求データを暗号化・復号化します。これは、自己暗号化ドライブ/TCG OPAL/ATAセキュリティ規格などのフルディスク暗号化ソリューションとは大きく異なり、インライン暗号化ではカーネルが選ぶ任意の暗号化コンテキストでディスク上の任意のブロックを暗号化できます。

目的¶

カーネル内にインライン暗号化（IE）をサポートしたいと考えています。テストのためには、実際のIEハードウェアが存在しない場合でもcrypto APIのフォールバックを提供したいです。また、dmやループバックなどのレイヤードデバイスとIEが動作することも求めています（つまり、下位デバイスにIEハードウェアが存在する場合にそれを使用し、なければcrypto APIによる暗号化・復号化にフォールバックするようにします）。

制約と注意点¶

  • IEハードウェアには、いつでも暗号化コンテキスト（鍵、アルゴリズム、データ単位サイズなど）を設定できる「keyslot（鍵スロット）」の数が限られています。デバイスへのデータ要求にkeyslotを指定することで、デバイスはそのkeyslotに設定された暗号化コンテキストでデータを暗号化・復拡します。可能であれば、同じ暗号化コンテキストで複数の要求を同じkeyslotを共有したいです。

  • ファイルシステムなどの上位レイヤーがstruct bioの暗号化・復号に使用する暗号化コンテキストを指定できる仕組みが必要です。また、UFSなどのデバイスドライバーは、その暗号化コンテキストをbioの処理時に使用できる必要があります。

  • デバイスドライバーが上位レイヤーに統一してインライン暗号化の機能を公開できる仕組みが必要です。

設計¶

上位レイヤー（例：ファイルシステム層）からデバイスドライバーに暗号化コンテキストを渡すために、struct bioにstruct bio_crypt_ctxを追加しました。

IEハードウェアはkeyslotの概念に基づいて動作しますが、ファイルシステム層はkeyslotの知識を持ちません。ファイルシステム層は単にbioの暗号化・復号に使用する暗号化コンテキストを指定したいだけです。

FSが指定する暗号化コンテキストをIEハードウェアのキースロットに変換するためのキースロットマネージャー（KSM）を紹介します。このKSMは、IEハードウェアが上位レイヤーに自身の機能を提供するためのインターフェースとしても機能します。一般的な動作モードは、IEをサポートしたいデバイスドライバーがKSMを構築し、struct request_queueに設定します。その後、このデバイスでIEを使用したい上位レイヤーは、デバイスのstruct request_queue内のこのKSMを使用して暗号化コンテキストをキースロットに変換します。request queueにKSMが存在することを意味するのは、デバイスがIEをサポートしていることです。

KSMは参照カウントを使用して、キースロットがアイドル状態かどうかを追跡します（暗号化コンテキストがプログラムされていないか、またはそのキースロットを参照しているstruct biosがありません）。新しい暗号化コンテキストがキースロットを必要とする場合、同じ暗号化コンテキストですでにプログラムされたキースロットを探します。見つからない場合は、最も最近使用されていないアイドルキースロットを追い出し、新しい暗号化コンテキストをそのキースロットにプログラムします。アイドルキースロットが利用できない場合は、呼び出し元が待機状態になるまで待機します。

blk-mqの変更、その他のブロックレイヤーの変更およびblk-crypto-fallback¶

を導入します。 block/blk-crypto-fallback.c上位レイヤーが実際のインライン暗号化ハードウェアが存在するかどうかを気にすることなく動作できるようにします。bioがターゲット request_queue で指定された暗号化コンテキストをサポートしていない場合、ブロックレイヤーはblk-crypto-fallbackを使用してbioを暗号化または復号します。

bioが WRITE bioの場合、バウンスbioが割り当てられ、bio内のデータがバウンスbioに暗号化して保存されます。その後、blk-mqはバウンスbioを暗号化されていないものとして処理します（blk-integrityに関係なく）。 blk-crypto-fallback バウンスbioの bi_end_io を内部関数に設定し、バウンスbioをクリーンアップして元のbioを終了します。

bioが READ bioの場合、bioの bi_end_io (および bi_private)は保存され、 blk-crypto-fallback に（木の下から葉に向かって） bio_crypto_fallback_decrypt_bioによって上書きされます。bioの bi_crypt_context も NULLに上書きされるため、スタックの他の部分にはこのbioが通常のbioのように見えるようにします。 bio_crypto_fallback_decrypt_bio はbioを復号し、元の bi_end_io (および bi_private)を復元してbioを再び終了します。

リアルタイム暗号化ハードウェアが使用されても、blk-crypto-fallbackが使用されても、ディスクに書き込まれる暗号文（したがってデータのディスク上の形式）は同じになります（ハードウェアが使用するアルゴリズムの実装が仕様に準拠し、正しく動作していると仮定します）。

If a request queueのインライン暗号化ハードウェアがbioで指定された暗号文脈をサポートすると主張している場合、それは blk-crypto-fallbackによって処理されません。最終的にblk-mqにおいて、そのbioに対応するstruct requestが割り当てられる時点で、blk-mqは暗号文脈を request_queueのkeyslot_managerにプログラミングし、keyslotを取得して、新たに追加された keyslot フィールドに保存します。このkeyslotはリクエストが完了したときに解放されます。

リクエストに最初のbioが追加されたとき、 blk_crypto_rq_bio_prep が呼び出され、リクエストの crypt_ctx がbioの bi_crypt_contextのコピーに設定されます。その後のbioがリクエストの前面にマージされるたびにbio_crypt_do_front_mergeが呼び出され、リクエストの crypt_ctx が新たにマージされたbioの bi_crypt_contextに更新されます。特に、リクエストはbioリストに最初のbioの bi_crypt_context を保持しています（blk-mqはbioおよびリクエストのマージ中にこの不変性を維持する必要があります）。

インライン暗号化がリクエストキューベースのレイヤードデバイスと互換性を持つためには、リクエストがクローンされるとき、その crypto fields もクローンされます。クローンされたリクエストが送信されるとき、blk-mqはリクエストの bi_crypt_context をクローンのリクエストキューのkeyslotマネージャーにプログラミングし、返されたkeyslotをクローンの keyslot.

デバイスドライバーに提示されるAPI¶

は、デバイスのstruct blk_keyslot_manager でデバイスドライバーが設定する必要があります。デバイスドライバーは、ハードウェアがサポートするキースロット数を指定して、 request_queue を呼び出す必要があります。 blk_ksm_init （またはそのリソース管理バリアント devm_blk_ksm_init）を blk_keyslot_managerに呼び出します。

デバイスドライバーはまた、KSMにIEハードウェアを操作する方法を伝える必要があります（例：暗号キーを特定のキースロットにプログラミング）。すべての操作は、デバイスドライバーが初期化した blk_keyslot_manager.

のstruct blk_ksm_ll_opsフィールドを通じて実現されます。 dev KSMは、必要に応じてデバイスのランタイム電源管理を処理します（例：暗号キーをIEハードウェアにプログラミングする際、デバイスはランタイム電源がオンになっている必要があります）。そのため、デバイスドライバーは、KSMにランタイム電源管理に使用する struct device を指す

blk_ksm_reprogram_all_keys が呼ばれる必要があります。この関数は、デバイスが関数呼び出し時点での「正しい」キーですべてのキースロットを再プログラミングする必要がある場合にデバイスドライバーによって呼び出されます。これは、デバイスがランタイム電源のON/OFF時にすべてのキーを失った場合などに役立ちます。

レイヤードデバイス¶

dm-rqなどのリクエストキューを基盤とするレイヤードデバイスで、IEをサポートしたい場合、各自でキースロットマネージャーを実装し、必要な機能を公開する必要があります。レイヤードデバイスが別のデバイスにリクエストのクローンを渡す場合、blk-cryptoは必要に応じてクローンを初期化・準備します。詳しくは request_queueFuture Optimizations for layered devices blk_crypto_insert_cloned_request の blk-crypto.c.

レイヤードデバイス用のキースロットマネージャーを作成すると、各キースロットにメモリが消費されますが、一般的にレイヤードデバイスはリクエストを「子」デバイスに単純に転送するため、自身のキースロットは一切使用されず、参照カウントやキースロットプログラミングも必要ありません。代わりに、レイヤードデバイスが無限のキースロット数をアドバタイズし、選ぶ暗号アルゴリズムをサポートできる「透過型キースロットマネージャー（passthrough KSM）」という新しいタイプのKSMを定義できます。これにより、各キースロットにメモリを一切使用しないことが可能です。また、「透過型キースロットマネージャー」は、キースロット数が制限されていないIEデバイスにも利用できます。¶

インライン暗号化とblk整合性の相互作用

このパッチ時点では、これら2つの機能をサポートする現実のハードウェアは存在しません。しかし、これらの機能は相互に影響し合い、両方を正しく動作させるのは完全に単純ではありません。特に、インライン暗号化をサポートするデバイスでWRITE bioが暗号化を実行する場合、bioに暗号化コンテキストが指定され、その後整合性情報が計算されます（暗号化はデータが書き込まれる際に行われるため、平文データを使用して計算されます）。この整合性情報とデータはデバイスに送信されます。明らかに、データが暗号化される前に整合性情報が検証される必要があります。データが暗号化されると、デバイスは平文データとともに受信した整合性情報を保存すべきではありません（これにより平文データの情報が漏洩する可能性があります）。したがって、デバイスは暗号化後のデータから整合性情報を再生成し、ディスクに保存する必要があります。また、平文データの整合性情報を保存するもう一つの問題は、ハードウェアインライン暗号化サポートがあるか、カーネル暗号APIのフォールバックが使用されるかによって、ディスク上のフォーマットが変化することです（フォールバックが使用される場合、デバイスは暗号化後のデータの整合性情報を受信します）。¶

参照

現時点では実際のハードウェアが存在していないため、ハードウェア実装が両方の機能を正しく同時に実装しない可能性を慎重に想定し、一時的に組み合わせを禁止する方が適切であると考えられる。デバイスが整合性をサポートしている場合、カーネルはそのデバイスがハードウェア内蔵暗号化をサポートしていないと装う（実質的にデバイスのrequest_queue内のkeyslot managerをNULLに設定する）。crypto APIのフォールバックが有効な場合、すべての暗号化コンテキストを持つBIOSはフォールバックを使用し、IOは通常通り完了する。フォールバックが無効な場合、暗号化コンテキストを持つBIOSは失敗する。

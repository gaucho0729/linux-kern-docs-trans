データの整合性¶

1. はじめに¶

現代のファイルシステムはデータおよびメタデータのチェックサムを用いてデータ破損を防ぐ機能を備えています。しかし、破損の検出は読み込み時に実施されるため、データが書き込まれた数か月後になってから発覚する可能性があります。その時点でアプリケーションが書き込もうとした元データはほぼ確実に失われています。

解決策は、ディスクがアプリケーションが意図したデータを実際に保存していることを保証することです。SCSIファミリプロトコル（SBC Data Integrity Field、SCC保護提案）およびSATA/T13（External Path Protection）においても、I/Oに整合性メタデータを追加することでこの問題を改善しようとしています。整合性メタデータ（SCSIでは保護情報と呼ばれる）には各セクタのチェックサムと、セクタが正しい順序で書き込まれることを保証するインクリメントカウンタが含まれます。一部の保護スキームでは、I/Oがディスク上の正しい場所に書き込まれることも保証されます。

現在のストレージコントローラーおよびデバイスは、チェックサムやスクラブビングなどのさまざまな保護機能を実装しています。しかし、これらの技術はそれぞれ独立したドメインで動作しているか、あるいはI/Oパスの隣接ノード間でのみ動作しています。DIFやその他の整合性拡張機能の興味深い点は、保護フォーマットが明確に定義されており、I/OパスのすべてのノードがI/Oの整合性を検証し、破損を検出すれば拒否できる点です。これにより、データ破損の防止だけでなく、故障点の分離も可能になります。

2. データの整合性拡張機能¶

プロトコル拡張機能は現在、コントローラーとストレージデバイス間のパスを保護するように設計されています。しかし、多くのコントローラーはオペレーティングシステムが整合性メタデータ（IMD）と相互作用できるようにします。我々は複数のFC/SAS HBAベンダーと協力し、保護情報がそのコントローラーに送信・受信されるようにする機能を実装しています。

SCSI Data Integrity Fieldは、各セクタに8バイトの保護情報を追加することで動作します。データ＋整合性メタデータはディスク上に520バイトのセクタとして保存されます。コントローラーとターゲット間でデータ＋IMDは交差して転送されます。T13の提案も同様です。

オペレーティングシステムが520（および4104）バイトセクタを扱うのが非常に不便であるため、我々は複数のHBAベンダーに協力を求め、データと整合性メタデータのスキャッターガatherリストを分離できるようにする機能を実装するよう奨励しました。

コントローラーは、書き込み時にバッファを交互に配置し、読み込み時に分割して処理します。これにより、Linuxはページキャッシュの変更なしにホストメモリとデータバッファ間でDMAを実行できます。

また、SCSIおよびSATA仕様で義務付けられている16ビットCRCチェックサムの計算はソフトウェアでは比較的重い処理です。ベンチマークでは、このチェックサムの計算が複数のワークロードにおいてシステムパフォーマンスに大きな影響を与えることが確認されました。一部のコントローラーは、オペレーティングシステムとのインターフェースで軽量なチェックサムを使用できるようにしています。例えば、EmulexはTCP/IPチェックサムを使用します。OSから受信したIPチェックサムは、書き込み時に16ビットCRCに変換され、読み込み時には逆を行います。これにより、Linuxやアプリケーションが低コストで整合性メタデータを生成できるようになります（ソフトウェアRAID5と同等のコストです）。

IPチェックサムはCRCよりもビット誤りの検出能力は弱いですが、データバッファと整合性メタデータの分離が本質的な強さです。これらの2つの異なるバッファは、I/Oが完了するためには一致しなければなりません。

データと整合性メタデータのバッファを分離し、チェックサムの選択肢を提供する仕組みは「データ整合性拡張機能」と呼ばれます。これらの拡張機能はプロトコル本体（T10、T13）の範囲外であるため、Oracleおよびパートナーはストレージネットワーキング業界協会（SNIA）内で標準化を進めています。

3. カーネルの変更¶

Linuxのデータ整合性フレームワークは、保護情報がI/Oに固定され、サポートするコントローラーと通信する際の送受信が可能になります。

SCSIおよびSATAの整合性拡張機能の利点は、アプリケーションからストレージデバイスまでの全体パスを保護できる点です。しかし同時にこれが最大の欠点でもあります。つまり、保護情報はディスクが理解できる形式でなければなりません。

一般的にLinux/POSIXアプリケーションは、アクセスしているストレージデバイスの詳細な仕様には無関心です。仮想ファイルシステムスイッチやブロックレイヤーによって、ハードウェアセクタサイズやトランスポートプロトコルなどの詳細はアプリケーションには完全に透明です。

しかし、ディスクに保護情報を送信する際にはこのレベルの詳細が必要になります。したがって、端到端保護スキームという概念自体がレイヤーの違反です。アプリケーションがSCSIまたはSATAディスクにアクセスしているかを意識するというのは完全に現実的ではありません。

Linuxで実装されたデータの整合性サポートは、アプリケーションからこの情報を隠蔽しています。アプリケーション（ある程度の範囲ではカーネルも）にとっては、整合性メタデータはI/Oに添付される不透明な情報とみなされます。

現在の実装では、ブロックレイヤーが任意のI/Oに対して保護情報の自動生成を許可しています。最終的には、ユーザー空間に整合性メタデータの計算を移行する予定です。メタデータやカーネル内部から発生するその他のI/Oについては、自動生成インターフェースを引き続き使用します。

一部のストレージデバイスでは、ハードウェアセクタごとに16ビットの値をタグとして割り当てることができます。このタグ領域の所有者はブロックデバイスの所有者（通常はファイルシステム）です。ファイルシステムは必要に応じてセクタにタグを自由に割り当てることができます。タグ領域は限られているため、ブロックインターフェースではインターリーブによってより大きなブロックにタグを割り当てることができます。これにより、通常の4KBファイルシステムブロックに8×16ビットの情報が添付されます。

これにより、fsckやmkfsなどのアプリケーションもユーザー空間からタグを操作する必要があります。このための透過インターフェースの実装が進行中です。

4. ブロックレイヤーの実装詳細¶

4.1 Bio¶

データの整合性パッチは、CONFIG_BLK_DEV_INTEGRITYが有効な場合、struct bioに新しいフィールドを追加します。bio_integrity(bio)は、struct bipへのポインタを返し、これは整合性ペイロードを含むstruct bioです。要するに、bipは簡略化されたstruct bioで、整合性メタデータを含むbio_vecと必要な管理情報（bvecプール、ベクター数など）を保持します。

カーネルサブシステムは、bio_integrity_alloc(bio)を呼び出して、bioにデータ整合性保護を有効化できます。これにより、bipが割り当てられ、bioに添付されます。

個々の整合性メタデータを含むページは、bio_integrity_add_page()を呼び出して後で添付できます。

bio_free()は自動的にbipを解放します。

4.2 ブロックデバイス¶

保護データの形式は物理ディスクに依存するため、各ブロックデバイスにブロック整合性プロファイル（struct blk_integrity）が拡張されました。このオプションのプロファイルは、ブロックレイヤーに以下のように登録されます。 blk_integrity_register().

プロファイルには、保護データの生成・検証に使用するコールバック関数、アプリケーションタグの取得・設定に使用する関数が含まれます。また、整合性メタデータの完了・マージ・スプリットを支援するためのいくつかの定数も含まれています。

レイヤードブロックデバイスは、すべてのサブデバイスに適したプロファイルを選択する必要があります。 blk_integrity_compare() その問題は解決できます。DMおよびMDのラインアライメント、RAID0およびRAID1は現在サポートされています。RAID4/5/6はアプリケーションタグのため追加の作業が必要です。

5.0 ブロックレイヤー整合性API¶

5.1 通常のファイルシステム¶

通常のファイルシステムは、基盤となるブロックデバイスが整合性メタデータを送受信できるという情報を把握していません。ブロックレイヤーがWRITE時のタイミングで自動的にIMDを生成します。 submit_bio() READリクエストは、完了時にI/O整合性を検証します。

IMDの生成および検証は次のコマンジを使用して切り替えられます：

/sys/block/<bdev>/integrity/write_generate

および：

/sys/block/<bdev>/integrity/read_verify

フラグを確認します。

5.2 整合性を意識したファイルシステム¶

整合性を意識したファイルシステムは、IMDを添付したI/Oを準備できます。ブロックデバイスがサポートする場合、アプリケーションタグ領域も利用可能です。

bool bio_integrity_prep(bio);

WRITE用のIMDを生成し、READ用のバッファを設定するには、ファイルシステムがbio_integrity_prep(bio)を呼び出す必要があります。

この関数を呼び出す前に、bioデータの方向と開始セクタを設定し、bioにすべてのデータページを追加しておく必要があります。I/Oが進行中にbioが変更されないことを呼び出し元が保証する必要があります。準備に失敗した場合はエラーで完了するbioを返します。

5.3 既存の整合性メタデータの渡し方¶

自身で整合性メタデータを生成するか、ユーザー空間からIMDを転送できるファイルシステムは、以下の関数を使用できます：

struct bip * bio_integrity_alloc(bio, gfp_mask, nr_pages);

bioの整合性ペイロードを割り当て、bioに接続します。nr_pagesは、整合性bio_vecリストに保存する保護データのページ数を示します（bio_alloc()と同様）。

整合性ペイロードはbio_free()のタイミングで解放されます。

int bio_integrity_add_page(bio, page, len, offset);

既存のbioに整合性メタデータを含むページを接続します。bioには既存のbipが必要であり、bio_integrity_alloc()が呼び出されている必要があります。WRITEの場合、ページ内の整合性メタデータはターゲットデバイスが理解できる形式でなければなりません。ただし、I/Oスタックを通過する際のセクタ番号は再マッピングされるため、この関数で追加したページはI/O中に変更される可能性があります！整合性メタデータの最初の参照タグはbip->bip_sectorの値を保つ必要があります。

bip bio_vec配列に空きがある限り（nr_pages）、bio_integrity_add_page()を使用してページを追加できます。

READ操作が完了した後、添付されたページにはストレージデバイスから受信した整合性メタデータが含まれます。整合性の検証は受信者が行い、操作完了時にデータの整合性を確認する必要があります。

5.4 ブロックデバイスを整合性メタデータの交換が可能なデバイスとして登録する¶

ブロックデバイスで整合性交換を有効にするには、gendiskがcapableとして登録する必要があります:

int blk_integrity_register(gendisk, blk_integrity);

blk_integrity構造体はテンプレートであり、以下の項目を含める必要があります:

static struct blk_integrity my_profile = {
    .name                   = "STANDARDSBODY-TYPE-VARIANT-CSUM",
    .generate_fn            = my_generate_fn,
    .verify_fn              = my_verify_fn,
    .tuple_size             = sizeof(struct my_tuple_size),
    .tag_size               = <tag bytes per hw sector>,
};

「name」はsysfsで表示されるテキスト文字列です。これはユーザーランドAPIの一部なので、慎重に選び、変更してはいけません。形式は標準機関-型-変異体です。例: T10-DIF-TYPE1-IPやT13-EPP-0-CRCなど。

「generate_fn」は適切な整合性メタデータ（WRITE用）を生成します。

「verify_fn」はデータバッファが整合性メタデータと一致することを確認します。

「tuple_size」はセクタあたりの整合性メタデータのサイズに合わせて設定する必要があります。つまり、DIFおよびEPPでは8です。

「tag_size」はハードウェアセクタあたりに利用可能なタグ領域のバイト数を識別するため、設定する必要があります。DIFの場合、制御モードページのATOビットの値によって2または0になります。

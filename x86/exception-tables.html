5. カーネルレベルの例外処理¶

Joerg Pommnitz による解説 <joerg@raleigh.ibm.com>

プロセスがカーネルモードで実行されている場合、信頼できないプログラムから渡されたアドレスを持つユーザーモードメモリにアクセスする必要がある。カーネルは自身を保護するため、このアドレスを検証する必要がある。

古いバージョンのLinuxでは、int verify_area(int type, const void * addr, unsigned long size)関数を使用していた（これは以降、置き換えられている）。 access_ok()).

この関数は、アドレス‘addr’から始まり、サイズ‘size’のメモリ領域がtype（読み取りまたは書き込み）でアクセス可能かどうかを検証した。verify_readは、アドレスaddrを含む仮想メモリ領域（vma）を検索する必要があった。通常の状況（正しく動作するプログラム）では検証が成功したが、一部のバグのあるプログラムでは失敗した。一部のカーネルプロファイリングテストでは、通常不要なこの検証が相当な時間を消費していた。

この状況を克服するため、リンスはすべてのLinux対応CPUに搭載されている仮想メモリハードウェアにこの検証を任せるように決定した。

これはどのように動作するのでしょうか？

カーネルが現在アクセスできないアドレスを参照しようとするたびに、CPUはページフォルト例外を生成し、ページフォルトハンドラを呼び出す：

void do_page_fault(struct pt_regs *regs, unsigned long error_code)

arch/x86/mm/fault.c で。スタック上のパラメータは、arch/x86/entry/entry_32.S にある低レベルのアセンブリコードによって設定される。regs パラメータは、スタック上の保存されたレジスタへのポインタで、error_code は例外の理由コードを含む。

do_page_fault はまず、CPUの制御レジスタ CR2 からアクセスできないアドレスを取得する。このアドレスがプロセスの仮想アドレス空間内にある場合、ページがスワップされていない、書き込み保護がかかっているなどの理由でエラーが発生した可能性がある。しかし我々が関心を持つのは別のケースである：アドレスが有効でなく、このアドレスを含む vma が存在しない場合である。この場合、カーネルは bad_area ラベルにジャンプする。

ここで、例外を引き起こした命令のアドレス（つまり regs->eip）を使用して、実行を継続できるアドレス（fixup）を検索する。この検索が成功した場合、エラー処理プログラムは返り先アドレス（再び regs->eip）を修正し、戻る。実行は fixup に記録されたアドレスで再開される。

fixup はどこを指していますか？

fixupの内容にジャンプすると、fixupは明らかに実行可能なコードを指しています。このコードはユーザー アクセスマクロ内に隠されています。例として、arch/x86/include/asm/uaccess.hで定義されたget_userマクロを選択しました。この定義はやや読みにくいため、プリプロセッサとコンパイラが生成するコードを確認しましょう。詳細な解析のためにdrivers/char/sysrq.c内のget_user呼び出しを選択しました。

何が起きたのでしょうか？アセンブリディレクティブ:

.section .fixup,"ax"
.section __ex_table,"a"

はアセンブラーに次のコードを指定されたELFオブジェクトファイルのセクションに移動するように指示しました。したがって、指令:

3:      movl $-14,%eax
        xorb %dl,%dl
        jmp 2b

はオブジェクトファイルの.fixupセクションに配置され、アドレス:

.long 1b,3b

はオブジェクトファイルの__ex_tableセクションに配置されました。1bと3bはローカルラベルです。ローカルラベル1b（1bは次のラベル1の後方を指す）はエラーが発生する可能性のある指令のアドレス、つまりこの場合ラベル1のアドレスc017e7a5です。元のアセンブリコード：> 1: movb (%ebx),%dl とvmlinuxでのリンク先：> c017e7a5 <do_con_write+e1> movb (%ebx),%dl

ローカルラベル3（再度後方を指す）はエラー処理を行うコードのアドレス、この場合の実際の値はc0199ff5です。元のアセンブリコード：> 3: movl $-14,%eax とvmlinuxでのリンク先：> c0199ff5 <.fixup+10b5> movl $0xfffffff2,%eax

fixupが例外を処理できた場合、制御フローはエラーを引き起こした指令の次の指令、つまりローカルラベル2bに戻る可能性があります。

アセンブリコード:

> .section __ex_table,"a"
>         .align 4
>         .long 1b,3b

は値のペアとして:

>  c01aa7d4 c017c2f6 c0199fe9 c017e7a5 c0199ff5  ................
                              ^this is ^this is
                              1b       3b

例外テーブルのカーネル内でc017e7a5,c0199ff5となります。

では、カーネルモードから発生した適切なvmaが見つからないエラーが発生した場合、実際に何が起こるのでしょうか？

  1. 無効なアドレスへのアクセス:

    > c017e7a5 <do_con_write+e1> movb   (%ebx),%dl

  2. MMUが例外を発生させます

  3. CPUがdo_page_faultを呼び出します

  4. do_page_faultはsearch_exception_tableを呼び出し、regs->eip == c017e7a5をチェックします

  5. search_exception_tableは例外テーブル（つまりELFセクション__ex_tableの内容）内のアドレスc017e7a5を検索し、関連するエラーハンドラコードc0199ff5のアドレスを返します

  6. do_page_faultは自身のリターンアドレスをエラーハンドラコードに変更し、戻ります

  7. エラーハンドリングコードで実行が続きます

    1. EAXは-Fault（==-14）になります

    2. DLはゼロになります（ユーザー領域から「読み取った」値）

    3. 実行はローカルラベル2（エラー発生したユーザーアクセスの直後の命令のアドレス）に戻ります

ステップ8a〜8cは、ある意味でエラーフォーミング命令をエミュレートします

これでほぼ完了です。例を確認すると、なぜ例外ハンドラコードでEAXを-Faultに設定しているのか疑問に思うかもしれません。get_userマクロは実際には値を返します：ユーザーアクセスが成功した場合は0、失敗した場合は-Fault。元のコードではこの戻り値をテストしていませんでしたが、get_userのインラインアセンブリコードは-Faultを返そうと試みています。GCCはこの値をEAXで返すように選択しました

注意: 例外テーブルの構築方法と並び順の関係により、.textセクション内のコードのみ例外を使用してください。他のセクションは例外テーブルが正しく並べられず、例外が失敗します

64ビットサポートがx86 Linuxに追加された際、例外テーブルを32ビットから64ビットに拡張してサイズを倍にするのではなく、テーブル自体からの相対オフセットとしてアドレスを保存するという工夫が使われました。アセンブリコードは以下のように変更されました:

  .long 1b,3b
to:
        .long (from) - .
        .long (to) - .

そして、これらの値を扱うCコードは以下のように絶対アドレスに戻します:

ex_insn_addr(const struct exception_table_entry *x)
{
        return (unsigned long)&x->insn + x->insn;
}

v4.6では例外テーブル項目に「ハンドラ」という新しいフィールドが追加されました。これは32ビット幅で、3番目の相対関数ポインタを含み、以下のいずれかを指します:

  1. int ex_handler_default(const struct exception_table_entry *fixup)

    このケースはただのfixupコードにジャンプする古いケースです

  2. int ex_handler_fault(const struct exception_table_entry *fixup)

    このケースは、エントリ->insnで発生したトラップのエラーフォーマット番号を提供します。ページフォールトとマシンチェックを区別するために使用されます

より多くの関数は簡単に追加できます

CONFIG_BUILDTIME_TABLE_SORT は、ホストユーティリティ scripts/sorttable を使って、カーネルイメージのリンク後に対応する __ex_table セクションをソートする機能を提供します。この機能は、シンボル main_extable_sort_needed を 0 に設定し、起動時の __ex_table セクションのソートを回避します。例外テーブルがソートされている場合、実行時において例外が発生した際には二分探索により迅速に __ex_table のエントリを検索できます。

これは単なる起動時の最適化にとどまらず、一部のアーキテクチャでは起動プロセスの初期段階で例外を処理するためにこのテーブルがソートされている必要があります。例えば、i386 はページングサポートが有効化される前からこの形式の例外処理を活用しています！

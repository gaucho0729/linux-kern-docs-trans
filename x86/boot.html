1. Linux/x86 ブートプロトコル¶

x86プラットフォームでは、Linuxカーネルは比較的複雑なブートコンベンションを使用しています。これは歴史的な要因や、初期の頃にカーネル自体をブートイメージとして扱いたいという希望、複雑なPCメモリモデル、および実モードDOSが主流OSから消え去ったことによるPC業界の期待値の変化などが原因で進化してきました。

現在、以下のLinux/x86ブートプロトコルのバージョンが存在しています。

1.1. メモリレイアウト¶

Image または zImage カーネルで使用される、カーネルローダーの伝統的なメモリマップは通常、以下のようになります:

        |                        |
0A0000  +------------------------+
        |  Reserved for BIOS     |      Do not use.  Reserved for BIOS EBDA.
09A000  +------------------------+
        |  Command line          |
        |  Stack/heap            |      For use by the kernel real-mode code.
098000  +------------------------+
        |  Kernel setup          |      The kernel real-mode code.
090200  +------------------------+
        |  Kernel boot sector    |      The kernel legacy boot sector.
090000  +------------------------+
        |  Protected-mode kernel |      The bulk of the kernel image.
010000  +------------------------+
        |  Boot loader           |      <- Boot sector entry point 0000:7C00
001000  +------------------------+
        |  Reserved for MBR/BIOS |
000800  +------------------------+
        |  Typically used by MBR |
000600  +------------------------+
        |  BIOS use only         |
000000  +------------------------+

bzImage を使用する場合、保護モードのカーネルが 0x100000（"高メモリ"）に再配置され、カーネルの実モードブロック（ブートセクタ、setup、スタック/ヒープ）は 0x10000 から低メモリの終わりまでの任意のアドレスに再配置可能になりました。問題は、プロトコル 2.00 および 2.01 では依然として 0x90000+ のメモリ範囲がカーネルによって内部的に使用されており、プロトコル 2.02 でこの問題が解決されました。

ブートローダーが触れる低メモリの最高点である "メモリ上限" を可能な限り低く保つことが望ましいです。なぜなら、一部の新しい BIOS では低メモリの上部に拡張 BIOS データエリアと呼ばれるかなり大きなメモリ領域を割り当て始めているからです。ブートローダーは "INT 12h" BIOS コールを使用して、利用可能な低メモリの量を確認する必要があります。

残念ながら、INT 12h がメモリ量が十分でないと報告した場合、ブートローダーが行えることはほとんどなく、ユーザーにエラーを報告するしかありません。そのため、ブートローダーは低メモリ内で可能な限り少ないスペースを占有するように設計されるべきです。zImage または古い bzImage カーネルでは 0x90000 セグメントにデータを書き込む必要があるため、ブートローダーは 0x9A000 以上のメモリを使用しないようにする必要があります。多くの BIOS がこのポイントを超えると動作しなくなるためです。

プロトコルバージョンが 2.02 以上の現代の bzImage カーネルでは、以下のメモリレイアウトが推奨されます:

              ~                        ~
              |  Protected-mode kernel |
      100000  +------------------------+
              |  I/O memory hole       |
      0A0000  +------------------------+
              |  Reserved for BIOS     |      Leave as much as possible unused
              ~                        ~
              |  Command line          |      (Can also be below the X+10000 mark)
      X+10000 +------------------------+
              |  Stack/heap            |      For use by the kernel real-mode code.
      X+08000 +------------------------+
              |  Kernel setup          |      The kernel real-mode code.
              |  Kernel boot sector    |      The kernel legacy boot sector.
      X       +------------------------+
              |  Boot loader           |      <- Boot sector entry point 0000:7C00
      001000  +------------------------+
              |  Reserved for MBR/BIOS |
      000800  +------------------------+
              |  Typically used by MBR |
      000600  +------------------------+
              |  BIOS use only         |
      000000  +------------------------+

... where the address X is as low as the design of the boot loader permits.

1.3. ヘッダーのフィールド詳細¶

すべての汎用ブートローダーは、(必須)とマークされたフィールドを書き込む必要があります。カーネルを非標準アドレスでロードするブートローダーは、(reloc)とマークされたフィールドを埋め込みます。他のブートローダーはこれらのフィールドを無視できます。

ゼロでない値に設定されている場合、NULL終端のヒューマンリーダブルなカーネルバージョン番号文字列へのポインタを含み、0x200を引いた値です。これによりユーザーにカーネルバージョンを表示できます。この値は(0x200*setup_sects)未満でなければなりません。

0x1c00  < 15*0x200 (= 0x1e00) but
0x1c00 >= 14*0x200 (= 0x1c00)

0x1c00 >> 9 = 14, So the minimum value for setup_secs is 15.

struct setup_data {
        u64 next;
        u32 type;
        u32 len;
        u8  data[0];
};

ここで、nextはリンクリストの次のノードへの64ビット物理ポインタで、最後のノードのnextフィールドは0です。typeはデータの内容を識別するために使用され、lenはデータフィールドの長さで、dataは実際のペイロードを保持します。

setup_dataは、非常に大きなデータオブジェクトを使用する際には少し使いにくいです。これは、setup_dataヘッダがデータオブジェクトに隣接していなければならないことと、32ビットの長さフィールドを持つことが原因です。しかし、ブートプロセスの中間段階で、カーネルデータが占有しているメモリのどのチャンクかを識別する方法が必要です。

そのため、プロトコル2.15でsetup_indirect構造体とSETUP_INDIRECT型が導入されました：

struct setup_indirect {
  __u32 type;
  __u32 reserved;  /* Reserved, must be set to zero. */
  __u64 len;
  __u64 addr;
};

タイプメンバはSETUP_INDIRECT | SETUP_*型のものです。ただし、SETUP_INDIRECT自身にはできません。なぜなら、setup_indirectをツリー構造にする必要がある場合、パースする必要があるものでスタック領域が限られているブートコンテキストでは多くのスタック領域が必要になるからです。

setup_indirectを使用してSETUP_E820_EXTデータを指す方法の例を示します。この場合、setup_dataとsetup_indirectは以下のようになります：

struct setup_data {
  __u64 next = 0 or <addr_of_next_setup_data_struct>;
  __u32 type = SETUP_INDIRECT;
  __u32 len = sizeof(setup_data);
  __u8 data[sizeof(setup_indirect)] = struct setup_indirect {
    __u32 type = SETUP_INDIRECT | SETUP_E820_EXT;
    __u32 reserved = 0;
    __u64 len = <len_of_SETUP_E820_EXT_data>;
    __u64 addr = <addr_of_SETUP_E820_EXT_data>;
  }
}

注意

SETUP_INDIRECT | SETUP_NONEオブジェクトはSETUP_INDIRECT自身と正しく区別できません。したがって、このようなオブジェクトはブートローダーによって提供されることはできません。

1.4. カーネル情報（kernel_info）¶

ヘッダー間の関係は、さまざまなデータセクションに類似しています：

setup_header = .data boot_params/setup_data = .bss

上記のリストに何が欠けていますか？正解は：

kernel_info = .rodata

我々は長期間、.dataセクションを .rodata や .bss に属すべきだったものに（ab）使用してきました。選択肢がなかったことと、特に初期には慣性のためです。また、BIOSスタブはboot_paramsを作成する責任があるため、BIOSベースのローダーには利用できません（setup_dataは利用可能です）。

setup_headerは、2バイトジャンプフィールドの到達範囲により、構造体の長さフィールドとしても機能するため、それに加えて「hole」構造体boot_params内のサイズを考慮すると、144バイトに永久的に制限されています。現在の長さは119バイトで、これにより25バイトという非常に貴重な領域が残されています。この問題を修正するには、ブートプロトコル全体を再設計する必要がありますが、後方互換性を破るため、現状では解決できません。

boot_params本体は4096バイトに制限されていますが、setup_dataエントリを追加することで任意に拡張可能です。ただし、これは.bssセクションに属するため、カーネルイメージのプロパティを通信するには利用できません。

kernel_infoは、カーネルイメージに関する情報を拡張可能な場所として提供することでこの問題を解決します。読み取り専用ですが、ブートローダーがコンテンツをどこかにコピーするのをカーネルが依頼できないためです。ただし、必要になった場合は、有効なブートローダーがsetup_dataチャンクにコピーする予期されるデータ項目を含めることも可能です。

すべてのkernel_infoデータはこの構造体に含まれるべきです。固定サイズのデータはkernel_info_var_len_dataラベルの前、可変サイズのデータはそのラベルの後ろに配置する必要があります。各可変サイズデータは、ヘッダ/マジックとそのサイズで前導する必要があります。例えば：

kernel_info:
        .ascii  "LToP"          /* Header, Linux top (structure). */
        .long   kernel_info_var_len_data - kernel_info
        .long   kernel_info_end - kernel_info
        .long   0x01234567      /* Some fixed size data for the bootloaders. */
kernel_info_var_len_data:
example_struct:                 /* Some variable size data for the bootloaders. */
        .ascii  "0123"          /* Header/Magic. */
        .long   example_struct_end - example_struct
        .ascii  "Struct"
        .long   0x89012345
example_struct_end:
example_strings:                /* Some variable size data for the bootloaders. */
        .ascii  "ABCD"          /* Header/Magic. */
        .long   example_strings_end - example_strings
        .asciz  "String_0"
        .asciz  "String_1"
example_strings_end:
kernel_info_end:

このようにしてkernel_infoは自己完結的なバイナリブロブになります。

注意

各可変サイズデータのヘッダ/マジックは、末尾に0が含まれない4文字の文字列で、既存の可変長データヘッダ/マジックと衝突しないようにします。

1.6. イメージチェックサム¶

ブートプロトコルバージョン2.08以降、CRC-32は特徴多項式0x04C11DB7と初期余り0xffffffffを使用してファイル全体を計算します。チェックサムはファイル末尾に追加されるため、syssizeフィールドで指定された制限までのファイルのCRCは常に0になります。

1.7. カーネルコマンドライン¶

カーネルコマンドラインは、ブートローダーがカーネルと通信するための重要な手段となっています。一部のオプションはブートローダー自体にも関係しており、下記の「特殊なコマンドラインオプション」を参照してください。

カーネルコマンドラインはNULL終端文字列です。最大長はcmdline_sizeフィールドから取得できます。プロトコルバージョン2.06以前では最大255文字でした。長すぎる文字列はカーネルが自動的に切り捨てます。

ブートプロトコルバージョンが2.02以上の場合、カーネルコマンドラインのアドレスはヘッダーフィールドcmd_line_ptr（上記参照）で指定されます。このアドレスは、セットアップヒープの終端から0xA0000の間のどこでも可能です。

プロトコルバージョンが ではありません 2.02以上の場合、以下のプロトコルを使用してカーネルコマンドラインを入力します。

  • オフセット0x0020（ワード）の「cmd_line_magic」にマジックナンバー0xA33Fを入力します。

  • オフセット0x0022（ワード）の「cmd_line_offset」にカーネルコマンドラインのオフセット（実モードカーネルの開始位置からの相対位置）を入力します。

  • カーネルコマンドライン grace periodsを尊重しなければなりませんし、 はsetup_move_sizeでカバーされるメモリ領域内に配置する必要があります。そのため、このフィールドを調整する必要があるかもしれません。

1.8. 実モードコードのメモリレイアウト¶

実モードコードにはスタック/ヒープの設定と、カーネルコマンドライン用のメモリの確保が必要です。これらは、ボトムメガバイト（1MB以下の領域）の実モードアクセス可能なメモリで行う必要があります。

現代のマシンでは、拡張BIOSデータ領域（EBDA）が大きく設定されていることが多く、そのため低メガバイトの使用を極力減らすことが推奨されます。

以下の状況では0x90000メモリセグメントを使用する必要があります：

  • zImageカーネルをロードする場合（（loadflags & 0x01） == 0）。

  • 2.01以前のブートプロトコルでカーネルをロードする場合。

注意

2.00および2.01のブートプロトコルでは、実モードコードは別のアドレスにロードされますが、内部的に0x90000に再配置されます。旧プロトコルでは実モードコードは0x90000にロードする必要があります。

0x90000にロードする場合、0x9a000以上のメモリは使用しないでください。

ブートプロトコル2.02以上では、カーネルコマンドラインは実モードセットアップコードと同じ64Kセグメントに配置する必要がありません。したがって、スタック/ヒープに64Kセグメント全体を割り当て、コマンドラインをその上に配置することが許可されます。

カーネルコマンドラインは実モードコードの下に配置してはならず、高メモリ領域にも配置してはなりません。

1.9. サンプルブート構成¶

サンプル構成として、実モードセグメントの以下のレイアウトを想定します。

0x90000以下の領域でロードする場合、セグメント全体を用います：

0x0000-0x7fff

実モードカーネル

0x8000-0xdfff

スタックとヒープ

0xe000-0xffff

カーネル コマンドライン

0x90000にロードされる場合、またはプロトコルバージョンが2.01またはそれ以前の場合:

0x0000-0x7fff

実モードカーネル

0x8000-0x97ff

スタックとヒープ

0x9800-0x9fff

カーネル コマンドライン

このようなブートローダーは、ヘッダーに以下のフィールドを記録する必要があります:

unsigned long base_ptr; /* base address for real-mode segment */

if ( setup_sects == 0 ) {
        setup_sects = 4;
}

if ( protocol >= 0x0200 ) {
        type_of_loader = <type code>;
        if ( loading_initrd ) {
                ramdisk_image = <initrd_address>;
                ramdisk_size = <initrd_size>;
        }

        if ( protocol >= 0x0202 && loadflags & 0x01 )
                heap_end = 0xe000;
        else
                heap_end = 0x9800;

        if ( protocol >= 0x0201 ) {
                heap_end_ptr = heap_end - 0x200;
                loadflags |= 0x80; /* CAN_USE_HEAP */
        }

        if ( protocol >= 0x0202 ) {
                cmd_line_ptr = base_ptr + heap_end;
                strcpy(cmd_line_ptr, cmdline);
        } else {
                cmd_line_magic  = 0xA33F;
                cmd_line_offset = heap_end;
                setup_move_size = heap_end + strlen(cmdline)+1;
                strcpy(base_ptr+cmd_line_offset, cmdline);
        }
} else {
        /* Very old kernel */

        heap_end = 0x9800;

        cmd_line_magic  = 0xA33F;
        cmd_line_offset = heap_end;

        /* A very old kernel MUST have its real-mode code
           loaded at 0x90000 */

        if ( base_ptr != 0x90000 ) {
                /* Copy the real-mode kernel */
                memcpy(0x90000, base_ptr, (setup_sects+1)*512);
                base_ptr = 0x90000;              /* Relocated */
        }

        strcpy(0x90000+cmd_line_offset, cmdline);

        /* It is recommended to clear memory up to the 32K mark */
        memset(0x90000 + (setup_sects+1)*512, 0,
               (64-(setup_sects+1))*512);
}

1.10. カーネルの残り部分をロードする¶

32ビット（リアルモードでない）カーネルは、カーネルファイル内のオフセット（setup_sects+1）*512から開始します（setup_sectsが0の場合は実際の値は4です）。このカーネルは、Image/zImageの場合0x10000、bzImageの場合0x100000のアドレスにロードする必要があります。

プロトコルが2.00以上で、loadflagsフィールドの0x01ビット（LOAD_HIGH）が設定されている場合、カーネルはbzImageです:

is_bzImage = (protocol >= 0x0200) && (loadflags & 0x01);
load_address = is_bzImage ? 0x100000 : 0x10000;

Image/zImageカーネルは最大512KBまでになるため、0x10000-0x90000のメモリ範囲をすべて使用します。これにより、これらのカーネルは0x90000にリアルモード部分をロードする必要があります。bzImageカーネルははるかに柔軟な配置が可能です。

1.11. 特別なコマンドラインオプション¶

ブートローダーがユーザーが入力したコマンドラインを提供する場合、ユーザーは以下のコマンドラインオプションが動作することを期待するかもしれません。これらは、すべてのカーネルが実際に意味を持つわけではないにもかかわらず、通常はカーネルのコマンドラインから削除すべきではありません。ブートローダー自身に追加のコマンドラインオプションが必要な開発者には、以下の場所に登録してもらう必要があります。 カーネルのコマンドラインパラメータ これにより、今後とも実際のカーネルオプションと競合しないようにします。

vga=<モード>

<モード>は、整数（C記法で10進、8進、16進いずれか）または「normal」（0xFFFF）、「ext」（0xFFFE）、「ask」（0xFFFD）のいずれかです。この値はvid_modeフィールドに設定する必要があります。これは、コマンドラインが解析される前にカーネルによって使用されます。

mem=<サイズ>

<サイズ>はC記法の整数で、K、M、G、T、P、E（それぞれ<<10、<<20、<<30、<<40、<<50、<<60を意味）を大文字小文字を問わず付けて指定できます。これはカーネルにメモリの終端を指定します。初期RAMディスク（initrd）の配置に影響を与えます。初期RAMディスクはメモリの終わり近くに配置されるべきです。注意: このオプションは、カーネルとブートローダーの両方に適用されます。 両方を組み合わせます カーネルとブートローダー!

initrd=<ファイル>

初期RAMディスクをロードする必要があります。<ファイル>の意味はブートローダー依存であり、一部のブートローダー（例: LILO）はこのようなコマンドをサポートしていません。

さらに、一部のブートローダーはユーザー指定のコマンドラインに以下のオプションを追加します:

BOOT_IMAGE=<ファイル>

ロードされたブートイメージ。再び、<ファイル>の意味はブートローダー依存です。

auto

ユーザーの明示的な操作なしにカーネルが起動しました。

ブートローダーによってこれらのオプションが追加された場合、ユーザー指定または設定指定のコマンドラインの前に配置することをお勧めします。 最初それ以外の場合、「init=/bin/sh」は「auto」オプションによって混乱する可能性があります。

1.12. カーネルの実行¶

カーネルは、リアルモードのカーネルの開始位置から0x20オフセットにあるエントリポイントにジャンプすることで起動されます。 セグメント これは、リアルモードのカーネルコードが0x90000にロードされている場合、エントリポイントが9020:0000になることを意味します。

エントリポイントでは、ds = es = ssがリアルモードのカーネルコードの開始位置（コードが0x90000にロードされている場合0x9000）を指し、spはヒープの上部を指すように適切に設定され、割り込みは無効化される必要があります。さらに、カーネルのバグを防ぐため、ブートローダーがfs = gs = ds = es = ssを設定することをお勧めします。

上記の例では、以下のようにします：

/* Note: in the case of the "old" kernel protocol, base_ptr must
   be == 0x90000 at this point; see the previous sample code */

seg = base_ptr >> 4;

cli();  /* Enter with interrupts disabled! */

/* Set up the real-mode kernel stack */
_SS = seg;
_SP = heap_end;

_DS = _ES = _FS = _GS = seg;
jmp_far(seg+0x20, 0);   /* Run the kernel */

ブートセクタがフロッピードライブにアクセスする場合、カーネルを実行する前にフロッピーモーターを停止することをお勧めします。なぜなら、カーネルのブートでは割り込みが無効になっているため、モーターが停止しない可能性があるからです（特にロードされたカーネルがフロッピードライバを_demand-loaded_モジュールとして含む場合）。

1.13. 高度なブートローダーのハック¶

ブートローダーが特に敵対的な環境（LOADLINなど、DOS下で実行されるもの）で動作する場合、標準のメモリ位置要件を満たすことは不可能になることがあります。このようなブートローダーは、カーネルが適切なタイミングで呼び出すために以下のハックを使用する場合があります。これらのハックの使用は、最終手段として考慮すべきです。

重要：すべてのハックは呼び出し時に%esp、%ebp、%esi、%ediを保持する必要があります。

realmode_swtch:

保護モードに入る直前に呼び出される16ビットリアルモードの遠いサブルーチン。デフォルトのルーチンではNMIが無効化されるため、あなたのルーチンも同様に実行してください。

code32_start:

32ビットフラットモードのルーチン 保護モードへの移行後、カーネルが展開される前にジャンプされます。 CS以外のセグメントは設定されていない可能性があるため（現在のカーネルでは設定されていますが、古いカーネルでは設定されていない）、BOOT_DS（0x18）に自分で設定してください。

ハックを完了した後、ブートローダーが上書きした前記フィールドにあったアドレスにジャンプしてください（必要に応じてリロケート済みのアドレス）。

1.14. 32ビットブートプロトコル¶

EFIなどの非伝統的なBIOS（例：LinuxBIOSなど）やkexecを使用するマシンでは、伝統的なBIOSに基づくカーネルのリアルモード設定コードは使用できません。そのため、32ビットブートプロトコルを定義する必要があります。

32ビットブートプロトコルでは、Linuxカーネルをロードする最初のステップは、ブートパラメータ（struct boot_params、伝統的に「ゼロページ」として知られている）を設定することです。struct boot_paramsのメモリは確保し、すべてゼロに初期化する必要があります。その後、カーネルイメージのオフセット0x01f1にあるセットアップヘッダーをstruct boot_paramsにロードし、確認します。セットアップヘッダーの終わりは以下の通り計算できます。

0x0202 + byte value at offset 0x0201

16ビットブートプロトコルと同様に、struct boot_paramsのセットアップヘッダーを読み込み/変更/書き込みするだけでなく、第3章で説明されているようにstruct boot_paramsの追加フィールドをブートローダーが埋め込む必要があります。 ゼロページ.

struct boot_paramsを設定した後、ブートローダーは16ビットブートプロトコルと同様の方法で32/64ビットカーネルをロードできます。

32ビットブートプロトコルでは、カーネルはロードされた32/64ビットカーネルの開始アドレスである32ビットカーネルエントリポイントにジャンプして起動します。

エントリポイントでは、CPUが32ビットプロテクトモードでページングが無効になっている必要があります。GDTは__BOOT_CS(0x10)と__BOOT_DS(0x18)のセレクターのディスクリプタでロードされ、両方のディスクリプタは4Gフラットセグメントでなければなりません。__BOOT_CSには実行/読み取り権限、__BOOT_DSには読み込み/書き込み権限が必要です。CSは__BOOT_CSで、DS、ES、SSはすべて__BOOT_DSにする必要があります。割り込みは無効にしてください。%esiにはstruct boot_paramsのベースアドレスを保持し、%ebp、%edi、%ebxはゼロにする必要があります。

1.15. 64ビットブートプロトコル¶

64ビットCPUと64ビットカーネルを持つマシンでは、64ビットブートローダーを使用し、64ビットブートプロトコルが必要です。

64ビットブートプロトコルでは、Linuxカーネルをロードする最初のステップは、ブートパラメータ（struct boot_params、伝統的に「ゼロページ」として知られている）を設定することです。struct boot_paramsのメモリはどこでも確保可能（4Gを超えることも含む）で、すべてゼロに初期化する必要があります。その後、カーネルイメージのオフセット0x01f1にあるセットアップヘッダーをstruct boot_paramsにロードし、確認します。セットアップヘッダーの終わりは以下の通り計算できます。

0x0202 + byte value at offset 0x0201

16ビットブートプロトコルと同様に、struct boot_paramsのセットアップヘッダーを読み込み/変更/書き込みするだけでなく、第3章で説明されているようにstruct boot_paramsの追加フィールドをブートローダーが埋め込む必要があります。 ゼロページ.

struct boot_paramsを設定した後、ブートローダーは16ビットブートプロトコルと同様の方法で64ビットカーネルをロードできますが、カーネルは4Gを超えてロードされる可能性があります。

64ビットブートプロトコルでは、カーネルはロードされた64ビットカーネルの開始アドレスに0x200を加えた64ビットカーネルエントリポイントにジャンプして起動します。

起動時、CPUはページングが有効になっている64ビットモードでなければなりません。setup_header.init_sizeの範囲からロードされたカーネルの開始アドレス、ゼロページ、コマンドラインバッファは識別マッピングされます。セレクター__BOOT_CS(0x10)と__BOOT_DS(0x18)のディスクリプタを持つGDTをロードしなければなりません。両方のディスクリプタは4Gフラットセグメントでなければなりません。__BOOT_CSには実行/読み取り権限、__BOOT_DSには読み込み/書き込み権限を設定しなければなりません。CSは__BOOT_CSでなければなりません。DS、ES、SSはすべて__BOOT_DSでなければなりません。割り込みは無効にしてください。%rsiはstruct boot_params構造体のベースアドレスを保持しなければなりません。

1.16. EFIハンドオーバープロトコル（非推奨）¶

このプロトコルは、ブートローダーがEFIブートスタブへの初期化を延期できるようにします。ブートローダーは、ブートメディアからカーネル/initrd（複数可能）をロードし、startup_{3、64}の開始位置からhdr->handover_offsetバイト分のEFIハンドオーバープロトコルのエントリポイントにジャンプしなければなりません。

ブートローダーは、PE/COFFメタデータのセクションアライメント、実行可能イメージのメモリフットプリント（ファイルサイズを超える部分）、およびPE/COFFヘッダーの他の項目がEFIファームウェアの実行コンテキストでPE/COFFバイナリとして正しく動作するための影響を与える可能性のある項目について、カーネルのPE/COFFメタデータを尊重しなければなりません。

ハンドオーバーエントリポイントの関数プロトタイプは次のようになります：

efi_main(void *handle, efi_system_table_t *table, struct boot_params *bp)

「handle」はEFIファームウェアからブートローダーに渡されるEFIイメージハンドルで、「table」はEFIシステムテーブルです。これらはUEFI仕様書のセクション2.3で説明する「ハンドオフステート」の最初の2つの引数です。「bp」はブートローダーが割り当てるboot_paramsです。

ブートローダー grace periodsを尊重しなければなりませんし、 bpの以下のフィールドを埋め込む必要があります：

- hdr.cmd_line_ptr
- hdr.ramdisk_image (if applicable)
- hdr.ramdisk_size  (if applicable)

他のすべてのフィールドはゼロにする必要があります。

注意：EFIハンドオーバープロトコルは、通常のPE/COFFエントリポイントとLINUX_EFI_INITRD_MEDIA_GUIDベースのinitrdローディングプロトコル（ブートローダー側の例については[0]を参照）を組み合わせることで非推奨となりました。

これにより、EFIブートローダーがboot_paramsの内部表現やコマンドラインおよびramdiskのメモリ配置、カーネルイメージの配置に関する知識を必要としなくなるため、その必要性が除去されます。

25. 共有仮想アドレス割当 (SVA) と ENQCMD¶

25.1. 背景¶

共有仮想アドレス割当 (SVA) は、プロセッサとデバイスが同じ仮想アドレスを使用し、ソフトウェアによる仮ザアドレスから物理アドレスへの変換の必要性を回避できるようにします。SVA は PCIe が呼ぶ共有仮想メモリ (SVM) です。

デバイスがアプリケーションの仮想アドレスを使用できるという利便性に加えて、DMA 用のページのピンニングも不要です。PCIe アドレス変換サービス (ATS) とページリクエストインターフェース (PRI) により、デバイスは CPU がアプリケーションページフォールトを処理するようにほぼ同じように動作できます。詳細については PCIe 標準仕様の第 10 章「ATS 標準仕様」を参照してください。

SVA の使用には、プラットフォームに IOMMU のサポートが必要です。IOM、MU は PCIe の機能 ATS および PRI をサポートするためにも必要です。ATS はデバイスが仮想アドレスの翻訳をキャッシュできるようにします。IOMMU ドライバーは mmu_notifier() を使用して、デバイス TLB キャッシュと CPU キャッシュを同期させます。仮想アドレスの ATS ロックアップが失敗した場合、デバイスは PRI を使用してその仮想アドレスが CPU ページテーブルにページングされるようにリクエストする必要があります。デバイスは使用前に翻訳を取得するために ATS を再度使用する必要があります。

25.2. 共有ハードウェアワークキュー¶

単一ルート I/O 虚擬化 (SR-IOV) とは異なり、拡張可能な IOV (SIOV) はアプリケーションと仮想マシン (VM) の双方が共有ワークキュー (SWQ) を使用できるようにします。これにより、ハードウェアの利用効率が向上し、ハードウェアリソースのハードパーティショニングによる過剰な未利用を防ぐことができます。SWQ インターフェースを通じてハードウェアがワークの実行コンテキストを区別できるようにするため、SIOV はプロセスアドレス空間 ID (PASID) を使用します。PASID は PCIe SIG によって定義された 20 ビットの数値です。

PASID の値は、デバイスからのすべてのトランザクションにエンコードされます。これにより、IOMMU は PCIe リソース識別子 (RID) であるバス/デバイス/ファンクションを使用しながら、PASID ごとに I/O を追跡できます。

25.3. ENQCMD¶

ENQCMD は、Intel プラットフォームで新たに導入された命令で、ワークディスクリプタをデバイスにアトミックに送信します。このディスクリプタには、実行する操作、すべてのパラメータの仮想アドレス、完了レコードの仮想アドレス、および現在のプロセスの PASID (プロセスアドレス空間 ID) が含まれます。

ENQCMDは非ポストセマンティクスを使用し、ハードウェアがコマンドを受信した場合に状態を返します。これにより、送信者が送信を再試行する必要があるか、または公平性を確保するためのデバイス固有のメカニズムを実装する必要があります。

ENQCMDはアプリケーションがハードウェアに直接コマンドを送信できるようにする橋渡しであり、PASIDの使用によりハードウェアがアプリケーションのコンテキストを認識できるようにします。

25.4. プロセスアドレス空間タギング¶

新しいスレッドスコープのMSR（IA32_PASID）は、ユーザープロセスと残りのハードウェアとの接続を提供します。アプリケーションがSVA対応デバイスに初めてアクセスする際、このMSRは新たに割り当てられたPASIDで初期化されます。デバイスのドライバーは、DMAおよびページリクエストのルーティングを設定するIOMMU固有のAPIを呼び出します。

たとえば、Intel Data Streaming Accelerator（DSA）はiommu_sva_bind_device()を使用します。これは以下の操作を行います：

  • PASIDを割り当て、PASIDコンテキストエントリ内にプロセスページテーブル（%cr3レジスタ）をプログラミングします。

  • mmu_notifier()を登録して、ページテーブルの無効化を追跡し、デバイスTLBを同期させます。たとえば、ページテーブルエントリが無効化されると、IOMMUはその無効化をデバイスTLBに伝播します。これにより、今後のデバイスのこの仮想アドレスへのアクセスはATSに参加するよう強制されます。IOMMUがページが存在しないことを適切に応答した場合、デバイスはI/O実行前にPCIe PRIプロトコルを介してページをページインリクエストします。

このMSRはXSAVE機能セットで「スーパーバイザーステート」として管理され、コンテキストスイッチ中にMSRが更新されるようにします。

25.5. PASID管理¶

カーネルはENQCMDを使用する各プロセスの代わりにPASIDを割り当て、新しいMSRにプログラミングしてプロセスの識別情報をプラットフォームハードウェアに伝達します。ENQCMDはこのMSRに保存されたPASIDを使用して、プロセスからのリクエストをタグ付けします。ユーザーがENQCMD指令を使用してデバイスにワークディスクリプタを送信すると、ディスクリプタ内のPASIDフィールドはMSR_IA32_PASIDの値で自動的に埋められます。デバイスからのDMAリクエストも同じPASIDでタグ付けされます。プラットフォームIOMMUはトランザクション内のPASIDを使用してアドレス変換を実行します。IOMMU APIは、CPUが使用するプロセスアドレス（例：x86の%cr3レジスタ）に対応するPASIDエントリをIOMMUに設定します。

アプリケーションスレッドがデバイスと相互作用する前に、各論理CPUでMSR（マシン固有レジスタ）を設定しておく必要があります。同じプロセスに属するスレッドは同じページテーブルを共有するため、同じMSR値を使用します。

PASID（プロセスアドレス空間ID）はプロセス作成時にクリアされます。PASIDの割当とMSRのプログラミングは、プロセスおよびそのスレッドが作成された後でも長期間にわたって行われることがあります。1つのスレッドがiommu_sva_bind_device()を呼び出すことで、プロセスのPASIDを割り当てます。スレッドがMSRが初期化される前にENQCMDを使用すると、#GP（一般保護違反）が発生します。カーネルはプロセス内のすべてのスレッドのPASID MSRをPASIDで更新します。複数のデバイスと同時に使用する際も、すべてのスレッドが同じアドレス空間を共有するため、単一のプロセスPASIDが使用可能です。

1つのスレッドがiommu_sva_unbind_device()を呼び出すことで、割り当てられたPASIDを解放します。カーネルはプロセスに属するすべてのスレッドのPAS, ID MSRをクリアします。

新しいスレッドは親スレッドからMSR値を継承します。

25.6. 関係性¶

  • プロセスには多くのスレッドがありますが、1つのPASIDのみが存在します。

  • デバイスにはハードウェアワークキューが限られた数（数十〜千程度）しかありません。デバイスドライバーがハードウェアワークキューの割当を管理します。

  • 1つのmmap()は1つのハードウェアワークキューを「ポータル」としてマッピングし、各ポータルは1つのワークキューにマッピングされます。

  • プロセスがデバイスと相互作用するごとに、1つ以上のmmap()されたポータルが必要です。

  • プロセス内の多数のスレッドが1つのポータルを共有して1つのデバイスにアクセスできます。

  • 複数のプロセスが同じポータルをmmap()する場合でも、それらは1つのデバイスハードウェアワークキューを共有します。

  • 1つのプロセス全体で使用されるPASIDは、すべてのスレッドがすべてのデバイスと相互作用するために使用されます。たとえば、各スレッドやスレッド<->デバイスペアごとにPASIDが存在するわけではありません。

25.7. よくある質問¶

  • SVA/SVMとは何ですか？

共有仮想アドレッシング（SVA）は、I/Oハードウェアとプロセッサが同じアドレス空間で動作できるようにします。つまり、アドレス空間を共有します。一部では「共有仮想メモリ（SVM）」と呼ばれることがありますが、LinuxコミュニティはPOSIX共有メモリやセキュア仮想マシンという既存の用語と混乱を避けるため、この用語を避けました。

  • PASIDとは何ですか？

プロセスアドレス空間ID（PASID）はPCIe定義のトランザクションレイヤパケット（TLP）のプレフィックスです。PASIDは20ビットの数値で、OSが割り当ておよび管理します。PASIDはプラットフォームとデバイス間のすべてのトランザクションに含まれます。

  • 共有ワークキューとはどのように異なりますか？

従来、ユーザースペースアプリケーションがハードウェアとやり取りするには、各プロセスに対して個別のハードウェアインスタンスが必要でした。たとえば、ドアベルはハードウェアに処理すべき作業を通知するメカニズムとされます。各ドアベルはプロセスの分離のために4k（またはページサイズ）の間隔を確保する必要があります。これによりハードウェアはその領域をプロビジョニングし、MMIO（メモリマップドI/O）で確保しなければなりません。スレッド数が非常に大きい場合、この方法はスケーラビリティに欠けています。また、ハードウェアは共有ワークキュー（SWQ）のキュー深度を管理しており、消費者はキュー深度を追跡する必要がありません。コマンドを受け入れる領域がなければない場合、デバイスは再試行を示すエラーを返します。

ユーザーはデバイスの遅延可能メモリ書き込み（DMWr）機能を確認し、デバイスがサポートしている場合にのみENQCMDを送信する必要があります。新しいDMWr PCIe用語では、デバイスがDMWrコンプリータ機能をサポートする必要があります。さらに、すべてのスイッチポートがDMWrルーティングをサポートし、PCIeサブシステムによって有効化される必要があります。これはPCIeアトミック操作が管理されるようにするのと同様です。

SWQはハードウェアがデバイス内で単一のアドレスをプロビジョニングできるようにします。ENQCMDを使用して作業を送信する場合、デバイスはその作業を送信したプロセスを識別できます。これはそのプロセスに割り当てられたPASIDが含まれるためです。これにより、デバイスは多数のプロセスにスケーラブルです。

  • これはユーザースペースデバイスドライバーと同じですか？

共有ワークキューを介してデバイスと通信するよりも、フルなユーザースペースドライバーを使用する方がはるかに簡単です。カーネルドライバーがハードウェアの初期化をすべて行います。ユーザースペースは作業の送信と完了処理のみを心配する必要があります。

  • これはSR-IOVと同じですか？

シングルルートI/O仮想化（SR-IOV）は、ハードウェアの仮想化に独立したハードウェアインターフェースを提供することを目的としています。そのため、伝統的なBAR（ベースアドレスレジスタ）をサポートするほぼ完全なインターフェース、MSI-Xを介した割り込み領域、独自のレジスタレイアウトが必要です。仮想関数（VFs）は物理関数（PF）ドライバーによって支援されます。

スケーラブルI/O仮想化はPASID概念を基盤にして仮想化用のデバイスインスタンスを構築します。SIOVはホストソフトウェアの支援により仮想デバイスを生成する必要があります。各仮想デバイスはデバイスのバス/デバイス/ファンクションとPASIDで表されます。これによりデバイスハードウェアがリソース生成を最適化でき、必要に応じて動的に拡張可能です。SR-IOVの生成と管理は非常に静的な性質を持っています。詳細については下記の参照資料をご覧ください。

  • 各アプリケーションに対して個別に仮想関数を生成するのではなぜしないのか？

PCIe SR-IOV型の仮想関数（VF）を生成するにはコストがかかる。VFはPCI構成空間やMSI-Xなどの割込みに複数のハードウェアを必要とし、リソース（割込みなど）はVF生成時にハードウェアでパーティション化され、動的にスケーラブルな要件に対応できない。VFは物理関数（PF）と完全に独立していない。ほとんどのVFはPFドライバからの通信や支援が必要である。一方、SIOVはソフトウェア定義デバイスを生成し、すべての設定と制御は遅い経路を介して行われる。ワークサブミットと完了は mediation なしで行われる。

  • これは仮想化をサポートしていますか？

ENQCMDはゲストVM内で使用できます。このような場合、VMMはゲストPASIDをホストPASIDに変換するための翻訳テーブルを設定するのに役立ちます。詳細についてはENQCMD命令セットリファレンスを参照してください。

  • メモリをピン留めする必要がありますか？

デバイスがSVAをサポートし、IOMMUなどのプラットフォームハードウェアもサポートしている場合、DMAの目的でメモリをピン留めする必要はありません。SVAをサポートするデバイスは、メモリのピン留めを不要にする他のPCIe機能もサポートしています。

デバイスTLBサポート - デバイスはAddress Translation Service (ATS)リクエストを通じてIOMMUにアドレスの照会を依頼します。マッピングが存在してもOSがページを割り当てていない場合、IOMMUハードウェアはマッピングが存在しないと返します。

デバイスはPage Request Interface (PRI)を通じて仮想アドレスのマッピングを依頼します。OSがマッピングを成功させると、デバイスに応答を返します。デバイスは再び翻訳を依頼し、処理を継続します。

IOMMUはOSと協力して、デバイスとページテーブルの整合性を管理します。ページを削除する際には、OSからマッピングを削除する前にキャッシュされていたデバイスTLBエントリをデバイスと協力して削除します。

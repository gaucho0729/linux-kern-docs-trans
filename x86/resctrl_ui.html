Intel ではこの機能を Intel Resource Director Technology（Intel(R) RDT）と呼び、AMD では AMD Platform Quality of Service（AMD QoS）と呼びます。

この機能は CONFIG_X86_CPU_RESCTRL と x8�6 /proc/cpuinfo フラグビットによって有効になります:

RDT（Resource Director Technology）割り当て

「rdt_a」

CAT（Cache Allocation Technology）

「cat_l3」, 「cat_l2」

CDP（Code and Data Prioritization）

「cdp_l3」, 「cdp_l2」

CQM（Cache QoS Monitoring）

「cqm_llc」, 「cqm_occup_llc」

MBM（Memory Bandwidth Monitoring）

「cqm_mbm_total」, 「cqm_mbm_local」

MBA（Memory Bandwidth Allocation）

「mba」

この機能を使用するには、ファイルシステムをマウントします:

# mount -t resctrl resctrl [-o cdp[,cdpl2][,mba_MBps]] /sys/fs/resctrl

マウントオプションは:

「cdp」:

L3 キャッシュ割り当てにおいてコード/データ優先化を有効にします。

「cdpl2」:

L2 キャッシュ割り当てにおいてコード/データ優先化を有効にします。

「mba_MBps」:

MBA ソフトウェアコントローラー（mba_sc）を有効にして、MBA バンド幅を MBps 単位で指定します

L2 および L3 の CDP は別々に制御されます。

RDT 機能は相互に独立しています。特定のシステムは監視機能のみ、制御機能のみ、あるいは監視と制御の両方をサポートする場合があります。キャッシュ擬似ロックは、キャッシュ制御を用いてデータをキャッシュに「固定」または「ロック」する一形態です。詳細は「キャッシュ擬似ロック」セクションをご参照ください。

割り当てまたは監視のいずれかが存在すればマウントは成功しますが、システムがサポートするファイルおよびディレクトリのみが作成されます。監視および割り当て時のインターフェースの挙動については、「リソース割り当ておよびモニタリンググループ」セクションをご参照ください。

20.1. 情報ディレクトリ¶

「info」ディレクトリには有効なリソースに関する情報が含まれています。各リソースには独自のサブディレクトリがあります。サブディレクトリ名はリソース名を反映しています。

各サブディレクトリには割り当てに関する以下のファイルが含まれます:

キャッシュリソース（L3/L2）サブディレクトリには割り当てに関する以下のファイルが含まれます:

「num_closids」:

このリソースに有効な CLOSID の数です。カーネルはすべての有効なリソースの中で最小の CLOSID 数を制限値として使用します。

「cbm_mask」:

このリソースに有効なビットマスクです。このマスクは 100% に相当します。

「min_cbm_bits」:

マスクを書き込む際には設定する必要のある連続するビットの最小数です。

「shareable_bits」:

他の実行エンティティ（例：I/O）と共有可能なリソースのビットマスク。ユーザーは排他キャッシュパーティションを設定する際にこのビットマスクを使用できます。一部のプラットフォームでは、デバイスごとにキャッシュ使用に関する独自の設定がサポートされており、これによりこれらのビットが上書きされる可能性があります。

「bit_usage」：

リソースのすべてのインスタンスがどのように使用されているかを示す注釈付きの容量ビットマスク。凡例は以下の通りです：

“0”:

対応する領域は未使用です。システムのリソースが割り当てられ、『bit_usage』に『0』が見つかった場合、リソースが無駄にされていることを示します。

“H”:

対応する領域はハードウェアのみで使用されますが、ソフトウェアの使用が可能です。リソースが『shareable_bits』にビットが設定されている場合でも、リソースグループのスキーマにすべてのビットが含まれていない場合、『shareable_bits』に含まれるがリソースグループに所属しないビットは『H』としてマークされます。

“X”:

対応する領域は共有可能で、ハードウェアとソフトウェアの両方が使用しています。これらは『shareable_bits』に含まれるビットおよびリソースグループの割り当てに含まれるビットです。

“S”:

対応する領域はソフトウェアによって使用され、共有可能です。

“E”:

対応する領域は1つのリソースグループによって排他的に使用されます。共有はできません。

“P”:

対応する領域は擬似ロックされています。共有はできません。

メモリ帯域幅（MB）サブディレクトリには、割り当てに関する以下のファイルがあります：

「min_bandwidth」：

ユーザーがリクエストできる最小メモリ帯域幅パーセンテージ。

「bandwidth_gran」：

メモリ帯域幅パーセンテージが割り当てられる粒度。割り当てられた帯域幅パーセンテージはハードウェア上の次のコントロールステップに四捨五入されます。利用可能な帯域幅コントロールステップは：min_bandwidth + N * bandwidth_gran です。

「delay_linear」：

遅延スケールが線形か非線形かを示します。このフィールドは情報的なものです。

「thread_throttle_mode」：

Intelシステムにおいて、物理コアのスレッドで実行されるタスクが異なるメモリ帯域幅パーセンテージをリクエストした場合にどのようにスレッド制限されるかを示します：

「max」：

すべてのスレッドに最小のパーセンテージが適用されます。

「per-thread」：

帯域幅パーセンテージがコアのスレッドに直接適用されます。

RDTモニタリングが利用可能であれば、「L3_MON」ディレクトリが存在し、以下のファイルがあります：

「num_rmids」：

利用可能なRMIDの数。これは「CTRL_MON」＋「MON」グループが作成できる上限です。

「mon_features」：

モニタリングがリソースに対して有効な場合、モニタリングイベントの一覧を表示します。

「max_threshold_occupancy」：

読み取り/書き込みファイルは、以前に使用されたLLC_occupancyカウンターが再利用されるための最大値（バイト単位）を提供します。

最後に、「info」ディレクトリのトップレベルに「last_cmd_status」というファイルがあります。このファイルは、ファイルシステム経由で実行される「コマンド」ごとにリセットされます（新しいディレクトリを作成したり、制御ファイルへの書き込みを行ったりする場合）。コマンドが成功した場合、このファイルは「ok」と表示され、失敗した場合は、ファイル操作のエラーリターンで返せるエラー情報が含まれます。例として、

# echo L3:0=f7 > schemata
bash: echo: write error: Invalid argument
# cat info/last_cmd_status
mask f7 has non-consecutive 1-bits

20.2. リソース割り当てとモニタリンググループ¶

リソースグループはresctrlファイルシステム内のディレクトリとして表されます。デフォルトのグループはルートディレクトリで、マウント直後にシステム内のすべてのタスクとCPUを所有し、すべてのリソースをフルに利用できるようになります。

RDT制御機能を持つシステムでは、ルートディレクトリに追加のディレクトリを作成できます。これにより、各リソースの異なる量を指定できます（以下で説明する「スキーマ」を参照）。ルートディレクトリとこれらの追加されたトップレベルディレクトリは、以下で「CTRL_MONグループ」と呼ばれます。

RDTモニタリングが可能なシステムでは、ルートディレクトリとその他のトップレベルディレクトリには、「mon_groups」というディレクトリが含まれています。このディレクトリ内に追加のディレクトリを作成することで、CTRL_MONグループ（親となるグループ）のタスクのサブセットを監視できます。これらはこのドキュメントの後半で「MONグループ」と呼ばれます。

ディレクトリを削除すると、そのグループが所有するすべてのタスクとCPUが親ディレクトリに移動します。作成されたCTRL_MONグループを削除すると、その下にあるすべてのMONグループも自動的に削除されます。

すべてのグループには次のファイルが含まれます：

「tasks」：

このファイルを読み込むと、このグループに属するすべてのタスクの一覧が表示されます。タスクIDをこのファイルに書き込むと、タスクがグループに追加されます。グループがCTRL_MONグループの場合、タスクは以前のCTRL_MONグループから削除され、所有していたすべてのMONグループからも削除されます。グループがMONグループの場合、タスクはこのグループのCTRL_MON親グループにすでに所属している必要があります。タスクは以前のMONグループから削除されます。

「cpus」：

このファイルを読み込むと、このグループが所有する論理CPUのビットマスクが表示されます。このファイルにマスクを書き込むと、CPUをグループに追加または削除できます。タスクファイルと同様に、階層が維持され、MONグループは親CTRL_MONグループが所有するCPUのみを含めることができます。リソースグループが擬似ロックモードの場合、このファイルは読み取り専用となり、擬似ロック領域に関連するCPUを反映します。

「cpus_list」：

「cpus」と同様ですが、ビットマスクではなくCPUの範囲を使用します。

制御が有効な場合、すべてのCTRL_MONグループには以下のファイルも含まれます：

「schemata」:

このグループに利用可能なすべてのリソースの一覧です。各リソースは個別に1行で表示され、フォーマットも異なります。詳細は下記をご参照ください。

「size」:

「schemata」ファイルの表示を反映し、割当てのバイト単位のサイズを表示します。これにより、割当てを表すビットではなく、バイト単位のサイズが表示されます。

「mode」:

リソースグループの「mode」は、その割当ての共有を制御します。「shareable」リソースグループは割当てを共有可能ですが、「exclusive」リソースグループは共有できません。キャッシュの擬似ロック領域を作成するには、まず「pseudo-locksetup」を「mode」ファイルに書き込み、その後、キャッシュ擬似ロック領域のスキーマをリソースグループの「schemata」ファイルに書き込みます。擬似ロック領域の作成が成功すると、自動的に「pseudo-locked」モードに切り替わります。

モニタリングが有効になっている場合、すべてのMONグループには以下が含まれます:

「mon_data」:

これは、L3ドメインごとに、RDTイベントごとに整理されたファイルのセットです。たとえば、2つのL3ドメインを持つシステムでは、「mon_L3_00」と「mon_L3_01」のサブディレクトリが存在します。これらのディレクトリには、各イベント（例:「llc_occupancy」、「mbm_total_bytes」、「mbm_local_bytes」）ごとに1つのファイルがあります。MONグループでは、グループ内のすべてのタスクのイベントの現在値を読み出すことができます。CTRL_MONグループでは、CTRL_MONグループ内のすべてのタスクとMONグループ内のすべてのタスクの合計値を提供します。詳しくは例のセクションをご参照ください。

20.2.1. リソース割当てルール¶

タスクが実行中である場合、以下のルールがそのタスクに利用可能なリソースを定義します:

  1. タスクが非デフォルトグループのメンバーである場合、そのグループのスキーマが使用されます。

  2. それ以外に、タスクがデフォルトグループに所属しているが、特定のグループに割当てられたCPUで実行されている場合、そのCPUのグループのスキーマが使用されます。

  3. それ以外の場合は、デフォルトグループのスキーマが使用されます。

20.2.2. リソースモニタリングルール¶

  1. タスクがMONグループまたは非デフォルトのCTRL_MONグループのメンバーである場合、そのタスクのRDTイベントはそのグループで報告されます。

  2. タスクがデフォルトのCTRL_MONグループのメンバーであるが、特定のグループに割当てられたCPUで実行されている場合、そのタスクのRDTイベントはそのグループで報告されます。

  3. それ以外の場合、タスクのRDTイベントはルートレベルの「mon_data」グループで報告されます。

20.3. キャッシュ占有モニタリングおよび制御に関する注意事項¶

タスクをグループ間で移動させる際、この操作は new タスクによって割り当てられたキャッシュの使用量を確認できます。たとえば、モニタリンググループ内のタスクが3MBのキャッシュ使用量を表示している場合があります。新しいグループに移動した直後に、古いグループと新しいグループの使用量を確認すると、古いグループは依然として3MBを表示し、新しいグループは0になる可能性があります。タスクが移動前のキャッシュにアクセスする場合、ハードウェアはカウンターを更新しません。忙しいシステムでは、キャッシュラインが追い出され再利用されるため、古いグループの使用量が減少し、新しいグループではタスクがメモリにアクセスしてキャッシュにロードされるたびに使用量が増えることが確認できます。

キャッシュ割り当て制御にも同様のことが適用されます。タスクをキャッシュパーティションが小さいグループに移動しても、キャッシュラインは追い出されません。プロセスは古いパーティションから引き続き使用を続ける可能性があります。

ハードウェアはCLOSid（Class of Service ID）とRMID（Resource Monitoring ID）を使用して、制御グループとモニタリンググループを識別します。各リソースグループは、グループの種類に基づいてこれらのIDにマッピングされます。CLOSidとRMIDの数はハードウェアによって制限されているため、CLOSIDまたはRMIDが不足すると「CTRL_MON」ディレクトリの作成が失敗する可能性があります。また、RMIDが不足すると「MON」グループの作成も失敗する可能性があります。

20.3.1. max_threshold_occupancy - 一般的な概念¶

一度解放されたRMIDは、すぐに再利用できない場合があります。これは、RMIDが以前のユーザーのキャッシュラインにタグ付けされているためです。このようなRMIDは一時リストに配置され、キャッシュ使用量が減少したときに再チェックされます。システムが多数の一時リストに登録されたRMIDを保持しているが、まだ使用準備が出来ていない場合、ユーザーはmkdir時に-EBUSYエラーを確認する可能性があります。

max_threshold_occupancyは、ユーザーが設定可能な値で、RMIDが解放されるキャッシュ使用量を決定します。

20.3.2. スキーマファイル - 一般的な概念¶

ファイルの各行はリソース1つを表し、各行はリソース名を開始として、システム内のそのリソースのインスタンスごとに適用される特定の値を記述します。

20.3.3. キャッシュID¶

現在の世代のシステムでは、ソケットごとに1つのL3キャッシュがあり、L2キャッシュは通常、コア内のハイパースレッド間で共有されるが、これはアーキテクチャ上の必須条件ではない。ソケット内に複数の別個のL3キャッシュを持つことも可能で、複数のコアが1つのL2キャッシュを共有することもできる。したがって、リソースを共有する論理CPUの集合を定義する際には、「ソケット」や「コア」ではなく、「キャッシュID」を使用する。あるキャッシュレベルにおいては、システム全体で一意の番号となるが（連続したシーケンスとは限らず、空きがある可能性がある）、各論理CPUのIDは/sys/devices/system/cpu/cpu*/cache/index*/idを確認する。

20.3.4. キャッシュ ビットマスク (CBM)¶

キャッシュリソースでは、ビットマスクを使用してキャッシュのどの部分が割り当て可能かを記述する。マスクの最大値は各CPUモデルごとに定義されており（異なるキャッシュレベルで異なってもよい）、CPUIDを使用して取得できるが、resctrlファイルシステムの「info/{resource}/cbm_mask」でも提供されている。インテルハードウェアでは、これらのマスクにすべての「1」ビットが連続したブロックでなければならない。したがって、0x3、0x6、0xCは2ビットが設定された4ビットマスクとして有効だが、0x5、0x9、0xAは無効である。20ビットのマスクを持つシステムでは、各ビットがキャッシュ容量の5%を表す。キャッシュを4等分に分割するには、マスクとして0x1f、0x3e0、0x7c00、0xf8000を使用できる。

20.4. メモリ帯域幅の割り当てと監視¶

メモリ帯域幅リソースでは、デフォルトではユーザーが総メモリ帯域幅のパーセンテージを指定することでリソースを制御する。

各CPUモデルの最小帯域幅パーセンテージ値は事前に定義されており、「info/MB/min_bandwidth」で確認できる。割り当てられる帯域幅の粒度はCPUモデルに依存し、「info/MB/bandwidth_gran」で確認できる。利用可能な帯域幅制御ステップは：min_bw + N * bw_gran。中間値はハードウェアが提供する次の制御ステップに四捨五入される。

帯域幅制限は一部のインテル製品でコア固有のメカニズムである。同じコアを共有する2つのスレッドで高帯域幅と低帯域幅の設定を使用すると、両方のスレッドが低帯域幅に制限される可能性がある（詳しくは「thread_throttle_mode」を参照）。

メモリ帯域幅割り当て（MBA）がコア固有のメカニズムである一方で、メモリ帯域幅監視（MBM）はパッケージレベルで行われるため、ユーザーがMBAを介して制御を適用した後、帯域幅を監視して効果を確認しようとすると混乱を生じる可能性がある。以下にそのようなシナリオを示す。

  1. ユーザーは ではありません パーセンテージ値を増加させると、実際の帯域幅が増加することを確認してください:

これは、集約されたL2外部帯域幅がL3外部帯域幅よりも大きい場合に発生します。例として、24コアを搭載したSKL SKUで、L2外部帯域幅が10GBps（集約されたL2外部帯域幅は240GBps）、L3外部帯域幅が100GBpsの場合を想定します。この場合、「20スレッドで50%帯域幅を指定し、各スレッドが5GBpsを消費するワークロード」は、指定された50%の帯域幅よりも低い100GBpsの最大L3帯域幅を消費します。したがって、帯域幅パーセンテージを増加させても帯域幅は増えません。これは、L2外部帯域幅にはまだ容量があるにもかかわらず、L3外部帯域幅が完全に使用されているためです。また、この挙動はベンチマークが実行されるコア数に依存します。

  1. 同じ帯域幅パーセンテージでも、スレッド数によって実際の帯域幅が異なる場合があります:

同じSKUで#1の場合、「単一スレッドで10%帯域幅を指定」し、「4スレッドで10%帯域幅を指定」した場合、それぞれ最大で10GBpsと40GBpsの帯域幅を消費します。これは、ユーザーが指定した帯域幅パーセンテージが同じでも、rdtgroupで使用されるコア数が増えるにつれて実際の帯域幅が増加または変化するためです。

インターフェースをユーザーに親しみやすくするため、resctrlはMBps単位で帯域幅を指定する機能を追加しました。内蔵のカーネルはソフトウェアフィードバックメカニズムまたは「ソフトウェアコントローラー(mba_sc)」を使用し、MBMカウンターで実際の帯域幅を読み取り、メモリ帯域幅パーセンテージを調整して以下を保証します:

"actual bandwidth < user specified bandwidth".

デフォルトでは、スキーマは帯域幅パーセンテージ値を使用します。ユーザーはマウントオプション「mba_MBps」を使用して「MBAソフトウェアコントローラー」モードに切り替えることができます。スキーマの形式は以下のセクションで指定されています。

20.4.1. L3スキーマファイルの詳細（コードとデータの優先度設定が無効）¶

CDPが無効な場合、L3スキーマの形式は以下の通りです:

L3:<cache_id0>=<cbm>;<cache_id1>=<cbm>;...

20.4.2. L3スキーマファイルの詳細（マウントオプションでCDPが有効）¶

CDPが有効な場合、L3制御は2つの別々のリソースに分割されるため、コードとデータに独立したマスクを指定できます:

L3DATA:<cache_id0>=<cbm>;<cache_id1>=<cbm>;...
L3CODE:<cache_id0>=<cbm>;<cache_id1>=<cbm>;...

20.4.3. L2スキーマファイルの詳細¶

L2では「cdpl2」マウントオプションを使用してCDPがサポートされています。スキーマの形式は以下の通りです:

L2:<cache_id0>=<cbm>;<cache_id1>=<cbm>;...

または

L2DATA:<cache_id0>=<cbm>;<cache_id1>=<cbm>;… L2CODE:<cache_id0>=<cbm>;<cache_id1>=<cbm>;…

20.4.4. メモリ帯域幅割当（デフォルトモード）¶

メモリ帯域幅ドメインはL3キャッシュです。

MB:<cache_id0>=bandwidth0;<cache_id1>=bandwidth1;...

20.4.5. メモリ帯域幅割当をMBps単位で指定¶

メモリ帯域幅ドメインはL3キャッシュです。

MB:<cache_id0>=bw_MBps0;<cache_id1>=bw_MBps1;...

20.4.6. スキーマファイルの読み込み/書き込み¶

スキーマファイルを読み込むことで、すべてのドメイン上のリソースの状態を確認できます。書き込む際には、変更したい値のみを指定するだけでよいです。例えば、

# cat schemata
L3DATA:0=fffff;1=fffff;2=fffff;3=fffff
L3CODE:0=fffff;1=fffff;2=fffff;3=fffff
# echo "L3DATA:2=3c0;" > schemata
# cat schemata
L3DATA:0=fffff;1=fffff;2=3c0;3=fffff
L3CODE:0=fffff;1=fffff;2=fffff;3=fffff

20.5. キャッシュ擬似ロック¶

CATは、アプリケーションが使用できるキャッシュ領域の量をユーザーが指定できるようにします。キャッシュ擬似ロックは、CPUがキャッシュヒット時に現在の割り当て領域外で事前に割り当てられたデータを読み書きできるという事実に基づいています。キャッシュ擬似ロックにより、アプリケーションが埋められない予約されたキャッシュ領域にデータを事前にロードし、その後はキャッシュヒットのみを処理するようになります。この擬似ロックされたメモリはユーザー空間にアクセス可能となり、アプリケーションは仮想アドレス空間にマップすることで、平均読み取り遅延が低いメモリ領域を利用できます。

キャッシュ擬似ロックされた領域の作成は、ユーザーがスキーマを伴って擬似ロックするリクエストを送る際にトリガーされます。キャッシュ擬似ロックされた領域は以下の手順で作成されます：

  • 擬似ロックされるキャッシュ領域に含まれるメモリを含むスキーマに一致するCBMを持つCLOSNEWを用いてCAT割り当てを作成します。この領域はシステム上の現在のCAT割り当て/CLOSと重複してはならず、擬似ロックされた領域が存在する間はこのキャッシュ領域との未来の重複も許されません。

  • キャッシュ領域と同じサイズの連続領域のメモリを作成します。

  • キャッシュをフラッシュし、ハードウェアのプリフェッチャーを無効化し、プリエンプションを無効化します。

  • CLOSNEWをアクティブなCLOSに設定し、割り当てられたメモリをタッチしてキャッシュにロードします。

  • 以前のCLOSをアクティブにします。

  • この時点でclosid CLOSNEWは解放できます。CBMがCAT割り当てに現れない限り、キャッシュ擬似ロックされた領域は保護されています。擬似ロックされた領域はこの時点でどのCLOSのCBMにも現れなくなりますが、どのCLOSで実行されるアプリケーションもこの擬似ロックされた領域のメモリにアクセスできるため、領域はキャッシュヒットを継続して処理します。

  • キャッシュにロードされた連続領域のメモリはユーザー空間にキャラクターデバイスとして公開されます。

キャッシュ擬似ロックは、CAT機能を慎重に設定し、アプリケーションの挙動を制御することで、データがキャッシュに残る確率を高めます。ただし、データがキャッシュに配置される保証はありません。INVD、WBINVD、CLFLUSHなどの命令でも、「ロック」されたデータがキャッシュから追い出される可能性があります。電源管理のC状態ではキャッシュが縮小または電源を切られることがあります。擬似ロックされた領域の作成時に深いC状態は自動的に制限されます。

擬似ロックされた領域を使用するアプリケーションは、その領域が存在するキャッシュに関連するコア（またはその一部）にアフィニティを持つ必要があります。コード内の健全性チェックにより、アプリケーションが正しいコアにアフィニティを持つ状態でなければ、擬似ロックされたメモリをマッピングできません。このチェックは初期のmmap()処理時のみ行われ、その後は強制されず、アプリケーション自身が正しいコアにアフィニティを保つ必要があります。

擬似ロックは2段階で実現されます。

  1. 第1段階では、システム管理者が擬似ロック用に割り当てるキャッシュの一部を割り当て、その同等のメモリ領域を割り当てたキャッシュにロードし、キャラクタデバイスとして公開します。

  2. 第2段階では、ユーザー空間アプリケーションが擬似ロックされたメモリをアドレス空間にmmap()でマッピングします。

20.5.1. キャッシュ擬似ロックインターフェース¶

擬似ロックされた領域はresctrlインターフェースを使用して以下のように作成されます。

  1. /sys/fs/resctrlに新しいディレクトリを作成して、新しいリソースグループを作成します。

  2. 「mode」ファイルに「pseudo-locksetup」と書き込むことで、新しいリソースグループのモードを「pseudo-locksetup」に変更します。

  3. 「schemata」ファイルに擬似ロックされた領域のスキーマを書き込みます。すべてのビットは「bit_usage」ファイルに従って「unused」に設定する必要があります。

擬似ロックされた領域の作成が成功した場合、「mode」ファイルには「pseudo-locked」と表示され、リソースグループと同じ名前のキャラクタデバイスが/dev/pseudo_lockに存在します。このキャラクタデバイスはユーザー空間からmmap()により擬似ロックされたメモリ領域にアクセスできます。

キャッシュ擬似ロックされた領域の作成と使用の例は以下にあります。

20.5.2.3. RDT割当使用例¶

  1. 例1

2スロットマシン（1スロットあたり1つのL3キャッシュ）で、キャッシュビットマスクに4ビットのみが割り当てられ、メモリ帯域幅の粒度が10%で最小帯域幅が10%の場合。

# mount -t resctrl resctrl /sys/fs/resctrl
# cd /sys/fs/resctrl
# mkdir p0 p1
# echo "L3:0=3;1=c\nMB:0=50;1=50" > /sys/fs/resctrl/p0/schemata
# echo "L3:0=3;1=3\nMB:0=50;1=50" > /sys/fs/resctrl/p1/schemata

デフォルトのリソースグループは変更されていないため、すべてのキャッシュのすべての部分にアクセスできます（スキーマファイルは「L3:0=f;1=f」と読みます）。

グループ「p0」に属するタスクは、キャッシュID 0の「下位」50%とキャッシュID 1の「上位」50%のみから割り当てを行うことができます。グループ「p1」に属するタスクは、両方のソケットの「下位」50%のキャッシュを使用します。

同様に、グループ「p0」に属するタスクは、ソケット0とソケット1のそれぞれで最大50%のメモリ帯域幅を使用できます。グループ「p1」に属するタスクも両方のソケットで最大50%のメモリ帯域幅を使用できます。注意点として、キャッシュマスクとは異なり、メモリ帯域幅はこれらの割り当てが重複可能かどうかを指定することはできません。割り当てはグループが使用できる最大帯域幅を示し、システム管理者が帯域幅を設定できます。

resctrlがソフトウェアコントローラー（mba_sc）を使用している場合、ユーザーはパーセンテージ値ではなくMB単位で最大帯域幅を入力できます。

# echo "L3:0=3;1=c\nMB:0=1024;1=500" > /sys/fs/resctrl/p0/schemata
# echo "L3:0=3;1=3\nMB:0=1024;1=500" > /sys/fs/resctrl/p1/schemata

上記の例では、ソケット0上の「p1」および「p0」のタスクは最大1024MBの帯域幅を使用し、ソケット1では500MBの帯域幅を使用します。

  1. 例2

再び2つのソケットですが、今回はより現実的な20ビットのマスクを使用します。

2つのリアルタイムタスク（pid=1234がプロセッサ0で実行、pid=5678がプロセッサ1で実行）がソケット0上の2ソケット・デュアルコアマシンで動作しています。ノイズネイバーを避けるため、2つのリアルタイムタスクはそれぞれソケット0上のL3キャッシュの四分の一を専有します。

# mount -t resctrl resctrl /sys/fs/resctrl
# cd /sys/fs/resctrl

まず、デフォルトグループのスキーマをリセットし、ソケット0上のL3キャッシュの「上位」50%およびソケット0とソケット1のメモリ帯域幅の50%は通常のタスクが使用できないようにします：

# echo "L3:0=3ff;1=fffff\nMB:0=50;1=100" > schemata

次に、最初のリアルタイムタスク用のリソースグループを作成し、ソケット0上のキャッシュの「上部」25%にアクセスできるようにします。

# mkdir p0
# echo "L3:0=f8000;1=fffff" > p0/schemata

最後に、最初のリアルタイムタスクをこのリソースグループに移動します。また、taskset(1)を使用して、タスクが常にソケット0の専用CPUで実行されるようにします。リソースグループのほとんどの用途では、タスクが実行されるプロセッサも制限されます。

# echo 1234 > p0/tasks
# taskset -cp 1 1234

2番目のリアルタイムタスクについても同様に（残りの25%のキャッシュ）：

# mkdir p1
# echo "L3:0=7c00;1=fffff" > p1/schemata
# echo 5678 > p1/tasks
# taskset -cp 2 5678

同じ2ソケットシステムでメモリ帯域幅リソースとCAT L3を使用する場合、スキーマは以下のようになります（min_bandwidth 10、bandwidth_gran 10を仮定）：

最初のリアルタイムタスクでは、ソケット0で最大20%のメモリ帯域幅を要求します。

# echo -e "L3:0=f8000;1=fffff\nMB:0=20;1=100" > p0/schemata

2番目のリアルタイムタスクでは、ソケット0でもう一つの20%のメモリ帯域幅を要求します。

# echo -e "L3:0=f8000;1=fffff\nMB:0=20;1=100" > p0/schemata

  1. 例3

コア4〜7にリアルタイムタスクを、コア0〜3に非リアルタイムワークロードを割り当てた単一のソケットシステム。リアルタイムタスクはテキストとデータを共有するため、タスクごとのアソシエーションは必要なく、カーネルとの相互作用のため、これらのコアのカーネルがタスクとL3キャッシュを共有することが望ましい。

# mount -t resctrl resctrl /sys/fs/resctrl
# cd /sys/fs/resctrl

まず、デフォルトグループのスキーマをリセットし、ソケット0のL3キャッシュの上位50%およびソケット0のメモリ帯域幅の50%が通常のタスクによって使用できないようにする:

# echo "L3:0=3ff\nMB:0=50" > schemata

次に、リアルタイムコア用のリソースグループを作成し、ソケット0のキャッシュの上位50%およびソケット0のメモリ帯域幅の50%へのアクセスを許可する。

# mkdir p0
# echo "L3:0=ffc00\nMB:0=50" > p0/schemata

最後に、コア4〜7を新しいグループに移動させ、カーネルおよびその上で実行されるタスクがキャッシュの50%を確保するようにする。コア4〜7がSMTサブレットであり、リアルタイムスレッドのみがスケジュールされる前提で、メモリ帯域幅の50%も確保されるべきである。

# echo F0 > p0/cpus

  1. 例4

前の例で使用したリソースグループはすべてデフォルトの「共有可能」モードで、キャッシュ割当の共有が可能だった。1つのリソースグループがキャッシュ割当を設定しても、他のリソースグループがその割当と重複するのを防ぐことはできない。

この例では、L2 CATシステムで2つのL2キャッシュインスタンスがあり、8ビットの容量ビットマスクで構成可能な新しい排他リソースグループを作成する。この新しい排他リソースグループは、各キャッシュインスタンスの25%を割り当てる。

# mount -t resctrl resctrl /sys/fs/resctrl/
# cd /sys/fs/resctrl

まず、デフォルトグループがすべてのL2キャッシュに割り当てられていることを確認する:

# cat schemata
L2:0=ff;1=ff

この時点で新しいリソースグループを作成しようとすると、デフォルトグループのスキーマと重複しているため失敗する:

# mkdir p0
# echo 'L2:0=0x3;1=0x3' > p0/schemata
# cat p0/mode
shareable
# echo exclusive > p0/mode
-sh: echo: write error: Invalid argument
# cat info/last_cmd_status
schemata overlaps

他のリソースグループと重複しないようにするには、デフォルトリソースグループのスキーマを変更し、新しいリソースグループが排他になることを可能にする必要がある。

# echo 'L2:0=0xfc;1=0xfc' > schemata
# echo exclusive > p0/mode
# grep . p0/*
p0/cpus:0
p0/mode:exclusive
p0/schemata:L2:0=03;1=03
p0/size:L2:0=262144;1=262144

新しいリソースグループは作成時に排他リソースグループと重複しない:

# mkdir p1
# grep . p1/*
p1/cpus:0
p1/mode:shareable
p1/schemata:L2:0=fc;1=fc
p1/size:L2:0=786432;1=786432

bit_usageはキャッシュの使用状況を反映する:

# cat info/L2/bit_usage
0=SSSSSSEE;1=SSSSSSEE

リソースグループは排他リソースグループと重複するように強制することはできない:

# echo 'L2:0=0x1;1=0x1' > p1/schemata
-sh: echo: write error: Invalid argument
# cat info/last_cmd_status
overlaps with exclusive group

20.5.2.4. キャッシュ擬似ロックの例¶

キャッシュID 1のL2キャッシュの一部をCBM 0x3で擬似ロックし、/dev/pseudo_lock/newlockに擬似ロックされた領域を提供し、アプリケーションにmmap()の引数として提供できる。

# mount -t resctrl resctrl /sys/fs/resctrl/
# cd /sys/fs/resctrl

擬似ロック可能なビットが存在することを確認する。擬似ロック可能なのは未使用のビットのみであり、擬似ロックするビットはデフォルトリソースグループのスキーマから削除する必要がある:

# cat info/L2/bit_usage
0=SSSSSSSS;1=SSSSSSSS
# echo 'L2:1=0xfc' > schemata
# cat info/L2/bit_usage
0=SSSSSSSS;1=SSSSSS00

擬似ロックされた領域に関連付ける新しいリソースグループを作成し、擬似ロックされた領域として使用することを示し、要求された擬似ロックされた領域の容量ビットマスクを設定します:

# mkdir newlock
# echo pseudo-locksetup > newlock/mode
# echo 'L2:1=0x3' > newlock/schemata

成功した場合、リソースグループのモードが擬似ロックされた状態に変わり、bit_usageが擬似ロックされた領域を反映し、擬似ロックされた領域を露出するキャラクタデバイスが存在します:

# cat newlock/mode
pseudo-locked
# cat info/L2/bit_usage
0=SSSSSSSS;1=SSSSSSPP
# ls -l /dev/pseudo_lock/newlock
crw------- 1 root root 243, 0 Apr  3 05:01 /dev/pseudo_lock/newlock

/*
* Example code to access one page of pseudo-locked cache region
* from user space.
*/
#define _GNU_SOURCE
#include <fcntl.h>
#include <sched.h>
#include <stdio.h>
#include <stdlib.h>
#include <unistd.h>
#include <sys/mman.h>

/*
* It is required that the application runs with affinity to only
* cores associated with the pseudo-locked region. Here the cpu
* is hardcoded for convenience of example.
*/
static int cpuid = 2;

int main(int argc, char *argv[])
{
  cpu_set_t cpuset;
  long page_size;
  void *mapping;
  int dev_fd;
  int ret;

  page_size = sysconf(_SC_PAGESIZE);

  CPU_ZERO(&cpuset);
  CPU_SET(cpuid, &cpuset);
  ret = sched_setaffinity(0, sizeof(cpuset), &cpuset);
  if (ret < 0) {
    perror("sched_setaffinity");
    exit(EXIT_FAILURE);
  }

  dev_fd = open("/dev/pseudo_lock/newlock", O_RDWR);
  if (dev_fd < 0) {
    perror("open");
    exit(EXIT_FAILURE);
  }

  mapping = mmap(0, page_size, PROT_READ | PROT_WRITE, MAP_SHARED,
          dev_fd, 0);
  if (mapping == MAP_FAILED) {
    perror("mmap");
    close(dev_fd);
    exit(EXIT_FAILURE);
  }

  /* Application interacts with pseudo-locked memory @mapping */

  ret = munmap(mapping, page_size);
  if (ret < 0) {
    perror("munmap");
    close(dev_fd);
    exit(EXIT_FAILURE);
  }

  close(dev_fd);
  exit(EXIT_SUCCESS);
}

20.5.3. アプリケーション間でのロック¶

resctrlファイルシステムにおける特定の操作は、複数のファイルへの読み書きを含むため、原子的に行う必要があります。

例として、L3キャッシュの排他的予約の割り当てには以下が含まれます:

  1. 各ディレクトリまたはリソースごとの「bit_usage」からcbmmasksを読み込みます

  2. ディレクトリcbmmasksのいずれかでクリアされているグローバルCBMビットマスク内の連続するビットセットを見つけます

  3. 新しいディレクトリを作成します

  4. ステップ2で見つかったビットを新しいディレクトリの「schemata」ファイルに設定します

2つのアプリケーションが同時に領域を割り当てる場合、同じビットを割り当てることになり、予約が共有される代わりに排他的になる可能性があります。

resctrlfsにおける原子的操作を調整し、上記の問題を回避するため、以下のロック処理が推奨されます:

ロックはflockに基づいており、libcに含まれており、シェルスクリプトコマンドとしても利用可能です

書き込みロック:

  1. /sys/fs/resctrlに対してflock(LOCK_EX)を取得します

  2. ディレクトリ構造を読み書きします。

  3. funlock

読み込みロック:

  1. /sys/fs/resctrlに対してflock(LOCK_SH)を取得します

  2. 成功した場合、ディレクトリ構造を読み込みます。

  3. funlock

bashでの例:

# Atomically read directory structure
$ flock -s /sys/fs/resctrl/ find /sys/fs/resctrl

# Read directory contents and create new subdirectory

$ cat create-dir.sh
find /sys/fs/resctrl/ > output.txt
mask = function-of(output.txt)
mkdir /sys/fs/resctrl/newres/
echo mask > /sys/fs/resctrl/newres/schemata

$ flock /sys/fs/resctrl/ ./create-dir.sh

Cでの例:

/*
* Example code do take advisory locks
* before accessing resctrl filesystem
*/
#include <sys/file.h>
#include <stdlib.h>

void resctrl_take_shared_lock(int fd)
{
  int ret;

  /* take shared lock on resctrl filesystem */
  ret = flock(fd, LOCK_SH);
  if (ret) {
    perror("flock");
    exit(-1);
  }
}

void resctrl_take_exclusive_lock(int fd)
{
  int ret;

  /* release lock on resctrl filesystem */
  ret = flock(fd, LOCK_EX);
  if (ret) {
    perror("flock");
    exit(-1);
  }
}

void resctrl_release_lock(int fd)
{
  int ret;

  /* take shared lock on resctrl filesystem */
  ret = flock(fd, LOCK_UN);
  if (ret) {
    perror("flock");
    exit(-1);
  }
}

void main(void)
{
  int fd, ret;

  fd = open("/sys/fs/resctrl", O_DIRECTORY);
  if (fd == -1) {
    perror("open");
    exit(-1);
  }
  resctrl_take_shared_lock(fd);
  /* code to read directory contents */
  resctrl_release_lock(fd);

  resctrl_take_exclusive_lock(fd);
  /* code to read and write directory contents */
  resctrl_release_lock(fd);
}

20.6. RDTモニタリングと割り当て使用量の例¶

20.6.1. モニタされたデータの読み込み¶

イベントファイル（例: mon_data/mon_L3_00/llc_occupancy）を読み込むと、対応するMONグループまたはCTRL_MONグループの現在のLLC占有量のスナップショットが表示されます。

20.6.2. 例1（CTRL_MONグループとそのCTRL_MONグループ内のタスクサブセットをモニタ）¶

2スロットマシン（各スロットに1つのL3キャッシュ）でキャッシュビットマスクに4ビットのみある場合:

# mount -t resctrl resctrl /sys/fs/resctrl
# cd /sys/fs/resctrl
# mkdir p0 p1
# echo "L3:0=3;1=c" > /sys/fs/resctrl/p0/schemata
# echo "L3:0=3;1=3" > /sys/fs/resctrl/p1/schemata
# echo 5678 > p1/tasks
# echo 5679 > p1/tasks

デフォルトのリソースグループは変更されていないため、すべてのキャッシュのすべての部分にアクセスできます（スキーマファイルは「L3:0=f;1=f」と読みます）。

グループ「p0」に属するタスクは、キャッシュID 0の「下位」50%とキャッシュID 1の「上位」50%のみから割り当てを行うことができます。グループ「p1」に属するタスクは、両方のソケットの「下位」50%のキャッシュを使用します。

モニタグループを作成し、各モニタグループにタスクサブセットを割り当てます。

# cd /sys/fs/resctrl/p1/mon_groups
# mkdir m11 m12
# echo 5678 > m11/tasks
# echo 5679 > m12/tasks

データを取得（表示されるデータはバイト単位）

# cat m11/mon_data/mon_L3_00/llc_occupancy
16234000
# cat m11/mon_data/mon_L3_01/llc_occupancy
14789000
# cat m12/mon_data/mon_L3_00/llc_occupancy
16789000

親ctrl_monグループは集計データを表示します。

# cat /sys/fs/resctrl/p1/mon_data/mon_l3_00/llc_occupancy
31234000

20.6.3. 例2（タスクの作成時にモニタ）¶

2スロットマシン（各スロットに1つのL3キャッシュ）:

# mount -t resctrl resctrl /sys/fs/resctrl
# cd /sys/fs/resctrl
# mkdir p0 p1

グループが作成された時点でRMIDが割り当てられ、以下のコマンドはその作成からモニタされます。

# echo $$ > /sys/fs/resctrl/p1/tasks
# <cmd>

データを取得:

# cat /sys/fs/resctrl/p1/mon_data/mon_l3_00/llc_occupancy
31789000

20.6.4. 例3（CATサポートなしまたはCATグループ作成前のモニタ）¶

HSWのようなシステムでCQMのみをサポートしCATをサポートしていない場合、resctrlは依然としてマウントされるが、CTRL_MONディレクトリを作成できなくなる。ただし、ユーザーはルートグループ内に異なるMONグループを作成することで、すべてのタスク（カーネルスレッドを含む）を監視できる。

これは、ジョブのキャッシュサイズの占有量をプロファイリングし、それらを異なる割り当てグループに配置する前に、キャッシュサイズの足跡を評価するのに利用できる。

# mount -t resctrl resctrl /sys/fs/resctrl
# cd /sys/fs/resctrl
# mkdir mon_groups/m01
# mkdir mon_groups/m02

# echo 3478 > /sys/fs/resctrl/mon_groups/m01/tasks
# echo 2467 > /sys/fs/resctrl/mon_groups/m02/tasks

グループを別々に監視し、各ドメインのデータも取得できる。以下から明らかなように、タスクは主にドメイン（ソケット）0で処理を行っている。

# cat /sys/fs/resctrl/mon_groups/m01/mon_L3_00/llc_occupancy
31234000
# cat /sys/fs/resctrl/mon_groups/m01/mon_L3_01/llc_occupancy
34555
# cat /sys/fs/resctrl/mon_groups/m02/mon_L3_00/llc_occupancy
31234000
# cat /sys/fs/resctrl/mon_groups/m02/mon_L3_01/llc_occupancy
32789

20.6.5. 例4（リアルタイムタスクの監視）¶

コア4〜7でリアルタイムタスクが実行され、他のCPUで非リアルタイムタスクが実行される単一のソケットシステムがある。このコアでのリアルタイムスレッドのキャッシュ占有量を監視したい。

# mount -t resctrl resctrl /sys/fs/resctrl
# cd /sys/fs/resctrl
# mkdir p1

コア4〜7をp1に移動:

# echo f0 > p1/cpus

LLC占有量のスナップショットを確認:

# cat /sys/fs/resctrl/p1/mon_data/mon_L3_00/llc_occupancy
11234000

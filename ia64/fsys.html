IA-64用の軽量システムコール¶

Started: 13-Jan-2003

Last update: 23-Sep-2003

David Mosberger-Tang <davidm@hpl.hp.com>

「epc」命令を効果的に使用することで、IA-64 Linuxカーネルに新しい実行モードが導入されます。このモードを「fsys-mode」と呼びます。要約すると、通常の実行状態は以下の通りです：

  • カーネルモード：

    レジスタスタックとメモリスタックがどちらもカーネルメモリに切り替えられています。ユーザー側の状態は、カーネルメモリスタックのトップにあるpt-regs構造体に保存されています。

  • ユーザーモード：

    レジスタスタックとカーネルスタックのどちらもユーザーメモリにあります。ユーザー側の状態はCPUレジスタに含まれています。

  • バンク0割込み処理モード：

    これはすべての割込みハンドラが実行を開始する非割込み可能状態です。ユーザー側の状態はCPUレジスタに保持され、一部のカーネル状態はレジスタr16-r31のバンク0に保存されることがあります。

一方、fsys-modeは以下の特異な性質を持ちます：

  • 実行は特権レベル0（最も特権を持つ）で行われます

  • CPUレジスタにはユーザー側とカーネル側の状態が混在する可能性があります（セキュリティに敏感なカーネル側の状態がユーザー側に漏れることを防ぐため、カーネルの責任です）

  • 実行は割込み可能でプリエンプション可能（fsys-modeハンドラは割込みを無効化し、他の割込みソースを回避することでプリエンプションを防ぐことができます）

  • fsys-mode中にメモリスタックもレジスタスタックも信頼できません（これらはユーザー側のスタックを指しており、無効なアドレスや完全に偽のアドレスである可能性があります）

要約すると、fsys-modeはカーネルモードよりもユーザーモードに近いです。もちろん、特権レベルが0であるため、fsys-modeには注意が必要です（以下を参照）。

fsys-modeの識別方法¶

Linuxがfsys-modeで動作しているのは、(a)特権レベルが0（最も特権を持つ）であり、かつ(b)スタックがカーネルメモリに切り替えられていない場合です。便利のため、ヘッダーファイル<asm-ia64/ptrace.h>は3つのマクロを提供しています：

user_mode(regs)
user_stack(task,regs)
fsys_mode(task,regs)

「regs」引数はpt_regs構造体へのポインタです。「task」引数は「regs」ポインタが属するタスク構造体へのポインタです。user_mode()は「regs」ポインタで指すCPU状態がユーザーモード（特権レベル3）で実行されていた場合にTRUEを返します。user_stack()は「regs」ポインタで指す状態がユーザー側スタックで実行されていた場合にTRUEを返します。最後に、fsys_mode()は「regs」ポインタで指す状態がfsys-modeで実行されていた場合にTRUEを返します。fsys_mode()マクロは以下の式に等価です：

!user_mode(regs) && user_stack(task,regs)

fsyscallハンドラの書き方¶

ファイル arch/ia64/kernel/fsys.S には fsyscallハンドラのテーブル(fsyscall_table)が含まれています。このテーブルには各システムコールに対応するエントリが1つずつ含まれています。デフォルトでは、システムコールは fsys_fallback_syscall() によって処理されます。このルーチンはフルなカーネルモードに移行し、通常のLinuxシステムコールハンドラを呼び出す処理を行います。パフォーマンスが重要なシステムコールについては、手で調整した fsyscallハンドラを書くことが可能です。例えば、fsys.S には getpid() システムコールの手で調整したバージョンである fsys_getpid() が含まれています。

fsyscallハンドラのエントリおよびエクスイット時のマシン状態は以下の通りです：

fsyscallハンドラへのエントリ時のマシン状態¶

r10

0

r11

保存された ar.pfs（ユーザー側の値）

r15

システムコール番号

r16

「current」タスクポインタ（通常のカーネルモードでは r13 に保持されます）

r32-r39

システムコール引数

b6

リターンアドレス（ユーザー側の値）

ar.pfs

前のフレーム状態（ユーザー側の値）

PSR.be

ゼロにクリアされる（つまり、レトルトエンディアンのバイト順が有効になります）

他のすべてのレジスタはユーザー側から渡された値を保持する可能性があります

fsyscallハンドラへのエクスイット時の必要なマシン状態¶

r11

保存された ar.pfs（fsyscallハンドラに渡された値）

r15

システムコール番号（fsyscallハンドラに渡された値）

r32-r39

システムコール引数（fsyscallハンドラに渡された値）

b6

リターンアドレス（fsyscallハンドラに渡された値）

ar.pfs

前のフレーム状態（fsyscallハンドラに渡された値）

fsyscallハンドラは非常に低遅延で実行できますが、その高速性にはいくつかの制限があります：

  • fsyscallハンドラは、thread-info構造体のflagsメンバに待機中の作業が存在するか必ず確認しなければなりません。TIF_ALLWORK_MASK フラグのいずれかが設定されている場合、ハンドラはフルなシステムコールにフォールバックする必要があります（fsys_fallback_syscall を呼び出すこと）。

  • fsyscallハンドラは、システムコールの再実行が必要な場合に使用されるため、入力引数（r32-r39、r11、r15、b6、および ar.pfs）を必ず保持しなければなりません。もちろん、すべての「保持される」レジスタも通常のコール規約に従って保持しなければなりません。

  • fsyscallハンドラは、NaT値を含む引数レジスタを使用する前に、NaT消費フェーズを引き起こす可能性のある操作を行う前に、引数レジスタにNaT値が含まれているか必ず確認しなければなりません。システムコール引数にNaT値が含まれている場合、fsyscallハンドラは r8=EINVAL、r10=-1 で即座にリターンすることが可能です。

  • fsyscallハンドラは、「alloc」命令を使用したり、他の操作で必須のRSE（レジスタスタックエンジン）トラフィックを引き起こすことはできません。

  • Fsyscall-handlersは、スタックレジスタに書き込みを行ってはならない。ユーザー側が適切な引数数でハンドラを呼び出したと仮定して安全であるとは限らないからである。

  • Fsyscall-handlersは、パーコア変数にアクセスする際には注意が必要である。適切な安全措置（例：中断を回避）が取られない限り、実行が割込みによって中断され、いつでも別のCPUで再開される可能性がある。

  • Fsyscall-handlersは、敏感なカーネル情報がユーザー側に漏れることを防ぐ必要がある。特に、ユーザー側に戻る前に、スクラッチレジスタに敏感な情報が含まれていないかを確認し、必要に応じてクリアする必要がある（現在のタスクポインタは敏感な情報とはみなされない：ar.k6を通じてすでに公開されているため）。

  • Fsyscall-handlersは、ユーザー記憶域にアクセスする際には、まずアクセス権限を検証しなければならない（これはprobe.r.faultおよび/またはprobe.w.faultを通じて通常行われる）し、メモリアクセス例外に対処する必要がある（これはasmmacro.hで定義されたEX()マクロを通じて行える）。

上述の制限は厳しいように見えるかもしれないが、一部の制限をトレードオフすることで、わずかに高いオーバーヘッドを払うことで柔軟性を確保できる。例えば、Fsyscall-handlersがシャドウレジスタバンクの恩恵を受ける場合、PSR.iおよびPSR.icを一時的に無効化し、バンク0（bsw.0）に切り替え、必要に応じてシャドウレジスタを使用できる。言い換えれば、上述のルールに従うことで非常に高速なシステムコール実行が可能であり（システムコールのセマンティクスを完全に保持しながら）、複雑なケースの処理にも多くの柔軟性がある。

シグナル処理¶

非同期シグナルの配信は、fsysモードが終了するまで遅延させる必要がある。これは低権限転送トラップの助けを借りて実現される：arch/ia64/kernel/process.c:do_notify_resume_user()は、中断されたタスクがfsysモードで実行されていたかを確認し、そうであればPSR.lpを設定して即座に返す。fsysモードが「br.ret」指令を通じて権限レベルを下げる際にトラップが発生し、トラップハンドラがPSR.lpを再びクリアして即座に返す。その後、カーネルの終了パスが待機中のシグナルを検出し、配信する。

PSRの処理¶

「epc」指令はPSRの内容を一切変更しない。これは通常の割込みとは異なり、ほぼすべてのビットをクリアするのとは対照的である。そのため、期待通りに動作するよう注意が必要である。以下では、各PSRビットの処理方法について説明する。

PSR.be

fsys-modeに入るときにクリアされます。最初のロード/ストア命令が実行される前にCPUがlittle-endianモードであることを保証するため、srlz.d命令が使用されます。PSR.beは通常、fsys-modeハンドラから戻る際に復元されません。言い換えれば、ユーザーレベルのコードは、システムコールの実行中にPSR.beが保持されることに依存してはいけません。

PSR.up

変更ありません。

PSR.ac

変更ありません。

PSR.mfl

変更ありません。注意: fsys-modeハンドラはレジスタを書き込むことはできません！

PSR.mfh

変更ありません。注意: fsys-modeハンドラはレジスタを書き込むことはできません！

PSR.ic

変更ありません。注意: fsys-modeハンドラが必要な場合、ビットをクリアできます。

PSR.i

変更ありません。注意: fsys-modeハンドラが必要な場合、ビットをクリアできます。

PSR.pk

変更ありません。

PSR.dt

変更ありません。

PSR.dfl

変更ありません。注意: fsys-modeハンドラはレジスタを書き込むことはできません！

PSR.dfh

変更ありません。注意: fsys-modeハンドラはレジスタを書き込むことはできません！

PSR.sp

変更ありません。

PSR.pp

変更ありません。

PSR.di

変更ありません。

PSR.si

変更ありません。

PSR.db

変更ありません。カーネルは、ユーザーレベルが権限レベル3（ユーザーモード）以外でトリガーされるハードウェアブレイクポイントを設定することを防いでいます。

PSR.lp

変更ありません。

PSR.tb

ラズィー・リダイレクト。fsys-mode内でのジャンプされたブランチトラップが発生した場合、トラップハンドラは機械状態を変更し、syscall_via_break()でのゲートページでの実行を再開します。権限レベル3で実行されます。注意: ジャンプされたブランチは、fsysモードハンドラを呼び出すブランチで発生します。この時点で、システムコールの再開は依然として安全です。システムコール番号が無効な場合、fsys-modeハンドラはユーザーレベルに直接戻ります。この戻りはジャンプされたブランチトラップを発生させますが、トラップは権限レベルを復元した後で発生するため、CPUはすでにfsys-modeから抜け出しているため、特別な処理は必要ありません。

PSR.rt

変更ありません。

PSR.cpl

0にクリアされます。

PSR.is

変更ありません（ゲートページへの移行時に必ず0になります）。

PSR.mc

変更ありません。

PSR.it

変更ありません（必ず1になります）。

PSR.id

変更ありません。注意: ia64 Linuxカーネルはこのビットを設定しません。

PSR.da

変更ありません。注意: ia64 Linuxカーネルはこのビットを設定しません。

PSR.dd

変更ありません。注意: ia64 Linuxカーネルはこのビットを設定しません。

PSR.ss

ラズィー・リダイレクト。設定されている場合、「epc」はシングルステップトラップを発生させます。トラップハンドラは機械状態を変更し、syscall_via_break()でのゲートページでの実行を再開します。権限レベル3で実行されます。

PSR.ri

変更ありません。

PSR.ed

変更ありません。注意: このビットが影響を及ぼすのは、fsys-modeハンドラがスペキュレートしたロードをNaTtedした場合のみです。その場合、これは通常の動作であり、特別な処理は必要ありません。

PSR.bn

変更なし。注意: fsys-mode ハンドラは必要に応じてビットをクリアする場合があります。その場合は PSR.i および PSR.ic も同時にクリアする必要があります。

PSR.ia

変更ありません。注意: ia64 Linuxカーネルはこのビットを設定しません。

高速システムコールの使用¶

高速システムコールを使用するには、ユーザー空間アプリケーションは単に __kernel_syscall_via_epc() を呼び出すだけで十分です。例えば

– fgettimeofday() の呼び出し例 –

– fgettimeofday.S –

#include <asm/asmmacro.h>

GLOBAL_ENTRY(fgettimeofday)
.prologue
.save ar.pfs, r11
mov r11 = ar.pfs
.body

mov r2 = 0xa000000000020660;;  // gate address
                             // found by inspection of System.map for the
                             // __kernel_syscall_via_epc() function.  See
                             // below for how to do this for real.

mov b7 = r2
mov r15 = 1087                       // gettimeofday syscall
;;
br.call.sptk.many b6 = b7
;;

.restore sp

mov ar.pfs = r11
br.ret.sptk.many rp;;       // return to caller
END(fgettimeofday)

– fgettimeofday.S 終了 –

実際には、ゲートアドレスを取得するには、ELF補助ベクター経由で2つの追加値が渡されます（include/asm-ia64/elf.h）

  • AT_SYSINFO : は __kernel_syscall_via_epc() のアドレスです

  • AT_SYSINFO_EHDR : はカーネルゲート ELF DSO のアドレスです

ELF DSO は事前にリンクされたライブラリであり、カーネルがゲートページにマッピングします。これは正しい ELF シェアードオブジェクトであり、ダイナミックロー�ーダーがこのライブラリを認識する場合、他のシェアードライブラリと同様にエクスポートされた関数への呼び出しが可能です。AT_SYSINFO は、歴史的要因によりカーネル DSO 内の __kernel_syscall_via_epc() 関数を指しています（カーネル DSO が導入される前から使用されていました）また、利便性のためにもそのようにしています。

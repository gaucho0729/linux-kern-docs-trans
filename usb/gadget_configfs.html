Linux USB gadget（configfsを介して設定された）¶

2013年4月25日

概要¶

USB Linux Gadgetは、UDC（USB Device Controller）を持ち、USB Hostに接続されることでシリアルポートやマスストレージ機能などの追加機能を拡張するデバイスです。

ゲッタはホストから見ると、複数の設定からなるものと見なされ、それぞれの設定には複数のインターフェースが含まれます。ゲッタの観点ではこれらが「機能」と呼ばれ、シリアル接続やSCSIディスクなど、それぞれの機能を表します。

Linuxはゲッタが使用する機能を複数提供しています。

ゲッタを作成するとは、どの設定が存在するかを決定し、それぞれの設定が提供する機能を指定することを意味します。

configfs（詳しくは Configfs - ユーザー空間駆動型カーネルオブジェクト設定をご覧ください）は、上記の決定をカーネルに伝えることに非常に適しています。このドキュメントはそのやり方について説明しています。

また、configfsがゲッタに統合される設計についても説明しています。

要件¶

この機能を動作させるにはconfigfsが利用可能でなければなりません。そのため、.configファイルにおいてCONFIGFS_FSが「y」または「m」になっている必要があります。この執筆時点ではUSB_LIBCOMPOSITEがCONFIGFS_FSを選択しています。

使い方¶

(configfsを通じて最初に利用可能な機能を説明した元の投稿はここにあります： http://www.spinics.net/lists/linux-usb/msg76388.html)

$ modprobe libcomposite
$ mount none $CONFIGFS_HOME -t configfs

where CONFIGFS_HOMEはconfigfsのマウントポイントです

1. ゲッタの作成¶

作成する各ゲッタに対応するディレクトリを作成する必要があります：

$ mkdir $CONFIGFS_HOME/usb_gadget/<gadget name>

e.g.:

$ mkdir $CONFIGFS_HOME/usb_gadget/g1

...
...
...

$ cd $CONFIGFS_HOME/usb_gadget/g1

各ゲッタにはベンダーID <VID> と製品ID <PID> を指定する必要があります：

$ echo <VID> > idVendor
$ echo <PID> > idProduct

ゲッタにはシリアル番号、メーカー名、製品名などの文字列も必要です。これらを保存するための場所となる文字列サブディレクトリを作成する必要があります。例えば：

$ mkdir strings/0x409

その後、文字列を指定します：

$ echo <serial number> > strings/0x409/serialnumber
$ echo <manufacturer> > strings/0x409/manufacturer
$ echo <product> > strings/0x409/product

2. 設定の作成¶

各ゲッタは複数の設定からなり、それぞれに対応するディレクトリを作成する必要があります：

$ mkdir configs/<name>.<number>

where <name>はファイルシステムで有効な任意の文字列で、<number>は設定番号です。例えば：

$ mkdir configs/c.1

...
...
...

各設定にも文字列が必要なので、各言語に対応するサブディレクトリを作成する必要があります。例えば：

$ mkdir configs/c.1/strings/0x409

その後、設定文字列を指定します：

$ echo <configuration> > configs/c.1/strings/0x409/configuration

設定にはさらに属性を設定することもできます。例えば：

$ echo 120 > configs/c.1/MaxPower

3. 機能の作成¶

ゲッタはいくつかの機能を提供します。各機能に対応するディレクトリを作成する必要があります：

$ mkdir functions/<name>.<instance name>

where <name>は許可された機能名の一つに該当し、instance nameはファイルシステムで有効な任意の文字列です。例えば：

$ mkdir functions/ncm.usb0 # usb_f_ncm.ko gets loaded with request_module()

...
...
...

各関数は、読み取り専用または読み取り/書き込みアクセスを持つ特定の属性セットを提供します。必要に応じて適切に書き込む必要があります。詳しくはDocumentation/ABI/をご参照ください。/configfs-usb-gadget 詳しくは

4. 関数と構成の関連付け¶

現在、複数のデバイスが作成され、それぞれが指定された構成と利用可能な関数を持っています。残る作業は、どの関数がどの構成で利用されるかを指定することです（同じ関数は複数の構成で使用可能です）。これはシンボリックリンクの作成によって実現されます:

$ ln -s functions/<name>.<instance name> configs/<name>.<number>

e.g.:

$ ln -s functions/ncm.usb0 configs/c.1

...
...
...

5. デバイスの有効化¶

上記のすべての手順は、構成と関数を組み合わせてデバイスを構築する目的を持っています。

例としてのディレクトリ構造は以下のようになります:

.
./strings
./strings/0x409
./strings/0x409/serialnumber
./strings/0x409/product
./strings/0x409/manufacturer
./configs
./configs/c.1
./configs/c.1/ncm.usb0 -> ../../../../usb_gadget/g1/functions/ncm.usb0
./configs/c.1/strings
./configs/c.1/strings/0x409
./configs/c.1/strings/0x409/configuration
./configs/c.1/bmAttributes
./configs/c.1/MaxPower
./functions
./functions/ncm.usb0
./functions/ncm.usb0/ifname
./functions/ncm.usb0/qmult
./functions/ncm.usb0/host_addr
./functions/ncm.usb0/dev_addr
./UDC
./bcdUSB
./bcdDevice
./idProduct
./idVendor
./bMaxPacketSize0
./bDeviceProtocol
./bDeviceSubClass
./bDeviceClass

このようなデバイスは最終的に有効化される必要があります。USBホストがこれを列挙できるようにするためです。

デバイスを有効化するには、UDC（USBデバイスコントローラー）にバインドする必要があります:

$ echo <udc name> > UDC

ここで<udc name>は/sys/class/udc/*に存在するものの中から選択します。例:

$ echo s3c-hsotg > UDC

6. デバイスの無効化¶

$ echo "" > UDC

7. 削除処理¶

構成から関数を削除するには:

$ rm configs/<config name>.<number>/<function>

ここで<config name>.<number>は構成を指定し、<function>は削除する関数へのシンボリックリンクを示します。例:

$ rm configs/c.1/ncm.usb0

...
...
...

構成内の文字列ディレクトリを削除するには:

$ rmdir configs/<config name>.<number>/strings/<lang>

e.g.:

$ rmdir configs/c.1/strings/0x409

...
...
...

そして構成を削除するには:

$ rmdir configs/<config name>.<number>

e.g.:

rmdir configs/c.1

...
...
...

関数を削除するには（関数モジュールはアンロードされません）:

$ rmdir functions/<name>.<instance name>

e.g.:

$ rmdir functions/ncm.usb0

...
...
...

デバイス内の文字列ディレクトリを削除するには:

$ rmdir strings/<lang>

e.g.:

$ rmdir strings/0x409

最後にデバイスを削除するには:

$ cd ..
$ rmdir <gadget name>

e.g.:

$ rmdir g1

実装設計¶

以下にconfigfsの仕組みについて説明します。configfsではアイテムとグループがあり、どちらもディレクトリとして表現されます。アイテムとグループの違いは、グループが他のグループを含むことができる点です。以下の図ではアイテムのみが示されています。アイテムとグループはどちらも属性を持ち、これはファイルとして表現されます。ユーザーはディレクトリを作成・削除できますが、ファイルは読み取り専用または読み取り/書き込みアクセスを持つため、削除できません。

configfsのファイルシステム部分は、すべての設定要素で共通の型を持つconfig_items/groupsとconfigfs_attributesを操作します。ただし、これらは使用用途に応じたより大きな構造に埋め込まれています。以下の図では「cs」がconfig_itemを含み、「sa」がconfigfs_attributeを含んでいます。

ファイルシステムのビューは以下のようになります:

./
./cs        (directory)
   |
   +--sa    (file)
   |
   .
   .
   .

ユーザーが「sa」ファイルを読み書きするたびに、struct config_itemとstruct configfs_attributeを受け取る関数が呼び出されます。この関数では、container_ofテクニックを使用して「cs」と「sa」が取得され、適切な「sa」の関数（showまたはstore）が呼び出されます。この関数には「cs」と文字バッファが渡されます。「show」はファイルの内容を表示するため（csからデータをバッファにコピー）、「store」はファイルの内容を変更するため（バッファからデータをcsにコピー）ですが、実装者はこれらの関数が実際に何を行うかを決定します。

typedef struct configured_structure cs;
typedef struct specific_attribute sa;

                                       sa
                       +----------------------------------+
        cs             |  (*show)(cs *, buffer);          |
+-----------------+    |  (*store)(cs *, buffer, length); |
|                 |    |                                  |
| +-------------+ |    |       +------------------+       |
| | struct      |-|----|------>|struct            |       |
| | config_item | |    |       |configfs_attribute|       |
| +-------------+ |    |       +------------------+       |
|                 |    +----------------------------------+
| data to be set  |                .
|                 |                .
+-----------------+                .

ファイル名はconfig item/groupデザイナーによって決定されますが、ディレクトリ名は任意に設定できます。グループにはデフォルトのサブグループが自動的に作成されます。

configfsに関する詳細情報については Configfs - ユーザー空間駆動型カーネルオブジェクト設定.

上記の概念はUSB gadgetとして以下のように対応します:

1. ガジェットは設定グループを持ち、そのグループにはidVendor、idProductなどの属性とデフォルトのサブグループ（configs、functions、strings）が含まれます。属性への書き込みにより情報が適切な場所に保存されます。configs、functions、stringsサブグループでは、ユーザーが配置、機能、および特定の言語の文字列グループを表すサブグループを作成できます。

2. ユーザーは配置と機能を作成し、配置内で機能へのシンボリックリンクを作成します。この情報はガジェットのUDC属性に書き込まれるときに使用され、ガジェットとUDCのバインディングを意味します。drivers/usb/gadget/configfs.c内のコードはすべての配置を反復処理し、各配置内ですべての機能を反復処理してそれらをバインドします。このようにしてガジェット全体がバインドされます。

  1. ファイルdrivers/usb/gadget/configfs.cには

    • ガジェットの設定グループ

    • ガジェットのデフォルトグループ（configs、functions、strings）

    • 機能と配置の関連付け（シンボリックリンク）

4. 各USB機能は自身の設定を示す視点を持ちますので、特定の機能のconfig_groupsはdrivers/usb/gadget/f_*.cの機能実装ファイルで定義されます。

  1. 機能のコードは、usb_get_function_instance()を使用して書かれています。これは、request_moduleを呼び出すことになります。modprobeが動作する限り、特定の機能のモジュールが自動的にロードされます。注意点として、逆は成立しません：ガジェットが無効化され teardown されても、モジュールはロードされたままです。

usbmon¶

はじめに¶

「usbmon」の小文字は、USBバス上のI/Oトラッキングを収集するカーネル内の機能を指します。これはネットワークモニタリングツール（tcpdump(1)やEtherealなど）で使用されるパケットソケットと同様の機能です。同様に、usbmonによって生成されたrawトレースを検査するには、usbdumpやUSBMon（大文字で表記）などのツールが使用されます。

usbmonは、ペリフェラル固有のドライバがホストコントローラードライバ（HCD）に送信するリクエストを報告します。したがって、HCDがバグっている場合、usbmonが報告するトレースはバストランザクションと正確に対応しない可能性があります。これはtcpdumpと同じ状況です。

現在実装されているAPIは「text」と「binary」の2つです。「binary」APIは/dev名前空間内のキャラクタデバイスを通じて利用でき、ABIです。「text」APIは2.6.35以降非推奨ですが、利便性のために利用可能です。

usbmonを用いてraw textトレースを収集する方法¶

パケットソケットとは異なり、usbmonはテキスト形式でトレースを提供するインターフェースを持っています。これは2つの目的で使用されます。1つ目は、より高度なフォーマットが確定するまで、ツール間で共通のトレース交換フォーマットとしての役割を果たします。2つ目は、ツールが利用できない場合でも人間が読み取れるようにするためです。

raw textトレースを収集するには、以下の手順を実行してください。

1. 事前準備¶

debugfsをマウントする（カーネル構成で有効になっている必要があります）、およびusbmonモジュールをロードする（モジュールとして構築されている場合）。usbmonがカーネルに組み込まれている場合は、このステップはスキップされます：

# mount -t debugfs none_debugs /sys/kernel/debug
# modprobe usbmon
#

バスソケットが存在するか確認します：

# ls /sys/kernel/debug/usb/usbmon 0s 0u 1s 1t 1u 2s 2t 2u 3s 3t 3u 4s 4t 4u #

次に、ソケット‘0u’（すべてのバスのパケットをキャプチャ）を使用してステップ#3に進むか、またはステップ#2でデバイスが使用するバスを特定してからステップ#3に進むことができます。これにより、連続的に通信する邪魔なデバイスをフィルタリングできます。

2. 目標デバイスに接続するバスを特定する¶

「cat /sys/kernel/debug/usb/devices」を実行し、デバイスに対応するTラインを検索します。通常はベンダ文字列で検索します。多くの類似デバイスがある場合は、1つを外して、2つの/sys/kernel/debug/usb/devices出力とを比較します。Tラインにはバス番号が含まれています。

例:

T:  Bus=03 Lev=01 Prnt=01 Port=00 Cnt=01 Dev#=  2 Spd=12  MxCh= 0
D:  Ver= 1.10 Cls=00(>ifc ) Sub=00 Prot=00 MxPS= 8 #Cfgs=  1
P:  Vendor=0557 ProdID=2004 Rev= 1.00
S:  Manufacturer=ATEN
S:  Product=UC100KM V2.00

「Bus=03」はバス3を意味します。代替案として、「lsusb」の出力から適切な行からバス番号を取得することもできます。例：

Bus 003 Device 002: ID 0557:2004 ATEN UC100KM V2.00

3. ‘cat’を開始する¶

# cat /sys/kernel/debug/usb/usbmon/3u > /tmp/1.mon.out

単一のバスを監視するには、以下のコマンドを実行してください。すべてのバスを監視する場合は：

# cat /sys/kernel/debug/usb/usbmon/0u > /tmp/1.mon.out

このプロセスは終了するまで読み続けます。自然に、出力は望ましい場所にリダイレクトできます。これは望ましい方法です、なぜなら出力が非常に長くなるからです。

4. USBバス上で望む操作を実行します¶

ここではトラフィックを生成する操作を行います：フラッシュメモリを挿す、ファイルをコピーする、ウェブカメラを制御するなど。

5. catプロセスを終了します¶

通常はキーボード割込み（Control-C）で行います。

この時点で出力ファイル（この例では/tmp/1.mon.out）を保存したり、メールで送信したり、テキストエディタで確認したりできます。最後の場合は、お好みのエディタにファイルサイズが適していることを確認してください。

Rawテキストデータ形式¶

現在サポートされている形式は2種類です：元の形式（'1t'形式）と'1u'形式です。'1t'形式はカーネル2.6.21で非推奨となりました。'1u'形式はISOフレーム記述子やインターバルなどのいくつかのフィールドを追加しており、やや長い行を生成しますが、それ以外は'1t'形式の完全なサブセットです。

プログラム内で'1t'形式と'1u'形式を区別する場合は、「address」ワード（以下参照）を見てください。'1u'形式ではバス番号が追加されています。2つのコロンが含まれている場合は'1t'形式、それ以外は'1u'形式です。

任意のテキスト形式データは、URB送信、URBコールバック、送信エラーなどのイベントストリームから構成されます。それぞれのイベントは、空白文字で区切られた単語からなるテキスト行です。単語の数や位置はイベントタイプにより異なりますが、すべてのタイプで共通する単語の集合があります。

左から右までの単語一覧は以下の通りです：

  • URBタグ。これはURBを識別するためのもので、通常はURB構造体のカーネル内アドレス（16進数）ですが、セッション番号や他の一意な文字列でも可能です（現実的であれば）。

  • マイクロ秒単位のタイムスタンプ、10進数です。タイムスタンプの分解能は利用可能なクロックにより異なり、マイクロ秒より劣る場合があります（たとえばjiffiesを用いる実装の場合）。

  • イベントタイプ。これはイベントの形式を指し、URBタイプではありません。利用可能なタイプは：S - 送信、C - コールバック、E - 送信エラーです。

  • 「address」ワード（以前は「pipe」）。これはコロンで区切られた4つのフィールドからなり、URBタイプと方向、バス番号、デバイスアドレス、エンドポイント番号を含みます。タイプと方向は以下の方法で2バイトでエンコードされます：

    Ci

    Co

    コントロール入力および出力

    Zi

    Zo

    イソクロナス入力および出力

    Ii

    Io

    割込み入力および出力

    Bi

    Bo

    バルク入力および出力

    バス番号、デバイスアドレス、エンドポイントは10進数ですが、人間が読みやすいように前導ゼロを含む場合があります。

  • URBステータスワード。これは文字か、コロンで区切られた複数の数字のいずれかです。URBステータス、インターバル、開始フレーム、エラー数が含まれます。『アドレス』ワードとは異なり、ステータス以外のフィールドはすべてオプションです。インターバルは割り込みおよびイソクロナスURBの場合にのみ表示されます。開始フレームはイソクロナスURBの場合にのみ表示されます。エラー数はイソクロナスコールバックイベントの場合にのみ表示されます。

    ステータスフィールドは10進数の数値で、負の値になることもあります。これはURBの『ステータス』フィールドを表します。サブミッションでは意味がありませんが、スクリプトの解析を補助するためには常に存在します。エラーが発生した場合、このフィールドにはエラーコードが含まれます。

    コントロールパケットのサブミッションの場合、このフィールドにはセットアップタグが含まれ、数字のグループではなくなります。セットアップタグが存在するかどうかは、数字でないため簡単に判断できます。したがって、スクリプトがこのワードに数字のグループを見つけた場合、データ長を読みます（イソクロナスURBを除く）。何か他のもの（例: 文字）を見つけた場合は、データ長またはイソクロナスディスクリプタを読み出す前にセットアップパケットを読みます。

  • セットアップパケット（存在する場合）は5つのワードから構成され、bmRequestType、bRequest、wValue、wIndex、wLengthのそれぞれ1つずつで、USB Specification 2.0で指定されています。セットアップタグが「s」の場合、これらのワードは安全にデコードできます。それ以外の場合、セットアップパケットは存在しましたがキャプチャされず、フィールドにはフィラーが含まれています。

  • イソクロナスフレームディスクリプタの数とディスクリプタ自体です。イソクロナス転送イベントがディスクリプタのセットを持つ場合、URB内のディスクリプタの総数が最初に表示され、その後ディスクリプタごとに1つのワードが表示されます（最大5つまで）。このワードは、ステータス、オフセット、長さの3つの10進数でコロンで区切られています。サブミッションでは初期長さが報告され、コールバックでは実際の長さが報告されます。

  • データ長。サブミッションではリクエストされた長さが、コールバックでは実際の長さが含まれます。

  • データタグ。usbmonがデータを常にキャプチャするとは限りません。長さがゼロでない場合でもデータワードが含まれるかどうかは、このタグが「＝」かどうかで判断されます。

  • データワードは、ビッグエンディアンの16進形式で続きます。注意点として、これらはマシンワードではなく、単なるバイトストリームをワード単位に分割して読みやすさを確保したものです。そのため、最後のワードには1〜4バイトが含まれることがあります。収集されたデータの長さは制限されており、データ長レポートのデータ長よりも短くなる可能性があります。イソクロナス入力(Zi)の完了でバッファ内にデータが希薄な場合、収集されたデータの長さはデータ長値よりも長くなることがあります（データ長は受信したバイト数のみをカウントするのに対し、データワードは転送バッファ全体を含みます）。

例:

ポート状態を取得するための入力コントロール転送:

d5ea89a0 3575914555 S Ci:1:001:0 s a3 00 0000 0003 0004 4 <
d5ea89a0 3575914560 C Ci:1:001:0 0 4 = 01050000

SCSIコマンド0x28（READ_10）を31バイトのバULKラッパーでストレージデバイスアドレス5に送信するための出力バULK転送:

dd65f0e8 4128379752 S Bo:1:005:2 -115 31 = 55534243 ad000000 00800000 80010a28 20000000 20000040 00000000 000000
dd65f0e8 4128379808 C Bo:1:005:2 0 31 >

Rawバイナリ形式とAPI¶

APIの全体的なアーキテクチャは上記と同じですが、イベントはバイナリ形式で届けられます。各イベントは以下の構造で送信されます（名前は仮造ですが、参照用に設定しています）:

struct usbmon_packet {
      u64 id;                 /*  0: URB ID - from submission to callback */
      unsigned char type;     /*  8: Same as text; extensible. */
      unsigned char xfer_type; /*    ISO (0), Intr, Control, Bulk (3) */
      unsigned char epnum;    /*     Endpoint number and transfer direction */
      unsigned char devnum;   /*     Device address */
      u16 busnum;             /* 12: Bus number */
      char flag_setup;        /* 14: Same as text */
      char flag_data;         /* 15: Same as text; Binary zero is OK. */
      s64 ts_sec;             /* 16: gettimeofday */
      s32 ts_usec;            /* 24: gettimeofday */
      int status;             /* 28: */
      unsigned int length;    /* 32: Length of data (submitted or actual) */
      unsigned int len_cap;   /* 36: Delivered length */
      union {                 /* 40: */
              unsigned char setup[SETUP_LEN]; /* Only for Control S-type */
              struct iso_rec {                /* Only for ISO */
                      int error_count;
                      int numdesc;
              } iso;
      } s;
      int interval;           /* 48: Only for Interrupt and ISO */
      int start_frame;        /* 52: For ISO */
      unsigned int xfer_flags; /* 56: copy of URB's transfer_flags */
      unsigned int ndesc;     /* 60: Actual number of ISO descriptors */
};                            /* 64 total length */

これらのイベントはread(2)でキャラクタデバイスから読み取ることで受信可能です。ioctl(2)を使用することも、mmapでバッファにアクセスすることもできます。ただし、read(3)は互換性のため最初の48バイトのみを返します。

キャラクタデバイスは通常/dev/usbmonNと呼ばれ、NはUSBバス番号です。ゼロ（/dev/usbmon0）は特殊で「すべてのバス」を意味します。注意点として、特定の命名ポリシーはLinuxディストリビューションによって設定されます。

/dev/usbmon0を手動で作成する場合、root所有でモード0600にする必要があります。それ以外の場合、権限のないユーザーがキーボードトラフィックを盗聴できる可能性があります。

以下のioctlコールが利用可能です（MON_IOC_MAGIC 0x92）:

MON_IOCQ_URB_LENは_IO(MON_IOC_MAGIC, 1)で定義されています

このコールは次のイベントに含まれるデータの長さを返します。注意点として、ほとんどのイベントはデータを含まないため、このコールがゼロを返してもイベントが利用不可であるとは限りません。

MON_IOCG_STATSは_ION(MON_IOC_MAGIC, 3, struct mon_bin_stats)で定義されています

引数は以下の構造体へのポインタです:

struct mon_bin_stats {
      u32 queued;
      u32 dropped;
};

「queued」メンバはバッファ内に現在キューイングされているイベント数を示し（最後のリセットからの処理済みイベント数とは異なります）

「dropped」メンバは最後のMON_IOCG_STATS呼び出し以来失われたイベント数を示します。

MON_IOCT_RING_SIZEは_IO(MON_IOC_MAGIC, 4)で定義されています

このコールはバッファサイズを設定します。引数はバイト単位のサイズです。サイズは次のチャンク（またはページ）に四捨五入される可能性があります。このカーネルで指定されたサイズが指定範囲外の場合、-EINVALで失敗します。

MON_IOCQ_RING_SIZE、定義は _IO(MON_IOC_MAGIC, 5)

このコールはバッファの現在のサイズ（バイト単位）を返します。

MON_IOCX_GET、定義は _IOW(MON_IOC_MAGIC, 6, struct mon_get_arg) MON_IOCX_GETX、定義は _IOW(MON_IOC_MAGIC, 10, struct mon_get_arg)

これらのコールは、カーネルバッファにイベントがなければ待機し、最初のイベントを返します。引数は以下の構造体へのポインタです：

struct mon_get_arg {
      struct usbmon_packet *hdr;
      void *data;
      size_t alloc;           /* Length of data (can be zero) */
};

コール前にはhdr、data、allocを埋めます。コール後、hdrポインタが指す領域には次のイベント構造体が、dataバッファにはデータ（存在すれば）が格納されます。イベントはカーネルバッファから削除されます。

MON_IOCX_GETはhdr領域に48バイトをコピーし、MON_IOCX_GETXは64バイトをコピーします。

MON_IOCX_MFETCH、定義は _IOWR(MON_IOC_MAGIC, 7, struct mon_mfetch_arg)

このioctlはアプリケーションがmmap(2)でバッファにアクセスする場合に主に使用されます。引数は以下の構造体へのポインタです：

struct mon_mfetch_arg {
      uint32_t *offvec;       /* Vector of events fetched */
      uint32_t nfetch;        /* Number of events to fetch (out: fetched) */
      uint32_t nflush;        /* Number of events to flush */
};

このioctlは3段階で動作します。

まず、nflushイベントをカーネルバッファから削除・破棄します。実際に破棄されたイベント数はnflushに返されます。

次に、O_NONBLOCKで擬似デバイスを開いていない限り、バッファにイベントが存在するのを待機します。

最後に、mmapバッファ内の最大nfetchオフセットを取得し、offvecに保存します。実際に取得されたイベントオフセット数はnfetchに保存されます。

MON_IOCH_MFLUSH、定義は _IO(MON_IOC_MAGIC, 8)

このコールはカーネルバッファからイベントを削除します。引数は削除するイベント数です。バッファに指定された数より少ないイベントしか含まれていない場合、すべてのイベントを削除し、エラーは報告されません。イベントがまったくない場合でも動作します。

FIONBIO

ioctl(2)とread(2)に加えて、バイナリAPIの特殊ファイルはselect(2)とpoll(2)でポーリング可能です。ただしlseek(2)は動作しません。

バイナリAPIのカーネルバッファのメモリマップアクセス

  • 基本的な考え方はシンプルです：

準備として、現在のサイズを取得してバッファをmmap(2)でマッピングし、以下の擬似コードのようなループを実行します：

したがって、主な考え方はNイベントごとに1回のioctlを実行することです。

struct mon_mfetch_arg fetch;
struct usbmon_packet *hdr;
int nflush = 0;
for (;;) {
   fetch.offvec = vec; // Has N 32-bit words
   fetch.nfetch = N;   // Or less than N
   fetch.nflush = nflush;
   ioctl(fd, MON_IOCX_MFETCH, &fetch);   // Process errors, too
   nflush = fetch.nfetch;       // This many packets to flush when done
   for (i = 0; i < nflush; i++) {
      hdr = (struct ubsmon_packet *) &mmap_area[vec[i]];
      if (hdr->type == '@')     // Filler packet
         continue;
      caddr_t data = &mmap_area[vec[i]] + 64;
      process_packet(hdr, data);
   }
}

このコールはカーネルバッファからイベントを削除します。引数は削除するイベント数です。バッファに指定された数より少ないイベントしか含まれていない場合、すべてのイベントを削除し、エラーは報告されません。イベントがまったくない場合でも動作します。

バッファが環状であるにもかかわらず、返却されるヘッダーとデータはバッファの端を越えないため、上記の擬似コードでは収集が必要ありません。

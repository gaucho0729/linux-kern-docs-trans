RISC-V プラットフォームにおける PMU のサポート¶

Alan Kao <alankao@andestech.com>, 2018年3月

はじめに¶

本執筆時点でのRISC-V ISAプライベート版バージョン1.10で記載されているperf_event関連の機能は以下の通りです（詳細はマニュアルを参照してください）:

  • [m|s]counteren

  • mcycle[h], cycle[h]

  • minstret[h], instret[h]

  • mhpeventx, mhpcounterx[h]

このような機能セットだけでは、perfの移植には多くの作業が必要です。これは以下の一般的なアーキテクチャ性能モニタリング機能が欠如しているためです:

  • カウンタの有効/無効化 カウンタは常に自由に動作しています。

  • カウンタオーバーフローによる割り込み プライベート版仕様にはこの機能はありません。

  • 割り込みインジケータ カウンタごとに割り込みポートを用意するのは現実的ではありませんので、ソフトウェアがどのカウンタがオーバーフローしたかを通知するための割り込みインジケータが必要です。

  • カウンタへの書き込み カーネルがカウンタを変更できないため、SBIを用いてサポートする予定です[1]。代替案として、一部のベンダーはM-S-Uモデルマシン向けにハードウェア拡張を実装してカウンタを直接書き込む方法を検討しています。

このドキュメントは、開発者にカーネルでのPMUサポートの簡単なガイドを提供することを目的としています。以下のセクションではperfのメカニズムと実装すべきタスクを簡潔に説明します。

以前の議論はここで確認できます[1][2]。また、関連するカーネル構造体については付録を参照すると役立つかもしれません。

1. 初期化¶

riscv_pmu は型 struct riscv_pmuのグローバルポインタであり、perfの内部規約とPMU固有のパラメータを含みます。PMUを表すインスタンスを宣言する必要があります。デフォルトでは、 riscv_pmu は定数構造体 riscv_base_pmuを指しており、ベースラインのQEMUモデルに非常に基本的なサポートを提供しています。

その後、インスタンスのポインタを riscv_pmu に割り当てることで既存の最小限の実装ロジックを活用できます。あるいは、自前の riscv_init_platform_pmu は常に有効な文字列を返すため、また、不要にdestバッファの末尾をゼロに強制しないからです。ゼロ化が必要な場合は、

2. イベント初期化¶

ユーザーがperfコマンドでイベントを監視する際、まずユーザー空間のperfツールが複数の perf_event_open システムコールに解釈され、それぞれが前のステップで割り当てられた event_init メンバ関数の本体を呼び出します。 riscv_base_pmuの場合、それは riscv_event_init.

この関数の主な目的は、ユーザーが提供したイベントをビットマップに変換し、ハードウェア関連の制御レジスタやカウンターを直接操作できるようにすることです。この変換は、以下のマッピングとメソッドに基づいて行われます。 riscv_pmu.

注意: 一部の機能はこの段階でも実行可能です:

  1. 割込み設定（次のセクションで説明されています）;

  2. 特権レベル設定（ユーザー空間のみ、カーネル空間のみ、両方）;

  3. デストラクタ設定。通常は以下の関数を適用するだけで十分です riscv_destroy_event;

  4. 非サンプリングイベントの調整、以下の関数などによって利用されます perf_adjust_period, 通常は以下のようになります:

    if (!is_sampling_event(event)) {
        hwc->sample_period = x86_pmu.max_period;
        hwc->last_period = hwc->sample_period;
        local64_set(&hwc->period_left, hwc->sample_period);
}

以下のケースでは riscv_base_pmu, 現在は(3)のみが提供されています。

3. 割込み¶

3.1. 割込み初期化

これは通常、以下のメソッドの開始時に発生します。 event_init メソッド。一般的な実装では、以下のようなコードセグメントになります:

int x86_reserve_hardware(void)
{
      int err = 0;

      if (!atomic_inc_not_zero(&pmc_refcount)) {
              mutex_lock(&pmc_reserve_mutex);
              if (atomic_read(&pmc_refcount) == 0) {
                      if (!reserve_pmc_hardware())
                              err = -EBUSY;
                      else
                              reserve_ds_buffers();
              }
              if (!err)
                      atomic_inc(&pmc_refcount);
              mutex_unlock(&pmc_reserve_mutex);
      }

      return err;
}

そして、魔法は以下の reserve_pmc_hardware、通常はアトミック操作を行い、実装されたIRQをグローバルな関数ポインタからアクセス可能にします。 release_pmc_hardware は逆の目的を持ち、前節で説明したイベントデストラクタで使用されます。

(注意: すべてのアーキテクチャにおける実装では、 reserve/release ペアは常にIRQ設定であり、 pmc_hardware この表現はどこか誤解を招くように感じられます。これはイベントと物理カウンターのバインディングを扱うものではなく、次のセクションで紹介される内容です。

3.2. IRQ構造

基本的に、IRQは以下の擬似コードを実行します:

for each hardware counter that triggered this overflow

    get the event of this counter

    // following two steps are defined as *read()*,
    // check the section Reading/Writing Counters for details.
    count the delta value since previous interrupt
    update the event->count (# event occurs) by adding delta, and
               event->hw.period_left by subtracting delta

    if the event overflows
        sample data
        set the counter appropriately for the next overflow

        if the event overflows again
            too frequently, throttle this event
        fi
    fi

end for

しかし、現在のところRISC-Vの実装にはパフォーマンス用の割り込みを設計したものはありませんので、詳細は今後完成する予定です。

4. カウンターの読み書き¶

これらは対称的に見えるものの、perfでは非常に異なる扱いをします。読み取りに関しては、 読み取り インターフェースが struct pmu内にありますが、これは単なる読み取りにとどまらず、文脈により 読み取り 関数はイベント->countの内容を読み取りつつ、次の割り込み用にイベント->hw.period_leftを更新します。

しかし、perfのコアはカウンターへの直接書き込みは必要ありません。カウンターの書き込みは1) pmu->startという抽象化の背後で行われます。つまり、カウンターを次の割り込み用に適切な値に設定する必要があり、2) IRQ内では同じ適切な値に設定する必要があります。

RISC-Vでは読み取りは問題ありませんが、書き込みにはいくつかの努力が必要です。カウンターはSモードでの書き込みが許可されていないからです。

5. add()/del()/start()/stop()¶

基本的な考え方は、add()/del()がPMUにイベントを追加/削除し、 start()/stop() PMU内の特定のイベントのカウンターを開始/停止します。これらすべては同じ引数を取ります: struct perf_event *event および int flag.

perfを状態機械として考えると、これらの関数はこれらの状態間の状態遷移プロセスとして機能します。3つの状態(event->hw.state)が定義されています:

  • PERF_HES_STOPPED: カウンターが停止している状態

  • PERF_HES_UPTODATE: event->countが最新である状態

  • PERF_HES_ARCH: アーキテクチャ依存の使用方法… 今回は必要ありません

これらの状態遷移の通常のフローは以下の通りです:

  • ユーザーがperfイベントを起動すると、以下のように呼び出されます event_init.

  • コンテキストスイッチイン時に 追加 perfコアによってPERF_EF_STARTフラグで呼び出され、イベントが追加後に起動されるべきです。この段階で、一般的なイベントは物理カウンターにバインドされます（必要があれば）。状態はPERF_HES_STOPPEDとPERF_HES_UPTODATEに変更され、現在停止しており、ソフトウェアイベントカウントの更新も必要ありません。

    • start その後、呼び出され、カウンターが有効になります。PERF_EF_RELOADフラグが含まれる場合、カウンターに適切な値を書き込みます（詳細は前節を参照）。PERF_EF_RELOADフラグが含まれない場合は何も書きません。この時点で状態は停止も更新もされていないため、初期状態に戻ります。

  • コンテキストスイッチアウト時に リスナーが停止したときに呼ばれます 呼び出されます。その後、PMU内のすべてのイベントを確認し、 停止 を呼び出してカウントを更新します。

    • 停止 は リスナーが停止したときに呼ばれます によって呼び出され、PERF_EF_UPDATEフラグとともにperfコアによって呼び出されます。これは通常、 読み取り と同じサブルーチンを共有し、同じロジックを用います。状態は再びPERF_HES_STOPPEDとPERF_HES_UPTODATEになります。

    • これらの2つのペアのライフサイクル: 追加 および リスナーが停止したときに呼ばれます タスクがインとアウトするたびに繰り返し呼び出されます; start および 停止 perfコアが迅速な停止と再開が必要な場合にも呼び出されます。たとえば、割り込み期間が調整されるときなど。

現在の実装は十分で、今後追加の機能に簡単に拡張可能です。

A. 関連する構造体¶

  • struct pmu: include/linux/perf_event.h

  • struct riscv_pmu: arch/riscv/include/asm/perf_event.h

    これらの構造体は読み取り専用として設計されています。

    struct pmu いくつかの関数ポインタインターフェースを定義し、多くは struct perf_event をメインの引数として使用し、perfの内部状態機械に従ってperfイベントを処理します（詳細はkernel/events/core.cを参照）。

    struct riscv_pmu PMU固有のパラメータを定義します。命名規則は他のすべてのアーキテクチャと同じです。

  • struct perf_event: include/linux/perf_event.h

  • struct hw_perf_event

    一般的なperfイベントを表し、ハードウェア関連の詳細を含む汎用構造体です。

  • struct riscv_hw_events: arch/riscv/include/asm/perf_event.h

    イベントの状態を保持する構造体は、固定されたメンバとしてイベントの数とイベントの配列の2つの要素を持っています。

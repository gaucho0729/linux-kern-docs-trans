Open Firmware Device Treeユニットテスト¶

著者: Gaurav Minocha <gaurav.minocha@os>gaurav.minocha.os@gmail.com>

1. はじめに¶

このドキュメントでは、OFユニットテストを実行するために必要なテストデータが、マシンのアーキテクチャにかかわらず、ライブツリーに動的にアタッチされる仕組みについて説明します。

次のドキュメントを読み終えることをお勧めします。

  1. LinuxとDevice Tree

  2. http://www.devicetree.org/Device_Tree_Usage

OF Selftestは、デバイスドライバ開発者に提供されるインターフェース（include/linux/of.h）をテストするためのもので、未フラット化されたデバイスツリーのデータ構造からデバイス情報を取得する機能を検証します。このインターフェースは、さまざまな使用ケースにおいて多くのデバイスドライバで使用されています。

2. テストデータ¶

デバイスツリーのソースファイル（drivers/of/unittest-data/testcases.dts）には、drivers/of/unittest.cで自動化されたユニットテストを実行するために必要なテストデータが含まれています。現在、testcases.dtsには以下のデバイスツリーのソースインクルードファイル（.dtsi）が含まれています：

drivers/of/unittest-data/tests-interrupts.dtsi
drivers/of/unittest-data/tests-platform.dtsi
drivers/of/unittest-data/tests-phandle.dtsi
drivers/of/unittest-data/tests-match.dtsi

OF_SELFTESTが有効になっている場合、カーネルをビルドする際には以下のmakeルールが使用されます：

$(obj)/%.dtb: $(src)/%.dts FORCE
        $(call if_changed_dep, dtc)

DTソースファイル（testcases.dts）をバイナリブロブ（testcases.dtb）にコンパイルするために使用され、これはフラット化されたDTとしても呼ばれます。

その後、以下のルールを使用して、上記のバイナリブロブがアセンブリファイル（testcases.dtb.S）としてラップされます：

$(obj)/%.dtb.S: $(obj)/%.dtb
        $(call cmd, dt_S_dtb)

アセンブリファイルはオブジェクトファイル（testcases.dtb.o）にコンパイルされ、カーネルイメージにリンクされます。

2.1. テストデータの追加¶

未フラット化されたデバイスツリー構造：

未フラット化されたデバイスツリーは、以下に記述された木構造形式で接続されたdevice_node(s)から構成されています：

// following struct members are used to construct the tree
struct device_node {
    ...
    struct  device_node *parent;
    struct  device_node *child;
    struct  device_node *sibling;
    ...
};

図1は、子ノードと兄弟ポインタのみを考慮したマシンの未フラット化デバイスツリーの一般的な構造を説明しています。また、別のポインタが存在します、 *parent、これはツリーを逆方向にトラバースするために使用されます。したがって、特定のレベルでは、子ノードとすべての兄弟ノードが、共通のノード（例：child1、sibling2、sibling3、sibling4の親はルートノードを指します）を指す親ポインタを持ちます：

root ('/')
|
child1 -> sibling2 -> sibling3 -> sibling4 -> null
|         |           |           |
|         |           |          null
|         |           |
|         |        child31 -> sibling32 -> null
|         |           |          |
|         |          null       null
|         |
|      child21 -> sibling22 -> sibling23 -> null
|         |          |            |
|        null       null         null
|
child11 -> sibling12 -> sibling13 -> sibling14 -> null
|           |           |            |
|           |           |           null
|           |           |
null        null       child131 -> null
                        |
                        null

図1: 未フラット化デバイスツリーの一般的な構造

OFユニットテストを実行する前に、マシンのデバイスツリー（存在する場合）にテストデータをアタッチする必要があります。したがって、selftest_data_add()が呼ばれた場合、まず以下のカーネルシンボルを通じてカーネルイメージにリンクされたフラット化されたデバイスツリーのデータを読み込みます：

__dtb_testcases_begin - address marking the start of test data blob
__dtb_testcases_end   - address marking the end of test data blob

次に、of_fdt_unflatten_tree()を呼び出してフラット化されたブロブを未フラット化します。最後に、マシンのデバイスツリー（つまりライブツリー）が存在する場合、未フラット化されたテストデータツリーをライブツリーにアタッチします。そうでない場合は、自身をライブデバイスツリーとしてアタッチします。

attach_node_and_children()は、of_attach_node()を使用して、以下の説明のようにノードをライブツリーに接続します。この動作を説明するために、図1に示すライブツリーに図2に示すテストデータツリーが接続される様子を示します:

root ('/')
    |
testcase-data
    |
test-child0 -> test-sibling1 -> test-sibling2 -> test-sibling3 -> null
    |               |                |                |
test-child01      null             null             null

図2: ライブツリーに接続される例としてのテストデータツリー。

上述のシナリオによると、ライブツリーはすでに存在しているため、ルートノード(‘/’)は接続不要です。すべての他のノードは、各ノードに対してof_attach_node()を呼び出すことで接続されます。

of_attach_node()関数では、新しいノードをライブツリーの指定された親ノードの子として接続します。ただし、親ノードにすでに子が存在する場合、新しいノードは現在の子を置き換え、その子を兄弟ノードにします。したがって、図1に示すライブツリーにテストケースデータノードが接続される際（図1）、最終的な構造は図3に示すようになります:

root ('/')
|
testcase-data -> child1 -> sibling2 -> sibling3 -> sibling4 -> null
|               |          |           |           |
(...)             |          |           |          null
                |          |         child31 -> sibling32 -> null
                |          |           |           |
                |          |          null        null
                |          |
                |        child21 -> sibling22 -> sibling23 -> null
                |          |           |            |
                |         null        null         null
                |
                child11 -> sibling12 -> sibling13 -> sibling14 -> null
                |          |            |            |
                null       null          |           null
                                        |
                                        child131 -> null
                                        |
                                        null
-----------------------------------------------------------------------

root ('/')
|
testcase-data -> child1 -> sibling2 -> sibling3 -> sibling4 -> null
|               |          |           |           |
|             (...)      (...)       (...)        null
|
test-sibling3 -> test-sibling2 -> test-sibling1 -> test-child0 -> null
|                |                   |                |
null             null                null         test-child01

図3: テストケースデータを接続した後のライブデバイスツリー構造。

気づきがある読者の方は、テストチルド0ノードが以前の構造（図2）と比較して最後の兄弟ノードになったことに気づいたことでしょう。テストチルド0を最初に接続した後、テストシルバー1が接続され、その結果、チルドノード（つまりテストチルド0）が兄弟ノードとなり、自身がチルドノードになることになります。

重複するノードが見つかった場合（つまり、full_nameプロパティが同じでライブツリーにすでに存在するノードがある場合）、そのノードは接続されず、代わりにupdate_node_properties()関数を呼び出して、そのプロパティをライブツリーのノードに更新します。

2.2. テストデータの削除¶

テストケースの実行が完了した後、selftest_data_removeが呼び出されて、最初に接続されたデバイスノードが削除されます（最初に葉ノードが分離され、その後親ノードが上位に移動しながら削除され、最終的に全体のツリーが削除されます）。selftest_data_remove()はdetach_node_and_children()を呼び出し、of_detach_node()を使用してライブデバイスツリーからノードを分離します。

ノードを分離する際、of_detach_node()は、指定されたノードの親の子ポインタをその兄弟ノードに更新するか、または適切な処理により前の兄弟ノードを指定されたノードの兄弟ノードに接続します。以上です :)

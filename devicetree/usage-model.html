LinuxとDevice Tree¶

Linux におけるデバイスツリー データの利用モデル

著者

Grant Likely <grant.likely@secretlab.ca>

この記事では、Linux がデバイスツリーを使用する仕組みについて説明します。デバイスツリー データ形式の概要については、devicetree.org にあるデバイスツリー利用ページをご参照ください1.

1(1,2)

https://elinux.org/Device_Tree_Usage

「Open Firmware デバイスツリー」、または単にデバイスツリー（DT）と呼ばれるものは、ハードウェアを記述するためのデータ構造および言語です。より具体的には、オペレーティングシステムがハードウェアの詳細をハードコードせずに読み取れるようにするためのハードウェアの記述です。

構造的には、DT は木構造、または名前がついたノードを持つ無閉路グラフであり、ノードは任意の数の名前付きプロパティを持つことができ、それらは任意のデータを包み込むことができます。また、自然な木構造を超えてノード間の任意のリンクを生成するメカニズムも存在します。

概念的には、データバス、割込みライン、GPIO 接続、周辺機器などの典型的なハードウェア特性を記述するためのデータがツリーにどのように表示されるべきかを定義する、共通の使用規約のセット、つまり「バインディング」と呼ばれるものが定義されています。

可能な限り、既存のバインディングを使用してハードウェアを記述し、既存のサポートコードを最大限に活用します。しかし、プロパティおよびノード名は単なるテキスト文字列であるため、新しいノードおよびプロパティを定義することで既存のバインディングを拡張したり、新しいバインディングを作成したりするのは簡単です。ただし、既存のバインディングを調査せずに新しいバインディングを作成するのは注意が必要です。現在、I2C バス用に2つの異なる互換性のないバインディングが存在しており、これは新しいバインディングが作成される前に既存システムでの I2C デバイスの列挙方法を調査しなかったためです。

1. 歴史¶

DT はもともと Open Firmware によって作成され、Open Firmware からクライアントプログラム（例：オペレーティングシステム）へデータを渡す通信方法の一部として使用されていました。オペレーティングシステムは、デバイスツリーを使用してハードウェアのトポロジを実行時に発見し、ドライバがすべてのデバイスに用意されていると仮定した場合、ハードウェアの大部分をハードコードせずにサポートしました。

Open Firmware は PowerPC および SPARC プラットフォームで一般的に使用されるため、Linux はこれらのアーキテクチャのサポートにおいて長年デバイスツリーを使用してきました。

2005年にPowerPC Linuxが大規模なリファクタリングを開始し、32ビットと64ビットのサポートを統合する際、すべてのPowerPCプラットフォームでDT（Device Tree）のサポートを必須化するという決定がなされました。これは、Open Firmwareを使用するかどうかに関わらずです。これを実現するため、Flattened Device Tree（FDT）と呼ばれるDT表現が作成され、これは実際のOpen Firmware実装を必要とせずにカーネルにバイナリーブロブとして渡すことが可能となりました。U-Boot、kexec、その他のブートローダーは、Device Tree Binary（dtb）を渡すだけでなく、ブート時にdtbを変更する機能も追加されました。また、PowerPCブート Wrapper（arch/powerpc/boot/*)にもDTが追加され、既存のDTを意識していないファームウェアでのブートをサポートするため、カーネルイメージとdtbを一緒にパッケージ化できるようになりました。

その後、FDTインフラストラクチャがすべてのアーキテクチャで利用可能になるように一般化されました。本書の執筆時点では、6つの主要アーキテクチャ（arm、microblaze、mips、powerpc、sparc、x86）と1つの非主要アーキテクチャ（nios）が、ある程度のDTサポートを提供しています。

2. データモデル¶

2.1 高レベルな概要¶

最も重要なのは、DTは単なるハードウェアを記述するデータ構造であり、魔法のようなものではありません。すべてのハードウェア設定問題が自動的に解決するわけではありません。しかし、DTはハードウェア設定をLinuxカーネル（あるいは他のオペレーティングシステムでも）のボードやデバイスドライバサポートから分離するための言語を提供します。これにより、ボードやデバイスサポートがデータ駆動型となり、カーネルに渡されるデータに基づいて設定決定を行うことが可能になります。

理想的には、データ駆動型のプラットフォーム設定によりコードの重複が少なくなり、単一のカーネルイメージで幅広いハードウェアをサポートしやすくなります。

LinuxはDTデータを以下の3つの主要な目的で使用しています：

  1. プラットフォームの識別、

  2. ランタイム設定、および

  3. デバイスの構築。

2.2 プラットフォームの識別¶

まず第一に、カーネルはDT内のデータを使用して特定のマシンを識別します。理想的な状況では、カーネルにとって特定のプラットフォームは重要ではありません。なぜなら、デバイスツリーが一貫して信頼性のある方法ですべてのプラットフォーム詳細を記述するからです。しかし、ハードウェアは完璧ではありません。そのため、カーネルは早期ブート時にマシンを識別しなければならないのです。その理由は、マシン固有の修正を実行する機会を確保するためです。

ほとんどの場合、マシンのアイデンティティは関係ありません。代わりに、カーネルはマシンのコアCPUまたはSoCに基づいてセットアップコードを選択します。ARMの場合、arch/arm/kernel/setup.cにあるsetup_arch()は、arch/arm/kernel/devtree.cにあるsetup_machine_fdt()を呼び出します。この関数はmachine_descテーブルを検索し、デバイスツリーのデータと最も一致するmachine_descを選択します。この一致は、ルートデバイスツリーノードの'compatible'プロパティと、struct machine_desc内のdt_compatリストを比較することで決定されます（興味があれば、arch/arm/include/asm/mach/arch.hで定義されています）。

'compatible'プロパティには、機種名をはじめとする機種名と互換性のあるボードの一覧が並んでおり、互換性の高い順に並べられています。たとえば、TIのBeagleBoardとその後継機であるBeagleBoard xMのルート'compatible'プロパティは、それぞれ以下のようになります：

compatible = "ti,omap3-beagleboard", "ti,omap3450", "ti,omap3";
compatible = "ti,omap3-beagleboard-xm", "ti,omap3450", "ti,omap3";

「ti,omap3-beagleboard-xm」は正確なモデル名を指定し、OMAP 3450 SoCおよび一般的なomap3ファミリーソックにも互換性があることを主張しています。リストは、最も具体的な（正確なボード）から最も一般的な（SoCファミリー）へと並んでいます。

注意深い読者の中には、Beagle xMが元のBeagleボードとの互換性も主張できるかもしれません。しかし、ボードレベルでこれを行うのは注意が必要です。同じ製品ライン内でも、ボード同士の変更は大きく、あるボードが他のボードと互換性があると主張しても、正確に何を意味しているかは明確ではありません。トップレベルでは、他のボードとの互換性を主張するのは控えるのが安全です。ただし、あるボードが別のボードをキャリアする場合（例：CPUモジュールがキャリアボードに接続されている場合）は、この例外があります。

互換性値に関するもう一つの注意点。'compatible'プロパティに使用されるすべての文字列は、その意味を文書化する必要があります。Documentation/devicetree/bindingsに'compatible'文字列のドキュメンテーションを追加してください。

ARMにおいても、各machine_descに対して、dt_compatリストのエントリがcompatibleプロパティに含まれているかを確認します。一致するエントリがあれば、そのmachine_descがマシンを駆動する候補となります。machine_descのテーブルをすべて検索した後、setup_machine_fdt()は、compatibleプロパティ内の各machine_descが一致するエントリに基づいて「最も互換性が高い」machine_descを返します。一致するmachine_descが見つからない場合はNULLを返します。

このスキームの理由は、ほとんどの場合、同じSoCまたはSoCファミリを使用するボードであれば、1つのmachine_descで多数のボードをサポートできるという観察に基づいています。ただし、例外として特定のボードに特殊な初期設定コードが必要なケースもあります。このような特殊ケースは、一般的な初期設定コード内でトラブルのあるボードを明示的にチェックすることで処理できますが、ケースが複数になるとコードが複雑になり、保守性が低下します。

代わりに、compatibleリストは、dt_compatリストで「互換性が低い」値を指定することで、一般的なmachine_descが幅広い共通ボードをサポートできるようにします。上記の例では、一般的なボードサポートは「ti,omap3」や「ti,omap3450」と互換性を持つと宣言できます。もともとのbeagleboardで発見されたバグに特化したワークアラウンドコードが必要な場合、新しいmachine_descを追加してそのワークアラウンドを実装し、「ti,omap3-beagleboard」にのみマッチするようにできます。

PowerPCは、各machine_descから.probe()フックを呼び出し、最初にTRUEを返すものを使用する異なるスキームを使用します。ただし、このアプローチはcompatibleリストの優先順位を考慮していませんので、新しいアーキテクチャのサポートには避けるべきです。

2.3 ランタイム構成¶

ほとんどの場合、DTはファームウェアからカーネルへデータを伝達する唯一の方法であり、カーネルパラメータ文字列やinitrdイメージの場所などのランタイムおよび構成データを渡すためにも使用されます。

このデータの多くは/chosenノードに含まれており、Linuxの起動時に以下のようになります：

chosen {
        bootargs = "console=ttyS0,115200 loglevel=8";
        initrd-start = <0xc8000000>;
        initrd-end = <0xc8200000>;
};

bootargsプロパティにはカーネルの引数が含まれており、initrd-*プロパティはinitrdブロブのアドレスとサイズを定義します。注意点として、initrd-endはinitrdイメージの直後のアドレスであり、通常のstruct resourceのセマンティクスとは一致しません。chosenノードには、プラットフォーム固有の設定データを含む任意の数の追加プロパティをオプションで含むことができます。

早期ブートの際、アーキテクチャのセットアップコードはpagingが設定される前に対象のデバイスツリーを解析するために、of_scan_flat_dt()関数を異なるヘルパーカルバックとともに複数回呼び出します。of_scan_flatのコードはデバイスツリーをスキャンし、ヘルパーを使用して早期ブート時に必要な情報を抽出します。一般的にはearly_init_dt_scan_chosen()ヘルパーを使用してchosenノードを解析し、kernelパラメータを処理します。early_init_dt_scan_root()はDTアドレス空間モデルの初期化を行い、early_init_dt_scan_memory()は利用可能なRAMのサイズと位置を決定します。

ARMでは、setup_machine_fdt()関数が正しいmachine_descを選択した後でデバイスツリーの早期スキャンを担当します。

2.4 デバイスの populate¶

ボードが識別され、早期設定データが解析された後、カーネルの初期化は通常通り進みます。このプロセスの途中でunflatten_device_tree()が呼び出され、データをより効率的なランタイム表現に変換します。この時点でマシン固有のセットアップフックが呼ばれます。ARMではmachine_descの.init_early()、.init_irq()、.init_machine()フックが呼び出されます。このセクションの残りの部分はARM実装の例を使用していますが、すべてのアーキテクチャはDTを使用する際、ほぼ同じ処理を行います。

.init_early()は名前の通り、ブートプロセスの初期段階で実行するマシン固有のセットアップに使用されます。.init_irq()は割り込みハンドリングの設定に使用されます。DTを使用してもこれらの関数の動作は大きく変わりません。DTが提供されている場合、.init_early()と.init_irq()はDTクエリ関数（include/linux/of*.h内のof_*）を呼び出して、プラットフォームに関する追加データを取得できます。

DTコンテキストで最も興味深いハックは.init_machine()です。これは主にLinuxデバイスモデルにプラットフォームに関する情報を埋め込む責任を担っています。歴史的には、埋め込みプラットフォームでは、ボードサポート.cファイルで静的なクロック構造、platform_devices、その他のデータを定義し、.init_machine()で一括して登録することで実装されてきました。DTが使用される場合、各プラットフォームごとに静的なデバイスをハードコードする代わりに、DTを解析してデバイスリストを取得し、デバイス構造を動的に割り当てることになります。

.init_machine()が単にplatform_devicesのブロックを登録するだけのシンプルなケースもあります。platform_deviceはLinuxがメモリまたはI/Oマッピングされたハードウェアで検出できないデバイスや、「複合」または「仮想」デバイス（後述）を表す概念です。DTには「platform device」という用語は存在しませんが、platform devicesはツリーのルートにあるデバイスノードや、単純なメモリマッピングバスノードの子ノードに概ね対応します。

ここで例を示すのが良いタイミングです。ここにNVIDIA Tegraボードのデバイスツリーの一部を示します：

/{
      compatible = "nvidia,harmony", "nvidia,tegra20";
      #address-cells = <1>;
      #size-cells = <1>;
      interrupt-parent = <&intc>;

      chosen { };
      aliases { };

      memory {
              device_type = "memory";
              reg = <0x00000000 0x40000000>;
      };

      soc {
              compatible = "nvidia,tegra20-soc", "simple-bus";
              #address-cells = <1>;
              #size-cells = <1>;
              ranges;

              intc: interrupt-controller@50041000 {
                      compatible = "nvidia,tegra20-gic";
                      interrupt-controller;
                      #interrupt-cells = <1>;
                      reg = <0x50041000 0x1000>, < 0x50040100 0x0100 >;
              };

              serial@70006300 {
                      compatible = "nvidia,tegra20-uart";
                      reg = <0x70006300 0x100>;
                      interrupts = <122>;
              };

              i2s1: i2s@70002800 {
                      compatible = "nvidia,tegra20-i2s";
                      reg = <0x70002800 0x100>;
                      interrupts = <77>;
                      codec = <&wm8903>;
              };

              i2c@7000c000 {
                      compatible = "nvidia,tegra20-i2c";
                      #address-cells = <1>;
                      #size-cells = <0>;
                      reg = <0x7000c000 0x100>;
                      interrupts = <70>;

                      wm8903: codec@1a {
                              compatible = "wlf,wm8903";
                              reg = <0x1a>;
                              interrupts = <347>;
                      };
              };
      };

      sound {
              compatible = "nvidia,harmony-sound";
              i2s-controller = <&i2s1>;
              i2s-codec = <&wm8903>;
      };
};

.init_machine()のタイミングで、TegraボードサポートコードはこのDTを確認し、どのノードにplatform_devicesを作成するかを決定する必要があります。しかし、ツリーを眺めても、各ノードがどの種類のデバイスを表しているのか、あるいはデバイスを表しているのかは一目でわかりません。/chosen、/aliases、/memoryノードは情報的なノードであり、デバイスを記述していません（ただし、メモリがデバイスとして考えられるかどうかは議論の余地があります）。/socノードの子ノードはメモリマッピングされたデバイスですが、 codec@1a はI2Cデバイスであり、soundノードはデバイスではなく、他のデバイスがどのように接続されてオーディオサブシステムを構成しているかを表しています。私はボード設計に精通しているからこそ各デバイスの役割がわかりますが、カーネルは各ノードに対して何をすべきかをどう知るのでしょうか？

そのヒントは、カーネルがツリーのルートから始まり、「compatible」プロパティを持つノードを探すことです。まず、一般的には「compatible」プロパティを持つノードは何か種類のデバイスを表していると仮定され、次に、ツリーのルートにあるノードはプロセッサバスに直接接続されているか、それとも他の方法で記述できない miscellaneous システムデバイスであると仮定されます。これらのノードごとにLinuxはplatform_deviceを割り当てて登録し、それがプラットフォームドライバーにバインドされる可能性があります。

これらのノードに対してplatform_deviceを使用するという仮定はなぜ安全なのでしょうか？Linuxがデバイスをモデル化する仕組みでは、ほぼすべてのbus_typeがそのデバイスがバス制御機器の子であると仮定しています。たとえば、i2c_clientはi2c_masterの子であり、spi_deviceはSPIバスの子です。USB、PCI、MDIOなども同様です。DT（Device Tree）においても、I2Cデバイスノードは常にI2Cバスノードの子として現れます。SPI、MDIO、USBなども同様です。platform_device（およびamba_devices、後述）以外のデバイスは特定の親デバイスのタイプを必要とせず、Linuxの/sys/devicesツリーのベースに自由に存在できます。したがって、DTノードがツリーのルートに位置する場合、platform_deviceとして登録するのが最も適切です。

Linuxのボードサポートコードでは、of_platform_populate(NULL, NULL, NULL, NULL)を呼び出して、ツリーのルートにあるデバイスの発見を開始します。パラメータはすべてNULLです。なぜなら、ツリーのルートから開始する場合、開始ノード（最初のNULL）や親（最後のNULL）を指定する必要がなく、マッチテーブル（yet）を使用しないからです。 struct device ボードがデバイスの登録のみを必要とする場合、.init_machine()はof_platform_populate()呼び出し以外に完全に空になります。

テラジアの例では、/socと/soundノードが該当しますが、SoCノードの子ノードはplatform_deviceとして登録すべきでしょうか？LinuxのDTサポートでは、子デバイスは親ドライバのドライバ.probe()タイミングで自動的に登録されます。たとえば、I2Cバスドライバは各子ノードに対してi2c_clientを登録し、SPIバスドライバは各子ノードに対してspi_deviceを登録します。同様に他のbus_typeもです。このモデルに従うと、SoCノードにバインドするドライバを記述し、各子ノードに対してplatform_deviceを登録するのも可能です。ボードサポートコードではSoCデバイスを割り当てて登録し、理論的なSoCデバイスドライバがSoCデバイスにバインドし、/soc/interrupt-controller、/soc/serial、/soc/i2s、/soc/i2cなどの子ノードを.probe()ハンドラで登録します。簡単ですよね？

実際には、一部のplatform_devicesの子デバイスをさらにplatform_devicesとして登録するというパターンはよく見られ、デバイスツリーのサポートコードはこれを反映しており、上の例をよりシンプルにしています。of_platform_populate()の第二引数はof_device_idテーブルであり、このテーブル内のエントリと一致するノードは自動的にその子ノードを登録します。テラジナのケースでは、コードは以下のように見えます:

static void __init harmony_init_machine(void)
{
      /* ... */
      of_platform_populate(NULL, of_default_bus_match_table, NULL, NULL);
}

「simple-bus」はデバイスツリー仕様で定義されたプロパティで、単純なメモリマップバスを意味します。そのため、of_platform_populate()コードは「simple-bus」互換のノードが常に走査されるものと仮定して書くことができます。しかし、引数として渡すことで、ボードサポートコードがデフォルトの動作を上書きできるようにしています。

i2c/spi/etcの子デバイスの追加についての議論を追加する必要があります

付録A: AMBAデバイス¶

ARM PrimecellsはARM AMBAバスに接続された特定のデバイスで、ハードウェア検出や電源管理のサポートが含まれます。Linuxではstruct amba_deviceとamba_bus_typeがPrimecellデバイスを表します。ただし、AMBAバス上のすべてのデバイスがPrimecellであるとは限らず、Linuxでは通常、amba_deviceとplatform_deviceのインスタンスが同じバスセグメントの兄弟ノードとして存在します。

DTを使用すると、of_platform_populate()が各ノードをplatform_deviceかamba_deviceとして登録するかどうかを判断しなければならないため、デバイス作成モデルがやや複雑になります。しかし、この問題の解決策はあまり侵襲的ではありません。ノードが「arm,amba-primecell」に互換性がある場合、of_platform_populate()はそれをamba_deviceとして登録します。

I2C マルチプレクサと複雑なトポロジー¶

複数の理由があり、単純な I2C バス（1 つのアダプタと 1 つ以上のデバイス）よりも複雑な I2C トポロジーを構築する必要がある。

  1. バス上にマルチプレクサが設置される必要がある場合があり、アドレス衝突を防ぐためです。

  2. バスは外部のバスマスターからアクセス可能であり、バスへのアクセスが許可されるかを判断するための仲裁が必要な場合があります。

  3. デバイス（特に RF ティーナー）は、少なくともほとんどの時間、I2C バスからのデジタルノイズを避ける必要があり、デバイスにアクセスする前にゲートを操作する必要があります。

など¶

これらの構造は、Linux では I2C アダプタツリーとして表現されます。各アダプタは親アダプタ（ルートアダプタを除く）を持ち、ゼロ個以上の子アダプタを持ちます。ルートアダプタは実際に I2C トランスファーを実行するアダプタであり、親を持つアダプタは「i2c-mux」オブジェクト（引用符付きですが、これは仲裁者やゲートでもあり得るため）の一部です。

特定のマルチプレクサドライバーによっては、子アダプタの I2C トランスファーが発生した際に動作します。マルチプレクサドライバーは明らかにマルチプレクサを操作できますが、外部バスマスターとの仲裁やゲートの開閉も行うことができます。マルチプレクサドライバーには、セレクトとデセレクトという 2 つの操作があります。セレクトはトランスファー前に呼び出され、（オプションの）デセレクトはトランスファー後に呼び出されます。

mux-locked マルチプレクサ¶

muxロックされたmuxは、選択-転送-解除の全処理中に親アダプター全体をロックしません。むしろ、親アダプター上のmuxのみがロックされます。muxロックされたmuxは、選択および/または解除操作がI2C転送を介して完了する必要がある場合に特に重要です。親アダプターが全処理中には完全にロックされないため、関係のないI2C転送が処理の各段階を混在させる可能性があります。この方法の利点は、muxドライバがより簡単でクリーンに実装できる点ですが、いくつかの注意点があります。

ML1.

muxロックされたmuxを親アダプターの親アダプターとして使用するトポロジーを構築すると、親ロックされたmuxがトランザクション中にルートアダプターがロックされているという期待に反する可能性があります。

ML2.

非兄弟のmux間で子アダプター上のデバイス間でアドレス衝突が発生する場合、複数のmuxロックされたmuxを含む任意のトポロジーを構築するのは安全ではありません。

つまり、mux-oneの背後にあるデバイスアドレス0x42を対象とした選択-転送-解除処理が、mux-twoの背後にある同じアドレス0x42を対象とした類似操作と混在する可能性があります。この仮定的な例では、mux-oneとmux-twoが同時に選択されないことが意図されていましたが、muxロックされたmuxはすべてのトポロジーでそのような保証を提供しません。

ML3.

muxロックされたmuxは、自動閉じるゲート/マトリクス（特定のI2C転送回数（通常は1回）後に自動的に閉じる機能）を備えたドライバで使用できません。関係のないI2C転送が入り込み、早すぎる閉じる動作を引き起こす可能性があります。

ML4.

muxドライバ内で非I2C操作がI2Cマトリクス状態を変更する場合、ドライバはその操作中にルートアダプターをロックする必要があります。そうでない場合、muxの背後にあるデバイスから見ると、関係のないI2C転送が進行中の非I2Cマトリクス変更操作中にバスにゴミデータが出現する可能性があります。

muxロックされた例¶

               .----------.     .--------.
.--------.     |   mux-   |-----| dev D1 |
|  root  |--+--|  locked  |     '--------'
'--------'  |  |  mux M1  |--.  .--------.
            |  '----------'  '--| dev D2 |
            |  .--------.       '--------'
            '--| dev D3 |
               '--------'

D1へのアクセスがある場合、以下のように動作します：

  1. 誰かがD1へのI2C転送を実行します。

  2. M1が親（この場合ルートアダプター）のmuxをロックします。

  3. M1が->selectを呼び出してmuxを準備します。

  4. M1（おそらく）選択処理としていくつかのI2C転送を行います。これらは通常のI2C転送であり、親アダプターをロックします。

  5. M1がステップ1のI2C転送を親アダプターとして通常のI2C転送として処理し、親アダプターをロックします。

  6. M1が->deselectを呼び出す場合があります。

  7. ステップ4と同じルールですが、->deselectに適用されます。

  8. M1が親のmuxをアンロックします。

これは、D2へのアクセスが操作全体の期間中、ロックアウトされるということを意味します。ただし、D3へのアクセスは操作のどの時点でも混在する可能性があります。

Parent-locked muxes¶

Parent-locked muxesは、親アダプターをselect-トランスファ- deselectトランザクションの全期間ロックします。これは、muxドライバーが、その親アダプターを通じてトランザクション中に発生するすべてのI2CトランスファがアンロックされたI2Cトランスファ（例: __i2c_transfer）であることを保証しなければならないことを意味します。そうしないとデッドロックが発生します。いくつかの注意点があります。

PL1.

親アダプターをロックするmuxが他のmuxの子としてトポロジーを構築すると、子muxがrootアダプターがselect操作と実際のトランスファの間に使用されていないという仮定を破る可能性があります（例: 子muxが自動閉じる場合で、親muxがselect中にI2Cトランスファを実行する場合）。これは特に親muxがmuxロックされている場合に顕著ですが、親muxがparent-lockedの場合でも発生する可能性があります。

PL2.

select/deselect呼び出しがgpio、pinctrl、regmap、iioなどの他のサブシステムに依存する場合、これらのサブシステムによって引き起こされるI2Cトランスファがアンロックされている必要があることが重要です。これは複雑で、場合によっては適切な解決策が求められる限り不可能になるかもしれません。

Parent-locked 例¶

               .----------.     .--------.
.--------.     |  parent- |-----| dev D1 |
|  root  |--+--|  locked  |     '--------'
'--------'  |  |  mux M1  |--.  .--------.
            |  '----------'  '--| dev D2 |
            |  .--------.       '--------'
            '--| dev D3 |
               '--------'

D1へのアクセスがある場合、以下のように動作します：

  1. 誰かがD1へのI2C転送を実行します。

  2. M1が親（この場合ルートアダプター）のmuxをロックします。

  3. M1は親アダプターをロックします。

  4. M1が->selectを呼び出してmuxを準備します。

  5. M1がselect中にこのrootアダプターでI2Cトランスファを実行する場合、それらのトランスファはアンロックされたI2Cトランスファでなければならず、rootアダプターのデッドロックを防がなければなりません。

  6. M1はステップ1のI2CトランスファをrootアダプターにアンロックされたI2Cトランスファとして転送し、親アダプターのデッドロックを防ぎます。

  7. M1が->deselectを呼び出す場合があります。

  8. ステップ5と同じルールですが、->deselectの場合です。

  9. M1は親アダプターをアンロックします。

  10. M1が親のmuxをアンロックします。

これは、D2とD3へのアクセスが操作全体の期間中、ロックアウトされるということを意味します。

複雑な例¶

Parent-locked muxがparent-locked muxの親となる場合¶

これは有用なトポロジーですが、問題があります：

               .----------.     .----------.     .--------.
.--------.     |  parent- |-----|  parent- |-----| dev D1 |
|  root  |--+--|  locked  |     |  locked  |     '--------'
'--------'  |  |  mux M1  |--.  |  mux M2  |--.  .--------.
            |  '----------'  |  '----------'  '--| dev D2 |
            |  .--------.    |  .--------.       '--------'
            '--| dev D4 |    '--| dev D3 |
               '--------'       '--------'

どのデバイスもアクセスされるとき、他のすべてのデバイスは操作の全期間ロックアウトされます（両方のmuxが親をロックし、特にM2が親をロックするようリクエストするとき、M1が責任をrootアダプターに押し付ける）。

M2が自動閉じるmuxであり、M1->selectがrootアダプターでアンロックされたI2Cトランスファを実行し、それがM2アダプターに漏れ出してM2を早すぎるタイミングで閉じる場合、このトポロジーは悪影響を及ぼします。

Mux-locked muxがmux-locked muxの親となる場合¶

これは良いトポロジーです：

               .----------.     .----------.     .--------.
.--------.     |   mux-   |-----|   mux-   |-----| dev D1 |
|  root  |--+--|  locked  |     |  locked  |     '--------'
'--------'  |  |  mux M1  |--.  |  mux M2  |--.  .--------.
            |  '----------'  |  '----------'  '--| dev D2 |
            |  .--------.    |  .--------.       '--------'
            '--| dev D4 |    '--| dev D3 |
               '--------'       '--------'

デバイス D1 がアクセスされるとき、操作の全期間を通して D2 へのアクセスはロックされ（M1 の上位子アダプターの MUX がロックされる）、D3 と D4 へのアクセスはいつでも交差する可能性があります。D3 へのアクセスは D1 と D2 をロックしますが、D4 へのアクセスは依然として交差する可能性があります。

MUXロックされた MUX が親MUXの親MUX¶

これはおそらく悪いトポロジーです：

               .----------.     .----------.     .--------.
.--------.     |   mux-   |-----|  parent- |-----| dev D1 |
|  root  |--+--|  locked  |     |  locked  |     '--------'
'--------'  |  |  mux M1  |--.  |  mux M2  |--.  .--------.
            |  '----------'  |  '----------'  '--| dev D2 |
            |  .--------.    |  .--------.       '--------'
            '--| dev D4 |    '--| dev D3 |
               '--------'       '--------'

デバイス D1 がアクセスされるとき、操作の全期間を通して D2 と D3 へのアクセスはロックされ（M1 がルートアダプターの子MUXをロック）、D4 へのアクセスはいつでも交差する可能性があります。

このようなトポロジーは一般的に不適切で、避けたほうがよいでしょう。理由は M2 が ->select と ->deselect の呼び出し中に I2C 転送が行われないことを前提としているためで、もし行われる場合、M2 のスレーブ側で部分的な I2C 転送（つまりゴミデータやより深刻な問題）として現れる可能性があります。これによりデバイスのロックアップやその他の問題が発生する可能性があります。

M2 が自動閉じるMUXである場合、このトポロジーは特に問題になります。その場合、D4 への交差アクセスが M2 を早すぎるタイミングで閉じる原因となり、M1->select の一部である I2C 転送も同様に M2 を閉じる可能性があります。

ただし、M2 が上述の前提を仮定していない場合、かつ M2 が自動閉じない場合、このトポロジーは問題ありません。

親ロックされたMUXがMUXロックされたMUXの親¶

これは良いトポロジーです：

               .----------.     .----------.     .--------.
.--------.     |  parent- |-----|   mux-   |-----| dev D1 |
|  root  |--+--|  locked  |     |  locked  |     '--------'
'--------'  |  |  mux M1  |--.  |  mux M2  |--.  .--------.
            |  '----------'  |  '----------'  '--| dev D2 |
            |  .--------.    |  .--------.       '--------'
            '--| dev D4 |    '--| dev D3 |
               '--------'       '--------'

D1 がアクセスされるとき、D2 へのアクセスは操作の全期間を通してロックされ（M1 の上位子アダプターのMUXがロックされる）、D3 と D4 へのアクセスはいつでも交差する可能性があります（MUXロックされたMUXの予期される挙動と同じです）。

D3 または D4 がアクセスされるとき、他のすべてのアクセスはロックされます。D3 へのアクセスでは M1 がルートアダプターをロックし、D4 へのアクセスではルートアダプターが直接ロックされます。

MUXロックされた兄弟MUX¶

これは良いトポロジーです：

                                .--------.
               .----------.  .--| dev D1 |
               |   mux-   |--'  '--------'
            .--|  locked  |     .--------.
            |  |  mux M1  |-----| dev D2 |
            |  '----------'     '--------'
            |  .----------.     .--------.
.--------.  |  |   mux-   |-----| dev D3 |
|  root  |--+--|  locked  |     '--------'
'--------'  |  |  mux M2  |--.  .--------.
            |  '----------'  '--| dev D4 |
            |  .--------.       '--------'
            '--| dev D5 |
               '--------'

D1 がアクセスされるとき、D2、D3 および D4 へのアクセスはロックされますが、D5 へのアクセスはいつでも交差する可能性があります。

親ロックされた兄弟MUX¶

これは良いトポロジーです：

                                .--------.
               .----------.  .--| dev D1 |
               |  parent- |--'  '--------'
            .--|  locked  |     .--------.
            |  |  mux M1  |-----| dev D2 |
            |  '----------'     '--------'
            |  .----------.     .--------.
.--------.  |  |  parent- |-----| dev D3 |
|  root  |--+--|  locked  |     '--------'
'--------'  |  |  mux M2  |--.  .--------.
            |  '----------'  '--| dev D4 |
            |  .--------.       '--------'
            '--| dev D5 |
               '--------'

どのデバイスもアクセスされるとき、他のすべてのデバイスへのアクセスはロックされます。

MUXロックされた兄弟MUXと親ロックされた兄弟MUX¶

これは良いトポロジーです：

                                .--------.
               .----------.  .--| dev D1 |
               |   mux-   |--'  '--------'
            .--|  locked  |     .--------.
            |  |  mux M1  |-----| dev D2 |
            |  '----------'     '--------'
            |  .----------.     .--------.
.--------.  |  |  parent- |-----| dev D3 |
|  root  |--+--|  locked  |     '--------'
'--------'  |  |  mux M2  |--.  .--------.
            |  '----------'  '--| dev D4 |
            |  .--------.       '--------'
            '--| dev D5 |
               '--------'

D1 または D2 がアクセスされるとき、D3 と D4 へのアクセスはロックされますが、D5 へのアクセスは交差する可能性があります。D3 または D4 がアクセスされるとき、すべての他のデバイスへのアクセスはロックされます。

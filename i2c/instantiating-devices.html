I2Cデバイスのインスタンス化方法¶

PCIやUSBデバイスとは異なり、I2Cデバイスはハードウェアレベルで列挙されません。代わりに、ソフトウェアは各I2Cバスセグメントに接続されているデバイスを把握し、それらのデバイスが使用するアドレスを知る必要があります。このため、カーネルコードはI2Cデバイスを明示的にインスタンス化する必要があります。コンテキストや要件に応じて、いくつかの方法があります。

方法1: I2Cデバイスを静的に宣言する¶

この方法は、I2Cバスがシステムバスである場合に適しています（多くの埋め込みシステムでこのケースが発生します）。このようなシステムでは、各I2Cバスに事前にわかっている番号があり、そのためこのバスに接続されているI2Cデバイスを事前に宣言することが可能です。

この情報は、アーキテクチャによって異なる方法でカーネルに提供されます：デバイスツリー、ACPI、またはボードファイル。

関連するI2Cバスが登録されると、i2c-coreがI2Cデバイスを自動的にインスタンス化します。デバイスが存在するバスがなくなった場合（もしあれば）、デバイスは自動的にアンバインドされ破壊されます。

デバイスツリー経由でI2Cデバイスを宣言する¶

デバイスツリーを使用するプラットフォームでは、I2Cデバイスの宣言はマスターファームウェアのサブノードで行われます。

例:

i2c1: i2c@400a0000 {
        /* ... master properties skipped ... */
        clock-frequency = <100000>;

        flash@50 {
                compatible = "atmel,24c256";
                reg = <0x50>;
        };

        pca9532: gpio@60 {
                compatible = "nxp,pca9532";
                gpio-controller;
                #gpio-cells = <2>;
                reg = <0x60>;
        };
};

ここでは、100kHzの速度で2つのデバイスがバスに接続されています。デバイスの設定に必要な追加プロパティについては、Documentation/devicetree/bindings/にあるデバイスツリードキュメンテーションを参照してください。

ACPI経由でI2Cデバイスを宣言する¶

ACPIはI2Cデバイスを記述することもできます。これに関する特別なドキュメンテーションは現在、以下にあります ACPIベースのデバイス列挙.

ボードファイルでI2Cデバイスを宣言する¶

多くの埋め込みアーキテクチャでは、デバイスツリーが古いハードウェア記述（ボードファイルベース）を置き換えていますが、古いコードではまだボードファイルが使用されています。ボードファイルを介してI2Cデバイスをインスタンス化するには、配列を使用します struct i2c_board_info これは、以下のように呼び出すことで登録されます i2c_register_board_info().

例（omap2 h4から）：

static struct i2c_board_info h4_i2c_board_info[] __initdata = {
      {
              I2C_BOARD_INFO("isp1301_omap", 0x2d),
              .irq            = OMAP_GPIO_IRQ(125),
      },
      {       /* EEPROM on mainboard */
              I2C_BOARD_INFO("24c01", 0x52),
              .platform_data  = &m24c01,
      },
      {       /* EEPROM on cpu card */
              I2C_BOARD_INFO("24c01", 0x57),
              .platform_data  = &m24c01,
      },
};

static void __init omap_h4_init(void)
{
      (...)
      i2c_register_board_info(1, h4_i2c_board_info,
                      ARRAY_SIZE(h4_i2c_board_info));
      (...)
}

上記のコードは、I2Cバス1上に3つのデバイスを宣言しており、それぞれのアドレスとドライバに必要なカスタムデータを含んでいます。

方法2: デバイスを明示的にインスタンス化する¶

この方法は、大きなデバイスが内部通信のためにI2Cバスを使用する場合に適しています。典型的な例はテレビアダプターです。これらはチューナー、ビデオデコーダー、オーディオデコーダーなど、主チップにI2Cバスで接続されることが一般的です。I2Cバスの番号を事前に把握できないため、前述の方法1は使用できません。代わりに、I2Cデバイスを明示的にインスタンス化できます。これは、 struct i2c_board_info を埋め込み、 i2c_new_client_device().

例（sfe4001ネットワークドライバーから）：

static struct i2c_board_info sfe4001_hwmon_info = {
      I2C_BOARD_INFO("max6647", 0x4e),
};

int sfe4001_init(struct efx_nic *efx)
{
      (...)
      efx->board_info.hwmon_client =
              i2c_new_client_device(&efx->i2c_adap, &sfe4001_hwmon_info);

      (...)
}

上記のコードは、ネットワークアダプターにあるI2Cバス上に1つのI2Cデバイスを生成しています。

このようなケースの変異形は、I2Cデバイスが存在するか確実に分からない場合（例えば、ボードの安価なバージョンでは搭載されていないオプション機能で、それらを区別する手段がない場合）や、ボードによってI2Cデバイスのアドレスが異なる場合（メーカーが設計を変更したが通知なし）です。このような場合、i2c_new_scanned_device()を代わりに呼び出します。 i2c_new_client_device().

例（nxp OHCIドライバーから）：

static const unsigned short normal_i2c[] = { 0x2c, 0x2d, I2C_CLIENT_END };

static int usb_hcd_nxp_probe(struct platform_device *pdev)
{
      (...)
      struct i2c_adapter *i2c_adap;
      struct i2c_board_info i2c_info;

      (...)
      i2c_adap = i2c_get_adapter(2);
      memset(&i2c_info, 0, sizeof(struct i2c_board_info));
      strscpy(i2c_info.type, "isp1301_nxp", sizeof(i2c_info.type));
      isp1301_i2c_client = i2c_new_scanned_device(i2c_adap, &i2c_info,
                                                  normal_i2c, NULL);
      i2c_put_adapter(i2c_adap);
      (...)
}

上記のコードは、OHCIアダプターにあるI2Cバス上に最大1つのI2Cデバイスを生成します。まずアドレス0x2cで試し、何も見つからなければアドレス0x2dで試し、それでも見つからなければ単純に処理を中断します。

I2Cデバイスを生成したドライバーは、クリーンアップ時にそのデバイスを破棄する責任があります。これは、 i2c_unregister_device() 以前に返されたポインタに対して呼び出します。 i2c_new_client_device() or i2c_new_scanned_device()。

方法3：特定のデバイスを検出するI2Cバスのスキャン¶

時折、I2Cデバイスに関する情報が不十分で、i2c_new_scanned_device()を呼び出すこともできない場合があります。典型的な例は、PCマザーボード上のハードウェアモニタリングチップです。これには数十のモデルがあり、25の異なるアドレスに配置されることがあります。既存のマザーボードの数が膨大なため、使用されているハードウェアモニタリングチップの完全なリストを作成するのは現実的ではありません。幸いなことに、これらのチップの多くはメーカーIDとデバイスIDレジスタを持ち、それらをスキャンによって識別可能です。

その場合、I2Cデバイスは明示的に宣言されたり生成されたりしません。代わりに、i2c-coreはそのドライバーがロードされる直ちにそのデバイスをスキャンし、見つかった場合は自動的にI2Cデバイスを生成します。このメカニズムの誤動作を防ぐため、以下の制限が適用されます：

  • I2Cデバイスドライバーはdetect()メソッドを実装しなければなりません。このメソッドは、任意のレジスタから読み取ることによってサポートされているデバイスを識別します。

  • サポートされているデバイスが存在する可能性があると判断されるバスで、スキャンに同意するバスのみがスキャンされます。たとえば、テレビアダプター上のハードウェアモニタリングチップのスキャンを回避します。

例：drivers/hwmon/lm90.c内のlm90_driverおよびlm90_detect()を参照してください。

このようなスキャンによって生成されたI2Cデバイスは、検出したドライバーが削除されるか、その下にあるI2Cバスが破棄されるか whichever が先に起きた時点で自動的に破棄されます。

2.4カーネルおよび初期の2.6カーネルのI2Cサブシステムをご存じの方は、このメソッド3がそこでの実施方法と本質的に類似していることに気づくでしょう。重要な違いは以下の2点です:

  • プロービングは現在I2Cデバイスをインスタンス化するための1つの方法にすぎず、かつては唯一の方法でした。可能な限りメソッド1およびメソッド2を優先すべきです。メソッド3は他の方法が使えない場合にのみ使用すべきで、不都合な副作用を引き起こす可能性があります。

  • I2Cバスは現在、どのI2Cドライバクラスがプロービングを実行できるかを明示的に指定する必要があります（クラスビットフィールドを介して）。かつてはすべてのI2Cバスがデフォルトでプロービングされました。デフォルトは空のクラスであり、プロービングは行われません。クラスビットフィールドの目的は、上述の不都合な副作用を制限することです。

再び、メソッド3は可能な限り避けるべきです。明示的なデバイスインスタンス化（メソッド1およびメソッド2）は安全で速いため、強く推奨されます。

メソッド4: ユーザースペースからインスタンス化¶

通常、カーネルは接続されているI2Cデバイスとそのアドレスを把握しています。しかし、特定の状況では把握できないため、ユーザーが情報を提供できるようsysfsインターフェースが追加されました。このインターフェースは、すべてのI2Cバスディレクトリに2つの属性ファイルが作成され、以下のように構成されています: new_device および delete_device. 両方のファイルは書き込み専用であり、適切にインスタンス化または削除するには正しいパラメータを書き込む必要があります。

ファイル new_device 2つのパラメータを取る: I2Cデバイスの名前（文字列）とI2Cデバイスのアドレス（数値、通常は0xで始まる16進数で表現されるが、10進数でも可能）。

ファイル delete_device 1つのパラメータを取る: I2Cデバイスのアドレス。同じI2Cセグメント上の2つのデバイスが同じアドレスを持つことはできないため、アドレスだけでデバイスを一意に特定できます。

例:

# echo eeprom 0x50 > /sys/bus/i2c/devices/i2c-3/new_device

このインターフェースは、カーネル内でのデバイス宣言ができない場合にのみ使用すべきですが、以下のケースでは役立ちます:

  • I2Cドライバは通常デバイスを検出します（上記のメソッド3）が、デバイスが接続されているバスセグメントのクラスビットが設定されていないため検出がトリガーされません。

  • I2Cドライバは通常デバイスを検出しますが、デバイスが予期せぬアドレスに接続されているためです。

  • I2Cドライバは通常デバイスを検出しますが、デバイスが検出されない場合があります。これは検出ルーチンが厳しすぎるか、またはデバイスが公式にサポートされていないが互換性があるためです。

  • テストボード上でドライバを開発しており、I2Cデバイスを自らSMDで実装している場合です。

このインターフェースは、一部のI2Cドライバーが実装するforce_*モジュールパラメータの代替です。i2c-core内で実装されているため、各デバイスドライバーごとに個別に実装するよりもはるかに効率的であり、設定を変更する際にドライバーを再ロードする必要がないという利点もあります。また、ドライバーがロードされる前や利用可能になる前でもデバイスをインスタンス化でき、デバイスがどのドライバーを必要とするかを知る必要がないというメリットがあります。

I2Cデバイスドライバーの実装¶

Linuxをプロトコルホスト/マスター（スレーブではない）として使用する場合のガイドです。

ドライバを設定するにはいくつかの作業が必要です。一部はオプションで、一部は多少または完全に異なる方法で実行できます。これはガイドとして利用してください、ルールブックではありません！

一般的な注意事項¶

カーネル名前空間をできるだけクリーンに保つことが重要です。すべてのグローバルシンボルに一意のプレフィックスを使用するのが最善の方法です。これは特にエクスポートされたシンボルに対して重要ですが、非エクスポートされたシンボルにも適用するのが良いです。我々はこのチュートリアルでは次のプレフィックスを使用します。 foo_ このチュートリアルでは、このプレフィックスを使用します。

ドライバ構造体¶

通常、単一のドライバ構造体を実装し、すべてのクライアントをその構造体からインスタンス化します。覚えておくべきは、ドライバ構造体には一般的なアクセスルーチンが含まれており、ユーザーが提供したデータのフィールド以外はゼロ初期化する必要があります。クライアント構造体は、ドライバモデルのデバイスノードやI2Cアドレスなどのデバイス固有の情報を保持します。

static struct i2c_device_id foo_idtable[] = {
      { "foo", my_id_for_foo },
      { "bar", my_id_for_bar },
      { }
};

MODULE_DEVICE_TABLE(i2c, foo_idtable);

static struct i2c_driver foo_driver = {
      .driver = {
              .name   = "foo",
              .pm     = &foo_pm_ops,  /* optional */
      },

      .id_table       = foo_idtable,
      .probe          = foo_probe,
      .remove         = foo_remove,
      /* if device autodetection is needed: */
      .class          = I2C_CLASS_SOMETHING,
      .detect         = foo_detect,
      .address_list   = normal_i2c,

      .shutdown       = foo_shutdown, /* optional */
      .command        = foo_command,  /* optional, deprecated */
}

nameフィールドはドライバ名で、スペースを含めることはできません。モジュール名（ドライバがモジュールとしてコンパイル可能場合）と一致させる必要があります。ただし、MODULE_ALIAS（この例では「foo」を渡す）を使用してモジュールに別の名前を追加することもできます。ドライバ名とモジュール名が一致しない場合、モジュールは自動的にロードされません（ホットプラグ/コールドプラグ）。

他のすべてのフィールドは、以下で説明するコールバック関数用です。

追加のクライアントデータ¶

各クライアント構造体には、任意の構造体を指す特別な data フィールドがあります。デバイス固有のデータを保持するためにこのフィールドを使用してください。

/* store the value */
void i2c_set_clientdata(struct i2c_client *client, void *data);

/* retrieve the value */
void *i2c_get_clientdata(const struct i2c_client *client);

カーネル2.6.34以降では、remove()またはprobe()が失敗した場合にこの data フィールドをNULLに設定する必要はありません。i2c-coreがこれらの状況で自動的に処理します。これらは、コアがこのフィールドに触れる唯一のタイミングです。

クライアントへのアクセス¶

有効なクライアント構造体がある場合、いつかクライアントから情報を収集するか、新しい情報をクライアントに書き込む必要があります。

私はfoo_readとfoo_write関数を定義することで役に立ちました。一部のケースではI2C関数を直接呼び出す方が簡単ですが、多くのチップにはレジスタ値の概念があり、それを簡単にカプセル化できます。

以下の関数は簡単な例であり、文字通りコピーしないでください：

int foo_read_value(struct i2c_client *client, u8 reg)
{
      if (reg < 0x10) /* byte-sized register */
              return i2c_smbus_read_byte_data(client, reg);
      else            /* word-sized register */
              return i2c_smbus_read_word_data(client, reg);
}

int foo_write_value(struct i2c_client *client, u8 reg, u16 value)
{
      if (reg == 0x10)        /* Impossible to write - driver error! */
              return -EINVAL;
      else if (reg < 0x10)    /* byte-sized register */
              return i2c_smbus_write_byte_data(client, reg, value);
      else                    /* word-sized register */
              return i2c_smbus_write_word_data(client, reg, value);
}

プローブとアタッチ¶

LinuxのI2Cスタックは、PCマザーボード上のハードウェアモニタリングチップへのアクセスをサポートするために最初に書かれたものであり、そのためSMBus（およびPC）よりもI2Cに適した前提を含んでいた。そのような前提の一つは、ほとんどのアダプタとデバイスドライバがSMBUS_QUICKプロトコルをサポートしてデバイスの存在を検出するものであり、もう一つは、プローブプリミティブのみでデバイスとそのドライバを十分に構成できるというものだった。

LinuxとそのI2Cスタックがエミュレートシステムや複雑なコンポーネント（例：DVBアダプタ）においてより広く使用されるにつれて、これらの前提はより問題となった。中断を発生させるI2Cデバイスのドライバには、より多くの（そして異なる）構成情報が必要となり、プロトコルプローブで区別できないチップの変異を処理するドライバや、ボード固有の情報が必要なデバイスのドライバも同様である。

デバイス/ドライババインディング¶

システムインフラストラクチャ、通常はボード固有の初期化コードやブートファームウェアが、I2Cデバイスの存在を報告する。例えば、カーネルやブートローダーに存在するテーブルがあり、I2Cデバイスとボード固有の設定情報（IRQや他の配線アーティファクト、チップタイプなど）を関連付ける場合がある。これにより、各I2Cデバイス用のi2c_clientオブジェクトが作成される。

このバインディングモデルを使用するI2Cデバイスドライバは、Linuxの他のドライバと同様に動作する。プローブ()メソッドを提供してデバイスにバインドし、リムーブ()メソッドを提供してアンバインドする。

static int foo_probe(struct i2c_client *client,
                     const struct i2c_device_id *id);
static int foo_remove(struct i2c_client *client);

i2c_driverがクライアントハンドルを作成しないことを覚えておく。ハンドルはfoo_probe()中に使用される。foo_probe()が成功（ゼロでない負のステータスコードでない）を報告すれば、ハンドルを保存し、foo_remove()が返るまで使用できる。このバインディングモデルはほとんどのLinuxドライバで使用されている。

プローブ関数は、id_tableの名前フィールドがデバイスの名前と一致したときに呼び出される。一致したエントリが渡されるため、ドライバがどのエントリと一致したかを把握できる。

デバイスの作成¶

I2Cデバイスが特定のI2Cバスに接続されていることを確実に知っている場合、i2c_board_info構造体にデバイスアドレスとドライバ名を記入し、呼び出すことでデバイスをインスタンス化できる。 i2c_new_client_device(). この操作によりデバイスが作成され、ドライバコアが適切なドライバを検索し、そのプローブ()メソッドを呼び出す。ドライバが異なるデバイスタイプをサポートする場合、typeフィールドで望むタイプを指定できる。必要に応じてIRQやプラットフォームデータを指定することもできる。

あるデバイスが特定のI2Cバスに接続されていることがわかっているが、使用する正確なアドレスが分からない場合があります。たとえばテレビアダプターでは、同じドライバーが数十種類のやや異なるモデルをサポートしており、モデルによってI2Cデバイスのアドレスが変化するため、このような状況が発生します。その場合、i2c_new_scanned_device()変体を使用できます。これは、 i2c_new_client_device()と似ていますが、追加でスキャンするI2Cアドレスのリストを指定できる点が異なります。デバイスはリスト内で最初に応答するアドレスに作成されます。アドレス範囲内に複数のデバイスが存在する予想がある場合は、その分だけi2c_new_scanned_device()を呼び出してください。

…の呼び出し i2c_new_client_device() やi2c_new_scanned_device()は通常、I2Cバスドライバー内で行われます。返されたi2c_client参照を後で使用するために保存することを検討してください。

デバイス検出¶

事前にどのI2Cデバイスが特定のI2Cバスに接続されているかわかっていない場合があります。これはPCのSMBus上のハードウェアモニタリングデバイスのような例です。その場合、ドライバーがサポートするデバイスを自動的に検出させたいかもしれません。これは従来のモデルの仕組みであり、現在は標準ドライバーモデルの拡張として利用可能です。

検出コールバックを定義するだけで十分です。このコールバックはサポートされているデバイスを識別しようと試み（サポートされている場合は0を、サポートされていない場合は-ENODEVを返します）、スキャンするアドレスリスト、およびデバイスのタイプ（またはクラス）を指定します。これにより、そのタイプのデバイスが接続されている可能性のあるI2Cバス（それ以外に列挙されていない）のみがスキャンされます。たとえば、自動検出が必要なハードウェアモニタリングチップのドライバーでは、クラスをI2C_CLASS_HWMONに設定します。これにより、I2CアダプターのクラスにI2C_CLASS_HWMONを含むもののみがこのドライバーによってスキャンされます。注意点として、マッチするクラスが存在しなくても、そのタイプのデバイスが指定されたI2Cアダプターで使用されることを妨げません。自動検出はされないだけで、明示的なデバイスのインスタンス化は依然として可能です。

このメカニズムは純粋にオプションであり、すべてのデバイスに適用可能ではありません。サポートされているデバイスを特定するためには、信頼性の高い方法（通常はデバイス固有の識別レジスタを使用）が必要ですが、そうでない場合、誤検出が発生し、状況がすぐに悪化する可能性があります。I2Cプロトコルには、特定のアドレスでチップが存在するかどうかを検出する標準的な方法が含まれていませんし、デバイスを識別する標準的な方法もありません。さらに悪化するのが、バス転送に付随するセマンティクスの欠如で、同じ転送が1つのチップでは読み取り操作と、別のチップでは書き込み操作とみなされる可能性があります。このような理由から、可能な限り明示的なデバイスインスタンス化を自動検出よりも優先すべきです。

デバイス削除¶

I2Cデバイスは、 i2c_new_client_device() or i2c_new_scanned_device() を使用して作成された場合、unregister によって登録を解除できます。 i2c_unregister_device()を呼び出すことで解除できます。明示的に呼び出さない場合でも、その処理は、基盤となるI2Cバスが削除される前に自動的に呼び出されます。なぜなら、デバイスは親デバイスよりも長生きできませんからです。

ドライバの初期化¶

カーネルが起動するとき、またはfooドライバモジュールがロードされるときに初期化が必要です。幸いなことに、ドライバモジュールの登録だけで通常十分です。

static int __init foo_init(void)
{
      return i2c_add_driver(&foo_driver);
}
module_init(foo_init);

static void __exit foo_cleanup(void)
{
      i2c_del_driver(&foo_driver);
}
module_exit(foo_cleanup);

The module_i2c_driver() macro can be used to reduce above code.

module_i2c_driver(foo_driver);

一部の関数は __initでマークされています。これらの関数は、カーネル起動（またはモジュールロード）が完了した後は削除可能です。同様に、 __exit でマークされた関数は、カーネルに組み込まれる際にはコンパイラによって削除され、呼び出されることはありません。

電源管理¶

I2Cデバイスがシステムの低電力状態に移行する際、特別な処理が必要な場合（例: レシーバーを低電力モードに、またはシステムのウェイクアップメカニズムをアクティブにする）は、ドライバのdev_pm_opsの適切なコールバックを実装することで実現します（例: suspendとresume）。

これらは標準的なドライバモデルのコールです。他のドライバスタックと同様に動作し、コールはスリープ可能で、スリープまたは再開されるデバイスへのI2Cメッセージングも可能です（なぜなら、これらのコールが実行される際には親I2Cアダプターがアクティブで、IRQも有効だからです）。

システムシャットダウン¶

システムがシャットダウンまたは再起動（kexecを含む）する際、特別な処理が必要なI2Cデバイス（例: 某些をオフにする）には、shutdown()メソッドを使用してください。

また、これは他のドライバスタックと同様に動作する標準的なドライバモデルコールです。コールはスリープ可能で、I2Cメッセージングも可能です。

コマンド関数¶

一般的なioctlのような関数呼び出し用のコールバックがサポートされています。これが必要なことはほとんどなく、また非推奨のため、新しい設計では使用しないべきです。

送受信¶

デバイスと通信するには、いくつかの関数を使用できます。これらはすべて<linux/i2c.h>にあります。

通常のI2C通信とSMBusレベル通信のどちらかを選べる場合は、後者を使用してください。すべてのアダプタがSMBusレベルのコマンドを理解しますが、通常のI2Cを理解するアダプタは一部です！

通常のI2C通信¶

int i2c_master_send(struct i2c_client *client, const char *buf,
                    int count);
int i2c_master_recv(struct i2c_client *client, char *buf, int count);

これらの関数はクライアントから/へのいくつかのバイトを読み書きします。クライアントにはI2Cアドレスが含まれているため、それを含める必要はありません。第二パラメータには読み書きするバイトが含まれ、第三パラメータには読み書きするバイト数が含まれます（バッファの長さより小さく、msg.lenがu16のため64k以下である必要があります）。戻り値は実際に読み書きされたバイト数です。

int i2c_transfer(struct i2c_adapter *adap, struct i2c_msg *msg,
                 int num);

これは一連のメッセージを送信します。各メッセージは読み取りまたは書き込みであり、これらは任意の順序で混在できます。トランザクションは結合され、トランザクション間でストップ条件は発行されません。i2c_msg構造体には、各メッセージのクライアントアドレス、メッセージのバイト数、メッセージデータ自体が含まれます。

ファイルを読み込むことができます i2c-protocol 実際のI2Cプロトコルについての詳細については。

SMBus通信¶

s32 i2c_smbus_xfer(struct i2c_adapter *adapter, u16 addr,
                   unsigned short flags, char read_write, u8 command,
                   int size, union i2c_smbus_data *data);

これは汎用的なSMBus関数です。以下のすべての関数はこの関数を基に実装されています。この関数を直接使用しないでください！

s32 i2c_smbus_read_byte(struct i2c_client *client);
s32 i2c_smbus_write_byte(struct i2c_client *client, u8 value);
s32 i2c_smbus_read_byte_data(struct i2c_client *client, u8 command);
s32 i2c_smbus_write_byte_data(struct i2c_client *client,
                              u8 command, u8 value);
s32 i2c_smbus_read_word_data(struct i2c_client *client, u8 command);
s32 i2c_smbus_write_word_data(struct i2c_client *client,
                              u8 command, u16 value);
s32 i2c_smbus_read_block_data(struct i2c_client *client,
                              u8 command, u8 *values);
s32 i2c_smbus_write_block_data(struct i2c_client *client,
                               u8 command, u8 length, const u8 *values);
s32 i2c_smbus_read_i2c_block_data(struct i2c_client *client,
                                  u8 command, u8 length, u8 *values);
s32 i2c_smbus_write_i2c_block_data(struct i2c_client *client,
                                   u8 command, u8 length,
                                   const u8 *values);

これらはi2c-coreから削除されました。ユーザーがいなかったため、必要があれば後で再追加する可能性があります：

s32 i2c_smbus_write_quick(struct i2c_client *client, u8 value);
s32 i2c_smbus_process_call(struct i2c_client *client,
                           u8 command, u16 value);
s32 i2c_smbus_block_process_call(struct i2c_client *client,
                                 u8 command, u8 length, u8 *values);

すべてのこれらのトランザクションは失敗時に負のerrno値を返します。'write'トランザクションは成功時に0を返し、'read'トランザクションは読み取った値を返します（ブロックトランザクションは読み取った値の数を返します）。ブロックバッファは32バイト以上必要ありません。

ファイルを読み込むことができます smbus-protocol 実際のSMBusプロトコルについての詳細については。

Linuxカーネルトレースポイントの利用¶

著者

Mathieu Desnoyers

このドキュメントではLinux Kernel Tracepointsとその利用方法について紹介します。カーネル内にトレースポイントを挿入し、プローブ関数を接続する方法の例を提供し、プローブ関数の例も示します。

tracepointsの目的¶

コード中に設置されたトレースポイントは、実行時に提供された関数（プローブ）を呼び出すフックを提供します。トレースポイントは「オン」（プローブが接続されている状態）または「オフ」（プローブが接続されていない状態）の2種類があります。「オフ」状態では、わずかな時間のペナルティ（分岐条件のチェック）と空間のペナルティ（インストルメント化された関数末尾に関数呼び出しを追加し、別セクションにデータ構造を追加）を除けば影響はありません。「オン」状態では、トレースポイントが実行されるたびに提供された関数が呼び出され、呼び出し元の実行コンテキストで実行されます。関数の実行が終了すると、呼び出し元に戻り（トレースポイントの場所から継続）、実行が続きます。

コード内の重要な場所にトレースポイントを設置できます。これらは任意の数のパラメータを渡すことができる軽量なフックであり、ヘッダーファイルに記述されたトレースポイント宣言でプロトタイプが定義されています。

トレースおよびパフォーマンスアカウントングに利用できます。

使い方¶

トレースポイントには2つの要素が必要です：

  • ヘッダーファイルに配置されたトレースポイントの定義。

  • Cコード内のトレースポイントステートメント。

トレースポイントを使用するには、linux/tracepoint.hをインクルードする必要があります。

include/trace/events/subsys.h:

#undef TRACE_SYSTEM
#define TRACE_SYSTEM subsys

#if !defined(_TRACE_SUBSYS_H) || defined(TRACE_HEADER_MULTI_READ)
#define _TRACE_SUBSYS_H

#include <linux/tracepoint.h>

DECLARE_TRACE(subsys_eventname,
        TP_PROTO(int firstarg, struct task_struct *p),
        TP_ARGS(firstarg, p));

#endif /* _TRACE_SUBSYS_H */

/* This part must be outside protection */
#include <trace/define_trace.h>

subsys/file.c（トレースステートメントを追加する必要のある場所）:

#include <trace/events/subsys.h>

#define CREATE_TRACE_POINTS
DEFINE_TRACE(subsys_eventname);

void somefct(void)
{
        ...
        trace_subsys_eventname(arg, task);
        ...
}
Where:

  • subsys_eventnameはイベントに固有の識別子です

    • subsysはサブシステムの名前です。

    • eventnameはトレースするイベントの名前です。

  • TP_PROTO(int firstarg, struct task_struct *p) はこのトレースポイントで呼び出される関数のプロトタイプです。

  • TP_ARGS(firstarg, p) はプロトタイプに記述されたパラメータ名と一致します。

  • ヘッダーファイルを複数のソースファイルで使用する場合、 #define CREATE_TRACE_POINTS は一つのソースファイルにのみ出現する必要があります。

関数（プローブ）をトレースポイントに接続するには、register_trace_subsys_eventname()を通じて特定のトレースポイント用のプローブ（呼び出す関数）を提供します。プローブの削除はunregister_trace_subsys_eventname()を通じて行われ、プローブを削除します。

tracepoint_synchronize_unregister()は、モジュールの終了関数の終わりよりも前に呼び出す必要があります。これにより、プローブを使用している呼び出し元が残っていないことを保証します。また、プローブ呼び出し周辺でプリエンプションが無効になっていることにより、プローブの削除とモジュールのアンロードが安全に行えるようになります。

トレースポイントメカニズムは、同じトレースポイントを複数インスタンスで挿入することをサポートしていますが、カーネル全体で同じトレースポイント名に対して1つの定義をすることを必ず行う必要があります。これにより、型の競合が発生しないようにします。トレースポイントの名前変換はプロトタイプを使用して行われ、型が正しいことを保証します。コンパイラが登録場所でプローブの型の正しさを検証します。トレースポイントはインライン関数、インライン静的関数、展開されたループ、および通常の関数にも配置できます。

ここでは「subsys_event」という命名規則を推奨します。これは衝突を防ぐための慣例として意図されています。トレースポイント名はカーネル全体でグローバルであり、コアカーネルイメージ内かモジュール内かに関わらず同じとみなされます。

トレースポイントがカーネルモジュールで使用される場合、EXPORT_TRACEPOINT_SYMBOL_GPL()またはEXPORT_TRACEPOINT_SYMBOL()を使用して定義されたトレースポイントをエクスポートできます。

トレースポイントパラメータに対して少しの作業を行う必要がある場合、その作業はトレースポイント専用に使用されるため、以下のif文の中にまとめることができます。

if (trace_foo_bar_enabled()) {
        int i;
        int tot = 0;

        for (i = 0; i < count; i++)
                tot += calculate_nuggets();

        trace_foo_bar(tot);
}

すべてのtrace_<tracepoint>()呼び出しには、トレースポイントが有効かどうかを返すtrace_<tracepoint>_enabled()関数が定義されています。trace_<tracepoint>()は常にif (trace_<tracepoint>_enabled())のブロック内に配置する必要があります。これにより、トレースポイントが有効化されている間にチェックが行われる競合を防ぎます。

trace_<tracepoint>_enabled()を使用する利点は、トレースポイントのstatic_keyを活用してif文をジャンプラベルで実装し、条件分岐を避けることができる点です。

注意

便利なマクロTRACE_EVENTはトレースポイントの定義方法を提供する代替手段です。確認してください http://lwn.net/Articles/379903, http://lwn.net/Articles/381064 および http://lwn.net/Articles/383362 詳しい情報については、シリーズ記事を参照してください。

ヘッダーファイルからトレースポイントを呼び出す必要がある場合、直接呼び出すかtrace_<tracepoint>_enabled()関数を使用するのは推奨されません。なぜなら、ヘッダーファイルに含まれるトレースポイントは、CREATE_TRACE_POINTSが設定されたファイルからインクルードされる場合に副作用を引き起こす可能性があり、trace_<tracepoint>()はインラインとしてそれほど小さくないため、他のインライン関数で使用するとカーネルが肥大化する可能性があるからです。代わりにtracepoint-defs.hをインクルードし、tracepoint_enabled()を使用してください。

Cファイルでは:

void do_trace_foo_bar_wrapper(args)
{
        trace_foo_bar(args);
}

ヘッダーファイルでは:

DECLARE_TRACEPOINT(foo_bar);

static inline void some_inline_function()
{
        [..]
        if (tracepoint_enabled(foo_bar))
                do_trace_foo_bar_wrapper(args);
        [..]
}

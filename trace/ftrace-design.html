関数トレーサー設計¶

著者

Mike Frysinger

注意

このドキュメントは古くなっています。以下に記載されている説明の一部が現在の実装と一致していない可能性があります。

はじめに¶

ここでは、一般的なファンクショントレースコードが適切に動作するために依存するアーキテクチャの要素について説明します。複雑さが増す順に解説しているため、まずは簡単な部分から基本的な機能を取得できるようにしています。

このドキュメントはアーキテクチャの実装詳細にのみ焦点を当てています。共通コードに関する機能の説明が必要な場合は、common ftrace.txt ファイルを参照してください。

理想的には、トレースをサポートしつつパフォーマンスを維持したい開発者は、動的ftraceサポートまで実装するべきです。

前提条件¶

Ftraceは以下の機能が実装されることに依存しています:

  • STACKTRACE_SUPPORT - save_stack_trace()を実装する

  • TRACE_IRQFLAGS_SUPPORT - include/asm/irqflags.hを実装する

HAVE_FUNCTION_TRACER¶

mcountおよびftrace_stub関数の実装が必要です。

mcountシンボルの正確な名前はツールチェーンに依存します。一部のツールチェーンでは「mcount」、「_mcount」、または「__mcount」と呼ばれることがあります。以下のようなコマンドを実行することで確認できるでしょう:

$ echo 'main(){}' | gcc -x c -S -o - - -pg | grep mcount
        call    mcount

以下では、シンボルが「mcount」として扱うことを前提にします。例を簡潔にするためです。

mcount関数内で有効なABIは 高度に アーキテクチャ/ツールチェーンに依存しています。この点についてはお手伝いできませんので、ご了承ください。古いドキュメントを調べたり、より詳しい人に相談したりしてください。通常、レジスタの使用方法（引数/scratch/etc…）がこの時点で大きな問題になります。特に、mcount呼び出しの位置（関数プロローグの前後）に関連しています。また、glibcがあなたのアーキテクチャでmcount関数をどのように実装しているかを確認することも役立つかもしれません。これは（半分ほど）関連性があるかもしれません。

mcount関数は、関数ポインタftrace_trace_functionがftrace_stubに設定されているかを確認する必要があります。設定されている場合は、何も処理する必要がなく、すぐに返すだけでよいです。設定されていない場合は、mcount関数が通常通り__mcount_internalを呼び出すのと同じ方法でその関数を呼び出します。第一引数は「frompc」、第二引数は「selfpc」（mcount呼び出しのサイズを差し引いた調整済み値）です。

たとえば、関数foo()がbar()を呼び出し、bar()がmcount()を呼び出す場合、mcount()がトレーサーに渡す引数は以下の通りです:

  • 「frompc」 - bar()がfoo()に戻るために使用するアドレス

  • 「selfpc」 - bar()（mcount()のサイズ調整済み）のアドレス

このmcount関数が呼び出されることがご注意ください 何度も呼ばれるため、トレースが無効な状態でシステムがスムーズに動作するためには、トレース機能が無効なデフォルトケースを最適化することが重要です。したがってmcount関数の開始処理は、戻る前にチェックする最小限の処理にとどまります。これはコードフローが通常直線的になるべきことを意味します（つまり、nopケースではブランチ処理を避けるべきです）。もちろんこれは最適化であり、ハード要件ではありません。

以下の擬似コードが参考になります（これらの関数は実際にアセンブリで実装する必要があります）：

void ftrace_stub(void)
{
        return;
}

void mcount(void)
{
        /* save any bare state needed in order to do initial checking */

        extern void (*ftrace_trace_function)(unsigned long, unsigned long);
        if (ftrace_trace_function != ftrace_stub)
                goto do_trace;

        /* restore any bare state */

        return;

do_trace:

        /* save all state needed by the ABI (see paragraph above) */

        unsigned long frompc = ...;
        unsigned long selfpc = <return address> - MCOUNT_INSN_SIZE;
        ftrace_trace_function(frompc, selfpc);

        /* restore all state needed by the ABI */
}

モジュールのためにmcountをエクスポートしてください！

extern void mcount(void);
EXPORT_SYMBOL(mcount);

HAVE_FUNCTION_GRAPH_TRACER¶

深呼吸…実際の作業に入ります。ここではmcount関数を更新し、ftraceグラフ関数ポインタをチェックする必要があります。また、リターンアドレスを保存（ハッキング）し復元するための関数も実装する必要があります。

mcount関数は、ftrace_graph_return（ftrace_stubと比較）およびftrace_graph_entry（ftrace_graph_entry_stubと比較）の関数ポインタをチェックする必要があります。どちらかのポインタが関連するスタブ関数に設定されていない場合、アーキテクチャ固有の関数ftrace_graph_callerを呼び出します。この関数は順にアーキテクチャ固有のprepare_ftrace_return関数を呼び出します。これらの関数名は厳密には必須ではありませんが、アーキテクチャポート間で一貫性を保つため、これらを使用する必要があります。これにより比較・対照が容易になります。

prepare_ftrace_return関数の引数はftrace_trace_functionに渡されるものとはやや異なります。2番目の引数「selfpc」は同じですが、1番目の引数は「frompc」へのポインタで、通常スタック上に位置します。これにより、関数は一時的にリターンアドレスをアーキテクチャ固有の関数return_to_handlerに変更し、その関数はcommon ftrace_return_to_handler関数を呼び出します。この関数は元のリターンアドレスを復元し、元の呼び出し先に戻るようになります。

以下に更新されたmcountの擬似コードを示します：

void mcount(void)
{
...
        if (ftrace_trace_function != ftrace_stub)
                goto do_trace;

+#ifdef CONFIG_FUNCTION_GRAPH_TRACER
+       extern void (*ftrace_graph_return)(...);
+       extern void (*ftrace_graph_entry)(...);
+       if (ftrace_graph_return != ftrace_stub ||
+           ftrace_graph_entry != ftrace_graph_entry_stub)
+               ftrace_graph_caller();
+#endif

        /* restore any bare state */
...

以下に新しいftrace_graph_callerアセンブリ関数の擬似コードを示します：

#ifdef CONFIG_FUNCTION_GRAPH_TRACER
void ftrace_graph_caller(void)
{
        /* save all state needed by the ABI */

        unsigned long *frompc = &...;
        unsigned long selfpc = <return address> - MCOUNT_INSN_SIZE;
        /* passing frame pointer up is optional -- see below */
        prepare_ftrace_return(frompc, selfpc, frame_pointer);

        /* restore all state needed by the ABI */
}
#endif

prepare_ftrace_return()の実装方法については、x86版を参照してください（フレームポインタの渡し方はオプションです；次のセクションで詳しく説明します）。この関数のアーキテクチャ固有な部分は、障害回復テーブルの設定（asm(…)コード）のみです。それ以外の部分はアーキテクチャ間で共通しています。

新しいreturn_to_handlerアセンブリ関数の擬似コードは以下の通りです。注意すべきは、ここに適用されるABIがmcountコードに適用されるABIとは異なっていることです。関数から戻る際（エピローグの後）、通常は返却値を渡すレジスタのみを保存・復元することができるので、他の保存・復元は省略できる可能性があります。

#ifdef CONFIG_FUNCTION_GRAPH_TRACER
void return_to_handler(void)
{
        /* save all state needed by the ABI (see paragraph above) */

        void (*original_return_point)(void) = ftrace_return_to_handler();

        /* restore all state needed by the ABI */

        /* this is usually either a return or a jump */
        original_return_point();
}
#endif

HAVE_FUNCTION_GRAPH_FP_TEST¶

アーキテクチャによっては、関数の呼び出しと戻り時にフレームポインタ（一意の値）を渡すことがあります。戻る際、この値が一致しない場合、カーネルがパニックを起こします。これは主にgccによる不適切なコード生成を検出するための Sanity Check です。あなたのアーキテクチャで gcc が異なる最適化レベルでフレームポインタを適切に更新する場合、このオプションは無視してください。

ただし、この機能をサポートする追加はそれほど難しくありません。prepare_ftrace_return() を呼び出すアセンブリコードで、フレームポインタを3番目の引数として渡します。その後、その関数のC版ではx86アーキテクチャが行っているように、ftrace_push_return_trace() にこのフレームポインタを渡すようにします（0のスタブ値ではなく）。

同様に、ftrace_return_to_handler() を呼び出す際には、フレームポインタを渡してください。

HAVE_FUNCTION_GRAPH_RET_ADDR_PTR¶

アーキテクチャによっては、スタック上のリターンアドレスへのポインタを渡すことがあります。これにより、スタックアンワインド（stack unwinding）の問題が発生する際、アンワインダーがret_stackと同期を取れず、ftrace_graph_ret_addr() が誤ったアドレスを報告する問題を防ぎます。

サポートの追加は簡単です。asm/ftrace.h でマクロを定義し、ftrace_push_return_trace() に'retp'引数としてリターンアドレスポインタを渡すだけです。

HAVE_SYSCALL_TRACEPOINTS¶

アーキテクチャでシステムコールのトレースを実装するには、必要な要素は極めて少数量です。

  • HAVE_ARCH_TRACEHOOK（arch/Kconfig を参照）をサポートする必要があります。

  • <asm/unistd.h> に NR_syscalls 変数を定義し、アーキテクチャがサポートするシステムコールの数を提供します。

  • TIF_SYSCALL_TRACEPOINT スレッドフラグをサポートする必要があります。

  • ptrace での trace_sys_enter() と trace_sys_exit() トレースポイント呼び出しを、ptrace システムコールのトレースパスに配置します。

  • このアーキテクチャのシステムコールテーブルが単純なアドレス配列より複雑な場合、arch_syscall_addr を実装して、指定されたシステムコールのアドレスを返します。

  • システムコールのシンボル名がアーキテクチャの関数名と一致しない場合、asm/ftrace.h に ARCH_HAS_SYSCALL_MATCH_SYM_NAME を定義し、arch_syscall_match_sym_name で適切な論理を実装して、関数名がシンボル名と一致する場合に true を返します。

  • このアーキテクチャを HAVE_SYSCALL_TRACEPOINTS としてタグ付けします。

HAVE_FTRACE_MCOUNT_RECORD¶

詳細についてはscripts/recordmcount.plを参照してください。アーキテクチャ固有の詳細を埋めることで、objdumpを用いてmcount呼び出し先のアドレスを特定する方法を記述してください。このオプションは、動的ftraceを実装しないとあまり意味がありません。

HAVE_DYNAMIC_FTRACE¶

まずHAVE_FTRACE_MCOUNT_RECORDとHAVE_FUNCTION_TRACERが必要です。少し過ぎた場合は読み上げる際には上に戻ってください。

それらの処理が済んだら、以下の実装が必要です：
  • asm/ftrace.h:

    • MCOUNT_ADDR

    • ftrace_call_adjust()

    • struct dyn_arch_ftrace{}

  • アセンブリコード:

    • mcount()（新しいスタブ）

    • ftrace_caller()

    • ftrace_call()

    • ftrace_stub()

  • Cコード:

    • ftrace_dyn_arch_init()

    • ftrace_make_nop()

    • ftrace_make_call()

    • ftrace_update_ftrace_func()

まずasm/ftrace.hにアーキテクチャ固有の詳細を記述する必要があります。

MCOUNT_ADDRをmcountシンボルのアドレスとして定義してください（例：

#define MCOUNT_ADDR ((unsigned long)mcount)

この関数の宣言は誰も持たないため、以下のように実装する必要があります：

extern void mcount(void);

また、補助関数ftrace_call_adjust()が必要です。ほとんどの場合、以下のようにスタブ化できます：

static inline unsigned long ftrace_call_adjust(unsigned long addr)
{
        return addr;
}

<埋めるべき詳細>

最後に、カスタムのdyn_arch_ftrace構造体が必要です。ランタイムパッチングで任意の呼び出し先に追加の状態が必要な場合はここに記述してください。現時点では空の構造体を作成してください：

struct dyn_arch_ftrace {
        /* No extra data needed */
};

ヘッダの処理が済んだら、アセンブリコードを埋め始めましょう。以前にmcount()関数を作成しましたが、動的ftraceはスタブ関数のみを望みます。これはmcount()が起動時のみ使用され、その後すべての参照がパッチングされて戻らないためです。代わりに古いmcount()の本体が使用され、新しいftrace_caller()関数が作成されます。2つを統合するのは難しいため、#ifdefで分離した2つの定義がより簡単です。ftrace_stub()も同様で、これ以降はftrace_caller()内でインライン化されます。

混乱する前に、以下の擬似コードを確認してください。これによりアセンブリで独自の実装を記述できます：

void mcount(void)
{
        return;
}

void ftrace_caller(void)
{
        /* save all state needed by the ABI (see paragraph above) */

        unsigned long frompc = ...;
        unsigned long selfpc = <return address> - MCOUNT_INSN_SIZE;

ftrace_call:
        ftrace_stub(frompc, selfpc);

        /* restore all state needed by the ABI */

ftrace_stub:
        return;
}

最初は少し不自然に見えるかもしれませんが、ランタイムで複数の処理をパッチングするためです。まず、トレースしたい関数のみがftrace_caller()にパッチングされます。次に、1つのトレーサーのみが有効なため、ftrace_caller()自身をそのトレーサーに呼び出すようにパッチングします。これがftrace_callラベルの役割です。

この点を踏まえて、実際にランタイムパッチングを行うCコードに移ります。次のセクションを通過するには、アーキテクチャごとのオプコードについての知識が必要です。

すべてのアーキテクチャには初期化用のコールバック関数があります。初期状態を初期化する必要がある場合は、このタイミングで実行してください。それ以外の場合は、以下のシンプルな関数でほとんどのユーザーが十分に対応できるでしょう:

int __init ftrace_dyn_arch_init(void)
{
        return 0;
}

任意の関数のランタイムパッチングを行うための関数は2つあります。1つ目はmcountコールサイトをnop（ノープ）に変換し、トレースしていないときにランタイムパフォーマンスを維持するのに役立ちます。2つ目はmcountコールサイトを任意の場所へのコールに変換します（通常はftracer_caller()になります）。関数の一般的な定義についてはlinux/ftrace.hを参照してください:

ftrace_make_nop()
ftrace_make_call()

rec->ip値は、ビルド時にscripts/recordmcount.plによって収集されたmcountコールサイトのアドレスです。

最後の関数は、アクティブなトレーサーのランタイムパッチングを行います。これはftrace_callシンボル内のftrace_caller()関数の場所のアセンブリコードを変更します。そのため、新しい関数呼び出しを挿入する際には十分なパディングが存在している必要があります。一部のユーザーは「call」タイプの命令を使用し、他は「branch」タイプの命令を使用します。具体的には以下の関数が用意されています:

ftrace_update_ftrace_func()

HAVE_DYNAMIC_FTRACE + HAVE_FUNCTION_GRAPH_TRACER¶

関数グラファーは動的ftraceと併用するためいくつかの調整が必要です。基本的に、以下の手順が必要です:

  • 更新:

    • ftrace_caller()

    • ftrace_graph_call()

    • ftrace_graph_caller()

  • 実装:

    • ftrace_enable_ftrace_graph_caller()

    • ftrace_disable_ftrace_graph_caller()

<埋めるべき詳細>

補足:

  • ftrace_callの場所にNOPストゥブを追加し、ftrace_graph_caller()へのコールが可能になるようにサイズを確保してください

  • ftrace_graph_caller()を新しいftrace_caller()から呼び出されるように修正し、一部のセマンティクスが変更されている可能性があるため

  • ftrace_enable_ftrace_graph_caller()はftrace_graph_callの場所をランタイムパッチングし、ftrace_graph_caller()へのコールに変換します

  • ftrace_disable_ftrace_graph_caller()はftrace_graph_callの場所をランタイムパッチングし、nopに変換します

Intel(R)トレースハブ（TH）¶

概要¶

Intel(R) Trace Hub (TH)は、複数のハードウェアおよびソフトウェアソースから、System Trace Protocol (MIPI STPv2)でエンコードされた複数のトレース出力ポートを介してトレースデータを生成・スイッチング・出力するハードウェアブロックの集合で、フルシステムデバッグを目的としています。ハードウェアに関する詳細情報は、Intel(R) Trace Hub開発者マニュアル[1]をご参照ください。

トレースソース、トレース宛先（出力）、スイッチ（グローバルトレースハブ、GTH）から構成されています。これらのデバイスは独自のバス（"intel_th"）に配置されており、sysfs属性を通じて発見および設定が可能です。

現在、サポートされているIntel THサブデバイス（ブロック）は以下の通りです：

  • ソフトウェアトレースハブ（STH）、トレースソースで、システムトレースモジュール（STM）デバイスです。

  • メモリストレージユニット（MSU）、トレース出力で、トレースハブの出力をシステムメモリに保存できます。

  • パラレルトレースインターフェース出力（PTI）、外部デバッグホストへのトレース出力で、PTIポートを介して行われます。

  • グローバルトレースハブ（GTH）は、スイッチであり、Intel(R) Trace Hubアーキテクチャの中心的なコンポーネントです。

出力デバイスの共通属性についてはDocumentation/ABI/testing/sysfs-bus-intel_th-output-devicesに記載されており、特に重要なのは"active"属性で、特定の出力デバイスへのトレース出力を有効または無効にします。

GTHは"masters"属性グループを通じて、異なるSTPマスタを異なる出力ポートにリダイレクトできます。GTHインターフェースの詳細情報はDocumentation/ABI/testing/sysfs-bus-intel_th-devices-gthをご参照ください。

STHはstmクラスデバイスを登録し、ユーザー空間およびカーネル空間のソフトウェアトレースソースへのインターフェースを提供します。詳しくは システムトレースモジュール をご参照ください。

MSUは、トレースデータをシステムメモリバッファに収集するように設定でき、後でそのデバイスノードからread()またはmmap()インターフェースを通じて読み取ることができ、"ソフトウェアシンク"ドライバにデータを転送または中継します。

全体的に、Intel(R) Trace Hubは特別なユーザー空間ソフトウェアを必要とせず、すべてsysfs属性およびデバイスノードを通じて設定、開始、収集が可能です。

[1] https://software.intel.com/sites/default/files/managed/d3/3c/intel-th-developer-manual.pdf

バスとサブデバイス¶

システム内の各Intel THデバイスには独自のバスが作成され、id番号が割り当てられ、THデバイスの列挙順序を反映しています。すべてのTHサブデバイス（intel_thバス上のデバイス）はこのidから始まります：0-gth、0-msc0、0-msc1、0-pti、0-sth、続いてデバイス名とオプションのインデックスが続きます。

出力デバイスは/dev/intel_thNというデバイスノードを取得します。ここでNはIntel THデバイスIDです。たとえば、MSUのメモリバッファは割り当てられると、/dev/intel_th0/msc{0,1}からアクセスできます。

クイック例¶

# GTHポートのうち最初のメモリコントローラーを特定する:

$ cat /sys/bus/intel_th/devices/0-msc0/port
0

# おそらくポート0です。マスター33をポート0にデータを送るように設定:

$ echo 0 > /sys/bus/intel_th/devices/0-gth/masters/33

# 最初のメモリコントローラーに2窓のマルチブロックバッファを割り当てます。各窓は64ページ分です:

$ echo multi > /sys/bus/intel_th/devices/0-msc0/mode
$ echo 64,64 > /sys/bus/intel_th/devices/0-msc0/nr_pages

# このコントローラーにもラッピングを有効化:

$ echo 1 > /sys/bus/intel_th/devices/0-msc0/wrap

# さらにこのポートにトレースを有効化:

$ echo 1 > /sys/bus/intel_th/devices/0-msc0/active

# .. マスター33にデータを送信し、stm.txtで詳細を確認 .. # .. トレースが蓄積するのを待つ .. # .. トレースを停止 ..

$ echo 0 > /sys/bus/intel_th/devices/0-msc0/active

# そして今、デバイスノードからトレースを収集できます:

$ cat /dev/intel_th0/msc0 > my_stp_trace

ホストデバッガーモード¶

リモートデバッグホストからTrace Hubを設定し、トレースキャプチャを制御することが可能です。これはハードウェアデバッグインターフェースを介して接続され、Intel Trace Hubを制御し、トレースデータをデバッグホストに転送するために使用されます。

ドライバーにこのような構成が行われていることを伝える必要があります。これにより、キャプチャ/ポート設定に干渉せず、デバッグホストの設定アクセスと競合を避けることができます。このモードでは、ドライバーが行う唯一のアクティビティは、ソフトウェアトレースをSoftware Trace Hub（stmクラスのデバイス）に収集することです。ユーザーは、デコーダーが認識できるマスター/チャンネルマッピングを依然として適切に設定する責任があります。

ホストモードを有効にするには、intel_thカーネルモジュールの'host_mode'パラメータを'y'に設定します。intel_thバス上には仮想出力デバイスが表示されません。また、gthデバイスのトレース設定およびキャプチャ制御属性グループも露出されません。sthデバイスは通常通り動作します。

ソフトウェアシンク¶

メモリストレージユニット（MSU）ドライバーは、ドライバーがトレースデータをソフトウェアシンクとして登録できるインカーネルAPIを提供します。このようなドライバーは、USBデバイスコントローラーやネットワークカードなどの他のデバイス経由でデータをエクスポートすることもできます。

このAPIは2つの主な部分を持っています:

  • ソフトウェアシンクに特定の窓が満杯であることを通知し、その窓を「ロック」して利用不可にすること、つまりトレース収集ができないようにすることです。このとき、MSUドライバーはその窓がロックされていない場合にバッファ内の次の窓に自動的に切り替え、ロックされている場合はトレースキャプチャを停止します。

  • 窓の「ロック」状態を追跡し、ソフトウェアシンクドライバーが窓がアンロックされ再利用可能になったときにMSUドライバーに通知する方法を提供します。

ソフトウェアのシンク（sink）ドライバーの例であるmsu-sinkは、ソフトウェアシンクの実装を示しています。機能的には、ウィンドウが満たされるとすぐにアンロックし、MSUを巡回バッファモードで動作させます。『multi』モードとは異なり、バッファ内のすべてのウィンドウを埋めることになります。この機能を有効にするには、「mode」ファイルに「sink」と書き込むことで有効化できます（msu-sink.koがロードされている前提）

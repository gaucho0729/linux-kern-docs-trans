概念: Kprobes と Return Probes¶

Kprobes は、動的に任意のカーネルルーチンに割り込み、干渉せずにデバッグやパフォーマンス情報を収集できる機能です。ほぼすべてのカーネルコードアドレスでトラップが可能です 1、ブレイクポイントが発生した際に実行されるハンドラールーチンを指定できます。

1

一部のカーネルコードはトラップできません。詳しくは ブラックリスト)

現在、2種類のプローブがあります: kprobes と kretprobes (リターンプローブとも呼ばれます)。kprobe は、カーネル内のほぼすべてのインストラクションに挿入可能です。リターンプローブは指定された関数が返るときに発火します。

通常のケースでは、Kprobesベースのインストルメンテーションはカーネルモジュールとしてパッケージされます。モジュールの init 関数は1つ以上のプローブをインストール("登録")し、exit 関数はそれらを解除します。register_kprobe() などの登録関数は、プローブを挿入する位置と、プローブが発生した際に呼び出すハンドラを指定します。

また、 register_/unregister_*probes() 複数のプローブをバッチで登録/解除するための関数 *probes。これらの関数は、一度に多数のプローブを解除する際の処理を高速化します。

次の4つのサブセクションでは、さまざまなプローブの動作方法とジャンプ最適化の仕組みを説明します。Kprobesを最大限に活用するために必要な知識（例: pre_handler と post_handler の違い、kretprobe の maxactive と nmissed フィールドの使い方など）を解説します。ただし、Kprobesの使い方を早速知りたい場合は、 サポートされるアーキテクチャ.

Kprobeはどのように動作するか？¶

kprobe が登録されると、Kprobes はプローブ対象のインストラクションをコピーし、その最初のバイトをブレイクポイント指令（例: i386 および x86_64 では int3）に置き換えます。

CPU がブレイクポイント指令にヒットすると、トラップが発生し、CPU のレジスタが保存され、notifier_call_chain メカニズムを通じて Kprobes に制御が移ります。Kprobes は kprobe に関連付けられた "pre_handler" を実行し、ハンドラに kprobe 結構と保存されたレジスタのアドレスを渡します。

次に、Kprobes はプローブ対象のインストラクションのコピーをシングルステップします。（実際にインストラクションを場所そのままシングルステップする方が簡単ですが、その場合 Kprobes は一時的にブレイクポイント指令を削除しなければならないため、他の CPU がプローブポイントを通り抜ける可能性がある小さな時間窓が生じます。)

インストラクションがシングルステップされた後、Kprobesは関連するkprobeに関連付けられた「post_handler」（存在する場合）を実行します。その後、プローブポイントの次のインストラクションから実行が続きます。

実行パスの変更¶

Kprobesは実行中のカーネルコードにプローブを実行できるため、レジスタセット（インストラクションポインタを含む）を変更できます。この操作はスタックフレームの保持や実行パスの復元など、最大限の注意が必要です。実行中のカーネルに作用し、コンピュータアーキテクチャや並行処理に関する深い知識が求められるため、足をやけどする可能性があります。

pre_handlerでインストラクションポインタ（および他の関連レジスタ）を変更した場合、kprobesがシングルステップを停止し、指定されたアドレスに戻るようするために!0を返す必要があります。これにより、post_handlerはもう呼び出されません。

TOC（コンテントテーブル）を関数呼び出しに使用するアーキテクチャでは、この操作がより困難になる可能性があります。なぜなら、モジュール内で関数用に新しいTOCを設定し、戻る際に古いTOCを復元する必要がありますからです。

リターンプローブ¶

リターンプローブはどのように動作するか？¶

register_kretprobe()を呼び出すと、Kprobesは関数のエントリポイントにkprobeを設定します。プローブ対象の関数が呼び出され、このプローブがヒットした場合、Kprobesはリターンアドレスのコピーを保存し、リターンアドレスを「トラミプル」のアドレスに置き換えます。トラミプルは任意のコード（通常はNOP命令のみ）です。起動時、Kprobesはトラミプルにkprobeを登録します。

プローブ対象の関数がリターン命令を実行すると、制御はトラミプルに移り、そのプローブがヒットします。Kprobesのトラミプルハンドラは、kretprobeに関連付けられたユーザー指定のリターンハンドラを呼び出し、保存されたインストラクションポインタを保存されたリターンアドレスに設定します。これにより、トラップからの戻り時に実行が再開します。

プローブ対象の関数が実行中である間、そのリターンアドレスはkretprobe_instance型のオブジェクトに保存されます。register_kretprobe()を呼び出す前には、ユーザーがkretprobe構造体のmaxactiveフィールドを設定し、指定された関数の同時プローブ可能なインスタンス数を指定します。register_kretprobe()は、指定された数のkretprobe_instanceオブジェクトを事前に割り当てます。

たとえば、関数が非再帰的であり、スピンロックを保持しながら呼び出される場合、maxactive = 1で十分です。関数が非再帰的であり、CPUを解放することのできない状態（例：セマフォやプリエンプションを通じて）にある場合、NR_CPUSで十分です。maxactive <= 0の場合は、デフォルト値に設定されます。CONFIG_PREEMPTが有効な場合、デフォルト値はmax(10, 2*NR_CPUS)になります。それ以外の場合は、NR_CPUSがデフォルト値です。

maxactiveを低すぎる値に設定しても大した問題ではありません。その結果、一部のプローブが無視されるだけです。kretprobe構造体のnmissedフィールドは、返却プローブが登録されるときにゼロに初期化され、プローブ対象関数が呼び出され、かつkretprobe_instanceオブジェクトが利用できない場合に毎回インクリメントされます。

Kretprobeエントリーハンドラ¶

Kretprobesは、関数のエントリーポイントで実行されるユーザー指定のハンドラをオプションで提供します。このハンドラは、kretprobe構造体のentry_handlerフィールドを設定することで指定されます。kretprobeが関数のエントリーポイントにkprobeを配置した際にそのハンドラが呼び出されます。entry_handlerが0（成功）を返す場合、関数のリターン時に対応するリターンハンドラが確実に呼び出されます。entry_handlerが非ゼロのエラーを返す場合、Kprobesはリターンアドレスを変更せず、kretprobeはその関数インスタンスに対して効果を持たなくなります。

複数のエントリーハンドラとリターンハンドラの呼び出しは、それらに関連する一意なkretprobe_instanceオブジェクトによって一致されます。さらに、ユーザーは各リターンインスタンスごとのプライベートデータをkretprobe_instanceオブジェクトに含めることが可能です。これは、対応するユーザーのエントリーハンドラとリターンハンドラ間でプライベートデータを共有する場合に特に有用です。各プライベートデータオブジェクトのサイズは、kretprobeの登録時にkretprobe構造体のdata_sizeフィールドを設定することで指定できます。このデータは、各kretprobe_instanceオブジェクトのdataフィールドを通じてアクセス可能です。

プローブ対象関数が呼び出され、かつkretprobe_instanceオブジェクトが利用できない場合、nmissedカウントをインクリメントするだけでなく、ユーザーのエントリーハンドラの呼び出しもスキップされます。

ジャンプ最適化はどのように動作するか？¶

あなたのカーネルがCONFIG_OPTPROBES=y（現在はx86/x86-64、非プリエンプションカーネルではこのフラグが自動的に'y'に設定される）で構築されており、かつ「debug.kprobes_optimization」カーネルパラメータが1に設定されている場合（sysctl(8)を参照）、Kprobesはプローブポイントごとにブレイクポイント命令ではなくジャンプ命令を使用して、プローブヒットのオーバーヘッドを削減しようとします。

Kprobeの初期化¶

プローブが登録される際、この最適化を試行する前に、Kprobesは指定されたアドレスに通常のブレイクポイントベースのkprobeを挿入します。そのため、この特定のプローブポイントを最適化できない場合でも、その場所にはプローブが存在します。

安全性チェック¶

プローブを最適化する前に、Kprobesは以下の安全性チェックを行います:

  • Kprobesは、ジャンプ命令で置き換える領域（「最適化領域」と呼ばれる領域）が1つの関数内に完全に含まれていることを確認します。（ジャンプ命令は複数バイトであり、複数の命令を上書きする可能性があります）

  • Kprobesは関数全体を分析し、最適化領域内にジャンプが行われていないことを確認します。具体的には:

    • 関数に間接ジャンプは含まれていません;

    • 関数に例外を引き起こす命令は含まれていません（例外によってトリガーされる修正コードが最適化領域に戻ってジャンプする可能性があるため、Kprobesは例外テーブルを確認してこれを検証します）;

    • 最適化領域へのニアジャンプ（最初のバイトを除く）はありません。

  • 最適化領域内の各命令について、Kprobesはその命令がオフラインで実行可能であることを確認します。

デトーリングバッファの準備¶

次に、Kprobesは以下の命令シーケンスを含む「デトーリング」バッファを準備します:

  • CPUのレジスタをプッシュするコード（ブレイクポイントトラップをエミュレート）

  • ユーザーのプローブハンドラを呼び出すトランポリンコードへの呼び出し

  • レジスタを復元するコード

  • 最適化領域の命令

  • 元の実行パスに戻るジャンプ

最適化前の確認¶

デトーリングバッファの準備後、Kprobesは以下の状況が存在しないことを確認します:

  • プローブにpost_handlerがあります。

  • 最適化領域内の他の命令がプローブされています。

  • プローブが無効化されています。

上記のいずれかの状況がある場合、Kprobesはプローブの最適化を開始しません。これらの状況は一時的なものであるため、状況が変化した場合、Kprobesは再度最適化を試みます。

kprobeが最適化可能である場合、Kprobesはkprobeを最適化リストに登録し、kprobe-optimizerワークキューを起動して最適化を行います。最適化されるプローブポイントが最適化される前にヒットした場合、KprobesはCPUの指令ポインタをデトーリングバッファ内のコピーされたコードに設定して、元の実行パスに戻します。これにより、少なくとも単一ステップの処理を回避します。

最適化¶

Kprobe-optimizerはジャンプ命令を即座に挿入しません。むしろ、 synchronize_rcu() 安全性を最優先に、なぜならCPUが最適化領域を実行中に中断される可能性があるからです 3. ご存知の通り、 synchronize_rcu() 中断が発生していた場合、すべての中断が完了することを保証できますが、これはCONFIG_PREEMPT=nの場合に限ります。 synchronize_rcu() したがって、このkprobeの最適化バージョンは、CONFIG_PREEMPT=nのカーネルのみをサポートします。 4.

その後、Kprobe-optimizerはstop_machine()を呼び出して、最適化された領域をdetourバッファへのジャンプ命令に置き換えるため、text_poke_smp()を使用します。

アンオプティマイゼーション¶

最適化されたkprobeがアンレジスタ、無効化、または他のkprobeによってブロックされた場合、アンオプティマイズされます。この処理が最適化が完了する前に行われた場合、kprobeは最適化リストから dequeue されます。最適化が完了している場合は、text_poke_smp()を使用してジャンプ命令を元のコード（最初のバイトのint3ブレイクポイントを除く）に戻します。

3

2番目の命令が中断され、その後オプティマイザが2番目の命令をジャンプ命令に置き換えると想像してください。 アドレス 割り込みハンドラが実行中である間。割り込みが元のアドレスに戻るとき、有効な命令が存在せず、予期せぬ結果を引き起こします。

4

この最適化安全性のチェックは、kspliceがCONFIG_PREEMPT=yカーネルをサポートするために使用するstop-machineメソッドで置き換えることができます。

技術者向けの注意: ジャンプ最適化は、kprobeのpre_handlerの挙動を変更します。最適化されていない場合、pre_handlerはregs->ipを変更して実行パスを変更し、1を返します。しかし、プローブが最適化されている場合、この変更は無視されます。したがって、カーネルの実行パスを調整したい場合は、以下の技術のいずれかを使用して最適化を抑制する必要があります:

  • kprobeのpost_handlerに空の関数を指定します。

または

  • sysctl -w debug.kprobes_optimization=nを実行します。

ブラックリスト¶

Kprobesは自身を除くカーネルの大部分をプローブできます。これは、一部の関数ではプローブができないためです。このような関数をプローブ（トラップ）すると、再帰的なトラップ（例: ダブルフォールト）や、ネストされたプローブハンドラが呼び出されない可能性があります。Kprobesはこのような関数をブラックリストとして管理しています。ブラックリストに追加したい関数は、(1) linux/kprobes.hをインクルードし、(2) NOKPROBE_SYMBOL()マクロを使用してブラックリスト化する関数を指定します。Kprobesは、指定されたプローブアドレスをブラックリストと照合し、該当する場合に登録を拒否します。

サポートされるアーキテクチャ¶

Kprobesおよびreturn probesは以下のアーキテクチャで実装されています:

  • i386 (ジャンプ最適化をサポート)

  • x86_64 (AMD-64, EM64T) (ジャンプ最適化をサポート)

  • ppc64

  • ia64 (指令スロット1でのプローブをサポートしていません。)

  • sparc64 (return probesはまだ実装されていません。)

  • arm

  • ppc

  • mips

  • s390

  • parisc

Kprobesの設定¶

make menuconfig/xconfig/oldconfigを使用してカーネルを構成する際、CONFIG_KPROBESを「y」に設定してください。「General setup」の下で「Kprobes」を探してください。

Kprobesベースのインストゥルメンテーションモジュールをロードおよびアンロードできるようにするため、「Loadable module support」(CONFIG_MODULES)と「Module unloading」(CONFIG_MODULE_UNLOAD)を「y」に設定してください。

また、CONFIG_KALLSYMSおよびおそらくCONFIG_KALLSYMS_ALLも「y」に設定してください。kallsyms_lookup_name()は、カーネル内でのkprobeアドレス解決コードで使用されるためです。

関数の中間でプローブを挿入する必要がある場合、「Compile the kernel with debug info」(CONFIG_DEBUG_INFO)を有効にして、"objdump -d -l vmlinux"を使用してソースコードとオブジェクトコードのマッピングを確認するのに役立ちます。

APIリファレンス¶

Kprobes APIには、各タイプのプローブ用に「register」関数と「unregister」関数が含まれています。また、プローブの配列を登録・解除するための「register_*probes」および「unregister_*probes」関数も含まれています。以下は、これらの関数と関連するプローブハンドラの簡潔なミニマニュアルページ仕様です。例はsamples/kprobes/サブディレクトリ内のファイルを参照してください。

register_kprobe¶

#include <linux/kprobes.h>
int register_kprobe(struct kprobe *kp);

kp->addrアドレスにブレイクポイントを設定します。ブレイクポイントがヒットした際、Kprobesはkp->pre_handlerを呼び出します。プローブされたインストラクションをシングルステップ実行後、Kprobeはkp->post_handlerを呼び出します。kp->pre_handlerまたはkp->post_handlerの実行中にエラーが発生した場合、またはプローブされたインストラクションのシングルステップ中にエラーが発生した場合、Kprobesはkp->fault_handlerを呼び出します。すべてのハンドラはNULLにすることができます。kp->flagsがKPROBE_FLAG_DISABLEDに設定されている場合、そのプローブは登録されますが無効のままとなり、enable_kprobe(kp)を呼び出すまでハンドラが実行されません。

注意

  1. struct kprobeに「symbol_name」フィールドが導入されたことにより、プローブポイントアドレス解決はカーネルによって自動処理されます。以下のコマンドが動作するようになりました：

    kp.symbol_name = "symbol_name";

    (64ビットPowerPCの複雑な処理、例えば関数記述子は透明に処理されます)

  2. プローブポイントをインストールするためのシンボル内のオフセットがわかっている場合、struct kprobeの「offset」フィールドを使用してください。このフィールドはプローブポイントの計算に使用されます。

  3. 「symbol_name」か「addr」のいずれかを指定してください。両方を指定した場合、kprobeの登録は-EINVALで失敗します。

  4. CISCアーキテクチャ（i386やx86_64など）では、kprobe.addrがインストラクション境界に位置しているかを検証しません。そのため、「offset」の使用には注意が必要です。

register_kprobe()は成功時に0を、失敗時には負のエラー番号を返します。

ユーザーのプリハンドラ（kp->pre_handler）：

#include <linux/kprobes.h>
#include <linux/ptrace.h>
int pre_handler(struct kprobe *p, struct pt_regs *regs);

breakpointに関連付けられたkprobeを指すpと、ブレイクポイントが発生した際に保存されたレジスタを含む構造体を指すregsで呼び出されます。ここでは0を返しますが、Kprobesのエキスパートでない限りは。

ユーザーのポストハンドラ (kp->post_handler):

#include <linux/kprobes.h>
#include <linux/ptrace.h>
void post_handler(struct kprobe *p, struct pt_regs *regs,
                  unsigned long flags);

pとregsはpre_handlerで説明されている通りです。flagsは常にゼロのようです。

ユーザーのフォールトハンドラ (kp->fault_handler):

#include <linux/kprobes.h>
#include <linux/ptrace.h>
int fault_handler(struct kprobe *p, struct pt_regs *regs, int trapnr);

pとregsはpre_handlerで説明されている通りです。trapnrは、フォールトに関連するアーキテクチャ固有のトラップ番号です（例: i386では、一般的な保護フォールトには13、ページフォールトには14）。例外を成功裏に処理した場合、1を返します。

register_kretprobe¶

#include <linux/kprobes.h>
int register_kretprobe(struct kretprobe *rp);

関数のアドレスrp->kp.addrにリターンプローブを設定します。その関数が返るとき、Kprobesはrp->handlerを呼び出します。register_kretprobe()を呼び出す前に、rp->maxactiveを適切に設定する必要があります。「リターンプローブの仕組み」を参照してください。

register_kretprobe()は成功時に0を返し、それ以外の場合は負のerrnoを返します。

ユーザーのリターンプローブハンドラ (rp->handler):

#include <linux/kprobes.h>
#include <linux/ptrace.h>
int kretprobe_handler(struct kretprobe_instance *ri,
                      struct pt_regs *regs);

regsはkprobe.pre_handlerで説明されている通りです。riはkretprobe_instanceオブジェクトを指し、以下のフィールドが関心の対象となる可能性があります:

  • ret_addr: 戻り先アドレス

  • rp: 対応するkretprobeオブジェクトを指します

  • task: 対応するタスク構造体を指します

  • data: 各リターンインスタンスごとのプライベートデータを指します。「Kretprobe」を参照してください

    エントリーハンドラの詳細については

regs_return_value(regs)マクロは、アーキテクチャのABIで定義された適切なレジスタから返却値を抽出するための単純な抽象化を提供します。

ハンドラの返却値は現在無視されています。

unregister_*probe¶

#include <linux/kprobes.h>
void unregister_kprobe(struct kprobe *kp);
void unregister_kretprobe(struct kretprobe *rp);

指定されたプローブを削除します。プローブが登録された後であればいつでもunregister関数を呼び出すことができます。

注意

関数が不正なプローブ（例：未登録のプローブ）を見つけた場合、そのプローブのaddrフィールドをクリアします。

register_*probes¶

#include <linux/kprobes.h>
int register_kprobes(struct kprobe **kps, int num);
int register_kretprobes(struct kretprobe **rps, int num);

指定された配列内のnum個のプローブをそれぞれ登録します。登録中にエラーが発生した場合、配列内のエラー発生したプローブまでのすべてのプローブを安全に解除した後、register_*probes関数が返却します。

  • kps/rps: データ構造へのポインタを含む配列 *probe data structures

  • num: 配列のエントリ数。

注意

これらの関数を使用する前に、ポインタの配列を確保（または定義）し、すべてのエントリを設定する必要があります。

unregister_*probes¶

#include <linux/kprobes.h>
void unregister_kprobes(struct kprobe **kps, int num);
void unregister_kretprobes(struct kretprobe **rps, int num);

指定された配列内のnum個のプローブを一度に削除します。

注意

指定された配列に不正なプローブ（例：登録されていないプローブ）が含まれている場合、関数はその不正なプローブのaddrフィールドをクリアします。ただし、配列内の他のプローブは正しく登録されています。

disable_*probe¶

#include <linux/kprobes.h>
int disable_kprobe(struct kprobe *kp);
int disable_kretprobe(struct kretprobe *rp);

指定されたプローブを一時的に無効にします。 *probe再度有効にするには、enable_*probe()を使用してください。有効化するプローブはすでに登録されている必要があります。

enable_*probe¶

#include <linux/kprobes.h>
int enable_kprobe(struct kprobe *kp);
int enable_kretprobe(struct kretprobe *rp);

有効にする *probe disable_*probe()で無効にされたプローブ。有効化するプローブはすでに登録されている必要があります。

Kprobesの特徴と制限¶

Kprobesは同じアドレスに複数のプローブを許可します。また、ポストハンドラが存在するプローブポイントは最適化されません。したがって、最適化されていないプローブポイントでkprobeをインストールすると、自動的にそのプローブポイントが最適化されません。

一般的に、カーネルのどこでもプローブをインストールできます。特に、割込みハンドラのプローブも可能です。ただし、このセクションで説明する例外があります。

register_*probe関数は、Kprobesの実装コード（主にkernel/kprobes.cと、do_page_faultやnotifier_call_chainなどの関数）内でプローブをインストールしようとすると-EINVALを返します。 arch/*/kernel/kprobes.cコード内でプローブをインストールしようとすると、register_*probe関数は-EINVALを返します。

インライン化可能な関数内でプローブをインストールした場合、Kprobesはその関数のすべてのインラインインスタンスを追跡してプローブをインストールしようとしません。gccは要求なく関数をインライン化するため、予期しないプローブヒットが発生する可能性があります。

プローブハンドラはプローブ対象関数の環境を変更できます（例：カーネルデータ構造を変更する、pt_regs構造体の内容を変更する）。プローブ対象関数が戻るときにレジスタに復元されるため、pt_regs構造体の内容は変更可能です。これにより、例えばバグ修正やテスト用のエラーを注入できます。ただし、Kprobesは意図的に注入されたエラーと誤って発生したエラーを区別できません。飲酒してプローブしないでください。

Kprobesはプローブハンドラ同士が競合するのを防ぐ試みはしません – 例として、プローブ printk() を実行した後、プローブハンドラから printk() を呼び出す場合があります。プローブハンドラがプローブにヒットすると、その2番目のプローブのハンドラは実行されず、2番目のプローブのkprobe.nmissedメンバがインクリメントされます。

Linux v2.6.15-rc1以降、複数のハンドラ（または同じハンドラの複数インスタンス）が異なるCPUで同時に実行されることがあります。

Kprobesは登録・解除時のみmutexを用いたり、メモリを割り当てたりします。

プローブハンドラは、アーキテクチャと最適化状態に応じてプリエンプションが無効化されたり割込みが無効化されたりして実行されます。(例: x86/x86-64では、kretprobeハンドラと最適化されたkprobeハンドラは割込み無効化せずに実行されます) いずれにしても、ハンドラはCPUを解放してはいけません(例: セマフォを取得しようとしたり、I/Oを待機したりするなど)

リターンプローブは、リターンアドレスをトランポールのアドレスに置き換えることで実装されるため、スタックバックトレースや__builtin_return_address()の呼び出しは、kretprobed関数の実際のリターンアドレスではなくトランポールのアドレスを返すことが通常です。(我々が確認した限りでは、__builtin_return_address()はインストルメンテーションやエラー報告の目的でしか使用されていません)

関数の呼び出し回数とリターン回数が一致しない場合、その関数にリターンプローブを登録すると不望な結果を生じる可能性があります。このような場合、以下のような行が表示されます: "kretprobe BUG!: Processing kretprobe d000000000041aa8 @ c00000000004f48c" この情報から、問題を引き起こした正確なkretprobeのインスタンスを関連付けることが可能です。do_exit()のケースはすでにカバー済みです。do_execve()およびdo_fork()は問題になりません。我々は他の特定のケースでの問題になる可能性について認識していません。

関数のエントリまたはエクスイット時にCPUが現在タスクのスタック以外のスタック上で実行されている場合、その関数にリターンプローブを登録すると不望な結果を生じる可能性があります。そのため、Kprobesはx86_64版の__switch_to()に対してリターンプローブ(またはkprobes)をサポートしていません。登録関数は-EINVALを返します。

x86/x86-64では、Kprobesのジャンプ最適化が指令を広範に変更するため、最適化にはいくつかの制限があります。これを説明するために、いくつかの用語を導入します。2バイトの指令が2つと3バイトの指令が1つ含まれる3指令のシーケンスを想像してください。

        IA
        |
[-2][-1][0][1][2][3][4][5][6][7]
        [ins1][ins2][  ins3 ]
        [<-     DCR       ->]
        [<- JTPR ->]

ins1: 1st Instruction
ins2: 2nd Instruction
ins3: 3rd Instruction
IA:  Insertion Address
JTPR: Jump Target Prohibition Region
DCR: Detoured Code Region

DCR内の指令は、DCR内のバイトが5バイトのジャンプ指令に置き換えられるため、アウトオブラインバッファにコピーされます。そのため、いくつかの制限があります。

  1. DCR内の指令は再配置可能でなければなりません。

  2. DCR内の指令にはコール指令を含んではいけません。

  3. JTPRはジャンプまたはコール指令の対象にならなければなりません。

  4. DCRは関数の境界をまたぐことはできません。

いずれにしても、これらの制限は内蔵の指令デコーダーによってチェックされるため、心配する必要はありません。

プローブオーバーヘッド¶

2005年に使用されていた典型的なCPUでは、kprobeのヒット処理に0.5〜1.0マイクロ秒かかります。具体的には、同じprobepointを繰り返しヒットし、各ヒットごとに単純なハンドラを実行するベンチマークでは、アーキテクチャによって1〜2百万回のヒットが毎秒報告されます。リターンプローブのヒットは、kprobeのヒットに比べて通常50〜75%長くかかります。関数にリターンプローブを設定している場合、その関数のエントリポイントにkprobeを追加しても、ほぼゼロのオーバーヘッドが生じます。

以下に、さまざまなアーキテクチャにおけるオーバーヘッドのサンプル値（マイクロ秒単位）を示します：

k = kprobe; r = return probe; kr = kprobe + return probe
on same function

i386: Intel Pentium M, 1495 MHz, 2957.31 bogomips
k = 0.57 usec; r = 0.92; kr = 0.99

x86_64: AMD Opteron 246, 1994 MHz, 3971.48 bogomips
k = 0.49 usec; r = 0.80; kr = 0.82

ppc64: POWER5 (gr), 1656 MHz (SMT disabled, 1 virtual CPU per physical CPU)
k = 0.77 usec; r = 1.26; kr = 1.45

最適化されたプローブのオーバーヘッド¶

通常、最適化されたkprobeのヒット処理に0.07〜0.1マイクロ秒かかります。以下に、x86アーキテクチャにおけるオーバーヘッドのサンプル値（マイクロ秒単位）を示します：

k = unoptimized kprobe, b = boosted (single-step skipped), o = optimized kprobe,
r = unoptimized kretprobe, rb = boosted kretprobe, ro = optimized kretprobe.

i386: Intel(R) Xeon(R) E5410, 2.33GHz, 4656.90 bogomips
k = 0.80 usec; b = 0.33; o = 0.05; r = 1.10; rb = 0.61; ro = 0.33

x86-64: Intel(R) Xeon(R) E5410, 2.33GHz, 4656.90 bogomips
k = 0.99 usec; b = 0.43; o = 0.06; r = 1.24; rb = 0.68; ro = 0.30

  • trace-eventを使用してターゲット関数のトレース（引数を含む）。

    trace-eventは、静的に定義されたイベントインターフェースで低オーバーヘッド（オフの場合はほぼ見えないオーバーヘッド）を提供します。新しいイベントを定義し、ftraceや他のトレースツールを介してトレースできます。

    カーネルをdebug info（CONFIG_DEBUG_INFO=y）でビルドした場合、perf-probeを使用してどのレジスタ/スタックがどのローカル変数や引数に割り当てられているかを確認し、新しいイベントでトレースを設定できます。

kprobes debugfsインターフェース¶

最近のカーネル（2.6.20以上）では、/sys/kernel/debug/kprobes/ディレクトリ（debugfsが/sys/kernel/debugにマウントされている前提）に登録されたkprobeの一覧が表示されます。

/sys/kernel/debug/kprobes/list: システム全体に登録されているプローブの一覧を表示します：

c015d71a  k  vfs_read+0x0
c03dedc5  r  tcp_v4_rcv+0x0

1列目はプローブが挿入されたカーネルアドレスを示し、2列目はプローブの種類（k - kprobe、r - kretprobe）を指定します。3列目はプローブのシンボルオフセットを示します。プローブ対象の関数がモジュールに属する場合、モジュール名も表示されます。続く列はプローブの状態を示します。プローブが有効でなくなった仮想アドレス（モジュール初期セクション、アンロードされたモジュールに該当する仮想アドレスなど）にある場合、[GONE]でマークされます。一時的に無効化されたプローブは[DISABLED]でマークされ、最適化されたプローブは[OPTIMIZED]でマークされます。FTRACEベースのプローブは[FTRACE]でマークされます。

/sys/kernel/debug/kprobes/enabled: kprobesを強制的にON/OFFします。

登録されたkprobesをグローバルかつ強制的にONまたはOFFにするためのコントロール手段を提供します。デフォルトではすべてのkprobesが有効になっています。このファイルに"0"をエコーバックすると、すべての登録プローブが無効化され、"1"をエコーバックするまで有効状態のままです。注意点として、このコントロール手段はすべてのkprobesを無効化・有効化するだけで、各プローブの無効化状態を変更しません。つまり、無効化されたkprobes（[DISABLED]でマークされているもの）は、このコントロール手段ですべてのkpro, besをONにしても有効にはなりません。

kprobes sysctlインターフェース¶

/proc/sys/debug/kprobes-optimization: kprobesの最適化を有効/無効にします。

CONFIG_OPTPROBES=yの場合は、このsysctlインターフェースが表示され、ジャンプ最適化（セクション ジャンプ最適化はどのように動作するか？)をグローバルかつ強制的に有効/無効にします。デフォルトではジャンプ最適化が有効（ON）になっています。このファイルに"0"をエコーバックするか、sysctl経由で"debug.kprobes_optimization"を0に設定すると、すべての最適化されたプローブが非最適化され、その後に登録される新しいプローブは最適化されなくなります。

このコントロール手段は に指定する必要があります。 最適化状態を変更します。つまり、最適化されたプローブ（[OPTIMIZED]でマークされているもの）は非最適化され（[OPTIMIZED]のタグが削除されます）。このコントロール手段をONにすると、再び最適化されます。

はじめに¶

Ftraceは、開発者やシステム設計者向けにカーネル内部の状況を把握するための内部トレーサーです。デバッグや、ユーザー空間外で発生するレイテンシーおよびパフォーマンスの問題の分析に利用できます。

Ftraceは通常関数トレーサーとして扱われますが、実際には複数のトレースユーティリティを含むフレームワークです。プリエンプションや、タスクが目覚めたタイミングから実際にスケジューリングされるまでの間のレイテンシーを確認するためのトレースもあります。

Ftraceの最も一般的な用途の一つはイベントトレースです。カーネル内には数百の静的イベントポイントがあり、tracefsファイルシステムを介して有効化することで、カーネルの特定部分での動作を確認できます。

詳細については events.rst を参照してください。

ファイルシステム¶

Ftraceはtracefsファイルシステムを使用して制御ファイルと出力ファイルを保持します。

tracefsがカーネルに組み込まれている場合（どのftraceオプションを選択してもこの設定になります）、/sys/kernel/tracingディレクトリが作成されます。このディレクトリをマウントするには、/etc/fstabファイルに以下を追加できます：

tracefs       /sys/kernel/tracing       tracefs defaults        0       0

または、実行時にもう一度マウントできます：

mount -t tracefs nodev /sys/kernel/tracing

より速くアクセスしたい場合は、このディレクトリにソフトリンクを作成することもできます：

ln -s /sys/kernel/tracing /tracing

注意

4.1以前では、すべてのftraceトレース制御ファイルがdebugfsファイルシステム内にありました。通常は/sys/kernel/debug/tracingに位置します。後方互換性のために、debugfsファイルシステムをマウントする際、tracefsファイルシステムは自動的に以下にマウントされます：

/sys/kernel/debug/tracing

tracefsファイルシステム内のすべてのファイルは、このdebugfsファイルシステムディレクトリ内にも存在します。

tracefsをdebugfsファイルシステム内で自動マウントしない場合は、defconfigオプション CONFIG_TRACEFS_DISABLE_AUTOMOUNT を有効にしてください。

注意

選択したftraceオプションは、tracefsファイルシステムも作成します。このドキュメントの残りの部分では、ftraceディレクトリ（cd /sys/kernel/tracing）にいるものとし、そのディレクトリ内のファイルにのみ焦点を当て、拡張された「/sys/kernel/tracing」パス名による分散を避けることとします。

完了です！（※カーネルにftraceがコンパイルされていると仮定しています）

tracefsをマウントした後、ftraceの制御ファイルと出力ファイルにアクセスできるようになります。以下に、いくつかの重要なファイルの一覧を示します：

注意：すべての時間値はマイクロ秒単位です。

current_tracer:

これは、現在設定されているトレーサーを設定または表示するために使用します。トレーサーを変更すると、リングバッファの内容および「snapshot」バッファもクリアされます。

available_tracers:

これは、カーネルにコンパイルされているさまざまなトレーサーの種類を保持しています。ここでリストされているトレーサーは、名前をcurrent_tracerにエコーバックすることで設定できます。

tracing_on:

これは、トレースリングバッファへの書き込みが有効になっているかどうかを設定または表示します。このファイルに0をエコーバックするとトレーサーを無効にし、1をエコーバックすると有効にします。注意：これはリングバッファへの書き込みを無効にするだけで、トレースオーバーヘッドは依然として発生する可能性があります。

カーネル内部では、トレースオフ機能を実行する関数tracing_off()を使用してリングバッファへの書き込みを無効にでき、これによりこのファイルが「0」と設定されます。ユーザー空間では、このファイルに「1」をエコーバックすることでトレースを再有効化できます。

注意：関数およびイベントトリガーの「traceoff」もこのファイルをゼロに設定し、トレースを停止します。ユーザー空間でもこのファイルを使用してトレースを再有効化できます。

trace:

このファイルは、人間が読みやすい形式でトレースの出力を保持しています（以下で説明します）。このファイルをO_TRUNCフラグで書き込みモードで開くと、リングバッファの内容がクリアされます。注意：このファイルは消費者ではありません。トレースがオフになっている場合（トレーサーが動作していない、またはtracing_onがゼロの場合）、毎回読み込むたびに同じ出力が生成されます。トレースがオンになっている場合、このファイルはバッファ全体を読み取ろうとしますが、消費者ではないため不一致な結果になる可能性があります。

trace_pipe:

出力は「trace」ファイルと同じですが、このファイルはライブトレースにストリーム形式で使用することを目的としています。このファイルから読み込むと、新しいデータが取得されるまでブロックします。一方、「trace」ファイルとは異なり、このファイルは消費者です。つまり、このファイルから読み込むことで、順次読み込みによりより最新のデータが表示されます。データがこのファイルから読み取られると、それ以降の順次読み込みでは再度読み取られません。一方、「trace」ファイルは静的であり、トレーサーが新しいデータを追加しなければ、毎回読み込むたびに同じ情報を表示します。

trace_options:

このファイルは、上記の出力ファイルに表示されるデータ量をユーザーが制御できるようにします。トレーサーやイベントの動作を変更するオプションも存在します（スタックトレース、タイムスタンプなど）。

オプション:

このディレクトリには、すべてのトレースオプションに対応するファイルが含まれています（trace_optionsにも同様です）。オプションは、それぞれのオプション名を持つファイルに「1」または「0」を書き込むことで設定またはクリアできます。

tracing_max_latency:

一部のトレーサーは最大レイテンシーを記録します。たとえば、割込みが無効になっている最大時間などです。最大時間はこのファイルに保存され、最大トレースも「trace」コマンドで表示されます。レイテンシーがこのファイル内の値（マイクロ秒単位）よりも大きい場合のみ、新しい最大トレースが記録されます。

このファイルに時間値をエコーバックすると、レイテンシーがこのファイル内の時間値よりも大きい場合を除き、レイテンシーの記録は行われません。

tracing_thresh:

一部のレイテンシートレーサーは、このファイル内の数値よりもレイテンシーが大きい場合にトレースを記録します。このファイルに0より大きい数値が含まれている場合にのみ有効です（マイクロ秒単位）。

buffer_size_kb:

この設定は、各CPUバッファが保持するキロバイト数を設定または表示します。デフォルトでは、すべてのCPUのトレースバッファのサイズは同じです。表示される数値はCPUバッファのサイズであり、すべてのバッファの合計サイズではありません。トレースバッファはページ（カーネルが割り当て用に使用するメモリのブロック、通常4KB）で割り当てられます。バッファ管理用メタデータを収容するために、いくつかの追加ページが割り当てられる場合があります。最後に割り当てられたページが要求されたバイト数よりも多くの容量を持つ場合、そのページの残りは使用され、実際の割り当てサイズが要求または表示されたサイズより大きくなることがあります。（注意：バッファ管理用メタデータのため、サイズがページサイズの倍数でない場合があります。）

個々のCPUごとのバッファサイズは異なり得ます（下記の「per_cpu/cpu0/buffer_size_kb」を参照）、その場合このファイルには「X」が表示されます。

buffer_total_size_kb:

このファイルは、すべてのトレースバッファの合計サイズを表示します。

free_buffer:

プロセスがトレースを実行している場合、プロセスが終了した際にリングバッファを縮小（解放）する必要がある場合は、このファイルを使用できます。このファイルを閉じる際、リングバッファは最小サイズにリサイズされます。トレースを実行しているプロセスがこのファイルを開いている場合、プロセスが終了時にこのファイルのディスクリプタが閉じられ、その結果リングバッファが「解放」されます。

disable_on_freeオプションが設定されている場合、トレースを停止する可能性もあります。

tracing_cpumask:

これは、ユーザーが指定されたCPUのみをトレースできるマスクです。形式は、CPUを表す16進文字列です。

set_ftrace_filter:

動的ftraceが構成されている場合（下記の「動的ftrace」セクションを参照）、コードは動的に変更され（コードテキストの再構成）、関数プロファイラー（mcount）の呼び出しが無効になります。これにより、パフォーマンスにほとんど影響を与えることなくトレースを構成できます。また、特定の関数のトレースを有効または無効にする副作用も生じます。このファイルに関数名をエコーバックすると、トレースはその関数のみに限定されます。これにより、トレーサー「function」と「function_graph」に影響を与え、関数プロファイリング（「function_profile_enabled」を参照）にも影響します。

「available_filter_functions」に記載されている関数は、このファイルに書き込むことができる関数です。

このインターフェースはコマンドの使用も可能ですが、詳細については「フィルタコマンド」セクションを参照してください。

処理文字列はコストが高く、トレースに登録されたすべての関数をチェックする必要があるため、速度向上のためこのファイルにインデックスを書き込むことができます。数字（「1」から始まる）を書き込むと、「available_filter_functions」ファイルの行位置に該当する関数を選択します。

set_ftrace_notrace:

これはset_ftrace_filterの効果とは逆のものです。ここに追加された関数はトレースされません。set_ftrace_filterとset_ftrace_notraceの両方に存在する関数は、トレースされません。

set_ftrace_pid:

このファイルに記載されたPIDのスレッドのみを関数トレーサーでトレースします。

「function-fork」オプションが設定されている場合、このファイルに記載されたPIDのタスクがフォークした際、子のPIDが自動的にこのファイルに追加され、関数トレーサーによってトレースされます。このオプションは、終了したタスクのPIDもこのファイルから削除します。

set_ftrace_notrace_pid:

このファイルに記載されたPIDのスレッドを関数トレーサーで無視します。

「function-fork」オプションが設定されている場合、このファイルに記載されたPIDのタスクがフォークした際、子のPIDが自動的にこのファイルに追加され、関数トレーサーによってトレースされません。このオプションは、終了したタスクのPIDもこのファイルから削除します。

このファイルと「set_ftrace_pid」の両方にPIDが存在する場合、このファイルが優先され、スレッドはトレースされません。

set_event_pid:

イベントは、このファイルに記載されているPIDを持つタスクのみをトレースします。注意: sched_switchおよびsched_wake_upイベントもこのファイルに記載されているイベントをトレースします。

タスクの子プロセスのPIDをこのファイルに自動的に追加するには、「event-fork」オプションを有効にしてください。このオプションは、タスクが終了する際、そのタスクのPIDをこのファイルから削除することも引き起こします。

set_event_notrace_pid:

イベントは、このファイルに記載されているPIDを持つタスクをトレースしません。注意: sched_switchおよびsched_wakeupイベントは、このファイルに記載されていないスレッドをトレースします。スレッドのPIDがこのファイルに含まれている場合でも、sched_switchまたはsched_wakeupイベントがトレースすべきスレッドをトレースしている場合を除き、トレース対象外とします。

タスクの子プロセスのPIDをこのファイルに自動的に追加するには、「event-fork」オプションを有効にしてください。このオプションは、タスクが終了する際、そのタスクのPIDをこのファイルから削除することも引き起こします。

set_graph_function:

このファイルに記載された関数は、関数グラフトレーサーがこれらの関数とそれらを呼び出す関数のみをトレースします。(詳細については「動的ftrace」セクションを参照してください)。注意: set_ftrace_filterおよびset_ftrace_notraceは依然としてトレース対象関数を制御します。

set_graph_notrace:

set_graph_functionと同様ですが、関数が実行されるまで関数グラフトレースを無効にし、特定の関数が呼び出す関数のトレースを無視できるようにします。

available_filter_functions:

このファイルには、ftraceが処理可能でトレース可能な関数の一覧が表示されます。これらは「set_ftrace_filter」、「set_ftrace_notrace」、「set_graph_function」、「set_graph_notrace」に渡すことができる関数名です。(詳細については以下の「動的ftrace」セクションを参照してください)

dyn_ftrace_total_info:

このファイルはデバッグ用です。NOPに変換されトレース可能な関数の数を表示します。

enabled_functions:

このファイルは主にftraceのデバッグに使用されますが、関数にコールバックがアタッチされているか確認するのに役立つ場合もあります。トレースインフラストラクチャはftrace関数トレースユーティリティを使用しますが、他のサブシステムも同様に使用する可能性があります。このファイルは、コールバックがアタッチされているすべての関数と、アタッチされたコールバックの数を表示します。注意: コールバックは複数の関数を呼び出す可能性があり、その場合はこのカウントには表示されません。

関数に「save regs」属性を持つ関数でトレースされるコールバックが登録されている場合、関数がレジスタを返す行に'R'が表示されます。

関数に「ip modify」属性を持つ関数でトレースされるコールバックが登録されている場合、IPを上書きできる関数の行に'I'が表示されます。

アーキテクチャがサポートする場合、関数が直接呼び出しているコールバックが表示されます。カウントが1より大きい場合、ほぼ確実にftrace_ops_list_func()が呼び出されます。

関数のコールバックが特定のコールバック用のジャンプ先（トラマポール）にジャンプする場合、そのアドレスとトラマポールが呼び出す関数が表示されます。

function_profile_enabled:

設定すると、関数トレーサーまたは関数グラフトレーサー（設定されている場合）ですべての関数を有効にします。呼び出された関数の数をヒストグラムとして保持し、関数グラフトレーサーが設定されている場合、その関数で費やした時間を記録します。ヒストグラムの内容は以下のファイルに表示されます：

trace_stat/function<cpu> (function0, function1, など)

trace_stat:

さまざまなトレース統計を保持するディレクトリです。

kprobe_events:

動的トレースポイントを有効にします。kprobetrace.rstを参照してください。

kprobe_profile:

動的トレースポイントの統計情報です。kprobetrace.rstを参照してください。

max_graph_depth:

関数グラフトレーサーで使用されます。これは関数にトレースする最大深度を指定します。この値を1に設定すると、ユーザー空間から呼び出される最初のカーネル関数のみ表示されます。

printk_formats:

rawフォーマットファイルを読み込むツール向けです。リングバッファ内のイベントが文字列を参照する場合、その文字列自体ではなくポインタのみがバッファに記録されます。これにより、ツールがその文字列の内容を知ることはできません。このファイルでは文字列とそのアドレスを表示し、ツールがポインタを文字列にマッピングできるようにします。

saved_cmdlines:

トレースイベントにタスクのcomm（実行名）を記録しない限り、タスクのpidのみが記録されます。Ftraceはpidマッピングをcommにキャッシュして、イベントでcommを表示しようとします。pidがcommにマッピングされていない場合、出力には「<…>」が表示されます。

「record-cmd」オプションが「0」に設定されている場合、レコード中にタスクのcommは保存されません。デフォルトでは有効です。

saved_cmdlines_size:

デフォルトでは128個のcommが保存されます（「saved_cmdlines」を参照）。保存するcommの数を増減するには、このファイルにキャッシュするcommの数をエコーバックしてください。

saved_tgids:

「record-tgid」オプションが設定されている場合、スケジューリングコンテキストスイッチごとにタスクのタスクグループID（TGID）がPIDからTGIDへのマッピングテーブルに保存されます。デフォルトでは「record-tgid」オプションは無効です。

snapshot:

「スナップショット」バッファを表示し、現在実行中のトレースのスナップショットをユーザーが取得できるようにします。詳細については、「スナップショット」セクションを参照してください。

stack_max_size:

スタックトレーサーが有効になると、この項目はそのトレーサーがこれまでに遭遇した最大スタックサイズを表示します。詳細については、「スタックトレース」セクションを参照してください。

stack_trace:

スタックトレーサーが有効になった際に遭遇した最大のスタックのスタックバックトレースを表示します。詳細については、「スタックトレース」セクションを参照してください。

stack_trace_filter:

"set_ftrace_filter"と似ていますが、スタックトレーサーがチェックする関数を制限します。

trace_clock:

イベントがリングバッファに記録されるたびに「タイムスタンプ」が追加されます。このタイムスタンプは指定されたクロックから取得されます。デフォルトではftraceは「ローカル」クロックを使用します。このクロックは非常に高速でCPUごとに厳密に動作しますが、一部のシステムでは他のCPUに対して単調性を持たない可能性があります。つまり、ローカルクロックは他のCPUのローカルクロックと同期していない可能性があります。

トレース用のクロック:

# cat trace_clock
[local] global counter x86-tsc

四角括弧で囲まれたクロックが現在有効なクロックです。

local:

デフォルトのクロックですが、CPU間で同期していない可能性があります

global:

このクロックはすべてのCPUと同期していますが、ローカルクロックに比べてやや遅くなる可能性があります。

counter:

これはクロックではなく、実際にはアトミックカウンターです。1つずつカウントアップしますが、すべてのCPUと同期しています。複数のCPU間でのイベントの正確な順序を把握するのに役立ちます。

uptime:

この機能はjiffiesカウンターを使用し、タイムスタンプは起動からの相対時間を示します。

perf:

この機能はftraceがperfが使用するクロックを使用します。最終的にはperfがftraceバッファを読み取れるようになり、データの重ね合わせに役立ちます。

x86-tsc:

アーキテクチャごとに独自のクロックを定義できます。たとえば、x86はここでは自身のTSCサイクルクロックを使用します。

ppc-tb:

この機能はPowerPCのタイムベースレジスタ値を使用します。CPU間で同期しており、tb_offsetがわかればハイパーサー/ゲスト間のイベントも関連付けることができます。

mono:

この機能は高速な単調クロック（CLOCK_MONOTONIC）を使用します。単調性を持ち、NTPのレート調整に影響されます。

mono_raw:

これは素朴な単調クロック（CLOCK_MONOTONIC_RAW）です。単調性を持ち、レート調整には影響されず、ハードウェアクロックソースと同じレートで刻みます。

boot:

これはブートクロック（CLOCK_BOOTTIME）です。これは高速モノトニッククロックに基づいていますが、スリープ時間も考慮されます。クロックアクセスはスリープパスでのトレース用途に設計されており、高速モノクロックが更新される前にスリープ時間の記録が行われた後にクロックにアクセスすると、一部の副作用が発生する可能性があります。その場合、クロックの更新は通常よりやや早めに見えることがあります。また、32ビットシステムでは、64ビットのブートオフセットが部分的に更新される可能性があります。これらの影響はまれですが、後処理で対応できるはずです。詳しくは、関数のコメントを参照してください。 ktime_get_boot_fast_ns() 関数のコメントを参照してください。

クロックを設定するには、このファイルにクロック名をエコーバックしてください：

# echo global > trace_clock

クロックの設定により、リングバッファの内容および「スナップショット」バッファもクリアされます。

trace_marker:

トレーサー¶

現在設定可能なトレーサーの一覧です。

「function」

すべてのカーネル関数をトレースする関数呼び出しトレーサー

「function_graph」

関数トレーサーと似ていますが、関数のエントリとエクスイットの両方をトレースします。これにより、Cコードソースに似た関数呼び出しのグラフを描くことが可能です。

「blk」

ブロックトレーサー。blktraceユーザー アプリケーションで使用されるトレーサー。

「hwlat」

ハードウェア遅延トレーサーは、ハードウェアが遅延を生成しているかを検出するために使用されます。下記の「ハードウェア遅延検出器」セクションを参照してください。

「irqsoff」

割込みを無効にする領域をトレースし、最大遅延を持つトレースを保存します。新しい最大値が記録されると、古いトレースは置き換えられます。このトレースはlatency-formatオプションを有効にした状態で確認するのが最適です。

「preemptoff」

irqsoffと同様ですが、プリエンプションが無効になる時間のトレースと記録を行います。

「preemptirqsoff」

irqsoffとpreemptoffと同様ですが、割込みと/またはプリエンプションが無効になる時間の最大値をトレースおよび記録します。

「wakeup」

最高優先度のタスクが目覚めた後にスケジューリングされるまでの最大遅延をトレースします。平均的な開発者が期待するようにすべてのタスクをトレースします。

「wakeup_rt」

RTタスク（現在の「wakeup」と同様）の目覚めのタイミングをトレースします。RTタスクの目覚めタイミングに興味がある人にとって役立ちます。

「wakeup_dl」

SCHED_DEADLINEタスクが目覚めるまでの最大遅延をトレースします（「wakeup」と「wakeup_rt」と同様）。

「mmiotrace」

バイナリモジュールのハードウェアへの呼び出しをトレースします。I/Oへの読み込み・書き込みもすべてトレースします。

「branch」

likelyおよびunlikelyブランチがヒットした場合をトレースし、予測が正しかったかを記録します。

“nop”

これは「何もトレースしない」トレーサーです。すべてのトレーサーを無効にするには、current_tracerに「nop」をエコーします。

エラー条件¶

ほとんどのftraceコマンドでは、失敗モードは明確で、標準の戻りコードを使用して通知されます。

より複雑なコマンドについては、トレーシング/エラーログファイルから拡張されたエラーメッセージが利用可能です。エラーメッセージを確認するには、エラー後にトレーシング/エラーログファイルを読み込むことで、問題の詳細な情報が得られる場合があります。トレーシング/エラーログファイルは、巡回エラーログであり、現在は8つのftraceエラーを表示します（過去8回の失敗したコマンドに関するものです）。

拡張エラーメッセージおよび使用方法の例は以下の通りです：

# echo xxx > /sys/kernel/debug/tracing/events/sched/sched_wakeup/trigger
echo: write error: Invalid argument

# cat /sys/kernel/debug/tracing/error_log
[ 5348.887237] location: error: Couldn't yyy: zzz
  Command: xxx
           ^
[ 7517.023364] location: error: Bad rrr: sss
  Command: ppp qqq
               ^

エラーログをクリアするには、空文字列をエコーしてください：

# echo > /sys/kernel/debug/tracing/error_log

  • 「p」はPREEMPT_NEED_RESCHEDのみが設定されている場合、

  • 「.」はそれ以外のケースです。

  • 「Z」- NMIがハード割り込み内での発生を示す

  • 「z」- NMIが実行中を示す

  • 「H」- ソフト割り込み内でのハード割り込み発生

  • 「h」- ハード割り込みが実行中

  • 「s」- ソフト割り込みが実行中

  • 「.」- 通常のコンテキスト

  • 「*」- 10ミリ秒以上

  • 「 」- 10マイクロ秒以下。

このオプションはトレース出力の形式を変更します。有効にすると、トレースに遅延に関する追加情報を表示します（「Latency trace format」を参照）。

pause-on-trace

設定されている場合、トレースファイルを読み込みモードで開くと、リングバッファへの書き込みを一時停止します（tracing_onがゼロに設定されたようにします）。ファイルを閉じると、トレースが再び有効になります。

record-cmd

任意のイベントまたはトレーサーが有効になっている場合、sched_switchトレースポイントでハックが有効になり、commキャッシュにマッピングされたPIDとコムが埋められます。ただし、これは一部のオーバーヘッドを引き起こす可能性があり、タスク名ではなくPIDだけに興味がある場合、このオプションを無効にすることでトレースの影響を軽減できます。詳しくは「saved_cmdlines」を参照してください。

record-tgid

任意のイベントまたはトレーサーが有効になっている場合、sched_switchトレースポイントでハックが有効になり、マッピングされたスレッドグループID（TGID）のキャッシュにPIDがマッピングされます。詳しくは「saved_tgids」を参照してください。

overwrite

トレースバッファが満杯になったときに起こる動作を制御します。「1」（デフォルト）の場合、最も古いイベントが破棄され上書きされます。「0」の場合、最も新しいイベントが破棄されます。（オーバーランとドロップについてはper_cpu/cpu0/statsを参照してください）

disable_on_free

free_bufferが閉じられたとき、トレースは停止します（tracing_onが0に設定されます）。

irq-info

割込み、プリエンプトカウント、need reschedデータを表示します。無効にするとトレースは以下のようになります：

# tracer: function
#
# entries-in-buffer/entries-written: 144405/9452052   #P:4
#
#           TASK-PID   CPU#      TIMESTAMP  FUNCTION
#              | |       |          |         |
          <idle>-0     [002]  23636.756054: ttwu_do_activate.constprop.89 <-try_to_wake_up
          <idle>-0     [002]  23636.756054: activate_task <-ttwu_do_activate.constprop.89
          <idle>-0     [002]  23636.756055: enqueue_task <-activate_task
markers

有効にするとtrace_markerはrootのみが書き込み可能になります。無効にするとtrace_markerは書き込み時にEINVALエラーを返します。

event-fork

set_event_pidに記載されたPIDを持つタスクがフォークする際、その子のPIDがset_event_pidに追加されます。また、set_event_pidに記載されたPIDを持つタスクが終了する際、そのPIDはファイルから削除されます。

set_event_notrace_pidに記載されたPIDにも影響します。

function-trace

このオプションが有効になっている場合（デフォルトでは有効）、レイテンシトレーサーはファンクショントレースを有効にします。無効にすると、レイテンシトレーサーは関数をトレースしません。これによりレイテンシテスト時のトレーサーのオーバーヘッドを抑えることができます。

function-fork

set_ftrace_pidに記載されたPIDを持つタスクがフォークする際、その子のPIDがset_ftrace_pidに追加されます。また、set_ftrace_pidに記載されたPIDを持つタスクが終了する際、そのPIDはファイルから削除されます。

set_ftrace_notrace_pidに記載されたPIDにも影響します。

display-graph

有効にすると、レイテンシトレーサー（irqsoff、wakeupなど）はファンクショングラフトレースを使用します。

stacktrace

有効にすると、任意のトレースイベントが記録された後にスタックトレースが記録されます。

branch

トレーサーとともにブランチトレースを有効にします。このオプションを「nop」トレーサーで有効にすると、単に「branch」トレーサーを有効にするのと同じです。

ヒント

一部のトレーサーには独自のオプションがあります。これらはトレーサーがアクティブなときにのみこのファイルに表示され、常にoptionsディレクトリに存在します。

各トレーサーのオプションは以下の通りです：

ファンクショントレーサーのオプション：

func_stack_trace

設定すると、記録される関数ごとにスタックトレースが記録されます。注意！ この機能を有効にする前に、「set_ftrace_filter」で記録する関数を制限してください。 otherwise システムパフォーマンスが深刻に低下します。関数フィルタをクリアする前にこのオプションを無効にしてください。

function_graphトレーサーのオプション:

function_graphトレーサーは出力がやや異なり、表示する内容を制御する独自のオプションを持っています。

funcgraph-overrun

設定すると、トレースされた関数ごとにグラフスタックの「overrun」が表示されます。overrunは、呼び出しスタックの深さが各タスクで予約されているよりも大きい場合に発生します。各タスクには呼び出しグラフでトレースする関数の固定配列があります。呼び出し深さがその配列を超えると、関数はトレースされません。overrunは、この配列を超えた際に無視された関数の数を表します。

funcgraph-cpu

設定すると、トレースが発生したCPUの番号が表示されます。

funcgraph-overhead

設定すると、関数が特定の時間以上かかる場合、遅延マーカーが表示されます。上記の「delay」セクションを参照してください。

funcgraph-proc

他のトレーサーとは異なり、デフォルトではプロセスのコマンドラインは表示されません。代わりにコンテキストスイッチ中にタスクがトレースされる際のみ表示されます。このオプションを有効にすると、各プロセスのコマンドラインがすべての行で表示されます。

funcgraph-duration

関数の終わり（戻り）時に、関数内で消費された時間（マイクロ秒単位）が表示されます。

funcgraph-abstime

設定すると、各行にタイムスタンプが表示されます。

funcgraph-irqs

無効にすると、割込み内で発生する関数はトレースされません。

funcgraph-tail

設定すると、戻りイベントにその関数を表す関数が含まれます。デフォルトではオフで、関数の戻りには閉じ括弧「}」のみ表示されます。

sleep-time

関数グラフトレーサーを実行中に、タスクがスケジューリングを終了した時間を関数に含めるためのオプションです。有効にすると、タスクがスケジューリングを終了した時間も関数呼び出しの一部として計測されます。

graph-time

関数グラフトレーサーを使用した関数プロファイラーで、ネストされた関数の呼び出し時間を含めるためのオプションです。このオプションが設定されていない場合、関数の報告時間は関数自体の実行時間のみを含み、呼び出した関数の時間は含まれません。

blkトレーサーのオプション:

blk_classic

よりミニマルな出力を表示します。

割り込みが無効になっている時間やプリエンプションが無効になっている時間が最も長い場所を把握することは役立ちます。しかし、時折、プリエンプションと/または割り込みが無効になっているタイミングを知りたい場合もあります。

wakeup¶

人々がトレースしたい典型的なケースの一つは、タスクが目覚めた後実際に実行されるまでの時間です。非リアルタイムタスクではこの時間は任意ですが、それでもトレースする価値があります。

wakeup_rt¶

リアルタイム環境では、最高優先度のタスクが起動して実行するまでにかかるウェイクアップ時間は非常に重要です。これは「スケジュールラテンシー」とも呼ばれます。ここで強調したいのは、これはリアルタイム（RT）タスクに関する話です。非リアルタイム（非RT）タスクのスケジュールラテンシーも重要ですが、非RTタスクでは平均的なラテンシーの方が適切です。このような測定にはLatencyTopなどのツールがより適しています。

リアルタイム環境では、最悪のラテンシーに注目します。これは何かが起きてかかる最も長いラテンシーであり、平均値ではなく、最悪のケースを指します。非常に高速なスケジューラであっても、まれに大きなラテンシーが発生する場合がありますが、リアルタイムタスクには不適切です。wakeup_rtトレーサーは、リアルタイムタスクの最悪のウェイクアップを記録するように設計されています。非RTタスクは記録されません。なぜなら、トレーサーは1つの最悪ケースのみを記録し、予測不可能な非RTタスクをトレースするとRTタスクの最悪ラテンシーが上書きされるからです（通常のwakeupトレーサーを少し実行してその効果を確認してください）。

このトレーサーはRTタスクのみを対象とするため、以前のトレーサーとは異なり少し異なる方法で実行します。'ls'ではなく、'chrt'の下で'sleep 1'を実行します。これはタスクの優先度を変更します。

実行中に関数をトレースしたい場合は、以下のシンプルなプログラムを使用できます。

#include <stdio.h>
#include <stdlib.h>
#include <sys/types.h>
#include <sys/stat.h>
#include <fcntl.h>
#include <unistd.h>
#include <string.h>

#define _STR(x) #x
#define STR(x) _STR(x)
#define MAX_PATH 256

const char *find_tracefs(void)
{
       static char tracefs[MAX_PATH+1];
       static int tracefs_found;
       char type[100];
       FILE *fp;

       if (tracefs_found)
               return tracefs;

       if ((fp = fopen("/proc/mounts","r")) == NULL) {
               perror("/proc/mounts");
               return NULL;
       }

       while (fscanf(fp, "%*s %"
                     STR(MAX_PATH)
                     "s %99s %*s %*d %*d\n",
                     tracefs, type) == 2) {
               if (strcmp(type, "tracefs") == 0)
                       break;
       }
       fclose(fp);

       if (strcmp(type, "tracefs") != 0) {
               fprintf(stderr, "tracefs not mounted");
               return NULL;
       }

       strcat(tracefs, "/tracing/");
       tracefs_found = 1;

       return tracefs;
}

const char *tracing_file(const char *file_name)
{
       static char trace_file[MAX_PATH+1];
       snprintf(trace_file, MAX_PATH, "%s/%s", find_tracefs(), file_name);
       return trace_file;
}

int main (int argc, char **argv)
{
        if (argc < 1)
                exit(-1);

        if (fork() > 0) {
                int fd, ffd;
                char line[64];
                int s;

                ffd = open(tracing_file("current_tracer"), O_WRONLY);
                if (ffd < 0)
                        exit(-1);
                write(ffd, "nop", 3);

                fd = open(tracing_file("set_ftrace_pid"), O_WRONLY);
                s = sprintf(line, "%d\n", getpid());
                write(fd, line, s);

                write(ffd, "function", 8);

                close(fd);
                close(ffd);

                execvp(argv[1], argv+1);
        }

        return 0;
}

関数グラフトレーサー（function graph tracer）¶

このトレーサーは、関数トレーサーと似ていますが、関数のエントリとエクスイットの両方でプローブを実行します。これは、各task_structにダイナミックに割り当てられた戻り先アドレススタックを使用して行われます。関数のエントリ時にトレーサーは、トレース対象の関数の戻り先アドレスをカスタムプローブに設定し、元の戻り先アドレスをtask_struct内の戻り先アドレススタックに保存します。

関数の両端でプローブを行うことで、以下の特徴が得られます:

  • 関数の実行時間の測定

  • 信頼できるコールスタックを取得して関数呼び出しのグラフを描画する

このトレーサーは以下の状況で役立ちます:

  • カーネルの不思議な挙動の原因を特定したい場合で、詳細な動作を任意の領域（または特定の領域）で確認したい場合。

  • 不思議なレイテンシーを経験しているが、その起源を特定するのが難しい場合。

  • 特定の関数がどのパスを取るかを素早く確認したい場合。

  • 動作しているカーネルの中身を確認したい場合で、そこで何が起きているかを確認したい場合。

このトレーサーには、以下の「dynamic ftrace」セクションで説明されている他の有用な機能（特定の関数やタスクのみをトレースする機能など）が含まれています。

dynamic ftrace¶

CONFIG_DYNAMIC_FTRACEが設定されている場合、関数トレースが無効な状態ではシステムがほぼゼロのオーバーヘッドで動作します。これは、mcount関数呼び出し（gccの-pgスイッチで生成されるすべてのカーネル関数の開始位置に配置される）が最初は単純なリターンを指しているためです。（FTRACEを有効にすると、カーネルのコンパイル時に-pgスイッチが含まれます。）

コンパイル時にすべてのCファイルオブジェクトはrecordmcountプログラム（scriptsディレクトリに配置）を経由します。このプログラムは、CオブジェクトのELFヘッダーを解析し、.textセクション内のすべてのmcount呼び出し位置を検出します。gccバージョン4.6以降では、x86向けに-mfentryスイッチが追加され、mcountではなく「__fentry__」を呼び出します。これはスタックフレームの作成前に呼び出されます。

注意: すべてのセクションがトレースされるわけではありません。notrace または他の方法でブロックされる可能性があり、すべてのインライン関数はトレースされません。トレース可能な関数を確認するには、「available_filter_functions」ファイルをご覧ください。

「__mcount_loc」というセクションが作成され、.textセクション内のすべての mcount/fentry 呼び出し場所への参照を保持します。recordmcount プログラムはこのセクションを元のオブジェクトに戻して再リンクします。カーネルの最終リンクステージでは、これらのすべての参照を1つのテーブルに追加します。

起動時にSMPが初期化される前、動的ftraceコードはこのテーブルをスキャンし、すべての場所をnopsに更新します。また、これらの場所はavailable_filter_functionsリストに追加されます。モジュールはロードされるときおよび実行される前にも処理されます。モジュールがアンロードされるとき、その関数はftrace関数リストから削除されます。これはモジュールアンロードコードで自動的に行われ、モジュール作成者は気にする必要がありません。

トレースが有効になっている場合、関数トレースポイントの変更プロセスはアーキテクチャに依存します。古い方法は、kstop_machine を使用して、変更対象のコードを実行しているCPUとの競合条件を防ぐためです（これはCPUが不望な動作を引き起こす可能性があり、特に変更されたコードがキャッシュ（またはページ）境界を越える場合）。この場合、nopsは再び呼び出しにパッチされます。しかし、今回はmcount（これは単なる関数スタブです）を呼びません。代わりに、ftraceインフラストラクチャに呼び出します。

関数トレースポイントを変更する新しい方法は、変更する場所にブレイクポイントを設置し、すべてのCPUを同期させ、ブレイクポイントでカバーされない他のインストラクションを変更することです。再度すべてのCPUを同期させ、その後、完了したバージョンでブレイクポイントをftrace呼び出し先に移動します。

一部のアーキテクチャでは、同期処理すら必要なく、他のCPUが同時に実行している間に新しいコードを古いコードの上に置くだけで問題ありません。

トレースされている関数の記録には、特別な副作用があり、今では選択的にどの関数をトレースしたいか、どの関数のmcount呼び出しをnopsのままにしたいかを指定できます。

ftrace_enabled¶

注意、proc sysctl ftrace_enableは関数トレーサーの大きなオン/オフスイッチです。デフォルトでは有効（カーネルで関数トレースが有効になっている場合）。無効にするとすべての関数トレースが無効になります。これはftraceの関数トレーサーだけでなく、perf、kprobes、スタックトレース、プロファイリングなど他の用途にも影響します。FTRACE_OPS_FL_PERMANENTが設定されたコールバックが登録されている場合は無効にできません。

注意してこの機能を無効にしてください。

これは無効化（有効化も可能）できます。

 sysctl kernel.ftrace_enabled=0
 sysctl kernel.ftrace_enabled=1

or

 echo 0 > /proc/sys/kernel/ftrace_enabled
 echo 1 > /proc/sys/kernel/ftrace_enabled

フィルタリングコマンド¶

set_ftrace_filterインターフェースでいくつかのコマンドがサポートされています。トレースコマンドは以下の形式を持ちます。

<function>:<command>:<parameter>

サポートされているコマンドは以下の通りです：

  • mod: このコマンドはモジュールごとに関数フィルタリングを有効にします。パラメータはモジュールを定義します。たとえば、ext3モジュール内のwrite*関数のみを希望する場合、実行してください:

    echo ‘write*:mod:ext3’ > set_ftrace_filter

    このコマンドは、関数名に基づいたフィルタリングと同じようにフィルターと相互作用します。したがって、別のモジュールに追加の関数を追加するには、フィルターファイルに追加（>>）します。特定のモジュールの関数を削除するには、'!'を先頭に付けてください:

    echo '!writeback*:mod:ext3' >> set_ftrace_filter

    Modコマンドはモジュールグロブをサポートします。すべての関数のトレースを無効化し、特定のモジュールのみをトレースするには:

    echo '!*:mod:!ext3' >> set_ftrace_filter

    すべてのモジュールのトレースを無効化しますが、カーネルのトレースは有効にします:

    echo '!*:mod:*' >> set_ftrace_filter

    カーネルのみにフィルタを有効にするには:

    echo '*write*:mod:!*' >> set_ftrace_filter

    モジュールグロブにフィルタを有効にするには:

    echo '*write*:mod:*snd*' >> set_ftrace_filter

  • traceon/traceoff: これらのコマンドは、指定された関数が呼び出されるときにトレースをオン/オフにします。パラメータはトレースシステムをオン/オフにする回数を決定します。指定がない場合、制限はありません。たとえば、schedule bugが最初の5回呼び出されるときにトレースを無効にするには、実行してください:

    echo '__schedule_bug:traceoff:5' > set_ftrace_filter

    常に__schedule_bugが呼び出されるときにトレースを無効にするには:

    echo '__schedule_bug:traceoff' > set_ftrace_filter

    これらのコマンドは、set_ftrace_filterに追加するかどうかに関わらず累積されます。コマンドを削除するには、'!'を先頭に付け、パラメータを省略してください:

    echo '!__schedule_bug:traceoff:0' > set_ftrace_filter

    上記は、カウンターを持つ__schedule_bug用のtraceoffコマンドを削除します。カウンターを持たないコマンドを削除するには:

    echo '!__schedule_bug:traceoff' > set_ftrace_filter

  • snapshot: 関数が呼び出されるときにスナップショットがトリガーされます。

    echo 'native_flush_tlb_others:snapshot' > set_ftrace_filter

    1回だけスナップショットを撮るには：

    echo 'native_flush_tlb_others:snapshot:1' > set_ftrace_filter

    上記のコマンドを削除するには：

    echo '!native_flush_tlb_others:snapshot' > set_ftrace_filter
echo '!native_flush_tlb_others:snapshot:0' > set_ftrace_filter

  • enable_event/disable_event: これらのコマンドはトレースイベントを有効または無効にできます。注意: 関数トレースコールバックは非常に敏感なので、これらのコマンドが登録されると、トレースポイントがアクティブになりますが、「ソフト」モードで無効になります。つまり、トレースポイントは呼び出されますが、実際にトレースされません。イベントトレースポイントは、コマンドがトリガーする限りこのモードのままです。

    echo 'try_to_wake_up:enable_event:sched:sched_switch:2' > \
      set_ftrace_filter

    フォーマットは以下の通りです:

    <function>:enable_event:<system>:<event>[:count]
<function>:disable_event:<system>:<event>[:count]

    イベントコマンドを削除するには:

    echo '!try_to_wake_up:enable_event:sched:sched_switch:0' > \
      set_ftrace_filter
echo '!schedule:disable_event:sched:sched_switch' > \
      set_ftrace_filter

  • dump: 関数が呼び出されるときに、ftraceリングバッファの内容をコンソールにダンプします。これはデバッグが必要な場合、特定の関数が呼び出されるときにトレースをダンプしたいときに便利です。たとえば、トリプルフォールトが発生する前に呼ばれる関数で、通常のダンプを取得できない場合に役立ちます。

  • cpudump: この関数が呼び出されると、現在のCPUのftraceリングバッファの内容がコンソールに出力されます。"dump"コマンドとは異なり、この関数によってトリガーされたCPUのリングバッファの内容のみが表示されます。

  • stacktrace: この関数が呼び出されると、スタックトレースが記録されます。

トレースエントリ¶

カーネルの問題診断において、データ量が多すぎたり少なすぎたりするのは問題になります。buffer_size_kbファイルは内部トレースバッファのサイズを変更するために使用されます。表示される数値は各CPUごとに記録可能なエントリ数を示します。総サイズを知るには、可能なCPU数をエントリ数で乗算してください。

# cat buffer_size_kb
1408 (units kilobytes)

あるいはbuffer_total_size_kbを読み取るだけで済みます

# cat buffer_total_size_kb
5632

バッファを変更するには、1024バイトセグメント単位の数値をエコします。

# echo 10000 > buffer_size_kb
# cat buffer_size_kb
10000 (units kilobytes)

できるだけ多くのメモリを割り当てようとします。ただし、割り当てすぎるとOut-Of-Memoryが発生する可能性があります。

# echo 1000000000000 > buffer_size_kb
-bash: echo: write error: Cannot allocate memory
# cat buffer_size_kb
85

per_cpuバッファは個別に変更することもできます:

# echo 10000 > per_cpu/cpu0/buffer_size_kb
# echo 100 > per_cpu/cpu1/buffer_size_kb

per_cpuバッファがすべて同じでない場合、トップレベルのbuffer_size_kbはXを表示します

# cat buffer_size_kb
X

このときbuffer_total_size_kbは役立ちます:

# cat buffer_total_size_kb
12916

トップレベルのbuffer_size_kbに書き込むことで、すべてのバッファを同じサイズに戻せます。

スナップショット¶

CONFIG_TRACER_SNAPSHOTは、すべての非遅延トレーサーに汎用的なスナップショット機能を提供します。(遅延を記録する遅延トレーサー、例えば"irqsoff"や"wakeup"は、内部で既にスナップショットメカニズムを使用しているため、この機能は利用できません。)

スナップショットはトレースバッファを特定のタイミングで保持し、トレースを停止せずに動作を継続します。Ftraceは現在のバッファと余分なバッファを交換し、トレースは新しい現在のバッファ（＝以前の余分なバッファ）で継続します。

「tracing」ディレクトリ内の以下のtracefsファイルはこの機能に関連しています:

インスタンス¶

tracefsトレースディレクトリ内には「instances」というディレクトリがあります。このディレクトリ内にはmkdirコマンドで新しいディレクトリを作成し、rmdirコマンドでディレクトリを削除できます。このディレクトリ内でmkdirコマンドで作成したディレクトリは、作成後すぐにファイルや他のディレクトリを含みます。

# mkdir instances/foo
# ls instances/foo

set_event  snapshot  trace  trace_clock  trace_marker  trace_options
trace_pipe  tracing_on

新しいディレクトリはトレースディレクトリ自身と非常に似ています。実際には、メインディレクトリや他のインスタンスとは無関係なバッファとイベントを持つため、それ以外の点では非常に似ています。

新しいディレクトリ内のファイルは、トレースディレクトリ内の同名のファイルと同様に動作しますが、使用するバッファは別途に作成された新しいバッファです。これらのファイルはこのバッファに影響を与えますが、メインバッファには影響を与えません（trace_optionsを除く）。現在、trace_optionsはすべてのインスタンスとトップレベルのバッファに影響を与えますが、今後のリリースではこの挙動が変更される可能性があります。つまり、オプションがインスタンスごとに特定されるようになるかもしれません。

スタックトレース¶

カーネルは固定サイズのスタックを持つため、関数内でスタックを無駄にしないことが重要です。カーネル開発者はスタックに何を割り当てるかを意識する必要があります。割り当てすぎると、システムがスタックオーバーフローの危険にさらされ、通常はシステムパニックを引き起こす腐敗が発生します。

このチェックを行うためのツールはいくつか存在し、通常は定期的に中断して使用状況を確認します。ただし、関数呼び出しごとにチェックを行うことで非常に有用になります。ftraceが関数トレーサーを提供しているため、関数呼び出しごとにスタックサイズを確認するのに便利です。これはスタックトレーサーを通じて有効になります。

CONFIG_STACK_TRACERはftraceのスタックトレース機能を有効にします。有効にするには、/proc/sys/kernel/stack_tracer_enabledに'1'を書き込みます。

# echo 1 > /proc/sys/kernel/stack_tracer_enabled

また、カーネルコマンドラインパラメータに"stacktrace"を追加することで、起動時にカーネルのスタックサイズをトレースするための設定も可能です。

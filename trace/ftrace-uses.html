ftraceを用いた関数へのフック¶

対象バージョン: 4.14

はじめに¶

ftraceインフラストラクチャは、カーネルの関数の開始部分にコールバックをアタッチしてフローを記録・トレースするためのものとして最初に作成されました。ただし、関数の開始にコールバックを追加する用途は他にもあります。ライブカーネルパッチングやセキュリティモニタリングなどです。このドキュメントでは、ftraceを使用して独自の関数コールバックを実装する方法について説明します。

ftraceのコンテキスト¶

警告

カーネル内のほぼすべての関数にコールバックを追加できる機能にはリスクがあります。コールバックは、通常コンテキスト、softirq、irq、NMIなど、任意のコンテキストから呼び出される可能性があります。また、アイドル状態に入る直前やCPUの起動・停止中、ユーザースペースに移行する際にも呼び出されることがあります。これにより、コールバック内で実行できる処理には特別な注意が必要です。RCUの保護範囲外で呼び出される可能性があります。

ftraceインフラストラクチャには再帰やRCUに対する保護がありますが、それでもコールバックの使用方法に非常に注意する必要があります。

ftrace_ops構造体¶

関数コールバックを登録するにはftrace_opsが必要です。この構造体はftraceにどの関数をコールバックとして呼び出すかを伝えるだけでなく、コールバックが実行する保護処理を指定し、ftraceが処理する必要がないことを示します。

ftrace_opsをftraceに登録する際には、設定する必要があるフィールドは1つだけです:

struct ftrace_ops ops = {
      .func                    = my_callback_func,
      .flags                   = MY_FTRACE_FLAGS
      .private                 = any_private_data_structure,
};

.flagsと.privateはどちらもオプションです。.funcのみが必須です。

トレースを有効にするには以下を呼び出します:

register_ftrace_function(&ops);

トレースを無効にするには以下を呼び出します:

unregister_ftrace_function(&ops);

上記は以下のヘッダーファイルをインクルードすることで定義されます:

#include <linux/ftrace.h>

登録されたコールバックはregister_ftrace_function()が呼ばれた後で、その関数が返る前に開始されます。コールバックが開始される正確なタイミングはアーキテクチャとサービスのスケジューリングに依存します。コールバック自体は、正確なタイミングで実行する必要がある場合、同期処理を担当する必要があります。

unregister_ftrace_function()は、その関数がコールバックを呼び出さなくなることを保証します。注意点として、この保証を実行するためにunregister_ftrace_function()は時間がかかる場合があります。

コールバック関数¶

コールバック関数のプロトタイプは以下の通りです（v4.14以降）:

void callback_func(unsigned long ip, unsigned long parent_ip,
                   struct ftrace_ops *op, struct pt_regs *regs);
@ip

これはトレース対象の関数のインストラクションポインタです（fentryまたはmcountが含まれる関数内）。

@parent_ip

これはトレース対象の関数を呼び出した関数のインストラクションポインタです（関数呼び出しが行われた場所）。

@op

このポインタは、コールバックを登録するために使用されたftrace_opsへのポインタです。このポインタは、コールバックにデータを渡すためにプライベートポインタを通じて使用できます。

@regs

ftrace_ops構造体にFTRACE_OPS_FL_SAVE_REGSまたはFTRACE_OPS_FL_SAVE_REGS_IF_SUPPORTEDフラグが設定されている場合、これはpt_regs構造体を指すことがあり、関数の開始位置にブレイクポイントが設定されている場合と同じように動作します。それ以外の場合、これは無効な値またはNULLを指しています。

ftraceのフラグ¶

ftrace_opsフラグはすべてinclude/linux/ftrace.hで定義され、ドキュメントされています。一部のフラグはftraceの内部インフラストラクチャに使用されるものですが、ユーザーが意識すべきフラグは以下の通りです。

FTRACE_OPS_FL_SAVE_REGS

コールバックがpt_regsを読み取るか変更する必要がある場合、このフラグを設定する必要があります。このフラグを設定してftrace_opsを登録したアーキテクチャがpt_regsをコールバックに渡すことをサポートしない場合、登録は失敗します。

FTRACE_OPS_FL_SAVE_REGS_IF_SUPPORTED

SAVE_REGSと似ていますが、このフラグを設定した場合、アーキテクチャがregsを渡すことをサポートしない場合でもftrace_opsの登録は失敗しません。ただし、コールバックはregsがNULLかどうかを確認して、アーキテクチャがサポートしているかを判断する必要があります。

FTRACE_OPS_FL_RECURSION_SAFE

デフォルトでは、コールバックの周りにラッパーが追加され、関数の再帰が発生しないようにします。つまり、コールバックの実行結果として呼び出される関数がトレースされている場合でも、ftraceはコールバックが再度呼び出されることを防ぎます。ただし、このラッパーはオーバーヘッドを追加するため、コールバックが再帰安全である場合、このフラグを設定してftraceの保護を無効にできます。

注意：このフラグが設定されており、再帰が発生した場合、システムがクラッシュし、三重フェールトにより再起動する可能性があります。

他のコールバックが再帰安全のコールバックによって呼び出される関数をトレースしても問題ありません。再帰安全なコールバックは、自身またはそのネストされた関数が呼び出す関数をトレースしてはなりません。

このフラグが設定されている場合、プリエンプションが有効になっている状態でコールバックが呼び出される可能性があります（CONFIG_PREEMPTIONが設定されている場合）。ただし、これは保証されたものではありません。

FTRACE_OPS_FL_IPMODIFY

FTRACE_OPS_FL_SAVE_REGSを設定する必要があります。コールバックが「トレースされる関数をハッキング」して（トレースされる関数の代わりに別の関数を呼び出す）場合、このフラグを設定する必要があります。これはライブカーネルパッチが使用する仕組みです。このフラグが設定されていない場合、pt_regs->ipを変更することはできません。

注意: 1つの関数に対して、FTRACE_OPS_FL_IPMODIFYが設定されたftrace_opsは一度に1つしか登録できません。

FTRACE_OPS_FL_RCU

このフラグが設定されている場合、コールバックはRCUが「監視中」である関数のみから呼び出されます。コールバック関数がRCUの保護を必要とする処理を実行する場合は、このフラグを設定する必要があります。 rcu_read_lock() operation.

RCUはシステムがアイドル状態になったとき、CPUが停止して再びオンラインになるとき、およびキーネル空間からユーザースペースへ移行し戻るときに監視を停止します。これらの移行期間中、コールバックが実行される可能性があり、RCUの同期はその保護を提供しません。

FTRACE_OPS_FL_PERMANENT

このフラグが設定されたftrace_opsがある場合、proc sysctlのftrace_enabledに0を書き込むことでトレースを無効にすることができません。同様に、ftrace_enabledが0の状態でこのフラグを設定したコールバックの登録はできません。

ライブパッチは関数リダイレクトを失わないように使用するため、システムは常に保護されています。

トレースする関数のフィルタリング¶

コールバックが特定の関数のみから呼び出される場合、フィルタを設定する必要があります。フィルタは関数名で指定するか、IPアドレス（既知の場合）で指定します。

int ftrace_set_filter(struct ftrace_ops *ops, unsigned char *buf,
                      int len, int reset);
@ops

フィルタを設定するためのops

@buf

関数フィルタのテキストを保持する文字列。

@len

文字列の長さ。

@reset

フィルタを適用する前にすべてのフィルタをリセットする場合は0以外の値を指定します。

フィルタはトレースが有効なときにどの関数を有効にするかを指定します。@bufがNULLでresetが設定されている場合、すべての関数がトレース対象になります。

@bufは特定のパターンにマッチするすべての関数を有効にするグロブ式としても使用できます。

フィルタコマンドについては Documentation/trace/ftrace.rst.

schedule関数のみをトレースするには:

ret = ftrace_set_filter(&ops, "schedule", strlen("schedule"), 0);

追加の関数をトレースする場合は、@resetパラメータを0に設定してftrace_set_filter()を複数回呼び出します。現在のフィルタを削除し、@bufで定義された新しい関数に置き換えるには、@resetを0以外の値に設定します。

すべてのフィルタされた関数を削除し、すべての関数をトレースするには:

ret = ftrace_set_filter(&ops, NULL, 0, 1);

複数の関数が同じ名前を持つ場合、特定の関数のみをトレースするにはftrace_set_filter_ip()を使用できます。

ret = ftrace_set_filter_ip(&ops, ip, 0, 0);

ただし、ipはfentryまたはmcountへの呼び出しのアドレスでなければなりません。この関数はperfやkprobesから使用され、ユーザーがdebug情報から取得したipアドレスを取得します。

グロブ式でフィルタを設定した場合、関数を「notrace」リストに追加して、これらの関数がコールバックを呼び出さないようにできます。「notrace」リストは「filter」リストよりも優先されます。両方のリストが空でなく同じ関数を含む場合、コールバックはどの関数からも呼び出されません。

「notrace」リストが空である場合、フィルタで定義されたすべての関数がトレースされることが許可されます。

int ftrace_set_notrace(struct ftrace_ops *ops, unsigned char *buf,
                       int len, int reset);

これはftrace_set_filter()と同じパラメータを取るが、見つかった関数をトレースしないリストに追加します。これはフィルタリストとは別のリストであり、この関数はフィルタリストを変更しません。

非ゼロの@resetは、@bufに一致する関数を追加する前に「notrace」リストをクリアします。

「notrace」リストをクリアすることは、フィルタリストをクリアすることと同様です。

ret = ftrace_set_notrace(&ops, NULL, 0, 1);

フィルタとnotraceリストはいつでも変更可能です。特定の関数のみがコールバックを呼び出す必要がある場合、コールバックの登録前にフィルタを設定するのが望ましいです。ただし、コールバックが登録された後でも変更することがあります。

フィルタが有効な状態で、@resetが非ゼロであり、@bufに関数に一致するグロブが含まれている場合、ftrace_set_filter()呼び出し中に切り替えが行われます。いつでもすべての関数がコールバックを呼び出すことはありません。

ftrace_set_filter(&ops, "schedule", strlen("schedule"), 1);

register_ftrace_function(&ops);

msleep(10);

ftrace_set_filter(&ops, "try_to_wake_up", strlen("try_to_wake_up"), 1);

は同じではありません：

ftrace_set_filter(&ops, "schedule", strlen("schedule"), 1);

register_ftrace_function(&ops);

msleep(10);

ftrace_set_filter(&ops, NULL, 0, 1);

ftrace_set_filter(&ops, "try_to_wake_up", strlen("try_to_wake_up"), 0);

後者は、リセット時間と新しいフィルタ設定時間の間にすべての関数がコールバックを呼び出す短い期間を持つため、前者とは異なります。

イベントヒストグラム¶

Tom Zanussi によって書かれたドキュメンテーション

1. はじめに¶

ヒストグラムトリガーは、トレースイベントデータをヒストグラムに集約するために使用できる特別なイベントトリガーです。トレースイベントとイベントトリガーに関する情報については、 イベントトレース.

2. ヒストグラムトリガー コマンド¶

ヒストグラムトリガー コマンットは、イベントのヒットをハッシュテーブルに集約するイベントトリガー コマンドです。このハッシュテーブルは、1つ以上のトレースイベント形式フィールド（またはスタックトレース）と、1つ以上のトレースイベント形式フィールドおよび/またはイベントカウント（ヒットカウント）から導出された累積合計に基づいてキー付けされます。

ヒストグラムトリガーの形式は次のとおりです：

hist:keys=<field1[,field2,...]>[:values=<field1[,field2,...]>]
  [:sort=<field1[,field2,...]>][:size=#entries][:pause][:continue]
  [:clear][:name=histname1][:<handler>.<action>] [if <filter>]

一致するイベントが発生すると、キー（key）と値（value）でハッシュテーブルにエントリが追加されます。キーと値はイベントの形式説明にあるフィールドに対応します。値は数値フィールドに限られ、イベント発生時にそのフィールドの累積合計に値が加算されます。特別な文字列「hitcount」は明示的な値フィールドの代わりに使用でき、これは単にイベント発生数のカウントです。値が指定されていない場合、自動的に「hitcount」が作成され、唯一の値として使用されます。キーは任意のフィールドまたは特別な文字列「stacktrace」（イベントのカーネルスタックトレースをキーとして使用）を指定できます。キーワード「keys」または「key」でキーを指定し、「values」「vals」「val」で値を指定します。複合キーは「keys」キーワードで最大2つのフィールドを指定できます。複合キーをハッシュ化すると、各コンポーネントキーのユニークな組み合わせごとにテーブルにユニークなエントリが生成され、イベントデータのより細かいサマリーに役立ちます。さらに、「sort」キーワードで最大2つのフィールドを指定したソートキーも可能です。複数のフィールドを指定した場合、結果は「ソート内でのソート」となり、最初のキーを主ソートキー、2番目のキーを副ソートキーとします。ヒストグラムトリガーに「name」パラメータで名前を指定すると、同じ名前の他のトリガーとヒストグラムデータを共有し、トリガーのヒットがこの共通データを更新します。互換性のあるフィールドを持つトリガーのみがこのように組み合わせられます。互換性があるとは、トリガーで指定したフィールドが同じ数と種類のフィールドを持ち、かつフィールド名も同じであることです。注意点として、任意の2つのイベントは常に互換性のある「hitcount」および「stacktrace」フィールドを共有しているため、これらのフィールドを用いて組み合わせることは可能です。ただし、その意味は無駄である可能性があります。

‘hist’トリガーは、各イベントのサブディレクトリに‘hist’ファイルを追加します。イベントの‘hist’ファイルを読み込むと、ハッシュテーブルの全内容が標準出力にダンプされます。複数の‘hist’トリガーがイベントに接続されている場合、出力には各トリガーごとにテーブルが表示されます。名前が指定されたトリガーのテーブルは、同じ名前を持つ他のインスタンスと同一です。各印刷されたハッシュテーブルのエントリは、エントリを構成するキーと値の簡単なリストです。キーは最初に表示され、カーネルのブレースで区切られ、その後にエントリの値フィールドのセットが続きます。デフォルトでは、数値フィールドは10進整数として表示されます。この表示形式は、フィールド名に以下のいずれかの修飾子を追加することで変更できます:

.hex

数値を16進数として表示

.sym

アドレスをシンボルとして表示

.sym-offset

アドレスをシンボルおよびオフセットとして表示

.syscall

システムコールIDをシステムコール名として表示

.execname

common_pidをプログラム名として表示

.log2

raw数値ではなくlog2値を表示

.usecs

common_timestampをマイクロ秒で表示

通常、フィールドのセマンティクスは修飾子を適用する際には解釈されませんが、この点に関するいくつかの制限があります:

  • 値（値は基本的に合計であり、他の修飾子はその文脈では意味を持たないため）にはのみ‘hex’修飾子が使用できます。

  • ‘execname’修飾子は‘common_pid’にのみ適用できます。その理由は、execnameはイベントがトリガーされた際の現在のプロセスの‘comm’値を保存したものです。これはイベントトレースコードが保存するcommon_pid値と同じです。他のpid値にそのcomm値を適用しようとすると不正確であり、通常、イベントがpid固有のcommフィールドをイベント自体に保存します。

histトリガーを有効化し、現在の内容を読み込み、その後無効にする典型的な使用例は以下の通りです:

# echo 'hist:keys=skbaddr.hex:vals=len' > \
  /sys/kernel/debug/tracing/events/net/netif_rx/trigger

# cat /sys/kernel/debug/tracing/events/net/netif_rx/hist

# echo '!hist:keys=skbaddr.hex:vals=len' > \
  /sys/kernel/debug/tracing/events/net/netif_rx/trigger

トリガー自身のファイルを読み込むことで、現在接続されているhistトリガーの詳細を確認できます。この情報は、‘hist’ファイルを読み込む際にも上部に表示されます。

デフォルトではハッシュテーブルのサイズは2048エントリです。‘size’パラメータを使用して、より多くまたは少なくすることができ、単位はハッシュテーブルエントリ数です。ランが指定したよりも多くのエントリを使用する場合、結果には‘drops’（無視されたヒット数）が表示されます。サイズは128から131072までの2の累乗でなければなりません（非2の累乗の数値は上向きに丸められます）。

「sort」パラメータは、ソート対象の値フィールドを指定するために使用できます。指定されていない場合のデフォルトは「hitcount」で、デフォルトのソート順は「昇順」です。逆順にソートするには、ソートキーに「.descending」を追加してください。

「pause」パラメータは、既存のhistトリガーを一時停止するか、またはhistトリガーを開始するがイベントをログに記録しない状態で起動するのに使用できます。「continue」または「cont」は、一時停止されたhistトリガーを再開または再起動するために使用できます。

「clear」パラメータは、実行中のhistトリガーの内容をクリアし、現在の一時停止/アクティブ状態を維持します。

既存のトリガーに適用する場合、「pause」、「cont」、「clear」パラメータは「append」シェル演算子（「>>」）を使用する必要があります。これに対して「>」演算子を使用すると、トリガーがtruncateによって削除されてしまいます。

  • enable_hist/disable_hist

    enable_histとdisable_histトリガーは、あるイベントが既にアタッチされているhistトリガーを条件付きで開始および停止するのに使用できます。任意の数のenable_histとdisable_histトリガーを特定のイベントにアタッチできるため、そのイベントが他の多数のイベントの集計を開始および停止できるようになります。

    フォーマットはenable/disable_eventトリガーと非常に似ています:

    enable_hist:<system>:<event>[:count]
disable_hist:<system>:<event>[:count]

    enable/disable_eventトリガーがターゲットイベントのトレースバッファへのトレースを有効または無効にするのとは異なり、enable/disable_histトリガーはターゲットイベントをハッシュテーブルへの集計を有効または無効にします。

    enable_hist/disable_histトリガーの典型的な使用例は、まずあるイベントに一時停止されたhistトリガーを設定し、その後、条件に応じてhist集計をオン/オフにするenable_hist/disable_histペアを使用することです:

    # echo 'hist:keys=skbaddr.hex:vals=len:pause' > \
   /sys/kernel/debug/tracing/events/net/netif_receive_skb/trigger

 # echo 'enable_hist:net:netif_receive_skb if filename==/usr/bin/wget' > \
   /sys/kernel/debug/tracing/events/sched/sched_process_exec/trigger

 # echo 'disable_hist:net:netif_receive_skb if comm==wget' > \
   /sys/kernel/debug/tracing/events/sched/sched_process_exit/trigger

    上記は、特定のプログラムが実行されるときに一時停止されたhistトリガーを解除してイベントを集計を開始し、プロセスが終了してhistトリガーが再び一時停止されるときに集計を停止するように設定します。

    以下の例は、上記で説明した概念と典型的な使用パターンをより具体的に示しています。

「special」イベントフィールド¶

histトリガーのキーまたは値として使用できる「特殊なイベントフィールド」はいくつかあります。これらは実際のイベントフィールドのように見え、動作しますが、イベントのフィールド定義やフォーマットファイルには含まれていません。ただし、すべてのイベントで利用可能で、実際のイベントフィールドの場所に使用できます。

common_timestamp

u64

イベントに関連するタイムスタンプ（リングバッファから取得）で、ナノ秒単位です。.usecs パラメータを使用してタイムスタンプをマイクロ秒として解釈するように変更できます。

common_cpu

int

イベントが発生したCPU

拡張エラー情報¶

hist トリガー コマンドを呼び出す際に発生する一部のエラー条件では、tracing/error_log ファイルを介して拡張エラー情報が利用可能です。エラー条件については、以下を参照してください。 Documentation/trace/ftrace.rst 詳しくは以下をご参照ください。

6.2 ‘hist’ トリガーの例¶

最初の例では、kmalloc イベントを使用して集約を生成します。hist トリガーで使用可能なフィールドは、kmalloc イベントのフォーマットファイルに記載されています：

# cat /sys/kernel/debug/tracing/events/kmem/kmalloc/format
name: kmalloc
ID: 374
format:
    field:unsigned short common_type;       offset:0;       size:2; signed:0;
    field:unsigned char common_flags;       offset:2;       size:1; signed:0;
    field:unsigned char common_preempt_count;               offset:3;       size:1; signed:0;
    field:int common_pid;                                   offset:4;       size:4; signed:1;

    field:unsigned long call_site;                          offset:8;       size:8; signed:0;
    field:const void * ptr;                                 offset:16;      size:8; signed:0;
    field:size_t bytes_req;                                 offset:24;      size:8; signed:0;
    field:size_t bytes_alloc;                               offset:32;      size:8; signed:0;
    field:gfp_t gfp_flags;                                  offset:40;      size:4; signed:0;

まず、kmalloc を1回以上呼び出したカーネル内の関数ごとにリクエストされたバイト数の合計を表示するシンプルなテーブルを生成する hist トリガーを作成します：

# echo 'hist:key=call_site:val=bytes_req' > \
        /sys/kernel/debug/tracing/events/kmem/kmalloc/trigger

これは、tracing システムに kmalloc イベントの call_site フィールドをテーブルのキーとして使用する ‘hist’ トリガーを作成する指示です。つまり、各一意の call_site アドレスにテーブルにエントリが作成されるということです。‘val=bytes_req’ パラメータは、hist トリガーに、テーブル内の各一意のエントリ（call_site）に対して、その call_site がリクエストしたバイト数の累積合計を保持するように指示します。

出力は、トリガーで指定されたキーから始まり、トリガーで指定された値（複数可）が続く各行を表示します。出力の先頭には、トリガー情報が表示される行があり、これは ‘trigger’ ファイルを読み込むことで確認することもできます：

出力の最後には、実行全体の合計値を表示するいくつかの行があります。‘Hits’ フィールドは、イベントトリガーがヒットした総回数を示し、‘Entries’ フィールドはハッシュテーブルに使用されたエントリの総数を示し、‘Dropped’ フィールドは、実行中の使用エントリ数がテーブルに許可されている最大エントリ数を超えたためドロップされたヒット数を示します（通常は0ですが、これが0でない場合、テーブルのサイズを ‘size’ パラメータを使用して増やすことを検討するヒントになります）。

上記の出力で、トリガーに指定されていない「hitcount」という追加フィールドがあることに注意してください。また、トリガー情報の出力には「sort=hitcount」というパラメータが含まれていますが、トリガーに指定されていません。これは、すべてのトリガーが暗黙的に、特定のエントリに帰属するヒット数を「hitcount」としてカウントするためです。このhitcount情報は出力に明示的に表示され、ユーザーが指定していないソートパラメータの場合は、デフォルトのソートフィールドとして使用されます。

「hitcount」は、特定のフィールドを合計する必要がなく、主にヒット頻度に興味がある場合に、「values」パラメータの明示的な値の代わりに使用できます。

ヒストグラムトリガーをオフにするには、コマンド履歴で該当のトリガーを呼び出し、先頭に「!」を付けて再実行します。

# echo '!hist:key=call_site:val=bytes_req' > \
       /sys/kernel/debug/tracing/events/kmem/kmalloc/trigger

前記の例では、ヒストグラムトリガーを開始および停止する方法として、ヒストグラムトリガーコマンドにpauseとcontinueを追加する方法を示しました。ヒストグラムトリガーは、最初から:pauseを追加して一時停止状態で起動することも可能です。これにより、データの収集を開始する準備ができてからトリガーを開始し、それ以前に開始しないようにできます。例えば、トリガーを一時停止状態で起動し、その後一時停止を解除して測定したい操作を行った後、再度一時停止するなど、測定対象の操作を制御できます。

もちろん、このような手動での操作は困難でエラーが発生しやすいですが、条件に基づいてヒストグラムトリガーを自動的に開始および停止する方法もあります。その方法はenable_histとdisable_histトリガーを通じて実現可能です。

例えば、wgetを使用して適度なサイズのファイルをダウンロードする際、netif_receive_skbイベントに至る各コールパスのskb長に基づく相対的な重みを確認したいとします。

まず、netif_receive_skbイベントに初期状態で一時停止中のスタックトレーストリガーを設定します：

# echo 'hist:key=stacktrace:vals=len:pause' > \
       /sys/kernel/debug/tracing/events/net/netif_receive_skb/trigger

次に、sched_process_exec イベントに対して 'enable_hist' トリガーを設定し、'if filename==/usr/bin/wget' というフィルタを適用します。この新しいトリガーの効果は、'netif_receive_skb' に設定した 'hist' トリガーを 'unpause' するというものです。これは、'sched_process_exec' イベントが '/usr/bin/wget' というファイル名を持つ場合にのみ発生します。その際、すべての netif_receive_skb イベントがスタックトレースをキーにしたハッシュテーブルに集約されます:

# echo 'enable_hist:net:netif_receive_skb if filename==/usr/bin/wget' > \
       /sys/kernel/debug/tracing/events/sched/sched_process_exec/trigger

この集約は、netif_receive_skb が再び一時停止されるまで続きます。これは次の disable_hist イベントが sched_process_exit イベントに対して同様の設定を実行することで実現され、'comm==wget' というフィルタを使用します:

# echo 'disable_hist:net:netif_receive_skb if comm==wget' > \
       /sys/kernel/debug/tracing/events/sched/sched_process_exit/trigger

プロセスが終了し、disable_hist トリガーのフィルタで 'comm==wget' と一致する場合、netif_receive_skb の hist トリガーは無効になります。

2.2 イベント間histトリガー¶

イベント間histトリガーは、1つ以上の他のイベントからの値を組み合わせてそのデータを使用してヒストグラムを作成するhistトリガーです。イベント間ヒストグラムのデータは、さらに組み合わせたヒストグラムのソースとなるため、関連するヒストグラムの連鎖を提供し、一部のアプリケーションでは重要です。

このように使用できるイベント間量の最も重要な例は、2つのイベント間のタイムスタンプの差分であるレイテンシーです。レイテンシーは最も重要なイベント間量ですが、トレースイベントサブシステム全体で完全に一般的なサポートがあるため、どのイベントフィールドもイベント間量として使用できます。

他のヒストグラムからデータを統合して有用な連鎖を作成するヒストグラムの例は、「wakeupswitch latency（ wakeupswitch遅延）」ヒストグラムで、これは「wakeup latency（ wakeup遅延）」ヒストグラムと「switch latency（ switch遅延）」ヒストグラムを組み合わせたものです。

通常、ヒストグラムのトリガー仕様は、（複合的な）キーと1つ以上の数値から構成され、そのキーに関連する継続的に更新される合計値を含みます。この場合のヒストグラム仕様は、1つのイベントタイプに関連するトレースイベントフィールドを参照する個々のキーと値の仕様で構成されます。

インターフェースイベントヒストグラムトリガー拡張機能は、複数のイベントからフィールドを参照して複数イベントヒストグラム仕様に組み込むことを可能にします。この全体的な目標を支援するため、いくつかの機能拡張がヒストグラムトリガーサポートに追加されました。

  • インターフェースイベント量を計算するには、1つのイベントからの値を保存し、その後別のイベントから参照する必要があります。これにより、ヒストグラムの「変数」をサポートする機能の導入が必要になります。

  • インターフェースイベント量の計算と組み合わせには、変数に対して単純な式（加算や減算）を適用するためのある程度のサポートが必要です。

  • インターフェースイベント量を含むヒストグラムは、どちらのイベントにも論理的にヒストグラムではありません（したがって、どちらのイベントの「hist」ファイルにもヒストグラム出力が存在する意味はあまりありません）。このヒストグラムが複数のイベントの組み合わせに関連しているというアイデアに対応するため、合成イベントの作成を可能にする機能が追加されました。これらの合成イベントは他のイベントから派生したイベントですが、他のイベントと同様に完全なイベントであり、例えば前述の「組み合わせ」ヒストグラムを作成するために使用できます。

  • ヒストグラムエントリに関連する「アクション」を設定できます。これらは前述の合成イベントを生成するために使用できますが、最大遅延が発生した際にコンテキストを保存するなど他の用途にも利用できます。

  • トレースイベントには「timestamp」が関連付けられていませんが、ftraceリングバッファ内にイベントとともに暗黙のタイムスタンプが保存されています。このタイムスタンプは現在、「common_timestamp」という合成フィールドとして公開されており、他のイベントフィールドと同様にヒストグラムで使用できます。これは実際にトレースフォーマットに存在するフィールドではなく、合成された値ですが、実際のフィールドとして扱うことができます。デフォルトではナノ秒単位で表示され、common_timestampフィールドに「.usecs」を追加することでマイクロ秒単位に変更できます。

イベント間のタイムスタンプに関する注意点: common_timestampをヒストグラムで使用する場合、トレースバッファは自動的に絶対タイムスタンプと「グローバル」トレースクロックを使用するよう切り替えられます。これにより、CPU間で整合性のないクロックによる偽のタイムスタンプ差を防ぎます。この挙動は、「clock=XXX」ヒストグラムトリガー属性で他のトレースクロックを指定することで上書き可能です。XXXはtracing/trace_clock擬似ファイルに記載されているクロックのいずれかです。

これらの機能については次のセクションでより詳しく説明します。

2.2.1 ヒストグラム変数¶

変数は、一致するイベント間で値を保存および取得するために使用される名前付きの場所です。「一致するイベント」とは、特定のキーフィールドと一致するイベントを指します。変数がヒストグラムエントリーキーと一致する場合に保存されると、その後の一致するキーフィールドを持つイベントはその変数にアクセスできます。

変数の値は、その後のイベントで別の値が設定されるまで常に利用可能です。ただし、式で使用される変数は例外があり、式で一度使用されると自動的に「未設定」状態に戻り、再度使用するには再度設定する必要があります。これにより、計算で未初期化の変数が使用されることを防ぎ、また変数が一度しか使用されず、関連のない後のマッチングで再利用されることを防ぎます。

変数を保存する基本的な構文は、イベントフィールドに「=」で接続し、キーワードと一致しない一意の変数名を指定するだけです。

キーや値のいずれもこの方法で保存および取得できます。これにより、「next_pid」キーフィールドを持つヒストグラムエントリーに変数「ts0」が作成されます:

# echo 'hist:keys=next_pid:vals=$ts0:ts0=common_timestamp ... >> \
      event/trigger

ts0変数は、「next_pid」と同じpidを持つすべての後のイベントで参照可能です。

変数参照は、変数名の前に「$」記号を付けて形成されます。したがって、上記のts0変数は式において「$ts0」として参照されます。

「vals=」が使用されているため、上記のcommon_timestamp変数の値も通常のヒストグラム値のように合計されます（ただし、タイムスタンプに対しては意味がありません）。

以下に示すように、キーバリューも同様の方法で保存できます：

# echo 'hist:timer_pid=common_pid:key=timer_pid ...' >> event/trigger

変数がキーバリアブルでないか、「vals=」で前付けていない場合、関連するイベントフィールドは変数に保存されますが、値として合計されません：

# echo 'hist:keys=next_pid:ts1=common_timestamp ...' >> event/trigger

複数の変数を同時に割り当てることができます。以下は、ts0とbの両方が変数として作成され、common_timestampとfield1も追加で値として合計される例です：

# echo 'hist:keys=pid:vals=$ts0,$b:ts0=common_timestamp,b=field1 ...' >> \
      event/trigger

変数割り当ては、使用の前後に関係なく出現できます。以下に示すコマンドは上記のコマンドと同等の動作を行います：

# echo 'hist:keys=pid:ts0=common_timestamp,b=field1:vals=$ts0,$b ...' >> \
      event/trigger

「vals=」で束縛されていない変数は、コロンで区切ることで複数同時に割り当てられます。以下は、ヒストグラムに値を合計しない同じ内容です：

# echo 'hist:keys=pid:ts0=common_timestamp:b=field1 ...' >> event/trigger

上記のように設定された変数は、他のイベントにおける式で参照および使用できます。

例えば、以下のようにレイテンシーを計算できます：

# echo 'hist:keys=pid,prio:ts0=common_timestamp ...' >> event1/trigger
# echo 'hist:keys=next_pid:wakeup_lat=common_timestamp-$ts0 ...' >> event2/trigger

上記の最初の行では、イベントのタイムスタンプが変数ts0に保存されます。次の行では、ts0を2番目のイベントのタイムスタンプから引いてレイテンシーを計算し、それを別の変数「wakeup_lat」に割り当てます。以下のヒストグラムトリガーは、このwakeup_lat変数を使用して、別のイベントからの同じキーバリアブルと変数を用いて合計レイテンシーを計算します：

# echo 'hist:key=pid:wakeupswitch_lat=$wakeup_lat+$switchtime_lat ...' >> event3/trigger

2.2.2 シンセティックイベント¶

シンセティックイベントは、ヒストグラムトリガーの変数または1つ以上の他のイベントに関連するフィールドからユーザーが定義するイベントです。目的は、通常のイベントの既存の使い方に従って複数イベントにまたがるデータを表示するメカニズムを提供することです。

シンセティックイベントを定義するには、ユーザーが新しいイベント名と、1つ以上の変数およびその型（有効なフィールド型のいずれか）をセミコロンで区切って、tracing/synthetic_eventsファイルに記述します。

利用可能なタイプについてはsynth_field_size()を参照してください。

field_nameに[n]が含まれる場合、そのフィールドは静的配列とみなされます。

field_namesに[]（サブスクリプトなし）が含まれる場合、そのフィールドは動的配列とみなされ、イベントに必要なだけのスペースのみを確保します。

文字列フィールドは、静的記法を使用して指定できます：

char name[32];

または動的記法：

char name[];

どちらのサイズ制限も256です。

例えば、以下の例は「wakeup_latency」という名前の新しいイベントを作成し、lat、pid、prioという3つのフィールドを持たせます。それぞれのフィールドは、他のイベントの変数への参照です：

# echo 'wakeup_latency \
        u64 lat; \
        pid_t pid; \
        int prio' >> \
        /sys/kernel/debug/tracing/synthetic_events

tracing/synthetic_eventsファイルを読み込むことで、現在定義されているすべての合成イベントが一覧表示されます。この場合、上記で定義されたイベントが表示されます:

# cat /sys/kernel/debug/tracing/synthetic_events
  wakeup_latency u64 lat; pid_t pid; int prio

既に定義されている合成イベントは、その定義を示すコマンドの前に「!」を追加することで削除できます:

# echo '!wakeup_latency u64 lat pid_t pid int prio' >> \
  /sys/kernel/debug/tracing/synthetic_events

この時点では、イベントサブシステムに実際に「wakeup_latency」イベントがインスタンス化されていません。このイベントが生成されるには、「hist trigger action」をインスタンス化し、他のイベントで定義されたフィールドや変数にバインドする必要があります（以下の2.2.3節で「hist trigger」の「onmatch」アクションを使用してこれを実行する方法を説明しています）。この作業が完了すると、「wakeup_latency」の合成イベントインスタンスが作成されます。

新しい合成イベントに対してヒストグラムを定義できます:

# echo 'hist:keys=pid,prio,lat.log2:sort=pid,lat' >> \
      /sys/kernel/debug/tracing/events/synthetic/wakeup_latency/trigger

新しいイベントはtracing/events/synthetic/ディレクトリ下に作成され、他のイベントと同様の見た目と動作になります:

# ls /sys/kernel/debug/tracing/events/synthetic/wakeup_latency
      enable  filter  format  hist  id  trigger

ヒストグラムが有効になったイベントでは、イベントの「hist」ファイルを読み込むことで出力を表示できます。

2.2.3 ヒストグラムトリガー「ハンドラ」および「アクション」¶

ヒストグラムトリガーの「アクション」は、ヒストグラムのエントリが追加または更新されるたびに実行される関数です（ほとんどの場合、条件付きで実行されます）。

ヒストグラムのエントリが追加または更新されるとき、ヒストグラムトリガーの「ハンドラ」が、対応するアクションが実際に実行されるかどうかを決定します。

ヒストグラムトリガーのハンドラとアクションは、一般的な形式でペアになります:

<ハンドラ>.<アクション>

イベントに対してハンドラ.アクションペアを指定するには、ヒストグラムトリガーの指定内でコロンの間にそのハンドラ.アクションペアを指定します。

理論上は、どのハンドラもどのアクションとも組み合わせられます。しかし、実際にはすべてのハンドラ.アクション組み合わせがサポートされているわけではありません。サポートされていないハンドラ.アクション組み合わせの場合、ヒストグラムトリガーは-EINVALで失敗します。

明示的に指定しない場合のデフォルトの「ハンドラ.アクション」は、以前と同様に、エントリに関連する値のセットを更新することです。ただし、一部のアプリケーションでは、この時点で追加のアクションを実行したい場合があります。たとえば、別のイベントを生成するか、最大値を比較して保存するなどです。

サポートされているハンドラとアクションの一覧は以下に示され、それぞれの詳細については、以下の段落で一般的なハンドラ.アクション組み合わせの説明の中で詳しく説明します。

利用可能なハンドラは:

  • onmatch(matching.event) - 任意の追加または更新時にアクションを実行

  • onmax(var) - varが現在の最大値を超えたときにアクションを実行

  • onchange(var) - varが変化したときにアクションを実行

利用可能なアクションは:

  • trace(<合成イベント名>,パラメータリスト) - 合成イベントを生成

  • save(field,…) - 現在のイベントフィールドを保存します

  • snapshot() - トレースバッファのスナップショットを取得します

以下に、よく使用されるハンドラ・アクションのペアが用意されています:

  • onmatch(matching.event).trace(<合成イベント名>,パラメータリスト)

    「onmatch(matching.event).trace(<合成イベント名>,パラメータリスト)」のヒストグラムトリガー アクションは、イベントが一致した際にヒストグラムエントリが追加または更新されるたびに呼び出されます。これにより、パラメータリストに指定された値を持つ指定された合成イベントが生成されます。結果として、呼び出しイベントが発生した時点での変数に含まれる値を持つ合成イベントが生成されます。たとえば、合成イベント名が「wakeup_latency」の場合、onmatch(event).trace(wakeup_latency,arg1,arg2)を実行することでwakeup_latencyイベントが生成されます。

    合成イベントの生成には、同等の代替形式も利用可能です。この形式では、合成イベント名を関数名のように扱います。たとえば、「wakeup_latency」の合成イベント名を使用して、関数呼び出しのようにイベントを生成します。この際、イベントフィールドの値を引数として渡します：onmatch(event).wakeup_latency(arg1,arg2)。この形式の構文は以下の通りです:

    onmatch(matching.event).<synthetic_event_name>(パラメータリスト)

    いずれの場合も、「パラメータリスト」には、1つ以上のパラメータが含まれます。これらは、「matching.event」またはターゲットイベントで定義された変数またはフィールドです。パラメータリストに指定された変数またはフィールドは、完全修飾または未修飾のいずれかです。変数が未修飾で指定されている場合、2つのイベント間で一意である必要があります。フィールド名をパラメータとして使用する場合、ターゲットイベントを参照する場合は未修飾でよいですが、マッチングイベントを参照する場合は完全修飾でなければなりません。完全修飾名は「system.event_name.$var_name」または「system.event_name.field」の形式です。

    「matching.event」の指定は、onmatch()機能でターゲットイベントと一致するイベントの完全修飾イベント名を表します。ヒストグラムキーの比較によってイベントが一致するかどうかを判定します。複数のヒストグラムキーが使用される場合、指定された順序ですべて一致する必要があります。

    最後に、「パラメータリスト」に含まれる変数/フィールドの数と型は、生成される合成イベントのフィールドの数と型と一致する必要があります。

    例として、以下は単純な合成イベントを定義し、sched_wakeup_new イベントで定義された変数を合成イベントを呼び出す際のパラメータとして使用する例です。ここでは合成イベントを定義します:

    # echo 'wakeup_new_test pid_t pid' >> \
       /sys/kernel/debug/tracing/synthetic_events

# cat /sys/kernel/debug/tracing/synthetic_events
      wakeup_new_test pid_t pid

    次の hist トリガーは、欠けている testpid 変数を定義し、onmatch() アクションを指定して、sched_wakeup_new イベントが発生するたびに wakeup_new_test という合成イベントを生成します。これは 'if comm == "cyclictest"' フィルタにより、実行ファイルが cyclictest の場合にのみ発生します:

    # echo 'hist:keys=$testpid:testpid=pid:onmatch(sched.sched_wakeup_new).\
        wakeup_new_test($testpid) if comm=="cyclictest"' >> \
        /sys/kernel/debug/tracing/events/sched/sched_wakeup_new/trigger

    あるいは、'trace' キーワード構文を使用して以下のように記述することもできます:

    # echo ‘hist:keys=$testpid:testpid=pid:onmatch(sched.sched_wakeup_new).

    trace(wakeup_new_test,$testpid) if comm=="cyclic, test"’ >> /sys/kernel/debug/tracing/events/sched/sched_wakeup_new/trigger

    これらのイベントを基にヒストグラムを作成・表示するには、通常通り tracing/events/synthetic ディレクトリにあるフィールドと新しい合成イベントを使用するだけで済みます:

    # echo 'hist:keys=pid:sort=pid' >> \
       /sys/kernel/debug/tracing/events/synthetic/wakeup_new_test/trigger

    cyclictest を実行すると、wakeup_new イベントが wakeup_new_test の合成イベントを生成し、その結果、wakeup_new_test イベントの hist ファイルにヒストグラム出力が表示されるはずです:

    # cat /sys/kernel/debug/tracing/events/synthetic/wakeup_new_test/hist

    より一般的な用途では、2つのイベントを使用してレイテンシーを計算します。次の例では、ヒストグラムトリガーのセットを使用して 'wakeup_latency' ヒストグラムを生成しています。

    まず、'wakeup_latency' の合成イベントを定義します:

    # echo 'wakeup_latency u64 lat; pid_t pid; int prio' >> \
        /sys/kernel/debug/tracing/synthetic_events

    次に、cyclictest スレッドで sched_waking イベントが発生したときに、'ts0' 変数にタイムスタンプを保存します:

    # echo 'hist:keys=$saved_pid:saved_pid=pid:ts0=common_timestamp.usecs \
        if comm=="cyclictest"' >> \
        /sys/kernel/debug/tracing/events/sched/sched_waking/trigger

    その後、対応するスレッドが sched_switch イベントによりCPUにスケジューリングされる（saved_pid が next_pid と一致する）ときに、レイテンシーを計算し、その結果を別の変数とイベントフィールドとともに使用して wakeup_latency の合成イベントを生成します:

    # echo 'hist:keys=next_pid:wakeup_lat=common_timestamp.usecs-$ts0:\
        onmatch(sched.sched_waking).wakeup_latency($wakeup_lat,\
                $saved_pid,next_prio) if next_comm=="cyclictest"' >> \
        /sys/kernel/debug/tracing/events/sched/sched_switch/trigger

    さらに、wakeup_latency の合成イベントにヒストグラムを作成して、生成された合成イベントデータを集約する必要があります:

    # echo 'hist:keys=pid,prio,lat:sort=pid,lat' >> \
        /sys/kernel/debug/tracing/events/synthetic/wakeup_latency/trigger

    最後に、cyclictest を実行して実際にイベントを生成した後、wakeup_latency の合成イベントの hist ファイルを確認することで出力を確認できます:

    # cat /sys/kernel/debug/tracing/events/synthetic/wakeup_latency/hist

  • onmax(var).save(field,.. .)

    ‘onmax(var).save(field,…)’ は、ヒストグラムエントリに関連付けられた 'var' の値が、その変数内の現在の最大値を上回るたびに呼び出される hist トリガーのアクションです。

    結果として、onmax.save()のパラメータとして指定されたトレースイベントのフィールドが、'var'がそのヒストグラムのトリガー項目における現在の最大値を超えた場合に保存されます。これにより、新しい最大値を示したイベントのコンテキストが後で参照できるようになります。ヒストグラムが表示される際には、保存された値を表示する追加のフィールドが印刷されます。

    例として、以下はsched_wakingとsched_switchの2つのヒストグラムのトリガーを定義しており、pidをキーとしています。sched_wakingが発生するたびに、現在のpidに対応する項目にタイムスタンプが保存され、スケジューラがそのpidに戻るときにはタイムスタンプの差分が計算されます。結果として得られたレイテンシーがwakeup_latに保存され、現在の最大レイテンシーを超えた場合、save()フィールドで指定された値が記録されます：

    # echo 'hist:keys=pid:ts0=common_timestamp.usecs \
        if comm=="cyclictest"' >> \
        /sys/kernel/debug/tracing/events/sched/sched_waking/trigger

# echo 'hist:keys=next_pid:\
        wakeup_lat=common_timestamp.usecs-$ts0:\
        onmax($wakeup_lat).save(next_comm,prev_pid,prev_prio,prev_comm) \
        if next_comm=="cyclictest"' >> \
        /sys/kernel/debug/tracing/events/sched/sched_switch/trigger

    ヒストグラムが表示されるとき、最大値とその最大値に対応する保存された値が他のフィールドとともに表示されます：

    # cat /sys/kernel/debug/tracing/events/sched/sched_switch/hist
  { next_pid:       2255 } hitcount:        239
    common_timestamp-ts0:          0
    max:         27
    next_comm: cyclictest
    prev_pid:          0  prev_prio:        120  prev_comm: swapper/1

  { next_pid:       2256 } hitcount:       2355
    common_timestamp-ts0: 0
    max:         49  next_comm: cyclictest
    prev_pid:          0  prev_prio:        120  prev_comm: swapper/0

  Totals:
      Hits: 12970
      Entries: 2
      Dropped: 0

  • onmax(var).snapshot()

    onmax(var).snapshot()のヒストグラムのトリガー動作は、ヒストグラム項目に関連付けられた'var'の値がその変数内の現在の最大値を超えたときに呼び出されます。

    結果として、'var'がどのヒストグラムのトリガー項目の現在の最大値も超えた場合、トレースバッファのグローバルなスナップショットがtracing/snapshotファイルに保存されます。

    注意点として、この場合の最大値は現在のトレースインスタンスにおけるグローバルな最大値であり、ヒストグラムのすべてのバケットにおける最大値です。最大値を引き起こした特定のトレースイベントのキーと、そのグローバルな最大値自体が表示され、スナップショットが取得された旨とその場所がメッセージとして表示されます。ユーザーは表示されたキー情報をもとに、ヒストグラム内の対応するバケットを特定してさらに詳細な情報を得ることができます。

    例として、以下はsched_wakingとsched_switchの2つのヒストグラムのトリガーを定義しており、pidをキーとしています。sched_wakingイベントが発生するたびに、タイムスタンプが現在のpidに対応する項目に保存され、スケジューラがそのpidに戻るときにはタイムスタンプの差分が計算されます。結果として得られたレイテンシーがwakeup_latに保存され、現在の最大レイテンシーを超えた場合、スナップショットが取得されます。設定の一環として、すべてのスケジューライベントも有効化され、これらがスナップショットに表示されるイベントです：

    # echo 1 > /sys/kernel/debug/tracing/events/sched/enable

    # echo ‘hist:keys=pid:ts0=common_timestamp.usecs

    if comm=="cyclictest"' >> /sys/kernel/debug/tracing/events/sched/sched_waking/trigger

    # echo 'hist:keys=next_pid:wakeup_lat=common_timestamp.usecs-$ts0:

    onmax($wakeup_lat).save(next_prio,next_comm,prev_pid,prev_prio, prev_comm):onmax($wakeup_lat).snapshot() if next_comm=="cyclictest"' >> /sys/kernel/debug/tracing/events/sched/sched_switch/trigger

    ヒストグラムが表示されるとき、各バケットごとに最大値とその最大値に対応する保存された値が、他のフィールドとともに表示されます。

    スナップショットが取得された場合、その旨のメッセージと、グローバル最大値をトリガーした値とイベントも表示されます。

    # cat /sys/kernel/debug/tracing/events/sched/sched_switch/hist
    { next_pid: 2101 } ヒット数: 200

  • onchange(var).save(field,.. .)

    「onchange(var).save(field,…)」ヒストグラムトリガー操作は、ヒストグラムエントリに関連する「var」の値が変化するたびに実行されます。

    結果として、ヒストグラムトリガーのエントリで「var」が変化した場合、指定されたonchange.save()パラメータのトレースイベントフィールドが保存されます。これにより、値を変更したイベントのコンテキストが後で参照できるようになります。ヒストグラムが表示されるとき、保存された値を表示する追加フィールドが印刷されます。

  • onchange(var).snapshot()

3. ユーザースペースでのトリガー作成¶

/sys/kernel/tracing/trace_markerへの書き込みはftraceリングバッファに書き込みます。これは、/sys/kernel/tracing/events/ftrace/print/にあるトリガーファイルに書き込むことでイベントとしての動作も行えます。

cyclictestを、睡眠前にtrace_markerファイルに書き込み、目覚めた後に再度書き込むように変更することで、以下のような感じになります：

static void traceputs(char *str)
{
      /* tracemark_fd is the trace_marker file descriptor */
      if (tracemark_fd < 0)
              return;
      /* write the tracemark message */
      write(tracemark_fd, str, strlen(str));
}

その後、以下のようなものを追加します:

traceputs("start");
clock_nanosleep(...);
traceputs("end");

これからヒストグラムを作成できます:

# cd /sys/kernel/tracing
# echo 'latency u64 lat' > synthetic_events
# echo 'hist:keys=common_pid:ts0=common_timestamp.usecs if buf == "start"' > events/ftrace/print/trigger
# echo 'hist:keys=common_pid:lat=common_timestamp.usecs-$ts0:onmatch(ftrace.print).latency($lat) if buf == "end"' >> events/ftrace/print/trigger
# echo 'hist:keys=lat,common_pid:sort=lat' > events/synthetic/latency/trigger

上記では「latency（レイテンシー）」という合成イベントを生成し、trace_markerに対して2つのヒストグラムを作成しました。1つはtrace_markerファイルに「start（スタート）」が書き込まれたときにトリガーされ、もう1つは「end（エンド）」が書き込まれたときにトリガーされます。pidが一致する場合、計算されたレイテンシーをパラメータとして「latency」の合成イベントを呼び出します。最後に、この合成イベントにヒストグラムを追加して、計算されたレイテンシーとpidを記録します。

cyclictestを以下のように実行します:

# ./cyclictest -p80 -d0 -i250 -n -a -t --tracemark -b 1000

-p80  : run threads at priority 80
-d0   : have all threads run at the same interval
-i250 : start the interval at 250 microseconds (all threads will do this)
-n    : sleep with nanosleep
-a    : affine all threads to a separate CPU
-t    : one thread per available CPU
--tracemark : enable trace mark writing
-b 1000 : stop if any latency is greater than 1000 microseconds

注意: -b 1000は-tracemarkを有効にするためのオプションです。

# cd /sys/kernel/tracing
# echo 'latency u64 lat' > synthetic_events
# echo 'hist:keys=pid:ts0=common_timestamp.usecs' > events/sched/sched_waking/trigger

# echo 'hist:keys=lat,common_pid:sort=lat' > events/synthetic/latency/trigger

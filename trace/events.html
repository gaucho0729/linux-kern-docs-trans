著者

1. はじめに¶

トレースポイント（参照 Linuxカーネルトレースポイントの利用) は、カスタムのカーネルモジュールを作成することなく、イベントトレースインフラストラクチャを使用してプローブ関数を登録できます。

すべてのトレースポイントがイベントトレースシステムでトレースできるわけではありません。カーネル開発者は、トレース情報がトレースバッファに保存される方法や、トレース情報がどのように出力されるかを定義するコードスニペットを提供する必要があります。

2. イベントトレースの使用方法¶

2.1 'set_event' インターフェース経由¶

トレース可能なイベント一覧は、/sys/kernel/debug/tracing/available_events ファイルにあります。

特定のイベント（例：'sched_wakeup'）を有効にするには、それを /sys/kernel/debug/tracing/set_event にエコーします。例えば：

# echo sched_wakeup >> /sys/kernel/debug/tracing/set_event

注意

>> は必要です。そうでないと、すべてのイベントが最初に無効になります。

イベントを無効にするには、set_event ファイルにエクスクラメーションポイントを先頭にしたイベント名をエコーします：

# echo '!sched_wakeup' >> /sys/kernel/debug/tracing/set_event

すべてのイベントを無効にするには、set_event ファイルに空行をエコーします：

# echo > /sys/kernel/debug/tracing/set_event

すべてのイベントを有効にするには、 *:* または *: を set_event ファイルにエコーします：

# echo *:* > /sys/kernel/debug/tracing/set_event

イベントは ext4、irq、sched など、サブシステムごとに分類されており、完全なイベント名は <サブシステム>:<イベント> の形式です。サブシステム名はオプションですが、available_events ファイルに表示されます。サブシステム内のすべてのイベントは、次の構文で指定できます： <subsystem>:*; 例えば、すべての irq イベントを有効にするには、次のコマンドを使用できます：

# echo 'irq:*' > /sys/kernel/debug/tracing/set_event

2.2 'enable' トグル経由¶

イベント一覧は、/sys/kernel/debug/tracing/events/ ディレクトリ階層にも表示されています。

イベント 'sched_wakeup' を有効にするには：

# echo 1 > /sys/kernel/debug/tracing/events/sched/sched_wakeup/enable

無効にするには:

# echo 0 > /sys/kernel/debug/tracing/events/sched/sched_wakeup/enable

sched サブシステム内のすべてのイベントを有効にするには：

# echo 1 > /sys/kernel/debug/tracing/events/sched/enable

すべてのイベントを有効にするには：

# echo 1 > /sys/kernel/debug/tracing/events/enable

これらの enable ファイルを読み込む際には、4つの結果があります：

  • 0 - このファイルが影響を与えるすべてのイベントが無効

  • 1 - このファイルが影響を与えるすべてのイベントが有効

  • X - 有効と無効のイベントが混在している

  • ? - このファイルはどのイベントにも影響を与えていない

2.3 ブートオプション¶

早期ブート時のデバッグを容易にするために、ブートオプションを使用します：

trace_event=[event-list]

event-list は、カンマで区切られたイベント一覧です。イベント形式については、セクション 2.1 を参照してください。

4. イベント形式¶

各トレースイベントには、イベントのログに記録された各フィールドの説明を含む 'format' ファイルが関連付けられています。この情報はバイナリトレースストリームを解析するのに使用でき、イベントフィルタで使用可能なフィールド名もここにあります（セクション 5 を参照）

テキストモードでイベントを印刷する際に使用されるフォーマット文字列も表示されます。これは、プロファイリングに使用されるイベント名とIDも含まれます。

すべてのイベントには、 common 関連するフィールドが含まれており、これらは「prefix with」で始まるフィールドです； common_. 他のフィールドはイベントによって異なり、それぞれのイベントのTRACE_EVENT定義で定義されたフィールドと対応します。

フォーマット内の各フィールドは次の形式を持ちます：

field:field-type field-name; offset:N; size:N;

ここでoffsetはトレースレコード内のフィールドのオフセットで、sizeはデータ項目のサイズ（バイト単位）です。

たとえば、ここに'sched_wakeup'イベントの表示情報が示されています：

# cat /sys/kernel/debug/tracing/events/sched/sched_wakeup/format

name: sched_wakeup
ID: 60
format:
        field:unsigned short common_type;       offset:0;       size:2;
        field:unsigned char common_flags;       offset:2;       size:1;
        field:unsigned char common_preempt_count;       offset:3;       size:1;
        field:int common_pid;   offset:4;       size:4;
        field:int common_tgid;  offset:8;       size:4;

        field:char comm[TASK_COMM_LEN]; offset:12;      size:16;
        field:pid_t pid;        offset:28;      size:4;
        field:int prio; offset:32;      size:4;
        field:int success;      offset:36;      size:4;
        field:int cpu;  offset:40;      size:4;

print fmt: "task %s:%d [%d] success=%d [%03d]", REC->comm, REC->pid,
           REC->prio, REC->success, REC->cpu

このイベントには10のフィールドがあり、最初の5つは共通フィールドで、残りの5つはイベント固有です。このイベントのすべてのフィールドは数値ですが、「comm」は文字列であり、イベントフィルタリングにおいて重要な区別です。

5. イベントフィルタリング¶

トレースイベントは、論理演算子「&&」および「||」を用いて、イベントにbool型の「フィルタ表現」を関連付けることでカーネル内でフィルタリングできます。イベントがトレースバッファにログ出力される直後に、そのイベントタイプに関連付けられたフィルタ表現がフィールド値と比較されます。フィルタ表現と一致するイベントはトレース出力に表示され、一致しないイベントは破棄されます。フィルタが設定されていないイベントはすべて一致するため、デフォルトではイベントにフィルタが設定されていない場合に適用されます。

5.1 表現構文¶

フィルタ表現は、論理演算子「&&」および「||」を用いて複数の「述語」から構成され、述語はログされたイベント内のフィールド値と定数値を比較し、フィールド値が一致した場合に1、一致しなかった場合に0を返す単純な文です：

field-name relational-operator value

括弧は任意の論理グループを提供するために使用でき、ダブルクォーテーションはシェルが演算子をメタキャラクタとして解釈しないようにします。

フィルタで使用可能なフィールド名は、トレースイベントの「format」ファイルに記載されています（セクション4を参照）。

比較演算子はテストされるフィールドのタイプに依存します：

数値フィールドに使用可能な演算子は：

==, !=, <, <=, >, >=, &

文字列フィールドに使用可能な演算子は：

==, !=, ~

ワイルドカード（~）は、*、?、および文字クラス（[）をサポートします。たとえば：

prev_comm ~ "*sh"
prev_comm ~ "sh*"
prev_comm ~ "*sh*"
prev_comm ~ "ba*sh"

フィールドがユーザー空間へのポインタ（例：sys_enter_openatからの「filename」）である場合、フィールド名に「.ustring」を追加する必要があります：

filename.ustring ~ "password"

カーネルがポインタが指すユーザー空間のメモリを取得する方法を知る必要があります。

5.2 フィルタの設定¶

個々のイベント用のフィルタは、指定されたイベントの「filter」ファイルにフィルタ表現を記述することで設定されます。

例:

# cd /sys/kernel/debug/tracing/events/sched/sched_wakeup
# echo "common_preempt_count > 4" > filter

やや複雑な例:

# cd /sys/kernel/debug/tracing/events/signal/signal_generate
# echo "((sig >= 10 && sig < 15) || sig == 17) && comm != bash" > filter

表現にエラーがある場合、設定時に「Invalid argument（無効な引数）」エラーが発生し、エラーの発生した文字列とエラーメッセージを確認できます（例：

# cd /sys/kernel/debug/tracing/events/signal/signal_generate
# echo "((sig >= 10 && sig < 15) || dsig == 17) && comm != bash" > filter
-bash: echo: write error: Invalid argument
# cat filter
((sig >= 10 && sig < 15) || dsig == 17) && comm != bash
^
parse_error: Field not found

現在、エラーのカーソル（^）は常にフィルタ文字列の先頭に表示されるため、より正確な位置情報がなくてもエラーメッセージは依然として役立ちます。

5.2.1 フィルタの制限¶

文字列ポインタにフィルタを設定した場合 (char *) リングバッファにない文字列を指している場合、安全性のため最大1024バイトのコンテンツを一時バッファにコピーして比較を行います。メモリのコピーに失敗した場合（ポインタがアクセスすべきでないメモリを指している場合）、文字列比較は一致とみなされません。

5.3 フィルタのクリア¶

イベントのフィルタをクリアするには、イベントの「filter」ファイルに「0」を書き込みます。

サブシステム内のすべてのイベントのフィルタをクリアするには、サブシステムの「filter」ファイルに「0」を書き込みます。

5.3 サブシステムフィルタ¶

便利なため、サブシステム内のすべてのイベントのフィルタをグループで設定またはクリアできます。ただし、サブシステムフィルタで指定されたフィールドがイベントのフィルタに存在しない場合、または他の理由でフィルタを適用できない場合、そのイベントのフィルタは以前の設定を維持します。これにより、ユーザーが想定しているフィルタが有効であると誤解する可能性のある混在したフィルタが発生する可能性があります。すべてのイベントに確実に適用されるのは、共通フィールドを参照するフィルタに限られます。

以下のサブシステムフィルタの例は、上記のポイントを示しています:

schedサブシステム内のすべてのイベントのフィルタをクリアするには:

# cd /sys/kernel/debug/tracing/events/sched
# echo 0 > filter
# cat sched_switch/filter
none
# cat sched_wakeup/filter
none

schedサブシステム内のすべてのイベントに共通フィールドのみを用いてフィルタを設定（すべてのイベントが同じフィルタを持つ）:

# cd /sys/kernel/debug/tracing/events/sched
# echo common_pid == 0 > filter
# cat sched_switch/filter
common_pid == 0
# cat sched_wakeup/filter
common_pid == 0

schedサブシステム内のすべてのイベントに非共通フィールドを用いてフィルタを設定を試みる（prev_pidフィールドを持つイベント以外は以前のフィルタを維持）:

# cd /sys/kernel/debug/tracing/events/sched
# echo prev_pid == 0 > filter
# cat sched_switch/filter
prev_pid == 0
# cat sched_wakeup/filter
common_pid == 0

5.4 PIDフィルタ¶

上位イベントディレクトリと同じディレクトリにあるset_event_pidファイルに記述されたPIDを持つタスク以外のすべてのイベントをフィルタリングします。

# cd /sys/kernel/debug/tracing
# echo $$ > set_event_pid
# echo 1 > events/enable

現在のタスクのみをトレースします。

既に含まれているPIDを失うことなく、追加のPIDを追加するには、‘>>’を使用してください。

# echo 123 244 1 >> set_event_pid

6. イベントトリガー¶

トレースイベントは、条件付きでトリガー‘コマンド’を呼び出すことができます。このコマンドはさまざまな形式を取り得、詳細は以下に記載しています。例えば、他のトレースイベントの有効化または無効化、またはトレースイベントがヒットした際にスタックトレースを呼び出すなどです。トレースイベントにトリガーがアタッチされている場合、そのイベントが呼び出されるたびに、それに紐付けられたトリガー コマンドのセットが実行されます。任意のトリガーには、セクション5（イベントフィルタ）で説明した形式のイベントフィルタが関連付けられることも可能です。コマンドは、呼び出されるイベントが関連付けられたフィルタを通過した場合にのみ実行されます。トリガーにフィルタが関連付けされていない場合、常に通過します。

トリガー式を指定することで、特定のイベントにトリガーを追加または削除します。これは、該当イベントの‘trigger’ファイルに記述します。

イベントに関連付けられるトリガーの数は、個々のコマンドがその点で課す制限に従って、任意の数です。

イベントトリガーは「ソフト」モード上に実装されています。つまり、トレースイベントに1つ以上のトリガーが関連付けられている場合、そのイベントは実際に有効になっていなくても、ソフトモードで無効にされている状態で起動されます。つまり、トレースポイントは呼び出されるが、トレースされません（ただし、実際に有効になっている場合は除きます）。このスキームにより、有効になっていないイベントでもトリガーを呼び出すことが可能となり、現在のイベントフィルタ実装を条件付きでトリガー呼び出しに使用できるようになります。

イベントトリガーの構文は、set_ftrace_filter ‘ftrace フィルタ コマンド’（参照：‘フィルタ コマンド’セクション）の構文に概ね基づいています ftrace - 関数トレーサー)。ただし、主な違いがあり、現在の実装はこの構文と関連付けられていないため、両者を一般化して比較しないように注意してください。

注意

trace_marker（参照： ftrace - 関数トレーサー)への記述により、/sys/kernel/tracing/events/ftrace/print/trigger に記述されたトリガーを有効化することも可能です。

6.1 表現構文¶

トリガーは、コマンドを‘trigger’ファイルにエコーすることで追加します：

# echo 'command[:count] [if filter]' > trigger

トリガーは、コマンドの先頭に‘!’を付けて同じコマンドを‘trigger’ファイルにエコーすることで削除します：

# echo '!command[:count] [if filter]' > trigger

削除時のマッチングコマンドでは[if filter]部分は使用されません。したがって、‘!’コマンドでその部分を省略しても、[if filter]を含む場合と同じ結果になります。

フィルタ構文は、上記の‘イベントフィルタ’セクションで説明したとおりです。

使いやすさのため、トリガー ファイルに「>」で書き込むと現在は単一のトリガーを追加または削除するだけで、明示的な「>>」サポートはありません（「>」は実際には「>>」のように動作します）また、すべてのトリガーを削除する truncate サポートもありません（各トリガーを削除するには「!」を個別に使用する必要があります）。

6.2 サポートされているトリガー コマンド¶

サポートされているコマンドは以下の通りです：

  • enable_event/disable_event

    これらのコマンドは、トリガーイベントが発生するたびに、他のトレースイベントを有効または無効にします。これらのコマンドを登録すると、他のトレースイベントがアクティブになりますが、「ソフト」モードで無効にされます。つまり、トレースポイントは呼び出されますが、トレースされません。イベントトレースポイントは、トリガーが有効な限りこのモードのままです。

    例えば、以下のトリガーは、read システムコールが呼ばれたときに kmalloc イベントをトレースし、最後の :1 はこの有効化が一度だけ行われることを指定します：

    # echo 'enable_event:kmem:kmalloc:1' > \
    /sys/kernel/debug/tracing/events/syscalls/sys_enter_read/trigger

    以下のトリガーは、read システムコールが終了するたびに kmalloc イベントのトレースを停止します。この無効化はすべての read システムコール終了時に実行されます：

    # echo 'disable_event:kmem:kmalloc' > \
    /sys/kernel/debug/tracing/events/syscalls/sys_exit_read/trigger

    フォーマットは以下の通りです:

    enable_event:<system>:<event>[:count]
disable_event:<system>:<event>[:count]

    上記のコマンドを削除するには：

    # echo '!enable_event:kmem:kmalloc:1' > \
    /sys/kernel/debug/tracing/events/syscalls/sys_enter_read/trigger

# echo '!disable_event:kmem:kmalloc' > \
    /sys/kernel/debug/tracing/events/syscalls/sys_exit_read/trigger

    トリガーイベントごとに任意の数の enable/disable_event トリガーが存在できますが、トリガーされたイベントごとに1つのみトリガーが存在できます。たとえば、sys_enter_read は kmem:kmalloc と sched:sched_switch の両方を有効にするトリガーを持つことができますが、kmem:kmalloc と kmem:kmalloc:1 または「kmem:kmalloc if bytes_req == 256」および「kmem:kmalloc if bytes_alloc == 25、6」のような複数の kmem:kmalloc 版は存在できません（これらは kmem:kmalloc の1つのフィルタで統合可能ですが）。

  • stacktrace

    このコマンドは、トリガーイベントが発生するたびにトレースバッファにスタックトレースを出力します。

    例えば、以下のトリガーは kmalloc トレースポイントが呼ばれるたびにスタックトレースを出力します：

    # echo 'stacktrace' > \
      /sys/kernel/debug/tracing/events/kmem/kmalloc/trigger

    以下のトリガーは、kmalloc 要求がサイズ >= 64K で発生するたびに最初の5回だけスタックトレースを出力します：

    # echo 'stacktrace:5 if bytes_req >= 65536' > \
      /sys/kernel/debug/tracing/events/kmem/kmalloc/trigger

    フォーマットは以下の通りです:

    stacktrace[:count]

    上記のコマンドを削除するには：

    # echo '!stacktrace' > \
      /sys/kernel/debug/tracing/events/kmem/kmalloc/trigger

# echo '!stacktrace:5 if bytes_req >= 65536' > \
      /sys/kernel/debug/tracing/events/kmem/kmalloc/trigger

    後者はフィルタを省略して以下のようにより簡単に削除できます：

    # echo '!stacktrace:5' > \
      /sys/kernel/debug/tracing/events/kmem/kmalloc/trigger

    トリガーイベントごとにスタックトレースのトリガーは1つだけ存在できます。

  • スナップショット

    このコマンドは、トリガーイベントが発生するたびにスナップショットをトリガーします。

    以下のコマンドは、ブロック要求キューが深さ > 1 でアンプルグされたたびにスナップショットを生成します。トレースしているイベントや関数が存在する場合、スナップショットトレースバッファはトリガーイベント発生時にそれらのイベントをキャプチャします：

    # echo 'snapshot if nr_rq > 1' > \
      /sys/kernel/debug/tracing/events/block/block_unplug/trigger

    1回だけスナップショットを撮るには：

    # echo 'snapshot:1 if nr_rq > 1' > \
      /sys/kernel/debug/tracing/events/block/block_unplug/trigger

    上記のコマンドを削除するには：

    # echo '!snapshot if nr_rq > 1' > \
      /sys/kernel/debug/tracing/events/block/block_unplug/trigger

# echo '!snapshot:1 if nr_rq > 1' > \
      /sys/kernel/debug/tracing/events/block/block_unplug/trigger

    トリガーイベントごとにスナップショットのトリガーは1つだけ存在できます。

  • traceon/traceoff

    これらのコマンドは、指定されたイベントが発生したときにトレーシングをオン/オフに切り替えます。パラメータはトレーシングシステムがオン/オフになる回数を決定します。指定されていない場合は、制限はありません。

    次のコマンドは、ブロックリクエストキューが深さ > 1 の状態で解除された最初のタイミングでトレーシングをオフにします。トレースバッファを確認して、トリガーイベントに至るまでのイベントの順序を確認できます。

    # echo 'traceoff:1 if nr_rq > 1' > \
      /sys/kernel/debug/tracing/events/block/block_unplug/trigger

    nr_rq > 1 のときにトレーシングを常に無効にするには:

    # echo 'traceoff if nr_rq > 1' > \
      /sys/kernel/debug/tracing/events/block/block_unplug/trigger

    上記のコマンドを削除するには：

    # echo '!traceoff:1 if nr_rq > 1' > \
      /sys/kernel/debug/tracing/events/block/block_unplug/trigger

# echo '!traceoff if nr_rq > 1' > \
      /sys/kernel/debug/tracing/events/block/block_unplug/trigger

    各トリガーイベントごとにtraceonまたはtraceoffのトリガーは1つしか存在できません。

  • hist

    このコマンドは、イベントのヒットをハッシュテーブルに集約し、1つまたは複数のトレースイベント形式フィールド（またはスタックトレース）と、1つまたは複数のトレースイベント形式フィールドおよび/またはイベントカウント（ヒットカウント）から導出されたランニングトータルに基づいてキー付けします。

    参照 イベントヒストグラム 詳細情報と例については

7. インカーネルトレースイベントAPI¶

ほとんどの場合、トレースイベントのコマンドラインインターフェースは十分ですが、アプリケーションが複雑な関係を表現する必要がある場合や、複数のコマンドを組み合わせる作業が煩雑になる場合があります。たとえば、スケジューラ内で不正なカーネル状態が発生したときにインカーネルのステートマシンを維持するアプリケーションが、トレースストリームを「聞く」必要がある場合などが考えられます。

トレースイベントサブシステムは、モジュールやその他のカーネルコードが任意にユーザー定義の「合成」イベントを生成できるインカーネルAPIを提供し、これにより既存のトレースストリームを拡張したり、特定の重要な状態が発生したことを通知したりできます。

kprobeおよびkretprobeイベントの作成にも、インカーネルAPIが利用可能です。

合成イベントおよびk/ret/probeイベントのAPIは、低レベルの「dynevent_cmd」イベントコマンドAPIに基づいています。これはより専門的な用途に利用可能で、他の高レベルのトレースイベントAPIの基盤としても利用できます。

以下のAPIが提供されており、以下の機能を実行できます:

  • 動的に合成イベントの定義を作成

  • 動的にkprobeおよびkretprobeイベントの定義を作成

  • インカーネルコードから合成イベントをトレース

  • 低レベルの「dynevent_cmd」API

7.1 動的に合成イベントの定義を作成¶

カーネルモジュールやその他のカーネルコードから新しい合成イベントを作成する方法はいくつかあります。

最初の方法では、synth_event_create()関数を使用して1ステップでイベントを作成します。このメソッドでは、作成するイベントの名前と、フィールドを定義する配列をsynth_event_create()に渡します。成功した場合、この呼び出し後にはその名前とフィールドを持つ合成イベントが存在します。たとえば、「schedtest」という新しい合成イベントを作成する場合:

ret = synth_event_create("schedtest", sched_fields,
                         ARRAY_SIZE(sched_fields), THIS_MODULE);

この例におけるsched_fieldsパラメータは、struct synth_field_desc型の配列を指しており、それぞれの要素はタイプと名前でイベントフィールドを記述します:

static struct synth_field_desc sched_fields[] = {
      { .type = "pid_t",              .name = "next_pid_field" },
      { .type = "char[16]",           .name = "next_comm_field" },
      { .type = "u64",                .name = "ts_ns" },
      { .type = "u64",                .name = "ts_ms" },
      { .type = "unsigned int",       .name = "cpu" },
      { .type = "char[64]",           .name = "my_string_field" },
      { .type = "int",                .name = "my_int_field" },
};

利用可能なタイプについてはsynth_field_size()を参照してください。

field_nameに[n]が含まれる場合、そのフィールドは静的配列とみなされます。

field_namesに[]（サブスクリプトなし）が含まれる場合、そのフィールドは動的配列とみなされ、イベントに必要なだけのスペースのみを確保します。

イベントのスペースが事前に確保されるため、動的配列を使用すると、以下に記述するピースワイズな内核APIは使用できません。ただし、その他の非ピースワイズな内核APIは動的配列と併用可能です。

イベントがモジュール内で作成される場合、synth_event_create()にモジュールへのポインタを渡す必要があります。これにより、モジュールが除去された際にトレースバッファに読み込めないイベントが含まれることを防ぎます。

この時点で、イベントオブジェクトは新しいイベントを生成するために準備ができています。

2番目の方法では、イベントが複数のステップで作成されます。これにより、事前にフィールド配列を作成・埋め込む必要なく、動的にイベントを作成できます。

このメソッドを使用するには、まずsynth_event_gen_cmd_start()またはsynth_event_gen_cmd_array_start()を使用して空または部分的に埋められた合成イベントを作成する必要があります。synth_event_gen_cmd_start()では、イベント名と1つ以上の「タイプ フィールド名」のペアを指定します。synth_event_gen_cmd_array_start()では、イベント名とstruct synth_field_desc型の配列を指定します。synth_event_gen_cmd_start()またはsynth_event_gen_cmd_array_start()を呼び出す前には、synth_event_cmd_init()を使用してdynevent_cmdオブジェクトを作成・初期化する必要があります。

たとえば、「schedtest」という新しい合成イベントで2つのフィールドを作成する場合:

struct dynevent_cmd cmd;
char *buf;

/* Create a buffer to hold the generated command */
buf = kzalloc(MAX_DYNEVENT_CMD_LEN, GFP_KERNEL);

/* Before generating the command, initialize the cmd object */
synth_event_cmd_init(&cmd, buf, MAX_DYNEVENT_CMD_LEN);

ret = synth_event_gen_cmd_start(&cmd, "schedtest", THIS_MODULE,
                                "pid_t", "next_pid_field",
                                "u64", "ts_ns");

代わりに、同じ情報を含むstruct synth_field_desc型の配列を使用する方法もあります:

ret = synth_event_gen_cmd_array_start(&cmd, "schedtest", THIS_MODULE,
                                      fields, n_fields);

合成イベントオブジェクトが作成されると、そのオブジェクトにさらにフィールドを追加できます。synth_event_add_field()関数を使用して、1つずつフィールドを追加します。この関数には、dynevent_cmdオブジェクト、フィールドのタイプ、およびフィールド名を指定します。たとえば、「intfield」という名前の新しいint型フィールドを追加するには、以下の呼び出しを行います：

ret = synth_event_add_field(&cmd, "int", "intfield");

利用可能なタイプについてはsynth_field_size()を参照してください。フィールド名に[n]が含まれている場合、そのフィールドは配列とみなされます。

複数のフィールドを一度に追加するには、synth_field_descの配列を用いたadd_synth_fields()関数を使用できます。たとえば、この方法で最初の4つのsched_fieldsを追加できます：

ret = synth_event_add_fields(&cmd, sched_fields, 4);

すでに「type field_name」という形式の文字列を持っている場合、synth_event_add_field_str()関数を使用してそのまま追加できます。この関数は自動的に文字列の末尾に「;」を追加します。

すべてのフィールドを追加したら、synth_event_gen_cmd_end()関数を呼び出してイベントを確定し、登録します：

ret = synth_event_gen_cmd_end(&cmd);

この時点で、イベントオブジェクトは新しいイベントをトレースするために準備ができています。

7.2 カーネル内コードから合成イベントをトレースする¶

合成イベントをトレースするにはいくつかのオプションがあります。最初のオプションは、synth_event_trace()関数を使用して1回の呼び出しでイベントをトレースすることです。この関数には可変長の値を指定します。または、synth_event_trace_array()関数を使用して値の配列を指定することもできます。2番目のオプションは、事前に作成された値の配列や引数リストを必要としない場合に、synth_event_trace_start()とsynth_event_trace_end()関数を併用し、synth_event_add_next_val()またはsynth_event_add_val()関数で値を段階的に追加します。

7.2.1 一度に合成イベントをトレースする¶

一度に合成イベントをトレースするには、synth_event_trace()またはsynth_event_trace_array()関数を使用できます。

synth_event_trace()関数は、合成イベントを表すtrace_event_fileを渡します（このファイルはtrace_get_event_file()関数を使用して取得できます。合成イベント名は「synthetic」、システム名は「synthetic」、トレースインスタンス名はNULL（グローバルトレース配列を使用する場合）を指定します）。この関数には、合成イベントのフィールドごとに1つずつ指定するu64型の引数と、渡す値の数を指定します。

上記の合成イベント定義に対応するイベントをトレースするには、以下のコードが使用できます：

ret = synth_event_trace(create_synth_test, 7, /* number of values */
                        444,             /* next_pid_field */
                        (u64)"clackers", /* next_comm_field */
                        1000000,         /* ts_ns */
                        1000,            /* ts_ms */
                        smp_processor_id(),/* cpu */
                        (u64)"Thneed",   /* my_string_field */
                        999);            /* my_int_field */

すべての値はu64型にキャストし、文字列の値は文字列へのポインタをu64型にキャストします。文字列は、イベントに予約された領域にコピーされます。

代わりに、synth_event_trace_array()関数を使用して同じことを達成することもできます。この関数には、合成イベントを表すtrace_event_fileが渡され、これは「synthetic」というシステム名とトレースインスタンス名（グローバルトレース配列を使用する場合はNULL）を指定してtrace_get_event_file()を使用して取得できます。さらに、合成イベントの各フィールドに対応するu64型の配列も渡されます。

上記の合成イベント定義に対応するイベントをトレースするには、以下のコードを使用できます：

u64 vals[7];

vals[0] = 777;                  /* next_pid_field */
vals[1] = (u64)"tiddlywinks";   /* next_comm_field */
vals[2] = 1000000;              /* ts_ns */
vals[3] = 1000;                 /* ts_ms */
vals[4] = smp_processor_id();   /* cpu */
vals[5] = (u64)"thneed";        /* my_string_field */
vals[6] = 398;                  /* my_int_field */

「vals」配列は単なるu64型の配列であり、合成イベントのフィールド数と一致する必要があり、また合成イベントのフィールドと同じ順序でなければなりません。

すべての値はu64型にキャストし、文字列の値は文字列へのポインタをu64型にキャストします。文字列は、イベントに予約された領域にコピーされます。

合成イベントをトレースするには、トレースイベントファイルへのポインタが必要です。trace_get_event_file()関数を使用して取得できます。この関数は指定されたトレースインスタンス（この場合はグローバルトレース配列を使用するためNULL）内でファイルを見つけ、同時にそのインスタンスが消失しないようにします：

schedtest_event_file = trace_get_event_file(NULL, "synthetic",
                                            "schedtest");

イベントをトレースする前に、何らかの方法で有効化する必要があります。それしないと、トレースバッファに合成イベントが実際に表示されません。

カーネルから合成イベントを有効にするには、trace_array_set_clr_event()関数を使用できます（これは合成イベントに特有ではありませんので、「synthetic」というシステム名を明示的に指定する必要があります）。

イベントを有効にするには、trueを渡します：

trace_array_set_clr_event(schedtest_event_file->tr,
                          "synthetic", "schedtest", true);

無効にするにはfalseを渡します：

trace_array_set_clr_event(schedtest_event_file->tr,
                          "synthetic", "schedtest", false);

最後に、synth_event_trace_array()関数を使用して実際にイベントをトレースし、その後トレースバッファに表示されるはずです：

ret = synth_event_trace_array(schedtest_event_file, vals,
                              ARRAY_SIZE(vals));

合成イベントを削除するには、イベントを無効にして、trace_put_event_file()関数を使用してトレースインスタンスを「戻す」必要があります：

trace_array_set_clr_event(schedtest_event_file->tr,
                          "synthetic", "schedtest", false);
trace_put_event_file(schedtest_event_file);

これらが成功した場合、synth_event_delete()関数を呼び出してイベントを削除できます：

ret = synth_event_delete("schedtest");

7.2.2 合成イベントのピースごとのトレース¶

上記のピースごとの方法で合成イベントをトレースするには、synth_event_trace_start()関数を使用して「合成イベントトレースを開く」必要があります：

struct synth_trace_state trace_state;

ret = synth_event_trace_start(schedtest_event_file, &trace_state);

この関数には、前述の方法と同じように取得したtrace_event_fileが渡され、さらにstruct synth_trace_stateオブジェクトへのポインタが渡されます。このオブジェクトは使用前にはゼロ初期化され、この呼び出しと次の呼び出しの間で状態を保持するために使用されます。

イベントが開かれた後、つまりトレースバッファにスペースが確保された状態で、個々のフィールドを設定できます。これには2つの方法があります。1つは、各フィールドに対して順番に設定する方法で、リファレンス検索は不要です。もう1つは、フィールド名を指定して設定する方法です。この2つの方法のトレードオフは、割り当ての柔軟性と、各フィールドごとのリファレンス検索のコストのバランスです。

リファレンス検索をせずに順番に値を割り当てる場合は、synth_event_add_next_val()を使用します。各呼び出しでは、synth_event_trace_start()で使用した同じsynth_trace_stateオブジェクトを渡し、イベントの次のフィールドに設定する値を指定します。各フィールドが設定されると、「カーソル」は次のフィールドを指し、その後の呼び出しで設定されます。この方法を用いた呼び出しの順序例（エラー処理コードを除く）は以下の通りです：

/* next_pid_field */
ret = synth_event_add_next_val(777, &trace_state);

/* next_comm_field */
ret = synth_event_add_next_val((u64)"slinky", &trace_state);

/* ts_ns */
ret = synth_event_add_next_val(1000000, &trace_state);

/* ts_ms */
ret = synth_event_add_next_val(1000, &trace_state);

/* cpu */
ret = synth_event_add_next_val(smp_processor_id(), &trace_state);

/* my_string_field */
ret = synth_event_add_next_val((u64)"thneed_2.01", &trace_state);

/* my_int_field */
ret = synth_event_add_next_val(395, &trace_state);

任意の順序で値を割り当てたい場合は、synth_event_add_val()を使用します。各呼び出しでは、synth_event_trace_start()で使用した同じsynth_trace_stateオブジェクトを渡し、設定するフィールド名とその値を指定します。この方法を用いた呼び出しの順序例（エラー処理コードを除く）は以下の通りです：

ret = synth_event_add_val("next_pid_field", 777, &trace_state);
ret = synth_event_add_val("next_comm_field", (u64)"silly putty",
                          &trace_state);
ret = synth_event_add_val("ts_ns", 1000000, &trace_state);
ret = synth_event_add_val("ts_ms", 1000, &trace_state);
ret = synth_event_add_val("cpu", smp_processor_id(), &trace_state);
ret = synth_event_add_val("my_string_field", (u64)"thneed_9",
                          &trace_state);
ret = synth_event_add_val("my_int_field", 3999, &trace_state);

注意点として、synth_event_add_next_val()とsynth_event_add_val()は、同じイベントのトレース内で同時に使用することはできません。どちらか一方のみを使用可能です。

最後に、イベントは「クローズ」されるまで実際にトレースされません。これはsynth_event_trace_end()関数で行い、この関数は以前の呼び出しで使用したsynth_trace_state構造体のみを引数として受け取ります：

ret = synth_event_trace_end(&trace_state);

注意点として、synth_event_trace_end()は、どのadd呼び出しが失敗したかに関係なく、必ず最後に呼び出す必要があります（たとえば、不正なフィールド名が渡された場合など）。

7.3 ダイナミックにkprobeおよびkretprobeイベント定義を作成する¶

カーネルコードからkprobeまたはkretprobeトレースイベントを作成するには、kprobe_event_gen_cmd_start()またはkretprobe_event_gen_cmd_start()関数を使用できます。

kprobeイベントを作成するには、まずkprobe_event_gen_cmd_start()を呼び出して空または部分的に埋められたkprobeイベントを作成します。イベント名とプローブ位置を指定し、1つまたは複数の引数を表すプローブフィールドをこの関数に渡します。kprobe_event_gen_cmd_start()を呼び出す前には、ユーザーがdynevent_cmdオブジェクトを作成し、kprobe_event_cmd_init()で初期化する必要があります。

たとえば、2つのフィールドを持つ新しい「schedtest」kprobeイベントを作成する場合：

struct dynevent_cmd cmd;
char *buf;

/* Create a buffer to hold the generated command */
buf = kzalloc(MAX_DYNEVENT_CMD_LEN, GFP_KERNEL);

/* Before generating the command, initialize the cmd object */
kprobe_event_cmd_init(&cmd, buf, MAX_DYNEVENT_CMD_LEN);

/*
 * Define the gen_kprobe_test event with the first 2 kprobe
 * fields.
 */
ret = kprobe_event_gen_cmd_start(&cmd, "gen_kprobe_test", "do_sys_open",
                                 "dfd=%ax", "filename=%dx");

kprobeイベントオブジェクトが作成されると、そのオブジェクトにさらにフィールドを追加できます。フィールドを追加するには、kprobe_event_add_fields()を使用し、dynevent_cmdオブジェクトとプローブフィールドの変数引数リストを指定します。たとえば、いくつかの追加フィールドを追加するには、次の呼び出しを行うことができます：

ret = kprobe_event_add_fields(&cmd, "flags=%cx", "mode=+4($stack)");

すべてのフィールドを追加した後は、kprobe_event_gen_cmd_end()またはkretprobe_event_gen_cmd_end()関数を呼び出してイベントを確定し、登録する必要があります。どちらの関数を呼び出すかは、kprobeコマンドかkretprobeコマンドを開始したかによります：

ret = kprobe_event_gen_cmd_end(&cmd);

または:

ret = kretprobe_event_gen_cmd_end(&cmd);

この時点で、イベントオブジェクトは新しいイベントをトレースするために準備ができています。

同様に、kretprobeイベントは、プローブ名と位置、および$retvalなどの追加パラメータとともにkretprobe_event_gen_cmd_start()関数を使用して作成できます：

ret = kretprobe_event_gen_cmd_start(&cmd, "gen_kretprobe_test",
                                    "do_sys_open", "$retval");

合成イベントの場合と同様に、以下のようなコードを使用して新たに作成されたkprobeイベントを有効化できます：

gen_kprobe_test = trace_get_event_file(NULL, "kprobes", "gen_kprobe_test");

ret = trace_array_set_clr_event(gen_kprobe_test->tr,
                                "kprobes", "gen_kprobe_test", true);

最後に、合成イベントと同様に、以下のコードを使用してkprobeイベントファイルを返却し、イベントを削除できます：

trace_put_event_file(gen_kprobe_test);

ret = kprobe_event_delete("gen_kprobe_test");

7.4 「dynevent_cmd」低レベルAPI¶

カーネル内での合成イベントおよびkprobeインターフェースは、低レベルの「dynevent_cmd」インターフェースに基づいて構築されています。このインターフェースは、合成イベントやkprobeインターフェースなどの上位レベルインターフェースの基盤となるものであり、例として利用できます。

基本的な考え方は単純で、トレースイベントコマンドを生成するために使用できる汎用レイヤーを提供することです。生成されたコマンド文字列は、既にトレースイベントサブシステムに存在するコマンド解析およびイベント作成コードに渡され、対応するトレースイベントが作成されます。

要約すると、高レベルインターフェースコードはstruct dynevent_cmdオブジェクトを作成し、dynevent_arg_add()とdynevent_arg_pair_add()などの関数を使用してコマンド文字列を構築します。最終的に、dynevent_create()関数を使用してコマンドが実行されます。インターフェースの詳細は以下の通りです。

新しいコマンド文字列を作成する最初のステップは、dynevent_cmdのインスタンスを作成して初期化することです。ここでは、例えばスタック上にdynevent_cmdを作成し、初期化します：

struct dynevent_cmd cmd;
char *buf;
int ret;

buf = kzalloc(MAX_DYNEVENT_CMD_LEN, GFP_KERNEL);

dynevent_cmd_init(cmd, buf, maxlen, DYNEVENT_TYPE_FOO,
                  foo_event_run_command);

dynevent_cmdの初期化には、ユーザー指定のバッファとそのバッファの長さ（MAX_DYNEVENT_CMD_LENを使用可能 - 2KBはスタックに載せるのが不便なので、動的に割り当てられます）を指定する必要があります。また、dyneventタイプIDも指定し、これにより後続のAPI呼び出しが正しいコマンドタイプであることを確認します。さらに、イベント固有のrun_command()コールバック関数へのポインタも指定します。この関数が実際にイベント固有のコマンドを実行します。

これにより、コマンド文字列は、引数を追加する関数を連続して呼び出すことで構築できます。

単一の引数を追加するには、struct dynevent_argまたはstruct dynevent_arg_pairオブジェクトを定義して初期化します。以下は、最も単純な引数追加の例で、与えられた文字列を空白区切りでコマンドに追加する例です。

struct dynevent_arg arg;

dynevent_arg_init(&arg, NULL, 0);

arg.str = name;

ret = dynevent_arg_add(cmd, &arg);

argオブジェクトは最初にdynevent_arg_init()で初期化され、この場合パラメータはNULLまたは0であり、これはオプションの健全性チェック関数や引数末尾に追加されるセパレータが存在しないことを意味します。

もう一つの複雑な例として、'arg pair'を使用したものです。これは複数のコンポーネントを単位として結合した引数を生成するために使用され、例えば'type field_name;'のような引数や、'flags=%cx'などの単純な式の引数などです。

struct dynevent_arg_pair arg_pair;

dynevent_arg_pair_init(&arg_pair, dynevent_foo_check_arg_fn, 0, ';');

arg_pair.lhs = type;
arg_pair.rhs = name;

ret = dynevent_arg_pair_add(cmd, &arg_pair);

同様に、arg_pairは最初に初期化され、この場合、引数の健全性をチェックするコールバック関数（例えば、ペアのどちらかがNULLでないことを確認）と、ペアの間に追加される演算子（ここではなし）、および引数ペア末尾に追加されるセパレータ（ここでは';'）が指定されます。

また、dynevent_str_add()関数を使用して、スペースやセパレータ、引数チェックをせずに文字列を直接追加することも可能です。

任意の回数のdynevent_*_add()呼び出しで文字列を構築できます（cmd->maxlenを超えるまで）。すべての引数が追加され、コマンド文字列が完成したら、コマンドを実行するだけです。これには単にdynevent_create()を呼び出すだけで完了します。

ret = dynevent_create(&cmd);

その時点で、返却値が0であれば、動的イベントが作成され、使用準備が整っています。

APIの詳細については、dynevent_cmd関数の定義自体を参照してください。

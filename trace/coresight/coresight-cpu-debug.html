Coresight CPU Debug Module¶

著者

Leo Yan <leo.yan@linaro.org>

日付

2017年4月5日

はじめに¶

Coresight CPU debug moduleはARMv8-aアーキテクチャリファレンスマニュアル（ARM DDI 0487A.k）の「Part H: External debug」章で定義されており、CPUはデバッグモジュールを統合可能で、主にself-hosted debugモードとexternal debugモードの2つのモードで使用されます。通常、external debugモードは外部デバッガーがJTAGポートからSoCに接続されることが知られています。一方で、プログラムはself-hosted debugモードに依存したデバッグ方法を探索できます。このドキュメントはこの部分に焦点を当てます。

デバッグモジュールはsample-based profiling拡張機能を提供し、CPUプログラムカウンタ、セキュア状態、例外レベルなどに使用できます。通常、各CPUには専用のデバッグモジュールが接続されます。self-hosted debugメカニズムに基づき、カーネルパニック発生時にmmio領域から関連レジスタにアクセスできます。カーネルパニック時のコールバック通知により、すべてのCPUの関連レジスタをダンプし、パニックの補助分析に役立ちます。

ハードロックアップ検出器は、定期的に実行されるhrtimerによって生成される割込みでウォッチドッグタスクを起動します。ハードロックアップの検出には、「watchdog_thresh」（コンパイル時に初期化され、sysctlの同じ名前で設定可能）秒ごとにNMI perfイベントが生成されます。システム内のどのCPUもその間hrtimer割込みを受けていない場合、ハードロックアップ検出器（NMI perfイベントのハンドラ）がカーネル警告を生成するか、設定に応じてパニックを呼び出します。¶

  • ドライバ登録時にEDDEVIDおよびEDDEVID1という2つのデバイスIDレジスタを使用して、sample-based profilingが実装されているかを判断します。一部のプラットフォームではこのハードウェア機能が完全または部分的に実装されている場合があり、この機能がサポートされていない場合は登録が失敗します。

  • このドキュメンテーションが書かれた時点では、デバッグドライバはカーネルパニックコールバック通知から収集された情報に基づき、3つのサンプリングレジスタEDPCSR、EDVIDSR、EDCIDSRを主に使用しています。EDPCSRからプログラムカウンタを取得でき、EDVIDSRにはセキュア状態、例外レベル、ビット幅などの情報があり、EDCIDSRはCONTEXTIDR_EL1のサンプル値を含むコンテキストID値です。

  • ドライバはAArch64モードまたはAArch32モードで動作するCPUをサポートしています。レジスタの命名規則は異なります。AArch64はARM DDI 0487A.kのH9.1章で「ED」をレジスタプレフィックスとして使用し、AArch32はARM DDI 0487A.kのG5.1章で「DBG」をプレフィックスとして使用します。ドライバは統一的にAArch64の命名規則を使用します。

  • ARMv8-a（ARM DDI 0487A.k）とARMv7-a（ARM DDI 0406C.b）のレジスタビット定義は異なります。そのため、ドライバは2つの違いを統合しています：

    PCSROffset=0b0000の場合、ARMv8-AではEDPCSRの機能は実装されていません。ARMv7-Aでは「PCSRサンプルはインストラクションセット状態に依存する値でオフセットされる」と定義されています。ARMv7-Aでは、ドライバがCPUがARMまたはThumbインストラクションセットで実行されているかをさらに確認し、PCSR値を校正します。オフセットに関する詳細な説明はARMv7-A ARM（ARM DDI 0406C.b）のC11.11.34章「DBGPCSR、プログラムカウンタサンプリングレジスタ」に記載されています。

    PCSROffset=0b0010の場合、ARMv8-Aでは「EDPCSRが実装され、サンプルにはオフセットが適用されず、AArch32状態ではインストラクションセット状態をサンプリングしない」と定義されています。したがって、ARMv8でEDDEVID1.PCSROffsetが0b0010であり、CPUがAArch32状態で実行されている場合、EDPCSRはサンプリングされません。CPUがAArch64状態で実行されている場合、EDPCSRはサンプリングされ、オフセットは適用されません。

クロックおよび電源ドメイン¶

デバッグレジスタにアクセスする前に、クロックおよび電源ドメインが適切に有効になっていることを確認する必要があります。ARMv8-A ARM（ARM DDI 0487A.k）の「H9.1 デバッグレジスタ」章では、デバッグレジスタが2つのドメインに分類されています：デバッグドメインとCPUドメイン。

                               +---------------+
                               |               |
                               |               |
                    +----------+--+            |
       dbg_clock -->|          |**|            |<-- cpu_clock
                    |    Debug |**|   CPU      |
dbg_power_domain -->|          |**|            |<-- cpu_power_domain
                    +----------+--+            |
                               |               |
                               |               |
                               +---------------+

デバッグドメインでは、ユーザーはDTバインディングの「clocks」と「power-domains」を用いて、デバッグ論理に該当するクロック源および電源供給を指定します。ドライバは必要に応じてpm_runtime_{put|get}操作を呼び出して、デバッグ電源ドメインを管理します。

CPUドメインでは、異なるSoC設計が異なる電源管理スキームを持ち、最終的にこれは外部デバッグモジュールに大きな影響を与えます。したがって、以下のようなケースに分類できます：

  • 電源制御器がCPU電源ドメインに対して正しく動作する健全な電源制御器を持つシステムでは、ドライバがEDPRCRレジスタを用いてCPU電源ドメインを制御できます。ドライバはまずEDPRCR.COREPURQビットを書き込み、CPUを電源ONにし、次にEDPRCR.CORENPDRQビットを書き込んでCPU電源オフのエミュレーションを行います。これにより、デバッグ関連レジスタにアクセスする期間中、CPU電源ドメインが適切に電源ONされていることを保証できます。

  • 一部の設計では、クラスタ内のすべてのCPUが電源オフになると、デバッグレジスタの一部を含むクラスタ全体を電源オフします。この場合、EDPRCRのビットは無視されるため、これらの設計ではCoreSight/デバッグ設計者予想の通りに電源オフ時のデバッグをサポートしていません。これは、ターゲットレジスタが電源が入っていない場合、EDPRSRを確認するだけでもバスハングを引き起こす可能性があります。

    この場合、デバッグレジスタにアクセスする際、電源が入っていない状態で行うことは大変な問題を引き起こすため、起動時またはユーザーがモジュールを実行時に関係なくCPUの低電力状態を防ぐ必要があります。詳細な使用方法については、『モジュールの使用方法』の章を参照してください。

モジュールの使用方法¶

起動時にデバッグ機能を有効にする場合は、カーネルのコマンットラインパラメータに "coresight_cpu_debug.enable=1" を追加してください。

ドライバはモジュールとしても動作するため、insmod でモジュールを有効化してデバッグを実行できます。

# insmod coresight_cpu_debug.ko debug=1

起動時またはモジュールをロードした際、デバッグが有効になっていない場合、ドライバは debugfs ファイルシステムを使用して、動的にデバッグを有効/無効にするための設定を提供します。

有効にするには、/sys/kernel/debug/coresight_cpu_debug/enable に '1' を書き込みます。

# echo 1 > /sys/kernel/debug/coresight_cpu_debug/enable

無効にするには、/sys/kernel/debug/coresight_cpu_debug/enable に '0' を書き込みます。

# echo 0 > /sys/kernel/debug/coresight_cpu_debug/enable

『クロックと電源ドメイン』の章で説明されているように、あるプラットフォームでアイドル状態によりデバッグロジックを電源オフし、電源制御が EDPRCR のリクエストに対応できず、デバッグロジックへのアクセスを確保するためには、CPU アイドル状態を制限する必要があります。

起動時にアイドル状態を制限するには、カーネルのコマンドラインに "nohlt" または "cpuidle.off=1" を使用してください。

実行時においては、以下の方法でアイドル状態を無効にできます。

PM QoS サブシステムを使用して CPU アイドル状態を無効にすることが可能です。具体的には、"/dev/cpu_dma_latency" インターフェースを使用します（参照： PM Quality Of Service インターフェース 詳細についてはこちら）。PM QoS ドキュメンテーションに記載されているように、リクエストされたパラメータはファイルディスクリプタが解放されるまで有効です。例えば：

# exec 3<> /dev/cpu_dma_latency; echo 0 >&3
...
Do some work...
...
# exec 3<>-

アプリケーションプログラムからも同様の操作が可能です。

cpuidle sysfs から特定のCPUの特定のアイドル状態を無効にすることができます（参照： CPUアイドル時間管理):

# echo 1 > /sys/devices/system/cpu/cpu$cpu/cpuidle/state$state/disable

coresight-cpu-debug 850000.debug:  EDCIDSR: 00000000
coresight-cpu-debug 850000.debug:  EDVIDSR: 90000000 (State:Non-secure Mode:EL1/0 Width:64bits VMID:0)

coresight-cpu-debug 852000.debug:  EDPCSR:  debug_notifier_call+0x23c/0x358

Coresight - ARM におけるハードウェア支援トレース¶

著者

Mathieu Poirier <mathieu.poirier@linaro.org>

日付

2014年9月11日

はじめに¶

Coresightは、ARMベースのSoCのデバッグを可能にする技術の集合体です。JTAGやハードウェア支援トレースの解決策を含み、このドキュメントは後者の取り扱いについて説明しています。

ハードウェア支援トレースは、多くのSoCやGPU、DMAエンジンなどのコンポーネントを持つシステムを扱う際にますます重要性を増しています。ARMは、合成時に関連するトレースニーズに応じて設計に組み込まれるさまざまなコンポーネントを用いてハードウェア支援トレースの解決策を開発しました。コンポーネントは一般的にソース、リンク、シンクの3つに分類され、通常はAMBAバスを用いて発見されます。

「ソース」は、ユーザーが設定したトレースシナリオに基づいてプロセッサの指令パスを表す圧縮ストリームを生成します。このストリームはATBバスを介してコアスカイシステムを経由し、ソースからシンク（複数可）へリンクを介して流されます。シンクはコアスカイ実装のエンドポイントとして機能し、圧縮ストリームをメモリバッファに保存するか、外部世界へのインターフェースを提供してホストにデータを転送し、オンボードのコアスカイメモリバッファが満杯になるのを防ぎます。

典型的なコアスカイシステムは以下のようになります:

 *****************************************************************
**************************** AMBA AXI  ****************************===||
 *****************************************************************    ||
       ^                    ^                            |            ||
       |                    |                            *            **

 |  # ETM #    :::::  |  # PTM #    :::::    :::::       @   |
 |   #####      ^ ^   |   #####      ^ !      ^ !        .   |   |||||||||
 | |->###       | !   | |->###       | !      | !        .   |   || DAP ||
 | |   #        | !   | |   #        | !      | !        .   |   |||||||||
 | |   .        | !   | |   .        | !      | !        .   |      |  |
 | |   .        | !   | |   .        | !      | !        .   |      |  *
 | |   .        | !   | |   .        | !      | !        .   |      | SWD/
 | |   .        | !   | |   .        | !      | !        .   |      | JTAG
 *****************************************************************<-|
*************************** AMBA Debug APB ************************
 *****************************************************************
  |    .          !         .          !        !        .    |
  |    .          *         .          *        *        .    |

 *****************************************************************
  |    .     ^              .                            .    |
  |    *     !              *                            *    |
 *****************************************************************
****************** AMBA Advanced Trace Bus (ATB) ******************
 *****************************************************************
  |          !                        ===============         |
  |          *                         ===== F =====<---------|
  |   :::::::::                         ==== U ====
  |-->:: CTI ::<!!                       === N ===
  |   :::::::::  !                        == N ==
  |    ^         *                        == E ==
  |    !  &&&&&&&&&       IIIIIII         == L ==
  |------>&& ETB &&<......II     I        =======
  |    !  &&&&&&&&&       II     I           .
  |    !                    I     I          .

  |------>& TPIU  &<......II    I            DAP = Debug Access Port
          &&&&&&&&&       IIIIIII            ETM = Embedded Trace Macrocell
              ;                              PTM = Program Trace Macrocell
              ;                              CTI = Cross Trigger Interface
              *                              ETB = Embedded Trace Buffer
         To trace port                       TPIU= Trace Port Interface Unit
                                             SWD = Serial Wire Debug

コンポーネントのターゲット構成はAPBバスを介して行われますが、すべてのトレースデータはATBバスを介して帯外で転送されます。CTMはコアスカイコンポーネント間で信号を集約・配布する方法を提供します。

コアスカイフレームワークは、プラットフォーム上のコアスカイデバイスを表現・設定・管理する中心的なポイントを提供します。この最初の実装は基本的なトレース機能に焦点を当てており、ETM/PTM、ファンネル、レプリケータ、TMC、TPIU、ETBなどのコンポーネントをサポートします。今後はSTMやCTIなどのより複雑なIPブロックのサポートが行われます。

略語と分類¶

略語:

PTM:

プログラムトレースマクロセル

ETM:

埋め込まれたトレースマクロセル

STM:

システムトレースマクロセル

ETB:

埋め込まれたトレースバッファ

ITM:

インストゥルメンテーショントレースマクロセル

TPIU:

トレースポートインターフェースユニット

TMC-ETR:

トレースメモリコントローラー、埋め込まれたトレースルーターとして構成

TMC-ETF:

トレースメモリコントローラー、埋め込まれたトレースFIFOとして構成

CTI:

クロストリガーインターフェース

分類:

ソース:

ETMv3.x ETMv4, PTMv1.0, PTMv1.1, STM, STM500, ITM

リンク：

ファンネル、レプリケータ（知能有無を問わず）、TMC-ETR

シンク:

ETBv1.0, ETB1.1, TPIU, TMC-ETF

その他の:

CTI

デバイスツリーバインディング¶

詳細については、Documentation/devicetree/bindings/arm/coresight.txt を参照してください。

本執筆時点では、ITM、STMsおよびCTIs用のドライバーは提供されていませんが、ソリューションが成熟するにつれて追加される予定です。

フレームワークと実装¶

CoreSightフレームワークは、プラットフォーム上でCoreSightデバイスを表現し、設定し、管理するための中心的なポイントを提供します。CoreSight準拠のデバイスは、正しいAPIを使用する限り、フレームワークに登録できます：

struct coresight_device *coresight_register(struct coresight_desc *desc);¶
void coresight_unregister(struct coresight_device *csdev);¶

登録関数は、 struct coresight_desc *desc を取得し、デバイスをコアフレームワークに登録します。アンレジスト関数は、登録時の取得時に得られた struct coresight_device *csdev の参照を取得します。

登録プロセスが順調に進むと、新しいデバイスは/sys/bus/coresight/devices下に表示されます。TC2プラットフォームの例を以下に示します：

root:~# ls /sys/bus/coresight/devices/
replicator  20030000.tpiu    2201c000.ptm  2203c000.etm  2203e000.etm
20010000.etb         20040000.funnel  2201d000.ptm  2203d000.etm
root:~#

関数は、 struct coresight_device、これは以下のようになります:

struct coresight_desc {
        enum coresight_dev_type type;
        struct coresight_dev_subtype subtype;
        const struct coresight_ops *ops;
        struct coresight_platform_data *pdata;
        struct device *dev;
        const struct attribute_group **groups;
};

を取得します。『coresight_dev_type』はデバイスの種類を示します（つまり、ソースリンクかシンクか）、『coresight_dev_subtype』はその種類をさらに特徴づけます。

以下の struct coresight_ops は必須であり、フレームワークがコンポーネントに関連する基本操作をどのように実行するかを示します。各コンポーネントは異なる要件を持つため、 struct coresight_ops_sink, struct coresight_ops_link および struct coresight_ops_source が提供されています。

次のフィールド struct coresight_platform_data *pdata は、 of_get_coresight_platform_data()を呼び出すことで取得され、 struct device *dev がデバイス参照を埋め込んでいる amba_device:

static int etm_probe(struct amba_device *adev, const struct amba_id *id)
{
 ...
 ...
 drvdata->dev = &adev->dev;
 ...
}

特定のデバイスクラス（ソース、リンク、またはシンク）には、それらに共通する一般的な操作が実行可能です（参照： struct coresight_ops）。この **groups は、そのコンポーネントに特有の操作に関するsysfsエントリのリストです。「実装定義」のカスタマイズは、これらのエントリを通じてアクセスおよび制御されることが予期されます。

デバイスの命名規則¶

『coresight』バスに表示されるデバイスは、その親デバイスと同じ名前が付けられています。つまり、AMBAバスやプラットフォームバスに表示される実際のデバイスです。したがって、名前はLinux Open Firmwareレイヤーの命名規約に基づいており、デバイスのベース物理アドレスに続いてデバイスタイプが追加されます。例:

root:~# ls /sys/bus/coresight/devices/
 20010000.etf  20040000.funnel      20100000.stm     22040000.etm
 22140000.etm  230c0000.funnel      23240000.etm     20030000.tpiu
 20070000.etr  20120000.replicator  220c0000.funnel
 23040000.etm  23140000.etm         23340000.etm

しかし、ACPIサポートの導入により、実際のデバイスの名前はやや暗号化されていて、非直感的です。そのため、新しい命名規則が導入され、デバイスの種類に基づいたより一般的な名前が使用されるようになりました。以下のルールが適用されます：

1) Devices that are bound to CPUs, are named based on the CPU logical
   number.

   e.g, ETM bound to CPU0 is named "etm0"

2) All other devices follow a pattern, "<device_type_prefix>N", where :

      <device_type_prefix>    - A prefix specific to the type of the device
      N                       - a sequential number assigned based on the order
                                of probing.

      e.g, tmc_etf0, tmc_etr0, funnel0, funnel1

したがって、新しい規則により、デバイスは以下のようになります：

root:~# ls /sys/bus/coresight/devices/
 etm0     etm1     etm2         etm3  etm4      etm5      funnel0
 funnel1  funnel2  replicator0  stm0  tmc_etf0  tmc_etr0  tpiu0

以下の例の一部は古い命名規則を、一部は新しい規則を参照している場合があります。システム上で表示される内容が予期されていない可能性があることを確認するためです。システム上で指定された場所に表示される『names』を実際に使用する必要があります。

トポロジの表現¶

各CoreSightコンポーネントは、 connections 他のCoreSightコンポーネントへのリンクを含むディレクトリです。これにより、ユーザーがトレース topology を探索でき、大規模なシステムでは特定のソースに対して適切なシンクを決定できます。接続情報は、特定のコンポーネントに接続されているCTIデバイスを特定するのに利用できます。このディレクトリには、 nr_links このディレクトリ内のリンク数を示す属性があります。

ETMソースの場合、この場合 etm0 Junoプラットフォームでは、典型的な配置は以下の通りです：

linaro-developer:~# ls - l /sys/bus/coresight/devices/etm0/connections
<file details>  cti_cpu0 -> ../../../23020000.cti/cti_cpu0
<file details>  nr_links
<file details>  out:0 -> ../../../230c0000.funnel/funnel2

アウトポートをたどって funnel2:

linaro-developer:~# ls -l /sys/bus/coresight/devices/funnel2/connections
<file details> in:0 -> ../../../23040000.etm/etm0
<file details> in:1 -> ../../../23140000.etm/etm3
<file details> in:2 -> ../../../23240000.etm/etm4
<file details> in:3 -> ../../../23340000.etm/etm5
<file details> nr_links
<file details> out:0 -> ../../../20040000.funnel/funnel0

そして再度 funnel0:

linaro-developer:~# ls -l /sys/bus/coresight/devices/funnel0/connections
<file details> in:0 -> ../../../220c0000.funnel/funnel1
<file details> in:1 -> ../../../230c0000.funnel/funnel2
<file details> nr_links
<file details> out:0 -> ../../../20010000.etf/tmc_etf0

最初のシンクを見つける tmc_etf0。これは、シンクとしてデータを収集するか、チェーンをさらに進むリンクとして利用できます：

linaro-developer:~# ls -l /sys/bus/coresight/devices/tmc_etf0/connections
<file details> cti_sys0 -> ../../../20020000.cti/cti_sys0
<file details> in:0 -> ../../../20040000.funnel/funnel0
<file details> nr_links
<file details> out:0 -> ../../../20150000.funnel/funnel4

を funnel4:

linaro-developer:~# ls -l /sys/bus/coresight/devices/funnel4/connections
<file details> in:0 -> ../../../20010000.etf/tmc_etf0
<file details> in:1 -> ../../../20140000.etf/tmc_etf1
<file details> nr_links
<file details> out:0 -> ../../../20120000.replicator/replicator0

ビットのワードと replicator0:

linaro-developer:~# ls -l /sys/bus/coresight/devices/replicator0/connections
<file details> in:0 -> ../../../20150000.funnel/funnel4
<file details> nr_links
<file details> out:0 -> ../../../20030000.tpiu/tpiu0
<file details> out:1 -> ../../../20070000.etr/tmc_etr0

チェーン内の最終シンクに到達した場合、 tmc_etr0:

linaro-developer:~# ls -l /sys/bus/coresight/devices/tmc_etr0/connections
<file details> cti_sys0 -> ../../../20020000.cti/cti_sys0
<file details> in:0 -> ../../../20120000.replicator/replicator0
<file details> nr_links

以下の説明では、sysfsを使用する場合、シンクとソースを有効にすることでトレースを成功させることができます。フレームワークは必要なすべての中間リンクを正しく有効にします。

注意: cti_sys0 上記の2つの接続リストに表示されます。CTIは複数のデバイスに接続され、CTMを介してスター topology で配置されます。詳しくは（CoreSight エンベデッドクロストリガー（CTI & CTM）。) 4 をご覧ください。このデバイスを確認すると、4つの接続があります：

linaro-developer:~# ls -l /sys/bus/coresight/devices/cti_sys0/connections
<file details> nr_links
<file details> stm0 -> ../../../20100000.stm/stm0
<file details> tmc_etf0 -> ../../../20010000.etf/tmc_etf0
<file details> tmc_etr0 -> ../../../20070000.etr/tmc_etr0
<file details> tpiu0 -> ../../../20030000.tpiu/tpiu0

トレーサー モジュールの使用方法¶

Coresightフレームワークを使用する方法は2通りあります：

  1. perfコマンドラインツールを使用する。

  2. sysFSインターフェースを使用してCoresightデバイスと直接やり取りする。

sysFSインターフェースを使用するには、Coresight HWについて深い理解が必要なので、前者を優先します。以下のセクションでは、両方の方法の使用方法について詳しく説明します。

  1. sysFSインターフェースを使用する場合：

トレース収集を開始する前に、coresightシンクを特定する必要があります。有効にできるシンク（またはソース）の数には制限はありません。一般的な操作として、シンククラスに関連するすべてのデバイスにはsysfsに「active」エントリがあります：

root:/sys/bus/coresight/devices# ls
replicator  20030000.tpiu    2201c000.ptm  2203c000.etm  2203e000.etm
20010000.etb         20040000.funnel  2201d000.ptm  2203d000.etm
root:/sys/bus/coresight/devices# ls 20010000.etb
enable_sink  status  trigger_cntr
root:/sys/bus/coresight/devices# echo 1 > 20010000.etb/enable_sink
root:/sys/bus/coresight/devices# cat 20010000.etb/enable_sink
1
root:/sys/bus/coresight/devices#

起動時に現在のetm3xドライバーは、最初のアドレス比較器を「_stext」と「_etext」で設定し、この範囲内のすべてのインストラクションをトレースします。したがって、「ソースを有効にする」ことで即座にトレースキャプチャが開始されます：

root:/sys/bus/coresight/devices# echo 1 > 2201c000.ptm/enable_source
root:/sys/bus/coresight/devices# cat 2201c000.ptm/enable_source
1
root:/sys/bus/coresight/devices# cat 20010000.etb/status

トレース収集は同じ方法で停止されます：

root:/sys/bus/coresight/devices# echo 0 > 2201c000.ptm/enable_source
root:/sys/bus/coresight/devices#

of=~/cstrace.bin

  1. perfフレームワークを使用する場合：

Coresightトレーサーは、Perfフレームワークのパフォーマンスモニタリングユニット（PMU）の抽象化を使用して表されます。したがって、perfフレームワークは、関心のあるプロセスがスケジューリングされるタイミングに基づいてトレースが有効になるタイミングを制御します。システムで構成されている場合、Coresight PMUはperfコマンドラインツールによってクエリされるとリストされます:

linaro@linaro-nano:~$ ./perf list pmu

予め定義されたイベントの一覧（-e で使用するための）:

cs_etm// [カーネルPMUイベント]

linaro@linaro-nano:~$

システムに存在するトレーサーの数（通常はプロセッサコアの数に等しい）に関係なく、「cs_etm」PMUはリストに1度だけ表示されます。

Coresight PMUは他のPMUと同じように動作します。つまり、PMUの名前はフォワードスラッシュ（/）で囲まれた中にリストされ、設定オプションとともに表示されます。Coresightシステムは通常複数のシンクを持つため、トレースセッションで使用するシンクの名前をイベントオプションとして指定する必要があります。新しいカーネルでは、シンクの一覧は($SYSFS)/bus/event_source/devices/cs_etm/sinks/の下にsysFSで表示されます:

root@localhost:/sys/bus/event_source/devices/cs_etm/sinks# ls
tmc_etf0  tmc_etr0  tpiu0

古いカーネルでは、この情報は($SYSFS)/bus/coresight/devices/の下にあるコアスカイトデバイスの一覧から見つける必要があります:

root:~# ls /sys/bus/coresight/devices/
 etm0     etm1     etm2         etm3  etm4      etm5      funnel0
 funnel1  funnel2  replicator0  stm0  tmc_etf0  tmc_etr0  tpiu0
root@linaro-nano:~# perf record -e cs_etm/@tmc_etr0/u --per-thread program

上記の「デバイス名の命名スキーム」セクションで述べたように、デバイス名は例のように表示されるとは限りません。sysFSの下にあるデバイス名を使用する必要があります。

フォワードスラッシュ（/）内の構文は重要です。'@'文字はパーサーにシンクが指定されると通知し、このシンクをトレースセッションで使用するように指示します。

上記の内容や、perfツールを使用したCoresightの使用例については、openCSD gitHubリポジトリの「HOWTO.md」ファイルに詳細が記載されています 3.

2.1) perfツールを使用したAutoFDO分析:

perfはプログラムのトレースを記録および分析するために使用できます。

実行を記録するには、「perf record」コマンドを使用し、cs_etmイベントを指定し、記録先のシンクの名前を指定します。例えば:

perf record -e cs_etm/@tmc_etr0/u --per-thread

'perf report'および'perf script'コマンドは実行を分析し、指令トレースから指令およびブランチイベントを合成します。'perf inject'はトレースデータを合成イベントに置き換えることができます。--itraceオプションは合成イベントの種類と頻度を制御します（perfドキュメンテーションを参照）。

注意として、現在は64ビットのプログラムのみがサポートされています。32ビットARMプログラムの指令デコードをサポートするためにはさらに作業が必要です。

2.2) PIDのトレース

カーネルは、PID値をPE ContextIDレジスタに書き込むように構築できます。EL1で実行されているカーネルでは、PIDはCONTEXTIDR_EL1に保存されます。PEはArm Virtualization Host Extensions（VHE）を実装する場合があり、その場合はカーネルはEL2で仮想化ホストとして実行されます。この場合、PID値はCONTEXTIDR_EL2に保存されます。

perfは、ETMにこれらの値をトレースデータに挿入するようにプログラムするPMU形式を提供します。PMU形式の定義は以下の通りです：

「contextid1」：EL1カーネルおよびEL2カーネルの両方で利用可能です。カーネルがEL1で実行されている場合、「contextid1」はPIDトレーシングを有効にします。カーネルがEL2で実行されている場合、この機能はゲストアプリケーションのPIDをトレースするために使用されます。

「contextid2」：カーネルがEL2で実行されている場合にのみ使用可能です。カーネルがEL2で実行されているときに

この機能は、ゲストアプリケーションのPIDをトレースするために使用されます。

選択すると、EL2 コアでのPIDトレースを有効にします。

「contextid」: PIDトレースを有効にするオプションの別名になります。

トレース。つまり、EL1 コアではcontextid == contextid1、EL2 コアではcontextid == contextid2です。

perfは常に関連するELでPIDトレースを自動的に有効にします。これは「contextid」設定を自動的に有効にするためです。ただし、EL2では「context、contextid1」と「contextid2」の設定を組み合わせることで、特定の調整が可能です。例えば、ユーザーがホストとゲストの両方のPIDをトレースしたい場合、以下のコマンドで2つの設定を同時に有効にできます：

perf record -e cs_etm/contextid1,contextid2/u – vm

フィードバックをもとにした最適化（Feedback Directed Optimization）のカバレッジファイルを生成: AutoFDO¶

‘perf inject’は–itraceオプションを受け付けるが、この場合トレースデータは削除され、合成イベントに置き換えられる。例:

perf inject --itrace --strip -i perf.data -o perf.data.new

以下はAutoFDOでARM ETMを自動的に使用する例である。これはautofdo（https://github.com/google/autofdo)とgccバージョン5を必要とする。バブルソートの例はAutoFDOチュートリアル（https://gcc.gnu.org/wiki/AutoFDO/Tutorial).

$ gcc-5 -O3 sort.c -o sort
$ taskset -c 2 ./sort
Bubble sorting array of 30000 elements
5910 ms

$ perf record -e cs_etm/@tmc_etr0/u --per-thread taskset -c 2 ./sort
Bubble sorting array of 30000 elements
12543 ms
[ perf record: Woken up 35 times to write data ]
[ perf record: Captured and wrote 69.640 MB perf.data ]

$ perf inject -i perf.data -o inj.data --itrace=il64 --strip
$ create_gcov --binary=./sort --profile=inj.data --gcov=sort.gcov -gcov_version=1
$ gcc-5 -O3 -fauto-profile=sort.gcov sort.c -o sort_autofdo
$ taskset -c 2 ./sort_autofdo
Bubble sorting array of 30000 elements
5806 ms

STMモジュールの使用方法¶

システムトレースマクロセル（STM）モジュールを使用する方法はトレーサーと同様である。違いは、クライアントがトレースキャプチャを制御することになる点である。プログラムフローを通じたコードの実行ではなく、クライアントが直接制御する点が異なる。

他のCoreSightコンポーネントと同様に、STMトレーサーに関する詳細情報はsysfsで確認できる。各エントリの詳細情報については 1:

root@genericarmv8:~# ls /sys/bus/coresight/devices/stm0
enable_source   hwevent_select  port_enable     subsystem       uevent
hwevent_enable  mgmt            port_select     traceid
root@genericarmv8:~#

他のソースと同様に、シンクを特定し、STMを有効にしてから使用する必要がある:

root@genericarmv8:~# echo 1 > /sys/bus/coresight/devices/tmc_etf0/enable_sink
root@genericarmv8:~# echo 1 > /sys/bus/coresight/devices/stm0/enable_source

その先、ユーザー空間アプリケーションは、ジェネリックSTM APIが提供するdevfsインターフェースを通じてチャネルを要求し使用できる:

root@genericarmv8:~# ls -l /dev/stm0
crw-------    1 root     root       10,  61 Jan  3 18:11 /dev/stm0
root@genericarmv8:~#

ジェネリックSTM APIの使用方法については以下に詳述されている:- システムトレースモジュール 2.

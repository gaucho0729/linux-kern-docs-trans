イベントとトレースポイントを用いた挙動分析ノート¶

著者

Mel Gorman (PCLに関する情報はIngo Molnarからのメールに基づいています)

1. はじめに¶

トレースポイント（参照 Linuxカーネルトレースポイントの利用) は、カスタムのカーネルモジュールを作成することなく、イベントトレースインフラストラクチャを使用してプローブ関数を登録できます。

単純に説明すると、トレースポイントはシステム内での状況を把握するための重要なイベントを表します。他のトレースポイントと組み合わせて使用することで、全体像を構築できます。これらのイベントを収集・解釈する方法は多数存在しますが、現在のベストプラクティスが欠如しているため、このドキュメントではいくつかの方法を紹介します。

このドキュメントでは、debugfsが/sys/kernel/debugにマウントされており、トレーシングオプションがカーネルに正しく設定されていると仮定します。また、PCLツール（tools/perf）がインストールされ、PATHに含まれているとします。

2. 利用可能なイベントの一覧¶

2.1 標準的なユーティリティ¶

すべてのイベントは/sys/kernel/debug/tracing/eventsから確認できます。単純に以下のコマンドを実行するだけで、利用可能なイベント数を把握できます。

$ find /sys/kernel/debug/tracing/events -type d

will give a fair indication of the number of events available.

2.2 PCL（Linux用パフォーマンスカウンタ）¶

perfツールを使用することで、すべてのカウンタおよびイベント（トレースポイントを含む）の発見と列挙が可能です。利用可能なイベントの一覧を取得するには、以下のコマンドを実行するだけで十分です。

$ perf list 2>&1 | grep Tracepoint
ext4:ext4_free_inode                     [Tracepoint event]
ext4:ext4_request_inode                  [Tracepoint event]
ext4:ext4_allocate_inode                 [Tracepoint event]
ext4:ext4_write_begin                    [Tracepoint event]
ext4:ext4_ordered_write_end              [Tracepoint event]
[ .... remaining output snipped .... ]

3. イベントの有効化¶

3.1 システム全体でのイベント有効化¶

参照 イベントトレース システム全体でのイベント有効化の詳細については、以下の例のようにすべてのページ割当に関連するイベントを有効にすることができます。

$ for i in `find /sys/kernel/debug/tracing/events -name "enable" | grep mm_`; do echo 1 > $i; done

3.2 SystemTapを用いたシステム全体でのイベント有効化¶

SystemTapでは、kernel.trace()関数呼び出しを使用してトレースポイントにアクセスできます。以下の例は、5秒ごとにページを割当てるプロセスを報告するものです。

global page_allocs

probe kernel.trace("mm_page_alloc") {
      page_allocs[execname()]++
}

function print_count() {
      printf ("%-25s %-s\n", "#Pages Allocated", "Process Name")
      foreach (proc in page_allocs-)
              printf("%-25d %s\n", page_allocs[proc], proc)
      printf ("\n")
      delete page_allocs
}

probe timer.s(5) {
        print_count()
}

3.3 PCLを用いたシステム全体でのイベント有効化¶

-aスイッチを指定し、スリープを分析することで、特定の時間範囲におけるシステム全体のイベントを調査できます。

$ perf stat -a \
       -e kmem:mm_page_alloc -e kmem:mm_page_free \
       -e kmem:mm_page_free_batched \
       sleep 10
Performance counter stats for 'sleep 10':

          9630  kmem:mm_page_alloc
          2143  kmem:mm_page_free
          7424  kmem:mm_page_free_batched

  10.002577764  seconds time elapsed

同様に、シェルを実行して任意のタイミングで終了させることで、その時点でのレポートを取得することも可能です。

3.4 ローカルでのイベント有効化¶

ftrace - 関数トレーサー set_ftrace_pidを使用して、スレッド単位でイベントを有効化する方法を説明しています。

3.5 PCLを用いたローカルでのイベント有効化¶

PCLを使用して、プロセスの実行中にローカルでイベントを有効化し、追跡する方法です。

$ perf stat -e kmem:mm_page_alloc -e kmem:mm_page_free \
               -e kmem:mm_page_free_batched ./hackbench 10
Time: 0.909

  Performance counter stats for './hackbench 10':

        17803  kmem:mm_page_alloc
        12398  kmem:mm_page_free
         4827  kmem:mm_page_free_batched

  0.973913387  seconds time elapsed

4. イベントフィルタリング¶

ftrace - 関数トレーサー ftraceでイベントをフィルタリングする方法について詳しく説明しています。grepやawkによるtrace_pipeの処理、またはtrace_pipeを読み取るスクリプトの使用も可能です。

5. PCLを用いたイベントの変異分析¶

どのワークロードでも実行ごとに変動があり、標準偏差を把握することが重要です。一般的には、これはパフォーマンス分析者が手動で行う必要があります。ただし、離散的なイベント発生がパフォーマンス分析者にとって有用な場合、perfツールを使用できます。

$ perf stat --repeat 5 -e kmem:mm_page_alloc -e kmem:mm_page_free
                      -e kmem:mm_page_free_batched ./hackbench 10
Time: 0.890
Time: 0.895
Time: 0.915
Time: 1.001
Time: 0.899

 Performance counter stats for './hackbench 10' (5 runs):

        16630  kmem:mm_page_alloc         ( +-   3.542% )
        11486  kmem:mm_page_free          ( +-   4.771% )
         4730  kmem:mm_page_free_batched  ( +-   2.325% )

  0.982653002  seconds time elapsed   ( +-   1.448% )

いくつかの高レベルのイベントが、いくつかの個別イベントの集約に依存する場合、スクリプトを開発する必要があります。

–repeatを使用することで、-aとsleepを用いて、システム全体でのイベントの時間変化を確認できます。

$ perf stat -e kmem:mm_page_alloc -e kmem:mm_page_free \
              -e kmem:mm_page_free_batched \
              -a --repeat 10 \
              sleep 1
Performance counter stats for 'sleep 1' (10 runs):

         1066  kmem:mm_page_alloc         ( +-  26.148% )
          182  kmem:mm_page_free          ( +-   5.464% )
          890  kmem:mm_page_free_batched  ( +-  30.079% )

  1.002251757  seconds time elapsed   ( +-   0.005% )

6. 補助スクリプトを用いた高レベルの分析¶

イベントが有効になると、イベントがトリガーされた内容は、/sys/kernel/debug/tracing/trace_pipeから人間が読みやすい形式で読み取れます（バイナリ形式のオプションも存在します）。出力結果を後処理することで、適切なタイミングでオンラインで追加情報を収集できます。後処理の例としては、

  • トリガーされたイベントのPIDに関する情報を/procから読み取る

  • 複数の低レベルイベントから高レベルのイベントを導出する

  • 2つのイベント間のレイテンシーを計算する

Documentation/trace/postprocess/trace-pagealloc-postprocess.plは、trace_pipeをSTDINまたはトレースのコピーから読み取る例のスクリプトです。オンラインで使用する場合、1回中断するとレポートを生成して終了せず、2回中断すると終了します。

単純にスクリプトはSTDINを読み込みイベントをカウントしますが、さらに以下の処理も行えます、例えば

  • 多数の低レベルイベントから高レベルのイベントを導出します。複数のページがCPUごとのリストからメインアロケータに解放された場合、それらを1つのCPUごとのドレインとして認識します（そのイベントに特有のトレースポイントは存在しません）

  • PIDまたは個々のプロセス番号に基づいて集約できます

  • メモリが外部的にフラグメント化されている場合、フラグメント化イベントが深刻か中程度かを報告します。

  • PIDに関するイベントを受信する際、そのプロセスの親プロセスを記録できます。これにより、非常に短命なプロセスからの多数のイベントが発生している場合、すべてのヘルパーを生成した親プロセスを特定できます。

7. PCLを用いた低レベルの分析¶

また、プログラム内のどの関数がカーネル内でイベントを生成しているかを特定する必要がある場合もあります。このような分析を開始するには、データを記録する必要があります。執筆時点では、これにはroot権限が必要です：

$ perf record -c 1 \
      -e kmem:mm_page_alloc -e kmem:mm_page_free \
      -e kmem:mm_page_free_batched \
      ./hackbench 10
Time: 0.894
[ perf record: Captured and wrote 0.733 MB perf.data (~32010 samples) ]

イベントサンプリングの期間を設定するための'-c 1'の使用を注意してください。デフォルトのサンプリング期間はオーバーヘッドを最小限に抑えるために非常に長いですが、結果として収集される情報は非常に粗くなります。

この記録はperf.dataというファイルを出力し、perf reportを使用して解析できます。

$ perf report
# Samples: 30922
#
# Overhead    Command                     Shared Object
# ........  .........  ................................
#
    87.27%  hackbench  [vdso]
     6.85%  hackbench  /lib/i686/cmov/libc-2.9.so
     2.62%  hackbench  /lib/ld-2.9.so
     1.52%       perf  [vdso]
     1.22%  hackbench  ./hackbench
     0.48%  hackbench  [kernel]
     0.02%       perf  /lib/i686/cmov/libc-2.9.so
     0.01%       perf  /usr/bin/perf
     0.01%       perf  /lib/ld-2.9.so
     0.00%  hackbench  /lib/i686/cmov/libpthread-2.9.so
#
# (For more details, try: perf report --sort comm,dso,symbol)
#

このことから、VDSO内のイベントによってトリガーされるイベントはほぼすべてです。シンプルなバイナリではこれはよくあることなので、少し異なる例を見てみましょう。この文章を書いている過程で、Xが膨大なページ割当を生成していることに気づきました。それを見てみましょう：

$ perf record -c 1 -f \
              -e kmem:mm_page_alloc -e kmem:mm_page_free \
              -e kmem:mm_page_free_batched \
              -p `pidof X`

数秒後に中断され、

$ perf report
# Samples: 27666
#
# Overhead  Command                            Shared Object
# ........  .......  .......................................
#
    51.95%     Xorg  [vdso]
    47.95%     Xorg  /opt/gfx-test/lib/libpixman-1.so.0.13.1
     0.09%     Xorg  /lib/i686/cmov/libc-2.9.so
     0.01%     Xorg  [kernel]
#
# (For more details, try: perf report --sort comm,dso,symbol)
#

したがって、ほぼ半数のイベントがライブラリ内で発生しています。どのシンボルに関連しているかを把握するためには、

$ perf report --sort comm,dso,symbol

# Overhead  Command                            Shared Object  Symbol

     0.01%     Xorg  /opt/gfx-test/lib/libpixman-1.so.0.13.1  [.] get_fast_path

アセンブリ注釈¶

著作権 (c) 2017-2019 Jiri Slaby

このドキュメントは、アセンブリ言語におけるデータおよびコードの注釈に使用される新しいマクロについて説明しています。特に、以下の情報について記載しています SYM_FUNC_START, SYM_FUNC_END, SYM_CODE_START、および類似のものです。

理由¶

エントリーやジャンプテーブル、ブートコードなどの一部のコードはアセンブリ言語で記述する必要があります。C言語と同様に、このようなコードは関数にグループ化され、データとともに記述されます。標準的なアセンブリツールは、これらのコードを正確にコード、データ、または長さを指定する必要はありません。しかし、アセンブリツールは開発者にこのような注釈を提供し、デバッグツールの支援を目的としています。さらに、開発者は一部の関数を グローバル としてマークし、その翻訳単位の外で参照可能にする必要があります。

時間とともに、Linux カーネルはさまざまなプロジェクト（例: binutils）からマクロを導入し、このような注釈を簡便化するための手段として採用してきました。そのため、歴史的な理由から、開発者は ENTRY, END, ENDPROC、および他の注釈をアセンブリ言語で使用してきました。しかし、ドキュメンテーションの欠如により、これらのマクロはいくつかの場所で誤った文脈で使用されています。明らかに、 ENTRY はグローバルなシンボル（データまたはコードを問わず）の開始を示すために意図されていました。 END はデータの終わりまたは非標準のコール・コントラクトを持つ特殊な関数の終わりを 非標準 でマークしていました。一方で、 ENDPROC は標準的な関数の終わりのみを注釈すべきです。 標準 関数の終わりを注釈する必要があります。

これらのマクロが正しく使用されると、アセンブリツールがサイズと型が正しく設定された良いオブジェクトを生成できるようになります。例えば、 arch/x86/lib/putuser.S:

Num:    Value          Size Type    Bind   Vis      Ndx Name
 25: 0000000000000000    33 FUNC    GLOBAL DEFAULT    1 __put_user_1
 29: 0000000000000030    37 FUNC    GLOBAL DEFAULT    1 __put_user_2
 32: 0000000000000060    36 FUNC    GLOBAL DEFAULT    1 __put_user_4
 35: 0000000000000090    37 FUNC    GLOBAL DEFAULT    1 __put_user_8

の結果は、デバッグ目的だけでなく、このような適切に注釈されたオブジェクトに対してツールを実行することでより有用な情報を得ることができます。特に、適切に注釈されたオブジェクトに対して、 objtool が実行され、必要に応じてオブジェクトをチェック・修正できます。現在、 objtool は関数内でフレームポインタの設定/解除が欠如している場合を報告できます。また、ほとんどのコードに対して自動的に注釈を生成することもできます。 ORC unwinder これらは、信頼性の高いスタックトレースをサポートするために特に重要であり、それが逆に カーネル・ライブパッチング.

注意事項と議論¶

ある読者であれば気づくかもしれませんが、これまでにしか使われていないマクロは3つしかありません。これは確かにすべてのケースの組み合わせをカバーするには不十分です：

  • 標準/非標準関数

  • コード/データ

  • グローバル/ローカルシンボル

ある 議論 があり、現在の ENTRY/END* マクロを拡張するのではなく、新たにマクロを導入することに決定しました：

So how about using macro names that actually show the purpose, instead
of importing all the crappy, historic, essentially randomly chosen
debug symbol macro names from the binutils and older kernels?

マクロの説明¶

新しいマクロは SYM_ プレフィックスで始まり、大きく3つのグループに分類されます：

  1. SYM_FUNC_* – Cライクの関数に注釈をつける。これは標準的なCの呼び出し規約を持つ関数を指す。たとえばx86では、スタックに予定された場所にリターンアドレスが存在し、関数から標準的な方法でリターンできるようにする。フレームポインタが有効な場合、関数の開始/終了時にフレームポインタの保存/復元を行う必要がある。

    チェックツールなど objtool はこれらのマーキングされた関数がこれらのルールに準拠していることを保証すべきである。ツールはまた、デバッグ情報（例えば ORCデータ)を自動的にこれらの関数に注釈をつけることもできる。

  2. SYM_CODE_* – 特別なスタックで呼ばれる特殊な関数。割込みハンドラなどの特別なスタック内容を持つ関数、ジャンプボード、またはスターティング関数などである。

    チェックツールはこれらの関数のチェックを主に無視するが、一部のデバッグ情報は自動的に生成される。正しいデバッグデータを得るには、開発者が提供するヒント（例えば UNWIND_HINT_REGS ）が必要である。

  3. SYM_DATA* – 明らかに .data セクションに属するデータであり、 .textセクションに属さないデータである。データは命令を含まないため、ツールは特別に扱う必要がある：命令として扱ったり、デバッグ情報を割り当てたりしてはならない。

命令マクロ¶

このセクションでは上記で列挙した SYM_FUNC_* および SYM_CODE_* をカバーする。

objtool はすべてのコードがELFシンボルに含まれることを要求する。プレフィックスが付いたシンボル名はシンボルテーブルのエントリを生成しない。 .L プレフィックス付きシンボルはコード領域内で使用できるが、 .L 注釈を介してコード範囲を表すには避けたほうがよい。 SYM_*_START/END は、

  • SYM_FUNC_START および SYM_FUNC_START_LOCAL が最も一般的なマーキングである。これらは標準的な呼び出し規約を持つ関数（グローバルおよびローカル）に使用され、Cと同様にアーキテクチャ固有の バイトに合わせて関数をアライメントする。特殊なケースでは開発者がこの暗黙のアライメントを望まない場合のために、の変異形も提供されている。 __ALIGN マーキングはまた、Cの _NOALIGN 属性に相当するアセンブリの対応物として提供されている。

    SYM_FUNC_START_WEAK および SYM_FUNC_START_WEAK_NOALIGN これらすべての は と組み合わせて使用する必要がある。まず、これは命令列を関数としてマークし、生成されたオブジェクトファイルのサイズを計算する。次に、ツールがオブジェクトファイルの正確な関数境界を簡単に見つけることができるので、チェックおよび処理が容易になる。

    したがって、ほとんどの場合、開発者は次の例のように、マクロの間にアセンブリ命令を挟んで記述する必要がある: 実際、この種の注釈は現在非推奨となった マクロに相当する。 SYM_FUNC_ENDは、1つの関数に複数の名前を割り当てるために使用される。典型的な用途は:

    この例では、1つ目の関数を

    SYM_FUNC_START(memset)
    ... asm insns ...
SYM_FUNC_END(memset)

    で呼び出すことができる。 ENTRY および ENDPROC は、複数の名前で1つの関数を表すために使用される。典型的な用途は:

  • SYM_FUNC_START_ALIAS および SYM_FUNC_START_LOCAL_ALIAS この例では、1つ目の関数を

    SYM_FUNC_START_ALIAS(__memset)
SYM_FUNC_START(memset)
    ... asm insns ...
SYM_FUNC_END(memset)
SYM_FUNC_END_ALIAS(__memset)

    で呼び出すことができる。 __memset または memset 同じ結果になりますが、インストラクションのデバッグ情報はオブジェクトファイルに1回だけ生成され、非-ALIAS ケースです。

  • SYM_CODE_START および SYM_CODE_START_LOCAL 特殊なケースでのみ使用すべきです – 自分が何をやっているかわかっている場合に限ります。これは、Cの呼び出し規約でない中断ハンドラや類似の用途にのみ使用されます。 _NOALIGN 変異体も存在します。使用方法は以下の FUNC カテゴリと同じです：

    SYM_CODE_START_LOCAL(bad_put_user)
    ... asm insns ...
SYM_CODE_END(bad_put_user)

    また、すべての SYM_CODE_START* 実際、この種の注釈は現在非推奨となった 結合される SYM_CODE_END.

    ある程度、このカテゴリは非推奨 ENTRY および END。ただし END 他の意味も持っていました。

  • SYM_INNER_LABEL* これは、いくつかの内部のラベルを表すために使用されます。 SYM_{CODE,FUNC}_START および SYM_{CODE,FUNC}_END。これらはCのラベルと非常に似ていますが、グローバルにできる点が異なります。使用例：

    SYM_CODE_START(ftrace_caller)
    /* save_mcount_regs fills in first two parameters */
    ...

SYM_INNER_LABEL(ftrace_caller_op_ptr, SYM_L_GLOBAL)
    /* Load the ftrace_ops into the 3rd parameter */
    ...

SYM_INNER_LABEL(ftrace_call, SYM_L_GLOBAL)
    call ftrace_stub
    ...
    retq
SYM_CODE_END(ftrace_caller)

データマクロ¶

インストラクションと同様に、アセンブリでデータを記述するためのいくつかのマクロがあります。

  • SYM_DATA_START および SYM_DATA_START_LOCAL 特定のデータの開始を示し、以下のいずれかと併用して使用する必要があります。 SYM_DATA_END（sleepable RCU）が導入されました。 SYM_DATA_END_LABEL後者は終端にもラベルを追加するため、人々が使用できるようにします。 lstack および（ローカル） lstack_end 次の例では：

    SYM_DATA_START_LOCAL(lstack)
    .skip 4096
SYM_DATA_END_LABEL(lstack, SYM_L_LOCAL, lstack_end)

  • SYM_DATA および SYM_DATA_LOCAL は、シンプルで、主に1行のデータ用の変異体です：

    SYM_DATA(HEAP,     .long rm_heap)
SYM_DATA(heap_end, .long rm_stack)

    結局、これらは SYM_DATA_START with SYM_DATA_END 内部的に展開されます。

サポートマクロ¶

上記のすべては、いくつかの呼び出しに帰着します。 SYM_START, SYM_END（sleepable RCU）が導入されました。 SYM_ENTRY 最後に。通常、開発者はこれらを使用すべきではありません。

さらに、上記の例では、以下のような SYM_L_LOCAL。また、 SYM_L_GLOBAL および SYM_L_WEAK。これらすべては、それらによってマークされたシンボルのリンクを示すために意図されています。これらは、以下のいずれかで使用されます。 _LABEL 以前のマクロの変異体、または SYM_START.

オーバーライドマクロ¶

アーキテクチャは、自前の asm/linkage.h、シンボルのタイプを指定するマクロを含むSYM_T_FUNC, SYM_T_OBJECT, and SYM_T_NONE）。このファイルで記述されているすべてのマクロは、 #ifdef + #endif、上記のアーキテクチャ依存のヘッダでマクロを異なる方法で定義するだけで十分です。

はじめに¶

このドキュメントはLinux/390における共通デバイスサポートルーチンについて説明しています。他のハードウェアアーキテクチャと異なり、ESA/390は統一されたI/Oアクセスメソッドを定義しています。これにより、デバイスドライバはバスタイプの違いやポーリング versus インターナル処理、共有 versus 非共有の割込み処理、DMA versus ポートI/O（PIO）などのハードウェア機能を扱う必要がありません。ただし、これはすべてのデバイスドライバがハードウェアI/O接続機能を自前で実装する必要があるか、またはオペレーティングシステムが統一的なハードウェアアクセスメソッドを提供し、すべての機能をドライバが実装する必要があることを意味します。

このドキュメントはESA/390ハードウェアアーキテクチャの詳細な説明は行いません。その情報はESA/390 Principles of Operationマニュアル（IBM Form. No. SA22-7201）から取得可能です。

ESA/390 I/Oインターフェースの共通デバイスサポートを構築するため、汎用的なI/Oアクセスメソッドをハードウェアに提供する機能層が導入されました。

共通デバイスサポート層は以下のI/Oサポートルーチンを含みます。一部は一般的なLinuxデバイスドライバインターフェースを実装しており、一部はESA/390プラットフォーム固有のものです。

注意:

S/390用のドライバを書くには、以下のインターフェースも確認する必要があります S/390ドライバモデルインターフェース.

2.4から移植する際の注意点:

主な変更点は以下の通りです:

  • 関数はirq（サブチャネル）ではなくccw_deviceを使用します。

  • すべてのドライバはccw_driver（driver-model.txtを参照）を定義し、関連する関数を定義する必要があります。

  • request_irq() および free_irq() ドライバが実行する必要はありません。

  • oper_handlerは（ほぼ）ccw_driverのprobe()およびset_online()関数に置き換えられます。

  • not_oper_handlerは（ほぼ）ccw_driverのremove()およびset_offline()関数に置き換えられます。

  • チャネルデバイス層は廃止されました。

  • 割込みハンドラはccw_deviceを引数として使用する必要があります。さらに、devstatを返すのではなくirbを返します。

  • I/Oを開始する前に、オプションは以下の関数で設定する必要があります ccw_device_set_options().

  • read_dev_chars()/read_conf_data()の呼び出しではなく、ドライバがチャネルプログラムを発行し、割込みを自前で処理します。

do_IRQ()

汎用的な割り込みルーチンです。この関数は、I/O割り込みがシステムに提示された際、割り込みエントリールーチンから呼び出されます。do_IRQ()ルーチンは割り込みステータスを判定し、do_IO()で定義されたルール（フラグ）に従ってデバイス固有の割り込みハンドラを呼び出します。

次の章では、do_IRQ()以外の関数について詳しく説明します。do_IRQ()インターフェースは、Linux/390の第一レベル割り込みハンドラからのみ呼び出されるため、デバイスドライバが呼び出せるインターフェースではありません。代わりに、do_IO()の機能説明では、デバイス固有の割り込みハンドラへの入力も説明されています。

Linux/390デバイスドライバ用の共通デバイスサポート（CDS）¶

General Information¶

次の章では、Linux/390共通デバイスサポート（CDS）が提供するI/O関連インターフェースルーチンについて説明します。これにより、IBM ESA/390ハードウェアプラットフォーム上でデバイス固有のドライバ実装が可能になります。これらのインターフェースは、ESA/390プラットフォーム上で特定のハードウェアデバイスを駆動するために必要な機能を提供することを目的としています。一部のインターフェースはLinux/390固有であり、他のLinuxプラットフォームでも利用可能なインターフェースもあります。その他の関数プロトタイプ、データ宣言、マクロ定義は、アーキテクチャ固有のCヘッダーファイルlinux/arch/s390/include/asm/irq.hに記述されています。

CDSインターフェース概念の概要¶

他のハードウェアプラットフォームと異なり、ESA/390アーキテクチャは特定の割り込みコントローラーおよびバスシステムによって管理される割り込みラインを定義していません。共有割り込み、DMA処理など、割り込みの共有が可能かどうかはプラットフォームにより異なります。代わりに、ESA/390アーキテクチャは、システムに物理的に接続されたデバイスの統一的なビューを提供する「チャネルサブシステム」を実装しています。ESA/390ハードウェアプラットフォームは、ディスクデバイス（DASDを含む）、テープ、通信コントローラーなど、さまざまな周辺機器をサポートしていますが、これらはすべて明確に定義されたアクセスメソッドでアクセスされ、I/O完了は統一的な方法（I/O割り込み）で提示されます。すべてのデバイスは、システムに対して一意のサブチャネルによって識別されます。ESA/390アーキテクチャでは、最大64kのデバイスが接続可能です。

Linuxは最初、Intel PCアーキテクチャ上で構築され、2つの連続した8259プログラマブル割込み制御器(PIC)を備えており、最大15の異なる割込みラインを提供します。このようなシステムに接続されたすべてのデバイスは、これらの15の割込みレベルを共有します。ISAバスシステムに接続されたデバイスは、割込みレベル（IRQ）を共有してはいけません（ISAバスはエッジトリガー割込みを基盤としています）。MCA、EISA、PCIなどのバスシステムはレベルトリガー割込みを基盤としており、これにより共有IRQが可能になります。ただし、複数のデバイスが同じ（共有）IRQでハードウェア状態を提示する場合、オペレーティングシステムはこのIRQに登録されたすべてのデバイスドライバーを呼び出して、割込みを発生させたデバイスを所有するドライバーを特定する必要があります。

カーネル2.4以前では、Linux/390はIRQ（サブチャネル）を介してインターフェースを提供していました。共通I/Oレイヤーの内部利用にはこれらはまだ存在しますが、デバイスドライバーはccw_device経由の新しい呼び出しインターフェースを使用すべきです。

起動中にLinux/390システムは周辺デバイスを検出します。これらのデバイスはESA/390チャネルサブシステムによって一意に定義されるサブチャネルによって識別されます。サブチャネル番号はシステムが生成しますが、各サブチャネルはユーザー定義属性であるデバイス番号も持ちます。サブチャネル番号とデバイス番号はともに65535を超えてはなりません。sysfsの初期化中に、制御ユニットタイプや特定のI/Oコマンド（チャネルコマンドワード-CCW）を実行するデバイスタイプに関する情報が収集されます。デバイスドライバーは初期化ステップでこのハードウェア情報セットを取得し、保存された情報に基づいてサポートするデバイスを認識します。 struct ccw_device これにより、Linux/390は自由な（未武装）割込み要求ライン（IRQ）をスキャンする必要がありません。必要に応じて、デバイスドライバーはオンラインルーチンでREAD DEVICE CHARACTERISTICS ccwを実行してデバイス特性を取得できます。

I/Oの簡単な開始を可能にするため、CDSレイヤーは ccw_device_start() デバイス固有のチャネルプログラム（1つ以上のCCW）を入力として受け取り、必要なアーキテクチャ固有の制御ブロックを設定し、デバイスドライバーの代わりにI/Oリクエストを開始するインターフェースを提供します。この ccw_device_start() ルーチンは、CDSレイヤーが観測するすべての割込みでデバイスドライバーを通知するか、最終状態のみ通知するかを指定できます。参照してください ccw_device_start() 詳細については、以下の説明を参照してください。デバイスドライバーはESA/390 I/Oコマンドを直接発行してはならないが、Linux/390 CDSインターフェースを使用する必要があります。

長時間実行されるI/Oリクエストをキャンセルするため、CDSレイヤーは以下の機能を提供します。 ccw_device_halt() 一部のデバイスは、未完了のI/Oリクエストを発生させることなく、最初にHALT SUBCHANNEL (HSCH)コマンドを発行する必要があります。この機能も ccw_device_halt().

ccw_device_start() - Initiate I/O Request

以下の ccw_device_start() ルーチンはI/Oリクエストのフロントエンドプロセッサです。すべてのデバイスドライバーI/Oリクエストはこのルーチンを使用して発行する必要があります。デバイスドライバーはESA/390 I/Oコマンドを直接発行してはなりません。代わりに、 ccw_device_start() ルーチンは、任意のデバイスを駆動するために必要なすべてのインターフェースを提供します。

使用注意:

ccw_device_start() 無効にしてCCWデバイスロックを保持した状態で呼び出さなければなりません。

デバイスドライバーは、その割込みハンドラ内で次の呼び出しをすでに実行できます。ボトムハーフをスケジュールする必要はありませんが、非決定的に長時間かかるエラー回復手順などの場合を除いては。I/O処理中にLinux/390汎用I/OデバイスドライバサポートはすでにIRQロックを取得しているため、ハンドラが呼び出す際には再度ロックを取得してはいけません ccw_device_start() 、それによりデッドロック状態に陥ります！ ccw_device_start() デバイスドライバーが次のI/Oリクエストを開始する前に現在のI/Oリクエストが完了することを依存している場合、CCW_CMD_NOOPというNoOp I/Oコマンドを提出されたCCWチェインの末尾にチェインすることでI/O処理オーバーヘッドを削減できます。これによりチャネル終了とデバイス終了のステータスが単一の割込みで同時に提示されます。ただし、この技術は注意深く使用する必要があります。なぜなら、チャネルがビジー状態のままになり、同じチャネル上の他のデバイスのI/Oリクエストを処理できなくなるからです。したがって、読み取りコマンドなどはこの技術を用いてはいけません。なぜなら、結果はすでに単一の割込みで提示されるからです。

I/Oオーバーヘッドを最小限に抑えるため、デバイスドライバーはデバイスがデバイス終了前に中間割込み情報を報告できる場合に限りDOIO_REPORT_ALLを使用すべきです。この場合、すべてのI/O割込みがデバイスドライバーに提示され、最終ステータスが認識されるまで続きます。

デバイスが非同期的に提示されたI/Oエラーから回復できる場合、DOIO_EARLY_NOTIFICATIONフラグを使用してオーバーラップI/Oを実行できます。一部のデバイスは常にチャネル終了とデバイス終了を単一の割込みで報告しますが、他のデバイスはチャネルが次のI/Oリクエストを待機できるときにチャネル終了の主なステータスを提示し、データ送信が完了したときにデバイス終了の副次的なステータスを提示します。

デバイスが非同期的に提示されたI/Oエラーから回復できる場合、DOIO_EARLY_NOTIFICATIONフラグを使用してオーバーラップI/Oを実行できます。一部のデバイスは常にチャネル終了とデバイス終了を単一の割込みで報告しますが、他のデバイスはチャネルが次のI/Oリクエストを待機できるときにチャネル終了の主なステータスを提示し、データ送信が完了したときにデバイス終了の副次的なステータスを提示します。

上記のフラグにより、この機能を活用することが可能で、例えばネットワークでデータの喪失を処理できる通信デバイスにおいて、I/O処理の向上を実現できます。

チャネルサブシステムがいつでも二次ステータス割込みを提示しない限り、この機能を活用するとオーバーラップI/Oが実行される間、主ステータス割込みのみがデバイスドライバに提示されます。二次ステータス（エラーなし、アラートステータス）が提示された場合、これは最後の二次ステータス（最終ステータス）以降に送出されたすべてのオーバーラップリクエストの成功完了を示します。 ccw_device_start() 二次ステータス（エラーなし、アラートステータス）が提示された場合、これは最後の二次ステータス（最終ステータス）以降に送出されたすべてのオーバーラップリクエストの成功完了を示します。

チャネルプログラムがチャネルコマンドワード（CCW）のスリープフラグを設定する意図がある場合、DOIO_ALLOW_SUSPENDオプションでI/O操作を開始する必要があります。チャネルプログラムがスリープ状態になると、チャネルサブシステムが中間割込みを生成します。

ccw_device_resume() - チャネルプログラムの実行を再開

デバイスドライバが特定のCCWのCCWスリープフラグを設定して現在のチャネルプログラム実行を一時停止した場合、チャネルプログラムの実行は停止します。チャネルプログラムの実行を再開するには、CIOレイヤーが提供する ccw_device_resume() ルーチン。

int ccw_device_resume(struct ccw_device *cdev);

cdev

再開操作が求められたccw_device

以下の ccw_device_resume() 関数の戻り値:

0

停止中のチャネルプログラムが再開されます

-EBUSY

ステータス待機中

-ENODEV

cdevが無効または非運用サブチャネル

-EINVAL

再開機能は適用できません

-ENOTCONN

完了待機中のI/Oリクエストはありません

使用注意:

詳細については、 ccw_device_start() 使用注意を参照してください。

ccw_device_halt() - I/Oリクエスト処理を停止

時折、デバイスドライバが長時間実行されるチャネルプログラムの処理を停止する必要があるか、デバイスが最初にhaltサブチャネル（HSCH）I/Oコマンドを送出する必要がある場合があります。このような用途のために、 ccw_device_halt() コマンドが提供されています。

ccw_device_halt() 無効にしてCCWデバイスロックを保持した状態で呼び出さなければなりません。

int ccw_device_halt(struct ccw_device *cdev,
                    unsigned long intparm);

cdev

停止操作が求められたccw_device

intparm

中断パラメータ；I/Oが進行中でない場合のみ使用される値、それ以外の場合はI/Oリクエストに関連するintparmが返されます

以下の ccw_device_halt() 関数の戻り値:

0

リクエストが正常に開始されました

-EBUSY

デバイスが現在ビジー中、またはステータス待機中です。

-ENODEV

cdevが無効です。

-EINVAL

デバイスが運用可能でない、またはccwデバイスがオンラインでない状態です。

使用注意:

デバイスドライバーは、チャネルプログラムが終了時に転送チャネル（TIC）コマンド（CCW_CMD_TIC）により開始部に戻る無限ループのチャネルプログラムを書き込むことができます。通常、ネットワークデバイスドライバーはPCI CCWフラグ（CCW_FLAG_PCI）を設定することによりこの処理を行います。このCCWが実行されると、プログラム制御割込み（PCI）が生成されます。その後、デバイスドライバーは適切なアクションを実行できます。ネットワークデバイスへの Outstanding Read 割込み（PCIフラグありまたはなし）の前には、 ccw_device_halt() 待機中の操作を終了させる必要があります。

ccw_device_clear() - Terminage I/O Request Processing

サブチャネルでのすべてのI/O処理を終了させるには、クリアサブチャネル（CSCH）コマンドを使用します。これは ccw_device_clear().

ccw_device_clear() 無効にしてCCWデバイスロックを保持した状態で呼び出さなければなりません。

int ccw_device_clear(struct ccw_device *cdev, unsigned long intparm);

cdev

ccw_device でクリア操作が要求される

intparm

割込みパラメータ（参照 ccw_device_halt())

以下の ccw_device_clear() 関数の戻り値:

0

リクエストが正常に開始されました

-ENODEV

cdev 無効

-EINVAL

デバイスが運用可能でない、またはccwデバイスがオンラインでない状態です。

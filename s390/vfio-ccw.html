vfio-ccw: 基本的なインフラストラクチャ¶

はじめに¶

ここでは、Linux/s390用のI/Oサブチャネルデバイスに対するvfioのサポートについて説明します。vfio-ccwの動機は、仮想マシンにサブチャネルを透過することであり、vfioがその手段です。

他のハードウェアアーキテクチャとは異なり、s390では統合されたI/Oアクセスメソッドが定義されており、これをチャネルI/Oと呼びます。これは独自のアクセスパターンを持ちます：

  • チャネルプログラムは、別個の（共通）プロセッサ上で非同期に実行されます。

  • チャネルサブシステムは、チャネルプログラムで呼び出し元が指定した任意のメモリを直接アクセスします。つまり、IOMMUは関与しません。

したがって、これらのデバイスに対するvfioサポートを導入する際には、mediated device（mdev）実装で実現します。vfio mdevはiommuグループに追加され、vfioフレームワークによって管理可能になります。また、特殊なvfio I/O領域に対して読み書きコールバックを追加し、mdevから親デバイス（実際のI/Oサブチャネルデバイス）にチャネルプログラムを渡して、さらにアドレス変換を行いI/O指令を実行します。

このドキュメントはs390 I/Oアーキテクチャの詳細な説明は意図していません。より詳しい情報や参照は以下をご覧ください：

  • チャネルI/Oの一般的な理解のための良い出発点： https://en.wikipedia.org/wiki/Channel_I/O

  • s390アーキテクチャ: s390 Principles of Operationマニュアル（IBM Form. No. SA22-7832）

  • 既存のQEMUコードで実装されたシンプルなエミュレートチャネルサブシステムも、良い参照になります。これにより、フローを追跡しやすくなります。qemu/hw/s390x/css.c

vfio mediated deviceフレームワーク: - VFIO メディエイテッドデバイス

vfio-ccwの動機¶

通常、s390でQEMU/KVMを介して仮想化されたゲストは、「Virtio Over Channel I/O（virtio-ccw）」トランスポート経由でパラバーチャライズドなvirtioデバイスを認識します。これにより、チャネルデバイスの標準OSアルゴリズムでvirtioデバイスを検出可能になります。

しかし、これだけでは不十分です。s390で標準のチャネルI/Oベースメカニズムを使用するほとんどのデバイスにおいて、QEMU仮想マシンに透過させる機能も必要です。これは、virtio対応がないデバイス（例：テープドライブ）や、ゲストが利用したい特定の特性を持つデバイスも含まれます。

デバイスをゲストに透過させる際には、他のすべてのデバイスと同じインターフェース、つまりvfioを使用したいです。これを実現するため、チャネルデバイスのvfioサポートはvfio mediated deviceフレームワークとサブチャネルデバイスドライバー「vfio_ccw」を通じて実装します。

CCWデバイスのアクセスパターン¶

s390アーキテクチャは、システムに物理的に接続されているデバイスの統一されたビューを提供する「チャネルサブシステム」と呼ばれる機能を実装しています。s390ハードウェアプラットフォームは、ディスクデバイス（DASDsを含む）、テープ、通信コントローラーなど、さまざまな外付けデバイスを認識しています。これらはすべて、明確に定義されたアクセスメソッドでアクセス可能であり、I/O完了は統一された方法で提供されます：I/O割込み。

すべてのI/O操作にはチャネルコマンドワード（CCW）が必要です。CCWは、専用のI/Oチャネルプロセッサへの指令です。チャネルプログラムは、CCWのシーケンスであり、I/Oチャネルサブシステムによって実行されます。チャネルサブシステムにチャネルプログラムを実行させるには、操作要求ブロック（ORB）を構築する必要があります。ORBは、CCWの形式やその他の制御情報をシステムに伝えるための指針となります。オペレーティングシステムはSSCH（サブチャネル開始）指令を介してI/Oチャネルサブシステムにチャネズルプログラムの実行を指示します。その後、中央プロセッサはI/O指令を中断されるまで非I/O指令の処理に専念できます。I/O完了結果は、割込みハンドラによって中断応答ブロック（IRB）として取得されます。

vfio-ccwに戻ると、要約すると：

  • ORBおよびチャネルプログラムはゲストカーネル内で構築され（ゲスト物理アドレスで）、

  • ORBおよびチャネルプログラムはホストカーネルに渡されます。

  • ホストカーネルはゲスト物理アドレスを実際のアドレスに変換し、特権チャネルI/O指令（例：SSCH）を発行してI/Oを開始します。

  • チャネルプログラムは別個のプロセッサで非同期に実行されます。

  • I/O完了はI/O割込みによってホストに通知され、その後ユーザー空間にIRBとしてコピーされてゲストに返されます。

物理vfio ccwデバイスとその子mdev¶

上記のように、vfio-ccwはmdev実装によって実現されています。

チャネルI/OはIOMMUハードウェアサポートがありませんので、物理vfio ccwデバイスはIOMMUレベルの翻訳や隔離機能を持ちません。

サブチャネルI/O指令はすべて特権指令です。I/O指令の検出処理において、vfio-ccwはソフトウェアによるポリシングと翻訳を行い、チャネルプログラムがハードウェアに送信される前にその構成をチェックします。

この実装では、2種類のデバイス用に2つのドライバがあります：

  • 物理サブチャネルデバイス用のvfio_ccwドライバー。これは、実際のサブチャネルデバイス用のI/Oサブチャネルドライバーです。このドライバーは、mdevフレームワークに親（物理）デバイスとしてコールバック群とレジストレーションを実装し、提供します。その結果、mdevはvfio_ccwに対してsysfsを介した汎用的なインターフェースを提供し、mdevデバイスの作成を可能にします。vfio_ccwによってvfio mdevが作成され、mediatedバスに追加されることが可能です。これはIOMMUグループおよびvfioグループに追加されたvfioデバイスです。vfio_ccwはさらに、ユーザー空間からのチャネルプログラムリクエストを受け入れるI/O領域を提供し、ユーザー空間がI/O割込み結果を取得できるようにします。I/O完了をユーザー空間に通知するためには、イベントfd fdを設定するインターフェースを提供します。

  • 媒介されたvfio ccwデバイス用のvfio_mdevドライバー。これはmdevフレームワークによって提供されます。これはvfio_ccwによって作成されたmdev用のvfioデバイスドライバーです。このドライバーはvfioデバイスドライバーのコールバック群を実装し、自身をvfioグループに追加し、mdevフレームワークにmdevドライバーとしてレジストレーションします。これは既存のマッピングとアンマッピングioctlを用いるvfio iommuバックエンドを使用しますが、デバイスのIOMMUにプログラミングするのではなく、後続のリクエストで使用するための翻訳情報を単純に保存します。これにより、ゲスト物理アドレスでプログラミングされたデバイスは、vfioカーネルがそのアドレスをプロセス仮想アドレスに変換し、ページをピン止めし、ホスト物理アドレスでハードウェアをプログラミングする1ステップで動作します。mdevの場合、vfio iommuバックエンドはVFIO_IOMMU_MAP_DMA ioctl中にページをピン止めしません。mdevフレームワークはこの操作でiova<->vaddrマッピングのデータベースのみを維持します。さらに、物理デバイスが需要に基づいてページをピン止め・アンピンするため、vfio_pin_pagesおよびvfio_unpin_pagesインターフェースをvfio iommuバックエンドからエクスポートします。

以下にハイレベルブロック図を示します。

+-------------+
|             |
| +---------+ | mdev_register_driver() +--------------+
| |  Mdev   | +<-----------------------+              |
| |  bus    | |                        | vfio_mdev.ko |
| | driver  | +----------------------->+              |<-> VFIO user
| +---------+ |    probe()/remove()    +--------------+    APIs
|             |
|  MDEV CORE  |
|   MODULE    |
|   mdev.ko   |
| +---------+ | mdev_register_device() +--------------+
| |Physical | +<-----------------------+              |
| | device  | |                        |  vfio_ccw.ko |<-> subchannel
| |interface| +----------------------->+              |     device
| +---------+ |       callback         +--------------+
+-------------+

これらがどのように協力するかのプロセス。

  1. vfio_ccw.koは物理I/Oサブチャネルを駆動し、コールバック付きの物理デバイスをmdevフレームワークに登録します。vfio_ccwがサブチャネルデバイスをプローブする際、mdevフレームワークにデバイスポインタとコールバックを登録します。sysfsのデバイスノード下にサブチャネルデバイス用のmdev関連ファイルノードが作成されます。つまり、「mdev_create」、「mdev_destroy」、「mdev_supported_types」です。

  2. 媒介されたvfio ccwデバイスを作成します。'mdev_create' sysfsファイルを使用して、手動で1つ（この場合、1つだけ）の媒介デバイスを作成する必要があります。

  3. vfio_mdev.koはmediated ccwデバイスを駆動します。vfio_mdevはまたvfioデバイスドライバーでもあります。mdevを検出し、iommu_groupとvfio_groupに追加します。これによりゲストにmdevを透過的に提供できます。

VFIO-CCW レギオン¶

vfio-ccwドライバーは、ユーザー空間からのリクエストを受け入れ、結果を返すためのMMIOレギオンを公開します。

vfio-ccw I/Oレギオン¶

I/Oレギオンは、ユーザー空間からのチャネルプログラムリクエストを受け入れ、ユーザー空間が取得できるI/O割込み結果を保存します。このレギオンの定義は以下の通りです：

struct ccw_io_region {
#define ORB_AREA_SIZE 12
        __u8    orb_area[ORB_AREA_SIZE];
#define SCSW_AREA_SIZE 12
        __u8    scsw_area[SCSW_AREA_SIZE];
#define IRB_AREA_SIZE 96
        __u8    irb_area[IRB_AREA_SIZE];
        __u32   ret_code;
} __packed;

このレギオンは常に利用可能です。

I/Oリクエストを開始する際、orb_areaにはゲストのORBを、scsw_areaには仮想サブチャネルのSCSWを設定する必要があります。

irb_areaはI/O結果を保存します。

ret_codeはこのレギオンの各アクセスに対して戻りコードを保存します。以下の値が発生する可能性があります：

0

操作が成功しました。

-EOPNOTSUPP

orbで指定されたトランスポートモードや未識別IDAW形式、またはscswで指定された機能が開始機能以外だった場合。

-EIO

デバイスがリクエストを受け入れる準備ができていない状態だった場合、または内部エラーが発生した場合。

-EBUSY

サブチャネルがステータス保留中やビジー状態だった、またはリクエストが既にアクティブだった場合。

-EAGAIN

リクエストが処理中で、呼び出し元は再試行する必要があります。

-EACCES

I/Oに使用されたチャネルパスが運用不可能であることが判明した場合。

-ENODEV

デバイスが運用不可能であることが判明した場合。

-EINVAL

orbで指定されたチェーンが255を超えるccwだった、または内部エラーが発生した場合。

vfio-ccw コマンドレギオン¶

vfio-ccw コマンドレギオンは、ユーザー空間からの非同期指令を受け入れるために使用されます：

#define VFIO_CCW_ASYNC_CMD_HSCH (1 << 0)
#define VFIO_CCW_ASYNC_CMD_CSCH (1 << 1)
struct ccw_cmd_region {
       __u32 command;
       __u32 ret_code;
} __packed;

このレギオンは、レギオンタイプVFIO_REGION_SUBTYPE_CCW_ASYNC_CMDを介して公開されます。

現在、CLEAR SUBCHANNELおよびHALT SUBCHANNELはこのレギオンを使用しています。

commandは実行するコマンドを指定し、ret_codeはこのレギオンの各アクセスに対して戻りコードを保存します。以下の値が発生する可能性があります：

0

操作が成功しました。

-ENODEV

デバイスが運用不可能であることが判明した場合。

-EINVAL

haltまたはclear以外のコマンドが指定された場合。

-EIO

デバイスがリクエストを受け入れる準備ができていない状態でリクエストが発行された場合。

-EAGAIN

リクエストが処理中で、呼び出し元は再試行する必要があります。

-EBUSY

haltリクエストを処理中にサブチャネルがステータス保留中やビジー状態だった場合。

vfio-ccw schibレギオン¶

vfio-ccw schibレギオンは、サブチャネル情報ブロック（SCHIB）データをユーザー空間に返すために使用されます：

struct ccw_schib_region {
#define SCHIB_AREA_SIZE 52
       __u8 schib_area[SCHIB_AREA_SIZE];
} __packed;

このレギオンは、レギオンタイプVFIO_REGION_SUBTYPE_CCW_SCHIBを介して公開されます。

このレギオンを読み込むと、関連するハードウェアにSTORE SUBCHANNELが発行されます。

vfio-ccw crwレギオン¶

vfio-ccw crwレギオンは、チャネルレポートワード（CRW）データをユーザー空間に返すために使用されます：

struct ccw_crw_region {
       __u32 crw;
       __u32 pad;
} __packed;

このレギオンは、レギオンタイプVFIO_REGION_SUBTYPE_CCW_CRWを介して公開されます。

この領域を読み込むと、このサブチャネルに関連するCRW（例えば、チャネルパス状態の変化を報告しているもの）が待機中であればCRWを返し、待機していない場合はすべてゼロを返します。複数のCRWが待機中である場合（連鎖している可能性を含む）、この領域を再度読み込むと次のCRWが返されます。待機中のCRWがなくなるまでこのプロセスは続き、最終的にゼロが返されます。これはSTORE CHANNEL REPORT WORDの動作と似ています。

vfio-ccwの操作詳細¶

vfio-ccwはs390プラットフォームにおけるvfio-pciの動作を継承し、vfio-iommu-type1をvfio iommuバックエンドとして使用します。

  • CCW翻訳API グループのAPI（cp_で始まる）を使用してCCWの翻訳を行います。ユーザー空間のプログラムから渡されるCCWはゲスト物理メモリアドレスで組織化されています。これらのAPIはCCWをカーネル空間にコピーし、ゲスト物理アドレスをホスト物理アドレスに置き換えることで実行可能なカーネルチャネルプログラムを構築します。注意点として、直接アクセスのCCWでもIDALを使用する必要があります。参照されるメモリはどこにでも存在する可能性があり、2Gを超える領域にも含まれるからです。 cp_)でCCWの翻訳を行います。ユーザー空間のプログラムから渡されたCCWはゲスト物理メモリアドレスで組織化されています。これらのAPIはCCWをカーネル空間にコピーし、ゲスト物理アドレスをホスト物理アドレスに置き換えることで実行可能なカーネルチャネルプログラムを構築します。注意点として、直接アクセスのCCWでもIDALを使用する必要があります。参照されるメモリはどこにでも存在する可能性があり、2Gを超える領域にも含まれるからです。

  • vfio_ccwデバイスドライバー このドライバーはCCW翻訳APIを利用し、vfio_ccwというI/Oサブチャネルデバイスを透過的に使用するドライバーを導入します。vfio_ccwは以下のvfio ioctlsを実装します：

    VFIO_DEVICE_GET_INFO
VFIO_DEVICE_GET_IRQ_INFO
VFIO_DEVICE_GET_REGION_INFO
VFIO_DEVICE_RESET
VFIO_DEVICE_SET_IRQS

    これによりユーザー空間のプログラムがカーネルにチャネルプログラムを渡すI/O領域が提供され、実際のデバイスに送信する前にCCWの翻訳が行われます。また、SET_IRQ ioctlsによりイベント通知を設定し、I/O完了を非同期でユーザー空間のプログラムに通知します。

制限¶

現在のvfio-ccwの実装は、DASD/ECKDデバイスのブロックデバイス機能（読み込み/書き込み）を実装するために必要な基本コマンドのみをサポートしています。今後、パスグループに関連するなど一部のコマンドは特別な処理が必要になる可能性があります。

DASDは一種のストレージデバイスです。ECKDはデータ記録形式です。DASDおよびECKDに関する詳細情報は以下にあります： https://en.wikipedia.org/wiki/Direct-access_storage_device https://en.wikipedia.org/wiki/Count_key_data

QEMUでの対応作業と組み合わせることで、ゲスト内で透過的に提供されたDASD/ECKDデバイスをブロックデバイスとして利用可能にすることが出来ます。

現在のコードにより、ゲストはSTART SUBCHANNELを通じてチャネルプログラムを開始し、HALT SUBCHANNEL、CLEAR SUBCHANNEL、STORE SUBCHANNELを発行できます。

現在、すべてのチャネルプログラムがpビットの設定に関係なくプリフェッチされます。これにより、自己修正可能なチャネルプログラムはサポートされていません。このため、IPLはユーザー空間/ゲストプログラムによって特別な処理が必要であり、これはQEMU 4.1以降のs390-ccw BIOSで実装されています。

vfio-ccwは古典的（コマンドモード）のチャネルI/Oのみをサポートしています。トランスポートモード（HPF）はサポートされていません。

QDIOサブチャネルは現在サポートされていません。DASD/ECKD以外の古典的なデバイスは動作する可能性がありますが、テストされていません。

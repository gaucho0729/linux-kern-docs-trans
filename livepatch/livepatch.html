Livepatch¶

このドキュメントでは、カーネルのライブパッチングに関する基本的な情報を説明します。

1. 動機¶

ユーザーがシステムの再起動をためらう状況は多くあります。システムが複雑な科学計算を実行中であったり、ピーク利用時の重負荷下にある場合などがその例です。システムを稼働させ続けるだけでなく、安定かつセキュアな環境を維持したいというユーザーの要望に応えるため、ライブパッチングはシステム再起動をせずに機能呼び出しを再配向することで、重要な機能の修正を実現します。

2. Kprobes、Ftrace、Livepatching¶

Linuxカーネルには、コードの実行を再配向するための複数のメカニズムがあります。具体的には、カーネルプローブ、関数トレース、ライブパッチングです：

  • カーネルプローブは最も汎用性が高いメカニズムです。任意のインストラクションをブレイクポイント指令に置き換えることでコードの再配向が可能です。

  • 関数トレーサーは、関数エントリポイントに近い予め定義された場所からコードを呼び出します。この場所はコンパイラが'-pg' gccオプションを使用して生成します。

  • ライブパッチングでは、関数パラメータやスタックが何らかの形で変更される前、関数エントリの非常に初期段階でコードを再配向する必要があります。

これら3つのアプローチはすべて、実行時において既存のコードを変更する必要があります。そのため、お互いの領域を侵さないよう注意を払う必要があります。これらの問題の多くは、動的ftraceフレームワークをベースに解決されています。関数エントリをプローブする際、Kprobeはftraceハンドラとして登録されます（CONFIG_KPROBES_ON_FTRACEを参照）。また、ライブパッチから代替関数を呼び出す際には、カスタムのftraceハンドラを使用します。ただし、いくつかの制限があります（以下を参照）。

3. 一貫性モデル¶

関数はその理由があって存在します。入力パラメータを受け取り、ロックを取得または解放し、データを特定の方法で読み込み・処理・書き込みし、返却値を返します。言い換えれば、各関数には定義されたセマンティクスがあります。

多くの修正は、修正された関数のセマンティクスを変更しません。たとえば、NULLポインタや境界チェックを追加する、レース条件を修正するためのメモリバリアを追加する、またはクリティカルセクションをロックで囲むなどです。このような変更は大半が自立しており、関数はシステムの他の部分に対して同じように振る舞います。このような場合、関数は個別に更新することが可能です。

しかし、より複雑な修正方法もあります。たとえば、パッチは複数の関数におけるロックの順序を同時に変更する場合があります。あるいは、パッチはいくつかの一時的な構造体の意味を交換し、関連するすべての関数を更新する場合もあります。このような場合、影響を受けるユニット（スレッド、全体のカーネル）は、すべての新しい関数バージョンを同時に使用する必要があります。また、切り替えは安全なタイミングに限って行われるべきです。たとえば、影響を受けるロックが解放されたとき、または修正された構造体にデータが現在保存されていないときに限ります。

安全に関数を適用する方法に関する理論は比較的複雑です。目標は、いわゆる整合性モデルを定義することです。このモデルは、新しい実装がシステムの整合性を維持しながら使用できる条件を定義しようとするものです。

Livepatchは、kGraftとkpatchのハイブリッド型の整合性モデルを使用しています。これは、kGraftのタスクごとの整合性とシステムコールバリアの切り替えを組み合わせ、kpatchのスタックトレース切り替えを採用しています。また、いくつかのフォールバックオプションが用意されており、非常に柔軟性があります。

パッチは、タスクが安全に切り替わる deemed なタイミングで、タスク単位で適用されます。パッチが有効になると、livepatchはタスクがパッチ済み状態に収束する移行状態に入ります。通常、この移行状態は数秒で完了します。パッチが無効化されるときにも同様のシーケンスが発生しますが、タスクはパッチ済み状態から未パッチ状態に収束します。

割り込みハンドラは、割り込まれたタスクのパッチ済み状態を継承します。フォークされたタスク（子プロセス）についても同様に、親プロセスのパッチ済み状態を継承します。

Livepatchは、タスクをパッチするタイミングを判断するため、いくつかの補完的なアプローチを使用しています。

  1. 最も効果的なアプローチは、スリープ中のタスクのスタックチェックです。あるタスクのスタックに影響を受ける関数がなければ、そのタスクをパッチします。ほとんどの場合、最初の試行でほとんどのタスクまたはすべてのタスクをパッチできます。そうでない場合は、定期的に再試行します。このオプションは、アーキテクチャが信頼できるスタック（HAVE_RELIABLE_STACKTRACE）を持つ場合にのみ利用可能です。

  2. 必要に応じて使用される2番目のアプローチは、カーネルの終了切り替えです。タスクは、システムコールからユーザースペースに戻るとき、ユーザースペースのIRQ、またはシグナルのとき、切り替えられます。以下のケースで特に有用です：

    1. 影響を受ける関数に待機しているI/Oバウンドのユーザータスクをパッチする場合。この場合、SIGSTOPとSIGCONTを送信して、タスクをカーネルから強制的に抜けさせ、パッチを適用する必要があります。

    2. CPU負荷が高いユーザーのタスクをパッチングします。タスクが非常にCPU負荷が高い場合、IRQによって中断された次の機会にパッチングされます。

  3. アイドル状態の「swapper」タスクについては、これらは常にカーネル内に留まるため、アイドルループ内でklp_update_patch_state()関数を呼び出すことで、CPUがアイドル状態に入る前にパッチングされます。

    (注意: kthreadsについてはこのようなアプローチはまだ実装されていません。)

HAVE_RELIABLE_STACKTRACEをサポートしていないアーキテクチャは、この2番目のアプローチにのみ依存します。関数の古いバージョンがまだ実行中のタスクが存在する可能性があり、その関数が返るまでパッチングが完了しない場合があります。このような場合はタスクにシグナルを送信する必要があります。これは特にkthreadsに適用されます。これらは起動されない可能性があり、強制的に起動させる必要があります。詳細については下記を参照してください。

kthreadsを別の方法でパッチングする方法が見つからない限り、HAVE_RELIABLE_STACKTRACEをサポートしていないアーキテクチャは、カーネルライブパッチングによって完全にサポートされていないとみなされます。

/sys/kernel/livepatch/<patch>/transitionファイルは、パッチが遷移状態にあるかどうかを示します。一度に1つのみパッチが遷移状態にあることができます。タスクが初期パッチ状態にとどまっている場合、遷移状態は無限に続く可能性があります。

遷移状態中に、/sys/kernel/livepatch/<patch>/enabledファイルに逆の値を書き込むことで、遷移を逆転させ効果的にキャンセルできます。これにより、すべてのタスクが元のパッチ状態に戻るよう試みます。

また、/proc/<pid>/patch_stateファイルを使用して、パッチング操作を妨げるタスクを特定できます。パッチが遷移状態にある場合、このファイルはタスクが未パッチ状態（0）かパッチ済み状態（1）かを示します。パッチが遷移状態でない場合は-1を表示します。遷移を妨げるタスクはSIGSTOPとSIGCONTシグナルで強制的に状態を変更させることができます。ただし、システムに悪影響を及ぼす可能性があります。代替案として、残りの妨害タスクに偽のシグナルを送信する方法があります。実際にはシグナルが届くことはなく（シグナル待機構造にデータは存在しません）、タスクは中断されたり起動されたりして、パッチ状態を変更させられます。偽のシグナルは自動的に15秒ごとに送信されます。

管理者は、/sys/kernel/livepatch/<patch>/force属性を通じてトランジションを影響させることもできます。この属性に1を書き込むと、すべてのタスクのTIF_PATCH_PENDINGフラグをクリアし、タスクをパッチ済み状態に強制的に移行させます。重要な注意点！force属性は、ブロッキングタスクにより長時間トランジションが停止している場合にのみ使用する意図です。管理者は、必要なデータ（ブロッキングタスクのスタックトレースなど）を収集し、パッチ配布元から強制移行の承認を求める必要があります。未承認での使用はシステムに損害を及ぼす可能性があります。パッチの性質により、どの関数が（非）パッチされるか、ブロッキングタスクがスリープしている関数がどれか（/proc/<pid>/stackがここに役立ちます）によって、どの機能が影響を受けるか異なります。force機能が使用されている場合、パッチモジュールの削除（rmmod）は永久に無効化されます。このようなモジュール内にスリープしているタスクが存在する可能性があるため、保証できません。パッチモジュールがループで無効化・有効化される場合、参照カウントが無限に増える可能性があります。

さらに、forceの使用は今後のライブパッチの適用にも影響を及ぼし、システムにさらなる損害を引き起こす可能性があります。管理者はまず、単純にトランジションをキャンセルする（上記を参照）ことを検討すべきです。forceを使用する場合は、再起動を計画し、今後はライブパッチの適用を行わないべきです。

3.1 新しいアーキテクチャへの整合性モデルのサポートの追加¶

新しいアーキテクチャに整合性モデルのサポートを追加するには、いくつかのオプションがあります：

  1. CONFIG_HAVE_RELIABLE_STACKTRACEを追加します。これはobjtoolの移植を意味し、非DWARFアンワインドラーを使用する場合、スタックトレースコードがスタック内の割り込みを検出できるようにするため、スタックトレースコードが割り込みを検出できるようにするための方法が存在することを確認する必要があります。

  2. 代わりに、すべてのkthreadが安全な場所でklp_update_patch_state()を呼び出すことを確保します。kthreadは通常、繰り返し実行する無限ループにあり、安全な場所はループ内でロックを取得していない状態で、すべてのデータ構造が明確な状態にある場所です。

    ワークキューまたはkthreadワーカーAPIを使用している場合、場所は明確です。これらのkthreadは一般的なループ内で独立したアクションを処理します。

    カスタムループを持つkthreadの場合、場所はケースバイケースで慎重に選択する必要があります。

    その場合、HAVE_RELIABLE_STACKTRACEを持たないアーキテクチャでも、整合性モデルのスタックチェックを行わない部分を依然として利用できます：

    1. カーネル/ユーザースペース境界を越えたユーザータスクのパッチング；および

    2. 指定されたパッチポイントでキーテッドとアイドルタスクのパッチング。

    このオプションはオプション1より劣ります。なぜなら、ユーザーのタスクを通知し、kthreadsを起こしてパッチを適用する必要があるからです。ただし、まだ信頼できるスタックトレースが提供されていないアーキテクチャでは、このオプションがバックアップとして依然として有効かもしれません。

4. ライブパッチモジュール¶

ライブパッチはカーネルモジュールを使用して配布されます。サンプルはsamples/livepatch/livepatch-sample.cを参照してください。

このモジュールには、置き換える関数の新しい実装が含まれています。さらに、元の実装と新しい実装の関係を記述する構造体が定義されています。その後、ライブパッチモジュールがロードされるとカーネルが新しいコードを使用を開始するコード、およびライブパッチモジュールが削除される前にクリーンアップを行うコードが含まれています。これらについては次のセクションで詳しく説明します。

4.1. 新しい関数¶

新しい関数のバージョンは通常、元のソースからコピーされます。良い実践としては、関数名にプレフィックスを付けて元の関数と区別するため、例えばバックトレースで識別できるようにする方法があります。また、これらは直接呼び出されず、グローバルな可視性を必要としないため、staticとして宣言することもできます。

パッチには実際に変更された関数のみが含まれます。ただし、元のソースファイルから関数やデータへのアクセスが必要な場合がありますが、これらはローカルにのみアクセス可能である可能性があります。このような場合、生成されたライブパッチモジュールに特別なリロケーションセクションを設けることで解決できます。詳しくは ライブパッチモジュールELF形式 詳細についてはこちら。

4.2. メタデータ¶

パッチはいくつかの構造体によって記述され、情報を3つのレベルに分割しています。

  • struct klp_funcはそれぞれのパッチされた関数に対して定義されます。これは元の関数と新しい実装の関係を記述します。

    この構造体には、元の関数の名前（文字列として）が含まれます。関数アドレスは実行時にkallsymsを介して取得されます。

    次に、新しい関数のアドレスが含まれます。これは関数ポインタを直接割り当てることで定義されます。注意点として、新しい関数は通常同じソースファイル内で定義されます。

    オプションのパラメータとして、kallsymsデータベース内のシンボルの位置を使用して、同じ名前の関数を区別できます。これはデータベース内の絶対的な位置ではなく、特定のオブジェクト（vmlinuxまたはカーネルモジュール）で見つかった順序を指します。注意点として、kallsymsはオブジェクト名に基づいてシンボルを検索できます。

  • struct klp_objectは同じオブジェクト内のパッチされた関数（struct klp_func）の配列を定義します。オブジェクトはvmlinux（NULL）かモジュール名です。

    この構造体は、各オブジェクトの関数をグループ化して処理するのに役立ちます。注意点として、パッチされたモジュールがパッチ自体よりも後でロードされる可能性があり、関連する関数は利用可能になったタイミングでのみパッチされることがあります。

  • struct klp_patch はパッチされたオブジェクト（struct klp_object）の配列を定義します。

    この構造体はすべてのパッチされた関数を一貫して処理し、最終的に同期的に適用されます。すべてのパッチされたシンボルが見つかるまで全体のパッチは適用されません。例外は、まだロードされていないオブジェクト（カーネルモジュール）からのシンボルです。

    パッチがタスクごとに適用される仕組みについての詳細は、「一貫性モデル」セクションをご参照ください。

5. Livepatch ライフサイクル¶

Livepatching はロード、有効化、置き換え、無効化、削除の5つの基本的な操作で説明できます。

置き換えと無効化の操作は排他的です。特定のパッチに対しては同じ結果をもたらしますが、システム全体では異なる結果をもたらします。

5.1. ロード¶

合理的な方法は、Livepatch カーネルモジュールがロードされるときにパッチを有効化することです。そのため、klp_enable_patch() は callback 内で呼び出さなければなりません。 module_init() callback. その主な理由は以下の通りです：

まず、モジュールは関連する struct klp_patch に簡単にアクセスできます。

第二に、エラーコードは、パッチが有効にならない場合にモジュールのロードを拒否するために使用される可能性があります。

5.2. 有効化¶

ライブパッチは、コールバックから klp_enable_patch() を呼び出すことで有効になります。この段階で、システムはパッチされた関数の新しい実装を開始して使用します。 module_init() この段階で、システムはパッチされた関数の新しい実装を開始して使用します。

まず、パッチされた関数のアドレスは関数名に基づいて検出されます。セクション「New functions」で説明されている特別なリロケーションが適用されます。関連するエントリは /sys/kernel/livepatch/<name> の下に作成されます。上述のどの操作も失敗した場合、パッチは拒否されます。

第二に、ライブパッチは、タスクがパッチされた状態に収束する遷移状態に入ります。オリジナルの関数が初めてパッチされる場合、関数固有の struct klp_ops が作成され、汎用的な ftrace ハンドラが登録されます。1. この段階は、/sys/kernel/livepatch/<name>/transition に '1' の値があることで示されます。このプロセスについての詳細情報は、「Consistency model」セクションを参照してください。

最後に、すべてのタスクがパッチされると、'transition' の値が '0' に変わります。

1

関数が複数回パッチされる可能性があることに注意してください。特定の関数に対して ftrace ハンドラは一度しか登録されません。追加のパッチはリストにエントリを追加するだけです（フィールド func_stack) of the struct klp_ops. The right implementation is selected by the ftrace handler, see the “Consistency model” section.

That said, it is highly recommended to use cumulative livepatches because they help keeping the consistency of all changes. In this case, functions might be patched two times only during the transition period.

5.3. 置き換え¶

All enabled patches might get replaced by a cumulative patch that has the .replace flag set.

Once the new patch is enabled and the ‘transition’ finishes then all the functions (struct klp_func) associated with the replaced patches are removed from the corresponding struct klp_ops. Also the ftrace handler is unregistered and the struct klp_ops is freed when the related function is not modified by the new patch and func_stack list becomes empty.

参照 アトミック置換と累積パッチ 詳細についてはこちら。

5.4. 無効化¶

Enabled patches might get disabled by writing ‘0’ to /sys/kernel/livepatch/<name>/enabled.

First, livepatch enters into a transition state where tasks are converging to the unpatched state. The system starts using either the code from the previously enabled patch or even the original one. This stage is indicated by a value of ‘1’ in /sys/kernel/livepatch/<name>/transition. For more information about this process, see the “Consistency model” section.

Second, once all tasks have been unpatched, the ‘transition’ value changes to ‘0’. All the functions (struct klp_func) associated with the to-be-disabled patch are removed from the corresponding struct klp_ops. The ftrace handler is unregistered and the struct klp_ops is freed when the func_stack list becomes empty.

Third, the sysfs interface is destroyed.

5.5. 削除¶

Module removal is only safe when there are no users of functions provided by the module. This is the reason why the force feature permanently disables the removal. Only when the system is successfully transitioned to a new patch state (patched/unpatched) without being forced it is guaranteed that no task sleeps or runs in the old code.

6. sysfs¶

Information about the registered patches can be found under /sys/kernel/livepatch. The patches could be enabled and disabled by writing there.

/sys/kernel/livepatch/<patch>/force attributes allow administrator to affect a patching operation.

See Documentation/ABI/testing/sysfs-kernel-livepatch for more details.

7. 制限¶

The current Livepatch implementation has several limitations:

  • Only functions that can be traced could be patched.

    Livepatchは動的ftraceに基づいています。特に、ftraceを実装する関数や、livepatch用のftraceハンドラを実装する関数はパッチできません。そうしないとコードが無限ループに陥る可能性があります。このような潜在的な誤りを防ぐため、問題のある関数は「notrace」でマークされます。

  • 動的ftraceが関数の最初に位置している場合にのみ、Livepatchは信頼性を保証します。

    スタックや関数パラメータが何らかの形で変更される前に、関数をリダイレクトする必要があります。たとえば、x86_64ではgccコンパイラオプション「-fentry」を使用する必要があります。

    例外としてPPCポートがあります。これは相対アドレッシングとTOCを使用しており、各関数がTOCを処理し、LRを保存した後にftraceハンドラを呼び出す必要があります。この操作は戻るときに逆操作する必要があります。幸いなことに、汎用的なftraceコードも同様の問題があり、すべてftraceレベルで処理されています。

  • ftraceフレームワークを使用するkretprobesは、パッチされた関数と競合します。

    kretprobesとlivepatchの両方とも、リターンアドレスを変更するftraceハンドラを使用します。最初にハンドラを使用する側が勝ち、もう一方のハンドラが既に使用されている場合、プローブまたはパッチのいずれかが拒否されます。

  • 元の関数内のkprobesは、コードが新しい実装にリダイレクトされたときに無視されます。

    この状況に関する警告を追加するための進行中の作業があります。

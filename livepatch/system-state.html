システム状態の変更¶

一部のユーザーはシステムの再起動を非常にためらいます。これにより、より多くのライブパッチを提供し、それらの互換性を維持する必要があります。

累積型ライブパッチを使用することで、より多くのライブパッチの管理が容易になります。新しいライブパッチは古いものすべてを完全に置き換えます。修正を保持・追加・削除することもでき、原子的な置き換え機能により、どのバージョンのライブパッチでも安全に置き換えることができます。

シャドウ変数やコールバックによってシステムの挙動や状態が変更される可能性があり、それにより古いライブパッチや元のカーネルコードに戻って使用するのを安全にできない場合があります。また、新しいライブパッチはすでにインストールされたライブパッチによって行われた変更を検出する必要があります。

このとき、ライブパッチシステム状態トラッキングが役立ちます。これにより以下が可能になります：

  • システム状態を操作および復元するために必要なデータを保存する

  • 変更IDとバージョンを使用してライブパッチ間の互換性を定義する

1. ライブパッチシステム状態API¶

システムの状態は複数のライブパッチコールバックや新たに使用されるコードによって変更される可能性があります。また、すでにインストールされたライブパッチによって行われた変更を特定する必要があります。

各変更された状態はstruct klp_stateで記述され、include/linux/livepatch.hを参照してください。

各ライブパッチはstruct klp_statesの配列を定義し、それらが変更するすべての状態を記述します。

ライブパッチ作成者は、各struct klp_stateに対して次の2つのフィールドを定義する必要があります：

  • id

    • 影響を受けるシステム状態を識別するためのゼロでない数値

  • version

    • システム状態変更のバリアントを記述する数値

状態は次の2つの関数を使用して操作できます：

  • klp_get_state(patch, id)

    • 指定されたライブパッチと状態IDに関連するstruct klp_stateを取得します。

  • klp_get_prev_state(id)

    • 指定された機能IDとすでにインストールされたライブパッチに関連するstruct klp_stateを取得します。

2. ライブパッチ互換性¶

システム状態バージョンは不兼容なライブパッチのロードを防ぐために使用されます。ライブパッチが有効化される際、以下のルールが適用されます：

  • 完全に新しいシステム状態の変更は許可されます。

  • 同じバージョンまたはそれ以降のバージョンのシステム状態変更は許可されます。

  • 累積型ライブパッチは、すでにインストールされたライブパッチによって行われたすべてのシステム状態変更を処理する必要があります。

  • 非累積型ライブパッチは、すでに変更されたシステム状態に触れることを許可されます。

3. サポートされるシナリオ¶

ライブパッチはライフサイクルを持ち、システム状態の変更も同様です。すべての互換性のあるライブパッチは、以下のシナリオをサポートしなければなりません。

  • ライブパッチが有効になったときにシステム状態を変更し、既に置き換えられているライブパッチによって変更されていない場合に適用します。

  • 既に置き換えられているライブパッチによってシステム状態の変更が行われている場合は、それを引き継ぐか更新します。

  • ライブパッチが無効になったときに元の状態に戻します。

  • 遷移が元に戻ったときに以前の状態に戻します。これは元のシステム状態または置き換えられているライブパッチによって行われた状態変更を含む可能性があります。

  • エラーが発生した場合、ライブパッチが有効にならないため、すでに行われた変更をすべて取り消します。

4. 期待される使用方法¶

システム状態は通常、ライブパッチのコールバックによって変更されます。各コールバックの期待される役割は以下の通りです。

pre_patch()

  • 割り当てる state->data 必要に応じて。割当が失敗する可能性があり、 pre_patch() ライブパッチのロードを停止できる唯一のコールバックです。データがすでに以前にインストールされたライブパッチによって提供されている場合、割当は必要ありません。

  • 遷移が完了する前に新しいコードが必要とする他の準備作業を行います。たとえば、初期化 state->data.

    システム状態自体は通常、 post_patch() システム全体がこれを処理できるときに変更されます。

  • エラー発生時に自身の状態を整理します。これはカスタムコードによって行われるか、post_unpatch()を呼び出すことで実現できます。 post_unpatch() 明示的に呼び出すこともできます。

post_patch()

  • コピー state->data 以前のライブパッチから、互換性がある場合に。

  • 実際にシステム状態を変更します。最終的には新しいコードがこれを使用できるようにします。

  • 確保する必要があります。 state->data 置き換えられたライブパッチから必要な情報をすべて取得していることを確認してください。

  • 無料 state->data 必要なくなった場合に、以前のライブパッチからデータを削除します。

pre_unpatch()

  • ライブパッチによって追加されたコードがシステム状態の変更に依存しているのを防ぎます。

  • システム状態の変更を元に戻します。

post_unpatch()

  • 遷移の逆操作とライブパッチの無効化を区別するために、 klp_get_prev_state().

  • 遷移の逆操作の場合は、以前のシステム状態を復元します。これは何もしない場合も含まれます。

  • もはや必要ない設定やデータをすべて削除します。

注意

pre_unpatch() 通常は、 post_patch()と対称的な操作を行います。ただし、ライブパッチが無効化されるときにのみ呼び出されるため、以前にインストールされたライブパッチに気を配る必要がありません。

post_unpatch() 通常は、 pre_patch()これは遷移の逆操作中に呼び出される可能性があるため、以前にインストールされたライブパッチの状態を扱う必要があります。

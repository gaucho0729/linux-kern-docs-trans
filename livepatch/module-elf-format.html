ライブパッチモジュールELF形式¶

このドキュメントでは、livepatchモジュールが従うべきELF形式の要件について説明しています。

1. 背景と動機¶

以前は、livepatchがアーキテクチャ固有のコードを別途記述してリロケーションを実装する必要がありました。しかし、モジュールローダー内にすでにアーキテクチャ固有のリロケーション処理用のコードが存在しているため、この古いアプローチではコードが冗長になってしまいました。そのため、コードを複製したり、モジュールローダーが既に実装している処理を再実装するのではなく、livepatchはモジュールローダー内の既存コードを活用してすべてのアーキテクチャ固有のリロケーション処理を行います。具体的には、livepatchはモジュールローダー内のapply_relocate_add()関数を再利用してリロケーションを記述します。このドキュメントで説明するpatchモジュールELF形式により、livepatchがこのような処理を実行できるようになります。このアプローチにより、livepatchが他のアーキテクチャへの移植をより容易にし、特定のアーキテクチャへの移植に必要なアーキテクチャ固有のコード量を減らすことが期待されています。

apply_relocate_add()はモジュールのセクションヘッダーテーブル、シンボルテーブル、リロケーションセクションインデックスにアクセスする必要があります。そのため、livepatchモジュールではELF情報が保持されています（第5節を参照してください）。livepatchは独自のリロケーションセクションとシンボルを管理しており、このドキュメントでその詳細を説明しています。ELF定数としてlivepatchシンボルおよびリロケーションセクションをマークするための値は、glibcからの定義に基づきOS固有の範囲から選定されています。

なぜlivepatchは独自のリロケーションを書く必要があるのでしょうか？¶

典型的なライブパッチモジュールは、非エクスポートされたグローバルシンボルや非インクルードされたローカルシンボルを参照できる関数のパッチ版を含みます。これらのシンボルを参照するリロケーションは、カーネルモジュールロー�ーダーが解決できないため、そのまま残すことはできません。したがって、ライブパッチモジュールは拒否されます。さらに、パッチモジュールのロード時にまだロードされていないモジュールに影響を与えるリロケーションを適用することもできません（例：未ロードのドライバに対するパッチ）。以前は、ライブパッチは結果となるパッチモジュールELF出力に特別な「dynrela」（ダイナミックrela）セクションを埋め込むことでこの問題を解決していました。dynrelのセクションを使用して、シンボルのスコープや所属するモジュールを考慮しながらシンボルを解決し、その後手動でダイナミックリロケーションを適用していました。しかし、このアプローチでは、ライブパッチがアーキテクチャ固有のコードを提供する必要がありました。新しい形式では、ライブパッチはdynrelaセクションの代わりに自身でSHT_RELAリロケーションセクションを管理し、リロケーションで参照するシンボルは特別なライブパッチシンボルです（セクション2と3を参照）。アーキテクチャ固有のライブパッチリロケーションコードは、apply_relocate_add()関数の呼び出しに置き換えられます。

2. ライブパッチ modinfoフィールド¶

ライブパッチモジュールは「livepatch」modinfo属性を必ず持つ必要があります。サンプルライブパッチモジュールの実装方法は、samples/livepatch/に記載されています。

ユーザーは'modinfo'コマンドを使用し、「livepatch」フィールドの存在を確認することでライブパッチモジュールを識別できます。このフィールドは、カーネルモジュールローダーがライブパッチモジュールを識別するためにも使用されます。

例:¶

modinfo出力:

% modinfo livepatch-meminfo.ko
filename:               livepatch-meminfo.ko
livepatch:              Y
license:                GPL
depends:
vermagic:               4.3.0+ SMP mod_unload

3. ライブパッチリロケーションセクション¶

ライブパッチモジュールは、適切なタイミングでモジュールやカーネル（vmlinux）にリロケーションを適用するために自身でELFリロケーションセクションを管理します。たとえば、現在ロードされていないドライバをパッチする場合、ライブパッチはそのドライバがロードされるときに該当するライブパッチリロケーションセクションを適用します。

パッチモジュール内の各「オブジェクト」（例：vmlinux、またはモジュール）には、複数のライブパッチリロケーションセクションが関連付けられることがあります（例：同じオブジェクト内の複数関数へのパッチ）。ライブパッチリロケーションセクションとリロケーションを適用するターゲットセクション（通常は関数のテキストセクション）には1対1の対応関係があります。また、ライブパッチモジュールはライブパッチリロケーションセクションを持たない場合もあります（例：サンプルライブパッチモジュール、samples/livepatchを参照）

ライブパッチモジュールではELF情報が保持されるため（第5節を参照）、apply_relocate_add()に適切なセクションインデックスを渡すことで、ライブパッチ再配置セクションを適用できます。これにより、再配置セクションにアクセスし、再配置を適用します。

ライブパッチ再配置セクション内のrelaによって参照されるすべてのシンボルはライブパッチシンボルです。ライブパッチがapply_relocate_add()を呼び出す前にこれらのシンボルは解決する必要があります。詳しくは第3節をご参照ください。

3.1 ライブパッチ再配置セクションの形式¶

ライブパッチ再配置セクションはSHF_RELA_LIVEPATCHセクションフラグでマークする必要があります。include/uapi/linux/elf.hで定義を確認してください。モジュールロー�ーダーはこのフラグを認識し、パッチモジュールのロード時にこれらの再配置セクションを適用しないようにします。また、SHF_ALLOCフラグでマークする必要があります。これにより、モジュールロード時にロー�ーダーがセクションを破棄しないようにします（つまり、他のSHF_ALLOCセクションと同様にメモリにコピーされます）。

ライブパッチ再配置セクションの名前は以下の形式に従う必要があります：

.klp.rela.objname.section_name
^        ^^     ^ ^          ^
|________||_____| |__________|
   [A]      [B]        [C]
[A]

再配置セクション名は文字列「.klp.rela.」で前につながれます。

[B]

再配置セクションが属するオブジェクトの名前（つまり「vmlinux」またはモジュール名）は前記のプレフィックスの直後に続きます。

[C]

この再配置セクションが適用されるセクションの実際の名前。

ライブパッチ再配置セクションの名前：

.klp.rela.ext4.text.ext4_attr_store
.klp.rela.vmlinux.text.cmdline_proc_show

vmlinuxおよびモジュール9p、btrfs、ext4をパッチするパッチモジュールの`readelf –sections`出力：

4. ライブパッチシンボル¶

Livepatch symbolsは、ライブパッチリロケーションセクションによって参照されるシンボルです。これらは、パッチ対象オブジェクトの新しいバージョンの関数からアクセスされるシンボルであり、モジュールロー�ーダーによってアドレスが解決できない（ローカルまたは未エクスポートされたグローバルシンボルの場合）ため、導入されました。モジュールローダーはエクスポートされたシンボルのみを解決し、すべての新しいパッチ関数で参照されるシンボルがエクスポートされているわけではありません。したがって、Livepatch symbolsが導入されました。また、パッチモジュールがまだロードされていないモジュールをパッチする場合など、パッチモジュールがロードされる時点でシンボルのアドレスが即座に判明しない場合にも使用されます。たとえば、ライブパッチがまだロードされていないモジュールをパッチする場合、関連するLivepatch symbolsはターゲットモジュールがロードされるときに単純に解決されます。いずれにしても、任意のLivepatchリロケーションセクションに対して、そのセクションで参照されるすべてのLivepatch symbolsは、apply_relocate_add()を呼び出す前に解決する必要があります。

Livepatch symbolsはSHN_LIVEPATCHでマークする必要があります。これにより、モジュールローダーが識別し、無視できるようにします。Livepatchモジュールはこれらのシンボルをシンボルテーブルに保持し、シンボルテーブルはmodule->symtabを通じてアクセス可能になります。

4.1 ライブパッチモジュールのシンボルテーブル¶

通常、モジュールのシンボルテーブル（「コア」シンボルのみを含む簡易なコピー）はmodule->symtabを通じて利用可能になります（kernel/module.cのlayout_symtab()を参照）。ライブパッチモジュールでは、モジュールロード時にメモリにコピーされるシンボルテーブルは、パッチモジュールがコンパイルされたときに生成されるシンボルテーブルと完全に一致する必要があります。これは、各ライブパッチリロケーションセクションのリロケーションが、それぞれのシンボルに対してシンボルインデックスを参照するためであり、元のシンボルインデックス（およびシンボルテーブルの順序）が保持されることが、apply_relocate_add()が正しいシンボルを検索するための条件です。

例えば、ライブパッチモジュールからの特定のrelaを以下のようにします::

Relocation section '.klp.rela.btrfs.text.btrfs_feature_attr_show' at offset 0x2ba0 contains 4 entries:
    Offset             Info             Type               Symbol's Value  Symbol's Name + Addend
000000000000001f  0000005e00000002 R_X86_64_PC32          0000000000000000 .klp.sym.vmlinux.printk,0 - 4

This rela refers to the symbol '.klp.sym.vmlinux.printk,0', and the symbol index is encoded
in 'Info'. Here its symbol index is 0x5e, which is 94 in decimal, which refers to the
symbol index 94.
And in this patch module's corresponding symbol table, symbol index 94 refers to that very symbol:
[ snip ]
94: 0000000000000000     0 NOTYPE  GLOBAL DEFAULT OS [0xff20] .klp.sym.vmlinux.printk,0
[ snip ]

4.2 ライブパッチシンボルの形式¶

ライブパッチシンボルのセクションインデックスはSHN_LIVEPATCHでマークする必要があります。これにより、モジュールローダーが識別し、解決を試みないようになります。実際の定義はinclude/uapi/linux/elf.hを参照してください。

ライブパッチシンボルの名前は次の形式に従う必要があります:

.klp.sym.objname.symbol_name,sympos
^       ^^     ^ ^         ^ ^
|_______||_____| |_________| |
   [A]     [B]       [C]    [D]
[A]

シンボル名は文字列「.klp.sym.」で接頭辞となります。

[B]

接頭辞の後には、シンボルが属するオブジェクト（つまり、「vmlinux」またはモジュール名）の名前が直ちに続きます。

[C]

実際のシンボル名

[D]

オブジェクト内のシンボルの位置（kallsymsに基づく）この情報は、同じオブジェクト内での複数のシンボルを区別するために使用されます。シンボルの位置は数値で表されます（0、1、2…）。一意のシンボルの位置は0です。

例:¶

ライブパッチのシンボル名:

.klp.sym.vmlinux.snprintf,0
.klp.sym.vmlinux.printk,0
.klp.sym.btrfs.btrfs_ktype,0

パッチモジュールの`readelf –symbols`出力:

Symbol table '.symtab' contains 127 entries:
   Num:    Value          Size Type    Bind   Vis     Ndx         Name
   [ snip ]
    73: 0000000000000000     0 NOTYPE  GLOBAL DEFAULT OS [0xff20] .klp.sym.vmlinux.snprintf,0
    74: 0000000000000000     0 NOTYPE  GLOBAL DEFAULT OS [0xff20] .klp.sym.vmlinux.capable,0
    75: 0000000000000000     0 NOTYPE  GLOBAL DEFAULT OS [0xff20] .klp.sym.vmlinux.find_next_bit,0
    76: 0000000000000000     0 NOTYPE  GLOBAL DEFAULT OS [0xff20] .klp.sym.vmlinux.si_swapinfo,0
  [ snip ]                                               ^
                                                         |
                                                        [*]
[*]

これらのシンボルの「Ndx」（セクションインデックス）はSHN_LIVEPATCH（0xff20）です。「OS」はOS固有のことを意味します。

5. シンボルテーブルとElfセクションのアクセス¶

ライブパッチモジュールのシンボルテーブルはmodule->symtabを通じてアクセス可能です。

apply_relocate_add()は、モジュールのセクションヘッダ、シンボルテーブル、リロケーションセクションインデックスにアクセスする必要があります。そのため、ライブパッチモジュールではElf情報が保持され、モジュールロー�ーダーがmodule->klp_info（klp_modinfo構造体）を通じてアクセス可能にしています。ライブパッチモジュールがロードされる際、この構造体はモジュールロー�ーダーによって埋められます。以下の項目が記載されています。

struct klp_modinfo {
        Elf_Ehdr hdr; /* Elf header */
        Elf_Shdr *sechdrs; /* Section header table */
        char *secstrings; /* String table for the section headers */
        unsigned int symndx; /* The symbol table section index */
};

hwpoison¶

hwpoison とは？¶

今後のインテルCPUは、一部のメモリエラーからの回復をサポートしています（MCA recovery）。これにより、OSがページを「毒された」と宣言し、関連するプロセスを終了させ、今後は使用しないようにする必要があります。

このパッチキットは、VM内での必要なインフラストラクチャを実装しています。

概要コメントを引用します：

High level machine check handler. Handles pages reported by the
hardware as being corrupted usually due to a 2bit ECC memory or cache
failure.

This focusses on pages detected as corrupted in the background.
When the current CPU tries to consume corruption the currently
running process can just be killed directly instead. This implies
that if the error cannot be handled for some reason it's safe to
just ignore it because no corruption has been consumed yet. Instead
when that happens another machine check will happen.

Handles page cache pages in various states. The tricky part
here is that we can access any page asynchronous to other VM
users, because memory failures could happen anytime and anywhere,
possibly violating some of their assumptions. This is why this code
has to be extremely careful. Generally it tries to use normal locking
rules, as in get the standard locks, even if that means the
error handling takes potentially a long time.

Some of the operations here are somewhat inefficient and have non
linear algorithmic complexity, because the data structures have not
been optimized for this case. This is in particular the case
for the mapping from a vma to a process. Since this case is expected
to be rare we hope we can get away with this.

コードは、mm/memory-failure.cにある高レベルハンドラ、新しいページ毒ビット、およびVM内での毒されたページを処理するためのさまざまなチェックから構成されています。

現在の主な対象はKVMゲストですが、すべてのアプリケーションにも適用可能です。KVMサポートには最近のqemu-kvmリリースが必要です。

KVM利用には、KVMがゲストに機械チェックを注入する際に適切なアドレスを指定できる新しいシグナルタイプが必要でした。理論上、他のアプリケーションもメモリエラーを処理できるようになります。ただし、ほぼすべてのアプリケーションはこれを実行しないと考えられますが、一部の特殊なアプリケーションでは可能かもしれません。

失敗回復モード¶

メモリエラーリカバリは、次の2つの（実際には3つの）モードで行われます：

vm.memory_failure_recovery sysctlがゼロに設定されている場合：

すべてのメモリエラーはパニックを引き起こします。回復を試みません。（x86では、これはMCEサブシステムの許容レベルにも影響されます）

早期終了

（グローバルおよびプロセスごとに制御可能）エラーが検出された直ちにアプリケーションにSIGBUSを送信します。これにより、メモリエラーを穏やかに処理できるアプリケーション（例：影響を受けたオブジェクトを削除）が利用可能です。これはKVM qemuが使用するモードです。

遅延終了

アプリケーションが破損ページにアクセスした際にSIGBUSを送信します。これはメモリエラーを認識していないアプリケーションにとって最適で、デフォルトです。注意：一部のページは常に遅延終了として扱われます。

ユーザー制御¶

vm.memory_failure_recovery

sysctl.txt を参照

vm.memory_failure_early_kill

早期終了モードをグローバルで有効化

PR_MCE_KILL

早期/遅延終了モードを設定またはシステムデフォルトに戻す

arg1: PR_MCE_KILL_CLEAR:

システムデフォルトに戻す

arg1: PR_MCE_KILL_SET:

arg2でスレッド固有のモードを定義

PR_MCE_KILL_EARLY:

早期終了

PR_MCE_KILL_LATE:

遅延終了

PR_MCE_KILL_DEFAULT

システムグローバルデフォルトを使用

プロセスのSIGBUS(BUS_MCEERR_AO)を担当する専用スレッドを設置したい場合、その指定されたスレッドでprctl(PR_MCE_KILL_EARLY)を呼び出す必要があります。それ以外の場合、SIGBUSはメインスレッドに送信されます。

PR_MCE_KILL_GET

現在のモードを返す

テスト¶

  • madvise(MADV_HWPOISON, ….)（root権限で） - テストのためにプロセス内のページを毒化する

  • debugfsを通じたhwpoison-injectモジュール /sys/kernel/debug/hwpoison/

    corrupt-pfn

    このファイルにエコーされたPFNでhwpoisonのエラーを注入します。テストスイートで意図しない破損ページを避けるため、早期のフィルタリングを行います。

    unpoison-pfn

    このファイルにエコーされたPFNでソフトウェアでunpoisonページを設定します。これによりページが再利用可能になります。これはLinuxで注入されたエラー専用の機能であり、実際のメモリエラーには対応しません。

    これらの注入インターフェースは安定していません。カーネルバージョンによって変更される可能性があります

    corrupt-filter-dev-major, corrupt-filter-dev-minor

    ブロックデバイスのメジャーマイナーマスクで定義されたファイルシステムに関連するページのメモリエラーのみを処理します。-1Uはワイルドカード値です。これは人工的な注入でのテスト専用に使用するべきです。

    corrupt-filter-memcg

    memgroupに所属するページのみに注入を制限します。memcgのinode番号で指定します。

    例:

    mkdir /sys/fs/cgroup/mem/hwpoison

usemem -m 100 -s 1000 &
echo `jobs -p` > /sys/fs/cgroup/mem/hwpoison/tasks

memcg_ino=$(ls -id /sys/fs/cgroup/mem/hwpoison | cut -f1 -d' ')
echo $memcg_ino > /debug/hwpoison/corrupt-filter-memcg

page-types -p `pidof init`   --hwpoison  # shall do nothing
page-types -p `pidof usemem` --hwpoison  # poison its pages
    corrupt-filter-flags-mask, corrupt-filter-flags-value

    指定された場合、((page_flags & mask) == value)の条件を満たすページのみをpoisonします。これにより、さまざまな種類のページのストレステストが可能です。page_flagsは/proc/kpageflagsと同一です。フラグビットはinclude/linux/kernel-page-flags.hに定義され、ドキュメントは プロセスページテーブルの検証

  • アーキテクチャ固有のMCEインジェクター

    x86にはmce-inject、mce-testがあります

    mce-test内にportableなhwpoisonテストプログラムがあります。以下を参照してください。

制限¶

  • すべてのページタイプがサポートされていませんし、今後もサポートされません。ほとんどのカーネル内部オブジェクトは回復できません。現在はLRUページのみが対象です。

  • 現在、hugepageのサポートは不足しています。

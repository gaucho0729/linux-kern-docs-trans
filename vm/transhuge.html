Transparent Hugepage Support¶

このドキュメントは、透明大ページ（THP）のサポートに関する設計原則と、メモリ管理システムの他の部分との相互作用について説明しています。

設計原則¶

  • 「graceful fallback（優雅なフェールバック）」：THPに関する知識を持たないmmコンポーネントは、大ページのpmdマッピングをpteテーブルに分割し、必要に応じて透明大ページを分割して、通常のページや通常のpteマッピングで継続的に動作できるようにします。

  • メモリのフラグメンテーションにより大ページの割り当てが失敗した場合、通常のページを優雅に割り当てて同様のvmaに混在させ、ユーザー空間に失敗や大幅な遅延を通知することなく処理します。

  • タスクが終了し、より多くの大ページが利用可能になった場合（即座にbuddy領域に出現するか、VMを通じて）、通常のページでバックエンドされたゲスト物理メモリはkhugepagedを通じて自動的に大ページに再配置されます。

  • メモリの予約は必要とならず、逆に可能であれば常に大ページを使用します（ここでの唯一の予約はkernelcore=パラメータで、不動ページを避けてメモリ全体をフラグメンテーションから守るためのものです。ただし、この調整はTHPサポートに特有ではなく、カーネル内のすべての動的高オーダー割り当てに共通する機能です）。

get_user_pagesおよびfollow_page¶

get_user_pagesおよびfollow_pageが大ページを対象に実行されても、通常通りヘッドまたはテールページを返します（hugetlbfsでの挙動と同様です）。ほとんどのGUPユーザーはページの物理アドレスとI/O完了後の一時的なピン固定にのみ関心を持ち、ページが大ページであることに気づきません。ただし、ドライバがテールページのページ構造を操作する場合（例：page->mappingの確認やヘッドページに関連する他のビットの確認）、ヘッドページをチェックするようにコードを更新する必要があります。ヘッド/テールページへの参照取得は、ページが誰かによって分割されることを防ぎます。

注意

これらはGUP APIに新たな制約ではありませんし、hugetlbfsにも適用される同じ制約です。したがって、hugetlbfsでGUPを処理できるドライバは、透明大ページでバックエンドされるマッピングでも問題なく動作します。

follow_pageが返すcompoundページを処理できない場合、follow_pageにFOLL_SPLITビットをパラメータとして指定することで、返す前に大ページを分割します。

Graceful fallback¶

ページテーブルを歩く際、巨大なpmd（ページディスクリプタ）の存在に無知なコードは、split_huge_pmd(vma, pmd, addr)を呼び出すことで透明なヒープページ対応を実現できます。pmd_offsetが返すpmdの位置にsplit_huge_pmdを追加するだけで、コードを透明なヒープページ対応に変換できます。これは、優雅なフェールバック設計のおかげで、1行の変更で複数数百から数千行に及ぶ複雑なコードを書く必要がなくなります。

ページテーブルを歩くことなく、コード内でネイティブに処理できない物理的なヒープページに遭遇した場合、split_huge_page(page)を呼び出して分割できます。これはLinux VMがヒープページをスワップアウトする前に実行する処理の例です。split_huge_page()はページがピンされている場合に失敗する可能性があるため、正しい処理を実装する必要があります。

mremap.cを透明なヒープページ対応にするためのワンライナーの変更例:

diff --git a/mm/mremap.c b/mm/mremap.c
--- a/mm/mremap.c
+++ b/mm/mremap.c
@@ -41,6 +41,7 @@ static pmd_t *get_old_pmd(struct mm_stru
                return NULL;

        pmd = pmd_offset(pud, addr);
+       split_huge_pmd(vma, pmd, addr);
        if (pmd_none_or_clear_bad(pmd))
                return NULL;

透明なヒープページ対応コードにおけるロック¶

可能な限り多くのコードを透明なヒープページ対応にすることが望ましいです。split_huge_page()やsplit_huge_pmd()を呼び出すことはコストがかかるためです。

ページテーブルを歩く際、巨大なpmdを対応させるには、pmd_offsetで取得したpmdに対してpmd_trans_huge()を呼び出すだけです。khugepagedが巨大なpmdを生成しないようにするため、mmap_lockを読み取り（または書き込み）モードで保持する必要があります（khugepagedはcollapse_huge_pageでmmap_lockを書き込みモードで取得します）。pmd_trans_hugeがfalseを返す場合、従来のコードパスにフェールバックします。pmd_trans_hugeがtrueを返す場合、ページテーブルロック（pmd_lock()）を取得し、再びpmd_trans_hugeを実行する必要があります。ページテーブルロックを取得することで、他のスレッドが巨大なpmdを通常のpmdに変換するのを防ぎます（split_huge_pmdはページテーブルウォークと並行して実行可能）。2回目のpmd_trans_hugeがfalseを返す場合、ページテーブルロックを解放して従来のコードにフェールバックします。それ以外の場合、巨大なpmdとヒープページをネイティブで処理できます。処理が終わったらページテーブルロックを解放してください。

参照カウントと透明なヒープページ¶

透明なヒープページ（THP）における参照カウントは、他の複合ページにおける参照カウントとほぼ一致しています:

  • get_page()/put_page()およびGUPはヘッドページの->_refcountを操作します。

  • ->_refcountは末尾ページでは常にゼロです：get_page_unless_zero()は末尾ページで成功しません。

  • 複合ページのサブページにおけるPTEエントリの増減を伴うマッピング/アンマッピング ->_mapcountの処理。

  • 複合ページ全体のマップ/アンマップは、compound_mapcount（最初のテールページに保存）で処理されます。ファイルのヒューゲンページの場合、すべてのサブページの->_mapcountもインクリメントし、サブページの最後のアンマップを競合条件を避けて検出できるようにします。

PageDoubleMap()はページが おそらく PTEでマップされていることを示します。

匿名ページの場合、PageDoubleMap()はすべてのサブページの->_mapcountが1つずつオフセットされることを示します。これにより、PMDとPTEの両方でマップされているサブページのアンマップを競合条件を避けて検出できるようになります。

この最適化はサブページごとのmapcount追跡のオーバーヘッドを低減するために必要です。代替案は、複合ページ全体のマップ/アンマップごとにすべてのサブページの->_mapcountを変更することです。

匿名ページの場合、ページのPMDが初めて分割されるときにPG_double_mapを設定しますが、まだPMDマッピングが存在する限り保持します。追加の参照は最後のcompound_mapcountとともに消えます。

ファイルページでは、ページがPTEでマップされる最初のときにPG_double_mapが設定され、ページキャッシュから除外されるときに消えます。

split_huge_pageは、ヘッドページの参照カウントをテールページに配分する必要があります。その後、ページ構造体のすべてのPG_head/tailビットをクリアします。ページテーブルエントリで取得した参照カウントについては簡単に処理できますが、get_user_pagesからの追加ピン（参照）の配分方法については情報が不足しています。split_huge_page()はピンされたヒューゲンページの分割を要求すると失敗します。page countはすべてのサブページのmapcountの合計＋1（split_huge_pageの呼び出し元がヘッドページの参照を保持している必要があります）に等しくなければなりません。

split_huge_pageは匿名ページのpage->_refcountとpage->_mapcountを移動エントリを使って安定化します。ファイルページは単にアンマップされます。

物理メモリスキャナーにも安全です。スキャナーがページに参照を取得する唯一の正当な方法はget_page_unless_zero()です。

すべてのテールページはatomic_add()実行前まで->_refcountがゼロです。これにより、スキャナーがテールページに参照を取得するのを防ぎます。atomic_add()後は->_refcountの値には関心がありません。ヘッドページからどのくらいの参照が未払いであるかはすでに把握しています。

ヘッドページではget_page_unless_zero()が成功し、気にすることはありません。split後の参照の行き先は明確です。すべての参照はヘッドページに残ります。

split_huge_pmd()は参照カウントに関する制限がありません。PMDはいつでも分割可能で、失敗することはありません。

部分アンマップとdeferred_split_huge_page()¶

THP（Transparent Huge Pages）の一部をアンマップ（munmap() または他の方法で）しても、メモリはすぐに解放されません。代わりに、page_remove_rmap() で THP のサブページが使用されていないことを検出し、メモリ圧力が発生した際に THP を分割するようにキューイングします。分割によって未使用のサブページが解放されます。

ロックコンテキストの制約により、即座にページを分割することはできません。また、多くの場合、THP が VMA バウンダリを越える際の exit(2) で部分的なアンマップが発生するため、逆効果になる可能性もあります。

deferred_split_huge_page() 関数はページを分割するためのキューイングを行います。実際の分割は shrinker インターフェースを通じてメモリ圧力が発生した際に実行されます。

ページの移動¶

ページマиграーشنは、プロセスが実行されている間、NUMAシステム内のノード間でページの物理的な位置を移動させることを可能にします。これにより、プロセスが見ている仮想アドレスは変化しません。ただし、システムはこれらのページの物理的な位置を再配置します。

ページマиграーشنの主な目的は、メモリアクセスのレイテンシーを減らすために、プロセスがそのメモリをアクセスしているプロセッサに近い場所にページを移動させることです。

ページマиграーشنは、mbind()を通じて新しいメモリポリシーを設定しながら、MF_MOVE および MF_MOVE_ALL オプションを使用してプロセスがページを配置しているノードを手動で移動させることを可能にします。また、sys_migrate_pages() 関数呼び出しを使用して、他のプロセスからプロセスのページを移動させることもできます。migrate_pages() 関数呼び出しは、2つのノードセットを指定し、プロセスのページを from ノードから destination ノードへ移動します。ページマиграーشن関数は、Andi Kleen による numactl パッケージで提供されており（0.9.3 より新しいバージョンが必要です。取得は https://github.com/numactl/numactl.git)。numactl は、ページマиграーشن用に他の NUMA 機能と似たインターフェースを提供する libnuma を提供します。cat /proc/<pid>/numa_maps プロセスのページが配置されている場所を簡単に確認できます。proc(5) マニュアルページの numa_maps ドキュメンテーションも参照してください。

手動でのマиграーشنは、たとえばスケジューラがプロセスを遠くのノードにあるプロセッサに移動させた場合などに役立ちます。バッチスケジューラや管理者が状況を検出し、プロセスのページを新しいプロセッサに近づけることができます。カーネル自身は手動でのページマиграーشنをサポートしています。自動的なページマиграーشنは、ユーザー空間プロセスがページを移動させることが可能です。特別な関数呼び出し「move_pages」は、プロセス内の個々のページを移動させることができます。たとえば、NUMAプロファイラーは、頻繁なノード外アクセスを示すログを取得し、その結果をもとにページをより有利な場所に移動させることができます。

大規模なインストールでは、通常 cpusets を使用してシステムをノードごとにセクションに分割します。Paul Jackson は cpusets にタスクが別の cpuset に移動したときにページを移動する機能を追加しました（参照 CPUSETS)。cpusets はプロセスのローカル性を自動化します。タスクが新しい cpuset に移動した場合、そのすべてのページも一緒に移動するため、プロセスのパフォーマンスが大幅に低下しません。また、cpuset 内のプロセスのページは、cpuset の許可メモリノードが変更されたときに移動されます。

ページの移動は、プロセスを移動させても、ノード群内のページの相対的な位置関係を保持するためのメモリ割当パターンを維持するすべての移動技術において、メモリ遅延を保持するために必要です。移動後も同様のパフォーマンスでプロセスが実行されます。

ページの移動は複数のステップで行われます。まず、カーネルからmigrate_pages()を使用するユーザー（ユーザースペースでの使用については上記のAndi Kleenのnumactlパッケージを参照）向けの高レベルな説明を示し、次に低レベルの詳細について説明します。

カーネルでのmigrate_pages()の使用¶

  1. LRUからページを削除します。

    ページの移動リストは、ページをスキャンしてリストに移動させることで生成されます。これはisolate_lru_page()を呼び出すことで実現され、この関数はページの参照カウントを増加させることで、ページ移動中にページが消失しないようにします。また、スワッパーまたは他のスキャン処理がページに遭遇しないようにします。

  2. migrate_pages()に渡すことができるnew_page_t型の関数が必要です。この関数は、古いページから正しい新しいページを割当てる方法を決定する必要があります。

  3. migrate_pages()関数が呼び出され、移動を試行します。各移動対象ページに対して新しいページを割当てる関数を呼び出します。

migrate_pages()の動作方法¶

migrate_pages()はページリストを複数回スキャンします。ページがすべての参照が移動時に除去可能である場合にのみ移動されます。ページは既にisolate_lru_page()によってLRUから削除されており、参照カウントが増加しているため、ページ移動中にページが解放されません。

手順:

  1. 移動するページをロックします。

  2. Writebackが完了していることを確認します。

  3. 移動先の新しいページをロックします。このページ（まだ最新でない）へのアクセスは、移動中に即座にブロックされます。

  4. ページのページテーブル参照はすべて移動エントリに変換されます。これによりページのマップカウントが減少します。結果のマップカウントがゼロでない場合、ページを移動しません。すべてのユーザースペースプロセスは、ページロックまたは移動ページテーブルエントリの削除を待つことになります。

  5. i_pagesロックを取得します。これにより、マッピングを通じてページにアクセスしようとするすべてのプロセスはスピンロックでブロックされます。

  6. ページの参照カウントを確認し、参照が残っている場合は戻ります。それ以外の場合、このページを参照しているのは自分だけであることがわかります。

  7. radix treeがチェックされ、このページへのポインタが含まれていない場合、他のプロセスがradix treeを変更したため、処理を戻します。

  8. 新しいページは古いページの一部の設定を引き継ぎ、新しいページへのアクセスが正しい設定を持つページとして検出されるように準備されます。

  9. radix treeは新しいページへのポインタに変更されます。

  10. 古いページの参照カウントはアドレス空間参照がなくなったため減少し、新しいページへの参照がアドレス空間によって設定されるため新しいページの参照カウントが増加します。

  11. i_pagesロックが解除され、マッピングの検索が再び可能になります。プロセスはロックを待つ状態から、新しいページのロックを待つ状態に移行します。

  12. ページの内容が新しいページにコピーされます。

  13. 残りのページフラグが新しいページにコピーされます。

  14. 古いページフラグがクリアされ、ページがもはや情報を提供しないことを示します。

  15. 新しいページにキューイングされたWritebackがトリガーされます。

  16. ページテーブルにマиграーションエントリが挿入されていた場合、それらを実際のpteに置き換えます。これにより、既にページロックを待っているユーザー空間プロセス以外のプロセスがアクセス可能になります。

  17. 古いページと新しいページのページロックが解除され、ページロックを待つプロセスはページフォールトを再実行し、新しいページに到達します。

  18. 新しいページがLRUリストに移動し、swapperなどによるスキャンが再開されます。

非LRUページのマиграーション¶

マиграーションはもともとNUMAによるメモリアクセス遅延の削減を目的としていましたが、コンパクションもマиграーションを用いて高オーダーのページを生成するため使用しています。

現在の実装の問題点は、ページのみをマиграーション可能に設計していることです。 LRU しかし、ドライバなどでは潜在的に非LRUページをマиграーション可能にすることができます。例えば、zsmallocやvirtio-balloonページなどです。

virtio-balloonページでは、マиграーションコードパスの一部にドライバ固有の処理を追加し、マиграーションロジックをインターセプトする関数を追加しています。しかし、ドライバ固有の処理が多すぎるため、他のドライバがページをマиграーション可能にするには、マиграーションパスに独自のハックを追加する必要があります。

この問題を解決するため、VMは非LRUページのマиграーションをサポートし、マиграーションパスにドライバ固有のハックを含まず、非LRUマиграーション可能なページ用の汎用関数を提供します。

ドライバがページをマиграーション可能にする場合、struct address_space_operationsの関数ポインタとして3つの関数を定義する必要があります。

  1. bool (*isolate_page) (struct page *page, isolate_mode_t mode);

    ドライバのisolate_page()関数がVMに提供すべきことは、 true ドライバがページを成功裏に隔離した場合、trueを返すとVMがページをPG_isolatedとしてマークし、複数のCPUによる同時隔離処理はそのページを隔離対象から除外します。ドライバがページを隔離できなかった場合は、適切に返却してください false.

    ページが成功裏に隔離された後、VMはpage.lruフィールドを使用するため、ドライバはこれらのフィールドの値を保持する必要はありません

2. int (*migratepage) (struct address_space *mapping, | struct page *newpage, struct page *oldpage, enum migrate_mode);

隔離後、VMはドライバのmigratepage()関数を隔離されたページとともに呼び出します。migratepage()関数の役割は、古いページの内容を新しいページに移動し、struct page newpageのフィールドを設定することです。古いページを成功裏に移動させた場合、page_lockの下で__ClearPageMovable()を呼び出してVMに古いページがもはや移動可能でなくなったことを示す必要があります。ドライバが現在の時点でページを移動できなかった場合は-EAGAINを返却できます。-EAGAINを返却した場合、VMは短期間でページの再移動を試みます（VMは-EAGAINを「一時的な移動失敗」と解釈するため）。-E_NOWAIT以外のエラーを返却した場合、VMは再試行せずにページの移動を放棄します

migratepage()関数内ではドライバはpage.lruフィールドを操作すべきではありません

  1. void (*putback_page)(struct page *);

    隔離されたページの移動が失敗した場合、VMは隔離されたページをドライバに返却し、putback_page()関数を呼び出します。この関数では、ドライバは隔離されたページを自身のデータ構造に戻す必要があります

  2. 非LRU可動ページフラグ

    非LRU可動ページをサポートするためのページフラグは2つあります

    • PG_movable

      ドライバは以下の関数を使用してpage_lockの下でページを可動にする必要があります:

      void __SetPageMovable(struct page *page, struct address_space *mapping)

      移動ファミリ関数を登録する際にaddress_spaceの引数が必要です。厳密に言えば、PG_movableはstruct pageの実際のフラグではありません。代わりに、VMはpage->mappingの下位ビットを再利用して表現しています:

      #define PAGE_MAPPING_MOVABLE 0x2
page->mapping = page->mapping | PAGE_MAPPING_MOVABLE;

      そのため、ドライバはpage->mappingを直接アクセスすべきではありません。代わりに、page_mapping()関数を使用し、page_lockの下でpage->mappingの下位2ビットをマスクして正しい値を取得できます struct address_space.

      非LRU可動ページのテストには、VMが__PageMovable()関数をサポートしています。しかし、この関数は非LRU可動ページを正確に識別する保証は提供しません。なぜなら、page->mappingフィールドはstruct page内の他の変数と統合されているためです。ドライバがVMによってページを隔離後に解放した場合、page->mappingには安定した値が含まれず、PAGE_MAPPING_MOVABLEが設定されているにもかかわらず（__ClearPageMovableを参照）、このフィールドは信頼性がありません。ただし、ページが隔離された後であれば、LRUページはpage->mappingにPAGE_MAPPING_MOVABLEを設定できないため、__PageMovable()は呼び出しコストが低く、LRUか非LRU可動ページかに関わらず呼び出せます。これは、lock_page()によるより高コストなチェックよりも先に、非LRU可動ページのテストに適しています。

      非LRU可動ページを保証するため、VMはPageMovable()関数を提供しています。__PageMovable()とは異なり、PageMovable()はlock_page()の下でpage->mappingとmapping->a_ops->isolate_pageを検証します。lock_page()はpage->mappingの突然の破壊を防ぎます。

      __SetPageMovable()を使用するドライバは、ページを解放する前にpage_lock()の下で__ClearMovablePage()を介してフラグをクリアする必要があります。

    • PG_isolated

      複数のCPU間での同時隔離を防ぐため、VMはlock_page()の下で隔離されたページをPG_isolatedにマークします。そのため、CPUがPG_isolatedの非LRU可動ページに遭遇した場合、それをスキップできます。ドライバはフラグを操作する必要がありません。なぜなら、VMが自動的にフラグを設定またはクリアするからです。注意点として、ドライバがPG_isolatedページを確認した場合、それはVMによって隔離されたページであるため、page.lruフィールドを操作してはいけません。PG_isolatedフラグはPG_reclaimフラグと同一のため、ドライバは自身の目的でPG_isolatedを使用してはいけません。

移動の監視¶

以下のイベント（カウンタ）を使用してページの移動を監視できます。

  1. PGMIGRATE_SUCCESS: 正常なページ移動成功。各カウントはページが移動したことを示します。ページが非THPページだった場合、このカウントは1増加します。THPだった場合、このカウントはTHPのサブページ数だけ増加します。例えば、4KBサイズのベースページ（サブページ）を持つ単一の2MB THPの移動は、このカウントを512増加させます。

  2. PGMIGRATE_FAIL: 正常なページ移動失敗。PGMIGRATE_SUCCESSと同様のカウントルールが適用されます。THPだった場合、サブページ数だけカウントされます。

  3. THP_MIGRATION_SUCCESS: THPが分割せずに移動されました。

  4. THP_MIGRATION_FAIL: THPが移動できず、分割もできませんでした。

  5. THP_MIGRATION_SPLIT: THPが移行されたが、そのままで移行されなかった。まず、THPは分割する必要があった。分割後、サブページに対して移行再試行が行われた。

THP_MIGRATION_*イベントは、適切なPGMIGRATE_SUCCESSまたはPGMIGRATE_FAILイベントを更新する。たとえば、THPの移行失敗は、THP_MIGRATION_FAILとPGMIGRATE_FAILの両方が増加する原因となる。

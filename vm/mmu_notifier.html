ページテーブルロック内で通知が必要なのはいつですか？¶

pte/pmdをクリアする際、ページテーブルロックの下で（*_clear_flushコールの通知バージョンであるmmu_notifier_invalidate_rangeを介して）イベントを通知する選択肢があります。ただし、すべてのケースで通知が必要ではありません。

二次TLB（CPU TLB以外のもの、IOMMU TLBやデバイスTLBなど）の場合、デバイスがATS/PASIDなどの機能を使用してIOMMUを介してCPUページテーブルを歩くことでプロセスの仮想アドレス空間にアクセスするときがあります。pte/pmdをクリアする際、ページテーブルロックを保持しながら二次TLBに通知が必要なのは次の2つのケースのみです：

  1. mmu_notifier_invalidate_range_end()の前にページバックイングアドレスが解放されている場合

  2. ページテーブルエントリが新しいページを指すように更新される（COW、ゼロページへのライトフォールト、__replace_page()など）

ケースAは明らかに、デバイスが完全に異なるタスクによって使用される可能性のあるページに書き込むリスクを取ることを望んでいないためです。

ケースBはより微妙です。正しさを保つためには、以下の順序で動作させる必要があります：

  • ページテーブルロックを取得する

  • ページテーブルエントリをクリアし、通知する（[pmd/pte]p_huge_clear_flush_notify()）

  • ページテーブルエントリを新しいページを指すように設定する

ページテーブルエントリをクリアした後、新しいpte/pmd値を設定する前に通知を行わない場合、デバイスのメモリモデル（C11やC++11など）を破損させる可能性があります。

以下のシナリオを考慮してください（デバイスがATS/PASIDに似た機能を使用する場合）：

addrAとaddrBという2つのアドレスがあり、|addrA - addrB| >= PAGE_SIZEのとき、COWのためにこれらがライト保護されていると仮定します（Bの他のケースも同様です）。

[Time N] --------------------------------------------------------------------
CPU-thread-0  {try to write to addrA}
CPU-thread-1  {try to write to addrB}
CPU-thread-2  {}
CPU-thread-3  {}
DEV-thread-0  {read addrA and populate device TLB}
DEV-thread-2  {read addrB and populate device TLB}
[Time N+1] ------------------------------------------------------------------
CPU-thread-0  {COW_step0: {mmu_notifier_invalidate_range_start(addrA)}}
CPU-thread-1  {COW_step0: {mmu_notifier_invalidate_range_start(addrB)}}
CPU-thread-2  {}
CPU-thread-3  {}
DEV-thread-0  {}
DEV-thread-2  {}
[Time N+2] ------------------------------------------------------------------
CPU-thread-0  {COW_step1: {update page table to point to new page for addrA}}
CPU-thread-1  {COW_step1: {update page table to point to new page for addrB}}
CPU-thread-2  {}
CPU-thread-3  {}
DEV-thread-0  {}
DEV-thread-2  {}
[Time N+3] ------------------------------------------------------------------
CPU-thread-0  {preempted}
CPU-thread-1  {preempted}
CPU-thread-2  {write to addrA which is a write to new page}
CPU-thread-3  {}
DEV-thread-0  {}
DEV-thread-2  {}
[Time N+3] ------------------------------------------------------------------
CPU-thread-0  {preempted}
CPU-thread-1  {preempted}
CPU-thread-2  {}
CPU-thread-3  {write to addrB which is a write to new page}
DEV-thread-0  {}
DEV-thread-2  {}
[Time N+4] ------------------------------------------------------------------
CPU-thread-0  {preempted}
CPU-thread-1  {COW_step3: {mmu_notifier_invalidate_range_end(addrB)}}
CPU-thread-2  {}
CPU-thread-3  {}
DEV-thread-0  {}
DEV-thread-2  {}
[Time N+5] ------------------------------------------------------------------
CPU-thread-0  {preempted}
CPU-thread-1  {}
CPU-thread-2  {}
CPU-thread-3  {}
DEV-thread-0  {read addrA from old page}
DEV-thread-2  {read addrB from new page}

ここでは、時間N+2において、クリアされたページテーブルエントリが二次TLBの無効化通知とペアになっていなかったため、デバイスがaddrBの新しい値をaddrAの新しい値よりも先に見ることになります。これにより、デバイスの完全なメモリ順序が破綻します。

pteをライト保護に変更するか、同じ内容の新しいライト保護ページを指すように変更する場合（KSM）、mmu_notifier_invalidate_range_end()の外側でmmu_notifier_invalidate_rangeコールを遅延させても問題ありません。ページテーブルロックを解放した後で、mmu_notifier_invalidate_range_end()を呼び出す前にページテーブル更新を実行するスレッドがプリエンプションされる場合でも、これは成立します。

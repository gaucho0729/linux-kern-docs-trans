SLUBの短いユーザーガイド¶

SLUBの基本的な哲学はSLABとは大きく異なります。SLABでは、すべてのslabキャッシュのデバッグオプションを有効にするにはカーネルを再構築する必要があります。SLUBでは常にフルデバッグが含まれていますが、デフォルトでは無効になっています。SLUBは全体的なシステムパフォーマンスへの影響を避けるために、特定のslabのみにデバッグを有効にすることができます。これにより、バグの検出が難しくなるのを防ぎます。

デバッグを有効にするには、オプションを追加します slub_debug カーネル コマンドラインに追加します。これにより、すべてのslabに対してフルデバッグが有効になります。

通常は、次のコマン�ドを使用します slabinfo 統計データを取得し、slabに対して操作を行うコマンドを使用します。デフォルトでは slabinfo データが含まれているスラブのみを一覧表示します。コマンドを実行時のオプションについては、「slabinfo -h」を参照してください。 slabinfo コンパイル時に

gcc -o slabinfo tools/vm/slabinfo.c

いくつかの運用モードは slabinfo コマンドラインでslubデバッグが有効になっている必要があります。例えば、デバッグがオフの場合、トレース情報が取得できず、検証は一部のみ実行可能です。

slub_debugのより高度な使用例:¶

パラメータを指定できます slub_debug指定がない場合はフルデバッグが有効になります。形式:

slub_debug=<Debug-Options>

すべてのslabに対してオプションを有効にする

slub_debug=<Debug-Options>,<slab name1>,<slab name2>,…

特定のslabのみにオプションを有効にする（コンマの後にはスペースを空けない）

すべてのslabまたは選択したslab用のオプションブロックを複数指定できます。ブロックはセミコロンで区切られます。最後の「すべてのslab」ブロックは、選択したslabブロックにマッチするもの以外のすべてのslabに適用されます。最初の「選択したslab」ブロックにマッチするslabのオプションが適用されます。

利用可能なデバッグオプションは次の通りです。

F               Sanity checks on (enables SLAB_DEBUG_CONSISTENCY_CHECKS
                Sorry SLAB legacy issues)
Z               Red zoning
P               Poisoning (object and padding)
U               User tracking (free and alloc)
T               Trace (please only use on single slabs)
A               Enable failslab filter mark for the cache
O               Switch debugging off for caches that would have
                caused higher minimum slab orders
-               Switch all debugging off (useful if the kernel is
                configured with CONFIG_SLUB_DEBUG_ON)

たとえば、健全性チェックと赤ゾーニングのみで起動する場合は、以下のように指定します:

slub_debug=FZ

dentryキャッシュの問題を特定している場合は、以下を試してください:

slub_debug=,dentry

dentryキャッシュにのみデバッグを有効にすることができます。slab名の末尾にアスタリスクを付けることで、同じ接頭辞を持つすべてのslabをカバーできます。たとえば、以下のようにdentryキャッシュとすべてのkmalloc slabを毒化できます:

slub_debug=P,kmalloc-*,dentry

赤ゾーニングとトラッキングはslabの再配置を引き起こす可能性があります。dentryキャッシュに健全性チェックを適用するには以下のようにします:

slub_debug=F,dentry

デバッグオプションは、メタデータの保存により最小限のslabオーダーが増加する可能性があります（例: PAGE_SIZEオブジェクトサイズを持つキャッシュ）。これにより、メモリが少なくなる場合やメモリのフラグメンテーションが高い場合にslab割当エラーが発生する可能性が高くなります。このようなキャッシュのデバッグをデフォルトで無効にするには、以下を使用してください:

slub_debug=O

異なるslab名のリストに対して、オプションブロックを使用して異なるオプションを適用できます。これにより、dentryのレッドゾーニングとkmallocのユーザートラッキングが有効になります。他のslabにはデバッグが有効になりません:

slub_debug=Z,dentry;U,kmalloc-*

また、特定のキャッシュ（パフォーマンス的にあまり重要でないもの）を除き、すべてのキャッシュに対してオプション（例: sanity checks、poisoning）を有効化できます。これは、グローバルなデバッグオプションを指定し、'-'をオプションとしてslab名のリストを指定することで実現されます:

slub_debug=FZ;-,zs_handle,zspage

各slabのデバッグオプションの状態は、以下のファイルに記録されています:

/sys/kernel/slab/<slab name>/

ファイルに1が含まれている場合、オプションが有効になり、0は無効を意味します。'parameter'から取得したデバッグオプションは以下のファイルにマッピングされます: slub_debug 'parameter'から取得したデバッグオプションは以下のファイルにマッピングされます:

F       sanity_checks
Z       red_zone
P       poison
U       store_user
T       trace
A       failslab

トレーシングには注意してください。誤ったslabに適用すると、大量の情報が出力され、停止しなくなる可能性があります。

slabのマージング¶

デバッグオプションが指定されていない場合、SLUBはオーバーヘッドを減らし、オブジェクトのキャッシュホットネスを向上させるために類似したslabをマージする可能性があります。 slabinfo -a マージされたslabの一覧を表示します。

slabの検証¶

カーネルがslub_debugで起動されている場合、SLUBはすべてのオブジェクトを検証できます。そのためには、以下のツールが必要です。 slabinfo ツールを用意した後、以下を実行できます。

slabinfo -v

すべてのオブジェクトをテストします。出力はsyslogに生成されます。

slab debugが使われていない場合でも、より限定的な形で動作します。その場合 slabinfo -v すべての到達可能なオブジェクトをテストします。通常はCPUスラブと部分スラブに含まれています。フルスラブは非デバッグ状態ではSLUBによって追跡されません。

パフォーマンスの向上¶

ある程度、SLUBのパフォーマンスは、部分スラブを処理するためにリストロック(list_lock)を定期的に取得する必要があるため制限されています。このオーバーヘッドは、各スラブの割当順序によって制御されます。割当は以下のカーネルパラメータによって影響されます：

slub_min_objects

割当て順序が受け入れられるためには、1つのスラブに少なくとも収まるオブジェクト数を指定します。一般的に、slubはリストロック(list_lock)を参照することなくこの数の割当てをスラブ内で実行できます。競合が発生する可能性のある中央集約リソースを参照しません。

slub_min_order

スラブの最小順序を指定します。これは、 slub_min_objects.

slub_max_order

で指定された順序に、 slub_min_objects がもはやチェックされなくなるようにします。これは、SLUBが非常に大きな順序のページを生成しようとするのを防ぐために役立ちます slub_min_objects 大容量オブジェクトサイズのスラブキャッシュを1つの高順序ページに収めるために。コマンドラインパラメータ debug_guardpage_minorder=N (N > 0)を設定すると、 slub_max_order を0に強制します。これによりスラブ割当の最小可能な順序が設定されます。

SLUBが破損したオブジェクトに遭遇した場合（完全な検出にはカーネルをslub_debugで起動する必要があります）、以下の出力がsyslogにダンプされます:

  1. 発生した問題の説明

    これはシステムログに記録されるメッセージで、以下のように始まります:

    ===============================================
BUG <slab cache affected>: <What went wrong>
-----------------------------------------------

INFO: <corruption start>-<corruption_end> <more info>
INFO: Slab <address> <slab information>
INFO: Object <address> <object information>
INFO: Allocated in <kernel function> age=<jiffies since alloc> cpu=<allocated by
   cpu> pid=<pid of the process>
INFO: Freed in <kernel function> age=<jiffies since free> cpu=<freed by cpu>
   pid=<pid of the process>

    (オブジェクトの割り当て/解放情報は、slabにSLAB_STORE_USERが設定されている場合にのみ利用可能です。slub_debugはこのオプションを設定します)

  2. オブジェクトに関与していた場合のオブジェクトの内容。

    BUG SLUB行の後にさまざまな種類の行が続くことがあります:

    Bytes b4 <address><bytes>

    オブジェクトの問題が検出された場所の直前のいくつかのバイトを表示します。オブジェクトの開始位置で腐敗が止まらない場合に役立つことがあります。

    オブジェクト <address><bytes>

    オブジェクトのバイト。オブジェクトが非アクティブな場合、バイトは通常ポイズン値を含みます。非ポイズン値がある場合は、オブジェクトの解放後に書いたことが原因の腐敗を示します。

    Redzone <address><bytes>

    オブジェクトの後に続くレッドゾーン。レッドゾーンはオブジェクトの後に書いたことを検出するために使用されます。すべてのバイトは常に同じ値を保つ必要があります。変動がある場合は、オブジェクトの境界を超えて書いたことが原因です。

    (レッドゾーン情報はSLAB_RED_ZONEが設定されている場合にのみ利用可能です。slub_debugはこのオプションを設定します)

    Padding <address><bytes>

    次のオブジェクトを正しくアライメントさせるために使用される未使用データ。デバッグの場合、少なくとも4バイトのパディングを確保します。これにより、オブジェクトの前での書込みを検出できます。

  3. スタックダンプ

    スタックダンプはエラーが検出された場所を記録します。腐敗の原因は、オブジェクトを割り当てたか、解放した関数を確認することでより確実に特定できます。

  4. システムの継続的な運用を確保するための問題の処置方法に関するレポート。

    これらはシステムログに記録されるメッセージで、以下のように始まります:

    FIX <slab cache affected>: <corrective action taken>

    上記の例では、SLUBがアクティブなオブジェクトのレッドゾーンが上書きされたことを検出しました。ここでは、8文字の文字列が8文字の長さを持つスラブに書き込まれました。ただし、8文字の文字列には終端の0が必要です。その0がレッドゾーンフィールドの最初のバイトを上書きしました。問題の詳細を報告した後、FIX SLUBメッセージがSLUBがレッドゾーンを正しい値に戻し、その後システムの運用が継続することを伝えます。

緊急操作¶

最小限のデバッグ（健全性チェックのみ）は、以下のように起動することで有効になります:

slub_debug=F

これにより、slub のレジリエンス機能が有効になり、システムが悪意のあるカーネルコンポーネントがオブジェクトを破壊し続ける場合でも動作し続けるようになります。これは生産環境のシステムにとって重要かもしれません。パフォーマンスは健全性チェックによって影響を受け、syslog に連続するエラーメッセージが表示されるかもしれませんが、追加のメモリは使用されません（フルデバッグとは異なります）。

保証はありません。カーネルコンポーネントはまだ修正が必要です。パフォーマンスをさらに最適化するには、破壊が発生しているスラブを特定し、そのキャッシュだけにデバッグを有効にすることができます。

I.e.:

slub_debug=F,dentry

オブジェクトの終わりを超えて書き込まれた場合に破壊が発生する場合は、他のオブジェクトの先頭を破壊するのを防ぐために、レッドゾーンを有効にするのが推奨されます：

slub_debug=FZ,dentry

拡張スラブ情報モードとプロット¶

以下の slabinfo ツールには特別な「拡張」（「-X」）モードがあり、以下を含みます：

  • スラブキャッシュの合計

  • サイズでソートされたスラブ（最大 -N <num> スラブ、デフォルト 1）

  • 損失でソートされたスラブ（最大 -N <num> スラブ、デフォルト 1）

さらに、このモードでは slabinfo 動的にサイズ（G/M/K）をスケールしないで、すべてをバイト単位で報告します（この機能は「-B」オプションで他のスラブ情報モードにも利用可能です）これにより、報告がより正確かつ正確になります。さらに、ある意味では、 -X モードはスラブの挙動の分析を簡略化します。なぜなら、その出力は ``slabinfo-gnuplot.sh` スクリプトでプロットできるからです。 これにより、数値を眺める（大量の数値）ことから、視覚的な分析に移行する分析が可能になります。

プロットを生成するには：

  1. スラブ情報拡張レコードを収集します。たとえば：

    while [ 1 ]; do slabinfo -X >> FOO_STATS; sleep 1; done

  2. stats ファイル(-s)を slabinfo-gnuplot.sh スクリプトに渡します：

    slabinfo-gnuplot.sh FOO_STATS [FOO_STATS2 .. FOO_STATSN]

    以下の slabinfo-gnuplot.sh スクリプトは収集したレコードを前処理し、STATS ファイルごとに 3 つの png ファイル（および 3 つの前処理キャッシュファイル）を生成します：- スラブキャッシュの合計: FOO_STATS-totals.png - サイズでソートされたスラブ: FOO_STATS-slabs-by-size.png - 損失でソートされたスラブ: FOO_STATS-slabs-by-loss.png

また、 slabinfo-gnuplot.sh が役立つのは、あるコード変更の「以前」および「以後」のスラブの挙動を比較する必要がある場合です。ご支援のため、 slabinfo-gnuplot.sh スクリプトは異なる測定からの スラブキャッシュの合計 セクションを「-t」モードで、すべての生成された前処理 *-totals を渡して統合できます。N 個のプロットを視覚的に比較するには：

  1. 必要なだけ STATS1, STATS2, .. STATSN ファイルを収集します：

    while [ 1 ]; do slabinfo -X >> STATS<X>; sleep 1; done

  2. それらの STATS ファイルを前処理します：

    slabinfo-gnuplot.sh STATS1 STATS2 .. STATSN

  3. モジュールのアンロードを許可します。 slabinfo-gnuplot.sh 「-t」モードで、生成されたすべての前処理 *-totals を渡します：

    slabinfo-gnuplot.sh -t STATS1-totals STATS2-totals .. STATSN-totals

    これにより、1 つのプロット（png ファイル）が生成されます。

    プロットは予想通り大きく、そのため一部の変動や小さなピークは見逃される可能性があります。その対処として、 slabinfo-gnuplot.sh は「拡大/縮小」を実行するための 2 つのオプションを持っています：

    1. -s %d,%d – 既定の画像幅と高さを上書きします

    2. -r %d,%d – 指定するサンプルの範囲を（たとえば、 slabinfo -X >> FOO_STATS; sleep 1; 場合、使用する -r 40,60 範囲を指定すると、40秒から60秒にかけて収集されたサンプルのみをプロットします。

zsmalloc¶

このメモリ確保アルゴリズムはzramと併用するための設計であり、低メモリ状態でも安定して動作するように設計されています。特に、メモリ負荷が高い状態でも高次のページ割当を試みることはありません。一方で、単一の0次のページのみを用いる場合、非常に高いメモリの断片化が発生します。PAGE_SIZE/2以上のサイズのオブジェクトは、常に1つのページを占有するためです。これはその前身(xvmalloc)の主な問題の一つでした。

これらの問題を解決するために、zsmallocは複数の0次のページを確保し、'struct page'フィールドを用いてそれらを連結します。この連結されたページは単一の高次のページとして扱われ、オブジェクトは0次のページ境界を跨ぐことができます。コードではこれらの連結ページを「zspage」と呼ばれる単一のエンティティとして扱います。

簡便のため、zsmallocはPAGE_SIZE以下のサイズのオブジェクトのみを確保します。これは現在のすべてのユーザーの要件を満たしており（最悪の場合、ページは圧縮不可能で「そのまま」保存されるため）、このサイズを超える確保要求は失敗します（zs_malloc参照）。

さらに、zs_malloc()は参照可能なポインタを返しません。代わりに、確保されたオブジェクトの実際の位置を符号化した不透明なハンドル（unsigned long）を返します。この間接参照の理由は、zsmallocがzspageを永続的にマップ保持しないからです。32ビットシステムでは、カーネル空間の仮想アドレス領域が非常に小さいため、マップ保持が問題となるからです。そのため、確保したメモリを使用する前に、zs_map_object()を呼び出して有効なポインタを取得し、その後zs_unmap_object()でマップを解除する必要があります。

stat¶

CONFIG_ZSMALLOC_STATを有効にすると、zsmallocの内部情報を以下のように確認できます /sys/kernel/debug/zsmalloc/<user name>. ここにstat出力のサンプルを示します：

# cat /sys/kernel/debug/zsmalloc/zram0/classes

class  size almost_full almost_empty obj_allocated   obj_used pages_used pages_per_zspage

   10   192           1            0          2880       2872        135                3

クラス

index

size

オブジェクトサイズ zspageが保持するオブジェクトのサイズ

almost_empty

ZS_ALMOST_EMPTY状態のzspageの数（以下参照）

almost_full

ZS_ALMOST_FULL状態のzspageの数（以下参照）

obj_allocated

確保されたオブジェクトの数

obj_used

ユーザーに確保されたオブジェクトの数

pages_used

このクラスに割り当てられたページ数

pages_per_zspage

1つのzspageに使用する0次のページ数

n <= N / fのとき、zspageをZS_ALMOST_EMPTY状態のグループに割り当てます。ここで

  • n = 確保されたオブジェクト数

  • N = zspageが保持できるオブジェクトの総数

  • f = fullness_threshold_frac（現在は4）

同様に、zspageは以下のようになります：

  • n > N / fのときZS_ALMOST_FULL状態

  • n == 0のときZS_EMPTY状態

  • n == NのときZS_FULL状態

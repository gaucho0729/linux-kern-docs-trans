異質メモリ管理（HMM）¶

非従来のメモリ（GPUなどのデバイスメモリなど）を通常のカーネル処理に統合するためのインフラストラクチャとヘルパーを提供し、この仕組みの柱となるのが、このようなメモリ用に特別に設計された struct page です（このドキュメントのセクション5〜7を参照）。

HMM は、SVM（Share Virtual Memory）のオプションヘルパーも提供しており、デバイスが CPU と同様にプログラムアドレスを透明にアクセスできるようにします。つまり、CPU で有効なポインタはデバイスでも有効なポインタになります。これは、GPU、DSP、FPGA を使用した高度なヘテロジニアスコンピューティングを簡易化するために必須となっています。

このドキュメントは以下の構成であります：第1セクションでは、デバイス固有のメモリアロケータを使用する際の問題点を説明し、第2セクションでは多くのプラットフォームに共通するハードウェアの制限を解説します。第3セクションでは HMM の設計概要を、第4セクションでは CPU ページテーブルのミラーリングと HMM の役割を説明します。第5セクションでは、デバイスメモリがカーネル内でどのように表現されるかを、最後に第6セクションではデバイスDMAエンジンを活用するための新しいミグレーションヘルパーを紹介します。

デバイス固有のメモリアロケータを使用する際の問題¶

ボードメモリが数ギガバイト規模にあるデバイス（例：GPU）は、従来はデバイス固有のドライバAPIを通じてメモリを管理してきました。これにより、デバイスドライバが管理するメモリと通常のアプリケーションメモリ（プライベート匿名、共有メモリ、または通常ファイルバックドメモリ）の間で断絶が生じています。ここからはこの状況を「分割アドレス空間」と呼びます。一方、「共有アドレス空間」とは、アプリケーションメモリのどの領域もデバイスが透明に利用可能である状態を指します。

分割アドレス空間は、デバイスがデバイス固有のAPIを通じてのみメモリをアクセスできるため発生します。これは、プログラム内のすべてのメモリオブジェクトがデバイスの観点から等しく扱われないことを意味し、幅広いライブラリを依存する大規模なプログラムには複雑さをもたらします。

具体的には、GPUなどのデバイスを活用したいコードは、一般的なメモリ割当（malloc、mmap private、mmap share）とデバイスドライバAPIで割当たったメモリ（これは最終的にデバイスファイルのmmapになる）の間でオブジェクトをコピーする必要があります。

フラットなデータセット（配列、グリッド、画像など）ではこれは比較的簡単に実現できますが、複雑なデータセット（リスト、木など）では正しく実装するのは困難です。複雑なデータセットを複製するには、その要素間のポインタ関係をすべて再マッピングする必要があります。これはエラーが発生しやすく、複製されたデータセットとアドレスによりデバッグが難しくなります。

分割されたアドレス空間は、ライブラリがコアプログラムや他のライブラリから取得したデータを透明に利用できなくなります。そのため、各ライブラリがデバイス固有のメモリ割当を使用して入力データセットを複製する必要があり、大規模なプロジェクトではリソースの浪費が発生します。

各デバイス固有のメモリ割当を入力または出力として受け入れるためのライブラリAPIを複製する選択肢は現実的ではありません。これによりライブラリエントリポイントが組み合わせ爆発的に増加します。

さらに、高レベル言語構造（C++だけでなく他の言語でも）の進化により、プログラマの知識を問わずコンパイラがGPUや他のデバイスを活用できるようになりました。一部のコンパイラが特定するパターンは共有アドレス空間のみで実現可能です。また、他のパターンにも共有アドレス空間を使用することがより現実的です。

I/Oバス、デバイスメモリの特性¶

I/Oバスはいくつかの制限により共有アドレス空間を制限します。ほとんどのI/Oバスはデバイスからメインメモリへの基本的なメモリアクセスのみを許可し、キャッシュコヒーレンシーはしばしばオプションです。CPUからデバイスメモリへのアクセスはさらに制限されており、多くの場合キャッシュコヒーレントではありません。

PCIEバスのみを考慮すると、デバイスがメインメモリ（IOMMUを通じて）にアクセスし、CPUとキャッシュコヒーレントになることが可能です。しかし、デバイスがメインメモリに対して行えるアトミック操作は限定されています。逆に、CPUはデバイスメモリの限定された範囲しかアクセスできず、アトミック操作を実行できません。したがって、カーネルの観点からデバイスメモリは通常のメモリとみなせません。

もう一つの制限要因は、帯域幅の限界(~32GBytes/s で PCIE 4.0 と 16 レーン)です。これは最速の GPU メモリ帯域幅(1 TBytes/s)の約33分の1に過ぎません。最終的な制限はレイテンシーです。デバイスが主記憶からアクセスする際のレイテンシーは、デバイスが自身のメモリにアクセスするときと比べて1桁以上高いです。

一部のプラットフォームでは、これらの制限に対応するため新しいI/OバスやPCIEへの拡張・改良(OpenCAPI, CCIX)が開発されています。これらは主にCPUとデバイス間の双方向キャッシュコヒーレンスを許可し、アーキテクチャがサポートするすべてのアトミック操作を可能にします。残念ながら、すべてのプラットフォームがこのトレンドに従うわけではなく、一部の大規模なアーキテクチャはハードウェアの解決策が提供されていません。

共有アドレス空間が意味を持つためには、デバイスが任意のメモリにアクセスできるだけでなく、デバイスが使用中にメモリをデバイスメモリに移動させることも許可しなければなりません(移動中にCPUのアクセスをブロックする必要があります)。

共有アドレス空間とミグレーション¶

HMMは2つの主な機能を提供することを目的としています。1つ目の機能は、CPUページテーブルをデバイスページテーブルに複製することで、プロセスアドレス空間内の有効な主記憶アドレスのすべてが同じ物理メモリを指すようにするものです。

これを実現するため、HMMはデバイスページテーブルを更新する際のCPUページテーブルの更新を追跡するヘルパー関数を提供します。デバイスページテーブルの更新はCPUページテーブルの更新ほど簡単ではありません。デバイスページテーブルを更新するには、バッファ(または事前に割り当てたバッファプール)を確保し、その中にGPU固有のコマンド(アンマップ、キャッシュ無効化、フラッシュなど)を記述する必要があります。これはすべてのデバイスに共通のコードで実行することはできません。そのためHMMはハードウェア固有の詳細をデバイスドライバに委譲するよう、共通処理をヘルパー関数として抽出しています。

HMMが提供する2つ目のメカニズムは、デバイスメモリの各ページに対応するstruct pageを割り当てる新しいZONE_DEVICEメモリです。これらのページはCPUがマップできない特殊なページです。しかし、これらを用いることで既存の移動メカニズムを活用して主記憶をデバイスメモリに移動させることができ、CPUの観点からはディスクにスワップアウトされたページのように見えます。struct pageを用いることで既存のmmメカニズムとの統合が最も簡単で洗練されています。ここでもHMMはヘルパー関数を提供し、まずデバイスメモリ用のZONE_DEVICEメモリをホットプラグする処理、次に移動処理を実行します。移動の対象やタイミングに関するポリシー決定はデバイスドライバに委譲されています。

デバイスページへのCPUアクセスはページフォールトを引き起こし、メインメモリへの移動を開始します。たとえば、あるCPUアドレスAをバックするページがメインメモリページからデバイスページに移動した場合、アドレスAへのCPUアクセスはページフォールトを引き起こし、メインメモリへの移動を開始します。

これらの2つの機能により、HMMはデバイスがプロセスアドレス空間をミラーリングし、CPUとデバイスのページテーブルを同期させるとともに、デバイスがアクティブに使用しているデータセットの一部をデバイスメモリに活用することを可能にします。

アドレス空間ミラーリングの実装とAPI¶

アドレス空間ミラーリングの主な目的は、CPUページテーブルの範囲をデバイスページテーブルに複製することです。HMMはこの同期を保持します。プロセスアドレス空間をミラーリングしたいデバイスドライバーは、まずmmu_interval_notifierの登録を開始する必要があります。

int mmu_interval_notifier_insert(struct mmu_interval_notifier *interval_sub,
                                 struct mm_struct *mm, unsigned long start,
                                 unsigned long length,
                                 const struct mmu_interval_notifier_ops *ops);

invalidate()コールバック中にデバイスドライバーは範囲の更新操作（範囲を読み取り専用に設定、または完全にアンマップなど）を行う必要があります。デバイスはドライバーのコールバックが返る前に更新を完了する必要があります。

デバイスドライバーが仮想アドレス範囲を埋める場合、以下の関数を使用できます：

int hmm_range_fault(struct hmm_range *range);

読み込み専用エントリまたは存在しないエントリへの書き込みアクセスが要求された場合、ページフォールトが発生します（以下参照）。ページフォールトはCPUのページフォールトと同様に一般的なmmページフォールトコードパスを使用します。

両方の関数はCPUページテーブルエントリをpfns配列引数にコピーします。この配列の各エントリは仮想範囲内のアドレスに対応します。HMMはドライバーが特殊なCPUページテーブルエントリを識別するのに役立つフラグのセットを提供します。

sync_cpu_device_pagetables()コールバック内のロックは、ドライバーが適切に同期を保つために最も重要な要素です。使用パターンは以下の通りです：

int driver_populate_range(...)
{
     struct hmm_range range;
     ...

     range.notifier = &interval_sub;
     range.start = ...;
     range.end = ...;
     range.hmm_pfns = ...;

     if (!mmget_not_zero(interval_sub->notifier.mm))
         return -EFAULT;

again:
     range.notifier_seq = mmu_interval_read_begin(&interval_sub);
     mmap_read_lock(mm);
     ret = hmm_range_fault(&range);
     if (ret) {
         mmap_read_unlock(mm);
         if (ret == -EBUSY)
                goto again;
         return ret;
     }
     mmap_read_unlock(mm);

     take_lock(driver->update);
     if (mmu_interval_read_retry(&ni, range.notifier_seq) {
         release_lock(driver->update);
         goto again;
     }

     /* Use pfns array content to update device page table,
      * under the update lock */

     release_lock(driver->update);
     return 0;
}

ドライバ->update ロックは、ドライバーがinvalidate()コールバック内で取得する同じロックです。mmu_interval_read_retry()を呼び出す前にこのロックを保持する必要があります。これにより、同時進行するCPUページテーブル更新との競合を回避します。

default_flags と pfn_flags_mask を活用する¶

hmm_range構造体には、default_flagsとpfn_flags_maskという2つのフィールドがあり、pfns配列の各エントリではなく、全体のフォールトまたはスナップショットポリシーを指定します。

たとえば、デバイスドライバーが範囲のページで少なくとも読み取り権限を持つ場合、以下のように設定します：

range->default_flags = HMM_PFN_REQ_FAULT;
range->pfn_flags_mask = 0;

そして、上記のようにhmm_range_fault()を呼び出します。これにより、範囲内のすべてのページが少なくとも読み取り権限を持つように埋められます。

では、ドライバーが範囲内の1ページを除いて同じ操作を行うが、そのページには書き込み権限を保有したいとします。この場合、ドライバーは以下の設定を行います:

range->default_flags = HMM_PFN_REQ_FAULT;
range->pfn_flags_mask = HMM_PFN_REQ_WRITE;
range->pfns[index_of_write] = HMM_PFN_REQ_WRITE;

これにより、HMMは範囲内のすべてのページで少なくとも読み取り（つまり有効）であるページをフォールト処理し、アドレス == range->start + (index_of_write << PAGE_SHIFT) の場合、書き込み権限でフォールトを発生させます。つまり、CPUのpteが書き込み権限を設定していない場合、HMMはhandle_mm_fault()を呼び出します。

hmm_range_faultが完了した後、フラグビットはページテーブルの現在の状態に設定されます。つまり、ページが書き込み可能な場合、HMM_PFN_VALID | HMM_PFN_WRITEが設定されます。

コアカーネルの観点からデバイスメモリを表現・管理する¶

デバイスメモリをサポートするため、いくつかの設計が試されました。最初の設計では、デバイス固有のデータ構造を使用して移動メモリに関する情報を保持し、HMMはmmコードのさまざまな場所に自身を接続して、デバイスメモリでバックアップされたアドレスへのアクセスを処理しました。しかし、これはstruct pageのほとんどのフィールドを再実装し、多くのカーネルコードパスを更新する必要がありました。

ほとんどのカーネルコードパスは、ページの背後にあるメモリにアクセスすることを試みず、struct pageの内容のみに注目しています。そのため、HMMはデバイスメモリにstruct pageを直接使用することに切り替え、ほとんどのカーネルコードパスは差異を認識していません。ただし、CPU側からこれらのページをマッピングしようとする者がいないことを確認する必要があります。

デバイスメモリとの間でのミグレーション¶

CPUがデバイスメモリを直接アクセスできないため、デバイスドライバーはハードウェアDMAやデバイス固有のロード/ストア命令を使用してデータを移動させる必要があります。migrate_vma_setup()、migrate_vma_pages()、migrate_v3_finalize()関数は、ドライバーの記述を簡単にするため、またドライバー間で共通コードを中央化するため設計されています。

ページをデバイスプライベートメモリに移動する前に、特別なデバイスプライベート struct page ページが必要です。これらは特殊な「スワップ」ページテーブルエントリとして使用され、CPUプロセスがデバイスプライベートメモリに移動したページをアクセスしようとするとフォールトを発生させます。

これらは以下の関数で割り当てられ、解放されます:

struct resource *res;
struct dev_pagemap pagemap;

res = request_free_mem_region(&iomem_resource, /* number of bytes */,
                              "name of driver resource");
pagemap.type = MEMORY_DEVICE_PRIVATE;
pagemap.range.start = res->start;
pagemap.range.end = res->end;
pagemap.nr_range = 1;
pagemap.ops = &device_devmem_ops;
memremap_pages(&pagemap, numa_node_id());

memunmap_pages(&pagemap);
release_mem_region(pagemap.range.start, range_len(&pagemap.range));

また、 devm_request_free_mem_region(), devm_memremap_pages(), devm_memunmap_pages(), および devm_release_mem_region() が、リソースが特定の struct device.

に結びつけられる場合に使用されます。全体的な移動ステップは、システムメモリ内のNUMAページの移動（参照 ページの移動) と類似していますが、ステップはデバイスドライバ固有のコードと共有された共通コードに分かれています:

  1. mmap_read_lock()

    デバイスドライバーは、migrate_vma_setup() に struct vm_area_struct を渡す必要があります。そのため、mmap_read_lock() または mmap_write_lock() は移動期間中保持する必要があります。

  2. migrate_vma_setup(struct migrate_vma *args)

    デバイスドライバーは、 struct migrate_vma フィールドとポインタをmigrate_vma_setup()に渡します。このフィールドは、どのソースページが移動するかをフィルタリングするために使用されます。たとえば、設定するとシステムメモリのみが移動し、 args->flags はデバイスプライベートメモリに存在するページのみを移動します。後者のフラグが設定されている場合、このフィールドはドライバが所有するデバイスプライベートページを特定するために使用されます。これにより、他のデバイスに存在するデバイスプライベートページの移動を試みることを防ぎます。現在は、匿名プライベートVMA範囲のみがシステムメモリやデバイスプライベートメモリに移動可能です。 MIGRATE_VMA_SELECT_SYSTEM システムメモリのみが移動し、 MIGRATE_VMA_SELECT_DEVICE_PRIVATE デバイスプライベートメモリに存在するページのみを移動します。後者のフラグが設定されている場合、このフィールドはドライバが所有するデバイスプライベートページを特定するために使用されます。これにより、他のデバイスに存在するデバイスプライベートページの移動を試みることを防ぎます。現在は、匿名プライベートVMA範囲のみがシステムメモリやデバイスプライベートメモロリに移動可能です。 args->pgmap_owner migrate_vma_setup()が最初に行うステップの一つは、ページテーブルのウォークを埋めるために周囲の呼び出しで他のデバイスのMMUを無効化することです。この際、

    配列に移動するPFNを記録します。この mmu_notifier_invalidate_range_start(() および mmu_notifier_invalidate_range_end() コールバックは、 args->src フィールドが invalidate_range_start() に設定されている場合、 struct mmu_notifier_range これは、そのコア内のすべての論理CPU（SMTスレッド）が event フィールドが MMU_NOTIFY_MIGRATE 2.5開発シリーズで導入された形式です。 migrate_pgmap_owner フィールドがmigrate_vma_setup()に渡されたものに設定されます。これにより、デバイスドライバは無効化コールバックをスキップし、実際に移動しているデバイスプライベートMMUマッピングのみを無効化できます。この説明は次のセクションでより詳しく説明します。 args->pgmap_owner ページテーブルをウォークしている間、

    エントリが有効な「ゼロ」PFNを pte_none() または is_zero_pfn() 配列に格納します。これにより、ドライバはデバイスプライベートメモリを割り当てて初期化する代わりに、ゼロページをコピーするのを避けることができます。システムメモリまたはデバイスプライベート構造ページへの有効なPTEエントリは、 args->src でロックされ、LRUから隔離されます（システムメモリの場合、デバイスプライベートページはLRUに存在しないため）、プロセスからマップ解除され、元のPTEの代わりに特別なマиграーションPTEが挿入されます。migrate_vma_setup()はさらに、 lock_page()をクリアします。 args->dst 配列を表しています。

  3. デバイスドライバは宛先ページを割り当て、ソースページを宛先ページにコピーします。

    ドライバは各 src エントリを確認し、 MIGRATE_PFN_MIGRATE ビットが設定されているかを確認し、移動しないエントリはスキップします。ドライバはまた、そのページの dst 配列を埋めないことで、ページの移動をスキップすることも選択できます。

    ドライバは、デバイスプライベート構造ページまたはシステムメモリページを割り当て、 lock_page()でページをロックし、 dst 配列のエントリを以下のように埋めます：

    dst[i] = migrate_pfn(page_to_pfn(dpage)) | MIGRATE_PFN_LOCKED;

    ドライバがこのページが移動していることを知った後、デバイスプライベートMMUマッピングを無効化し、デバイスプライベートメモリをシステムメモリまたは他のデバイスプライベートページにコピーできます。コアLinuxカーネルがCPUページテーブルの無効化を処理するため、デバイスドライバは自身のMMUマッピングのみを無効化する必要がります。

    ドライバは migrate_pfn_to_page(src[i]) を使用して、ソースの struct page を取得し、ポインタが NULL である場合（ソースページがシステムメモリにポップュレーションされていないことを意味する）、ソースページを宛先にコピーするか、宛先デバイスプライベートメモリをクリアできます。

  4. migrate_vma_pages()

    このステップが実際にマиграーションが「コミットされる」場所です。

メモリcgroup（memcg）とRSSアカウント¶

現時点では、デバイスメモリはrssカウンターで通常のページと同じようにカウントされます（デバイスページが匿名メモリに使用される場合は匿名、ファイルバックドページに使用される場合はファイル、共有メモリに使用される場合はshmem）。これは、既存のアプリケーションがデバイスメモリを使用することを知らなかったとしても動作に影響を与えないようにするための意図的な選択です。

デメリットとして、デバイスメモリを使用しているアプリケーションが大量のシステムメモリを使用していない場合、OOMキラーがそのアプリケーションを終了させる可能性があり、システムメモリを多く解放しない可能性があります。アプリケーションやシステムがメモリ圧力下でどのように反応するかの実世界での経験を収集した後、デバイスメモリを異なる方法でカウントするかどうかを決定したいと考えています。

メモリcgroupにも同じ決定がされました。デバイスメモリページは、通常のページと同じメモリcgroupにカウントされます。これにより、デバイスメモリとの間での移動が簡単になります。また、デバイスメモリから通常メモリへの移動が失敗することはありません。これは、メモリcgroupの制限を超えるためです。デバイスメモリの使用状況やそのメモリリソース制御への影響をより多く経験した後、この選択肢を再考するかもしれません。

注意点として、デバイスドライバーによってもGUPを通じてもデバイスメモリは固定されず、したがってプロセス終了時に常に解放されます。共有メモリやファイルバックドメモリの場合、最後の参照が解除されたときにも同様です。

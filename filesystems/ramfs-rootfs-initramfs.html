ディスクレスシステム（たとえばXターミナルやプリンターサーバーなど）を使用するには、ルートファイルシステムがディスク以外のデバイス上に存在する必要があります。これはinitramfs（参照：Ramfs, rootfs and initramfs）やramdisk（参照：Ramfs, rootfs and initramfs）やNFS経由でマウントされたファイルシステムを使用する場合です。以下のテキストではNFSをルートファイルシステムとして使用する方法について説明します。このテキストの後半では、「クライアント」とはディスクレスシステムを、「サーバー」とはNFSサーバーを指します。¶

ramfsとは何ですか？¶

ramfsは、Linuxのディスクキャッシュメカニズム（ページキャッシュとdentryキャッシュ）を動的にリサイズ可能なRAMベースのファイルシステムとしてエクスポートする非常に単純なファイルシステムです。

通常、すべてのファイルはメモリでキャッシュされます。バックイングストア（ファイルシステムがマウントされているブロックデバイスなど）から読み込まれたデータページは、再度必要になる可能性があるため保持されますが、仮想メモリシステムが他の用途にメモリを必要とする場合、クリーン（解放可能）とマークされます。同様に、ファイルに書かれたデータはバックイングストアに書き込まれた時点でクリーンとマークされますが、キャッシュ目的で保持され続けます。このようなメカニズム（dentryキャッシュ）により、ディレクトリへのアクセスが大幅に高速化されます。

ramfsではバックイングストアがありません。ramfsに書かれたファイルは通常通りdentryとページキャッシュを割り当てますが、どこにも書き出す場所がないため、ページは常にクリーンとマークされず、仮想メモリシステムがメモリを再利用しようとする際には解放されません。

ramfsを実装するに必要なコード量は極めて小さく、すべての処理は既存のLinuxキャッシュインフラストラクチャによって行われます。要するに、ディスクキャッシュをファイルシステムとしてマウントしているだけです。そのため、menuconfigを通じて削除可能なオプションではありません。空間節約効果は無視できるほど小さいからです。

ramfsとramdisk:¶

古い「ramディスク」メカニズムでは、RAMの一部を合成ブロックデバイスとして作り、ファイルシステムのバックイングストアとして使用しました。このブロックデバイスは固定サイズであり、マウントされたファイルシステムも固定サイズでした。ramディスクを使用するには、仮想ブロックデバイスのメモリをページキャッシュにコピー（変更内容も逆に取り出す）し、dentryを生成・破棄する必要があり、さらにext2などのファイルシステムドライバーが必要でした。

ramfsと比較すると、ramディスクはメモリ（およびメモリバス帯域幅）を無駄にし、CPUに不要な作業を強制し、CPUキャッシュを汚染します。（ページテーブルを操作してコピーを回避するトリックもありますが、複雑で、結局コピーと同じくらいコストがかかるため実用的ではありません。）重要なのは、ramfsが行っているすべての処理は、ファイルアクセスがページキャッシュとdentryキャッシュを通じて行われるため、必ず行われる必要があります。ramディスクは本来不要であり、ramfsは内部的にずっとシンプルです。

ramdisksが半分に古くなったもう一つの理由は、ループバックデバイスの導入により、メモリのチャンクではなくファイルから合成ブロックデバイスを作成するより柔軟で便利な方法が提供されたためです。詳細についてはlosetup (8)を参照してください。

ramfsとtmpfs:¶

ramfsの欠点の一つは、メモリをすべて使い果たすまでデータを書き続けることができ、仮想メモリがバックイングストア（スワップ領域ではなく）にファイルを書くべきだと考えているため、データを解放できなくなることです。ramfsにはバックイングストアが存在しないため、このため、ramfsのマウントに書き込みアクセスを許可するにはroot（または信頼できるユーザー）のみが許可されるべきです。

サイズ制限を追加し、データをスワップ領域に書き込む機能を備えたramfsの派生版であるtmpfsが作成されました。通常のユーザーにもtmpfsのマウントに書き込みアクセスを許可できます。参照: Tmpfs 詳しくは

rootfsとは何ですか？¶

rootfsは、2.6系システムで常に存在するramfs（またはtmpfsが有効な場合）の特別なインスタンスです。rootfsをアンマウントできない理由は、initプロセスをkillできない理由とほぼ同じです。特殊なコードで空リストをチェック・処理するよりも、カーネルが特定のリストが空にならないようにする方が小さくてシンプルです。

ほとんどのシステムではrootfs上に別のファイルシステムをマウントし、rootfs自体は無視します。空のramfsインスタンスが占めるスペースは非常に小さいです。

CONFIG_TMPFSが有効な場合、rootfsはデフォルトでtmpfsを使用します。ramfsを強制的に使用するには、カーネルコマンドラインに「rootfstype=ramfs」を追加してください。

initramfsとは何ですか？¶

すべての2.6系Linuxカーネルには、gzippedされた「cpio」形式のアーカイブが含まれており、カーネルが起動時にrootfsに展開されます。展開後、カーネルはrootfsに「init」というファイルが存在するか確認し、存在する場合はPID 1として実行します。このinitプロセスがシステムを完全に起動し、実際のルートデバイス（必要に応じて）を検出・マウントする責任があります。rootfsにcpioアーカイブが展開された後、initプログラムが見つからない場合、カーネルは古いコードにフォールバックし、ルートパーティションを検出・マウントした後、/sbin/initの変異形を実行します。

これは古いinitrdとはいくつかの点で異なります:

  • 古いinitrdは常に別ファイルでしたが、initramfsアーカイブはlinuxカーネルイメージにリンクされています。（ディレクトリ linux-*/usr はビルド中にこのアーカイブを生成するために用意されています。)

  • 古いinitrdファイルは、gzip圧縮されたファイルシステムイメージ（ext2などのファイル形式で、カーネルにドライバを組み込む必要があるもの）であり、新しいinitramfsアーカイブはgzip圧縮されたcpioアーカイブ（tarと似た形式だがより単純で、cpio(1)と参照のこと）です。 initramfs バッファ形式カーネルのcpio展開コードは、非常に小さく、さらに__initテキストとデータであり、ブートプロセス中に削除可能なものです。

  • 古いinitrdで実行されたプログラム（/initrdという名前で、/initではなかった）は設定を行った後、カーネルに戻りましたが、initramfsのinitプログラムはカーネルに戻る予定がありません。（/initが制御を譲る必要がある場合は、新しいルートデバイスで/を再マウントし、別のinitプログラムをexecすることができ、switch_rootユーティリティを参照してください。）

  • 別のルートデバイスに切り替える際、initrdはpivot_rootを使用してルートを切り替え、その後ramdiskをumountしました。しかしinitramfsはrootfsであり、pivot_root rootfsは行えず、rootfsをunmountすることもできません。代わりにrootfsからすべてのファイルを削除してスペースを確保（find -xdev / -exec rm ‘{}’ ‘;’）、新しいルートでrootfsを再マウント（cd /newmount; mount –move . /; chroot .）、新しい/dev/consoleにstdin/stdout/stderrを接続し、新しいinitをexecします。

    このプロセスは非常に複雑で（実行する前にコマンドを削除する必要があるため）、klibcパッケージはこの作業を自動化するヘルパープログラム（utils/run_init.c）を導入しました。他の多数のパッケージ（busyboxなど）はこのコマンドを「switch_root」と名付けています。

initramfsの作成:¶

2.6カーネルのビルドプロセスでは常にgzip圧縮されたcpio形式のinitramfsアーカイブを作成し、結果のカーネルバイナリにリンクします。デフォルトではこのアーカイブは空で（x86では134バイト消費します）。

CONFIG_INITRAMFS_SOURCEという設定オプション（menuconfigのGeneral Setupにあり、usr/Kconfigに存在）は、initramfsアーカイブのソースを指定することができ、自動的に結果のバイナリに組み込まれます。このオプションは既存のgzip圧縮cpioアーカイブ、またはアーカイブするファイルを含むディレクトリ、または以下の例のようなテキストファイルの指定に指すことができます:

dir /dev 755 0 0
nod /dev/console 644 0 0 c 5 1
nod /dev/loop0 644 0 0 b 7 0
dir /bin 755 1000 1000
slink /bin/sh busybox 777 0 0
file /bin/busybox initramfs/busybox 755 0 0
dir /proc 755 0 0
dir /sys 755 0 0
dir /mnt 755 0 0
file /init initramfs/init.sh 755 0 0

カーネルのビルド後、"usr/gen_init_cpio"を実行して、上記のファイル形式についての使用法メッセージを確認してください。

設定ファイルの利点は、新しいアーカイブにパーミッションを設定したりデバイスノードを作成したりする際にrootアクセスが不要であることです。（注意：これらの例の「ファイル」エントリは、linux-2.6.*ディレクトリ内のinitramfsという名前のディレクトリにinit.shおよびbusyboxという名前のファイルを期待しています。詳しくは 早期ユーザースペースサポート をご覧ください。)

カーネルは外部のcpioツールに依存していません。構成ファイルの代わりにディレクトリを指定した場合、カーネルのビルドインフラストラクチャがそのディレクトリから構成ファイルを作成します（usr/Makefileはusr/gen_initramfs.shを呼び出します）。その後、このディレクトリを構成ファイルとしてパッケージ化します（usr/gen_init_cpioに渡すことで、usr/gen_init_cpio.cから生成されたものです）。カーネルのビルド時のcpio生成コードは完全に自前で動作し、起動時の抽出器も（明らかに）自前で動作します。

外部のcpioユーティリティをインストールしておく必要があるのは、カーネルビルドに事前に準備されたcpioファイルを渡す場合（構成ファイルやディレクトリの代わりに）です。

以下のコマンドラインは、cpioイメージを（上記のスクリプトまたはカーネルビルドによって）その構成ファイルに戻して抽出できます：

cpio -i -d -H newc -F initramfs_data.cpio --no-absolute-filenames

以下のシェルスクリプトは、上記の構成ファイルの代わりに使用できる事前にビルドされたcpioアーカイブを作成できます：

#!/bin/sh

# Copyright 2006 Rob Landley <rob@landley.net> and TimeSys Corporation.
# Licensed under GPL version 2

if [ $# -ne 2 ]
then
  echo "usage: mkinitramfs directory imagename.cpio.gz"
  exit 1
fi

if [ -d "$1" ]
then
  echo "creating $2 from $1"
  (cd "$1"; find . | cpio -o -H newc | gzip) > "$2"
else
  echo "First argument must be a directory"
  exit 1
fi

注意

cpioのmanページには、initramfsアーカイブを破損させる可能性のある悪いアドバイスが含まれています。それは「ファイルリストを生成する典型的な方法はfindコマンドで、ディレクトリが読み取り不可または検索不可の場合の権限問題を最小限に抑えるためにfindに-depthオプションを指定する」と述べています。initramfs.cpio.gzイメージを生成する際にはこれを実行しないでください。Linuxカーネルのcpio抽出器は、既存のディレクトリがない場合にファイルを作成しません。そのため、ディレクトリエントリはそのディレクトリに含まれるファイルよりも前に配置する必要があります。上記のスクリプトは正しい順序でこれらを取得します。

外部initramfsイメージ：¶

カーネルにinitrdサポートが有効になっている場合、2.6カーネルに外部cpio.gzアーカイブをinitrdの代わりに渡すこともできます。この場合、カーネルは自動的にタイプ（initramfsではなくinitrd）を検出し、/initを実行する前にrootfsに外部cpioアーカイブを抽出します。

これはinitramfsのメモリ効率の利点（RAMディスクブロックデバイスなし）を持ちつつ、initrdの別個のパッケージ化（initramfsから非GPLコードを実行したい場合に便利で、GPLライセンスのLinuxカーネルバイナリと混同せずに使用できる）の利点もあります。

また、カーネルの組み込みinitramfsイメージを補完するためにも使用できます。外部アーカイブ内のファイルは組み込みinitramfsアーカイブ内の競合するファイルを上書きします。一部のディストリビューションでは、再コンパイルせずにタスクに応じたinitramfsイメージで単一のカーネルイメージをカスタマイズすることを好む場合があります。

initramfsの内容：¶

initramfsアーカイブは、Linux用の完全な自己完結型ルートファイルシステムです。shared libraries（共有ライブラリ）、devices（デバイス）、paths（パス）についての知識が不足している場合は、以下に参考資料を示します：

  • https://www.tldp.org/HOWTO/Bootdisk-HOWTO/

  • https://www.tldp.org/HOWTO/From-PowerUp-To-Bash-Prompt-HOWTO.html

  • http://www.linuxfromscratch.org/lfs/view/stable/

「klibc」パッケージ（https://www.kernel.org/pub/linux/libs/klibc)は、初期ユーザースペースコードを静的リンクするための小さなCライブラリであり、関連するユーティリティも含まれています。これはBSDライセンスです。

私はuClibc（https://www.uclibc.org)とbusybox（https://www.busybox.net)を使用しています。これらはそれぞれLGPLとGPLです。（busybox 1.3リリースで自己完結型のinitramfsパッケージが計画されています。）

理論上はglibcを使用することも可能ですが、これはこのような小さな埋め込み用途にはあまり向いていません。（glibcに静的リンクした「hello world」プログラムは400KB以上ですが、uClibcを使用すると7KBになります。また、glibcは静的リンクされている場合でも、名前解決のためにlibnssをdlopenするため、注意が必要です。）

最初のステップとして、initramfsが静的リンクされた「hello world」プログラムをinitとして実行し、qemu（www.qemu.org）やUser Mode Linuxなどのエミュレータでテストする方法があります。

cat > hello.c << EOF
#include <stdio.h>
#include <unistd.h>

int main(int argc, char *argv[])
{
  printf("Hello world!\n");
  sleep(999999999);
}
EOF
gcc -static hello.c -o init
echo init | cpio -o -H newc | gzip > test.cpio.gz
# Testing external initramfs using the initrd loading mechanism.
qemu -kernel /boot/vmlinuz -initrd test.cpio.gz /dev/zero

通常のルートファイルシステムをデバッグする際、「init=/bin/sh」で起動できると便利です。initramfsの同等物は「rdinit=/bin/sh」で、同様に役立ちます。

cpioをtarよりも選ぶ理由は？¶

この決定は2001年12月にされました。議論はここから始まりました：

http://www.uwsg.iu.edu/hypermail/linux/kernel/0112.2/1538.html

そして、第二のスレッド（特にtarとcpioの比較について）がここから始まりました：

http://www.uwsg.iu.edu/hypermail/linux/kernel/0112.2/1587.html

簡潔なまとめ（上記のスレッドを読む代わりにはなりません）は：

  1. cpioは標準です。これは数十年の歴史があり（AT&T時代から）、すでにLinuxで広く使用されています（RPM内、Red Hatのデバイスドライバディスクなど）。1996年のLinux Journal記事はこちら：

    http://www.linuxjournal.com/article/1213

    cpioはtarほど人気ではありません。これは伝統的なcpioコマンドラインツールが非常に不快なコマンドライン引数を必要とするためです。ただし、アーカイブ形式についてはどちらも同じく評価されていません。代替ツールとしては、以下のようなものがあります：

    http://freecode.com/projects/afio

  2. カーネルが選んだcpioアーカイブ形式は、（実際には数十ある）さまざまなtarアーカイブ形式よりもシンプルで洗練されており（したがって作成や解析が容易です）。完全なinitramfsアーカイブ形式はbuffer-format.txtで説明されており、usr/gen_init_cpio.cで作成され、init/initramfs.cで抽出されます。これらすべて合わせて、人間が読めるテキストとして26KB未満です。

  3. GNUプロジェクトがtarを標準化していることは、Windowsがzipを標準化していることとほぼ同様の関連性があります。Linuxはどちらにも属さず、独自の技術的決定を行うことができます。

  4. これはカーネル内部の形式であるため、まったく新しいものである可能性もありました。しかし、カーネルはこの形式の作成と抽出に独自のツールを提供しています。既存の標準を使用するのは望ましいですが、必須ではありません。

  5. アル・バイロは次の決定を下しました（引用：『tarは地獄のように醜く、カーネル側でサポートされない』）：

    http://www.uwsg.iu.edu/hypermail/linux/kernel/0112.2/1540.html

    その理由を説明しました：

    • http://www.uwsg.iu.edu/hypermail/linux/kernel/0112.2/1550.html

    • http://www.uwsg.iu.edu/hypermail/linux/kernel/0112.2/1638.html

    最も重要なのは、initramfsコードの設計と実装を行ったことです。

今後の方向性：¶

現在（2.6.16）ではinitram,fsは常にコンパイルされますが、常に使用されるわけではありません。カーネルはinitramfsに/initプログラムが含まれていない場合にのみ、レガシーブートコードにフォールバックします。このフォールバックはレガシーコードであり、平滑な移行を確保し、早期ブート機能を段階的に「早期ユーザースペース」（つまりinitramfs）に移行できるようにするためのものです。

早期ユーザースペースへの移行は必要不可欠です。なぜなら、実際のルートデバイスの検出とマウントは複雑であり、ルートパーティションは複数のデバイス（raidや別途のジャーナル）をまたぐことがあります。ネットワーク上にある場合もあり（dhcpの使用、特定のMACアドレスの設定、サーバーへのログインなどが必要）、外付けメディアに保存されている場合もあります（動的に割り当てられたメジャーマイナーナンバーと永続的なネーミング問題があり、完全なudev実装が必要です）。また、圧縮、暗号化、コピーオンライト、ループバックマウント、不思議なパーティション構成など、さまざまな複雑さがあります。

このような複雑さ（必然的にポリシーも含まれます）はユーザースペースで適切に処理されるべきです。klibcとbusybox/uClibcは、カーネルビルドに組み込むためのシンプルなinitramfsパッケージの開発を進めています。

klibcパッケージは現在、アンドリュー・モートンの2.6.17-mmツリーに受理されました。カーネルの現在の早期ブートコード（パーティション検出など）は、おそらくデフォルトのinitramfsに移行され、カーネルビルド時に自動的に作成・使用されるようになります。

Linuxカーネルにおけるファイル管理¶

このドキュメントでは、ファイル（struct file）とファイル記述子テーブル（struct files）のロック処理について説明します。

2.6.12以前では、ファイル記述子テーブルはロック（files->file_lock）と参照カウント（files->count）で保護されていました。->file_lockはテーブル内のすべてのファイル関連フィールドへのアクセスを保護し、->countはCLONE_FILESフラグでクローンされたタスク間でのファイル記述子テーブルの共有に使用されました。通常はPOSIXスレッドのケースです。カーネル内の一般的な参照カウントモデルと同様に、最後にput_files_struct()を実行したタスクがファイル記述子（fd）テーブルを解放します。ファイル（struct file）自体は参照カウント（->f_count）で保護されています。

新しいロックフリー型のファイル記述子管理モデルでは、参照カウントの仕組みは同様ですが、ロックはRCU（Read-Copy-Update）に基づいています。ファイル記述子テーブルには複数の要素が含まれます（open_fdsとclose_on_exec、ファイルポインタの配列、セットのサイズ、配列など）。ロックフリーの読み取り者にとって更新がアトミックに見えるようにするため、ファイル記述子テーブルのすべての要素は別個の構造体（struct fdtable）に配置されています。files_structはstruct fdtableへのポインタを含み、実際のfdテーブルにアクセスします。初期状態ではfdtableはfiles_struct自身に埋め込まれています。fdtableの拡張時に新しいfdtable構造体が割り当てられ、files->fdtabは新しい構造体を指します。fdtable構造体はRCUで解放され、ロックフリーの読み取り者は古いfdtableまたは新しいfdtableをいずれも見ることで更新がアトミックに見えるようにします。fdtable構造体のロックルールは以下の通りです。

  1. fdtableへの参照は常にfiles_fdtable()マクロを通じて行う必要があります。

    struct fdtable *fdt;

rcu_read_lock();

fdt = files_fdtable(files);
....
if (n <= fdt->max_fds)
        ....
...
rcu_read_unlock();

    files_fdtable()マクロは rcu_dereference() マクロで、ロックフリーの参照におけるメモリバリア要件を処理します。fdtableポインタは読み取り側のクリティカルセクション内で読み取る必要があります。

  2. 上記のfdtableの読み取りは、 rcu_read_lock()/rcu_read_unlock().

  3. で保護される必要があります。fdテーブルの更新を行う際には、files->file_lockを保持する必要があります。

  4. fdからファイル構造体を検索する際には、読み取り者はfcheck()またはfcheck_files()APIを使用する必要があります。これらはロックフリーの検索におけるバリア要件を処理します。

    例:

    struct file *file;

rcu_read_lock();
file = fcheck(fd);
if (file) {
        ...
}
....
rcu_read_unlock();

  5. ファイル構造体の処理は特殊です。ファイル記述子（fget()/fget_light()）の検索がロックフリーであるため、ファイル構造体の最後のput()操作と競合する可能性があります。これは->f_countのアトミックなインクリメント（atomic_long_inc_not_zero()）で回避されます。

    rcu_read_lock();
file = fcheck_files(files, fd);
if (file) {
        if (atomic_long_inc_not_zero(&file->f_count))
                *fput_needed = 1;
        else
        /* Didn't get the reference, someone's freed */
                file = NULL;
}
rcu_read_unlock();
....
return file;

    atomic_long_inc_not_zero() は refcounts がすでにゼロか、インクリメント中にゼロになるかどうかを検出します。その場合、fget()/fget_light() が失敗します。

  6. fdtable と file 構造体はロックフリーで検索可能なので、API を使ってインストールする必要があります。 rcu_assign_pointer() ロックフリーで検索される場合、 rcu_dereference() 使用する必要があります。しかし、files_fdtable() と fcheck()/fcheck_files() を使用することをお勧めします。これらはこれらの問題を処理します。

  7. 更新中に、files->file_lock を保持しながら fdtable ポインタを検索する必要があります。->fileのロックを解放すると、他のスレッドが files を拡張し、新しい fdtable を作成して、以前の fdtable ポインタを古くしてしまう可能性があります。

    例:

    spin_lock(&files->file_lock);
fd = locate_fd(files, file, start);
if (fd >= 0) {
        /* locate_fd() may have expanded fdtable, load the ptr */
        fdt = files_fdtable(files);
        __set_open_fd(fd, fdt);
        __clear_close_on_exec(fd, fdt);
        spin_unlock(&files->file_lock);
.....

    locate_fd() は ->file_lock を解放する可能性があります（再取得することもあります）。したがって、fdtable ポインタ（fdt）は locate_fd() の後で読み込む必要があります。

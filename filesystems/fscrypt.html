ファイルシステムレベルでの暗号化 (fscrypt)¶

はじめに¶

fscrypt は、ファイルシステムが透明なファイルおよびディレクトリの暗号化をサポートするために接続可能なライブラリです。

注意: このドキュメントにおける「fscrypt」は、カーネルレベルの部分を指し、実装されています fs/crypto/, 対してユーザースペースツール fscrypt. このドキュメントはカーネルレベルの部分のみをカバーしています。コマンドラインでの暗号化の使用例については、ユーザースペースツールのドキュメンテーションを参照してください fscrypt. また、カーネルの API を直接使用する代わりに、fscrypt ユーザースペースツールや、fscryptctl、Android のキーマネジメントシステムなどの既存のツールを使用することを推奨します。 fscryptctl または Android のキーマネジメントシステム, カーネルの API を直接使用するよりも推奨されます。既存のツールを使用することで、自らのセキュリティバグを導入する可能性を減らすことができます。(ただし、完全性を保つため、このドキュメンテーションではカーネルの API についてもカバーしています。)

dm-crypt とは異なり、fscrypt はブロックデバイスレベルではなくファイルシステムレベルで動作します。これにより、異なるファイルに異なる鍵で暗号化し、同じファイルシステム内に未暗号化のファイルを保持できるようになります。これは、各ユーザーの静的データが他者から暗号的に隔離される必要がある複数ユーザーのシステムにおいて有用です。ただし、ファイル名を除き、fscrypt はファイルシステムのメタデータを暗号化しません。

eCryptfs とは異なり、eCryptfs はスタックファイルシステムですが、fscrypt は現在 ext4、F2FS、UBIFS などのサポートされているファイルシステムに直接統合されています。これにより、暗号化されたファイルをページキャッシュに復号化されたページと暗号化されたページの両方をキャッシュする必要がなく、メモリ使用量をほぼ半分に抑え、未暗号化ファイルと同様の性能を実現します。同様に、dentries と inodes の必要数も半分になります。eCryptfs は暗号化されたファイル名を 143 バイトに制限し、アプリケーション互換性の問題を引き起こしますが、fscrypt は最大 255 バイト (NAME_MAX) を許可します。最後に、eCryptfs とは異なり、fscrypt API はマウントする必要なく権限のないユーザーでも使用可能です。

fscrypt はファイルを場所を変えて暗号化することをサポートしていません。代わりに、空のディレクトリを暗号化済みとしてマークすることをサポートしています。その後、ユーザースペースがキーを提供した後、そのディレクトリツリー内に作成されるすべての通常ファイル、ディレクトリ、およびシンボリックリンクが透明に暗号化されます。

脅威モデル¶

オフライン攻撃¶

ユーザー空間が強力な暗号化キーを選択した場合、fscryptはブロックデバイスの内容が特定の時点における永続的なオフライン侵害を受けた際、ファイルの内容およびファイル名の機密性を保護します。ただし、fscryptはファイルサイズ、ファイルパーミッション、ファイルタイムスタンプ、拡張属性などのファイル名以外のメタデータの機密性を保護しません。また、ファイル内の空き領域（論理的にゼロを含む未割当ブロック）の存在や位置も保護されません。

攻撃者が認可されたユーザーがファイルシステムにアクセスする前にオフラインでファイルシステムを操作できる場合、fscryptは機密性や正当性を保護するものではありません。

オンライン攻撃¶

fscrypt（および一般的なストレージ暗号化）は、オンライン攻撃に対して制限された保護を提供する可能性があります。詳細は以下の通りです。

サイドチャネル攻撃¶

fscryptは、Linux Cryptographic APIアルゴリズムの安全性に依存してサイドチャネル攻撃（例：タイミングや電磁的な攻撃）に対して抵抗性を持ちます。テーブルベースのAESなどの脆弱なアルゴリズムが使用されている場合、攻撃者がオンラインシステムに対してサイドチャネル攻撃を実行する可能性があります。サイドチャネル攻撃は、復号データを消費するアプリケーションにも適用されることがあります。

未承認のファイルアクセス¶

暗号化キーが追加された後、fscryptは同じシステム上の他のユーザーからプレーンテキストのファイル内容やファイル名を隠すことはできません。代わりに、ファイルモードビット、POSIX ACL、LSM、ネームスペースなどの既存のアクセス制御メカニズムを使用する必要があります。

(この理由について理解するには、暗号化キーが追加された時点で、システム自体の観点からデータの機密性は、 ではありません 暗号化の数学的性質によって保護されるのではなく、カーネルの正しさによってのみ保護されるため、 コード そのため、暗号化に特化したアクセス制御チェックは、カーネルによってのみ強制されるため、既存のアクセス制御メカニズムの幅広さと大きく重複する可能性があります。)

カーネルメモリの侵害¶

物理的な攻撃やカーネルのセキュリティ脆弱性を悪用して任意のメモリから読み取れるほどシステムを侵害した攻撃者は、現在使用中のすべての暗号化キーを侵害できます。

ただし、fscryptはカーネルから暗号化キーを削除できるため、それらが後続の侵害から保護される可能性があります。

詳しく説明すると、FS_IOC_REMOVE_ENCRYPTION_KEY ioctl（またはFS_IOC_REMOVE_ENCRYPTION_KEY_ALL_USERS ioctl）は、カーネルメモリからマスターエンクリプションキーを削除（「ワイプ」）することができ、その場合、このキーで「アンロック」されていたインODEのキャッシュをすべて強制的に削除しようとします。これにより、各ファイルのキーも削除され、再度「ロック」状態に戻り、暗号化された形式（暗号文）として表示されるようになります。

しかし、これらのioctlにはいくつかの制限があります：

  • 使用中のファイルのファイルごとのキーは ではありません 削除またはワイプされます。したがって、最大の効果を得るためには、ユーザー空間では関連する暗号化ファイルやディレクトリを閉じ、影響を受ける暗号化ディレクトリに作業ディレクトリを持つプロセスをすべて終了させる必要があります。

  • カーネルは、ユーザー空間が保持しているマスターキーのコピーを魔法のようにワイプすることはできません。そのため、ユーザー空間でもマスターキーのコピーをすべてワイプする必要があります。通常はFS_IOC_ADD_ENCRYPTION_KEYを実行した直後にこれを実行すべきで、FS_IOC_REMOVE_ENCRYPTION_KEYを待つことなく。もちろん、キーヒエラルキーの上位レベルにも同様の適用が求められます。また、キーを含むメモリをmlock()でロックして、スワップから保護するなどの他のセキュリティ対策も実施すべきです。

  • 一般的に、カーネルVFSキャッシュ内の復号化されたコンテンツやファイル名は解放されるが、ワイプされません。そのため、対応するキーがワイプされた後でも、解放されたメモリから一部のデータが復元される可能性があります。この問題を部分的に解決するには、カーネル構成にCONFIG_PAGE_POISONING=yを設定し、カーネルコマンドラインにpage_poison=1を追加することで、ページポイズニングを有効にできます。ただし、これはパフォーマンスにコストがかかるため注意が必要です。

  • CPUレジスタや暗号アクセラレータハードウェア（暗号APIがアルゴリズムを実装するために使用されている場合）、またはここでは考慮されていない他の場所に秘密鍵が依然として存在している可能性があります。

v1ポリシーの制限¶

v1暗号化ポリシーはオンライン攻撃に対していくつかの弱点があります：

  • 提供されたマスターキーが正しいかどうかの検証が行われていません。そのため、悪意のあるユーザーは、読み取り専用アクセスを持つ他のユーザーの暗号化ファイルに間違ったキーを一時的に関連付けることができます。ファイルシステムキャッシュのため、他のユーザーのアクセスがこれらのファイルに対して間違ったキーを使用することになり、他のユーザーが自身のキーリングに正しいキーを保持している場合でも、読み取り専用アクセスの意味を侵害します。

  • ファイルごとのキーが侵害されると、そのキーを生成したマスターキーも侵害されます。

  • 非rootユーザーは暗号化キーを安全に削除できません。

上記のすべての問題はv2暗号化ポリシーで解決されています。この理由のほかにも、すべての新しい暗号化ディレクトリに対してv2暗号化ポリシーを使用することを推奨します。

キーヒエラルキー¶

マスターキー¶

各暗号化ディレクトリツリーはマスターキーによって保護されています。 マスターキーマスターキーは最大で64バイトの長さにすることができます。コンテンツとファイル名の暗号モードのセキュリティ強度のうち大きい方以上である必要があります。たとえば、AES-256モードを使用する場合、マスターキーは少なくとも256ビット、つまり32バイトである必要があります。v1暗号化ポリシーで使用され、AES-256-XTSが使用される場合、より厳しい要件が適用されます。そのようなキーは64バイトにする必要があります。

暗号化されたディレクトリツリーを「アンロック」するには、ユーザー空間が適切なマスターキーを提供する必要があります。マスターキーは任意の数存在でき、それぞれが任意の数のファイルシステム上のディレクトリツリーを保護できます。

マスターキーは、実際の暗号化されたキーや、同じ長さのランダムなバイト列と区別がつかないものでなければなりません。これは、ユーザーが eisa_driver_registerから戻るときにEISAデバイスが検出されることを期待しないでください。なぜなら、バスがまだプローブされていない可能性が高いからです。実際には、ほとんどの場合（バスルートドライバーがブートプロセスの後半になってから動作するため）このことが起こります。残念ながら、ほとんどのドライバーは自らプローブを行い、プローブルーティンを終了するときに全体のマシンを探索していると期待しています。 パスワードを直接マスターキーとして使用する、短いキーやをゼロパディングする、または短いキーやを繰り返すなどの方法を取る場合、セキュリティが保証されないことを意味します。ユーザー空間がこのようなエラーを犯す場合、暗号化証明や分析はもはや適用されなくなります。

代わりに、ユーザーは暗号化されたランダム数生成器を使用するか、キーデリバーション関数（KDF）を使用してマスターキーを生成する必要があります。カーネルはキーストretchingを行いませんため、ユーザー空間がパスフレーズなどの低エントロピーの秘密情報をもとにキーやを導出する場合、scrypt、PBKDF2、Argon2などの目的に適したKDFを必ず使用する必要があります。

キーデリバーション関数¶

1つの例外を除き、fscryptはマスターキーやを直接暗号化に使用しません。代わりに、これらはキーデリバーション関数（KDF）への入力として使用され、実際のキーやを導出します。

特定のマスターキーに使用されるKDFは、キーやがv1暗号化ポリシーかv2暗号化ポリシーかによって異なります。ユーザーが eisa_driver_registerから戻るときにEISAデバイスが検出されることを期待しないでください。なぜなら、バスがまだプローブされていない可能性が高いからです。実際には、ほとんどの場合（バスルートドライバーがブートプロセスの後半になってから動作するため）このことが起こります。残念ながら、ほとんどのドライバーは自らプローブを行い、プローブルーティンを終了するときに全体のマシンを探索していると期待しています。 v1とv2の両方の暗号化ポリシーで同じキーやを使用する場合、（現実世界での攻撃は確認されていませんが）セキュリティが保証されない可能性があります。なぜなら、暗号化証明や分析はもはや適用されないからです。

v1の暗号化ポリシーでは、KDFはファイルごとの暗号化キーを導出するのみをサポートしています。この仕組みは、マスターキーをAES-128-ECBで暗号化し、ファイルの16バイトのノンスをAESの鍵として使用することで動作します。生成された暗号文は導出キーとして使用され、暗号文が必要な長さより長くなる場合は、必要な長さにトリミングされます。

v2の暗号化ポリシーでは、KDFはHKDF-SHA512を使用します。マスターキーは「input keying material」として渡され、ソルトは使用されません。各導出キーに対して、異なる「アプリケーション固有の情報文字列」が使用されます。たとえば、ファイルごとの暗号化キーを導出する場合、アプリケーション固有の情報文字列は「fscrypt\0」という文字列をファイルのノンスの前に接続し、コンテキストバイトを追加したものです。他の種類の導出キーには異なるコンテキストバイトが使用されます。

HKDF-SHA512は元のAES-128-ECBベースのKDFよりも優れています。HKDFは柔軟性があり、逆再生不可能であり、マスターキーからのエントロピーを均等に分散します。また、HKDFは標準化されており、他のソフトウェアでも広く使用されています。一方、AES-128-ECBベースのKDFは一時的な実装です。

ファイルごとの暗号化キー¶

各マスターキーが多数のファイルを保護できるため、各ファイルの暗号化を「調整（tweak）」する必要があります。これにより、2つのファイルで同じ平文が同じ暗号文にマッピングしない、または逆に同じ暗号文が異なる平文にマッピングしないようにします。ほとんどの場合、fscryptはファイルごとのキーを導出することでこの調整を行います。新しい暗号化されたインノデ（通常ファイル、ディレクトリ、シンボリックリンク）が作成されるとき、fscryptはランダムに16バイトのノンスを生成し、インノデの暗号化xattrに保存します。その後、KDF（上記の説明に従って）を使用して処理を行います。 キーデリバーション関数) マスターキーとノンスからファイルの鍵を導出するために使用されます。

キーデリバティブがキーワラピングよりも選ばれた理由は、ワラップされたキーデータはより大きなxattrsを必要とし、ファイルシステムのinodeテーブル内にインラインで収まりにくかったためです。また、キーワラピングには顕著な利点が見られませんでした。特に、現在は複数の代替マスターキーでファイルをアンロックする必要も、マスターキーのローテーションをサポートする必要もありません。代わりに、マスターキーはユーザー空間でワラップされることが可能です。例えば、DIRECT_KEYポリシーで行われるように。 fscrypt ツールによって解決されます。

DIRECT_KEYポリシー¶

Adiantum暗号化モード（参照： 暗号化モードと使用方法) はコンテンツおよびファイル名の暗号化に適しており、長めのIVを受容します。長さは8バイトの論理ブロック番号と16バイトのファイルごとのノンスを同時に保持できるほど十分です。また、AdiantのキーのオーバーヘッドはAES-256-XTSキーに比べて大きいです。

したがって、パフォーマンスの向上とメモリの節約のために、Adiantumでは「direct key（直接キー）」の設定がサポートされています。ユーザーがfscryptポリシーでFSCRYPT_POLICY_FLAG_DIRECT_KEYを有効に設定した場合、ファイルごとの暗号化キーは使用されません。代わりに、データ（コンテンツまたはファイル名）が暗号化されるたびに、そのファイルの16バイトのnonceがIVに含まれます。さらに：

  • v1暗号化ポリシーでは、暗号化はマスターキーを直接使用して行われます。このため、ユーザーは eisa_driver_registerから戻るときにEISAデバイスが検出されることを期待しないでください。なぜなら、バスがまだプローブされていない可能性が高いからです。実際には、ほとんどの場合（バスルートドライバーがブートプロセスの後半になってから動作するため）このことが起こります。残念ながら、ほとんどのドライバーは自らプローブを行い、プローブルーティンを終了するときに全体のマシンを探索していると期待しています。 他の用途でも、他のv1ポリシーでもマスターキーを同じく使用します。

  • v2暗号化ポリシーでは、KDFを使用してモードごとのキーが導出されて暗号化が行われます。ユーザーは、他のv2暗号化ポリシーでも同じマスターキーを使用できます。

IV_INO_LBLK_64ポリシー¶

fscryptポリシーでFSCRYPT_POLICY_FLAG_IV_INO_LBLK_64が設定されている場合、暗号化キーはマスターキー、暗号化モード番号、ファイルシステムUUIDから導出されます。通常、この設定により、同じマスターキーで保護されるすべてのファイルはコンテンツ暗号化キーとファイル名暗号化キーを共通で使用します。ただし、異なるファイルのデータを異なる方法で暗号化する必要があるため、inode番号がIVに含まれます。その結果、ファイルシステムの縮小が許可されない場合があります。

この形式は、UFS準拠のインライン暗号化ハードウェアに最適化されており、1回のI/Oリクエストあたりに64ビットのIVのみをサポートし、キースロットの数が極めて少ないハードウェアに使用されます。

IV_INO_LBLK_32ポリシー¶

IV_INO_LBLK_34ポリシーはIV_INO_LBLK_64と同様ですが、IV_INO_LBLK_32ではinode番号をSipHash-2-4（SipHashキーはマスターキーから導出）でハッシュ化し、ファイル論理ブロック番号を2^32で割った余りを加算して32ビットのIVを生成します。

この形式は、eMMC v5.2準拠のインライン暗号化ハードウェアに最適化されており、1回のI/Oリクエストあたりに32ビットのIVのみをサポートし、キースロットの数が極めて少ないハードウェアに使用されます。この形式はハードウェアの制限によりIVの再利用が発生するため、必要に応じてのみ使用すべきです。

キーアイデンティファイア¶

v2暗号化ポリシーで使用されるマスターキーには、KDFを使用してユニークな16バイトの「キーアイデンティファイア」も導出されます。この値は明文で保存されるため、キーアイデンティファイア自体を信頼性を持って識別するために必要です。

ディーライハッシュキー¶

平文のファイル名に基づいて秘密鍵でハッシュ化されたディレクトリについては、KDF（Key Derivation Function）が使用され、各ディレクトリに対して128ビットのSipHash-2-4鍵を導出してファイル名をハッシュ化します。これはファイルごとの暗号化鍵を導出するのと同様の仕組みですが、異なるKDFコンテキストが使用されます。現在は、ケースフォールド（ケースインセンシティブ）で暗号化されたディレクトリのみがこのハッシュ方式を使用しています。

暗号化モードと使用方法¶

fscryptは、ファイルコンテンツとファイル名それぞれに対して暗号化モードを指定できます。異なるディレクトリツリーは異なる暗号化モードを使用することが許可されています。現在、次の暗号化モードのペアがサポートされています：

  • コンテンツにはAES-256-XTS、ファイル名にはAES-256-CTS-CBC

  • コンテンツにはAES-128-CBC、ファイル名にはAES-128-CTS-CBC

  • コンテンツとファイル名の両方にAdiantum

不明な場合は、(AES-256-XTS, AES-256-CTS-CBC)のペアを使用してください。

AES-128-CBCは、XTSをサポートしない暗号アクセラレータ（CAAMやCESAなど）を持つ低消費電力の埋め込みデバイスのために追加されました。AES-128-CBCを使用するには、CONFIG_CRYPTO_ESSIVとCONFIG_CRYPTO_SHA256（または他のSHA-256実装）が有効化されている必要があります。

Adiantumは主にストリーム暗号ベースのモードで、専用の暗号指令を備わわないCPUでも高速に動作します。また、XTSとは異なり、真のワイドブロックモードです。これにより、ファイルごとの暗号化鍵の導出が必要なくなる場合もあります。ただし、2つの原始的暗号（XChaCha12とAES-256）のセキュリティに依存するため、1つの原始的暗号に比べて安全性が低下する可能性があります。詳しくは論文『Adiantum: length-preserving encryption for entry-level processors』（https://eprint.iacr.org/2018/720.pdf)を参照してください。Adiantumを使用するには、CONFIG_CRYPTO_ADIANTUMが有効化されている必要があります。また、ChaChaとNHPoly1305の高速実装も有効化する必要があります（例：ARM向けにはCONFIG_CRYPTO_CHACHA20_NEONとCONFIG_CRYPTO_NHPOLY1305_NEON）。

新しい暗号化モードはファイルシステムごとの変更なしに相対的に簡単に追加できます。ただし、認証付き暗号（AE）モードは、暗号文拡張の処理が難しいため、現在はサポートされていません。

コンテンツの暗号化¶

ファイルコンテンツについては、各ファイルシステムブロックが独立して暗号化されます。Linuxカーネル5.5以降では、ブロックサイズがシステムのページサイズより小さいファイルシステムの暗号化がサポートされています。

各ブロックのIV（初期化ベクトル）は、ファイル内の論理ブロック番号をリトルエンディアンとして設定します。ただし、

  • CBCモード暗号化ではESSIVも使用されます。具体的には、各IVがAES-256で暗号化され、AES-256の鍵はファイルのデータ暗号化鍵のSHA-256ハッシュから生成されます。

  • With DIRECT_KEYポリシー、ファイルのnonceはIVに接続されます。現在はAdiantum暗号モードでのみ許可されています。

  • With IV_INO_LBLK_64ポリシー、論理ブロック番号は32ビットに制限され、IVのビット0〜31に配置されます。inode番号（これも32ビットに制限されます）はビット32〜63に配置されます。

  • With IV_INO_LBLK_32ポリシー、論理ブロック番号は32ビットに制限され、IVのビット0〜31に配置されます。inode番号はその後ハッシュ化され、2^32で割った余りとして追加されます。

ファイルの論理ブロック番号がIVに含まれるため、ファイルシステムは暗号化されたファイル内でブロックが移動されることを防ぐ必要があります。たとえば、「collapse range」や「insert range」などの操作を介して。

ファイル名の暗号化¶

ファイル名については、各フルファイル名を一度に暗号化します。ディレクトリ検索の効率を維持し、ファイル名の最大長が255バイトであるという要件のため、ディレクトリ内のすべてのファイル名には同じIVが使用されます。

ただし、各暗号化ディレクトリは一意のキーを使用するか、またはファイルのnonce（ DIRECT_KEYポリシー）やinode番号（ IV_INO_LBLK_64ポリシー）をIVに含めることが可能です。したがって、IVの再利用は単一のディレクトリ内で制限されます。

CTS-CBCでは、IVの再利用により、平文ファイル名が暗号ブロックサイズ（AESでは16バイト）以上に共通のプレフィックスを持つ場合、対応する暗号化ファイル名も同じプレフィックスを持つことになります。これは望ましくありません。Adiantumはワイドブロック暗号モードであるため、このような脆弱性はありません。

すべてのサポートされているファイル名暗号化モードは、平文長が16バイト以上であれば任意の長さを受け入れます。暗号ブロックのアライメントは必要ありません。ただし、16バイト未満のファイル名は暗号化前にNULLパディングで16バイトに拡充されます。さらに、ファイル名長の情報漏洩を防ぐため、すべてのファイル名は次の4、8、16、または32バイト境界（設定可能）にNULLパディングされます。32バイトは推奨されます。これは機密性を最大限に高める代償として、ディレクトリエントリがやや多くの空間を消費するためです。注意点として、NULL（\0）はファイル名として有効な文字ではないため、パディングは重複した平文を生成することはありません。

シンボリックリンクのターゲットはファイル名の一種とみなされ、ディレクトリエントリ内のファイル名と同様に暗号化されます。ただし、各シンボリックリンクは独自のinodeを持ち、IVの再利用が問題にならないためです。

暗号化ポリシーの設定¶

FS_IOC_SET_ENCRYPTION_POLICY¶

FS_IOC_SET_ENCRYPTION_POLICY ioctlは、空のディレクトリに暗号化ポリシーを設定するか、既に指定された暗号化ポリシーを持つディレクトリまたは通常ファイルを検証します。このioctlは、struct fscrypt_policy_v1またはstruct fscrypt_policy_v2へのポインタを引数として受け取ります。

#define FSCRYPT_POLICY_V1               0
#define FSCRYPT_KEY_DESCRIPTOR_SIZE     8
struct fscrypt_policy_v1 {
        __u8 version;
        __u8 contents_encryption_mode;
        __u8 filenames_encryption_mode;
        __u8 flags;
        __u8 master_key_descriptor[FSCRYPT_KEY_DESCRIPTOR_SIZE];
};
#define fscrypt_policy  fscrypt_policy_v1

#define FSCRYPT_POLICY_V2               2
#define FSCRYPT_KEY_IDENTIFIER_SIZE     16
struct fscrypt_policy_v2 {
        __u8 version;
        __u8 contents_encryption_mode;
        __u8 filenames_encryption_mode;
        __u8 flags;
        __u8 __reserved[4];
        __u8 master_key_identifier[FSCRYPT_KEY_IDENTIFIER_SIZE];
};

この構造体は以下の通り初期化する必要があります：

  • version struct fscrypt_policy_v1が使用される場合はFSCRYPT_POLICY_V1 (0)、struct fscrypt_policy_v2が使用される場合はFSCRYPT_POLICY_V2 (2)を設定する必要があります。(注: 元のポリシーバージョンは「v1」と呼ばいますが、実際のバージョンコードは0です。) 新しい暗号化ディレクトリにはv2ポリシーを使用してください。

  • contents_encryption_mode および filenames_encryption_mode は、以下の定数から選ぶ必要があります： <linux/fscrypt.h> で指定する暗号化モードを識別します。不明な場合は、ファイル名の暗号化時に使用するNULLパディングの量を指定するFSCRYPT_POLICY_FLAGS_PAD_32 (0x3)を使用してください。 contents_encryption_mode で指定する暗号化モードを識別します。不明な場合は、FSCRYPT_MODE_AES_256_XTS (1)を使用してください。 filenames_encryption_mode.

  • flags は、以下のフラグから選ぶことができます： <linux/fscrypt.h>:

    • FSCRYPT_POLICY_FLAGS_PAD_*: ファイル名を暗号化する際のNULLパディングの量を指定します。不明な場合はFSCRYPT_POLICY_FLAGS_PAD_3,2 (0x3)を使用してください。

    • FSCRYPT_POLICY_FLAG_DIRECT_KEY: 詳細は DIRECT_KEYポリシー.

    • FSCRYPT_POLICY_FLAG_IV_INO_LBLK_64: 詳細は IV_INO_LBLK_64ポリシー.

    • FSCRYPT_POLICY_FLAG_IV_INO_LBLK_32: 詳細は IV_INO_LBLK_32ポリシー.

    v1暗号化ポリシーはPAD_*およびDIRECT_KEYフラグのみをサポートします。他のフラグはv2暗号化ポリシーでのみサポートされます。

    DIRECT_KEY、IV_INO_LBLK_64、IV_INO_LBLK_32フラグは互いに排他的です。

  • v2暗号化ポリシーの場合、 __reserved をゼロに設定する必要があります。

  • v1暗号化ポリシーの場合、 master_key_descriptor はキーリング内のマスターキーを検索する方法を指定します。詳細は Adding keysを参照してください。ユーザー空間は各マスターキーに対して一意の master_key_descriptor を選択する必要があります。e4cryptおよびfscryptツールは、 SHA-512(SHA-512(master_key))の最初の8バイトを使用しますが、この特定のスキームは必須ではありません。また、FS_IOC_SET_ENCRYPTION_POLICYの実行時にマスターキーがキーリングにすでに存在する必要はありません。ただし、暗号化ディレクトリにファイルを作成する前にマスターキーをキーリングに追加する必要があります。

    v2暗号化ポリシーの場合、 master_key_descriptor は master_key_identifierに置き換えられました。これはより長く、任意に選ぶことができません。代わりに、キーリングに追加する前に FS_IOC_ADD_ENCRYPTION_KEYを使用してキーリングに追加する必要があります。その後、 key_spec.u.identifier で、カーネルがstruct fscrypt_add_key_argで返した値を master_key_identifier としてstruct fscrypt_policy_v2に使用する必要があります。

ファイルがまだ暗号化されていない場合、FS_IOC_SET_ENCRYPTION_POLICYはそのファイルが空のディレクトリであることを確認します。そうであれば、指定された暗号化ポリシーをディレクトリに割り当て、暗号化ディレクトリに変換します。その後、 Adding keysで説明したように対応するマスターキーを提供した後、ディレクトリ内に作成されるすべての通常ファイル、ディレクトリ（再帰的に）、およびシンボリックリンクは暗号化され、同じ暗号化ポリシーを継承します。ディレクトリのエントリ内のファイル名も暗号化されます。

代替として、ファイルがすでに暗号化されている場合、FS_IOC_SET_ENCRYPTION_POLICYは指定された暗号化ポリシーが実際に適用されているものと完全に一致しているかを検証します。一致している場合、ioctlは0を返します。一致しない場合はEEXISTで失敗します。これは通常のファイルとディレクトリ、および空でないディレクトリにも適用されます。

v2暗号化ポリシーがディレクトリに割り当てられた場合、指定されたキーが現在のユーザーによってすでに追加されているか、または呼び出し元が初期ユーザー名前空間でCAP_FOWNERの能力を持っている必要があります。(これはユーザーが他のユーザーのキーでデータを暗号化するのを防ぐためのものです。) キーはFS_IOC_SET_ENCRYPTION_POLICYの実行中に常に追加されている必要があります。ただし、新しい暗号化ディレクトリがすぐにアクセスされる必要がない場合、キーはすぐに削除してもよいです。

注意点として、ext4ファイルシステムではルートディレクトリを暗号化することはできません。空であってもです。全体のファイルシステムを1つのキーで暗号化したいユーザーは、dm-cryptを使用することを検討してください。

FS_IOC_SET_ENCRYPTION_POLICYは以下のエラーで失敗する場合があります：

  • EACCESプロセスのUIDで所有されていないファイル、またはファイル所有者のUIDがマップされている名前空間でプロセスがCAP_FOWNERの能力を持っていない

  • EEXISTファイルが指定された暗号化ポリシーとは異なる暗号化ポリシーで既に暗号化されている

  • EINVAL無効な暗号化ポリシーが指定された(無効なバージョン、モード、フラグ、または予約ビットが設定されている)、またはv1暗号化ポリシーが指定されたがディレクトリにケースフォールドフラグが有効になっている場合(ケースフォールドはv1ポリシーと互換性がありません)

  • ENOKEYv2暗号化ポリシーが指定されたが、指定された master_key_identifier キーがまだ追加されていない、または初期ユーザー名前空間でプロセスがCAP_FOWNERの能力を持っていない

  • ENOTDIRファイルが未暗号化で、通常のファイルであり、ディレクトリではない

  • ENOTEMPTYファイルが未暗号化で、空でないディレクトリである

  • ENOTTYこの種のファイルシステムは暗号化を実装していない

  • EOPNOTSUPPカーネルがファイルシステムの暗号化をサポートしていない、またはファイルシステムのスーパーブロックに暗号化が有効になっていない。(たとえば、ext4ファイルシステムで暗号化を使用するには、カーネル構成にCONFIG_FS_ENCRYPTIONが有効になっていなければならず、スーパーブロックに「encrypt」機能フラグが有効になっている必要があります) tune2fs -O encrypt または mkfs.ext4 -O encrypt.)

  • EPERMこのディレクトリは暗号化できません。たとえば、ext4ファイルシステムのルートディレクトリである可能性があります

  • EROFSファイルシステムが読み取り専用です

暗号化ポリシーの取得¶

ファイルの暗号化ポリシーを取得するには次の2つのioctlが利用可能です：

  • FS_IOC_GET_ENCRYPTION_POLICY_EX

  • FS_IOC_GET_ENCRYPTION_POLICY

拡張版(_EX)のioctlコマンドはより一般的で、可能な限り使用することをお勧めします。ただし、古いカーネルでは元のioctlコマンドのみが利用可能です。アプリケーションではまず拡張版を試し、失敗した場合にENOTTYエラーが発生した場合は元のバージョンにフォールバックする必要があります。

FS_IOC_GET_ENCRYPTION_POLICY_EX¶

FS_IOC_GET_ENCRYPTION_POLICY_EXは、ディレクトリまたは通常ファイルの暗号化ポリシー（存在する場合）を取得します。ファイルを開く権限があれば、追加の権限は必要ありません。このコマンドはstruct fscrypt_get_policy_ex_argへのポインタを引数として受け取り、以下のように定義されています:

struct fscrypt_get_policy_ex_arg {
        __u64 policy_size; /* input/output */
        union {
                __u8 version;
                struct fscrypt_policy_v1 v1;
                struct fscrypt_policy_v2 v2;
        } policy; /* output */
};

呼び出し元は policy_size ポリシー構造体に割り当て可能なサイズに初期化する必要があります。つまり、 sizeof(arg.policy).

成功した場合、ポリシー構造体は policyに返され、その実際のサイズは policy_size. policy.version で確認する必要があります。注意点として、「v1」ポリシーのバージョンコードは実際には0（FSCRYPT_POLICY_V1）です。

FS_IOC_GET_ENCRYPTION_POLICY_EXは以下のエラーで失敗することがあります:

  • EINVAL: ファイルは暗号化されていますが、認識されていない暗号化ポリシーのバージョンを使用しています

  • ENODATA: ファイルは暗号化されていません

  • ENOTTY: このファイルシステムは暗号化を実装していません、またはこのカーネルがFS_IOC_GET_ENCRYPTION_POLICY_EXをサポートしていない（代わりにFS_IOC_GET_ENCRYPTION_POLICYを使用してください）

  • EOPNOTSUPP: このファイルシステムの暗号化サポートがカーネルに構成されていない、またはファイルシステムのスーパーブロックに暗号化が有効になっていない

  • EOVERFLOW: ファイルは暗号化されており、認識された暗号化ポリシーのバージョンを使用していますが、提供されたバッファにポリシー構造体が収まらない

注意: ファイルが暗号化されているかを確認するだけであれば、ほとんどのファイルシステムではFS_IOC_GETFLAGS ioctlを使用してFS_ENCRYPT_FLを確認するか、statx()システムコールを使用してstx_attributes内のSTATX_ATTR_ENCRYPTEDを確認することも可能です。

FS_IOC_GET_ENCRYPTION_POLICY¶

FS_IOC_GET_ENCRYPTION_POLICYコマンドも、ディレクトリまたは通常ファイルの暗号化ポリシー（存在する場合）を取得できます。ただし、 FS_IOC_GET_ENCRYPTION_POLICY_EXとは異なり、FS_IOC_GET_ENCRYPTION_POLICYはもともとのポリシーバージョンのみをサポートしています。このコマンドはstruct fscrypt_policy_v1への直接のポインタを引数として受け取り、struct fscrypt_get_policy_ex_argではなく使用します。

FS_IOC_GET_ENCRYPTION_POLICYのエラーコードはFS_IOC_GET_ENCRYPTION_POLICY_EXと同様ですが、FS_IOC_GET_ENCRYPTION_POLICYはファイルが新しい暗号化ポリシーのバージョンで暗号化されている場合にも EINVAL を返します。

ファイルシステムごとのsaltの取得¶

ext4やF2FSなどの一部のファイルシステムは、非推奨となったioctl FS_IOC_GET_ENCRYPTION_PWSALTをサポートしています。このioctlは、ファイルシステムのスーパーブロックに保存されているランダムに生成された16バイトの値を取得します。この値は、パスフレーズやその他の低エントロピーのユーザー資格情報をもとに暗号化キーを導出する際のソルトとして使用することを意図しています。

FS_IOC_GET_ENCRYPTION_PWSALTは非推奨です。代わりに、必要なソルトをユーザー空間で生成・管理することをお勧めします。

ファイルの暗号化ノンスを取得する¶

Linux v5.7以降、ioctl FS_IOC_GET_ENCRYPTION_NONCEがサポートされています。暗号化されたファイルやディレクトリでは、インノデの16バイトノンスを取得し、暗号化されていないファイルやディレクトリではENODATAで失敗します。

このioctlは、暗号化が正しく行われているかを確認する自動テストに役立ちます。fscryptの通常利用には必要ありません。

Adding keys¶

FS_IOC_ADD_ENCRYPTION_KEY¶

FS_IOC_ADD_ENCRYPTION_KEY ioctlは、ファイルシステムにマスターエンクリプションキーを追加し、そのキーで暗号化されたファイルシステム上のすべてのファイルが「アンロックス」状態（つまり平文形式）になるようにします。このioctlはターゲットファイルシステム上の任意のファイルやディレクトリで実行できますが、ファイルシステムのルートディレクトリを使用することをお勧めします。このioctlはstruct fscrypt_add_key_argへのポインタを引数として受け取り、以下のように定義されています：

struct fscrypt_add_key_arg {
        struct fscrypt_key_specifier key_spec;
        __u32 raw_size;
        __u32 key_id;
        __u32 __reserved[8];
        __u8 raw[];
};

#define FSCRYPT_KEY_SPEC_TYPE_DESCRIPTOR        1
#define FSCRYPT_KEY_SPEC_TYPE_IDENTIFIER        2

struct fscrypt_key_specifier {
        __u32 type;     /* one of FSCRYPT_KEY_SPEC_TYPE_* */
        __u32 __reserved;
        union {
                __u8 __reserved[32]; /* reserve some extra space */
                __u8 descriptor[FSCRYPT_KEY_DESCRIPTOR_SIZE];
                __u8 identifier[FSCRYPT_KEY_IDENTIFIER_SIZE];
        } u;
};

struct fscrypt_provisioning_key_payload {
        __u32 type;
        __u32 __reserved;
        __u8 raw[];
};

struct fscrypt_add_key_argはゼロ初期化され、次のように初期化します：

  • v1暗号化ポリシーで使用するキーを追加する場合、 key_spec.type FSCRYPT_KEY_SPEC_TYPE_DESCRIPTORを含む必要があります、そして key_spec.u.descriptor 追加されるキーのディスクリプターを含み、これは master_key_descriptor 構造体fscrypt_policy_v1の

    フィールドに記載されている値と一致する必要があります。この種のキーを追加するには、呼び出しプロセスが初期ユーザー名前空間でCAP_SYS_ADMINの能力を持つ必要があります。 key_spec.type 代わりに、v2暗号化ポリシーで使用するキーを追加する場合、 key_spec.u.identifier FSCRYPT_KEY_SPEC_TYPE_IDENTIFIERを含む必要があります、そして 出力 は、カーネルがキーの暗号ハッシュを埋め込むフィールドです。この種のキーを追加するには、呼び出しプロセスは特権を必要としません。ただし、追加可能なキー数はユーザーのkeyringsサービスのクォータに制限されます（参照： Documentation/security/keys/core.rst).

  • raw_size が、 raw フィールドに指定されたキーのサイズ（バイト単位）でなければなりません。あるいは、 key_id がゼロでない場合、このフィールドはゼロでなければなりません。その場合、サイズは指定されたLinux keyringキーによって自動的に推測されます。

  • key_id がゼロの場合は、 raw フィールドに直接raw keyが指定されています。それ以外の場合、 key_id は、タイプ「fscrypt-provisioning」のLinux keyringキーのIDであり、そのペイロードはstruct fscrypt_provisioning_key_payloadで、 raw フィールドにraw keyが含まれ、 type フィールドが key_spec.typeと一致する必要があります。_since raw 可変長であり、このキーのペイロードの合計サイズは sizeof(struct fscrypt_provisioning_key_payload) raw keyのサイズを加えたものでなければなりません。このキーに対して検索権限を有している必要があります。

    ほとんどのユーザーはこの値を0に残し、直接のraw keyを指定するべきです。Linux keyring keyを指定するサポートは、ファイルシステムがアンマウントされ再マウントされる際にraw keyをユーザースペースメモリに保存せずにキーを再追加できるようにするためのものです。

  • raw 実際のキーを含む可変長フィールドであり、 raw_size バイト長です。代替として、 key_id がゼロでない場合、このフィールドは使用されません。

キーレス¶

暗号化された通常ファイル、ディレクトリ、シンボリックリンクでは、暗号化キーが追加される前や削除された後でも、一部のファイルシステム操作が実行可能です:

  • ファイルメタデータは読み取れます（例: stat() を使用する場合）。

  • ディレクトリは一覧表示され、その場合、ファイル名は暗号文から導出された符号化形式で表示されます。現在の符号化アルゴリズムについては ファイル名ハッシュと符号化を参照してください。アルゴリズムは変更される可能性がありますが、提示されるファイル名は NAME_MAX バイト以内で、 / または \0 文字を含まず、ディレクトリエントリを一意に識別します。

    以下の . および .. ディレクトリエントリは特殊です。常に存在し、暗号化または符号化されません。

  • ファイルは削除される可能性があります。つまり、ディレクトリ以外のファイルは通常のunlink()で削除でき、空のディレクトリは通常のrmdir()で削除できます。したがって、 rm および rm -r 予期通りに動作します。

  • シンボリックリンクのターゲットは読み取れたり、フォローされたりするかもしれませんが、ディレクトリ内のファイル名と同様に暗号化された形式で表示されるため、有用な場所を指す可能性は低いです。

鍵がない場合、通常のファイルは開けたり、切り詰めたりすることはできません。このような操作を試みるとENOKEYで失敗します。これは、ファイルディスクリプタが必要な通常のファイル操作（read()、write()、mmap()、fallocate()、ioctl()など）も禁止されることを意味します。

鍵がない場合、どの種類のファイル（ディレクトリを含む）も暗号化されたディレクトリに作成したりリンクしたりすることはできません。また、暗号化されたディレクトリ内の名前はリネームのソースまたはターゲットにもなり得ず、O_TMPFILEの一時ファイルも暗号化されたディレクトリ内に作成できません。このような操作はすべてENOKEYで失敗します。

暗号化キーなしで暗号化ファイルのバックアップや復元は現在不可能です。これには特別なAPIが必要ですが、それらはまだ実装されていません。

暗号化ポリシーの強制¶

暗号化ポリシーがディレクトリに設定されると、そのディレクトリ内に作成されるすべての通常ファイル、ディレクトリ、シンボリックリンク（再帰的に）はその暗号化ポリシーを継承します。特殊ファイル（名前付きパイプ、デバイスノード、UNIXドメインソケット）は暗号化されません。

特殊ファイルを除き、暗号化されたディレクトリツリー内には未暗号化のファイルや、異なる暗号化ポリシーで暗号化されたファイルは存在できません。このようなファイルを暗号化されたディレクトリにリンクしたりリネームしたりするとEXDEVで失敗します。これは->lookup()の際にも強制されるため、アプリケーションが後で敏感なデータを書き込む可能性のある場所で暗号化を無効化または downgrade しようとするオフライン攻撃に対する制限的な保護を提供します。"検証されたブート"の形式を実装するシステムでは、アクセス前にすべてのトップレベルの暗号化ポリシーを検証することを推奨します。

実装詳細¶

暗号化コンテキスト¶

暗号化ポリシーはディスク上ではstruct fscrypt_context_v1またはstruct fscrypt_context_v2で表されます。個々のファイルシステムはポリシーをどこに保存するかを決定しますが、通常は隠しの拡張属性に保存されます。これについては ではありません getxattr()やsetxattr()などのxattr関連のシステムコールによって、暗号化xattrの特殊なセマンティクスのため、情報が漏洩する可能性があります。(特に、暗号化ポリシーを空でないディレクトリ以外の何かに追加または削除した場合、混乱が生じる可能性が非常に高いです。) これらの構造体は以下の通り定義されています:

#define FSCRYPT_FILE_NONCE_SIZE 16

#define FSCRYPT_KEY_DESCRIPTOR_SIZE  8
struct fscrypt_context_v1 {
        u8 version;
        u8 contents_encryption_mode;
        u8 filenames_encryption_mode;
        u8 flags;
        u8 master_key_descriptor[FSCRYPT_KEY_DESCRIPTOR_SIZE];
        u8 nonce[FSCRYPT_FILE_NONCE_SIZE];
};

#define FSCRYPT_KEY_IDENTIFIER_SIZE  16
struct fscrypt_context_v2 {
        u8 version;
        u8 contents_encryption_mode;
        u8 filenames_encryption_mode;
        u8 flags;
        u8 __reserved[4];
        u8 master_key_identifier[FSCRYPT_KEY_IDENTIFIER_SIZE];
        u8 nonce[FSCRYPT_FILE_NONCE_SIZE];
};

コンテキスト構造体は、対応するポリシー構造体(参照 暗号化ポリシーの設定)と同じ情報を含みますが、コンテキスト構造体にはnonceも含まれます。nonceはカーネルによってランダムに生成され、KDFの入力として使用されるか、またはファイルごとに暗号化を異にするようにするための調整値として使用されます。参照 ファイルごとの暗号化キー および DIRECT_KEYポリシー.

データパスの変更¶

通常のファイルの読み込みパス(->readpage())では、ファイルシステムがページキャッシュに暗号文を読み込み、その場で復号することができ、復号が完了するまでページロックを保持する必要があります。これにより、ユーザー空間が早すぎるタイミングでページを参照することを防ぎます。

通常のファイルの書き込みパス(->writepage())では、ページキャッシュ内でデータをインプレースで暗号化することはできません。キャッシュされた平文を保持する必要があるためです。代わりに、ファイルシステムは一時バッファや「バウンスページ」に暗号化を行い、その後一時バッファを書き出す必要があります。UBIFSなどの一部のファイルシステムは、暗号化に関係なくすでに一時バッファを使用しています。一方、ext4やF2FSなどの他のファイルシステムは、暗号化のために特別にバウンスページを割り当てる必要があります。

Fscryptは、ファイルコンテンツの暗号化・復号にカーネル暗号APIではなくインライン暗号化ハードウェアを使用することも可能です。可能であれば、および指定された場合(例: ext4/F2FSファイルシステムで「inlinecrypt」マウントオプションを指定した場合)、FscryptはBIOSに暗号化コンテキストを追加し、blk-cryptoを使用して暗号化・復号を行います。上記の読み込み/書き込みパスの変更を使用しないで処理を行います。もちろん、インライン暗号化を指定されたとしても、選択された暗号アルゴリズムにハードウェアインライン暗号化サポートが存在するか、またはCONFIG_BLK_INLINE_ENCRYPTION_FALLBACKが選択されている場合に限り、Fscryptはインライン暗号化を使用できます。どちらも存在しない場合、Fscryptは上記の読み込み/書き込みパスの変更を使用して暗号化・復号を行います。

ファイル名ハッシュと符号化¶

現代のファイルシステムは、インデックス付きディレクトリを使用してディレクトリ検索を高速化しています。インデックス付きディレクトリは、ファイル名ハッシュでキー付けされた木構造に組織化されています。->lookup()が要求された場合、ファイルシステムは通常、検索対象のファイル名をハッシュ化して、対応するディレクトリエントリを素早く見つけることができます。

暗号化を行う場合、暗号化キーあり・なしの両方で検索がサポートされ、効率的に行われることが必要です。明文のファイル名をハッシュ化することはできません。なぜなら、暗号化キーがないと明文のファイル名は取得できないからです。(明文のファイル名をハッシュ化すると、ファイルシステムの fsck ツールが暗号化されたディレクトリを最適化できなくなるためです。) 代わりに、ファイルシステムは暗号化されたファイル名（つまり、ディレクトリエントリに実際に保存されているバイト）をハッシュ化します。暗号化キーを用いて検索が要求された場合、ファイルシステムはユーザーが指定した名前を暗号化して、暗号化された名前を取得します。

暗号化キーがない状態での検索はより複雑です。暗号化されたバイトは、ファイル名として不適切な文字を含む可能性があり、そのため readdir() は暗号化された名前を base64 エンコードして表示します。 \0 および / ほとんどのファイル名ではこれで問題ありませんが、->lookup() が呼ばれた際には、ユーザーが指定した名前を base64 デコードして、暗号化されたバイトに戻します。

ただし、非常に長いファイル名の場合は、base64 エンコードによりファイル名の長さが NAME_MAX を超えてしまいます。これを防ぐため、readdir() は暗号化されたファイル名の「ハッシュ」を含む略称形式で長ファイル名を表示します。これにより、ファイルシステムは、readdir() で以前に表示されたディレクトリエントリを、高い信頼性で ->lookup() で指定されたファイル名と関連付けることができます。詳細はソースコードの struct fscrypt_nokey_name を参照してください。

暗号化キーがない状態でユーザー空間に提示されるファイル名の具体的な形式は、今後変更される可能性があります。これは、暗号化ディレクトリでコマンドが期待どおりに動作するための一時的な方法です。 rm -r ls などのコマンドが期待どおりに動作するようにするためです。

テスト¶

fscrypt のテストには、Linux の事実上のファイルシステムテストスイートである xfstests を使用します。まず、関連するファイルシステムに「encrypt」グループのすべてのテストを実行してください。また、「inlinecrypt」マウントオプションでテストを実行することで、インライン暗号化の実装をテストすることもできます。たとえば、kvm-xfstests を使って ext4 と f2fs の暗号化をテストするには、 kvm-xfstests:

kvm-xfstests -c ext4,f2fs -g encrypt
kvm-xfstests -c ext4,f2fs -g encrypt -m inlinecrypt

UBIFS の暗号化もこの方法でテストできますが、別個のコマンドで実行し、kvm-xfstests がエミュレートされた UBI ボリュームをセットアップするのに時間がかかるため、注意が必要です。

kvm-xfstests -c ubifs -g encrypt

テストが失敗するべきではありません。ただし、非デフォルトの暗号化モード（例: generic/549 および generic/550）を使用するテストは、必要なアルゴリズムがカーネルの暗号APIに組み込まれていない場合、スキップされます。また、raw block device（例: generic/399、generic/548、generic/549、generic/550）にアクセスするテストは、UBIFSでスキップされます。

「encrypt」グループのテストを実行するだけでなく、ext4およびf2fsでは、「test_dummy_encryption」マウントオプションを使用してほとんどのxfstestsを実行することも可能です。このオプションは、新しいファイルが_dummy_キーで自動的に暗号化されるようにします。API呼び出しを一切行わずに動作をテストします。この方法でkvm-xfstestsを使用する場合、以下の「encrypt」ファイルシステム構成を使用してください：

kvm-xfstests -c ext4/encrypt,f2fs/encrypt -g auto
kvm-xfstests -c ext4/encrypt,f2fs/encrypt -g auto -m inlinecrypt

この方法は「-g encrypt」よりも多くのテストを実行するため、実行に時間がかかります。そのため、以下の代替案も検討してください： gce-xfstests kvm-xfstestsではなく：

gce-xfstests -c ext4/encrypt,f2fs/encrypt -g auto
gce-xfstests -c ext4/encrypt,f2fs/encrypt -g auto -m inlinecrypt

FS-CacheネットワークファイルシステムAPI¶

ネットワークファイルシステムがFS-Cacheの機能を活用できるようにするAPIがあります。これはいくつかの原則に基づいています：

  1. キャッシュはさまざまなオブジェクトタイプを保存できます。主なオブジェクトタイプはインデックスとファイルです。インデックスはFS-Cacheがオブジェクトを素早く見つけやすく、複数のオブジェクトの廃止を容易にする特別なタイプです。

  2. すべてのインデックス、ファイル、またはその他のオブジェクトはクッキーで表されます。このクッキーには何かが関連付けられているかどうかは関係ありませんが、netfsは気にする必要がありません。

  3. トップレベルのインデックス（キャッシュされたnetfsごとに1つのエントリ）を除き、各netfsのインデックス階層はnetfsの都合に応じて構造化されます。

このAPIは<linux/fscache.h>で宣言されています。

ネットワークファイルシステムの定義¶

FS-Cacheはネットワークファイルシステムの説明が必要です。これは次の構造を持つレコードを使用して指定されます：

struct fscache_netfs {
        uint32_t                        version;
        const char                      *name;
        struct fscache_cookie           *primary_index;
        ...
};

最初の2つのフィールドは登録前に埋め込まれるべきで、3番目のフィールドは登録関数によって埋め込まれます。他のフィールドは無視され、内部使用のみのものです。

フィールドは次の通りです：

  1. ネットワークファイルシステムの名前（トップレベルインデックスでのキーとして使用されます）。

  2. ネットワークファイルシステムのバージョン（名前が一致してもバージョンが一致しない場合、このnetfsのキャッシュされた階層全体が破棄され、新たに開始されます）。

  3. プライマリインデックスを表すクッキーは、登録関数に渡された他のパラメータに基づいて割り当てられます。

たとえば、kAFS（linux/fs/afs/）は次の定義を使用して自身を記述します：

struct fscache_netfs afs_cache_netfs = {
        .version        = 0,
        .name           = "afs",
};

インデックスの定義¶

インデックスは2つの目的に使用されます：

  1. 複数のキー（AFSの「cell」、「volume ID」、「vnode ID」など）に基づいてファイルを検索するのを支援します。

  2. 特定のキーに基づいてキャッシュされたファイルのサブセットを削除するのを容易にするため、例えばAFSのボリュームの削除を模倣します。

しかし、どの2つのネットワークファイルシステムもインデックス階層をまったく同じように定義したいとは思わないため、FS-Cacheはインデックスの構造やツリーでの配置にできるだけ多くの制限を課していません。ネットワークファイルシステムは、同じレベルでインデックスとデータファイルを混在させることもできますが、推奨されません。

各インデックスエントリは、長さが不定のキーと、長さも不定の補助データから構成されます。

インデックスにはいくつかの制限があります：

  1. 非インデックスオブジェクトを含むインデックスは、単一のキャッシュに制限されるべきです。このようなオブジェクトがインデックス内で作成されると、常に最初のキャッシュにのみ作成されます。インデックスが作成されるキャッシュはキャッシュタグ（以下参照）によって制御できます。

  2. エントリデータは原子的にジャーナル可能でなければならないため、現在は約400バイトに制限されています。少なくとも400バイトは利用可能です。

  3. 検索機能が再帰的であるため、インデックスツリーの深さは慎重に判断する必要があります。層が多すぎるとカーネルのスタックをオーバーフローさせます。

オブジェクトの定義¶

オブジェクトを定義するには、次の構造の型を埋め込む必要があります。

struct fscache_cookie_def
{
        uint8_t name[16];
        uint8_t type;

        struct fscache_cache_tag *(*select_cache)(
                const void *parent_netfs_data,
                const void *cookie_netfs_data);

        enum fscache_checkaux (*check_aux)(void *cookie_netfs_data,
                                           const void *data,
                                           uint16_t datalen,
                                           loff_t object_size);

        void (*get_context)(void *cookie_netfs_data, void *context);

        void (*put_context)(void *cookie_netfs_data, void *context);

        void (*mark_pages_cached)(void *cookie_netfs_data,
                                  struct address_space *mapping,
                                  struct pagevec *cached_pvec);
};

これは次のフィールドを持ちます：

  1. オブジェクトのタイプ [必須]

    これは次の値のいずれかです：

    FSCACHE_COOKIE_TYPE_INDEX

    これは特殊なFS-Cache型のインデックスを定義します。

    FSCACHE_COOKIE_TYPE_DATAFILE

    これは通常のデータファイルを定義します。

    2〜255の間の他の値

    これはXATTRなどの特異なオブジェクトを定義します。

  2. オブジェクトタイプの名前（NUL終端でない場合、最大16文字まで）[任意]

  3. インデックスを保存するキャッシュを選択する関数 [任意]

    非インデックスオブジェクトのインスタンス化中にインデックスをキャッシュにインスタンス化する必要がある場合、この関数が呼び出されます。非インデックスオブジェクトの直下のインデックス親のみが照会されます。階層上にあるインデックスは複数のキャッシュに保存される可能性があります。非インデックスオブジェクトまたはインデックス子のみを持つインデックスにはこの関数を提供する必要はありません。

    この関数が提供されていないかNULLを返す場合、親のリストの最初のキャッシュが選ばれます。親のリストにない場合は、マスターリストの最初のキャッシュが選ばれます。

  4. 補助データを検証する関数 [任意]

    この関数は、キャッシュ内のこのオブジェクトの一致が有効であるかを確認するために呼び出されます。例えばAFSでは、サーバーから返されたデータバージョン番号と補助データを比較して、キャッシュ内のインデックスエントリがまだ有効かどうかを確認できます。

    この関数が存在しない場合、キャッシュ内の一致するオブジェクトは常に有効とみなされます。

    この関数にはキャッシュが持つオブジェクトサイズの概念が渡され、これを使って整合性を管理することもできます。

    存在する場合、この関数は次の値のいずれかを返す必要があります：

    FSCACHE_CHECKAUX_OKAY

    • エントリがそのままでは問題ない

    FSCACHE_CHECKAUX_NEEDS_UPDATE

    • エントリが更新が必要

    FSCACHE_CHECKAUX_OBSOLETE

    • エントリが削除されるべき

    この関数は、キャッシュ内の補助データからデータを抽出してネットファイルシステム（netfs）の構造体にコピーすることもできます。

  5. 完了コールバックのコンテキストを管理する関数のペア [任意]

    キャッシュの読み書き関数は、コンテキストを渡され、その後そのコンテキストがI/O完了コールバック関数に渡されます。I/O完了が呼び出されるまでこのコンテキストが有効であることを確保するため、2つの関数が提供されることがあります：コンテキストに追加の参照を取得する関数と、参照を解除する関数。

    コンテキストが使用されないか、またはスコープ外にならないオブジェクトのタイプである場合、これらの関数は必要ありません。インデックスについては、インデックスにデータが含まれないため、これらの関数は必要ありません。これらの関数は割込みコンテキストで呼び出されるため、スリープを許容しません。

  6. ページをキャッシュメタデータを保持するようにマークする関数[オプション]

    これはキャッシュがこのページにメモリ内情報を保持していることを示し、netfsが完了後にこのページをアンキャッシュするようにするためのものです。この処理はディスクにデータがあるかどうかを示すものではありません。複数のページが一度にマークされる可能性があることに注意してください。

    この関数が呼び出される前にPG_fscacheビットがページに設定されているため、この設定が十分であれば関数は提供する必要がありません。

    インデックスについては、データが許可されていないため、この関数は必要ありません。

  7. キャッシュメタデータを保持するすべてのページをアンマークする関数[必須]

    これはFS-Cacheがバックイングストアをクッキーからアンバインドしていることを示し、ページ上のすべてのマークをクリアして混乱を防ぐことを意味します。注意点として、キャッシュはすでにすべてのトラッキング情報を破棄しているため、ページを明示的にアンキャッシュする必要はありません。

    インデックスについては、データが許可されていないため、この関数は必要ありません。

ネットワークファイルシステムの（登録と解除）¶

最初のステップはネットワークファイルシステムをキャッシュに宣言することです。これにはプライマリインデックスのレイアウト（AFSの場合、「セル」レベル）を指定することも含まれます。

登録関数は以下の通りです：

int fscache_register_netfs(struct fscache_netfs *netfs);

これはネットfsの定義へのポインタを渡します。適切に0またはエラーを返します。

kAFSの場合、登録は以下の通り行われます：

ret = fscache_register_netfs(&afs_cache_netfs);

最後のステップは、もちろんアンレジストレーションです：

void fscache_unregister_netfs(struct fscache_netfs *netfs);

キャッシュタグの検索¶

FS-Cacheは複数のキャッシュの使用を許可しています。特定のインデックスサブツリーを特定のキャッシュにバインドするためには、2番目のステップとしてキャッシュ表現タグを検索する必要があります。このステップはオプションであり、FS-Cacheがどのキャッシュを使用するかを完全に決定するのも可能です。ただし、その問題点はFS-Cacheが常に最初に登録されたキャッシュを選択するためです。

名前付きタグの表現を取得するには：

struct fscache_cache_tag *fscache_lookup_cache_tag(const char *name);

これは名前としてテキスト文字列を渡し、タグの表現を返します。エラーを返すことは決してありません。メモリが不足した場合、ダミータグを返す可能性があります。これにより、このタグでのキャッシュが抑制されます。

取得した表現は、この関数に渡すことで解放しなければなりません：

void fscache_release_cache_tag(struct fscache_cache_tag *tag);

FS-Cacheは、オブジェクト定義操作 select_cache() を呼び出すときにこのタグを取得します。

インデックスの登録¶

3番目のステップは、ファイルを検索するために使用できるインデックス階層の一部をFS-Cacheに通知することです。これは、ファイルへのパス内の各インデックスに対してクッキーを要求することで実現されます：

struct fscache_cookie *
fscache_acquire_cookie(struct fscache_cookie *parent,
                       const struct fscache_object_def *def,
                       const void *index_key,
                       size_t index_key_len,
                       const void *aux_data,
                       size_t aux_data_len,
                       void *netfs_data,
                       loff_t object_size,
                       bool enable);

この関数は、親によって表されるインデックス内のインデックスエントリを作成し、defによって指される操作を呼び出してインデックスエントリを埋めます。

親内のオブジェクトを表す一意のキーは、index_key によって指され、その長さは index_key_len です。

キャッシュ内に保存される補助データのオプションなblobは、aux_data によって指され、その長さは aux_data_len でなければなりません。これは通常、整合性データの保存に使用されます。

netfsはnetfs_dataに任意の値を渡すことができます。これは、呼び出し元からの呼び出しの際にこの値が提示されます。また、トレースやメッセージのロギングにも使用できます。

キャッシュはオブジェクトに添付されたデータのサイズを追跡し、この値を object_size に設定します。インデックスの場合、この値は0でなければなりません。この値は ->check_aux() コールバックに渡されます。

この関数はエラーを返しません - すべてのエラーは内部で処理されます。ただし、クッキーがないことを示すためにNULLを返すこともできます。このトークンを別の取得（または、解放クッキー、読み込みページ、書き込みページ関数など - 以下参照）の親としてこの関数に戻すことは問題ありません。

さらに、階層の下で非インデックスオブジェクトが作成されるまで、キャッシュ内にインデックスが実際に作成されません。また、インデックスは複数の異なるキャッシュで異なるタイミングで独立して作成される可能性があります。これはすべて透明に処理され、netfsはこれらを認識しません。

enabled が false の場合、クッキーは無効状態で作成されます。クッキーを使用するには有効にする必要があります。無効なクッキーは fscache_enable_cookie() を呼び出して有効にできます（以下参照）。

たとえば、AFSでは、セルがプライマリインデックスに追加されます。このインデックスエントリには、このセル内のボリュームマッピングを含む依存インノードがあります：

cell->cache =
        fscache_acquire_cookie(afs_cache_netfs.primary_index,
                               &afs_cell_cache_index_def,
                               cell->name, strlen(cell->name),
                               NULL, 0,
                               cell, 0, true);

その後、特定のボリュームはIDによってこのインデックスに追加され、 vnode（AFSインノードの同等物）用の別のインデックスが作成されます：

volume->cache =
        fscache_acquire_cookie(volume->cell->cache,
                               &afs_volume_cache_index_def,
                               &volume->vid, sizeof(volume->vid),
                               NULL, 0,
                               volume, 0, true);

データファイルの登録¶

4番目のステップは、キャッシュ内にデータファイルを作成するリクエストです。これはインデックスクッキーの取得と同一です。違いは、オブジェクト定義のタイプがインデックスタイプ以外であることです：

vnode->cache =
        fscache_acquire_cookie(volume->cache,
                               &afs_vnode_cache_object_def,
                               &key, sizeof(key),
                               &aux, sizeof(aux),
                               vnode, vnode->status.size, true);

その他のオブジェクトの登録¶

オプションのステップとして、キャッシュに雑種のタイプのオブジェクトを作成するリクエストを行うことができます。これはインデックスクッキーの取得とほぼ同じです。違いは、オブジェクト定義におけるタイプがインデックスタイプ以外であることです。親オブジェクトがインデックスである可能性もありますが、より可能性が高いのは、データファイルなどの他のタイプのオブジェクトです:

xattr->cache =
        fscache_acquire_cookie(vnode->cache,
                               &afs_xattr_cache_object_def,
                               &xattr->name, strlen(xattr->name),
                               NULL, 0,
                               xattr, strlen(xattr->val), true);

雑種のオブジェクトは、拡張属性やディレクトリエントリなどを保存するために使用されることがあります。

データファイルサイズの設定¶

第5ステップは、ファイルの物理属性（サイズなど）を設定することです。これはキャッシュにスペースを自動的に確保しないですが、キャッシュがデータ追跡用のメタデータを適切に調整できるようにします:

int fscache_attr_changed(struct fscache_cookie *cookie);

キャッシュは、バックイングキャッシュが存在しないか、キャッシュに必要な追加メタデータのスペースがなければ -ENOBUFS を返します。

このサイズを超えてキャッシュ内のデータページを読み書きしようとした場合、-ENOBUFS で拒否される可能性があります。

この操作は、将来の時点で非同期に属性調整をスケジュールします。そのため、関数が呼び出し元に戻る後でも発生する可能性があります。属性調整は読み込みおよび書き込み操作を除きます。

ページの割り当て/読み込み/書き込み¶

第6ステップは、キャッシュ内でページを保存および取得することです。これを行うための関数は3つあります。

注意:

  1. ページを再読み込みまたは再割当する前に、まずキャッシュから外す必要があります。

  2. ネットファイルシステム（netfs）のページがページキャッシュから解放される際には、そのページをキャッシュから外す必要があります。

  3. ページをキャッシュに書き込む前に、以前に読み込まれたか、または割当されたかを確認する必要があります。

これにより、キャッシュがページ追跡を正しい順序で維持できます。

ページ読み込み¶

まず、netfs は FS-Cache に、特定のファイルの特定のページがキャッシュされている場合にその内容を読み込み、そうでない場合はスペースを割当てるよう依頼します:

typedef
void (*fscache_rw_complete_t)(struct page *page,
                              void *context,
                              int error);

int fscache_read_or_alloc_page(struct fscache_cookie *cookie,
                               struct page *page,
                               fscache_rw_complete_t end_io_func,
                               void *context,
                               gfp_t gfp);

クッキー引数には、インデックスでないオブジェクトのクッキーを指定する必要があります。指定されたページにはデータがロードされ（またページ番号を指定する役割も果たします）、gfp 引数はメモリ割当の方法を制御します。

クッキーが inode がキャッシュされていないことを示している場合:

  1. 関数は -ENOBUFS を返します。

それ以外に、キャッシュにページのコピーが存在する場合:

  1. そのページに mark_pages_cached() クッキー操作が呼び出されます。

  2. 関数は、指定されたページに直接キャッシュのバックイングデバイスからデータを読み込むリクエストを送信します。

  3. 関数は 0 を返します。

  4. 読み込みが完了した後、end_io_func() が呼び出されます:

    • クッキーが作成されたときに提供されたnetfsデータ。

    • ページ記述子。

    • 上記の関数に渡されたコンテキスト引数。これは上記のget_context/put_context関数を使用して維持されます。

    • 成功時は0、エラー時は負のエラーコードを表す引数。

    エラーが発生した場合、ページに利用可能なデータが含まれていないと想定されるため、fscache_readpages_cancel()を呼び出す必要があります。

    読み込みがエラーとなった場合、end_io_func()はプロセスコンテキストで呼び出されます。ただし、読み込みが成功した場合は割込みコンテキストで呼び出される可能性があります。

キャッシュにコピーが存在しないが、キャッシュがページを保存できる場合:

  1. そのページに mark_pages_cached() クッキー操作が呼び出されます。

  2. キャッシュにブロックが予約され、オブジェクトに適切な場所にアタッチされる可能性があります。

  3. 関数は-ENODATAを返します。

この関数は-ENOMEMまたは-EINTRを返すこともあり、その場合キャッシュからデータを読み取っていません。

ページ割り当て¶

ファイルが拡張されてキャッシュにデータが存在しないと予想される場合、ブロックを単純に割り当てることができます:

int fscache_alloc_page(struct fscache_cookie *cookie,
                       struct page *page,
                       gfp_t gfp);

これはfscache_read_or_alloc_page()関数に似ていますが、キャッシュからデータを読み取らない点が異なります。ブロックが割り当てられた場合0を返し、他の関数では-ENODATAを返します。キャッシュへの書き込み前にどちらか一方を実行する必要があります。

成功した場合、mark_pages_cached() クッキー操作がページに呼び出されます。

ページ書き込み¶

netfsがページの内容を変更した場合（初期ダウンロードによるものか、ユーザーが書き込みを行った場合でも）、ページをキャッシュに書き戻す必要があります:

int fscache_write_page(struct fscache_cookie *cookie,
                       struct page *page,
                       loff_t object_size,
                       gfp_t gfp);

クッキー引数にはデータファイルのクッキーを指定し、ページには書き込むデータを含める必要があります（またページ番号を指定するためにも使用されます）。object_sizeはオブジェクトの再定義されたサイズで、gfp引数はメモリ割当の方法を制御します。

ページはまず読み込まれたり、割り当てられたりした成功した状態でなければならず、書き込み前にキャッシュされていない必要があります。

クッキーがインノードがキャッシュされていないことを示している場合:

  1. 関数は -ENOBUFS を返します。

それ以外に、キャッシュにこのページを保持するために空間を確保できる場合:

  1. PG_fscache_writeがページに設定されます。

  2. 関数は、指定されたページからデータをキャッシュのバックイングデバイスに直接書き込むリクエストを送信します。

  3. 関数は 0 を返します。

  4. 書き込みが完了すると、ページのPG_fscache_writeがクリアされ、そのビットを待っているすべてのプロセスが起動されます。

キャッシュに空きがなければ -ENOBUFS が返されます。予期せぬ状況（ディスクエラーなど）により書き込みが行われなかったにもかかわらず PG_fscache_write ビットがクリアされる可能性もあります。

書き込みは非同期で行われます。

複数ページの読み込み¶

readpages() アドレス空間操作で要求されたように、複数のページを一度に読み込む機能が提供されています。

int fscache_read_or_alloc_pages(struct fscache_cookie *cookie,
                                struct address_space *mapping,
                                struct list_head *pages,
                                int *nr_pages,
                                fscache_rw_complete_t end_io_func,
                                void *context,
                                gfp_t gfp);

fscache_read_or_alloc_page() と同様の仕組みで動作しますが、以下の点が異なります。

  1. データを取得できるページは pages から削除され、nr_pages も減らされ、ディスクに読み込まれるよう送信されます。ディスク上の隣接するページの読み込みは効率を高めるためにマージされることがあります。

  2. 複数のページが読み込まれたり割当先になった場合、mark_pages_cached() コークレート操作が一括で呼び出されます。

  3. 一般的なエラーが発生した場合は、そのエラーが返されます。

    また、一部のページが割当先にできなかったり読み込めなかった場合、-ENOBUFS が返されます。

    一部のページが読み込めなかったが割当先にされた場合、-ENODATA が返されます。

    すべてのページが読み込まれた場合、0 が返され、リストは空になり、 *nr_pages 値は 0 になります。

  4. 読み込みが完了するごとに end_io_func が各ページに対して呼び出されます。エラーが発生した場合（error != 0）はプロセスコンテキストで呼び出されますが、エラーがない場合は割込みコンテキストで呼び出される可能性があります。

注意：-ENODATA、-ENOBUFS またはその他のエラーが返されたとしても、一部のページが読み込まれ、一部が割当先になる可能性があります。そのようなページは適切にマークされ、キャッシュ解除が必要です。

未読ページのキャンセル¶

fscache_read_or_alloc_pages() に1つ以上のページが渡され、キャッシュから読み込まれず、下位ファイルシステムからも読み込まれなかった場合、そのページのマークや予約を削除する必要があります。これは以下の関数を呼び出すことで実現できます：

void fscache_readpages_cancel(struct fscache_cookie *cookie,
                              struct list_head *pages);

呼び出し元に戻る前に呼び出してください。cookie 引数は fscache_read_or_alloc_pages() に渡されたものと同じにしてください。pages リスト内のすべてのページが検査され、PG_fscache が設定されているページはキャッシュ解除されます。

ページのアンキャッシュ¶

ページをキャッシュ解除するには、この関数を呼び出してください：

void fscache_uncache_page(struct fscache_cookie *cookie,
                          struct page *page);

この関数は、ネットFS ページに対するキャッシュ内のメモリ表現を解放するためのものです。この関数は、上記の読み込みまたは書き込みページ関数が呼び出されたすべてのページに対して1回ずつ呼び出さなければなりません。キャッシュのメモリ内の追跡情報を正しく破壊するためです。

注意：ページはデータファイルから明示的に削除できません。データファイル全体を廃止する必要があります（下記の relinquish コークレート関数を参照してください）。

さらに、この操作はread/allocおよびwrite関数によって開始された非同期読み込みまたは書き込み操作をキャンセルしないことに注意してください。そのため、ページ無効化関数は以下のものを使用しなければなりません。

bool fscache_check_page_write(struct fscache_cookie *cookie,
                              struct page *page);

キャッシュにページが書き込まれているかを確認するためのもので、

void fscache_wait_on_page_write(struct fscache_cookie *cookie,
                                struct page *page);

書き込まれている場合は待機するためのものです。

releasepage()を実装する際には、vmscanがページを強制的に排出しようとしている場合のヒューリスティクスを管理する特別なFS-Cache関数が存在します。これは、キャッシュがページをキャッシュに書き込もうとしている場合（その場合、メモリの割当が必要になることもあります）と衝突する可能性があるためです。

bool fscache_maybe_release_page(struct fscache_cookie *cookie,
                                struct page *page,
                                gfp_t gfp);

この関数はnetfsのcookieと、releasepage()に渡されたページおよびgfp引数を取ります。ページが何らかの理由でまだ解放できない場合はfalseを返し、trueを返すとページがキャッシュから解除され、解放可能になったことを示します。

ページの解放を可能にするため、この関数は進行中のストレージ要求を待機するか、またはストレージ要求をキャンセルするかを選択します。後者の場合は、そのページは今回はキャッシュに保存されません。

Bulk Image Page Uncache¶

inodeにアタッチされているすべてのページに対してuncacheを実行するための簡易ルーチンが提供されています。これは、inode上のページがキャッシュ上のページと1対1で対応していると仮定しています。

void fscache_uncache_all_inode_pages(struct fscache_cookie *cookie,
                                     struct inode *inode);

この関数は、ページがキャッシュされた際に使用されたnetfsのcookieと、ページがアタッチされているinodeを取ります。この関数は、キャッシュへのページの書き込みが完了するのを待機し、キャッシュがページを一般に処理を終了するのを待機します。エラーは返されません。

インデックスとデータファイルの整合性¶

オブジェクトの補助データがキャッシュ内で最新であるかを確認するには、次の関数を呼び出せます。

int fscache_check_consistency(struct fscache_cookie *cookie,
                              const void *aux_data);

この関数はnetfsに呼び戻して、cookieに関連する補助データが正しいかを確認します。aux_dataがNULLでない場合、まず補助データバッファを更新します。正しい場合は0を、正しい場合は-ESTALEを返します。また、-ENOMEMや-ERESTARTSYSも返す可能性があります。

インデックスやその他のオブジェクトのインデックスデータの更新を要求するには、次の関数を呼び出さなければなりません。

void fscache_update_cookie(struct fscache_cookie *cookie,
                           const void *aux_data);

この関数は、aux_dataがNULLでない場合、cookieの補助データバッファをaux_dataから更新し、その後、そのデータをディスクに保存するスケジュールを設定します。親インデックス定義の更新メソッドが呼び出されてデータを転送します。

一部の更新は、データブロックがデータファイルオブジェクトに追加されるなど、他のタイミングで自動的に発生する可能性があります。

クッキーの有効化¶

クッキーは有効または無効の2つの状態のいずれかに存在します。クッキーが無効の場合、子クッキーの取得や状態の確認・更新・無効化、バックイングページの割り当て・読み込み・書き込みを無視しますが、ページのアンキャッシュ化やクッキーの解放は依然として可能です。

初期の有効状態はfscache_acquire_cookie()によって設定されますが、後でクッキーを有効または無効にすることも可能です。クッキーを無効にするには、以下を呼び出します:

void fscache_disable_cookie(struct fscache_cookie *cookie,
                            const void *aux_data,
                            bool invalidate);

クッキーがすでに無効でない場合、この関数は他の有効化・無効化操作をブロックし、クッキーを無効化中とマークし、バックイングオブジェクトを破棄または無効化し、関連するオブジェクトの活動が停止するのを待ってからクッキーをアンロックします。

すべての可能性のある失敗は内部で処理されます。呼び出し元は、すべてのページのマーキングをクリアするためにfscache_uncache_all_inode_pages()を呼び出すことを検討すべきです。

クッキーは有効化または再有効化するには、以下を使用します:

void fscache_enable_cookie(struct fscache_cookie *cookie,
                           const void *aux_data,
                           loff_t object_size,
                           bool (*can_enable)(void *data),
                           void *data)

クッキーがすでに有効でない場合、この関数は他の有効化・無効化操作をブロックし、can_enable()を呼び出し、クッキーがインデックスクッキーでない場合、バックイングオブジェクトの取得手順を開始します。

オプションのcan_enable()関数はdata引数を受け取り、有効化が実際に開始されるべきかどうかを判断して返します。

すべての可能性のある失敗は内部で処理されます。一時的なバックイングオブジェクトが割り当てられた場合に限り、クッキーが有効とマークされます。

オブジェクトのデータサイズはobject_sizeから更新され、->check_aux()関数に渡されます。

有効化ロック内でaux_dataがNULLでない場合、クッキーの補助データバッファはaux_dataから更新されます。

その他のクッキー操作¶

いくつかの操作を用いてクッキーを制御できます:

  • クッキーのピン固定:

    int fscache_pin_cookie(struct fscache_cookie *cookie);
void fscache_unpin_cookie(struct fscache_cookie *cookie);

これらの操作はデータクッキーをキャッシュにピン固定し、ピン固定を解除するのを許可します。インデックスクッキーには適用されません。

ピン固定関数は成功時に0を返し、クッキーがキャッシュでサポートされていない場合は-ENOBUFS、キャッシュがピン固定をサポートしていない場合は-EOPNOTSUPP、十分なスペースがない場合は-ENOSPC、その他の問題がある場合は-ENOMEMまたは-EIOを返します。

  • データ領域の予約:

    int fscache_reserve_space(struct fscache_cookie *cookie, loff_t size);

    これはネットファイルシステムがファイルの指定された量をキャッシュに予約するのを許可します。ファイルの現在のサイズを超える量を要求しても、今後の拡張を考慮するため許可されます。

    sizeがゼロの場合、予約はキャンセルされます。

    操作が成功した場合は0を返します。クッキーがキャッシュによってサポートされていない場合は-ENOBUFSを、キャッシュが予約をサポートしていない場合は-EOPNOTSUPPを、操作を実行するための十分なスペースがない場合は-ENOSPCを、それ以外の問題がある場合は-ENOMEMまたは-EIOを返します。

    この操作はキャッシュ内のオブジェクトを固定しません。使用されていない場合は、スペースを確保するために削除される可能性があります。

クッキーの解除¶

クッキーを削除するには、この関数を呼び出す必要があります。

void fscache_relinquish_cookie(struct fscache_cookie *cookie,
                               const void *aux_data,
                               bool retire);

retireがゼロでない場合、オブジェクトは再利用のためにマークされ、そのオブジェクトが存在するすべてのアクティブなキャッシュから削除されます。さらに、すべての子オブジェクトもリタイアされます。

retireがゼロの場合、次の取得関数が呼び出されるときにオブジェクトが再び利用可能になる可能性があります。ここでリタイアはクッキーのピン固定を上書きします。

aux_dataがNULLでない場合、クッキーの補助データが更新され、キャッシュがディスク上でこれを非同期に更新します。

非常に重要な注意点があります - 「子」インデックス、オブジェクト、ページのすべてのクッキーがリリクィッシュされた後に、クッキーに対してリリクィッシュを呼び出す必要があります。

インデックスの無効化¶

インデックスサブツリーを直接無効化する方法はありません。これを実行するには、現在所有しているクッキーをリリクィッシュし、リタイアした後、新しいクッキーを取得する必要があります。

データファイルの無効化¶

データを含むオブジェクトを無効化する必要がある場合があります。これは通常、サーバーがネットFSに外的な変更を通知したときに発生します。その際、ネットFSはインノードに関するすべての状態を破棄し、サーバーから再読み込みする必要があります。

キャッシュオブジェクトを無効化する必要がある場合、次の関数を呼び出すことができます。

void fscache_invalidate(struct fscache_cookie *cookie);

スピンロックを保持しながら呼び出すことができます。この関数はスレッドプールに作業をdeferします。この時点ですべての既存のストレージ、取得、属性変更操作はキャンセルされ破棄されます。一部の将来の操作は、キャッシュが操作キューにバリアを挿入するまで拒否されます。その後、無効化操作の後に操作が再びキューに追加されます。

無効化操作は属性変更操作と補助データ更新操作を行います。これらが変更される可能性が高いからです。

ネットFSが無効化操作が通常の操作を再開できるポイントに到達するのを待つには、次の関数を使用できます。

void fscache_wait_on_invalidate(struct fscache_cookie *cookie);

FS-cache専用のページフラグ¶

FS-Cacheは自身の目的のためにページフラグPG_private_2を使用します。これはPG_fscacheと別名で呼ばれます。

PG_fscacheは、ページがキャッシュによって認識されていることを示し、ページが消失する際にはキャッシュに通知する必要があることを表します。これはnetfsに、このページに関心があることを示すフラグであり、関心とはそのページへのポインタ、割り当てられたリソース、または進行中のI/Oなどが含まれます。

netfsはreleasepage()などのメソッドでこの情報を活用し、ページをアンキャッシュする必要があるかどうか、または更新する必要があるかどうかを判断します。

さらに、このビットが設定されている場合、PG_privateが設定されていない場合でもreleasepage()およびinvalidatepage()操作が呼び出され、ページを削除します。これにより、fscache_read_or_alloc_pages()が呼ばれる前にキャッシュが試行されることが可能になります。 read_cache_pages() fscache_read_or_alloc_pages()が呼ばれる前にこの操作が呼び出されるため、前者は特定の状況において与えられたページを解放しようとします。

このビットはPG_privateなどの他のビットと重複しません。これは、ブロックバッファリングコードを使用するファイルシステムでもFS-Cacheを使用可能であることを意味します。

このフラグには複数の操作が定義されています。

int PageFsCache(struct page *page);
void SetPageFsCache(struct page *page)
void ClearPageFsCache(struct page *page)
int TestSetPageFsCache(struct page *page)
int TestClearPageFsCache(struct page *page)

これらの関数は、PG_fscacheのビットのテスト、設定、クリア、テストと設定、テストとクリアの操作です。

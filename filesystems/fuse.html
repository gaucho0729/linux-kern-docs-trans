FUSE¶

定義¶

ユーザー空間ファイルシステム:

データとメタデータが通常のユーザー空間プロセスによって提供されるファイルシステム。カーネルインターフェースを通じて通常のアクセスが可能です。

ファイルシステムデーモン:

ファイルシステムのデータとメタデータを提供するプロセス（複数可）。

非特権マウント（またはユーザーマウント）:

非特権ユーザー（ルート以外）によってマウントされるユーザー空間ファイルシステム。ファイルシステムデーモンはマウントユーザーの特権で実行されています。注意: これは/etc/fstabの「user」オプションで許可されるマウントとは異なり、ここでは説明しません。

ファイルシステム接続:

ファイルシステムデーモンとカーネル間の接続。デーモンが終了するか、ファイルシステムがumountされるまで接続が維持されます。注意: ファイルシステムの切断（またはラズィーumount）は ではありません 接続を切断します。この場合、接続はファイルシステムへの最後の参照が解放されるまで維持されます。

マウント所有者:

マウントを実行するユーザー。

ユーザー:

ファイルシステム操作を実行するユーザー。

FUSEとは何ですか？¶

FUSEはユーザー空間ファイルシステムのフレームワークです。カーネルモジュール（fuse.ko）、ユーザー空間ライブラリ（libfuse.*）、マウントユーティリティ（fusermount）から構成されています。

FUSEの最も重要な特徴の一つは、セキュアで権限のないマウントを許可することです。これによりファイルシステムの利用可能性が新たな可能性を開きます。良い例はsshfsで、これはsftpプロトコルを使用したセキュアなネットワークファイルシステムです。

ユーザー空間のライブラリとユーティリティは、 FUSE ホームページ:

ファイルシステムタイプ¶

mount(2)に指定されるファイルシステムのタイプは次のいずれかです：

fuse

これはFUSEファイルシステムをマウントする通常の方法です。mountシステムコールの最初の引数には、カーネルが解釈しない任意の文字列を指定できます。

fuseblk

このファイルシステムはブロックデバイスベースです。mountシステムコールの最初の引数はデバイス名として解釈されます。

マウントオプション¶

fd=N

ユーザー空間ファイルシステムとカーネル間での通信に使用するファイルディスクリプタ。このファイルディスクリプタは、FUSEデバイス（‘/dev/fuse’）を開いて取得したものでなければなりません。

rootmode=M

ファイルシステムのルートのファイルモードをoctal表記で指定します。

user_id=N

マウント所有者の数値ユーザーID。

group_id=N

マウント所有者の数値グループID。

default_permissions

デフォルトではFUSEはファイルアクセス権限のチェックを行いません。ファイルシステムはアクセスポリシーを実装するか、下位のファイルアクセスメカニズムに委譲することができます（例：ネットワークファイルシステムの場合）。このオプションにより権限チェックが有効になり、ファイルモードに基づいたアクセス制限が行われます。通常、'allow_other'マウントオプションと併用して使用されます。

allow_other

このオプションは、ファイルアクセスをマウントするユーザーにのみ制限するセキュリティ措置を上書きします。このオプションはデフォルトではrootのみが使用可能ですが、(userspace)設定オプションによりこの制限を解除できます。

max_read=N

このオプションにより、読み取り操作の最大サイズを設定できます。デフォルトは無限です。注意：読み取りリクエストのサイズは、i386では32ページ（128kbyte）に制限されています。

blksize=N

ファイルシステムのブロックサイズを設定します。デフォルトは512です。このオプションは'fuseblk'タイプのマウントにのみ有効です。

制御ファイルシステム¶

FUSE用の制御ファイルシステムがあり、以下のようにマウントできます：

mount -t fusectl none /sys/fs/fuse/connections

これを'/sys/fs/fuse/connections'ディレクトリ以下にマウントすることで、以前のバージョンとの互換性が確保されます。

fuse制御ファイルシステムでは、各接続に対して一意の番号で名付けられたディレクトリが存在します。

各接続に対して、このディレクトリ内には以下のファイルが存在します：

waiting

ユーザー空間またはファイルシステムデーモンによって処理待ちのリクエスト数です。ファイルシステムにアクティビティがなくかつ'waiting'がゼロでない場合、ファイルシステムが停止しているかデッドロックしている可能性があります。

abort

このファイルに何でも書き込むと、ファイルシステム接続が中止されます。これにより、すべての待機中のリクエストが中止され、すべての中断リクエストおよび新しいリクエストにエラーが返されます。

これらのファイルの読み取りまたは書き込みは、マウントの所有者だけが行えます。

ファイルシステム操作の中断¶

FUSEファイルシステムリクエストを発行するプロセスが中断された場合、以下が起こります：

  • リクエストがユーザー空間に送信されていない場合かつシグナルが致命的（SIGKILLや未処理の致命的シグナル）であれば、リクエストはキューから外され、即座に返されます。

  • リクエストがユーザー空間に送信されていない場合かつシグナルが致命的でない場合は、リクエストに中断フラグが設定されます。リクエストがユーザー空間に成功裏に送信され、かつこのフラグが設定されている場合、INTERRUPTリクエストがキューに追加されます。

  • リクエストがすでにユーザー空間に送信されている場合、INTERRUPTリクエストがキューに追加されます。

INTERRUPTリクエストは他のリクエストよりも優先度が高く、ユーザー空間ファイルシステムは他のリクエストよりもまずキューに並んだINTERRUPTリクエストを受信します。

ユーザースペースファイルシステムは、INTERRUPT 要求を完全に無視するか、または元の要求に応答を送信してエラーを EINTR に設定するかのいずれかを行う可能性があります。 元の 要求に応答を送信してエラーを EINTR に設定する

元の要求の処理とその INTERRUPT 要求の処理の間に競合状態が発生する可能性もあります。この場合、2つの可能性があります：

  1. INTERRUPT 要求が元の要求の処理よりも先に処理される

  2. INTERRUPT 要求が元の要求が応答された後で処理される

ファイルシステムが元の要求を検出できない場合、タイムアウトや新しい要求の到着を待つ必要があります。その後、INTERRUPT 要求に EAGAIN エラーで応答します。ケース1では INTERRUPT 要求が再キューイングされます。ケース2では INTERRUPT 応答が無視されます。

ファイルシステム接続の中断¶

ファイルシステムが応答しない状況に陥る可能性があります。その理由は以下の通りです：

  1. 不完全なユーザースペースファイルシステムの実装

  2. ネットワーク接続の切断

  3. 意図せぬデッドロック

  4. 悪意のあるデッドロック

(c) および d) については後述のセクションを参照してください)

これらのいずれかの状況では、ファイルシステムへの接続を中断することが役立つ場合があります。その方法は以下の通りです：

  • ファイルシステムデーモンを終了する。a) および b) の場合に有効です。

  • ファイルシステムデーモンとそのすべてのユーザーを終了する。すべてのケースに有効ですが、一部の悪意のあるデッドロックには効きません。

  • 強制的なアンマウント (umount -f) を使用する。すべてのケースに有効ですが、ファイルシステムがまだ接続されている必要があります（ラズィーアンマウントされていない必要があります）。

  • FUSE コントロールファイルシステムを通じてファイルシステムを中断する。最も強力な方法で常に有効です。

非特権マウントはどのように動作するのか？¶

mount() システムコールは特権操作であるため、ヘルパープログラム (fusermount) が必要です。これは setuid root でインストールされています。

非特権マウントを提供する意味は、マウント所有者がこの機能を使用してシステムを侵害することができないことです。これに伴う明確な要件は以下の通りです：

  1. マウント所有者がマウントされたファイルシステムを介して昇格した権限を取得できないこと

  2. マウント所有者が他のユーザーおよびスーパーユーザーのプロセスから不正なアクセスを取得できないこと

  3. マウント所有者が他のユーザーまたはスーパーユーザーのプロセスに不望な挙動を誘発できないこと

これらの要件はどのように満たされるのか？¶

  1. マウント所有者が昇格した権限を取得する方法は以下の通りです：

    1. デバイスファイルを含むファイルシステムを作成し、このデバイスを開くこと

    2. suid または sgid アプリケーションを含むファイルシステムを作成し、このアプリケーションを実行すること

    解決策は、デバイスファイルを開くことを許可せず、実行時にsetuidとsetgidビットを無視することです。これにより、fusermountは非特権マウントの際に常に「nosuid」と「nodev」をマウントオプションに追加します。

  2. 他のユーザーがファイルシステム内のファイルやディレクトリにアクセスしている場合、ファイルシステムのデーモンがリクエストを処理中に実行された操作の正確な順序とタイミングを記録できます。この情報は通常マウント所有者にはアクセス不可能であり、これにより情報漏洩が発生します。

    この問題の解決策はC)の2)で説明します。

  3. マウント所有者は、他のユーザーのプロセスに不望な挙動を誘発する複数の方法があります。例えば:

    1. マウント所有者が通常変更できない（または制限付きでしか変更できない）ファイルやディレクトリ上にファイルシステムをマウントすることです。

      fusermountでは、マウントポイントのアクセス権限を確認し、マウント所有者がマウントポイントに書き込みアクセス可能であり、かつマウントポイントが「sticky」ディレクトリでない場合にのみマウントを許可します。

    2. 1)の問題が解決しても、マウント所有者は他のユーザーのプロセスの挙動を変更できます。

      1. ファイルシステム操作の実行を遅延させたり、無限に停止させることでユーザーまたは全体システムに対するDoS攻撃を引き起こすことができます。例えば、suidアプリケーションがシステムファイルをロックし、その後マウント所有者のファイルシステム上のファイルにアクセスすると、システムファイルが永久にロックされる可能性があります。

      2. 無限の長さのファイルやディレクトリ、または無限の深さのディレクトリ構造を提供することで、システムプロセスがディスク容量やメモリ、その他のリソースを消費させ、再びDoSを引き起こす可能性があります。 DoS.

      この問題およびB)の解決策は、マウント所有者が監視または操作できないプロセスがファイルシステムにアクセスすることを許可しないことです。なぜなら、マウント所有者がプロセスをptraceできる場合、FUSEマウントを使わずに上述のすべての操作を実行できるからです。したがって、ptraceで使用される同じ基準を用いて、プロセスがファイルシステムにアクセスできるかどうかを判定できます。

      注意: 空文字（null byte）は文字列の一部とみなされ、検索対象となる。 ptrace B/2/iを防ぐには厳密にはチェックは必要ありません。マウント所有者がファイルシステムをアクセスしているプロセスにシグナルを送信できる権限があるかどうかを確認すれば十分です、なぜなら SIGSTOP を用いることで同様の効果を得られます。

これらの制限は受け入れがたいでしょうか？¶

システム管理者がユーザーに十分信頼を寄せている、または他の手段でシステムプロセスが非特権マウントに進入することを確実に確保できる場合、'user_allow_other'という設定オプションで最後の制限を緩和できます。この設定オプションが有効な場合、マウントするユーザーは'allow_other'マウントオプションを指定することで、他のユーザーのプロセスに対するチェックを無効化できます。

カーネル - ユーザースペースインターフェース¶

以下のダイアグラムは、FUSEにおいてファイルシステム操作（この例ではunlink）がどのように実行されるかを示しています。

|  "rm /mnt/fuse/file"               |  FUSE filesystem daemon
|                                    |
|                                    |  >sys_read()
|                                    |    >fuse_dev_read()
|                                    |      >request_wait()
|                                    |        [sleep on fc->waitq]
|                                    |
|  >sys_unlink()                     |
|    >fuse_unlink()                  |
|      [get request from             |
|       fc->unused_list]             |
|      >request_send()               |
|        [queue req on fc->pending]  |
|        [wake up fc->waitq]         |        [woken up]
|        >request_wait_answer()      |
|          [sleep on req->waitq]     |
|                                    |      <request_wait()
|                                    |      [remove req from fc->pending]
|                                    |      [copy req to read buffer]
|                                    |      [add req to fc->processing]
|                                    |    <fuse_dev_read()
|                                    |  <sys_read()
|                                    |
|                                    |  [perform unlink]
|                                    |
|                                    |  >sys_write()
|                                    |    >fuse_dev_write()
|                                    |      [look up req in fc->processing]
|                                    |      [remove from fc->processing]
|                                    |      [copy write buffer to req]
|          [woken up]                |      [wake up req->waitq]
|                                    |    <fuse_dev_write()
|                                    |  <sys_write()
|        <request_wait_answer()      |
|      <request_send()               |
|      [add request to               |
|       fc->unused_list]             |
|    <fuse_unlink()                  |
|  <sys_unlink()                     |

注意

上記の説明ではすべてが大幅に簡略化されています

FUSEファイルシステムがデッドロックする方法はいくつかありますが、ここでは権限のないユーザースペースプログラムについて話しているため、何か対策が必要です。

シナリオ1 - シンプルなデッドロック:

|  "rm /mnt/fuse/file"               |  FUSE filesystem daemon
|                                    |
|  >sys_unlink("/mnt/fuse/file")     |
|    [acquire inode semaphore        |
|     for "file"]                    |
|    >fuse_unlink()                  |
|      [sleep on req->waitq]         |
|                                    |  <sys_read()
|                                    |  >sys_unlink("/mnt/fuse/file")
|                                    |    [acquire inode semaphore
|                                    |     for "file"]
|                                    |    *DEADLOCK*

この問題の解決策は、ファイルシステムを中止できるようにすることです。

シナリオ2 - 複雑なデッドロック

このケースは、ファイルシステムを巧妙に設計する必要があります。これは上記のケースの変種で、ファイルシステムへの呼び出しは明示的ではなく、ページフォールトによって引き起こされます。

|  Kamikaze filesystem thread 1      |  Kamikaze filesystem thread 2
|                                    |
|  [fd = open("/mnt/fuse/file")]     |  [request served normally]
|  [mmap fd to 'addr']               |
|  [close fd]                        |  [FLUSH triggers 'magic' flag]
|  [read a byte from addr]           |
|    >do_page_fault()                |
|      [find or create page]         |
|      [lock page]                   |
|      >fuse_readpage()              |
|         [queue READ request]       |
|         [sleep on req->waitq]      |
|                                    |  [read request to buffer]
|                                    |  [create reply header before addr]
|                                    |  >sys_write(addr - headerlength)
|                                    |    >fuse_dev_write()
|                                    |      [look up req in fc->processing]
|                                    |      [remove from fc->processing]
|                                    |      [copy write buffer to req]
|                                    |        >do_page_fault()
|                                    |           [find or create page]
|                                    |           [lock page]
|                                    |           * DEADLOCK *

解決策は基本的に上記と同じです。

追加の問題として、書き込みバッファがリクエストにコピーされる間、リクエストは中断・中止されてもいけません。これは、リクエストが返った後でコピー先のアドレスが有効でなくなる可能性があるためです。

これは、コピーをアトミックに実行し、get_user_pages()で書き込みバッファに属するページがフォールトされる間、中止を許可することで解決します。'req->locked'フラグはコピーが進行中のことを示し、このフラグが未設定になるまで中止が遅延されます。

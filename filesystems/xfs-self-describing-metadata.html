XFS 自己記述メタデータ¶

はじめに¶

XFS が直面している最大のスケーラビリティ問題は、アルゴリズムのスケーラビリティではなく、ファイルシステム構造の検証に起因しています。ディスク上の構造とインデックス、およびそれらを反復処理するアルゴリズムのスケーラビリティは、ペタバイト規模のファイルシステムで数十億の inode をサポートするには十分ですが、このスケーラビリティが検証問題を引き起こしています。

XFS のほぼすべてのメタデータは動的に割り当てられています。固定位置にあるメタデータは、割当グループヘッダー（SB、AGF、AGFL および AGI）に限られ、他のすべてのメタデータ構造は、ファイルシステム構造をさまざまな方法で歩くことで発見する必要があります。これはすでにユーザー空間ツールが構造の検証や修復に使用していますが、それらが検証できる範囲には限界があり、これにより XFS ファイルシステムのサポート可能なサイズに制限がかかっています。

たとえば、100TB のファイルシステムの構造を分析して破損原因を特定しようとしても、xfs_db とスクリプトを手動で使用して解析することは可能ですが、依然として単一ビットエラーまたは不適切な書き込みが破損イベントの根本原因であるかを確認する作業は手動です。このような法医学的分析には数時間から数日かかるため、この規模での原因究明は完全に可能です。

しかし、ファイルシステムを 1PB までスケーラブルにすると、分析対象となるメタデータは 10 倍になり、法医学的分析の作業時間は週単位、月単位に拡大します。ほとんどの分析作業は遅く手間がかかるため、分析量が増えるほど原因がノイズに埋もれやすくなります。したがって、PB スケールのファイルシステムをサポートする上で最も重要な課題は、基本的な法医学的分析に必要な時間と労力を最小限に抑えることです。

自己記述メタデータ¶

現在のメタデータ形式の問題点の一つは、メタデータブロック内のマジックナンバー以外に、それが何であるかを特定する方法がありません。正しい場所にあるかすら確認できません。要するに、単独でメタデータブロックを確認しても、それが正しい場所にあるか、内容が有効かを判断することはできません。

したがって、法医学的分析に費やす時間の多くは、メタデータ値の基本的な検証に費やされ、範囲内にある値（自動検証チェックで検出されないが正しくない値）を特定する作業になります。クロスリンクされたブロックリスト（例：Bツリーにおける兄弟ポインタがリスト内にループを形成するなど）のような要素を特定し、その仕組みを理解することが、問題が発生した原因を理解する鍵になりますが、事後にはブロックがどのようにリンクされ、ディスクに書き込まれた順序を特定することは不可能です。

したがって、メタデータにより多くの情報を記録し、メタデータが健全であるかを素早く判断できるようにする必要があります。すべての可能性のあるエラーを防ぐことはできませんが、一般的なエラーは容易に検出可能にする必要があります。そのため、自己記述型メタデータという概念が導入されました。

自己記述型メタデータの最初で最も重要な要件は、メタデータオブジェクトに特定の場所に一意の識別子が含まれていることです。これにより、ブロックの期待される内容を特定し、メタデータオブジェクトをパース・検証することができるようになります。オブジェクト内のメタデータの種類を独立して特定できない場合、メタデータは自分自身を十分に記述していません！

幸いなことに、XFSメタデータのほぼすべてにマジックナンバーが埋め込まれています（AGFL、リモートシンボリックリンク、リモート属性ブロックを除く）。したがって、これらのオブジェクトのディスク上のフォーマットを変更し、マジックナンバーに追加の識別情報を追加することで、単純にメタデータオブジェクトのマジックナンバーを変更するだけで検出可能です。つまり、現在のマジックナンバーを持つ場合、メタデータは自己記述ではありません。新しいマジックナンバーを持つ場合、自己記述型となり、フォレンジック分析や修復中にメタデータオブジェクトの自動検証を大幅に拡張できます。

まず第一に、自己記述型メタデータには全体的な整合性チェックが必要です。外部からの影響で変更された可能性があるメタデータを信頼することはできません。そのため、整合性チェックの仕組みが必要であり、これはメタデータブロックにCRC32c検証を追加することで実現されます。ブロックが意図したメタデータを含んでいることを確認できる場合、多くの手動検証作業を省略できます。

XFSではメタデータの長さは64kを超えてはならないため、CRC32cが選ばれました。これによりメタデータブロックのマルチビットエラーを検出するのに32ビットのCRCは十分です。また、CRC32cは現在の一般的なCPUでハードウェアで加速されているため、高速です。したがって、CRC32cは使用可能な整合性チェックの中で最も強力なものではありませんが、私たちのニーズには十分であり、オーバーヘッドも比較的少ないです。より大きな整合性フィールドやアルゴリズムのサポートを追加してもCRC32cよりも追加価値はほとんどありませんが、複雑さが大幅に増すため、整合性チェックメカニズムの変更は提供されていません。

自己記述型メタデータには、他のメタデータを参照することなくメタデータブロックが正しい場所にあることを検証できるだけの情報が含まれなければなりません。つまり、場所情報が必要です。メタデータにブロック番号を追加するだけでは誤った宛先への書き込みを防げません。書き込みが誤って別のLUNに向けられ、結果として誤ったファイルシステムの「正しいブロック」に書き込まれる可能性があるためです。したがって、場所情報にはファイルシステム識別子とブロック番号の両方が含まれるべきです。

法医学分析において重要な情報の一つは、メタデータブロックがどのオーナーに属するかを把握することです。すでにメタデータの種類、場所、有効/破損状態、最後に変更された時間などがわかっています。ブロックのオーナーを知ることは、関連する他のメタデータを探して破損範囲を特定するのに重要です。たとえば、拡張属性Btreeオブジェクトの場合、どのinodeに属するかが不明で、結果としてファイルシステム全体を走査する必要があります。さらに悪いことに、破損によりオーナーが見つからない場合（つまり孤立ブロック）があり、メタデータにオーナー情報がないと破損範囲を特定できません。メタデータオブジェクトにオーナー情報があれば、すぐに上から下への検証を実施して問題の範囲を特定できます。

メタデータの種類によってオーナー識別子は異なります。たとえば、ディレクトリ、属性、拡張Btreeブロックはすべてinodeによって所有され、空き領域Btreeブロックは割り当てグループによって所有されます。したがって、オーナー情報のサイズや内容は、対象とするメタデータオブジェクトの種類によって決まります。オーナー情報はまた、不適切な宛先への書き込み（例：空き領域Btreeブロックが誤ったAGに書き込まれる）を特定するのに役立ちます。

自己記述メタデータにも、ファイルシステムに書き込まれた日時を示す情報が含まれる必要があります。フォレンジック分析において重要な情報の一つは、ブロックが最後に変更された時期です。破損したメタデータブロックのセットを変更日時に基づいて関連付けることは重要です。これにより、破損が関連しているか、複数の破損イベントが最終的な失敗を引き起こしたか、さらには実行時の検証で検出されていない破損が存在するかを推測できるからです。

たとえば、メタデータオブジェクトが所有者によってまだ参照されている場合、空き領域BTREEブロックが最後に書き込まれた日時とメタデータオブジェクト自体が最後に書き込まれた日時の比較により、そのオブジェクトが空き領域であるべきか、まだ割り当てられているかを判断できます。空き領域ブロックがオブジェクトおよびオブジェクトの所有者よりも新しい場合、ブロックが所有者から削除されるべきである可能性が高いです。

「書き込み時刻」を提供するため、各メタデータブロックには、そのブロックが最後に変更されたトランザクションのログシーケンス番号（LSN）が記録されます。この番号はファイルシステムの寿命を通じて常に増加し、ファイルシステムに対してxfs_repairを実行した場合のみリセットされます。さらに、LSNを用いることで、破損したメタデータがすべて同じログチェックポイントに属しているかを確認できます。これにより、最初の破損メタデータと最後の破損メタデータの間でどれだけ変更が行われたか、さらには破損が書き込まれた時点と検出された時点の間でどれだけ変更が行われたかを推測できます。

ランタイム検証¶

自己記述メタデータの検証は、実行時において2つの場所で行われます：

  • ディスクから成功した読み取りの直後

  • 書き込みIOのサブミッションの直前

検証は完全にステートレスです。変更プロセスとは独立して行われ、メタデータが自身が述べている内容と一致しているか、メタデータフィールドが範囲内であり内部的に整合しているかを確認するのみです。そのため、ブロック内でのすべての破損を検出することはできません。メタデータに運用状態が強制する制限がある場合や、ブロック間の関係（例：破損した兄弟ポインタリスト）が破損している場合があります。したがって、メインコード本体ではステートフルなチェックが必要ですが、一般的にフィールドごとの検証は verifier によって処理されます。

読み込み検証では、呼び出し元が確認したいメタデータの種類を指定する必要があります。IO完了プロセスがメタデータオブジェクトが予期していたものと一致しているかを検証します。検証が失敗した場合、読み込まれたオブジェクトにEFSCORRUPTEDを設定します。呼び出し元はこのエラーをキャッチする必要があります（IOエラーと同じ処理）。検証エラーにより特別な処置が必要な場合は、EFSCORRUPTEDエラー値をキャッチすることで対応できます。より上位レイヤーでエラー種別の区別が必要な場合は、必要に応じて新しいエラー番号を定義できます。

読み込み検証の最初のステップはマジックナンバーの確認とCRC検証が必要かどうかの判定です。必要とすればCRC32cを計算し、オブジェクト内に保存されている値と比較します。この検証が完了した後、位置情報の確認に進み、その後はオブジェクト固有のメタデータの検証を行います。これらの検証のいずれかが失敗した場合、バッファが破損しているとみなされ、EFSCORRUPTEDエラーが適切に設定されます。

書き込み検証は読み込み検証の逆のプロセスです。まずオブジェクトを詳細に検証し、問題なければオブジェクトに最後に変更されたLSNを更新します。その後、CRCを計算してオブジェクトに挿入します。この処理が完了した後、書き込みIOが続行されます。このプロセス中にエラーが発生した場合、バッファに再びEFSCORRUPTEDエラーが設定され、上位レイヤーでキャッチされます。

構造体¶

典型的なディスク上の構造には以下の情報が含まれる必要があります：

struct xfs_ondisk_hdr {
        __be32  magic;              /* magic number */
        __be32  crc;                /* CRC, not logged */
        uuid_t  uuid;               /* filesystem identifier */
        __be64  owner;              /* parent object */
        __be64  blkno;              /* location on disk */
        __be64  lsn;                /* last modification in log, not logged */
};

メタデータによっては、この情報がメタデータコンテンツとは分離したヘッダ構造に含まれる場合もあります。後者の場合、すでに一部の情報を含んでいるメタデータ（スーパーブロックやAGヘッダなど）が存在するため、情報が既存の構造に分散されます。

他のメタデータは情報のフォーマットが異なりますが、一般的に同じレベルの情報が提供されます。例えば：

  • 短いbtreeブロックは32ビットの所有者（ag番号）と32ビットのブロック番号を持つことで位置情報を示します。これら2つの組み合わせは、上記構造の@ownerと@blknoと同じ情報を提供しますが、ディスク上では8バイトのスペースを節約しています。

  • ディレクトリ/属性ノードブロックは16ビットのマジックナンバーを持ち、マジックナンバーを含むヘッダにはその他の情報も含まれています。したがって、追加のメタデータヘッダーによりメタデータ全体のフォーマットが変化します。

典型的なバッファ読み込み検証器は以下のように構成されています：

#define XFS_FOO_CRC_OFF             offsetof(struct xfs_ondisk_hdr, crc)

static void
xfs_foo_read_verify(
        struct xfs_buf      *bp)
{
    struct xfs_mount *mp = bp->b_mount;

        if ((xfs_sb_version_hascrc(&mp->m_sb) &&
            !xfs_verify_cksum(bp->b_addr, BBTOB(bp->b_length),
                                        XFS_FOO_CRC_OFF)) ||
            !xfs_foo_verify(bp)) {
                XFS_CORRUPTION_ERROR(__func__, XFS_ERRLEVEL_LOW, mp, bp->b_addr);
                xfs_buf_ioerror(bp, EFSCORRUPTED);
        }
}

このコードは、ファイルシステムがCRCを有効にしているかどうかをsuperblockの機能ビットで確認し、CRCが正常（または不要）である場合、ブロックの実際の内容を検証します。

検証関数は、マジックナンバーがブロックの形式を特定できるかどうかによって複数の形式を取ります。マジックナンバーで形式を特定できない場合、コードは以下のようになります：

static bool
xfs_foo_verify(
        struct xfs_buf              *bp)
{
        struct xfs_mount    *mp = bp->b_mount;
        struct xfs_ondisk_hdr       *hdr = bp->b_addr;

        if (hdr->magic != cpu_to_be32(XFS_FOO_MAGIC))
                return false;

        if (!xfs_sb_version_hascrc(&mp->m_sb)) {
                if (!uuid_equal(&hdr->uuid, &mp->m_sb.sb_uuid))
                        return false;
                if (bp->b_bn != be64_to_cpu(hdr->blkno))
                        return false;
                if (hdr->owner == 0)
                        return false;
        }

        /* object specific verification checks here */

        return true;
}

異なる形式ごとに異なるマジックナンバーがある場合、検証関数は以下のようになります：

static bool
xfs_foo_verify(
        struct xfs_buf              *bp)
{
        struct xfs_mount    *mp = bp->b_mount;
        struct xfs_ondisk_hdr       *hdr = bp->b_addr;

        if (hdr->magic == cpu_to_be32(XFS_FOO_CRC_MAGIC)) {
                if (!uuid_equal(&hdr->uuid, &mp->m_sb.sb_uuid))
                        return false;
                if (bp->b_bn != be64_to_cpu(hdr->blkno))
                        return false;
                if (hdr->owner == 0)
                        return false;
        } else if (hdr->magic != cpu_to_be32(XFS_FOO_MAGIC))
                return false;

        /* object specific verification checks here */

        return true;
}

書き込み検証関数は読み込み検証関数と非常に似ています。ただ処理順序が読み込み検証関数とは逆の順序で行われます。典型的な書き込み検証関数は以下の通りです：

static void
xfs_foo_write_verify(
        struct xfs_buf      *bp)
{
        struct xfs_mount    *mp = bp->b_mount;
        struct xfs_buf_log_item     *bip = bp->b_fspriv;

        if (!xfs_foo_verify(bp)) {
                XFS_CORRUPTION_ERROR(__func__, XFS_ERRLEVEL_LOW, mp, bp->b_addr);
                xfs_buf_ioerror(bp, EFSCORRUPTED);
                return;
        }

        if (!xfs_sb_version_hascrc(&mp->m_sb))
                return;


        if (bip) {
                struct xfs_ondisk_hdr       *hdr = bp->b_addr;
                hdr->lsn = cpu_to_be64(bip->bli_item.li_lsn);
        }
        xfs_update_cksum(bp->b_addr, BBTOB(bp->b_length), XFS_FOO_CRC_OFF);
}

この処理では、メタデータの内部構造をさらに進む前に検証し、メモリ内でメタデータが変更された際に発生した破損を検出します。メタデータの検証が正常で、CRCが有効な場合、LSNフィールド（最後に変更された時間）を更新し、メタデータのCRCを計算します。この処理が完了した後、IOを実行できます。

インノデとDクォット¶

インODEとdquotは特別な存在です。これらはオブジェクトごとにCRCと自己識別子を持ちますが、バッファに複数のオブジェクトが詰め込まれているため、バッファ単位での検証やCRC計算を行いません。バッファ単位の検証関数は、バッファがインODEまたはdquotを含んでいること、そして予期される場所にマジックナンバーがあることを基本的な識別を行います。すべてのCRCおよび検証チェックは、各インODEがバッファから読み出されるか、バッファに書き戻される際に実行されます。

検証関数の構造と識別チェックは、上記のバッファコードと非常に似ています。違いは呼び出す場所にあります。例えば、インODE読み込み検証は、インODEがバッファから最初に読み出される際のxfs_inode_from_disk()関数で行われます。インODEはxfs_iflush_intでの書き戻し時にすでに詳細に検証されているため、ここではインODEにLSNとCRCを追加するだけです。

XXX: インODE切断リストの変更ではインODEのCRCを再計算していません！切断リストの変更処理ではCRCのチェックや更新が行われていません。これはアンリンク時やログ回復時にも行われていません。そのためこれまで気づかなかったのです。これは直ちに問題にはなりませんが、修復ツールが警告を出す可能性がありますので、修正が必要です。

はじめに¶

仮想ファイルシステム（仮想ファイルシステムスイッチとも呼ばれる）は、カーネル内のソフトウェア層で、ユーザー空間のプログラムにファイルシステムインターフェースを提供します。また、カーネル内で異なるファイルシステム実装が共存できるようにする抽象化も提供します。

VFSシステムコール（open(2)、stat(2)、read(2)、write(2)、chmod(2)など）はプロセスコンテキストから呼び出されます。ファイルシステムのロックについては、ドキュメントで説明しています。 ロック.

ディレクトリエントリーキャッシュ（dcache）¶

VFSはopen(2)、stat(2)、chmod(2)などのシステムコールを実装します。これらに渡されるパス名引数は、VFSがディレクトリエントリキャッシュ（dentryキャッシュまたはdcacheとも呼ばれる）を検索するために使用されます。これにより、パス名（ファイル名）を特定のdentryに高速に変換するメカニズムが提供されます。dentriesはRAMに存在し、ディスクには保存されません。これらはパフォーマンス向上のためだけに存在します。

dentryキャッシュは、あなたのすべてのファイルスペースを表示するためのものです。ほとんどのコンピュータでは、すべてのdentriesを一度にRAMに収めることが出来ないため、キャッシュの一部が欠落しています。パス名をdentryに解決するには、VFSはパスの途中でdentriesを作成し、その後inodeをロードする必要があるかもしれません。これはinodeを検索することで行われます。

インノデオブジェクト¶

個々のdentryは通常、inodeへのポインタを持っています。inodeは、通常のファイル、ディレクトリ、FIFO、その他のオブジェクトなどのファイルシステムオブジェクトです。これらは、ブロックデバイスファイルシステムの場合にはディスクに、擬似ファイルシステムの場合にはメモリに存在します。ディスクに存在するinodeは必要に応じてメモリにコピーされ、inodeの変更はディスクに戻されます。1つのinodeは複数のdentryによって参照されることがあります（ハードリンクなど）。

inodeを検索するには、VFSが親ディレクトリinodeのlookup()メソッドを呼び出す必要があります。このメソッドは、inodeが存在する特定のファイルシステム実装によってインストールされます。VFSが必要なdentry（そしてinode）を取得した後、ファイルを開く（open(2)）やinodeデータを確認する（stat(2)）などの作業が可能になります。stat(2)操作は比較的簡単です：VFSがdentryを取得した後、inodeデータを確認し、一部をユーザー空間に返します。

ファイルオブジェクト¶

ファイルを開くには、別の操作が必要です: ファイル構造体の割当（これはファイル記述子のカーネル側の実装です）。新たに割当されたファイル構造体は、dentryへのポインタと、ファイル操作メンバ関数のセットで初期化されます。これらはinodeデータから取得されます。その後、open()ファイルメソッドが呼び出され、特定のファイルシステム実装が作業を開始します。このようにして、VFSが行うもう一つのスイッチがわかります。ファイル構造体は、プロセスのファイル記述子テーブルに配置されます。

読み込み、書き込み、ファイルの閉じる（およびその他の assorted VFS 操作）は、ユーザースペースのファイル記述子を使用して適切なファイル構造体を取得し、必要なファイル構造体メソッドを呼び出すことで実行されます。ファイルが開いている限り、dentryは使用中であり、これによりVFS inodeも依然として使用中です。

ファイルシステムの登録とマウント¶

ファイルシステムを登録および解除するには、次のAPI関数を使用してください:

#include <linux/fs.h>

extern int register_filesystem(struct file_system_type *);
extern int unregister_filesystem(struct file_system_type *);

渡される struct file_system_type はあなたのファイルシステムを記述します。あなたの名前空間内のディレクトリにファイルシステムをマウントするリクエストが行われた場合、VFSは特定のファイルシステムの mount() メソッドを呼び出します。new vfsmount は ->mount() で返されたツリーを参照し、マウントポイントに接続されます。これにより、パスネーム解決がマウントポイントに到達したときに、その vfsmount のルートにジャンプします。

カーネルに登録されているすべてのファイルシステムは、/proc/filesystems ファイルで確認できます。

struct file_system_type¶

これはファイルシステムを記述します。カーネル2.6.39以降、次のメンバが定義されています:

struct file_system_operations {
        const char *name;
        int fs_flags;
        struct dentry *(*mount) (struct file_system_type *, int,
                                 const char *, void *);
        void (*kill_sb) (struct super_block *);
        struct module *owner;
        struct file_system_type * next;
        struct list_head fs_supers;
        struct lock_class_key s_lock_key;
        struct lock_class_key s_umount_key;
};
name

ファイルシステムタイプの名前、例えば「ext2」、「iso9660」、「msdos」など

fs_flags

さまざまなフラグ（例: FS_REQUIRES_DEV、FS_NO_DCACHE など）

mount

このファイルシステムの新しいインスタンスをマウントする際呼び出すメソッド

kill_sb

このファイルシステムのインスタンスをシャットダウンする際呼び出すメソッド

owner

内部でVFSが使用する: ほとんどの場合、THIS_MODULE に初期化してください。

next

内部でVFSが使用する: ほとんどの場合、NULL に初期化してください。

s_lock_key、s_umount_key: lockdep 特有のもの

mount() メソッドは次の引数を持ちます:

struct file_system_type *fs_type

ファイルシステムを部分的に初期化した特定のファイルシステムコードによって記述されるファイルシステム

int flags

マウントフラグ

const char *dev_name

マウントするデバイス名。

void *data

任意のマウントオプション、通常はASCII文字列として渡されます（「マウントオプション」セクションを参照）

mount() メソッドは、呼び出し元が要求したツリーのルートdentryを返さなければなりません。アクティブな参照を取得し、superblockをロックしなければなりません。失敗した場合はERR_PTR(error)を返してください。

引数はmount(2)と同じであり、その解釈はファイルシステムの種類に依存します。例えば、ブロックファイルシステムの場合、dev_nameはブロックデバイス名として解釈され、そのデバイスが開かれ、適切なファイルシステムイメージを含む場合、メソッドはstruct super_blockを生成・初期化し、そのルートdentryを呼び出し元に返します。

->mount()は既存のファイルシステムのサブツリーを返すことも選択可能です。新しいものを生成する必要はありません。呼び出し元にとっての主な結果は、(サブ)ツリーのルートにあるdentryへの参照です。新しいsuperblockの生成は一般的な副作用です。

mount()メソッドが埋め込むsuperblock構造体で最も重要なメンバは「s_op」フィールドです。これは「struct super_operations」へのポインタで、ファイルシステム実装の次のレベルを記述します。

通常、ファイルシステムは一般的なmount()実装のいずれかを使用し、fill_super()コールバックを提供します。一般的な変体は以下の通りです。

mount_bdev

ブロックデバイス上に存在するファイルシステムをマウントする

mount_nodev

デバイスでサポートされていないファイルシステムをマウントする

mount_single

すべてのマウントで共有されるインスタンスを持つファイルシステムをマウントする

fill_super()コールバック実装は以下の引数を持ちます。

struct super_block *sb

superblock構造体。コールバックはこれを適切に初期化する必要があります。

void *data

任意のマウントオプション、通常はASCII文字列として渡されます（「マウントオプション」セクションを参照）

int silent

エラー時に静かに動作するかどうか

スーパーブロックオブジェクト¶

superblockオブジェクトはマウントされたファイルシステムを表します。

struct super_operations¶

これはVFSが貴社のファイルシステムのsuperblockを操作する方法を記述します。カーネル2.6.22以降では以下のメンバが定義されています。

struct super_operations {
        struct inode *(*alloc_inode)(struct super_block *sb);
        void (*destroy_inode)(struct inode *);

        void (*dirty_inode) (struct inode *, int flags);
        int (*write_inode) (struct inode *, int);
        void (*drop_inode) (struct inode *);
        void (*delete_inode) (struct inode *);
        void (*put_super) (struct super_block *);
        int (*sync_fs)(struct super_block *sb, int wait);
        int (*freeze_fs) (struct super_block *);
        int (*unfreeze_fs) (struct super_block *);
        int (*statfs) (struct dentry *, struct kstatfs *);
        int (*remount_fs) (struct super_block *, int *, char *);
        void (*clear_inode) (struct inode *);
        void (*umount_begin) (struct super_block *);

        int (*show_options)(struct seq_file *, struct dentry *);

        ssize_t (*quota_read)(struct super_block *, int, char *, size_t, loff_t);
        ssize_t (*quota_write)(struct super_block *, int, const char *, size_t, loff_t);
        int (*nr_cached_objects)(struct super_block *);
        void (*free_cached_objects)(struct super_block *, int);
};

すべてのメソッドはロックを保持せずに呼び出されます（例外は明記されている場合を除く）。これにより、ほとんどのメソッドはブロック処理を安全に実行できます。すべてのメソッドはプロセスコンテキストからのみ呼び出されます（割込みハンドラやボトムハーフからの呼び出しは含まれません）。

alloc_inode

alloc_inode()がこのメソッドを呼び出して、struct inodeのメモリを確保し、初期化します。この関数が定義されていない場合、単純な「struct inode」が割り当てられます。通常、alloc_inodeはより大きな構造体を割り当てて、その中にstruct inodeが埋め込まれます。

destroy_inode

destroy_inode()がこのメソッドを呼び出して、struct inodeに割り当てられたリソースを解放します。->alloc_inodeが定義されている場合にのみ必要で、->alloc_inodeで行った処理を逆転します。

dirty_inode

VFSがinodeを汚染（dirty）とみなすときにこのメソッドが呼び出されます。

write_inode

VFSがinodeをディスクに書き込む必要があるときに呼び出されます。第2パラメータは書き込みが同期的かどうかを示します。すべてのファイルシステムがこのフラグをチェックするわけではありません。

drop_inode

inodeへの最後のアクセスが解除されるときに呼び出されます。このとき、inode->i_lockスピンロックが保持されています。

このメソッドはNULL（通常のUNIXファイルシステム semantics）か、「generic_delete_inode」（inodeをキャッシュしたくないファイルシステムで、i_nlinkの値に関係なく「delete_inode」が常に呼び出される）のいずれかにする必要があります。

「generic_delete_inode()」の挙動は、かつてput_inode()のケースで「force_delete」を使用する古い慣習と同等ですが、「force_delete()」アプローチには存在した競合状態（races）は持ちません。

delete_inode

VFSがinodeを削除したいときに呼び出されます。

put_super

VFSがsuperblockを解放したい（つまりアンマウント）ときに呼び出されます。このときsuperblockロックが保持されています。

sync_fs

VFSがsuperblockに関連するすべての汚染データを書き出すときに呼び出されます。第二パラメータは、このメソッドが書き出し完了まで待機するかどうかを示します。オプションです。

freeze_fs

VFSがファイルシステムをロックし、一貫性のある状態に強制するときに呼び出されます。このメソッドは現在、論理ボリュームマネージャー（LVM）によって使用されています。

unfreeze_fs

VFSがファイルシステムをアンロックし、再度書き込み可能にするときに呼び出されます。

statfs

VFSがファイルシステムの統計情報を取得するときに呼び出されます。

remount_fs

ファイルシステムが再マウントされるときに呼び出されます。このときカーネルロックが保持されています。

clear_inode

VFSがinodeをクリアするときに呼び出されます。オプションです。

umount_begin

VFSがファイルシステムをアンマウントするときに呼び出されます。

show_options

VFSが/proc/<pid>/mountsにマウントオプションを表示するときに呼び出されます。（「Mount Options」セクションを参照）

quota_read

VFSがファイルシステムのクォータファイルから読み込むときに呼び出されます。

quota_write

VFSがファイルシステムのクォータファイルに書き込むときに呼び出されます。

nr_cached_objects

ファイルシステムがsbキャッシュの縮小処理を行う際、そのキャッシュに含まれる解放可能なオブジェクトの数を返すために呼び出されます。オプションです。

free_cache_objects

sbキャッシュの縮小処理を行う際、指定された数のオブジェクトをスキャンして解放するため、ファイルシステムが呼び出されます。オプションですが、このメソッドを実装するファイルシステムは同時に->nr_cached_objectsも実装する必要があります。

ファイルシステムが遭遇したエラーに対して何の処理も行えないため、void型の戻り値が採用されています。VMがGFP_NOFS条件でメモリを回収しようとしている場合はこのメソッドが呼ばれないため、このメソッドはその状況を自身で処理する必要がありません。

スキャンループ内で条件付きの再スケジュール呼び出しを必ず実装する必要があります。これにより、VFSはスキャンバッチサイズを適切に決定できるようになり、実装が大規模なスキャンバッチサイズによって制約される問題を気にすることなくなります。

inodeを設定する責任者は、「i_op」フィールドを埋め込む必要があります。これは、「struct inode_operations」へのポインタであり、個々のinodeに対して実行可能なメソッドを記述しています。

struct xattr_handlers¶

拡張属性(xattrs)をサポートするファイルシステムでは、s_xattrスーパーブロックフィールドはNULL終端のxattrハンドラ配列を指します。拡張属性は名前:値のペアです。

name

ハンドラが指定された名前（例：「system.posix_acl_access」）を持つ属性に一致することを示します。この場合、prefixフィールドはNULLでなければなりません。

prefix

ハンドラが指定された名前プレフィックス（例：「user.」）を持つすべての属性に一致することを示します。この場合、nameフィールドはNULLでなければなりません。

list

特定のdentryに対して、このxattrハンドラに一致する属性がリストされるべきかどうかを決定します。generic_listxattrなどのリストxattr実装で使用されます。

get

VFSが特定の拡張属性の値を取得するときに呼び出されます。このメソッドはgetxattr(2)システムコールによって呼び出されます。

set

VFSが特定の拡張属性の値を設定するときに呼び出されます。新しい値がNULLの場合、特定の拡張属性を削除するための呼び出しになります。このメソッドはsetxattr(2)およびremovexattr(2)システムコールによって呼び出されます。

ファイルシステムのxattrハンドラが指定された属性名に一致しない場合、またはファイルシステムが拡張属性をサポートしない場合、さまざまな *xattr(2) システムコールは-EOPNOTSUPPを返します。

インノデオブジェクト¶

inodeオブジェクトはファイルシステム内のオブジェクトを表します。

struct inode_operations¶

これは、VFSが貴社のファイルシステム内のinodeを操作する方法を記述しています。カーネル2.6.22以降では、次のメンバが定義されています：

struct inode_operations {
        int (*create) (struct inode *,struct dentry *, umode_t, bool);
        struct dentry * (*lookup) (struct inode *,struct dentry *, unsigned int);
        int (*link) (struct dentry *,struct inode *,struct dentry *);
        int (*unlink) (struct inode *,struct dentry *);
        int (*symlink) (struct inode *,struct dentry *,const char *);
        int (*mkdir) (struct inode *,struct dentry *,umode_t);
        int (*rmdir) (struct inode *,struct dentry *);
        int (*mknod) (struct inode *,struct dentry *,umode_t,dev_t);
        int (*rename) (struct inode *, struct dentry *,
                       struct inode *, struct dentry *, unsigned int);
        int (*readlink) (struct dentry *, char __user *,int);
        const char *(*get_link) (struct dentry *, struct inode *,
                                 struct delayed_call *);
        int (*permission) (struct inode *, int);
        int (*get_acl)(struct inode *, int);
        int (*setattr) (struct dentry *, struct iattr *);
        int (*getattr) (const struct path *, struct kstat *, u32, unsigned int);
        ssize_t (*listxattr) (struct dentry *, char *, size_t);
        void (*update_time)(struct inode *, struct timespec *, int);
        int (*atomic_open)(struct inode *, struct dentry *, struct file *,
                           unsigned open_flag, umode_t create_mode);
        int (*tmpfile) (struct inode *, struct dentry *, umode_t);
};

また、すべてのメソッドはロックを保持せずに呼び出されます（特に記載がない限り）。

create

open(2)およびcreat(2)システムコールによって呼び出されます。通常ファイルをサポートしたい場合にのみ必要です。取得するdentryはinodeを持っていない必要があります（つまり、負のdentryです）。ここでおそらく呼び出すのは d_instantiate() dentryと新たに作成されたinode

lookup

VFSが親ディレクトリ内のinodeを検索する必要があるときに呼び出されます。検索する名前はdentryに含まれています。このメソッドは必ず d_add() 見つかった inode を dentry に挿入する必要があります。inode 構造体の「i_count」フィールドはインクリメントする必要があります。指定された inode が存在しない場合、NULL inode を dentry に挿入する必要があります（これは「負の dentry」と呼ばれます）。この関数からエラーコードを返すのは、実際のエラーが発生した場合に限ります。それ以外の場合、create(2)、mknod(2)、mkdir(2) などのシステムコールで inode を作成すると失敗します。dentry メソッドをオーバーライドしたい場合は、dentry の「d_dop」フィールドを初期化する必要があります。これは struct 「dentry_operations」へのポインタであり、このメソッドはディレクトリ inode セマフォを保持しながら呼ばれます

link

link(2) システムコールによって呼ばれます。ハードリンクをサポートしたい場合にのみ必要です。おそらく以下を呼び出す必要があります d_instantiate() create() メソッドで行うのと同じように呼び出します

unlink

unlink(2) システムコールによって呼ばれます。inode の削除をサポートしたい場合にのみ必要です

symlink

symlink(2) システムコールによって呼ばれます。シンボリックリンクをサポートしたい場合にのみ必要です。おそらく以下を呼び出す必要があります d_instantiate() create() メソッドで行うのと同じように呼び出します

mkdir

mkdir(2) システムコールによって呼ばれます。サブディレクトリの作成をサポートしたい場合にのみ必要です。おそらく以下を呼び出す必要があります d_instantiate() create() メソッドで行うのと同じように呼び出します

rmdir

rmdir(2) システムコールによって呼ばれます。サブディレクトリの削除をサポートしたい場合にのみ必要です

mknod

mknod(2) システムコールによって呼ばれます。キャラクタデバイス、ブロックデバイスの inode または名前付きパイプ（FIFO）やソケットを作成します。これらの inode の作成をサポートしたい場合にのみ必要です。おそらく以下を呼び出す必要があります d_instantiate() create() メソッドで行うのと同じように呼び出します

rename

rename(2) システムコールによって呼ばれます。対象オブジェクトを、第二引数の inode と dentry で指定された親ディレクトリと名前を持つものにリネームします

ファイルシステムは、サポートされていないまたは未知のフラグに対して -EINVAL を返す必要があります。現在実装されているフラグは以下の通りです：(1) RENAME_NOREPLACE: このフラグは、リネーム対象が存在する場合、-EEXIST で失敗するように指示します（上書きは行いません）。VFS がすでに存在確認を行っているため、ローカルファイルシステムでは RENAME_NOREPLACE の実装は通常のリネームと同等です。(2) RENAME_EXCHANGE: ソースとターゲットを交換します。どちらも存在する必要があります（これは VFS が確認します）。通常のリネームとは異なり、ソースとターゲットの種類が異なる場合でも可能です

get_link

VFSがシンボリックリンクをinodeに指す先にフォローランする際に呼び出されます。シンボリックリンクをサポートしたい場合のみ必要です。このメソッドはトラバースするシンボリックリンクの本体を返し（必要に応じてnd_jump_link()で現在のポジションをリセットします）、inodeが消去されるまで本体が消えなくなる場合は何も他に必要ありません。それ以外の状況で本体を固定する必要がある場合は、get_link(…, …, done)でset_delayed_call(done, destructor, argument)を呼び出して解放を手配してください。その場合、VFSが返した本体を処理終了後にdestructor(argument)が呼び出されます。RCUモードで呼び出される可能性があります（NULLのdentry引数で示されます）。RCUモードを離れる必要がない場合に処理できない場合は、ERR_PTR(-ECHILD)を返してください。

ファイルシステムが->i_linkにシンボリックリンクのターゲットを保存している場合、VFSは->get_link()を呼び出さずに直接使用できます。ただし->get_link()は依然として提供する必要があります。->i_linkはRCUのgrace periodが終わるまで解放してはなりません。iget()以降に->i_linkに書き込むには'release'メモリバリアが必要です。

readlink

これは現在、readlink(2)が->get_linkを使用する場合やオブジェクトが実際にはシンボリックリンクでない場合にのみオーバーライドとして使用されます。通常はファイルシステムはシンボリックリンクに対してのみ->get_linkを実装すべきで、readlink(2)は自動的にそれを利用します。

permission

POSIXに類似したファイルシステムにおけるアクセス権の確認のためにVFSによって呼び出されます。

rcu-walkモード（mask & MAY_NOT_BLOCK）で呼び出される可能性があります。rcu-walkモードの場合、ファイルシステムはブロッキングせずにinodeに書き込まずに権限を確認しなければなりません。

rcu-walkが処理できない状況に遭遇した場合、-ECHILDを返して再度ref-walkモードで呼び出されます。

setattr

ファイルの属性を設定するためにVFSによって呼び出されます。これはchmod(2)や関連するシステムコールによって呼び出されます。

getattr

ファイルの属性を取得するためにVFSによって呼び出されます。これはstat(3)や関連するシステムコールによって呼び出されます。

listxattr

指定されたファイルのすべての拡張属性を一覧表示するためにVFSによって呼び出されます。これはlistxattr(2)システムコールによって呼び出されます。

update_time

inodeの特定の時間やi_versionを更新するためにVFSによって呼び出されます。このメソッドが定義されていない場合、VFSがinode自体を更新し、mark_inode_dirty_sync()を呼び出します。

atomic_open

オープン中の最後のコンポーネントに対して呼び出されます。このオプションメソッドを使用することで、ファイルシステムは1回のアトミック操作でファイルを検索、作成およびオープンすることが可能です。呼び出し元に実際にオープンを委譲する必要がある場合（例: ファイルがシンボリックリンク、デバイス、またはファイルシステムがアトミックオープンをサポートしない場合）、finish_no_open(file, dentry)を返してこの動作を示します。このメソッドは、最後のコンポーネントが負のエントリ（negative dentry）または検索が必要な場合にのみ呼び出されます。キャッシュされたポジティブなdentryは依然としてf_op->open()で処理されます。ファイルが作成された場合、file->f_modeにFMODE_CREATEDフラグを設定する必要があります。O_EXCLの場合、メソッドはファイルが存在しなかった場合にのみ成功するため、成功時にFMODE_CREATEDフラグは常に設定されるべきです。

tmpfile

O_TMPFILEオープンの終わりに呼び出されます。オプションで、指定されたディレクトリにファイルをアトミックに作成、オープンし、アンリンクする操作に相当します。

アドレススペースオブジェクト¶

アドレス空間オブジェクトは、ページキャッシュ内のページをグループ化・管理するために使用されます。ファイル（または他の任意のオブジェクト）内のページを追跡し、ファイルのセクションをプロセスアドレス空間にマッピングする追跡も行うことができます。

アドレス空間は、メモリ圧力を通信する、アドレスによるページ検索、DirtyまたはWritebackとしてタグ付けされたページの追跡など、いくつかの関連するサービスを提供します。

最初のサービスは他のものとは独立して使用可能です。VMは、汚染されたページをクリーンにすることで削除するか、クリーンなページを再利用するために解放するかを選択できます。これを行うには、汚染されたページに対して->writepageメソッドを呼び出し、クリーンなページに対してPagePrivateが設定された状態で->releasepageメソッドを呼び出します。外部参照がなくPagePrivateも設定されていないクリーンなページは、アドレス空間に通知することなく解放されます。

この機能を実現するには、ページをlru_cache_addでLRUリストに配置し、ページが使用されるたびにmark_page_activeを呼び出す必要があります。

通常、ページは->indexで管理されるradix treeインデックスに保持されます。この木は各ページのPG_DirtyおよびPG_Writebackステータス情報を保持し、これらのフラグを持つページを迅速に検索できるようにします。

Dirtyタグは主にmpage_writepages（デフォルトの->writepagesメソッド）で使用されます。このメソッドはタグを使用して汚染されたページを検索し、->writepageを呼び出します。mpage_writepagesが使用されない場合（つまりアドレス空間が独自の->writepagesを提供する場合）、PAGECACHE_TAG_DIRTYタグはほぼ使用されません。write_inode_nowおよびsync_inodeは__sync_single_inodeを通じてこのタグを使用して、->writepagesがアドレス空間全体を正しく書き出しているかを確認します。

Writebackタグは、filemap_fdatawait_rangeを通じてfilemap*wait*およびsync_page*関数が使用され、すべてのWritebackが完了するのを待機するために使用されます。

アドレススペースハンドラは、通常struct page内の'private'フィールドを使用して、ページに追加情報をアタッチすることがあります。このような情報がアタッチされている場合、PG_Privateフラグを設定する必要があります。これにより、さまざまなVMルーチンがアドレススペースハンドラに対して追加の呼び出しを行います。

アドレススペースは、ストレージとアプリケーションの間のインターフェースとして機能します。データはアドレススペースに1ページずつ読み込まれ、アプリケーションにページのコピーによって提供されるか、メモリマッピングによって提供されます。データはアプリケーションからアドレススペースに書き込まれ、その後通常は1ページずつストレージに書き戻されます。ただし、アドレススペースは書き込みサイズに対してより細かい制御を行います。

読み込みプロセスは基本的に'readpage'のみが必要ですが、書き込みプロセスは複雑で、write_begin/write_endまたはset_page_dirtyを使用してデータをアドレススペースに書き込み、writepageおよびwritepagesを使用してストレージにデータを書き戻します。

アドレススペースにページを追加または削除する際は、inodeのi_mutexによって保護されます。

ページにデータが書き込まれた場合、PG_Dirtyフラグを設定する必要があります。通常、このフラグはwritepageが書き込みを要求するまで保持されます。このフラグはPG_Dirtyがクリアされた後で実際に書き込まれることができます。安全であることが確認された後、PG_Writebackはクリアされます。

Writebackはwriteback_control構造体を使用して操作を制御します。これにより、writepageおよびwritepages操作に、Writebackリクエストの性質や理由、および実行される制約に関する情報が提供され、またwritepageまたはwritepagesリクエストの結果に関する情報を呼び出し元に返します。

Writeback時のエラー処理¶

バッファードI/Oを行うアプリケーションは、データがバックストレージに確実に書き込まれたことを確認するために、定期的にファイル同期呼び出し（fsync、fdatasync、msyncまたはsync_file_range）を行います。Writeback中にエラーが発生した場合、アプリケーションはファイル同期リクエストが行われた際にそのエラーが報告されることを期待します。1つのリクエストでエラーが報告された後、同じファイルディスクリプタに対する次のリクエストは0を返す必要があります（ただし、前の同期後から新たなWritebackエラーが発生した場合を除く）

理想的には、カーネルは書き込みが失敗したファイル記述子のみにエラーを報告すべきです。ただし、一般的なpagecacheインフラストラクチャは、各ページが汚染されたファイル記述子を追跡していませんため、どのファイル記述子にエラーを戻すかを特定することはできません。

代わりに、カーネル内の一般的なwritebackエラー追跡インフラストラクチャは、エラーが発生した時点でのすべてのオープン中のファイル記述子に対してfsyncにエラーを報告します。複数のライタが存在する状況では、すべてのライタがその後のfsyncでエラーを受けることになります。たとえ特定のファイル記述子を通じて行われたすべての書き込みが成功した（あるいはそのファイル記述子にまったく書き込みが行われなかった）場合でもです。

このインフラストラクチャを使用したいファイルシステムは、エラーが発生した際にmapping_set_errorを呼び出してaddress_spaceにエラーを記録する必要があります。その後、pagecacheからデータを戻し処理した後、file->fsync操作でfile_check_and_advance_wb_errを呼び出して、struct fileのエラーカーソルがバックドライブ（s）から発行されたエラー列の正しい位置に進んでいることを確認する必要があります。

struct address_space_operations¶

これは、VFSがファイルをpagecacheにマッピングする方法をどのように操作するかを説明しています。以下に定義されたメンバがあります：

        int (*readpage)(struct file *, struct page *);
        int (*writepages)(struct address_space *, struct writeback_control *);
        int (*set_page_dirty)(struct page *page);
        void (*readahead)(struct readahead_control *);
        int (*readpages)(struct file *filp, struct address_space *mapping,
                         struct list_head *pages, unsigned nr_pages);

writepage

VMが汚染ページをバックストレージに書き出すために呼び出されます。これはデータの整合性のため（つまり「sync」）やメモリを解放するため（flush）のいずれかの理由で発生します。違いはwbc->sync_modeで確認できます。PG_Dirtyフラグはクリアされ、PageLockedはtrueです。writepageは書き出しを開始し、PG_Writebackを設定し、書き込み操作が完了時に同期的にもしくは非同期的にページをアンロックする必要があります。

wbc->sync_modeがWB_SYNC_NONEの場合、->writepageは問題が発生した際にあまり頑張らなくてもよいです。他のページをマッピングから書き出すのがより簡単な場合（内部依存関係など）に、その処理を選択的に実行できます。writeoutを開始しない場合、AOP_WRITEPAGE_ACTIVATEを返す必要があります。これにより、VMがそのページに対して->writepageを繰り返し呼び出すのを防ぎます。

詳細についてはファイル「Locking」を参照してください。

readpage

VMがバックストアからページを読み込むために呼び出されます。readpageが呼び出されるとページがロックされ、読み込みが完了した後はアンロックされ uptodate とマークされる必要があります。->readpageが何らかの理由でページをアンロックする必要があると判断した場合、その処理を行ってAOP_TRUNCATED_PAGEを返すことができます。この場合、ページが再配置され再ロックされ、すべて成功した場合、->readpageが再度呼び出されます。

writepages

VMがaddress_spaceオブジェクトに関連するページを書き出すために呼び出されます。wbc->sync_modeがWB_SYNC_ALLの場合、writeback_controlは書き出すべきページ範囲を指定します。WB_SYNC_NONEの場合、nr_to_writeが指定され、その数のページを可能な限り書き出す必要があります。->writepagesが指定されていない場合はmpage_writepagesが代わりに使用されます。この処理はaddress_spaceにDIRTYとしてタグ付けされたページを選択し、->writepageに渡します。

set_page_dirty

VMがページを汚染（dirty）状態にするために呼び出されます。address_spaceがページにプライベートデータをアタッチしている場合など、ページが汚染されたときにそのデータを更新する必要がある場合は特に重要です。例えばメモリマップされたページが変更されたときに呼び出されます。定義されている場合はPageDirtyフラグを設定し、radix treeのPAGECACHE_TAG_DIRTYタグも設定する必要があります。

readahead

VMがaddress_spaceオブジェクトに関連するページを読み込むために呼び出されます。ページはページキャッシュ内で連続しており、ロックされています。実装では各ページのI/Oを開始した後にページのrefcountを減算する必要があります。通常、I/O完了ハンドラがページをアンロックします。ファイルシステムが読み取り先のウィンドウの終わりに到達する前にI/Oを停止する場合、単に返すだけでよいです。呼び出し元が残りのページのrefcountを減算し、アンロックを行います。I/Oが成功した場合はPageUptodateを設定してください。どのページにもPageErrorを設定しても無視されます。I/Oエラーが発生した場合はページをアンロックしてください。

readpages

VMがaddress_spaceオブジェクトに関連するページを読み込むために呼び出されます。これはreadpageのベクター版であり、複数のページを一度に要求します。readpagesは読み取り先読み専用で使用されるため、読み取りエラーは無視されます。何か問題が起きた場合はすぐに処理を中断しても構いません。このインターフェースは非推奨となっており、2020年末までに削除されます。readaheadを実装してください。

write_begin

一般的なバッファード・ライトコードによって呼び出され、ファイル内の指定されたオフセット位置にlenバイトを書く準備をファイルシステムに依頼します。address_spaceは、必要に応じて領域を確保し、その他の内部処理を行うことで、このライトが完了できるよう確認する必要があります。ストレージ上の基本ブロックを更新する場合、それらのブロックがすでに読み込まれていない場合は事前に読み込む必要があります（更新されたブロックを適切に書き出すため）。

指定されたオフセット位置のロックされたpagecacheページを返す必要があります。 *pagep呼び出し元が書き込むために

短い書き込み（write_beginに渡された長さが、ページにコピーされたバイト数より大きい場合）に対応できる必要があります。

flagsは、include/linux/fs.hで説明されているAOP_FLAG_xxxフラグのフィールドです。

fsdataにはvoid *が返され、その後write_endに渡されます。

成功時は0を、失敗時は負のエラーコードを返します（この場合write_endは呼ばれません）。

write_end

write_beginが成功し、データのコピーが完了した後、write_endを呼び出す必要があります。lenはwrite_beginに渡された元の長さで、copiedは実際にコピーできたバイト数です。

ファイルシステムはページのロックを解除し、参照カウントを解放し、i_sizeを更新する必要があります。

失敗時は負の値を、成功時は実際にページキャッシュにコピーできたバイト数（copied以下）を返します。

bmap

VFSがオブジェクト内の論理ブロックオフセットを物理ブロック番号にマッピングするため呼び出されます。このメソッドはFIBMAP ioctlおよびスワップファイルの処理で使用されます。ファイルがブロックデバイスへの安定したマッピングを持つことでスワップ可能であり、スワップシステムはファイルシステムを経由せず、bmapを用いてファイル内のブロック位置を直接取得して使用します。

invalidatepage

ページがPagePrivateが設定されている場合、ページの一部または全部がアドレス空間から削除される際にはinvalidatepageが呼び出されます。これは通常、トリミング、穴あけ、またはアドレス空間の完全な無効化に対応します（後者の場合、オフセットは常に0で、長さはPAGE_SIZEになります）。ページに関連するプライベートデータはこのトリミングを反映する必要があります。オフセットが0で長さがPAGE_SIZEの場合、プライベートデータは解放されるべきです（ページが完全に破棄可能になるため）。これは->releasepage関数を呼び出すことで実現できますが、この場合releaseは必ず成功する必要があります。

releasepage

PagePrivateページにおいてreleasepageは、ページを可能であれば解放すべきことを示すために呼び出されます。->releasepageは、ページからプライベートデータを削除し、PagePrivateフラグをクリアする必要があります。releasepage()が何らかの理由で失敗した場合、0を返して失敗を示す必要があります。releasepage()は2つの異なるが関連するケースで使用されます。1つ目のケースは、VMがクリーンなアクティブなユーザーがいないページを見つけ、それをフリーのページに変換したい場合です。->releasepageが成功した場合、そのページはaddress_spaceから削除され、フリーになります。

2つ目のケースは、address_space内の一部またはすべてのページを無効化するリクエストが行われた場合です。これはfadvise(POSIX_FADV_DONTNEED)システムコールを通じて、またはファイルシステムがnfsや9fsのようにキャッシュがストレージと同期していないと信じる場合に明示的にリクエストする際に発生します（その際、callする）。 invalidate_inode_pages2()ファイルシステムがこのようなcallを実行した場合、すべてのページが無効化されることが確実である必要があるときは、そのreleasepageはこれを保証する必要があります。プライベートデータをまだ解放できない場合、PageUptodateビットをクリアする可能性があります。

freepage

ページキャッシュに表示されなくなったページに対してfreepageが呼び出され、プライベートデータのクリーンアップを許可します。memory reclaimerが呼び出す可能性があるため、address_spaceマッピングがまだ存在しているとは仮定せず、ブロックすることを避ける必要があります。

direct_IO

generic read/writeルーチンがdirect_IO（ページキャッシュをバイパスし、ストレージとアプリケーションのアドレス空間間でデータを直接転送するIOリクエスト）を実行するために呼び出されます。

isolate_page

VMがmovable non-lruページをisolateする際に呼び出されます。ページが成功裏にisolateされた場合、VMは__SetPageIsolatedを通じてページをPG_isolatedとしてマークします。

migrate_page

物理メモリの使用量をコンパクトにするためにVMがページを再配置する（例：メモリカードが即将的な失敗を信号している場合）場合、新しいページと古いページをこの関数に渡します。migrate_pageはプライベートデータを転送し、ページへの参照を更新する必要があります。

putback_page

isolatedページのmigrationが失敗した際にVMが呼び出します。

launder_page

ページを解放する前に呼び出され、dirtyページを書き戻します。ページを再汚染しないように、操作全体中はロックされています。

is_partially_uptodate

ページキャッシュを通じてファイルを読み込む際、基盤のブロックサイズがpagesizeと異なる場合にVMが呼び出されます。必要なブロックが最新であれば、IOでページを最新に読み込むことなく読み込みが完了できます。

is_dirty_writeback

ページを回収しようとする際に仮想マシン（VM）が呼び出します。VMはdirty（汚染）およびwriteback（書き戻し）情報をもとに、フラッシャーがIOを完了する機会を確保するための停止が必要かどうかを判断します。通常はPageDirtyおよびPageWritebackを使用しますが、一部のファイルシステムでは状態が複雑（NFSのunstableページが回収を妨げる）またはロック問題によりこれらのフラグを設定しない場合があります。このコールバックは、ファイルシステムがページをdirtyまたはwritebackとして扱うべきかどうかをVMに通知します。

error_remove_page

通常、このアドレス空間がtruncate（切り捨て）可能である場合にgeneric_error_remove_pageに設定されます。メモリ故障処理のために使用されます。この設定をすることで、ページが突然消失することを扱う責任を負います（ページをロックしているか、参照カウントを増加している場合は除く）。

swap_activate

ファイルをswaponで使用して領域を確保し、ブロック検索情報をメモリに固定する際に呼び出されます。ゼロを返すと成功を示し、このファイルをスワップ領域として使用可能になります。

swap_deactivate

swap_activateが成功したファイルに対してswapoffの際呼び出されます。

ディレクトリエントリーキャッシュ（dcache）¶

struct dentry_operations¶

これは、ファイルシステムが標準のdentry操作をオーバーライドする方法を記述しています。dentriesとdcacheはVFSの領域であり、個々のファイルシステム実装が管理します。デバイスドライバはここに関与すべきではありません。これらのメソッドは、オプションであるか、VFSがデフォルトを使用するため、NULLに設定される場合があります。カーネル2.6.22以降では、次のメンバが定義されています:

struct dentry_operations {
        int (*d_revalidate)(struct dentry *, unsigned int);
        int (*d_weak_revalidate)(struct dentry *, unsigned int);
        int (*d_hash)(const struct dentry *, struct qstr *);
        int (*d_compare)(const struct dentry *,
                         unsigned int, const char *, const struct qstr *);
        int (*d_delete)(const struct dentry *);
        int (*d_init)(struct dentry *);
        void (*d_release)(struct dentry *);
        void (*d_iput)(struct dentry *, struct inode *);
        char *(*d_dname)(struct dentry *, char *, int);
        struct vfsmount *(*d_automount)(struct path *);
        int (*d_manage)(const struct path *, bool);
        struct dentry *(*d_real)(struct dentry *, const struct inode *);
};
d_revalidate

VFSがdentryを再検証する必要があるときに呼び出されます。これは、名前検索でdcacheにdentryが見つかったときに呼び出されます。ほとんどのローカルファイルシステムでは、すべてのdcache内のdentryが有効であるため、この関数はNULLに設定されています。ネットワークファイルシステムでは、サーバー側で変更が発生してもクライアントが必ずしも認識しないため、この処理は異なります。

この関数は、dentryが依然として有効である場合は正の値を返し、有効でない場合はゼロまたは負のエラーコードを返します。

d_revalidateはrcu-walkモード（flags & LOOKUP_RCU）で呼び出されることがあります。rcu-walkモードの場合、ファイルシステムはブロッキングせずにdentryを再検証しなければなりません。このモードでは、d_parentやd_inodeは慎重に使用する必要があります（これらが変化したり、d_inodeの場合はNULLになる可能性があります）。

rcu-walkが処理できない状況に遭遇した場合、-ECHILDを返して再度ref-walkモードで呼び出されます。

_weak_revalidate

VFSが「ジャンプした」dentryを再検証するときに呼び出されます。これは、親ディレクトリのlookupを行わずにpath-walkがdentryに終了したときに呼び出されます。これは「/」「．」「..」、procfsスタイルのシンボリックリンクやマウントポイントのトラバーサルを含みます。

この場合、dentryが完全に正しいかどうかよりも、inodeが依然として有効であることが重要です。d_revalidateと同様に、ほとんどのローカルファイルシステムではdcacheエントリが常に有効であるため、この関数はNULLに設定されます。

この関数はd_revalidateと同様の戻り値コードセマンティクスを持ちます。

d_weak_revalidateはrcu-walkモードを離れた後だけ呼び出されます。

d_hash

VFSがdentryをハッシュテーブルに追加するときに呼び出されます。d_hashに最初に渡されるdentryは、名前をハッシュ化する親ディレクトリです。

d_compareと同じロックと同期化のルールを適用します。参照が安全ななどに関する規則も含みます。

d_compare

dentry名を指定された名前と比較するための関数です。最初のdentryは比較対象のdentryの親、2番目のdentryは子です。lenとname文字列は比較対象のdentryのプロパティです。qstrは比較対象の名前です。

定数であり、恒等性を持つ必要があります。可能な限りロックを取らないようにし、dentryに保存しないようにしてください。dentryの外部のポインタを参照する際は慎重に、（例：d_parent、d_inode、d_nameは使用しないでください）。

ただし、我々のvfsmountはピン留めされており、RCUが保持されているため、dentryやinodeは消えません。また、sbやファイルシステムモジュールも消えません。->d_sbは使用可能です。

呼び出し規約は複雑です。RCU-walkの下で呼び出さなければならないため、ロックや参照が一切ない状態で呼び出す必要があります。

d_delete

dentryの最後の参照が解除され、dcacheがキャッシュするかどうかを決定するときに呼ばれます。1を返すと即座に削除、0を返すとキャッシュします。デフォルトはNULLで、到達可能なdentryは常にキャッシュします。d_deleteは定数かつ恒等性を持つ必要があります。

d_init

dentryが割り当てられたときに呼ばれます

d_release

dentryが実際に割り当てが解除されたときに呼ばれます

d_iput

dentryがinodeを失うとき（削除される直前）に呼ばれます。この関数がNULLの場合、VFSは iput(). このメソッドを定義する場合は、必ず iput() 自分自身を呼び出す必要があります

d_dname

dentryのパス名を生成するときに呼ばれます。一部の仮想ファイルシステム（sockfs、pipefsなど）で、パス名の生成を遅延させるために有用です。（dentryが作成されるときにではなく、パスが必要なときにのみ実行されます）。実際のファイルシステムはおそらく使用しないでしょう、なぜならdentryがグローバルなdcacheハッシュに存在するため、ハッシュは不変であるべきだからです。ロックを保持していないため、d_dname()はdentry自体を変更しないようにする必要があります（適切なSMPの安全性が使用される場合を除く）。注意： d_path() 論理はかなり複雑です。例えば「Hello」という文字列を返す正しい方法は、バッファの最後に配置し、最初の文字へのポインタを返すことです。dynamic_dname()というヘルパ関数がこの処理を担当します。

例:

static char *pipefs_dname(struct dentry *dent, char *buffer, int buflen)
{
        return dynamic_dname(dentry, buffer, buflen, "pipe:[%lu]",
                        dentry->d_inode->i_ino);
}
d_automount

automount dentryがトラバースされるときに呼ばれる（オプション）。これは新しいVFSマウントレコードを作成し、呼び出し元にレコードを返す必要があります。呼び出し元には、automountディレクトリを記述するためのパスパラメータと、継承可能なマウントパラメータを提供する親VFSマウントレコードが渡されます。他の誰かがすでにautomountを実行した場合、NULLを返す必要があります。vfsmountの作成に失敗した場合は、エラーコードを返す必要があります。-EISDIRを返すと、ディレクトリは通常のディレクトリとして扱われ、pathwalkに再び処理を続けるよう戻されます。

vfsmountが返された場合、呼び出し元はそのマウントポイントにマウントを試み、失敗した場合はそのvfsmountを期限切れリストから削除します。vfsmountには2つの参照カウントを保持して返す必要があります（自動期限切れを防ぐため）。呼び出し元が追加の参照カウントをクリーンアップします。

この関数は、dentryにDCACHE_NEED_AUTOMOUNTが設定されている場合にのみ使用されます。これは、__d_instantiate()がinodeにS_AUTOMOUNTが設定されている場合に設定されます。

d_manage

dentry（オプション）の遷移をファイルシステムが管理できるようにするため呼ばれます。たとえばautofsは、クライアントが'mountpoint'の背後を探索している間、その待機を保持し、デーモンが通過してそのサブツリーを構築できるようにします。呼び出しプロセスが継続するように0を返す必要があります。-EISDIRを返すと、pathwalkがこのディレクトリを通常のディレクトリとして扱い、その上にマウントされたものを無視し、automountフラグをチェックしないようにします。他のエラーコードはpathwalkを完全に中止します。

「rcu_walk」パラメータがtrueの場合、呼び出し元はRCU-walkモードでpathwalkを行っています。このモードではスリープは許可されず、呼び出し元に-ECHILDを返してこのモードから離脱し、再度呼び出すように求めることができます。-EISDIRを返すと、pathwalkがd_automountやマウントを無視するよう指示されます。

この関数は、遷移元のdentryにDCACHE_MANAGE_TRANSITが設定されている場合にのみ使用されます。

d_real

オーバーレイ/ユニオン型ファイルシステムは、このメソッドを実装して、オーバーレイによって隠された下位のdentryの1つを返します。これは2つの異なるモードで使用されます：

file_dentry()から呼ばれる場合、inode引数に一致する実際のdentryを返します。実際のdentryはすでに下位レイヤーからコピーされて上層に移動しているかもしれませんが、ファイルから参照されています。このモードは、NULLでないinode引数で選択されます。

NULLのinodeの場合、最も上位の実際の下位dentryが返されます。

各dentryは、親のdentryへのポインタと、子dentryのハッシュリストを持っています。子dentryは基本的にディレクトリ内のファイルに相当します。

ディレクトリエントリキャッシュAPI¶

ファイルシステムがdentryを操作できるようにする関数がいくつか定義されています:

dget

既存のdentryに対して新しいハンドルを開く（これは使用カウントをインクリメントするだけです）

dput

dentryのハンドルを閉じる（使用カウントをデクリメントします）。使用カウントが0になった場合、かつdentryが親のハッシュリストにまだ存在する場合、"d_delete"メソッドが呼び出されてキャッシュすべきかどうかを確認します。キャッシュすべきでない場合、またはハッシュされていない場合は削除されます。それ以外の場合はキャッシュされたdentryがLRUリストに追加され、メモリ不足時に回収されます。

d_drop

dentryを親のハッシュリストからアンハッシュします。その後、使用カウントが0になった場合、dput()の呼び出しがdentryを解放します

d_delete

dentryを削除します。dentryに他のオープンな参照がなければ、dentryは負のdentry（"d_iput()"メソッドが呼び出されます）に変換されます。他の参照がある場合は"d_drop()"が呼び出されます

d_add

dentryを親のハッシュリストに追加し、その後 d_instantiate()

d_instantiate

inodeのaliasハッシュリストにdentryを追加し、"d_inode"メンバを更新します。inode構造体の"i_count"メンバは設定またはインクリメントする必要があります。inodeポインタがNULLの場合、dentryは"負のdentry"と呼ばれます。この関数は、既存の負のdentryに対してinodeが作成される際によく呼び出されます

d_lookup

親とパス名コンポーネントを指定してdentryを検索します。指定された名前の子dentryをdcacheハッシュテーブルから検索します。見つかった場合は参照カウントをインクリメントし、dentryを返します。呼び出し元は使用が終わったらdput()を呼び出してdentryを解放する必要があります

マウントオプション¶

オプションの解析¶

マウントおよび再マウント時にファイルシステムに、コンマで区切られたマウントオプションを含む文字列が渡されます。オプションは次の形式のいずれかを持つことができます:

オプション オプション=値

<linux/parser.h>ヘッダーファイルは、これらのオプションを解析するためのAPIを定義しています。既存のファイルシステムではこのAPIの使用例が豊富にあります

オプションの表示¶

ファイルシステムがマウントオプションを受け入れる場合、show_options()を定義して現在有効なオプションをすべて表示する必要があります。ルールは以下の通りです:

  • デフォルト値と異なるオプションは必ず表示する必要があります

  • デフォルト値を持つオプションは表示するかどうかは任意です

マウントヘルパーとカーネル間で内部的に使用されるオプション（ファイル記述子など）、またはマウント時にのみ効果を発揮するオプション（ジャーナルの作成を制御するものなど）は、上記の規則から除外されます。

上記の規則の根本的な理由は、/proc/mountsに記録されている情報に基づき、マウントを正確に再現可能（例：アンマウントして再度マウント）にすることを保証することです。

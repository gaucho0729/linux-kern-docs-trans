ORANGEFS¶

OrangeFS は LGPL ユーザースペース スケールアウト型パラレルストレージシステムです。HPC、ビッグデータ、ストリーミング動画、ゲノム学、バイオインフォマティクスなどで発生する大規模なストレージ問題に最適です。

Orangefs（元々は PVFS と呼ばれていました）は、1993年に Walt Ligon と Eric Blumer が NASA の研究資金により、並列プログラムの I/O パターンを研究するため、Parallel Virtual Machine（PVM）用の並列ファイルシステムとして最初に開発されました。

Orangefs の特徴には以下が含まれます：

  • 複数のファイルサーバー間でファイルデータを分散

  • 複数のクライアントによる同時アクセスをサポート

  • ファイルデータとメタデータをローカルファイルシステムとアクセスメソッドを使用してサーバーに保存

  • ユーザー空間実装はインストールとメンテナンスが簡単

  • 直接 MPI サポート

  • ステートレス

ORANGEFSを単一サーバーで実行¶

OrangeFS は通常、複数のサーバーとクライアントを持つ大規模なインストール環境で動作しますが、開発およびテストには単一のマシン上で完全なファイルシステムを実行できます。

Fedora では orangefs と orangefs-server をインストールします：

dnf -y install orangefs orangefs-server

/etc/orangefs/orangefs.conf に例のサーバー構成ファイルがあります。必要に応じて localhost をホスト名に変更してください。

xfstests に対してファイルシステムを生成するには、以下を参照してください。

/etc/pvfs2tab に例のクライアント構成ファイルがあります。これは1行のファイルです。コメントを解除し、必要に応じてホスト名を変更してください。これは libpvfs2 を使用するクライアントを制御します。これは pvfs2-client-core を制御しません。

ファイルシステムを作成します：

pvfs2-server -f /etc/orangefs/orangefs.conf

サーバーを起動します：

systemctl start orangefs-server

サーバーをテストします：

pvfs2-ping -m /pvfsmnt

クライアントを起動します。この時点でモジュールがコンパイル済みか、ロード済みである必要があります：

systemctl start orangefs-client

ファイルシステムをマウントします：

mount -t pvfs2 tcp://localhost:3334/orangefs /pvfsmnt

単一サーバーでのORANGEFS構築¶

ディストリビューションパッケージからインストールできない場合、ソースコードからビルドできます。

/usr/local に散らばる可能性を気にしなければ、--prefix を省略できます。バージョン 2.9.6 以降、OrangeFS はデフォルトで Berkeley DB を使用します。今後は LMDB に変更する可能性があります。

./configure --prefix=/opt/ofs --with-db-backend=lmdb --disable-usrint

make

make install

pvfs2-genconfig を実行し、ターゲットの構成ファイルを指定して orangefs の構成ファイルを作成します。Pvfs2-genconfig はプロンプトを表示します。通常はデフォルト値を使用するのが問題ありませんが、その質問ではサーバーのホスト名を使用する必要があります（localhost ではなく）：

/opt/ofs/bin/pvfs2-genconfig /etc/pvfs2.conf

/etc/pvfs2tab ファイルを作成します（localhost は問題ありません）：

echo tcp://localhost:3334/orangefs /pvfsmnt pvfs2 defaults,noauto 0 0 > \
    /etc/pvfs2tab

タブファイルで指定したマウントポイントが必要な場合は作成します：

mkdir /pvfsmnt

サーバーをブートストラップします：

/opt/ofs/sbin/pvfs2-server -f /etc/pvfs2.conf

サーバーを起動します：

/opt/ofs/sbin/pvfs2-server /etc/pvfs2.conf

今後、サーバーが動作しているはずです。Pvfs2-ls はサーバーが動作しているかを確認する簡単なテストです：

/opt/ofs/bin/pvfs2-ls /pvfsmnt

動作しているようであれば、カーネルモジュールをロードし、クライアントコアを有効にしてください：

/opt/ofs/sbin/pvfs2-client -p /opt/ofs/sbin/pvfs2-client-core

ファイルシステムをマウントしてください:

mount -t pvfs2 tcp://`hostname`:3334/orangefs /pvfsmnt

xfstestsの実行¶

xfstests と併用する scratch ファイルシステムを使用すると便利です。これを行うには、1台のサーバーで十分です。

サーバー構成ファイルである /etc/orangefs/orangefs.conf の FileSystem セクションを2つ作成します。Name を scratch に変更し、ID を最初の FileSystem セクションの ID と異なる値（通常は2が良いです）に変更してください。

これにより、2つの FileSystem セクション（orangefs と scratch）が存在します。

この変更はファイルシステムを作成する前に実施してください。

pvfs2-server -f /etc/orangefs/orangefs.conf

xfstests を実行するには、/etc/xfsqa.config を作成してください:

TEST_DIR=/orangefs
TEST_DEV=tcp://localhost:3334/orangefs
SCRATCH_MNT=/scratch
SCRATCH_DEV=tcp://localhost:3334/scratch

これにより xfstests を実行できます:

./check -pvfs2

オプション¶

以下のマウントオプションが受け付けられます:

acl

ファイルおよびディレクトリにアクセス制御リスト（ACL）の使用を許可します。

intr

カーネルクライアントとユーザー空間ファイルシステム間の一部の操作は割り込み可能で、デバッグレベルの変更やチューニングパラメータの設定などがあります。

local_lock

「この」カーネルの観点から POSIX ロックを有効にします。デフォルトの file_operations ロックアクションは ENOSYS を返します。ファイルシステムを -o local_lock でマウントすると POSIX ロックが有効になります。分散ロックの実装は今後の計画です。

デバッグ¶

特定のソースファイル（例: inode.c）のデバッグ（GOSSIP）ステートメントを syslog に送るには:

echo inode > /sys/kernel/debug/orangefs/kernel-debug

デバッグなし（デフォルト）:

echo none > /sys/kernel/debug/orangefs/kernel-debug

複数のソースファイルからのデバッグ:

echo inode,dir > /sys/kernel/debug/orangefs/kernel-debug

すべてのデバッグ:

echo all > /sys/kernel/debug/orangefs/kernel-debug

すべてのデバッグキーワード一覧を取得します:

cat /sys/kernel/debug/orangefs/debug-help

カーネルモジュールとユーザースペース間のプロトコル¶

Orangefs はユーザー空間ファイルシステムであり、関連するカーネルモジュールも含まれます。ここからは Orangefs のユーザー空間部分を「ユーザースペース」と呼ぶことにします。Orangefs は PVFS から派生しており、ユーザースペースコードはまだ PVFS を使用して関数および変数名を保持しています。ユーザースペースでは多くの重要な構造体を typedef しています。カーネルモジュールの関数および変数名は「orangefs」に移行しており、Linux コーディングスタイルでは typedef を避けるため、ユーザースペース構造体に対応するカーネルモジュール構造体は typedef されていません。

カーネルモジュールは、ユーザースペースから読み書き可能な擬似デバイスを実装しています。ユーザースペースは ioctl を使用してカーネルモジュールを操作することもできます。

Bufmap¶

起動時にユーザースペースは、ページサイズに合わせた（posix_memalign）mlocked メモリバッファを2つ割り当てます。1つはIO用、もう1つはreaddir操作用です。IOバッファは41943040バイト、readdirバッファは4194304バイトです。各バッファには論理的なチャンク（パーティション）が含まれており、各バッファのポインタはPVFS_dev_map_desc構造体に追加され、その合計サイズ、パーティションのサイズと数も記述されています。

IOバッファのPVFS_dev_map_desc構造体へのポインタが、ioctlを通じてカーネルモジュールのマッピングルーチンに送信されます。この構造体はcopy_from_userによってユーザー空間からカーネル空間へコピーされ、カーネルモジュールの「bufmap」(struct orangefs_bufmap)を初期化するために使用され、その後以下の内容を含みます:

  • refcnt - 参照カウンタ

  • desc_size - PVFS2_BUFMAP_DEFAULT_DESC_SIZE (4194304) - IOバッファのパーティションサイズで、ファイルシステムのブロックサイズを表し、superブロックのs_blocksizeに使用されます。

  • desc_count - PVFS2_BUFMAP_DEFAULT_DESC_COUNT (10) - IOバッファのパーティション数。

  • desc_shift - log2(desc_size)、superブロックのs_blocksize_bitsに使用されます。

  • total_size - IOバッファの総サイズ。

  • page_count - IOバッファ内の4096バイトページの数。

  • page_array - page_count * (sizeof(struct page*)) kcallocedメモリへのポインタ。このメモリはget_user_pages呼び出しを通じて、IOバッファ内の各ページへのポインタを配列として使用します。

  • desc_array - desc_count * (sizeof(struct orangefs_bufmap_desc)) kcallocedメモリへのポインタ。このメモリはさらに初期化されます:

    user_descはカーネルが保持するIOバッファのORANGEFS_dev_map_desc構造体のコピーで、user_desc->ptrはIOバッファへのポインタを指します。

    pages_per_desc = bufmap->desc_size / PAGE_SIZE
offset = 0

bufmap->desc_array[0].page_array = &bufmap->page_array[offset]
bufmap->desc_array[0].array_count = pages_per_desc = 1024
bufmap->desc_array[0].uaddr = (user_desc->ptr) + (0 * 1024 * 4096)
offset += 1024
                   .
                   .
                   .
bufmap->desc_array[9].page_array = &bufmap->page_array[offset]
bufmap->desc_array[9].array_count = pages_per_desc = 1024
bufmap->desc_array[9].uaddr = (user_desc->ptr) +
                                       (9 * 1024 * 4096)
offset += 1024

  • buffer_index_array - desc_countサイズの整数配列で、IOバッファのどのパーティションが使用可能かを示します。

  • buffer_index_lock - buffer_index_arrayを更新時に保護するスピンロック。

  • readdir_index_array - 5 (ORANGEFS_READDIR_DEFAULT_DESC_COUNT)要素の整数配列で、readdirバッファのどのパーティションが使用可能かを示します。

  • readdir_index_lock - readdir_index_arrayを更新時に保護するスピンロック。

操作¶

カーネルモジュールはユーザー空間と通信する必要があるときに「op」(struct orangefs_kernel_op_s)を構築します。このopには「upcall」が含まれ、ユーザー空間へのリクエストを表現します。また、このopには最終的に「downcall」が含まれ、リクエストの結果を表現します。

スラブアロケータはop構造体のキャッシュを保持するために使用されます。

初期化時にカーネルモジュールは、進行中のすべてのopを追跡するためのリクエストリストとin_progressハッシュテーブルを定義および初期化します。

opは状態を持つ:

  • 不明

    • opが初期化されたばかり

  • waiting

    • opがrequest_listにあり（上向きの状態）

  • inprogr

    • opが進行中（ダウンコールを待っている）

  • serviced

    • マッチするダウンコールがある；OK

  • purged

    • クライアントコアがopの処理前に不正に終了したため、タイマースタートが必要

  • given up

    • submitterが待機をやめた

Orangefsのファイルシステム操作（readdir、I/O、createなど）が必要な任意のユーザースペースプログラムでは、オペレーション構造体が初期化され、区別可能なID番号でタグ付けされます。アップコール部分が埋められ、その後「service_operation」関数にオペレーションが渡されます。

service_operationはオペレーションの状態を「待機中」に変更し、リクエストリストに追加します。その後、wait queueを通じてOrangefsのfile_operations.poll関数にシグナルを送ります。ユーザースペースは擬似デバイスをポーリングしており、アップコールリクエストの読み取りが必要であることを認識します。

Orangefsのfile_operations.read関数がトリガーされると、リクエストリストから処理可能と判断されたオペレーションが検索されます。オペレーションはリクエストリストから削除され、オペレーションのタグと埋められたアップコール構造体がユーザースペースにcopy_to_userで戻されます。

これらのコピー操作（および一部の追加プロトコル）が失敗した場合、オペレーションの状態は「待機中」に設定され、再びリクエストリストに追加されます。それ以外の場合、オペレーションの状態は「進行中」に変更され、タグに基づいてハッシュされ、in_progressハッシュテーブルの該当インデックスにあるリストの末尾に追加されます。

ユーザースペースがアップコールへの応答を組み立てる場合、応答（区別タグを含む）がio_vecsを用いて擬似デバイスに書き込まれます。これにより、Orangefsのfile_operations.write_iter関数が関連するタグを持つオペレーションを検索し、in_progressハッシュテーブルから削除します。オペレーションの状態が「キャンセル」または「放棄」でない限り、状態を「サービス済み」に設定します。file_operations.write_iter関数は待機中のvfsに戻り、wait_for_matching_downcallを通じてservice_operationに戻ります。

service_operationは、アップコールへの応答が埋められたオペレーションのダウンコール部分を含めて呼び出し元に返します。

「client-core」はカーネルモジュールとユーザースペースの橋渡しとなる役割を担います。client-coreはデーモンです。client-coreには関連するウォッチドッグデーモンが付随しています。client-coreがいつか終了信号を受けると、ウォッチドッグデーモンがclient-coreを再起動します。client-coreが即座に再起動されるように見えても、このようなイベント中にclient-coreが一時的に停止している期間があります。停止したclient-coreはOrangefsのfile_operations.poll関数でトリガーされません。service_operationを通じて処理される操作は「停止期間」中に待機キューでタイムアウトし、再利用を試みるための一回の試行が行われます。明らかに、client-coreが長時間停止し続けると、Orangefsを使用しようとする任意のユーザースペースプロセスに悪影響を及ぼします。処理できない待機操作はリクエストリストから削除され、状態が「放棄」に設定されます。処理できない進行中の操作はin_progressハッシュテーブルから削除され、状態が「放棄」に設定されます。

readdirおよびI/O操作は、ペイロードに関して特異な挙動を示します。

  • readdir操作は、事前に割り当てられた2つの事前にパーティション化されたメモリバッファのうち小さい方を使用します。readdirバッファはユーザースペース専用です。カーネルモジュールはreaddir操作を開始する前に空きパーティションのインデックスを取得します。ユーザースペースは結果をインデックス付きパーティションに格納し、その後pvfsデバイスに書き戻します。

  • I/O（読み取りおよび書き込み）操作は、事前に割り当てられた2つの事前にパーティション化されたメモリバッファのうち大きい方を使用します。I/Oバッファはユーザースペースおよびカーネルモジュールからアクセス可能です。カーネルモジュールはI/O操作を開始する前に空きパーティションのインデックスを取得します。カーネットモジュールは書き込みデータをインデックス付きパーティションに格納し、ユーザースペースによって直接消費されます。ユーザースペースは読み取りリクエストの結果をインデックス付きパーティションに格納し、カーネルモジュールによって直接消費されます。

カーネルからのリクエストに対する応答はすべてpvfs2_downcall_t構造体でパッケージ化されます。pvfs2_downcall_tにはいくつかの他のメンバに加えて、特定の応答タイプに関連する構造体のユニオンが含まれています。

ユニオンの外側にあるメンバは以下の通りです：

int32_t type

  • 操作の種類。

int32_t status

  • 操作の戻りコード。

int64_t trailer_size

  • readdir操作の場合は0でない。

char *trailer_buf

  • readdir操作中に使用されるNULL初期化されたポインタ。

どの応答に対しても、ユニオン内の適切なメンバが埋められます。

PVFS2_VFS_OP_FILE_IO

pvfs2_io_response_t構造体を埋める

PVFS2_VFS_OP_LOOKUP

PVFS_object_krefを埋める

PVFS2_VFS_OP_CREATE

PVFS_object_krefを埋める

PVFS2_VFS_OP_SYMLINK

PVFS_object_krefを埋める

PVFS2_VFS_OP_GETATTR

PVFS_sys_attr_sに情報を入力する（カーネルが不要な大量の情報）オブジェクトがシンリンクの場合、リンク先の文字列を入力する。

PVFS2_VFS_OP_MKDIR

PVFS_object_krefを埋める

PVFS2_VFS_OP_STATFS

pvfs2_statfs_response_tに不要な情報<g>を埋め込む。我々は、分散ネットワークファイルシステムに関するこれらの統計情報をタイムリーに把握するのが難しい。

PVFS2_VFS_OP_FS_MOUNT

pvfs2_fs_mount_response_tを埋め込む。これはPVFS_object_krefと似ているが、メンバの順序が異なり、「__pad1」は「id」に置き換えられている。

PVFS2_VFS_OP_GETXATTR

pvfs2_getxattr_response_tを埋め込む

PVFS2_VFS_OP_LISTXATTR

pvfs2_listxattr_response_tを埋め込む

PVFS2_VFS_OP_PARAM

pvfs2_param_response_tを埋め込む

PVFS2_VFS_OP_PERF_COUNT

pvfs2_perf_count_response_tを埋め込む

PVFS2_VFS_OP_FSKEY

pvfs2_fs_key_response_tを提出する

PVFS2_VFS_OP_READDIR

pvfs2_readdir_response_tを表す必要な情報を、アップコールで指定されたreaddirバッファディスクリプタに詰め込む。

ユーザースペースは、/dev/pvfs2-reqにwritev()を用いて、カーネル側が行ったリクエストのレスポンスを渡す。

バッファリストは以下の内容を含みます：

  • カーネルからのリクエストに対する準備されたレスポンスへのポインタ（struct pvfs2_downcall_t）。

  • また、readdirリクエストの場合は、ターゲットディレクトリ内のオブジェクトのディスクリプタを含むバッファへのポインタも含みます。

…は、writevを実行する関数（PINT_dev_write_list）に送信されます。

PINT_dev_write_listはローカルのiovec配列：struct iovec io_array[10];

すべてのレスポンスに対して、io_arrayの最初の4要素は以下のように初期化されます：

io_array[0].iov_base = address of local variable "proto_ver" (int32_t)
io_array[0].iov_len = sizeof(int32_t)

io_array[1].iov_base = address of global variable "pdev_magic" (int32_t)
io_array[1].iov_len = sizeof(int32_t)

io_array[2].iov_base = address of parameter "tag" (PVFS_id_gen_t)
io_array[2].iov_len = sizeof(int64_t)

io_array[3].iov_base = address of out_downcall member (pvfs2_downcall_t)
                       of global variable vfs_request (vfs_request_t)
io_array[3].iov_len = sizeof(pvfs2_downcall_t)

readdirレスポンスでは、io_arrayの第5要素は以下のように初期化されます：

io_array[4].iov_base = contents of member trailer_buf (char *)
                       from out_downcall member of global variable
                       vfs_request
io_array[4].iov_len = contents of member trailer_size (PVFS_size)
                      from out_downcall member of global variable
                      vfs_request

Orangefsはdcacheを活用して、ユーザースペースへの冗長なリクエストを回避します。オブジェクトのinode属性はorangefs_inode_getattrで最新に保たれています。orangefs_inode_getattrは「new」と「bypass」の2つの引数を使用して、inodeを更新するかどうかを決定します。Orangefsはオブジェクトのinodeにプライベートデータを保持しており、その中に短いタイムアウト値を含むgetattr_timeがあります。これは、orangefs_inode_getattrのどのイテレーションでもinodeが更新されたからどれくらい経過したかを把握できます。オブジェクトがnewでない（new == 0）かつbypassフラグが設定されていない（bypass == 0）場合、getattr_timeがタイムアウトしていない限り、orangefs_inode_getattrはinodeを更新せずに返します。getattr_timeはinodeが更新されるたびに更新されます。

新しいオブジェクト（ファイル、ディレクトリ、シンボリックリンク）の作成には、そのパス名の評価が含まれ、これによりオブジェクトに対応する負のディレクトリエントリが生成されます。新しいインノードが割り当てられ、そのディレクトリエントリ（dentry）と関連付けられることで、負のディレクトリエントリは「生産的な社会の一員」となるのです。OrangefsはLinuxから新しいインノードを取得し、 new_inode() そのインノードをディレクトリエントリと関連付けるために、ペアを再びLinuxに返送します。 d_instantiate().

オブジェクトのパス名の評価は、それに応じたディレクトリエントリ（dentry）に解決します。対応するディレクトリエントリが存在しない場合、dcacheに新たに作成されます。ディレクトリエントリが変更または検証されるたびに、Orangefsはそのdentryのd_timeに短いタイムアウト値を設定し、その期間はディレクトリエントリが信頼される期間となります。Orangefsはネットワークファイルシステムであり、オブジェクトは特定のOrangefsカーネルモジュールインスタンスとは関係なくオフバンドで変更される可能性があるため、ディレクトリエントリを信頼することはリスクがあります。ディレクトリエントリを信頼する代わりに、必要な情報を常にユーザー空間から取得する必要があります。少なくともクライアントコアに、場合によってはサーバーにアクセスする必要があります。ディレクトリエントリから情報を取得するコストは低く、ユーザー空間から取得するコストは相対的に高いため、可能な限りディレクトリエントリを使用する動機があります。

タイムアウト値d_timeおよびgetattr_timeはジッファーベースであり、コードはジッファーワラップ問題を回避するように設計されています：

"In general, if the clock may have wrapped around more than once, there
is no way to tell how much time has elapsed. However, if the times t1
and t2 are known to be fairly close, we can reliably compute the
difference in a way that takes into account the possibility that the
clock may have wrapped between times."

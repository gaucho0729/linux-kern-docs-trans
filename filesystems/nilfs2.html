NILFS2¶

NILFS2は、連続的なスナップショット作成をサポートするログ構造ファイルシステム(LFS)です。ファイルシステム全体のバージョン管理機能に加え、数秒前までに誤って上書きまたは破壊されたファイルの復元も可能です。NILFS2は従来のLFSと同様に一貫性を保つため、システムのクラッシュ後の迅速な復旧が実現されています。

NILFS2は、数秒ごとまたは同期書き込みごとに（変更がない場合は除く）複数のチェックポイントを生成します。ユーザーは連続して生成されたチェックポイントの中から重要なバージョンを選択し、それをスナップショットとして保存できるように変換できます。スナップショットは変更されるまで保持されます。

ボリュームが満たれるまでスナップショットの数に制限はありません。各スナップショットは、読み取り専用ファイルシステムとしてその書き込み可能マウントと同時にマウント可能であり、オンラインバックアップに便利な機能です。

ユーザー空間ツールはnilfs-utilsパッケージに含まれており、以下のダウンロードページから入手可能です。少なくとも「mkfs.nilfs2」「mount.nilfs2」「umount.nilfs2」「nilfs_cleanerd」（いわゆるクリーナーやガベージコレクター）が必要です。ツールの詳細は、パッケージに同梱されたmanページで説明されています。

注意事項¶

NILFS2がまだサポートしていない機能:

  • アクセス時刻の更新

  • 拡張属性

  • POSIX ACL

  • クォータ

  • fsck

  • デフラグメント

マウントオプション¶

NILFS2がサポートするマウントオプション: (*) == デフォルト

barrier(*)

書き込みバリアの使用を有効/無効にします。この

nobarrier

機能にはバリアをサポートするIOスタックが必要であり、nilfsがバリア書き込みでエラーを検出すると、警告とともに再度無効になります。

errors=continue

ファイルシステムエラーでも継続して動作します。

errors=remount-ro(*)

エラー発生時にファイルシステムを読み取り専用で再マウントします。

errors=panic

エラーが発生した場合、panicを発生させ機械を停止します。

cp=n

マウントするスナップショットのチェックポイント番号を指定します。チェックポイントとスナップショットはlscpユーザコマンドで一覧表示されます。このオプションでマウント可能なのはスナップショットとしてマークされたチェックポイントのみです。スナップショットは読み取り専用なので、読み取り専用マウントオプションを同時に指定する必要があります。

order=relaxed(*)

メタデータ更新が行われていない場合でも、データブロックの変更をディスクに書き出すことを許可する緩和された順序セマンティクスを適用します。このモードはext3ファイルシステムの順序データモードと同等ですが、データブロックの更新は原子性を保つため、上書き時の同期書き込みパフォーマンスが向上します。

order=strict

すべてのファイル操作の順序を保持する厳格な順序セマンティクスを適用します。これにより、クラッシュ後の復旧ファイルシステムでイベントのオーバーラップが発生しないことが保証されます。

norecovery

マウント時にファイルシステムの回復を無効にします。これは、読み取り専用マウントまたはスナップショットの場合、デバイス上のすべての書き込みアクセスを無効にします。このオプションは、不完全なボリューム上の読み書き可能マウントでは失敗します。

discard

discard/TRIMコマンドの使用を有効/無効にします。

nodiscard(*)

ブロックが解放されるときにdiscard/TRIMコマンドが下位ブロックデバイスに送信されます。これはSSDデバイスやスパース/スリムプロビジョニングされたLUNに特に役立ちます。

Ioctls¶

NILFS2固有の機能があり、アプリケーションはシステムコールインターフェースを通じてアクセスできます。すべてのNILFS2固有のioctlの一覧は以下の表に示されています。

NILFS2固有のioctl一覧:

Ioctl

説明

NILFS_IOCTL_CHANGE_CPMODE

指定されたチェックポイントのモードをチェックポイント状態とスナップショット状態の間で変更します。このioctlはchcpおよびmkcpユーティリティで使用されます。

NILFS_IOCTL_DELETE_CHECKPOINT

NILFS2ファイルシステムからチェックポイントを削除します。このioctlはrmcpユーティリティで使用されます。

NILFS_IOCTL_GET_CPINFO

指定されたチェックポイントに関する情報を返します。このioctlはlscpユーティリティおよびnilfs_cleanerdデーモンで使用されます。

NILFS_IOCTL_GET_CPSTAT

チェックポイントの統計情報を返します。このioctlはlscp、rmcpユーティリティおよびnilfs_cleanerdデーモンで使用されます。

NILFS_IOCTL_GET_SUINFO

指定されたセグメントに関するセグメント使用情報を返します。このioctlはlssu、nilfs_resizeユーティリティおよびnilfs_cleanerdデーモンで使用されます。

NILFS_IOCTL_SET_SUINFO

指定されたセグメントのセグメント使用情報を変更します。このioctlはnilfs_cleanerdデーモンがセグメントの不要なクリーンアップ操作をスキップし、フラッシュデバイスのパフォーマンス低下や摩耗を防ぐために使用されます。

NILFS_IOCTL_GET_SUSTAT

セグメント使用統計情報を返します。このioctlはlssu、nilfs_resizeユーティリティおよびnilfs_cleanerdデーモンで使用されます。

NILFS_IOCTL_GET_VINFO

仮想ブロックアドレスに関する情報を返します。このioctlはnilfs_cleanerdデーモンで使用されます。

NILFS_IOCTL_GET_BDESCS

ディスクブロック番号の記述子に関する情報を返します。このioctlはnilfs_cleanerdデーモンで使用されます。

NILFS_IOCTL_CLEAN_SEGMENTS

ユーザー空間からの指定パラメータ環境でガベージコレクション操作を行います。このioctlはnilfs_cleanerdデーモンで使用されます。

NILFS_IOCTL_SYNC

チェックポイントを作成します。このioctlはmkcpユーティリティで使用されます。

NILFS_IOCTL_RESIZE

NILFS2ボリュームをリサイズします。このioctlはnilfs_resizeユーティリティで使用されます。

NILFS_IOCTL_SET_ALLOC_RANGE

セグメントの下限と上限（バイト単位）を定義します。このioctlはnilfs_resizeユーティリティで使用されます。

NILFS2の使用方法¶

nilfs2をローカルファイルシステムとして使用するには、単に:

# mkfs -t nilfs2 /dev/block_device
# mount -t nilfs2 /dev/block_device /dir

これは、マウント補助プログラム（mount.nilfs2）を通じて清掃プロセスも呼び出します。

チェックポイントとスナップショットは以下のコマンドで管理されます。これらのマニュアルページは上記のnilfs-utilsパッケージに含まれています。

lscp

チェックポイントまたはスナップショットの一覧を表示します。

mkcp

チェックポイントまたはスナップショットを作成します。

chcp

既存のチェックポイントをスナップショットに、または逆に変更します。

rmcp

指定されたチェックポイントを無効化します。

スナップショットをマウントするには:

# mount -t nilfs2 -r -o cp=<cno> /dev/block_device /snap_dir

ここで <cno> はスナップショットのチェックポイント番号です。

NILFS2 マウントポイントまたはスナップショットをアンマウントするには、単に:

# umount /dir

その後、アンマウント補助プログラム（umount.nilfs2）が自動的に清掃デーモンを停止します。

ディスクフォーマット¶

NILFS2 ボリュームはスーパーブロック（SB）およびセグメント #0 を除き、複数のセグメントに均等に分割されます。セグメントはログのコンテナです。各ログは要約情報ブロック、ペイロードブロック、およびオプションのスーパールートブロック（SR）から構成されます：

 ______________________________________________________
| |SB| | Segment | Segment | Segment | ... | Segment | |
|_|__|_|____0____|____1____|____2____|_____|____N____|_|
0 +1K +4K       +8M       +16M      +24M  +(8MB x N)
     .             .            (Typical offsets for 4KB-block)
  .                  .
.______________________.
| log | log |... | log |
|__1__|__2__|____|__m__|
      .       .
    .               .
  .                       .
.______________________________.
| Summary | Payload blocks  |SR|
|_blocks__|_________________|__|

ペイロードブロックはファイルごとに整理され、各ファイルはデータブロックとBツリーノードブロックから構成されます：

 |<---       File-A        --->|<---       File-B        --->|
_______________________________________________________________
 | Data blocks | B-tree blocks | Data blocks | B-tree blocks | ...
_|_____________|_______________|_____________|_______________|_

ログにのみ変更されたブロックが記録されるため、データブロックやBツリーノードブロックが存在しないファイルも存在する可能性があります。

ブロックの構造は要約情報ブロックに記録され、各ファイル構造（nilfs_finfo）、各ブロック構造（nilfs_binfo）とともにヘッダ構造（nilfs_segment_summary）を含みます：

 _________________________________________________________________________
| Summary | finfo | binfo | ... | binfo | finfo | binfo | ... | binfo |...
|_blocks__|___A___|_(A,1)_|_____|(A,Na)_|___B___|_(B,1)_|_____|(B,Nb)_|___

ログには通常ファイル、ディレクトリファイル、シンボリックリンクファイル、およびいくつかのメタデータファイルが含まれます。メタデータファイルはファイルシステムのメタデータを維持するために使用されるファイルです。現在のNILFS2バージョンでは以下のメタデータファイルを使用しています：

1) Inode file (ifile)             -- Stores on-disk inodes
2) Checkpoint file (cpfile)       -- Stores checkpoints
3) Segment usage file (sufile)    -- Stores allocation state of segments
4) Data address translation file  -- Maps virtual block numbers to usual
   (DAT)                             block numbers.  This file serves to
                                     make on-disk blocks relocatable.

以下の図は、ログの典型的な構造を示しています：

 _________________________________________________________________________
| Summary | regular file | file  | ... | ifile | cpfile | sufile | DAT |SR|
|_blocks__|_or_directory_|_______|_____|_______|________|________|_____|__|

セグメント境界を越えて移動するため、このファイルのシーケンスは複数のログに分割されることがあります。論理的に1つのログとして扱われるログのシーケンスは、セグメント要約でマークされたフラグで区切られます。NILFS2の回復コードはこの境界情報を参照して、更新の原子性を保証します。

スーパールートブロックはすべてのチェックポイントに挿入されます。これはDAT、cpfile、sufileの3つの特別なインノデを含みます。通常のファイル、ディレクトリ、シンボリックリンク、その他の特別なファイルのインノデはifileに含まれます。ifile自体のインノデはcpfile内の対応するチェックポイントエントリに含まれます。したがって、NILFS2ファイル間の階層構造は以下のようになります：

Super block (SB)
     |
     v
Super root block (the latest cno=xx)
     |-- DAT
     |-- sufile
     `-- cpfile
            |-- ifile (cno=c1)
            |-- ifile (cno=c2) ---- file (ino=i1)
            :        :          |-- file (ino=i2)
            `-- ifile (cno=xx)  |-- file (ino=i3)
                                :        :
                                `-- file (ino=yy)
                                  ( regular file, directory, or symlink )

各ファイルの形式の詳細については、include/uapi/linux ディレクトリにある nilfs2_ondisk.h を参照してください。

NILFS2の設計に関して、私たちは特許やその他の知的財産権を保護していません。この形式で保存されたデータを他のオペレーティングシステムが共有（マウント、読み込み、書き込みなど）できるようにするため、設計を複製することが許可されています。

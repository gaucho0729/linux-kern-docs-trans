Linux Journalling API¶

概要¶

詳細¶

ジャーナリングレイヤーは簡単に使用できます。まず最初に journal_t データ構造を生成する必要があります。ジャーナルが保存される物理メディアの割当方法に応じて、2つの呼び出し方法があります。 jbd2_journal_init_inode() 呼び出しはファイルシステム inode に保存されたジャーナル用で、 jbd2_journal_init_dev() 呼び出しは raw デバイス（連続するブロック範囲）に保存されたジャーナル用です。journal_t は構造体ポインタの typedef なので、最終的に完了したら必ず jbd2_journal_destroy() を呼び出して使用中のカーネルメモリを解放してください。

journal_t オブジェクトを取得したら、ジャーナルファイルを「マウント」またはロードする必要があります。ジャーナリングレイヤーはユーザー空間のツールがすでに領域を確保・初期化済みであることを期待しています。ジャーナルをロードする際には必ず jbd2_journal_load() を呼び出してジャーナル内容を処理してください。クライアントファイルシステムがジャーナル内容を処理する必要がない（または有効な内容すら必要でない）と検知した場合、 jbd2_journal_wipe() を呼び出してジャーナル内容をクリアし、その後 jbd2_journal_load().

を呼び出す前に実行できます。注意点として、jbd2_journal_wipe(..,0) がジャーナルに未処理のトランザクションを検知した場合、自動的に jbd2_journal_skip_recovery() を呼び、同様に jbd2_journal_load() が必要な場合は自動的に jbd2_journal_recover() を呼びます。この段階の例については fs/ext4/super.c の ext4_load_journal() を読むことをお勧めします。

これで、下層のファイルシステムを変更する準備が整いました。ほぼ完了です。

実際にジャーナル化する必要があります。これは変更をトランザクションにラップすることで実現します。さらに、各バッファの変更もジャーナルレイヤーに呼び出しをラップして、変更内容をジャーナルレイヤーが把握できるようにします。これを実行するには jbd2_journal_start() を使用し、トランザクションハンドルを返します。

jbd2_journal_start() およびその対応する jbd2_journal_stop()はトランザクションの終わりを示す関数で、ネスト可能な呼び出しです。必要に応じてトランザクションを再エントリできますが、必ず jbd2_journal_stop() を jbd2_journal_start() 呼び出す回数と同じ回数呼び出さなければなりません（正確にはトランザクションが更新フェーズを終了するまで）。ext4/VFS はこの機能を使用して、インODEの汚染処理やクォータサポートなどの処理を簡略化しています。

各トランザクション内で、個々のバッファ（ブロック）の変更をラップする必要があります。バッファを変更する前に適切に jbd2_journal_get_create_access() / jbd2_journal_get_write_access() / jbd2_journal_get_undo_access() を呼び出す必要があります。これにより、ジャーナリングレイヤーが必要に応じて未変更データをコピーできるようになります。すべてのバッファが以前にコミットされていないトランザクションの一部である可能性があるためです。この時点でようやくバッファを変更できるようになり、変更を実行した後には必ず jbd2_journal_dirty_metadata()バッファへのアクセスを要求した場合、そのバッファがもう一度デバイスにプッシュバックする必要がないことが分かっているなら、呼び出せます jbd2_journal_forget() 過去にbforget()を使用していたのと同じように

A jbd2_journal_flush() すべてのトランザクションをコミットし、チェックポイントするため、いつでも呼び出すことができます

umount時に、put_super()内で呼び出すことができます jbd2_journal_destroy() インコアのジャーナルオブジェクトをクリーンアップします

残念ながら、ジャーナルレイヤーはデッドロックを引き起こす可能性があります。まず注意すべき点は、タスクごとに一度に1つの未完了トランザクションしか存在できないということです。何もコミットされませんが、外側のトランザクションが jbd2_journal_stop()これは、各ファイル/インノデ/アドレスなどの操作の終わりにトランザクションを完了させる必要があります。これにより、別のジャーナルに再エントリされません。トランザクションは、異なるジャーナル間でネストまたはバッチ処理できません。後続のシステムコールで、あなたのファイルシステム以外のファイルシステム（たとえばext4）が変更される可能性があります

注意すべき2番目のケースは、 jbd2_journal_start() トランザクションに必要なスペースがジャーナルに十分でない場合、ブロックされます（nblocksパラメータに基づく）。ブロックされた場合、他のタスクからのトランザクションの完了とコミットを待つだけです。つまり、 jbd2_journal_stop()したがって、デッドロックを避けるためには、 jbd2_journal_start() / jbd2_journal_stop() セマフォとして扱い、セマフォの順序ルールに含めることでデッドロックを防ぎます。注意してください、 jbd2_journal_extend() のブロッキング動作は、に似ています jbd2_journal_start() したがって、ここでも同様にデッドロックする可能性があります jbd2_journal_start().

最初に適切なブロック数を確保してください。 ;-) このトランザクションで操作するブロック数の最大値です。少なくともext4_jbd.hを見て、ext4がこれらの決定を行う基準を確認することをお勧めします

注意すべきもう一つの点は、ディスク上のブロック割当戦略です。なぜなら、削除を行った場合、解放されたブロックを再利用する前にトランザクションがコミットするのを確認する必要があります。もしブロックを再利用してクラッシュが発生した場合、最後に完全にコミットされたトランザクションの終わりで再配分されたブロックの内容を復元する方法はありません。これを実現する簡単な方法は、トランザクションがコミットした後に、内部のメモリ内のブロック割当構造でブロックを空き状態としてマークすることです。Ext4はジャーナルコミットコールバックを使用してこの目的を達成しています

ジャーナル コミット コールバックを使用することで、トランザクションが最終的にディスクにコミットされるときに、ジャーナリングレイヤーにコールバック関数を呼び出すように依頼できます。これにより、自前の管理を行うことができます。コールバック関数を呼び出すようにジャーナリングレイヤーに依頼するには、単に関数ポインタを設定するだけで、各トランザクションコミット後にその関数が呼び出されます。 journal->j_commit_callback トランザクションがコミットされるときに処理が必要なエントリをトランザクションにアタッチするには、 transaction->t_private_list を使用します。

JBD2は、すべてのトランザクション更新をブロックする方法も提供しています。 jbd2_journal_lock_updates() / jbd2_journal_unlock_updates()。Ext4は、一時的にクリーンで安定したファイルシステムのウィンドウが必要なときにこの機能を使用します。例えば、

jbd2_journal_lock_updates() //stop new stuff happening..
jbd2_journal_flush()        // checkpoint everything.
..do stuff on stable fs
jbd2_journal_unlock_updates() // carry on with filesystem use.

この機能を使用することで発生する悪用やDoS攻撃の可能性は明らかでしょう。非特権ユーザー空間がこれらの呼び出しをトリガーできるように許可すると、そのようなコードパスが実行される可能性があります。

高速コミット¶

JBD2は、ファイルシステム固有のデルタコミット、つまり高速コミットを行うこともできます。高速コミットを使用するには、以下のコールバック関数を設定する必要があります。

journal->j_fc_cleanup_cb: 全コミットおよび高速コミットごとに呼び出されるクリーンアップ関数。

journal->j_fc_replay_cb: 高速コミットブロックの再現時に呼び出されるレプレイ関数。

ファイルシステムはJBD2から許可を得ることでいつでも高速コミットを行うことができます。許可を得るには、関数 jbd2_fc_begin_commit()を呼び出す必要があります。高速コミットが完了した後、クライアントのファイルシステムはJBD2にその事実を通知するために、 jbd2_fc_end_commit()を呼び出す必要があります。ファイルシステムが高速コミットを停止後にJBD2に即時フルコミットを実行させる必要がある場合、 jbd2_fc_end_commit_fallback()を呼び出すことで実現できます。これは高速コミット操作が何らかの理由で失敗した場合、一貫性を保証する唯一の方法としてJBD2がフルな伝統的なコミットを実行させるために役立ちます。

JBD2のヘルパー関数で高速コミットバッファを管理します。ファイルシステムは jbd2_fc_get_buf() および jbd2_fc_wait_bufs() を使用して高速コミットバッファの割り当てとIO完了を待機できます。

現在、高速コミットを実装しているのはExt4のみです。Ext4の高速コミット実装の詳細については、fs/ext4/fast_commit.cのトップレベルコメントを参照してください。

Summary¶

ジャーナルを使用するには、マウント、変更（トランザクション）、および変更されたバッファそれぞれについてコンテキストの変更をラップし、ジャーナリングレイヤーにそれらを通知する必要があります。

データ型¶

ジャーナリングレイヤーはtypedefを使用して、使用する構造体の具体的な定義を「隠す」ことができます。JBD2レイヤーのクライアントとして、単にポインタをマジッククッキーとして使用するだけでよいです。ただし、これはC言語のため、隠蔽は強制されません。

構造体¶

type handle_t¶

handle_t型は、プロセスが実行する単一のアトミックな更新を表します。

説明

このハンドルを通じて、プロセスが行ったすべてのファイルシステムの変更が行われます。再帰的な操作（クォータ操作など）は単一の更新としてまとめられます。

バッファクレジットフィールドは、実行中のプロセスがジャーナル化されたバッファを変更していることを記録します。すべての未完了操作に十分なログスペースを確保するため、任意のタイミングで存在するバッファの数を制限する必要があります。操作が完了した場合、未使用のバッファクレジットはトランザクションに戻して、常にトランザクションの未完了更新がどれだけのバッファに影響する可能性があるかを把握します。

これは不透明データ型です。

type journal_t¶

journal_tは、単一のファイルシステムのジャーナリング状態情報を保持します。

説明

journal_tはfsスーパーブロック構造体からリンクされています。

journal_tを使用して、ファイルシステム上のすべての未完了トランザクション活動を追跡し、ログ書き込みプロセスの状態を管理します。

これは不透明データ型です。

struct jbd2_inode¶

jbd_inode型は、トランザクション内に存在する順序モードのインODEをリンクし、コミット時に同期するための構造体です。

定義

  struct inode *i_vfs_inode;

  loff_t i_dirty_end;
};

void jbd2_journal_abort (ジャーナル中止)(journal_t *ジャーナル, int エラー番号)¶

ジャーナルを即時でシャットダウンします。

パラメータ

journal_t *journal

シャットダウンするジャーナル

int errno

ジャーナルに記録するエラー番号（シャットダウンの理由を示します）

説明

全体のジャーナル（単一トランザクションではなく）を完全に即時でシャットダウンします。この操作はジャーナルを閉じて再開しないと元に戻せません。

jbd2_journal_abort 関数は、ext2/ext3 の remount-readonly エラーモードなどの上位エラー回復メカニズムをサポートするためのものです。

ジャーナルアボートは非常に特定のセマンティクスを持ちます。メインファイルシステム内の既存の汚染された、ジャーナル化されていないバッファは bdflush によってディスクに書き出されます。ただし、ジャーナリングメカニズムは即座に停止され、以降のトランザクションコミットは無視されます。

汚染されたジャーナル化されたバッファはジャーナルを経由せずにディスクに書き戻されます。アボートされたファイルシステムでは原子性が保証されませんが、fsck がクリーンアップに使用できるデータをできるだけ残すように試みます。

ジャーナルがABORT状態にある場合、新しいトランザクションハンドルを取得する試みは常に-EROFSエラーが返されます。既存のハンドルに対してjbd2_journal_stopを実行すると、更新中にABORT状態に入った場合、-EIOエラーが返されます。

再帰的なトランザクションは、最終的なjbd2_journal_stopが実行されるまでジャーナルのABORT状態に影響を受けません。この最終的なjbd2_journal_stopは-EIOエラーを返します。

最後に、jbd2_journal_abortコールは呼び出し元がエラーコード(errno)を提供できるようにし、これを可能であればジャーナルスーパーブロックに記録します。これにより、トランザクション途中で失敗状態を記録することなく、トランザクションを完了せずにディスクに失敗状態を記録できます。たとえばext3_errorはこの機能を使用しています。

時折、ディスクにコミットされたメタデータと未コミットのメタデータを区別する必要があります。ext3fsコードでは、この機能をスペースの解放と割当に使用しており、デアルロケーションがコミットされるまで、解放されたスペースを再利用してはいけません。なぜなら、そのスペースを上書きすると、クラッシュ時の削除が巻き戻し不可能になるからです。

これを処理するために、jbd2_journal_get_undo_accessは、ビットマップ上の削除などの非巻き戻し可能な操作の一部にバッファへの書き込みアクセスを要求します。ジャーナリングコードは、undo_access呼び出しの前にバッファの内容のコピーを保持しておく必要があります。バッファがディスクに確実にコミットされるまで、そのコピーを保持しておく必要があります。

コミットされたデータがどのトランザクションに属するかは必要ありません。ここに触れたバッファは、後で汚染されることが保証されており、適切なタイミングで新しいトランザクションにコミットされるため、その時点で古いコミットされたデータポインタを破棄できます。

エラー番号または成功時の0を返します。

int jbd2_journal_dirty_metadata(handle_t *handle, struct buffer_head *bh)¶

バッファを汚れたメタデータを含むものとしてマークする。

パラメータ

handle_t *handle

バッファを追加するトランザクション。

struct buffer_head *bh

マークするバッファ。

説明

現在のトランザクションの一部としてジャーナル化する必要がある汚染されたメタデータをマークする。

バッファは以前に呼び出されて、バッファヘッドに有効なjournal_headが接続されている必要があります。 jbd2_journal_get_write_access() 呼び出されて、バッファヘッドに有効なjournal_headが接続されている必要があります。

バッファはトランザクションのメタデータリストに配置され、トランザクションに属するものとしてマークされます。

エラー番号または成功時の0を返します。

バッファがすでに現在のコミット中のトランザクションに属している場合（その場合、そのコミット用に凍結データが存在する必要があります）、特別な注意が必要です。その場合、バッファを再リンクしないでください。古いトランザクションが最終的にコミットを完了するまで、それだけが行われます。

パラメータ

handle_t *handle

完了するトランザクション。

説明

int jbd2_journal_try_to_free_buffers(journal_t *ジャーナル, struct page *page)¶

ページバッファを解放しようとします。

パラメータ

journal_t *journal

操作用のジャーナル

struct page *page

解放しようとします。

説明

このページ上のすべてのバッファについて、完全に書き出された順序データである場合、BUF_CLEANに移動してtry_to_free_buffers()が回収できるようにします。

この関数は、try_to_free_buffers()を呼び出すことを希望する場合に非ゼロを返します。try_to_free_buffers()でページが解放可能である場合、またはページにロックまたは汚染されたバッファがあり、呼び出し元が同期または非同期の書き出しを実行したい場合にこれを実行します。

これはJBDロックをやや複雑にします。ここではBKLによって保護されていません。__jbd2_journal_unfile_bufferを介して、バッファをコミット中のまたは実行中のトランザクションの->t_datalistから削除したいです。

これは可能です。 変更します。 transaction_t->t_datalistの値を変更するため、t_datalistを確認する人はこの関数に対してロックを取得する必要があります。

さらに悪いことに、このバッファに対してjbd2_journal_dirty_dataが実行されている可能性があります。そのため、この処理にはロックが必要です。jbd2_journal_dirty_data()はロックを解除する際にバッファが汚染されている状態で終了し、これによりここで解放対象外とみなされます。

この影響を受けるのは誰ですか？…実際には競合する処理はdo_get_write_access()のみです。journal_try_to_free_buffer()がバッファの状態を変更している間、この関数がバッファを参照している可能性がありますが、データがトランザクションに含まれている間は解放されたデータをメタデータとして再割当することはできないため、このような状況は発生しません。はい？

失敗時は0を、成功時は1を返す

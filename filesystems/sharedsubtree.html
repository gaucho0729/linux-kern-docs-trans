Shared Subtrees¶

1) 概要¶

以下の状況を考えてみましょう:

プロセスが自身の名前空間をクローンしたいが、最近マウントされたCDにもアクセスしたい場合があります。共有サブツリーのセマンティクスは、このような目的を達成するための必要なメカニズムを提供します。

per-user-namespaceやバージョン付きファイルシステムなどの機能に必要な構築ブロックを提供します。

2) 特徴¶

共有サブツリーは、struct vfsmountを正確に言うと4つの異なるマウントタイプを提供します

  1. 共有マウント

  2. スレーブマウント

  3. プライベートマウント

  4. アンバインド不可マウント

2a) 共有マウントは複数のマウントポイントに複製され、すべての複製が正確に同じになります。

例を以下に示します：

例えば/mntに共有マウントがあるとします:

mount --make-shared /mnt

注: mount(8)コマンドは現在--make-sharedフラグをサポートしているため、サンプルの'smount'プログラムは不要となり削除されました。

# mount --bind /mnt /tmp

上記のコマンドにより/mntのマウントが/tmpのマウントポイントに複製され、両方のマウントの内容は常に同一です。

#ls /mnt
a b c

#ls /tmp
a b c

次に、/tmp/aにデバイスをマウントするとします:

# mount /dev/sd0  /tmp/a

#ls /tmp/a
t1 t2 t3

#ls /mnt/a
t1 t2 t3

注: マウントは/mntのマウントにも伝播しています。

また、/dev/sd0が/mnt/aにマウントされている場合でも、/tmp/aにコンテンツが表示されます。

2b) スレーブマウントは共有マウントと同様ですが、マウントおよびアンマウントイベントは

のみその方向に伝播します。

すべてのスレーブマウントにはマスターマウントがあり、これは共有マウントです。

例を以下に示します：

例えば/mntに共有マウントがあるとします。# mount –make-shared /mnt

次に/mntを/tmpにバインドマウントします。# mount –bind /mnt /tmp

新しいマウントポイント/tmpは共有マウントとなり、/mntのマウントと同一の複製になります。

次に/tmpのマウントを/mntのスレーブにします。# mount –make-slave /tmp

次に/mnt/aに/dev/sd0をマウントします。# mount /dev/sd0 /mnt/a

#ls /mnt/a t1 t2 t3

#ls /tmp/a t1 t2 t3

注: マウントイベントが/tmpのマウントに伝播しています

しかし、/tmpのマウントに何かをマウントした場合、どうなりますか？

# mount /dev/sd1 /tmp/b

#ls /tmp/b s1 s2 s3

#ls /mnt/b

注: マウントイベントが/mntのマウントに伝播していません

2c) プライベートマウントは伝播を受けることや送ることをしません。

これは私たちがよく知っているマウントタイプです。デフォルトのタイプです。

2d) アンバインド不可マウントはアンバインド不可プライベートマウントです

例えば/mntにマウントがあり、それをアンバインド不可にします:

   # mount --make-unbindable /mnt

Let's try to bind mount this mount somewhere else::

   # mount --bind /mnt /tmp
   mount: wrong fs type, bad option, bad superblock on /mnt,
           or too many mounted file systems

アンバインド不可マウントのバインド操作は無効です。

  1. マウント状態の設定

    mountコマンド（util-linuxパッケージ）を使用してマウント状態を設定できます:

    mount --make-shared mountpoint
mount --make-slave mountpoint
mount --make-private mountpoint
mount --make-unbindable mountpoint

4) 利用例¶

  1. プロセスが自身の名前空間をクローンしたいが、最近マウントされたCDにもアクセスしたい場合があります。

    解決策:

    システム管理者は、/cdrom にマウントされたファイルシステムを共有可能に設定できます:

    mount --bind /cdrom /cdrom
mount --make-shared /cdrom

    その後、新しいネームスペースをクローンしたプロセスは、/cdrom にマウントされたファイルシステムを取得し、これは親ネームスペースの /cdrom にマウントされたファイルシステムと同一のマウントになります。

    したがって、CDが挿入され /cdrom にマウントされた場合、そのマウントはすべてのクローンネームスペースの /cdrom にマウントされたマウントに伝播します。

B) プロセスは、他のプロセスにマウントが見えないようにしたいが、他のシステムのマウントは依然として確認できるようにしたい。

解決策:

まず、管理者は全体のマウントツリーを共有可能に設定できます:

mount --make-rshared /

新しいプロセスが新しいネームスペースをクローンし、そのネームスペースの一部をslaveとしてマークできます:

mount --make-rslave /myprivatetree

以降、プロセスが /myprivatetree 内で行ったマウントは、他のネームスペースに表示されません。ただし、親ネームスペースの /myprivatetree で行われたマウントは、プロセスのネームスペースでも表示されます。

上記のセマンティクスに加えて、この機能は以下の問題を解決するための基盤を提供します:

  1. ユーザーごとのネームスペース

    上記のセマンティクスにより、ネームスペース間でのマウントの共有が可能になります。しかし、ネームスペースはプロセスに関連付けられています。ネームスペースをユーザーIDと関連付けるためのユーザーAPIで、ネームスペースを第一級オブジェクトとして扱うことで、各ユーザーが独自のネームスペースを持ち、自身の要件に合わせてカスタマイズできます。これはPAMでサポートされる必要があります。

  2. バージョン付きファイル

    マウントツリー全体が複数の場所で表示される場合、下位のバージョン管理ファイルシステムは、ファイルにアクセスするパスに応じて、そのファイルの異なるバージョンを返すことができます。

    例として:

    mount --make-shared /
mount --rbind / /view/v1
mount --rbind / /view/v2
mount --rbind / /view/v3
mount --rbind / /view/v4

    そして、/usr にバージョン管理ファイルシステムがマウントされている場合、そのマウントは /view/v1/usr、/view/v2/usr、/view/v3/usr および /view/v4/usr にも表示されます。

    ユーザーは、/usr/fs/namespace.c の v3 バージョンを取得するには、/view/v3/usr/fs/namespace.c にアクセスできます。この際、下位のバージョン管理ファイルシステムは v3 バージョンのファイルシステムが要求されていると判別し、対応する inode を返します。

5) 詳細なセマンティクス¶

以下のセクションでは、バインド、リバインド、ムーブ、マウント、アンマウント、クローンネームスペース操作の詳細なセマンティクスを説明します。

注意: このドキュメント全体を通して、「vfsmount」という語と名詞「mount」は同じ意味で使用されています。

5a) マウント状態

あるマウントは、以下の状態のいずれかにあります

  1. 共有

  2. スレーブ

  3. 共有およびslave

  4. プライベートな

  5. unbindable

「伝播イベント」とは、vfsmount で発生し、他の vfsmount のマウントまたはアンマウントアクションを引き起こすイベントを指します。

「ペアーグループ」とは、お互いにイベントを伝播する vfsmount のグループを指します。

  1. 共有マウント

    「共有マウント」は、『ペアーグループ』に属するvfsmountとして定義されます。

    例:

    mount --make-shared /mnt
mount --bind /mnt /tmp

    mntとtmpにマウントされたマウントはどちらも共有されており、同じペアーグループに属しています。mntまたはtmpの下でマウントまたはアンマウントされたものは、そのペアーグループの他のすべてのマウントに反映されます。

  2. スレーブマウント

    「スレーブマウント」は、伝播イベントを受信するが、伝播イベントを転送しないvfsmountとして定義されます。

    スレーブマウントは名前からもわかる通り、マウント/アンマウントイベントを受信するマスターマウントを持ちます。イベントはスレーブマウントからマスターマウントへ伝播しません。共有マウントのみが次のコマンドを実行することでスレーブマウントにできます。

    mount --make-slave mount

    共有マウントがスレーブマウントにされた後は、変更しない限り共有マウントではなくなります。

  3. 共有とスレーブ

    vfsmountは共有でありながらスレーブでもできます。この状態は、マウントが他のvfsmountのスレーブであり、独自のペアーグループも持つことを示します。このvfsmountはマスターマウントから伝播イベントを受信し、また自身の『ペアーグループ』およびスレーブマウントへ伝播イベントを転送します。

    厳密には、vfsmountは独自のペアーグループを持つ共有マウントであり、このペアーグループは他のペアーグループのスレーブです。

    スレーブvfsmountのみが次のコマンドを実行することで『共有かつスレーブ』にできます。

    mount --make-shared mount

    または、スレーブvfsmountを共有vfsmountの下に移動することでも可能です。

  4. プライベートマウント

    「プライベートマウント」は、伝播イベントを受信または転送しないvfsmountとして定義されます。

  5. アンバインド可能マウント

    「アンバインド可能マウント」は、伝播イベントを受信または転送しないことと、バインドマウントできないvfsmountとして定義されます。

状態図:

以下の状態図は、さまざまなコマンドに対するマウントの状態遷移を説明しています。

-----------------------------------------------------------------------
|             |make-shared |  make-slave  | make-private |make-unbindab|
--------------|------------|--------------|--------------|-------------|
|shared       |shared      |*slave/private|   private    | unbindable  |
|             |            |              |              |             |
|-------------|------------|--------------|--------------|-------------|
|slave        |shared      | **slave      |    private   | unbindable  |
|             |and slave   |              |              |             |
|-------------|------------|--------------|--------------|-------------|
|shared       |shared      | slave        |    private   | unbindable  |
|and slave    |and slave   |              |              |             |
|-------------|------------|--------------|--------------|-------------|
|private      |shared      |  **private   |    private   | unbindable  |
|-------------|------------|--------------|--------------|-------------|
|unbindable   |shared      |**unbindable  |    private   | unbindable  |
------------------------------------------------------------------------

* if the shared mount is the only mount in its peer group, making it
slave, makes it private automatically. Note that there is no master to
which it can be slaved to.

** slaving a non-shared mount has no effect on the mount.

以下のコマンド以外でも、「移動」操作は、宛先マウントの種類に応じてマウントの状態を変更します。詳しくは第5d節を参照してください。

5b) バインドセマンティクス

以下のコマンドを考慮してください：

mount --bind A/a  B/b

ここで、「A」はソースマウント、「a」はマウント「A」内のデントリ、「B」は宛先マウント、「b」は宛先マウント内のデントリです。

結果は「A」と「B」のマウントの種類に依存します。以下の表は簡単な参照です：

--------------------------------------------------------------------------
|         BIND MOUNT OPERATION                                           |
|************************************************************************|
|source(A)->| shared      |       private  |       slave    | unbindable |
| dest(B)  |              |                |                |            |
|   |      |              |                |                |            |
|   v      |              |                |                |            |
|************************************************************************|
|  shared  | shared       |     shared     | shared & slave |  invalid   |
|          |              |                |                |            |
|non-shared| shared       |      private   |      slave     |  invalid   |
**************************************************************************

詳細：

  1. 「A」は共有マウントで、「B」も共有マウントです。「A」は共有マウントで、「B」も共有マウントです。新しいマウント「C」

    ‘A’のクローンが作成され、そのルートdentryは‘a’です。‘C’はマウント‘B’のdentry‘b’にマウントされます。また、新しいマウント‘C1’、‘C2’、‘C3’…が‘B’が伝播するすべてのマウントのdentry‘b’に作成されマウントされます。‘C1’…‘Cn’を含む新しい伝播木が作成され、これは‘B’の伝播木と完全に一致します。最後に‘C’のピアグループが‘A’のピアグループとマージされます。

  2. ‘A’はプライベートマウントで、‘B’は共有マウントです。新しいマウント‘C’

    が‘A’のクローンとして作成されます。そのルートdentryは‘a’です。‘C’はマウント‘B’のdentry‘b’にマウントされます。また、新しいマウント‘C1’、‘C2’、‘C3’…が‘B’が伝播するすべてのマウントのdentry‘b’に作成されマウントされます。‘C’、‘C1’…‘Cn’を含む新しい伝播木が設定され、これは‘B’の伝播木と完全に同じ構成になります。

  3. ‘A’はマウント‘Z’のスレーブマウントで、‘B’は共有マウントです。新しい

    マウント‘C’が‘A’のクローンとして作成されます。そのルートdentryは‘a’です。‘C’はマウント‘B’のdentry‘b’にマウントされます。また、新しいマウント‘C1’、‘C2’、‘C3’…が‘B’が伝播するすべてのマウントのdentry‘b’に作成されマウントされます。‘C’、‘C1’…‘Cn’を含む新しい伝播木が作成され、これは‘B’の伝播木と完全に一致します。最後にマウント‘C’とそのピアグループがマウント‘Z’のスレーブになります。言い換えれば、マウント‘C’は‘スレーブかつ共有’の状態になります。

  4. ‘A’はアンバインド不可マウントで、‘B’は共有マウントです。これは

    無効な操作です。

  5. ‘A’はプライベートマウントで、‘B’は非共有（プライベートまたはスレーブまたは

    アンバインド不可）マウントです。新しいマウント‘C’が‘A’のクローンとして作成されます。そのルートdentryは‘a’です。‘C’はマウント‘B’のdentry‘b’にマウントされます。

  6. ‘A’は共有マウントで、‘B’は非共有マウントです。新しいマウント‘C’

    が‘A’のクローンとして作成されます。そのルートdentryは‘a’です。‘C’はマウント‘B’のdentry‘b’にマウントされます。‘C’は‘A’のピアグループのメンバーになります。

  7. ‘A’はマウント‘Z’のスレーブマウントで、‘B’は非共有マウントです。新しい

    マウント‘C’が‘A’のクローンとして作成されます。そのルートdentryは‘a’です。‘C’はマウント‘B’のdentry‘b’にマウントされます。また、‘C’は‘Z’のスレーブマウントに設定されます。言い換えれば、‘A’と‘C’はどちらも‘Z’のスレーブマウントです。‘Z’のマウント/アンマウントイベントは‘A’と‘C’に伝播します。ただし、‘A’のマウント/アンマウントイベントは他の場所に伝播しません。同様に、‘C’のマウント/アンマウントイベントも他の場所に伝播しません。

  8. ‘A’はアンバインド不可マウントで、‘B’は非共有マウントです。これは

    無効な操作です。バインド不可マウントはバインドマウントできません。

5c) Rbindのセマンティクス

Rbindはバインドと同じです。バインドは指定されたマウントを複製します。Rbindは指定されたマウントに属するツリー内のすべてのマウントを複製します。Rbindマウントは、ツリー内のすべてのマウントにバインドマウントが適用されます。

Rbindされるソースツリーにバインド不可マウントが含まれている場合、そのバインド不可マウントの下にあるサブツリーは新しい場所で切り取られます。

例：

以下のようなマウントツリーがあるとします：

   A
 /   \
 B   C
/ \ / \
D E F G

ツリー内のマウントC以外のすべてのマウントは、バインド不可タイプ以外のタイプです。

このツリーがZにRbindされる場合

新しい場所で以下のツリーがあります：

    Z
    |
    A'
   /
  B'                Note how the tree under C is pruned
 / \                in the new location.
D' E'

5d) 移動セマンティクス

以下のコマンドを考慮してください

mount –move A B/b

ここで、'A'はソースマウント、'B'は宛先マウント、'b'は宛先マウント内のデントリです。

結果は'A'と'B'のマウントタイプに依存します。以下の表は簡単な参照です：

---------------------------------------------------------------------------
|                   MOVE MOUNT OPERATION                                 |
|**************************************************************************
| source(A)->| shared      |       private  |       slave    | unbindable |
| dest(B)  |               |                |                |            |
|   |      |               |                |                |            |
|   v      |               |                |                |            |
|**************************************************************************
|  shared  | shared        |     shared     |shared and slave|  invalid   |
|          |               |                |                |            |
|non-shared| shared        |      private   |    slave       | unbindable |
***************************************************************************

注意

共有マウントの下に存在するマウントを移動することは無効です。

詳細は以下の通りです：

  1. ‘A’は共有マウントで、‘B’も共有マウントです。マウント‘A’は

    マウント‘B’のデントリ‘b’にマウントされます。また、‘B’からプロパゲーションを受けるすべてのマウントのデントリ‘b’に新しいマウント‘A1’、‘A2’…‘An’が作成され、マウントされます。‘B’と同じ構成で新しいプロパゲーションツリーが作成されます。この新しいプロパゲーションツリーにはすべての新しいマウント‘A1’、‘A2’…‘An’が含まれます。この新しいプロパゲーションツリーは既存のプロパゲーションツリー‘A’に追加されます。

  2. ‘A’はプライベートマウントで、‘B’は共有マウントです。マウント‘A’は

    マウント‘B’のデントリ‘b’にマウントされます。また、‘B’からプロパゲーションを受けるすべてのマウントのデントリ‘b’に新しいマウント‘A1’、‘A2’…‘An’が作成され、マウントされます。マウント‘A’は共有マウントになります。そして、‘B’と同じ構成のプロパゲーションツリーが作成されます。この新しいプロパゲーションツリーにはすべての新しいマウント‘A1’、‘A2’…‘An’が含まれます。

  3. ‘A’はマウント‘Z’のスレーブマウントで、‘B’は共有マウントです。マウント‘A’は

    マウント‘B’のデントリ‘b’にマウントされます。また、‘B’からプロパゲーションを受けるすべてのマウントのデントリ‘b’に新しいマウント‘A1’、‘A2’…‘An’が作成され、マウントされます。‘B’と同じ構成で新しいプロパゲーションツリーが作成されます。この新しいプロパゲーションツリーにはすべての新しいマウント‘A1’、‘A2’…‘An’が含まれます。この新しいプロパゲーションツリーは既存のプロパゲーションツリー‘A’に追加されます。マウント‘A’は依然としてマウント‘Z’のスレーブマウントですが、同時に共有マウントにもなります。

  4. ‘A’はバインド不可マウントで、‘B’は共有マウントです。操作

    有効ではありません。共有マウント「B」に何らかのマウントをマウントすると、Bからプロパゲーションを受けるマウントにマウントされる新しいマウントが生成される可能性があります。また、「A」マウントはアンバインド不可であり、他のマウントポイントにクローンしてマウントすることはできません。

  5. ‘A’はプライベートマウントで、‘B’は非共有（プライベートまたはスレーブまたは

    アンバインド不可) マウントです。「A」マウントは「B」マウントのデントリー「b」にマウントされています。

  6. 「A」は共有マウントで、「B」は非共有マウントです。「A」マウントは

    「B」マウントのデントリー「b」にマウントされています。「A」マウントは引き続き共有マウントのままです。

  7. 「A」は「Z」マウントのスレーブマウントで、「B」は非共有マウントです。

    「A」マウントは「B」マウントのデントリー「b」にマウントされています。「A」マウントは引き続き「Z」マウントのスレーブマウントのままです。

  8. 「A」はアンバインド不可マウントで、「B」は非共有マウントです。「A」マウントは

    「B」マウントのデントリー「b」にマウントされています。「A」マウントは引き続きアンバインド不可マウントのままです。

5e) マウントセマンティクス

以下のコマンドを考慮してください：

mount device  B/b

「B」が宛先マウントで、「b」が宛先マウント内のデントリーです。

上記の操作はバインド操作と同じですが、ソースマウントは常にプライベートマウントである点が異なります。

5f) アンマウントセマンティクス

以下のコマンドを考慮してください：

umount A

「A」が「B」マウントのデントリー「b」にマウントされている状態です。

「B」マウントが共有の場合、「B」からプロパゲーションを受けるマウントのデントリー「b」に最新にマウントされたマウントで、内部にサブマウントを持たないものはすべてアンマウントされます。

例: 仮に「B1」、「B2」、「B3」がお互いにプロパゲーションする共有マウントとします。

「A1」、「A2」、「A3」がそれぞれ「B1」、「B2」、「B3」のデントリー「b」に最初にマウントされます。

「C1」、「C2」、「C3」がそれぞれ「B1」、「B2」、「B3」のデントリー「b」に次にマウントされます。

「C1」がアンマウントされると、「B1」および「B1」にプロパゲーションするマウントのデントリー「b」に最新にマウントされたマウントすべてがアンマウントされます。

「B1」は「B2」および「B3」にプロパゲーションします。「B2」のデントリー「b」に最新にマウントされたマウントは「C2」で、「B3」のデントリー「b」に最新にマウントされたマウントは「C3」です。

したがって、「C1」、「C2」、「C3」すべてがアンマウントされるべきです。

「C2」または「C3」のいずれかにサブマウントがある場合、そのマウントはアンマウントされませんが、他のすべてのマウントはアンマウントされます。ただし、「C1」がアンマウントされると、「C1」にサブマウントがある場合、アンマウント操作は完全に失敗します。

5g) クローンネームスペース

クローンネームスペースには親ネームスペースと同じすべてのマウントが含まれます。

「A」と「B」が親ネームスペースと子ネームスペースにおける対応するマウントです。

「A」が共有の場合、「B」も共有となり、「A」と「B」はお互いにプロパゲーションします。

「A」が「Z」マウントのスレーブマウントの場合、「B」も「Z」マウントのスレーブマウントになります。

「A」がプライベートマウントの場合、「B」もプライベートマウントになります。

Aがアンバインド可能マウントである場合、Bもアンバインド可能マウントです。

  2. よくある質問

    Q1. バインドマウントが必要な理由は何ですか？シンボリックリンクとはどのように異なりますか？

    シンボリックリンクは、宛先マウントがアンマウントされるか移動された場合、古くなることがあります。一方、バインドマウントは、他のマウントがアンマウントされても移動されても存在し続けます。

    Q2. シェアードサブツリーはexportfsで実装できない理由は何ですか？

    exportfsは、シェアードサブツリーが実行できる一部の機能を実現する重い方法です。私は、スレーブマウントのセマンティクスをexportfsで実装する方法を想像できません。

8A) データ構造

struct vfsmountに4つの新しいフィールドが追加されました:

  • ->mnt_share

  • ->mnt_slave_list

  • ->mnt_slave

  • ->mnt_master

->mnt_share

このvfsmountが送信/受信するプロパゲーションイベントを結びつけるためのリンクです。

->mnt_slave_list

このvfsmountがプロパゲーションするマウントを結びつけるためのリンクです。

->mnt_slave

マスターファイルシステムマウントがプロパゲーションするスレーブマウントを結びつけるためのリンクです。

->mnt_master

このvfsmountがプロパゲーションを受ける主なvfsmountを指します。

->mnt_flags

vfsmountのプロパゲーション状態を示すために、さらに2つのフラグを取る。MNT_SHAREは、vfsmountが共有vfsmountであることを示し、MNT_UNCLONABLEは、vfsmountが複製できないことを示します。

ピアグループ内のすべての共有vfsmountは、->mnt_shareを通じて環状リストを形成します。

同じ->mnt_masterを持つすべてのvfsmountは、->mnt_master->mnt_slave_listに根を置き、->mnt_slaveを通じて環状リストを形成します。

->mnt_masterは、マスターピアグループの任意（かつ異なる可能性のある）メンバを指すことができます。ピアグループのすべての即時スレーブを確認するには、そのメンバのすべての->mnt_slave_listを辿る必要があります。概念的には単一のセットと考え、個々のリストの分布はプロパゲーションや操作によってプロパゲーションツリーがどのように変更されるかに影響しません。

ピアグループ内のすべてのvfsmountは同じ->mnt_masterを持ち、それがNULLでない場合、それらはスレーブリストの連続した（順序付き）セグメントを形成します。

プロパゲーションツリーの例は以下の図に示されています。[ノート: 見て感じる通り森のように見えますが、すべての共有マウントを概念的な「pnode」として扱うと、実際にはツリーになります]:

    A <--> B <--> C <---> D
   /|\            /|      |\
  / F G          J K      H I
 /
E<-->K
    /|\
   M L N

上記の図において、A、B、C、Dはすべて共有しており、お互いにプロパゲーションしています。'A'にはスレーブマウント'E'、'F'、'G'が3つあり、'C'にはスレーブマウント'J'、'K'が2つあり、'D'にはスレーブマウント'H'、'I'が2つあります。'E'は'K'と共有しており、お互いにプロパゲーションしています。また、'K'にはスレーブマウント'M'、'L'、'N'が3つあります。

'A'の->mnt_shareは'B'、'C'、'D'の->mnt_shareとリンクします。

'A'の->mnt_slave_listは'E'、'K'、'F'、'G'の->mnt_slaveとリンクします。

'E'の->mnt_shareは'K'の->mnt_shareとリンクします。

'E'、'K'、'F'、'G'の->mnt_masterは'A'のstruct vfsmountを指します。

'M'、'L'、'N'の->mnt_masterは'K'のstruct vfsmountを指します。

'K'の->mnt_slave_listは'M'、'L'、'N'の->mnt_slaveとリンクします。

'C'の->mnt_slave_listは'J'、'K'の->mnt_slaveとリンクします。

'J'と'K'の->mnt_masterは'C'のstruct vfsmountを指します。

最後に'D'の->mnt_slave_listは'H'、'I'の->mnt_slaveとリンクします。

'H'と'I'の->mnt_masterは'D'のstruct vfsmountを指します。

ノート: プロパゲーションツリーはマウントツリーとは直交しています。

8B ロッキング:

->mnt_share、->mnt_slave、->mnt_slave_list、->mnt_masterはnamespace_semによって保護され（変更には排他ロック、読み取りには共有ロック）ます。

通常、mnt_flags の変更は vfsmount_lock によってシリアル化されています。ただし、2つの例外があります: do_add_mount() と clone_mnt()。前者はまだ共有データ構造に表示されていない vfsmount を変更します。後者は namespace_sem を保持しており、vfsmount への参照は namespace_sem なしではトラバースできないリストにのみ存在します。

8C アルゴリズム:

実装の核心は rbind/move 操作にあります。

全体のアルゴリズムは操作を 3 つのフェーズに分割します: (attach_recursive_mnt() と propagate_mnt() を参照)

  1. 準備フェーズ。

  2. コミットフェーズ。

  3. アボートフェーズ。

準備フェーズ:

ソースツリーの各マウントごとに:

  1. 宛先となるマウントにプロパゲーションを実施するための必要な数のマウントツリーを生成します

    各マウントにプロパゲーションを実施するための必要な数のマウントツリーを生成します

  2. これらのツリーを宛先にアタッチすることは行いません。ただし、->mnt_parent と ->mnt_mountpoint を記録してください

  3. 新しいマウントを連結し、宛先マウントのプロパゲーションツリーと同一のプロパゲーションツリーを形成します

このフェーズが成功した場合、ソースツリーのマウント数「n」の新しいプロパゲーションツリーが存在するはずです。コミットフェーズに移ります

また、宛先マウントがプロパゲーションするマウント数「m」の新しいマウントツリーも存在するはずです。

メモリ割当が失敗した場合、アボートフェーズに移ります。

コミットフェーズ

各マウントツリーを対応する宛先マウントにアタッチします。

アボートフェーズ

新たに作成されたツリーをすべて削除します。

注意

プロパゲーションに関連するすべての機能は pnode.c ファイルにあります

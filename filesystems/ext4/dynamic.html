4. ダイナミック構造¶

ファイルとブロックがファイルに割り当てられるときに動的メタデータが即時的に生成される。

4.1. インデックスノード¶

通常のUNIXファイルシステムでは、インデックスノード（inode）がファイルに関するすべてのメタデータ（タイムスタンプ、ブロックマップ、拡張属性など）を保持し、ディレクトリエントリには含まれない。ファイルに関連する情報を取得するには、まずディレクトリファイルをたどって該当するディレクトリエントリを特定し、その後インデックスノードを読み込む必要がある。ext4はパフォーマンスのため、通常インデックスノードに保存されるファイルタイプをディレクトリエントリに直接保存している（これはFATと比較すると、FATはディレクトリエントリにすべてのファイル情報を直接保存するが、ハードリンクをサポートせず、単純なブロックアロケータとリンクリストの広範な使用によりext4より検索に時間がかかる傾向がある）。

インデックスノードテーブルは線形配列で、 struct ext4_inodeのサイズが確保されており、少なくとも sb.s_inode_size * sb.s_inodes_per_group バイトを保存できるようにしている。インデックスノードが含まれるブロックグループの番号は、 (inode_number - 1) / sb.s_inodes_per_groupで計算され、グループ内のテーブルへのオフセットは (inode_number - 1) % sb.s_inodes_per_groupである。インデックスノード0は存在しない。

インデックスノードチェックサムはFS UUID、インデックスノード番号、およびインデックスノード構造自体を基に計算される。

インデックスノードテーブルエントリは struct ext4_inode.

4.1.1. インODEサイズ¶

ext2およびext3では、インODE構造体のサイズは固定で128バイト（EXT2_GOOD_OLD_INODE_SIZE）であり、各インODEは128バイトのディスクレコードサイズを持ちました。ext4からは、フォーマット時にすべてのインODEに大きなディスクインODEを割り当てることで、元のext2インODEの末尾を超えた領域を確保できるようになりました。ディスクインODEレコードサイズはスーパーブロックで s_inode_sizeに記録されます。struct ext4_inodeが元の128バイトのext2インODEを超えて実際に使用するバイト数は、各インODEの i_extra_isize フィールドに記録されており、これにより新しいカーネルでstruct ext4_inodeを拡張する際に、すべてのディスクインODEをアップグレードする必要がありません。EXT2_GOOD_OLD_INODE_SIZEを超えるフィールドへのアクセスは、 i_extra_isize以内であることを確認する必要があります。デフォルトではext4のインODEレコードは256バイトで、（2019年8月時点では）インODE構造体は160バイト（i_extra_isize = 32）です。インODE構造体の末尾とインODEレコードの末尾の間にある余分な領域は、拡張属性を保存するために使用できます。各インODEレコードはファイルシステムブロックサイズまで最大で大きくなりますが、これは効率が悪いです。

4.1.2. インODEの検索¶

各ブロックグループには sb->s_inodes_per_group インODEがあります。インODE 0は存在しないと定義されているため、この式を使用してインODEが属するブロックグループを特定できます: bg = (inode_num - 1) / sb->s_inodes_per_group。特定のインODEは、ブロックグループのインODEテーブル内の index = (inode_num - 1) % sb->s_inodes_per_groupに位置します。インODEテーブル内のバイトアドレスを取得するには、 offset = index * sb->s_inode_size.

4.1.3. インODEタイムスタンプ¶

インODE構造体の下位128バイトに4つのタイムスタンプが記録されています – インODE変更時間（ctime）、アクセス時間（atime）、データ変更時間（mtime）、削除時間（dtime）。これら4つのフィールドは、Unixエポック（1970-01-01 00:00:00 GMT）からの秒数を32ビット符号付き整数で表しており、2038年1月にオーバーフローします。ディレクトリからリンクされていないがまだ開いている（orphans）インODEでは、dtimeフィールドがorphansリストに使用されるためにオーバーロードされます。スーパーブロックフィールド s_last_orphan は、orphansリストの最初のインODEを指しており、dtimeは次のorphansインODEの番号になります（もしあれば）。

インODE構造体サイズ sb->s_inode_size が128バイトより大きく、 i_inode_extra フィールドがそれぞれを含むだけの大きさがあれば i_[cma]time_extra field, the ctime, atime, and mtime inode fields are widened to 64 bits. Within this “extra” 32-bit field, the lower two bits are used to extend the 32-bit seconds field to be 34 bit wide; the upper 30 bits are used to provide nanosecond timestamp accuracy. Therefore, timestamps should not overflow until May 2446. dtime was not widened. There is also a fifth timestamp to record inode creation time (crtime); this field is 64-bits wide and decoded in the same manner as 64-bit [cma]time. Neither crtime nor dtime are accessible through the regular stat() interface, though debugfs will report them.

We use the 32-bit signed time value plus (2^32 * (extra epoch bits)). In other words:

4.2. inode.i_blockの内容¶

ファイルが記述するファイルタイプによって、 inode.i_block の60バイトのストレージは異なる用途で使用されます。通常、正規ファイルとディレクトリはファイルブロックインデックス情報を、特殊ファイルは特殊な用途に使用します。

4.2.1. シンボリックリンク¶

シンボリックリンクのターゲットは、ターゲット文字列が60バイト未満の場合、このフィールドに保存されます。それ以外の場合、エクステンスやブロックマップを使用してデータブロックを割り当ててリンクターゲットを保存します。

4.2.2. 直接/間接ブロックアドレス指定¶

ext2/3では、ファイルブロック番号は1〜3段階のブロックマップによって論理ブロック番号にマッピングされました。特定のファイルブロックを格納する論理ブロックを検索するには、この複雑な構造を navigated する必要がありました。注意してください、ブロックがゴミデータであることを確認するためのマジックナンバーもチェックサムもありません。

このブロックマッピングスキームでは、大規模な連続ファイルであっても多くのマッピングデータを記録する必要があります。この非効率性により、以下の通りエクステントマッピングスキームが作成されました。

このマッピングスキームを使用したファイルは、2^32ブロックを超えて配置することはできません。

4.2.3. エクステントツリー¶

ext4では、ファイルと論理ブロックのマッピングはエクステントツリーに置き換えられました。旧スキームでは、1,000ブロックの連続領域を割り当てるには1,000項目をマッピングする間接ブロックが必要でしたが、エクステントではマッピングを単一の struct ext4_extent with ee_len = 1000にまで減らすことができます。flex_bgが有効な場合、単一のエクステントで非常に大きなファイルを割り当てることにより、メタデータブロックの使用量が大幅に削減され、ディスク効率にも若干の改善が得られます。この機能を使用するには、インノデがエクステントフラグ（0x80000）を設定しておく必要があります。

拡張領域は木構造として配置されます。この木構造の各ノードは、 struct ext4_extent_header。ノードが内部ノード（eh.eh_depth ＞0）の場合、ヘッダーの後に eh.eh_entries インスタンスが続きます struct ext4_extent_idx；これらのインデックスエントリのそれぞれは、拡張領域木に含まれるさらに多くのノードを含むブロックを指します。ノードが葉ノード（eh.eh_depth == 0）その後、ヘッダーは続く eh.eh_entries インスタンスが続きます struct ext4_extent; これらのインスタンスはファイルのデータブロックを指します。extentツリーのルートノードは inode.i_block、最初の4つのextentを追加のメタデータブロックを使用せずに記録できるようにします。

ファイルシステムにインラインデータ機能が有効化されており、インノードにフラグが設定されている場合、この場所にファイルデータの最初の60バイトが格納されている可能性があります。

4.3. ディレクトリエントリ¶

ext4ファイルシステムでは、ディレクトリはほぼフラットなファイルであり、任意のバイト列（通常はASCII）をファイルシステム上のinode番号にマッピングします。ファイルシステム全体にわたって同じinode番号を参照するディレクトリエントリが存在することもあり、これらはハードリンクと呼ばれ、ハードリンクは他のファイルシステム上のファイルを参照することはできません。このような理由から、特定のディレクトリエントリを取得するには、そのディレクトリファイルに関連するデータブロック（複数可能）を読み込む必要があります。

4.3.1. 線形（クラシック）ディレクトリ¶

デフォルトでは、各ディレクトリは「ほぼ線形」な配列でエントリをリストします。『ほぼ』と書くのは、メモリ上の線形配列ではなく、ファイルシステムブロックに分割されていないためです。したがって、より正確にはディレクトリがデータブロックの系列であり、各ブロックが線形配列のディレクトリエントリを含んでいると表現できます。各ブロック内の配列の終わりはブロックの終わりに達したとき、ブロック内の最後のエントリはブロックの終わりまでをカバーするレコード長を持ちます。全体のディレクトリの終わりはファイルの終わりに達したときです。未使用のディレクトリエントリはinode = 0で表されます。デフォルトではファイルシステムは struct ext4_dir_entry_2 ディレクトリエントリを処理します（"filetype"機能フラグが設定されていない場合、この処理は struct ext4_dir_entry.

4.3.2. ハッシュツリー・ディレクトリ¶

線形配列のディレクトリエントリはパフォーマンス面で不向きなので、ext3に新しい機能としてハッシュを基にしたバランスツリーが導入されました。インノードのEXT4_INDEX_FL（0x1000）フラグが設定されている場合、このディレクトリはハッシュ化されたBツリー（htree）でディレクトリエントリを整理・検索します。ext2との後方読み取り互換性のために、このツリーは実際にはディレクトリファイル内に隠蔽され、「空」のディレクトリデータブロックとして偽装されています。以前に述べたように、線形ディレクトリエントリテーブルの終わりはインノード0を指すエントリで示されましたが、これは古い線形スキャンアルゴリズムを欺いて残りのディレクトリブロックが空であると誤認させ、処理を進めるために再利用されています。

ツリーのルートは常にディレクトリの最初のデータブロックに存在します。ext2の慣例により、「．」と「..」のエントリはこの最初のブロックの先頭に配置されるため、ここに配置され、ツリーには保存されません。ルートノードの残りはツリーに関するメタデータを含み、最後にハッシュ→ブロックマップが含まれて、htree内の下位ノードを検索します。もし struct ext4_dir_entry_2がゼロでなければ、htreeは2段階になります。ルートノードのマップで指すデータブロックは内部ノードであり、これはマイナーハッシュでインデックスされます。このツリーの内部ノードはゼロに設定された dx_root.info.indirect_levels の後にマイナーハッシュ→ブロックマップが続き、葉ノードを検索します。葉ノードはすべての struct ext4_dir_entry_2 を含む線形配列を持ちます struct ext4_dir_entry_2これらすべてのエントリ（おそらく）同じ値にハッシュ化されます。オーバーフローがある場合、エントリは次の葉ノードにオーバーフローし、この次の葉ノードに到達するためのハッシュの最下位ビット（内部ノードマップ内）が設定されます。

htreeとしてディレクトリをトラバースする場合、コードは目的のファイル名のハッシュを計算し、それに応じたブロック番号を検索します。ツリーがフラットな場合、ブロックは線形配列のディレクトリエントリで検索可能です。それ以外の場合、ファイル名の小ハッシュを計算し、この2番目のブロックに対して使用して3番目のブロック番号を検索します。その3番目のブロック番号は線形配列のディレクトリエントリになります。

ディレクトリを線形配列としてトラバースする場合（古いコードのように）、コードはディレクトリ内のすべてのデータブロックを読み込みます。htreeで使用されるブロックは、'.' および '..' を除いてエントリがありませんので、みたすには葉ノードのみが興味深いコンテンツを含むように見えます。

4.4. 拡張属性¶

拡張属性（xattrs）は通常、ディスク上の別データブロックに保存され、インODEから参照されます。 inode.i_file_acl*。拡張属性の最初の使用例は、ファイルACLやその他のセキュリティデータ（SELinux）の保存に用いられたようです。 user_xattr マウントオプションを使用することで、ユーザーはすべての属性名が「user」で始まる限り、拡張属性を保存できます。この制限はLinux 3.0以降ではなくなったようです。

拡張属性は2つの場所に存在します。1つ目の場所は、各インODEエントリの終わりと次のインODEエントリの始めの間にあります。たとえば、inode.i_extra_isize = 28 かつ sb.inode_size = 256 の場合、インODE内に利用可能な領域は 256 - (128 + 28) = 100 バイトです。2つ目の場所は、 inode.i_file_aclが指すブロックにあります。Linux 3.11以降では、このブロックが2番目の拡張属性ブロック（またはクラスターの残りのブロックさえ）へのポインタを含むことはできません。理論上は、各属性の値を個別のデータブロックに保存することが可能ですが、Linux 3.11以降のコードではこれを許可していません。

キーは一般的にASCIIZ文字列とみなされ、値は文字列またはバイナリデータのいずれかです。

4.4.1. 属性名インデックス¶

論理的には、拡張属性はキー=値のペアの系列である。キーはNULL終端文字列とみなされる。キーローカルに消費するディスクスペースを減らすために、キーストリングの先頭が属性名インデックスと照合される。一致があれば、属性名インデックスフィールドが設定され、一致する文字列はキーネームから削除される。以下に名前インデックス値とキープレフィックスのマッピングを示す：

名前インデックス

キープレフィックス

例えば、属性キーが「user.fubar」の場合、属性名インデックスは1に設定され、「fubar」の名前がディスクに記録される。

4.4.2. POSIX ACL¶

POSIX ACLはLinuxカーネル（およびlibaclの）内部ACL形式の簡略版として保存される。主な違いはバージョン番号が異なる（1）ことと、 e_id フィールドは名前付きユーザーおよびグループACLのみに保存される。

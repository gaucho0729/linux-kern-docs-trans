このドキュメントは、Coda ファイルシステムの動作に必要な Venus とカーネルレベルのファイルシステムコード間の通信を説明しています。このドキュメントバージョンは、現在のインターフェース（バージョン1.0）および将来の改善点を説明することを目的としています。

1. はじめに¶

Coda 分散ファイルシステムの重要なコンポーネントはキャッシュマネージャー、Venus です。

Coda 対応システムでプロセスが Coda ファイルシステムのファイルにアクセスするとき、リクエストはオペレーティングシステム内のファイルシステムレイヤーに送られます。オペレーティングシステムは Venus と通信してプロセスのリクエストを処理します。Venus は永続的なクライアントキャッシュを管理し、Coda ファイルサーバーや関連サーバー（認証サーバーなど）へのリモートプロシージャ呼び出しを実行してリクエストを処理します。Venus がリクエストを処理したら、適切な戻り値コードと関連データをオペレーティングシステムに応答します。オプションで Coda のカーネルサポートは最近処理したリクエストのミニキャッシュを保持して、Venus とのやり取りを制限します。Venus はミニキャッシュ内の要素がもはや有効でなくなったときにカーネルに通知する機能を持っています。

このドキュメントは、カーネルと Venus 間のこの通信を正確に説明します。アップコールおよびダウンコールという用語の定義と、それらが処理するデータの形式を示します。また、呼び出しによって生じるセマンティック不変性についても説明します。

歴史的にCodaはBSDファイルシステム上でMach 2.6で実装されていました。カーネルとVenusのインターフェースはBSD VFSインターフェースと非常に似ています。同様の機能が提供され、パラメータの形式や返却されるデータの形式もBSD VFSと非常に似ています。これにより、BSDシステム上でCoda用のカーネルレベルファイルシステムドライバーを実装するための自然な環境が整っています。ただし、LinuxやWindows 95、NTなどの他のオペレーティングシステムでは、インターフェースが異なる仮想ファイルシステムが存在します。

これらのシステム上でCodaを実装するには、Venus/カーネルプロトコルの逆コンピューティングが必要です。また、他のシステムがプロトコルの特定の小さな最適化や変更によって大幅な恩恵を受けることが明らかになりました。この作業を容易にするため、また今後の移植を容易にするために、Venusとカーネル間の通信は詳細にドキュメンテーションされるべきです。これはこのドキュメントの目的です。

2. Codaファイルシステムコールの処理¶

Codaファイルシステムサービスのリクエスト処理は、CodaファイルにアクセスするプロセスPから始まります。このプロセスはカーネルにシステムコールを実行し、トラップします。このようなカーネルにトラップするシステムコールの例として、Unix コンテキストがあります。 read, write, open, close, create, mkdir, rmdir, chmod Win32環境でも同様のコールが存在し、名前は CreateFile.

一般的に、オペレーティングシステムは仮想ファイルシステム（VFS）レイヤーでリクエストを処理します。NTではI/O Managerと呼ばれ、Windows 95ではIFS Managerと呼ばれます。VFSはリクエストの一部の処理を行い、リクエストの一部を処理する特定のファイルシステム（FS）ドライバーを特定します。通常、パス内の情報は正しいFSドライバーを特定するのに役立ちます。時には、広範な事前処理の後、VFSはFSドライバー内のエクスポートされた関数を呼び出します。これはFS固有のリクエスト処理が開始されるポイントであり、ここではCoda固有のカーネルコードが登場します。

CodaのFSレイヤーはいくつかのインターフェースを公開し実装する必要があります。まず第一に、VFSがCoda FSレイヤーに対して必要なすべての呼び出しを実行できるようにするため、Coda FSドライバーはオペレーティングシステムで適用可能なVFSインターフェースを公開する必要があります。これらのインターフェースはオペレーティングシステムによって大きく異なりますが、オブジェクトの読み書きや作成・削除などの機能は共通しています。Coda FSレイヤーは、キャッシュマネージャーVenusが提供する明確に定義されたサービスを1つまたは複数呼び出すことによってVFSのリクエストを処理します。Venusからの応答がFSドライバーに戻ってきた後、VFSリクエストの処理は続き、最終的にカーネルのVFSに応答を返します。最後にVFSレイヤーはプロセスに戻ります。

この設計により、FSドライバーが公開する基本的なインターフェースはVenusがメッセージ通信を管理できるようにする必要があります。特にVenusはメッセージの取得・配置ができ、新しいメッセージの到着を通知される必要があります。通知はVenusが他のタスクを処理する際でもブロックされないメカニズムで行われるべきです。

Coda FSドライバーのインターフェース

さらにFSレイヤーは、ユーザープロセスとVenusとの特別な通信経路、pioctlインターフェースを提供します。pioctlインターフェースは、Venusが管理する永続的なキャッシュに関する詳細な情報を要求するなど、Coda固有のサービスに使用されます。この際、カーネルの関与は最小限です。呼び出し元プロセスを特定し、情報をVenusに転達します。Venusが応答を返すと、その応答は変更せずに呼び出し元に返されます。

最後にVenusはカーネルのFSドライバーに特定のサービスの結果をキャッシュさせることができます。これによりコンテキストスイッチを過剰に減らし、効率的なシステムを実現します。ただし、Venusはネットワークなどから情報を取得する場合があり、その結果キャッシュされた情報がフラッシュまたは置き換えなければならないことがあります。その際、VenusはCoda FSレイヤーにダウンコールを実行し、キャッシュのフラッシュまたは更新を依頼します。カーネルのFSドライバーはこのようなリクエストを同期的に処理します。

これらのインターフェースの中では、VFSインターフェースおよびメッセージの配置・受信・通知のための機能はプラットフォーム固有です。VFSレイヤーにエクスポートされる呼び出しについては詳しく説明しませんが、メッセージ交換メカニズムの要件を述べます。

3. メッセージレイヤー¶

最低レベルでは、ヴェネスとFSドライバ間の通信はメッセージを通じて行われます。コダーファイルサービスを要求するプロセス間の同期は、プロセスをブロックし、再び起動する仕組みに依存しています。コダーファイルシステムドライバは、プロセスPの代わりにVFSおよびpioctlリクエストを処理し、ヴェネスにメッセージを作成して、応答を待ってから呼び出し元に戻ります。メッセージのやり取りの実装はプラットフォーム依存しますが、セマンティクスはこれまで一般的に適用可能であるように見えています。データバッファはFSドライバがカーネルメモリでPの代わりに作成し、ヴェネスでユーザーメモリにコピーされます。

FSドライバがPの処理を行っている間、ヴェネスへのアップコールが行われます。このようなアップコールは、メッセージ構造体を作成してヴェネスにディスパッチされます。構造体にはPの識別情報、メッセージのシーケンス番号、リクエストのサイズ、カーネルメモリ内のリクエストデータへのポインタが含まれます。データバッファはヴェネスからの応答を保持するために再利用されるため、応答のサイズを示すフィールドがあります。メッセージにフラグフィールドが使用され、メッセージの状態を正確に記録します。追加のプラットフォーム依存構造体には、メッセージがキューにある位置を示すポインタと同期オブジェクトへのポインタが含まれます。アップコールルーチンでは、メッセージ構造体が埋められ、フラグが0に設定され、その後 保留中 キューに配置されます。アップコールを呼び出すルーチンはデータバッファの割り当てを担当しており、その構造については次のセクションで説明します。

ヴェネスにメッセージが作成されたことを通知するための機能が存在する必要があります。これはOS内の利用可能な同期オブジェクトを使用して実装されます。この通知はプロセスPのアップコールコンテキストで行われます。メッセージが保留中キューにある間、プロセスPはアップコールを進めることが出来ません。ファイルシステムリクエストルーチンでのPのカーネルモード処理は、ヴェネスが応答するまで一時停止される必要があります。そのため、Pの呼び出しスレッドはアップコール中にブロックされます。メッセージ構造体内のポインタは、Pが待機している同期オブジェクトを指します。

ヴェネスはメッセージが到着したことを通知し、FSドライバはgetmsg_from_kernel呼び出しを通じてヴェネスにメッセージを取得させます。この動作はカーネル内でメッセージ処理キューにメッセージを追加し、フラグをREADに設定することで完了します。ヴェネスはデータバッファの内容を受け取り、getmsg_from_kernel呼び出しは返り、ヴェネスはリクエストを処理します。

後述のタイミングでFSドライバがVenusからメッセージを受信します。具体的には、Venusがsendmsg_to_kernelを呼び出すタイミングです。このとき、Coda FSドライバはメッセージの内容を確認し、以下の判断を行います。

  • メッセージが待機中のスレッドPに対する応答である場合、ドライバは処理キューからメッセージを取り除き、メッセージをWRITTENとしてマークします。その後、FSドライバはVenusのカーネルモードコンテキスト内でスレッドPをブロック解除し、sendmsg_to_kernel呼び出しはVenusに戻ります。その後、スレッドPはスケジューリングされて、Venusからの応答データをもとにアップコール処理を再開します。

  • メッセージは downcallです。ダウンコールとは、VenusからFSドライバへのリクエストです。FSドライバは即座にリクエストを処理します（通常はキャッシュの追い出しまたは置き換え処理）その後、処理が完了するとsendmsg_to_kernelが戻ります。

このときPは目覚め、アップコール処理を再開します。いくつかの注意点があります。まず、Pは他のソースからのシグナル（例：Pの終了を試みる操作）によってアップコールで目覚めたのか、通常通りVenusのsendmsg_to_kernel呼び出しによって目覚めたのかを判定します。通常のケースでは、アップコールルーチンがメッセージ構造体を解放して戻り、FSルーチンが処理を継続します。

待機とIPCの設定

Pがシグナルによって目覚めた場合、Venusによる目覚めでない場合は、まずフラグフィールドを確認します。メッセージがまだREADされていない場合、PはVenusへの通知なしにシグナルを処理できます。VenusがREADしており、リクエストを処理すべきでない場合、PはVenusにシグニアルメッセージを送って以前のメッセージを無視するように通知します。このようなシグナルはキューの先頭に追加され、Venusが最初に読み込みます。メッセージがすでにWRITTENとしてマークされている場合、処理を停止することはできません。VFSルーチンは継続します。（– VFSリクエストが複数のアップコールを含む場合、このように複雑な状態が生じるため、メッセージ構造体に「handle_signals」という追加フィールドを設けることで、不可逆的なポイントを示すことができます。–）

3.1. 実装の詳細¶

このメカニズムのUnix実装は、Codaに関連するキャラクタデバイスの実装を通じて行われました。Venusはデバイスのread呼び出しによりメッセージを取得し、応答はwrite呼び出しで送信され、通知はデバイスのファイルディスクリプタに対するselectシステムコールを通じて行われます。プロセスPは割込み可能なウェイトキューオブジェクトに待機します。

Windows NTおよびDPMI Windows 95の実装では、DeviceIoControlコールが使用されます。DeviceIoControlコールは、ユーザー記憶域からカーネル記憶域へバッファをコピーするためのオペコードを設計しています。sendmsg_to_kernelは同期コールとして発行され、getmsg_from_kernelは非同期コールとして実行されます。メッセージ到着の通知にはWindowsイベントオブジェクトが使用されます。NTではプロセスPがKernelEventオブジェクトに待機し、Windows 95ではセマフォで待機します。

4. 呼び出しレベルのインターフェース¶

このセクションでは、Coda FSドライバがVenusに呼び出すアップコールについて説明します。これらのアップコールはすべて、inputArgsとoutputArgsという2つの構造体を使用しています。擬似BNF形式で構造体は以下のようになります：

struct inputArgs {
    u_long opcode;
    u_long unique;     /* Keep multiple outstanding msgs distinct */
    u_short pid;                 /* Common to all */
    u_short pgid;                /* Common to all */
    struct CodaCred cred;        /* Common to all */

    <union "in" of call dependent parts of inputArgs>
};

struct outputArgs {
    u_long opcode;
    u_long unique;       /* Keep multiple outstanding msgs distinct */
    u_long result;

    <union "out" of call dependent parts of inputArgs>
};

進む前に、各フィールドの役割について明確に説明します。inputArgsは、Venusからサービスを要求する種類を定義するオペコードで始まります。現在は約30のアップコールがあり、それらについて説明します。uniqueフィールドはinputArgを一意に識別する番号を割り当てます。プロセスとプロセスグループIDが渡され、最後に呼び出し元の資格情報が含まれます。

具体的なコールに入る前に、カーネルとVenusで共有されるさまざまなデータ構造について議論する必要があります。

4.1. カーネルとVenusで共有されるデータ構造¶

CodaCred構造体は、呼び出しプロセスで設定されたユーザーおよびグループIDを複数のユーザーとグループIDを定義します。vuid_tとvgid_tは32ビットの符号なし整数です。また、グループメンバシップは配列で定義されています。UnixではCodaCredはCodaのセキュリティセマンティクスを実装するために十分ですが、Windows環境ではこれらの成熟に伴って構造体の変更が必要になる可能性があります：

struct CodaCred {
    vuid_t cr_uid, cr_euid, cr_suid, cr_fsuid; /* Real, effective, set, fs uid */
    vgid_t cr_gid, cr_egid, cr_sgid, cr_fsgid; /* same for groups */
    vgid_t cr_groups[NGROUPS];        /* Group membership for caller */
};

注意

VenusにCodaCredsが必要かどうかは疑問です。最終的にVenusはグループについて知らないものの、デフォルトUID/GIDでファイルを作成します。グループメンバシップのリストは余分かもしれません。

次の項目はCodaファイルを識別するための基本的な識別子であるViceFidです。ファイルのfidは、Codaファイルシステム内のセル内でファイルまたはディレクトリを一意に定義します。 1:

typedef struct ViceFid {
    VolumeId Volume;
    VnodeId Vnode;
    Unique_t Unique;
} ViceFid;
1

セルとは、単一のシステム制御マシン（SCM）の下で動作するCodaサーバーのグループです。SCMの役割についての詳細な説明は、Coda管理マニュアルをご参照ください。

各構成フィールド：VolumeId、VnodeIdおよびUnique_tは符号なし32ビット整数です。今後、Codaセルを識別するための追加フィールドを先頭に追加する必要があると考えています。これはおそらくDNSを介してCodaセルを名付けるIPv6サイズのIPアドレスの形式になるでしょう。

金星とカーネルが共有する次の重要な構造は、ファイルの属性です。以下の構造は情報を交換するために使用されます。今後拡張可能な機能（現在はCodaには存在しませんが、デバイスファイルのサポートなど）に備えるための余地があります：

struct coda_timespec {
        int64_t         tv_sec;         /* seconds */
        long            tv_nsec;        /* nanoseconds */
};

struct coda_vattr {
        enum coda_vtype va_type;        /* vnode type (for create) */
        u_short         va_mode;        /* files access mode and type */
        short           va_nlink;       /* number of references to file */
        vuid_t          va_uid;         /* owner user id */
        vgid_t          va_gid;         /* owner group id */
        long            va_fsid;        /* file system id (dev for now) */
        long            va_fileid;      /* file id */
        u_quad_t        va_size;        /* file size in bytes */
        long            va_blocksize;   /* blocksize preferred for i/o */
        struct coda_timespec va_atime;  /* time of last access */
        struct coda_timespec va_mtime;  /* time of last modification */
        struct coda_timespec va_ctime;  /* time file changed */
        u_long          va_gen;         /* generation number of file */
        u_long          va_flags;       /* flags defined for file */
        dev_t           va_rdev;        /* device special file represents */
        u_quad_t        va_bytes;       /* bytes of disk space held by file */
        u_quad_t        va_filerev;     /* file modification number */
        u_int           va_vaflags;     /* operations flags, see below */
        long            va_spare;       /* remain quad aligned */
};

4.2. pioctlインターフェース¶

アプリケーションはpioctlインターフェースを通じてCoda固有のリクエストを行うことができます。pioctlは、仮想ファイル/coda/.CONTROLを対象とした通常のioctlとして実装されています。pioctl呼び出しではこのファイルを開き、ファイルハンドルを取得しioctl呼び出しを行います。最後にファイルを閉じます。

カーネルの関与は、pioctlデータバッファ内のパスがCodaファイルシステム内のファイルであることを確認し、ファイルを開閉する機能とioctlメッセージを渡す機能に限定されます。

カーネルに渡されるデータパケットの形式は以下の通りです：

struct {
    const char *path;
    struct ViceIoctl vidata;
    int follow;
} data;

where:

struct ViceIoctl {
        caddr_t in, out;        /* Data to be transferred in, or out */
        short in_size;          /* Size of input buffer <= 2K */
        short out_size;         /* Maximum size of output buffer, <= 2K */
};

パスはCodaファイルでなければなりません。そうでない場合、ioctlアップコールは行われません。

注意

データ構造とコードは雑乱しています。これを整理する必要があります。

ここからは個々の呼び出しについてドキュメントを記述します:

の

out:

struct cfs_root_out {

この呼び出しはCodaファイルシステムの初期化時に金星に対して行われます。結果がゼロの場合、cfs_root構造体はCodaファイルシステムのルートのViceFidを含みます。非ゼロの結果が発生した場合、その値は金星がCodaファイルシステムのルートを検出する際に遭遇したプラットフォーム依存のエラーコードを示します。

4.4. lookup¶

Summary

ディレクトリにオブジェクトが存在する場合、そのViceFidとタイプを検索します。

引数

in:

struct  cfs_lookup_in {
    ViceFid     VFid;
    char        *name;          /* Place holder for data. */
} cfs_lookup;

out:

struct cfs_lookup_out {
    ViceFid VFid;
    int vtype;
} cfs_lookup;
説明

この呼び出しはディレクトリエントリのViceFidとファイルタイプを確認するために行われます。要求されたディレクトリエントリは名前'name'を持ち、金星はcfs_lookup_in.VFidで指定されたディレクトリを検索します。結果がゼロの場合、cfs_lookup_out.VFidはターゲットのViceFidを、cfs_lookup_out.vtypeはcoda_vtypeを指定して、名前が示すオブジェクトのタイプを表します。結果がゼロでない場合、名前が存在しないか、検索中に困難があった（例：切断のため）ことを示します。

オブジェクトの名前は最大長CFS_MAXNAMLEN（現在は256で、0終端を含む）の8ビット文字列です。

金星がカーネル名キャッシュにオブジェクトを格納しないことを示すために、cfs_lookup.vtypeフィールドにCFS_NOCACHEをビットごとに論理和で設定することが極めて重要です。

注意

vtypeの型は現在間違っています。coda_vtypeにする必要があります。LinuxはCFS_NOCACHEを無視しています。注意が必要です。

Summary

5. ミニキャッシュとダウンコール¶

Coda FSドライバーは、アップコールの頻度を制限するために、検索やアクセスアップコールの結果をキャッシュできる。アップコールにはコストがあり、プロセスコンテキストのスイッチが必要になる。情報のキャッシュの対応として、VenusはFSドライバーにキャッシュされたエントリがフラッシュされるべきか、またはリネームされるべきことを通知する。

カーネルコードは一般的に、内部ファイルハンドル（BSDではvnode、Linuxではinode、WindowsではFileHandleと呼ばれる）をVenusが管理するViceFidと関連付ける構造を維持しなければなりません。その理由は、アップコールの実行やアップコール結果の利用に必要な頻繁な変換が行われるためです。このような関連付けオブジェクトはcnodeと呼ばれます。

現在のminicacheの実装では、キャッシュエントリが以下の情報を記録しています：

  1. ファイル名

  2. 対象オブジェクトを含むディレクトリのcnode

  3. 検索が許可されるCodaCredのリスト

  4. オブジェクトのcnode

Coda FSドライバの検索呼び出しでは、呼び出し元の名前、ディレクトリ、CodaCredを渡して、キャッシュから対象オブジェクトのcnodeを取得することが可能です。キャッシュはcnodeを返すか、見つからないことを示します。Coda FSドライバは、オブジェクトを変更または削除する際にはキャッシュエントリを無効化する必要があります。

Venusがキャッシュエントリがもはや有効でなくなったことを示す情報を取得した場合、カーネルにダウンコールを実行します。ダウンコールはCoda FSドライバによって捕捉され、以下に説明するようなキャッシュ無効化が行われます。ダウンコールのデータがカーネルメモリに読み込めなかった場合を除き、Coda FSドライバはエラーを返しません。

5.1. 無効化¶

この呼び出しに関する情報は利用できません。

5.2. クリーン¶

引数

なし

Summary

名前キャッシュを完全にクリアします。

説明

Venusは起動時および終了時にこの呼び出しを実行します。これにより、古いキャッシュ情報が保持されることを防ぎます。一部のオペレーティングシステムでは、カーネル名キャッシュを動的にオフにできるため、その際このダウンコールが実行されます。

説明

ファイルの属性をフラッシュします。ディレクトリ（奇数の vnode）の場合、その子項目をネームキャッシュから削除し、ファイル自体もネームキャッシュから除去します。

5.8. REPLACE¶

Summary

複数の名前の_fid_を置き換えます。

引数
struct cfs_replace_out { /* cfs_replace is a venus->kernel call */
    ViceFid NewFid;
    ViceFid OldFid;
} cfs_replace;
説明

このルーチンでは、ネームキャッシュ内のViceFidを別のものに置き換えます。これは、Venusが切断状態でグローバル_fid_とローカルに割り当てた一時_fid_を再統合時に置き換えるための機能として追加されました。その際、これらの_fid_の参照カウントがゼロでなくても処理可能です。

6. 初期化とクリーンアップ¶

このセクションでは、Coda FS Driverが起動時およびシャットダウンやVenusの失敗時に望ましい機能についての簡潔なヒントを示します。この論議に入る前に、Coda FS Driverが保持するデータについて繰り返し述べます。

  1. メッセージキュー

  2. cnodes

  3. ネームキャッシュエントリ

    ネームキャッシュエントリはドライバー専用なので、簡単に操作できます。メッセージキューは一般的に明確な初期化と破壊のポイントを持ちます。一方、cnodesははるかに繊細です。ユーザープロセスはCodaファイルシステムで参照カウントを保持しており、cnodesのクリーンアップは困難です。

リクエストは次の経路を通じて到達します：

  1. メッセージサブシステム

  2. VFSレイヤー

  3. pioctlインターフェース

    現在、pioctlはCoda用にVFSを通じて処理されるため、これらは同様に扱えます。

6.1. 要件¶

以下の要件を満たす必要があります：

  1. メッセージキューにはオープンとクローズのルーチンが必要です。Unixではキャラクタデバイスのオープンはこのようなルーチンです。

  • オープン前のメッセージの配置はできません。

  • オープンにより、まだ処理待ちの古いメッセージは削除されます。

  • クローズにより、upcallが完了できないと待機しているプロセスに通知されます。

  • クローズにより、メッセージキューによって割り当てられたすべてのメモリが解放されます。

  1. オープン時にネームキャッシュは空の状態に初期化されます。

  2. メッセージキューがオープンされる前には、すべてのVFS操作が失敗します。幸いなことに、Codaファイルシステムのマウントがオープン前に成功しないようにするだけで実現可能です。

  3. キューのクローズ後、VFS操作は成功しません。ここでは注意が必要で、いくつかの操作（検索、読み込み／書き込み、ディレクトリの読み取り）はupcallなしでも実行可能です。これらは明示的にブロックする必要があります。

  4. クローズ時にネームキャッシュはフラッシュされ、無効にされます。

  5. cnodesによって保持されるすべてのメモリは、upcallに依存せずに解放できます。

  6. ファイルシステムのアンマウントはupcallに依存せずに実行できます。

  7. Codaファイルシステムのマウントは、Venusがrootfidやrootfidの属性を取得できない場合、エラーハンドリングを含めて正常に失敗する必要があります。後者はVenusがマウントを試みる前にこれらのオブジェクトを取得することで実装するのが望ましいです。

注意

特にNetBSDですが、Linuxも同様に上述の要件を完全に実装していません。スムーズな動作のためにこれを修正する必要があります。

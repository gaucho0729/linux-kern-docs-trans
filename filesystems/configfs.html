configfsとは何ですか？¶

configfsはRAMベースのファイルシステムで、sysfsの機能の逆を行います。sysfsはカーネルオブジェクトのファイルシステムベースのビューですが、configfsはカーネルオブジェクト、またはconfig_itemsのファイルシステムベースのマネージャーです。

sysfsでは、オブジェクトがカーネル内で作成され（例えばデバイスが検出されたとき）、sysfsに登録されます。その属性はsysfsに表示され、ユーザー空間からreaddir(3)/read(2)を介して読み取れます。一部の属性はwrite(2)で変更可能かもしれません。重要な点は、オブジェクトがカーネル内で作成・破棄され、カーネルがsysfs表現のライフサイクルを制御し、sysfsはすべての情報を表示する窓であるということです。

configfsのconfig_itemは明示的なユーザー空間操作（mkdir(2)）で作成され、rmdir(2)で破棄されます。属性はmkdir(2)のタイミングで表示され、read(2)でデフォルト値を読み取れ、write(2)で新しい値を保存できます。sysfsと同様に、readdir(3)は項目や属性のリストを照会し、symlink(2)は項目をグループ化できます。sysfsとは異なり、表現のライフタイムは完全にユーザー空間によって駆動され、カーネルモジュールはこれを応答しなければなりません。

sysfsとconfigfsは同じシステム上で共存できます。どちらも他を置き換えるものではありません。

configfsの使用方法¶

configfsはモジュールとしてコンパイルするか、カーネルに組み込むことができます。アクセスするには以下を行います：

mount -t configfs none /config

configfsツリーはクライアントモジュールがロードされていない限り空です。これらはconfigfsにアイテムタイプを登録するサブシステムとして機能するモジュールです。クライアントサブシステムがロードされると、/config以下のサブディレクトリ（複数可能）に表示されます。sysfsと同様に、configfsツリーはマウントされていなくても常に存在します。

アイテムはmkdir(2)で作成され、そのタイミングでアイテムの属性も表示されます。readdir(3)で属性を確認し、read(2)でデフォルト値を読み取り、write(2)で新しい値を保存できます。1つの属性ファイルに複数の属性を混在させないでください。

configfsの属性には2つの種類があります：

  • sysfs属性と似た性質を持つ通常の属性は、最大1ページ（PAGE_SIZE、i386では4096バイト）の小さなASCIIテキストファイルです。1ファイルに1つの値のみを記録することが推奨され、sysfsと同じ注意点が適用されます。configfsはwrite(2)を用いてバッファ全体を一度に保存することを期待しています。通常のconfigfs属性に書き込む際、ユーザー空間のプロセスはまずファイル全体を読み込み、変更したい部分を修正した後、バッファ全体を再び書き戻す必要があります。

  • sysfsのバイナリ属性と類似していますが、セマンティクスにいくつかの軽微な変更があるバイナリ属性です。PAGE_SIZEの制限は適用されませんが、全体のバイナリ項目は単一のカーネルvmalloc’edバッファに収める必要があります。ユーザー空間からのwrite(2)呼び出しはバッファリングされ、属性のwrite_bin_attributeメソッドは最終的なclose(2)時に呼び出されるため、ユーザー空間はclose(2)の戻り値を確認して操作が成功したかを検証する必要があります。カーネルを悪意のあるユーザーがOOMさせるのを防ぐため、各バイナリ属性には最大バッファ値が設定されています。

項目を削除するにはrmdir(2)を使用します。他の項目がシンボリックリンク（symlink(2)）でこの項目を参照している場合、削除できません。リンクはunlink(2)で削除可能です。

Configuring FakeNBD: 例¶

ネットワークブロックデバイス（NBD）ドライバーがあり、リモートブロックデバイスにアクセスできるとします。これをFakeNBDと呼びます。FakeNBDはconfigfsを構成に使用します。明らかに、sysadminsが使用する便利なプログラムがありますが、そのプログラムがドライバーに情報を伝える必要があります。ここがconfigfsの出番です。

FakeNBDドライバーがロードされると、configfsに登録されます。readdir(3)はこれを見つけることができます。

# ls /config
fakenbd

fakenbd接続はmkdir(2)で作成できます。名前は任意ですが、ツールがその名前を何かしら利用する可能性があります。おそらくUUIDやディスク名です。

# mkdir /config/fakenbd/disk1
# ls /config/fakenbd/disk1
target device rw

ターゲット属性にはFakeNBDが接続するサーバーのIPアドレスが含まれます。デバイス属性はサーバー上のデバイスです。予想通り、rw属性は接続が読み取り専用か読み書きかを決定します。

# echo 10.0.0.1 > /config/fakenbd/disk1/target
# echo /dev/sda1 > /config/fakenbd/disk1/device
# echo 1 > /config/fakenbd/disk1/rw

これで完了です。これ以上のことはありません。今やデバイスはシェルを介して構成されました。

configfs でのコーディング¶

configfs内のすべてのオブジェクトはconfig_itemです。config_itemはサブシステム内のオブジェクトを反映しており、そのオブジェクトの属性はその値と一致しています。configfsはこのオブジェクトとその属性のファイルシステム表現を処理し、サブシステムは基本的なshow/storeのやり取り以外を無視できます。

アイテムはconfig_group内で作成および削除されます。グループは同じ属性と操作を持つアイテムのコレクションです。アイテムはmkdir(2)で作成され、rmdir(2)で削除されますが、configfsがこれを処理します。グループはこれらのタスクを行うための操作セットを持っています。

サブシステムはクライアントモジュールのトップレベルです。初期化時にクライアントモジュールがconfigfsにサブシステムを登録し、configfsファイルシステムのトップにディレクトリとして表示されます。サブシステムはまたconfig_groupであり、config_groupが行えるすべての操作を行えます。

struct config_item¶

struct config_item {
        char                    *ci_name;
        char                    ci_namebuf[UOBJ_NAME_LEN];
        struct kref             ci_kref;
        struct list_head        ci_entry;
        struct config_item      *ci_parent;
        struct config_group     *ci_group;
        struct config_item_type *ci_type;
        struct dentry           *ci_dentry;
};

void config_item_init(struct config_item *);
void config_item_init_type_name(struct config_item *,
                                const char *name,
                                struct config_item_type *type);
struct config_item *config_item_get(struct config_item *);
void config_item_put(struct config_item *);

一般的に、struct config_itemはコンテナ構造体に埋め込まれています。この構造体は実際にサブシステムが行っている内容を表します。この構造体のconfig_item部分がオブジェクトがconfigfsとやり取りする方法です。

ソースファイルで静的に定義されているか、親のconfig_groupによって作成されたかに関わらず、config_itemには_ init()関数のいずれかが呼ばなければなりません。これにより参照カウントが初期化され、適切なフィールドが設定されます。

config_itemのすべてのユーザーはconfig_item_get()を通じて参照を持ち、使用終了後にconfig_item_put()で参照を解放する必要があります。

単独ではconfig_itemはconfigfsで表示されるだけです。通常、サブシステムはアイテムが属性を表示および/または保存できるようにしたいです。そのためにタイプが必要です。

struct config_item_type¶

struct configfs_item_operations {
        void (*release)(struct config_item *);
        int (*allow_link)(struct config_item *src,
                          struct config_item *target);
        void (*drop_link)(struct config_item *src,
                         struct config_item *target);
};

struct config_item_type {
        struct module                           *ct_owner;
        struct configfs_item_operations         *ct_item_ops;
        struct configfs_group_operations        *ct_group_ops;
        struct configfs_attribute               **ct_attrs;
        struct configfs_bin_attribute           **ct_bin_attrs;
};

config_item_typeの最も基本的な機能は、config_itemに行える操作を定義することです。動的に割り当てられたすべてのアイテムはct_item_ops->release()メソッドを提供する必要があります。このメソッドはconfig_itemの参照カウントがゼロになるときに呼び出されます。

struct configfs_attribute¶

struct configfs_attribute {
        char                    *ca_name;
        struct module           *ca_owner;
        umode_t                  ca_mode;
        ssize_t (*show)(struct config_item *, char *);
        ssize_t (*store)(struct config_item *, const char *, size_t);
};

config_itemが属性をアイテムのconfigfsディレクトリ内のファイルとして表示したい場合、その属性を記述するconfigfs_attributeを定義する必要があります。その後、属性をNULL終端の配列config_item_type->ct_attrsに追加します。アイテムがconfigfsに表示されると、属性ファイルはconfigfs_attribute->ca_nameというファイル名で表示され、configfs_attribute->ca_modeがファイルのパーミッションを指定します。

属性が読み取り可能であり、showメソッドを提供している場合、ユーザー空間が属性の読み取り（read(2)）を要求するたびに、そのメソッドが呼び出されます。属性が書き込み可能であり、storeメソッドを提供している場合、ユーザー空間が属性の書き込み（write(2)）を要求するたびに、そのメソッドが呼び出されます。

struct configfs_bin_attribute¶

struct configfs_bin_attribute {
        struct configfs_attribute       cb_attr;
        void                            *cb_private;
        size_t                          cb_max_size;
};

バイナリ属性は、ファイルとしてのコンテンツをアイテムのconfigfsディレクトリに表示するためにバイナリのblobを使用する場合に使用されます。これを実現するには、NULL終端の配列config_item_type->ct_bin_attrsにバイナリ属性を追加します。アイテムがconfigfsに表示されると、属性ファイルはconfigfs_bin_attribute->cb_attr.ca_nameというファイル名で表示されます。configfs_bin_attribute->cb_attr.ca_modeはファイルのパーミッションを指定します。cb_privateメンバはドライバが使用するために提供され、cb_max_sizeメンバは使用するvmallocバッファの最大サイズを指定します。

バイナリ属性が読み取り可能であり、config_itemがread_bin_attribute()メソッドを提供している場合、ユーザー空間が属性の読み取り（read(2)）を要求するたびに、そのメソッドが呼び出されます。書き込み（write(2)）については逆の動作が行われます。読み書きはバッファリングされるため、1回の読み書きのみが行われ、属性はこれに直接関与する必要がありません。

struct config_group¶

config_itemは真空の状態で存在できません。作成するには、config_group上のmkdir(2)が必要です。これにより、子アイテムが作成されます:

struct config_group {
        struct config_item              cg_item;
        struct list_head                cg_children;
        struct configfs_subsystem       *cg_subsys;
        struct list_head                default_groups;
        struct list_head                group_entry;
};

void config_group_init(struct config_group *group);
void config_group_init_type_name(struct config_group *group,
                                 const char *name,
                                 struct config_item_type *type);

config_group構造体はconfig_itemを含みます。このアイテムを正しく設定することで、グループは自身の権利としてアイテムとして振る舞うことができます。ただし、これ以上に機能もあります：子アイテムやグループを作成できます。これは、グループのconfig_item_type上で指定されたグループ操作によって実現されます:

struct configfs_group_operations {
        struct config_item *(*make_item)(struct config_group *group,
                                         const char *name);
        struct config_group *(*make_group)(struct config_group *group,
                                           const char *name);
        int (*commit_item)(struct config_item *item);
        void (*disconnect_notify)(struct config_group *group,
                                  struct config_item *item);
        void (*drop_item)(struct config_group *group,
                          struct config_item *item);
};

グループはct_group_ops->make_item()メソッドを提供することで子アイテムを作成します。このメソッドが提供されている場合、グループのディレクトリ上のmkdir(3)から呼び出されます。サブシステムは新しいconfig_item（もしくはそのコンテナ構造体）を割り当て、初期化し、configfsに返します。configfsはその後、ファイルシステムツリーを更新して新しいアイテムを反映します。

サブシステムが子アイテムをグループとして扱いたい場合、ct_group_ops->make_group()メソッドを提供します。それ以外の動作は同じで、グループの_group_init()関数を使用して処理されます。

最後に、ユーザー空間がアイテムまたはグループに対してrmdir(2)を呼び出すと、ct_group_ops->drop_item()が呼び出されます。config_groupはconfig_itemの一種であるため、別途drop_group()メソッドを用意する必要はありません。サブシステムは、アイテムの割当時に初期化された参照に対してconfig_item_put()を呼び出す必要があります。サブシステムが処理を行う必要がない場合、ct_group_ops->drop_item()メソッドを省略できます。この場合、configfsはサブシステムの代わりにアイテムに対してconfig_item_put()を呼び出します。

重要:

drop_item()はvoid（戻り値なし）であり、失敗する可能性はありません。rmdir(2)が呼び出されると、configfsはファイルシステムツリーからアイテムを必ず削除します（子アイテムが存在しないと仮定します）。サブシステムはこれを処理する責任があります。サブシステムが他のスレッドでアイテムへの参照を保持している場合、メモリは安全です。アイテムが実際にサブシステムの使用から完全に消失するまでに時間がかかる場合がありますが、configfsからは既に削除されています。

drop_item()が呼び出される際、アイテムのリンクはすでに破壊されています。親に参照が存在しなくなり、アイテム階層での位置もありません。クライアントがこの破壊処理前にクリーンアップを行う必要がある場合、サブシステムはct_group_ops->disconnect_notify()メソッドを実装できます。このメソッドは、configfsがファイルシステムビューからアイテムを削除した後で、親グループからアイテムを削除する前に関数が呼び出されます。drop_item()と同様に、disconnect_notify()もvoidであり失敗しません。クライアントサブシステムはここで参照を解放すべきではありません。drop_item()で処理する必要があります。

config_groupは子アイテムが存在する間は削除できません。これはconfigfsのrmdir(2)コードで実装されています。->drop_item()は呼び出されません（アイテムがまだ解放されていないため）。rmdir(2)はディレクトリが空でないため失敗します。

struct configfs_subsystem¶

サブシステムは通常モジュール初期化時に関数を登録する必要があります。これにより、configfsがファイルツリーにサブシステムを表示するようになります:

struct configfs_subsystem {
        struct config_group     su_group;
        struct mutex            su_mutex;
};

int configfs_register_subsystem(struct configfs_subsystem *subsys);
void configfs_unregister_subsystem(struct configfs_subsystem *subsys);

サブシステムはトップレベルのconfig_groupとミューテックスから構成されます。グループは子config_itemが作成される場所です。サブシステムではこのグループは通常静的に定義されます。configfs_register_subsystem()を呼び出す前に、サブシステムは通常のgroup _init()関数でグループを初期化し、ミューテックスも初期化しておく必要があります。

登録呼び出しが返ると、サブシステムは動作開始し、configfs経由で表示されます。この時点でmkdir(2)が呼び出され、サブシステムは準備ができている必要があります。

例¶

これらの基本的な概念の最も良い例は、samples/configfs/configfs_sample.cにあるsimple_childrenサブシステム/グループとsimple_childアイテムです。これは、属性を表示および保存する単純なオブジェクトと、これらの子を生成および破壊する単純なグループを示しています。

階層ナビゲーションとサブシステムミューテックス¶

configfsは追加の特典を提供しています。config_groupsとconfig_itemsは、ファイルシステム上に出現するため階層構造を形成しています。サブシステムは決してファイルシステムの部分に触れることがありませんが、この階層構造に興味を持つ可能性があります。そのため、階層構造はconfig_group->cg_childrenとconfig_item->ci_parent構造メンバを通じて反映されています。

サブシステムはcg_childrenリストとci_parentポインタを通じて、自身が作成したツリーを確認できます。ただし、configfsが階層構造を管理する際の競合状態を避けるため、configfsはサブシステムミューテックスを使用して変更を保護します。サブシステムが階層構造をナビゲートする際には、常にサブシステムミューテックスの保護下で行う必要があります。

サブシステムは、新たに割り当てられたアイテムがこの階層構造にリンクされるまでミューテックスを取得できません。同様に、アイテムが未リンク状態のまま解除されるまでミューテックスを取得できません。これにより、configfs内ではアイテムのci_parentポインタが常にNULLにならず、アイテムは親のcg_childrenリストにのみその期間存在します。これにより、サブシステムはミューテックスを保持している間、ci_parentとcg_childrenを信頼して利用できます。

symlink(2)を介したアイテム集約¶

configfsはgroup->itemの親子関係を通じて単純なグループを提供します。しかし、多くの場合、より大きな環境では親子関係を超えた集約が必要になります。これはsymlink(2)を通じて実装されます。

config_itemはct_item_ops->allow_link()とct_item_ops->drop_link()メソッドを提供できます。allow_link()メソッドが存在する場合、symlink(2)はconfig_itemをリンクのソースとして指定可能になります。これらのリンクはconfigfsのconfig_item間でのみ許可され、configfsファイルシステム外でのsymlink(2)呼び出しは拒否されます。

symlink(2)が呼び出される際、ソースのconfig_itemのallow_link()メソッドは自身とターゲットアイテムを引数として呼び出されます。ソースアイテムがターゲットアイテムへのリンクを許可する場合、0を返します。ソースアイテムが特定の種類のオブジェクト（自身のサブシステム内のものなど）へのリンクのみを許可する場合、リンクを拒否したい場合があります。

シンボリックリンクからunlink(2)が呼び出されるとき、ソース項目は->drop_link()メソッドを通じて通知されます。->drop_item()メソッドと同様に、これはvoid関数であり失敗を返すことはできません。サブシステムはこの変更に対応する責任があります。

config_itemは他の項目にリンクしている間、または他の項目がリンクしている間は削除できません。configfsではダングリングシンボリックリンクは許容されません。

自動的に作成されるサブグループ¶

新しいconfig_groupは2種類の子config_itemを持つことを望む場合があります。これは->make_item()メソッド内のマジック名でコード化するよりも、ユーザー空間がこの差異を明示的に認識できるメソッドを提供する方がはるかに明確です。

一部の項目が他の項目と異なる挙動を示すグループを作成するのではなく、configfsは親グループの作成時に1つまたは複数のサブグループを自動的に作成するメカニズムを提供します。これにより、mkdir(“parent”)は「parent」、「parent/subgroup1」、…、「parent/subgroupN」が作成されます。項目タイプ1は「parent/subgroup1」に、項目タイプNは「parent/subgroupN」に作成されます。

これらの自動生成サブグループ、またはデフォルトグループは親グループの他の子項目を排除しません。ct_group_ops->make_group()が存在する場合、親グループに直接他の子グループを作成できます。

configfsサブシステムはconfigfs_add_default_group()関数を用いて親config_group構造体にデフォルトグループを追加することで指定します。各追加グループは親グループと同時にconfigfsツリーに展開されます。同様に、親グループとともに削除されます。追加の通知は提供されません。親グループが消滅する旨の->drop_item()メソッド呼び出しがサブシステムに通知されるとき、その親グループに関連するすべてのデフォルトグループ子も同時に消滅します。

この結果として、デフォルットグループはrmdir(2)で直接削除できません。また、親グループのrmdir(2)が子項目を確認する際には考慮されません。

依存するサブシステム¶

他のドライバが特定のconfigfs項目に依存する場合があります。たとえば、ocfs2マウントはハートビート領域アイテムに依存します。その領域アイテムがrmdir(2)で削除されると、ocfs2マウントはBUGを発生させるか読み取り専用にしなければなりません。これは望ましくありません。

configfsは2つの追加のAPIコールを提供しています: configfs_depend_item()とconfigfs_undepend_item()。クライアントドライバーは、既存のアイテムに対してconfigfs_depend_item()を呼び出して、configfsにそのアイテムが依存していることを通知できます。configfsはその後、rmdir(2)に対して-EBUSYを返します。アイテムがもはや依存していない場合、クライアントドライバーはconfigfs_undepend_item()を呼び出します。

これらのAPIはconfigfsのコールバックの下で呼び出すことはできません。なぜなら、競合するためです。これらはブロッキングしてメモリを割り当てることができます。クライアントドライバーは自ら呼び出すべきではありません。むしろ、外部サブシステムから呼び出されるAPIを提供するべきです。

これはどのように動作するのでしょうか？想像してみてください。ocfs2のマウントプロセス。マウント時にハートビート領域アイテムを要求します。これはハートビートコードへのコールによって実行されます。ハートビートコード内では、領域アイテムが検索されます。ここで、ハートビートコードはconfigfs_depend_item()を呼び出します。成功すれば、ハートビートは領域がocfs2に安全に渡せることを知ります。失敗すれば、それはすでに破棄されているため、ハートビートはエラーを丁寧に上位に伝達できます。

コミット可能なアイテム¶

注意:

コミット可能なアイテムは現在実装されていません。

一部のconfig_itemは有効な初期状態を持てません。つまり、アイテムの属性にデフォルト値を指定できないため、アイテムが作業を実行できません。ユーザースペースは、1つ以上の属性を設定した後、サブシステムがこのアイテムを表すエンティティを開始できるようにする必要があります。

上記のFakeNBDデバイスを考えてください。ターゲットアドレスがなければ および ターゲットデバイスがなければ、サブシステムはどのブロックデバイスをインポートすべきかわかりません。単純な例では、サブシステムはすべての適切な属性が設定されるのを待ってから接続するものと仮定しています。これは確かに機能しますが、今後すべての属性ストアが属性が初期化されているかを確認する必要があります。すべての属性ストアがその条件を満たすと接続を実行する必要があります。

より良い方法は、サブシステムにconfig_itemが準備完了であることを通知する明示的なアクションです。さらに重要なのは、明示的なアクションにより、サブシステムが属性が初期化されているかどうかを意味のある方法でフィードバックできるようになります。configfsはこれをコミット可能なアイテムとして提供しています。

configfsはまだ通常のファイルシステム操作のみを使用しています。アイテムはrename(2)によってコミットされます。アイテムは編集可能なディレクトリから編集不可なディレクトリへ移動します。

ct_group_ops->commit_item()メソッドを提供する任意のグループは、コミット可能なアイテムを持ちます。このグループがconfigfsに表示される場合、mkdir(2)はグループ内で直接動作しません。代わりに、グループには「live」と「pending」の2つのサブディレクトリが存在します。「live」ディレクトリはmkdir(2)やrmdir(2)をサポートせず、rename(2)のみを許可します。「pending」ディレクトリではmkdir(2)とrmdir(2)が可能です。アイテムは「pending」ディレクトリに作成され、その属性は任意に変更可能です。ユーザー空間はアイテムを「live」ディレクトリにリネームすることでコミットします。この時点でサブシステムが->commit_item()コールバックを受信します。必要な属性が満たされれば、メソッドはゼロを返し、アイテムが「live」ディレクトリに移動します。

「live」ディレクトリではrmdir(2)が動作しないため、アイテムは停止状態または「uncommitted（未確定）」状態にする必要があります。これもrename(2)を介して行われ、今回は「live」ディレクトリから「pending」ディレクトリへ戻します。サブシステムはct_group_ops->uncommit_object()メソッドを通じて通知されます。

リレーアプリケーションインターフェース (以前はrelayfsと呼ばれていた)¶

レレイインターフェースは、カーネルアプリケーションがカーネルからユーザー空間へ大容量のデータを効率的にログとして記録し転送するためのメカニズムを提供します。このメカニズムはユーザー定義の「レレイチャネル」として実装されます。

「レレイチャネル」は、CPUごとのカーネルバッファ（「チャネルバッファ」）として実装されたカーネル→ユーザー空間のデータ中継メカニズムです。各チャネルバッファはユーザー空間において通常のファイル（「レレイファイル」）として表現されます。カーネルクライアントは効率的な書き込み関数を使用してチャネルバッファにデータを書き込み、これらは自動的に現在のCPUのチャネルバッファにログとして記録されます。ユーザー空間アプリケーションはレレイファイルをmmap()またはread()で読み込み、データが利用可能になったときに取得します。レレイファイル自体はホストファイルシステム（例: debugfs）に作成され、以下に記述するAPIを使用してチャネルバッファと関連付けられます。

チャネルバッファにログとして記録されるデータの形式は完全にカーネルクライアントの自由です。レレイインターフェースはカーネルクライアントがバッファデータに構造を課すためのハックを提供しますが、データフィルタリングの実装はカーネルクライアントに委譲されています。これにより、シンプルな設計を維持します。

このドキュメントではレレイインターフェースAPIの概要を説明します。関数パラメータの詳細については、レレイインターフェースコード内の関数と併せて記述されています。詳細についてはそちらをご参照ください。

セマンティクス¶

各レレイチャネルはCPUごとに1つのバッファを持ち、各バッファは1つまたは複数のサブバッファを含みます。メッセージは最初のサブバッファに書き込まれますが、新たなメッセージを含むには十分な容量がなくなった場合、次のサブバッファに書き込まれます（存在する場合）。メッセージはサブバッファをまたがって分割されることはありません。この時点でユーザー空間に通知が送られ、最初のサブバッファを空にしながら、カーネルは次のサブバッファに継続して書き込みます。

サブバッファが満杯であることを通知された際、カーネルはそのサブバッファのうちどの部分がパディング（未使用領域）であるかを把握します。これは完全なメッセージがサブバッファに収まらなかったための空き領域です。ユーザー空間はこの情報を活用し、有効なデータのみをコピーできます。

コピーを完了した後、ユーザー空間はサブバッファが消費されたことをカーネルに通知できます。

レレイチャネルは、ユーザー空間がまだ収集していないデータを上書きするモードで動作できます。ユーザー空間がデータを消費するのを待つことなく、即座に上書きします。

リレーチャンネル自体は、ユーザー空間とカーネル間でのこのようなデータの通信を提供していません。これにより、カーネル側はシンプルに保つことができ、ユーザー空間に対して単一のインターフェースを強制しません。ただし、以下に記載するように、例や別途のヘルパーツールを提供しています。

read()インターフェースはパディングを削除し、内部的にreadサブバッファを消費するため、read(2)がチャネルバッファを空にするために使用される場合、カーネルとユーザー間の特別な通信は基本的な動作には必要ありません。

リレーファイアウォールの主な目標の一つは、カーネルデータをユーザー空間に伝達するための低負荷メカニズムを提供することです。read()インターフェースは使いやすくはなりますが、mmap()アプローチほど効率的ではありません。例コードはこの二つのアプローチ間のトレードオフをできるだけ小さくするように試みています。

klogおよびrelay-appsの例コード¶

リレーファイアウォール自体はすぐに使用可能ですが、操作を簡単にするためにいくつかのシンプルなユーティリティ関数と例が提供されています。

リレーアプリケーションの例を含むrelay-appsというtarballが、リレーフォーラムサイトで入手可能です。このtarballには、ユーザー空間とカーネル空間の両方の側にボイラープレートコードを含む.cファイルのペアからなる自立した例が含まれており、これらを組み合わせることで、日常的な管理作業を気にすることなくデータをディスクにストリーム送信するためのグルーブが提供されます。

「klogデバッグ関数」パッチ（relay-apps tarball内のklog.patch）は、チャネルが存在するかどうかに関係なく、フォーマットされたテキストやrawデータをチャネルに書き込むための高レベルのロギング関数をカーネルに提供します。これらの関数は、カーネルやカーネルモジュールのどこにでも無条件の「トレース」ステートメントを挿入できます。ただし、データが実際にログ出力されるのは「klogハンドラ」が登録されている場合のみです（klogおよびkleakの例を参照してください）。

リレーアプリケーションの例コードやklogを使用せずに、リレーアクセスインターフェースをからscratchで利用することも可能です。ただし、ユーザー空間とカーネル間の通信を実装する必要があります。これにより、バッファの状態（満杯、空、パディング量など）を双方が共有できるようになります。read()インターフェースはパディングを除去し、内部的に読み込みサブバッファを消費するため、read(2)がチャネルバッファを空にしている場合、基本的な動作にはカーネルとユーザー間の特別な通信は必要ありません。ただし、バッファ満杯などの状態は依然として何らかのチャネルを通じて通知する必要があります。

klogおよびリレーアプリケーションの例は、relay-apps tarballに含まれています。 http://relayfs.sourceforge.net

リレーアプリケーションインターフェースユーザースペースAPI¶

リレーアクセスインターフェースは、ユーザー空間がリレーチャネルバッファデータにアクセスするための基本的なファイル操作を実装しています。利用可能なファイル操作とその動作に関するコメントを以下に示します：

open()

ユーザーが既存のチャネルバッファを開くことを可能にします。

mmap()

呼び出し元のメモリ空間にチャネルバッファをマッピングします。注意点として、部分的なmmapは行えません。必ず全体をマッピングする必要があります。これはNRBUF * SUBBUFSIZEのサイズのファイルです。

read()

チャネルバッファの内容を読み込みます。読み込まれたバイトは読者によって消費されるため、その後の読み込みでは再利用できません。チャネルがno-overwriteモード（デフォルト）で使用されている場合、アクティブなカーネルライターが存在していてもいつでも読み込むことができます。チャネルがoverwriteモードで使用されており、アクティブなチャネルライターが存在する場合、結果が予測不能になる可能性があります。ユーザーは、チャネルへのログ出力をすべて終了した後にread()をoverwriteモードで使用する必要があります。サブバッファのパディングは自動的に除去されるため、読者には表示されません。

sendfile()

チャネルバッファのデータを出力ファイル記述子に転送します。サブバッファのパディングは自動的に除去されるため、読者には表示されません。

poll()

POLLIN/POLLRDNORM/POLLERRがサポートされています。サブバッファ境界が跨がれたときにユーザー アプリケーションが通知されます。

close()

チャネルバッファの参照カウントを減算します。参照カウントが0になると、つまりどのプロセスもカーネルクライアントもバッファを開いていない場合、チャネルバッファが解放されます。

ユーザー アプリケーションがリレーファイルを使用するためには、ホストファイルシステムがマウントされている必要があります。例えば：

mount -t debugfs debugfs /sys/kernel/debug

注意

ホストファイルシステムは、カーネルクライアントがチャネルを作成または使用する際にはマウントする必要がありません。ユーザー スペース アプリケーションがバッファデータにアクセスする必要がある場合にのみマウントする必要があります。

チャネルの作成¶

relay_open() チャネルと、それぞれのCPUごとのチャネルバッファを作成するための関数です。各チャネルバッファにはホストファイルシステムにファイルが作成され、ユーザー空間からマッピングや読み取りが可能です。ファイル名はbasename0…basenameN-1の形式で、NはオンラインCPUの数を表し、デフォルトではファイルシステムのルートに作成されます（親パラメータがNULLの場合）。リレーファイルを含むディレクトリ構造を作成したい場合は、ホストファイルシステムのディレクトリ作成関数を使用して作成し、親ディレクトリを debugfs_create_dir()に渡してください。 relay_open()ユーザーはチャネルが閉じるときに作成したディレクトリ構造をクリーンアップする責任があります。その際は、再びホストファイルシステムのディレクトリ削除関数を使用してください。例えば、 debugfs_remove().

チャネルを作成し、ホストファイルシステムのチャネルバッファに関連するファイルを関連付けるには、ユーザーがcreate_buf_file()とremove_buf_file()の2つのコールバック関数を定義する必要があります。create_buf_file()は、それぞれのCPUごとのバッファから呼ばれる関数で、ユーザーがチャネルバッファを表すファイルを作成するためのものです。コールバックは、作成したファイルのdentryを返す必要があります。remove_buf_file()も定義する必要があります。これはcreate_buf_file()で作成したファイルを削除する責任があり、 relay_open() の際に呼ばれます。 relay_close().

これらのコールバックの典型的な定義例を以下に示します。この場合、debugfsを使用しています:

/*
* create_buf_file() callback.  Creates relay file in debugfs.
*/
static struct dentry *create_buf_file_handler(const char *filename,
                                            struct dentry *parent,
                                            umode_t mode,
                                            struct rchan_buf *buf,
                                            int *is_global)
{
        return debugfs_create_file(filename, mode, parent, buf,
                                &relay_file_operations);
}

/*
* remove_buf_file() callback.  Removes relay file from debugfs.
*/
static int remove_buf_file_handler(struct dentry *dentry)
{
        debugfs_remove(dentry);

        return 0;
}

/*
* relay interface callbacks
*/
static struct rchan_callbacks relay_callbacks =
{
        .create_buf_file = create_buf_file_handler,
        .remove_buf_file = remove_buf_file_handler,
};

そして例 relay_open() それらを使用した呼び出し:

chan = relay_open("cpu", NULL, SUBBUF_SIZE, N_SUBBUFS, &relay_callbacks, NULL);

create_buf_file()コールバックが失敗したり、定義されていない場合、チャネル作成が失敗し、 relay_open() 失敗します。

各CPUごとのバッファの総サイズは、サブバッファ数をサブバッファサイズに掛けた値で計算されます。 relay_open()サブバッファのアイデアは、基本的にNバッファへのダブルバッファリングの拡張であり、アプリケーションがバッファ境界でのランダムアクセススキーマを簡単に実装できるようにするものです。これは、一部の高負荷アプリケーションにおいて重要です。サブバッファの数とサイズはアプリケーションに完全に依存しており、同じアプリケーションでも、状況によってこれらのパラメータの値が異なります。通常、適切な値は実験を通じて決定するのが良いですが、一般的には1つのサブバッファのみを持つことは悪いアイデアです。チャンネルモードによってはデータの上書きまたはイベントの喪失が確実に発生します。

create_buf_file()の実装は、デフォルトのCPUごとのセットではなく、単一の「グローバル」バッファの作成を可能にするように定義することもできます。これは、システム全体のイベントの相対順序を確認するのに主に興味があるアプリケーションにとって有用です。このような場合、後処理ステップでのCPUごとのファイルのマージ/ソートに明示的なタイムスタンプを保存する必要がありません。

To have relay_open() グローバルバッファを作成するには、create_buf_file()の実装では、単一バッファを表すファイルを作成するだけでなく、is_globalの出力パラメータをゼロ以外の値に設定する必要があります。グローバルバッファの場合、create_buf_file()とremove_buf,File()は一度だけ呼ばれます。通常のチャンネル書き込み関数（例：relay_write()）は引き続き使用可能です。どのCPUからの書き込みも透明にグローバルバッファに反映されますが、グローバルバッファであるため、呼び出し元はこのバッファに適切なロックをかける必要があります。これはスピンロックで書き込みをラップするか、relay.hから書き込み関数をコピーしてローカルバージョンを作成し、内部で適切なロックを実施する方法があります。

private_dataが渡される relay_open() クライアントがチャンネルに関連付けるユーザー定義データを可能にし、create_buf_file()を含む即座に利用可能（chan->private_dataまたはbuf->chan->private_dataを通じて）です。

バッファのみのチャンネル¶

これらのチャンネルはファイルを関連付けず、relay_open(NULL, NULL, …)で作成できます。このようなチャンネルは、VFSが起動する前のカーネルでの初期トレースなど、特定のシナリオで有用です。このような場合、バッファのみのチャンネルを開き、その後、カーネルがファイルを処理できるようになるときに relay_late_setup_files() ユーザー空間にバッファデータを露出するための関数を呼び出します。

チャンネル ‘モード’¶

レレーアクセラは、「オーバーライド」モードか「オーバーライドしない」モードのいずれかで使用できます。モードは、以下の説明で示すように、subbuf_start()コールバックの実装によって完全に決定されます。subbuf_start()コールバックが定義されていない場合のデフォルトは「オーバーライドしない」モードです。デフォルトモードで十分で、チャネルデータを取得するためread()インターフェースを使用する予定であれば、このセクションの詳細は無視できます。このセクションの内容は主にmmap()実装に関連しています。

「オーバーライド」モード（別名「フライトレコーダー」モード）では、書き込みはバッファを連続して循環し、失敗することはありませんが、古いデータを無条件で上書きします（実際に消費されていなくても）。一方、「オーバーライドしない」モードでは、未消費のサブバッファの数がチャネル内のサブバッファの総数に等しい場合、書き込みが失敗し、つまりデータが失われる可能性があります。消費者がいないか、消費者がサブバッファを十分に処理できない場合、どちらのモードでもデータが失われる可能性があります。違いは、データがバッファの先頭から失われるか、末尾から失われるかです。

上記のように、レレーアクセラは、1つ以上のCPUごとのチャネルバッファから構成され、それぞれが円環バッファとして実装され、1つ以上のサブバッファに分割されています。メッセージは、以下の書き込み関数を通じて、チャネルの現在のCPUごとのバッファの現在のサブバッファに書き込まれます。メッセージが現在のサブバッファに収まらない場合（スペースが足りない場合）、クライアントはsubbuf_start()コールバックを通じて新しいサブバッファへの切り替えが行われる予定であることを通知されます。クライアントはこのコールバックを用いて、1) 適切な場合に次のサブバッファを初期化する、2) 適切な場合に前のサブバッファを終了する、3) 次のサブバッファへの切り替えを実際に実行するかどうかを示すブール値を返す、という3つの動作を行います。

「オーバーライドしない」モードを実装するには、ユーザースペースクライアントがsubbuf_start()コールバックの実装を提供します。以下のような形で実装されます：

static int subbuf_start(struct rchan_buf *buf,
                        void *subbuf,
                        void *prev_subbuf,
                        unsigned int prev_padding)
{
        if (prev_subbuf)
                *((unsigned *)prev_subbuf) = prev_padding;

        if (relay_buf_full(buf))
                return 0;

        subbuf_start_reserve(buf, sizeof(unsigned int));

        return 1;
}

現在のバッファが満杯である場合、つまりすべてのサブバッファが未消費のままの場合、コールバックは0を返して、バッファの切り替えをまだ行わないことを示します。つまり、消費者が現在の準備ができたサブバッファを読み取る機会があるまで待機します。この関数が意味を持つためには、消費者がサブバッファが消費されたことを通じてレレーアクセラインターフェースに通知する責任があります。 relay_buf_full() via relay_subbufs_consumed()バッファに書き込む試みは、再度subbuf_start()コールバックが同じパラメータで呼び出されます。消費者が1つ以上の準備ができているサブバッファを消費した場合に限り、 relay_buf_full() 0を返します。その場合、バッファの切り替えが続きます。

「上書き」モードにおけるsubbuf_start()コールバックの実装は非常に似ています：

static int subbuf_start(struct rchan_buf *buf,
                        void *subbuf,
                        void *prev_subbuf,
                        size_t prev_padding)
{
        if (prev_subbuf)
                *((unsigned *)prev_subbuf) = prev_padding;

        subbuf_start_reserve(buf, sizeof(unsigned int));

        return 1;
}

この場合、 relay_buf_full() チェックは意味がなく、コールバックは常に1を返します。これにより、バッファの切り替えは条件に関係なく行われます。このモードではクライアントがこの relay_subbufs_consumed() 関数を使用しても意味がありません。なぜなら、この関数は常に呼び出されないからです。

クライアントがどのコールバックも定義していない場合、またはsubbuf_start()コールバックを定義していない場合に使用されるデフォルトのsubbuf_start()実装は、最もシンプルな「上書き不可」モードを実装します。つまり、何もせず0を返すだけです。

サブバッファの先頭にヘッダー情報を予約するには、subbuf_start()コールバック内でsubbuf_start_reserve()ヘルパ関数を呼び出します。この予約領域はクライアントが望む情報を保存するために使用できます。上記の例では、各サブバッファにパディングカウントを保存するための領域が予約されています。これは、subbuf_start()実装内で前のサブバッファに値が設定されるため、前のサブバッファのパディング値はsubbuf_start()コールバックに渡されるとともに、前のサブバッファへのポインタも渡されます。なぜなら、パディング値はサブバッファが満たされるまで判明しないためです。チャンネルがオープンされる際には、最初のサブバッファにもsubbuf_start()コールバックが呼び出され、クライアントがそのサブバッファに領域を確保する機会を与えます。この場合、コールバックに渡される前のサブバッファポインタはNULLとなるため、クライアントは前のサブバッファに書き込む前にprev_subbufポインタの値を確認する必要があります。

チャンネルへの書き込み¶

カーネルクライアントは、relay_write()または__relay_write()を使用して、現在のCPUのチャンネルバッファにデータを書き込みます。relay_write()は主なログ記録関数であり、ローカルIRQセーブを用いてバッファを保護します。割り込みコンテキストからログを記録する可能性がある場合に使用すべきです。割り込みコンテキストから決してログを記録しないことが確実である場合、__relay_write()を使用できます。これはプリエンプションのみを無効化します。これらの関数は戻り値を返さないため、失敗したかどうかを判定することはできません。高速なログ記録パスでは戻り値をチェックする必要がないと想定されており、バッファが満杯で上書き不可モードが有効になっている場合を除けば常に成功するものとされています。この場合、subbuf_start()コールバックで失敗した書き込みを検出するために呼び出します。 relay_buf_full() さらに、

relay_reserve()は、後で書き込むことができるチャンネルバッファ内のスロットを確保するために使用されます。これは、一時的なバッファにデータをステージングせずに直接チャンネルバッファに書き込む必要があるアプリケーションで通常使用されます。実際の書き込みがスロットを確保した後すぐに実行されない可能性があるため、relay_reserve()を使用するアプリケーションは、サブバッファ内に確保されたスペースや別個の配列として、実際に書き込まれたバイト数をカウントできます。relay-appsアーカイブの'reserve'例を参照してください。 http://relayfs.sourceforge.net 書き込み操作はクライアントの制御下で行われ、確保と分離されているため、relay_reserve()はバッファを一切保護しません。relay_reserve()を使用する際には、クライアントが適切な同期を提供する必要があります。

チャンネルの閉じ方¶

クライアントは、チャンネルを使用が終了した際に relay_close() を呼び出します。チャンネルとその関連するバッファは、チャンネルバッファへの参照がなくなったときに破壊されます。 relay_flush() すべてのチャンネルバッファでサブバッファの切り替えを強制し、チャンネルが閉じられる前に最後のサブバッファを確定および処理するために使用できます。

雑項¶

一部のアプリケーションでは、新しいチャンネルを開閉するたびにチャンネルを保持し再利用する方が望ましい場合があります。 relay_reset() この目的には使用できます。これは、チャンネルバッファメモリを再割当したり既存のマッピングを破棄することなくチャンネルを初期状態に戻します。ただし、チャンネルが現在書き込まれていない状態で安全に実行できる場合にのみ呼び出す必要があります。

最後に、さまざまな目的で使用できるユーティリティコールバックがいくつかあります。buf_mapped()は、チャネルバッファがユーザー空間からmmappedされるたびに呼び出され、buf_unmapped()はそのバッファがunmappedされるときに呼び出されます。クライアントはこの通知を使用して、カーネルアプリケーション内でアクションをトリガーできます。たとえば、チャネルへのログ出力を有効/無効にしたりできます。

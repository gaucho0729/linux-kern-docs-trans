Squashfs 4.0ファイルシステム¶

Squashfs は Linux 用の圧縮された読み取り専用ファイルシステムです。

zlib、lz4、lzo、または xz の圧縮アルゴリズムを用いてファイル、インODE、ディレクトリを圧縮します。システム内のインODEは非常に小さく、すべてのブロックがデータオーバーヘッドを最小限に抑えられるようにパックされています。ブロックサイズは4K以上で最大1Mバイト（デフォルトブロックサイズは128Kバイト）までサポートされています。

Squashfs は一般的な読み取り専用ファイルシステム用途、アーカイブ用途（.tar.gz ファイルの代わりに使用される場合）、および低オーバーヘッドが必要な制約されたブロックデバイス/メモリシステム（例: 埋め込みシステム）で使用されるように設計されています。

メールリスト: squashfs-devel@lists.sourceforge.net ウェブサイト: www.squashfs.org

Squashfs はデータ、インODE、ディレクトリを圧縮します。さらに、インODEおよびディレクトリデータは高密度に圧縮され、バイト境界でパックされています。各圧縮インODEの平均長さは8バイト（正確な長さはファイルタイプによって異なります。例: 普通のファイル、ディレクトリ、シンボリックリンク、ブロック/キャラクタデバイスインODEはそれぞれ異なるサイズを持ちます）です。

2. Squashfsの使用方法¶

Squashfs は読み取り専用ファイルシステムであるため、mksquashfs プログラムを使用して populated squashfs ファイルシステムを作成する必要があります。このほかの squashfs ユーティリティは、 http://www.squashfs.orgから取得できます。使用方法の説明もこのサイトから取得できます。

squashfs-tools 開発ツリーは現在 kernel.org に移動しました

git://git.kernel.org/pub/scm/fs/squashfs/squashfs-tools.git

Squashfs ファイルシステムは最大9つの部分から構成され、バイトアライメントでパックされています:

|---------------|
|  compression  |
|    options    |
|---------------|
|  datablocks   |
|  & fragments  |
|---------------|
|  inode table  |
|---------------|
|   directory   |
|     table     |
|---------------|
|   fragment    |
|    table      |
|---------------|
|    export     |
|    table      |
|---------------|
|    uid/gid    |
|  lookup table |
|---------------|

圧縮データブロックはソースディレクトリからファイルが読み込まれるたびにファイルシステムに書き込まれ、重複をチェックします。すべてのファイルデータが書き込まれた後、完了したインODE、ディレクトリ、フラグメント、エクスポート、uid/gid ラックアップ、xattr テーブルが書き込まれます。

3.1 圧縮オプション¶

圧縮器は圧縮に特有のオプション（例: 辞書サイズ）をオプションでサポートできます。非デフォルトの圧縮オプションが使用された場合、これらはここで保存されます。

3.2 イノデ¶

メタデータ（インODEとディレクトリ）は8キロバイトブロックで圧縮されます。各圧縮ブロックは、2バイトの長さが先頭に付いており、上位ビットが設定されている場合、ブロックは未圧縮です。-noIオプションが設定されている場合、または圧縮ブロックが未圧縮ブロックよりも大きい場合、ブロックは未圧縮になります。

インODEはメタデータブロックに詰め込まれており、ブロック境界に合わせて配置されないため、インODEは圧縮ブロックと重なっています。インODEは、インODEを含む圧縮メタデータブロックの位置を表す48ビットの番号で識別され、そのブロック内のインODEの位置（<ブロック、オフセット>）が記録されています。

圧縮効率を最大化するため、各ファイルタイプ（通常ファイル、ディレクトリ、デバイスなど）に別々のインODEが用意されており、インODEの内容と長さはファイルタイプによって異なります。

さらに圧縮効率を高めるため、通常ファイルインODEとディレクトリインODEの2種類が定義されています。1種類は頻繁に出現する通常ファイルやディレクトリに最適化されており、もう1種類は追加情報を保存する必要がある拡張タイプです。

3.3 ディレクトリ¶

インODE同様に、ディレクトリも圧縮メタデータブロックに詰め込まれており、ディレクトリテーブルに保存されます。ディレクトリは、メタブロック内のディレクトリの開始アドレスと、復元されたブロック内のオフセット（<ブロック、オフセット>）を使用してアクセスされます。

ディレクトリはやや複雑な構造で整理されており、単純なファイル名の一覧ではありません。この構造は、（ほとんどの場合）ファイルのインODEが同じ圧縮メタデータブロックに存在するため、共有された開始ブロックを共有できるという特徴を活用しています。そのため、ディレクトリは2段階のリスト構造で整理されており、共有された開始ブロック値を含むディレクトリヘッダと、そのブロックを共有するディレクトリエントリのシーケンスが含まれています。インODEの開始ブロックが変更されるたびに新しいディレクトリヘッダが書き込まれます。ディレクトリヘッダ/ディレクトリエントリリストは必要に応じて繰り返されます。

ディレクトリはアルファベット順に並べられ、ファイルの検索を高速化するためのディレクトリインデックスを含めることができます。ディレクトリインデックスは、メタブロックごとに1つのエントリを保持し、各メタデータブロック内の最初のディレクトリヘッダへのインデックス/ファイル名のマッピングを記録します。ディレクトリはアルファベット順に並べられ、検索時にはインデックスを線形にスキャンして、検索対象のファイル名よりもアルファベット順で大きい最初のファイル名を探します。この時点で、ファイル名が含まれるメタデータブロックの位置が特定されます。インデックスの一般的な考え方は、ディレクトリの長さに関係なく、検索を行うために1つのメタデータブロックのみをデコンプレスする必要があることです。このスキームには、追加のメモリオーバーヘッドを必要とせず、ディスク上の追加ストレージも不要という利点があります。

3.4 ファイルデータ¶

通常のファイルは、連続した圧縮ブロックのシーケンス、および/または圧縮されたフラグメントブロック（テールエンドパックブロック）から構成されます。各データブロックの圧縮サイズは、ファイルのインノード内に含まれるブロックリストに記録されます。

「大規模な」ファイル（256 Mbytes以上）のデータブロックへのアクセスを高速化するため、コードはブロックインデックスからデータブロックのディスク上の位置へのマッピングをキャッシュするインデックスキャッシュを実装しています。

インデックスキャッシュにより、Squashfsは大規模なファイル（最大1.75 TiB）を処理しながら、ディスク上のシンプルかつ空間効率の良いブロックリストを維持できます。キャッシュはスロットに分割され、最大8つの224 GiBファイル（128 KiBブロック）をキャッシュします。より大きなファイルは複数のスロットを使用し、1.75 Tiのファイルはすべての8スロットを使用します。インデックスキャッシュはメモリ効率が高く、デフォルトでは16 KiBを使用します。

3.5 フラグメント検索テーブル¶

通常のファイルは、ディスク上のフラグメント位置と圧縮サイズをマッピングするフラグメントインデックスを含む場合があります。このフラグメント検索テーブルはメタデータブロック内に圧縮して保存され、もう一つのインデックステーブルによって位置が特定されます。この2番目のインデックステーブルはアクセス速度を重視し（またサイズが小さいため）、マウント時に読み込まれてメモリにキャッシュされます。

3.6 Uid/gid検索テーブル¶

空間効率を重視して、通常のファイルはuidとgidのインデックスを保存し、id検索テーブルを使用して32ビットのuid/gidに変換します。このテーブルはメタデータブロック内に圧縮して保存され、もう一つのインデックステーブルによって位置が特定されます。この2番目のインデックステーブルはアクセス速度を重視し（またサイズが小さいため）、マウント時に読み込まれてメモリにキャッシュされます。

3.7 エクスポートテーブル¶

SquashfsファイルシステムをNFSなどの手段でエクスポート可能にするため、ファイルシステムはオプションで（-no-exports Mksquashfsオプションで無効化可能）inode番号からinodeのディスク上の位置を検索するテーブルを含めることができます。これは、エクスポートコードが期限切れ/フラッシュされたinodeを再生成する際、inode番号がファイルハンドルとして渡されたときにディスク上のinode位置をマッピングするために必要です。

このテーブルは圧縮されたメタデータブロックに格納され、別のインデックステーブルがこれらの位置を検索するために使用されます。アクセス速度の向上（およびテーブルのサイズが小さいため）のために、この第二のインデックステーブルはマウント時に読み込まれてメモリにキャッシュされます。

3.8 Xattrテーブル¶

xattrテーブルは各inodeの拡張属性を含み、各inodeのxattrはリスト形式で格納されます。リストの各エントリにはタイプ、名前、値のフィールドが含まれます。タイプフィールドはxattrのプレフィックス（「user.」、「trusted.」など）をエンコードし、名前/値フィールドの解釈方法も指定します。現在、タイプは値がインラインで保存される（その場合、値フィールドにxattrの値が含まれる）か、オフラインで保存される（その場合、値フィールドに実際の値が保存されている場所への参照が含まれる）かを示します。これにより、大容量の値をオフラインで保存し、スキャンおよび検索のパフォーマンスを向上させることができ、また値の重複を防ぐことも可能です。

xattrリストは圧縮された8Kメタデータブロックにパックされます。inodeのオーバーヘッドを減らすため、各inode内にxattrリストのディスク上の位置を保存する代わりに、32ビットのxattr IDが保存されます。このxattr IDは、別のxattr ID検索テーブルを介してxattrリストの位置にマッピングされます。

4.2 Squashfs内部キャッシュ¶

Squashfsのブロックは圧縮されています。最近アクセスしたデータの繰り返し解凍を避けるため、Squashfsは2つの小さなメタデータとフラグメントキャッシュを使用します。

ファイルデータブロックはキャッシュされません。これらは通常の方法でページキャッシュに展開され、キャッシュされます。キャッシュは、メタデータ（インノデまたはディレクトリ）やフラグメントへのアクセス結果として読み込まれたフラグメントおよびメタデータブロックを一時的にキャッシュするために使用されます。メタデータとフラグメントは圧縮効率を高めるためにブロックにパックされているため、特定のメタデータまたはフラグメントの読み込みは、それとパックされている他のメタデータ/フラグメントも一緒に取得します。参照の局所性により、これらは近い将来に読み込まれる可能性があります。一時的にキャッシュすることで、追加の読み込みと展開を必要とすることなく、近い将来のアクセスが可能になります。

今後、この内部キャッシュは、カーネルページキャッシュを使用する実装に置き換わる可能性があります。ページキャッシュはページ単位で動作するため、ロックや関連するレース条件といった複雑さが導入される可能性があります。

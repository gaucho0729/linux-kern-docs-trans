第1章: システム情報の収集¶

この章では¶

  • 擬似ファイルシステム/procの性質と、稼働中のLinuxシステムに関する情報を提供する能力を調査します

  • /procの構造を検証します

  • システム上で実行中のカーネルおよびプロセスに関するさまざまな情報を明らかにします

プロセスファイルシステムは、カーネル内の内部データ構造へのインターフェースとして機能します。システムに関する情報を取得し、実行時（sysctl）に特定のカーネルパラメータを変更するのに利用できます。

まず、/procの読み取り専用部分を見てみましょう。第2章では、/proc/sysを用いて設定を変更する方法を紹介します。

1.1 プロセス固有のサブディレクトリ¶

/procディレクトリには（その他の情報も含めて）、システム上で実行中の各プロセスに対応するサブディレクトリが含まれており、プロセスID（PID）で名付けられています。

「self」リンクは、ファイルシステムを読み取るプロセスを指します。各プロセスサブディレクトリには、表1-1に示すエントリが含まれています。

注意点として、/proc/<pid>またはその中のファイルやサブディレクトリへのオープンファイルディスクリプタは、<pid>が終了した場合でも、<pid>が他のプロセスに再利用されるのを防ぐことはありません。オープンされている/proc/<pid>ファイルディスクリプタに対して行われる操作は、カーネルが偶然にもプロセスID <pid>を割り当てた場合でも、新しいプロセスに対して動作しません。代わりに、これらのFD（ファイルディスクリプタ）に対する操作は通常、ESRCHで失敗します。

最初の行は/proc/PID/mapsで表示されるマッピングの情報と同じです。続く行はマッピングのサイズ（size）、VMAをバックする際に割り当てられたページのサイズ（KernelPageSize）、通常はページテーブルエントリのサイズと同じです。MMUがVMAをバックする際に使用するページサイズ（ほとんどの場合、KernelPageSizeと同じ）、マッピングが現在RAMにрезидентしている部分（RSS）、プロセスのこのマッピングに対する割合（PSS）、そしてマッピング内のクリーンで汚染された共有およびプライベートページの数を示します。

プロセスの「プロポーショナルセットサイズ」（PSS）は、メモリ内のページ数をカウントしたものです。各ページは共有しているプロセス数で割られます。したがって、プロセスが1000ページをすべて自分だけに占有し、1000ページを1つの他のプロセスと共有している場合、PSSは1500になります。

注意：MAP_SHAREDマッピングの一部であっても、単一のpteがマップされている場合、つまり現在1つのプロセスのみが使用している場合、これはプライベートとしてカウントされ、共有としてカウントされません。

「参照」は現在参照またはアクセスされたメモリの量を示します。

「Anonymous」は、どのファイルにも属さないメモリの量を示します。ファイルに関連するマッピングであっても、MAP_PRIVATEとページが変更された場合、ファイルのページはプライベートな匿名コピーに置き換えられます。

「LazyFree」は、madvise(MADV_FREE)でマークされたメモリの量を示します。madvise()によって即座に解放されません。メモリ圧力が発生した際に、メモリがクリーンであれば解放されます。現在の実装で使用される最適化により、表示される値が実際の値より低くなる可能性があることにご注意ください。これは望ましくない場合は、バグレポートを提出してください。

「AnonHugePages」は、透過的ヒューゲンページでバックアップされるメモリの量を示します。

この現象は、これらのファイルの部分的な読み取りが行われる間、メモリマップが変更されているときに通常発生します。競合状態を考慮しても、以下の保証を提供しています:

  1. マッピングされたアドレスは常に後ろへ進むことがなく、これにより2つの領域が重複することはありません。

  2. smaps/mapsウォークの寿命全体において、特定の仮想アドレスに何かが存在する場合、それに応じた出力が存在します。

  • Pss_Anon

  • Pss_File

  • Pss_Shmem

これらは、smapsで説明したように、匿名、ファイル、shmemページの比例的なシェアを表します。smapsでは各マッピングが含むページのタイプ（anon、file、またはshmem）を特定するため、これらのフィールドは省略されています。したがって、smaps_rollup内のすべての情報はsmapsから導出可能ですが、大幅に高いコストが伴います。

> echo 2 > /proc/PID/clear_refs

> echo 3 > /proc/PID/clear_refs

> echo 4 > /proc/PID/clear_refs

2.6.2*では/proc/interruptsが再び拡張されました。今回は/proc/interruptsがシステムで使用されているすべてのIRQベクターを表示するようにし、以前は「最も重要とされる」ものだけを表示していました。新しいベクターは以下の通りです：

THR

マシンチェック閾値カウンター（通常はメモリやキャッシュのECC訂正エラーをカウント）が設定可能な閾値を超えたときに発生する割り込み。一部のシステムでのみ利用可能です。

TRM

CPUの温度閾値を超えたときに発生する熱イベント割り込み。温度が通常に戻ったときにも発生する場合があります。

SPU

不正な割り込みは、IOデバイスがAPICに完全に処理される前に割り込みを上げて下げた場合に発生します。APICはこの割り込みを認識しますが、どのデバイスからのものか判っていません。このような場合、APICはIRQベクター0xffで割り込みを生成します。これはチップセットのバグによっても発生する可能性があります。

RES, CAL, TLB

再スケジューリング、コール、TLBフラッシュ割り込みは、OSの必要に応じて1つのCPUから別のCPUへ送信されます。通常、カーネル開発者や関心を持つユーザーがこれらの統計を用いて、特定のタイプの割り込みの発生頻度を確認します。

上記のIRQベクターは関連する場合にのみ表示されます。例えば、閾値ベクターはx86_64プラットフォームでは存在しません。シングルプロセッサのシステムでは他のベクターが抑制されます。執筆時点では、i386およびx86_64プラットフォームのみが新しいIRQベクターの表示をサポートしています。

smp_affinityはビットマスクで、IRQを処理できるCPUを指定できます。設定は以下のように行います：

> echo 1 > /proc/irq/10/smp_affinity

これは、IRQを処理するCPUが最初のCPUだけになることを意味しますが、5をエコーすることもでき、これによりIRQを処理するCPUは最初のCPUと3番目のCPUだけになります。

> cat /proc/irq/0/smp_affinity
ffffffff

代替インターフェースとしてsmp_affinity_listがあり、これはビットマスクではなくCPU範囲を指定可能にします:

> cat /proc/irq/0/smp_affinity_list
1024-1031

prof_cpu_maskは、システム全体のプロファイラーがプロファイリングするCPUを指定します。デフォルト値はffffffff（32個のCPUしかない場合のみすべてのCPU）です。

IRQのルーティングはIO-APICによって処理され、ラウンドロビン方式で許可されたすべてのCPU間で行われます。通常、カーネルはあなたより詳しい情報を持ち、より良い判断を下すため、デフォルト設定がほぼすべてのユーザーにとって最適です。[この注意は「ラウンドロビン」をサポートするIO-APICにのみ適用されます。]

カーネル内のフラグメンテーション回避は、異なる移動タイプのページを、メモリの連続領域（page block）にグループ化することで実現されます。page blockは通常、デフォルトのヒューゲページサイズ（例：X86-64では2MB）のサイズです。ページを移動可能な能力に基づいてグループ化することで、カーネルはpage block内からページを回収し、高オーダーの割当を満たすことができます。

pagetypinfoはまずpage blockのサイズに関する情報を示し、その後buddyinfoと同じような情報を提供しますが、migrate-typeごとに分解して表示します。最後には、各タイプのpage blockの数についての詳細が記載されています。

min_free_kbytesが適切にチューニングされている場合（libhugetlbfsからhugeadmが提供する推奨事項に基づく） https://github.com/libhugetlbfs/libhugetlbfs/、ある時点で割り当て可能なヒューゲページの数を推定できます。すべての「Movable」ブロックはメモリがmlock()されていない限り割り当て可能ですが、一部のReclaimableブロックも割り当て可能ですが、ファイルシステムメタデータの多くを回収する必要があります。

CommitLimitは以下の式で計算されます：

CommitLimit = ([total RAM pages] - [total huge TLB pages]) *
               overcommit_ratio / 100 + [total swap pages]

たとえば、1ギガバイトの物理メモリと7ギガバイトのスワップ領域を持つシステムで、 vm.overcommit_ratio が30の場合、CommitLimitは7.3ギガバイトになります。

1.8 /proc/statのその他のカーネル統計情報¶

カーネルの活動に関するさまざまな情報は、/proc/statファイルにあります。このファイルに報告されているすべての数値は、システムが最初に起動してからの集計値です。簡単な確認には、ファイルをcatコマンドで表示してください：

> cat /proc/stat
cpu  2255 34 2290 22625563 6290 127 456 0 0 0
cpu0 1132 34 1441 11311718 3675 127 438 0 0 0
cpu1 1123 0 849 11313845 2614 0 18 0 0 0
intr 114930548 113199788 3 0 5 263 0 4 [... lots more numbers ...]
ctxt 1990473
btime 1062191376
processes 2915
procs_running 1
procs_blocked 0
softirq 183433 0 21755 12 39 1137 231 21459 2263

最初の「cpu」行は、すべての「cpuN」行の数値を集計しています。これらの数値は、CPUがさまざまな種類の作業に費やす時間を示します。時間単位はUSER_HZ（通常は100万分の1秒）です。列の意味は左から右へ以下のように定義されています：

  • user: ユーザーモードで実行中の通常プロセス

  • nice: ユーザーモードで実行中のniceプロセス

  • system: カーネルモードで実行中のプロセス

  • idle: アイドル時間（何もしていない状態）

  • iowait: 要するに、iowaitはI/O完了を待っている時間を示します。ただし、いくつかの問題があります：

    1. CPUはI/O完了を待つことはありません。iowaitはタスクがI/O完了を待っている時間です。CPUが未処理のタスクI/Oのためにアイドル状態になると、そのCPUに別のタスクがスケジュールされます。

    2. マルチコアCPUでは、I/O完了を待っているタスクがどのCPUにも実行されていないため、各CPUのiowait値を正確に計算するのが困難です。

    3. /proc/statファイルのiowaitフィールドの値は、特定の条件下で減少します。

    そのため、/proc/statから読み取ったiowaitは信頼性が低いです。

  • irq: 割り込み処理

  • softirq: ソフトライト割り込み処理

  • steal: 自発的でない待機時間

  • guest: 通常ゲストを実行中

  • guest_nice: niceプロセスとして実行中のゲスト

「intr」行は、起動後で割り込み処理された回数を、各可能なシステム割り込みごとに表示します。最初の列はすべての割り込み処理を含む合計（非番号付きのアーキテクチャ固有の割り込みも含む）で、その後の列はそれぞれの番号付き割り込みの合計です。非番号付き割り込みは表示されず、合計値にのみ含まれます。

「ctxt」行は、すべてのCPUにおけるコンテキストスイッチの総数を示します。

「btime」行は、システムが起動した時間（Unixエポックからの秒数）を示します。

「processes」行は、作成されたプロセスとスレッドの数を示します。これはfork()やclone()システムコールによって作成されたプロセス（およびスレッド）を含むが、これらに限定されません。

「procs_running」行は、実行中または待機中のスレッドの総数（つまり、実行可能なスレッドの総数）を示します。

「procs_blocked」行は、I/O完了を待っている現在のプロセス数を示します。

「softirq」行は、システム起動後からサービスされたsoftirqのカウントを、各可能なシステムsoftirqごとに示します。最初の列はすべてのsoftirqの合計であり、その後の各列はその特定のsoftirqの合計です。

第2章: システムパラメータの変更¶

この章では¶

  • /proc/sys配下のファイルに書き込むことによりカーネルパラメータを変更できます

  • 特定のパラメータを変更するファイルの調査

  • /proc/sysファイルツリーの概要

/procの非常に興味深い部分は/proc/sysディレクトリです。これは情報源だけでなく、カーネル内のパラメータを変更する機能もあります。この操作は慎重に行う必要があります。システムを最適化することもできますが、クラッシュを引き起こす可能性もあります。本番環境のシステムではカーネルパラメータを変更しないでください。開発用マシンを用意し、動作をテストしてから変更してください。エラーが発生した場合は再起動をせざるを得ない場合があります。

値を変更するには、ファイルに新しい値をechoしてください。この操作を行うにはroot権限が必要です。システム起動時にこの操作を自動化するための独自のブートスクリプトを作成することも可能です。

Linuxカーネルの動作に関する多様な一般的な設定を微調整およびモニタリングするために、/proc/sysディレクトリ内のファイルを使用できます。一部のファイルは意図せずシステムを破壊する可能性があるため、実際に調整を行う前にドキュメンテーションとソースコードを必ず確認してください。いずれにせよ、これらのファイルへの書き込みには非常に注意が必要です。/procディレクトリ内のエントリは2.1.*と2.2カーネルで若干異なる場合がありますので、疑いがある場合は/usr/src/linux/Documentationディレクトリ内のカーネルドキュメンテーションを確認してください。本章は2.2カーネル以前のドキュメンテーションに基づいており、Linuxカーネルの2.2.1バージョンでこの内容が統合されました。

詳しくはDocumentation/admin-guide/sysctl/ディレクトリをご参照ください。

Summary¶

カーネルの動作の一部は再コンパイルせずに実行時にも変更可能です。/proc/sysツリー内のファイルは読み取るだけでなく、変更することもできます。echoコマンドを使用してこれらのファイルに値を書き込むことで、カーネルのデフォルト設定を変更できます。

第3章: プロセスごとのパラメータ¶

3.1 /proc/<pid>/oom_adj & /proc/<pid>/oom_score_adj- oom-killerスコアの調整¶

これらのファイルは、メモリ不足（oom）状態でどのプロセスを終了させるかを決定するための「悪さ」のヒューリスティックを調整するために使用できます。

悪さヒューリスティックは、各候補タスクに0（決して終了させない）から1000（常に終了させる）までの値を割り当て、どのプロセスをターゲットにするかを決定します。単位は、プロセスが現在のメモリおよびスワップ使用量に基づいて推定される許容メモリ範囲内の比例として概算されます。たとえば、タスクが許容メモリのすべてを使用している場合、悪さスコアは1000になります。半分だけ使用している場合は、スコアは500になります。

「許容」メモリ量は、oomキラーが呼び出されたコンテキストによって異なります。もしタスクのcpusetに割り当てられたメモリが枯渇した場合、許容メモリはそのcpusetに割り当てられたメモリセットを表します。mempolicyのノード（複数）が枯渇した場合は、許容メモリはmempolicyノードのセットを表します。メモリ制限（またはスワップ制限）が達成された場合は、許容メモリは設定された制限を表します。最後に、システム全体がメモリ不足となった場合は、許容メモリはすべての割当可能なリソースを表します。

プロセスの/proc/<pid>/oom_score_adjの値は、タスクを殺すかどうかを決定する際の悪さスコアに加算される。許容される値の範囲は-1000（OOM_SCORE_ADJ_MIN）から+1000（OOM_SCORE_ADJ_MAX）までである。これにより、ユーザースペースが特定のタスクを常に優先するか、完全に無効にするなど、OOMキルの好みを極端に調整できる。最も低い値である-1000は、そのタスクに対してOOMキルを完全に無効化するのと同義であり、常に悪さスコア0を報告するためである。

したがって、ユーザースペースは各タスクに対して考慮するメモリ量を簡単に定義できる。例えば、/proc/<pid>/oom_score_adjを+500に設定すると、同じシステム、cpuset、mempolicy、またはメモリ制御器リソースを共有する他のタスクが少なくとも50%多くメモリを使用できるようにする。一方、-500の値は、タスクの許容メモリの50%をスコア計算から除外するのとほぼ同等である。

以前のカーネルとの後方互換性のために、/proc/<pid>/oom_adjもまた悪さスコアの調整に使用できる。許容される値の範囲は-16（OOM_ADJUST_MIN）から+15（OOM_ADJUST_MAX）までであり、タスクに対してOOMキルを完全に無効化する特別な値として-17（OOM_DISABLE）が存在する。その値は/proc/<pid>/oom_score_adjと線形にスケーリングされる。

/proc/<pid>/oom_score_adjの値は、CAP_SYS_RESOURCEを持つプロセスが最後に設定した値以下に下げることはできない。さらに低い値に下げたい場合はCAP_SYS_RESOURCEが必要である。

3.2 /proc/<pid>/oom_score - OOMキラーアクセス中の現在のスコアを表示¶

このファイルは、任意の<pid>に対してOOMキラーアクセス中の現在のスコアを確認するのに使用できる。OOMキラーアクセス中のどのプロセスを殺すかを調整するには、/proc/<pid>/oom_score_adjと併用する。

注意点として、エクスポートされる値にはoom_score_adjが含まれるため、有効範囲は[0,2000]となる。

3.3 /proc/<pid>/io - IOアカウントフィールドを表示¶

このファイルには、各実行中のプロセスのIO統計情報が含まれている。

例¶

test:/tmp # dd if=/dev/zero of=/tmp/test.dat &
[1] 3828

test:/tmp # cat /proc/3828/io
rchar: 323934931
wchar: 323929600
syscr: 632687
syscw: 632675
read_bytes: 0
write_bytes: 323932160
cancelled_write_bytes: 0

説明¶

rchar¶

IOカウンター: 読み取った文字数 このタスクがストレージから読み取らせたバイト数を示す。これは、このプロセスがread()とpread()に渡したバイト数の合計に等しい。ターミナルIOも含まれるが、実際に物理ディスクIOが必要だったかどうかは影響しない（読み取りがページキャッシュから満たされていた可能性があるため）。

wchar¶

IOカウンター: 書き込んだ文字数 このタスクがディスクに書き込ませた、または書き込むことになるバイト数を示す。rcharと同様の注意点が適用される。

syscr¶

I/Oカウンター: read syscalls read()やpread()などのread I/O操作の回数をカウントしようとしています。

syscw¶

I/Oカウンター: write syscalls write()やpwrite()などのwrite I/O操作の回数をカウントしようとしています。

read_bytes¶

I/Oカウンター: 読み取ったバイト数 このプロセスがストレージレイヤーから実際にフェッチしたバイト数をカウントしようとしています。ブロックベースのファイルシステムでは正確ですが、 submit_bio() レベルで実行されるため、NFSやCIFSに関する状態については後で追加してください。

write_bytes¶

I/Oカウンター: 書き込んだバイト数 このプロセスがストレージレイヤーに送信したバイト数をカウントしようとしています。これはページが汚染されるタイミングで行われます。

cancelled_write_bytes¶

ここでの大きな誤差はtruncateです。プロセスがファイルに1MB書き込みその後ファイルを削除した場合、実際には書き出しが行われません。しかし1MBの書き込みとしてカウントされます。つまり：このプロセスがページキャッシュのtruncateによって「負の」I/Oを引き起こしたバイト数です。タスクは「負の」I/Oを引き起こすこともできます。このタスクが汚染されたページキャッシュをtruncateした場合、他のタスクがカウントしたI/O（write_bytes）が実際には行われません。これをtruncateタスクのwrite_bytesから差し引くこともできますが、情報が失われる可能性があります。

注意

現在の実装状態では32ビットマシンでは少しレース条件があります：プロセスAがプロセスBの/proc/pid/ioを読み込む間にプロセスBが64ビットカウンターを更新している場合、プロセスAは中間結果を確認する可能性があります。

この情報についてはDocumentation/accountingにあるtaskstatsドキュメンテーションで確認できます。

3.4 /proc/<pid>/coredump_filter - コアダンプフィルタリング設定¶

プロセスがダンプされる際、コアファイルのサイズが制限されていない限り、匿名メモリはすべてコアファイルに書き込まれます。しかし、特定のメモリセグメント（例：大容量共有メモリやDAX）をダンプしたくない場合もあります。逆に、ファイルバックドメモリセグメントをコアファイルに保存したい場合もあります。

/proc/<pid>/coredump_filterは、<pid>プロセスがダンプされる際のどのメモリセグメントをダンプするかをカスタマイズできます。coredump_filterはメモリタイプのビットマスクです。ビットが設定されている場合、対応するメモリタイプのセグメントがダンプされ、設定されていない場合はダンプされません。

サポートされるメモリタイプは以下の9種類です：

  • (bit 0) アノニマスプライベートメモリ

  • (bit 1) アノニマスシャーディングメモリ

  • (bit 2) ファイルバックドプライベートメモリ

  • (bit 3) ファイルバックドシャーディングメモリ

  • (bit 4) ELF header pages in file-backed private memory areas (it is effective only if the bit 2 is cleared)

  • (bit 5) hugetlb private memory

  • (bit 6) hugetlb shared memory

  • (bit 7) DAX private memory

  • (bit 8) DAX shared memory

Note that MMIO pages such as frame buffer are never dumped and vDSO pages are always dumped regardless of the bitmask status.

Note that bits 0-4 don’t affect hugetlb or DAX memory. hugetlb memory is only affected by bit 5-6, and DAX is only affected by bits 7-8.

The default value of coredump_filter is 0x33; this means all anonymous memory segments, ELF header pages and hugetlb private memory are dumped.

If you don’t want to dump all shared memory segments attached to pid 1234, write 0x31 to the process’s proc file:

$ echo 0x31 > /proc/1234/coredump_filter

When a new process is created, the process inherits the bitmask status from its parent. It is useful to set up coredump_filter before the program runs. For example:

$ echo 0x7 > /proc/self/coredump_filter
$ ./some_program

3.6 /proc/<pid>/comm & /proc/<pid>/task/<tid>/comm¶

These files provide a method to access a task’s comm value. It also allows for a task to set its own or one of its thread siblings comm value. The comm value is limited in size compared to the cmdline value, so writing anything longer then the kernel’s TASK_COMM_LEN (currently 16 chars) will result in a truncated comm value.

3.7 /proc/<pid>/task/<tid>/children - Information about task children¶

This file provides a fast way to retrieve first level children pids of a task pointed by <pid>/<tid> pair. The format is a space separated stream of pids.

Note the “first level” here – if a child has its own children they will not be listed here; one needs to read /proc/<children-pid>/task/<tid>/children to obtain the descendants.

このインターフェースは高速で低コストを目的としているため、正確な結果を保証せず、一部の子プロセスがスキップされる可能性があります（特にPIDを印刷した直後にプロセスが終了した場合）。正確な結果が必要な場合は、検査中のプロセスを停止または凍結する必要があります。

3.8 /proc/<pid>/fdinfo/<fd> - 開いているファイルに関する情報¶

このファイルは、開いているファイルに関する情報を提供します。通常のファイルは少なくとも4つのフィールド（'pos'、'flags'、'mnt_id'、'ino'）を持ち、'pos'は開いているファイルの現在のオフセットを10進数で表します（詳細はlseek(2)を参照）、'flags'はファイルが作成された際のoctal O_xxxマスクを表し（詳細はopen(2)を参照）、'mnt_id'は開いているファイルを含むファイルシステムのマウントIDを表し（詳細は3.5 /proc/<pid>/mountinfoを参照）、'ino'はファイルのインノデ番号を表します。

典型的な出力は以下の通りです：

mnt_id: 19
ino:    63107

lock:       1: FLOCK  ADVISORY  WRITE 359 00:13:11691 0 EOF

eventfd、fsnotify、signalfd、epollなどの通常のpos/flagsペアのファイルは、それらが表すオブジェクト特有の追加情報を提供します。

mnt_id: 9

ここで「eventfd-count」はカウンタの16進数値を表します。

Signalfdファイル¶

mnt_id: 9

ここで「sigmask」はファイルに関連するシグナルマスクの16進数値を表します。

ここで「tfd」はターゲットファイルディスクリプタ番号（10進数）、'events'は監視中のイベントマスク、'data'はターゲットに関連するデータを表します（詳細はepoll(7)を参照）。

'pos'はターゲットファイルの現在のオフセット（10進数）を表し（lseek(2)を参照）、'ino'および'sdev'はターゲットファイルが存在するインノデ番号とデバイス番号を表し、すべて16進数形式です。

inotify wd:3 ino:9e7e sdev:800013 mask:800afce ignored_mask:0 fhandle-bytes:8 fhandle-type:1 f_handle:7e9e0000640d1b6d

ここで「wd」はウォッチディスクリプタ（10進数）を表し、つまりターゲットファイルディスクリプタ番号、'ino'および'sdev'はターゲットファイルが存在するインノデ番号とデバイス番号、'mask'はイベントマスクを表し、すべて16進数形式です（詳細はinotify(7)を参照）。

カーネルがexportfsサポートで構築されている場合、ターゲットファイルへのパスはファイルハンドルとして符号化されます。ファイルハンドルは3つのフィールド「fhandle-bytes」、「fhandle-type」、「f_handle」で提供され、すべて16進数形式です。

カーネルがexportfsサポートを搭載していない場合、ファイルハンドルは表示されません。

inotifyマーキングがまだない場合、「inotify」行は省略されます。

fanotifyファイルのフォーマットは以下の通りです：

pos:    0
flags:  02
mnt_id: 9
ino:    63107
fanotify flags:10 event-flags:0
fanotify mnt_id:12 mflags:40 mask:38 ignored_mask:40000003
fanotify ino:4f969 sdev:800013 mflags:0 mask:3b ignored_mask:40000000 fhandle-bytes:8 fhandle-type:1 f_handle:69f90400c275b5b4

fanotifyの「flags」および「event-flags」は、fanotify_initコールで使用される値です。「mnt_id」はマウントポイントの識別子で、「mflags」はマークに関連するフラグ値で、イベントマスクとは別に追跡されます。「ino」と「sdev」はターゲットのインノードとデバイス、「mask」はイベントマスク、「ignored_mask」は無視されるイベントのマスクです。すべての値は16進形式です。mflags、mask、ignored_maskの組み合わせは、fanotify_markコールで使用されるフラグとマスクに関する情報を提供します（詳細はfsnotifyマニュアルページを参照）。

最初の3行は必須で常に表示されますが、残りはオプションで、まだマークが作成されていない場合は省略可能です。

タイマーファイル¶

pos:    0
flags:  02
mnt_id: 9
ino:    63107
clockid: 0
ticks: 0
settime flags: 01
it_value: (0, 49406829)
it_interval: (1, 0)

「clockid」は時計の種類で、「ticks」はタイマーエクスプロリーションが発生した回数です（詳細はtimerfd_create(2)を参照）。『settime flags』はタイマーセットアップに使用される8進形式のフラグです（詳細はtimerfd_settime(2)を参照）。『it_value』はタイマーエクスプロリーションまでの残り時間で、「it_interval」はタイマーアクセス間隔です。タイマがTIMER_ABSTIMEオプションで設定されている場合、『settime flags』に表示されるかもしれませんが、「it_value」は依然としてタイマーエクスプロリーションまでの残り時間を示します。

DMAバッファファイル¶

pos:    0
flags:  04002
mnt_id: 9
ino:    63107
size:   32768
count:  2
exp_name:  system-heap

「size」はDMAバッファのバイト数で、「count」はDMAバッファファイルのファイル数。「exp_name」はDMAバッファエクスポート名です。

3.9 /proc/<pid>/map_files - メモリマップファイルに関する情報¶

このディレクトリには、プロセスが保持しているメモリマップファイルを表すシンボリックリンクが含まれます。例の出力:

| lr-------- 1 root root 64 Jan 27 11:24 333c600000-333c620000 -> /usr/lib64/ld-2.18.so
| lr-------- 1 root root 64 Jan 27 11:24 333c81f000-333c820000 -> /usr/lib64/ld-2.18.so
| lr-------- 1 root root 64 Jan 27 11:24 333c820000-333c821000 -> /usr/lib64/ld-2.18.so
| ...
| lr-------- 1 root root 64 Jan 27 11:24 35d0421000-35d0422000 -> /usr/lib64/libselinux.so.1
| lr-------- 1 root root 64 Jan 27 11:24 400000-41a000 -> /usr/bin/ls

リンクの名前は仮想メモリの境界を表し、つまりvm_area_struct::vm_start - vm_area_struct::vm_endです。

map_filesの主な目的は、/proc/<pid>/mapsや/proc/<pid>/smapsの解析よりも高速にメモリマップファイルのセットを取得することです。これらはどちらも多くのレコードを含んでいます。同時に、2つのプロセスのリストからマッピングを開き、インノード番号を比較することで、実際に共有されている匿名メモリ領域を特定できます。

3.10 /proc/<pid>/timerslack_ns - タスクタイマースラック値¶

このファイルは、タスクのタイマースラック値（ナノ秒単位）を提供します。この値は、通常のタイマを遅延させる時間量を指定し、タイマを統合して不要なウェイクアップを回避します。

これにより、タスクのインタラクティブ性と電力消費のトレードオフを調整できます。

このファイルに0を書き込むと、タスクのタイマースラックをデフォルト値に設定します。

有効な値は0 - ULLONG_MAXの範囲です

値を設定するアプリケーションは、タスクのtimerslack_ns値を変更するためには、指定されたタスクに対してPTRACE_MODE_ATTACH_FSCREDSレベルの権限を有している必要があります。

3.11 /proc/<pid>/patch_state - Livepatchパッチ操作状態¶

CONFIG_LIVEPATCHが有効な場合、このファイルはタスクのパッチ状態の値を表示します。

値が'-1'の場合は、パッチの変更が進行中ではありません。

値が'0'の場合は、パッチの変更が進行中でタスクが未パッチ状態です。パッチが有効化されている場合、タスクはまだパッチされていません。パッチが無効化されている場合、タスクはすでに未パッチ状態となっています。

値が'1'の場合は、パッチの変更が進行中でタスクがパッチ状態です。パッチが有効化されている場合、タスクはすでにパッチされています。パッチが無効化されている場合、タスクはまだ未パッチ状態となっています。

3.12 /proc/<pid>/arch_status - タスク固有のアーキテクチャ状態¶

CONFIG_PROC_PID_ARCH_STATUSが有効な場合、このファイルはタスクのアーキテクチャ固有の状態を表示します。

例¶

$ cat /proc/6753/arch_status
AVX512_elapsed_ms:      8

説明¶

x86固有の項目¶

AVX512_elapsed_ms¶

AVX512がマシンでサポートされている場合、この項目は最後のAVX512使用記録からの経過ミリ秒を表示します。タスクがスケジューリング外れになった際にベストエフォートで記録されるため、値は以下の2つの要因に依存します：

  1. タスクがスケジューリング外れになる前のCPUでの実行時間。CPU隔離と単一の実行可能タスクがある場合、これは数秒に及ぶことがあります。

  2. タスクが最後にスケジューリング外れになったからの経過時間。スケジューリング外れの理由（タイムスライス切れ、システムコールなど）により、この時間は任意に長くなることがあります。

その結果、この値は正確で信頼できる情報とは言えません。この情報を利用するアプリケーションは、システム全体の状況を把握して、タスクが実際のAVX512ユーザーであるかどうかを判断する必要があります。正確な情報はパフォーマンスカウンタで取得できます。

特別な値'-1'はAVX512の使用が記録されていないことを示し、タスクがAVX512ユーザーである可能性は低いですが、ワークロードやスケジューリングの状況により、上記の誤検出（偽陰性）である可能性もあります。

第4章: procfsの設定¶

4.1 マウントオプション¶

サポートされているマウントオプションは次の通りです:

hidepid=

/proc/<pid>/へのアクセスモードを設定します。

gid=

プロセス情報を取得できるグループを設定します。

subset=

procfsの指定されたサブセットのみを表示します。

hidepid=offまたはhidepid=0はクラシックモードを意味し、全ユーザーがすべての/proc/<pid>/ディレクトリにアクセス可能（デフォルト）です。

hidepid=noaccess または hidepid=1 は、ユーザーが自身の /proc/<pid>/ ディレクトリ以外のディレクトリにアクセスできないようにします。cmdline、sched*、status などの敏感なファイルは、他のユーザーからのアクセスを防ぐようになりました。これにより、特定のプログラムが実行されているかを他のユーザーが確認できなくなります（プログラムが自身の動作で情報を漏らさない場合）。追加のメリットとして、/proc/<pid>/cmdline が他のユーザーにアクセスできないため、プログラム引数経由で敏感な情報を渡すように書かれた脆弱なプログラムは、ローカルの傍受者から保護されます。

hidepid=invisible または hidepid=2 は、hidepid=1 に加えて、すべての /proc/<pid>/ ディレクトリが他のユーザーに完全に見えなくなります。これは、特定の pid 値を持つプロセスが存在するかを隠すわけではありません（他の手段で確認可能、例: "kill -0 $PID" など）が、プロセスの uid と gid を隠します。これにより、stat() で /proc/<pid>/ を参照することで得られる情報が隠されます。これにより、実行中のプロセスに関する情報収集が侵入者にとって困難になり、どのデーモンが昇格した特権で実行されているか、他のユーザーが敏感なプログラムを実行しているか、他のユーザーがどのプログラムを実行しているかなど、情報収集が困難になります。

hidepid=ptraceable または hidepid=4 は、caller が ptrace できるプロセスの /proc/<pid>/ ディレクトリのみを procfs に含めるようにします。

gid= は、hidepid= で制限されるプロセス情報の取得を許可されたグループを定義します。identd などのプロセス情報を取得する必要があるデーモンを使用する場合は、このグループに identd を追加してください。

subset=pid は、タスクに関係のないすべてのトップレベルのファイルとディレクトリを procfs から非表示にします。

第5章: ファイルシステムの動作¶

pid 名前空間が導入される前は、procfs はグローバルなファイルシステムでした。つまり、システム全体に1つの procfs インスタンスしか存在しませんでした。

pid 名前空間が導入されると、各 pid 名前空間に別個の procfs インスタンスがマウントされました。したがって、procfs のマウントオプションは、同じ名前空間内のすべてのマウントポイントでグローバルに適用されます。

# grep ^proc /proc/mounts
proc /proc proc rw,relatime,hidepid=2 0 0

# strace -e mount mount -o hidepid=1 -t proc proc /tmp/proc
mount("proc", "/tmp/proc", "proc", 0, "hidepid=1") = 0
+++ exited with 0 +++

# grep ^proc /proc/mounts
proc /proc proc rw,relatime,hidepid=2 0 0
proc /tmp/proc proc rw,relatime,hidepid=2 0 0

procfs のマウントオプションは、再マウントされてからすべてのマウントポイントで変更されます。

# mount -o remount,hidepid=1 -t proc proc /tmp/proc

# grep ^proc /proc/mounts
proc /proc proc rw,relatime,hidepid=1 0 0
proc /tmp/proc proc rw,relatime,hidepid=1 0 0

これは、他のファイルシステムと異なる挙動です。

新しい procfs の挙動は、他のファイルシステムに近づいています。各 procfs マウントは新しい procfs インスタンスを生成します。マウントオプションは自身の procfs インスタンスにのみ影響します。つまり、1つの pid 名前空間内で、異なるフィルタリングオプションでタスクを表示する複数の procfs インスタンスを持つことが可能になりました。

# mount -o hidepid=invisible -t proc proc /proc
# mount -o hidepid=noaccess -t proc proc /tmp/proc
# grep ^proc /proc/mounts
proc /proc proc rw,relatime,hidepid=invisible 0 0
proc /tmp/proc proc rw,relatime,hidepid=noaccess 0 0

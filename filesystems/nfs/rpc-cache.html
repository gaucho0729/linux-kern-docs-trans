RPCキャッシュ¶

このドキュメントでは、特にNFS認証に使用されるsunrpcレイヤー内のキャッシュメカニズムについて簡潔に紹介します。

キャッシュ¶

キャッシュは古いエクスポートテーブルの代わりに使用され、幅広い値をキャッシュする機能を提供します。

構造は似ていますが、内容や用途が大きく異なるキャッシュがいくつかあります。これらのキャッシュを管理するための共通コードが存在します。

必要となるキャッシュの例としては、以下のものが挙げられます：

  • IPアドレスからクライアント名へのマッピング

  • クライアント名とファイルシステムからエクスポートオプションへのマッピング

  • UIDからGIDの一覧へのマッピング（NFSの16つのGID制限を回避するため）

  • ローカルUID/GIDとリモートUID/GIDの間のマッピング（UID割当が統一されていないサイト向け）

  • ネットワーク識別子から公開鍵へのマッピング（暗号認証用）

共通コードは以下の機能を提供します：

  • 正しいロックを用いた一般的なキャッシュ検索

  • 「NEGATIVE」のエントリもサポート

  • キャッシュ項目にEXPIRED時間の設定、期限切れ後の削除、使用状態がなくなった後の削除

  • ユーザー空間へのリクエストを介したキャッシュエントリの補完

  • ユーザー空間がキャッシュに直接エントリを設定できるようにする

  • 未完成なキャッシュエントリに依存するRPCリクエストを一時的に延期し、キャッシュエントリが完成したタイミングで再実行

  • 期限切れとなった古いエントリを削除する

キャッシュの作成¶

  • キャッシュには保存するためのデータが必要です。これは、struct cache_headを要素として含む構造体定義の形式です（通常は最初の要素）。また、キーといくつかのコンテンツも含まれます。各キャッシュ要素は参照カウントされ、キャッシュ管理に使用する期限や更新時間も保持します。

  • キャッシュには「cache_detail」構造体が必要です。これはハッシュテーブル、キャッシュ管理のパラメータ、および特定のキャッシュ項目を操作する方法を記述します。

    操作は以下の通りです：

    struct cache_head *alloc(void)

    これは適切なメモリを割り当て、構造体内のcache_detailへのポインタを返します

    void cache_put(struct kref *)

    項目への最後の参照が解除されたときに呼ばれます。渡されるポインタはcache_head内の「ref」フィールドです。cache_putは「cache_init」で作成された参照を解放し、CACHE_VALIDが設定されている場合は「cache_update」で作成された参照も解放します。その後、「alloc」で割り当てたメモリを解放します。

    int match(struct cache_head *orig, struct cache_head *new)

    2つの構造体のキーが一致するかテストします。一致する場合は1を、一致しない場合は0を返します。

    void init(struct cache_head *orig, struct cache_head *new)

    「new」の「key」フィールドを「orig」から設定します。これは共有オブジェクトへの参照を取る可能性があります。

    void update(struct cache_head *orig, struct cache_head *new)

    「new」の「content」フィールドを「orig」から設定します。

    int cache_show(struct seq_file *m, struct cache_detail *cd, struct cache_head *h)

    オプションです。キャッシュの内容をリスト表示する/procファイルを提供するために使用します。1項目を1行で表示する必要があります。

    int cache_request(struct cache_detail *cd, struct cache_head *h, char **bpp, int *blen)

    ユーザー空間に送信するリクエストをフォーマットします。*bppは*blenサイズのバッファです。bppは符号化されたメッセージを進めていくことで移動し、*blenは残りの空き容量を示すように減らします。成功時は0を、空き容量が不足またはその他の問題時は負数を返します。

    int cache_parse(struct cache_detail *cd, char *buf, int len)

    ユーザー空間からのメッセージが到着し、キャッシュ項目を埋めるために使用されます。このメッセージは「buf」に長さ「len」で格納されています。「buf」を解析し、sunrpc_cache_lookup_rcuを使用してキャッシュ内の項目を検索し、sunrpc_cache_updateで項目を更新します。

  • キャッシュはcache_register()を使用して登録する必要があります。これは定期的に古いデータを削除するためのキャッシュリストに追加されます。

キャッシュの使用¶

キャッシュ内の値を検索するには、サンプル項目の「key」フィールドを埋めたキャッシュ_headへのポインタを渡してsunrpc_cache_lookup_rcuを呼び出します。このポインタは->matchを介してターゲット項目を識別します。項目が見つからない場合は、新しい項目を作成してキャッシュに追加し、有効データとしてマークされません。

返却された項目は通常、cache_checkに渡されます。cache_checkはデータが有効かどうかを確認し、必要に応じてアップコールを実行します。項目が無効またはアップコールが必要ですが実行不可能な場合は-ENOENTを、アップコールが待機中の場合は-EAGAINを、データが有効な場合は0を返します。

cache_checkには「struct cache_req*」を渡すことができます。この構造体は通常、実際のリクエストに埋め込まれており、deferred copy（struct cache_deferred_req）を作成するために使用されます。見つかったキャッシュ項目が最新でないが、ユーザー空間が情報を提供する可能性があると推測される場合に実行されます。キャッシュ項目が有効になるとき、deferred copyされたリクエストは->revisitで再検討されます。このメソッドがリクエストの処理を再スケジュールするものと期待されます。

sunrpc_cache_lookup_rcu によって返された値は、sunrpc_cache_update に渡してアイテムの内容を設定することも可能です。この際、内容を保持するアイテムの2番目の引数を渡します。_lookup で見つけたアイテムが有効なデータを保持している場合、そのデータは破棄され新しいアイテムが作成されます。これにより、アイテムの内容が検査中に変化する心配をユーザーから完全に排除できます。_lookup で見つけたアイテムが有効なデータを保持していない場合、その内容がコピーされ CACHE_VALID が設定されます。

キャッシュの初期化¶

各キャッシュは名前を持ち、キャッシュが登録される際には /proc/net/rpc にその名前のディレクトリが作成されます。

このディレクトリには「channel」というファイルが含まれており、これはカーネルとユーザースペース間でキャッシュを初期化するための通信チャネルです。このディレクトリは今後、キャッシュとやり取りするための他のファイルも含む可能性があります。

「channel」はデータグラムソケットと少し似た仕組みで動作します。各「write」はキャッシュに全体として渡され、パースおよび解釈されます。各キャッシュは「write」リクエストを異なる方法で処理できますが、メッセージに含まれるべき要素は以下の通りです：

  • キー

  • 有効期限

  • コンテンツ。

このようにして、キャッシュ内の指定されたキーを持つアイテムが作成または更新され、指定されたコンテンツが設定され、そのアイテムの有効期限が設定される予定です。

チャネルからの読み取りは少し複雑です。キャッシュの検索が失敗した場合、または検索が成功したがそのエントリがすぐに期限切れになる可能性がある場合、ユーザースペースからそのキャッシュアイテムを更新するリクエストが生成されます。これらのリクエストはチャネルファイルに表示されます。

連続する読み取りは連続するリクエストを返します。返すリクエストがなくなった場合、read は EOF を返しますが、read 用の select または poll は次のリクエストが追加されるのを待つまでブロックします。

そのため、ユーザースペースのアシスタントは以下のような動作をします：

open the channel.
  select for readable
  read a request
  write a response
loop.

もし終了して再起動が必要になった場合、未処理のリクエストはファイルに依然として表示され、新しいアシスタントインスタンスによって読み取られます。

各キャッシュは「cache_parse」メソッドを定義すべきで、これはユーザースペースから書かれたメッセージを処理します。エラーを返す（これは write システムコールに逆流します）か 0 を返す必要があります。

各キャッシュはまた「cache_request」メソッドも定義すべきで、これはキャッシュアイテムを提供されたバッファにエンコードします。

注意

チャンネルにアクティブなリーダーがいない場合、かつ60秒以上アクティブなリーダーがいない場合、さらに多くのリクエストはチャンネルに追加されず、有効なエントリが見つからない検索は失敗します。これは一部の後方互換性のためです：以前のnfsエクスポートテーブルが優先されるとされており、失敗した検索は明確な「no（否定）」を意味しました。

リクエスト/レスポンス形式¶

各キャッシュはチャンネルを介したリクエストとレスポンスの形式を自由に選択できますが、以下の形式が推奨され、サポート用ルーチンが提供されています：各リクエストまたはレスポンスレコードは印刷可能なASCII文字で構成され、末尾に正確に1つの改行文字を含める必要があります。レコード内のフィールドはスペースで区切られ、通常は1つのスペースです。フィールド内にスペース、改行、またはヌル文字が必要な場合は、それらを引用符で囲む必要があります。2つのメカニズムが利用可能です：

  • フィールドが「x」で始まる場合、そのフィールドには偶数の16進数の桁が含まれなければなりません。これらの桁のペアは、フィールド内のバイトを表します。

  • それ以外の場合、フィールド内に「o」が含まれる場合は、その後ろに3桁の8進数が続く必要があります。これはバイトのコードを表します。他の文字は自身のまま扱われます。少なくともスペース、改行、ヌル、および引用符はこのように引用する必要があります。

ROMFS - ROMファイルシステム¶

これは非常に単純で読み取り専用のファイルシステムで、主にインストールディスクの初期RAMディスクとして使用されます。モジュールをブート時にロードする必要が生じたことにより発展しました。このファイルシステムを使用することで、非常に類似した機能を得ることができ、さらに、ルーターのベースメントにある機能に有用なメモリを占拠しないファイルシステムを持つ小さなカーネルの実装も可能です。

比較すると、古いminixおよびxiafs（後者は現在非動作）ファイルシステムはモジュールとしてコンパイルすると20000バイト以上を必要としますが、romfsは1ページ未満、約4000バイト（i586コードを仮定）で済みます。同様の条件では、msdosファイルシステムは約30Kを必要とし（デバイスノードやシンボリックリンクをサポートしません）、nfsモジュールとnfsrootは約57Kを必要とします。さらに、少し不正確な比較ですが、実際の救急ディスクはext2で3202ブロックを必要としましたが、romfsでは3079ブロックで済みました。

このようなファイルシステムを作成するには、genromfsというユーザー用プログラムが必要です。これは http://romfs.sourceforge.net/

名前の通り、romfsは（E）EPROMディスクなどのさまざまな読み取り専用メディアでも（誰かが動機があれば）空間効率よく利用可能です。:)

しかし、romfsの主な目的は、このファイルシステムのみをリンクし、非常に小さなカーネルを作成することです。その後、現在のモジュールユーティリティを使用して、後から任意のモジュールをロードできます。また、SCSIデバイスが必要かどうかを判断するプログラムを実行することも可能です。さらに、IDEやフロッピーディスクドライブも、「initrd（初期RAMディスク）」機能を使用すれば後からロードできます。これは実に驚くべきニュースではありませんが、romfsではext2やminix、あるいはaffsファイルシステムを必要に応じて後から読み込むことも可能になります。

例えば、ディストリビューションのブートディスクには、CDディスクドライバ（およびSCSIドライバを含む場合あり）とISO 9660ファイルシステムモジュールのみを含めることができます。カーネルは他のファイルシステム（例えば、かなり大きいext2fsモジュールなど）を含まないため、非常に小さくでき、インストールの後段階でCDからそのモジュールをロードできます。もう一つの用途はネットワークからワークステーションを再インストールする際の回復ディスクで、近くのサーバーからすべてのツール/モジュールを取得できるため、ext2に収まらないため2枚のディスクを携帯する必要がないことです。

romfsはブロックデバイス上で動作し、その下層構造は非常に単純です。すべてのアクセス可能な構造は16バイト境界から始まり、高速なアクセスを可能にしています。ファイルが占める最小の領域は32バイト（これは空ファイルで、名前の長さが16文字未満の場合）です。非空ファイルの最大オーバーヘッドはヘッダーと、名前およびコンテンツの16バイトパディングです（合計16+14+15=45バイト）。ただし、これは非常にまれなケースで、ほとんどのファイル名は3バイト以上15バイト未満です。

ファイルシステムのレイアウトは以下の通りです。

offset     content

       +---+---+---+---+
 0     | - | r | o | m |  \
       +---+---+---+---+       The ASCII representation of those bytes
 4     | 1 | f | s | - |  /    (i.e. "-rom1fs-")
       +---+---+---+---+
 8     |   full size   |       The number of accessible bytes in this fs.
       +---+---+---+---+
12     |    checksum   |       The checksum of the FIRST 512 BYTES.
       +---+---+---+---+
16     | volume name   |       The zero terminated name of the volume,
       :               :       padded to 16 byte boundary.
       +---+---+---+---+
xx     |     file      |
       :    headers    :

すべてのマルチバイト値（32ビットワード、以降はlongwordsと呼びます）はビッグエンディアン順でなければなりません。

最初の8バイトはファイルシステムを識別します（初心者でも確認可能です）。その後、3番目のlongwordにはこのファイルシステムからアクセス可能なバイト数が記録されています。4番目のlongwordは最初の512バイト（またはアクセス可能なバイト数、どちらか小さい方）のチェックサムです。使用されるアルゴリズムはAFFSファイルシステムと同じで、longwordの単純な合計（再度ビッグエンディアンの値を仮定）です。詳細はソースコードをご参照ください。このアルゴリズムは信頼性が高くありませんが、テーブルを必要とせず非常に単純なため選ばれました。

以下のバイトはファイルシステムの一部です。各ファイルヘッダーは16バイト境界で開始しなければなりません。

offset     content

       +---+---+---+---+
 0     | next filehdr|X|       The offset of the next file header
       +---+---+---+---+         (zero if no more files)
 4     |   spec.info   |       Info for directories/hard links/devices
       +---+---+---+---+
 8     |     size      |       The size of this file in bytes
       +---+---+---+---+
12     |   checksum    |       Covering the meta data, including the file
       +---+---+---+---+         name, and padding
16     | file name     |       The zero terminated name of the file,
       :               :       padded to 16 byte boundary
       +---+---+---+---+
xx     | file data     |
       :               :

ファイルヘッダーは常に16バイト境界で開始するため、次のfilehdrポインタの下位4ビットは常にゼロになります。この4ビットはモード情報として使用されます。ビット0〜2はファイルの種類を指定し、ビット4はファイルが実行可能かどうかを示します。このビットが設定されていない場合、パーミッションはワールド読み込み可能と仮定され、設定されている場合はワールド実行可能とします（ただし、キャラクタデバイスとブロックデバイスは所有者以外にはアクセスできません）。すべてのファイルの所有者はユーザーおよびグループ0であり、これは意図した用途では問題になりません。8つの可能な値がファイルタイプにマッピングされる仕様は以下の通りです。

0

ハードリンク

リンク先[file header]

1

構成ROMから文字列を読み込み

最初のファイルのヘッダー

2

通常ファイル

未使用、ゼロでなければならない[MBZ]

3

シンボリックリンク

未使用、MBZ（ファイルデータはリンクコンテンツ）

4

ブロックデバイス

16/16ビットメジャーマイナーナンバー

5

キャラクタデバイス

  • ” -

6

ソケット

未使用、MBZ

7

FIFO

未使用、MBZ

このファイルシステムではハードリンクが特に明示的にマークされていますが、それらは予想通りの動作（つまりインノード番号を共有する）を行います。また、ハードリンクのループを作成しない責任はユーザーにあり、ディレクトリに対してすべての「.」と「..」リンクを作成することも求められます。これは通常genromfsプログラムが正しく行っています。ソケットとfifoの特殊ファイルに対して実行可能ビットを特別な用途に使用しないでください。これらは今後他の用途に使用される可能性があります。さらに、通常ファイルおよびシンボリックリンクのみがサイズフィールドにゼロ以外の値を持つべきであり、それらは（パディングされた）ファイル名の直後に利用可能なバイト数を示します。

romfsはファイルヘッダとデータを16バイト境界にアライメントしていますが、ほとんどのハードウェアデバイスやブロックデバイスドライバーはブロックサイズより小さいデータを扱うことができません。この制限を克服するため、ファイルシステム全体のサイズは1024バイト境界にパディングする必要があります。

このファイルシステムに関する問題や提案があれば、私に連絡してください。ただし、私が機能やコードを追加するよう依頼する前に、よく考えた方がよいでしょう。なぜなら、このファイルシステムの主な利点はコードの小ささです。一方で心配する必要はありません。私はromfsに関するメールをあまり受けません。今やアveryがARCnetドキュメントで詩を書いたのはフィードバックを求めるためだったのかと理解できます。:)

romfsにはメーリングリストもあります。しかし現在までにトラフィックは受信していませんので、あなたのアイデアを議論するためにぜひ参加してください。:)

ezmlmによって運用されているため、メッセージを送信することでサブスクリプションできます。 romfs-subscribe@shadow.banki.hu、内容は関係ありません。

未解決の問題:

  • パーミッションと所有者情報はUnixのようなシステムにおいて非常に重要な機能ですが、romfsはこれらを完全に提供していません。私はこれまでこの制限を感じたことはありませんが、他のユーザーにとっては問題になるかもしれません。

  • このファイルシステムは読み取り専用なので非常に小さくできますが、何かをファイルシステムに書きたい場合、依然として書き込み可能なファイルシステムが必要になります。これによりサイズの利点が失われます。解決策として、コンパイル時のオプションで書き込みアクセスを実装するか、RAMディスク用に同様に小さな新しい書き込み可能なファイルシステムを実装するという選択肢があります。

  • ファイルが16バイト境界でのアライメントのみが必要であるため、現在、ファイルシステムからファイルを読み込んだり実行したりする行為は不十分かもしれません。ファイルデータを再配置して、ほとんどの部分（つまり先頭と末尾を除く）を「自然な」境界に配置することでこの問題は解決される可能性があり、その結果、ファイルの大部分をmmサブシステムに直接マッピングすることが可能になります。

  • 圧縮は有用な機能かもしれませんが、私にとってメモリはかなり制約となる要因です。

  • インテルとモトローラ以外のアーキテクチャでも動作しますか？

はじめに¶

User Mode Linuxへようこそ

User Mode Linuxは、1991年に最初にリリースされたオープンソースの仮想化プラットフォームであり、x86 PC用の第二の仮想化プラットフォームです。

UML は Virtualization パッケージ X を使用する仮想マシンとどう違いますか？¶

私たちは仮想化がハードウェアエミュレーションの何らかのレベルを意味すると仮定してきました。しかし、実際にはそうではありません。仮想化パッケージがOSに認識可能なデバイスを提供し、そのOSがドライバを持っている限り、デバイスは実際のハードウェアをエミュレートする必要はありません。現代のほとんどのOSは、仮想化環境下でのみ使用される「偽の」デバイスのいくつかを内蔵でサポートしています。User Mode Linuxはこの概念を極限まで追求しており、実際には1つの実際のデバイスは存在しません。これは100%人工的であり、正しい用語を使うとすれば100%パラバーチャルです。すべてのUMLデバイスは抽象的な概念であり、ホストが提供するもの（ファイル、ソケット、パイプなど）にマッピングされています。

UMLとさまざまな仮想化パッケージのもう一つの主な違いは、UMLカーネルとUMLプログラムが動作する仕組みの違いです。UMLカーネルはLinux上に実行されるプロセスであり、他のプログラムと同様です。権限のないユーザーでも実行でき、特別なCPU機能は必要ありません。一方、UMLユーザースペースはやや異なります。ホストマシンのLinuxカーネルは、UMLインスタンス上で実行されているプログラムが試みるすべての操作をインターセプトし、UMLカーネルがすべてのリクエストを処理するようにします。これは、ゲストカーネルとゲストプログラムの違いを考慮しない他の仮想化パッケージとは異なります。この違いは、後のこのドキュメントで説明するように、UMLがQEMUなどの他の仮想化パッケージと比較して持つ利点と欠点を生み出します。

なぜユーザー・モード・Linuxを望むのでしょうか？¶

  • User Mode Linuxカーネルがクラッシュしても、ホストカーネルは問題ありません。これは加速されていません（vhost、kvmなど）し、直接デバイスにアクセスしようともしていません。実際には、他のプロセスと同様のプロセスです。

  • 非rootユーザーでもユーザーモードカーネルを実行できます（一部のデバイスには適切な権限を設定する必要があります）。

  • 特定のタスク用に非常に小さな仮想マシンを実行でき、最小のフットプリントで動作します（例：32MB以下）。

  • フォワーディング、ファイアウォールなど、カーネル特有のタスクにおいて極めて高いパフォーマンスを実現できます。また、ホストカーネルとは隔離された状態で動作します。

  • カーネルの概念を実験できますが、システムを破壊することはありません。

  • ハードウェアを「エミュレート」する必要がないため、時間旅行やUMLが行うシステムクロックの動作に依存するなど、実際のハードウェアをエミュレートする際には非常に困難な概念を試すことができます。

  • 面白いです。

UMLを実行しない理由¶

  • UMLが使用するシステムコールのインターセプション技術により、ユーザー空間アプリケーションでは本来よりも遅くなります。しかし、カーネルタスクについては他の仮想化パッケージと同様の性能を発揮しますが、ユーザー空間は 遅延モード非常に高いコストで新しいプロセスとスレッドを生成する必要があります（これはUnix/Linuxアプリケーションでは通常無視されています）。

  • 現在のUMLはシングルプロセッサのみをサポートしています。多くのCPUを必要とするアプリケーションを実行する場合は、UMLは明らかに適切ではありません。

UMLインスタンスの構築¶

どのディストリビューションにもUML専用のインストーラーは存在しません。既製のインストールメディアを使用して仮想化パッケージで空白の仮想マシンにインストールすることは可能ですが、UMLに相当するものは存在しません。ホスト側で適切なツールを使用して、実用可能なファイルシステムイメージを構築する必要があります。

Debianでは非常に簡単です - debootstrapを使用すれば実行できます。OpenWRTでも同様に簡単で、ビルドプロセスでUMLイメージを構築できます。その他のディストリビューションでは結果は環境により異なります。

イメージの作成¶

スパースなRAWディスクイメージを作成します：

# dd if=/dev/zero of=disk_image_name bs=1 count=1 seek=16G

これにより16GBのディスクイメージが作成されます。OSは初期に1ブロックのみを割り当て、UMLが書き込むたびに追加で割り当てます。カーネルバージョン4.19以降ではUMLがTRIMを完全にサポートしており（フラッシュドライブで通常使用されるように）、TRIMをイメージ内で使用するにはマウントオプションにdiscardを指定するか、以下のコマンドを実行します。 tune2fs -o discard /dev/ubdXX これによりUMLが未使用のブロックをOSに返却します。

ディスクイメージにファイルシステムを作成し、マウントします：

# mkfs.ext4 ./disk_image_name && mount ./disk_image_name /mnt

この例ではext4を使用していますが、ext3、btrfs、xfs、jfsなど他のファイルシステムでも動作します。

マウントされたファイルシステムに最小限のOSインストールを行います：

# debootstrap buster /mnt http://deb.debian.org/debian

debootstrapはルートパスワード、fstab、ホスト名、ネットワーク設定などに関連する設定を行いません。これらはユーザー自身で行う必要があります。

ルートパスワードを設定するには、マウントされたイメージにchrootして実行するのが最も簡単です：

# chroot /mnt
# passwd
# exit

重要なシステムファイルを編集¶

UMLのブロックデバイスはubdsと呼ばれます。debootstrapで作成されるfstabは空で、ルートファイルシステムのエントリが必要です：

/dev/ubd0   ext4    discard,errors=remount-ro  0       1

イメージのホスト名は作成しているホストのホスト名と同じになります。誤って別のマシンを再起動したなどのトラブルを避けるため、ホスト名を変更することをお勧めします。

UMLは、古いuml_netデバイスと新しいvector IOデバイスの2つのクラスのネットワークデバイスをサポートしています。古いuml_netデバイスは廃止予定となっており、ethXと呼ばれます。また、新しいvector IOデバイスは大幅に高速化されており、Ethernet over GREやEthernet over L2TPv3などの標準的な仮想ネットワークのカプセル化をサポートしています。これらはvec0と呼ばれます。

使用しているデバイスによって、 /etc/network/interfaces 次のエントリが必要になります：

# legacy UML network devices
auto eth0
iface eth0 inet dhcp

# vector UML network devices
auto vec0
iface eth0 inet dhcp

現在、動作に必要な準備がほぼ整ったUMLイメージがあります。すべて必要なのはUMLカーネルとそれに必要なモジュールです。

ほとんどのディストリビューションにはUMLパッケージが含まれています。自作のカーネルを使用する予定であっても、標準的なカーネルでイメージをテストすることは常に良い出発点です。これらのパッケージにはモジュールが含まれており、これをターゲットファイルシステムにコピーする必要があります。場所はディストリビューションによって異なります。Debianの場合、/usr/lib/uml/modulesに配置されています。このディレクトリの内容をマウントされたUMLファイルシステムに再帰的にコピーしてください：

# cp -rax /usr/lib/uml/modules /mnt/lib/modules

自作のカーネルをコンパイルした場合は、通常の「モジュールを特定の場所にインストール」の手順で以下のコマンドを実行してください：

# make install MODULES_DIR=/mnt/lib/modules

この時点でイメージは起動準備が整いました。

UMLネットワーク設定¶

ネットワーク設定の特権¶

サポートされているネットワーキングモードの多くは root 特権が必要です。たとえば、レガシートントップモードでは、ユーザーがトンネルデバイスに関連するグループに所属していた必要があります。

vector transports などの新しいネットワークドライバでは、 root ioctl を実行して tun インターフェースを設定したり、必要に応じて raw ソケットを使用したりするための特権が必要です。

これを行うには、ユーザーに特定の特権を付与するか、UML を root で実行するのではなく、通常のユーザー特権で実行できます。vector transports の場合、ユーザーは uml バイナリにこの特権を追加できます。 CAP_NET_ADMIN または CAP_NET_RAWこれにより、UML は通常のユーザー特権で実行され、フルネットワーキングが可能です。

例:

# sudo setcap cap_net_raw,cap_net_admin+ep linux

ベクター転送の設定¶

すべての vector transports は類似の構文をサポートしています:

vec0、vec1、vec2 などのインターフェース番号 X として、オプションの一般的な構文は:

vecX:transport="Transport Name",option=value,option=value,...,option=value

一般的なオプション¶

これらのオプションはすべてのトランスポートで共通しています:

  • depth=int - ベクターIOのキュー深度を設定します。これはUMLが1回のシステムコールで読み取ったり書き込んだりするパケット数です。デフォルト値は64で、2〜4Gbitのスループットを必要とするほとんどのアプリケーションで十分です。高速化にはより大きな値が必要かもしれません。

  • mac=XX:XX:XX:XX:XX - インターフェースのMACアドレスを設定します。

  • gro=[0,1] - GROをオンまたはオフに設定します。受信/送信オフロードを有効にします。このオプションの効果は、設定しているトランスポートのホスト側でのサポートに依存します。ほとんどの場合、TCPセグメンテーションとRX/TXチェックサムオフロードを有効にします。ホスト側とUML側で設定が一致する必要があります。設定が一致しない場合、UMLカーネルは警告を出します。たとえば、ローカルマシンインターフェース（vethペア、ブリッジなど）ではGROがデフォルトで有効なので、UMLの対応トランスポート（raw、tap、ハイブリッド）でもGROを有効にしなければネットワーキングが正しく動作しません。

  • mtu=int - インターフェースのMTUを設定します

  • headroom=int - パケットがVXLANなどの再エンカプスレーションが必要な場合に、デフォルトのヘッドルーム（32バイト）を調整します。

  • vec=0 - マルチパケットIOを無効にして、パケット単位モードに戻します

共有オプション¶

  • ifname=str ローカルネットワークインターフェースにバインドするトランスポートは、共有オプションとしてインターフェース名を指定します。

  • src, dst, src_port, dst_port - ソケットを使用するすべてのトランスポートで、ソースと宛先、またはソースポートと宛先ポートの概念がある場合、これらを指定します。

  • v6=[0,1] IPを介して動作するすべてのトランスポートでIPv6接続を指定するかどうかを設定します。また、v4とv6で動作方法に違いがあるトランスポート（例：EoL2TPv3など）では、正しい動作モードを設定します。このオプションが指定されていない場合、ソケットタイプはsrcとdst引数が解決/パースされる結果に基づいて決定されます。

tap転送¶

例:

vecX:transport=tap,ifname=tap0,depth=128,gro=1

vec0をホスト上のtap0に接続します。tap0はすでに存在している必要があります（たとえばtunctlで作成済みでUP状態であること）。

tap0はポイントツーポイントインターフェースとして構成されIPアドレスを割り当てることで、UMLがホストと通信できるようにできます。 alternatively、UMLをブリッジに接続されたタップインターフェースに接続することも可能です。

tapはベクターインフラストラクチャに依存していますが、現在は真のベクタートランスポートではありません。これはLinuxが通常のユーザースペースアプリケーション（例：UML）でタップファイルディスクリプタのマルチパケットIOをサポートしていないためです。この特権は、カーネルレベルで専用インターフェース（例：vhost-net）に接続できるものにのみ提供されています。今後、UML用のvhost-netのようなアシスタントが計画されています。

必要な特権：tapトランスポートには以下のいずれかが必要です：

  • tapインターフェースが存在し、tunctlで永続的に作成され、UMLユーザーが所有していること。例 tunctl -u uml-user -t tap0

  • バイナリに CAP_NET_ADMIN 特権

ハイブリッド転送¶

例:

vecX:transport=hybrid,ifname=tap0,depth=128,gro=1

これは、送信にはタップ、受信にはrawソケットを使用する実験的/デモ用トランスポートです。rawソケットはマルチパケット受信を可能にし、通常のタップよりも大幅に高いパケットレートを実現します。

必要な特権：ハイブリッドトランスポートには CAP_NET_RAW UMLユーザーによるキャパビリティの設定およびtapトランスポートの要件が必要です。

rawソケット転送¶

例:

vecX:transport=raw,ifname=p-veth0,depth=128,gro=1

このトランスポートはrawソケット上でベクターIOを使用します。任意のインターフェース（物理的なものも含む）にバインドできますが、最も一般的な用途はvethペアの「ペア」側にバインドし、もう一方はホストで構成することです。

Debianのホスト構成例：

/etc/network/interfaces:

auto veth0
iface veth0 inet static
     address 192.168.4.1
     netmask 255.255.255.252
     broadcast 192.168.4.3
     pre-up ip link add veth0 type veth peer name p-veth0 && \
       ifconfig p-veth0 up

UMLは次のようにp-veth0にバインドできます：

vec0:transport=raw,ifname=p-veth0,depth=128,gro=1

UMLゲストが192.168.4.2とサブネットマスク255.255.255.0で構成されている場合、ホストの192.168.4.1と通信できます。

rawトランスポートはホストにフィルタリングの一部をオフロードするサポートも提供します。この制御には次のオプションがあります：

  • bpffile=str raw BPFコードをソケットフィルタとしてロードするためのファイル名

  • bpfflash=int 0/1 0/1で、User Mode Linux内部からBPFコードのロードを許可します。このオプションにより、ethtool load firmwareコマンドを使用してBPFコードをロードできます。

いずれの場合も、BPFコードはホストカーネルにロードされます。現在はLegacy BPF構文（ebpfではありません）に限定されていますが、依然としてセキュリティリスクです。User Mode Linuxインスタンスが信頼されていると判断される限り、この機能を許可することを推奨しません。

必要な権限: raw socket transportには CAP_NET_RAW capability.

GREソケット転送¶

例:

vecX:transport=gre,src=$src_host,dst=$dst_host

これは、Ethernet over GRE (aka GRETAP または GREIRB)トンネルを構成します。これにより、UMLインスタンスがホストdst_hostにある GRE エンドポイントに接続されます。 GRE 以下の追加オプションをサポートしています:

  • rx_key=int - GRE 32ビット整数キー（rxパケット用）。設定されている場合は、 txkey must be set too

  • tx_key=int - GRE 32ビット整数キー（txパケット用）。設定されている場合は rx_key must be set too

  • sequence=[0,1] - GREシーケンスを有効にする

  • pin_sequence=[0,1] - 各パケットごとにシーケンスを常にリセットするように見せかける（一部の非常に破損した実装と互換性があるため）

  • v6=[0,1] - IPv4またはIPv6ソケットを強制的に使用する

  • GREチェックサムは現在サポートされていません

GREにはいくつかの注意点があります:

  • 1つのIPアドレスに対してのみGRE接続を使用できます。GREトンネルはUMLインスタンスで直接終端されるため、接続を多重化することはできません。

  • キーは本当にセキュリティ機能ではありません。意図としてはそうでしたが、その「セキュリティ」は冗談です。ただし、トンネルが誤って構成されていないことを確認するための有用な機能です。

Linuxホストの例: ローカルアドレスが192.168.128.1で、UMLインスタンス192.168.129.1に接続する設定

/etc/network/interfaces:

auto gt0
iface gt0 inet static
 address 10.0.0.1
 netmask 255.255.255.0
 broadcast 10.0.0.255
 mtu 1500
 pre-up ip link add gt0 type gretap local 192.168.128.1 \
        remote 192.168.129.1 || true
 down ip link del gt0 || true

さらに、GREはさまざまなネットワーク機器とテストされています。

必要な権限: GREには CAP_NET_RAW

L2TPv3ソケット転送¶

_警告_. L2TPv3には「バグ」があります。その「バグ」は「GNU lsより多くのオプションがある」というものです。いくつかの利点がありますが、通常はUMLインスタンスを何かに接続するにはより簡単（かつ簡潔）な方法があります。たとえば、L2TPv3をサポートするほとんどのデバイスはGREもサポートしています。

例:

vec0:transport=l2tpv3,udp=1,src=$src_host,dst=$dst_host,srcport=$src_port,dstport=$dst_port,depth=128,rx_session=0xffffffff,tx_session=0xffff

これは、Ethernet over L2TPv3固定トンネルを構成します。これにより、UMLインスタンスがホスト$dst_hostにあるL2TPv3エンドポイントに接続され、L2TPv3 UDP flavourとUDP宛先ポート$dst_portを使用します。

L2TPv3は常に以下の追加オプションを必要とします:

  • rx_session=int - l2tpv3 32ビット整数セッション（rxパケット用）

  • tx_session=int - l2tpv3 32ビット整数セッション（txパケット用）

トンネルが固定されているため、これらは交渉されず、両端で事前に設定されています。

さらに、L2TPv3は以下のオプションパラメータをサポートしています

  • rx_cookie=int - l2tpv3 32ビット整数クッキー（rxパケット用）- GREキーと同じ機能ですが、誤って構成されないことを防ぐためのものであり、実際のセキュリティを提供するものではありません

  • tx_cookie=int - l2tpv3 32ビット整数クッキー（txパケット用）

  • cookie64=[0,1] - 32ビットではなく64ビットのクッキーを使用する

  • counter=[0,1] - l2tpv3カウンターを有効にする

  • pin_counter=[0,1] - パケットごとにカウンターを常にリセットするように装備する（一部の非常に破損した実装と互換性が必要な場合）

  • v6=[0,1] - v6ソケットを強制的に使用

  • udp=[0,1] - プロトコルのrawソケット（0）またはUDP（1）バージョンを使用

L2TPv3にはいくつかの注意点があります:

  • rawモードではIPアドレスごとに1つの接続のみを使用可能です。各L2TPv3トンネルがUMLインスタンス上で直接終了するため、接続を多重化することはできません。UDPモードではこの目的に異なるポートを使用可能です。

LinuxホストがUML経由でL2TPv3で接続するための設定例:

/etc/network/interfaces:

auto l2tp1
iface l2tp1 inet static
 address 192.168.126.1
 netmask 255.255.255.0
 broadcast 192.168.126.255
 mtu 1500
 pre-up ip l2tp add tunnel remote 127.0.0.1 \
        local 127.0.0.1 encap udp tunnel_id 2 \
        peer_tunnel_id 2 udp_sport 1706 udp_dport 1707 && \
        ip l2tp add session name l2tp1 tunnel_id 2 \
        session_id 0xffffffff peer_session_id 0xffffffff
 down ip l2tp del session tunnel_id 2 session_id 0xffffffff && \
        ip l2tp del tunnel tunnel_id 2

必要な権限: L2TPv3は CAP_NET_RAW raw IPモードでは必要ですが、UDPモードでは特別な権限は必要ありません。

UMLの実行¶

このセクションでは、ディストリビューションからインストールしたuser-mode-linuxパッケージまたはカスタムビルドされたカーネルがホストにインストールされていると仮定しています。

これらはシステムに実行可能ファイルとしてlinuxという名前の実行可能ファイルを追加します。これはUMLカーネルです。他の実行可能ファイルと同様に実行可能です。通常のLinuxカーネル引数の大部分をコマンドライン引数として受け取り、さらにUML固有の引数を指定して有用な動作をします。

引数¶

必須引数:¶

  • mem=int[K,M,G] - メモリ量。デフォルトではバイト単位で指定できます。K、M、Gなどのクォーラリファイターも受け付けます。

  • ubdX[s,d,c,t]= 仮想ディスクの仕様。これは必須ではありませんが、ほぼすべてのケースでルートファイルシステムを指定する必要があります。最も簡単なイメージ仕様は、ファイルシステム用のイメージファイル名（これは以下の方法のいずれかで作成します）です。 イメージの作成)

    • UBDデバイスはコピーオンライト（COW）をサポートします。変更は別のファイルに保存され、そのファイルは破棄することで元の純粋なイメージへのロールバックが可能です。COWが必要な場合、UBDイメージは以下のように指定します: cow_file,master_image. 例:ubd0=Filesystem.cow,Filesystem.img

    • UBDデバイスは同期IOを使用するように設定できます。すべての書き込みは即座にディスクにフラッシュされます。これは以下の追加で実行されます s after the ubdX 仕様

    • UBDは単一のファイル名で指定されたデバイスに対していくつかの推論を行います。COWファイルがイメージとして指定されていないことを確認します。これらを無効にするには、以下のフラグを追加します d の後 ubdX

    • UBDはTRIMをサポートしており、ホストOSにイメージ内の未使用ブロックの回収を依頼します。無効にするには、以下を指定してください t の後 ubdX

  • root= rootデバイス - おそらく /dev/ubd0 (これはLinuxファイルシステムのイメージです)

重要なオプション引数¶

UMLを「linux」で実行し、追加の引数を指定しない場合、イメージ内に設定されたすべてのコンソールに対してxtermを起動しようとします（ほとんどのLinuxディストリビューションでは最大6つまで）。各コンソールはxterm内で起動します。これはGUIを持つホストでUMLを使用する際には便利ですが、テストハーネスとして使用する場合やテキストのみの環境で実行する場合は不適切です。

この挙動を変更するには、代替のコンソールを指定し、サポートされている「line」チャネルのいずれかに接続する必要があります。そのためには、デフォルトのxtermとは異なるものを使用するコンソールをマッピングする必要があります。

コンソール番号1をstdin/stdoutにリダイレクトする例

con1=fd:0,fd:1

UMLは幅広いシリアルラインチャネルをサポートしており、以下の構文で指定します

conX=channel_type:options[,channel_type:options]

チャネル指定がカンマで区切られた2つの部分に分かれている場合、最初の部分は入力、2番目の部分は出力になります。

  • nullチャネル - すべての入力または出力を破棄します。例 con=null すべてのコンソールをデフォルトでnullに設定します

  • fd チャネル - ファイルディスクリプタ番号を使用して入出力を行います。例: con1=fd:0,fd:1.

  • ポート チャネル - TCP ポート番号を待ち受けします。例: con1=port:4321

  • pty および pts チャネル - システムの pty/pts を使用します。

  • tty チャネル - 既存のシステム tty にバインドします。例: con1=/dev/tty8 UML がホストの 8番目のコンソールを使用するため、同じターミナルで表示されます（通常は使用されません）。

  • xterm チャネル - これはデフォルトです。このチャネルで xterm を起動し、入出力をそのターミナルに直接行います。注意: xterm が動作するには、ホストに UML ディストリビューションパッケージがインストールされている必要があります。これは通常、UML が xterm と通信するための port-helper およびその他のユーティリティを含みます。代わりに、ソースコードからコンパイルしてインストールする必要があります。コンソールに適用されるすべてのオプションは、UML 内で ttyS として表示されるシリアルラインにも適用されます。

UMLの起動¶

UML を実行できます。

# linux mem=2048M umid=TEST \
 ubd0=Filesystem.img \
 vec0:transport=tap,ifname=tap0,depth=128,gro=1 \
 root=/dev/ubda con=null con0=null,fd:2 con1=fd:0,fd:1

これは、以下のようなインスタンスを実行します 2048M RAM、以下のようなイメージファイルを使用してください Filesystem.img root として実行します。tap0 を使用してホストに接続します。すべてのコンソールを無効化し、 con1 無効化され、コンソール1は標準入出力を使用して、起動したターミナルと同じ場所に表示されます。

ログイン¶

イメージを生成する際、パスワードを設定していない場合、UML インスタンスを停止し、イメージをマウントして chroot してパスワードを設定する必要があります（Generating an Image セクションに記載の手順に従います）。パスワードがすでに設定されている場合は、単にログインするだけで済みます。

UML管理コンソール¶

通常のシステム管理者ツールで「内側」からイメージを管理するだけでなく、UMLマネジメントコンソールを使用することで、低レベルの操作を行うことが可能です。UMLマネジメントコンソールは、実行中のUMLインスタンスにおけるカーネルに対する低レベルインターフェースで、i386のSysRqインターフェースに似ています。UMLの下にフルなオペレーティングシステムがあるため、SysRqメカニズムよりもはるかに柔軟な操作が可能です。

mconsoleインターフェースで行える操作は以下の通りです:

  • カーネルバージョンを取得する

  • デバイスを追加および削除する

  • マシンを停止または再起動する

  • SysRqコマンドを送信する

  • UMLを一時停止および再開する

  • UML内でのプロセスを確認する

  • UMLの内部/proc状態を確認する

mconsoleクライアント（uml_mconsole）が必要です。これはUMLツールパッケージに含まれており、ほとんどのLinuxディストリビューションで利用可能です。

また、 CONFIG_MCONSOLE （「一般設定」の下）で有効にしておく必要があります。UMLを起動すると、以下のような行が表示されます:

mconsole initialized on /home/jdike/.uml/umlNJ32yL/mconsole

UMLコマンドラインで一意のマシンIDを指定した場合、つまり umid=debian、以下のように表示されます:

mconsole initialized on /home/jdike/.uml/debian/mconsole

このファイルは、uml_mconsoleがUMLと通信するためのソケットです。このファイルを引数として実行します。引数はumidまたはフルパスを使用できます:

# uml_mconsole debian

または

# uml_mconsole /home/jdike/.uml/debian/mconsole

プロンプトが表示され、以下のコマンドを実行できます:

  • version

  • help

  • 停止

  • 再起動

  • config

  • remove

  • sysrq

  • help

  • cad

  • 停止

  • go

  • proc

  • stack

version¶

このコマンドは引数を取らず、UMLのバージョンを表示します:

(mconsole)  version
OK Linux OpenWrt 4.14.106 #0 Tue Mar 19 08:19:41 2019 x86_64

このコマンドはいくつかの用途があります。UMLが動作しているかを確認するためのシンプルなノーアクションコマンドとして使用できます。また、UMLにデバイス割込みを送信する方法としても利用できます。UML内部ではmconsoleはUMLデバイスとして扱われます。

help¶

このコマンドは引数を取らず、サポートされているmconsoleコマンドの一覧を表示する短いヘルプ画面を表示します。

停止と再起動¶

これらのコマンドは引数を取らず、ディスクの同期やユーザー空間のクリーンシャットダウンを行わずにマシンを即座に停止します。したがって、マシンをクラッシュするのとほぼ同じ効果があります:

(mconsole)  halt
OK

config¶

「config」は仮想マシンに新しいデバイスを追加します。これはほとんどのUMLデバイスドライバーでサポートされています。引数はカーネルコマンドラインと同じ構文で、追加するデバイスを指定します:

(mconsole) config ubd3=/home/jdike/incoming/roots/root_fs_debian22

remove¶

「remove」はシステムからデバイスを削除します。引数は削除するデバイス名のみです。ドライバーが必要とする意味でのアイドル状態でなければなりません。ubdドライバーの場合、削除されるブロックデバイスはマウントされていないこと、スワップされていないこと、または他のオープン状態になっていない必要があります。ネットワークドライバーの場合、デバイスはダウンしている必要があります:

(mconsole)  remove ubd3

sysrq¶

このコマンドは1つの引数を取り、これは1文字です。これはジェネリックなカーネルのSysRqドライバを呼び出し、その引数によって指定された動作を行います。詳しくは、 Linux Magic System Request Key Hacks お好きなカーネルツリーのSysRqドキュメンテーションを参照してください。有効な文字とそれらの動作を確認できます。

cad¶

これは現在実行中のイメージで Ctl-Alt-Del アクションを実行します。このコマンドが実際にどのような動作を起こすかは、init、systemdなどに依存します。通常はマシンを再起動します。

停止¶

これはmconsoleリクエストを読み続けるループ状態にUMLを置き、'go' mconsoleコマンドが受信されるまで待機します。これはデバッグやスナップショット作成に非常に役立ちます。

go¶

これは'停止'コマンドで一時停止されたUMLを再開します。注意点として、UMLが再開された後、TCP接続がタイムアウトしている可能性があり、長時間停止した場合、crondが以前に実行できなかったジョブをすべて実行しようとして異常な挙動を示すことがあります。

proc¶

これは1つの引数を取ります - /proc内のファイル名を指定し、mconsole標準出力に印刷します

stack¶

これは1つの引数を取ります - プロセスのpid番号を指定し、そのスタックを標準出力に印刷します

高度なUMLトピック¶

仮想マシン間でのファイルシステム共有¶

単に同じファイルから2つのUMLを起動することでファイルシステムを共有しないでください。これは物理マシンを共有ディスクから起動するのと同じです。これによりファイルシステムの破損が発生します。

レイヤードブロックデバイスの使用¶

2つの仮想マシン間でファイルシステムを共有する正しい方法は、ubdブロックドライバのコピー・オン・ライト（COW）レイヤリング機能を使用することです。変更されたブロックはプライベートなCOWファイルに保存され、読み込みはプライベートなデバイスか共有デバイスから行われます。要求されたブロックがプライベートデバイスに有効な場合、プライベートデバイスから読み込み、そうでない場合は共有デバイスから読み込みます。この方式により、変更されていないデータの大部分が任意の数の仮想マシン間で共有され、各仮想マシンはそれ自身の変更内容を含む小さなファイルを持つことになります。多数のUMLが大容量のルートファイルシステムから起動する場合、これはディスク領域の大幅な節約につながります。

ファイルシステムデータの共有はパフォーマンス向上にも貢献します。ホストは共有データをより少ないメモリでキャッシュできるため、UMLのディスク要求はホストのメモリから処理されます。ただし、マルチソケットNUMAマシンでこの操作を行う場合、重大な注意点があります。このようなハードウェアでは、共有マスターファイルとCOW変更を持つ多数のUMLインスタンスを実行すると、ソケット間のトラフィック過多によりNMIsなどの問題が発生する可能性があります。

このような高性能ハードウェアでUMLを実行する場合、同じソケット上の論理CPUにUMLをバインドする必要があります。これは taskset コマンドを使用するか、「チューニング」セクションを参照してください。

既存のブロックデバイスファイルにコピーオンライターレイヤーを追加するには、適切なubdスイッチにCOWファイルの名前を追加するだけでよい:

ubd0=root_fs_cow,root_fs_debian_22

オプションを指定する必要があります。形式は以下の通りです： root_fs_cow プライベートなCOWファイルで、 root_fs_debian_22 既存の共有ファイルシステムです。COWファイルは存在しなくてもよいです。存在しない場合、ドライバーが自動的に作成および初期化します。

ディスク使用量¶

UMLはTRIMサポートを備えており、ディスクイメージファイルの未使用領域を下位OSに解放します。実際のファイルサイズを確認するには、ls -lsまたはduを使用することが重要です。

COWの有効性。¶

マスターファイルへの変更はすべてのCOWファイルを無効にします。このような場合、UMLは 禁止です 自動的にすべてのCOWファイルを削除し、起動を拒否します。この場合、解決策は古いイメージ（最後の変更タイムスタンプを含む）を復元するか、すべてのCOWファイルを削除して再作成する必要があります。COWファイルの変更内容は失われます。

牛はモーと鳴く - uml_moo : COWファイルをバックイングファイルとマージする¶

UMLとCOWデバイスの使用方法によっては、定期的にCOWファイルの変更内容をバックインファイルにマージすることを推奨します。

この作業を行うユーティリティはuml_mooです。使い方は以下の通り:

uml_moo COW_file new_backing_file

バックインファイルを指定する必要はありません。その情報はすでにCOWファイルヘッダーに含まれています。心配する場合は、新しいマージファイルを起動して確認し、問題なければ古いバックインファイルを上書きしてください。

uml_moo デフォルトでは新しいバックインファイルを安全対策として作成します。また、破壊的なマージオプションがあり、COWファイルを現在のバックインファイルに直接マージします。これはバックインファイルにのみ1つのCOWファイルが関連付けられている場合にのみ有効です。複数のCOWファイルが関連付けられている場合、1つのCOWファイルに対して-dマージを行うと、他のすべてのCOWファイルが無効になります。ただし、ディスク容量が限られている場合や、非破壊的マージよりもはるかに高速に動作するため、便利です。

uml_moo uml_mooはUML配布パッケージとともにインストールされ、UMLユーティリティの一部として利用可能です。

ホストファイルへのアクセス¶

ホストマシンのファイルをUML内からアクセスしたい場合は、別個のマシンとして扱い、ホストからnfsマウントディレクトリを設定するか、scpでファイルを仮想マシンにコピーできます。ただし、UMLはホスト上で実行されているため、ネットワークを使わずにホストのファイルに直接アクセスでき、仮想マシン内に提供できます。これはhostfs仮想ファイルシステムの機能です。hostfsを使用すると、ホストディレクトリをUMLファイルシステムにマウントし、ホスト上と同じようにその中のファイルにアクセスできます。

セキュリティ警告

ホストファイルシステムをUMLイメージにマウントし、ホストファイルシステムの任意の部分に書き込むことが可能になります。UMLを実行している場合、hostfsは特定の「安全な」ディレクトリに限定して使用する必要があります（例 /var/tmp)。特にUMLをrootとして実行している場合、これは非常に重要です。

hostfsの使用¶

まず、仮想マシン内でhostfsが利用可能であることを確認してください:

# cat /proc/filesystems

hostfs リストに表示される必要があります。表示されない場合は、hostfsをモジュールとしてコンパイルし、仮想マシン内で利用可能にするか、カーネルを再構築してhostfsを内蔵するか、insmodでモジュールをロードしてください。

次に、mountコマンドを実行するだけで済みます:

# mount none /mnt/host -t hostfs

ホストの / を仮想マシンの /mnt/hostにマウントします。ホストのルートディレクトリをマウントしたくない場合は、-oオプションでマウントするサブディレクトリを指定できます:

# mount none /mnt/home -t hostfs -o /home

ホストの/homeを仮想マシンの/mnt/homeにマウントします。

hostfsをルートファイルシステムとして¶

ホストのディレクトリ階層を使用してhostfsで起動することも可能です。標準のファイルシステムではなく、ファイル内の標準ファイルシステムを使用する代わりに。まず、その階層が必要です。最も簡単な方法は、既存のroot_fsファイルをループマウントすることです:

#  mount root_fs uml_root_dir -o loop

のファイルシステムタイプを / の etc/fstab に変更する必要があります。この行は以下のようになります:

/dev/ubd/0       /        hostfs      defaults          1   1

次に、そのディレクトリ内のroot所有のすべてのファイルの所有者を自分に変更する必要があります。私の場合、以下のように動作しました:

#  find . -uid 0 -exec chown jdike {} \;

次に、UMLカーネルにhostfsがコンパイルされていることを確認してください（モジュールとしてではなく）。その後、ブートデバイスをそのディレクトリに pointing してUMLを実行してください:

ubd0=/path/to/uml/root/directory

UMLは通常通り起動します。

hostfsの注意点¶

hostfsはホスト（UML外）のファイルシステム変更を追跡できません。結果として、UMLの知識の外でファイルが変更された場合、UMLはその変更を認識せず、ファイルのメモリ内のキャッシュが破損する可能性があります。修正は可能ですただし、現在はこの問題に取り組んでいません。

UMLのチューニング¶

現在、UMLは単一プロセッサ（uniprocessor）です。ただし、さまざまな機能を処理するために複数のスレッドを生成します。

UBDドライバ、SIGIO、MMUエミュレーションがその処理を行います。システムがアイドル状態の場合は、これらのスレッドがSMPホストの他のプロセッサに移動します。残念ながら、コア間でのキャッシュ/メモリ同期トラフィックによりパフォーマンスが低下します。結果として、大規模なシステムではUMLが単一CPUに固定されることでパフォーマンスが向上します。一部のベンチマークでは、パフォーマンス差が5倍以上になることがあります。

同様に、大規模な多ノードNUMAシステムでは、UMLが動作するNUMAノードと同じNUMAノードからすべてのメモリを割り当てることでパフォーマンスが向上します。OSは 禁止です デフォルトで実行されます。そのためには、システム管理者が特定のノードにバインドされた適切なtmpfs ramdiskを作成し、TMPまたはTEMP環境変数に指定してUML RAM割当てのソースとして使用する必要があります。UMLはこれらの値を確認します。 TMPDIR, TMP または TEMP そのために確認します。失敗した場合、shmfsがマウントされている場所を確認します。 /dev/shmすべての方法が失敗した場合は、 /tmp/ ファイルシステムタイプに関係なく、

mount -t tmpfs -ompol=bind:X none /mnt/tmpfs-nodeX
TEMP=/mnt/tmpfs-nodeX taskset -cX linux options options options..

UMLへの貢献と開発¶

UMLは新しいLinuxカーネルの概念（ファイルシステム、デバイス、仮想化など）を開発するための優れたプラットフォームです。特定のハードウェアをエミュレートする制約なしに、これらを構築・テストするための無類の機会を提供します。

例 - 4096台の「正しい」ネットワークデバイスでLinuxがどのように動作するか試してみませんか？

UMLでは問題ではありません。一方で、他の仮想化パッケージではこの点が難しいです。それらはエミュレートしようとしているハードウェアバスに許可されるデバイス数に制約されます（例：qemuのPCIバスでは16台）。

パッチ、バグ修正、新機能などの貢献がある場合は、以下に送信してください linux-um@lists.infradead.org

標準的なLinuxパッチガイドラインをすべて遵守してください。関係するメンテナにCCし、 ./sripts/checkpatch.pl パッチを実行してください。詳細については Documentation/process/submitting-patches.rst

注意 - このリストはHTMLや添付ファイルを受け付けません。すべてのメールはプレーンテキスト形式で送信する必要があります。

開発は常にデバッグとセットです。まず、UMLをgdbで実行できます。後述するセクションでその方法を説明します。ただし、これはLinuxカーネルをデバッグするための唯一の方法ではありません。多くの場合、トレースステートメントの追加や、UML固有のアプローチ（UMLカーネルプロセスのptracing）ははるかに情報量が豊富です。

UMLのトレーシング¶

UMLを実行する際には、メインのカーネルスレッドと複数のアシスタントスレッドがあります。トレース対象のスレッドは、UMLがMMUエミュレーションの一環としてすでにptracedしているスレッドではありません。

これらは通常、psディスプレイで表示される最初の3つのスレッドです。PID番号が最も小さくCPU使用率が高いのはカーネルスレッドです。他のスレッドはディスク（ubd）デバイスのアシスタントスレッドとsigioアシスタントスレッドです。このスレッドにptraceを実行すると、次のようになります：

これは主にアイドル状態のUMLインスタンスの典型的な画面です

  • UML割込みコントローラーはepollを使用します - これはUMLがIO割込みを待っている状態です：

    epoll_wait(4, [{EPOLLIN, {u32=3721159424, u64=3721159424}}], 64, 0) = 1

  • ptrace呼び出しのシーケンスはMMUエミュレーションの一環であり、UMLユーザースペースの実行に関与しています

  • timer_settime は、UMLの高解像度タイマサブシステムの一部であり、UML内部のタイマリクエストをホストの高解像度タイマにマッピングします。

  • clock_nanosleep UMLがアイドル状態（PCがACPIアイドルを実行するように）に入るかどうかです。

ご覧の通り、UMLはアイドル状態でも多くの出力を生成します。この出力はIOの観察において非常に情報量が豊富で、実際のIOコール、その引数および戻り値を表示します。

カーネルのデバッグ¶

現在、gdbでUMLを実行することは可能です。ただし、必ずしもgdbで起動されることを許可するわけではありません。実行中のUMLインスタンスにgdbをアタッチしてUMLを実行させることで、ランタイムのバグを追跡する場合にずっと効果的です。

前記の例と同じPID番号を仮定すると、これは以下のようになります：

# gdb -p 16566

これはUMLインスタンスを停止します。したがって、GDBコマンドラインで cont を入力して継続をリクエストする必要があります。この操作をgdbスクリプトとして作成し、gdbに引数として渡すのが良いでしょう。

デバイスドライバの開発¶

ほぼすべてのUMLドライバーはモノリシックです。UMLドライバーをカーネルモジュールとして構築することは可能ですが、これにより実行可能な機能はカーネル内でのみ、かつUML固有でないものに限定されます。これは、UMLを本格的に活用するには、ドライバーの概念をホストのユーザー空間コールにマッピングするユーザー空間コードを書く必要があるためです。

これはいわゆる「ユーザー」部分を形成します。カーネル概念を再利用する点では多くの点で共通していますが、一般的には単なるユーザー空間コードの一部です。この部分には、UMLイメージ内に存在するLinuxカーネル部分を実装する「カーネル」コードが対応する必要があります。

注意：「カーネル」と「ユーザー」がどのように相互作用するかには非常に少ない制限があります.

UMLには厳密に定義されたカーネルからホストへのAPIはありません。特定のアーキテクチャやバスをエミュレートしようとはしません。UMLの「カーネル」と「ユーザー」は、ソフトウェア開発者が思い描く設計を実装するために必要な記憶域、コード、相互作用を共有・実行できます。唯一の制限は技術的なものであり、多くの関数や変数が同じ名前を持つため、開発者は参照しているインクルードやライブラリに注意する必要があります。

その結果、多くのユーザー空間コードは単純なラッパーから構成されています。例えば、 os_close_file() は単なる close() のラッパーであり、ユーザー空間の関数closeがカーネル部分の同名関数と衝突しないようにします。

セキュリティに関する考慮事項¶

ドライバーや新しい機能は、任意のファイル名、BPFコード、またはホストに影響を与える可能性のある他のパラメータをデフォルトで受け入れないべきです。たとえば、ドライバとホスト間のIPC通信に使用するソケットをUMLコマンドラインで指定することはセキュリティ上問題ありませんが、ロード可能なモジュールパラメータとして許可するのは避けるべきです。

特定のアプリケーションでこのような機能が必要な場合（例: ラウドソケットネットワークトランスポート用のBPF「ファームウェア」をロードする場合）、デフォルトでは無効にして、起動時にコマンドラインパラメータとして明示的に有効化する必要があります。

このような点を考慮しても、UMLとホスト間の隔離レベルは相対的に弱いです。UMLユーザースペースが任意のカーネルドライバをロードできる場合、攻撃者がUMLから脱出できる可能性があります。したがって、UMLを生産環境で使用する場合は、すべてのモジュールを起動時にロードし、その後のカーネルモジュールのロードを無効化することをお勧めします。

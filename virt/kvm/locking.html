KVMロック概要¶

1. 取得注文¶

ミューテックスの取得順序は以下の通りです:

  • kvm->lockはvcpu->mutexの外側で取得されます

  • kvm->lockはkvm->slots_lockおよびkvm->irq_lockの外側で取得されます

  • kvm->slots_lockはkvm->irq_lockの外側で取得されます。ただし、両方を同時に取得するケースは非常に稀です。

x86では、vcpu->mutexはkvm->arch.hyperv.hv_lockの外側で取得されます

その他はすべて葉ノードです: キリカセクション内では他のロックは取得されません。

2. 例外¶

高速ページフォールト:

高速ページフォールトは、x86においてmmu-lockを外側でゲストのページフォールトを修正する高速パスです。現在、ページフォールトが高速になるケースは以下の2つの場合があります:

  1. アクセストラッキング: SPTEは存在しないが、アクセストラッキング用に設定されている(i.e. SPTE_SPECIAL_MASKが設定されている)。これは保存されたR/Xビットを復元する必要があります。詳しくは後述します。

  2. 書き込み保護: SPTEは存在し、フォールトは書き込み保護によって発生しています。これはspteのWビットを変更するだけで済みます。

レースを回避するために使用するビットはspte上のSPTE_HOST_WRITEABLEビットとSPTE_MMU_WRITEABLEビットです:

  • SPTE_HOST_WRITEABLEはホスト側でgfnが書き込み可能を示します。

  • SPTE_MMU_WRITEABLEはMMU側でgfnが書き込み可能を示します。このビットはゲストMMUでgfnが書き込み可能であり、シャドウページ書き込み保護で保護されていないときに設定されます。

高速ページフォールトパスでは、cmpxchgを用いてspteのWビットを原子的に設定します。条件はspte.SPTE_HOST_WRITEABLE=1かつspte.SPTE_WRITE_PROTECT=1の場合、またはVMX_EPT_TRACK_ACCESSマスクが設定されている場合、または両方です。これはcmpxchgでこれらのビットの変更を検出できるため安全です。

ただし、以下のケースを慎重に確認する必要があります:

  1. gfnからpfnへのマッピング

gfnからpfnへのマッピングはcmpxchg中に変更される可能性があります。これはpfnが変更されないことを保証できるため、ABA問題が発生します。例えば以下のケースが発生します:

開始時:

gpte = gfn1
gfn1 is mapped to pfn1 on host
spte is the shadow page table entry corresponding with gpte and
spte = pfn1

高速ページフォールトパス:

CPU 0:

CPU 1:

 
old_spte = *spte;

pfn1がスワップアウト:

spte = 0;

pfn1がgfn2のために再割当:

ゲストがgpteをgfn2にポインタを変更:

spte = pfn1;

if (cmpxchg(spte, old_spte, old_spte+W)
    mark_page_dirty(vcpu->kvm, gfn1)
         OOPS!!!

gfn1に対してdirty-logを記録するため、gfn2がdirty-bitmapで失われます。

直接SPの場合、spteがgfnに固定されているため簡単に回避できます。間接SPの場合、簡潔さのため高速ページフォールトを無効化しています。

間接SPに対する解決策として、cmpxchg前に関数kvm_vcpu_gfn_to_pfn_atomicを用いてgfnをピン留めする方法があります。ピン留め後:

  • pfnのrefcountを保持しているため、pfnは解放されず他のgfnに再利用されません。

  • pfnは書き込み可能であり、KSMによって異なるgfn間で共有されません。

次に、ゲストフレーム番号(gfn)に対してDirtyビットマップが正しく設定されていることを確認できます。

  1. Dirtyビットの追跡

元のコードでは、spteが読み取り専用であり、Accessedビットがすでに設定されている場合、AccessedビットとDirtyビットが失われることはないため、spteは高速に更新（非原子的）できます。

しかし、高速ページフォールト後ではこの状態は正しくありません。なぜなら、spteの読み取りと更新の間にspteが書き込み可能にマークされる可能性があるからです。以下のようなケースがあります：

開始時:

spte.W = 0
spte.Accessed = 1

CPU 0:

CPU 1:

mmu_spte_clear_track_bits()関数内では：

old_spte = *spte;


/* 'if' condition is satisfied. */
if (old_spte.Accessed == 1 &&
     old_spte.W == 0)
   spte = 0ull;

高速ページフォールトパスでは：

spte.W = 1

spteへのメモリ書き込み：

spte.Dirty = 1

else
  old_spte = xchg(spte, 0ull)
if (old_spte.Accessed == 1)
  kvm_set_pfn_accessed(spte.pfn);
if (old_spte.Dirty == 1)
  kvm_set_pfn_dirty(spte.pfn);
  OOPS!!!

この場合、Dirtyビットが失われます。

このような問題を避けるため、mmu-lock外で更新される可能性があるspteは常に「volatile」と扱います（spte_has_volatile_bits()を参照）。つまり、この場合spteは常に原子的に行う更新が行われます。

  1. spteの更新によりTLBのフラッシュ

spteが書き込み可能から読み取り専用に更新された場合、すべてのTLBをフラッシュする必要があります。そうでないと、rmap_write_protectが読み取り専用のspteを検出してしまう可能性があります（CPUのTLBに書き込み可能なspteがキャッシュされている場合も）。

前述の通り、高速ページフォールトパスではmmu-lock外でspteが書き込み可能に更新されることがあります。このパスを簡単に監査できるように、mmu_spte_update()関数内でこの理由によるTLBのフラッシュが必要かどうかを確認します。これはspte（存在状態→存在状態）を更新する一般的な関数です。

spteがmmu-lock外で更新される場合、「volatile」とみなされるため、常に原子的に行う更新が行われます。これにより、高速ページフォールトによる競合が回避されます。spte_has_volatile_bits()およびmmu_spte_update()のコメントを参照してください。

ロックレスアクセス追跡：

これはEPTをサポートしていないIntel CPU向けの機能です。KVM MMU通知がページへのアクセスを追跡する際（kvm_mmu_notifier_clear_flush_youngを通じて）、PTEを非存在状態にし、RWXビットをクリアして元のR & Xビットを無視されるビットに保存します。さらに、SPTE_SPECIAL_MASKもPTEに設定されます（無視されるビット62を使用）。VMが後でページにアクセスしようとすると、フォールトが発生し、上記の高速ページフォールトメカニズムが使用されてPTEが存在状態に戻されます。アクセス追跡中にWビットは保存されません。復元時にWビットは、アクセスが書き込みだったかどうかに応じて設定されます。書き込みでなかった場合、Wビットは書き込みが発生するまでクリアのままです。その際、上記のDirty追跡メカニズムを使用して設定されます。

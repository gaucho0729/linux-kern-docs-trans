KVMを用いたネストゲストの実行¶

ネストゲストとは、別のゲストの内部でゲストを実行できる機能であり（KVMベースでも異なるハイパーバイザでも可能）、単純な例はKVMゲストがKVMゲスト上で実行されるケースです（このドキュメントの残りの部分はこの例に基づいています）：

        .----------------.  .----------------.
        |                |  |                |
        |      L2        |  |      L2        |
        | (Nested Guest) |  | (Nested Guest) |
        |                |  |                |
        |----------------'--'----------------|
        |                                    |
        |       L1 (Guest Hypervisor)        |
        |          KVM (/dev/kvm)            |
        |                                    |
.------------------------------------------------------.
|                 L0 (Host Hypervisor)                 |
|                    KVM (/dev/kvm)                    |
|------------------------------------------------------|
|        Hardware (with virtualization extensions)     |
'------------------------------------------------------'

用語:

  • L0 – レベル0; バーメタルホスト、KVMを実行中

  • L1 – レベル1ゲスト; L0上で実行される仮想マシン（VM）; また「ゲストハイパーバイザ」とも呼ばれる、自身でKVMを実行できる機能を持つものです。

  • L2 – レベル2ゲスト; L1上で実行される仮想マシン、これは「ネストゲスト」と呼ばれます

注意

上記の図はx86アーキテクチャに基づいてモデル化されています;s390x、ppc64などの他のアーキテクチャではネストの設計が異なる可能性があります。

例えば、s390xでは常にバーメタル上でLPAR（Logical Partition）ハイパーバイザが実行され、これにより少なくとも4段階のネスト構成が生じます — L0（バーメタル、LPARハイパーバイザを実行中）、L1（ホストハイパーバイザ）、L2（ゲストハイパーバイザ）、L3（ネストゲスト）。

このドキュメントではすべてのアーキテクチャで3段階の用語（L0、L1、L2）を使用し、主にx86に焦点を当てます。

使用例¶

ネストKVMが役立つシナリオはいくつかあります、例を挙げると：

  • 開発者として、ソフトウェアをさまざまなOSでテストしたい場合。クラウドプロバイダーから複数の仮想マシンを借りる代わりに、ネストKVMを用いることで、十分な「ゲストハイパーバイザ」（レベル1ゲスト）を借りることができます。これにより、複数のネストゲスト（レベル2ゲスト）を構築し、異なるOSで開発・テストが可能になります。

  • 「ゲストハイパーバイザ」およびそのネストゲストのライブマイグレーション（負荷分散、災害復旧など）

  • VMイメージ作成ツール（例： virt-installなど）は通常自身のVMを実行し、ユーザーはこれらがVM内でも動作することを期待しています。

  • 一部のOSはセキュリティのため内部で仮想化を採用しています（例：アプリケーションを隔離して安全に実行するため）。

「nested」の有効化 (x86)¶

Linuxカーネルv4.19以降、 nested KVMパラメータはIntelおよびAMDでデフォルトで有効になっています。（ただし、あなたのLinuxディストリビューションがこのデフォルトを上書きしている可能性があります。）

カーネルがv4.19未満の場合、ネストを有効にするには、 nested KVMモジュールパラメータを Y または 1に設定してください。再起動後に設定を維持するには、以下の通り設定ファイルに追加できます：

  1. バーメタルホスト（L0）でカーネルモジュールを一覧表示し、KVMモジュールが含まれているか確認してください：

    $ lsmod | grep -i kvm
kvm_intel             133627  0
kvm                   435079  1 kvm_intel

  2. モジュールに関する情報を表示するには、 kvm_intel コマンドを使用してください：

    $ modinfo kvm_intel | grep -i nested
parm:           nested:bool

  3. ネストKVMの設定を再起動後に維持するには、以下の内容を /etc/modprobed/kvm_intel.conf （ファイルが存在しない場合は作成してください）に追加してください：

    $ cat /etc/modprobe.d/kvm_intel.conf
options kvm-intel nested=y

  4. KVM Intelモジュールをアンロードして再ロードしてください：

    $ sudo rmmod kvm-intel
$ sudo modprobe kvm-intel

  5. 以下のコマンドで nested KVMのパラメータが有効になっています:

    $ cat /sys/module/kvm_intel/parameters/nested
Y

AMDホストの場合、上記のプロセスは同じですが、モジュール名は kvm-amd.

ネスト関連のカーネルパラメータ (x86)¶

ハードウェアが十分に進化している場合（Intel Haswellプロセッサまたはそれ以上のもので、新しいハードウェア仮想拡張機能を備えている場合）、以下の追加機能もデフォルトで有効になります: 「シャドウVMCS（仮想マシン制御構造）」、ホストのバーメタルホスト（L0）におけるAPIC仮想化。Intelホストのパラメータ:

$ cat /sys/module/kvm_intel/parameters/enable_shadow_vmcs
Y

$ cat /sys/module/kvm_intel/parameters/enable_apicv
Y

$ cat /sys/module/kvm_intel/parameters/ept
Y

注意

L2（つまりネストゲスト）が遅く動作していると疑う場合は、上記のパラメータが有効になっていることを確認してください（特に enable_shadow_vmcs および ept).

ネストゲストの起動 (x86)¶

バーメタルホスト（L0）がネスト設定に適応したら、以下の設定でL1ゲストを起動できます:

$ qemu-kvm -cpu host [...]

上記はホストCPUの機能をそのままゲストに渡しますが、ライブマイグレーションの互換性を高めるためには、QEMUでサポートされている名前付きCPUモデルを使用してください。例:

$ qemu-kvm -cpu Haswell-noTSX-IBRS,vmx=on

これにより、ゲストハイパーバイザは加速されたKVMでネストゲストを実行できるようになります。

ネストされたKVMを用いたライブマイグレーション¶

これにより、L1（ゲストハイパーバイザ）でKVMモジュールをロードできます: live ネストゲストを含むL1ゲストを別のバーメタルホストにマイグレーションする機能は、Linuxカーネル5.3およびQEMU 4.2.0からIntel x86システムで利用可能となり、s390xではより古いバージョンでも動作します。

AMDシステムでは、L1ゲストがL2ゲストを起動した後、L1ゲストのマイグレーションや保存（QEMUドキュメンテーションの「savevm」/「loadvm」参照）はL2ゲストがシャットダウンするまで行うべきではありません。L2ゲストが動作している間、L1ゲストをマイグレーションまたは保存・読み込みしようとすると未定義の動作が発生します。このようなマイグレーションまたは読み込まれたL1ゲストは安定的またはセキュアとは見なされなくなり、再起動が必要です。L2ゲストを実行していない状態でネストをサポートするように設定されたL1ゲストをマイグレーションしても、AMDシステムでは通常動作しますが、ゲストが起動すると失敗する可能性があります。 kernel BUG! ネストゲスト（L2）のマイグレーションは常に成功するため、以下のすべてのシナリオはAMDシステムでも動作します: dmesgネストゲスト（L2）を別のL1ゲストにマイグレーションする

ネストゲスト（L2）を別のL1ゲストにマイグレーションする

  • ネストゲスト（L2）を別のL1ゲストにマイグレーションする 同じ バーメタルホスト上

  • ネストゲスト（L2）を別のL1ゲストにマイグレーションする 異なる バーメタルホスト上

  • ネストゲスト（L2）をバーメタルホストにマイグレーションする

ネストされた設定からのバグの報告¶

「ネストされた」問題のデバッグには、L0、L1、L2のログファイルを確認する作業が含まれ、これにより、バグ報告者と修正者間で煩雑な往復が生じることがあります。

  • 「ネストされた」設定であることを明記してください。ネスト処理を行っている場合は、その旨を必ずお伝えください。残念ながら、バグ報告時にこの点を忘れてしまう人が多いので、明記する必要があります。 mention ネストされた仮想化を実行していることを

  • KVMがKVM上で実際に動作していることを確認してください。時折、ゲスト仮想マシン（L1）のKVMが有効になっていない場合があり、これにより純粋なエミュレーション（QEMUでは「TCG」と呼ばれる）で動作しているにもかかわらず、ネストされたKVMを実行していると誤認していることがあります。これにより、「ネストされた仮想化」（QEMU on KVMを含む）と「ネストされたKVM」（KVM on KVM）の区別が曖昧になることがあります。

KVM（Kernel-based Virtual Machine）APIドキュメンテーション（完全版）¶

1. 一般的な説明¶

kvm APIは、仮想マシンのさまざまな側面を制御するために発行されるioctlの集合です。ioctlは以下のクラスに分類されます：

  • システムioctl: これらは、全体のkvmサブシステムに影響を与えるグローバル属性を照会および設定します。また、システムioctlは仮想マシンの作成にも使用されます。

  • VM ioctl: これらは、仮想マシン全体に影響を与える属性を照会および設定します。例えばメモリレイアウトなどです。また、VM ioctlは仮想CPU（vcpu）やデバイスの作成にも使用されます。

    VM ioctlは、VMを作成したプロセス（アドレス空間）からのみ発行する必要があります。

  • vcpu ioctl: これらは、単一の仮想CPUの操作を制御する属性を照会および設定します。

    vcpu ioctlは、vcpuを作成したスレッドから発行する必要があります。ただし、ドキュメンテーションで「非同期」と明記されている例外を除きます。スレッドを切り替えた後で最初のioctlを実行するとパフォーマンスへの影響が生じる可能性があります。

  • デバイスioctl: これらは、単一のデバイスの操作を制御する属性を照会および設定します。

    デバイスioctlは、VMを作成したプロセス（アドレス空間）からのみ発行する必要があります。

2. ファイル記述子¶

kvm APIはファイル記述子を中心に構成されています。初期のopen("/dev/kvm")はkvmサブシステムのハンドルを取得し、このハンドルを使用してシステムioctlを発行できます。このハンドルにKVM_CREATE_VM ioctlを実行すると、VMファイル記述子が作成され、VM ioctlを発行できます。VM fdにKVM_CREATE_VCPUまたはKVM_CREATE_DEVICE ioctlを実行すると、仮想CPUまたはデバイスが作成され、新しいリソースへのファイル記述子が返されます。最後に、vcpuまたはデバイスfdのioctlは、vcpuまたはデバイスの制御に使用されます。vcpuには、ゲストコードの実行という重要なタスクも含まれます。

一般的に、ファイル記述子はfork()やunixドメインソケットのSCM_RIGHTS機能によってプロセス間で移動できます。ただし、kvmではこのようなトリックは明示的にサポートされていません。これらはホストに害を及ぼさないものの、APIの保証された動作は保証されません。KVMがサポートするioctlの使用モデルについては「一般的な説明」を参照してください。

VM ioctlは、VMを作成したプロセスのみから発行される必要がありますが、VMのライフサイクルはそのファイル記述子に関連しており、作成者（プロセス）とは関係ありません。言い換えれば、VMとそのリソース、関連するアドレス空間を含む ファイル記述子に依存していますVMのファイルディスクリプタへの最後の参照が解放されるまで、VMは解放されません。たとえば、ioctl(KVM_CREATE_VM)の後にfork()が実行された場合、VMは親プロセス（元のプロセス）とその子プロセスがVMのファイルディスクリプタへの参照を解放するまで解放されません。

VMのリソースは、VMのファイルディスクリプタへの最後の参照が解放されるまで解放されないため、fork()、dup()などによりVMへの追加の参照を生成する際には、慎重な考慮が欠かせません。これは不望な副作用を引き起こす可能性があり、たとえばVMのプロセスによって割り当てられたメモリがVMがシャットダウン時に解放されず、未計上となる可能性があります。

3. 拡張機能¶

Linux 2.6.22以降、KVM ABIは安定しており、後方不兼容な変更は許可されていません。ただし、後方互換性のある拡張機能をAPIに問い合わせて使用できる拡張機能の仕組みがあります。

拡張機能のメカニズムはLinuxのバージョン番号に基づいていません。代わりに、kvmが拡張機能の識別子を定義し、特定の拡張機能識別子が利用可能かどうかを問い合わせる仕組みを提供します。利用可能な場合は、アプリケーションで使用できるioctlのセットが利用可能です。

4. APIの説明¶

このセクションでは、KVMゲストを制御するためのioctlについて説明します。各ioctlについて、以下の情報と説明が提供されます：

キャパビリティ：

このioctlを提供するKVM拡張機能。'basic'の場合、APIバージョン12をサポートするすべてのカーネルで提供されるため、'KVM_CAP_xyz'定数の場合にはKVM_CHECK_EXTENSION（セクション4.4参照）で利用可能かどうかを確認する必要があります。'none'の場合、すべてのカーネルがこのioctlをサポートしない場合でも、利用可能かどうかを確認するキャピビリティビットは存在しないため、サポートしていないカーネルではioctlが-ENOTTYを返します。

アーキテクチャ:

このioctlを提供する指令セットアーキテクチャ。x86にはi386とx86_64が含まれます。

タイプ:

system、vm、vcpu。

パラメータ:

このioctlが受け取るパラメータ。

戻り値:

戻り値。一般的なエラー番号（EBADF、ENOMEM、EINVAL）については詳細は省略しますが、特定の意味を持つエラーについては説明します。

4.2 KVM_CREATE_VM¶

機能

basic

アーキテクチャ

すべての読者が完了するまで待機したとしても、更新処理が読者がいないと信頼できる期間はゼロである。

タイプ

システムioctl

パラメータ

マシンタイプ識別子 (KVM_VM_*)

を渡します。

新しい仮想マシンを制御するために使用できるVM fdです。

新しいVMには仮想CPUもメモリもありません。おそらく0をマシンタイプとして使用することをお勧めします。

S390上でのユーザー制御の仮想マシンを作成するには、KVM_CAP_S390_UCONTROLを確認し、権限のあるユーザー（CAP_SYS_ADMIN）としてフラグKVM_VM_S390_UCONTROLを使用してください。

MIPS（VZ ASE）でのハードウェア支援仮想化を使用する代わりに、デフォルトのトラップ＆エミュレート実装（仮想メモリレイアウトをユーザーモードに合わせて変更）を使用する場合は、KVM_CAP_MIPS_VZを確認し、フラグKVM_VM_MIPS_VZを使用してください。

arm64では、VMの物理アドレスサイズ（IPA Size limit）はデフォルトで40ビットに制限されます。ホストが拡張機能KVM_CAP_ARM_VM_IPA_SIZEをサポートする場合、この制限は設定可能です。サポートされている場合は、マシンタイプ識別子でKVM_VM_TYPE_ARM_IPA_SIZE(IPA_Bits)を使用してサイズを設定します。IPA_BitsはVMで使用される物理アドレスの最大幅を表します。IPA_Bitsはマシンタイプ識別子のビット[7-0]にエンコードされます。

例として、ゲストが48ビットの物理アドレスサイズを使用するように構成する場合:

vm_fd = ioctl(dev_fd, KVM_CREATE_VM, KVM_VM_TYPE_ARM_IPA_SIZE(48));

要求されるサイズ（IPA_Bits）は:

0

40ビット（後方互換性のためのデフォルトサイズ）を示します

N

Nビットを示します。ここでNは正の整数であり、32 <= N <= Host_IPA_Limitを満たす必要があります。

Host_IPA_LimitはホストでIPA_Bitsの最大値であり、CPUの能力とカーネル構成に依存します。この制限は、KVM_CHECK_EXTENSION ioctl()でKVM_CAP_ARM_VM_IPA_SIZEを使用して実行時により取得可能です。

ホストで要求されたIPAサイズ（明示的または暗黙的であれ）がサポートされていない場合、VMの作成は失敗します。

IPAサイズの設定がゲストCPUのID_AA64MMFR0_EL1[PARange]で露出される能力に影響を与えないことにご注意ください。これは、ステージ2レベルでアドレスが翻訳されるサイズにのみ影響します（ゲスト物理アドレスからホスト物理アドレスへの翻訳）。

4.7 KVM_CREATE_VCPU¶

機能

basic

アーキテクチャ

すべての読者が完了するまで待機したとしても、更新処理が読者がいないと信頼できる期間はゼロである。

タイプ

vm ioctl

パラメータ

vcpu ID（x86ではAPIC ID）

を渡します。

成功時はvcpu fd、エラー時は-1

このAPIは仮想マシンにvcpuを追加します。追加可能な最大数はmax_vcpusを超えてなりません。vcpu IDは[0, max_vcpu_id)の範囲の整数です。

推奨されるmax_vcpus値は、KVM_CHECK_EXTENSION ioctl()のKVM_CAP_NR_VCPUSを実行時に取得できます。max_vcpusの最大可能値は、KVM_CHECK_EXTENSION ioctl()のKVM_CAP_MAX_VCPUSを実行時に取得できます。

KVM_CAP_NR_VCPUSが存在しない場合、max_vcpusは4コア最大とみなします。KVM_CAP_MAX_VCPUSが存在しない場合、max_vcpusはKVM_CAP_NR_VCPUSから返された値と同一とみなします。

max_vcpu_idの最大可能値は、KVM_CHECK_EXTENSION ioctl()でKVM_CAP_MAX_VCPU_IDを使用して実行時に行います。

KVM_CAP_MAX_VCPU_IDが存在しない場合、max_vcpu_idはKVM_CAP_MAX_VCPUSから返された値と同一とみなします。

powerpcでbook3s_hvモードを使用する場合、vcpuは1つ以上の仮想CPUコア内の仮想スレッドにマッピングされます。(これはハードウェアがCPUコア内のすべてのハードウェアスレッドが同一パーティションに属する必要があるためです。) KVM_CAP_PPC_SMT能力は、仮想コア(vcore)あたりのvcpu数を示します。vcore IDは、vcpu IDをvcoreあたりのvcpu数で割ることで取得します。あるvcore内のvcpuは常に互いに同じ物理コアに配置されます(ただし、時間によっては異なる物理コアになる可能性もあります)。ユーザースペースは、vcpu IDの割り当てによってゲストのスレッディング(SMT)モードを制御できます。たとえば、ユーザースペースが単一スレッドのゲストvcpuを望む場合、すべてのvcpu IDをvcoreあたりのvcpu数の倍数に設定する必要があります。

S390ユーザー制御仮想マシンで作成された仮想CPUについては、仮想CPUのハードウェア制御ブロックのメモリマップを取得するために、ページオフセットKVM_S390_SIE_PAGE_OFFSETでメモリマップできます。

PPC:¶

外部割り込みを注入するキューを生成します。このioctlは3種類のirq値をサポートしています：

  1. KVM_INTERRUPT_SET

    ゲストが割り込みを受信できる状態になったときにエッジタイプの外部割り込みを注入します。注入後は割り込みが完了します。

  2. KVM_INTERRUPT_UNSET

    未解決の割り込みを解除します。

    KVM_CAP_PPC_UNSET_IRQ が有効な場合のみ利用可能です。

  3. KVM_INTERRUPT_SET_LEVEL

    KVM_CAP_PPC_IRQ_LEVEL が有効な場合のみ利用可能です。

注意: 上記の値以外の ‘irq’ の値は無効であり、予期せぬ挙動を引き起こします。

これは非同期の vcpu ioctl であり、任意のスレッドから呼び出すことができます。

仮想CPUにインジェクトされる外部割り込みをキューに入れます。負の割り込み番号は割り込みをキューから外します。

これは非同期の vcpu ioctl であり、任意のスレッドから呼び出すことができます。

4.25 KVM_IRQ_LINE¶

機能

KVM_CAP_IRQCHIP

アーキテクチャ

x86, arm, arm64

タイプ

vm ioctl

パラメータ

struct kvm_irq_level

を渡します。

成功時は0、エラー時は-1

カーネル内の割り込み制御器モデルにGSI入力のレベルを設定します。一部のアーキテクチャでは、KVM_CREATE_IRQCHIPで割り込み制御器モデルが事前に作成されている必要があります。注意：エッジトリガー割り込みではレベルを1に設定し、その後0に戻す必要があります。

実際のハードウェアでは、割り込みピンはアクティブローまたはアクティブハイのいずれかです。struct kvm_irq_levelのレベルフィールドでは、1は常にアクティブ（アサート）、0は非アクティブ（デアサート）を意味します。

x86ではOSがレベルトリガー割り込みの極性（アクティブロー/アクティブハイ）をプログラミングでき、KVMは以前は極性を考慮していました。しかし、アクティブロー割り込みの処理におけるbitrotのため、x86でも上記の規約が有効です。これはKVM_CAP_X86_IOAPIC_POLARITY_IGNOREDで示されます。ユーザースペースは、この能力が存在しない場合（またはカーネル内割り込みチップを使用していない場合を除く）、ゲストにアクティブロー割り込みを提示すべきではありません。

ARM/arm64ではCPUレベルまたはカーネル内割り込みチップ（GIC）で割り込みを信号できます。カーネル内割り込みチップではGICに特定のCPU用のPPIを指定できます。irqフィールドは以下のように解釈されます：

bits:  |  31 ... 28  | 27 ... 24 | 23  ... 16 | 15 ... 0 |
field: | vcpu2_index | irq_type  | vcpu_index |  irq_id  |

irq_type フィールドには次の値があります:

  • irq_type[0]:

    out-of-kernel GIC: irq_id 0 は IRQ、irq_id 1 は FIQ

  • irq_type[1]:

    in-kernel GIC: SPI、irq_id は 32 から 1019（含む）の範囲（vcpu_index フィールドは無視されます）

  • irq_type[2]:

    in-kernel GIC: PPI、irq_id は 16 から 31（含む）の範囲

(irq_id フィールドはARM GIC仕様のIRQ IDとよく対応しています)

どちらの場合もlevelフィールドはラインのアサート/デアサートに使用されます。

KVM_CAP_ARM_IRQ_LINE_LAYOUT_2がサポートされている場合、ターゲットのvcpuは(256 * vcpu2_index + vcpu_index)で識別されます。それ以外の場合、vcpu2_indexはゼロでなければなりません。

ARM/arm64では、KVM_CAP_IRQCHIP能力はin-kernel irqchipの割り込み注入にのみ影響します。KVM_IRQ_LINEはユーザースペースの割り込みコントローラーに対して常に使用可能です。

struct kvm_irq_level {
      union {
              __u32 irq;     /* GSI */
              __s32 status;  /* not used for KVM_IRQ_LEVEL */
      };
      __u32 level;           /* 0 or 1 */
};

ARM/ARM64:¶

ゲストがホストカーネルがエミュレートしているデバイスにアクセスし、実際のデバイスが物理的な SError を生成するようにする場合、KVM はその VCPU に仮想的な SError を待機状態にします。このシステムエラー割込みは、ゲストが PSTATE.A をアンマスクして例外を処理するまで待機状態のままです。

VCPU の実行中に待機中の SError を処理するか、アクセスによって SError が待機状態になる可能性があります。イベントの説明は VCPU が実行されていない間のみ有効です。

この API は、ゲストに見えない待機中の「イベント」状態を読み書きする方法を提供します。VCPU の保存、復元、移動には、この GET/SET API を使用して状態を読み書きし、他のゲスト可視レジスタと併用します。待機中の SError はキャンセルできません。

ユーザースペースでエミュレートされているデバイスも SError を生成できます。これを行うには、ユーザースペースがイベント構造体を埋めます。まず現在の状態を読み取って、既存の SError が待機していないことを確認します。既存の SError が待機している場合、アーキテクチャの「複数の SError 割込み」ルールに従う必要があります。(DDI0587.a 「ARM 可靠性、可用性、サービス性 (RAS) 指南」の 2.5.3 節)

SError 例外には常に ESR 値があります。一部の CPU は仮想 SError の ESR 値を指定できる機能を持っています。このようなシステムは KVM_CAP_ARM_INJECT_SERROR_ESR をアドバタイズします。この場合、exception.has_esr は常にゼロ以外の値になります。待機中の SError を生成するエージェントは、exception.serror_esr の下位 24 ビットに ISS フィールドを指定する必要があります。システムが KVM_CAP_ARM_INJECT_SERROR_ESR をサポートしていても、ユーザースペースが exception.has_esr をゼロに設定した場合、KVM は ESR を選択します。

例外処理.has_esrをサポートしていないシステムで指定すると-EINVALが返されます。exception.serror_esrの下位24ビット以外を設定すると-EINVALが返されます。

待機中の外部アボート（KVM_SET_VCPU_EVENTSを通じてインジェクトされたものも含む）を読み戻すことはできません。このような例外は常に仮想CPUに直接配信されるためです。

struct kvm_vcpu_events {
      struct {
              __u8 serror_pending;
              __u8 serror_has_esr;
              __u8 ext_dabt_pending;
              /* Align it to 8 bytes */
              __u8 pad[5];
              __u64 serror_esr;
      } exception;
      __u32 reserved[12];
};

ゲストがI/Oメモリへのアクセスを行い、ユーザー空間が処理できない場合（例：インストラクションシンドロームデコード情報の不足や、アクセスされたIPAにデバイスがマッピングされていない場合など）、ユーザー空間は、VCPUのエクソイット時のフォールトアドレスを用いて外部アボートをインジェクトするようにカーネルを依頼できます。エクソイットがKVM_EXIT_MMIOまたはKVM_EXIT_ARM_NISV以外のものである場合、ext_dabt_pendingを設定することはプログラミングエラーです。この機能はKVM_CAP_ARM_INJECT_EXT_DABTをサポートするシステムでのみ利用可能です。これは、ユーザー空間が上記のケースでゲストにアクセスを報告する際の共通性を提供するヘルパーであり、異なるユーザー空間実装間で一貫性を保つためのものです。ただし、ユーザー空間はKVM_SET_ONE_REG APIを用いて個々のレジスタを操作することで、すべてのArm例外をエミュレートすることも可能です。

データ構造についてはKVM_GET_VCPU_EVENTSを参照してください。

機能

KVM_CAP_USER_MEMORY

アーキテクチャ

すべての読者が完了するまで待機したとしても、更新処理が読者がいないと信頼できる期間はゼロである。

タイプ

vm ioctl

パラメータ

を渡します。

成功時は0、エラー時は-1

struct kvm_userspace_memory_region {
      __u32 slot;
      __u32 flags;
      __u64 guest_phys_addr;
      __u64 memory_size; /* bytes */
      __u64 userspace_addr; /* start of the userspace allocated memory */
};

/* for kvm_memory_region::flags */
#define KVM_MEM_LOG_DIRTY_PAGES       (1UL << 0)

このioctlは、ユーザーがゲスト物理メモリスロットを生成、変更、または削除できるようにします。"slot"のビット0〜15はスロットIDを指定し、この値はVMごとの最大ユーザーメモリスロット数未満でなければなりません。最大スロット数はKVM_CAP_NR_MEMSLOTSを使用して照会できます。スロットはゲスト物理アドレス空間で重複してはなりません。

KVM_CAP_MULTI_ADDRESS_SPACEが利用可能であれば、"slot"のビット16〜31は変更されるアドレス空間を指定します。これらはKVM_CHECK_EXTENSIONでKVM_CAP_MULTI_ADDRESS_SPACEの値未満でなければなりません。異なるアドレス空間のスロットは無関係であり、重複の制限は各アドレス空間内で適用されます。

スロットの削除はmemory_sizeをゼロに設定することで行います。既存のスロットを変更する場合、ゲスト物理メモリ空間内で移動したり、フラグを変更したりできますが、サイズ変更はできません。

領域のメモリはuserspace_addrフィールドで指定されたアドレスから開始され、このアドレスは全体のメモリスロットサイズ分ユーザーがアクセス可能なメモリを指さなければなりません。このメモリは匿名メモリ、通常ファイル、hugetlbfsなどの任意のオブジェクトで構成できます。

アドレスタグがサポートされるアーキテクチャでは、userspace_addrは未タグ付けされたアドレスでなければなりません。

ゲスト_phys_addrとuserspace_addrの下位21ビットが同一であることを推奨します。これにより、ゲストの大ページがホストの大ページでサポートされます。

flagsフィールドはKVM_MEM_LOG_DIRTY_PAGESとKVM_MEM_READONLYの2つのフラグをサポートします。前者はKVMがスロット内のメモリへの書き込みを追跡するように指示します。KVM_GET_DIRTY_LOG ioctlを使用方法を参照してください。後者はKVM_CAP_READONLY_MEMの能力が許可されている場合、新しいスロットを読み取り専用に設定できます。この場合、このメモリへの書き込みはKVM_EXIT_MMIOでユーザー空間にポストされます。

KVM_CAP_SYNC_MMUの能力が利用可能であれば、メモリ領域のバックの変更は自動的にゲストに反映されます。たとえば、影響を与えるmmap()は即座に表示され、もう一つの例はmadvise(MADV_DROP)です。

KVM_SET_MEMORY_REGION ioctlではなく、このAPIを使用することをお勧めします。KVM_SET_MEMORY_REGIONはメモリ割当の細かい制御を許可せず、非推奨です。

ユーザー空間は、'nent'フィールドにエントリ数を指定してkvm_cpuid2構造体を渡してKVM_GET_SUPPORTED_CPUIDを呼び出します。エントリ数がCPU機能を十分に記述できない場合、エラー（E2BIG）が返されます。エントリ数が多すぎる場合、'nent'フィールドが調整され、エラー（ENOMEM）が返されます。エントリ数がちょうど良い場合、'nent'フィールドが'entries'配列内の有効なエントリ数に調整され、その後配列が埋められます。

返されるエントリは、cpuid命令で返されるホストcpuidであり、未知またはサポートされていない機能はマスクされています。一部の機能（例：x2apic）はホストCPUに存在しない場合がありますが、KVMがそれらを効率的にエミュレートできる場合、KVMによって暴露されます。各エントリのフィールドは以下の通りです：

関数：

エントリを取得するために使用したeax値

インデックス：

エントリを取得するために使用したecx値（ecxによって影響を受けるエントリの場合）

フラグ:

以下のいずれかのOR:

KVM_CPUID_FLAG_SIGNIFCANT_INDEX:

インデックスフィールドが有効である場合

eax, ebx, ecx, edx:

この関数/インデックス組み合わせに対するcpuid命令で返される値

TSCデッドラインタイマーフィーチャー（CPUIDリーフ1、ecx[24]）は常にfalseとして返されます。このフィーチャーはKVM_CREATE_IRQCHIPによるローカルAPICサポートに依存するためです。代わりに以下の通り報告されます：

ioctl(KVM_CHECK_EXTENSION, KVM_CAP_TSC_DEADLINE_TIMER)

その結果がtrueを返し、KVM_CREATE_IRQCHIPを使用する場合、またはユーザー空間でこのフィーチャーをエミュレートする場合、KVM_SET_CPUID2でこのフィーチャーを有効にすることができます。

機能

アーキテクチャ

タイプ

vm ioctl

パラメータ

struct kvm_ioeventfd {
      __u64 datamatch;
      __u64 addr;        /* legal pio/mmio address */
      __u32 len;         /* 0, 1, 2, 4, or 8 bytes    */
      __s32 fd;
      __u32 flags;
      __u8  pad[36];
};

s390におけるvirtio-ccwデバイスの特別なケースでは、ioeventはサブチャネル/virtqueueのタプルにマッチされます。

以下のフラグが定義されています：

#define KVM_IOEVENTFD_FLAG_DATAMATCH (1 << kvm_ioeventfd_flag_nr_datamatch)
#define KVM_IOEVENTFD_FLAG_PIO       (1 << kvm_ioeventfd_flag_nr_pio)
#define KVM_IOEVENTFD_FLAG_DEASSIGN  (1 << kvm_ioeventfd_flag_nr_deassign)
#define KVM_IOEVENTFD_FLAG_VIRTIO_CCW_NOTIFY \
      (1 << kvm_ioeventfd_flag_nr_virtio_ccw_notify)

datamatchフラグが設定されている場合、登録されたアドレスへの書き込み値がstruct kvm_ioeventfdのdatamatchと等しい場合にのみイベントがシグナルされます。

virtio-ccwデバイスでは、addrはサブチャネルIDを、datamatchはvirtqueueインデックスを含みます。

KVM_CAP_IOEVENTFD_ANY_LENGTHにより、ゼロ長さのioeventfdが許可され、カーネルはゲストの書き込み長さを無視し、より高速なvmexitが可能になります。この速度アップは特定のアーキテクチャにのみ適用される可能性がありますが、ioeventfdはいずれにしても動作します。

struct kvm_dirty_tlb {

ユーザー空間が共有TLBのエントリを変更した際、関連するvcpuに対してKVM_RUNを呼び出す前に必ず呼び出す必要があります。

機能

これは、PAPRスタイルの仮想I/O用のIOMMUとして機能する仮想TCE（トランスレーションコントロールエントリ）テーブルを作成します。論理アドレスをゲスト物理アドレスに変換し、PAPR仮想I/Oのスキャッタ/ガッタ能力を提供します。

この機能は、起動時にカーネルが割り当てたプールからリアルモード領域（RMA）を割り当てます。RMAは、古いPOWERプロセッサでリアルモード（MMUオフ）アクセスが行われるKVMゲストにアクセス可能なメモリを提供する、物理的に連続かつアライメントされたメモリ領域です。POWERプロセッサはRMAのサイズとして64MB、128MB、256MB、およびいくつかの大きな2の累乗をサポートします。

0x6080 0000 0015 00 <n:5> <slice:5>   Zn bits[2048*slice + 2047 : 2048*slice]
0x6050 0000 0015 04 <n:4> <slice:5>   Pn bits[256*slice + 255 : 256*slice]
0x6050 0000 0015 060 <slice:5>        FFR bits[256*slice + 255 : 256*slice]

2048 * slice >= 128 * max_vqとなるレジスタIDへのアクセスはENOENTで失敗します。max_vqはvcpuがサポートする最大ベクターレンジ長（128ビットクワッドワード単位）です：参照 2 も参照してください。

これらのレジスタはSVEが有効化されたvcpuでのみアクセス可能です。詳細はKVM_ARM_VCPU_INITを参照してください。

さらに、KVM_REG_ARM64_SVE_VLSを除き、これらのレジスタはvcpuのSVE構成がKVM_ARM_VCPU_FINALIZE(KVM_ARM_VCPU_SVE)で確定されるまでアクセスできません。詳細はKVM_ARM_VCPU_INITおよびKVM_ARM_VCPU_FINALIZEを参照してください。

KVM_REG_ARM64_SVE_VLSは擬似レジスタであり、ユーザー空間がvcpuがサポートするベクターレンジ長を発見および設定できるようにします。KVM_GET_ONE_REGまたはKVM_SET_ONE_REGを介してユーザーメモリとやり取りする際、このレジスタの値は__u64[KVM_ARM64_SVE_VLS_WORDS]型であり、以下の通りベクターレンジ長をエンコードします：

__u64 vector_lengths[KVM_ARM64_SVE_VLS_WORDS];

if (vq >= SVE_VQ_MIN && vq <= SVE_VQ_MAX &&
    ((vector_lengths[(vq - KVM_ARM64_SVE_VQ_MIN) / 64] >>
              ((vq - KVM_ARM64_SVE_VQ_MIN) % 64)) & 1))
      /* Vector length vq * 16 bytes supported */
else
      /* Vector length vq * 16 bytes not supported */
2

上記の条件が成立する最大のvq値はmax_vqです。これはこのvcpuでゲストが利用可能な最大ベクターレンジ長であり、このioctlインターフェースを通じてどのレジスタスライスが見えるかを決定します。

(参照 AArch64 Linuxにおけるスケーラブルベクターエクステンション（SVE）サポート で「vq」の命名規則についての説明があります。)

KVM_REG_ARM64_SVE_VLSはKVM_ARM_VCPU_INIT後にのみアクセス可能です。KVM_ARM_VCPU_INITはホストがサポートする最良のベクターレンジ長セットで初期化します。

ユーザー空間は、vcpuのSVE構成がKVM_ARM_VCPU_FINALIZE(KVM_ARM_VCPU_SVE)で確定されるまで、必要に応じてこのレジスタを変更できます。

ホストセットからベクターレンジが指定された値を超えるものをすべて削除する以外、選ばれたベクターレンジのセットに対するサポートはハードウェア依存であり、利用可能であるとは限りません。KVM_SET_ONE_REGを介して無効なベクターレンジのセットを設定しようとすると、EINVALで失敗します。

vcpuのSVE構成が確定した後、このレジスタへの書き込みはEPERMで失敗します。

これは、KVMがサポートする「Server」クラスMMUエミュレーションの機能を記述する構造体を生成・返却します。この構造体は、ゲストOSに適切なデバイスツリーのプロパティを生成するためにユーザースペースで使用できます。

この構造体には、まずグローバルな情報が含まれ、その後にサポートされるセグメントページサイズの配列が続きます:

struct kvm_ppc_smmu_info {

       __u32 slb_size;
       __u32 pad;

サポートされるフラグは以下の通りです:

  • KVM_PPC_PAGE_SIZES_REAL:

    このフラグが設定されている場合、ゲストのページサイズは「バックイングストアのページサイズに合わせる必要があります。」設定されていない場合、リスト内の任意のページサイズを使用できます（ユーザースペースのバックイングにかかわらず）。

  • KVM_PPC_1T_SEGMENTS

    エミュレートされるMMUは、標準の256Mセグメントに加えて1Tセグメントもサポートします。

  • KVM_PPC_NO_HASH

    このフラグは、KVMがHPTゲストをサポートしないことを示します。したがって、すべてのゲストはラディックスMMUモードを使用しなければなりません。

「slb_size」フィールドはサポートされるSLBエントリ数を示します

「sps」配列には、セグメントごとのサポートされるベースページサイズが増加順に8項目含まれています。各項目は以下のようになります:

struct kvm_ppc_one_seg_page_size {
     __u32 page_shift;       /* Base page shift of segment (or 0) */
     __u32 slb_enc;          /* SLB encoding for BookS */
     struct kvm_ppc_one_page_size enc[KVM_PPC_PAGE_SIZES_MAX_SZ];
};

「page_shift」が0の項目は使用されません。配列が増加順に並んでいるため、このような項目に出会うと検索はそこで終了します。

「slb_enc」フィールドは、ページサイズのSLBでのエンコード方法を示します。ビットは「slbmte命令のvsid引数に直接OR操作で組み込むことができる」ように位置が設定されています。

「enc」配列は、各セグメントベースページサイズに対応するサポートされる実際のページサイズ（ベースページサイズ以上でなければなりません）と、ハッシュPTEでのエンコードを示すリストです。同様に、配列は増加順に8項目あり、「0」シフトの項目は空の項目であり、終端を示します:

struct kvm_ppc_one_page_size {
     __u32 page_shift;       /* Page shift (or 0) */
     __u32 pte_enc;          /* Encoding in the HPTE (>>12) */
};

「pte_enc」フィールドは、ハッシュPTEのRPNフィールドにOR操作で組み込むことができる値を示します（つまり、ハッシュPTEの2番目のダブルワードに組み込むには12ビット左にシフトする必要があります）。

4.75 KVM_IRQFD¶

機能

KVM_CAP_IRQFD

アーキテクチャ

x86 s390 arm arm64

タイプ

vm ioctl

パラメータ

struct kvm_irqfd (入力)

を渡します。

成功時は0、エラー時は-1

イベントfdを直接ゲスト割込みをトリガーするための設定を許可します。kvm_irqfd.fdは使用するイベントfdのファイルディスクリプタを指定し、kvm_irqfd.gsiはこのイベントでトグルされるirqchipピンを指定します。イベントfdでイベントがトリガーされると、指定されたgsiピンを使用してゲストに割込みが注入されます。irqfdはKVM_IRQFD_FLAG_DEASSIGNフラグを使用して削除され、kvm_irqfd.fdとkvm_irqfd.gsiを指定します。

KVM_CAP_IRQFD_RESAMPLEを使用すると、KVM_IRQFDはレベルトリガー型のirqfdベースの割り込みのエミュレーションを可能にするデアサートと通知メカニズムをサポートします。KVM_IRQFD_FLAG_RESAMPLEが設定されている場合、ユーザーはkvm_irqfd.resamplefdフィールドに追加のeventfdを渡す必要があります。再サンプリングモードで動作している場合、kvm_irq.fdを通じた割り込みのポスティングは、irqchip内の指定されたGSIをアサートします。irqchipが再サンプリングされる（例：EOIから）、GSIはデアサートされ、ユーザーはkvm_irqfd.resamplefdを通じて通知されます。デバイスが依然としてサービスを必要とする場合、ユーザーが割り込みを再キューイングする責任があります。注意点として、resamplefdのクローズはirqfdを無効にはしません。KVM_IRQFD_FLAG_RESAMPLEは割り当て時にのみ必要であり、KVM_IRQFD_FLAG_DEASSIGNとともに指定する必要はありません。

arm/arm64では、GSIルーティングがサポートされているため、以下のことが起こり得ます：

  • このGSIにルーティングエントリが関連付けられていない場合、インジェクションは失敗します。

  • このGSIがirqchipルーティングエントリに関連付けられている場合、irqchip.pin + 32はインジェクションされたSPI IDに対応します。

  • このGSIがMSIルーティングエントリに関連付けられている場合、MSIメッセージとデバイスIDはLPI（GICv3 ITSのインカーネルエミュレーションに限定）に変換されます。

4.76 KVM_PPC_ALLOCATE_HTAB¶

機能

KVM_CAP_PPC_ALLOC_HTAB

アーキテクチャ

タイプ

パラメータ

ハッシュテーブルのオーダーを含むu32へのポインタ（入出力）

を渡します。

ホストカーネルにゲスト用にMMUハッシュテーブルを割り当てるよう要求します。これは、カーネルがBook 3S HVスタイルの仮想化を使用している場合にのみ動作します。それ以外の場合、この機能は存在せず、ioctlはENOTTYエラーを返します。以下の説明はBook 3S HVを前提としています。

4.78 KVM_PPC_GET_HTAB_FD¶

機能

KVM_CAP_PPC_HTAB_FD

アーキテクチャ

powerpc

タイプ

vm ioctl

パラメータ

struct kvm_get_htab_fd へのポインタ（入力）

を渡します。

成功時はファイルディスクリプタ番号（>= 0）、エラー時は -1

ゲストのハッシュページテーブル（HPT）のエントリを読み出すためのファイルディスクリプタまたはHPTを初期化するためのエントリを書くためのディスクリプタとして使用できます。返されたfdは、引数のflagsフィールドにKVM_GET_HTAB_WRITEビットが設定されている場合にのみ書き込み可能で、そのビットがクリアされている場合にのみ読み取り可能です。引数の構造は以下の通りです:

/* For KVM_PPC_GET_HTAB_FD */
struct kvm_get_htab_fd {
      __u64   flags;
      __u64   start_index;
      __u64   reserved[2];
};

/* Values for kvm_get_htab_fd.flags */
#define KVM_GET_HTAB_BOLTED_ONLY      ((__u64)0x1)
#define KVM_GET_HTAB_WRITE            ((__u64)0x2)

‘start_index’ フィールドは、HPTのエントリを読み始めるインデックスを指定します。書き込み時には無視されます。

fd への読み込みは、最初にすべての「興味深い」HPT エントリに関する情報を提供します。興味深いエントリは、KVM_GET_HTAB_BOLTED_ONLY ビットが設定されている場合、ボルテッド ビットが設定されているエントリであり、それ以外の場合はすべてのエントリです。HPT の終わりに達した場合、read() は終了します。read() を再度 fd に対して呼び出すと、HPT の先頭から再開しますが、最後に読み取ったときに変更されていないエントリのみを返します。

読み込まれたデータまたは書き込まれたデータは、ヘッダー (8 バイト) に続いて、複数の有効な HPT エントリ (16 バイトずつ) で構成されます。ヘッダーは有効な HPT エントリの数と、有効なエントリの後に続く無効なエントリの数を示します。無効なエントリはストリームに明示的に表されません。ヘッダーの形式は以下の通りです：

struct kvm_get_htab_header {
      __u32   index;
      __u16   n_valid;
      __u16   n_invalid;
};

fd への書き込みは、ヘッダーに指定されたインデックスから HPT エントリを生成します。最初に「n_valid」個の有効なエントリをデータの内容で作成し、その後に「n_invalid」個の無効なエントリを追加します。これにより、以前に有効だったエントリは無効になります。

4.82 KVM_ARM_VCPU_INIT¶

機能

basic

アーキテクチャ

arm, arm64

タイプ

パラメータ

struct kvm_vcpu_init (入力)

を渡します。

成功時は0、エラー時は-1

エラー:

EINVAL

ターゲットが不明であるか、または機能の組み合わせが無効です。

これはKVMがゲストに提示するCPUの種類と、持つべきオプション機能を指定します。これによりCPUレジスタが初期値にリセットされます。この関数を呼び出さない場合、KVM_RUNはそのvcpuに対してENOEXECを返します。

一部のレジスタがマシンのトポロジを反映しているため、このioctlを呼び出す前にすべてのvcpuが作成される必要があります。

ユーザースペースは、指定されたvcpuに対してこの関数を複数回呼び出すことができます（vcpuが実行された後でも）。これによりvcpuが初期状態に戻ります。初期呼び出し後のすべての呼び出しでは同じターゲットと機能フラグのセットを使用する必要があります。それ以外の場合、EINVALが返されます。

可能な機能:

  • KVM_ARM_VCPU_POWER_OFF: CPUを電源オフ状態で起動します。KVM_CAP_ARM_PSCIに依存します。設定されていない場合、KVM_RUNが呼び出されるとCPUが電源が入りゲストコードを実行します。

  • KVM_ARM_VCPU_EL1_32BIT: CPUを32bitモードで起動します。KVM_CAP_ARM_EL1_32BIT（arm64専用）に依存します。

  • KVM_ARM_VCPU_PSCI_0_2: CPUに対してPSCI v0.2（またはv0.2と後方互換性のある今後のバージョン）をエミュレートします。KVM_CAP_ARM_PSCI_0_2に依存します。

  • KVM_ARM_VCPU_PMU_V3: CPUに対してPMUv3をエミュレートします。KVM_CAP_ARM_PMU_V3に依存します。

  • KVM_ARM_VCPU_PTRAUTH_ADDRESS: arm64専用のAddress Pointer認証を有効にします。KVM_CAP_ARM_PTRAUTH_ADDRESSに依存します。KVM_CAP_ARM_PTRAUTH_ADDRESSとKVM_CAP_ARM_PTRAUTH_GENERICが共に存在する場合、KVM_ARM_VCPU_PTRAUTH_ADDRESSとKVM_ARM_VCPU_PTRAUTH_GENERICの両方を要求するか、どちらも要求しない必要があります。

  • KVM_ARM_VCPU_PTRAUTH_GENERIC: arm64専用のGeneric Pointer認証を有効にします。KVM_CAP_ARM_PTRAUTH_GENERICに依存します。KVM_CAP_ARM_PTRAUTH_ADDRESSとKVM_CAP_ARM_PTRAUTH_GENERICが共に存在する場合、KVM_ARM_VCPU_PTRAUTH_ADDRESSとKVM_ARM_VCPU_PTRAUTH_GENERICの両方を要求するか、どちらも要求しない必要があります。

  • KVM_ARM_VCPU_SVE: CPUにSVEを有効にします（arm64専用）。KVM_CAP_ARM_SVEに依存します。KVM_ARM_VCPU_FINALIZE(KVM_ARM_VCPU_SVE):

    • KVM_ARM_VCPU_INITの後:

      • KVM_REG_ARM64_SVE_VLSはKVM_GET_ONE_REGを使用して読み取ることができます。この擬似レジスタの初期値は、このホスト上のvcpuで可能なベクターレンジの最適なセットを示します。

    • KVM_ARM_VCPU_FINALIZE(KVM_ARM_VCPU_SVE)実行前には、

      • KVM_RUNおよびKVM_GET_REG_LISTは利用できません；

      • KVM_GET_ONE_REGおよびKVM_SET_ONE_REGは、スケーラブルなアーキテクチャのSVEレジスタ（KVM_REG_ARM64_SVE_ZREG()、KVM_REG_ARM64_SVE_PREG()、KVM_REG_ARM64_SVE_FFR）にアクセスできません。

      • KVM_REG_ARM64_SVE_VLSはKVM_SET_ONE_REGを使用してオプションで書き込むことができます。これにより、vcpuに利用可能なベクターレンジのセットを変更できます。

    • KVM_ARM_VCPU_FINALIZE(KVM_ARM_VCPU_SVE)実行後には、

      • KVM_REG_ARM64_SVE_VLSという擬似レジスタは変更不可能であり、KVM_SET_ONE_REGを使用して書き込むことはできなくなります。

  • KVM_GUESTDBG_SINGLESTEP: 次の実行はシングルステップで実行

VCPUの論理（仮想）メモリからデータを読み書きします。

パラメータは以下の構造体を通じて指定されます：

struct kvm_s390_mem_op {
      __u64 gaddr;            /* the guest address */
      __u64 flags;            /* flags */
      __u32 size;             /* amount of bytes */
      __u32 op;               /* type of operation */
      __u64 buf;              /* buffer in userspace */
      __u8 ar;                /* the access register number */
      __u8 reserved[31];      /* should be set to 0 */
};

操作の種類は「op」フィールドで指定されます。読み取りの場合はKVM_S390_MEMOP_LOGICAL_READ、書き込みの場合はKVM_S390_MEMOP_LOGICAL_WRITEが指定されます。「flags」フィールドにKVM_S390_MEMOP_F_CHECK_ONLYフラグを設定することで、該当のメモリアクセスがアクセス例外を引き起こすかどうかを確認できます（メモリのデータは変更されません）。ゲストのMMUテーブルをウォーキング中にアクセス例外が発生した場合、ioctlは正のエラーコードを返して例外の種類を示します。また、「flags」フィールドにKVM_S390_MEMOP_F_INJECT_EXCEPTIONフラグが設定されている場合、該当のVCPUに直接例外が発生します。

メモリ領域の開始アドレスは「gaddr」フィールドに指定し、領域の長さは「size」フィールドに指定します（0にはできません）。sizeの最大値はKVM_CAP_S390_MEM_OPのキャパビリティを確認することで取得できます。「buf」はユーザー空間アプリケーションから提供されたバッファで、KVM_S390_MEMOP_LOGICAL_READの場合は読み込んだデータを書き込む場所、KVM_S390_MEMOP_LOGICAL_WRITEの場合は書き込むデータを格納する場所です。KVM_S390_MEMOP_F_CHECK_ONLYが指定されている場合、「buf」は使用されずNULLでも構いません。「ar」は使用するアクセスレジスタ番号を指定し、有効範囲は0..15です。

「reserved」フィールドは今後の拡張のために用意されており、現在定義されたフラグセットではKVMでは使用されません。

4.97 KVM_CAP_PPC_MULTITCE¶

機能

アーキテクチャ

ppc

この機能は、カーネルがhypercall H_PUT_TCE_INDIRECTおよびH_STUFF_TCEを処理できることを意味します。これらをユーザースペースに渡す必要がなく、これによりPPC KVMゲストのDMA操作が大幅に高速化されます。ユーザースペースは、KVMにLIOBNを以前に登録した場合（KVM_CREATE_SPAPR_TCEや類似のコールを通じて）、これらのhypercallハンドラが呼ばれないことを期待すべきです。

この機能は常に有効です。

struct kvm_s390_cmma_log {

      __u32 count;
      __u32 flags;
      union {
              __u64 remaining;
              __u64 mask;

      __u64 values;
};

start_gfn は CMMA 値を取得するゲストフレームの最初の番号です。

values は結果を書き込むバッファへのポインタです。

count が KVM_S390_SKEYS_MAX を超える場合、KVM_S390_SKEYS_MAX とみなされます。KVM_S390_SKEYS_MAX は他の ioctl と一貫性を保つため再利用されています。

フラグによって異なる動作が行われます。現在サポートされているフラグは KVM_S390_CMMA_PEEK だけです。

KVM_S390_CMMA_PEEKが設定されていない場合のデフォルト動作は：start_gfnはCMMAビットが汚染された最初のページフレームを示します。これは入力されたものとは必ずしも一致しない場合があります。なぜなら、クリーンなページはスキップされるからです。

countはバッファに実際に書き込まれたバイト数を示します。これは入力値よりも小さくなることがあります（通常はそうなります）。なぜなら、バッファは16バイトのクリーンな値が見つかるまでのみ埋められ、その値はバッファにコピーされないからです。CMMA移行ブロックはベースアドレスと長さの合計16バイトを必要とするため、その後に汚染データがある場合でも、ヘッダーのサイズを超えない限りクリーンなデータを送信します。これにより、ネットワーク経由で保存または転送するデータ量を最小化でき、ユーザー空間へのラウンドトリップ回数を増やす代償が生じます。次のioctl呼び出しではすべてのクリーンな値をスキップするため、16バイト以上を節約できる可能性があります。

KVM_S390_CMMA_PEEKが設定されている場合：移行モードに関係なく既存のストレージ属性が読み込まれ、他の処理は行われません。

出力のstart_gfnは入力のstart_gfnと一致します。

出力のcountは入力のcountと一致します。ただし、メモリの終わりに達した場合は除きます。

いずれの場合も："remaining"フィールドはまだ汚染されたCMMA値の総数を示します。KVM_S390_CMMA_PEEKが設定されており移行モードが有効でない場合は0になります。

maskは使用されません。

valuesは結果を格納するユーザー空間のバッファへのポインタを示します。

このioctlは、必要なメモリが確保できない場合に-ENOMEMで失敗します。CMMAが有効でない場合に-ENXIO、KVM_S390_CMMA_PEEKが設定されていないが移行モードが有効でない場合に-EINVAL、ユーザー空間のアドレスが無効またはアドレスにページテーブルが存在しない場合（例：ヒューゲンページを使用している場合）に-EFAULTで失敗します。

KVM_MSR_FILTER_DEFAULT_DENY

フィルタリング範囲に一致するMSRインデックスがアクセスされていない場合、KVMはMSRへのアクセスを拒否するよう戻ります。このモードでは、KVMで処理すべきすべてのMSRはビットマップで明示的に許可される必要があります。

このioctlは、ユーザー空間が最大16のMSR範囲のビットマップを定義し、特定のMSRアクセスが明示的にフィルタリングされるべきかどうかを指定するためのものです。

このioctlが一度も呼び出されていない場合、MSRアクセスは保護されず、デフォルトのKVM内カーネルエミュレーション動作が完全に保持されます。

このioctlを空の範囲セット（すべてのnmsrs == 0）で呼び出すと、MSRフィルタリングが無効になります。そのモードでは、 KVM_MSR_FILTER_DEFAULT_DENY が無効であり、エラーを引き起こします。

フィルタリングが有効になると、すべてのMSRアクセスがフィルタリングを通じて処理されます。ただし、x2APIC MSR（0x800から0x8ff）へのアクセスは常に許可され、の設定とは関係ありません。 default_allow 設定、およびその動作はのビットに依存します。 X2APIC_ENABLE APICベースレジスタのビットです。

あるビットが定義された範囲のいずれかに含まれている場合、アクセスの種類が含まれている場合、そのMSRインデックスのビットマップの値によって読み込みおよび書き込みアクセスが保護されます。 struct kvm_msr_filter_range フラグです。この特定のアクセスがどの範囲にも含まれていない場合、のkvm_msr_filter構造体のフラグフィールドによって動作が決定されます： KVM_MSR_FILTER_DEFAULT_ALLOW および KVM_MSR_FILTER_DEFAULT_DENY.

各ビットマップ範囲は、MSRの範囲を指定し、アクセスを許可する可能性があります。範囲はMSRインデックス[base .. base+nmsrs]から始まります。フラグフィールドは、対応するMSRインデックスのビットマップに1ビットを設定することで、読み取り、書き込み、または読み取りと書き込みの両方をフィルタリングするかどうかを示します。

MSRへのアクセスがフィルタリングによって許可されない場合、ゲスト内で#GP（ページフォールト）が発生します。KVM_CAP_X86_USER_SPACE_MSRと組み合わせることで、ユーザー空間がさまざまなMSRアクセスをユーザー空間に転送し、処理できるようになります。

注意：このioctlを実行する際、稼働中のvCPUを指定すると競合状態が発生します。ただし、KVMはvCPUが以前のフィルタまたは新しいフィルタをいずれか必ず見ることを保証しており、古いフィルタと新しいフィルタでMSRの設定が同じ場合、決定的な動作が保証されます。

仮想CPUのTLB配列を設定し、ユーザースペースとKVM間で共有メモリ領域を確立します。"params"および"array"フィールドは、mmuタイプ固有のデータ構造のユーザースペースアドレスです。"array_len"フィールドは安全メカニズムであり、ユーザースペースが配列用に確保したメモリのバイト数を設定する必要があります。これは"mmu_type"および"params"によって規定されるサイズ以上でなければなりません。

KVM_RUNが有効な間、共有領域はKVMの制御下にあり、その内容は未定義です。ユーザースペースによる変更は制限された未定義の動作を引き起こします。

KVM_RUNから戻るとき、共有領域はゲストのTLBの現在の状態を反映します。ユーザースペースが変更を加える場合、再度このvcpuでKVM_RUNを呼び出す前にKVM_DIRTY_TLBを呼び出して変更されたエントリをKVMに通知する必要があります。

mmuタイプKVM_MMU_FSL_BOOKE_NOHVおよびKVM_MMU_FSL_BOOKE_HVの場合:

  • "params"フィールドは"struct kvm_book3e_206_tlb_params"型です。

  • "array"フィールドは"struct kvm_book3e_206_tlb_entry"型の配列を指します。

  • 配列は最初のTLBのすべてのエントリに続き、2番目のTLBのすべてのエントリが続きます。

  • TLB内では、最初にset番号の増加順に並び、set内ではway（ESELの増加順）で並びます。

  • TLB0におけるset番号を決定するハッシュは: (MAS2 >> 12) & (num_sets - 1) です。ここで"num_sets"はtlb_sizes[]値をtlb_ways[]値で割った値です。

  • mas1のtsizeフィールドはTLB0において4Kに設定する必要があります。ハードウェアはこの値をTLB0で無視します。

#define KVM_DIRTY_LOG_INITIALLY_SET           (1 << 1)

KVM_DIRTY_LOG_MANUAL_PROTECT_ENABLEが設定されている場合、KVM_GET_DIRTY_LOGは自動的に返された汚染ページをクリアして読み取り保護しない。代わりに、ユーザー空間がKVM_CLEAR_DIRTY_LOGを使用してこの操作を個別に実行する必要があります。

やや複雑な操作が必要になる代わりに、この機能はスケーラビリティとレスポンシブネスの向上を実現します。その理由は2つあります。まず、KVM_CLEAR_DIRTY_LOG ioctlは64ページ単位で動作可能になり、全体のmemslotを同期する必要がなくなるため、KVMがスピンロックを長時間保持するのを防ぎます。次に、KVM_GET_DIRTY_LOGの呼び出しとユーザー空間がページのデータを実際に使用するまでの間に、長時間経過する場合があります。この間にページが変更されるため、ゲストとユーザー空間の双方にとって効率が低下します。ゲストは書き込み保護違反によるペナルティが高くなり、ユーザー空間は汚染ページの誤検出が発生します。手動での再保護によりこの時間を短縮し、ゲストのパフォーマンス向上と汚染ログの誤検出数の削減が可能になります。

KVM_DIRTY_LOG_INITIALLY_SETが設定されている場合、dirty bitmapのすべてのビットは作成時に1に初期化されます。これはパフォーマンス向上にも寄与します。最初のKVM_CLEAR_DIRTY_LOG呼び出しでdirty loggingを小さなチャンクで段階的に有効化できるためです。KVM_DIRTY_LOG_INITIALLY_SETはKVM_DIRTY_LOG_MANUAL_PROTECT_ENABLEに依存しており（現時点ではx86およびarm64プラットフォームでのみ利用可能です）。

KVM_CAP_MANUAL_DIRTY_LOG_PROTECT2は以前はKVM_CAP_MANUAL_DIRTY_LOG_PROTECTという名前で提供されていましたが、実装上のバグにより正しく使用するのが困難または不可能でした。KVM_CAP_MANUAL_DIRTY_LOG_PROTECT2の利用可能化は、これらのバグが修正されたことを示しています。ユーザー空間はKVM_CAP_MANUAL_DIRTY_LOG_PROTECTを使用すべきではありません。

7.19 KVM_CAP_PPC_SECURE_GUEST¶

アーキテクチャ

ppc

この機能は、KVMがultravisorファームウェアを搭載したホスト上で動作していることを示します。このようなシステムでは、ゲストがultravisorに自身をセキュアゲストに変更するよう依頼できるため、ホストがアクセスできないメモリ（ホストと共有するページを除く）を持つセキュアゲストが実現されます。ultravisorはゲストがセキュアゲストになることを依頼した際にKVMを通知し、KVMはその移行を拒否する機会を持ちます。

この機能が存在する場合、VMに対して有効化できます。つまりKVMはセキュアゲストモードへの移行を許可します。そうでない場合はKVMが移行を拒否します。

8.5 KVM_CAP_MIPS_VZ¶

アーキテクチャ

mips

この機能は、メインのkvmハンドルのKVM_CHECK_EXTENSIONが利用可能であることを示す場合、ハードウェアの完全なハードウェア支援仮想化機能がKVMを通じて利用可能であることを意味します。KVM_CREATE_VMでVMを生成する際には、適切なKVM_VM_MIPS_*タイプを渡す必要があります。

kvm VMハンドルのKVM_CHECK_EXTENSIONがこの機能を利用可能であることを示す場合、そのVMがハードウェアの完全なハードウェア支援仮想化機能を使用していることを意味します。これは、KVM_VM_MIPS_DEFAULTでVMを生成した後確認するために役立ちます。

KVM_CHECK_EXTENSIONで返される値は、既知の値（以下参照）と比較する必要があります。他の値は予約されています。これは、MIPS VZ ASEと互換性のない他のハードウェア支援仮想化実装が存在する可能性を考慮するためです。

0

ゲストコードをユーザーモードで実行するためにトラップ＆エミュレート実装が使用されています。ゲスト仮想メモリセグメントは、ユーザーモードアドレス空間にゲストを収めるために再配置されます。

1

MIPS VZ ASEが使用されており、完全なハードウェア支援仮想化を提供しています。これは標準のゲスト仮想メモリセグメントも含みます。

8.6 KVM_CAP_MIPS_TE¶

アーキテクチャ

mips

この機能は、メインのkvmハンドルのKVM_CHECK_EXTENSIONが利用可能である場合、KVM_CAP_MIPS_VZがハードウェア支援仮想化を示しているとしても、トラップ＆エミュレート実装がユーザーモードでゲストコードを実行するために利用可能であることを意味します。KVM_CREATE_VMでVMを生成する際には、KVM_VM_MIPS_TE (0)を渡す必要があります。

kvm VMハンドルのKVM_CHECK_EXTENSIONがこの機能を利用可能であることを示す場合、そのVMがトラップ＆エミュレートを使用していることを意味します。

8.7 KVM_CAP_MIPS_64BIT¶

アーキテクチャ

mips

この機能は、ゲストのサポートされるアーキテクチャタイプを示します。つまり、サポートされるレジスタおよびアドレス幅です。

この機能をkvm VMハンドルのKVM_CHECK_EXTENSIONで確認した際の返却値は、CP0_Config.ATレジスタフィールドに概ね対応し、既知の値（以下参照）と具体的に比較する必要があります。他の値はすべて予約されています。

0

MIPS32またはmicroMIPS32です。レジスタおよびアドレスはすべて32ビット幅です。32ビットのゲストコードのみを実行可能です。

1

MIPS64またはmicroMIPS64で、32ビット互換セグメントへのアクセスのみが可能。レジスタは64ビット幅ですが、アドレスは32ビット幅です。64ビットゲストコードは実行可能ですが、MIPS64メモリセグメントへのアクセスはできません。32ビットゲストコードの実行も可能です。

2

MIPS64またはmicroMIPS64で、すべてのアドレスセグメントへのアクセスが可能。レジスタおよびアドレスはともに64ビット幅です。64ビットまたは32ビットゲストコードの実行が可能です。

8.9 KVM_CAP_ARM_USER_IRQ¶

アーキテクチャ

arm, arm64

この機能がKVM_CHECK_EXTENSIONで利用可能と示されている場合、ユーザースペースがカーネル内割り込み制御器を持たない仮想マシンを生成した場合、カーネル内エミュレートデバイスの出力レベルの変化を通知されます。このような仮想マシンでは、ユーザースペースへの戻りごとに、カーネルがvcpuのrun->s.regs.device_irq_levelフィールドをデバイスの実際の出力レベルに更新します。

kvmがデバイス出力レベルの変化を検出するたびに、仮想マシンを実行する前にユーザースペースへの少なくとも1回の戻りを保証します。この戻りはKVM_EXIT_INTRか、KVM_EXIT_MMIOなどの他のイベントでも可能です。これにより、ユーザースペースが常にデバイス出力レベルをサンプリングし、ユーザースペース割り込み制御器の状態を再計算できます。ユーザースペースはすべてのkvmエクスイット時にrun->s.regs.device_irq_levelの状態を確認する必要があります。run->s.regs.device_irq_levelの値は、デバイスによってレベルトリガーまたはエッジトリガーされた割り込み信号を表す場合があります。エッジトリガーされた割り込み信号は、エッジ信号ごとにrun->s.regs.device_irq_levelのビットがちょうど1回設定されます。

run->s.regs.device_irq_levelフィールドは、run->kvm_valid_regsまたはrun->kvm_dirty_regsビットとは関係なく利用可能です。

KVM_CAP_ARM_USER_IRQがサポートされている場合、KVM_CHECK_EXTENSION ioctlはこの機能のバージョン番号を示す0より大きい数値を返し、これによりrun->s.regs.device_irq_levelのどのビットが値を示すかを示します。

現在、device_irq_levelビットマップには次のビットが定義されています:

KVM_CAP_ARM_USER_IRQ >= 1:

  KVM_ARM_DEV_EL1_VTIMER -  EL1 virtual timer
  KVM_ARM_DEV_EL1_PTIMER -  EL1 physical timer
  KVM_ARM_DEV_PMU        -  ARM PMU overflow interrupt signal

今後のkvmバージョンでは追加のイベントが実装される可能性があります。これらはKVM_CHECK_EXTENSIONからより高い数値を返すことで示され、上記にリストされます。

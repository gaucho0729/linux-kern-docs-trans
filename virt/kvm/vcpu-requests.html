KVM VCPUリクエスト¶

概要¶

KVM は、スレッドが VCPU スレッドに特定のアクティビティを実行させるリクエストを求める内部 API をサポートしています。たとえば、スレッドは VCPU に TLB のフラッシュをリクエストするなど、アクティビティを実行させることがあります。この API は以下の関数から構成されています：

/* Check if any requests are pending for VCPU @vcpu. */
bool kvm_request_pending(struct kvm_vcpu *vcpu);

/* Check if VCPU @vcpu has request @req pending. */
bool kvm_test_request(int req, struct kvm_vcpu *vcpu);

/* Clear request @req for VCPU @vcpu. */
void kvm_clear_request(int req, struct kvm_vcpu *vcpu);

/*
 * Check if VCPU @vcpu has request @req pending. When the request is
 * pending it will be cleared and a memory barrier, which pairs with
 * another in kvm_make_request(), will be issued.
 */
bool kvm_check_request(int req, struct kvm_vcpu *vcpu);

/*
 * Make request @req of VCPU @vcpu. Issues a memory barrier, which pairs
 * with another in kvm_check_request(), prior to setting the request.
 */
void kvm_make_request(int req, struct kvm_vcpu *vcpu);

/* Make request @req of all VCPUs of the VM with struct kvm @kvm. */
bool kvm_make_all_cpus_request(struct kvm *kvm, unsigned int req);

通常、リクエスターはリクエストを出した後すぐに VCPU がアクティビティを実行することを望みます。これは、ほとんどのリクエスト（kvm_make_request() 呼び出し）が kvm_vcpu_kick() の呼び出しで続いていることを意味します。また、kvm_make_all_cpus_request() はすべての VCPU のキックを組み込んでいます。

VCPU キック¶

VCPU キックの目的は、VCPU スレッドをゲストモードから抜け出して KVM のメンテナンスを実行することです。そのためには、IPI が送信され、ゲストモードの終了を強制します。ただし、キックのタイミングで VCPU スレッドがゲストモードにいない場合があります。したがって、VCPU スレッドのモードと状態に応じて、キックが行う他のアクションは2つあります。すべてのアクションは以下に示します：

  1. IPI を送信します。これにより、ゲストモードの終了が強制されます。

  2. スリープ中の VCPU を起こします。スリープ中の VCPU は、waitqueues に待機しているゲストモード外の VCPU スレッドです。これらを起こすと、スレッドが waitqueues から外れ、再び実行可能になります。この挙動は抑止可能です（以下で説明します：KVM_REQUEST_NO_WAKEUP）

  3. 何もしない。VCPU がゲストモード外にあり、VCPU スレッドがスリープしていない場合、何も行う必要はありません。

VCPU モード¶

VCPU はモード状態を持っています、 vcpu->mode、ゲストがゲストモードで実行されているかを追跡するだけでなく、特定のゲストモード外の状態も追跡します。アーキテクチャは vcpu->mode を用いて、VCPU リクエストが VCPU に見られるようにする（「リクエストが見られるようにする」を参照）、不要な IPI の送信を避ける（「IPI の削減」を参照）、さらには IPI の確認を待つ（「確認の待機」を参照）ために使用します。以下のモードが定義されています：

OUTSIDE_GUEST_MODE

VCPU スレッドはゲストモード外です。

IN_GUEST_MODE

VCPU スレッドはゲストモード内です。

EXITING_GUEST_MODE

VCPU スレッドは IN_GUEST_MODE から OUTSIDE_GUEST_MODE へ移行しています。

READING_SHADOW_PAGE_TABLES

VCPU スレッドはゲストモード外ですが、特定の VCPU リクエスト（KVM_REQ_TLB_FLUSH）の送信元が、VCPU スレッドがページテーブルを読み終わるまで待機するようにしたいです。

VCPUリクエストの内部¶

VCPU リクエストは単に vcpu->requests ビットマップのビットインデックスです。これは、一般的なビット操作（[atomic-ops] に記載されているものなど）も使用可能です、例えば。 [atomic-ops] 使用可能です、例えば。

clear_bit(KVM_REQ_UNHALT & KVM_REQUEST_MASK, &vcpu->requests);

ただし、VCPUリクエストのユーザーは、抽象化を破るため、これを実行すべきではありません。最初の8ビットはアーキテクチャに依存しないリクエスト用に予約されており、追加のビットはアーキテクチャに依存するリクエスト用に利用可能です。

アーキテクチャに依存しないリクエスト¶

KVM_REQ_TLB_FLUSH

KVMの共通MMU通知者は、ゲストのTLBエントリをすべてフラッシュする必要があり、これを実行するにはkvm_flush_remote_tlbs()を呼び出します。共通のkvm_flush_remote_tlbs()実装を使用するアーキテクチャは、このVCPUリクエストを処理する必要があります。

KVM_REQ_MMU_RELOAD

シャドウページテーブルが使用され、メモリスロットが削除された場合、各VCPUにテーブルを完全に再読み込みする必要があります。このリクエストはその目的で使用されます。

KVM_REQ_PENDING_TIMER

このリクエストは、ホスト上でVCPUの代わりに実行されるタイマーハンドラから生成される可能性があります。これはVCPUスレッドにタイマーアラームを注入する通知です。

KVM_REQ_UNHALT

このリクエストは、KVMの共通関数kvm_vcpu_block()から生成される可能性があります。この関数は、CPUがアーキテクチャ固有のイベントおよび/または割り込みのいずれかを受信するまで停止状態になるようにシミュレートする命令をエミュレートするために使用されます（kvm_arch_vcpu_runnable()で判定）。そのイベントまたは割り込みが到達すると、kvm_vcpu_block()がこのリクエストを生成します。これは、kvm_vcpu_block()が他の理由（例えば待機中のシグナル）で返る場合と対照的です。その場合、VCPUの停止エミュレーションを停止する必要はなく、リクエストを生成しません。

KVM_REQUEST_MASK¶

VCPUリクエストは、bitopsを使用する前にKVM_REQUEST_MASKでマスクする必要があります。これは、リクエスト番号を表すのは下位8ビットのみであり、上位ビットはフラグとして使用されるためです。現在は2つのフラグのみが定義されています。

VCPUリクエストフラグ¶

KVM_REQUEST_NO_WAKEUP

このフラグは、ゲストモードで実行中のVCPUのみに即時対応が必要なリクエストに適用されます。つまり、待機中のVCPUはこれらのリクエストのために起こされません。待機中のVCPUは、他の理由で後で起こされたときにリクエストを処理します。

KVM_REQUEST_WAIT

kvm_make_all_cpus_request()でこのフラグを持つリクエストが生成されると、呼び出し元は各VCPUがIPIを確認するまで待機します。このフラグは、IPIを受信するVCPUにのみ適用されます。たとえば、VCPUが待機中でIPIが不要な場合、呼び出しスレッドは待機しません。これは、KVM_REQUEST_NO_WAKEUPと安全に組み合わせて使用できるということを意味します。詳しくは「ACKの待機」セクションを参照してください。

関連する状態を持つVCPUリクエスト¶

受信するVCPUが新しい状態を処理する必要があるリクエスターは、新しい状態が受信するVCPUスレッドのCPUで観測可能になるように、リクエストを観測する前にその状態を書き込む必要があります。これは、新しい状態を書き込んだ後で、VCPUリクエストビットを設定する前に、書き込みメモリバリアを挿入する必要があります。また、受信するVCPUスレッド側では、リクエストビットを読み取った後で、新しい状態を読み取る前に、対応する読み取りバリアを挿入する必要があります。詳しくは、[lwn-mb]およびカーネルドキュメンテーションの[memory-barriers]を参照してください。 [lwn-mb] およびカーネルドキュメンテーション [memory-barriers].

関数ペア、kvm_check_request()とkvm_make_request()はメモリバリアを提供し、この要件をAPI内部で処理できるようにします。

リクエストが見られるようにする¶

VCPUへのリクエストを送信する際には、受信するVCPUがゲストモードで任意に長い時間実行し、リクエストを処理しない状態を避ける必要があります。VCPUスレッドがゲストモードに入る前にkvm_request_pending()を確認することを保証すれば、この状態は発生しません。また、必要に応じてキックがIPIを送信してゲストモードから強制的に退出させるため、キックIPIが送信される必要があります。特に、VCPUスレッドが最後のkvm_request_pending()確認後にゲストモードに入った直前までの期間には、より注意が必要です。キックIPIは、ゲストモード内にいるVCPUスレッドや、ゲストモードに入る準備として割り込みを無効にしたスレッドに対してのみゲストモードの退出をトリガーします。これは、IPIの送信を安全に省略できるタイミングを確実に把握する必要があります（「IPIの削減」を参照）。すべてのアーキテクチャで適用される解決策の一つは以下の通りです：

  • set vcpu->mode 割り込みを無効化と最後のkvm_request_pending()確認の間にIN_GUEST_MODEを設定する。

  • ゲストに入る際には割り込みを原子的に有効にする。

この解決策では、リクエスタースレッドと受信するVCPUの両方でメモリバリアを慎重に配置する必要があります。メモリバリアにより、VCPUスレッドが最後の確認で!kvm_request_pending()を観測した後で、次のリクエストが送信されたとしてもIPIを受け取らない可能性を排除できます。これはデッカーのメモリバリアパターン（シナリオ10の）を介して実現されます。デッカーのパターンは2つの変数を必要とするため、この解決策では以下の変数をペアにしています。 [lwn-mb]シナリオ10 vcpu->mode with vcpu->requestsこれらをパターンに代入すると以下のようになります：

CPU1                                    CPU2
=================                       =================
local_irq_disable();
WRITE_ONCE(vcpu->mode, IN_GUEST_MODE);  kvm_make_request(REQ, vcpu);
smp_mb();                               smp_mb();
if (kvm_request_pending(vcpu)) {        if (READ_ONCE(vcpu->mode) ==
                                            IN_GUEST_MODE) {
    ...abort guest entry...                 ...send IPI...
}                                       }

上記のように、IPIはゲストモードで動作するVCPUスレッドや、すでに割込みを無効にしたスレッドにのみ有効です。これは、この特定のDekkerパターンのケースが、割込みを無効にしてから設定するように拡張された理由です。 vcpu->mode WRITE_ONCE()とREAD_ONCE()は、メモリバリアパターンを厳密に実装するために使用され、コンパイラがアクセスに干渉しないことを保証します。 vcpu->modeの慎重に計画されたアクセスを保証します。

IPIの削減¶

VCPUが任意の/すべてのリクエストを確認するために1つのIPIのみが必要なため、これらは統合されることが可能です。これは、最初のIPI送信時にVCPUのモードを!IN_GUEST_MODEに変更することで簡単に実現できます。この目的のために、遷移状態であるEXITING_GUEST_MODEが使用されます。

応答の待機¶

一部のリクエスト（KVM_REQUEST_WAITフラグが設定されているもの）は、ターゲットVCPUスレッドがIN_GUEST_MODE以外のモードであっても、IPIを送信し、応答を待つ必要があります。たとえば、ターゲットVCPUスレッドがREADING_SHADOW_PAGE_TABLESモード（割込みを無効にしてから設定されるモード）にいる場合があります。このようなケースをサポートするため、KVM_REQUEST_WAITフラグはIPI送信の条件を、VCPUがIN_GUEST_MODEであることを確認するから、VCPUがOUTSIDE_GUEST_MODEでないことを確認するように変更します。

リクエストなしのVCPUキック¶

IPIの送信を決定する条件が2変数のDekkerメモリバリアパターンに基づいているため、リクエストなしのVCPUキックはほぼ常に正しいとは言えません。リクエスト付きキックのように、最終的なkvm_request_pending()チェックが受け取るVCPUが動作を実行する保証を提供しない場合、キックがまったく役に立たない可能性があります。たとえば、リクエストなしのキックがIN_GUEST_MODEにモードを変更する直前のVCPUに送信された場合、割込みが送信されず、VCPUスレッドは実際の動作を実行せずにエントリを継続する可能性があります。

x86のポスト割込みメカニズムを除けば、リクエストなしのVCPUキックも同様のローカル割込み無効化() + smp_mb()パターンと結合されています。ポスト割込み記述子のONビット（ Outstanding Notification）は、この場合、 vcpu->requestsを担当します。ポスト割込みを送信する際、PIR.ONは読み込みよりも先に設定されます。 vcpu->mode；逆に、VCPUスレッドでは、vmx_sync_pir_to_irr()はPIRを設定した後、 vcpu->mode IN_GUEST_MODEに設定した後、PIRを読み込みます。

追加の考慮事項¶

スリープ中のVCPU¶

VCPUスレッドは、kvm_vcpu_block()などの関数を呼び出す前後で要請を考慮する必要があります。それらが行うかどうか、および行う場合のどの要請を考慮すべきかはアーキテクチャに依存します。kvm_vcpu_block()は、アーキテクチャに応じてスレッドを再開すべきかを確認するため、kvm_arch_vcpu_runnable()を呼び出します。このような処理を行う理由の一つは、アーキテクチャに必要な要請の確認を行うための関数を提供することです。

要請のクリアリング¶

通常は、要請を受けるVCPUスレッドだけが要請をクリアする必要があります。ただし、リクエスターのスレッドと受信するVCPUスレッドがシリアルに実行される場合（同じスレッドの場合や、一時的に同期して実行するためのコンカレンシー制御を使用している場合など）には、要請が即座にクリアされる可能性があり、VCPU RUNで要請を処理を待つ必要はありません。現在の例としては、VCPUが自身をブロックするために呼び出すkvm_vcpu_block()の呼び出しが挙げられます。この呼び出しの副作用として、KVM_REQ_UNHALT要請が生成される可能性があり、VCPUがこの呼び出しから戻る際に即座にクリアされることがあります。

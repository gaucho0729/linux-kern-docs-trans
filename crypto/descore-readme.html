このパッケージは以下の目標で設計されました:

  1. 最高の暗号化/復号パフォーマンス。

  2. 32ビットの符号化されたC型を持つバイトアドレス可能なホストへのポータビリティ。

  3. KERBEROSの低レベルルーチンのプラグコンパチブルな置き換え。

この2番目のリリースでは、レジスタが不足しているマシン向けにいくつかのパフォーマンス改善が含まれています。マイクロソフトのリチャード・アウターブリッジとの議論がこれらの改善のいくつかをもたらしました。 71755.204@compuserve.com、をきっかけにこれらの改善が生まれました。

このパッケージ内のコードをより迅速に理解するには、desSmallFips.i（タイプ make) に目を通すことをお勧めします。desCode.hはパラメータ化された構造で設計されており、スピードダーモンハッカーが最後のマイクロ秒を追求するため簡単に変更可能です。具体的な実装を確認し、その後共通の抽象的なスケルトンに移行する方がより理解が深まります。

    動機と歴史

以前、DES ルーチンが必要になり、Sun の man ページに記載されていたルーチンは存在しなかったり、コアダンプを起こしたりしました。Kerberos について聞いたことがあるので、DES を使用していると知っていたため、そのルーチンを使用しようとしました。しかし、コードを確認した後、多くのイライラを引き起こしました。コードが複雑すぎたこと、IP、E、FP などの操作の規則的な構造を活用していなかったこと（つまり、作者がコードを書く前に十分に考えなかったこと）、非常に遅いこと、作者がコードを明確にするためにデータの移動をより明確にするために追加のステートメントを追加したことで、実際にはコードを簡潔にするのではなく、データの移動を増やしたことです。また、L1、R1、L2、R2 の使用など、愚かな実装が含まれていました。¶

データの移動を簡素化し、すべてのデータの移動を減らす（特にL1、R1、L2、R2 の使用）ことなく、 consistent 愚かな tweaks 特定のマシンでは、速度の向上が見られなかったが、すべてを複雑化していた。そのため、彼の検証プログラムからテストデータを取り、それ以外の部分をすべて再構築した。

しばらくして、上記で紹介した大規模な暗号化パッケージcrypt(3)に出会った。この人がテーブル検索ごとに2つのSボックスを処理していること（そしてそれにより非常に大きなテーブルを使用していること）に気づき、同様のアプローチを取ることを勇気づけられた。私はそれまで、大きなテーブルサイズのためこの変更を恐れていたが、実際には、インデックス用に半分のSボックスを簡単に利用できる形式と、他の半分を簡単に利用できる形式の2つのデータを保持する必要はなく、代わりに最初の半分の形式で保持し、単純な回転操作で他の半分を取得できる。このため、私はほぼ半分のデータ操作とテーブルサイズで済む。ただし、彼のテーブルにはcrypt(3)に特有のエンコーディングが含まれている可能性もあるため、私は確認していない。

私が実装した方法が正しいことを確認できてよかったです。このC言語バージョンは移植可能（#ifdefはパフォーマンス向上のための最適化）であり、sparc向けに手書きされたアセンブリコードよりも高速です。

移植に関する注意点¶

私が避けたかったのは、エンドイアンスや他のマシンの特徴に依存した巨大な混乱を生むコードの作成であり、異なるマシンごとに異なるコードと検索テーブルを生成する必要があったことです。kerberosコードは、私が避けたいような例です。すべてのエンドイアンス固有の処理を含んでいます。 optimizations コードを複雑化してしまい、結果として単純でマシンに依存しないアプローチよりも遅くなることがありました。ただし、常にいくつかの移植性の考慮が必要であり、私はレジスタ変数の数を変更可能なオプションをいくつか含めました。おそらく、一部の人にとっては結果が依然として混乱していると感じるかもしれません。

  1. すべてがバイトアドレス可能であると仮定していますが、実際にバイト順に依存しているわけではありません。バイトは8ビットと仮定しています。また、ワードポインタはチャラポインタに自由にキャスト可能と仮定しています。注意点として、99%のC言語プログラムがこれらの仮定をしています。高ビットが設定される可能性がある場合は常にunsigned charを使用します。

  2. typedef word 32ビットの符号なし整数型を意味します。もし unsigned long が32ビットでない場合は、desCore.h内のtypedefを変更してください。私はsizeof(word)が常に4であると仮定しています。

鍵反復周辺のデータ読み込みと保存コードでエンデインス固有の最適化を行わないことの（最悪の場合）コストは12%未満です。さらに、入力および出力作業領域がワードアライメントを必要としないという利点もあります。

オプションのパフォーマンス最適化¶

  1. you should define one of i386, vax, mc68000, または sparc, whichever one is closest to the capabilities of your machine. see the start of desCode.h to see exactly what this selection implies. note that if you select the wrong one, the des code will still work; these are just performance tweaks.

  2. for those with functional asm keywords: you should change the ROR and ROL macros to use machine rotate instructions if you have them. this will save 2 instructions and a temporary per use, or about 32 to 40 instructions per en/decryption.

    note that gcc is smart enough to translate the ROL/R macros into machine rotates!

these optimizations are all rather persnickety, yet with them you should be able to get performance equal to assembly-coding, except that:

  1. with the lack of a bit rotate operator in C, rotates have to be synthesized from shifts. so access to asm will speed things up if your machine has rotates, as explained above in (3) (not necessary if you use gcc).

  2. if your machine has less than 12 32-bit registers i doubt your compiler will generate good code.

    i386 tries to configure the code for a 386 by only declaring 3 registers (it appears that gcc can use ebx, esi and edi to hold register variables). however, if you like assembly coding, the 386 does have 7 32-bit registers, and if you use ALL of them, use scaled by 8 address modes with displacement and other tricks, you can get reasonable routines for DesQuickCore… with about 250 instructions apiece. For DesSmall… it will help to rearrange des_keymap, i.e., now the sbox # is the high part of the index and the 6 bits of data is the low part; it helps to exchange these.

    since i have no way to conveniently test it i have not provided my shoehorned 386 version. note that with this release of desCore, gcc is able to put everything in registers(!), and generate about 370 instructions apiece for the DesQuickCore… routines!

coding notes¶

the en/decryption routines each use 6 necessary register variables, with 4 being actively used at once during the inner iterations. if you don’t have 4 register variables get a new machine. up to 8 more registers are used to hold constants in some configurations.

i assume that the use of a constant is more expensive than using a register:

  1. additionally, i have tried to put the larger constants in registers. registering priority was by the following:

    • anything more than 12 bits (bad for RISC and CISC)

    • greater than 127 in value (can’t use movq or byte immediate on CISC)

    • 9-127 (may not be able to use CISC shift immediate or add/sub quick),

    • 1〜8は常に登録されず、最もコスト効率の高い定数として扱われています。

  2. コンパイラがテーブルとテーブル+256を異なる定数レジスタに割り当てるのを理解できないため、繰り返し算術処理を行う可能性があります。そのため、可能な限り明示的にレジスタ変数に割り当てます。 m 可能であれば、レジスタ変数に割り当てることで助けになります。

インデックスが7ビットの符号なしまたはそれ以下のサイズであると仮定します。この仮定は68kおよびVAXでは逆になります。

アドレスは2つのレジスタまたはレジスタと小さな定数から効率的に形成できると仮定します。68000ではこの形式は控えめに使用されます。 two registers and small offset すべてのインデックススケーリングは明示的に実行され、log2(sizeof)による隠しシフトは行われません。

コードは、連想ができないコンパイラでも1つの隠しテンポラリしか必要としないように書かれています。これにより、すべてがレジスタに収まる可能性が高くなります。 KEEP THIS MORE SUBTLE POINT IN MIND IF YOU REWRITE ANYTHING.

（実際には、現在のコードの一部は2つのテンポラリを必要としますが、修正するとマクロの構造を破壊するか、別のテンポラリを宣言する必要があります。）

特別な効率的なデータ形式¶

ビットは通常（S7 S5 S3 S1）の配置で操作されます：

003130292827xxxx242322212019xxxx161514131211xxxx080706050403xxxx

（xビットはまだ存在しますが、Sボックスの位置を強調しています）。S6 S4 S2 S0を計算する際には、ビットが左に4ビット回転します：

282726252423xxxx201918171615xxxx121110090807xxxx040302010031xxxx

右端の2ビットは通常クリアされ、下位バイトがSボックスマッピングテーブルへのインデックスとして使用できます。次の2ビットは、テーブルのさまざまな部分にアクセスするためにさまざまな値に設定されます。

ルーチンの使用方法

データ型：

DesData型の8バイト領域へのポインタ。DESの鍵と入出力ブロックを保持します。

DesKeys型の128バイト領域へのポインタ。フルな768ビットの鍵を保持します。longアライメントが必要です。

DesQuickInit()

他のルーチンを使用する前にこの関数を呼び出してください。 Quick この関数は、これらのルーチンに必要な特別な64kテーブルを生成します。

DesQuickDone()

このテーブルを解放します。

DesMethod(m, k)

mは128バイトブロックへのポインタ、kは8バイトのDES鍵へのポインタです。鍵は奇数パリティを有する必要があります（または-1が返されます）。また、（半分の）弱い鍵であってはなりません（または-2が返されます）。通常、DesMethod()は0を返します。

mはkから埋め込まれ、mを呼び出す際のルーチンが、標準的なDESの暗号化/復号動作をkの鍵で行うようになります。DesMethodを使用する場合、標準的な56ビットの鍵を指定しますが、mを自分で埋め込むと768ビットの鍵になりますが、これは標準的な鍵ではありません。768ビットではなく1024ビットではないのは、各バイトの最下位2ビットが使用されないためです。これらの2ビットは、一部のマシンで暗号化/復号を高速化するためのマジック定数に設定されます。また、各バイトが特定のイテレーションで特定のS-boxを制御することも確認してください。

768ビット形式を直接使用するのは避けてください。私は128個の6ビットバイト（S-boxマッピング順など）を正しい形式に変換するルーチンを提供すべきです。これはいくつかのバイトの連結と回転処理を含みます。

Des{Small|Quick}{Fips|Core}{Encrypt|Decrypt}(d, m, s)

sに存在する8バイトをDES処理し、結果を d. (d,s: char *).

上記のようにmを768ビットの鍵として使用します。

Encrypt|Decryptの選択は明らかです。

Fips|Coreは、完全な標準FIPS初期および最終並び処理が行われるかどうかを決定します。行われない場合、データは非標準的なビット順序でロードおよび保存されます（FIPS無しIP/FP）。

FipsはQuickを10%、Smallを9%遅くします。

Small|Quickは、通常のルーチンか、64KB多くメモリを消費するクレイジーな高速ルーチンを使用するかを決定します。SmallはQuickより50%遅く、Quickは32倍のメモリを必要とします。DESのみを行うプログラム（例: 暗号化フィルタなど）のためにQuickが含まれています。

あなたのマシンでコンパイルするための手順¶

コードにはマシン依存性はなく（ポートングを参照）、おそらく now() desTest.c内のマクロのみです。すべての生成されたテーブルはマシンに依存しません。あなたのコンパイラに適した最適化フラグでMakefileを編集してください（MAX最適化）。

Kerberos（および/またはそのDESライブラリ）の高速化¶

Kerberos互換のインターフェースをdesUtil.cに含めています（des_key_sched()とdes_ecb_encrypt()関数）。KerberosまたはKerberos互換コードでこれらの関数を使用する場合は、リンカのコマンドラインでdesCore.aをKerberos互換ライブラリの前に配置してください。desCore.hを#includeする必要はありません。代わりにKerberosライブラリのヘッダーファイルを含めてください。

その他の用途¶

desCode.h内のマクロは、複雑な暗号化ルーチンにインラインDES関数を組み込むのに非常に役立ちます。

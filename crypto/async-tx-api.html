非同期転送/変換API¶

1. はじめに¶

async_tx APIは、非同期のバULKメモリ転送/変換の連鎖を記述するためのメソッドを提供し、トランザクション間の依存関係をサポートしています。これはdmaengineクライアントとして実装され、異なるハードウェアオフロードエンジン実装の詳細を抽象化します。このAPIにコードを書くことで、非同期操作を最適化し、APIが利用可能なオフロードリソースに操作の連鎖をフィットさせます。

2.系譜¶

このAPIは最初に、Intel(R) XscaleシリーズのI/Oプロセッサに搭載されたオフロードエンジンを使用して、md-raid5ドライバのメモリコピーおよびxor-パリティ計算をオフロードするための設計が行われました。また、Intel(R) I/OATエンジンを用いたネットワークスタックでのメモリコピーのオフロードに開発された'dmaengine'レイヤーにも拡張されました。以下の設計特徴が導入されました：

  1. 暗黙の同期パス：APIの利用者は、実行しているプラットフォームがオフロード機能をサポートしているかどうかを知る必要がありません。エンジンが利用可能な場合にオフロードが行われ、それ以外の場合はソフトウェアで実行されます。

  2. クロスチャネル依存連鎖：APIは、xor->copy->xorのようなraid5の場合の依存操作の連鎖をサブミットできます。APIは、操作の切り替えがハードウェアチャネルの切り替えを意味する場合を自動的に処理します。

  3. dmaengine拡張機能で、'memcpy'を超えた複数クライアントと操作タイプをサポート

3.使用方法¶

3.1 APIの一般的な形式¶

struct dma_async_tx_descriptor *
async_<operation>(<op specific parameters>, struct async_submit ctl *submit)

3.2 サポートされる操作¶

memcpy

ソースと宛先バッファ間のメモリコピー

memset

宛先バッファを特定のバイト値で埋める

xor

複数のソースバッファをxorし、結果を宛先バッファに書き込む

xor_val

複数のソースバッファをxorし、結果がゼロである場合にフラグを設定する。実装はメモリへの書き込みを防ぐように試みる

pq

複数のソースバッファからp+q（raid6シンドローム）を生成する

pq_val

pおよび/またはqバッファが与えられたソース系列と同期しているかを検証する

datap

(raid6_datap_recov) 与えられたソースからraid6データブロックおよびpブロックを復元する

2data

(raid6_2data_recov) 与えられたソースから2つのraid6データブロックを復元する

3.3 デスクリプタ管理¶

操作が非同期的に実行されるようキューイングされた場合、戻り値はNULLでなく、'descriptor'を指します。descriptorはオフロードエンジンドライバが制御し、操作が完了した際に再利用可能なリソースです。アプリケーションが連続する操作を送信する必要がある場合、依存関係が送信される前にdescriptorが自動的に再利用されないことを保証しなければなりません。これにより、オフロードエンジンドライバがdescriptorを再利用（または解放）できるようにする前に、アプリケーションがすべてのdescriptorを確認しなければなりません。descriptorは以下のいずれかの方法で確認できます。

  1. 子操作が送信されない場合、ASYNC_TX_ACKフラグを設定します。

  2. 別のasync_tx呼び出しの依存関係として未確認のdescriptorを送信すると、自動的に確認済み状態になります。

  3. descriptorに対してasync_tx_ack()を呼び出します。

3.4 操作はいつ実行されますか？¶

操作はasync_<operation>呼び出し後の即座に実行されません。オフロードエンジンドライバはパフォーマンス向上のため操作をバッチ処理し、チャネル管理に必要なmmioサイクルを減らします。ドライバ固有のしきい値に達した後、ドライバが待機中の操作を自動的に実行します。アプリケーションはasync_tx_issue_pending_all()を呼び出すことでこのイベントを強制的に実行できます。この関数はすべてのチャネルに適用されるため、アプリケーションはチャネルと操作のマッピングを把握していません。

3.5 操作はいつ完了しますか？¶

アプリケーションが操作の完了を知るための方法は2つあります。

  1. dma_wait_for_async_tx()を呼び出します。この呼び出しはCPUが操作の完了をポーリングしながらスピンします。依存関係チェーンや待機中の操作の実行も処理します。

  2. 完了コールバックを指定します。オフロードエンジンドライバが割り込みをサポートする場合、コールバックルーチンはタスクレットコンテキストで実行され、操作がソフトウェアで同期的に実行される場合、アプリケーションコンテキストで呼び出されます。コールバックはasync_<operation>呼び出し時に設定できます。また、アプリケーションが未知の長さの操作チェーンを送信する必要がある場合、async_trigger_callback()ルーチンを使用してチェーンの終わりで完了割り込み/コールバックを設定できます。

3.6 制約¶

  1. async_<operation>呼び出しはIRQコンテキストでは許可されません。他のコンテキストは制約#2に違反しない限り許可されます。

  2. 完了コールバックルーチンは新しい操作を送信できません。これにより同期的な場合では再帰が発生し、非同期的な場合ではスピンロックが2回取得される可能性があります。

3.7 例¶

xor->copy->xor操作を実行し、各操作は前の操作の結果に依存します:

void callback(void *param)
{
        struct completion *cmp = param;

        complete(cmp);
}

void run_xor_copy_xor(struct page **xor_srcs,
                    int xor_src_cnt,
                    struct page *xor_dest,
                    size_t xor_len,
                    struct page *copy_src,
                    struct page *copy_dest,
                    size_t copy_len)
{
        struct dma_async_tx_descriptor *tx;
        addr_conv_t addr_conv[xor_src_cnt];
        struct async_submit_ctl submit;
        addr_conv_t addr_conv[NDISKS];
        struct completion cmp;

        init_async_submit(&submit, ASYNC_TX_XOR_DROP_DST, NULL, NULL, NULL,
                        addr_conv);
        tx = async_xor(xor_dest, xor_srcs, 0, xor_src_cnt, xor_len, &submit)

        submit->depend_tx = tx;
        tx = async_memcpy(copy_dest, copy_src, 0, 0, copy_len, &submit);

        init_completion(&cmp);
        init_async_submit(&submit, ASYNC_TX_XOR_DROP_DST | ASYNC_TX_ACK, tx,
                        callback, &cmp, addr_conv);
        tx = async_xor(xor_dest, xor_srcs, 0, xor_src_cnt, xor_len, &submit);

        async_tx_issue_pending_all();

        wait_for_completion(&cmp);
}

include/linux/async_tx.hを参照してください。drivers/md/raid5.c内のops_run_*およびops_complete_*ルーチンも参照してください。

4. ドライバ開発ノート¶

4.1 コンフォーマンスポイント¶

dmaengineドライバでは、アプリケーションがasync_tx APIを使用する際に想定する仮定を満たすためにいくつかのコンフォーマンスポイントが必要です:

  1. 完了コールバックはタスケットコンテキストで実行されることが期待されます

  2. dma_async_tx_descriptorのフィールドはIRQコンテキストで操作されることはありません

  3. 依存操作のサブミット処理にはasync_tx_run_dependencies()をデスクリプタクリーンアップパスで使用してください

4.2 「私のアプリケーションはハードウェアチャネルの排他制御が必要です」¶

これは主にDMAエンジンドライバがデバイスからメモリへの操作をサポートする場合に発生します。これらの操作を実行するチャネルは、多くのプラットフォーム固有の理由により共有できません。このようなケースではdma_request_channel()インターフェースが提供されます。

インターフェースは:

struct dma_chan *dma_request_channel(dma_cap_mask_t mask,
                                     dma_filter_fn filter_fn,
                                     void *filter_param);

dma_filter_fnは以下のように定義されています:

typedef bool (*dma_filter_fn)(struct dma_chan *chan, void *filter_param);

オプションの'filter_fn'パラメータがNULLに設定されている場合、dma_request_channelはキャパビリティマスクを満たす最初のチャネルを単純に返します。逆にマスクパラメータで必要なチャネルを指定できない場合、filter_fnルーチンを使用してシステム内の利用可能なチャネルを処理できます。filter_fnルーチンはシステム内の各空きチャネルに対して1回呼び出されます。適切なチャネルを見つけた場合、filter_fnはDMA_ACKを返します。これはdma_request_channelの返却値としてそのチャネルを指定します。このインターフェースで割り当てられたチャネルは、dma_release_channel()が呼ばれるまで呼び出し元専用です。

DMA_PRIVATEキャパビリティフラグは、一般用途のアロケータによって使用されないDMAデバイスをタグ付けするために使用されます。チャネルが常にプライベートであることがわかっている場合、初期化時にこのフラグを設定できます。あるいは、dma_request_channel()が未使用の「パブリック」チャネルを見つけたときに設定されます。

ドライバおよびコンシューマーの実装において注意すべき注意点:

  1. チャネルがプライベートに割り当てられると、dma_release_channel()の呼び出し後でも一般用途アロケータによって考慮されなくなります。

  2. キャパビリティはデバイスレベルで指定されるため、dma_deviceが複数のチャネルを持つ場合、すべてのチャネルがパブリックか、すべてのチャネルがプライベートかのいずれかです。

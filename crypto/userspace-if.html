ユーザー空間インターフェース¶

はじめに¶

カーネル暗号APIがカーネル空間に提供する概念は、ユーザー空間インターフェースにも完全に適用可能です。したがって、カーネル内での使用ケースにおける高レベルなカーネル暗号APIの議論は、こちらでも同様に適用されます。

ただし、主な違いはユーザー空間が変換または暗号アルゴリズムの提供者となることはできず、常に消費者としてしか機能できないということです。

以下は、カーネル暗号APIがユーザー空間にエクスポートするインターフェースを説明しています。この説明の動作例としてlibkcapiというライブラリがあり、[1]から取得可能です。このライブラリは、カーネルから暗号サービスを必要とするユーザー空間アプリケーションで使用できます。

ただし、カーネル内での暗号APIの一部の詳細はユーザー空間には適用されません。これは、同期処理と非同期処理の違いが含まれます。ユーザー空間APIの呼び出しは完全に同期処理です。

[1] https://www.chronox.de/libkcapi.html

User Space API 一般的な注意事項¶

カーネル暗号APIはユーザー空間からアクセス可能です。現在、以下の暗号がアクセス可能です：

  • メッセージダイジェスト（鍵付きメッセージダイジェストを含む）（HMAC, CMAC）

  • 対称暗号

  • AEAD暗号

  • ランダムナンバー生成器

インターフェースはAF_ALG型のソケットタイプを介して提供されます。さらに、setsockoptオプションの型としてSOL_ALGが使用されます。ユーザー空間のヘッダーファイルがこれらのフラグをまだエクスポートしていない場合、以下のマクロを使用してください：

#ifndef AF_ALG
#define AF_ALG 38
#endif
#ifndef SOL_ALG
#define SOL_ALG 279
#endif

暗号はカーネル内API呼び出しと同じ名前でアクセスされます。これは暗号の汎用名と一意な名前の命名スキーマを含むだけでなく、汎用名の優先度の強制も含まれます。

カーネル暗号APIとやりとりするには、ユーザー空間アプリケーションがソケットを作成する必要があります。ユーザー空間はsend()/write()システムコールファミリを使用して暗号操作を呼び出し、結果はread()/recv()システムコールファミリで取得します。

以下のAPI呼び出しは、ユーザー空間アプリケーションがすでにソケットディスクリプタを開いていると仮定しています。ここではカーネル暗号APIに特有の呼び出しについてのみ説明します。

ソケットインターフェースを初期化するには、消費者が以下の手順を実行する必要があります：

  1. 異なる暗号タイプごとに以下のstruct sockaddr_algパラメータを指定してAF_ALG型のソケットを作成します。

  2. ソケットディスクリプタに対してbindを呼び出します

  3. ソケット記述子を使用してacceptを呼び出します。acceptシステムコールは、特定の暗号インスタンスとやり取りするために使用する新しいファイル記述子を返します。データをカーネルに送信するか、カーネルからデータを取得する際には、acceptで返されたファイル記述子を使用する必要があります。

インプレース暗号化操作¶

カーネル暗号APIのインカーネル操作と同様に、ユーザー空間インターフェースは暗号操作をインプレースで実行できます。つまり、送信/書き込みシステムコールで使用する入力バッファと、読み込み/受信システムコールで使用する出力バッファは同一でもよいです。これは対称暗号操作において、出力データを最終的な場所にコピーする必要を省くため特に重要です。

一方で、消費者が平文と暗号文を異なるメモリ領域に保持したい場合、暗号化および復号化操作でそれぞれ異なるメモリポインタを提供するだけで十分です。

メッセージダイジェストAPI¶

暗号操作に使用するメッセージダイジェストのタイプは、bindシステムコールを呼び出す際に選択します。bindは呼び出し元にstruct sockaddrデータ構造を埋めることを要求します。このデータ構造は以下の通り埋めなければなりません:

struct sockaddr_alg sa = {
    .salg_family = AF_ALG,
    .salg_type = "hash", /* this selects the hash logic in the kernel */
    .salg_name = "sha1" /* this is the cipher name */
};

salg_type値「hash」はメッセージダイジェストおよび鍵付きメッセージダイジェストに適用されます。ただし、鍵付きメッセージダイジェストは適切なsalg_nameで参照されます。鍵付きメッセージダイジェストの鍵を設定する方法については、以下のsetsockoptインターフェースを参照してください。

send()システムコールを使用して、処理すべきデータをアプリケーションが提供します。sendシステムコールは以下のフラグを指定できます:

  • MSG_MORE: このフラグが設定されている場合、sendシステムコールはメッセージダイジェストのアップデート関数のように動作し、最終的なハッシュはまだ計算されません。フラグが設定されていない場合、sendシステムコールは即座に最終メッセージダイジェストを計算します。

recv()システムコールを使用して、アプリケーションはカーネル暗号APIからメッセージダイジェストを読み取れます。メッセージダイジェストがバッファよりも大きい場合、カーネルがMSG_TRUNCフラグを設定します。

メッセージダイジェストの鍵を設定するには、呼び出しアプリケーションはALG_SET_KEYオプションを使用したsetsockopt()を呼び出す必要があります。鍵が設定されていない場合、HMAC操作は鍵による初期HMACステート変化なしで行われます。

対称暗号API¶

操作はメッセージダイジェストの議論と非常に似ています。初期化時にstruct sockaddrデータ構造は以下の通り埋めなければなりません:

struct sockaddr_alg sa = {
    .salg_family = AF_ALG,
    .salg_type = "skcipher", /* this selects the symmetric cipher */
    .salg_name = "cbc(aes)" /* this is the cipher name */
};

データをwrite/sendシステムコールファミリを使用してカーネルに送信する前に、消費者はキーパラメータを設定する必要があります。キーパラメータの設定方法は以下のsetsockopt呼び出しで説明されています。

sendmsg()システムコールを使用して、アプリケーションは暗号化または復号化処理対象のデータを提供します。また、sendmsg()システムコールが提供するデータ構造を使用して初期ベクトル（IV）を指定することもできます。

sendmsgシステムコールのstruct msghdrパラメータはstruct cmsghdrデータ構造に埋め込まれます。cmsghdrデータ構造がsend/recvシステムコールファミリとどのように一緒に使用されるかについては、recv(2)とcmsg(3)を参照してください。このcmsghdrデータ構造は、以下の情報が別個のヘッダーアクセスで指定されています。

  • 以下のフラグのいずれかを使用して、暗号操作の種類を指定します:

    • ALG_OP_ENCRYPT - データの暗号化

    • ALG_OP_DECRYPT - データの復号化

  • ALG_SET_IVフラグでマークされた初期ベクトル（IV）情報を指定します。

sendシステムコールファミリは以下のフラグを指定できます:

  • MSG_MORE: このフラグが設定されている場合、sendシステムコールは次のsendコール呼び出しでさらに入力データが期待される暗号更新関数として動作します。

注意: カーネルは予期しないデータに対して-EINVALを報告します。呼び出し元は、選択された暗号に対して/proc/cryptoに記載されている制約条件をすべて満たす必要があります。

recv()システムコールを使用して、アプリケーションはカーネル暗号APIから暗号操作の結果を読み取ることができます。出力バッファは暗号化または復号化されたデータのすべてのブロックを保持できるようにする必要があります。出力データサイズが小さい場合、その出力バッファサイズに収まるだけのブロック数が返されます。

AEAD暗号API¶

操作は対称暗号の議論と非常に似ています。初期化時にstruct sockaddrデータ構造は以下の通り埋め込まれます:

struct sockaddr_alg sa = {
    .salg_family = AF_ALG,
    .salg_type = "aead", /* this selects the symmetric cipher */
    .salg_name = "gcm(aes)" /* this is the cipher name */
};

データをwrite/sendシステムコールファミリを使用してカーネルに送信する前に、消費者はキーパラメータを設定する必要があります。キーパラメータの設定方法は以下のsetsockopt呼び出しで説明されています。

さらに、write/sendシステムコールファミリを使用してデータをカーネルに送信する前に、消費者は認証タグサイズを設定する必要があります。認証タグサイズを設定するには、以下のsetsockopt呼び出しを使用します。

sendmsg()システムコールを使用して、アプリケーションは暗号化または復号化処理対象のデータを提供します。また、sendmsg()システムコールが提供するデータ構造を使用して初期ベクトル（IV）を指定することもできます。

sendmsgシステムコールのstruct msghdrパラメータはstruct cmsghdrデータ構造に埋め込まれます。cmsghdrデータ構造がsend/recvシステムコールファミリとどのように一緒に使用されるかについては、recv(2)とcmsg(3)を参照してください。このcmsghdrデータ構造は、以下の情報が別個のヘッダーアクセスで指定されています。

  • 以下のフラグのいずれかを使用して、暗号操作の種類を指定します:

    • ALG_OP_ENCRYPT - データの暗号化

    • ALG_OP_DECRYPT - データの復号化

  • ALG_SET_IVフラグでマークされた初期ベクトル（IV）情報を指定します。

  • ALG_SET_AEAD_ASSOCLENフラグを使用して関連認証データ（AAD）を指定します。AADは平文/暗号文とともにカーネルに送信されます。メモリ構造については下記を参照してください。

sendシステムコールファミリは以下のフラグを指定できます:

  • MSG_MORE: このフラグが設定されている場合、sendシステムコールは次のsendコール呼び出しでさらに入力データが期待される暗号更新関数として動作します。

注意: カーネルは予期しないデータに対して-EINVALを報告します。呼び出し元は、選択された暗号に対して/proc/cryptoに記載されている制約条件をすべて満たす必要があります。

recv()システムコールを使用することで、アプリケーションはカーネルの暗号APIから暗号処理の結果を読み取ることができます。出力バッファは、以下に記載されたメモリ構造で定義されたサイズ以上である必要があります。出力データのサイズが小さければ、暗号処理は実行されません。

認証された復号処理では整合性エラーが発生する可能性があります。このような整合性の破綻は-EBADMSGエラー コードで示されます。

AEAD メモリ構造¶

AEAD暗号化は、ユーザー空間とカーネル空間間で1つのデータストリームとしてやり取りされる以下の情報に基づいて動作します。

  • 平文または暗号文

  • 関連認証データ (AAD)

  • 認証タグ

AADおよび認証タグのサイズはsendmsgおよびsetsockoptコールで提供されます（参照してください）。カーネルはデータストリーム全体のサイズを把握しているため、データストリーム内のデータコンポーネントの正しいオフセットを計算できるようになりました。

ユーザー空間の呼び出し元は、以下の順序で上記の情報を配置する必要があります。

  • AEAD暗号化入力: AAD || 平文

  • AEAD復号入力: AAD || 暗号文 || 認証タグ

ユーザー空間の呼び出し元が提供する出力バッファは、以下のデータを保持するために十分なサイズである必要があります。

  • AEAD暗号化出力: 暗号文 || 認証タグ

  • AEAD復号出力: 平文

ランダム数生成器API¶

また、操作は他のAPIと非常に似ています。初期化時にstruct sockaddrデータ構造体を以下のように埋める必要があります:

struct sockaddr_alg sa = {
    .salg_family = AF_ALG,
    .salg_type = "rng", /* this selects the random number generator */
    .salg_name = "drbg_nopr_sha256" /* this is the RNG name */
};

RNGの種類に応じて、RNGはシードを必要とします。シードはsetsockoptインターフェースを使用してキーを設定するために提供されます。たとえば、ansi_cprngはシードを必要とします。DRBGはシードを必要としませんが、シードを設定することが可能です。シードはまた Personalization String（パーソナライズ文字列） NIST SP 800-90A標準に記載されています。

read()/recvmsg()システムコールを使用することで、ランダムな数値を取得できます。カーネルは1回の呼び出しで最大128バイトを生成します。ユーザー空間がより多くのデータを必要とする場合、複数回のread()/recvmsg()呼び出しを行う必要があります。

警告: ユーザースペースの呼び出し元は、最初に述べたacceptシステムコールを複数回呼び出す可能性があります。この場合、返されたファイル記述子は同じ状態を持ちます。

カーネルがCRYPTO_USER_API_RNG_CAVPオプションでビルドされる場合、以下のCAVPテストインターフェースが有効になります:

  • 結合された エントロピー および ノンス ALG_SET_DRBG_ENTROPY setsockoptインターフェースを介してRNGに提供できます。エントロピーの設定にはCAP_SYS_ADMINの権限が必要です。

  • 追加データ send()/sendmsg()システムコールを使用して提供できますが、エントロピーが設定された後でのみ可能です。

ゼロコピーインターフェース¶

send/write/read/recvシステムコールファミリに加えて、AF_ALGインターフェースはsplice/vmspliceのゼロコピーインターフェースでアクセス可能です。名前のとおり、カーネルはカーネル空間へのコピー操作を避けるように試みます。

ゼロコピー操作ではデータがページ境界にアライメントされている必要があります。非アライメントデータでも使用可能ですがあまりに多くのカーネル操作が必要となり、ゼロコピーインターフェースの速度向上効果を打ち消す可能性があります。

ゼロコピー操作のシステム固有のサイズ制限は16ページです。AF_ALGにより多くのデータを送信する場合、ユーザー空間では最大16ページのサイズに分割して入力データを処理する必要があります。

以下のコード例でゼロコピーを使用できます（libkcapiには完全な動作例が含まれています）：

int pipes[2];

pipe(pipes);
/* input data in iov */
vmsplice(pipes[1], iov, iovlen, SPLICE_F_GIFT);
/* opfd is the file descriptor returned from accept() system call */
splice(pipes[0], NULL, opfd, NULL, ret, 0);
read(opfd, out, outlen);

setsockoptインターフェース¶

暗号処理に伴うデータの送受信をsend/write/read/recvシステムコールで処理するほか、暗号処理に追加情報を設定する必要があります。この追加情報は、オープンした暗号のファイルディスクリプタ（acceptシステムコールで返されるファイルディスクリプタ）を指定してsetsockoptシステムコールで設定します。

各setsockopt呼び出しではレベルSOL_ALGを使用する必要があります。

setsockoptインターフェースは、以下のデータをoptnameで指定して設定できます：

  • ALG_SET_KEY – キーの設定。キー設定は以下のタイプに適用されます：

    • skcipher暗号タイプ（対称暗号）

    • ハッシュ暗号タイプ（鍵付きメッセージダイジェスト）

    • AEAD暗号タイプ

    • 種子を提供するRNG暗号タイプ

  • ALG_SET_AEAD_AUTHSIZE – AEAD暗号の認証タグサイズの設定。暗号処理では指定されたサイズの認証タグが生成され、復号処理では指定されたサイズの認証タグが暗号文に含まれていると仮定します（下記のAEADメモリレイアウトセクションを参照）。

  • ALG_SET_DRBG_ENTROPY – ランダム数生成器のエントロピーの設定。このオプションはRNG暗号タイプにのみ適用されます。

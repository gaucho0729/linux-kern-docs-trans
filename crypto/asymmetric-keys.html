非対称/公開鍵暗号 キー タイプ¶

概要¶

「asymmetric（非対称）」キーテイプは、公開鍵暗号で使用されるキーデータをコンテナとして保持するように設計されており、暗号化の形式やメカニズム、キーフォームに特定の制限を課すことはありません。

非対称キーテイプは、キーデータに関連するデータ種類を定義するサブタイプを持ち、キーデータの記述や破壊を行う操作を提供します。ただし、キーデータが実際にキーファイルに保存されている必要はありません。

カーネル内でのキーリテンションと操作のサブタイプを定義することも可能です。ただし、暗号化ハードウェア（例: TPM）へのアクセスを提供することも可能で、そのハードウェアがキーリテンションと操作を行うために使用される場合があります。その場合、非対称キーテイプはTPMドライバへのインターフェースに過ぎません。

データパーサーの概念も提供されています。データパーサーは、インスタンス化関数に渡されたデータブロブから情報を抽出する責任があります。最初にブロブを認識するデータパーサーが、キーテイプのサブタイプを設定し、そのキーテイプで実行可能な操作を定義します。

データパーサーは、データブロブをキービットの集合として解釈するか、システムの他の場所に保管されているキーリファレンスとして解釈するかを判断します。

キーロケーション¶

名前が空のキーテイプが追加された場合、インスタンス化データパーサーがキーデータを事前にパースし、キーデータの記述をその内容から決定する機会が与えられます。

これにより、キーテイプを完全一致または部分一致で参照することが可能になります。キーテイプは、他の基準でもキーロケーションを参照する場合があります。

非対称キーテイプのマッチ関数は、記述と基準文字列の単純な比較にとどまらず、より幅広い比較が可能です:

  1. 基準文字列が「id:<hexdigits>」形式の場合、マッチ関数はキーフィンガープリントを検査し、「id:」後のhexdigitsがフィンガープリントの末尾と一致するかを確認します。例えば:

    keyctl search @s asymmetric id:5acc2142

    フィンガープリント:

    1A00 2040 7601 7889 DE11  882C 3823 04AD 5ACC 2142

  2. 基準文字列が「<subtype>:<hexdigits>」形式の場合、(1)と同様にIDを検査しますが、追加された制限として指定されたサブタイプ（例: tpm）のキーロケーションに限定されます。例えば:

    keyctl search @s asymmetric tpm:5acc2142

/proc/keysを確認すると、キーフィンガープリントの最後の8桁のhex値とサブタイプが表示されます:

1a39e171 I-----     1 perm 3f010000     0     0 asymmetric modsign.0: DSA 5acc2142 []

非対称キーパッケージのアクセス¶

カーネル内部から非対称鍵への一般的なアクセスを行うには、以下のインクルージョンが必要です:

#include <crypto/public_key.h>

これは非対称/公開鍵を扱うための関数にアクセスを提供します。その場所で、公開鍵暗号アルゴリズムを表すための3つの列挙型が定義されています:

enum pkey_algo

これらで使用されるハッシュアルゴリズム:

enum pkey_hash_algo

および鍵識別子の表現:

enum pkey_id_type

鍵タイプの表現タイプが必要なのは、異なる標準から得られた鍵識別子が必ずしも互換性があるからです。たとえば、PGPは鍵データとPGP固有のメタデータをハッシュ化して鍵識別子を生成しますが、X.509は任意の証明書識別子を持ちます。

鍵に対して定義される操作は次の通りです:

  1. 署名検証。

他の操作（暗号化など）は検証に必要な同じ鍵データで実行可能ですが、現在はサポートされていません。また、復号や署名生成など他の操作は追加の鍵データが必要です。

署名検証¶

暗号化された署名の検証を行うための操作が提供されています。非対称鍵を使用して、公開鍵を提供またはアクセス可能にするためです:

int verify_signature(const struct key *key,
                     const struct public_key_signature *sig);

呼び出し元はすでに何らかのソースから鍵を取得しており、その後その鍵を使って署名を検証できます。呼び出し元は署名を解析し、関連するビットをsigで指される構造体に転送する必要があります:

struct public_key_signature {
        u8 *digest;
        u8 digest_size;
        enum pkey_hash_algo pkey_hash_algo : 8;
        u8 nr_mpi;
        union {
                MPI mpi[2];
                ...
        };
};

使用するアルゴリズムはsig->pkey_hash_algoに記録され、実際の署名を構成するすべてのMPIはsig->mpi[]に保存され、MPIの数はsig->nr_mpiに設定されます。

さらに、呼び出し元がデータをハッシュ化し、その結果のハッシュをsig->digestに指し、ハッシュのサイズをsig->digest_sizeに設定する必要があります。

関数は成功時に0を返し、署名が一致しない場合は-EKEYREJECTEDを返します。

関数はまた、サポートされていない公開鍵アルゴリズムまたは公開鍵/ハッシュアルゴリズムの組み合わせが指定された場合、または鍵が操作をサポートしていない場合に-ENOTSUPPを返すことがあります。また、一部のパラメータに不正なデータがある場合は-EBADMSGまたは-ERANGEを、メモリ割当が失敗した場合は-ENOMEMを返します。鍵引数が正しい型でないか、不完全に設定されている場合は-EINVALを返すことがあります。

非対称鍵サブタイプ¶

非対称鍵は、その鍵に対して実行可能な操作のセットを定義し、鍵ペイロードとして添付されるデータを決定するサブタイプを持っています。ペイロード形式はサブタイプの都合次第です。

サブタイプは鍵データパーサーによって選択され、パーサーはそのサブタイプに必要なデータを初期化しなければなりません。非対称鍵はサブタイプモジュールへの参照を保持します。

サブタイプの定義構造は以下にあります:

#include <keys/asymmetric-subtype.h>

以下のように表示されます:

struct asymmetric_key_subtype {
        struct module           *owner;
        const char              *name;

        void (*describe)(const struct key *key, struct seq_file *m);
        void (*destroy)(void *payload);
        int (*query)(const struct kernel_pkey_params *params,
                     struct kernel_pkey_query *info);
        int (*eds_op)(struct kernel_pkey_params *params,
                      const void *in, void *out);
        int (*verify_signature)(const struct key *key,
                                const struct public_key_signature *sig);
};

非対称鍵は、payload[asym_subtype]メンバを通じてこの構造を指します。

所有者と名前フィールドは、所有モジュールとサブタイプの名前に設定する必要があります。現在、名前は印刷ステートメントにのみ使用されています。

サブタイプによって定義された操作は以下の通りです:

  1. describe().

    必須です。これにより、サブタイプは/proc/keysにキーに対して何かを表示できます。例えば、公開鍵アルゴリズムのタイプ名を表示できます。キーの種類は、この後ろのキー識別子文字列の末尾を表示します。

  2. destroy().

    必須です。これにより、キーに関連するメモリが解放されます。非対称鍵は、指紋を解放し、サブタイプモジュールの参照を解放する責任を負います。

  3. query().

    必須です。これは、キーの機能を照会するための関数です。

  4. eds_op().

    オプションです。これは、暗号化、復号、署名作成操作のエントリポイントです（操作IDによってパラメータ構造体で区別されます）。サブタイプは、操作を実装するために好きなように処理できます（ハードウェアへのオフロードを含む）。

  5. verify_signature().

    オプションです。これは署名検証のエントリポイントです。サブタイプは、操作を実装するために好きなように処理できます（ハードウェアへのオフロードを含む）。

インスタンス化データパーサー¶

非対称鍵タイプは、通常、キーのデータを保持する素のblobデータを保存したり扱ったりしたくありません。使用するたびにこれを解析し、エラーをチェックする必要があります。さらに、blobの内容には、さまざまなチェックが行われる可能性があります（例：自己署名、有効期限）、また、キーに関する有用なデータ（識別子、機能）を含んでいる場合があります。

また、blobは、キー自体ではなく、キーを含むハードウェアへのポインタを表す場合もあります。

パーサーが実装可能なblob形式の例には次の通りです:

  • OpenPGPパケットストリーム [RFC 4880].

  • X.509 ASN.1ストリーム.

  • TPMキーへのポインタ.

  • UEFIキーへのポインタ.

  • PKCS#8プライベートキー [RFC 5208].

  • PKCS#5暗号化されたプライベートキー [RFC 2898].

キーインスタンス化中に、リスト内の各パーサーが試され、-EBADMSGを返さないまで続けます。

パーサーの定義構造は以下にあります:

#include <keys/asymmetric-parser.h>

以下のように表示されます:

struct asymmetric_key_parser {
        struct module   *owner;
        const char      *name;

        int (*parse)(struct key_preparsed_payload *prep);
};

所有者と名前フィールドは、所有モジュールとパーサーの名前に設定する必要があります。

現在、パーサーによって定義されている操作は1つのみであり、これは必須です:

  1. parse().

    これは、キーパスの作成および更新時にキーパースを事前に解析するために呼び出されます。特に、キーパスが割り当てられる前に呼び出され、呼び出し元が説明を提供しない場合でもキーディスクリプションを提供することが許可されています。

    呼び出し元は、data、datalen、quotalenを除きすべてのフィールドがクリアされた以下の構造体へのポインタを渡します[参照 Kernel Key Retention Service]:

    struct key_preparsed_payload {
        char            *description;
        void            *payload[4];
        const void      *data;
        size_t          datalen;
        size_t          quotalen;
};

    インスタンスデータはdataポインタで指されるblobに格納され、datalenのサイズです。parse()関数はこれらの2つの値を一切変更してはなりません。他の値も変更しない必要があります。ただし、blob形式を認識し、-EBADMSGを返さない場合を除きます。

    パーサーがblobを受け入れる場合、キーディスクリプションを提案し、->descriptionにアタッチする必要があります。->payload[asym_subtype]は使用するサブタイプへのポインタに設定し、->payload[asym_crypto]はそのサブタイプの初期化データへのポインタに設定します。->payload[asym_key_ids]は1つ以上の16進形式のフィンガープリントへのポインタに設定し、quotalenはこのキーパスがどのくらいのクォータを占有するかを示すように更新します。

    クリアアップ時に、->payload[asym_key_ids]および->descriptionにアタッチされたデータは kfree()’dされ、->payload[asm_crypto]にアタッチされたデータはサブタイプの->destroy()メソッドに渡され、破棄されます。->payload[asym_subtype]で指されるサブタイプのモジュール参照が設定されます。

    データ形式が認識されない場合、-EBADMSGを返す必要があります。認識されてもキーパスの設定が不可能な場合は、他の負のエラーコードを返します。成功時は0を返します。

    キーフィンガープリント文字列は部分的に一致する場合があります。RSAやDSAなどの公開鍵アルゴリズムでは、キーフィンガープリントの印刷可能な16進形式が使用される可能性があります。

パーサーの登録と解除に使用される関数が提供されています:

int register_asymmetric_key_parser(struct asymmetric_key_parser *parser);
void unregister_asymmetric_key_parser(struct asymmetric_key_parser *subtype);

パーサーは同じ名前を持つことはできません。名前はデバッグメッセージの表示にのみ使用されます。

Keyring Link Restrictions¶

add_keyを使用してユーザー空間から作成されたキーリングは、リンクされるキーランクの署名を確認するように構成できます。有効な署名を持たないキーランクはリンクできません。

いくつかの制限方法が利用可能です:

  1. キーベースのカーネル組み込み信頼キーリングを使用する制限

    • KEYCTL_RESTRICT_KEYRINGと併用されるオプション文字列: - “builtin_trusted”

    サインインキーは、カーネルのビルイン信頼キーリングから検索されます。ビルイン信頼キーリングが構成されていない場合、すべてのリンクが拒否されます。ca_keys カーネルパラメータも、署名検証に使用されるキーの選定に影響を与えます。

  2. カーネルのビルインおよび二次信頼キーリングの使用を制限する

    • KEYCTL_RESTRICT_KEYRING と併用するオプション文字列: - 「builtin_and_secondary_trusted」

    サインインキーは、カーネルのビルイン信頼キーリングおよび二次信頼キーリングから検索されます。二次信頼キーリングが構成されていない場合、この制限は「builtin_trusted」オプションと同じ挙動になります。ca_keys カーネルパラメータも、署名検証に使用されるキーの選定に影響を与えます。

  3. 別途のキーまたはキーリングの使用を制限する

    • KEYCTL_RESTRICT_KEYRING と併用するオプション文字列: - 「key_or_keyring:<キーまたはキーリングのシリアル番号>[:chain]」

    キーのリンクリクエストが行われるたびに、リンクが成功するためには、リンクされるキーが指定されたキーのいずれかによって署名されている必要があります。このキーは、非対称鍵のシリアル番号を直接指定することで指定できます。また、キーリングのシリアル番号を指定することで、複数のキーから署名キーを検索することも可能です。

    文字列の最後に「chain」オプションが指定されている場合、宛先キーリング内のキーも署名キーとして検索されます。これにより、証明書チェーンの検証が可能になります。各証明書をルートに近い順にキーリングに追加することで、証明書チェーンを検証できます。例えば、ルート証明書のセットへのリンクを持つキーリングを1つ用意し、検証対象の各証明書チェーンに別途制限されたキーリングを設定できます:

    # Create and populate a keyring for root certificates
root_id=`keyctl add keyring root-certs "" @s`
keyctl padd asymmetric "" $root_id < root1.cert
keyctl padd asymmetric "" $root_id < root2.cert

# Create and restrict a keyring for the certificate chain
chain_id=`keyctl add keyring chain "" @s`
keyctl restrict_keyring $chain_id asymmetric key_or_keyring:$root_id:chain

# Attempt to add each certificate in the chain, starting with the
# certificate closest to the root.
keyctl padd asymmetric "" $chain_id < intermediateA.cert
keyctl padd asymmetric "" $chain_id < intermediateB.cert
keyctl padd asymmetric "" $chain_id < end-entity.cert

    最終的なエンドエンティティ証明書が「chain」キーリングに成功して追加された場合、その証明書がルート証明書のいずれかに有効な署名チェーンを持つことが確認できます。

    ルート証明書をリンクした後でキーリングを制限することで、1つのキーリングを用いて署名チェーンの検証が可能です:

    # Create a keyring for the certificate chain and add the root
chain2_id=`keyctl add keyring chain2 "" @s`
keyctl padd asymmetric "" $chain2_id < root1.cert

# Restrict the keyring that already has root1.cert linked.  The cert
# will remain linked by the keyring.
keyctl restrict_keyring $chain2_id asymmetric key_or_keyring:0:chain

# Attempt to add each certificate in the chain, starting with the
# certificate closest to the root.
keyctl padd asymmetric "" $chain2_id < intermediateA.cert
keyctl padd asymmetric "" $chain2_id < intermediateB.cert
keyctl padd asymmetric "" $chain2_id < end-entity.cert

    最終的なエンドエンティティ証明書が「chain2」キーリングに成功して追加された場合、キーリングが制限される前のルート証明書に有効な署名チェーンが存在することが確認できます。

これらのすべてのケースにおいて、署名キーが見つかった場合、リンクするキーの署名は署名キーを使用して検証されます。署名が成功した場合にのみ、要求されたキーがキーリングに追加されます。親証明書が見つからない場合は-ENOKEYが返され、署名検証が失敗したか、キーがブラックリストに登録されている場合は-EKEYREJECTEDが返されます。署名検証が実行できない場合、他のエラーが返される可能性があります。

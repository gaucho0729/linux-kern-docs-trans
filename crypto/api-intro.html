スクラットリスト暗号API¶

はじめに¶

Scatterlist暗号化APIはページベクター（scatterlists）を引数として受け取り、ページ自体に対して直接処理を行います。ECBモード暗号などの一部のケースでは、ページをコピーすることなく場所をそのまま暗号化することが可能です。

この設計の初期目標の一つはIPsecの容易なサポートを実現することでした。これにより、ページ分割されたskb（スケルトンパケット）の処理を線形化せずに実行できるようになります。

詳細¶

最も基本的なレベルにはアルゴリズムがあり、これらは動的にAPIに登録されます。

「変換（Transforms）」はユーザーがインスタンス化するオブジェクトであり、状態を保持し、すべての実装ロジック（例：ページベクターの操作）を処理し、下位アルゴリズムへの抽象化を提供します。しかし、ユーザー側では非常にシンプルです。

概念的には、APIのレイヤー構造は以下のようになります：

[transform api]  (user interface)
[transform ops]  (per-type logic glue e.g. cipher.c, compress.c)
[algorithm api]  (for registering algorithms)

ユーザーインターフェースとアルゴリズム登録APIを極力シンプルにし、コアロジックを隠蔽するように設計されています。CryptoapiやNettleなどの既存APIから多くの良いアイデアを採用しています。

現在のAPIは、AEAD（認証付き暗号化（関連データあり））、ブロック暗号、暗号、圧縮機、ハッシュの5つの主な変換タイプをサポートしています。

注意：ブロック暗号はやや誤解を招く表現です。実際にはストリーム暗号を含むすべての暗号をサポートすることを意味します。ブロック暗号と暗号の違いは、後者が常に1ブロックのみを処理するのに対し、前者はブロックサイズの要件に応じて任意の量のデータを処理可能である点です（つまり、ストリーム暗号以外はブロック単位での処理のみが可能です）。

APIの使用例はこちら：

#include <crypto/hash.h>
#include <linux/err.h>
#include <linux/scatterlist.h>

struct scatterlist sg[2];
char result[128];
struct crypto_ahash *tfm;
struct ahash_request *req;

tfm = crypto_alloc_ahash("md5", 0, CRYPTO_ALG_ASYNC);
if (IS_ERR(tfm))
        fail();

/* ... set up the scatterlists ... */

req = ahash_request_alloc(tfm, GFP_ATOMIC);
if (!req)
        fail();

ahash_request_set_callback(req, 0, NULL, NULL);
ahash_request_set_crypt(req, sg, result, 2);

if (crypto_ahash_digest(req))
        fail();

ahash_request_free(req);
crypto_free_ahash(tfm);

多くの実例は再現テストモジュール（tcrypt.c）に含まれています。

開発者向けノート¶

変換はユーザーコンテキストでのみ割り当てられ、暗号処理メソッドはsoftirqおよびユーザーコンテキストからのみ呼び出されます。setkeyメソッドを持つ変換については、同様にユーザーコンテキストでのみ呼び出されるべきです。

暗号処理でAPIを使用する場合、各scatterlistが暗号のブロックサイズ（通常は8バイト）の倍数であるデータを含めることでパフォーマンスが最適になります。これにより、非アライメントされたページフラグメント境界でのコピー作業を回避できます。

新アルゴリズムの追加¶

新規アルゴリズムの導入申請時には、少なくともいくつかのテストベクター（標準的なソースを優先）を含めることが必須条件です。

既存のよく知られたコードの変換は推奨されます。なぜなら、コードがレビューされ広くテストされている可能性が高いからです。LGPLソースからコードを提出する場合、GPLライセンスに変更することをご検討ください（LGPLのセクション3を参照）。

提出されたアルゴリズムは一般的に特許のないものでなければなりません（例：IDEAは2011年頃までメインラインに含まれていなかった）。また、認められた標準に基づいたものか、適切な同僚レビューを経たものでなければなりません。

特定のアルゴリズムの使用に関連するRFCや、一般的なアプリケーションノート（例：RFC2451（『ESP CBC-Mode Cipher Algorithms』））を確認してください。

マクロの過度な使用は避けて、インライン関数を使用することをお勧めします。gccはインライン処理をうまく行いますが、一部のプラットフォームではマクロの過剰使用がコンパイル問題を引き起こす可能性があります。

下記のウェブサイトにあるTODOリストを確認し、すでに誰かが取り組んでいる可能性のある項目を確認してください。

暗号アルゴリズムの開発¶

変換の登録と解除¶

Crypto API には 3 種類の登録関数があります。1 番目は汎用的な暗号変換を登録するためのもので、他の 2 番目はハッシュ変換と圧縮変換に特化しています。後者の 2 番目については別章で詳しく説明しますが、ここでは汎用的な関数のみを確認します。

登録関数について説明する前に、各々に埋め込む必要のあるデータ構造 struct crypto_algを考慮しなければなりません — 以下にこのデータ構造の説明を示します。

汎用的な登録関数は include/linux/crypto.h に定義されており、その定義は以下に示します。前者は単一の変換を登録し、後者は変換の記述を配列で受け取るためのものです。後者はドライバが複数の変換を一括して登録する際などに役立ちます。

int crypto_register_alg(struct crypto_alg *alg);
int crypto_register_algs(struct crypto_alg *algs, int count);

これらの関数に対応する関数は以下の通りです。

void crypto_unregister_alg(struct crypto_alg *alg);
void crypto_unregister_algs(struct crypto_alg *algs, int count);

登録関数は成功時は 0 を返し、失敗時は負の errno 値を返します。crypto_register_algs() はすべての指定されたアルゴリズムを成功裏に登録した場合にのみ成功し、途中で失敗した場合は変更内容をロールバックします。

解除関数は常に成功するため、戻り値を持ちません。現在登録されていないアルゴリズムを解除しようとしないでください。

単一ブロック対称暗号 [CIPHER]¶

変換の例: aes, serpent, …

このセクションでは、最も単純な変換実装である CIPHER 型について説明します。CIPHER 型は対称暗号で、1 ブロックずつ処理し、ブロック間には依存関係が全くない変換に使用されます。

登録の詳細¶

[CIPHER] アルゴリズムの登録は、 struct crypto_alg フィールド .cra_type が空である点が特徴です。.cra_u.cipher には、この変換を実装するための適切なコールバック関数を設定する必要があります。

参照 struct cipher_alg も参照してください。

struct cipher_alg による暗号定義¶

struct cipher_alg は単一のブロック暗号を定義します。

これらの関数がカーネルの他の部分から呼び出される際のフローチャートを以下に示します。注意点として、.cia_setkey() の呼び出しがこれらのフローチャートの前後でも可能ですが、実行中には呼び出せません。

KEY ---.    PLAINTEXT ---.
       v                 v
 .cia_setkey() -> .cia_encrypt()
                         |
                         '-----> CIPHERTEXT

また、.cia_setkey() を複数回呼び出すパターンも有効です:

KEY1 --.    PLAINTEXT1 --.         KEY2 --.    PLAINTEXT2 --.
       v                 v                v                 v
 .cia_setkey() -> .cia_encrypt() -> .cia_setkey() -> .cia_encrypt()
                         |                                  |
                         '---> CIPHERTEXT1                  '---> CIPHERTEXT2

多ブロック暗号¶

変換の例: cbc(aes), chacha20, …

このセクションでは、マルチブロック暗号変換の実装について説明します。マルチブロック暗号は、変換関数に供給されたデータのスキャッターリストを処理する変換に使用されます。結果は、データのスキャッターリストに出力されます。

登録の詳細¶

マルチブロック暗号アルゴリズムの登録は、暗号API全体で最も標準的な手順の一つです。

注意：暗号実装がデータの適切なアライメントを必要とする場合、呼び出し元はcrypto_skcipher_alignmask()関数を使用してメモリアライメントマスクを特定する必要があります。カーネルの暗号APIは未アライメントのリクエストを処理できますが、これによりカーネルがデータの再アライメントを実行する必要があり、データの移動が伴う追加のオーバーヘッドが発生します。

struct skcipher_algによる暗号定義¶

struct skcipher_algは、マルチブロック暗号、またはより一般的に長さを保持する対称暗号アルゴリズムを定義します。

スキャッターリストの処理¶

一部のドライバは、ハードウェアに平文を含むスキャッターリストの別個のチャンクを供給する必要がある場合、ジェネリックスキャッターウォーキングを用いることがあります。Linuxカーネルのスキャッターリスト実装が提供するスキャッターウォーキングインターフェースを参照してください。

ハッシュ処理 [HASH]¶

変換の例：crc32, md5, sha1, sha256,…

変換の登録と解除¶

ハッシュ変換の登録方法は、変換が同期的[SHASH]か非同期的[AHASH]か、および登録するハッシュ変換の数によって異なります。プロトタイプはinclude/crypto/internal/hash.hに定義されています:

int crypto_register_ahash(struct ahash_alg *alg);

int crypto_register_shash(struct shash_alg *alg);
int crypto_register_shashes(struct shash_alg *algs, int count);

ハッシュ変換の解除に当たっては、以下の対応処理が用意されています:

void crypto_unregister_ahash(struct ahash_alg *alg);

void crypto_unregister_shash(struct shash_alg *alg);
void crypto_unregister_shashes(struct shash_alg *algs, int count);

struct shash_algおよびahash_algによる暗号定義¶

これらの関数がカーネルの他の部分から操作される際の呼び出し手順の概要です。注意点として、.setkey()呼び出しはこれらの手順の前後に行うことが可能ですが、実行中には行うことはできません。また、.init()を直後に.follow()呼び出しを行うことも、完全に有効な変換です。

I)   DATA -----------.
                     v
      .init() -> .update() -> .final()      ! .update() might not be called
                  ^    |         |            at all in this scenario.
                  '----'         '---> HASH

II)  DATA -----------.-----------.
                     v           v
      .init() -> .update() -> .finup()      ! .update() may not be called
                  ^    |         |            at all in this scenario.
                  '----'         '---> HASH

III) DATA -----------.
                     v
                 .digest()                  ! The entire process is handled
                     |                        by the .digest() call.
                     '---------------> HASH

カーネルの他の部分から使用される場合の.export()/.import()関数の呼び出し手順の概要です。

KEY--.                 DATA--.
     v                       v                  ! .update() may not be called
 .setkey() -> .init() -> .update() -> .export()   at all in this scenario.
                          ^     |         |
                          '-----'         '--> PARTIAL_HASH

----------- other transformations happen here -----------

PARTIAL_HASH--.   DATA1--.
              v          v
          .import -> .update() -> .final()     ! .update() may not be called
                      ^    |         |           at all in this scenario.
                      '----'         '--> HASH1

PARTIAL_HASH--.   DATA2-.
              v         v
          .import -> .finup()
                        |
                        '---------------> HASH2

リクエストオブジェクトを「放棄」することも完全に合法です：.init()を呼び出し、その後（複数回）.update()を呼び出すだけで、今後は.final()、.finup()、.export()のいずれも呼び出さないことが可能です。

言い換えれば、実装ではリソースの割り当てとクリーンアップに注意する必要があります。.init()または.update()の呼び出し後には、リクエストオブジェクトに関連するリソースが割り当てられたまま残ってはいけません。それらのリソースを解放する機会がなくなる可能性があるからです。

非同期ハッシュ変換の詳細¶

一部のドライバでは、スキャッターリスト内の入力データを分割して供給する必要がある場合、Generic ScatterWalkを使用したいと考えます。結果のハッシュを含むバッファは常に.cra_alignmaskに正しくアライメントされているため、この点について心配する必要はありません。

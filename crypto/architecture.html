カーネル暗号APIアーキテクチャ¶

暗号アルゴリズムの種類¶

カーネル暗号APIは、以下の暗号タイプ用に異なるAPIコールを提供します:

  • 対称暗号

  • AEAD暗号

  • メッセージダイジェスト、含む鍵付きメッセージダイジェスト

  • ランダム数生成

  • ユーザー空間インターフェース

暗号とテンプレート¶

カーネル暗号APIは単一ブロック暗号およびメッセージダイジェストの実装を提供します。さらに、カーネル暗号APIは単一ブロック暗号およびメッセージダイジェストと併用可能な多数の「テンプレート」を提供します。テンプレートにはブロックチェインモードのすべての種類、HMACメカニズムなどが含まれます。

単一ブロック暗号およびメッセージダイジェストは、呼び出し元が直接使用するか、テンプレートと併せて使用してマルチブロック暗号または鍵付きメッセージダイジェストを形成できます。

単一ブロック暗号は複数のテンプレートとともに呼び出すこともできます。ただし、テンプレートは単一暗号なしでは使用できません。

proc/cryptoを確認し、「name」を検索してください。例えば:

  • aes

  • ecb(aes)

  • cmac(aes)

  • ccm(aes)

  • rfc4106(gcm(aes))

  • sha1

  • hmac(sha1)

  • authenc(hmac(sha1),cbc(aes))

これらの例では、「aes」と「sha1」は暗号であり、他のすべてはテンプレートです。

同期と非同期操作¶

カーネル暗号APIは同期および非同期のAPI操作を提供します。

同期API操作を使用する場合、呼び出し元は暗号操作を実行し、カーネル暗号APIが同期的に実行します。つまり、呼び出し元は暗号操作が完了するまで待機します。そのため、カーネル暗号APIの呼び出しは通常の関数呼び出しのように動作します。同期操作ではAPIコールのセットは小さく、他の暗号ライブラリと概念的に類似しています。

非同期操作はカーネル暗号APIが提供し、暗号操作の呼び出しはほぼ即座に完了します。この呼び出しは暗号操作をトリガーしますが、完了を通知しません。暗号操作を呼び出す前に、呼び出し元はカーネル暗号APIが完了を通知するために呼び出すコールバック関数を提供する必要があります。さらに、呼び出し元はデータの整合性を保護するために適切なロックを適用し、非同期イベントを処理できるようにする必要があります。カーネル暗号APIは呼び出し元のデータ整合性を保護するための特別なシリアル化操作は行いません。

暗号API暗号参照と優先度¶

呼び出し元は文字列で暗号を参照します。この文字列には以下のセマンティクスがあります:

template(single block cipher)

「template」と「single block cipher」は、前述のテンプレートおよび単一ブロック暗号をそれぞれ指します。追加でテンプレートが他のテンプレートを含む場合、例えば

template1(template2(single block cipher)))

カーネル暗号APIは、テンプレートまたは単一ブロック暗号の複数の実装を提供する場合があります。例えば、新しいインテルハードウェアにおけるAESには、AES-NI、アセンブリ実装、またはストレートCの3つの実装があります。現在、カーネル暗号APIで文字列「aes」を使用して暗号実装を指定する場合、どの実装が選択されるかは、カーネル暗号APIが各暗号実装に割り当てた優先度番号によって決まります。呼び出し元が暗号ハンドルの初期化時に暗号を参照する文字列を使用する場合、カーネル暗号APIはその名前を持つ実装をすべて検索し、最も高い優先度を持つ実装を選択します。

現在、呼び出し元が特定の暗号実装を参照する必要がある場合があり、優先度に基づく選択に依存したくないことがあります。このようなシナリオに対応するため、カーネル暗号APIは暗号実装が一般的な名前に加えて一意の名前を登録できるようにしています。その一意の名前を使用する場合、呼び出し元は常に意図した暗号実装を参照できるようになります。

利用可能な暗号の一覧は/proc/cryptoに記載されています。ただし、そのリストはテンプレートと暗号のすべての組み合わせを指定するものではありません。/proc/cryptoに記載された各ブロックには、以下の情報が含まれる場合があります（以下に記載されたコンポーネントのうち、暗号に適用できない場合は表示されません）：

  • name: 優先度に基づく選択に用いられる暗号の一般的な名前 – この名前は暗号割当APIコールで使用できます（上記に記載されたすべての名前はこのような一般的な名前の例です）

  • driver: 暗号の一意の名前 – この名前は暗号割当APIコールで使用できます

  • module: 暗号実装を提供するカーネルモジュール（または静的リンクされた暗号の場合は「kernel」）

  • priority: 暗号実装の優先度値

  • refcnt: その暗号の参照カウント（つまり、この暗号を現在消費している消費者の数）

  • selftest: その暗号の自己テストが成功したかどうかの指定

  • type:

    • 対称鍵暗号用のskcipher

    • 追加のテンプレートとともに使用可能な単一ブロック暗号用のcipher

    • 同期メッセージダイジェスト用のshash

    • 非同期メッセージダイジェスト用のahash

    • AEAD暗号タイプ用のaead

    • 圧縮タイプ変換用のcompression

    • ランダム数生成器用のrng

    • ECDHやDHなどのキーアグリーメントプロトコル素子（KPP）暗号用のkpp

  • blocksize: 暗号のブロックサイズ（バイト）

  • keysize: キーのサイズ（バイト）

  • ivsize: IVのサイズ（バイト）

  • seedsize: 乱数生成器に必要な種データのサイズ

  • digestsize: メッセージダイジェストの出力サイズ

  • geniv: IV生成器（非推奨）

鍵サイズ¶

暗号ハンドルを割り当てる際、呼び出し元は暗号タイプのみを指定します。対称暗号は通常複数のキーサイズ（例: AES-128 vs. AES-192 vs. AES-256）をサポートしますが、これらのキーサイズは提供されたキーサイズの長さで決定されます。そのため、カーネル暗号APIは別途で対称暗号の特定のキーサイズを選択する方法を提供していません。

暗号割り当てタイプとマスク¶

異なる暗号ハンドル割り当て関数はタイプとマスクフラグの指定を許可します。両方のパラメータは以下の意味を持ち（以下セクションでは説明されません）、

タイプフラグは暗号アルゴリズムのタイプを指定します。呼び出し元がデフォルト処理を希望する場合、通常0を指定します。それ以外の場合、呼び出し元は以下の選択肢を指定できます（前述の暗号タイプに一致します）：

  • CRYPTO_ALG_TYPE_CIPHER 単一ブロック暗号

  • CRYPTO_ALG_TYPE_COMPRESS 圧縮

  • CRYPTO_ALG_TYPE_AEAD 付随データ付き認証暗号化（MAC）

  • CRYPTO_ALG_TYPE_KPP キーアグリーメントプロトコル素子（KPP）（例: ECDHやDHの実装）

  • CRYPTO_ALG_TYPE_HASH ラウドメッセージダイジェスト

  • CRYPTO_ALG_TYPE_SHASH 同期マルチブロックハッシュ

  • CRYPTO_ALG_TYPE_AHASH 非同期マルチブロックハッシュ

  • CRYPTO_ALG_TYPE_RNG 乱数生成

  • CRYPTO_ALG_TYPE_AKCIPHER 非対称暗号

  • CRYPTO_ALG_TYPE_PCOMPRESS CRYPTO_ALG_TYPE_COMPRESSの拡張版で、セグメント化された圧縮/復元を可能にします。CRYPTO_ALG_TYPE_PCOMPRESSは既存の消費者が変換されるまでCRYPTO_ALG_TYPE_COMPRESSを置き換える予定です。

マスクフラグは暗号のタイプを制限します。許可されるフラグはCRYPTO_ALG_ASYNCのみで、暗号検索関数を非同期暗号に限定します。通常、呼び出し元はマスクフラグに0を指定します。

呼び出し元がマスクとタイプを指定した場合、カーネル暗号APIが指定された暗号名に対応する実装を検索する範囲が限定されます。つまり、呼び出し元が初期化呼び出し時に存在する暗号名を使用しても、タイプとマスクフィールドの影響でカーネル暗号APIが選択しない可能性があります。

カーネル暗号APIの内部構造¶

カーネル暗号APIは、暗号実装が複数の層や間接的な構造を採用する可能性がある内部構造を持っています。このセクションでは、カーネル暗号APIがさまざまなコンポーネントをどのように活用して完全な暗号を実装するかを明確にするための説明を行います。

以下のサブセクションでは、既存の暗号実装に基づいた内部構造を説明します。最初のセクションでは最も複雑なシナリオを扱い、他のすべてのシナリオが論理的なサブセットとして形成されています。

汎用的なAEAD暗号構造¶

以下のASCIIアートは、自動生成IVを用いたAEAD暗号をカーネル暗号APIで使用する際のレイヤー構造を分解したものです。この例はIPSECレイヤーによって使用されています。

他のAEAD暗号の使用ケースにおいてもASCIIアートは適用されます。ただし、呼び出し元が別途のIVジェネレータを用いてAEAD暗号を実行しない場合があります。その場合、呼び出し元がIVを生成する必要があります。

この例では、一般的なC実装（gcm.c、aes-generic.c、ctr.c、ghash-generic.c、seqiv.c）に基づいてGCM(AES)のAEAD暗号を分解しています。汎用的な実装は、カーネル暗号APIの完全な論理を示す例として機能します。

一部の簡略化された暗号実装（例: AES-NI）では、カーネル暗号APIの観点から層に分解できない要素が統合されることがあります。AES-NIの実装では、CTRモード、GHASH実装、AES暗号がすべて1つの暗号実装としてカーネル暗号APIに登録されています。このような場合、以下のASCIIアートで説明される概念も適用されます。ただし、カーネル暗号APIによるGCMの個々のサブコンポーネントへの分解は行われません。

以下のASCIIアートの各ブロックは、カーネル暗号APIから取得した独立した暗号インスタンスです。各ブロックは呼び出し元や他のブロックが、カーネル暗号APIで定義されたAPI関数を用いてアクセスします。

以下のブロックは暗号タイプおよびその暗号で実装された特定の論理を示しています。

ASCIIアートの図は呼び出し構造も示しており、矢印は呼び出し元がどのコンポーネントを呼び出しているかを示します。矢印は呼び出し元がブロックに指定された暗号タイプに応じたAPIを用いて呼び出すブロックを指しています。

kernel crypto API                                |   IPSEC Layer
                                                 |
+-----------+                                    |
|           |            (1)
|   aead    | <-----------------------------------  esp_output
|  (seqiv)  | ---+
+-----------+    |
                 | (2)
+-----------+    |
|           | <--+                (2)
|   aead    | <-----------------------------------  esp_input
|   (gcm)   | ------------+
+-----------+             |
      | (3)               | (5)
      v                   v
+-----------+       +-----------+
|           |       |           |
|  skcipher |       |   ahash   |
|   (ctr)   | ---+  |  (ghash)  |
+-----------+    |  +-----------+
                 |
+-----------+    | (4)
|           | <--+
|   cipher  |
|   (aes)   |
+-----------+

IPSECレイヤーがesp_output関数を使用して暗号化操作をトリガーする場合、以下のコールシーケンスが適用されます。設定時に管理者がseqiv(rfc4106(gcm(aes)))をESPの暗号として使用することを設定しました。以下のASCIIアートに示されているコールシーケンスが現在適用されます。

  1. esp_output()は crypto_aead_encrypt() AEAD暗号とIVジェネレータを使用した暗号化操作をトリガーするために呼び出されます。

    SEQIVはIVを生成します。

  2. 現在、SEQIVはAEAD API関数呼び出しを使用して関連するAEAD暗号を呼び出します。この場合、SEQIVのインスタンス化時にGCMの暗号ハンドルがSEQIVに提供されるため、SEQIVはGCM暗号ハンドルを使用してAEAD暗号操作を呼び出します。

    GCMハンドルのインスタンス化時に、CTR(AES)およびGHASH暗号がインスタンス化されます。CTR(AES)およびGHASHの暗号ハンドルは後続の使用のために保持されます。

    GCM実装は、GCM仕様を実装するため、CTRモードAESおよびGHASH暗号を適切に呼び出します。

  3. GCM AEAD暗号タイプ実装は、インスタンス化されたCTR(AES)暗号ハンドルを使用してSKCIPHER APIを呼び出します。

    CTR(AES)暗号のインスタンス化時に、AESのCIPHERタイプ実装がインスタンス化されます。AESの暗号ハンドルは保持されます。

    これは、CTR(AES)のSKCIPHER実装がCTRブロックチェインモードのみを実装することを意味します。ブロックチェイン操作を実行した後、AESのCIPHER実装が呼び出されます。

  4. CTR(AES)のSKCIPHERは、AES暗号ハンドルを使用してCIPHER APIを呼び出し、1ブロックを暗号化します。

  5. GCM AEAD実装は、AHASH APIを介してGHASH暗号実装を呼び出します。

IPSECレイヤーがesp_input()関数をトリガーする場合、同じコールシーケンスが続き、違いは操作がステップ(2)から始まる点です。

汎用ブロック暗号構造¶

汎用ブロック暗号は、上記のASCIIアートに示されている概念と同じです。

例えば、CBC(AES)はcbc.cおよびaes-generic.cで実装され、上記のASCIIアートも適用されます。違いはステップ(4)のみが使用され、SKCIPHERブロックチェインモードがCBCである点です。

汎用鍵付きメッセージダイジェスト構造¶

鍵付きメッセージダイジェスト実装は、上記のASCIIアートに示されている概念と同じです。

例えば、HMAC(SHA256)はhmac.cおよびsha256_generic.cで実装されます。以下のASCIIアートが実装を示しています：

kernel crypto API            |       Caller
                             |
+-----------+         (1)    |
|           | <------------------  some_function
|   ahash   |
|   (hmac)  | ---+
+-----------+    |
                 | (2)
+-----------+    |
|           | <--+
|   shash   |
|  (sha256) |
+-----------+

呼び出し元がHMAC操作をトリガーする場合、以下のコールシーケンスが適用されます：

  1. AHASH API関数は呼び出し元によって呼び出されます。HMACの実装は必要に応じて動作を行います。

    HMAC暗号の初期化中、SHA256のSHASH暗号タイプがインスタンス化されます。SHA256インスタンスの暗号ハンドルは保持されます。

    ある時点で、HMACの実装はSHA256暗号ハンドルを使用したSHA256操作を必要とします。

  2. HMACインスタンスは現在、SHA256暗号ハンドルを使用してSHASH APIを呼び出し、メッセージダイジェストを計算します。

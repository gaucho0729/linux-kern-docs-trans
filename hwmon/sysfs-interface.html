sysfsファイルの命名規則とデータフォーマット標準¶

libsensorsライブラリは、sysfsインターフェースを通じて素データへのインターフェースを提供します。lm-sensors 3.0.0以降では、libsensorsはチップ依存性を持たない完全な実装となっています。すべてのカーネルドライバがこのドキュメントで説明する標準sysfsインターフェースを実装していると仮定しています。これにより、任意のチップのサポート追加や更新が非常に簡単になります。libsensorsおよびその利用アプリケーションは変更不要です。これはlm-sensors 2と比較して大きな改善点です。

マザーボードのセンサチップへの接続方法は多様であり、標準がありません。たとえば、2番目の温度センサがCPUに接続されているか、2番目のファンがCPUに設置されているかといった保証はありません。また、チップが報告する一部の値は、意味を成すまでに計算が必要です。たとえば、ほとんどのチップは0〜+4Vの電圧しか測定できません。他の電圧は外部抵抗を用いてこの範囲にスケーリングされます。これらの抵抗値はマザーボードによって異なり、ドライバ内にハードコードすることはできません。したがって、変換はユーザー空間で行う必要があります。

このため、チップ依存性を持たないlibsensorsであっても、適切な値の変換や入力のラベリング、未使用入力の非表示を行うための設定ファイル（例: /etc/sensors.conf）が必要です。

一部のアプリケーションはsysfsファイルを直接アクセスする方法を使用します。このドキュメントでは、ドライバが従う標準を簡潔に説明しており、アプリケーションがエントリをスキャンし、データを簡単かつ一貫してアクセスできるようにしています。ただし、このようなアプリケーションは依然として変換、ラベリング、未使用入力の非表示の実装が必要であり、そのためlibrairyをバイパスすることは推奨されません。

各チップはsysfs /sys/devicesツリー内の独自のディレクトリを持ちます。センサチップをすべて見つけるには、以下のデバイスシンボリックリンクから追随する方が簡単です /sys/class/hwmon/hwmon*.

lm-sensors 3.0.0以前では、libsensorsは「physical」デバイスディレクトリ内のハードウェアモニタリング属性を検索していました。lm-sensors 3.0.1以降では、hwmon「class」デバイスディレクトリ内の属性もサポートされています。複雑なドライバ（例: 多機能チップのドライバ）は、名前空間の汚染を避けるためにこの機能を使用したいかもしれません。ただし、古いバージョンのlibsensorsはこのドライバをサポートしなくなるというデメリットがあります。

すべてのsysfs値は固定小数点数です。

1つのファイルに1つの値しか含まれません。これは古い/proc仕様とは異なります。ファイルの一般的な命名規則は：<type><number>_<item>です。センサーチップの一般的なtypeは、「in」（電圧）、「temp」（温度）、「fan」（ファン）です。一般的なitemは、「input」（測定値）、「max」（上限閾値）、「min」（下限閾値）です。番号は通常1から始まりますが、電圧は0から始まります（ほとんどのデータシートがこの方式を採用するため）。複数回出現する可能性のある要素には常に番号が使用され、特定のチップに1つの要素しかない場合でも同様です。他のファイルは特定の要素を参照しないので、単純な名前でなく数字を含みません。

アラームはチップから直接読み取った指示です。ドライバは読み取り値を閾値と比較しません。これにより、読み取り値の違反を検出・アラームを発生させることができます。アラームの正確な定義（例えば、閾値を満たすか超えるかによってアラームが発生するか）はチップに依存します。

hwmon sysfs属性の値を設定する際には、望む値の文字列表現を記述する必要があります。注意：数値でない文字列は0とみなされます！ 記述された文字列がどのように解釈されるかについては、このファイル末尾の「sysfs属性書き込み解釈」セクションを参照してください。

[0-*]

0から始まる任意の正数を表します

[1-*]

1から始まる任意の正数を表します

RO

読み取り専用値

WO

書き込み専用値

RW

読み取り/書き込み値

読み取り/書き込み可能な値は、ハードウェア実装に応じて一部のチップでは読み取り専用となることがあります。

すべての項目（名前を除く）はオプションであり、チップがその機能をサポートしている場合にのみドライバで作成する必要があります。

PWM¶

pwm[1-*]

パルス幅変調ファン制御。

0から255までの整数値

RW

255は最大値または100%を表します。

pwm[1-*]_enable

ファン速度制御方法:

  • 0: ファン速度制御なし（つまりファンはフルスピードで動作）

  • 1: 手動ファン速度制御が有効（ pwm[1-*])

  • 2+: 自動ファン速度制御が有効

自動モードの詳細については、個々のチップドキュメンテーションファイルを確認してください。

RW

pwm[1-*]_mode

  • 0: 直流モード（直流）

  • 1: PWMモード（パルス幅変調）

RW

ベースPWM周波数（Hz）。

pwmN_modeがPWMの場合にのみ可能ですが、常に存在するとは限りません。

RW

pwm[1-*]_auto_channels_temp

自動モードでこのPWM出力に影響を与える温度チャンネルを選択します。

ビットフィールド、1はtemp1、2はtemp2、4はtemp3など… 使用するチップによって可能値が異なります。

RW

pwm[1-*]_auto_point[1-*]_pwm / pwm[1-*]_auto_point[1-*]_temp / pwm[1-*]_auto_point[1-*]_temp_hyst

PWMと温度の曲線を定義します。

トリップポイントの数はチップに依存します。トリップポイントをPWM出力チャンネルに関連付けるチップにはこの機能を使用してください。

RW

temp[1-*]_auto_point[1-*]_pwm / temp[1-*]_auto_point[1-*]_temp / temp[1-*]_auto_point[1-*]_temp_hyst

PWMと温度の曲線を定義します。

トリップポイントの数はチップに依存します。温度チャネルにトリップポイントを関連付けるチップに対して使用してください。

RW

PWM出力チャネルと温度チャネルの両方にトリップポイントが関連付けられる第三のケースがあります。この場合、PWM値はPWM出力チャネルに関連付けられ、温度値は温度チャネルに関連付けられます。その際、温度入力とPWM出力のマッピングによって結果が決まります。複数の温度入力が1つのPWM出力にマッピングされている場合、複数の候補となるPWM値が生じます。実際の結果はチップに依存しますが、一般的には最も高い候補値（ファンの最大速度）が優先されます。

アラーム¶

各チャネルまたは限界値には、ブール値を含むアラームファイルが関連付けられている場合があります。1はアラーム条件が存在することを、0はアラームがないことを表します。

一般的に、あるチップはチャネル関連のアラームか、限界値関連のアラームのいずれか一方のみを使用します。ドライバーはハードウェアの実装を反映するだけでよいです。

`in[0-*]_alarm`, `curr[1-*]_alarm`, `power[1-*]_alarm`, `fan[1-*]_alarm`, `temp[1-*]_alarm`

チャネルアラーム

  • 0: アラームなし

  • 1: アラーム

RO

または

`in[0-*]_min_alarm`, `in[0-*]_max_alarm`, `in[0-*]_lcrit_alarm`, `in[0-*]_crit_alarm`, `curr[1-*]_min_alarm`, `curr[1-*]_max_alarm`, `curr[1-*]_lcrit_alarm`, `curr[1-*]_crit_alarm`, `power[1-*]_cap_alarm`, `power[1-*]_max_alarm`, `power[1-*]_crit_alarm`, `fan[1-*]_min_alarm`, `fan[1-*]_max_alarm`, `temp[1-*]_min_alarm`, `temp[1-*]_max_alarm`, `temp[1-*]_lcrit_alarm`, `temp[1-*]_crit_alarm`, `temp[1-*]_emergency_alarm`

リミットアラーム

  • 0: アラームなし

  • 1: アラーム

RO

各入力チャネルには関連するエラー情報ファイルが存在する場合があります。これはハードウェアがサポートする場合、オープンダイオードや接続されていないファンなどの通知に利用できます。このブール値が1の場合は、そのチャネルの測定値は信頼できません。

  • 0: 故障が発生していません

  • 1: 故障条件

RO

一部のチップでは、アラームが発生した際にビープ音を鳴らす機能があります:

マスタービープ音の有効化

  • 0: ビープ音なし

  • 1: ビープ音あり

in[0-*]_beep, curr[1-*]_beep, fan[1-*]_beep, temp[1-*]_beep,

チャンネルビープ

  • 0: 無効

  • 1: 有効

RW

理論上、チップは各限界ごとのビープ音マスクを提供できますが、これまでにそのようなチップは確認されていません。

古いドライバーでは、アラームおよびビープ音に対して非標準のインターフェースを提供していました。これらのインターフェースファイルは非推奨ですが、互換性のためには残されます:

alarms

アラーム ビットマスク。

RO

1〜4バイトの整数表現。

「1」ビットはアラームを示します。

チップは「コンパレータ」モードでプログラミングされるべきです。アラームがまだ有効な場合、レジスタを読み取るとアラームが「戻る」ようになります。

一般的にチップの内部アラームレジスタの直接的な表現です。個々のビットの位置には標準がありません。このため、新しいドライバーでこのインターフェースファイルを使用することを推奨しません。代わりに individual *_alarm および *_fault ファイルを使用してください。ビットはkernel/include/sensors.hで定義されています。

beep_mask

ビープ音のビットマスク。'alarms'と同じ形式で、同じビット位置を使用します。同様の理由で使用を推奨しません。代わりに *_beep ファイルを使用してください。RW

sysfs属性の書き込み解釈¶

sysfs属性は常に数字を含むため、最初にユーザー入力を数字に変換する必要があります。数値が負の値を許可するかどうかによって2つの方法があります。

unsigned long u = simple_strtoul(buf, NULL, 10);
long s = simple_strtol(buf, NULL, 10);

bufがカーネルによって渡されるユーザー入力バッファです。strto[u]lの第2引数を使用しないことで、0が返された場合にそれが本当に0か、または無効な入力によるものかを判断できません。これはカーネル全体にわたるチェックを追加する必要があるため、意図的にこのようにしています。

変換後の値をunsigned longまたはlongに常に保存する必要があります。これにより、その後のチェック前の巻き戻しを防げます。

入力文字列が(unsigned) longに変換された後、値が許容範囲内であるかを確認する必要があります。有効性を確認する前に値をさらに変換すると、巻き戻しが発生する可能性があります。たとえば、結果を乗算しないでください。加算/減算を行う場合は、それ以前に除算を行った後に行う必要があります。

無効な値が検出された場合、sysfs属性の種類によって処理が異なります。連続的な設定（例: tempX_maxやinX_max属性）の場合、clamp_val(value, min_limit, max_limit)を使用して値を制限します。連続的な設定でない場合（例: tempX_type）、無効な値が書き込まれた場合は-EINVALを返します。

例1: temp1_max、レジスタは符号付き8ビット値（-128〜127度）です。

long v = simple_strtol(buf, NULL, 10) / 1000;
v = clamp_val(v, -128, 127);
/* write v to register */

例2: ファンディバイダー設定、有効な値は2、4、8です。

unsigned long v = simple_strtoul(buf, NULL, 10);

switch (v) {
case 2: v = 1; break;
case 4: v = 2; break;
case 8: v = 3; break;
default:
        return -EINVAL;
}
/* write v to register */

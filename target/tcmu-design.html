TCM ユーザースペース設計¶

設計¶

TCM は LIO（カーネル内 iSCSI ターゲット（サーバー））の別名であり、既存の TCM ターゲットはカーネル内に実行されています。TCMU（TCM のユーザー空間実装）は、iSCSI ターゲットとして動作するユーザー空間のプログラムを書くことを可能にします。このドキュメントでは設計について説明します。

既存のカーネルは、さまざまな SCSI トランスポートプロトコル用のモジュールを提供しています。TCM はデータストレージもモジュール化しており、ファイル、ブロックデバイス、RAM、または他の SCSI デバイスをストレージとして使用するモジュールが既に存在します。これらは「バックストア（backstores）」または「ストレージエンジン（storage engines）」と呼ばれます。これらの組み込みモジュールはすべてカーネルコードで実装されています。

背景¶

SCSI コマンドを運ぶためのトランスポートプロトコル（「ファブリック（fabrics）」）だけでなく、Linux カーネルのターゲットである LIO は、実際にデータストレージもモジュール化しています。これらは「バックストア（backstores）」または「ストレージエンジン（storage engines）」と呼ばれます。ターゲットは、エクスポートされる SCSI LUN に必要なローカルストレージとしてファイル、ブロックデバイス、RAM、または他の SCSI デバイスを用いるためのバックストアを提供します。LIO の他の部分同様、これらはすべてカーネルコードで実装されています。

これらのバックストアは一般的な用途をカバーしていますが、すべてではありません。他の非カーネルターゲットソリューション（たとえば tgt）がサポートできる新しい用途の一つは、Gluster の GLFS や Ceph の RBD をバックストアとして使用することです。このターゲットは、これらの非伝統的なネットワークストレージシステムにデータを保存させながら、標準プロトコルのみを使用するように、イニシエーターに翻訳者として機能します。

ターゲットがユーザー空間プロセスである場合、サポートは比較的簡単です。たとえば tgt は、それぞれに対して小さなアダプターモジュールのみが必要で、モジュールは RBD と GLFS の利用可能なユーザー空間ライブラリを使用するだけで済みます。

LIO でこれらのバックストアをサポートするには considerably 困難です。なぜなら LIO はすべてカーネルコードで実装されているからです。GLFS や RBD の API とプロトコルをカーネルに移植するための大幅な作業を実施する代わりに、LIO 用のユーザー空間透過バックストア「TCMU」を作成するという別のアプローチが採用されます。

Benefits¶

RBD と GLFS のサポートを比較的容易にするだけでなく、TCMU は新しいバックストアの開発も容易にします。TCMU は LIO ループバックファブリックと組み合わせることで、ファイルシステム層ではなく SCSI 層で動作する FUSE（Filesystem in Userspace）に似たものです。いわば SUSE（SUSE は Linux ディストリビューションの一つ）のようなものです。

デメリットは、設定する必要のある異なるコンポーネントがより多く、故障する可能性があることです。これは避けられませんが、可能な限りシンプルにすることで致命的な問題にはならないことを願っています。

Design constraints¶

  • 高性能: 高スループット、低レイテンシー

  • ユーザー空間が以下の場合も適切に処理:

    1. アタッチしない

    2. ハングする

    3. 終了する

    4. 不適切な動作をする

  • 今後のユーザー空間とカーネルの実装における柔軟性を確保

  • 合理的なメモリ効率を確保

  • 設定および実行が簡単

  • ユーザー空間のバックエンドを書くのが簡単

実装概要¶

TCMUインターフェースのコアは、カーネルとユーザー空間が共有するメモリ領域です。この領域には、制御領域（メモブックス）、ロックフリーなプロダクション/コンシューマー環状バッファ（コマンドを上位に渡すためのもの、およびステータスを返すためのもの）、および入出力データバッファ領域が含まれます。

TCMUは事前に存在するUIOサブシステムを使用しています。UIOはユーザー空間でのデバイスドライバ開発を可能にし、これはTCMUの使用ケースと概念的に非常に近いです。ただし、物理デバイスではなく、SCSIコマンド用に設計されたメモリマップレイアウトを実装しています。UIOを使用することにより、TCMUはデバイスの自己認識（例: ユーザー空間が共有領域のサイズを確認する方法）や両方向のシグナル処理を処理できます。

メモリ領域には埋め込まれたポインタがありません。すべての情報は、領域の開始アドレスからのオフセットとして表現されます。これにより、ユーザープロセスが終了して再起動され、領域が異なる仮想アドレスにマッピングされた場合でも環状バッファが動作します。

構造体の定義についてはtarget_core_user.hを参照してください。

メモブックス¶

メモブックスは常に共有メモリ領域の開始位置にあり、バージョン、コマンドリングの開始オフセットとサイズの詳細、およびカーネルとユーザー空間が環状バッファにコマンドを置く際やコマンドが完了したことを示すためのヘッドとテールポインタが含まれます。

バージョン - 1（他の場合にユーザー空間は中止する必要があります）

フラグ:
  • TCMU_MAILBOX_FLAG_CAP_OOOC:

    アウトオブオーダー完了がサポートされていることを示します。詳細は「コマンドリング」を参照してください。

cmdr_off

メモリ領域の開始位置からのコマンドリングの開始オフセット（メモブックスのサイズを考慮して）

cmdr_size

コマンドリングのサイズ。これは ではありません 2の累乗である必要はありません。

cmd_head

カーネルがコマンドがリングに置かれたことを示すために更新されます。

cmd_tail

ユーザー空間がコマンドの処理を完了したことを示すために更新されます。

コマンドリング¶

カーネルがコマンドリングにコマンドを置く際には、mailbox.cmd_headをコマンドのサイズ分インクリメントし、cmdr_sizeをモジュロで計算した後、ユーザー空間にシグナルを送信して通知します。 uio_event_notify()コマンドが完了した後、ユーザースペースはmailbox.cmd_tailを同じように更新し、4バイトのwrite()を介してカーネルに信号を送ります。cmd_headがcmd_tailと等しい場合、リングは空になっており、ユーザースペースが処理待ちしているコマンドはありません。

TCMUコマンドは8バイトアライメントされています。これらは共通ヘッダで始まり、"len_op"という32ビットの値が長さを格納し、最低未使用ビットにオペコードが含まれます。また、cmd_idとフラグフィールドが含まれており、これらはカーネル(kflags)とユーザースペース(uflags)から設定されます。

現在はTCMU_OP_CMDとTCMU_OP_PADの2つのオペコードのみが定義されています。

オペコードがCMDの場合、コマンドリング内のエントリはstruct tcmu_cmd_entryです。ユーザースペースはtcmu_cmd_entry.req.cdb_offを通じてSCSI CDB(コマンドデータブロック)を取得します。cdb_offは全体の共有メモリ領域の開始位置からのオフセットであり、エントリそのものではなく、データの入出力バッファはtht req.iov[]配列を通じてアクセス可能です。iov_cntは、データインまたはデータアウトバッファを記述するために必要なiov[]内のエントリ数を示します。双方向コマンドの場合、iov_cntはデータアウト領域をカバーするiovecエントリ数を指定し、iov_bidi_cntはその直後にデータイン領域をカバーするiovecエントリ数を示します。他のフィールドと同様に、iov.iov_baseは領域の開始位置からのオフセットです。

コマンドを完了する際、ユーザースペースはrsp.scsi_statusを設定し、必要に応じてrsp.sense_bufferも設定します。その後、mailbox.cmd_tailをentry.hdr.length（cmdr_sizeをモジュロにした値）でインクリメントし、UIOメソッドを介してカーネルに信号を送ります。これはファイルディスクリプタへの4バイトのwrite()です。

mailbox->flagsにTCMU_MAILBOX_FLAG_CAP_OOOCが設定されている場合、カーネルは順序を問わない完了処理をサポートしています。この場合、ユーザースペースは元の順序とは異なる順序でコマンドを処理できます。ただし、カーネルはコマンドリング内で出現した順序でコマンドを処理するため、ユーザースペースはコマンドを完了する際にcmd->idを更新する必要があります（元のコマンドのエントリを「盗む」ことになります）。

オペコードがPADの場合、ユーザースペースは上記のようにcmd_tailのみを更新します（ノーオペレーションです）。（カーネルはPADエントリを挿入して、コマンドリング内で各CMDエントリが連続していることを保証します。）

今後、さらに多くのオペコードが追加される可能性があります。ユーザースペースが処理できないオペコードに遭遇した場合、UNKNOWN_OPビット（bit 0）をhdr.uflagsに設定し、cmd_tailを更新した後、追加のコマンドを処理する必要があります。

データ領域¶

これはコマンドリングの後に続く共有メモリ領域です。この領域の構造はTCMUインターフェースで定義されていません。ユーザースペースは、保留中のiovによって参照される部分のみにアクセスする必要があります。

デバイスの検出¶

他のデバイスもTCMU以外でUIOを使用している可能性があります。関係のないユーザープロセスも、異なるセットのTCMUデバイスを処理しているかもしれません。TCMUユーザースペースプロセスは、sysfs class/uio/uio*/nameをスキャンしてデバイスを検出する必要があります。TCMUデバイスの場合は、これらの名前は次の形式になります：

tcm-user/<hba_num>/<device_name>/<subtype>/<path>

ここで「tcm-user」はすべてのTCMUバックエンドUIOデバイスで共通です。<hba_num>と<device_name>は、ユーザースペースがカーネルターゲットのconfigfsツリー内のデバイスのパスを特定するのに役立ちます。通常のマウントポイントを仮定すると、次の場所にあります：

/sys/kernel/config/target/core/user_<hba_num>/<device_name>

この場所には「hw_block_size」などの属性が含まれており、これらを正しく動作させるためにユーザースペースが知る必要があります。

<subtype>はユーザープロセス固有の文字列で、TCMUデバイスが特定のハンドラによってバックエンドされるものであることを識別します。<path>はユーザープロセスがデバイスを構成するためにハンドラ固有の文字列です。名前には':'を含んではいけません（LIOの制限のため）。

すべての検出されたデバイスに対して、ユーザーハンドラは/dev/uioXを開き、mmap()を呼び出します：

mmap(NULL, size, PROT_READ|PROT_WRITE, MAP_SHARED, fd, 0)

sizeは/sys/class/uio/uioX/maps/map0/sizeから読み取った値と等しくなければなりません。

デバイスイベント¶

新しいデバイスが追加されたり、削除されたりした場合、netlink経由で通知が送信されます。ジェネリックなnetlinkファミリ名は「TCM-USER」、マルチキャストグループ名は「config」です。これには前記のセクションで説明したUIO名とUIOマイナーデバイス番号が含まれます。これにより、ユーザースペースはUIOデバイスとLIOデバイスの両方を特定できるようになり、 subtypeに基づいてデバイスがサポートされていると判断した後、適切なアクションを取ることができます。

その他の緊急事態¶

ユーザースペースハンドラープロセスがアタッチしない場合：

  • TCMUはコマンドをポストし、タイムアウト期間（30秒）後にそれらを中止します。

ユーザースペースハンドラープロセスがキルされた場合：

  • TCMUデバイスへの再接続と再起動は可能です。コマンドリングは保持されます。ただし、タイムアウト期間が経過した後、カーネルは保留中のタスクを中止します。

ユーザースペースハンドラープロセスがハングした場合：

  • タイムアウト期間が経過した後、カーネルは保留中のタスクを中止します。

ユーザースペースハンドラープロセスがマルウェアである場合：

  • プロセスは制御しているデバイスのハンドリングを簡単に破損させることができます。ただし、共有メモリ領域以外のカーネルメモリにアクセスすることはできません。

ユーザーパススルーハンドラの作成（例コード付き）¶

TCMUデバイスをハンドリングするユーザープロセスは以下の機能をサポートしなければなりません：

  1. TCMU uioデバイスの検出と設定

  2. デバイス（複数可）でのイベントを待機中

  3. コマンドリングの管理：操作とコマンドの解析、必要な作業の実行、応答フィールド（scsi_statusおよびsense_bufferを含む）の設定、cmd_tailの更新、作業完了をカーネルに通知

代わりにtcmu-runner用のプラグインを書くことを検討してください。tcmu-runnerはすべての機能を実装しており、プラグイン開発者向けにより高レベルのAPIを提供しています

TCMUは、複数の関係のないプロセスがTCMUデバイスを個別に管理できるように設計されています。すべてのハンドラは、既知のサブタイプ文字列に基づいてのみ自身のデバイスを開くようにする必要があります

  1. TCMU UIOデバイスの発見と設定:

    /* error checking omitted for brevity */

int fd, dev_fd;
char buf[256];
unsigned long long map_len;
void *map;

fd = open("/sys/class/uio/uio0/name", O_RDONLY);
ret = read(fd, buf, sizeof(buf));
close(fd);
buf[ret-1] = '\0'; /* null-terminate and chop off the \n */

/* we only want uio devices whose name is a format we expect */
if (strncmp(buf, "tcm-user", 8))
  exit(-1);

/* Further checking for subtype also needed here */

fd = open(/sys/class/uio/%s/maps/map0/size, O_RDONLY);
ret = read(fd, buf, sizeof(buf));
close(fd);
str_buf[ret-1] = '\0'; /* null-terminate and chop off the \n */

map_len = strtoull(buf, NULL, 0);

dev_fd = open("/dev/uio0", O_RDWR);
map = mmap(NULL, map_len, PROT_READ|PROT_WRITE, MAP_SHARED, dev_fd, 0);


b) Waiting for events on the device(s)

while (1) {
  char buf[4];

  int ret = read(dev_fd, buf, 4); /* will block */

  handle_device_events(dev_fd, map);
}

  1. コマンドリングの管理:

    #include <linux/target_core_user.h>

int handle_device_events(int fd, void *map)
{
  struct tcmu_mailbox *mb = map;
  struct tcmu_cmd_entry *ent = (void *) mb + mb->cmdr_off + mb->cmd_tail;
  int did_some_work = 0;

  /* Process events from cmd ring until we catch up with cmd_head */
  while (ent != (void *)mb + mb->cmdr_off + mb->cmd_head) {

    if (tcmu_hdr_get_op(ent->hdr.len_op) == TCMU_OP_CMD) {
      uint8_t *cdb = (void *)mb + ent->req.cdb_off;
      bool success = true;

      /* Handle command here. */
      printf("SCSI opcode: 0x%x\n", cdb[0]);

      /* Set response fields */
      if (success)
        ent->rsp.scsi_status = SCSI_NO_SENSE;
      else {
        /* Also fill in rsp->sense_buffer here */
        ent->rsp.scsi_status = SCSI_CHECK_CONDITION;
      }
    }
    else if (tcmu_hdr_get_op(ent->hdr.len_op) != TCMU_OP_PAD) {
      /* Tell the kernel we didn't handle unknown opcodes */
      ent->hdr.uflags |= TCMU_UFLAG_UNKNOWN_OP;
    }
    else {
      /* Do nothing for PAD entries except update cmd_tail */
    }

    /* update cmd_tail */
    mb->cmd_tail = (mb->cmd_tail + tcmu_hdr_get_len(&ent->hdr)) % mb->cmdr_size;
    ent = (void *) mb + mb->cmdr_off + mb->cmd_tail;
    did_some_work = 1;
  }

  /* Notify the kernel that work has been finished */
  if (did_some_work) {
    uint32_t buf = 0;

    write(fd, &buf, 4);
  }

  return 0;
}

最後に¶

SCSI仕様で定義された戻りコードを正しく返すように注意してください。これらはscsi/scsi.hインクルードファイルで定義された値とは異なります。たとえば、CHECK CONDITIONのステータスコードは2であり、1ではありません

このドキュメントはrtmutex.cの実装設計について説明を試みています。rtmutex.cが存在する理由については説明していません。その点については PIサポート付きRTミューテックスサブシステム。このドキュメントはこのコードがない場合に発生する問題を説明していますが、コードが実際に何をしているかを理解するための概念として説明しています。

このドキュメントの目的は、優先度継承（PI）アルゴリズムの仕組みや、PIをこのように実装した理由について理解を助けることです。

無限優先度逆転¶

優先度逆転とは、低優先度のプロセスが実行されている間に高優先度のプロセスが実行を待っている状態を指します。これはいくつかの理由で発生しますが、ほとんどの場合回避できません。高優先度のプロセスが低優先度のプロセスが所有しているリソース（例えばミューテックス）を使用したい場合、高優先度のプロセスは低優先度のプロセスがリソースを解放するまで待つ必要があります。これは優先度逆転です。防ぎたいのは「無限優先度逆転」と呼ばれる状態で、高優先度のプロセスが低優先度のプロセスによって不定期に実行を妨げられる状態です。

無限優先度逆転の典型的な例は、3つのプロセス（A、B、C）がある場合です。Aは最高優先度、Cは最低優先度、Bはその間の優先度です。AがCが所有するロックを取得しようとすると、Cがロックを解放するまで待つ必要があります。その間、Bが実行され、Bの優先度がCより高いのでCを中断しますが、実際にはAというより高い優先度のプロセスを中断しています。Aがロックを解放するまでどれだけ待つのかは予測できません。なぜなら、BがCPUを大量に消費している可能性があり、Cがロックを解放する機会を与えてくれないからです。このような状態を無限優先度逆転と呼びます。

問題を示すためのASCIIアートを以下に示します：

   grab lock L1 (owned by C)
     |
A ---+
        C preempted by B
          |
C    +----+

B         +-------->
                B now keeps A from running.

優先度継承（PI）¶

この問題を解決する方法はいくつかありますが、他の方法についてはこのドキュメントの範囲外です。ここではPIのみを説明します。

PIとは、他のプロセスが現在のプロセスが所有するロックにブロックしている場合、そのプロセスが他のプロセスの優先度を継承する仕組みです。この説明をより理解しやすくするために、以前の例に戻ります。

今回は、AがCが所有するロックをブロックしている場合、CはAの優先度を継承します。そのため、Bが実行可能になったとしても、Cは現在Aの高い優先度を保っているため、Cを優先して実行しません。Cがロックを解放した瞬間、継承した優先度を失い、その後AはCが保持していたリソースを再び利用できます。

用語¶

このドキュメントでは、設計を説明するために使用される用語について説明します。

PI chain

  • PI chainは、プロセスが前のプロセスのロックにブロックされている際に優先度を継承するロックとプロセスの順序付きシリーズです。このドキュメントの後述でより詳しく説明します。

mutex

  • このドキュメントでは、PIを実装するロックとPIコードで使用されるスピンロックを区別するために、以降PIロックはmutexと呼びます。

lock

  • このドキュメントでは、PIアルゴリズムを保護するために使用されるスピンロックを指す際には「lock」という用語を使用します。これらのロックはUP（CONFIG_PREEMPTが有効の場合）でプリエマプションを無効にし、SMPでは複数のCPUが同時にクリティカルセクションに入らないようにします。

スピンロック

  • 上記のlockと同じです。

待機中のプロセス

  • waiterは、ブロックされているプロセスのスタック上に保存される構造体です。waiterのスコープはミューテックスにブロックされているプロセスのコード内に限定されているため、プロセスのスタック（ローカル変数）にwaiterを割り当てても問題ありません。この構造体はタスクへのポインタと、タスクがブロックされているミューテックスを保持しており、さらにrbtreeノード構造体を含み、ミューテックスのwaiters rbtreeおよびミューテックス所有タスクのpi_waiters rbtreeにタスクを配置します（以下で説明します）。

    waiterは、ミューテックスを待っているタスクを指す場合もあります。これはwaiter->taskと同じです。

待機者

  • ミューテックスにブロックされているプロセスの一覧です。

top waiter

  • 特定のミューテックスに待機している最高優先度のプロセスです。

top pi waiter

  • 特定のプロセスが所有するミューテックスのうちの1つに待機している最高優先度のプロセスです。

注意:

このドキュメントでは、記述している2つのプロセスを区別するためにtaskとprocessを使い分けます。

PI chain¶

PI chainは、優先度継承が発生する可能性のあるプロセスとミューテックスのリストです。複数のチェーンが合流することもありますが、チェーンは一度分岐しません。なぜなら、プロセスが一度に複数のミューテックスにブロックされることがないからです。

例:

Process:  A, B, C, D, E
Mutexes:  L1, L2, L3, L4

A owns: L1
        B blocked on L1
        B owns L2
               C blocked on L2
               C owns L3
                      D blocked on L3
                      D owns L4
                             E blocked on L4

チェーンは以下のようになります：

E->L4->D->L3->C->L2->B->L1->A

2つのチェーンが合流する場所を示すために、別のプロセスFと別のミューテックスL5を追加します。BがL5を所有し、FがL5にブロックされているとします。

Fのチェーンは以下のようになります：

F->L5->B->L1->A

プロセスが複数のミューテックスを所有する可能性があるが、一度にブロックされるのは1つだけであるため、チェーンは統合されます。

ここでは両方のチェーンを示します:

E->L4->D->L3->C->L2-+
                    |
                    +->B->L1->A
                    |
              F->L5-+

PIが機能するためには、これらのチェーンの右端にあるプロセス（あるいはこれを「チェーンの先頭」と呼ぶこともできます）の優先度が、チェーンの左または下にあるプロセスの優先度以上でなければなりません。

また、ミューテックスが複数のプロセスにブロックされる可能性があるため、ミューテックスで複数のチェーンが統合されることがあります。新たにプロセスGがミューテックスL2にブロックされる場合:

G->L2->B->L1->A

そして再び、チェーンがどのように成長するかを示すために、マージされたチェーンを示します:

E->L4->D->L3->C-+
                +->L2-+
                |     |
              G-+     +->B->L1->A
                      |
                F->L5-+

プロセスGがチェーン内で最高の優先度を持つ場合、チェーン上にあるすべてのタスク（この例ではAとB）の優先度をGの優先度に引き上げる必要があります。

ミューテックス・ウェイターツリー¶

すべてのミューテックスは、自身にブロックされているウェイターを追跡します。ミューテックスは、優先度でウェイターツリーを保持するためのrbtreeを持ち、このツリーはミューテックス構造体内のスピンロックで保護されます。このロックはwait_lockと呼ばれます。

タスクPIツリー¶

PIチェーンを追跡するため、各プロセスは独自のPI rbtreeを持ちます。これは、プロセスが所有するミューテックスのすべてのトップウェイターのツリーです。注意点として、このツリーはすべてのブロックされているウェイターではなく、プロセスが所有するミューテックスにブロックされているトップウェイターのみを保持します。

タスクのPIツリーの先頭は、タスクが所有するミューテックスに待機している最高優先度のタスクです。タスクが継承した優先度を持つ場合でも、このツリーの先頭は常にそのタスクの優先度になります。

このツリーは、プロセスのタスク構造体内でpi_waitersというrbtreeとして保存され、タスク構造体内のスピンロックpi_lockで保護されます。このロックは割り込みコンテキストでも取得可能なので、pi_lockをロックする際は割り込みを無効化する必要があります。

PIチェーンの深さ¶

PIチェーンの最大深さは動的ではなく、実際には定義可能です。しかし、すべてのミューテックスのネスト構造に依存するため、非常に複雑です。3つのミューテックスL1、L2、L3と4つの関数func1、func2、func3、func4を持つ例を見てみましょう。以下の例ではL1→L2→L3のロック順序が示されていますが、実際に直接ネストされているとは限りません:

void func1(void)
{
      mutex_lock(L1);

      /* do anything */

      mutex_unlock(L1);
}

void func2(void)
{
      mutex_lock(L1);
      mutex_lock(L2);

      /* do something */

      mutex_unlock(L2);
      mutex_unlock(L1);
}

void func3(void)
{
      mutex_lock(L2);
      mutex_lock(L3);

      /* do something else */

      mutex_unlock(L3);
      mutex_unlock(L2);
}

void func4(void)
{
      mutex_lock(L3);

      /* do something again */

      mutex_unlock(L3);
}

次に、これらの関数をそれぞれ実行する4つのプロセスA、B、C、Dを追加します。Dが最初に実行され、Aが最後に実行され、Dがfunc4の「do something again」領域でプリエンプションされる場合、以下のロック順序になります:

D owns L3
       C blocked on L3
       C owns L2
              B blocked on L2
              B owns L1
                     A blocked on L1

And thus we have the chain A->L1->B->L2->C->L3->D.

これによりPI深度が4（4つのプロセス）になりますが、個々の関数を確認すると、最大でロック深度が2にしかなさそうに見えます。したがって、ロック深度はコンパイル時に定義されていますが、その深度の可能性を見つけるのは依然として非常に困難です。

mutexはユーザー領域のアプリケーションによって定義されるため、DOS型のアプリケーションが大量のmutexをネストしてPIチェーンを長くし、大量のデータを確認しながらスピンロックを保持するのを防ぎたいです。そのため、実装では最大ロック深度だけでなく、PIチェーンを歩く際には一度に最大2つの異なるロックのみを保持するようにしています。以下で詳しく説明します。

ミューテックス所有者とフラグ¶

ミューテックス構造体にはミューテックスの所有者へのポインタが含まれています。ミューテックスが所有されていない場合、所有者はNULLに設定されます。すべてのアーキテクチャでタスク構造体が少なくとも2バイトアライメント（この条件が満たされない場合、rtmutex.cコードは破損します）を確保しているため、最下位ビットをフラグとして使用できます。ビット0は「待機中のプロセスがある」フラグとして使用され、ミューテックスに待機中のプロセスがあるときに設定されます。

参照 PIサポート付きRTミューテックスサブシステム を参照してください。

cmpxchgのトリック¶

一部のアーキテクチャではアトミックなcmpxchg（Compare and Exchange）が実装されています。この機能は、必要に応じてミューテックスの取得と解放の高速パスを短くするために使用されます。

cmpxchgは基本的に以下の関数をアトミックに実行します：

unsigned long _cmpxchg(unsigned long *A, unsigned long *B, unsigned long *C)
{
      unsigned long T = *A;
      if (*A == *B) {
              *A = *C;
      }
      return T;
}
#define cmpxchg(a,b,c) _cmpxchg(&a,&b,&c)

これは非常に便利です。変数を更新する際、変数が予期する値である場合にのみ更新できるため、返値（Aの古い値）がBと等しいかどうかで成功を確認できます。

rt_mutex_cmpxchgマクロはミューテックスのロックとアンロックを試みるために使用されます。アーキテクチャがCMPXCHGをサポートしない場合、このマクロは常に失敗します。CMPXCHGをサポートする場合、高速パスを短くするのに非常に役立ちます。

rt_mutex_cmpxchgマクロは、所有者のフラグフィールドと組み合わせて使用され、CMPXCHGをサポートするアーキテクチャ向けにシステムを最適化します。この点については後述します。

優先度調整¶

rtmutex.cにおけるPIコードの実装では、プロセスが優先度を調整する必要がある場所がいくつかあります。プロセスのpi_waitersを活用することで、調整が必要な項目を簡単に把握できます。

タスク調整を実装する関数はrt_mutex_adjust_prioとrt_mutex_setprioです。rt_mutex_setprioはrt_mutex_adjust_prio内でのみ使用されます。

rt_mutex_adjust_prioはタスクの優先度と、タスクが所有するミューテックスのいずれかに待機している最高優先度のプロセスを検査します。タスクのpi_waitersは、タスクが所有するすべてのミューテックスのトップウェイターを優先度順に保持しているため、タスクの通常/デッドライン優先度とトップpiウェイターを比較し、高い方を採用するだけで十分です。その後、rt_mutex_setprioが呼び出され、タスクの優先度が新しい優先度に調整されます。注意点として、rt_mutex_setprioはkernel/sched/core.cで定義されており、実際の優先度変更を実装しています。

注意:

task_structの「prio」フィールドでは、数字が小さいほど優先度が高いです。「prio」が5のタスクは、「prio」が10のタスクよりも高い優先度を持ちます。

rt_mutex_adjust_prioはタスクの優先度を上げたり下げたりする可能性があります。タスクが所有するミューテックスに高い優先度のプロセスが新たにブロックした場合、この関数はタスクの優先度を上げます。しかし、高い優先度のタスクが何らかの理由でミューテックスを離れた場合（タイムアウトやシグナル）、この関数はタスクの優先度を下げます。これはpi_waitersが常にタスクが所有するミューテックスに待機している最高優先度のタスクを保持しているため、タスクの通常優先度とトップpiウェイターの優先度を比較するだけで十分だからです。

PIチェーンのウォークの高レベルな概要¶

PIチェーンのウォークは関数rt_mutex_adjust_prio_chainによって実装されています。

この実装は複数のイテレーションを経て、現在のところ最も効率的な形に落ち着いています。1回の処理で最大2つのロックを取得し、非常に効率的な処理が可能です。

rt_mutex_adjust_prio_chainはプロセスの優先度を上げたり下げたりするための関数として使用できます。

この関数は、PI（デ）ブーストを検討するタスク（プロセスがブロックしているミューテックスの所有者）、デッドロック検出をチェックするフラグ、タスクが所有するミューテックス、プロセスのウェイターストラクチャをブロックしているミューテックスへのポインタ（デブーストの場合はこのパラメータがNULLになる可能性あり）、タスクがブロックされているミューテックスへのポインタ、そしてミューテックスのトップタスク（トップウェイター）を引数として呼び出されます。

この説明ではデッドロック検出については触れません。説明は高レベルに留めます。

この関数が呼び出される際にはロックが保持されていません。これにより、関数に入った時点で所有者とロックの状態が変化する可能性があります。

この関数が呼び出される前には、タスクに対してrt_mutex_adjust_prioがすでに実行されています。これは、タスクが正しい優先度に設定されていることを意味しますが、タスクのwaiterのrbtreeノードは新しい優先度に更新されておらず、このタスクがブロックされているpi_waitersとwaitersツリーの適切な位置にない可能性があります。この関数は、こうした問題をすべて解決します。

この関数の主な処理は、Thomas Gleixnerがrtmutex.cで説明した通りです。詳細については、「チェーンウォークの基本と保護範囲」のコメントを参照してください。

ミューテックスの取得（ウォークスルー）¶

はい、ではミューテックスを取得する際の詳細なウォークスルーを見てみましょう。

最初に試されるのはミューテックスの高速取得です。CMPXCHGが有効になっている場合（それ以外の場合、高速取得は自動的に失敗します）にのみ実行されます。ミューテックスのownerフィールドがNULLの場合のみ、CMPXCHGでロックを取得でき、それ以外の処理は必要ありません。

ロックに競合がある場合、遅いパス（rt_mutex_slowlock）を処理します。

遅いパスの関数では、タスクのwaiter構造体がスタック上に作成されます。これは、この関数のスコープにのみ必要なためです。waiter構造体は、タスクをミューテックスのwaitersツリーに登録するためのノードを保持し、必要に応じて所有者のpi_waitersツリーにも登録します。

ミューテックスのwait_lockを取得します。ミューテックスのロック解除の遅いパスもこのロックを取得するためです。

次にtry_to_take_rt_mutexを呼び出します。これは、CMPXCHGを実装していないアーキテクチャでは、競合がない場合に常にロックを取得する処理です。

try_to_take_rt_mutexは、タスクが遅いパスでミューテックスを取得するたびに使用されます。ここではまず、ミューテックスのownerフィールドの「待機中のタスクがいる」フラグをアトミックに設定します。このフラグを設定することで、現在のミューテックスの所有者はこのコードを遅いアンロックパスで解放しなければならず、wait_lockを取得する必要があります。これにより、現在の所有者はこのコードと同期するよう強制されます。

以下の条件がすべて真である場合、ロックを取得できます：

  1. ロックに所有者はいません

  2. 現在のタスクがロックの他のすべての待機者よりも高い優先度です

タスクがロックを取得成功した場合、タスクをロックの所有者に設定し、ロックにまだ待機者がいる場合は、ロックを待っている最高優先度のタスク（top_waiter）をこのタスクのpi_waitersツリーに追加します。

try_to_take_rt_mutex()でロックが取得されなかった場合、task_blocks_on_rt_mutex()関数が呼び出されます。これにより、タスクがロックの待機木に追加され、ロックのPIチェーンが伝播され、ロックの所有者のpi_waiters木も更新されます。これは次のセクションで詳しく説明します。

タスクがミューテックスをブロックする¶

ミューテックスおよびプロセスのアカウントは、プロセスのウェイターストラクチャによって行われます。"task"フィールドはプロセスに設定され、"lock"フィールドはミューテックスに設定されます。ウェイターのRBツリーのノードは、プロセスの現在の優先度で初期化されます。

slow lockのエントリでwait_lockが取得されているため、タスクをタスクのウェイターツリーに安全に追加できます。現在のプロセスがこのミューテックスを待機しているプロセスの中で最優先度の場合、所有者のpi_waitersから前のトップウェイタープロセス（存在すれば）を削除し、現在のプロセスをそのツリーに追加します。所有者のpi_waiterが変更されたため、所有者に対してrt_mutex_adjust_prioを呼び出して、所有者が優先度を調整する必要があるか確認します。

所有者が別のロックにブロックされており、pi_waitersが変更された（またはデッドロックチェックが有効）場合、ミューテックスのwait_lockをアンロックし、前述のように所有者に対してrt_mutex_adjust_prio_chainを実行します。

すべてのロックが解放され、現在のプロセスがまだミューテックスを待機している場合（ウェイターの"task"フィールドがNULLでない場合）、スリープ状態に移行します（scheduleを呼び出します）。

ループ内で目覚める¶

タスクは以下の理由で目覚めることがあります：

  1. 前のロック所有者がロックを解放したため、タスクがトップウェイターになった

  2. シグナルまたはタイムアウトを受けた

いずれの場合も、タスクは再びロックを取得しようと試みます。成功すると、待機木から自身を外し、TASK_RUNNING状態に戻します。

最初の場合、このタスクがロックを取得する前に他のタスクがロックを取得していた場合、タスクは再びスリープ状態に戻り、再度目覚めるのを待つことになります。

2番目のケースは、シグナルまたはタイムアウトによりロック取得前に目覚めることが可能なミューテックスを取得しようとしているタスクにのみ適用されます（例：rt_mutex_timed_futex_lock()）。目覚めた場合、再びロックを取得しようと試みます。成功するとロックを保持して戻り、失敗した場合はシグナルで目覚めた場合は-EINTR、タイムアウトで終了した場合は-ETIMEDOUTを返します。

ミューテックスのアンロック¶

ミュートックスのアンロックにも、CMPXCHGを持つアーキテクチャ向けに高速なパスがあります。ミュートックスの所有者が競合状態でミュートックスを取得した際には常に「Waitersが存在する」フラグが設定されるため、このフラグをもってアンロック時に高速パスを採用するかどうかを判断します。ミュートックスに待機中のプロセスがいない場合、ミュートックスの所有者フィールドは現在のプロセスと一致し、所有者フィールドをNULLに置き換えることでミュートックスをアンロックできます。

所有者フィールドに「Waitersが存在する」ビットが設定されている（またはCMPXCHGが利用できない）場合、遅いアンロックパスが採用されます。

遅いアンロックパスの最初の処理は、ミュートックスのwait_lockを取得することです。これによりミュートックスのロックとアンロックが同期されます。

ミュートックスに待機中のプロセスがいるかを確認します。CMPXCHGを持たないアーキテクチャでは、この確認はミュートックスの所有者が待機プロセスを起こす必要があるかどうかを判断する場所です。CMPXCHGを持つアーキテクチャではこの確認は高速パスで行われますが、遅いパスでも必要です。所有者が高速パスのCMPXCHGチェックで失敗した後、wait_lockを取得する間に待機プロセスがシグナルやタイムアウトで起こった場合、ミュートックスに待機プロセスがいない可能性があるため、所有者はこの確認を再度行う必要があります。待機プロセスがなければ、ミュートックスの所有者フィールドをNULLに設定し、wait_lockを解放して処理を終了します。

待機プロセスがある場合、1つを起こす必要があります。

起こす処理では、現在の所有者のpi_lockを取得します。ロックの上位待機プロセスを特定し、ミュートックスの待機ツリーから削除するとともに、現在の所有者のpi_waitersツリーからも削除します。「Waitersが存在する」ビットを設定して、低優先度タスクがロックを奪うのを防ぎます。

最後に、保留中の所有者のpi_lockをアンロックして起こします。

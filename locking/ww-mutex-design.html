Wound/Wait Deadlock-Proof Mutex Design¶

まず mutex-design.txt を読みましょう。これは wait/wound ミューテックスにも適用されます。

WW-ミューテックスの動機¶

GPU は多くのバッファを扱う操作を行うことが多く、これらのバッファはコンテキスト/プロセス間で共有可能であり、異なるメモリドメイン（例：VRAM とシステムメモリ）に存在する場合もあります。PRIME / dmabuf を使用すれば、デバイス間でも共有可能になります。そのため、ドライバがバッファが準備完了を待つ必要がある状況はいくつかあります。この状況をバッファミューテックスの待機として考える場合、問題はバッファが execbuf/batch でどの順序で出現するかを保証することができない点にあります。これはユーザー空間の制御下にあり、アプリケーションが行う GL コールの順序の結果です。これによりデッドロックの可能性が生じます。問題はさらに複雑になりますが、ここでは簡略化のために、カーネルが GPU がバッファを処理する前にバッファを VRAM に移動する必要があるという点は無視してください。

TTM グラフィックスサブシステムがこの問題に対処するためのアルゴリズムは非常に単純です。各バッファグループ（execbuf）をロックする際には、呼び出し元にグローバルカウンターから一意の予約ID/チケットが割り当てられます。execbuf に関連するすべてのバッファをロック中にデッドロックが発生した場合、予約ID（つまり最も古いタスク）が優先され、予約IDが大きい（つまり若いタスク）はすでにロックしたバッファをすべてアンロックし、再試行します。

RDBMSの文献において、予約チケットはトランザクションと関連付けられ、デッドロック処理のアプローチとして「Wait-Die」と呼ばれる方法が用いられます。この名前は、ロックしているスレッドが既にロックされているミューテックスに遭遇した際の動作に基づいています。ロックしているトランザクションが若い場合、ロックしているトランザクションは待機します。ロックしているトランザクションが古い場合、ロックしているトランザクションはバックオフし、終了します。これがWait-Dieの由来です。また、もう一つのアルゴリズムとして「Wound-Wait」と呼ばれるものもあります。ロックしているトランザクションが若い場合、ロックしているトランザクションはロックしているトランザクションを「Wound（傷つける）」し、終了を求める処理を行います。ロックしているトランザクションが古い場合、ロックしているトラン�クションは他のトランザクションを待機します。これがWound-Waitの由来です。この2つのアルゴリズムはどちらも、トランザクションが最終的に成功することを保証する公平な方法です。しかし、Wound-WaitアルゴリズムはWait-Dieに比べて通常より少ないバックオフを生成する一方で、バックオフからの復旧においてはWait-Dieに比べてより多くの作業を伴います。また、Wound-Waitはトランザクションが他のトランザクションによって「Wound」される点でプリエンプティブなアルゴリズムとされます。これには、傷ついた状態を正確に検出する信頼できる方法と、実行中のトランザクションをプリエンプションする必要があるためです。注意点として、これはプロセスのプリエンプションとは異なります。Wound-Waitトランザクションは、傷つけられ（-EDEADLKを返す）後に終了した際にプリエンプションされたとみなされます。

概念¶

通常のミューテックスと比較して、w/wミューテックスのロックインターフェースには2つの追加の概念/オブジェクトが現れます:

取得コンテキスト: 進展を最終的に確保するためには、ロックを取得しようとするタスクが新しい予約IDを取得するのではなく、ロック取得を開始した際に取得したIDを保持することが重要です。このチケットは取得コンテキストに保存されます。さらに、取得コンテキストはデバッグ状態を追跡し、w/wミューテックスインターフェースの誤使用を検出します。取得コンテキストはトランザクションを表します。

w/wクラス: 通常のミューテックスと異なり、w/wミューテックスではロッククラスを明示的に指定する必要があります。これは取得コンテキストを初期化するための必要条件であり、ロッククラスは使用するアルゴリズム（Wound-WaitまたはWait-Die）を指定します。

さらに、w/wロック取得関数には3つの異なるクラスがあります:

  • ww_mutex_lockを使用した通常のロック取得

  • 競合しているロックに対してスローパスロック取得を実行する関数で、既に取得したロックをすべて解放した後、自身のトランザクションを殺したタスクが使用します。これらの関数には_slowというサフィックスが付きます。

    セマンティクスの観点から見れば、_slow関数は厳密には必要ではありません。なぜなら、他のすべての既取得ロックを解放した後で通常のww_mutex_lock関数を競合するロックに対して呼び出すだけで正しく動作するからです。畢竟、他のwwミューテックスがまだ取得されていない場合、デッドロックの可能性はなく、ww_mutex_lock呼び出しはブロック状態となり、-EDEADLKを早期に返すことはありません。_slow関数の利点はインターフェースの安全性にあります：

    • ww_mutex_lockは__must_check int型の戻り値を持ち、ww_mutex_lock_slowはvoid型の戻り値を持ちます。注意してください、wwミューテックスコードはループ/再試行が必要なため、__must_checkは偽の警告を引き起こしません。ただし、最初のロック操作は決して失敗しません。

    • フルデバッグが有効な場合、ww_mutex_lock_slowはすべての取得したwwミューテックスが解放されているかを確認し（デッドロックを防ぐ）、競合するロックに対してブロックするようにします（-EDEADLKのスローパスでスピンするのを防ぎ、ロックを取得できるまで待機します）。

  • 単一のw/wミューテックスを取得するための関数で、通常のミューテックスと同じセマンティクスをもたらします。これはNULLコンテキストでww_mutex_lockを呼び出すことで実現されます。

    これは厳密には必要ではありませんが、通常は単一のロックを取得するだけの場合、コンテキストを設定する必要がなく、デッドロック回避チケットを取得するのを避けるのが望ましいです。

もちろん、シグナルによるウェイクアップ処理の通常のバリエーションも提供されています。

使い方¶

アルゴリズム（Wait-Die vs Wound-Wait）はDEFINE_WW_CLASS（Wound-Wait）かDEFINE_WD_CLASS（Wait-Die）を使用して選択されます。大まかなルールとして、同時進行する競合トランザクションの数が通常小さく、ロールバックの数を減らしたい場合にWound-Waitを使用します。

同じw/wクラス内でロックを取得する3つの方法があります。メソッド#1および#2の一般的な定義：

static DEFINE_WW_CLASS(ww_class);

struct obj {
      struct ww_mutex lock;
      /* obj data */
};

struct obj_entry {
      struct list_head head;
      struct obj *obj;
};

メソッド1、execbuf->buffers内のリストを使用し、再配置が許可されません。これはすでにどこかで追跡されている必要なオブジェクトのリストがある場合に便利です。さらに、ロックアシスタントは-EALREADYの戻りコードを呼び出し元に伝播させ、リストにオブジェクトが2回登録されていることを示す信号として利用できます。これはユーザー空間からの入力でリストが構築され、ABIがユーザー空間に重複エントリを許さない場合（例：GPUコマンドバッファ送信ioctl）に特に有用です：

int lock_objs(struct list_head *list, struct ww_acquire_ctx *ctx)
{
      struct obj *res_obj = NULL;
      struct obj_entry *contended_entry = NULL;
      struct obj_entry *entry;

      ww_acquire_init(ctx, &ww_class);

retry:
      list_for_each_entry (entry, list, head) {
              if (entry->obj == res_obj) {
                      res_obj = NULL;
                      continue;
              }
              ret = ww_mutex_lock(&entry->obj->lock, ctx);
              if (ret < 0) {
                      contended_entry = entry;
                      goto err;
              }
      }

      ww_acquire_done(ctx);
      return 0;

err:
      list_for_each_entry_continue_reverse (entry, list, head)
              ww_mutex_unlock(&entry->obj->lock);

      if (res_obj)
              ww_mutex_unlock(&res_obj->lock);

      if (ret == -EDEADLK) {
              /* we lost out in a seqno race, lock and retry.. */
              ww_mutex_lock_slow(&contended_entry->obj->lock, ctx);
              res_obj = contended_entry->obj;
              goto retry;
      }
      ww_acquire_fini(ctx);

      return ret;
}

メソッド2は、execbuf->buffers内のリストを再配置可能な形で使用します。これはメソッド1と同様の- EALREADYによる重複エントリ検出のセマンティクスを持ちますが、リストの再配置により多少自然なコード表現が可能になります。

int lock_objs(struct list_head *list, struct ww_acquire_ctx *ctx)
{
      struct obj_entry *entry, *entry2;

      ww_acquire_init(ctx, &ww_class);

      list_for_each_entry (entry, list, head) {
              ret = ww_mutex_lock(&entry->obj->lock, ctx);
              if (ret < 0) {
                      entry2 = entry;

                      list_for_each_entry_continue_reverse (entry2, list, head)
                              ww_mutex_unlock(&entry2->obj->lock);

                      if (ret != -EDEADLK) {
                              ww_acquire_fini(ctx);
                              return ret;
                      }

                      /* we lost out in a seqno race, lock and retry.. */
                      ww_mutex_lock_slow(&entry->obj->lock, ctx);

                      /*
                       * Move buf to head of the list, this will point
                       * buf->next to the first unlocked entry,
                       * restarting the for loop.
                       */
                      list_del(&entry->head);
                      list_add(&entry->head, list);
              }
      }

      ww_acquire_done(ctx);
      return 0;
}

メソッド#1と#2の両方において、ロック解除の仕組みは同じです。

void unlock_objs(struct list_head *list, struct ww_acquire_ctx *ctx)
{
      struct obj_entry *entry;

      list_for_each_entry (entry, list, head)
              ww_mutex_unlock(&entry->obj->lock);

      ww_acquire_fini(ctx);
}

オブジェクトのリストが即興的に構築される場合にメソッド3が有用です。例えば、グラフのエッジを調整する際、各ノードが独自のww_mutexロックを持つ場合、すべての関与ノードのロックを保持しているときにのみエッジを変更できるため、w/w mutexはこのようなケースに自然に適合します。その理由は以下の通りです：

  • ロック取得の順序を問わないため、グラフの開始点から歩き始め、新しいエッジを繰り返し発見し、それらのエッジに接続するノードをロックダウンできるからです。

  • - EALREADYの返却コードにより、特定のオブジェクトがすでにロックされていることを示すため、グラフ内のサイクルを解除するための追加の記録処理や、複数の開始点を使用する際の既にロックされているノードの追跡は不要です。

このアプローチは、上述のメソッドと2つの重要な点で異なります：

  • オブジェクトのリストは動的に構築されるため（再試行時に-EDEADLKの条件に遭遇した場合、リストは大きく異なる可能性があります）、ロックされていないオブジェクトを永続的なリストに保持する必要はありません。したがって、リスト_headをオブジェクト自体に移動できます。

  • 一方で、動的なオブジェクトリスト構築により、- EALREADYの返却コードを伝播させることはできません。

メソッド#1と#2およびメソッド#3を組み合わせることも可能です。例えば、ユーザー空間から渡された開始ノードのリストを上述のメソッドのいずれかで最初にロックし、その後、メソッド#3を使用して操作に影響される追加のオブジェクトをロックします。バックオフ/再試行プロセスはやや複雑になります。なぜなら、動的ロックステップが-EDEADLKに遭遇した場合、固定リストで取得したすべてのオブジェクトをアンロックする必要があります。ただし、w/w mutexのデバッグチェックはこれらのケースにおけるインターフェースの誤使用を検出します。

また、メソッド3はロック取得ステップで失敗しないです。なぜなら、- EALREADYを返却しないからです。もちろん、_interruptibleバリアントを使用する場合は異なりますが、ここでの例の範囲外です：

struct obj {
      struct ww_mutex ww_mutex;
      struct list_head locked_list;
};

static DEFINE_WW_CLASS(ww_class);

void __unlock_objs(struct list_head *list)
{
      struct obj *entry, *temp;

      list_for_each_entry_safe (entry, temp, list, locked_list) {
              /* need to do that before unlocking, since only the current lock holder is
              allowed to use object */
              list_del(&entry->locked_list);
              ww_mutex_unlock(entry->ww_mutex)
      }
}

void lock_objs(struct list_head *list, struct ww_acquire_ctx *ctx)
{
      struct obj *obj;

      ww_acquire_init(ctx, &ww_class);

retry:
      /* re-init loop start state */
      loop {
              /* magic code which walks over a graph and decides which objects
               * to lock */

              ret = ww_mutex_lock(obj->ww_mutex, ctx);
              if (ret == -EALREADY) {
                      /* we have that one already, get to the next object */
                      continue;
              }
              if (ret == -EDEADLK) {
                      __unlock_objs(list);

                      ww_mutex_lock_slow(obj, ctx);
                      list_add(&entry->locked_list, list);
                      goto retry;
              }

              /* locked a new object, add it to the list */
              list_add_tail(&entry->locked_list, list);
      }

      ww_acquire_done(ctx);
      return 0;
}

void unlock_objs(struct list_head *list, struct ww_acquire_ctx *ctx)
{
      __unlock_objs(list);
      ww_acquire_fini(ctx);
}

メソッド4：単一のオブジェクトのみをロックします。この場合、デッドロック検出と防止は明らかに過剰です。なぜなら、単一のロックを取得するだけで、1つのクラス内でデッドロックを発生させることはできません。このケースを簡略化するため、NULLコンテキストでw/w mutex APIを使用できます。

実装の詳細¶

設計:¶

ww_mutexは現在、struct mutexをラップしており、これは通常のミューテックスロックには追加のオーバーヘッドが発生しないことを意味します。通常のミューテックスロックははるかに一般的です。そのため、wait/woundミューテックスが使われていない場合でも、コードサイズの増加はわずかです。

waitリストには以下の不変条件を維持しています:

  1. 取得コンテキストを持つ待機者はスタンプ順に並び、取得コンテキストを持たない待機者はFIFO順に混在します。

  2. wait-dieでは、コンテキストを持つ待機者の中で、最初の待機者だけが他のロックをすでに取得している可能性があります（ctx->acquired > 0）。注意点として、この待機者はリスト内で他のコンテキストを持たない待機者よりも後ろにくる可能性があります。

wound-waitのプリエンプションはラズィプリエンプションスキームで実装されています。トランザクションのwounded状態は、新しいロックの競合が発生した際にのみチェックされます。その状況でトランザクションがwoundedであれば、バックオフしてwounded状態をクリアし、再試行します。このようにプリエンプションを実装する大きな利点は、woundedトランザクションが再開前に競合しているロックを特定して待機できる点です。単純にトランザクションを再開してしまうと、再度バックオフする必要がある状況に陥る可能性があります。

一般的には競合が少ないものと期待されます。ロックは通常、デバイスへのアクセスをシリアル化するために使用され、最適化は無競合なケースに焦点を当てるべきです。

Lockdep:¶

APIの誤用をできるだけ多く警告するため、特別な注意を払っています。いくつかの一般的なAPIの誤用はCONFIG_DEBUG_MUTEXESで検出されますが、CONFIG_PROVE_LOCKINGが推奨されます。

警告されるエラーの例:

  • ww_acquire_finiまたはww_acquire_initを呼び忘れた。

  • ww_acquire_done後に多くのミューテックスをロックしようとした。

  • -EDEADLKで全てのミューテックスをアンロックした後、間違ったミューテックスをロックしようとした。

  • -EDEADLK後に全てのミューテックスをアンロックする前、正しいミューテックスをロックしようとした。

  • -EDEADLKが返された後でww_mutex_lock_slowを呼び出した。

  • 間違ったアンロック関数でミューテックスをアンロックした。

  • 同じコンテキストでww_acquire_*を2回呼び出した。

  • ミューテックスとww_acquire_ctxで異なるww_classを使用した。

  • デッドロックを引き起こす可能性のある通常のロックデップエラー。

デッドロックを引き起こす可能性のあるロックデップエラー:

  • ww_acquire_finiを1回目のww_acquire_ctxで呼び終わる前にもう一度ww_acquire_initを呼び出した。

  • 通常のデッドロックが発生する可能性がある。

プリエンプティブカーネルでの適切なロック: カーネルコードのプリエンプ安全性を保つ¶

著者

Robert Love <rml@tech9.net>

はじめに¶

プリエンプション可能なカーネルは新たなロックの問題を生じます。この問題はSMP（対称マルチプロセッサ）環境での問題と同様で、並行性と再入性に関するものです。幸いなことに、Linuxのプリエンプション可能なカーネルモデルは既存のSMPロックメカニズムを活用しています。そのため、カーネルは非常に限られた状況においてのみ明示的な追加ロックが必要です。

このドキュメントはすべてのカーネル開発者向けです。カーネル内でのコード開発には、このような状況を保護する必要があります。

ルール #1: Per-CPUデータ構造には明示的な保護が必要です¶

2つの類似した問題が生じます。コードスニペットの例:

struct this_needs_locking tux[NR_CPUS];
tux[smp_processor_id()] = some_value;
/* task is preempted here... */
something = tux[smp_processor_id()];

まず、データがPer-CPUであるため、明示的なSMPロックが存在しない可能性がありますが、それ以外の状況では必要です。また、プリエンプションされたタスクが再スケジューリングされた際に、smp_processor_idの前の値が現在の値と一致しない可能性があります。このような状況を保護するため、それらの周囲でプリエンプションを無効にする必要があります。

put_cpu()とget_cpu()を使用することもできます。これらはプリエンプションを無効にします。

ルール #2: CPUの状態を保護する必要があります¶

プリエンプション下ではCPUの状態を保護する必要があります。これはアーキテクチャに依存しますが、コンテキストスイッチで保持されないCPU構造と状態を含みます。たとえばx86では、FPUモードのエントリとエクスイットはプリエンプションを無効にして実行するクリティカルセクションです。カーネルが浮動小数点命令を実行中にプリエンプションされた場合、何が起こるか想像してください。記憶してください、カーネルはユーザータスク以外ではFPU状態を保存しません。したがって、プリエンプションが発生した際、FPUレジスタは最低額で売却されることになります。そのため、このような領域ではプリエンプションを無効にする必要があります。

注意: 一部のFPU関数はすでに明示的にプリエンプション安全です。たとえば、kernel_fpu_beginとkernel_fpu_endはプリエンプションを無効にして有効にします。

ルール #3: ロックの取得と解放は同じタスクで行う必要があります¶

タスクAで取得したロックはタスクAで解放する必要があります。これは、ロックを取得して別のタスクで処理を進めるような非標準的な操作は行えないことを意味します。このような操作を行いたい場合は、同じコードパスで取得と解放を行い、他タスクのイベントを呼び出し元が待機するようにします。

解決策¶

プリエンプション下でのデータ保護は、クリティカルセクションの期間中プリエンプションを無効にする方法で実現されます。

preempt_enable()              decrement the preempt counter
preempt_disable()             increment the preempt counter
preempt_enable_no_resched()   decrement, but do not immediately preempt
preempt_check_resched()       if needed, reschedule
preempt_count()               return the preempt counter

関数はネスト可能である。言い換えれば、コードパス内でpreempt_disableをn回呼び出すことができ、preempt_enableをn回目の呼び出しまでプリエマプションが再有効化されない。プリエマプションのステートメントは、プリエマプションが有効でない場合に何もしない。

ロックを保持しているか、割り込みが無効化されている場合は、明示的にプリエマプションを無効化する必要がない。なぜなら、これらの状況ではプリエマプションは暗黙的に無効化されるからである。

しかし、「割り込み無効化」によるプリエマプションの無効化は根本的に危険な方法である。cond_resched()やcond_resched_lock()などの関数は、プリエマプションカウントが0の場合に再スケジューリングをトリガーする可能性がある。簡単な printk() 操作でも再スケジューリングを引き起こす可能性がある。したがって、この暗黙的なプリエマプション無効化の特性は、影響を受けるコードパスがこのような操作を行わないことを確認した上でのみ使用すべきである。ベストなポリシーは、自分が書いた小さなアトミックなコードで、複雑な関数を呼び出さないものに限定することである。

例:

cpucache_t *cc; /* this is per-CPU */
preempt_disable();
cc = cc_data(searchp);
if (cc && cc->avail) {
        __free_block(searchp, cc_entry(cc), cc->avail);
        cc->avail = 0;
}
preempt_enable();
return 0;

プリエマプションステートメントがクリティカルな変数のすべての参照を含む必要があることに注意してほしい。もう一つの例:

int buf[NR_CPUS];
set_cpu_val(buf);
if (buf[smp_processor_id()] == -1) printf(KERN_INFO "wee!\n");
spin_lock(&buf_lock);
/* ... */

このコードはプリエマプション安全ではないが、spin_lockを2行上に移動するだけで簡単に修正できることがわかる。

割り込み無効化によるプリエマプションの無効化¶

local_irq_disableとlocal_irq_saveを使用することでプリエマプションイベントを防ぐことができる。ただし、この操作を行う際には、need_reschedを設定し、プリエマプションチェックを引き起こすイベントを引き起こさないよう、非常に注意深く行う必要がある。疑問がある場合は、ロックや明示的なプリエマプション無効化に依存すべきである。

2.5では割り込み無効化はCPUごとに適用される（例: ローカル）。

さらに重要なのはlocal_irq_disableとlocal_irq_saveの適切な使用である。これらはプリエマプションを防ぐために使用できるが、退出時にプリエマプションが有効になる可能性があるため、プリエマプションが必要かどうかを確認するテストを行うべきである。これらの関数がspin_lockやread/write lockマクロから呼ばれる場合、正しい動作が行われる。また、spin-lock保護された領域内で呼ばれる場合でも、これらがこのコンテキスト外で呼ばれた場合は、プリエマプションのテストを行う必要がある。注意すべきは、割り込みコンテキストやボトムハーフ/タスクレットからの呼び出しもプリエマプションロックによって保護されているため、プリエマプションのチェックを行わないバージョンを使用してもよいということである。

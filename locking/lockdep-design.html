ランタイムロックの正しさを検証するツール¶

Ingo Molnar により開始 <mingo@redhat.com>

Arjan van de Ven <arjan@linux.intel.com>

ロッククラス¶

検証器が操作する基本的なオブジェクトは、「ロックのクラス」です。

ロックのクラスとは、ロックの取得ルールに関して論理的に同じであるグループのロックを指します。ロックは複数（数十万もの）インスタンスを持つ可能性がありますが、これらは論理的に同じクラスに属します。たとえば、inode構造体内のロックは1つのクラスに属し、各inodeはそのロッククラスのインスタンスを持ちます。

検証器はロッククラスの「使用状態」を追跡し、異なるロッククラス間の依存関係も追跡します。ロックの使用状態は、IRQコンテキストにおけるロックの使用方法を示し、ロック依存関係はロックの順序を意味します（L1 -> L2は、L1を保持しつつL2を取得しようとしているタスクを示します）。lockdepの観点では、これらの2つのロック（L1とL2）は必ずしも関連しているとは限りませんが、その依存関係は過去に発生した順序を示します。検証器は常にロックの使用状態と依存関係が正しいことを証明しようとする努力を続け、誤った場合にsplatを出力します。

ロッククラスの挙動は、そのインスタンス全体で構成されます。起動後に最初のロッククラスのインスタンスが使用されると、クラスが登録され、その後のすべてのインスタンスはそのクラスにマッピングされます。したがって、その使用状態や依存関係はクラス全体に貢献します。ロックインスタンスが削除されてもロッククラスは消えませんが、ロッククラスのメモリ領域（静的または動的）が回収されると、クラスは削除されることがあります（たとえば、モジュールがロード解除されたり、ワークキューが破壊されたりする場合）。

状態¶

検証器はロッククラスの使用履歴を追跡し、これを（4つの使用状態 × n STATEs + 1）のカテゴリに分類します。

ここで、4つの使用状態は以下の通りです：

  • 「STATEコンテキストで常に保持されていた」

  • 「STATEコンテキストで常に読み込みロックとして保持されていた」

  • 「STATEコンテキストで常に有効な状態で保持されていた」

  • 「STATEコンテキストで常に読み込みロックとして有効な状態で保持されていた」

ここで、n STATEsはkernel/locking/lockdep_states.hに記述されており、現在は以下の通りです：

  • hardirq

  • softirq

最後の1つのカテゴリは以下の通りです：

  • 「常に使用されていた」[ == !unused]

ロックルールが違反された場合、これらの使用状態ビットはロックエラーのメッセージ内でカッコ内に表示され、合計で2 × n STATEsビットが表示されます。例を挙げると：

modprobe/2287 is trying to acquire lock:
 (&sio_locks[i].lock){-.-.}, at: [<c02867fd>] mutex_lock+0x21/0x24

but task is already holding lock:
 (&sio_locks[i].lock){-.-.}, at: [<c02867fd>] mutex_lock+0x21/0x24

あるロックに対して、左から右へ順にビット位置は、上記のn STATEsごとにロックと読み込みロック（存在する場合）の使用状態を示し、各ビット位置に表示される文字は以下の通りです：

‘.’

IRQが無効な状態で取得され、IRQコンテキストにない

‘-’

割り込みコンテキストで取得された

‘+’

割り込みが有効な状態で取得された

‘?’

割り込みコンテキストで取得され、割り込みが有効な状態で取得された。

ビットは以下の例で説明されています:

(&sio_locks[i].lock){-.-.}, at: [<c02867fd>] mutex_lock+0x21/0x24
                     ||||
                     ||| \-> softirq disabled and not in softirq context
                     || \--> acquired in softirq context
                     | \---> hardirq disabled and not in hardirq context
                      \----> acquired in hardirq context

特定のSTATEにおいて、ロックがそのSTATEコンテキストで取得される可能性があるか、そのSTATEが有効であるかによって、以下の表に示す4つのケースが生じます。ビットは、レポート時点でのロックの正確なケースを示すことができます。

割り込みが有効

割り込みが無効

常に割り込み中

‘?’

‘-’

常に割り込み中ではない

‘+’

‘.’

文字‘-’は割り込みが無効であることを示します。そうでなければ‘?’が表示されるはずです。同様に‘+’についても同様の推論が適用されます。

未使用のロック（例：ミューテックス）はエラーの原因にはなりません。

単一ロックの状態規則:¶

ロックが割り込み安全（irq-safe）であるとは、そのロックが割り込みコンテキストで使用されたことがあることを意味します。ロックが割り込み非安全（irq-unsafe）であるとは、そのロックが割り込みが有効な状態で取得されたことがあることを意味します。

ソフト割り込み非安全（softirq-unsafe）なロッククラスは自動的にハード割り込み非安全（hardirq-unsafe）にもなります。以下の状態は排他的でなければなりません：どのロッククラスも、その使用状況に基づいてこれらの状態のうち1つだけが設定される必要があります:

<hardirq-safe> or <hardirq-unsafe>
<softirq-safe> or <softirq-unsafe>

これは、ロックが割り込みコンテキストで使用可能（irq-safe）である場合、割り込みが有効な状態で取得されることはない（irq-unsafe）からです。そうでない場合、デッドロックが発生する可能性があります。例えば、このロックが取得された後、解放される前に関数が中断されると、このロックが2回取得されるようになり、デッドロック（ロック再帰デッドロック）が発生します。

検証器は、これらの単一ロック状態規則を違反するロックの使用を検出し、レポートします。

複数ロックの依存規則:¶

同じロッククラスが2回取得されることを防ぐ必要があります。これはロック再帰デッドロックを引き起こす可能性があるからです。

さらに、2つのロックが逆順で取得されることも許されません:

<L1> -> <L2>
<L2> -> <L1>

これは、2つのロックの取得が循環してしまい、お互いに待機し続けるデッドロック（ロック逆転デッドロック）を引き起こす可能性があるからです。検証器は、任意の複雑さを持つ依存関係の循環を検出します。つまり、取得操作の間に他のロックの取得順序が存在しても、検証器はこれらのロックが循環的に取得可能かどうかを判定します。

さらに、以下の使用に基づくロックの依存関係は、どの2つのロッククラス間でも許されません:

<hardirq-safe>   ->  <hardirq-unsafe>
<softirq-safe>   ->  <softirq-unsafe>

最初のルールは、ハードIRQセーフなロックがハードIRQコンテキストによって取得され、ハードIRQアンセーフなロックを中断してしまう可能性があるためです。これにより、ロック逆転のデッドロックが発生する可能性があります。同様に、ソフトIRQセーフなロックはソフトIRQコンテキストによって取得され、ソフトIRQアンセーフなロックを中断してしまうため、同様の問題が生じます。

上記のルールは、カーネル内で発生するすべてのロックの順序に適用されます。新しいロックを取得する際、検証器は新しいロックと保持しているすべてのロックの間でルール違反がないかを確認します。

ロッククラスの状態が変化した場合、以下の依存関係ルールが強制されます：

  • 新しいハードIRQセーフなロックが発見された場合、過去にハードIRQアンセーフなロックを取得したかを確認します。

  • 新しいソフトIRQセーフなロックが発見された場合、過去にソフトIRQアンセーフなロックを取得したかを確認します。

  • 新しいハードIRQアンセーフなロックが発見された場合、過去にハードIRQセーフなロックがそのロックを取得したかを確認します。

  • 新しいソフトIRQアンセーフなロックが発見された場合、過去にソフトIRQセーフなロックがそのロックを取得したかを確認します。

(再度、中断コンテキストが_IRQアンセーフなロックまたはハードIRQアンセーフなロックのいずれかを中断する可能性があるため、これらのチェックを行います。これにより、ロック逆転のデッドロックが発生する可能性があります—even if そのロックシナリオは実際にはまだ発生していません。)

例外：ネストされたデータ依存関係によるネストされたロック¶

Linuxカーネルが同じロッククラスの複数インスタンスを取得するケースはいくつかあります。このようなケースは、同じタイプのオブジェクト内で階層構造が存在する場合に通常発生します。このような場合、2つのオブジェクト間には階層の性質によって定義される「自然な」順序があり、カーネルは各オブジェクトに対してこの固定順序でロックを取得します。

「全体ディスク」ブロックデバイスオブジェクトと「パーティション」ブロックデバイスオブジェクトの階層構造は、このような「ネストされたロック」を生じる例です。パーティションは全体ディスクの一部であり、常に全体ディスクロックをパーティションロックよりも高いロックとして取得する限り、ロックの順序は完全に正しいです。検証器はこの自然な順序を自動的に検出しません。なぜなら、この順序の背後にあるロックルールは静的ではないからです。

検証器にこの正しい使用モデルを教えるために、さまざまなロックプリミティブの新しいバージョンが追加されました。これにより、ネストレベルを指定することが可能です。ブロックデバイスミューテックスの例として、以下のような呼び出しが行われます：

enum bdev_bd_mutex_lock_class
{
     BD_MUTEX_NORMAL,
     BD_MUTEX_WHOLE,
     BD_MUTEX_PARTITION
};

mutex_lock_nested(&bdev->bd_contains->bd_mutex, BD_MUTEX_PARTITION);

この場合、パーティションとして知られているbdevオブジェクトに対してロックが取得されます。

検証器は、このようなネストされた形で取得されたロックを、検証の目的で別の（サブ）クラスとして扱います。

注意: コードを _nested() プリミティブを使用して変更する際は、階層が正しくマッピングされているかを慎重に確認してください。そうでない場合、偽陽性または偽陰性が発生する可能性があります。

アノテーション¶

特定のロックが保持されている場所や条件をアノテーションし、確認するためには、lockdep_assert_held*(&lock) と lockdep_*pin_lock(&lock) の2つの構文を使用できます。

名前のとおり、lockdep_assert_held* マクロファミリは、特定のロックが特定のタイミングで保持されていることをアサートします（保持されていない場合は WARN() を生成します）。このアノテーションは、カーネル全体で広く使用されており、例えば kernel/sched/core.c などです。

void update_rq_clock(struct rq *rq)
{
      s64 delta;

      lockdep_assert_held(&rq->lock);
      [...]
}

rq->lock の保持が、rq のクロックを安全に更新するために必要です。

もう一つのマクロファミリは lockdep_*pin_lock() で、現時点では rq->lock にのみ使用されています。これらのアノテーションは採用範囲が限られているにもかかわらず、関心のあるロックが「誤って」アンロックされた場合に WARN() を生成します。これは、上位レイヤーがロックが保持されていると想定しているが、下位レイヤーがロックを解放して再取得できるかもしれないと誤って考える場合（意図せずにレース条件を導入する場合）に特に役立ちます。lockdep_pin_lock() は 'struct pin_cookie' を返し、lockdep_unpin_lock() でロックが改ざんされていないかを確認します。例えば kernel/sched/sched.h などです。

static inline void rq_pin_lock(struct rq *rq, struct rq_flags *rf)
{
      rf->cookie = lockdep_pin_lock(&rq->lock);
      [...]
}

static inline void rq_unpin_lock(struct rq *rq, struct rq_flags *rf)
{
      [...]
      lockdep_unpin_lock(&rq->lock, rf->cookie);
}

ロックの要件に関するコメントは有用な情報を提供するかもしれませんが、アノテーションによって行われる実行時チェックはロックの問題をデバッグする際に非常に重要です。コードを検証する際の詳細度も同様です。疑問があるときは常にアノテーションを優先してください！

100%の正しさの証明:¶

検証器は、カーネルの寿命中に少なくとも1回発生したすべての単純な、独立した単一タスクのロックシーケンスについて、数学的な「クロージャー」（ロックの正しさの証明）を達成します。つまり、これらのロックシーケンスの組み合わせやタイミングによって、どの種類のロック関連デッドロックも発生しないことを100%の確信で証明します。 1

つまり、デッドロックを証明するには、複雑なマルチCPU・マルチタスクのロックシナリオが実際に発生する必要はなく、単純な「コンポーネント」ロックチェーンが少なくとも一度（いつでも、どのタスク/コンテキストでも）発生すればよい。たとえば、通常は3つのCPU以上と非常にまれなタスク、IRQコンテキスト、タイミングの組み合わせが必要な複雑なデッドロックも、単純で負荷の低いシングルCPUシステムでも検出可能である。

これにより、ロック関連のQA（品質保証）の複雑さが劇的に低下する。QAで行うべきことは、ロックの正しさを証明するために、カーネル内で可能な限り多くの「単純な」単一タスクのロック依存関係を少なくとも一度はトリガーすることである。これに対し、CPU間のすべてのロック相互作用の組み合わせと、ハードIRQおよびソフトIRQのネストシナリオをすべて検証する必要はなく（実際には不可能である）。

1

検証器自身が100%正しいと仮定し、システムの他の部分が検証器の状態を一切破壊しないという前提も置く。また、すべてのNMI/SMMパス（ハードIRQ無効化コードパスを中断する可能性のあるもの）も正しいものとし、検証器に干渉しないと仮定する。さらに、システム内のすべてのロックチェーンに64ビットの「チェーンハッシュ」値が一意であるとし、ロック再帰は20を超えないものと仮定する。

パフォーマンス:¶

上記のルールは 大量のランタイムチェックを必要とする。 もしすべてのロック取得やIRQ有効化イベントに対してこれを実行すれば、システムは実用上遅すぎて使用不可になる。チェックの複雑度はO(N^2)であり、たとえ数百のロッククラスしかない場合でも、イベントごとに数万のチェックを実行しなければならない。

この問題は、任意の「ロックシナリオ」（連続して取得されるロックの一連のシーケンス）を一度だけチェックすることで解決する。保持中のロックのスタックを簡易に維持し、そのロックチェーンに一意な64ビットのハッシュ値を計算する。このハッシュ値は、チェーンが初めて検証されるときにハッシュテーブルに保存され、このハッシュテーブルはロックフリーモードで検証可能である。その後、同じロックチェーンが再度発生した場合、ハッシュテーブルがそのチェーンを再度検証する必要がないことを示してくれる。

トラブルシューティング:¶

検証器は最大MAX_LOCKDEP_KEYS個のロッククラスを追跡する。この数を超えると、以下のlockdep警告が発生する：

(DEBUG_LOCKS_WARN_ON(id >= MAX_LOCKDEP_KEYS))

デフォルトでは、MAX_LOCKDEP_KEYS は現在 8191 に設定されており、典型的なデスクトップシステムではロッククラスが 1,000 を超えないため、この警告は通常ロッククラスのリークやロックの適切な初期化が行われていないことにより発生します。これらの2つの問題は以下に示します。

  1. 検証器を実行中にモジュールの繰り返しのロードとアンロードはロッククラスのリークを引き起こします。問題は、モジュールごとに新しいロッククラスが作成される一方で、モジュールアンロードでは古いクラスが削除されないためです（ロッククラスの再利用に関する以下の議論を参照）。したがって、そのモジュールが繰り返しロード・アンロードされる場合、ロッククラスの数は最終的に最大値に達します。

  2. 配列などの構造体で大量のロックが含まれており、明示的に初期化されていない場合があります。例えば、8192 個のバケットを持つハッシュテーブルで、各バケットに spinlock_t が存在する場合、8192 個のロッククラスが消費されます（ただし、各 spinlock が実行時において明示的に初期化される場合を除く）。実行時に spin_lock_init() を使用して各 spinlock を初期化しないと、ロッククラスのオーバーフローが発生します。一方で、ループで各ロックに spin_lock_init() を呼び出すと、すべての 8192 個のロックが1つのロッククラスに配置されます。

    この物語の教訓は、常に明示的にロックを初期化するべきです。

有人が検証器を修正してロッククラスの再利用を許可すべきだと主張するかもしれません。しかし、そのような変更を検討する前に、コードを確認し、必要な変更を検討してください。削除するロッククラスはロック依存グラフにリンクされている可能性があるため、実際には言うより実装するのが難しいです。

もちろん、ロッククラスが不足した場合は、まず問題のロッククラスを特定する必要があります。まず、以下のコマンドで現在使用中のロッククラス数と最大値を確認できます。

grep "lock-classes" /proc/lockdep_stats

このコマンドは、標準的なシステムでは以下の出力結果を生成します。

lock-classes:                          748 [max: 8191]

割り当てられた数（上記の748）が時間とともに継続的に増加する場合、リークの可能性があります。以下のコマンドを使用してリークしているロッククラスを特定できます。

grep "BD" /proc/lockdep

コマンドを実行し、出力を保存した後、このコマンドを後で実行した出力と比較することでリーク元を特定できます。この出力は、実行時ロック初期化が省略されている状況も特定するのに役立ちます。

再帰的な読み込みロック:¶

残りのドキュメント全体は、特定の種類のサイクルがデッドロックの可能性と等価であることを証明しようとしています。

ロックの種類は3つあります：ライター（つまり、排他ロック、spin_lock()やwrite_lock()のような）、非再帰リーダー（つまり、共有ロック、down_read()のような）および再帰リーダー（再帰的な共有ロック、例えば rcu_read_lock())。そして、この後ろのドキュメントでは、これらのロックを以下の表記で使用します：

WまたはE：ライター（排他ロック）を表します。r：非再帰リーダーを表します。R：再帰リーダーを表します。S：すべてのリーダー（非再帰＋再帰）を表し、どちらも共有ロックです。N：ライターと非再帰リーダーを表し、どちらも非再帰です。

明らかに、Nは「rまたはW」で、Sは「rまたはR」です。

再帰リーダーは、その名前が示すように、同じロックインスタンスのリーダーのクリティカルセクション内でも取得可能であり、つまり、一つのロックインスタンスの読み込み側のクリティカルセクションをネストして実行できるロックです。

非再帰リーダーは、同じロックインスタンスのリーダーのクリティカルセクション内で取得しようとすると、自己デッドロックを引き起こします。

再帰リーダーと非再帰リーダーの違いは、再帰リーダーは書き込みロックのみでブロックされるのに対し、 holder非再帰リーダーは書き込みロックでもブロックされるからです。 待機中のプロセス以下の例を考慮してください：

TASK A:                 TASK B:

read_lock(X);
                        write_lock(X);
read_lock_2(X);

タスクAがread_lock()でロックXを取得します（再帰的でも非再帰でもかまいません）。そして、タスクBがロックXのライターを取得しようとすると、ブロックされ、ロックXのライター待機者になります。このとき、read_lock_2()が再帰リーダーであれば、タスクAは進展し、ライター待機者が再帰リーダーをブロックしないのでデッドロックは発生しません。しかし、read_lock_2()が非再帰リーダーであれば、ライター待機者Bによってブロックされ、自己デッドロックを引き起こします。

同じロックインスタンスのリーダー/ライター間のブロック条件：¶

単純に4つのブロック条件があります：

  1. ライターは他のライターをブロックします。

  2. リーダーはライターをブロックします。

  3. ライターは再帰リーダーおよび非再帰リーダーをブロックします。

  4. リーダー（再帰的でも非再帰でも）は他の再帰リーダーをブロックしませんが、非再帰リーダーをブロックする可能性があります（書き込み待機者が共存するため）。

TASK A:                 TASK B:

read_lock(X);

                        write_lock(X);

read_lock(X);

これは再帰的な読み込みロックのデッドロックではありません。タスクBがロックXを待っている間、第二のread_lock()は再帰的な読み込みロックのため待機する必要がありません。しかし、read_lock()が非再帰的な読み込みロックである場合、上記のケースはデッドロックになります。なぜなら、タスクBのwrite_lock()がロックを取得できない場合でも、タスクAの第二のread_lock()がブロックされるからです。

ロックは、取得時に使用されるロック操作（特にlock_acquire()の「read」パラメータの値）によって、書き込みロック（排他ロック）、非再帰的な読み込みロック（非再帰的な共有ロック）、または再帰的な読み込みロック（再帰的な共有ロック）のいずれかになります。言い換えれば、単一のロックインスタンスは、取得関数によって3つの種類の取得方法を持ちます：排他、非再帰的な読み込み、再帰的な読み込み。

簡潔にまとめると、書き込みロックと非再帰的な読み込みロックを「非再帰的なロック」と呼び、再帰的な読み込みロックを「再帰的なロック」と呼びます。

再帰的なロックはお互いにブロックしませんが、非再帰的なロックはブロックします（これは2つの非再帰的な読み込みロックでも同様です）。非再帰的なロックは対応する再帰的なロックをブロックし、逆もしかりです。

再帰的なロックを含むデッドロックのケースは以下の通りです：

TASK A:                 TASK B:

read_lock(X);
                        read_lock(Y);
write_lock(Y);
                        write_lock(X);

タスクAはタスクBがYをread_unlock()するのを待っており、タスクBはタスクAがXをread_unlock()するのを待っています。

依存関係の種類と強い依存関係のパス：¶

ロック依存関係は2つのロックの取得順序を記録し、ロックの種類が3つあるため理論上9種類のロック依存関係が存在しますが、デッドロック検出には4種類のロック依存関係で十分です。

各ロック依存関係について：

L1 -> L2

これは、ランタイムで同じコンテキストでL1が保持された後にL2が保持されたことをlockdepが観測したことを意味します。デッドロック検出では、L1を保持している状態でL2にブロックされる可能性があるかどうか（つまり、L1がブロックするロックL3があり、L2がL3によってブロックされるかどうか）を確認します。したがって、我々が気にするのは1) L1がブロックするものと2) L2がブロックされるものです。その結果、L1の再帰的リーダーと非再帰的リーダーを統合（彼らが同じタイプをブロックするため）し、L2のライターや非再帰的リーダーを統合（彼らが同じタイプによってブロックされるため）できます。

上記の簡略化の組み合わせにより、lockdepグラフには4種類の依存関係エッジがあります：

  1. -(ER)->:

    排他ライターから再帰的リーダーへの依存関係、「X -(ER)-> Y」はX -> Yであり、XがライターでYが再帰的リーダーであることを意味します。

  2. -(EN)->:

    排他ライターと非再帰ロック依存関係、"X -(EN)-> Y" は X -> Y であり、X がライターで Y がライターまたは非再帰リーダーであることを意味します。

  3. -(SR)->:

    共有リーダーと再帰リーダーの依存関係、"X -(SR)-> Y" は X -> Y であり、X がリーダー（再帰的でも非再帰的でも）で Y が再帰リーダーであることを意味します。

  4. -(SN)->:

    共有リーダーと非再帰ロックの依存関係、"X -(SN)-> Y" は X -> Y であり、X がリーダー（再帰的でも非再帰的でも）で Y がライターまたは非再帰リーダーであることを意味します。

2つのロックが存在する場合、それらの間に複数の依存関係がある可能性があります。例えば：

TASK A:

read_lock(X);
write_lock(Y);
...

TASK B:

write_lock(X);
write_lock(Y);

、依存関係グラフには X -(SN)-> Y と X -(EN)-> Y の両方が存在します。

-(xN)-> は -(EN)-> または -(SN)-> のエッジを表し、-(Ex)->、-(xR)->、-(Sx)-> についても同様です。

「パス」はグラフ内の結合された依存関係のエッジの連続です。「強い」パスは、パス内の各依存関係において強い依存関係が存在することを示し、-(xR)-> と -(Sx)-> の2つの結合エッジを含まないパスとして定義されます。言い換えれば、「強い」パスはロック間の依存関係を通じて別のロックへと移動するパスであり、X -> Y -> Z（X、Y、Z はロック）がパスに含まれる場合、X から Y への移動が -(SR)-> または -(ER)-> の依存関係を通じたものであれば、Y から Z への移動は -(SN)-> または -(SR)-> の依存関係を通じたものであってはなりません。

次のセクションでなぜこのパスが「強い」と呼ばれるのかを確認できます。

再帰的リードロック検出:¶

ここで2つのことを証明します:

補題1:

閉じた強いパス（つまり強いループ）が存在する場合、ロックの組み合わせによってデッドロックが発生することを示します。つまり、強いループはデッドロック検出の十分条件です。

補題2:

閉じた強いパス（つまり強いループ）が存在しない場合、ロックの組み合わせによってデッドロックが発生しないことを示します。つまり、強いループはデッドロック検出の必要条件です。

これらの2つの補題により、閉じた強いパスはデッドロックの十分条件かつ必要条件であり、したがって閉じた強いパスはデッドロックの可能性と等価です。閉じた強いパスはデッドロックを引き起こす可能性のある依存関係の連鎖を表すため、「強い」と呼ばれます。これは、依存関係のループであってもデッドロックを引き起こさない可能性があるためです。

十分性の証明（補題1）:

強いループがあると仮定します：

L1 -> L2 ... -> Ln -> L1

、これは以下の依存関係を持つことを意味します：

L1 -> L2
L2 -> L3
...
Ln-1 -> Ln
Ln -> L1

ここで、デッドロックを引き起こすロックの組み合わせを構築できます：

まず、1つのCPU/タスクがL1 -> L2でL1を取得し、次に別のCPU/タスクがL2 -> L3でL2を取得し、このように順に進めていきます。その後、すべてのLx（Lx -> Lx+1）は異なるCPU/タスクによって保持されます。

次に、L1 -> L2があるため、L1を保持しているCPU/タスクがL2を取得しようとしますが、L2は別のCPU/タスクによって保持されており、さらにL1 -> L2とL2 -> L3は-(xR)->と-(Sx)->の組み合わせではなく（強さの定義）、つまりL1 -> L2におけるL2は非再帰的なロック（誰かによってブロックされる）か、L2 -> L3におけるL2はライタ（誰かをブロックする）であるため、L1を保持しているCPU/タスクはL2を取得できず、L2の保持者から解放されるのを待つ必要があります。

さらに、L2の保持者にも同様の結論が成り立ち、L3の保持者から解放されるのを待つ必要があります。このようにして、Lxの保持者はLx+1の保持者から解放されるのを待つことになり、Ln+1がL1であるため、循環的な待機状態が生じ、誰も進展できず、デッドロックが発生します。

必要性の証明（補題2）:

補題2は以下の通りです：デッドロック状態が発生している場合、依存グラフに強さを持つ循環が存在する必要があります。

ウィキペディア[1]によると、デッドロックが発生している場合、循環的な待機状態が存在するため、N個のCPU/タスクがあり、CPU/タスクP1がP2が保持しているロックを待っている、P2がP3が保持しているロックを待っている、…、PnがP1が保持しているロックを待っている状態です。ここで、Pxが待っているロックをLxと名付けると、P1がL1を待っている一方でLnを保持しているため、依存グラフにはLn -> L1が存在します。同様に、L1 -> L2、L2 -> L3、…、Ln-1 -> Lnが依存グラフに存在し、これにより循環が成立します。

Ln -> L1 -> L2 -> ... -> Ln

そして、この循環が強さを持つことを証明します:

ロックLxに対して、PxがLx-1 -> Lxの依存を提供し、Px+1がLx -> Lx+1の依存を提供します。PxがPx+1からLxを解放されるのを待っているため、LxがPx+1でライダーであり、LxがPxで再帰的なライダーであることは不可能です（ライダー（再帰的であれなかれ）は再帰的なライダーをブロックしません）。したがって、Lx-1 -> LxとLx -> Lx+1は-(xR)-> -(Sx)->のペアにはなり得ず、これは循環内のすべてのロックに当てはまります。したがって、この循環は強さを持ちます。

カーネルロックのトラウトテスト操作¶

CONFIG_LOCK_TORTURE_TEST¶

CONFIG_LOCK_TORTURE_TEST設定オプションは、カーネルの基本的なロックプリミティブに拷問テストを実行するカーネルモジュールを提供します。必要に応じて、テスト対象の実行中のカーネルで事後で「locktorture」というカーネルモジュールを構築できます。テストは定期的にステータスメッセージを printk()dmesg経由で出力し、これらはgrepで「torture」を検索して確認できます。テストはモジュールのロード時に開始し、モジュールのアンロード時に停止します。このプログラムはRCUの拷問テストを参考にしています。

この拷問テストは、ロックを取得して特定の時間保持する複数のカーネルスレッドを生成し、異なるクリティカルリージョンの挙動をシミュレートします。ロックの競合度は、このクリティカルリージョンの保持時間を長くするか、またはより多くのkthreadを生成することでシミュレートできます。

モジュールパラメータ¶

このモジュールは以下のパラメータを持ちます:

locktorture固有のパラメータ¶

nwriters_stress

排他ロック所有をストレスかけるカーネルスレッド数。デフォルト値はオンラインCPUの数の2倍です。

nreaders_stress

共有ロック所有をストレスかけるカーネルスレッド数。デフォルトはライターロックと同じ数です。ユーザーがnwriters_stressを指定しなかった場合、ライダーアンドライターともオンラインCPUの数になります。

torture_type

拷問するロックの種類。デフォルトではスピンロックのみが拷問されます。このモジュールは以下のロックを拷問でき、文字列値は以下の通りです:

  • 「lock_busted」:

    バグのあるロック実装をシミュレートします。

  • 「spin_lock」:

    spin_lock()とspin_unlock()のペア。

  • 「spin_lock_irq」:

    spin_lock_irq()とspin_unlock_irq()のペア。

  • 「rw_lock」:

    read/write lock()とunlock()のrwlockペア。

  • 「rw_lock_irq」:

    read/write lock_irq()とunlock_irq()のrwlockペア。

  • 「mutex_lock」:

    mutex_lock() および mutex_unlock() ペアで使用します。

  • 「rtmutex_lock」:

    rtmutex_lock()とrtmutex_unlock()のペア。カーネルはCONFIG_RT_MUTEX=yを有効にする必要があります。

  • 「rwsem_lock」:

    read/write down()とup()セマフォペア。

拷問フレームワーク（RCU + ロック）¶

shutdown_secs

テストを終了してシステムをシャットダウンするまでの秒数。デフォルトはゼロで、テスト終了とシャットダウンを無効にします。これは自動テストに有用です。

onoff_interval

ランダムに選択されたCPUホットプラグ操作を実行する間に経過する秒数。デフォルトはゼロで、これによりCPUホットプラグが無効になります。CONFIG_HOTPLUG_CPU=nのカーネルでは、onoff_intervalの値に関係なくlocktortureが静かにCPUホットプラグ操作を実行しません。

onoff_holdoff

CPUホットプラグ操作を開始する前に待つ秒数。通常はロックトーチャーがカーネルに組み込まれて起動時に自動的に実行される場合にのみ使用されます。このパラメータはCONFIG_HOTPLUG_CPUが有効になっている場合にのみ役立ちます。

stat_interval

統計関連の秒数 printk()s. デフォルトではlocktortureは60秒ごとに統計を報告します。インターバルをゼロに設定すると、モジュールがアンロードされるときにのみ統計が表示されます。

stutter

テストを実行してからこの期間を待つ時間。デフォルトは「stutter=5」で、約5秒間隔で実行と一時停止を行います。「stutter=0」を指定すると、テストは連続して実行されます。

shuffle_interval

テストスレッドを特定のCPUサブセットにアフィニティを保持する秒数。デフォルトは3秒です。test_no_idle_hzと併用されます。

verbose

詳細なデバッグ出力を有効化、via printk(). デフォルトで有効です。この追加情報は主に高レベルのエラーおよびメインの『torture』フレームワークからのレポートに関連しています。

統計¶

統計は以下の形式で表示されます：

spin_lock-torture: Writes:  Total: 93746064  Max/Min: 0/0   Fail: 0
   (A)                    (B)            (C)            (D)          (E)

(A): Lock type that is being tortured -- torture_type parameter.

(B): Number of writer lock acquisitions. If dealing with a read/write
     primitive a second "Reads" statistics line is printed.

(C): Number of times the lock was acquired.

(D): Min and max number of times threads failed to acquire the lock.

(E): true/false values if there were errors acquiring the lock. This should
     -only- be positive if there is a bug in the locking primitive's
     implementation. Otherwise a lock should never fail (i.e., spin_lock()).
     Of course, the same applies for (C), above. A dummy example of this is
     the "lock_busted" type.

使い方¶

次のスクリプトを使用してロックをテストできます：

#!/bin/sh

modprobe locktorture
sleep 3600
rmmod locktorture
dmesg | grep torture:

出力結果は手動で「!!!」というエラーフラグを確認できます。もちろん、より複雑なスクリプトを作成してこのようなエラーを自動的に検出することも可能です。「rmmod」コマンドは「SUCCESS」「FAILURE」、または「RCU_HOTPLUG」のいずれかを強制的に表示します。 printk()ed. 最初の2つは自明ですが、最後のものはロック失敗がなかったにもかかわらずCPUホットプラグの問題が検出されたことを示します。

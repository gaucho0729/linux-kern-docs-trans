ミューテックスとは何ですか？¶

Linuxカーネルでは、ミューテックスとは共有メモリシステムでのシリアル化を強制する特定のロックプリミティブを指し、学術や理論的な教科書で見られる「相互排他」の一般的な用語を指すわけではありません。ミューテックスはスリープロックであり、バイナリセマフォのように動作し、2006年にこれらの代替として導入されました[1]。この新しいデータ構造は、よりシンプルなインターフェースや、当時のコードサイズの小ささ（詳細は「欠点」を参照）などの利点を提供しました。

[1] https://lwn.net/Articles/164802/

ハードロックアップ検出器は、定期的に実行されるhrtimerによって生成される割込みでウォッチドッグタスクを起動します。ハードロックアップの検出には、「watchdog_thresh」（コンパイル時に初期化され、sysctlの同じ名前で設定可能）秒ごとにNMI perfイベントが生成されます。システム内のどのCPUもその間hrtimer割込みを受けていない場合、ハードロックアップ検出器（NMI perfイベントのハンドラ）がカーネル警告を生成するか、設定に応じてパニックを呼び出します。¶

ミューテックスは「struct mutex」として表され、include/linux/mutex.hで定義され、kernel/locking/mutex.cで実装されています。これらのロックは、ロックのライフタイム中にロック状態を追跡するため、アトミック変数（->owner）を使用します。ownerフィールドは実際に struct task_struct * を現在のロック所有者に指し、現在所有されていない場合はNULLです。task_structポインタは少なくともL1_CACHE_BYTESでアライメントされているため、低ビット（3ビット）は待機リストが空でないなどの追加状態を保存するために使用されます。最も基本的な形式では、待機キューとアクセスをシリアル化するスピンロックも含みます。さらに、CONFIG_MUTEX_SPIN_ON_OWNER=yのシステムでは、以下で説明する(ii)に記載のspinner MCSロック（->osq）が使用されます。

ミューテックスを取得する際には、ロックの状態に応じて3つの可能なパスがあります：

  1. 高速パス：cmpxchg()を使用して現在のタスクでロックを原子的に取得しようと試みます。これは競合が起きない場合（cmpxchg()が0ULと比較するため、上記の3つの状態ビットがすべて0である必要があります）にのみ動作します。競合が起きている場合は次のパスに移行します。

  2. 中間パス：もしくは楽観的スピンと呼ばれる方法で、ロック所有者が実行中で他の優先度の高いタスクが待機していない場合にスピンして取得を試みます。理由は、ロック所有者が実行中であれば、すぐにロックを解放する可能性が高いからです。ミューテックススピンナーはMCSロックを使用してキューイングされ、同時に1つのスピンナーだけがミューテックスを競合するようにします。

    MCSロック（Mellor-CrummeyとScottによって提案）は、公平性を持ち、各CPUがローカル変数でロックを取得する試行を繰り返すシンプルなスピンロックです。これは、一般的なテストアンドセットスピンロック実装が引き起こすコストのかかるキャッシュラインのバウンスを回避します。MCSに類似したロックは、スリープ状態でのロック実装に最適化されています。カスタマイズされたMCSロックの重要な特徴は、スピンナーが再スケジューリングが必要な場合にMCSスピンロックキューから抜け出せるという追加の特性です。これにより、再スケジューリングが必要なMCSスピンナーがミューテックス所有者に待機し続けることなく、MCSロックを取得した後すぐにスローパスに移行する状況を回避できます。

  3. スローパス: ロックが取得できない場合、タスクは待機キューに追加され、アンロックパスによって起こされるまでスリープします。通常の状況ではTASK_UNINTERRUPTIBLEとしてブロックします。

形式的にはカーネルミューテックスはスリープ可能なロックですが、実際には（ii）の経路によりハイブリッド型とみなされます。タスクを中断せず、数サイクルだけビジー waits する代わりにすぐにスリープしないことで、このロックのパフォーマンスがいくつかのワークロードで大幅に向上することが観察されています。この技術はrwセマフォアにも使用されています。

セマンティクス¶

ミューテックスサブシステムが確認・強制するルールは以下の通りです:

  • 一度に1つのタスクしかミューテックスを保持できません。

  • ミューテックスをアンロックできるのは所有者だけです。

  • 複数のアンロックは許可されません。

  • 再入ロック/アンロックは許可されません。

  • ミューテックスはAPI（以下参照）を介してのみ初期化する必要があります。

  • タスクがミューテックスを保持しながら終了することはできません。

  • 保持中のロックが存在するメモリ領域は解放してはなりません。

  • 保持中のミューテックスは再初期化してはなりません。

  • タスケットやタイマなどのハードウェアまたはソフトウェア割込みコンテキストではミューテックスを使用してはなりません。

CONFIG DEBUG_MUTEXESが有効な場合、これらのセマンティクスが完全に強制されます。さらに、ミューテックスのデバッグコードはロックのデバッグをより簡単に・速くするためのいくつかの機能も実装しています:

  • デバッグ出力でミューテックスが表示される際には、記号名を使用します。

  • 取得位置の追跡、関数名の記号的な検索、システム内のすべてのロックのリスト、それらの表示。

  • 所有者追跡。

  • 自己再帰ロックを検出し、関連する情報を表示します。

  • マルチタスクの円環デッドロックを検出し、影響を受けたロックとタスク（およびそれらのタスクのみ）を表示します。

インターフェース¶

ミューテックスを静的に定義する:

DEFINE_MUTEX(name);

ミューテックスを動的に初期化する:

mutex_init(mutex);

ミューテックスを取得する（中断不能）:

void mutex_lock(struct mutex *lock);
void mutex_lock_nested(struct mutex *lock, unsigned int subclass);
int  mutex_trylock(struct mutex *lock);

中断可能でミューテックスを取得する:

int mutex_lock_interruptible_nested(struct mutex *lock,
                                    unsigned int subclass);
int mutex_lock_interruptible(struct mutex *lock);

カウンターが0になるまで待機して、中断可能でミューテックスを取得する:

int atomic_dec_and_mutex_lock(atomic_t *cnt, struct mutex *lock);

ミューテックスをアンロックする:

void mutex_unlock(struct mutex *lock);

ミューテックスがロックされているかをテストする:

int mutex_is_locked(struct mutex *lock);

欠点¶

‘struct mutex’は、元の設計目的とは異なり、カーネル内で最も大きなロックの一つです。例えばx86-64では32バイトで、‘struct semaphore’は24バイト、rw_semaphoreは4、40バイトです。構造体サイズが大きいほど、CPUキャッシュとメモリの使用量が増えるため、注意が必要です。

ミューテックスを使用するタイミング¶

mutexの厳密なセマンティクスが不適切で、またはクリティカルセクションがロックを共有できない場合を除き、他のロックプリミティブよりも常に選ぶべきです。

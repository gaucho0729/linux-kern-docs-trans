フェイクス再配置PI¶

非PIファutexからPIファutexへのタスクの再キューイングには、rt_mutexが待機中のタスクを持つ場合に所有者を常に保持する必要があるため、特別な処理が必要です。rt_mutexが所有者を失うと、PIの優先度上げロジックが破綻します[参照: rt-mutex-desgin.txt]。簡潔さのため、この動作はこのドキュメント全体で「requeue_pi」と呼ばれます。PIは常に「PI」と略します。

動機¶

requeue_piがなければ、glibcのpthread_cond_broadcast()実装は、pthread_condvarに待機中のタスクをすべて起こして、クラシックなサンダーハード形成でタスクがどの順序で実行するかを解決させることになります。理想的な実装では、最も高い優先度を持つ待機中のタスクを起こし、残りはcondvarに関連するミューテックスのアンロック時の自然なウェイクアップで処理します。

簡略化されたglibcの呼び出しを考慮してください:

/* caller must lock mutex */
pthread_cond_wait(cond, mutex)
{
        lock(cond->__data.__lock);
        unlock(mutex);
        do {
        unlock(cond->__data.__lock);
        futex_wait(cond->__data.__futex);
        lock(cond->__data.__lock);
        } while(...)
        unlock(cond->__data.__lock);
        lock(mutex);
}

pthread_cond_broadcast(cond)
{
        lock(cond->__data.__lock);
        unlock(cond->__data.__lock);
        futex_requeue(cond->data.__futex, cond->mutex);
}

pthread_cond_broadcast()がタスクを再キューイングした後、cond->mutexには待機中のタスクがあります。注意点として、pthread_cond_wait()はユーザー空間に戻った後でミューテックスのロックを試みます。これにより、rt_mutexには待機中のタスクが存在し、所有者がいない状態となり、前述したPI優先度上げアルゴリズムが破綻します。

PIを意識したpthread_condvarをサポートするため、カーネルはタスクをPIファutexに再キューイングする機能を備える必要があります。このサポートにより、futex_waitシステムコールが成功した場合、呼び出し元はユーザー空間に戻る時点でPIファutexを保持している必要があります。glibcの実装は以下のようになります:

/* caller must lock mutex */
pthread_cond_wait_pi(cond, mutex)
{
        lock(cond->__data.__lock);
        unlock(mutex);
        do {
        unlock(cond->__data.__lock);
        futex_wait_requeue_pi(cond->__data.__futex);
        lock(cond->__data.__lock);
        } while(...)
        unlock(cond->__data.__lock);
        /* the kernel acquired the mutex for us */
}

pthread_cond_broadcast_pi(cond)
{
        lock(cond->__data.__lock);
        unlock(cond->__data.__lock);
        futex_requeue_pi(cond->data.__futex, cond->mutex);
}

実際のglibc実装では、PIを検出しその必要に応じて既存の呼び出し内で変更を行うことが考えられます。同様の変更はpthread_cond_timedwait()およびpthread_cond_signal()にも必要です。

ハードロックアップ検出器は、定期的に実行されるhrtimerによって生成される割込みでウォッチドッグタスクを起動します。ハードロックアップの検出には、「watchdog_thresh」（コンパイル時に初期化され、sysctlの同じ名前で設定可能）秒ごとにNMI perfイベントが生成されます。システム内のどのCPUもその間hrtimer割込みを受けていない場合、ハードロックアップ検出器（NMI perfイベントのハンドラ）がカーネル警告を生成するか、設定に応じてパニックを呼び出します。¶

rt_mutexが待機中のタスクを持つ場合に所有者を確保するため、再キューイングコードおよび待機コードの両方がユーザー空間に戻る前にrt_mutexを取得できる必要があります。再キューイングコードは単に待機中のタスクを起こしてrt_mutexの取得を任せることはできません。再キューイング呼び出しがユーザー空間に戻るタイミングと待機中のタスクが起きて実行を開始するタイミングの間にレースコンディションが生じるからです。特に競合が発生しない場合にこれが顕著です。

この解決策には、2つの新しいrt_mutexの補助関数、rt_mutex_start_proxy_lock()とrt_mutex_finish_proxy_lock()が含まれており、これらは再割り当てコードが待機中のrt_mutexを代行して取得し、待機中のタスクを競合状態のrt_mutexに並び替える機能を提供します。2つの新しいシステムコールがrequeue_pi機能のカーネル<->ユーザーインターフェースを提供します:FUTEX_WAIT_REQUEUE_PIとFUTEX_CMP_REQUEUE_PI。

FUTEX_WAIT_REQUEUE_PIは待機中のタスク（pthread_cond_wait()とpthread_cond_timedwait()）が初期のfutexにブロックし、PI対応のfutexに再割り当てされるのを待つために呼び出されます。実装はfutex_wait()とfutex_lock_pi()の高速な衝突の結果であり、追加のウェイクアップシナリオをチェックするためのいくつかの追加ロジックが含まれています。

FUTEX_CMP_REQUEUE_PIは起動中のタスク（pthread_cond_broadcast()とpthread_cond_signal()）が待機中のタスクを再割り当ておよび可能であれば起動するためのシステムコールです。内部的にはこのシステムコールはfutex_requeue（requeue_pi=1を渡す形で）によって処理されます。再割り当て前に、 futex_requeue() 再割り当て対象のPI futexを待機中のトップタスクの代行で取得しようとします。取得できた場合、この待機中のタスクが起動されます。 futex_requeue() 次に、残りのnr_wake+nr_requeueタスクをPI futexに再割り当てを行い、各再割り当て前にrt_mutex_start_proxy_lock()を呼び出してタスクを下位のrt_mutexの待機者として準備します。この段階でロックが取得できた可能性もあります。その場合、次の待機中のタスクが起動され、ロックの取得を完了します。

FUTEX_CMP_REQUEUE_PIはnr_wakeとnr_requeueを引数として受け取りますが、その合計が実際に重要な要素です。 futex_requeue() nr_wake+nr_requeueタスクまで起動または再割り当てを行います。起動できるタスク数はロックを取得できるだけに限られ、ほとんどの場合、呼び出し元がpthread_cond_broadcast()またはpthread_cond_signal()を呼び出す前にミューテックスを取得するという良いプログラミングの慣習により0になります。FUTEX_CMP_REQUEUE_PIはnr_wake=1を必須とし、ブロードキャストの場合はnr_requeueをINT_MAXに、シグナルの場合は0に設定する必要があります。

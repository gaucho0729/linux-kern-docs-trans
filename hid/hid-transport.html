HID I/Oトランスポートドライバ¶

HIDサブシステムはトランスポートドライバーに依存しません。初期にはUSBのみがサポートされていましたが、他の規格もHID設計を採用し、新しいトランスポートドライバーを提供しています。カーネルには少なくともUSB、Bluetooth、I2Cおよびユーザー空間I/Oドライバーのサポートが含まれています。

1) HIDバス¶

HIDサブシステムはバスとして設計されています。どのI/OサブシステムもHIDデバイスを提供し、HIDバスに登録できます。HIDコアはこれに.genericデバイスドライバーをロードします。トランスポートドライバーは素データの転送とデバイスのセットアップ・管理を担当し、HIDコアはレポートのパース、解釈およびユーザー空間APIを担当します。デバイス固有の動作やクイックは、クイックに応じて各レイヤーで処理されます。

+-----------+  +-----------+            +-----------+  +-----------+
| Device #1 |  | Device #i |            | Device #j |  | Device #k |
+-----------+  +-----------+            +-----------+  +-----------+
         \\      //                              \\      //
       +------------+                          +------------+
       | I/O Driver |                          | I/O Driver |
       +------------+                          +------------+
             ||                                      ||
    +------------------+                    +------------------+
    | Transport Driver |                    | Transport Driver |
    +------------------+                    +------------------+
                      \___                ___/
                          \              /
                         +----------------+
                         |    HID Core    |
                         +----------------+
                          /  |        |  \
                         /   |        |   \
            ____________/    |        |    \_________________
           /                 |        |                      \
          /                  |        |                       \
+----------------+  +-----------+  +------------------+  +------------------+
| Generic Driver |  | MT Driver |  | Custom Driver #1 |  | Custom Driver #2 |
+----------------+  +-----------+  +------------------+  +------------------+

例:

  • I/O: USB, I2C, Bluetooth-l2cap

  • トランスポート: USB-HID, I2C-HID, BT-HIDP

このグラフでは「HIDコア」以下の部分はHIDデバイスドライバーのみに興味があるため、簡略化されています。トランスポートドライバーは具体的な詳細を知る必要はありません。

1.1) デバイスセットアップ¶

I/Oドライバーは通常、ホットプラグ検出またはデバイス列挙APIをトランスポートドライバーに提供します。トランスポートドライバーはこれを用いて適切なHIDデバイスを検出します。HIDデバイスオブジェクトを割り当ててHIDコアに登録します。トランスポートドライバーはHIDコアに自身を登録する必要はありません。HIDコアはどのトランスポートドライバーが利用可能かを把握せず、関心もありません。関心があるのはデバイスだけです。

トランスポートドライバーは各デバイスに定常的な「struct hid_ll_driver」オブジェクトをアタッチします。デバイスがHIDコアに登録されると、この構造体から提供されるコールバックがHIDコアがデバイスと通信するための手段となります。

トランスポートドライバーはデバイスの失敗や外付けを検出する責任があります。HIDコアはデバイスが登録されている限り動作を続けます。トランスポートドライバーが外付けや失敗イベントを検出すると、HIDコアからデバイスを登録解除し、HIDコアは提供されたコールバックを停止します。

1.2) トランスポートドライバーの要件¶

このドキュメントにおける「非同期」および「同期」の用語は、確認応答に関する送信動作を記述しています。非同期チャネルは、確認応答の待機や検証などの同期操作を実行してはいけません。一般的に、非同期チャネルで動作するHIDコールは、アトミックコンテキストで十分に動作します。一方、同期チャネルはトランスポートドライバーが好きに実装できます。これらは単に非同期チャネルと同じである場合もありますが、ブロッキング方式で確認応答レポートや失敗時の自動再送信などの機能も提供できます。このような機能が必要な場合、トランスポートドライバーは自身のワーカースレッドを通じて実装しなければなりません。

HIDコアはトランスポートドライバーが指定された設計に従うことを求めています。トランスポートドライバーは各HIDデバイスに対して2つの双方向I/Oチャネルを提供しなければなりません。ハードウェア自体が必ずしも双方向である必要はありません。トランスポートドライバーは単に4つの単方向チャネルを提供するだけでよいですし、あるいは4つのチャネルを1つの物理チャネルに多重化しても構いません。ただし、このドキュメントではこれらを2つの双方向チャネルとして説明します。なぜなら、これらにはいくつか共通する特性があるからです。

  • 割込みチャネル（intr）：intrチャネルは非同期データレポートの送受信に使用されます。このチャネルでは管理コマンドやデータ確認応答は送信されません。未承諾の入力または出力データレポートはこのチャネルで送信され、リモート側から確認されることはありません。デバイスは通常このチャネルで入力イベントを送信します。出力イベントは通常intrチャネルで送信されませんが、高スループットが必要な場合を除きます。

  • コントロールチャネル（ctrl）：ctrlチャネルは同期通信のリクエストやデバイス管理に使用されます。未承諾のデータ入力イベントはこのチャネルで送信されることはできず、通常無視されます。代わりに、デバイスはこのチャネルで管理イベントやホストリクエストへの応答のみを送信します。コントロールチャネルはintrチャネル上のイベントとは関係なく、デバイスへの直接的なブロッキングクエリに使用されます。出力レポートは通常、同期通信のSET_REPORTリクエストを通じてctrlチャネルで送信されます。

デバイスとHIDコア間の通信は主にHIDレポートを通じて行われます。レポートは次の3つのタイプのいずれかです：

  • INPUTレポート: INPUTレポートは、デバイスからホストへデータを送信します。このデータにはボタンイベント、軸イベント、バッテリー状態などが含まれる場合があります。このデータはデバイスが生成し、ホストへの明示的なリクエストが必要なくとも送信されます。デバイスは連続的にデータを送信するか、変化があったときにのみ送信するかを選択できます。

  • OUTPUTレポート: OUTPUTレポートはデバイスの状態を変更します。これらはホストからデバイスへ送信され、LEDリクエスト、振動リクエストなどが含まれる場合があります。OUTPUTレポートはデバイスからホストへ送信されることはありませんが、ホストは現在の状態を取得できます。ホストはOUTPUTレポートを連続的に送信するか、変化があったときにのみ送信するかを選択できます。

  • FEATUREレポート: FEATUREレポートは特定の静的なデバイス機能に使用され、自発的に送信されることはありません。ホストはバッテリー状態やデバイス設定などのデータにアクセスするため、これらを読み取りまたは書き込むことができます。FEATUREレポートは明示的なリクエストがないと送信されません。ホストはFEATUREレポートを明示的に設定または取得する必要があります。これにより、FEATUREレポートはintrチャネルで送信されることもありません。なぜなら、このチャネルは非同期的だからです。

INPUTおよびOUTPUTレポートはintrチャネルで純粋なデータレポートとして送信できます。INPUTレポートの場合これは通常の運用モードです。しかしOUTPUTレポートの場合、これはほとんど行われません。なぜならOUTPUTレポートは通常非常に少ないからです。ただし、デバイスは非同期的なOUTPUTレポートを過度に使用することができるため、例えばカスタムHIDオーディオスピーカーはこの機能をよく活用しています。

純粋なレポートはctrlチャネルで送信してはいけません。代わりに、ctrlチャネルは同期的なGET/SET_REPORTリクエストを提供します。純粋なレポートはintrチャネルでのみ許可され、そこでのデータ伝達の唯一の手段です。

  • GET_REPORT: GET_REPORTリクエストは、ホストからデバイスへ送信され、ペイロードにレポートIDを含みます。デバイスは、指定されたレポートIDに対応するデータレポートをコントロールチャネルで同期応答として返す必要があります。各デバイスに対して同時に1つのGET_REPORTリクエストのみが待機可能であり、この制限はHIDコアによって強制されます。複数の同時GET_REPORTリクエストを許可しない輸送ドライバが存在するためです。注意点として、GET_REPORTリクエストに対する応答として送信されるデータレポートは、一般的なデバイスイベントとして扱われません。つまり、デバイスが連続データレポートモードで動作していない場合、状態変化時にintrチャネル上のrawデータレポートを置き換えることはありません。GET_REPORTは、カスタムHIDドライバがデバイスの状態を照会する際にのみ使用されます。通常、HIDコアはデバイスの状態をキャッシュしているため、HID仕様に準拠するデバイスでは初期化時に現在の状態を取得する以外ではこのリクエストは必要ありません。GET_REPORTリクエストは3つのレポートタイプのいずれでも送信可能であり、デバイスの現在のレポート状態を返します。ただし、仕様に許可されていない場合、ペイロードとしてOUTPUTレポートがブロックされる可能性があります。

  • SET_REPORT: SET_REPORTリクエストは、レポートIDとデータをペイロードとして含み、ホストからデバイスへ送信されます。デバイスは、指定されたデータに応じて現在のレポート状態を更新する必要があります。3つのレポートタイプのいずれでも使用可能です。ただし、仕様に許可されていない場合、ペイロードとしてINPUTレポートがブロックされる可能性があります。デバイスは同期応答で応答する必要があります。ただし、HIDコアは輸送ドライバがこの応答をHIDコアに転送する必要があるとは限りません。GET_REPORTの場合と同様に、同時に1つのSET_REPORTリクエストのみが待機可能です。この制限はHIDコアによって強制され、一部の輸送ドライバが複数の同期SET_REPORTリクエストをサポートしないからです。

USB-HIDは他の輸送レベル仕様では利用不可（または非推奨）であるが、コントロールチャネルのその他のリクエストをサポートしています：

  • GET/SET_IDLE: USB-HIDおよびI2C-HIDのみで使用されます。

  • GET/SET_PROTOCOL: HIDコアでは使用されません。

  • RESET: I2C-HIDで使用され、HIDコアには接続されていません。

  • SET_POWER: I2C-HIDで使用され、HIDコアには接続されていません。

2) HID API¶

2.1) 初期化¶

輸送ドライバは通常、HIDコアに新しいデバイスを登録する際には以下の手順を使用します：

struct hid_device *hid;
int ret;

hid = hid_allocate_device();
if (IS_ERR(hid)) {
        ret = PTR_ERR(hid);
        goto err_<...>;
}

strscpy(hid->name, <device-name-src>, sizeof(hid->name));
strscpy(hid->phys, <device-phys-src>, sizeof(hid->phys));
strscpy(hid->uniq, <device-uniq-src>, sizeof(hid->uniq));

hid->ll_driver = &custom_ll_driver;
hid->bus = <device-bus>;
hid->vendor = <device-vendor>;
hid->product = <device-product>;
hid->version = <device-version>;
hid->country = <device-country>;
hid->dev.parent = <pointer-to-parent-device>;
hid->driver_data = <transport-driver-data-field>;

ret = hid_add_device(hid);
if (ret)
        goto err_<...>;

hid_add_device()が呼ばれると、HIDコアは「custom_ll_driver」で提供されたコールバックを使用する可能性があります。注意してください。「country」などのフィールドは、サポートされていない場合、下位のトランスポートドライバによって無視されることがあります。

デバイスをアンレジストレッドするには、次のコマンドを使用してください:

hid_destroy_device(hid);

hid_destroy_device()が返る後、HIDコアはドライバのコールバックを一切使用しなくなります。

2.2) hid_ll_driver操作¶

利用可能なHIDコールバックは以下の通りです:

int (*start) (struct hid_device *hdev)

HIDデバイスドライバがデバイスを使用したいときに呼び出されます。トランスポートドライバはこのコールバックでデバイスの設定を行うことができます。ただし、通常、トランスポートドライバがHIDコアに登録する前にデバイスはすでに設定済みなので、これは主にUSB-HIDで使用されます。

void (*stop) (struct hid_device *hdev)

HIDデバイスドライバがデバイスの使用を終えたときに呼び出されます。トランスポートドライバはバッファを解放し、デバイスの初期化を解除できます。ただし、->start() 別のHIDデバイスドライバがデバイスにロードされた場合、再度呼び出される可能性があります。

トランスポートドライバはこれを無視して、hid_destroy_device()で破壊した後でデバイスを初期化解除できます。

int (*open) (struct hid_device *hdev)

HIDデバイスドライバがデータレポートに興味があるときに呼び出されます。通常、ユーザー空間が入力API/etc.を開いていない場合、デバイスドライバはデバイスデータに興味を持たず、トランスポートドライバはデバイスをスリープ状態にできます。ただし、->open()が呼び出されると、トランスポートドライバはI/Oに備える必要があります。->open()はHIDデバイスを開く各クライアントごとにネストされます。

void (*close) (struct hid_device *hdev)

->open()が呼び出された後でデバイスドライバがもはやデバイスレポートに興味を持たなくなったときに呼び出されます。(通常、ユーザー空間がドライバの入力デバイスを閉じた場合)

トランスポートドライバはデバイスをスリープ状態にし、すべての->open()呼び出しが->close()呼び出しされた後にすべてのI/Oを終了できます。ただし、->start() デバイスドライバが再び入力レポートに興味を持つ場合、再度呼び出される可能性があります。

int (*parse) (struct hid_device *hdev)

->が呼び出された後、デバイスの設定中に一度呼び出されます。start() トランスポートドライバはデバイスからHIDレポート記述子を読み取り、hid_parse_report()を通じてHIDコアに通知する必要があります。

int (*power) (struct hid_device *hdev, int level)

HIDコアがトランスポートドライバにPMヒントを提供するために呼び出されます。通常、これは->open()と->close()のヒントに類似しており、冗長です。

void (*request) (struct hid_device *hdev, struct hid_report *report,
                 int reqtype)

コントロールチャネルでHIDリクエストを送信します。「report」には送信するレポートが含まれており、「reqtype」にはリクエストタイプが指定されます。リクエストタイプはHID_REQ_SET_REPORTまたはHID_REQ_GET_REPORTのいずれかです。

このコールバックはオプションです。提供されていない場合、HIDコアはHID仕様に従ってrawレポートを組み立て、->raw_request()コールバックを通じて送信します。トランスポートドライバはこれを非同期に実装できます。

int (*wait) (struct hid_device *hdev)

HIDコアが->request()を再度呼び出す前に使用されます。トランスポートドライバーは、同時に1つのリクエストのみを許可する場合、待機リクエストが完了するのを待つためにこれを使用できます。

int (*raw_request) (struct hid_device *hdev, unsigned char reportnum,
                    __u8 *buf, size_t count, unsigned char rtype,
                    int reqtype)

->request()と同じですが、レポートをrawバッファとして提供します。このリクエストは同期処理でなければなりません。トランスポートドライバーはこのようなリクエストを完了するために->wait()を使用してはなりません。このリクエストは必須であり、hidコアはこのリクエストが存在しない場合、デバイスを拒否します。

int (*output_report) (struct hid_device *hdev, __u8 *buf, size_t len)

intrチャネルを介してraw出力レポートを送信します。一部のHIDデバイスドライバーがintrチャネルでの出力リクエストに高スループットを必要とするため、これを使用します。SET_REPORTコールを引き起こしてはなりません！これはintrチャネルでの非同期出力レポートとして実装しなければなりません！

int (*idle) (struct hid_device *hdev, int report, int idle, int reqtype)

SET/GET_IDLEリクエストを実行します。USB-HID専用で、実装しないでください！

2.3) データパス¶

トランスポートドライバーはI/Oデバイスからデータを読み取る責任があります。I/O関連の状態追跡はドライバー自身が処理しなければなりません。HIDコアは、指定されたHIDトランスポート仕様で必要なプロトコルハンドシェイクやその他の管理コマンドを実装しません。

デバイスから読み取ったすべてのrawデータパケットはhid_input_report()を介してHIDコアに送信しなければなりません。チャネルタイプ（intrまたはctrl）とレポートタイプ（入力/出力/機能）を指定しなければなりません。通常の状況では、このAPIを通じて提供されるのは入力レポートのみです。

->request()を介してGET_REPORTリクエストに対する応答もこのAPIを通じて提供しなければなりません。->raw_request()に対する応答は同期処理であり、トランスポートドライバーが捕捉し、hid_input_report()に渡すことはできません。SET_REPORTリクエストに対する応答はHIDコアには関心がありません。

UHID - HIDサブシステム用ユーザースペースI/Oドライバサポート¶

UHIDは、ユーザースペースでHIDトランスポートドライバを実装するための仕組みです。HIDトランスポートドライバについての導入はhid-transport.txtをご参照ください。このドキュメントはその定義に大きく依存しています。

UHIDにより、ユーザースペース制御のバスに接続された各デバイスに対してカーネルのhidデバイスを生成できます。UHID APIは、カーネルからユーザースペースへのI/Oイベントおよび逆にユーザースペースからカーネルへのI/Oイベントを定義しています。

例として、./samples/uhid/uhid-example.cにユーザースペースアプリケーションがあります

UHID API¶

UHIDはキャラクターミスチップデバイスを通じてアクセスされます。マイナーナンバーは動的に割り当てられるため、udev（または類似のツール）に依存してデバイスノードを生成する必要があります。デフォルトでは/dev/uhidです。

新しいデバイスがHID I/Oドライバによって検出され、HIDサブシステムに登録する必要がある場合、登録する各デバイスに対して/dev/uhidを開く必要があります。以降の通信はすべてread()またはwrite()でstruct uhid_eventオブジェクトを処理します。非ブロッキング操作はO_NONBLOCKを設定することでサポートされます。

struct uhid_event {
      __u32 type;
      union {
              struct uhid_create2_req create2;
              struct uhid_output_req output;
              struct uhid_input2_req input2;
              ...
      } u;
};

「type」フィールドにはイベントのIDが含まれています。IDによって異なるペイロードが送信されます。単一のイベントは複数のread()またはwrite()に分割してはいけません。常に1つのイベントとして送信する必要があります。さらに、read()またはwrite()ごとに1つのイベントのみを送信できます。待機中のデータは無視されます。複数のイベントを1つのシステムコールで処理する場合は、readv()/writev()によるベクタI/Oを使用してください。「type」フィールドでペイロードを指定します。各typeには、ユニオン「u」内のペイロード構造体が用意されています（空のペイロードを除く）。このペイロードには管理情報および/またはデバイスデータが含まれます。

最初に行うべきことは、UHID_CREATE2イベントを送信することです。これによりデバイスが登録されます。UHIDはUHID_STARTイベントで応答します。これでデータをUHIDに送信し、UHIDからデータを読み取る作業を開始できます。ただし、UHIDがUHID_OPENイベントを送信しない限り、内部的に接続されているHIDデバイスドライバにはユーザーが接続されていないため、デバイスがスリープ状態になる可能性があります。UHID_OPENイベントを受信した場合は、I/Oを開始する必要があります。最後のユーザーがHIDデバイスを閉じると、UHID_CLOSEイベントを受信します。その後、再度UHID_OPENイベントが送信される可能性があります。ユーザー空間で参照カウントを管理する必要はありません。つまり、UHID_CLOSEイベントが発生しない限り、複数のUHID_OPENイベントを受信することはありません。HIDサブシステムが参照カウントを管理します。UHID_OPEN/UHID_CLOSEイベントを無視することも可能です。デバイスにユーザーがいない場合でもI/Oは許可されます。

HIDサブシステムに割り込みチャネルでデータを送信したい場合は、rawデータペイロードを含むHID_INPUT2イベントを送信します。逆に、カーネルが割り込みチャネルでデバイスにデータを送信したい場合は、UHID_OUTPUTイベントを読み取る必要があります。現在、コントロールチャネルでのデータリクエストはGET_REPORTとSET_REPORTに限定されており、他のデータレポートは未定義です。これらのリクエストは常に同期処理です。つまり、カーネルがUHID_GET_REPORTやUHID_SET_REPORTイベントを送信し、これらをコントロールチャネルでデバイスに転送する必要があります。デバイスが応答した後、UHID_GET_REPORT_REPLYとUHID_SET_REPORT_REPLYを介してカーネルに応答を転送しなければなりません。カーネルはこのようなラウンドトリップ中（ハードコードされた期間後にタイムアウト）に内部ドライバの実行をブロックします。

デバイスが切断した場合は、UHID_DESTROYイベントを送信してください。これによりデバイスが登録解除されます。これで再度UHID_CREATE2を送信して新しいデバイスを登録できます。fdをclose()した場合、デバイスは自動的に登録解除され内部的に破壊されます。

write()¶

write()はデバイスの状態を変更し、カーネルに入力データを供給できます。カーネルはイベントを即座に解析し、イベントIDがサポートされていない場合は-EOPNOTSUPPを返します。ペイロードが無効な場合は-EINVALを返します。それ以外の場合は、読み取ったデータ量を返し、リクエストが成功しました。O_NONBLOCKはwrite()に影響を与えません。なぜなら、write()は常に非ブロッキングモードで即座に処理されるからです。今後、O_NONBLOCKがリクエスト処理に利用される可能性があります。

UHID_CREATE2:

これは内部のHIDデバイスを作成します。このイベントをカーネルに送信するまで、入出力操作はできません。ペイロードはstruct uhid_create2_req型で、デバイスに関する情報を含みます。これで入出力操作を開始できます。

UHID_DESTROY:

これは内部のHIDデバイスを破壊します。これ以降の入出力操作は受け付けません。未処理のメッセージがまだある可能性があり、read()で受信できますが、これ以降のUHID_INPUTイベントをカーネルに送信することはできません。新しいデバイスを作成するには再度UHID_CREATE2を送信してください。キャラクタデバイスを再オープンする必要はありません。

UHID_INPUT2:

カーネルに入力データを送信する前にUHID_CREATE2を必ず送信してください。このイベントはデータペイロードを含みます。これは割り込みチャネルからデバイスから読み取る素データです。カーネルがHIDレポートを解析します。

UHID_GET_REPORT_REPLY:

UHID_GET_REPORTリクエストを受信した場合は、このリクエストで応答してください。リクエストの「id」フィールドを応答の「id」フィールドにコピーしてください。「err」フィールドはエラーが発生しなかった場合は0、I/Oエラーが発生した場合はEIOを設定してください。「err」が0の場合は、応答のバッファにGET_REPORTリクエストの結果を書き込み、「size」をそれに合わせて設定してください。

UHID_SET_REPORT_REPLY:

これはUHID_GET_REPORT_REPLYのSET_REPORT相当です。GET_REPORTとは異なり、SET_REPORTはデータバッファを返しません。そのため、「id」および「err」フィールドを正しく設定するだけで十分です。

read()¶

read()はキューイングされた出力レポートを返します。これらに対して特に反応する必要はありませんが、必要に応じて処理してください。

UHID_START:

HIDデバイスが起動したときに送信されます。これはUHID_CREATE2への応答として考えることができます。常に最初に送信されるイベントです。注意点として、write(UHID_CREATE2)が返る直後にこのイベントが必ず送信されるとは限りません。ドライバは遅延されたセットアップを必要とする場合があります。このイベントのペイロードはuhid_start_req型で、「dev_flags」フィールドはデバイスの特殊な動作を記述します。以下のフラグが定義されています：

  • UHID_DEV_NUMBERED_FEATURE_REPORTS

  • UHID_DEV_NUMBERED_OUTPUT_REPORTS

  • UHID_DEV_NUMBERED_INPUT_REPORTS

    これらのフラグは、それぞれのレポートタイプが番号付きレポートを使用するかどうかを定義します。番号付きレポートが使用されるタイプの場合、カーネルから送信されるすべてのメッセージにはレポート番号がプレフィックスとして付加されます。それ以外の場合は、カーネルがプレフィックスを追加しません。ユーザー空間からカーネルに送信するメッセージでは、これらのフラグに応じてプレフィックスを調整する必要があります。

UHID_STOP:

HIDデバイスが停止したときに送信されます。これはUHID_DESTROYへの応答として考えることができます。

UHID_DESTROYでデバイスを破壊しなかった場合でも、カーネルがUHID_STOPイベントを送信した場合は通常無視してください。これはカーネルがHIDデバイスにロードされたドライバを再ロード/変更した（または他のメンテナンス作業が行われた）ことを意味します。

UHID_STOPイベントは通常安全に無視できます。

UHID_OPEN:

これはHIDデバイスが開かれたときに送信されます。つまり、HIDデバイスが提供するデータが他のプロセスによって読み取られている状態です。このイベントは無視しても問題ありませんが、電源管理に有用です。UHID_OPENイベントを受信していない限り、他のプロセスがデータを読み取っていませんので、UHID_INPUT2イベントをカーネルに送信する必要はありません。

UHID_CLOSE:

これにより、HIDデータを読み取るプロセスがもう存在しないことを示します。これはUHID_OPENの対応イベントであり、このイベントも無視しても問題ありません。

UHID_OUTPUT:

HIDドライバが割込みチャネルを通じてI/Oデバイスにrawデータを送信したい場合に送信されます。ペイロードを読み取り、デバイスに転送する必要があります。ペイロードは「struct uhid_output_req」型です。UHID_OPENイベントを受信していない場合でもこのイベントを受信する可能性があります。

UHID_GET_REPORT:

カーネルドライバがHID仕様で定義されたコントロールチャネルでのGET_REPORTリクエストを実行する場合に送信されます。レポートタイプとレポート番号はペイロードに含まれています。カーネルはGET_REPORTリクエストをシリアル化するため、同時に複数のリクエストは発生しません。ただし、UHID_GET_REPORT_REPLYで応答しなかった場合、リクエストは静かにタイムアウトする可能性があります。GET_REPORTリクエストを読み取った後は、HIDデバイスに転送し、ペイロードの「id」フィールドを記憶してください。HIDデバイスがGET_REPORTに応答した（または失敗した）後、リクエストに使われた「id」と同じ値を用いてUHID_GET_REPORT_REPLYをカーネルに送信する必要があります。リクエストがすでにタイムアウトしていた場合、カーネルは応答を無視します。「id」フィールドは再利用されないため、競合が発生しません。

UHID_SET_REPORT:

これはUHID_GET_REPORTのSET_REPORT相当です。受信時にHIDデバイスにSET_REPORTリクエストを送信してください。応答後はUHID_SET_REPORT_REPLYを通じてカーネルに結果を報告してください。UHID_GET_REPORTと同様の制限が適用されます。

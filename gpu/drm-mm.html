DRMメモリ管理¶

現代のLinuxシステムは、フレームバッファ、テクスチャ、頂点などグラフィック関連データを格納するために大容量のグラフィックメモリを必要とします。このようなデータの非常に動的な性質を考慮すると、グラフィックスタックにおいてグラフィックメモリを効率的に管理することは極めて重要であり、DRMインフラストラクチャにおいて中心的な役割を果たしています。

DRMコアには、翻訳テーブルマップ（TTM）とグラフィック実行マネージャー（GEM）という2つのメモリマネージャーが含まれています。TTMは最初に開発されたDRMメモリマネージャーであり、一括解決策を試みたものです。これはすべてのハードウェアのニーズに対応するための単一ユーザースペースAPIを提供し、統合メモリアーキテクチャ（UMA）デバイスおよび専用ビデオRAMを持つデバイス（つまり、ほとんどのディスクリートビデオカード）をサポートします。これにより、非常に複雑なコードとなり、ドライバ開発において使いにくくなるという問題が生じました。

GEMはTTMの複雑さへの反応としてインテルが支援するプロジェクトとして開始されました。設計哲学は完全に異なり、すべてのグラフィックメモリ関連の問題に一括して対応するのではなく、ドライバ間で共通するコードを特定し、サポートライブラリとして共有するというアプローチを採用しました。GEMはTTMよりも初期化および実行要件がシンプルですが、ビデオRAM管理機能を持たず、UMAデバイスに限定されます。

翻訳テーブルマネージャー（TTM）¶

TTMの設計背景および情報はここに記載されます。

TTM初期化¶

警告 このセクションは非推奨です。

TTMをサポートするドライバは、埋められた構造体をttm_bo_device_initに渡す必要があります。 ttm_bo_driver 構造体をttm_bo_device_initに渡すとともに、メモリマネージャーのグローバルな参照を初期化したものを一緒に渡します。ttm_bo_driver構造体には、TTMの初期化、メモリの割り当ておよび解放、コマンド完了の待機およびフェンス同期、メモリの移動に関連する関数ポインタを持つ複数のフィールドが含まれています。

以下の struct drm_global_reference はいくつかのフィールドから構成されています:

struct drm_global_reference {
        enum ttm_global_types global_type;
        size_t size;
        void *object;
        int (*init) (struct drm_global_reference *);
        void (*release) (struct drm_global_reference *);
};

あなたのメモリマネージャー全体に1つのグローバルな参照構造体が必要であり、メモリマネージャーが実行時において作成する各オブジェクトごとに他の構造体も必要です。あなたのグローバルTTMはTTM_GLOBAL_TTM_MEMタイプでなければなりません。グローバルオブジェクトのサイズフィールドはsizeof(struct ttm_mem_global)でなければなりません。初期化と解放のハンドラーは、ドライバ固有の初期化および解放ルーチンをそれぞれ指さなければなりません。これらは最終的にttm_mem_global_initおよびttm_mem_global_releaseを呼び出す可能性があります。

グローバルなTTMアカウント構造がttm_global_item_ref()を呼び出して設定され初期化されると、クライアントおよびカーネル自身がバッファーオブジェクトを割り当てられるプールを提供するバッファーオブジェクトTTMを作成する必要があります。このオブジェクトの型はTTM_GLOBAL_TTM_BOでなければならず、サイズはsizeof(struct ttm_bo_global)に設定する必要があります。また、ドライバ固有の初期化および解放関数が提供される可能性があり、最終的にはttm_bo_global_ref_init()とttm_bo_global_ref_release()をそれぞれ呼び出すことが予想されます。また、前のオブジェクトと同様に、ttm_global_item_ref()はTTMの初期参照カウントを作成するために使用され、これによりあなたの初期化関数が呼び出されます。

使用例についてはradeon_ttm.cファイルを参照してください。

グラフィックス実行マネージャー (GEM)¶

GEMの設計アプローチにより、ユーザー空間またはカーネルAPIにおいてすべて（あるいはすべての一般的な）使用ケースを完全にカバーするメモリマネージャーが実現されています。GEMはユーザー空間に標準的なメモリ関連操作を、ドライバにヘルパ関数を提供し、ドライバが独自のプライベートAPIを使用してハードウェア固有の操作を実装できるようにしています。

GEMユーザー空間APIは以下の GEM - グラフィックス実行マネージャー LWNの記事で説明されています。やや古くなったものの、ドキュメントはGEM APIの原則について良い概要を提供しています。バッファーアロケーションおよび読み取り・書き込み操作は、一般的なGEM APIとして説明されているものの、現在はドライバ固有のioctlを使用して実装されています。

GEMはデータに依存しません。個々のバッファーオブジェクトが何を含んでいるかを知らないまま、抽象的なバッファーオブジェクトを管理します。バッファーオブジェクトの割り当てや同期プリミティブなど、バッファーコンテンツや目的に関する知識を必要とするAPIは、GEMの範囲外であり、ドライバ固有のioctlを使用して実装する必要があります。

根本的なレベルでは、GEMには以下の操作が含まれます:

  • メモリの割り当てと解放

  • コマンドの実行

  • コマンド実行時のアペルチャー管理

バッファーオブジェクトの割り当ては比較的簡単で、主にLinuxのshmemレイヤーによって提供されるため、各オブジェクトにメモリを割り当てる機能が備わっています。

コマンド実行、ピンニング、バッファーリード＆ライト、マッピング、ドメイン所有権の転送などのデバイス固有の操作は、ドライバ固有のioctlに委譲されます。

GEM初期化¶

GEMを使用するドライバでは、struct struct drm_driver driver_features フィールド。DRMコアはその後、ロード操作を呼び出す前にGEMコアを自動的に初期化します。裏で、これはDRMメモリマネージャーオブジェクトを作成し、オブジェクトの割り当てに必要なアドレス空間プールを提供します。

KMS構成では、ハードウェアによって必要とされる場合、ドライバはコアGEM初期化後にコマンドリングバッファを割り当てて初期化する必要があります。UMAデバイスは通常、「stolen」メモリ領域と呼ばれる領域を持ち、これは初期フレームバッファとデバイスが必要とする大容量の連続メモリ領域を提供します。この領域は通常GEMによって管理されず、独自のDRM MMオブジェクトに別途初期化する必要があります。

GEMオブジェクトの作成¶

GEMはGEMオブジェクトの作成と、それらを裏付けるメモリの割り当てを2つの異なる操作に分離します。

GEMオブジェクトはstructのインスタンスで表されます。 struct drm_gem_object。ドライバは通常、プライベート情報でGEMオブジェクトを拡張する必要があり、そのためドライバ固有のGEMオブジェクト構造体タイプを作成し、structのインスタンスを埋め込む必要があります。 struct drm_gem_object.

GEMオブジェクトを作成するには、ドライバは自身の特定のGEMオブジェクトタイプのインスタンスのメモリを割り当て、埋め込まれたstructを初期化します。 struct drm_gem_object callを介して drm_gem_object_init(). この関数は、DRMデバイスへのポインタ、GEMオブジェクトへのポインタ、およびバッファオブジェクトのバイト数を引数として受け取ります。

GEMはshmemを使用して匿名ページ可能メモリを割り当てます。 drm_gem_object_init() 要求されたサイズのshmfsファイルを作成し、struct filpフィールドに保存します。 struct drm_gem_object このメモリは、グラフィックスハードウェアがシステムメモリを直接使用する場合のオブジェクトの主なストレージとして、またはそれ以外の場合はバックイングストレージとして使用されます。

ドライバーは、各ページに対してshmem_read_mapping_page_gfp()を呼び出して、実際の物理ページの割り当てを担当します。注意点として、ドライバーはGEMオブジェクトの初期化時にページを割り当てるか、メモリが必要になるまで（たとえばユーザー空間メモリアクセスによるページフォルトが発生する場合や、ドライバーがDMA転送を開始する際に）割り当てを延期することもできます。

匿名ページ可能メモリの割り当ては常に望ましいわけではありません。たとえば、ハードウェアが物理的に連続したシステムメモリを必要とする場合（これはエミベッドデバイスでよく見られるケース）があります。ドライバーは、shmem_read_mapping_page_gfp()の呼び出しによって、shmfsのバックイングを持たないGEMオブジェクト（プライベートGEMオブジェクトと呼ばれます）を作成できます。 drm_gem_private_object_init() …の代わりに drm_gem_object_init(). プライベートGEMオブジェクトのストレージはドライバーによって管理される必要があります。

すべてのGEMオブジェクトはGEMコアによって参照カウントされます。参照は、呼び出しによって取得および解放できます。 drm_gem_object_get() および drm_gem_object_put() それぞれに保存されます

GEMオブジェクトへの最後の参照が解放された際、GEMコアはgem_free_object_unlocked操作を呼び出します。 struct drm_driver この操作はGEMを有効化したドライバにとって必須であり、GEMオブジェクトおよびすべての関連リソースを解放する必要があります。

GEMオブジェクトの命名¶

ユーザースペースとカーネル間の通信では、GEMオブジェクトをローカルハンドル、グローバル名、または最近ではファイル記述子を使用して参照します。これらすべては32ビットの整数値であり、ファイル記述子には通常のLinuxカーネルの制限が適用されます。

GEMハンドルはDRMファイルに固有です。アプリケーションはドライバ固有のioctlを通じてGEMオブジェクトのハンドルを取得し、そのハンドルを使用して他の標準的またはドライバ固有のioctlでGEMオブジェクトを参照できます。DRMファイルハンドルを閉じることで、すべてのGEMハンドルが解放され、関連するGEMオブジェクトの参照が解除されます。

GEMオブジェクトのハンドルを作成するには、ドライバが drm_gem_handle_create(). この関数はDRMファイルへのポインタとGEMオブジェクトを受け取り、ローカルに一意なハンドルを返します。ハンドルがもはや必要なくなった場合、ドライバは drm_gem_handle_delete(). でハンドルを削除します。最後に、ハンドルに関連するGEMオブジェクトは drm_gem_object_lookup().

で取得できます。ハンドルはGEMオブジェクトの所有権を取得せず、オブジェクトへの参照のみを取得します。ハンドルが破棄されるときに参照が解除されます。GEMオブジェクトのリークを防ぐため、ドライバは所有する参照（例えばオブジェクト作成時の初期参照）を適切に解除する必要があります。ハンドルの処理において特別な考慮は不要です。例えば、dumb_create操作の実装におけるGEMオブジェクトとハンドルの組み合わせ作成の場合、ドライバはハンドルを返す前にGEMオブジェクトの初期参照を解除する必要があります。

GEM名はハンドルと同様の目的を持ちますが、DRMファイルに局所的ではありません。プロセス間でGEMオブジェクトをグローバルに参照するために使用できます。名前はDRM API内のオブジェクトを直接参照することはできません。アプリケーションはDRM_IOCTL_GEM_FLINKとDRM_IOCTL_GEM_OPEN ioctlsをそれぞれ使用してハンドルを名前に、名前をハンドルに変換する必要があります。この変換はDRMコアによって処理され、ドライバ固有のサポートは不要です。

GEMは、PRIMEを通じてdma-bufファイルディスクリプタを介したバッファ共有もサポートしています。GEMベースのドライバは、エクスポートおよびインポートを正しく実装するため、提供されたヘルパ関数を使用する必要があります。参照: ?. ファイルディスクリプタの共有は、簡単に推測可能でグローバルなGEM名よりも本質的にセキュアであるため、バッファ共有メカニズムとして優先されます。GEM名を介したバッファ共有は、レガシユーザースペースにのみサポートされています。さらに、PRIMEはdma-bufsに基づくため、クロスデバイスのバッファ共有も可能にします。

GEMオブジェクトのマッピング¶

マッピング操作は比較的重い操作であるため、GEMはバッファへの読み書きのようなアクセスをドライバ固有のioctlを通じて実装する方法を好んでいます。ただし、バッファへのランダムアクセスが必要な場合（例：ソフトウェアレンダリングを行う場合など）、オブジェクトへの直接アクセスの方が効率的です。

mmapシステムコールを直接使ってGEMオブジェクトをマッピングすることはできません。なぜなら、GEMオブジェクトには独自のファイルハンドルがないからです。現在、GEMオブジェクトをユーザースペースにマッピングするための2つの代替方法が共存しています。1つ目の方法は、ドライバ固有のioctlを用いてマッピング操作を行い、内部ではdo_mmap()を呼び出す方法です。これはしばしば疑わしいとされており、新規のGEM対応ドライバには推奨されておらず、ここでは説明しません。

2つ目の方法は、DRMファイルハンドル上でmmapシステムコールを使用します。void *mmap(void *addr, size_t length, int prot, int flags, int fd, off_t offset); DRMはmmapオフセット引数を通じて渡された仮のオフセットをもとにGEMオブジェクトを特定します。マッピングされる前に、GEMオブジェクトは仮のオフセットと関連付けられる必要があります。そのため、ドライバは drm_gem_create_mmap_offset() オブジェクトに対して呼び出す必要があります。

割り当てられると、仮のオフセット値はドライバ固有の方法でアプリケーションに渡され、その後、mmapオフセット引数として使用できます。

GEMコアはオブジェクトマッピングを処理するヘルパー関数を提供しています。 drm_gem_mmap() をオブジェクトマッピングに使用できます。この関数は直接mmapファイル操作ハンドラとして設定できます。この関数はオフセット値をもとにGEMオブジェクトを検索し、VMA操作を struct drm_driver gem_vm_ops フィールド。ご注意ください drm_gem_mmap() メモリをユーザースペースにマッピングしないで、ドライバが提供するフォールトハンドラに個別にページをマッピングを依存しています

使用するには drm_gem_mmap()ドライバは構造体を埋める必要があります struct drm_driver gem_vm_ops フィールドに VM操作へのポインタを設定する必要があります

VM操作は struct vm_operations_struct 複数のフィールドから構成され、特に注目すべきものは以下の通りです

struct vm_operations_struct {
        void (*open)(struct vm_area_struct * area);
        void (*close)(struct vm_area_struct * area);
        vm_fault_t (*fault)(struct vm_fault *vmf);
};

オープンとクローズ操作はGEMオブジェクトの参照カウントを更新する必要があります。ドライバは以下のヘルパー関数を直接使用してオープンとクローズハンドラとして利用できます drm_gem_vm_open() および drm_gem_vm_close() ヘルパー関数を直接使用してオープンとクローズハンドラとして利用できます

ページフォールトが発生した際に、個々のページをユーザー空間にマッピングする責任は、フォールト操作ハンドラが担います。メモリ割当スキームに応じて、ドライバはフォールト発生時にページを割当てるか、またはGEMオブジェクトのメモリをオブジェクト作成時に割当てるかを決定できます。

GEMオブジェクトをフォールト処理ではなく事前にマッピングしたいドライバは、独自のmmapファイル操作ハンドラを実装できます。

MMUを持たないプラットフォームでは、GEMコアがヘルパーメソッドを提供します drm_gem_cma_get_unmapped_area()。mmap()ルーチンはこのメソッドを呼び出して、マッピングの提案されたアドレスを取得します。

使用するには drm_gem_cma_get_unmapped_area()ドライバは構造体を埋める必要があります struct file_operations get_unmapped_areaフィールドにポインタを指定して drm_gem_cma_get_unmapped_area().

Memory Coherency¶

デバイスまたはコマンドバッファでマッピングされた場合、オブジェクトのバックイングページはメモリにフラッシュされ、ライトコンビネッドとしてマークされるため、GPUとコヒーレントになります。同様に、GPUがオブジェクトへのレンダリングを完了した後、CPUがオブジェクトにアクセスする場合、オブジェクトはCPUのメモリビューとコヒーレントにする必要があります。これは通常、GPUキャッシュのフラッシュなどの操作を伴います。このコアなCPU<->GPUのコヒーレンス管理は、デバイス固有のioctlによって提供され、オブジェクトの現在のドメインを評価し、必要なフラッシュや同期を実行してオブジェクトを目的のコヒーレンスドメインに配置します（注意：オブジェクトがビジー状態である可能性があります、つまりアクティブなレンダーターゲットである場合、ドメインの設定はクライアントをブロックし、レンダリング完了を待ってから必要なフラッシュ操作を実行します）。

コマンド実行¶

GPUデバイスにおいて最も重要なGEM機能は、クライアントにコマンド実行インターフェースを提供することです。クライアントプログラムは、事前に割り当てられたメモリオブジェクトへの参照を含むコマンドバッファを構築し、それをGEMにサブミットします。この時点で、GEMはすべてのオブジェクトをGTT（Graphics Translation Table）にバインドし、バッファを実行し、同じバッファを参照するクライアント間での必要な同期を提供します。これはしばしばGTTからいくつかのオブジェクトを追い出し、他のオブジェクトを再バインドする（比較的コストのかかる操作）ことや、固定されたGTTオフセットをクライアントから隠すためのリロケーションサポートを提供することを伴います。クライアントは、GTTに収まるよりも多くのオブジェクトを参照するコマンドバッファをサブミットしないように注意する必要があります。そうでない場合、GEMはそれらを拒否し、レンダリングが行われません。同様に、バッファ内のいくつかのオブジェクトが正しいレンダリングのためにフェンスレジスタを割り当てなければならない場合（例：965チップ以前の2Dブリット）、クライアントが利用可能なフェンスレジスタよりも多くの数を必要としないように注意する必要があります。このようなリソース管理はlibdrmでクライアントから抽象化されるべきです。

GEM VRAMヘルパーファンクションリファレンス¶

このライブラリは提供します struct drm_gem_vram_object (GEM VRAM)、ビデオRAM（VRAM）でバックアップされるGEMバッファオブジェクトであり、専用メモリを持つフレームバッファデバイスで使用できます

データ構造 struct drm_vram_mm およびそのヘルパは、専用ビデオメモリを持つシンプルなフレームバッファデバイスのメモリマネージャーを実装します。GEM VRAMバッファオブジェクトはビデオメモリに配置されるか、システムメモリに追い出されます

GEMインターフェースにより、ユーザー空間アプリケーションがグラフィックスバッファ（例：スクリーン上のフレームバッファ）を作成、管理、破壊できます。GEMはこれらのインターフェースの実装を提供しません。ハードウェアドライバがハードウェアに合わせた実装を提供する必要があります。ハードウェアデバイスに専用ビデオメモリがある場合、DRMドライバはVRAMヘルパライブラリを使用できます。アクティブなバッファオブジェクトはすべてビデオRAMに保存されます。アクティブなバッファは現在のフレームの描画に使用され、通常スキャンアウトバッファやカーソル画像などです。VRAMにスペースがなくなった場合、非アクティブなGEMオブジェクトはシステムメモリに移動されます

VRAMヘルパライブラリを初期化するにはdrmm_vram_helper_alloc_mm()を呼び出します。この関数は struct drm_vram_mm の struct drm_device.vram_mm . Use DRM_GEM_VRAM_DRIVER 初期化する struct drm_driver および DRM_VRAM_MM_FILE_OPERATIONS 初期化する struct file_operations; 以下の例のように使用します

struct file_operations fops ={
        .owner = THIS_MODULE,
        DRM_VRAM_MM_FILE_OPERATION
};
struct drm_driver drv = {
        .driver_feature = DRM_ ... ,
        .fops = &fops,
        DRM_GEM_VRAM_DRIVER
};

int init_drm_driver()
{
        struct drm_device *dev;
        uint64_t vram_base;
        unsigned long vram_size;
        int ret;

        // setup device, vram base and size
        // ...

        ret = drmm_vram_helper_alloc_mm(dev, vram_base, vram_size);
        if (ret)
                return ret;
        return 0;
}

これは struct drm_vram_mmGEMバッファ管理のためのユーザースペースインターフェースをエクスポートし、ファイル操作を初期化して作成されたGEMバッファへのアクセスを可能にします。この設定により、DRMドライバがビデオRAMの領域をVRAM MMで管理し、ユーザースペースにGEM VRAMオブジェクトを提供します。

VRAM MMのインスタンスを手動でクリーンアップする必要はありません。drmm_vram_helper_alloc_mm()は管理インターフェースであり、DRMデバイスのリリース時にクリーンアップハンドラを実行します。

描画またはスキャンアウト操作を行うには、rsp. バッファオブジェクトをビデオRAMにピン固定する必要があります。呼び出し drm_gem_vram_pin() with DRM_GEM_VRAM_PL_FLAG_VRAM または DRM_GEM_VRAM_PL_FLAG_SYSTEM を実行して、ビデオRAMまたはシステムメモリにバッファオブジェクトをピン固定します。呼び出し drm_gem_vram_unpin() を実行して、ピン固定されたオブジェクトを解放します。

ビデオRAMにピン固定されたバッファオブジェクトは、そのメモリ領域内で固定のアドレスを持ちます。呼び出し drm_gem_vram_offset() を実行してこの値を取得します。通常は、ハードウェアのスキャンアウトエンジンにフレームバッファをプログラミングするため、マウスカーソルのカーソルオーバーレイ画像を設定するため、またはハードウェアのドラーニングエンジンへの入力として使用されます。

DRMドライバからバッファオブジェクトのメモリにアクセスするには、呼び出し drm_gem_vram_vmap()します。これはバッファをカーネルアドレス空間にマッピングし、メモリアドレスを返します。使用 drm_gem_vram_vunmap() を実行してマッピングを解放します。

VMAオフセットマネージャー¶

vmaマネージャーは、任意のドライバ依存のメモリ領域を線形ユーザーアドレス空間にマッピングする責任があります。呼び出し元にオフセットを提供し、drmデバイスのaddress_spaceで使用できます。重複しないように、適切なサイズにし、mm-coreを混乱させないための不正確なfake vm_pgoffフィールドを避けるための処置を行います。ドライバはこのマネージャーを使用してVMEM内のオブジェクトの配置は行わないべきです。このマネージャーは、線形ユーザー空間VMへのマッピングの管理にのみ使用するべきです。

我々はdrm_mmをバックエンドとしてオブジェクトの割当管理に使用します。しかし、alloc/free呼び出しには高度に最適化されており、検索には最適化されていません。したがって、オフセット検索を高速化するためにrb-treeを使用します。

単一のaddress_spaceに対して複数のオフセットマネージャーを使用してはなりません。そうすると、mm-coreがメモリマッピングを破壊できなくなり、仮想マシンがもはや線形でなくなるため、メモリマッピングの teardown が実行できなくなります。

このオフセットマネージャーはページベースのアドレスを処理します。つまり、すべての引数および戻り値（ただし drm_vma_node_offset_addr())はバイト数ではなくページ数で指定されます。これは、オブジェクトのサイズおよびオフセットが常にページアライメントされている必要があります（通常通りです）。指定されたオフセットに対応する有効なユーザー空間アドレスを取得したい場合は、 drm_vma_node_offset_addr().

オフセット管理に加えて、vmaオフセットマネージャーはアクセス管理も処理します。すべてのオープンファイルコンテキストが特定のノードにアクセスを許可されている場合、それぞれに対して drm_vma_node_allow()を呼び出す必要があります。それにより、このオープンファイルに対してノードのオフセットを使用したmmap()呼び出しが-EACCESで失敗します。アクセスを再び取り消すには、 drm_vma_node_revoke()を使用してください。ただし、呼び出し元は必要に応じて既存のマッピングを破壊する責任があります。

DRM MM範囲アロケータ¶

概要¶

drm_mmは単純な範囲アロケータを提供します。ドライバはlinuxコアのリソースアロケータを使用することも自由ですが、drm_mmの利点はDRMコアに含まれているため、GPUの特殊な用途のニーズに応じて拡張が容易です。

主なデータ構造は drm_mm、割り当ては drm_mm_nodeで追跡されます。ドライバはこれらを自身の適切なデータ構造に埋め込むことができます。drm_mm自体はメモリの割り当てを行いませんので、ノードを埋め込まない場合でも、ドライバはそれらを自分で割り当てなければなりません。

範囲アロケータは予約された事前に割り当てられたブロックのサポートも行います。これはファームウェアから初期モード設定構成を引き継ぐ際に、ファームウェアのスキャンアウトターゲットと完全に一致するオブジェクトを作成するのに役立ちます。範囲がまだ空いている限り、アロケータが初期化された後でもいつでも挿入可能で、ドライバのロード順序におけるループ依存関係を回避するのに役立ちます。

drm_mmは、最近解放された空き領域のスタックを保持しており、すべての単純なデータ構造の中でも、割当のクラスタリングや過剰なフラグメンテーションを避けるための比較的効果的なアプローチとして思われます。これは空き領域の検索がO(num_holes)となることを意味します。drm_mmがサポートするすべての複雑な機能を考えると、より良い方法を実装するにはかなり複雑で、グラフィックスのスラッシングは比較的急な崖であり、現実的な問題とはなりません。ノードの削除はO(1)です。

drm_mmはいくつかの機能をサポートしています：アライメントや範囲制限を指定することが可能です。さらに、すべての drm_mm_node ノードには色値（これは単なる不透明な符号なし長整数）があり、ドライバのコールバックと組み合わせることで、複雑な割当制限を実装できます。i915 DRMドライバは、グラフィックスTTにおける不一致なキャッシュドメイン間のガードページを実装するためにこの機能を使用しています。

割当の検索と割当には、ボトムアップとトッピングダウンの2つの挙動がサポートされています。デフォルトはボトムアップです。メモリ領域に異なる制限がある場合や、フラグメンテーションを減らすためにだけ使用する場合はトッピングダウン割当を使用できます。

最後に、すべてのノードとすべての空き領域を歩くためのイテレーションヘルパと、デバッグ用の基本的なアロケータダンパが提供されています。

この範囲アロケータはスレッドセーフではありません。ドライバは自身のロックで変更を保護する必要があります。この設計の目的は、完全なメモリマネージャーでは追加のデータを保護する必要があるため、内部ロックは完全に冗長であるということです。

LRUスキャン/エビクションサポート¶

GPUは特定のオブジェクトに対して連続的な割当が必要なことがよくあります。新しいオブジェクトの割当のためにオブジェクトを解放する際、単にLRUの末尾からすべてのオブジェクトを選択するよりも効率的ではありません。特に大きなオブジェクトや特別な割当制限を持つノードの場合、不要な（小さな）オブジェクトを多数解放してしまう可能性があります。

DRM範囲アロケータはこのユースケースをスキャンインターフェースを通じてサポートしています。まずスキャン操作は drm_mm_scan_init() または drm_mm_scan_init_with_range()で初期化され、ドライバはロスターにオブジェクトを追加します（おそらくLRUリストを歩くことによりますが、これは自由に実装可能です）。エビクション候補は drm_mm_scan_add_block() で追加され、適切な空き領域が見つかったり、さらなるエビクション可能なオブジェクトがなくなるまで続けられます。エビクションロスターのメタデータは struct drm_mm_scan.

で追跡されます。ドライバは、アロケータの状態を復元するため、すべてのオブジェクトを逆の順序で再び歩く必要があります。注意点として、スキャンモードでアロケータを使用している間は、他の操作は許可されません。

最後にドライバは選択されたすべてのオブジェクトをエビクトします（drm_mm_scan_remove_block() スキャン中に報告された真値) およびカラーアジャスト後の重なったノード (drm_mm_scan_color_evict()). オブジェクトの追加・削除は O(1) であり、ノードの解放も O(1) なので全体の複雑度は O(スキャンされたオブジェクト数) です。フリースタックのようにスキャン操作が始まる前から歩く必要があるのと同じく、これはオブジェクト数に線形で依存します。あまり深刻な影響のようではありません。

enum drm_mm_insert_mode¶

検索と割当の挙動を制御

定数

DRM_MM_INSERT_BEST

検索範囲内で、目的のノードに合う最小の穴を検索します。

見つかった穴の底からノードを割り当てます。

DRM_MM_INSERT_LOW

検索範囲内で、目的のノードに合う最小のアドレス（0に近い）の穴を検索します。

見つかった穴の底からノードを割り当てます。

DRM_MM_INSERT_HIGH

検索範囲内で、目的のノードに合う最大のアドレス（U64_MAXに近い）の穴を検索します。

見つかった穴の top からノードを割り当てます。ノードの指定されたアライメントはノードベース（drm_mm_node.start).

DRM_MM_INSERT_EVICT

検索範囲内で、目的のノードに合う最も最近のエビクションされた穴を検索します。これはエビクションスキャン（参照 drm_mm_scan_init()) を実行した直後に選択したノードを削除して穴を形成する際に適しています。

見つかった穴の底からノードを割り当てます。

DRM_MM_INSERT_ONCE

すべての穴を検索せず、最初の穴のみを検査し、適切でなければ即座に -ENOSPC を報告します。他の検索方法（例: DRM_MM_INSERT_HIGH や DRM_MM_INSERT_LOW）と併用する必要があります。

DRM_MM_INSERT_HIGHEST

最大のアドレスを持つ穴のみを検索し、その穴の上部にノードを割り当てます。適切でなければ -ENOSPC を報告します。

すべての穴を検索しません。

DRM_MM_INSERT_LOWEST

最小のアドレスを持つ穴のみを検索し、その穴の下部にノードを割り当てます。適切でなければ -ENOSPC を報告します。

すべての穴を検索しません。

説明

以下の struct drm_mm レンジマネージャーは複数の検索木を用いて、適切なモードを見つけることができます。これらの木はサイズ、アドレス、および最近のエビクション順に整理されています。これにより、ユーザーが再利用可能な最小の穴、または最低または最高のアドレスの穴、あるいは最近のエビクションを再利用できるようにします。ノードを drm_mm_node 内から割り当てると、 drm_mm_insert_mode も、最低の一致アドレスか最高のアドレスかを指定します。

DRM アロケータ

struct drm_mm {
  void (*color_adjust)(const struct drm_mm_node *node,unsigned long color, u64 *start, u64 *end);

DRM同期オブジェクト¶

DRM同期オブジェクト(syncobj、struct drm_syncobj)は、ユーザー空間がGPUコマンドを明示的に同期するための同期プリミティブを含むコンテナであり、ユーザー空間プロセス間で共有可能で、異なるDRMドライバー間でも共有可能です。主な用途はVulkanのフェンスとセマフォの実装です。syncobjユーザー空間APIは以下の操作を提供します：

  • syncobjの生成と破棄

  • syncobjファイル記述子とのインポートおよびエクスポート

  • syncobjの下位フェンスをsyncファイルとの間でインポートおよびエクスポート

  • syncobjをリセット（フェンスをNULLに設定）

  • syncobjをシグナル（簡単にシグナルを送出するフェンスを設定）

  • syncobjのフェンスが出現しシグナルを送出するのを待機

syncobjユーザー空間APIは、struct dma_fence_chain のタイムラインに依存せず、以下の操作を通じてsyncobjを操作できます： dma_fence、

  • タイムライン上の特定のポイントをシグナル

  • 特定のポイントが出現し、またはシグナルを送出するのを待機

  • 特定のタイムラインポイントとのインポートおよびエクスポート

根本的に、syncobjはstruct dma_fence へのポインタをラッパーとして持つだけです。このポインタはNULLの場合もあります。syncobjが初めて生成される際、ポインタはNULLか、すでにシグナルを送出したフェンスへのポインタのいずれかです。これは DRM_SYNCOBJ_CREATE_SIGNALED フラグが DRM_IOCTL_SYNCOBJ_CREATE.

に渡されたかどうかに依存します。syncobjを二値（状態がシグナルまたは未シグナル）のプリミティブとみなす場合、DRMドライバー内でGPU作業をキューインしてsyncobjをシグナルする際、syncobjのフェンスはその作業の完了時にシグナルを送出するフェンスに置き換えられます。syncobjをタイムラインプリミティブとみなす場合、DRMドライバー内でGPU作業をキューインしてsyncobjの特定のポイントをシグナルする際、新しいstruct dma_fence_chain が作成され、これはDRMドライバーのフェンスを指し、かつsyncobj内の以前のフェンスを指します。新しいstruct dma_fence_chain フェンスはsyncobjのフェンスを置き換え、DRMドライバの作業完了および以前にsyncobjに含まれていたフェンスに関連する作業の完了時にシグナルを送出されます。

GPU作業がDRMドライバ内でsyncobjを待機してキューイングされる場合、作業がキューイングされる時点では、ハードウェアに作業を送信する前にsyncobjのフェンスを待機します。そのフェンスは以下のいずれかです：

  • syncobjがバイナリ・プリミティブとして扱われる場合、syncobjの現在のフェンス

  • 構造体 dma_fence syncobjがタイムライン・プリミティブとして扱われる場合、特定のポイントに関連付けられた構造体

syncobjのフェンスがNULLまたはsyncobjのタイムラインに存在しない場合、キューイング操作は失敗すると期待されます。

バイナリ・syncobjでは、syncobjのフェンスのすべての操作は、ユーザー空間がioctlを呼び出す時点の現在のフェンスに基づいて行われます。これは、操作が即時ホスト側の操作（signalまたはreset）であれ、ドライバのキューにキューイングされる操作であれ、すべて適用されます。 DRM_IOCTL_SYNCOBJ_RESET および DRM_IOCTL_SYNCOBJ_SIGNAL ホスト側からsyncobjを操作するために使用でき、そのポインタをNULLにリセットするか、すでにシグナルを送出されたフェンスにポインタを設定できます。

タイムライン・syncobjでは、syncobjのフェンスのすべての操作は、タイムライン内のポイントを参照するu64値に基づいて行われます。特定のポイントがタイムライン内でどのように見つかるかについては、dma_fence_chain_find_seqno()関数を参照してください。

アプリケーションは、syncobjがタイムラインとして扱われる場合に常にタイムラインセットのioctl()を使用する必要があります。タイムラインとして扱われるsyncobjに対してバイナリセットのioctl()を使用すると、不正確な同期が発生する可能性があります。バイナリ・syncobjの使用は、タイムラインセットのioctl()でポイント値0を使用することでサポートされており、これによりバイナリセットのioctl()の挙動（例：シグナル時にsyncobjのフェンスを置き換える）が再現されます。

ホスト側でのsyncobjの待機¶

DRM_IOCTL_SYNCOBJ_WAIT syncobjハンドルの配列を取り込み、すべてのsyncobjフェンスを同時にホスト側で待機します。もし DRM_SYNCOBJ_WAIT_FLAGS_WAIT_ALL が設定されている場合、wait ioctlはすべてのsyncobjフェンスがシグナルを送出されるのを待ってから戻ります。そうでない場合、少なくとも1つのsyncobjフェンスがシグナルを送出されるとすぐに戻り、シグナルを送出したフェンスのインデックスをクライアントに書き戻します。

キューイングされたGPU作業依存関係は、syncobjにNULLフェンスを検出すると失敗しますが、もし DRM_SYNCOBJ_WAIT_FLAGS_WAIT_FOR_SUBMIT が設定されている場合、ホスト側の待機はまずsyncobjが非NULLフェンスを受信するのを待ってから、そのフェンスを待機します。もし DRM_SYNCOBJ_WAIT_FLAGS_WAIT_FOR_SUBMIT syncobjsの配列内のいずれかがNULLフェンスを持つ場合、-EINVALが返されます。syncobjが初期状態でNULLフェンスを持つと仮定すると、クライアントは1つのスレッド（またはプロセス）でGPUワークを別のスレッド（またはプロセス）で送信した状態でホスト待機を行うことができ、2つの間で手動での同期を必要としなくなります。この要件はVulkanフェンスAPIから継承されています。

同様に、 DRM_IOCTL_SYNCOBJ_TIMELINE_WAIT syncobjハンドルの配列およびu64ポイントの配列を受け取り、指定されたポイントでsyncobjフェンスのすべてにホスト側で同時に待機を行います。

DRM_IOCTL_SYNCOBJ_TIMELINE_WAIT また、タイムライン上での特定のフェンスが実体化されるのを待機する機能も追加しています。これにより、フェンスがシグナルされるのを待つことなく、 DRM_SYNCOBJ_WAIT_FLAGS_WAIT_AVAILABLE フラグを使用して待機が可能です。この要件はVulkanタイムラインセマフォAPIが要求するwait-before-signalの挙動から継承されています。

syncobjのインポート/エクスポート¶

DRM_IOCTL_SYNCOBJ_FD_TO_HANDLE および DRM_IOCTL_SYNCOBJ_HANDLE_TO_FD syncobjのインポート/エクスポートには2つのメカニズムを提供します。

1つ目のメカニズムでは、クライアントがsyncobj全体をファイル記述子にインポートまたはエクスポートできます。これらのファイル記述子は不透明であり、プロセス間でのsyncobjのやり取り以外には他の用途はありません。すべてのエクスポートされたファイル記述子およびそれらのファイル記述子をインポートして作成されたsyncobjハンドルは、同じ基盤となる構造体への参照を保持します。 drm_syncobj syncobjは、共有されているすべてのプロセスで永続的に使用可能です。syncobjは最後の参照が解除されたときのみ解放されます。dma-bufとは異なり、syncobjのインポートはファイル記述子のインポートごとに新しいハンドル（独自の参照を持つ）を作成し、重複を排除しません。この永続的なインポート/エクスポートの主な用途は共有Vulkanフェンスおよびセマフォです。

2つ目のインポート/エクスポートメカニズムは、 DRM_SYNCOBJ_FD_TO_HANDLE_FLAGS_IMPORT_SYNC_FILE または DRM_SYNCOBJ_HANDLE_TO_FD_FLAGS_EXPORT_SYNC_FILE を介してクライアントがsyncobjの現在のフェンスをファイルにインポートまたはエクスポートできます。 sync_filesyncobjを同期ファイルにエクスポートすると、その同期ファイルはエクスポート時のsyncobjのフェンスをラップし、その後のsyncobjのシグナルまたはリセット操作は同期ファイルに影響を与えません。同期ファイルをsyncobjにインポートすると、syncobjのフェンスはその同期ファイルがラップするフェンスに設定されます。同期ファイルは不変であるため、syncobjのリセットまたはシグナルは、syncobjにインポートされたフェンスを持つすべての同期ファイルに影響を与えません。

GPUスケジューラ¶

概要¶

GPUスケジューラは、ユーザー空間からジョブをソフトウェアキューにプッシュし、その後ハードウェア実行キュー上でスケジューリングするためのエンティティを提供します。ソフトウェアキューには優先度があり、スケジューラはFIFOを用いて実行キューからエンティティを選択します。スケジューラはジョブ間の依存関係の処理機能も提供します。ドライバは、ジョブをハードウェア実行キューに送信するなど、バックエンド操作用のコールバック関数をスケジューラに提供する必要があります。

スケジューラの構成は以下の通りです。

  1. 各ハードウェア実行キューには1つのスケジューラが割り当てられています

  2. 各スケジューラには、異なる優先度（例: HIGH_HW,HIGH_SW, KERNEL, NORMAL）を持つ複数の実行キューがあります

  3. 各スケジューラ実行キューにはスケジューリング対象のエンティティのキューがあります

  4. エンティティ自身がハードウェア上でスケジューリングされるジョブのキューを保持しています

エンティティ内のジョブは常にプッシュされた順序でスケジューリングされます

struct drm_sched_fence¶

ジョブのスケジューリングに応じるフェンス。

定義

struct drm_sched_fence {
  struct dma_fence                scheduled;
  struct dma_fence                finished;
  struct dma_fence                *parent;
  struct drm_gpu_scheduler        *sched;
  spinlock_t lock;
  void *owner;
};

メンバ

scheduled

このフェンスは、ジョブがスケジューリングされるときにスケジューラーがシグナルを送るものです。

finished

このフェンスは、ジョブが完了したときにスケジューラーがシグナルを送るものです。

ジョブのアウトフェンスを設定する際には、このフェンスを使用すべきです。これは即座に利用可能で drm_sched_job_init()、ドライバーがrun_job()から返すフェンスは、依存関係が解決するまで作成されません。

parent

ドライバーが返すフェンス drm_sched_backend_ops.run_job ハードウェアでジョブをスケジューリングする際。このフェンスをシグナルを送ります drm_sched_fence.finished 親フェンスがシグナルを送ったときにこのフェンスをシグナルを送ります。

sched

この構造体を持つジョブが属するスケジューラーインスタンス。

lock

スケジュールされたフェンスと完了フェンスが使用するロック。

owner

デバッグ用のジョブ所有者

struct drm_sched_backend_ops¶

定義

struct drm_sched_backend_ops {
  struct dma_fence *(*dependency)(struct drm_sched_job *sched_job, struct drm_sched_entity *s_entity);
  struct dma_fence *(*run_job)(struct drm_sched_job *sched_job);
  void (*timedout_job)(struct drm_sched_job *sched_job);
  void (*free_job)(struct drm_sched_job *sched_job);
};

メンバ

dependency

スケジューラーがこのジョブを次のスケジューリングの候補として検討するときに呼び出されます。これにより、別の struct dma_fence このジョブがブロックするためのオブジェクトを取得します。NULLを返すと、run_job()が呼び出される可能性があります。

run_job

すべての依存関係が解決した後にジョブを実行するために呼び出されます。timedout_job()が発生し、drm_sched_job_recovery()が再試行を決定した場合、複数回呼び出される可能性があります。

timedout_job

ジョブが実行に時間がかかりすぎた場合に呼び出され、GPUの回復をトリガーします。

free_job

ジョブの完了フェンスがシグナルを送られ、クリーンアップのタイミングになったときに呼び出されます。

説明

スケジューラーが呼び出すバックエンド操作を定義します。これらの関数はドライバー側で実装する必要があります。

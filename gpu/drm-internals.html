DRM内部¶

この章では、ドライバ開発者や、既存のドライバに最新の機能を追加するための開発者向けに、DRM内部の重要な情報を記載しています。

まず、ドライバ初期化に必要な典型的な要件について説明します。コマンドバッファの設定、初期出力構成の作成、コアサービスの初期化などです。その後のセクションでは、コア内部の詳細について掘り下げ、実装ノートと例を提供します。

DRMレイヤーはグラフィックスドライバにいくつかのサービスを提供しており、多くはlibdrmを通じて提供するアプリケーションインターフェースによって駆動されます。libdrmはDRM ioctlsをラップしたライブラリです。これらには、vblankイベント処理、メモリ管理、出力管理、フレームバッファ管理、コマンド送信＆フェンチング、スリープ/再起動サポート、DMAサービスなどが含まれます。

ドライバ初期化¶

すべてのDRMドライバの中心には struct drm_driver 構造体があります。ドライバは通常、drm_driver構造体を静的に初期化し、その後 drm_dev_alloc() を呼び出してデバイスインスタンスを割り当てます。デバイスインスタンスが完全に初期化されると、ユーザー空間からアクセス可能になるように登録（register）します。 drm_dev_register().

以下の struct drm_driver 構造体には、ドライバとそのサポートする機能を記述する静的情報と、DRMコアがDRM APIを実装するために呼び出すメソッドへのポインタが含まれています。まず、静的情報フィールドについて説明し、その後で後述のセクションで使用される個々の操作について詳細に説明します。 struct drm_driver 静的情報フィールド

ドライバ情報¶

メジャーバージョン、マイナーバージョン、パッチレベル¶

int major; int minor; int patchlevel; DRMコアはメジャーバージョン、マイナーバージョン、パッチレベルの triplet でドライババージョンを識別します。この情報は初期化時にカーネルログに印刷され、DRM_IOCTL_VERSION ioctls を通じてユーザースペースに渡されます。

メジャーバージョンとマイナーバージョンは、DRM_IOCTL_SET_VERSION に渡されたリクエストされたドライバAPIバージョンを検証するためにも使用されます。マイナーバージョン間でドライバAPIが変更された場合、アプリケーションは DRM_IOCTL_SET_VERSION を呼び出して特定のAPIバージョンを選択できます。リクエストされたメジャーバージョンがドライバのメジャーバージョンと一致しない、またはリクエストされたマイナーバージョンがドライバのマイナーバージョンより大きい場合、DRM_IOCTL_SET_VERSION 呼び出しはエラーを返します。それ以外の場合、ドライバの set_version() メソッドがリクエストされたバージョンとともに呼び出されます。

名前、説明および日付¶

char *name; char *desc; char *date; ドライバ名は初期化時にカーネルログに印刷され、IRQ登録に使用され、DRM_IOCTL_VERSION を通じてユーザースペースに渡されます。

ドライバの説明は、ユーザー空間にDRM_IOCTL_VERSION ioctlを通じて渡される純粋な情報文字列であり、それ以外ではカーネルによって使用されません。

ドライバの日付はYYYYMMDD形式で、ドライバの最新の変更日を識別するためのものです。しかし、ほとんどのドライバーがこれを更新しないので、値はほとんど無意味です。DRMコアは初期化時にカーネルログにこれを出力し、DRM_IOCTL_VERSION ioctlを通じてユーザー空間に渡します。

デバイスインスタンスとドライバーハンドリング¶

drmドライバのデバイスインスタンスは struct drm_deviceで表されます。これは、ドライバが実装したバス固有の->probe()コールバックから通常、割り当てられ初期化されます。 devm_drm_dev_alloc()ドライバはその後、drmデバイスのさまざまなサブシステム（メモリ管理、vblank処理、モード設定サポート、初期出力構成など）を初期化し、それに加えて、対応するハードウェアのビットを明確に初期化する必要があります。すべてが動作し、ユーザー空間に準備ができたら、デバイスインスタンスを公開するために drm_dev_register().

があります。また、バス固有のヘルパーと drm_driver.load コールバックを使用してデバイスインスタンスを初期化する古いサポートもあります。しかし、後方互換性のため、デバイスインスタンスは早すぎる段階で公開する必要があります。これにより、グローバルなロックを必要とし、安全を確保するための不美な処理が必要となるため、この古いサポートは既存の未変換ドライバのみに限定されます。

デバイスインスタンスをクリーンアップする際には、逆の順序で操作が必要です。まず、 drm_dev_unregister()でデバイスインスタンスを非公開にしてから、デバイス初期化時に割り当てられた他のリソースをクリーンアップし、ドライバの参照を drm_device を使用して drm_dev_put().

から解除します。注意点として、ユーザー空間に見えるすべての割り当てやリソースは、最終的に drm_dev_put() が呼ばれたときにのみ解放すべきであり、ドライバが下位物理構造からアンバインドされるときに解放してはいけません。 deviceは、 drm_device で管理されるリソースを使用するのが最適です。 drmm_add_action(), drmm_kmalloc() devres管理されたリソースのような

は、下位ハードウェアデバイスに直接関連するリソースにのみ使用でき、かつ、完全に devm_kmalloc() で保護されたコードパスでのみ使用できます。 drm_dev_enter() および drm_dev_exit().

ディスプレイドライバーアクセサリ¶

以下の例は、典型的なDRMディスプレイドライバの構造を示しています。この例はプローブ関数に焦点を当て、常に存在する他の関数を示し、 devm_drm_dev_alloc().

struct driver_device {
        struct drm_device drm;
        void *userspace_facing;
        struct clk *pclk;
};

static struct drm_driver driver_drm_driver = {
        [...]
};

static int driver_probe(struct platform_device *pdev)
{
        struct driver_device *priv;
        struct drm_device *drm;
        int ret;

        priv = devm_drm_dev_alloc(&pdev->dev, &driver_drm_driver,
                                  struct driver_device, drm);
        if (IS_ERR(priv))
                return PTR_ERR(priv);
        drm = &priv->drm;

        ret = drmm_mode_config_init(drm);
        if (ret)
                return ret;

        priv->userspace_facing = drmm_kzalloc(..., GFP_KERNEL);
        if (!priv->userspace_facing)
                return -ENOMEM;

        priv->pclk = devm_clk_get(dev, "PCLK");
        if (IS_ERR(priv->pclk))
                return PTR_ERR(priv->pclk);

        // Further setup, display pipeline etc

        platform_set_drvdata(pdev, drm);

        drm_mode_config_reset(drm);

        ret = drm_dev_register(drm);
        if (ret)
                return ret;

        drm_fbdev_generic_setup(drm, 32);

        return 0;
}

// This function is called before the devm_ resources are released
static int driver_remove(struct platform_device *pdev)
{
        struct drm_device *drm = platform_get_drvdata(pdev);

        drm_dev_unregister(drm);
        drm_atomic_helper_shutdown(drm)

        return 0;
}

// This function is called on kernel restart and shutdown
static void driver_shutdown(struct platform_device *pdev)
{
        drm_atomic_helper_shutdown(platform_get_drvdata(pdev));
}

static int __maybe_unused driver_pm_suspend(struct device *dev)
{
        return drm_mode_config_helper_suspend(dev_get_drvdata(dev));
}

static int __maybe_unused driver_pm_resume(struct device *dev)
{
        drm_mode_config_helper_resume(dev_get_drvdata(dev));

        return 0;
}

static const struct dev_pm_ops driver_pm_ops = {
        SET_SYSTEM_SLEEP_PM_OPS(driver_pm_suspend, driver_pm_resume)
};

static struct platform_driver driver_driver = {
        .driver = {
                [...]
                .pm = &driver_pm_ops,
        },
        .probe = driver_probe,
        .remove = driver_remove,
        .shutdown = driver_shutdown,
};
module_platform_driver(driver_driver);

をデモンストレーションしています。USBやDTオーバーレイアンロードなどのデバイスアンプラグをサポートするドライバーは、 drm_dev_unplug() …の代わりに drm_dev_unregister()を使用すべきです。ドライバは、デバイスリソースにアクセスする領域を保護し、リリース後に使用しないようにする必要があります。これは drm_dev_enter() および drm_dev_exit()を使用して実現されます。ただし、1つの欠点があります。 drm_dev_unplug() は、ドライバをアンプラグする前にdrm_deviceをアンプラグします。 drm_atomic_helper_shutdown() 呼び出されます。これは、無効化コードパスが保護されている場合、通常のドライバーモジュールアンロード時に実行されず、ハードウェアが有効なままになる可能性があることを意味します。

コンポーネントヘルパの使用¶

ファイル操作¶

ドライバは、DRMユーザースペースAPIのエントリポイントとなるファイル操作構造体を定義しなければなりません。ただし、これらの操作の多くはDRMコアで実装されています。結果として struct file_operations は drm_driver.fops フィールドに格納しなければなりません。必須の関数は drm_open(), drm_read(), drm_ioctl() および drm_compat_ioctl() CONFIG_COMPATが有効の場合、drm_compat_ioctlはCONFIG_COMPAT=nの場合はNULLとなるため、コード中に#ifdefを散らす必要はありません。プライベートなIOCTLを実装し、32/64ビット互換性をサポートするドライバは、自身の file_operations.compat_ioctl ハンドラを提供し、プライベートなIOCTLを処理して drm_compat_ioctl() コアIOCTLを呼び出す必要があります。

さらに drm_read() および drm_poll() DRMイベントのサポートを提供します。DRMイベントは、ファイルディスクリプタを通じてユーザースペースに非同期イベントを送信するための汎用的で拡張可能な手段です。KMS APIではvblankイベントやページフラップ完了を送信するために使用されますが、ドライバも自身の用途（例: レンダリング完了の通知）に利用できます。

ドライバ側のイベントインターフェースについては drm_event_reserve_init() および drm_send_event() を主な開始点とします。

メモリマッピングの実装はドライバがメモリをどのように管理するかに依存します。legacyドライバは非推奨のdrm_legacy_mmap()関数を使用し、現代のドライバは提供されたメモリマネージャー固有の実装を使用すべきです。GEMベースのドライバでは drm_gem_mmap()が使用され、CMA GEMヘルパを用いるドライバでは drm_gem_cma_mmap().

です。 file_operations フィールドはRCU読み込み側クリティカルセクションのネストレベルを記録し、

static const example_drm_fops = {
        .owner = THIS_MODULE,
        .open = drm_open,
        .release = drm_release,
        .unlocked_ioctl = drm_ioctl,
        .compat_ioctl = drm_compat_ioctl, // NULL if CONFIG_COMPAT=n
        .poll = drm_poll,
        .read = drm_read,
        .llseek = no_llseek,
        .mmap = drm_gem_mmap,
};

シンプルなGEMベースのドライバには DEFINE_DRM_GEM_FOPS() マクロがあり、CMAベースのドライバには DEFINE_DRM_GEM_CMA_FOPS() マクロがあります。

ドライバの file_operations は drm_driver.fops.

レガシーサポートコード¶

このセクションでは、古いレガシーのサポートコードについて簡潔に説明します。これは、古いDRMドライバが実際のドライバとして登録する代わりに、下位デバイスにshadow-attachした場合にのみ使用されるコードです。また、古い一般的なバッファ管理とコマンド送信コードも含まれます。新しい現代的なドライバでは一切使用しないでください。

レガシースリープ/再開¶

DRMコアは一部のスリープ/再開コードを提供していますが、完全なスリープ/再開サポートを提供するドライバは、save() および restore() 関数を提供する必要があります。これらはスリープ、ハイブリネート、または再開時のタイミングで呼び出され、ドライバがスリープまたはハイブリネート状態間でデバイスが必要とする状態の保存または復元を行う必要があります。

int (*suspend) (struct drm_device *, pm_message_t state); int (*resume) (struct drm_device *); これらはレガシーのスリープおよび再開メソッドであり、 のみ レガシーのシャドウアタッチドライバ登録関数と互換性があります。新しいドライバは、バスタイプが提供するパワーマネジメントインターフェース（通常は struct device_driver dev_pm_opsを通じて）を使用し、これらのメソッドをNULLに設定する必要があります。

レガシーディーエムエーエスサービス¶

これはコアがDMAマッピングなどのサポートを行う方法を説明する必要があります。これらの関数は非推奨であり、使用すべきではありません。

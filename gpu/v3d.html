drm/v3d Broadcom V3Dグラフィックスドライバ¶

このドライバーは Broadcom V3D 3.3 および 4.1 OpenGL ES GPU をサポートしています。V3D 2.x のサポートについては VC4 ドライバーを参照してください。

V3D GPU にはタイルレンダリング（ビンとレンダリングパイプラインから構成される）、テクスチャフォーマットユニット（TFU）、コンピュートシェーダディスパッチ（CSD）が含まれます。

GPUバッファオブジェクト（BO）管理¶

VC4（V3D 2.x）と比較して、V3D 3.3 は GPU とバスの間に MMU（メモリマッピングユニット）が導入され、CMA ではなく shmem オブジェクトをストレージとして使用できるようになりました。

物理的に連続したオブジェクトは V3D にもインポート可能ですが、ドライバーは自動的に物理的に連続したオブジェクトを割り当てません。物理的に連続した割当が必要なディスプレイエンジンは、Mesa の「renderonly」サポート（Mesa pl111 ドライバーで使用されている例）を参考にして V3D との統合方法を検討してください。

長期的にはメモリ圧力下で MMU からページを追い出すサポートを実装すべきですが、システムがスワップをあまり使用しない傾向にあるため、優先度は高くありません。

アドレス空間管理¶

V3D 3.x ハードウェア（VC4 と比較）には MMU が導入され、V3D の 4GB アドレス空間を AXI バスアドレスにマッピングするための単一レベルのページテーブルが含まれます。これにより、PTE（ページテーブルエントリ）を保存するために最大 4MB の物理的に連続したメモリが必要になる場合があります。

4MB の連続メモリは貴重で、切り替えは高コストとなるため、すべての BO（ボーファイバー）を同じ 4GB アドレス空間にロードします。

クライアント同士の競合を防ぐため、GMP（グラフィックスメモリプロテクション）を用いて、クライアントごとに 128KB 単位で利用可能なページをマスクする必要があります。これは現時点では実装されていません。

GPUスケジューリング¶

共有 DRM GPU スケジューラはハードウェアへのジョブ送信を調整します。各 DRM fd（クライアントプロセスに相当）には独自のスケジューラエンティティが割り当てられ、ジョブを順番に処理します。GPU スケジューラはクライアント間でラウンドロビン方式で次のジョブを送信します。

簡潔さを重視し、バックグラウンドジョブがキューイングされている際のインタラクティブジョブのレイテンシーを低く保つため、最後のジョブが完了するまで新たなジョブをハードウェアに送信しません。CT[01]Q FIFO にジョブを詰め込むのではなく、v3d_job_dependency() を使ってビンとレンダリングの依存関係を管理します。クライアントがハードウェアのセマフォを使用して相互に制御するのではなく、この方法を採用しています。

割込み¶

ビン、レンダリング、TFU 完了、または CSD 完了の割り込みを検出すると、そのジョブのフェンスをシグナルする必要があります。これによりスケジューラが次のジョブをキューイングし、待機中のプロセスをアンブロックします。

メモリ割込みからバインナを外す際には、新しいメモリを確保し、バインナに渡す必要があります。これにより、現在のジョブが進捗を遂げられるようになります。

drm/komeda アームディスプレイドライバー¶

drm/komedaドライバは、ArmディスプレイプロセッサD71以降の製品をサポートしており、このドキュメントではドライバ設計の簡単な概要を説明します。ドライバの仕組みやその設計理由について解説します。

D71のようなディスプレイIPの概要¶

D71からは、ArmディスプレイIPが柔軟でモジュール化されたアーキテクチャを採用開始しました。ディスプレイパイプラインは、複数の個別かつ機能的なパイプラインステージ（コンポーネント）で構成され、各コンポーネントは特定の処理能力を持ち、流れ込むピクセルデータに特有の処理を施します。

典型的なD71コンポーネント:

レイヤー¶

レイヤーは最初のパイプラインステージで、次のステージに向けたピクセルデータを準備します。メモリからピクセルを取得し、AFBCの場合はデコードし、ソース画像を回転させ、YUVピクセルをデバイス内部のRGBピクセルにアンパッキングまたは変換し、必要に応じてピクセルのカラースペースを調整します。

スケーラー¶

名前の通り、スケーラーはスケーリングを担当し、D71ではスケーラーを用いた画像補正もサポートしています。スケーラーの使用は非常に柔軟で、レイヤー出力に接続してレイヤー内でのスケーリングを行うか、コンポジターに接続して全体のディスプレイフレームをスケーリングし、その後wb_layerに出力データを供給してメモリに書き込むことができます。

コンポジター（compiz）¶

コンポジターは複数のレイヤーやピクセルデータフローを1つのディスプレイフレームにマージします。その出力フレームはポスト画像プロセッサに供給してモニターに表示するか、wb_layerに供給してメモリに同時に書き込むことができます。ユーザーはコンポジターとwb_layerの間にスケーラーを挿入して、ディスプレイフレームを事前にダウンスケーリングし、その後メモリに書き込むことも可能です。

Writebackレイヤー（wb_layer）¶

ライトバックレイヤーはレイヤーの逆の処理を行います。コンピズに接続し、コンポジット結果をメモリに書き込みます。

ポスト画像処理器（improc）¶

ポスト画像プロセッサは、モニターの要件に合わせてフレームデータをガンマやカラースペースなどに調整します。

タイミングコントローラー (timing_ctrlr)¶

ディスプレイパイプラインの最終段階。タイミングコントローラーはピクセル処理ではなく、ディスプレイタイミングの制御のみを行います。

マージャー¶

D71のスケーラーはレイヤーに比べて水平方向の入出力能力が半分程度しかありません。例えばレイヤーが4K入力サイズをサポートする場合、スケーラーは同時には2K入出力のみをサポートします。フルフレームスケーリングを実現するため、D71ではレイヤースプリットを導入しました。これは画像全体を2つの半分の部分に分割し、2つのレイヤーAとBに供給し、それぞれで独立してスケーリングを行います。スケーリング結果はマージャーに供給して2つの部分画像を統合し、その後統合結果をコンピズに出力します。

スプリッター¶

レイヤースプリットと類似していますが、Splitterは書き戻しに使用され、compizの結果を2つの部分に分割して、それぞれを2つのスケーラーに供給します。

D71パイプラインの使用が可能です¶

モジュール化されたアーキテクチャにより、D71パイプラインはさまざまな用途に簡単に調整可能です。D71は2つのパイプラインをサポートしており、2種類の作業モードをサポートしています。

  • デュアルディスプレイモード 2つのパイプラインが独立して動作し、2つのディスプレイ出力に駆動します。

  • シングルディスプレイモード 2つのパイプラインが協働して、1つのディスプレイ出力のみを駆動します。

    このモードでは、パイプライン_Bは独立して動作せず、その合成結果をパイプライン_Aに送出し、ピクセルタイミングもパイプライン_A.timing_ctrlrから取得します。パイプライン_Bはパイプライン_A（マスター）の「スレーブ」として動作します。

リソースの発見と初期化¶

パイプラインとコンポーネントはピクセルデータの処理方法を記述する。我々はまだ @struct komeda_dev デバイス全体のビューを記述し、デバイスの制御機能を示す

我々は &komeda_dev, &komeda_pipeline, &komeda_component を持つ。現在デバイスをパイプラインで埋める。komeda は D71 だけでなく、今後の製品にも対応するため、異なる製品間で共有できるようにする必要がある。そのため、komeda デバイスを CORE と CHIP の二つのレイヤーに分割する。

  • CORE: 共通の機能と能力の処理を行う。

  • CHIP: レジスタプログラミングとハードウェア固有の機能（制限）の処理を行う。

CORE は CHIP にアクセスするための3つのチップ機能構造体を持つ:

  • struct komeda_dev_funcs

  • struct komeda_pipeline_funcs

  • struct komeda_component_funcs

komeda_devをDRM-KMSにアタッチ¶

Komedaはパイプライン/コンポーネントでリソースを抽象化していますが、DRM-KMSはcrtc/plane/connectorを使用します。1つのKMSオブジェクトが単一のコンポーネントを表すことはできません。なぜなら、単一のKMSオブジェクトで要求を満たすことは困難であり、通常複数のコンポーネントが必要です。例えば、KMSのモード設定、ガンマ、CTMはすべてCRTCオブジェクトに依存しますが、Komedaはcompiz、improc、timing_ctrlrの組み合わせでこれらの要求を満たします。また、KMS-Planeは複数のKomedaリソース（layer/scaler/compiz）を必要とする場合があります。

したがって、1つのKMS-ObjはKomedaのサブパイプラインを表します。

  • プレーン: レイヤー(入力)パイプライン

  • Wb_connector: ライトバック(出力)パイプライン

  • Crtc: ディスプレイ出力パイプライン

したがって、KomedaではKMSのcrtc/plane/connectorをパイプラインとコンポーネントのユーザーとして扱い、同時に1つのパイプライン/コンポーネントは1つのユーザーのみが使用可能です。パイプライン/コンポーネントはDRM-KMSのプライベートオブジェクトとして扱われ、drm_atomic_stateで状態を管理します。

平面をレイヤー(入力)パイプラインにマッピングする方法¶

Komedaには複数のレイヤー入力パイプラインがあります、参照: 単一パイプラインデータフロー - Slaveが有効なデュアルパイプライン

最も簡単な方法は、プレーンを固定されたレイヤーパイプラインにバインディングすることですが、Komedaの機能を考慮してください:

  • レイヤースプリット、参照 レイヤー(入力)パイプライン

    レイヤースプリットは複雑な機能で、大きな画像を2つの部分に分割し、2つのレイヤーと2つのスケーラーで個別に処理します。ただし、分割後の画像中央にエッジの問題や効果が生じる可能性があります。このような問題を回避するには、複雑な分割計算とレイヤーおよびスケーラーへの特別な設定が必要です。このようなハードウェア関連の複雑さはユーザー側に隠すべきです。

  • スレーブパイプライン、参照 Slaveが有効なデュアルパイプライン

    compizコンポーネントはアルファ値を出力しないので、スレーブパイプラインは下層レイヤーの合成にのみ使用可能です。Komedaドライバーはこの制限をユーザーに隠したいです。これを実現するには、plane_state->zposに基づいて適切なレイヤーを選択します。

したがって、KomedaではKMS-Planeが固定されたkomedaレイヤーパイプラインを表すのではなく、同じ機能を持つ複数のレイヤーを表します。Komedaは1つのKMS-Planeの要件に合った1つまたは複数のレイヤーを選択します。

struct komeda_component {

komedaコンポーネント検証¶

Komedaには複数のコンポーネントタイプがありますが、検証プロセスは通常以下のステップを含みます:

int komeda_xxxx_validate(struct komeda_component_xxx xxx_comp,
            struct komeda_component_output *input_dflow,
            struct drm_plane/crtc/connector *user,
            struct drm_plane/crtc/connector_state, *user_state)
{
     setup 1: check if component is needed, like the scaler is optional depending
              on the user_state; if unneeded, just return, and the caller will
              put the data flow into next stage.
     Setup 2: check user_state with component features and capabilities to see
              if requirements can be met; if not, return fail.
     Setup 3: get component_state from drm_atomic_state, and try set to set
              user to component; fail if component has been assigned to another
              user already.
     Setup 3: configure the component_state, like set its input component,
              convert user_state to component specific state.
     Setup 4: adjust the input_dflow and prepare it for the next stage.
}

komedaをLinuxモジュールドライバとして構築¶

現在、2段階のデバイスがあります:

  • komeda_dev: 実際のディスプレイハードウェアを記述します

  • komeda_kms_dev: komeda_devをDRM-KMSに接続またはアタッチします

すべてのkomeda操作はkomeda_devまたはkomeda_kms_devによって提供または実行されます。モジュールドライバーはLinuxコマンド（probe/remove/pm）をkomeda_devまたはkomeda_kms_devに渡すための単純なラッパーです

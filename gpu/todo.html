このセクションには、カーネルのDRMグラフィックスサブシステムにおける小さなメンテナンスタスクの一覧が含まれており、初心者向けのプロジェクトとして利用可能。または暇な雨の日に実施するのに適しています。

難易度¶

タスクをレベルごとに分類してわかりやすくしています:

初心者向け: DRMサブシステムの導入に適したタスク。

中級者向け: DRMサブシステムでの作業経験や、特定のGPU/ディスプレイグラフィックス知識が必要なタスク。デバッグを行う際には、関連するハードウェア（または仮想ドライバのセットアップ）がテスト用に利用可能であることが望ましい。

上級者向け: DRMサブシステムおよびグラフィックス関連の知識をある程度理解している必要がある複雑なタスク。通常は開発およびテストに必要な関連するハードウェアが必要です。

既存のKMSドライバをアトミックモード設定に変換¶

3.19にはアトミックモードセットインターフェースとヘルパーが導入され、ドライバの変換が可能になりました。現代のコンポジタ（例: WaylandやAndroidのSurfaceflinger）はアトミックモードセットインターフェースを強く望んでいるため、これは明るい未来に関する話です。

平面アトミックチェックヘルパを改善¶

GEMドライバからdev->struct_mutexを除去¶

dev->struct_mutex はレガシ時代からのビッグDRMロックで、すべてに感染していました。現代のドライバでは、GEMバッファオブジェクトの破壊をシリアル化する場所のみが必須です。残念ながらドライバはこのロックを保持し、コンテキストに応じて unreference または unreference_locked を呼び出す必要があります。

Core GEMには struct_mutex 4.8以降はもうありません。また、すべてのドライバーにcallbackを提供しています。 gem_free_object_unlocked 必要なドライバーについては struct_mutex すべてのドライバーにcallbackを提供しています。

代替として、ドライバ専用のロックを使用する必要があります。難しい点はBOの解放関数で、それらはもうロックを確実に取得できなくなりました。 struct_mutex 代わりに、状態は適切な下位ロックで保護するか、クリーンアップ作業をワーカースレッドに押し付ける必要があります。パフォーマンスが重要なドライバーでは、バッファごとのオブジェクトとコンテキストごとのロックスキーマを使用する方が良いかもしれません。現在は msm および i915 ドライバーのみが使用しています。 struct_mutex.

ジェネリックfbdev defioサポート¶

fbdevコア内のdefioサポートコードには特定の要件があり、ドライバがfbdev用に特別なフレームバッファを持つ必要があります。主な問題は、struct page自身の一部のフィールドを使用しているため、shmem gemオブジェクト（および他のもの）が破壊される点です。defioをサポートするには、影響を受けたドライバがシャドウバッファを使用する必要がありますが、これによりCPUおよびメモリのオーバーヘッドが発生する可能性があります。

解決策として、drm fbdevエミュレーション内で独自のdefio mmapコードを書くことが考えられます。これには、既存のmmap操作を完全にラップし、write-protect/mkwriteのトリックを実行した後ですべてをフォワーディングする必要があります:

  • drm_fbdev_fb_mmapヘルパー内でdefioが必要な場合、デフォルトのページプロテクションを書き込み保護に変更する必要があります。例えば以下のように:

    vma->vm_page_prot = pgprot_wrprotect(vma->vm_page_prot);

  • mkwriteおよびfsyncコールバックをコアfbdev defioの実装と同様の実装で設定します。これらはすべてplain ptesで動作し、struct page自体は必要ありません。uff。これらはすべてplain ptesで動作し、struct page自体は必要ありません。

  • struct pageを破壊しないように、別個の構造体（1ページあたり1ビットのビットフィールド）で汚染されたページを追跡します。

この機能に合わせて、いくつかのigtテストケースを作成するのも良いでしょう。

drm_atomic_stateを全体に統合¶

現在、さまざまなアトミック関数は単一または少数のオブジェクト状態（例: プレーン状態）のみを引数として受け取ります。単一のオブジェクト状態は一部の単純なケースでは十分ですが、個々のオブジェクトやそれらを表すハードウェア間の依存関係を処理するには、追加のオブジェクト状態を引き出す必要があります。この追加状態の取得プロセスは非直感的でエラーが発生しやすいです。

これを修正するには、ほとんどの関数がdrm_atomic_stateを引数の一つとして受け取るべきです。他の引数は主に操作したいオブジェクト（s）になります。

例えば、

int (*atomic_check)(struct drm_plane *plane, struct drm_plane_state *state);

代わりに、

int (*atomic_check)(struct drm_plane *plane, struct drm_atomic_state *state);

実装は、drm_atomic_stateを介して必要なオブジェクト状態（s）に簡単にアクセスできます。 drm_atomic_get_plane_state(), drm_atomic_get_new_plane_state(), drm_atomic_get_old_plane_state()、および他のオブジェクトタイプの同等のメソッド。

さらに、現在多くのドライバがcommit関数内で直接object->stateポインタを参照しています。これは、より深いcommitパイプラインを許可したい場合など、今後のcommitに該当する状態を指してしまう可能性があるため、機能しません。また、非ブロッキングcommitはロックなしで実行されるため、ロックを保持せずにobject->stateポインタを参照するには重大な懸念があります。このような問題は、drm_atomic_stateなどを介して特定のcommitに関連付けられるため、回避できます。 drm_atomic_get_new_plane_state(), drm_atomic_get_old_plane_state()、など。

コアのリファクタリング¶

パンク処理を動作させる¶

これは本当に多岐にわたるタスクで、たくさんの小細かい作業があります:

  • 現在、パンクパスはテストできません。これにより常に破壊されます。主な問題は、パンクがハードIRQコンテキストからトリガーされるため、すべてのパンク関連コールバックがハードIRQコンテキストで実行される点です。少なくともfbdevヘルパーコードやドライバコードをテストできるように、drmデバッグfsファイルを通じて呼び出しをトリガーできると望ましいです。ハードIRQコンテキストは、ローカルプロセッサへのIPIを使用することで実現できます。

  • さまざまなパンクハンドラの混乱が深刻です。DRM fbdevエミュレーションヘルパーやfbconコード自体にもパンクハンドラがあります。これらがお互いに競合しないようにする必要があります。

  • drm_can_sleep() 状態が悪すぎる。通常の操作中に実際のバグを隠蔽しており、パニック時の処理には完全な解決策ではない。実際のパニックが発生している場合にのみtrueを返すようにし、すべての影響を修正する必要がある。

  • パニックハンドラは決してスリープしてはいけない。これはまた、 mutex_lock()スピンロック（NMIやhardirqがパニックを引き起こす可能性があるため）を無条件で取得することもできない。このようなパスを呼び出さないか、すべてをtrylockする必要がある。非常に複雑だ。

  • 上記のロックに関する問題のため、パニックハンドラから同期モード設定を試行するのはほぼ不可能だ。試みるとしても、プライマリ・プレーンのアトミックな操作のみが可能で、それが表示されるように祈るしかない。 set_base それ以外の処理は、後で実行されるワーカーなどに遅延させるべきだ。そうしないと、システムをより強く破壊してしまい、ネットコンソールなどにパニックを出力できなくなる。

  • また、fbconとDRM fbdevエミュレーションではなく、簡易なDRMコンソールの提案もされている。いずれkmslogがマージされる場合でも、パニック処理のトリックは両方のコンソールで動作するべきだ。

デバッグfsのサポートを整理¶

これにはいくつかの問題がある:

  • drm_info_listの->show()関数は、drm構造体へのキャストすらユーザーに任せている。これは怠慢だ。

  • おそらく、crtc/コネクタや他のKMSオブジェクトをコア内で直接debugfsファイルをサポートすべきだ。これらのオブジェクトのfuncsにはdrm_printを介したKMS状態のダンプ機能も含まれているので、すべて揃っている。このため、->show()関数は正しいオブジェクトへのポインタを返すべきだ。

  • drm_info_listはdrm_minorではなくdrm_deviceを中心にしている。何を印刷するにも、drm_device（あるいはdrm_file）が正しい対象だ。

  • drm_driver->debugfs_initのハンドラは、古い中間レイヤーのロード順序のアーティファクトだ。DRM debugfsはsysfsのように、オブジェクトに対していつでもプロパティやファイルを作成でき、コアが登録/解除時にすべてのファイルを公開/非公開する仕組みを取るべきだ。ドライバはこれらの技術的詳細に気を配らなくていい。この修正（drm_minor->drm_deviceの移行と併せて）によりdebugfs_initを削除できる。

  • すべてのdebugfs関数からリターンコードとエラーチェックを削除する。グレッグ・KHがすでにこの作業を行っている。

Contact: Daniel Vetter

レベル: 中級者

KMSのクリーンアップ¶

これらの中には、KMSの導入（2008年）からずっと続くものもある…

  • ->funcs と ->helper_private vtables をオプション化します。ドライバ内には空の関数テーブルが多数存在していますが、それらを削除する前に、helpers と drivers におけるすべてのユーザーが NULL vtable を正しくチェックしていることを確認する必要があります。

  • ->destroy コールバックを整理します。多くのコールバックは drm_*_cleanup の実装をラップしており、削除可能です。一部は最後に追加されるため、drm_*_cleanup_kfree() を追加できます。 kfree() 誤って名付けられた（歴史的要因により） drm_primary_helper_destroy() function.

レベル: 中級者

dma-bufのインポートから自動ページマッピングを削除¶

dma-buf をインポートする際、dma-buf と PRIME フレームワークは、インポートされたページをインポーターの DMA ドメインに自動的にマッピングします。 drm_gem_prime_fd_to_handle() および drm_gem_prime_handle_to_fd() インポーターが呼び出す必要があります dma_buf_attach() 実際のデバイス DMA を実行しない場合でも、CPU アクセスを通じてのみ行われる場合でも dma_buf_vmap()これは DMA 操作をサポートしない USB デバイスにとっての問題です。

この問題を修正するには、バッファ共有コードから自動的なページマッピングを削除する必要があります。修正は少し複雑です。import/export キャッシュは &drm_gem_object.import_attach にも関連しているためです。USB デバイスの問題については、DMA をサポートする限り、USB ホストコントローラーデバイスを取得することで、一時的に回避しています。そうでない場合、インポートが不要に失敗する可能性があります。

i-g-t内のKMSテストを汎用化¶

i915ドライバーチームは、i915 DRMドライバー用に幅広いテストスイートを維持しており、modesetting APIのエッジケースに関する多数のテストケースを含んでいます。これらのテスト（少なくともIntel固有のGEM機能に依存しないもの）が、どのKMSドライバーでも実行できるようにできれば素晴らしいでしょう。

i-g-tテストを非i915ドライバーで実行するための基本的な作業は完了していますが、今後は大規模に変換作業が不足しています。modesetテストではまず、非i915固有のmodesetテストを実行するために、ドムバッファを未タイルバッファに使用するインフラストラクチャを整える必要があります。

DRM外¶

fbdevドライバーをDRMに変換¶

古いハードウェア用のfbdevドライバは多数存在します。一部のハードウェアは廃盤となりましたが、いくつかは依然として十分なフレームバッファを提供しています。今後も有用なドライバはDRMに移行し、その後fbdevから削除する必要があります。

非常にシンプルなfbdevドライバは、新しいDRMドライバから作成するのが最適です。シンプルなKMSヘルパーやSHMEMは、すべての既存ハードウェアを処理できるはずです。新しいドライバのコールバック関数は、既存のfbdevコードから埋め込まれます。

複雑なfbdevドライバは、DRMドライバへ段階的にリファクタリングできます。DRM fbconvヘルパーや[1]で説明されているように、DRMコアインフラストラクチャとfbdevドライバインターフェースの間のトランジションレイヤーを提供します。fbconvヘルパーの上に新しいDRMドライバを作成し、fbdevドライバをコピーしてDRMコードに接続します。複数のfbdevドライバの例は[1]に、このプロセスのチュートリアルは[2]にあります。結果として得られるのは、X11とWestonを実行可能な基本的なDRMドライバです。

  • [1] https://gitlab.freedesktop.org/tzimmermann/linux/tree/fbconv

  • [2] https://gitlab.freedesktop.org/tzimmermann/linux/blob/fbconv/drivers/gpu/drm/drm_fbconv_helper.c

Contact: Thomas Zimmermann <tzimmermann@suse.de>

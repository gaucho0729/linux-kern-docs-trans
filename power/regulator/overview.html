Linux パワーレギュレータフレームワーク¶

概要¶

このフレームワークは、電圧および電流レギュレータを制御するための標準的なカーネルインターフェースを提供することを目的としています。

システムがレギュレータの電力出力を動的に制御できるようにすることで、省電力化とバッテリー寿命の延長を目的としています。これは電圧レギュレータ（電圧出力が制御可能）および電流吸収器（電流制限が制御可能）の両方に適用されます。

  1. 2008 Wolfson Microelectronics PLC.

Author: Liam Girdwood <lrg@slimlogic.co.uk>

用語¶

このドキュメントで使用される用語:

  • レギュレータ

    • 他のデバイスに電力を供給する電子デバイス。ほとんどのレギュレータは出力の有効/無効を制御でき、一部は出力電圧および/または電流を制御できます。

      入力電圧 -> レギュレータ -> 出力電圧

  • PMIC

    • 電源管理IC。複数のレギュレータを含むことが多く、他のサブシステムも含むことがあります。

  • コンシューマ

    • レギュレータによって電力を供給される電子デバイス。コンシューマは2つのタイプに分類されます:-

      静的: コンシューマは供給電圧や電流制限を変更しません。電源の有効/無効のみを制御します。供給電圧はハードウェア、ブートローダー、ファームウェア、またはカーネルボード初期化コードによって設定されます。

      動的: コンシューマは動作要件に応じて供給電圧や電流制限を変更する必要があります。

  • 電源ドメイン

    • レギュレータ、スイッチ、または他の電源ドメインの出力電力によって電力を供給される電子回路。

      供給レギュレータはスイッチの後ろに配置されることがあります。つまり:

      Regulator -+-> Switch-1 -+-> Switch-2 --> [Consumer A]
           |             |
           |             +-> [Consumer B], [Consumer C]
           |
           +-> [Consumer D], [Consumer E]

      これは1つのレギュレータと3つの電源ドメインです:

      • ドメイン1: スイッチ-1、コンシューマDおよびE。

      • ドメイン2: スイッチ-2、コンシューマBおよびC。

      • ドメイン3: コンシューマA。

      これは「供給」関係を表しています:

      ドメイン-1 –> ドメイン-2 –> ドメイン-3。

      電源ドメインには他のレギュレータによって電力を供給されるレギュレータが含まれることがあります。つまり:

      Regulator-1 -+-> Regulator-2 -+-> [Consumer A]
             |
             +-> [Consumer B]

      これにより2つのレギュレータと2つの電源ドメインが得られます:

      • ドメイン1: レギュレータ-2、コンシューマB。

      • ドメイン2: コンシューマA。

      そして「供給」関係は:

      ドメイン-1 –> ドメイン-2

  • 制約

    • 制約はパフォーマンスやハードウェア保護のための電源レベルを定義します。制約は3つのレベルで存在します:

      レギュレータレベル: このレベルはレギュレータハードウェアの動作パラメータによって定義され、レギュレータデータシートで指定されます。つまり:

      • 出力電圧は800mV -> 3500mVの範囲です。

      • レギュレータ電流出力制限は5Vで20mAですが、10Vで10mAです。

      電源ドメインレベル: このレベルはカーネルレベルのボード初期化コードによってソフトウェアで定義されます。これは電源ドメインを特定の電源範囲に制限するために使用されます。つまり:

      • ドメイン-1電圧は3300mV

      • ドメイン-2電圧は1400mV -> 1600mV

      • ドメイン-3電流制限は0mA -> 20mA。

      コンシューマレベル: このレベルはコンシューマドライバが動的に電圧または電流制限レベルを設定することによって定義されます。

      例: コンシューマバックライトドライバがLCDの照度を上げるために電流を5mAから10mAに増やすと、次の通りレベルを通じて伝達されます:-

      消費者: LCDの明るさを増やす必要があります。明るさテーブルから次の電流mA値を検索し、リクエストしてください（消費者ドライバーは、同じ参照デバイスを基にした複数のパーソナリティで使用される可能性があります）。

      電源ドメイン: 新しい電流制限値が、このドメインおよびシステム状態（例: バッテリー電源、USB電源）のドメイン動作限界内に含まれていますか？

      レギュレータドメイン: 新しい電流制限値が、入出力電圧のレギュレータ動作パラメータ内に含まれていますか？

      レギュレータリクエストがすべての制約テストを通過した場合、新しいレギュレータ値が適用されます。

設計¶

このフレームワークはSoCベースのデバイスを対象として設計されていますが、非SoCデバイスにも適用可能であり、以下の4つのインターフェースに分割されています:-

  1. 消費者ドライバーインターフェース。

    これはカーネルクロックインターフェースと類似したAPIを使用しており、消費者ドライバーはレギュレータを取得・解放（現在はクロックと同様に）し、電圧、電流制限、モード、有効/無効の取得/設定が可能です。これにより、消費者が供給電圧および電流制限を完全に制御できるようになります。また、使用されていない場合はコンパイルされないため、レギュレータベースの電源制御がないシステムでもドライバーを再利用できます。

    参照 レギュレータ消費者ドライバインターフェース

  2. レギュレータドライバーインターフェース。

    レギュレータドライバーがレギュレータを登録し、コアに操作を提供できるようにします。また、レギュレータイベントをクライアントに伝播するための通知コールチェーンも備えています。

    参照 レギュレータドライバインターフェース

  3. マシンインターフェース。

    これはマシン固有のコード用のインターフェースで、各レギュレータに対して電圧/電流ドメイン（制約付き）を作成できます。これにより、クライアントドライバーのバグによって引き起こされる過電圧や過電流によるデバイスの破損を防ぐ制約を提供します。また、レギュレータツリーの作成も可能で、一部のレギュレータが他のレギュレータによって供給される（クロックツリーに似た）構造を実現します。

    参照 レギュレータマシンドライバインターフェース

  4. ユーザースペースABI。

    このフレームワークは、sysfsを介して多くの有用な電圧/電流/オペレーションモードデータをユーザースペースにエクスポートします。これにより、デバイスの電力消費状況のモニタリングが可能になります。

    Documentation/ABI/testing/sysfs-class-regulatorを参照してください

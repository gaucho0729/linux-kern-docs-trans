ヒーバートーションおよびスリープのデバッグ¶

  1. 2007 Rafael J. Wysocki <rjw@sisk.pl>, GPL

1. ヒbernationのテスト (通称: suspend to disk または STD)¶

ヒbernationが正常に動作するか確認するには、「reboot」モードでhibernationを試してみることができます:

# echo reboot > /sys/power/disk
# echo disk > /sys/power/state

システムがhibernation画像を作成し、再起動して復元し、開始した移行のコマンドプロンプトに戻ることを確認してください。もしこれが起きた場合、ヒbernationはおそらく正しく動作しています。ただし、信頼性を確保するためには、連続してテストを複数回行う必要があります。[これは必要です、なぜなら一部の問題は、システムのスリープと復元を2回目に試したときだけ現れるからです。] さらに、「reboot」モードと「shutdown」モードでhibernationを行うと、PMコアが一部のプラットフォーム関連のコールバックをスキップします。これはACPIシステムではhibernationが動作するために必要な場合があります。したがって、あなたのマシンが「reboot」モードでhibernationや復元に失敗した場合、「platform」モードを試してください:

# echo platform > /sys/power/disk
# echo disk > /sys/power/state

これはhibernationのデフォルトかつ推奨されるモードです。

残念ながら、一部の破損したBIOSを持つシステムでは「platform」モードのhibernationは動作しません。そのような場合、「shutdown」モードのhibernationが動作する可能性があります:

# echo shutdown > /sys/power/disk
# echo disk > /sys/power/state

(これは「reboot」モードと類似していますが、システムの復元には電源ボタンを押す必要があります。)

「platform」モードもしくは「shutdown」モードのhibernationが動作しない場合、問題の原因を特定する必要があります。

a) ヒbernationのテストモード¶

ヒbernationがシステムで失敗する理由を確認するには、カーネルがCONFIG_PM_DEBUGが設定されている場合に利用できる特別なテスト機能を使用できます。この場合、/sys/power/pm_testというファイルを使用して、hibernationコアがテストモードで動作させることができます。利用可能なテストモードは5種類あります:

freezer

  • プロセスの凍結をテストする

devices

  • プロセスの凍結とデバイスの停止をテストする

platform

  • プロセスの凍結、デバイスの停止、プラットフォームグローバル制御メソッドをテストする 1

processors

  • プロセスの凍結、デバイスの停止、プラットフォームグローバル制御メソッドをテストする 1 および非起動CPUの無効化

コア

  • プロセスの凍結、デバイスの停止、プラットフォームグローバル制御メソッドをテストする1, 非起動CPUの無効化とプラットフォーム/システムデバイスの停止をテストする

1(1,2,3)

プラットフォームグローバル制御メソッドはACPIシステムでのみ利用可能であり、hibernationモードが「platform」に設定されている場合にのみテストされます。

これらを使用するには、/sys/power/pm_test に該当する文字列を記述する必要があります（例:「devices」はプロセスの凍結とデバイスの待機状態のテストに使用）。標準的な休止状態のコマンドを実行します。たとえば、「devices」テストモードを「platform」モードの休止状態と併用する場合は、以下の手順を行います。

# echo devices > /sys/power/pm_test
# echo platform > /sys/power/disk
# echo disk > /sys/power/state

次に、カーネルはプロセスを凍結し、デバイスを待機状態に移行して、数秒（デフォルトでは5秒ですが、suspend.pm_test_delay モジュールパラメータで設定可能）、デバイスを再起動し、プロセスを解凍します。もし「platform」を /sys/power/pm_test に記述した場合、デバイスを待機状態にした後、カーネルはプラットフォームファームウェアを休止状態に準備するために使用されるグローバルコントロールメソッド（例: ACPI グローバルコントロールメソッド）を追加で呼び出します。次に、設定可能な秒数待機した後、休止状態をキャンセルするためのプラットフォーム（例: ACPI）グローバルメソッドを呼び出します。

/sys/power/pm_test に「none」を記述すると、カーネルは通常の休止状態/待機状態操作に切り替えます。また、読み取り可能状態では、/sys/power/pm_test は現在のテストレベルを括弧で示しながら、すべての利用可能なテスト（「none」を含む）をスペースで区切ったリストとして表示します。

一般的に、ご覧の通り、各テストレベルは前のレベルよりより「深刻」であり、「core」レベルでは休止状態イメージを作成せずにハードウェアとドライバを最も詳細にテストします。明らかに、「devices」テストが失敗した場合、「platform」テストも失敗し、同様に「core」テストも失敗します。したがって、一般的なルールとして、テストモードは「freezer」から「devices」、「platform」、「processors」まで「core」まで順に試す必要があります（各レベルで複数回テストを行い、ランダムな要因を避けるようにします）。

「freezer」テストが失敗した場合、凍結できないタスクが存在します（この場合、dmesg の出力を分析することで、問題のタスクを特定できます）。このレベルでの失敗は、タスク凍結サブシステムの問題を示しており、報告する必要があります。

「devices」テストが失敗した場合、おそらくドライバがデバイスを待機状態に移行できず、または再起動できず（後者の場合、テスト後システムが停止したり不安定になる可能性があるため、注意が必要です）。このドライバを特定するには、以下のルールに従って二分法を実施できます：

  • テストが失敗した場合、現在ロードされているドライバの半分をアンロードし、再度試行してください（これにはシステムの再起動が必要となる可能性があるため、テスト前のロード済みドライバを必ずメモしてください）

  • テストが成功した場合、最も最近アンロードしたドライバの半分をロードし、再度試行してください。

故障しているドライバ（複数ある場合もあります）を特定した後は、ヒーバートーション（省電力モード）を行うたびにそのドライバを必ずアンロードする必要があります。その際は、ドライバの問題を必ず報告してください。

すべてのモジュールをアンロードした後でも「デバイス」テストが失敗する可能性があります。その場合は、カーネル設定でモジュールとしてコンパイル可能なドライバを確認し、それらをモジュールとしてコンパイルして再度テストしてください。また、「noapic」「noacpi」や「acpi=off」などの特別なカーネルコマンドラインオプションを試してみるのも有効です。

「プラットフォーム」テストが失敗した場合、システムのプラットフォーム（例：ACPI）ファームウェアの処理に問題があります。この場合、ヒーバートーションの「プラットフォームモード」は動作しない可能性が高く、代替として「シャットダウンモード」を試すこともできますが、これは一時的な対処法です。

「プロセッサ」テストが失敗した場合、非起動CPUの無効化/有効化が正常に動作しない（これはSMPシステムでのみ問題となる可能性があります）ため、問題を報告してください。その際、/sys/devices/system/cpu/cpu*/onlineというsysfs属性を使用して非起動CPUを手動でオフ/オンにして動作確認するのも有効です。

「コア」テストが失敗した場合、システム/プラットフォームデバイスのスリープ処理が失敗しています（これらのデバイスは1つのCPUで割り込みをオフにしてスリープ状態にします）。この問題はほぼ間違いなくハードウェア関連の深刻な問題であるため、必ず報告してください。

「プラットフォーム」「プロセッサ」「コア」のいずれかのテストが失敗すると、システムがフリーズしたり不安定になる可能性があります。ご注意ください。このような失敗はハードウェア関連の深刻な問題を示すことが多く、必ず報告してください。

b) 最小構成でのテスト¶

すべてのヒbernationテストモードが正常に動作する場合、システムを「init=/bin/bash」コマンドラインパラメータで起動し、「reboot」、「shutdown」、「platform」モードでhibernationを試みることができます。もし動作しない場合、おそらくカーネルに静的にコンパイルされているドライバに問題があり、より多くのドライバをモジュールとしてコンパイルして個別にテストする必要があります。それ以外の場合は、モジュールドライバに問題があり、その問題を特定するには、通常使用するモジュールの半分をロードして、アルゴリズムに従ってバイナリサーチを行います：- n個のモジュールがロードされていて、スリープと復元が失敗する場合、n/2個のモジュールをアンロードして再度試す（これにはおそらくシステムの再起動が必要です）- n個のモジュールがロードされていて、スリープと復元が成功する場合、n/2個のモジュールを追加して再度試す。

再度、問題を引き起こしているモジュール（複数ある場合）が見つかった場合、毎回hibernationの前にそのモジュール（たち）をアンロードする必要があります。また、その問題を報告してください。

c) 「test_resume」hibernationオプションの使用¶

/sys/power/diskは、hibernation画像を作成した後に行うべき動作をカーネルに伝える一般的な設定です。利用可能なオプションの一つに「test_resume」があり、これにより作成した画像をすぐに復元するために使用されます。つまり、以下の手順を実行した後、

# echo test_resume > /sys/power/disk
# echo disk > /sys/power/state

hibernation画像が作成され、その画像から即座にresumeがトリガーされます。プラットフォームファームウェアの関与は一切ありません。

このテストは、hibernationからの復元に失敗する原因がプラットフォームファームウェアとの悪意的な相互作用に関係しているかを確認するために使用できます。つまり、上述のテストが常に成功するが、実際のhibernationからの復元が動作しないか信頼性が低い場合、プラットフォームファームウェアが原因である可能性があります。

復元用に異なるカーネルを用いることが可能なアーキテクチャやプラットフォーム（つまり、画像からストレージから読み込み、メモリにロードするカーネルが画像に含まれているカーネルと異なる）や、カーネルアドレス空間ランダム化をサポートする場合にも、このテストは復元に失敗する原因が復元用カーネルと画像カーネルの違いに関係しているかを確認するために使用できます。

d) 高度なデバッグ¶

システムの最小構成でヒbernationが動作しない場合、ドライバをモジュールとしてコンパイルするのも現実的でない、または一部のモジュールがアンロードできない場合、問題の原因を特定するためにはより高度なデバッグ技術を使用できます。まず、ボックスにシリアルポートがある場合、'no_console_suspend'パラメータでカーネルを起動し、シリアルコンソールを使用してカーネルメッセージをログに残すことができます。これにより、スリープ（再開）失敗の原因についての情報が得られる可能性があります。代替案として、firewireポートを使用してfirescopeでデバッグすることも可能です（http://v3.sk/~lkundrak/firescope/)。x86では、PM_TRACEメカニズムを使用することも可能です。これは s2ram の動作方法 .

2. RAMへのスリープ（STR）テスト¶

STRが正常に動作するかを確認するには、s2ramツールを使用するのが一般的に便利です。このツールは http://suspend.sf.net から入手でき、ドキュメンテーションは http://en.opensuse.org/SDB:Suspend_to_RAM (S2RAM_LINK)にあります。

つまり、/sys/power/pm_test（カーネルがCONFIG_PM_DEBUGでコンパイルされている場合に利用可能）に「freezer」、「devices」、「platform」、「processors」、「core」のいずれかを書き込むと、指定された文字に応じたテストモードでスリープコードが動作します。STRテストモードはhibernationの場合と同じように定義されているため、詳細についてはセクション1を参照してください。特に、「core」テストモードは、プラットフォームファームウェアを実際に呼び出してシステムをスリープ状態にするのを除いて、すべてのテストを実行できます。

/sys/power/pm_testを用いたテストにより、スリープまたは再開時にデバイスを制御できないドライバを特定できる場合があります。このようなドライバは、STRの移行のたびに必ずアンロードする必要があります。

次に、S2RAM_LINKの指示に従ってシステムをテストできますが、'out of the box'で動作しない場合、'init=/bin/bash'で起動し、最小構成でs2ramをテストする必要があります。その場合、セクション1に記載された手順に類似した手順により、失敗しているドライバを特定できる可能性があります。失敗しているドライバを発見した場合は、STRの移行（つまりs2ramを実行する前）のたびに必ずアンロードする必要があります。問題が発生したドライバについては、問題を報告してください。

suspend to RAMの統計情報を表示するdebugfsエントリがあります。以下はその出力例です：

# mount -t debugfs none /sys/kernel/debug
# cat /sys/kernel/debug/suspend_stats
success: 20
fail: 5
failed_freeze: 0
failed_prepare: 0
failed_suspend: 5
failed_suspend_noirq: 0
failed_resume: 0
failed_resume_noirq: 0
failures:
  last_failed_dev:      alarm
                        adc
  last_failed_errno:    -16
                        -16
  last_failed_step:     suspend
                        suspend

Field successはsuspend to RAMの成功回数を示し、field failは失敗回数を示します。その他はsuspend to RAMの異なるステップごとの失敗回数を示します。suspend_statsは最後に2つの失敗したデバイス、エラー番号、および失敗したステップをリストします。

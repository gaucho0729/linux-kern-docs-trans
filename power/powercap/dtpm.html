ダイナミックサーマルパワーマネジメントフレームワーク¶

埋め込み分野では、SoCの複雑さによりホットスポットの数が増加しており、温度が規範的かつ法的に定義された「皮膚温度」を超えないようにするため、これらを全体で監視・制御する必要があります。

もう一つの側面は、与えられた電力予算内で性能を維持することです。例えばバーチャルリアリティでは、CPUが他の処理を実行している間、パフォーマンスが制限されるとユーザーがめまいを感じるため、電力制限を回避する必要があります。あるいは、他のデバイスの消費電力と比較して過剰な消費電力がある場合、バッテリーの充電を減らすなどの対応が必要です。

アプリケーションのプロファイルに応じてデバイスの電力を制限するためには、ユーザー空間が最も適切な場所です。ユーザー空間はプラットフォームに関する知識を持っています。

ダイナミックサーマルパワーマネジメント（DTPM）は、デバイスの電力を制限し、または複数のデバイス間で電力予算をバランスを取る技術です。

DTPMフレームワークは、デバイスの電力管理を行うための統一インターフェースを提供します。

概要¶

DTPMフレームワークは、powercapフレームワークに依存し、sysfsディレクトリにpowercapエントリを生成し、バックエンドドライバーを実装して電力管理可能なデバイスと接続します。

DTPMは、デバイス間で共有される電力制約を表すツリー表現であり、デバイスの物理的位置とは関係ありません。

ツリーのノードは、子ノードの電力特性とその電力制限をまとめた仮想的な説明です。

ツリーの葉は、実際の電力管理可能なデバイスです。

例えば：

SoC
 |
 `-- pkg
      |
      |-- pd0 (cpu0-3)
      |
      `-- pd1 (cpu4-5)

pkg電力はpd0とpd1の電力数値の合計になります：

SoC (400mW - 3100mW)
 |
 `-- pkg (400mW - 3100mW)
      |
      |-- pd0 (100mW - 700mW)
      |
      `-- pd1 (300mW - 2400mW)

ノードがツリーに挿入される際、その電力特性は親ノードに伝播されます：

SoC (600mW - 5900mW)
 |
 |-- pkg (400mW - 3100mW)
 |    |
 |    |-- pd0 (100mW - 700mW)
 |    |
 |    `-- pd1 (300mW - 2400mW)
 |
 `-- pd2 (200mW - 2800mW)

各ノードは、兄弟ノードにおける電力消費の割合を2^10ベースで示す重みを持っています：

SoC (w=1024)
 |
 |-- pkg (w=538)
 |    |
 |    |-- pd0 (w=231)
 |    |
 |    `-- pd1 (w=794)
 |
 `-- pd2 (w=486)

 Note the sum of weights at the same level are equal to 1024.

ノードに電力制限が適用されると、その重みに応じて子ノードに配分されます。例えば、「SoC」ルートノードに3200mWの電力制限を設定すると、結果として以下のツリーになります：

SoC (w=1024) <--- power_limit = 3200mW
 |
 |-- pkg (w=538) --> power_limit = 1681mW
 |    |
 |    |-- pd0 (w=231) --> power_limit = 378mW
 |    |
 |    `-- pd1 (w=794) --> power_limit = 1303mW
 |
 `-- pd2 (w=486) --> power_limit = 1519mW

フラットな説明¶

ルートノードが作成され、すべてのノードの親になります。この説明は最も単純で、ユーザー空間に電力制限をサポートするすべてのデバイスのフラットな表現を提供します。

階層的な説明¶

電力制限をサポートするさまざまなデバイスは階層的に表現されています。1つのルートノードがあり、すべての中間ノードは子ノードをグループ化し、それらは中間ノードでも実際のデバイスでもあります。

中間ノードは電力情報を集約し、ノードの重みに基づいて電力制限を設定する機能を提供します。

ユーザースペースAPI¶

概要で述べたように、DTPMフレームワークはpowercapフレームワーク上に構築されています。したがってsysfsインターフェースは同じであり、詳細についてはpowercapドキュメンテーションを参照してください。

  • power_uw: その瞬間の電力消費量。ノードが中間ノードである場合、電力消費量はすべての子ノードの電力消費量の合計になります。

  • max_power_range_uw: 最大電力から最小電力を引いた電力範囲です。

  • name: ノードの名前。これは実装依存であり、ユーザー空間では推奨されませんが、複数のノードが同じ名前を持つことができます。

  • constraint_X_name: 制約の名前です。

  • constraint_X_max_power_uw: ノードに適用される最大電力制限です。

  • constraint_X_power_limit_uw: ノードに適用される電力制限です。constraint_X_max_power_uwに設定された値がある場合、制約は削除されます。

  • constraint_X_time_window_us: このファイルの意味は制約番号に依存します。

制約¶

  • 制約0: 電力制限は時間制限なしに即座に適用されます。

カーネルAPI¶

概要¶

DTPMフレームワークは電力制限のバックエンドサポートを持っていません。これは汎用的であり、さまざまなドライバがバックエンド部分を実装し、電力制限の制約ツリーを作成するためのAPIを提供します。

プラットフォームがツリーのノードを割り当ててリンクする初期化関数を提供する必要があります。

特殊なマクロがノードを宣言し、説明構造体を通じて対応する初期化関数を宣言する役割を持っています。これはオプションの親フィールドを含み、起動時に既存のツリーにさまざまなデバイスを接続する機能を提供します。

例えば：

struct dtpm_descr my_descr = {
        .name = "my_name",
        .init = my_init_func,
};

DTPM_DECLARE(my_descr);

DTPMツリーのノードはdtpm構造体で記述されます。新しい電力制限可能なデバイスを追加する手順は以下の3段階で行われます：

  • dtpmノードを割り当てます

  • dtpmノードの電力番号を設定します

  • dtpmノードを登録します

dtpmノードの登録はpowercap opsを通じて行われます。基本的に、電力と制限の取得・設定に必要なコールバック関数を実装する必要があります。

代替として、挿入するノードが中間ノードである場合、将来の親として挿入するための単純な関数が利用可能です。

デバイスの電源特性が変化する場合、新しい電源数値と重みをもとにツリーを更新する必要があります。

用語¶

  • dtpm_alloc() : dtpm構造体を割り当ておよび初期化する

  • dtpm_register() : dtpmノードをツリーに追加する

  • dtpm_unregister() : dtpmノードをツリーから削除する

  • dtpm_update_power() : dtpmノードの電源特性を更新する

1. はじめに¶

I/Oデバイスのランタイム電源管理（ランタイムPM）のサポートは、電源管理コア（PMコア）レベルで以下により提供されます:

  • バスタイプやデバイスドライバーがPM関連の作業項目をキューイングするためのパワーマネジメントワークキュー pm_wq。このpm_wqをランタイムPMに関連するすべての作業項目のキューイングに強く推奨します。これにより、システム全体の電源遷移（RAMへのサスペンド、ハイبرネーション、システムスリープ状態からのリザーブ）と同期することが可能になります。pm_wqは include/linux/pm_runtime.h で宣言され、kernel/power/main.c で定義されています。

  • 「power」メンバ（型は include/linux/pm.h で定義された struct dev_pm_info）内のランタイムPMに関連する複数のフィールドで、ランタイムPM操作を相互に同期するために使用できます。struct device「’（型は include/linux/pm.h で定義された struct dev_pm_info）内のランタイムPMに関連する複数のフィールドで、ランタイムPM操作を相互に同期するために使用できます。

  • 「’（include/linux/pm.h で定義）内の3つのデバイスランタイムPMコールバック。struct dev_pm_ops「’（include/linux/pm.h で定義）内の3つのデバイスランタイムPMコールバック。

  • drivers/base/power/runtime.c に定義された、ランタイムPM操作を実行する際の同期処理をPMコアが自動で行うよう設計されたヘルパーファンクションのセットです。バスタイプやデバイスドライバーはこれらの関数を使用することを推奨します。

‘struct dev_pm_ops’に存在するランタイムPMコールバック、‘struct dev_pm_info’のデバイスランタイムPMフィールド、およびランタイムPM用に提供されるコアヘルパーファンクションについて説明します。

2. デバイスランタイムPMコールバック¶

‘struct dev_pm_ops’:

struct dev_pm_ops {
      ...
      int (*runtime_suspend)(struct device *dev);
      int (*runtime_resume)(struct device *dev);
      int (*runtime_idle)(struct device *dev);
      ...
};

に定義されているデバイスランタイムPMコールバックは、以下のいずれかのサブシステムでPMコアが実行します：

  1. デバイスのPMドメインオブジェクト dev->pm_domain が存在する場合、そのデバイスのPMドメイン。

  2. dev->type と dev->type->pm が存在する場合、デバイスのタイプ。

  3. dev->class と dev->class->pm が存在する場合、デバイスのクラス。

  4. dev->bus と dev->bus->pm が存在する場合、デバイスのバスタイプ。

上記のルールで選択されたサブシステムが関連するコールバックを提供しない場合、PMコアは dev->driver->pm に格納されている対応するドライバーコールバックを直接呼び出します（存在する場合）

PMコアは常に上記の順序でどのコールバックを使用するかを確認するため、コールバックの優先順位は高い順にPMドメイン、デバイスタイプ、クラス、バスタイプの順となる。さらに、高優先度のコールバックは常に低優先度のコールバックよりも優先される。以下では、PMドメイン、バスタイプ、デバイスタイプ、クラスのコールバックをサブシステムレベルのコールバックと呼ぶ。

デフォルトでは、コールバックは割込みが有効なプロセスコンテキストで常に実行される。ただし、pm_runtime_irq_safe()というアシスタント関数を使用することで、PMコアに指定されたデバイスの->runtime_suspend()、->runtime_resume()、->runtime_idle()コールバックが割込み無効なアトミックコンテキストで実行可能であることを通知できる。これは、関連するコールバックルーチンがブロック処理やスリープを行わない必要があることを意味するが、さらにセクション4末尾に記載された同期アシスタント関数は、割込みハンドラや一般的なアトミックコンテキスト内でそのデバイスに対して使用可能である。

サブシステムレベルのスリープコールバックが存在する場合、そのコールバックはデバイスのスリープ処理を適切に処理する責任がある。これは、デバイスドライバー自身の->runtime_suspend()コールバックを実行する必要があるとは限らない（PMコアの観点では、サブシステムレベルのスリープコールバックがデバイスの処理を適切に行える限り、デバイスドライバーに->runtime_suspend()コールバックを実装する必要はない）。

  • 指定されたデバイスのサブシステムレベルスリープコールバック（または直接呼び出されたドライバースリープコールバック）が成功した後、PMコアはそのデバイスをスリープ状態とみなす。これは必ずしも低電力状態に移行したことを意味する必要はなく、ただし適切なリザーブコールバックが実行されるまで、デバイスがデータ処理を行わずCPUやRAMと通信しないことを意味する。スリープコールバックの成功後、デバイスのランタイムPM状態は「スリープ」状態となる。

  • スリープコールバックが-EBUSYまたは-EAGAINを返す場合、デバイスのランタイムPM状態は「アクティブ」のままとなり、これによりデバイスはその後必ずフルに動作可能でなければならない。

  • スリープコールバックが-EBUSYおよび-EAGAIN以外のエラーコードを返す場合、PMコアは致命的なエラーとみなし、そのデバイスのセクション4に記載されたアシスタント関数の実行を拒否する。デバイスの状態を直接「アクティブ」または「スリープ」に設定するまで、この状態を変更しない。PMコアはこの目的のために特別なアシスタント関数を提供している。

特に、ドライバがリモートウェイクアップ機能（つまり、デバイスが自身の電源状態を変更するリクエストを送信できるハードウェアメカニズム、例えばPCI PMEなど）を必要とし、device_can_wakeup()がデバイスに対して'false'を返す場合、->runtime_suspend()は-EBUSYを返すべきです。一方で、device_can_wakeup()がデバイスに対して'true'を返し、スリープコールバックの実行中にデバイスが低電力状態に移行した場合、リモートウェイクアップがデバイスに対して有効になることが期待されます。通常、ランタイムで低電力状態に移行したすべての入力デバイスに対してリモートウェイクアップが有効化されるべきです。

サブシステムレベルの再起動コールバックが存在する場合、それは 完全に責任を負います デバイスの再起動を適切に処理する責任があります。これは、デバイスドライバ自身の->runtime_resume()コールバックを実行することを含むかもしれませんが、必ずしも含む必要はありません（PMコアの観点では、サブシステムレベルの再起動コールバックがデバイスの処理を適切に行える限り、デバイスドライバで->runtime_resume()コールバックを実装する必要はありません）。

  • サブシステムレベルの再起動コールバック（または直接呼び出されたドライバ再起動コールバック）が正常に完了した後、PMコアはデバイスが完全に動作可能であるとみなします。これは、デバイスが必要なI/O操作を完了できることが必須です。このとき、デバイスのランタイムPM状態は「アクティブ」になります。

  • 再起動コールバックがエラーコードを返す場合、PMコアはこれを致命的なエラーと見なし、セクション4で説明した補助関数をデバイスに対して実行を拒否します。デバイスの状態が直接「アクティブ」または「スリープ」（PMコアが提供する特別な補助関数を用いて）に設定されるまで、この状態は維持されます。

PMコアは、デバイスがアイドル状態に見えるたびに、アイドルコールバックを実行します。これは、デバイスの使用カウンタと「アクティブ」な子デバイスのカウンタの2つのカウンターによってPMコアに通知されます。

  • これらのカウンターのいずれかをPMコアが提供する補助関数を用いて減少させ、結果としてゼロになった場合、もう一方のカウンターを確認します。そのカウンターもゼロである場合、PMコアはデバイスを引数としてアイドルコールバックを実行します。

アイドルコールバックによって実行されるアクションは、対象のサブシステム（またはドライバ）に完全に依存しますが、推奨されるアクションは、デバイスがスリープ状態に移行可能かどうか（つまり、デバイスをスリープ状態に移行するためのすべての条件が満たされているかどうか）を確認し、その場合、デバイスのスリープ要求をキューイングする必要があります。アイドルコールバックが存在しない場合、またはコールバックが0を返す場合、PMコアはデバイスのランタイムスリープを試行します。この際、オートスリープが設定されたデバイスにも対応します。要するに、pm_runtime_autosuspend()の呼び出しになります（注意点として、ドライバはこの状況下で遅延を制御するため、デバイスの最後のbusyマーキングを更新するpm_runtime_mark_last_busy()を呼び出す必要があります）。この動作を防ぐため（たとえば、コールバックルーチンが遅延スリープを開始した場合）、ルーチンはゼロ以外の値を返す必要があります。負のエラーコードはPMコアによって無視されます。

PMコアが提供する補助関数（セクション4で説明）は、デバイスに関するランタイムPMコールバックに対して以下の制約が満たされることを保証しています。

  1. コールバックは排他的です（たとえば、->runtime_suspend()は->runtime_resume()や同一デバイスの別の->runtime_suspend()と同時に実行することは禁止されています）。ただし、->runtime_suspend()または->runtime_resume()は->runtime_idle()と同時に実行可能です（ただし、同一デバイスの他のコールバックが実行中である場合は->runtime_idle()は開始されません）。

  2. ->runtime_idle()および->runtime_suspend()は、ランタイムPM状態が「active」であるデバイスに対してのみ実行可能です（つまり、PMコアはランタイムPM状態が「active」であるデバイスに対してのみ->runtime_idle()または->runtime_suspend()を実行します）。

  3. ->runtime_idle()および->runtime_suspend()は、使用カウンタがゼロであり、かつ「active」な子デバイスのカウンタがゼロであるか、または「power.ignore_children」フラグが設定されているデバイスに対してのみ実行可能です。

  4. ->runtime_resume()は、ランタイムPM状態が「suspended」であるデバイ�スに対してのみ実行可能です（つまり、PMコアはランタイムPM状態が「suspended」であるデバイスに対してのみ->runtime_resume()を実行します）。

さらに、PMコアが提供する補助関数は以下のルールに従います。

  • ->runtime_suspend()が実行されるか、実行待ちがある場合、同一デバイスに対して->runtime_idle()は実行されません。

  • ->runtime_suspend()の実行または実行スケジュールを求めるリクエストは、同じデバイスに対する待機中の->runtime_idle()の実行リクエストをすべてキャンセルします。

  • ->runtime_resume()が実行されるか、待機中の実行リクエストがある場合、同じデバイスに対する他のコールバックは実行されません。

  • ->runtime_resume()の実行リクエストは、同じデバイスに対する他のコールバックの待機中またはスケジュール済みリクエストをすべてキャンセルします（スケジュール済みオートスリープを除く）。

3. ランタイムPMデバイスフィールド¶

次のデバイスランタイムPMフィールドは、include/linux/pm.hで定義された'struct dev_pm_info'に存在します：

struct timer_list suspend_timer;

  • スケジュール（遅延）スリープおよびオートスリープリクエスト用のタイマ

unsigned long timer_expires;

  • タイマの期限（jiffies単位。この値がゼロでない場合、タイマが動作中で期限がその時間に達し、ゼロの場合タイマは動作していません）

struct work_struct work;

  • pm_wqにリクエストをキューイングするためのワーク構造体（つまり、pm_wq内のワークアイテム）

wait_queue_head_t wait_queue;

  • ヘルパ関数が他の関数の完了を待つ必要がある場合に使用する待機キュー

spinlock_t lock;

  • 同期に使用するロック

atomic_t usage_count;

  • デバイスの使用カウンター

atomic_t child_count;

  • デバイスの「アクティブ」な子の数

unsigned int ignore_children;

  • 設定されている場合、child_countの値は無視されます（ただし、依然として更新されます）

unsigned int disable_depth;

  • ヘルパ関数の無効化に使用（この値がゼロの場合、ヘルパ関数は正常に動作します）；初期値は1（つまり、すべてのデバイスでランタイムPMは初期状態で無効）

int runtime_error;

  • 致命的なエラーが発生した場合（セクション2で説明したように、コールバックがエラーコードを返した場合）、このフラグがクリアされるまでヘルパ関数は動作しません；これは失敗したコールバックで返されたエラーコードです

unsigned int idle_notification;

  • 設定されている場合、->runtime_idle()が実行中です

unsigned int request_pending;

  • 設定されている場合、待機中のリクエスト（つまり、pm_wqにキューイングされたワークアイテム）があります

enum rpm_request request;

  • 待機中のリクエストの種類（request_pendingが設定されている場合に有効）

unsigned int deferred_resume;

  • ->runtime_suspend()が実行中で、->runtime_resume()を実行する必要がありますが、スリープ完了を待つのが現実的でない場合に設定；「スリープが完了した時点で即座に再開を開始する」を意味します

enum rpm_status runtime_status;

  • デバイスのランタイムPMステータス; このフィールドの初期値はRPM_SUSPENDEDであり、これはPMコアがすべてのデバイスを実際のハードウェア状態とは関係なく初期状態で「スリープ状態」とみなすことを意味します

unsigned int runtime_auto;

  • 設定されている場合、ユーザースペースがデバイスドライバが/sys/devices/…/power/controlを通じてランタイムで電源管理を実行できるように許可していることを示します interface; pm_runtime_allow()およびpm_runtime_forbid()のヘルパ関数を介してのみ変更可能です

unsigned int no_callbacks;

  • デバイスがランタイムPMコールバックを使用していないことを示します(セクション8を参照); pm_runtime_no_callbacks()のヘルパ関数のみで変更可能です

unsigned int irq_safe;

  • ->runtime_suspend()および->runtime_resume()コールバックはスピンロックを保持し割り込みを無効にして呼び出されます

unsigned int use_autosuspend;

  • デバイスドライバが遅延されたオートスリープをサポートしていることを示します(セクション9を参照); pm_runtime{_dont}_use_autosuspend()のヘルパ関数のみで変更可能です

unsigned int timer_autosuspends;

  • PMコアがタイマーエクスプローラーが切れたときにオートスリープを実行するように試みるべきであり、通常のスリープではなく

int autosuspend_delay;

  • オートスリープに使用する遅延時間(ミリ秒単位)

unsigned long last_busy;

  • pm_runtime_mark_last_busy()ヘルパ関数が最後にこのデバイスに対して呼び出された時間(ジャイフス単位); オートスリープの不活動期間を計算するために使用されます

上記のすべてのフィールドは、「power」メンバの「struct device’.

4. ランタイムPMデバイスヘルパ関数¶

次のランタイムPMヘルパ関数はdrivers/base/power/runtime.cおよびinclude/linux/pm_runtime.hに定義されています:

void pm_runtime_init(struct device *dev);

  • struct dev_pm_info内のデバイスランタイムPMフィールドを初期化します

void pm_runtime_remove(struct device *dev);

  • デバイスをデバイス階層から削除した後、ランタイムPMが無効になるようにします

int pm_runtime_idle(struct device *dev);

  • デバイスのサブシステムレベルのアイドルコールバックを実行します; 失敗時はエラーコードを返します(-EINPROGRESSは->runtime_idle()がすでに実行中であることを意味します); コールバックがないか、コールバックが0を返す場合はpm_runtime_autosuspend(dev)を実行し、その結果を返します

int pm_runtime_suspend(struct device *dev);

  • デバイスのサブシステムレベルのスリープコールバックを実行します。成功時は0を返し、デバイスのランタイムPM状態がすでに「スリープ」状態だった場合は1を返します。失敗時はエラーコードを返し、-EAGAINまたは-EBUSYは今後再度スリープを試みるのに安全であることを意味し、-EACCESは「power.disable_depth」が0以外であることを示します。

int pm_runtime_autosuspend(struct device *dev);

  • pm_runtime_suspend()と同様ですが、オートスリープ遅延を考慮します。 遅延を考慮して実行します; pm_runtime_autosuspend_expiration()が遅延がまだ期限切れていないと判定する場合、適切なタイミングでオートスリープがスケジュールされ、0を返します。

int pm_runtime_resume(struct device *dev);

  • デバイスのサブシステムレベルのリザーブコールバックを実行します。成功時は0を返し、デバイスのランタイムPM状態がすでに「アクティブ」状態だった場合は1を返します。失敗時はエラーコードを返し、-EAGAINは今後再度リザーブを試みるのに安全である可能性があることを示しますが、「power.runtime_error」も確認する必要があります。-EACCESは「power.disable_depth」が0以外であることを示します。

int pm_request_idle(struct device *dev);

  • デバイスのサブシステムレベルのアイドルコールバックを実行するリクエストを送信します（リクエストはpm_wq内のワーキットで表されます）。成功時は0を返し、リクエストがキューに登録されていない場合はエラーコードを返します。

int pm_request_autosuspend(struct device *dev);

  • オートスリープ遅延が期限切れになったときにデバイスのサブシステムレベルのスリープコールバックを実行するスケジュールを設定します。遅延がすでに期限切れの場合は、即座にワーキットがキューに登録されます。

int pm_schedule_suspend(struct device *dev, unsigned int delay);

  • 将来、デバイスのサブシステムレベルのスリープコールバックを実行するスケジュールを設定します。'delay'は、pm_wqにスリープワーキットをキューに登録する前に待つ時間（ミリ秒単位）を表し、'delay'がゼロの場合は即座にワーキットがキューに登録されます。成功時は0を返し、デバイスのPMランタイム状態がすでに「スリープ」状態だった場合は1を返します。リクエストがスケジュールされていない（または'delay'がゼロの場合にキューに登録されていない）場合はエラーコードを返します。'delay'の新しい値が使用されます。すでに->runtime_suspend()がスケジュールされていて期限切れになっていない場合、新しい'delay'値が待つ時間として使用されます。

int pm_request_resume(struct device *dev);

  • デバイスのサブシステムレベルのリザーブコールバックを実行するリクエストを送信します（リクエストはpm_wq内のワーキットで表されます）。成功時は0を返し、デバイスのランタイムPM状態がすでに「アクティブ」状態だった場合は1を返します。リクエストがキューに登録されていない場合はエラーコードを返します。

void pm_runtime_get_noresume(struct device *dev);

  • デバイスの使用カウンターをインクリメントする

int pm_runtime_get(struct device *dev);

  • デバイスの使用カウンターをインクリメントし、pm_request_resume(dev)を実行してその結果を返す

int pm_runtime_get_sync(struct device *dev);

  • デバイスの使用カウンターをインクリメントし、pm_runtime_resume(dev)を実行してその結果を返す

int pm_runtime_get_if_in_use(struct device *dev);

  • power.disable_depthがゼロでない場合、-EINVALを返す。それ以外の場合、ランタイムPMステータスがRPM_ACTIVEであり、ランタイムPM使用カウンターがゼロでない場合、カウンターをインクリメントして1を返す。それ以外はカウンターを変更せずに0を返す

int pm_runtime_get_if_active(struct device *dev, bool ign_usage_count);

  • power.disable_depthがゼロでない場合、-EINVALを返す。それ以外の場合、ランタイムPMステータスがRPM_ACTIVEであり、ign_usage_countがtrueかデバイスのusage_countがゼロでない場合、カウンターをインクリメントして1を返す。それ以外はカウンターを変更せずに0を返す

void pm_runtime_put_noidle(struct device *dev);

  • デバイスの使用カウンターをデクリメントする

int pm_runtime_put(struct device *dev);

  • デバイスの使用カウンターをデクリメントし、結果が0の場合pm_request_idle(dev)を実行してその結果を返す

int pm_runtime_put_autosuspend(struct device *dev);

  • デバイスの使用カウンターをデクリメントし、結果が0の場合pm_request_autosuspend(dev)を実行してその結果を返す

int pm_runtime_put_sync(struct device *dev);

  • デバイスの使用カウンターをデクリメントし、結果が0の場合pm_runtime_idle(dev)を実行してその結果を返す

int pm_runtime_put_sync_suspend(struct device *dev);

  • デバイスの使用カウンターをデクリメントし、結果が0の場合pm_runtime_suspend(dev)を実行してその結果を返す

int pm_runtime_put_sync_autosuspend(struct device *dev);

  • デバイスの使用カウンターをデクリメントし、結果が0の場合pm_runtime_autosuspend(dev)を実行してその結果を返す

void pm_runtime_enable(struct device *dev);

  • デバイスのpower.disable_depthフィールドをデクリメントする。そのフィールドがゼロの場合、ランタイムPMヘルパ関数がセクション2で説明したサブシステムレベルのコールバックをデバイスに対して実行できる

int pm_runtime_disable(struct device *dev);

  • デバイスの 'power.disable_depth' フィールドをインクリメントします（そのフィールドの値が以前ゼロだった場合、この操作によりサブシステムレベルのランタイムPMコールバックが実行されなくなります）。デバイスの待機中のランタイムPM操作はすべて完了またはキャンセルする必要があります。待機中の再起動リクエストがあり、そのリクエストを満たすためにデバイスのサブシステムレベルの再起動コールバックを実行する必要があった場合、1を返します。それ以外の場合は0を返します。

int pm_runtime_barrier(struct device *dev);

  • デバイスに再起動リクエストが待機中である場合、それを同期して再起動します。その際、他の待機中のランタイムPMリクエストをキャンセルし、進行中のすべてのランタイムPM操作を完了するまで待機します。再起動リクエストが待機中で、そのリクエストを満たすためにデバイスのサブシステムレベルの再起動コールバックを実行する必要があった場合、1を返します。それ以外の場合は0を返します。

void pm_suspend_ignore_children(struct device *dev, bool enable);

  • デバイスの power.ignore_children フラグを設定または解除します。

int pm_runtime_set_active(struct device *dev);

  • デバイスの 'power.runtime_error' フラグをクリアし、デバイスのランタイムPMステータスを 'active' に設定し、親の 'active' チャイルドカウンタを適切に更新します（この関数は、'power.runtime_error' が設定されているか、'power.disable_depth' がゼロより大きい場合にのみ有効です）。デバイスの親がアクティブでなく、その親の 'power.ignore_children' フラグが設定されていない場合、エラーコードを返します。

void pm_runtime_set_suspended(struct device *dev);

  • デバイスの 'power.runtime_error' フラグをクリアし、デバイスのランタイムPMステータスを 'suspended' に設定し、親の 'active' チャイルドカウンタを適切に更新します（この関数は、'power.runtime_error' が設定されているか、'power.disable_depth' がゼロより大きい場合にのみ有効です）。

bool pm_runtime_active(struct device *dev);

  • デバイスのランタイムPMステータスが 'active' であるか、'power.disable_depth' フィールドがゼロでない場合、trueを返します。それ以外の場合はfalseを返します。

bool pm_runtime_suspended(struct device *dev);

  • デバイスのランタイムPMステータスが 'suspended' であり、'power.disable_depth' フィールドがゼロである場合、trueを返します。それ以外の場合はfalseを返します。

bool pm_runtime_status_suspended(struct device *dev);

  • デバイスのランタイムPMステータスが 'suspended' である場合、trueを返します。

void pm_runtime_allow(struct device *dev);

  • デバイスの power.runtime_auto フラグを設定し、使用カウンタを減らします（/sys/devices/…/power/control インターフェースがデバイスを実行時において電源管理可能にするために使用されます）

void pm_runtime_forbid(struct device *dev);

  • デバイスの power.runtime_auto フラグを解除し、使用カウンタを増やします（/sys/devices/…/power/control インターフェースがデバイスを実行時において電源管理から除外するための処理に使用されます）

void pm_runtime_no_callbacks(struct device *dev);

  • デバイスの power.no_callbacks フラグを設定し、/sys/devices/…/power からランタイムPM属性を削除します（またはデバイスが登録される際にはこれらの属性が追加されないようにします）

void pm_runtime_irq_safe(struct device *dev);

  • デバイスの power.irq_safe フラグを設定し、ランタイムPMコールバックが割込みを無効にして呼び出されるようにします

bool pm_runtime_is_irq_safe(struct device *dev);

  • デバイスの power.irq_safe フラグが設定されている場合、ランタイムPMコールバックが割込みを無効にして呼び出されるため true を返します

void pm_runtime_mark_last_busy(struct device *dev);

  • power.last_busy フィールドを現在の時刻に設定します

void pm_runtime_use_autosuspend(struct device *dev);

  • power.use_autosuspend フラグを設定し、オートスリープ遅延を有効にします；このフラグが以前クリアされており power.autosuspend_delay が負数の場合、pm_runtime_get_sync を呼び出します

void pm_runtime_dont_use_autosuspend(struct device *dev);

  • power.use_autosuspend フラグをクリアし、オートスリープ遅延を無効にします；このフラグが以前設定されており power.autosuspend_delay が負数の場合、デバイスの使用カウンタを減らし pm_runtime_idle を呼び出します

void pm_runtime_set_autosuspend_delay(struct device *dev, int delay);

  • power.autosuspend_delay の値を 'delay'（ミリ秒単位）に設定します；'delay' が負数の場合、ランタイムスリープは防止されます；power.use_autosuspend が設定されている場合、pm_runtime_get_sync が呼び出されるか、デバイスの使用カウンタが減らされ pm_runtime_idle が呼び出されるかどうかは、power.autosuspend_delay が負数に変更されたか、または負数から正数に戻ったかによって異なります；power.use_autosuspend が未設定の場合、pm_runtime_idle が呼び出されます

unsigned long pm_runtime_autosuspend_expiration(struct device *dev);

  • power.last_busy と power.autosuspend_delay を基に、現在のオートスリープ遅延期間がいつ期限切れになるかを計算します；遅延時間が 1000 ミリ秒以上の場合、期限切れ時間は秒単位で四捨五入されます；遅延期間がすでに期限切れているか、power.use_autosuspend が未設定の場合、0 を返します；それ以外の場合、ジャイブス単位での期限切れ時間を返します

以下の補助関数は割込みコンテキストから実行することができ、安全です:

  • pm_request_idle()

  • pm_request_autosuspend()

  • pm_schedule_suspend()

  • pm_request_resume()

  • pm_runtime_get_noresume()

  • pm_runtime_get()

  • pm_runtime_put_noidle()

  • pm_runtime_put()

  • pm_runtime_put_autosuspend()

  • pm_runtime_enable()

  • pm_suspend_ignore_children()

  • pm_runtime_set_active()

  • pm_runtime_set_suspended()

  • pm_runtime_suspended()

  • pm_runtime_mark_last_busy()

  • pm_runtime_autosuspend_expiration()

デバイスに対してpm_runtime_irq_safe()が呼び出された場合、以下の補助関数も割込みコンテキストから使用することも可能です:

  • pm_runtime_idle()

  • pm_runtime_suspend()

  • pm_runtime_autosuspend()

  • pm_runtime_resume()

  • pm_runtime_get_sync()

  • pm_runtime_put_sync()

  • pm_runtime_put_sync_suspend()

  • pm_runtime_put_sync_autosuspend()

5. ランタイムPMの初期化、デバイスの検出と除去¶

初期状態では、すべてのデバイスに対してランタイムPMは無効になっており、セクション4で説明したほとんどのランタイムPM補助関数はpm_runtime_enable()がデバイスに対して呼び出されるまで-EAGAINを返します。

さらに、すべてのデバイスの初期ランタイムPM状態は「スリープ状態」ですが、これはデバイスの実際の物理的な状態を反映する必要はありません。したがって、デバイスが初期状態でアクティブ（I/O処理が可能）である場合、pm_runtime_enable()が呼び出される前にpm_runtime_set_active()を用いて状態を「アクティブ」に変更する必要があります。

ただし、デバイスが親デバイスを持ち、親のランタイムPMが有効になっている場合、デバイスに対してpm_runtime_set_active()を呼び出すと親に影響を及ぼします（親の「power.ignore_children」フラグが設定されていない場合）。つまり、この場合、子デバイスの状態が「アクティブ」である限り、親はPMコアの補助関数を用いてランタイムスリープを実行できず、子デバイスのランタイムPMが無効（pm_runtime_enable()が呼び出されていない、またはpm_runtime_disable()が呼び出されている）であってもです。このため、pm_runtime_set_active()が呼び出されたデバイスに対しては、できるだけ早くpm_runtime_enable()を呼び出すか、pm_runtime_set_suspended()を用いて状態を再び「スリープ」に戻す必要があります。

デバイスのデフォルトの初期ランタイムPM状態（つまり、「suspended」）がデバイスの実際の状態を反映している場合、そのバスタイプのまたはドライバの->probe()コールバックは、第4節で説明するPMコアのヘルパ関数のいずれかを使用してデバイスを起動する必要があるでしょう。その場合、pm_runtime_resume()を使用する必要があります。もちろん、この目的でデバイスのランタイムPMは、pm_runtime_enable()を呼び出して事前に有効化する必要があります。

注意：デバイスがプローブ中にpm_runtime呼び出しを実行する可能性がある場合（例えば、サブシステムに登録されていてそのサブシステムがコールバックを呼び出す可能性がある場合）、pm_runtime_get_sync()とpm_runtime_put()のペアを呼び出すことで、プローブ中にデバイスが再びスリープ状態に戻らないようにする必要があります。これはネットワークデバイスレイヤーなどのシステムで発生することがあります。

->probe()が完了した後、デバイスをスリープ状態にしたい場合があります。そのため、ドライバコアは非同期のpm_request_idle()を呼び出して、その時点でデバイスのサブシステムレベルのアイドルコールバックを実行するようリクエストします。ランタイムオートスリープ機能を使用するドライバは、->probe()から戻る前に最後のbusyマーキングを更新することが望ましいです。

さらに、ドライバコアは、__device_release_driver()内のバス通知コールバックとランタイムPMコールバックの競合を防ぐ必要があります。これは、一部のサブシステムがランタイムPM機能に影響を与える操作を実行するために通知を使用するためです。これを実現するため、ドライバコアはdriver_sysfs_remove()とBUS_NOTIFY_UNBIND_DRIVER通知の前にpm_runtime_get_sync()を呼び出します。これにより、デバイスがスリープ状態にある場合でも再起動され、その処理が実行される間は再度スリープ状態にされません。

バスタイプやドライバが、->remove()ルーチンからpm_runtime_suspend()を呼び出してデバイスをスリープ状態にすることを許可するため、ドライバコアは__device_release_driver()内でBUS_NOTIFY_UNBIND_DRIVER通知を実行した後、pm_runtime_put_sync()を実行します。これにより、バスタイプやドライバは->remove()コールバックでランタイムPMと直接競合するのを避ける必要がありますが、ドライバの削除中にデバイスの処理をより柔軟に扱うことが可能になります。

->remove()コールバック内で、->probe()で行ったランタイムPMの変更を元に戻す必要があります。通常はpm_runtime_disable()、pm_runtime_dont_use_autosuspend()など、関連する関数を呼び出すことで実現します。

ユーザー空間は、デバイスドライバーが実行時においてそのデバイスの電源管理を制御できないようにする効果があります。これは、/sys/devices/…/power/control属性の値を「on」に変更することで実現され、pm_runtime_forbid()が呼び出されます。原則として、このメカニズムは、ユーザー空間がデバイスの実行時電源管理を有効にするまで、ドライバーがデバイスの実行時電源管理を無効にするためにも利用可能です。つまり、初期化中にドライバーはデバイスの実行時PM状態が「active」であることを確認し、pm_runtime_forbid()を呼び出すことができます。ただし、ユーザー空間がすでに/sys/devices/…/power/controlの値を「auto」に変更してドライバーが実行時電源管理を制御できるようにしている場合、pm_runtime_forbid()のこの使い方はドライバーを混乱させる可能性があります。

6. ランタイムPMとシステムスリープ¶

ランタイムPMとシステムスリープ（つまり、システムスリープとヒbernation、RAMスリープおよびディスクスリープとしても知られる）は複数の方法で相互作用します。デバイスがシステムスリープ開始時にアクティブな場合、すべてが簡単です。しかし、デバイスがすでにスリープしている場合、どのような処理が適切でしょうか？

デバイスはランタイムPMとシステムスリープごとに異なるウェイクアップ設定を持つ可能性があります。たとえば、ランタイムスリープではリモートウェイクアップが有効化されているが、システムスリープでは無効化されている場合（device_may_wakeup(dev)は「false」を返す）があります。このような場合、サブシステムレベルのシステムスリープコールバックはデバイスのウェイクアップ設定を変更する責任があります（デバイスドライバーのシステムスリープルーチンにその処理を委譲する場合もあります）。このような処理を行うために、デバイスを再起動して再度スリープさせる必要があるかもしれません。ドライバーがランタイムスリープとシステムスリープで異なる電源レベルやその他の設定を使用する場合にも同様です。

システム再起動中に最も簡単な方法は、システムスリープ開始前にスリープしていたすべてのデバイスをフル電源状態に戻すことです。このような処理を行う理由はいくつかあります：

  • デバイスが電源レベルやウェイクアップ設定などを切り替える必要がある場合があります。

  • リモートウェイクアップイベントがファームウェアによって失われた可能性があります。

  • デバイスの子デバイスがデバイスをフル電源状態にして自己再起動を行う必要がある場合があります。

  • ドライバーがデバイスの状態を把握しているか、デバイスの物理的な状態と一致しているかが確認できません。これはヒbernationからの再起動中に発生する可能性があります。

  • デバイスがリセットされる必要があります。

  • デバイスがスリープ状態であっても、使用カウンタが0より大きい場合、近い将来にランタイム再起動が必要になる可能性が高いためです。

システムスリープ開始前にデバイスがスリープ状態にされており、再起動時にフル電源状態に戻された場合、そのランタイムPM状態を実際のシステムスリープ後の状態に更新する必要があります。これを実行する方法は以下の通りです。

  • pm_runtime_disable(dev);

  • pm_runtime_set_active(dev);

  • pm_runtime_enable(dev);

PMコアは、->suspend()コールバックを呼び出す前にランタイム使用カウンタをインクリメントし、->resume()コールバックを呼び出す後にデクリメントします。したがって、このような一時的なランタイムPMの無効化は、ランタイムスリープの試行を永久に失うことはありません。->resume()コールバックの戻り後に使用カウンタがゼロになった場合、->runtime_idle()コールバックは通常通り呼び出されます。

しかし一部のシステムでは、システムスリープはグローバルなファームウェアまたはハードウェア操作を通じて行われません。代わりに、カーネルがハードウェアコンポーネントを協調して低電力状態に直接置きます。その後、システムスリープ状態はハードウェアコンポーネントの最終的な状態から導き出され、ハードウェア割込みや類似のメカニズムによってカーネルの制御下でシステムがその状態から起動します。その結果、カーネルは制御を他に譲ることなく、再起動時のすべてのデバイスの状態を正確に把握しています。このような状況で上記のいずれかの状況が発生しない場合（特にシステムがヒーブリッドから起動していない場合）、システムスリープ開始前のスリープ状態にあったデバイスをスリープ状態に残す方が効率的かもしれません。

このため、PMコアはデバイス階層の異なるレベル間での連携を可能にするメカニズムを提供しています。つまり、システムスリープの.prepare()コールバックがデバイスに対して正の数を返す場合、そのデバイスがランタイムスリープ状態であり、その状態が問題ないため、すべての子孫デバイスもランタイムスリープ状態に残すことが許可されます。このような場合、PMコアはすべてのそのデバイスに対してシステムスリープおよび再起動コールバックを実行しません（完全コールバックを除く）。完全コールバックは、デバイスを適切に処理する責任があります。これはヒーブリッドに関係しないシステムスリープの遷移にのみ適用されます（参照 デバイス電源管理の基礎 の属性はすべてのケースで期待通り動作する必要があります（つまり、トルボPステートを無効に設定した場合でも常にそれらの使用を防ぐ必要があります）。

PMコアは、ランタイムPMとシステムスリープ/再起動（およびヒーブリッド）コールバック間のレース条件の発生確率を減らすために以下の操作を行います：

  • システムのスリープ中に、各デバイスに対してpm_runtime_get_noresume()が呼び出され、その後サブシステムレベルの.prepare()コールバックが実行される直前に、pm_runtime_barrier()が各デバイスに対して呼び出されます。さらに、PMコアは、各デバイスに対してサブシステムレベルの.suspend_late()コールバックが実行される直前に、__pm_runtime_disable()を「false」を第二引数として呼び出します。

  • システムのリザーブ中に、各デバイスに対して.pm_runtime_enable()が、サブシステムレベルの.resume_early()コールバックが実行された直後に呼び出され、各デバイスに対して.pm_runtime_put()が、サブシステムレベルの.complete()コールバックが実行された直後に呼び出されます。

  1. 汎用サブシステムコールバック

サブシステムは、PMコアが提供する汎用電源管理コールバックセットを使用することでコードスペースを節約できます。この汎用コールバックはdriver/base/power/generic_ops.cで定義されています:

int pm_generic_runtime_suspend(struct device *dev);

  • このデバイスのドライバが提供する->runtime_suspend()コールバックを呼び出し、その結果を返します。ドライバで定義されていない場合は0を返します。

int pm_generic_runtime_resume(struct device *dev);

  • このデバイスのドライバが提供する->runtime_resume()コールバックを呼び出し、その結果を返します。ドライバで定義されていない場合は0を返します。

int pm_generic_suspend(struct device *dev);

  • デバイスがランタイムでスリープされていない場合、そのドライバが提供する->suspend()コールバックを呼び出し、結果を返します。ドライバで定義されていない場合は0を返します。

int pm_generic_suspend_noirq(struct device *dev);

  • pm_runtime_suspended(dev)が「false」を返す場合、そのデバイスのドライバが提供する->suspend_noirq()コールバックを呼び出し、結果を返します。ドライバで定義されていない場合は0を返します。

int pm_generic_resume(struct device *dev);

  • このデバイスのドライバが提供する->resume()コールバックを呼び出し、成功した場合、デバイスのランタイムPMステータスを「アクティブ」に変更します。

int pm_generic_resume_noirq(struct device *dev);

  • このデバイスのドライバが提供する->resume_noirq()コールバックを呼び出します。

int pm_generic_freeze(struct device *dev);

  • デバイスがランタイムでスリープされていない場合、そのドライバが提供する->freeze()コールバックを呼び出し、結果を返します。ドライバで定義されていない場合は0を返します。

int pm_generic_freeze_noirq(struct device *dev);

  • pm_runtime_suspended(dev)が「false」を返す場合、そのデバイスのドライバが提供する->freeze_noirq()コールバックを呼び出し、結果を返します。ドライバで定義されていない場合は0を返します。

int pm_generic_thaw(struct device *dev);

  • デバイスが実行時においてスリープ状態になっていない場合、そのドライバが提供する->thaw()コールバックを呼び出し、その結果を返す。コールバックが定義されていない場合は0を返す。

int pm_generic_thaw_noirq(struct device *dev);

  • pm_runtime_suspended(dev)が"false"を返す場合、デバイスのドライバが提供する->thaw_noirq()コールバックを呼び出し、その結果を返す。コールバックが定義されていない場合は0を返す。

int pm_generic_poweroff(struct device *dev);

  • デバイスが実行時においてスリープ状態になっていない場合、そのドライバが提供する->poweroff()コールバックを呼び出し、その結果を返す。コール,バックが定義されていない場合は0を返す。

int pm_generic_poweroff_noirq(struct device *dev);

  • pm_runtime_suspended(dev)が"false"を返す場合、デバイスのドライバが提供する->poweroff_noirq()コールバックを実行し、その結果を返す。コールバックが定義されていない場合は0を返す。

int pm_generic_restore(struct device *dev);

  • このデバイスのドライバが提供する->restore()コールバックを呼び出し、成功した場合、デバイスのランタイムPM状態を"active"に変更する。

int pm_generic_restore_noirq(struct device *dev);

  • デバイスのドライバが提供する->restore_noirq()コールバックを呼び出す。

これらの関数は、サブシステムが->runtime_idle()、->runtime_suspend()、->runtime_resume()、->suspend()、->suspend_noirq()、->resume()、->resume_noirq()、->freeze()、->freeze_noirq()、->thaw()、->thaw_noirq()、->poweroff()、->poweroff_noirq()、->restore()、->restore_noirq()などのコールバックをサブシステムレベルのdev_pm_ops構造体で提供していない場合、PMコアが使用するデフォルトの関数です。

システムスリープ、フリーズ、電源オフ、ランタイムスリープコールバックとして同じ関数を使用したいデバイスドライバは、include/linux/pm.hで定義されたUNIVERSAL_DEV_PM_OPSマクロ（最後の引数をNULLに設定する場合もある）を活用することで実現できます。

8. "コールバックなし"デバイス¶

一部の"デバイス"は親デバイスの論理的なサブデバイスであり、個別に電源管理ができない場合があります。（例としてUSBインターフェースが挙げられます。全体としてUSBデバイスが低電力モードに移行したり、ウェイクアップリクエストを送信したりできますが、個々のインターフェースではこれらは実行できません。）このようなデバイスのドライバはランタイムPMコールバックを必要としません。コールバックが存在したとしても、->runtime_suspend()と->runtime_resume()は常に0を返し、->runtime_idle()は常にpm_runtime_suspend()を呼び出します。

サブシステムは、pm_runtime_no_callbacks()を呼び出してPMコアにこれらのデバイスについて報告できます。これはデバイス構造体が初期化された後で、登録される前に行うべきですが（登録後でも問題ありません）、このルーチンはデバイスのpower.no_callbacksフラグを設定し、デバッグ以外のランタイムPM sysfs属性の作成を防ぎます。

power.no_callbacksフラグが設定されている場合、PMコアは->runtime_idle()、->runtime_suspend()、->runtime_resume()コールバックを呼びません。代わりに、スリープと再起動が常に成功すると想定し、アイドル状態のデバイスはスリープ状態に保持するとします。

その結果、PMコアはデバイスのサブシステムやドライバにランタイム電力変化を直接通知しません。代わりに、親デバイスのドライバが親の電力状態変化時に子デバイスのドライバに通知する責任を負います。

9. オートスリープ（自動遅延スリープ）¶

デバイスの電力状態を変更するには時間とエネルギーがかかるため、デバイスが長時間その状態にとどまる理由がある場合にのみ低電力状態にします。一般的なヒューリスティックでは、長期間使用されていないデバイスは今後も使用されない可能性が高いとされ、ドライバはデバイスが最小限の不活性期間を経過するまでランタイムスリープを許可すべきではありません。ヒューリスティックが最適でない場合でも、デバイスが低電力とフル電力の状態を急速に切り替えることを防ぐことができます。

「オートスリープ」という用語は歴史的な残滓です。デバイスが自動的にスリープする（サブシステムやドライバが適切なPMルーチンを呼び出す必要がある）ことを意味しません。むしろ、ランタイムスリープが望ましい不活性期間が経過するまで自動的に遅延されるということを意味します。

不活性期間はpower.last_busyフィールドに基づいて決定されます。ドライバはI/Oを実行した後、通常pm_runtime_put_autosuspend()を呼び出す直前にpm_runtime_mark_last_busy()を呼び出してこのフィールドを更新すべきです。不活性期間の望ましい長さはポリシーの問題です。サブシステムはpm_runtime_set_autos��uspend_delay()を呼び出して初期の長さを設定できますが、デバイス登録後はユーザー空間が/sys/devices/…/power/autosuspend_delay_ms属性を通じて制御します。

autosuspendを使用するには、サブシステムまたはドライバがpm_runtime_use_autosuspend()を呼び出す必要があります（デバイスの登録前に実行することをお勧めします）。その後は、各種*_autosuspend()ヘルパ関数を使用する必要があります。 *_autosuspend() 非autosuspend版のヘルパ関数ではなく、以下のヘルパ関数を使用してください：

Instead of: pm_runtime_suspend    use: pm_runtime_autosuspend;
Instead of: pm_schedule_suspend   use: pm_request_autosuspend;
Instead of: pm_runtime_put        use: pm_runtime_put_autosuspend;
Instead of: pm_runtime_put_sync   use: pm_runtime_put_sync_autosuspend.

ドライバは非autosuspend版のヘルパ関数を引き続き使用することもできます。この場合、通常の動作をしますが、時折autosuspend遅延を考慮する場合があります（pm_runtime_idleを参照）。

特定の状況では、デバイスが即座にautosuspendされないようにする必要があります。使用カウンタがゼロであり、autosuspend遅延時間が経過したにもかかわらずです。->runtime_suspend()コールバックが-EAGAINまたは-EBUSYを返す場合、次のautosuspend遅延の経過時刻が将来にある（通常はpm_runtime_mark_last_busy()が呼び出されているため）場合、PMコアが自動的にautosuspendの再スケジュールを行います。->runtime_suspend()コールバック自体では、デバイスがsuspending中（つまり、コールバックが実行中）の間、どの種類のスリープ要求も受け付けないため、この再スケジュールは行えません。

この実装は割り込みコンテキストでの非同期使用に適しています。ただし、PMコアが->runtime_suspend()コールバックをI/Oリクエストの到着と同期することができないため、競合条件が発生します。この同期はドライバがプライベートロックを使用して処理する必要があります。以下は概要の擬似コード例です：

foo_read_or_write(struct foo_priv *foo, void *data)
{
        lock(&foo->private_lock);
        add_request_to_io_queue(foo, data);
        if (foo->num_pending_requests++ == 0)
                pm_runtime_get(&foo->dev);
        if (!foo->is_suspended)
                foo_process_next_request(foo);
        unlock(&foo->private_lock);
}

foo_io_completion(struct foo_priv *foo, void *req)
{
        lock(&foo->private_lock);
        if (--foo->num_pending_requests == 0) {
                pm_runtime_mark_last_busy(&foo->dev);
                pm_runtime_put_autosuspend(&foo->dev);
        } else {
                foo_process_next_request(foo);
        }
        unlock(&foo->private_lock);
        /* Send req result back to the user ... */
}

int foo_runtime_suspend(struct device *dev)
{
        struct foo_priv foo = container_of(dev, ...);
        int ret = 0;

        lock(&foo->private_lock);
        if (foo->num_pending_requests > 0) {
                ret = -EBUSY;
        } else {
                /* ... suspend the device ... */
                foo->is_suspended = 1;
        }
        unlock(&foo->private_lock);
        return ret;
}

int foo_runtime_resume(struct device *dev)
{
        struct foo_priv foo = container_of(dev, ...);

        lock(&foo->private_lock);
        /* ... resume the device ... */
        foo->is_suspended = 0;
        pm_runtime_mark_last_busy(&foo->dev);
        if (foo->num_pending_requests > 0)
                foo_process_next_request(foo);
        unlock(&foo->private_lock);
        return 0;
}

重要な点は、foo_io_completion()がautosuspendを要求した後、foo_runtime_suspend()コールバックがfoo_read_or_write()と競合する可能性があることです。そのため、foo_runtime_suspend()はプライベートロックを保持しながら、待機中のI/Oリクエストがあるかどうかを確認する必要があります。

さらに、ユーザー空間がいつでもpower.autosuspend_delayフィールドを変更できます。ドライバがこの点を気にする場合は、->runtime_suspend()コールバック内でプライベートロックを保持しながらpm_runtime_autosuspend_expiration()を呼び出します。この関数がゼロでない値を返す場合、遅延がまだ期限切れになっていないため、コールバックは-EAGAINを返すべきです。

スワップスリープ¶

まずはいくつかの警告を確認しましょう。

警告

重大な警告

スリープと再起動の間にディスク上の何でも操作すると…

…データを永久に失うことになります。

ファイルシステムがマウントされている後にinitrdから再起動すると…

…ルートパーティションを永久に失うことになります。

[これは上記と同じケースです]

DMAをサポートしていないデバイスを使用している場合、問題が発生する可能性があります。ディスクドライバーがスリープをサポートしていない（IDEはサポートしています）場合、問題が発生する可能性もあります。スリープと再起動の間にカーネルコマンドラインを変更すると、誤動作する可能性があります。システムがスリープ中にある間にハードウェアを変更すると、これは良い考えではありませんでしたが、おそらくクラッシュするだけです。

( ) スリープ/再起動のサポートが必要です。

ソフトウェアスリープ前にUSBデバイス上のファイルシステムをマウントしている場合、再起動後にアクセスできなくなり、データを失う可能性があります。これはUSBデバイスをマウントしたまま外すのと同じ結果になります。詳しくは以下のFAQを参照してください。（これは「スタンバイ」などのより伝統的な電源状態では当てはまりません。通常、USBをオフにしません。）

スワップパーティション:

カーネルコマンドラインに resume=/dev/your_swap_partition を追加する必要があります。または /sys/power/resume で指定できます。

スワップファイル:

スワップファイルを使用している場合、カーネルコマンドラインに resume_offset=<number> を指定できます。または /sys/power/resume_offset で指定できます。

準備ができたら、以下のようにスリープします：

echo shutdown > /sys/power/disk; echo disk > /sys/power/state

  • ACPI がシステム上で十分に動作する場合は、以下を試してみてください：

    echo platform > /sys/power/disk; echo disk > /sys/power/state

  • hibernation image をスワップに書き出し、RAM にスリープする（プラットフォームがサポートする場合）には、以下を試してみてください：

    echo suspend > /sys/power/disk; echo disk > /sys/power/state

  • SATA ディスクを使用している場合、SATA スリープサポートを持つ最新のカーネルが必要です。スリープと再起動が動作するためには、ディスクドライバーがカーネルに組み込まれている必要があります（モジュールにはできません）。[モジュール化されたディスクドライバーでスリープ/再起動を行う方法もありますが、FAQ を参照してください。ただし、通常は避けるべきです。]

スリープ画像のサイズを N バイトに制限するには、

echo N > /sys/power/image_size

スリープ前（デフォルトでは、利用可能な RAM の約 2/5 に制限されます）。

  • 再起動プロセスは、resume デバイスの存在を確認し、見つかった場合、hibernation image のサインを確認します。両方とも見つかった場合、hibernation image を再開します。

  • 再起動プロセスは以下の 2 つの方法でトリガーされます：

    1. lateinit 期間中: kernel command line に resume=/dev/your_swap_partition が指定されている場合、lateinit が再起動プロセスを実行します。resume デバイスがまだプローブされていない場合、再起動プロセスが失敗し、起動が続きます。

    2. initrdまたはinitramfsから手動で: /sys/power/resumeファイルを使用してinitスクリプトから実行できます。ファイルシステムを再マウントする前に（読み取り専用でも）必ずこの操作を行う必要があります。それ以外にデータが破損する可能性があります。

ソフトウェアスリープの目標と実装についての記事¶

著者: Gábor Kuti 最終修正日: 2003-10-20（Pavel Machekによる）

アイデアと達成すべき目標¶

現在、いくつかのノートPCではスリープボタンが標準機能となっています。この機能はマシンの状態をファイルシステムまたはパーティションに保存し、スタンバイモードに移行します。後でマシンを再開する際には保存した状態をメモリに読み戻し、作業を再開できます。この機能には2つの主なメリットがあります。1つ目のメリットは、マシンが停止して再起動する時間を節約できることで、バッテリーからの動作時のエネルギー消費が非常に高いためです。もう1つのメリットは、長時間計算を続けるプロセスを中断する必要がないことです。

swsuspはマシンの状態をアクティブなスワップ領域に保存し、その後再起動または電源オフします。再開するスワップパーティションを明示的に指定する必要があります。 resume= カーネルオプション。サインチャーが見つかった場合は保存した状態をロードして復元します。オプション noresume がブートパラメータとして指定されると再開がスキップされます。オプション hibernate=nocompress がブートパラメータとして指定されると、ヒーブリネーションイメージを圧縮せずに保存します。

システムがスリープ状態にある間は、ハードウェアの追加・削除、ファイルシステムへの書き込みなどを行わないでください。

スリープ状態の概要¶

3つの異なるインターフェースを使用できます。/proc/acpiは以下のように動作します:

本当に完璧な世界では:

echo 1 > /proc/acpi/sleep       # for standby
echo 2 > /proc/acpi/sleep       # for suspend to ram
echo 3 > /proc/acpi/sleep       # for suspend to ram, but with more power
                                # conservative
echo 4 > /proc/acpi/sleep       # for suspend to disk
echo 5 > /proc/acpi/sleep       # for shutdown unfriendly the system

あるいは:

echo 4b > /proc/acpi/sleep      # for suspend to disk via s4bios

よくある質問¶

Q:

まあ、サーバーをスリープさせるのは私個人としては非常に馬鹿げたことですが…（Diego Zuccato）:

A:

サーバー用の新しいUPSを購入しました。マシンを停止せずにインストールするにはどうすればよいですか？ディスクへのスリープ、電源ケーブルの配線変更、再開。

サーバーはUPSで稼働しています。電源が切れ、UPSが30秒後に故障すると表示しています。どうすればよいですか？ディスクへのスリープ。

Q:

何か抜けているかもしれませんが、なぜ通常のI/O経路が使えないのでしょうか？

A:

通常のI/O経路を使用していますが、ロードする際にはデータを元の場所に戻すことはできません。これにより、カーネルの不一致な状態が発生し、オプス（panic）が発生する可能性があります。代わりに、未使用のメモリにイメージをロードし、その後原子的に元の場所に戻します。これは、イメージサイズがメモリの半分までに制限されることを意味します。

これには2つの解決策があります:

  • スリープ中にメモリの半分を空けておく必要があります。そうすれば、空き領域に「新しい」データを読み込み、CLIでコピーできます。

  • 特殊な「ポーリング」IDEドライバを仮定すると、0-640KBのメモリ領域をスリープ中に空けなければなりませんが、それ以外は動作します…

suspend2はこの基本的な制限を共有していますが、ユーザーのデータやディスクキャッシュを事前に保存して「使用中のメモリ」に含めないため、実際にはこの制限は解消されます。

Q:

LinuxはACPI S4をサポートしていますか？

A:

はい。これはecho platform > /sys/power/diskで行います。

Q:

suspend2とは何ですか？

A:

suspend2は「ソフトウェアスリープ2（Software Suspend 2）」と呼ばれ、swsusp.sourceforge.netから提供される2.4および2.6カーネル用のパッチとして利用可能なスリープトディスクの実装です。SMP、4GB highmem、プリエンプションのサポートを含み、拡張可能なアーキテクチャを備えており、イメージの変換（圧縮、暗号化）や書き込みバックエンド（例: swapやNFS共有[作業中]）を任意に実行できます。suspend2に関する質問は、suspend2公式サイトから取得可能なメーリングリストに送信してください。Linuxカーネルメーリングリストには送信しないでください。我々はsuspend2をメインラインカーネルに統合する方向で進んでいます。

Q:

タスクの凍結とは何ですか？なぜ使用しているのですか？

A:

タスクの凍結は、ヒーバートionやシステム全体の待機中にユーザー空間プロセスや一部のカーネルスレッドを制御するメカニズムです（一部のアーキテクチャでは）。詳細はfreezing-of-tasks.txtを参照してください。

Q:

「platform」と「shutdown」の違いは何ですか？

A:
shutdown:

Linuxで状態を保存し、BIOSに電源を切るように指示します。

platform:

Linuxで状態を保存し、BIOSに電源を切るように指示し、『スリープLED』を点滅させます。

「platform」はサポートされている場合は正しい方法ですが、「shutdown」はACPIシステムを除いて最も信頼性が高いです。

Q:

なぜ選択的なスリープというアイデアに対して強い反対意見を持っているのですか？

A:

ランタイム電源管理中に選択的なスリープを行っても問題ありませんが、スリープトディスクには無用です。（また、スリープトRAMにも利用できないと思いますが、それをお望みですか？）

では、以下の手順を提案します

  • SWAPデバイスと親をすべてスリープ

  • スナップショット

  • イメージをディスクに書き込み

  • SWAPデバイスと親をスリープ

  • 電源を切る

あらら、これは機能しません。SWAPデバイスやその親がDMAを使用している場合、データが破損します。代わりに

  • SWAPデバイスと親をすべてスリープ

  • SWAPデバイスと親を凍結

  • スナップショット

  • SWAPデバイスと親を凍結解除

  • 書込み

  • SWAPデバイスと親をスリープ

つまり、あなたは依然としてFREEZE状態が必要であり、コードはより複雑になります。(システムデバイスなどの詳細についてはまだ紹介していません)

Q:

SUSPENDとFREEZEの間には、一般的に有用な動作上の違いは見られません。

A:

FREEZEを実行するように求められたときにSUSPENDを実行しても常に正しいですが、無駄に遅くなる可能性があります。ドライバをシンプルにしたい場合は、遅さは気にしなくてよいかもしれません。後で修正できます。

ディスクなどのデバイスでは問題があります。FREEZE時にスピンダウンさせたくないのです。

Q:

再開後、システムが重いページングを行い、インタラクティブ性が非常に悪くなります。

A:

再開後に実行してみてください:

cat /proc/[0-9]*/maps | grep / | sed 's:.* /:/:' | sort -u | while read file
do
  test -f "$file" && cat "$file" > /dev/null
done

swapoff -a; swapon -aも役立つかもしれません。

Q:

swsusp中にデバイスには何が起こるのでしょうか？システムのスリープ中にデバイスが再開されているように見えます。

A:

それは正しいです。ディスクにイメージを書き込むためにデバイスを再開する必要があります。全体の流れは以下の通りです

スリープ処理

動作中のシステムで、ユーザーがディスクスリープを要求します

ユーザーのプロセスが停止します

suspend(PMSG_FREEZE): デバイスを凍結し、状態スナップショットに干渉しないようにします

状態スナップショット: 中断を無効にして、使用中のすべてのメモリをコピーします

resume(): デバイスを起動し、イメージをスワップに書き込むことができます

イメージをスワップに書き込みます

suspend(PMSG_SUSPEND): デバイスを停止し、電源を切る準備をします

電源を切ります

再開処理

(実際には非常に似ています)

動作中のシステムで、ユーザーがディスクスリープを要求します

ユーザーのプロセスが停止します(通常はゼロですが、再開-from-initrdの場合は誰も知りません)

イメージをディスクから読み込みます

suspend(PMSG_FREEZE): デバイスを凍結し、イメージの復元に干渉しないようにします

イメージ復元: メモリをイメージで上書きします

resume(): デバイスを起動し、システムが再開できるようにします

すべてのユーザープロセスを再開します

Q:

この「Encrypt suspend image（スリープイメージの暗号化）」は何のために使われますか？

A:

まず第一に、これはdm-cryptで暗号化されたスワップの代替ではありません。スリープ中にはコンピュータを保護できません。代わりに、スリープからの再開後に敏感なデータが漏れることを防ぐためのものです。

以下の点を考慮してください：アプリケーションが実行中にメモリに敏感なデータを保持している状態でスリープ状態に移行します。アプリケーション自体がデータをスワップ領域に交換しないように制御しています。しかし、スリープ状態に移行するには、これらのデータをスワップ領域に書き出す必要があります。スリープ時の暗号化を実施しない場合、敏感なデータはディスクに平文で保存されてしまいます。これにより、再起動後に敏感なデータがスワップデバイスに直接アクセスできるすべてのアプリケーションにアクセス可能になります。スリープ後にスワップ領域を使用しなくなった場合、これらのデータはディスクにほぼ永久に残る可能性があります。そのため、システムが数週間後に破損した場合、あなたが暗号化されて保護されていると考えていた敏感なデータがスワップデバイスから取得・盗まれる可能性があります。このような状況を防ぐためには、「スリープイメージを暗号化する」機能を使用してください。

スリープ中に一時的な鍵が生成され、この鍵を使用してディスクに書き込まれるデータが暗号化されます。再起動時にデータがメモリに読み込まれる際、この一時的な鍵は破棄されるため、スリープ中にディスクに書き込まれたデータはその後アクセス不可能になります。これにより、後からデータが盗まれることを防ぐことができます。ただし、スリープ用に使用するスワップパーティションに対して「mkswap」コマンドを通常の起動時にできるだけ早く実行する必要があります。これにより、エラーが発生したスリープや失敗した再起動による一時的な鍵がスワップデバイスから削除されます。

一般的に、システムがシャットダウンまたはスリープ状態にある間、データを保護するためには暗号化されたスワップを使用してください。さらに、スリープイメージを暗号化することで、再起動後に敏感なデータが盗まれることを防ぎます。

Q:

スワップファイルにスリープ状態に移行することは可能ですか？

A:

一般的には可能です。ただし、リカバリーパラメータとして「resume=」と「resume_offset=」をカーネルコマンドラインに指定する必要があります。そのため、スワップファイルからのリカバリはinitrdまたはinitramfsイメージから実行することはできません。詳細についてはswsusp-and-swap-files.txtを参照してください。

Q:

swsuspがサポートする最大のシステムRAMサイズはありますか？

A:

highmemに対応して問題ありません。

Q:

swsusp（ディスクに保存）は単一のスワップパーティションを使用するだけで、複数のスワップパーティションを1つの論理領域に統合して使用することは可能ですか？

A:

スワップパーティションは1つだけです、申し訳ありません。

Q:

私のアプリケーションがシステムRAMの半分以上をメモリとスワップ領域に使用している場合、そのアプリが実行されている間、ディスクにスリープ状態に移行する試みは無駄でしょうか？

A:

いいえ、アプリケーションがmlock()を呼び出していない限り問題ありません。十分なサイズのスワップパーティションを用意してください。

Q:

スリープトディスクの問題をデバッグする際に有用な情報はありますか？

A:

画面に表示される最後のメッセージは常に役立ちます。何かが壊れている場合、通常はカーネルドライバーが原因となるため、できるだけ少ないモジュールをロードして試すことで解決します。また、コンソールからスリープさせることを推奨します（Xが動作していない状態が望ましいです）。init=/bin/bashで起動し、swaponを実行して手動でスリープシーケンスを開始する方法が一般的です。その後、最新のバーナンクルカーネルを使用して試すのが良いでしょう。

Q:

ディストリビューションがSWSUSPをサポートするカーネルをモジュール化されたディスクドライバー（特にSATA）とともに配布する方法はありますか？

A:

可能です。ドライバーをロードし、initrdから/sys/power/resumeファイルにechoを実行します。何もマウントしないように注意してください（読み取り専用マウントでも同様です）。そうすればデータロスのリスクがあります。

Q:

スリープをより詳細に表示する方法はありますか？

A:

スリープ中にカーネルが切り替える仮想ターミナルで非エラーのカーネルメッセージを確認するには、カーネルコンソールログレベルを少なくとも4（KERN_WARNING）に設定する必要があります。例えば、以下のように実行します：

# save the old loglevel
read LOGLEVEL DUMMY < /proc/sys/kernel/printk
# set the loglevel so we see the progress bar.
# if the level is higher than needed, we leave it alone.
if [ $LOGLEVEL -lt 5 ]; then
        echo 5 > /proc/sys/kernel/printk
        fi

IMG_SZ=0
read IMG_SZ < /sys/power/image_size
echo -n disk > /sys/power/state
RET=$?
#
# the logic here is:
# if image_size > 0 (without kernel support, IMG_SZ will be zero),
# then try again with image_size set to zero.
if [ $RET -ne 0 -a $IMG_SZ -ne 0 ]; then # try again with minimal image size
        echo 0 > /sys/power/image_size
        echo -n disk > /sys/power/state
        RET=$?
fi

# restore previous loglevel
echo $LOGLEVEL > /proc/sys/kernel/printk
exit $RET
Q:

USBデバイスにマウントされたファイルシステムでスリープトディスクを行った場合、データが失われる可能性があるのでしょうか？

A:

その通りです…デバイスを切断するとデータロスのリスクがあります。実際には、-o syncオプションを指定していても、プログラムがバッファに情報を保持している場合や、デバイスがデータをディスクに書き終わる前に切断した場合でもデータロスが発生する可能性があります。

ソフトウェアスリープは通常、USBコントローラーをオフにします。これはシステムに接続されたすべてのUSBデバイスを切断するのと同等です。

システムは、スリープ状態でUSBコントローラーの低消費電力モードをサポートしている場合があります。これにより、接続を維持し、『スリープトRAM』や『スタンバイ』などの真のスリープモードを維持できます。（/sys/power/stateファイルに『disk』を書くのではなく、『standby』または『mem』を指定してください。）ソフトウェアスリープを通じてこれらのモードをサポートするハードウェアは現時点では確認されていませんが、理論上は一部のシステムが『プラットフォーム』モードをサポートしている可能性があります。

マウントされたファイルシステムを含むディスクドライブを外すのは常に危険です。システムがスリープ状態でも同様です！最も安全なのは、スリープ前に外付けメディア（USB、Firewire、CompactFlash、MMC、外部SATA、またはIDEホットプラグベイなど）にマウントされたすべてのファイルシステムをアンマウントすることです。その後、再起動後に再マウントしてください。

この問題に対する対処法があります。詳細は システムスリープ時のUSBデバイスの永続性.

Q:

LVM下のスワップパーティションを使用してスリープトディスクすることは可能ですか？

A:

はい、いいえ。スリープは正常に実行できますが、カーネルが自動的に再開することはできません。再開状況を認識し、スワップボリュームを含む論理ボリュームをアクティブ化（ファイルシステムは一切操作しない！）し、最終的に次のコマンドを呼び出すinitramfsが必要です:

echo -n "$major:$minor" > /sys/power/resume

ここで、$majorと$minorはスワップボリュームのそれぞれの主装置番号と補助装置番号です。

uswsuspはLVMにも対応しています。参照: http://suspend.sourceforge.net/

Q:

私はカーネルを2.6.15から2.6.16にアップグレードしました。両方のカーネルは類似したコンフィギュレーションファイルでコンパイルされました。しかし、スリープ（ディスクへのスリープと再開）が2.6.16では2.6.15に比べて大幅に遅くなっていることに気づきました。なぜこのようなことが起こるのか、またはどのようにして早めるかについてのアイデアはありますか？

A:

これは、スリープイメージのサイズが2.6.15よりも大きくなったためです（より多くのデータを保存することで、再起動後のシステムがより応答性が高いことが可能になります）。

/sys/power/image_sizeというコントロールパラメータでイメージのサイズを制御できます。この値を0に設定（例: rootとしてecho 0 > /sys/power/image_size）すると、2.6.15の挙動に戻ります。それでも遅い場合は、suspend.sf.netを参照してください – ユーザーランドでのスリープは速く、LZF圧縮をサポートしてさらに高速化できます。

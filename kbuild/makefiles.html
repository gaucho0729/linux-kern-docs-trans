Linuxカーネルメイクファイル¶

このドキュメントでは、LinuxカーネルのMakefileについて説明します。

1 概要¶

Makefileは5つの部分から構成されています：

Makefile                the top Makefile.
.config                 the kernel configuration file.
arch/$(ARCH)/Makefile   the arch Makefile.
scripts/Makefile.*      common rules etc. for all kbuild Makefiles.
kbuild Makefiles        there are about 500 of these.

トップMakefileは、カーネルの構成プロセスから生成される.configファイルを読み込みます。

トップMakefileは、vmlinux（常駐するカーネルイメージ）とmodules（任意のモジュールファイル）という2つの主要な製品を構築します。これらを構築するには、カーネルソースツリーのサブディレクトリに再帰的に移動して構築します。訪問するサブディレクトリのリストはカーネル構成によって異なります。トップMakefileは、arch/$(ARCH)/Makefileという名前のアーキテクチャ用Makefileをテキスト的にインクルードします。アーキテクチャ用MakefileはトップMakefileにアーキテクチャ固有の情報を提供します。

各サブディレクトリには、上から渡されたコマンドを実行するkbuild用Makefileがあります。kbuild用Makefileは、.configファイルから得た情報をもとに、kbuildが構築する任意のビルトインまたはモジュール対象に使用されるさまざまなファイルリストを構築します。

scripts/Makefile.*は、kbuild makefileに基づいてカーネルを構築するために使用されるすべての定義/ルールなどを含んでいます。

2 誰が何を行うか¶

人々はカーネルMakefileと4つの異なる関係を持っています。

ユーザー カーネルを構築する人々です。これらの人は「make menuconfig」や「make」といったコマンドを入力します。通常はカーネルMakefile（または他のソースファイル）を読み込んだり編集したりしません。

通常の開発者 デバイスドライバ、ファイルシステム、ネットワークプロトコルなどの機能に取り組む人々です。これらの人は、自分が取り組んでいるサブシステムのkbuild用Makefileを維持する必要があります。これを効果的に行うには、カーネルMakefileについての全体的な知識と、kbuildの公開インターフェースに関する詳細な知識が必要です。

アーキテクチャ開発者 sparcやia64などの全体的なアーキテクチャに取り組む人々です。アーキテクチャ開発者は、アーキテクチャ用Makefileおよびkbuild用Makefileについての知識が必要です。

kbuild開発者 カーネルビルドシステム自身に取り組む人々です。これらの人は、カーネルMakefileのすべての側面について知識が必要です。

このドキュメントは通常の開発者とアーキテクチャ開発者を対象としています。

3 kbuildファイル¶

カーネル内のほとんどのMakefileはkbuild用Makefileであり、kbuildインフラストラクチャを使用しています。この章では、kbuild makefileで使用される構文について紹介します。kbuildファイルの推奨される名前は「Makefile」ですが、「Kbuild」も使用でき、両方が存在する場合、「Kbuild」ファイルが優先されます。

セクション3.1「目標定義」は簡単な紹介です。以降の章では詳細な説明と実際の例が提供されます。

3.1 目標定義¶

目標定義はkbuild Makefileの中心（心）です。これらの行はビルドするファイル、特殊なコンパイルオプション、および再帰的に進入するサブディレクトリを定義します。

最もシンプルなkbuild Makefileは1行だけです：

例:

obj-y += foo.o

これはkbuildに、そのディレクトリにfoo.oという1つのオブジェクトがあることを伝えます。foo.oはfoo.cまたはfoo.Sからビルドされます。

foo.oがモジュールとしてビルドされる場合、変数obj-mが使用されます。そのため、次のパターンがよく使われます：

例:

obj-$(CONFIG_FOO) += foo.o

($(CONFIG_FOO)はビルトインの場合はy、モジュールの場合はmに評価されます。CONFIG_FOOがyもmもでなければ、ファイルはコンパイルもリンクもされません。

3.2 ビルドインオブジェクト目標 - obj-y¶

kbuild Makefileは$(obj-y)リストでvmlinux用のオブジェクトファイルを指定します。これらのリストはカーネル構成に依存します。

kbuildはすべての$(obj-y)ファイルをコンパイルし、その後「$(AR) rcSTP」を呼び出してこれらのファイルを1つのビルトイン.aファイルにマージします。これはシンボルテーブルを持たない薄いアーカイブです。後述のscripts/link-vmlinux.shスクリプトでvmlinuxにリンクされます。

$(obj-y)内のファイルの順序は重要です。リストに重複があっても問題ありません：最初のインスタンスはビルトイン.aにリンクされ、後のインスタンスは無視されます。

リンク順序は重要です。特定の関数（module_init() / __initcall）は起動時に出現順で呼び出されます。したがって、リンク順序を変更すると、SCSIコントローラーの検出順序やディスクの再番号付けが変化する可能性があるため、注意が必要です。

例:

#drivers/isdn/i4l/Makefile
# Makefile for the kernel ISDN subsystem and device drivers.
# Each configuration option enables a list of files.
obj-$(CONFIG_ISDN_I4L)         += isdn.o
obj-$(CONFIG_ISDN_PPP_BSDCOMP) += isdn_bsdcomp.o

3.3 ロード可能なモジュール目標 - obj-m¶

($(obj-m)はロード可能なカーネルモジュールとしてビルドされるオブジェクトファイルを指定します。

モジュールは1つのソースファイルまたは複数のソースファイルからビルドできます。1つのソースファイルの場合、kbuild Makefileはそのファイルを$(obj-m)に単純に追加します。

例:

#drivers/isdn/i4l/Makefile
obj-$(CONFIG_ISDN_PPP_BSDCOMP) += isdn_bsdcomp.o

注意: この例では$(CONFIG_ISDN_PPP_BSDCOMP)は’m’に評価されます

カーネルモジュールが複数のソースファイルからビルドされる場合、上記と同じようにモジュールをビルドするように指定します。ただし、kbuildはどのオブジェクトファイルからモジュールをビルドするかを知る必要がありますので、$(<module_name>-y)変数を設定して指定する必要があります。

例:

#drivers/isdn/i4l/Makefile
obj-$(CONFIG_ISDN_I4L) += isdn.o
isdn-y := isdn_net_lib.o isdn_v110.o isdn_common.o

この例ではモジュール名がisdn.oになります。kbuildは$(isdn-y)にリストされたオブジェクトをコンパイルし、その後これらのファイルのリストに対して「$(LD) -r」を実行してisdn.oを生成します。

kbuildが複合オブジェクトに対して$(<module_name>-y)を認識するため、値の CONFIG_ 複合オブジェクトの一部としてオブジェクトファイルをオプションで含めるためのシンボル。

例:

#fs/ext2/Makefile
obj-$(CONFIG_EXT2_FS) += ext2.o
ext2-y := balloc.o dir.o file.o ialloc.o inode.o ioctl.o \
          namei.o super.o symlink.o
ext2-$(CONFIG_EXT2_FS_XATTR) += xattr.o xattr_user.o \
                                xattr_trusted.o

この例では、xattr.o、xattr_user.o および xattr_trusted.o は、$(CONFIG_EXT2_FS_XATTR) が 'y' に評価される場合にのみ、複合オブジェクト ext2.o の一部となります。

注意: カーネルにオブジェクトをビルドする際も、上記の構文は動作します。CONFIG_EXT2_FS=y の場合、kbuild は個々の部品から ext2.o ファイルを自動的に生成し、built-in.a にリンクします。

3.4 シンボルをエクスポートするオブジェクト¶

シンボルをエクスポートするモジュール用の makefile には特別な記法は必要ありません。

3.5 ライブラリファイルのターゲット - lib-y¶

obj-* でリストされたオブジェクトはモジュール用または特定のディレクトリの built-in.a に組み込まれます。また、lib.a に含めるオブジェクトをリストすることも可能です。lib-y でリストされたオブジェクトは、そのディレクトリに1つのライブラリとして組み込まれます。obj-y にもリストされているオブジェクトは、すでにアクセス可能なのでライブラリには含めません。一貫性を保つため、lib-m でリストされたオブジェクトは lib.a に含めます。

同一の kbuild makefile がビルドインとライブラリに含めるファイルを同時にリストする場合があります。そのため、同じディレクトリに built-in.a と lib.a の両方が存在する可能性があります。

例:

#arch/x86/lib/Makefile
lib-y    := delay.o

delay.o を基にライブラリ lib.a を作成します。kbuild が実際に lib.a をビルドしていることを認識するためには、ディレクトリが libs-y にリストされている必要があります。

「6.4 ディレクトリを再帰的に訪問する際のリスト」も参照してください。

lib-y の使用は通常、 lib/ および arch/*/lib.

3.6 ディレクトリ内を再帰的に下りる¶

makefile は自身のディレクトリ内のオブジェクトのビルドにのみ責任を持ちます。サブディレクトリ内のファイルは、それらのサブディレクトリにある makefile が処理します。ビルドシステムは、サブディレクトリを再帰的にビルドする際、指定されたディレクトリを知らせることで自動的に実行します。

これを実現するには obj-y と obj-m を使用します。ext2 は別ディレクトリに存在し、fs/ ディレクトリ内の makefile は以下の割り当てにより kbuild にディレクトリを下りるよう指示します。

例:

#fs/Makefile
obj-$(CONFIG_EXT2_FS) += ext2/

CONFIG_EXT2_FS が 'y'（ビルドイン）または 'm'（モジュール）に設定されている場合、対応する obj- 変数が設定され、kbuild が ext2 ディレクトリに下りることになります。

kbuild はこの情報を使ってディレクトリを訪問するかどうかを判断するだけでなく、そのディレクトリのオブジェクトを vmlinux にリンクするかどうかも決定します。

Kbuildが’y’でディレクトリに移動すると、そのディレクトリのすべての組み込みオブジェクトがbuilt-in.aに統合され、最終的にvmlinuxにリンクされます。

Kbuildが’m’でディレクトリに移動すると、そのディレクトリの内容はvmlinuxにリンクされません。そのディレクトリのMakefileがobj-yを指定している場合、これらのオブジェクトは孤立してしまいます。これはMakefileまたはKconfigの依存関係のバグである可能性が高いです。

ディレクトリ名を割り当てる際には変数を使用するのが良い実践です。 CONFIG_ これにより、対応するオプションが’y’もしくは’m’でない場合、kbuildがそのディレクトリを完全にスキップできます。 CONFIG_ option is neither ‘y’ nor ‘m’。

3.7 コンパイルフラグ¶

ccflags-y, asflags-y and ldflags-y

これらの3つのフラグは、それらが割り当てられたkbuild makefileにのみ適用されます。これらは、再帰的なビルド中に発生するすべての通常のcc、as、ldの呼び出しに使用されます。注意: 同様の動作を持つフラグは以前はEXTRA_CFLAGS、EXTRA_AFLAGS、EXTRA_LDFLAGSと呼ばれていました。これらはまだサポートされていますが、使用は非推奨です。

ccflags-yは$(CC)でコンパイルする際のオプションを指定します。

例:

# drivers/acpi/acpica/Makefile
ccflags-y                       := -Os -D_LINUX -DBUILDING_ACPICA
ccflags-$(CONFIG_ACPI_DEBUG)    += -DACPI_DEBUG_OUTPUT

この変数は必要です。なぜなら、トップのMakefileが$(KBUILD_CFLAGS)変数を所有しており、全体のツリーのコンパイルフラグとして使用しているからです。

asflags-yはアセンブリーフラグを指定します。

例:

#arch/sparc/kernel/Makefile
asflags-y := -ansi

ldflags-yは$(LD)でリンクする際のオプションを指定します。

例:

#arch/cris/boot/compressed/Makefile
ldflags-y += -T $(srctree)/$(src)/decompress_$(arch-y).lds
subdir-ccflags-y, subdir-asflags-y

上記の2つのフラグはccflags-yとasflags-yに似ています。違いは、subdir-変体がそれらが存在するkbuildファイルおよびすべてのサブディレクトリに影響を与えることです。subdir-*で指定されたオプションは、非subdir変体で指定されたオプションよりもコマンドラインに先に追加されます。

例:

subdir-ccflags-y := -Werror
ccflags-remove-y, asflags-remove-y

これらのフラグは、コンパイラーやアセンブラー呼び出しにおける特定のフラグを削除するために使用されます。

例:

ccflags-remove-$(CONFIG_MCOUNT) += -pg
CFLAGS_$@, AFLAGS_$@

CFLAGS_$@とAFLAGS_$@は、現在のkbuild makefile内のコマンドにのみ適用されます。

$(CFLAGS_$@)は$(CC)に対してファイルごとのオプションを指定します。$@部分は、対象のファイルを指定する文字列値を持っています。

CFLAGS_$@はccflags-remove-yよりも優先度が高いため、ccflags-remove-yで削除されたコンパイラーフラグを再追加できます。

例:

# drivers/scsi/Makefile
CFLAGS_aha152x.o =   -DAHA152X_STAT -DAUTOCONF
CFLAGS_gdth.o    = # -DDEBUG_GDTH=2 -D__SERIAL__ -D__COM2__ \
                     -DGDTH_STATISTICS

これらの2行は、aha152x.oとgdth.oのコンパイルフラグを指定しています。

$(AFLAGS_$@)はアセンブリーファイルのソースファイルに類似した機能です。

AFLAGS_$@はasflags-remove-yよりも優先度が高いため、asflags-remove-yで削除されたアセンブラーのフラグを再追加できます。

例:

# arch/arm/kernel/Makefile
AFLAGS_head.o        := -DTEXT_OFFSET=$(TEXT_OFFSET)
AFLAGS_crunch-bits.o := -Wa,-mcpu=ep9312
AFLAGS_iwmmxt.o      := -Wa,-mcpu=iwmmxt

3.9 依存関係の追跡¶

Kbuildは以下のものを依存関係として追跡します:

  1. すべての前提ファイル（両方 *.c および *.h)

  2. CONFIG_ すべての前提ファイルで使用されるオプション

  3. ターゲットをコンパイルするために使用されるコマンドライン

したがって、$(CC)のオプションを変更すると、影響を受けるすべてのファイルが再コンパイルされます。

3.10 特殊ルール¶

kbuildインフラストラクチャが必要なサポートを提供しない場合に特殊ルールが使用されます。典型的な例はビルドプロセス中に生成されるヘッダーファイルです。もう一つの例は、ブートイメージなどを作成するためにアーキテクチャ固有のMakefileが特殊ルールを必要とする場合です。

特殊ルールは通常のMakeルールとして記述されます。kbuildはMakefileが配置されているディレクトリで実行されないため、すべての特殊ルールは前提ファイルやターゲットファイルへの相対パスを提供する必要があります。

特殊ルールを定義する際に使用される変数は2つあります：

($(src))

($(src))はMakefileが配置されているディレクトリへの相対パスです。srcツリーに配置されているファイルを参照する際は常に($(src))を使用してください。

($(obj))

($(obj))はターゲットが保存されているディレクトリへの相対パスです。生成されたファイルを参照する際は常に($(obj))を使用してください。

例:

#drivers/scsi/Makefile
$(obj)/53c8xx_d.h: $(src)/53c7,8xx.scr $(src)/script_asm.pl
        $(CPP) -DCHIP=810 - < $< | ... $(src)/script_asm.pl

これは通常のmakeで必要な構文に従う特殊ルールです。

ターゲットファイルは2つの前提ファイルに依存しています。ターゲットファイルへの参照は($(obj))で前につながれ、前提ファイルへの参照は($(src))で行われます（これらは生成されたファイルではないため）。

($(kecho))

ルール内でユーザーに情報を出力することは良い実践ですが、実行「make -s」の際には警告やエラー以外の出力は期待されません。このサポートのためにkbuildは($(kecho))を定義しており、make -sが使用されている場合を除き、($(kecho))の後のテキストを標準出力に表示します。

例:

#arch/blackfin/boot/Makefile
$(obj)/vmImage: $(obj)/vmlinux.gz
        $(call if_changed,uimage)
        @$(kecho) 'Kernel: $@ is ready'

3.11 $(CC)サポート関数¶

カーネルは$(CC)の複数のバージョンで構築可能で、それぞれがユニークな機能とオプションをサポートします。kbuildは$(CC)の有効なオプションを確認するための基本的なサポートを提供します。$(CC)は通常gccコンパイラですが、他の代替も利用可能です。

as-option

as-optionは$(CC)がアセンブリファイルをコンパイルする際に指定されたオプションをサポートしているかを確認するために使用されます。*.S)

例:

#arch/sh/Makefile
cflags-y += $(call as-option,-Wa$(comma)-isa=$(isa-y),)

上の例では、cflags-yに-Wa$(comma)-isa=$(isa-y)というオプションが$(CC)でサポートされている場合に割り当てられます。第二引数はオプションで、第一引数がサポートされていない場合に使用されます。

as-instr

as-instrはアセンブラーが特定のインストラクションを報告するかを確認し、その後にオプション1またはオプション2を出力します。Cエスケープはテストインストラクションでサポートされています。注意: as-instr-optionはKBUILD_AFLAGSでアセンブラーのオプションを使用します。

cc-option

cc-optionは、$(CC)が指定されたオプションをサポートしているかを確認し、サポートされていない場合はオプションの2番目の代替オプションを使用します。

例:

#arch/x86/Makefile
cflags-y += $(call cc-option,-march=pentium-mmx,-march=i586)

上記の例では、cflags-yに-march=pentium-mmxが割り当てられます（$(CC)がサポートしている場合）。サポートされていない場合は-march=i586が割り当てられます。cc-optionの2番目の引数はオプションであり、省略された場合、1番目のオプションがサポートされていない場合はcflags-yに値が割り当てられません。注意：cc-optionは$(CC)のオプションにKBUILD_CFLAGSを使用します。

cc-option-yn

cc-option-ynは、gccが指定されたオプションをサポートしているかを確認し、サポートされている場合は'y'を返します。サポートされていない場合は'n'を返します。

例:

#arch/ppc/Makefile
biarch := $(call cc-option-yn, -m32)
aflags-$(biarch) += -a32
cflags-$(biarch) += -m32

上記の例では、$(biarch)が$(CC)が-m32オプションをサポートしている場合に'y'に設定されます。$(biarch)が'y'の場合、展開された変数$(aflags-y)と$(cflags-y)にそれぞれ-a32と-m32が割り当てられます。注意：cc-option-ynは$(CC)のオプションにKBUILD_CFLAGSを使用します。

cc-disable-warning

cc-disable-warningは、gccが指定された警告をサポートしているかを確認し、その警告を無効にするコマンドラインスイッチを返します。この特殊な関数は必要です、なぜならgcc 4.4以降は任意の-Wno-*オプションを許容し、ソースファイルに他の警告が存在しない限り警告を出さないからです。

例:

KBUILD_CFLAGS += $(call cc-disable-warning, unused-but-set-variable)

上記の例では、-Wno-unused-but-set-variableがKBUILD_CFLAGSに追加されるのは、gccが実際にそれを受け入れる場合に限られます。

cc-ifversion

cc-ifversionは$(CC)のバージョンをテストし、式が真の場合には第4パラメータ、偽の場合には第5パラメータ（指定があれば）を返します。

例:

#fs/reiserfs/Makefile
ccflags-y := $(call cc-ifversion, -lt, 0402, -O1)

この例では、$(CC)のバージョンが4.2未満の場合、ccflags-yに-O1が割り当てられます。cc-ifversionはすべてのシェル演算子（-eq、-ne、-lt、-le、-gt、-ge）をサポートします。第3パラメータはこの例のようにテキストでもよいですが、展開された変数やマクロでも可能です。

cc-cross-prefix

cc-cross-prefixは、PATHにリストされたプレフィックスのいずれかを持つ$(CC)が存在するかを確認します。PATHに存在する最初のプレフィックス$(CC)が返され、存在しない場合は何も返されません。追加のプレフィックスはスペースで区切ってcc-cross-prefixの呼び出しで指定します。この機能は、ホストアーキテクチャがターゲットアーキテクチャと異なるクロスビルドの場合にCROSS_COMPILEを設定しようとするアーキテクチャMakefileで役立ちます。CROSS_COMPILEが既に設定されている場合は、古い値を保持することをお勧めします。

例:

#arch/m68k/Makefile
ifneq ($(SUBARCH),$(ARCH))
        ifeq ($(CROSS_COMPILE),)
               CROSS_COMPILE := $(call cc-cross-prefix, m68k-linux-gnu-)
        endif
endif

3.12 $(LD)サポート関数¶

ld-option

ld-optionは、$(LD)が指定されたオプションをサポートしているかを確認するために使用されます。ld-optionには2つのオプションを引数として受け取ります。2番目の引数は、1番目のオプションが$(LD)でサポートされていない場合に使用できるオプションです。

例:

#Makefile
LDFLAGS_vmlinux += $(call ld-option, -X)

3.13 スクリプトの実行¶

Makeルールは、カーネルのビルドにスクリプトを呼び出すことができます。ルールは常にスクリプトを実行するための適切なインタプリタを提供する必要があります。実行ビットが設定されていることを依存せず、スクリプトを直接呼び出すことはできません。手動でのスクリプト実行（例: ./scripts/checkpatch.plの呼び出し）を便利にするため、スクリプトに実行ビットを設定することをお勧めします。

Kbuildは、スクリプトのインタプリタを参照するための変数$(CONFIG_SHELL)、$(AWK)、$(PERL)、$(PYTHON)、$(PYTHON3)を提供します。

例:

#Makefile
cmd_depmod = $(CONFIG_SHELL) $(srctree)/scripts/depmod.sh $(DEPMOD) \
             $(KERNELRELEASE)

4 ホストプログラムのサポート¶

Kbuildは、コンパイルステージで使用するホスト用の実行可能ファイルのビルドをサポートしています。ホスト用の実行可能ファイルを使用するには2つのステップが必要です。

最初のステップは、kbuildにホストプログラムが存在することを伝えることです。これは変数「hostprogs」を活用して行います。

2番目のステップは、実行可能ファイルへの明示的な依存関係を追加することです。これは2つの方法で行えます。ルールに依存関係を追加するか、変数「always-y」を活用するかです。以下の節で両方の方法について説明します。

4.1 シンプルなホストプログラム¶

ある場合、ビルドが行われているコンピュータでプログラムをコンパイルして実行する必要があります。以下の行は、kbuildにbin2hexというプログラムがビルドホストでビルドされるように伝えます。

例:

hostprogs := bin2hex

上記の例では、kbuildがbin2hexがMakefileと同じディレクトリにあり、bin2hex.cという単一のCソースファイルから構成されていると仮定しています。

4.2 複合ホストプログラム¶

ホストプログラムは複合オブジェクトに基づいて構成できます。ホストプログラムの複合オブジェクトを定義するための構文は、カーネルオブジェクトの構文と似ています。$(<executable>-objs)は、最終的な実行可能ファイルをリンクするためのすべてのオブジェクトをリストします。

例:

#scripts/lxdialog/Makefile
hostprogs     := lxdialog
lxdialog-objs := checklist.o lxdialog.o

拡張子が.oのオブジェクトは、対応する.cファイルからコンパイルされます。上記の例では、checklist.cがchecklist.oに、lxdialog.cがlxdialog.oにコンパイルされます。

最後に、2つの.oファイルが実行可能ファイルlxdialogにリンクされます。注意: ホストプログラムには<executable>-yの構文は許可されていません。

4.3 ホストプログラムにC++を使用する¶

kbuildは、ホストプログラムにC++を用いたサポートを提供しています。これはkconfigのサポートのために導入されたものであり、一般的な用途には推奨されていません。

例:

#scripts/kconfig/Makefile
hostprogs     := qconf
qconf-cxxobjs := qconf.o

上記の例では、実行可能ファイルはC++ファイルqconf.ccから構成され、$(qconf-cxxobjs)で識別されます。

qconfが.cと.ccファイルの混合から構成されている場合、追加の行を使用してこれを特定できます。

例:

#scripts/kconfig/Makefile
hostprogs     := qconf
qconf-cxxobjs := qconf.o
qconf-objs    := check.o

4.4 ホストプログラムのコンパイラオプションの制御¶

ホストプログラムをコンパイルする際には、特定のフラグを設定することが可能です。プログラムは常に$(HOSTCC)を使用して$(KBUILD_HOSTCFLAGS)に指定されたオプションでコンパイルされます。すべてのホストプログラムに対して有効なフラグを設定するには、HOST_EXTRACFLAGS変数を使用してください。

例:

#scripts/lxdialog/Makefile
HOST_EXTRACFLAGS += -I/usr/include/ncurses

特定のファイルに対して特定のフラグを設定するには、以下の構文が使用されます：

例:

#arch/ppc64/boot/Makefile
HOSTCFLAGS_piggyback.o := -DKERNELBASE=$(KERNELBASE)

リンカに追加のオプションを指定することも可能です。

例:

#scripts/kconfig/Makefile
HOSTLDLIBS_qconf := -L$(QTDIR)/lib

qconfをリンクする際には、追加のオプション「-L$(QTDIR)/lib」が渡されます。

4.5 ホストプログラムが実際にビルドされるとき¶

Kbuildは、前提条件としてホストプログラムが参照される場合にのみビルドを行います。これは以下の2つの方法で可能です：

  1. 特別なルールで前提条件を明示的にリストします。

例:

#drivers/pci/Makefile
hostprogs := gen-devlist
$(obj)/devlist.h: $(src)/pci.ids $(obj)/gen-devlist
        ( cd $(obj); ./gen-devlist ) < $<

ターゲット$(obj)/devlist.hは、$(obj)/gen-devlistが更新されるまでビルドされません。特別なルールで参照するホストプログラムは、$(obj)で前につける必要があります。

  1. 常に-yを使用する

特別なルールが存在せず、makefileが読み込まれた際にホストプログラムをビルドする必要がある場合、always-y変数を使用してください。

例:

#scripts/lxdialog/Makefile
hostprogs     := lxdialog
always-y      := $(hostprogs)

Kbuildはこれを以下のように省略表現で提供します：

hostprogs-always-y := lxdialog

これはkbuildにlxdialogをビルドするように指示します。どのルールにも参照されていない場合でもです。

5 ユーザースペースプログラムのサポート¶

ホストプログラム同様に、Kbuildはターゲットアーキテクチャ（つまり、カーネルをビルドしているアーキテクチャと同じ）用のユーザースペース実行ファイルのビルドもサポートしています。

構文はほぼ同じですが、'userprogs'を使用します。

5.1 簡単なユーザースペースプログラム¶

以下の行は、kbuildにプログラムbpf-directがターゲットアーキテクチャでビルドされるように指示します。

例:

userprogs := bpf-direct

上記の例では、bpf-directはMakefileと同じディレクトリにあるbpf-direct.cという単一のCソースファイルから構成されていると仮定しています。

5.2 組み合わせ型ユーザースペースプログラム¶

ユーザースペースプログラムは複合オブジェクトに基づいて構成できます。ユーザースペースプログラムの複合オブジェクトを定義する構文は、カーネルオブジェクトの構文と同様です。$(<executable>-objs)は最終実行ファイルをリンクするために使用されるすべてのオブジェクトをリストします。

例:

#samples/seccomp/Makefile
userprogs      := bpf-fancy
bpf-fancy-objs := bpf-fancy.o bpf-helper.o

拡張子.oのオブジェクトは、対応する.cファイルからコンパイルされます。上記の例では、bpf-fancy.cがbpf-fancy.oに、bpf-helper.cがbpf-helper.oにコンパイルされます。

最後に、2つの.oファイルが実行可能ファイルbpf-fancyにリンクされます。注意: ユーザースペースプログラムでは<executable>-yという構文は許可されていません。

5.3 ユーザースペースプログラムのコンパイラオプションの制御¶

ユーザースペースプログラムをコンパイルする際、特定のフラグを設定することが可能です。プログラムは常に$(CC)を通じて$(KBUILD_USERCFLAGS)で指定されたオプションを使用してコンパイルされます。そのMakefileで作成されるすべてのユーザースペースプログラムに効果を発揮するフラグを設定するには、userccflags変数を使用してください。

例:

# samples/seccomp/Makefile
userccflags += -I usr/include

特定のファイルに対して特定のフラグを設定するには、以下の構文が使用されます：

例:

bpf-helper-userccflags += -I user/include

リンカに追加のオプションを指定することも可能です。

例:

# net/bpfilter/Makefile
bpfilter_umh-userldflags += -static

bpfilter_umhをリンクする際には、追加オプション-staticが渡されます。

コマンドラインから USERCFLAGSおよびUSERLDFLAGS も使用されます。

5.4 ユーザースペースプログラムの実際のビルド¶

Kbuildは明示的に指示された場合にのみユーザースペースプログラムをビルドします。これは2つの方法で実行できます。

  1. 他のファイルの前提条件として追加する

例:

#net/bpfilter/Makefile
userprogs := bpfilter_umh
$(obj)/bpfilter_umh_blob.o: $(obj)/bpfilter_umh

($(obj)/bpfilter_umhは($(obj)/bpfilter_umh_blob.oよりも先にビルドされます

  1. 常に-yを使用する

例:

userprogs := binderfs_example
always-y := $(userprogs)

Kbuildはこれを以下のように省略表現で提供します：

userprogs-always-y := binderfs_example

これはKbuildにこのMakefileを訪れた際にbinderfs_exampleをビルドするように指示します。

6 Kbuildのクリーンインフラストラクチャ¶

「make clean」は、カーネルがコンパイルされるobjツリー内のほとんどの生成ファイルを削除します。これはホストプログラムなどの生成ファイルを含みます。Kbuildは$(hostprogs)、$(always-y)、$(always-m)、$(always-)、$(extra-y)、$(extra-)および$(targets)にリストされているターゲットをすべて「make clean」の際に削除します。パターン「.[oas]」、「.ko」に一致するファイルに加えて、一部の追加ファイルもkbuildによって生成され、「make clean」の実行時にカーネルソースツリー全体から削除されます。.[oas]”, “.ko”, および一部の追加ファイルがkbuildによって生成され、「make clean」の実行時にカーネルソースツリー全体から削除されます。

追加のファイルまたはディレクトリは、$(clean-files)を使用してkbuild makefile内で指定できます。

例:

#lib/Makefile
clean-files := crc32table.h

「make clean」を実行すると、ファイル「crc32table.h」が削除されます。KbuildはMakefileと同じ相対ディレクトリにあるファイルを想定しますが、$(objtree)で前缀された場合はその例外です。

特定のファイルまたはディレクトリをmake cleanから除外するには、$(no-clean-files)変数を使用してください。

通常、kbuildは「obj-* := dir/」によりサブディレクトリに移動しますが、kbuildインフラストラクチャが不十分なアーキテクチャmakefileでは、この場合に明示的に指定する必要があります。

例:

#arch/x86/boot/Makefile
subdir- := compressed

上記の割り当ては、「make clean」の実行時にkbuildがディレクトリcompressed/に移動するように指示します。

最終ブートイメージをビルドするMakefileでクリーンインフラストラクチャをサポートするため、オプションのターゲットarchcleanがあります:

例:

#arch/x86/Makefile
archclean:
        $(Q)$(MAKE) $(clean)=arch/x86/boot

「make clean」を実行すると、makeはarch/x86/bootに移動し、通常通りクリーンします。arch/x86/bootにあるMakefileはsubdir-トリックを使用してさらに深く移動する可能性があります。

注意1: arch/$(ARCH)/Makefileでは「subdir-」を使用できません。なぜなら、このファイルはトップレベルのmakefileでインクルードされており、その時点ではkbuildインフラストラクチャが動作していないからです。

注意2: core-y、libs-y、drivers-yおよびnet-yに記載されたディレクトリは、「make clean」の実行時にすべて処理されます。

7 アーキテクチャ用Makefile¶

トップレベルのMakefileは、個々のディレクトリに下りる前に環境設定と準備を行います。トップレベルのmakefileには汎用的な部分が含まれており、arch/$(ARCH)/Makefileは特定のアーキテクチャ用にkbuildを設定するための内容が含まれています。そのため、arch/$(ARCH)/Makefileでは複数の変数を設定し、いくつかのターゲットを定義しています。

kbuildが実行される際のステップは以下の通りです（概ね）：

  1. カーネルの構成 => .configファイルの生成

  2. カーネルバージョンをinclude/linux/version.hに保存

  3. ターゲットprepareへの他のすべての前提条件を更新: - さらに詳細な前提条件はarch/$(ARCH)/Makefileで指定されています

  4. init-* core* drivers-* net-* libs-*に記載されたディレクトリに再帰的に下り、すべてのターゲットをビルド。- 上記変数の値はarch/$(ARCH)/Makefileで展開されます。

  5. すべてのオブジェクトファイルがリンクされ、結果として生成されるvmlinuxファイルはobjツリーのルートに位置します。最初にリンクされるオブジェクトはarch/$(ARCH)/Makefileで指定されるhead-yに記載されています。

  6. 最後に、アーキテクチャ固有の部分が必要なポスト処理を行い、最終的なブートイメージを構築します。- これはブートレコードの生成 - initrdイメージの準備などが含まれます

7.1 アーキテクチャに応じたビルドを調整する変数の設定¶

KBUILD_LDFLAGS

汎用的な$(LD)オプション

リンカーコマンドのすべての呼び出しに使用されるフラグ。通常はエミュレーションの指定で十分です。

例:

#arch/s390/Makefile
KBUILD_LDFLAGS         := -m elf_s390

注意: ldflags-yを使用してさらにフラグをカスタマイズできます。セクション3.7を参照してください。

LDFLAGS_vmlinux

vmlinuxをリンクする際の$(LD)オプション

LDFLAGS_vmlinuxは、最終的なvmlinuxイメージをリンクする際の追加フラグを指定するために使用されます。LDFLAGS_$@のサポートを使用しています。

例:

#arch/x86/Makefile
LDFLAGS_vmlinux := -e stext
OBJCOPYFLAGS

objcopyフラグ

$(call if_changed,objcopy)を使用して.oファイルを変換する際、OBJCOPYFLAGSに指定されたフラグが使用されます。$(call if_changed,objcopy)はvmlinuxからrawバイナリを生成するためによく使用されます。

例:

#arch/s390/Makefile
OBJCOPYFLAGS := -O binary

#arch/s390/boot/Makefile
$(obj)/image: vmlinux FORCE
        $(call if_changed,objcopy)

この例では、$(obj)/imageはvmlinuxのバイナリ版です。$(call if_changed,xxx)の使用方法については後述します。

KBUILD_AFLAGS

アセンブラフラグ

デフォルト値 - トップレベルのMakefileを参照してください。アーキテクチャごとに必要に応じて追加または変更してください。

例:

#arch/sparc64/Makefile
KBUILD_AFLAGS += -m64 -mcpu=ultrasparc
KBUILD_CFLAGS

($(CC)) コンパイラーフラグ

デフォルト値 - トップレベルのMakefileを参照してください。アーキテクチャごとに必要に応じて追加または変更してください。

通常、KBUILD_CFLAGS 変数は構成に依存します。

例:

#arch/x86/boot/compressed/Makefile
cflags-$(CONFIG_X86_32) := -march=i386
cflags-$(CONFIG_X86_64) := -mcmodel=small
KBUILD_CFLAGS += $(cflags-y)

多くのアーキテクチャ用 Makefile は、サポートされているオプションを調べるためにターゲット C コンパイラを動的に実行します：

#arch/x86/Makefile

...
cflags-$(CONFIG_MPENTIUMII)     += $(call cc-option,\
                                -march=pentium2,-march=i686)
...
# Disable unit-at-a-time mode ...
KBUILD_CFLAGS += $(call cc-option,-fno-unit-at-a-time)
...

最初の例では、選択されたときに構成オプションが 'y' に展開されるというトリックを利用しています。

KBUILD_AFLAGS_KERNEL

組み込み用のアセンブラー オプション

$(KBUILD_AFLAGS_KERNEL) は、常駐カーネルコードをコンパイルするために使用される追加の C コンパイラフラグを含みます。

KBUILD_AFLAGS_MODULE

モジュール用のアセンブラー オプション

$(KBUILD_AFLAGS_MODULE) は、アーキテクチャ固有のオプションをアセンブラーに使用するために追加します。

コマンドラインから AFLAGS_MODULE を使用してください（kbuild.rst を参照）。

KBUILD_CFLAGS_KERNEL

組み込み用の $(CC) オプション

$(KBUILD_CFLAGS_KERNEL) は、常駐カーネルコードをコンパイルするために使用される追加の C コンパイラフラグを含みます。

KBUILD_CFLAGS_MODULE

モジュールをビルドする際の $(CC) オプション

$(KBUILD_CFLAGS_MODULE) は、アーキテクチャ固有のオプションを $(CC) に使用するために追加します。コマンドラインから CFLAGS_MODULE を使用してください（kbuild.rst を参照）。

KBUILD_LDFLAGS_MODULE

モジュールをリンクする際の $(LD) オプション

$(KBUILD_LDFLAGS_MODULE) は、モジュールをリンクする際のアーキテクチャ固有のオプションを追加します。これは通常リンカースクリプトです。

コマンドラインから LDFLAGS_MODULE を使用してください（kbuild.rst を参照）。

KBUILD_LDS

フルパスのリンカースクリプト。トップレベル Makefile によって割り当てられます。

KBUILD_LDS_MODULE

フルパスのモジュールリンカースクリプト。トップレベル Makefile およびアーキテクチャ Makefile によって割り当てられます。

KBUILD_VMLINUX_OBJS

vmlinux 用のすべてのオブジェクトファイル。KBUILD_VMLINUX_OBJS に記載された順序で vmlinux にリンクされます。

KBUILD_VMLINUX_LIBS

vmlinux 用のすべての .a 「lib」ファイル。KBUILD_VMLINUX_OBJS と KBUILD_VMLINUX_LIBS は、vmlinux をリンクするために使用されるすべてのオブジェクトファイルを指定します。

7.2 アーキテクチャヘッダへの前提条件を追加¶

archheaders: ルールは、「make header_install」でユーザー空間にインストールされるヘッダファイルを生成するために使用されます。

アーキテクチャ自体で「make archprepare」を実行する際、このルールは「make archprepare」の前に実行されます。

7.3 アーキテクチャ準備への前提条件を追加¶

archprepare: ルールは、サブディレクトリに移る前に構築する必要のある前提条件をリストするために使用されます。これは通常、アセンブラー定数を含むヘッダファイルに使用されます。

例:

#arch/arm/Makefile
archprepare: maketools

この例では、ファイルターゲット maketools がサブディレクトリに移る前に処理されます。また、kbuild がオフセットヘッダーファイルを生成する方法を説明する章 XXX-TODO も参照してください。

7.4 サブディレクトリを訪問する順序をリスト¶

アーキテクチャ用 Makefile は、トップ Makefile と協力して、vmlinux ファイルを構築する方法を指定する変数を定義します。注意点として、モジュール構築用のアーキテクチャ固有セクションは存在せず、モジュール構築の仕組みはすべてアーキテクチャに依存しません。

head-y, init-y, core-y, libs-y, drivers-y, net-y

「$(head-y)」は、vmlinux に最初にリンクされるオブジェクトをリストします。

「$(libs-y)」は、lib.a アーカイブが配置されるディレクトリをリストします。

それ以外のリストは、built-in.a オブジェクトファイルが配置されるディレクトリを示します。

「$(init-y)」のオブジェクトは、「$(head-y)」の後ろに配置されます。

その後、この順序で以下のものが続きます：

「$(core-y)」, 「$(libs-y)」, 「$(drivers-y)」および 「$(net-y)」。

トップレベルの Makefile はすべての汎用ディレクトリの値を定義し、arch/$(ARCH)/Makefile はアーキテクチャ固有のディレクトリを追加します。

例:

#arch/sparc64/Makefile
core-y += arch/sparc64/kernel/
libs-y += arch/sparc64/prom/ arch/sparc64/lib/
drivers-$(CONFIG_OPROFILE)  += arch/sparc64/oprofile/

7.5 アーキテクチャ固有のブートイメージ¶

アーキテクチャ用 Makefile は、vmlinux ファイルを読み込み、圧縮し、ブートストラップコードでラップし、結果のファイルをどこかにコピーする目標を指定します。これはさまざまな種類のインストールコマンドを含みます。実際の目標はアーキテクチャごとに標準化されていません。

通常、追加の処理は arch/$(ARCH)/ の下にある boot/ ディレクトリに配置されます。

Kbuild は boot/ に指定されたターゲットを構築するためのスマートな方法を提供していません。そのため、arch/$(ARCH)/Makefile は手動で make を呼び出して、boot/ にあるターゲットを構築する必要があります。

推奨されるアプローチは、arch/$(ARCH)/Makefile にショートカットを含め、arch/$(ARCH)/boot/Makefile に下請けする際にはフルパスを使用することです。

例:

#arch/x86/Makefile
boot := arch/x86/boot
bzImage: vmlinux
        $(Q)$(MAKE) $(build)=$(boot) $(boot)/$@

「$(Q)$(MAKE) $(build)=<dir>」は、サブディレクトリで make を呼び出すための推奨方法です。

アーキテクチャ固有のターゲットの命名規則はありませんが、『make help』を実行するとすべての関連ターゲットが一覧表示されます。これをサポートするため、$(archhelp) が定義される必要があります。

例:

#arch/x86/Makefile
define archhelp
  echo  '* bzImage      - Image (arch/$(ARCH)/boot/bzImage)'
endif

make を引数なしで実行すると、最初に遭遇したターゲットが構築されます。トップレベル Makefile では最初のターゲットは all: です。アーキテクチャは常にデフォルトでブート可能なイメージを構築します。『make help』では、デフォルトターゲットは '*' で強調されます。all: に新しい前提条件を追加して、vmlinux 以外のデフォルトターゲットを選択できます。

例:

#arch/x86/Makefile
all: bzImage

『make』を引数なしで実行すると、bzImage が構築されます。

7.6 非 kbuild ターゲットの構築¶

extra-y

extra-y は、obj-* で指定されたターゲットに加えて、現在のディレクトリに追加で作成されるターゲットを指定します。 obj-*.

extra-y にすべてのターゲットをリストする必要があります。その目的は以下の2つです：

  1. コマンドラインの変更を kbuild が確認できるようにする

    • 「$(call if_changed,xxx)」が使用される場合

  2. 『make clean』時に削除すべきファイルを kbuild が把握できるようにする

例:

#arch/x86/kernel/Makefile
extra-y := head.o init_task.o

この例では、extra-yはビルドされるオブジェクトファイルを一覧表示するための変数として使用されますが、built-in.aにリンクされません。

7.7 ブートイメージを構築するためのコマン,ド¶

Kbuildはブートイメージを構築する際に役立ついくつかのマクロを提供しています。

if_changed

if_changedは以下のコマンドに使用されるインフラストラクチャです。

使用方法:

target: source(s) FORCE
        $(call if_changed,ld/objcopy/gzip/...)

ルールが評価される際、ファイルの更新が必要かどうか、またはコマンドラインが最後の実行以降に変更されていないかが確認されます。後者の場合、実行可能なオプションが変更された場合は再構築が強制されます。if_changedを利用するターゲットは必ず$(targets)にリストアップする必要があります。そうでない場合、コマンドラインのチェックが失敗し、ターゲットは常に構築されます。$(targets)への割り当てには$(obj)/プレフィックスは付けません。if_changedは7.8「カスタムkbuildコマンド」で定義されたカスタムコマンドと併用可能です。

注意: FORCE前提条件を忘れるのは典型的な間違いです。また、空白が重要な場合があります。例えば、以下の例は空白（カンマの後に余分なスペース）があるため失敗します:

target: source(s) FORCE

誤りです！ WRONG! $(call if_changed, ld/objcopy/gzip/…)

注意:

if_changedは1つのターゲットに対して複数回使用しないでください。実行されたコマンドは対応する.cmdファイルに保存され、複数の呼び出しはターゲットが最新であるにもかかわらず、変更されたコマンドのテストによって実行がトリガーされるため、上書きや不望な結果を招く可能性があります。

ld

リンクリングターゲット。通常、LDFLAGS_$@が使用され、ldに特定のオプションを設定します。

この例では、2つのターゲットがあり、それぞれに異なるリンカーオプションが必要です。リンカーオプションはLDFLAGS_$@構文で指定され、それぞれの潜在的なターゲットに対応します。$(targets)にはすべての潜在的なターゲットが割り当てられ、kbuildはターゲットを認識し、以下の動作を行います:

例:

#arch/x86/boot/Makefile
LDFLAGS_bootsect := -Ttext 0x0 -s --oformat binary
LDFLAGS_setup    := -Ttext 0x0 -s --oformat binary -e begtext

targets += setup setup.o bootsect bootsect.o
$(obj)/setup $(obj)/bootsect: %: %.o FORCE
        $(call if_changed,ld)

コマンドラインの変更を確認

  1. make clean時にターゲットを削除

  2. 「: %: %.o」の前提条件部分は、setup.oとbootsect.oファイルをリストアップする必要がないようにする省略形です。

ターゲットファイルが無駄に再コンパイルされる原因となる「targets :=」の割り当てを忘れるのはよくある間違いです。

注意:

objcopy

バイナリのコピー。arch/$(ARCH)/Makefileで通常指定されるOBJCOPYFLAGSを使用します。追加のオプションを設定するにはOBJCOPYFLAGS_$@を使用します。

gzip

圧縮ターゲット。ターゲットを最大圧縮して圧縮します。

dtc

例:

#arch/x86/boot/compressed/Makefile
$(obj)/vmlinux.bin.gz: $(vmlinux.bin.all-y) FORCE
        $(call if_changed,gzip)
vmlinuxにリンク可能なフラットなデバイスツリーBLOBオブジェクトを作成します。デバイスツリーBLOBがvmlinuxにリンクされると、イメージ内のinitセクションに配置されます。プラットフォームコード

unflatten_device_tree()を呼び出す前に、BLOBを非initメモリにコピーします。 grace periodsを尊重しなければなりませんし、 このコマンドを使用するには、単に

*.dtb を追加してください。 obj-yやtargetsに組み込むか、他のターゲットが依存するようにする %.dtb

中心的なルールが存在して、 $(obj)/%.dtb from $(src)/%.dts; アーキテクチャ用Makefileでは、そのルールを明示的に記述する必要はありません。

例:

targets += $(dtb-y)
DTC_FLAGS ?= -p 1024

7.8 カスタムkbuildコマンド¶

kbuildがKBUILD_VERBOSE=0で実行されている場合、通常はコマンドの略称のみが表示されます。カスタムコマンドに対してこの挙動を有効にするには、kbuildが2つの変数を設定する必要があります:

quiet_cmd_<command>     - what shall be echoed
      cmd_<command>     - the command to execute

例:

#
quiet_cmd_image = BUILD   $@
      cmd_image = $(obj)/tools/build $(BUILDFLAGS) \
                                     $(obj)/vmlinux.bin > $@

targets += bzImage
$(obj)/bzImage: $(obj)/vmlinux.bin $(obj)/tools/build FORCE
        $(call if_changed,image)
        @echo 'Kernel: $@ is ready'

($(obj)/bzImageターゲットを更新する際、以下の行:

BUILD arch/x86/boot/bzImage

make KBUILD_VERBOSE=0で表示されます。

7.9 リンカースクリプトのプリプロセス¶

vmlinuxイメージが構築される際、リンカースクリプトarch/$(ARCH)/kernel/vmlinux.ldsが使用されます。このスクリプトは、同じディレクトリにあるvmlinux.lds.Sファイルのプリプロセス済みバージョンです。kbuildは.ldsファイルを認識しており、ルールを含んでいます *lds.S -> *lds.

例:

#arch/x86/kernel/Makefile
extra-y := vmlinux.lds

#Makefile
export CPPFLAGS_vmlinux.lds += -P -C -U$(ARCH)

extra-yへの割り当ては、kbuildにvmlinux.ldsターゲットを構築するように指示します。$(CPPFLAGS_vmlinux.lds)への割り当ては、vmlinux.ldsターゲットを構築する際の指定オプションを使用するようにkbuildに指示します。

*.ldsターゲットを構築する際、kbuildは以下の変数を使用します: *.lds ターゲットを構築する際、kbuildは以下の変数を使用します:

KBUILD_CPPFLAGS : Set in top-level Makefile
cppflags-y      : May be set in the kbuild makefile
CPPFLAGS_$(@F)  : Target-specific flags.
                Note that the full filename is used in this
                assignment.

kbuildインフラストラクチャの *lds ファイルは、複数のアーキテクチャ固有のファイルで使用されています。

7.10 ジェネリックヘッダーファイル¶

include/asm-genericディレクトリには、個々のアーキテクチャ間で共有可能なヘッダーファイルが含まれています。ジェネリックヘッダーファイルを使用する推奨方法は、Kbuildファイルにそのファイルをリストアップすることです。詳しくは「8.2 generic-y」を参照してください。

7.11 リンク後の処理¶

arch/xxx/Makefile.postlinkファイルが存在する場合、このmakefileはアーキテクチャごとにリンクロブジェクト（vmlinuxとmodules.ko）に対してリンク後の処理を実行するために呼び出されます。cleanターゲットも処理する必要があります。

この処理はkallsyms生成の後に実行されます。アーキテクチャがシンボルの位置を変更する必要がある場合、kallsymsを操作する代わりに、link-vmlinux.shから呼び出される.tmp_vmlinux?ターゲット用に別のpostlinkターゲットを追加する方が簡単です。

たとえば、powerpcはリンクされたvmlinuxファイルのリロケーションの健全性を確認するためにこれを使用します。

8 エクスポートされたヘッダー用のKbuild構文¶

カーネルにはユーザー空間にエクスポートされるヘッダーのセットが含まれています。多くのヘッダーはそのままエクスポートできますが、他のヘッダーはユーザー空間で使用できるようになる前に最小限のプリプロセスが必要です。プリプロセスは以下の処理を行います:

  • カーネル固有の注釈を削除

  • compiler.hのインクルードを削除

  • すべてのカーネル内部セクション（__KERNEL__でガードされている）を削除 ifdef __KERNEL__)

include/uapi/、include/generated/uapi/、arch/<arch>/include/uapi/、arch/<arch>/include/generated/uapi/以下のすべてのヘッダーがエクスポートされます。

Kbuild ファイルは、arch/<arch>/include/uapi/asm/ および arch/<arch>/include/asm/ の下に定義され、asm-generic から来る asm ファイルを一覧表示します。Kbuild ファイルの構文については次の章を参照してください。

8.1 no-export-headers¶

no-export-headers は include/uapi/linux/Kbuild によって使用され、特定のヘッダ（例: kvm.h）をサポートしていないアーキテクチャでエクスポートを防ぐために使用されます。可能な限り使用を避けてください。

8.2 generic-y¶

アーキテクチャが include/asm-generic からのヘッダをverbatimにコピーしている場合、このヘッダは arch/$(ARCH)/include/asm/Kbuild のファイルに以下のように記載されます：

例:

#arch/x86/include/asm/Kbuild
generic-y += termios.h
generic-y += rtc.h

ビルドの prepare 階段において、ワレッタ include ファイルが次のディレクトリに生成されます：

arch/$(ARCH)/include/generated/asm

アーキテクチャが generic ヘッダを使用してヘッダをエクスポートする場合、エクスポートされたヘッダのセットとして、次のディレクトリに同様のワレッタが生成されます：

usr/include/asm

生成されたワレッタはどちらの場合も以下のようになります：

例: termios.h:

#include <asm-generic/termios.h>

8.3 generated-y¶

アーキテクチャが generic-y ワレッタと共に他のヘッダーファイルを生成する場合、generated-y でそれらを指定します。

これにより、それらが stale asm-generic ワレッタとして扱われ、削除されることを防ぎます。

例:

#arch/x86/include/asm/Kbuild
generated-y += syscalls_32.h

8.4 mandatory-y¶

mandatory-y は include/(uapi/)asm-generic/Kbuild によって使用され、すべてのアーキテクチャに必須の ASM ヘッダの最小セットを定義します。

これは optional generic-y と同様に動作します。mandatory ヘッダが arch/$(ARCH)/include/(uapi/)/asm に欠如している場合、Kbuild は自動的に asm-generic のワレッタを生成します。

9 Kbuild 変数¶

トップ Makefile は次の変数をエクスポートします：

VERSION, PATCHLEVEL, SUBLEVEL, EXTRAVERSION

これらの変数は現在のカーネルバージョンを定義します。一部のアーキテクチャ Makefile はこれらの値を直接使用していますが、$(KERNELRELEASE) を使用すべきです。

($(VERSION), $(PATCHLEVEL), および $(SUBLEVEL) は「2」、「4」、「0」などの基本的な3つのバージョン番号を定義します。これら3つの値は常に数値です。

($(EXTRAVERSION) はプレパッチや追加パッチ用のさらに小さなサブレベルを定義します。通常は「-pre4」などの非数値文字列であり、空欄の場合もあります。

KERNELRELEASE

($(KERNELRELEASE) は「2.4.0-pre4」などの単一文字列で、インストールディレクトリ名の構築やバージョン文字列の表示に適しています。一部のアーキテクチャ Makefile はこの目的で使用しています。

ARCH

この変数は「i386」、「arm」、「sparc」などのターゲットアーキテクチャを定義します。一部の kbuild Makefile は $(ARCH) をテストして、どのファイルをコンパイルするかを決定します。

デフォルトでは、トップのMakefileは$(ARCH)をホストシステムのアーキテクチャと同じに設定します。クロスビルドを行う場合は、ユーザーがコマンドラインで$(ARCH)の値を上書きできます:

make ARCH=m68k ...
INSTALL_PATH

この変数は、アーキテクチャ固有のMakefileがインストール用に使用するディレクトリを指定します。アーキテクチャ固有のインストールターゲットを実行する際にはこの変数を使用してください。

INSTALL_MOD_PATH, MODLIB

($(INSTALL_MOD_PATH))は、モジュールインストール用に$(MODLIB)に接頭辞として指定します。この変数はMakefileに明示的に定義されていませんが、ユーザーが望む場合はコマンドラインで渡すことができます。

($(MODLIB))はモジュールインストール用のディレクトリを指定します。トップのMakefileでは$(MODLIB)を$(INSTALL_MOD_PATH)/lib/modules/$(KERNELRELEASE)に定義しています。ユーザーが望む場合はコマンドラインでこの値を上書きできます。

INSTALL_MOD_STRIP

この変数が指定されている場合、モジュールがインストール後にストリップされます。INSTALL_MOD_STRIPが「1」の場合、デフォルトのオプション--strip-debugが使用されます。それ以外の場合は、INSTALL_MOD_STRIPの値をstripコマンドのオプションとして使用します。

10 Makefile言語¶

カーネルのMakefileはGNU Makeで実行することを設計しています。MakefileはGNU Makeのドキュメントに記載されている機能のみを使用していますが、多くのGNU拡張機能も使用しています。

GNU Makeは基本的なリスト処理機能をサポートしています。カーネルのMakefileでは、少数の「if」ステートメントを使用した新しいスタイルのリスト構築と操作を行っています。

GNU Makeには2つの割当演算子「:=」と「=」があります。「:=」は右辺を即時評価し、左辺に実際の文字列を格納します。「=」は式定義のように動作し、右辺を未評価の形で保存して、左辺が使用されるたびに評価します。

「=」は特定のケースで適切ですが、通常は「:=」が正しい選択です。

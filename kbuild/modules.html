外部モジュールのビルド¶

このドキュメントでは、ツリー外のカーネルモジュールをビルドする方法について説明します。

1. はじめに¶

「kbuild」はLinuxカーネルで使用されるビルドシステムです。モジュールはkbuildを使用して、ビルドインフラストラクチャの変更と「gcc」に適切なフラグを取得するために互換性を保ちます。ツリー内とツリー外の両方のモジュールをビルドする機能が提供されており、どちらのビルド方法も類似しています。すべてのモジュールは最初にツリー外で開発・ビルドされます。

このドキュメントでは、ツリー外（または「外部」）モジュールをビルドすることに興味のある開発者向けの情報が説明されています。外部モジュールの作成者は、複雑さを隠すmakefileを提供すべきであり、単に「make」を実行するだけでモジュールをビルドできます。これは簡単に実行でき、セクション3で完全な例を示します。

2. 外部モジュールのビルド方法¶

外部モジュールをビルドするには、ビルドに使用される設定ファイルとヘッダーファイルを含む事前にビルドされたカーネルが必要です。また、カーネルがモジュールを有効にしている必要があります。ディストリビューションのカーネルを使用している場合、ディストリビューションが提供するカーネルを実行しているバージョン用のパッケージがあります。

代替案として、「make」ターゲット「modules_prepare」を使用できます。これにより、カーネルに必要な情報が含まれていることを確認します。このターゲットは、外部モジュールをビルドするためのカーネットソースツリーを簡単に準備するためのものです。

注意: 「modules_prepare」はCONFIG_MODVERSIONSが設定されていても、Module.symversをビルドしません。したがって、モジュールバージョンングが動作するには、フルなカーネルビルドを実行する必要があります。

2.1 コマンド構文¶

外部モジュールをビルドするコマンドは:

$ make -C <path_to_kernel_src> M=$PWD

kbuildシステムは、「M=<dir>」オプションが与えられたため、外部モジュールがビルドされていることを認識します。

実行中のカーネルに対してビルドするには:

$ make -C /lib/modules/`uname -r`/build M=$PWD

次に、剛才ビルドしたモジュール（複数可）をインストールするには、「modules_install」ターゲットをコマンドに追加します:

$ make -C /lib/modules/`uname -r`/build M=$PWD modules_install

2.2 オプション¶

($KDIRはカーネルソースディレクトリのパスを指します。)

make -C $KDIR M=$PWD

-C $KDIR

カーネルソースが配置されているディレクトリ。実行時に「make」が指定されたディレクトリに移動し、完了後に元のディレクトリに戻ります。

M=$PWD

kbuildに外部モジュールがビルドされていることを通知します。「M」に与えられる値は、外部モジュール（kbuildファイル）が配置されているディレクトリの絶対パスです。

2.3 ターゲット¶

外部モジュールをビルドする際には、「make」ターゲットの一部みにのみアクセス可能です。

make -C $KDIR M=$PWD [target]

デフォルトでは、現在のディレクトリに配置されているモジュール（複数可）がビルドされるため、ターゲットを指定する必要はありません。すべての出力ファイルもこのディレクトリに生成されます。カーネルソースの更新は試行されません。また、カーネルの「make」が成功したことが前提条件です。

modules

外部モジュール用のデフォルトターゲットです。ターゲットを指定しなかった場合と同じ機能を持ちます。上記の説明を参照してください。

modules_install

外部モジュール（複数可）をインストールします。デフォルトの場所は/lib/modules/<kernel_release>/extra/ですが、INSTALL_MOD_PATH（セクション5で説明）でプレフィックスを追加できます。

headers_install

ユーザー空間で使用可能な形式でヘッダーファイルをエクスポートします。デフォルトの場所は$PWD/usrです。INSTALL_HDR_PATHでこのパスを変更できます。

クリーン

モジュールディレクトリ内のすべての生成ファイルを削除します。

help

外部モジュール用の利用可能なターゲット一覧を表示します。

2.4 個別ファイルのビルド¶

モジュールの一部である単一ファイルをビルドすることが可能です。これはカーネル、モジュール、さらには外部モジュールにも同様に適用されます。

例（モジュール foo.ko は bar.o と baz.o から構成されます）：

make -C $KDIR M=$PWD bar.lst
make -C $KDIR M=$PWD baz.o
make -C $KDIR M=$PWD foo.ko
make -C $KDIR M=$PWD ./

3. 外部モジュール用の Kbuild ファイルの作成¶

前節では、実行中のカーネル用にモジュールをビルドするコマンドを確認しました。ただし、実際にビルドされるわけではありません。なぜなら、ビルドファイルが必要だからです。このファイルにはビルドするモジュール（複数可）の名前と必要なソースファイルの一覧が含まれます。このファイルは単一行で以下のように記述できます：

obj-m := <module_name>.o

kbuild システムは <module_name>.c から <module_name>.o をビルドし、リンク後にカーネルモジュール <module_name>.ko を生成します。上記の行は「Kbuild」ファイルまたは「Makefile」のどちらでも記述できます。モジュールが複数のソースから構成される場合、ファイル一覧を記述する追加の行が必要です：

<module_name>-y := <src1>.o <src2>.o ...

注意: kbuild で使用される構文についての詳細なドキュメンテーションは、 Linuxカーネルメイクファイル.

以下の例は、モジュール 8123.ko をビルドするために必要なファイルを示しています：

8123_if.c
8123_if.h
8123_pci.c
8123_bin.o_shipped      <= Binary blob

3.1 共有 Makefile¶

外部モジュールは常に「make」コマンドで引数を指定せずにビルドするためのラッパー Makefile を含みます。このターゲットは kbuild では使用されません。ただの利便性のために存在するものです。テストターゲットなどの追加機能を含めてもよいですが、名前衝突の可能性があるため kbuild から除外する必要があります。

例1：

--> filename: Makefile
ifneq ($(KERNELRELEASE),)
# kbuild part of makefile
obj-m  := 8123.o
8123-y := 8123_if.o 8123_pci.o 8123_bin.o

else
# normal makefile
KDIR ?= /lib/modules/`uname -r`/build

default:
        $(MAKE) -C $(KDIR) M=$$PWD

# Module specific targets
genbin:
        echo "X" > 8123_bin.o_shipped

endif

KERNELRELEASEのチェックは、makefileの2つの部分を分離するために使用されます。例では、kbuildは2つの割り当てのみを認識し、"make"はこれら2つの割り当てを除くすべての内容を認識します。これはファイルに対して行われる2つの処理のためです：最初の処理はコマンドラインで実行される"make"の処理であり、2番目の処理はデフォルトターゲットのパラメータ化された"make"によって起動されるkbuildシステムの処理です。

3.2 KbuildファイルとMakefileの分離¶

新しいカーネルバージョンでは、kbuildはまず"Kbuild"という名前のファイルを探します。そのファイルが見つからない場合にのみ、"makefile"を探します。"Kbuild"ファイルを使用することで、例1のmakefileを2つのファイルに分割できます。

例2：

--> filename: Kbuild
obj-m  := 8123.o
8123-y := 8123_if.o 8123_pci.o 8123_bin.o

--> filename: Makefile
KDIR ?= /lib/modules/`uname -r`/build

default:
        $(MAKE) -C $(KDIR) M=$$PWD

# Module specific targets
genbin:
        echo "X" > 8123_bin.o_shipped

例2の分割は、各ファイルの単純さのため疑問視されるかもしれませんが、一部の外部モジュールでは数百行にも及ぶmakefileが使用され、このような場合ではkbuild部分を残りと分離するメリットが非常に大きいです。

次の例は後方互換性のあるバージョンを示しています。

例3:

--> filename: Kbuild
obj-m  := 8123.o
8123-y := 8123_if.o 8123_pci.o 8123_bin.o

--> filename: Makefile
ifneq ($(KERNELRELEASE),)
# kbuild part of makefile
include Kbuild

else
# normal makefile
KDIR ?= /lib/modules/`uname -r`/build

default:
        $(MAKE) -C $(KDIR) M=$$PWD

# Module specific targets
genbin:
        echo "X" > 8123_bin.o_shipped

endif

ここでは"Kbuild"ファイルがmakefileからインクルードされています。これにより、"make"とkbuildの部分を別ファイルに分離した場合でも、古いバージョンのkbuild（makefileのみを認識するもの）を用いることができます。

3.3 バイナリ・ブロブ¶

一部の外部モジュールは、オブジェクトファイルをブロブとして含める必要があります。kbuildはこの機能をサポートしていますが、ブロブファイルは<filename>_shippedという名前でなければなりません。kbuildルールが有効になると、<filename>_shippedのコピーが作成され、_shippedが削除されて<filename>になります。この短いファイル名はモジュールの割り当てに使用できます。

このセクションを通して、8123_bin.o_shippedが使用されてカーネルモジュール8123.koが構築されており、8123_bin.oとしてインクルードされています：

8123-y := 8123_if.o 8123_pci.o 8123_bin.o

通常のソースファイルとバイナリファイルの区別はなく、kbuildはモジュールのオブジェクトファイルを作成する際、異なるルールを適用します。

3.4 複数のモジュールのビルド¶

kbuildは1つのビルドファイルで複数のモジュールをビルドできます。たとえば、foo.koとbar.koの2つのモジュールをビルドする場合、kbuildの行は以下のようになります：

obj-m := foo.o bar.o
foo-y := <foo_srcs>
bar-y := <bar_srcs>

これだけです！

4. インクルードファイル¶

カーネル内部では、ヘッダーファイルは以下のルールに従って標準的な場所に保持されています：

  • ヘッダーファイルがモジュールの内部インターフェースのみを記述する場合、そのファイルはソースファイルと同じディレクトリに配置されます。

  • ヘッダーファイルがカーネルの他の部分で使用されるインターフェースを記述し、それらが異なるディレクトリに配置されている場合、ファイルはinclude/linux/に配置されます。

    ノート:

    このルールには2つの重要な例外があります：大きなサブシステムはinclude/配下に独自のディレクトリを持ちます（例：include/scsi）、またアーキテクチャ固有のヘッダーファイルはarch/$(ARCH)/include/配下に配置されます。

4.1 カーネルインクルード¶

include/linux/配下にあるヘッダーファイルをインクルードするには、単に以下のようにします：

#include <linux/module.h>

kbuildは「gcc」にオプションを追加し、関連するディレクトリを検索するようにします。

4.2 単一サブディレクトリ¶

外部モジュールは、ソースコードが配置されている場所の別個のinclude/ディレクトリにヘッダーファイルを配置する傾向がありますが、これは通常のカーネルスタイルではありません。kbuildにディレクトリを通知するには、ccflags-yまたはCFLAGS_<filename>.oを使用します。

セクション3の例を使用して、8123_if.hをサブディレクトリ名includeに移動した場合、結果となるkbuildファイルは以下のようになります：

--> filename: Kbuild
obj-m := 8123.o

ccflags-y := -Iinclude
8123-y := 8123_if.o 8123_pci.o 8123_bin.o

割り当てにおいて、-Iとパスの間にスペースがないことに注意してください。これはkbuildの制限であり、スペースは存在してはなりません。

4.3 複数のサブディレクトリ¶

kbuildは複数のディレクトリに分散したファイルを処理できます。以下の例を参考にしてください：

.
|__ src
|   |__ complex_main.c
|   |__ hal
|       |__ hardwareif.c
|       |__ include
|           |__ hardwareif.h
|__ include
|__ complex.h

complex.koモジュールをビルドするには、以下のkbuildファイルが必要です：

--> filename: Kbuild
obj-m := complex.o
complex-y := src/complex_main.o
complex-y += src/hal/hardwareif.o

ccflags-y := -I$(src)/include
ccflags-y += -I$(src)/src/hal/include

ご覧のように、kbuildは他のディレクトリにあるオブジェクトファイルを処理できます。トリックは、kbuildファイルの位置に対する相対パスを指定することです。ただし、これは推奨されません。

ヘッダーファイルについては、kbuildに明示的に検索先を指定する必要があります。kbuildが実行されるとき、現在のディレクトリは常にカーネルツリーのルート（「-C」の引数）であり、絶対パスが必要です。$(src)は、現在実行中のkbuildファイルが配置されているディレクトリを指すことで絶対パスを提供します。

4.4 UAPIヘッダーファイルのインストール¶

外部モジュールは、インツリーの対応するドライバと同様にユーザー空間にヘッダーファイルをエクスポートできます。kbuildは、アウトオブツリーでheaders_installターゲットを実行することをサポートしています。kbuildがヘッダーファイルを検索する場所は$(M)/include/uapiと$(M)/arch/$(SRCARCH)/include/uapiです。

関連項目 ユーザー空間で使用するカーネルヘッダのエクスポート.

5. モジュールのインストール¶

カーネルに含まれるモジュールは次のディレクトリにインストールされます：

/lib/modules/$(KERNELRELEASE)/kernel/

外部モジュールは次のディレクトリにインストールされます：

/lib/modules/$(KERNELRELEASE)/extra/

5.1 INSTALL_MOD_PATH¶

上記はデフォルトのディレクトリですが、常に一部のカスタマイズが可能です。インストールパスにプレフィックスを追加するには、変数INSTALL_MOD_PATHを使用します：

$ make INSTALL_MOD_PATH=/frodo modules_install
=> Install dir: /frodo/lib/modules/$(KERNELRELEASE)/kernel/

INSTALL_MOD_PATHは、通常のシェル変数として設定するか、上記のように「make」を呼び出す際のコマンドラインで指定することもできます。この設定は、インストール時にインラインモジュールおよびアウトオブツリーモジュールのどちらにも効きます。

5.2 INSTALL_MOD_DIR¶

外部モジュールはデフォルトで/lib/modules/$(KERNELRELEASE)/extra/以下のディレクトリにインストールされますが、特定の機能用のモジュールを別ディレクトリに配置したい場合があります。その際は、INSTALL_MOD_DIRを用いて「extra」の代わりに別の名前を指定してください。

$ make INSTALL_MOD_DIR=gandalf -C $KDIR \
       M=$PWD modules_install
=> Install dir: /lib/modules/$(KERNELRELEASE)/gandalf/

6. モジュールバージョン管理¶

モジュールバージョン管理はCONFIG_MODVERSIONSタグで有効化され、単純なABIの整合性チェックとして使用されます。エクスポートされたシンボルのフルプロトタイプのCRC値が作成されます。モジュールがロード/使用される際、カーネル内のCRC値とモジュール内の同様な値を比較し、一致しない場合はカーネルがモジュールのロードを拒否します。

Module.symversは、カーネルビルドからエクスポートされたすべてのシンボルの一覧を含みます。

6.1 カーネルからのシンボル（vmlinux + モジュール）¶

カーネルのビルド中にModule.symversというファイルが生成されます。Module.symversは、カーネルおよびコンパイルされたモジュールからエクスポートされたすべてのシンボルを含み、各シンボルに対応するCRC値も保存されます。

Module.symversファイルの構文は以下の通りです：

<CRC>       <Symbol>         <Module>                         <Export Type>     <Namespace>

0xe1cc2a05  usb_stor_suspend drivers/usb/storage/usb-storage  EXPORT_SYMBOL_GPL USB_STORAGE

フィールドはタブで区切られ、値は空欄になる場合があります（例えばエクスポートされたシンボルに名前空間が定義されていない場合）。

CONFIG_MODVERSIONSが有効でないカーネルビルドでは、CRC値は0x00000000となります。

Module.symversは以下の2つの目的があります：

  1. vmlinuxおよびすべてのモジュールからエクスポートされたシンボルの一覧を提供します。

  2. CONFIG_MODVERSIONSが有効な場合、CRC値の一覧を提供します。

6.2 シンボルと外部モジュール¶

外部モジュールをビルドする際、ビルドシステムはカーネルからのシンボルにアクセスして、すべての外部シンボルが定義されているかを確認する必要があります。これはMODPOSTステップで行われ、modpostはカーネルソースツリーからModule.symversを読み取ってシンボルを取得します。MODPOSTステップ中に、その外部モジュールからエクスポートされたすべてのシンボルを含む新しいModule.symversファイルが作成されます。

6.3 他の外部モジュールからのシンボル¶

ときどき、外部モジュールは他の外部モジュールからエクスポートされたシンボルを使用します。Kbuildはすべてのシンボルについて完全な知識を持つ必要がありますが、未定義シンボルに関する警告を出さないための2つの解決策があります。

注意：トップレベルのkbuildファイルを使用する方法は推奨されていますが、特定の状況では実用的でない場合があります。

トップレベルのkbuildファイルを使用する

foo.koとbar.koという2つのモジュールがあり、foo.koがbar.koからシンボルを必要とする場合、共通のトップレベルのkbuildファイルを使用して両方のモジュールを同じビルドでコンパイルできます。以下のディレクトリレイアウトを考慮してください：

./foo/ <= contains foo.ko
./bar/ <= contains bar.ko

この場合、トップレベルのkbuildファイルは以下のようになります：

#./Kbuild (or ./Makefile):
        obj-m := foo/ bar/

そして実行：

$ make -C $KDIR M=$PWD

は予想通り動作し、両方のモジュールをそれぞれのモジュールからのシンボルを完全に理解しながらコンパイルします。

「make」変数 KBUILD_EXTRA_SYMBOLS を使用する

トップレベルのkbuildファイルを追加するのが現実的でない場合、ビルドファイルでKBUILD_EXTRA_SYMBOLS変数にスペース区切りのファイル一覧を割り当てることができます。これらのファイルはmodpostがシンボルテーブルの初期化時にロードされます。

7. ヒントとコツ¶

7.1 CONFIG_FOO_BARのテスト¶

モジュールは特定の CONFIG_ オプションをチェックして、モジュールに特定の機能が含まれているかを決定する必要があります。kbuildではこれを実現するために、 CONFIG_ 変数を直接参照します：

#fs/ext2/Makefile
obj-$(CONFIG_EXT2_FS) += ext2.o

ext2-y := balloc.o bitmap.o dir.o
ext2-$(CONFIG_EXT2_FS_XATTR) += xattr.o

外部モジュールはこれまで「grep」を使用して、.config内の特定の CONFIG_ 設定を直接チェックしていました。この使用法は破綻しています。前述したように、外部モジュールはkbuildを使用してビルドするべきであり、したがってインストール済みモジュールと同じ方法で CONFIG_ 定義をテストできます。

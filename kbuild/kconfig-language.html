Kconfig言語¶

はじめに¶

構成データベースは、ツリー構造で整理された構成オプションのコレクションです:

+- Code maturity level options
|  +- Prompt for development and/or incomplete code/drivers
+- General setup
|  +- Networking support
|  +- System V IPC
|  +- BSD Process Accounting
|  +- Sysctl support
+- Loadable module support
|  +- Enable loadable module support
|     +- Set version information on all module symbols
|     +- Kernel module loader
+- ...

すべてのエントリは独自の依存関係を持ち、これらの依存関係はエントリの可視性を決定するために使用されます。すべての子エントリは、その親エントリが可視である場合にのみ可視です。

メニュー項目¶

ほとんどのエントリは構成オプションを定義し、他のすべてのエントリはそれらを整理する役割を持ちます。単一の構成オプションは次のようになります:

config MODVERSIONS
      bool "Set version information on all module symbols"
      depends on MODULES
      help
        Usually, modules have to be recompiled whenever you switch to a new
        kernel.  ...

すべての行はキーワードで始まり、複数の引数を後続する場合があります。「config」は新しい構成エントリを開始します。次の行はこの構成オプションの属性を定義します。属性にはオプションの型、入力プロンプト、依存関係、ヘルプテキスト、デフォルト値などが含まれます。同じ名前の構成オプションを複数回定義できますが、各定義には1つの入力プロンプトのみを含め、型が競合してはなりません。

メニュー属性¶

メニュー項目はいくつかの属性を持つことができますが、すべての属性がすべての場所で適用されるわけではありません（構文を参照）。

  • 型定義: 「bool」／「tristate」／「string」／「hex」／「int」

    すべての構成オプションには型が必要です。基本的な型は2種類のみあり、tristateとstringです。他の型はこれら2つに基づいています。型定義にはオプションで入力プロンプトを指定できるため、次の2つの例は同等です:

    bool "Networking support"

    および：

    bool
prompt "Networking support"

  • 入力プロンプト: 「prompt」<prompt> [「if」<expr>]

    すべてのメニュー項目は1つのプロンプトのみを持つことができ、これはユーザーに表示されます。オプションでこのプロンプト専用の依存関係を「if」で追加できます。

  • デフォルト値: 「default」<expr> [「if」<expr>]

    構成オプションには任意の数のデフォルト値を持つことができます。複数のデフォルト値が表示される場合、最初に定義されたもののみが有効です。デフォルト値はその定義されたメニュー項目に限らず、他の場所で定義されたり、以前の定義によって上書きされたりする可能性があります。ユーザーが入力プロンプトを通じて値を設定していない場合にのみ、デフォルト値が構成シンボルに割り当てられます。入力プロンプトが表示されている場合、デフォルト値はユーザーに提示され、上書きされる可能性があります。オプションでこのデフォルト値専用の依存関係を「if」で追加できます。

デフォルト値は意図的に「n」に設定されており、ビルドの肥大化を防ぐためです。例外を除いて、新しい構成オプションはこの設定を変更すべきではありません。意図は「make oldconfig」がリリースごとに構成に追加する内容をできるだけ少なくすることです。

注意:

「default y/m」に該当するものは以下の通り:

  1. 以前は常にビルドされていた何かのための新しいKconfigオプションは、「default y」にするべきです。

  2. 他のKconfigオプションを表示/非表示にするが自身のコードを生成しないゲートキープ用のKconfigオプションは、「default y」にすべきです。これによりユーザーが他のオプションを確認できるようにします。

  3. 「default n」のドライバ用のサブドライバの動作や類似オプション。これにより健全なデフォルト値を提供できます。

  4. 誰もが期待するハードウェアやインフラストラクチャ（例: CONFIG_NETやCONFIG_BLOCKなど）。これらはまれな例外です。

  • 型定義 + デフォルト値:

    "def_bool"/"def_tristate" <expr> ["if" <expr>]

    これは型定義と値の省略形です。必要に応じて「if」でこのデフォルト値の依存関係を追加できます。

  • 依存関係: 「depends on」<式>

    このメニュー項目の依存関係を定義します。複数の依存関係がある場合、'&&'で結合されます。依存関係はこのメニュー項目内のすべてのオプションに適用されるため、次の2つの例は同等です:

    bool "foo" if BAR
default y if BAR

    および：

    depends on BAR
bool "foo"
default y

  • 逆依存関係: 「select」<シンボル> [「if」<式>]

    通常の依存関係はシンボルの上界を制限します（下記参照）。逆依存関係は別のシンボルの下界を強制的に設定できます。現在のメニューシンボルの値が、<シンボル>の最小値として使用されます。<シンボル>が複数回選択された場合、下限は最大の選択値になります。逆依存関係は論理型または三態型のシンボルのみで使用できます。

    注意:

    selectは注意深く使用する必要があります。selectは依存関係を訪問せずにシンボルを特定の値に強制します。selectを濫用すると、FOOがBARに依存しているにもかかわらずBARが未設定の場合でもFOOを選択できるようになります。一般的には表示されないシンボル（どこにもプロンプトがない）や依存関係のないシンボルに対してのみselectを使用すべきです。これにより有用性は制限されますが、不正な構成設定を回避できます。

  • 弱い逆依存関係: 「imply」<シンボル> [「if」<式>]

    これは「select」と同様に他のシンボルの下界を強制しますが、'implied'シンボルの値は直接の依存関係や表示プロンプトによりnに設定される可能性があります。

    次の例を考慮してください:

    config FOO
    tristate "foo"
    imply BAZ

config BAZ
    tristate "baz"
    depends on BAR

    以下の値が可能です:

    FOO

    BAR

    BAZのデフォルト

    BAZの選択肢

    n

    y

    n

    N/m/y

    m

    y

    m

    M/y/n

    y

    y

    y

    Y/m/n

    n

    m

    n

    N/m

    m

    m

    m

    M/n

    y

    m

    n

    M/n

    y

    n

    N

    これは複数のドライバが二次サブシステムに接続できる能力を示しつつ、ユーザーがそのサブシステムを無効にしてもこれらのドライバをアンセットする必要がない場合に役立ちます。

    注意: FOO=yとBAR=mの組み合わせがリンクリンクエラーを引き起こす場合、関数呼び出しをIS_REACHABLE()で保護できます:

    foo_init()
{
        if (IS_REACHABLE(CONFIG_BAZ))
                baz_register(&foo);
        ...
}

    注意: BAZが提供する機能がFOOにとって非常に望ましい場合、FOOはBAZだけでなく、その依存関係であるBARも含めて明示する必要があります:

    config FOO
    tristate "foo"
    imply BAR
    imply BAZ

  • メニュー表示制限: 「表示条件を設定」<式>

    この属性はメニューブロックにのみ適用可能です。条件が偽の場合、メニューブロックはユーザーに表示されません（含まれる記号は他の記号によって選択される可能性があります）。これは個々のメニュー項目に対する条件付き「プロンプト」属性に似ています。デフォルト値は「表示」でtrueです。

  • 数値範囲: 「範囲」<記号> <記号> [「if」<式>]

    これはintおよびhex記号の可能な入力値の範囲を制限するための機能です。ユーザーは、最初の記号以上かつ第二の記号以下の値のみを入力できます。

  • ヘルプテキスト: 「ヘルプ」

    これはヘルプテキストを定義します。ヘルプテキストの終わりはインデントレベルによって決まり、これはヘルプテキストの最初の行よりもインデントが小さい最初の行で終了します。

  • その他のオプション: 「オプション」<記号>[=<値>]

    このオプション構文により、さまざまな非標準的なオプションを定義でき、メニュー項目およびその構成記号の動作を変更することが可能です。現在可能なオプションは以下の通りです:

    • 「defconfig_list」 このオプションは、メインの.configファイルがまだ存在していない場合に使用するデフォルト項目の一覧を宣言します。

    • 「modules」 このオプションは、すべての構成記号に第三のモジュール状態を有効にするMODULES記号としての記号を宣言します。最大1つの記号に「modules」オプションを設定できます。

    • 「allnoconfig_y」 このオプションは、「allnoconfig」を使用する際の値がyとなる記号を宣言します。他の記号を隠すための記号に使用します。

メニュー依存関係¶

依存関係はメニュー項目の表示可能性を定義し、三態記号の入力範囲を縮小することもできます。式で使用される三態論理は、通常の論理論証に比べて1つの状態を追加してモジュール状態を表現します。依存関係式の構文は以下の通りです:

<expr> ::= <symbol>                           (1)
         <symbol> '=' <symbol>                (2)
         <symbol> '!=' <symbol>               (3)
         <symbol1> '<' <symbol2>              (4)
         <symbol1> '>' <symbol2>              (4)
         <symbol1> '<=' <symbol2>             (4)
         <symbol1> '>=' <symbol2>             (4)
         '(' <expr> ')'                       (5)
         '!' <expr>                           (6)
         <expr> '&&' <expr>                   (7)
         <expr> '||' <expr>                   (8)

式は優先順位の高い順にリストされています。

  1. 記号を式に変換します。論理記号および三態記号はそれぞれの式値に変換され、他の記号タイプはすべて'n'になります。

  2. 両方の記号の値が等しい場合、'y'を返します。それ以外の場合、'n'を返します。

  3. 両方の記号の値が等しい場合、'n'を返します。それ以外の場合、'y'を返します。

  4. <記号1>の値が<記号2>の値よりそれぞれ小さい、大きい、小さいか等しい、大きいか等しい場合、'y'を返します。それ以外の場合、'n'を返します。

  5. 式の値を返します。優先順位を上書きするために使用します。

  6. （2-/expr/）の結果を返します。

  7. min(/expr/, /expr/)の結果を返します。

  8. max(/expr/, /expr/)の結果を返します。

式の値は「n」、「m」または「y」（計算ではそれぞれ0、1、2に対応）にすることができます。メニュー項目が表示されるのは、その式が「m」または「y」に評価されたときです。

シンボルには2種類あります：定数シンボルと非定数シンボルです。非定数シンボルは最も一般的で、「config」ステートメントで定義されます。非定数シンボルはアルファベット数字またはアンダースコアのみで構成されます。定数シンボルは式の一部としてのみ使用され、常にシングルクォートまたはダブルクォートで囲まれます。クォート内では任意の文字が使用可能で、クォートは「'」でエスケープします。

メニュー構造¶

メニュー項目のツリー上の位置は2つの方法で決定されます。まず、明示的に指定することもできます：

menu "Network device support"
      depends on NET

config NETDEVICES
      ...

endmenu

「menu」…「endmenu」ブロック内のすべての項目は「Network device support」のサブメニューになります。すべてのサブ項目は親メニュー項目の依存関係を継承します。たとえば、この場合、依存関係「NET」がconfigオプションNETDEVICESの依存関係リストに追加されます。

メニュー構造を生成するもう一つの方法は依存関係を分析することです。メニュー項目が前の項目に依存している場合、それをサブメニューにすることが可能です。まず、前の（親）シンボルが依存関係リストに含まれている必要があります。そして次の2つの条件のうち少なくとも1つが真である必要があります：

  • 親が「n」に設定されている場合、子項目は表示されません。

  • 親が表示されている場合に限り、子項目が表示されます：

    config MODULES
    bool "Enable loadable module support"

config MODVERSIONS
    bool "Set version information on all module symbols"
    depends on MODULES

comment "module support disabled"
    depends on !MODULES

MODVERSIONSはMODULESに直接依存しており、これはMODULESが「n」以外の場合にのみ表示されます。一方、コメントはMODULESが「n」に設定されているときにのみ表示されます。

Kconfig構文¶

設定ファイルは、各行がキーワードで始まる（ヘルプテキストを除く）一連のメニュー項目を記述します。次のキーワードはメニュー項目の終わりを示します：

  • config

  • menuconfig

  • choice/endchoice

  • コメント

  • menu/endmenu

  • if/endif

  • source

最初の5つはメニュー項目の定義を開始します。

config:

"config" <symbol>
<config options>

これはconfigシンボル <symbol> を定義し、上述の属性のいずれかをオプションとして受け入れます。

menuconfig:

"menuconfig" <symbol>
<config options>

これは上記のシンプルな設定項目と似ていますが、フロントエンドにサブオプションが別個のオプションリストとして表示されるようにヒントを与えます。すべてのサブオプションが本当にメニューconfig項目の下に表示され、外側に表示されないことを確認するには、<config options>リスト内のすべての項目がmenuconfigシンボルに依存している必要があります。実際には、次の2つの構造のいずれかを使用することでこの目的を達成します。

(1):
menuconfig M
if M
    config C1
    config C2
endif

(2):
menuconfig M
config C1
    depends on M
config C2
    depends on M

以下の例(3)と(4)では、C1とC2はまだMの依存関係を持ちますが、C0がMに依存しないことにより、menuconfig Mの下に表示されなくなります。

(3):
menuconfig M
    config C0
if M
    config C1
    config C2
endif

(4):
menuconfig M
config C0
config C1
    depends on M
config C2
    depends on M

choices:

"choice" [symbol]
<choice options>
<choice block>
"endchoice"

これは選択グループを定義し、上記の属性のいずれかをオプションとして受け入れます。選択肢はboolまたはtristateのタイプのみ許容されます。選択肢にタイプが指定されていない場合、そのグループ内の最初の選択肢要素のタイプによってタイプが決定され、どの選択肢要素にもタイプが指定されていない場合は未知のままになります。

ブール選択肢は単一の設定項目のみを選択可能ですが、トリステート選択肢は任意の数の設定項目を'm'に設定できます。複数のドライバが同じハードウェアに存在し、かつ1つのドライバのみがカーネルにコンパイル/ロードされる場合でも、すべてのドライバをモジュールとしてコンパイルできるため、この機能が利用できます。

選択肢は「optional」という別のオプションを受け入れ、選択肢を'n'に設定し、選択項目を指定する必要がありません。選択肢に[symbol]が関連付けされていない場合、その選択肢の複数の定義は許容されません。[symbol]が選択肢に関連付けられている場合、同じ選択肢（同じ項目を持つ）を別の場所で定義できます。

comment:

"comment" <prompt>
<comment options>

これは設定プロセス中にユーザーに表示され、出力ファイルにもエコーされるコメントを定義します。可能なオプションは依存関係のみです。

menu:

"menu" <prompt>
<menu options>
<menu block>
"endmenu"

これはメニューブロックを定義します。詳しくは上記の「メニュー構造」を参照してください。可能なオプションは依存関係と「visible」属性のみです。

if:

"if" <expr>
<if block>
"endif"

これはifブロックを定義します。依存式<expr>がすべての包含されたメニュー項目に追加されます。

source:

"source" <prompt>

指定された構成ファイルを読み込みます。このファイルは常に解析されます。

mainmenu:

"mainmenu" <prompt>

これは構成プログラムがタイトルバーを使用する場合にタイトルバーを設定します。構成の先頭に配置し、他のステートメントよりも前に配置する必要があります。

‘#’ Kconfigソースファイルコメント:

ソースファイルの行のどこかに引用符のない‘#’文字がある場合、それはソースファイルコメントの開始を示します。その行の残りはコメントです。

Kconfigヒント¶

これはKconfigのヒントのコレクションで、多くは最初は明らかではなく、多くの場合、複数のKconfigファイルでidiom（慣用句）となっています。

共通の機能を追加し、使用方法をカスタマイズ可能にします¶

一部のアーキテクチャでしか使われないが、すべてのアーキテクチャで必要ではない機能の実装は、一般的なidiomとして、共通のKconfigファイルで定義されたHAVE_*というconfig変数を使用し、関連するアーキテクチャで選択する方法が推奨されます。例として、汎用的なIOMAP機能があります。

lib/Kconfigで以下のように見ます：

# Generic IOMAP is used to ...
config HAVE_GENERIC_IOMAP

config GENERIC_IOMAP
      depends on HAVE_GENERIC_IOMAP && FOO

lib/Makefileで以下のように見ます：

obj-$(CONFIG_GENERIC_IOMAP) += iomap.o

汎用的なIOMAP機能を使用する各アーキテクチャで以下のように見ます：

config X86
      select ...
      select HAVE_GENERIC_IOMAP
      select ...

注意：既存のconfigオプションを使用し、新しいconfig変数を追加せずにHAVE_GENERIC_IOMAPを選択します。

注意：内部のconfig変数HAVE_GENERIC_IOMAPを使用しています。これはselectコマンドの制限（依存関係に関係なくconfigオプションを'y'に強制する）を克服するため導入されました。依存関係はGENERIC_IOMAPシンボルに移し、selectがシンボルを'y'に強制する状況を回避しています。

コンパイラのサポートが必要な機能の追加¶

いくつかの機能はコンパイラのサポートが必要です。コンパイラ機能への依存関係を記述する推奨方法は、「depends on」に続いてテストマクロを記述することです：

config STACKPROTECTOR
      bool "Stack Protector buffer overflow detection"
      depends on $(cc-option,-fstack-protector)
      ...

makefileおよび/またはCソースファイルにコンパイラの能力を公開する場合、 CC_HAS_ はconfigオプションの推奨されるプレフィックスです：

config CC_HAS_ASM_GOTO
      def_bool $(success,$(srctree)/scripts/gcc-goto.sh $(CC))

モジュールのみでビルドする¶

コンポーネントのビルドをモジュールのみに制限するには、configシンボルに「depends on m」を付与します。例：

config FOO
      depends on BAR && m

FOOはモジュール (=m) または無効 (=n) に制限されます。

Kconfig再帰的依存関係の制限¶

Kconfig で「recursive dependency detected（再帰的な依存関係が検出されました）」というエラーが発生した場合、Kconfig で再帰的な依存関係の問題に遭遇していることになります。再帰的な依存関係とは、循環的な依存関係を指します。Kconfig ツールは、Kconfig ファイルが指定された構成要件に合致していることを確認する必要があります。そのため、Kconfig はすべての Kconfig シンボルの可能な値を特定しなければなりませんが、2つ以上の Kconfig シンボル間に循環的な関係がある場合、これは現在実現不可能です。詳細については、以下の「Simple Kconfig recursive issue（シンプルな Kconfig 再帰問題）」サブセクションを参照してください。Kconfig は再帰的な依存関係の解決を行っていません。これは Kconfig ファイルの作成者にとっていくつかの影響を及ぼします。まず、この問題の原因について説明し、その後、この問題が Kconfig 開発者に与える技術的な制限の例を提供します。この制限を改善したい熱心な開発者は、次のサブセクションを参照してください。

シンプルな Kconfig 再帰問題¶

参照: Documentation/kbuild/Kconfig.recursion-issue-01

テスト方法:

make KBUILD_KCONFIG=Documentation/kbuild/Kconfig.recursion-issue-01 allnoconfig

Kconfig 再帰問題の実用的な解決策¶

再帰的な Kconfig 問題に遭遇した開発者には2つの選択肢があります。以下に記載し、これらの解決策で解決された歴史的な問題の一覧も提供します。

  1. 不要な「select FOO」または「depends on FOO」を削除してください

  2. 依存関係のセマンティクスを一致させる:

    b1) すべての「select FOO」を「depends on FOO」に置き換えるか、

    b2) すべての「depends on FOO」を「select FOO」に置き換えるか

a) の解決策は、サンプル Kconfig ファイル Documentation/kbuild/Kconfig.recursion-issue-01 を使用してテストできます。CORE_BELL_A_ADVANCED から「select CORE」を削除することで、CORE_BELL_A が CORE に依存しているため、すでに明示的に含まれているためです。ただし、一部の依存関係条件を削除できない場合があります。そのような場合は、解決策 b) を使用してください。

b) の2つの異なる解決策は、サンプル Kconfig ファイル Documentation/kbuild/Kconfig.recursion-issue-02 を使用してテストできます。

今後のKconfigの作業¶

Kconfigのセマンティクスの明確化と、SATソルバーの利用評価の両方の分野での作業は歓迎されます。完全なSATソルバーは、より複雑な依存関係マッピングやクエリを可能にするために望ましい場合があります。例えば、SATソルバーの利用例として、現在の再帰的な依存関係問題の処理が挙げられます。ただし、このような問題を解決するかどうかは不明ですが、その評価は望ましいです。もし完全なSATソルバーのサポートが複雑すぎて、再帰的な依存関係問題を解決できないと判明した場合、Kconfigは少なくとも明確で定義されたセマンティクスを有する必要があります。これは再帰的な依存関係などにかかわる制限や要件を文書化することも含みます。

Kconfigにおいて、これらの分野のさらなる作業は歓迎されます。次に2つのサブセクションでこれらについて詳しく説明します。

Kconfigのセマンティクス¶

Kconfigの利用範囲は広く、Linuxは現在Kconfigの利用者の中の一つに過ぎません：ある研究では、12プロジェクトにおけるKconfigの利用を広範な分析が完了しています 0. 広く利用されているにもかかわらず、このドキュメントは基本的なKconfig構文の記述には十分な仕事をしており、Kconfigのセマンティクスのより正確な定義は歓迎されます。あるプロジェクトでは、xconfigコンフィギュレータの利用を通じてKconfigのセマンティクスを推論しました 1. 推論されたセマンティクスが我々の意図したKconfig設計目標と一致するかを確認する作業が必要です。

明確に定義されたセマンティクスは、依存関係の実用的な評価に役立つツールにとって有用です。たとえば、Kconfigの推論されたセマンティクスを論理式に変換し、SATソルバーを実行して非活性のコード/機能（常に非アクティブ）を見つける作業が行われ、この手法によりLinuxでは114の非活性機能が見つかりました 1 (セクション8: 有効性への脅威)。

Kconfigが工業用変動モデリング言語のリーディングな言語の一つであるため、この確認は役立つかもしれません。 1 2. このような言語の実用的な利用を評価するのに役立ちます。その利用は理論的であり、現実世界の要件は十分に理解されていませんでした。現状では、Kconfigなどの変動モデリング言語のセマンティクスを推論するために逆工学技術がのみ使用されていました 3.

Kconfig用の完全なSATソルバー¶

SATソルバーは 4 以前のサブセクションで指摘されているように、Kconfigはまだ直接使用されていませんが、Kconfigの推論されたセマンティクスをブール抽象で表現し、Kconfig論理をブール式に翻訳してSATソルバーを実行するための作業が行われています 5もう一つの関連プロジェクトとして知られているのはCADOSです 6 (以前のVAMOS 7) およびツール、主にundertaker 8、最初に導入されたのは 9undertakerの基本的なコンセプトは、Kconfigから変動モデルを抽出し、CPPの#ifdefとビルドルールから抽出した命題論理式と組み合わせてSATソルバーに投入し、死コード、死ファイル、死シンボルを検出することです。KconfigでSATソルバーを使用することが望ましい場合、このような努力をKconfig上での再利用を検討する方法かもしれません。既存プロジェクトのメンターから十分な関心があり、この作業をアップストリームに統合する方法をアドバイスするだけでなく、長期的にメンテナンスする支援も得られます。関心のある開発者は以下のリンクを参照してください:

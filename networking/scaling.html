Linuxネットワーキングスタックにおけるスケーリング¶

はじめに¶

このドキュメントでは、Linuxネットワーキングスタックにおける補完的な技術セットについて説明し、マルチプロセッサシステムにおける並列性の向上とパフォーマンスの改善を目的としています。

以下の技術が説明されています：

  • RSS: 受信側スケーリング

  • RPS: 受信パケットステアリング

  • RFS: 受信フローステアリング

  • 高速化された受信フローのステアリング

  • XPS: 送信パケットステアリング

RSS: 受信側スケーリング¶

現代のNIC（ネットワークインターフェースカード）は、複数の受信および送信ディスクリプタキュー（マルチキュー）をサポートしています。受信時に、NICは異なるパケットを異なるキューに送ることで、CPU間で処理を分散できます。NICは、各パケットに対してフィルタを適用し、それを少数の論理フローのいずれかに割り当てることでパケットを分散します。各フローのパケットは、別個の受信キューにリダイレクトされ、そのキューは別個のCPUで処理されます。このメカニズムは一般的に「受信側スケーリング」（RSS）として知られています。RSSおよび他のスケーリング技術の目標は、パフォーマンスを均等に向上させることです。マルチキューの分散はトラフィックの優先順位付けにも利用できますが、これはこれらの技術の焦点ではありません。

RSSで使用されるフィルタは、ネットワークおよび/またはトランスポートレイヤーヘッダー上のハッシュ関数で構成されます。例えば、パケットのIPアドレスとTCPポートの4要素ハッシュです。RSSの最も一般的なハードウェア実装は、128エントリの間接テーブルを使用します。各エントリはキュー番号を保存しており、パケットの受信キューは、計算されたハッシュ（通常はトーチリズハッシュ）の下位7ビットをマスクして得られる数値を間接テーブルのキーとして使用し、対応する値を読み取ることで決定されます。

一部の高度なNICは、プログラマブルフィルタに基づいてパケットをキューにリダイレクトできます。例えば、ウェブサーバーにバインドされたTCPポート80のパケットは、独自の受信キューにリダイレクトされます。このような「n-タプル」フィルタは、ethtool（–config-ntuple）から設定できます。

RSSの設定¶

マルチキューをサポートするNICのドライバは、通常、ハードウェアキューの数を指定するカーネルモジュールパラメータを提供します。例えば、bnx2xドライバではこのパラメータはnum_queuesと呼ばれます。典型的なRSS設定では、デバイスが十分なキューをサポートする場合、各CPUに1つの受信キューを割り当て、そうでない場合は少なくとも各メモリドメイン（メモリレベルL1、L2、NUMAノードなどを持つCPUの集合）に1つずつ割り当てます。

RSSデバイスのインデックステーブルは、マスクされたハッシュでキューを解決する仕組みを持ち、通常ドライバが初期化時にプログラムします。デフォルトのマッピングはテーブル内でキューを均等に配分しますが、ethtoolコマンド（–show-rxfh-indir および –set-rxfh-indir）を使用して実行時にもインデックステーブルを取得・変更できます。インデックステーブルを変更することで、キューごとに異なる相対的な重みを割り当てることも可能です。

RSS IRQ設定¶

各受信キューには個別に割り当てられたIRQがあります。NICはこのIRQを通じて、指定されたキューに新しいパケットが到着したことをCPUに通知します。PCIeデバイスのシグナル経路ではメッセージ送信割込み（MSI-X）が使用され、各割込みを特定のCPUにルーティングできます。キューとIRQの割り当ては/proc/interruptsから確認可能です。デフォルトではIRQは任意のCPUで処理される可能性があります。パケット処理の一部が受信割込み処理で行われるため、CPU間で受信割込みを分散することが望ましいです。各割込みのIRQアフィニティを手動で調整するには SMP IRQ アフィニティ、一部のシステムではirqbalanceというデーモンが動的にIRQ割り当てを最適化し、手動設定を上書きする可能性があります。

推奨設定¶

レイテンシーが懸念される場合や受信割込み処理がボトルネックになる場合はRSSを有効にします。CPU間で負荷を分散することでキューの長さが短縮されます。低レイテンシーなネットワーキングでは、システム内のCPU数（またはNICの最大値、低い場合はそれに準じる）に合わせてキューを最大限に割り当てることが最適です。高レートでの最適な設定は、CPUの過負荷による受信キューのオーバーフローが発生しない最小の受信キュー数です。これはデフォルトモードで割込み統合が有効な場合、追加されるキューごとに割込み（および作業）の総数が増加するためです。

CPUごとの負荷はmpstatユーティリティで確認できますが、ハイパースレッディング（HT）を持つプロセッサでは各ハイパースレッディングが別個のCPUとして表示されます。割込み処理ではHTは初期テストではメリットが見られず、システム内のCPUコア数に合わせてキュー数を制限してください。

RPS: 受信パケットステアリング¶

Receive Packet Steering (RPS) は、論理的に RSS のソフトウェア実装とみなされます。ソフトウェアであるため、データパスにおいて後段で呼ばれる必要があります。RSS はハードウェア割込みハンドラを実行するキューおよび CPU を選択しますが、RPS は割込みハンドラの上位プロトコル処理を実行する CPU を選択します。これは、パケットを目的の CPU のバックログキューに配置し、CPU を起動することで実現されます。RPS は RSS と比較して以下の利点があります:

  1. 任意の NIC と併用可能です

  2. ソフトウェアフィルタを追加して新しいプロトコルのハッシュ処理が容易です

  3. ハードウェアデバイスの割込みレートは増加しません（ただしプロセッサ間割込み (IPI) を導入します）

RPS は受信割込みハンドラの下半分で呼ばれます。ドライバがネットワークスタックへパケットを送信する際、 netif_rx() または netif_receive_skb()。これらは get_rps_cpu() 関数を呼び出し、パケットを処理するキューを選択します。

RPS のターゲット CPU を決定する最初のステップは、パケットのアドレスやポートに基づいたフローのハッシュ計算です（プロトコルによって 2 重または 4 重のハッシュが使用されます）。これはパケットの関連するフローの一貫したハッシュとして機能します。このハッシュはハードウェアによって提供されるか、スタック内で計算されます。機能するハードウェアはパケットの受信ディスクリプタにハッシュを渡すことができ、これは通常 RSS で使用される同じハッシュ（例: Toeplitz ハッシュ）です。このハッシュは skb->hash に保存され、スタックの他の場所でパケットのフローのハッシュとして使用できます。

各受信ハードウェアキューには、RPS がパケットを処理するための CPU のリストが関連付けられています。各受信パケットに対して、フローのハッシュをリストのサイズで割った余りからインデックスを計算します。インデックスされた CPU がパケットの処理ターゲットとなり、パケットはその CPU のバックログキューの末尾にキューイングされます。下半分ルーチンの終わりに、キューイングされたパケットがある CPU に対して IPI が送信されます。IPI はリモート CPU のバックログ処理を起動し、キューイングされたパケットはネットワークスタックへ処理されます。

RPS 設定¶

RPS は CONFIG_RPS kconfig シンボルでコンパイルされたカーネルが必要です（SMP ではデフォルトで有効）。コンパイルされていても、明示的に設定されていない限り RPS は無効です。各受信キューに対して RPS がトラフィックを転送可能な CPU のリストを sysfs ファイルエントリで設定できます:

/sys/class/net/<dev>/queues/rx-<n>/rps_cpus

このファイルは CPU のビットマップを実装しています。ビットマップがゼロ（デフォルト）の場合、RPS は無効となり、パケットは割込みした CPU で処理されます。 SMP IRQ アフィニティ CPUがビットマップに割り当てられる仕組みを説明しています。

推奨設定¶

単一のキューデバイスの場合、典型的なRPS設定は、割り込みCPUと同じメモリドメインにあるCPUをrps_cpusに設定することです。NUMAローカリティが問題でなければ、システム内のすべてのCPUを指定することも可能です。高トラフィック状態では、割り込みCPUをマップから除外する方が賢明かもしれません。なぜなら、そのCPUがすでに多くの作業を実行しているからです。

マルチキューシステムでは、RSSがハードウェア受信キューを各CPUに割り当てるように設定されている場合、RPSは冗長で不要かもしれません。ハードウェアキューがCPUより少ない場合、各キューのrps_cpusがそのキューの割り込みCPUと同じメモリドメインのCPUである場合、RPSは有益かもしれません。

RPS フロー制限¶

RPSは、CPU間で受信処理をスケーリングする際にパケットの再配列を導入しません。すべてのフローが同じCPUにパケットを送信する場合のトレードオフは、パケットレートが異なるフローによってCPUの負荷が不均衡になる可能性があります。極端なケースでは、単一のフローがトラフィックを支配します。特に多くの同時接続を持つ一般的なサーバー作業負荷では、このような挙動は設定ミスや偽装されたソースからのDoS攻撃などの問題を示唆しています。

フロー制限はオプションのRPS機能で、CPU競合時に小規模なフローを優先するために、大規模なフローのパケットを小規模なフローのパケットよりも少し早くドロップします。これはRPSまたはRFS宛てのCPUが飽和に近づいた場合にのみ有効です。CPUの入力パケットキューがsysctl net.core.netdev_max_backlogで設定された最大キュー長の半分を超えた場合、カーネルは過去256パケットのフローベースのパケットカウントを開始します。新しいパケットが到着する際、フローが設定された比率（デフォルトでは半分）を超える場合、新しいパケットはドロップされます。他のフローのパケットは、入力パケットキューがnetdev_max_backットに達するまでドロップされません。入力パケットキュー長がしきい値以下の場合、パケットはドロップされませんので、フロー制限は接続を完全に切断しません。つまり、大規模なフローも接続を維持します。

インターフェース¶

フロー制限はデフォルトでコンパイルされています（CONFIG_NET_FLOW_LIMIT）が、有効になっていません。各CPUで独立して実装されており（ロックやキャッシュ競合を避けるため）、sysctl net.core.flow_limit_cpu_bitmapの関連ビットを設定することで各CPUごとに有効/無効を切り替えます。procfsから呼び出される際には、rps_cpusと同じCPUビットマップインターフェースを提供しています（上記参照）。

/proc/sys/net/core/flow_limit_cpu_bitmap

フローごとのレートは、各パケットをハッシュテーブルのバケットに割り当て、各バケットのカウンターをインクリメントすることで計算されます。ハッシュ関数はRPSでCPUを選択するのと同じですが、バケット数がCPU数よりはるかに多い場合があるため、フロー制限は大規模なフローをより細かい粒度で識別し、偽陽性を減らします。デフォルトのテーブルには4096個のバケットがあります。この値はsysctlを通じて変更可能です:

net.core.flow_limit_table_len

この値は新しいテーブルが割り当てられるときにのみ参照されます。変更しても既存のアクティブなテーブルには影響しません。

推奨設定¶

多くの同時接続を持つシステムでは、1つの接続がCPUの50%を占めることで問題が発生している場合があります。このような環境では、ネットワークrx割込みを処理するすべてのCPUでこの機能を有効にしてください（/proc/irq/N/smp_affinityで設定されたCPU）。

この機能は、入力パケットキューの長さがフロー制限閾値（50%）＋フロー履歴長（256）を上回ることを前提としています。実験ではnet.core.netdev_max_backlogを1000または10000に設定すると良好な性能を示しました。

RFS: 受信フローステアリング¶

RPSはハッシュ値のみに基づいてパケットを振り分け、一般的に均等な負荷分散を提供しますが、アプリケーションのローカル性を考慮しません。これを実現するのがReceive Flow Steering（RFS）です。RFSの目的は、パケットを処理するアプリケーションスレッドが実行されているCPUに処理を振り分け、データキャッシュヒット率を向上させることです。RFSはRPSのメカニズムを同じくして、他のCPUのバックログにパケットを enqueue し、そのCPUを起動します。

RFSでは、パケットのハッシュ値によって直接転送されません。代わりに、ハッシュ値はフローロックアップテーブルのインデックスとして使用されます。このテーブルはフローを処理しているCPUをマッピングしており、フローのハッシュ値（上記RPSセクション参照）をもとにこのテーブルのインデックスが計算されます。各エントリに記録されているCPUは、そのフローを最後に処理したCPUです。エントリに有効なCPUが記録されていない場合、そのエントリにマッピングされたパケットは通常のRPSで振り分けられます。複数のテーブルエントリが同じCPUを指す可能性があります。特に多くのフローと少ないCPUがある場合、1つのアプリケーションスレッドが多くの異なるフローハッシュを持つフローを処理している可能性が高いです。

rps_sock_flow_tableは、フローごとの 望ましい CPUを含むグローバルなフローテーブルです。各テーブル値は、現在ユーザー空間でフローを処理しているCPUのインデックスです。各テーブル値はrecvmsgおよびsendmsg呼び出し（特にinet_recvmsg(), inet_sendmsg(), inet_sendpage(), およびtcp_splice_read()）中に更新されるCPUインデックスです。

スケジューラが、古いCPUで受信待ちのパケットを持つスレッドを新しいCPUに移動させると、パケットが順序を崩して到着する可能性があります。これを防ぐためにRFSは、各フローの未処理パケットを追跡するための2番目のフローテーブルを使用します:rps_dev_flow_tableは、各デバイスのハードウェア受信キューごとに特有のテーブルです。各テーブル値はCPUインデックスとカウンタを保持しており、CPUインデックスはこのフローのパケットがさらにカーネル処理のためにキューイングされるCPUを示します。 現在の 理想的には、カーネルとユーザースペースの処理が同じCPUで行われるため、両テーブルのCPUインデックスは一致します。しかし、スケジューラが最近ユーザースペーススレッドを移動させた場合、カーネルが古いCPUで処理待ちのパケットを保持しているため、この条件は成立しない可能性があります。

rps_dev_flow_tableのカウンタは、このフローのパケットが最後にキューイングされた際の現在CPUのバックログ長を記録します。各バックログキューにはヘッドカウンタがあり、キューイング解除時にインクリメントされます。テールカウンタはヘッドカウンタ＋キュー長として計算されます。つまり、rps_dev_flow[i]のカウンタは、フローiの現在割り当てられたCPUでキューイングされたフローiの最後の要素を示します（もちろん、エントリiはハッシュによって選択され、複数のフローが同じエントリiにハッシュされる可能性があります）。

そして、出力順序のパケットを防ぐためのトリックは、パケット処理のCPUを選択する際（get_rps_cpu()）に、パケットが受信されたキューのrps_sock_flowテーブルとrps_dev_flowテーブルを比較することです。フローの望ましいCPU（rps_sock_flowテーブルに記録）が、現在のCPU（rps_dev_flowテーブルに記録）と一致する場合、パケットはそのCPUのバックログにキューイングされます。一致しない場合、以下のいずれかが真であれば現在のCPUを望ましいCPUに更新します：

  • 現在のCPUのキューイングヘッドカウンタ >= rps_dev_flow[i]に記録されたテールカウンタ値

  • 現在のCPUが未設定（>= nr_cpu_ids）

  • 現在のCPUがオフライン

このチェックの後、パケットは（更新された可能性のある）現在のCPUに送られます。これらのルールは、古いCPUに未処理のパケットが存在しない状態でフローが新しいCPUに移動するようにするため、未処理のパケットが新しいCPUで処理されるパケットよりも後に到着する可能性があるためです。

RFSの設定¶

RFSはkconfigシンボルCONFIG_RPSが有効になっている場合（SMPでデフォルトで有効）にのみ利用可能です。機能は明示的に設定されるまで無効のままです。グローバルフローテーブルのエントリ数は次の通り設定されます：

/proc/sys/net/core/rps_sock_flow_entries

各キューごとのフローテーブルのエントリ数は以下の方法で設定されます:

/sys/class/net/<dev>/queues/rx-<n>/rps_flow_cnt

推奨設定¶

これらは、受信キューでRFSを有効にする前に設定する必要があります。両方の値は2の累乗に丸められます。推奨されるフロー数は、任意の時点で予想されるアクティブな接続数に依存しますが、これはオープンしている接続数よりも大幅に少ない可能性があります。私たちは、中程度の負荷のサーバーでrps_sock_flow_entriesに32768を設定すると比較的うまく動作することを確認しました。

単一キューのデバイスの場合、単一キューのrps_flow_cnt値は通常、rps_sock_flow_entriesと同じ値に設定されます。複数キューのデバイスでは、各キューのrps_flow_cnt値はrps_sock_flow_entries / Nとして設定される可能性があります。ここでNはキューの数です。例えば、rps_sock_flow_entriesが32760に設定され、16の受信キューが設定されている場合、各キューのrps_flow_cnt値は2048に設定される可能性があります。

加速されたRFS¶

加速されたRFSはRFSに対してRSSがRPSに対して持つ役割と同じです。アプリケーションスレッドが各フローのパケットを処理している場所に基づいてフローを制御するソフトウェア状態を活用したハードウェアアクセラレートされたロードバランシングメカニズムです。パケットがデータを処理しているスレッドのローカルなCPUに直接送信されるため、加速されたRFSはRFSよりもパフォーマンスが向上するはずです。ターゲットCPUはアプリケーションが実行されているCPUと同じか、少なくともキャッシュ階層においてアプリケーションスレッドのCPUにローカルなCPUになります。

加速されたRFSを有効にするには、ネットワークスタックがパケットが特定のフローに一致するときに望ましいハードウェアキューを指定するndo_rx_flow_steerドライバ関数を呼び出します。ネットワークスタックは、rps_dev_flow_table内のフロー項目が更新されるたびにこの関数を自動的に呼び出します。ドライバは、そのデバイス固有の方法でNICにパケットを制御するようにプログラミングします。

フローのハードウェアキューはrps_dev_flow_tableに記録されたCPUから導出されます。スタックはNICドライバが維持するCPUとハードウェアキューのマップを参照します。これは/proc/interruptsで表示されるIRQアフィニティーテーブルの自動生成された逆マップです。ドライバはcpu_rmap（「CPUアフィニティ逆マップ」）カーネルライブラリ内の関数を使用してこのマップを埋めます。各CPUに対して、マップ内の対応するキューはキャッシュローカリティにおいて処理CPUに最も近いキューに設定されます。

加速されたRFSの設定¶

加速されたRFSは、カーネルがCONFIG_RFS_ACCELでコンパイルされ、NICデバイスとドライバがサポートを提供している場合にのみ利用可能です。また、ethtoolを通じてntupleフィルタリングが有効になっている必要があります。CPUとキューのマッピングは、ドライバが各受信キューに対して設定したIRQアフィニティから自動的に推論されるため、追加の設定は必要ありません。

推奨設定¶

RFSを使用したい場合、NICがハードウェアアクセラレーションをサポートしている場合は、この技術を有効にする必要があります。

XPS: 送信パケットステアリング¶

送信パケットステアリングは、複数のキューを持つデバイスでパケットを送信する際、どの送信キューを使用するかを知的選択で決定するメカニズムです。これは、CPUとハードウェアキューへのマッピング、または受信キューとハードウェア送信キューへのマッピングの2種類のマップを記録することで実現できます。

  1. XPS（CPUを使用）マップ

このマッピングの目的は、通常、特定のCPUサブセットにキューを専有的に割り当てることです。これらのキューの送信完了処理は、このセット内のCPUで行われます。この選択は2つの利点があります。まず、デバイスキューロックの競合が大幅に減少します（各CPUが独自の送信キューを持つ場合、競合を完全に排除できます）。次に、送信完了時のキャッシュミス率が低下します、特にsk_buff構造体を保持するデータキャッシュラインに対して特に効果的です。

  1. XPS（受信キューを使用）マップ

このマッピングは、管理者が設定した受信キュー（receive queue）のマッピング構成に基づいて送信キュー（transmit queue）を選択するために使用されます。複数の受信キューが複数の送信キューにマッピングされる（many:many）ことも可能ですが、一般的な使用ケースは1:1のマッピングです。これにより、送受信の同じキュー関連付けでパケットを送信できるようになります。これは、CPUを特定のアプリケーションスレッドに割り当てるのが難しい忙しいポーリング（busy polling）マルチスレッドワークロードにおいて、有効です。アプリケーションスレッドはCPUに固定されず、各スレッドが単一のキューで受信したパケットを処理します。受信キュー番号は接続のソケットにキャッシュされます。このモデルでは、関連する受信キューに対応する送信キューでパケットを送信することで、CPUのオーバーヘッドを低く保つことができます。送信完了処理は、アプリケーションがポーリングしている同じキュー関連付けにロックされます。これにより、別のCPUで割り込みをトリガーするオーバーヘッドを回避できます。アプリケーションが忙しいポーリング中にパケットをクリーンアップする際、送信完了処理も同じスレッドコンテキストで処理されるため、レイテンシーが低減されます。

XPSは、送信キューごとにCPU/受信キューのビットマップを設定することで送信キューに設定されます。ネットワークデバイスごとに、CPUから送信キューへの逆マッピング、または受信キューから送信キューへの逆マッピングが計算され維持されます。フローの最初のパケットを送信する際、get_xps_queue()関数が呼び出されてキューを選択します。この関数は、ソケット接続の受信キューIDを受信キューから送信キューの検索テーブルで一致させます。代替として、この関数は実行中のCPUのIDをCPUからキューの検索テーブルのキーとして使用することもできます。IDが単一のキューと一致する場合、そのキューが送信に使用されます。複数のキューが一致する場合、フローハッシュを用いてセット内のインデックスを計算してキューを選択します。受信キュー（複数）のマッピングに基づいて送信キューを選択する際、送信デバイスは受信デバイスと検証されません。これはデータパスでの高コストな検索操作を必要とするためです。

特定のフローを送信するために選択されたキューは、そのフロー（例：TCP接続）に対応するソケット構造体に保存されます。この送信キューは、その後のフローでのパケット送信時に無秩序（ooo）パケットを防ぐために使用されます。この選択は、フロー内のすべてのパケットに対してget_xps_queues()の呼び出しコストを均等に分散します。無秩序パケットを回避するため、フローのキューは、フロー内のパケットがskb->ooo_okayが設定されている場合にのみ変更可能です。このフラグは、フローに未処理のパケットが存在しないことを示しており、送信キューを変更しても無秩序パケットが発生するリスクがありません。トランスポート層はooo_okayを適切に設定する責任があります。たとえば、TCPは接続のすべてのデータが確認されたときにこのフラグを設定します。

XPSの設定¶

XPSはkconfigシンボルCONFIG_XPSが有効になっている場合（SMPではデフォルトで有効）にのみ利用可能です。コンパイルされた場合、デバイス初期化時にXPSがどのように設定されるかはドライバ依存です。CPU/受信キューと送信キューのマッピングはsysfsを使用して確認および設定可能です：

CPUマップに基づく選択:

/sys/class/net/<dev>/queues/tx-<n>/xps_cpus

受信キューのマップに基づく選択:

/sys/class/net/<dev>/queues/tx-<n>/xps_rxqs

推奨設定¶

単一の送信キューを持つネットワークデバイスでは、XPS設定に影響されません。これは選択肢がないためです。複数キューのシステムでは、XPSを設定して各CPUが1つのキューにマッピングされるようにすることが望ましいです。システム内のCPU数と同じ数のキューがある場合、各キューが1つのCPUにマッピングされ、競合が発生しない排他的なペアリングが可能です。キューがCPU数より少ない場合、そのキューを共有する最適なCPUは、そのキューの送信完了処理（送信割込み）を行うCPUとキャッシュを共有するCPUと考えられます。

受信キューに基づく送信キュー選択では、XPSが受信キューを送信キューにマッピングするように明示的に設定する必要があります。ユーザー設定の受信キューマップが適用されない場合、CPUマップに基づいて送信キューが選択されます。

各TXキューごとのレート制限¶

ハードウェアで実装されたレート制限メカニズムで、現在はMbps値を設定することでmax-rate属性をサポートしています：

/sys/class/net/<dev>/queues/tx-<n>/tx_maxrate

ゼロの値は無効を意味し、これはデフォルト値です。

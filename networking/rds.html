== RDS ===

概要¶

この README は RDS の方法と理由についての背景情報を提供し、コードを理解するのを助けることを目指しています。

さらに、RDS の起源についてのこのメールを参照してください: http://oss.oracle.com/pipermail/rds-devel/2007-November/000228.html

RDSアーキテクチャ¶

RDS は、クラスター内の任意の 2 つのノード間で単一の信頼性のある接続を使用して、信頼性の高い順序を保つデータグラムの配信を提供します。これにより、アプリケーションはクラスター内の他のプロセスと通信するための単一のソケットを使用できます。クラスターに N 個のプロセスがある場合、N 個のソケットが必要ですが、TCP などの接続志向のソケットトランスポートを使用する場合では N*N 個のソケットが必要になります。

RDS は Infiniband に特化したものではなく、さまざまなトランスポートをサポートするように設計されています。現在の実装では RDS over TCP および IB をサポートしていました。

アプリケーションの観点からの RDS の高レベルなセマンティクスは

  • アドレス指定

    RDS は IPv4 アドレスと 16 ビットのポート番号を使用して接続の終端ポイントを識別します。カーネルとユーザースペース間でアドレスをやり取りするすべてのソケット操作は一般的に struct sockaddr_in を使用します。

    IPv4 アドレスが使用されているということは、下層のトランスポートが IP ベースである必要があるとは限りません。実際、RDS over IB は信頼性のある IB 接続を使用しており、IP アドレスは遠隔ノードの GID を検索するためにのみ使用されます（指定された IP に対して ARPing によって）。

    ポート空間は UDP、TCP または他のプロトコルとは完全に独立しています。

  • ソケットインターフェース

    RDS ソケットは 主に BSD ソケットと同様の動作をします。次のセクションでは詳細を説明します。いずれにせよ、すべての I/O は標準の BSD ソケット API を通じて行われます。ゼロコピーのサポートなどの拡張機能は制御メッセージを通じて実装され、他の拡張機能は getsockopt/setsockopt 呼び出しを使用します。

    データを送信または受信する前にソケットをバインドする必要があります。これは、バインディングによってトランスポートが選択され、ソケットに接続されるためです。バインド後はトランスポートの割り当ては変更されません。RDS は IP が動くのを許容します（例：アクティブアクティブの HA シナリオ）、ただしアドレスが異なるトランスポートに移動しない限りです。

  • sysctls

    RDS は /proc/sys/net/rds に複数の sysctl をサポートしています

ソケットインターフェース¶

AF_RDS, PF_RDS, SOL_RDS

AF_RDS および PF_RDS は socket(2) を使用して RDS ソケットを作成するためのドメインタイプです。SOL_RDS は setsockopt(2) および getsockopt(2) で RDS 特有のソケットオプションを操作するためのソケットレベルです。

fd = socket(PF_RDS, SOCK_SEQPACKET, 0);

これは新しい、バインドされていない RDS ソケットを作成します。

setsockopt(SOL_SOCKET): 送受信バッファサイズ

RDSは送信バッファサイズと受信バッファサイズのソケットオプションを尊重します。ソケットにキューに蓄積できる最大バイト数はSO_SNDSIZEに制限されます。sendmsgが呼び出されるとメッセージがキューに追加され、リモートシステムが到達を確認した時点でキューから削除されます。

SO_RCVSIZEオプションは最大受信キュー長を制御します。これはハード制限ではなくソフト制限です。RDSはキュー長が制限を超えたとしても、受信メッセージを引き続き受け入れてキューに蓄積します。ただし、ポートを「混雑中」とマークし、混雑状態の更新を送信源ノードに通知します。送信源ノードはこの混雑ポートへの送信を制限する必要があります。

bind(fd, &sockaddr_in, …)

この関数は、ソケットをローカルIPアドレスとポート、およびトランスポートにバインドします。トランスポートがすでにSO_RDS_TRANSPORTオプションで選択されていない場合に有効です。

sendmsg(fd, …)

指定された宛先にメッセージを送信します。コアが信頼性のある接続が確立されていなければ、自動的にその接続を確立します。

SO_SNDSIZEを超えるメッセージ送信試行は-EMSGSIZEで失敗します。

SO_SNDSIZEの閾値を超える総キューのバイト数になるメッセージ送信試行はEAGAINで失敗します。

「混雑中」とマークされた宛先へのメッセージ送信試行はENOBUFSで失敗します。

recvmsg(fd, …)

このソケットにキューされているメッセージを受信します。受信キューの計測が調整され、キュー長がSO_SNDSIZEを下回るとポートが「混雑中」から解除され、すべてのピアに混雑状態の更新が送信されます。

アプリケーションはRDSカーネルモジュールに制御メッセージを通じて通知を受けることができます（例：混雑状態の更新が到達したとき、またはRDMA操作が完了したときなど）。これらの通知はstruct msghdrのmsg.msg_controlバッファを通じて受信され、メッセージの形式はmanpagesで説明されています。

poll(fd)

RDSはアプリケーションが非同期I/Oを実装できるpollインターフェースをサポートしています。

POLLINの処理は比較的簡単です。ソケットに受信メッセージがキューイングされているか、または待機中の通知がある場合、POLLINを信号として出力します。

POLLOUTの処理はやや複雑です。送信先が任意の宛先であるため、RDSは送信キューに空きがある限り（つまり、キューイングされたバイト数が送信バッファサイズを下回る限り）常にPOLLOUTを信号として出力します。

ただし、カーネルは congested（混雑している）とマークされた宛先へのメッセージを受け入れることを拒否します。この場合、poll に依存して動作を判断すると永遠にループしてしまいます。これは単純な問題ではありませんが、アプリケーションは congestion notifications（混雑通知）を使用し、sendmsg が返す ENOBUFS エラーを確認することでこれを処理できます。

setsockopt(SOL_RDS, RDS_CANCEL_SENT_TO, &sockaddr_in)

これにより、アプリケーションはこのソケットに特定の宛先にキューイングされているすべてのメッセージを破棄できます。

アプリケーションがタイムアウトを検出した場合、未完了のメッセージをキャンセルできます。例えば、メッセージを送信したが、リモートホストが到達不可だった場合、RDS は永遠に試行し続けます。アプリケーションがこれに価値を見出さない場合、操作をキャンセルします。この場合、RDS_CANCEL_SENT_TO を使用して待機中のメッセージをすべて破棄します。

setsockopt(fd, SOL_RDS, SO_RDS_TRANSPORT, (int *)&transport ..), getsockopt(fd, SOL_RDS, SO_RDS_TRANSPORT, (int *)&transport ..)

ソケットに使用する下位の輸送プロトコルを定義する整数を設定または取得します。設定する際には、整数引数は RDS_TRANS_TCP または RDS_TRANS_IB のいずれかでなければなりません。取得する際には、未バインドのソケットでは RDS_TRANS_NONE が返されます。このソケットオプションは、bind(2) システムコールでバインドする前に一度だけ設定可能です。すでに SO_RDS_TRANSPORT で明示的に設定済み（SO_RDS_TRANSPORT で設定）または暗黙に設定済み（bind(2) で設定）されている場合、EOPNOTSUPP エラーが返されます。SO_RDS_TRANSPORT を RDS_TRANS_NONE に設定する試みは常に EINVAL エラーを返します。

RDSプロトコル¶

メッセージヘッダー

メッセージヘッダーは 'struct rds_header'（rds.h を参照）です：

フィールド：

h_sequence:

パケットごとのシーケンス番号

h_ack:

最後に受信したパケットの確認応答（piggybacked acknowledgment）

h_len:

ヘッダーを除くデータの長さ

h_sport:

送信元ポート

h_dport:

宛先ポート

h_flags:

以下が可能です：

CONG_BITMAP

これは混雑状態のビットマップです

ACK_REQUIRED

受信側がこのパケットを確認する必要があります

RETRANSMITTED

このパケットは以前に送信済みです
h_credit:

接続の他端に送信可能なクレジットがさらにあります（つまり、送信可能領域がさらにあります）を示します

h_padding[4]:

未使用、今後の拡張用

h_csum:

ヘッダーのチェックサム

h_exthdr:

オプションでデータをここに渡せます。現在は RDMA 関連情報を渡すために使用されています。

ACK および再送処理

信頼性の高いIB接続があるにもかかわらず、受信したメッセージの確認応答（ack）を必要としないと考えられるかもしれません。問題は、IBハードウェアがメッセージをメモリにDMA（Direct Memory Access）してからではなく、DMAする前にもう一度ackメッセージを生成してしまうことです。これは、HCA（Host Channel Adapter）がack送信後、メッセージがDMAされ処理される前に無効化された場合に、メッセージが失われる可能性を生じさせます。これは、別のHCAがフェールオーバー用に利用可能である場合にのみ、潜在的な問題となります。

ackを即座に送信することで、送信側は送信メッセージを送信キューから迅速に解放できますが、ackによるトラフィックが過剰になる可能性があります。RDSは送信データパケットにackを乗せて送信します。ackのみのパケットは、同時に飛ばすことを制限し、送信側が送信バッファが満たされるタイミングでackを要求するようにすることで削減されます。すべての再送信もackされます。

フロー制御

RDSのIBトランスポートは、相手側の受信バッファにデータを追加できるスペースがあることを確認するため、クレジットベースのメカニズムを使用します。これにより、接続におけるハードウェアの再試行は不要になります。

混雑

受信ソケットの受信キューに待機しているメッセージは、ソケットのSO_RCVBUFオプション値に応じてカウントされます。カウントされるのはメッセージのペイロードバイトのみです。キューに待機しているバイト数がrcvbufに等しいかそれ以上になると、ソケットが混雑しているとみなされます。このソケットのアドレスに対して行われるすべての送信は、ブロックまたは-EWOULDBLOCKを返す必要があります。

アプリケーションはこの状況が非常にまれに発生するように適切にチューニングされることが期待されます。この「バックプレッシャー」に遭遇するアプリケーションは、バグとみなされます。

各ノードがバインドされたアドレスのどのポートが混雑しているかを示すビットマップを保持することで実装されます。ビットマップが変更されるたびに、その変更を、ビットマップが変更されたローカルアドレスに終端するすべての接続を通じて送信します。

ビットマップは接続が起動されるときに割り当てられます。これにより、割り込み処理パスでの割り当てを回避し、ソケットに待機中のスレッドをキューに溜めることを防ぎます。高密度のビットマップは、どのポートに送信するかを確認するための非常に低コストなビットテストを送信側が行うことで、ビットマップの変更ごとに効率的に全体を送信できます。これは、ポートごとの混雑状態をより細かく通信するよりもはるかに実装が簡単です。

RDSトランスポートレイヤー¶

上記のように、RDSはIBに特化した技術ではありません。そのコードは一般的なRDSレイヤーとトランスポートレイヤーに分かれています。

一般的なレイヤーはソケットAPI、混雑処理、ループバック、統計情報、ユーザーメモリのピンニング、接続状態マシンを処理します。

トランスポート層はトランスポートの詳細を処理します。たとえばIBトランスポートは、すべてのキュー・ペア、ワーク・リクエスト、CMイベントハンドラ、およびその他のInfinibandの詳細を処理します。

RDSカーネル構造体¶

struct rds_message

「rds_outgoing」として知られる一般的なRDS層は、送信するデータをコピーし、ソケットAPIに基づいてヘッダーフィールドを必要に応じて設定します。これにより、個々の接続にキューイングされ、接続のトランスポートによって送信されます。

struct rds_incoming

受信データをトランスポートから一般的なコードに渡し、ソケットが起動される間、一般的なコードによってキューイングされるための一般的な構造体です。その後、トランスポートコードに再び渡され、実際のユーザーへのコピー処理が行われます。

struct rds_socket

各ソケットに関する情報

struct rds_connection

各接続に関する情報

struct rds_transport

トランスポート固有の関数へのポインタ

struct rds_statistics

トランスポート固有でない統計情報

struct rds_cong_map

raw congestion bitmapをラップし、rbnode、waitqなどを持つ

接続管理¶

接続はUP、DOWN、CONNECTING、DISCONNECTING、およびERRORの状態を持つことができます。

RDSソケットが初めてノードにデータを送信しようとする際、接続が割り当てられ接続されます。その後、接続は永遠に維持されます。トランスポートエラーが発生した場合、接続は切断され再び確立されます。

パケットがキューイングされている間に接続を切断すると、キューイングされているか部分的に送信されたデータグラムが再送されます。

送信経路¶

rds_sendmsg()

  • インカムデータから構築されたstruct rds_message

  • CMSGが解析される（例: RDMA操作）

  • 接続がまだない場合はトランスポート接続が割り当てられ接続される

  • rds_messageが送信キューに配置される

  • 送信ワーカーが起動される

rds_send_worker()

  • キューが空になるまでrds_send_xmit()を呼び出す

rds_send_xmit()

  • コンゴステーションマップが待機している場合、それを送信する

  • ACK_REQUIREDを設定する可能性がある

  • トランスポートに非RDMAまたはRDMAメッセージ（RDMA操作は再送されない）を送信させる

rds_ib_xmit()

  • 送信リングからワーク・リクエストを割り当てる

  • 新しい送信クレジットを相手に送信する（h_credits）

  • rds_messageのsgリストをマッピングする

  • ACKをペイロードに添付する

  • ワーク・リクエストを埋める

  • 接続のキュー・ペアに送信をポストする

受信経路¶

rds_ib_recv_cq_comp_handler()

  • 書き込み完了を確認する

  • 受信バッファをデバイスからアンマッピングする

  • エラーがなければ、rds_ib_process_recv()を呼び出す

  • recvリングを補充する

rds_ib_process_recv()

  • ヘッダーチェックサムを検証する

  • 新規データグラムの開始であれば、ヘッダーをrds_ib_incoming構造体にコピーする

  • ibincのfraglistに追加する

  • 完了したデータグラムの場合:

    • データグラムがcong更新だった場合、congマップを更新する

    • それ以外の場合、rds_recv_incoming()を呼び出す

    • ACKが必要かどうかを記録する

rds_recv_incoming()

  • 重複パケットを破棄する

  • ピング応答を送信する

  • このデータグラムに関連するソケットを検索する

  • ソケットキューに追加する

  • ソケットを起動する

  • コンゴージョン計算を行う

rds_recvmsg

  • データをユーザーのiovecにコピーする

  • CMSGを処理する

  • アプリケーションに返す

マルチパスRDS (mprds)¶

Mprdsは複数経路をサポートしたRDSであり、主にRDS-over-TCPを想定している（ただし、他のトランスポートにも拡張可能）。古典的なRDS-over-TCPの実装は、2つのエンドポイント（エンドポイント＝[IPアドレス、ポート]）間の単一のTCPソケットを介して複数のPF_RDSソケットをデマルチプレックスする形態である。この方法には、複数のRDSフローを単一のTCPフローで処理するため、（a）単一フローの帯域幅に上限が設けられ、（b）すべてのRDSソケットでヘッド・オブ・ラインブロッキングが発生するという制限がある。

固定された小パケットサイズ（MTU）で、より高いスループットを達成するには、各rds/tcp接続に対して複数のTCP/IPフローを用いることが有効である。つまり、複数経路RDS（multipathed RDS: mprds）である。このようなTCP/IPフローは、rds/tcp接続のそれぞれの経路を構成する。RDSソケットは、あるハッシュ（例：ローカルアドレスとRDSポート番号のハッシュ）に基づいて経路にアタッチされ、そのRDSソケットのパケットは、アタッチされた経路を介してTCPを用いて送信され、その経路でRDSデータグラムをセグメント化・再構成する。

複数経路RDSは、struct rds_connectionを共通部分と、各経路用のstruct rds_conn_pathに分割して実装される。すべてのI/Oワーキングキューおよび再接続スレッドはrds_conn_pathから駆動される。複数経路をサポート可能なトランスポート（例：TCP）は、各rds_conn_pathに対してTCPソケットを設定し、これはトランスポートがtransport private cp_transport_dataポインタを介して管理する。

トランスポートは、rdsコアモジュールへの登録時にt_mp_capableビットを設定して複数経路をサポート可能であることを宣言する。トランスポートが複数経路をサポート可能な場合、rds_sendmsg()は複数の経路で出力トラフィックをハッシュする。出力ハッシュは、PF_RDSソケットがバインドされているローカルアドレスとポートに基づいて計算される。

さらに、トランスポートがMP対応である場合でも、ピアリングするノードがmprdsをサポートしていない、またはサポートするパス数が異なる場合があります。その結果、ピアリングノードは接続に使用するパス数を合意する必要があります。これは、最初のデータパケット送信前にコントロールパケットの交換によって行われます。トランスポートがマルチパス対応の場合、rds_sendmsg()での送出ハッシュ完了前にコントロールパケットの交換が完了している必要があります。

コントロールパケットはRDS pingパケット（つまり、rds宛てポート0へのパケット）であり、pingパケットにはrds拡張ヘッダーオプションとしてRDS_EXTHDR_NPATHSタイプ、長さ2バイト、値が送信元がサポートするパス数を示す必要があります。"probe" pingパケットは、予約されたポートRDS_FLAG_PROBE_PORT（<linux/rds.h>参照）から送信されます。RDS_FLAG_PROBE_PORTからのpingを受信した受信者は、即座に送信元のパス数と受信元のパス数の最小値を計算できます。mprds対応の受信元に対するprobe-pingへの応答として送信されるpongには、受信元のnpathsが含まれるべきです。

受信元がmprds対応でない場合、pingの拡張ヘッダーは無視されます。この場合、pongには拡張ヘッダーが含まれず、probe-pingを送信した送信者はデフォルトで単一パスのmprdsを使用します。

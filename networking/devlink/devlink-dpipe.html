Devlink DPIPE¶

背景¶

ハードウェアオフローディングプロセスを実行している間、多くのハードウェアの詳細は提示できません。これらの詳細はデバッグに有用で、 devlink-dpipe オフローディングプロセスの可視性を標準化して提供します。

たとえば、Linuxカーネルで使用されるルーティングのlongest prefix match (LPM) アルゴリズムは、ハードウェアの実装と異なる場合があります。パイプラインデバッグAPI (DPIPE) は、ユーザーがASICのパイプラインを一般的な方法で可視化できるようにするためのものです。

ハードウェアオフローディングプロセスは、ユーザーがハードウェアとソフトウェアの実装を区別できないようにする方法で行われるべきです。このプロセスでは、ハードウェアの詳細は無視されます。しかし、実際にはこれらの詳細には多くの意味があり、標準的な方法で公開されるべきです。

全体のネットワーキングスタックの制御パスをスイッチASICにオフロードしたい場合、この問題はさらに複雑になります。ハードウェアとソフトウェアモデルの違いにより、一部のプロセスは正しく表現できません。

一つの例は、カーネルのLPMアルゴリズムで、多くの場合ハードウェアの実装とは大きく異なります。設定APIは同じですが、フォワード情報ベース (FIB) がハードウェアのレベルパス圧縮木 (LPC-trie) と一致するとは限りません。

多くの場合、カーネルのダンプのみに基づいてシステムの失敗を分析しても不十分です。このデータを裏面のハードウェアに関する補完的な情報と組み合わせることで、デバッグが容易になります。さらに、パフォーマンス問題のデバッグにも情報が役立ちます。

概要¶

以下の devlink-dpipe インターフェースはこのギャップを埋めます。ハードウェアのパイプラインは、マッチ/アクションテーブルのグラフとしてモデル化されます。各テーブルは特定のハードウェアブロックを表します。このモデルは新しいものではなく、最初にP4言語で使用されました。

伝統的にハードウェアの設定の代替モデルとして使用されてきましたが、 devlink-dpipe インターフェースは、可視性の目的で標準的な補完ツールとしてこれを使用します。システムのビューは devlink-dpipe 標準的な設定ツールによって行われた変更に応じて変化する必要があります。

たとえば、アクセス制御リスト（ACL）をテナリーコンテンツアドレス可能なメモリ（TCAM）を使用して実装することは一般的です。TCAMメモリはTCAM領域に分割できます。複雑なTCフィルタは、優先度や検索キーが異なる複数のルールを持つことができます。一方、ハードウェアTCAM領域は予め定義された検索キーを持っています。TCフィルタルールをTCAMエンジンでオフロードすると、複数のTCAM領域がチェーン状に接続される可能性があり（これはデータパス遅延に影響を与える可能性があります）。新しいTCフィルタが出現した場合、その領域を記述する新しいテーブルを作成する必要があります。

モデル¶

以下の DPIPE モデルはいくつかのオブジェクトを導入しています：

  • ヘッダー

  • テーブル

  • エントリ

A header パケット形式を説明し、パケット内のフィールドの名前を提供します。A table ハードウェアブロックを説明します。An entry 特定のテーブルの実際の内容を説明します。

ハードウェアパイプラインはポート固有ではなく、むしろASIC全体を記述しています。そのため、 devlink インフラストラクチャ。

ドライバは実行時にテーブルを登録および解除できるようにし、動的動作をサポートする必要があります。この動的動作は、TCAM領域などのハードウェアブロックを動的に割り当てたり解放したりできる場合に必須です。

devlink-dpipe 設定は一般的には意図されていません。例外は特定のテーブルのハードウェアカウントです。

以下のコマンドを使用して、ユーザー空間から dpipe オブジェクトを取得します：

  • table_get: テーブルの説明を取得します。

  • headers_get: デバイスがサポートするヘッダーを取得します。

  • entries_get: テーブルの現在のエントリを取得します。

  • counters_set: テーブルのカウンターを有効または無効にします。

テーブル¶

ドライバは各テーブルに対して以下の操作を実装する必要があります：

  • matches_dump: サポートされているマッチをダンプします。

  • actions_dump: サポートされているアクションをダンプします。

  • entries_dump: テーブルの実際の内容をダンプします。

  • counters_set_update: カウンターを有効または無効にしたハードウェアと同期します。

ヘッダー/フィールド¶

P4のヘッダーとフィールドと同様に、ヘッダーとフィールドはテーブルの動作を記述するために使用されます。標準プロトコルヘッダーとASICメタデータには少しだけ違いがあります。プロトコルヘッダーは devlink コアAPIで宣言する必要があります。一方、ASICメタデータはドライバ固有であり、ドライバで定義する必要があります。さらに、各ドライバ固有のdevlinkドキュメンテーションファイルは、ドライバ固有の dpipe ヘッダーをドキュメント化する必要があります。ヘッダーとフィールドは列挙によって識別されます。

さらに高い可視性を提供するために、一部のASICメタデータフィールドはカーネルオブジェクトにマッピングされる場合があります。たとえば、内部ルータインターフェースインデックスはnetデバイスifindexに直接マッピングできます。異なる仮想ルーティングおよびフォワーディング（VRF）テーブルで使用されるFIBテーブルインデックスは、内部ルーティングテーブルインデックスにマッピングできます。

マッチ¶

マッチはハードウェア操作に近い原始的な形で保持されます。LPMなどのマッチタイプは、このプロセスを詳細に記述したいという意図によりサポートされません。マッチの例:

  • field_exact: 特定のフィールドに対する正確な一致。

  • field_exact_mask: マスキング後の特定のフィールドに対する正確な一致。

  • field_range: 特定の範囲に対する一致。

ヘッダとフィールドのIDを指定することで特定のフィールドを識別し、複数の同じタイプのヘッダをパケット（トンネリング）内で区別するためにはヘッダインデックスを指定する必要があります。

アクション¶

マッチと同様に、アクションもハードウェア操作に近い原始的な形で保持されます。例えば:

  • field_modify: フィールド値を変更する。

  • field_inc: フィールド値をインクリメントする。

  • push_header: ヘッダを追加する。

  • pop_header: ヘッダを削除する。

エントリ¶

特定のテーブルのエントリは必要に応じてダンプ（抽出）できます。各エントリはインデックスで識別され、マッチ/アクション値と特定のカウンターによってプロパティが記述されます。テーブルの内容をダンプすることで、テーブル間の相互作用を解決できます。

抽象化例¶

以下はMellanox Spectrum ASICのL3部分の抽象化モデルの例です。ブロックはパイプライン内で出現する順序で記述されています。以下の例でのテーブルサイズは実際のハードウェアサイズではなく、説明目的で示したものです。

LPM¶

LPMアルゴリズムはハッシュテーブルのリストとして実装できます。各ハッシュテーブルは同じプレフィックス長を持つルートを含みます。リストのルートは/32であり、ヒットがなければハードウェアは次のハッシュテーブルに進みます。検索の深さはデータパスのレイテンシーに影響を与えます。

ヒットした場合、エントリにはパイプラインの次のステージに関する情報が含まれており、これによりMACアドレスが解決されます。次のステージは、直接接続されたルート用のローカルホストテーブルか、次のホップ用の隣接テーブルのいずれかです。 meta.lpm_prefix フィールドは2つのLPMテーブルを接続するために使用されます。

table lpm_prefix_16 {
  size: 4096,
  counters_enabled: true,
  match: { meta.vr_id: exact,
           ipv4.dst_addr: exact_mask,
           ipv6.dst_addr: exact_mask,
           meta.lpm_prefix: exact },
  action: { meta.adj_index: set,
            meta.adj_group_size: set,
            meta.rif_port: set,
            meta.lpm_prefix: set },
}

ローカルホスト¶

ローカルルートの場合、LPM検索はすでにエグジットルーターインターフェース（RIF）を解決しますが、正確なMACアドレスはまだ不明です。ローカルホストテーブルは、出力インターフェースIDと宛先IPアドレスをキーとして組み合わせたハッシュテーブルであり、結果としてMACアドレスが得られます。

table local_host {
  size: 4096,
  counters_enabled: true,
  match: { meta.rif_port: exact,
           ipv4.dst_addr: exact},
  action: { ethernet.daddr: set }
}

隣接性¶

リモートルートの場合、このテーブルがECMP（等コスト多重経路）を実行します。LPM検索結果はECMPグループのサイズとインデックスとして、このテーブルのグローバルオフセットになります。同時にパケットのハッシュが生成されます。ECMPグループサイズとパケットのハッシュに基づいてローカルオフセットが生成され、複数のLPMエントリが同じ隣接グループを指すことができます。

table adjacency {
  size: 4096,
  counters_enabled: true,
  match: { meta.adj_index: exact,
           meta.adj_group_size: exact,
           meta.packet_hash_index: exact },
  action: { ethernet.daddr: set,
            meta.erif: set }
}

ERIF¶

以前のテーブルによってエグジットRIFおよび宛先MACアドレスが解決されている場合、このテーブルではTTLの減少やMTUの確認などの複数の操作を行います。その後、パケットの種別（ブロードキャスト、ユニキャスト、マルチキャスト）に基づいて転送/ドロップの決定が行われ、ポートL3統計が更新されます。

table erif {
  size: 800,
  counters_enabled: true,
  match: { meta.rif_port: exact,
           meta.is_l3_unicast: exact,
           meta.is_l3_broadcast: exact,
           meta.is_l3_multicast, exact },
  action: { meta.l3_drop: set,
            meta.l3_forward: set }
}

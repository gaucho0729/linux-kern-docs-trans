XFRM¶

同期パッチの作業は、Krisztian <hidden> および他者による初期パッチと、Jamal <hidden> による追加パッチに基づいています。hidden@balabit.hu> および他者による追加パッチです。hadi@cyberus.ca>.

同期の最終目標は、属性を挿入しイベントを生成できるようにすることで、SAを他のマシンに安全に移動できるようにすることです。このアイデアは、フェールオーバーの目的でSAを他のマシンに移動する際、そのマシンがSAにアクセスできる場合に正確に処理できるようにすることです。

すでにSAの追加/削除/更新イベントを生成する機能があります。これらのパッチは同期機能を追加し、正確なライフタイムバイト（SAの適切な減衰を確保）とリプレイカウンタを追加して、フェールオーバー時の最小限の損失でリプレイ攻撃を回避します。これにより、バックアップがアクティブなメンバーと同様に最新に保たれます。

上記の項目はパケットごとに変化するため、多くのイベントが生成される可能性があります。そのため、イベントの生成を制限する nagle アルゴリズムに似たアルゴリズムを追加します。つまり、リプレイシーケンスのしきい値が達成されたか、または10秒が経過した場合に通知するしきい値を設定します。これらのしきい値は、sysctl でシステム全体に設定するか、SAごとに更新できます。

同期が必要な項目は次の通りです: - ライフタイムバイトカウンタ（注意: フェールオーバーマシンが事前にわかっていると、時間制限は重要ではありません。なぜなら、時間カウントダウンの減衰はパケット到着に依存しないからです）- 両方向のリプレイシーケンス

1) メッセージ構造¶

nlmsghdr:aevent_id:optional-TLVs.

netlinkメッセージのタイプは次の通りです:

XFRM_MSG_NEWAE および XFRM_MSG_GETAE。

XFRM_MSG_GETAE は TLV を持ちません。

XFRM_MSG_NEWAE は少なくとも2つの TLV を持ちます（以下で詳しく説明します）。

aevent_id 構造は次の通りです:

struct xfrm_aevent_id {
          struct xfrm_usersa_id           sa_id;
          xfrm_address_t                  saddr;
          __u32                           flags;
          __u32                           reqid;
};

一意な SA は xfrm_usersa_id、reqid および saddr の組み合わせで識別されます。

フラグはさまざまな情報を示すために使用されます。可能なフラグは次の通りです:

XFRM_AE_RTHR=1, /* replay threshold*/
XFRM_AE_RVAL=2, /* replay value */
XFRM_AE_LVAL=4, /* lifetime value */
XFRM_AE_ETHR=8, /* expiry timer threshold */
XFRM_AE_CR=16, /* Event cause is replay update */
XFRM_AE_CE=32, /* Event cause is timer expiry */
XFRM_AE_CU=64, /* Event cause is policy update */

これらのフラグの使用方法は、メッセージの方向（カーネル<->ユーザー）および原因（設定、クエリ、イベント）に依存します。これは以下のさまざまなメッセージで説明されます。

netlink で pid は適切に設定され、方向を認識します（カーネルへの 0 と、カーネルからユーザー空間への pid = イベントを作成したプロセスID）

プログラムは、これらのイベントを通知するためにマルチキャストグループ XFRMNLGRP_AEVENTS にサブスクライブする必要があります。

2) TLVは異なるパラメータを反映しています:¶

  1. バイト値 (XFRMA_LTIME_VAL)

この TLV は、最後のイベント以来のバイト寿命の現在/実行中のカウンタを保持します。

b) リプレイ値 (XFRMA_REPLAY_VAL)

このTLVは、最後のイベント以降の再送序列の現在/実行中のカウンターを保持しています。

c) 再送閾値 (XFRMA_REPLAY_THRESH)

このTLVは、カーネルが再送序列が超過した際にイベントをトリガーするための閾値を保持しています。

  1. 有効期限タイマ (XFRMA_ETIMER_THRESH)

これは、イベントのレート制限に使用されるナゲル値としてミリ秒単位のタイマ値です。

3) パラメータのデフォルト設定:¶

デフォルトではこれらのイベントはオフにされますが、マルチキャストグループXFRMNLGRP_AEVENTSに少なくとも1つのリスナーが登録されている場合を除き、変更しないようにするため、これらのパラメータに対するデフォルトの閾値も提供しています。

SAをインストールするプログラムでは2つの閾値を指定する必要がありますが、既存のアプリケーション（例: racoon）を変更しないようにするため、指定されていない場合でもこれらのパラメータに対するデフォルトの閾値を提供しています。

2つのsysctl/procエントリは以下の通りです：

a) /proc/sys/net/core/sysctl_xfrm_aevent_etime は、XFRMA_ETIMER_THRESHのデフォルト値を100ms単位の時間のインクリメントで提供します。デフォルト値は10（1秒）です。

b) /proc/sys/net/core/sysctl_xfrm_aevent_rseqth は、XFRMA_REPLAY_THRESHパラメータのデフォルト値をパケット数のインクリメントで提供します。デフォット値は2パケットです。

4) メッセージタイプ¶

  1. XFRM_MSG_GETAEはユーザーからカーネルへ送信されるメッセージです。XFRM_MSG_GETAEはTLVを保持しません。

応答はXFRM_MSG_NEWAE形式で行われ、これはXFRM_MSG_GETAEが照会した内容に基づいています。

応答には常にXFRMA_LTIME_VALとXFRMA_REPLAY_VALのTLVが含まれます。* XFRM_AE_RTHRフラグが設定されている場合、XFRMA_REPLAY_THRESHも取得されます * XFRM_AE_ETHRフラグが設定されている場合、XFRMA_ETIMER_THRESHも取得されます

  1. XFRM_MSG_NEWAEはユーザー空間から設定するか、カーネルがイベントをアナウンスまたはXFRM_MSG_GETAEへの応答として送信します。

  1. ユーザーからカーネルへ、特定のSAを設定するためのメッセージです。

適切なTLVを指定することで、任意の値や閾値パラメータを更新できます。

ユーザー空間へ応答を送信し、成功または失敗を示します。

成功した場合、iii)に記載した通り、リスナーに対してXFRM_MSG_NEWAEイベントも送信されます。

  1. XFRM_MSG_GETAEへの応答としてカーネルからユーザーへ送信される方向です。

応答には常にXFRMA_LTIME_VALとXFRMA_REPLAY_VALのTLVが含まれます。

XFRM_MSG_GETAEメッセージで明示的に要求された場合にのみ、閾値TLVが含まれます。

  1. XFRM_MSG_NEWAEでSAの値や閾値を設定した場合（#iに記載の通り）にイベントとしてユーザーに報告します。その場合、XFRM_AE_CUフラグが設定され、ユーザーに変更が更新によって行われたことを通知します。メッセージには常にXFRMA_LTIME_VALとXFRMA_REPLAY_VALのTLVが含まれます。

  2. カーネルからユーザーへの報告が行われ、リプレイしきい値またはタイムアウトが超過した場合のイベントを報告します。

このような場合、XFRM_AE_CR（リプレイ超過）またはXFRM_AE_CE（タイムアウトが発生）が設定され、ユーザーに発生した状況を通知します。この2つのフラグは排他的です。メッセージには常にXFRMA_LTIME_VALおよびXFRMA_REPLAY_VAL TLVが含まれます。

閾値設定の例外¶

SAがトラフィックの爆発的な増加によって攻撃され、タイマースレッドが発生する間にパケットが見られない期間がある場合、以下の異常な挙動が観測されます：タイマースレッドの終了後に到達する最初のパケットはタイムアウトイベントをトリガーします。つまり、タイムアウト期間が経過するのを待ったり、パケットしきい値が達成されるのを待つことなく、即座にタイムアウトイベントが発生します。これは簡潔さと効率性のためです。

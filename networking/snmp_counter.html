SNMPカウンター¶

このドキュメントではSNMPカウンターの意味を説明します。

一般的なIPv4カウンタ¶

レイヤー4のパケットおよびICMPパケットはこれらのカウンターを変更しますが、レイヤー2のパケット（STPなど）やARPパケットはこれらのカウンターを変更しません。

  • IpInReceives

定義は RFC1213 ipInReceives

IPレイヤーで受信したパケット数を示します。ip_rcv関数の開始時に増加し、常にIpExtInOctetsと同時に更新されます。パケットが後でドロップされた場合（IPヘッダーが無効だったりチェックサムが誤っていたりなど）でも増加します。これはGRO/LRO後の集約セグメント数を示します。

  • IpInDelivers

定義は RFC1213 ipInDelivers

上位レイヤーのプロトコルに届けられたパケット数を示します。たとえばTCP、UDP、ICMPなどです。rawソケットに誰もリスニングしていない場合、カーネルがサポートするプロトコルのみが届けられ、rawソケットにリスニングしている場合、すべての有効なIPパケットが届けられます。

  • IpOutRequests

定義は RFC1213 ipOutRequests

IPレイヤー経由で送信されたパケット数を示します。シングルキャストおよびマルチキャストパケットを含むすべてのパケットで、常にIpExtOutOctetsと同時に更新されます。

  • IpExtInOctetsおよびIpExtOutOctets

これらはLinuxカーネルの拡張機能であり、RFCの定義はありません。RFC1213ではifInOctetsおよびifOutOctetsが定義されていますが、これらは異なる概念です。ifInOctetsおよびifOutOctetsにはMACレイヤーのヘッダー長が含まれますが、IpExtInOctetsおよびIpExtOutOctetsには含まれず、IPレイヤーのヘッダーおよびデータのみをカウントします。

  • IpExtInNoECTPkts、IpExtInECT1Pkts、IpExtInECT0Pkts、IpExtInCEPkts

これらは4種類のECN IPパケットの数を示します。参照してください 明示的な Congestion Notification 詳細についてはこちら。

これらの4つのカウンターは、ECN状態ごとの受信パケット数を計算します。LRO/GROに関係なく実際のフレーム数をカウントするため、同じパケットに対してIpInReceivesが1と表示される一方で、IpExtInNoECTPktsが2以上になる可能性があります。

  • IpInHdrErrors

定義は RFC1213 ipInHdrErrorsIPヘッダーのエラーによりパケットがドロップされたことを示します。IP入力およびIPフォワーディングの両パスで発生する可能性があります。

  • IpInAddrErrors

定義は RFC1213 ipInAddrErrorsIPアドレスが無効な場合、または宛先IPアドレスがローカルアドレスでなくIPフォワーディングが有効でない場合に増加します。

  • IpExtInNoRoutes

IPスタックがパケットを受信した際にルートテーブルからルートが見つからない場合にパケットがドロップされたことを示します。IPフォワーディングが有効で宛先IPアドレスがローカルアドレスでなく、宛先IPアドレスにルートが存在しない場合に発生します。

  • IpInUnknownProtos

定義は RFC1213 ipInUnknownProtos. カーネルがサポートしていないレイヤー4プロトコルの場合、このカウンターは増加します。アプリケーションがrawソケットを使用している場合、カーネルは常にパケットをrawソケットに配信するため、このカウンターは増加しません。

  • IpExtInTruncatedPkts

IPv4パケットの場合、実際のデータサイズがIPv4ヘッダーの「Total Length」フィールドよりも小さいことを意味します。

  • IpInDiscards

定義は RFC1213 ipInDiscards. IP受信パスでパケットがドロップされ、その原因がカーネル内部の理由（例：メモリ不足）であることを示します。

  • IpOutDiscards

定義は RFC1213 ipOutDiscards. IP送信パスでパケットがドロップされ、その原因がカーネル内部の理由であることを示します。

  • IpOutNoRoutes

定義は RFC1213 ipOutNoRoutes. IP送信パスでパケットがドロップされ、そのパケットにルートが見つからないことを示します。

ICMPカウンタ¶

  • IcmpInMsgs and IcmpOutMsgs

定義は RFC1213 icmpInMsgs および RFC1213 icmpOutMsgs

RFC1213に記載されている通り、これらのカウンターにはエラーが含まれます。ICMPパケットが無効なタイプでもカウンターは増加します。ICMP送信パスではrawソケットのヘッダーを確認するため、ユーザースペースのプログラムがIPヘッダーを構築した場合でもIcmpOutMsgsは更新されます。

  • ICMPの名前付きタイプ

これらのカウンターには一般的なICMPタイプの大部分が含まれており、以下が該当します：

IcmpInTimeExcds: RFC1213 icmpInTimeExcds
IcmpInParmProbs: RFC1213 icmpInParmProbs
IcmpInSrcQuenchs: RFC1213 icmpInSrcQuenchs
IcmpInRedirects: RFC1213 icmpInRedirects
IcmpInEchos: RFC1213 icmpInEchos
IcmpInEchoReps: RFC1213 icmpInEchoReps
IcmpInTimestamps: RFC1213 icmpInTimestamps
IcmpInTimestampReps: RFC1213 icmpInTimestampReps
IcmpInAddrMasks: RFC1213 icmpInAddrMasks
IcmpInAddrMaskReps: RFC1213 icmpInAddrMaskReps
IcmpOutDestUnreachs: RFC1213 icmpOutDestUnreachs
IcmpOutTimeExcds: RFC1213 icmpOutTimeExcds
IcmpOutParmProbs: RFC1213 icmpOutParmProbs
IcmpOutSrcQuenchs: RFC1213 icmpOutSrcQuenchs
IcmpOutRedirects: RFC1213 icmpOutRedirects
IcmpOutEchos: RFC1213 icmpOutEchos
IcmpOutEchoReps: RFC1213 icmpOutEchoReps
IcmpOutTimestamps: RFC1213 icmpOutTimestamps

IcmpOutAddrMasks: RFC1213 icmpOutAddrMasks
IcmpOutAddrMaskReps: RFC1213 icmpOutAddrMaskReps

すべてのICMPタイプには「In」と「Out」の2つのカウンターがあります。たとえばICMPエコーパケットの場合、IcmpInEchosとIcmpOutEchosが対応します。意味は明確です。「In」カウンターはカーネルがそのパケットを受信したことを示し、「Out」カウンターはカーネルがそのパケットを送信したことを示します。

  • ICMP数値タイプ

これらはIcmpMsgInType[N]とIcmpMsgOutType[N]です。[N]はICMPタイプ番号を示します。これらのカウンターはすべてのICMPパケットを追跡します。ICMPタイプ番号の定義は ICMPパラメータ ドキュメントに記載されています。

たとえば、LinuxカーネルがICMPエコーパケットを送信した場合、IcmpMsgOutType8が1増加します。また、カーネルがICMPエコーレスポンスパケットを受信した場合、IcmpMsgInType0が1増加します。

  • IcmpInCsumErrors

このカウンターはICMPパケットのチェックサムが正しくないことを示します。カーネルはIcmpInMsgsを更新した後、IcmpMsgInType[N]を更新する前にチェックサムを検証します。チェックサムが不正なパケットはIcmpInMsgsが更新されますが、IcmpMsgInType[N]は更新されません。

  • IcmpInErrorsとIcmpOutErrors

定義は RFC1213 icmpInErrors および RFC1213 icmpOutErrors

ICMPパケットハンドラの処理中にエラーが発生した場合、これらの2つのカウンターが更新されます。受信パケット処理ではIcmpInErrorsが更新され、送信パケット処理ではIcmpOutErrorsが更新されます。IcmpInCsumErrorsが増加した場合、IcmpInErrorsも常に増加します。

ICMPカウンターの関係¶

IcmpMsgOutType[N]の合計は常にIcmpOutMsgsと等しくなります。これらは同時に更新されるためです。IcmpMsgInType[N]の合計にIcmpInErrorsを加えると、IcmpInMsgs以上になる必要があります。カーネルがICMPパケットを受信する際、以下の論理を実行します:

  1. IcmpInMsgsを増やす

  2. エラーがあればIcmpInErrorsを更新し、処理を終了する

  3. IcmpMsgOutType[N]を更新する

  4. パケットのタイプに応じて処理を行い、エラーがあればIcmpInErrorsを更新し、プロセスを終了する

ステップ(2)ですべてのエラーが発生した場合、IcmpInMsgsはIcmpMsgOutType[N]の合計とIcmpInErrorsの合計に等しくなる。ステップ(4)ですべてのエラーが発生した場合、IcmpInMsgsはIcmpMsgOutType[N]の合計に等しくなる。ステップ(2)とステップ(4)の両方でエラーが発生した場合、IcmpInMsgsはIcmpMsgOutType[N]の合計とIcmpInErrorsの合計より小さくなる。

一般的なTCPカウンタ¶

  • TcpInSegs

定義は RFC1213 tcpInSegs

TCPレイヤーによって受信されたパケット数を示す。RFC1213で説明されているように、チェックサムエラー、無効なTCPヘッダなどエラーのあるパケットも含む。ただし、レイヤー2の宛先アドレスがNICのレイヤー2アドレスでない場合のエラーは含まれない。これはマルチキャストやブロードキャストパケット、またはNICがプロミスカスモードになっている場合に発生する。このような状況ではパケットがTCPレイヤーに届くが、TCPレイヤーがTcpInSegsを増加する前にパケットを破棄する。TcpInSegsカウンタはGRO（Generic Receive Offload）を認識していないため、GROによって2つのパケットがマージされた場合、TcpInSegsカウンタは1だけ増加する。

  • TcpOutSegs

定義は RFC1213 tcpOutSegs

TCPレイヤーによって送信されたパケット数を示す。RFC1213で説明されているように、再送されたパケットは含まないが、SYN、ACK、RSTパケットは含む。TcpInSegsとは異なり、TcpOutSegsはGSO（Generic Segmentation Offload）を認識しているため、GSOによってパケットが2つに分割される場合、TcpOutSegsは2だけ増加する。

  • TcpActiveOpens

定義は RFC1213 tcpActiveOpens

TCPレイヤーがSYNを送信し、SYN-SENT状態になることを示す。TcpActiveOpensが1増加するたびに、TcpOutSegsは常に1増加する。

  • TcpPassiveOpens

定義は RFC1213 tcpPassiveOpens

TCPレイヤーがSYNを受信し、SYN+ACKを返信してSYN-RCVD状態になることを示す。

  • TcpExtTCPRcvCoalesce

TCPレイヤーによって受信され、アプリケーションによって読み取られないパケットはマージされる。このカウンタはこのような状況でマージされたパケット数を示す。GROが有効な場合、多くのパケットがGROによってマージされ、これらはTcpExtTCPRcvCoalesceにカウントされない。

  • TcpExtTCPAutoCorking

パケットを送信する際、TCPレイヤーは小さなパケットを大きなパケットにマージする。このカウンタはこのような状況でマージされたパケットごとに1増加する。詳細についてはLWN記事を参照してください: https://lwn.net/Articles/576263/

  • TcpExtTCPOrigDataSent

このカウンタは カーネルコミット f19c29e3e391で説明されている。以下に私が貼り付けた説明を示します:

TCPOrigDataSent: number of outgoing packets with original data (excluding
retransmission but including data-in-SYN). This counter is different from
TcpOutSegs because TcpOutSegs also tracks pure ACKs. TCPOrigDataSent is
more useful to track the TCP retransmission rate.

  • TCPSynRetrans

このカウンタは カーネルコミット f19c29e3e391で説明されている。以下に私が貼り付けた説明を示します:

TCPSynRetrans: number of SYN and SYN/ACK retransmits to break down
retransmissions into SYN, fast-retransmits, timeout retransmits, etc.

  • TCPFastOpenActiveFail

このカウンタは カーネルコミット f19c29e3e391で説明されている。以下に私が貼り付けた説明を示します:

TCPFastOpenActiveFail: Fast Open attempts (SYN/data) failed because
the remote does not accept it or the attempts timed out.

  • TcpExtListenOverflowsとTcpExtListenDrops

カーネルがクライアントからのSYNを受け取り、TCP acceptキューが満杯の場合、カーネルはSYNを破棄しTcpExtListenOverflowsに1を加算します。同時にTcpExtListenDropsにも1を加算します。TCPソケットがLISTEN状態にあるとき、カーネルがパケットを破棄する必要がある場合、常にTcpExtListenDropsに1を加算します。したがってTcpExtListenOverflowsが増加するとTcpExtListenDropsも同時に増加しますが、TcpExtListenDropsはTcpExtListenOverflowsが増加しなくても増加することがあります。例えばメモリ割当て失敗などもTcpExtListenDropsの増加を引き起こします。

注: 上記の説明はカーネル4.10以上での挙動に基づいています。古いカーネルではTCPスタックの挙動が異なります。古いカーネルではTCP acceptキューが満杯の場合、SYNを破棄せず3-way handshakeを完了します。acceptキューが満杯のため、TCPスタックはソケットをTCP half-openキューに保持します。half-openキューにいる間、指数関数的バックオフタイマ後にSYN+ACKを送信します。クライアントがACKを返すと、TCPスタックはacceptキューがまだ満杯か確認し、満杯でなければacceptキューにソケットを移動し、満杯であればhalf-openキューに保持します。次回クライアントがACKを返すと、このソケットはacceptキューに再び移動する機会を得ます。

TCP Fast Open¶

  • TcpEstabResets

定義は RFC1213 tcpEstabResets.

  • TcpAttemptFails

定義は RFC1213 tcpAttemptFails.

  • TcpOutRsts

定義は RFC1213 tcpOutRstsRFCではこのカウンターが「RSTフラグを含むセグメントを送信した回数」を示すと説明されていますが、Linuxカーネルではこのカウンターがカーネルが送信しようとしたセグメントの数を示します。送信プロセスはメモリ割当て失敗などのエラーにより失敗することがあります。

  • TcpExtTCPSpuriousRtxHostQueues

TCPスタックがパケットを再送信しようとするが、ネットワークでパケットが失われていないものの、まだ送信されていない場合、TCPスタックは再送信を放棄し、このカウンターを更新します。パケットがqdiscやドライバキューに長時間滞在している場合にこのようなことが起こることがあります。

  • TcpEstabResets

ソケットがEstablishまたはCloseWait状態でRSTパケットを受信しました。

  • TcpExtTCPKeepAlive

このカウンターは多くのkeepaliveパケットが送信されたことを示します。keepaliveはデフォルトでは無効です。ユーザー空間のプログラムがSO_KEEPALIVEソケットオプションを設定することで有効にすることができます。

  • TcpExtTCPSpuriousRTOs

F-RTOアルゴリズムによって検出された誤った再送信タイムアウト F-RTO アルゴリズム。

TCP高速経路¶

カーネルがTCPパケットを受け取ると、パケットを処理するための2つのパスがあります。1つは高速パス、もう1つは遅延パスです。カーネルコードのコメントにはこれらをよく説明しており、以下に貼り付けています：

It is split into a fast path and a slow path. The fast path is
disabled when:

- A zero window was announced from us
- zero window probing
  is only handled properly on the slow path.
- Out of order segments arrived.
- Urgent data is expected.
- There is no buffer space left
- Unexpected TCP flags/window values/header lengths are received
  (detected by checking the TCP header against pred_flags)
- Data is sent in both directions. The fast path only supports pure senders
  or pure receivers (this means either the sequence number or the ack
  value must stay constant)
- Unexpected TCP option.

カーネルは、上記のいずれかの条件が満たされる場合を除き、高速経路を優先して使用しようとします。パケットが順序がずれている場合、カーネルは遅延経路で処理します。これによりパフォーマンスが十分でなくなる可能性があります。また、「遅延ACK」が使用されている場合もカーネルは遅延経路に移行します。これは「遅延ACK」を使用するとデータが双方向に送信されるためです。TCPウィンドウスケールオプションが使用されていない場合、接続が確立状態になった直ちに高速経路を有効化しようとしますが、TCPウィンドウスケールオプションが使用されている場合は、最初に高速経路を無効化し、カーネルがパケットを受信した後で再び高速経路を有効化しようとします。

  • TcpExtTCPPureAcks と TcpExtTCPHPAcks

パケットがACKフラグを設定しておりデータが含まれていない場合、それは純粋なACKパケットです。カーネルが高速経路で処理する場合、TcpExtTCPHPAcks が1増加し、遅延経路で処理する場合、TcpExtTCPPureAcks が1増加します。

  • TcpExtTCPHPHits

TCPパケットにデータが含まれている（つまり純粋なACKパケットではない）場合、このパケットが高速経路で処理されるたびに TcpExtTCPHPHits が1増加します。

TCPアボート¶

  • TcpExtTCPAbortOnData

これはTCPレイヤーに送信中のデータがありながら接続を終了しようとする状態を示します。そのため、TCPレイヤーは相手側にRSTを送信し、接続が丁寧に終了していないことを示します。このカウンターを簡単に増やす方法は、SO_LINGERオプションを使用することです。詳しくは、 socket man page:

デフォルトでは、アプリケーションが接続を閉じる場合、close関数はすぐに返り、カーネルが送信中のデータを非同期で送信しようとします。SO_LINGERオプションを使用し、l_onoffを1に、l_lingerを正の数に設定すると、close関数はすぐに返らず、送信中のデータが相手側からACKを受信するまで待機します。最大待機時間はl_linger秒です。l_onoffを1に設定し、l_liferを0に設定した場合、アプリケーションが接続を閉じると、カーネルがすぐにRSTを送信し、TcpExtTCPAbortOnDataカウンターが増加します。

  • TcpExtTCPAbortOnClose

このカウンターは、アプリケーションがTCP接続を閉じようとする際、TCPレイヤーに未読のデータが存在することを示します。このような状況では、カーネルがTCP接続の相手側にRSTを送信します。

  • TcpExtTCPAbortOnMemory

アプリケーションがTCP接続を閉じるとき、カーネルは接続をまだ追跡する必要があります。これにより、TCP切断プロセスが完了するのを待つことになります。例えば、アプリケーションがソケットのcloseメソッドを呼び出すと、カーネルは接続のもう一方の端にFINパケットを送信します。その後、アプリケーションはソケットと関係がなくなるものの、カーネルはソケットを保持する必要があります。このソケットは孤児ソケットと呼ばれ、カーネルはもう一方の端からの応答を待つことになります。最終的にはTIME_WAIT状態になります。カーネルが孤児ソケットを保持するためのメモリが不足した場合、カーネルはもう一方の端にRSTパケットを送信し、ソケットを削除します。このような状況では、TcpExtTCPAbortOnMemoryカウンターに1が加算されます。TcpExtTCPAbortOnMemoryカウンターを増やす条件は以下の通りです:

1. TCPプロトコルが使用するメモリがtcp_memの第三値を上回った場合です。詳しくは、 TCP man ページ:

  1. のtcp_memセクションを参照してください。

  • net.ipv4.tcp_max_orphansの値を超えた孤児ソケットの数

TcpExtTCPAbortOnTimeout

  • このカウンターは、どのTCPタイマが期限切れになった場合でも増加します。このような状況では、カーネルはRSTを送信せず、接続を放棄します。

TcpExtTCPAbortOnLinger

  • TCP接続がFIN_WAIT_2状態に入った場合、もう一方の端からのFINパケットを待つ代わりに、カーネルがRSTを送信してソケットを即座に削除することも可能です。これはLinuxカーネルのTCPスタックのデフォルト動作ではありません。TCP_LINGER2ソケットオプションを設定することで、カーネルがこの動作を実行するようにできます。

TcpExtTCPAbortFailed RFC2525 2.17セクション が満たされた場合、カーネルTCPレイヤーはRSTを送信します。このプロセス中に内部エラーが発生した場合、TcpExtTCPAbortFailedカウンターが増加します。

TCPハイブリッドスロースタート¶

ハイブリッドスロースタートアルゴリズムは、伝統的なTCP渋滞ウィンドウスロースタートアルゴリズムの拡張です。このアルゴリズムは、TCP経路の最大帯域幅が近づいているかを検出するために、ACK列長とパケット遅延の増加という2つの情報を使用します。詳細については、 ハイブリッドスロースタート論文を参照してください。ACK列長またはパケット遅延が特定のしきい値を超えると、渋滞制御アルゴリズムは渋滞回避状態に移行します。v4.20までのバージョンでは、ハイブリッドスロースタートアルゴリズムを使用している渋滞制御アルゴリズムは2つあり、それらはcubic（デフォルトの渋滞制御アルゴリズム）とcdgです。4つのSNMPカウンターがハイブリッドスロースタートアルゴリズムに関連しています。

  • TcpExtTCPHystartTrainDetect

ACK列長しきい値が検出された回数

  • TcpExtTCPHystartTrainCwnd

ACKトレイン長さによって検出されたCWNDの合計値。この値をTcpExtTCPHystartTrainDetectで割ることで、ACKトレイン長さによって検出された平均CWNDを求めることができます。

  • TcpExtTCPHystartDelayDetect

パケット遅延しきい値が検出された回数。

  • TcpExtTCPHystartDelayCwnd

パケット遅延によって検出されたCWNDの合計値。この値をTcpExtTCPHystartDelayDetectで割ることで、パケット遅延によって検出された平均CWNDを求めることができます。

TCP再送信および Congestion Control¶

TCPプロトコルにはSACKとファストリカバリーという2つのリトライメカニズムがあります。これらは排他的に動作します。SACKが有効な場合、カーネルのTCPスタックはSACKを使用するか、またはカーネルがファストリカバリーを使用します。SACKはTCPオプションであり、 RFC2018で定義されており、ファストリカバリーは RFC6582で定義されており、これは「レノ」とも呼ばれます。

TCPのコンガestion制御は大規模で複雑なトピックです。関連するSNMPカウンターを理解するには、コンガestion制御のステートマシンの状態を把握する必要があります。状態は5つあります：Open、Disorder、CWR、Recovery、Loss。これらの状態の詳細については、このドキュメントのページ5およびページ6を参照してください： https://pdfs.semanticscholar.org/0e9c/968d09ab2e53e24c4dca5b2d67c7f7140f8e.pdf

  • TcpExtTCPRenoRecoveryとTcpExtTCPSackRecovery

コンガestion制御がRecovery状態に移行した場合、SACKが使用されている場合はTcpExtTCPSackRecoveryが1増加し、SACKが使用されていない場合はTcpExtTCPRenoRecoveryが1増加します。これらの2つのカウンターは、TCPスタックが失われたパケットの再送を開始していることを示します。

  • TcpExtTCPSACKReneging

パケットがSACKによって確認されたが、受信側でこのパケットがドロップされたため、送信側がこのパケットを再送する必要があります。このような状況では、送信側がTcpExtTCPSACKRenegingに1を加えます。受信側がSACKによって確認されたパケットをドロップすることはまれですが、TCPプロトコルでは許可されています。送信側は受信側での実際の状況を把握できません。送信側はこのパケットのRTOが期限切れになるのを待って、このパケットが受信側でドロップされたと仮定します。

  • TcpExtTCPRenoReorder

再配列パケットはファストリカバリーによって検出されます。これはSACKが無効になっている場合にのみ使用されます。ファストリカバリーアルゴリズムは、複数のACK番号によって再配列を検出します。例えば、リトライがトリガーされ、元のリトライパケットが失われていない場合、単に順序がずれているだけです。受信側はリトライパケットに対して複数回ACKを送信し、元の順序ずれたパケットが到達した際にまたACKを送信します。これにより、送信側は予期しないACKの数を検出します。送信側は順序ずれが発生したことを認識します。

  • TcpExtTCPTSReorder

穴が埋まるときに再配信パケットが検出されます。例えば、送信者がパケット1、2、3、4、5を送信し、受信順序が1、2、4、5、3となった場合、送信者がパケット3のACKを受信したとき（これは穴を埋める）、TcpExtTCPTSReorderが1増加する条件は以下の2つです：(1) パケット3が再送信されていない場合。(2) パケット3が再送信されているが、そのACKのタイムスタンプが再送信タイムスタンプよりも古い場合。

  • TcpExtTCPSACKReorder

SACKによって検出された再配信パケット。SACKは再配信を検出するための2つの方法を持っています：(1) 送信者がDSACKを受信した場合。これは送信者が同一のパケットを複数回送信したことを意味し、その理由は送信者が順序が取れていないパケットを失ったと誤って考えたためです。(2) 送信者がパケット1、2、3、4、5を送信し、パケット2と5のSACKを受信した後、パケット4のSACKを受信した場合（パケット4はまだ再送信されていない）、送信者はパケット4が順序が取れていないことを認識します。カーネルのTCPスタックは、上記のいずれかのシナリオにおいてTcpExtTCPSACKReorderを増加させます。

  • TcpExtTCPSlowStartRetrans

TCPスタックがパケットを再送信しようとしており、渋滞制御状態が「Loss（損失）」です。

  • TcpExtTCPFastRetrans

TCPスタックがパケットを再送信しようとしており、渋滞制御状態が「Loss（損失）」ではありません。

  • TcpExtTCPLostRetransmit

SACKが再送信パケットが再度失われたことを指しています。

  • TcpExtTCPRetransFail

TCPスタックが再送信パケットを下層に配信しようとしたが、下層がエラーを返しました。

  • TcpExtTCPSynRetrans

TCPスタックがSYNパケットを再送信しています。

DSACK¶

DSACKは RFC2883で定義されています。受信者はDSACKを使用して、送信者に重複パケットを報告します。重複の種類は2つあります：(1) 既に確認済みのパケット。(2) 順序が取れていないパケット。TCPスタックは、受信側と送信側の両方でこれらの2種類の重複をカウントします。

  • TcpExtTCPDSACKOldSent

TCPスタックが確認済みの重複パケットを受信したため、DSACKを送信します。

  • TcpExtTCPDSACKOfoSent

TCPスタックが順序が取れていない重複パケットを受信したため、DSACKを送信します。

  • TcpExtTCPDSACKRecv

TCPスタックがDSACKを受信し、確認済みの重複パケットが受信されたことを示しています。

  • TcpExtTCPDSACKOfoRecv

TCPスタックがDSACKを受信し、順序が取れていない重複パケットが受信されたことを示しています。

無効なSACKおよびDSACK¶

SACK（またはDSACK）ブロックが無効な場合、対応するカウンターが更新されます。検証方法はSACKブロックの開始/終了シーケンス番号に基づいています。詳細については、カーネルソースコード内の関数tcp_is_sackblock_validのコメントを参照してください。SACKオプションは最大4つのブロックを持つことができ、それぞれ個別に検証されます。例えば、3つのSACKブロックが無効な場合、対応するカウンターが3回更新されます。コメントの 無効なSACKブロック用のカウンターを追加 パッチには追加の説明があります:

  • TcpExtTCPSACKDiscard

このカウンターは無効なSACKブロックの数を示します。無効なSACKブロックがACK記録によって発生した場合、TCPスタックはそれを無視し、このカウンターを更新しません。

  • TcpExtTCPDSACKIgnoredOldとTcpExtTCPDSACKIgnoredNoUndo

DSACKブロックが無効な場合、これらの2つのカウンターのうち1つが更新されます。どのカウンターが更新されるかはTCPソケットのundo_markerフラグに依存します。undo_markerが設定されていない場合、TCPスタックはパケットの再送信を unlikely に行わず、無効なDSACKブロックを依然として受信する場合、その理由はネットワークの中間でパケットが複製されている可能性があります。このようなシナリオではTcpExtTCPDSACKIgnoredNoUndoが更新されます。undo_markerが設定されている場合、TcpExtTCPDSACKIgn,oredOldが更新されます。名前の通り、これは古いパケットである可能性があります。

SACKシフト¶

Linuxのネットワーキングスタックはsk_buff構造体（skbと略称）にデータを保存します。SACKブロックが複数のskbをまたぐ場合、TCPスタックはこれらのskb内のデータを再配置しようとします。例えば、SACKブロックがシーケンス番号10〜15を確認する場合、skb1には10〜13、skb2には14〜20が含まれています。この場合、skb2内の14〜15のデータがskb1に移動されます。この操作は「シフト」と呼ばれます。SACKブロックがシーケンス番号10〜20を確認する場合、skb1には10〜13、skb2には14〜20が含まれています。この場合、skb2内のすべてのデータがskb1に移動され、skb2は破棄されます。この操作は「マージ」と呼ばれます。

  • TcpExtTCPSackShifted

skbがシフトされました

  • TcpExtTCPSackMerged

skbがマージされました

  • TcpExtTCPSackShiftFallback

skbがシフトまたはマージすべきですが、何らかの理由でTCPスタックが行いません。

TCP順序外¶

  • TcpExtTCPOFOQueue

TCPレイヤーがオーダー外のパケットを受信し、十分なメモリがあるため、キューに格納します。

  • TcpExtTCPOFODrop

TCPレイヤーがオーダー外のパケットを受信しましたが、メモリが不足しているため、破棄します。このようなパケットはTcpExtTCPOFOQueueにカウントされません。

  • TcpExtTCPOFOMerge

受信したオーダー外のパケットが前のパケットとオーバーラップしています。オーバーラップ部分は破棄され、すべてのTcpExtTCPOFOMergeパケットもTcpExtTCPOFOQueueにカウントされます。

TCP PAWS¶

PAWS（Protection Against Wrapped Sequence numbers）は、古いパケットを破棄するためのアルゴリズムです。TCPタイムスタンプに依存しています。詳細情報については、 タイムスタンプのウィキ 2.5開発シリーズで導入された形式です。 PAWSのRFC.

  • TcpExtPAWSActive

PAWSはSyn-Sent状態でパケットを破棄します。

  • TcpExtPAWSEstab

PAWSはSyn-Sent状態以外のすべての状態でパケットを破棄します。

TCP ACKスキップ¶

一部のシナリオでは、カーネルが重複ACKを頻繁に送信することを避けることがあります。詳細については、 sysctlドキュメントのtcp_invalid_ratelimitセクションを参照してください。カーネルがtcp_invalid_ratelimitによりACKをスキップする場合、以下のカウンターのいずれかを更新して、ACKがどのシナリオでスキップされたかを示します。ACKがスキップされるのは、受信したパケットがSYNパケットか、データが含まれていない場合のみです。

  • TcpExtTCPACKSkippedSynRecv

Syn-Recv状態でACKがスキップされました。Syn-Recv状態は、TCPスタックがSYNを受信しSYN+ACKを返信した状態を指します。現在、TCPスタックはACKを待っています。通常、Syn-Recv状態ではACKを送信する必要はありませんが、いくつかのシナリオではACKを送信する必要があります。たとえば、TCPスタックが同じSYNパケットを繰り返し受信する場合、PAWSチェックに通らないパケットを受信する場合、またはシーケンス番号がウィンドウ外のパケットを受信する場合です。これらのシナリオではACKを送信する必要があります。ACK送信頻度がtcp_invalid_ratelimitの許容範囲を超える場合、TCPスタックはACKを送信せず、TcpExtTCPACKSkippedSynRecvを増加させます。

  • TcpExtTCPACKSkippedPAWS

PAWS（Protection Against Wrapped Sequence numbers）のチェックが失敗したためACKがスキップされました。PAWSチェックがSyn-Recv、Fin-Wait-2、またはTime-Wait状態で失敗した場合、スキップされたACKはTcpExtTCPACKSkippedSynRecv、TcpExtTCPACKSkippedFinWait2、またはTcpExtTCPACKSkippedTimeWaitにカウントされます。それ以外の状態では、スキップされたACKはTcpExtTCPACKSkippedPAWSにカウントされます。

  • TcpExtTCPACKSkippedSeq

シーケンス番号がウィンドウ外で、タイムスタンプがPAWSチェックを通過し、TCP状態がSyn-Recv、Fin-Wait-2、およびTime-Wait以外の場合です。

  • TcpExtTCPACKSkippedFinWait2

Fin-Wait-2状態でACKがスキップされました。その理由はPAWSチェックの失敗または受信したシーケンス番号がウィンドウ外である可能性があります。

  • TcpExtTCPACKSkippedTimeWait

Time-Wait状態でACKがスキップされました。その理由はPAWSチェックの失敗または受信したシーケンス番号がウィンドウ外である可能性があります。

  • TcpExtTCPACKSkippedChallenge

ACKがチャレンジACKである場合、ACKがスキップされます。RFC 5961では3種類のチャレンジACKが定義されています。詳しくは RFC 5961セクション3.2, RFC 5961セクション4.2 および RFC 5961 section 5.2これらの3つのシナリオに加えて、一部のTCP状態では、ACK番号が最初の未確認番号よりも前の場合、LinuxのTCPスタックがチャレンジACKを送信することがあります（より厳しい条件で） RFC 5961 section 5.2).

TCP受信ウィンドウ¶

  • TcpExtTCPWantZeroWindowAdv

現在のメモリ使用量に応じて、TCPスタックが受信ウィンドウをゼロに設定しようとしますが、受信ウィンドウの値はゼロでない場合もあります。例えば、以前のウィンドウサイズが10で、TCPスタックが3バイト受信した場合、メモリ使用量に基づく計算値がゼロであっても、現在のウィンドウサイズは7のままです。

  • TcpExtTCPToZeroWindowAdv

TCP受信ウィンドウがゼロでない値からゼロに設定されました

  • TcpExtTCPFromZeroWindowAdv

TCP受信ウィンドウがゼロからゼロでない値に設定されました

遅延ACK¶

TCP遅延ACKは、ネットワーク内のパケット数を減らすために使用される技術です。詳細については、 Delayed ACK wiki

  • TcpExtDelayedACKs

遅延ACKタイマが期限切れました。TCPスタックは純粋なACKパケットを送信し、遅延ACKモードから抜け出します

  • TcpExtDelayedACKLocked

遅延ACKタイマが期限切れましたが、TCPスタックはユーザースペースのプログラムによってソケットがロックされているため、即時ACK送信ができません。TCPスタックはユーザースペースのプログラムがソケットをアンロックした後、純粋なACKパケットを送信します。その際、TcpExtDelayedACKsを更新し、遅延ACKモードから抜け出します

  • TcpExtDelayedACKLost

TCPスタックがACKされたパケットを受信したときに更新されます。遅延ACKのロスがこの問題を引き起こす可能性がありますが、ネットワーク内のパケットが重複するなどの他の理由でも発生します

テールロスプローブ (TLP)¶

TLPはTCPパケットロスを検出するためのアルゴリズムです。詳細については、 TLP論文.

  • TcpExtTCPLossProbes

TLPプローブパケットが送信されました

  • TcpExtTCPLossProbeRecovery

パケットロスが検出され、TLPによって回復されました

TCP Fast Openの説明¶

TCP Fast Openは、3-wayハンドシェイクが完了する前にデータ転送を可能にする技術です。詳細については、 TCP Fast Open wiki をご参照ください

  • TcpExtTCPFastOpenActive

TCPスタックがSYN-SENT状態でACKパケットを受信し、そのACKパケットがSYNパケット内のデータを確認している場合、TFOクッキーが相手側で受け入れられたと判断し、このカウンタを更新します

  • TcpExtTCPFastOpenActiveFail

このカウンターは、TCPスタックがTCP Fast Openを開始しましたが失敗したことを示しています。このカウンターは以下の3つのシナリオで更新されます：(1) 他端がSYNパケット内のデータを確認しなかった場合。(2) TFOクッキーを含むSYNパケットが少なくとも1回タイムアウトした場合。(3) 3-way handshakeの後、再送信タイムアウトがnet.ipv4.tcp_retries1回発生した場合。これは、ハンドシェイク後の中間デバイスがFast Openをブラックホールする可能性があるためです。

  • TcpExtTCPFastOpenPassive

このカウンターは、TCPスタックがFast Openリクエストを受け入れた回数を示しています。

  • TcpExtTCPFastOpenPassiveFail

このカウンターは、TCPスタックがFast Openリクエストを拒否した回数を示しています。これはTFOクッキーが無効だったり、ソケット作成プロセス中にエラーが発生したためです。

  • TcpExtTCPFastOpenListenOverflow

保留中のFast Openリクエスト数がfastopenq->max_qlenを超過した場合、TCPスタックはFast Openリクエストを拒否し、このカウンターを更新します。このカウンターが更新されても、TcpExtTCPFastOpenPassiveまたはTcpExtTCPFastOpenPassiveFailは更新されません。fastopenq->max_qlenはTCP_FASTOPENソケット操作で設定され、net.core.somaxconnを超えることはできません。例えば：

setsockopt(sfd, SOL_TCP, TCP_FASTOPEN, &qlen, sizeof(qlen));

  • TcpExtTCPFastOpenCookieReqd

このカウンターは、クライアントがTFOクッキーを要求した回数を示しています。

SYNクッキー¶

SYNフロッドを緩和するためにSYNクッキーが使用されます。詳細は SYNクッキーWiki.

  • TcpExtSyncookiesSent

送信されたSYNクッキーの数を示します。

  • TcpExtSyncookiesRecv

TCPスタックが受信したSYNクッキーの応答パケットの数です。

  • TcpExtSyncookiesFailed

SYNクッキーからデコードされたMSSが無効です。このカウンターが更新されると、受信パケットはSYNクッキーとして扱われず、TcpExtSyncookiesRecvカウンターも更新されません。

チャレンジACK¶

チャレンジACKの詳細については、TcpExtTCPACKSkippedChallengeの説明を参照してください。

  • TcpExtTCPChallengeACK

送信されたチャレンジACKの数です。

  • TcpExtTCPSYNChallenge

SYNパケットに対するチャレンジACKの送信回数です。このカウンターを更新後に、TCPスタックがチャレンジACKを送信してTcpExtTCPChallengeACKカウンターを更新するか、またはチャレンジACKを送信しないでTcpExtTCPACKSkippedChallengeを更新する可能性があります。

プルーン¶

ソケットがメモリの圧力にさらされている場合、TCPスタックは受信キューおよび順序を失ったキューからメモリを回収しようとします。回収方法の一つが「圧縮（collapse）」で、これは大きなskbを割り当て、連続するskbを単一の大きなskbにコピーし、それらの連続するskbを解放する処理です。

  • TcpExtPruneCalled

TCPスタックはソケットのメモリを回収しようとします。このカウンタを更新した後、TCPスタックは順序を失ったキューおよび受信キューを圧縮します。メモリが依然として不足している場合、TCPスタックは順序を失ったキューからパケットを破棄し（TcpExtOfoPrunedカウンタを更新します）

  • TcpExtOfoPruned

TCPスタックは順序を失ったキューにあるパケットを破棄します。

  • TcpExtRcvPruned

「圧縮」および順序を失ったキューからのパケット破棄を行った後、実際に使用しているメモリが最大許容メモリよりも依然として大きい場合、このカウンタが更新されます。これは「剪定（prune）」が失敗したことを意味します。

  • TcpExtTCPRcvCollapsed

このカウンタは「圧縮」処理中に解放されたskbの数を示します。

パインテスト¶

パブリックDNSサーバー8.8.8.8に対してpingコマンドを実行します:

--- 8.8.8.8 ping statistics ---
1 packets transmitted, 1 received, 0% packet loss, time 0ms
rtt min/avg/max/mdev = 17.875/17.875/17.875/0.000 ms

nstaytの結果:

nstatuser@nstat-a:~$ nstat
#kernel
IpInReceives                    1                  0.0
IpInDelivers                    1                  0.0
IpOutRequests                   1                  0.0
IcmpInMsgs                      1                  0.0
IcmpInEchoReps                  1                  0.0
IcmpOutMsgs                     1                  0.0
IcmpOutEchos                    1                  0.0
IcmpMsgInType0                  1                  0.0
IcmpMsgOutType8                 1                  0.0

IpExtOutOctets                  84                 0.0

LinuxサーバーはICMPエコーパケットを送信したため、IpOutRequests、IcmpOutMsgs、IcmpOutEchosおよびIcmpMsgOutType8が1増加しました。サーバーは8.8.8.8からICMPエコー応答を受信したため、IpInReceives、IcmpInMsgs、IcmpInEchoRepsおよびIcmpMsgInType0が1増加しました。ICMPエコー応答はIPレイヤー経由でICMPレイヤーに渡されたため、IpInDeliversが1増加しました。デフォルトのpingデータサイズは48バイトなので、ICMPエコーパケットと対応するエコー応答パケットは以下のようになります:

  • 14バイトMACヘッダ

  • 20バイトIPヘッダ

  • 16バイトICMPヘッダ

  • 48バイトデータ（pingコマンドのデフォルト値）

したがってIpExtInOctetsおよびIpExtOutOctetsは20+16+48=84バイトになります。

TCP 3-way handshake¶

サーバー側で実行:

nstatuser@nstat-b:~$ nc -lknv 0.0.0.0 9000
Listening on [0.0.0.0] (family 0, port 9000)

クライアント側で実行:

nstatuser@nstat-a:~$ nc -nv 192.168.122.251 9000
Connection to 192.168.122.251 9000 port [tcp/*] succeeded!

サーバーはTCP 9000ポートでリスンし、クライアントが接続したため、3-way handshakeが完了しました。

サーバー側で以下のnstat出力が確認できます:

nstatuser@nstat-b:~$ nstat | grep -i tcp
TcpPassiveOpens                 1                  0.0
TcpInSegs                       2                  0.0
TcpOutSegs                      1                  0.0
TcpExtTCPPureAcks               1                  0.0

クライアント側で以下のnstat出力が確認できます:

nstatuser@nstat-a:~$ nstat | grep -i tcp
TcpActiveOpens                  1                  0.0
TcpInSegs                       1                  0.0
TcpOutSegs                      2                  0.0

サーバーが最初のSYNを受信した際、SYN+ACKを返信し、SYN-RCVD状態に移行したため、TcpPassiveOpensが1増加しました。サーバーがSYNを受信し、SYN+ACKを送信し、ACKを受信したため、サーバーは1パケット送信し、2パケット受信しました。TcpInSegsは2増加し、TcpOutSegsは1増加しました。3-way handshakeの最後のACKはデータを含まない純粋なACKなので、TcpExtTCPPureAcksが1増加しました。

クライアントがSYNを送信したとき、クライアントはSYN-SENT状態に移行し、TcpActiveOpensが1増加しました。クライアントがSYNを送信し、SYN+ACKを受信した後、ACKを送信したため、クライアントは2つのパケットを送信し、1つのパケットを受信しました。TcpInSegsは1増加し、TcpOutSegsは2増加しました。

TcpExtTCPAbortOnClose¶

サーバー側で以下のPythonスクリプトを実行します:

import socket
import time

port = 9000

s = socket.socket(socket.AF_INET, socket.SOCK_STREAM)
s.bind(('0.0.0.0', port))
s.listen(1)
sock, addr = s.accept()
while True:
    time.sleep(9999999)

このPythonスクリプトは9000ポートでリッスンしますが、接続からのデータは読み取りません。

クライアント側では、ncを使用して文字列「hello」を送信します。

nstatuser@nstat-a:~$ echo "hello" | nc nstat-b 9000

次に、サーバー側に戻ると、サーバーが「hello」パケットを受信し、TCPレイヤーがこのパケットをACKしましたが、アプリケーションはまだ読み込んでいません。Ctrl-Cをタイプしてサーバーのスクリプトを終了します。その後、サーバー側でTcpExtTCPAbortOnCloseが1増加していることが確認できます:

nstatuser@nstat-b:~$ nstat | grep -i abort
TcpExtTCPAbortOnClose           1                  0.0

サーバー側でtcpdumpを実行すると、Ctrl-Cをタイプした後、サーバーがRSTを送信していることが確認できます。

TcpExtTCPAbortOnMemoryとTcpExtTCPAbortOnTimeout¶

以下は、orphaneソケット数がnet.ipv4.tcp_max_orphansを超える例です。クライアント側でtcp_max_orphansの値を小さくします:

sudo bash -c "echo 10 > /proc/sys/net/ipv4/tcp_max_orphans"

クライアントコード（サーバーに64接続を確立）:

nstatuser@nstat-a:~$ cat client_orphan.py
import socket
import time

server = 'nstat-b' # server address
port = 9000

count = 64

connection_list = []

for i in range(64):
    s = socket.socket(socket.AF_INET, socket.SOCK_STREAM)
    s.connect((server, port))
    connection_list.append(s)
    print("connection_count: %d" % len(connection_list))

while True:
    time.sleep(99999)

サーバーコード（クライアントからの64接続を受信）:

nstatuser@nstat-b:~$ cat server_orphan.py
import socket
import time

port = 9000
count = 64

s = socket.socket(socket.AF_INET, socket.SOCK_STREAM)
s.bind(('0.0.0.0', port))
s.listen(count)
connection_list = []
while True:
    sock, addr = s.accept()
    connection_list.append((sock, addr))
    print("connection_count: %d" % len(connection_list))

サーバーとクライアントでPythonスクリプトを実行します。

サーバー側:

python3 server_orphan.py

クライアント側:

python3 client_orphan.py

サーバー側でiptablesを実行します:

sudo iptables -A INPUT -i ens3 -p tcp --destination-port 9000 -j DROP

クライアントでCtrl-Cをタイプしてclient_orphan.pyを停止します。

クライアント側でTcpExtTCPAbortOnMemoryを確認します:

nstatuser@nstat-a:~$ nstat | grep -i abort
TcpExtTCPAbortOnMemory          54                 0.0

クライアント側のorphaneソケット数を確認します:

nstatuser@nstat-a:~$ ss -s
Total: 131 (kernel 0)
TCP:   14 (estab 1, closed 0, orphaned 10, synrecv 0, timewait 0/0), ports 0

Transport Total     IP        IPv6
*         0         -         -
RAW       1         0         1
UDP       1         1         0
TCP       14        13        1
INET      16        14        2
FRAG      0         0         0

テストの説明: server_orphan.pyとclient_orphan.pyを実行して、サーバーとクライアント間で64接続を確立します。iptablesコマンドを実行すると、サーバーがクライアントからのすべてのパケットをドロップします。client_orphan.pyでCtrl-Cをタイプして、クライアントシステムがこれらの接続を閉じようとする際、これらがorphaneソケットになります。サーバー側のiptablesがクライアントからのパケットをブロックしているため、サーバーはクライアントからのFINパケットを受け取れず、クライアント側のすべての接続がFIN_WAIT_1ステージに停滞します。これにより、orphaneソケットとして保持されます。/proc/sys/net/ipv4/tcp_max_orphansにecho 10を実行したため、クライアントシステムは最大10のorphaneソケットを保持します。それ以上のorphaneソケットはRSTを送信して削除されます。64接続があるため、ss -sコマンドでシステムが10のorphaneソケットを保持していることが確認でき、TcpExtTCPAbortOnMemoryの値は54になっています。

orphansocketの数に関する追加説明: 'ss -s'コマンドで正確なorphansocketの数を確認できますが、カーネルがTcpExtTCPAbortOnMemoryを増加させ、RSTを送信する際には常に正確な数をチェックしない場合があります。パフォーマンス向上のため、カーネルはまず概算の数をチェックし、その数がtcp_max_orphansを超える場合にのみ正確な数を再チェックします。したがって、概算の数がtcp_max_orphans未満でも、正確な数がtcp_max_orphansを超えていた場合、TcpExtTCPAbortOnMemoryは増加しません。tcp_max_orphansが十分大きい場合、このような問題は発生しませんが、テストのようにtcp_max_orphansを小さな値に設定するとこの問題が発生します。テストではクライアントが64接続を設定しましたが、tcp_max_orphansは10でした。クライアントが11接続を設定した場合、TcpExtTCPAbortOnMemoryの変化は確認できませんでした。

前のテストを継続し、数分間待機します。サーバー側のiptablesがトラフィックをブロックしているため、サーバーはFINを受け取らず、クライアントのorphansocketは最終的にFIN_WAIT_1状態でタイムアウトします。数分待機した後、クライアント側で10個のタイムアウトが確認できます。

nstatuser@nstat-a:~$ nstat | grep -i abort
TcpExtTCPAbortOnTimeout         10                 0.0

このカウンターは、どのTCPタイマが期限切れになった場合でも増加します。このような状況では、カーネルはRSTを送信せず、接続を放棄します。¶

サーバー側のコード:

TcpExtListenOverflowsとTcpExtListenDrops¶

サーバーでncコマンドを実行し、ポート9000で監聽:

nstatuser@nstat-b:~$ nc -lkv 0.0.0.0 9000
Listening on [0.0.0.0] (family 0, port 9000)

クライアントで異なるターミナルで3つのncコマンドを実行:

nstatuser@nstat-a:~$ nc -v nstat-b 9000
Connection to nstat-b 9000 port [tcp/*] succeeded!

ncコマンドは1つの接続のみを受け付け、acceptキューの長さは1です。現在のLinux実装では、キュー長をnに設定すると実際のキュー長はn+1になります。今回は3つの接続を作成し、1つはncによって受け付けられ、2つはacceptキューに待機しているため、acceptキューが満杯になります。

4番目のncを実行する前、サーバーでnstatの履歴をクリアします:

nstatuser@nstat-b:~$ nstat -n

クライアントで4番目のncを実行:

nstatuser@nstat-a:~$ nc -v nstat-b 9000

ncサーバーがkernel 4.10以上で動作している場合、"Connection to … succeeded!"という文字列は表示されません。なぜなら、accept queueが満杯の状態でkernelがSYNパケットをドロップするためです。一方、ncクライアントが古いkernelで動作している場合、接続が成功したと表示されます。なぜなら、kernelが3-way handshakeを完了し、half open queueにソケットを保持するからです。私はkernel 4.15でテストを行いました。以下はサーバーのnstatの出力です:

nstatuser@nstat-b:~$ nstat
#kernel
IpInReceives                    4                  0.0
IpInDelivers                    4                  0.0
TcpInSegs                       4                  0.0
TcpExtListenOverflows           4                  0.0
TcpExtListenDrops               4                  0.0
IpExtInOctets                   240                0.0
IpExtInNoECTPkts                4                  0.0

TcpExtListenOverflowsとTcpExtListenDropsの値はどちらも4でした。4番目のncとnstatの間の時間が長くなると、TcpExtListenOverflowsとTcpExtListenDropsの値が大きくなるため、4番目のncのSYNパケットがドロップされ、クライアントが再試行しているからです。

IpInAddrErrors, IpExtInNoRoutesおよびIpOutNoRoutes¶

サーバーAのIPアドレス: 192.168.122.250 サーバーBのIPアドレス: 192.168.122.251 サーバーAで準備を行います。サーバーBへのルートを追加します:

$ sudo ip route add 8.8.8.8/32 via 192.168.122.251

サーバーBで準備を行います。すべてのインターフェースでsend_redirectsを無効にします:

$ sudo sysctl -w net.ipv4.conf.all.send_redirects=0
$ sudo sysctl -w net.ipv4.conf.ens3.send_redirects=0
$ sudo sysctl -w net.ipv4.conf.lo.send_redirects=0
$ sudo sysctl -w net.ipv4.conf.default.send_redirects=0

サーバーAがパケットを8.8.8.8に送信し、それをサーバーB経由でルーティングするようにしたいです。サーバーBがこのようなパケットを受信した場合、ICMPリダイレクトメッセージをサーバーAに送信する可能性があります。send_redirectsを0に設定することでこの挙動を無効化します。

まず、InAddrErrorsを生成します。サーバーBでIPフォワーディングを無効にします:

$ sudo sysctl -w net.ipv4.conf.all.forwarding=0

サーバーAで8.8.8.8にパケットを送信します:

$ nc -v 8.8.8.8 53

サーバーBでnstatの出力を確認します:

$ nstat
#kernel
IpInReceives                    3                  0.0
IpInAddrErrors                  3                  0.0
IpExtInOctets                   180                0.0
IpExtInNoECTPkts                3                  0.0

サーバーAが8.8.8.8をサーバーB経由でルーティングしており、サーバーBでIPフォワーディングを無効にしているため、サーバーAがパケットを送信するとサーバーBがパケットをドロップし、IpInAddrErrorsが増加します。ncコマンドがSYN+ACKを受信しなかった場合、SYNパケットを再送するため、複数のIpInAddrErrorsが発生します。

次に、IpExtInNoRoutesを生成します。サーバーBでIPフォワーディングを有効にします:

$ sudo sysctl -w net.ipv4.conf.all.forwarding=1

サーバーBのルートテーブルを確認し、デフォルトルートを削除します:

$ ip route show
default via 192.168.122.1 dev ens3 proto static
192.168.122.0/24 dev ens3 proto kernel scope link src 192.168.122.251
$ sudo ip route delete default via 192.168.122.1 dev ens3 proto static

サーバーAで再び8.8.8.8に接続します:

$ nc -v 8.8.8.8 53
nc: connect to 8.8.8.8 port 53 (tcp) failed: Network is unreachable

サーバーBでnstatを実行します:

$ nstat
#kernel
IpInReceives                    1                  0.0
IpOutRequests                   1                  0.0
IcmpOutMsgs                     1                  0.0
IcmpOutDestUnreachs             1                  0.0
IcmpMsgOutType3                 1                  0.0
IpExtInNoRoutes                 1                  0.0
IpExtInOctets                   60                 0.0
IpExtOutOctets                  88                 0.0
IpExtInNoECTPkts                1                  0.0

サーバーBでIPフォワーディングを有効にしたため、サーバーBが8.8.8.8宛のパケットを受信するとフォワーディングを試みます。デフォルトルートを削除したため、8.8.8.8へのルートが存在しないため、サーバーBがIpExtInNoRoutesを増加させ、"ICMP Destination Unreachable"メッセージをサーバーAに送信します。

最後に、IpOutNoRoutesを生成します。サーバーBでpingコマンドを実行します:

$ ping -c 1 8.8.8.8
connect: Network is unreachable

サーバーBでnstatを実行します:

$ nstat
#kernel
IpOutNoRoutes                   1                  0.0

サーバーBでデフォルトルートを削除したため、8.8.8.8宛のIPアドレスにルートが見つからず、サーバーBがIpOutNoRoutesを増加させました。

TcpExtTCPACKSkippedSynRecv¶

このテストでは、クライアントからサーバーへ同じSYNパケットを3回送信します。最初のSYNはサーバーがソケットを作成し、Syn-Recv状態に設定し、SYN/ACK応答を返します。2番目のSYNはサーバーが再度SYN/ACK応答を行い、応答時間を記録します（重複ACK応答時間）。3番目のSYNはサーバーが前の重複ACK応答時間を確認し、重複ACKをスキップしてTcpExtTCPACKSkippedSynRecvカウンタを増やすことになります。

tcpdumpを実行してSYNパケットをキャプチャします：

nstatuser@nstat-a:~$ sudo tcpdump -c 1 -w /tmp/syn.pcap port 9000
tcpdump: listening on ens3, link-type EN10MB (Ethernet), capture size 262144 bytes

別のターミナルでncコマンドを実行します：

nstatuser@nstat-a:~$ nc nstat-b 9000

nstat-bがポート9000でリスニングしていないため、RST応答を返し、ncコマンドはすぐに終了します。tcpdumpコマンドでSYNパケットをキャプチャするだけでも十分です。LinuxサーバーではTCPチェックサムのハードウェアオフロードが使用されるため、/tmp/syn.pcapのチェックサムが正しくない可能性があります。これを修正するにはtcprewriteを使用します：

nstatuser@nstat-a:~$ tcprewrite --infile=/tmp/syn.pcap --outfile=/tmp/syn_fixcsum.pcap --fixcsum

nstat-bでncを実行してポート9000でリスニングします：

nstatuser@nstat-b:~$ nc -lkv 9000
Listening on [0.0.0.0] (family 0, port 9000)

nstat-aでポート9000からのパケットをブロックするか、nstat-aがnstat-bにRSTを送信します：

nstatuser@nstat-a:~$ sudo iptables -A INPUT -p tcp --sport 9000 -j DROP

nstat-bにSYNを3回繰り返し送信します：

nstatuser@nstat-a:~$ for i in {1..3}; do sudo tcpreplay -i ens3 /tmp/syn_fixcsum.pcap; done

nstat-bのSNMPカウンタを確認します：

nstatuser@nstat-b:~$ nstat | grep -i skip
TcpExtTCPACKSkippedSynRecv      1                  0.0

予想通り、TcpExtTCPACKSkippedSynRecvは1になっています。

TcpExtTCPACKSkippedPAWS¶

PAWS（Protection Against Wrapped Sequences）をトリガーするには、古いSYNパケットを送信します。

nstat-bでncを実行してポート9000でリスニングします：

nstatuser@nstat-b:~$ nc -lkv 9000
Listening on [0.0.0.0] (family 0, port 9000)

nstat-aでtcpdumpを実行してSYNをキャプチャします：

nstatuser@nstat-a:~$ sudo tcpdump -w /tmp/paws_pre.pcap -c 1 port 9000
tcpdump: listening on ens3, link-type EN10MB (Ethernet), capture size 262144 bytes

nstat-aでncをクライアントとして実行してnstat-bに接続します：

nstatuser@nstat-a:~$ nc -v nstat-b 9000
Connection to nstat-b 9000 port [tcp/*] succeeded!

tcpdumpはSYNをキャプチャし、終了しました。チェックサムを修正する必要があります：

nstatuser@nstat-a:~$ tcprewrite --infile /tmp/paws_pre.pcap --outfile /tmp/paws.pcap --fixcsum

SYNパケットを2回送信します：

nstatuser@nstat-a:~$ for i in {1..2}; do sudo tcpreplay -i ens3 /tmp/paws.pcap; done

nstat-bでSNMPカウンタを確認します：

nstatuser@nstat-b:~$ nstat | grep -i skip
TcpExtTCPACKSkippedPAWS         1                  0.0

tcpreplayで2つのSYNを送信しました。どちらもPAWSチェックに失敗し、nstat-bは最初のSYNにACK応答を返し、2番目のSYNのACKをスキップしてTcpExtTCPACKSkippedPAWSを更新しました。

TcpExtTCPACKSkippedSeq¶

TcpExtTCPACKSkippedSeqをトリガーするには、タイムスタンプが有効（PAWSチェックを通る）が、シーケンス番号がウィンドウ外のパケットを送信します。LinuxのTCPスタックはデータを持つパケットをスキップしないので、純粋なACKパケットが必要です。このようなパケットを生成するには、ポート9000とポート9001の2つのソケットを作成し、ポート9001でACKをキャプチャして、ソース/宛先ポート番号をポート9000のソケットに変更します。これによりTcpExtTCPACKSkippedSeqをトリガーできます。

nstat-bで2つのターミナルを開き、ポート9000とポート9001の両方でncコマンドを実行してリスニングします：

nstatuser@nstat-b:~$ nc -lkv 9000
Listening on [0.0.0.0] (family 0, port 9000)

nstatuser@nstat-b:~$ nc -lkv 9001
Listening on [0.0.0.0] (family 0, port 9001)

nstat-aで2つのncクライアントを実行します：

nstatuser@nstat-a:~$ nc -v nstat-b 9000
Connection to nstat-b 9000 port [tcp/*] succeeded!

nstatuser@nstat-a:~$ nc -v nstat-b 9001
Connection to nstat-b 9001 port [tcp/*] succeeded!

nstat-aでtcpdumpを実行してACKをキャプチャします：

nstatuser@nstat-a:~$ sudo tcpdump -w /tmp/seq_pre.pcap -c 1 dst port 9001
tcpdump: listening on ens3, link-type EN10MB (Ethernet), capture size 262144 bytes

nstat-bでポート9001のソケット経由でパケットを送信します。例えば、私たちの例では'foo'という文字列を送信しました：

nstatuser@nstat-b:~$ nc -lkv 9001
Listening on [0.0.0.0] (family 0, port 9001)
Connection from nstat-a 42132 received!
foo

nstat-aでtcpdumpはACKをキャプチャしました。2つのncクライアントのソースポート番号を確認する必要があります：

nstatuser@nstat-a:~$ ss -ta '( dport = :9000 || dport = :9001 )' | tee
State  Recv-Q   Send-Q         Local Address:Port           Peer Address:Port
ESTAB  0        0            192.168.122.250:50208       192.168.122.251:9000
ESTAB  0        0            192.168.122.250:42132       192.168.122.251:9001

tcprewriteを実行し、ポート9001をポート9000に、ポート42132をポート50208に変更してください:

nstatuser@nstat-a:~$ tcprewrite --infile /tmp/seq_pre.pcap --outfile /tmp/seq.pcap -r 9001:9000 -r 42132:50208 --fixcsum

現在、/tmp/seq.pcapが必要なパケットです。nstat-bに送信してください:

nstatuser@nstat-a:~$ for i in {1..2}; do sudo tcpreplay -i ens3 /tmp/seq.pcap; done

nstat-bでTcpExtTCPACKSkippedSeqを確認してください:

nstatuser@nstat-b:~$ nstat | grep -i skip
TcpExtTCPACKSkippedSeq          1                  0.0

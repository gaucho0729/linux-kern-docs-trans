カーネルコネクションマルチプレクサ¶

カーネル接続多重器（KCM）は、汎用アプリケーションプロトコル用にTCPを介したメッセージベースのインターフェースを提供するメカニズムです。KCMを用いることで、アプリケーションはデータグラムソケットを用いてTCP経由でアプリケーションプロトコルメッセージを効率的に送受信できます。

KCMは、下図のようにカーネル内にNxM多重器を実装しています：

+------------+   +------------+   +------------+   +------------+
| KCM socket |   | KCM socket |   | KCM socket |   | KCM socket |
+------------+   +------------+   +------------+   +------------+
    |                 |               |                |
    +-----------+     |               |     +----------+
                |     |               |     |
            +----------------------------------+
            |           Multiplexor            |
            +----------------------------------+
                |   |           |           |  |
    +---------+   |           |           |  ------------+
    |             |           |           |              |
+----------+  +----------+  +----------+  +----------+ +----------+
|  Psock   |  |  Psock   |  |  Psock   |  |  Psock   | |  Psock   |
+----------+  +----------+  +----------+  +----------+ +----------+
    |              |           |            |             |
+----------+  +----------+  +----------+  +----------+ +----------+
| TCP sock |  | TCP sock |  | TCP sock |  | TCP sock | | TCP sock |
+----------+  +----------+  +----------+  +----------+ +----------+

KCMソケット¶

KCMソケットは多重器のユーザーインターフェースを提供します。すべてのKCMソケットが同一の多重器にバインドされている場合、各ソケット間のI/O操作はユーザー空間でのスレッド間の同期を必要とせずに並行して実行可能です。

マルチプレクサ¶

多重器はメッセージのルーティングを提供します。送信経路では、KCMソケットに書かれたメッセージは適切なTCPソケットを介して原子的に送信されます。同様に、受信経路では各TCPソケット（Psock）でメッセージが構築され、完全なメッセージはKCMソケットにルーティングされます。

TCPソケット & Psocks¶

TCPソケットはKCM多重器にバインド可能です。バインドされた各TCPソケットに対応するPsock構造体が割り当てられ、これは受信時にメッセージを構築するための状態およびKCM用のその他の接続固有情報を保持します。

接続モードセマンティクス¶

各多重器は、すべての接続が同一の宛先に向かっていると想定し、送信時に異なる接続を用いてロードバランシングを実行可能です。通常のsendおよびrecv呼び出し（sendmmsgおよびrecvmmsgを含む）を用いてKCMソケットからメッセージを送受信できます。

ソケットタイプ¶

KCMはSOCK_DGRAMおよびSOCK_SEQPACKETのソケットタイプをサポートしています。

メッセージの区切り¶

メッセージはTCPストリームを介して送信され、通常はメッセージをフレームするアプリケーションプロトコルメッセージ形式を含みます。受信メッセージの長さはアプリケーションプロトコルヘッダー（多くの場合、単純な長さフィールド）から推定できます。

TCPストリームはメッセージ境界を解析する必要があります。この解析にはBerkeley Packet Filter（BPF）が使用されます。TCPソケットを多重器にバインドする際にはBPFプログラムを指定する必要があります。このプログラムは新しいメッセージの受信開始時に呼び出され、これまでに受信したバイトを含むskbuffが渡されます。このプログラムはメッセージヘッダーを解析し、メッセージの長さを返します。この情報に基づき、KCMは指定された長さのメッセージを構築してKCMソケットに配信します。

TCPソケット管理¶

TCPソケットがKCMマルチプレクサにアタッチされると、データの準備完了（POLLIN）や書き込みスペースの利用可能（POLLOUT）イベントはマルチプレクサによって処理されます。TCPソケットに状態変化（切断）やその他のエラーが発生した場合、エラーがTCPソケットにポストされ、POLLERRイベントが発生しKCMはそのソケットを使用を停止します。アプリケーションがTCPソケットのエラー通知を受ける場合、まずKCMからソケットをアンアタッチし、その後エラー条件を処理する必要があります（典型的な対応はソケットを閉じて必要に応じて新しい接続を確立することです）。

KCMは、アタッチされたTCPソケットの受信ソケットバッファサイズを最大受信メッセージサイズの上限とします（このバッファサイズはSO_RCVBUFで設定可能です）。BPFプログラムが報告する新しいメッセージの長さがこの上限を超える場合、TCPソケットに該当するエラー（EMSGSIZE）がポストされます。BPFプログラムは最大メッセージサイズを強制的に設定し、その上限を超えた場合にエラーを報告することも可能です。

受信ソケットでのメッセージの組み立てにはタイムアウトを設定可能です。タイムアウト値はアタッチされたTCPソケットの受信タイムアウト（SO_RCVTIMEOで設定）から取得されます。タイマが組み立て完了前に期限切れした場合、ソケットにエラー（ETIMEDOUT）がポストされます。

ユーザーインターフェース¶

マルチプレクサの作成¶

新しいマルチプレクサと初期のKCMソケットは、ソケットコールによって作成されます：

socket(AF_KCM, type, protocol)

  • typeはSOCK_DGRAMまたはSOCK_SEQPACKETのいずれかです

  • protocolはKCMPROTO_CONNECTEDです

KCMソケットのクローン作成¶

上記のソケットコールで最初のKCMソケットが作成された後、マルチプレクサ用の追加のソケットはKCMソケットをクローンすることで作成可能です。これはKCMソケット上でioctlコールによって実行されます：

/* From linux/kcm.h */
struct kcm_clone {
      int fd;
};

struct kcm_clone info;

memset(&info, 0, sizeof(info));

err = ioctl(kcmfd, SIOCKCMCLONE, &info);

if (!err)
  newkcmfd = info.fd;

トランスポートソケットのアタッチ¶

トランスポートソケットをマルチプレクサにアタッチするには、マルチプレクサのKCMソケット上でioctlコールを呼び出します。例：

/* From linux/kcm.h */
struct kcm_attach {
      int fd;
      int bpf_fd;
};

struct kcm_attach info;

memset(&info, 0, sizeof(info));

info.fd = tcpfd;
info.bpf_fd = bpf_prog_fd;

ioctl(kcmfd, SIOCKCMATTACH, &info);

kcm_attach構造体には以下が含まれます：

  • fd: アタッチするTCPソケットのファイルディスクリプタ

  • bpf_prog_fd: ダウンロードされたコンパイル済みBPFプログラムのファイルディスクリプタ

トランスポートソケットのアンアタッチ¶

トランスポートソケットをマルチプレクサからアンアタッチするのは簡単です。アンアタッチioctlをkcm_unattach構造体を引数として実行します：

/* From linux/kcm.h */
struct kcm_unattach {
      int fd;
};

struct kcm_unattach info;

memset(&info, 0, sizeof(info));

info.fd = cfd;

ioctl(fd, SIOCKCMUNATTACH, &info);

KCMソケットの受信無効化¶

setsockoptを用いてKCMソケットの受信を無効化または有効化します。受信が無効化されると、ソケットの受信バッファ内の待機中のメッセージが他のソケットに移動します。この機能は、アプリケーションスレッドが特定のリクエスト処理に多くの作業を実行し、しばらくの間新しいメッセージの処理ができない場合に役立ちます。例：

int val = 1;

setsockopt(kcmfd, SOL_KCM, KCM_RECV_DISABLE, &val, sizeof(val))

メッセージの区切り処理用のBPFプログラム¶

BPFプログラムはBPF LLVMバックエンドを使用してコンパイルできます。例えば、Thriftを解析するためのBPFプログラムの例は以下の通りです。

#include "bpf.h" /* for __sk_buff */
#include "bpf_helpers.h" /* for load_word intrinsic */

SEC("socket_kcm")
int bpf_prog1(struct __sk_buff *skb)
{
     return load_word(skb, 0) + 4;
}

char _license[] SEC("license") = "GPL";

アプリケーションでの使用¶

KCMはアプリケーションレイヤーのプロトコルを高速化します。具体的には、アプリケーションがメッセージベースのインターフェースを使用してメッセージを送受信できるようにします。カーネルはメッセージが原子的に行われることを保証し、これによりアプリケーションがTCPストリーム上でメッセージベースのプロトコルをマッピングする際の負担を大幅に軽減します。KCMはさらに、カーネル内でアプリケーションレイヤーのメッセージをユニットとして扱い、ルーティングおよびスケジューリングの目的で作業単位とします。これによりマルチスレッドアプリケーションにおけるネットワーキングモデルが簡略化されます。

設定¶

Nx1構成では、KCMは同じTCP接続に対して複数のソケットハンドルを論理的に提供します。これにより、TCPソケット上のI/O操作（例えばデータのコピーインとコピーアウト）が並列化されます。アプリケーションでは、各処理スレッドに対してKCMソケットを開き、epollに挿入することができます（SO_REUSEPORTと同様の方法で同じポートに複数のリスナー・ソケットを許可するようにします）。

MxN構成では、同じ宛先に対して複数の接続が確立されます。これらは単純なロードバランシングに使用されます。

メッセージのバッチ処理¶

KCMの主な目的は、KCMソケット間のロードバランシングであり、一般的な使用ケースではスレッド間のロードバランシングです。完全なロードバランシング（つまり、受信メッセージを異なるKCMソケットにルーティングするか、送信メッセージを異なるTCPソケットにルーティングする）は、アフィニティの確立ができないためパフォーマンスに悪影響を及ぼす可能性があります。グループやメッセージのバッチベースのバランスはパフォーマンス向上に寄与します。

送信時に、アプリケーションはKCMソケット上でメッセージをバッチ（パイプライン）処理する3つの方法があります。

  1. 1回のsendmmsgで複数のメッセージを送信します。

  2. sendmsg呼び出しでメッセージをグループ化し、最後のメッセージ以外のすべてのメッセージにMSG_BATCHフラグを設定します。

  3. 複数のメッセージを構成した「スーパー・メッセージ」を作成し、1回のsendmsgで送信します。

受信時に、KCMモジュールはTCP準備完了コールバックごとに同じKCMソケットで受信したメッセージをキューに並べます。KCMソケットごとの受信準備完了コールバックごとにターゲットのKCMソケットが変更されます。アプリケーションはこれを設定する必要はありません。

エラー処理¶

アプリケーションは、TCP接続で発生したエラーを監視するスレッドを含めるべきです。通常、これはKCMマルチプレクサに接続された各TCPソケットをepollセットに配置し、POLLERRイベントを監視することで実現されます。接続されたTCPソケットでエラーが発生した場合、KCMはそのソケットにEPIPEを設定し、アプリケーションスレッドを起こします。アプリケーションがエラー（たとえば切断）を検知した後は、ソケットをKCMから解除し、その後で閉じるべきです。TCPソケットにエラーが発生した後は、データストリームが復旧不可能であると想定されます（つまり、メッセージの受信途中でエラーが発生した可能性があるため）。

TCP接続の監視¶

KCMでは、メッセージを送信または受信したTCPソケットと関連付ける手段がありません（ただし、接続されたTCPソケットが1つだけの場合を除く）。ただし、アプリケーションはソケットへのオープンファイルディスクリプタを保持しているため、ソケットから統計情報を取得でき、再送通信などの問題の検出に利用できます。

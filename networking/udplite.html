UDP-Liteプロトコル (RFC 3828)¶

UDP-Liteは、可変長チェックサムを特徴とするIETFの標準トラックトランスポートプロトコルです。これは無線ネットワークを介したマルチメディア（動画、VoIP）の転送において、一部損傷したパケットでもチェックサムテストの失敗により廃棄されずにコーデックに供給できるため、利点があります。

このファイルは現在のカーネルサポートとソケットAPIについて簡潔に説明しています。詳細な情報については以下をご参照ください：

  • UDP-Liteホームページ： http://web.archive.org/web/%2E/http://www.erg.abdn.ac.uk/users/gerrit/udp-lite/

    ここからも例としてのアプリケーションソースコードをダウンロードできます。

  • UDP-Lite HOWTO（ http://web.archive.org/web/%2E/http://www.erg.abdn.ac.uk/users/gerrit/udp-lite/files/UDP-Lite-HOWTO.txt

  • WiresharkのUDP-Lite Wiki（キャプチャファイルあり）： https://wiki.wireshark.org/Lightweight_User_Datagram_Protocol

  • プロトコル仕様、RFC 3828、 http://www.ietf.org/rfc/rfc3828.txt

1. アプリケーション¶

いくつかのアプリケーションがUDP-Liteに成功裏に移植されています。Ethereal（現在はWiresharkと呼ばれる）はUDP-Litev4/v6をデフォルトでサポートしています。

アプリケーションをUDP-Liteに移植するのは簡単です：ソケットレベルとIPPROTOのみを変更すればよいです。送信側はさらにチェックサムカバー長さを設定します（デフォルト＝ヘッダ長さ＝8）。詳細は次のセクションに記載しています。

2. プログラミングAPI¶

UDP-Liteは接続レス、信頼性のないデータグラムサービスを提供するため、UDPと同じソケットタイプを使用します。実際、UDPからUDP-Liteへの移植は非常に簡単です：socket(2)呼び出しの最後の引数に IPPROTO_UDPLITE を追加し、ステートメントが以下のようになります：

s = socket(PF_INET, SOCK_DGRAM, IPPROTO_UDPLITE);

または、それぞれ

s = socket(PF_INET6, SOCK_DGRAM, IPPROTO_UDPLITE);

上記の変更だけでUDP-Liteサービスを実行したりUDP-Liteサーバーに接続したりできます。カーネルは部分チェックサムカバーの使用に興味がないと想定し、UDPモード（フルカバー）をエミュレートします。

部分チェックサムカバー機能を使用するには、単一のソケットオプションを設定する必要があります。これはカバー長さを指定する整数を取るものです：

  • 送信側チェックサムカバー：UDPLITE_SEND_CSCOV

    例:

    int val = 20;
setsockopt(s, SOL_UDPLITE, UDPLITE_SEND_CSCOV, &val, sizeof(int));

    チェックサムカバー長さを20バイト（12bデータ＋8bヘッダ）に設定します。各パケットの最初の20バイト（擬似ヘッダを含む）のみチェックサムが計算されます。これは12バイトのベースヘッダを持つRTPアプリケーションに有用です。

  • 受信側チェックサムカバー：UDPLITE_RECV_CSCOV

    このオプションは受信側の対応です。これは本当にオプションです、つまり部分チェックサムカバーでトラフィックを有効にする必要はありません。その機能はトラフィックフィルタとして、有効にするとカーネルにカバーがこの値よりも小さいパケットをすべて破棄するよう指示します。例えば、RTPとUDPヘッダを保護する場合、受信側は最小カバー長さ20を持つパケットのみを許可するよう強制できます：

    int min = 20;
setsockopt(s, SOL_UDPLITE, UDPLITE_RECV_CSCOV, &min, sizeof(int));

getsockopt(2)への呼び出しは類似しています。拡張機能であり単独のプロトコルではなく、UDPで使用可能なすべてのソケットオプションは以前と同様に正確に使用可能です。例えばUDP_CORKやUDP_ENCAPなどです。

UDP-Liteチェックサムカバレッジオプションについての詳細な議論はセクションIVに記載されています。

3. ヘッダーファイル¶

ソケットAPIは以下のヘッダーファイルを通じてサポートされます：

  • /usr/include/netinet/in.h でIPPROTO_UDPLITEを定義します

  • /usr/include/netinet/udplite.h でUDP-Liteヘッダーフィールドおよびプロトコル定数を定義します

テスト目的で、以下のヘッダーファイルを使用できます mini ヘッダーファイル：

#define IPPROTO_UDPLITE       136
#define SOL_UDPLITE           136
#define UDPLITE_SEND_CSCOV     10
#define UDPLITE_RECV_CSCOV     11

さまざまなディストロ用の既製のヘッダーファイルはUDP-Liteターブルに含まれています。

4. 各ソケットオプションに関するカーネルの動作¶

デバッグメッセージを有効にするには、ログレベルを8に設定する必要があります。ほとんどのメッセージはKERN_DEBUGレベル（7）を使用します。

  1. 送信元ソケットオプション

送信元がカバレッジ長の値を0に指定した場合、モジュールはフルカバレッジを想定し、カバレッジ長0でチェックサムを含むパケットを送信します。送信元がカバレッジ長<8かつ0でない値を指定した場合、カーネルは8をデフォルト値とします。最後に、指定されたカバレッジ長がパケット長を上回る場合、パケット長がカバレッジ長として使用されます。

  1. 受信元ソケットオプション

受信元は受け入れるカバレッジ長の最小値を指定します。ここでの値が0の場合は、受信元がパケット全体をカバーしたいことを示します。この場合、部分的にカバーされたパケットはすべて破棄され、エラーがログに記録されます。

不正な値（<0 および <8）を指定することはできません。このような場合、デフォルト値の8が使用されます。

指定されたしきい値より小さいカバレッジ値を持つすべてのパケットは破棄され、これらのイベントもログに記録されます。

  1. チェックサム計算の無効化

送信元および受信元の両方でチェックサムの計算は常に実行され、SO_NO_CHECKを使用して無効化することはできません。したがって：

setsockopt(sockfd, SOL_SOCKET, SO_NO_CHECK,  ... );

は常に無視され、以下の値：

getsockopt(sockfd, SOL_SOCKET, SO_NO_CHECK, &value, ...);

はTCPと同様に意味がありません。ゼロチェックサムフィールドを持つパケットは不正（RFC 3828、セクション3.1参照）であり、静かに破棄されます。

  1. フラグメンテーション

チェックサムの計算はバッファサイズおよびMTUを考慮します。UDP-Liteパケットのサイズは送信バッファのサイズによって決定されます。送信バッファの最小サイズは2048（include/net/sock.hで定義されるSOCK_MIN_SNDBUF）であり、デフォルト値はnet.core.wmem_defaultで設定可能またはSO_SNDBUFソケット（7）オプションで設定できます。送信バッファの最大上限はnet.core.wmem_maxで決定されます。

送信バッファサイズよりも大きいペイロードサイズの場合、UDP-Liteはペイロードを複数の個別のパケットに分割し、各々の送信バッファサイズを満たして送信します。

正確な値はインターフェースMTUにも依存します。インターフェースMTUはIPのフラグメンテーションを引き起こす可能性があり、その場合、生成されたUDP-Liteパケットは複数のIPパケットに分割されます。このとき、最初のパケットのみがL4ヘッダーを含みます。

送信バッファサイズはチェックサムのカバー長に影響を与えます。以下に例を示します：

Payload: 1536 bytes          Send Buffer:     1024 bytes
MTU:     1500 bytes          Coverage Length:  856 bytes

UDP-Liteは1536バイトを2つの個別のパケットに送信します：

Packet 1: 1024 payload + 8 byte header + 20 byte IP header = 1052 bytes
Packet 2:  512 payload + 8 byte header + 20 byte IP header =  540 bytes

カバーパケットは最初のパケットのUDP-Liteヘッダーと848バイトのペイロードをカバーし、2番目のパケットは完全にカバーされます。注意点として、2番目のパケットではカバー長がパケット長を上回るため、カーネルはこのような場合、常にカバー長をパケット長に再調整します。

UDP-Liteパケットが複数の小さなフラグメントに分割される際の挙動の例として、以下の例を考慮してください：

Payload: 1024 bytes            Send buffer size: 1024 bytes
MTU:      300 bytes            Coverage length:   575 bytes

+-+-----------+--------------+--------------+--------------+
|8|    272    |      280     |     280      |     280      |
+-+-----------+--------------+--------------+--------------+
            280            560            840           1032
                                    ^
*****checksum coverage*************

UDP-Liteモジュールは1032バイトのパケット（1024 + 8バイトのヘッダー）を生成します。インターフェースMTUに基づき、これらは4つのIPパケット（280バイトのIPペイロード + 20バイトのIPヘッダー）に分割されます。カーネルモジュールは、最初の2つのパケット全体の内容と最後のパケットの15バイトを合計し、その後IPモジュールにフラグメントを解放します。

IPv6フラグメンテーションの同様なケースを確認するため、リンクMTUが1280バイトで、書き込みバッファが3356バイトの場合を考えてください。チェックサムカバーが1232バイト（MTUからIPv6/フラグメントヘッダー長を引いた値）未満の場合、最初のフラグメントのみを考慮する必要があります。チェックサムカバー長が大きい場合、各適格フラグメントをチェックサム処理する必要があります。チェックサムカバーが3062の場合、3356バイトのバッファは以下のフラグメントに分割されます：

Fragment 1: 1280 bytes carrying  1232 bytes of UDP-Lite data
Fragment 2: 1280 bytes carrying  1232 bytes of UDP-Lite data
Fragment 3:  948 bytes carrying   900 bytes of UDP-Lite data

最初の2つのフラグメントは完全にチェックサム処理され、最後のフラグメントでは598バイト（3062 - 2*1232）のみがチェックサム処理されます。

このようなケースを正しく処理することが重要ですが、（うっとうしいですが）非常にまれです：UDP-Liteは無線（または一般的なノイズのある）リンクでのマルチメディア性能の最適化を目的としており、そのためより短いカバー長が期待される可能性が高いです。

5. UDP-Lite ランタイム統計情報およびその意味¶

例外やエラー条件はsyslogにKERN_DEBUGレベルで記録されます。UDP-Liteに関するライブ統計情報は/proc/net/snmpにあり、新しいnetstatバージョンでは以下のコマンドで確認できます：

netstat -svu

これはUDP-Liteの統計変数を表示し、その意味は以下の通りです。

InDatagrams

ユーザーに届けられたデータグラムの総数。

NoPorts

未知のポートに到達したパケット数。これらのケースは別個にカウントされます（InErrorsとしてカウントされません）。

InErrors

エラーを含むUDP-Liteパケットの数。エラーには以下のものが含まれます：

  • 内部ソケットキュー受信エラー

  • パケットが短すぎる（8バイト未満または指定されたカバー長さが受信長さを上回る）

  • xfrm4_policy_check()がエラーを返した

  • アプリケーションが受信パケットのカバー長さより大きい最小カバー長さを指定した

  • チェックサムカバーが違反した

  • 不正なチェックサム

OutDatagrams

送信されたデータグラムの総数。

これらの統計はUDP MIB（RFC 2013）から導出されています。

6. IPtables¶

UDP-LiteのパケットマッチサポートおよびLOGターゲットのサポートがあります。以下の行を/etc/protocolsにコピー＆ペーストすると：

udplite 136     UDP-Lite        # UDP-Lite [RFC 3828]

すると:

iptables -A INPUT -p udplite -j LOG

syslogにログ出力が生成されます。パケットのドロップおよび拒否も動作します。

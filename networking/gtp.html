LinuxカーネルGTPトンネリングモジュール¶

ドキュメンテーション by

Harald Welte <laforge@gnumonks.org> および Andreas Schultz <aschultz@tpip.net>

「drivers/net/gtp.c」では、モバイルステーション（電話、モデム）と外部パケットデータネットワーク（インターネットなど）の間でユーザーIPペイロードをトンネルするためのカーネルレベルの実装が見つかります。

GTPとは¶

GTPは、モバイルステーション（電話、モデム）と外部パケットデータネットワーク（インターネットなど）の間でユーザーIPペイロードをトンネルするための汎用トンネルプロトコルで、3GPPプロトコルです。

モバイル電話からデータ接続を開始すると、電話はコントロールプレーンを介して、外部データネットワークと電話の間でこのようなトンネルの確立を信号として送信します。トンネルエンドポイントは電話とゲートウェイに存在し、中間ノードはエンカプスレーションされたパケットを単に転送します。

電話自体はGTPを実装していませんが、LLC/SNDCP/RLC/MACなどの技術依存プロトコルスタックを使用してユーザーIPペイロードを送信します。

セルラー事業者のインフラ内部のネットワーク要素（GPRS/EGPRSまたはクラシックUMTSの場合のSGSN、3Gフェムトセルの場合のhNodeB、4G/LTEの場合のeNodeB）では、セルラープロトコルスタックがGTPに変換されます エンドツーエンドのトンネルを破壊することなく。したがって、中間ノードは特定のリレーファンクションを実行します。

GTPパケットは最終的にGGSN（GSM/UMTS）またはP-GW（LTE）に到達し、トンネルを終了してパケットをデカプスレーションし、外部パケットデータネットワークに転送します。これはパブリックインターネットであるかもしれませんが、任意のプライベートIPネットワーク（理論上はX.25などの非IPネットワークも含む）です。

プロトコル仕様は3GPP TS 29.060に記載されており、3GPPウェブサイトから公開されています http://www.3gpp.org/DynaReport/29060.htm

便利のためにv13.6.0のPDFリンクを以下に提供します: http://www.etsi.org/deliver/etsi_ts/129000_129099/129060/13.06.00_60/ts_129060v130600p.pdf

Linux GTPトンネルモジュール¶

このモジュールはトンネルエンドポイントの機能を実装しており、電話から発信されたアップリンクでエンカプスレーションされたIPパケットをデカプスレーションし、外部パケットネットワークから受信したRAW IPパケットをダウンリンクで電話にエンカプスレーションします。

また、 のみ ユーザープレーン（ユーザーIPペイロードを運ぶ）として知られるGTP-Uを実装しています。コントロールプレーン（GTPトンネルの確立と終了に使用されるシグナリングプロトコルであるGTP-C）は実装していません。

動作するGGSN/P-GWの設定を行うには、GTP-Cプロトコルを実装したユーザー空間のプログラムが必要です。このプログラムは、カーネル内のGTP-Uモジュールが提供するnetlinkインターフェースを使用して、カーネルモジュールを設定します。

この分割アーキテクチャは、PPPoeやL2TPなどのトンネルプロトコルのトンネルモジュールと同様です。トンネルの確立や認証などはユーザー空間でデーモンを実行し、データプレーンのみをカーネル内で高速化します。

用語に惑わされないでください：GTPユーザープレーンはカーネルの高速化経路を通りますが、GTPコントロールプレーンはユーザー空間に移ります :)

このモジュールの公式ホームページは https://osmocom.org/projects/linux-kernel-gtp-u/wiki

LinuxカーネルGTP-Uサポートを実装したユーザー空間のプログラム¶

この執筆時点では、少なくとも2つのフリーソフトウェア実装があり、GTP-Cを実装し、netlinkインターフェースを通じてLinuxカーネルのGTP-Uサポートを活用できます：

  • OpenGGSN（C言語によるクラシックな2G/3G GGSN）： https://osmocom.org/projects/openggsn/wiki/OpenGGSN

  • ergw（ErlangによるGGSN + P-GW）： https://github.com/travelping/ergw

ユーザー空間ライブラリ / コマンドラインユーティリティ¶

「libgtpnl」というユーザー空間ライブラリがあり、libmnlに基づき、カーネルGTPモジュールが提供するnetlinkインターフェースに対してC言語APIを実装しています：

http://git.osmocom.org/libgtpnl/

プロトコルバージョン¶

GTP-Uには2つのバージョンがあります：v0 [GSM TS 09.60] と v1 [3GPP TS 29.281]。どちらもカーネルGTPモジュールで実装されています。v0は非推奨の古いバージョンです。

GTP-UはUDPを用いてPDUを転送します。GTPv1-Uの受信UDPポートは2151、GTPv0-Uの受信UDPポートは3386です。

GTP-Cにはv0、v1、v2の3つのバージョンがあります。カーネルではGTP-Cを実装していないため、気にする必要はありません。コントロールプレーンの実装はユーザー空間の実装責任です。

IPv6¶

3GPP仕様では、内側（ユーザ）IPレイヤーや外側（トランスポート）IPレイヤーのどちらでもIPv4またはIPv6を使用できます。

残念ながら、カーネルモジュールはユーザIPペイロードにも外側IPレイヤーにもIPv6をサポートしていません。この問題の修正に向けたパッチやその他の貢献は歓迎されます！

アーキテクチャの詳細¶

ローカルGTP-Uエンティティとトンネルの識別¶

GTP-UはPDUの転送にUDPを使用します。GTPv1-Uの受信UDPポートは2152で、GTPv0-Uの場合は3386です。

IPアドレスごとに1つのGTP-Uエンティティ（およびSGSN/GGSN/S-GW/PDN-GWインスタンス）があります。トンネルエンドポイント識別子（TEID）はGTP-Uエンティティごとに一意です。

トンネルは宛先エンティティによってのみ定義されます。宛先ポートは固定されているため、宛先IPアドレスとTEIDのみでトンネルが定義されます。ソースIPアドレスとポートはトンネルには意味がありません。

したがって：

  • 送信時に、リモートエンティティはリモートIPアドレスとトンネルエンドポイントIDで定義されます。ソースIPアドレスとポートは意味を持たず、いつでも変更可能です。

  • 受信時に、ローカルエンティティはローカル宛先IPアドレスとトンネルエンドポイントIDで定義されます。ソースIPアドレスとポートは意味を持たず、いつでも変更可能です。

[3GPP TS 29.281] 第4.3.0節ではこのように定義されています：

The TEID in the GTP-U header is used to de-multiplex traffic
incoming from remote tunnel endpoints so that it is delivered to the
User plane entities in a way that allows multiplexing of different
users, different packet protocols and different QoS levels.
Therefore no two remote GTP-U endpoints shall send traffic to a
GTP-U protocol entity using the same TEID value except
for data forwarding as part of mobility procedures.

上記の定義は、2つのリモートGTP-Uエンドポイントが 同じTEIDを送信しない ことを規定していますが、 必要としない そのようなシナリオを禁止または排除するものではありません。実際、述べた移動性プロセッディングにより、GTP-Uエンティティは複数のまたは未知のペアのTEIDからのトラフィックを受け入れる必要があります。

したがって、受信側はTEIDのみを基にトンネルを識別します。ソースIPアドレスに基づくことはありません！

APN vs. ネットワークデバイス¶

GTP-Uドライバーは各Gi/SGiインターフェースに対してLinuxネットワークデバイスを作成します。

[3GPP TS 29.281] はGi/SGi参照ポイントをインターフェースと呼びます。これにより、GGSN/P-GWがこのようなインターフェースを1つしか持たないという誤解を生じる可能性があります。

正しいのは、Gi/SGi参照ポイントが3GPPパケットドメイン（PDN）に基づくGTP-UトンネルとIPベースネットワーク間の相互運用性を定義しているということです。

3GPPドキュメントには、GGSN/P-GWが実装するGi/SGiインターフェースの数に制限を設ける記述はありません。

[3GPP TS 29.061] 第11.3節は、特定のGi/SGiインターフェースの選択がアクセスポイント名（APN）を通じて行われることを明確にしています：

2. each private network manages its own addressing. In general this
   will result in different private networks having overlapping
   address ranges. A logically separate connection (e.g. an IP in IP
   tunnel or layer 2 virtual circuit) is used between the GGSN/P-GW
   and each private network.

   In this case the IP address alone is not necessarily unique.  The
   pair of values, Access Point Name (APN) and IPv4 address and/or
   IPv6 prefixes, is unique.

重複するアドレス範囲の使用ケースをサポートするため、各APNは別個のGi/SGiインターフェース（ネットワークデバイス）にマッピングされます。

注意

アクセスポイント名は純粋に制御平面（GTP-C）の概念です。GTP-Uレベルでは、GTP-Uパケット内にはトンネルエンドポイント識別子のみが存在し、ネットワークデバイスが識別されています。

したがって、特定のUEに対してIPネットワークからPDNネットワークへのマッピングは次の通りです：

  • ネットワークデバイス + MS IP → ピアIP + ピアTEID、

PDNからIPネットワークへのマッピングは次の通りです：

  • ローカルGTP-U IP + TEID → ネットワークデバイス

さらに、受信したT-PDUがネットワークデバイスに注入される前に、MS IPがPDPコンテキストに記録されたIPと照合されます。

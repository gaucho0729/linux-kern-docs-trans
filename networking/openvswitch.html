Open vSwitch datapath開発者ドキュメント¶

Open vSwitchのカーネルモジュールは、選択されたネットワークデバイスにおけるフローレベルのパケット処理を柔軟にユーザースペースから制御できます。これにより、単純なイーサネットスイッチ、ネットワークデバイスのボンディング、VLAN処理、ネットワークアクセス制御、フローベースのネットワーク制御など、さまざまな機能を実装できます。

カーネルモジュールは複数の「データパス」（ブリッジに相当）を実装しており、それぞれが複数の「バーチャルポート」（ブリッジ内のポートに相当）を持ちます。各データパスには「フローテーブル」が関連付けられており、ユーザースペースがパケットヘッダーとメタデータに基づくキーをもとにアクションのセットをマッピングする「フロー」を設定します。最も一般的なアクションはパケットを別のバーチャルポートに転送することですが、他のアクションも実装可能です。

パケットがバーチャルポートに到達すると、カーネルモジュールはそのフローキーを抽出し、フローテーブルで検索します。マッチするフローがあれば関連するアクションを実行し、マッチしない場合はユーザースペースにパケットをキューイングして処理させます（ユーザースペースは、同様のパケットを完全にカーネル内での処理に移行するためのフローを設定する可能性があります）。

フロー キーの互換性¶

ネットワークプロトコルは時間とともに進化します。新しいプロトコルが重要になり、既存のプロトコルはその重要性を失います。Open vSwitchのカーネルモジュールが今後も関連性を持ち続けるためには、新しいバージョンがフローキーとして追加プロトコルを解析できる必要があります。将来は、すでに廃れたプロトコルの解析をサポートしないことも望ましいかもしれません。そのため、Open vSwitchのNetlinkインターフェースは、ユーザースペースアプリケーションが過去または将来のバージョンのフローキーと互換性を保つように設計されています。

この前後互換性をサポートするため、カーネルモジュールがユーザースペースにパケットを渡す際には、パケットから解析したフローキーも同時に渡します。ユーザースペースはパケットから自身のフローキーを抽出し、カーネルが提供するバージョンと比較します：

  • ユーザースペースがパケットのフローキーとして認識している内容がカーネルのものと一致する場合、特別な処理は必要ありません。

  • カーネルのフローキーがユーザースペースのバージョンよりも多くのフィールドを含む場合（例えば、カーネルがIPv6ヘッダーを解析したが、ユーザースペースはイーサネットタイプに止まっている場合など）、これも特別な処理は必要ありません。ユーザースペースはカーネルが提供するフローキーを使用して通常通りフローを設定できます。

  • ユーザースペースのフロー・キーにカーネルのそれよりも多くのフィールドが含まれる場合、例えばユーザースペースがIPv6ヘッダをデコードしたが、カーネルがイーサネットタイプで停止した場合、ユーザースペースはフローをカーネルに設定せずにパケットを手動で転送できます。このケースではパフォーマンスが悪化しますが、カーネルがフローの一部とみなすすべてのパケットがユーザースペースに送られるためです。ただし、ユーザースペースが追加フィールドの値が転送動作に影響を与えないことを確認できる場合、フローを設定してもかまいません。

フロー・キーが時間とともにどのように進化するかは、この仕組みが動作する上で重要です。以下のセクションでは詳しく説明します。

フロー キー形式¶

フロー・キーはNetlinkソケットを介して、Netlink属性のシーケンスとして渡されます。一部の属性はパケットメタデータを表し、パケット自体から抽出できない情報（例：パケットが受信されたvport）を指します。ほとんどの属性はパケット内のヘッダから抽出され、例えばイーサネット、IP、TCPヘッダのソースおよび宛先アドレスなどが該当します。

<linux/openvswitch.h>ヘッダーファイルがフロー・キー属性の正確な形式を定義しています。ここでの説明を簡潔にするために、ここではカンマで区切った文字列として記述し、括弧で引数やネストを示します。例えば、以下の例はvport 1で到達したTCPパケットに対応するフロー・キーを表しています。

in_port(1), eth(src=e0:91:f5:21:d0:b2, dst=00:02:e3:0f:80:a4),
eth_type(0x0800), ipv4(src=172.16.0.20, dst=172.18.0.52, proto=17, tos=0,
frag=no), tcp(src=49163, dst=80)

議論に重要な情報でない引数はしばしば省略されます。例えば：

in_port(1), eth(...), eth_type(0x0800), ipv4(...), tcp(...)

ワイルドカード付きフロー キー形式¶

ワイルドカードフローはNetlinkソケットを介して2つのNetlink属性シーケンスで記述されます。1つは上述のフロー・キーと、もう1つはオプションのフロー・マスクです。

ワイルドカードフローは、正確な一致フローのグループを表すことができます。マスクの各「1」ビットは、フロー・キーの対応するビットと正確に一致します。一方、「0」ビットは無視するビットであり、入力パケットの「1」または「0」ビットと一致します。ワイルドカードフローを使用することで、ユーザー空間プログラムが処理する必要のある新しいフローの数を減らすことで、フローの設定速度を向上させることができます。

マスクNetlink属性のサポートは、カーネルとユーザースペースプログラムの双方でオプションです。カーネルはマスク属性を無視し、正確な一致フローをインストールするか、ユーザースペースプログラムが指定したよりも少ない数のワイルドカードビットをカーネルで実装する場合があります。この場合、カーネルが実装しないビットの変化は、追加のフロー設定にしかなりません。また、カーネルモジュールは、フローコンテキスト属性をサポートもしくは提供しないユーザースペースプログラムとも動作します。

カーネルがワイルドカードビットを無視または変更するため、ユーザースペースプログラムが正確にインストールされたマッチを把握するのは困難です。2つのアプローチが考えられます：カーネルフローテーブルに一致しなくなったときにフローを反応的にインストールする（ワイルドカードの変化を一切確認しない）か、カーネルの応答メッセージを利用してインストールされたワイルドカードを特定する方法です。

ユーザースペースとやりとりする際、カーネルは最初にインストールされたキーのマッチ部分を正確に保持する必要があります。これにより、将来のすべての操作でフローを特定するハンドルが得られます。ただし、インストールされたフローのマスクを報告する際には、カーネルが課す制限を含める必要があります。

オーバーラップしたワイルドカードフローを使用する際の挙動は未定義です。ユーザースペースプログラムは、入力パケットがワイルドカードを含むか含まないかに関わらず、常に1つのフローのみに一致するように保証する責任があります。現在の実装では、オーバーラップしたワイルドカードフローをベストエフォートで検出し、一部のフローを拒否する可能性があります。ただし、この挙動は今後のバージョンで変更される可能性があります。

一意のフロー識別子¶

フロー識別のハンドルとして、キーの元のマッチ部分を使用する代わりに、ユニークフロー識別子（UFID）を使用するという代替案があります。UFIDは、カーネルとユーザースペースプログラムの双方でオプションです。

UFIDをサポートするユーザースペースプログラムは、フロー設定時にフローに加えてUFIDを提供する必要があります。その後、すべての将来の操作でUFIDを使用してフローを参照する必要があります。カーネルはUFIDが指定されている場合、元のフローキーでフローをインデックス化する必要はありません。

フロー キーの進化に関する基本ルール¶

「フローキー互換性」のルールに従うアプリケーションの前後互換性を維持するためには、注意が必要です。

基本的なルールは明らかです：

==================================================================
New network protocol support must only supplement existing flow
key attributes.  It must not change the meaning of already defined
flow key attributes.
==================================================================

このルールには目立ちにくい影響があるため、いくつかの例を確認してみる価値があります。例えば、カーネルモジュールがすでにVLANパースを実装していなかったとします。代わりに、802.1Q TPID（0x8100）をエッジタイプとして解釈し、パケットの解析をそこで打ち切ったとします。このような802.1Qヘッダーを持つパケットのフロー・キーは、メタデータを無視すると以下のように見えます。

eth(...), eth_type(0x8100)

直感的には、VLANサポートを追加するには、「vlan」フロー・キー属性という新しい属性を追加してVLANタグを含め、既存のフィールド定義を用いてVLANタグの後ろにあるエンカプスレーションヘッダーを解析し続けるのが合理的です。この変更により、VLAN 10のTCPパケットのフロー・キーは以下のように見えます。

eth(...), vlan(vid=10, pcp=0), eth_type(0x0800), ip(proto=6, ...), tcp(...)

しかし、この変更は、新しい「vlan」フロー・キー属性を理解していないユーザースペースアプリケーションに悪影響を及ぼします。アプリケーションは、上記のフロー互換性ルールに従って理解できない「vlan」属性を無視し、フローがIPパケットを含んでいると誤って仮定する可能性があります。これは悪い仮定です（フローがIPパケットを含んでいるのは、803.1Qヘッダーを解析してスキップした場合に限ります）。これにより、アプリケーションの挙動がカーネルバージョンによって変化する可能性があります。

解決策は、ネストされた属性を用いることです。これは、802.1Qサポートがネストされた属性を用いる理由です。VLAN 10のTCPパケットは実際に以下のように表現されます。

eth(...), eth_type(0x8100), vlan(vid=10, pcp=0), encap(eth_type(0x0800),
ip(proto=6, ...), tcp(...)))

「eth_type」、「ip」、「tcp」フロー・キー属性が「encap」属性内にネストされていることに注目してください。したがって、「vlan」キーを理解していないアプリケーションはこれらの属性を認識できず、誤って解釈することはありません。（また、外側のeth_typeは0x8100のまま変更されていません。）

形式の正しくないパケットの処理¶

カーネル内で形式の悪いプロトコルヘッダー、不良なチェックサムなどによるパケットをドロップしないでください。これにより、ユーザースペースが単純なイーサネットスイッチを実装してすべてのパケットを転送するのを防ぐことができます。

代わりに、このような場合、空のコンテンツを持つ属性を含めます。空のコンテンツが有効なプロトコル値である可能性があっても、実際にはほとんど見られない限り、ユーザースペースがそれらの値を持つすべてのパケットを個別に処理するために転送するだけで十分です。

例えば、IPヘッダーがTCP（プロトコル6）を示しているが、IPヘッダーの後にTCPヘッダーが欠落しているパケットを考えてみましょう。このパケットのフロー・キーには、ソースと宛先がすべてゼロのtcp属性が含まれます。

eth(...), eth_type(0x0800), ip(proto=6, ...), tcp(src=0, dst=0)

もう一つの例として、Ethernetタイプが0x8100であるパケットを考えてみましょう。これはVLAN TCIが続くことを示していますが、Ethernetタイプの直後に切断されている場合があります。このようなパケットのフロー・キーには、すべてゼロビットのVLANと空のencap属性が含まれ、以下のように表示されます：

eth(...), eth_type(0x8100), vlan(0), encap()

TCPパケットでソースと宛先ポートが0であるような場合とは異なり、すべてゼロビットのVLAN TCIはそれほど珍しくありません。そのため、カーネル内ではVLAN_TAG_PRESENT（CFIビット）が通常設定されており、この状況を区別できるようにしています。したがって、この第二例のフロー・キーは、欠落または不正なVLAN TCIを明確に示します。

その他のルール¶

フロー・キーに関する他のルールははるかに繊細ではありません：

  • 同一のネスティングレベルで重複した属性は許容されません。

  • 属性の順序は重要ではありません。

  • カーネルがユーザースペースにフロー・キーを送信する際には、常に同じ方法で組み立てます。これにより、ユーザースペースが完全に解釈できないフロー・キーでもハッシュ処理や比較が可能になります。

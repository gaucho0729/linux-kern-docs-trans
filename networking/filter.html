Linux Socket Filtering（別名Berkeley Packet Filter（BPF））¶

はじめに¶

Linux Socket Filtering（LSF）はBSDのBerkeley Packet Filterから派生しています。BSDとLinux Kernelのフィルタリングにはいくつかの違いがありますが、Linuxの文脈でBPFやLSFを言及する場合、Linux Kernel内のフィルタリングメカニズムを指します。

BPFはユーザー空間のプログラムが任意のソケットにフィルタを接続し、特定のデータタイプを許可または拒否する機能を提供します。LSFはBSDのBPFと同じフィルタコード構造を採用しているため、BSDのbpf.4 manページを参照するとフィルタの作成に非常に役立ちます。

LinuxではBSDよりもBPFがはるかにシンプルです。デバイスやその他の心配は不要です。フィルタコードを作成し、SO_ATTACH_FILTERオプションを通じてカーネルに送信します。カーネルのチェックに通ると、そのソケットで即座にデータのフィルタリングを開始できます。

SO_DETACH_FILTERオプションを使用してフィルタをソケットから分離することもできます。ただし、通常はあまり使用されません。ソケットを閉じる際にはフィルタが自動的に削除されるためです。もう一つのレアなケースは、既存のフィルタが動作中である同じソケットに別のフィルタを追加することです。その場合、カーネルが古いフィルタを削除し、新しいフィルタを置き換える処理を行います（フィルタがチェックに通った場合）。チェックに失敗した場合は、古いフィルタが残ります。

SO_LOCK_FILTERオプションは、ソケットに接続されたフィルタをロックする機能を持っています。設定後、フィルタは削除または変更できません。これにより、プロセスがソケットを設定し、フィルタを接続してロックし、権限を降ろしても、フィルタがソケットが閉じるまで保持されることが保証されます。

この構造を最大限に活用しているのはlibpcapかもしれません。高レベルのフィルタコマンドを実行すると、 tcpdump -i em1 port 22 libpcapの内部コンパイラを通じて生成された構造体が、最終的にSO_ATTACH_FILTERを通じてカーネルにロードされます。 tcpdump -i em1 port 22 -ddd この構造体に設定されている内容を表示します。

ここではソケットについてのみ述べましたが、LinuxのBPFは多くの場所で使用されています。netfilterにはxt_bpf、カーネルのキュー管理層にはcls_bpf、セキュアコンピューティング用のSECCOMP-BPF（SECure COMPuting）などがあります。 1チームドライバーやPTPコードなど、BPFが使用されている他の多くの場所にもあります。

Structure¶

ユーザー空間アプリケーションには <linux/filter.h> が含まれており、これは以下の関連する構造体を含みます:

struct sock_filter {    /* Filter block */
        __u16   code;   /* Actual filter code */
        __u8    jt;     /* Jump true */
        __u8    jf;     /* Jump false */
        __u32   k;      /* Generic multiuse field */
};

このような構造体は、コード、jt、jf および k 値を含む 4 つの要素からなる配列として組み立てられます。jt と jf はジャンプオフセットで、k は提供されたコードのために使用される一般的な値です:

struct sock_fprog {                     /* Required for SO_ATTACH_FILTER. */
        unsigned short             len; /* Number of filter blocks */
        struct sock_filter __user *filter;
};

ソケットフィルタリングでは、この構造体へのポインタ（後続の例で示すように）が setsockopt(2) を通じてカーネルに渡されます。

#include <sys/types.h>
#include <arpa/inet.h>
#include <linux/if_ether.h>
/* ... */

/* From the example above: tcpdump -i em1 port 22 -dd */
struct sock_filter code[] = {
        { 0x28,  0,  0, 0x0000000c },
        { 0x15,  0,  8, 0x000086dd },
        { 0x30,  0,  0, 0x00000014 },
        { 0x15,  2,  0, 0x00000084 },
        { 0x15,  1,  0, 0x00000006 },
        { 0x15,  0, 17, 0x00000011 },
        { 0x28,  0,  0, 0x00000036 },
        { 0x15, 14,  0, 0x00000016 },
        { 0x28,  0,  0, 0x00000038 },
        { 0x15, 12, 13, 0x00000016 },
        { 0x15,  0, 12, 0x00000800 },
        { 0x30,  0,  0, 0x00000017 },
        { 0x15,  2,  0, 0x00000084 },
        { 0x15,  1,  0, 0x00000006 },
        { 0x15,  0,  8, 0x00000011 },
        { 0x28,  0,  0, 0x00000014 },
        { 0x45,  6,  0, 0x00001fff },
        { 0xb1,  0,  0, 0x0000000e },
        { 0x48,  0,  0, 0x0000000e },
        { 0x15,  2,  0, 0x00000016 },
        { 0x48,  0,  0, 0x00000010 },
        { 0x15,  0,  1, 0x00000016 },
        { 0x06,  0,  0, 0x0000ffff },
        { 0x06,  0,  0, 0x00000000 },
};

struct sock_fprog bpf = {
        .len = ARRAY_SIZE(code),
        .filter = code,
};

sock = socket(PF_PACKET, SOCK_RAW, htons(ETH_P_ALL));
if (sock < 0)
        /* ... bail out ... */

ret = setsockopt(sock, SOL_SOCKET, SO_ATTACH_FILTER, &bpf, sizeof(bpf));
if (ret < 0)
        /* ... bail out ... */

/* ... */
close(sock);

上記の例コードは PF_PACKET ソケットにソケットフィルタをアタッチし、ポート 22 の IPv4/IPv6 パケットのみを通過させ、それ以外のパケットはこのソケットでドロップされます。

setsockopt(2) による SO_DETACH_FILTER の呼び出しには引数が不要であり、フィルタの分離を防ぐ SO_LOCK_FILTER には 0 または 1 の整数値を指定します。

ソケットフィルタは PF_PACKET ソケットに限定されず、他のソケットファミリでも使用可能です。

システムコールの概要:

  • setsockopt(sockfd, SOL_SOCKET, SO_ATTACH_FILTER, &val, sizeof(val));

  • setsockopt(sockfd, SOL_SOCKET, SO_DETACH_FILTER, &val, sizeof(val));

  • setsockopt(sockfd, SOL_SOCKET, SO_LOCK_FILTER, &val, sizeof(val));

通常、パケットソケットでのソケットフィルタリングのほとんどの使用例は、libpcap が提供する高レベルの構文でカバーされるため、アプリケーション開発者はそれに依存すべきです。libpcap はこれらの処理を独自のレイヤーで纏めています。

以下の条件が成立する場合を除き、libpcap に依存せずフィルタを「手動で」記述する選択肢があります：i) libpcap の使用/リンクが不可能な場合、ii) 必要な BPF フィルタが libpcap のコンパイラでサポートされていない Linux 拡張機能を使用する場合、iii) libpcap のコンパイラで正確に実装できない複雑なフィルタ、または iv) 特定のフィルタコードが libpcap 内部コンパイラの最適化と異なる場合です。たとえば、xt_bpf および cls_bpf のユーザーは、複雑なフィルタコードや、libpcap で表現できないコード（例：さまざまなコードパスで異なる戻り値を返す）を必要する可能性があります。さらに、BPF JIT 実装者はテストケースを手動で記述するために、BPF コードへの低レベルアクセスが必要な場合があります。

特にxt_bpfやcls_bpfと併用するとより複雑なBPFフィルタが作成されるため、ライブシステムに接続する前にフィルタをテストすることが推奨されます。その目的で、カーネルソースディレクトリのtools/bpf/配下にある小さなツール「bpf_dbg」があります。このデバッガーは、指定されたpcapファイルに対してBPFフィルタをテストし、pcapのパケットをステップ実行し、BPFマシンレジスタダンプを行うことができます。

bpf_dbgの起動は簡単で、以下を実行するだけで十分です:

# ./bpf_dbg

入力と出力がstdin/stdoutでない場合、bpf_dbgは第一引数に代替のstdinソース、第二引数に代替のstdoutシンクを指定します。例えば: ./bpf_dbg test_in.txt test_out.txt.

他にも、ファイル「~/.bpf_dbg_init」で特定のlibreadline設定を指定でき、コマンド履歴は「~/.bpf_dbg_history」ファイルに保存されます。

    JITコンパイラ

Linuxカーネルにはx86_64、SPARC、PowerPC、ARM、ARM64、MIPS、RISC-V、s390向けの組み込みBPF JITコンパイラがあり、CONFIG_BPF_JITを有効にすることで利用可能です。JITコンパイラは、ユーザー空間からアタッチされたフィルタごとに透明に呼び出されます。または、rootによって事前に有効化されている場合、カーネル内部のユーザー向けにも呼び出されます：¶

JIT開発者や監査を行うユーザー向けに、各コンパイル実行時に生成されたオペコードイメージをカーネルログに出力できます：

echo 1 > /proc/sys/net/core/bpf_jit_enable

dmesgからの例出力：

echo 2 > /proc/sys/net/core/bpf_jit_enable

CONFIG_BPF_JIT_ALWAYS_ONが有効な場合、bpf_jit_enableは常に1に設定され、他の値を設定すると失敗します。これはbpf_jit_enableを2に設定する場合でも同様です。カーネルログに最終的なJITイメージをダンプするのは推奨されず、代わりにtools/bpf/bpftool/以下のbpftoolを使用してintrospectionを行うのが一般的な方法です。

BPFカーネル内部

BPFカーネル内部¶

内側では、カーネルインタプリタのために、以前の段落で説明したBPFと同様の基本原理を持つ異なる命令セット形式が使用されています。ただし、命令セット形式は、下位のアーキテクチャに近づけて設計されており、ネイティブの命令セットを模倣することで、より高いパフォーマンスを達成しています（詳細は後述）。この新しいISAは、「eBPF」または「内部BPF」として使い分けられます。(注: eBPFは[e]xtended BPFから派生したものであり、BPF拡張とは異なります。eBPFはISAであり、BPF拡張は古典BPFの「BPF_LD | BPF_{B,H,W} | BPF_ABS」命令のオーバーロードから始まったものです。)

1対1のマッピングでJIT化可能に設計されており、GCC/LLVMコンパイラがeBPFバックエンドを通じてネイティブにコンパイルされたコードとほぼ同等の速度で最適化されたeBPFコードを生成する可能性が開かれています。

この新しい命令セットは、最初に「制限されたC」でプログラムを書くことを目的として設計されており、オプションでGCC/LLVMバックエンドを通じてeBPFにコンパイルできるようにされています。これにより、C -> eBPF -> ネイティブコードの2段階でのみ最小限のパフォーマンスオーバーヘッドで現代の64ビットCPUにジェットストリームマッピングできます。

現在、この新しい形式はユーザーBPFプログラムの実行に使用されており、seccomp BPF、古典ソケットフィルタ、cls_bpfトラフィック分類器、teamドライバのロードバランシングモード用の分類器、netfilterのxt_bpf拡張、PTPディスセクター/分類器、そして多くの他の用途が含まれます。これらはすべて、カーネル内で新しい命令セット表現に変換され、eBPFインタプリタで実行されます。インカーネルハンドラでは、以下の通り透明に動作します。 bpf_prog_create() フィルタの設定には、resp. bpf_prog_destroy()で破棄します。BPF_PROG_RUN(filter, ctx)マクロは、フィルタをeBPFインタプリタまたはJIT化されたコードで透明に実行します。'filter'はstruct bpf_progへのポインタで、 bpf_prog_create()から取得し、'ctx'は与えられたコンテキスト（例: skbポインタ）です。すべての制約と制限は、背景で新しいレイアウトへの変換前にbpf_check_classic()から適用されます！

現在、32ビットアーキテクチャでは古典BPF形式がJIT化に使用されており、x86-64、aarch64、s390x、powerpc64、sparc64、arm32、riscv64、riscv32はeBPF命令セットからJITコンパイルを行います。

新しい内部形式の主な変更点:

  • レジスタ数は2から10に増加:

    古い形式では、レジスタAとX、および隠しのフレームポインタの2つのレジスタがありました。新しいレイアウトではこれを10の内部レジスタと読み取り専用のフレームポインタに拡張しています。64ビットCPUでは関数の引数をレジスタで渡すため、eBPFプログラムから内核関数への引数数は5に制限され、1つのレジスタが内核関数からの戻り値を受け取るためのものとして使用されます。ネイティブでは、x86_64は最初の6つの引数をレジスタで渡し、aarch64/sparcv9/mips64では7〜8つのレジスタが引数に使用されます。x86_64では6つの呼び出し元保存レジスタがあり、aarch64/sparcv9/mips64では11以上が呼び出し元保存レジスタです。

    したがって、eBPFの呼び出し規約は以下のようになります:

    • R0 - 内核関数からの戻り値、およびeBPFプログラムの終了値

    • R1 - R5 - eBPFプログラムから内核関数への引数

    • R6 - R9 - 内核関数が保持する呼び出し元保存レジスタ

    • R10 - スタックを参照する読み取り専用フレームポインタ

    したがって、すべてのeBPFレジスタはx86_64、aarch64などでのハードウェアレジスタと1対1で対応し、eBPFの呼び出し規約は64ビットアーキテクチャでの内核が使用するABIに直接マッピングされます。

    32ビットアーキテクチャではJITが32ビット算術のみを使用するプログラムをマッピングし、より複雑なプログラムはインタプリタで実行される可能性があります。

    R0 - R5はスクラッチレジスタであり、eBPFプログラムは呼び出し間で必要に応じてスプライス/フィルする必要があります。注意点として、eBPFプログラムは1つしか存在せず（＝1つのeBPFメインルーチン）、他のeBPF関数を呼び出すことはできず、事前に定義された内核関数のみを呼び出すことができます。

  • レジスタ幅は32ビットから64ビットへと拡大しています:

    なお、元の32ビットALU操作のセマンティクスは32ビットサブレジスタを通じて保持されます。すべてのeBPFレジスタは64ビットであり、32ビットの下位サブレジスタが64ビットにゼロ拡張されます。この挙動はx86_64およびarm64のサブレジスタ定義に直接対応していますが、他のJITには困難を伴います。

    32ビットアーキテクチャでは64ビット内部BPFプログラムをインタプリタで実行します。そのJITは、32ビットサブレジスタのみを使用するBPFプログラムをネイティブな指令セットに変換し、残りの部分をインタプリタで実行する可能性があります。

    操作は64ビットです。これは、64ビットアーキテクチャではポインタも64ビット幅を持つため、カーネル関数内で64ビット値をやり取りしたいからです。32ビットeBPFレジスタを使用すると、レジスタペアのABIを定義する必要がありますが、その結果、直接のeBPFレジスタとハードウェアレジスタのマッピングが行えず、JITコンパイラは関数内のすべてのレジスタに対して結合/分割/移動操作を行う必要があり、複雑でバグが入りやすく遅くなります。もう一つの理由は、アトミックな64ビットカウンタの使用です。

  • 条件付きjt/jfターゲットがjt/フォールスルーに置き換えられました:

    元の設計にはこのような構造がありますが if (cond) jump_true; else jump_false;、それらは代替の構造に置き換えられています。 if (cond) jump_true; /* else fall-through */.

  • bpf_callインストラクションとレジスタ渡しのコンベンションを導入し、他のカーネル関数とのゼロオーバーヘッド呼び出しを実現します:

    カーネル内関数呼び出しの前には、内部BPFプログラムがR1からR5レジスタに関数引数を配置して呼び出し規約を満たす必要があります。その後、インタプリタがレジスタから引数を取り出し、カーネル内関数に渡します。R1からR5レジスタがアーキテクチャで使用される引数渡し用のハードウェアレジスタにマッピングされている場合、JITコンパイラは追加の移動命令を出力する必要がなくなります。関数引数は正しいレジスタに配置され、BPF_CALLインストラクションは単一の「call」ハードウェア命令としてJITされます。この呼び出し規約はパフォーマンスへの影響を最小限に抑えつつ、一般的な呼び出し状況をカバーするように選ばれました。

    カーネル内関数呼び出し後、R1からR5は読み込み不可となり、R0には関数の戻り値が格納されます。R6からR9はcallee保存レジスタであり、呼び出しの前後で状態が保持されます。

    例えば、以下の3つのC関数を考えてみましょう:

    u64 f1() { return (*_f2)(1); }
u64 f2(u64 a) { return f3(a + 1, a); }
u64 f3(u64 a, u64 b) { return a - b; }

    GCCはf1、f3をx86_64にコンパイルできます:

    f1:
    movl $1, %edi
    movq _f2(%rip), %rax
    jmp  *%rax
f3:
    movq %rdi, %rax
    subq %rsi, %rax
    ret

    eBPF内の関数f2は以下のようになります:

    f2:
    bpf_mov R2, R1
    bpf_add R1, 1
    bpf_call f3
    bpf_exit

    f2がJITされ、ポインタが _f2に保存されている場合、f1 → f2 → f3の呼び出しと戻り値はスムーズに行われます。JITが使われない場合、__bpf_prog_run()インタプリタを使用してf2に呼び出さなければなりません。

    実用上の理由から、すべてのeBPFプログラムは「ctx」という1つの引数のみを持ち、これはすでにR1に配置されています（例：__bpf_prog_run()起動時）。プログラムは最大5つの引数を持つカーネル関数を呼び出せますが、6つ以上の引数を持つ呼び出しは現在サポートされていません。ただし、必要に応じて今後これらの制限は解除される可能性があります。

    64ビットアーキテクチャではすべてのレジスタがハードウェアレジスタに1対1でマッピングされます。例えば、x86_64 JITコンパイラはこれらを…

    R0 - rax
R1 - rdi
R2 - rsi
R3 - rdx
R4 - rcx
R5 - r8
R6 - rbx
R7 - r13
R8 - r14
R9 - r15
R10 - rbp

    …x86_64 ABIが引数渡しにrdi、rsi、rdx、rcx、r8、r9を指定し、rbx、r12〜r15がcallee保存レジスタであるためです。

    その後、以下の内部BPF擬似プログラム:

    bpf_mov R6, R1 /* save ctx */
bpf_mov R2, 2
bpf_mov R3, 3
bpf_mov R4, 4
bpf_mov R5, 5
bpf_call foo
bpf_mov R7, R0 /* save foo() return value */
bpf_mov R1, R6 /* restore ctx for next call */
bpf_mov R2, 6
bpf_mov R3, 7
bpf_mov R4, 8
bpf_mov R5, 9
bpf_call bar
bpf_add R0, R7
bpf_exit

    x86_64にJITされると以下のようになります:

    push %rbp
mov %rsp,%rbp
sub $0x228,%rsp
mov %rbx,-0x228(%rbp)
mov %r13,-0x220(%rbp)
mov %rdi,%rbx
mov $0x2,%esi
mov $0x3,%edx
mov $0x4,%ecx
mov $0x5,%r8d
callq foo
mov %rax,%r13
mov %rbx,%rdi
mov $0x6,%esi
mov $0x7,%edx
mov $0x8,%ecx
mov $0x9,%r8d
callq bar
add %r13,%rax
mov -0x228(%rbp),%rbx
mov -0x220(%rbp),%r13
leaveq
retq

    この例ではC言語に相当するものは次のとおりです:

    u64 bpf_filter(u64 ctx)
{
    return foo(ctx, 2, 3, 4, 5) + bar(ctx, 6, 7, 8, 9);
}

    プロトタイプ: u64 (*)(u64 arg1, u64 arg2, u64 arg3, u64 arg4, u64 arg5) のインカーネル関数 foo() と bar() は、適切なレジスタに引数を受け取り、その戻り値を %rax R0 に格納します。プロローグとエピローグはJITによって生成され、インタプリタでは暗黙のうちに処理されます。R0-R5はスクラッチレジスタであり、eBPFプログラムは呼び出し規約に従って呼び出し間でこれらを保持する必要があります。

    例えば、以下のプログラムは無効です:

    bpf_mov R1, 1
bpf_call foo
bpf_mov R0, R1
bpf_exit

    呼び出し後、レジスタ R1-R5 には無駄な値が格納されており、読み取れません。内部のBPFプログラムを検証するためにインカーネルのeBPF検証器が使用されます。

新しい設計では、eBPFは最大4096インスンに制限されており、これによりすべてのプログラムが迅速に終了し、固定数のカーネル関数のみを呼び出すことになります。元のBPFと新しい形式は2オペランドインスンであり、JIT時にeBPFインスンとx86インスンの1対1マッピングを容易にします。

インタプリタ関数を呼び出す際の入力コンテキストポインタは汎用的であり、その内容は特定の用途によって定義されます。セックompではR1がseccomp_dataを指し、変換されたBPFフィルタではR1がskbを指します。

内部的に翻訳されるプログラムは以下の要素から構成されています:

op:16, jt:8, jf:8, k:32    ==>    op:8, dst_reg:4, src_reg:4, off:16, imm:32

これまでに87の内部BPFインスンが実装されました。8ビットの「op」オペコードフィールドには新しいインスンの追加が可能です。一部は16/24/32バイトのエンコーディングを使用する可能性があります。新しいインスンは8バイトの倍数でなければならないため、後方互換性を維持します。

内部BPFは汎用的なRISCインスンセットです。元のBPFから新しい形式への翻訳では、すべてのレジスタやインスンが使用されるわけではありません。例えば、ソケットフィルタは exclusive add インスンを使用しませんが、トレースフィルタはイベントカウンタを維持するためにインスンを使用する場合があります。レジスタR9もソケットフィルタでは使用されませんが、より複雑なフィルタはレジスタが不足するためスタックへのスパイル/フィル操作に頼る必要があります。

内部BPFは最終段階のパフォーマンス最適化やソケットフィルタ、セックompなどに汎用アセンブラーとして使用されます。トレースフィルタも内核コード生成にアセンブラーとして使用可能です。内核での使用はセキュリティ上の制約に縛られず、生成された内部BPFコードがユーザー空間に露出しない限り、内部コードパスの最適化が可能です。内部BPFの安全性は検証器（TBD）から保証されるかもしれません。このような使用ケースでは、安全なインスンセットとして使用できます。

オリジナルのBPFと同様に、新しい形式も制御された環境内で実行され、決定性を持ち、カーネルが簡単に証明できる。プログラムの安全性は2段階で判定される。1段階目では深さ優先探索を行い、ループやCFGの検証を禁止する。2段階目では最初のインストラクションからすべての可能なパスを辿り、すべてのインストラクションの実行をシミュレートし、レジスタやスタックの状態変化を観察する。

eBPFオペコードの符号化¶

eBPFはクラシックBPFの大部分のオペコード符号化を再利用し、クラシックBPFからeBPFへの変換を簡略化している。算術およびジャンプ命令では、8ビットの‘code’フィールドは3つの部分に分かれている。

+----------------+--------+--------------------+
|   4 bits       |  1 bit |   3 bits           |
| operation code | source | instruction class  |
+----------------+--------+--------------------+
(MSB)                                      (LSB)

3つのLSBビットは命令クラスを表し、次のいずれかである:

BPF_LD 0x00

BPF_LDX 0x01

BPF_LDX 0x01

BPF_ST 0x02

BPF_ST 0x02

BPF_STX 0x03

BPF_STX 0x03

BPF_ALU 0x04

BPF_ALU 0x04

BPF_JMP 0x05

BPF_JMP 0x05

BPF_JMP32 0x06

BPF_CLASS(code) == BPF_ALUまたはBPF_JMPの場合、4番目のビットはソースオペランドを符号化する…

BPF_K     0x00
BPF_X     0x08

  • クラシックBPFでは、これは:

    BPF_SRC(code) == BPF_X - use register X as source operand
BPF_SRC(code) == BPF_K - use 32-bit immediate as source operand

  • eBPFでは、これは:

    BPF_SRC(code) == BPF_X - use 'src_reg' register as source operand
BPF_SRC(code) == BPF_K - use 32-bit immediate as source operand

…そして4つのMSBビットは操作コードを保存する。

BPF_END   0xd0  /* eBPF only: endianness conversion */

BPF_CLASS(code) == BPF_JMPまたはBPF_JMP32 [eBPFの場合]の場合、BPF_OP(code)は次のうちの一つである:

BPF_JA    0x00  /* BPF_JMP only */

BPF_JGT   0x20

BPF_EXIT  0x90  /* eBPF BPF_JMP only: function return */
BPF_JLT   0xa0  /* eBPF only: unsigned '<' */

BPF_JSLT  0xc0  /* eBPF only: signed '<' */
BPF_JSLE  0xd0  /* eBPF only: signed '<=' */

したがって、BPF_ADD | BPF_X | BPF_ALUはクラシックBPFおよびeBPFの両方で32ビットの加算を意味する。クラシックBPFにはみみつレジスタしかないので、A += Xを意味する。eBPFではdst_reg = (u32) dst_reg + (u32) src_regを意味する。同様に、BPF_XOR | BPF_K | BPF_ALUはクラシックBPFではA ^= imm32を意味し、eBPFではsrc_reg = (u32) src_reg ^ (u32) imm32を意味する。

クラシックBPFではBPF_MISCクラスを使用してA = XおよびX = Aの移動を表現している。eBPFではBPF_MOV | BPF_X | BPF_ALUコードを使用している。eBPFにはBPF_MISC操作が存在しないため、クラス7はBPF_ALU64として使用され、BPF_ALUと同じ操作を64ビット幅のオペランドで実行する。したがって、BPF_ADD | BPF_X | BPF_ALU64は64ビット加算を意味し、dst_reg = dst_reg + src_regとなる。

クラシックBPFでは、BPF_RETクラス全体を単一の ret 操作に使用している。クラシックBPF_RET | BPF_Kはimm32を返却レジスタにコピーし、関数終了を実行する。eBPFはCPUに合わせてモデル化されているため、eBPFではBPF_JMP | BPF_EXITは関数終了のみを意味する。eBPFプログラムではBPF_EXITを行う前に返却値をレジスタR0に保存する必要がある。eBPFのクラス6はBPF_JMP32として使用され、BPF_JMPと同じ操作を32ビット幅の比較オペランドで実行する。

ロードおよびストア命令では、8ビットの‘code’フィールドは次のようになる:

+--------+--------+-------------------+
| 3 bits | 2 bits |   3 bits          |
|  mode  |  size  | instruction class |
+--------+--------+-------------------+
(MSB)                             (LSB)

BPF_H   0x08    /* half word */
BPF_B   0x10    /* byte */
BPF_DW  0x18    /* eBPF only, double word */

…ロード/ストア操作のサイズを符号化しています:

B  - 1 byte
H  - 2 byte
W  - 4 byte
DW - 8 byte (eBPF only)

モード修飾子は次のいずれかです:

BPF_MSH  0xa0  /* classic BPF only, reserved in eBPF */
BPF_XADD 0xc0  /* eBPF only, exclusive add */

eBPFには2つの非汎用指令があります: (BPF_ABS | <size> | BPF_LD) と (BPF_IND | <size> | BPF_LD) で、これらはパケットデータにアクセスするために使用されます。

これらはクラシックから引き継がれなければならなかった指令で、eBPFインタープリタで実行されるソケットフィルタの強力なパフォーマンスを確保するためです。これらの指令は、インタープリタコンテキストがポインタである場合にのみ使用できます struct sk_buff および7つの暗黙のオペランドを持ちます。レジスタR6は暗黙の入力であり、sk_buffへのポインタを保持しなければなりません。レジスタR0は暗黙の出力で、パケットから取得したデータを保持します。レジスタR1-R5はスクラッチレジスタであり、BPF_ABS | BPF_LDまたはBPF_IND | BPF_LD指令間でデータを保持してはなりません。

これらの指令には暗黙のプログラム終了条件もあります。eBPFプログラムがパケット境界を超えてデータにアクセスしようとした場合、インタープリタはプログラムの実行を中止します。JITコンパイラはこの性質を保持しなければなりません。src_regおよびimm32フィールドはこれらの指令の明示的な入力です。

例:

BPF_IND | BPF_W | BPF_LD means:

  R0 = ntohl(*(u32 *) (((struct sk_buff *) R6)->data + src_reg + imm32))
  and R1 - R5 were scratched.

クラシックBPF指令セットとは異なり、eBPFには汎用ロード/ストア操作があります:

BPF_MEM | <size> | BPF_STX:  *(size *) (dst_reg + off) = src_reg
BPF_MEM | <size> | BPF_ST:   *(size *) (dst_reg + off) = imm32
BPF_MEM | <size> | BPF_LDX:  dst_reg = *(size *) (src_reg + off)
BPF_XADD | BPF_W  | BPF_STX: lock xadd *(u32 *)(dst_reg + off16) += src_reg
BPF_XADD | BPF_DW | BPF_STX: lock xadd *(u64 *)(dst_reg + off16) += src_reg

ここでsizeはBPF_BまたはBPF_HまたはBPF_WまたはBPF_DWのいずれかです。注意点として、1バイトおよび2バイトのアトミックインクリメントはサポートされていません。

eBPFには1つの16バイト指令:BPF_LD | BPF_DW | BPF_IMMがあり、これは2つの連続する8バイトブロックから構成されています。 struct bpf_insn 8バイトブロックとして解釈され、dst_regに64ビットの即値をロードします。クラシックBPFには類似の指令:BPF_LD | BPF_W | BPF_IMMがあり、これは32ビットの即値をレジスタにロードします。

eBPF検証器¶

eBPFプログラムの安全性は2段階で判定されます。

最初の段階ではDAGチェックを行い、ループやその他のCFG検証を禁止します。特に、到達不能な指令を持つプログラムを検出します。(クラシックBPF検証器はこれらを許容します)

2番目の段階では最初のインスンからすべての可能なパスをたどり、各インスンの実行をシミュレートします。レジスタおよびスタックの状態変化を観察します。

プログラムの開始時、レジスタR1にはコンテキストへのポインタが含まれており、型はPTR_TO_CTXです。検証器がR2=R1というインスンを検出すると、R2もPTR_TO_CTX型となり、式の右辺で使用できます。R1=PTR_TO_CTXで、インスンがR2=R1+R1の場合、R2=SCALAR_VALUEになります。(「セキュア」モードでは、カーネルアドレスが非特権ユーザーに漏れないように、すべてのポインタ算術を拒否します)

レジスタが一度も書き込まれていない場合、読み込みできません:

bpf_mov R0 = R2
bpf_exit

プログラムの開始時にR2が読み取れないため、拒否されます。

カーネル関数呼び出し後、R1-R5は読み取れない状態に戻され、R0は関数の戻り値の型を持つことになります。

R6-R9は呼び出し元で保存されるため、呼び出しの間にその状態が保持されます。

bpf_mov R6 = 1
bpf_call foo
bpf_mov R0 = R6
bpf_exit

正しいプログラムです。R6の代わりにR1が使われていた場合、拒否されていました。

ロード/ストア命令は、PTR_TO_CTX、PTR_TO_MAP、PTR_TO_STACKの有効な型のレジスタのみで許可されます。これらは境界とアライメントのチェックが行われます。たとえば：

bpf_mov R1 = 1
bpf_mov R2 = 2
bpf_xadd *(u32 *)(R1 + 3) += R2
bpf_exit

bpf_xadd命令の実行時、R1が有効なポインタ型を持っていないため、拒否されます。

開始時、R1の型はPTR_TO_CTX（一般的なポインタへのポインタ）です。 struct bpf_context) コールバックを使用して検証器をカスタマイズし、eBPFプログラムがctx構造体内の特定のサイズとアライメントを持つフィールドのみにアクセスできるように制限します。

たとえば、次のインスン：

bpf_ld R0 = *(u32 *)(R6 + 8)

R6 + 8のアドレスからワードを読み込み、R0に保存することを意図しています。R6がPTR_TO_CTXの場合、is_valid_access()コールバックを通じて検証器がオフセット8の4バイトサイズの読み取りが可能であることを知ります。それ以外の場合、検証器はプログラムを拒否します。R6がPTR_TO_STACKの場合、アクセスはアライメントされ、スタックの境界[-MAX_BPF_STACK, 0)内に収まらなければなりません。この例ではオフセットが8なので、境界外であるため検証が失敗します。

検証器は、eBPFプログラムがスタックに書き込みを行った後にのみ読み取りを許可します。

クラシックなBPF検証器は、M[0-15]メモリスロットを使用して同様のチェックを行います。たとえば：

bpf_ld R0 = *(u32 *)(R10 - 4)
bpf_exit

無効なプログラムです。R10は正しい読み取り専用レジスタで、PTR_TO_STACK型を持ち、R10 - 4はスタックの境界内ですが、その場所への書き込みがありませんでした。

ポインタレジスタのスパイル/フィルも追跡されます。4つの（R6-R9）呼び出し元で保存されるレジスタが一部のプログラムでは不足するためです。

許可される関数呼び出しはbpf_verifier_ops->get_func_proto()でカスタマイズされます。eBPF検証器はレジスタが引数制約に一致しているかを確認します。呼び出し後、R0は関数の戻り値の型に設定されます。

関数呼び出しは、eBPFプログラムの機能拡張の主要なメカニズムです。ソケットフィルタはプログラムが特定の関数セットを呼び出せるようにし、トレーシングフィルタは完全に異なる関数セットを許可する場合があります。

eBPFプログラムにアクセス可能な関数が作成される場合、安全性の観点から慎重に検討する必要があります。検証器は、関数が有効な引数で呼び出されることを保証します。

seccomp と socket filters は、classic BPF に対して異なるセキュリティ制限を持っています。seccomp は 2 階段の検証器によってこの問題を解決します：classic BPF 検証器が実行された後、seccomp 検証器が実行されます。eBPF の場合は、すべての使用ケースで 1 つの設定可能な検証器が共有されます。

eBPF 検証器の詳細については、kernel/bpf/verifier.c を参照してください

レジスタ値の追跡¶

eBPF プログラムの安全性を判定するためには、検証器が各レジスタおよび各スタックスロットにおける可能な値の範囲を追跡する必要があります。これは以下の通り行われます struct bpf_reg_state、include/linux/bpf_verifier.h で定義されており、スカラー値とポインタ値の追跡を統合しています。各レジスタ状態にはタイプがあり、NOT_INIT（レジスタに値が未設定）、SCALAR_VALUE（ポインタとして使用できないスカラー値）、またはポインタタイプのいずれかです。ポインタのタイプはベースとなるアドレスを以下のように記述します：

PTR_TO_CTX

bpf_context へのポインタ。

CONST_PTR_TO_MAP

struct bpf_map へのポインタ。『Const』はこれらのポインタに対して算術演算が禁止されているためです。

PTR_TO_MAP_VALUE

マップ要素に格納された値へのポインタ。

PTR_TO_MAP_VALUE_OR_NULL

マップ値へのポインタまたは NULL。マップアクセス（以下の「eBPF マップ」セクションを参照）はこのタイプを返し、NULL でチェックした後は PTR_TO_MAP_VALUE になります。これらのポインタに対して算術演算は禁止されています。

PTR_TO_STACK

フレームポインタ。

PTR_TO_PACKET

skb->data。

PTR_TO_PACKET_END

skb->data + headlen; 算術演算は禁止されています。

PTR_TO_SOCKET

struct bpf_sock_ops へのポインタ、暗黙的に参照カウントされています。

PTR_TO_SOCKET_OR_NULL

ソケットへのポインタまたは NULL。ソケット検索はこのタイプを返し、NULL でチェックした後は PTR_TO_SOCKET になります。PTR_TO_SOCKET は参照カウントされているため、プログラム終了前に socket release 関数を通じて参照を解放する必要があります。これらのポインタに対して算術演算は禁止されています。

ただし、ポインタはこのベースからオフセット（ポインタ算術の結果）を持つ場合があり、これは「固定オフセット」と「変動オフセット」の 2 つの部分で追跡されます。前者は正確にわかっている値（例えば、即値オペランド）がポインタに加算された場合に使用され、後者は正確にわかっていない値の場合に使用されます。変動オフセットは SCALAR_VALUE でも使用され、レジスタ内の可能な値の範囲を追跡します。

検証器が持つ変動オフセットに関する知識は以下の通りです：

  • 符号なしでの最小値と最大値

  • 符号付きでの最小値と最大値

  • 個々のビットの値に関する知識は、「tnum」という形式で表現されます。これはu64型の「mask」とu64型の「value」から成り、maskの1はそのビットの値が未知であることを、valueの1はそのビットが1であることを示します。0であることが確実なビットはmaskとvalueの両方に0が設定され、どちらにも1が設定されることはありません。例えば、メモリからバイトをレジスタに読み込むと、レジスタの上位56ビットは0であることが確実で、下位8ビットは未知となるため、tnumとして(0x0; 0xff)と表されます。この値に0x40をORすると(0x40; 0xbf)となり、その後1を加算すると(0x0; 0x1ff)になります（潜在的なキャリーのため）。

算術演算に加えて、レジスタの状態は条件分岐によっても更新されます。例えばSCALAR_VALUEが8より大きい場合、'true'分岐ではumin_value（符号なし最小値）が9となり、'false'分岐ではumax_value（符号なし最大値）が8になります。符号付き比較（BPF_JSGTやBPF_JSGEを使用）では、符号付きの最小/最大値が更新されます。符号付きと符号なしの境界情報は組み合わせられ、例えば値がまず8未満で次に符号付きで4より大きい場合、検証器はその値が4より大きく符号付きで8未満であると結論付けます（境界が符号境界を越えないため）。

変動オフセットを持つPTR_TO_PACKETは、同じ変動オフセットを持つすべてのポインタに共通する'id'を持ちます。これはパケット範囲チェックにおいて重要です。パケットポインタレジスタAに変数を加算した後、別のレジスタBにコピーし、その後Aに定数4を加算すると、両レジスタは同じ'id'を持ちますが、Aは固定オフセット+4を持つようになります。このときAが境界チェックでPTR_TO_PACKET_END未満であると判定されると、レジスタBは少なくとも4バイトの安全な範囲を持つことが判明します。詳しくは以下の「Direct packet access」セクションをご参照ください。

PTR_TO_MAP_VALUE_OR_NULLの'id'フィールドは、マップ検索から返されたポインタのすべてのコピーに共通して使用されます。これは、1つのコピーがNULLでないことが確認されると、すべてのコピーがPTR_TO_MAP_VALUEになることを意味します。範囲チェックに加えて、追跡情報はポインタアクセスのアライメントを強制するためにも使用されます。たとえば、ほとんどのシステムではパケットポインタが4バイトアライメントの2バイト後にあるため、プログラムがそのポインタに14バイトを加算してイーサネットヘッダを飛び越え、その後IHLを読み込み(IHL * 4)を加算する場合、結果のポインタは4n+2という変動オフセットを持つことがわかっています。この2バイト（NET_IP_ALIGN）を加えることで4バイトアライメントになり、このポインタを通じたワードサイズのアクセスが安全になります。'id'フィールドは、PTR_TO_SOCKETおよびPTR_TO_SOCKET_OR_NULLにも使用され、ソケット検索から返されたポインタのすべてのコピーに共通しています。これはPTR_TO_MAP_VALUE_OR_NULL->PTR_TO_MAP_VALUEの処理と同様の挙動ですが、ポインタの参照トラッキングも処理します。PTR_TO_SOCKETは、対応する参照を暗黙的に表します struct sock参照がリークされないことを確保するため、参照をNULLチェックし、NULLでない場合に有効な参照をソケットリリース関数に渡すことが必須です。

直接的なパケットアクセス¶

cls_bpfおよびact_bpfプログラムでは、検証者がskb->dataおよびskb->data_endポインタを通じてパケットデータへの直接アクセスを許可します。例:

1:  r4 = *(u32 *)(r1 +80)  /* load skb->data_end */
2:  r3 = *(u32 *)(r1 +76)  /* load skb->data */
3:  r5 = r3
4:  r5 += 14
5:  if r5 > r4 goto pc+16
R1=ctx R3=pkt(id=0,off=0,r=14) R4=pkt_end R5=pkt(id=0,off=14,r=14) R10=fp
6:  r0 = *(u16 *)(r3 +12) /* access 12 and 13 bytes of the packet */

この2バイトのロードは、プログラム作者がチェックしたため安全です if (skb->data + 14 > skb->data_end) goto err insn #5で確認されているため、フォールスルーの場合、レジスタR3（skb->dataを指す）には少なくとも14バイトの直接アクセス可能なバイトがあります。検証者はこれをR3=pkt(id=0,off=0,r=14)としてマークします。id=0はレジスタに追加された変数がありません。off=0は追加された定数がありません。r=14は安全なアクセス範囲を意味し、バイト[R3, R3 + 14)がOKです。R5はR5=pkt(id=0,off=14,r=14)としてマークされ、パケットデータを指していますが、定数14がレジスタに追加されたため、現在は skb->data + 14 アクセス可能な範囲は[R5, R5 + 14 - 14)となり、ゼロバイトです。

より複雑なパケットアクセスは次のようになります:

R0=inv1 R1=ctx R3=pkt(id=0,off=0,r=14) R4=pkt_end R5=pkt(id=0,off=14,r=14) R10=fp
6:  r0 = *(u8 *)(r3 +7) /* load 7th byte from the packet */
7:  r4 = *(u8 *)(r3 +12)
8:  r4 *= 14
9:  r3 = *(u32 *)(r1 +76) /* load skb->data */
10:  r3 += r4
11:  r2 = r1
12:  r2 <<= 48
13:  r2 >>= 48
14:  r3 += r2
15:  r2 = r3
16:  r2 += 8
17:  r1 = *(u32 *)(r1 +80) /* load skb->data_end */
18:  if r2 > r1 goto pc+2
R0=inv(id=0,umax_value=255,var_off=(0x0; 0xff)) R1=pkt_end R2=pkt(id=2,off=8,r=8) R3=pkt(id=2,off=0,r=8) R4=inv(id=0,umax_value=3570,var_off=(0x0; 0xfffe)) R5=pkt(id=0,off=14,r=14) R10=fp
19:  r1 = *(u8 *)(r3 +4)

レジスタR3の状態はR3=pkt(id=2,off=0,r=8)です。id=2は2つの r3 += rX インスンスが見られたことを意味し、r3はパケット内のオフセットに指しており、プログラム作者が if (r3 + 8 > r1) goto err インスン #18 では、安全な範囲は [R3, R3 + 8) です。検証器はパケットレジスタに対してのみ 'add'/'sub' 操作を許可しています。他の操作はレジスタの状態を 'SCALAR_VALUE' に設定し、パケットへの直接アクセスはできなくなります。

操作 r3 += rX オーバーフローして元の skb->data よりも小さくなる可能性があるため、検証器はこれを防がなければなりません。そのため、インスンを見たとき r3 += rX がインスンで rX が 16 ビット以上の値である場合、その後の r3 と skb->data_end との境界チェックは範囲情報を提供しないため、ポインタ経由での読み取りは「パケットへの無効なアクセス」エラーになります。

例: インスン r4 = *(u8 *)(r3 +12) (上記インスン #7) では r4 の状態は R4=inv(id=0,umax_value=255,var_off=(0x0; 0xff)) であり、これはレジスタの上位 56 ビットがゼロであることが保証されており、下位 8 ビットについては何も分かっていません。インスン r4 *= 14 の後、状態は R4=inv(id=0,umax_value=3570,var_off=(0x0; 0xfffe)) になります。これは 8 ビット値を定数 14 で乗算すると上位 52 ビットがゼロのままとなり、14 は偶数のため最下位ビットもゼロになるためです。同様に r2 >>= 48 は R2=inv(id=0,umax_value=65535,var_off=(0x0; 0xffff)) になります。シフトは符号拡張を行わないためです。この論理は adjust_reg_min_max_vals() 関数で実装されており、ポインタとスカラーの加算（逆も可）には adjust_ptr_min_max_vals() を、スカラー同士の操作には adjust_scalar_min_max_vals() を呼び出します。

結果として、bpf プログラムの作成者は通常の C コードでパケットを直接アクセスできるようになります:

void *data = (void *)(long)skb->data;
void *data_end = (void *)(long)skb->data_end;
struct eth_hdr *eth = data;
struct iphdr *iph = data + sizeof(*eth);
struct udphdr *udp = data + sizeof(*eth) + sizeof(*iph);

if (data + sizeof(*eth) + sizeof(*iph) + sizeof(*udp) > data_end)
        return 0;
if (eth->h_proto != htons(ETH_P_IP))
        return 0;
if (iph->protocol != IPPROTO_UDP || iph->ihl != 5)
        return 0;
if (udp->dest == 53 || udp->source == 9)
        ...;

これにより、LD_ABS インスンと比較してプログラムの記述が容易になり、大幅に高速化されます。

eBPF マップ¶

‘maps’ は、カーネルとユーザースペース間でデータを共有するための汎用的なストレージです。

マップはユーザースペースから BPF システムコールを介してアクセスされ、コマンドは以下の通りです:

  • 指定されたタイプと属性でマップを作成 map_fd = bpf(BPF_MAP_CREATE, union bpf_attr *attr, u32 size) attr->map_type, attr->key_size, attr->value_size, attr->max_entries を使用して、プロセスローカルのファイル記述子を返すか、負のエラーを返す

  • 指定されたマップ内のキーを検索 err = bpf(BPF_MAP_LOOKUP_ELEM, union bpf_attr *attr, u32 size) attr->map_fd, attr->key, attr->value を使用して、ゼロを返し value に見つかった要素を格納するか、負のエラーを返す

  • 指定されたマップ内のキー/値ペアを作成または更新 err = bpf(BPF_MAP_UPDATE_ELEM, union bpf_attr *attr, u32 size) attr->map_fd, attr->key, attr->value を使用して、ゼロか負のエラーを返す

  • 指定されたマップ内のキーで要素を検索して削除 err = bpf(BPF_MAP_DELETE_ELEM, union bpf_attr *attr, u32 size) attr->map_fd, attr->key を使用して

  • マップを削除するには close(fd) を実行。プロセスの終了時にマップが自動的に削除されます

ユーザースペースプログラムはこのシステムコールを使用して、eBPF プログラムが同時に更新しているマップを操作します。

マップはハッシュ、配列、ブロムフィルタ、ラジックスツリーなど、さまざまなタイプを持つことができます。

マップは以下の通り定義されます:

  • type

  • 最大要素数

  • キーバイト数

  • バイト数

Pruning¶

検証者は、プログラム内のすべての可能なパスを実際に歩くことはありません。新しいブランチを分析する際、検証者はその指令に到達した際にこれまでにあったすべての状態を確認します。これらの状態のうち、現在の状態をサブセットとして含むものが存在する場合、そのブランチは「Pruning（剪定）」されます。つまり、以前の状態が受け入れられたという事実は、現在の状態も受け入れられることを意味します。例えば、以前の状態では r1 がパケットポインタを保持しており、現在の状態では r1 が範囲が長くまたは同じく、かつアライメントがより厳格なパケットポインタを保持している場合、r1 は安全です。同様に、r2 が以前 NOT_INIT だった場合、その時点以降のどのパスも r2 を使用していないため、r2 に存在する値（NOT_INIT を含む）はすべて安全です。この実装は regsafe() 関数にあります。Pruning はレジスタだけでなく、スタック（およびそのスタックに保持される可能性のあるスプレッドレジスタも含む）を考慮します。これらすべてが安全である必要があります。これは states_equal() 関数で実装されています。

テスト¶

BPF ツールチェーンに加えて、カーネルはテストモジュールも提供しており、クラシックおよび内部 BPF のテストケースを BPF インタプリタと JIT コンパイラに対して実行できます。このテストモジュールは lib/test_bpf.c にあり、Kconfig で有効化できます:

CONFIG_TEST_BPF=m

モジュールが構築・インストールされた後、test_bpf モジュールに対して insmod または modprobe を使用してテストスイートを実行できます。テストケースの結果およびナノ秒単位のタイミング情報は、カーネルログ（dmesg）に記録されています。

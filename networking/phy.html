PHY抽象レイヤー¶

目的¶

ほとんどのネットワークデバイスは、MACレイヤーと通信するためのインターフェースを提供するレジスタの集合体で構成されており、このMACレイヤーは物理的な接続を介してPHYと通信します。PHYは、ネットワーク接続の他端にあるリンクパートナー（通常はイーサネットケーブル）とリンクパラメータを交渉し、ドライバが選択した設定を確認し、許可される設定を構成するためのレジスタインターフェースを提供します。

これらのデバイスはネットワークデバイスとは別物であり、レジスタの標準的なレイアウトに準拠していますが、PHY管理コードをネットワークドライバと統合するという慣例が一般的です。これにより、大量の冗長コードが生じています。また、複数の（時にはかなり異なる）イーサネットコントローラーが同じ管理バスに接続されている埋め込みシステムでは、バスの安全な使用を保証するのが困難です。

PHYはデバイスであり、それらをアクセスする管理バスも実際にはバスであるため、PHYアブストラクションレイヤーはそれらをデバイスとして扱います。これにより以下の目標を達成します：

  1. コードの再利用を増やす

  2. 全体のコードのメンテナビリティを向上させる

  3. 新しいネットワークドライバや新しいシステムの開発時間を短縮する

基本的に、このレイヤーはネットワークドライバの開発者に、フルな機能セットを提供しつつ最小限のコードでPHYデバイスにインターフェースを提供することを目的としています。

MDIOバス¶

ほとんどのネットワークデバイスは管理バスを介してPHYに接続されています。異なるデバイスは異なるバス（一部は共通のインターフェースを共有しています）を使用します。PALを活用するためには、各バスインターフェースを別個のデバイスとして登録する必要があります。

  1. 読み込みおよび書き込み関数を実装する必要があります。そのプロトタイプは以下の通りです：

    int write(struct mii_bus *bus, int mii_id, int regnum, u16 value);
int read(struct mii_bus *bus, int mii_id, int regnum);

    mii_idはバス上のPHYのアドレスで、regnumはレジスタ番号です。これらの関数は割込み時間に呼び出されることは保証されていないため、ブロックして割込みが操作完了を通知するのを待つことが安全です。

  2. リセット関数はオプションです。これによりバスが初期化された状態に戻されます。

  3. プローブ関数は必要です。この関数はバスドライバが必要とする設定をセットアップし、mii_bus構造体を設定し、PALにmdiobus_registerを使用して登録する必要があります。同様に、remove関数はすべての操作を逆にするため（mdiobus_unregisterを使用）用意されています。

  4. 他のドライバ同様、device_driver構造体を設定する必要があります。初期化/終了関数を使用してドライバを登録します。

  5. バスはデバイスとしてどこかに宣言され、登録する必要があります。

1つのドライバーがmdioバスドライバーを実装する方法の例として、drivers/net/ethernet/freescale/fsl_pq_mdio.cと、そのユーザーの関連するDTSファイルを参照してください。(例: 「git grep fsl,.*-mdio arch/powerpc/boot/dts/」)

(RG)MII/電気的インターフェースの考慮事項¶

Reduced Gigabit Medium Independent Interface (RGMII) は、同期クロック信号（125MHz）と複数のデータラインを使用する12ピンの電気信号インターフェースです。この設計選択により、クロックライン（RXCまたはTXC）とデータラインの間に1.5nsから2nsの遅延を追加する必要があります。PHY（クロックシンク）がデータラインを正しくサンプリングできるように、十分なセットアップ時間とホールド時間を確保するためです。PHYライブラリは、PHYドライバーおよびオプションでMACドライバーが必要な遅延を実装できるように、さまざまなPHY_INTERFACE_MODE_RGMII*値を提供しています。phy_interface_tの値はPHYデバイス自体の観点から理解する必要があります。以下の通りです:

  • PHY_INTERFACE_MODE_RGMII: PHYは内部遅延を挿入する責任はありません。Ethernet MAC（機能がある場合）またはPCBトレースが正しい1.5-2nsの遅延を挿入することを前提としています。

  • PHY_INTERFACE_MODE_RGMII_TXID: PHYはPHYデバイスで処理される送信データライン（TXD[3:0]）に内部遅延を挿入する必要があります。

  • PHY_INTERFACE_MODE_RGMII_RXID: PHYはPHYデバイスで処理される受信データライン（RXD[3:0]）に内部遅延を挿入する必要があります。

  • PHY_INTERFACE_MODE_RGMII_ID: PHYはPHYデバイスとの送信および受信データラインの両方に内部遅延を挿入する必要があります。

可能な限り、PHY側のRGMII遅延を使用してください。以下の理由があります:

  • PHYデバイスは、受信機/送信機側の遅延をナノ秒以下の粒度で指定できる場合があります（例: 0.5、1.0、1.5ns）。このような精度は、PCBトレース長の違いを補償するために必要となることがあります。

  • PHYデバイスは通常、幅広いアプリケーション（産業、医療、自動車など）に適合しており、温度/圧力/電圧範囲において一定で信頼性の高い遅延を提供します。

  • PHYLIB内のPHYデバイスドライバーは再利用可能な性質を持ち、指定された遅延を正しく設定できるようにすることで、類似の遅延要件を持つ設計が正しく動作できるようになります。

PHYがこの遅延を提供できないが、イーサネットMACドライバーが提供可能な場合、正しいphy_interface_t値はPHY_INTERFACE_MODE_RGMIIでなければなりません。また、イーサネットMACドライバーが要求される送信および/または受信側の遅延をPHYデバイスの観点から提供するように正しく構成される必要があります。逆に、イーサネットMACドライバーがphy_interface_t値を参照する場合、PHY_INTERFACE_MODE_RGMII以外のモードであれば、MACレベルの遅延が無効になっていることを確認する必要があります。

イーサネットMACおよびPHYがRGMII標準で定義された必要な遅延を提供できない場合、いくつかの選択肢が考えられます：

  • 一部のSoCは、ピンの強度、遅延、電圧を設定可能なピンパッド/マトリクス/コントローラーを提供しており、この場合、予想される2nsのRGMII遅延を挿入するための適切な選択肢となる可能性があります。

  • PCB設計を変更して固定遅延（例：特注の蛇行配線を使用）を含める方法もあり、ソフトウェアの設定は一切必要ない場合があります。

RGMII遅延の不一致に関する一般的な問題¶

イーサネットMACとPHY間でRGMII遅延が不一致の場合、PHYまたはMACがこれらの信号をスナップショットを撮って論理1または0に変換し、送信/受信データを再構築する際にクロックおよびデータラインの信号が不安定になる可能性があります。典型的な症状には、

  • 送信/受信が一部機能するが、頻繁または偶発的なパケットロスが観察される

  • イーサネットMACがFCS/CRCエラーを伴うパケットを報告するか、またはすべてを破棄する

  • 10/100Mbits/secなどの低速に切り替えると問題が解消する（その場合、十分なセットアップ/ホールド時間が確保されるため）

PHYへの接続¶

ネットワークドライバーがPHYデバイスとネットワークデバイス間の接続を確立する必要がある場合があります。このとき、PHYのバスおよびドライバーがすべてロードされているので、接続準備が整っています。この時点で、PHYに接続する方法はいくつかあります：

  1. PALがすべてを処理し、リンク状態変化時にのみネットワークドライバーを呼び出すため、反応できます。

  2. PALがすべてを処理しますが、割り込み（通常はコントローラーが割り込みレジスタを持つため）を除きます。

  3. PALがすべてを処理しますが、ドライバーに毎秒確認を行い、PALが反応する前にネットワークドライバーが変化に反応できるようにします。

  4. PALは機能のライブラリとしてのみ機能し、ネットワークデバイスが手動で関数を呼び出してステータスを更新し、PHYを構成します

PHY抽象レイヤーがすべてを行うようにする¶

オプション1を選択した場合（すべてのドライバーが可能であることを願っていますが、まだできないドライバーにも役立つようにするため）、PHYへの接続は簡単です:

まず、リンク状態の変化に反応する関数が必要です。この関数は次のプロトコルに従います:

static void adjust_link(struct net_device *dev);

次に、このデバイスに接続されているPHYのデバイス名を把握する必要があります。名前は「0:00」のように表示され、最初の数字はバスID、2番目の数字はそのバス上のPHYのアドレスを示します。通常、バスは自身のIDを一意にする責任があります。

現在、接続するには、この関数を呼び出してください:

phydev = phy_connect(dev, phy_name, &adjust_link, interface);

phydev これはPHYデバイス構造体へのポインタであり、PHYを表します。phy_connectが成功した場合、このポインタが返されます。devは、あなたのnet_deviceへのポインタです。処理が完了すると、この関数はPHYのソフトウェアステートマシンを開始し、PHYが割り込みを有する場合、その割り込みを登録します。phydev構造体には現在の状態に関する情報が埋め込まれますが、この時点でPHYはまだ完全に動作しています。

phydev->dev_flagsにPHY固有のフラグを設定しておく必要があります。これにより、下位のPHYドライバがフラグを確認し、それに基づいて特定の操作を実行できます。システムがPHY/コントローラーにハードウェア制限を課している場合、PHYがその制限を認識する必要があります。 phy_connect() コントローラーとPHY間の接続タイプを指定するu32です。例としてGMII、MII、RGMII、SGMIIがあります。詳しくは「PHYインターフェースモード」のセクションを参照してください。完全なリストについてはinclude/linux/phy.hを参照してください。

インターフェース phydev->supportedとphydev->advertisingには、あなたのコントローラーにとって意味のない値が含まれていないことを確認してください（例：10/100コントローラーがギガビット対応PHYに接続されている場合、SUPPORTED_1000baseT*をマスクする必要があります）。これらのビットフィールドの定義についてはinclude/linux/ethtool.hを参照してください。注意点として、SUPPORTED_PauseとSUPPORTED_AsymPauseビット以外のビットを設定しないでください（下記を参照）。

最後に、コントローラーがネットワークトラフィックを処理できるようになったら、phy_start(phydev)を呼び出します。これによりPALに準備完了を通知し、PHYがネットワークに接続されるように構成します。ネットワークドライバのMAC割り込みがPHYの状態変化を処理する場合、phy_startを呼び出す前にphydev->irqをPHY_IGNORE_INTERRUPTに設定し、使用してください。

PHYの割り込みを無視する設定を指定する phy_mac_interrupt() ネットワークドライバーから。割り込みを使用したくない場合は、phydev->irq を PHY_POLL に設定してください。 phy_start() PHY 割り込み（必要に応じて）を有効にし、phylib システム状態マシンを開始します。

ネットワークから切断したい場合（一時的でも）、phy_stop(phydev) を呼び出します。この関数は、phylib システム状態マシンを停止し、PHY 割り込みを無効にもします。

PHYインターフェースモード¶

提供された PHY インターフェースモードは、 phy_connect() 関数ファミリは PHY インターフェースの初期動作モードを定義します。これは常に一定とは限りません。ネゴシエーション結果に応じて、ソフトウェアの介入なしにインターフェースモードを動的に変更する PHY も存在します。

インターフェースモードの一部を以下に説明します。

PHY_INTERFACE_MODE_1000BASEX

これは、802.3 標準セクション 36 で定義された 1000BASE-X 単一レーンの serdes リンクを定義します。このリンクは、10B/8B エンコーディング方式を使用して固定ビットレート 1.25Gbaud で動作し、結果としての下位データレートは 1Gbps になります。データストリームに埋め込まれた 16 ビットのコントロールワードは、リモート端と duplex および pause モードを協議するために使用されます。これは 2.5Gbps などの「up-clocked」変種を含みません（下記参照）。

PHY_INTERFACE_MODE_2500BASEX

これは、802.3 標準の 2.5 倍のクロック速度で動作する 1000BASE-X の変種を定義します。固定ビットレートは 3.125Gbaud になります。

PHY_INTERFACE_MODE_SGMII

これは、Cisco SGMII に使用されます。SGMII は、802.3 標準で定義された 1000BASE-X の変種です。SGMII リンクは、10B/8B エンコーディング方式で固定ビットレート 1.25Gbaud で動作する単一の serdes レーンから構成されます。下位データレートは 1Gbps で、100Mbps および 10Mbps の遅い速度は各データシンボルの複製によって達成されます。802.3 コントロールワードは、MAC に交渉された速度と duplex 情報を送信し、MAC が受信を確認するための再利用されます。これは 2.5Gbps などの「up-clocked」変種を含みません。

注意: リンク上の SGMII と 1000BASE-X の設定が一致していない場合、一部の状況ではデータを正常に通過させることができます。ただし、16 ビットのコントロールワードが正しく解釈されない可能性があり、duplex、pause またはその他の設定の不一致を引き起こす可能性があります。これは MAC および/または PHY の動作に依存します。

PHY_INTERFACE_MODE_10GBASER

これは IEEE 802.3 Clause 49 で定義された 10GBASE-R プロトコルで、さまざまな媒体で使用されます。このプロトコルの定義については IEEE 標準を参照してください。

注意: 10GBASE-RはXFIおよびSFIで使用可能なプロトコルの一つにすぎません。XFIおよびSFIは、単一のSERDESラインを介して複数のプロトコルをサポートし、ホストコンプライアンスボードがホストXFP/SFPコネクタに挿さっている場合の信号の電気的特性を定義します。したがって、XFIおよびSFIはそれ自体のPHYインターフェースタイプではありません。

PHY_INTERFACE_MODE_10GKR

これはIEEE 802.3 Clause 49で定義された10GBASE-Rで、Clause 73のオートネゴシエーションを組み合わせたものです。詳細についてはIEEEの標準をご参照ください。

注意: 既存の使用方法のため、一部の10GBASE-Rの使用はこの定義を誤って利用しています。

パーズフレーム / フロー制御¶

PHYはフロー制御/パーズフレームの直接的な参加は行いませんが、MII_ADVERTISEにSUPPORTED_PauseおよびSUPPORTED_AsymPauseビットを設定することにより、リンクパートナーに対してイーサネットMACコントローラーがその機能をサポートしていることを示します。フロー制御/パーズフレームの生成はイーサネットMACドライバの責任であり、このドライバがSUPPORTED_PauseおよびSUPPORTED_AsymPauseビットを適切に設定することにより、機能の広告およびサポートを正しく示す必要があります。これは、ethtool::set_pauseparam機能の実装の前後またはその結果として行われることができます。 phy_connect() and/or as a result of implementing the ethtool::set_pauseparam feature.

PALを常に確認する¶

PALの組み込みステートマシンがネットワークデバイスとPHYを正しく同期させるために少しの手助けが必要な場合があります。その場合は、PHYに接続する際にヘルパーファンクションを登録できます。このファンクションは、ステートマシンが変更に反応する前に毎秒呼び出されます。これを実行するには、手動で phy_attach() および phy_prepare_link(), そして phy_start_machine() を呼び出す必要があります。この際、第二引数はあなたの特別なハンドラを指すように設定してください。

現在、この機能の使用方法に関する例は存在せず、テストも限られています。著者はこの機能を使用するドライバを持っていないためです（すべてのドライバはオプション1を使用しています）。自己責任でお願いします。

すべて自分で行う¶

PALの組み込みステートマシンがPHYとあなたのネットワークデバイス間の複雑な相互作用を追跡できない可能性があります。その場合は、単に phy_attach()を呼び出し、phy_start_machineまたは phy_prepare_link()を呼び込まないことが可能です。これにより、phydev->stateはすべてあなたの責任になります（phy_startとphy_stopはいくつかの状態を切り替えるため、避けなければならない可能性があります）。

有用な機能にアクセスするためにはステートマシンの実行が不要であるようにするための努力がなされており、これらの関数の多くは複雑なステートマシンと相互作用しない関数から派生しています。ただし、ステートマシンなしで実行するテストについてはこれまでのところ行いませんでしたので、試してくださる方は自己責任でお願いします。

以下に機能の簡単な概要を示します:

int phy_read(struct phy_device *phydev, u16 regnum);
int phy_write(struct phy_device *phydev, u16 regnum, u16 val);

シンプルな読み込み/書き込みプリミティブ。これらはバスの読み込み/書き込み関数ポインタを呼び出します。

void phy_print_status(struct phy_device *phydev);

PHYの状態を整然と出力するための便利な関数。

void phy_request_interrupt(struct phy_device *phydev);

PHY割込み用のIRQを要求します。

struct phy_device * phy_attach(struct net_device *dev, const char *phy_id,
                               phy_interface_t interface);

ネットワークデバイスを特定のPHYに接続し、バス初期化時にドライバーが見つからなかった場合、PHYを汎用ドライバーにバインドします。

int phy_start_aneg(struct phy_device *phydev);

phydev構造体内の変数を使用して、広告設定や自動交渉の再設定を行うか、自動交渉を無効化し、強制設定を構成します。

static inline int phy_read_status(struct phy_device *phydev);

phydev構造体に現在のPHY設定の最新情報を埋め込みます。

int phy_ethtool_ksettings_set(struct phy_device *phydev,
                              const struct ethtool_link_ksettings *cmd);

Ethtoolの便利な関数。

int phy_mii_ioctl(struct phy_device *phydev,
                  struct mii_ioctl_data *mii_data, int cmd);

MII ioctl。注意: この関数はBMCR、BMSR、ADVERTISEなど、レジスタを書き込むと状態機械を完全に破壊する可能性があります。標準でないレジスタのみに使用するべきです。再交渉を引き起こさないレジスタに限定してください。

PHYデバイスドライバ¶

PHY抽象レイヤーにより、新しいPHYのサポートを追加するのは非常に簡単です。一部のケースではまったく作業が不要です！ただし、多くのPHYは少し手助けが必要です。

汎用PHYドライバー¶

望むPHYにエラタやクイア、サポートしたい特殊機能がなければ、サポートを追加せず、PHY抽象レイヤーの汎用PHYドライバーにすべての作業を任せた方が良いでしょう。

PHYドライバーの作成¶

PHYドライバーを作成する場合は、まず適切なPHYデバイスとマッチできるようにする必要があります。これはバス初期化中にデバイスのUID（レジスタ2および3に保存）を読み取り、各ドライバーのphy_idフィールドとAND演算で比較します。また、名前も必要です。例:

static struct phy_driver dm9161_driver = {
      .phy_id         = 0x0181b880,
      .name           = "Davicom DM9161E",
      .phy_id_mask    = 0x0ffffff0,
      ...
}

次に、PHYデバイスとドライバーがサポートする機能（速度、双方向通信、自動交渉など）を指定する必要があります。ほとんどのPHYはPHY_BASIC_FEATURESをサポートしますが、include/mii.hで他の機能を確認できます。

各ドライバーは、include/linux/phy.hにあるphy_driver構造体で記述される関数ポインタの数を含みます。

これらの中でも、config_anegとread_statusはドライバーコードによって必ず割り当てなければなりません。他の関数はオプションです。できれば、genphy_read_statusとgenphy_config_anegという汎用PHYドライバーのバージョンを使用してください。不可能な場合は、これらの関数を呼び出す前後でいくつかの処理を行うだけかもしれません。そのため、あなたの関数は汎用関数をラップする形になります。

ご自由に確認してください。drivers/net/phy/に記載されているMarvell、Cicada、Davicomドライバの例をご参照ください（lxtおよびqsemiドライバは執筆時点ではテストされていません）。

PHYのMMDレジスタアクセスは、デフォルトではPALフレームワークによって処理されます。ただし、特定のPHYドライバが要求される場合、この処理はオーバーライド可能です。これは、MMD PHYレジスタ定義がIEEEによって標準化される前の製品が製造に投入された場合に該当します。ほとんどの現代のPHYは、一般的なPALフレームワークを使用してMMDレジスタにアクセスできます。このような使用例として、Energy Efficient Ethernet（EEE）のサポートがあります。このサポートはPALを介して、EEEのクエリおよび設定に必要なMMDレジスタにアクセスします。PHYがIEEE標準のアクセスメカニズムをサポートする場合、または特定のPHYドライバによってオーバーライドされた場合、PHYの特定のアクセスインターフェースを使用できます。drivers/net/phy/に記載されているMicrelドライバを参照してください。

ボードの修正¶

場合によっては、プラットフォームとPHY間の特定の相互作用に特別な処理が必要です。例えば、PHYのクロック入力の位置を変更する場合、またはデータパスにおけるレイテンシーの問題を補償するための遅延を追加する場合です。このような緊急事態をサポートするため、PHYレイヤーはプラットフォームコードがPHYを起動（またはその後のリセット）時に実行するfixupを登録できるようにします。

PHYレイヤーがPHYを起動する際、UID（PHYデバイスのphy_idフィールドに含まれる）とバス識別子（phydev->dev.bus_idに含まれる）に基づいて登録されたfixupが存在するか確認します。両方の条件が一致する必要がありますが、バスIDおよびUIDにはそれぞれPHY_ANY_IDとPHY_ANY_UIDというワイルドカードが提供されています。

一致が見つかった場合、PHYレイヤーは関連するfixupのrun関数を呼び出します。この関数には、対象のphy_deviceへのポインタが渡されるため、この関数は指定されたPHYに対してのみ動作する必要があります。

プラットフォームコードは、以下のいずれかを使用してfixupを登録できます phy_register_fixup():

int phy_register_fixup(const char *phy_id,
        u32 phy_uid, u32 phy_uid_mask,
        int (*run)(struct phy_device *));

または、phy_register_fixup_for_uid()およびphy_register_fixup_for_id()のいずれかのスタブを使用します：

int phy_register_fixup_for_uid(u32 phy_uid, u32 phy_uid_mask,
               int (*run)(struct phy_device *));
int phy_register_fixup_for_id(const char *phy_id,
               int (*run)(struct phy_device *));

スタブは、2つのマッチング基準のうちの1つを設定し、もう1つは任意の値を許容するよう設定します。

が呼ばれるとき、modprobeは phy_register_fixup() モジュールロード時に*_for_uid()/*_for_id()が呼び出された場合、モジュールがアンロードされるときにfixupをアンレジスターし、割り当てられたメモリを解放する必要があります。

モジュールをアンロードする前に、以下の関数のいずれかを呼び出してください：

int phy_unregister_fixup(const char *phy_id, u32 phy_uid, u32 phy_uid_mask);
int phy_unregister_fixup_for_uid(u32 phy_uid, u32 phy_uid_mask);
int phy_register_fixup_for_id(const char *phy_id);

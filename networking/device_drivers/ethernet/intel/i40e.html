アダプターの特定¶

ドライバは以下のデバイスベースドのデバイスと互換性があります：

  • Intel(R) Ethernet Controller X710

  • Intel(R) Ethernet Controller XL710

  • Intel(R) Ethernet Network Connection X722

  • Intel(R) Ethernet Controller XXV710

最高のパフォーマンスを確保するには、デバイスに最新のNVM/FWがインストールされていることを確認してください。

アダプターの識別方法や最新のNVM/FWイメージ、Intelネットワークドライバーについては、Intelサポートウェブサイトを参照してください： https://www.intel.com/support

SFP+ and QSFP+ Devices¶

サポートされているメディアについての情報は、このドキュメントを参照してください： https://www.intel.com/content/dam/www/public/us/en/documents/release-notes/xl710-ethernet-controller-feature-matrix.pdf

注意：一部のIntel(R) Ethernet Controller 700 Seriesベースのアダプターは、Intel Ethernet Opticsモジュールのみをサポートしています。これらのアダプターでは、他のモジュールはサポートされず、動作しません。すべての場合において、IntelはIntel Ethernet Opticsの使用を推奨しています。他のモジュールは動作する可能性がありますが、Intelによる検証されていません。サポートされているメディアタイプについてはIntelにご連絡ください。

注意：Intel(R) Ethernet Controller 700 Seriesベースの接続では、サポートはシステムボードに依存します。詳細については、ベンダーにご確認ください。

注意：アダプターおよび光学モジュールの十分な空気の流れが得られないシステムでは、高温度光学モジュールを使用する必要があります。

仮想ファンクション(VFs)¶

sysfsを使用してVFを有効化します。たとえば：

#echo $num_vf_enabled > /sys/class/net/$dev/device/sriov_numvfs #enable VFs
#echo 0 > /sys/class/net/$dev/device/sriov_numvfs #disable VFs

たとえば、以下の手順はPF eth0とVLAN 10上の最初のVFを設定します：

$ ip link set dev eth0 vf 0 vlan 10

VLANタグパケットステアリング¶

特定のVLANタグを持つすべてのパケットを特定のSR-IOV仮想機能(VF)に送信できるようにします。さらに、この機能は特定のVFを信頼できるものとして指定でき、その信頼できるVFが物理機能(PF)上で選択的な混雑モードを要求できるようにします。

ハイパーバイザに以下のコマンドを入力して、VFを信頼できるか信頼できないか設定してください。

# ip link set dev eth0 vf 1 trust [on|off]

VFが信頼できると指定された後、VMで以下のコマンドを使用してVFを混雑モードに設定してください。

For promiscuous all:
#ip link set eth2 promisc on
Where eth2 is a VF interface in the VM

For promiscuous Multicast:
#ip link set eth2 allmulticast on
Where eth2 is a VF interface in the VM

注意: 既定では、ethtoolのpriv-flag vf-true-promisc-supportは「off」に設定されており、VFのプロミスカスモードは制限されます。VFのプロミスカスモードを真のプロミスカスモードに設定し、VFがすべてのイングレストラフィックを確認できるようにするには、以下のコマンドを使用してください:

#ethtool -set-priv-flags p261p1 vf-true-promisc-support on

vf-true-promisc-support priv-flagはプロミスカスモードを有効化するものではなく、上記のip linkコマンドでプロミスカスモードを有効化した際に得られるプロミスカスモードの種類（制限付きまたは真のプロミスカスモード）を指定します。注意として、これはデバイス全体に影響するグローバルな設定ですが、vf-true-promisc-support priv-flagはデバイスの最初のPFのみに露出しています。PFはvf-true-promisc-supportの設定に関係なく、制限付きプロミスカスモード（MFPモードの場合は除く）のままです。

VFインターフェースにVLANインターフェースを追加してください:

#ip link add link eth2 name eth2.100 type vlan id 100

VFをプロミスカスモードに設定し、VLANインターフェースを追加する順序は重要ではありません（どちらを先に実行しても構いません）。この例の最終的な結果として、VFはVLAN 100にタグ付けされたすべてのトラフィックを確認します。

Intel(R) Ethernet Flow Director¶

Intel Ethernet Flow Directorは以下のタスクを実行します:

  • 受信パケットをフローごとに異なるキューにリダイレクトします。

  • プラットフォーム内でフローをルーティングする際の厳密な制御を可能にします。

  • フローとCPUコアをフローのアフィニティにマッチングします。

  • L3およびL4フロータイプでの柔軟なフロー分類とロードバランシングをサポートします（SFPモードでのみ有効）。

注意: Linux i40eドライバはIPv4、TCPv4、UDPv4の3種類のフロータイプをサポートします。特定のフロータイプに対しては、IPアドレス（送信元または送信先）とUDP/TCPポート（送信元および送信先）の有効な組み合わせをサポートします。たとえば、送信元IPアドレスのみ、送信元IPアドレスと送信先ポート、またはこれらの4つのパラメータのいずれか1つ以上の組み合わせを指定できます。

注意: Linux i40eドライバは、ethtoolのuser-defおよびmaskフィールドを使用して、ユーザー定義の柔軟な2バイトパターンとオフセットに基づいたトラフィックフィルタリングを許可します。ユーザー定義の柔軟なフィルタはL3およびL4フロータイプのみをサポートします。特定のフロータイプに対しては、入力セット（そのフロータイプに関するもの）を変更する前に、すべてのIntel Ethernet Flow Directorフィルタをクリアする必要があります。

Intel Ethernet Flow Directorを有効化または無効化するには:

# ethtool -K ethX ntuple <on|off>

ntupleフィルタを無効化する際には、すべてのユーザーが設定したフィルタがドライバキャッシュおよびハードウェアから削除されます。ntupleを再有効化する際には、すべての必要なフィルタを再追加する必要があります。

パケットをキュー2にリダイレクトするフィルタを追加するには、-Uまたは-Nスイッチを使用してください:

# ethtool -N ethX flow-type tcp4 src-ip 192.168.10.1 dst-ip \
192.168.10.2 src-port 2000 dst-port 2001 action 2 [loc 1]

送信元および送信先IPアドレスのみを使用してフィルタを設定するには:

# ethtool -N ethX flow-type tcp4 src-ip 192.168.10.1 dst-ip \
192.168.10.2 action 2 [loc 1]

現在のフィルタの一覧を確認するには:

# ethtool <-u|-n> ethX

アプリケーションターゲットルーティング(ATR) パーフェクトフィルタ¶

カーネルが複数送信キューモードにある場合、ATRはデフォルトで有効になります。TCP-IPフローが開始されるとATR Intel Ethernet Flow Directorフィルタールールが追加され、フローが終了すると削除されます。ethtool（サイドバンドフィルター）からTCP-IP Intel Ethernet Flow Directorルールが追加される場合、ドライバがATRを無効化します。ATRを再有効にするには、ethtool -Kオプションでサイドバンドを無効化します。例えば：

ethtool –K [adapter] ntuple [off|on]

ATRが再有効になってからサイドバンドを再有効にしても、ATRはTCP-IPフローが追加されるまで有効のままです。すべてのTCP-IPサイドバンドルールが削除されると、ATRは自動的に再有効になります。

ATRルールに一致するパケットは、ethtoolのfdir_atr_match statsでカウントされ、これによりATRルールがまだ存在しているかを確認することもできます。

サイドバンドパーフェクトフィルタ¶

サイドバンドパーフェクトフィルタは、指定された特徴に一致するトラフィックを制御するために使用されます。これらはethtoolのntupleインターフェースを通じて有効化されます。新しいフィルターを追加するには、次のコマンドを使用します：

ethtool -U <device> flow-type <type> src-ip <ip> dst-ip <ip> src-port <port> \
dst-port <port> action <queue>
以下では:

<device> - プログラムするイーサネットデバイス <type> - ip4、tcp4、udp4、またはsctp4のいずれか <ip> - マッチするIPアドレス <port> - マッチするポート番号 <queue> - トラフィックを誘導するキュー（-1は一致するトラフィックを破棄）

アクティブなすべてのフィルターを表示するには、次のコマンドを使用します：

ethtool -u <device>

フィルターを削除するには、次のコマンドを使用します：

ethtool -U <device> delete <N>

<N>はすべてのアクティブなフィルターを印刷した際に表示されるフィルターIDであり、フィルターを追加する際に「loc <N>」で指定した場合にも使用できます。

次の例は、192.168.0.1から送信され、ポート5300で、192.168.0.5に送信され、ポート80で、キュー7に誘導されるTCPトラフィックをマッチさせます：

ethtool -U enp130s0 flow-type tcp4 src-ip 192.168.0.1 dst-ip 192.168.0.5 \
src-port 5300 dst-port 80 action 7

各フローティプーごとに、プログラムされたフィルターはすべて同じマッチング入力セットを必要とします。たとえば、次の2つのコマンドを実行することは問題ありません：

ethtool -U enp130s0 flow-type ip4 src-ip 192.168.0.1 src-port 5300 action 7
ethtool -U enp130s0 flow-type ip4 src-ip 192.168.0.5 src-port 55 action 10

しかし、次の2つのコマンドを実行すると、最初のコマンドがsrc-ipを指定し、2番目のコマンドがdst-ipを指定しているため、受け入れられません：

ethtool -U enp130s0 flow-type ip4 src-ip 192.168.0.1 src-port 5300 action 7
ethtool -U enp130s0 flow-type ip4 dst-ip 192.168.0.5 src-port 55 action 10

2番目のコマンドはエラーで失敗します。同じフィールドで異なる値を使用して複数のフィルターをプログラムすることは可能ですが、1つのデバイスでは、異なるマッチングフィールドを持つ2つのtcp4フィルターをプログラムすることはできません。

i40eドライバは、フィールドのサブセクションでのマッチングをサポートしていませんため、部分マスクフィールドはサポートされていません。

ドライバは、パケットペイロード内のユーザー定義データのマッチングもサポートしています。この柔軟なデータは、ethtoolコマンドの「user-def」フィールドを使用して次のように指定します：

31 28 24 20 16

15 12 8 4 0

パケットペイロード内のオフセット

2バイトの柔軟なデータ

例えば、

... user-def 0x4FFFF ...

フィルタがペイロードの4バイト先を参照し、その値を0xFFFFと照合するように指定します。オフセットはペイロードの開始位置に基づき、パケットの開始位置ではなく設定されます。したがって

flow-type tcp4 ... user-def 0x8BEAF ...

TCP/IPv4ペイロードの8バイト先に0xBEAFが存在するTCP/IPv4パケットに一致します。

ICMPヘッダーは4バイトのヘッダーと4バイトのペイロードとして解析されます。したがって、ペイロードの最初のバイトに一致させるには、オフセットに4バイトを加える必要があります。また、ip4フィルタはICMPフレームだけでなく、raw（未定義）ip4フレームにも一致します。この場合、ペイロードはIP4フレームのL3ペイロードになります。

最大オフセットは64です。ハードウェアはペイロードから最大64バイトのデータを読み取ります。オフセットは偶数でなければなりません。なぜなら、フレキシブルデータは2バイト長であり、パケットペイロードのバイト0にアライメントする必要があるからです。

ユーザー定義のフレキシブルオフセットは入力セットの一部とみなされ、同じタイプの複数のフィルタで個別に設定することはできません。ただし、フレキシブルデータは入力セットに含まれず、複数のフィルタが同じオフセットを使用しても異なるデータに一致することができるため、複数のフィルタで同じオフセットを共有できます。

特定の仮想ファンクションにトラフィックをリダイレクトするフィルタを作成するには、「action」パラメータを使用します。アクションを64ビットの値として指定し、下位32ビットがキュー番号を、次に8ビットがVFを表します。注意点として、0はPF（物理ファンクション）であり、VF識別子は1オフセットされています。例えば：

... action 0x800000002 ...

仮想ファンクション7（8から1を引いた値）にトラフィックを、そのVFのキュー2にリダイレクトします。

これらのフィルタは内部ルーティングルールを破壊せず、指定された仮想ファンクションに送信されないはずだったトラフィックをルーティングしません。

リンクダウンオンクローズプライベートフラグの設定¶

リンクダウンオンクローズプライベートフラグが「on」に設定されている場合、ifconfig ethX downコマンドでインターフェースをダウンにした際にポートのリンクがダウンします。

ethtoolを使用してリンクダウンオンクローズを表示および設定します。以下のように：

ethtool --show-priv-flags ethX
ethtool --set-priv-flags ethX link-down-on-close [on|off]

リンクメッセージの表示¶

ディストリビューションがシステムメッセージを制限している場合、リンクメッセージはコンソールに表示されません。ネットワークドライバーリンクメッセージをコンソールで確認するには、次のコマンドを入力してdmesgを8に設定してください：

dmesg -n 8

注意：この設定は再起動後に保持されません。

ジャンボフレーム¶

ジャンボフレームのサポートは、最大送信ユニット（MTU）をデフォルト値1500より大きい値に変更することで有効になります。

ifconfigコマンドを使用してMTUサイズを増やすことができます。例えば、<x>はインターフェース番号で、以下のコマンドを入力してください:

ifconfig eth<x> mtu 9000 up

代わりに、ipコマンドを使用することもできます:

ip link set mtu 9000 dev eth<x>
ip link set up dev eth<x>

この設定は再起動時に保持されません。設定変更を永続化するには、以下のファイルに'MTU=9000'を追加してください:

/etc/sysconfig/network-scripts/ifcfg-eth<x> // for RHEL
/etc/sysconfig/network/<config_file> // for SLES

注意：Jumboフレームの最大MTU設定は9702です。これはJumboフレームの最大サイズ9728バイトに一致します。

注意: このドライバーは、ジャンボパケットを受信する際に複数のページサイズのバッファを試行します。これにより、受信パケットの割当時にバッファの枯渇問題を回避するのに役立ちます。

ethtool¶

ドライバーはethtoolインターフェースを使用してドライバーの設定および診断、統計情報の表示を行います。この機能には最新のethtoolバージョンが必要です。ダウンロードはこちら: https://www.kernel.org/pub/software/network/ethtool/

ethtoolコマンドおよびフィルタリングオプションのサポート¶

-n –show-nfc

受信ネットワークフロー分類構成を取得します。

rx-flow-hash tcp4|udp4|ah4|esp4|sctp4|tcp6|udp6|ah6|esp6|sctp6

指定されたネットワークトラフィックタイプのハッシュオプションを取得します。

速度とフル デュプレックス設定¶

速度と双方向通信の設定に関する問題を解決する際には、銅ベースのアダプターとファイバーベースのアダプターを区別する必要があります。

デフォルトモードでは、銅ベースのIntel(R) エスネットワークアダプターはリンクパートナーと自動交渉を行い、最適な設定を決定します。アダプターが自動交渉でリンクパートナーとリンクを確立できない場合、アダプターとリンクパートナーの設定を同一に手動で設定する必要があります。これは、自動交済をサポートしていない古いスイッチや、特定の速度または双方向通信モードに強制されたスイッチとリンクを確立する場合にのみ必要です。リンクパートナーは選択した設定と一致する必要があります。1 Gbps以上の速度は強制できません。1 Gbps以上を手動で設定するには、自動交渉の広告設定を使用してください。

注意：Intel(R) Ethernet Network Adapter XXV710ベースのデバイスでは、速度を設定することはできません。

速度、双方向通信、自動交渉の広告設定はethtoolユーティリティを通じて設定されます。

注意: 速度と双方向通信の強制や自動交渉の広告設定の変更は、経験豊富なネットワーク管理者のみが行うべきです。スイッチの設定は常にアダプターの設定と一致する必要があります。アダプターのパフォーマンスが低下するか、アダプターが正常に動作しなくなる可能性があります。

ファイバーベースの接続を使用するIntel(R) エスネットワークアダプターは、リンクパートナーと自動交渉を行いません。これらのアダプターはフルダブルクォーテーションで動作し、ネイティブ速度のみで動作します。

NAPI¶

NAPI（Rxポーリングモード）はi40eドライバでサポートされています。NAPIについての詳細情報は以下を参照してください。 https://wiki.linuxfoundation.org/networking/napi

フロー制御¶

イーサネットフロー制御（IEEE 802.3x）はethtoolを使用して、i40eで受信および送信のパーズフレームを有効化する設定が可能です。送信が有効な場合、受信パケットバッファが事前に定義されたしきい値を超えるとパーズフレームが生成されます。受信が有効な場合、送信ユニットは受信されたパーズフレームに指定された時間遅延分停止します。

注意: フローコントロールをサポートするリンクパートナーを保有している必要があります。

フローコントロールはデフォルトで有効になっています。

ethtoolを使用してフローコントロールの設定を変更してください。

受信（Rx）または送信（Tx）フローコントロールを有効にするか無効にするには、

ethtool -A eth? rx <on|off> tx <on|off>

注意: このコマンドは自動交渉が無効になっている場合にのみフローコントロールを有効または無効にします。自動交渉が有効な場合、このコマンドはリンクパートナーとの自動交渉に使用されるパラメータを変更します。

自動交渉を有効にするか無効にするには、

ethtool -s eth? autoneg <on|off>

注意: フローコントロール自動交渉はリンク自動交渉の一部です。デバイスによっては自動交渉設定を変更できない場合があります。

RSSハッシュフロー¶

受信側スケーリング（RSS）ハッシュバイトの設定に、フローティプごとのハッシュバイト数を設定し、1つまたは複数のオプションの組み合わせを指定できます。

# ethtool -N <dev> rx-flow-hash <type> <option>
＜type＞は次の通りです：

tcp4 は IPv4上でのTCP、udp4 は IPv4上でのUDP、tcp6 は IPv6上でのTCP、udp6 は IPv6上でのUDPを表します。

＜option＞は次の1つまたは複数です：

s RxパケットのIPソースアドレスにハッシュをかけます。d RxパケットのIP宛先アドレスにハッシュをかけます。f Layer4ヘッダーのバイト0および1にハッシュをかけます。n Layer4ヘッダーのバイト2および3にハッシュをかけます。

MACおよびVLANアンチスプーフィング機能¶

悪意のあるドライバーがスプーフィングパケットを送信しようとした場合、ハードウェアによってそのパケットが破棄されません。注意: この機能は特定の仮想機能（VF）に対して無効にすることができます：

ip link set <pf dev> vf <vf id> spoofchk {off|on}

IEEE 1588高精度時刻プロトコル（PTP）ハードウェア時計（PHC）¶

高精度時刻プロトコル（PTP）はコンピュータネットワーク内の時計を同期するために使用されます。PTPのサポートはIntelデバイスによって異なります。デバイスがサポートするPTP機能の詳細なリストは、「ethtool -T <netdev名>」を使用してください。

IEEE 802.1ad（QinQ）サポート¶

IEEE 802.1ad標準は、非公式にQinQと呼ばれるもので、1つのイーサネットフレーム内で複数のVLAN IDをサポートします。VLAN IDはしばしば「タグ」と呼ばれるため、複数のVLAN IDは「タグスタック」と呼ばれます。タグスタックはL2トンネリングを可能にし、特定のVLAN ID内でトラフィックを分離するなどの用途があります。

以下の例は、802.1ad（QinQ）の設定方法です：

ip link add link eth0 eth0.24 type vlan proto 802.1ad id 24
ip link add link eth0.24 eth0.24.371 type vlan proto 802.1Q id 371

ここで「24」と「371」は例としてのVLAN IDです。

ノート：

802.1ad (QinQ)パケットには、受信チェックサムオフロード、クラウドフィルタ、VLAN加速がサポートされません。

VXLANおよびGENEVEオーバーレイハードウェアオフローディング¶

仮想拡張LAN (VXLAN)は、L2ネットワークをL3ネットワーク上に拡張する機能を提供し、仮想化された環境やクラウド環境で有用です。一部のIntel(R) EthernetネットワークデバイスはVXLAN処理を実行し、オペレーティングシステムからオフロードします。これによりCPUの利用率が低下します。

VXLANオフローディングは、ethtoolが提供するTxおよびRxチェックサムオフロードオプションによって制御されます。つまり、Txチェックサムオフロードが有効で、アダプターがその機能をサポートしている場合、VXLANオフローディングも有効になります。

VXLANおよびGENEVEハードウェアオフローディングのサポートは、カーネルがハードウェアオフローディング機能をサポートしているかどうかに依存します。

ポートごとの複数機能¶

Intel EthernetコントローラーX710/XL710ベースの一部のアダプターは、単一の物理ポートで複数の機能をサポートします。これらの機能はシステム設定/BIOSを通じて設定します。

最小TX帯域幅は、物理ポートリンク速度の百分率として、パーティションが受信する保証された最小データ送信帯域幅です。パーティションが獲得する帯域幅は、指定したレベルを下回ることはありません。

最小帯域幅値の範囲は：1から((100－物理ポート上のパーティション数)＋1)です。たとえば、物理ポートに4つのパーティションがある場合、範囲は：1から((100－4)＋1＝97)になります。

最大帯域幅百分率は、パーティションに割り当てられる最大送信帯域幅を、物理ポートリンク速度の百分率で表します。許容される値の範囲は1〜100です。この値は、特定の機能がポートの帯域幅の100%を消費しないようにする制限として使用されます。最大帯域幅のすべての値の合計には制限がありません。なぜなら、ポートの帯域幅は常に100%を超えることはないからです。

注意：X710/XXV710デバイスは、ポートごとの複数機能(MFP)とSR-IOVが有効になっている場合、最大VF(64)を有効にすることができません。i40eからエラーがログに記録され、「VF Nのvsic追加に失敗しました、aq_err 16」と表示されます。この問題を回避するには、64未満の仮想機能(VF)を有効にします。

データセンターブリッジング (DCB)¶

DCBはハードウェアでの品質保証（Quality of Service）の実装です。VLANプライオリティタグ（802.1p）を使用してトラフィックをフィルタリングします。これにより、トラフィックは8つの異なる優先度にフィルタリングされます。また、優先度フロー制御（802.1Qbb）も有効化され、ネットワークのストレス時にドロップされるパケット数を制限または完全に防止できます。帯域幅はこれらの優先度ごとに割り当てられ、ハードウェアレベルで強制されます（802.1Qaz）。

アダプタファームウェアは、802.1ABおよび803.1Qazに従ってLLDPおよびDCBXプロトコルエージェントを実装します。ファームウェアベースのDCBXエージェントはワイリングモードのみで動作し、DCBX対応のペアから設定を受けることができます。ソフトウェアによるDCBXパラメータの設定（dcbtool/lldptool経由）はサポートされていません。

注意: ファイアウォールLLDPを無効にするには、プライベートフラグ disable-fw-lldp を設定します。

i40eドライバはDCBネットリンクインターフェースレイヤーを実装し、ユーザー空間がドライバと通信し、ポートのDCB設定を照会できるようにします。

注意: カーネルはTC0が利用可能であることを前提とし、TC0が利用不可の場合、デバイスで優先度フロー制御（PFC）を無効化します。この問題を修正するには、スイッチでDCBを設定する際、TC0が有効になっていることを確認してください。

割り込みレート制限¶

有効な範囲

0-235（0＝制限なし）

Intel(R) Ethernet Controller XL710ファミリは割り込みレート制限メカニズムをサポートしています。ユーザーはethtoolを介して、割り込み間のマイクロ秒数を制御できます。

構文:

# ethtool -C ethX rx-usecs-high N

0-235マイクロ秒の範囲は、4,310から250,000個の秒あたり割り込みに相当します。rx-usecs-highの値は、同じethtoolコマンド内でrx-usecsおよびtx-usecsとは独立して設定でき、アダプティブ割り込みモジュレーションアルゴリズムとも独立しています。基盤となるハードウェアは4マイクロ秒間隔での粒度をサポートしているため、隣接する値は同じ割り込みレートを生成する可能性があります。

以下の使用例が考えられます:

# ethtool -C ethX adaptive-rx off adaptive-tx off rx-usecs-high 20 rx-usecs \
  5 tx-usecs 5

上記のコマンドはアダプティブ割り込みモジュレーションを無効化し、受信または送信完了を示すために最大5マイクロ秒を許容します。しかし、秒あたり200,000個の割り込みを生じるのではなく、rx-usecs-highパラメータにより秒あたり50,000個の割り込みに制限します。

パフォーマンスの最適化¶

ドライバのデフォルト値は幅広いワークロードに適していますが、さらに最適化が必要な場合は、以下の設定を試すことをお勧めします。

注意: 小さなフレームサイズ（64B）を処理する際のパフォーマンス向上のために、BIOSでHyper-threadingを有効にして、システム内の論理コア数を増やすことで、アダプターに利用可能なキュー数を増やすことを試してください。

仮想化環境¶

1. 両端でXPSを無効にするには、含まれているvirt_perf_defaultスクリプトを使用するか、以下のコマンドをrootとして実行してください:

for file in `ls /sys/class/net/<ethX>/queues/tx-*/xps_cpus`;
do echo 0 > $file; done

2. vm内での適切なメカニズム（vcpupin）を使用し、CPUを個々のlcpuにピン固定してください。deviceのlocal_cpulist（/sys/class/net/<ethX>/device/local_cpulist）に含まれるCPUセットを使用してください。

3. VMで利用可能なRx/Txキュー数を最大に設定してください。デフォルト設定の1に依存しないでください。

非仮想化環境¶

irqbalanceサービスを無効にして、含まれているset_irq_affinityスクリプトを使用して、アダプターのIRQを特定のコアにピン固定してください。詳細なオプションについてはスクリプトのヘルプテキストを参照してください。

  • 以下の設定は、IRQをすべてのコアに均等に分散します:

    # scripts/set_irq_affinity -x all <interface1> , [ <interface2>, ... ]

  • 以下の設定は、アダプター（同じNUMAノード）にローカルなコアにIRQを分散します:

    # scripts/set_irq_affinity -x local <interface1> ,[ <interface2>, ... ]

非常にCPU負荷の高いワークロードの場合、IRQをすべてのコアにピン固定することをお勧めします。

IPフォワーディングの場合: Adaptive ITRを無効にして、ethtoolを使用してRxおよびTxのキューごとの割り込みを低減してください。

  • rx-usecsおよびtx-usecsを125に設定すると、キューごとに約8000回の割り込みに制限されます。

# ethtool -C <interface> adaptive-rx off adaptive-tx off rx-usecs 125 \
  tx-usecs 125

CPU利用率を低減する場合: Adaptive ITRを無効にして、ethtoolを使用してRxおよびTxのキューごとの割り込みを低減してください。

  • rx-usecsおよびtx-usecsを250に設定すると、キューごとに約4000回の割り込みに制限されます。

# ethtool -C <interface> adaptive-rx off adaptive-tx off rx-usecs 250 \
  tx-usecs 250

低遅延を実現する場合: Adaptive ITRおよびITRを無効化し、ethtoolを使用してRxおよびTxを0に設定してください。

# ethtool -C <interface> adaptive-rx off adaptive-tx off rx-usecs 0 \
  tx-usecs 0

アプリケーションデバイスキュー（ADq）¶

アプリケーションデバイスキュー（ADq）は、特定のアプリケーションに1つまたは複数のキューを割り当てることができます。これにより、指定されたアプリケーションの遅延を削減し、アプリケーションごとにTxトラフィックをレート制限できます。以下の手順に従ってADqを設定してください。

1. トランク（TC）を作成します。インターフェースごとに最大8つのTCを作成できます。shaperのbw_rlimitパラメータはオプションです。

例: tc0とtc1の2つのtcsを設定し、それぞれ16キューを割り当て、tc0には最大Txレートを1Gbit、tc1には3Gbitに設定します。

# tc qdisc add dev <interface> root mqprio num_tc 2 map 0 0 0 0 1 1 1 1
queues 16@0 16@16 hw 1 mode channel shaper bw_rlimit min_rate 1Gbit 2Gbit
max_rate 1Gbit 3Gbit

map: 16つの優先度をtcsにマッピング（例: map 0 0 0 0 1 1 1 1 は優先度0-3をtc0、4-7をtc1に割り当てます）

queues: 各tcに対して <num queues>@<offset>（例: queues 16@0 16@16 tc0にオフセット0で16キューを、tc1にオフセット16で16キューを割り当てます。すべてのtcにおける最大キュー数は64またはコア数のいずれか小さい方になります。

hw 1モードチャネル: 'channel'で'hw'を1に設定したものは、mqprioにおける新しいハードウェアオフロードモードで、mqprioオプション、TC、キュー構成、QoSパラメータを最大限に活用します。

shaper bw_rlimit: 各tcごとに最小および最大帯域幅レートを設定します。合計値はポート速度以下でなければなりません。

例: min_rate 1Gbit 3Gbit: ネットワークモニタリングツール（ifstatやsar –n DEV [interval] [サンプル数]など）を使用して帯域幅制限を確認してください。

  1. インターフェースにHW TCオフロードを有効化します。

    # ethtool -K <interface> hw-tc-offload on

  2. インターフェースのイングレス（RX）フローにTCを適用します。

    # tc qdisc add dev <interface> ingress
ノート：

  • すべてのtcコマンドはiproute2 <pathtoiproute2>/tc/ディレクトリから実行してください。

  • ADqはクラウドフィルタと互換性がありません。

  • TCがmqprioで設定されている場合、ethtool（ethtool -L）によるチャネル設定はサポートされていません。

  • 最新版iproute2が必要です。

  • NVMバージョン6.01以上が必要です。

  • 以下の機能が有効になっている場合、ADqを有効化できません: データセンターブリッジング（DCB）、ポートごとの複数機能（MFP）、サイドバンドフィルタ。

  • 他のドライバー（例: DPDK）がクラウドフィルタを設定している場合、ADqを有効化できません。

  • ADqではトンネルフィルタがサポートされていません。暗号化されたパケットがトンネルモードで到達した場合、フィルタは内側のヘッダーで行われます。例えば、VXLANトラフィックがトンネルモードでない場合、PCTYPEはVXLAN暗号化パケットとして識別され、外側のヘッダーは無視されます。したがって、内側のヘッダーがマッチされます。

  • PF上のTCフィルタがVF（PF上）でのトラフィックをマッチした場合、そのトラフィックはPFの適切なキューにルーティングされ、VFを通じて転送されません。このようなトラフィックはTCP/IPスタックの上位でドロップされます（PFのアドレスデータと一致しないからです）。

  • 複数のTCフィルタが異なるTCを指している場合、そのトラフィックはすべてのマッチしたTCキューに複製され送信されます。ハードウェアスイッチは複数のフィルタがマッチした場合、パケットをVSIリストにミラーリングします。

既知の問題/トラブルシューティング¶

注意: Intel(R) Ethernet Network Connection X722ベースの1 Gbデバイスは以下の機能をサポートしていません:

  • データセンターブリッジング (DCB)

  • QOS

  • VMQ

  • SR-IOV

  • タスクエンカプスレーションオフロード（VXLAN、NVGRE）

  • エネルギー効率Ethernet（EEE）

  • オートメディア検出

デバイスドライバとDPDKが同じデバイスを共有する場合の予期せぬ問題¶

i40eデバイスがマルチドライバーモードで動作し、カーネルドライバとDPDKドライバがデバイスを共有している場合、予期せぬ問題が発生する可能性があります。これは、複数のドライバー間でグローバルなNICリソースへのアクセスが同期されていないためです。グローバルなNIC設定（グローバルレジスタへの書き込み、AQによるグローバル設定、スイッチモードの変更）の変更は、デバイス上のすべてのポートとドライバに影響を及ぼします。DPDKを「multi-driver」モジュールパラメータでロードすることで、一部の問題を軽減できる場合があります。

スイッチでDCBを設定する際にはTC0を有効にする必要があります。¶

カーネルはTC0が利用可能であると想定しており、TC0が利用できない場合、デバイス上でプライオリティフローコントロール（PFC）を無効にします。この問題を修正するには、スイッチでDCBを設定する際にはTC0を有効にすることを確認してください。

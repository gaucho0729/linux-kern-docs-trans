このリリースでは¶

このファイルは、10ギガビットIntel(R)ネットワーク接続用のixgb Linuxベースドドライバーについて説明しています。このドライバーはItanium(R)2ベースのシステムにも対応しています。

ハードウェア要件に関する質問については、お使いの10ギガビットアダプターに同梱されているドキュメンテーションをご参照ください。すべてのハードウェア要件はLinuxとの使用に適用されます。

このカーネルで利用可能な機能は以下の通りです:

  • ネイティブVLAN

  • チャネルボンディング（チームング）

  • SNMP

チャネルボンディングに関するドキュメンテーションはLinuxカーネルソースの以下の場所にあります:/LinuxイーサネットボンディングドライバHOWTO

以前は/procファイルシステムで表示されていたドライバー情報はこのリリースではサポートされていません。代わりにethtool（バージョン1.6以降）、lspci、およびiproute2を使用して同じ情報を取得できます。

ethtoolの更新に関する手順は、このドキュメンテーションの後半にある「追加の設定」セクションで説明しています。

コマンドラインパラメータ¶

ドライバがモジュールとして構築されている場合、以下のオプションパラメータはmodprobeコマンドを使用してコマンドラインに入力することで使用されます。

modprobe ixgb [<option>=<VAL1>,<VAL2>,...]

たとえば、2つの10GbE PCIアダプターを使用して、

modprobe ixgb TxDescriptors=80,128

1番目のアダプターには80のTXリソース、2番目のアダプターには128のTXリソースを割り当ててixgbドライバーをロードします。

各パラメータのデフォルト値は一般的に推奨設定ですが、特に記載がない限りそのままでよいです。

Copybreak¶

有効な範囲

0-XXXX

デフォルト値

256

受信時に新しいバッファにコピーされるパケットの最大サイズです。

Debug¶

有効な範囲

0-16（0=なし,…,16=すべて）

デフォルト値

0

このパラメータは、システムログに表示されるデバッグメッセージのレベルを調整します。

FlowControl¶

有効な範囲

0-3 (0=なし、1=受信のみ、2=送信のみ、3=受信&送信)

デフォルト値

EEPROMがない場合は1、それ以外はEEPROMから読み込みます

このパラメータは、イーサネットPAUSEフレームの自動生成（Tx）および応答（Rx）を制御します。Txフロー制御を有効にするハードウェアのバグがあるため、注意が必要です。

RxDescriptors¶

有効な範囲

64-4096

デフォルト値

1024

この値はドライバーが割り当てた受信ディスクリプタの数です。この値を増やすとドライバーがより多くの受信パケットをバッファリングできます。各ディスクリプタは16バイトです。ディスクリプタごとに受信バッファも割り当てられ、MTU設定に応じて2048、4056、8192、または16384バイトのいずれかになります。MTUサイズが1500以下の場合、受信バッファサイズは2048バイトです。MTUが1500より大きい場合、受信バッファサイズは4056、8192、または16384バイトのいずれかになります。最大MTUサイズは16114です。

TxDescriptors¶

有効な範囲

64-4096

デフォルト値

256

この値はドライバが割り当てた送信ディスクリプタの数です。この値を増やすことで、ドライバがより多くの送信をキューイングできるようになります。各ディスクリプタは16バイトです。

RxIntDelay¶

有効な範囲

0-65535（0=オフ）

デフォルト値

72

この値は受信割り込みの生成を遅延させる単位で0.8192マイクロ秒です。受信割り込みの削減は、特定のネットワークトラフィックに適切に調整すればCPU効率を向上させる可能性があります。この値を増やすとフレーム受信に追加のレイテンシーが発生し、TCPトラフィックのスループットが低下する可能性があります。システムが受信をドロップしている場合、この値が高すぎる可能性があり、ドライバーが利用可能な受信ディスクリプタを枯渇させているかもしれません。

TxIntDelay¶

有効な範囲

0-65535（0=オフ）

デフォルト値

32

この値は、送信割込みの生成を0.8192マイクロ秒単位で遅延させます。適切に調整すれば、特定のネットワークトラフィックに対してCPU効率を向上させることが可能です。この値を増やすとフレーム送信に追加のレイテンシーが生じ、結果としてTCPトラフィックのスループットが低下する可能性があります。この値をあまりにも高く設定すると、ドライバが利用可能な送信ディスクリプタを枯渇させることになります。

XsumRX¶

有効な範囲

0-1

デフォルト値

1

値が「1」の場合は、ドライバが受信パケット（UDPおよびTCP）のIPチェックサムオフロードをアダプターのハードウェアに有効にする必要があります。

RxFCHighThresh¶

有効な範囲

1,536-262,136 (0x600 - 0x3FFF8, 8 byte granularity)

デフォルト値

196,608 (0x30000)

受信フロー制御の高閾値（パーズフレームを送信する際）

RxFCLowThresh¶

有効な範囲

64-262,136 (0x40 - 0x3FFF8, 8 byte granularity)

デフォルト値

163,840 (0x28000)

受信フロー制御の低閾値（リカバリーフレームを送信する際）

FCReqTimeout¶

有効な範囲

1-65535

デフォルト値

65535

フロー制御リクエストタイムアウト（リンクパートナーの送信を一時停止する期間）

IntDelayEnable¶

値の範囲

0,1

デフォルト値

1

割込み遅延、0は送信割込み遅延を無効化し、1は有効化します。

パフォーマンスの向上¶

10ギガビットサーバーアダプターでは、デフォルトのLinux設定が実際のトータル利用可能スループットを人工的に制限している可能性があります。Linuxがデータを送受信する能力を向上させるには、特定の設定を組み合わせて適用する必要があります。以下の改善策は、Linuxを用いたさまざまな結果の設定から元々取得したものです。 https://www.spec.org/web99/ Linuxを用いたさまざまな提出結果から取得したものです。

ノート:

これらの変更は提案であり、ネットワークパフォーマンスのチューニングの出発点としての役割を果たします。

変更は大きく3つの方法で行われ、影響度の高い順に以下の通りです：

  • ip linkを使用して、MTU（最大伝送単位）とtxqueuelenパラメータを変更します。

  • sysctlを使用して、/procパラメータ（実質的にカーネルのチューニング）を変更します。

  • setpciを使用して、PCI-X構成空間内のMMRBCフィールドを変更し、バス上の送信バースト長を増やします。

ノート:

setpciはアダプターの構成レジスタを変更し、一度に最大4KBのデータを読み取れるようにします（送信用）。ただし、一部のシステムではこのレジスタを変更した後の挙動が未定義になる可能性があります（エラーが発生する可能性あり）。安定した設定に戻すには、電源を再起動する、ハードリセットを行う、またはe6レジスタを明示的に22に戻す（setpci -d 8086:1a48 e6.b=22）必要があります。

  • これらの行をixgb_perf.shにコピーして貼り付けます：

#!/bin/bash
echo "configuring network performance , edit this file to change the interface
or device ID of 10GbE card"
# set mmrbc to 4k reads, modify only Intel 10GbE device IDs
# replace 1a48 with appropriate 10GbE device's ID installed on the system,
# if needed.
setpci -d 8086:1a48 e6.b=2e
# set the MTU (max transmission unit) - it requires your switch and clients
# to change as well.
# set the txqueuelen
# your ixgb adapter should be loaded as eth1 for this to work, change if needed
ip li set dev eth1 mtu 9000 txqueuelen 1000 up
# call the sysctl utility to modify /proc/sys entries
sysctl -p ./sysctl_ixgb.conf

  • これらの行をsysctl_ixgb.confにコピーして貼り付けます：

# some of the defaults may be different for your kernel
# call this file with sysctl -p <this file>
# these are just suggested values that worked well to increase throughput in
# several network benchmark tests, your mileage may vary

### IPV4 specific settings
# turn TCP timestamp support off, default 1, reduces CPU use
net.ipv4.tcp_timestamps = 0
# turn SACK support off, default on
# on systems with a VERY fast bus -> memory interface this is the big gainer
net.ipv4.tcp_sack = 0
# set min/default/max TCP read buffer, default 4096 87380 174760
net.ipv4.tcp_rmem = 10000000 10000000 10000000
# set min/pressure/max TCP write buffer, default 4096 16384 131072
net.ipv4.tcp_wmem = 10000000 10000000 10000000
# set min/pressure/max TCP buffer space, default 31744 32256 32768
net.ipv4.tcp_mem = 10000000 10000000 10000000

### CORE settings (mostly for socket and UDP effect)
# set maximum receive socket buffer size, default 131071
net.core.rmem_max = 524287
# set maximum send socket buffer size, default 131071
net.core.wmem_max = 524287
# set default receive socket buffer size, default 65535
net.core.rmem_default = 524287
# set default send socket buffer size, default 65535
net.core.wmem_default = 524287
# set maximum amount of option memory buffers, default 10240
net.core.optmem_max = 524287
# set number of unprocessed input packets before kernel starts dropping them; default 300
net.core.netdev_max_backlog = 300000

必要に応じてixgb_perf.shスクリプトを編集し、eth1を自分のixgbドライバが使用しているインターフェースに変更し、または'1a48'をシステムにインストールされている10GbEデバイスの適切なIDに置き換えます。

ノート:

これらのスクリプトをブートプロセスに追加しない限り、これらの変更は次のシステム再起動まで有効です。

UDPトラフィックの遅延を解消する¶

サーバーがTCPトラフィックよりもUDPトラフィックを受信する速度が遅いように見える場合、Linuxのデフォルトではネットワークスタックのバッファサイズが高スループットなUDP転送をサポートするのに必要なサイズに設定されていない可能性があります。この問題を緩和する方法の一つは、IPスタックが受信データを保存するために使用するメモリ量を増やすことです。

例えば、以下のコマンドを使用してください：

sysctl -w net.core.rmem_max=262143

および：

sysctl -w net.core.rmem_default=262143

読み取りバッファメモリの最大値とデフォルト値を262143 (256k - 1) に増やすことで、デフォルトの最大値131071 (128k - 1) とデフォルト値65535 (64k - 1) から変更します。これらの変数はネットワークスタックが受信する際のメモリ使用量を増やすためのものであり、アプリケーションに応じてさらに大幅に増やすことも可能です。

追加の設定¶

異なるディストリビューションでのドライバーの設定¶

ネットワークドライバーがシステム起動時に正しくロードされるように設定する方法はディストリビューションによって異なります。通常、設定プロセスは /etc/modprobe.conf に alias 行を追加し、他のシステム起動スクリプトや設定ファイルを編集する必要があります。多くのポピュラーなLinuxディストリビューションは、これらの変更を自動で行うツールを提供しています。システムに適したネットワークデバイスの設定方法を学ぶには、ディストリビューションのドキュメンテーションを参照してください。このプロセス中にドライバーまたはモジュール名を尋ねられたら、Intel 10GbEファミリーアダプター用のLinuxベースドライバーの名前は ixgb です。

リンクメッセージの表示¶

ディストリビューションがシステムメッセージを制限している場合、リンクメッセージはコンソールに表示されません。ネットワークドライバーリンクメッセージをコンソールで確認するには、次のコマンドを入力してdmesgを8に設定してください：

dmesg -n 8

注意：この設定は再起動後に保持されません。

ジャンボフレーム¶

このドライバーはすべてのアダプターでジャンボフレームをサポートしています。ジャンボフレームのサポートは、MTUをデフォルトの1500より大きい値に変更することで有効になります。MTUの最大値は16114です。MTUサイズを増やすには ip コマンドを使用してください。例えば：

ip li set dev ethx mtu 9000

ジャンボフレームの最大MTU設定は16114です。これはジャンボフレームの最大サイズ16128と一致します。

Ethtool¶

ドライバーはethtoolインターフェースを使用してドライバーの設定と診断、統計情報の表示を行います。この機能にはethtoolバージョン1.6以降が必要です。

最新のethtoolは以下の場所から入手可能です https://www.kernel.org/pub/software/network/ethtool/

ノート:

ethtoolバージョン1.6はethtoolオプションの一部しかサポートしていません。より完全なethtool機能をサポートするには、最新バージョンにアップグレードしてください。

NAPI¶

ixgbドライバーはNAPI（Rxポーリングモード）をサポートしています。

既知の問題/トラブルシューティング¶

ノート:

ドライバーをインストールした後、Intelネットワーク接続が動作しない場合は、READMEファイルの「このリリースにおける」セクションで正しいドライバーをインストールしているか確認してください。

富士通XENPAKモジュールとSmartBitsチャッサのケーブルの互換性問題¶

Intel(R) PRO/10GbE CX4 Server アダプターがファジットのXENPAK CX4モジュールと15 m/24AWGケーブルアセンブリ（ファジットまたはレオニ製）を用いてスマートビットスケルトンに接続されている場合、CRCエラーが過剰に発生する可能性があります。このCRCエラーはIntel(R) PRO/10GbE CX4 Server アダプターまたはスマートビットスケルトンで受信される可能性があります。この状況が発生した場合、異なるケーブルアセンブリを使用することで問題を解決できる可能性があります。

HP Procurve 3400cl スイッチポートとのケーブルの互換性問題¶

Intel(R) PRO/10GbE CX4 Server アダプターがHP Procurve 3400cl スイッチポートに短いケーブル（1 m以下の長さ）で接続されている場合、CRCエラーが過剰に発生する可能性があります。この状況が発生した場合、長いケーブルを使用することで問題を解決できる可能性があります。

ファジット製の24AWGケーブルアセンブリで10 m以上またはレオニ製の15 m/24AWGケーブルアセンブリを使用している場合、CRCエラーが過剰に発生する可能性があります。このCRCエラーはCX4 Server アダプターまたはスイッチで受信される可能性があります。この状況が発生した場合、異なるケーブルアセンブリを使用することで問題を解決できる可能性があります。

ジャンボフレームのシステム要件¶

Linuxシステムで64 MB以下のRAMを搭載してジャンボフレームを使用している場合、メモリ割り当て失敗が観測されることがあります。ジャンボフレームを使用している場合、システムは64 MBのシステムメモリの広告された最小要件より多く必要になる可能性があります。

ジャンボフレームでのパフォーマンス低下¶

Jumbo frames環境ではスループット性能の劣化が観測される場合があります。このような状況が確認された場合は、アプリケーションのソケットバッファサイズを増やすことや、/proc/sys/net/ipv4/tcp_*memエントリの値を増やすことで改善される可能性があります。詳細については、特定のアプリケーションのマニュアルおよび/usr/src/linux*/Documentation/networking/ip-sysctl.txtを参照してください。

ジャンボフレームを使用する際のRxバッファの割り当て¶

2.6.xカーネルでジャンボフレームを使用する際、利用可能なメモリが深刻にフラグメント化されている場合、Rxバッファの割り当てが失敗する可能性があります。これはPCI-Xアダプターまたはパケット分割が無効になっている場合に発生する可能性があります。この問題は、受信バッファ割り当て用の利用可能なメモリ量を変更するか、/proc/sys/vm/min_free_kbytesを増やすことで軽減または解消できます。

同一イーサネットブロードキャストネットワーク上の複数インターフェース¶

LinuxのデフォルトのARP動作により、1つのシステムが同一イーサネットブロードキャストドメイン（非分割スイッチ）内の2つのIPネットワークに配置されても、期待される動作にはなりません。すべてのイーサネットインターフェースがシステムに割り当てられたすべてのIPアドレスのIPトラフィックに応答します。これにより受信トラフィックが不均等になります。

サーバーに複数のインターフェースがある場合、以下のいずれかを行ってください：

  • ARPフィルタリングを有効にするには、以下を入力してください：

    echo 1 > /proc/sys/net/ipv4/conf/all/arp_filter

  • インターフェースを別個のブロードキャストドメインにインストールしてください - これには異なるスイッチまたはVLANに分離されたスイッチを使用します。

UDP ストレステストにおけるパケットドロップの問題¶

10GbEドライバでの小パケットUDP ストレステストでは、Linuxシステムがソケットバッファの満杯によりUDPパケットをドロップする可能性があります。パケット受信を制御するドライバのフロー制御変数を最小値に設定することで、この問題を回避できます。

ストレス状態でのTXハングの可能性¶

ストレス状態でTXハングが発生した場合、TSOをオフにすることで問題を解決できる可能性があります（ethtool -K eth0 tso off）

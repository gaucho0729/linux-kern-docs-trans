概要¶

このファイルはiavf Linuxベースドドライバーについて説明しています。このドライバーは以前はi40evfと呼ばれていました。

iavfドライバーは以下の仮想機能デバイスをサポートしており、i40eまたは新しいバージョンのPhysical Function (PF)ドライバーでコンパイルされたカーネルでのみ有効化できます。iavfドライバーではCONFIG_PCI_MSIが有効化されている必要があります。

iavfドライバーをロードするゲストOSはMSI-X割込みをサポートする必要があります。

アダプターの特定¶

このカーネル内のドライバーは以下のデバイスと互換性があります:

  • Intel(R) XL710 X710 Virtual Function

  • Intel(R) X722 Virtual Function

  • Intel(R) XXV710 Virtual Function

  • Intel(R) Ethernet Adaptive Virtual Function

最高のパフォーマンスを確保するには、デバイスに最新のNVM/FWがインストールされていることを確認してください。

アダプターの識別方法や最新のNVM/FWイメージ、Intelネットワークドライバーについては、Intelサポートウェブサイトを参照してください： https://www.intel.com/support

追加の機能と設定¶

リンクメッセージの表示¶

ディストリビューションがシステムメッセージを制限している場合、リンクメッセージはコンソールに表示されません。ネットワークドライバーリンクメッセージをコンソールで確認するには、次のコマンドを入力してdmesgを8に設定してください：

# dmesg -n 8
ノート:

この設定は再起動後に保持されません。

ethtool¶

ドライバーはethtoolインターフェースを使用してドライバーの設定および診断、統計情報の表示を行います。この機能には最新のethtoolバージョンが必要です。ダウンロードはこちら: https://www.kernel.org/pub/software/network/ethtool/

VLANタグの剥離設定¶

VLANタグを含むパケットを仮想機能(VF)で受信するアプリケーションがある場合、VFのVLANタグ剥離を無効化できます。物理機能(PF)はVFからの要請を処理してVLANタグ剥離の有効/無効を管理します。注意点として、PFがVFにVLANを割り当てた場合、そのVFからのVLANタグ剥離設定の要請は無視されます。

VFを実行している仮想マシン内で以下のコマンドを実行してVFのVLANタグ剥離を有効/無効にできます:

# ethtool -K <if_name> rxvlan on/off

または代替として:

# ethtool --offload <if_name> rxvlan on/off

Adaptive Virtual Function¶

Adaptive Virtual Function (AVF)は、仮想機能ドライバー（VF）が関連付けられた物理機能ドライバー（PF）の変化する機能セットに適応できるようにします。これにより、システム管理者はPFを更新するだけで、関連するすべてのVFを更新する必要がなくなります。すべてのAVFは単一の共通デバイスIDとブランド名を持っています。

AVFは「ベースモード」と呼ばれる最小限の機能セットを持ちますが、関連付けられたPFの機能により追加の機能を提供する場合があります。ベースモードの機能には以下のものがあります:

  • 4キュー・ペア (QP) および関連する設定ステータスレジスタ (CSRs) がTx/Rxに使用される

  • i40eデスクリプタおよびリング形式

  • デスクリプタの書込み完了通知

  • 1つの制御キューで、i40eデスクリプタ、CSRsおよびリング形式が使用される

  • 5つのMSI-X割込みベクターおよび対応するi40e CSRs

  • 1つの割込みスロットレート (ITR) インデックス

  • 1つの仮想ステーションインターフェース (VSI) がVFごとに割り当てられる

  • 1つのトラフィッククラス (TC)、TC0

  • PFを通じて設定される64エントリの間接テーブルおよびキーを持つ受信側スケーリング (RSS)

  • 1つのユニキャストMACアドレスがVFごとに予約される

  • 各VFごとに16つのMACアドレスフィルタ

  • ステートレスオフロード - 非トンネル化されたチェックサム

  • AVFデバイスID

  • HWメールボックスはVFとPF間の通信に使用されます（Windowsを含む）

IEEE 802.1ad（QinQ）サポート¶

IEEE 802.1ad標準は、非公式にQinQと呼ばれるもので、1つのイーサネットフレーム内で複数のVLAN IDをサポートします。VLAN IDはしばしば「タグ」と呼ばれるため、複数のVLAN IDは「タグスタック」と呼ばれます。タグスタックはL2トンネリングを可能にし、特定のVLAN ID内でトラフィックを分離するなどの用途があります。

以下の例は、802.1ad（QinQ）の設定方法です：

# ip link add link eth0 eth0.24 type vlan proto 802.1ad id 24
# ip link add link eth0.24 eth0.24.371 type vlan proto 802.1Q id 371

ここで「24」と「371」は例としてのVLAN IDです。

ノート：

802.1ad (QinQ)パケットには、受信チェックサムオフロード、クラウドフィルタ、VLAN加速がサポートされません。

アプリケーションデバイスキュー（ADq）¶

アプリケーションデバイスキュー（ADq）は、特定のアプリケーションに1つまたは複数のキューを割り当てることができます。これにより、指定されたアプリケーションの遅延を削減し、アプリケーションごとにTxトラフィックをレート制限できます。以下の手順に従ってADqを設定してください。

要件:

  • sch_mqprio、act_mirredおよびcls_flowerモジュールがロードされている必要があります

  • 最新版のiproute2

  • 他のドライバー（例：DPDK）がクラウドフィルタを設定している場合、ADQを有効にすることができません

  • 以下の機能が有効になっている場合、ベースとなるPFデバイスによってADQを有効にすることができません：

    • データセンターブリッジング (DCB)

    • ポートごとの複数機能（MFP）

    • サイドバンドフィルタ

1. トランク（TC）を作成します。インターフェースごとに最大8つのTCを作成できます。shaperのbw_rlimitパラメータはオプションです。

例: tc0とtc1の2つのtcsを設定し、それぞれ16キューを割り当て、tc0には最大Txレートを1Gbit、tc1には3Gbitに設定します。

tc qdisc add dev <interface> root mqprio num_tc 2 map 0 0 0 0 1 1 1 1
queues 16@0 16@16 hw 1 mode channel shaper bw_rlimit min_rate 1Gbit 2Gbit
max_rate 1Gbit 3Gbit

map: 16つの優先度をtcsにマッピング（例: map 0 0 0 0 1 1 1 1 は優先度0-3をtc0、4-7をtc1に割り当てます）

queues: 各tcに対して <num queues>@<offset>（例: queues 16@0 16@16 tc0にオフセット0で16キューを、tc1にオフセット16で16キューを割り当てます。すべてのtcにおける最大キュー数は64またはコア数のいずれか小さい方になります。

hw 1モードチャネル: 'channel'で'hw'を1に設定したものは、mqprioにおける新しいハードウェアオフロードモードで、mqprioオプション、TC、キュー構成、QoSパラメータを最大限に活用します。

shaper bw_rlimit: 各tcごとに最小および最大帯域幅レートを設定します。合計値はポート速度以下でなければなりません。

例: min_rate 1Gbit 3Gbit: ネットワークモニタリングツール（ifstatやsar –n DEV [interval] [サンプル数]など）を使用して帯域幅制限を確認してください。

ノート:

TCがmqprioで設定されている場合、ethtool（ethtool -L）によるチャネル設定はサポートされていません。

  1. インターフェースにHW TCオフロードを有効化します。

    # ethtool -K <interface> hw-tc-offload on

  2. インターフェースのイングレス（RX）フローにTCを適用します。

    # tc qdisc add dev <interface> ingress
ノート：

  • tcコマンドはiproute2 <pathtoiproute2>/tc/ディレクトリから実行する必要があります

  • ADqはクラウドフィルタと互換性がありません

  • mqprioでTCを設定している場合、ethtool（ethtool -L）によるチャネルの設定はサポートされていません

  • 最新版iproute2が必要です。

  • NVMバージョン6.01以上が必要です

  • 以下の機能のいずれかが有効になっている場合、ADqを有効にすることができません：データセンターブリッジング（DCB）、ポートごとの複数機能（MFP）、またはサイドバンドフィルタ

  • 他のドライバー（例：DPDK）がクラウドフィルタを設定している場合、ADqを有効にすることができません

  • ADqではトンネルフィルタがサポートされていません。暗号化されたパケットがトンネルモードで到達した場合、フィルタは内側のヘッダーで行われます。例えば、VXLANトラフィックがトンネルモードでない場合、PCTYPEはVXLAN暗号化パケットとして識別され、外側のヘッダーは無視されます。したがって、内側のヘッダーがマッチされます。

  • PF上のTCフィルタがVF（PF上）でのトラフィックをマッチした場合、そのトラフィックはPFの適切なキューにルーティングされ、VFを通じて転送されません。このようなトラフィックはTCP/IPスタックの上位でドロップされます（PFのアドレスデータと一致しないからです）。

  • 複数のTCフィルタが異なるTCを指している場合、そのトラフィックはすべてのマッチしたTCキューに複製され送信されます。ハードウェアスイッチは複数のフィルタがマッチした場合、パケットをVSIリストにミラーリングします。

既知の問題/トラブルシューティング¶

VFがIntel(R) Ethernet Controller 700シリーズデバイスにバインドされている場合、ボンディングが失敗します¶

Intel(R) Ethernet Controller 700シリーズベースのデバイスに仮想機能（VF、仮想NIC）をバインドしている場合、VFスレーブがアクティブスレーブになるときに失敗する可能性があります。VFのMACアドレスがデバイスのPF（物理機能）によって設定されている場合、スレーブを追加するかアクティブバックアップスレーブを変更すると、LinuxボンディングがバックアップスレーブのMACアドレスをアクティブスレーブと同じMACアドレスに同期しようとします。この時点でLinuxボンディングが失敗します。VFのMACアドレスがPFによって設定されていない場合、この問題は発生しません。

VMとクライアント間でトラフィックが通過していない¶

仮想機能（VF、仮想NIC）が信頼モードになっていない場合、スプーフィングチェックがVFで有効になっていると、クライアントシステムと別々のホスト上で実行されている仮想マシン（VM）間でトラフィックを通過できなくなる可能性があります。この状況は、クライアント、ホスト、ゲストのオペレーティングシステムの組み合わせによって発生する場合があります。VFを信頼モードに設定する方法については、このリーダーメモの「VLANタグパケットステアリング」セクションを参照してください。スプーフィングチェックの設定については、「MACおよびVLANアンチスプーフィング機能」セクションを参照してください。

アクティブなVMがバインドされているVFがあるポートドライバーをアンロードしないでください¶

アクティブなVMがバインドされているVFがあるポートのドライバーをアンロードしないでください。これを行うと、ポートがハング状態に見える可能性があります。VMがシャットダウンするか、VFを解放した後、コマンドが完了します。

4つのトラフィッククラスを使用すると失敗します¶

iavfドライバで3つ以上のトラフィッククラスを予約しないでください。これを行うと、どのトラフィッククラスも設定されず、ドライバがstdoutにエラーを書き込む原因になります。この問題を避けるため、最大3つのキューを使用してください。

iavfドライバの削除時に複数のログエラーが発生¶

複数のVFがある場合、iavfドライバを削除すると、以下のログエラーが複数回出力されます:

Unable to send opcode 2 to PF, err I40E_ERR_QUEUE_EMPTY, aq_err ok
Unable to send the message to VF 2 aq_err 12
ARQ Overflow Error detected

仮想マシンにリンクが取得されない¶

仮想マシンに複数の仮想ポートが割り当てられ、それらが異なる物理ポートにバインドされている場合、すべての仮想ポートでリンクが取得できない可能性があります。以下のコマンドで問題を回避できます:

# ethtool -r <PF>

<PF>はホスト内のPFインターフェースを示します（例: p5p1）。すべての仮想ポートでリンクを取得するには、このコマンドを複数回実行する必要がある場合があります。

仮想ファンクションのMACアドレスが不意に変更される¶

ホストで仮想ファンクション（VF）のMACアドレスが割り当てられていない場合、VFドライバはランダムなMACアドレスを使用します。このランダムなMACアドレスはVFドライバが再ロードされるたびに変更される可能性があります。ホストマシンで静的MACアドレスを割り当てることで回避できます。この静的MACアドレスはVFドライバの再ロードでも維持されます。

ドライババッファオーバーフローの修正¶

Intel SA-00069で参照されているCVE-2016-8105の修正 https://www.intel.com/content/www/us/en/security-center/advisory/intel-sa-00069.html このドライバおよび今後のバージョンに含まれています。

同一イーサネットブロードキャストネットワーク上の複数インターフェース¶

LinuxのデフォルトのARP動作により、1つのシステムが同一イーサネットブロードキャストドメイン（非分割スイッチ）内の2つのIPネットワークに配置されても、期待される動作にはなりません。すべてのイーサネットインターフェースがシステムに割り当てられたすべてのIPアドレスのIPトラフィックに応答します。これにより受信トラフィックが不均等になります。

サーバーに複数のインターフェースがある場合、次のコマンドを実行してARPフィルタリングを有効にしてください:

# echo 1 > /proc/sys/net/ipv4/conf/all/arp_filter
ノート:

この設定は再起動後に保持されません。永続的な設定にするには、/etc/sysctl.confファイルに次の行を追加してください:

net.ipv4.conf.all.arp_filter = 1

別の代替案として、インターフェースを別個のブロードキャストドメイン（異なるスイッチやVLANに分割されたスイッチ）にインストールすることもできます。

Rxページ割当エラー¶

「Page allocation failure. order:0」エラーはストレス状態で発生する可能性があります。これはLinuxカーネルがストレス状態を報告する仕様によるものです。

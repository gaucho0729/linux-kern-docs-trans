SFP+のレーザーは、ifconfig ethX downでオフになります¶

「ifconfig ethX down」は、82599ベースのSFP+ファイバーアダプターのレーザーをオフにし、「ifconfig ethX up」はレーザーをオンにします。代替として、「ip link set [down/up] dev ethX」を使用してレーザーをオフ/オンにすることもできます。

コマンドラインパラメータ¶

max_vfs¶

有効な範囲

1-63

このパラメータは SR-IOV のサポートを追加します。これにより、ドライバーが max_vfs に相当する仮想関数を生成します。値が 0 より大きい場合、VMDq パラメータが 1 またはそれ以上になるように強制します。

注意: このパラメータは、カーネル3.7.xおよびそれ以前のバージョンでのみ使用されます。カーネル3.8.xおよびそれ以降ではsysfsを使用してVFを有効化してください。また、Red Hatディストリビューションでは、このパラメータはバージョン6.6およびそれ以前でのみ使用されます。バージョン6.7およびそれ以降ではsysfsを使用してください。例えば:

#echo $num_vf_enabled > /sys/class/net/$dev/device/sriov_numvfs // enable VFs
#echo 0 > /sys/class/net/$dev/device/sriov_numvfs               //disable VFs

ドライバーのパラメータは位置によって参照されます。したがって、システムにデュアルポートアダプタや複数のアダプタがあり、各ポートごとに N 個の仮想関数を希望する場合、各ポートに対して数字を指定し、各パラメータをコンマで区切ってください。たとえば：

modprobe ixgbe max_vfs=4

これは最初のポートに 4 個の VF を生成します。

modprobe ixgbe max_vfs=2,4

これは最初のポートに 2 個の VF を生成し、2 番目のポートに 4 個の VF を生成します。

注意: これらのパラメータでドライバーをロードする際には注意が必要です。システムの構成、スロット数などに応じて、コマンドラインでの位置がすべての場合で予測できない可能性があります。

注意: デバイスもしくはドライバーがVFがコンフィギュレーションスペースにマッピングされる方法を制御しません。バスレイアウトはオペレーティングシステムによって異なります。サポートしているOSではsysfsを確認してマッピングを確認できます。

注意: SR-IOVモードまたはVMDqモードが有効になっている場合、ハードウェアのVLANフィルタリングおよびVLANタグの除去/挿入は有効のままになります。新しいVLANフィルタが追加される前に、古いVLANフィルタを削除してください。例えば、

ip link set eth0 vf 0 vlan 100 // set VLAN 100 for VF 0
ip link set eth0 vf 0 vlan 0   // Delete VLAN 100
ip link set eth0 vf 0 vlan 200 // set a new VLAN 200 for VF 0

カーネル3.6では、ドライバがmax_vfsとDCB機能の同時使用をサポートします（以下に記載する制約に従います）。カーネル3.6以前では、max_vfsが0より大きい場合のDCB機能（複数のトラフィッククラスをPriority Flow ControlおよびExtended Transmission Selectionを用いて利用）の同時動作はサポートされていません。

DCBが有効になっている場合、ネットワークトラフィックは複数のトラフィッククラス（NIC内のパケットバッファ）を通じて送受信されます。トラフィックは、優先度に基づいて特定のクラスに割り当てられ、VLANタグで使用される値0〜7の優先度に基づいています。SR-IOVが有効でない場合、各トラフィッククラスは受信/送信ディスクリプタキュー・ペアのセットと関連付けられます。特定のトラフィッククラスのキュー・ペア数はハードウェアの設定に依存します。SR-IOVが有効になっている場合、ディスクリプタキュー・ペアはプールにグループ化されます。物理ファンクション（PF）および各仮想ファンクション（VF）に受信/送信ディスクリプタキュー・ペアのプールが割り当てられます。複数のトラフィッククラスが設定されている場合（例：DCBが有効になっている場合）、各プールには各トラフィッククラスから1つのキュー・ペアが含まれます。ハードウェアで単一のトラフィッククラスが設定されている場合、プールにはその単一のトラフィッククラスからの複数のキュー・ペアが含まれます。

割り当て可能なVFの数は、有効にできるトラフィッククラスの数に依存します。各有効VFに対して設定可能なトラフィッククラス数は以下の通りです：0〜15 VF = デバイスのサポートに応じて最大8トラフィッククラス 16〜31 VF = 最大4トラフィッククラス 32〜63 VF = 1トラフィッククラス

VFが設定されている場合、PFにも1つのプールが割り当てられます。PFはDCB機能をサポートしますが、各トラフィッククラスが単一のキュー・ペアのみを使用する制約があります。VFが0個設定されている場合、PFは各トラフィッククラスに対して複数のキュー・ペアをサポートできます。

追加の機能と設定¶

フロー制御¶

イーサネットフロー制御（IEEE 802.3x）はethtoolを使用して設定でき、ixgbeで受信および送信のパーズフレームを有効にします。送信が有効になっている場合、受信パケットバッファが事前に定義されたしきい値を超えるとパーズフレームが生成されます。受信が有効になっている場合、パーズフレームを受信した際に送信ユニットは指定された時間遅延で停止します。

注意: フローコントロールをサポートするリンクパートナーを保有している必要があります。

フロー制御はデフォルトで有効になっています。

ethtoolを使用してフロー制御の設定を変更します。受信（Rx）または送信（Tx）フロー制御を有効にするか無効にするには、以下のコマンドを使用します：

ethtool -A eth? rx <on|off> tx <on|off>

注意: このコマンドは自動交渉が無効になっている場合にのみフローコントロールを有効または無効にします。自動交渉が有効な場合、このコマンドはリンクパートナーとの自動交渉に使用されるパラメータを変更します。

自動交渉を有効にするか無効にするには、

ethtool -s eth? autoneg <on|off>

注意: フローコントロール自動交渉はリンク自動交渉の一部です。デバイスによっては自動交渉設定を変更できない場合があります。

注意：82598バックプレーンカードが1ギガビットモードに入っている場合、フロー制御のデフォルト動作はオフに変更されます。これらのデバイスでの1ギガビットモードにおけるフロー制御は送信のハングを引き起こす可能性があります。

Intel(R) Ethernet Flow Director¶

Intel Ethernet Flow Directorは以下のタスクを実行します:

  • 受信パケットをフローごとに異なるキューにリダイレクトします。

  • プラットフォーム内でフローをルーティングする際の厳密な制御を可能にします。

  • フローとCPUコアをフローのアフィニティにマッチングします。

  • L3およびL4フロータイプでの柔軟なフロー分類とロードバランシングをサポートします（SFPモードでのみ有効）。

注意：インテルイーサネットフロー・ディレクターマスキングはサブネットマスキングとは逆の動作を行います。以下のコマンドで：

#ethtool -N eth11 flow-type ip4 src-ip 172.4.1.2 m 255.0.0.0 dst-ip \
172.21.1.1 m 255.128.0.0 action 31

フィルタに記録されるsrc-ip値は0.4.1.2になります。予想される172.0.0.0とは異なります。同様に、dst-ip値は0.21.1.1になります。172.0.0.0とは異なります。

Intel Ethernet Flow Directorを有効化または無効化するには:

# ethtool -K ethX ntuple <on|off>

ntupleフィルタを無効化する際には、すべてのユーザーが設定したフィルタがドライバキャッシュおよびハードウェアから削除されます。ntupleを再有効化する際には、すべての必要なフィルタを再追加する必要があります。

パケットをキュー2にリダイレクトするフィルタを追加するには、-Uまたは-Nスイッチを使用してください:

# ethtool -N ethX flow-type tcp4 src-ip 192.168.10.1 dst-ip \
192.168.10.2 src-port 2000 dst-port 2001 action 2 [loc 1]

現在のフィルタの一覧を確認するには:

# ethtool <-u|-n> ethX

サイドバンドパーフェクトフィルタ¶

サイドバンドパーフェクトフィルタは、指定された特徴に一致するトラフィックを制御するために使用されます。これらはethtoolのntupleインターフェースを通じて有効化されます。新しいフィルターを追加するには、次のコマンドを使用します：

ethtool -U <device> flow-type <type> src-ip <ip> dst-ip <ip> src-port <port> \
dst-port <port> action <queue>
以下では:

<device> - プログラムするイーサネットデバイス <type> - ip4、tcp4、udp4、sctp4のいずれか <ip> - マッチするIPアドレス <port> - マッチするポート番号 <queue> - トラフィックを誘導するキュー（-1はマッチしたトラフィックを破棄する）

フィルターを削除するには、次のコマンドを使用します：

ethtool -U <device> delete <N>

<N>はすべてのアクティブなフィルターを印刷した際に表示されるフィルターIDであり、フィルターを追加する際に「loc <N>」で指定した場合にも使用できます。

次の例は、192.168.0.1から送信され、ポート5300で、192.168.0.5に送信され、ポート80で、キュー7に誘導されるTCPトラフィックをマッチさせます：

ethtool -U enp130s0 flow-type tcp4 src-ip 192.168.0.1 dst-ip 192.168.0.5 \
src-port 5300 dst-port 80 action 7

各フローティプーごとに、プログラムされたフィルターはすべて同じマッチング入力セットを必要とします。たとえば、次の2つのコマンドを実行することは問題ありません：

ethtool -U enp130s0 flow-type ip4 src-ip 192.168.0.1 src-port 5300 action 7
ethtool -U enp130s0 flow-type ip4 src-ip 192.168.0.5 src-port 55 action 10

しかし、次の2つのコマンドを実行すると、最初のコマンドがsrc-ipを指定し、2番目のコマンドがdst-ipを指定しているため、受け入れられません：

ethtool -U enp130s0 flow-type ip4 src-ip 192.168.0.1 src-port 5300 action 7
ethtool -U enp130s0 flow-type ip4 dst-ip 192.168.0.5 src-port 55 action 10

2番目のコマンドはエラーで失敗します。同じフィールドで異なる値を使用して複数のフィルタをプログラミングすることは可能ですが、1つのデバイスでは2つのTCP4フィルタを異なるマッチングフィールドでプログラミングすることはできません。

ixgbeドライバはフィールドのサブ部分でのマッチングをサポートしていないため、部分的なマスクフィールドはサポートされていません。

トラフィックを特定の仮想ファンクション（VF）に誘導するフィルタを作成するには、「user-def」パラメータを使用してください。user-defを64ビットの値として指定し、下位32ビットがキュー番号を、次に8ビットがVFを表します。注意点として、0はPF（物理ファンクション）を表すため、VF識別子は1オフセットされます。例えば：

... user-def 0x800000002 ...

仮想ファンクション7（8から1を引いた値）にトラフィックを、そのVFのキュー2にリダイレクトします。

これらのフィルタは内部ルーティングルールを破壊せず、指定された仮想ファンクションに送信されないはずだったトラフィックをルーティングしません。

ジャンボフレーム¶

ジャンボフレームのサポートは、最大送信ユニット（MTU）をデフォルト値1500より大きい値に変更することで有効になります。

ifconfigコマンドを使用してMTUサイズを増やすことができます。例えば、<x>はインターフェース番号で、以下のコマンドを入力してください:

ifconfig eth<x> mtu 9000 up

代わりに、ipコマンドを使用することもできます:

ip link set mtu 9000 dev eth<x>
ip link set up dev eth<x>

この設定は再起動時に保持されません。設定変更を永続化するには、以下のファイルに'MTU=9000'を追加してください:

/etc/sysconfig/network-scripts/ifcfg-eth<x> // for RHEL
/etc/sysconfig/network/<config_file> // for SLES

注意：ジャンボフレームの最大MTU設定は9710です。これはジャンボフレームの最大サイズ9728バイトと一致します。

注意: このドライバーは、ジャンボパケットを受信する際に複数のページサイズのバッファを試行します。これにより、受信パケットの割当時にバッファの枯渇問題を回避するのに役立ちます。

注意：82599ベースのネットワーク接続の場合、仮想ファンクション（VF）でジャンボフレームを有効にする前に、物理ファンクション（PF）でジャンボフレームを有効にする必要があります。VFのMTU設定はPFのMTU設定を超えてはなりません。

NBASE-Tサポート¶

ixgbeドライバーは一部のデバイスでNBASE-Tをサポートしています。ただし、NBASE-T速度のアドバタイズはデフォルトで抑制されており、アドバタイズされたNBASE-T速度に対応できない破損したネットワークスイッチを考慮してこのようにしています。NBASE-T速度のアドバタイズを有効にするには、ethtoolコマンドを使用してください：

ethtool -s eth? advertise 0x1800000001028

LinuxシステムでINTERFACES(5)を使用している場合、/etc/network/interfacesでpre-upコマンドとして指定することで、インターフェースが常にNBASE-Tサポートで起動されるようにできます。例:

iface eth? inet dhcp
     pre-up ethtool -s eth? advertise 0x1800000001028 || true

ジェネリックリシーブオフロード(GRO)¶

ドライバーは、カーネル内でのソフトウェア実装によるGROをサポートしています。GROは、受信トラフィックをより大きなデータチャンクに結合することで、大規模な受信負荷下でのCPU利用率を大幅に削減することが確認されています。GROは以前に使用されていたLROインターフェースの進化版であり、TCP以外のプロトコルにも結合可能です。また、LROが問題となる構成（ブリッジングやiSCSI）でも安全に使用できます。

データセンターブリッジング (DCB)¶

注意: カーネルはTC0が利用可能であることを前提とし、TC0が利用不可の場合、デバイスで優先度フロー制御（PFC）を無効化します。この問題を修正するには、スイッチでDCBを設定する際、TC0が有効になっていることを確認してください。

DCBはハードウェアでの品質保証（Quality of Service）の実装です。VLANプライオリティタグ（802.1p）を使用してトラフィックをフィルタリングします。これにより、トラフィックは8つの異なる優先度にフィルタリングされます。また、優先度フロー制御（802.1Qbb）も有効化され、ネットワークのストレス時にドロップされるパケット数を制限または完全に防止できます。帯域幅はこれらの優先度ごとに割り当てられ、ハードウェアレベルで強制されます（802.1Qaz）。

アダプタファームウェアは、802.1ABおよび803.1Qazに従ってLLDPおよびDCBXプロトコルエージェントを実装します。ファームウェアベースのDCBXエージェントはワイリングモードのみで動作し、DCBX対応のペアから設定を受けることができます。ソフトウェアによるDCBXパラメータの設定（dcbtool/lldptool経由）はサポートされていません。

ixgbeドライバーはDCB netlinkインターフェースレイヤーを実装しており、ユーザー空間とドライバー間の通信を可能にし、ポートのDCB設定を照会できるようにします。

ethtool¶

ドライバーはethtoolインターフェースを使用してドライバーの設定および診断、統計情報の表示を行います。この機能には最新のethtoolバージョンが必要です。ダウンロードはこちら: https://www.kernel.org/pub/software/network/ethtool/

FCoE¶

ixgbeドライバーはファイバー・チャネル・オーバー・イーサネット（FCoE）およびデータセンター・ブリッジング（DCB）をサポートしています。このコードは通常のドライバー動作には影響を与えません。DCBおよびFCoEの設定はこのREADMEの範囲外です。参照してください http://www.open-fcoe.org/ FCoEプロジェクトの情報と連絡先については ixgbe-eedc@lists.sourceforge.net DCBに関する情報については

MACおよびVLANアンチスプーフィング機能¶

悪意のあるドライバーがスプーフィングパケットを送信しようとした場合、ハードウェアによってパケットが破棄され、送信されません。

スプーフィングの試行を通知するため、PFドライバに割り込みが送信されます。スプーフィングされたパケットが検出された場合、PFドライバはシステムログに以下のメッセージを送信します（"dmesg"コマンドで表示されます）：

ixgbe ethX: ixgbe_spoof_check: n spoofed packets detected

ここで "x" は PF インターフェース番号で、"n" はスプーフィングされたパケット数です。注意：この機能は特定の仮想ファンクション（VF）に対して無効化できます：

ip link set <pf dev> vf <vf id> spoofchk {off|on}

IPsec オフロード¶

ixgbeドライバはIPsecハードウェアオフロードをサポートしています。"ip xfrm …"でセキュリティアソシエーション（SA）を作成する際、"offload"タグオプションを使用してIPsec SAをドライバに登録し、セキュアな通信における高いスループットを実現できます。

ixgbeのVFにもオフロードはサポートされていますが、VFは"trusted"として設定され、以下のコマンドでサポートを有効化する必要があります：

ethtool --set-priv-flags eth<x> vf-ipsec on
ip link set eth<x> vf <y> trust on

既知の問題/トラブルシューティング¶

64ビットのMicrosoft Windows Server 2012/R2ゲストOSでのSR-IOVの有効化¶

Linux KVM ハイパーバイザ/VMMは、PCIeデバイスをVMに直接割り当てることをサポートしています。これは従来のPCIeデバイスだけでなく、Intel Ethernet Controller XL710ベースのSR-IOV対応デバイスも含まれます。

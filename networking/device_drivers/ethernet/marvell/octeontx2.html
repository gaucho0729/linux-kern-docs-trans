概要¶

MarvellのOcteonTX2 SoCにおけるリソース仮想化ユニット (RVU)は、ネットワーク、暗号処理などの機能ブロックからPCI互換の物理および仮想機能にハードウェアリソースをマッピングします。各機能ブロックは、PCIデバイスへのプロビジョニングのために複数のローカル機能 (LF) を持ちます。RVUは複数のPCIe SRIOV物理機能 (PF) および仮想機能 (VF) をサポートします。PF0は管理/管理機能 (AF) と呼ばれ、RVU機能ブロックのLFを各PF/VFにプロビジョニングする権限を持ちます。

RVU管理ネットワーク機能ブロック

  • ネットワークプールまたはバッファアロケータ (NPA)

  • ネットワークインターフェースコントローラー (NIX)

  • ネットワークパーサーCAM (NPC)

  • スケジュール/同期/順序ユニット (SSO)

  • ループバックインターフェース (LBK)

RVU管理非ネットワーク機能ブロック

  • 暗号アクセラレータ (CPT)

  • スケジュール済みタイマーユニット (TIM)

  • スケジュール/同期/順序ユニット (SSO) これはネットワークおよび非ネットワーク用途の両方に使用されます

リソースプロビジョニングの例

  • NIX-LFおよびNPA-LFリソースを持つPF/VFは純粋なネットワークデバイスとして機能します

  • CPT-LFリソースを持つPF/VFは純粋な暗号オフロードデバイスとして機能します。

RVU機能ブロックはソフトウェア要件に応じて高度にカスタマイズ可能です。

カーネル起動前のファームウェア設定

  • 物理リンク数に基づいて必要なRVU PFの数を有効にします。

  • 各PFあたりのVF数はコンパイル時に静的または設定可能です。設定に基づきファームウェアは各PFにVFを割り当てます。

  • また各PFおよびVFにMSIXベクターを割り当てます。

  • これらはカーネル起動後は変更されません。

ドライバ¶

LinuxカーネルはRVUのさまざまなPFおよびVFに複数のドライバーを登録します。ネットワークに関しては3つのドライバー種類があります。

管理機能ドライバー¶

上記のようにRVU PF0は管理機能 (AF) と呼ばれます。このドライバーは機能ブロックのリソースプロビジョニングおよび設定をサポートします。I/O処理は行いません。基本的な設定を設定しますが、主にPFおよびVFからの設定リクエストによって機能が実現されます。

PF/VFはAFと共有メモリ領域 (メーラー) を介して通信します。リクエストを受信したAFはリソースプロビジョニングや他のハードウェア設定を行います。AFは常にホストカーネルに接続されていますが、PFおよびそのVFはホストカーネル自身や仮想マシン、DPDKなどのユーザースペースアプリケーションに接続される場合があります。したがってAFは、どのドメインからも送信されるプロビジョニング/設定リクエストを処理する必要があります。

AFドライバーは、下位のファームウェアと相互作用します

  • 物理的なイーサネットリンクを管理します。つまりCGX LMACです。

  • 速度、ダブルックス、オートネゴシエーションなどの情報を取得します。

  • PHY EEPROMおよび統計情報を取得します。

  • FEC、PAMモードを設定します。

  • など

純粋なネットワーキング側では、AFドライバーが以下の機能をサポートします。

  • 物理リンクをnetdevが登録されているRVU PFにマッピングします。

  • NIXおよびNPAブロックのLFを、バッファプール、RQ、SQを提供するRVU PF/VFにアタッチします。

  • フロー制御（パーズフレーム）の有効/無効/設定。

  • ハードウェアPTPタイムスタンプ関連の設定。

  • NPCパーサープロファイルの設定、つまりパケットをどのように解析し、何情報を抽出するか。

  • NPC抽出プロファイルの設定、パケットから何を抽出してMCAMエントリのデータと一致させるか。

  • NPC MCAMエントリを管理し、要請があればフレームを組み、指定されたパケット転送ルールをインストールできます。

  • 受信側スケーリング（RSS）アルゴリズムを定義します。

  • セグメントオフロードアルゴリズム（例：TSO）を定義します。

  • VLANストリピング、キャプチャ、挿入の設定。

  • パケットスケジューリングをサポートするSSOおよびTIMブロックの設定。

  • デバッグ用のdebugfsサポートがあり、現在のリソース提供状況、NPAプール、NIX RQ、SQ、CQなどの現在の状態、さまざまな統計情報などを確認でき、問題のデバッグに役立ちます。

  • その他多数。

物理ファンクションドライバー¶

このRVU PFはIOを処理し、物理イーサネットリンクにマッピングされ、このドライバーはnetdevを登録します。SR-IOVをサポートしています。上記のように、このドライバーはメモリーボックスを介してAFと通信します。物理リンクから情報を取得するには、このドライバーはAFに通信し、AFはファームウェアから情報を取得して応答します。つまり、ファームウェアに直接通信することはできません。

リンク、RSS、キュー数、キューサイズ、フロー制御、ntupleフィルタ、PHY EEPROMのダンプ、FECの設定など、ethtoolをサポートして設定を行います。

仮想ファンクションドライバー¶

2つのタイプのVFがあります。親SR-IOV PFと物理リンクを共有するVFと、内部のHWループバックチャネル（LBK）を使用してペアで動作するVFです。

タイプ1:

  • これらのVFと親PFは物理リンクを共有し、外部通信に使用されます。

  • VFはAFと直接通信できません。mboxメッセージをPFに送信し、PFがAFに中継します。AFが処理を終えたら、PFに応答し、PFがVFに返信します。

  • 機能面ではPFとVFには違いがありません。同じタイプのHWリソースがどちらにもアタッチされています。ただし、ユーザーはPFからのみ一部の設定を行えるため、PFはリンクの所有者/管理者として扱われます。

タイプ2:

  • RVU PF0（管理者機能）がこれらのVFを作成し、ループバックブロックのチャネルにマッピングします。

  • VF0とVF1（VF2とVF3など）といったVFペアは、ペアとして動作します。つまり、VF0から送信されたパケットはVF1で受信され、逆も同様です。

  • これらのVFは、アプリケーションや仮想マシンが外部ネットワーク経由ではなく、直接通信するために使用できます。ハードウェアにスイッチが存在しないため、ループバックVFのサポートが可能となっています。

  • これらは、AF（PF0）と直接mbox経由で通信します。

パケットの受信・送信に使用されるIOチャネルやリンク以外には、これらのVFタイプ間で違いはありません。AFドライバーがIOチャネルの割り当てを担当するため、同一のVFドライバーが両タイプのデバイスに対応可能です。

基本的なパケットフロー¶

イングレス¶

  1. CGX LMACがパケットを受信します。

  2. NIXブロックにパケットを転送します。

  3. 次に、NPCブロックでパース処理を行い、MCAM検索を実施して、宛先RVUデバイスを取得します。

  4. 宛先RVUデバイスにアタッチされたNIX LFが、NPAブロックLFのRQマップバッファプールからバッファを割り当てます。

  5. RQはRSSによって選択されるか、MCAMルールにRQ番号を設定して選択されます。

  6. パケットがDMAで転送され、ドライバーに通知されます。

エグレス¶

  1. ドライバーが送信ディスクリプタを準備し、SQ経由で送信します。

  2. SQはAFによって特定のリンク/チャネルで送信するよう事前に設定されています。

  3. SQディスクリプタリングは、SQマッププールから割り当てられたバッファで維持されます。

  4. NIXブロックが指定されたチャネルでパケットを送信します。

  5. NPC MCAMエントリを設定することで、パケットを別のチャネルに転送できます。

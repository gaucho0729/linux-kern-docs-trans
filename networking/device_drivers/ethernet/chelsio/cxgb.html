Chelsio N210 10Gb Ethernet ネットワークコントローラー¶

Linux用ドライバリリースノート

バージョン 2.1.1

2005年6月20日

はじめに¶

このドキュメントは、Chelsio 10Gb Ethernet Network Controller用のLinuxドライバについて説明しています。このドライバはChelsio N210 NICをサポートし、Chelsio N110モデルの10Gb NICにも後方互換性を持ちます。

機能¶

アダプティブ割込み (adaptive-rx)¶

この機能は、割込みコールセイングパラメータを調整する適応アルゴリズムを提供し、ドライバがさまざまなネットワーク負荷条件下で最大のパフォーマンスを達成するように、遅延設定を動的に調整します。

この機能を制御するインターフェースはethtoolです。追加の使用情報についてはethtoolのmanページをご参照ください。

デフォルトでは、adaptive-rxは無効になっています。adaptive-rxを有効にするには:

ethtool -C <interface> adaptive-rx on

adaptive-rxを無効にするにはethtoolを使用してください:

ethtool -C <interface> adaptive-rx off

adaptive-rxを無効にした後、タイマーラテナシー値が50マイクロ秒に設定されます。adaptive-rxを無効にした後でタイマーラテナシー値を設定することもできます:

ethtool -C <interface> rx-usecs <microseconds>

eth0でタイマーラテナシー値を100マイクロ秒に設定する例:

ethtool -C eth0 rx-usecs 100

adaptive-rxを無効にしている間にタイマーラテナシー値を指定することもできます:

ethtool -C <interface> adaptive-rx off rx-usecs <microseconds>

adaptive-rxが無効になっておりタイマーラテナシー値が指定されている場合、タイマーセットはユーザーが変更するか、adaptive-rxが有効になるまで指定された値に設定されます。

adaptive-rxおよびタイマーラテナシー値の状態を確認するには:

ethtool -c <interface>

TCPセグメンテーションオフローディング (TSO) サポート¶

この機能は「大送信」とも呼ばれており、システムのプロトコルスタックがネットワークインターフェースカードに送信TCP処理の一部をオフロードすることで、システムCPUの使用率を削減しパフォーマンスを向上させます。

この機能を制御するインターフェースはethtoolバージョン1.8以上です。追加の使用情報についてはethtoolのmanページをご参照ください。

デフォルトではTSOは有効になっています。TSOを無効にするには:

ethtool -K <interface> tso off

TSOを有効にするには:

ethtool -K <interface> tso on

TSOの状態を確認するには:

ethtool -k <interface>

パフォーマンス¶

以下に、パフォーマンスチューニングに使用するシステムパラメータの変更方法と、使用する値の例を示します。サーバー/ワークステーションアプリケーションに応じて、これらのシステムパラメータを変更するかどうかは任意です。Chelsio Communicationsはこれを何らかの保証なしに推奨しておりません。変更によるデータの喪失や機器への損害についてはChelsioは責任を負いません。

ご使用のディストリビューションでは異なる方法がある場合もありますし、ご自身の好みの方法を採用することもできます。これらのコマンドは、実施すべきことの例を示すためのみに示されており、何らの決定的なものではありません。

以下のシステム変更を行うと、システムの再起動まで効果が続きます。システムの最適な設定を含む、起動時に実行されるスクリプトを作成することを検討してください。

PCI Latency Timerの設定:

setpci -d 1425::

  • 0x0c.l=0x0000F800

    TCP timestampの無効化:

    sysctl -w net.ipv4.tcp_timestamps=0

    SACKの無効化:

    sysctl -w net.ipv4.tcp_sack=0

    多数の受信接続要求の設定:

    sysctl -w net.ipv4.tcp_max_syn_backlog=3000

    最大受信ソケットバッファサイズの設定:

    sysctl -w net.core.rmem_max=1024000

    最大送信ソケットバッファサイズの設定:

    sysctl -w net.core.wmem_max=1024000

    マルチプロセッサシステムにおけるsmp_affinityを単一のCPUに設定:

    echo 1 > /proc/irq/<interrupt_number>/smp_affinity

    受信ソケットバッファサイズの初期値設定:

    sysctl -w net.core.rmem_default=524287

    送信ソケットバッファサイズの初期値設定:

    sysctl -w net.core.wmem_default=524287

    最大オプションメモリバッファの設定:

    sysctl -w net.core.optmem_max=524287

    最大バックログ（未処理パケット数の上限、カーネルが破棄するまで）の設定:

    sysctl -w net.core.netdev_max_backlog=300000

    TCP読み取りバッファ（最小/初期値/最大）の設定:

    sysctl -w net.ipv4.tcp_rmem="10000000 10000000 10000000"

    TCP書き込みバッファ（最小/圧力/最大）の設定:

    sysctl -w net.ipv4.tcp_wmem="10000000 10000000 10000000"

    TCPバッファ空間（最小/圧力/最大）の設定:

    sysctl -w net.ipv4.tcp_mem="10000000 10000000 10000000"

    単一接続のTCPウィンドウサイズ:

    受信バッファ（RX_WINDOW）のサイズは、送信者と受信者の通信リンクの帯域幅・遅延積（Bandwidth-Delay Product）以上である必要があります。RTT（Round-Trip Time）の変動により、帯域幅・遅延積の2倍程度にバッファサイズを増やすことを検討してください。参考：W. Richard Stevens著『TCP/IP Illustrated, Volume 1, The Protocols』の289ページ。

    10Gb速度の場合、以下の式を使用してください:

    RX_WINDOW >= 1.25MBytes * RTT(in milliseconds)
Example for RTT with 100us: RX_WINDOW = (1,250,000 * 0.1) = 125,000

    RX_WINDOWサイズは256KB〜512KB程度で十分です。

    最小値、最大値、初期値の受信バッファ（RX_WINDOW）サイズの設定:

    sysctl -w net.ipv4.tcp_rmem="<min> <default> <max>"
    複数接続のTCPウィンドウサイズ:

    受信バッファ（RX_WINDOW）サイズは単一接続の場合と同様に計算できますが、接続数で割る必要があります。小さなウィンドウは混雑を防ぎ、特にMACレベルのフロー制御がうまく機能しない場合やサポートされていない機器では、パッキングをより効率的に行うことができます。正しい値を得るために実験が必要な場合があります。この方法は正しい受信バッファサイズの初期値として提供しています。

    単一接続の場合と同様の方法で、最小値、最大値、初期値の受信バッファ（RX_WINDOW）サイズを設定します。

ドライバメッセージ¶

以下のメッセージはsyslogによって最もよくログに記録されるメッセージです。これらは/var/log/messagesに見つけることができます。

ドライバが起動しました:

Chelsio Network Driver - version 2.1.1

NICが検出されました:

eth#: Chelsio N210 1x10GBaseX NIC (rev #), PCIX 133MHz/64-bit

リンクがアップしました:

eth#: link is up at 10 Gbps, full duplex

リンクがダウンしました:

eth#: link is down

既知の問題¶

テスト中に以下の問題が確認されました。以下の情報は問題の回避策として提供されています。一部のケースでは、この問題はLinux自体や特定のLinuxディストリビューション、ハードウェアプラットフォームに固有である可能性があります。

  1. マルチプロセッサ（SMP）システムにおける多数のTCP再送信

    複数のCPUを持つシステムでは、ネットワーク制御機器の割込み（IRQ）が複数のCPUにバインドされることがあります。パケットデータが異なるCPUに分割され、予期しない順序で再構築された場合、TCPの再送が発生します。

    TCPの再送を防ぐには、特定の割込み（IRQ）のsmp_affinityを単一のCPUに設定してください。N110/N210で使用される割込み（IRQ）を確認するにはifconfigを使用します：

    ifconfig <dev_name> | grep Interrupt

    smp_affinityを単一のCPUに設定してください：

    echo 1 > /proc/irq/<interrupt_number>/smp_affinity

    irqbalanceデーモンをシステム上で実行しないことを強く推奨します。このデーモンは10秒間隔で実行され、負荷が最も少ないCPUに割込みをバインドします。これにより、設定したsmp_affinityが上書きされるためです。このデーモンを無効にするには：

    chkconfig --level 2345 irqbalance off

    一部のLinuxディストリビューションでは、irqbalanceというカーネル機能がデフォルトで有効になっています。この機能を無効にするには、ブートローダーに以下の行を追加してください：

    noirqbalance

Example using the Grub bootloader::

    title Red Hat Enterprise Linux AS (2.4.21-27.ELsmp)
    root (hd0,0)
    kernel /vmlinuz-2.4.21-27.ELsmp ro root=/dev/hda3 noirqbalance
    initrd /initrd-2.4.21-27.ELsmp.img

  2. insmodを実行後、ドライバがロードされ、ifupを実行せずに不正なネットワークインターフェースが起動します。

    2.4.xカーネル（RHELカーネルを含む）を使用する場合、Linuxカーネルは「hotplug」と呼ばれるスクリプトを実行します。このスクリプトは主にUSBデバイスを挿すと自動的に起動させますが、カーネルモジュールをロード後にネットワークインターフェースも自動的に起動しようとします。hotplugスクリプトは、/etc/sysconfig/network-scriptsディレクトリ内のifcfg-eth#構成ファイルをスキャンし、HWADDR=<mac_address>を探します。

    hotplugスクリプトがifcfg-eth#ファイル内のHWADDRRを確認しなかった場合、次の利用可能なインターフェース名でデバイスを起動します。このインターフェースが既に別のネットワークカードに設定されている場合、新しいインターフェースのIPアドレスやネットワーク設定が正しくありません。

    この問題を解決するには、ネットワーク制御機器のインターフェース設定ファイルにHWADDR=<mac_address>というキーを追加してください。

    この「hotplug」機能を無効にするには、ドライバ（モジュール名）を/etc/hotplugに存在する「blacklist」ファイルに追加できます。ただし、ネットワークデバイスではnet.agentスクリプトがblacklistファイルを使用しないため、この方法は機能しない可能性があります。代替策として、/etc/hotplug内のnet.agentスクリプトを削除またはリネームしてください。

  3. AMD OpteronシステムでHyperTransport PCI-X Tunnelチップセットを使用して重いマルチ接続トラフィックを実行すると、トランスポートプロトコル（TP）がフリーズします。

    AMD OpteronシステムがAMD-8131 HyperTransport PCI-X Tunnelチップセットを使用している場合、133Mhz PCI-XカードをPCI-Xバス上で使用中に「133-MHzモードスプリットコンプリーションデータ破損」というバグが発生する可能性があります。これはAMDが特定の条件でAMD-8131 PCI-X Tunnelが133Mhzで動作するPCI-Xカードに古いデータをスプリットコンプリーションサイクルで提供することによりデータ破損を引き起こすと識別しています。

    AMDは、「非常に特定の条件下で、AMD-8131 PCI-X Tunnelが133Mhzで動作するPCI-Xカードに古いデータをスプリットコンプリーションサイクルで提供する可能性があり、これによりデータ破損が発生する」と述べています。

    AMDはこの問題に対して3つの対処法を提供していますが、Chelsioはこのバグにおいて性能を最適化するため最初のオプションを推奨しています。

    133Mhzのセカンダリバス運用においては、PCI-XカードのBIOS設定プログラミングを通じて以下の制限を設定することを推奨します：

    データ長（バイト）：1k

    許容される Outstanding トランザクション数：2

    このバグに関する詳細情報およびAMDが提案する対処法については、AMD 8131-HT/PCI-X Errata 26310 Rev 3.08 August 2004、セクション56「133-MHzモードスプリットコンプリーションデータ破損」を参照してください。

    AMDが推奨するPCI-X設定を外れて運用することも可能です。パフォーマンス向上のためにデータ長を2kバイトに増やすことを試してみてください。これらの設定で問題が発生した場合は、「安全な」設定に戻し、問題を再現した上でバグ報告やサポート依頼を行ってください。

    注意

    ほとんどのシステムではデフォルトで8つのOutstandingトランザクションと2kバイトのデータ長が設定されています。

  4. マルチプロセッサシステムでは、10Gbネットワーキングを処理するアプリケーションがCPU間を切り替えることで、パフォーマンスの低下や不安定な動作が報告されています。

    SMPシステム上でパフォーマンス測定を行っている場合、最新のnetperf-2.4.0+を実行するか、Tim Hockinのprocstateユーティリティ（runon）を使用することを推奨します。<http://www.hockin.org/~thockin/procstate/>.

    netserverとnetperf（または他のアプリケーション）を特定のCPUにバインドすると、パフォーマンス測定に大きな違いが生じます。アプリケーションをどのCPUにバインドするかを実験して、システムに最適なパフォーマンスを達成する必要があります。

    10Gbネットワーキング用のアプリケーションを開発している場合、カーネル関数sched_setaffinityとsched_getaffinityを使用してアプリケーションをバインドすることを検討してください。

    ftp、telnetなどのユーザー空間アプリケーションを実行している場合、Tim Hockinのprocstateユーティリティで提供されるrunonツールを試してみてください。また、インターフェースを特定のCPUにバインドする方法として、runon 0 ifup eth0を実行することも可能です。

パケットMMAP¶

要約¶

このファイルは、2.4/2.6/3.x カーネルで PACKET ソケットインターフェースで利用可能な mmap() 機能について記述しています。この種のソケットは

  1. tcpdump などのツールでネットワークトラフィックをキャプチャするため、

  2. ネットワークトラフィックを送信するため、またはネットワークインターフェースへのrawアクセスが必要な他の用途に使用されます。

Howto は以下にあります:

https://sites.google.com/site/packetmmap/

PACKET_MMAP の利用理由¶

Linux 2.4/2.6/3.x において PACKET_MMAP が有効でない場合、キャプチャプロセスは非常に非効率です。非常に限られたバッファを使用し、各パケットのキャプチャには1つのシステムコールが必要で、パケットのタイムスタンプを取得する場合は2つのシステムコールが必要です（libpcap が常にそうします）。

一方で PACKET_MMAP は非常に効率的です。PACKET_MMAP は、ユーザー空間にマップされたサイズを設定可能な環状バッファを提供し、パケットの送受信に使用できます。このようにしてパケットを読み込むには、単に待つだけでよく、ほとんどの場合、1つのシステムコールを実行する必要がありません。送信に関しては、1つのシステムコールで複数のパケットを送信することで最大帯域幅を達成できます。カーネルとユーザー間で共有バッファを使用することにより、パケットのコピーを最小化するという利点もあります。

キャプチャおよび送信プロセスのパフォーマンス向上に PACKET_MMAP を使用するのは良いですが、すべてではありません。少なくとも、高速でキャプチャしている場合（これはCPU速度に依存します）、ネットワークインターフェースカードのドライバが中断負荷軽減機能や（より良い）NAPIをサポートしているか確認してください。また、それが有効になっていることを確認してください。送信に関しては、ネットワークデバイスが使用およびサポートするMTU（Maximum Transmission Unit）を確認してください。ネットワークインターフェースカードのCPU IRQピンニングもメリットとなる場合があります。

mmap() を使用してキャプチャプロセスを改善する方法¶

ユーザーの観点からすれば、rawインターフェースでリンクレベル情報のキャプチャが可能（SOCK_RAW）またはcookedインターフェースでリンクレベル情報のキャプチャがサポートされず、カーネルがリンクレベル擬似ヘッダーを提供する（SOCK_DGRAM）のいずれかを使用する高レベルのlibpcapライブラリを使用すべきです。libpcapは、ほぼすべてのオペレーティングシステム（Win32を含む）で動作する事実上の標準です。

Packet MMAPサポートはlibpcapが1.3.0版の頃に統合され、TPACKET_V3サポートは1.5.0版で追加されました

mmap() を直接使用してキャプチャプロセスを改善する方法¶

システムコールの観点からすると、PACKET_MMAPの使用には以下のプロセスが関与します:

[setup]     socket() -------> creation of the capture socket
            setsockopt() ---> allocation of the circular buffer (ring)
                              option: PACKET_RX_RING
            mmap() ---------> mapping of the allocated buffer to the
                              user process

[capture]   poll() ---------> to wait for incoming packets

[shutdown]  close() --------> destruction of the capture socket and
                              deallocation of all associated
                              resources.

ソケットの作成と破壊は直感的で、PACKET_MMAPを使用するか使用しないかに関わらず同じ方法で行われます:

int fd = socket(PF_PACKET, mode, htons(ETH_P_ALL));

ここで mode は rawインターフェースでリンクレベル情報のキャプチャが可能（SOCK_RAW）またはcookedインターフェースでリンクレベル情報のキャプチャがサポートされず、カーネルがリンクレベル擬似ヘッダーを提供する（SOCK_DGRAM）のいずれかを指定します。

ソケットと関連するすべてのリソースの破壊は、close(fd)という単純な呼び出しで行われます。

PACKET_MMAPなしの場合と同様に、1つのソケットをキャプチャと送信の両方に使用することが可能です。これは、割り当てられたRXとTXバッファリングリングを1回のmmap()呼び出しでマッピングすることで実現できます。詳しくは「環状バッファ（リング）のマッピングと使用方法」を参照してください。

次に、PACKET_MMAPの設定とその制限、ユーザープロセスにおける環状バッファのマッピングおよびこのバッファの使用について説明します。

mmap() を直接使用して送信プロセスを改善する方法¶

送信プロセスはキャプチャと同様です。以下に示します：

[setup]         socket() -------> creation of the transmission socket
                setsockopt() ---> allocation of the circular buffer (ring)
                                  option: PACKET_TX_RING
                bind() ---------> bind transmission socket with a network interface
                mmap() ---------> mapping of the allocated buffer to the
                                  user process

[transmission]  poll() ---------> wait for free packets (optional)
                send() ---------> send all packets that are set as ready in
                                  the ring
                                  The flag MSG_DONTWAIT can be used to return
                                  before end of transfer.

[shutdown]      close() --------> destruction of the transmission socket and
                                  deallocation of all associated resources.

ソケットの作成と破壊も同様に簡単で、前段落で説明したキャプチャと同じ方法で行われます。

int fd = socket(PF_PACKET, mode, 0);

プロトコルは、このソケット経由での送信のみを目的とする場合、0に設定することでpacket_rcv()への高コストな呼び出しを回避できます。この場合、TX_RINGをsll_protocol = 0でバインドする必要があります。それ以外の場合は、htons(ETH_P_ALL)や他のプロトコル（例：）を使用します。

ゼロコピーを用いて、ネットワークインターフェースにソケットをバインドする必要があります。これにより、環状バッファで使用されるフレームのヘッダーサイズを把握できます。

キャプチャと同様に、各フレームは2つの部分から構成されています：

   --------------------
   | struct tpacket_hdr | Header. It contains the status of
   |                    | of this frame
   |--------------------|
   | data buffer        |
   .                    .  Data that will be sent over the network interface.
   .                    .
   --------------------

bind() associates the socket to your network interface thanks to
sll_ifindex parameter of struct sockaddr_ll.

Initialization example::

   struct sockaddr_ll my_addr;
   struct ifreq s_ifr;
   ...

   strncpy (s_ifr.ifr_name, "eth0", sizeof(s_ifr.ifr_name));

   /* get interface index of eth0 */
   ioctl(this->socket, SIOCGIFINDEX, &s_ifr);

   /* fill sockaddr_ll struct to prepare binding */
   my_addr.sll_family = AF_PACKET;
   my_addr.sll_protocol = htons(ETH_P_ALL);
   my_addr.sll_ifindex =  s_ifr.ifr_ifindex;

   /* bind socket to eth0 */
   bind(this->socket, (struct sockaddr *)&my_addr, sizeof(struct sockaddr_ll));

A complete tutorial is available at: https://sites.google.com/site/packetmmap/

デフォルトでは、ユーザーはデータを以下に配置する必要があります：

frame base + TPACKET_HDRLEN - sizeof(struct sockaddr_ll)

したがって、ソケットモード（SOCK_DGRAMまたはSOCK_RAW）を選択しても、ユーザーのデータの開始位置は以下になります：

frame base + TPACKET_ALIGN(sizeof(struct tpacket_hdr))

フレームの開始位置からのカスタムオフセットにユーザーのデータを配置したい場合（SOCK_RAWモードでのペイロードのアライメントなど）、tp_net（SOCK_DGRAMの場合）またはtp_mac（SOCK_RAWの場合）を設定できます。この機能を有効にするには、事前にsetsockopt()でPACKET_TX_HAS_OFFオプションを設定する必要があります。

PACKET_MMAP 設定¶

ユーザー側のコードからPACKET_MMAPを設定するには、以下のような呼び出しが行われます：

  • キャプチャプロセス：

    setsockopt(fd, SOL_PACKET, PACKET_RX_RING, (void *) &req, sizeof(req))

  • 送信プロセス：

    setsockopt(fd, SOL_PACKET, PACKET_TX_RING, (void *) &req, sizeof(req))

前記の呼び出しで最も重要な引数はreqパラメータであり、このパラメータは以下の構造を持つ必要があります：

struct tpacket_req
{
    unsigned int    tp_block_size;  /* Minimal size of contiguous block */
    unsigned int    tp_block_nr;    /* Number of blocks */
    unsigned int    tp_frame_size;  /* Size of frame */
    unsigned int    tp_frame_nr;    /* Total number of frames */
};

この構造は、/usr/include/linux/if_packet.hで定義されており、非交換メモリの環状バッファ（リング）を確立します。キャプチャプロセスでマッピングされることで、システムコールを必要とせずにキャプチャされたフレームおよびタイムスタンプなどの関連メタ情報の読み取りが可能になります。

フレームはブロックにグループ化されます。各ブロックは物理的に連続したメモリ領域であり、tp_block_size/tp_frame_sizeのフレームを保持します。ブロックの総数はtp_block_nrです。tp_frame_nrは冗長なパラメータであることに注意してください：

frames_per_block = tp_block_size/tp_frame_size

実際に、packet_set_ringは以下の条件が真であることを確認します：

frames_per_block * tp_block_nr == tp_frame_nr

例を見てみましょう。以下の値を使用します：

tp_block_size= 4096
tp_frame_size= 2048
tp_block_nr  = 4
tp_frame_nr  = 8

以下のようなバッファ構造が得られます：

        block #1                 block #2
+---------+---------+    +---------+---------+
| frame 1 | frame 2 |    | frame 3 | frame 4 |
+---------+---------+    +---------+---------+

        block #3                 block #4
+---------+---------+    +---------+---------+
| frame 5 | frame 6 |    | frame 7 | frame 8 |
+---------+---------+    +---------+---------+

フレームはブロックに収まる条件を満たす限り、任意のサイズにすることができます。ブロックは整数個のフレームのみを保持でき、つまりフレームは2つのブロックにまたがって生成することはできません。そのため、frame_sizeを選択する際にはいくつかの詳細な点を考慮する必要があります。詳しくは「環状バッファ（リング）のマッピングと使用方法」を参照してください。

PACKET_MMAP 設定制約¶

2.4.26（2.4ブランチ）および2.6.5（2.6ブランチ）以前のカーネルでは、PACKET_MMAPバッファは32ビットアーキテクチャでは32768フレーム、64ビットアーキテクチャでは16384フレームしか保持できませんでした。これらのカーネルバージョンに関する情報については http://pusa.uv.es/~ulisses/packet_mmap/packet_mmap.pre-2.4.26_2.6.5.txt

ブロックサイズの制限¶

前述のように、各ブロックは物理的に連続したメモリ領域です。これらのメモリ領域は__get_free_pages()関数の呼び出しによって割り当てられます。関数名からもわかるように、この関数はメモリページを割り当て、第2引数は「order（ページ数の2の累乗）」を表します。PAGE_SIZE == 4096の場合、order=0 ⇒ 4096バイト、order=1 ⇒ 8192バイト、order=2 ⇒ 16384バイトなどです。__get_free_pagesで割り当て可能な領域の最大サイズはMAX_ORDERマクロによって決定されます。正確には、制限は以下の式で計算されます：

PAGE_SIZE << MAX_ORDER

In a i386 architecture PAGE_SIZE is 4096 bytes
In a 2.4/i386 kernel MAX_ORDER is 10
In a 2.6/i386 kernel MAX_ORDER is 11

したがって、i386アーキテクチャでは2.4/2.6カーネルでget_free_pagesは最大4MBまたは8MBを割り当てることができます。

ユーザー空間のプログラムは/usr/include/sys/user.hおよび/usr/include/linux/mmzone.hをインクルードすることでPAGE_SIZEおよびMAX_ORDERの宣言を取得できます。

また、getpagesize (2)システムコールを用いることで動的にページサイズを取得することも可能です。

ブロック数の制限¶

PACKET_MMAPの制限を理解するには、各ブロックへのポインタを保持する構造体を確認する必要があります。

現在、この構造体はkmallocによって動的に割り当てられたベクター(pg_vec)です。そのサイズは割り当て可能なブロック数を制限します：

+---+---+---+---+
| x | x | x | x |
+---+---+---+---+
  |   |   |   |
  |   |   |   v
  |   |   v  block #4
  |   v  block #3
  v  block #2
 block #1

kmallocは、事前に決められたサイズのメモリプールから物理的に連続したメモリを任意のバイト数割り当てます。このメモリプールはslabアロケータによって管理され、最終的にはアロケーションを担当するため、kmallocが割り当て可能な最大メモリサイズを制限します。

2.4/2.6カーネルおよびi386アーキテクチャでは、制限は131072バイトです。kmallocが使用する事前決められたサイズは、/proc/slabinfoの「size-<bytes>」エントリで確認できます。

32ビットアーキテクチャではポインタが4バイト長いため、ブロックへのポインタの総数は：

131072/4 = 32768 blocks

PACKET_MMAP バッファサイズ計算機¶

定義:

<size-max>

はkmallocで割り当て可能な最大サイズ（/proc/slabinfoを参照）

<pointer size>

はアーキテクチャに依存 – sizeof(void *)

<page size>

はアーキテクチャに依存 – PAGE_SIZE または getpagesize (2)

<max-order>

MAX_ORDERで定義された値です

<frame size>

フレームのキャプチャサイズの上界です（後述します）

これらの定義から導き出します：

<block number> = <size-max>/<pointer size>
<block size> = <pagesize> << <max-order>

したがって、最大バッファサイズは：

<block number> * <block size>

そして、フレーム数は：

<block number> * <block size> / <frame size>

以下のパラメータを仮定します。これは2.6カーネルとi386アーキテクチャに適用されます：

<size-max> = 131072 bytes
<pointer size> = 4 bytes
<pagesize> = 4096 bytes
<max-order> = 11

および<frame size>の値が2048バイトです。これらのパラメータは次の結果をもたらします：

<block number> = 131072/4 = 32768 blocks
<block size> = 4096 << 11 = 8 MiB.

したがって、バッファは262144 MiBのサイズになります。したがって、262144 MiB / 2048バイト = 134217728フレームを保持できます

実際には、i386アーキテクチャではこのバッファサイズは不可能です。メモリはカーネル空間で割り当てられ、i386カーネルの場合、メモリサイズは1GiBに制限されています。

すべてのメモリ割り当てはソケットが閉じるまで解放されません。メモリ割り当てはGFP_KERNEL優先度で行われ、これは割り当てが待機し、他のプロセスのメモリを交換して必要なメモリを確保できるため、通常の制限に達することがあります。

その他の制約¶

ソースコードを確認すると、ここで私が描いているフレームはリンクレベルのフレームだけでなく、各フレームの先頭にstruct tpacket_hdrというヘッダーがあり、PACKET_MMAPで使用され、リンクレベルのフレームのメタ情報（タイムスタンプなど）を保持しています。したがって、ここで描いているフレームは次の通りです（include/linux/if_packet.hより）：

/*
  Frame structure:

  - Start. Frame must be aligned to TPACKET_ALIGNMENT=16
  - struct tpacket_hdr
  - pad to TPACKET_ALIGNMENT=16
  - struct sockaddr_ll
  - Gap, chosen so that packet data (Start+tp_net) aligns to
    TPACKET_ALIGNMENT=16
  - Start+tp_mac: [ Optional MAC header ]
  - Start+tp_net: Packet data, aligned to TPACKET_ALIGNMENT=16.
  - Pad to align to TPACKET_ALIGNMENT=16
*/

以下の条件はpacket_set_ringでチェックされます

  • tp_block_sizeはPAGE_SIZEの倍数でなければなりません（1）

  • tp_frame_sizeはTPACKET_HDRLENより大きくなければなりません（明らか）

  • tp_frame_sizeはTPACKET_ALIGNMENTの倍数でなければなりません

  • tp_frame_nrはframes_per_block*tp_block_nrと厳密に一致しなければなりません

tp_block_sizeは2の累乗にすべきで、それ以外ではメモリの浪費が生じます。

環状バッファ（リング）のマッピングと使用¶

ユーザープロセスにおけるバッファのマッピングは従来のmmap関数で行われます。環状バッファは複数の物理的に離散的なメモリブロックから構成されていますが、ユーザー空間に対して連続しています。したがって、mmap関数の1回の呼び出しだけで十分です：

mmap(0, size, PROT_READ|PROT_WRITE, MAP_SHARED, fd, 0);

tp_frame_sizeがtp_block_sizeの約数である場合、フレームはtp_frame_sizeバイトごとに連続して配置されます。そうでない場合、各tp_block_size/tp_frame_sizeフレームごとにフレーム間のギャップが生じます。これはフレームが2つのブロックをまたがないためです。

キャプチャと送信のための1つのソケットを使用するには、RXとTXのバッファリングリングのマッピングはmmap関数の1回の呼び出しで行う必要があります：

...
setsockopt(fd, SOL_PACKET, PACKET_RX_RING, &foo, sizeof(foo));
setsockopt(fd, SOL_PACKET, PACKET_TX_RING, &bar, sizeof(bar));
...
rx_ring = mmap(0, size * 2, PROT_READ|PROT_WRITE, MAP_SHARED, fd, 0);
tx_ring = rx_ring + size;

RXは最初にマッピングされる必要があります。カーネルはRXのメモリの直後にTXリングのメモリをマッピングするからです。

各フレームの開始位置にはステータスフィールドがあります（struct tpacket_hdrを参照）。このフィールドが0の場合、フレームがカーネルで使用可能であることを意味します。そうでない場合、ユーザーが読み取れるフレームがあり、以下のフラグが適用されます。

キャプチャプロセス¶

include/linux/if_packet.hから

#define TP_STATUS_COPY (1 << 1) #define TP_STATUS_LOSING (1 << 2) #define TP.CSUMNOTREADY (1 << 3) #define TP_STATUS_CSUM_VALID (1 << 7)

TP_STATUS_COPY

このフラグは、フレーム（および関連するメタ情報）がtp_frame_sizeよりも大きいことにより切り捨てられたことを示します。このパケットはrecvfrom()で完全に読み取ることができます。

この機能を使用するには、事前にsetsockopt()でPACKET_COPY_THRESHオプションを有効にする必要があります。

recvfrom()で読み取れるバッファーフレーム数は、通常のソケットと同様に制限されます。socket(7)マニュアルページのSO_RCVBUFオプションを参照してください。

TP_STATUS_LOSING

getsockopt()でPACKET_STATISTICSオプションを使用して最後の統計を確認した際のパケットドロップが発生したことを示します。

TP_STATUS_CSUMNOTREADY

これは、ハードウェアでチェックサムが計算される出力IPパケットに現在使用されています。パケットを読み取る際にはチェックサムの確認を行わないでください。

TP_STATUS_CSUM_VALID

このフラグは、パケットのトランスポートヘッダーチェックサムがカーネル側で既に検証されていることを示します。このフラグが設定されていない場合、TP_STATUS_CSUMNOTREADYが設定されていない限り、自分自身でチェックサムを確認できます。

便利のため、以下の定義も用意されています:

#define TP_STATUS_KERNEL        0
#define TP_STATUS_USER          1

カーネルはすべてのフレームをTP_STATUS_KERNELに初期化します。カーネルがパケットを受信すると、バッファに保存し、少なくともTP_STATUS_USERフラグでステータスを更新します。その後、ユーザーがパケットを読み取ることができ、パケットが読み取られた後はユーザーがステータスフィールドをゼロにしなければなりません。これにより、カーネルが再度そのフレームバッファを使用できるようになります。

ユーザーはpoll（他の変体も適用可能）を使用してリングに新しいパケットがあるかを確認できます:

struct pollfd pfd;

pfd.fd = fd;
pfd.revents = 0;
pfd.events = POLLIN|POLLRDNORM|POLLERR;

if (status == TP_STATUS_KERNEL)
    retval = poll(&pfd, 1, timeout);

ステータス値を確認した後でpollでフレームを待機する場合でもレース条件にはなりません。

送信プロセス¶

これらの定義は送信にも使用されます:

#define TP_STATUS_AVAILABLE        0 // Frame is available
#define TP_STATUS_SEND_REQUEST     1 // Frame will be sent on next send()
#define TP_STATUS_SENDING          2 // Frame is currently in transmission
#define TP_STATUS_WRONG_FORMAT     4 // Frame format is not correct

まず、カーネルはすべてのフレームをTP_STATUS_AVAILABLEに初期化します。パケットを送信するには、ユーザーが利用可能なフレームのデータバッファを埋め、tp_lenを現在のデータバッファサイズに設定し、ステータスフィールドをTP_STATUS_SEND_REQUESTに設定します。これは複数のフレームでも可能です。ユーザーが送信準備ができたらsend()を呼び出します。これにより、ステータスがTP_STATUS_SEND_REQUESTに設定されているすべてのバッファがネットワークデバイスに転送されます。カーネルは送信中のフレームのステータスをTP_STATUS_SENDINGに更新し、転送完了まで続きます。

各転送終了時に、バッファのステータスは再びTP_STATUS_AVAILABLEに戻ります。

header->tp_len = in_i_size;
header->tp_status = TP_STATUS_SEND_REQUEST;
retval = send(this->socket, NULL, 0, 0);

ユーザーはpoll()を使用して、バッファが利用可能かどうかを確認することもできます:

(status == TP_STATUS_SENDING)

struct pollfd pfd;
pfd.fd = fd;
pfd.revents = 0;
pfd.events = POLLOUT;
retval = poll(&pfd, 1, timeout);

利用可能な TPACKET バージョンとその利用タイミング¶

int val = tpacket_version;
setsockopt(fd, SOL_PACKET, PACKET_VERSION, &val, sizeof(val));
getsockopt(fd, SOL_PACKET, PACKET_VERSION, &val, sizeof(val));

ここで‘tpacket_version’はTPACKET_V1（デフォルト）, TPACKET_V2, TPACKET_V3のいずれかです。

TPACKET_V1:

  • setsockopt(2)で明示的に指定されていない場合のデフォルト値です

  • RX_RING, TX_RINGが利用可能です

TPACKET_V1 –> TPACKET_V2:

  • TPACKET_V1構造体におけるunsigned longの使用により64ビット環境にも対応し、32ビットユーザースペースと64ビットカーネルの組み合わせでも動作します

  • タイムスタンプの解像度がナノ秒からマイクロ秒に変更されました

  • RX_RING, TX_RINGが利用可能です

  • tpacket2_hdr構造体において、パケットのVLANメタデータ情報が利用可能です（TP_STATUS_VLAN_VALID, TP_STATUS_VLAN_TPID_VALID）:

    • tp_statusフィールドにTP_STATUS_VLAN_VALIDビットが設定されている場合、tp_vlan_tciフィールドに有効なVLAN TCI値が含まれています

    • tp_statusフィールドにTP_STATUS_VLAN_TPID_VALIDビットが設定されている場合、tp_vlan_tpidフィールドに有効なVLAN TPID値が含まれています

  • TPACKET_V2への切り替え方法:

    1. struct tpacket_hdrをstruct tpacket2_hdrに置き換えます

    2. ヘッダ長を確認し、保存します

    3. プロトコルバージョンを2に設定し、通常通りリングを設定します

    4. sockaddr_llを取得するには、 (void *)hdr + TPACKET_ALIGN(hdrlen) …の代わりに (void *)hdr + TPACKET_ALIGN(sizeof(struct tpacket_hdr))

TPACKET_V2 –> TPACKET_V3:
  • RX_RINGにおける柔軟なバッファ実装:

    1. ブロックは非静的なフレームサイズで構成可能です

    2. 読み取り/ポーリングはブロックレベルで行われます（パケットレベルとは異なります）

    3. 無限のユーザースペース待機を避けるため、ポーリングタイムアウトを追加しました

    4. ユーザー設定可能な設定項目を追加しました:

      4.1 block::timeout 4.2 tpkt_hdr::sk_rxhash

  • RXハッシュデータがユーザースペースで利用可能です

  • TX_RINGのセマンティクスはTPACKET_V2と概念的に類似しています。tpacket3_hdrをtpacket2_hdrに、TPACKET3_HDRLENをTPACKET2_HDRLENに使用します。現在の実装では、tpacket3_hdrのtp_next_offsetフィールドをゼロに設定しなければなりません。これはリングが可変長フレームを保持しないことを示します。tp_next_offsetがゼロ以外の値を持つパケットは無視されます。

AF_PACKET ファノットモード¶

AF_PACKETファンアウトモードでは、パケット受信をプロセス間で負荷分散できます。これはパケットソケットとmmap(2)を組み合わせて使用することも可能です。

現在実装されているファンアウトポリシーは以下の通りです:

  • PACKET_FANOUT_HASH: skbのパケットハッシュに基づいてソケットにスケジュールを割り当てる

  • PACKET_FANOUT_LB: ラウンドロビン方式でソケットにスケジュールを割り当てる

  • PACKET_FANOUT_CPU: パケット到着したCPUに基づいてソケットにスケジュールを割り当てる

  • PACKET_FANOUT_RND: ランダム選択でソケットにスケジュールを割り当てる

  • PACKET_FANOUT_ROLLOVER: 1つのソケットが満杯になった場合、別のソケットにロールオーバーする

  • PACKET_FANOUT_QM: skbsの記録されたキュー_マッピングに基づいてソケットにスケジュールを割り当てる

David S. Millerによる最小限の例コード（「./test eth0 hash」「./test eth0 lb」など試してみてください）:

#include <stddef.h>
#include <stdlib.h>
#include <stdio.h>
#include <string.h>

#include <sys/types.h>
#include <sys/wait.h>
#include <sys/socket.h>
#include <sys/ioctl.h>

#include <unistd.h>

#include <linux/if_ether.h>
#include <linux/if_packet.h>

#include <net/if.h>

static const char *device_name;
static int fanout_type;
static int fanout_id;

#ifndef PACKET_FANOUT
# define PACKET_FANOUT                      18
# define PACKET_FANOUT_HASH         0
# define PACKET_FANOUT_LB           1
#endif

static int setup_socket(void)
{
        int err, fd = socket(AF_PACKET, SOCK_RAW, htons(ETH_P_IP));
        struct sockaddr_ll ll;
        struct ifreq ifr;
        int fanout_arg;

        if (fd < 0) {
                perror("socket");
                return EXIT_FAILURE;
        }

        memset(&ifr, 0, sizeof(ifr));
        strcpy(ifr.ifr_name, device_name);
        err = ioctl(fd, SIOCGIFINDEX, &ifr);
        if (err < 0) {
                perror("SIOCGIFINDEX");
                return EXIT_FAILURE;
        }

        memset(&ll, 0, sizeof(ll));
        ll.sll_family = AF_PACKET;
        ll.sll_ifindex = ifr.ifr_ifindex;
        err = bind(fd, (struct sockaddr *) &ll, sizeof(ll));
        if (err < 0) {
                perror("bind");
                return EXIT_FAILURE;
        }

        fanout_arg = (fanout_id | (fanout_type << 16));
        err = setsockopt(fd, SOL_PACKET, PACKET_FANOUT,
                        &fanout_arg, sizeof(fanout_arg));
        if (err) {
                perror("setsockopt");
                return EXIT_FAILURE;
        }

        return fd;
}

static void fanout_thread(void)
{
        int fd = setup_socket();
        int limit = 10000;

        if (fd < 0)
                exit(fd);

        while (limit-- > 0) {
                char buf[1600];
                int err;

                err = read(fd, buf, sizeof(buf));
                if (err < 0) {
                        perror("read");
                        exit(EXIT_FAILURE);
                }
                if ((limit % 10) == 0)
                        fprintf(stdout, "(%d) \n", getpid());
        }

        fprintf(stdout, "%d: Received 10000 packets\n", getpid());

        close(fd);
        exit(0);
}

int main(int argc, char **argp)
{
        int fd, err;
        int i;

        if (argc != 3) {
                fprintf(stderr, "Usage: %s INTERFACE {hash|lb}\n", argp[0]);
                return EXIT_FAILURE;
        }

        if (!strcmp(argp[2], "hash"))
                fanout_type = PACKET_FANOUT_HASH;
        else if (!strcmp(argp[2], "lb"))
                fanout_type = PACKET_FANOUT_LB;
        else {
                fprintf(stderr, "Unknown fanout type [%s]\n", argp[2]);
                exit(EXIT_FAILURE);
        }

        device_name = argp[1];
        fanout_id = getpid() & 0xffff;

        for (i = 0; i < 4; i++) {
                pid_t pid = fork();

                switch (pid) {
                case 0:
                        fanout_thread();

                case -1:
                        perror("fork");
                        exit(EXIT_FAILURE);
                }
        }

        for (i = 0; i < 4; i++) {
                int status;

                wait(&status);
        }

        return 0;
}

AF_PACKET TPACKET_V3 例¶

AF_PACKETのTPACKET_V3リングバッファは、独自のメモリ管理により非静的フレームサイズを設定可能で、ブロックベースのポーリングが行われます。これはTPACKET_V2およびその前身と異なり、リング単位ではなくブロック単位で動作します。

TPACKET_V3は以下のメリットがあるとされています:

  • ~15% - 20%のCPU使用率削減

  • ~20%のパケットキャプチャ率向上

  • ~2倍のパケット密度向上

  • ポートアグリゲーション分析

  • 非静的フレームサイズでパケットペイロード全体をキャプチャ可能

これらから、パケットファンアウトと組み合わせて使用するのに適していると考えられます。

Daniel BorkmannによるChetan Lokeのlolpcapに基づく最小限の例コード（gcc -Wall -O2 blob.cでコンパイルし、「./a.out eth0」など試してみてください）:

/* Written from scratch, but kernel-to-user space API usage
* dissected from lolpcap:
*  Copyright 2011, Chetan Loke <loke.chetan@gmail.com>
*  License: GPL, version 2.0
*/

#include <stdio.h>
#include <stdlib.h>
#include <stdint.h>
#include <string.h>
#include <assert.h>
#include <net/if.h>
#include <arpa/inet.h>
#include <netdb.h>
#include <poll.h>
#include <unistd.h>
#include <signal.h>
#include <inttypes.h>
#include <sys/socket.h>
#include <sys/mman.h>
#include <linux/if_packet.h>
#include <linux/if_ether.h>
#include <linux/ip.h>

#ifndef likely
# define likely(x)          __builtin_expect(!!(x), 1)
#endif
#ifndef unlikely
# define unlikely(x)                __builtin_expect(!!(x), 0)
#endif

struct block_desc {
        uint32_t version;
        uint32_t offset_to_priv;
        struct tpacket_hdr_v1 h1;
};

struct ring {
        struct iovec *rd;
        uint8_t *map;
        struct tpacket_req3 req;
};

static unsigned long packets_total = 0, bytes_total = 0;
static sig_atomic_t sigint = 0;

static void sighandler(int num)
{
        sigint = 1;
}

static int setup_socket(struct ring *ring, char *netdev)
{
        int err, i, fd, v = TPACKET_V3;
        struct sockaddr_ll ll;
        unsigned int blocksiz = 1 << 22, framesiz = 1 << 11;
        unsigned int blocknum = 64;

        fd = socket(AF_PACKET, SOCK_RAW, htons(ETH_P_ALL));
        if (fd < 0) {
                perror("socket");
                exit(1);
        }

        err = setsockopt(fd, SOL_PACKET, PACKET_VERSION, &v, sizeof(v));
        if (err < 0) {
                perror("setsockopt");
                exit(1);
        }

        memset(&ring->req, 0, sizeof(ring->req));
        ring->req.tp_block_size = blocksiz;
        ring->req.tp_frame_size = framesiz;
        ring->req.tp_block_nr = blocknum;
        ring->req.tp_frame_nr = (blocksiz * blocknum) / framesiz;
        ring->req.tp_retire_blk_tov = 60;
        ring->req.tp_feature_req_word = TP_FT_REQ_FILL_RXHASH;

        err = setsockopt(fd, SOL_PACKET, PACKET_RX_RING, &ring->req,
                        sizeof(ring->req));
        if (err < 0) {
                perror("setsockopt");
                exit(1);
        }

        ring->map = mmap(NULL, ring->req.tp_block_size * ring->req.tp_block_nr,
                        PROT_READ | PROT_WRITE, MAP_SHARED | MAP_LOCKED, fd, 0);
        if (ring->map == MAP_FAILED) {
                perror("mmap");
                exit(1);
        }

        ring->rd = malloc(ring->req.tp_block_nr * sizeof(*ring->rd));
        assert(ring->rd);
        for (i = 0; i < ring->req.tp_block_nr; ++i) {
                ring->rd[i].iov_base = ring->map + (i * ring->req.tp_block_size);
                ring->rd[i].iov_len = ring->req.tp_block_size;
        }

        memset(&ll, 0, sizeof(ll));
        ll.sll_family = PF_PACKET;
        ll.sll_protocol = htons(ETH_P_ALL);
        ll.sll_ifindex = if_nametoindex(netdev);
        ll.sll_hatype = 0;
        ll.sll_pkttype = 0;
        ll.sll_halen = 0;

        err = bind(fd, (struct sockaddr *) &ll, sizeof(ll));
        if (err < 0) {
                perror("bind");
                exit(1);
        }

        return fd;
}

static void display(struct tpacket3_hdr *ppd)
{
        struct ethhdr *eth = (struct ethhdr *) ((uint8_t *) ppd + ppd->tp_mac);
        struct iphdr *ip = (struct iphdr *) ((uint8_t *) eth + ETH_HLEN);

        if (eth->h_proto == htons(ETH_P_IP)) {
                struct sockaddr_in ss, sd;
                char sbuff[NI_MAXHOST], dbuff[NI_MAXHOST];

                memset(&ss, 0, sizeof(ss));
                ss.sin_family = PF_INET;
                ss.sin_addr.s_addr = ip->saddr;
                getnameinfo((struct sockaddr *) &ss, sizeof(ss),
                            sbuff, sizeof(sbuff), NULL, 0, NI_NUMERICHOST);

                memset(&sd, 0, sizeof(sd));
                sd.sin_family = PF_INET;
                sd.sin_addr.s_addr = ip->daddr;
                getnameinfo((struct sockaddr *) &sd, sizeof(sd),
                            dbuff, sizeof(dbuff), NULL, 0, NI_NUMERICHOST);

                printf("%s -> %s, ", sbuff, dbuff);
        }

        printf("rxhash: 0x%x\n", ppd->hv1.tp_rxhash);
}

static void walk_block(struct block_desc *pbd, const int block_num)
{
        int num_pkts = pbd->h1.num_pkts, i;
        unsigned long bytes = 0;
        struct tpacket3_hdr *ppd;

        ppd = (struct tpacket3_hdr *) ((uint8_t *) pbd +
                                    pbd->h1.offset_to_first_pkt);
        for (i = 0; i < num_pkts; ++i) {
                bytes += ppd->tp_snaplen;
                display(ppd);

                ppd = (struct tpacket3_hdr *) ((uint8_t *) ppd +
                                            ppd->tp_next_offset);
        }

        packets_total += num_pkts;
        bytes_total += bytes;
}

static void flush_block(struct block_desc *pbd)
{
        pbd->h1.block_status = TP_STATUS_KERNEL;
}

static void teardown_socket(struct ring *ring, int fd)
{
        munmap(ring->map, ring->req.tp_block_size * ring->req.tp_block_nr);
        free(ring->rd);
        close(fd);
}

int main(int argc, char **argp)
{
        int fd, err;
        socklen_t len;
        struct ring ring;
        struct pollfd pfd;
        unsigned int block_num = 0, blocks = 64;
        struct block_desc *pbd;
        struct tpacket_stats_v3 stats;

        if (argc != 2) {
                fprintf(stderr, "Usage: %s INTERFACE\n", argp[0]);
                return EXIT_FAILURE;
        }

        signal(SIGINT, sighandler);

        memset(&ring, 0, sizeof(ring));
        fd = setup_socket(&ring, argp[argc - 1]);
        assert(fd > 0);

        memset(&pfd, 0, sizeof(pfd));
        pfd.fd = fd;
        pfd.events = POLLIN | POLLERR;
        pfd.revents = 0;

        while (likely(!sigint)) {
                pbd = (struct block_desc *) ring.rd[block_num].iov_base;

                if ((pbd->h1.block_status & TP_STATUS_USER) == 0) {
                        poll(&pfd, 1, -1);
                        continue;
                }

                walk_block(pbd, block_num);
                flush_block(pbd);
                block_num = (block_num + 1) % blocks;
        }

        len = sizeof(stats);
        err = getsockopt(fd, SOL_PACKET, PACKET_STATISTICS, &stats, &len);
        if (err < 0) {
                perror("getsockopt");
                exit(1);
        }

        fflush(stdout);
        printf("\nReceived %u packets, %lu bytes, %u dropped, freeze_q_cnt: %u\n",
            stats.tp_packets, bytes_total, stats.tp_drops,
            stats.tp_freeze_q_cnt);

        teardown_socket(&ring, fd);
        return 0;
}

PACKET_QDISC_BYPASS¶

pktgenが行うように多数のパケットをネットワークに負荷をかけたい場合、ソケット作成後に以下のオプションを設定できます:

int one = 1;
setsockopt(fd, SOL_PACKET, PACKET_QDISC_BYPASS, &one, sizeof(one));

これにより、PF_PACKET経由で送信されるパケットはカーネルのqdiscレイヤーをバイパスし、ドライバに直接押し出されます。つまり、パケットはバッファされず、tcディスシプリンが無視され、損失が増加する可能性があり、他のPF_PACKETソケットには表示されなくなります。ご注意ください。一般的に、これはシステムのさまざまなコンポーネントのストレステストに有用です。

デフォルトではPACKET_QDISC_BYPASSは無効で、PF_PACKETソケットで明示的に有効にする必要があります。

PACKET_TIMESTAMP¶

PACKET_TIMESTAMPの設定は、mmap(2)されたRX_RINGとTX_RINGのパケットメタ情報におけるタイムスタンプのソースを決定します。NICがハードウェアでタイムスタンプを生成できる場合、そのハードウェアタイムスタンプを要求できます。注意: ハードウェアタイムスタンプの生成を有効にするにはSIOCSHWTSTAMPを有効にする必要があります（関連情報については、以下を参照してください タイムスタンピング).

PACKET_TIMESTAMPはSO_TIMESTAMPINGと同じ整数ビットフィールドを受け取ります:

int req = SOF_TIMESTAMPING_RAW_HARDWARE;
setsockopt(fd, SOL_PACKET, PACKET_TIMESTAMP, (void *) &req, sizeof(req))

mmap(2)されたリングバッファでは、このようなタイムスタンプは tpacket{,2,3}_hdr 構造体のtp_secと tp_{n,u}sec メンバ。tp_statusフィールドが以下の可能なビットとビナリORされるため、報告されたタイムスタンプの種類を確認できます…

TP_STATUS_TS_RAW_HARDWARE
TP_STATUS_TS_SOFTWARE

…その対応する値と同等です。 SOF_TIMESTAMPING_* RX_RINGの場合、どちらも設定されていない（つまりPACKET_TIMESTAMPが設定されていない）場合、ソフトウェアのフォールバックが実行されました。 の PF_PACKETの処理コード（精度が低い）。

TX_RINGのタイムスタンプ取得は以下の手順で行われます：i) リングフレームを埋める、ii) sendto()を呼び出す（例：ブロッキングモードで）、iii) 関連するフレームのステータスが更新されるのを待つか、アプリケーションに渡されたフレームのステータスを待つ、iv) フレームを走査して個々のハードウェア/ソフトウェアタイムスタンプを取得します。

送信タイムスタンピングが有効な場合のみ、これらのビットはTP_STATUS_AVAILABLEとビナリORされます。したがって、アプリケーションではこれを確認する必要があります（例：!(tp_status & (TP_STATUS_SEND_REQUEST | TP_STATUS_SENDING))で、フレームがアプリケーションに属するかを確認し、その後tp_statusからタイムスタンプの種類を抽出します）！

これらに興味がない場合、つまり無効にしている場合、TP_STATUS_AVAILABLEまたはTP_STATUS_WRONG_FORMATの確認で十分です。TX_RING部分でTP_STATUS_AVAILABLEのみが設定されている場合、tp_secおよびtp_{n,u}secメンバには有効な値が含まれていません。TX_RINGではデフォルトではタイムスタンプが生成されません！

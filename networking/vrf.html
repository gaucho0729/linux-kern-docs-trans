仮想ルーティングおよびフォワーディング (VRF)¶

VRFデバイス¶

VRFデバイスとipルールの組み合わせにより、Linuxネットワークスタック内で仮想ルーティングとフォワーディングドメイン（VRF、具体的にはVRF-lite）を作成できるようになります。一つの使用例はマルチテナント問題で、各テナントが独自のルーティングテーブルを持ち、少なくともデフォルトゲートウェイが異なる必要があるケースです。

プロセスはVRFデバイスにソケットをバインドすることで「VRFを意識した」状態になります。その結果、ソケットを通るパケットはVRFデバイスに関連付けられたルーティングテーブルを使用します。VRFデバイスの実装の重要な特徴は、レイヤー3以上にのみ影響を与えるため、L2ツール（例：LLDP）は影響を受けません（つまり、各VRFごとに実行する必要はありません）。設計上、より優先度の高いipルール（ポリシーベースルーティング、PBR）をVRFデバイスのルールよりも優先して使用できるようにしています。

さらに、VRFデバイスはネットワークネームスペース内にVRFをネストする機能も提供します。例えばネットワークネームスペースはデバイス層でネットワークインターフェースを分離し、ネームスペース内のインターフェース上のVLANはL2分離を提供し、VRFデバイスはL3分離を提供します。

設計¶

VRFデバイスは関連付けられたルーティングテーブルとともに作成されます。ネットワークインターフェースはその後、VRFデバイスに所属させられます：

+-----------------------------+
|           vrf-blue          |  ===> route table 10
+-----------------------------+
   |        |            |
+------+ +------+     +-------------+
| eth1 | | eth2 | ... |    bond1    |
+------+ +------+     +-------------+
                         |       |
                     +------+ +------+
                     | eth8 | | eth9 |
                     +------+ +------+

受信された所属デバイスのパケットはIPv4およびIPv6処理スタック内でVRFデバイスに切り替えられ、パケットがVRFデバイスを通るかのように見えるようになります。同様に、出力時にルーティングルールが使用され、パケットはVRFデバイスドライバに送られ、その後実際のインターフェースから送出されます。これにより、VRFデバイス上のtcpdumpはVRF全体の入出力パケットをキャプチャできます。1。同様に、netfilter2 およびtcルールもVRFデバイスを使用して、VRFドメイン全体に適用されるルールを指定できます。

1

転送状態のパケットはデバイスを通らないため、tcpdumpで確認できません。この制限については今後のリリースで再検討します。

2

イングレス時のiptablesはPREROUTINGルールをサポートし、skb->devは実際のイングレスデバイスに設定され、INPUTおよびPREROUTINGルールはskb->devがVRFデバイスに設定されます。エグレス時のPOSTROUTINGおよびOUTPUTルールは、VRFデバイスまたは実際のエグレスデバイスのいずれかを使用して記述できます。

設定¶

  1. VRFデバイスはFIBテーブルと関連付けられて作成されます。例：

    ip link add vrf-blue type vrf table 10
ip link set dev vrf-blue up

  2. l3mdev FIBルールは、デバイスに関連するテーブルへのルックアップを指示します。1つのl3mdevルールですべてのVRFに対応可能です。最初のデバイスがデフォルトの優先度1000で作成されるとき、VRFデバイスはIPv4およびIPv6用のl3mdevルールを追加します。必要に応じてユーザーはこのルールを削除し、異なる優先度で追加したり、VRFごとのルールをインストールできます。

    v4.8カーネル以前では、各VRFデバイスに対してiifおよびoifルールが必要でした：

    ip ru add oif vrf-blue table 10
ip ru add iif vrf-blue table 10

  3. テーブル（およびしたがってVRFのデフォルトルート）のデフォルトルートを設定します：

    ip route add table 10 unreachable default metric 4278198272

    この高いメトリック値は、ルーティングプロトコルによってデフォルトの到達不能ルートを上書きできるようにします。FRRoutingはカーネルメトリックを管理距離（上位バイト）と優先度（下位3バイト）の組み合わせとして解釈します。したがって、上記のメトリックは[255/8192]に翻訳されます。

  4. L3インターフェースをVRFデバイスに所属させます：

    ip link set dev eth1 master vrf-blue

    所属させたデバイスのローカルおよび接続ルートは、自動的にVRFデバイスに関連するテーブルに移動します。所属させたデバイスに依存する追加のルートは削除され、所属後のVRF FIBテーブルに再挿入する必要があります。

    IPv6 sysctlオプションkeep_addr_on_downを有効にすると、VRF所属の変更に伴ってIPv6グローバルアドレスを保持できます：

    sysctl -w net.ipv6.conf.all.keep_addr_on_down=1

  5. 追加のVRFルートが関連するテーブルに追加されます：

    ip route add table 10 ...

アプリケーション¶

VRF内で動作するアプリケーションは、ソケットをVRFデバイスにバインドする必要があります：

setsockopt(sd, SOL_SOCKET, SO_BINDTODEVICE, dev, strlen(dev)+1);

またはcmsgとIP_PKTINFOを使用して出力デバイスを指定します。

未バインドソケットのポートバインディングのスコープはデフォルトVRFに限定されます。つまり、l3mdevに所属するインターフェースからのパケットには一致せず、プロセスはl3mdevにバインドすることで同じポートにバインドできます。

デフォルトVRFコンテキスト（つまり、どのVRFデバイスにもバインドされていない）で動作するTCP & UDPサービスは、tcp_l3mdev_acceptおよびudp_l3mdev_accept sysctlオプションを有効にすることで、すべてのVRFドメインを横断して動作できます：

sysctl -w net.ipv4.tcp_l3mdev_accept=1
sysctl -w net.ipv4.udp_l3mdev_accept=1

これらのオプションはデフォルトで無効なので、ソケットはそのVRFのパケットのみを選択します。RAWソケットには類似のオプションがあり、後方互換性のためデフォルトで有効です。これは、cmsgとIP_PKTINFOを使用して出力デバイスを指定するためのものです。ただし、対応するVRFにバインドされていないソケットを使用します。これにより、例えば古いping実装をデバイスを指定して実行できますが、VRF内で実行する必要はありません。このオプションは無効にすることで、VRFコンテキストで受信したパケットはVRFにバインドされたRAWソケットのみで処理され、デフォルトVRFのパケットはバインドされていないソケットのみで処理されます：

sysctl -w net.ipv4.raw_l3mdev_accept=0

VRFデバイス上のnetfilterルールは、デフォルトのVRFコンテキストで実行されているサービスへのアクセスを制限するために使用できます。

iproute2を用いたVRFの利用¶

iproute2はv4.7からvrfキーワードをサポートしています。後方互換性のため、このセクションでは適切な場所でvrfキーワードを使用したコマンドと古い形式のコマンドの両方をリストしています。

  1. VRFを作成する

    VRFデバイスをインスタンス化し、テーブルに関連付けるには:

    $ ip link add dev NAME type vrf table ID

    v4.8からはカーネルがl3mdev FIBルールをサポートしており、1つのルールですべてのVRFをカバーできます。l3mdevルールは最初のデバイス作成時にIPv4およびIPv6で作成されます。

  2. VRFの一覧表示

    作成されたVRFの一覧を表示するには:

    $ ip [-d] link show type vrf
  NOTE: The -d option is needed to show the table id

    vrf table 1 addrgenmode eui64

  3. ネットワークインターフェースをVRFに割り当てる

    ネットワークインターフェースは、netdeviceをVRFデバイスにslave化することでVRFに割り当てられます:

    $ ip link set dev NAME master NAME

    slave化により、接続済みおよびローカルルートは自動的にVRFデバイスに関連付けられたテーブルに移動します。

    例:

    $ ip link set dev eth0 master mgmt

    VRFのテストルート検索は以下のようになります:

    $ ip [-6] route get vrf NAME ADDRESS

  9. ネットワークインターフェースをVRFから削除する

    ネットワークインターフェースは、VRFデバイスとのslave化を解除することでVRFから削除されます:

    $ ip link set dev NAME nomaster

    接続済みルートはデフォルトテーブルに戻され、ローカルエントリはローカルテーブルに移動します。

    例:

    $ ip link set dev eth0 nomaster

この例で使用したコマンド:

cat >> /etc/iproute2/rt_tables.d/vrf.conf <<EOF
1  mgmt
10 red
66 blue
81 green
EOF

function vrf_create
{
    VRF=$1
    TBID=$2

    # create VRF device
    ip link add ${VRF} type vrf table ${TBID}

    if [ "${VRF}" != "mgmt" ]; then
        ip route add table ${TBID} unreachable default metric 4278198272
    fi
    ip link set dev ${VRF} up
}

vrf_create mgmt 1
ip link set dev eth0 master mgmt

vrf_create red 10
ip link set dev eth1 master red
ip link set dev eth2 master red
ip link set dev eth5 master red

vrf_create blue 66
ip link set dev eth3 master blue

vrf_create green 81
ip link set dev eth4 master green

MSG_ZEROCOPY¶

はじめに¶

MSG_ZEROCOPYフラグは、ソケット送信呼び出しにおけるコピー回避を有効にします。この機能は現在、TCPとUDPソケットで実装されています。

機会と注意点¶

ユーザープロセスとカーネル間で大容量のバッファをコピーする作業はコストが高くなります。Linuxは、コピーを避けるためのさまざまなインターフェースをサポートしています。たとえば、sendpageやspliceなどです。MSG_ZEROCYPYフラグは、一般的なソケット送信呼び出しにもこのコピー回避メカニズムを拡張します。

コピー回避は無料のランチではありません。実装では、ページピンニングにより、1バイトごとのコピーコストをページアカウントと完了通知のオーバーヘッドに置き換えています。その結果、MSG_ZEROCOPYは一般的に10KB程度以上の書き込みで効果を発揮します。

ページピンニングはシステムコールのセマンティクスにも影響を与えます。プロセスとネットワークスタックがバッファを一時的に共有します。コピーとは異なり、システムコールの戻り値後、プロセスが即座にバッファを上書きすることはできません。これは進行中のデータを変更する可能性があるためです。カーネルの整合性は影響を受けませんが、バグのあるプログラムは自身のデータストリームを破損させる可能性があります。

カーネルはデータを変更できるようになったことを通知します。既存のアプリケーションをMSG_ZEROCOPYに変換するのは、単にフラグを渡すだけでは常に簡単ではありません。

インターフェース¶

MSG_ZEROCOPYフラグを渡すことは、コピー回避を有効にする最も明白なステップですが、唯一のステップではありません。

ソケットの設定¶

アプリケーションがsendシステムコールに未定義のフラグを渡した場合、カーネルはデフォルトでは無視します。これにより、誤ってこのフラグを渡している既存のプロセスがコピー回避モードを有効にするのを防ぐため、プロセスはまずソケットオプションを設定して意図を示す必要があります。

if (setsockopt(fd, SOL_SOCKET, SO_ZEROCOPY, &one, sizeof(one)))
        error(1, errno, "setsockopt zerocopy");

送信¶

send（またはsendto、sendmsg、sendmmsg）自体への変更は簡単です。新しいフラグを渡すだけです。

ret = send(fd, buf, sizeof(buf), MSG_ZEROCOPY);

ゼロコピー失敗は、errno ENOBUFSとともに-1を返します。これは、ソケットオプションが設定されていない、ソケットがoptmem制限を超えた、またはユーザーがロックされたページのulimitを超過した場合に発生します。

コピー回避とコピーの混在¶

多くのワークロードでは、大容量と小容量のバッファが混在しています。コピー回避は小パケットではコピーするよりもコストが高いため、この機能はフラグとして実装されています。フラグを含む呼び出しと含まない呼び出しを混在させても安全です。

通知¶

カーネルは、以前に渡されたバッファを再利用できる状態になったときにプロセスに通知する必要があります。この通知は、送信タイムスタンプインターフェースと同様に、ソケットのエラーキューに完了通知をキューイングします。

通知自体は単純なスカラー値です。各ソケットは内部で無符号の32ビットカウンタを保持しています。MSG_ZEROCOPYで成功した送信呼び出しはこのカウンタをインクリメントします。失敗時や長さゼロで呼び出された場合はカウンタはインクリメントされません。カウンタはバイト数ではなく、システムコールの呼び出し回数をカウントします。UINT_MAX回の呼び出しでカウンタはリセットされます。

通知の受信¶

以下のスニペットはAPIの例です。最も簡単なケースでは、各送信システムコールの後にエラーキューに対するpollとrecvmsgが続きます。

エラーキューからの読み取りは常に非ブロッキング操作です。poll呼び出しはエラーが発生しているのを待つためのものです。この呼び出しが出力フラグにPOLLERRを設定します。このフラグはeventsフィールドに設定する必要はありません。エラーは常に通知されます。

pfd.fd = fd;
pfd.events = 0;
if (poll(&pfd, 1, -1) != 1 || pfd.revents & POLLERR == 0)
        error(1, errno, "poll");

ret = recvmsg(fd, &msg, MSG_ERRQUEUE);
if (ret == -1)
        error(1, errno, "recvmsg");

read_notification(msg);

この例はデモンストレーション用です。実際には通知を待つことなく、数回の送信呼び出しごとにブロッキングせずに読み取る方が効率的です。

通知はソケット上の他の操作と順不同で処理できます。エラーがキューイングされているソケットは通常、エラーが読まれるまで他の操作をブロックします。しかしゼロコピー通知はゼロエラーコードを持つため、送信および受信呼び出しをブロックしません。

通知のバッチ処理¶

recvmmsg呼び出しを使用することで、複数の未処理パケットを一度に読み取れます。これは多くの場合必要ありません。各メッセージでカーネルが返すのは単一の値ではなく、範囲です。エラーキューで受信待ちの通知が連続している場合、カーネルはそれらを統合して1つの範囲として扱います。

新しい通知がキューイングされる際、キュー末尾の通知の範囲を新しい値が拡張するかを確認します。そうであれば、新しい通知パケットをドロップし、代わりに未処理通知の上界値を増加させます。

順序通りにデータを確認するプロトコル（例：TCP）では、各通知を前の通知に統合できるため、常に1つ以上の通知が未処理になることはありません。

順序付き配信は一般的なケースですが、保証されていません。再送信やソケットの終了により、通知が順不同で到達することがあります。

通知のパース¶

以下のスニペットは制御メッセージをどのようにパースするかを示しています：前のスニペットのread_notification()呼び出し。通知は標準的なエラーフォーマット、sock_extended_errでエンコードされています。

コントロールデータ内のレベルおよびタイプフィールドはプロトコルファミリースペシックであり、IP_RECVERRまたはIPV6_RECVERRです。

エラーの出所は新しいタイプのSO_EE_ORIGIN_ZEROCOPYです。以前に説明したように、ee_errnoはゼロであり、ソケット上のブロッキングな読み書きシステムコールを回避します。

32ビットの通知範囲は[ee_info, ee_data]としてエンコードされます。この範囲は包含的です。構造体の他のフィールドは未定義とみなされ、以下で説明するee_codeを除きます。

struct sock_extended_err *serr;
struct cmsghdr *cm;

cm = CMSG_FIRSTHDR(msg);
if (cm->cmsg_level != SOL_IP &&
    cm->cmsg_type != IP_RECVERR)
        error(1, 0, "cmsg");

serr = (void *) CMSG_DATA(cm);
if (serr->ee_errno != 0 ||
    serr->ee_origin != SO_EE_ORIGIN_ZEROCOPY)
        error(1, 0, "serr");

printf("completed: %u..%u\n", serr->ee_info, serr->ee_data);

遅延コピー¶

フラグMSG_ZEROCOPYを渡すことは、カーネルにコピー回避を適用するヒントであり、カーネルが完了通知をキューイングする契約です。これはコピーが省略される保証ではありません。

コピー回避は常に可能ではありません。スキャッターガather I/Oをサポートしないデバイスは、カーネル生成のプロトコルヘッダとゼロコピーユーザーデータで構成されたパケットを送信できません。パケットはスタックの奥深い場所でデータのプライベートなコピーに変換される場合があります（例：チェックサムの計算）。

このようなすべてのケースでは、カーネルは共有ページの占有を解放するときに完了通知を返します。この通知は（コピーされた）データが完全に送信される前に到達する可能性があります。ゼロコピーの完了通知は送信完了通知ではありません。

データがキャッシュで温まっていない場合、遅延コピーはシステムコール内で即時コピーするよりもコストが高くなることがあります。プロセスは通知処理コストを無駄にします。そのため、カーネルはee_codeフィールドのSO_EE_CODE_ZEROCOPY_COPIEDフラグを設定して、コピーで完了したデータを信号として通知します。プロセスはこの信号を使用して、同じソケットでの次のリクエストでMSG_ZEROCOPYフラグを渡さないようにできます。

ハードロックアップ検出器は、定期的に実行されるhrtimerによって生成される割込みでウォッチドッグタスクを起動します。ハードロックアップの検出には、「watchdog_thresh」（コンパイル時に初期化され、sysctlの同じ名前で設定可能）秒ごとにNMI perfイベントが生成されます。システム内のどのCPUもその間hrtimer割込みを受けていない場合、ハードロックアップ検出器（NMI perfイベントのハンドラ）がカーネル警告を生成するか、設定に応じてパニックを呼び出します。¶

ループバック¶

ローカルソケットに送信されたデータは、受信プロセスがソケットを読み取らない場合、無限にキューイングされる可能性があります。無制限の通知遅延は受け入れられません。そのため、MSG_ZEROCOPYで生成されたすべてのループバックパケットは遅延コピーを伴います。これはパケットソケット（例：tcpdump）やtunデバイスへのループバックにも含まれます。

テスト¶

より現実的な例コードは、カーネルソースのtools/testing/selftests/net/msg_zerocopy.cにあります。

ループバック制約を意識してください。テストはホストペア間で実行できますが、ローカルプロセスペア間（例：msg_zerocopy.shでネームスペース横断のvethペアで実行）で実行すると改善効果がありません。テストのためには、skb_orphan_frags_rxをskb_orphan_fragsと同等にすることでループバック制約を一時的に緩和できます。

イーサネットスイッチデバイスドライバモデル (switchdev)¶

著作権 © 2014 Jiri Pirko <jiri@resnulli.us>

著作権 © 2014-2015 Scott Feldman <sfeldma@gmail.com>

イーサネットスイッチデバイスドライバモデル（switchdev）は、カーネル内に実装されたスイッチデバイス用のドライバモデルであり、転送（データ）平面をカーネルからオフロードするものです。

インクルードファイル¶

#include <linux/netdevice.h>
#include <net/switchdev.h>

設定¶

ドライバのKconfigに「depends NET_SWITCHDEV」を指定することで、switchdevモデルのサポートがドライバに組み込まれることを確保してください。

スイッチポート¶

switchdevドライバの初期化時に、ドライバは各列挙された物理スイッチポートに対して struct net_device (using register_netdev())を割り当てて登録します。ポートnetdevは物理ポートのソフトウェア表現であり、コントローラー（カーネル）とネットワーク間の制御トラフィックの経路を提供し、ブリッジ、ボンド、VLAN、トンネル、L3ルーターなどの上位構造のアンカーとなるポイントです。標準のnetdevツール（iproute2、ethtoolなど）を使用すると、ポートnetdevはユーザーにスイッチポートの物理的な特性（PHYリンク状態やI/O統計など）へのアクセスを提供します。

（現在は）スイッチに対してはポートnetdevを超えるより上位のカーネルオブジェクトはありません。すべてのswitchdevドライバ操作はnetdev操作またはswitchdev操作です。

スイッチ管理ポートはswitchdevドライバモデルの範囲外です。通常、管理ポートはオフロードされたデータ平面に参加せず、管理ポートデバイス上で異なるドライバ（例: NICドライバ）がロードされます。

スイッチID¶

switchdevドライバは、各ポートnetdevに対してnet_device操作ndo_get_port_parent_idを実装しなければなりません。これにより、スイッチの各ポートに対して同じ物理IDが返されます。IDは同じシステム内のスイッチ間で一意でなければなりませんが、異なるシステムのスイッチ間では一意である必要はありません。

スイッチIDは、スイッチ上のポートを特定するためのものであり、集約されたポートが同じスイッチに属するかどうかを判断するために使用されます。

ポートnetdevの命名¶

ポートnetdevの命名にはudevルールを使用し、ポートの一部のユニークな属性（例: ポートMACアドレスやポートPHYS名）をキーとして使用してください。ドライバ内でカーネルnetdev名をハードコードするのは推奨されません。カーネルがデフォルトのnetdev名を選択し、udevがポート属性に基づいて最終的な名前を設定するようにしてください。

ポートの物理名（ndo_get_phys_port_name）を使用する方法は、外部設定に基づいてデバイスがポートを名前付ける動的ポートにおいて特に有用です。たとえば、物理的な40Gポートが論理的に4つの10Gポートに分割され、4つのポートnetdevが生成される場合、デバイスはポート PHYS 名を使用して各ポートに一意の名前を付けることができます。udev ルールは以下のようになります：

SUBSYSTEM=="net", ACTION=="add", ATTR{phys_switch_id}=="<phys_switch_id>", \
        ATTR{phys_port_name}!="", NAME="swX$attr{phys_port_name}"

推奨される命名規則は「swXpYsZ」です。ここで、Xはスイッチ名またはID、Yはポート名またはID、Zはサブポート名またはIDを表します。たとえば、sw1p1s0はスイッチ1のポート1のサブポート0を表します。

ポート機能¶

NETIF_F_NETNS_LOCAL

スイッチdevドライバー（およびデバイス）がデフォルトのネットワークネームスペース（netns）のみをオフロードサポートする場合、ドライバーはこの機能フラグを設定して、ポートnetdevがデフォルトnetnsから外れることを防ぐ必要があります。ネットネームスペースを意識したドライバー／デバイスはこのフラグを設定せず、ハードウェアをパーティション化してnetnsの包含性を維持する責任があります。これは、ハードウェアが1つのnetns内のポートから別のnetns内のポートへのトラフィックの転送を実行できないことを意味します。

ポートのトポロジー¶

物理スイッチポートを表すポートnetdevは、より高レベルのスイッチング構造に整理できます。デフォルトでは、L3フォワーディングをオフロードするためのスタンドアロンのルーターポートが使用されます。2つ以上のポートをバウンドしてLAGを形成することも、2つ以上のポート（またはLAG）をブリッジしてL2ネットワークをブリッジすることもできます。VLANはL2ネットワークをサブディビジョンできます。L2オーバーL3トンネルはポート上に構築できます。これらの構造は、ブリッジドライバー、バウンド／チームドライバー、netlinkベースのツール（例：iproute2）などの標準的なLinuxツールを使用して構築されます。

スイッチdevドライバーは、NETDEV_CHANGEUPPER通知を監視することで、特定のポートのトポロジーアクセス位置を把握できます。たとえば、ポートがバウンドに移動すると、その上位マスターが変更されます。そのバウンドがブリッジに移動すると、バウンドの上位マスターが変更されます。このような移動をドライバーが追跡することで、ネットデバイスイベントを登録し、NETDEV_CHANGEUPPERに応じて、全体のトポロジーでのポートの位置を把握できます。

L2フォワーディングオフロード¶

L2データフォワーディング（スイッチング）パスをカーネルからスイッチdevデバイスにオフロードするためのアイデアは、ブリッジFDBエントリをデバイスにミラーリングすることです。FDBエントリは、{ポート、MAC、VLAN}の組み合わせでフォワーディング先を示します。

L2ブリッジングのオフロードには、switchdevドライバー／デバイスが次の機能をサポートする必要があります：

  • ブリッジポートにインストールされた静的FDBエントリ

  • デバイスから学習／忘れられた送信元MAC／VLANの通知

  • ポートのSTP状態の変化

  • マルチキャスト/ブロードキャストおよび未登録のユニキャストパケットのVLANフロッディング

静的FDBエントリ¶

switchdevドライバは、静的FDBエントリをデバイスにインストールするため、ndo_fdb_add、ndo_fdb_delおよびndo_fdb_dumpを実装する必要があります。静的ブリッジFDBエントリは、iproute2のブリッジコマンドを使用してインストールされます:

bridge fdb add ADDR dev DEV [vlan VID] [self]

ドライバはswitchdev_port_fdb_xxx opsを使用してndo_fdb_xxx opsを処理し、SWITCHDEV_OBJ_ID_PORT_FDBオブジェクトの追加/削除/ダンプをswitchdev_port_obj_xxx opsを使用して処理する必要があります。

echo 1 >/sys/class/net/<bridge>/bridge/vlan_filtering

学習/忘れられたソースMAC/VLANの通知¶

スイッチデバイスはイングレスパケットでソースMACアドレス/VLANを学習/忘れ、mac/vlan/portの組み合わせをスイッチドライバに通知します。スイッチドライバは、switchdevノティファイコールを使用してブリッジドライバに通知します:

err = call_switchdev_notifiers(val, dev, info, extack);

valは学習時にSWITCHDEV_FDB_ADD、忘れ時にSWITCHDEV_FDB_DELになります。infoはstruct switchdev_notifier_fdb_infoを指します。SWITCHDEV_FDB_ADDの場合、ブリッジドライバはFDBエントリをブリッジのFDBにインストールし、エントリをNTF_EXT_LEARNEDとしてマークします。iproute2のブリッジコマンドはこれらのエントリを「オフロード」とラベル付けします:

$ bridge fdb

00:02:00:00:02:00 dev sw1p1 master br0 offload
00:02:00:00:02:00 dev sw1p1 self
52:54:00:12:35:02 dev sw1p2 master br0 permanent
00:02:00:00:03:00 dev sw1p2 master br0 offload
00:02:00:00:03:00 dev sw1p2 self
33:33:00:00:00:01 dev eth0 self permanent
01:00:5e:00:00:01 dev eth0 self permanent
33:33:ff:00:00:00 dev eth0 self permanent
01:80:c2:00:00:0e dev eth0 self permanent
33:33:00:00:00:01 dev br0 self permanent
01:00:5e:00:00:01 dev br0 self permanent
33:33:ff:12:35:01 dev br0 self permanent

ブリッジコマンドを使用してポートの学習を無効化する必要があります:

bridge link set dev DEV learning off

デバイスポートの学習および学習同期を有効にする必要があります。

bridge link set dev DEV learning on self
bridge link set dev DEV learning_sync on self

学習同期属性は、学習/忘れられたFDBエントリをブリッジのFDBに同期します。デバイスポートとブリッジポートの学習を有効にし、学習同期を無効にするのは可能ですが、最適ではありません。

学習をサポートするため、ドライバはSWITCHDEV_ATTR_PORT_ID_{PRE}_BRIDGE_FLAGSを処理するswitchdev_port_attr_setを実装します。

FDBエイジング¶

ブリッジはNTF_EXT_LEARNEDでマークされたFDBエントリのエイジングをスキップします。これらのエントリのエイジングはポートドライバ/デバイスの責任です。デバイスがエイジングをサポートする場合、FDBエントリが期限切れになると、ドライバが通知し、ブリッジにSWITCHDEV_FDB_DELを通知します。デバイスがエイジングをサポートしない場合、ドライバはガベージコレクションタイマーやFDBエントリを監視するタイマーモードでエイジングをシミュレートできます。期限切れのエントリはSWITCHDEV_FDB_DELでブリッジに通知されます。rockerドライバはエイジングタイマーモードを実行するドライバの例です。

NTF_EXT_LEARNEDエントリを「有効」に保つには、ドライバーがcall_switchdev_notifiers(SWITCHDEV_FDB_ADD, …)を呼び出してFDBエントリを更新する必要があります。この通知により、FDBエントリの最後に使用された時間は現在にリセットされます。ドライバーは、リフレッシュ通知を制限する必要があります（例：1秒に1回まで）。(最後に使用された時間はbridge -s fdbオプションを使用して確認できます）。

ポートにおけるSTPの状態変化¶

内部的にもしくは第三者のSTPプロトコル実装（例：mstpd）を使用して、ブリッジドライバーがポートのSTP状態を管理し、switchdev_op switchdev_attr_port_setを使用してSWITCHDEV_ATTR_PORT_ID_STP_UPDATEを介してSTP状態変化をスイッチドライバーに通知します。

状態はBR_STATE_*のいずれかです。スイッチドライバーはSTP状態の更新を用いて、ポートのイングレスパケットフィルタリストを更新できます。例えば、ポートがDISABLEDの場合、パケットは通過すべきではありませんが、ポートがBLOCKEDに移行した場合、STP BPDUsやIEEE 01:80:c2:xx:xx:xxのリンクローカルマルチキャストパケットが通過できます。

STP BPDUsはラベルなしで送信され、STP状態はポート上のすべてのVLANに適用されるため、ラベルなしとラベルありのVLANでパケットフィルタを一貫して適用する必要があります。

L2ドメインにおけるフロッディング¶

特定のL2 VLANドメインにおいて、ポートの現在のSTP状態が許可する限り、スイッチデバイスはそのドメイン内のすべてのポートにマルチキャスト/ブロードキャストおよび未知のユニキャストパケットをフロッディングする必要があります。スイッチドライバーは、どのポートがどのVLAN L2ドメインに属するかを把握しており、スイッチデバイスにフロッディングを設定できます。パケットはブリッジドライバーによって処理されるポートnetdevに送信される可能性があります。ブリッジは、デバイスがフロッディングしたポートに再フロッディングしないようにする必要があります。そうしないと、ワイヤー上に重複パケットが発生します。

重複パケットを避けるため、スイッチドライバーはskb->offload_fwd_markビットを設定してパケットをすでに転送済みとマークする必要があります。ブリッジドライバーはイングレスブリッジポートのマークを使用してskbをマークし、同じマークを持つすべてのブリッジポートを介して転送を防ぎます。

スイッチデバイスがフロッディングを処理せず、ブリッジドライバーにパケットを上位に押し上げてフロッディングする可能性があります。これはL2ドメインのポート数が増えるにつれてソフトウェアよりもデバイスが効率的にパケットをフロッディングできるため、理想的ではありません。

デバイスがサポートする場合、フロッディング制御をオフロードして、特定のnetdevがFDBエントリがない場合のユニキャストトラフィックをフロッディングしないようにできます。

IGMPスヌープ¶

IGMP snoopingをサポートするため、ポートnetdevはすべてのIGMP joinおよびleaveメッセージをブリッジドライバーにトラップする必要があります。ブリッジマルチキャストモジュールは、マルチキャストグループが変更されたときに、そのグループが静的設定か動的に参加/離脱かを含めてポートnetdevに通知します。ハードウェア実装では、登録されたマルチキャストトラフィックグループをのみ、設定されたポートに転送する必要があります。

L3ルーティングオフロード¶

L3ルーティングのオフロードには、デバイスにカーネルからのFIBエントリをプログラミングし、デバイスがFIB検索と転送を行う必要があります。デバイスはFIBエントリのルートプレフィックスと一致する最も長いプレフィックス一致（LPM）を行い、パケットを一致したFIBエントリのnexthop（出力ポート）に転送します。

デバイスをプログラミングするには、ドライバーはregister_fib_notifierを使用してFIB notifierハンドラを登録する必要があります。以下のイベントが利用可能です：

FIB_EVENT_ENTRY_ADD

新しいFIBエントリをデバイスに追加するか、既存のエントリを変更する場合に使用されます。

FIB_EVENT_ENTRY_DEL

FIBエントリを削除する場合に使用されます。

FIB_EVENT_RULE_ADD,

FIB_EVENT_RULE_DEL

FIBルールの変更を伝播する場合に使用されます。

FIB_EVENT_ENTRY_ADDおよびFIB_EVENT_ENTRY_DELイベントは以下の情報を渡します：

struct fib_entry_notifier_info {
        struct fib_notifier_info info; /* must be first */
        u32 dst;
        int dst_len;
        struct fib_info *fi;
        u8 tos;
        u8 type;
        u32 tb_id;
        u32 nlflags;
};

table tb_idにIPv4 dst/dest_lenプレフィックスを追加/変更/削除する場合。The *fi 構造体はルートとそのルートのnexthopsの詳細を保持しています。 *dev ルートのnexthopリストに記載されているポートnetdevの一つです。

デバイスにオフロードされたルートは、ip routeリストで「offload」とラベル付けされます：

$ ip route show
default via 192.168.0.2 dev eth0
11.0.0.0/30 dev sw1p1  proto kernel  scope link  src 11.0.0.2 offload
11.0.0.4/30 via 11.0.0.1 dev sw1p1  proto zebra  metric 20 offload
11.0.0.8/30 dev sw1p2  proto kernel  scope link  src 11.0.0.10 offload
11.0.0.12/30 via 11.0.0.9 dev sw1p2  proto zebra  metric 20 offload
12.0.0.2  proto zebra  metric 30 offload
        nexthop via 11.0.0.1  dev sw1p1 weight 1
        nexthop via 11.0.0.9  dev sw1p2 weight 1
12.0.0.3 via 11.0.0.1 dev sw1p1  proto zebra  metric 20 offload
12.0.0.4 via 11.0.0.9 dev sw1p2  proto zebra  metric 20 offload
192.168.0.0/24 dev eth0  proto kernel  scope link  src 192.168.0.15

少なくとも一つのデバイスがFIBエントリをオフロードしている場合、「offload」フラグが設定されます。

nexthopの解決¶

FIBエントリのnexthopリストには（ゲートウェイ、dev）のタプルが含まれていますが、スイッチデバイスが正しいdst macアドレスでパケットを転送するには、nexthopゲートウェイを隣接ノードのmacアドレスに解決する必要があります。隣接macアドレスの発見はARP（またはND）プロセスを通じて行われ、arp_tbl隣接テーブルで利用可能です。ルートのnexthopゲートウェイを解決するには、ドライバーはカーネルの隣接解決プロセスをトリガーする必要があります。rockerドライバーのrocker_port_ipv4_resolve関数を参照してください。

ドライバーはnetevent notifier NETEVENT_NEIGH_UPDATEを使用してarp_tblの更新を監視できます。arp_tblの更新に応じて、デバイスにルートの解決済みnexthopをプログラミングできます。ドライバーはndo_neigh_destroyを実装して、ポートからarp_tbl隣接エントリが削除されたときに通知を受けます。

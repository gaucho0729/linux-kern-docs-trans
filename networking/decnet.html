2. カーネルの設定¶

以下のオプションを有効にする必要があります:

  • CONFIG_DECNET (明らかに)

  • CONFIG_PROC_FS (現在の状況を確認するため)

  • CONFIG_SYSCTL (簡単な設定のために)

ルーターのサポートを試してみたい場合は（まだ十分にデバッグされていません）、以下のオプションも必要です…

  • CONFIG_DECNET_ROUTER (ルートを追加/削除できるようにするため)

  • CONFIG_NETFILTER (DECnet ルーティングデーモンに必要)

DECnet 用の SIOCGIFCONF サポートを有効にしないでください。本当に必要であることを確認した場合を除き、通常は必要ありません。これにより ifconfig が異常動作する可能性があります。

実行時の設定は 2.4 システムと若干異なります。エンドノードを設定したい場合は、以下の簡略手順を行います:

  • ネットワークプロトコルを開始する前に、イーサネットカードの MAC アドレスを設定してください。

ネットワークカードが UP 状態になった直ちに DECnet は動作を開始します。より複雑な設定が必要な場合や、MAC アドレスの設定方法が分からない場合は、次のセクションを参照してください。また、2.4 で動作したすべての設定は 2.5 でも変更することなく動作します。

3. コマンドラインオプション¶

2.4 の設定手順との互換性のために、カーネルのコマンドラインで DECnet アドレスを設定できますが、通常は必要ありません。コマンドラインで DECnet アドレスを設定した場合、その目的はループバックデバイスのアドレスに追加することです。

2.4 カーネルでは、ループバックデバイスに追加されたアドレスのみがローカルと認識されました。2.5 では、ローカルインターフェースのアドレスを用いてローカルマシンにループバックできます。もちろん、追加のアドレスをループバックデバイスに追加することを望む場合は、妨げはつきません。

N.B. インターフェースのアドレスリストは、「hello」メッセージが送信されるアドレスを決定するため、ループバックインターフェースにアドレスを設定しない場合、接続を開始するまで /proc/net/neigh にローカルホストに関するエントリが表示されません。ただし、ローカル通信の他の動作には影響しません。

カーネルのコマンドラインは以下のようないくつかのオプションを受け付けます:

decnet.addr=1,2

2つの数字はノードアドレスで、1,2 = 1.2 です。2.2.xx カーネルおよび早期の 2.3.xx カーネルでは、DECnet アドレスを指定する際にはコンマを使用する必要があります。より新しい 2.3.xx カーネルでは、スペース以外のほぼすべての文字を使用できますが、 . 最も明白な選択肢でしょう :-)

以前はノードタイプを指定するための3番目の数字がありました。このオプションは、インターフェースごとのノードタイプに置き換えられました。現在は/proc/sys/net/decnet/conf/<dev>/forwardingで設定されます。このファイルは1桁の数字で設定でき、0=エンドノード、1=L1ルーター、2=L2ルーターです。

モジュールにも同等のオプションがあります。ノードアドレスは/proc/sys/net/decnet/ファイルを通じて設定でき、他のシステムパラメータも同様です。

現在サポートされているデバイスはイーサネットとip_greのみです。イーサネットカードのイーサネットアドレスは、ノードのDECnetアドレスに合わせて設定する必要があります（自動設定され、/proc/net/decnet_devに表示されます）。上記のFTPサイトで利用できるdn2ethaddrというユーティリティで正しいイーサネットアドレスを計算できます。ifconfigで設定する際は、デバイスが起動される前でも起動時でも可能です。RedHatを使用している場合は、/etc/sysconfig/network-scripts/ifcfg-eth0やネットワークカードの設定ファイルに以下の行を追加できます：

MACADDR=AA:00:04:00:03:04

or something similar, to /etc/sysconfig/network-scripts/ifcfg-eth0 or wherever your network card’s configuration lives. Setting the MAC address of your ethernet card to an address starting with “hi-ord” will cause a DECnet address which matches to be added to the interface (which you can verify with iproute2).

ルーティング用のデフォルトデバイスは/procファイルシステムを通じて/proc/sys/net/decnet/default_deviceに設定できます。DECnetが特定のルートが存在しない場合にパケットをルーティングするデバイスを指定します。通常はeth0です（例：

echo -n "eth0" >/proc/sys/net/decnet/default_device

デフォルトデバイスを設定しない場合、上記の自動設定で最初に設定されたイーサネットカードがデフォルトになります。default_deviceファイルを確認することで確認できます。

kernel patch web site（上記に示されている）で/proc/sys/net/decnet/配下の他のファイルの機能について確認できます。

4. ランタイムカーネル設定¶

これはsysctl/procインターフェースを通じて（カーネルウェブページで各オプションの詳細を確認できます）またはiproute2パッケージを通じてIPv4/6の設定と同様に行えます。

iproute2のドキュメンテーションはパッケージに含まれていますが、DECnetに関する特定のセクションはまだありません。ほとんどの機能はIPとDECnetの両方に適用可能ですが、IPアドレスの代わりにDECnetアドレスを使用し、機能は一部簡略化されています。

DECnetルーターを構成する場合は、iproute2パッケージが必要です。現在、ルートの追加および削除を行う唯一の方法です。最終的には、インターフェースごとにルーティングメッセージを送受信し、カーネルのルーティングテーブルを更新するルーティングデーモンが導入される予定です。このルーティングデーモンはnetfilterを使用してルーティングパケットを監視し、rtnetlinkを使用してカーネルのルーティングテーブルを更新します。

DECnetのrawソケットレイヤーは、ルーティングデーモンの使用にのみ存在していたため、現在はnetfilterを使用する（より清潔で一般的な解決策）に置き換えられました。

5. 動作しているか確認する方法はありますか？¶

DECnetカーネルサブシステムが正常に動作しているか確認するための簡単なガイドです。

  • ノードアドレスが設定されているか確認してください（/proc/sys/net/decnet/node_address を参照）

  • ノードのタイプが正しいか確認してください（/proc/sys/net/decnet/conf/<dev>/forwarding を参照）

  • 各イーサネットカードのイーサネットMACアドレスがDECnetアドレスと一致しているか確認してください。疑問がある場合は、ftpアーカイブで入手可能なdn2ethaddrユーティリティを使用してください。

  • 前の2つのステップが満たされ、イーサネットカードが起動している場合、/proc/net/decnet_dev にリストアップされており、/proc/sys/net/decnet/conf/ にディレクトリとして表示されるはずです。ループバックデバイス（lo）も表示され、ノード内での通信には必要です。

  • ネットワーク上にDECnetルーターがある場合、/proc/net/decnet_neigh に表示されます。そうでない場合は、このファイルにはノード自身のエントリ（loが起動しているか確認していない場合）のみ含まれます。

  • /proc/net/decnet_neigh ファイルにリストされていないノードに送信する場合、デフォルトデバイスをイーサネットカード（ルーターに接続）に設定する必要があります。これは再び /proc/sys/net/decnet/default_device ファイルで行います。

  • ループバックインターフェースでdnping/dnmirrorなどのシンプルなサーバーとクライアントを起動してみてください。幸運にも通信が成功するはずです。このステップと後のステップには、DECnetライブラリが必要です。これは上記のftpサイトから取得可能であり、実際のユーティリティも同様です。

  • これで動作するようであれば、ローカルネットワーク上のノードと通信して、同じ結果が得られるか確認してください。

  • この時点で自分自身で解決してください… :-)

6. バグレポートの送信方法¶

バグを見つけた場合、それを報告する際には、私が正確に問題の所在を特定するのを助けるためにいくつかの情報を提供することが役立ちます。有用な情報（ほとんどが必須です）には以下が含まれます：

  • 現在使用しているカーネルのバージョンは？

  • 現在使用しているパッチのバージョンはどれですか？

  • 上記のテストセットをどれだけ進めることが可能ですか？

  • proc/decnet* ファイルおよび proc/sys/net/decnet/* ファイルには何が含まれていますか？

  • 現在実行中のサービスはどれですか？

  • 問題を引き起こしたクライアントはどれですか？

  • 転送されていたデータ量はどれくらいですか？

  • ネットワークが混雑していましたか？

  • 問題を再現するにはどうすればよいですか？

  • tcpdump を使ってトレースを取得できますか？（注：ほとんどの（すべての？）tcpdump のバージョンは DECnet のダンプ方法を理解していないため、パケット内容の 16進数のリストを _必須_ として含める必要があります。通常は -x フラグを使用します。また、-s フラグで取得する長さを増やす必要がある場合があります。-e フラグもエーテルネット MAC アドレスなどの非常に有用な情報を提供します）

7. MAC FAQ¶

Ethernet カードの MAC アドレスに関する簡単な FAQ で、Linux と DECnet の相互作用方法や、ハードウェアから最高のパフォーマンスを得る方法を説明しています。

Ethernet カードは通常、受信したネットワークフレームをホストコンピュータに転送する際、そのフレームが自分宛てか、ブロードキャストアドレス宛ての場合にのみ動作します。

Linux には、Ethernet カードに追加のアドレスを設定するインターフェースがあります。Ethernet カードがこれをサポートする場合、フィルタリングはハードウェアで行われ、サポートしない場合はホストコンピュータが不要なパケットを棄却します。後者の場合、忙しいネットワークではプロセッサ時間とバス帯域幅が大幅に使用されます（NAPI ドキュメンテーションでこれらの効果についての詳細説明があります）。

DECnet はこのインターフェースを使用して、TCP/IP で設定済みの Ethernet カード（通常の MAC アドレスを使用）に DECnet を実行するか、各物理インターフェースに複数の DECnet アドレスを設定するための機能を提供します。この場合、Ethernet カードが MAC アドレスフィルタで完全ハッシュをサポートしない場合、コンピュータが過剰な作業を行う可能性があります。一部のカードは、DECnet 指定のアドレスからのパケットを受信するためにプロミスカuous モードに設定されます。このようなカードを使用している場合、上記の方法で MAC アドレスを設定することで最適な効率を得られます。さらに良いのは、NAPI をサポートするカードを使用することです。

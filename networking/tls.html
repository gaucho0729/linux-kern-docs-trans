カーネルTLS¶

概要¶

トランスポートレイヤーセキュリティ（TLS）は、TCPを介して動作する上位レイヤープロトコル（ULP）であり、データの整合性と機密性を提供します。

ユーザーインターフェース¶

TLS接続の作成¶

まず、新しいTCPソケットを作成し、TLS ULPを設定します。

sock = socket(AF_INET, SOCK_STREAM, 0);
setsockopt(sock, SOL_TCP, TCP_ULP, "tls", sizeof("tls"));

TLS ULPを設定することで、TLSソケットオプションの設定/取得が可能になります。現在はカーネルで対称暗号処理のみが行われています。TLSハンドシェイクが完了後、データパスをカーネルに移行するために必要なすべてのパラメータを取得できます。送信と受信の処理をカーネルに移行するためには、それぞれの送信/受信に向けた別個のソケットオプションがあります。

/* From linux/tls.h */
struct tls_crypto_info {
        unsigned short version;
        unsigned short cipher_type;
};

struct tls12_crypto_info_aes_gcm_128 {
        struct tls_crypto_info info;
        unsigned char iv[TLS_CIPHER_AES_GCM_128_IV_SIZE];
        unsigned char key[TLS_CIPHER_AES_GCM_128_KEY_SIZE];
        unsigned char salt[TLS_CIPHER_AES_GCM_128_SALT_SIZE];
        unsigned char rec_seq[TLS_CIPHER_AES_GCM_128_REC_SEQ_SIZE];
};


struct tls12_crypto_info_aes_gcm_128 crypto_info;

crypto_info.info.version = TLS_1_2_VERSION;
crypto_info.info.cipher_type = TLS_CIPHER_AES_GCM_128;
memcpy(crypto_info.iv, iv_write, TLS_CIPHER_AES_GCM_128_IV_SIZE);
memcpy(crypto_info.rec_seq, seq_number_write,
                                      TLS_CIPHER_AES_GCM_128_REC_SEQ_SIZE);
memcpy(crypto_info.key, cipher_key_write, TLS_CIPHER_AES_GCM_128_KEY_SIZE);
memcpy(crypto_info.salt, implicit_iv_write, TLS_CIPHER_AES_GCM_128_SALT_SIZE);

setsockopt(sock, SOL_TLS, TLS_TX, &crypto_info, sizeof(crypto_info));

送信と受信はそれぞれ別に設定されますが、設定方法は同じで、TLS_TXまたはTLS_RXを使用します。

TLSアプリケーションデータの送信¶

TLS_TXソケットオプションを設定した後、このソケットを介して送信されるすべてのアプリケーションデータは、TLSとソケットオプションで指定されたパラメータを使用して暗号化されます。たとえば、以下のように暗号化された「Hello World」レコードを送信できます。

const char *msg = "hello world\n";
send(sock, msg, strlen(msg));

send()で送信されるデータは、可能であればユーザー空間のバッファから直接暗号化され、暗号化済みカーネル送信バッファに直接書き込まれます。

sendfileシステムコールは、最大長さ（2^14）のTLSレコードを介してファイルのデータを送信します。

file = open(filename, O_RDONLY);
fstat(file, &stat);
sendfile(sock, file, &offset, stat.st_size);

send()呼び出しごとにTLSレコードが作成され送信されます。ただし、MSG_MOREを渡すと、そのレコードの作成が延期され、MSG_MOREが渡されなくなるか、最大レコードサイズに達するまで待機します。

カーネルは暗号化データ用のバッファを確保する必要があります。このバッファはsend()呼び出しのタイミングで確保され、send()呼び出し全体が-ENOMEM（またはメモリ待機）で終了するか、暗号化が常に成功するかのいずれかです。send()が-ENOMEMを返し、かつ前回のMSG_MOREを使用した呼び出しでデータがソケットバッファに残っていた場合、MSG_MOREのデータはソケットバッファに残されます。

TLSアプリケーションデータの受信¶

TLS_RXソケットオプションを設定した後、すべてのrecvファミリーソケット呼び出しは、提供されたTLSパラメータを使用して復号されます。復号には、完全なTLSレコードが受信される必要があります。

char buffer[16384];
recv(sock, buffer, 16384);

受信データは、ユーザー空間バッファが十分大きい場合、直接そのバッファに復号され、追加の割り当ては行われません。ユーザー空間バッファが小さすぎる場合、復号はカーネルで行われ、その後ユーザー空間にコピーされます。

EINVAL 受信メッセージのTLSバージョンが設定されたsetsockoptで指定されたバージョンと一致しない場合、エラーが返されます。

EMSGSIZE 受信メッセージが大きすぎる場合、エラーが返されます。

EBADMSG 他の理由で復号に失敗した場合、エラーが返されます。

TLSコントロールメッセージの送信¶

アプリケーションデータ以外にも、TLSはアラートメッセージ（レコードタイプ21）やハンドシェイクメッセージ（レコードタイプ22）などの制御メッセージを含みます。これらのメッセージは、CMSGを介してTLSレコードタイプを指定することでソケット経由で送信できます。例えば、以下の関数は@record_typeのレコードを使用して@lengthバイトの@dataを送信します。

/* send TLS control message using record_type */
static int klts_send_ctrl_message(int sock, unsigned char record_type,
                                  void *data, size_t length)
{
      struct msghdr msg = {0};
      int cmsg_len = sizeof(record_type);
      struct cmsghdr *cmsg;
      char buf[CMSG_SPACE(cmsg_len)];
      struct iovec msg_iov;   /* Vector of data to send/receive into.  */

      msg.msg_control = buf;
      msg.msg_controllen = sizeof(buf);
      cmsg = CMSG_FIRSTHDR(&msg);
      cmsg->cmsg_level = SOL_TLS;
      cmsg->cmsg_type = TLS_SET_RECORD_TYPE;
      cmsg->cmsg_len = CMSG_LEN(cmsg_len);
      *CMSG_DATA(cmsg) = record_type;
      msg.msg_controllen = cmsg->cmsg_len;

      msg_iov.iov_base = data;
      msg_iov.iov_len = length;
      msg.msg_iov = &msg_iov;
      msg.msg_iovlen = 1;

      return sendmsg(sock, &msg, 0);
}

制御メッセージのデータは暗号化せずに提供する必要があります。暗号化はカーネルによって行われます。

TLS制御メッセージの受信¶

TLS制御メッセージはユーザー空間バッファ内に渡され、メッセージタイプはcmsgを介して渡されます。cmsgバッファが提供されていない場合、制御メッセージが受信された場合はエラーが返されます。データメッセージはcmsgバッファが設定されていない場合でも受信されることがあります。

char buffer[16384];
char cmsg[CMSG_SPACE(sizeof(unsigned char))];
struct msghdr msg = {0};
msg.msg_control = cmsg;
msg.msg_controllen = sizeof(cmsg);

struct iovec msg_iov;
msg_iov.iov_base = buffer;
msg_iov.iov_len = 16384;

msg.msg_iov = &msg_iov;
msg.msg_iovlen = 1;

int ret = recvmsg(sock, &msg, 0 /* flags */);

struct cmsghdr *cmsg = CMSG_FIRSTHDR(&msg);
if (cmsg->cmsg_level == SOL_TLS &&
    cmsg->cmsg_type == TLS_GET_RECORD_TYPE) {
    int record_type = *((unsigned char *)CMSG_DATA(cmsg));
    // Do something with record_type, and control message data in
    // buffer.
    //
    // Note that record_type may be == to application data (23).
} else {
    // Buffer contains application data.
}

recvは、TLSレコードの複数種類からのデータを返しません。

統計¶

TLS実装は以下の各名前空間ごとの統計情報を公開します（/proc/net/tls_stat):

  • TlsCurrTxSw, TlsCurrRxSw - ホストが暗号化を処理している現在の送信（TX）および受信（RX）セッション数

  • TlsCurrTxDevice, TlsCurrRxDevice - NICが暗号化を処理している現在の送信（TX）および受信（RX）セッション数

  • TlsTxSw, TlsRxSw - ホスト暗号化を使用して開かれた送信（TX）および受信（RX）セッション数

  • TlsTxDevice, TlsRxDevice - NIC暗号化を使用して開かれた送信（TX）および受信（RX）セッション数

  • TlsDecryptError - レコード復号化失敗（例：認証タグの誤りによる）

  • TlsDeviceRxResync - 暗号化を処理しているNICに送信されたRX再同期数

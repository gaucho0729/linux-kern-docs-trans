SocketCAN - コントローラー・エリア・ネットワーク¶

概要 / SocketCANとは¶

socketcanパッケージは、Linux用のCANプロトコル（Controller Area Network）の実装です。CANは自動化、埋め込みデバイス、自動車分野などで広く利用されるネットワーク技術です。以前からLinux用のCAN実装は存在していましたが、SocketCANはBerkeleyソケットAPI、Linuxネットワークスタックを使用し、CANデバイスドライバをネットワークインターフェースとして実装しています。CANソケットAPIはTCP/IPプロトコルにできるだけ似せて設計されており、ネットワークプログラミングに精通したプログラマがCANソケットを使用するのを容易にするためのものです。

動機 / なぜソケットAPIを使用するのか¶

SocketCAN以前にもLinux用のCAN実装は存在していました。なぜまた新しいプロジェクトを開始したのかという疑問が生じます。ほとんどの既存の実装は特定のCANハードウェア用のデバイスドライバとして提供されており、キャラクターデバイスベースで、機能は比較的限定的です。通常、ハードウェア固有のデバイスドライバが提供され、キャラクターデバイスインターフェースを通じてraw CANフレームをコントローラーハードウェアと直接やり取りする機能が備えられています。フレームのキューイングやISO-TPなどの高レベルトランスポートプロトコルはユーザー空間アプリケーションで実装する必要があります。また、ほとんどのキャラクターデバイス実装は、シリアルインターフェースと同様に、一度に1つのプロセスのみがデバイズを開くことができます。CANコントローラーの交換には別のデバイスドライバの導入が必要で、多くのアプリケーションの一部を新しいドライバのAPIに合わせて調整する必要がありました。

SocketCANはこれらの制限を克服するために設計されました。新しいプロトコルファミリが実装され、ユーザー空間アプリケーションに対してソケットインターフェースを提供し、Linuxネットワークレイヤーに基づいており、提供されるキュー処理機能をすべて利用可能にしています。CANコントローラハードウェアのデバイスドライバーはLinuxネットワークレイヤーにネットワークデバイスとして登録され、コントローラからCANフレームがネットワークレイヤーに伝送され、CANプロトコルファミリーモジュールに到達し、逆も可能です。また、プロトコルファミリーモジュールはトランスポートプロトコルモジュールが登録できるAPIを提供しており、任意の数のトランスポートプロトコルが動的にロードまたはアンロード可能になります。実際、canコアモジュール単体ではプロトコルを提供せず、少なくとも1つの追加プロトコルモジュールをロードしないと使用できません。複数のソケットが同時に開けられ、異なるまたは同じプロトコルモジュール上で動作し、異なるまたは同じCAN IDでフレームをリスニング/送信可能です。同じインターフェースで同じCAN IDを持つフレームをリスニングする複数のソケットは、すべて同じ受信フレームを受信します。特定のトランスポートプロトコル、例えばISO-TPで通信したいアプリケーションは、ソケットを開く際にそのプロトコルを選択し、その後アプリケーションデータバイトストリームを読み書きできるようになります。CAN-IDやフレームなどの処理は必要ありません。

ユーザー空間から同様の機能を提供するには、キャラクタデバイスでも可能ですが、いくつかの理由により技術的に不適切な解決策になります。

  • 複雑な使用方法: socket(2)にプロトコル引数を渡す代わりに、bind(2)でCANインターフェースとCAN IDを選択する代わりに、アプリケーションはioctl(2)を使用してすべての操作を行う必要があります。

  • コードの複製: キャラクタデバイスはLinuxネットワークキュー処理コードを活用できないため、CANネットワーキング用にすべてのコードを複製する必要があります。

  • 抽象化: 現在のキャラクターデバイス実装の多くでは、CANコントローラーのハードウェア固有のデバイスドライバーがアプリケーションが操作するキャラクターデバイスを直接提供します。これは、Unixシステムにおいて、キャラクターデバイスとブロックデバイスの双方で非常に珍しい実装です。例えば、シリアルインターフェースの特定のUART、コンピュータ内の特定のサウンドチップ、SCSIまたはIDEコントローラーがハードディスクやテープストリーマーへのアクセスを提供するといったケースは、キャラクターデバイスが存在しません。代わりに、アプリケーション側に統一されたキャラクターデバイスまたはブロックデバイスインターフェースを提供する抽象レイヤーがあり、一方ではハードウェア固有のデバイスドライバのインターフェースが提供されます。このような抽象化は、ttyレイヤー、オーディオサブシステム、SCSIおよびIDEサブシステムなどのサブシステムによって提供されます。

    CANデバイスドライバーを実装する最も簡単な方法は、このような（完全な）抽象レイヤーを用いないキャラクターデバイスとして実装することです。これは現在の大多数のドライバーで行われています。しかし、正しい方法は、特定のCAN IDへの登録、複数のオープンファイルディスクリプタのサポート、CANフレームの（デ）マルチプレクシング、（複雑な）キューイング、デバイスドライバーが登録できるAPIを提供するような抽象レイヤーを追加することです。しかし、その場合、Linuxカーネルが提供するネットワーキングフレームワークを使用する方がむしろ簡単になるかもしれません。これはSocketCANが行っていることです。

LinuxでCANを実装する最も自然で適切な方法は、Linuxカーネルのネットワーキングフレームワークを使用することです。

SocketCANのコンセプト¶

説明に従って 動機 / なぜソケットAPIを使用するのか SocketCANの主な目的は、Linuxネットワークレイヤーに基づくソケットインターフェースをユーザー空間アプリケーションに提供することです。これは、一般的に知られているTCP/IPおよびイーサネットネットワーキングとは異なり、CANバスはブロードキャストのみの（！）媒体であり、イーサネットのようにMACレイヤーのアドレス指定がありません。CAN識別子（can_id）はCANバスでの arbitration に使用されます。そのため、CAN-IDsはバス上で一意に選択する必要があります。CAN-ECUネットワークを設計する際には、CAN-IDsは特定のECUが送信するようにマッピングされます。このため、CAN-IDはソースアドレスの一種として扱うのが最適です。

受信リスト¶

複数のアプリケーションがネットワーク透過的にアクセスすることで、同じCANネットワークインターフェースから同じCAN-IDsに興味を持つアプリケーションが存在する可能性があります。このため、SocketCANコアモジュール（プロトコルファミリーキャンを実装）は、複数の高効率受信リストを提供しています。例えば、ユーザー空間アプリケーションがCAN RAWソケットを開く場合、rawプロトコルモジュール自体がユーザーが要求するCAN-IDs（範囲）をSocketCANコアから取得します。CAN-IDsのサブスクリプションとアンサブスクリプションは、can_rx_(un)register()関数を使用して、特定のCANインターフェースまたはすべての（！）CANインターフェースに対してSocketCANコアが提供します（参照 SocketCANコアモジュール）。使用時のCPU使用率を最適化するため、受信リストは各デバイスごとに使用ケースに応じたフィルタ複雑度に合わせて複数の特定リストに分割されています。

送信フレームのローカルループバック¶

他のネットワーキング概念から知られているように、データ交換アプリケーションは、アドレス情報の変更を除けば、同じノードまたは異なるノードでも動作します：

 ___   ___   ___                   _______   ___
| _ | | _ | | _ |                 | _   _ | | _ |
||A|| ||B|| ||C||                 ||A| |B|| ||C||
|___| |___| |___|                 |_______| |___|
  |     |     |                       |       |
-----------------(1)- CAN bus -(2)---------------

例（2）でアプリケーションAが例（1）で得られる情報と同じ情報を受信するためには、適切なノードで送信されたCANフレームのローカルループバックが必要です。

Linuxネットワークデバイス（デフォルトでは）は、メディア依存フレームの送受信を処理するだけで、CANバスでのアリーナビュレーションにより、低優先度CAN-IDの送信が高優先度CANフレームの受信によって遅延することがあります。正しい 1 ノードでのトラフィックを反映するため、送信成功後に送信データのループバックを実行する必要があります。CANネットワークインターフェースが何らかの理由でループバックを実行できない場合、SocketCANコアがフォールバックとしてこのタスクを担当します。詳細は 送信フレームのローカルループバック をご参照ください（推奨）。

ループバック機能はデフォルトで有効になっており、CANアプリケーションの標準的なネットワーキング動作を反映しています。一部のRT-SocketCANグループからの要望により、各ソケットごとにループバックをオプションで無効化できます。詳細はCAN RAWソケットのsockoptsを RAWプロトコルソケットとcan_filters（SOCK_RAW）.

1

分析ツール（例：'candump'や'cansniffer'）を（同じ）ノードで実行する際には、この機能が非常に役立ちます。

ネットワーク問題通知¶

CANバスの使用は、物理層およびメディアアクセス制御層でいくつかの問題を引き起こす可能性があります。これらの下位層の問題を検出・ログとして記録することは、CANユーザーが物理トランシーバー層のハードウェア問題や、異なるECUによって引き起こされる arbitration問題やエラーフレームを特定するための重要な要件です。検出されたエラーの発生は診断において重要であり、正確なタイムスタンプとともにログとして記録する必要があります。そのため、CANインターフェースドライバーは、他のCANフレームと同じようにユーザー アプリケーションにオプションで渡せる「エラーメッセージフレーム」と呼ばれるフレームを生成します。物理層またはMAC層でエラーが検出された場合（例：CANコントローラーによって）、ドライバーは適切なエラーメッセージフレームを作成します。ユーザー アプリケーションは一般的なCANフィルターメカニズムを使用してエラーメッセージフレームを要求できます。このフィルターディフィニション内で、関心のあるエラーの種類を選択できます。エラーメッセージの受信はデフォルトで無効になっています。CANエラーメッセージフレームの形式は、Linuxヘッダーファイル「include/uapi/linux/can/error.h」で簡潔に説明されています。

SocketCANの使用方法¶

TCP/IPと同様に、CANネットワークを介して通信するためにはまずソケットを開く必要があります。SocketCANは新しいプロトコルファミリを実装しているため、socket(2)システムコールに最初の引数としてPF_CANを渡す必要があります。現在、選択できるCANプロトコルは2種類あります。raw socketプロトコルとブロードキャストマネージャー（BCM）です。そのため、ソケットを開くには以下のように記述します：

s = socket(PF_CAN, SOCK_RAW, CAN_RAW);

および：

s = socket(PF_CAN, SOCK_DGRAM, CAN_BCM);

それぞれ。ソケットの成功した作成後、通常はbind(2)システムコールを使用してソケットをCANインターフェースにバインドします（TCP/IPとは異なりアドレス指定が異なるため、参照してください SocketCANのコンセプト）。CAN_RAWでバインド（またはCAN_BCMで接続）した後、通常のread(2)とwrite(2)を使用してソケットからデータを読み書きできます。send(2)、sendto(3)、sendmsg(2)やrecv*の対応操作も同様に使用できます。以下にCAN固有のソケットオプションについても説明します。

基本的なCANフレーム構造とsockaddr構造体はinclude/linux/can.hに定義されています：

struct can_frame {
        canid_t can_id;  /* 32 bit CAN_ID + EFF/RTR/ERR flags */
        __u8    can_dlc; /* frame payload length in byte (0 .. 8) */
        __u8    __pad;   /* padding */
        __u8    __res0;  /* reserved / padding */
        __u8    __res1;  /* reserved / padding */
        __u8    data[8] __attribute__((aligned(8)));
};

（線形）ペイロードデータ[]を64ビット境界にアライメントすることで、ユーザーはカスタムの構造体やユニオンを定義してCANペイロードを簡単にアクセスできるようになります。CANバスにはデフォルトではバイトオーダーが指定されていません。CAN_RAWソケットのread(2)システムコールは、ユーザー空間にstruct can_frameを転送します。

sockaddr_can構造体はPF_PACKETソケットと同様にインターフェースインデックスを持ち、特定のインターフェースにバインドします：

struct sockaddr_can {
        sa_family_t can_family;
        int         can_ifindex;
        union {
                /* transport protocol class address info (e.g. ISOTP) */
                struct { canid_t rx_id, tx_id; } tp;

                /* reserved for future CAN protocols address information */
        } can_addr;
};

インターフェースインデックスを決定するには、適切なioctl()を使用する必要があります（エラー検証なしのCAN_RAWソケットの例）：

int s;
struct sockaddr_can addr;
struct ifreq ifr;

s = socket(PF_CAN, SOCK_RAW, CAN_RAW);

strcpy(ifr.ifr_name, "can0" );
ioctl(s, SIOCGIFINDEX, &ifr);

addr.can_family = AF_CAN;
addr.can_ifindex = ifr.ifr_ifindex;

bind(s, (struct sockaddr *)&addr, sizeof(addr));

(..)

すべての(!)CANインターフェースにソケットをバインドするには、インターフェースインデックスが0（ゼロ）でなければなりません。この場合、ソケットはすべての有効なCANインターフェースからCANフレームを受信します。発信元のCANインターフェースを特定するには、read(2)ではなくrecvfrom(2)システムコールを使用できます。'any'インターフェースにバインドされたソケットから送信するには、送信先インターフェースを指定するためにsendto(2)が必要です。

バインドされたCAN_RAWソケットからCANフレームを読み取るには、can_frame構造体を読み取る必要があります：

struct can_frame frame;

nbytes = read(s, &frame, sizeof(struct can_frame));

if (nbytes < 0) {
        perror("can raw socket read");
        return 1;
}

/* paranoid check ... */
if (nbytes < sizeof(struct can_frame)) {
        fprintf(stderr, "read: incomplete CAN frame\n");
        return 1;
}

/* do something with the received CAN frame */

CANフレームの書き込みは、write(2)システムコールを使用して同様に行えます：

nbytes = write(s, &frame, sizeof(struct can_frame));

'any'既存のCANインターフェースにCANインターフェースがバインドされている場合（addr.can_ifindex = 0）、発信元のCANインターフェースに関する情報を必要とする場合はrecvfrom(2)を使用することをお勧めします：

struct sockaddr_can addr;
struct ifreq ifr;
socklen_t len = sizeof(addr);
struct can_frame frame;

nbytes = recvfrom(s, &frame, sizeof(struct can_frame),
                  0, (struct sockaddr*)&addr, &len);

/* get interface name of the received CAN frame */
ifr.ifr_ifindex = addr.can_ifindex;
ioctl(s, SIOCGIFNAME, &ifr);
printf("Received a CAN frame from interface %s", ifr.ifr_name);

'any' CANインターフェースにバインドされたソケットからCANフレームを書き込むには、送信インターフェースを明示的に定義する必要があります：

strcpy(ifr.ifr_name, "can0");
ioctl(s, SIOCGIFINDEX, &ifr);
addr.can_ifindex = ifr.ifr_ifindex;
addr.can_family  = AF_CAN;

nbytes = sendto(s, &frame, sizeof(struct can_frame),
                0, (struct sockaddr*)&addr, sizeof(addr));

ソケットからメッセージを読み取った後、ioctl(2)コールを使用して正確なタイムスタンプを取得できます：

struct timeval tv;
ioctl(s, SIOCGSTAMP, &tv);

タイムスタンプはマイクロ秒単位の解像度を持ち、CANフレームの受信時に自動的に設定されます。

CAN FD（flexible data rate）サポートに関する補足：

一般的に、CAN FDの処理は以前に記述した例と非常に類似しています。新しいCAN FD対応CANコントローラーは、CAN FDフレームの仲裁段階とペイロード段階で異なるビットレートをサポートし、最大で64バイトのペイロードをサポートします。この拡張されたペイロード長は、固定8バイトのペイロード（can_frame構造体）を前提とした多くのカーネルインターフェース（ABI）を破壊します。たとえば、CAN_RAWソケットは新しいソケットオプションCAN_RAW_FD_FRAMESをサポートし、CAN FDフレームと（レガシー）CANフレームの同時処理を可能にします（参照： RAW Socket Option CAN_RAW_FD_FRAMES).

canfd_frame構造体はinclude/linux/can.hに定義されています：

struct canfd_frame {
        canid_t can_id;  /* 32 bit CAN_ID + EFF/RTR/ERR flags */
        __u8    len;     /* frame payload length in byte (0 .. 64) */
        __u8    flags;   /* additional flags for CAN FD */
        __u8    __res0;  /* reserved / padding */
        __u8    __res1;  /* reserved / padding */
        __u8    data[64] __attribute__((aligned(8)));
};

canfd_frame構造体と既存のcan_frame構造体は、can_id、ペイロード長、ペイロードデータが同じオフセット位置に配置されているため、異なる構造体をほぼ同様に処理できます。can_frame構造体の内容をcanfd_frame構造体にコピーする場合、すべての構造体要素をそのまま使用できます（データ[]は拡張されます）。

canfd_frame構造体を導入する際、can_frame構造体のデータ長コード（DLC）が長さ情報を表し、DLCは0〜8の範囲で1:1のマッピングを有していました。長さ情報を容易に扱えるようにするため、canfd_frame.len要素は0〜64の平文の長さ値を含みます。したがって、canfd_frame.lenとcan_frame.can_dlcは等しく、長さ情報を含み、DLCは含みません。CANとCAN FDをサポート可能なデバイスの区別およびバス関連のデータ長コード（DLC）へのマッピングについての詳細は CAN FD (Flexible Data Rate) ドライバサポート.

2つのCAN(FD)フレーム構造体の長さは、CAN(FD)ネットワークインターフェースおよびskbuffデータ長の最大転送単位（MTU）を定義します。CAN固有のMTUについては、include/linux/can.hに2つの定義が指定されています:

#define CAN_MTU   (sizeof(struct can_frame))   == 16  => 'legacy' CAN frame
#define CANFD_MTU (sizeof(struct canfd_frame)) == 72  => CAN FD frame

RAWプロトコルソケットとcan_filters（SOCK_RAW）¶

CAN_RAWソケットの使用は、一般的なCANキャラクタデバイスへのアクセスと非常に類似しています。多ユーザーのSocketCANアプローチが提供する新たな可能性に対応するため、RAWソケットのバインディング時にいくつかの合理的なデフォルト設定が行われます:

  • フィルタが1つだけを設定し、すべてのデータを受信するように設定されています

  • ソケットは有効なデータフレームのみを受信します（=> エラーメッセージフレームは含まれません）

  • 送信されたCANフレームのループバックが有効になっています（参照 送信フレームのローカルループバック)

  • ソケットはループバックモードで自身が送信したフレームを受信しません

これらのデフォルト設定はソケットをバインドする前後でも変更可能です。CAN_RAWソケットの参照定義をソケットオプションで使用するには、<linux/can/raw.h>をインクルードしてください。

RAWソケットオプション CAN_RAW_FILTER¶

CAN_RAWソケットを使用したCANフレームの受信は、CAN_RAW_FILTERソケットオプションで0〜n個のフィルタを定義することで制御可能です。

CANフィルタ構造体はinclude/linux/can.hに定義されています:

struct can_filter {
        canid_t can_id;
        canid_t can_mask;
};

フィルタがマッチするのは、

<received_can_id> & mask == can_id & mask

これは既知のCANコントローラハードウェアフィルタのセマンティックに類似しています。can_filter構造体のcan_id要素にCAN_INV_FILTERビットが設定されている場合、このセマンティックでフィルタを反転させることができます。CANコントローラハードウェアフィルタとは異なり、ユーザーは各オープンソケットに対して0〜n個の受信フィルタを個別に設定可能です:

struct can_filter rfilter[2];

rfilter[0].can_id   = 0x123;
rfilter[0].can_mask = CAN_SFF_MASK;
rfilter[1].can_id   = 0x200;
rfilter[1].can_mask = 0x700;

setsockopt(s, SOL_CAN_RAW, CAN_RAW_FILTER, &rfilter, sizeof(rfilter));

選択されたCAN_RAWソケットでCANフレームの受信を無効にするには:

setsockopt(s, SOL_CAN_RAW, CAN_RAW_FILTER, NULL, 0);

フィルタをゼロに設定することは、データを読み込まないためrawソケットが受信したCANフレームを破棄するため、かなり古風な方法です。しかし、この「送信専用」のユースケースを考慮し、カーネル内で受信リストを削除して、わずかな（本当にわずかな！）CPU使用量を節約する方法があります。

CANフィルタ使用の最適化¶

CANフィルタは、CANフレームの受信時に各デバイスごとのフィルタリストで処理されます。フィルタリストを走査する際のチェック回数を減らすために、CANコアは単一のCAN IDに焦点を当てたフィルタ登録時に最適化されたフィルタ処理を提供します。

2048個の可能なSFF CAN識別子に対しては、識別子をインデックスとして使用して対応する登録リストに直接アクセスします（追加のチェックは不要です）。2^29個の可能なEFF CAN識別子に対しては、10ビットのXORフォールディングをハッシュ関数として使用してEFFテーブルインデックスを取得します。

単一のCAN識別子に最適化されたフィルタを活用するには、can_filter.maskにCAN_SFF_MASKまたはCAN_EFF_MASKを設定し、CAN_EFF_FLAGおよびCAN_RTR_FLAGビットを設定する必要があります。can_filter.maskのCAN_EFF_FLAGビットが設定されていると、SFFまたはEFF CAN IDの登録が区別されることを示します。例えば上記の例では：

rfilter[0].can_id   = 0x123;
rfilter[0].can_mask = CAN_SFF_MASK;

CAN ID 0x123のSFFフレームと、0xXXXXX123のEFFフレームの両方が通過します。

0x123（SFF）および0x12345678（EFF）のCAN識別子のみをフィルタリングするには、このようにフィルタを定義する必要があります（最適化されたフィルタを活用するため）：

struct can_filter rfilter[2];

rfilter[0].can_id   = 0x123;
rfilter[0].can_mask = (CAN_EFF_FLAG | CAN_RTR_FLAG | CAN_SFF_MASK);
rfilter[1].can_id   = 0x12345678 | CAN_EFF_FLAG;
rfilter[1].can_mask = (CAN_EFF_FLAG | CAN_RTR_FLAG | CAN_EFF_MASK);

setsockopt(s, SOL_CAN_RAW, CAN_RAW_FILTER, &rfilter, sizeof(rfilter));

RAWソケットオプション CAN_RAW_ERR_FILTER¶

説明に従って ネットワーク問題通知 CANインターフェースドライバーは、エラーメッセージフレームを生成でき、ユーザー アプリケーションに他のCANフレームと同様にオプションで転送できます。エラーはいくつかのエラーカテゴリに分類され、適切なエラーマスクを使用してフィルタリング可能です。すべての可能なエラー条件を登録するには、エラーマスクにCAN_ERR_MASKを使用します。エラーマスクの値はlinux/can/error.hで定義されています：

can_err_mask_t err_mask = ( CAN_ERR_TX_TIMEOUT | CAN_ERR_BUSOFF );

setsockopt(s, SOL_CAN_RAW, CAN_RAW_ERR_FILTER,
           &err_mask, sizeof(err_mask));

RAWソケットオプション CAN_RAW_LOOPBACK¶

多ユーザーのニーズに対応するため、ローカルループバックはデフォルトで有効になっています（詳しくは 送信フレームのローカルループバック を参照）。ただし、一部の埋め込み用途（例：CANバスを1つのアプリケーションのみが使用する場合）では、このループバック機能を個別に各ソケットごとに無効にできます：

int loopback = 0; /* 0 = disabled, 1 = enabled (default) */

setsockopt(s, SOL_CAN_RAW, CAN_RAW_LOOPBACK, &loopback, sizeof(loopback));

RAWソケットオプション CAN_RAW_RECV_OWN_MSGS¶

ローカルループバックが有効な場合、送信されたすべてのCANフレームは、指定されたインターフェースでCAN-IDに登録したオープンなCANソケットにループバックされます。同じソケットで送信したCANフレームの受信は不要とみなされ、デフォルトでは無効になっています。このデフォルト動作は必要に応じて変更可能です：

int recv_own_msgs = 1; /* 0 = disabled (default), 1 = enabled */

setsockopt(s, SOL_CAN_RAW, CAN_RAW_RECV_OWN_MSGS,
           &recv_own_msgs, sizeof(recv_own_msgs));

RAW Socket Option CAN_RAW_FD_FRAMES¶

CAN_RAWソケットにおけるCAN FDのサポートは、新しいソケットオプションCAN_RAW_FD_FRAMESを有効にすることで実現可能です。このオプションはデフォルトではオフになっています。新しいソケットオプションがCAN_RAWソケットでサポートされていない場合（例：古いカーネルの場合）、CAN_RAW_FD_FRAMESオプションの切り替えは-ENOPROTOOPTエラーを返します。

CAN_RAW_FD_FRAMESが有効になると、アプリケーションはCANフレームとCAN FDフレームの両方を送信できます。一方で、ソケットから読み込む際には、アプリケーションはCANフレームとCAN FDフレームの両方を処理する必要があります。

CAN_RAW_FD_FRAMES enabled:  CAN_MTU and CANFD_MTU are allowed
CAN_RAW_FD_FRAMES disabled: only CAN_MTU is allowed (default)

例:

[ remember: CANFD_MTU == sizeof(struct canfd_frame) ]

struct canfd_frame cfd;

nbytes = read(s, &cfd, CANFD_MTU);

if (nbytes == CANFD_MTU) {
        printf("got CAN FD frame with length %d\n", cfd.len);
        /* cfd.flags contains valid data */
} else if (nbytes == CAN_MTU) {
        printf("got legacy CAN frame with length %d\n", cfd.len);
        /* cfd.flags is undefined */
} else {
        fprintf(stderr, "read: invalid CAN(FD) frame\n");
        return 1;
}

/* the content can be handled independently from the received MTU size */

printf("can_id: %X data length: %d data: ", cfd.can_id, cfd.len);
for (i = 0; i < cfd.len; i++)
        printf("%02X ", cfd.data[i]);

CANFD_MTUサイズで読み込む場合、受信したCAN_MTUバイトのみが返され、提供されたCAN FD構造体にレガシCANフレームが読み込まれます。注意点として、canfd_frame.flagsデータフィールドはstruct can_frameには指定されていないため、CANFD_MTUサイズのCAN FDフレームでのみ有効です。

新規CANアプリケーションの実装ヒント:

CAN FDをサポートするアプリケーションを構築するには、CAN_RAWベースのアプリケーションで基本的なCANデータ構造としてstruct canfd_frameを使用してください。アプリケーションが古いLinuxカーネルで実行され、CAN_RAW_FD_FRAMESソケットオプションの切り替えでエラーが発生しても問題ありません。レガシCANフレームまたはCAN FDフレームを取得でき、同じ方法で処理可能です。

CANデバイスに送信する際は、デバイスがCAN FDフレームを処理できるか確認してください。デバイスの最大転送単位（MTU）がCANFD_MTUであるかを確認します。CANデバイスのMTUは、SIOCGIFMTU ioctl()システムコールなどで取得可能です。

RAWソケットオプション CAN_RAW_JOIN_FILTERS¶

CAN_RAWソケットは複数のCAN識別子に特化したフィルタを設定できます。これにより、af_can.cフィルタ処理で複数のフィルタが生成されます。これらのフィルタは互いに独立しており、適用時に論理ORのフィルタになります（参照 RAWソケットオプション CAN_RAW_FILTER).

このソケットオプションは、指定されたCANフィルタを組み合わせて、ユーザー空間に転送されるCANフレームが指定されたフィルタに一致するようにします。 すべての読者が完了するまで待機したとしても、更新処理が読者がいないと信頼できる期間はゼロである。 適用されたフィルタのセマンティックは論理ANDに変更されます。

特に、フィルタセットがCAN_INV_FILTERフラグが設定された複数のフィルタで構成されている場合、この機能は入力トラフィックから特定のCAN IDやCAN ID範囲を除外するために役立ちます。

RAWソケットで返されるメッセージフラグ¶

recvmsg()呼び出しを使用する場合、msg->msg_flagsには以下のフラグが含まれる可能性があります:

MSG_DONTROUTE:

受信フレームがローカルホストで作成された場合に設定されます。

MSG_CONFIRM:

フレームが受信したソケットを介して送信された場合に設定されます。CANドライバがドライバレベルでフレームのエコーをサポートする場合、このフラグは「送信確認」と解釈できます（参照 送信フレームのローカルループバック および 送信フレームのローカルループバックこのようなメッセージを受信するには、CAN_RAW_RECV_OWN_MSGSを設定する必要があります。

ブロードキャストマネージャプロトコルソケット (SOCK_DGRAM)¶

ブロードキャストマネージャプロトコルは、カーネル空間でフィルタリングして送信（例：周期的な）CANメッセージのコマンドベースの設定インターフェースを提供します。

受信フィルタは、頻繁なメッセージを減らすために使用でき、メッセージ内容の変更、パケット長の変更などのイベントを検出したり、受信メッセージのタイムアウト監視を行うことができます。

CANフレームまたはCANフレームのシーケンスの周期的な送信タスクは、実行時に作成および変更でき、メッセージ内容および2つの可能な送信間隔を変更できます。

BCMソケットは、CAN_RAWソケットで知られているstruct can_frameを使用して個々のCANフレームを送信するためのものではありません。代わりに、特別なBCM構成メッセージが定義されています。ブロードキャストマネージャと通信するための基本的なBCM構成メッセージおよび利用可能な操作は、linux/can/bcm.hに含まれています。BCMメッセージは、コマンド（'オペコード'）を持つメッセージヘッダーに続いてゼロまたは複数のCANフレームで構成され、ブロードキャストマネージャはユーザー空間に同じ形式で応答を送信します。

struct bcm_msg_head {
        __u32 opcode;                   /* command */
        __u32 flags;                    /* special flags */
        __u32 count;                    /* run 'count' times with ival1 */
        struct timeval ival1, ival2;    /* count and subsequent interval */
        canid_t can_id;                 /* unique can_id for task */
        __u32 nframes;                  /* number of can_frames following */
        struct can_frame frames[0];
};

アライメントされたペイロード 'frames' は、最初の RAW Socket Option CAN_RAW_FD_FRAMES include/linux/can.h に定義された基本的なCANフレーム構造を使用しています。ユーザー空間からブロードキャストマネージャへのすべてのメッセージはこの構造を持っています。

注意：CAN_BCMソケットは、ソケット作成後に接続する必要があります（エラー検査なしの例）：

int s;
struct sockaddr_can addr;
struct ifreq ifr;

s = socket(PF_CAN, SOCK_DGRAM, CAN_BCM);

strcpy(ifr.ifr_name, "can0");
ioctl(s, SIOCGIFINDEX, &ifr);

addr.can_family = AF_CAN;
addr.can_ifindex = ifr.ifr_ifindex;

connect(s, (struct sockaddr *)&addr, sizeof(addr));

(..)

ブロードキャストマネージャソケットは、任意の数の進行中の送信または受信フィルタを同時に処理できます。異なるRX/TXジョブは、各BCMメッセージ内の一意のcan_idで区別されます。ただし、複数のCANインターフェース間で通信するには、追加のCAN_BCMソケットが推奨されます。ブロードキャストマネージャソケットが 'any' CANインターフェースにバインドされている場合（=> インターフェースインデックスがゼロに設定されている）、設定された受信フィルタは任意のCANインターフェースに適用されます（ただし、sendto() システムコールを使用して 'any' CANインターフェースインデックスを上書きできます）。recvfrom() を read() ではなく使用してBCMソケットメッセージを取得する場合、発信元のCANインターフェースは can_ifindex で提供されます。

ブロードキャストマネージャ操作¶

オペコードは、ブロードキャストマネージャが実行する操作を定義するか、またはユーザーからのリクエストを含むいくつかのイベントに対するブロードキャストマネージャの応答を詳細に説明します。

送信操作（ユーザー空間からブロードキャストマネージャ）：

TX_SETUP:

周期的な送信タスクを生成します。

TX_DELETE:

周期的な送信タスクを削除します（can_idのみが必要です）。

TX_READ:

can_idの周期的な送信タスクのプロパティを読み込む。

TX_SEND:

1つのCANフレームを送信する。

ブロードキャストマネージャーからユーザー空間への応答を送信する：

TX_STATUS:

TX_READリクエスト（送信タスクの設定）への応答を返す。

TX_EXPIRED:

カウンターが初期間隔‘ival1’で送信を終了したときに通知する。TX_SETUPでTX_COUNTEVTフラグが設定されている必要があります。

受信操作（ユーザー空間からブロードキャストマネージャー）：

RX_SETUP:

RXコンテンツフィルタースブスクリプションを作成する。

RX_DELETE:

RXコンテンツフィルタースブスクリプションを削除する（can_idのみ必要）。

RX_READ:

can_idのRXコンテンツフィルタースブスクリプションのプロパティを読み込む。

ブロードキャストマネージャーからユーザー空間への応答：

RX_STATUS:

RX_READリクエスト（フィルタータスクの設定）への応答を返す。

RX_TIMEOUT:

周期的なメッセージが欠落していることを検出（タイマーアイテム1が期限切れ）。

RX_CHANGED:

BCMメッセージで更新されたCANフレーム（検出されたコンテンツ変更）。最初のメッセージ受信時または修正されたCANメッセージ受信時に送信される。

ブロードキャストマネージャーメッセージフラグ¶

ブロードキャストマネージャーにメッセージを送信する際、‘flags’要素には以下のフラグ定義が含まれる可能性があり、動作に影響を与える：

SETTIMER:

ival1、ival2およびcountの値を設定する

STARTTIMER:

ival1、ival2およびcountの現在値でタイマースタート。タイマースタートは同時にCANフレームの送信を開始する。

TX_COUNTEVT:

countが期限切れ時にメッセージTX_EXPIREDを生成する

TX_ANNOUNCE:

プロセスによるデータの変更は即時に発信される。

TX_CP_CAN_ID:

メッセージヘッダーから各次のフレームにcan_idをコピーします。これは使用法の簡略化を目的としています。TXタスクでは、メッセージヘッダーからの一意なcan_idは、次のstruct can_frame(s)で送信するために保存されたcan_id(s)と異なる場合があります。

RX_FILTER_ID:

can_idのみでフィルタリング（フレーム不要、nframes=0）。

RX_CHECK_DLC:

DLCの変更によりRX_CHANGEDが発生します。

RX_NO_AUTOTIMER:

タイムアウトモニタの自動起動を防ぐ。

RX_ANNOUNCE_RESUME:

RX_SETUPで指定され、受信タイムアウトが発生した場合、(サイクル)受信が再開するとRX_CHANGEDメッセージが生成されます。

TX_RESET_MULTI_IDX:

多重フレーム送信のインデックスをリセットします。

RX_RTR_FRAME:

RTRリクエストに対する応答を送信します（op->frames[0]に配置されます）。

ブロードキャストマネージャー送信タイマ¶

周期的な送信設定では最大2つのインターバルタイマを使用できます。この場合、BCMはインターバル「ival1」で「count」回メッセージを送信し、その後「ival2」で継続して送信します。1つのタイマのみが必要な場合は「count」をゼロに設定し、「ival2」のみ使用します。SET_TIMERおよびSTART_TIMERフラグが設定されている場合、タイマがアクティブになります。SET_TIMERのみ設定されている場合、実行時にもタイマ値を変更できます。

ブロードキャストマネージャーメッセージシーケンス送信¶

サイクル送信タスク設定の場合、最大256のCANフレームをシーケンスで送信できます。BCMメッセージヘッダーの「nframes」要素にCANフレームの数が指定されます。定義されたCANフレーム数はTX_SETUP BCM設定メッセージに配列として追加されます：

/* create a struct to set up a sequence of four CAN frames */
struct {
        struct bcm_msg_head msg_head;
        struct can_frame frame[4];
} mytxmsg;

(..)
mytxmsg.msg_head.nframes = 4;
(..)

write(s, &mytxmsg, sizeof(mytxmsg));

送信ごとにCANフレーム配列のインデックスが増加し、インデックスオーバーフロー時にゼロに戻します。

ブロードキャストマネージャー受信フィルタタイマ¶

RX_SETUPでタイマ値ival1またはival2をゼロ以外に設定できます。SET_TIMERフラグが設定されている場合、タイマが有効になります：

ival1:

指定された時間内に受信メッセージが再受信されない場合、RX_TIMEOUTを送信します。RX_SETUPでSTART_TIMERフラグが設定されている場合、以前のCANフレーム受信なしでもタイムアウト検出が即座に有効になります。

ival2:

受信メッセージのレートをival2の値に制限します。CANフレーム内の信号がステートレスである場合、ival2期間内でのステート変化が失われる可能性があるため、アプリケーションでメッセージを減らすのに役立ちます。

ブロードキャストマネージャー多重メッセージ受信フィルタ¶

多重メッセージシーケンスのコンテンツ変化をフィルタリングするには、RX_SETUP設定メッセージに1つ以上のCANフレームを配列として渡します。最初のCANフレームのデータバイトに、後続のCANフレームで受信したCANフレームと一致する必要のある関連ビットのマスクが含まれます。後続のCANフレームのうち、そのフレームデータのビットと一致するものが存在する場合、その関連コンテンツを前回受信したコンテンツと比較します。最大257のCANフレーム（多重フィルタビットマスクCANフレーム＋256のCANフィルタ）をTX_SETUP BCM設定メッセージに配列として追加できます：

/* usually used to clear CAN frame data[] - beware of endian problems! */
#define U64_DATA(p) (*(unsigned long long*)(p)->data)

struct {
        struct bcm_msg_head msg_head;
        struct can_frame frame[5];
} msg;

msg.msg_head.opcode  = RX_SETUP;
msg.msg_head.can_id  = 0x42;
msg.msg_head.flags   = 0;
msg.msg_head.nframes = 5;
U64_DATA(&msg.frame[0]) = 0xFF00000000000000ULL; /* MUX mask */
U64_DATA(&msg.frame[1]) = 0x01000000000000FFULL; /* data mask (MUX 0x01) */
U64_DATA(&msg.frame[2]) = 0x0200FFFF000000FFULL; /* data mask (MUX 0x02) */
U64_DATA(&msg.frame[3]) = 0x330000FFFFFF0003ULL; /* data mask (MUX 0x33) */
U64_DATA(&msg.frame[4]) = 0x4F07FC0FF0000000ULL; /* data mask (MUX 0x4F) */

write(s, &msg, sizeof(msg));

ブロードキャストマネージャーCAN FDサポート¶

CAN_BCMのプログラミングAPIはbcm_msg_head構造体の直後に配列として直接渡されるstruct can_frameに依存しています。CAN FDフレームに対応するためには、bcm_msg_headフラグに新しいフラグ'CAN_FD_FRAME'を追加し、bcm_msg_headの後にある連結されたCANフレーム構造体がstruct canfd_frameとして定義されていることを示します。

struct {
        struct bcm_msg_head msg_head;
        struct canfd_frame frame[5];
} msg;

msg.msg_head.opcode  = RX_SETUP;
msg.msg_head.can_id  = 0x42;
msg.msg_head.flags   = CAN_FD_FRAME;
msg.msg_head.nframes = 5;
(..)

CAN FDフレームをマルチプレクスフィルタリングに使用する場合でも、struct canfd_frameデータセクションの最初の64ビットにMUXマスクが依然として期待されます。

rcvlist_inv - list for mask/value filters (inverse semantic)
rcvlist_sff - list for single standard frame (SFF) entries

独自のCANプロトコルモジュールの作成¶

PF_CANプロトコルファミリーに新しいプロトコルを実装するには、include/linux/can.hで新しいプロトコルを定義する必要があります。SocketCANコアを使用するためのプロトタイプと定義はinclude/linux/can/core.hをインクルードすることで利用できます。CANプロトコルとCANデバイスノティフィケーションチェーンの登録関数に加えて、CANインターフェースで受信したCANフレームをサブスクライブする関数やCANフレームを送信する関数もあります:

can_rx_register   - subscribe CAN frames from a specific interface
can_rx_unregister - unsubscribe CAN frames from a specific interface
can_send          - transmit a CAN frame (optional with local loopback)

詳細はnet/can/af_can.cにあるkerneldocドキュメンテーションやnet/can/raw.cまたはnet/can/bcm.cのソースコードを参照してください。

CANネットワークドライバ¶

CANネットワークデバイスドライバの作成はCANキャラクタデバイスドライバよりもはるかに簡単です。他のネットワークデバイスドライバと同様に、主に以下の処理に取り組む必要があります:

  • TX: ソケットバッファからCANフレームをCANコントローラーに転送します。

  • RX: CANコントローラーからCANフレームをソケットバッファに転送します。

例えば、 ネットワークデバイス、カーネル、そしてあなた！ にあるように、CANネットワークデバイスドライバの作成における違いは以下の通りです:

一般的な設定¶

dev->type  = ARPHRD_CAN; /* the netdevice hardware type */
dev->flags = IFF_NOARP;  /* CAN has no arp */

dev->mtu = CAN_MTU; /* sizeof(struct can_frame) -> legacy CAN interface */

or alternative, when the controller supports CAN with flexible data rate:
dev->mtu = CANFD_MTU; /* sizeof(struct canfd_frame) -> CAN FD interface */

struct can_frame または struct canfd_frame は、プロトコルファミリーペフカーン（PF_CAN）における各ソケットバッファ（skbuff）のペイロードです。

送信フレームのローカルループバック¶

説明に従って 送信フレームのローカルループバック CANネットワークデバイスドライバーは、ttyデバイスのローカルエコー（例：ローカルループバック）に類似したローカルループバック機能をサポートする必要があります。この場合、ドライバーのフラグ IFF_ECHO を設定して、PF_CAN コアが送信フレームをローカルでエコー（ループバック）するのを防ぐ必要があります（代替手段として）：

dev->flags = (IFF_NOARP | IFF_ECHO);

CANコントローラーハードウェアフィルタ¶

深く埋め込まれたシステムの割り込み負荷を軽減するため、一部のCANコントローラーはCAN IDまたはCAN IDの範囲をフィルタリングする機能をサポートしています。これらのハードウェアフィルタ機能はコントローラーによって異なり、マルチユーザーネットワーキングアプローチでは実現不可能とされる場合があります。非常に専用なユースケースにおいては、コントローラー固有のハードウェアフィルタを使用する意義があります。ドライバレベルでのフィルタは、マルチユーザーシステム内のすべてのユーザーに影響を及ぼすため、ハードウェアフィルタは「深く埋め込まれたシステムの手作りチューニング」カテゴリに属します。著者は2002年にMPC603e @133MHzで4つのSJA1000 CANコントローラーを使用し、重いバス負荷下でも問題なく動作しています…

仮想CANドライバー（vcan）¶

ネットワークループバックデバイスと同様に、vcanは仮想ローカルCANインターフェースを提供します。CANの完全なアドレスは

  • 一意のCAN識別子（CAN ID）

  • そのCAN IDが送信されるCANバス（例：can0）

したがって、一般的なユースケースでは複数の仮想CANインターフェースが必要です。

仮想CANインターフェースは、実際のCANコントローラーハードウェアを使わずにCANフレームの送受信を可能にします。仮想CANネットワークデバイスは通常「vcanX」と名付けられ、例えばvcan0、vcan1、vcan2などです。モジュールとしてコンパイルされた場合、仮想CANドライバーモジュールはvcan.koと呼ばれます。

Linuxカーネルバージョン2.6.24以降、vcanドライバーはカーネルnetlinkインターフェースをサポートし、vcanネットワークデバイスの作成を可能にします。ip(8)ツールを使用してvcanネットワークデバイスの作成と削除を管理できます：

- Create a virtual CAN network interface:
     $ ip link add type vcan

- Create a virtual CAN network interface with a specific name 'vcan42':
     $ ip link add dev vcan42 type vcan

- Remove a (virtual CAN) network interface 'vcan42':
     $ ip link del vcan42

CANネットワークデバイスドライバーアプリケーションプログラミングインターフェース¶

CANネットワークデバイスドライバインターフェースは、CANネットワークデバイスの設定、構成、モニタリングを行うための汎用インターフェースを提供します。ユーザーは、「IPROUTE2」ユーティリティスイートから「ip」というプログラムを用いてnetlinkインターフェースを通じてCANデバイスを構成できます（ビットタイミングパラメータの設定など）。以下の章ではその使用方法を簡潔に説明します。さらに、このインターフェースは共通のデータ構造を使用し、すべての実際のCANネットワークデバイスドライバが使用すべき共通の関数セットをエクスポートします。SJA1000またはMSCANドライバを参照することで、これらの関数の使用方法を理解できます。モジュール名はcan-dev.koです。

上記の出力に関する詳細情報:

「<TRIPLE-SAMPLING>」

選択されたCANコントローラーモード（LOOPBACK、LISTEN-ONLY、またはTRIPLE-SAMPLING）の一覧を表示します。

「state ERROR-ACTIVE」

CANコントローラーの現在の状態：「ERROR-ACTIVE」、「ERROR-WARNING」、「ERROR-PASSIVE」、「BUS-OFF」または「STOPPED」

「restart-ms 100」

自動再起動遅延時間。値がゼロでない場合、バスオフ状態が発生した後、指定されたミリ秒の遅延時間経過後にCANコントローラーの自動再起動がトリガーされます。デフォルトでは無効です。

「bitrate 125000 sample-point 0.875」

「sja1000: tseg1 1..16 tseg2 1..8 sjw 1..4 brp 1..64 brp-inc 1 clock 8000000」

CANコントローラー（ここでは「sja1000」）のビットタイミング定数を表示します。時間セグメント1および2の最小値と最大値、同期ジャンプ幅（tq単位）、ビットレートプリスケーラー、CANシステムクロック周波数（Hz）を表示します。これらの定数は、ユーザー空間でのユーザー定義（非標準）ビットタイミング計算アルゴリズムに使用できます。

「re-started bus-errors arbit-lost error-warn error-pass bus-off」

再起動回数、バスエラーおよび仲裁ロストエラーの数、エラー警告、エラーパッシブ、バスオフ状態への状態変化を表示します。RXオーバーランエラーは標準ネットワーク統計の「overrun」フィールドにリストされます。

CANビットタイミングの設定¶

CANビットタイミングパラメータは、Bosch CAN 2.0仕様で提案されているハードウェア依存のない形式で常に定義できます。引数として「tq」、「prop_seg」、「phase_seg1」、「phase_seg2」、「sjw」を指定します。

$ ip link set canX type can tq 125 prop-seg 6 \
                            phase-seg1 7 phase-seg2 2 sjw 1

カーネルオプションCONFIG_CAN_CALC_BITTIMINGが有効な場合、ビットレートを引数「bitrate」で指定すると、CIAが推奨するCANビットタイミングパラメータが計算されます。

$ ip link set canX type can bitrate 125000

標準ビットレートを持つ一般的なCANコントローラーには問題ありませんが、 fail 特殊なビットレートやCANシステムクロック周波数には対応しません。CONFIG_CAN_CALC_BITTIMINGを無効にするとメモリ使用量を節約でき、ユーザー空間ツールがビットタイミングパラメータを完全に決定・設定できます。CANコントローラー固有のビットタイミング定数を使用できます。以下のコマンドでリストされます：

$ ip -details link show can0
...
  sja1000: clock 8000000 tseg1 1..16 tseg2 1..8 sjw 1..4 brp 1..64 brp-inc 1

CANネットワークデバイスの起動と停止¶

CANネットワークデバイスは「ifconfig canX up/down」または「ip link set canX up/down」というコマンドで通常のように起動または停止します。注意として、 grace periodsを尊重しなければなりませんし、 実際のCANデバイスを起動する前に、適切なビットタイミングパラメータを定義してください。デフォルト設定の誤った設定を避けてください：

$ ip link set canX up type can bitrate 125000

CANバスでエラーが多発するとデバイスが「bus-off」状態に入る可能性があります。その後、メッセージの受信・送信が停止します。自動バスオフ回復を有効にするには、「restart-ms」をゼロ以外の値に設定します。例えば：

$ ip link set canX type can restart-ms 100

代替として、アプリケーションはCANエラーメッセージフレームを監視して「bus-off」状態を検出し、適切なタイミングで以下のコマンドで再起動できます：

$ ip link set canX type can restart

再起動はCANエラーメッセージフレームを生成することにも注意してください（詳しくは ネットワーク問題通知).

CAN FD (Flexible Data Rate) ドライバサポート¶

CAN FD対応のCANコントローラーは、CAN FDフレームの仲裁段階とペイロード段階に異なるビットレートをサポートします。そのため、CAN FDビットレートを有効にするために第二のビットタイミングを指定する必要があります。

さらに、CAN FD対応のCANコントローラーは最大64バイトのペイロードをサポートしています。ユーザー空間アプリケーションやLinuxネットワーク層内でcan_frame.can_dlcおよびcanfd_frame.lenとして表現されるこの長さは、CANの「データ長コード」ではなく、0〜64の平文値として扱われます。データ長コードは本来のCANフレームのペイロード長に1対1で対応しておりました。ペイロード長とバス関連のDLC（データ長コード）のマッピングは、CANドライバ内で行われ、can_dlc2len()およびcan_len2dlc()などの補助関数を用いて行われます。

CANネットデバイスドライバの機能は、ネットワークデバイスの最大転送単位（MTU）によって区別されます：

MTU = 16 (CAN_MTU)   => sizeof(struct can_frame)   => 'legacy' CAN device
MTU = 72 (CANFD_MTU) => sizeof(struct canfd_frame) => CAN FD capable device

CANデバイスのMTUは、SIOCGIFMTU ioctl()システムコールなどにより取得できます。注意：CAN FD対応デバイスは、legacy CANフレームも処理および送信可能です。

CAN FD対応のCANコントローラーを設定する際には、追加の「データ」ビットレートを設定する必要があります。CAN FDフレームのデータフェーズのビットレートは、仲裁フェーズで設定されたビットレート以上にする必要があります。この2番目のビットレートは、1番目のビットレートと同様に指定されますが、「データ」ビットレートの設定キーワードは「d」で始まります（例：dbitrate、dsample-point、dsjw、dtqなど）。設定プロセス中にデータビットレートを設定した場合、コントローラーのオプション「fd on」を指定することで、CANコントローラーでCAN FDモードを有効化できます。このオプションは、デバイスMTUを72（CANFD_MTU）に切り替えます。

2012年の国際CANコンファレンスで提示された最初のCAN FD仕様は、データ整合性の観点から改善が必要でした。そのため、現在では2つのCAN FD実装を区別する必要があります：

  • ISO準拠：ISO 11898-1:2015 CAN FD実装（デフォルト）

  • ISO準拠外：2012年白書に基づくCAN FD実装

最後に、CAN FDコントローラーには3つのタイプがあります：

  1. ISO準拠（固定）

  2. ISO準拠外（固定、例：m_can.c内のM_CAN IPコアv3.0.1）

  3. ISO/ISO準拠外CAN FDコントローラー（切り替え可能、例：PEAK PCAN-USB FD）

現在のISO/ISO準拠外モードは、CANコントローラードライバがnetlink経由で通知し、'ip'ツールで表示されます（コントローラーオプションFD-NON-ISO）。切り替え可能なCAN FDコントローラーでは、'fd-non-iso {on|off}'を設定することでISO/ISO準拠外モードを変更できます。

500 kbit/sの仲裁ビットレートと4 Mbit/sのデータビットレートを設定する例：

$ ip link set can0 up type can bitrate 500000 sample-point 0.75 \
                               dbitrate 4000000 dsample-point 0.8 fd on
$ ip -details link show can0
5: can0: <NOARP,UP,LOWER_UP,ECHO> mtu 72 qdisc pfifo_fast state UNKNOWN \
         mode DEFAULT group default qlen 10
link/can  promiscuity 0
can <FD> state ERROR-ACTIVE (berr-counter tx 0 rx 0) restart-ms 0
      bitrate 500000 sample-point 0.750
      tq 50 prop-seg 14 phase-seg1 15 phase-seg2 10 sjw 1
      pcan_usb_pro_fd: tseg1 1..64 tseg2 1..16 sjw 1..16 brp 1..1024 \
      brp-inc 1
      dbitrate 4000000 dsample-point 0.800
      dtq 12 dprop-seg 7 dphase-seg1 8 dphase-seg2 4 dsjw 1
      pcan_usb_pro_fd: dtseg1 1..16 dtseg2 1..8 dsjw 1..4 dbrp 1..1024 \
      dbrp-inc 1
      clock 80000000

'fd-non-iso on'が追加された切り替え可能なCAN FDアダプターの例：

can <FD,FD-NON-ISO> state ERROR-ACTIVE (berr-counter tx 0 rx 0) restart-ms 0

RxRPC ネットワークプロトコル¶

RxRPCプロトコルドライバーは、UDP上での信頼性のある二段階のトランスポートを提供し、RxRPCリモート操作を実行するために使用できます。これはAF_RXRPCファミリーのソケットを使用し、sendmsg()とrecvmsg()を用いて制御データとともにデータ、中止、エラーを送受信します。

概要¶

RxRPCは二層プロトコルです。セッション層はUDPをIPv4（またはIPv6）としてトランスポート層として使用し、信頼性のある仮想接続を提供しますが、実際のネットワークプロトコルを実装します。また、プレゼンテーション層はXDRを用いて構造化データをバイナリーブロブに変換し、逆に変換します（SunRPCも同様です）：

+-------------+
| Application |
+-------------+
|     XDR     |         Presentation
+-------------+
|    RxRPC    |         Session
+-------------+
|     UDP     |         Transport
+-------------+

AF_RXRPCは提供します：

  1. カーネルとユーザースペースアプリケーションのためのRxRPC機能の一部を、セッション部分をLinuxネットワークプロトコル（AF_RXRPC）として実現することで提供します。

  2. 二段階プロトコルです。クライアントはブロブ（リクエスト）を送信し、その後ブロブ（レスポンス）を受信します。サーバーはリクエストを受信し、その後レスポンスを送信します。

  3. 1回の呼び出しで設定されたトランスポートシステムの再利用可能な要素を保持し、次の呼び出しを高速化します。

  4. セキュアなプロトコルで、クライアント側ではLinuxカーネルのキー保持機能を使用してセキュリティを管理します。サーバー側ではセキュリティ交渉においてより積極的である必要があります。

AF_RXRPCはXDRマーシャリング/プレゼンテーション機能を提供しません。これはアプリケーションの責任です。AF_RXRPCはブロブのみを扱います。操作IDもリクエストブロブの最初の4バイトであり、カーネルの関心の範囲外です。

AF_RXRPCファミリーのソケットは：

  1. SOCK_DGRAM型として作成されます；

  2. 下位トランスポートを使用するプロトコルタイプとして提供されます - 現在はPF_INETのみがサポートされています。

Andrew File System（AFS）は、このプロトコルを使用し、カーネル（ファイルシステム）とユーザースペース（ユーティリティ）の両方のコンポーネントを持つアプリケーションの例です。

RxRPCプロトコル概要¶

RxRPCプロトコルの概要：

  1. RxRPCは他のネットワーキングプロトコル（現在はUDPのみ）上に配置され、ネットワークトランスポートを提供します。UDPポートなどはトランスポートエンドポイントを提供します。

  2. RxRPCは、任意のトランスポートエンドポイントから複数の仮想「接続」をサポートし、エンドポイントを共有可能にします。同じリモートエンドポイントでも共有できます。

  3. 各接続は特定の「サービス」に接続されます。1つの接続は複数のサービスに接続することはできません。サービスはRxRPCにおけるポート番号に相当します。AF_RXRPCは複数のサービスがエンドポイントを共有できるようにします。

  4. クライアントが生成するパケットはマークされるため、トランスポートエンドポイントはクライアントとサーバーの接続間で共有できます（接続は方向性を持ちます）。

  5. 1つのローカルトランスポートエンドポイントと1つのリモートエンドポイント上の1つのサービス間で、最大10億の接続が同時にサポートされることがあります。RxRPC接続は7つの数字で記述されます。

Remote address  }
Remote port     }
Direction
Connection ID
Service ID

  6. 各RxRPC操作は「コール」と呼ばれます。接続は最大40億のコールを実行できますが、1つの接続において同時に進行中のコールは最大4つまでです。

  7. コールは2段階で行われ、非対称です。クライアントが要求データを送信し、サービスが受信します。その後、サービスが応答データを送信し、クライアントが受信します。

  8. データブロブのサイズは不定であり、各段階の終わりはパケット内のフラグで示されます。1つのブロブを構成するパケット数は40億を越えてはなりません。これはシーケンス番号が巻き戻す可能性があるためです。

  9. 要求データの最初の4バイトはサービス操作IDです。

  10. セキュリティは接続ごとに交渉されます。接続はその上に最初に到達したデータパケットで開始されます。セキュリティが要求された場合、サーバーは「チャレンジ」を発行し、クライアントが「レスポンス」で応じます。レスポンスが成功した場合、その接続の寿命にわたってセキュリティが設定され、その後のすべてのコールはそのセキュリティを使用します。サーバーがクライアントより接続を終了した場合、クライアントが再び接続を使用する際にはセキュリティが再交渉されます。

  11. コールはACKパケットを使用して信頼性を確保します。データパケットも各コールごとに明示的にシーケンス付けられます。

  12. ポジティブな確認にはハード・ACKとソフト・ACKの2種類があります。ハード・ACKは、遠隔側にすべてのデータが受信され処理されたことを示します。ソフト・ACKは、データが受信されたが、まだ破棄される可能性があることを示します。送信者は、ハード・ACKが届くまではどのパケットも破棄してはなりません。

  13. 応答データパケットの受信は、要求を構成するすべてのデータパケットをハード・ACKします。

  14. 要求が送信され、応答が受信され、応答の最後のパケットに対する最終的なハード・ACKがサーバーに届いたとき、コールは完了します。

  15. コールは、完了するまで任意のタイミングで両端から中止できます。

AF_RXRPCドライバモデル¶

AF_RXRPCドライバについて:

  1. AF_RXRPCプロトコルは、トランスポートプロトコルの内部ソケットを透明に使用して、トランスポートエンドポイントを表します。

  2. AF_RXRPCソケットはRxRPC接続バンドルにマッピングされます。実際のRxRPC接続は透明に処理されます。1つのクライアントソケットは、同じサービスへの複数の同時呼び出しを行うことができます。1つのサーバークソケットは、多くのクライアントからの呼び出しを処理できます。

  3. 追加の並列クライアント接続が起動され、追加の同時呼び出しをサポートします。これは調整可能な上限までです。

  4. 各接続は、最後の呼び出しの完了後、調整可能な時間の間保持されます。新しい呼び出しで再利用できる場合があります。

  5. 各内部UDPソケットは、最後の接続が破棄された後、調整可能な時間の間保持されます。新しい接続で再利用できる場合があります。

  6. クライアント側の接続は、セキュリティを記述する同じkey構造を持つ呼び合いで共有されます（他の条件が接続共有を許可する場合）。非セキュリティ保護の呼び出しも、接続を共有できます。

  7. サーバー側の接続は、クライアントがそう指定した場合に共有されます。

  8. ACKの処理はプロトコルドライバが自動で行い、Ping応答も含まれます。

  9. SO_KEEPALIVEは、接続を維持するために相手側にPingを自動で送ります[TODO]。

  10. ICMPエラーが受信された場合、そのエラーに影響されたすべての呼び出しは、recvmsg()を通じて適切なネットワークエラーで中止されます。

RxRPCソケットのユーザーとの相互作用:

  1. アドレスに非ゼロのサービスIDを割り当てることで、ソケットをサーバークソケットにします。

  2. クライアントでは、複数のsendmsgsの後にreplyをrecvmsgsで受信します。

  3. クライアントから送信されるリクエストの最初のsendmsgには、その呼び出しに関連するすべてのsendmsgsやrecvmsgsで使用するタグが含まれます。このタグは制御データに含まれます。

  4. connect()はクライアントソケットにデフォルトの宛先アドレスを提供します。これは、呼び出しの最初のsendmsg()で代替アドレスを指定することで上書きできます（struct msghdr::msg_name）。

  5. 未バインドのクライアントにconnect()が呼ばれた場合、操作前にランダムなローカルポートが割り当てられます。

  6. サーバークソケットはクライアント呼び出しを行うこともできます。これを行うには、呼び出しの最初のsendmsg()で宛先アドレスを指定する必要があります。サーバーのトランスポートエンドポイントを使用してパケットを送信します。

  7. アプリケーションがコールに関連する最後のメッセージを受信した後、タグは再び表示されず、クライアントリソースを固定するために使用できます。同じタグで新しいコールを開始しても干渉の心配がありません。

  8. サーバーでは、1つまたは複数のrecvmsgsでリクエストが受信され、その後1つまたは複数のsendmsgsで応答が送信され、最後にlast recvmsgで最終ACKが受信されます。

  9. コールのデータを送信する際、sendmsgにMSG_MOREが指定される場合があります。これはそのコールでさらにデータが届くことを示します。

  10. コールのデータを受信する際、recvmsgにMSG_MOREが設定され、そのコールでさらにデータが届くことを示します。

  11. コールのデータまたはメッセージを受信する際、recvmsgがMSG_EORフラグを設定し、そのコールの最後のメッセージを示します。

  12. コールは、制御データにアボート制御メッセージを追加することで中止できます。アボートを発行すると、カーネルがそのコールのタグを使用しなくなります。そのコールの受信キューに待機しているメッセージは破棄されます。

  13. アボート、ビジー通知、チャレンジパケットはrecvmsgで配信され、制御データメッセージはコンテキストを示すよう設定されます。アボートまたはビジーメッセージを受信すると、カーネルがそのコールのタグを使用しなくなります。

  14. msghdr構造体の制御データ部分は、複数の用途があります：

    1. 対応するコールのタグ。

    2. 送信または受信エラー、アボート、ビジー通知。

    3. 受信コールの通知。

    4. デバッグリクエストの送信とデバッグ応答の受信 [TODO]。

  15. カーネルが受信コールを受信し設定した後、サーバーアプリケーションに新しいコールが受け入れ待機中であることを通知するメッセージを送信します [recvmsgが特別な制御メッセージを報告します]。サーバーアプリケーションはsendmsgを使用して新しいコールにタグを割り当てます。割り当てが完了すると、リクエストデータの最初の部分がrecvmsgで配信されます。

  16. サーバーアプリケーションは、許可するセキュリティタイプに対応する秘密鍵のキーリングをサーバーソケットに提供する必要があります。セキュアな接続を設定する際、カーネルはキーリングから適切な秘密鍵を検索し、チャレンジパケットをクライアントに送信し、応答パケットを受信します。その後、カーネルがパケットの認証を確認し、接続を中止するかセキュリティを設定します。

  17. クライアントが通信をセキュリティで保護するために使用する鍵の名前は、ソケットオプションで指定されます。

sendmsgに関する注意点：

  1. MSG_WAITALLを設定することで、sendmsgがペアがパケットの受信を進んでいる場合にシグナルを無視して、合理的な時間内にすべてのデータを送信キューに並べることを可能にします。これにはクライアントが2*RTT時間ごとに少なくとも1つのパケットを受信する必要があります。

    この設定がされていない場合、sendmsg()は即座に返却します。何も消費されなかった場合はEINTR/ERESTARTSYSを返却し、消費されたデータ量を返却します。

recvmsgに関する注意点:

  1. 受信キューに特定のコールに属するデータメッセージの連続がある場合、recvmsgは以下の条件に達するまでそれらを処理し続けます:

    1. そのコールの受信データの終わりに達した場合、

    2. 非データメッセージに出会った場合、

    3. 他のコールに属するメッセージに出会った場合、または

    4. ユーザー・バッファが満たされた場合。

    recvmsgがブロッキングモードで呼ばれた場合、上記の4つの条件のいずれかが満たされるまで待機し続けることになります。

  1. MSG_PEEKは同様に動作しますが、バッファにデータを一度でも入れた時点で即座に返却します。バッファを満たすのを待つことはありません。

  2. ユーザー・バッファにデータメッセージを部分的に消費した場合、そのメッセージの残りは次の受取者がキューの先頭に残されます。MSG_TRUNCは常にフラグ付けされません。

  3. コールにまだデータが残っている場合（そのフェーズで最後のデータメッセージの最後のバイトをコピーしていない場合）、MSG_MOREがフラグ付けされます。

  1. RXRPC_USER_CALL_ID

    アプリケーションの呼び出しIDを示すために使用されます。これはアプリケーションがクライアントで最初のデータメッセージにこれを添付するか、サーバーでRXRPC_ACCEPTメッセージとともに渡すことで指定します。recvmsg()はRXRPC_NEW_CALLメッセージ以外のすべてのメッセージとともにこれを渡します。

  2. RXRPC_ABORT

    アプリケーションがsendmsgにこれを渡すことで呼び出しを中止できます。また、recvmsgがリモートからの中止を示すためにこれを届けることもできます。いずれの場合も、影響を受ける呼び出しを指定するためRXRPC_USER_CALL_IDと関連付ける必要があります。中止を送信する場合、そのユーザーIDに該当する呼び出しがなければエラーEBADSLTが返されます。

  3. RXRPC_ACK

    サーバーアプリケーションに、クライアントから呼び出しの最終ACKが到達したことを通知します。これは影響を受ける呼び出しを示すRXRPC_USER_CALL_IDと関連付けられます。

  4. RXRPC_NET_ERROR

    アプリケーションに、ペアーメッセージをやり取りする過程でICMPエラーメッセージが発生したことを通知します。制御メッセージデータには問題を示すerrnoクラスの整数値が含まれ、RXRPC_USER_CALL_IDは影響を受ける呼び出しを示します。

  5. RXRPC_BUSY

    クライアントアプリケーションに、サーバーがビジーなため呼び出しを拒否したことを通知します。これは影響を受ける呼び出しを示すRXRPC_USER_CALL_IDと関連付けられます。

  6. RXRPC_LOCAL_ERROR

    アプリケーションに、ローカルエラーが発生し、その結果呼び出しが中止されたことを通知します。制御メッセージデータには問題を示すerrnoクラスの整数値が含まれ、RXRPC_USER_CALL_IDは影響を受ける呼び出しを示します。

  7. RXRPC_NEW_CALL

    サーバーアプリケーションに、新しい呼び出しが到着し受け入れを待っていることを通知します。ユーザーIDはこの後RXRPC_ACCEPTを通じて割り当てられるため、関連付けられません。

  8. RXRPC_ACCEPT

    サーバーアプリケーションが呼び出しを受け入れようとする際に使用されます。RXRPC_USER_CALL_IDと関連付けられることで割り当てられるユーザーIDを示します。受け入れるべき呼び出しがない場合（タイムアウト、中止など）、sendmsgはエラーENODATAを返します。ユーザーIDが他の呼び出しで既に使用されている場合、エラーEBADSLTが返されます。

  9. RXRPC_EXCLUSIVE_CALL

    クライアント呼び出しを一時的な接続で行うことを示すために使用します。呼び出しが終了した後で接続は破棄されます。

  10. RXRPC_UPGRADE_SERVICE

    指定されたサービスIDがサーバーによってアップグレード可能かどうかを確認するためにクライアント呼び出しを行います。呼び出し元はrecvmsg()で返されるmsg_nameを確認し、実際に使用されているサービスIDを把握する必要があります。確認する操作は、両サービスで同じ引数を取る操作でなければなりません。

    このオプションがサーバーのアップグレード機能（またはその absence）を確立した後、返されたサービスIDをすべての今後の通信に使用し、RXRPC_UPGRADE_SERVICEはもはや設定されません。

  11. RXRPC_TX_LENGTH

    呼び出しによって送信されるデータの総量をカーネルに通知するために使用します（クライアントリクエストまたはサービス応答に関わらず）。指定された場合、カーネルがユーザー空間バッファからパケットバッファへ直接暗号化を行うことが可能になります。これにより、バッファへのコピーとその後の暗号化を省略できます。このオプションは、呼び出しデータを提供する最初のsendmsg()にのみ指定可能です。実際に指定されたデータ量が異なる場合、EMSGSIZEエラーが発生します。

    このパラメータは__s64型で、送信されるデータ量を示します。この値はゼロ以下であってはなりません。

RXRPC__SUPPORTEDは、サポートされているコントロールメッセージタイプの最大値に1を加えた値として定義されています。実行時にはRXRPC_SUPPORTED_CMSGソケットオプション（以下参照）で照会可能です。

ソケットオプション¶

AF_RXRPCソケットはSOL_RXRPCレベルで以下のソケットオプションをサポートしています：

  1. RXRPC_SECURITY_KEY

    使用する鍵の説明を指定するために使用します。鍵は呼び出しプロセスのkeyringsからrequest_key()で抽出され、"rxrpc"型の鍵である必要があります。

    optvalポインタは説明文字列を指し、optlenは文字列の長さを示します（NULL終端文字は含めません）。

  2. RXRPC_SECURITY_KEYRING

    上記と同様ですが、使用するサーバー秘密鍵のkeyringを指定します（鍵タイプは"keyring"）。セキュリティセクションを参照してください。

  3. RXRPC_EXCLUSIVE_CONNECTION

    このオプションは、このソケットで行われる今後のすべての呼び出しに新しい接続を使用するように要求します。optvalはNULL、optlenは0でなければなりません。

  4. RXRPC_MIN_SECURITY_LEVEL

    このオプションは、このソケットでの呼び出しに必要な最小セキュリティレベルを指定します。optvalは以下の値を持つintを指します：

    1. RXRPC_SECURITY_PLAIN

      暗号化されたチェックサムのみ。

    2. RXRPC_SECURITY_AUTH

      暗号化されたチェックサムに加えて、パケットがパディングされ、最初の8バイトが暗号化される。これは実際のパケット長を含むため、パケット長を含む情報が暗号化されます。

    3. RXRPC_SECURITY_ENCRYPT

      暗号化されたチェックサムに加えて、パケット全体をパディングして暗号化し、実際のパケット長も含めています。

  5. RXRPC_UPGRADEABLE_SERVICE

    クライアントが要求した場合、2つのバインディングを持つサービスソケットが1つのバインドされたサービスを別のサービスにアップグレードできるようにするためのオプションです。optvalは2つの無符号短整数の配列を指さなければなりません。最初の値はアップグレード元のサービスIDで、2番目の値はアップグレード先のサービスIDです。

  6. RXRPC_SUPPORTED_CMSG

    これは読み取り専用のオプションで、バッファにサポートされている最高のコントロールメッセージタイプを示す整数を書き込みます。

セキュリティ¶

現在、実装されているのはkerberos 4に相当するプロトコルのみです（セキュリティインデックス2 - rxkad）。これにはrxkadモジュールをロードし、クライアント側ではAFS kaserverまたはkerberosサーバーから適切なタイプのチケットを取得し、「rxrpc」タイプのキーとしてインストールする必要があります。これは通常klogプログラムを使用して行います。簡単なklogプログラムの例は以下のURLにあります：

http://people.redhat.com/~dhowells/rxrpc/klog.c

クライアントでadd_key()に提供されるペイロードは以下の形式にする必要があります：

struct rxrpc_key_sec2_v1 {
        uint16_t        security_index; /* 2 */
        uint16_t        ticket_length;  /* length of ticket[] */
        uint32_t        expiry;         /* time at which expires */
        uint8_t         kvno;           /* key version number */
        uint8_t         __pad[3];
        uint8_t         session_key[8]; /* DES session key */
        uint8_t         ticket[0];      /* the encrypted ticket */
};

チケットブロブは上記の構造に単純に追加されます。

サーバーでは、「rxrpc_s」タイプのキーをサーバーに利用可能にする必要があります。これらは「<serviceID>:<securityIndex>」（例：AFS VLサービス用のrxkadキーは「52:2」）という説明を持つことになります。このようなキーが作成される際には、サーバーのシークレットキーをインスタンス化データとして指定する必要があります（以下例を参照）。

add_key(“rxrpc_s”, “52:2”, secret_key, 8, keyring);

サーバー・ソケットにキー環を渡すには、ソックス・オプションで名前を指定します。サーバー・ソケットは、セキュアなインカム接続が行われる際、このキー環からサーバーのシークレットキーを検索します。これは以下の例プログラムで確認できます：

http://people.redhat.com/~dhowells/rxrpc/listen.c

例: クライアントの使用方法¶

クライアントは操作を以下のように実行します：

  1. RxRPCソケットは以下のように設定されます：

    client = socket(AF_RXRPC, SOCK_DGRAM, PF_INET);

    第三パラメータは使用されるトランスポート・ソケットのプロトコルファミリを示します - 通常はIPv4ですが、IPv6も可能です [TODO]。

  2. ローカルアドレスはオプションでバインドできます：

    struct sockaddr_rxrpc srx = {
        .srx_family     = AF_RXRPC,
        .srx_service    = 0,  /* we're a client */
        .transport_type = SOCK_DGRAM,   /* type of transport socket */
        .transport.sin_family   = AF_INET,
        .transport.sin_port     = htons(7000), /* AFS callback */
        .transport.sin_address  = 0,  /* all local interfaces */
};
bind(client, &srx, sizeof(srx));

    これは使用するローカルUDPポートを指定します。指定しない場合、ランダムな非特権ポートが使用されます。UDPポートは複数の関係のないRxRPCソケット間で共有可能です。セキュリティは各RxRPC仮想接続ごとに処理されます。

  3. セキュリティ設定は以下の通りです：

    const char *key = "AFS:cambridge.redhat.com";
setsockopt(client, SOL_RXRPC, RXRPC_SECURITY_KEY, key, strlen(key));

    セキュリティコンテキストを表すキーを取得するためrequest_key()を実行します。最小セキュリティレベルを設定できます：

    unsigned int sec = RXRPC_SECURITY_ENCRYPT;
setsockopt(client, SOL_RXRPC, RXRPC_MIN_SECURITY_LEVEL,
           &sec, sizeof(sec));

  4. 接続先のサーバーを指定できます（代替としてsendmsgを通じて指定することも可能です）：

    struct sockaddr_rxrpc srx = {
        .srx_family     = AF_RXRPC,
        .srx_service    = VL_SERVICE_ID,
        .transport_type = SOCK_DGRAM,   /* type of transport socket */
        .transport.sin_family   = AF_INET,
        .transport.sin_port     = htons(7005), /* AFS volume manager */
        .transport.sin_address  = ...,
};
connect(client, &srx, sizeof(srx));

  5. 要求データは、各々に以下のコントロールメッセージが添付されてsendmsg()呼び出しでサーバーのソケットに投稿される必要があります。

    RXRPC_USER_CALL_ID

    この呼び出しのユーザーIDを指定します

    要求の最後の部分以外のすべての部分でmsghdr::msg_flagsにMSG_MOREを設定する必要があります。複数の要求は同時に送信可能です。

    最初のsendmsg()呼び出しでRXRPC_TX_LENGTHというコントロールメッセージを指定することもできます。

    デフォルトで接続された宛先以外の宛先に呼び出しが送信される場合は、その呼び出しの最初のメッセージでmsghdr::msg_nameを設定する必要があります。

  6. 応答データは、recvmsg()が取得できるようにサーバーのソケットに投稿されます。特定の呼び出しにまだ応答データが残っている場合、recvmsg()はMSG_MOREフラグを設定します。呼び出しの終了読み取りにはMSG_EORフラグが設定されます。

    すべてのデータは以下のコントロールメッセージが添付されて送信されます：

    RXRPC_USER_CALL_ID - この呼び出しのユーザーIDを指定します

    中止やエラーが発生した場合、この情報はコントロールデータバッファに返され、MSG_EORフラグが設定されて呼び出しの終了を示します。

クライアントは、RXRPC_UPGRADE_SERVICEを最初のsendmsg()呼び出しで指定することで、既知のサービスIDをアップグレード要求できます（利用可能な場合）。その後、recvmsg()が埋め込むmsg_nameでsrx_serviceを確認する必要があります。アップグレード要求が無視された場合、srx_serviceはsendmsg()に渡された値と同じになります。それ以外の場合は、サーバーがアップグレードしたサービスIDを示す値になります。注意点として、アップグレードされたサービスIDはサーバーが選択します。呼び出し元は、応答でサービスIDを確認するまで、さらなる呼び出しを送信してはなりません（同じ宛先への呼び出しはプローブが完了するまでブロックされます）。

例サーバーの使用方法¶

サーバーは次の手順で操作を受け付けるように設定されます：

  1. RxRPCソケットは以下の通り作成されます：

    server = socket(AF_RXRPC, SOCK_DGRAM, PF_INET);

    第三パラメータは使用するトランスポートソケットのアドレスタイプを示します（通常はIPv4）。

  2. セキュリティ設定は、ソケットにサーバー秘密鍵を含むキーリングを指定することで望ましい場合に行われます：

    keyring = add_key("keyring", "AFSkeys", NULL, 0,
                  KEY_SPEC_PROCESS_KEYRING);

const char secret_key[8] = {
        0xa7, 0x83, 0x8a, 0xcb, 0xc7, 0x83, 0xec, 0x94 };
add_key("rxrpc_s", "52:2", secret_key, 8, keyring);

setsockopt(server, SOL_RXRPC, RXRPC_SECURITY_KEYRING, "AFSkeys", 7);

    キーリングはソケットに渡した後でも操作可能です。これにより、サーバーはライブ状態でキーを追加したり、置き換えたりできます。

  3. ローカルアドレスは次にバインドする必要があります：

    struct sockaddr_rxrpc srx = {
        .srx_family     = AF_RXRPC,
        .srx_service    = VL_SERVICE_ID, /* RxRPC service ID */
        .transport_type = SOCK_DGRAM,   /* type of transport socket */
        .transport.sin_family   = AF_INET,
        .transport.sin_port     = htons(7000), /* AFS callback */
        .transport.sin_address  = 0,  /* all local interfaces */
};
bind(server, &srx, sizeof(srx));

    トランスポートパラメータが同じ場合、ソケットに複数のサービスIDをバインドできます（現在の制限は2つ）。これを実行するにはbind()を2回呼び出す必要があります。

  4. サービスのアップグレードが必要な場合、最初の2つのサービスIDがバインドされていなければなりません。その後、以下のオプションを設定する必要があります:

    unsigned short service_ids[2] = { from_ID, to_ID };
setsockopt(server, SOL_RXRPC, RXRPC_UPGRADEABLE_SERVICE,
           service_ids, sizeof(service_ids));

    これは、サービスfrom_IDからサービスto_IDへの接続を自動的にアップグレードします。ユーザー空間にリクエストデータが届いたときに、recvmsg()を通じて取得するmsg_nameに反映されます。

  5. サーバーは次に、受信する呼び出しを待機するように設定されます:

    listen(server, 100);

  6. カーネルは、受信する接続があることを通知するために、サーバーにメッセージを送信します。これはサーバーのソケットでrecvmsg()で受信され、データはなく、単一のデータのない制御メッセージが添付されています:

    RXRPC_NEW_CALL

    この時点でrecvmsg()で返されるアドレスは無視すべきです。受信メッセージがポストされた呼び出しは、受信される前に処理される可能性があるため、キューに残っている最初の呼び出しが受信されます。

  7. サーバーは、2つの制御データと実際のデータを含まないsendmsg()を発行して新しい呼び出しを承認します:

    RXRPC_ACCEPT

    接続の承認を示す

    RXRPC_USER_CALL_ID

    この呼び出しのユーザーIDを指定する

  8. 最初のリクエストデータパケットは、サーバーのソケットにポストされ、recvmsg()によって取得されます。この時点で、msghdr構造体のアドレスフィールドから呼び出しのRxRPCアドレスを読み取ることができます。

    その後のリクエストデータは、到着するたびにサーバーのソケットにポストされ、recvmsg()によって収集されます。リクエストデータのすべてのピースは、最後のピースを除いてMSG_MOREフラグが設定されます。

    すべてのデータは以下のコントロールメッセージが添付されて送信されます：

    RXRPC_USER_CALL_ID

    この呼び出しのユーザーIDを指定します

  9. 応答データは、以下の制御メッセージを添付したsendmsg()呼び出しの連続でサーバーのソケットにポストする必要があります:

    RXRPC_USER_CALL_ID

    この呼び出しのユーザーIDを指定します

    特定の呼び出しの最後のメッセージを除き、すべてのmsghdr::msg_flagsにMSG_MOREを設定する必要があります。

  1. クライアントからの最終ACKは、受信時にrecvmsg()で取得できるようにポストされます。これは、データのないメッセージで、2つの制御メッセージが添付された形になります:

    RXRPC_USER_CALL_ID

    この呼び出しのユーザーIDを指定します

    RXRPC_ACK

    最終ACKを示す（データなし）

    この呼び出しの最後のメッセージであることを示すためにMSG_EORフラグが設定されます。

  2. 応答データの最後のパケットが送信されるまで、sendmsg()を呼び出してデータのないメッセージを送信することで、呼び出しを中止できます。このメッセージには以下の制御メッセージが添付されます:

    RXRPC_USER_CALL_ID

    この呼び出しのユーザーIDを指定します

    RXRPC_ABORT

    中止コードを示す（4バイトのデータ）

    この操作を実行すると、ソケットの受信キューに待機しているパケットはすべて破棄されます。

特定のサービスのすべての通信は、1つのサーバー・ソケットを通じて行われ、sendmsg()とrecvmsg()の制御メッセージによって影響を受ける呼び出しを特定します。

AF_RXRPCカーネルインターフェース¶

AF_RXRPCモジュールは、AFSファイルシステムなどの内核ユーティリティでも使用可能なインターフェースも提供しています。これにより、このようなユーティリティは次の操作が可能になります:

  1. 1つのソケット上で個々のクライアント呼び出しに直接異なるキーを使用するのではなく、使用したいキーごとに多数のソケットを開く必要はありません。

  2. RxRPCが呼び出しの発行またはソケットのオープン時にrequest_key()を呼び出すのを避けることができます。代わりに、ユーティリティが適切なタイミングでキーを要求する責任があります。たとえばAFSは、open()やunlink()などのVFS操作中にこれを実行します。このとき、呼び出し開始時にキーが渡されます。

  3. GFP_KERNEL以外のメモリ割当方法を使用することを要求できます。

  4. recvmsg()呼び出しのオーバーヘッドを回避できます。RxRPCメッセージはソケットRxキューに投入される前にインターセプトされ、ソケットバッファを直接操作することが可能です。

RxRPC機能を使用するには、内核ユーティリティが依然としてAF_RXRPCソケットを開き、適切なアドレスをバインドし、サーバーのソケットである場合はリスンする必要があります。その後、このソケットを内核インターフェース関数に渡します。

内核インターフェース関数は以下の通りです:

  1. 新しいクライアント呼び出しを開始:

    struct rxrpc_call *
rxrpc_kernel_begin_call(struct socket *sock,
                        struct sockaddr_rxrpc *srx,
                        struct key *key,
                        unsigned long user_call_ID,
                        s64 tx_total_len,
                        gfp_t gfp,
                        rxrpc_notify_rx_t notify_rx,
                        bool upgrade,
                        bool intr,
                        unsigned int debug_id);

    新しいRxRPC呼び出しを行うインフラストラクチャを割り当て、呼び出しと接続の番号を割り当てます。呼び出しはソケットがバインドされているUDPポートで行われ、接続済みクライアントソケットの宛先アドレスに送信されます（代替アドレスが指定されていない限り）。

    キーが指定されている場合、このキーが呼び出しをセキュリティ保護するために使用されます。ソケットにRXRPC_SECURITY_KEYソケットオプションでバインドされたキーではなく、このキーが使用されます。このようにセキュリティ保護された呼び出しは、可能な限り接続を共有します。

    user_call_IDはsendmsg()に渡される制御データバッファ内の値と同等です。これは内核データ構造を指すために使用することも完全に可能です。

    tx_total_lenは、この呼び出しで送信したいデータ量（この時点で未知の場合には-1）です。データサイズを設定することで、内核がパケットバッファに直接暗号化できるようになり、コピーを省略できます。値は-1以下であってはなりません。

    notify_rxは、受信データパケットやリモート中止などのイベントが発生したときに呼び出される関数へのポインタです。

    クライアント操作がサーバーにサービスのアップグレードを要求する場合は、upgradeをtrueに設定します。結果として得られるサービスIDはrxrpc_kernel_recv_data()によって返されます。

    呼出が中断可能である場合はintrをtrueに設定する必要があります。このフラグが設定されていない場合、この関数はチャネルが割り当てられるまで戻らない可能性があります。設定されている場合は、-ERESTARTSYSを返す可能性があります。

    debug_idはトレース用の呼び出しデバッグIDです。これはrxrpc_debug_idを原子的にインクリメントすることで取得できます。

    この関数が成功した場合、RxRPC呼出に対するオパキートな参照が返されます。呼び出し元はこの参照を保持しており、適切に終了させる必要があります。

  2. クライアント呼出を終了する:

    void rxrpc_kernel_end_call(struct socket *sock,
                           struct rxrpc_call *call);

    以前に開始された呼出を終了するために使用します。user_call_IDはAF_RXRPCの知識から削除され、指定された呼出と関連付けられることはありません。

  3. 呼出を通じてデータを送信する:

    typedef void (*rxrpc_notify_end_tx_t)(struct sock *sk,
                                      unsigned long user_call_ID,
                                      struct sk_buff *skb);

int rxrpc_kernel_send_data(struct socket *sock,
                           struct rxrpc_call *call,
                           struct msghdr *msg,
                           size_t len,
                           rxrpc_notify_end_tx_t notify_end_rx);

    これはクライアント呼出のリクエスト部分またはサーバー呼出の応答部分を提供するために使用されます。msg.msg_iovlenとmsg.msg_iovは使用するデータバッファを指定します。msg_iovはNULLであってはならず、内核の仮想アドレスにのみポインタを指さなければなりません。msg.msg_flagsにはMSG_MOREを指定する場合があります。これにより、この呼出に関する次のデータ送信が行われる可能性があります。

    msgは宛先アドレス、制御データ、またはMSG_MORE以外のフラグを指定してはなりません。lenは送信するデータの総量です。

    notify_end_rxはNULLであったり、呼出がTxフェーズを終了する状態に変化したときに呼び出す関数を指定するためのものです。この関数は呼出状態スピンロックを保持しながら呼び出されるため、応答や最終ACKが先に届くのを防ぎます。

  4. 呼出からデータを受信する:

      int rxrpc_kernel_recv_data(struct socket *sock,
                             struct rxrpc_call *call,
                             void *buf,
                             size_t size,
                             size_t *_offset,
                             bool want_more,
                             u32 *_abort,
                             u16 *_service)

This is used to receive data from either the reply part of a client call
or the request part of a service call.  buf and size specify how much
data is desired and where to store it.  *_offset is added on to buf and
subtracted from size internally; the amount copied into the buffer is
added to *_offset before returning.

want_more should be true if further data will be required after this is
satisfied and false if this is the last item of the receive phase.

There are three normal returns: 0 if the buffer was filled and want_more
was true; 1 if the buffer was filled, the last DATA packet has been
emptied and want_more was false; and -EAGAIN if the function needs to be
called again.

If the last DATA packet is processed but the buffer contains less than
the amount requested, EBADMSG is returned.  If want_more wasn't set, but
more data was available, EMSGSIZE is returned.

If a remote ABORT is detected, the abort code received will be stored in
``*_abort`` and ECONNABORTED will be returned.

The service ID that the call ended up with is returned into *_service.
This can be used to see if a call got a service upgrade.

  5. 呼出を中止する??

    void rxrpc_kernel_abort_call(struct socket *sock,
                             struct rxrpc_call *call,
                             u32 abort_code);

    呼出が中止可能状態にある場合、この関数を使用して呼出を中止できます。指定された中止コードはABORTメッセージに含まれます。

  6. 受信したRxRPCメッセージをインターセプトする:

    typedef void (*rxrpc_interceptor_t)(struct sock *sk,
                                    unsigned long user_call_ID,
                                    struct sk_buff *skb);

void
rxrpc_kernel_intercept_rx_messages(struct socket *sock,
                                   rxrpc_interceptor_t interceptor);

    この関数は指定されたAF_RXRPCソケットにインターセプター関数をインストールします。それ以降、ソケットのRxキューにたどり着くはずだったすべてのメッセージはこの関数にリダイレクトされます。注意点として、メッセージを正しい順序で処理し、DATAメッセージの順序性を維持する必要があります。

    インターセプター関数には、ソケットのアドレスと受信メッセージの処理、カーネルユーティリティによって割り当てられた呼出ID、およびメッセージを含むソケットバッファが提供されます。

    skb->markフィールドはメッセージのタイプを示します:

    マークする

    意味

    RXRPC_SKB_MARK_DATA

    データメッセージ

    RXRPC_SKB_MARK_FINAL_ACK

    インカム呼出のための最終ACKが受信されました

    RXRPC_SKB_MARK_BUSY

    サーバーがビジーなためクライアント呼出が拒否されました

    RXRPC_SKB_MARK_REMOTE_ABORT

    ピアによって呼出が中止されました

    RXRPC_SKB_MARK_NET_ERROR

    ネットワークエラーが検出されました

    RXRPC_SKB_MARK_LOCAL_ERROR

    ローカルエラーが発生しました

    RXRPC_SKB_MARK_NEW_CALL

    受け入れ待ちの新しいインカム呼出

    リモート中止メッセージはrxrpc_kernel_get_abort_code()で取得できます。2つのエラーメッセージはrxrpc_kernel_get_error_number()で取得できます。新しいコールはrxrpc_kernel_accept_call()で受け入れられます。

    データメッセージの内容は通常のソケットバッファ操作関数で抽出できます。データメッセージがシーケンスの最後のメッセージであるかどうかはrxrpc_kernel_is_data_last()で判定できます。データメッセージが使用されると、rxrpc_kernel_data_consumed()を呼び出す必要があります。

    メッセージはrxrpc_kernel_free_skb()で処理して破棄してください。すべてのメッセージタイプに追加の参照を取得して後で解放することが可能です。ただし、これはコールの状態を保持する可能性があり、メッセージが最終的に解放されるまでコールの状態を固定する場合があります。

  7. 受信コールを受け入れる:

    struct rxrpc_call *
rxrpc_kernel_accept_call(struct socket *sock,
                         unsigned long user_call_ID);

    これは受信コールを受け入れてコールIDを割り当てるための関数です。この関数はrxrpc_kernel_begin_call()に似ており、受け入れたコールは同じ方法で終了する必要があります。

    この関数が成功した場合、RxRPC呼出に対するオパキートな参照が返されます。呼び出し元はこの参照を保持しており、適切に終了させる必要があります。

  8. 受信コールを拒否する:

    int rxrpc_kernel_reject_call(struct socket *sock);

    これはソケットのキューにある最初の受信コールをBUSYメッセージで拒否します。受信コールがなかった場合は-ENODATAが返されます。コールが中止されていた場合は-ECONNABORTED、タイムアウトしていた場合は-ETIMEが返される可能性があります。

  9. 匿名セキュリティを行うためのnullキーを割り当てる:

    struct key *rxrpc_get_null_key(const char *keyname);

    これは特定のドメインで匿名セキュリティを示すために使用できるnull RxRPCキーを割り当てるための関数です。

  10. コールのピアアドレスを取得する:

    void rxrpc_kernel_get_peer(struct socket *sock, struct rxrpc_call *call,
                           struct sockaddr_rxrpc *_srx);

    これはコールのリモートピアアドレスを取得するための関数です。

  11. コールのトータル送信データサイズを設定する:

    void rxrpc_kernel_set_tx_length(struct socket *sock,
                                struct rxrpc_call *call,
                                s64 tx_total_len);

    これはコールで送信するデータ量を設定します。これはコール開始時にリクエストサイズを設定する際の返信サイズとして使用する予定です。tx_total_lenは0未満であってはなりません。

  12. コールのRTTを取得する:

    u64 rxrpc_kernel_get_rtt(struct socket *sock, struct rxrpc_call *call);

    コールが使用するピアへのRTT時間を取得します。返される値はナノ秒単位です。

  13. コールがまだ生きているかを確認する:

    bool rxrpc_kernel_check_life(struct socket *sock,
                             struct rxrpc_call *call,
                             u32 *_life);
void rxrpc_kernel_probe_life(struct socket *sock,
                             struct rxrpc_call *call);

    最初の関数は *_life ピアからACKが受信されるたびに更新される数値を返します（特にPING RESPONSE ACKを含む）。呼び出し元は適切なインターバルを待ってから、2つのコールの数値を比較してコールが生きているかどうかを確認します。コールが完了状態に達するまでは常にtrueを返します。

    これにより、呼び出し元はサーバーがまだアクセス可能で、コールがサーバー上でまだ生きているかどうかを確認できます。サーバーがクライアント操作を処理している間、待機中に確認できます。

    2番目の関数は、ピングACKを送信してペアに応答させる試みを行い、その結果、1番目の関数が返す値が変化するようにします。注意点として、この関数はTASK_RUNNING状態で呼び出す必要があります。

  14. 返信のタイムスタンプを取得:

    bool rxrpc_kernel_get_reply_time(struct socket *sock,
                                 struct rxrpc_call *call,
                                 ktime_t *_ts)

    クライアントからの応答の最初のDATAパケットのタイムスタンプを取得できます。ただし、このタイムスタンプがRxリングにまだ存在している必要があります。成功した場合、タイムスタンプが *_ts に保存され、trueが返されます。失敗した場合はfalseが返されます。

  15. リモートクライアントのエポックを取得:

    u32 rxrpc_kernel_get_epoch(struct socket *sock,
                           struct rxrpc_call *call)

    インカムクライアントコールのパケットに含まれるエポックを取得できます。この値が返されます。コールがまだ進行中である限り、この関数は常に成功します。コールが期限切れになった後は呼び出すべきではありません。注意点として、ローカルクライアントコールに対してこの関数を呼び出すと、ローカルのエポックのみが返されます。

    この値は、リモートクライアントが再起動されたかどうかを判定するために使用できます。通常は変化しません。

  16. コールの最大寿命を設定:

    void rxrpc_kernel_set_max_life(struct socket *sock,
                               struct rxrpc_call *call,
                               unsigned long hard_timeout)

    コールの最大寿命をhard_timeout（ジーフィーズ単位）に設定します。タイムアウトが発生した場合、コールは中止され、-ETIMEまたは-ETIMEDOUTが返されます。

  17. カーネル内でソケットにRXRPC_MIN_SECURITY_LEVEL sockoptを適用:

    int rxrpc_sock_set_min_security_level(struct sock *sk,
                                      unsigned int val);

    このソケットで行われるコールに必要な最小セキュリティレベルを指定します。

設定可能なパラメータ¶

RxRPCプロトコルドライバーには、/proc/net/rxrpc/内のsysctlを通じて調整可能な複数の設定パラメータがあります:

  1. req_ack_delay

    リクエストACKフラグが設定されたパケットを受信した後、実際にACKを送信するまでに待つミリ秒数です。

    通常、相手側は受信ウィンドウが満たされるまで（最大255パケット）パケットを送信し続けます。ACKを遅らせることが、複数のパケットを一度にACKするのを可能にします。

  2. soft_ack_delay

    新しいパケットを受信した後、送信者に再送不要であることを通知するソフトACKを生成するまでのミリ秒数です。

  3. idle_ack_delay

    受信キュー内のすべてのパケットが消費された後、ACKを送信して送信者がバッファを解放できるように通知するハードACKを生成するまでのミリ秒数です。ただし、ACKを送信する他の理由がなければこの処理は行われません。

  4. resend_timeout

    パケットを送信した後、ACKが受信されない場合にパケットを再送するまでのミリ秒数です。

  5. max_call_lifetime

    コールが進行中の最大時間（秒単位）で、この時間経過後にコールが予防的に終了します。

  6. dead_call_expiry

    呼リストから死んだ呼を削除するまでの時間（秒単位）。死んだ呼は、ACKおよびABORTパケットの再送を目的として一時的に保持されます。

  7. connection_expiry

    接続リストから接続を削除するまでの時間（秒単位）。接続が存在する間は、交渉されたセキュリティのプレースホルダーとして機能し、削除時にセキュリティ再交渉が必要になります。

  8. transport_expiry

    トランスポートリストからトランスポートを削除するまでの時間（秒単位）。トランスポートが存在する間は、ペアデータを固定し、接続IDカウンターを保持します。

  9. rxrpc_rx_window_size

    受信ウィンドウのサイズ（パケット単位）。これは、特定の呼に対して保持する未処理の受信パケットの最大数を示します。

  10. rxrpc_rx_mtu

    受け入れる最大パケットMTUサイズ（バイト単位）。これは、ジャンボパケットを受け入れる意欲をペアに示します。

  11. rxrpc_rx_jumbo_max

    受け入れるジャンボパケット内の最大パケット数。ジャンボパケット内の非終端パケットは4バイトのヘッダーに加えて正確に1412バイトのデータを含む必要があります。終端パケットは4バイトのヘッダーに加えて任意のデータを含むことができます。いずれにしても、ジャンボパケットのサイズはrxrpc_rx_mtuを超えてはなりません。

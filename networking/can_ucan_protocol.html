UCANプロトコル¶

UCANは、Theobroma Systemsが提供するSystem-on-Modulesに統合されているマイクロコントローラーベースのUSB-CANアダプターで使用されるプロトコルであり、スタンドアロンのUSBスティックとしても利用可能です。

UCANプロトコルはハードウェアに依存しないように設計されています。Linuxが内部でCANデバイスをどのように表現しているかに準拠しており、すべてのマルチバイト整数はリトルエンディアンでエンコードされます。

このドキュメントで説明されているすべての構造体は drivers/net/can/usb/ucan.c.

USBエンドポイント¶

UCANデバイスは3つのUSBエンドポイントを使用します：

コントロールエンドポイント

ドライバーがデバイス管理コマンドを送信するエンドポイント

インエンドポイント

デバイスがCANデータフレームとCANエラーフレームを送信するエンドポイント

アウトエンドポイント

ドライバーがアウトエンドポイントを通じてCANデータフレームを送信します

コントロールメッセージ¶

UCANデバイスはコントロールパイプ上のベンダーリクエストによって設定されます。

単一のUSBデバイス内で複数のCANインターフェースをサポートするため、すべての設定コマンドはUSBディスクリプター内の対応するインターフェースをターゲットとします。

ドライバーは ucan_ctrl_command_in/out および ucan_device_request_in デバイスにコマンドを届けるために使用します。

INメッセージ形式¶

USB INエンドポイント上のデータパケットには1つまたは複数の ucan_message_in 値が含まれます。複数のメッセージがUSBデータパケットにバッチ処理される場合、 len フィールドを使用して次の ucan_message_in 値（実際のデータサイズと比較して sanity-check を行うことを忘れないでください）。 len 値を実際にデータサイズと照合してください。

len フィールド¶

Each ucan_message_in 4バイト境界に合わせて配置する必要があります（データバッファの開始位置に対して）。つまり、複数の ucan_message_in values:

+----------------------------+ < 0
|                            |
|   struct ucan_message_in   |
|                            |
+----------------------------+ < len
          [padding]
+----------------------------+ < round_up(len, 4)
|                            |
|   struct ucan_message_in   |
|                            |
+----------------------------+
            [...]

type フィールド¶

以下の type フィールドはメッセージのタイプを指定します。

UCAN_IN_RX¶

subtype

ゼロ

CANバスから受信したデータ（ID + ペイロード）

UCAN_IN_TX_COMPLETE¶

subtype

ゼロ

CANデバイスがCANバスにメッセージを送信しました。リストのタプル<エコーディ、フラグ>で応答します。

エコーディはフレームを識別します（以前のUCAN_OUT_TXメッセージからのIDをエコーします）。フラグは送信結果を示します。ビット0が設定されている場合、成功を示します。他のビットは予約されており、ゼロに設定されます。

フロー制御¶

CANメッセージを受信する際、USBバッファにはフロー制御がありません。ドライバーはインバウンドメッセージを速やかに処理しなければならないため、ドロップを防がなければなりません。デバイスバッファがオーバーフローした場合、対応するエラーフレームを送信して状態を報告します（参照 CANエラー処理)

アウトメッセージフォーマット¶

USB OUTエンドポイント上のデータパケットには1つまたは複数の struct ucan_message_out 値が含まれます。複数のメッセージが1つのデータパケットにバッチ処理される場合、デバイスは len フィールドを使用して次のucan_message_out値にジャンプします。各ucan_message_outはデータバッファの開始位置から4バイトにアライメントする必要があります。このメカニズムは lenフィールド.

+----------------------------+ < 0
|                            |
|   struct ucan_message_out  |
|                            |
+----------------------------+ < len
          [padding]
+----------------------------+ < round_up(len, 4)
|                            |
|   struct ucan_message_out  |
|                            |
+----------------------------+
            [...]

type フィールド¶

プロトコルバージョン3においてのみ UCAN_OUT_TX が定義され、他のものはレガシー機器（プロトコルバージョン1）のみで使用されます。

UCAN_OUT_TX¶

subtype

CAN_IN_TX_COMPLETEメッセージ内で応答するエコーアイド

CANフレームを送信します。（パラメータ： id, data)

フロー制御¶

デバイスのアウトバウンドバッファが満杯になると、 NAKを送信し始めます。 on the OUT パイプを続けるまで、より多くのバッファが利用可能になるのを待つ必要があります。ドライバーは、一定数のアウトパケットが未完了である場合にキューを停止します。

CANエラー処理¶

エラー報告が有効になっている場合、デバイスはCANエラーフレームにエラーをエンコードして（参照 uapi/linux/can/error.h)、INエンドポイントを使用して送信します。ドライバーはエラー統計を更新し、それを転送します。

UCANデバイスはエラーフレームを完全に抑制できますが、Linuxではドライバーは常にエラーフレームに興味を持ちます。そのため、デバイスは常に UCAN_MODE_BERR_REPORT が設定された状態で起動されます。ユーザー空間でのメッセージフィルタリングはドライバーによって行われます。

バスオフ¶

  • デバイスはバスオフ状態から自動的に回復しません。

  • バスオフ状態はエラーフレームによって示されます（参照 uapi/linux/can/error.h)

  • バスオフ回復は UCAN_COMMAND_RESTART

  • バスオフ回復が完了した後、デバイスはエラーフレームを送信してERROR-ACTIVE状態にあることを示します。

  • バスオフ状態中、デバイスはフレームを送信しません。

  • バスオフ状態中、ホストからの送信要求は即座に完了され、成功ビットは未設定のままです。

例: 会話¶

  1. デバイスがUSBに接続されました

  2. ホストがコマンドを送信しました UCAN_COMMAND_RESET、サブコマンド 0

  3. ホストがコマンドを送信しました UCAN_COMMAND_GET、サブコマンド UCAN_COMMAND_GET_INFO

  4. デバイスが送信しました UCAN_IN_DEVICE_INFO

  5. ホストがコマンドを送信しました UCAN_OUT_SET_BITTIMING

  6. ホストがコマンドを送信しました UCAN_COMMAND_START、サブコマンド 0、モード UCAN_MODE_BERR_REPORT

セグメンテーションオフロード¶

はじめに¶

このドキュメントは、Linux ネットワークスタックにおけるセグメンテーションオフロードの機能を活用するための技術について説明しています。

以下の技術が説明されています：

  • TCP セグメンテーションオフロード - TSO

  • UDP フラグメンテーションオフロード - UFO

  • IPIP、SIT、GRE、および UDP テンネルオフロード

  • ジェネリックセグメンテーションオフロード - GSO

  • ジェネリックリーブートオフロード - GRO

  • 部分的なジェネリックセグメンテーションオフロード - GSO_PARTIAL

  • GSO による SCTP 加速 - GSO_BY_FRAGS

TCPセグメンテーションオフロード¶

TCP セグメンテーションにより、デバイスが単一フレームを複数のフレームに分割し、skb_shinfo()->gso_size に指定されたデータペイロードサイズで送信できます。TCP セグメンテーションが要求される場合、skb_shinfo()->gso_type に SKB_GSO_TCPV4 または SKB_GSO_TCPV6 のいずれかのビットを設定し、skb_shinfo()->gso_size をゼロ以外の値に設定する必要があります。

TCP セグメンテーションは、部分的なチェックサムオフロードのサポートに依存しています。そのため、送信チェックサムオフロードが無効になっているデバイスでは通常 TSO は無効になります。

TCP セグメンテーションオフロードをサポートするには、skbuff のネットワークヘッダとトランスポートヘッダのオフセットを設定する必要があります。これにより、デバイスドライバーが IP または IPv6 ヘッダと TCP ヘッダのオフセットを特定できるようになります。また、CHECKSUM_PARTIAL が必要なため、csum_start はパケットの TCP ヘッダを指す必要があります。

IPv4 セグメンテーションでは、IP ID の処理方法として2つのタイプをサポートしています。デフォルトでは、セグメントごとに IP ID をインクリメントします。GSO タイプ SKB_GSO_TCP_FIXEDID を指定した場合、IP ID はインクリメントされず、すべてのセグメントで同じ IP ID を使用します。デバイスが NETIF_F_TSO_MANGLEID を設定している場合、TSO で IP ID を無視し、すべてのフレームで IP ID をインクリメントするか、ドライバの好みに基づいて静的な値を保持します。

UDPフラグメンテーションオフロード¶

UDP フラグメンテーションオフロードにより、デバイスが oversized UDP データグラムを複数の IPv4 フラグメントに分割できます。UDP フラグメンテーションオフロードの多くの要件は TSO と同様ですが、単一の IPv4 データグラムがフラグメント化される際には IPv4 ID はインクリメントされません。

UFO は非推奨です：現代のカーネルでは UFO skbs を生成しなくなりましたが、tuntap などのデバイスから受信することは可能です。UDP 基盤のトンネルプロトコルのオフロードは引き続きサポートされています。

IPIP, SIT, GRE, UDPトンネル、およびリモートチェックサムオフロード¶

上記のオフロードに加えて、フレームには外側のトンネルなどの追加ヘッダーが含まれる場合があります。このようなケースを考慮するため、追加のセグメントオフロードタイプが導入されました。これにはSKB_GSO_IPXIP4、SKB_GSO_IPXIP6、SKB_GSO_GRE、SKB_GSO_UDP_TUNNELが含まれます。これらの追加セグメントタイプは、1セットのヘッダー以外にも存在するケースを識別するために使用されます。たとえば、IPIPやSITの場合、ネットワーク層とトランスポート層のヘッダーは標準的なヘッダー一覧から「内側」のヘッダーオフセットに移動する必要があります。

現在は最大2段階のヘッダーのみがサポートされています。慣例として、トンネルヘッダーは「外側のヘッダー」と呼ばれ、その中でエンカプスレーションされたデータは通常「内側のヘッダー」と呼ばれます。以下に、指定されたヘッダーにアクセスするための関数の一覧を示します：

IPIP/SITトンネル：

           Outer                  Inner
MAC        skb_mac_header
Network    skb_network_header     skb_inner_network_header
Transport  skb_transport_header

UDP/GREトンネル：

           Outer                  Inner
MAC        skb_mac_header         skb_inner_mac_header
Network    skb_network_header     skb_inner_network_header
Transport  skb_transport_header   skb_inner_transport_header

上記のトンネルタイプに加えて、SKB_GSO_GRE_CSUMとSKB_GSO_UDP_TUNNEL_CSUMという2つの追加トンネルタイプもあります。これらは、外側のヘッダーにもゼロでないチェックサムが含まれることを示しています。

最後に、SKB_GSO_TUNNEL_REMCSUMというタイプがあります。これは、指定されたトンネルヘッダーがリモートチェックサムオフロードを要求していることを示します。この場合、内側のヘッダーは部分的なチェックサムを保持し、外側のヘッダーのみが計算されます。

ジェネリックセグメンテーションオフロード¶

ジェネリックセグメントオフロードは、デバイスドライバーが上記のオフロードを実行できない場合に使用される純粋なソフトウェアオフロードです。GSOでは、指定されたskbuffのデータが、skb_shinfo()->gso_sizeで提供されたMSSに合わせてリサイズされた複数のskbuffに分割されます。

ハードウェアセグメントオフロードを有効にする前に、GSOにおける対応するソフトウェアオフロードが必要です。それがない場合、フレームがデバイス間で再ルーティングされ、送信ができない可能性があります。

ジェネリック受信オフロード¶

ジェネリックリシーブオフロード（GRO）はGSOの補完です。理想的には、GROでアセンブリされたフレームはGSOでセグメント化され、同じシーケンスのフレームに変換されるべきです。また、GSOでセグメント化されたフレームのシーケンスはGROによって元のフレームに戻されるべきです。ただし、IPv4 IDのケースではDFビットが設定されている場合を除き、例外があります。IPv4 IDの値が連続的にインクリメントされていない場合、GROでアセンブリされたフレームがGSOでセグメント化される際、その値を修正して連続的にします。

部分的なジェネリックセグメンテーションオフロード¶

部分的なジェネリックセグメンテーションオフロードは、TSOとGSOの中間的な手法です。この手法は、TCPとトンネルの特徴を活用し、各セグメントごとにパケットヘッダーを再構築する必要がなく、内側のトランスポートヘッダーおよび外側のネットワークヘッダーのみを更新することで、トンネルオフロードやチェックサム付きトンネルオフロードをサポートしないデバイスでもセグメンテーションを活用できるようにします。

部分的なオフロードでは、内側のトランスポートヘッダー以外のすべてのヘッダーが更新され、ヘッダーが単に複製された場合でも正しい値を持つようになります。ただし、外側のIPv4 IDフィールドはこの例外です。IPv4 IDフィールドのインクリメントは、ヘッダーにDFビットが設定されていない場合にデバイスドライバーが保証する必要があります。

GSOによるSCTP加速¶

SCTPは、ハードウェアのサポートがなくても、GSOを活用してネットワークスタックを介して1つの大きなパケットを通過させ、複数の小さなパケットを送信するのではなく、処理を効率化できます。

これは他のオフロードとは異なるアプローチが必要です。SCTPパケットは(P)MTUにセグメント化するのではなく、IPセグメントにチャンクを含め、パディングを尊重する必要があります。従来のGSOとは異なり、SCTPは単に大きなskbを生成し、gso_sizeをフラグメンテーションポイントに設定してIPレイヤーに渡すことはできません。

代わりに、SCT、プロトコルレイヤーはパディングが正しい状態でセグメントを含むskbを構築し、 skb_segment() そのセグメントに基づいて分割します。この動作を示すために、gso_sizeは特別な値GSO_BY_FRAGSに設定されます。

したがって、コアネットワーキングスタック内のすべてのコードは、gso_sizeがGSO_BY_FRAGSである可能性を認識し、そのケースを適切に処理する必要があります。

この処理をより簡単にするために、いくつかの補助関数があります：

  • skb_is_gso(skb) && skb_is_gso_sctp(skb)は、skbがSCTP GSO skbであるかを確認する最良の方法です。

  • サイズの確認では、skb_gso_validate_*_lenファミリの補助関数がGSO_BY_FRAGSを正しく考慮します。

  • パケットの操作では、skb_increase_gso_sizeとskb_decrease_gso_sizeはGSO_BY_FRAGSを検出し、これらのskbを操作するよう求められるとWARNします。

これはNETIF_F_FRAGLISTとNETIF_F_GSO_SCTPビットが設定されたドライバにも影響します。また、NETIF_F_GSO_SCTPはNETIF_F_GSO_SOFTWAREに含まれています。

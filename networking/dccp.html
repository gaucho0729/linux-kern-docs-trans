DCCPプロトコル¶

はじめに¶

データグラムコンガスト制御プロトコル（DCCP）は、UDPとTCPに存在する問題を解決するために設計された、信頼性のない接続型プロトコルです。特にリアルタイムおよびマルチメディア（ストリーミング）トラフィックに適しています。DCCPはベースプロトコル（RFC 4340）と呼ばれるプラグイン可能なコンガスト制御モジュール（CCIDs）から構成され、少なくとも1つのCCIDが有効化されている必要があります。Linux実装では、TCPに似たCCID2（RFC 4341）が使用されます。追加のCCIDs、例えばTCPに親和的なCCID3（RFC 4342）はオプションです。CCIDsの概要と、特定のアプリケーションに適したCCIDの選択方法については、RFC 4340のセクション10を参照してください。

ベースプロトコルと挿し替え可能なコンガスト制御ID（CCIDs）を持っています。

DCCPは提案標準（RFC 2026）であり、DCCPプロトコルのホームページは以下の通りです http://www.ietf.org/html.charters/dccp-charter.html

未実装機能¶

LinuxのDCCP実装は、RFC 4340…42に記載されているすべての機能を現在サポートしていません。

既知のバグについては以下にあります:

http://www.linuxfoundation.org/collaborate/workgroups/networking/todo#DCCP

最新のDCCP実装バージョンをご希望される場合は、実験用DCCPテストツリーをご利用ください。インストール手順については以下を参照してください: http://www.linuxfoundation.org/collaborate/workgroups/networking/dccp_testing#Experimental_DCCP_source_tree

ソケットオプション¶

DCCP_SOCKOPT_QPOLICY_IDは、出力パケットのキューイングポリシーを設定します。引数としてポリシーIDを指定し、接続開始前（つまり確立済み接続での変更はサポートされていません）にのみ設定可能です。現在、2つのポリシーが定義されています：『simple』ポリシー（DCCPQ_POLICY_SIMPLE）は特別な処理を行わず、『prio』ベースの変種（DCCPQ_POLICY_PRIO）はsendmsg()にu32型の優先度値を補助データとして渡します（高い数値は高いパケット優先度を示します、SO_PRIORITYに類似）。この補助データは、以下の通りcmsg(3)メッセージヘッダーでフォーマットする必要があります：

cmsg->cmsg_level = SOL_DCCP;
cmsg->cmsg_type  = DCCP_SCM_PRIORITY;
cmsg->cmsg_len   = CMSG_LEN(sizeof(uint32_t));  /* or CMSG_LEN(4) */

DCCP_SOCKOPT_QPOLICY_TXQLENは出力キューの最大長を設定します。ゼロ値は常に無限キュー長を意味します。ゼロ以外の値の場合、現在のキューイングポリシー（上記参照）に依存します：『simple』ポリシーは固定キュー長を強制し、EAGAINを返します。『prio』ポリシーは固定キュー長を強制し、最も低い優先度のパケットを最初に破棄します。このパラメータのデフォルト値は/proc/sys/net/dccp/default/tx_qlenから初期化されます。

DCCP_SOCKOPT_SERVICEはサービスを設定します。仕様ではサービスコード（RFC 4340、セクション8.1.2）の使用が義務付けられています。このソケットオプションが設定されていない場合、ソケットは0にフォールバックし（これは意味のあるサービスコードが存在しないことを意味します）、アクティブなソケットではconnect()呼び出し前に設定されます。複数のコードを指定しても効果がありません（すべての後のサービスコードは無視されます）。パッシブなソケットでは、bind()呼び出し前に最大32個のサービスコードを設定できます。

DCCP_SOCKOPT_GET_CUR_MPSは読み取り専用で、現在の最大パケットサイズ（アプリケーションペイロードサイズ）をバイト単位で取得します。RFC 4340、セクション14を参照してください。

DCCP_SOCKOPT_AVAILABLE_CCIDSも読み取り専用で、エンドポイントがサポートするCCIDの一覧を返します。オプション値はuint8_t型の配列で、サイズはオプション長として渡されます。最小の配列サイズは4要素で、optlen引数に返される値は常に組み込まれたCCIDの実際の数を反映します。

DCCP_SOCKOPT_CCIDは書き込み専用で、TXとRXのCCIDを同時に設定します。次の2つのソケットオプションの操作を組み合わせたものです。このオプションは後述の2つのオプションよりも優先されます。なぜなら、アプリケーションは通常、両方向で同じタイプのCCIDを使用するためです。また、CCIDの混用は現在よく理解されていません。このソケットオプションは、少なくとも1つのuint8_t値またはuint8_t値の配列を引数として受け取り、利用可能なCCID（上記参照）と一致する必要があります。CCIDはconnect()またはlisten()を呼び出す前にソケットに登録する必要があります。

DCCP_SOCKOPT_TX_CCIDは読み書き可能です。現在のCCID（設定されている場合）を返すか、TX CCIDの優先リストを設定します。これはDCCP_SOCKOPT_CCIDと同じ形式を使用します。注意点として、getsockopt引数の型は int、uint8_tではありません。

DCCP_SOCKOPT_RX_CCIDはDCCP_SOCKOPT_TX_CCIDに類似していますが、RX CCIDに関するものです。

DCCP_SOCKOPT_SERVER_TIMEWAITは、接続を閉じるときにサーバー（リスニングソケット）がタイムウェイト状態を保持できるようにします（RFC 4340、セクション8.3）。通常のケースでは、閉じるサーバーがCloseReqを送信し、クライアントがタイムウェイト状態を保持します。このブール型のソケットオプションが有効な場合、サーバーはCloseを送信し、TIMEWAIT状態に入るため、accept()が返る後でこのオプションを設定する必要があります。

DCCP_SOCKOPT_SEND_CSCOV と DCCP_SOCKOPT_RECV_CSCOV は、部分的なチェックサムのカバレッジ設定（RFC 4340、第9.2節）に使用されます。デフォルトではチェックサムがパケット全体を常にカバーし、受信側は完全にカバーされたアプリケーションデータのみを受け入れます。したがって、送信側でこの機能を使用する場合、受信側でもCsCovの適切な選択により有効化する必要があります。

DCCP_SOCKOPT_SEND_CSCOV は送信側のチェックサムカバレッジを設定します。値の範囲は

0..15 で、デフォルト設定は 0（完全カバー）であり、1..15 の値は部分的なカバーを示します。

DCCP_SOCKOPT_RECV_CSCOV は受信側用のオプションで、意味は異なります：これは

しきい値を設定するもので、再度値の範囲は 0..15 です。デフォルトの 0 は部分的なカバーを持つパケットをすべて破棄する意味であり、1..15 の値は少なくともそのカバー値を持つパケットも受け入れるを示します。値が大きいほどこの設定は厳格になります（RFC 4340、第9.2.1節参照）。部分的なカバー設定は accept() で生成された子ソケットに継承されます。

以下の2つのオプションは CCID 3 にのみ適用され、getsockopt() でのみ取得可能です。いずれの場合も、TFRC 情報構造体（<linux/tfrc.h> で定義）が返されます。

DCCP_SOCKOPT_CCID_RX_INFO

を返します struct tfrc_rx_info optval に格納され、optval と optlen のバッファは少なくとも sizeof(struct tfrc_rx_info) に設定する必要があります。

DCCP_SOCKOPT_CCID_TX_INFO

を返します struct tfrc_tx_info optval に格納され、optval と optlen のバッファは少なくとも sizeof(struct tfrc_tx_info) に設定する必要があります。

単方向接続では、使用していない半接続を shutdown（SHUT_WR または SHUT_RD）で閉じることで、パケットごとの処理コストを削減できます。

Sysctl 変数¶

いくつかの DCCP のデフォルトパラメータは、以下の sysctl（sysctl net.dccp.default または /proc/sys/net/dccp/default）で管理できます：

request_retries

タイムアウトするまでにアクティブな接続初期化リトライ回数（リクエストの数から1を引いた値）。また、これは受動的な側の動作も制御します：この変数は、初期ハンドシェイクが RESPOND から OPEN に進まない場合（つまり、初期リクエスト後の Ack を受信しない場合）に、DCCP がレスポンスを繰り返し送信する回数を設定します。この値は 0 より大きく、推奨値は 10 未満です。tcp_syn_retries と対応する値です。

retries1

DCCP レスポンスがリッスニング側が接続先を死んだとみなすまでに再送される回数。tcp_retries1 と対応する値です。

retries2

一般的なDCCPパケットが再送される回数。再送された確認応答と機能交渉には重要ですが、データパケットは決して再送されません。これはtcp_retries2のアナログです。

tx_ccid = 2

送信者受信者半接続のデフォルトCCID。CCIDの選択に応じて、送信ACKベクター機能が自動的に有効になります。

rx_ccid = 2

受信者送信者半接続のデフォルトCCID；tx_ccidを参照してください。

seq_window = 100

送信者の初期シーケンスウィンドウ（セクション7.5.2）です。これはローカルのACK有効性とリモートのシーケンス番号有効性ウィンドウ（7.5.1）に影響を与えます。Wmin = 32（RFC 4340、7.5.2）から2^32-1までの範囲で値を設定できます。

tx_qlen = 5

送信バッファのサイズ（パケット数）。値が0の場合は無制限の送信バッファになります。

sync_ratelimit = 125 ms

同じソケット上でシーケンス無効パケットに対するDCCP-Syncパケットを送信する際のタイムアウト間隔（RFC 4340、7.5.4）。このパラメータの単位はミリ秒で、値が0の場合はレート制限を無効にします。

IOCTLS¶

FIONREAD

udp(7)と同様に動作し、引数ポインタに次の待機中のデータグラムのバイト数を返します。待機中のデータグラムがない場合は0を返します。 int argument pointerに次の待機中のデータグラムのサイズ（バイト）を返します。待機中のデータグラムがない場合は0を返します。

SIOCOUTQ

ソケット送信キューにある未送データバイト数を、引数ポインタ指定のバッファに返します。 int 引数ポインタ指定のバッファに送信キューの未送データバイト数を返します。

その他のチューニングパラメータ¶

ルートごとのrto_minサポート

CCID-2は、RTOタイマの最小値としてルートごとのRTAX_RTO_MIN設定をサポートします。この設定はiproute2の'rto_min'オプションで変更可能です。例えば：

> ip route change 10.0.0.0/24   rto_min 250j dev wlan0
> ip route add    10.0.0.254/32 rto_min 800j dev wlan0
> ip route show dev wlan0

CCID-3もrto_min設定をサポートしており、これはnofeedbackタイマの有効期限の下限を定義します。これは非常に低いRTT（例：ループバック、Gbitイーサネット）を持つLANで役立ちます。

備考¶

現在、多くのマシンではDCCPがNATを通過できません。これはチェックサムがTCPおよびUDPと同様に擬似ヘッダーをカバーするためです。LinuxにおけるDCCP用のNATサポートは追加されました。

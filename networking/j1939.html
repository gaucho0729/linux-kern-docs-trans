J1939ドキュメンテーション¶

概要 / J1939とは¶

SAE J1939 は CAN 上でより上位レイヤーのプロトコルを定義しています。これにより、より複雑なアドレス割り当て方式が実装され、最大パケットサイズが8バイトを超えるよう拡張されています。いくつかの派生仕様が存在し、アプリケーションレイヤーでは元の J1939 と異なります。例えば MilCAN A、NMEA2000、特に ISO-11783 (ISOBUS) などです。最後のものは、いわゆる ETP (Extended Transport Protocol) と呼ばれるプロトコルを規定しており、この実装には含まれています。これにより、最大パケットサイズは ((2 ^ 24) - 1) * 7 バイト == 111 MiB になります。

使用する仕様¶

  • SAE J1939-21 : データリンク層

  • SAE J1939-81 : ネットワーク管理

  • ISO 11783-6 : ビーチャルテルミナル (Extended Transport Protocol)

動機¶

SocketCAN が API として BSD ソケットに似たものがあるため、J1939 で使用されるアドレス割り当てやトランスポート方式の実装をカーネルで行う理由がいくつかありました。

  • アドレス割り当て: ECU 上のプロセスが J1939 を通じて通信を行う際、必ずしもソースアドレスを知る必要はありません。ただし、少なくとも1つのプロセスはソースアドレスを把握しておく必要があります。他のプロセスはそのアドレスを再利用可能でなければなりません。これにより、同じ ECU を協働して動作する異なるプロセス間でアドレスパラメータが重複しないようにします。この仕組みは UNIX の概念に近いです。UNIX ではプログラムが1つのことだけを丁寧に実行します。

  • 動的アドレス割り当て: J1939 のアドレス主張は時間的に重要です。また、アドレス交渉中にデータトランスポートを適切に処理する必要があります。この機能をカーネルに実装することで、_すべての_ J1939 を通じて通信するユーザースペースプロセスがこの要件を満たす必要がなくなります。これにより、J1939 バスの整合性と適切なアドレス割り当てが保証されます。

  • トランスポート: TP および ETP はどちらもいくつかの PGN を再利用して大容量パケットを転送します。そのため、異なるプロセスが同じ TP および ETP PGN を使用しても気づかない場合があります。個々の TP および ETP セッションは _必須_ で、異なるプロセス間でシリアル化 (同期) される必要があります。カーネルはこの問題を適切に解決し、_すべての_ J1939 を通じて通信するユーザースペースプロセスがシリアル化 (同期) を行う必要をなくしています。

J1939 はリレー、ゲートウェイ、高速パケットトランスポートなど他の機能も定義しています。これらの実装はプロトコルの安定性に寄与しないため、これらはユーザースペースに任されています。

J1939のソケットはCANネットワークデバイス（SocketCANを参照）で動作します。CANのrawソケットで動作するJ1939ユーザースペースライブラリは依然として正常に動作します。このようなライブラリはカーネル内実装と通信しないため、これら2つの要素が干渉しないように注意する必要があります。実際には、これらはECUアドレスを共有できません。1つのECU（または仮想ECU）アドレスはライブラリが排他的に使用するか、カーネル内システムが排他的に使用する必要があります。

J1939の概念¶

PGN¶

PGN（パラメータグループ番号）はパケットを識別する番号です。PGNは以下のようになります：1ビット：予約ビット 1ビット：データページ 8ビット：PF（PDUフォーマット） 8ビット：PS（PDU固有）

J1939-21ではPDU1フォーマット（PF < 240）とPDU2フォーマット（PF >= 240）の区別が行われます。さらに、PDU2フォーマットを使用する場合、PSフィールドには「グループ拡張」と呼ばれる、PGNの一部となる情報が含まれます。PDU2フォーマットを使用する場合、グループ拡張はPSフィールドに設定されます。

一方、PDU1フォーマットを使用する場合、PSフィールドには「宛先アドレス」と呼ばれる情報が含まれます。これはPGNの一部ではありません。ユーザースペースからカーネル（または逆）でPGNを通信する際、PDU2フォーマットを使用する場合はPGNのPSフィールドをゼロに設定する必要があります。宛先アドレスは別途設定する必要があります。

PGNを29ビットCAN識別子にマッピングする際、カーネルが識別子の適切なビットから宛先アドレスを取得・設定します。

アドレス指定¶

静的アドレス割り当てと動的アドレス割り当ての両方を使用できます。

静的アドレスの場合、カーネルは追加のチェックを行わず、提供されたアドレスは正しいとみなされます。この責任はOEMやシステム統合責任者にあります。

動的アドレス割り当てでは「アドレス主張」と呼ばれる機能がカーネルでサポートされます。J1939ではすべてのECUが64ビットのNAMEで識別されます。アドレス主張が成功した際、カーネルはNAMEと主張されたソースアドレスを記録します。これはフィルタリングスキームのベースになります。デフォルトでは、ローカルでない宛先を持つパケットは拒否されます。

静的アドレスと動的アドレスの混合モードパケット（逆も可）は許可されます。BSDソケットはローカルとリモートアドレスの取得・設定に別個のAPIを定義しており、J1939ソケットにも適用されます。

フィルタリング¶

J1939はソケットごとにユーザーが受信するJ1939トラフィックのサブセットを受信するためのホワイトリストフィルタを定義しています。フィルタリングは以下の基準に基づきます：

  • SA

  • SOURCE_NAME

  • PGN

1つのソケットに対して複数のフィルタが適用されている場合、複数のフィルタに一致するパケットが到達したときでも、そのソケットに対してパケットは1度だけ受信されます。

J1939の使い方¶

API呼び出し¶

CANでは、CANネットワークを介した通信を行うためにはまずソケットを開く必要があります。J1939を使用するには、 #include <linux/can/j1939.h>。その先で、 <linux/can.h> も含まれます。ソケットを開くには、以下を使用してください：

s = socket(PF_CAN, SOCK_DGRAM, CAN_J1939);

J1939はソケットを使用します。 SOCK_DGRAM J1939仕様では、トランスポートプロトコルセッションの文脈で接続が言及されています。これらは、複数のCANパケットを使用して他端にパケットを送信します。 SOCK_STREAM サポートされていません。

ソケットが正常に作成された後、通常はシステムコールを使用して、CANインターフェースにソケットをバインドします。 bind(2) および/または connect(2) ソケットのバインドおよび/または接続が完了した後、ソケットから/へデータを送信/受信するか、通常のソケット操作を使用できます。 read(2) および write(2) ソケットから/へデータを送信/受信するか、通常のソケット操作を使用できます。 send(2), sendto(2), sendmsg(2) 2.5開発シリーズで導入された形式です。 recv*() J1939固有のソケットオプションも以下に記載されています。

データを送信するには、 bind(2) ソケットが正常に設定されている必要があります。 bind(2) ローカルアドレスをソケットに割り当てます。

CANとは異なり、ペイロードデータはヘッダ情報なしに送信されるだけで、ヘッダ情報はsockaddrに供給されたアドレスから導出されます。 bind(2), connect(2), sendto(2) および recvfrom(2). A write(2) サイズ4の場合は、4バイトのパケットになります。

sockaddr構造体には、以下の通りJ1939用の拡張機能が含まれています:

struct sockaddr_can {
   sa_family_t can_family;
   int         can_ifindex;
   union {
      struct {
         __u64 name;
                  /* pgn:
                   * 8 bit: PS in PDU2 case, else 0
                   * 8 bit: PF
                   * 1 bit: DP
                   * 1 bit: reserved
                   */
         __u32 pgn;
         __u8  addr;
      } j1939;
   } can_addr;
}

can_family & can_ifindex 他のSocketCANソケットと同じ目的を果たします。

can_addr.j1939.pgn PGNを指定します（最大値は0x3ffff）。個々のビットについては上記の通りです。

can_addr.j1939.name 64ビットのJ1939 NAMEを含みます。

can_addr.j1939.addr アドレスを含みます。

以下の bind(2) システムコールはローカルアドレスを割り当てます。つまり、パケットを送信する際のソースアドレスです。PGNが設定されている場合、 bind(2) 受信フィルタとして使用されます。つまり、一致するPGNを持つパケットのみが受信されます。ADDRまたはNAMEが設定されている場合、それも受信フィルタとして使用されます。これは、受信パケットの宛先NAMEまたはADDRと一致するためです。NAMEフィルタは、CANバス上でこのNAMEに対する適切なAddress Claimingが行われ、カーネルに登録・キャッシュされている場合にのみ機能します。

一方で connect(2) リモートアドレスを割り当てます。つまり、宛先アドレスです。PGNは connect(2) パケットを送信する際のデフォルトのPGNとして使用されます。ADDRまたはNAMEが設定されている場合、それらはデフォルトの宛先ADDRまたはNAMEとして使用されます。さらに、ADDRまたはNAMEが設定されている場合、 connect(2) 受信フィルタとして使用されます。これは、受信パケットのソースNAMEまたはADDRと一致するためです。

両方 write(2) および send(2) ローカルアドレスから送信するパケットを送信します。 bind(2) リモートアドレスから connect(2)。使用してください sendto(2) 宛先アドレスを上書きします。

もし can_addr.j1939.name 設定されている場合（！= 0）、カーネルがNAMEを検索し、対応するADDRが使用されます。If can_addr.j1939.name 設定されていない場合（== 0）、 can_addr.j1939.addr が使用されます。

ソケットを作成する際には、合理的なデフォルト値が設定されます。一部のオプションは setsockopt(2) & getsockopt(2).

RXパス関連のオプション:

  • SO_J1939_FILTER - フィルタの配列を設定

  • SO_J1939_PROMISC - 他の設定で設定されたフィルタを無効化 bind(2) および connect(2)

デフォルトではブロードキャストパケットの送受信はできません。ブロードキャストパケットの送受信を有効にするには、ソケットオプションを使用してください SO_BROADCAST:

int value = 1;
setsockopt(sock, SOL_SOCKET, SO_BROADCAST, &value, sizeof(value));

次のダイアグラムはRXパスを示しています:

send()時のメッセージフラグおよび関連するシステムコール¶

send(2), sendto(2) および sendmsg(2) flags引数を取る。現在サポートされているフラグは以下の通り:

  • MSG_DONTWAIT, つまり非ブロッキング操作です。

recvmsg(2)¶

ほとんどの場合 recvmsg(2) を取得するには必要です。たとえばパケット優先度やタイムスタンプなどの情報を取得する場合。宛先アドレス、名前、パケット優先度（必要な場合）は、 recvfrom(2) 呼び出し時にmsghdrに添付されます。これらは recvmsg(2) マクロを使用して抽出できます。 cmsg(3) マクロ、 cmsg_level == SOL_J1939 && cmsg_type == SCM_J1939_DEST_ADDR, SCM_J1939_DEST_NAME または SCM_J1939_PRIOで取得できます。返されたデータは uint8_t のために、 priority および dst_addr, and uint64_t のために、 dst_name.

uint8_t priority, dst_addr;
uint64_t dst_name;

for (cmsg = CMSG_FIRSTHDR(&msg); cmsg; cmsg = CMSG_NXTHDR(&msg, cmsg)) {
        switch (cmsg->cmsg_level) {
        case SOL_CAN_J1939:
                if (cmsg->cmsg_type == SCM_J1939_DEST_ADDR)
                        dst_addr = *CMSG_DATA(cmsg);
                else if (cmsg->cmsg_type == SCM_J1939_DEST_NAME)
                        memcpy(&dst_name, CMSG_DATA(cmsg), cmsg->cmsg_len - CMSG_LEN(0));
                else if (cmsg->cmsg_type == SCM_J1939_PRIO)
                        priority = *CMSG_DATA(cmsg);
                break;
        }
}

動的アドレス割当て¶

使用するアドレスとアドレスの主張を行う区別が必要です。既に主張されたアドレスを使用するには、 j1939.name メンバを埋め込み、それを bind(2)に提供する必要があります。もし名前で以前にアドレスを主張していた場合、その後のすべてのメッセージ送信はそのアドレスを使用します。この場合、 j1939.addr メンバは無視されます。

例外はPGN 0x0ee00です。これは「アドレス主張/アドレスを主張できない」メッセージで、カーネルがそのPGNに必要に応じて j1939.addr メンバを使用します。

アドレスを主張するには、次のコード例を使用できます:

struct sockaddr_can baddr = {
        .can_family = AF_CAN,
        .can_addr.j1939 = {
                .name = name,
                .addr = J1939_IDLE_ADDR,
                .pgn = J1939_NO_PGN,    /* to disable bind() rx filter for PGN */
        },
        .can_ifindex = if_nametoindex("can0"),
};

bind(sock, (struct sockaddr *)&baddr, sizeof(baddr));

/* for Address Claiming broadcast must be allowed */
int value = 1;
setsockopt(sock, SOL_SOCKET, SO_BROADCAST, &value, sizeof(value));

/* configured advanced RX filter with PGN needed for Address Claiming */
const struct j1939_filter filt[] = {
        {
                .pgn = J1939_PGN_ADDRESS_CLAIMED,
                .pgn_mask = J1939_PGN_PDU1_MAX,
        }, {
                .pgn = J1939_PGN_REQUEST,
                .pgn_mask = J1939_PGN_PDU1_MAX,
        }, {
                .pgn = J1939_PGN_ADDRESS_COMMANDED,
                .pgn_mask = J1939_PGN_MAX,
        },
};

setsockopt(sock, SOL_CAN_J1939, SO_J1939_FILTER, &filt, sizeof(filt));

uint64_t dat = htole64(name);
const struct sockaddr_can saddr = {
        .can_family = AF_CAN,
        .can_addr.j1939 = {
                .pgn = J1939_PGN_ADDRESS_CLAIMED,
                .addr = J1939_NO_ADDR,
        },
};

/* Afterwards do a sendto(2) with data set to the NAME (Little Endian). If the
 * NAME provided, does not match the j1939.name provided to bind(2), EPROTO
 * will be returned.
 */
sendto(sock, dat, sizeof(dat), 0, (const struct sockaddr *)&saddr, sizeof(saddr));

送信後250ms以内に他の誰もアドレス主張を争わない場合、カーネルがNAME-SA割当を有効とマークします。有効な割当は他の有効なNAME-SA割当と同様に保持されます。この時点で、NAMEにバインドされたソケットはパケットを送信できます。

他のECUがアドレスを主張した場合、カーネルはNAME-SAを期限切れとマークします。NAMEにバインドされたソケットは（アドレス主張を除いて）パケットを送信できません。別のアドレスを主張するには、NAMEにバインドされたソケットが bind(2) を再度実行し、 j1939.addr を新しいSAに変更し、その後有効なアドレス主張パケットを送信する必要があります。これにより、カーネル（およびバス上の他の参加者）のこのNAMEに対するステートマシンが再初期化されます。

can-utils また、 j1939acd ツールも含めるため、コード例としてまたはデフォルトのアドレス主張デーモンとして使用できます。

送信例¶

静的アドレス割当て¶

この例では、SA 0x20からDA 0x30へPGN (0x12300)を送信します。

バインド:

struct sockaddr_can baddr = {
        .can_family = AF_CAN,
        .can_addr.j1939 = {
                .name = J1939_NO_NAME,
                .addr = 0x20,
                .pgn = J1939_NO_PGN,
        },
        .can_ifindex = if_nametoindex("can0"),
};

bind(sock, (struct sockaddr *)&baddr, sizeof(baddr));

これにより、ソケット'sock'はSA 0x20にバインドされます。この時点で connect(2) が呼び出されていないため、この時点で使用できるのは sendto(2) または sendmsg(2).

のみです。送信:

const struct sockaddr_can saddr = {
        .can_family = AF_CAN,
        .can_addr.j1939 = {
                .name = J1939_NO_NAME;
                .addr = 0x30,
                .pgn = 0x12300,
        },
};

sendto(sock, dat, sizeof(dat), 0, (const struct sockaddr *)&saddr, sizeof(saddr));

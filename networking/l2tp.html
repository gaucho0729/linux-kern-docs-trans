L2TP¶

レイヤー2トンネリングプロトコル（L2TP）は、IPネットワークを介してL2フレームをトンネル化する機能を提供します。

このドキュメントはカーネルのL2TPサブシステムについて説明しており、L2TPサブシステムを使用するアプリケーション開発者向けのカーネルAPIを記載し、カーネル開発者やメンテナにとって有用な内部実装の技術的詳細も提供しています。

概要¶

カーネルのL2TPサブシステムはL2TPv2およびL2TPv3のデータパスを実装しています。L2TPv2はUDPを、L2TPv3はUDPまたは直接IP（プロトコル115）を介して運ばれます。

L2TP RFCでは、L2TPパケットを2つの基本的な種類に分類しています：コントロールパケット（「コントロールプレーン」）とデータパケット（「データプレーン」）。カーネルはデータパケットのみを処理し、より複雑なコントロールパケットはユーザー空間で処理されます。

L2TPトンネルは1つまたは複数のL2TPセッションを運び、各トンネルはソケットと関連付けられ、各セッションは仮想ネットデバイスと関連付けられます。例えば、データフレームがL2TPを介して通過する経路です。 pppN, l2tpethNL2TPヘッダー内のフィールドはトンネルまたはセッションを識別し、パケットがコントロールパケットかデータパケットかを示します。LinuxカーネルAPIを用いてトンネルとセッションを設定する際には、L2TPデータパスの設定にとどまり、コントロールプロトコルのすべての側面はユーザー空間で処理されます。

この責任の分離により、トンネルとセッションの確立時に自然な操作の順序が生じます。手順は以下の通りです：

  1. トンネルソケットを作成し、そのソケットを介してペアとコントロールプロトコルメッセージを交換してトンネルを確立します。

  2. コントロールプロトコルメッセージから得た情報を基に、カーネル内でトンネルコンテキストを作成します。

  3. トンネルソケットを介してペアとコントロールプロトコルメッセージを交換してセッションを確立します。

  4. コントロールプロトコルメッセージから得た情報を基に、カーネル内でセッションコンテキストを作成します。

L2TP API¶

このセクションではL2TPサブシステムの各ユーザー空間APIを記載しています。

トンネルソケット¶

L2TPv2は常にUDPを使用し、L2TPv3はUDPまたはIPカプセル化を使用することがあります。

L2TP用のトンネルソケットを作成するには、標準的なPOSIXソケットAPIを使用します。

IPv4アドレスとUDPカプセル化を使用するトンネルの例：

int sockfd = socket(AF_INET, SOCK_DGRAM, IPPROTO_UDP);

IPv6アドレスとIPカプセル化を使用するトンネルの例：

int sockfd = socket(AF_INET6, SOCK_DGRAM, IPPROTO_L2TP);

UDPソケットプログラミングについては説明する必要はありません。

IPPROTO_L2TPはカーネルのL2TPサブシステムで実装されるIPプロトコルタイプです。L2TPIPソケットアドレスは、struct sockaddr_l2tpipおよびstruct sockaddr_l2tpip6で定義されています。 include/uapi/linux/l2tp.hアドレスにはL2TPトンネル（接続）IDが含まれます。L2TP IPエンカプスレーションを使用するには、L2TPv3アプリケーションはローカルに割り当てられたトンネルIDを使用してL2TPIPソケットにバインドする必要があります。ペアのトンネルIDとIPアドレスがわかっている場合、接続を確立する必要があります。

L2TPアプリケーションがL2TPIPを使用してペアからL2TPv3トンネルのセットアップリクエストを処理する必要がある場合、そのリクエストをリッスンするための専用のL2TPIPソケットを開き、トンネルID 0を使用してソケットにバインドする必要があります。なぜなら、トンネルのセットアップリクエストはトンネルID 0宛てに送信されるからです。

L2TPトンネルとそのすべてのセッションは、トンネルソケットが閉じられたときに自動的に閉じられます。

Netlink API¶

L2TPアプリケーションはNetlinkを使用して、カーネル内のL2TPトンネルおよびセッションインスタンスを管理します。L2TP Netlink APIの定義は include/uapi/linux/l2tp.h.

L2TPは ジェネリックネットリンク (GENL)で定義されています。いくつかのコマンドが定義されています：トンネルおよびセッションインスタンス用の作成、削除、変更、取得など、例えば L2TP_CMD_TUNNEL_CREATEAPIヘッダーは、各コマンドで使用可能なNetlink属性タイプを一覧しています。

トンネルおよびセッションインスタンスは、ローカルで一意な32ビットIDで識別されます。L2TPトンネルIDは L2TP_ATTR_CONN_ID および L2TP_ATTR_PEER_CONN_ID 属性で指定され、L2TPセッションIDは L2TP_ATTR_SESSION_ID および L2TP_ATTR_PEER_SESSION_ID 属性で指定されます。Netlinkを使用してL2TPv2トンネルおよびセッションインスタンスを管理する場合、L2TPv2の16ビットトンネル/セッションIDがこれらの属性で32ビット値にキャストされます。

～において、クエリは L2TP_CMD_TUNNEL_CREATE コマンド、 L2TP_ATTR_FD がカーネルにトンネルソケットのファイル記述子を通知します。指定されない場合、カーネルはIPパラメータを設定した L2TP_ATTR_IP[6]_SADDR, L2TP_ATTR_IP[6]_DADDR, L2TP_ATTR_UDP_SPORT, L2TP_ATTR_UDP_DPORT 属性を使用してトンネル用のカーネルソケットを作成します。カーネルソケットは、未管理のL2TPv3トンネル（iproute2の「ip l2tp」コマンド）を実装するために使用されます。もし L2TP_ATTR_FD が指定されている場合、それはすでにバインドおよび接続済みのソケットファイル記述子でなければなりません。このドキュメント後半で未管理トンネルについてさらに詳述します。

PPPoL2TPセッションソケットAPI¶

PPPセッションタイプの場合、PPPoL2TPソケットを開き、L2TPセッションに接続する必要があります。

PPPoL2TPソケットを作成する際、アプリケーションはソケットconnect()呼び出しを通じてカーネルにトンネルおよびセッションに関する情報を提供します。ソースおよび宛先のトンネルおよびセッションID、UDPまたはL2TPIPソケットのファイルディスクリプタが提供されます。struct pppol2tp_addrについては include/linux/if_pppol2tp.hを参照してください。歴史的な理由により、L2TPv2/L2TPv3 IPv4/IPv6トンネルにはやや異なるアドレス構造があります。ユーザースペースは、トンネルソケットのタイプに応じて適切な構造を使用する必要があります。

ユーザースペースは、PPPoXソケットのsetsockoptおよびioctlを通じてトンネルまたはセッションの動作を制御できます。サポートされるソケットオプションは次の通り:

DEBUG

デバッグメッセージカテゴリのビットマスク。以下を参照してください。

SENDSEQ

  • 0 => シーケンス番号付きのパケットを送信しない

  • 1 => シーケンス番号付きのパケットを送信する

RECVSEQ

  • 0 => 受信パケットのシーケンス番号は任意

  • 1 => シーケンス番号のない受信パケットをドロップする

LNSMODE

  • 0 => LACとして動作する

  • 1 => LNSとして動作する

REORDERTO

再配列タイムアウト（ミリ秒単位）。0の場合は再配列を試みません。

標準的なPPP ioctlsに加えて、PPPIOCGL2TPSTATSは、適切なトンネルまたはセッションのPPPoXソケットを使用してカーネルからトンネルおよびセッションの統計情報を取得するために提供されています。

ユーザースペースのサンプルコード:

  • セッションPPPoXデータソケットを作成:

    struct sockaddr_pppol2tp sax;
int fd;

/* Note, the tunnel socket must be bound already, else it
 * will not be ready
 */
sax.sa_family = AF_PPPOX;
sax.sa_protocol = PX_PROTO_OL2TP;
sax.pppol2tp.fd = tunnel_fd;
sax.pppol2tp.addr.sin_addr.s_addr = addr->sin_addr.s_addr;
sax.pppol2tp.addr.sin_port = addr->sin_port;
sax.pppol2tp.addr.sin_family = AF_INET;
sax.pppol2tp.s_tunnel  = tunnel_id;
sax.pppol2tp.s_session = session_id;
sax.pppol2tp.d_tunnel  = peer_tunnel_id;
sax.pppol2tp.d_session = peer_session_id;

/* session_fd is the fd of the session's PPPoL2TP socket.
 * tunnel_fd is the fd of the tunnel UDP / L2TPIP socket.
 */
fd = connect(session_fd, (struct sockaddr *)&sax, sizeof(sax));
if (fd < 0 ) {
        return -errno;
}
return 0;

旧L2TPv2専用API¶

L2TPがLinuxカーネルに最初に導入された2.6.23では、L2TPv2のみを実装しており、netlink APIは含まれていませんでした。代わりに、カーネル内のトンネルおよびセッションインスタンスは、PPPoL2TPソケットを介して直接管理されていました。PPPoL2TPセッションソケットAPIのセクションで説明されているように、PPPoL2TPソケットは接続時に自動的にトンネルおよびセッションインスタンスが作成されるようになりました。

  • トンネルは、専用のPPPoL2TPソケットであるトンネル管理ソケットを使用して管理されます。このソケットは無効なセッションID 0に接続されています。PPPoL2TPトンネル管理ソケットが接続されるとL2TPトンネルインスタンスが作成され、ソケットが閉じるとインスタンスが破棄されます。

  • セッションインスタンスは、PPPoL2TPソケットがゼロでないセッションIDに接続されたときにカーネル内で作成されます。セッションパラメータはsetsockoptを使用して設定されます。ソケットが閉じるとL2TPセッションインスタンスが破棄されます。

このAPIはまだサポートされていますが、使用は推奨されません。代わりに新しいL2TPv2アプリケーションでは、まずnetlinkを使用してトンネルとセッションを作成し、その後セッション用のPPPoL2TPソケットを作成する必要があります。

未管理のL2TPv3トンネル¶

カーネルのL2TPサブシステムは、静的（未管理）なL2TPv3トンネルもサポートしています。未管理トンネルはユーザースペースのトンネルソケットを持たず、ピアとの通信で制御メッセージを交換せずにトンネルを設定します。トンネルの設定は各端で手動で行われ、すべての設定はnetlinkを使用して行われます。この場合、L2TPユーザースペースアプリケーションは必要ありません。カーネルがトンネルソケットを作成し、netlinkリクエストで送信されたパラメータで設定します。 L2TP_CMD_TUNNEL_CREATE netlinkリクエスト。 ip ユーティリティの iproute2 静的L2TPv3トンネルを管理するコマンドを備えています。do ip l2tp help 詳しくは

デバッグ¶

L2TPサブシステムはdebugfsファイルシステムを通じてさまざまなデバッグインターフェースを提供しています。

これらのインターフェースにアクセスするには、まずdebugfsファイルシステムをマウントする必要があります:

# mount -t debugfs debugfs /debug

l2tpディレクトリ以下のファイルはアクセス可能となり、カーネル内に存在するトンネルおよびセッションコンテキストの現在の状態を要約しています:

# cat /debug/l2tp/tunnels

アプリケーションがL2TPの状態情報を取得するためにdebugfsファイルを使用すべきではありません。ファイル形式は変更される可能性があります。これは問題の診断を支援するための追加のデバッグ情報を提供するための実装です。アプリケーションでは代わりにnetlink APIを使用すべきです。

さらに、L2TPサブシステムは標準のカーネルイベントトレースAPIを使用してトレースポイントを実装しています。利用可能なL2TPイベントは以下の通り確認できます:

# find /debug/tracing/events/l2tp

最後に、/proc/net/pppol2tpは元のpppol2tpコードとの後方互換性のために提供されています。これはL2TPv2トンネルおよびセッションに関する情報のみをリストアップします。その使用は推奨されません。

内部実装¶

このセクションはカーネルの開発者およびメンテナナー向けです。

ソケット¶

UDPソケットはネットワーキングコアによって実装されています。L2TPトンネルがUDPソケットを使用して作成される場合、UDPソケットにencap_rcvとencap_destroyコールバックを設定することで、エンカプスレーションされたUDPソケットとしてセットアップされます。パケットがソケットで受信されるとl2tp_udp_encap_recvが呼び出され、ユーザー空間がソケットを閉じるときにはl2tp_udp_encap_destroyが呼び出されます。

L2TPIPソケットは net/l2tp/l2tp_ip.c および net/l2tp/l2tp_ip6.c.

トンネル¶

カーネルはL2TPトンネルごとにstruct l2tp_tunnelコンテキストを保持しています。l2tp_tunnelは常にUDPまたはL2TP/IPソケットと関連付けられ、トンネル内のセッションリストを保持しています。L2TPコアにトンネルが最初に登録される際、ソケットの参照カウントが増加します。これにより、L2TPのデータ構造が参照している間、ソケットが削除されることを防ぎます。

トンネルは一意のトンネルIDで識別されます。IDはL2TPv2では16ビット、L2TPv3では32ビットです。内部的にはIDは32ビット値として保存されます。

トンネルはトンネルIDでインデックス化されたネットごとのリストに保持されます。トンネルIDの名前空間はL2TPv2とL2TPv3で共有されています。トンネルコンテキストはソケットのsk_user_dataから導出できます。

トンネルソケットの閉じ処理はL2TP実装の中で最も複雑な部分かもしれません。ユーザー空間がトンネルソケットを閉じる場合、L2TPトンネルとそのすべてのセッションが閉じられ削除される必要があります。トンネルコンテキストはトンネルソケットに参照を保持しているため、ソケットのsk_destructはトンネルsock_putがソケットを解放するまで呼び出されません。UDPソケットの場合、ユーザー空間がトンネルソケットを閉じると、ソケットのencap_destroyハンドラが呼び出され、L2TPがトンネル閉じアクションを開始します。L2TPIPソケットの場合、ソケットのcloseハンドラが同じトンネル閉じアクションを開始します。すべてのセッションがまず閉じられ、各セッションはトンネル参照をリリースします。トンネル参照がゼロになると、トンネルはソケット参照を解放します。ソケットが最終的に破壊されるとき、sk_destructがL2TPトンネルコンテキストを解放します。

セッション¶

カーネルは各セッションに対してstruct l2tp_sessionコンテキストを保持しています。各セッションはセッションタイプに特有のデータを保持するプライベートデータを持っています。L2TPv2ではセッションは常にPPPトラフィックを運搬します。L2TPv3ではセッションはイーサネットフレーム（イーサネット擬似ワイヤー）やPPP、ATM、HDLC、フレームリレーなどの他のデータタイプを運搬できます。Linuxでは現在、イーサネットとPPPのセッションタイプのみを実装しています。

一部のL2TPセッションタイプにはソケット（PPP擬似ワイヤー）があり、他のタイプにはありません（イーサネット擬似ワイヤー）。したがって、ソケット参照カウントをセッションコンテキストの参照カウントとして使用することはできません。L2TPの実装では、セッションコンテキストに独自の内部参照カウントを保持しています。

トンネル同様に、L2TPセッションは一意のセッションIDで識別されます。トンネルIDと同様に、L2TPv2ではセッションIDが16ビット、L2TPv3では32ビットです。内部的には、IDは32ビットの値として保存されます。

セッションは親トンネルに参照を保持し、1つ以上のセッションが参照している間、トンネルが存在し続けるようにしています。

セッションはトンネルごとのリストに保持され、セッションIDでインデックス付けされます。L2TPv3セッションはさらにネットワークごとのリストに保持され、セッションIDでインデックス付けされます。これはL2TPv3セッションIDがすべてのトンネルを越えて一意であり、L2TPv3データパケットにトンネルIDがヘッダーに含まれていないためです。このリストは、トンネルコンテキストがトンネルソケットから導出できない場合に、受信したデータパケットに関連するセッションコンテキストを検索するために必要です。

L2TPv3 RFCではL2TPv3セッションIDがトンネルスコープ外であると規定していますが、カーネルはL2TPv3 UDPトンネルに対してこの制限をチェックせず、L2TPv3 UDPトンネルのセッションをネットワークごとのセッションリストに追加しません。UDP受信コードでは、トンネルソケットのsk_user_dataを用いてトンネルを特定し、トンネルのセッションリストではなくネットワークごとのセッションリストでセッションを検索する必要があります。

PPP¶

net/l2tp/l2tp_ppp.c PPP over L2TP（PPPoL2TP）ソケットファミリを実装しています。各PPPセッションにはPPP over L2TPソケットが割り当てられます。

PPP over L2TPソケットのsk_user_dataはl2tp_sessionを参照しています。

ユーザースペースはPPP over L2TPソケットを介してL2TPを介してPPPパケットを送受信します。このソケットを介して通過するのはPPPコントロールフレームのみです：PPPデータパケットはカーネルが処理し、L2TPセッションとその関連する pppN netdevを介してカーネルPPPサブシステムのPPPチャネルインターフェースを通じて処理されます。

L2TP PPP実装では、PPPoL2TPソケットの閉じる操作は、対応するL2TPセッションの閉じることで行われます。これはネットリンクセッションの作成/破壊リクエストとpppol2tp_connectによる再接続がセッションの閉じる過程で競合するため複雑です。トンネルとは異なり、PPPセッションは関連するソケットに参照を保持していないため、コードでは必要に応じてsock_holdを呼び出す必要があります。詳細については、コミット3d609342cc04129ff7568e19316ce3d7451a27e8を参照してください。

イーサネット¶

net/l2tp/l2tp_eth.c L2TPv3 Ethernetの擬似ワイヤーを実装しています。各セッションに対してnetdevを管理します。

L2TP Ethernetセッションはnetlinkリクエストによって作成または破棄され、トンネルが破棄されるときに破棄されます。PPPセッションとは異なり、Ethernetセッションには関連するソケットがありません。

制限¶

現在の実装にはいくつかの制限があります：

  1. 同じ5つのタプルアドレスを持つ複数のUDPソケットは使用できません。カーネルのトンネルコンテキストはソケットに関連付けられたプライベートデータで識別されるため、各ソケットがアドレスで一意に識別されることが重要です。

  2. オープンバーチャルスイッチ(OVS)とのインターフェースはまだ実装されていません。OVSのイーサネットおよびVLANポートをL2TPv3トンネルにマッピングすることができると便利かもしれません。

  3. VLAN擬似ワイヤーは l2tpethN VLANサブインターフェースで構成されたインターフェースを使用して実装されています。L2TPv3 VLAN擬似ワイヤーは1つのVLANのみを運ぶため、複数のVLANセッションごとに:Mペアを使用するよりも、単一のネットデバイスを使用する方が良いかもしれません。 l2tpethN および l2tpethNnetlink属性 L2TP_ATTR_VLAN_ID はこれのために追加されましたが、実装されていませんでした。

テスト¶

未管理のL2TPv3 Ethernet機能はカーネルの組み込み自己テストでテストされます。詳しくは tools/testing/selftests/net/l2tp.sh.

別のテストスイート l2tp-ktestはすべてのL2TP APIとトンネル/セッションタイプをカバーしています。今後、カーネルの組み込みL2TP自己テストに統合される可能性があります。

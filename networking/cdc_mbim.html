cdc_mbim - CDC MBIMモバイルブロードバンドモデム用ドライバー¶

cdc_mbimドライバは、『Universal Serial Bus Communications Class Subclass Specification for Mobile Broadband Interface Model』[1]に準拠したUSBデバイスをサポートします。これは『Universal Serial Bus Communications Class Subclass Specifications for Network Control Model Devices』[2]の拡張版で、モバイルブロードバンドデバイス（いわゆる「3G/LTEモデム」）に最適化された仕様です。

コマンドラインパラメータ¶

cdc_mbimドライバは独自のパラメータを持たないものの、NCM 1.0との後方互換性を持つMBIM機能（[1]のセクション3.2で定義される「NCM/MBIM機能」）のプロービング動作は、cdc_ncmドライバのパラメータによって影響されます。

prefer_mbim¶

タイプ

ブール型

有効な範囲

N/Y (0-1)

デフォルト値

Y（MBIMが優先されます）

このパラメータはNCM/MBIM機能のシステムポリシーを設定します。このような機能は、prefer_mbimの設定に応じてcdc_ncmドライバまたはcdc_mbimドライバのいずれかで処理されます。prefer_mbim=Nに設定すると、cdc_mbimドライバはこれらの機能を無視し、cdc_ncmドライバが処理します。

このパラメータは書き換え可能で、いつでも変更可能です。NCM/MBIM機能が「間違った」ドライバにバインドされている場合、変更を有効にするには手動でアンバインド/バインドが必要です。

基本的な使い方¶

管理されていない状態ではMBIM機能は無効です。cdc_mbimドライバはMBIM制御チャネルのユーザー空間インターフェースを提供するだけで、機能の管理には参加しません。これは、MBIM機能を有効にするには常にユーザー空間のMBIM管理アプリケーションが必要であることを意味します。

このようなユーザー空間アプリケーションには、以下のものが含まれますが、これに限定されるわけではありません：

  • mbimcli（libmbim [3]ライブラリに同梱）および

  • ModemManager [4]

MBIM IPセッションの確立には、管理アプリケーションが少なくとも以下のアクションを実行する必要があります：

  • 制御チャネルを開く

  • ネットワーク接続設定を構成する

  • ネットワークに接続する

  • IPインターフェースを構成する

管理アプリケーションの開発¶

ドライバーアプリケーション間インターフェースについては以下に記載します。MBIM制御チャネルプロトコルについては[1]を参照してください。

MBIM制御チャネルユーザー空間ABI¶

/dev/cdc-wdmXキャラクターデバイス¶

ドライバはcdc-wdmドライバをサブドライバとして使用して、MBIM機能の制御チャネルに双方向パイプを構築します。ユーザー空間側の制御チャネルパイプの終端は/dev/cdc-wdmXというキャラクターデバイスです。

cdc_mbimドライバは制御チャネルのメッセージを処理または制御しません。このチャネルは完全にユーザー空間の管理アプリケーションに委譲されています。したがって、このアプリケーションが[1]に記載されているすべての制御チャネルの要件に準拠することを確保する必要があります。

cdc-wdmXデバイスはMBIM制御インターフェースUSBデバイスの子デバイスとして作成されます。特定のMBIM機能に関連するキャラクターデバイスはsysfsを使用して検索できます。例えば：

bjorn@nemi:~$ ls /sys/bus/usb/drivers/cdc_mbim/2-4:2.12/usbmisc
cdc-wdm0

bjorn@nemi:~$ grep . /sys/bus/usb/drivers/cdc_mbim/2-4:2.12/usbmisc/cdc-wdm0/dev
180:0

USBコンフィギュレーションデスクリプタ¶

CDC MBIM機能デスクリプターのwMaxControlMessageフィールドは、最大制御メッセージサイズを制限します。管理アプリケーションは、[1]の第9.3.1節に記載されている要件を満たす制御メッセージサイズを協議し、このデスクリプタフィールドを考慮して責任を負います。

ユーザー空間アプリケーションは、[6]または[7]に記載されている2つのUSBコンフィギュレーションデスクリプタカーネルインターフェースのいずれかを使用して、MBIM機能のCDC MBIM機能デスクリプターにアクセスできます。

以下のioctlドキュメンテーションも参照してください。

フラグメンテーション¶

ユーザー空間アプリケーションは、[1]の第9.5節に記載されているように、すべての制御メッセージのフラグメンテーションおよびデフラグメンテーションを担当します。

/dev/cdc-wdmX write()¶

管理アプリケーションからのMBIM制御メッセージ eisa_driver_registerから戻るときにEISAデバイスが検出されることを期待しないでください。なぜなら、バスがまだプローブされていない可能性が高いからです。実際には、ほとんどの場合（バスルートドライバーがブートプロセスの後半になってから動作するため）このことが起こります。残念ながら、ほとんどのドライバーは自らプローブを行い、プローブルーティンを終了するときに全体のマシンを探索していると期待しています。 協議された制御メッセージサイズを超過しています。

/dev/cdc-wdmX read()¶

管理アプリケーション grace periodsを尊重しなければなりませんし、 協議された制御メッセージサイズまでの制御メッセージを受け入れます。

/dev/cdc-wdmX ioctl()¶

IOCTL_WDM_MAX_COMMAND: 最大コマンドサイズ取得 このioctlはMBIMデバイスのCDC MBIM機能デスクリプターのwMaxControlMessageフィールドを返します。これはユーザー空間からUSBデスクリプタを解析する必要がないようにするための利便性として意図されています。

#include <stdio.h>
#include <fcntl.h>
#include <sys/ioctl.h>
#include <linux/types.h>
#include <linux/usb/cdc-wdm.h>
int main()
{
        __u16 max;
        int fd = open("/dev/cdc-wdm0", O_RDWR);
        if (!ioctl(fd, IOCTL_WDM_MAX_COMMAND, &max))
                printf("wMaxControlMessage is %d\n", max);
}

カスタムデバイスサービス¶

MBIM仕様はベンダーが追加サービスを自由に定義できるようにしています。これはcdc_mbimドライバが完全にサポートしています。

新しいMBIMサービス、包括してベンダー指定のサービスのサポートは、MBIM制御プロトコルの他の部分と同様にユーザー空間で完全に実装されています。

新しいサービスはMBIMレジストリ[5]に登録する必要があります。

MBIMデータチャネルユーザー空間ABI¶

wwanYネットワークデバイス¶

cdc_mbimドライバはMBIMデータチャネルを「wwan」タイプの単一ネットワークデバイスとして表現します。このネットワークデバイスは初期的にMBIM IPセッション0にマッピングされます。

多重化されたIPセッション（IPS）¶

MBIMは単一のUSBデータチャネルを介して最大256のIPセッションを多重化できます。cdc_mbimドライバはこのようなIPセッションを、マスターデバイスであるwwanYデバイスの802.1q VLANサブデバイスとしてモデル化し、MBIM IPセッションZをすべてのZ値が0より大きい場合にVLAN ID Zにマッピングします。

デバイスの最大Z値は、[1]のセクション10.5.1で説明されているMBIM_DEVICE_CAPS_INFO構造体に記載されています。

MBIM IPセッションを確立する前に、SessionIdが0より大きい場合の新しいVLANリンクの追加は、ユーザースペース管理アプリケーションの責任です。これらのリンクは、ioctlまたはnetlinkを用いた通常のVLANカーネルインターフェースを使用して追加できます。

例えば、SessionId 3を持つMBIM IPセッション用のリンクを追加する場合、

ip link add link wwan0 name wwan0.3 type vlan id 3

ドライバーは自動的に「wwan0.3」ネットワークデバイスをMBIM IPセッション3にマッピングします。

デバイスサービスストリーム（DSS）¶

MBIMは、同じ共有USBデータチャネルを介して最大256の非IPデータストリームを多重化することを許可しています。cdc_mbimドライバーは、これらのセッションをマスターデバイスwwanYの別の802.1q VLANサブデバイスとしてモデル化し、MBIM DSSセッションAをすべてのA値に対してVLAN ID（256 + A）にマッピングします。

デバイスの最大A値は、[1]のセクション10.5.29で説明されているMBIM_DEVICE_SERVICES_INFO構造体に記載されています。

DSS VLANサブデバイスは、共有MBIMデータチャネルとMBIM DSSを認識するユーザースペースアプリケーションの間の実用的なインターフェースとして使用されます。これは最終ユーザーに直接提示するものではなく、ユーザースペースアプリケーションがDSSセッションを開始する際には、DSSデータの必要なフレーミングを処理し、ストリームタイプに応じて適切な形で最終ユーザーにストリームを提示する必要があります。

ネットワークデバイスABIは、DSSデータフレームを転送する際にすべてのDSSデータフレームにダミーイーサネットヘッダーを必要とします。このヘッダーの内容は以下の例外を除いて任意です：

  • IPプロトコル（0x0800または0x86dd）を使用するTXフレームは破棄されます

  • RXフレームはプロトコルフィールドにETH_P_802_3を設定します（ただし、適切にフォーマットされた802.3フレームではありません）

  • RXフレームは、マスターデバイスのハードウェアアドレスを宛先アドレスとして設定します

DSSをサポートするユーザースペース管理アプリケーションは、TX時にダミーイーサネットヘッダーを追加し、RX時にそれを削除する責任があります。

これは一般的なツールを用いた簡単な例で、/dev/nmeaシンボリックリンクによって指されるptyキャラクターデバイスとしてDssSessionId 5をエクスポートしています：

ip link add link wwan0 name wwan0.dss5 type vlan id 261
ip link set dev wwan0.dss5 up
socat INTERFACE:wwan0.dss5,type=2 PTY:,echo=0,link=/dev/nmea

これはテスト用の例にすぎません。特定のMBIM DSSサービスをサポートするユーザースペースアプリケーションは、そのサービスに必要なツールとプログラミングインターフェースを使用する必要があります。

DSSセッション用のVLANリンクを追加するのは完全にオプションです。管理アプリケーションは、受信したVLANタグを使用してフレームを正しいDSSセッションにマッピングし、適切なタグをTX時に18バイトのVLANイーサネットヘッダーとして追加するため、パケットソケットをマスターネットワークデバイスに直接バインドする選択肢もあります。この場合、DSS VLANサブセットのみをマッチするソケットフィルタの使用が推奨されます。これにより、関係のないIPセッションデータのユーザー空間への不要なコピーを回避できます。例えば：

static struct sock_filter dssfilter[] = {
      /* use special negative offsets to get VLAN tag */
      BPF_STMT(BPF_LD|BPF_B|BPF_ABS, SKF_AD_OFF + SKF_AD_VLAN_TAG_PRESENT),
      BPF_JUMP(BPF_JMP|BPF_JEQ|BPF_K, 1, 0, 6), /* true */

      /* verify DSS VLAN range */
      BPF_STMT(BPF_LD|BPF_H|BPF_ABS, SKF_AD_OFF + SKF_AD_VLAN_TAG),
      BPF_JUMP(BPF_JMP|BPF_JGE|BPF_K, 256, 0, 4),     /* 256 is first DSS VLAN */
      BPF_JUMP(BPF_JMP|BPF_JGE|BPF_K, 512, 3, 0),     /* 511 is last DSS VLAN */

      /* verify ethertype */
      BPF_STMT(BPF_LD|BPF_H|BPF_ABS, 2 * ETH_ALEN),
      BPF_JUMP(BPF_JMP|BPF_JEQ|BPF_K, ETH_P_802_3, 0, 1),

      BPF_STMT(BPF_RET|BPF_K, (u_int)-1),     /* accept */
      BPF_STMT(BPF_RET|BPF_K, 0),             /* ignore */
};

タグ付きIPセッション0 VLAN¶

上記のように、ドライバーはMBIM IPセッション0を特別に扱います。これは最初にwwanYネットワークデバイスのタグ未設定フレームにマッピングされます。

このマッピングは、多重化されたIPSおよびDSSセッションにいくつかの制限をもたらします。これらは常に実用的とは限りません：

  • IPセッション0のMTUを超えるフレームサイズを使用することはできません

  • IPセッション0を表すネットワークデバイスがアップ状態でない限り、どのIPSまたはDSSセッションもアップ状態にできません

これらの問題は、オプションでドライバーがIPセッション0を他のIPセッションと同様にVLANサブデバイスにマッピングするように設定することで回避できます。この動作は、マジックVLAN ID 4094用のVLANリンクを追加することでトリガーされます。ドライバーはこのVLANにMBIM IPセッション0をすぐにマッピングし、マスターデバイスwwanY上のタグ未設定フレームをドロップします。

ヒント：最終ユーザーにとって混乱を減らすために、このVLANサブデバイスをVLAN IDではなくMBIMセッションIDで名付けるのが良いかもしれません。例えば：

ip link add link wwan0 name wwan0.0 type vlan id 4094

VLANマッピング¶

上記のcdc_mbimドライバーのマッピングをまとめると、wwanYネットワークデバイスのVLANタグと共有USBデータチャネル上のMBIMセッションの関係は以下の通りです：

VLAN ID       MBIM type   MBIM SessionID           Notes
---------------------------------------------------------
untagged      IPS         0                        a)
1 - 255       IPS         1 - 255 <VLANID>
256 - 511     DSS         0 - 255 <VLANID - 256>
512 - 4093                                         b)
4094          IPS         0                        c)

  a) if no VLAN ID 4094 link exists, else dropped
  b) unsupported VLAN range, unconditionally dropped
  c) if a VLAN ID 4094 link exists, else dropped

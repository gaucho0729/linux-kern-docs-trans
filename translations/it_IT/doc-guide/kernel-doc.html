kernel-docでのコメントの作成¶

Linuxカーネルのソースファイルには、kernel-doc形式に従ったドキュメンテーションコメントが含まれています。これらは関数、データ型、コードのアーキテクチャを説明できます。

注意

kernel-doc形式はgtk-docやDoxygenに似ているように見えるかもしれませんが、歴史的な理由により実際には大きく異なります。カーネルのソースコードには数万のkernel-docコメントが含まれています。ここに記述されたスタイルに従ってください。

kernel-docの構造はコメントから抽出され、それからC用のSphinxドメインが生成されます。 C用のSphinxドメイン 関数とデータ型の適切な説明およびそれらの関連リンクを含みます。説明はフィルタリングされ、参照とマーカーを検索します。

以下に詳細情報を確認してください。

すべての外部モジュールにエクスポートされる関数は、 EXPORT_SYMBOL o EXPORT_SYMBOL_GPL kernel-docコメントを持つ必要があります。モジュールで使用する予定であれば、ヘッダーファイル内の関数およびデータ構造にもkernel-docコメントが必要です。

他のカーネルファイルから見える関数（つまり、「static」で宣言されていない関数）に対して、kernel-doc形式でドキュメンテーションを提供することが良い実践とされています。 staticさらに、プライベートな手続き（つまり、「static」で宣言されたもの）にもkernel-doc形式のドキュメンテーションを提供することを推奨します。これによりソースコードのより一貫した構造が得られます。ただし、この推奨は優先度が低く、ソースファイルのマントーナー（MAINTAINER）の裁量に委ねられます。

外部モジュールにエクスポートされる関数については、kernel-doc形式でドキュメンテーションを提供することが絶対に必要です。 EXPORT_SYMBOL o EXPORT_SYMBOL_GPL.

他のカーネルファイルから見える関数（つまり、「static」で宣言されていない関数）にも、kernel-doc形式でドキュメンテーションを提供することを推奨します。

さらに、プライベートな手続き（つまり、「static」で宣言されたもの）にもkernel-doc形式のドキュメンテーションを提供することを推奨します。これによりソースコードのより一貫した構造が得られます。ただし、この推奨は優先度が低く、ソースファイルのマントーナー（MAINTAINER）の裁量に委ねられます。

ヘッダーファイルで見えるデータ構造も、kernel-doc形式のコメントでドキュメンテーションする必要があります。

kernel-doc コメントのフォーマット方法¶

kernel-doc コメントは、マーカー /**. プログラム kernel-doc このようにマークされたコメントは表示されます。コメントの他の部分は通常のマルチラインコメントとしてフォーマットされ、各行の先頭にアスタリスクが付けられ、別行で終了します。 */ 別の行で終了します。

関数や型のkernel-docコメントは、その関数や型の直前に配置すべきです。これにより、コードを変更する人がドキュメントも更新する可能性が高まります。より一般的なkernel-docコメントはファイルのどこでも配置可能です。

コメントが正しくフォーマットされているかを確認するには、以下のコマンドを実行してください。 kernel-doc 高詳細な出力レベルで実行し、ドキュメントを生成しないようにします。例えば：

scripts/kernel-doc -v -none drivers/foo/bar.c

ドキュメントのフォーマットは、GCCを使用したカーネル生成プロセスの検証時に確認されます。

make W=n

関数のドキュメンテーション¶

関数やマクロのkernel-docコメントの一般的なフォーマットは以下の通りです：

/**
 * function_name() - Brief description of function.
 * @arg1: Describe the first argument.
 * @arg2: Describe the second argument.
 *        One can provide multiple line descriptions
 *        for arguments.
 *
 * A longer description, with more discussion of the function function_name()
 * that might be useful to those using or modifying it. Begins with an
 * empty comment line, and may include additional embedded empty
 * comment lines.
 *
 * The longer description may have multiple paragraphs.
 *
 * Context: Describes whether the function can sleep, what locks it takes,
 *          releases, or expects to be held. It can extend over multiple
 *          lines.
 * Return: Describe the return value of function_name.
 *
 * The return value description can also have multiple paragraphs, and should
 * be placed at the end of the comment block.
 */

関数名の後に続く簡潔な説明は、複数行にわたって続き、引数の説明、空行、またはコメントの終わりで終了します。

関数の引数¶

関数の各引数は、簡潔な説明の直後に順番に記述する必要があります。簡潔な説明と引数の説明の間に空行を挟まず、引数同士も空行を挟みません。

各 @argument: は複数行にわたって記述できます。

注意

の説明が複数行にわたる場合、継続行は前の行と同じ列から開始する必要があります： @argument: の説明が複数行にわたる場合、継続行は前の行と同じ列から開始する必要があります：

* @argument: some long description
*            that continues on next lines

または:

* @argument:
*         some long description
*         that continues on next lines

関数が可変長引数を持つ場合、kernel-docの記法を使用して説明する必要があります：

* @...: description

関数のコンテキスト¶

関数が呼ばれるコンテキストは、セクション Contextで説明します。これにより、関数がスリープ（sleep）する可能性や、割込みコンテキストで呼ばれる可能性、また呼び出し元が取得・解放すべきリソースが説明されます。 lock 取得・解放すべきリソース、呼び出し元が取得・解放すべきリソース、呼び出し元が取得・解放すべきリソースが説明されます。

例：

* Context: Any context.
* Context: Any context. Takes and releases the RCU lock.
* Context: Any context. Expects <lock> to be held by caller.
* Context: Process context. May sleep if @gfp flags permit.
* Context: Process context. Takes and releases <mutex>.
* Context: Softirq or process context. Takes and releases <lock>, BH-safe.
* Context: Interrupt context.

戻り値¶

戻り値がある場合、専用のセクション Return.

注意

  1. で説明します。マルチラインコメントは改行を認識しないため、以下の例のようにテキストを整えると、

    * Return:
* 0 - OK
* -EINVAL - invalid argument
* -ENOMEM - out of memory

    行が結合され、結果は以下のようになります：

    Return: 0 - OK -EINVAL - invalid argument -ENOMEM - out of memory

    したがって、行が実際に生成される場合は、ReSTリストを使用する必要があります。例えば：

    * Return:
* * 0             - OK to runtime suspend the device
* * -EBUSY        - Device should not be runtime suspended

  2. もしテキストに冒頭が文とコロンで始まる行がある場合、それぞれの文は新しいセクション名として扱われ、おそらく意図した効果を生じない可能性があります。

構造体、ユニオン、列挙型のドキュメンテーション¶

一般的に、kernel-doc コメントの構造体のフォーマットは、 union ed enum の場合、

/**
 * struct struct_name - Brief description.
 * @member1: Description of member1.
 * @member2: Description of member2.
 *           One can provide multiple line descriptions
 *           for members.
 *
 * Description of the structure.
 */

上記の例では、 struct を union o enum に置き換えることで、ユニオンおよび列挙型を記述できます。 member は構造体およびユニオンのメンバーや、列挙型の値を示すために使用されます。

関数名の後に続く簡潔な説明は、複数行にわたって続き、引数の説明、空行、またはコメントの終わりで終了します。

メンバーアイテム¶

構造体、ユニオン、列挙型のメンバーアイテムは関数のパラメータとしてドキュメンテーションする必要があります。説明文の後に続き、複数行にわたって記述できます。

構造またはユニオン内では、ラベルを使用できます private: e public:. Area内のフィールド private: 最終ドキュメンテーションには含まれません。

ラベル private: e public: コメントのマーカーの直後に配置する必要があります /*. オプションでは、開始マーカーと : 終了マーカーの間にコメントを含めることができます */.

例:

/**
 * struct my_struct - short description
 * @a: first member
 * @b: second member
 * @d: fourth member
 *
 * Longer description
 */
struct my_struct {
    int a;
    int b;
/* private: internal use only */
    int c;
/* public: the next one is public */
    int d;
};

ネストされた構造とユニオン¶

ネストされた構造とユニオンをドキュメンテーションできます。例:

/**
 * struct nested_foobar - a struct with nested unions and structs
 * @memb1: first member of anonymous union/anonymous struct
 * @memb2: second member of anonymous union/anonymous struct
 * @memb3: third member of anonymous union/anonymous struct
 * @memb4: fourth member of anonymous union/anonymous struct
 * @bar: non-anonymous union
 * @bar.st1: struct st1 inside @bar
 * @bar.st2: struct st2 inside @bar
 * @bar.st1.memb1: first member of struct st1 on union bar
 * @bar.st1.memb2: second member of struct st1 on union bar
 * @bar.st2.memb1: first member of struct st2 on union bar
 * @bar.st2.memb2: second member of struct st2 on union bar
 */
struct nested_foobar {
  /* Anonymous union/struct*/
  union {
    struct {
      int memb1;
      int memb2;
  }
    struct {
      void *memb3;
      int memb4;
    }
  }
  union {
    struct {
      int memb1;
      int memb2;
    } st1;
    struct {
      void *memb1;
      int memb2;
    } st2;
  } bar;
};

注意

  1. ネストされた構造体または共用体をドキュメントする場合、例えば名前のように foo、そのフィールド bar は、以下の方法でドキュメントする必要があります @foo.bar:

  2. ネストされた構造体または共用体が匿名の場合、そのフィールドは bar は、以下の方法でドキュメントする必要があります @bar:

メンバのドキュメント用のインラインコメント¶

構造体のメンバは、その定義内にインラインでドキュメントできます。スタイルは2種類あります：1行のコメントで、以下のように始まります /** …で終わります； */複数行のコメントは、他のkernel-docコメントと同様に

/**
 * struct foo - Brief description.
 * @foo: The Foo member.
 */
struct foo {
      int foo;
      /**
       * @bar: The Bar member.
       */
      int bar;
      /**
       * @baz: The Baz member.
       *
       * Here, the member description may contain several paragraphs.
       */
      int baz;
      union {
              /** @foobar: Single line description. */
              int foobar;
      };
      /** @bar2: Description for struct @bar2 inside @foo */
      struct {
              /**
               * @bar2.barbar: Description for @barbar inside @foo.bar2
               */
              int barbar;
      } bar2;
};

データ型のドキュメント¶

typedefのkernel-docコメントの一般的な形式は以下の通りです：

/**
 * typedef type_name - Brief description.
 *
 * Description of the type.
 */

関数プロトタイプのデータ型もドキュメントできます：

/**
 * typedef type_name - Brief description.
 * @arg1: description of arg1
 * @arg2: description of arg2
 *
 * Description of the type.
 *
 * Context: Locking context.
 * Return: Meaning of the return value.
 */
 typedef void (*type_name)(struct v4l2_ctrl *arg1, void *arg2);

一般ドキュメンテーション用のコメント¶

コードとコメントが同じファイルに含まれるようにするには、関数、構造体、共用体、列挙型、データ型用の特定のフォーマットではなく、自由なフォーマットのドキュメンテーションブロックを含めることができます。例えば、ドライバやライブラリの操作説明にこの種のコメントが使用されることがあります。

これは、以下のキーワードを使用することで実現されます： DOC: タイトルと関連付けられます。

一般的なコメントまたは概要のフォーマットは通常、次のようになります：

/**

 *
 * The whizbang foobar is a dilly of a gizmo. It can do whatever you
 * want it to do, at any time. It reads your mind. Here's how it works.
 *
 * foo bar splat
 *
 * The only drawback to this gizmo is that is can sometimes damage
 * hardware, software, or its subject(s).
 */

タイトルは以下の通り DOC: ソースファイル内の見出しとして機能し、これらのドキュメンテーションコメントの抽出にも使用されるため、タイトルはファイル内で一意である必要があります。

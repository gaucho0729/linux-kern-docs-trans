批判的セクションとセクション¶

このような重なり合い、つまり結果が異なるプロセス間のタイミングに依存する状況は「批判的競合（race condition）」と呼ばれます。この問題を含むコードの一部は「セクション（critical section）」と呼ばれます。特にLinuxがマルチプロセッサマシンで動作し始めた後、セクションはコア設計および実装において最大の問題の一つとなっています。

優先度の処理でも同様の影響が生じます。単一のCPUであっても、プロセスのセクション中を中断することで、同じ批判的競合が発生します。この場合、実行を継続するスレッドがセクションを実行する可能性があります。

解決策は、このような同時アクセスを認識し、 lock を用いて、一度に1つのインスタンスのみがセクションに入るよう保証することです。コアにはこの目的に適した機能が用意されています。そして、それらよりも劣る機能もありますが、今回は存在しないとします。

ユーザー空間での同期¶

ユーザー空間のみで使用されるデータ構造を保護するには、単純なミューテックス（include/linux/mutex.h）を使用できます。これは最も簡単なケースです：ミューテックスを初期化し、 mutex_lock_interruptible() で保持し、 mutex_unlock() で解放します。また、 mutex_lock() もありますが、シグナルが発生した場合に戻らないため、使用を避けてください。

例えば： net/netfilter/nf_sockopt.c は、setsockopt()とgetsockopt()の新しい呼び出しを登録するためにnf_register_sockopt()関数を使用します。登録と削除は、モジュールがロードまたはアンロードされるとき（およびシステム起動時、この時点で競合はありません）にのみ行われ、登録された関数の一覧は、setsockopt()またはgetsockopt()がシステムで未登録のときにのみ参照されます。このような場合、 nf_sockopt_mutex は目的に非常に適しています、特にsetsockoptおよびgetsockoptが待機する可能性があるためです。

ユーザー コンテキストと softirq との同期化¶

softirq がユーザー コンテキストとデータを共有する場合、2つの問題があります。1つ目は、現在のユーザー コンテキストが softirq によって中断される可能性があり、2つ目は、クリティカルセクションが別のプロセッサによって実行される可能性があります。これは spin_lock_bh() (include/linux/spinlock.h) が使用される場合です。この関数はプロセッサの softirq を無効化し、 lockを保持します。代わりに spin_unlock_bh() は逆の動作を行います。(「_bh」のサフィックスは、かつてソフトウェア インタラクションの古い名前だった「Bottom Halves」に由来する歴史的残滓であり、理想的にはこの関数は「spin_lock_softirq()」と呼ばれるべきです)

この場合、spin_lock_irq() や spin_lock_irqsave() を使用することも可能です。これらはハードウェア インタラクションも停止します：参照 ハードウェア割込みのコンテキスト.

これは単一プロセッサ システムでも完全に機能します。スピンロックは消失し、このマクロは単に local_bh_disable() (include/linux/interrupt.h) になります。これは softirq の実行を防ぎます。

ハードウェア割込みとsoftirq/tasklet間の同期¶

ハードウェア割込みハンドラがsoftirqと共有データを使用する場合、2つの懸念があります。1つ目はsoftirqがハードウェア割込みによって中断される可能性、2つ目はcritical sectionが別のプロセッサ上でハードウェア割込みによって実行される可能性です。この場合、spin_lock_irq()が使用されます。この関数は実行中のプロセッサの割込みを無効化し、ロックを取得します。spin_unlock_irq()はその逆を行います。

ハードウェア割込みハンドラはspin_lock_irq()を使用する必要がありません。なぜなら、softirqはハードウェア割込みハンドラが実行中である間は実行されないからです。そのため、spin_lock()を使用できます。これはやや高速です。例外は別のハードウェア割込みハンドラが同じリソースを使用する場合です。 lock: spin_lock_irq()はこの2番目のハンドラが実行中のハンドラを中断することを防ぎます。

これは単一プロセッサシステムでも問題なく動作します。spinlockは消失し、このマクロは単にlocal_irq_disable()（include/asm/smp.h）となり、softirq/tasklet/BHの実行を防ぎます。

spin_lock_irqsave（include/linux/spinlock.h）は割込み状態を変数に保存する変体であり、spin_unlock_irqrestore()に渡されます。これにより、同じコードがハードウェア割込み（割込みは既に無効）とsoftirq（割込み無効が必要な状況）の両方で使用できます。

注意すべきは、softirq（したがってタスクレットとタイマー）がハードウェア割込みの戻り後に実行されるため、spin_lock_irq()はこれらも中断することです。この点を考慮すると、spin_lock_irqsave()は最も一般的で強力な同期関数です。

ハードウェア割り込みハンドラ間でデータを共有することは非常にまれですが、もし発生した場合は spin_lock_irqsave() を使用すべきです：アーキテクチャの特性として、割り込みハンドラが実行中である間、すべての割り込みが中断されるためです。

#include <linux/list.h>
#include <linux/slab.h>
#include <linux/string.h>
#include <linux/mutex.h>
#include <asm/errno.h>

struct object
{
        struct list_head list;
        int id;
        char name[32];
        int popularity;
};

/* Protects the cache, cache_num, and the objects within it */
static DEFINE_MUTEX(cache_lock);
static LIST_HEAD(cache);
static unsigned int cache_num = 0;
#define MAX_CACHE_SIZE 10

/* Must be holding cache_lock */
static struct object *__cache_find(int id)
{
        struct object *i;

        list_for_each_entry(i, &cache, list)
                if (i->id == id) {
                        i->popularity++;
                        return i;
                }
        return NULL;
}

/* Must be holding cache_lock */
static void __cache_delete(struct object *obj)
{
        BUG_ON(!obj);
        list_del(&obj->list);
        kfree(obj);
        cache_num--;
}

/* Must be holding cache_lock */
static void __cache_add(struct object *obj)
{
        list_add(&obj->list, &cache);
        if (++cache_num > MAX_CACHE_SIZE) {
                struct object *i, *outcast = NULL;
                list_for_each_entry(i, &cache, list) {
                        if (!outcast || i->popularity < outcast->popularity)
                                outcast = i;
                }
                __cache_delete(outcast);
        }
}

int cache_add(int id, const char *name)
{
        struct object *obj;

        if ((obj = kmalloc(sizeof(*obj), GFP_KERNEL)) == NULL)
                return -ENOMEM;

        strscpy(obj->name, name, sizeof(obj->name));
        obj->id = id;
        obj->popularity = 0;

        mutex_lock(&cache_lock);
        __cache_add(obj);
        mutex_unlock(&cache_lock);
        return 0;
}

void cache_delete(int id)
{
        mutex_lock(&cache_lock);
        __cache_delete(__cache_find(id));
        mutex_unlock(&cache_lock);
}

int cache_find(int id, char *name)
{
        struct object *obj;
        int ret = -ENOENT;

        mutex_lock(&cache_lock);
        obj = __cache_find(id);
        if (obj) {
                ret = 0;
                strcpy(name, obj->name);
        }
        mutex_unlock(&cache_lock);
        return ret;
}

割り込みハンドラによって主に使用されるデータ¶

データが常に同じ割り込みハンドラによって使用される場合、その lock データはまったく必要ありません：カーネルがすでに割り込みハンドラが複数のプロセッサ上で同時に実行されることを防いでいるためです。

Manfred Spraulは、データがユーザーコンテキストやソフトウェア割り込みによって偶発的に使用される場合でも、このような動作を続けることができます。割り込みハンドラはどの lockデータも使用せず、すべての他のアクセスはこのように行われます：

spin_lock(&lock);
disable_irq(irq);
...
enable_irq(irq);
spin_unlock(&lock);

spin_trylock() は、最初の試行で lock を取得できればゼロ以外の値を返し、失敗すればゼロを返します。この関数は、ハードウェアまたはソフトウェア割り込みのコンテキストでは安全に使用できません。 disable_irq() 割り込みハンドラの実行を防ぎ（他のプロセッサ上で実行中であれば終了を待つ）、スピンロックは同時にアクセスを防ぎます。ただし、これは単純なspin_lock_irq()呼び出しよりも遅いため、このようなアクセスが極めてまれな場合にのみ意味があります。

割込みから安全に呼び出せる関数はどれですか？¶

カーネルの多くの関数はスリープします（実際にはschedule()を呼び出します）。スピンロックを保持中やプリエンプションが無効な状態では、これらの関数を呼び出すことはできません。つまり、ユーザーコンテキストでなければなりません：割り込みコンテキストから呼び出すことは違法です。

一部のスリープする関数¶

最も一般的なものは以下に記載されていますが、通常はコードを確認する必要がありますが、他の呼び出しも安全かどうかを確認できます。誰かがそれらを呼び出すと眠る場合、あなたも眠ることができます。特に、登録と解除関数は通常、ユーザーコンテキストから呼び出されることが期待されており、それらが眠る可能性があります。

  • ユーザー空間へのアクセス:

    • copy_from_user()

    • copy_to_user()

    • get_user()

    • put_user()

  • kmalloc(GFP_KERNEL) <kmalloc>`

  • mutex_lock_interruptible() および mutex_lock()

    また、 mutex_trylock() は眠りません。ただし、割り込みコンテキストでは使用すべきではありません。なぜなら、その実装がそのコンテキストでは安全でないからです。また、 mutex_unlock() は決して眠りません。ただし、割り込みコンテキストでは使用できません。なぜなら、ミューテックスは取得したプロセスのみが解放できるからです。

眠らない関数の一例¶

一部の関数は、どのコンテキストからでも呼び出せます。または、任意の lock.

  • printk()

  • kfree()

  • add_timer() e del_timer()

語彙集¶

プリエンプション

2.5カーネル以前、または CONFIG_PREEMPT 設定されていない場合、ユーザー空間のプロセスは実行を順番に実行されません（実際には、プロセスは割込みがない限りプロセッサを終了するまで使用します）。『spinlock』の導入により、 CONFIG_PREEMPT 2.5.4バージョンではこの仕様が変更されました：ユーザー空間で実行中でも、優先度の高いプロセスが実行を中断して実行されるようになりました。spinlockは単一プロセッサシステムでもプリエンプションを無効にするために変更されました。

bh

ボトムハーフ：歴史的な理由により、名前に『_bh』が含まれる関数はすべてソフトウェア割込みを指します。たとえば、spin_lock_bh()は現在のプロセッサ上のすべてのソフトウェア割込みをブロックします。I ボトムハーフ は非推奨となり、おそらくタスケットに置き換えられます。ある時点で、ただ一つの 下半分 実行中。

中断コンテキスト

ユーザー コンテキストではありません: ここでハードウェアおよびソフトウェアの割り込みが処理されます。in_interrupt() マクロは true を返します。

ユーザー コンテキスト

特定のプロセス（たとえばシステムコール）またはカーネル スレッドの代わりに何かを実行するカーネル。プロセスをマクロで識別できます currentユーザー スペースとは区別してください。ソフトウェアおよびハードウェアの割り込みによって中断される可能性があります。

ハードウェア 割り込み

ハードウェア 割り込みのリクエスト。ハードウェア 割り込みのハンドラでは in_irq() が true を返します。

ソフトウェア 割り込み / softirq

ソフトウェア 割り込みハンドラ: in_irq() は false を返し、in_softirq() は true を返します。tasklet と softirq はどちらも ‘ソフトウェア 割り込み’ とみなされます。

soldoniにおいて、softirqは32のソフトウェア割込みの一つで、複数のプロセッサで同時に実行可能です。時には、タスクレット（実際にはすべてのソフトウェア割込み）を指すこともあります。

monoprocessore / UP

(Uni-Processor) 単一プロセッサ、つまりSMPではありません。(CONFIG_SMP=n).

multi-processore / SMP

(Symmetric Multi-Processor) 複数プロセッサシステム用にコンパイルされたカーネル (CONFIG_SMP=y).

spazio utente

カーネルの外で自身のコードを実行するプロセス。

tasklet

動的に登録可能なソフトウェア割込みで、一度に1つのプロセッサのみで実行されることが保証されています。

タイマ

動的に登録可能なソフトウェア割込みで、特定のタイミングで実行されます（ほぼ）。実行中はタスクレットのように動作します（実際には、 TIMER_SOFTIRQ).

アクター¶

システム内のCPUはいつでも以下のいずれかの状態になります：

  • どのプロセスにも関連付けられず、ハードウェア割込みを処理中;

  • どのプロセスにも関連付けられず、softirqまたはtaskletを処理中;

  • ユーザー空間でプロセスを実行中（ユーザー コンテキスト）;

  • ユーザー空間でプロセスを実行中;

これらのケースには順序があります。最後の2つは（プリエンプション）によって交互に実行されます。ただし、この他に厳格な階層があり、それぞれの状態は下位の状態のみとプリエンプション可能です。例えば、softirqがCPU上で実行中である場合、他のsoftirqは実行を中断できませんが、ハードウェア割込みは可能です。ただし、システム内の他のCPUは独立して動作します。

後述するように、ユーザー コンテキストでは割込みをブロックする方法があります。これにより、本当に割込みの優先順位を防ぐことができます。

ユーザー コンテキスト¶

システムコールやその他の例外から来た場合、ユーザー コンテキストにいます。ユーザー空間では、他の重要なプロセスや割込みが、あなたのプロセスの優先順位を主張する可能性があります。プロセスの実行を一時停止するには、 schedule().

注意

常にユーザー コンテキストです。モジュールがロードまたはアンロードされるとき、ブロックレイヤー（block layer).

ユーザー コンテキストでは、 current (現在実行中のプロセスを指すポインタ)は有効であり、 in_interrupt() (include/linux/preempt.h)は偽です。

警告

注意してください。割込みの優先順位やsoftirqが無効になっている場合（以下を参照） in_interrupt() 偽陽性を返すことがあります。

ハードウェア割込み (Hard IRQs)¶

タイマーやネットワークカード、キーボードは、いつでも割り込みを発生させる真のハードウェアの例です。カーネルはハードウェアにサービスを提供する割り込みハンドラを実行します。カーネルはこれらのハンドラが決して中断されないことを保証しており、同じ割り込みが到来した場合、キューイング（または無視）されます。割り込みの実行中に割り込みが無効化されるため、ハンドラは高速でなければなりません。通常は、割り込みの処理を通知し、ソフトウェア割り込みのスケジュールを設定してから終了します。

ハードウェア割り込みであることを確認できます in_irq() 真を返します。

警告

注意: 割り込みが無効になっている場合、偽陽性を返す可能性があります（以下を参照）。

ソフトウェア割り込みのコンテキスト: softirq と tasklet¶

システムコールがユーザー空間に戻るとき、または割り込みハンドラが終了するとき、すべての「ソフトウェア割り込み」が実行されます（kernel/softirq.c).

割り込みの管理に必要な大部分の作業はここにあります。マルチプロセッサシステムへの移行初期には、ただの「ボトムハーフ（BH）」という形式しかありませんでしたが、これらはマルチプロセッサシステムの恩恵を受けることができませんでした。コンピュータの改造が終わると、この制限も捨て、ソフトウェア割り込み「softirqs」に移行しました。

ファイル include/linux/interrupt.h は「softirq」のさまざまなタイプを列挙しています。重要なsoftirqの一種はタイマ（include/linux/timer.h）で、特定の時間経過後に処理を実行するように設定できます。

softirqは複数のプロセッサ上で同時に実行されるため、扱いが煩雑になることがあります。そのため、タスクレット（include/linux/interrupt.h）がより頻繁に使用されます：動的に登録できる（つまり、必要に応じて何でも作成可能）し、複数のタスクレットが同時に実行される一方で、1つのプロセッサで1つのタスクレットのみを実行することを保証します。

警告

タスクレットという名前は誤解を招くかもしれません：これは「プロセス（タスク）」とは一切関係がなく、おそらくアレクセイ・クズネツォフがその頃に飲んだ悪質なウーロン茶にちなんで名付けられたものです。

softirq（またはタスクレット）であるかを確認するには、マクロ in_softirq() (include/linux/preempt.h).

警告

いくつかの基本的なルール¶

メモリ保護なし

メモリが破損すると、ユーザー コンテキストか割り込み コンテキストかに関わらず、マシンがクラッシュします。本当にユーザー スペースで実行可能な処理を実行するつもりですか？

浮動小数点数やMMXは使用不可

FPU コンテキストが保存されていません。ユーザー コンテキスト内であっても、FPUの状態は現在のプロセスとは一致しない可能性があります。他のプロセスの状態と混乱するため、浮動小数点数を使用する場合は、FPUの状態を保存・復元する必要があります（コンテキストの切り替えを避ける必要があります）。通常は悪い考えです。固定小数点算術を使用してください。

スタックの厳格な制限

カーネルの設定により、32ビットアーキテクチャではスタックサイズが3K〜6K、64ビットアーキテクチャでは14K程度です。また、割り込みと共有されるため使用できません。スタックに深い再帰や巨大なローカル配列は避けて、動的配列で確保してください。

Linux カーネルは移植可能

そのままでお使いください。コードは64ビットで、プロセッサのバイト順（エンドイアンネス）に依存しないようにしてください。また、プロセッサ固有のコードは最小限に抑え、アセンブリコードは綺麗で最小限にまとめて移植性を高めてください。通常はアーキテクチャ固有のカーネル部分に限定してください。

ioctl: 新しいシステム コールを作成しないでください¶

一般的にシステム コールは以下のように書かれます:

asmlinkage long sys_mycall(int arg)
{
        return 0;
}

まず、ほとんどの場合新しいシステム コールを作成する必要はありません。キャラクタデバイスを作成し、適切なioctlを実装してください。このメカニズムはシステム コールよりもはるかに柔軟です。システム コールはすべてのアーキテクチャで宣言する必要があるため、 include/asm/unistd.h e arch/kernel/entry.S; また、Linus に受け入れられにくいです。

コードが読み書きするパラメータがすべてであれば、インターフェースの実装を検討してください sysfs().

ioctl 内ではプロセスのユーザー コンテキストにいます。エラーが発生した場合は errno の負数を返してください（参照 include/uapi/asm-generic/errno-base.h, include/uapi/asm-generic/errno.h e include/linux/errno.h）、それ以外は0を返してください。

眠った後はシグナルが発生していないか確認してください。Unix/Linux ではシグナルを処理する方法として、システム コールを一時的に中断してエラーで終了します -ERESTARTSYSシステムコールはユーザーのコンテキストに戻り、シグナルハンドラを実行した後、あなたのシステムコールは再開されます（ユーザーが無効にしていない限り）。したがって、データ構造の操作の途中などで実行を再開する準備ができている必要があります。

kmalloc()/kfree()¶

定義されています include/linux/slab.h

[待機可能：下記を読みましょう]

これらのプロシージャは、mallocとfreeと同じようにユーザー空間でメモリのアラインメントされたポインタを動的に要求するために使用されます。ただし、 kmalloc() 追加の引数でいくつかのオプションを指定します。重要なオプションは以下の通りです。

GFP_KERNEL

メモリを解放するために待機する場合があります。このオプションはメモリを割り当てる最も信頼性の高い方法ですが、その使用はユーザー空間に厳密に制限されます。

GFP_ATOMIC

待機しません。信頼性は GFP_KERNELよりも低く、ただし割り込みコンテキストで使用できます。メモリ不足の場合のエラー処理に、 本当に 信頼性の高い戦略が必要です。

GFP_DMA

ISAバスのDMA用に16MB以下のアドレス空間でメモリを割り当てます。もし何のことか分からないなら必要ありません。非常に信頼性が低く、危険です。

関数が間違ったコンテキストから呼び出されたときに警告メッセージが表示された場合は、おそらく割り込みコンテキストから待機する割り当て関数を使用しています。 GFP_ATOMICを呼び出さなければなりません。これを修正してください。急いでください、時間を無駄にしないでください。

少なくとも PAGE_SIZE``(``asm/page.h o asm/page_types.h)バイトを割り当てると、 __get_free_pages() (include/linux/gfp.h)を使用することを検討してください。ページサイズのサイズ（0）、ダブルページ（1）、4ページ（2）など、ページサイズのオーダーを指定する引数と、前述の割り当てオプションを受け入れます。

ページよりも大幅に大きいバイト数を割り当てている場合は、 vmalloc()このメモリは、カーネル空間内で仮想メモリを割り当てます。これは物理的に連続していないメモリブロックですが、MMU（メモリ管理ユニット）はこれを連続しているように感じさせます（つまり、プロセッサの観点では連続していますが、外部デバイスドライバの観点では連続していません）。もし何か奇妙な理由で、物理的に連続した大量のメモリが必要な場合は、問題があります：Linuxはこの用途に対して良いサポートを持っていません。時間が経つとメモリのフラグメンテーションにより、この操作が困難になるためです。システム起動初期にこのようなブロックを割り当てる最善の方法は、以下の手順を通じて行います。 alloc_bootmem().

詳しくは include/asm/current.h

__initcall()/module_init()¶

定義されています include/linux/init.h / include/linux/module.h

カーネルの多くの部分はモジュール（動的にロード可能なカーネルコンポーネント）として動作します。マクロ module_init() e module_exit() は、#ifdefを用いずにモジュールまたはカーネルの一部として動作するコードの記述を簡略化します。

マクロ module_init() は、モジュールがインサートされるときに呼び出す関数（ファイルがモジュールとしてコンパイルされている場合）または起動時に呼び出す関数を定義します。ファイルがモジュールとしてコンパイルされていない場合、マクロ module_init() は __initcall()と同等になり、リンカーマジックにより起動時に関数が呼び出されるようになります。

関数は負のエラーコードを返してロード失敗を引き起こすことができます（不幸にも、この機能はカーネルの一部としてコンパイルされているモジュールには効きません）。この関数はユーザー空間で割り込みが有効な状態で呼び出されるため、待機する可能性があります。

module_exit()¶

詳しくは include/linux/module.h

このマクロは削除時に呼び出す関数を定義します（カーネルの一部である場合、呼び出されません）。この関数は、モジュールの使用カウンターがゼロになるときにのみ呼び出されます。この関数は待機するかもしれませんが、失敗することはできません。関数が戻る前にすべてのクリーンアップを完了しなければなりません。

注意してください。このマクロはオプションです。存在しない場合、モジュールは削除できません（'rmmod -f' を使用しない限り）

これらの関数は、モジュールの使用カウンターを管理して、モジュールの削除を防ぎます（さらに、他のモジュールがそのエクスポートされたシンボルの1つを使用している場合、モジュールは削除できません：以下を参照してください）。モジュールのコードを実行する前に、以下の関数を呼び出す必要があります。 try_module_get() そのモジュールに対して呼び出してください：失敗した場合、モジュールが削除されたことを意味し、そのモジュールが存在しないように扱う必要があります。それ以外の場合、安全にモジュールにアクセスできます。完了したら、以下の関数を呼び出してください。 module_put() 待ち行列

待ち行列に追加¶

待ち行列に追加するのは複雑です。なぜなら、条件を確認する前に待ち行列に登録する必要がありますからです。この目的のマクロがあります： wait_event_interruptible() (include/linux/wait.h）。最初の引数は待ち行列のヘッドで、2番目の引数は評価される式です。このマクロは、式が真である場合に0を返します。それ以外の場合、 -ERESTARTSYS シグナルが受信された場合を返します。バージョン wait_event() はシグナルを無視します。

シンボル¶

カーネル内部ではリンカの通常のルールに従います（つまり、ファイル内に制限された可視性を持つシンボルでない限り、カーネルのどこでも使用可能です）。ただし、モジュールに関しては、カーネルへのアクセスポイントを制限するエクスポートされたシンボルのテーブルがあります。モジュールもシンボルをエクスポートできます。 staticこれはシンボルをエクスポートする典型的な方法です：ダイナミックにロードされたモジュールもこのシンボルを通常通り使用できます。

プロシージャとコンベンション¶

二重連結リスト include/linux/list.h¶

カーネルのヘッダーファイルにはかつてリスト操作用の3つのグループの関数がありました。しかし、これは最適な選択肢です。単純な連結リストが必要でない限り、この選択肢は適切です。

特に、 list_for_each_entry() は役立ちます。

戻り値のコンベンション¶

ユーザー空間コンテキストから呼ばれるコードでは、Cのコンベンションを無視して、成功時は0を、失敗時は負のエラーコード（例： -EFAULT）を返すことが一般的です。これは最初は逆直感に感じるかもしれませんが、カーネルではよく見られます。

負のエラーコードをポインタにエンコードするには ERR_PTR() (include/linux/err.h)を使用し、 IS_ERR() e PTR_ERR() で再取得します：これにより、エラーコード用の専用ポインタを必要としなくなります。不気味ですが、ポジティブな意味で。

コンパイルを破壊する¶

Linus と他の開発者たちは、開発中のカーネルで関数や構造体の名前を変更することがあります。これは単にすべての人に混乱をもたらすためだけではありません。これは、根拠のある変更を反映しています（例：関数はアクティブな関数で呼ばれることはできなくなりました、または追加のチェックを行ったり、以前に実施されていたチェックを行わなくなりました）。通常、このような変更には、linux-kernel メーリングリストの議論リストに適切で完全な説明が添えられます。アーカイブを確認してください。通常、ファイル全体にわたる単純な置換は状況を悪化させます peggiori.

構造体のフィールドの初期化¶

構造体の初期化には、ISO C99 標準で定義された指定初期化子を使用するのが望ましい方法です。例:

static struct block_device_operations opt_fops = {
        .open               = opt_open,
        .release            = opt_release,
        .ioctl              = opt_ioctl,
        .check_media_change = opt_media_change,
};

これは grep での検索を容易にし、どのフィールドが設定されているかが明確になります。そのため、このような方法を採用すべきです。

GNU 拡張¶

GNU 拡張は Linux カーネル内で明示的に許可されています。注意すべきは、一部の複雑な拡張が開発が進んでいないためサポートが不十分であることです。以下のものは一般的です（詳細については、GCC の info ページの「C Extensions」セクションを参照してください - はい、本当に info ページです、man ページはその内容の要約です）。

  • インライン関数

  • 式内での指令（つまり、({ ... }) の構文）。

  • 関数/変数/型の属性を宣言する（__attribute__ を使用）

  • typeof

  • ゼロ長さの配列

  • マクロ変数引数

  • void ポインタの算術

  • 非定数初期化子

  • アセンブリ指令（'arch/' および 'include/asm/' の外側では使用不可）

  • 関数名を文字列として使用する (__func__)。

  • __builtin_constant_p()

kernel 内での long long の使用は注意が必要です。gcc が生成するコードはひどく、特に i386 プラットフォームでは割り算や乗算が動作しません。

C++¶

通常、kernel 内で C++ を使用するのは悪い考えです。なぜなら、kernel が実行時環境を提供せず、ヘッダーファイルが検証されていないからです。ただし、使用する場合は例外を避けるようにしてください。

NUMif¶

ヘッダーファイル（または .c ファイルの先頭）でマクロを使用して関数を抽象化する方が、ソースコード内に #if 指令を使用するよりも綺麗です。

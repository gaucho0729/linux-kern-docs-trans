シンボルネームスペース¶

このドキュメントでは、EXPORT_SYMBOL() マクロファミリーを使用して、カーネル内部でエクスポートされるものを構造化するためのシンボル名前空間の使用方法について説明します。

1. はじめに¶

シンボル名前空間は、カーネル内部で公開されるAPIを構造化するための手段として導入されました。サブシステムのメンテナがエクスポートするシンボルを複数の名前空間に整理できるようにします。このメカニズムはドキュメンテーション（たとえばSUBSYSTEM_DEBUG名前空間）や、カーネルの他の部分でのシンボルの利用範囲を制限する用途にも有効です。現在、名前空間からエクスポートされたシンボルを使用するモジュールは、まずその名前空間をインポートする必要があります。それにより、カーネルがモジュールのロードを拒否するか、インポート不足をユーザーに警告するのを防ぎます。

2. シンボル名前空間の定義方法¶

シンボルはさまざまなメカニズムで名前空間にエクスポートできます。すべてのメカニズムは、EXPORT_SYMBOL および類似のマクロが ksymtab にエントリを生成する方法を変更します。

2.1 EXPORT_SYMBOL マクロの使用¶

カーネルのシンボルをそれぞれのテーブルにエクスポートするための EXPORT_SYMBOL() および EXPORT_SYMBOL_GPL() マクロに加え、名前空間内にシンボルをエクスポートするための EXPORT_SYMBOL_NS() および EXPORT, SYMBOL_NS_GPL() という変種もあります。これらのマクロは追加の引数である名前空間を必要とします。マクロ展開のため、この引数はプリプロセッサシンボルでなければなりません。たとえば、シンボル usb_stor_suspend を名前空間 USB_STORAGE にエクスポートするには、以下のようにします：

EXPORT_SYMBOL_NS(usb_stor_suspend, USB_STORAGE);

その結果、カーネルのシンボルテーブルには、構造体 kernel_symbol で表されるエントリが追加され、そのフィールド ネームスペース (名前空間) が設定されます。名前空間を指定せずにエクスポートされたシンボルは、このフィールドが NULLに設定されます。基本となる名前空間は存在しません。プログラム modpost および kernel/module.c に含まれるコードは、それぞれコンパイルおよびモジュールのロード時に名前空間を使用します。

2.2 プリプロセッサシンボル DEFAULT_SYMBOL_NAMESPACE の使用¶

サブシステムのすべてのシンボルの名前空間を定義することは、消耗的でメンテナンスが難しい作業です。そのため、ベースとなるプリプロセッサシンボル（DEFAULT_SYMBOL_NAMESPACE）が提供され、これが設定されている場合、EXPORT_SYMBOL() および EXPORT_SYMBOL_GPL() のすべての使用において、明示的に名前空間を指定しない場合のベースとなる名前空間になります。

このプリプロセッサシンボルを指定する方法はいくつかあり、その使用はサブシステムのメンテナの好みに依存します。最初の選択肢は、サブシステムの Makefile Makefile でこのシンボルを定義することです。例えば、usb-common で定義されたすべてのシンボルを USB_COMMON 名前空間にエクスポートするには、drivers/usb/common/Makefile に以下の行を追加します：

ccflags-y += -DDEFAULT_SYMBOL_NAMESPACE=USB_COMMON

これにより、すべての EXPORT_SYMBOL() および EXPORT_SYMBOL_GPL() マクロが変更されます。一方、EXPORT_SYMBOL_NS() でエクスポートされたシンボルは変更されず、指定された名前空間にエクスポートされます。

二番目の選択肢は、コンパイル対象ファイル内で直接プリプロセッサシンボルを定義することです。前の例は以下のようになります：

#undef  DEFAULT_SYMBOL_NAMESPACE
#define DEFAULT_SYMBOL_NAMESPACE USB_COMMON

これは、 EXPORT_SYMBOL のどの使用よりも前に配置する必要があります。

3. 名前空間を介してエクスポートされたシンボルの使用方法¶

名前空間からエクスポートされたシンボルを使用するには、カーネルモジュールが明示的にその名前空間をインポートする必要があります。それ以外の場合、カーネルがモジュールのロードを拒否する可能性があります。モジュールのコードでは、MODULE_IMPORT_NS マクロを使用して、必要なシンボルを含む名前空間をインポートする必要があります。例えば、usb_stor_suspend シンボルを使用するモジュールは、以下の宣言で USB_STORAGE 名前空間をインポートします：

MODULE_IMPORT_NS(USB_STORAGE);

これにより、インポートされたすべての名前空間にラベルが割り当てられます。この事実は、モジュールがインポートした名前空間を modinfo で確認できるという利点があります： modinfo この事実は、モジュールがインポートした名前空間を modinfo で確認できるという利点があります：

$ modinfo drivers/usb/storage/ums-karma.ko
[...]
import_ns:      USB_STORAGE
[...]

MODULE_IMPORT_NS() の宣言は、MODULE_AUTHOR() や MODULE_LICENSE() などのメタデータに近い位置に配置することをお勧めします。自動的に欠落したインポートを生成するには、セクション 5 を参照してください。

4. 名前空間から提供されるシンボルを使用するモジュールのロード¶

モジュールがロードされるとき（例えば、 insmodカーネルが確認します。使用されているすべてのシンボルの利用可能性と、それらを含む可能性のある名前空間がインポートされているかを。カーネルの基本的な動作は、必要なすべての名前空間をインポートしていないモジュールをロードを拒否することです。エラーが記録され、EINVAL エラーでロードが失敗します。この要件を満たしていないモジュールをロードするには、設定オプションを設定します: MODULE_ALLOW_MISSING_NAMESPACE_IMPORTS=y を設定すると、モジュールをロードしますが警告を出します。

5. MODULE_IMPORT_NS の宣言を自動的に作成する¶

コンパイル時にインポートされていない名前空間からのシンボルの使用が検出されます。modpost が警告を出します。MODULE_IMPORT_NS() の宣言は通常、特定の場所に追加されます（他のモジュールメタデータとともに）。モジュールを書く人やサブシステムのメンテナにとっての負担を減らすため、スクリプトと make ビルドターゲットが用意されています。これは以下のコマンドで行えます:

$ make nsdeps

モジュールを書く人の典型的なシナリオは次のとおりです:

- scrivere codice che dipende da un simbolo appartenente ad uno spazio
  dei nomi non importato
- eseguire `make`
- aver notato un avviso da modpost che parla di un'importazione
  mancante
- eseguire `make nsdeps` per aggiungere import nel posto giusto

サブシステムのメンテナが名前空間を追加したい場合、アプローチは似ています。再度、以下のコマンドを実行します: make nsdeps カーネルに含まれるモジュールに不足しているインポートを追加します:

- spostare o aggiungere simboli ad uno spazio dei nomi (per esempio
  usando EXPORT_SYMBOL_NS())
- eseguire `make` (preferibilmente con allmodconfig per coprire tutti
  i moduli del kernel)
- aver notato un avviso da modpost che parla di un'importazione
  mancante
- eseguire `make nsdeps` per aggiungere import nel posto giusto

外部モジュールにも nsdeps を実行できます。通常は次のように使います:

$ make -C <path_to_kernel_src> M=$PWD nsdeps

翻訳者

Linuxの-stableリリースについてのすべての情報¶

「-stable」ソースに受け入れられるか受け入れられないかのパッチの種類に関するルール:

  • もちろん、正しいことである必要があり、確認済みである必要があります。

  • 100行を超えてはいけません（コンテキストを含む）。

  • 1つの問題のみを修正する必要があります。

  • ユーザーに影響を与えている真のバグを修正する必要があります（「これは問題になる可能性があります…」のようなものではありません）。

  • コンパイル問題（すでにCONFIG_BROKENでマークされたもの以外）、カーネルのoops、ブロック、データの破損、真のセキュリティ問題、または「これは良くないですね」のような問題を修正する必要があります。実際には、何か重要な問題を修正する必要があります。

  • 配布版のユーザーが報告した重要な問題は、パフォーマンスやインタラクションに関する重要な問題を修正する場合にのみ考慮されます。ただし、これらの問題は明らかではなく、修正がリグレッションを導く可能性が高いので、配布版のメンテナがバグレポートのリンク（存在すれば）とユーザーへの影響に関する追加情報を含めてのみ提出する必要があります。

  • 「理論的なクリティカルセクション」に関する問題は修正しないでください（その発生方法を説明しない限り）。

  • 「単純な」修正（文法修正、空白文字の整理など）は含めないでください。

  • 以下のルールに従う必要があります パッチ送信：あなたのコードがカーネルに取り込まれるためのエッセンシャルガイド

  • このパッチまたは同等のパッチがすでにLinuxの主要なソースコードに存在している必要があります

「-stable」ソースコード用のパッチの提出手順¶

  • パッチがnet/またはdrivers/netフォルダ内のファイルを変更する場合、以下のガイドラインに従ってください： netdev FAQ；ただし、以下のURLでパッチが既にキューにないか確認した後でなければなりません： https://patchwork.kernel.org/bundle/netdev/stable/?state=*

  • セキュリティパッチは（単に）-stableのレビュープロセスでしか処理されないのではなく、以下の手順に従う必要があります： Bachi di sicurezza.

他のすべてのサブミッションについては、以下のいずれかの手順を選択してください：¶

オプション1¶

パッチが自動的に安定版ソースコードに含まれるようにするには、以下のラベルを追加してください：

Cc: stable@vger.kernel.org

署名用のエリアに追加してください。パッチが含まれると、サブシステムの著者やメンテナが何もしなくても安定版ソースコードに適用されます。

オプション2¶

パッチがLinuxのソースコードに含まれた後、以下にメールを送信してください： stable@vger.kernel.org パッチには、パッチのタイトル、コミットID、パッチを適用すべき理由、そしてどのカーネルバージョンで適用したいかを含める必要があります。

オプション3¶

パッチを送信後、以前に記述したルールを遵守していることを確認した上で、 stable@vger.kernel.orgチェンジログにメインソースのコミットIDを記載し、パッチを適用したいカーネルバージョンも記載する必要があります。

L’オプション1 強く推奨されます；これは最も簡単で一般的な方法です。このオプション2 e l’オプション3 メインソースを含む際、安定版にも含めないべきと判断される場合（たとえば、_regression_の検証がより多く必要とされる場合）に特に有用です。このオプション3 パッチがより古いカーネルに適用するために修正が必要な場合（たとえば、APIが変更されたため）に特に有用です。

メインソースのコミットIDをパッチメッセージの上に記載する必要があります。以下のように：オプション3さらに、一部のパッチは、他のパッチの包含が必要な場合があります。このような状況は、署名エリアで以下のように示すことができます：

ラベルの順序は以下の意味を持ちます：

commit <sha1> upstream.

さらに、一部のパッチはカーネルバージョンに関する要件を持つ場合があります。この要件は、署名エリアで以下の形式で示すことができます：オプション1 ラベルの意味は以下の通りです：

Cc: <stable@vger.kernel.org> # 3.3.x: a1f84a3: sched: Check for idle
Cc: <stable@vger.kernel.org> # 3.3.x: 1b9508f: sched: Rate-limit newidle
Cc: <stable@vger.kernel.org> # 3.3.x: fd21073: sched: Fix affinity logic
Cc: <stable@vger.kernel.org> # 3.3.x
Signed-off-by: Ingo Molnar <mingo@elte.hu>

各「-stable」ソースが指定されたバージョンから始まる場合に適用されます。

git cherry-pick a1f84a3
git cherry-pick 1b9508f
git cherry-pick fd21073
git cherry-pick <this commit>

提出後：

Cc: <stable@vger.kernel.org> # 3.3.x

送信者は、パッチが承認されキューに追加された場合にACKを、拒否された場合にNAKを受信します。開発者の負担によっては、この返信には数日かかることがあります。

git cherry-pick <this commit>

承認された場合、パッチは-stableキューに追加され、他の開発者とそのサブシステムの主要なメンテナによってレビューされます。

レビューのサイクル

  • -stableメンテナがレビューサイクルを実施する場合、パッチはレビュー委員会、パッチ変更に影響を受けるメンテナ（送信者がそのカーネル領域のメンテナである場合を除く）に送信され、linux-kernelディスカッションリストにCCされます。

  • パッチが承認された場合、パッチは-stableキューに追加され、他の開発者とそのサブシステムの主要なメンテナによってレビューされます。

レビューのサイクル¶

  • -stableメンテナがレビューサイクルを実施する場合、パッチはレビュー委員会、パッチ変更に影響を受けるメンテナ（送信者がそのカーネル領域のメンテナである場合を除く）に送信され、linux-kernelディスカッションリストにCCされます。

  • レビューコミッティは、パッチに対してACKまたはNACKを48時間以内に提出する必要があります。

  • コミッティのメンバーがパッチを却下した場合、またはlinux-kernelリストのメンバーがパッチの品質に異議を唱え、メンテナやメンバーが理解していなかった問題を指摘した場合、そのパッチはキューから削除されます。

  • レビューサイクル終了後、ACKを受け取ったすべてのパッチが次の-stableリリースに追加され、その後、この新しいリリースが行われます。

  • セキュリティパッチは、カーネルセキュリティチームが直接-stableソースに受け入れます。通常のレビューサイクルを経ることなく、上記のチームに詳細な手順についてお問い合わせください。

ソース¶

  • パッチのキュー（すでに適用されたものも含む）は次のアドレスで確認できます：

    https://git.kernel.org/pub/scm/linux/kernel/git/stable/stable-queue.git

  • すべての安定版カーネルの正式なリリース（バージョンごとに分かれたブランチ）は次のアドレスで確認できます：

    https://git.kernel.org/pub/scm/linux/kernel/git/stable/linux-stable.git

5. 変更の公開¶

いつかはあなたの作業がコミュニティに提示され、レビューされるだけでなく、メインブランチへの導入も検討される段階がやってきます。予想通り、カーネル開発コミュニティはパッチの公開に関するガイドラインと手順を策定しており、これらを守ることで全員にとっての作業が楽になります。このドキュメントではこれらのトピックを適切な詳細レベルで説明します。さらに詳しい情報は「Documentation」フォルダ内のファイル、 translations/it_IT/process/submitting-patches.rst, translations/it_IT/process/submitting-drivers.rst, e translations/it_IT/process/submit-checklist.rst.

5.1. いつ公開すべきか¶

パッチが本当に「完成」するまで公開するのは抵抗があります。単純なパッチであれば問題ありませんが、複雑な作業の場合は、完成前にコミュニティのフィードバックを得ることで多くの利益があります。未完成の作業を公開するか、関心のある開発者にgitブランチを提供して、いつでも進捗を追跡できるようにするのも有効です。

未完成のコードを公開する際は、その旨を公開時に明記してください。また、未実装の機能や既知の問題についても情報を添えると良いです。中途半端なパッチはあまり見てもらえませんが、見る人はあなたの開発を正しい方向へ導くためのアドバイスをくれるかもしれません。

5.2. パッチを送信する前に¶

コミュニティにパッチを送信する前に、以下の点を確認してください。

  • コードを最大限に検証してください。カーネルのデバッグツールを使用し、すべての現実的なオプションの組み合わせでカーネルがビルドできるか確認し、クロスコンパイラで異なるアーキテクチャ向けにビルドするなどしてください。

  • あなたのコードがカーネルのコードスタイルガイドラインに準拠しているか確認してください。

  • あなたのパッチがパフォーマンスに影響を与える場合は、その影響を示す benchmark を実行し、結果の概要をパッチに含めてください。

  • コードを公開する権利があることを確認してください。この作業が雇用主のために行われた場合、雇用主がこの作業の権利を持ち、GPLライセンスに基づいて公開に同意する必要があります。

一般的なルールとして、コードを送信する前に少し考える方が、ほぼ常に労力に報われるでしょう。

5.3. パッチの準備¶

公開用のパッチの準備には相当な作業が必要になるかもしれませんが、繰り返しますが、この段階で時間を節約するのは一般的に推奨されません。短期間でも同様です。

パッチは特定のカーネルバージョンに基づいて準備する必要があります。一般的なルールとして、パッチはLinusのGitソースにある現在のメインブランチに基づくべきです。メインブランチを基にしている場合、安定したリリースポイントや-rcバージョンから始めることをお勧めします。メインブランチのランダムなポイントから自分のブランチを作成するのではなく、そうすることが望ましいです。

レビューと検証をより広範に進めるために、-mm、linux-next、またはサブシステムのソースコードに基づいたバージョンの作成が必要になる場合があります。これらのソースコードに基づいたパッチの作成には、コンフリクトの解決やAPI変更の修正に相当な作業が必要となり、これはあなたのパッチの分野やカーネルの他の部分での変化に応じて異なります。

最も単純な変更は1つのパッチとして準備すべきですが、それ以外のものは論理的な修正シリーズとして準備する必要があります。パッチを分割することは少し芸術的です。一部の開発者は、コミュニティに好まれる方法を理解するために多くの時間を費やすことがあります。ただし、いくつかの目安はありますが、それらは非常に役立ちます：

  • 公開するパッチシリーズは、あなたのバージョン管理システムに存在するものとはほぼ確実に異なります。代わりに、あなたの変更は最終的な形態で考慮され、意味のある部分に分離される必要があります。開発者たちは、独立した・微細な変更に興味があるのです。あなたがそれらを取得するために経た道ではなく、変更そのものに注目します。

  • 論理的に独立した変更は、それぞれ別のパッチとして作成すべきです。これらの変更は、小さなもの（「この構造にフィールドを追加した」など）でも、大きなもの（新しいドライバの追加など）でも構いませんが、概念的に小さく、1行で説明できるべきです。それぞれのパッチは、独立してレビュー可能な特定の変更を含むべきです。

  • 上で述べたことを改めて強調しますが、1つのパッチに複数種類の変更を混ぜるのは避けてください。たとえば、セキュリティ上の重大なバグの修正、構造の再編、コードのフォーマット変更を1つのパッチに含めると、修正が無視され、重要な修正が失われる可能性があります。

  • それぞれの変更は、コンパイル・動作する正しいカーネルをもたらすべきです。パッチシリーズが途中で中断しても、結果として常に動作するカーネルを保つべきです。パッチシリーズの一部を適用した状態で問題が発生した場合、"git bisect"コマンドがリグレッションを検出するシナリオがよくあります。カーネルが破損している場合、開発者の作業を難しくし、問題を特定する作業を困難にします。

  • ただし、過剰にパッチを分割しないでください。以前、開発者が1つのファイルを変更するための500パッチを投稿したことがあります。その結果、カーネルディスカッションリストで彼は人気を博しませんでした。1つのパッチは単一の変更を含む限り、適切に大きなサイズでも問題ありません。 論理的.

  • 新しいインフラストラクチャをパッチシリーズとして追加する考えは魅力的ですが、最後のパッチがすべてを有効化するまでそのインフラストラクチャを無駄にしているのは避けたほうがいいです。可能な限り、この方法は避けてください。このシリーズがリグレッションを引き起こす場合、"bisect"は最後のパッチを問題の原因と誤って特定します。新しいコードを追加するパッチは、すぐにそのコードを有効にするべきです。

完璧なパッチシリーズを作成する作業は、時間がかかりストレスがかかるため、挫折する可能性があります。ただし、丁寧に作成すれば、時間を無駄にしない価値のある作業です。

5.4. パッチのフォーマットと変更履歴¶

これで、公開用の完全なパッチセットが完成しましたが、作業は本当に終わりではありません。すべてのパッチには、その目的を明確かつ迅速に世界に伝えるメッセージを添える必要があります。このメッセージを取得するため、各パッチには以下の要素が含まれます。

  • パッチの著者の名前を記載するオプションの「From」フィールド。この行は、メールで他人のパッチを送る場合にのみ必要ですが、疑いがある場合は追加しておくとよいでしょう。

  • パッチが行う動作を説明する1行の説明。このメッセージは、他の情報なしで読者にパッチの目的を理解させるために十分であるべきです。通常、このメッセージは、関連するサブシステムの名前を先頭にし、パッチの目的を記載します。例えば：

    gpio: fix build on CONFIG_GPIO_SYSFS=n

  • 空行の後にパッチの詳細な説明を記載します。この説明は必要に応じて長くても構いません。パッチが行う動作と、なぜカーネルに追加すべきかを説明する必要があります。

  • 1行以上のラベル、少なくとも1行は必要です Signed-off-by: パッチの著者の名前。これらのラベルについては後ほど詳しく説明します。

上記の要素を合わせて、パッチの変更履歴（changelog）となります。良い変更履歴を書くことは非常に重要ですが、しばしば見過ごされがちです。この点については少し時間をかけて考える価値があります。変更履歴を書く際には、多くの人があなたの文章を読むことを意識すべきです。これらには、サブシステムのメンテナーや、パッチを含めるべきかを判断するレビュアー、配布版や他のメンテナーが、古いカーネルにこのパッチを適用すべきかを評価する人、バグを追跡する開発者などが含まれます。良い変更履歴は、これらすべての人々に、最も直接的かつ簡潔な形で必要な情報を提供します。

この目的のために、要約行は1行の制限にもかかわらず、変更の影響とパッチの理由をできるだけ丁寧に説明する必要があります。詳細な説明は、テーマをより明確にし、追加の情報を提供します。パッチがバグを修正する場合、可能であれば、そのバグを導入したコミットを引用してください（コミットを引用する際は、識別子とタイトルの両方を含めてください）。問題がログファイルやコンパイラの出力と関連している場合、それらを含めることで、他の人が同じ問題の解決策を見つけるのを助けることができます。パッチが今後の開発をサポートする目的であれば、それを明記してください。内部APIが変更された場合、その変更内容と、他の開発者がそれを適用するための対応方法を詳しく説明してください。一般的に、あなたの変更履歴が誰かの目を通して読まれるようになればするほど、変更履歴（そして全体のカーネル）は良くなります。

言うまでもありませんが、変更履歴はバージョン管理システムにおけるコミットメッセージとして使用されるべきです。続いて以下の内容が続きます：

  • パッチ自体で、パッチ形式（"-u"）の統一フォーマットで記載してください。"-p"オプションを使用すると、関連する関数名が変更に結びつけられ、他の人にとって読みやすくなります。

パッチには、関係のないファイル（例：生成プロセスで生成されたファイルや、エディタのバックアップファイルなど）の変更は含めないでください。Documentationフォルダ内の"dontdiff"ファイルを"-X"オプションとともにdiffに渡すことで、この点を助けることができます。

上記のラベルは、パッチの開発に関与した各開発者を関連付けるために使用されます。詳細は以下のドキュメントで説明されています。 translations/it_IT/process/submitting-patches.rst; 以下に、それぞれの行のフォーマットの簡単なまとめを示します。

tag: Full Name <email address>  optional-other-stuff

よく使われるラベルは以下の通りです：

  • Signed-off-by: このラベルは、開発者がパッチをカーネルへの統合に提出する権限があることを認証します。これは開発者のソースコードの認証への同意を表します。詳細は以下のドキュメントで確認できます。 パッチ送信：あなたのコードがカーネルに取り込まれるためのエッセンシャルガイド. 適切な署名が付いていないコードは統合されません。

  • Co-developed-by: は、パッチが複数の開発者によって共同で作成されたことを示します。複数の人がパッチに貢献した場合、このラベルを使用して複数の著者を指定します（From: に記載された著者とは別に）。各 Co-developed-by: は、対応する共同著者の Signed-off-by: で直ちに続きます。詳細な説明や例については パッチ送信：あなたのコードがカーネルに取り込まれるためのエッセンシャルガイド.

  • Acked-by: は、他の開発者（しばしば対象コードのメンテナ）がパッチをカーネルに統合することを承認したことを示します。

  • Tested-by: は、パッチをテストし、動作していることを確認した人物を示します。

  • Reviewed-by: は、パッチをレビューした開発者を示します。詳細については、レビュアーの声明を パッチ送信：あなたのコードがカーネルに取り込まれるためのエッセンシャルガイド

  • Reported-by: は、このパッチで修正された問題を報告したユーザーを示します。このラベルは、コードを確認し、問題が正しく動作しなかったことを報告した人々への貢献を称揚するためのものです。

  • Cc: に記載された人物は、パッチのコピーを受け取り、コメントする機会がありました。

パッチにこれらのラベルを追加する際は注意してください: 『Cc:』は、記載された人物の明示的な許可なしに追加できます。

5.5. 変更を送信する¶

パッチを送信する前に、まだいくつか注意すべきことがあります:

  • メールクライアントがパッチを破壊していないか確認してください。メールクライアントが空白や余分な改行を追加すると、受信者がパッチを正しく受け取れず、通常は詳細な検討もされません。何か疑いがある場合は、自分自身にパッチを送って、整合性を確認してください。

    Linux用メールソフトに関する情報 メールクライアントの設定に関するいくつかのヒントが含まれています。

  • パッチに明らかなエラーがないか確認してください。常に scripts/checkpatch.pl でパッチを処理し、指摘された問題を修正してください。checkpatch.pl はあなたの知識以上に賢くありませんが、ある程度の論理に基づいています。checkpatch.pl のアドバイスを従うことでコードが悪化する場合は、無視してください。

パッチは常に純粋なテキストとして送信する必要があります。添付ファイルとして送信しないでください。これは、レビュアーがコメントしたいパッチの一部を引用するのを非常に困難にします。代わりに、パッチをメッセージ本文に直接含めてください。

パッチを送信する際には、関係するすべての人にコピーを送る必要があります。他のプロジェクトとは異なり、カーネルは多くのコピーを送る行為を奨励しています。関係者にあなたのメッセージがディスカッションリストで見られるとは思わないでください。特に、以下の人にコピーを送るべきです:

  • 変更が影響を与えるサブシステムのメンテナ。前述の通り、MAINTAINERSファイルはこれらの人物の名前を探す最初の場所です。

  • 同じ環境で作業した他の開発者 - 特に現在その環境で作業している可能性のある人々。gitを使用して、あなたが作業しているファイルを変更した他の人々を確認するのに役立ちます。

  • バグレポートや機能要望への返信をしている場合、それらのレポートや要望の著者にもコピーを送るべきです。

  • 関連するディスカッションリストにコピーを送るべきです。それ以外の選択肢がなければ、linux-kernelリストに送るのも良いでしょう。

  • バグを修正している場合、このパッチが次の安定版リリースに含めるべきかどうかを検討してください。そうであれば、ディスカッションリストにコピーを送るべきです。 stable@vger.kernel.org パッチ自体に「Cc:」というラベルを追加してください。これにより、この修正がメインブランチに統合される際、チームが通知を受けられます。 stable@vger.kernel.org「Cc:」というラベルをパッチに追加してください。これにより、この修正がメインブランチに統合される際、チームが通知を受けられます。 stable チームがこの修正がメインブランチに統合される際、通知を受けられるようにします。

パッチの送信先を選ぶ際には、最終的にあなたのパッチを承認し、統合する人物を想定しておくことが重要です。直接Linus Torvaldsにパッチを送って彼が統合するという選択肢はありますが、通常は最良の選択ではありません。Linusは忙しく、特定のカーネル部分を管理するサブシステムのメンテナがいます。通常は、これらのメンテナがあなたのパッチを統合するようにしたいです。メンテナが明確でない場合は、Andrew Mortonが最後の選択肢となることがよくあります。

パッチには良いサブジェクトが必要です。パッチのサブジェクトの典型的なフォーマットは以下の通りです:

[PATCH nn/mm] subsys: one-line description of the patch

ここで「nn」はパッチの順序番号、「mm」はシリーズ内のパッチ総数、「subsys」は関係するサブシステムの名前です。明らかに、単一のパッチを含むシリーズの場合は「nn/mm」は省略できます。

重要なパッチのシリーズがある場合、導入部分としての説明を含めることが一般的ですが、この慣習は universally ではありません。導入部分の情報はカーネルの changelog に含まれませんので、ご注意ください。そのため、各パッチが完全な changelog を持つようにしてください。

複合的なパッチの第二部およびそれ以降の部分は、最初のパッチに対する返信として送信すべきです。これにより、1つの単位として扱われます。 ビットマスクで追跡するgit や quilt などのツールには、適切な構造を持つパッチグループを送信するためのコマンドがあります。長期間のパッチを git で使用している場合は、--chain-reply-to オプションは避け、過剰なネストを防ぎましょう。

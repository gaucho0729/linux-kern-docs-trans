新しいシステムコールを追加する¶

このドキュメントでは、Linux カーネルに新しいシステムコールを追加するために必要な知識を説明しています。これは、新しい変更を提案するための通常のアドバイスに加えて、追加の情報を提供しています。 パッチ送信：あなたのコードがカーネルに取り込まれるためのエッセンシャルガイド.

システムコールの代替案¶

新しいシステムコールを追加する際の最初の考慮点は、代替案を評価することです。システムコールはユーザー空間とカーネルの間の伝統的で明白なインターフェースですが、他の選択肢もあります。自分たちのインターフェースに最も適したものを選ぶべきです。

  • 関連する操作がファイルシステムのそれと似ている場合、新しいファイルシステムやデバイスの作成の方が意味があります。また、この方法により、新しい機能をカーネルモジュールにまとめやすくなり、カーネルの中心部で開発するよりも簡単になります。

    • 新しい機能が、カーネルがイベントに基づいてユーザー空間に通知する操作を含む場合、対応するオブジェクトにファイルディスクリプタを返すことで、ユーザー空間がその通知を受信できるようになります。 poll/select/epoll その通知を受信するため。

    • ただし、タイプの操作とよく合うわけではない操作については、 read(2)/write(2) これらは呼び出しとして実装すべきです。 ioctl(2)、これはAPIがやや曖昧になる可能性があります。

  • システム情報のみを公開する必要がある場合、sysfs（参照 Documentation/filesystems/sysfs.rst) または procfs に新しいノードを追加するだけで十分かもしれません。ただし、これらのメカニズムへのアクセスには、ファイルシステムがマウントされている必要があります。常にそうとは限りません（たとえば、namespace/sandbox/chroot などの環境では）。debugfs に新しいAPIを追加するのは避けてください。これはユーザー空間に対する「生産用」インターフェースとは見なされません。

  • 特定のファイルまたはディスクリプタに特化した操作の場合、コマンドの追加が適切かもしれません。 fcntl(2)。ただし、 fcntl(2) これはマルチプレクターベースのシステムコールであり、相当な複雑さを隠しています。そのため、新しい機能が既存のそれらに似ている場合、または本当にシンプルな機能（たとえば、ファイルディスクリプタに関連する簡単なフラグの読み書き）である場合にのみ有効です。 fcntl(2)、または新しい機能が本当にシンプルな場合（たとえば、ファイルディスクリプタに関連する簡単なフラグの読み書き）です。

  • 特定のプロセスに特化した操作の場合、コマンドの追加が適切かもしれません。 prctl(2)。これは fcntl(2)、このシステムコールはマルチプレクターベースの複雑なものです。そのため、既存のコマンドと非常に似たものにのみ使用するべきです。 prctl または、プロセスに関連する単純なフラグを読み書きするため。

APIを設計する: 拡張機能の計画¶

新しいシステムコールはカーネルAPIの一部となり、無期限にサポートされる必要があります。そのため、カーネルのディスカッションリストでインターフェースを公開して議論することが非常に良い考えです。また、今後の拡張機能も計画しておくことが同様に重要です。

(システムコールのテーブルには、このようなことが行われなかった例と、対応する更新が含まれています - eventfd/eventfd2, dup2/dup3, inotify_init/inotify_init1, pipe/pipe2, renameat/renameat2 –そのため、カーネルの歴史を学び、拡張機能を最初から計画してください)

単純なシステムコールで2つの引数しか受け取らない場合、拡張性を確保するには、システムコールに1つ追加の引数を含めるのが最善です。 フラグ ユーザー空間のプログラムが、さまざまなカーネルバージョンで安全に使用できるようにするためには、 フラグ 引数に未知の値が含まれているか確認し、その場合はシステムコールを拒否してください（ フラグ カーネルバージョンがまだ使われていない場合、引数がゼロであることを確認してください） EINVAL):

if (flags & ~(THING_FLAG1 | THING_FLAG2 | THING_FLAG3))
    return -EINVAL;

(もし フラグ がまだ使われていない場合、引数がゼロであることを確認してください）

より複雑なシステムコールで多くの引数を扱う場合、ほとんどの引数をデータ構造にまとめ、ポインタで渡すのが最善です。このデータ構造は今後の拡張にも対応できるように、ゼロを意味するフィールドを含めることで実現できます。 size:

struct xyzzy_params {
    u32 size; /* userspace sets p->size = sizeof(struct xyzzy_params) */
    u32 param_1;
    u64 param_2;
    u64 param_3;
};

新しいフィールドが追加されても、ゼロの場合は以前の動作を維持するように設計されている限り、 param_4、このアプローチは両方向のバージョンコンフリクトを処理できます。

  • 古いカーネルは、ユーザー空間の新しいプログラムのアクセスを処理する際、予想されるデータ構造のサイズを超えたメモリがゼロであることを確認することで、 param_4 == 0).

  • 新しいカーネルは、ユーザー空間の古いプログラムのアクセスを処理する際、ゼロで埋めたデータ構造を拡張することで、 param_4 = 0).

を参照してください perf_event_open(2) および関数 perf_copy_attr() (in kernel/events/core.c) でこのアプローチの実際の例を確認してください。

APIを設計する: その他の考慮事項¶

新しいシステムコールがユーザー空間からカーネルオブジェクトを参照できる場合、ファイルディスクリプタを使用してオブジェクトにアクセスする必要があります。カーネルが既に明確なセマンティクスを持つファイルディスクリプタメカニズムを持っているため、ユーザー空間から独自のアクセスタイプを新たに設計しないでください。

新しいシステムコールが xyzzy(2) 新しいファイルディスクリプタを返す場合、引数 フラグ これは、同等の値を含めるべきです O_CLOEXEC 新しいディスクリプタについて。これにより、ユーザー空間において、呼び出し間のタイムアウトの閉じ方が可能になります xyzzy() e fcntl(fd, F_SETFD, FD_CLOEXEC)ここで予期せぬ fork() o execve() がディスクリプタを実行中のプログラムに転送する可能性があります（ただし、アーキテクチャ固有の値を再利用しないでください O_CLOEXEC これはアーキテクチャ固有であり、フラグの列挙に属するため O_* これは十分に豊富なため）。

新しいシステムコールがファイルディスクリプタを返す場合、システムコールファミリーの使用意義を検討すべきです poll(2)ファイルディスクリプタを読み取りまたは書き込み用に準備することは、カーネルがユーザー空間にカーネルオブジェクトに関連するイベントを通知する典型的な方法です

新しいシステムコールが xyzzy(2) 引数はファイルへのパスです:

int sys_xyzzy(const char __user *path, ..., unsigned int flags);

さらに、より適切なバージョンを検討すべきです xyzzyat(2):

int sys_xyzzyat(int dfd, const char __user *path, ..., unsigned int flags);

これにより、ユーザー空間がファイルを指定する方法に柔軟性が生まれます。特に、既に開かれたファイルディスクリプタに対して機能を要求できるようになります フラグ AT_EMPTY_PATH、実際には、無料で操作を取得できます fxyzzy(3):

- xyzzyat(AT_FDCWD, path, ..., 0) is equivalent to xyzzy(path,...)
- xyzzyat(fd, "", ..., AT_EMPTY_PATH) is equivalent to fxyzzy(fd, ...)

（*at() のロジックについての詳細は、man ページを参照してください openat(2)；AT_EMPTY_PATH の例については、man ページを参照してください fstatat(2)).

新しいシステムコールが xyzzy(2) ファイル内のオフセットを記述するパラメータを備える場合、 loff_t タイプとして使用し、64ビットのオフセットを32ビットアーキテクチャでもサポート可能にします

新しいシステムコールが xyzzy(2) 特殊な関数を使用する場合、適切な特権ビットで管理する必要があります（chiamata a で確認） capable()）により、対象プロセスと同じ権限を持つ呼び出し元プロセス、または必要な特権を持つプロセスのみが操作できるようになります capabilities(7)既存の特権ビットで関連機能を管理すべきですが、弱い関連性を持つ機能を同一ビットで組み合わせるのは、root の権限分離の原則に反します 機能 非常に一般的な特権である fin-troppo-generico を新たな用途に追加しないでください CAP_SYS_ADMIN.

新しいシステムコールが xyzzy(2) 他のプロセスを操作する機能を備える場合、制限（chiamata a による）を設けるべきです ptrace_may_access()）により、対象プロセスと同じ権限を持つ呼び出し元プロセス、または必要な特権を持つプロセスのみが操作できるようになります

最後に、非x86アーキテクチャでは、64ビットの引数を持つシステムコールのライフサイクルが、これらの引数が奇数位置にある場合（実際にはパラメータ1、3、5）に簡略化されることがあります。これにより、連続する32ビットレジスタのペアを使用できるようになります。（ただし、引数がポインタで渡される構造体の一部である場合はこの限りではありません）。

APIを提案する¶

新しいシステムコールの変更を容易にレビューできるようにするため、変更内容をセグメントごとに分けてください。これらには少なくとも以下の項目を含める必要があります： コミット 分離して（それぞれ後述します）：

  • システムコールの実装の本質、プロトタイプ、汎用的な番号、Kconfigの変更、および実装 スタブ フォールバック。

  • 特定のアーキテクチャ（通常はx86、つまりx86_64、x86_32、x32）向けに新しいシステムコールを準備する

  • 自動検証プログラムを設置する tools/testing/selftests/ システムコールの使用例を示す

  • 新しいシステムコール用のmanページのドラフト。これはプレゼンテーションメールに記載するか、manページのリポジトリへの直接の修正として作成できます。

新しいシステムコールの提案は、カーネルAPIの他の変更と同様に、ディスカッションリストに提出する必要があります linux-api@vger.kernel.org.

汎用システムコールの実装¶

新しいシステムコールの主なアクセスポイント xyzzy(2) 呼ばれる sys_xyzzy()；ただし、明示的にではなく、マクロ SYSCALL_DEFINEnを通じて追加します。'n'はシステムコールの引数の数を示し、マクロの引数にはシステムコール名の後に（型、名前）のペアでパラメータを定義します。このマクロの使用により、他のツールでも新しいシステムコールのメタデータが利用可能になります。

新しいアクセスポイントには、 include/linux/syscalls.hヘッダーファイルに含まれる関数プロトタイプが必要で、asmlinkageとしてマークすることで、そのシステムコールがどのように呼び出されるかに合わせます：

asmlinkage long sys_xyzzy(...);

一部のアーキテクチャ（例：x86）では、独自のシステムコールテーブルがありますが、多くの他のアーキテクチャでは汎用的なシステムコールテーブルを共有します。汎用テーブルに新しいシステムコールを追加するには、 include/uapi/asm-generic/unistd.h:

#define __NR_xyzzy 292
__SYSCALL(__NR_xyzzy, sys_xyzzy)

____NR_syscallsのカウンターも更新し、新しいシステムコールの追加に合わせて整合性を保つ必要があります。注意点として、複数の新しいシステムコールが同じ開発ウィンドウで追加された場合、あなたの新しいシステムコールの番号が競合を解決するために調整される可能性があります。

ファイル kernel/sys_ni.c 実装を提供します スタブ バックアップとして戻る -ENOSYS. 新しいシステムコールを以下にも追加してください：

COND_SYSCALL(xyzzy);

あなたの新しいカーネル機能とそれに伴うシステムコールはオプションで提供すべきです。そのため、オプション CONFIG (通常は init/Kconfig). 新しいオプションについてはいつも通り、 CONFIG:

  • 新しい機能とそれに伴うシステムコールの説明を含めてください。

  • ユーザーに隠す必要がある場合は、このオプションをEXPERTに依存させます。

  • Makefileにおいて、新しい機能を実装するすべてのソースファイルをCONFIGオプションに依存させます（例： obj-$(CONFIG_XYZZY_SYSCALL) += xyzzy.o).

  • 新しいCONFIGオプションを無効にした状態でもカーネルが生成可能であることを確認してください。

要約すると、あなたには コミット を含む必要があります：

  • オプション CONFIG``per la nuova funzione, normalmente in ``init/Kconfig

  • SYSCALL_DEFINEn(xyzzy, ...) アクセスポイント

  • の対応するプロトタイプ include/linux/syscalls.h

  • の一般的なテーブル内の要素 include/uapi/asm-generic/unistd.h

  • スタブ のバックアップ kernel/sys_ni.c

x86システムコールの実装¶

新しいシステムコールをx86プラットフォームに接続するには、主なシステムコールテーブルを更新する必要があります。新しいシステムコールが特に特殊でない場合（以下を参照）、arch/x86/entry/syscalls/syscall_64.tblにx86_64およびx32用の要素を追加してください： 通常 および

333   common   xyzzy     sys_xyzzy

の要素を追加してください i386 arch/x86/entry/syscalls/syscall_32.tbl:

380   i386     xyzzy     sys_xyzzy

これらの番号は、統合ウィンドウでの競合により変更される可能性があります。

互換性のあるシステムコール（汎用）¶

多くのシステムコールでは、32ビットのユーザー空間アプリケーションが64ビットの実装を呼び出すことができます。システムコールが明示的にポインタを含んでも、これは透過的に処理されます。

ただし、32ビットと64ビットのサイズ差を解決するために互換性レベルが必要な状況はいくつかあります。

最初のケースは、64ビットのカーネルが32ビットのユーザー空間アプリケーションもサポートする場合で、メモリの領域（__user)を検査しなければならないため、その中には32ビットまたは64ビットの値が含まれる可能性があります。特に、システムコールの引数が

  • ポインタのポインタ

  • データ構造を含むポインタ（例えば struct iovec __user *)

  • 可変長整数型のポインタ（time_t, off_t, long, …)

  • データ構造を含む可変長整数型のポインタ。

2番目の互換性管理レベルが必要なケースは、システムコールの引数が32ビットアーキテクチャでも64ビット型である場合です（例えば loff_t o __u64. この場合、32ビットアプリケーションから64ビットカーネルへ送られる値は、2つの32ビット値に分割され、この互換性レベルで再構成される必要があります。

(64ビット型のポインタである引数にはこの互換性レベルは必要ありません；例えば、 splice(2) 型の引数 loff_t __user * システムコールを必要としません compat_)

私たちのシステムコールの互換性バージョンは compat_sys_xyzzy()と呼ばれ、マクロ COMPAT_SYSCALL_DEFINEn() (SYSCALL_DEFINEnに似たもの) を使って追加されます。この実装バージョンは64ビットカーネルの一部ですが、32ビットパラメータを受け入れて必要に応じて変換します（通常、 compat_sys_ はこれらの値を64ビットに変換し、 sys_ バージョンを呼び出すか、共通部分を実装する関数を呼び出します）。

エントリポイント compat は、 include/linux/compat.hヘッダーファイルに含まれる関数プロトタイプが必要で、asmlinkageとしてマークすることで、そのシステムコールがどのように呼び出されるかに合わせます：

asmlinkage long compat_sys_xyzzy(...);

に該当する関数プロトタイプを備える必要があります。 struct xyzzy_argsシステムコールが32ビットと64ビットのシステムでデータ構造を異なる方法で構成する場合（例えば then the include/linux/compat.h ヘッダーファイル 互換性バージョンを含める必要があります； (struct compat_xyzzy_argsの変数で可変長なものはそれぞれ compat_ に該当する型を備える必要があります。 struct xyzzy_args関数 compat_sys_xyzzy() は、 compat_ 構造体を使用して32ビット呼び出しの引数を解析できます。

例えば、以下のフィールドがある場合：

struct xyzzy_args {
    const char __user *ptr;
    __kernel_long_t varying_val;
    u64 fixed_val;
    /* ... */
};

構造体 struct xyzzy_argsでは、 struct compat_xyzzy_args 以下のようにする必要があります：

struct compat_xyzzy_args {
    compat_uptr_t ptr;
    compat_long_t varying_val;
    u64 fixed_val;
    /* ... */
};

一般的なシステムコールリストは、バージョン 互換性バージョンを含める必要があります；の使用を可能にするために調整必要があります； include/uapi/asm-generic/unistd.h のエントリは __SC_COMP ではなく __SYSCALL:

#define __NR_xyzzy 292
__SC_COMP(__NR_xyzzy, sys_xyzzy, compat_sys_xyzzy)

まとめると、以下が必要です：

  • 一つの COMPAT_SYSCALL_DEFINEn(xyzzy, ...) アクセスポイント 互換性バージョンを含める必要があります；

  • プロトタイプを include/linux/compat.h

  • (必要に応じて) 32ビット互換構造体を include/linux/compat.h

  • エントリを __SC_COMPではなく __SYSCALL、 include/uapi/asm-generic/unistd.h

システムコールの互換性 (x86)¶

x86アーキテクチャでシステムコールをそのバージョンとリンクするには、 互換性バージョンを含める必要があります；シスコールテーブル内のエントリを調整する必要があります。

まず、以下の項目に arch/x86/entry/syscalls/syscall_32.tbl 追加の引数を指定して、32ビットのユーザー空間で実行されるプログラムが64ビットのカーネル上で実行される際、64ビット互換のアクセスポイントを通じてアクセスする必要があります:

380   i386     xyzzy     sys_xyzzy    __ia32_compat_sys_xyzzy

次に、ABI x32版の新しいシステムコールがどのように動作するかを理解する必要があります。ここでは選択肢があります: 引数は64ビット版か32ビット版のどちらに合わせるべきかです。

ポインタのポインタがある場合、選択は簡単です: x32はILP32であり、したがって引数は32ビット版に合わせるべきです。このため、以下の項目に arch/x86/entry/syscalls/syscall_64.tbl 分割され、x32のプログラムがシステムコールを実行できるようになります。 互換性バージョンを含める必要があります；:

333   64       xyzzy     sys_xyzzy
...
555   x32      xyzzy     __x32_compat_sys_xyzzy

ポインタがなければ、x32のABI用に64ビットのシステムコールを再利用するのが望ましいです（結果として、arch/x86/entry/syscalls/syscall_64.tblの項目は変更されません）。

いずれの場合も、引数で使用される型がx32（-mx32）から32ビット（-m32）または64ビット（-m64）に正確に対応しているかを確認する必要があります。

他の場所に戻るシステムコール¶

ほとんどのシステムコールでは、ユーザー空間のプログラムが実行終了後に正確に中断した場所から再開します。つまり、次の命令から再開し、 stack 同じレジスタの多くを呼び出し前と同様に保持し、同じ仮想メモリも保持します。

ただし、一部のシステムコールは異なる方法で動作します。異なる場所（rt_sigreturn)に戻るか、fork/vfork/clone)ユーザー空間のメモリを変更するか、execve/execveat).

)さらにはプログラムのアーキテクチャを変更する可能性があります。このような動作を可能にするため、カーネル内のこの種のシステムコールの実装では、 stack カーネルの領域で追加のレジスタを保存・復元する必要があり、システムコール実行後の実行継続先の場所や方法を完全に制御できるようになります。

これらはすべてアーキテクチャごとに異なりますが、通常は アセンブリ で追加のレジスタを保存・復元し、その後システムコールの本番のアクセスポイントを呼び出すことで実装されます。

x86_64アーキテクチャでは、これは stub_xyzzy の arch/x86/entry/entry_64.Sのアクセスポイントとして実装され、arch/x86/entry/syscalls/syscall_64.tblのテーブル項目はそれに応じて修正されます:

333   common   xyzzy     stub_xyzzy

64ビットカーネル上で実行される32ビットプログラムの同等物は通常 stub32_xyzzy と呼ばれ、 arch/x86/entry/entry_64_compat.S で実装され、 arch/x86/entry/syscalls/syscall_32.tbl のテーブル項目は以下のようになります:

380   i386     xyzzy     sys_xyzzy    stub32_xyzzy

システムコールが互換性レベル（前のセクションのように）が必要な場合、そのバージョン stub32_ は、64ビットネイティブ版ではなく、 compat_sys_ を呼び出す必要があります。さらに、ABI x32の実装がx86_64とは異なる場合、システムコールテーブルのそのエントリは、 スタブ を呼び出す必要があります。 compat_sys_,

完全性を保つために、マッピングを設定するのが良いでしょう。そうすれば、 ユーザーモード Linux（UML）が動作し続けることができます。そのシステムコールテーブルはstub_xyzzyを参照しますが、UMLはその実装を含んでいません（UMLはレジスタなどをシミュレートするため）。これを修正するのは簡単で、 arch/x86/entry/entry_64.S に#defineを追加するだけです。 arch/x86/um/sys_call_table_64.c:

#define stub_xyzzy sys_xyzzy

他の詳細¶

ほとんどのカーネルはシステムコールを同じように処理しますが、まれな例外がある場合、システムコールの更新が必要になるかもしれません。

制御サブシステム（audit subsystem）はそのような特別なケースの一つです。このサブシステムは（アーキテクチャごとに）ファイルのオープン（open/openat）、プログラムの実行（execve/exeveat）やソケットマルチプレクサ（socketcall）などの一部のシステムコールを分類する機能を含みます。もし新しいシステムコールがこれらに似ているなら、制御サブシステムも更新する必要があります。

より一般的に、もし類似したシステムコールが既にあるなら、 grep で検索し、他の特別なケースがないか確認しましょう。

検証¶

新しいシステムコールは、もちろんテストが必要です。レビュワーにそのシステムコールの使用例を示すユーザースペースのプログラムを提供すると役立ちます。これらを組み合わせる良い方法は、 tools/testing/selftests/.

に新しいフォルダを作成し、簡単な自己検証プログラムを追加することです。 syscall()新しいシステムコールにはlibcの関数がありませんので、検証プログラムは

で呼び出す必要があります。さらに、新しいシステムコールがユーザースペースで見える新しいデータ構造を含む場合、そのヘッダーファイルをインストールしてコンパイルできるようにする必要があります。すべてのサポートされるアーキテクチャで自己検証プログラムが動作することを確認してください。たとえば、x86_64（-m64）、x86_32（-m32）およびx32（-mx32）でコンパイルして動作することを確認してください。

新しい機能のより詳細な検証を行うためには、'Linux Test'プロジェクトまたはxfstestsプロジェクトに新しいテストを追加することを検討してください。これはファイルシステムに関する変更に関連するものです。

man ページ¶

すべての新しいシステムコールには、groffマーカーを使用した完全なmanページが理想ですが、純粋なテキストでも問題ありません。groffを使用している場合は、提出メールにASCII形式に変換済みのバージョンを添付しておくと、レビュアーの作業が楽になります。

manページはcopyleft形式で公開する必要があります linux-man@vger.kernel.org 詳細については、以下のリンクを参照してください https://www.kernel.org/doc/man-pages/patches.html

カーネル内部からシステムコールを呼び出さないでください¶

システムコールは、すでに述べたようにユーザー空間とカーネルの間のインターフェースです。したがって、以下のシステムコールは sys_xyzzy() o compat_sys_xyzzy() ユーザー空間からsyscallテーブルを通じてのみ呼び出されるべきであり、カーネル内部のどこからでも呼び出さないでください。新しい機能がカーネル内部で必要であれば（例えば、古いシステムコールと新しいシステムコールの間で共有される必要がある場合、またはシステムコールとその互換性バージョンで使用される場合）、サポート用の関数（helper function)（例: kern_xyzzy())として実装する必要があります。この関数は、 スタブ (sys_xyzzy())、互換性バージョン（compat_sys_xyzzy())、および/またはカーネルの他の部分から呼び出すことができます。

x86-64ビットシステムでは、v4.17以降、カーネル内部でシステムコールを呼び出すことは必須ではありません。カーネルは、システムコールの呼び出しを別の方法で処理しており、 struct pt_regs その場でデコードして、実行されるシステムコールを含む関数に変換します。これにより、特定のシステムコールに必要なパラメータのみが渡され、ユーザー空間からプロセッサの6つのレジスタを毎回埋める必要がなくなり、呼び出しの順序に深刻な問題を引き起こす可能性が低くなります。

さらに、カーネルとユーザー空間ではデータの使用規則が異なる可能性があります。これが、システムコールを呼び出すことが一般的に悪いアイデアである理由の一つです。 sys_xyzzy() この規則の例外は、アーキテクチャ固有の機能、互換性関連の機能、またはarch/ディレクトリ内のその他のコードに限られます

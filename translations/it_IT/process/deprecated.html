非推奨インターフェース、言語の特徴、属性、および慣例¶

理想的な世界では、非推奨インターフェースのすべての使用例を新しいインターフェースに変換し、1つの開発サイクルで古いインターフェースを削除できるはずですが、カーネルの規模、メンテナの階層、スケジュールの制約により、このような変換を一度で行うことは常に可能ではありません。これにより、古いインターフェースの新しいインスタンスがカーネルに追加される可能性があり、作業負荷が増加します。そのため、開発者に何が非推奨とされ、その理由を説明するため、以下のリストが作成され、非推奨の要素を使用する変更を提案する際の参考としています。

__deprecated¶

この属性は非推奨インターフェースを目立つようにマークしますが、 コンパイル時に警告を出さなくなりました なぜなら、カーネルの目標の一つが警告なしにコンパイルすることであり、またこれらのインターフェースを削除するためのアクションは誰も取っていません。非推奨の使用が __deprecated ヘッダーファイルでインターフェースを「古い」とマークすることは、一時的な対策に過ぎません。インターフェースはカーネルから削除する必要があります、またはこのドキュメントに記載することでその使用を抑制する必要があります。

代わりに WARN() および WARN_ON() を使用して「不可能な」状況を処理し、それらを処理可能なように扱ってください。BUG() 家族の関数は「不可能な」状況をアサートし、カーネルスレッドを安全に停止するように設計されていますが、これらは危険すぎることが判明しました（例：どの順序でロックを解放すべきか？）。一部のケースではBUG()の使用がシステムを不安定にしたり、完全に破壊したりするため、デバッグ作業やエラー報告すら困難になります。Linusはこれについて非常に批判的です： lockemail 1 email 2, 注意してください。WARN() 家族の関数は「不可能な」状況にのみ使用すべきです。何かが発生した可能性があるが望ましくない場合、その警告を出すには、

アロケータの引数にコード化された計算¶

動的サイズ計算（特に乗算）は、メモリ割当関数（または類似の）の引数で行うべきではありません。その理由は、オーバーフローのリスクがあるためです。これにより、呼び出し元が予期しないよりも小さな値が発生する可能性があります。この割当方法の使用は、ヒープメモリのオーバーフローおよび他の不具合を引き起こす可能性があります。(数値の場合はコンパイラが潜在的なオーバーフローに関する警告を生成できるため、例外があります。ただし、以下の提案通り数値を使用することは無害です)

例えば、 count * size を引数として使用しないでください:

foo = kmalloc(count * size, GFP_KERNEL);

代わりに、2引数のアロケータを使用すべきです:

foo = kmalloc_array(count, size, GFP_KERNEL);

この種のアロケータが利用できない場合、以下の形式の関数を使用すべきです saturate-on-overflow:

bar = vmalloc(array_size(count, size));

回避すべきもう一つの典型的なケースは、構造体のサイズを計算してその後に他の構造体の配列を追加する場合です。例えば以下のケース:

header = kzalloc(sizeof(*header) + count * sizeof(*header->item),
                 GFP_KERNEL);

代わりに、以下の関数を使用してください:

header = kzalloc(struct_size(header, item, count), GFP_KERNEL);

詳細については、 array_size(), array3_size(), e struct_size()およびcheck_add_overflow()とcheck_mul_overflow()の関数ファミリを参照してください。

simple_strtol(), simple_strtoll(), simple_strtoul(), simple_strtoull()¶

関数 simple_strtol(), simple_strtoll(), simple_strtoul(), e simple_strtoull() 意図的にオーバーフローを無視しており、これにより呼び出し元が予期しない結果を生成する可能性があります。それぞれの関数 kstrtol(), kstrtoll(), kstrtoul(), e kstrtoull() は正しい置き換えとみなされますが、注意すべきは、これらは文字列がNUL文字または改行文字で終了している必要があります。

strcpy()¶

spin_trylock() は、最初の試行で lock を取得できればゼロ以外の値を返し、失敗すればゼロを返します。この関数は、ハードウェアまたはソフトウェア割り込みのコンテキストでは安全に使用できません。 strcpy() 宛先バッファの境界をチェックしません。これにより、バッファの限界を超えたオーバーフローが発生し、さまざまな不具合が発生する可能性があります。コンパイラのオプション CONFIG_FORTIFY_SOURCE=y や複数のコンパイラオプションはリスクを減らすのに役立ちますが、この関数を続ける理由は全くありません。安全なバージョンは strscpy().

の使用は、宛先バッファがNUL文字で終了することを保証しません。これにより、NUL文字の欠如によって引き起こされるさまざまな読み込みオーバーフローまたは他の不具合が発生する可能性があります。この関数は、元の文字列が短い場合、宛先バッファに終了を拡張します。これにより、NULで終了する文字列のみを使用するユーザーにパフォーマンスのペナルティが発生する可能性があります。安全なバージョンは strncpy() です。(NULで終了する文字列を使用するユーザーは strscpy()を参照してください。 strscpy() NULで終端を拡張するには、呼び出しを追加する必要があります memset())

NULで終端された文字列を使用しない場合、 strncpy() 使用は続けられますが、宛先バッファは属性でマークする必要があります __nonstring コンパイル時の警告を避けるため。

strlcpy()¶

spin_trylock() は、最初の試行で lock を取得できればゼロ以外の値を返し、失敗すればゼロを返します。この関数は、ハードウェアまたはソフトウェア割り込みのコンテキストでは安全に使用できません。 strlcpy()まず、ソースバッファを完全に読み込み、おそらく実際にコピーされるよりも多くのデータを読み込むことになります。これは効率が悪く、NULで終端されていない文字列の場合、読み取りオーバーフローを引き起こす可能性があります。安全なバージョンは strscpy().

%pのフォーマット文字列¶

伝統的に、「%p」フォーマット文字列はdmesg、proc、sysfsなどにメモリアドレスを表示します。悪意のあるユーザーがこれらのアドレスを悪用しないようにするため、カーネル内のすべての「%p」使用はアドレスのハッシュに変換され、実際には利用不可能になります。新しい「%p」使用はカーネルに追加されません。アドレスのテキスト表現が必要な場合は、「%pS」を使用してください。出力はより良いです。シンボル名を表示します。それ以外の場合は、「%p」は使用しないでください。

可変長配列（VLA）¶

スタック上のVLAを使用すると、固定長配列を使用する場合よりも劣るコードになります。これら パフォーマンスの問題、決して無視できない問題であり、すでにVLAを削除する正当な理由となっています。さらに、セキュリティ上の問題にもなります。スタック上のベクトルが動的に成長すると、そのセグメントの残りメモリを越える可能性があります。これにより、異常動作やスタックの終わりに重要なデータを上書き（カーネルが CONFIG_THREAD_INFO_IN_TASK=y無効の場合）、 CONFIG_VMAP_STACK=y).

switch-caseステートメントの暗黙のジャンプ スイッチ 現在、コード内で「break」ステートメントが省略された場合、次のケースにジャンプする動作が行われます。ただし、この方法はコードの意味を曖昧にします。なぜなら、「break」ステートメントが意図的に省略されているのか、それともバグなのかが常に明確でないからです。たとえば、以下のコードを見ると、状態が意図的に設計されていても、あるいはバグである可能性があることがはっきりしません。 STATE_ONE 意図的に設計されていても STATE_TWO:

switch (value) {
case STATE_ONE:
        do_something();
case STATE_TWO:
        do_other();
        break;
default:
        WARN("unknown state");
}

「break」ステートメントの省略によって引き起こされる問題が長期間にわたって多数報告されてきたため 、今では「暗黙のジャンプ（fall-through）」を許可しなくなりました。意図的な暗黙のジャンプを識別するため、GCC拡張で「fallthrough」という擬似キーワードを採用しています。」を拡張して実装しています __attribute__((fallthrough)) ステートメント属性. (C17/C18の構文が [[fallthrough]] Cのコンパイラ、静的解析ツール、IDEがこの構文をより広くサポートするようになると、その構文を擬似キーワードとして使用できるようになります。

[[fallthrough]]構文がコンパイラ、静的解析ツール、およびIDE開発環境でより広くサポートされるようになると、私たちはそれを使用できるようになります。

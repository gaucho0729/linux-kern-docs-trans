Linuxカーネルドライバのインターフェース¶

(すべての質問への回答とその他の情報)

Greg Kroah-Hartman <greg@kroah.com>

これはLinuxについてなぜそのようにしているのかを説明しようとしたものです バイナリーアプリケーションインターフェースを持っておらず、安定したインターフェースも持っていません.

注意

この記事はインターフェースについて述べます カーネル内部のインターフェース、ユーザー空間へのインターフェースではありません。

カーネルがユーザー空間に対して提供するインターフェースは、プログラムが使用するシステムコールです。これらのインターフェースは 非常に 時間とともに安定しており、変更されません。私が以前にコンパイルした古いプログラムは、0.9程度のカーネルで動作し、現在でも2.6系のカーネルで動作しています。これらはユーザーおよびプログラマが安定しているとみなせるインターフェースです。

全体の概要¶

カーネルの安定したインターフェースを望んでいるかもしれませんが、実際にはそうではありませんし、望んでいないことに気づいていません。望んでいるのは安定した動作するドライバであり、これはドライバがカーネルソースに含まれている場合にのみ得られます。カーネルソースに自分のドライバを含める他の利点もあります。これらはLinuxが堅牢で安定し、成熟したオペレーティングシステムになった理由です。これらがLinuxを選んだ理由でもあります。

導入¶

インターフェース内部の変更に常に懸念を抱くことになるため、カーネルドライバを書くことの希望者は少数派です。世界の他の人々にとっては、これらのインターフェースは見えないものや興味の対象ではありません。

まず、法的な問題について論じません 一切 閉源コード、隠蔽されたコード、ラッパされたコード、バイナリーブロック、またはGPLライセンスでソースコードを公開していないドライバに関する法的問題。法的問題については弁護士に相談してください。私はプログラマであり、ここでは技術的な話題のみを述べます（法的問題については軽視しているわけではなく、実際には重大な問題です）。

したがって、2つの主なテーマがあります：カーネルのバイナリーアプリケーションインターフェースとカーネルソース内の安定したインターフェース。これらは互いに関連していますが、まずバイナリーアプリケーションインターフェースについて論じます。

カーネルのバイナリーアプリケーションインターフェース¶

カーネルソース内の安定したインターフェースがあると仮定します。すると、バイナリーアプリケーションインターフェースも安定しているはずです、正しいですか？誤りです。以下の事実を考慮してください：

  • 使用しているCコンパイラのバージョンによって、カーネルのデータ構造のアライメントが異なり、関数のインライン化などの処理方法も異なり得ます。個々の関数の構造はそれほど重要ではありませんが、データ構造内の間隔（パディング) は重要です。

  • カーネルを生成する際の選択されたオプションによって、いくつかのことが起こり得ます：

    • データ構造が異なる場合、含まれるフィールドも異なります

    • 一部の関数は実装されない場合があります（例えば、シングルプロセッサシステムでコンパイルされた場合に消えてしまう lock の関数など）

    • カーネルの内部メモリのアライメントは、コンパイルオプションによって異なることがあります。

  • Linuxは幅広いプロセッサアーキテクチャで動作しますが、あるアーキテクチャのドライバービナリが他のアーキテクチャで正しく動作する可能性はまったくありません。

これらの問題の一部は、カーネルと同じ設定でコンパイルしたモジュールを作成し、カーネルと同じコンパイラバージョンを使用することで解決できます。これは特定のLinuxディストリビューションの特定のリリース向けモジュールを提供するには十分ですが、Linuxディストリビューションの数とそのサポートするリリース数を掛け合わせると、設定とハードウェアプラットフォームの組み合わせが増えていき、たちまち複雑な状況になります。そのため、単一のモジュールリリースでも、異なるプラットフォームやコンパイラオプションに対応する複数のバージョンを作成する必要があります。

信頼してください。この方法を試すと、時間が経つにつれて精神的に追い詰められることでしょう。私は長年以前にその教訓を学んでいます…

カーネルソースコード内の安定したインターフェース¶

カーネルソースコードに含まれていないLinuxドライバをメンテナンスしようとする人々にとって、この話題は「困難」です。

Linuxカーネルの開発は常に進行しており、安定したペースで進み、決して遅れることはない。そのため、カーネル開発者たちは現在のインターフェースにバグを見つけたり、より良い方法を模索したりする。それらの改善点が見つかった場合、それを修正して改善する。このプロセスにおいて、関数名が変更される可能性があり、データ構造が大きくなるか小さくなる可能性があり、関数の引数も見直されることがある。このような変更が発生した場合、そのインターフェースが使用されているすべての場所が同時に修正されるため、すべてが問題なく動作し続けるようにする。

例えば、USBサブシステムの内部インターフェースはこれまでに3回の再構築を経た。これらの再構築は以下の問題を解決するため行われた：

  • データフローの同期型から非同期型への変更が行われた。これにより、多くのドライバの複雑さが減り、すべてのドライバの伝送能力が向上し、ほぼ最大限の速度に近づいた。

  • USBサブシステムがドライバの代わりにパケットを割り当てる仕組みが変更された。これにより、ドライバはUSBサブシステムにより多くの情報を提供する必要があり、特定のブロックを修正するための情報が得られるようになった。

これは一部の商用OSが古いUSBインターフェースへのサポートを長期間維持する必要があったこととは完全に逆の状況である。新しい開発者が誤って古いインターフェースを使用して不適切なコードを書くと、システムの不安定化を招く可能性がある。

どちらのシナリオにおいても、開発者たちはこれらの重要な変更が必須であると判断し、苦しみながら実施した。もしLinuxが内部インターフェースを安定的に維持するという保証を提供していたら、新しいインターフェースの作成が必要となり、古いインターフェースは動作不良を引き起こしながらメンテナンスを受ける必要があり、USBサブシステムの開発者に追加の作業を課すことになる。開発者たちはすでにこの種の作業に時間を費やしているため、利益を得られない追加の作業を要求することは現実的ではない。

セキュリティに関する問題はLinuxにとって非常に重要です。セキュリティ上の問題が発覚した場合、迅速に修正されます。一部のケースでは、セキュリティ問題を防ぐためにカーネル内部のインターフェースを変更する必要がありました。その際、そのインターフェースを使用していたすべてのドライバが同時に更新され、問題の根本的な修正が行われ、今後誤って修正を忘れることもありませんでした。もし内部インターフェースを変更しなかった場合、問題の修正や再発防止が不可能になっていたでしょう。

時間とともにカーネルのインターフェースはいくつかの整理が行われます。もはや誰も使用していないインターフェースは削除されます。これによりカーネルが可能な限り小さくなり、すべての潜在的なインターフェースが可能な限り検証されるようになります（使用されていないインターフェースは検証が不可能です）。

行うべきこと¶

したがって、Linuxカーネル用のドライバがカーネルの主要なソースコードに含まれていない場合、開発者としてどのような対応をすべきでしょうか？各カーネルバージョンおよび各ディストリビューションごとにバイナリ形式のドライバをリリースするのは地獄のような作業であり、さらにカーネルのすべての変更に追従するのも大変な作業です。

単純に、あなたのカーネルドライバが主要なカーネルソースコードに含まれるようにしてください（注意してください、ここでの話題はGPL互換ライセンスでリリースされているドライバについてです；あなたのコードがこのカテゴリに該当しない場合は、ごめんね、自分でなんとかしてください）。

あなたのドライバがカーネルソースコードに含まれており、インターフェースが変更された場合、その変更をした人物が即座にドライバを修正します。これにより、ドライバのコンパイルが常に可能で、動作するようになることが保証され、あなたの側で最小限の労力で済みます。

カーネルの主要なソースコードに自分のドライバを持つことの利点は以下の通りです：

  • ドライバの品質が向上し、開発者のメンテナンスコストが減少します。

  • 他の開発者があなたのドライバに新しい機能を追加します。

  • 他の人があなたのドライバのバグを発見し、修正します。

  • 他の人があなたのドライバの改善点を提案します。

  • 他の人がインターフェースの変更に伴ってドライバを更新します。

  • ドライバはすべてのLinuxディストリビューションで自動的に利用可能になります。どのディストリビューションにも追加を依頼する必要はありません。

Linuxは他のどのオペレーティングシステムよりも多くのデバイスをサポートしており、多くの種類のプロセッサでも動作するという点から、この開発モデルが何か正しい点を持っているのは確かです :)

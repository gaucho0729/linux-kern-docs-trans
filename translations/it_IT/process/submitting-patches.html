パッチ送信：あなたのコードがカーネルに取り込まれるためのエッセンシャルガイド¶

カーネルにパッチを送りたい個人または企業は、特に「システム」にあまりなじみがない場合、送信プロセスに意気消沈しやすいかもしれません。このテキストは、あなたのパッチが受け入れられやすくなるよう、多くのアドバイスをまとめたものです。

このドキュメントには、多くの簡潔なアドバイスが含まれています。カーネル開発プロセスの詳細については、 Documentation/translations/it_IT/processまた、以下のリンクを参照してください。 Linuxカーネルのパッチを送信する前のチェックリスト コードを送る前に確認すべきポイントのリスト。ドライバを送る場合は、以下のリンクも参照してください。 Linuxカーネル用ドライバを提出する；Device Treeのアソシエーションに関連するパッチについては、以下のリンクを参照してください。 devicetree (DT)バインディングのパッチを送信する.

これらの多くのステップは、バージョン管理システムの基本的な動作を説明しています。 git；バージョン管理システムを使用している場合、 git パッチの準備には、多くの繰り返し作業がすでに済んでいますが、ある程度のパッチの作成とドキュメンテーションは必要です。一般的に、 git カーネル開発者の生活をより楽にします。

0) 現在のソースコードを取得する¶

カーネルの最新のソースコードを含むリポジトリを持っていない場合は、以下を使用してください。 git それらを取得するために以下を使用してください。最初にメインリポジトリから始めることをおすすめします。

git clone git://git.kernel.org/pub/scm/linux/kernel/git/torvalds/linux.git

ただし、カーネルのメインソースコードを直接使って開発することを望まない可能性もあります。ほとんどのメンテナは独自のソースコードを持ち、それらに基づいてパッチを準備することを望んでいます。 T: ソースコード内のMAINTANERSファイルで特定のサブシステムに関する項目を確認してください。使用するソースコードがそのファイルに記載されていない場合は、メンテナに直接尋ねてください。

カーネルのリリースをtarアーカイブとしてダウンロードする方法もあります（次のセクションで説明されています）が、これはカーネル開発するための最も複雑な方法です。

1) diff -up¶

手動でパッチを作成する場合は、以下を使用してください。 diff -up o diff -uprN それらを作成するために使用してください。Gitは通常、この形式でパッチを生成します。 git特定のツールを使用している場合は、このセクションを完全にスキップしてください。

すべてのLinuxカーネルの変更はパッチを通じて行われ、以下に説明されています。 diff(1)。自分のパッチを作成する際には、「unified diff」形式で作成してください。 -u di diff(1)。さらに、変更に関連するC関数を表示するために、以下の引数を使用してください -p 異なる変更に関連するC関数を表示します。これにより、結果が diff はるかに読みやすくします。パッチはカーネルのソースコードのルートに基づくべきで、サブディレクトリではなくする必要があります。

単一のファイル用のパッチを作成するには、通常以下を行います：

SRCTREE=linux
MYFILE=drivers/net/mydriver.c

cd $SRCTREE
cp $MYFILE $MYFILE.orig
vi $MYFILE      # make your change
cd ..
diff -up $SRCTREE/$MYFILE{.orig,} > /tmp/patch

複数のファイル用のパッチを作成するには、未変更の「素の」ソースコードを展開し、次のようにします： diff あなたのものです。例えば：

MYSRC=/devel/linux

tar xvfz linux-3.19.tar.gz
mv linux-3.19 linux-3.19-vanilla
diff -uprN -X linux-3.19-vanilla/Documentation/dontdiff \
        linux-3.19-vanilla $MYSRC > /tmp/patch

dontdiff は、カーネルのコンパイルプロセスで生成されるファイルの一覧です。これらは、何らかのツールで生成されたパッチでは無視すべきです。 diff(1).

パッチに含まれるべきでないファイルを含まないよう確認してください。正確性を確認するため、生成後にパッチをレビューすることも重要です。 diff(1).

もしあなたの変更が多くの違いを生じる場合、論理的なステップで変更を加える独立したパッチに分ける必要があります。以下のガイドを参照してください。 変更点を分離してください. これにより、他の開発者によるレビューが容易になります。パッチが受け入れられることを望む場合、これは非常に重要です。

もし以下のツールを使用している場合、 git, git rebase -i このツールはプロセスを支援します。もし使用していない場合、一般的な代替案は gitです。 quilt <http://savannah.nongnu.org/projects/quilt>.

2) あなたの変更を説明してください¶

あなたの問題を説明してください。常に何か問題があり、それがあなたの作業を動機としています。それは1行のバグの修正であれ、5000行のコードの新しい機能であれです。レビュアーにあなたの問題が解決する価値があり、最初の段落の後も読み続ける意味があることを説得してください。

ユーザーが見ることになる影響を説明してください。明確なシステムエラーまたはブロックは非常に説得力がありますが、すべてのバグがそうではありません。コードのレビュー中に問題が発見された場合でも、ユーザーへの影響を説明してください。ほとんどのLinuxインストールでは、安定版のソースコードまたは特定のディストリビューションのソースコードからカーネルが使用されるため、あなたの変更を理解するためのすべての情報を含めてください：dmesgからのエラーメッセージ、システムエラーの説明、パフォーマンスの低下、レイテンシーのピーク、ブロック、など。

最適化とトレードオフを定量的に評価してください。パフォーマンスの改善、メモリ消費量の削減、スタックへの影響、バイナリーファイルのサイズなど、改善を主張する場合は、数値を添えてその主張を裏付けてください。ただし、明らかでないコストについても記述してください。通常、最適化は無料ではありませんが、CPU使用量、メモリ使用量、可読性の間のトレードオフ、または推測的な仮定の場では、異なる負荷の間のトレードオフとして考えられます。最適化の予想されるデメリットを記述することで、レビュアーがコストと利益を評価できるようにしてください。

問題が明確になった後、技術的な詳細を含めてその解決策を説明してください。レビュアーがコードが説明通り動作するか確認できるように、シンプルな英語で変更内容を記述することが非常に重要です。

カーネルが使用するソースコード管理システムと互換性のあるフォーマットでパッチの説明を書くことで、メンテナに感謝されます。 git、例えば「コミットログ」という形式を使用してください。読みましょう 15) ヘッダーに明示的にIn-Reply-Toを記載する.

パッチで解決する問題は1つに限定してください。説明が長くなる場合、パッチを分割する必要がある可能性があります。読みましょう 変更点を分離してください.

パッチまたはパッチシリーズを送信または再送信する際は、変更内容の完全な説明とその正当性を含めてください。パッチ（またはシリーズ）のバージョンNであるとだけ述べるのではなく、サブシステムのメンテナが以前のバージョンを探す必要がないようにしてください。実際には、パッチ（またはシリーズ）とその説明は1つにまとめる必要があります。これによりメンテナとレビュアーの作業が楽になります。おそらく、一部のレビュアーは以前のパッチバージョンをまだ見ていないかもしれません。

変更内容を説明する際は命令形を使用してください。例えば「xyzzyがfrotzを実行するようにしてください」ではなく、「[このパッチ]はxyzzyがfrotzを実行するようにします」や「[私は] xyzzyをfrot, zを実行するように変更しました」という表現は避け、コードに命令するようにしてください。

既知のバグを修正するパッチの場合は、そのバグの番号またはURLを参照してください。パッチがリストの議論の結果である場合は、その議論のアーカイブURLを提供してください。リンクを https://lkml.kernel.org/ 、 Message-Id、このようにしてリンクが時間とともに無効にならないようにします。

ただし、外部のソースを参照せずに説明を理解できるようにしてください。リンクやリストのディスカッションの他に、パッチ作成に至った議論の重要なポイントを要約してください。

特定のコミットを参照する場合、SHA-1識別子だけではなく、コミットの要約行も追加してください。レビュアーが目的を明確に理解できるようにしてください。例えば：

Commit e21d2170f36602ae2708 ("video: remove unnecessary
platform_set_drvdata()") removed the unnecessary
platform_set_drvdata(), but left the variable "dev" unused,
delete it.

SHA-1識別子の最初の12文字を使用してください。kernelリポジトリには多くのオブジェクトがあり、 多くの オブジェクトがあり、短い文字列で識別子の衝突が起こる可能性があります。注意してください。現在の6文字の識別子でも衝突がなければ、5年後には衝突が発生する可能性があります。

特定のコミットのバグを修正する場合、例えば、 git bisectを使用して問題を発見した場合、'Fixes:'ラベルを付けて、SHA-1の最初の12文字と要約行を記載してください。例えば：

Fixes: e21d2170f366 ("video: remove unnecessary platform_set_drvdata()")

以下の設定は、 git config の結果をフォーマットするために使用できます git log o git show 、前の例のように表示されます：

[core]
        abbrev = 12
[pretty]
        fixes = Fixes: %h (\"%s\")

3) あなたの変更を分離してください¶

論理的な変更を に分離してください 個別のパッチに分割してください。

例えば、1つのドライバに関する変更がバグ修正とパフォーマンス改善を含む場合、それらを2つ以上のパッチに分けてください。APIのアップデートとそのAPIを活用する新しいドライバを含む変更は、2つのパッチに分けてください。

一方で、複数のファイルにわたる単一の変更は、1つのパッチにまとめください。つまり、論理的な変更は1つのパッチに含まれるべきです。

重要なのは、各変更がレビュアーが理解しやすく、検証可能な内容であることです。各パッチは、自体で正当化できる必要があります。

パッチが他のパッチに依存する場合、問題ありません。ただし、パッチの説明にその旨を明記してください： “this patch depends on patch X”.

変更を複数のパッチに分割する場合、各パッチの検証に特に注意してください。各パッチはカーネルがコンパイルし、正しく動作する必要があります。使用している開発者は git bisect 問題を発見するためには、あなたのパッチシリーズのどこかに問題が含まれている可能性があります。中盤にバグを導入した場合、それらはあなたにとって好意的な評価をもたらしません。

自分のパッチシリーズをより小さなサイズに圧縮できない場合、一度に10〜15個のパッチを公開し、それらがレビューされ統合されるのを待つのが一般的です。

4) あなたの変更のスタイルを確認してください¶

あなたのパッチがコードスタイルに違反していないか確認してください。詳細については Linuxカーネル用コードスタイルをご覧ください。スタイルに沿わないコードを提出すると、レビュアーの時間の無駄になり、あなたのパッチはおそらく読まれることなく却下されるでしょう。

コードが別のファイルから別のファイルへ移動される場合を除けば、コード移動された部分を理由の如何にかかわらず変更すべきではありません。これにより、コードの移動という行動とあなたの変更という行動を明確に分離でき、本質的な差分のレビューを大幅に助け、コードの履歴をツールがより正確に追跡できるようになります。

パッチを送信する前に、scripts/checkpatch.plという専用のスタイルチェックツールでスタイルを確認してください。ただし、スタイルチェックツールはガイドとしての役割であり、人間の判断を代替するものではありません。あなたのコードがスタイル違反を犯しながらもより優れている場合、そのままでおくのが良いでしょう。

チェックツールには3つの異なる深刻度レベルがあります:

  • ERROR: おそらく重大な間違いが含まれています

  • WARNING: 丁寧なレビューが必要です

  • CHECK: 一層の検討が必要です

あなたのパッチに残るすべてのスタイル違反について、説明責任を果たせる必要があります。

5) あなたのパッチの送信先を選択してください¶

常に、変更が影響を与えるサブシステムのメンテナにパッチのコピーを送信してください。MAINTAINERSファイルやレビューの履歴を確認して、どのメンテナがコードを担当しているかを把握してください。scripts/get_maintainer.plスクリプトが役に立つかもしれません。サブシステムのメンテナが見つからない場合は、Andrew Morton（akpm@linux-foundation.org）が最終的な選択肢になります。

通常、あなたのパッチシリーズを送信するためのディスカッションリストも選ぶ必要があります。ディスカッションリスト linux-kernel@vger.kernel.org これは最終手段です。このリストのメールボリュームが多いため、いくつかの開発者が追随していないようです。MAINTAINERSファイルを確認して、特定のサブシステムに割り当てられたディスカッションリストを検索してください。おそらく、あなたのパッチはそこでより多くの注目を浴びるでしょう。ただし、関係のないディスカッションリストにスパムメールを送らないでください。

カーネル関連のディスカッションリストは多くがvger.kernel.orgにホストされています。そのリストは以下のページで確認できます http://vger.kernel.org/vger-lists.html.ただし、他にも他の場所にホストされているディスカッションリストがあります。

vgerのディスカッションリストに1回に15を超えるパッチを送らないでください!!!

受け入れられた変更の統合に関する最終的な判断はLinux Torvaldsが行います。彼のメールアドレスは<torvalds@linux-foundation.org>.彼は多数のメールを受け取り、この段階では直接的な判断を通すパッチは極めて少ないため、できるだけ彼にメールを送らないようにしてください。

セキュリティバグの修正を行うパッチがある場合は、 security@kernel.orgに送ってください。重大なバグの場合は、配布版がパッチをユーザーに提供するまでに時間を確保するため、短期間の embargo が検討されることがあります。その場合、パッチはどの公開ディスカッションリストにも送らないでください。

既にリリースされたカーネルでの重大なバグ修正を行うパッチは、安定版カーネルのメンテナに送信し、パッチの署名セクションに以下の行を追加してください：

Cc: stable@vger.kernel.org

この行はメール宛先としてではなく、署名セクションに追加してください。このファイルに加えて、 Linuxの-stableリリースについてのすべての情報

も読みましょう。ただし、一部のサブシステムメンテナは安定版カーネルにどのパッチを含めるかの最終決定権を持っています。メンテナネットワークは、個々の開発者がパッチに上記のような行を追加することを望んでいません。

ユーザー空間インターフェースに影響を与える変更がある場合は、関連するマニュアルページのメンテナ（MAINTAINERSファイルに記載）にパッチを送るか、少なくとも変更の通知を送ってください。そうすることで情報がマニュアルに反映されるようになります。ユーザー空間APIの変更は、さらに linux-api@vger.kernel.org.

にもCCで送信してください。 Trivial Patch Monkey trivial@kernel.org 「banali（平凡）なパッチ」を収集する目的を持っています。MAINTAINERSファイルをご覧ください。現在の管理者が誰かを確認してください。

平凡なパッチは以下のいずれかのカテゴリに該当する必要があります：

  • ドキュメンテーションの文法ミス

  • エラーの文法ミス（エラーが発生してシステムを破壊する可能性のあるもの） エラーにより動作が破綻する可能性のあるスペル修正

  • コンパイル警告の修正（無駄な警告を出力するのは悪影響です）

  • コンパイルエラーの修正（本質的な修正が含まれる場合に限ります）

  • 非推奨の関数/マクロの削除

  • 非移植性コードの移植性コードへの置き換え（特定のアーキテクチャ向けコードでも可。ただし変更が平凡である必要があります）

  • ファイルの著者/メンテナによる変更（実際には「パッチモンキー」のリプレイモード）

6) 何も含まない：MIME、リンク、圧縮、添付ファイル。純粋なテキストのみ¶

Linusやカーネル開発者たちは投稿するパッチをコメントする必要があります。開発者にとって重要なのは、通常のメールソフトで投稿したパッチを「引用」して特定のコード部分にコメントできるということです。

そのため、すべてのパッチはメール本文としてテキスト形式で送信する必要があります。

警告

パッチをメール本文に貼り付ける場合は、メールソフトが自動改行で内容を破壊しないように注意してください。

パッチはMIME添付ファイル、圧縮ファイルとして送信してはいけません。多くのポピュラーなメールソフトがMIME添付ファイルを純粋なテキストとして送信しないので、コードへのコメントが不可能になります。また、MIME添付ファイルはLinusの作業を困難にし、あなたのMIME添付ファイルが受け入れられにくい原因になります。

例外：あなたのメールサーバーがパッチを破壊する場合、誰かがあなたにMIME添付として再送してほしいと依頼するかもしれません。

読みましょう Linux用メールソフトに関する情報 メールソフトの設定について、パッチを破壊せずに送信するためのヒントが記載されています。

7) メールのサイズ¶

大規模な変更はディスカッションリストや一部のメンテナにとって適していません。あなたのパッチが圧縮せずに300KBを越える場合、インターネット上のアクセス可能な場所にアップロードし、そのURL（リンク）を添えてください。ただし、パッチが300KBを越えると、ほぼ確実に分割する必要があります。

8) レビューコメントへの返信¶

レビュアーがご提案の改善点についてコメントを送る可能性が高いです。これらのコメントに必ずご返答ください。レビュアーを無視すると、逆に無視される可能性が高いためです。コードの変更につながらないフィードバックや質問は、変更履歴にコメントして次回のレビュアーが状況を理解しやすくなるようにしてください。

レビュアーに変更内容を明確に伝え、ご協力への感謝を忘れずに。コードのレビューは手間のかかる作業であり、時にはレビュアーが苛立つこともあります。しかし、その場合でも丁寧に対応し、指摘された問題に集中してください。

9) 気を落とさないで - または焦らないで¶

変更内容を送信後は忍耐強く待つ必要があります。レビュアーは忙しい人々であり、すぐにご提案を確認できない場合があります。

かつてはご提案が無視されることが多かったものの、現在の開発プロセスは改善されています。1週間以内にコメントが届くことが期待されます。届かない場合は、ご提案が正しく送信されたか確認してください。1週間以上待ってから再送またはレビュアーへの催促を行ってください。統合期間中はさらに長く待つのが望ましいです。

10) 件名に PATCH を追加¶

Linusへのメールやlinux-kernelリストの高メール量を考慮し、件名に[PATCH]を付けることが慣例です。これにより、Linusや他のカーネル開発者たちは、他の議論と区別してご提案を簡単に識別できます。

11) あなたの作業を署名する - 開発者の元の証明書¶

特に複数のメンテナを通じて最終ステージに至るご提案の追跡可能性を向上させるため、メールで送信するご提案に署名プロセスを導入しました。

署名は、ご提案の説明文末尾に追加する単純な行で、その内容が貴方自身が書いたものであるか、またはオープンソースとして公開する権限があることを証明します。ルールはシンプルで、以下の点を証明できる場合に署名してください：

開発者の元の証明書 1.1¶

このプロジェクトへの貢献を通じて、私は以下を保証します：

  1. この貢献は完全に、または一部を私自身が作成し、オープンソースライセンスに従って送信する権利を持っていることを。または

  2. この貢献は、私の知識の範囲内で適切なオープンソースライセンスに基づいており、そのライセンスにより改変・送信する権利があるとされています。この改変は、完全または一部を含む私のものです（他のライセンスを使用する許可がない限り）。この情報はファイルに記載されているオープンソースライセンスに従って、またはその他の条件に従って行われます。

  3. この貢献は、(a)、(b)、または(c)を証明した人物から直接提供され、私はそれを改変していません。

  4. このプロジェクトおよびその貢献は公開されていることを理解し、同意します。貢献履歴（含まれる個人情報や署名を含む）は永久に保存され、このプロジェクトまたは関連するオープンソースライセンスに従って再配布されることがあります。

次に、以下の行を追加するだけです。

Signed-off-by: Random J Developer <random@developer.example.org>

本名を使用してください（ごめんなさい、ペンネームや匿名での貢献は受け付けていません）。

一部の人は最後にラベルを追加することがあります。現時点では無視されますが、内部プロセスを特定するためや署名に関する詳細を追加するためには、自由に使用できます。

サブシステムやブランチのメンテナである場合、受け取ったパッチをわずかに修正して統合する必要があります。これは、あなたのソースコードと貢献者のソースコードにコードが完全に一致しないからです。規則(c)を厳密に守る場合、送信者にパッチを再作成してもらう必要がありますが、これは時間とエネルギーの無駄です。規則(b)によりコードを修正できますが、他人のパッチを変更して自分のバグの責任を押し付けるのは不適切です。この問題を解決するため、最後のSigned-off-byとあなたの署名の間に、あなたの修正を説明する行を追加してください。義務ではありませんが、効果的な方法は、あなたの名前やメールアドレスを括弧で囲い、短い説明をつけることです。これにより、最近の修正の責任者を明確にできます。例えば：

Signed-off-by: Random J Developer <random@developer.example.org>
[lucky@maintainer.example.org: struct foo moved from foo.c to foo.h]
Signed-off-by: Lucky K Maintainer <lucky@maintainer.example.org>

この慣例は、安定したブランチをメンテナとしている場合に特に役立ちます。作者への貢献を記録し、修正を追跡・統合し、送信者をクレームから守るためです。注意点として、作者の識別情報（Fromヘッダー）の変更は一切許可されていません。これはチェンジログに表示されるためです。

古いバージョンにコードを適用する人々向けの特別な注意点です。コミットメッセージの先頭（オブジェクト行の直後に）にパッチの出所を示す記述を追加する実用的な方法が一般的であるように見えます。これは、トレーサビリティを向上させるためです。たとえば、安定版3.x-stableのリリースでは以下のように表示されます:

Date:   Tue Oct 7 07:26:38 2014 -0400

  libata: Un-break ATA blacklist

  commit 1c40279960bcd7d52dbdf1d466b20d24b99176c8 upstream.

ここでは、より古いカーネルでこのパッチが適用された場合に見られる例が示されています:

Date:   Tue May 13 22:12:27 2008 +0200

    wireless, airo: waitbusy() won't delay

    [backport of 2.6 commit b7acbdfbd1f277c1eb23f344f899cfa4cd0bf36a]

どのフォーマットであれ、この情報はソースコードを追跡したい人々やバグを探している人々にとって重要な助けとなります。

12) Acked-by:、Cc:、Co-developed-by: の利用タイミング¶

Signed-off-by: のラベルは、署名者がパッチの開発に関与したか、またはその配布経路に含まれていたことを示します。

パッチの準備や管理には直接関与していないが、署名して承認を記録したい人々は、パッチのチェンジログに Acked-by: の行を追加するようリクエストできます。

Acked-by: は、パッチを担当するサブシステムのメンテナが、自身がパッチを提供・配布しなかった場合にしばしば使用されます。

Acked-by: は Signed-off-by: ほど公式ではありません。これは、パッチをレビューし、受け入れ可能なと判断した人物を示します。そのため、時折、パッチを統合する人が「はい、これでよさそう」という意見を Acked-by: に変換します（ただし、通常は明示的に依頼するのが望ましいです）。

Acked-by: はパッチ全体の承認を示しません。たとえば、パッチが複数のサブシステムに影響し、そのうちの1つに属するメンテナが Acked-by: を付与した場合、そのメンテナは自身が管理するサブシステムに関連するコード部分を承認していることを意味します。ここでは注意が必要です。疑問がある場合は、論議の元となったディスカッションアーカイブを参照してください。

パッチにコメントをした機会があったがしなかった人物には、このラベルを Cc: パッチに追加できます。これは、関係者に何らかの行動を取らせる必要がない唯一のラベルです。ただし、このラベルは人物がパッチのコピーを受け取ったことを記録するためのものです。このラベルは、関心を持つ第三者が議論に含まれたことを示します。

Co-developed-by: は複数の開発者によって作成されたパッチを示します。複数の人がパッチに貢献している場合、このフィールドは追加の著者（From: に記載された著者とは別に）を割り当てるために使用されます。Co-developed-by: はパッチの親権を示すため、各 Co-developed-by: は即座に該当する共同著者の Signed-off-by: で続きます。ここでは基本的なサインオフ手順が適用され、Signed-off-by: の順序はパッチの履歴の時系列順をできるだけ反映する必要があります。From: や Co-developed-by: によって親権が割り当てられたとしても、この順序は変わりません。注意すべきは、最後の Signed-off-by: がパッチを提出した人のものです。

From: は、From: に記載された著者がメールの From: ヘッダーに記載された人物（およびメールアドレス）と同じである場合、オプションです。

From: の著者がパッチを提出した例:

<changelog>

Co-developed-by: First Co-Author <first@coauthor.example.org>
Signed-off-by: First Co-Author <first@coauthor.example.org>
Co-developed-by: Second Co-Author <second@coauthor.example.org>
Signed-off-by: Second Co-Author <second@coauthor.example.org>
Signed-off-by: From Author <from@author.example.org>

Co-developed-by: の著者がパッチを提出した例:

From: From Author <from@author.example.org>

<changelog>

Co-developed-by: Random Co-Author <random@coauthor.example.org>
Signed-off-by: Random Co-Author <random@coauthor.example.org>
Signed-off-by: From Author <from@author.example.org>
Co-developed-by: Submitting Co-Author <sub@coauthor.example.org>
Signed-off-by: Submitting Co-Author <sub@coauthor.example.org>

13) Reported-by:、Tested-by:、Reviewed-by:、Suggested-by: および Fixes: の使用:¶

Reported-by: は、バグを発見・報告した人々への謝意を表します。このフィールドは、今後も彼らが私たちを支援してくれるよう、インスピレーションを与えることを期待しています。注意すべきは、バグがプライベートで報告された場合、Reported-by: を使用する前に許可を得る必要があります。

Tested-by: は、特定の人物がパッチをあるシステム上で成功裏に検証したことを示します。このフィールドはメンテナに検証が行われたことを通知し、今後のコードの検証を担当する人々を特定する手段を提供し、またこれらの人物がその作業に対して適切に評価されることを保証します。

Reviewed-by: は、パッチがレビュアーの声明に従って受け入れ可能な状態であることを示します:

レビュアーの声明¶

Reviewed-by: を使用することにより、以下の声明を提供します:

  1. 私はこのパッチを技術的にレビューし、その内容がカーネルのメインブランチへの統合に適切であるかを評価しました。

  2. このパッチに関するすべての問題や質問は送信者に伝えられ、送信者の回答に満足しています。

  3. このサブミッションには改善の余地があるかもしれませんが、現在の時点で（1）カーネルにとって有益な変更であり、（2）統合を妨げる問題が存在しないと信じています。

  4. パッチを確認し、問題ないと判断しましたが、これは常に動作するとは保証しません（特に明示されていない限り）。このパッチが期待通りに動作するか、すべての状況で正しく動作するかは保証しません。

Reviewed-byというラベルは、修正が適切で技術的な重大な問題がないと判断したレビュアーの意見を示すものです。関心のあるレビュアー（すでに実施した人）がパッチにReviewed-byを付けることができます。このラベルはレビュアーへの貢献を示し、メンテナにパッチがどの程度レビューされたかを伝えるためのものです。対象分野に関する知識と、レビューの真剣さが認められたレビュアーがReviewed-byを付けると、あなたのパッチがカーネルに取り込まれる確率が高まります。

Suggested-byというラベルは、パッチのアイデアが指定された人物によって提案されたことを示し、その人物への貢献を認めるためのものです。このラベルを追加する際は、特にアイデアが公開フォーラムで公表されていない場合を除き、明示的な許可を得るべきです。こうして貢献者への感謝を示すことで、今後も協力していただけるよう励ます。

Fixesというラベルは、パッチが以前のコミットの問題を修正することを示します。これにより、問題の起源が明確になり、問題のレビューが容易になります。このラベルは、安定版カーネルのメンテナにとってどのカーネルに修正を適用すべきかを理解するのに役立ちます。問題がパッチで修正されたことを示すための推奨方法です。詳細については、以下のセクションを参照してください。 2) あなたの変更を説明してください

14) カノニカルなパッチのフォーマット¶

このセクションでは、パッチに使用すべきフォーマットについて説明します。注意点として、リポジトリを使用している場合、 git パッチを保存する際には、以下のコマンドを使用して git format-patch 適切なフォーマットのパッチを取得できます。このツールは必要なテキストを自動生成しないので、以下の指示をよく読みましょう。

カノニカルなパッチのサブジェクトは次の行です：

Subject: [PATCH 001/123] subsystem: summary phrase

カノニカルなパッチの本文には次の要素が含まれます：

  • 1行 from パッチの著者を指定する行、その後に空行（パッチを送信した人が著者である場合は必要ありません）。

  • 75文字以下の行で構成される説明本文。これはchange logに永久にコピーされるため、パッチの説明として使用されます。

  • 空行

  • 前述した行、これらもchange logに含まれます。 Signed-off-by:区切り線として単なる

  • の行が含まれます。 ---.

  • Changelogに含まれるべきではない他のコメント。

  • コードの実際の変更点（コード変更の製品として） diff).

オブジェクトの形式は、メールソフトがパッチをアルファベット順に並べるために使用可能で、すべてのメールソフトがこの機能を備えています。数値の前にゼロを追加することで、数値順とアルファベット順が一致します。

The subsystem メールの件名では、パッチで変更されたエリアまたはサブシステムを特定する必要があります。

リスト形式のテーブル summary phrase メールの件名では、パッチの内容を簡潔に説明する必要があります。La summary phrase ファイル名としては使用すべきではありません。同じ summary phrase シリーズ内のすべてのパッチ（一つのパッチが serie di patch 一連の関連する複数のパッチの順序付きリスト）。

メールの件名が、 summary phrase メールの件名が、そのパッチのグローバルで一意な識別子になります。これはchangelogに伝播します。 git今後、開発者たちはこのパッチを参照するために使用できます。人々はインターネットでこの summary phrase を検索して、関連する議論を読むでしょう。また、2〜3か月後に数百のパッチをツール（例： summary phrase ）で検索する際、人々が最初に見る可能性のある唯一の情報かもしれません。 gitk o git log --oneline.

これらの理由から、件名は70〜75文字程度にし、変更内容とその必要性を説明する必要があります。短くかつ説明的であることは難しい挑戦ですが、これは良いサマリの特徴です。

リスト形式のテーブル summary phrase ラベル（tag）を角括弧「Subject: [PATCH <tag>…] <summary phrase>」内に含めることができます。ラベルはサマリ文の一部とは見なされませんが、パッチの処理方法を示します。一般的なラベルには、パッチが複数回送信された場合に使用されるバージョンラベル（例：「v1, v2, v3」）や、「RFC」（Request For Comments）があります。シリーズ内の4つのパッチは「1/4, 2/4, 3/4, 4/4」として列挙すべきです。これにより、開発者がパッチの適用順序を理解し、レビュー済みまたは適用済みのパッチを追跡できるようになります。

件名の例:

Subject: [PATCH 2/5] ext2: improve scalability of bitmap searching
Subject: [PATCH v2 01/27] x86: fix eflags tracking

以下の行 from はメッセージ本文の最初にあり、形式は以下の通りです：

From: パッチ作成者 <author@例.com>

以下の行 from これは、永続的なchangelogでパッチの著者として記載される人物を示します。もし from が存在しない場合、changelogに記載する著者は From メールのヘッダーにある行を使用します。

説明の本文は永続的な変更履歴に含まれるため、専門家向けに読みやすく、論議の詳細を忘れてしまった読者でも理解できるようにしなければなりません。パッチで修正された問題に関する情報（カーネルメッセージ、oopsメッセージなど）は、そのパッチを検索している人にとって特に有用です。コンパイルエラーを修正するパッチの場合、コンパイラから出力されたすべての情報は必要ありません。パッチが見つかるように必要な情報だけを記載してください。また、 summary phrase説明は簡潔かつ具体的に書くことが重要です。

デマルケーションライン --- 変更履歴メッセージの終わりを示すために主に使用されます。

このスペースに追加する diffstat の後ろに --- は、変更されたファイルを表示し、追加または削除されたファイルの数を示すための良い使い方です。特に、大規模なパッチには diffstat が非常に役立ちます。メンテナだけに重要で、変更履歴に適さないコメントはここに記載すべきです。このようなコメントの良い例は、パッチの各バージョン間の違いを説明することです。

Se includete un diffstat の後ろに ---, usate le opzioni -p 1 -w70 cosicché i nomi dei file elencati non occupino troppo spazio (facilmente rientreranno negli 80 caratteri, magari con qualche indentazione). (git genera di base dei diffstat adatti).

Maggiori dettagli sul formato delle patch nei riferimenti qui di seguito.

15) ヘッダーに明示的にIn-Reply-Toを記載する¶

Aggiungere manualmente In-Reply-To: nell’intestazione dell’e-mail potrebbe essere d’aiuto per associare una patch ad una discussione precedente, per esempio per collegare la correzione di un baco con l’e-mail che lo riportava. Tuttavia, per serie di patch multiple è generalmente sconsigliato l’uso di In-Reply-To: per collegare precedenti versioni. In questo modo versioni multiple di una patch non diventeranno un’ingestibile giungla di riferimenti all’interno dei programmi di posta. Se un collegamento è utile, potete usare https://lkml.kernel.org/ per ottenere i collegamenti ad una versione precedente di una serie di patch (per esempio, potete usarlo per l’email introduttiva alla serie).

16) Inviare richieste git pull¶

Se avete una serie di patch, potrebbe essere più conveniente per un manutentore tirarle dentro al repositorio del sottosistema attraverso l’operazione git pullただし、このように開発者からパッチを取得するには、メールリストから取得するよりも高い信頼が必要です。そのため、多くのメンテナは新規のリクエストを受けることをためらいます。 pull特に新米開発者や未知の開発者からのリクエストに対しては、疑問がある場合は、 pull 通常のパッチ公開に introductory message として提出することで、メンテナがパッチをどのように統合するかを選べるようになります。

リクエスト pull 件名に [GIT] または [PULL] を記載する必要があります。リクエスト自体には、リポジトリ名とブランチ名を1行に記載し、以下のように記載するのが一般的です：

Please pull from

    git://jdelvare.pck.nerim.net/jdelvare-2.6 i2c-for-linus

to get these changes:

リクエスト pull さらに、含まれる内容を簡潔に説明する一般的なメッセージ、パッチ一覧を git shortlog使用して、パッチシリーズの影響についての概要を diffstat使用して記載する必要があります。すべての情報を取得する最も簡単な方法は、当然のことながら、 git コマンドを使用してすべてを任せることです。 git request-pull.

一部のメンテナ（リンスを含む）は、リクエストを確認したいと考えています。 pull GPGで署名されたコミット; これにより、リクエストが本当にあなた自身が行ったものであることをより確実に保証できます。このような署名付きのラベルがなければ、特にリンスはGitHubなどの公開サイトからのパッチを一切受け取りません。

この署名付きラベルを作成するための最初のステップは、GNUPGの鍵を作成し、それをカーネルの主要な開発者1人または複数によって署名してもらうことです。これは新規開発者にとって難しいかもしれませんが、他の選択肢はありません。カンファレンスに参加するのも、あなたの鍵を署名してくれる開発者を見つけるための良い方法です。

パッチシリーズを準備し、 git誰かがそれを取り扱いたい場合、以下のコマンドで署名付きラベルを作成してください git tag -sこれにより、あなたの秘密鍵で作成された署名を含むシリーズの最後のコミットを特定する新しいラベルが作成されます。また、このラベルに変更履歴メッセージを追加する機会もあります。これは、リクエストの効果を説明するのに最適な場所です。 pull.

メンテナがパッチを取得するソースが、あなたが作業しているリポジトリのソースと異なる場合、公開ソースにも署名付きラベルをアップロードしないと忘れずに。

リクエストを生成する際、 pull署名付きラベルをターゲットとして使用してください。次のコマンドのようなもので目的を果たします:

git request-pull master git://my.public.tree/linux.git my-signed-tag

Linuxカーネル用コードスタイル¶

これはLinux Kernel用のコードスタイルの簡単なドキュメントです。コードスタイルは非常に個人的で、私は誰もを強制的に私のスタイルを受け入れることを望んでいませんが、 強制する 誰もを私のスタイルを受け入れることを強制するのではなく、このスタイルは私がメンテナンスできるすべてのものに使用されるべきです。また、多くの他のことも含めてこのスタイルを好んでいます。少なくとも、ここで述べた観点を考慮してください。

私が最初に提案するのは、GNUのコーディング標準のコピーを印刷して、読まないことです。それを燃やして、それは大きな象徴的な行動です。

しかし、以下がポイントです：

1) インデント幅¶

タブ（tab）は8文字で、インデントも同様です。一部の異端者たちは4（または2！）文字のインデント幅を望んでいますが、これは円周率の値を3に定義する試みに似ています。

理由：インデントの目的は、制御構造のブロックがどこで始まり、どこで終わるかを明確にすることです。特に20時間もファイルを睨み続けた後、インデント幅が広い方がレベルを理解するのがはるかに簡単です。

さて、一部の人たちは8文字のインデント幅がコードを右にずらしすぎて、80文字幅の画面で読みにくくなると主張します。その主張に対する答えは、もし3段以上のインデントが必要なら、あなたのプログラムはすでに不適切で修正が必要です。

要するに、8文字のインデント幅は読みやすさを高め、またあなたの関数のネストが深すぎるときに警告を出します。この警告をよく覚えておいてください。

switch構文のインデントを容易にするために、キーワード switch とそのサブ要素を case同じ列に揃えることが好ましいです。これにより、 caseの二重インデントを避けることができます。例：

switch (suffix) {
case 'G':
case 'g':
        mem <<= 30;
        break;
case 'M':
case 'm':
        mem <<= 20;
        break;
case 'K':
case 'k':
        mem <<= 10;
        /* fall through */
default:
        break;
}

何かを隠す必要がない限り、1行に複数のステートメントを書かないでください：

if (condition) do_this;
  do_something_everytime;

また、1行に複数の代入を書かないでください。カーネルのスタイルは極めてシンプルです。複雑な式は避けてください。

コメントやドキュメンテーション、Kconfigを除き、インデントにはスペースは使われません。上の例は意図的に誤っています。

良いテキストエディタを手に入れ、行末の空白文字を残さないでください。

2) 長い行と文字列の折り返し¶

コードスタイルは、一般的なツールを用いて読みやすさとメンテナビリティを重視します。

行の最大文字数は80文字で、これは強く望まれる制限です。

80文字を超える長い式は、読みやすさを損なわずに情報を隠さない限り小さな塊に分割されます。導出された塊は元の式よりはるかに短く、より右に配置されます。ヘッダーファイルにおいても、引数リストが非常に長い関数については同様の適用がされます。ただし、ユーザーが見られる文字列（printkメッセージなど）は決して分割しないでください。なぜなら、grepで検索する機能を妨げてしまうからです。

3) かっことスペースの配置¶

C言語のスタイルについて話すとき、常に直面する問題の一つが、かっこの配置です。インデントのサイズとは異なり、技術的な理由に基づいて特定の配置戦略を選ぶ理由はありません。ただし、KernighanとRitchieが示したように、行の最後に開き括弧を置き、次の行の最初に閉じ括弧を置くのが好ましいです。以下のようにします：

if (x is true) {
        we do y
}

これは、関数でないすべての式に適用されます（if、switch、for、while、doなど）。例えば：

switch (action) {
case KOBJ_ADD:
        return "add";
case KOBJ_REMOVE:
        return "remove";
case KOBJ_CHANGE:
        return "change";
default:
        return NULL;
}

ただし、特別なケースとして関数があります。関数では開き括弧を次の行の先頭に置きます。以下のように：

int function(int x)
{
        body of function
}

世界中の異端者たちはこの不一致を…まあ…矛盾していると主張しますが、合理的な人々は（a）K&Rが 正しい （b）K&Rが正しいことを知っています。それ以外にしても、関数は特別な存在です（Cではネストできません）。

閉じ括弧は常に1行に配置されますが、 例外 の場合は、同じ式の続きに続くため、 while do-while式の場合、または else if-else式の場合、例えば以下のように：

do {
        body of do-loop
} while (condition);

e

if (x == y) {
        ..
} else if (x > y) {
        ...
} else {
        ....
}

理由：K&R。

さらに、この配置は空行の数を最小限に抑えながらも読みやすさを失いません。これにより、画面の行数が限られている（例：25行のターミナル）ため、空行にコメントを追加して埋めることができます。

単一の式で十分な場合、かっこは無駄に使用しないでください。

if (condition)
        action();

e

if (condition)
        do_this();
else
        do_that();

ただし、if-else式のどちらか一方の分岐にのみ単一の式がある場合、両方の分岐にかっこを使用してください：

if (condition) {
        do_this();
        do_that();
} else {
        otherwise();
}

さらに、ループが複数のステートメントを含む場合、かっこを使用してください：

while (condition) {
        if (test)
                do_something();
}

3.1) スペース¶

Linuxカーネルのスタイルでは、スペースの使用は（主に）関数とキーワードによって決まります。キーワードの後には（ほぼすべてのキーワードに対して）スペースを1つ入れます。例外は明らかにsizeof、typeof、alignof、および__attribute__です。これらは関数に非常に似た見た目を持ち、Linuxでは通常括弧を使用します（言語的には必要ではありませんが）、例えば sizeof info 宣言した後 struct fileinfo info).

以下のキーワードの後にはスペースを1つ入れます：

if, switch, case, for, do, while

ただし、sizeof、typeof、alignof、または__attribute__にはスペースを付けません。例えば、

s = sizeof(struct file);

括弧内に式がある場合は、その周辺にスペースを付けません。この例は 悪い:

s = sizeof( struct file );

変数や関数（関数がポインタを返す場合）をポインタで宣言する際、アスタリスクの位置は変数名または関数名に隣接するべきであり、型名に隣接するべきではありません。例： * 二項演算子や三項演算子の周辺にはスペースを1つ入れます。以下の例のように：

char *linux_banner;
unsigned long long memparse(char *ptr, char **retptr);
char *match_strdup(substring_t *s);

ただし、一項演算子の後にはスペースを付けません：

=  +  -  <  >  *  /  %  |  &  ^  <=  >=  ==  !=  ?  :

後置一項演算子の後にはスペースを付けません：

&  *  +  -  ~  !  sizeof  typeof  alignof  __attribute__  defined

前置一項演算子の後にはスペースを付けません：

++  --

構造体メンバの演算子にはスペースを付けません

++  --

行末に空白を残さないでください。一部のエディタではインデント処理中に新しい行の先頭に適切な空白を自動的に挿入します。そのため、次の行のコードをすぐに記述できます。ただし、これらのエディタは新しい行に何も記述しない場合（例えば空行を残す場合）にこれらの空白を削除しないことがあります。結果として、行末に空白が残る行が発生します。 . e ->.

Gitはこれらの行末の空白を追加した変更を警告します。また、オプションで自動的に削除することもできます。ただし、複数の変更を適用する場合、この処理により後の変更が失敗する可能性があります。 furba 4) 名前の割り当て

5) 型の定義（typedef）¶

以下のものは使用しないでください： vps_t。構造体やポインタのtypedefは、 間違いです。ソースコードで以下のコードを見たとき、

vps_t a;

は何を意味するのでしょうか？もし、以下のようであれば：

struct virtual_container *a;

と書かれていたら、実際に何であるかを説明できます。 a.

多くの人が型の定義 migliori la leggibilitàと誤解しています。それほどではありません。有用なのは：

  1. 完全に不透明なオブジェクト（typedefがその目的で使用される場所で、 隠す オブジェクトの実際の内容を隠します）です。

    例: pte_t などは、関数の補助関数のみで操作可能な不透明オブジェクトです。

    注意

    不透明オブジェクトと funzioni accessorie は、それ自体では良いものではありません。pte_tなどにこのようなものがある理由は、実際には移植可能な情報がまったくないからです。

  2. 明確な整数型では、抽象化 が役立ち、 それが整数であることを誤解するのを防ぎます。 int または long.

    u8/u16/u32はtypedefとして完全に受け入れ可能な表現です。ただし、これは（d）カテゴリに属するのではなく、このカテゴリに属します。

    注意

    さらに、 正しい を設ける必要があります。何かが unsigned longである場合、

    typedef unsigned long myfalgs_t;

    のようなものは必要ありません。ただし、特定の状況で unsigned int になる可能性があり、 unsigned long他の構成でもそうである場合、typedefは良い選択肢です。

  3. あまりに文字列リテラルを 新しい 検証を行うタイプ

  4. 例外的な状況で、C99標準で定義されたタイプと同一の新しいタイプが定義されます。

    標準タイプの使用に目と脳を慣らすには時間がかかりませんが、 uint32_tしかし、一部の人々はその使用を反対しています。

    そのため、Linux固有のタイプ u8/u16/u32/u64 およびその符号付き同等物は標準タイプと同一ですが、新しいコードでは必須ではありません。

  5. ユーザー空間の安全なタイプ

    ユーザー空間から見えるデータ構造では、C99タイプや以前に説明したさまざまなタイプの使用を要求できません。 u32 そのため、ユーザー空間と共有するすべてのデータ構造で__u32や同様のタイプを使用します。

他の有効なケースがあるかもしれませんが、基本的なルールはここに記載されたルールのいずれかに該当しない限り、決してtypedefを使用しないことです。

一般的に、直接的にアクセス可能なポインタや構造体は 決して typedefで定義すべきではありません。

6) 関数¶

関数は短く、かわいく、1つのことだけを行うべきです。1〜2画面（ISO/ANSI標準では80x24）に収まるようにし、1つのことだけを丁寧に実行する必要があります。

関数の最大長さはその複雑さとインデントレベルに逆比例します。したがって、概念的に単純ですが、長く（ただし単純）なケースごとの処理を多数含む実装の場合、関数が長くても問題ありません。

ただし、複雑な関数で、高校1年生の普通の生徒がその機能を理解できないと懸念する場合は、厳密に制限を守るべきです。説明的な名前のサポート関数を使用してください（パフォーマンス向上のためにコンパイラにインライン化を依頼するのもあり、コンパイラがより良い結果をもたらす可能性があります）。

関数のもう一つの指標はローカル変数の数です。5〜10を越えると何か間違いをしている可能性があります。関数を再考し、小さな部分に分割してください。一般的に、人間の脳は7つの異なることを簡単に追えるので、それ以上は混乱します。あなたは優秀ですが、2週間前に行っていたことを理解したいかもしれません。

ソースファイルでは、関数を空行で区切ってください。関数がエクスポートされている場合、そのマクロ EXPORT はこの関数の閉じ括弧の行の直後に即座に記述する必要があります。例えば：

int system_is_up(void)
{
        return system_state == SYSTEM_RUNNING;
}
EXPORT_SYMBOL(system_is_up);

関数プロトタイプでは、パラメータ名とその型を含めてください。これはC言語では必須ではありませんが、Linuxでは読み手にとって重要な情報を簡単に追加できるため、推奨されます。

関数プロトタイプで extern を使用しないでください。これは行を長くし、厳密には必要ではありません。

7) 関数の戻り値を中央で統合する¶

多くの人が非推奨としているgoto文ですが、コンパイラは無条件ジャンプとして頻繁に使用しています。

関数が複数のエクスポートポイントを持ち、共通のクリーンアップ処理が必要な場合、goto文は役立ちます。何もクリーンアップしなくても、直接戻るだけでよいです。

ラベルに名前を付けて、goto文の目的や存在理由を示してください。良い名前の例は out_free_buffer: gotoで（free）する bufferを示す名前です。GW-BASICのような名前（例： err1: ed err2:）は避けましょう。エクスポートポイントを追加・削除する際に並び替えが必要になり、正しいか確認するのが難しくなります。

goto文を使用する理由は：

  • 無条件ジャンプは理解しやすく追跡しやすい

  • ネストレベルが減る

  • エクスポートポイントを忘れずに更新する間違いを防げる

  • コンパイラが冗長なコードを最適化しやすい ;)

int fun(int a)
{
        int result = 0;
        char *buffer;

        buffer = kmalloc(SIZE, GFP_KERNEL);
        if (!buffer)
                return -ENOMEM;

        if (condition1) {
                while (loop1) {
                        ...
                }
                result = 1;
                goto out_free_buffer;
        }
        ...
out_free_buffer:
        kfree(buffer);
        return result;
}

注意すべき比較的一般的なバグは、 one err bugs のようなものです：

err:
        kfree(foo->bar);
        kfree(foo);
        return ret;

このコードのバグは、いくつかのエクスポートポイントで変数 foo がNULLであることです。通常、このバグはエラー処理を2つの部分に分けることで修正します。 err_free_bar: e err_free_foo::

err_free_bar:
       kfree(foo->bar);
err_free_foo:
       kfree(foo);
       return ret;

理想的には、エラー条件をシミュレートして、エクスポートパスを検証してください。

8) コメント¶

コメントは良いですが、過剰になるリスクもあります。決してコードの動作方法をコメントで説明しないでください。コードの動作が明らかであれば、コメントは不要です。下手に書いたコードを説明するのは時間の無駄です。

通常、コメントはコードが何をしているかを説明すべきで、どのように実装しているかを書くべきではありません。また、関数本体内にコメントを書くのを避けてください。関数が非常に複雑で、その内容を断片的にコメントする必要がある場合は、一度第6点に戻って見直すことをお勧めします。ただし、特に巧妙（または不適切）な部分を注記するための短いコメントは記述しても構いませんが、過度に長くなるのを避けましょう。代わりに、関数の冒頭にコメントを記述し、その関数が何をしているかを説明し、必要に応じてその理由も記載してください。

APIの関数をコメントする際は、kernel-doc形式を使用してください。詳細については、:ref:に記載されています。Documentation/translations/it_IT/doc-guide/ および script/kernel-doc.

複数行のコメント（長いコメント）のスタイルとして、以下のような形式が好ましいです：

/*
 * This is the preferred style for multi-line
 * comments in the Linux kernel source code.
 * Please use it consistently.
 *
 * Description:  A column of asterisks on the left side,
 * with beginning and ending almost-blank lines.
 */

net/ ディレクトリおよび drivers/net/ ディレクトリ内のファイルでは、複数行のコメントのスタイルがやや異なります。

/* The preferred comment style for files in net/ and drivers/net
 * looks like this.
 *
 * It is nearly the same as the generally preferred comment style,
 * but there is no initial almost-blank line.
 */

データのコメントも重要です。基本型や派生型のデータについてもコメントしてください。この目的で、1行に1つのデータを宣言し（複数行宣言にはコンマを用いない）、コメントを記載するスペースを確保してください。

これにより、kernelのスタイルに合わせて、以下のディレクトリ内のファイルでemacsがより適切に動作します： ~/src/linux-trees.

しかし、emacsで合理的なフォーマットが得られなくても、すべてが失われるわけではありません。以下のコマンドを使用してください： indent.

現在、GNU indentもGNU emacsと同様に混乱した設定を持っています。そのため、コマンドラインにいくつかのオプションを渡す必要があります。しかし、あまり恐れることはありません。GNU indentの開発者たちはK&Rスタイルの権威を認めているためです（GNUプロジェクトの人は悪意があるわけではなく、単にこの問題について誤解しているだけです）。したがって、indentに以下のオプションを渡してください： -kr -i8 (つまり K&R, 8 caratteri di indentazione), または以下のコマンドを使用してください： scripts/Lindent これにより、最新のスタイルでインデントをかけます。

indent は多くのオプションを持ち、特にコメントの再フォーマットを行う際にはmanページを確認することをお勧めします。ただし、覚えておいてください： indent それは悪いプログラミングのための修正ツールではありません。

注意してください。また、以下のようなことも利用できます clang-format これらのルールを助けるために、コードの一部を自動的に再フォーマットするのに、またはファイル全体を検査してスタイルの誤りや誤字脱字、さらには改善点を特定するのに役立ちます。また、変数/マクロを揃えたり、テキストを再配列したりするなど、似たような作業にも役立ちます。詳細については、ファイル #includeを参照してください clang-format.

10) Kconfig設定ファイル¶

すべてのKconfig*設定ファイル（ソースコード中に存在するもの）では、インデントの仕方がやや異なります。ある行の後に続く config の行はタブでインデントされ、説明文はさらに2つのスペースインデントされます。例:

config AUDIT
      bool "Auditing support"
      depends on NET
      help
        Enable auditing infrastructure that can be used with another
        kernel subsystem, such as SELinux (which requires this for
        logging of avc messages output).  Does not do system-call
        auditing without CONFIG_AUDITSYSCALL.

本当に危険な機能（特定のファイルシステムの書き込みサポートなど）は、タイトル文字列で明確に宣言する必要があります:

config ADFS_FS_RW
      bool "ADFS write support (DANGEROUS)"
      depends on ADFS_FS
      ...

Kconfig設定ファイルに関する詳しいドキュメンテーションは、ドキュメント Kconfig言語

11) データ構造¶

特定のスレッドの上下文を超えて可視性を持つデータ構造は、常に参照カウンターを備える必要があります。カーネルには garbage collector (カーネル外では garbage collector は遅く効率が悪い), これは意味しますが 必ず すべてのものを使用する際には、参照カウンターを備える必要があります。

参照カウンターを備えることで、同期を回避でき、複数のユーザーがデータ構造に同時にアクセスできるようになります。また、プロセスが一時的に処理を中断していたとしても、データ構造が突然見えなくなる心配はありません。

注意してください。同期 ではなく は参照カウンターの代わりに使用されます。同期はデータ構造の整合性を保つためのもので、参照カウンターはメモリ管理の技術です。通常、両方の技術が必要であり、混同してはいけません。

複数のユーザークラスがある場合、データ構造は2段階の参照カウンターを持つことができます。クラスカウンターはそのユーザー数を、グローバルカウンターはクラスカウンターがゼロになるときに1回だけ減算されます。

このような多段階参照カウンターの例は、メモリ管理（struct mm_sturct: mm_userとmm_count)、およびファイルシステムコード（struct super_block: s_countとs_active)に見られます。

覚えておくべきことは、他のスレッドがお使いのデータ構造を見つけられる場合、それに参照カウンタを持たなければほぼ間違いなくバグがあります。

12) マクロ、列挙型およびRTL¶

定数を定義するマクロや列挙型のラベルはすべて大文字で書きます。

#define CONSTANT 0x12345

複数の関連する定数を定義する際には、列挙型を優先してください。

大文字で書かれたマクロ名は好ましいですが、関数に似たマクロは小文字で書くことができます。

インライン関数は、関数に見えるマクロよりも一般的に好ましいです。

複数のステートメントを含むマクロは常にdo - whileブロックで囲むべきです：

#define macrofun(a, b, c)                       \
        do {                                    \
                if (a == 5)                     \
                        do_this(b, c);          \
        } while (0)

マクロを使用する際は避けなければならないこと：

  1. コードの制御フローに影響を与えるマクロ：

#define FOO(x)                                  \
        do {                                    \
                if (blah(x) < 0)                \
                        return -EBUGGERED;      \
        } while (0)

sono proprio それは明らかに悪いアイデアです。関数呼び出しのように見えますが、呼び出し元の関数を終了させます。コードを読む人の内部デコードを壊そうとしないでください。

  1. ローカル変数にマジックな名前を使用するマクロ：

#define FOO(val) bar(index, val)

それは一見良いように見えますが、コードを読む人が混乱し、無害に見える変更で壊す可能性があります。

3) 引数としてl-valueとして使用されるマクロの引数：これは、例えばFOOをインライン関数に変換した場合に逆効果になる可能性があります。

4) 漏れの優先順位を忘れる：式を定義するマクロは括弧で囲む必要があります。パラメータ付きマクロでも同様の問題に注意してください。

#define CONSTANT 0x4000
#define CONSTEXP (CONSTANT | 3)

5) 関数に見えるマクロでローカル変数を定義する際の名前空間の衝突：

#define FOO(x)                          \
({                                      \
        typeof(x) ret;                  \
        ret = calc_ret(x);              \
        (ret);                          \
})

retはローカル変数の一般的な名前ですが、__foo_retは既存の変数と衝突しにくいです。

cppマニュアルはマクロについて詳しく説明しています。gcc開発マニュアルは、カーネルでよく使われるアセンブリ言語のRTLについてもカバーしています。

13) カーネルのメッセージを表示する¶

カーネル開発者たちは博士のように見られたいです。正字を気を配り、良い印象を与えましょう。英語では、"OK"や"API"などの略語の誤った使用を避けてください。 dont: 使います do not または don't. 短く、明確で、誤解の余地のないメッセージを書くようにしてください。

カーネルのメッセージは句点で終わらせません。

括弧内に数字を書く（%d）ことは何も改善せず、そのため避けましょう。

linux/device.h には、デバイスとドライバに正しくメッセージを関連付けるための診断用マクロがあります。dev_err()、dev_warn()、dev_info() など、適切にラベルを付けてください。デバイスに結びつかないメッセージについては、linux/printk.h が定義しています。 pr_info(), pr_warn(), pr_err()など。

デバッグメッセージを抽出するのは本当の挑戦です。しかし、取得したメッセージはリモートでの問題解決に大変役立ちます。ただし、デバッグメッセージは他のメッセージと異なり特別に扱われます。pr_XXX() 関数は条件に関係なく出力しますが、 pr_debug() no; これはデフォルトのコンフィギュレーションに組み込まれません。DEBUG または CONFIG_DYNAMIC_DEBUG が設定されている場合を除きます。dev_dbg() 同様に、VERBOSE_DEBUG を設定することで dev_vdbg() のメッセージも追加されます。

多くのサブシステムは Kconfig のデバッグオプションを持ち、対応する Makefile に -DDEBUG を追加します。また、特定のファイルに #define DEBUG を追加する場合もあります。最後に、デバッグメッセージを常に出力する必要がある場合（例: #ifdef で囲まれたデバッグセクション内）、printk(KERN_DEBUG …) を使用してください。

14) メモリを割り当てる¶

カーネルは次の一般的なメモリ割り当て関数を提供しています： kmalloc(), kzalloc(), kmalloc_array(), kcalloc(), vmalloc(), e vzalloc()さらに詳しい情報が必要な場合は、API ドキュメンテーションを参照してください： メモリ割当ガイド

構造体のサイズを渡す最適な方法は次の通りです：

p = kmalloc(sizeof(*p), ...);

構造体名を完全に書く形式は可読性を低下させ、ポインタの型が変化した場合でも sizeof の更新が行われない可能性があるため、潜在的なバグを引き起こします。

戻り値は void ポインタであり、これをキャストするのは冗長です。C 言語では void ポインタと任意のポインタ型の間の変換が保証されています。

ベクターを割り当てる最適な方法は次の通りです：

p = kmalloc_array(n, sizeof(...), ...);

ゼロ埋めベクターを割り当てる最適な方法は次の通りです：

p = kcalloc(n, sizeof(...), ...);

どちらも割り当てサイズ n * sizeof(…) におけるオーバーフローを検証し、発生した場合は NULL を返します。

これらの一般的なアロケータは一つの スタックダンプ 失敗した場合、__GFP_NOWARN を明示的に指定しない限り、。したがって、これらのアロケータが NULL ポインタを返した場合、追加のメッセージ出力はほとんどの場合無駄です。

15) インラインの病気¶

gcc が「より速くする」ための特別なオプションとして「rendimi più veloce」を備えているという誤解があるようです。 inlineいくつかのケースではインラインの使用は適切です（マクロの代わりとして、第12章を参照）、しかし非常に多くのケースでは適切ではありません。インラインキーワードの過剰な使用は、コアサイズを大きくし、結果としてCPUの指令キャッシュが大きくなるため、全体としてシステムが遅くなる原因になります。また、キャッシュページのスペースが少なくなるため、全体的に遅くなるのです。ちょっと考えてみてください。キャッシュミスはディスクへのアクセスを必要とし、これは5ミリ秒程度かかることがあります。この5ミリ秒の間に、たくさんのCPUサイクルが使われています。

多くの人が、静的宣言で1回しか使わない関数にインラインを追加することは常に最善の選択肢だと考えています。これは技術的に正しいですが、gccは自動的にこれらの関数をインライン化できます。コードのメンテナンスにおいて、2番目のユーザーが現れたときにインラインを削除する作業の手間は、gccにインライン化を指示する潜在的な利点を上回るため、このアプローチは推奨されません。

16) ファンクションの名前と戻り値¶

関数はさまざまな型の値を返すことができ、そのうち最も一般的なのは、関数が成功して終了したか否かを示す値です。この値は、整数型のエラーコード（-Exxx = 失敗、0 = 成功）か、ブール型の成功フラグ（0 = 失敗、非ゼロ = 成功）で表現できます。

これらの2つの表現タイプを混在させることは、非常に危険なバグの温床になります。C言語が整数とブール型を明確に区別していたら、コンパイラがこれらのエラーを自動的に検出してくれますが、現状ではその機能はありません。このようなバグに遭遇しないようにするため、常に以下のコンベンションを守ってください。

Se il nome di una funzione è un'azione o un comando imperativo,
essa dovrebbe ritornare un codice di errore intero.  Se il nome
è un predicato, la funzione dovrebbe ritornare un booleano di
"successo"

例えば、 add work はコマンドであり、add_work()関数は成功時は0、失敗時は-EBUSYを返します。同様に、 PCI device present は述語であり、関数 pci_dev_present() は成功して該当デバイスを見つけた場合1を、それ以外は0を返します。

すべてのエクスポート関数（EXPORT）はこのコンベンションを守るべきですし、すべてのパブリック関数も同様にすべきです。プライベート関数（static）はこのコンベンションを守らなくても良いですが、できれば守るべきです。

戻り値が計算結果そのものであるかわりに、計算の成功を示すものではない関数については、このルールの対象外です。通常はエラーを示すために、範囲外の値を返すことでエラーを示します。典型的な例はポインタを返す関数で、これらはNULLまたはERR_PTRをエラー通知のためのメカニズムとして使用します。

17) boolの使用¶

Linuxカーネルではbool型はC99標準の_Bool型から導出されています。bool型は0または1の値のみをとることができ、明示的または暗黙的なboolへの変換は値を真（true)または偽（false)に変換します。bool型を使用する場合、!!構文はもはや必要なく、これによりいくつかのバグが排除されます。

論理値を使用する際は、trueとfalseの定義を使用して1と0の代わりに、論理値を表すべきです。

関数の戻り値やスタック上の変数についてはbool型の使用は常に適切です。可読性を高めるため、bool型の使用を推奨します。boolean値の処理において、int型よりもしばしば優れています。

キャッシュラインの順序やサイズが重要である場合はbool型を使用しないでください。サイズやアライメントはコンパイル対象のアーキテクチャによって異なります。アライメントやサイズを最適化した構造体はbool型を使用すべきではありません。

構造体に多数のtrue/false値がある場合、1ビットのフィールドを使用してまとめるか、固定幅の型（例：u8）を使用することを検討してください。

関数の引数同様に、多数のtrue/false値は「flags」と呼ばれる1ビットの引数にまとめることができます。true/falseの定数値がある場合、「flags」はしばしば読みやすさの観点からより良い選択肢です。

このような点を踏まえ、データ構造や引数においてbool型を節約的に使用することで可読性が向上します。

18) カーネルのマクロを再発明しないでください¶

include/linux/kernel.hヘッダーファイルには、カスタムの実装ではなく既存のマクロを使用すべきです。例えば、ベクトルの長さを計算する場合、以下のマクロを使用してください：

#define ARRAY_SIZE(x) (sizeof(x) / sizeof((x)[0]))

同様に、構造体のフィールドのサイズを計算する場合、

#define sizeof_field(t, f) (sizeof(((t*)0)->f))

min()とmax()というマクロも存在し、必要に応じて型の厳密なチェックを行います。このヘッダーファイルを丁寧に読み、自分のコードで再実装すべきでない定義を確認してください。

19) エディタの設定行や他の雑多な設定¶

一部のエディタは、ソースファイル内に埋め込まれた特別なマーカーで示された設定パラメータを解釈できます。例えば、emacsは以下のようになります:

-*- mode: c -*-

またはこのような形式:

/*
Local Variables:
compile-command: "gcc -DMAGIC_DEBUG_FLAG foo.c"
End:
*/

vimはこのようなマーカーを以下のように解釈します:

/* vim:set sw=8 noet */

ソースファイルにこれらの設定を含めないでください。ユーザー各自がエディタのカスタマイズ設定を持ち、あなたのソースがそれを上書きしないようにしてください。これはインデント設定やモード設定にも同じく適用されます。ユーザーがカスタマイズしたモードを設定している場合や、インデントをうまく動かすための特別な設定をしている可能性があります。

20) インラインアセンブリ¶

特定のアーキテクチャ向けのコードでは、 インラインアセンブリ プロセッサやプラットフォーム固有の機能とインターフェースする必要がある場合があります。必要に応じて自由に使用してください。ただし、C言語で同等の処理が可能であれば、無理にアセンブリを使用しないでください。可能な限りC言語でハードウェアを操作してください。

共通のアセンブリコードをまとめたシンプルな関数を書くことを検討してください。小さな変種を繰り返し書くのではなく、コードの再利用を意識してください。また、 インラインアセンブリ C言語のパラメータを活用できます。

複雑なアセンブリコードは.Sファイルに配置し、ヘッダーファイルで対応するCのプロトタイプ宣言を定義してください。アセンブリ関数のCプロトタイプは asmlinkage.

GCCが副作用がないと判断してコードを削除しないようにするには、asmコードをvolatileにマークする必要があります。ただし、常に必要とは限りません。不要にvolatileを指定すると最適化が制限される可能性があります。

単一の式で複数の命令を含む場合、 インラインアセンブリ 各命令を別の文字列と行に配置してください。最後の文字列/命令を除き、各行末には \n\t を付けて、生成されるアセンブリを正しくアライメントしてください:

asm ("magic %reg1, #42\n\t"
     "more_magic %reg2, %reg3"
     : /* outputs */ : /* inputs */ : /* clobbers */);

21) 条件付きコンパイル¶

可能な限り、.cファイル内で#if、#ifdefなどのプリプロセッサの条件式を使わないでください。このような処理はコードを読みにくくし、追跡困難にします。代わりに、ヘッダーファイル内でこれらの条件式を使って関数を定義し、#elseでstub（ダミー）関数を提供し、その後で条件式を使わずにこれらの関数を呼び出すようにしてください。コンパイラはstub関数のコードを生成せず、同じ結果を出力し、論理はシンプルに保たれます。

全体の関数をコンパイルするのではなく、部分的な関数や式の一部をコンパイルする方が望ましいです。式内でifdefを使う代わりに、式の一部または全部を関数に分解し、その関数に条件式を適用してください。

ある変数や関数が特定の構成で使用されない可能性がある場合、コンパイラが未使用定義の警告を出すことがあります。このような場合、__maybe_unused属性で定義をマークする方が望ましいです（ただし、変数や関数が常に未使用の場合は、削除してください）。 常に 未使用の場合は削除してください。

コード内で可能であれば、KconfigシンボルをC言語の論理式に変換するためのマクロIS_ENABLEDを使用し、古典的なC言語の条件式として使用してください：

if (IS_ENABLED(CONFIG_SOMETHING)) {
        ...
}

コンパイラは条件式を定数評価（constant-fold）し、#ifdefのようにコードブロックを含むか含まないかを判断します。したがって実行時間に影響を与えません。しかし、コンパイラが条件式ブロック内のコードを確認し、構文や型、シンボル参照などの正しさを検証できるため、条件式ブロック内のコードが条件を満たした場合にのみ存在する場合は、#ifdefを依然として使用する必要があります。

長い#ifや#ifdefブロック（複数行）の終わりには、#endifと同じ行にコメントで終了条件を記載してください。例えば：

#ifdef CONFIG_SOMETHING
...
#endif /* CONFIG_SOMETHING */

如何让你的改动进入内核¶

Linux内核に変更を提出したい個人や企業にとって、ルールを知らないと提出プロセスは恐ろしく思えるかもしれません。このドキュメントでは、あなたの変更が受け入れられやすくなるためのいくつかのアドバイスをまとめました。

以下文档含有大量简洁的建议， 具体请见： Documentation/process 同样，Linuxカーネルパッチ提出チェックリスト 给出在提交代码前需要检查的项目的列表。如果你在提交一个驱动程序，那么 同时阅读一下: Linux Kernel用ドライバの提出

多くのステップはGitバージョン管理システムのデフォルト動作を説明しています。Gitを使ってパッチを準備する場合、多くの機械的な作業を自動で行いますが、依然として合理的なパッチのセットを準備・記録する必要があります。一般的に、Gitを使うことで内核開発者の生活は楽になります。

0) 获取当前源码树¶

現在の内核ソースコードのリポジトリを持っていない場合は、gitを使って取得してください。あなたが開始するにはメインラインリポジトリが必要です。以下のように取得できます:

git clone git://git.kernel.org/pub/scm/linux/kernel/git/torvalds/linux.git

ただし、メインラインツリーに直接開発するのを望まないかもしれません。ほとんどのサブシステムメンテナは自分のツリーを運用しており、これらのツリー向けにパッチを準備してもらうのが望ましいです。詳しくはMAINTAINERSファイルのサブシステムの T: 项以查找该树，或者简单地询问维护者该树是否未在其中列出。

依然としてtarballから内核バージョンをダウンロードできます（次のセクションで説明します）。ただし、これは内核開発を行うには困難な方法です。

1) "diff -up"¶

パッチを作成するには"diff -up"または"diff -uprN"を使用してください。

すべての内核の変更はパッチとして提示されます。パッチはdiff(1)で生成されます。パッチを作成する際には"unified diff"形式で作成することを確認してください。これはdiff(1)の'-u'パラメータで生成されます。また、'-p'パラメータを使用して、各変更がどのC関数にあるかを表示させることで、生成されたパッチは読みやすくなります。パッチは内核ソースコードツリーのルートディレクトリに基づいて作成し、サブディレクトリではなく、ルートディレクトリを基準にします。

为一个单独的文件创建补丁，一般来说这样做就够了:

SRCTREE=linux
MYFILE=drivers/net/mydriver.c

cd $SRCTREE
cp $MYFILE $MYFILE.orig
vi $MYFILE      # make your change
cd ..
diff -up $SRCTREE/$MYFILE{.orig,} > /tmp/patch

複数のファイルのパッチを作成するには、変更されていない内核ソースコードツリーを展開し、自分のコードツリーと差分を比較してください。例えば:

MYSRC=/devel/linux

tar xvfz linux-3.19.tar.gz
mv linux-3.19 linux-3.19-vanilla
diff -uprN -X linux-3.19-vanilla/Documentation/dontdiff \
        linux-3.19-vanilla $MYSRC > /tmp/patch

"dontdiff"はコンパイル時に内核が生成するファイルの一覧で、差分（diff(1)）で生成されるパッチではこれらのファイルがスキップされます。

あなたのパッチに含まれるファイルが今回のパッチ投稿に含まれるべきでないものを含まないことを確認してください。diff(1)でパッチを生成した後、パッチを確認して正確であることを確認してください。

如果你的改动很散乱，你应该研究一下如何将补丁分割成独立的部分，将改动分 割成一系列合乎逻辑的步骤。这样更容易让其他内核开发者审核，如果你想你的 补丁被接受，这是很重要的。请参阅： 3) 拆分你的改动

如果你用 git , git rebase -i 可以帮助你这一点。如果你不用 git, quilt <https://savannah.nongnu.org/projects/quilt> 另外一个流行的选择。

2) 描述你的改动¶

描述你的问题。无论您的补丁是一行错误修复还是5000行新功能，都必须有一个潜在 的问题激励您完成这项工作。让审稿人相信有一个问题值得解决，让他们读完第一段 是有意义的。

ユーザーが見える影響を記述してください。直接的なクラッシュやロックは非常に説得力がありますが、すべてのエラーがそうではありません。コードレビュー中にこの問題が発見されたとしても、ユーザーに与える影響を記述してください。ほとんどのLinuxインストールでは、セカンドスタビリティツリーまたはベンダー/製品固有のツリーから内核が実行され、アップストリームから選別された特定のパッチのみが適用されるため、補正の場面、DMESGの抜粋、クラッシュの説明、パフォーマンスの後退、遅延のピーク、ロックなど、ダウンストリームに情報を伝えるための内容を含めてください。

パフォーマンス、メモリ使用量、スタック使用量、バイナリサイズなどの最適化やトレードオフを数値で示してください。ただし、見えないコストも記述してください。最適化は通常無料ではありません。CPU、メモリ、可読性の間でトレードオフが行われたり、探索的な作業で異なるワークロード間でトレードオフが行われたりします。最適化の予想される欠点を記述することで、レビュアーがコストと利益を比較できるようにしてください。

一旦问题建立起来，就要详细地描述一下您实际在做什么。对于审阅者来说，用简单的 英语描述代码的变化是很重要的，以验证代码的行为是否符合您的意愿。

補丁の説明をフォームに記載し、このフォームをLinuxのソースコード管理システムgitの「コミットログ」として簡単に取り込めると、メンテナは非常に感謝します。見 15) メールヘッダー（In-Reply-To）の明確な返信.

每个补丁只解决一个问题。如果你的描述开始变长，这就表明你可能需要拆分你的补丁。 请见 3) 拆分你的改动

補丁または補丁シリーズを送信または再送信する際には、補丁の説明と理由を含めてください。補丁（シリーズ）のバージョン番号を単に述べるのではなく、補丁（シリーズ）の説明と理由を含めてください。サブシステムメンテナが以前の補丁バージョンを参照したり、URLを介して補丁説明を検索して補丁に含めるのを期待しないでください。つまり、補丁（シリーズ）とその説明は独立してあるべきです。これはメンテナとレビュアーにとっても有益です。一部のレビュアーは補丁の早期バージョンを受信していない可能性があります。

命令形の語で変更を記述してください。例えば"make xyzzy do frotz"ではなく"[この補丁]make xyzzy do frotz"や"[私は]xyzzyをdo frotzに変更した"のように、コードベースを変更するように命令するようにしてください。

補丁が記録されたバグチケットを修正する場合、バグチケット番号とURLで参照してください。メールリストのディスカッションから補丁が来た場合、メールリストアーカイブのURLを提供してください。使用する Message-ID 的 https://lkml.kernel.org/ 重定向，以确保链接不会过时。

ただし、外部リソースなしであなたの説明が理解可能であることを心がけてください。メールリストアーカイブやバグのURLを提供した後でも、補丁を提出する際の関連するディスカッションの要点を要約してください。

特定のコミットを参照する際には、コミットのSHA-1 IDだけでなく、コミットの一行のサマリを含めてください。レビュアーがそのコミットについて何についてのものかを理解できるようにしてください。例えば:

Commit e21d2170f36602ae2708 ("video: remove unnecessary
platform_set_drvdata()") removed the unnecessary
platform_set_drvdata(), but left the variable "dev" unused,
delete it.

少なくとも前12桁のSHA-1 IDを使用してください。内核リポジトリには*多くの*オブジェクトが含まれており、短いIDで衝突する可能性が非常に高いです。覚えておくべきは、現在は6文字のIDで衝突しない場合でも、5年後に状況が変わる可能性があることです。

如果修补程序修复了特定提交中的错误，例如，使用 git bisct 、前12文字のSHA-1 IDを使用した"Fixes:"タグと一行のサマリを使用してください。タグを複数行に分けることなく、分析スクリプト"75列の改行"ルールに従う必要はありません。例えば:

Fixes: 54a4f0239f2e ("KVM: MMU: make kvm_mmu_zap_page() return the number of pages it actually freed")

下列 git config 设置可以添加让 git log, git show 漂亮的显示格式:

[core]
        abbrev = 12
[pretty]
        fixes = Fixes: %h (\"%s\")

3) 拆分你的改动¶

将每个逻辑更改分隔成一个单独的补丁。

あなたの変更がバグ修正とパフォーマンス最適化を同時に含む場合、これらの変更を2つ以上のパッチファイルに分割してください。あなたの変更がAPIの変更を含み、ドライバが新しいAPIに適応するように変更されている場合、これらの変更を2つのパッチに分割してください。

另一方面，如果你将一个单独的改动做成多个补丁文件，那么将它们合并成一个 单独的补丁文件。这样一个逻辑上单独的改动只被包含在一个补丁文件里。

如果有一个补丁依赖另外一个补丁来完成它的改动，那没问题。简单的在你的补 丁描述里指出“这个补丁依赖某补丁”就好了。

在将您的更改划分为一系列补丁时，要特别注意确保内核在系列中的每个补丁之后 都能正常构建和运行。使用 git bisect 来追踪问题的开发者可能会在任何时 候分割你的补丁系列；如果你在中间引入错误，他们不会感谢你。

如果你不能将补丁浓缩成更少的文件，那么每次大约发送出15个，然后等待审查 和集成。

4) 检查你的更改风格¶

检查您的补丁是否存在基本样式冲突，详细信息可在 Linuxカーネルコードスタイル 中找到。如果不这样做，只会浪费审稿人的时间，并且会导致你的补丁被拒绝，甚至 可能没有被阅读。

一个重要的例外是在将代码从一个文件移动到另一个文件时——在这种情况下，您不应 该在移动代码的同一个补丁中修改移动的代码。这清楚地描述了移动代码和您的更改 的行为。这大大有助于审查实际差异，并允许工具更好地跟踪代码本身的历史。

送信前に、パッチスタイルチェックスクリプト（scripts/check patch.pl）でパッチをチェックしてください。ただし、スタイルチェックスクリプトはガイドラインとしてではなく、人間の判断の代替として扱うべきではありません。あなたのコードがより良ければ、スタイルチェックスクリプトに違反していても、使用しないほうが良いでしょう。

检查者报告三个级别：

  • ERROR：間違いが起こりやすいこと

  • WARNING：注意深くレビューが必要なこと

  • CHECK：考えることを必要とすること

您应该能够判断您的补丁中存在的所有违规行为。

5) 选择补丁收件人¶

どのパッチにも対応するサブシステムメンテナを必ずCCしてください。メンテナが管理するコードを確認するため、メンテナファイルとソースコードの変更履歴を確認してください。スクリプトscripts/get_Maintainer.plはこのステップで非常に役立ちます。特定のサブシステムのメンテナが見つからない場合は、Andrew Morton（akpm@linux-foundation.org）将充当最后的维护 人员。

您通常还应该选择至少一个邮件列表来接收补丁集的。linux-kernel@vger.kernel.org 最後の解決策リストですが、このリストに投稿する量はすでに多くの開発者の拒否を引き起こしています。MAINTAINERSファイルでサブシステム固有のリストを検索してください。あなたのパッチはそこでより多くの注目を浴びる可能性があります。ただし、関係のないリストにスパムを送信しないでください。

多くの内核関連のリストはvger.kernel.orgにホストされています。詳しくは http://vger.kernel.org/vger-lists.html 上找到它们的列表。不过，也有与内核相关 的列表托管在其他地方。

vgerメールリストに一度に15個以上のパッチを送信しないで！！！！

Linus Torvalds は Linux 内核に変更を導入するかどうかを最終的に決定する人物です。彼のメールアドレスは <torvalds@linux-foundation.org> です。彼のメールは多く届くため、一般的には彼にメールを送るのを避けるのがよいでしょう。

如果您有修复可利用安全漏洞的补丁，请将该补丁发送到 security@kernel.org。重大なバグの修正については、一時的に停止してディストリビューターがユーザーにパッチを配布できるようにするという選択肢がありますが、そのような場合、パッチをどのパブリックリストにも送ってはいけません。

修复已发布内核中严重错误的补丁程序应该指向稳定版维护人员，方法是放这样的一行:

Cc: stable@vger.kernel.org

进入补丁的签准区（注意，不是电子邮件收件人）。除了这个文件之外，您还应该阅读 Linux -stableリリースについて知りたいすべての情報

但是，请注意，一些子系统维护人员希望得出他们自己的结论，即哪些补丁应该被放到 稳定的树上。尤其是网络维护人员，不希望看到单个开发人员在补丁中添加像上面这样 的行。

ユーザーと内核インターフェースに影響を与える変更については、マニュアルページのメンテナ（メンテナファイルに記載されているもの）にマニュアルページのパッチを送るか、少なくとも変更通知を送る必要があります。また、ユーザー空間APIの変更は linux-api@vger.kernel.org。

小さなパッチについては、雑なパッチを集めるメールリスト（Trivial Patch Monkey）にCCするのもよいでしょう。 trivial@kernel.org，那里专门收集琐碎的补丁。下面这样的补丁会被看作“琐碎的” 补丁：

  • 文档的拼写修正。

  • 修正が grep(1) のスペルに影響します。

  • 警告信息修正(频繁的打印无用的警告是不好的。)

  • 编译错误修正（代码逻辑的确是对的，只是编译有问题。）

  • 运行时修正（只要真的修正了错误。）

  • 廃止された関数/マクロを使用しているコードを削除してください（例：check_region）。

  • 联系方式和文档修正。

  • 用可移植的代码替换不可移植的代码（即使在体系结构相关的代码中，既然有

  • 人拷贝，只要它是琐碎的）

  • ファイルの著者/メンテナによるファイルの変更（例：patch monkey の再送モード）

(翻訳注: 「雑なパッチ」に関する補足説明: 原文のこの部分は簡潔すぎて、例外的に翻訳注を追加します。「trivial」は英語では「雑な、重要でない」という意味ですが、ここでは少し意味が変わります。例えば、明らかにNULLポインタの修正は実行時修正に分類され、雑なパッチに含まれます。NULLポインタの修正は重要ですが、修正が小さく検証しやすいので雑なパッチに分類されます。雑なパッチのより正確な分類は「simple, localized & easy to verify」つまり「シンプルで局所的で検証しやすい」です。 trivial@kernel.org メールリストの目的は、このようなパッチを投稿するための中心的な場所を提供することです。投稿のハードルを下げることを目的としています。)

6) MIME エンコードなし、リンクなし、圧縮なし、添付ファイルなし、純粋なテキストのみ¶

Linus と他の内核開発者が必要に応じてあなたの変更を読む・コメントする必要があります。内核開発者にとって、あなたの変更を「引用」することが重要で、一般的なメールツールを使ってあなたのコードのどこでもコメントを追加できます。

そのため、すべての投稿されたパッチはメール内の「内蔵」形式で送られます。

警告

如果你使用剪切-粘贴你的补丁，小心你的编辑器的自动换行功能破坏你的补丁

MIME エンコードされた添付ファイルとしてパッチを送らないでください。圧縮して送るかどうかに関わらず、多くのポピュラーなメールソフトウェアは MIME エンコードされた添付ファイルを純粋なテキストとして送信しないことがあり、他人があなたのコードにコメントを追加できなくなります。また、MIME エンコードされた添付ファイルは Linus にとって処理に時間がかかるため、あなたの変更が採用される可能性が低下します。

例外: あなたの郵便配達人がパッチを破損した場合、誰かが MIME で再送信するよう求めることもあります。

请参阅 Linuxメールクライアント設定情報 以获取有关配置电子邮件客户端以使其不受影响地发送修补程序的提示。

7) メールのサイズ¶

大きな変更はメールリストには不適切で、一部のメンテナにも不適切です。圧縮せずに300kBを越える場合、パッチをインターネットでアクセス可能なサーバーに置き、そのURLを代わりに使用するのが望ましいです。ただし、300kBを越えるパッチはほぼ確実に破損するでしょう。

8）回复评审意见¶

你的补丁几乎肯定会得到评审者对补丁改进方法的评论。您必须对这些评论作出 回应；让补丁被忽略的一个好办法就是忽略审阅者的意见。不会导致代码更改的 意见或问题几乎肯定会带来注释或变更日志的改变，以便下一个评审者更好地了解 正在发生的事情。

一定要告诉审稿人你在做什么改变，并感谢他们的时间。代码审查是一个累人且 耗时的过程，审查人员有时会变得暴躁。即使在这种情况下，也要礼貌地回应并 解决他们指出的问题。

9）不要泄气或不耐烦¶

提交更改后，请耐心等待。审阅者是忙碌的人，可能无法立即访问您的修补程序。

曾几何时，补丁曾在没有评论的情况下消失在空白中，但开发过程比现在更加顺利。 您应该在一周左右的时间内收到评论；如果没有收到评论，请确保您已将补丁发送 到正确的位置。在重新提交或联系审阅者之前至少等待一周-在诸如合并窗口之类的 繁忙时间可能更长。

10）件名に PATCH を含める¶

Linus と Linux 内核へのメールの流量が非常に高いので、通常、件名の前に [PATCH] という接頭辞を付けています。これにより、Linus と他の内核開発者にとって、パッチを他のメールディスカッションと区別しやすくなります。

11）签署你的作品-开发者原始认证¶

特に複数層のメンテナを通じて送信されるパッチの追跡を強化するため、送信されたパッチに「サインオフ」プロセスを追加することを推奨します。

「サインオフ」は、パッチのコメントの最後に1行のテキストで、あなたがそのパッチを書いたか、またはオープンソースのパッチとして送信する権限があることを認証します。ルールは簡単です：以下の情報を認証できる場合、

开发者来源证书 1.1¶

对于本项目的贡献，我认证如下信息：

（a）这些贡献是完全或者部分的由我创建，我有权利以文件中指出

的开放源代码许可证提交它；或者

（b）这些贡献基于以前的工作，据我所知，这些以前的工作受恰当的开放

源代码许可证保护，而且，根据许可证，我有权提交修改后的贡献， 无论是完全还是部分由我创造，这些贡献都使用同一个开放源代码许可证 （除非我被允许用其它的许可证），正如文件中指出的；或者

（c）这些贡献由认证（a），（b）或者（c）的人直接提供给我，而

且我没有修改它。

（d）我理解并同意这个项目和贡献是公开的，贡献的记录（包括我

一緒に送信された個人記録（サインオフを含む）は、プロジェクトやオープンソースライセンスと同時に再配布されるため、永久に維持される必要があります。

那么加入这样一行:

Signed-off-by: Random J Developer <random@developer.example.org>

使用你的真名（抱歉，不能使用假名或者匿名。）

誰かが最後にラベルを追加します。これらは無視されるかもしれませんが、会社内のプロセスをマークするか、サインオフに関する特別な詳細を示すためにこれを行うことができます。

如果您是子系统或分支维护人员，有时需要稍微修改收到的补丁，以便合并它们， 因为树和提交者中的代码不完全相同。如果你严格遵守规则（c），你应该要求提交者 重新发布，但这完全是在浪费时间和精力。规则（b）允许您调整代码，但是更改一个 提交者的代码并让他认可您的错误是非常不礼貌的。要解决此问题，建议在最后一个 由签名行和您的行之间添加一行，指示更改的性质。虽然这并不是强制性的，但似乎 在描述前加上您的邮件和/或姓名（全部用方括号括起来），这足以让人注意到您对最 后一分钟的更改负有责任。例如:

Signed-off-by: Random J Developer <random@developer.example.org>
[lucky@maintainer.example.org: struct foo moved from foo.c to foo.h]
Signed-off-by: Lucky K Maintainer <lucky@maintainer.example.org>

安定したブランチをメンテナしており、著者への感謝、変更の追跡、修正のマージ、および投稿者への苦情の防止が必要な場合、この方法は特に有用です。注意: どの場合でも著者のID（Fromヘッダー）を変更してはいけません。これは変更履歴に表示される識別子です。

バックポート（back-porters）に関する特別な説明: パッチの起源を示す指示を、投稿メッセージの先頭（件名の後に）に挿入するという慣例が一般的で有用です。これにより、追跡が容易になります。例えば、以下は3.x安定版で見られる内容です:

Date:   Tue Oct 7 07:26:38 2014 -0400

  libata: Un-break ATA blacklist

  commit 1c40279960bcd7d52dbdf1d466b20d24b99176c8 upstream.

还有， 这里是一个旧版内核中的一个回合补丁:

Date:   Tue May 13 22:12:27 2008 +0200

    wireless, airo: waitbusy() won't delay

    [backport of 2.6 commit b7acbdfbd1f277c1eb23f344f899cfa4cd0bf36a]

12）Acked-by:、CC:、およびCo-Developed by: の使用タイミング¶

Singed-off-by: ラベルは、サインオフ者がパッチの開発に参加したか、またはパッチの伝達パスに含まれていることを示します。

誰もパッチの準備や処理に直接参加していないが、パッチの承認を示し記録したい場合は、変更履歴にAcked-by:を追加するよう要求できます。

Acked-by: は通常、影響を受けるコードのメンテナによって使用され、メンテナが貢献していないにもかかわらずパッチを転送していない場合です。

Acked-by: はサインオフほど正式ではありません。これは、少なくともパッチを確認し、受け入れることを示す記録です。そのため、パッチのマージ時には、Ackerの「Yep, looks good to me」を手動で Acked-By: に変換することがあります（ただし、通常は明示的なAckを求めるのが望ましいです）。

Acked-by: は全体のパッチを確認するとは限りません。例えば、パッチが複数のサブシステムに影響し、そのうち1つのサブシステムメンテナが Acked-by: を追加した場合、これはそのメンテナのコードに影響する部分を確認していることを示します。ここでは注意が必要です。疑問がある場合は、メールリストアーカイブの元の議論を参照してください。

如果某人有机会对补丁进行评论，但没有提供此类评论，您可以选择在补丁中添加 Cc: 这是唯一一个标签，它可以在没有被它命名的人显式操作的情况下添加，但它应该表明 这个人是在补丁上抄送的。讨论中包含了潜在利益相关方。

Co-developed-by: はパッチが複数の開発者によって共同で作成されたことを宣言します。複数の開発者が同じパッチに協力している場合、このラベルは共同著者（From: で指定された著者以外）に属性を割り当てます。Co-developed-by: は著者を示すため、各共同開発者：は関連する共同著者のサインオフの直後に必ず追加する必要があります。標準的なサインオフプロセスでは、ラベルのサインオフ順序は著者の投稿時間の歴史をできるだけ反映する必要があります。著者は From: か Co-developed-by: による共同開発者に関係なく、最後のサインオフ者はパッチを投稿した開発者でなければなりません。

注意: 作者がメールタイトルの「From:」行に記載されている人物である場合、「From:」ラベルはオプションです。

作者提交的补丁程序示例:

<changelog>

Co-developed-by: First Co-Author <first@coauthor.example.org>
Signed-off-by: First Co-Author <first@coauthor.example.org>
Co-developed-by: Second Co-Author <second@coauthor.example.org>
Signed-off-by: Second Co-Author <second@coauthor.example.org>
Signed-off-by: From Author <from@author.example.org>

合作开发者提交的补丁示例:

From: From Author <from@author.example.org>

<changelog>

Co-developed-by: Random Co-Author <random@coauthor.example.org>
Signed-off-by: Random Co-Author <random@coauthor.example.org>
Signed-off-by: From Author <from@author.example.org>
Co-developed-by: Submitting Co-Author <sub@coauthor.example.org>
Signed-off-by: Submitting Co-Author <sub@coauthor.example.org>

13）使用报告人：、测试人：、审核人：、建议人：、修复人：¶

Reported-by: 間違いを見つけた人やその間違いを報告した人に感謝を示し、将来またお手伝いいただけるよう励ます。ただし、プライベートで報告されたバグについては、Reported-byを記載する前に権限を確認してください。

Tested-by: これはパッチが特定の人物（ある環境では）によって成功裏にテストされたことを示すラベルです。このラベルはメンテナにテストが実施されたことを通知し、今後のパッチでテスト担当者を特定する方法を提供し、テスト担当者の信頼性を確保します。

Reviewed-by：逆に、レビューを行った人物の声明によって、このパッチがレビューされ適切であると判断されていることを示します：

审查人的监督声明¶

Reviewed-byを提供することで、私は以下を宣言します：

  1. 我已经对这个补丁进行了一次技术审查，以评估它是否适合被包含到 主线内核中。

  2. 与补丁相关的任何问题、顾虑或问题都已反馈给提交者。我对提交者对 我的评论的回应感到满意。

  3. 虽然这一提交可能会改进一些东西，但我相信，此时，（1）对内核 进行了有价值的修改，（2）没有包含争论中涉及的已知问题。

  4. 虽然我已经审查了补丁并认为它是健全的，但我不会（除非另有明确 说明）作出任何保证或保证它将在任何给定情况下实现其规定的目的 或正常运行。

Reviewed-byは、パッチがカーネルに適切な変更であり、重大な技術的問題が残っていないと判断されたという意見表明です。関心のあるレビュー者（作業を完了した人物）がパッチにReviewed-byラベルを付与できます。このラベルはレビュー者への感謝を示し、メンテナにレビューが完了した程度を通知します。Reviewed-by: 既にテーマ分野を熟知し、詳細な検証を行ったレビュー者が提供した場合、パッチがカーネルに採用される可能性が高まります。

Suggested-by: これはパッチのアイデアが指定された人物によって提案されたことを示し、そのアイデアを指定された人物に帰属させます。注意：このラベルは許可なく追加してはいけません、特にそのアイデアが公開フォーラムで発表されていない場合。つまり、私たちが創作者に感謝をしっかり示すことで、彼らが将来またお手伝いいただけるよう励まされる可能性があります。

Fixes: これはパッチが以前のコミットで修正した問題を示します。これにより、エラーの原因を簡単に特定でき、エラー修正の検証が容易になります。このラベルは、カーネルチームが安定版にどのバージョンに修正を含めるべきかを判断するのにも役立ちます。エラー修正を示すための最適な方法です。参照してください 2) 描述你的改动 描述您的更改以了解更多详细信息。

12）标准补丁格式¶

本节描述如何格式化补丁本身。请注意，如果您的补丁存储在 Git 存储库中，则 可以使用 git format-patch 进行正确的补丁格式设置。但是，这些工具无法创建 必要的文本，因此请务必阅读下面的说明。

标准的补丁，标题行是:

Subject: [PATCH 001/123] 子系统:一句话概述

标准补丁的信体存在如下部分：

  • 「from」行はパッチの著者を示します。その後に空行を1行挟みます（パッチを送信した人物が著者でない場合にのみ必要です）。

  • 解释的正文，行以75列包装，这将被复制到永久变更日志来描述这个补丁。

  • 一个空行

  • 上記で説明した「Signed-off-by」行は、変更履歴にも表示されます。

  • 只包含 --- 的标记线。

  • 任何其他不适合放在变更日志的注释。

  • 实际补丁（ diff 输出）。

タイトル行のフォーマットにより、タイトル行をアルファベット順に並べるのが非常に容易です - 複数のメールクライアントがサポートしています - なぜなら、シリアル番号はゼロ埋めされているため、数字順に並べてもアルファベット順に並べても同じです。

メールのタイトルにある「サブシステム」は、どのカーネルサブシステムがパッチ対象であるかを示します。

メールタイトルにある「一文での概要」は、メール内のパッチを簡潔に説明します。「一文での概要」はファイル名ではなく、複数の関連するパッチ（パッチシリーズ）に対しては、各パッチに同じ「一文での概要」を用いることはありません。

メールの「一文での概要」は、そのパッチのグローバルな一意の識別子になります。これはgitの変更履歴に広がっていきます。その後、「一文での概要」は開発者の議論の中でこのパッチを指すために使われます。ユーザーはGoogleでこの「一文での概要」を検索して、このパッチに関する議論を探すことを希望しています。人々が2〜3か月後に以下のようないくつかのキーワードを使って gitk 或 git log --oneline 之类 的工具查看数千个补丁时，也会很快看到它。

出于这些原因，概述必须不超过70-75个字符，并且必须描述补丁的更改以及为 什么需要补丁。既要简洁又要描述性很有挑战性，但写得好的概述应该这样做。

概要の前には角括弧で括って、「Subject: [PATCH <tag>…] <概要>」とします。マークは概要の一部ではなく、パッチの処理方法を説明するものです。複数のバージョンのパッチがレビューに応じて送信された場合（つまり「v1, v2, v3」や「rfc」でレビューを依頼する場合）、一般的なマークにはバージョン記述子が含まれることがあります。パッチシリーズに4つのパッチがある場合、それぞれのパッチは「1/4、2/4、3/4、4/4」として番号をつけることができます。これにより、開発者がパッチの適用順序を理解し、すべてのパッチを確認または適用したことを知ることができます。

一些标题的例子:

Subject: [patch 2/5] ext2: improve scalability of bitmap searching
Subject: [PATCHv2 001/207] x86: fix eflags tracking
「From」行は本文の一番上の行で、以下のフォーマットを持ちます：

From: パッチ作成者 <author@例.com>

「From」行は、永久的な変更履歴において、誰が著者とされるかを示します。もし「From」行がない場合、メールヘッダーの「From:」行が変更履歴の著者を決定します。

説明のタイトルは永久的なソースコード変更履歴に投稿されるため、このパッチに関連する議論の詳細を忘れてしまった読者にとって意味があります。パッチが修正した問題の症状（カーネルログメッセージ、OOPSメッセージなど）を含めることで、修正パッチを探す人々にとって特に役立ちます。パッチがコンパイルエラーを修正した場合、すべてのコンパイルエラーを含める必要はありません。検索する人々がパッチを見つけるのに十分なだけです。概要と同様に、簡潔かつ説明的な表現が必要です。

“—” 标记行对于补丁处理工具要找到哪里是改动日志信息的结束，是不可缺少 的。

「—」のマーク後の追加注釈として、diffstatを作成するのに役立ちます。diffstatは変更されたファイルや各ファイルの追加・削除行数を表示します。大きなパッチには特に役立ちます。その他の注釈は、時間や開発者に関連するため、永久的な変更履歴には含めないのが適切です。diffstatのオプション「-p 1 -w 70」を使用することで、ファイル名はカーネルソースコードツリーのディレクトリから始まり、幅を広く占めることなく（80列幅に収まるように、少しインデントがあるかもしれません）。

在后面的参考资料中能看到适当的补丁格式的更多细节。

15) メールヘッダー（In-Reply-To）の明確な返信¶

手動で返信パッチのタイトルヘッダー（In-Reply-To:）を追加することは役立ちます（例えば、 git send-email ）で、パッチと以前の関連する議論を関連付けることができます。例えば、バグ修正プログラムをメールとバグレポートにリンクします。ただし、複数のパッチシリーズがある場合、古いバージョンへのリンクは避けたほうが良いです。これにより、パッチの複数バージョンがメールクライアントで管理できない参照列になってしまうからです。リンクが役立つ場合は、 https://lkml.kernel.org/ 重定向器（例如，在封面电子邮件文本中） 链接到补丁系列的早期版本。

16) Git プルリクエストを送信する¶

複数のパッチがある場合、メンテナがgit pull操作でそれらを直接サブシステムリポジトリにプルすることができれば最も便利です。ただし、開発者からパッチを取得するよりも、メールリストからパッチを取得するには高い信頼度が必要です。そのため、多くのサブシステムメンテナは、特に新規の未知の開発者からのリクエストは受け入れません。疑問がある場合は、カバーメールでプルリクエストを補丁シリーズの通常の公開オプションとして使用し、メンテナがそのうちのいずれかを選択できるようにします。

プルリクエストのタイトル行には[Git Pull]を含めるべきです。リクエスト自体は1行にリポジトリ名と興味のあるブランチを含め、以下のように表示します：

Please pull from

    git://jdelvare.pck.nerim.net/jdelvare-2.6 i2c-for-linus

to get these changes:

プルリクエストには、リクエストに含まれる内容を説明する全体的なメッセージと、パッチ自体の Git shortlog 以及一个显示补丁系列整体效果的 diffstat 。当然，将所有这些信息收集在一起 的最简单方法是让 git 使用 git request-pull 命令为您完成这些工作。

一部のメンテナ（含むLinus）は署名されたコミットからのリクエストを希望しています。これにより、あなたのリクエストに対する信頼度が高まります。特に、署名ラベルがなければ、LinusはGithubなどの公開ホスティングサイトからのリクエストをプルしません。

このような署名を作成する最初のステップは、GNRPG鍵を生成し、1つまたは複数のコアカーネル開発者によって署名することです。これは新規開発者にとって難しいかもしれませんが、回避する方法はありません。会議に出席することは、あなたの鍵を署名できる開発者を見つけるための良い方法です。

Gitでパッチシリーズを準備し、誰かがプルできるようにした後、 git tag -s サイン付きタグを作成します。これは、シリーズ内の最後のコミットを識別し、あなたの秘密鍵で作成されたサインを含む新しいタグを作成します。また、タグにチャレンジロギングスタイルのメッセージを追加することもでき、これはプルリクエスト全体の効果を説明する理想的な場所です。

如果维护人员将要从中提取的树不是您正在使用的存储库，请不要忘记将已签名的标记 显式推送到公共树。

生成拉请求时，请使用已签名的标记作为目标。这样的命令可以实现:

git request-pull master git://my.public.tree/linux.git my-signed-tag

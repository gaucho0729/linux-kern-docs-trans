5. 发布补丁¶

迟早，当您的工作准备好提交给社区进行审查，并最终包含到主线内核中时。不出所料， 内核开发社区已经发展出一套用于发布补丁的约定和过程；遵循这些约定和过程将使 参与其中的每个人的生活更加轻松。本文件将试图合理详细地涵盖这些期望；更多信息 也可在以下文件中找到 如何让你的改动进入内核, Linux Kernel用ドライバの提出 和 Linuxカーネルパッチ提出チェックリスト.

5.1. 何时邮寄¶

補丁が完全に『準備完了』する前には、パッチを公開しないという誘惑があります。単純な補丁であれば問題ありませんが、複雑な作業を進めている場合、作業が完了する前からコミュニティからフィードバックを得ることは多くのメリットがあります。そのため、進行中の作業を公開することを検討し、必要に応じてGitツリーを公開して、関心のある開発者にいつでも作業内容を追い合わせてもらうことが望ましいです。

当发布还没有准备好包含的代码时，最好在发布本身中这样说。还应提及任何有待完成 的主要工作和任何已知问题。很少有人会看到那些被认为是半生不熟的补丁，但是那些 人会想到他们可以帮助你把工作推向正确的方向。

5.2. 创建补丁之前¶

在考虑将补丁发送到开发社区之前，有许多事情应该做。这些包括：

  • 尽可能地测试代码。利用内核的调试工具，确保内核使用所有合理的配置选项组合 进行构建，使用跨编译器为不同的体系结构进行构建等。

  • 确保您的代码符合内核编码风格指南。

  • 您的更改是否具有性能影响？如果是这样，您应该运行基准测试来显示您的变更的 影响（或好处）；结果的摘要应该包含在补丁中。

  • コードを公開する権限があることを確認してください。この作業が雇用主のために行われている場合、雇用主が著作権を保有しており、GPLに基づいて許諾を得る必要があります。

一般来说，在发布代码之前进行一些额外的思考，几乎总是能在短时间内得到回报。

5.3. 补丁准备¶

准备发布补丁可能是一个惊人的工作量，但再次尝试节省时间在这里通常是不明智的， 即使在短期内。

内核の特定バージョンに対して補丁を準備する必要があります。一般的なルールとして、補丁はLinusのGitツリーにある現在のメインラインに基づくべきです。メインラインをベースにした場合、よく知られたリリースポイントから開始すべきです——安定版やRCリリースなど、メインラインブランチの任意のポイントではなく。

ただし、-mm、linux-next、またはサブシステムツリー向けにバージョンを生成する必要がある場合があります。これによりより広範なテストとレビューが可能になります。補丁の範囲や他の場所の状況によっては、これらの他のツリー向けに補丁を生成するには、コンフリクトの解決やAPI変更の処理に多くの作業が必要になる場合があります。

只有最简单的更改才应格式化为单个补丁；其他所有更改都应作为一系列逻辑更改进行。 分割补丁是一门艺术；一些开发人员花了很长时间来弄清楚如何按照社区期望的方式来 做。然而，有一些经验法则可以大大帮助：

  • 您发布的补丁程序系列几乎肯定不会是工作系统中的一系列更改。相反，您所做的 更改需要在最终形式中加以考虑，然后以有意义的方式进行拆分。开发人员对离散的、 自包含的更改感兴趣，而不是您获取这些更改的路径。

  • 每个逻辑上独立的变更都应该格式化为单独的补丁。这些更改可以是小的（“向此 结构添加字段”）或大的（例如，添加一个重要的新驱动程序），但它们在概念上 应该是小的，并且可以接受一行描述。每个补丁都应该做一个特定的更改，可以单独 检查并验证它所做的事情。

  • 作为重申上述准则的一种方法：不要在同一补丁中混合不同类型的更改。如果一个 补丁修复了一个关键的安全漏洞，重新排列了一些结构，并重新格式化了代码，那么 很有可能它会被忽略，而重要的修复将丢失。

  • 各補丁は、正しく構築・動作する内核を生成する必要があります。補丁シリーズが途中で中断された場合でも、結果として動作する内核であるべきです。補丁シリーズの部分適用は、『git bisct』ツールを使用してリグレッションを検出する典型的なシナリオです。結果が破損した内核である場合、問題を追跡している開発者やユーザーにとって非常に不便になります。

  • 不过，不要过分。一位开发人员曾经将一组编辑内容作为500个单独的补丁发布到一个 文件中，这并没有使他成为内核邮件列表中最受欢迎的人。一个补丁可以相当大， 只要它仍然包含一个单一的逻辑变更。

  • 新たなインフラストラクチャを一連の補丁で追加することは魅力的ですが、シリーズの最後の補丁が有効化される前にはそのインフラストラクチャは使用されません。可能な限りこの誘惑を避けるべきです。もしこのシリーズがリグレッションを引き起こす場合、バイナリ検索は最後の補丁を問題の原因と特定しますが、実際のバグは他の場所にある可能性があります。可能な限り、新コードを追加する補丁はそのコードをすぐに有効化するべきです。

创建完美补丁系列的工作可能是一个令人沮丧的过程，在完成“真正的工作”之后需要花费 大量的时间和思考。但是，如果做得好，这是一段很好的时间。

5.4. 补丁格式和更改日志¶

所以现在你有了一系列完美的补丁可以发布，但是这项工作还没有完成。每个补丁都 需要被格式化成一条消息，它可以快速而清晰地将其目的传达给世界其他地方。为此， 每个补丁将由以下部分组成：

  • 補丁著者のオプションの『from』行。他人の補丁をメールで送る場合にのみ必要ですが、疑問があれば追加しても問題ありません。

  • 一行描述补丁的作用。对于没有其他上下文的读者来说，此消息应该足够了解补丁 的范围；这是将在“短格式”变更日志中显示的行。此消息通常首先用相关的子系统 名称格式化，然后是补丁的目的。例如：

    gpio: fix build on CONFIG_GPIO_SYSFS=n

  • 一个空白行，后面是补丁内容的详细描述。这个描述可以是必需的；它应该说明补丁 的作用以及为什么它应该应用于内核。

  • 1行または複数行のマーキング行、少なくとも1行は補丁著者の『signed-off-by』署名を含む必要があります。署名については後述します。

上記の項目は補丁の変更履歴を構成します。良い変更履歴を書くことは、しばしば無視されるが非常に重要な芸術です。時間をかけてこの点について議論する価値があります。変更履歴を書く際には、多くの人が読むことを想定してください。その中にはサブシステムメンテナーやレビュー担当者、パッチを逆移植するかどうかを判断する配布者やメンテナ、問題を追跡しているバグハンターなどが含まれます。変更履歴は、これらのすべての人々に必要な情報を最も直接的かつ簡潔な形で伝えなければなりません。

そのため、要約行は変更の影響と動機、および1行の制約条件下での変更を説明する必要があります。その後、詳細な説明でこれらのトピックを詳しく説明し、必要な追加情報を提供してください。もし補丁がバグを修正している場合、そのバグを導入したコミットを引用してください（可能な限りコミットIDとタイトルも含めて）。特定のログやコンパイラ出力に関連する問題がある場合、その出力を含めて他の人が同じ問題を検索するのを助けるようにしてください。もし変更が今後の他の補丁の変更をサポートする目的であれば、その旨を明記してください。内部APIを変更した場合、その変更内容と他の開発者がどのように対応すべきかを詳しく説明してください。読者に立った視点で変更履歴を書くほど、変更履歴（および内核全体）は良くなります。

不用说，变更日志应该是将变更提交到修订控制系统时使用的文本。接下来是：

  • 統一された（『-u』）形式のパッチとして、補丁自体を提供してください。diffに『-p』オプションを使用すると、関数名と変更の関連性が明確になり、結果として他の人が読みやすくなります。

補丁には関係のないファイル（例えば、ビルドプロセスで生成されるファイルやエディタのバックアップファイル）の変更を含めないでください。ドキュメントディレクトリ内の『dontdiff』ファイルはこの点に役立ちます。diffに『-X』オプションでこれを渡してください。

上面提到的标签用于描述各种开发人员如何与这个补丁的开发相关联。 如何让你的改动进入内核 文档中对它们进行了详细描述；下面是一个简短的总结。每一行的格式如下：

tag: Full Name <email address>  optional-other-stuff

常用的标签有：

  • Signed-off-by: これは、パッチを内核に含める権限があることを証明する開発者の署名です。これは開発者認証プロトコルで、その全文は 如何让你的改动进入内核 中找到，如果没有适当的签字，则不能合并到主线中。

  • Co-developed-by: 補丁が複数の開発者によって共同で作成されたことを宣言します。複数の人が同じ補丁に協力している場合、共同著者を明示するために使用します（From: で指定された著者以外にも）。Co-developed-by: は著者を示すため、各共同開発者について、関連する共同著者の署名の直後に記載する必要があります。詳細な内容と例は以下のファイルに記載されています 如何让你的改动进入内核

  • Acked-by: 他の開発者（通常は関連するコードのメンテナ）がパッチが内核に含めるべきであることを承認していることを示します。

  • Tested-by: 指定された人物がパッチをテストし、動作することを確認したことを宣言します。

  • Reviewed-by: 指定された開発者がパッチの正しさをレビューしたことを示します。詳細については、 如何让你的改动进入内核

  • Reported-by: このパッチで修正された問題を報告したユーザーを示します。このマーキングは感謝を示すために使用されます。

  • Cc: 指定された人物にパッチのコピーを送信し、コメントを求める機会を提供します。

パッチにラベルを追加する際は注意が必要です：明確な許可がない限り、Cc: 以外は追加しないでください。

5.5. 发送补丁¶

在邮寄补丁之前，您还需要注意以下几点：

  • 您确定您的邮件发送程序不会损坏补丁吗？有免费的空白更改或由邮件客户端 执行的行包装的补丁不会在另一端复原，并且通常不会进行任何详细检查。如果有 任何疑问，把补丁寄给你自己，让你自己相信它是完好无损的。

    Linuxメールクライアント設定情報 提供了一些有用的提示，可以让特定的邮件客户机工作以发送补丁。

  • あなたのパッチに馬鹿げたミスがないか確認しましたか？常にscripts/checkpatch.plを実行し、その指摘を解決してください。checkpatch.plは内核パッチがどうべきかについて多くの思考を反映していますが、あなたよりはるかに賢くありません。checkpatch.plの指摘を修正するがコードを悪化させる場合は、それを行わないでください。

补丁应始终以纯文本形式发送。请不要将它们作为附件发送；这使得审阅者在答复中更难 引用补丁的部分。相反，只需将补丁直接放到您的消息中。

邮寄补丁时，重要的是将副本发送给任何可能感兴趣的人。与其他一些项目不同，内核 鼓励人们错误地发送过多的副本；不要假定相关人员会看到您在邮件列表中的发布。 尤其是，副本应发送至：

  • 受影响子系统的维护人员。如前所述，维护人员文件是查找这些人员的第一个地方。

  • 特に現在その分野で作業している開発者や、将来作業する可能性のある開発者を含む他の同分野の開発者。gitでどの開発者があなたが処理しているファイルを変更したかを確認すると役立ちます。

  • 如果您对错误报告或功能请求做出响应，也可以抄送原始发送人。

  • 関連するメールリストにコピーを送信するか、それ以外の適用がない場合はLinux内核リストに送信してください。

  • バグを修正している場合、この修正が次の安定版アップデートに含まれるべきかどうかを考慮してください。そうであれば、 stable@vger.kernel.org パッチのコピーを取得する必要があります。また、パッチ自体のラベルに『cc:stable@vger.kernel.org』を追加してください。これにより、安定チームが修正がメインラインに取り込まれる際の通知を受けられます。

パッチの受信者を選ぶ際は、最終的にそのパッチを受け入れてマージするであろう人物を把握しておくのが望ましいです。パッチを直接Linus Torvaldsに送って彼がマージするという選択肢は理論上はありますが、通常はそうはしません。Linusは非常に忙しく、特定の内核部分を監視するサブシステムメンテナがいます。通常は、メンテナがパッチをマージするようにするのが望ましいです。メンテナが明確でない場合は、Andrew Mortonが最終的なパッチの宛先になります。

补丁需要好的主题行。补丁程序行的规范格式如下：

[PATCH nn/mm] subsys: one-line description of the patch

ここで「nn」はパッチの順番、「mm」はシリーズ内のパッチ総数、「subsys」は影響を受けるサブシステムの名前を表します。明らかに1つのパッチだけの場合は「nn/mm」を省略できます。

如果您有一系列重要的补丁，那么通常将介绍性描述作为零部分发送。不过，这种约定 并没有得到普遍遵循；如果您使用它，请记住简介中的信息不会使它进入内核变更日志。 因此，请确保补丁本身具有完整的变更日志信息。

一般的に、複数のパッチを送る場合、2番目のパッチ以降は1番目のパッチに対する返信として送信し、受信側でつながった形で表示されるようにします。gitやcoiltなどのツールでは、適切なスレッドで複数のパッチを送信するコマンドがあります。ただし、長いシリーズをgitで送る際は、–chain reply-toオプションは避けてください。これにより異常に深いネストが発生する可能性があるからです。

Linuxカーネルコードスタイル¶

これは linux 内核のコードスタイルの推奨事項を記した簡潔なドキュメントです。コードスタイルは個人差がありますが、私は自分の意見を押し付けることはありません。しかし、私が何か行動を起こす際には必ず遵守するべき原則があるように、私はほとんどの場面でこの姿勢を維持したいと考えています。コードを書く際には、少なくともこのコードスタイルを考慮してください。

まず、GNU コードスタイルを印刷して、読まないでください。焼却しましょう。これは重大な象徴的な意味を持つ行動です。

不管怎样，现在我们开始：

1) 缩进¶

制表符是 8 个字符，所以缩进也是 8 个字符。有些异端运动试图将缩进变为 4 (甚至 2！) 字符深，这几乎相当于尝试将圆周率的值定义为 3。

理由：缩进的全部意义就在于清楚的定义一个控制块起止于何处。尤其是当你盯着你的 屏幕连续看了 20 小时之后，你将会发现大一点的缩进会使你更容易分辨缩进。

现在，有些人会抱怨 8 个字符的缩进会使代码向右边移动的太远，在 80 个字符的终端 屏幕上就很难读这样的代码。这个问题的答案是，如果你需要 3 级以上的缩进，不管用 何种方式你的代码已经有问题了，应该修正你的程序。

简而言之，8 个字符的缩进可以让代码更容易阅读，还有一个好处是当你的函数嵌套太 深的时候可以给你警告。留心这个警告。

switch 文で複数レベルのインデントを削除する推奨される方法は、 switch 和从属于它的 case 标签对齐于同一列，而不要 两次缩进 case 标签。比如：

switch (suffix) {
case 'G':
case 'g':
        mem <<= 30;
        break;
case 'M':
case 'm':
        mem <<= 20;
        break;
case 'K':
case 'k':
        mem <<= 10;
        /* fall through */
default:
        break;
}

不要把多个语句放在一行里，除非你有什么东西要隐藏：

if (condition) do_this;
  do_something_everytime;

也不要在一行里放多个赋值语句。内核代码风格超级简单。就是避免可能导致别人误读 的表达式。

コメント、ドキュメント、Kconfig 以外ではスペースでインデントしないでください。前の例は例外であり、意図的にそうしています。

选用一个好的编辑器，不要在行尾留空格。

2) 把长的行和字符串打散¶

代码风格的意义就在于使用平常使用的工具来维持代码的可读性和可维护性。

每一行的长度的限制是 80 列，我们强烈建议您遵守这个惯例。

80 列を超える行は、意味のあるセグメントに分割してください。80 列を超えることで可読性が大幅に向上し、情報が隠蔽されない限りです。サブセグメントは親セグメントよりも明らかに短く、右に位置する必要があります。これは長すぎるパラメータリストを持つ関数ヘッダにも同様に適用されます。ただし、ユーザーが見ることができる文字列（例: printk 情報）は絶対に分割しないでください。それにより grep が困難になるからです。

3) 大括号和空格的放置¶

C 言語スタイルでよく見られるもう一つの問題は、大括弧の位置です。インデントのサイズと異なり、特定の配置戦略を採用するか否かには技術的な理由はほとんどありませんが、Kernighan と Ritchie が示したように、開始大括弧は行末に、終了大括弧は行頭に配置するのが推奨されます。つまり：

if (x is true) {
        we do y
}

これはすべての非関数のブロック（if, switch, for, while, do）に適用されます。例えば：

switch (action) {
case KOBJ_ADD:
        return "add";
case KOBJ_REMOVE:
        return "remove";
case KOBJ_CHANGE:
        return "change";
default:
        return NULL;
}

不过，有一个例外，那就是函数：函数的起始大括号放置于下一行的开头，所以：

int function(int x)
{
        body of function
}

全世界的异端可能会抱怨这个不一致性是… 呃… 不一致的，不过所有思维健全的人 都知道 (a) K&R 是 正确的 并且 (b) K&R 是正确的。此外，不管怎样函数都是特 殊的 (C 函数是不能嵌套的)。

終了大括弧は、次の文の残り部分と同一の文脈に続く場合を除き、1行にわたって表示する必要があります。例えば do 文の "while" または if 文の "else" の後ろに続く場合です。

do {
        body of do-loop
} while (condition);

和

if (x == y) {
        ..
} else if (x > y) {
        ...
} else {
        ....
}

理由：K&R。

也请注意这种大括号的放置方式也能使空 (或者差不多空的) 行的数量最小化，同时不 失可读性。因此，由于你的屏幕上的新行是不可再生资源 (想想 25 行的终端屏幕)，你 将会有更多的空行来放置注释。

当只有一个单独的语句的时候，不用加不必要的大括号。

if (condition)
        action();

和

if (condition)
        do_this();
else
        do_that();

这并不适用于只有一个条件分支是单语句的情况；这时所有分支都要使用大括号：

if (condition) {
        do_this();
        do_that();
} else {
        otherwise();
}

3.1) 空格¶

Linux 内核のスペースの使用方法（主に）は、それが関数かキーワードかによって異なります。（ほとんどの）キーワードの後にはスペースを追加する必要があります。ただし、sizeof, typeof, alignof, および __attribute__ は、ある程度関数のように見え、Linux では括弧とともに使用されることが多く（C 言語では括弧は必須ではありません）、 struct fileinfo info; 声明过后的 sizeof info)。

所以在这些关键字之后放一个空格:

if, switch, case, for, do, while

sizeof, typeof, alignof, または __attribute__ などのキーワードの後にはスペースを追加しないでください。例えば、

s = sizeof(struct file);

不要在小括号里的表达式两侧加空格。这是一个 反例 ：

s = sizeof( struct file );

当声明指针类型或者返回指针类型的函数时， * 的首选使用方式是使之靠近变量名 或者函数名，而不是靠近类型名。例子：

char *linux_banner;
unsigned long long memparse(char *ptr, char **retptr);
char *match_strdup(substring_t *s);

在大多数二元和三元操作符两侧使用一个空格，例如下面所有这些操作符:

=  +  -  <  >  *  /  %  |  &  ^  <=  >=  ==  !=  ?  :

但是一元操作符后不要加空格:

&  *  +  -  ~  !  sizeof  typeof  alignof  __attribute__  defined

后缀自加和自减一元操作符前不加空格:

++  --

前缀自加和自减一元操作符后不加空格:

++  --

. 和 -> 结构体成员操作符前后不加空格。

不要在行尾留空白。有些可以自动缩进的编辑器会在新行的行首加入适量的空白，然后 你就可以直接在那一行输入代码。不过假如你最后没有在那一行输入代码，有些编辑器 就不会移除已经加入的空白，就像你故意留下一个只有空白的行。包含行尾空白的行就 这样产生了。

git がパッチに行末の空白を検出すると警告を表示します。行末の空白を削除することも可能です。ただし、複数のパッチを適用している場合、この操作は後続のパッチに失敗を引き起こす可能性があります。なぜなら、パッチのコンテキストを変更しているからです。

4) 命名¶

C はシンプルな言語であり、命名も同様にシンプルにするべきです。Modula-2 または Pascal のプログラマとは異なり、C のプログラマは ThisVariableIsATemporaryCounter などの華やかな名前を使いません。C のプログラマはその変数を tmp ，这样写起来会更容易，而且至少不会令其难于理解。

不过，虽然混用大小写的名字是不提倡使用的，但是全局变量还是需要一个具描述性的 名字。称一个全局函数为 foo 是一个难以饶恕的错误。

全局变量 (只有当你 真正 需要它们的时候再用它) 需要有一个具描述性的名字，就 像全局函数。如果你有一个可以计算活动用户数量的函数，你应该叫它 count_active_users() 或者类似的名字，你不应该叫它 cntuser() 。

在函数名中包含函数类型 (所谓的匈牙利命名法) 是脑子出了问题——编译器知道那些类 型而且能够检查那些类型，这样做只能把程序员弄糊涂了。难怪微软总是制造出有问题 的程序。

本地变量名应该简短，而且能够表达相关的含义。如果你有一些随机的整数型的循环计 数器，它应该被称为 i 。叫它 loop_counter 并无益处，如果它没有被误解的 可能的话。类似的， tmp 可以用来称呼任意类型的临时变量。

如果你怕混淆了你的本地变量名，你就遇到另一个问题了，叫做函数增长荷尔蒙失衡综 合症。请看第六章 (函数)。

5) Typedef¶

不要使用类似 vps_t 之类的东西。

構造体とポインタに対して typedef を使用することは 错误 。当你在代码里看到：

vps_t a;

这代表什么意思呢？

相反，如果是这样

struct virtual_container *a;

你就知道 a 是什么了。

多くの人々は typedef 能提高可读性 。实际不是这样的。它们只在下列情况下有用：

  1. 完全に不透明なオブジェクト（このような場合、typedef を積極的に使用して 隐藏 这个对象实际上 是什么)。

    例如： pte_t 等不透明对象，你只能用合适的访问函数来访问它们。

    注意

    不透明性と "アクセッサ関数" 自体は悪い設計です。pte_t などの型を使用する理由は、本当に完全に共有可能な情報がありませんからです。

  2. 清楚的整数类型，如此，这层抽象就可以 帮助 消除到底是 int 还是 long 的混淆。

    u8/u16/u32 は問題ありませんが、これらは（d）カテゴリに属するよりもここに属するためです。

    注意

    要这样做，必须事出有因。如果某个变量是 unsigned long ，那么没有必要

    typedef unsigned long myflags_t;

    不过如果有一个明确的原因，比如它在某种情况下可能会是一个 unsigned int 而在其他情况下可能为 unsigned long そのような場合、迷わず typedef を使用してください。

  3. sparse を使って字面通りに 新 类型来做类型检查的时候。

  4. 和标准 C99 类型相同的类型，在某些例外的情况下。

    虽然让眼睛和脑筋来适应新的标准类型比如 uint32_t 不需要花很多时间，可 是有些人仍然拒绝使用它们。

    Linux 特有の標準型に相当する u8/u16/u32/u64 类型和它们的有符号 类型是被允许的——尽管在你自己的新代码中，它们不是强制要求要使用的。

    当编辑已经使用了某个类型集的已有代码时，你应该遵循那些代码中已经做出的选 择。

  5. 可以在用户空间安全使用的类型。

    在某些用户空间可见的结构体里，我们不能要求 C99 类型而且不能用上面提到的 u32 类型。因此，我们在与用户空间共享的所有结构体中使用 __u32 和类似 的类型。

可能还有其他的情况，不过基本的规则是 永远不要 typedef を使用しないでください。ただし、上述のいずれかのルールに明確に該当する場合を除いて。

一般的に、ポインタや構造体の要素が直接アクセス可能であれば、typedef として扱うべきではありません。

6) 函数¶

関数は短く、美しく、そして1つの目的だけを達成するべきです。1画面または2画面で表示可能（ISO/ANSI スクリーンサイズは80x24）で、1つのことだけを行い、それを丁寧に実行する必要があります。

関数の最大長は、その複雑さとインデントレベルに反比例します。したがって、理論的に非常に単純で、1つの非常に長い（しかし単純な）case 文を持つ関数があり、かつ各caseで多くの小さな処理を行う必要がある場合、関数が長くても問題ありません。

不过，如果你有一个复杂的函数，而且你怀疑一个天分不是很高的高中一年级学生可能 甚至搞不清楚这个函数的目的，你应该严格遵守前面提到的长度限制。使用辅助函数， 并为之取个具描述性的名字 (如果你觉得它们的性能很重要的话，可以让编译器内联它 们，这样的效果往往会比你写一个复杂函数的效果要好。)

函数的另外一个衡量标准是本地变量的数量。此数量不应超过 5－10 个，否则你的函数 就有问题了。重新考虑一下你的函数，把它分拆成更小的函数。人的大脑一般可以轻松 的同时跟踪 7 个不同的事物，如果再增多的话，就会糊涂了。即便你聪颖过人，你也可 能会记不清你 2 个星期前做过的事情。

在源文件里，使用空行隔开不同的函数。如果该函数需要被导出，它的 EXPORT 宏 应该紧贴在它的结束大括号之下。比如：

int system_is_up(void)
{
        return system_state == SYSTEM_RUNNING;
}
EXPORT_SYMBOL(system_is_up);

関数プロトタイプでは、関数名とデータ型を含めるべきです。C言語ではこのような要求はありませんが、Linuxではこの方法が推奨されており、読者に多くの価値のある情報を提供できます。

7) 集中的函数退出途径¶

一部の人々がすでに陳腐化したと主張しているにもかかわらず、goto 文の同等物はコンパイラによって頻繁に使用され、無条件ジャンプ命令として現れます。

関数が複数の場所から終了し、共通のクリーンアップ操作が必要な場合、goto 文は便利です。クリーンアップ操作が不要な場合は、単に return してください。

goto 文の動作やその存在理由を示すラベル名を選択してください。goto がリソースを解放する場合、 buffer, 一个不错的名字可以是 out_free_buffer: 。别去使用像 err1: 和 err2: このような GW_BASIC のような名前は、関数の終了パスを追加または削除した際に再番号付けが必要になるため、正しさの検証が困難です。

goto 文を使用する理由は：

  • 无条件语句容易理解和跟踪

  • 嵌套程度减小

  • 可以避免由于修改时忘记更新个别的退出点而导致错误

  • 让编译器省去删除冗余代码的工作 ;)

int fun(int a)
{
        int result = 0;
        char *buffer;

        buffer = kmalloc(SIZE, GFP_KERNEL);
        if (!buffer)
                return -ENOMEM;

        if (condition1) {
                while (loop1) {
                        ...
                }
                result = 1;
                goto out_free_buffer;
        }
        ...
out_free_buffer:
        kfree(buffer);
        return result;
}

一个需要注意的常见错误是 一个 err 错误 ，就像这样：

err:
        kfree(foo->bar);
        kfree(foo);
        return ret;

这段代码的错误是，在某些退出路径上 foo NULL です。通常、これを2つのエラーラベルに分離することで、 err_free_bar: 和 err_free_foo: 来修复这个错误：

err_free_bar:
       kfree(foo->bar);
err_free_foo:
       kfree(foo);
       return ret;

理想情况下，你应该模拟错误来测试所有退出路径。

8) 注释¶

注释是好的，不过有过度注释的危险。永远不要在注释里解释你的代码是如何运作的： 更好的做法是让别人一看你的代码就可以明白，解释写的很差的代码是浪费时间。

一般的，你想要你的注释告诉别人你的代码做了什么，而不是怎么做的。也请你不要把 注释放在一个函数体内部：如果函数复杂到你需要独立的注释其中的一部分，你很可能 需要回到第六章看一看。你可以做一些小注释来注明或警告某些很聪明 (或者槽糕) 的 做法，但不要加太多。你应该做的，是把注释放在函数的头部，告诉人们它做了什么， 也可以加上它做这些事情的原因。

内核 API 関数をコメントする際には、kernel-doc フォーマットを使用してください。詳細については Documentation/doc-guide/ および scripts/kernel-doc を参照してください。

长 (多行) 注释的首选风格是：

/*
 * This is the preferred style for multi-line
 * comments in the Linux kernel source code.
 * Please use it consistently.
 *
 * Description:  A column of asterisks on the left side,
 * with beginning and ending almost-blank lines.
 */

net/ および drivers/net/ のファイルでは、長文のコメントスタイルは若干異なります。

/* The preferred comment style for files in net/ and drivers/net
 * looks like this.
 *
 * It is nearly the same as the generally preferred comment style,
 * but there is no initial almost-blank line.
 */

注释数据也是很重要的，不管是基本类型还是衍生类型。为了方便实现这一点，每一行 应只声明一个数据 (不要使用逗号来一次声明多个数据)。这样你就有空间来为每个数据 写一段小注释来解释它们的用途了。

9) 你已经把事情弄糟了¶

これは問題ありません。私たちはみなそうしています。おそらく、Unix を長年使用している友達にすでに GNU emacs C ソースコードを自動的に整形してくれるツールがあり、あなたも気づいているでしょう。しかし、そのデフォルト値は私たちが望むものとはかけ離れており（実際にはランダムに打ち込まれたコードよりも悪質です——無限のサルが GNU emacs でタイプしても良いコードは作れません）（訳注：無限のサル定理）

したがって、GNU emacs を放棄するか、それをより現実的な設定に変更する必要があります。後者を採用するには、.emacs ファイルに以下のコードを貼り付けてください。

(defun c-lineup-arglist-tabs-only (ignored)
  "Line up argument lists by tabs, not spaces"
  (let* ((anchor (c-langelem-pos c-syntactic-element))
         (column (c-langelem-2nd-pos c-syntactic-element))
         (offset (- (1+ column) anchor))
         (steps (floor offset c-basic-offset)))
    (* (max steps 1)
       c-basic-offset)))

(dir-locals-set-class-variables
 'linux-kernel
 '((c-mode . (
        (c-basic-offset . 8)
        (c-label-minimum-indentation . 0)
        (c-offsets-alist . (
                (arglist-close         . c-lineup-arglist-tabs-only)
                (arglist-cont-nonempty .
                    (c-lineup-gcc-asm-reg c-lineup-arglist-tabs-only))
                (arglist-intro         . +)
                (brace-list-intro      . +)
                (c                     . c-lineup-C-comments)
                (case-label            . 0)
                (comment-intro         . c-lineup-comment)
                (cpp-define-intro      . +)
                (cpp-macro             . -1000)
                (cpp-macro-cont        . +)
                (defun-block-intro     . +)
                (else-clause           . 0)
                (func-decl-cont        . +)
                (inclass               . +)
                (inher-cont            . c-lineup-multi-inher)
                (knr-argdecl-intro     . 0)
                (label                 . -1000)
                (statement             . 0)
                (statement-block-intro . +)
                (statement-case-intro  . +)
                (statement-cont        . +)
                (substatement          . +)
                ))
        (indent-tabs-mode . t)
        (show-trailing-whitespace . t)
        ))))

(dir-locals-set-directory-class
 (expand-file-name "~/src/linux-trees")
 'linux-kernel)

これにより、emacs は ~/src/linux-trees 下的 C 源文件获得更好的内核代码风格。

しかし、emacs でコードを正しく整形することができなくても、すべてを失うわけではありません。代わりに indent 。

ただし、GNU indent も GNU emacs と同様に設定の問題があるため、いくつかのコマンドオプションを指定する必要があります。ただし、これはまだそれほど深刻ではありません。なぜなら、GNU indent の開発者も K&R の権威を認めているからです（GNU の人々は悪人ではありません。彼らはこの問題に関して重大な誤解に陥っているだけです）。したがって、indent にオプションを指定するだけで十分です。 -kr -i8 (代表 K&R，8 字符缩进)，或使用 scripts/Lindent 这样就可以以最时髦的方式缩进源代码。

indent 有很多选项，特别是重新格式化注释的时候，你可能需要看一下它的手册。 不过记住： indent 不能修正坏的编程习惯。

11) 数据结构¶

如果一个数据结构，在创建和销毁它的单线执行环境之外可见，那么它必须要有一个引 用计数器。内核里没有垃圾收集 (并且内核之外的垃圾收集慢且效率低下)，这意味着你 绝对需要记录你对这种数据结构的使用情况。

引用计数意味着你能够避免上锁，并且允许多个用户并行访问这个数据结构——而不需要 担心这个数据结构仅仅因为暂时不被使用就消失了，那些用户可能不过是沉睡了一阵或 者做了一些其他事情而已。

注意上锁 不能 取代引用计数。上锁是为了保持数据结构的一致性，而引用计数是一 个内存管理技巧。通常二者都需要，不要把两个搞混了。

很多数据结构实际上有 2 级引用计数，它们通常有不同 类 的用户。子类计数器统 计子类用户的数量，每当子类计数器减至零时，全局计数器减一。

这种 多级引用计数 的例子可以在内存管理 (struct mm_struct: s_count と s_active) で見つけることができます。struct super_block覚えておくべきことは、他の実行スレッドがデータ構造にアクセスできる場合、このデータ構造に参照カウンタがなければほぼ間違いなくバグです。

12) マクロ、列挙とRTL

複数のステートメントを持つマクロは do-while ブロックで囲むべきです：¶

用于定义常量的宏的名字及枚举里的标签需要大写。

#define CONSTANT 0x12345

在定义几个相关的常量时，最好用枚举。

宏的名字请用大写字母，不过形如函数的宏的名字可以用小写字母。

一般的，如果能写成内联函数就不要写成像函数的宏。

左辺値として使用されるパラメータ付きマクロ：FOO(x) = y；もし FOO をインライン関数に変換すると、この使い方はエラーになります。

#define macrofun(a, b, c)                       \
        do {                                    \
                if (a == 5)                     \
                        do_this(b, c);          \
        } while (0)

使用宏的时候应避免的事情：

  1. 影响控制流程的宏：

#define FOO(x)                                  \
        do {                                    \
                if (blah(x) < 0)                \
                        return -EBUGGERED;      \
        } while (0)

非常 不好。它看起来像一个函数，不过却能导致 调用 它的函数退出；不要打 乱读者大脑里的语法分析器。

  1. 依赖于一个固定名字的本地变量的宏：

#define FOO(val) bar(index, val)

可能看起来像是个不错的东西，不过它非常容易把读代码的人搞糊涂，而且容易导致看起 来不相关的改动带来错误。

  1. ret はローカル変数の一般的な名前ですが、__foo_ret は既存の変数と衝突する可能性が低いため、より安全です。

  2. 忘记了优先级：使用表达式定义常量的宏必须将表达式置于一对小括号之内。带参数 的宏也要注意此类问题。

#define CONSTANT 0x4000
#define CONSTEXP (CONSTANT | 3)

  1. 在宏里定义类似函数的本地变量时命名冲突：

#define FOO(x)                          \
({                                      \
        typeof(x) ret;                  \
        ret = calc_ret(x);              \
        (ret);                          \
})

cpp マニュアルではマクロについて詳しく説明されています。gcc internals マニュアルでは RTL（Register Transfer Language）について詳しく説明されており、カーネル内のアセンブリ言語でよく使われます。

<linux/device.h> にはドライバモデル診断マクロがいくつか定義されており、これらを使用して情報を正しいデバイスとドライバに紐付け、適切なメッセージレベルで表示する必要があります。これらのマクロには dev_err()、dev_warn()、dev_info() などがあります。特定のデバイスに関連しない情報については、<linux/printk.h> が定義しています。

13) 打印内核消息¶

内核开发者应该是受过良好教育的。请一定注意内核信息的拼写，以给人以好的印象。 不要用不规范的单词比如 dont，而要用 do not 或者 don't 。保证这些信 息简单明了,无歧义。

内核信息不必以英文句号结束。

在小括号里打印数字 (%d) 没有任何价值，应该避免这样做。

良いデバッグ情報の作成は大きな挑戦ですが、作成後はリモートデバッグ時に大きな助けになります。しかし、デバッグ情報の出力方法は通常の情報と異なります。他の pr_XXX() 関数は条件に関係なく出力しますが、デフォルトではコンパイルされません（DEBUG が定義されているか、CONFIG_DYNAMIC_DEBUG が設定されている必要があります）。実際にはこれも dev_dbg() に関連します。すでに DEBUG が有効な場合、 VERBOSE_DEBUG を使用して dev_vdbg() を追加するという慣例があります。 pr_notice(), pr_info(), pr_warn(), pr_err() 和其他。

多くのサブシステムは Kconfig を通じてデバッグオプションを提供しており、対応する Makefile に -DDEBUG を設定します。他の場合では特殊なファイルで #define DEBUG が使用されます。デバッグ情報が常に出力される必要がある場合は（たとえば、すでにデバッグ関連の #ifdef 条件が含まれている場合）、printk(KERN_DEBUG …) を使用できます。pr_debug() 16) Kconfig デバッグオプション

多くのサブシステムは Kconfig を通じてデバッグオプションを提供しており、対応する Makefile に -DDEBUG を設定します。他の場合では特殊なファイルで #define DEBUG が使用されます。デバッグ情報が常に出力される必要がある場合は（たとえば、すでにデバッグ関連の #ifdef 条件が含まれている場合）、printk(KERN_DEBUG …) を使用できます。

14) 分配内存¶

内核提供了下面的一般用途的内存分配函数： kmalloc(), kzalloc(), kmalloc_array(), kcalloc(), vmalloc() 和 vzalloc()。 API ドキュメントを参照してください。

传递结构体大小的首选形式是这样的：

p = kmalloc(sizeof(*p), ...);

別のやり方では、sizeof の操作数は構造体の名前になります。これにより可読性が低下し、バグの原因になる可能性があります。ポインタ変数の型が変更された場合でも、メモリ割り当て関数に渡す sizeof の結果は変化しない可能性があります。

void ポインタの戻り値を強制的にキャストするのは冗長です。C 言語では、void ポインタから他のポインタ型への変換は問題ありません。

分配一个数组的首选形式是这样的：

p = kmalloc_array(n, sizeof(...), ...);

分配一个零长数组的首选形式是这样的：

p = kcalloc(n, sizeof(...), ...);

n * sizeof(…) のオーバーフローを検出する 2 種類の形式があります。オーバーフローが発生した場合は NULL を返します。

15) 内联弊病¶

有一个常见的误解是 内联 gcc が提供するコードの実行速度を速くするオプションです。インライン関数の使用は、マクロの代替として必要な場合（第 12 章を参照）にのみ適切ですが、多くの場合そうではありません。インラインの過剰使用はカーネルサイズを大きくし、全体のシステムの実行速度を遅くします。カーネルが大きいと、インストラクションキャッシュを多く占領し、pagecache の利用可能なメモリが減少します。想像してみてください、pagecache のヒットミスが一度発生すると、5 ミリ秒のディスクアクセスが必要になります。5 ミリ秒の間に CPU は多くの命令を実行できます。

関数が 3 行以上ある場合、それをインライン関数にしないという基本的な原則があります。ただし、あるパラメータがコンパイル時定数であり、その定数によりコンパイラが関数の大部分を最適化できるとわかっている場合は、inline キーワードを付けることができます。 kmalloc() 内联函数就是一个很好的例子。

static で一度しか使われない関数に inline を付けることは、損失がありません。なぜなら、何らかの妥協が不要だからです。技術的には正しいですが、実際には gcc が自動的にインライン化してくれます。また、他のユーザーが inline を削除するよう求めると、その議論が inline の潜在的な価値を打ち消してしまい、得にならない場合があります。

16) 函数返回值及命名¶

関数は複数の型の値を返すことができます。最も一般的なのは、関数が成功または失敗を示す値です。このような値は、エラーコード整数（-Exxx＝失敗、0＝成功）または 成功 布尔值 (0＝失败，非0＝成功)。

この 2 種類の表現を混用すると、見つけにくいバグの原因になります。C 言語が整数型とブール型を厳密に区別していたら、コンパイラがこれらのエラーを検出してくれますが、C 言語は区別していません。このようなバグを防ぐために、以下の慣習を守ってください:

如果函数的名字是一个动作或者强制性的命令，那么这个函数应该返回错误代
码整数。如果是一个判断，那么函数应该返回一个 "成功" 布尔值。

比如， add work コマンドです。add_work() が成功時は 0 を返し、失敗時は -EBUSY を返します。同様に、 PCI device present 是一个判断，所以 pci_dev_present() 在成功找到一个匹配的设备时应该返回 1，如果找不到时应该返回 0。

すべての EXPORTed 関数はこの慣習に従う必要があります。すべての公開関数も同様にすべきです。プライベート(static) 関数はこの慣習に従う必要はありませんが、同様にすることを推奨します。

計算結果そのものを返す関数はこの慣習に従う必要がありません。一般的に、正常な値範囲外の結果を返してエラーを示します。典型的な例はポインタを返す関数で、NULL や ERR_PTR メカニズムを使ってエラーを報告します。

17) 不要重新发明内核宏¶

include/linux/kernel.h にはいくつかのマクロが含まれています。これらを使用してください。自分で変種を作成しないでください。例えば、配列の長さを計算する場合はこのマクロを使用してください

#define ARRAY_SIZE(x) (sizeof(x) / sizeof((x)[0]))

类似的，如果你要计算某结构体成员的大小，使用

#define sizeof_field(t, f) (sizeof(((t*)0)->f))

厳密な型チェックが可能な min() と max() マクロもあります。必要に応じて使用してください。自分で確認して、そのヘッダーファイルに定義されている他のユーティリティを活用してください。定義がある場合は、自分のコードで再定義しないでください。

18) 编辑器模式行和其他需要罗嗦的事情¶

ソースファイルに埋め込まれた特殊なマーカーで示された構成情報は、いくつかのエディタが解釈できます。例えば、emacs はこのような行を解釈できます：

-*- mode: c -*-

或者这样的：

/*
Local Variables:
compile-command: "gcc -DMAGIC_DEBUG_FLAG foo.c"
End:
*/

Vim はこのようなマーカーを解釈できます：

/* vim:set sw=8 noet */

不要在源代码中包含任何这样的内容。每个人都有他自己的编辑器配置，你的源文件不 应该覆盖别人的配置。这包括有关缩进和模式配置的标记。人们可以使用他们自己定制 的模式，或者使用其他可以产生正确的缩进的巧妙方法。

19) 内联汇编¶

特定のアーキテクチャのコードでは、CPUやプラットフォームに依存した機能と接続するためにインラインアセンブリを使用する必要があります。必要と判断した場合は躊躇わずに使用してください。ただし、C言語で実現可能な場合、無理にインラインアセンブリを使用しないでください。可能な限り、C言語とハードウェアの通信はC言語で行うべきです。

共通部分をラップするためのインラインアセンブリの簡単なアシスタント関数を作成してください。微細な違いがあるだけの複数のインラインアセンブリを繰り返し記述しないでください。インラインアセンブリはC言語のパラメータを使用できます。

大型，有一定复杂度的汇编函数应该放在 .S 文件内，用相应的 C 原型定义在 C 头文 件中。汇编函数的 C 原型应该使用 asmlinkage 。

アセンブリ命令をvolatile属性でマークすることで、GCCが副作用がないと判断して削除しないようにできます。常にこの方法を使う必要はありませんが、不要な操作は最適化を制限するため、避けたほうが良いです。

複数の命令を含む単一のインラインアセンブリ命令を記述する際は、各命令をダブルクォーテーションで区切り、改行して記述してください。最後の命令を除き、各命令末尾にntを追加することで、アセンブリ出力時に次の命令の正しいインデントが可能です：

asm ("magic %reg1, #42\n\t"
     "more_magic %reg2, %reg3"
     : /* outputs */ : /* inputs */ : /* clobbers */);

20) 条件编译¶

可能な限り.cファイル内でプリプロセッサ条件(#if, #ifdef)を使用しないでください。これによりコードの可読性が低下し、論理の追跡が難しくなります。代替案として、ヘッダーファイル内でプリプロセッサ条件で関数を提供し、#elseで無効なスタブ関数(no-op stub)バージョンを提供します。その後、.cファイル内でヘッダーファイル内に定義された関数を無条件で呼び出してください。これにより、コンパイラがスタブ関数の呼び出しにコードを生成しなくなり、結果は同じですが論理が明確になります。

全体の関数をコンパイルする方が、関数や式の一部をコンパイルするよりも望ましいです。式内にifdefを設置するのではなく、式の一部または全部を別個のアシスタント関数に分解し、その関数内でプリプロセッサ条件を適用してください。

特定の構成で未使用になる可能性のある関数や変数がある場合、コンパイラは未使用定義として警告を出します。このような場合、__maybe_unused属性を付与するのではなく、プリプロセッサ条件で囲むべきではありません。(ただし、関数や変数が常に未使用であれば、直接削除してください。)

コード内でKconfigマーキングをCの論理式に変換する際には、IS_ENABLEDマクロを使用してください。一般的なC条件式で使用してください：

if (IS_ENABLED(CONFIG_SOMETHING)) {
        ...
}

コンパイラは定数畳み込みを行い、#ifdefのようにコードブロックを含むか排除するため、実行時コストは発生しません。しかし、この方法はCコンパイラがブロック内のコードを確認し、構文や型、シンボル参照などの正しさをチェックできるため、条件が満たされない場合でも、シンボルが存在しないコードブロックでは# ifdefを使用する必要があります。

意味のある#ifや#ifdefブロックの末尾（複数行の場合は）で、#endifの行の後に条件式をコメントで記載してください。例えば：

#ifdef CONFIG_SOMETHING
...
#endif /* CONFIG_SOMETHING */

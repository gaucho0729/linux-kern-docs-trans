LinuxSH への新しいボードの追加¶

Paul Mundt <lethal@linux-sh.org>

このドキュメントは、LinuxSHポートに新しいボードのサポートを追加するために必要な手順を概説しています。これは2.5および2.6のカーネルにおいても同様に、2.4と2.5/2.6のSHバックエンドの間で顕著な変更点を説明することも試みています。

1. 新しいディレクトリ構造¶

まず注意すべきは新しいディレクトリ構造です。2.4では、ボード固有のコード（stboardsを除く）はarch/sh/kernel/直下に配置されていました。ボード固有のヘッダーはinclude/asm-sh/に配置されていました。新しいカーネルでは、ボードタイプ、コンパニオンチップタイプ、CPUタイプごとに分離されています。このディレクトリ階層のツリー表示は以下のようになります：

ボード固有のコード：

.
|-- arch
|   `-- sh
|       `-- boards
|           |-- adx
|           |   `-- board-specific files
|           |-- bigsur
|           |   `-- board-specific files
|           |
|           ... more boards here ...
|
`-- include
    `-- asm-sh
        |-- adx
        |   `-- board-specific headers
        |-- bigsur
        |   `-- board-specific headers
        |
        .. more boards here ...

次に、コンパニオンチップについて：

.
`-- arch
    `-- sh
        `-- cchips
            `-- hd6446x
                `-- hd64461
                    `-- cchip-specific files

…そして同様に。コンパニオンチップのヘッダーはボード固有のヘッダーと同じように扱われます。したがって、include/asm-sh/hd64461はhd6446の固有のヘッダーをすべて含んでいます。

最後に、CPUファミリーのサポートも抽象化されています：

.
|-- arch
|   `-- sh
|       |-- kernel
|       |   `-- cpu
|       |       |-- sh2
|       |       |   `-- SH-2 generic files
|       |       |-- sh3
|       |       |   `-- SH-3 generic files
|       |       `-- sh4
|       |           `-- SH-4 generic files
|       `-- mm
|           `-- This is also broken out per CPU family, so each family can
|               have their own set of cache/tlb functions.
|
`-- include
    `-- asm-sh
        |-- cpu-sh2
        |   `-- SH-2 specific headers
        |-- cpu-sh3
        |   `-- SH-3 specific headers
        `-- cpu-sh4
            `-- SH-4 specific headers

CPUサブタイプは抽象化されていません。したがって、これらは依然としてCPUファミリー固有のコードで処理する必要があります。

2. 新しいボードの追加¶

まず確認すべきは、追加するボードが独立したボードか、それともボードファミリーの一部で、ほぼ同じボード固有コードを共有できるものかです。

最初のケースでは、arch/sh/boards/にディレクトリを作成し、ビルドシステムにボードを接続するためのルールを追加するだけで十分です（次のセクションで詳しく説明します）。ただし、ボードファミリーの場合は、arch/sh/boards/の上位ディレクトリに共通のディレクトリを作成し、ファミリーの各メンバーごとにサブディレクトリを設置するのがより合理的です。Solution Engineとhp6xxボードはこの例です。

新しいarch/sh/boards/ディレクトリを設定した後、include/asm-shにこのボード専用のヘッダーを格納するディレクトリも作成する必要があります（複数ある場合）。ビルドシステムとシームレスに連携するためには、このディレクトリ名をarch/sh/boards/のディレクトリ名と一致させるのが望ましいですが、ボードが再度ファミリーの一部である場合、ビルドシステムはincdir-yのオーバーロードによりこれを処理できるため、ファミリーのメンバー名でディレクトリを名付けることも可能です。

各ボードが持つ必要がある要素は、arch/sh/boards と include/asm-sh/ の階層に共通しています。この説明をより明確にするために、仮想のボードを追加する例を挙げます。設定コードでは、少なくとも get_system_type() と platform_setup() の定義を提供する必要があります。仮想ボードの場合、このようなコードになるかもしれません:

/*
* arch/sh/boards/vapor/setup.c - Setup code for imaginary board
*/
#include <linux/init.h>

const char *get_system_type(void)
{
        return "FooTech Vaporboard";
}

int __init platform_setup(void)
{
        /*
        * If our hardware actually existed, we would do real
        * setup here. Though it's also sane to leave this empty
        * if there's no real init work that has to be done for
        * this board.
        */

        /* Start-up imaginary PCI ... */

        /* And whatever else ... */

        return 0;
}

新しい仮想ボードは、machvec に接続しないと実用性がありません。

machvec の関数はいくつかのカテゴリに分類されます:

  • I/O メモリ（inb など）や PCI/主記憶（readb など）への I/O 関数。

  • I/O マッピング関数（ioport_map, ioport_unmap など）。

  • 「ハートビート」関数。

  • PCI および IRQ の初期化ルーチン。

  • 一貫性のあるアロケータ（特殊なアロケータが必要なボード向け、特にボード固有の SRAM から DMA ハンドルを割り当てる場合）。

machvec に追加・削除される関数は時間とともに変化するため、常に include/asm-sh/machvec.h を確認してください。

カーネルは、起動時に machvec 内の未定義の関数ポインタを一般的なルーチンで自動的にラップします。machvec 関数はツリーの大部分で条件付きで参照されるためです。一部のボード（例: dreamcast と sh03）は非常に少ない machvec を持つ一方、他のボード（例: rts7751r2d）はほぼすべてを定義する必要があります。

新しいマシンを追加するのは比較的簡単です（vapor を例にします）:

ボード固有の定義が極めて簡潔な場合（これはほとんどのボードに当てはまります）、単一のボード固有ヘッダーファイルで十分です。

  • include/asm-sh/vapor.h という新しいファイルを追加し、マシン固有の I/O 関数のプロトタイプを記述します。これらの関数は、マシンベクターを埋める際に必要になります。例えば vapor_inb など、マシン名で始まる関数です。

    これらのプロトタイプは、__IO_PREFIX を適切な値に設定することで自動的に生成されます。典型的な例は以下の通り:

    #define __IO_PREFIX vapor
#include <asm/io_generic.h>

    ボード固有のヘッダーファイルのどこかにあります。まだ legacy io.h を使用しているボードを移植する場合は、完全に削除し新しいモデルに移行してください。

  • ボードの setup.c にマシンベクターの定義を追加します。最低限、以下のように定義する必要があります:

    struct sh_machine_vector mv_vapor __initmv = {
        .mv_name = "vapor",
};
ALIAS_MV(vapor)

  • 最後に、arch/sh/boards/vapor/io.c というファイルを追加し、マシン固有の I/O 関数の定義を記述します（関数が十分にある場合のみ）。

3. ビルドシステムへの接続¶

対応するディレクトリが設定され、ボード固有のコードもすべて整った今、ビルドシステムにすべてを組み込む方法を確認しましょう。

ビルドシステムの大部分はすでに動的になり、必要なのはここに適切なエントリを追加するだけです。

最初に実行すべきことは、arch/sh/Kconfigに「システムタイプ」メニューの下にエントリを追加することです：

config SH_VAPOR
        bool "Vapor"
        help
        select Vapor if configuring for a FooTech Vaporboard.

次に、arch/sh/Makefileにもこのエントリを追加する必要があります。すべてのボードは、arch/sh/boardsに存在するボードディレクトリ名をmachdir-yとして登録することでビルド可能になります。このエントリは、arch/sh/boards配下のサブディレクトリに存在する場合でも、その親ディレクトリをすべてリストに含める必要があります。新しいボードの場合、このエントリは以下のようになります：

machdir-$(CONFIG_SH_VAPOR)  += vapor

arch/sh/boards/vapor/ディレクトリにすべてのファイルを配置している前提で、

次に、ビルドシステムはinclude/asm-shディレクトリも同様に名前を付けていると仮定します。もし名前が異なる場合（例えば複数のボードが共通のファミリに属する場合）、ディレクトリ名はincdir-yに暗黙的に追加される必要があります。既存のコードはSolution Engineおよびhp6xxボードでこの処理を行っているため、これらを参考にしてください。

これで準備が整いましたら、マシンタイプのエントリを追加する必要があります。これはarch/sh/tools/mach-typesリストの末尾にエントリを追加することで実現します。この処理方法は自明なので、ここでは説明は省略します。これにより、共通コードのどこかでボードのチェックが必要な場合、暗黙的にチェックが行われるようになります。例えば：

/* Make sure we're on the FooTech Vaporboard */
if (!mach_is_vapor())
        return -ENODEV;

また、mach_is_boardname()のチェックは、mach-typesのエントリがすべて大文字であるとしても、自動的に小文字に強制されます。本当に気になる場合はスクリプトを確認できますが、コードはかなり汚いので、おそらく読む必要はありません。

すべての準備が整った今、新しいボード用のdefconfigを提供する必要があります。これにより、このボードを使用する他のユーザーは、設定を推測するのではなく、この設定を参考にできるようになります。

さらに、新しいボード用のサンプル.config（例：arch/sh/configs/vapor_defconfig）をコピーした後、このファイルを直接ビルドターゲットとして使用でき、ヘルプテキストに自動的に表示されます。

make helpの出力を見てみると、以下のように表示されるはずです：

アーキテクチャ固有のターゲット (sh)：

zImage

圧縮されたカーネルイメージ (arch/sh/boot/zImage)

adx_defconfig

adx用にビルド

cqreek_defconfig

cqreek用にビルド

dreamcast_defconfig（デフォルト設定ファイル）

dreamcast用にビルド

…

vapor_defconfig（デフォルト設定ファイル）

vapor用にビルド

これにより、以下のような操作が可能になります:

$ make ARCH=sh CROSS_COMPILE=sh4-linux- vapor_defconfig vmlinux

これにより、このボード用のdefconfigをコピーし、oldconfigを実行して（作成時からの新しいオプションの入力が求められます）、新しいボード用の機能的なカーネルの構築を開始します。

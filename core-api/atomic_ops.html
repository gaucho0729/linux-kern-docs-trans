アトミックおよびビットマスク操作のセマンティクスと挙動¶

著者

David S. Miller

このドキュメントは、Linuxポートメンテナがアトミックカウンタ、ビット操作、スピンロックインターフェースを適切に実装する方法をガイドするものです。

アトミック型と操作¶

atomic_t型は符号付き整数として定義され、atomic_long_t型は符号付き長整数として定義されるべきです。また、これらは不透明な型として実装されるべきで、通常のC整数型へのキャストは失敗する必要があります。以下のようなコードで十分です：

typedef struct { int counter; } atomic_t;
typedef struct { long counter; } atomic_long_t;

歴史的にカウンタはvolatile修飾子で宣言されていましたが、これは現在は推奨されません。詳しくは なぜ「volatile」型クラスは使用すべきではないか をご参照ください。

local_tはatomic_tと非常に似ています。カウンタがCPUごとで、かつ1つのCPUのみで更新される場合、local_tはおそらくより適切です。詳しくは ローカルアトミック操作のセマンティクス をご参照ください。

atomic_tの最初に実装すべき操作は初期化子と通常の書き込みです。

#define ATOMIC_INIT(i)          { (i) }
#define atomic_set(v, i)        ((v)->counter = (i))

最初のマクロは、以下の定義などに使用されます：

static atomic_t my_counter = ATOMIC_INIT(1);

初期化子はアトミックな操作であり、初期化子が実行時よりも前に実行されれば、アトミック操作の戻り値が初期値を反映して正しく保証されます。初期化子が実行時で使用される場合、他のスレッドからatomic_readで値を読み取る前に、適切な暗黙のまたは明示的なメモリバリアが必要です。

すべての atomic_ インターフェースでは、先頭の atomic_ with atomic_long_ を変更して、atomic_long_tを操作するようにします。

2番目のインターフェースは実行時にも使用できます。例えば：

struct foo { atomic_t counter; };
...

struct foo *k;

k = kmalloc(sizeof(*k), GFP_KERNEL);
if (!k)
        return -ENOMEM;
atomic_set(&k->counter, 0);

設定はアトミックであり、すべてのスレッドのアトミック操作の戻り値が、この操作で設定された値または他の操作で設定された値を反映して正しく保証されます。他のスレッドからatomic_readで値を読み取る前に、適切な暗黙のまたは明示的なメモリバリアが必要です。

次に、以下の項目があります：

#define atomic_read(v)  ((v)->counter)

呼び出しスレッドが現在表示しているカウンタ値を単純に読み込むだけです。この読み込みはアトミックであり、適切な暗黙または明示的なメモリバリアーが他のスレッドによるランタイム初期化の後使用され、値がインターフェース操作のみで変更される場合、返却値はインターフェース操作で初期化または変更された値のいずれかを保証します。atomic_readは他のスレッドによるランタイム初期化がまだ可視でないため、ユーザーは適切な暗黙または明示的なメモリバリアーでその処理を担当する必要があります。

警告

atomic_read() および atomic_set() バリアーを暗黙に含めないでください！

一部のアーキテクチャでは、volatileキーワード、バリアー、インラインアセンブリなどを使用してatomic_read()とatomic_set()の一部の即時性を保証する場合があります。これは一貫して保証されておらず、今後変更される可能性があるため、atomic_tのすべてのユーザーはatomic_read()とatomic_set()を単なるCステートメントとして扱い、コンパイラまたはプロセッサが再配置または完全に最適化してしまう可能性があることを理解する必要があります。適切なコンパイラおよび/またはメモリバリアーを各使用ケースで明示的に呼び出す必要があります。これを行わない場合、異なるアーキテクチャやコンパイラ最適化、あるいは関連のないコードの変更によって最適化が変化し、コードが突然破綻する可能性があります。

適切にアライメントされたポインタ、ロング、インテグ、チャーやその符号なし版は、atomic_read()とatomic_set()で説明した意味と同様にアトミックに読み込まれたり保存されたりできます。このため、READ_ONCE()とWRITE_ONCE()マクロを使用して、コンパイラがアクセスを最適化して消去してしまうのを防ぐ必要があります。また、コンパイラがアクセスを不意に生成してしまうのを防ぐことも重要です。

例えば、以下のコードを考えてみましょう：

while (a > 0)
        do_something();

コンパイラが変数aに値を保存しないと証明できる場合、コンパイラは次のようになることを正当に変換できます：

if (a > 0)
        for (;;)
                do_something();

コンパイラがこれを実行したくない（おそらくそうでしょう）場合は、以下のようになるようにしてください：

while (READ_ONCE(a) > 0)
        do_something();

代わりに、ループ内にbarrier()呼び出しを追加することもできます。

もう一つの例として、以下のコードを考えてみましょう：

tmp_a = a;
do_something_with(tmp_a);
do_something_else_with(tmp_a);

コンパイラが変数aに値を保存しないと証明できる場合、コンパイラは次のようになることを正当に変換できます：

tmp_a = a;
do_something_with(tmp_a);
tmp_a = a;
do_something_else_with(tmp_a);

これは、do_something_with()とdo_something_else_with()に同じ値が渡されることが期待される場合、コードを致命的に混乱させる可能性があります。

do_something_with()がインライン関数であり、レジスタを非常に多く使用する場合、コンパイラがこの追加のロードを生成する可能性があります。変数aからロードし直すことで、スタックへのフラッシュを回避し、後続のロードを実行できるためです。このような方法でコンパイラがコードを攻撃しないようにするには、以下のコードを書く必要があります。

tmp_a = READ_ONCE(a);
do_something_with(tmp_a);
do_something_else_with(tmp_a);

最終的な例として、変数aが起動時に2番目のCPUがオンラインになる前に設定され、その後は変更されないものと仮定して、以下のようなコードを考えてみましょう。この場合、メモリバリアは必要ありません。

if (a)
        b = 9;
else
        b = 42;

コンパイラは、上記のコードを以下のコードに変換して追加のストアを生成することが法的に許容されます。

b = 42;
if (a)
        b = 9;

他の並行して実行されているコードがaがゼロであるときにbが42になることはないと期待していた場合、これは致命的な驚きとなる可能性があります。このようなコンパイラの動作を防ぐには、以下のよう書きましょう。

if (a)
        WRITE_ONCE(b, 9);
else
        WRITE_ONCE(b, 42);

変数aがランタイムで変更される可能性がある場合、適切なメモリバリア、ロック、またはアトミック操作を用いないと、絶対にこのような操作を行わないでください！

警告

READ_ONCE() または WRITE_ONCE() バリアを暗示しないでください！

では、次にアセンブリコードを用いて通常実装されるアトミック操作インターフェースについて説明します。

void atomic_add(int i, atomic_t *v);
void atomic_sub(int i, atomic_t *v);
void atomic_inc(atomic_t *v);
void atomic_dec(atomic_t *v);

これらの4つのルーチンは、指定されたatomic_t値に整数値を加算または減算します。最初の2つのルーチンは明示的な整数を渡して調整を行い、後者の2つは暗黙的な調整値「1」を使用します。

これらの2つのルーチンの非常に重要な点は、明示的なメモリバリアを必要としないということです。SMP安全な方法でatomic_tカウンターを更新するだけでよいです。

次に、以下の項目があります：

int atomic_inc_return(atomic_t *v);
int atomic_dec_return(atomic_t *v);

これらのルーチンは、指定されたatomic_tに1を加算または減算し、操作後の新しいカウンター値を返します。

上記のルーチンとは異なり、これらのプリミティブは操作の前後で明示的なメモリバリアを含む必要があります。すべてのメモリ操作がアトミック操作呼び出しの前後でアトミック操作自体に対して強く順序付けされている必要があります。

たとえば、アトミック操作の前後でsmp_mb()呼び出しが存在しているかのように振る舞う必要があります。

実装で使用されるアトミック命令が上記の要件を満たす明示的なメモリバリアセマンティクスを提供する場合、それは問題ありません。

では、次に進みましょう:

int atomic_add_return(int i, atomic_t *v);
int atomic_sub_return(int i, atomic_t *v);

これらはatomic_{inc,dec}_return()と同様の動作ですが、明示的なカウンター調整値を指定します。これはatomic_{inc,dec}_return()と同様に、メモリバリアセマンティクスが必要です。

次へ:

int atomic_inc_and_test(atomic_t *v);
int atomic_dec_and_test(atomic_t *v);

これらの関数は、指定されたアトミックカウンタをそれぞれ1ずつインクリメントおよびデクリメントします。これらは、結果となったカウンタ値がゼロかどうかを示すブール値を返します。

また、これらのプリミティブは、アトミック操作周辺に明示的なメモリバリアセマンティクスを提供します:

int atomic_sub_and_test(int i, atomic_t *v);

これはatomic_dec_and_test()と同様ですが、暗黙的な「1」ではなく明示的なデクリメントが行われます。このプリミティブは、操作周辺に明示的なメモリバリアセマンティクスを提供しなければなりません:

int atomic_add_negative(int i, atomic_t *v);

指定されたインクリメント値がアトミックカウンタ値に加算され、結果のカウンタ値が負数かどうかを示すブール値が返されます。このプリミティブは、操作周辺に明示的なメモリバリアセマンティクスを提供しなければなりません。

次に:

int atomic_xchg(atomic_t *v, int new);

アトミック変数vに対してアトミック交換操作を行い、指定された新しい値を設定します。この操作は、操作前のvの古い値を返します。

atomic_xchgは、操作周辺に明示的なメモリバリアを提供しなければなりません。

int atomic_cmpxchg(atomic_t *v, int old, int new);

アトミック値vに対して、指定された古い値と新しい値を用いたアトミック比較交換操作を行います。すべてのatomic_xxx操作と同様に、atomic_cmpxchgは、*vへのすべてのアクセスがatomic_xxx操作を通じて行われる限り、そのアトミック性セマンティクスを満たします。

atomic_cmpxchgは操作周辺に明示的なメモリバリアを提供しなければなりませんが、比較が失敗した場合はメモリ順序保証は必要ありません。

atomic_cmpx→のセマンティクスは、以下で定義される'cas'と同一です。

最後に:

int atomic_add_unless(atomic_t *v, int a, int u);

アトミック値vがuと等しくない場合、この関数はaをvに加算し、非ゼロを返します。vがuと等しい場合、ゼロを返します。これはアトミック操作として実行されます。

atomic_add_unlessは、失敗しなかった場合（0を返す場合を除く）操作周辺に明示的なメモリバリアを提供しなければなりません。

atomic_inc_not_zeroは、atomic_add_unless(v, 1, 0)と同等です。

値を返さないアトミック_t操作にメモリバリアセマンティクスを必要とする呼び出し元には、以下のインターフェースが定義されています:

void smp_mb__before_atomic(void);
void smp_mb__after_atomic(void);

値を返さない読み込み-変更-書き込みアトミック操作の前後にsmp_mb__before_atomic()とsmp_mb__after_atomic()を組み合わせることで、値を返す読み込み-変更-書き込みアトミック操作が提供する完全な順序を実現できます。

例えば、smp_mb__before_atomic()は以下のように使用されます:

obj->dead = 1;
smp_mb__before_atomic();
atomic_dec(&obj->ref_count);

atomic_dec()呼び出し前のすべてのメモリ操作が、アトミックカウンタ操作に対して強い順序で実行されるように保証します。上記の例では、obj->deadに「1」を割り当てる割り当てが、他のCPUに対してグローバルに可視になることを保証しています。

明示的なsmp_mb__before_atomic()呼び出しがなければ、実装は他のCPUに対してアトミックカウンタの更新が「obj->dead = 1;」の割り当てよりも先に可視になることが法的に許容される可能性があります。

上記のアトミック_t実装で必要なメモリバリアが欠如している場合、重大な結果を招くことがあります。これはLinuxカーネルで頻繁に見られるパターンの例で、アトミックカウンタを参照カウントの実装に使用するケースです。カウンタがゼロになると、オブジェクトへのアクセスが他のエンティティによって行われないことを保証します。

static void obj_list_add(struct obj *obj, struct list_head *head)
{
        obj->active = 1;
        list_add(&obj->list, head);
}

static void obj_list_del(struct obj *obj)
{
        list_del(&obj->list);
        obj->active = 0;
}

static void obj_destroy(struct obj *obj)
{
        BUG_ON(obj->active);
        kfree(obj);
}

struct obj *obj_list_peek(struct list_head *head)
{
        if (!list_empty(head)) {
                struct obj *obj;

                obj = list_entry(head->next, struct obj, list);
                atomic_inc(&obj->refcnt);
                return obj;
        }
        return NULL;
}

void obj_poke(void)
{
        struct obj *obj;

        spin_lock(&global_list_lock);
        obj = obj_list_peek(&global_list);
        spin_unlock(&global_list_lock);

        if (obj) {
                obj->ops->poke(obj);
                if (atomic_dec_and_test(&obj->refcnt))
                        obj_destroy(obj);
        }
}

void obj_timeout(struct obj *obj)
{
        spin_lock(&global_list_lock);
        obj_list_del(obj);
        spin_unlock(&global_list_lock);

        if (atomic_dec_and_test(&obj->refcnt))
                obj_destroy(obj);
}

注意

これはネットワーキングの一般的な隣接発見コードにおけるARPキュー管理の簡略化版です。Olaf Kirchは、メモリバリアに関するバグを発見し、 kfree_skb() アトミック_tメモリバリアの要件を明確に示しました。

上記のスキームでは、オブジェクトリスト削除時に実行されるobj->activeの更新が、アトミックカウンタのデクリメントが実行される前に他のプロセッサに可視である必要があります。

そうでない場合、カウンタがゼロになる前にobj->activeが設定されている可能性があり、obj_destroy()のアサーションがトリガーされます。エラーのシーケンスは以下の通りです：

cpu 0                           cpu 1
obj_poke()                      obj_timeout()
obj = obj_list_peek();
... gains ref to obj, refcnt=2
                                obj_list_del(obj);
                                obj->active = 0 ...
                                ... visibility delayed ...
                                atomic_dec_and_test()
                                ... refcnt drops to 1 ...
atomic_dec_and_test()
... refcount drops to 0 ...
obj_destroy()
BUG() triggers since obj->active
still seen as one
                                obj->active update visibility occurs

アトミック_t操作が返す値に必要なメモリバリアセマンティクスがあるため、上記のメモリ可視性のシーケンスは決して発生しません。具体的には、上記のケースでは、obj->activeの更新が完了するまで、atomic_dec_and_test()のカウンタデクリメントはグローバルに可視になりません。

歴史的な補足として、32ビットSparcはかつてatomic_t型の24ビットしか使用できませんでした。これはSMPの安全性のためにスピンロックとして8ビットを用いていたためです。Sparc32は「Compare and Swap」タイプの命令を持っていませんでしたが、その後「ハッシュテーブルのスピンロック」方式に移行し、32ビットのカウンタを実現できるようになりました。要するに、atomic_tのアドレスに基づいてスピンロックの配列をインデックス付けし、そのロックがアトミック操作を保護します。Pariscも同じ方式を使用しています。

古い386では、アトミック_t操作が返す値の処理が非常に遅いです。

アトミックビットマスク¶

ここでは、アトミックビットマスク操作を説明します。これらの操作のSMPおよびメモリバリアセマンティクスは、上記のatomic_t操作と同様の形状と範囲を持っています。

ネイティブなアトミックビット操作は、「unsigned long」Cデータ型のサイズにアライメントされたオブジェクトを処理し、少なくともそのサイズ以上である必要があります。各「unsigned long」内のビットのエンドイアンネスは、CPUのネイティブなエンドイアンネスです。

void set_bit(unsigned long nr, volatile unsigned long *addr);
void clear_bit(unsigned long nr, volatile unsigned long *addr);
void change_bit(unsigned long nr, volatile unsigned long *addr);

これらの関数は、「ADDR」で指されるビットマスクの「nr」ビットを設定、クリア、変更します。

これらは原子的に実行される必要がありますが、これらのインターフェースには暗黙のメモリバリアセマンティクスは必要ありません。

int test_and_set_bit(unsigned long nr, volatile unsigned long *addr);
int test_and_clear_bit(unsigned long nr, volatile unsigned long *addr);
int test_and_change_bit(unsigned long nr, volatile unsigned long *addr);

上記と同じですが、これらの関数は、アトミックビット操作前の変更されたビットが設定されていたかどうかを示すブール値を返します。

警告

「0」または「1」のブール値であることが極めて重要です。上記の関数が返す値として「long」を宣言して「old_val & mask」のような値を返すことで節約しようとするのは避けてください。それは機能しません。

一つの理由は、この返値が多くのインターフェースを使用するコードパスでintにトリミングされるため、64ビット環境でビットが上位32ビットに設定されている場合、テスト者はそれを決して見ることはないからです。

このような問題が発生する例として、thread_infoフラグ操作があります。test_and_set_ti_thread_flag()などの関数は返値をintに切り詰めます。このような現象は他の場所でも発生します。

これらの関数は、atomic_tカウンタ操作が返す値と同じように、実行周囲に明示的なメモリバリアセマンティクスを提供する必要があります。アトミックビット操作呼び出しの前に行われるすべてのメモリ操作は、アトミックビット操作がグローバルに可視化される前に、グローバルに可視化される必要があります。同様に、アトミックビット操作は、その後のすべてのメモリ操作がグローバルに可視化される前に、グローバルに可視化される必要があります。例えば：

obj->dead = 1;
if (test_and_set_bit(0, &obj->flags))
        /* ... */;
obj->killed = 1;

の実装は、各CPUに順番にスケジュールされます。run_on()プリミティブはsched_setaffinity()プリミティブをもとに簡単に実装できます。もちろん、多少「toy」に近い実装では、完了後にアフィニティを復元する方がより現実的ですが、「toy」と言った際の意図は test_and_set_bit() 「obj->dead = 1;」がCPUに可視になることを保証しなければなりません。アトミックメモリ操作によって test_and_set_bit() が可視になる前に、アトミックメモリ操作によって test_and_set_bit() が可視になる必要があります。「obj->killed = 1;」が可視になる前に。

最後に、基本的な操作があります：

int test_bit(unsigned long nr, __const__ volatile unsigned long *addr);

これは、「addr」で指されるビットマスクの「nr」ビットが設定されているかどうかを示すブール値を返します。

set_bit()やclear_bit()（値を返さないためメモリバリアセマンティクスを提供する必要がない）周囲に明示的なメモリバリアが必要な場合、2つのインターフェースが提供されます：

void smp_mb__before_atomic(void);
void smp_mb__after_atomic(void);

これらは、atomic_t操作の兄弟に似たように使用されます：

/* All memory operations before this call will
 * be globally visible before the clear_bit().
 */
smp_mb__before_atomic();
clear_bit( ... );

/* The clear_bit() will be visible before all
 * subsequent memory operations.
 */
 smp_mb__after_atomic();

ロックバリアセマンティクス（取得/解放、スピニングロックと同じ）を持つ特別なbitops（ビット操作）が2つあります。これらは、非_lock/unlockポストフィックス変体と同様の動作をしますが、取得/解放セマンティクスを提供するため、bit_spin_trylockおよびbit_spin_unlock型の操作で使用できます。これにより、追加のバリアを指定することなく使用できます。

int test_and_set_bit_lock(unsigned long nr, unsigned long *addr);
void clear_bit_unlock(unsigned long nr, unsigned long *addr);
void __clear_bit_unlock(unsigned long nr, unsigned long *addr);

.__clear_bit_unlockバージョンは非原子的ですが、依然としてアンロックバリアセマンティクスを実装しています。ロック自体がワード内の他のビットを保護している場合、これは有用です。

最後に、ビットマスク操作の非原子バージョンが提供されています。これらは、他の高レベルのSMPロックスキーマがビットマスクを保護しているコンテキストで使用され、実装に於いてはコストが低い非原子操作が使用可能であるためです。インターフェース名には2つのアンダースコアが接頭語として付与され、上記のビットマスク操作インターフェースと似ています。

void __set_bit(unsigned long nr, volatile unsigned long *addr);
void __clear_bit(unsigned long nr, volatile unsigned long *addr);
void __change_bit(unsigned long nr, volatile unsigned long *addr);
int __test_and_set_bit(unsigned long nr, volatile unsigned long *addr);
int __test_and_clear_bit(unsigned long nr, volatile unsigned long *addr);
int __test_and_change_bit(unsigned long nr, volatile unsigned long *addr);

これらの非原子バリアントは、特殊なメモリバリアセマンティクスを必要としません。

xchg()およびcmpxchg()は、値を返すアトミックおよびビット操作と同様の正確なメモリバリアセマンティクスを提供しなければなりません。

注意

xchg()、cmpxchg()およびその変体を使用したい場合は、linux/atomic.hをインクルードする必要があります。asm/cmpxchg.hではなく、コードがarch/*にあり、自身で処理できる場合を除きます。

スピニングロックおよび読み込み書き込みロック（rwlocks）にもメモリバリアの期待値があります。遵守すべきルールはシンプルです：

  1. ロックを取得する際、実装はその後のメモリ操作よりも先にグローバルに可視にする必要があります。

  2. ロックを解放する際、実装はすべての前のメモリ操作がロック解放よりも先にグローバルに可視になるようにする必要があります。

これにより、_atomic_dec_and_lock()が登場します。アーキテクチャに依存しないバージョンはlib/dec_and_lock.cに実装されていますが、ほとんどのプラットフォームではアセンブリで最適化したいでしょう。

int _atomic_dec_and_lock(atomic_t *atomic, spinlock_t *lock);

指定されたカウンタをアトミックにデクリメントし、ゼロになる場合、指定されたスピニングロックを取得してゼロになるまでカウンタをデクリメントします。ゼロにならない場合はスピニングロックには何もしません。

メモリバリアを正しく実装するのは実際には非常に簡単です。スピニングロックの取得要件を満たすだけで、スピニングロック操作がその後のメモリ操作よりも先にグローバルに可視になるようにします。

抽象的なアトミック操作を定義することで、この操作をより明確に示せます。

long cas(long *mem, long old, long new);

「cas」は「compare and swap（比較して交換）」を意味します。これは原子的に：

  1. 「old」と「mem」に現在の値を比較します。

  2. 等しい場合、「new」が「mem」に書き込まれます。

  3. いずれにせよ、「mem」の現在の値が返されます。

例として、アトミックカウンタの更新は以下のようになります:

void example_atomic_inc(long *counter)
{
        long old, new, ret;

        while (1) {
                old = *counter;
                new = old + 1;

                ret = cas(counter, old, new);
                if (ret == old)
                        break;
        }
}

擬似C言語のatomic_dec_and_lock()を構築するためにcas()を使用します:

int _atomic_dec_and_lock(atomic_t *atomic, spinlock_t *lock)
{
        long old, new, ret;
        int went_to_zero;

        went_to_zero = 0;
        while (1) {
                old = atomic_read(atomic);
                new = old - 1;
                if (new == 0) {
                        went_to_zero = 1;
                        spin_lock(lock);
                }
                ret = cas(atomic, old, new);
                if (ret == old)
                        break;
                if (went_to_zero) {
                        spin_unlock(lock);
                        went_to_zero = 0;
                }
        }

        return went_to_zero;
}

メモリバリアに関しては、spin_lock()が後続のメモリ操作（cas()を含む）を厳密に自身に対して順序付けている限り、問題ありません。

別の言い方をすれば、_atomic_dec_and_lock()はカウンタがゼロになることを取得されるスピンロックよりも前に表示されることを保証しなければなりません。

注意

注意してください。カウンタがゼロにならない場合、メモリ順序の要件は一切ありません。

メモリ割当制御¶

メモリを割り当てる必要がある関数は、そのメモリがどのように割り当てられるかを示すためにGFPフラグをよく使用します。GFPは「get free pages（空きページを取得）」の略で、その下にあるメモリ割り当て関数です。すべてのGFPフラグがすべてのメモリを割り当てる関数に許可されているわけではありません。ほとんどのユーザーは、シンプルな GFP_KERNEL.

ページの移動性と配置ヒント¶

これらのフラグは、ページがどれだけ移動可能かに関するヒントを提供します。移動性が似たページは、同じページブロック内に配置されるようにされ、外部フラグメンテーションによる問題を最小限に抑えます。

__GFP_MOVABLE (ゾーン修飾子としても使用される) ページがメモリコンパクション中にページ移動によって移動可能であるか、または回収可能であることを示します。

__GFP_RECLAIMABLE SLAB_RECLAIM_ACCOUNTを指定したスラブ割り当てや、shrinking経由でページを解放可能なスラブ割り当てに使用されます。

__GFP_WRITE 呼び出し元がページを汚染する意図を持っていることを示します。可能であれば、これらのページはローカルゾーン間で分散され、すべての汚染ページが1つのゾーンに集中しないようにします（公平なゾーン割り当てポリシー）。

__GFP_HARDWALL cpusetメモリ割り当てポリシーを強制します。

__GFP_THISNODE 割り当てが要求されたノードからのみ満たされ、フォールバックや配置ポリシーの強制が行われません。

__GFP_ACCOUNT 割り当てがkmemcgに記録されます。

ウォーターマーク修飾子 – 緊急予備領域へのアクセスを制御¶

__GFP_HIGH 呼び出し元が高優先度であり、システムが進展する前に要求を満たすことが必要であることを示します。たとえば、ページをクリーンにするためのIOコンテキストの作成。

__GFP_ATOMIC 呼び出し元が回収やスリープができない高優先度であることを示します。ユーザーは通常、割り込みハンドラです。これは __GFP_HIGH

回収修飾子¶

以下のすべてのフラグは、スリープ可能な割当（例： GFP_NOWAIT および GFP_ATOMIC に適用されるものであり、これらは無視されます。

__GFP_IO 物理I/Oを開始できます。

__GFP_FS 低レベルのファイルシステムに下請けできます。フラグをクリアすると、アロケータがファイルシステムに再帰することを防ぎ、すでにロックを保持している可能性のあるファイルシステムの動作を回避できます。

__GFP_DIRECT_RECLAIM 呼び出し元が直接回収を実行できることを示します。このフラグをクリアすることで、代替オプションが利用可能な場合に不要な遅延を回避できます。

__GFP_KSWAPD_RECLAIM 低水準に達したときにkswapdを起動し、高水準に達するまでページを回収するように示します。代替オプションが利用可能で、回収がシステムに影響を与える可能性がある場合、呼び出し元はこのフラグをクリアする必要があります。典型的な例はTHP割当で、代替オプションが安価ですが、回収/コンパクションが間接的な停止を引き起こす可能性があるためです。

__GFP_RECLAIM 直接回収とkswapd回収の許可/禁止を簡潔に表す省略表現です。

デフォルトのアロケータ動作は要求サイズに依存します。コストが高い割当（order > PAGE_ALLOC_COSTLY_ORDER）は、非常に重要で失敗してはならないため、暗黙的に失敗しない（ただし、OOM被害者などの例外を除く）とされます。コストが高い要求は、OOMキラーを呼び出さずに非干渉的になるように努力します。以下の3つの修飾子を使用することで、これらの暗黙的なルールを上書きできます

__GFP_NORETRY: VMの実装は、メモリ圧力の下でメモリを確保するために非常に軽量なメモリ直接回収を試みます（そのため、スリープ可能です）。OOMキラーなどの干渉的な動作は避けます。呼び出し元は、重いメモリ圧力下で発生する可能性のある失敗を処理する必要があります。このフラグは、失敗を低コストで簡単に処理できる場合（例：通過量の減少）に適しています。

__GFP_RETRY_MAYFAILVMの実装は、他の場所で進展があった場合に以前失敗したメモリ回収手続きを再試行します。他のタスクがメモリを解放するための高レベルのアプローチ（フラグメンテーションを削除するコンパクションやページアウト）を試みるのを待つことができます。再試行回数には明確な上限がありますが、それよりも大きな上限となっています。 __GFP_NORETRYこのフラグを指定した割り当ては失敗する可能性がありますが、これは本当に未使用メモリが極めて少なくなっている場合に限られます。これらの割り当ては直接OOMキラーをトリガーしませんが、失敗した場合、システムが直ちにOOMキラーを使用する必要があることを示しています。呼び出し元は失敗を処理しなければなりませんが、より効率の悪い方法で上位リクエストを失敗させるか、完了させるのが現実的です。割り当てが失敗した場合、呼び出し元が非必須メモリを解放できる状態であれば、システム全体にメリットがあります。

__GFP_NOFAILVMの実装は_必須_で無限に再試行しなければなりません：呼び出し元が割り当て失敗を処理することはできません。割り当ては無限にブロックされる可能性がありますが、失敗で戻ることはありません。失敗のテストは無意味です。新規ユーザーは慎重に評価すべきです（そして、合理的な失敗ポリシーがない場合にのみフラグを使用すべきです）。ただし、アロケータ周りの無限ループを自前で実装するよりも、このフラグを使用する方が明らかに優れています。コストのかかる割り当てにこのフラグを使用するのは_強く推奨しません_。

有用なGFPフラグの組み合わせ¶

よく使用されるGFPフラグの組み合わせです。サブシステムはこれらの組み合わせから始め、必要に応じてフラグを設定またはクリアするのを推奨します。 __GFP_FOO flagsを適切に設定してください。

GFP_ATOMIC ユーザーがスリープできない場合で割り当てが成功しなければならない状況です。低いウォーターマークが適用され、「アトミック予備」へのアクセスが可能になります。現在の実装はNMIや少数の厳格な非プリエンプティブコンテキスト（例：raw_spin_lockなど）をサポートしていません。同様に、 GFP_NOWAIT.

GFP_KERNEL これはカーネル内部の割り当てに典型的です。呼び出し元は ZONE_NORMAL または直接アクセス用の低いゾーンを指定し、直接回収を実行できますが、

GFP_KERNEL_ACCOUNT これはGFP_KERNELと同じですが、割り当てがkmemcgにアカウントされます。

GFP_NOWAIT これは直接回収を待機せず、物理IOを開始せず、ファイルシステムコールバックを使用しないでカーネル割り当てに使用されます。

GFP_NOIO クリーンなページや物理IOを開始する必要のないスラブページを直接リカレートして破棄します。このフラグを直接使用するのではなく、memalloc_noio_{save,restore}を使用して、IOを実行できないスコープを記述し、その理由を簡潔に説明してください。すべての割当リクエストはGFP_NOIOを暗黙的に継承します。

GFP_NOFS 直接リカレートを使用しますが、ファイルシステムインターフェースは使用しません。このフラグを直接使用するのではなく、memalloc_nofs_{save,restore}を使用して、FSレイヤーに再帰してはいけないスコープを記述し、その理由を簡潔に説明してください。すべての割当リクエストはGFP_NOFSを暗黙的に継承します。

GFP_USER カーネルやハードウェアが直接アクセス可能なユーザースペースの割当に使用されます。ハードウェアがユーザースペースにマッピングされたバッファ（例：グラフィックス）にDMAを実行する必要がある場合に通常使用されます。これらの割当にはcpusetの制限が適用されます。

GFP_DMA 歴史的な理由により存在しており、可能な限り使用を避けてください。フラグは呼び出し元が最低ゾーンを使用することを示します（ZONE_DMA またはx86-64では16M）。理想的にはこのフラグは削除されるべきですが、一部のユーザーが本当に必要とするため、慎重な検証が必要です。また、低メモリ予備を回避するためにこのフラグを使用しているケースもあります。 ZONE_DMA および最低ゾーンを一種の緊急予備として扱います。

GFP_DMA32 は GFP_DMA と似ていますが、呼び出し元が32ビットアドレスを必要とする点が異なります。

GFP_HIGHUSER ユーザースペースの割当で、ユーザースペースにマッピングされる可能性があるものの、カーネルが直接アクセスする必要はなく、使用後は移動できない場合に使用されます。ハードウェアがユーザースペースにデータを直接マッピングする割当で、アドレス制限がない例が考えられます。

GFP_HIGHUSER_MOVABLE カーネルが直接アクセスする必要はなく、アクセスが必要な場合にkmap()を使用可能なユーザースペースの割当です。ページリカレートやページ移動により移動可能と期待されます。通常、LRUリストに含まれるページはこのフラグで割当されます。 GFP_HIGHUSER_MOVABLE.

GFP_TRANSHUGE および GFP_TRANSHUGE_LIGHT THP（Transparent Huge Pages）の割当に使用されます。これらは複合割当であり、メモリが不足している場合に迅速に失敗し、kswapd/kcompactdを起動しません。_LIGHTバージョンはリカレートやコンパクションを一切行わず、ページフォールトパスでデフォルトで使用され、非ライトバージョンはkhugepagedで使用されます。

通常、この関数はキャッシュや暗号化ビットをmmap()時点では判明していない場合にドライバが使用します。これは、以下の条件を満たす限り問題ありません。 vma->vm_page_protが異なる場合 vma->vm_page_prot コアVMは、これらのvmas（COWページを除く）に対してキャッキングおよび暗号化ビットを設定するためにこのフィールドを使用していません。これは、コアVMがpte_modify()を使用してこれらのページテーブルエントリを変更する際、キャッキングまたは暗号化ビットに触れない関数のみを使用することによって保証されています。（例としてmprotect()を参照してください）。また、新しいページテーブルエントリが作成される場合も、これはfault()コールバックのみを使用して行われ、vma->vm_page_protの値は匿名ページへのポインタを持つページテーブルエントリの作成を除いて使用されません。

コンテキスト

プロセスコンテキスト。必要に応じて GFP_KERNEL.

戻り値

vm_fault_t値を使用して割り当てることができます。

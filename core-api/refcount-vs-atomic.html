はじめに¶

refcount_t API の目的は、オブジェクトの参照カウンタを実装するための最小限の API を提供することです。一般的なアーキテクチャに依存しない実装は lib/refcount.c から提供され、その下ではアトミック操作が使用されていますが、いくつかの関数間にはメモリ順序の保証に関する違いがあります。 refcount_*() および atomic_*() 関数間のメモリ順序の保証に関する違いについて説明し、それらのメモリ順序の保証の変化に対応するコードの検証を手助けするための例を提供しています。

このドキュメントで使用される用語は、tools/memory-model/Documentation/explanation.txt で定義された正式な LKMM に従っています。

memory-barriers.txt および atomic_t.txt は、一般的なメモリ順序およびアトミック操作に特化した背景情報を提供しています。

関連するメモリ順序の種類¶

注意

次のセクションでは、アトミック操作および参照カウンタに関連するこのドキュメントで使用されるメモリ順序の種類のみを説明しています。より幅広い視点を求める場合は、memory-barriers.txt ドキュメントをご参照ください。

メモリ順序の保証が全くない場合（つまり、完全に無秩序な状態）では、アトミック操作と参照カウンタは、同一のCPUでのみアトミック性とプログラム順序（po）の関係を提供します。これにより、各操作がアトミックであり、単一のCPU上で命令がプログラム順序で実行されることを保証します。 atomic_*() および refcount_*() これは READ_ONCE()/WRITE_ONCE() および compare-and-swap プリミティブを使用して実装されます。

強い（完全な）メモリ順序は、同じCPU上のすべての前のロードおよびストア（すべてのpo-earlier命令）が、同じCPU上のどのpo-later命令も実行される前に完了することを保証します。また、同じCPU上のすべてのpo-earlierストアおよび他のCPUから伝播したストアが、元のCPU（A-累積性）上のどのpo-later命令も実行される前にすべての他のCPUに伝播することを保証します。これは smp_mb() を使用して実装されます。

RELEASEメモリ順序は、同じCPU上のすべての以前のロードとストア（すべてのpo-earlier指令）が操作前に完了することを保証します。また、同じCPU上のすべてのpo-earlierストアおよび他のCPUからのすべての伝播ストアが、リリース操作前にすべての他のCPUに伝播することも保証します（A-累積性）。これはsmp_store_release()を使用して実装されます。

ACQUIREメモリ順序は、同じCPU上のすべての後続のロードとストア（すべてのpo-later指令）が取得操作後に完了することを保証します。また、同じCPU上のすべてのpo-laterストアが、取得操作が実行された後にすべての他のCPUに伝播することも保証します。これはsmp_acquire__after_ctrl_dep()を使用して実装されます。

参照カウンタに対する成功時の制御依存性は、オブジェクトの参照が成功裏に取得された場合（参照カウンタのインクリメントまたは追加が行われ、関数がtrueを返した場合）、その後のストアがこの操作に対して順序付けられることを保証します。ストアに対する制御依存性は明示的なバリアを用いず、CPUがストアを推測しないことを依拠としています。これは単一CPU間の関係に限られ、他のCPUに対する保証は提供しません。

関数の比較¶

ケース1) - RMW（読み込み/変更/書き込み）でない操作¶

関数の変更:

  • atomic_set() → refcount_set()

  • atomic_read() → refcount_read()

メモリ順序保証の変更:

  • none（両方完全に無秩序）

ケース2) - 値を返さないインクリメントベースの操作¶

関数の変更:

  • atomic_inc() → refcount_inc()

  • atomic_add() → refcount_add()

メモリ順序保証の変更:

  • none（両方完全に無秩序）

ケース3) - 値を返さないデクリメントベースのRMW操作¶

関数の変更:

  • atomic_dec() → refcount_dec()

メモリ順序保証の変更:

  • 完全に無秩序 → RELEASE順序

ケース4) - 値を返すインクリメントベースのRMW操作¶

関数の変更:

  • atomic_inc_not_zero() → refcount_inc_not_zero()

  • no atomic counterpart → refcount_add_not_zero()

メモリ順序保証の変更:

  • 完全に順序付けられた → 成功時のストアに対する制御依存性

注意

ここでは、オブジェクトへのポインタの取得によって必要な順序が提供されていると本当に仮定しています！

ケース5) - 値を返す一般的なデクリメント/サブデクリメントベースのRMW操作¶

関数の変更:

  • atomic_dec_and_test() → refcount_dec_and_test()

  • atomic_sub_and_test() → refcount_sub_and_test()

メモリ順序保証の変更:

  • 完全に順序付けられた → 成功時のRELEASE順序 + ACQUIRE順序

ケース6) - 値を返すその他のデクリメントベースのRMW操作¶

関数の変更:

  • no atomic counterpart → refcount_dec_if_one()

  • atomic_add_unless(&var, -1, 1) –> refcount_dec_not_one(&var)

メモリ順序保証の変更:

  • 完全に順序付けられた → RELEASE順序 + 制御依存性

注意

atomic_add_unless()は成功時にのみ完全な順序を提供します。

ケース7) - ロックベースのRMW¶

関数の変更:

  • atomic_dec_and_lock() → refcount_dec_and_lock()

  • atomic_dec_and_mutex_lock() –> refcount_dec_and_mutex_lock()

メモリ順序保証の変更:

  • 完全に順序付けられた → RELEASE順序 + 制御依存性 + 成功時のspin_lock()保持

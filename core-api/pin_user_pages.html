概要¶

このドキュメントでは以下の関数について説明します:

pin_user_pages()
pin_user_pages_fast()
pin_user_pages_remote()

FOLL_PIN の基本的な説明¶

FOLL_PIN および FOLL_LONGTERM は get_user_pages*()（"gup"）ファミリの関数に渡せるフラグです。FOLL_PIN は FOLL_LONGTERM と大きな相互作用・依存関係がありますので、ここでは両方を説明します。

FOLL_PIN は gup 内部で使用されるため、gup 呼び出し場所に現れるべきではありません。これにより、関連するWrapper関数（pin_user_pages*() など）がこれらのフラグの正しい組み合わせを設定し、問題を検出できるようになります。

一方で、FOLL_LONGTERM は 通常のRCU読み込み側クリティカルセクションは、条件付きでスリープロックを取得することが許容されます（例として gup 呼び出し場所で設定可能であり、これは get*(), pin*(), FOLL_LONGTERM などすべての組み合わせに対応するための大量のWrapper関数を生成するのを避けるためです。また、pin_user_pages*() API は get_user_pages*() API とは明確に区別されるため、自然な境界線であり、別々のWrapper呼び出しを行うべきです。言い換えれば、DMAピンされたページには pin_user_pages*() を、他のケースには get_user_pages*() を使用します。このドキュメント後半で説明する5つのケースにより、この概念をさらに明確にしています。

FOLL_PIN と FOLL_GET は、特定の gup 呼び出しでは排他的です。ただし、複数のスレッドや呼び出し場所は、FOLL_PIN と FOLL_GET の両方を介して同じ struct pages をピンできます。ただし、呼び出し場所がどちらか一方を選択する必要があります。struct page(s) 自体が選択するわけではありません。

FOLL_PIN の実装は FOLL_GET とほぼ同じですが、FOLL_PIN は異なる参照カウント技術を使用しています。

FOLL_PIN は FOLL_LONGTERM の前提条件です。言い換えれば、FOLL_LONGTERM は FOLL_PIN のより制限的な特定のケースです。

各Wrapperが設定するフラグはどれか¶

これらの pin_user_pages*() 関数では、FOLL_PIN は呼び出し元が提供する gup フラグと OR されます。呼び出し元は null でない struct pages* 配列を渡す必要があります。関数はその後、各ページを GUP_PIN_COUNTING_BIAS の特別な値でインクリメントしてピンします。

非常に大きなページ（実際には、2ページ以上で構成される複合ページも含む）では、GUP_PIN_COUNTING_BIASスキームは使用されません。代わりに、複合ページの3番目のstruct pageを使用することで、正確なピンカウントを実現しています。この目的で、struct pageに新たなフィールドhpage_pinned_refcountが追加されました。

この複合ページのアプローチは、以下の説明で述べるカウント上限の問題を回避します。これらの制限は、巨大ページによってさらに深刻化していたためです。なぜなら、各末尾ページがヘッドページにrefcountを追加するからです。実際のテストでは、別途hpage_pinned_refcountフィールドがない場合、一部の巨大ページのストレステストでページオーバーフローが発生したことが確認されました。

これは、巨大ページと複合ページ（オーダー>1のもの）が以下の誤検出問題に巻き込まれることはないことを意味します。

pin_user_pages          FOLL_PIN is always set internally by this function.
pin_user_pages_fast     FOLL_PIN is always set internally by this function.
pin_user_pages_remote   FOLL_PIN is always set internally by this function.

これらのget_user_pages*()関数では、FOLL_GETが指定されていない場合もあります。動作は上記よりもやや複雑です。FOLL_GETが指定されていた場合、呼び出し元がnullでないstruct pages*配列を渡した場合は、関数が自動的にFOLL_GETを設定し、各ページのrefcountを+1してピンを保持します。 ではありません 一部の重要な設計制約とその解決策は以下の通りです：dma-pinnedページの追跡に関して

DMAピンされたページの追跡¶

一部の重要な設計制約とその解決策は以下の通りです：dma-pinnedページの追跡に関して

  • struct pageごとの実際の参照カウントが必要です。これは、複数のプロセスがページをピンし、アンピンする可能性があるためです。

  • 偽陽性（ページがDMAピンされていると報告するが実際にはそうではない）は許容されるものの、偽陰性は許容されません。

  • struct pageのサイズはこの用途のために拡張できませんし、すべてのフィールドはすでに使用されています。

  • 上記の理由から、page->_refcountフィールドを再利用し、そのフィールドの上位ビットをDMAピンカウントとして使用します。『Sort of』とは、page->_refcountをビットフィールドに分割するのではなく、page->_refcountに中程度から大きく（GUP_PIN_COUNTING_BIAS、初期値は1024: 10ビット）の値を加算することで、曖昧な挙動を実現します。たとえば、ページにget_page()が1024回呼ばれた場合、1つのDMAピンカウントとして表示されます。これは許容範囲内です。

これにより制限も生じます：カウンタが10ビットずつ増分する場合、利用可能なビットは31-10=21ビットのみです。

  • 呼び出し元は『DMAピンのページ追跡』を明示的に要求する必要があります。言い換えれば、単にget_user_pages()を呼び出すだけでは不十分で、pin_user_page()などの新しい関数を用いなければなりません。

FOLL_PIN, FOLL_GET, FOLL_LONGTERM: どのフラグをいつ使用するか¶

Jan Kara氏、Vlastimil Babka氏、および他の-mm関係者氏らの貢献により、これらのカテゴリを記述していただきました：

ケース1: 直接IO (DIO)¶

GUPはDIOバッファとして使用されているページへの参照があります。これらのバッファは比較的短時間だけ必要なので（「長期」ではありません）、page_mkclean()やmunmap()との特別な同期は提供されません。したがって、呼び出し元で設定するフラグは以下の通りです。

FOLL_PIN

…FOLL_PINを直接設定するのではなく、呼び出し元ではpin_user_pages*()のいずれかの関数を使用すべきです。これらの関数はFOLL_PINを設定します。

ケース2: RDMA¶

GUPはDMAバッファとして使用されているページへの参照があります。これらのバッファは長時間必要なので（「長期」）、page_mkclean()やmunmap()との特別な同期は提供されません。したがって、呼び出し元で設定するフラグは以下の通りです。

FOLL_PIN | FOLL_LONGTERM

注意: DAXページなどの一部のページは、長期ピンで固定できません。それはDAXページが別個のページキャッシュを持っていないためで、『ピンニング』とはファイルシステムブロックのロックを意味しますが、この方法でのサポートはまだ（まだ）ありません。

ケース3: MMU通知レジストレーション、ハードウェアによるページフォールトありなし¶

デバイスドライバーはget_user_pages*()を通じてページをピンし、メモリ範囲のmmu notifierコールバックを登録できます。その後、 notifier「無効範囲」コールバックを受信した際には、デバイスがその範囲を使用するのを停止し、ページをアンピンします。他にも、例えば待機中のIOと明示的に同期するなど、同様の結果を達成する他の方法が考えられます。

あるいは、ハードウェアが再現可能なページフォールトをサポートする場合、デバイスドライバーはピンを一切行う必要がありません（これは理想的です）。以下の通り、mmu notifierコールバックを登録するだけで、コールバック内でデバイスを停止しアンピンする代わりに、デバイスのページテーブルから範囲を削除するだけです。

どちらの方法でも、ドライバーがmmu notifierコールバックでページをアンピンする限り、ファイルシステムとmm（page_mkclean()、munmap()など）との適切な同期が保証されます。したがって、どちらのフラグも設定する必要はありません。

ケース4: struct page操作専用のピン¶

構造体pageのデータ（ページが追跡する実際のメモリコンテンツとは異なり）だけが影響を受ける場合、通常のGUP呼び出しで十分で、どちらのフラグも設定する必要はありません。

ケース5: ページ内のデータへの書き込み用のピン¶

DMAやDirect IOに関与していない場合でも、単純な「ピン、ページデータに書き込み、アンピン」のパターンでも問題が発生する可能性があります。ケース5はケース1を含むだけでなく、ケース2も含むほか、このパターンを呼び出すすべてのケースを含むと考えられます。言い換えれば、コードがケース1でもケース2でもない場合でも、このようなパターンに該当する場合はFOLL_PINが必要になることがあります。

正しい（FOLL_PIN呼び出しを使用）:

pin_user_pages() ページ内のデータに書き込み unpin_user_pages()

不正（FOLL_GET呼び出しを使用）:

get_user_pages() ページ内のデータに書き込み put_page()

page_maybe_dma_pinned(): ピンの本質¶

ページを「DMA-pinned」または「gup-pinned」とマークする目的は、『このページはDMA-pinnedですか？』というクエリを実行できるようにすることです。これにより、page_mkclean()などのコード（および一般的なファイルシステムの書き戻しコード）は、ページがピン止めによりアンマップできない場合の適切な処理を判断できるようになります。

このようなケースでの対応策については、数年間にわたる議論と議論の対象となっています（このドキュメント末尾の参照を参照してください）。ここではその詳細を記載する必要がありますが、その解決が完了するまでは未解決のタスクとして残しておきます。その間、この機能が利用可能であることは、

static inline bool page_maybe_dma_pinned(struct page *page)

…長期にわたるgup+DMA問題を解決するための前提条件です。

FOLL_GET, FOLL_PIN, および FOLL_LONGTERM の別の視点¶

これらのフラグを別の視点で考えると、制限の段階として捉えることができます：FOLL_GETは構造体pageの操作に使用され、構造体pageが参照するデータには影響を与えません。FOLL_PINは replacement FOLL_GET 用であり、データがアクセスされるページにおける短期間のピン固定に使用されます。 will したがって、FOLL_PIN は「より厳しい」形式のピン固定です。さらに、FOLL_LONGTERM は FOLL_PIN が前提条件となるより制限的なケースであり、この場合は長期的にピン固定されるページで、そのデータがアクセスされるためのものです。

ユニットテスト¶

このファイル:

tools/testing/selftests/vm/gup_benchmark.c

新しい pin*() ウォーラッパー関数をテストするための新しい呼び出しを含んでいます。

  • PIN_FAST_BENCHMARK (./gup_benchmark -a)

  • PIN_BENCHMARK (./gup_benchmark -b)

システム起動後、取得および解放されたDMAピンされたページの総数を監視するには、2つの新しい/proc/vmstatエントリを介して可能です:

/proc/vmstat/nr_foll_pin_acquired
/proc/vmstat/nr_foll_pin_released

通常の状態では、これらの2つの値は等しくなります。ただし、長期的な[R]DMAピンが存在する場合、またはピン/アンピンの遷移中にあれば、等しくなりません。

  • nr_foll_pin_acquired: システム起動後、取得された論理的なピンの数です。大ページの場合、大ページ内の各ページ（ヘッドページと各テールページ）に対してヘッドページが1回ずつピンされます。これはget_user_pages()が大ページに対して使用する挙動と同様で、get_user_pages()が大ページに対して適用される際、大ページ内の各テールページまたはヘッドページごとにヘッドページの参照カウントが1回ずつ増加します。

  • nr_foll_pin_released: システム起動後、解放された論理的なピンの数です。注意点として、ページはPAGE_SIZEの粒度で解放（アンピン）されるため、元のピンが大ページに適用されていたとしても、この粒度で処理されます。上記の「nr_foll_pin_acquired」で説明したピンカウントの挙動により、会計がバランスを取るため、以下の処理後、以下が期待されます:

    pin_user_pages(huge_page);
for (each page in huge_page)
    unpin_user_page(page);

…以下の結果が予想されます:

nr_foll_pin_released == nr_foll_pin_acquired

(…ただし、長期的なRDMAピンが存在してすでにバランスを欠いていた場合は除きます。)

その他の診断¶

dump_page() は、新しいカウントフィールドを処理するため、および複合ページ全体の報告をより良くするため、わずかな改善が加えられました。具体的には、order > 1 の複合ページでは、正確な (hpage_pinned_refcount) ピンカウントが報告されます。

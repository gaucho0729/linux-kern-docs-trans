this_cpu操作¶

著者

Christoph Lameter, 2014年8月4日

著者

Pranith Kumar, 2014年8月2日

this_cpu操作は、現在実行中のプロセッサに関連するper-CPU変数へのアクセスを最適化する方法です。 現在 実行中のプロセッサ。これはセグメントレジスタ（または特定のプロセッサ用のper-CPU領域の開始位置を永続的に保持する専用レジスタ）を用いて実現されます。

this_cpu操作は、プロセッサ固有のper-CPUベースにper-CPU変数のオフセットを加算し、その操作をper-CPU変数に関する命令にエンコードします。

これにより、オフセット計算とデータ操作の間にアトミック性の問題が生じません。そのため、プリエンプションや割込みを無効化する必要はありません。

読み込み-変更-書き込み（RMW）操作は特に重要です。多くのプロセッサは、通常の同期オーバーヘッドなしで動作するが、緩いアトミック性を保証する特別な低レイテンシ命令を備えています。たとえばx86では、lockプレフィックスを省略したinc/dec/cmpxchgなどのRMW命令を実行できます。

lockプレフィックスを省略したアクセスは同期されませんが、同期は不要です。なぜなら、現在実行中のプロセッサに特有のper-CPUデータにアクセスしているからです。他のプロセッサからのアクセスは発生しないため、競合状態がありません。

リモートプロセッサによるper-CPU領域へのアクセスは例外的な状況であり、ローカルRMW操作のパフォーマンスや正しさ（リモート書き込み操作）に影響を与える可能性があります。

this_cpu操作の主な用途はカウンタ操作の最適化です。

以下のthis_cpu()操作はプリエンプション保護が暗黙的に含まれており、プリエンプションや割込みを気にせず使用できます：

this_cpu_read(pcp)
this_cpu_write(pcp, val)
this_cpu_add(pcp, val)
this_cpu_and(pcp, val)
this_cpu_or(pcp, val)
this_cpu_add_return(pcp, val)
this_cpu_xchg(pcp, nval)
this_cpu_cmpxchg(pcp, oval, nval)
this_cpu_cmpxchg_double(pcp1, pcp2, oval1, oval2, nval1, nval2)
this_cpu_sub(pcp, val)
this_cpu_inc(pcp)
this_cpu_dec(pcp)
this_cpu_sub_return(pcp, val)
this_cpu_inc_return(pcp)
this_cpu_dec_return(pcp)

this_cpu操作の内部仕組み¶

x86ではfs:またはgs:セグメントレジスタがper-CPU領域のベースを保持しています。これにより、セグメントオーバーライドを用いてper-CPU相対アドレスを正しいper-CPU領域に再配置できます。したがって、per-CPUベースへの再配置はセグメントレジスタプレフィックスを用いた命令にエンコードされます。

例:

DEFINE_PER_CPU(int, x);
int z;

z = this_cpu_read(x);

結果として、単一の命令になります：

mov ax, gs:[x]

CPUごとの計算結果を取得するためのアドレス計算とそのアドレスからの取得処理ではなく、per-CPU操作が行われます。この_cpu_opsの前には、プリエンプションの無効化/有効化が必要で、計算が行われる間、カーネルがスレッドを別のプロセッサに移動しないようにする必要があります。

以下のthis_cpu操作を考慮してください：

this_cpu_inc(x)

上記の結果は以下の単一の命令（ロックプレフィックスなし！）になります：

inc gs:[x]

セグメントレジスタが存在しない場合に必要な以下の操作と比較します：

int *y;
int cpu;

cpu = get_cpu();
y = per_cpu_ptr(&x, cpu);
(*y)++;
put_cpu();

これらの操作は特定のプロセッサに割り当てられたper-CPUデータにのみ使用可能です。周囲のコードでプリエンプションを無効にしていない場合、this_cpu_inc()はper-CPUカウンタのうちどれか1つが正しくインクリメントされることを保証しますが、OSがthis_cpu命令の実行前後でプロセスを移動させる可能性があるため、個々のプロセッサのカウンタ値は意味を持たず、すべてのper-CPUカウンタの合計値のみが重要です。

パフォーマンス向上のためper-CPU変数が使用されます。複数のプロセッサが同じコードパスを同時に通過する場合、キャッシュラインのバウンスを回避できます。各プロセッサが独自のper-CPU変数を持つため、同時にキャッシュラインの更新が行われません。この最適化の代償として、カウンタの値が必要なときにper-CPUカウンタを合計する必要があります。

特殊な操作¶

y = this_cpu_ptr(&x)

per-CPU変数（&x !）のオフセットを取得し、現在実行中のプロセッサに属するper-CPU変数のアドレスを返します。this_cpu_ptrはcommon get_cpu/put_cpuシーケンスが要求する複数のステップを回避します。プロセッサ番号は利用できません。代わりに、ローカルなper-CPU領域のオフセットを単純にper-CPUオフセットに加算します。

この操作は通常、プリエンプションが無効化されたコードセグメントで使用されます。その場合、ポインタはクリティカルセクションでローカルなper-CPUデータにアクセスするために使用されます。プリエンプションが再有効になると、このポインタはもはや現在のプロセッサのper-CPUデータを指さなくなるため、通常は使いません。

Per cpu変数とオフセット¶

Per cpu変数は オフセット per cpu領域の開始位置へのオフセットを持ち、コードではアドレスのように見えますが実際にはアドレスではありません。オフセットは直接デリファレンスできません。有効なアドレスを形成するには、プロセッサのper cpu領域のベースポインタにオフセットを加算する必要があります。

したがって、per cpu操作の文脈外でxまたは&xを使用することは無効であり、一般的にNULLポインタデリファレンスと同様に扱われます。

DEFINE_PER_CPU(int, x);

per cpu操作の文脈では、上記はxがper cpu変数であることを意味します。ほとんどのthis_cpu操作はcpu変数を引数とします。

int __percpu *p = &x;

&xおよびpはper cpu変数の オフセット オフセットです。this_cpu_ptr()はper cpu変数のオフセットを取るため、この表現は少し不自然に見えます。

per cpu構造体のフィールドに対する操作¶

例えば、以下のようなpercpu構造体があります:

struct s {
        int n,m;
};

DEFINE_PER_CPU(struct s, p);

これらのフィールドに対する操作はシンプルです:

this_cpu_inc(p.m)

z = this_cpu_cmpxchg(p.m, 0, 1);

struct sへのオフセットがある場合:

struct s __percpu *ps = &p;

this_cpu_dec(ps->m);

z = this_cpu_inc_return(ps->n);

ポインタの計算にはthis_cpu_ptr()の使用が必要かもしれません。後述のthis_cpu操作を用いない場合、特にフィールドを操作する際には:

struct s *pp;

pp = this_cpu_ptr(&p);

pp->m--;

z = pp->n++;

this_cpu操作の変種¶

this_cpu操作は割込み安全ですが、一部のアーキテクチャではこれらのper cpuローカル操作をサポートしていません。その場合、割込みを無効にしてアトミックな操作を実行し、その後割込みを再有効にするコードで置き換える必要があります。これはコストが高いため、スケジューラが実行中のプロセッサを変更できない理由がある場合以外では割込みを無効にする必要はありません。その目的のために以下の__this_cpu操作が提供されています。

これらの操作は割込みやプリエンプションに対する排他性を保証しません。per cpu変数が割込みコンテキストで使用されず、スケジューラがプリエンプションできない場合、これらは安全です。操作中に割込みが発生し、その割込みが変数を変更する場合、RMW（読み取り-変更-書き込み）操作の安全性が保証されません:

__this_cpu_read(pcp)
__this_cpu_write(pcp, val)
__this_cpu_add(pcp, val)
__this_cpu_and(pcp, val)
__this_cpu_or(pcp, val)
__this_cpu_add_return(pcp, val)
__this_cpu_xchg(pcp, nval)
__this_cpu_cmpxchg(pcp, oval, nval)
__this_cpu_cmpxchg_double(pcp1, pcp2, oval1, oval2, nval1, nval2)
__this_cpu_sub(pcp, val)
__this_cpu_inc(pcp)
__this_cpu_dec(pcp)
__this_cpu_sub_return(pcp, val)
__this_cpu_inc_return(pcp)
__this_cpu_dec_return(pcp)

xをインクリメントし、アドレス再配置と同一指令内でのRead-Modify-Write操作を通じたアトミック性が達成できないプラットフォームでは割込みを無効にするコードへのフォールバックを行いません。

&this_cpu_ptr(pp)->n vs this_cpu_ptr(&pp->n)¶

最初の操作はオフセットを取得してアドレスを形成し、その後nフィールドのオフセットを加算します。これによりコンパイラが2つのアディション命令を生成する可能性があります。

二つ目の操作はまず2つのオフセットを加算し、その後再配置を行います。私の意見では、二つ目の形式の方が見やすく、()の扱いも簡単です。また、この形式はthis_cpu_read()などの使用方法と整合性があります。

per cpuデータのリモートアクセス¶

per cpuデータ構造体は1つのCPU専用に設計されており、変数を意図通りに使用する場合、this_cpu_ops()は「アトミック」であると保証されます。他のCPUがこれらのデータ構造にアクセスできないためです。

パーコアデータ構造にリモートでアクセスする必要がある特別なケースがあります。通常、リモート読み取りは安全であり、カウンタの集計などに頻繁に使用されます。一方、リモート書き込みは問題になる可能性があり、this_cpu操作はロックセマンティクスを持っていません。リモート書き込みはthis_cpu RMW操作と干渉する可能性があります。

パーコアデータ構造へのリモート書き込みは、絶対に必要がない限り強く推奨されません。代替として、IPI（Inter-Processor Interrupt）でリモートCPUを起こし、そのパーコア領域の更新を行うことを検討してください。

パーコアデータ構造にリモートでアクセスする際には、通常per_cpu_ptr()関数が使用されます：

DEFINE_PER_CPU(struct data, datap);

struct data *p = per_cpu_ptr(&datap, cpu);

これは、パーコア領域にリモートでアクセスしようとしていることを明示しています。

以下の方法でも、データオフセットをアドレスに変換できます：

struct data *p = this_cpu_ptr(&datap);

ただし、this_cpu_ptrで計算されたポインタを他のCPUに渡すのは異常で、避けるべきです。

リモートアクセスは通常、他のCPUのパーコアデータの状態を読み取るためのものであり、書き込みは緩い同期要件により一意の問題を引き起こす可能性があります。

書き込み操作に関する懸念を示す例として、以下のシナリオがあります。これは、2つのパーコア変数がキャッシュラインを共有しているにもかかわらず、緩い同期がキャッシュラインを更新するプロセスにのみ適用されるためです。

以下の例を考慮してください：

struct test {
        atomic_t a;
        int b;
};

DEFINE_PER_CPU(struct test, onecacheline);

フィールド'a'が1つのプロセッサからリモートで更新され、ローカルプロセッサがthis_cpu操作でフィールド'b'を更新する場合の動作に懸念があります。同じキャッシュライン内のデータへの同時アクセスを避ける必要があります。また、コストのかかる同期が求められる場合もあります。このようなシナリオでは、リモートプロセッサのパーコア領域へのリモート書き込みではなく、IPIの使用が一般的に推奨されます。

リモート書き込みがまれな場合でも、リモート書き込みにより、最もアクセスする可能性のあるプロセッサのキャッシュラインが追い出される可能性があります。プロセッサが起動してローカルキャッシュラインが見つからないと、パフォーマンスに影響を与え、起動時間も遅くなる可能性があります。

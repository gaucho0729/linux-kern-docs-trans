Cache and TLB Flushing Under Linux¶

著者

David S. Miller <davem@redhat.com>

このドキュメントでは、Linux VMサブシステムが呼び出すキャッシュ/TLBフラッシュインターフェースについて説明します。各インターフェースの目的と、インターフェースが呼び出された後の副作用について記載しています。

以下で説明する副作用はシングルプロセッサ実装向けに記述されており、その単一プロセッサでの動作を示しています。SMP（対称マルチプロセッサ）のケースは、この副作用がシステム内のすべてのプロセッサで発生するように定義を拡張するだけであり、SMPのキャッシュ/TLBフラッシュが効率が悪いとは思わないでください。多くの最適化が可能であることがこの分野の特徴です。例えば、あるCPUでユーザーアドレス空間が実行されたことがないことが証明できる場合（mm_cpumask()を参照）、そのCPUではそのアドレス空間に対するフラッシュは行いません。

まずTLBフラッシュインターフェースについて説明します。これらは最もシンプルなインターフェースです。LinuxではTLBは、CPUがソフトウェアのページテーブルから取得した仮想アドレス→物理アドレスの翻訳をキャッシュする機構として抽象化されています。つまり、ソフトウェアのページテーブルが変更されると、このTLBキャッシュに古くなった翻訳が存在する可能性があります。そのため、ソフトウェアのページテーブルが変更された後、カーネルは以下のいずれかのフラッシュメソッドを呼び出します。

  1. void flush_tlb_all(void)

    最も深刻なフラッシュです。このインターフェースが実行されると、これまでのすべてのページテーブルの変更がCPUに反映されます。

    このインターフェースは、カーネルのページテーブルが変更された場合に通常呼び出されます。このような翻訳は「グローバル」な性質を持っています。

  2. void flush_tlb_mm(struct mm_struct *mm)

    このインターフェースは、ユーザーのアドレス空間全体をTLBからフラッシュします。実行後、アドレス空間「mm」のすべての以前のページテーブルの変更がCPUに反映される必要があります。つまり、実行後は「mm」に関するTLBにエントリが存在しなくなります。

    このインターフェースは、forkやexecなどのユーザーアドレス空間全体を扱うページテーブル操作を処理するために使用されます。

  3. void flush_tlb_range(struct vm_area_struct *vma, unsigned long start, unsigned long end)

    ここでは、特定の範囲の（ユーザー）仮想アドレスの翻訳をTLBからフラッシュします。実行後、アドレス空間「vma->vm_mm」の範囲「start」から「end-1」までのすべての以前のページテーブルの変更がCPUに反映される必要があります。つまり、実行後は「start」から「end-1」までの仮想アドレスに関する「mm」のTLBエントリは存在しなくなります。

    「vma」は、領域に使用されているバックストアです。主にmunmap()型の操作で使用されます。

    このインターフェースは、ポートが複数のページサイズの翻訳をTLBから効率的に削除する方法を見つけることを目的としています。これにより、各エントリに対してカーネルがflush_tlb_pageを呼び出すのではなく、より効率的な処理が可能になります（以下参照）。

  4. void flush_tlb_page(struct vm_area_struct *vma, unsigned long addr)

    今回は、PAGE_SIZEサイズの翻訳をTLBから削除する必要があります。「vma」はLinuxがプロセスのmmap’d領域を追跡するために使用するバックイング構造です。アドレス空間はvma->vm_mmを通じて取得可能です。また、(vma->vm_flags & VM_EXEC)をテストすることで、この領域が実行可能かどうか（したがって、split-tlb型の設定では「インストラクションTLB」に含まれる可能性があるかどうか）を確認できます。

    実行後、このインターフェースは、ユーザー仮想アドレス「addr」に対するアドレス空間「vma->vm_mm」の前のページテーブルの変更がCPUに見えるようにする必要があります。つまり、実行後、アドレス「addr」に対する「vma->vm_mm」のTLBにはエントリが存在しなくなります。

    主にフォールト処理中に使用されます。

  5. void update_mmu_cache(struct vm_area_struct *vma, unsigned long address, pte_t *ptep)

    ページフォールトの終わりに、このルーチンが呼び出され、アーキテクチャ固有のコードに、アドレス空間「vma->vm_mm」の仮想アドレス「address」に翻訳が存在することを通知します。これはソフトウェアページテーブル内で行われます。

    ポートはこの情報を利用して任意の方法を採用できます。例えば、ソフトウェア管理TLB構成のTLB翻訳を事前にロードするなど、このイベントを活用できます。sparc64ポートは現在このようにしています。

次に、キャッシュフラッシュインターフェースがあります。一般的に、Linuxが既存の仮想→物理マッピングを新しい値に変更する際、以下のいずれかの形式でシーケンスが行われます。

1) flush_cache_mm(mm);
   change_all_page_tables_of(mm);
   flush_tlb_mm(mm);

2) flush_cache_range(vma, start, end);
   change_range_of_page_tables(mm, start, end);
   flush_tlb_range(vma, start, end);

3) flush_cache_page(vma, addr, pfn);
   set_pte(pte_pointer, new_pte_val);
   flush_tlb_page(vma, addr);

キャッシュレベルのフラッシュは常に最初に行われます。これは、キャッシュが厳格で、仮想アドレスがキャッシュからフラッシュされる際、その仮想アドレスに仮想→物理の翻訳が存在している必要があるシステムを適切に処理するためです。HyperSparc CPUはこのような属性を持つCPUの例です。

以下のキャッシュフラッシュルーチンは、特定のCPUにとって必要な範囲でキャッシュフラッシュを処理するだけでよいです。主に、仮想インデックスを持つキャッシュがあり、仮想→物理の翻訳が変更または削除されるときにフラッシュが必要なCPUに対してこれらのルーチンを実装する必要があります。例えば、IA3,2プロセッサの物理インデックス・物理タグキャッシュは、キャッシュが完全に同期しており、翻訳情報に依存しないため、これらのインターフェースを実装する必要がありません。

以下にルーチンを一つずつ紹介します:

  1. void flush_cache_mm(struct mm_struct *mm)

    このインターフェースは、ユーザーのアドレス空間全体をキャッシュからフラッシュします。つまり、実行後、'mm' に関連するキャッシュラインは存在しなくなります。

    このインターフェースは、プロセスの mmap’d レギオンを追跡するための Linux の内部構造として使用される 'vma' が含まれるページテーブル操作を処理するために使用されます。

  2. void flush_cache_dup_mm(struct mm_struct *mm)

    このインターフェースは、ユーザーのアドレス空間全体をキャッシュからフラッシュします。つまり、実行後、'mm' に関連するキャッシュラインは存在しなくなります。

    このインターフェースは、fork 時に発生するページテーブル操作を処理するために使用されます。

    このオプションは flush_cache_mm とは別に用意されており、VIPT キャッシュに対する一部の最適化を可能にします。

  3. void flush_cache_range(struct vm_area_struct *vma, unsigned long start, unsigned long end)

    ここでは、特定の範囲の (ユーザー) 虚擬アドレスをキャッシュからフラッシュしています。実行後、'vma->vm_mm' に関連する 'start' から 'end-1' までの仮想アドレスのキャッシュエントリは存在しなくなります。

    「vma」は、領域に使用されているバックストアです。主にmunmap()型の操作で使用されます。

    このインターフェースは、複数のページサイズの領域をキャッシュから効率的に削除する方法をポートが見つけることを願って提供されています。これにより、各エントリを修正するたびにカーネルが flush_cache_page を呼び出す必要がなくなるためです（以下参照）。

  4. void flush_cache_page(struct vm_area_struct *vma, unsigned long addr, unsigned long pfn)

    今回は PAGE_SIZE サイズの範囲をキャッシュから削除する必要があります。'vma' は Linux がプロセスの mmap’d レギオンを追跡するために使用するバックイング構造であり、アドレス空間は vma->vm_mm から取得可能です。また、'vma->vm_flags & VM_EXEC' をテストすることで、この領域が実行可能かどうか（つまり「ハーバード」型キャッシュレイアウトでの「インストラクションキャッシュ」に含まれる可能性があるかどうか）を確認できます。

    'pfn' は 'addr' にマッピングされる物理ページフレーム（この値を PAGE_SHIFT だけ左シフトすることで物理アドレスを得られます）を示します。このマッピングがキャッシュから削除されるべきです。

    実行後、'vma->vm_mm' に関連する仮想アドレス 'addr'（これは 'pfn' にマッピングされます）のキャッシュエントリは存在しなくなります。

    主にフォールト処理中に使用されます。

  5. void flush_cache_kmaps(void)

    このルーチンは、プラットフォームが highmem を利用する場合にのみ実装する必要があります。これはすべての kmaps が無効化される直前に呼び出されます。

    実行後、カーネル仮想アドレス範囲 PKMAP_ADDR(0) から PKMAP_ADDR(LAST_PKMAP) のキャッシュエントリは存在しなくなります。

    このルーチンは asm/highmem.h で実装する必要があります。

  6. void flush_cache_vmap(unsigned long start, unsigned long end) void flush_cache_vunmap(unsigned long start, unsigned long end)

    ここではこの2つのインターフェースを通じて、特定の範囲の (カーネル) 虚擬アドレスをキャッシュからフラッシュしています。実行後、カーネルアドレス空間の 'start' から 'end-1' までの仮想アドレスのキャッシュエントリは存在しなくなります。

    これらの2つのルーチンのうち、最初のものは map_kernel_range() がページテーブルエントリをインストールした後に呼び出されます。2番目のものは unmap_kernel_range() がページテーブルエントリを削除する直前に呼び出されます。

現在、CPUキャッシュに関する別のクラスの問題があり、これらを適切に処理するにはまったく異なるインターフェースセットが必要です。最も大きな問題は、プロセッサのデータキャッシュにおける仮想アリアシング（仮想アドレスによる同一物理アドレスの複数キャッシュラインの存在）です。

あなたのポートがDキャッシュにおける仮想アリアシングに影響を受けている可能性がありますか？Dキャッシュが仮想インデックスで構成され、サイズがPAGE_SIZEより大きく、かつ同一物理アドレスに対応する複数のキャッシュラインが同時に存在することを防いでいない場合、この問題が発生します。

Dキャッシュにこの問題がある場合、まずasm/shmparam.hのSHMLBAを適切に定義してください。これは基本的にあなたの仮想アドレス空間で使用されるDキャッシュのサイズ（サイズが可変の場合には最大可能サイズ）に設定すべきです。この設定により、SYSv IPCレイヤーはユーザープロセスが共有メモリをマップする際、この値の倍数のアドレスのみを許可します。

注意

この方法は共有mmapを解決しません。解決方法の一つとしてsparc64ポートを参照してください（特にSPARC_FLAG_MMAPSHARED）。

次に、他のすべてのケースにおけるDキャッシュアリアシングの問題を解決する必要があります。注意すべきは、あるページがユーザーのアドレス空間にマップされている場合、常にそのページをカーネルが線形マッピング（PAGE_OFFSETから開始）でマップしているという事実です。したがって、ユーザーが最初に物理ページをアドレス空間にマップした瞬間、カーネルがそのページをすでに仮想アドレスでマップしているため、Dキャッシュアリアシングの問題が発生する可能性があります。

void copy_user_page(void *to, void *from, unsigned long addr, struct page *page) void clear_user_page(void *to, unsigned long addr, struct page *page)

これらのルーチンはユーザーの匿名またはCOWページにデータを保存します。これにより、ユーザー空間とカーネル間でのDキャッシュアリアシングの問題を効率的に回避できます。

たとえば、ポートはコピー中に「from」と「to」を一時的にカーネル仮想アドレスにマップする場合があります。これらの2つのページの仮想アドレスは、カーネルのロード/ストア命令がユーザーのページマッピングと同じ「色」の仮想アドレスを処理するように選択されます。SPARC64はこの技術を採用しています。

'addr'パラメータは、ユーザーが最終的にこのページをマップする仮想アドレスを指定し、'page'パラメータはターゲットのstruct pageへのポインタを提供します。

Dキャッシュアリアシングが問題でない場合、これらのルーチンはmemcpy/memsetを直接呼び出すだけで、他の処理は行いません。

void flush_dcache_page(struct page *page)

カーネルがページキャッシュページに書き込むとき、またはカーネルがページキャッシュページから読み込む準備をしているとき、かつユーザー空間での共有/読み取り可能マッピングが存在する場合、このルーチンが呼び出されます。

注意

このルーチンは、ユーザープロセスのアドレス空間にマッピングされる可能性のあるページキャッシュページに対してのみ呼び出さなければならない。たとえば、ページキャッシュ内でvfsシンボリックリンクを処理するVFSレイヤーのコードは、このインターフェースを一切呼び出さなくてもよい。

「カーネルがページキャッシュページに書き込む」という表現は、具体的には、カーネルがそのページのpage->virtualマッピングに対してストア命令を実行し、そのページにデータを汚染することを指す。ここでフラッシュを行うのは、Dキャッシュのアリアスングを処理するためであり、これらのカーネルのストアがそのページのユーザー空間マッピングに見えるようにするためである。

この逆のケースも同様に重要である。このファイルに共有可能で書き込み可能なマッピングを持つユーザーがいる場合、カーネルがこれらのページを読み込む際には、ユーザーが行った最新のストアを必ず見なければならない。

Dキャッシュのアリアスングが問題にならない場合、このルーチンはそのアーキテクチャでnop（何もしない）として定義することができる。

page->flags（PG_arch_1）には「アーキテクチャ固有」というビットが割り当てられている。カーネルは、ページキャッシュページが最初にページキャッシュに入るときにこのビットを必ずクリアする保証をする。

これにより、これらのインターフェースをはるかに効率よく実装できる。現在このページをマッピングしているユーザープロセスがなければ、実際のフラッシュを「遅延」（おそらく無限に）することが可能である。sparc64のflush_dcache_pageとupdate_mmu_cacheの実装例を参照されたい。

アイデアは、最初にflush_dcache_page()のタイミングで、page->mapping->i_mmapが空の木であれば、アーキテクチャ固有のページフラグビットを設定する。後でupdate_mmu_cache()でこのフラグビットを確認し、設定されている場合はフラッシュを実行してフラグビットをクリアする。

重要です。

フラッシュを遅延する場合、実際のフラッシュがページを汚染したCPUと同じCPUで行われることが重要である。再び、sparc64の例を参照されたい。

void copy_to_user_page(struct vm_area_struct *vma, struct page *page, unsigned long user_vaddr, void *dst, void *src, int len) void copy_from_user_page(struct vm_area_struct *vma, struct page *page, unsigned long user_vaddr, void *dst, void *src, int len)

カーネルがptrace()などの用途で、任意のユーザーページと任意のデータをやり取りする必要がある場合、この2つのルーチンを使用する。

必要なキャッシュフラッシュやその他のコヒーレンス操作はここに実行すべきである。プロセッサのインストラクションキャッシュがCPUストアをスヌープしない場合、copy_to_user_page()でインストラクションキャッシュをフラッシュする必要がある可能性が高い。

void flush_anon_page(struct vm_area_struct *vma, struct page *page, unsigned long vmaddr)

カーネルが匿名ページの内容にアクセスする必要がある場合、この関数（現在はget_user_pages()のみ）を呼び出します。注意：flush_dcache_page()は匿名ページに対して意図的に動作しません。デフォルトの実装は nop（すべてのコヒーレントアーキテクチャでこのまま維持すべきです）。非コヒーレントアーキテクチャでは、vmaddrのページキャッシュをフラッシュする必要があります。

void flush_kernel_dcache_page(struct page *page)

カーネルがkmapで取得したユーザーページを変更する必要がある場合、すべての変更が完了した後（kunmappingする前に）この関数を呼び出して、下位のページを最新状態に更新します。ここではユーザーが非コヒーレントなキャッシュコピーを持っていない（つまり、元のページはget_user_pages()などのメカニズムから取得されている）と仮定しています。デフォルトの実装は nop であり、すべてのコヒーレントアーキテクチャでこのまま維持すべきです。非コヒーレントアーキテクチャでは、page_address(page)を使用してページのカーネルキャッシュをフラッシュする必要があります。

void flush_icache_range(unsigned long start, unsigned long end)

カーネルが実行するコードからアクセスするアドレスにデータを保存する場合（例：モジュールをロードする際）、この関数が呼び出されます。

ICacheがストアをスヌープしない場合、このルーチンはICacheをフラッシュする必要があります。

void flush_icache_page(struct vm_area_struct *vma, struct page *page)

flush_icache_pageのすべての機能はflush_dcache_pageとupdate_mmu_cacheで実装可能です。今後はこのインターフェースを完全に削除する予定です。

最後のAPIカテゴリは、カーネル内部の意図的にアリアス化されたアドレス範囲へのI/O用です。このようなアリアスはvmap/vmalloc APIを使用して設定されます。カーネルのI/Oは物理ページを通じて行われるため、I/Oサブシステムはユーザーマッピングとカーネルオフセットマッピングが唯一のアリアスであると仮定しています。これはvmapアリアスには当てはまらないため、カーネル内でvmap領域へのI/Oを行う場合は、手動でコヒーレンシーを管理する必要があります。I/Oを行う前にvmap範囲をフラッシュし、I/Oが完了後にそれを無効化する必要があります。

void flush_kernel_vmap_range(void *vaddr, int size)

vmap領域内の指定された仮想アドレス範囲のカーネルキャッシュをフラッシュします。これにより、カーネルがvmap範囲で変更したデータが物理ページに反映されるようにします。この領域がI/O操作に安全であるように設計されています。注意：このAPIは ではありません 該当範囲のオフセットマップアリアスもフラッシュします。

void invalidate_kernel_vmap_range(void *vaddr, int size) invalidates

vmap領域内の指定された仮想アドレス範囲のキャッシュをフラッシュし、I/Oが物理ページに行われている間、プロセッサがキャッシュを古くしてデータをスペクテイティブに読み取らないようにします。これはvmap領域へのデータ読み取りにのみ必要です。

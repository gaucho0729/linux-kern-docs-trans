kobjects、ksets、ktypesについてのすべての知識¶

著者

Greg Kroah-Hartman <gregkh@linuxfoundation.org>

最終更新日

2007年12月19日

2003年10月1日にlwn.netで書かれたJon Corbetによる元記事に基づいています https://lwn.net/Articles/51437/

ドライバーモデルおよびそれに基づくkobjectの抽象化を理解する難しさの一つは、明確な出発点が見つからないことです。

  • kobjectはstruct kobject型のオブジェクトです。kobjectには名前と参照カウントがあり、親ポインタ（オブジェクトを階層構造に配置できるようにする）や特定の型、そして通常はsysfs仮想ファイルシステムでの表現があります。

    一般的には、kobject自体は興味深いものではありません。代わりに、コードが実際に興味を持つ情報が含まれる他の構造体に埋め込まれています。

    構造体は 決して 1つの構造体に複数のkobjectを埋め込むことはできません。そうすると、参照カウントが誤って計算され、コードが不具合を引き起こします。したがって、このようなことは行わないでください。

  • ktypeはkobjectを埋め込むオブジェクトの型です。すべてのkobjectを埋め込む構造体には対応するktypeが必要です。ktypeはkobjectが作成または破壊される際の動作を制御します。

  • ksetはkobjectのグループです。これらのkobjectは同じktypeを持つか、異なるktypeに属するかのいずれかです。ksetはkobjectのコレクションを含む基本的なコンテナ型です。ksetは自身のkobjectを含みますが、その実装詳細はksetコアコードが自動的に処理するため、気にする必要はありません。

    sysfsディレクトリ内に他のディレクトリがいっぱいの場合、通常、それぞれのディレクトリは同じkset内のkobjectに対応しています。

これらの型の作成と操作方法を確認します。下から上へと進むアプローチを取るため、再度kobjectに戻ります。

kobjectの埋め込み¶

カーネルコードがスタンドアロンのkobjectを作成するケースはめったにありません。ただし、以下の説明で示すように1つの主要な例外を除けばです。代わりに、kobjectsはより大きな、ドメイン固有のオブジェクトへのアクセスを制御するために使用されます。このため、kobjectsは他の構造体に埋め込まれて見つかります。オブジェクト指向の考え方になれている場合、kobjectsは他のクラスが派生するトップレベルの抽象クラスとして見なせます。kobjectは、他のオブジェクトにとって便利な機能を実装していますが、単体ではそれほど有用ではありません。C言語は継承の直接的な表現を許しませんので、構造体の埋め込みなどの他の技術を用います。

(余談ですが、カーネルのリンクリスト実装に詳しい読者には、この「list_head」構造体がほぼ常に大きなオブジェクトに埋め込まれるため、自身ではあまり役立ちませんという点に類似しています。)

例えば、UIOコードの drivers/uio/uio.c には、uioデバイスに関連するメモリ領域を定義する構造体があります:

struct uio_map {
        struct kobject kobj;
        struct uio_mem *mem;
};

struct uio_map構造体を持たせた場合、その埋め込まれたkobjectはkobjメンバを使用するだけで見つかります。ただし、kobjectsを扱うコードではしばしば逆の問題に直面します：struct kobjectポインタが与えられた場合、それを含む構造体へのポインタはどのように取得するのでしょうか？特定のトリック（例えば、kobjectが構造体の先頭に位置していると仮定するなど）を避けて、代わりに container_of() マクロを使用する必要があります。このマクロは <linux/kernel.h>:

container_of(ptr, type, member)

where:

  • ptr に存在します。ここで、

  • type は埋め込まれたkobjectへのポインタ、

  • member は含む構造体の型、そして pointer は

が指す構造体フィールドの名前です。 container_of() の戻り値は、対応するコンテナ型へのポインタです。例えば、 kp というstruct kobjectが の struct uio_map内に埋め込まれている場合、それを コンテナ のuio_map構造体へのポインタに変換するには以下のようになります:

struct uio_map *u_map = container_of(kp, struct uio_map, kobj);

便利さのためにプログラマは、 逆キャスト kobjectポインタを含む型へのポインタに変換するためのシンプルなマクロを定義することがよくあります。これは以前の drivers/uio/uio.cでまさに起こっています。ここに示すとおりです:

struct uio_map {
        struct kobject kobj;
        struct uio_mem *mem;
};

#define to_map(map) container_of(map, struct uio_map, kobj)

ここでマクロ引数「map」は対象のstruct kobjectへのポインタです。このマクロはその後、以下のようになります:

struct uio_map *map = to_map(kobj);

kobjectsの初期化¶

kobjectを作成するコードは、当然ながらそのオブジェクトを初期化する必要があります。一部の内部フィールドは必須の呼び出し kobject_init():

void kobject_init(struct kobject *kobj, struct kobj_type *ktype);

で設定されます。kobjectが正しく作成されるには、ktypeが必須です。なぜなら、すべてのkobjectは関連するkobj_typeを持つ必要がありますからです。その後、 kobject_init()を呼び出してsysfsにkobjectを登録する際、関数 kobject_add() を呼び出す必要があります:

int kobject_add(struct kobject *kobj, struct kobject *parent,
                const char *fmt, ...);

kobjectの親となる親オブジェクトとkobjectの名前を正しく設定します。kobjectが特定のksetと関連付けられる場合、kobj->ksetに割り当てることを呼び出し前に必須です kobject_add().ksetがkobjectに関連付けられている場合、呼び出し時にkobjectの親をNULLに設定できます kobject_add() その結果、kobjectの親はkset自身になります

kobjectの名前はカーネルに追加されるときに設定されるため、直接操作すべきではありません。kobjectの名前を変更する必要がある場合は、関数 kobject_rename():

int kobject_rename(struct kobject *kobj, const char *new_name);

kobject_rename() を呼び出す必要があります。この関数はロック処理を行わず、有効な名前の概念も明確でないため、呼び出し側で独自の整合性チェックとシリアル化を提供する必要があります

関数 kobject_set_name() がありますが、これはレガシーな不要なコードで、削除されています。コードでこの関数を呼び出している場合、不正であり修正が必要です

kobjectの名前を正しくアクセスするには、関数kobject_name()を使用してください：

const char *kobject_name(const struct kobject * kobj);

kobjectをカーネルに同時に初期化して追加するための補助関数があります。驚くほど適切な名前で kobject_init_and_add():

int kobject_init_and_add(struct kobject *kobj, struct kobj_type *ktype,
                         struct kobject *parent, const char *fmt, ...);

です。引数は上記の個別 kobject_init() および kobject_add() 関数と同様です

Uevents¶

kobjectがカーネルのkobjectコアに登録された後、世界にその存在を発表する必要があります。これはkobject_uevent()の呼び出しで行えます：

int kobject_uevent(struct kobject *kobj, enum kobject_action action);

を KOBJ_ADD アクションを使用してください。kobjectがカーネルに最初に追加される際にはこのアクションを実行する必要があります。この呼び出しが行われると、ユーザー空間が即座にその属性や子オブジェクトを検索し始めるため、この呼び出しは属性や子オブジェクトが正しく初期化されるのを待ってから行う必要があります

kobjectがカーネルから削除される際（詳細は以下のセクションに記載）、kobjectコアが自動的に KOBJ_REMOVE のueventを作成するため、呼び出し側は手動で行う必要がありません

参照カウント¶

kobjectの主な機能の1つは、埋め込まれたオブジェクトの参照カウントを管理することです。オブジェクトへの参照が存在する限り、オブジェクト（およびそのサポートコード）は存在し続けなければなりません。kobjectの参照カウントを操作する低レベル関数は以下の通りです：

struct kobject *kobject_get(struct kobject *kobj);
void kobject_put(struct kobject *kobj);

成功した呼び出しで、 kobject_get() はkobjectの参照カウントをインクリメントし、kobjectへのポインタを返します

参照が解放される際、 kobject_put() は参照カウントをデクリメントし、必要に応じてオブジェクトを解放します。注意として、 kobject_init() は参照カウントを1に設定するため、kobjectを設定するコードでは kobject_put() を最終的に呼び出してその参照を解放する必要があります

kobjectsは動的であるため、静的に宣言したりスタック上に宣言したりせず、常に動的に割り当ててください。今後のカーネルバージョンでは、静的に作成されたkobjectsに対してランタイムチェックを行い、この不適切な使用法を開発者に警告する予定です。

kobjectを構造体の参照カウンタとして使用するだけであれば、struct krefを使用してください。kobjectは過剰です。struct krefの使用方法については、以下のファイルを参照してください カーネルオブジェクトに参照カウンタ（krefs）を追加する Linuxカーネルソースツリー内の

「シンプルな」kobjectsの作成¶

開発者が望むのは、sysfs階層に単純なディレクトリを作成する方法であり、ksetsやshow/store関数、その他の詳細を扱う必要がない場合があります。これは単一のkobjectを作成すべき唯一の例外です。このようなエントリを作成するには、次の関数を使用してください：

struct kobject *kobject_create_and_add(const char *name, struct kobject *parent);

この関数はkobjectを作成し、指定された親kobjectの下にsysfsに配置します。このkobjectに関連するシンプルな属性を作成するには、次の関数を使用してください：

int sysfs_create_file(struct kobject *kobj, const struct attribute *attr);

または:

int sysfs_create_group(struct kobject *kobj, const struct attribute_group *grp);

ここでの両方の属性タイプは、 kobject_create_and_add()で作成されたkobjectと組み合わせてkobj_attribute型を使用できるため、特別なカスタム属性を作成する必要はありません。

例モジュール samples/kobject/kobject-example.c を参照してください。これはシンプルなkobjectと属性の実装例です。

ktypesとreleaseメソッド¶

これまでの議論にまだ欠けていた重要な点は、kobjectの参照カウンタがゼロになるときの処理です。kobjectを作成したコードは、そのタイミングを通常は把握していません。もし把握できたなら、kobjectの使用意義はほぼありません。また、sysfsがカーネルの他の部分と統合されると、システムに登録されたすべてのkobjectに参照が取得できるため、予測可能なオブジェクトライフサイクルも複雑になります。

結果として、kobjectで保護された構造体は、参照カウンタがゼロになるまで解放できません。参照カウンタはkobjectを作成したコードの直接的な制御下にありません。そのため、そのコードは、自身のkobjectの最後の参照が失われるたびに非同期で通知される必要があります。

kobjectを kobject_add()で登録した後、直接 kfree() を使用して解放してはいけません。安全な方法は kobject_put()を使用することです。常に kobject_put() RCU保護データ構造からデータ要素を削除した後、 kobject_init() を使用することが、エラーの発生を防ぐための良い実践です。

この通知はkobjectのrelease()メソッドを通じて行われます。通常、このようなメソッドは次の形式になります：

void my_object_release(struct kobject *kobj)
{
        struct my_object *mine = container_of(kobj, struct my_object, kobj);

        /* Perform any additional cleanup on this object, then... */
        kfree(mine);
}

重要な点を強調すると、すべてのkobjectはrelease()メソッドを必ず持つ必要があります。また、kobjectはそのメソッドが呼ばれるまで（一貫した状態で）存在しなければなりません。これらの制約が満たされない場合、コードにバグがあります。注意点として、release()メソッドを提供しなかった場合、カーネルが警告を出します。この警告を無視するためには、「空の」release関数を提供しないでください。

すべてのクリーンアップ関数が行う必要があるのは、call kfree()するだけであれば、 container_of() を用いて正しい型にキャスト（上位型への変換）し（上記の例のように）、その後 kfree() を全体構造に対して呼び出す必要があります。

注意点として、kobjectの名前はrelease関数内で利用可能です。ただし、このコールバック内で名前を変更してはいけません。それにより、kobjectコアのメモリリークが発生し、ユーザーに不快感を与えます。

興味深いことに、release()メソッドはkobject自体に保存されていません。代わりに、ktypeと関連付けられています。したがって、struct kobj_typeを紹介します:

struct kobj_type {
        void (*release)(struct kobject *kobj);
        const struct sysfs_ops *sysfs_ops;
        struct attribute **default_attrs;
        const struct attribute_group **default_groups;
        const struct kobj_ns_type_operations *(*child_ns_type)(struct kobject *kobj);
        const void *(*namespace)(struct kobject *kobj);
        void (*get_ownership)(struct kobject *kobj, kuid_t *uid, kgid_t *gid);
};

この構造体は、特定のタイプのkobject（正確には、包含オブジェクト）を記述するために使用されます。すべてのkobjectは、関連付けられたkobj_type構造体を持つ必要があります。この構造体へのポインタを指定して、 kobject_init() または kobject_init_and_add().

を呼び出す必要があります。struct kobj_typeのreleaseフィールドは、このタイプのkobjectのrelease()メソッドへのポインタです。他の2つのフィールド（sysfs_opsとdefault_attrs）は、このタイプのオブジェクトがsysfsでどのように表示されるかを制御しますが、このドキュメントの範囲を超えるため、ここでは説明しません。

default_attrsポインタは、このktypeで登録されたすべてのkobjectに自動的に作成されるデフォルト属性のリストです。

ksets¶

ksetは、お互いに関連付けたいと考えるkobjectのコレクションです。同じktypeである必要はありませんが、そうではない場合は注意が必要です。

ksetは以下の機能を持ちます:

  • グループのオブジェクトを含むバッグとして機能します。ksetは、カーネルが「すべてのブロックデバイス」や「すべてのPCIデバイスドライバー」を追跡するのに使用できます。

  • ksetはまた、sysfs内のサブディレクトリとしても機能します。ksetに関連するkobjectはこのディレクトリに表示されます。すべてのksetは、他のkobjectの親となるkobjectを持つことができます。sysfs階層のトップレベルディレクトリはこのように構築されます。

  • ksetはkobjectの「ホットプラグ」をサポートし、ueventイベントがユーザー空間に報告される方法を制御できます。

オブジェクト指向の観点から、「kset」はトップレベルのコンテナクラスです。ksetは自身のkobjectを含みますが、このkobjectはksetコードによって管理され、他のユーザーによって操作してはいけません。

ksetは、標準的なカーネルリンクリストに子供を保持します。kobjectsは、ksetフィールドを通じてその包含するksetに逆参照します。ほぼすべてのケースでは、ksetに属するkobjectsは、そのkset（厳密には、埋め込まれたkobject）を親としています。

ksetは内部にkobjectを保持するため、常に動的に生成され、静的に宣言されたりスタック上に宣言されたりしてはいけません。新しいksetを作成するには以下の通りです：

struct kset *kset_create_and_add(const char *name,
                                 const struct kset_uevent_ops *uevent_ops,
                                 struct kobject *parent_kobj);

ksetの使用が完了した後、以下を呼び出します：

void kset_unregister(struct kset *k);

これにより、ksetがsysfsから削除され、参照カウンタがデクリメントされます。参照カウンタがゼロになると、ksetが解放されます。他の参照がまだ存在する可能性があるため、解放はその後行われることがあります。 kset_unregister() 戻ります。

ksetの使用例は、 samples/kobject/kset-example.c ファイルに記載されています。

ksetが関連するkobjectsのuevent操作を制御したい場合、struct kset_uevent_opsを使用して処理できます：

struct kset_uevent_ops {
        int (* const filter)(struct kset *kset, struct kobject *kobj);
        const char *(* const name)(struct kset *kset, struct kobject *kobj);
        int (* const uevent)(struct kset *kset, struct kobject *kobj,
                      struct kobj_uevent_env *env);
};

フィルターファンクションは、特定のkobjectに対してueventがユーザー空間に送信されないようにksetに制御を許可します。このファンクションが0を返す場合、ueventは送信されません。

名前ファンクションは、ueventがユーザー空間に送信する際のksetのデフォルト名を上書きします。デフォルトでは、kset自身と同じ名前が使用されますが、このファンクションが存在する場合、その名前を上書きできます。

ueventファンクションは、ueventがユーザー空間に送信される直前に呼び出され、ueventに追加の環境変数を追加する機会を提供します。

では、kobjectがksetにどのように追加されるのか疑問に思うかもしれません。その答えは、このタスクが kobject_add()によって処理されるからです。kobjectが kobject_add()に渡される際、そのksetメンバは、kobjectが属するksetを指す必要があります。 kobject_add() は残りの処理を行います。

ksetに属するkobjectが親のkobjectを設定していない場合、ksetのディレクトリに追加されます。すべてのksetのメンバーが必ずしもksetディレクトリに存在するわけではありません。kobjectが追加される前に明示的な親のkobjectが割り当てられた場合、kobjectはksetに登録されますが、親のkobjectの下に追加されます。

kobjectの削除¶

kobjectがkobjectコアに成功して登録された後、コードが使用を終えたらクリーンアップする必要があります。これを実行するには、 kobject_put()を呼び出します。これにより、kobjectコアがこのkobjectによって割り当てられたすべてのメモリを自動的にクリーンアップします。もし KOBJ_ADD ueventがオブジェクトに対して送信された場合、対応する KOBJ_REMOVE ueventが送信され、呼び出し元に対してsysfsのメンテナンスが適切に処理されます。

kobjectを二段階で削除する必要がある場合（例として、オブジェクトを破壊する際にスリープが許可されていない場合）、以下の関数を呼び出してください。 kobject_del() これにより、kobjectはsysfsからアンレジストレッドされ、「不可視」になりますが、クリーンアップは行われず、オブジェクトの参照カウントは変わりません。後で以下の関数を呼び出して、kobjectに関連するメモリのクリーンアップを完了してください。 kobject_put() kobjectに関連するメモリのクリーンアップを完了するには、以下の関数を呼び出してください。

kobject_del() 循環参照が構築されている場合、親オブジェクトへの参照を解除するために使用できます。ある親オブジェクトが子オブジェクトを参照する場合、これは有効なケースですが、循環参照は明示的な呼び出しでなければなりません。 kobject_del()リリース関数が呼び出され、かつ以前の循環参照のオブジェクト同士がお互いにリリースされるようにします。

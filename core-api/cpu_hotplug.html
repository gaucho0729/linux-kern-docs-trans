日付

2016年12月

著者

はじめに¶

システムアーキテクチャの現代的な進歩により、プロセッサに高度なエラー報告および修正機能が導入されました。NUMAハードウェアをサポートするOEMはいくつかあり、ホットプラグ可能な物理ノードの挿入および除去にはCPUホットプラグのサポートが必要です。

このような進歩により、カーネルに利用可能なCPUをプロビジョニングの理由またはRAS（リーディング・アウェア・システム）の目的でシステム実行パスから除外する必要があります。そのため、LinuxカーネルでのCPUホットプラグのサポートが必要です。

CPUホットプラグのサポートのより新しい用途として、SMPのスリープおよび再起動サポートがあります。デュアルコアおよびHT（ハイパースレッディング）のサポートにより、ノートPCでもこれらの方法をサポートしていないSMPカーネルを実行できます。

コマンドラインスイッチ¶

maxcpus=n

ブート時のCPUを制限する n. 4つのCPUがある場合、 maxcpus=2 は2つしか起動しません。他のCPUは後でオンラインにできます。

nr_cpus=n

カーネルがサポートするCPUの総数を制限します。ここで指定された数が物理的に利用可能なCPUの数より少ない場合、それらのCPUは後でオンラインにできません。

additional_cpus=n

ホットプラグ可能なCPUを制限するために使用します。このオプションは cpu_possible_mask = cpu_present_mask + additional_cpus

IA64アーキテクチャに限定されます。

possible_cpus=n

このオプションは possible_cpus ビットを cpu_possible_mask.

X86およびS390アーキテクチャに限定されます。

cpu0_hotplug

CPU0をシャットダウンを許可します。

X86アーキテクチャに限定されます。

CPUマップ¶

cpu_possible_mask

システムで常に利用可能なCPUのビットマップ。これは、CPUが利用可能または除去されるたびにサイズが変化しないper_cpu変数のためのブート時のメモリを割り当てるために使用されます。ブート時の発見フェーズで設定された後、マップは静的になります（つまり、ビットは追加または削除されません）。システムのニーズに合わせて正確にトリムすることで、ブート時のメモリを節約できます。

cpu_online_mask

現在オンラインのすべてのCPUのビットマップ。これは __cpu_up() カーネルスケジューリングに利用可能になり、デバイスからの割込みを受信できる状態になった後。CPUが __cpu_disable()、その前にすべてのOSサービス（含む割込み）が別のターゲットCPUに移動されます。

cpu_present_mask

システムに現在存在するCPUのビットマップ。すべてがオンライン状態にあるとは限りません。関連するサブシステム（例: ACPI）がホットプラグを処理すると、イベントがホットアド/ホットリムーブであるかどうかに応じて、マップからビットが追加または削除されることがあります。現在はロックに関するルールは存在しません。典型的な用途は、起動時にトポロジを初期化することであり、その際ホットプラグは無効になっています。

システムCPUマップを操作する必要はありません。ほとんどの用途では読み取り専用です。パーコンピュータリソースを設定する際には常に cpu_possible_mask または for_each_possible_cpu() を用いてイテレーションを行います。マクロ for_each_cpu() はカスタムCPUマスクをイテレーションするために使用できます。

他の何ものも使用せず、常に cpumask_t を用いてCPUのビットマップを表してください。

CPUホットプラグの使用¶

カーネルオプション CONFIG_HOTPLUG_CPU が有効化されている必要があります。現在はARM、MIPS、PowerPC、X86などの複数アーキテクチャで利用可能です。設定はsysfsインターフェースを通じて行われます：

$ ls -lh /sys/devices/system/cpu
total 0
drwxr-xr-x  9 root root    0 Dec 21 16:33 cpu0
drwxr-xr-x  9 root root    0 Dec 21 16:33 cpu1
drwxr-xr-x  9 root root    0 Dec 21 16:33 cpu2
drwxr-xr-x  9 root root    0 Dec 21 16:33 cpu3
drwxr-xr-x  9 root root    0 Dec 21 16:33 cpu4
drwxr-xr-x  9 root root    0 Dec 21 16:33 cpu5
drwxr-xr-x  9 root root    0 Dec 21 16:33 cpu6
drwxr-xr-x  9 root root    0 Dec 21 16:33 cpu7
drwxr-xr-x  2 root root    0 Dec 21 16:33 hotplug
-r--r--r--  1 root root 4.0K Dec 21 16:33 offline
-r--r--r--  1 root root 4.0K Dec 21 16:33 online
-r--r--r--  1 root root 4.0K Dec 21 16:33 possible
-r--r--r--  1 root root 4.0K Dec 21 16:33 present

ファイル オフライン, オンライン, 可能, 存在 CPUマスクを表します。各CPUフォルダには オンライン というファイルがあり、論理的なON（1）およびOFF（0）状態を制御します。CPU4を論理的にシャットダウンするには、

$ echo 0 > /sys/devices/system/cpu/cpu4/online
 smpboot: CPU 4 is now offline

CPUがシャットダウンされると、 /proc/interrupts, /proc/cpuinfo から削除され、 top コマンドで表示されなくなります。CPU4を再びオンラインにします：

$ echo 1 > /sys/devices/system/cpu/cpu4/online
smpboot: Booting Node 0 Processor 4 APIC 0x1

CPUが再び使用可能になります。これはすべてのCPUで動作するはずです。CPU0は通常特殊で、ホットプラグの対象から除外されます。X86ではカーネルオプション CONFIG_BOOTPARAM_HOTPLUG_CPU0 が有効化されている必要があります。CPU0をシャットダウンするためには、またはカーネルコマンドオプション cpu0_hotplug を使用できます。CPU0の既知の依存関係：

  • ハイبرネーション/スリープからの復帰。ハイبرネーション/スリープがCPU0がオフラインの場合に失敗します。

  • PIC割込み。PIC割込みが検出されている場合、CPU0は削除できません。

CPU0への依存関係を発見した場合は、Fenghua Yu <fenghua.yu@intel.com> にご連絡ください。

CPUホットプラグの調整¶

オフラインケース¶

CPUが論理的にシャットダウンされると、登録されたホットプラグ状態の teardown コールバックが呼び出されます。最初に CPUHP_ONLINE が実行され、状態 CPUHP_OFFLINEで終了します。これは以下のものを含みます：

  • スリープ操作によりタスクが凍結している場合、 cpuhp_tasks_frozen が true に設定されます。

  • すべてのプロセスは、この出力CPUから新しいCPUへ移動されます。新しいCPUは、各プロセスの現在のcpusetから選択され、これはすべてのオンラインCPUのサブセットである可能性があります。

  • このCPUに割り当てられたすべての割り込みは、新しいCPUに移動されます。

  • タイマも新しいCPUに移動されます。

  • すべてのサービスが移動した後、カーネルはアーキテクチャ固有のルーチンを呼び出します。 __cpu_disable() アーキテクチャ固有のクリーンアップを実行します。

ホットプラグAPIを使用することで¶

CPUがオフラインまたはオンラインになったときに通知を受けることが可能です。これは、利用可能なCPUの数に基づいてセットアップやクリーンアップを行う必要がある特定のドライバにとって重要かもしれません:

#include <linux/cpuhotplug.h>

ret = cpuhp_setup_state(CPUHP_AP_ONLINE_DYN, "X/Y:online",
                        Y_online, Y_prepare_down);

X はサブシステムであり、 Y 特定のドライバです。この Y_online コールバックは、登録時にすべてのオンラインCPUで呼び出されます。オンラインコールバック中にエラーが発生した場合、 Y_prepare_down コールバックは、オンラインコールバックが以前に呼び出されたすべてのCPUで呼び出されます。登録が完了した後、 Y_online コールバックはCPUがオンラインになったときに呼び出され、 Y_prepare_down はCPUがシャットダウンするときに呼び出されます。以前に割り当てられたすべてのリソースは、 Y_online で解放される必要があります。 Y_prepare_down返却値 ret 登録プロセス中にエラーが発生した場合、負の値になります。それ以外の場合は、動的に割り当てられた状態（CPUHP_AP_ONLINE_DYN）に割り当てられたホットプラグ状態を含む正の値が返されます。事前に定義された状態についてはゼロが返されます。

コールバックは、 cpuhp_remove_state()を呼び出すことで削除できます。動的に割り当てられた状態（CPUHP_AP_ONLINE_DYN）を使用する際は、返却された状態を使用してください。ホットプラグ状態の削除中に teardown コールバックが呼び出されます。

複数インスタンス¶

ドライバが複数のインスタンスを持ち、各インスタンスがコールバックを独立して実行する必要がある場合、おそらく「マルチステート」を使用する必要があります。まず、マルチステートを登録します:

ret = cpuhp_setup_state_multi(CPUHP_AP_ONLINE_DYN, "X/Y:online,
                              Y_online, Y_prepare_down);
Y_hp_online = ret;

以下の cpuhp_setup_state_multi() は、 cpuhp_setup_state() と同様に動作しますが、マルチステート用のコールバックを準備し、コールバックを呼び出しません。これはワンタイムのセットアップです。新しいインスタンスが割り当てられた後、この新しいインスタンスを登録する必要があります:

ret = cpuhp_state_add_instance(Y_hp_online, &d->node);

この関数は、このインスタンスを以前に割り当てた Y_hp_online 状態に追加し、すべてのオンラインCPUで以前に登録したコールバック（Y_online）を呼び出します。 node 要素は、インスタンスごとのデータ構造の struct hlist_node メンバです。

インスタンスの削除時に:

cpuhp_state_remove_instance(Y_hp_online, &d->node)

を呼び出す必要があります。これにより、すべてのオンラインCPUでteardownコールバックが呼び出されます。

アーキテクチャの要件¶

次の関数と設定が必要です：

CONFIG_HOTPLUG_CPU

このエントリは Kconfig で有効にする必要があります

__cpu_up()

アーキテクチャのインターフェースで CPU を起動する

__cpu_disable()

アーキテクチャのインターフェースで CPU をシャットダウンする。このルーチンが返る後、カーネルはさらに割り込みを処理できません。これはタイマのシャットダウンも含みます。

__cpu_die()

これは実際にCPUの死を保証するための仕組みです。他のアーキテクチャでCPUホットプラグを実装している例コードを確認してください。プロセッサはその特定のアーキテクチャのループから取り除かれます。 idle() ループ __cpu_die() 通常は、いくつかのper_cpu状態が設定されるのを待機し、プロセッサの死処理が確実に呼び出されるようにします。

ユーザー空間通知¶

CPUが成功裏にオンラインまたはオフラインになった後、udevイベントが送信されます。udevルールの例として:

SUBSYSTEM=="cpu", DRIVERS=="processor", DEVPATH=="/devices/system/cpu/*", RUN+="the_hotplug_receiver.sh"

すべてのイベントを受信します。スクリプトの例として:

#!/bin/sh

if [ "${ACTION}" = "offline" ]
then
    echo "CPU ${DEVPATH##*/} offline"

elif [ "${ACTION}" = "online" ]
then
    echo "CPU ${DEVPATH##*/} online"

fi

イベントをさらに処理できます。

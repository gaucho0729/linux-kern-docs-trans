汎用連想配列の実装¶

概要¶

この連想配列の実装は、以下の特性を持つオブジェクトコンテナです：

  1. オブジェクトは不透明ポインタです。実装はそれらがどこを指しているか（どこを指しているか）や、指しているオブジェクトの内容（存在するかどうか）には関心を持ちません。

    注意

    オブジェクトへのポインタは、最下位ビットがゼロでなければなりません。

  2. オブジェクトは、配列による使用のためにリンクブロックを含む必要はありません。これにより、オブジェクトが複数の配列に同時に存在できるようになります。代わりに、配列はメタデータブロックから構成され、これらのブロックがオブジェクトを指します。

  3. オブジェクトは、配列内でそれらを特定するインデックスキーが必要です。

  4. インデックスキーは一意でなければなりません。同じキーを持つオブジェクトを配列に挿入すると、古いオブジェクトが置き換えられます。

  5. インデックスキーは任意の長さで、異なる長さのキーも可能です。

  6. インデックスキーは、長さの変化が見られる前に、長さを早期にエンコードする必要があります。

  7. インデックスキーにはハッシュを含めることで、配列内でオブジェクトを分散させることができます。

  8. この配列は反復可能であり、オブジェクトはキー順で必ずしも出力されるとは限りません。

  9. 配列が変更されている間でも反復可能です。ただし、イテレータがRCU readlockを保持している必要があります。注意点として、このような状況では一部のオブジェクトが複数回表示される可能性があります。これが問題となる場合は、イテレータが変更を防ぐロックを取得する必要があります。ただし、削除されていない限りオブジェクトは見逃されることはありません。

  10. 配列内のオブジェクトはインデックスキーにより検索可能です。

  11. 配列が変更されている間でも、RCU readlockを保持しているスレッドが検索を行う限り、オブジェクトを検索可能です。

この実装は、radix treeと同様の方法でインデックスキーのニブルを各レベルでインデックスする16ポインタノードの木を使用しています。メモリ効率を向上させるため、単一占有ノードの連続をスキップするショートカットを設置できます。さらに、ノードは、ノード内の空きスペースに葉オブジェクトポインタを詰め込むことで、追加する必要があるまで新たな枝を作成するのではなく、効率的に管理します。

パブリックAPI¶

パブリックAPIは <linux/assoc_array.h>にあります。連想配列は次の構造に根ざしています：

struct assoc_array {
        ...
};

コードは、 CONFIG_ASSOCIATIVE_ARRAY 以下のように変更してください：

./script/config -e ASSOCIATIVE_ARRAY

編集スクリプト¶

挿入および削除関数は、後に変更を実行する際にリスクを回避できます ENOMEMこれは、内部ツリーにインストールされる事前に割り当てられたメタデータブロックを保持し、スクリプトが適用される際にツリーから削除されるメタデータブロックを追跡します。

スクリプトが適用された後も、死んだブロックや死んだオブジェクトを追跡し、後で解放できるようにします。解放はRCU grace periodが終了した後に行われ、これによりRCU read lockの下でアクセス関数が実行されることが可能になります。

このスクリプトは、APIの外側で次の型のポインタとして表示されます:

struct assoc_array_edit;

スクリプトを処理するための関数は2つあります:

  1. 編集スクリプトを適用する:

    void assoc_array_apply_edit(struct assoc_array_edit *edit);

これは編集機能を実行し、さまざまなライトバリアを挿入してRCU read lockの下でアクセスが継続可能にするため、編集スクリプトは call_rcu() に渡され、それによってスクリプトおよびスクリプトが指す死んだデータを解放します。

  1. 編集スクリプトをキャンセルする:

    void assoc_array_cancel_edit(struct assoc_array_edit *edit);

これは編集スクリプトおよびすべての事前に割り当てられたメモリを即座に解放します。これは挿入に関連している場合でも、新しいオブジェクトはこの関数によって解放されず、呼び出し元が明示的に解放する必要があります。

これらの関数は失敗することが保証されています。

操作テーブル¶

複数の関数は操作テーブルを引数として受け取ります:

struct assoc_array_ops {
        ...
};

これは、すべてのメソッドを提供する必要があります:

  1. 呼び出し元データからインデックスキーのチャンクを取得する:

    unsigned long (*get_key_chunk)(const void *index_key, int level);

これは、レベル引数で指定された位置から、呼び出し元が提供したインデックスキーのチャンクを返す必要があります。レベル引数は ビット の倍数であり、関数は ASSOC_ARRAY_KEY_CHUNK_SIZE を返す必要があります。エラーは発生しません。 ASSOC_ARRAY_KEY_CHUNK_SIZE bits.

  1. オブジェクトのインデックスキーのチャンクを取得する:

    unsigned long (*get_object_key_chunk)(const void *object, int level);

前の関数と同様ですが、データは配列内のオブジェクトから取得します。

  1. これは私たちが探しているオブジェクトかどうかを確認する:

    bool (*compare_object)(const void *object, const void *index_key);

オブジェクトをインデックスキーと比較し、 true に一致した場合、 false に一致しない場合に返します。

  1. 2つのオブジェクトのインデックスキーを比較する:

    int (*diff_objects)(const void *object, const void *index_key);

指定されたオブジェクトのインデックスキーが与えられたインデックスキーと異なるビット位置を返します。同じ場合は-1を返します。

  1. オブジェクトを解放する:

    void (*free_object)(void *object);

指定されたオブジェクトを解放します。注意: この関数は、 assoc_array_apply_edit() が呼び出された後にRCU grace periodが終了した後に呼び出される可能性があるため、 synchronize_rcu() はモジュールアンロード時に必要となる場合があります。

連想配列を操作するための関数はいくつかあります:

  1. 連想配列を初期化する:

    void assoc_array_init(struct assoc_array *array);

これは連想配列のベース構造を初期化します。失敗することはありません。

インデックスキーの形式¶

インデックスキーは任意の形式で構いませんが、アルゴリズムにキーの長さが分からないため、キーの長さを早期に含めることが強く推奨されます。これにより、長さによる比較の影響が最小限に抑えられます。

これにより、長さの異なるキーを持つ葉は離れ離れになり、長さの同じキーを持つ葉は集まっていきます。

インデックスキーは、キーの残り部分のハッシュで始めることが推奨され、キースペース全体にわたって散らばりを最大化します。

散らばりが良いほど、内部の木は広く低くなります。

散らばりが悪い場合でも、ショートカットやノードが葉とメタデータポインタを混在させることで、あまり大きな問題にはなりません。

インデックスキーはマシンワード単位で読み込まれ、各チャンクはレベルごとに1つのニブル（4ビット）に分割されます。32ビットCPUでは8レベル、64ビットCPUでは16レベルが可能で、散らばりが十分であれば、どのインデックスキーでも1つのワードしか使用しない可能性が低いです。

内部の仕組み¶

連想配列のデータ構造には内部の木があります。この木はノードとショートカットの2種類のメタデータブロックで構成されています。

ノードはスロットの配列であり、各スロットは以下の4つの可能性のいずれかを含みます:

  • NULLポインタ、スロットが空であることを示します。

  • オブジェクトへのポインタ（葉）

  • 次のレベルのノードへのポインタ

  • ショートカットへのポインタ

ショートカット¶

ショートカットは、キー空間の一部をジャンプするメタデータレコードです。ショートカットは、レベルを上る単一占有ノードの連続を代替するものであり、メモリの節約とトラバーサルの高速化のために存在します。

ツリーのルートがショートカットである可能性があります。たとえば、ツリーに少なくとも17つのノードがあり、すべてのノードが同じキープレフィックス 1111を持つ場合、挿入アルゴリズムは、一度のバウンドで 1111 キー空間をスキップし、これらのキーが実際に異なるレベル4に到達するようにします。

ノードの分割と収束¶

各ノードは最大16つのリーフとメタデータポインタを保持できます。挿入アルゴリズムがノードに17番目のオブジェクトを挿入しようとする場合、そのノードは分割され、少なくともそのレベルで共通のキーセグメントを持つリーフが別のノードに配置され、その共通キーセグメントに基づいてルートされるようになります。

フルノード内のリーフと挿入されるリーフが十分に似ている場合、ツリーにショートカットが挿入されます。

ノードのサブツリー内のオブジェクト数が16個以下になる場合、そのサブツリーは単一のノードに収束され、可能であればルートに伝播します。

非再帰的反復¶

各ノードおよびショートカットは、親ノードへのバックポインタと、その親ノードがそのノードを指すスロット番号を含みます。非再帰的な反復処理では、これらのバックポインタを使用して木をルートに向かって進み、親ノードに移動し、スロットN＋1に進むことで、スタックを使用することなく進捗を確保します。

バックポインタは、同時に変更と反復処理を行うことを困難にします。

同時変更と反復¶

考慮すべきケースはいくつかあります：

  1. シンプルな挿入/置換。これは、バリアの後で新しい葉へのポインタにNULLまたは古い一致する葉ポインタを置き換えるだけの操作です。メタデータブロックはそれ以外に変更されません。古い葉はRCUのグレース期間が終了するまで解放されません。

  2. シンプルな削除。これは、古い一致する葉ポインタをクリアするだけの操作です。メタデータブロックはそれ以外に変更されません。古い葉はRCUのグレース期間が終了するまで解放されません。

  3. 未処理のサブツリーの一部を置き換える挿入。これは、サブツリーの一部を置き換える可能性がありますが、そのポインタに到達するまでは反復処理に影響を与えません。また、先祖ブロックは置き換えられず（レイアウトは変更されません）、そのため反復処理に影響を与えません。

  4. アクティブに処理中のノードを置き換える挿入。これは問題ではありません。なぜなら、アンカーポインタをすでに通過しており、バックポインタをたどるまで新しいレイアウトに切り替わらないからです。その時点で、置き換えられたノード内の葉はすでに検査済みであり（ノード内のすべての葉をメタデータポインタをたどる前に反復処理します）、そのため影響を受けません。

    ただし、私たちがいるスロットよりも後ろのスロットにある新しい枝に分離された一部の葉を再び見ることになる可能性があります。

  5. 依存する枝を処理中のノードを置き換える挿入。これは、バックポインタをたどるまで私たちに影響を与えません。これは（4）と同様です。

  6. 私たちの下にある枝を削除して縮小する場合。これは私たちに影響を与えません。なぜなら、バックポインタにより、新しいノードの親ノードに戻る前に新しいノードを見ることはできないからです。縮小されたサブツリー全体は変更せずに破棄され、同じスロットにルートが残るため、再度処理する必要がありません。私たちがスロット＋1に進むため、再度処理しないようにします。

注意

特定の状況では、ノードの親ポインタと親スロットポインタを同時に変更する必要があります（たとえば、別のノードを挿入してそのノードを上位レベルに移動した場合）。読み取りロックを回避せずにこれを行うことはできませんので、そのノードを置き換える必要があります。

ただし、ショートカットをノードに変換する際には問題になりません。ショートカットは1つのスロットしか持たないため、逆方向に移動する際には親のスロット番号は使用されません。これにより、バリアーを使用して親のスロット番号がバックポインタの後で読み込まれるように確保すれば、スロット番号を最初に変更しても問題ありません。

非活性ブロックやリーフはRCUグレースペリオドが過ぎた後で解放されるため、ウォーキングやイテレーションを行っている者がRCU読み込みロックを保持している限り、古いスーパーストラクチャが消えてしまうことはありません。

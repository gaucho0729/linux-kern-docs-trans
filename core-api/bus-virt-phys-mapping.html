AHA-1542はバスマスター機器であり、あなたのパッチによりドライバーがコントローラーにバッファの物理アドレスを提供するため、x86では正しいです（すべてのバスマスター機器が物理メモリマッピングを直接見ているため）。

しかし、多くのセットアップでは実際に 三つ メモリアドレスを確認する異なる方法があり、この場合、実際に望むのは第三の「バスアドレス」です。

基本的に、メモリを参照する三つの方法は（これは「実際のメモリ」であり、通常のRAMです–後述の他の詳細については参照）：

  • CPU未変換。これは「物理」アドレスです。物理アドレス0は、CPUがメモリバスにゼロを出力するときに見るアドレスです。

  • CPU変換アドレス。これは「仮想」アドレスで、CPU自身に完全に内部的で、CPUが「CPU未変換」に適切に変換を行います。

  • バスアドレス。これは、他のデバイスが見るメモリのアドレスで、CPUではありません。理論上は、多くの異なるバスアドレスがあり、各デバイスがデバイス固有の方法でメモリを認識するかもしれませんが、幸いなことに、ほとんどのハードウェア設計者は、必要以上に複雑にするのではなく、シンプルに設計しています。したがって、すべての外部ハードウェアがメモリを同じように見るものと仮定できます。

通常のPCでは、バスアドレスは物理アドレスと完全に同じで、非常に単純です。しかし、それらが単純なのは、メモリとデバイスが同じアドレス空間を共有しているからです。これは他のPCI/ISAのセットアップでは一般的に必ずしも真ではありません。

例として、PReP（PowerPC Reference Platform）では、CPUがメモリマップを以下のように見ます（これはメモリからのものです）：

0-2 GB          "real memory"
2 GB-3 GB       "system IO" (inb/out and similar accesses on x86)
3 GB-4 GB       "IO memory" (shared memory over the IO bus)

これだけでは単純に見えます。しかし、デバイスの視点から同じものを確認すると、逆になります。物理メモリアドレス0は、すべてのIOマスターに対してアドレス2 GBとして表示されます。

したがって、CPUがバスマスターに物理メモリ0に書き込むようにしたい場合、マスターにメモリアドレスとして0x80000000を指定する必要があります。

したがって、PPCでのカーネルの実際のマッピング方法によって、このような設定になることがあります：

physical address:      0
virtual address:       0xC0000000
bus address:           0x80000000

すべてのアドレスが実際に同じものに指しているだけで、異なる翻訳を通じて見られるだけです。

同様に、Alphaでは通常の翻訳は以下の通りです：

physical address:      0
virtual address:       0xfffffc0000000000
bus address:           0x40000000

(ただし、物理アドレスとバスアドレスが同じになるAlphaも存在します)

とにかく、これらの翻訳を調べる方法は、以下のようにします：

#include <asm/io.h>

phys_addr = virt_to_phys(virt_addr);
virt_addr = phys_to_virt(phys_addr);
 bus_addr = virt_to_bus(virt_addr);
virt_addr = bus_to_virt(bus_addr);

では、いつこれらの情報が必要になるのでしょうか？

あなたは 仮想 カーネルからそのポインタにアクセスする際のアドレスを望みます。そのため、以下のような形になります：

/*
 * this is the hardware "mailbox" we use to communicate with
 * the controller. The controller sees this directly.
 */
struct mailbox {
        __u32 status;
        __u32 bufstart;
        __u32 buflen;
        ..
} mbox;

        unsigned char * retbuffer;

        /* get the address from the controller */
        retbuffer = bus_to_virt(mbox.bufstart);
        switch (retbuffer[0]) {
                case STATUS_OK:
                        ...

一方で、コントローラーにバッファを渡したい場合、バスアドレスが必要です：

/* ask the controller to read the sense status into "sense_buffer" */
mbox.bufstart = virt_to_bus(&sense_buffer);
mbox.buflen = sizeof(sense_buffer);
mbox.status = 0;
notify_controller(&mbox);

また、一般的には 更新処理が完了した後でも新しい読者が即座に開始する可能性があるため、以下のコードは読者がいないと信頼してはならない。 物理アドレスを使用したいです。なぜなら、CPUからは使用できません（CPUは翻訳された仮想アドレスのみを使用）、バスマスターからも使用できませんからです。

では、なぜ物理アドレスに興味を持つのでしょうか？一部のケースでは物理アドレスが必要ですが、通常のコードではあまり使われません。メモリマッピングを使用する場合など、物理アドレスが必要なのはそのようなケースです。なぜなら、「mm関数」はページ単位で再マッピングされるメモリの物理アドレスを必要とするからです（メモリ管理レイヤーはCPU外のデバイスについて知らないため、バスアドレスなどについて知る必要はありません）。remap_pfn_range()上記は全体の式の一部に過ぎません。上記は「実際のメモリ」つまりCPUメモリ（RAM）についてのみ述べています。

注意

また、完全に異なる種類のメモリもあります。それはPCIまたはISAバス上の「共有メモリ」です。これは通常RAMではありません（ただし、ビデオグラフィックカードの場合は、フレームバッファとして使用される通常のDRAMもあります）が、ネットワークカードのパケットバッファなど、さまざまなデバイスに使用されることがあります。

このようなメモリは「PCIメモリ」「共有メモリ」「IOメモリ」などと呼ばれます。これらにアクセスする方法は1通りしかありません：readb/writebなどの関数です。このようなメモリのアドレスを取得すべきではありません。なぜなら、このようなアドレスは「実際のメモリ」という概念的空間に存在しないからです。したがって、ポインタを直接参照することはできません。（残念ながら、x86では

同じメモリ空間にあるため、x86ではポインタを参照するだけで動作しますが、これは移植性がありません）。 通常のRCU読み込み側クリティカルセクションは、条件付きでスリープロックを取得することが許容されます（例として このようなメモリに対しては、以下の操作が可能です：

読み取り：

  • 再マッピングと書き込み：

    /*
 * read first 32 bits from ISA memory at 0xC0000, aka
 * C000:0000 in DOS terms
 */
unsigned int signature = isa_readl(0xC0000);

  • コピーとクリアリング：

    /*
 * remap framebuffer PCI memory area at 0xFC000000,
 * size 1MB, so that we can access it: We can directly
 * access only the 640k-1MB area, so anything else
 * has to be remapped.
 */
void __iomem *baseptr = ioremap(0xFC000000, 1024*1024);

/* write a 'A' to the offset 10 of the area */
writeb('A',baseptr+10);

/* unmap when we unload the driver */
iounmap(baseptr);

カーネルバージョン2.0.x（および以前のバージョン）は誤って ioremap() 関数「vremap()」を呼び出していました。 ioremap() これは正しい名前ですが、最初に書いたときは考えがまとまっていませんでした。どちらのバージョンをサポートする必要がある人は、以下のようにすることができるでしょう：

/* support old naming silliness */
#if LINUX_VERSION_CODE < 0x020100
#define ioremap vremap
#define iounmap vfree
#endif

ソースファイルの先頭にこのコメントを追加し、その後で2.0.x系のシステムでも正しい名前を使用できるようになります。

上の説明は実際よりも悪く聞こえますが、実際にはほとんどの実際のドライバはそんなに複雑な処理を行っていません（あるいは、複雑さは実際のIOアクセスよりもエラー処理やタイムアウトなどの部分にあります）。ドライバの修正は一般的に難しくなく、多くの場合、修正後のコードは実際に読みやすくなります：

unsigned long signature = *(unsigned int *) 0xC0000;
        vs
unsigned long signature = readl(0xC0000);

カーネルオブジェクトに参照カウンタ（krefs）を追加する¶

著者

Corey Minyard <minyard@acm.org>

著者

Thomas Hellstrom <thellstrom@vmware.com>

この内容は、Greg Kroah-Hartman 氏が2004年のOLSで発表したkrefsに関する論文とプレゼンテーションから多くを借用しています。詳細は以下をご覧ください:

  • http://www.kroah.com/linux/talks/ols_2004_kref_paper/Reprint-Kroah-Hartman-OLS2004.pdf

  • http://www.kroah.com/linux/talks/ols_2004_kref_talk/

はじめに¶

krefsは、オブジェクトに参照カウンタを追加するためのメカニズムです。複数の場所で使用され、他のスレッドに渡されるオブジェクトがある場合、参照カウンタがなければコードはほぼ間違いなく破損しています。参照カウンタが必要な場合は、krefsを使用するのが最適です。

krefを使用するには、データ構造に以下のように追加します:

struct my_data
{
    .
    .
    struct kref refcount;
    .
    .
};

krefはデータ構造内のどこにでも存在できます。

初期化¶

krefを初期化するには、割り当てた後でkref_initを呼び出します。以下のようにします:

struct my_data *data;

data = kmalloc(sizeof(*data), GFP_KERNEL);
if (!data)
       return -ENOMEM;
kref_init(&data->refcount);

これにより、kref内の参照カウンタが1に設定されます。

krefのルール¶

初期化されたkrefを扱う際には、以下のルールを厳守してください:

  1. ポインタの非一時的なコピーを作成する場合、特に他の実行スレッドに渡す可能性がある場合は、渡す前にkref_get()で参照カウンタをインクリメントする必要があります:

    kref_get(&data->refcount);

    すでにkref-ed構造体（参照カウンタがゼロにならない）の有効なポインタを保持している場合、ロックなしでこの操作を行うことができます。

  2. ポインタを使用が終わった場合は、必ずkref_put()を呼び出してください:

    kref_put(&data->refcount, data_release);

    このポインタが最後の参照だった場合、解放ルーチンが呼び出されます。コードがすでに有効なポインタを保持している状態でkref-ed構造体への有効なポインタを取得しようとしていない限り、ロックなしでこの操作を行うことができます。

  3. コードがすでに有効なポインタを保持している状態でない場合にkref-ed構造体への参照を取得しようとすると、kref_get()中にkref_put()が発生しないようにアクセスをシリアライズする必要があります。また、kref_get()中に構造体が有効な状態を維持しなければなりません。

例えば、データを割り当てて別のスレッドに処理を渡す場合:

void data_release(struct kref *ref)
{
    struct my_data *data = container_of(ref, struct my_data, refcount);
    kfree(data);
}

void more_data_handling(void *cb_data)
{
    struct my_data *data = cb_data;
    .
    . do stuff with data here
    .
    kref_put(&data->refcount, data_release);
}

int my_data_handler(void)
{
    int rv = 0;
    struct my_data *data;
    struct task_struct *task;
    data = kmalloc(sizeof(*data), GFP_KERNEL);
    if (!data)
            return -ENOMEM;
    kref_init(&data->refcount);

    kref_get(&data->refcount);
    task = kthread_run(more_data_handling, data, "more_data_handling");
    if (task == ERR_PTR(-ENOMEM)) {
            rv = -ENOMEM;
            kref_put(&data->refcount, data_release);
            goto out;
    }

    .
    . do stuff with data here
    .
out:
    kref_put(&data->refcount, data_release);
    return rv;
}

このようにすることで、2つのスレッドがデータをどの順序で処理しても問題ありません。kref_put()がデータが参照されなくなったタイミングを把握し、解放処理を行います。kref_get()はすでに有効なポインタを保持しているためロック不要です。put操作もロック不要です。なぜなら、誰もポインタを取得せずにデータにアクセスしようとしていないからです。

上記の例では、成功経路とエラーパスの両方でkref_put()が2回呼び出されます。これはkref_init()とkref_get()で参照カウンタが2回インクリメントされたためです。

ルール1の「before（前）」の部分は非常に重要です。以下のようすることは決して行わないでください:

task = kthread_run(more_data_handling, data, "more_data_handling");
if (task == ERR_PTR(-ENOMEM)) {
        rv = -ENOMEM;
        goto out;
} else
        /* BAD BAD BAD - get is after the handoff */
        kref_get(&data->refcount);

自分の知識を過信せず、上記の構造を使用してください。まず、あなたが何をやっているのかを知らない可能性があります。第二に、あなたが何をやっているのかを知っている場合（ロックが関与する状況などでは上記の方法が法的に許可される場合があります）でも、他人がコードを変更したりコピーしたりする可能性があります。不適切なスタイルです。やめましょう。

get と put の最適化が可能な状況もあります。例えば、オブジェクトを別の処理に渡す際には、get と put を行う必要はありません:

/* Silly extra get and put */
kref_get(&obj->ref);
enqueue(obj);
kref_put(&obj->ref, obj_cleanup);

ただ enqueue を行うだけでよいです。この点に関するコメントは常に歓迎されます:

enqueue(obj);
/* We are done with obj, so we pass our refcount off
   to the queue.  DON'T TOUCH obj AFTER HERE! */

最後のルール（ルール3）は最も厄介なものです。例えば、リスト内の各項目が kref-ed されていて、最初の項目を取得したい場合、単にリストから最初の項目を取り出して kref_get() するのはルール3に違反します。なぜなら、すでに有効なポインタを持っていないからです。mutex（または他のロック）を追加する必要があります。例えば:

static DEFINE_MUTEX(mutex);
static LIST_HEAD(q);
struct my_data
{
        struct kref      refcount;
        struct list_head link;
};

static struct my_data *get_entry()
{
        struct my_data *entry = NULL;
        mutex_lock(&mutex);
        if (!list_empty(&q)) {
                entry = container_of(q.next, struct my_data, link);
                kref_get(&entry->refcount);
        }
        mutex_unlock(&mutex);
        return entry;
}

static void release_entry(struct kref *ref)
{
        struct my_data *entry = container_of(ref, struct my_data, refcount);

        list_del(&entry->link);
        kfree(entry);
}

static void put_entry(struct my_data *entry)
{
        mutex_lock(&mutex);
        kref_put(&entry->refcount, release_entry);
        mutex_unlock(&mutex);
}

kref_put() の戻り値は、ロックを全体の解放操作中保持しない場合に役立ちます。例えば、上記の例でロックを保持して呼び出す必要がない場合（それほど意味がないからです）: kfree() kref_put() を以下のように使用できます:

static void release_entry(struct kref *ref)
{
        /* All work is done after the return from kref_put(). */
}

static void put_entry(struct my_data *entry)
{
        mutex_lock(&mutex);
        if (kref_put(&entry->refcount, release_entry)) {
                list_del(&entry->link);
                mutex_unlock(&mutex);
                kfree(entry);
        } else
                mutex_unlock(&mutex);
}

他のルーチンを解放操作中に呼び出す必要がある場合、この方法はより有用です（長時間かかる場合や同じロックを取得する可能性がある場合）。ただし、すべての解放処理をリリースルーチン内で行うのがよりスマートです。

上記の例は、kref_get_unless_zero() を使用して最適化することもできます:

static struct my_data *get_entry()
{
        struct my_data *entry = NULL;
        mutex_lock(&mutex);
        if (!list_empty(&q)) {
                entry = container_of(q.next, struct my_data, link);
                if (!kref_get_unless_zero(&entry->refcount))
                        entry = NULL;
        }
        mutex_unlock(&mutex);
        return entry;
}

static void release_entry(struct kref *ref)
{
        struct my_data *entry = container_of(ref, struct my_data, refcount);

        mutex_lock(&mutex);
        list_del(&entry->link);
        mutex_unlock(&mutex);
        kfree(entry);
}

static void put_entry(struct my_data *entry)
{
        kref_put(&entry->refcount, release_entry);
}

put_entry() 内の kref_put() に mutex ロックを外すのに有用ですが、kref_get_unless_zero は検索テーブルでエントリを見つけた同じクリティカルセクション内に含める必要があります。そうでないと、kref_get_unless_zero がすでに解放されたメモリを参照する可能性があります。注意点として、kref_get_unless_zero を使用する際は必ず戻り値を確認する必要があります。すでに有効なポインタを持っていることを確認している場合は、kref_get() を使用してください。

Krefs と RCU¶

kref_get_unless_zero は、上記の例で検索に RCU ロックを使用することも可能にします:

struct my_data
{
        struct rcu_head rhead;
        .
        struct kref refcount;
        .
        .
};

static struct my_data *get_entry_rcu()
{
        struct my_data *entry = NULL;
        rcu_read_lock();
        if (!list_empty(&q)) {
                entry = container_of(q.next, struct my_data, link);
                if (!kref_get_unless_zero(&entry->refcount))
                        entry = NULL;
        }
        rcu_read_unlock();
        return entry;
}

static void release_entry_rcu(struct kref *ref)
{
        struct my_data *entry = container_of(ref, struct my_data, refcount);

        mutex_lock(&mutex);
        list_del_rcu(&entry->link);
        mutex_unlock(&mutex);
        kfree_rcu(entry, rhead);
}

static void put_entry(struct my_data *entry)
{
        kref_put(&entry->refcount, release_entry_rcu);
}

ただし、release_entry_rcu を呼び出した後も、struct kref メンバーが RCU グレース期間内に有効なメモリに保たれる必要があります。これは kfree_rcu(entry, rhead) を使用するか、kfree に使用する前に関数を呼び出すことで実現できます。 synchronize_rcu() kfree に使用する前に関数を呼び出すことができますが、 synchronize_rcu() は相当な時間の間待機する可能性があります。

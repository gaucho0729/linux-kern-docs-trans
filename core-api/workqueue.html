はじめに¶

非同期プロセス実行コンテキストが必要なケースが多数存在し、そのようなケースではworkqueue (wq) APIが最も一般的に使用されるメカニズムです。

このような非同期実行コンテキストが必要な場合、実行すべき関数を記述したwork itemがキューに置かれます。独立したスレッドが非同期実行コンテキストとして動作し、このキューはworkqueueと呼ばれ、スレッドはworkerと呼ばれます。

workqueueにwork itemが存在する間、workerはその関連する関数を順番に実行します。workqueueにwork itemがなくなった場合、workerはアイドル状態になります。新しいwork itemがキューに追加されると、workerは再び実行を開始します。

なぜcmwqなのか？¶

元のwq実装では、マルチスレッド（MT）のwqは各CPUごとにworkerスレッドを1つ保持し、シングルスレッド（ST）のwqはシステム全体で1つのworkerスレッドを保持していました。MTのwqではCPUの数と同程度のworkerスレッドを維持する必要があり、年々カーネルでMT wqのユーザーが増加し、CPUコア数が継続的に増加する中、一部のシステムでは起動時からデフォルトの32,768 PID空間を満たしてしまうほどになりました。

MT wqは多くのリソースを無駄にしていたものの、提供する並行性のレベルは不十分でした。この制限はSTとMTの両方のwqに共通していましたが、MTではより深刻な問題でした。各wqは独自のworkerプールを保持しており、MT wqは各CPUごとに1つの実行コンテキストしか提供できず、ST wqはシステム全体で1つの実行コンテキストを提供しました。work itemはこれらの限られた実行コンテキストを競争する必要があり、シングル実行コンテキスト周りのデッドロックの発生など、さまざまな問題を引き起こしました。

提供される並行性レベルとリソース使用量の間のトレードオフは、ユーザーに不要な選択を余儀なくさせました。たとえばlibataはポーリングPIOの処理にST wqを使用し、同時に2つのポーリングPIOが進まないという不要な制限を受け入れることになりました。MT wqは並行性を大幅に向上させるものではなく、より高い並行性が必要なユーザー（例: asyncやfscache）は自前のスレッドプールを実装する必要がありました。

Concurrency Managed Workqueue (cmwq)は、以下の目標を重視してwqの再実装です。

  • 元のworkqueue APIとの互換性を維持します。

  • per-CPUの統合workerプールをすべてのwqで共有し、リソースを無駄にせずに柔軟な並行性レベルを必要に応じて提供します。

  • ワーカーポールと並行度を自動的に調整し、APIユーザーがこのような詳細について心配する必要がないようにします。

デザイン¶

関数の非同期実行を容易にするために、新しい抽象化手法であるワークアイテムが導入されています。

ワークアイテムは、非同期に実行される関数へのポインタを保持するシンプルな構造体です。ドライバーやサブシステムが関数を非同期に実行したい場合、その関数へのポインタを持つワークアイテムを設定し、ワークキューにキューイングする必要があります。

特別な用途のスレッドであるワーカースレッドは、キューから関数を順番に実行します。キューに作業がなければ、ワーカースレッドはアイドル状態になります。これらのワーカースレッドは、ワーカーポールという名前の管理下で処理されます。

cmwq設計では、サブシステムやドライバーがワークアイテムをキューイングするユーザー向けワークキューと、ワーカーポールを管理し、キューイングされたワークアイテムを処理するバックエンドメカニズムの違いを区別しています。

各可能なCPUに対して、通常のワークアイテム用と高優先度のワークアイテム用の2つのワーカーポールがあり、さらに未バインドのワークキューにキューイングされたワークアイテムを処理する追加のワーカーポールがあります。これらのバックイングプールの数は動的です。

サブシステムやドライバーは、必要に応じて特別なワークキューAPI関数を通じてワークアイテムを生成し、キューイングできます。ワークアイテムを配置するワークキューにフラグを設定することで、ワークアイテムの実行方法に影響を与えることができます。これらのフラグには、CPUローカル性、並行度制限、優先度などが含まれます。詳細な概要については、APIの説明を参照してください。 alloc_workqueue() も参照してください。

ワークアイテムがワークキューにキューイングされるとき、キューのパラメータとワークキューの属性に基づいてターゲットのワーカーポールが決定され、そのワーカーポールの共有ワークリストに追加されます。たとえば、特に上書きされていない場合、バインドされたワークキューのワークアイテムは、発行者が実行しているCPUに関連する通常または高優先度のワーカーポールのワークリストにキューイングされます。

どのワーカーポールの実装においても、並行度（アクティブな実行コンテキストの数）の管理は重要な課題です。cmwqは、リソースを節約するための最小限の並行度を維持しつつ、システムが最大容量で利用されるように十分なレベルを保とうと努力しています。

各CPUにバインドされたワーカーポールは、スケジューラに接続してコンカレンシー管理を実装します。アクティブなワーカーが起動または停止した際、ワーカーポールは通知され、現在実行可能なワーカーの数を追跡します。一般的に、作業項目はCPUを長時間占有して多くのサイクルを消費するものではありません。つまり、作業処理が停止しないように必要なだけのコンカレンシーを維持することが最適です。CPUに1つ以上の実行可能なワーカーが存在する限り、ワーカーポールは新しい作業を実行しませんが、最後の実行中のワーカーが停止した際にはすぐに新しいワーカーをスケジュールして、未処理の作業項目がある間CPUがアイドル状態にならないようにします。

アイドル状態のワーカーを保持しておくコストは、kthreadのメモリ領域以外にありませんので、cmwqは一定時間アイドル状態のワーカーを保持した後、それらを終了します。

バインドされていないワークキューでは、バックイングプールの数は動的です。バインドされていないワークキューは、 apply_workqueue_attrs() カスタム属性を割り当てることができます。ワークキューは自動的に属性に一致するバックイングワーカーポールを生成します。コンカレンシー管理レベルの調整はユーザーの責任です。また、コンカレンシー管理を無視するバインドされたwqを指定するフラグもあります。詳細についてはAPIセクションを参照してください。

進捗保証は、必要に応じてワーカーが作成できることが前提です。これは救援ワーカーの使用によって保証されます。メモリ回収処理を扱うコードパスで使用される作業項目は、メモリ圧力下で実行できるように救援ワーカーを確保したワークキューにキューイングする必要があります。それ以外の場合、ワーカーポールが実行コンテキストを解放するのを待ってデッドロックする可能性があります。

アプリケーションプログラミングインターフェース（API）¶

alloc_workqueue() ワーキューを割り当てます。元の create_*workqueue() 関数は非推奨とされており、削除予定です。 alloc_workqueue() 3つの引数を取ります。 @name, @flags および @max_active. @name はワーキューの名前であり、救援スレッドの名前としても使用されます（存在する場合）。

ワーキューはもはや実行リソースを管理せず、進捗保証、フラッシュ、作業項目属性のドメインとして機能します。 @flags および @max_active 作業項目が実行リソースを割り当てられ、スケジュールされ、実行される方法を制御します。

flags¶

WQ_UNBOUND

未バインドのwqにキューイングされたワークアイテムは、特定のCPUにバインドされていないワーカーをホストする特別なワーカーポールによって処理されます。これにより、wqは並行性管理を行わない単純な実行コンテキストプロバイダーとして動作します。未バインドワーカーポールは、ワークアイテムの実行をできるだけ早く開始しようとします。未バインドのwqはローカル性を犠牲にしますが、以下のケースで有用です。

  • 並行性レベルの要件が大幅に変動する予想される場合、バインドされたwqを使用すると、発行元が異なるCPUを移動するたびに、多くのCPUにわたってほとんど使用されないワーカーが作成される可能性があります。

  • 長時間CPUを食い尽くすようなワークロードで、システムスケジューラによってより効率的に管理できる場合。

WQ_FREEZABLE

フリーザブルなwqはシステムのスリープ操作におけるフリーズフェーズに参加します。wq上のワークアイテムはドレインされ、解凍されるまで新たなワークアイテムの実行は行われません。

WQ_MEM_RECLAIM

メモリ回収パスで使用される可能性のあるすべてのwq MUST このフラグが設定されています。メモリ圧力に関係なく、wqは少なくとも1つの実行コンテキストを保証されています。

WQ_HIGHPRI

高優先度のwqのワークアイテムは、ターゲットCPUの高優先度ワーカーポールにキューイングされます。高優先度ワーカーポールは、niceレベルが上げられたワーカースレッドによって処理されます。

通常のワーカーポールと高優先度ワーカーポールは相互に干渉しません。それぞれが独立したワーカーポールを維持し、その内部のワーカー間で並行性管理を行います。

WQ_CPU_INTENSIVE

CPUを食い尽くすようなwqのワークアイテムは並行性レベルに貢献しません。つまり、実行可能なCPU食い尽くすワークアイテムは、同じワーカーポール内の他のワークアイテムの実行を妨げることはありません。これは、システムスケジューラによって実行が制御される予想されるバインドされたワークアイテムにとって有用です。

CPU食い尽くすワークアイテムは並行性レベルに貢献しませんが、実行の開始は依然として並行性管理によって制御され、実行可能な非CPU食い尽くすワークアイテムはCPU食い尽くすワークアイテムの実行を遅らせることができます。

このフラグは未バインドのwqには意味がありません。

フラグ WQ_NON_REENTRANT はすべてのワークキューが非再入可能になったため、現在は存在しません。どのCPUでも、任意の時点でワークアイテムが1つのワーカーによってのみ実行されることが保証されています。

max_active¶

@max_active このフラグは、ワークキューのワークアイテムに割り当て可能なCPUごとの実行コンテキストの最大数を決定します。例えば、 @max_active が16の場合、各CPUごとに同時に実行中のwqのワークアイテムは最大16個までです。

現在、バインドされたwqの場合、最大制限は @max_active は512であり、0が指定された場合のデフォルト値は256です。バインドされていないwqの場合、制限値は512と4 * のうち大きい方です。 num_possible_cpus()これらの値は、ランナウェイ状態での保護を確保しつつ、制限要因にならないように十分に高い値が選ばれています。

wqのアクティブなワーキットアイテム数は、通常、wqの利用者によって制御されます。具体的には、利用者が同時にキューに並べられるワーキットアイテム数によって制御されます。アクティブなワーキットアイテム数を制限する必要がない限り、'0'を指定することをお勧めします。

一部のユーザーはST wqの厳密な実行順序に依存しています。この動作を実現するために、 @max_active の1と WQ_UNBOUND が使用されます。このようなwqにキューイングされたワーキットアイテムは常にバインドされていないワーカーポールにキューイングされ、同時にアクティブなワーキットアイテムは1つだけであったため、ST wqと同じ順序性を達成していました。

現在の実装では、上述の設定は指定されたNUMAノード内でST動作を保証します。代わりに、 alloc_ordered_queue() を使用してシステム全体でのST動作を達成する必要があります。

ガイドライン¶

  • を忘れずに使用してください。メモリ回収中に使用されるワーキットアイテムを処理する可能性のあるwqの場合です。 WQ_MEM_RECLAIM が設定されているwqには、実行コンテキストが予約されています。メモリ回収中に使用される複数のワーキットアイテム間に依存関係がある場合、それらはそれぞれ WQ_MEM_RECLAIM が設定されている別個のwqにキューイングする必要があります。 WQ_MEM_RECLAIM.

  • 厳密な順序性が求められない限り、ST wqを使用する必要はありません。

  • 特定の必要がない限り、@max_activeに0を使用することをお勧めします。ほとんどの使用ケースでは、コンカレンシーレベルはデフォルトの制限を大幅に下回ります。

  • wqはフォワード進捗保証（WQ_MEM_RECLAIM、フラッシュおよびワーキットアイテム属性のドメインです。メモリ回収に関与しないことや、グループのワーキットアイテムとしてフラッシュする必要がないこと、また特別な属性を必要としないワーキットアイテムは、システムのwqのいずれかを使用できます。専用のwqを使用する場合とシステムwqを使用する場合の実行特性には違いはありません。

  • ワークアイテムが大量のCPUサイクルを消費する予定でない限り、ワークキュー操作およびワークアイテム実行におけるローカリティの向上により、バウンドのワークキューを使用することは通常有益です。

デバッグ¶

ワーク関数はジェネリックなワーカースレッドによって実行されるため、不適切なワークキュー利用の問題を明確にするためにいくつかのトリックが必要です。

ワーカースレッドはプロセスリストに以下のように表示されます:

root      5671  0.0  0.0      0     0 ?        S    12:07   0:00 [kworker/0:1]
root      5672  0.0  0.0      0     0 ?        S    12:07   0:00 [kworker/1:2]
root      5673  0.0  0.0      0     0 ?        S    12:12   0:00 [kworker/0:0]
root      5674  0.0  0.0      0     0 ?        S    12:13   0:00 [kworker/1:0]

kworkersが異常な状態（CPUを過剰に使用している）の場合、2種類の可能性のある問題があります:

  1. 連続してスケジュールされる何かが原因

  2. 単一のワークアイテムが大量のCPUサイクルを消費している

最初の問題はトレーシングを使用して追跡できます:

$ echo workqueue:workqueue_queue_work > /sys/kernel/debug/tracing/set_event
$ cat /sys/kernel/debug/tracing/trace_pipe > out.txt
(wait a few secs)
^C

ワークキューイングに忙しいループが原因の場合、出力に支配的になり、ワークアイテム関数を使用して問題の原因を特定できます。

2番目の問題については、問題の原因となるワーカースレッドのスタックトレースを確認するだけで解決可能でしょう。

$ cat /proc/THE_OFFENDING_KWORKER/stack

ワークアイテムの関数はスタックトレースで簡単に確認できます。

アライメントされていないメモリアクセス¶

アラン・コックス、アヴュトーン・オリッチ、ヘイッキ・オルシラ、ジャン・エンゲルハルト、ケイル・マクマーティン、ケイル・モフフィット、ランディ・ダンラップ、ロバート・ハンコック、ウリ・クニッツ、ヴァディム・ロバノフ

Linuxはさまざまなアーキテクチャで動作し、メモリアクセスの挙動はアーキテクチャによって異なります。このドキュメントでは、未アライメントアクセスについての詳細、なぜコードで未アライメントアクセスを起こさないことが重要なのか、そしてそのようなコードを書く方法について説明します。

未アライメントアクセスの定義¶

未アライメントメモリアクセスは、NバイトのデータをアドレスがNで割り切れない（addr % N != 0）場所から読み込むときに発生します。たとえば、アドレス0x10004から4バイトのデータを読み込むのは問題ありませんが、アドレス0x10005から4バイトのデータを読み込むと未アライメントメモリアクセスになります。

上記は少し曖昧に感じるかもしれませんが、コンテキストは機械語レベルです。特定の命令がメモリから複数バイトのデータを読み書きします（例: x86アセンブリのmovb、movw、movl）。後述するように、C言語の文が複数バイトのメモリアクセス命令にコンパイルされるのは、u16、u32、u64などの型を扱うときです。

ナチュラルアライメント¶

上記のルールはナチュラルアライメントと呼ばれます。Nバイトのメモリをアクセスする際、ベースアドレスはNで割り切れなければなりません（addr % N == 0）。

コードを書く際には、ターゲットアーキテクチャがナチュラルアライメントの要件を満たしているものと仮定してください。

現実には、ナチュラルアライメントをすべてのメモリアクセスサイズで要求するアーキテクチャは限られています。しかし、すべてのサポートされているアーキテクチャを考慮する必要があります。ナチュラルアライメントの要件を満たすコードを書くのが、フルポータビリティを達成する最も簡単な方法です。

未アライメントアクセスが悪い理由¶

未アライメントメモリアクセスの影響はアーキテクチャによって異なります。ここでの違いについての説明は長くなるため、以下に一般的なシナリオのサマリーを示します：

  • 一部のアーキテクチャでは未アライメントメモリアクセスを透明に処理できますが、通常はパフォーマンスに大きなコストが生じます。

  • 一部のアーキテクチャでは未アライメントアクセスが発生するとプロセッサ例外を発生させます。例外ハンドラは未アライメントアクセスを修正できますが、パフォーマンスに大きなコストが生じます。

  • 一部のアーキテクチャではアライメントが取れていないメモリアクセスが発生した際にプロセッサ例外が発生しますが、その例外にはアライメントが取れていないアクセスを修正するための情報が十分に含まれていません。

  • 一部のアーキテクチャではアライメントが取れていないメモリアクセスを実行することはできませんが、要求されたアクセスとは異なるメモリアクセスを静かに実行してしまい、検出が難しい微細なコードのバグを引き起こします！

上記の内容から明らかですが、コードがアライメントが取れていないメモリアクセスを引き起こす場合、特定のプラットフォームでは正しく動作しなくなり、他のプラットフォームではパフォーマンス問題を引き起こします。

アライメントが取れていないメモリアクセスを引き起こさないコード¶

最初は上記の概念が実際にコード作成にどう関係するのか少し理解が難しいかもしれません。畢竟、特定の変数のメモリアドレスに対して十分な制御を保有していないからです。

幸いなことに、ほとんどの場合コンパイラが問題なく動作するよう保証してくれます。例えば、以下の構造体を考えてみましょう：

struct foo {
        u16 field1;
        u32 field2;
        u8 field3;
};

上記の構造体のインスタンスがメモリ上にアドレス0x10000から開始して配置されていると仮定します。基本的な理解に基づけば、field2へのアクセスがアライメントが取れていないアクセスを引き起こすことは不自然ではありません。field2が構造体のオフセット2バイト位置に配置される（アドレス0x10002）と予想されますが、このアドレスは4で割り切れません（4バイトの値を読み込んでいることを思い出してください）。

幸いなことにコンパイラはアライメント制約を理解しているため、上記の例ではfield1とfield2の間に2バイトのパディングを挿入します。したがって、標準の構造体タイプに対してはコンパイラが構造体をパディングしてアライメントを確保してくれるため、フィールドへのアクセスが適切にアライメントされることが保証されます（ただし、フィールドを異なる長さの型にキャストしない限り）。

同様に、コンパイラは変数や関数パラメータを、変数の型のサイズに基づいた自然なアライメントに配置してくれます。

この時点で明らかですが、1バイト（u8またはchar）をアクセスしてもアライメントが取れていないメモリアクセスを引き起こすことはありません。なぜなら、すべてのメモリアドレスが1で割り切れているからです。

関連する話題として、上記の考慮点を踏まえると、構造体のフィールドの順序を変更してパディング領域に配置することで、構造体インスタンスの居住メモリサイズを削減できることが観察されます。上記の例の最適なレイアウトは：

struct foo {
        u32 field2;
        u16 field1;
        u8 field3;
};

自然なアライメントスキームの場合、コンパイラは構造体の最後に1バイトのパディングを追加するだけで済みます。このパディングは、これらの構造体の配列のアライメント制約を満たすために追加されます。

もう一つ注目すべき点は、構造体型に__attribute__((packed))を適用する方法です。これはGCC固有の属性で、コンパイラに構造体内部にパディングを挿入しないように指示します。Cの構造体を、固定の並びで取得されるデータを表現する際に有用です。

この属性の使用が、アーキテクチャのアライメント要件を満たさないフィールドにアクセスする際に未アライメントアクセスを引き起こす可能性があると考えられるかもしれません。しかし、コンパイラはアライメント制約を把握しており、メモリアクセスを未アライメントアクセスを引き起こさない方法で実行するための追加のインストラクションを生成します。ただし、この追加のインストラクションはパッケージ化されていない場合に比べてパフォーマンス低下を引き起こすため、パッケージ化属性は構造体パディングを回避する必要性が高いためにのみ使用すべきです。

未アライメントアクセスを引き起こすコード¶

上述のことを踏まえ、未アライメントメモリアクセスを引き起こす関数の現実的な例に移ります。次の関数は、include/linux/etherdevice.hから取得され、2つのイーサネットMACアドレスの等価性を比較するための最適化されたルーチンです：

bool ether_addr_equal(const u8 *addr1, const u8 *addr2)
{
#ifdef CONFIG_HAVE_EFFICIENT_UNALIGNED_ACCESS
      u32 fold = ((*(const u32 *)addr1) ^ (*(const u32 *)addr2)) |
                 ((*(const u16 *)(addr1 + 4)) ^ (*(const u16 *)(addr2 + 4)));

      return fold == 0;
#else
      const u16 *a = (const u16 *)addr1;
      const u16 *b = (const u16 *)addr2;
      return ((a[0] ^ b[0]) | (a[1] ^ b[1]) | (a[2] ^ b[2])) == 0;
#endif
}

上記の関数では、ハードウェアが効率的な未アライメントアクセスをサポートしている場合、このコードには問題はありません。しかし、ハードウェアが任意の境界でのメモリアクセスをサポートしていない場合、a[0]への参照はaddr1アドレスから2バイト（16ビット）のデータを読み込むことになります。

addr1が奇数アドレス（例：0x10003）だった場合に何が起こるか想像してください。（ヒント：これは未アライメントアクセスです。）

上記の関数における潜在的な未アライメントアクセスの問題にもかかわらず、この関数はカーネルに含まれていますが、16ビットアライメントアドレスでのみ正常に動作すると理解されています。このアライメント不安全な関数は、アライメントを確保する場合にのみ使用するか、呼び出し元がアライメントを確保する責任を負う必要があります。この関数は、イーサネットネットワーキングの文脈ではほぼ常にアライメントが確保されるため、十分な最適化として依然として有用です。

未アライメントアクセスを引き起こす可能性のあるコードのもう一つの例は以下の通りです：

void myfunc(u8 *data, u32 value)
{
        [...]
        *((u32 *) data) = cpu_to_le32(value);
        [...]
}

このコードは、dataパラメータが4で割り切れないアドレスを指しているたびに未アライメントアクセスを引き起こします。

まとめると、未アライメントアクセスの問題が発生する2つの主なシナリオは以下の通りです：

  1. 変数を長さの異なる型にキャストする

  2. ポインタ算術の後、少なくとも2バイトのデータへのアクセス

未アライメントアクセスを避ける¶

未アライメントアクセスを避ける最も簡単な方法は、<asm/unaligned.h>ヘッダーファイルで提供されているget_unaligned()とput_unaligned()マクロを使用することです。

未アライメントアクセスを引き起こす可能性のあるコードの以前の例に戻ります

void myfunc(u8 *data, u32 value)
{
        [...]
        *((u32 *) data) = cpu_to_le32(value);
        [...]
}

未アライメントメモリアクセスを避けるために、以下のように再構成します

void myfunc(u8 *data, u32 value)
{
        [...]
        value = cpu_to_le32(value);
        put_unaligned(value, (u32 *) data);
        [...]
}

dataがメモリへのポインタであると仮定し、未アライメントアクセスを避けるためにその使用方法は以下の通りです

u32 value = get_unaligned((u32 *) data);

これらのマクロは、メモリアクセスの長さに関係なく（上記の例のように32ビットに限らない）動作します。ただし、標準的なアライメントメモリアクセスと比較して、これらのマクロを使用して未アライメントメモリにアクセスすると、パフォーマンスにコストがかかる可能性があります。

このようなマクロの使用が不便な場合、別のオプションとして memcpy(), ソースまたは宛先（または両方）がu8*またはunsigned char*型である場合。この操作はバイト単位で行われるため、未アライメントアクセスは避けられます。

アライメント vs. ネットワーク¶

アライメントされたロードを必要とするアーキテクチャでは、ネットワークのためにはIPヘッダーが4バイト境界にアライメントされている必要があります。通常のイーサネットハードウェアでは、NET_IP_ALIGN定数が使用されます。ほとんどのアーキテクチャではこの定数は2に設定されており、通常のイーサネットヘッダーは14バイト長いため、適切なアライメントを得るためにDMAを4*n + 2のアドレスに実行する必要があります。ここでの例外はpowerpcで、NET_IP_ALIGNを0に定義しています。これはDMAを未アライメントアドレスに実行するコストが非常に高く、未アライメントロードのコストを上回るためです。

DMAを未アライメントアドレス（4*n+2や非イーサネットハードウェア）に実行できない一部のイーサネットハードウェアでは、この問題が生じるため、受信フレームをアライメントされたバッファにコピーする必要があります。これは未アライメントアクセスが可能であるアーキテクチャでは不要なため、コードはCONFIG_HAVE_EFFICIENT_UNALIGNED_ACCESSに依存するようにできます。

#ifdef CONFIG_HAVE_EFFICIENT_UNALIGNED_ACCESS
        skb = original skb
#else
        skb = copy skb
#endif

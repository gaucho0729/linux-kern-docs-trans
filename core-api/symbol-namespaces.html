シンボルネームスペース¶

以下のドキュメントは、Symbol Namespacesを使用して、 EXPORT_SYMBOL()マクロファミリを通じてエクスポートされる内蔵シンボルのエクスポート表面を構造化する方法について説明しています。

1. はじめに¶

Symbol Namespacesは、内蔵APIのエクスポート表面を構造化するための手段として導入されました。これにより、サブシステムメンテナはエクスポートされたシンボルを別個の名前空間に分割できます。これはドキュメンテーションの目的（SUBSYSTEM_DEBUG名前空間を思い浮かべてください）だけでなく、他のカーネル部分でのシンボルの利用を制限するためにも有用です。今日まで、名前空間にエクスポートされたシンボルを使用するモジュールは、その名前空間をインポートする必要があります。それ以外の場合、カーネルは構成に応じてモジュールのロードを拒否するか、インポートが不足していることを警告します。

2. シンボル名前空間の定義方法¶

シンボルは、さまざまな方法で名前空間にエクスポートできます。すべての方法は、 EXPORT_SYMBOLおよび関連するマクロのインストルメンテーション方法を変更してksymtabエントリを作成します。

2.1 EXPORT_SYMBOLマクロの使用¶

EXPORT_SYMBOL()および EXPORT_SYMBOL_GPL()マクロに加えて、これらを変種として、特定の名前空間にシンボルをエクスポートするための EXPORT_SYMBOL_NS()および EXPORT_SYMBOL_NS_GPL()が利用可能です。これらは追加の引数として名前空間を1つ受け取ります。注意点として、マクロ展開のため、この引数はプリプロセッサシンボルである必要があります。例えば、シンボル usb_stor_suspend を名前空間 USB_STORAGEにエクスポートするには、次のようにします：

EXPORT_SYMBOL_NS(usb_stor_suspend, USB_STORAGE);

対応するksymtabエントリ構造体 kernel_symbol はメンバー ネームスペース が適切に設定されます。名前空間を指定せずにエクスポートされたシンボルは、 NULL. どの名前空間も定義されていない場合、デフォルトの名前空間はありません。 modpost および kernel/module.c は、ビルド時またはモジュールロード時に名前空間を使用します。

2.2 DEFAULT_SYMBOL_NAMESPACE定義の使用¶

サブシステムのすべてのシンボルに対して名前空間を定義することは非常に冗長で、維持が難しくなる可能性があります。そのため、 DEFAULT_SYMBOL_NAMESPACEというデフォルト定義が提供されています。この定義が設定されている場合、 EXPORT_SYMBOL()および EXPORT_SYMBOL_GPL()マクロ展開のデフォルトとして使用されます（名前空間を指定しない場合）。

この定義を指定する方法は複数ありますが、サブシステムやメンテナの好みによってどの方法を使うか異なります。最初のオプションは、 Makefile サブシステムの。例えば、usb-commonで定義されたすべてのシンボルをUSB_COMMONという名前空間にエクスポートするには、drivers/usb/common/Makefileに以下のような行を追加します:

ccflags-y += -DDEFAULT_SYMBOL_NAMESPACE=USB_COMMON

これはすべてのEXPORT_SYMBOL()およびEXPORT_SYMBOL_GPL()ステートメントに影響します。この定義が存在する場合、EXPORT_SYMBOL_NS()でエクスポートされたシンボルは、namespace引数として渡された名前空間にエクスポートされ、この引数がデフォルトのシンボル名前空間よりも優先されます。

デフォルトの名前空間を定義するもう一つのオプションは、コンパイル単位内でプリプロセッサステートメントとして直接定義することです。この場合、上の例は以下のようになります:

#undef  DEFAULT_SYMBOL_NAMESPACE
#define DEFAULT_SYMBOL_NAMESPACE USB_COMMON

どのEXPORT_SYMBOLマクロも使用される前に、対応するコンパイル単位内で実施します。

3. 名前空間にエクスポートされたシンボルの使用方法¶

名前空間にエクスポートされたシンボルを使用するには、カーネルモジュールがこれらの名前空間を明示的にインポートする必要があります。それ以外の場合、カーネルがモジュールのロードを拒否する可能性があります。モジュールコードは、使用する名前空間に対してMODULE_IMPORT_NSマクロを使用する必要があります。例えば、上記のusb_stor_suspendシンボルを使用するモジュールは、以下のステートメントで名前空間USB_STORAGEをインポートする必要があります:

MODULE_IMPORT_NS(USB_STORAGE);

これにより、 modinfo タグが各インポートされた名前空間に対してモジュールに作成されます。これは、modinfoを使用してモジュールのインポートされた名前空間を確認できる副作用があります:

$ modinfo drivers/usb/storage/ums-karma.ko
[...]
import_ns:      USB_STORAGE
[...]

モジュールのインポートされた名前空間を確認するためには、MODULE_IMPORT_NS()ステートメントをMODULE_AUTHOR()やMODULE_LICENSE()などの他のモジュールメタデータ定義に近い位置に追加することをお勧めします。セクション5を参照してください。自動で欠落したインポートステートメントを生成する方法について説明しています。

4. 名前空間シンボルを使用するモジュールのロード¶

モジュールロード時（例: insmod）に、カーネルはモジュールから参照されるすべてのシンボルの利用可能性と、モジュールがインポートした名前空間がエクスポートされた名前空間かどうかを確認します。カーネルのデフォルト動作は、十分なインポートを指定していないモジュールのロードを拒否することです。エラーがログに記録され、EINVALでロードが失敗します。モジュールがこの前提条件を満たしていない場合でもロードを許可するには、設定オプションを有効化します：MODULE_ALLOW_MISSING_NAMESPACE_IMPORTS=yを設定すると、ロードを許可しますが、警告を出力します。

5. MODULE_IMPORT_NSステートメントの自動生成¶

ビルド時に簡単に検出できます。実際、modpostは、モジュールが名前空間からシンボルを使用しているがそれをインポートしていない場合、警告を出します。MODULE_IMPORT_NS()ステートメントは通常、他のモジュールメタデータとともに明確な場所に追加されます。モジュール作成者（およびサブシステムメンテナ）の作業をより簡単にするため、修正用のスクリプトとmakeターゲットが利用可能です。欠落しているインポートを修正するには以下のコマンドを使用します。

$ make nsdeps

モジュール作成者が直面する典型的なシナリオは以下の通りです：

- write code that depends on a symbol from a not imported namespace
- `make`
- notice the warning of modpost telling about a missing import
- run `make nsdeps` to add the import to the correct code location

サブシステムメンテナが名前空間を導入する際の手順は非常に類似しています。また、 make nsdeps は最終的にイン・ツリーのモジュールの欠落している名前空間インポートを追加します：

- move or add symbols to a namespace (e.g. with EXPORT_SYMBOL_NS())
- `make` (preferably with an allmodconfig to cover all in-kernel
  modules)
- notice the warning of modpost telling about a missing import
- run `make nsdeps` to add the import to the correct code location

外部モジュールビルドにもnsdepsを実行できます。典型的な使用例は以下の通りです：

$ make -C <path_to_kernel_src> M=$PWD nsdeps

errseq_t データ型¶

errseq_t は、エラーを1か所に記録し、任意の数の「サブスクライバー」がその値が以前にサンプリングした時点から変更されているかを確認できるようにする仕組みです。

この機能の初期用途は、ファイル同期システムコール（fsync、fdatasync、msync および sync_file_range）のエラーを追跡することですが、他の状況でも利用可能です。

errseq_t は符号なしの32ビット値として実装されています。低位ビットはエラーコード（1〜MAX_ERRNO）を保持し、高位ビットはカウンタとして使用されます。これにより、ロックを使わずアトミック操作で実装されており、どのコンテキストからでも呼び出せます。

新しいエラーが頻繁に記録される場合、カウンタに使用するビット数が少なくため、衝突のリスクがあることに注意してください。

これを緩和するため、エラーコードとカウンタの間にあるビットをフラグとして使用し、新しい値が記録された後でサンプリングされたかを判定します。これにより、最後にエラーが記録された後で誰もサンプリングしていない場合、カウンタをインクリメントしないことが可能になります。

「ウォッチャー」は errseq_t の値をサンプリングし、それを継続的に参照するカーソルとして保持します。この値は、サンプリング後新たにエラーが発生したかを確認するためのものであり、確認時に状態をアトミックに記録できます。これにより、エラーを1か所に記録し、複数の「ウォッチャー」が最後に確認した時点からの変更を検出できるようになります。

errseq_t は常にゼロに初期化する必要があります。すべてのビットがゼロの値は、エラーが一度も発生していないという特別（ただし一般的な）ケースです。すべてゼロの値は、エラーが最初に初期化された後で設定されたかを確認するための「エポック」として機能します。

APIの使用方法¶

ここで、ワーカードローンの物語を紹介します。彼は全体的に優れた労働者ですが、会社は少し…管理が過剰です。今日は77人の上司に報告しなければならず、明日は遠方からやってくる「大ボス」が来るので、彼をテストするつもりです。

すべての上司が彼に仕事を割り当てています。彼にはどれが誰から渡されたかを把握するほど多くの仕事があり、それ自体は大きな問題ではありません。上司たちは、これまでに渡されたすべての仕事を終えたか、そして最後に尋ねた後でエラーが発生したかを知りたいだけです。

彼が実際に渡された仕事で間違いを犯した可能性はあるが、そのレベルの詳細な記録を保つことはできない。彼が覚えているのは、自分がこれまでに犯した最新のミスだけだ。

こちらがworker_droneの表現だ：

struct worker_drone {
        errseq_t        wd_err; /* for recording errors */
};

毎日、worker_droneは空白の状態から始まる：

struct worker_drone wd;

wd.wd_err = (errseq_t)0;

管理者たちは朝から最初の評価を取ってくる。彼らは、自分の監督が始まる前の出来事には関心を持たない：

struct supervisor {
        errseq_t        s_wd_err; /* private "cursor" for wd_err */
        spinlock_t      s_wd_err_lock; /* protects s_wd_err */
}

struct supervisor       su;

su.s_wd_err = errseq_sample(&wd.wd_err);
spin_lock_init(&su.s_wd_err_lock);

それから彼に仕事を渡し始める。数分ごとにこれまで渡した仕事をすべて終わらせたか尋ねる。そして、その中で間違いがあったか確認する：

spin_lock(&su.su_wd_err_lock);
err = errseq_check_and_advance(&wd.wd_err, &su.s_wd_err);
spin_unlock(&su.su_wd_err_lock);

これまでのところ、この値は常に0を返している。

この会社の所有者は小細かいことでは節約志向で、彼に使う機材を劣化させている。たまに故障してミスを起こす。彼は重いため息をつき、それを記録する：

errseq_set(&wd.wd_err, -EIO);

…そして作業に戻る。管理者たちは最終的に再確認し、次にチェックするときにそのエラーを知る。その後の呼び出しでは0が返されるが、新たなエラーが記録された時点で再び報告される。

管理者たちは彼がどれだけミスをしたかを知ることはできない。彼らが最後にチェックした後でミスが起きたかどうか、そして最新の記録値のみを知る。

たまに大統領がスポットチェックをして、workerに一時的な作業をさせる。監督のようにworkerをフルタイムで見守るわけではないが、その作業中にミスが起きていないか確認する必要がある。

彼は単にworkerの現在のerrseq_tをサンプリングし、その後でその時点でエラーが起きていないかを判断できる：

errseq_t since = errseq_sample(&wd.wd_err);
/* submit some work and wait for it to complete */
err = errseq_check(&wd.wd_err, since);

その後で「since」を捨てることになるので、ここでカーソルを進める必要はない。また、他の誰も使用しないのでロックは必要ない。

errseq_tカーソルの更新をシリアル化する¶

errseq_t APIは、check_and_advance_operation中にerrseq_tカーソルを保護していない。しかしここでは正規のエラーコードのみがアトミックに処理される。複数のタスクが同時に同じerrseq_tカーソルを使用する可能性がある場合、そのカーソルの更新をシリアル化することが重要である。

これを実施しないと、カーソルが逆戻りする可能性があり、同じエラーが複数回報告される可能性がある。

このような理由から、まずerrseq_checkで変化があるか確認し、その後でロックを取得した後にerrseq_check_and_advanceを行うのが一般的に有利である。例：

if (errseq_check(&wd.wd_err, READ_ONCE(su.s_wd_err)) {
        /* su.s_wd_err is protected by s_wd_err_lock */
        spin_lock(&su.s_wd_err_lock);
        err = errseq_check_and_advance(&wd.wd_err, &su.s_wd_err);
        spin_unlock(&su.s_wd_err_lock);
}

最後にチェックしたときから何も変化していない一般的なケースでは、スピンロックを回避します。

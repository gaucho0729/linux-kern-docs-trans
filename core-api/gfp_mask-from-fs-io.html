FS/IOコンテキストから使用されるGFPマスク¶

日付

2018年5月

著者

Michal Hocko <mhocko@kernel.org>

はじめに¶

ファイルシステムとIOスタック内のコードパスは、メモリを割り当てる際には再帰的なデッドロックを防ぐために注意が必要です。これは直接的なメモリ回収がFSやIOパスに戻って呼び出され、既に保持しているリソース（例：ロック - 特にトランザクションコンテキストで使用されるロック）にブロックされるためです。

このデッドロック問題を回避する伝統的な方法は、アロケータを呼び出す際のgfpマスクから__GFP_FSをそれぞれ__GFP_IOをクリアすることです（後者は前者も自動的にクリアします）。GFP_NOFSまたはGFP_NOIOをショートカットとして使用できます。しかし、このアプローチは制限されたgfpマスクを「あえて」使用する場合に悪用されることが判明し、深い検討なしに「万一」に備えて使用すると、メモリの過剰な回収や他のメモリ回収問題を引き起こす可能性があります。

新しいAPI¶

4.12以降、NOFSおよびNOIOコンテキストのための汎用スコープAPIがあります memalloc_nofs_save, memalloc_nofs_restore それぞれ memalloc_noio_save, memalloc_noio_restore これはファイルシステムやI/Oの観点からクリティカルセクションとしてマークするためのスコープであり、このスコープからの割り当ては自動的に__GFP_FSまたは__GFP_IOをマスクから削除するため、FS/IOからの再帰的な割り当てが発生しません。

unsigned int memalloc_nofs_save(void)¶

GFP_NOFS割当スコープを暗黙的にマークします。

パラメータ

void

引数なし

説明

この関数はGFP_NOFS割当スコープの開始を示します。以降の割り当てはすべて__GFP_FSフラグを自動的に削除し、割り当て再帰の観点からFSのクリティカルセクションに対して安全です。memalloc_nofs_restoreを使用してスコープを終了し、この関数が返すフラグを元に戻します。

この関数は任意のコンテキストから安全に使用できます。

void memalloc_nofs_restore(unsigned int フラグ)¶

暗黙的なGFP_NOFSスコープを終了します。

パラメータ

unsigned int flags

復元するフラグ。

説明

memalloc_nofs_save関数で開始された暗黙的なGFP_NOFSスコープを終了します。常に与えられたフラグがペアリングされたmemalloc_nofs_save呼び出しの返値であることを確認してください。

パラメータ

void

引数なし

説明

この関数はGFP_NOIO割当スコープの開始を示します。以降の割り当てはすべて__GFP_IOフラグを自動的に削除し、割り当て再帰の観点からIOのクリティカルセクションに対して安全です。memalloc_noio_restoreを使用してスコープを終了し、この関数が返すフラグを元に戻します。

この関数は任意のコンテキストから安全に使用できます。

void memalloc_noio_restore(unsigned int フラグ)¶

暗黙的なGFP_NOIOスコープを終了します。

パラメータ

unsigned int flags

復元するフラグ。

説明

memalloc_noio_save関数で開始された暗黙的なGFP_NOIOスコープを終了します。常に与えられたフラグがペアリングされたmemalloc_noio_save呼び出しの返値であることを確認してください。

FS/IOコードは、リカレント処理に関連するクリティカルセクションが始まる前に適切なセーブ関数を呼び出します。たとえば、リカレントコンテキストと共有されるロックや、リカレントを通じたトランザクションコンテキストのネスティングが可能になる場合などです。クリティカルセクションが終了したときに復元関数を呼び出す必要があります。理想的には、リカレントコンテキストの説明を含めて、メンテナンスが容易になるようにしてください。

保存/復元関数の適切なペアリングによりネスティングが可能なので、安全に呼び出すことが可能です。 memalloc_noio_save または memalloc_noio_restore 既存のNOIOまたはNOFSスコープからそれぞれ呼び出すことができます。

What about __vmalloc(GFP_NOFS)¶

vmallocはGFP_NOFSセマンティクスをサポートしていません。これは、アロケータ内部にハードコードされたGFP_KERNELの割当があり、修正が非現実的なためです。つまり、GFP_NOFS/GFP_NOIOを指定して呼び出すことはほぼ常にバグです。 vmalloc 良いニュースは、NOFS/NOIOセマンティクスはスコープAPIを通じて達成可能ということです。

理想的な世界では、上位レイヤーがすでに危険なコンテキストをマークしているため、特別な処置は必要なく、vmallocは問題なく呼び出すことができます。ただし、コンテキストが明確でない場合やレイヤー違反がある場合は、スコープAPIで囲み、問題の説明コメントを追加するのが推奨されます。 vmalloc スコープAPIで囲み、問題の説明コメントを追加するのが推奨されます。

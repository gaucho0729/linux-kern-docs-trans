トランザクショナルメモリのサポート¶

POWER カーネルでのこの機能のサポートは、現在ユーザーのプログラムでの使用をサポートするだけです。カーネル自身は現在この機能を使用していません。

このファイルは、Linux がこの機能をどのようにサポートしているか、およびユーザーのプログラムが期待できる動作についてまとめています。

基本概要¶

ハードウェアトランザクショナルメモリは POWER8 プロセッサでサポートされており、異なる形式のアトミックなメモリアクセスを可能にする機能です。トランザクションの境界を定義する新しい複数の命令が導入され、トランザクションは、他のトランザクショナルまたは非トランザクショナルアクセスと競合がない場合にのみ一括して完了するか、ロールバックして部分的な変更を元に戻します。

シンプルなトランザクションは次のようになります：

begin_move_money:
  tbegin
  beq   abort_handler

  ld    r4, SAVINGS_ACCT(r3)
  ld    r5, CURRENT_ACCT(r3)
  subi  r5, r5, 1
  addi  r4, r4, 1
  std   r4, SAVINGS_ACCT(r3)
  std   r5, CURRENT_ACCT(r3)

  tend

  b     continue

abort_handler:
  ... test for odd failures ...

  /* Retry the transaction if it failed because it conflicted with
   * someone else: */
  b     begin_move_money

「tbegin」命令はトランザクションの開始点を示し、「tend」は終了点を示します。これらの点の間ではプロセッサは「トランザクショナル」状態にあり、システム内での他のトランザクショナルまたは非トランザクショナルアクセスと競合がない場合、メモリ参照は一括して完了します。この例では、他のプロセッサが SAVINGS_ACCT(r3) または CURRENT_ACCT(r3) にアクセスしていない場合、通常のストレートコードのようにトランザクションが完了し、現在の口座から貯金口座への金額のアトミックな移動が実行されます。通常の ld/std 命令（lwarx/stwcx ではなく）が使用されているにもかかわらず、 両方を組み合わせます SAVINGS_ACCT(r3) と CURRENT_ACCT(r3) はどちらも更新されるか、どちらも更新されません。

トランザクションが実行中にアクセスしている場所と競合が発生した場合、CPU がトランザクションを中止します。レジスタおよびメモリ状態は「tbegin」時点に戻され、制御は「tbegin+4」から継続します。アボートハンドラへの分岐が再度実行され、アボートハンドラは失敗の原因を確認し、再試行できます。

チェックポイントされたレジスタにはすべての GPRs、FPRs、VRs/VSRs、LR、CCR/CR、CTR、FPCSR およびいくつかのその他のステータス/フラグレジスタが含まれます。詳細については ISA を参照してください。

トランザクションアボートの原因¶

  • 他のプロセッサが使用するキャッシュラインとの競合

  • シグナル

  • コンテキストスイッチ

  • トランザクションを中止するすべての要因については ISA を参照してください。

システムコール¶

アクティブなトランザクション内からシステムコールが呼び出されると、システムコールは実行されず、カーネルが TM_CAUSE_SYSCALL | TM_CAUSE_PERSISTENT の失敗コードでトランザクションを破棄します。

スリープ中のトランザクション内で実行されるシステムコールは通常通り行われ、カーネルによって明示的に失敗（doomed）されることはありません。ただし、カーネルがシステムコールを実行する際に行う処理が、ハードウェアによってトランザクションが失敗（doomed）される可能性があります。システムコールはスリープモードで実行されるため、副作用はトランザクションの成功や失敗に関係なく永続的になります。カーネルはどのシステムコールがトランザクションの成功に影響を与えるかについて保証は提供しません。

アクティブなトランザクション中にシステムコールが実行され、その結果トランザクションが中止されることが依存している場合、ライブラリ経由で呼び出す際には注意が必要です。ライブラリは値をキャッシュする（成功の見せかけになる可能性がある）か、カーネルに入る前にトランザクションの失敗を引き起こす操作を行うことがあります（異なる失敗コードを生成する可能性がある）。例として、glibcのgetpid()やラズィーなシンボル解決が挙げられます。

シグナル¶

トランザクション中にシグナル（同期・非同期を問わず）が届くと、2番目のスレッド状態（ucontext/mcontext）がトランザクションのレジスタ状態を表します。シグナルの配信は「treclaim」によって両方のレジスタ状態をキャプチャするため、シグナルはトランザクションを中止します。通常のucontext_tはシグナルハンドラに渡され、チェックポイントされた/元のレジスタ状態を表します。シグナルは「tbegin+4」で発生したように見えます。

sighandlerのucontextがuc_linkが設定されている場合、2番目のucontextが配信されています。将来の互換性を考慮し、MSR.TSフィールドを確認してトランザクショナルな状態を判定する必要があります。MSR.TSフィールドが設定されている場合、uc->uc_link内の2番目のucontextはシグナル発生時のアクティブなトランザクショナルなレジスタを表します。

64ビットプロセスの場合、uc->uc_mcontext.regs->msrは完全な64ビットのMSRであり、TSフィールドがトランザクショナルなモードを示します。

32ビットプロセスの場合、mcontextのMSRレジスタは32ビットのみで、上位32ビットは2番目のucontextのMSRに格納されます。つまり、uc->uc_link->uc_mcontext.regs->msrに保存され、上位ワードにはトランザクショナルな状態TSが含まれます。

ただし、基本的なシグナルハンドラはトランザクションを意識する必要がなく、ハンドラからただ戻すだけで問題は正しく処理されます。

トランザクションを意識したシグナルハンドラは、2番目のucontextからトランザクショナルなレジスタ状態を読み取ることができます。これは、たとえばSIGSEGVの原因となった命令のアドレスを特定するためにクラッシュハンドラが行う必要があります。

シグナルハンドラの例:

  void crash_handler(int sig, siginfo_t *si, void *uc)
  {
    ucontext_t *ucp = uc;
    ucontext_t *transactional_ucp = ucp->uc_link;

    if (ucp_link) {
      u64 msr = ucp->uc_mcontext.regs->msr;
      /* May have transactional ucontext! */
#ifndef __powerpc64__
      msr |= ((u64)transactional_ucp->uc_mcontext.regs->msr) << 32;
#endif
      if (MSR_TM_ACTIVE(msr)) {
         /* Yes, we crashed during a transaction.  Oops. */
 fprintf(stderr, "Transaction to be restarted at 0x%llx, but "
                         "crashy instruction was at 0x%llx\n",
                         ucp->uc_mcontext.regs->nip,
                         transactional_ucp->uc_mcontext.regs->nip);
      }
    }

    fix_the_problem(ucp->dar);
  }

アクティブなトランザクション内でシグナルを取得する際、スタックの扱いには注意が必要です。tbeginの後でスタックが戻っている可能性があります。典型的なケースは、tbeginが関数内で呼び出され、tendよりも前に戻る場合です。この場合、スタックはチェックポイントされたトランザクショナルメモリ状態の一部です。トランザクショナルにない状態でこのスタックを上書きしたり、一時停止中に上書きすると、tm abortが発生した際にプログラムカウンターやスタックポインタがtbeginに戻る一方で、メモリ内のスタックが無効になるため、問題が発生します。

このような問題を回避するため、アクティブなトランザクション内でシグナルを取得する際は、チェックポイントされた状態のスタックポインタを使用する必要があります。これにより、シグナルコンテキスト（tm一時停止中に書かれたもの）がロールバックに必要なスタックよりも下に書かれるため、トランザクションはtreclaimのため中止されます。したがって、tbeginとシグナルの間に書かれたメモリは自動的にロールバックされます。

非TMモードまたは一時停止モードで取得されたシグナルについては、通常の/チェックポイントされていないスタックポインタを使用します。

シグナルハンドラ内で開始され、シグナルハンドラからカーネルに戻る際の一時停止中に起動されたトランザクションは、再取得され削除されます。

カーネルが使用する失敗原因コード¶

<asm/reg.h>で定義されており、カーネルがトランザクションを中止した理由を区別しています。

TM_CAUSE_RESCHED

スレッドが再スケジューリングされました。

TM_CAUSE_TLBI

ソフトウェアTLB無効。

TM_CAUSE_FAC_UNAV

FP/VEC/VSX利用不可トラップ。

TM_CAUSE_SYSCALL

アクティブなトランザクションからのシステムコール。

TM_CAUSE_SIGNAL

シグナルが届けられました。

TM_CAUSE_MISC

現在は使用されていません。

TM_CAUSE_ALIGNMENT

アライメントエラー。

TM_CAUSE_EMULATE

メモリにアクセスするエミュレーション。

これらはユーザープログラムの中止ハンドラでTEXASR[0:7]として確認できます。ビット7が設定されている場合、エラーが永続的なものとみなされます。たとえばTM_CAUSE_ALIGNMENTは永続的ですが、TM_CAUSE_RESCHEDはそうではありません。

GDB¶

GDBとptraceは現在TMを意識していません。トランザクション中に停止すると、トランザクションが開始したかのように見えます（チェックポイントされた状態が表示されます）。その後、トランザクションを再開できず、失敗ハンドラの処理に進みます。さらに、トランザクショナルな2番目のレジスタ状態はアクセスできません。GDBはTMを使用するプログラムに現在は使用できますが、トランザクション内では適切ではありません。

POWER9¶

POWER9のTMではレジスタ状態を完全に保存する問題があります。これはこのコミットで説明されています：

commit 4bb3c7a0208fc13ca70598efd109901a7cd45ae7
Author: Paul Mackerras <paulus@ozlabs.org>
Date:   Wed Mar 21 21:32:01 2018 +1100
KVM: PPC: Book3S HV: Work around transactional memory bugs in POWER9

この違いを考慮し、POWER9のチップによってTMが有効化される方法が異なります。

POWER9N DD2.01以下の場合はTMが無効になっています。つまりHWCAP2[PPC_FEATURE2_HTM]は設定されていません。

POWER9N DD2.1ではファームウェアがTMを常にトランザクションの中断時に中断するように構成しています。そのためtsuspendが発生するとトランザクションが中断されロールバックされます。カーネル例外もトランザクションを中断・ロールバックさせ、例外は発生しなくなります。ユーザースペースでsigcontextを構築してTMスリープを有効化すると、カーネルがsigcontextを拒否します。このモードはHWCAP2[PPC_FEATURE2_HTM_NO_SUSPEND]が設定されているユーザーに宣伝されます。このモードではHWCAP2[PPC_FEATURE2_HTM]は設定されていません。

POWER9N DD2.2以上ではKVMおよびPOWERVMがゲストに対してTMをエミュレートします（commit 4bb3c7a0208fに記載されている通り）。そのためゲストではTMが有効になります。つまりHWCAP2[PPC_FEATURE2_HTM]がゲストユーザースペースで設定されます。ゲストがTMスリープ（tsuspendまたはカーネルスリープ）を重く使用するとハイパーコアへのトラップが発生し、パフォーマンスの低下が生じます。ホストユーザースペースではTMが無効になっています（HWCAP2[PPC_FEATURE2_HTM]は設定されていません）。ただし将来、エミュレーションをホストユーザースペースコンテキストスイッチングに導入する場合にTMを有効化する予定です。

POWER9C DD1.2以上はPOWERVMのみで利用可能であり、Linuxはゲストとしてのみ動作します。これらのシステムではPOWER9N DD2.2と同様にTMがエミュレートされます。

POWER8からPOWER9へのゲスト移行はPOWER9N DD2.2およびPOWER9C DD1.2で動作します。ただし以前のPOWER9プロセッサはTMエミュレーションをサポートしていないため、POWER8からPOWER9への移行はサポートされていません。

カーネルの実装¶

h/rfid mtmsrd クイック¶

ISAで定義されているrfidには、早期例外処理で有用なクイックがあります。ユーザースペースのトランザクション中に例外を通じてカーネルに移行するとMSRはTM=0かつTS=01（つまりTMがオフだがTMスリープ中）になります。通常、カーネルはMSRのビットを変更し、rfidを実行します。この場合rfidはSRR0 TM=0かつTS=00（つまりTMオフでトランザクションなし）になり、結果としてMSRは以前のTM=0かつTS=01（つまりスリープ状態）を保持します。これはアーキテクチャのクイックであり、通常TS=01からTS=00への移行（つまりスリープ→非トランザクション）は不正な移行です。

このクイックはアーキテクチャのrfidの定義で以下のように説明されています：

if (MSR 29:31 ¬ = 0b010 | SRR1 29:31 ¬ = 0b000) ならば

MSR 29:31 <- SRR1 29:31

hrfid と mtmsrd は同じクイックを持っています。

Linux カーネルはこのクイックを早期の例外処理で使用しています。

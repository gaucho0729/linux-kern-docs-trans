Powerenv 上の PCI Express I/O ビジュー化リソース¶

Wei Yang <weiyang@linux.vnet.ibm.com>

Benjamin Herrenschmidt <benh@au1.ibm.com>

Bjorn Helgaas <bhelgaas@google.com>

26 Aug 2014

このドキュメントでは、PowerKVMにおけるPCI MMIOリソースのサイズ指定と割り当てに必要なハードウェアの要件と、汎用PCIコードがこの要件をどのように処理するかについて説明します。最初の2節では、Partitionable Endpoint（PE）の概念とP8（IODA2）での実装について説明します。次の2節では、IODA2でSRIOVを有効化する際の考慮点について述べます。

1. Partitionable Endpointの導入¶

Partitionable Endpoint（PE）は、デバイスまたは複数のデバイスに関連する各種リソースをグループ化して、パーティション間の隔離（DMAやMSIなどのフィルタリング）を提供し、エラーを引き起こしているデバイスを凍結して悪影響の拡散を制限するメカニズムを提供する方法です。

ハードウェアでは、PEの状態を表すテーブルがあり、各PEに対して「凍結」状態ビット（MMIO用とDMA用のペア、設定は同時にされますが個別にクリア可能です）が含まれています。

PEが凍結すると、すべてのストア（任意の方向）が無視され、すべてのロードはすべて1の値を返します。MSIもブロックされます。エラーの詳細などの追加状態が含まれますが、これは重要ではありません。

注目すべき点は、さまざまなPCIeトランザクション（MMIO、DMAなど）がそれぞれのPEにどのようにマッチされるかです。

次の節ではP8（IODA2）における概要を説明します。注意点として、これはすべてPHB（PCIホストブリッジ）ごとの情報です。各PHBは完全に独立したハードウェアエンティティであり、すべての論理を複製するため、独自のPEセットなどを保有します。

2. P8（IODA2）におけるPartitionable Endpointの実装¶

P8は各PHBあたり最大256のPartitionable Endpointをサポートします。

  • Inbound

    DMA、MSI、およびInbound PCIeエラーメッセージについては、メモリ内に保存されながらチップによってアクセスされるテーブルがあり、PCIe RID（バス/デバイス/ファンクション）とPE番号の直接的な対応関係を提供します。これをRTTと呼びます。

    • DMAについては、各PEに対して完全なアドレス空間を提供し、PCIアドレスビット59の値に応じて2つの「ウィンドウ」を含めることができます。各ウィンドウは「TCEテーブル」（IOMMU翻訳テーブル）を介してリマップ可能であり、ここでは説明しない複数の設定可能な特性を持ちます。

    • MSIについては、アドレス空間内に2つのウィンドウ（32ビット空間の上部と、それよりはるかに高い位置）があり、アドレスとMSI値の組み合わせによって、ブリッジごとに2048つの割込みのうちの1つがトリガーされます。また、割込み制御デスクリプターテーブルにもPE#（プロセッサエンティティ番号）が含まれており、RTTから取得したPE#と比較することで、デバイスが特定の割込みを発生させることが「認可」されます。

    • エラーメッセージはRTTのみを使用します。

  • アウトバウンド。これは複雑な部分です。

    他のPCIホストブリッジと同様に、Power8 IODA2 PHBもCPUアドレス空間からPCIアドレス空間への「ウィンドウ」をサポートしています。1つのM32ウィンドウと16つのM64ウィンドウがあります。これらは異なる特徴を持ちますが、共通点もあります。まず共通点について説明します：CPUアドレス空間の設定可能な一部をPCIeバスに転送し、サイズは自然数の2の累乗でなければならないという点です。それ以外の違いは以下の通りです：

    • M32ウィンドウ：

      • サイズは4GBに制限されています。

      • アドレスの上位ビット（サイズを超えた部分）を切り捨て、設定可能な値に置き換えます。これは通常、32ビットのPCIeアクセスを生成するために使用されます。このウィンドウはブート時にFWで設定し、Linuxでは変更しません。通常はCPUアドレス空間の2GB部分をPCIe 0x8000_0000..0xffff_ffffに転送するように設定されています。（注：上位64KBは実際にはMSI用に予約されていますが、この時点では問題ではありません。Linuxがその領域に割り当てないことを確認するだけで十分です。M32論理はその領域を無視し、必要に応じてその空間に転送します）

      • このウィンドウは256セグメントに均等に分割されます。チップ内のテーブルは各セグメントをPE#にマッピングします。これにより、MMIO空間の一部をセグメント単位でPEに割り当てることができます。2GBのウィンドウの場合、セグメント granularity は2GB/256 = 8MBです。

    これは現在Linuxで使用している「主な」ウィンドウです（SR-IOVを除く）。基本的にブリッジMMIOウィンドウをセグメントアライメント/ granularity に強制的に配置することで、ブリッジの後方の空間をPEに割り当てています。

    理想的にはPE内の個々のファンクションを割り当てたいですが、これには個々のファンクションBARを「1つまたは複数のセグメントに収められるようにグループ化」する新しいアドレス割り当てスキームが必要になります。

    • M64ウィンドウ：

      • サイズは少なくとも256MB以上でなければなりません。

      • アドレスは変換されません（PCIe上のアドレスはPowerBus上のアドレスと同じです）。PowerBusで伝達されない上位14ビットを設定することもできますが、これを使用していません。

      • セグメント化することができる。セグメント化されていない場合、全体のウィンドウに対してPE#を指定することが可能である。セグメント化されている場合、ウィンドウは256セグメントを持つが、セグメントとPE#のマッピングを行うテーブルは存在しない。セグメント番号 通常のRCU読み込み側クリティカルセクションは、条件付きでスリープロックを取得することが許容されます（例として のPE#。

      • 重複をサポートする。あるアドレスが複数のウィンドウによってカバーされている場合、どのウィンドウが適用されるかの定義された順序がある。

    我々は、64ビット空間における大容量BAR（Base Address Register）を扱うために、M32のものと比較して比較的新しいコードを用意している：

    FWがPHB（Physical Host Bridge）に割り当てたアドレス空間全体（約64GB、M32の空間は無視し、別の「reserve」から取得する）をカバーするM64ウィンドウを設定する。このウィンドウはセグメント化されている。

    次に、M32と同じようにブリッジアライメントのトリックを用いて、それらの大容量セグメントにマッチングする。

    再マッピングができないため、追加の制約条件が2つある：

    • PE#の割り当てを行う RCU保護データ構造からデータ要素を削除した後、 64ビット空間が割り当てられたのは、使用するアドレスが直接PE#を決定するためである。その後、32ビットと64ビット空間の両方を用いるデバイスのM32 PE#を更新するか、残りのPE#を32ビット専用デバイスに割り当てる。

    • ハードウェアでセグメントを「グループ化」することはできないため、デバイスが複数のセグメントを使用する場合、複数のPE#が発生する。ハードウェアでは、フリーズ状態が「コンパニオン」PEに連鎖するメカニズムがあるが、これはPCIeエラー通知（通常はスイッチをフリーズするとそのすべての子もフリーズするようにするため）にのみ適用される。そのため、ソフトウェアで実装する。この場合、EEHの効果がやや低下するが、これ以上ないという結論に至った。したがって、どのPEがフリーズしても、その「ドメイン」内の他のPEもフリーズする。このため、「マスターペ」としてDMAやMSIなどに使用されるPEと、「セカンダリPE」として残りのM64セグメントに使用されるPEの概念を導入した。

    さらに、特定のBAR（Base Address Register）にオーバーレイする形で、複数のM64ウィンドウを「単一PEモード」で使用して、一部の問題を回避する方法を検討したい。例えば、非常に大容量のBARを持つデバイス（例：GPU）に対して有効だが、まだ実装していない。

3. PowerKVMにおけるSR-IOVに関する考慮事項¶

  • SR-IOVの背景

    PCIe SR-IOV機能は、1つの物理関数（PF）が複数の仮想関数（VF）をサポートできるようにする。PFのSR-IOV能力レジスタは、VFの数とVFが有効かどうかを制御する。

    VFが有効になると、通常のPCIデバイスのように構成空間に表示されます。ただし、VFの構成空間ヘッダー内のBAR（Base Address Register）は特殊です。非VFデバイスの場合、ソフトウェアは構成空間ヘッダー内のBARを使用してBARのサイズを検出し、アドレスを割り当てます。VFデバイスでは、ソフトウェアはPFのSR-IOV Capability内のVF BARレジスタを使用してサイズを検出し、アドレスを割り当てます。VFの構成空間ヘッダー内のBARは読み取り専用のゼロです。 PF SR-IOV Capabilityを用いてサイズを検出・アドレスを割り当てます。VFの構成空間ヘッダー内のBARは読み取り専用のゼロです。

    PFのSR-IOV CapabilityにVF BARをプログラミングすると、すべての対応するVF(n) BARのベースアドレスを設定します。たとえば、PFのSR-IOV Capabilityが8つのVFを有効にするように設定され、1MBのVF BAR0を有する場合、そのVF BAR内のアドレスは8MB領域のベースを設定します。この領域は8つの連続する1MBの領域に分割され、それぞれが1つのVFのBAR0になります。注意点として、VF BARが8MBの領域を記述しているにもかかわらず、アライメント要件は単一のVF（この例では1MB）に適用されます。

PE内でVFを分離するための戦略はいくつかあります：

  • M32ウィンドウ：1つのM32ウィンドウがあり、256つの等しいサイズのセグメントに分割されます。最も細かい粒度は256MBのウィンドウで1MBのセグメントです。1MB以上のVF BARはこのウィンドウ内で別のPEにマッピングできます。各セグメントは検索テーブルを介して個別にPEにマッピング可能なので、柔軟性がありますが、すべてのVF BARが同じサイズである場合に最適です。サイズが異なる場合、全体のウィンドウは最小のVF BARのセグメントサイズに合わせて小さくする必要があります。つまり、大きなVF BARは複数のセグメントをカバーします。

  • 非セグメント化されたM64ウィンドウ：非セグメント化されたM64ウィンドウは1つのPEに完全にマッピングされるため、1つのVFのみを分離できます。

  • 単一セグメント化されたM64ウィンドウ：セグメント化されたM64ウィンドウはM32ウィンドウと同様に使用できますが、セグメントは個別にPEにマッピングできません（セグメント番号がPE番号になります）。柔軟性が低いため、複数のBARを持つVFは複数のPEの「ドメイン」に配置する必要がありますが、単一のPEに比べて分離度が低くなります。

  • 複数セグメント化されたM64ウィンドウ：通常通り、各ウィンドウは256つの等しいサイズのセグメントに分割され、セグメント番号がPE番号になります。ただし、複数のM64ウィンドウを使用する場合、それぞれのベースアドレスとセグメントサイズを異なる値に設定できます。VFがそれぞれ1MBのBARと32MBのBARを持つ場合、1つのM64ウィンドウで1MBのセグメントを割り当て、別のM64ウィンドウで32MBのセグメントを割り当てることができます。

最後に、次の2つのセクションでより詳しく説明するM64ウィンドウをSR-IOVに利用する計画について述べます。あるVF BARに対して、全体の256セグメント（256 * VF BARサイズ）を効果的に確保し、そのM64ウィンドウ内の空きセグメント/PEの開始位置にVF BARを配置する必要があります。

目標は、もちろん各VFに個別のPEを割り当てるということです。

IODA2プラットフォームは16つのM64ウィンドウを持ち、これらはMMIO範囲をPE#にマッピングするために使用されます。各M64ウィンドウは1つのMMIO範囲を定義し、この範囲は256セグメントに分割され、それぞれのセグメントは1つのPEに対応します。

SR-IOV VF BARはすべて同じサイズであるため、このM64ウィンドウを個々のPEにVFをマッピングするために活用することにしました。

しかし、この方法には別の問題が生じます：total_VFsは通常M64ウィンドウセグメントの数より小さいため、1つのVF BARを1つのM64ウィンドウに直接マッピングすると、他のデバイスのMMIO範囲に一部のM64ウィンドウがマッピングしてしまう可能性があります。

IODAは256つのPEをサポートしており、セグメントされたウィンドウは256セグメントを持ちます。そのため、total_VFsが256未満の場合、図1.0のようにM64ウィンドウのセグメント[total_VFs, 255]が他のデバイスのMMIO範囲にマッピングされる状況が生じます。

0      1                     total_VFs - 1
+------+------+-     -+------+------+
|      |      |  ...  |      |      |
+------+------+-     -+------+------+

                      VF(n) BAR space

0      1                     total_VFs - 1                255
+------+------+-     -+------+------+-      -+------+------+
|      |      |  ...  |      |      |   ...  |      |      |
+------+------+-     -+------+------+-      -+------+------+

                      M64 window

           Figure 1.0 Direct map VF(n) BAR space

現在の解決策は、VF(n) BAR領域がそれほど必要でなくても256セグメントを確保することです（図1.1を参照）：

0      1                     total_VFs - 1                255
+------+------+-     -+------+------+-      -+------+------+
|      |      |  ...  |      |      |   ...  |      |      |
+------+------+-     -+------+------+-      -+------+------+

                      VF(n) BAR space + extra

0      1                     total_VFs - 1                255
+------+------+-     -+------+------+-      -+------+------+
|      |      |  ...  |      |      |   ...  |      |      |
+------+------+-     -+------+------+-      -+------+------+

                      M64 window

           Figure 1.1 Map VF(n) BAR space + extra

余分な領域を確保することで、M64ウィンドウ全体がこのSR-IOVデバイスに割り当てられ、他のデバイスが利用可能な領域は一切ありません。注意点として、この拡張はソフトウェアで確保される領域に限られ、ハードウェアではセグメント[total_VFs, 255]は応答しません。実際には、total_VFsのVFのみがセグメント[0, total_VFs - 1]に応答します。

4. ジェネリックPCIコードへの影響¶

PCIe SR-IOV仕様では、VF(n) BAR領域のベースアドレスが個々のVF BARのサイズに合わせてアライメントされる必要があります。

IODA2では、MMIOアドレスがPE#を決定します。アドレスがM32ウィンドウ内にある場合、セグメントをPE#に変換するテーブルを更新することでPE#を設定できます。同様に、アドレスが未セグメント化されたM64ウィンドウ内にある場合、ウィンドウのPE#を設定できます。ただし、セグメント化されたM64ウィンドウ内にある場合、セグメント番号そのものがPE#になります。

したがって、VFのPE#を制御する唯一の方法は、VF(n) BAR領域のベースアドレスを変更することです。PCIコアがVF(n) BAR領域に必要な正確なサイズを割り当てれば、VF BARの値は固定され変更できません。

一方、PCIコアが追加の領域を割り当てた場合、VF BAR値を変更できるのは、全体のVF(n) BAR領域がコアによって割り当てられた領域内に収まっている限りです。

理想的にはセグメントサイズが個々のVF BARサイズと同じになります。この場合、各VFはそれぞれのPEに配置されます。VF BAR（したがってPE#）は連続します。VF0がPE(x)に配置されている場合、VF(n)はPE(x+n)に配置されます。256セグメントを割り当てた場合、VF0のPE#の選択肢は(256 - numVFs)個になります。

セグメントサイズがVF BARサイズより小さい場合、1つのVF BARをカバーするには複数のセグメントが必要となり、VFは複数のPEにまたがって配置されます。これは可能ですが、分離性が低下し、VF(n) BAR領域が(numVFs * n)セグメントを消費するため、PE#の選択肢が減少します。これにより、VF(n) BAR領域のベース調整に使えるセグメント数が少なくなります。

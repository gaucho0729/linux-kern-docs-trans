コヒーレントアクセラレータインターフェース (CXL)¶

はじめに¶

コヒーレントアクセラレータインターフェースは、FPGAやその他のデバイスをPOWERシステムにコヒーレントに接続できるように設計されています。これらのデバイスは、コヒーレントアクセラレータインターフェースアーキテクチャ（CAIA）に準拠する必要があります。

IBMではこれを「コヒーレントアクセラレータプロセッサインターフェース（CAPI）」と呼んでいます。カーネルでは、ISDN CAPIサブシステムと混乱を避けるため「CXL」として参照されます。

この文脈における「コヒーレント」は、アクセラレータとCPUがともにシステムメモリを直接アクセスでき、同じ有効アドレスでアクセスできるという意味です。

ハードウェア概要¶

  POWER8/9             FPGA
+----------+        +---------+
|          |        |         |
|   CPU    |        |   AFU   |
|          |        |         |
|          |        |         |
|          |        |         |
+----------+        +---------+
|   PHB    |        |         |
|   +------+        |   PSL   |
|   | CAPP |<------>|         |
+---+------+  PCIE  +---------+

POWER8/9チップには、PCIeホストブリッジ（PHB）の一部であるコヒーレントアタッチプロセッサプロキシ（CAPP）ユニットがあります。これはLinuxがOPALへの呼び出しによって管理します。LinuxはCAPPを直接プログラミングしません。

FPGA（またはコヒーレントアタッチデバイス）は2つの部分から構成されます。POWERサービスレイヤー（PSL）とアクセラレータ機能ユニット（AFU）。AFUはPSLの背後で特定の機能を実装するために使用されます。PSLは、AFUがユーザー空間メモリに直接アクセスできるようにするメモリアドレス変換サービスを提供します。

AFUはアクセラレータのコア部分です（例：圧縮、暗号処理など）。カーネルはAFUの機能についての知識を持ちません。AFUはユーザー空間のみが直接操作します。

PSLはAFUが必要とする翻訳および割込みサービスを提供します。これはカーネルがインタラクションする対象です。たとえば、AFUが特定の有効アドレスを読み込む必要がある場合、そのアドレスをPSLに送信します。PSLはアドレスを翻訳し、メモリからデータを取得してAFUに返します。PSLが翻訳ミスが発生した場合、カーネルに割込みを送信し、カーネルがそのエラーを処理します。このエラー処理のコンテキストは、そのアクセラレーション機能を所有する所有者によって決まります。

  • POWER8およびPSLバージョン8はCAIAバージョン1.0に準拠しています。

  • POWER9およびPSLバージョン9はCAIAバージョン2.0に準拠しています。

このPSLバージョン9は以下の新機能を提供します：

  • P9チップのネストMMUとの相互作用。

  • ネイティブDMAサポート。

  • ホストスレッドのウェイクアップ用ASB_Notifyメッセージの送信をサポート。

  • アトミック操作をサポート。

  • など

PSL9搭載のカードはPOWER8システムでは動作せず、PSL8搭載のカードはPOWER9システムでは動作しません。

AFUモード¶

AFUは2つのプログラミングモードをサポートしています。専用モードとAFU制御モード。AFUは1つまたは両方のモードをサポートする場合があります。

専用モードを使用する場合、1つのMMUコンテキストのみがサポートされます。このモードでは、一度に1つのユーザー空間プロセスのみがアクセラレータを使用できます。

AFUを制御するモードを使用する場合、最大で16Kの同時コンテキストがサポートされます。これは、最大で16Kのユーザー空間アプリケーションがアクセラレータを使用できることを意味します（ただし、特定のAFUはより少ない数をサポートする場合があります）。このモードでは、AFUが各リクエストに16ビットのコンテキストIDを送信します。これはPSLに各操作に関連するコンテキストを通知します。PSLが操作を翻訳できない場合、このIDはカーネルによってアクセスされ、操作に関連するユーザー空間コンテキストを特定できます。

MMIO領域¶

アクセラレータのMMIO領域の一部は、AFUからユーザー空間に直接マッピングできます。全体の領域をマッピングするか、各コンテキストごとの領域をマッピングするかを選択できます。ハードウェアは自己記述型であり、カーネルが各コンテキストごとの領域のオフセットとサイズを特定できます。

割込み¶

AFUはユーザー空間宛ての割込みを生成する場合があります。これらはカーネルがハードウェア割込みとして受信し、以下のreadシステムコールを通じてユーザー空間に渡されます。

データストレージエラーおよびエラーアクセス割込みはカーネルドライバによって処理されます。

ワーク要素記述子 (WED)¶

WEDは、コンテキストが開始されるときにAFUに渡される64ビットのパラメータです。フォーマットはAFUに依存するため、カーネルはWEDが何を表すかを把握していません。通常、ワークキューまたはステータスブロックの有効アドレスであり、AFUとユーザー空間が制御およびステータス情報を共有できます。

ユーザーAPI¶

1. AFUキャラクターデバイス¶

AFUがAFU制御モードで動作する場合、2つのキャラクターデバイスファイルが作成されます。/dev/cxl/afu0.0mはマスターコンテキストに対応し、/dev/cxl/af,0.0sはスレーブコンテキストに対応します。マスターコンテキストはAFUが提供する全MMIO領域にアクセスできます。スレーブコンテキストはAFUが提供する各プロセスごとのMMIO領域にのみアクセスできます。

AFUが専用プロセスモードで動作する場合、ドライバはAFUごとに1つのキャラクターデバイスのみを生成します。/dev/cxl/afu0.0dはAFUが提供する全MMIO領域にアクセスできます（AFU制御モードのマスターコンテキストと同様です）。

以下の型はinclude/uapi/misc/cxl.hに定義されています。

以下のファイル操作は、スレーブデバイスおよびマスターデバイスの両方に適用されます。

ユーザー空間ライブラリlibcxlは以下にあります:

https://github.com/ibm-capi/libcxl

これはカーネルAPIへのCインターフェースを提供します。

open¶

デバイスを開き、後続のAPIで使用するファイル記述子を割り当てます。

専用モードのAFUは1つのコンテキストのみを持ち、デバイスを一度しか開けない。

方向性モードのAFUは複数のコンテキストを持つことができ、利用可能な各コンテキストごとにデバイスを開けることができます。

すべての利用可能なコンテキストが割り当てられた場合、openコールは失敗し、-ENOSPCを返します。

注意:

各コンテキストにIRQを割り当てなければならないため、作成可能なコンテキスト数が制限され、デバイスを開ける回数も制限されます。POWER8 CAPPは2040個のIRQをサポートしており、カーネルが3個使用するため、2037個が残ります。1つのコンテキストに1つのIRQが必要な場合、2037個のコンテキストが割り当てられ、4つのIRQが必要な場合、2037/4 = 509個のコンテキストが割り当てられます。

ioctl¶

CXL_IOCTL_START_WORK:

AFUコンテキストを開始し、現在のプロセスと関連付ける。このioctlが成功すると、このプロセスにマップされたすべてのメモリは、同じ有効アドレスを使用してAFUコンテキストにアクセス可能になります。メモリのマップ/アンマップには追加のコールは必要ありません。ユーザー空間でメモリを割り当てたり解放したりするたびにAFUメモリコンテキストが更新されます。AFUコンテキストが開始されるとこのioctlは終了します。

struct cxl_ioctl_start_workへのポインタを取る

struct cxl_ioctl_start_work {
        __u64 flags;
        __u64 work_element_descriptor;
        __u64 amr;
        __s16 num_interrupts;
        __s16 reserved1;
        __s32 reserved2;
        __u64 reserved3;
        __u64 reserved4;
        __u64 reserved5;
        __u64 reserved6;
};
フラグ:

構造体の有効なオプションフィールドを示す

work_element_descriptor:

Work Element Descriptor (WED) はAFUによって定義された64ビットの引数です。通常これはAFU固有の構造体を指す有効アドレスで、実行すべき作業を記述します。

amr:

Authority Mask Register (AMR)、powerpcのAMRと同じです。このフィールドは、フラグにCXL_START_WORK_AMR値が指定されている場合にのみカーネルによって使用されます。指定されていない場合は、カーネルはデフォルト値0を使用します。

num_interrupts:

リクエストするユーザー空間の割り込み数。このフィールドは、フラグにCXL_START_WORK_NUM_IRQS値が指定されている場合にのみカーネルによって使用されます。指定されていない場合は、AFUが要求する最小数が割り当てられます。最小値と最大値はsysfsから取得できます。

reserved fields:

ABIパディングおよび今後の拡張用

CXL_IOCTL_GET_PROCESS_ELEMENT:

現在のコンテキストID、つまりプロセス要素を取得します。この値はカーネルから__u32として返されます。

mmap¶

AFUはMMIO領域を持つことで、AFUとの通信を促進する場合があります。その場合、MMIO領域はmmapを通じてアクセス可能です。この領域のサイズと内容はAFUごとに異なります。サイズはsysfsを通じて確認できます。

AFUのディレクテッドモードでは、マスタコンテキストはMMIO領域全体をマッピングできるが、スレーブコンテキストはコンテキストに関連するプロセスごとのMMIO領域のみをマッピングできる。専用プロセスモードでは、常に全体のMMIO領域をマッピングできる。

このmmapコールはSTART_WORK ioctlの後で実行する必要があります。

MMIO領域へのアクセスには注意が必要です。POWER8では32ビットおよび64ビットのアクセスのみがサポートされています。また、AFUは特定のエンディアンネスで設計されるため、すべてのMMIOアクセスではエンディアンネスを考慮する必要があります（レコメンデッドなエンドイアン変換関数例: le64toh()、be64toh()など）。これらのエンドイアン問題は、WEDが記述する共有メモリキューにも同様に適用されます。

読み取り¶

AFUからのイベントを読み込みます。イベントが待機していない場合、ブロックします（O_NONBLOCKが指定されている場合は除く）。回復不可能なエラーまたはカードが取り外された場合、-EIOを返します。

read()は常にイベントの整数倍を返します。

read()に渡すバッファは少なくとも4Kバイト以上である必要があります。

read()の結果は、1つ以上のイベントを含むバッファになります。各イベントはstruct cxl_event型で、サイズは異なります:

struct cxl_event {
        struct cxl_event_header header;
        union {
                struct cxl_event_afu_interrupt irq;
                struct cxl_event_data_storage fault;
                struct cxl_event_afu_error afu_error;
        };
};

struct cxl_event_headerは以下のように定義されています

struct cxl_event_header {
        __u16 type;
        __u16 size;
        __u16 process_element;
        __u16 reserved1;
};
type:

イベントの種類を定義します。種類によってイベントの構造が決まります。これらの種類はenum cxl_event_typeで定義されています。

size:

イベントのバイト数（struct cxl_event_headerを含む）。次のイベントの開始位置は、現在のイベントの開始位置からのこのオフセットで見つかります。

process_element:

イベントのコンテキストID。

予約済みフィールド:

今後の拡張用およびパディング。

イベントの種類がCXL_EVENT_AFU_INTERRUPTの場合、イベント構造は以下のように定義されています

struct cxl_event_afu_interrupt {
        __u16 flags;
        __u16 irq; /* Raised AFU interrupt number */
        __u32 reserved1;
};
フラグ:

これらのフラグは、この構造体に含まれるオプションフィールドを示します。現在はすべてのフィールドが必須です。

irq:

AFUから送信された割り込み番号。

予約済みフィールド:

今後の拡張用およびパディング。

イベントの種類がCXL_EVENT_DATA_STORAGEの場合、イベント構造は以下のように定義されています

struct cxl_event_data_storage {
        __u16 flags;
        __u16 reserved1;
        __u32 reserved2;
        __u64 addr;
        __u64 dsisr;
        __u64 reserved3;
};
フラグ:

これらのフラグは、この構造体に含まれるオプションフィールドを示します。現在はすべてのフィールドが必須です。

address:

AFUがアクセス失敗したアドレス。有効なアクセスはカーネルが透明に処理しますが、無効なアクセスはこのイベントを生成します。

dsisr:

このフィールドは、アドレスエラーが発生した際のエラー種類の情報を提供します。これはアドレスエラーが発生した際のPSLハードウェアからコピーされたDSISRです。DSISRの形式はCAIAで定義されています。

reserved fields:

今後の拡張用

イベントの種類がCXL_EVENT_AFU_ERRORの場合、イベント構造は以下のように定義されています

struct cxl_event_afu_error {
        __u16 flags;
        __u16 reserved1;
        __u32 reserved2;
        __u64 error;
};
フラグ:

これらのフラグは、この構造体に含まれるオプションフィールドを示します。現在はすべてのフィールドが必須です。

error:

AFUからのエラーステータス。AFUによって定義されています。

reserved fields:

今後の拡張用およびパディング

2. カードキャラクターデバイス (powerVMゲスト専用)¶

powerVMゲストでは、カード用に追加のキャラクターデバイスが作成されます。このデバイスはFPGAアクセラレータに新しいイメージをフラッシュ（書き込み）する際にのみ使用されます。イメージの書き込みと検証が完了した後、デバイスツリーが更新され、カードがリセットされて更新されたイメージが再読み込みされます。

open¶

デバイスを開き、APIの他の部分で使用するファイルディスクリプタを割り当てます。このデバイスは一度しか開けません。

ioctl¶

CXL_IOCTL_DOWNLOAD_IMAGE / CXL_IOCTL_VALIDATE_IMAGE:

新しいFPGAイメージのフラッシュを開始し、制御します。部分再構成はサポートされていません（まだ）、そのためイメージにはPSLとAFU（複数）のコピーが含まれていなければなりません。イメージが非常に大きい場合、呼び出し元はイメージを小さなチャンクに分割して繰り返し処理する必要があります。

struct cxl_adapter_imageへのポインタを取得します:

struct cxl_adapter_image {
    __u64 flags;
    __u64 data;
    __u64 len_data;
    __u64 len_image;
    __u64 reserved1;
    __u64 reserved2;
    __u64 reserved3;
    __u64 reserved4;
};
フラグ:

これらのフラグは、この構造体に含まれるオプションフィールドを示します。現在はすべてのフィールドが必須です。

data:

カードに書き込むイメージの一部を含むバッファへのポインタ

len_data:

dataポインタで指すバッファのサイズ

len_image:

イメージの全サイズ

Sysfs クラス¶

cxl sysfs クラスが /sys/class/cxl の下に追加され、アクセラレータの列挙とチューニングを容易にするためのインターフェースが提供されます。レイアウトの詳細は Documentation/ABI/testing/sysfs-class-cxl に記載されています。

Udev ルール¶

以下のUdevルールは、プログラミングモード（afuX.Ydで専用、afuX.YsでAFU指向）で使用する最も論理的なキャラクターデバイスへのシンヨケを生成するために使用できます。APIは各々ほぼ同じなので、

SUBSYSTEM=="cxl", ATTRS{mode}=="dedicated_process", SYMLINK="cxl/%b"
SUBSYSTEM=="cxl", ATTRS{mode}=="afu_directed", \
                  KERNEL=="afu[0-9]*.[0-9]*s", SYMLINK="cxl/%b"

1. ドライバ導入:¶

これはIBM Hypervisor Virtual Console Server（hvcs）用のデバイスドライバです。IBM hvcsは、論理的にパーティション化されたオペレーティングシステム（LinuxおよびAIX）のシステムコンソールにLinuxユーザースペースアプリケーションがアクセスできるようにするttyドライバインターフェースを提供します。このハードウェアでは物理的なハードウェアコンソールを各パーティションに割り当てるのは現実的ではありませんので、このドライバはファームウェアインターフェースを通じて仮想ターミナルデバイスを使用してシステムコンソールにアクセスします。

2. システム要件:¶

このデバイスドライバは2.6.4 LinuxカーネルAPIを使用して作成されており、このバージョン以降のカーネルでのみ構築および実行可能です。

このドライバはIBM Power5 ppc64ハードウェア専用に作成されていますが、アーキテクチャ依存のファームウェアコールをドライバコードから抽象化するための注意は払われています。

sysfsはシステムにマウントされる必要があります。ユーザーが各vty-serverに関連する主装置番号および補助装置番号を確認できるようにするためです。sysfsのマウント方法については本ドキュメントの範囲外です。

3. ビルドオプション:¶

hvcsドライバはttyドライバとして登録されます。ttyレイヤーは、登録するドライバが要求する数だけ主装置番号および補助装置番号のブロックを動的に割り当てます。hvcsドライバはデフォルトで64個の主装置番号/補助装置番号をttyレイヤーに要求して、hvcsデバイスノードエントリに使用します。

デフォルトのデバイスエントリ数が十分であれば、このドライバはカーネルに内蔵して構いません。そうでない場合は、insmodパラメータを使用してデフォルトを上書きしてドライバをモジュールとして挿入できます。

3.1 内蔵:¶

以下のmenuconfig例は、このドライバをカーネルに内蔵する選択方法を示しています:

Device Drivers  --->
        Character devices  --->
                <*> IBM Hypervisor Virtual Console Server Support

カーネルのmakeプロセスを開始します。

3.2 モジュール:¶

以下のmenuconfig例は、このドライバをカーネルモジュールとして構築する選択方法を示しています:

Device Drivers  --->
        Character devices  --->
                <M> IBM Hypervisor Virtual Console Server Support

makeプロセスは以下のカーネルモジュールを構築します:

  • hvcs.ko

  • hvcserver.ko

デフォルトの割り当てでモジュールを挿入するには、以下のコマンドを順に実行します:

insmod hvcserver.ko
insmod hvcs.ko

hvcserverモジュールにはアーキテクチャ固有のファームウェアコールが含まれており、最初に挿入する必要があります。そうでなければhvcsモジュールが期待する一部のシンボルを見つけることができません。

デフォルトを上書きするには、insmodパラメータを使用して以下のように指定します（例として4つのttyデバイスを要求する場合）:

insmod hvcs.ko hvcs_parm_num_devs=4

insmodで指定可能なdevエントリの最大数には制限があります。現在、1024はサーバーアダプターの適切な最大数として考えられます。ソースファイル内の定数を変更してビルドする前に、この値はいつでも変更可能です。

注意: ドライバをinsmodするのにかかる時間は、登録しているドライバが要求するttyインターフェースの数に関係しているようです。

ドライバモジュールを削除するには、次のコマンドを実行してください:

rmmod hvcs.ko

hvcsをモジュールとしてインストールする推奨方法は、depmodを使用して/lib/modules/以下のディレクトリに現在のmodules.depファイルを生成することです。uname -r そして次を実行してください:

modprobe hvcs hvcs_parm_num_devs=4

modules.depファイルは、hvcserver.koがhvcs.koよりも先に挿入される必要があることを示しており、modprobeはこのファイルを使用してモジュールを正しい順序で挿入します。

hvcsとhvcserverを正しい順序で削除するには、次のmodprobeコマンドを使用します:

modprobe -r hvcs

4. インストール:¶

ttyレイヤーは、hvcsドライバに割り当てられたメジャーアンドマイナーナンバーを含むsysfsエントリを作成します。次の「tree」コマンドの出力例は、これらのナンバーが表示される場所を示しています:

sys/
|-- *other sysfs base dirs*
|
|-- class
|   |-- *other classes of devices*
|   |
|   `-- tty
|       |-- *other tty devices*
|       |
|       |-- hvcs0
|       |   `-- dev
|       |-- hvcs1
|       |   `-- dev
|       |-- hvcs2
|       |   `-- dev
|       |-- hvcs3
|       |   `-- dev
|       |
|       |-- *other tty devices*
|
|-- *other sysfs base dirs*

上記の例では、次の出力はhvcsディレクトリ内の「dev」エントリをcatした結果です:

Pow5:/sys/class/tty/hvcs0/ # cat dev
254:0

Pow5:/sys/class/tty/hvcs1/ # cat dev
254:1

Pow5:/sys/class/tty/hvcs2/ # cat dev
254:2

Pow5:/sys/class/tty/hvcs3/ # cat dev
254:3

「dev」属性を読み込むと、ttyレイヤーがこのドライバの使用に割り当てたキャラクターデバイスのメジャーアンドマイナーナンバーが表示されます。hvcsを実行しているほとんどのシステムでは、デバイスエントリがすでに作成されているか、udevが自動的に実行します。

上記の出力例に基づき、/dev/hvcs*ノードエントリを手動で作成するには、mknodを使用して次のようになります:

mknod /dev/hvcs0 c 254 0
mknod /dev/hvcs1 c 254 1
mknod /dev/hvcs2 c 254 2
mknod /dev/hvcs3 c 254 3

mknodを使用してデバイスエントリを手動で作成すると、これらのデバイスノードが永続的に保持されます。作成後はドライバがinsmodされる前から存在します。

hvcsモジュールの挿入前にアプリケーションが/dev/hvcs*に接続しようとすると、次のようないずれかのエラーが発生します:

"/dev/hvcs*: No such device".

注意: デバイスノードが存在しているからといって、そのノードにvty-serverデバイスが設定されているとは限りません。

5. 接続¶

このドライバが制御するデバイスはttyインターフェースを提供するため、ユーザーは標準のttyインタラクティブメソッド（例:「cat」、「dd」、「echo」）を使用してデバイスノードエントリとやり取りできます。ただし、このドライバの目的は、Linuxパーティションのコンソールとのリアルタイムコンソールインタラクションを提供することであり、これにはttyデバイスとの双方向インタラクティブI/Oを提供するアプリケーションが必要です。

ターミナルエミュレータとして機能するアプリケーション（例："minicom" および "screen"）や、データを通過させる際にターミナルタイプの制御シーケンス変換を行うアプリケーションは、インタラクティブなコンソールI/Oを提供するためには不適切です。これらのプログラムはしばしば古いターミナルタイプ（vt100 および ANSI）をエミュレートし、入力データがこれらのサポートされているターミナルタイプのいずれかの形式を取ると想定していますが、出力データをターミナルが呼び出したターミナルタイプに変換しない、または十分に変換しないことがあり（"screen" は試みていますが、termcap の設定で複雑な設定が必要なようです）。

このため、kermit および cu は、hvcs デバイスを介して Linux コンソールとインタラクションするための推奨アプリケーションの一つです。これらのプログラムは単にデータ転送のための経路として機能し、特定のターミナルタイプを必要とせず、出力データを特定のターミナルタイプに変換することもありません。

コンソールアプリケーションが正しく動作するためには、/dev/hvcs コンソールに接続した後、コンソールの $TERM 環境変数を、使用したターミナルエミュレータの正確なターミナルタイプに設定する必要があります。xterm と kermit を使って /dev/hvcs0 に接続し、コンソールプロンプトが表示されたら、コンソール上で "export TERM=xterm" を実行します。これにより、コンソールから呼び出された ncurses アプリケーションが xterm が理解できる制御シーケンスを出力するよう指示します。

予防策として、hvcs ユーザーは常にアプリケーション（例：kermit）をデバイスノードから切断する前に "exit" を実行する必要があります。これをしないと、次のユーザーがコンソールに接続した際に、前のユーザーが設定した $TERM 変数を使用し続けるため、前のユーザーのログインセッションが引き続き使用されます。

ホットプラグによる vty-server アダプタの追加・削除は、どの /dev/hvcs* ノードがどの vty-server アダプタに接続されるかを決定します。どの vty-server アダプタがどの /dev/hvcs* ノードに関連しているかを特定するため、各 vty-server sysfs エントリに特別な sysfs 属性が追加されました。この属性は "index" と呼ばれ、表示するとその値は /dev/hvcs* ノードのエントリを参照する整数を示します。例えば、vty-server アダプタ 30000004 の index 属性を表示すると、以下のようになります：

Pow5:/sys/bus/vio/drivers/hvcs/30000004 # cat index
2

この index の "2" は、vty-server アダプタ 30000004 に接続するには、ユーザーが /dev/hvcs2 とインタラクションする必要があることを意味します。

システムのホットプラグI/O機能により、/dev/hvcs*エントリが特定のvty-serverアダプターと通信しているものの、システム再起動後にこのエントリが同じままになるとは限りません。この問題について詳しくはQ&Aセクションをご参照ください。

6. 接続の切断¶

セキュリティ機能として、古くなったデータが意図しないターゲットに届かないようにするため、Power5システムファームウェアはvty-serverとvty間の接続が切断された場合、データの取得を停止し、そのデータを破棄します。例えば、vty-serverがvtyにデータを送信した直後に接続が切断された場合、vtyアダプターはデータ取得をファームウェアが停止する前に、データを取得する時間が十分でない可能性があります。

hvcsがコンソールを提供する用途ではこの挙動は大きな問題ではありません。なぜなら、ほぼすべてのデータ書き込み後、アダプターは長時間接続されているからです。一方、hvcsを2つのパーティション間でデータをトンネルするttyコンディットとして使用する場合、この挙動は重大な問題になります。標準的なLinux動作では、catコマンドやddコマンドでデータをデバイスに送信する際、ttyを開いてデータを送信し、その後ttyを閉じます。このドライバーがttyの閉じるタイミングでvty-server接続を手動で切断すると、ターゲットのvtyがデータを取得する機会が失われる可能性があります。

さらに、モジュールの除去やアダプターの除去時にのみvty-serverとvtyを切断する方法は現実的ではありません。なぜなら、他のパーティションにある他のvty-serverがいつでもターゲットのvtyを使用する可能性があるからです。

この挙動制限により、vty-serverと接続されたvtyとの接続は、以下のsysfs属性への書き込みによる手動操作で行います。一方、初期のvty-serverとvtyとの接続はこのドライバーが自動的に確立します。手動でのvty-server接続は決して必要ありません。

vty-serverとvty間の接続を終了するには、各vty-serverのsysfsエントリ内の「vterm_state」sysfs属性を使用します。この属性を読み込むと、vty-serverアダプターの現在の接続状態がわかります。ゼロはvty-serverがvtyに接続されていないことを意味し、ワンは接続がアクティブであることを示します。

vterm_state属性に'0'（ゼロ）を書き込むと、vty-serverとターゲットvty間のVTERM接続を切断しますが、この動作はvterm_stateが以前に'1'を読み取っていた場合に限り適用されます。vterm_stateが'0'を読み取っていた場合、またはvterm_state属性に'0'以外の値が書き込まれた場合は、書き込みコマンドは無視されます。以下の例は、vty-server接続状態を確認し、接続を切断する方法を示しています。

Pow5:/sys/bus/vio/drivers/hvcs/30000004 # cat vterm_state
1

Pow5:/sys/bus/vio/drivers/hvcs/30000004 # echo 0 > vterm_state

Pow5:/sys/bus/vio/drivers/hvcs/30000004 # cat vterm_state
0

デバイスがホットプラグで除去された場合やモジュールが除去された場合、すべてのvty-server接続は自動的に終了します。

7. 設定¶

各vty-serverには、/sys/devices/vioディレクトリにsysfsエントリが存在し、hvcsドライバのエントリなど複数のsysfsツリーのディレクトリにシンボリックリンクされています。以下に例を示します。

Pow5:/sys/bus/vio/drivers/hvcs # ls
.  ..  30000003  30000004  rescan

設計上、ファームウェアはvty-serverのライフタイムやパートナーvtyの削除をhvcsドライバに通知しますが、パートナーvtyの追加は通知しません。HMCスーパーアドミニストレータが動的にパートナー情報を追加できるため、hvcsドライバのsysfsディレクトリに「rescan」更新属性を提供しています。この属性はファームウェアをクエリし、このドライバが管理するすべてのvty-serverのパートナー情報を更新します。'1'をこの属性に書き込むと更新がトリガーされます。以下の例は明示的な操作を示します。

Pow5:/sys/bus/vio/drivers/hvcs # echo 1 > rescan

この属性を読み込むと、'1'または'0'の状態が表示されます。'1'は更新中を示し、'0'は更新が完了したか、または実行されていないことを示します。

このディレクトリ内のvty-serverエントリは、ファームウェアによって作成される32ビットのパーティション一意のユニットアドレスです。vty-serverのsysfsエントリの例は以下の通りです。

Pow5:/sys/bus/vio/drivers/hvcs/30000004 # ls
.   current_vty   devspec       name          partner_vtys
..  index         partner_clcs  vterm_state

各エントリには、デフォルトで「name」属性が提供されます。この「name」属性を読み込むと、デバイスタイプが表示されます。以下の例を参照してください。

Pow5:/sys/bus/vio/drivers/hvcs/30000003 # cat name
vty-server

各エントリには、デフォルトで「devspec」属性も提供され、読み込むことで完全なデバイス仕様が表示されます。以下の例を参照してください。

Pow5:/sys/bus/vio/drivers/hvcs/30000004 # cat devspec
/vdevice/vty-server@30000004

各vty-server sysfsディレクトリには、簡単に解析可能なパートナーvtyデータのリストを提供する読み取り専用属性「partner_vtys」と「partner_clcs」が提供されます:

Pow5:/sys/bus/vio/drivers/hvcs/30000004 # cat partner_vtys
30000000
30000001
30000002
30000000
30000000

Pow5:/sys/bus/vio/drivers/hvcs/30000004 # cat partner_clcs
U5112.428.103048A-V3-C0
U5112.428.103048A-V3-C2
U5112.428.103048A-V3-C3
U5112.428.103048A-V4-C0
U5112.428.103048A-V5-C0

partner_vtysを読み込むと、パートナーのvtyの一覧が返されます。vtyユニットアドレスの番号はパーティション一意なので、エントリは頻繁に繰り返されます。

partner_clcsを読み込むと、「統合された位置コード（converged location codes）」の一覧が返されます。これらはシステムシリアル番号に「-V*」が接続され、'*'はターゲットパーティション番号を表し、「-C*」がアダプターのスロット番号を表す形式で構成されています。最初のvtyパートナーは最初のclc項目に対応し、2番目のvtyパートナーは2番目のclc項目に対応します。

vty-serverは一度に1つのvtyにのみ接続可能です。'current_vty'エントリは、読み込まれる際には現在選択中のパートナーディスプレイのclcを表示します。

現在のvtyを変更するには、以下の例のように有効なpartner clcを'current_vty'エントリに書き込みます。

Pow5:/sys/bus/vio/drivers/hvcs/30000004 # echo U5112.428.10304
8A-V4-C0 > current_vty

vty-serverがすでにvtyに接続されている状態で現在のvtyを変更しても、現在の接続には影響を与えません。変更は現在開いている接続が解放されたときに有効になります。

「vterm_state」属性に関する情報は、以前に「切断」に関する章で説明済みです。

8. 質問と回答:¶

Q: hvcsを使用したコンソールのセキュリティ上の懸念は何ですか？

A: 主に以下の3つのセキュリティ上の懸念があります:

1. /dev/hvcs*ノードの作成者は、デバイスエントリへのアクセスを特定のユーザーまたはグループに制限する権限を持っています。システムコンソールへのアクセスを提供するには、特別なhvcsグループの権限を作成することが望ましいです。

2. コンソールを取得する際のネットワークセキュリティを確保するため、SSHなどのセキュアな方法でコンソールホスティングパーティションに接続するか、ハードウェアコンソールに座ることが推奨されます。

3. コンソールの使用が終わったらユーザーセッションを終了してください。そうしないと、次のvty-server接続（別のパーティションからの可能性があります）で以前にログインしたセッションが表示されることがあります。

Q: hvcsを通じて取得したコンソールを複数人で共有するにはどうすればよいですか？

A: 「screen」を使用して/dev/hvcs*デバイスに直接接続し、コンソールグループの権限でローカルマシンにセッションを設定できます。以前に述べたように、デフォルトではscreenはほとんどのターミナルエミュレータに対してtermcap設定を提供せず、term型「screen」から他のタイプへの文字変換が適切に行われない可能性があります。これにより、cursesベースのプログラムがscreenセッションで正しく表示されない場合があります。

Q: なぜ色がすべておかしいのでしょうか？Q: なぜ制御文字が動作せず、異常な挙動を示すのでしょうか？Q: なぜコンソール出力がすべて奇妙で理解不能なのでしょうか？

A: キャラクターコントロールシーケンスが表示に与える影響についての説明は、「接続」セクションをご参照ください。また、xtermを使ってコンソールにログインしたからといって、他のユーザーがHMCコンソール(vt320)を使ってあなたよりも前にコンソールにログインし、セッションを終了していない可能性があります。コンソールに接続する際は、ターミナルエミュレータのターミナルタイプをTERMにエクスポートしてください。また、コンソールから切断する前に「exit」コマンドでセッションを終了してください。これにより、次のユーザーがログイン時に自分のTERMタイプが設定されるようになります。

Q: hvcsデバイスにkermitで接続しようとしたところ、「Sorry, can’t open connection: /dev/hvcs*」というエラーが発生しました。これは何が起きているのでしょうか？

A: 他のPower5コンソールメカニズムがvtyに接続しており、解放していない可能性があります。HMCからコンソールを強制的に切断するには、パーティションを右クリックして「close terminal」を選択してください。それ以外の場合、コンソール操作権限を持つユーザーを特定する必要があります。すでに別のkermitセッションでコンソールを開いていた可能性があり、忘れているだけかもしれません。Power5システムのコンソールオプションを確認し、システムコンソールが保持されるさまざまな方法を把握してください。

または

A: 他のユーザーが/dev/hv0cs*デバイスに接続していないにもかかわらず、vterm_stateがvtyサーバー接続が確立されていることを示している場合があります。他人が接続できるようにするには、「切断」セクションで説明した方法でこの状態を解放する必要があります。

または

A: kermitを実行しているユーザーのプロファイルが/dev/hvcs*デバイスを使用する権限を持っていない可能性があります。

または

A: hvcs.koモジュールをまだ挿入していない可能性がありますが、/dev/hvcs*エントリがシステムに存在している（udevを搭載していないシステムの場合）。

または

A: 既存の/dev/hvcs*エントリにマッピングされるvtyサーバーデバイスが存在しない可能性があります。

Q: hvcsデバイスにkermitで接続しようとしたところ、「Sorry, write access to UUCP lockfile directory denied.」というエラーが発生しました。

A: 指定した/dev/hvcs*エントリが存在しない可能性があります。モジュールを挿入していない（udevを搭載しているシステムの場合）かもしれません。

Q: 既に1つのLinuxパーティションをインストールしている場合、そのパーティションのhvcsを使って2番目のLinuxパーティションのインストール用コンソールとして使用できますか？

A: はい、ただし/dev/hvcs*デバイスにkermitやcuなどのターミナルエミュレータで接続している必要があります。

Q: このドライバーを使用して、一度に複数のパーティションのコンソールに接続できますか？

A: はい。もちろん、これはこのパーティションに複数のvty-serverが設定されていることを意味し、それぞれが切断されたvtyを指さなければなりません。

Q: hvcsドライバーは、動的（ホットプラグ）でデバイスを追加することをサポートしていますか？

A: はい。システムでdlparとhotplugが有効になっており、hvcsドライバーがカーネルに組み込まれている場合、新しいデバイスの追加や未使用デバイスの削除を動的に処理するよう構成されています。

Q: なぜか/dev/hvcs*が再起動後に同じvty-serverアダプターにマッピングされない場合があります。何が起きたのでしょうか？

A: /dev/hvcs*エントリへのvty-serverアダプターの割り当ては、アダプターが露出する順序で常に実行されます。このドライバーのホットプラグ機能により、ホットプラグで追加されたvty-serverの割り当て順序は、モジュールロード時に露出する順序とは異なる可能性があります。動的追加後に再起動またはモジュールの再ロードを行うと、vty-serverアダプターが他のvty-serverアダプターの間に挿入されたスロットに追加された場合、/dev/hvcs*とvty-serverの結合が変化する可能性があります。上記のセクションで、どのvty-serverがどの/dev/hvcs*ノードに割り当てられているかを確認する方法を参照してください。ヒント：vty-serverのsysfsの「index」属性を確認してください。

Q: /dev/hvcs*を別のパーティションに接続し、そのパーティションのttyデバイスをパイプのもう片方に使用できますか？

A: はい。Power5プラットフォームでは、hvc_consoleドライバーが追加の/dev/hvc*デバイス（/dev/hvc0がおそらくコンソール）にttyインターフェースを提供します。2つのパーティション間でttyコンディュートを動作させるには、HMC Super Adminがターゲットパーティションに追加の「シリアルサーバー」を作成し、HMC GUIで表示され、ターゲットパーティションが再起動後に/dev/hvc*として現れます。

その後、HMC Super Adminは現在のパーティションに追加の「シリアルクライアント」を作成し、これをターゲットパーティションの新しく作成された「シリアルサーバー」アダプター（スロットを覚えておくこと）にポイントします。これにより、追加の/dev/hvcs*デバイスが表示されます。

ターゲットシステムのプログラムを/dev/hvc*に読み書きし、現在のパーティションのプログラムを/dev/hvcs*に読み書きするように構成することで、2つのパーティション間でttyコンディュートが作成されます。

PCIバスEEHエラー回復¶

Linas Vepstas <linas@austin.ibm.com>

2005年1月12日

概要:¶

IBM POWERベースのpSeriesおよびiSeriesコンピュータは、PCIバスエラー条件の幅広い検出および報告が可能な拡張されたPCIバスコントローラーチップを搭載しています。これらの機能は「EEH（Enhanced Error Handling）」と呼ばれており、EEHハードウェア機能により、PCIバスエラーをクリアし、PCIカードを「再起動」することなく、オペレーティングシステムの再起動を必要としなくなります。

これは伝統的なPCIエラー処理とは対照的で、PCIチップがCPUに直接接続されており、エラーが発生するとCPUのマシンチェック/チェックストップ条件を引き起こし、CPUを完全に停止させる仕組みです。また、伝統的な技術としてエラーを無視する方法もありますが、これによりユーザーデータやカーネルデータの破損、アダプターの停止/応答なし状態、システムのクラッシュ/ロックアップといった問題が発生する可能性があります。したがって、EEHの目的は、オペレーティングシステムがPCIエラーから保護されることで信頼性と堅牢性が向上し、OSが個々のPCIデバイスを「再起動」/回復できるようになることです。

今後の他社製のPCI-E仕様に基づいたシステムでも同様の機能が搭載される可能性があります。

EEHエラーの原因¶

EEHは当初、ハードウェアの故障（例：熱、湿度、ほこり、振動、不良な電気接続によるPCIカードの故障など）を防ぐために設計されました。現実の「EEHエラー」の大部分は、PCIカードが正しく挿してあることのない状態、または残念ながら非常に頻繁に発生するデバイスドライバのバグ、デバイスファームウェアのバグ、あるいは場合によってはPCIカードハードウェアのバグが原因です。

最も一般的なソフトウェアのバグは、デバイスがシステムメモリ内のDMAアクセスが予約されていない場所にDMAを試行するものです。これは強力な機能であり、それ以外に静かなメモリ破損を防ぐことができます。過去数年間で、この方法により多数のデバイスドライバのバグが発見され修正されてきました。他のEEHエラーの原因として、データまたはアドレスラインのパリティエラー（例：PCIカードが正しく挿してあることのない状態による電気的接続不良）、PCI-Xスプリットコンプリーションエラー（ソフトウェア、デバイスファームウェア、またはデバイスPCIハードウェアのバグによる）が考えられます。ほぼすべての「真のハードウェア故障」は、物理的にPCIカードを外して再挿すことで解決できます。

検出と回復¶

以下の議論では、EEHエラーの検出と回復方法の一般的な概要を説明します。その後、Linuxカーネルでの現在の実装方法についても概説します。実際の実装は変更される可能性があり、一部の詳細な点についてはまだ議論が続いています。他のアーキテクチャが同様の機能を実装する場合、これらの点もまた影響を受ける可能性があります。

PCIホストブリッジ（PHB、PCIバスをシステムCPU電子複合体に接続するバス制御装置）がPCIエラー状態を検出すると、影響を受けるPCIカードを「分離」します。分離により、システムからカードへの書き込みやカードからシステムへの書き込みがすべてブロックされ、すべての読み込みはFF（0xff、0xffff、0xffffffff）を返します。この値は、デバイスが物理的にスロットから外された場合と同じ値であるため選ばれました。これはPCIメモリ、I/O領域、PCIコンフィギュレーション領域へのアクセスも含みます。ただし、割り込みは継続して送信されます。

検出と回復はppc64ファームウェアの支援で行われます。LinuxカーネルがファームウェアにアクセスするためのプログラミングインターフェースはRTAS（Run-Time Abstraction Services）と呼ばれます。Linuxカーネルは（すべきではありません）、PCIチップセット内のEEH機能を直接アクセスしない主な理由は、存在するチップセットが複数あり、それぞれ異なるインターフェースと特徴があるためです。ファームウェアは、すべてのpSeriesおよびiSeriesハードウェア（将来の互換性も含む）で動作する一貫した抽象レイヤーを提供します。

OSやデバイスドライバーがPCIスロットがEEH分離されていると疑う場合、ファームウェアが提供する関数を呼び出してその状態を確認できます。確認できた場合、デバイスドライバーは待機中の作業を完了できなくなるため、一貫した状態に移行し、カードの回復を開始する必要があります。回復は通常、PCIデバイスをリセットする（PCI #RSTラインを2秒間ハイに保つ）ことから始まり、その後デバイスコンフィギュレーション領域（ベースアドレスレジスタ（BAR）、レイテンシータイマ、キャッシュラインサイズ、割り込みラインなど）を設定します。その後、デバイスドライバーの再初期化が続きます。最悪の場合、ホットプラグ可能なスロットではカードの電源を切り替えることも可能です。原則として、デバイスドライバーよりも上のレイヤーはPCIカードがこのように「再起動」されたことを知る必要はなく、理想的にはカードがリセットされる間、イーサネット/ディスク/USB I/Oに最大で一時停止が生じる程度です。

3回または4回のリセット後もカードが復旧しない場合、カーネル/デバイスドライバーは最悪のシナリオ、つまりカードが完全に故障していると仮定し、このエラーをシステム管理者に報告する必要があります。さらに、エラー情報はRTASを通じて、またsyslogd（/var/log/messages）を通じてシステム管理者に通知されます。失敗したアダプターを処理する正しい方法は、標準的なPCIホットプラグツールを使用して故障したカードを除去・交換することです。

現在のPPC64 Linux EEH実装¶

現在、汎用的なEEH回復メカニズムが実装されており、個々のデバイスドライバーを修正することなくEEH回復をサポートできます。この汎用メカニズムはPCIホットプラグインフラストラクチャに依存し、イベントはユーザー空間/udevインフラストラクチャを通じて上位に伝搬されます。以下に、この仕組みがどのように実現されるかの詳細な説明を示します。

EEHは、ブートプロセスの非常に初期段階でPHB（PCIホストブリッジ）で有効化する必要があります。また、PCIスロットにホットプラグが行われる場合にも有効化する必要があります。前者はarch/powerpc/platforms/pseries/eeh.c内のeeh_init()関数で実行され、後者はdrivers/pci/hotplug/pSeries_pci.cがeeh.cコードを呼び出すことで実行されます。PCIデバイスのスキャンを開始する前にEEHを有効化する必要があります。現在のPower5ハードウェアはEEHが有効でない場合では動作しませんが、古いPower4は無効でも動作します。実質的に、EEHはもう無効にできません。PCIデバイス grace periodsを尊重しなければなりませんし、 はEEHコードに登録する必要があります。EEHコードはPCIデバイスのI/Oアドレス範囲を把握してエラーを検出する必要があります。任意のアドレスが与えられた場合、pci_get_device_by_addr()関数はそのアドレスに関連するPCIデバイス（存在すれば）を検索します。

デフォルトのarch/powerpc/include/asm/io.hマクロ（readb()、inb()、insb()など）は、I/O読み込みがすべての0xffを返した場合を検出するチェックを含んでいます。その場合、eeh_dn_check_failure()関数が呼び出され、ファームウェアにすべての0xff値が真のEEHエラーを示すかどうかを尋ねます。それ以外の場合は通常処理が続きます。これらの偽陽性（誤検出）の総数は/proc/ppc64/eeh（変更の可能性あり）で確認できます。通常、これらの誤検出は起動時にPCIバスがスキャンされる際、バススキャンプロセスの一環として多数の0xff読み込みが発生するため起きます。

フローズンスロットが検出された場合、arch/powerpc/platforms/pseries/eeh.cに記述されたコードがsyslog（/var/log/messages）にスタックトレースを出力します。このスタックトレースは、デバイスドライバの開発者にとって非常に有用で、EEHエラーが検出されたポイントを特定するのに役立ちます。エラー自体は通常、その少し前に行われます。

次に、Linuxカーネルの notifier chain/work queue メカニズムを使用して、関心を持つすべての関係者に失敗を通知します。デバイスドライバやカーネルの他の部分は、 eeh_register_notifier(struct notifier_block *) を使用してEEHイベントを通知を受け取ることができます。このイベントには、PCIデバイスへのポインタ、デバイスノード、およびいくつかの状態情報が含まれます。イベントの受信者は「自由に処理を行える」ことができ、デフォルトハンドラの説明はこのセクションの後半で行います。

デバイスの回復を支援するために、eeh.cは以下の関数をエクスポートしています：

rtas_set_slot_reset()

PCI #RSTラインを1/8秒間アサートする

rtas_configure_bridge()

ファームウェアに、PCIスロットのトポロジカルに位置するすべてのPCIブリッジを構成するよう依頼する

eeh_save_bars() および eeh_restore_bars()：

デバイスおよびその下位にあるすべてのデバイスのPCIコンフィギュレーションスペース情報を保存および復元する

EEH notifier_block イベントハンドラはdrivers/pci/hotplug/pSeries_pci.cに実装されており、handle_eeh_events()と呼ばれます。このハンドラはまずデバイスのBAR情報を保存し、その後rpaphp_unconfig_pci_adapter()を呼び出します。この最後の呼び出しにより、カードのデバイスドライバが停止され、ユーザー空間にueventsが送信されます。これにより、ユーザー空間のスクリプトが「ifdown eth0」などのコマンドを実行するなど、動作をトリガーします。このハンドラはその後5秒間待機し、ユーザー空間スクリプトが十分に実行されるのを待つためです。その後、PCIカードを再起動し、デバイスのBAR情報を再構成し、その下にあるすべてのブリッジを再構成します。最後にrpaphp_enable_pci_slot()を呼び出し、デバイスドライバを再起動し、ユーザー空間にさらにイベントをトリガーします（たとえば、eth0インターフェースの「ifup eth0」の呼び出しなど）。

デバイスシャットダウンとユーザー空間イベント¶

このセクションでは、PCIスロットがアンコンフィギュレーションされた際の挙動を説明し、特にデバイスドライバがシャットダウンされるプロセスと、ユーザー空間スクリプトにイベントが届く仕組みに焦点を当てます。

以下は、EEHリセットの最初のフェーズでデバイスドライバのclose関数が呼び出される例です。以下はpcnet32デバイスドライバの例です：

{
  calls
  pci_remove_bus_device (struct pci_dev *) // in /drivers/pci/remove.c
  {
    calls
    pci_destroy_dev (struct pci_dev *)
    {
      calls
      device_unregister (&dev->dev) // in /drivers/base/core.c
      {
        calls
        device_del (struct device *)
        {
          calls
          bus_remove_device() // in /drivers/base/bus.c
          {
            calls
            device_release_driver()
            {
              calls
              struct device_driver->remove() which is just
              pci_device_remove()  // in /drivers/pci/pci_driver.c
              {
                calls
                struct pci_driver->remove() which is just
                pcnet32_remove_one() // in /drivers/net/pcnet32.c
                {
                  calls
                  unregister_netdev() // in /net/core/dev.c
                  {
                    calls
                    dev_close()  // in /net/core/dev.c
                    {
                       calls dev->stop();
                       which is just pcnet32_close() // in pcnet32.c
                       {
                         which does what you wanted
                         to stop the device
                       }
                    }
                 }
               which
               frees pcnet32 device driver memory
            }
 }}}}}}

drivers/pci/pci_driver.cにおいて、struct device_driver->remove()はpci_device_remove()に等しく、これは struct pci_driver->remove() は pcnet32_remove_one() に等しく、これは unregister_netdev() （net/core/dev.c 内）で呼び出されます dev_close() （net/core/dev.c 内）で呼び出される dev->stop() これは pcnet32_close() であり、その後適切なシャットダウンを行います

現在の設計の利点と欠点¶

現在のEEHソフトウェア回復設計にはいくつかの問題があり、今後の改訂で改善される可能性があります。ただし、まず現在の設計の大きな利点は、個々のデバイスドライバーに変更を加える必要がないため、広範な対応が可能であることです。一方で、設計の最大の欠点は、ネットワークデーモンやファイルシステムといった必要のないものに影響を与える可能性があることです

  • 小さな不満としては、ネットワークカードのリセットがユーザー空間で連続して ifdown/ifup が実行され、ネットワークデーモンに影響を与える可能性があります。これはPCIカードが再起動されていることを知らなくても発生します

  • より深刻な懸念は、SCSIデバイスのリセットがマウントされたファイルシステムに混乱を引き起こすことです。スクリプトは待機中のバッファをフラッシュせずに事後的にファイルシステムをアンマウントすることはできませんが、これはI/Oがすでに停止しているため不可能です。したがって、理想的にはリセットはブロック層の下で行われるべきであり、ファイルシステムに影響を与えないようにする必要があります

    Reiserfsはブロックデバイスからのエラーを許容しません。Ext3fsは許容し、読み書きを再試行します。両方ともこのシナリオでは軽くテストされてのみています

    SCSI-genericサブシステムには、SCSIデバイスのリセット、SCSIバスのリセット、SCSIホストバスアダプタ（HBA）のリセットを行うための組み込みコードがあります。SCSIコマンドが失敗した場合、これらのリセットは連鎖して試行されます。これらはブロック層に対して完全に非表示です。したがって、EEHリセットをこの連鎖イベントに組み込むのは自然なことです

  • ルートデバイスでSCSIエラーが発生した場合、sysadminが/bin、/sbin、/etc、/varなどramdisk/tmpfsから実行した foresightがなければ、すべてが失われてしまいます

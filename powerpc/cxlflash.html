コヒーレントアクセラレータ (CXL) フラッシュ¶

はじめに¶

IBM Power アーキテクチャは、Power 8 システムの特定の PCIe スロットに搭載可能な CAPI（Coherent Accelerator Power Interface）をサポートしています。CAPI は PCIe を通じて特別なトンネリングプロトコルとみなせ、PCIe アダプターがアプリケーションのメモリを読み書きしページフォールトを生成する特別なコプロセッサとして動作させることができます。その結果、CAPI モードで動作するアダプターへのホストインターフェースは、データバッファがデバイスのメモリ（IOMMU バイパス）にマッピングされる必要がなく、メモリをピン留めする必要もありません。

Linux では、コハーヘントアクセラレータ（CXL）のカーネルサービスは、仮想PCIホストブリッジを実装してCAPIデバイスをPCIデバイスとして提示します。この抽象化によりインフラストラクチャとプログラミングモデルが簡素化され、ドライバが他のネイティブPCIデバイスドライバと同様に見えるようになります。

CXL は、ユーザー空間アプリケーションが通常のカーネル/デバイスドライバスタックを迂回してデバイス（ネットワークまたはストレージ）に直接通信できるメカニズムを提供します。CXLフラッシュアダプタードライバは、ユーザー空間アプリケーションがフラッシュストレージに直接アクセスできるようにします。

CXLフラッシュアダプタードライバは、IBM CXLフラッシュアダプタ用のSCSIスタック内に存在するカーネルモジュールで、低レベルデバイスドライバ（SCSIディスクおよびプロトコルドライバの下層）として機能します。このドライバはアダプタの初期化、ユーザー空間へのアクセス用特別パスの設定、エラー回復を担当します。これは、フラッシュアクセラレータ機能ユニット（AFU）に直接通信するため、記述されたように動作します。 コヒーレントアクセラレータインターフェース (CXL).

cxlflashドライバは、デバイス（LUN）レベルで2つの排他的な運用モードをサポートしています。

  • 任意のフラッシュデバイス（LUN）は通常のディスクデバイス（つまり：/dev/sdc）としてアクセスされるように設定できます。これはデフォルトモードです。

  • 任意のフラッシュデバイス（LUN）は、特別なブロックライブラリを介してユーザー空間からアクセスされるように設定できます。このモードではデバイスへのアクセス方法を指定し、LUN全体へのrawアクセス（直接または物理LUNアクセスと呼ばれる）またはカーネル/AFUを介したLUNのパーティションへのアクセス（仮想LUNアクセスと呼ばれる）のいずれかを選択できます。ディスクデバイスのセグメンテーションは、フラッシュAFUが提供する特別な翻訳サービスによって支援されます。

概要¶

コハーヘントアクセラレータインターフェースアーキテクチャ（CAIA）は、マスターコンテキストという概念を導入しています。マスターユーザーは、カーネルまたはハイパーバイザから特権が付与されており、AFU全体の管理と制御を行うことができます。マスターユーザーは各ユーザーI/Oに直接関与する必要はなく、少なくともユーザーアプリケーションがAFUに直接リクエストを送信できるようになる前の初期設定には関与します。

CXLフラッシュアダプタドライバはAFUとマスターコンテキストを確立します。この制御と設定にはメモリマップI/O（MMIO）を使用します。アダプタ問題領域メモリマップは以下のようになります：

+-------------------------------+
|    512 * 64 KB User MMIO      |
|        (per context)          |
|       User Accessible         |
+-------------------------------+
|    512 * 128 B per context    |
|    Provisioning and Control   |
|   Trusted Process accessible  |
+-------------------------------+
|         64 KB Global          |
|   Trusted Process accessible  |
+-------------------------------+

このドライバはSCSIソフトウェアスタックにアダプタドライバとして自身を設定します。ドライバは、上記のMMIO領域内のプロビジョニングおよび制御領域とグローバル領域をプログラミングするための信頼プロセスとして唯一のエンティティとみなされます。マスターコンテキストドライバはCXLフラッシュアダプタに接続されたすべてのLUNを検出し、各パスから見られるユニークなLUNごとにscsiブロックデバイス（/dev/sdb、/dev/sdcなど）をインスタンス化します。

これらのscsiブロックデバイスがインスタンス化されると、ブロックライブラリが提供する仕様に基づいて作成されたアプリケーションは、ユーザー空間からフラッシュにアクセスできるようになります（システムコールを必要としません）。

このマスターコンテキストドライバは、このブロックライブラリがユーザー空間からアクセスを可能にするために、一連のioctlを提供します。ドライバはブロックデバイスへのアクセスに2つのモードをサポートしています。

最初のモードは仮想モードと呼ばれます。このモードでは、単一のscsiブロックデバイス（/dev/sdb）が任意の数の異なる仮想LUNに分割されることがあります。仮想LUNは、すべての仮想LUNのサイズ合計とそれに付随するメタデータが物理容量を超えない限り、サイズを変更できます。

2番目のモードは物理モードと呼ばれます。このモードでは、ブロックライブラリが単一のブロックデバイス（/dev/sdb）を直接開き、LUN全体の領域がアプリケーションに利用可能になります。

データの永続性は物理モードのみが提供します。つまり、ブロックデバイスに書かれたデータはアプリケーションの終了や再起動、システムの再起動後も維持されます。仮想LUNは永続性を持たず（アプリケーションの終了やシステムの再起動後に消失します）。

ブロックライブラリAPI¶

ユーザー空間からCXL Flashへのアクセスを目的とするアプリケーションは、ブロックライブラリを使用すべきです。これは、cxlflashドライバに直接インターフェースする必要がある管理操作（例：セットアップ、 teardown、リサイズ）の詳細を抽象化しています。ブロックライブラリは、cxlflashドライバがユーザー空間アクセスモードで動作するデバイス（LUN）に特化して提供するサービス（IOCTL）を「ユーザー」として実装したものです。アプリケーションがブロックライブラリとcxlflashドライバのインターフェースを理解する必要はなく、以下に各サポートサービス（IOCTL）の概要を示します。

ブロックライブラリはGitHubで確認できます： http://github.com/open-power/capiflash

CXL Flashドライバ LUN IOCTL¶

ブロックライブラリなどのユーザーが、ユーザー空間アクセス経由でフラッシュデバイス（LUN）にインターフェースする場合、cxlflashドライバが提供するサービスを使用する必要があります。これらのサービスはIOCTLとして実装されているため、ユーザーとカーネル間の通信チャネルを確立するにはまずファイルディスクリプタハンドルを取得する必要があります。このファイルディスクリプタは、LUN検出時に作成されたSCSIディスクデバイス（/dev/sdb）に関連するデバイス特殊ファイルを開くことで取得します。cxlflashドライバがSCSIプロトコルスタック内で配置されているため、このオープン操作は実際にはcxlflashドライバには見えません。オープンが成功すると、ユーザーはファイルディスクリプタ（ここではfd1と呼ばれます）を取得し、以下に示すIOCTLを実行するために使用します。

これらのIOCTLの構造体定義は以下にあります：uapi/scsi/cxlflash_ioctl.h

DK_CXLFLASH_ATTACH¶

このIOCTLは、CXLカーネルサービスを使用してコンテキストを取得、初期化、起動します。これらのサービスは、コンテキストを一意に識別するためのコンテキストID（u16）を指定します。また、ブロックライブラリがCXLフラッシュデバイスに対してメモリマップI/O（mmap()経由）を開始し、完了イベントをポーリングするために使用する第二のファイルディスクリプタ（ここではfd2と呼ばれます）を提供します。このファイルディスクリプタは、このドライバが意図的にインストールしており、CXLカーネルサービスではなく、非ユーザー起因のclose()（例：終了プロセス）が発生した場合でも中間通知とアクセスを可能にするためです。この設計ポイントについては、DK_CXLFLASH_DETACH IOCTLの説明でさらに詳しく説明します。

ユーザーに返却される「トークン」（コンテキストIDとfd2）について重要な点があります：

  • これらのトークンは、作成されたプロセスにのみ有効です。フォークされたプロセスの子プロセスは、親プロセスが作成したコンテキストIDやファイル記述子を使用続けることができません（詳しくはDK_CXLFLASH_VLUN_CLONEを参照してください）。

  • これらのトークンは、コンテキストと作成されたプロセスの有効期間中にのみ有効です。どちらかが破棄されると、トークンは無効とみなされ、その後の使用はエラーを引き起こします。

  • コンテキストの初期アタッチ時にのみ、有効なアダプタファイル記述子（fd2 >= 0）が返されます。既存のコンテキストへのアタッチ（DK_CXLFLASH_ATTACH_REUSE_CONTEXTフラグが設定されている場合）では、アダプタファイル記述子は以前にアプリケーションに提供されたものと同じで、再提供されません。

  • コンテキストが不要になった場合は、DK_CXLFLASH_DETACH ioctlを介してコンテキストから切断する必要があります。このioctlが有効なアダプタファイル記述子を返し、DK_CXLFLASH_APP_CLOSE_ADAP_FDフラグが設定されている場合、アプリケーションは成功した切断後にアダプタファイル記述子を必ず閉じる必要があります。

  • このioctlが有効なfd2を返し、DK_CXLFLASH_APP_CLOSE_ADAP_FDフラグが設定されている場合、アプリケーションは以下の状況で必ずfd2を閉じる必要があります：

    • コンテキストの最後のユーザーが成功した切断後に

    • コンテキストの元のfd2での成功した回復後

    • fork()の子プロセスで、クローンioctl後にソースコンテキストに関連するfd2上で

  • いつでも、fd2の閉じることでトークンは無効になります。アプリケーションは、I/Oの早期喪失を避けるため、適切なタイミング（前の項目に記載）でのみfd2を閉じるべきです。

DK_CXLFLASH_USER_DIRECT¶

このioctlはLUNを直接（物理的）モードに切り替え、AFUをユーザー空間からの直接アクセスのためにコンテキストごとに設定します。また、ブロックサイズと最後の論理ブロックアドレス（LBA）がユーザーに返されます。

以前に述べたように、ユーザー空間アクセスモードで動作している場合、LUNは全体または一部でアクセス可能です。一度モードが有効（未解決の参照が存在）な場合、他のモードでのLUNの使用要求は拒否されます。

AFUは、AFUのリソースハンドルテーブルにエントリを追加することにより、ユーザー空間からの直接アクセスが設定されます。エントリのインデックスはリソースハンドルとして扱われ、ユーザーに返されます。これにより、ユーザーはI/O中にLUNを参照するためのハンドルを使用できます。

DK_CXLFLASH_USER_VIRTUAL¶

このioctlは、LUNを仮想モードへのアクセスに移行し、ユーザー空間からの仮想アクセスのためにAFUをコンテキストごとに構成する責任があります。さらに、ブロックサイズと最後の論理ブロックアドレス（LBA）がユーザーに返されます。

以前に述べたように、ユーザー空間アクセスモードで動作している場合、LUNは全体または一部でアクセス可能です。一度モードが有効（未解決の参照が存在）な場合、他のモードでのLUNの使用要求は拒否されます。

AFUのリソースハンドルテーブルにエントリを追加することで、AFUはユーザー空間からの仮想アクセスが構成されます。エントリのインデックスは、ユーザーに返されるリソースハンドルとして扱われ、ユーザーはI/O中にこのハンドルを使用してLUNを参照できます。

デフォルトでは、仮想LUNはサイズ0で作成されます。ユーザーはDK_CXLFLASH_VLUN_RESIZE ioctlを使用して仮想LUNのサイズを調整する必要があります。初期の仮想LUN作成時にこのリサイズ操作を実行する必要を避けるため、ユーザーはDK_CXLFLASH_USER_VIRTUAL ioctlでサイズを指定できます。成功が返される際、提供されるリソースハンドルは既にプロビジョニングされたストレージを参照しています。これは最後のLBAがゼロでない値を示しています。

LUNが複数のポートからアクセス可能な場合、このioctlはDK_CXLFLASH_ALL_PORTS_ACTIVEフラグが設定された状態で返されます。これにより、I/Oエラーが発生した場合でも、複数の経路を通じてLUNにアクセスできるため、I/Oの再試行が可能であることをユーザーに示します。

DK_CXLFLASH_VLUN_RESIZE¶

このioctlは、以前に作成された仮想LUNのサイズを変更します。LUNが仮想モードでない場合に呼び出されると失敗します。成功した場合、リソースハンドルに関連する仮想LUNの新しいサイズを示す更新された最後のLBAがユーザーに返されます。

仮想LUNのパーティションは、cxlflashドライバとAFUが共同で制御します。仮想モードで動作する各LUNには割当テーブルが保持され、AFUがリソースハンドルを提供された際に参照するLUN変換テーブルにプログラミングされます。

AFUの同期操作が長すぎる場合、このioctlは-EAGAINを返すことがあります。ユーザーに失敗を返すだけでなく、cxlflashは非同期のAFUリセットをスケジュールします。ユーザーが操作を再試行する場合、成功することが期待されます。このioctlが-EAGAINで失敗した場合、ユーザーは操作を再試行するか、失敗とみなすことができます。

DK_CXLFLASH_RELEASE¶

このioctlは、物理または仮想LUNへの以前に取得した参照を解放する責任があります。これはDK_CXLFLASH_USER_DIRECTまたはDK_CXLFLASH_USER_VIRTUAL ioctlの逆操作と考えることができます。成功した場合、リソースハンドルはもはや有効ではなく、リソースハンドルテーブルのエントリが再度使用可能になります。

仮想LUNの解放プロセスの一環として、まず仮想LUNが0にリサイズされ、それに伴って仮想LUN参照に関連する翻訳テーブルがクリアされ解放されます。

DK_CXLFLASH_DETACH¶

このioctlは、cxlflashドライバからコンテキストを登録解除し、DK_CXLFLASH_RELEASE ioctlで明示的に解放されていないリソースを解放します。成功した場合、DK_CXLFLASH_ATTACH以降にユーザーに提供されたすべての「トークン」はもはや有効ではありません。

成功したアタッチ時にDK_CXLFLASH_APP_CLOSE_ADAP_FDフラグが返された場合、アプリケーションは、コンテキストの最後のユーザーが切断された後に、関連するfd2を閉じる必要があります。

DK_CXLFLASH_VLUN_CLONE¶

このioctlは、以前に作成されたコンテキストをより最近作成されたコンテキストにクローンする責任があります。これはプロセスがフォークした後にユーザー空間へのストレージアクセスを維持するためのサポートのみの存在です。成功した場合、子プロセス（ioctlを呼び出したプロセス）は、親プロセスと同じリソースハンドル（s）を通じて同じLUNにアクセスできますが、異なるコンテキストの下で行われます。

CXLではプロセス間でのコンテキスト共有はサポートされていないため、各フォークには子プロセス用に新しいコンテキストの確立が必要です。このioctlは、このようなシナリオでユーザーが行う必要のある状態管理と再現作業を簡素化します。プロセスがフォークするとき、子プロセスはまずDK_CXLFLASH_ATTACHを通じてコンテキストを作成し、その後このioctlを使用して親から子へコンテキストをクローンします。

クローン自体は比較的単純です。リソースハンドルとLUN翻訳テーブルが親コンテキストから子コンテキストにコピーされ、AFUと同期されます。

成功したアタッチ時にDK_CXLFLASH_APP_CLOSE_ADAP_FDフラグが返された場合、アプリケーションは、クローン後、ソースコンテキスト（親プロセスでまだ居住/アクセス可能）に関連するfd2を閉じる必要があります。これは、子プロセスのファイルディスクリプタテーブルに古くなったエントリが残らないようにするためです。

AFUの同期操作が長すぎる場合、このioctlは-EAGAINを返すことがあります。ユーザーに失敗を返すだけでなく、cxlflashは非同期のAFUリセットをスケジュールします。ユーザーが操作を再試行する場合、成功することが期待されます。このioctlが-EAGAINで失敗した場合、ユーザーは操作を再試行するか、失敗とみなすことができます。

DK_CXLFLASH_VERIFY¶

このioctlは、ディスク容量の変更、可視のLUN数の変更など、さまざまな変更を検出するために使用されます。アプリケーションに影響を与える変更（例：LUNのリサイズ）が発生した場合、cxlflashドライバはアプリケーションに変更後の状態を報告します。

ユーザーは、LUNがチェック条件により変更されていないことを検証したいときにこのioctlを呼び出します。ユーザーはカーネルとは別途で動作しており、カーネルの知識なしにこのようなイベントを確認できます。このような状況に遭遇した場合、ユーザーのアーキテクチャ上の動作は、検証したい内容を指定し、適切な情報を渡してこのioctlを呼び出すことです。現時点では、センスデータとともにLUNの変更（例：サイズの違い）の検証のみがサポートされています。

DK_CXLFLASH_RECOVER_AFU¶

このioctlは、指定されたユーザー コンテキストの回復（必要に応じて）を実行するために使用されます。回復が成功した場合、ユーザー コンテキストに関連するすべての状態が再構築されます。

デバイスのリセットが必要な場合や終了している場合、ユーザー コンテキストはエラー状態になります。ユーザーはMMIO読み込み時にすべての0xFを確認することでこのエラー状態を通知されます。このような状況に遭遇した場合、ユーザーのアーキテクチャ上の動作は、コンテキストの回復を目的としたこのioctlを呼び出すことです。ユーザーはまた、デバイスが正常に動作しているかを確認するため、いつでもこのioctlを呼び出すことができます。このioctlから失敗が返された場合、ユーザーはリリース/デタッチ ioctlを介してコンテキストを穏やかにクリーンアップする必要があります。それまで、ユーザーが保持するコンテキストは解放されません。ユーザーはまた、プロセスを終了するオプションもあります。その場合、保持していたコンテキスト/リソースはリリースfopの一部として解放されます。

成功したアタッチでDK_CXLFLASH_APP_CLOSE_ADAP_FDフラグが返された場合、アプリケーションはこのioctlが成功し、コンテキストが回復された（DK_CXLFLASH_RECOVER_AFU_CONTEXT_RESET）ことを示した後、関連する元のコンテキストのfd2をマップを解除し、閉じる必要があります。

DK_CXLFLASH_MANAGE_LUN¶

このioctlは、LUNをファイルシステムへのアクセスが可能なモード（レガシー）から、排他的なユーザー スペースへのアクセスが設定されたモード（スーパーパイプ）に切り替えるために使用されます。LUNが複数のポートおよびアダプタで表示される場合、このioctlはWorld Wide Node Name（WWNN）を用いて各LUNを一意に識別します。

CXL Flash Driver ホスト IOCTL¶

cxlflashドライバがサポートする各ホストアダプタインスタンスには、ホスト管理機能を有効にするための特別なキャラクターデバイスが関連付けられています。これらのキャラクターデバイスは、cxlflash専用のクラスにホストされ、以下のようにアクセスできます。 /dev/cxlflash/*.

アプリケーションは、以下に示すホストioctl APIを使用してさまざまな機能を実行できます。

これらのIOCTLの構造体定義は以下にあります：uapi/scsi/cxlflash_ioctl.h

HT_CXLFLASH_LUN_PROVISION¶

このioctlは、外部のLUN管理インターフェースを持たないcxlflashデバイス上で永続的なLUNの作成と削除を行うために使用されます。このioctlは、LUNプロビジョニング機能をサポートするAFUと組み合わせてのみ有効です。

十分な空き容量がある場合、ターゲットポートでLUNをホストするターゲットポートと、4Kブロック単位の希望サイズを指定することでLUNを作成できます。成功した場合、作成されたLUNのLUN IDとWWIDが返され、SCSIバスをスキャンしてLUNトポロジーの変化を検出できます。部分的な割り当てはサポートされていません。作成が空間の問題で失敗した場合、ターゲットポートの現在のLUN幾何学を照会できます。

LUNを削除するには、まずデバイスがLinux SCSIサブシステムから関連付けられなくなります。その後、ターゲットポートとLUN IDを指定してLUN削除を開始できます。成功した場合、ポートに関連するLUN幾何学が更新され、新しいプロビジョニングされたLUN数と利用可能な容量が反映されます。

ポートのLUN幾何学を照会するには、ターゲットポートを指定します。成功した場合、以下の情報が表示されます：

  • ポートで最大でプロビジョニング可能なLUN数

  • ポートの現在のプロビジョニングされたLUN数

  • ポートのプロビジョニングされたLUNの最大総容量（4Kブロック）

  • ポートのプロビジョニングされたLUNの現在の総容量（4Kブロック）

この情報から、利用可能なLUN数と容量を計算できます。

HT_CXLFLASH_AFU_DEBUG¶

このioctlは、AFUデバッグ機能をサポートするAFUと組み合わせてのみ有効です。AFUデバッグコマンドをサポートするAFUと組み合わせてのみ有効です。

バッファ管理を除き、AFUデバッグコマンドはcxlflashによって透明に処理され、透過的に扱われます。データ転送を必要とするデバッグコマンドでは、ユーザーが適切なサイズのデータバッファを提供し、ホストに対するデータ転送方向を指定する必要があります。最大転送サイズは256Kに制限されます。部分的な読み取り完了はサポートされていません。ホスト読み取りデータ転送中にエラーが発生した場合、データバッファはユーザーにコピーされません。

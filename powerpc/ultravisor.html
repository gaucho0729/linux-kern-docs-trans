はじめに¶

Protected Execution Facility (PEF) は POWER 9 のアーキテクチャ変更で、Secure Virtual Machines (SVMs) を実現する機能です。DD2.3チップ (PVR=0x004e1203) またはそれ以降は PEF 対応となります。新しい ISA リリースには PEF RFC02487 の変更が含まれます。

有効化されると、PEF は POWER アーキテクチャに新しい高権限モードである Ultravisor モードを追加します。この新しいモードとともに、SVM とハイパーバイザー間の通信を管理する新しいファームウェアである Protected Execution Ultravisor (またはウルトラビジョンと略称されます) が導入されます。Ultravisor モードは POWER アーキテクチャで最も高権限のモードです。

ウルトラビジョン

PEF は SVMs をハイパーバイザー、特権ユーザー、システム内の他の VM から保護します。SVMs は静止状態でも保護され、認可されたマシンのみが実行できます。すべての仮想マシンはハイパーバイザーのサービスを利用します。ウルトラビジョンは SVMs とハイパーバイザー間のコールをフィルタリングし、情報の誤って漏洩を防ぎます。すべてのハイパーコールは H_RANDOM を除きハイパーバイザーに反映され、H_RANDOM はハイパーバイザーが SVM 内のランダム値に影響を与えないようにするために反映されません。

この機能をサポートするために、CPU 内のリソースの所有権が再構築されます。以前はハイパーバイザの特権だった一部のリソースは、今ではウルトラビジョンの特権になります。

ハードウェア¶

ハードウェアの変更には以下のものが含まれます:

  • MSR に新しいビットが追加され、現在のプロセスがセキュアモードで実行されているかを判定します。MSR(S) ビット41。MSR(S)=1 はセキュアモード、MSR(s)=0 はノーマルモードです。

  • MSR(S) ビットはウルトラビジョンによってのみ設定できます。

  • HRFID は MSR(S) ビットを設定するために使用できません。ハイパーバイザーが SVM に戻る必要がある場合、ultracall を使用しなければなりません。戻る VM がセキュアかどうかを判断できます。

  • 新しいウルトラビジョン特権レジスタ SMFCTRL があり、有効/無効ビット SMFCTRL(E) があります。

  • プロセスの権限は MSR ビット MSR(S, HV, PR) によって決定されます。以下の表では、権限レベルが最も低い順にモードがリストされています。権限レベルが高いモードは、権限レベルが低いモードのすべてのリソースにアクセスできます。

  • ハードウェアは、セキュアな状態で実行されていないプロセスがセキュアメモリにアクセスすることを許可していません。これは、ハイパーバイザがSVMのメモリにアクセスするためにはウルトラビジアに問い合わせるultracallを使用しなければならないことを意味します。ウルトラビジアは、SVMメモリを暗号化した状態でハイパーバイザに表示することを許可します。

  • プロセスがセキュアモードで実行されている場合、すべての割込みはウルトラビジアに送信されます。

    • プロセッサ設定レジスタ（SCOMs）。

    • 停止状態情報。

    • SMFCTRL(D)が設定されている場合のデバッグレジスタCIABR、DAWR、DAWRX。SMFCTRL(D)が設定されていない場合、セキュアモードでは動作しません。設定されている場合、読み書きにはウルトラビジア呼び出しを必要とし、それ以外の場合はハイパーバイザエミュレーションアシスタンス割込みが発生します。

    • PTCRおよびパーティションテーブルエントリ（パーティションテーブルはセキュアメモリに配置）。PTCRへの書き込み試行はハイパーバイザエミュレーションアシスタンス割込みを発生させます。

    • LDBAR（LDベースアドレスレジスタ）およびIMC（インメモリコレクション）非アーキテクチャレジスタ。これらへの書き込み試行はハイパーバイザエミュレーションアシスタンス割込みを発生させます。

    • SVMのページング、SVMとハイパーバイザ間のメモリ共有（仮想プロセッサ領域（VPA）および仮想I/Oを含む）。

ソフトウェア/マイクロコード¶

ソフトウェアの変更内容は以下の通りです：

  • SVMはIBMが提供するオープンソースツールを使用して通常のVMから作成されます。

  • すべてのSVMは通常のVMとして開始し、UV_ESM（セキュアモードへの移行）というultracallを使用して移行します。

  • UV_ESM ultracallが呼び出されると、ウルトラビジアはVMをセキュアメモリにコピーし、検証情報を復号化し、SVMの整合性を確認します。整合性チェックが通ると、ウルトラビジアはセキュアモードで制御を渡します。

  • 検証情報にはSVMに関連する暗号化ディスクのパスフレーズが含まれます。このパスフレーズはSVMが要求した際に提供されます。

  • ウルトラビジアはSVMの暗号化ディスクが休止状態にあるときの保護には関与していません。

  • 外部割込みについては、UltravisorがSVMの状態を保存し、その割込みをハイパーサーバーに反映して処理を行います。ハイパーコールについては、Ultravisorがハイパーコールに必要なレジスタ以外のすべてのレジスタに中立な状態を挿入した後、ハイパーサーバーにその呼び出しを反映して処理を行います。H_RANDOMハイパーコールはUltravisorが直接実行し、反映されません。

  • 仮想I/Oが正常に動作するためにはバウンドバッファリングが必須です。

  • UltravisorはSVMメモリの保護にAES（IAPM）を使用します。IAPMはAESのモードであり、整合性と秘密性を同時に提供します。

  • 通常メモリとセキュアメモリ間のデータの移動は、ハイパーサーバー内の新しいHMMプラグインを通じてUltravisorと連携して行われます。

UltravisorはハイパーサーバーおよびSVMに対して新たなサービスを提供します。これらはultracallsを通じてアクセスされます。

用語¶

  • ハイパーコール：ハイパーサーバーからサービスを要求する特別なシステムコール。

  • 通常メモリ：ハイパーサーバーがアクセス可能なメモリ。

  • 通常ページ：通常メモリでバックアップされ、ハイパーサーバーがアクセス可能なページ。

  • 共有ページ：通常メモリでバックアップされ、ハイパーサーバー/QEMUとSVMの両方がアクセス可能なページ（つまり、SVMとハイパーサーバー/QEMUにマッピングが存在するページ）。

  • セキュアメモリ：UltravisorおよびSVMのみがアクセス可能なメモリ。

  • セキュアページ：セキュアメモリでバックアップされ、UltravisorおよびSVMのみがアクセス可能なページ。

  • SVM：セキュア仮想マシン。

  • ウルトラコール：Ultravisorからサービスを要求する特別なシステムコール。

ウルトラビジョンコールAPI¶

このセクションでは、セキュア仮想マシン（SVM）およびパラバーチャライズドKVMをサポートするために必要なUltravisor呼び出し（ultracalls）について説明します。ultracallsは、SVMおよびハイパーサーバーがUltravisorからサービスを要求できるようにします。そのサービスには、Ultravisorプライベートモードで実行中の場合にのみアクセス可能なレジスタやメモリ領域のアクセスなどが含まれます。

ultracallから必要な特定のサービスは、レジスタR3（ultracallの最初のパラメータ）で指定されます。その他のultracallのパラメータ（存在する場合）は、レジスタR4からR12で指定されます。

すべてのultracallの戻り値はレジスタR3に格納されます。その他のultracallからの出力値（存在する場合）はレジスタR4からR12に返されます。このレジスタの使用に関する例外は、 UV_RETURN 以下のultracallに限られます。

各ultracallは、その文脈において特定のエラーコードを返します。しかし、PowerPC Architecture Platform Reference (PAPR)と同様に、特定のエラーコードが定義されていない場合、ultracallはエラーパラメータポジションに基づいたコードにフォールバックします。つまり、U_PARAMETER、U_P2、U_P3など、エラーを引き起こした可能性のあるultracallパラメータに応じて異なります。

一部のultracallは、UltravisorとHypervisor間でページ単位のデータを転送します。セキュアメモリからノーマルメモリへ転送されるセキュアページは、動的に生成された鍵で暗号化される場合があります。セキュアページが再びセキュアメモリへ戻される際には、同じ動的に生成された鍵で復号される可能性があります。これらの鍵の生成および管理については、別のドキュメントで説明します。

現時点では、HypervisorおよびSVMsで現在実装され使用されているultracallのみをカバーしていますが、必要に応じて他のultracallも追加できます。

すべてのhypercall/ultracallの完全な仕様は、最終的に公開/OpenPower版のPAPR仕様に含まれることになります。

注意

PEFが有効でない場合、ultracallはHypervisorにリダイレクトされ、Hypervisorが呼び出しを処理または失敗させる必要があります。

ハイパーバイザーより使用されるウルトラコール¶

このセクションでは、HypervisorがSVMsを管理するために使用する仮想メモリ管理ultracallについて説明します。

UV_PAGE_OUT¶

セキュアメモリからノーマルメモリへページの内容を暗号化して移動します。

        uint64_t src_gpa,       /* source guest-physical-address */
        uint8_t  flags,         /* flags */
        uint64_t order)         /* page size order */

  • U_P3がアドレスが無効な場合。 src_gpa U_P4が、

  • のどのビットも認識されない場合。 flags U_P5が、

  • セキュアページの内容を暗号化し、Hypervisorがノーマルページで利用できるようにします。

デフォルトでは、ソースページはSVMのパーティションスコープのページテーブルからマップされていません。ただし、HypervisorはUltravisorにページマッピングを保持するヒントを提供するために、

使用例¶

  1. QEMUがSVMのアドレスにアクセスしようとするが、そのアドレスのページフレームがQEMUのアドレス空間にマップされていない場合があります。この場合、Hypervisorがページフレームを割り当て、QEMUのアドレス空間にマップし、 UV_PAGE_OUT 呼び出しを実行してページの暗号化された内容を取得します。

  2. Ultravisorがセキュアメモリが不足し、LRUページをページアウトする必要がある場合。この場合、Ultravisorは H_SVM_PAGE_OUT ハイパーバイザへのハイパーコール。ハイパーバイザはその後、通常ページを割り当てて、 UV_PAGE_OUT ウルトラコールを実行し、ウルトラバイザがセキュアページの内容を暗号化して通常ページに移動させます。

  3. ハイパーバイザがSVMデータにアクセスする際、ハイパーバイザはウルトラバイザに該当するページを不安全なページに移動させることを依頼します。ハイパーバイザがアクセスできるようにします。通常ページ内のデータは暗号化されます。

UV_PAGE_IN¶

ページの内容を通常メモリからセキュアメモリへ移動します。

構文¶
uint64_t ultracall(const uint64_t UV_PAGE_IN,
        uint16_t lpid,          /* the LPAR ID */
        uint64_t src_ra,        /* source real address of page */
        uint64_t dest_gpa,      /* destination guest physical address */
        uint64_t flags,         /* flags */
        uint64_t order)         /* page size order */
返却値¶

次のいずれかの値:

  • 成功した場合にU_SUCCESS。

  • ページが現在ページインできない場合、U_BUSY

  • 機能がサポートされていない場合、U_FUNCTION

  • U_PARAMETERが lpid が無効な場合。

  • U_P2が src_ra が無効な場合。

  • U_P3がアドレスが無効な場合。 dest_gpa U_P4が、

  • のどのビットも認識されない場合。 flags U_P5が、

  • パラメータがサポートされていない場合。 order U_FUNCTIONが機能がサポートされていない場合。

説明¶

識別されたページの内容を src_ra 通常メモリからセキュアメモリへ移動し、ゲスト物理アドレスにマッピングします dest_gpa.

もし dest_gpa 共有アドレスを参照する場合、SVMのパーティションスコープのページテーブルにページをマッピングします。もし dest_gpa 共有されていない場合、ページの内容を対応するセキュアページにコピーします。文脈に応じて、コピー前にページを復号化します。

呼び出し元はページの属性を flags パラメータを通じて提供します。有効な値は flags は:

  • CACHE_INHIBITED

  • CACHE_ENABLED

  • WRITE_PROTECTION

ハイパーバイザが UV_PAGE_IN ウルトラコールを実行する前にページをメモリに固定する必要があります。

使用例¶

  1. 通常の仮想マシンがセキュアモードに切り替わるとき、すべての通常メモリに存在するページがセキュアメモリに移動します。

  2. SVMが仮想マシンと共有するページを要求するとき、ハイパーバイザはページを割り当ててウルトラバイザに通知します。

  3. SVMがセキュアページにアクセスし、そのページがページアウトされている場合、ウルトラバイザはハイパーバイザにページを検索させます。ページを検索した後、ハイパーバイザはUV_PAGE_INを実行してページをウルトラバイザに利用可能にします。

UV_WRITE_PATE¶

uint64_t ultracall(const uint64_t UV_WRITE_PATE,
        uint32_t lpid,          /* the LPAR ID */
        uint64_t dw0            /* the first double word to write */
        uint64_t dw1)           /* the second double word to write */

次のいずれかの値:

  • 成功した場合にU_SUCCESS。

  • PATEが現在書き込めない場合、U_BUSY

  • U_BUSYがページを現在ページアウトできない場合。

  • U_PARAMETERが lpid が無効な場合。

  • U_P2が dw0 が無効な場合。

  • U_P3がアドレスが無効な場合。 dw1 U_P4が、

  • ハイパーバイザがセキュア仮想マシンのPATEを変更しようとしている場合、またはハイパーバイザ以外のコンテキストから呼び出された場合、U_PERMISSION

    を返します。

説明¶

指定されたLPIDに対してLPIDを検証し、そのLPIDのパーティションテーブルエントリを記録します。LPIDがすでに割り当てられ初期化されている場合、この呼び出しはパーティションテーブルエントリを変更します。

使用例¶

  1. パーティションテーブルはセキュアメモリに存在し、PATE（パーティションテーブルエントリ）はハイパーバイザーや各仮想マシン（セキュアおよび通常のマシン）のパーティションスコープのページテーブルを指します。ハイパーバイザーはパーティション0で動作し、そのパーティションスコープのページテーブルは通常メモリに存在します。

  2. このウルトラコールにより、ハイパーバイザーは自身および他のパーティション（仮想マシン）のパーティションスコープおよびプロセススコープのページテーブルエントリをウルトラバイザーに登録できます。

  3. 既存のパーティション（仮想マシン）のPATE値が変更された場合、そのパーティションのTLBキャッシュはフラッシュされます。

  4. ハイパーバイザーがLPIDを割り当てます。LPIDとそのPATEエントリは一緒に登録されます。ハイパーバイザーは通常の仮想マシンのPATEエントリを管理でき、いつでも変更可能です。ウルトラバイザーがSVMのPATEエントリを管理し、ハイパーバイザーはそれらを変更できません。

UV_RETURN¶

ハイパーバイザーが処理したハイパーコールまたは転送（いわゆる reflected）された割込みから制御をウルトラバイザーに戻します。

構文¶
uint64_t ultracall(const uint64_t UV_RETURN)
返却値¶

成功した場合、このコールはハイパーバイザーに戻りません。ハイパーバイザーのコンテキストからウルトラコールが呼び出されていない場合、U_INVALIDを返します。

説明¶

SVMがハイパーコールを実行したり、他の例外を発生させた場合、ウルトラバイザーは通常（いわゆる reflects）これらの例外をハイパーバイザーに転送します。例外を処理した後、ハイパーバイザーは UV_RETURN ultracallを用いて制御をSVMに戻します。

このウルトラコールへの入力時のレジスタ状態は以下の通りです：

  • 非揮発性レジスタは元の値に戻されます。

  • ハイパーコールから戻る場合、レジスタR0には戻り値（他のウルトラコールとは異なり）が格納され、レジスタR4からR12にはハイパーコールの出力値が含まれます。

  • R3にはウルトラコール番号、つまりUV_RETURNが格納されます。

  • 合成割込みで戻る場合、R2には合成割込み番号が格納されます。

使用例¶

  1. ウルトラバイザーはSVMにいくつかのサービス（ハイパーコールや他の例外の処理など）をハイパーバイザーに提供させます。例外を処理した後、ハイパーバイザーはUV_RETURNを用いて制御をウルトラバイザーに戻します。

  2. ハイパーバイザーはこのウルトラコールを用いて制御をSVMに戻す必要があります。

ハイパーバイザーコールAPI¶

このドキュメントはUltravisorのサポートに必要なHypervisorの呼び出し（hypercall）について説明しています。hypercallはHypervisorが仮想マシンおよびUltravisorに対して提供するサービスです。

これらのhypercallのレジスタ使用は、Power Architecture Platform Reference (PAPR)ドキュメントで定義された他のhypercallと同様です。つまり、入力時、レジスタR3は要求される特定のサービスを識別し、R4からR11のレジスタには追加のパラメータが含まれます（必要に応じて）。出力時、レジスタR3には戻り値が含まれ、R4からR9のレジスタにはhypercallからの他の出力値が含まれます。

このドキュメントは現在実装または計画中のUltravisor使用に必要なhypercallのみをカバーしていますが、必要に応じて他のhypercallもここに追加できます。

すべてのhypercall/ultracallの完全な仕様は、最終的に公開/OpenPower版のPAPR仕様に含まれることになります。

ブロックレイヤーのキャッシュ（bcache）¶

大きな遅いRAID 6とSSDや複数のデバイスがある場合、それらをキャッシュとして利用できないかと考えるのは自然です。それがbcacheです。

bcacheのWikiは以下にあります：

https://bcache.evilpiepirate.org

これはbcache-toolsのgitリポジトリです：

https://git.kernel.org/pub/scm/linux/kernel/git/colyli/bcache-tools.git/

最新のbcacheカーネルコードはmainline Linuxカーネルから取得できます：

https://git.kernel.org/pub/scm/linux/kernel/git/torvalds/linux.git/

SSDの性能特性を基に設計されています。エラーストーンサイズのバケット単位で割り当てを行い、ハイブリッドのbtree/logを用いてキャッシュされたエクステント（1セクタからバケットサイズまでのどこでも）を追跡します。ランダムな書き込みを一切避けるように設計されており、エラーストーンを順次埋めてから削除を実行して再利用します。

ライトスルーおよびライトバックキャッシングの両方がサポートされています。ライトバックはデフォルトでオフですが、ランタイムで任意にオン/オフできます。bcacheはデータ保護に徹底しており、不完全なシャットダウンも信頼性高く処理します。（実際には「クリーンシャットダウン」の概念自体を持たず、安定したストレージに保存されるまで書き込みを完了とみなしません）

ライトバックキャッシングはキャッシュの大部分をバッファリングに使用します。バックインデックスの開始から終了まで順次バックインデックスに書き込みを行うため、汚染データの書き出しは常に順序的に実行されます。

SSDはランダムIOに優れているため、大規模なシーケンシャルIOをキャッシュするメリットは通常ありません。bcacheはシーケンシャルIOを検出するとスキップし、タスクごとのIOサイズのローリング平均を保持します。平均がしきい値を上回っている間は、そのタスクのすべてのIOをスキップします（たとえば、毎回シーク後に最初の512KBをキャッシュするのではなく）。バックアップや大容量ファイルのコピーはこのキャッシュを完全にバイパスします。

フラッシュメモリでのデータIOエラーが発生した場合、ディスクから読み込みまたはキャッシュエントリの無効化によって回復を試みます。回復不能なエラー（メタデータや汚染データ）が発生した場合、キャッシングは自動的に無効になります。汚染データがキャッシュに存在する場合は、まずライトバックキャッシングを無効にしてからすべての汚染データをフラッシュします。

開始方法：bcache utilをbcache-toolsリポジトリから取得してください。キャッシュデバイスとバックインデックスデバイスは使用前にフォーマットする必要があります：

bcache make -B /dev/sdb
bcache make -C /dev/sdc

bcache make 複数のデバイスを同時にフォーマットできる機能があります。バックインデックスデバイスとキャッシュデバイスを同時にフォーマットすれば、手動でアタッチする必要がありません：

bcache make -B /dev/sda /dev/sdb -C /dev/sdc

bcache-toolsが最新バージョンでなく、統合版の bcache ユーティリティを持っていない場合、 make-bcache ユーティリティを使用して、同じ-Bと-Cパラメータでbcacheデバイスをフォーマットできます。

bcache-tools は現在 udev ルールを提供しており、bcache デバイスがカーネルに即座に認識されます。udev が使われない場合、デバイスを手動で登録するには以下のようにします:

echo /dev/sdb > /sys/fs/bcache/register
echo /dev/sdc > /sys/fs/bcache/register

バックイングデバイスを登録すると、bcache デバイスが /dev に表示され、フォーマットして通常通り使用できます。ただし、新しい bcache デバイスを初めて使用する際は、キャッシュにアタッチするまでパステススモードで動作します。後で bcache を使用する予定がある場合は、すべての遅延デバイスをキャッシュなしで bcache バックイングデバイスとして事前に設定することをお勧めします。後からキャッシュデバイスを追加することも可能です。下記の「ATTACHING」セクションを参照してください。

デバイスは以下の通り表示されます:

/dev/bcache<N>

udev で表示される場合:

/dev/bcache/by-uuid/<uuid>
/dev/bcache/by-label/<label>

開始するには:

mkfs.ext4 /dev/bcache0
mount /dev/bcache0 /mnt

bcache デバイスは /sys/block/bcache<N>/bcache および /sys/fs//bcache/<cset-uuid>/ を通じて制御できます。

キャッシュデバイスはセット単位で管理され、複数のキャッシュを1セットに含むことはまだサポートされていませんが、今後メタデータと汚染データのミラーリングが可能になります。新しいキャッシュセットは /sys/fs/bcache/<UUID> に表示されます。

アタッチ¶

キャッシュデバイスとバックイングデバイスが登録された後、バックイングデバイスをキャッシュセットにアタッチしてキャッキングを有効にする必要があります。キャッシュセットにバックイングデバイスをアタッチするには、キャッシュセットの UUID を /sys/fs/bcache に指定して以下のように行います:

echo <CSET-UUID> > /sys/block/bcache0/bcache/attach

これは一度だけ行う必要があります。次回起動時にはすべての bcache デバイスを再登録するだけでよいです。バックイングデバイのキャッシュにデータが存在する場合、キャッシュが表示されるまで /dev/bcache<N> デバイスが作成されません。特にライトバックキャッシングが有効になっている場合に重要です。

起動中にキャッシュデバイスが消失し戻ってこない場合、バックイングデバイスを強制的に実行できます:

echo 1 > /sys/block/sdb/bcache/running

(/sys/block/sdb（あなたのバックイングデバイスの名前）を使用してください。/sys/block/bcache0 はまだ存在していないため、/sys/block/bcache0 は使えないです。パーティションを使用している場合、bcache ディレクトリは /sys/block/sdb/sdb2/bcache にあります）

バックイングデバイスは将来キャッシュセットが表示された場合でもそのキャッシュセットを使用しますが、すべてのキャッシュデータは無効になります。キャッシュに汚染データが含まれていた場合、ファイルシステムの復元は期待できません。ただし、ext4 の fsck は奇跡を起こすことがあります。

エラー処理¶

Bcache はキャッシュデバイスへの I/O エラーを透過的に処理し、通常の動作に影響を与えないように試みます。エラーが多すぎる場合（しきい値は設定可能で、デフォルトは 0）、キャッシュデバイスを停止し、すべてのバックイングデバイスをパステススモードに切り替えます。

  • キャッシュからの読み込みでエラーが発生した場合、バックイングデバイスから再度読み込みを試みます。

  • ライトスルー書き込みの場合、キャッシュへの書き込みが失敗した場合は、キャッシュ内のそのLBAのデータを無効化する処理に切り替えます（つまり、キャッシュをバイパスした書き込みと同じ処理を行います）。

  • ライトバック書き込みの場合、現在はエラーをファイルシステム/ユーザー空間に返しています。これは改善可能です - キャッシュをバイパスした書き込みとして再試行することで、書き込みエラーを回避できます。

  • 切断する際には、まずdirtyデータをフラッシュします（writebackモードで動作していた場合）。一部のdirtyデータの読み取りに失敗した場合でも、現在は特に賢い処理を行っていません。

Howto/cookbook¶

  1. キャッシュデバイスが欠落している状態でbcacheを起動する

バックイングデバイスの登録で改善されない場合、すでに存在しているため、キャッシュなしで強制的に起動する必要があります:

host:~# echo /dev/sdb1 > /sys/fs/bcache/register
[  119.844831] bcache: register_bcache() error opening /dev/sdb1: device already registered

次に、キャッシュデバイスが存在する場合、それを登録しようとします。ただし、デバイスが存在しない場合や登録に失敗した場合でも、キャッシュなしでbcacheを起動できます:

host:/sys/block/sdb/sdb1/bcache# echo 1 > running

これはwritebackモードで動作していた場合、データの喪失を引き起こす可能性があります。

  1. bcacheがキャッシュを検出できていない

    host:/sys/block/md5/bcache# echo 0226553a-37cf-41d5-b3ce-8b1e944543a8 > attach
[ 1933.455082] bcache: bch_cached_dev_attach() Couldn't find uuid for md5 in set
[ 1933.478179] bcache: __cached_dev_store() Can't attach 0226553a-37cf-41d5-b3ce-8b1e944543a8
[ 1933.478179] : cache set not found

この場合、キャッシュデバイスは起動時に登録されていなかったか、消失した後復帰したため、再登録が必要です:

host:/sys/block/md5/bcache# echo /dev/sdh2 > /sys/fs/bcache/register

  1. 破損したbcacheはデバイス登録時にカーネルをクラッシュします:

これは決して起こらないはずです。もし発生した場合は、バグが発見されたことになります！問題を以下の開発リストに報告してください: linux-bcache@vger.kernel.org

可能な限り多くの情報を提供してください（例: カーネルのdmesg出力など）。

  1. bcacheなしでのデータ復元:

bcacheがカーネルに存在しない場合でも、バックイングデバイス上のファイルシステムは8KiBオフセットで利用可能です。したがって、バックイングデバイスを–offset 8Kで作成したループデバイス、またはbcacheをフォーマット時に–data-offsetで指定した値を用いたループデバイスでアクセスできます bcache make.

例:

losetup -o 8192 /dev/loop0 /dev/your_bcache_backing_dev

これにより、/dev/loop0に変更のないバックイングデバイスのデータが表示されます

キャッシュデバイスがライトスルーモードの場合、キャッシュデバイスを削除してもデータを失いません。

  1. キャッシュデバイスの初期化

host:~# wipefs -a /dev/sdh2
16 bytes were erased at offset 0x1018 (bcache)
they were: c6 85 73 f6 4e 1a 45 ca 82 65 f5 7f 48 ba 6d 81

bcacheを有効にして再起動後、キャッシュを再構築して接続します:

host:~# bcache make -C /dev/sdh2
UUID:                   7be7e175-8f4c-4f99-94b2-9c904d227045
Set UUID:               5bc072a8-ab17-446d-9744-e247949913c1
version:                0
nbuckets:               106874
block_size:             1
bucket_size:            1024
nr_in_set:              1
nr_this_dev:            0
first_bucket:           1
[  650.511912] bcache: run_cache_set() invalidating existing data
[  650.549228] bcache: register_cache() registered cache device sdh2

バックイングデバイスを欠落した状態で起動:

host:/sys/block/md5/bcache# echo 1 > running

新しいキャッシュデバイスを接続:

host:/sys/block/md5/bcache# echo 5bc072a8-ab17-446d-9744-e247949913c1 > attach
[  865.276616] bcache: bch_cached_dev_attach() Caching md5 as bcache0 on set 5bc072a8-ab17-446d-9744-e247949913c1

  1. キャッシュデバイスの削除または交換:

    host:/sys/block/sda/sda7/bcache# echo 1 > detach
[  695.872542] bcache: cached_dev_detach_finish() Caching disabled for sda7

host:~# wipefs -a /dev/nvme0n1p4
wipefs: error: /dev/nvme0n1p4: probing initialization failed: Device or resource busy
Ooops, it's disabled, but not unregistered, so it's still protected

登録を解除する必要があります:

host:/sys/fs/bcache/b7ba27a1-2398-4649-8ae3-0959f57ba128# ls -l cache0
lrwxrwxrwx 1 root root 0 Feb 25 18:33 cache0 -> ../../../devices/pci0000:00/0000:00:1d.0/0000:70:00.0/nvme/nvme0/nvme0n1/nvme0n1p4/bcache/
host:/sys/fs/bcache/b7ba27a1-2398-4649-8ae3-0959f57ba128# echo 1 > stop
kernel: [  917.041908] bcache: cache_set_free() Cache set b7ba27a1-2398-4649-8ae3-0959f57ba128 unregistered

次に、デバイスを初期化します:

host:~# wipefs -a /dev/nvme0n1p4
/dev/nvme0n1p4: 16 bytes were erased at offset 0x00001018 (bcache): c6 85 73 f6 4e 1a 45 ca 82 65 f5 7f 48 ba 6d 81

  1. dm-crypt and bcache

まずbcacheを暗号化せずに設定し、その後/dev/bcache<N>上にdmcryptをインストールしてください。これにより、バックイングデバイスとキャッキングデバイスの両方をdmcryptで暗号化してからbcacheを上にインストールするよりも高速に動作します。[ベンチマーク？]

  1. 登録済みのbcacheを停止/解放して初期化および/または再作成します

バックイングまたはキャッキングデバイスがアクティブな状態で残っている場合、fdiskを実行して変更したパーティションテーブルを再登録することができません。そのような場合、すべてのbcache参照を解放する必要があります:

  1. /dev/bcache*に存在しますか？（ある場合もあります）

    そうであれば、簡単です:

    host:/sys/block/bcache0/bcache# echo 1 > stop

  2. バックイングデバイスがなくなった場合、この方法は機能しません:

    host:/sys/block/bcache0# cd bcache
bash: cd: bcache: No such file or directory

    このような場合、このbcacheを参照するdmcryptブロックデバイスをアンレジストレして解放する必要があります:

    host:~# dmsetup remove oldds1
bcache: bcache_device_free() bcache0 stopped
bcache: cache_set_free() Cache set 5bc072a8-ab17-446d-9744-e247949913c1 unregistered

    これにより、/sys/fs/bcacheからバックイングbcacheが削除され、その後再利用可能になります。これはbcacheが下位デバイスであるあらゆるブロックデバイススタッキングにおいて当てはまります。

  3. 他の場合でも、/sys/fs/bcache/を確認してください:

    host:/sys/fs/bcache# ls -l */{cache?,bdev?}
lrwxrwxrwx 1 root root 0 Mar  5 09:39 0226553a-37cf-41d5-b3ce-8b1e944543a8/bdev1 -> ../../../devices/virtual/block/dm-1/bcache/
lrwxrwxrwx 1 root root 0 Mar  5 09:39 0226553a-37cf-41d5-b3ce-8b1e944543a8/cache0 -> ../../../devices/virtual/block/dm-4/bcache/
lrwxrwxrwx 1 root root 0 Mar  5 09:39 5bc072a8-ab17-446d-9744-e247949913c1/cache0 -> ../../../devices/pci0000:00/0000:00:01.0/0000:01:00.0/ata10/host9/target9:0:0/9:0:0:0/block/sdl/sdl2/bcache/

    デバイス名は関連するUUIDを示します。そのディレクトリに移動してキャッシュを停止してください:

    host:/sys/fs/bcache/5bc072a8-ab17-446d-9744-e247949913c1# echo 1 > stop

    これによりbcache参照が解放され、他の用途でパーティションを再利用できるようになります。

パフォーマンスのトラブルシューティング¶

bcacheには多くの設定オプションとチューニングパラメータがあります。デフォルトは通常のデスクトップおよびサーバーワークロードに対して適切ですが、ベンチマーク時の最適な数値を得るために必要な設定ではありません。

  • バックイングデバイスのアライメント

    bcacheのデフォルトメタデータサイズは8kです。バックイングデバイスがRAIDベースの場合、ストライド幅の倍数でアライメントを確認してください bcache make –data-offset。今後ディスクアレイを拡張する予定がある場合、連続する素数をRAIDストライプサイズで乗算し、ディスクの倍数を取得してください。

    例えば：64k ストリーディングサイズの場合、以下のオフセットは多くの一般的なRAID5データスパイン数にアライメントを提供します:

    64k * 2*2*2*3*3*5*7 bytes = 161280k

    その空間は無駄ですが、わずか157.5MBでRAID 5ボリュームを以下のデータスパイン数に拡張できます（再アライメントせずに）:

    3,4,5,6,7,8,9,10,12,14,15,18,20,21 ...

  • 悪い書き込みパフォーマンス

    書き込みパフォーマンスが予想より低ければ、おそらく書き戻しモードで動作したいと考えていた可能性があります。これはデフォルトでは有効ではありません（成熟度の欠如によるものではなく、SSDに何かが起った場合データが失われるためです）:

    # echo writeback > /sys/block/bcache0/bcache/cache_mode

  • パフォーマンスが悪い、または予期しないSSDへのトラフィックがありません

    デフォルトでは、bcacheはすべてをキャッシュしません。順序的なIOをスキップしようと試みるため、ランダムなIOをキャッシュしたいのが本音です。10ギガバイトのファイルをコピーする際、その10ギガバイトのランダムにアクセスされるデータがキャッシュから押し出されるのを避けたいでしょう。

    キャッシュからの読み込みベンチマークを行いたい場合、最初にfioで8ギガバイトのテストファイルを書き込むと、その処理を無効にする必要があります。

    # echo 0 > /sys/block/bcache0/bcache/sequential_cutoff

    デフォルト（4MB）に戻すには、以下のようにします：

    # echo 4M > /sys/block/bcache0/bcache/sequential_cutoff

  • トラフィックは依然としてスピンナ（ディスク）へ行き、キャッシュミスが発生します。

    現実世界ではSSDがディスクに常に追いつくとは限りません。特に遅いSSDや、複数のディスクを1つのSSDでキャッシュしている場合、あるいは主に順序的なIOが行われる場合など、SSDでボトルネックになるのを避ける必要があります。

    これを避けるため、bcacheはキャッシュデバイスへのレイテンシーを追跡し、レイテンシーがしきい値を超えた場合にトラフィックを段階的に制限します（これは順序的なバイパスを減らすことで実現されます）。

    必要であれば、しきい値を0に設定してこの機能を無効化できます：

    # echo 0 > /sys/fs/bcache/<cache set>/congested_read_threshold_us
# echo 0 > /sys/fs/bcache/<cache set>/congested_write_threshold_us

    読み込みでは2000マイクロ秒（2ミリ秒）、書き込みでは20000マイクロ秒がデフォルトです。

  • 同じデータに対するキャッシュミスが引き続き発生します。

    時折人々を混乱させる最後の問題は、キャッシュミスにおけるキャッシュ整合性の処理の古いバグです。Btreeノードが満杯の場合、キャッシュミスでは新しいデータのキーを挿入できず、データがキャッシュに書き込まれません。

    実際には問題にはなりません。書き込みが発生するとすぐにBtreeノードが分割され、この現象が目立つほど多くの書き込みトラフィックを必要としません（特にbcacheのBtreeノードは巨大でデバイスの大規模な領域をインデックス化しているため）。ただしベンチマーク中にキャッシュをウォーム（温める）するために多数のデータを読み込むだけで、他のトラフィックがなければ問題になることがあります。

    解決策：キャッシュをウォームするには書き込みを行ってください、またはテストブランチを使用してください（そのブランチにはこの問題に対する修正が含まれています）。

Sysfs - バックインデバイス¶

利用可能：/sys/block/<bdev>/bcache、/sys/block/bcache*/bcacheおよび（接続されている場合）/sys/fs/bcache/<cset-uuid>/bdev*

アタッチ

キャッシュセットのUUIDをこのファイルにエコー（echo）することでキャッキングを有効化できます。

cache_mode

writethrough、writeback、writearound、noneのいずれかを指定できます。

clear_stats

このファイルに書き込むと、現在の統計値がリセットされます（日/時/5分間の減衰したバージョンはリセットされません）。

デタッチ

このファイルに書き込むと、キャッシュセットから接続を解除します。キャッシュに未保存データがある場合、そのデータが最初にフラッシュされます。

dirty_data

このバックイングデバイスのキャッシュ内の汚れたデータ量。キャッシュセットのバージョンとは異なり継続的に更新されるが、わずかにずれる可能性がある。

ラベル

基盤となるデバイスの名前。

読み込み予測

読み込み予測のサイズ。デフォルトは0。例えば1Mに設定すると、キャッシュミスの読み込みをそのサイズに丸めて読み込むが、既存のキャッシュエントリと重複しない。

稼働中

bcacheが稼働している場合（つまり/dev/bcacheデバイスが存在し、パステスモードかキャッキングか）に1を返す。

連続IO閾値

連続IOはこの閾値を超えるとキャッシュをバイパスする。最近の128つのIO履歴を追跡するため、一度にすべて読み終わらなくても連続IOを検出可能。

連続IOマージ

ゼロでない場合、bcacheは最後の128つのリクエストをリストとして保持し、新しいリクエストと比較して、前のリクエストの連続IOの継続であるかどうかを判定する。これは連続IO閾値が単一リクエストの最大許容連続サイズより大きい場合に必要。

状態

バックイングデバイスは次の4つの状態のいずれかになる:

キャッシュなし: キャッシュセットに一度も接続されていない。

クリーン: キャッシュセットに属し、汚れたキャッシュデータがない。

汚れた: キャッシュセットに属し、キャッシュされた汚れたデータがある。

不整合: ユーザーが汚れたデータがキャッシュされている状態でキャッシュセットが利用不可なときに強制的に実行したため、バックイングデバイス上のデータが破損している可能性がある。

停止

このファイルに書き込むことでbcacheデバイスを停止し、バックイングデバイスを閉じる。

キャッシュの書き戻し遅延

汚れたデータがキャッシュに書き込まれた際、かつ以前は汚れたデータを含んでいなかった場合、いくつかの秒待ってから書き戻しを開始する。デフォルトは30秒。

キャッシュの書き戻し割合

ゼロでない場合、bcacheはPD制御器を用いて背景の書き戻しを制御し、キャッシュ内の汚れたデータ量をこの割合に近づけるように調整する。

キャッシュの書き戻し速度

セクタ毎秒の速度。writeback_percentがゼロでない場合、背景の書き戻しはこの速度で制限される。bcacheが継続的に調整するが、ユーザーが設定することも可能。

キャッシュの書き戻し実行中

オフの場合、汚れたデータの書き戻しは一切行われない。キャッシュは満タンになるまでデータを追加し続ける。ベンチマーク用にのみ有効で、デフォルトはオン。

Sysfs - バックイングデバイスの統計情報¶

稼働中の累積合計のディレクトリと、過去1日/1時間/5分の減少するバージョンのディレクトリがあり、キャッシュセットディレクトリでも集計されている。

キャッシュヒット、キャッシュミス、キャッシュヒット比率

個々のIOごとにヒットとミスがカウントされます；部分的なヒットはミスとしてカウントされます。

キャッシュバイパスヒット、キャッシュバイパスミス

キャッシュをスキップする意図のIOのヒットとミスは依然としてカウントされますが、ここに分離して表示されます。

キャッシュミス衝突

キャッシュミスからキャッシュへのデータ挿入が予定されていたが、書き込みと競合しデータが既に存在していた場合のカウント（通常は0です。キャッシュミスの同期処理が再実装されたため）

IOエラー半減期、IOエラー制限

これらの値は、キャッシュを無効にする前に許容するエラー数を決定します。各エラーは半減期（#ios単位）で減衰します。減衰カウントがio_error_limitに達すると、汚染データが書き出され、キャッシュが無効になります。

ジャーナル遅延ミリ秒

ジャーナルの書き込みは、キャッシュフラッシュがより早く実行されるまで、このミリ秒数まで遅延します。デフォルトは100です。

ルート使用率パーセンテージ

ルートbtreeノードの使用率。この値が高すぎるとノードが分割し、ツリーの深さが増加します。

このファイルに書き込むと、キャッシュセットを停止します。すべての接続されたバックインデックスデバイスが停止するのを待機します。

ツリー深さ

btreeの深さ（単一ノードのbtreeは深さ0です）

登録解除

バックイングデバイスをすべて分離し、キャッシュデバイスを閉じます。汚染データが存在する場合、ライトバックキャッシュを無効にしてフラッシュを待機します。

btree_cache_max_chain

BTREEノードキャッシュのハッシュテーブルにおける最も長いチェーン。

freelistのサイズはnbucketsの百分率です。この値を書き込むことで、freelistに保持されるバケット数を増やすことができ、キャッシュサイズをランタイムで人工的に減らすことができます。主にテスト目的（異なるキャッシュサイズがヒット率に与える影響をテスト）ですが、バケットがfreelistに移動すると破棄されるため、SSDのガベージコレクションをより簡単にすることで、有効に予約領域を増やす効果があります。

発生したエラーの数（io_error_halflifeで減衰）。

metadata_written

すべての非データ書き込み（BTREE書き込みとその他のすべてのメタデータ）の合計。

nbuckets

このキャッシュ内の全バケット数。

キャッシュ内のデータが最近アクセスされた頻度に関する統計情報です。これにより、作業セットサイズを特定できます。Unusedはキャッシュにデータが含まれていない割合を示します。Metadataはbcacheのメタデータオーバーヘッドです。Averageはキャッシュバケットの平均優先度です。Nextは各優先度閾値を持つクォンタイルの一覧です。

written

キャッシュに書き込まれたすべてのデータの合計；btree_writtenと比較することで、bcacheにおける書き込み膨張量を示します。

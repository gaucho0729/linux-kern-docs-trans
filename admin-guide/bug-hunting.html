バグの位置を特定する¶

バグを報告する際には、バグの位置をカーネルソースファイルに直接示すと効果的です。その方法は2つあります。通常、 gdb を使用するのが簡単ですが、カーネルはデバッグ情報を含むように事前にコンパイルしておく必要があります。

gdb¶

GNUデバッガー（gdb)は、OOPSから正確なファイルと行番号を特定する最良の方法です。 vmlinux ファイル。

GDBの使用は、デバッグシンボルを含むコンパイルされたカーネルで最も効果的です。 CONFIG_DEBUG_INFO。これは、以下を実行することで設定できます：

$ ./scripts/config -d COMPILE_TEST -e DEBUG_KERNEL -e DEBUG_INFO

コンパイルされたカーネルでは、 CONFIG_DEBUG_INFO、OOPSからEIP値を単純にコピーできます：

EIP:    0060:[<c021e50e>]    Not tainted VLI

そしてGDBを使用して、その値を人間が読める形式に変換できます：

$ gdb vmlinux
(gdb) l *0xc021e50e

debug symbolsが有効でない場合、OOPSから関数オフセットを使用します： CONFIG_DEBUG_INFO そして、

EIP is at vt_ioctl+0xda8/0x1482

でカーネルを再コンパイルします。 CONFIG_DEBUG_INFO enabled:

$ ./scripts/config -d COMPILE_TEST -e DEBUG_KERNEL -e DEBUG_INFO
$ make vmlinux
$ gdb vmlinux
(gdb) l *vt_ioctl+0xda8
0x1888 is in vt_ioctl (drivers/tty/vt/vt_ioctl.c:293).

289           struct vc_data *vc = NULL;

293           if (VT_BUSY(vc_num))
294                   ret = -EBUSY;
295           else if (vc_num)
296                   vc = vc_deallocate(vc_num);
297           console_unlock();

、またはより詳細に表示したい場合は：

(gdb) p vt_ioctl
$1 = {int (struct tty_struct *, unsigned int, unsigned long)} 0xae0 <vt_ioctl>
(gdb) l *0xae0+0xda8

代わりに、オブジェクトファイルを使用できます：

$ make drivers/tty/
$ gdb drivers/tty/vt/vt_ioctl.o

objdump¶

カーネルのデバッグには、objdumpを使用し、クラッシュ出力のhexオフセットから有効なコード/アセンブリ行を見つけます。デバッグシンボルがない場合、アセンブリコードのみが表示されますが、カーネルにデバッグシンボルが含まれている場合、Cコードも利用可能です。(デバッグシンボルは、メニュー構成の「カーネルハッキング」メニューで有効化できます。) 例えば：

$ objdump -r -S -l --disassemble net/dccp/ipv4.o

バグの報告¶

バグが発生した場所を特定したら、その位置を確認して、自分で修正するか、アップストリームに報告できます。

アップストリームに報告するには、影響を受けたコードの開発に使用されるメールリストを特定する必要があります。これは、 get_maintainer.pl スクリプトを使用することで行えます。

例えば、gspcaのsonixj.cファイルでバグを見つけた場合、そのメンテナを取得するには：

$ ./scripts/get_maintainer.pl -f drivers/media/usb/gspca/sonixj.c
Hans Verkuil <hverkuil@xs4all.nl> (odd fixer:GSPCA USB WEBCAM DRIVER,commit_signer:1/1=100%)
Mauro Carvalho Chehab <mchehab@kernel.org> (maintainer:MEDIA INPUT INFRASTRUCTURE (V4L/DVB),commit_signer:1/1=100%)
Tejun Heo <tj@kernel.org> (commit_signer:1/1=100%)
Bhaktipriya Shridhar <bhaktipriya96@gmail.com> (commit_signer:1/1=100%,authored:1/1=100%,added_lines:4/4=100%,removed_lines:9/9=100%)
linux-media@vger.kernel.org (open list:GSPCA USB WEBCAM DRIVER)
linux-kernel@vger.kernel.org (open list)

注意してください。これは以下のアドレスを指します：

  • 最後にソースコードを修正した開発者(これはgitツリー内で行われた場合)。上記の例では、TejunとBhaktipriya(この特定のケースでは、このファイルの開発に関与した開発者はいません)；

  • ドライバメンテナ(Hans Verkuil)；

  • サブシステムメンテナ(Mauro Carvalho Chehab)；

  • ドライバおよび/またはサブシステムメールリスト(linux-media@vger.kernel.org);

  • Linuxカーネルメールリスト(linux-kernel@vger.kernel.org).

通常、バグを修正する最も速い方法は、コードの開発に使用されるメールリスト(linux-media ML)に報告し、ドライバメンテナ(Hans)をCCする方法です。

誰にレポートを送すべきかまったく分からなかったり、 get_maintainer.pl 何か役に立つ情報を提供しなかった場合は、送ってください。 linux-kernel@vger.kernel.org.

Oopsトレースに関するノート klogd¶

Linusと他のカーネル開発者をサポートするため、 klogd プロテクションフォールトの処理に特化した機能が大幅に組み込まれています。アドレス解決を完全にサポートするには、少なくとも sysklogd パッケージの1.3-pl3バージョンを使用してください。

プロテクションフォールトが発生した際、 klogd デーモンはカーネルログメッセージ内の重要なアドレスをシンボリックな同等物に自動的に変換します。この変換されたカーネルメッセージは、 whichever reporting mechanism klogd が使用している経路を通じて転送されます。プロテクションフォールトメッセージはメッセージファイルから簡単に切り出され、カーネル開発者に送信できます。

2つのアドレス解決タイプが klogdによって実行されます。1つ目は静的変換で、2つ目は動的変換です。静的変換はSystem.mapファイルを使用します。静的変換を行うには、 klogd デーモンがデーモン初期化時にシステムマップファイルを検索できる必要があります。klogdのmanページを参照してください。 klogd mapファイルの検索方法についての情報が記載されています。

動的アドレス変換は、カーネルロード可能なモジュールが使用されている場合に重要です。カーネルモジュールのメモリはカーネルの動的メモリプールから割り当てられるため、モジュールの開始位置やモジュール内の関数やシンボルの位置は固定ではありません。

カーネルは、プログラムがロードされたモジュールを確認し、そのメモリ位置を取得するシステムコールをサポートしています。これらのシステムコールを使用して、klogdデーモンはシンボルテーブルを構築し、ロード可能なカーネルモジュール内で発生したプロテクションフォールトをデバッグできます。

最低限、klogdはプロテクションフォールトを発生させたモジュールの名前を提供します。開発者がロード可能なモジュールからシンボル情報をエクスポートした場合、追加のシンボリック情報が利用できる場合があります。

カーネルモジュール環境は動的であるため、デーモンが通知を受けるためのメカニズムが必要です klogd モジュール環境の変化が発生した際にデーモンを通知します。klogdが現在実行中のデーモンにシンボル情報の再取得を通知するためのコマンドラインオプションが利用可能です。詳しくは klogd マニュアルページをご参照ください。

sysklogdの配布物にパッチが含まれており、このパッチによりパッケージがモジュールがロードまたはアンロードされるたびに自動的にklogdに通知します。このパッチを適用することで、カーネルロード可能なモジュールで発生する保護エラーのデバッグにほぼ無感覚なサポートが得られます。 modules-2.0.0 以下の例は、ロード可能なモジュールで発生する保護エラーの処理例です。

USB4 and Thunderbolt¶

USB4はThunderbolt 3プロトコルをベースとした公開仕様で、レジスタレベルなどいくつかの点で違いがあります。コネクションマネージャーはホストルーター（ホストコントローラー）上で動作するエンティティで、ルーターの列挙とトンネルの確立を担当します。コネクションマネージャーはファームウェアまたはソフトウェアのどちらでも実装可能です。通常のPCはThunderbolt 3および初期のUSB4対応システムにファームウェアベースのコネクションマネージャーを搭載しています。一方、Appleのシステムではソフトウェアベースのコネクションマネージャーを使用し、後続のUSB4準拠デバイスも同様に実装されています。

LinuxのThunderboltドライバは両方をサポートしており、実行時に使用するコネクションマネージャーの実装を検出可能です。安全を確保するため、Linuxのソフトウェアコネクションマネージャーはセキュリティレベルを宣伝します user これはPCIeトンネリングがデフォルトで無効になることを意味します。以下のドキュメンテーションは両実装に適用されますが、ソフトウェアコネクションマネージャーは user セキュリティレベルのみをサポートしており、IOMMUベースのDMA保護と併せて使用されることが予期されます。

セキュリティレベルとその使用方法¶

ここで提示されるインターフェースはエンドユーザー向けではありません。代わりに、低レイヤーの詳細を処理し、承認されたデバイスのデータベースを保持し、ユーザーに新しい接続を尋ねるユーザー空間ツールが存在すべきです。

Thunderboltデバイスのsysfsインターフェースに関する詳細情報は Documentation/ABI/testing/sysfs-bus-thunderbolt.

手動での作業なしに任意のデバイスを接続したいユーザーは、以下の行を /etc/udev/rules.d/99-local.rules:

ACTION=="add", SUBSYSTEM=="thunderbolt", ATTR{authorized}=="0", ATTR{authorized}="1"

に追加することで、デバイスが出現するたびに自動的に承認されます。ただし、これはセキュリティレベルをバイパスし、DMA攻撃へのシステムの脆弱性を生じますので注意してください。

Intel Falcon Ridge Thunderboltコントローラーから始めて4つのセキュリティレベルが利用可能となりました。Intel Titan Ridgeではさらに1つ（usbonly）のセキュリティレベルが追加されました。これは接続されたデバイスがDMAマスターとなり、CPUやOSが知らないうちにホストメモリの内容を読み取れる可能性があるためです。IOMMUを設定することでこのリスクを防ぐ方法がありますが、さまざまな理由により常に利用可能ではありません。

セキュリティレベルは以下の通りです：

none

すべてのデバイスはファームウェアによって自動的に接続されます。ユーザーの承認は必要ありません。BIOS設定ではこれは通常 レガシーモード.

user

ユーザーにデバイスが接続可能かどうかを尋ねます。利用可能なデバイス識別情報を通じて、ユーザーが決定を行います。BIOS設定ではこれは通常 /sys/bus/thunderbolt/devicesユーザー承認モード 一意のID.

secure

ユーザーにデバイスが接続可能かどうか尋ねられます。UUIDに加えて、デバイス（セキュアコネクトをサポートしている場合）には、ランダムなキーがsysfs属性に書き込まれたに基づいて一致するはずのチャレンジが送信されます key sysfs属性。BIOS設定では通常 ワンタイム保存鍵.

dponly

ファームウェアがディスプレイポートとUSBのトンネルを自動的に作成します。PCIeトンネルは行われません。BIOS設定では通常 ディスプレイポートのみ.

usbonly

ファームウェアがドック内のUSBコントローラーとディスプレイポートのトンネルを自動的に作成します。ドックの下流にあるすべてのPCIeリンクは削除されます

現在のセキュリティレベルは /sys/bus/thunderbolt/devices/domainX/security オプションを指定する必要があります。形式は以下の通りです： domainX Thunderboltドメインはホストコントローラーが管理するものです。Thunderboltホストコントローラーごとに通常1つのドメインがあります

セキュリティレベルが user または secure PCIeトンネルが作成される前に接続されたデバイスはユーザーによる承認が必要です（例：PCIeデバイスが表示される）

接続されたThunderboltデバイスはsysfsの下に表示されます /sys/bus/thunderbolt/devices。デバイスディレクトリには、デバイスの特定に使用できる情報（名前やUUIDを含む）が含まれています

セキュリティレベルが user または secure¶

デバイスが接続されるとsysfsに以下のように表示されます：

/sys/bus/thunderbolt/devices/0-1/authorized   - 0
/sys/bus/thunderbolt/devices/0-1/device       - 0x8004
/sys/bus/thunderbolt/devices/0-1/device_name  - Thunderbolt to FireWire Adapter
/sys/bus/thunderbolt/devices/0-1/vendor       - 0x1
/sys/bus/thunderbolt/devices/0-1/vendor_name  - Apple, Inc.
/sys/bus/thunderbolt/devices/0-1/unique_id    - e0376f00-0300-0100-ffff-ffffffffffff

以下の authorized 属性が0を読み込むと、PCIeトンネルがまだ作成されていません。ユーザーは以下のコマンドを実行してデバイスを承認できます：

# echo 1 > /sys/bus/thunderbolt/devices/0-1/authorized

これによりPCIeトンネルが作成され、デバイスが接続されます

デバイスがセキュアコネクトをサポートし、ドメインセキュリティレベルが secureに設定されている場合、追加の属性 key があり、今後の接続における認証とチャレンジに使用されるランダムな32バイト値を保持できます：

/sys/bus/thunderbolt/devices/0-3/authorized   - 0
/sys/bus/thunderbolt/devices/0-3/device       - 0x305
/sys/bus/thunderbolt/devices/0-3/device_name  - AKiTiO Thunder3 PCIe Box
/sys/bus/thunderbolt/devices/0-3/key          -
/sys/bus/thunderbolt/devices/0-3/vendor       - 0x41
/sys/bus/thunderbolt/devices/0-3/vendor_name  - inXtron
/sys/bus/thunderbolt/devices/0-3/unique_id    - dc010000-0000-8508-a22d-32ca6421cb16

キーフィールドはデフォルトで空です

ユーザーがセキュアコネクトを使用したくない場合は、単に echo 1 から authorized 属性と、セキュリティレベルの user の場合と同じ方法でPCIeトンネルが作成されます

ユーザーがセキュアコネクトを使用する場合、デバイスが最初に接続されるときにキーを生成してデバイスに送信する必要があります：

# key=$(openssl rand -hex 32)
# echo $key > /sys/bus/thunderbolt/devices/0-3/key
# echo 1 > /sys/bus/thunderbolt/devices/0-3/authorized

これによりデバイスが接続されました（PCIeトンネルが作成されました）さらに、キーはデバイスNVMに保存されます

次回デバイスが接続されるとき、ユーザーは同じキーを使用してデバイスを検証（チャレンジ）できます：

# echo $key > /sys/bus/thunderbolt/devices/0-3/key
# echo 2 > /sys/bus/thunderbolt/devices/0-3/authorized

デバイスが返すチャレンジがキーに基づいて予期されるものと一致する場合、デバイスは接続されPCIeトンネルが作成されます。ただし、チャレンジに失敗した場合、トンネルは作成されず、ユーザーにエラーが返されます

ユーザーがまだデバイスを接続したい場合は、キーなしでデバイスを承認するか、新しいキーを書き込み1を authorized デバイスのNVMに保存された新しいキーを取得するためのファイル。

IOMMUを用いたDMA保護¶

2018年以降の最近のシステムでThunderboltポートを搭載している場合、IOMMUをネイティブでサポートしている可能性があります。これはThunderboltセキュリティがIOMMUによって処理されるため、接続されたデバイスがドライバによって割り当てられたメモリ領域以外の領域にアクセスできないことを意味します。Linuxがこのようなシステム上で動作している場合、ユーザーがすでに有効にしていない場合でも自動的にIOMMUが有効になります。このようなシステムは以下の方法で識別できます。 1 from /sys/bus/thunderbolt/devices/domainX/iommu_dma_protection 属性。

この場合、ドライバは特別な処理を行いませんが、DMA保護はIOMMUによって処理されるため、セキュリティレベル（設定されている場合）は冗長になります。そのため、一部のシステムではセキュリティレベルを noneに設定されています。他のシステムではセキュリティレベルを user に設定されているため、古いOSへのロールバックをサポートしています。IOMMU DMA保護が有効になっているときにデバイスを自動的に認証したいユーザーは、以下の udev ルール:

ACTION=="add", SUBSYSTEM=="thunderbolt", ATTRS{iommu_dma_protection}=="1", ATTR{authorized}=="0", ATTR{authorized}="1"

Thunderboltデバイス、ホスト、リタイマのNVMアップグレード¶

ほとんどの機能はホストコントローラーまたはデバイス上で動作するファームウェアで処理されるため、可能な限りファームウェアを最新バージョンにアップグレードし、バグを修正することが重要です。通常、OEMはサポートサイトからこのファームウェアを提供します。

また、一部のマシン用ファームウェアをダウンロードするためのリンクが含まれる中心的なサイトもあります:

Thunderboltアップデート

デバイス、ホスト、リタイマのファームウェアをアップグレードする前に、アップグレードが適切であることを確認してください。これをしないと、特別なツールなしでデバイスが正しく使用できなくなる可能性があります！

Apple MacのホストNVMアップグレードはサポートされていません。

NVMイメージをダウンロードした後、Thunderboltデバイスを接続してホストコントローラーが表示されるようにしてください。接続するデバイスはどれでも構いません（デバイスのNVMをアップグレードする場合はその特定のデバイスを接続する必要があります）。

注意：OEM固有のコントローラーを起動するための「フォースパワーアップ」方法がシステムに存在する場合があります。その場合はThunderboltデバイスを接続する必要はありません。

その後、ホストまたはデバイスのNVMの非アクティブ部分にファームウェアを書き込むことができます。例として、Intel NUC6i7KYK（Skull Canyon）ThunderboltコントローラーのNVMアップグレード手順を以下に示します：

# dd if=KYK_TBT_FW_0018.bin of=/sys/bus/thunderbolt/devices/0-0/nvm_non_active0/nvmem

操作が完了した後、NVM認証およびアップグレードプロセスを以下のようにトリガーできます：

# echo 1 > /sys/bus/thunderbolt/devices/0-0/nvm_authenticate

エラーが返されない場合、ホストコントローラーは短時間で消失します。再び出現した後、ドライバーが認識し、完全な電源サイクルを開始します。ある程度時間が経つとホストコントローラーが再度出現し、この時点で正常に動作するはずです。

新しいNVMファームウェアがアクティブになっているかを確認するには、以下のコマンドを実行します：

# cat /sys/bus/thunderbolt/devices/0-0/nvm_authenticate
0x0
# cat /sys/bus/thunderbolt/devices/0-0/nvm_version
18.0

もし nvm_authenticate 0x0以外の値を含む場合、それは最後の認証サイクルで発生したエラーコードを示し、NVMイメージの認証に失敗したことを意味します。

NVMemデバイスの名前を確認してください nvm_activeN および nvm_non_activeN NVMemサブシステムで登録された順序に依存します。名前のNはNVMemサブシステムによって追加された識別子です。

ホストコントローラーがセーフモードにあるときにNVMをアップグレードする¶

既存のNVMが正しく認証されていない（または存在しない）場合、ホストコントローラーはセーフモードに移行します。このモードでは、新しいNVMイメージをフラッシュする機能のみが利用可能です。このモードでは読み込み nvm_version 失敗します ENODATA およびデバイス識別情報が不足しています。

このモードから回復するには、ホストコントローラーに有効なNVMイメージをフラッシュする必要があります。これは前章で説明されている方法と同じように行います。

スリーブケーブルを介したネットワーク接続¶

スリーブ技術は、スリーブケーブルで接続された2つのホスト間のソフトウェア通信を可能にします。

スリーブリンクを介して任意のトラフィックをトンネルすることは可能ですが、現在はApple ThunderboltIPプロトコルのみをサポートしています。

もう一方のホストがWindowsまたはmacOSを実行している場合、2つのホスト間にスリーブケーブルを接続するだけで、 thunderbolt-net ドライバーが自動的にロードされます。もう一方のホストもLinuxを実行している場合は、 thunderbolt-net 一方のホストで手動でロードする必要があります（どちらのホストでも構いません）：

# modprobe thunderbolt-net

これにより、もう一方のホストでモジュールのロードが自動的に実行されます。ドライバーがカーネルイメージに組み込まれている場合、何も操作する必要はありません。

ドライバーはスリーブポートごとに1つの仮想イーサネットインターフェースを作成し、インターフェース名は thunderbolt0 などと名付けられます。この時点で、標準のユーザースペースツール（例： ifconfig ）を使用してインターフェースを構成するか、GUIで自動的に処理させることができます。

強制電源¶

多くのOEMは、スリーブコントローラーの電源を「オン」状態に強制的に設定する方法を提供しており、接続されていない場合でも可能です。あなたのマシンがこれをサポートしている場合、WMIバスで「force_power」というsysfs属性として公開されます。

たとえば、intel-wmi-thunderboltドライバーは以下のパスにこの属性を公開します：

/sys/bus/wmi/devices/86CCFD48-205E-4A77-9C48-2021CBEDE341/force_power

強制電源をオンにするには、この属性ファイルに1を書き込みます。強制電源を無効にするには、この属性ファイルに0を書き込みます。

注意: 現在、プラットフォームの強制電源状態を照会することはできません。

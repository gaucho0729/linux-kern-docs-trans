汚染されたカーネル¶

カーネルが何か問題を調査する際に重要になる出来事があった場合、自身を「汚染（tainted）」とマークします。あまり心配する必要はありません。ほとんどの場合、汚染されたカーネルを実行しても問題ありません。この情報は、誰かが問題を調査する際に実際の原因が汚染イベントである可能性があるため、主にそのような場面で重要になります。そのため、開発者は汚染されたカーネルからのバグレポートをよく無視するため、汚染されていないカーネルで問題を再現するように試してください。

注意：カーネルが汚染状態を解除しても（たとえば、専用カーネルモジュールをアンロードしても）、カーネルが信頼できない状態であることを示すため、汚染状態は維持されます。これはまた、カーネルが内部問題（「カーネルのバグ」）、回復可能なエラー（「カーネルのオプス」）、または回復不可能なエラー（「カーネルのパニック」）を検出すると、汚染状態をログに記録し、デバッグ情報を出力するためです。 dmesg 出力。また、カーネルが実行中に汚染状態を確認するには、以下のファイルを /proc/.

汚染フラグのbugs、oopsまたはpanicsメッセージ¶

イベント発生時のカーネルの汚染状態は、'CPU:'で始まる行の上部に表示されます。その下には、汚染の原因となったプロセスID（'PID:'）と、イベントをトリガーしたコマンドの短縮名（'Comm:'）の後に、汚染の理由が表示されます。

BUG: unable to handle kernel NULL pointer dereference at 0000000000000000
Oops: 0002 [#1] SMP PTI
CPU: 0 PID: 4424 Comm: insmod Tainted: P        W  O      4.20.0-0.rc6.fc30 #1
Hardware name: Red Hat KVM, BIOS 0.5.1 01/01/2011
RIP: 0010:my_oops_init+0x13/0x1000 [kpanic]
[...]

イベント発生時のカーネルが汚染されていなかった場合、'Not tainted: 'と表示されます。汚染されていた場合は、'Tainted: 'とその後に文字（アルファベットまたはスペース）が表示されます。上の例では以下のようになります：

Tainted: P        W  O

これらの文字の意味は以下の表で説明されています。この例では、カーネルが以前に汚染された理由として、専用モジュール（P)がロードされ、警告（W)が発生し、外部でビルドされたモジュール（O)がロードされたことが原因です。他の文字をデコードする場合は、以下の表をご参照ください。

実行時における汚染状態のデコード¶

実行時においては、以下のファイルを読み込むことで汚染状態を照会できます。 cat /proc/sys/kernel/tainted。このファイルが 0を返す場合、カーネルは汚染されていません。他の数字が返る場合は、汚染の原因が表示されます。この数字をデコードする最も簡単な方法は、スクリプト tools/debugging/kernel-chktaintを使用することです。あなたのディストリビューションでは、パッケージ名 linux-tools または kernel-toolsとして配布されている場合があります。なければ、 git.kernel.org からダウンロードし、 sh kernel-chktaintで実行すると、前述のログに記載されたステートメントを含むマシンで以下のようになります：

Kernel is Tainted for following reasons:
 * Proprietary module was loaded (#0)
 * Kernel issued warning (#9)
 * Externally-built ('out-of-tree') module was loaded  (#12)
See Documentation/admin-guide/tainted-kernels.rst in the Linux kernel or
 https://www.kernel.org/doc/html/latest/admin-guide/tainted-kernels.html for
 a more details explanation of the various taint flags.
Raw taint value as int/string: 4609/'P        W  O     '

自分で数値をデコードしてみることができます。この場合のように、カーネルが汚染された原因が1つだけであれば、以下の表で数値を見つけることができます。複数の原因がある場合は、ビットフィールドとして扱われており、各ビットが特定の汚染タイプの存在または absence を示します。この処理は前述のスクリプトに任せるのが最善ですが、すぐに確認が必要な場合は、以下のシェルコマンドを使用して設定されているビットを確認できます。

$ for i in $(seq 18); do echo $(($i-1)) $(($(cat /proc/sys/kernel/tainted)>>($i-1)&1));done

汚染に関する詳細な説明¶

  1. G すべてのロードされたモジュールがGPLまたは互換ライセンスを持つ場合 P 任意のプロパティモジュールがロードされた場合。MODULE_LICENSEが設定されていないか、insmodがGPL互換と認識しないMODULE_LICENSEを持つモジュールはプロパティとみなされます。

  2. F 任意のモジュールが強制的にロードされた場合 insmod -f, ' ' すべてのモジュールが通常通りロードされた場合

  3. S SMPカーネルで動作するハードウェアがマルチプロセッサ動作を安全と認定されていない場合にoopsが発生した場合。現在はSMPをサポートしないさまざまなAthlonプロセッサでのみ発生します。

  4. R モジュールが強制的にアンロードされた場合 rmmod -f, ' ' すべてのモジュールが通常通りアンロードされた場合

  5. M 任意のプロセッサがMachine Check Exceptionを報告した場合 ' ' Machine Check Exceptionが発生していない場合

  6. B ページリリース関数が不良なページ参照または予期しないページフラグを見つけた場合。これはハードウェアの問題またはカーネルのバグを示しており、ログにこの汚染が発生した理由を示す他の情報があるはずです。

  7. U ユーザーまたはユーザーアプリケーションがTaintedフラグを設定することを明示的に要求した場合 ' ' それ以外の場合

  8. D カーネルが最近死んだ場合、つまりOOPSまたはBUGが発生した場合

  9. A ACPIテーブルが上書きされた場合

  10. W カーネルが以前に警告を発した場合。(ただし、一部の警告はより特定の汚染フラグを設定する可能性があります。)

  11. C スタジングドライバーがロードされた場合

  12. I プラットフォームファームウェア（BIOSなど）に深刻なバグがあるため、カーネルが回避処理を行っている場合

  13. O 外部でビルドされた（「out-of-tree」）モジュールがロードされた場合

  14. E モジュール署名をサポートするカーネルで署名のないモジュールがロードされた場合

  15. L システムで以前にソフトロックアップが発生した場合

  16. K カーネルがライブパッチを適用された場合

  17. X 補助的な汚染、Linuxディストリビューションで定義・使用

  18. T ランダム構造プラグイン(randstruct)でビルドされ、意図的に極めて異常なカーネル構造レイアウト（パフォーマンスに悪影響を及ぼすものも含む）を生成することが可能です。デバッグ時にはこの点を理解しておくことが重要です。ビルド時に設定されています。

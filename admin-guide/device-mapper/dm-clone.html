dm-clone¶

はじめに¶

dm-clone は、既存の読み取り専用ソースデバイスを、書き込み可能な宛先デバイスに1対1で複製するデバイスマッパーターゲットです。このターゲットは、すべてのデータが即座に表示される仮想ブロックデバイスを提供し、読み取りと書き込みを適切にリダイレクトします。

dm-clone の主な用途は、遠隔地にある高遅延、読み取り専用、アーカイブ型のブロックデバイスを、高速で低遅延なプライマリ型の書き込み可能なデバイスに複製することです。複製されたデバイスは即座に表示/マウント可能で、ソースデバイスのデータを宛先デバイスに複製する作業はユーザーI/Oと並行してバックグラウンドで行われます。

たとえば、ネットワークストレージプロトコル（NBD、ファイバー・チャネル、iSCSI、AoEなど）を通じてアクセス可能な読み取り専用コピーからアプリケーションのバックアップを復元し、ローカルのSSDまたはNVMeデバイスに移すことで、復元が完了するのを待つことなく即座にデバイスを使用できます。

複製が完了した後、dm-clone テーブルは完全に削除され、リニアテーブルなどに置き換えることができます（例：宛先デバイスに直接マッピングする）。

dm-clone ターゲットは、スリムプロビジョニングターゲットが使用するメタデータライブラリを再利用します。

用語集¶

ハイドレーション

ソースデバイスの同じ領域からデータを宛先デバイスの領域にコピーするプロセス、つまりソースから宛先への領域のコピー。

領域がハイドレーションされると、その領域に関するすべてのI/O操作を宛先デバイスにリダイレクトします。

設計¶

サブデバイス¶

このターゲットは、後に詳しく説明する他のパラメータとともに3つのデバイスを渡して構築されます：

  1. ソースデバイス - 複製される読み取り専用デバイスで、ハイドレーションの元となるデバイス。

  2. 宛先デバイス - ハイドレーションの対象となるデバイスで、ソースデバイスのクローンになるデバイス。

  3. 小さなメタデータデバイス - 宛先デバイスで既に有効な領域（ハイドレーション済みの領域またはユーザーI/Oで直接書き込まれた領域）を記録します。

宛先デバイスのサイズは、ソースデバイスのサイズ以上でなければなりません。

領域¶

dm-clone は、ソースと宛先デバイスを固定サイズの領域に分割します。領域はハイドレーションの単位であり、ソースから宛先にコピーされる最小のデータ量です。

dm-clone デバイスを作成する際、領域サイズを設定できます。推奨される領域サイズはファイルシステムのブロックサイズ（通常4KB）と同じです。領域サイズは8セクタ（4KB）から2097152セクタ（1GB）までで、2の累乗である必要があります。

ハイドレーションされた領域の読み取りと書き込みは、宛先デバイスから処理されます。

未ヒドレートの領域への読み込みは、ソースデバイスから直接処理されます。

未ヒドレートの領域への書き込みは、該当領域がヒドレートされるのを待ってから処理され、ヒドレートは即座に開始されます。

注意：領域サイズに等しいサイズの書き込みリクエストは、ソースデバイスから該当領域をコピーせず、直接宛先デバイスの領域を上書きします。

Discards¶

dm-cloneは、ヒドレートされていない範囲へのディスカードリクエストを、そのリクエストでカバーする領域のヒドレートをスキップするヒントと解釈します。つまり、ソースから宛先デバイスへの領域データのコピーをスキップし、メタデータのみを更新します。

宛先デバイスがディスカードをサポートする場合、dm-cloneはデフォルトでディスカードリクエストをそのデバイスに伝達します。

バックグラウンドヒドレート¶

dm-cloneは、ソースデバイスから宛先デバイスへ連続的にデータをコピーし、すべてのデバイスがコピーされるまで続きます。

ソースデバイスから宛先デバイスへのデータコピーは帯域幅を消費します。ユーザーはスロットルを設定して、一度にコピーされるデータ量を制限できます。さらに、dm-cloneはデバイスへのユーザーI/Oトラフィックを考慮し、I/Oが進行中であるときにバックグラウンドヒドレートを一時停止します。

メッセージ hydration_threshold <#regions> は、コピーされる領域の最大数を設定するためのパラメータで、デフォルトは1領域です。

dm-cloneは、dm-kcopydを使用してソースデバイスの一部を宛先デバイスにコピーします。デフォルトでは、領域サイズに等しいサイズのコピーリクエストを発行します。メッセージ hydration_batch_size <#regions> は、これらのコピーリクエストのサイズを調整するためのパラメータです。ヒドレートバッチサイズを増やすと、dm-cloneが連続する領域をバッチ処理するようになり、この数の領域ごとにデータをコピーします。

宛先デバイスのヒドレートが完了すると、ユーザー空間にdmイベントが送信されます。

ディスク上のメタデータの更新中¶

ディスク上のメタデータは、FLUSHまたはFUA bioが書き込まれるたびにコミットされます。このようなリクエストがなければ、秒単位でコミットされます。これは、dm-cloneデバイスが揮発性のライトキャッシュを持つ物理ディスクのように動作することを意味します。電源が切れた場合、最近の書き込みが失われる可能性があります。ただし、クラッシュに関係なくメタデータは常に一貫しています。

例¶

ファイルシステムを含むデバイスをクローンする¶

  1. dm-cloneデバイスを作成する

    dmsetup create clone --table "0 1048576000 clone $metadata_dev $dest_dev \
  $source_dev 8 1 no_hydration"

  2. デバイスをマウントし、ファイルシステムをトリムします。dm-cloneはファイルシステムから送信されるdiscardを解釈し、未使用の領域をハイドレートしません

    mount /dev/mapper/clone /mnt/cloned-fs
fstrim /mnt/cloned-fs

  3. 宛先デバイスのバックグラウンドハイドレーションを有効にする

    dmsetup message clone 0 enable_hydration

  4. ハイドレーションが完了すると、dm-cloneテーブルを線形テーブルに置き換えることができます

    dmsetup suspend clone
dmsetup load clone --table "0 1048576000 linear $dest_dev 0"
dmsetup resume clone

    メタデータデバイスはもはや必要なく、安全に破棄したり他の用途に再利用したりできます

既知の問題¶

  1. 未ハイドレートの領域への読み込みをソースデバイスにリダイレクトします。ソースデバイスの読み取りに高いレイテンシーがあり、ユーザーが同じ領域を繰り返し読み取る場合、この動作はパフォーマンスを低下させる可能性があります。これらの読み込みをヒントとして、関連する領域をより早くハイドレートするようにすべきです。現在は、これらの領域をページキャッシュに保存しているため、ソースデバイスから複数回読み取る必要がないようにしています

  2. ハイドレーションが完了後、インコアリソース（ハイドレートされている領域を追跡するビットマップなど）を解放します

  3. バックグラウンドでのハイドレーション中に、ソースデバイスの読み込みまたは宛先デバイスへの書き込みに失敗した場合、エラーメッセージを出力しますが、ハイドレーションプロセスは成功するまで無限に続きます。複数の失敗後にバックグラウンドハイドレーションを停止し、ユーザー空間に通知するdmイベントを発行すべきです。

なぜしないのか？¶

dm-cloneを実装する前に、以下の代替案を検討しました：

  1. ソースデバイスのサイズに等しいキャッシュサイズでdm-cacheを使用し、新しいクローンポリシーを実装する：

    • 結果として得られるキャッシュデバイスは、ソースデバイスの1対1のミラーデバイスではなく、そのためクローンが完了した後でもキャッシュデバイスを削除できません。

    • dm-cacheはソースデバイスに書き込みを行うため、ソースデバイスを読み取り専用として扱うという要件を満たしません。

    • キャッシュはクローンとは意味的に異なります。

  2. ソースデバイスと同等のCOWデバイスを使用してdm-snapshotを使用する：

    • dm-snapshotはCOWデバイスにメタデータを保存するため、結果として得られるデバイスはソースデバイスの1対1のミラーデバイスではありません。

    • バックグラウンドコピーのメカニズムがありません。

    • dm-snapshotは、待機中の例外が完了するたびにメタデータをコミットする必要がありますが、クローンの場合はこれほど厳格にしなくてもよく、FLUSHまたはFUA bioが書き込まれるたびに、またはdm-thinやdm-cacheのように定期的にメタデータをコミットすることで十分です。これによりパフォーマンスが大幅に向上します。

  3. dm-mirrorを使用する：ミラー対象はバックグラウンドでのコピー/ミラーリングメカニズムを持っていますが、すべてのミラーに書き込むため、ソースデバイスを読み取り専用として扱うという要件を満たしません。

  4. dm-thinの外部スナップショット機能を使用する。このアプローチはすべての代替案の中で最も有望です。なぜなら、スパースプロビジョニングされたボリュームはソースデバイスの1対1のミラーデバイスであり、未プロビジョニング/未クローンの領域への読み込みと書き込みをdm-cloneと同じように処理するからです。

    それでも：

    • バックグラウンドコピーのメカニズムはありませんが、実装することは可能です。

    • 最も重要なのは、クローンプロセスの宛先として任意のブロックデバイスをサポートすることであり、スパースプロビジョニングされたボリュームに限定しないことです。スパースプロビジョニングには、スパースボリュームのマッピングを維持するために必要なメタデータオーバーヘッドがあり、これによりパフォーマンスが大幅に低下します。

    さらに、デバイスのクローン化はスパースプロビジョニングの使用を強制するものではありません。一方で、スパースプロビジョニングを使用したい場合は、dm-cloneの宛先デバイスとしてスパースLVを使用するだけで済みます。

デバイスマッパースナップショットのサポート¶

Device-mapper は、大規模なデータコピーなしに以下の操作を可能にします:

  • 任意のブロックデバイス（マウント可能なブロックデバイス）のスナップショットを作成し、元のコンテンツに干渉することなく、ブロックデバイスの保存された状態を読み書き可能な状態で保持する;

  • 同じデータストリームの複数の異なるバージョンである「デバイスのフォーク」を作成する。

  • ブロックデバイスのスナップショットを元のデバイスに戻すことができます。

最初の2つのケースでは、変更されたデータのチャンクのみをコピーし、別個のコピー・オン・ライト (COW) ブロックデバイスでストレージします。

スナップショットの統合では、COW ストレージの内容を元のデバイスに戻します。

3つの dm テンプレートが利用可能です: snapshot, snapshot-origin, および snapshot-merge。

  • snapshot-origin <origin>

これは通常、1つ以上のスナップショットがベースとなるデバイスです。読み込みは直接バックイングデバイスにマッピングされます。各スナップショットの書き込みでは、<COW デバイス>に元のデータを保存し、その可視コンテンツを変更せずに保持します（<COW デバイス>が満杯になるまで）。

  • snapshot <origin> <COW デバイス> <永続?> <チャンクサイズ> [<# 特徴引数>] [<引数>*]

<origin> ブロックデバイスのスナップショットを作成します。変更された <チャンクサイズ> セクタのデータは <COW デバイス> に保存されます。書き込みは <COW デバイス> にのみ行われ、読み込みは <COW デバイス> または変更されていないデータの <origin> から行われます。<COW デバイス> は通常、元のデバイスより小さく、満杯になるとスナップショットは無効になりエラーを返します。そのため、空き容量を監視し、満杯になる前に <COW デバイス> を拡張することが重要です。

<永続?> は P (永続) または N (非永続 - 再起動後に失われる) です。O (オーバーフロー) を追加して永続ストレージオプションとして利用可能で、ユーザー空間が「オーバーフロー」をスナップショットステータスで認識できるようにします。サポートされるストレージタイプは「P」「PO」および「N」です。

永続と一時の違いは、一時スナップショットではディスクに保存するメタデータが少なく、カーネルがメモリに保持できる点です。

スナップショットテンプレートをロードまたはアンロードする際、対応する snapshot-origin または snapshot-merge テンプレートは一時停止する必要があります。テンプレートを一時停止しなかった場合、データの破損が発生する可能性があります。

オプション機能:

discard_zeroes_cow - スナップショットデバイスにディスカードが発行され、そのチャンク全体にマッピングされる場合、スナップショットの例外ストレージに該当する例外をゼロにします。

discard_passdown_origin - スナップショットデバイスへのdiscard操作は、スナップショットオリジンの下位デバイスに伝播されます。これはスナップショットオリジンターゲットがバイパスされるため、スナップショット例外ストレージへのコピー操作を引き起こしません。

discard_passdown_origin機能はdiscard_zeroes_cow機能が有効になっている必要があります。

  • snapshot-merge <origin> <COW device> <persistent> <chunksize> [<# feature args> [<arg>]*]

これはスナップショットターゲットと同じテーブル引数を取るが、永続スナップショットのみに適用されます。このターゲットは「snapshot-origin」ターゲットの役割を引き受けるため、<origin>で「snapshot-origin」がまだ存在する場合はロードしてはいけません。

<COW device>に格納された既存スナップショットの変更されたチャンクを手渡し手順を通じて制御し、<origin>に再統合するマージングスナップショットを作成します。マージがバックグラウンドで開始されると、<origin>を開いてI/Oが流れる間もマージが続きます。<origin>への変更は、マージングスナップショットの対応するチャンク（複数可）がマージされるまで延期されます。マージが開始されると、「snapshot」ターゲットに関連するスナップショットデバイスはアクセス時に-EIOを返します。

LVM2におけるスナップショットの使用方法¶

ボリュームの最初のLVM2スナップショットを作成する際には4つのdmデバイスが使用されます：

  1. ソースボリュームの元のマッピングテーブルを含むデバイス；

  2. COWデバイスとして使用されるデバイス；

  3. 「snapshot」デバイス、#1と#2を組み合わせたもので、可視スナップショットボリュームになります；

  4. 「original」ボリューム（元のソースボリュームが使用するデバイス番号を使用）、そのテーブルは#1の「snapshot-origin」マッピングに置き換えられます。

固定の命名スキームが使用されるため、以下のコマンドを使用すると：

lvcreate -L 1G -n base volumeGroup
lvcreate -L 100M --snapshot -n snap volumeGroup/base

上記の順序でボリュームがある状況になります：

# dmsetup table|grep volumeGroup

volumeGroup-base-real: 0 2097152 linear 8:19 384
volumeGroup-snap-cow: 0 204800 linear 8:19 2097536
volumeGroup-snap: 0 2097152 snapshot 254:11 254:12 P 16
volumeGroup-base: 0 2097152 snapshot-origin 254:11

# ls -lL /dev/mapper/volumeGroup-*
brw-------  1 root root 254, 11 29 ago 18:15 /dev/mapper/volumeGroup-base-real
brw-------  1 root root 254, 12 29 ago 18:15 /dev/mapper/volumeGroup-snap-cow
brw-------  1 root root 254, 13 29 ago 18:15 /dev/mapper/volumeGroup-snap
brw-------  1 root root 254, 10 29 ago 18:14 /dev/mapper/volumeGroup-base

LVM2におけるsnapshot-mergeの使用方法¶

マージングスナップショットはマージ中に「snapshot-origin」の役割を引き受けます。そのため「snapshot-origin」は「snapshot-merge」に置き換えられます。「-real」デバイスは変更されず、「-cow」デバイスは<origin name>-cowにリネームされ、マージングスナップショットが完了後にLVM2がクリーンアップを行うのを助けるためです。「snapshot」が「snapshot-merge」にCOWデバイスを手渡す際には、アクティブ状態が無効化されます（lvchange –refreshを使用しない場合）。アクティブ状態を維持すると、単にI/Oエラーを返します。

スナップショットは次のコマンドで自身のオリジンにマージします：

lvconvert --merge volumeGroup/snap

この状況になります：

# dmsetup table|grep volumeGroup

volumeGroup-base-real: 0 2097152 linear 8:19 384
volumeGroup-base-cow: 0 204800 linear 8:19 2097536
volumeGroup-base: 0 2097152 snapshot-merge 254:11 254:12 P 16

# ls -lL /dev/mapper/volumeGroup-*
brw-------  1 root root 254, 11 29 ago 18:15 /dev/mapper/volumeGroup-base-real
brw-------  1 root root 254, 12 29 ago 18:16 /dev/mapper/volumeGroup-base-cow
brw-------  1 root root 254, 10 29 ago 18:16 /dev/mapper/volumeGroup-base

マージが完了したかどうかを確認する方法¶

snapshot-mergeおよびsnapshotのステータス行は最後に：

<sectors_allocated>/<total_sectors> <metadata_sectors>

Both <sectors_allocated> and <total_sectors> include both data and metadata. During merging, the number of sectors allocated gets smaller and smaller. Merging has finished when the number of sectors holding data is zero, in other words <sectors_allocated> == <metadata_sectors>.

Here is a practical example (using a hybrid of lvm and dmsetup commands):

# lvs
  LV      VG          Attr   LSize Origin  Snap%  Move Log Copy%  Convert
  base    volumeGroup owi-a- 4.00g
  snap    volumeGroup swi-a- 1.00g base  18.97

# dmsetup status volumeGroup-snap
0 8388608 snapshot 397896/2097152 1560
                                  ^^^^ metadata sectors

# lvconvert --merge -b volumeGroup/snap
  Merging of volume snap started.

# lvs volumeGroup/snap
  LV      VG          Attr   LSize Origin  Snap%  Move Log Copy%  Convert
  base    volumeGroup Owi-a- 4.00g          17.23

# dmsetup status volumeGroup-base
0 8388608 snapshot-merge 281688/2097152 1104

# dmsetup status volumeGroup-base
0 8388608 snapshot-merge 180480/2097152 712

# dmsetup status volumeGroup-base
0 8388608 snapshot-merge 16/2097152 16

マージが完了しました。

# lvs
  LV      VG          Attr   LSize Origin  Snap%  Move Log Copy%  Convert
  base    volumeGroup owi-a- 4.00g

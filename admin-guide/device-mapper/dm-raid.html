dm-raid¶

デバイスマッパーRAID（dm-raid）ターゲットは、DMからMDへの橋渡しを提供します。これにより、MD RAIDドライバーをデバイスマッパーインターフェースでアクセス可能になります。

マッピングテーブルインターフェース¶

ターゲットの名前は「raid」で、以下のパラメータを受け付けます：

<raid_type> <#raid_params> <raid_params> \
  <#raid_devs> <metadata_dev0> <dev0> [.. <metadata_devN> <devN>]

<raid_type>:

raid0

RAID0 ストリピング（耐障害性なし）

raid1

RAID1 ミラーリング

raid4

RAID4 で最後のパリティディスクを専用で使用

raid5_n

RAID5 で最後のパリティディスクを専用で使用し、過渡的なレイアウトをサポート。raid4 と同様

  • 過渡的なレイアウト

raid5_la

RAID5 レフトアシメトリック

  • 回転パリティ0 でデータ継続

raid5_ra

RAID5 ライトアシメトリック

  • 回転パリティN でデータ継続

raid5_ls

RAID5 レフトシメトリック

  • 回転パリティ0 でデータ再開

raid5_rs

RAID5 ライトシメトリック

  • 回転パリティN でデータ再開

raid6_zr

RAID6 ゼロ再開

  • 回転パリティゼロ（左から右へ）でデータ再開

raid6_nr

RAID6 N 再開

  • 回転パリティN（右から左へ）でデータ再開

raid6_nc

RAID6 N 継続

  • 回転パリティN（右から左へ）でデータ継続

raid6_n_6

RAID6 でパリティディスクを専用で使用

  • 最後の2ディスクにパリティとQサインデュームを配置。raid4/raid5_nからの過渡的なレイアウト用

raid6_la_6

raid_la と同様で、最後のQサインデュームディスクを専用で使用

  • raid5_laからraid6へのオーバーテイクレイアウト

raid6_ra_6

raid5_raと同じで、最後のQ-syndromeディスク専用

  • raid5_lsからraid6へのオーバーテイクレイアウト

raid6_ls_6

raid5_lsと同じで、最後のQ-syndromeディスク専用

  • raid5_rsからraid6へのオーバーテイクレイアウト

raid6_rs_6

raid5_rsと同じで、最後のQ-syndromeディスク専用

  • raid5_rsからraid6へのオーバーテイクレイアウト

raid10

raid10をインスピレーションとしたさまざまなアルゴリズムで、追加パラメータで選択可能（raid10_formatおよびraid10_copiesの下記を参照）

  • RAID10: ストライプされたミラー（ミラー上のストライピングとも呼ばれる）

  • RAID1E: 集積隣接ストライプミラーリング

  • RAID1E: 集積オフセットストライプミラーリング

  • その他の類似RAID10の変種

参照: 以下の章4 https://www.snia.org/sites/default/files/SNIA_DDF_Technical_Position_v2.0.pdf

<#raid_params>: その後に続くパラメータの数。

<raid_params>は以下の要素から構成される

必須パラメータ：
<chunk_size>:

セクタ単位のチャンクサイズ。このパラメータはしばしば「ストライプサイズ」として知られている。これは必須パラメータであり、最初に指定される。

オプションパラメータ（順序は任意）が続く:
[sync|nosync]

RAIDの初期化を強制するか防止する。

[rebuild <idx>]

ドライブ番号「idx」（最初のドライブは0）を再構築する。

[daemon_sleep <ms>]

ビットマップデーモンがビットをクリアする間隔。間隔が長くなるほどビットマップI/Oは少なくなるが、障害後の再同期が遅くなる可能性がある。

[min_recovery_rate <kB/sec/disk>]

RAID初期化を制限する

[max_recovery_rate <kB/sec/disk>]

RAID初期化を制限する

[write_mostly <idx>]

ドライブインデックス「idx」をライトオンリーディスクにマークする。

[max_write_behind <sectors>]

「–write-behind=」(man mdadm)を参照

[stripe_cache <sectors>]

ストライプキャッシュサイズ（RAID 4/5/6専用）

[region_size <sectors>]

region_sizeにセクタ数を掛けると論理配列のサイズとなる。ビットマップは各regionのデバイス同期状態を記録する。

[raid10_copies <# copies>], [raid10_format <near|far|offset>]

[delta_disks <N>]

delta_disksオプション値（-251 < N < +251）は、再構成をサポートするRAIDレベル4/5/6および10に対して、デバイスの削除（負の値）または追加（正の値）をトリガーします。RAIDレベル4/5/6はデバイスの追加（メタデータおよびデータデバイスのペア）を許可しますが、raid10_nearおよびraid10_offsetはデバイスの追加のみを許可します。raid10_farは再構成を完全にサポートしていません。耐障害性を確保するためには、RAID4/5には少なくとも3台、RAID6には少なくとも4台のデバイスを維持する必要があります。

[data_offset <sectors>]

このオプション値は、データデバイス内のデータ開始位置を指定します。これにより、ストライプレイアウトの変更中にデータ上書きを防ぐための場所外の再構成スペースを提供します。これにより、いつでも中断やクラッシュが発生してもデータの喪失リスクがありません。例えば、既存のRAIDセットにデバイスを追加する際の前向き再構成では、各RAIDデバイスの開始位置に場所外スペースが割り当てられます。カーネルのRAID4/5/6/10 MDパーソナリティがこのようなデバイス追加をサポートする場合、既存の最初のストライプ（ストライプ数が少ないもの）からdata_offsetを起点にデータを読み込み、新しいストライプ（ストライプ数が多いもの）にデータを書き込み、冗長性ブロック（CRC/Q-syndrome）を計算してoffset 0に書き込みます。これによりRAIDタイプ（つまり割当アルゴリズム）の変更も可能です。例えば、raid5_lsからraid5_nへの変更です。

[journal_dev <dev>]

このオプションは、raid4/5/6のraidセットにジャーナルデバイスを追加し、コンポーネントデバイスの非原子的な更新によって引き起こされる「write hole（書き込み穴）」を閉じるために使用します。これにより、復元中にデータロスが発生する可能性を防ぎます。ジャーナルデバイスはwritethroughモードで使用されるため、書き込みが非ジャーナルのraid4/5/6セットよりも制限されます。raid4/5/6のジャーナルデバイスではトーカー/リシェイプは実行できません。これらの操作を実行する前に、ジャーナルデバイスをデコンフィギュアする必要があります。

[journal_mode <mode>]

このオプションは、ジャーナル化されたraid4/5/6 raidセットのキャッシュモードを「writethrough」または「writeback」に設定します（上記の「journal_dev <dev>」を参照）。'writeback'を選択した場合、ジャーナルデバイスは自己の「write hole」問題を抱えていないことが必要です（例: raid1またはraid10を使用）。これにより、単一の障害点を防ぎます。

<#raid_devs>: アレイを構成するデバイスの数。

各デバイスは2つのエントリで構成されます。最初のエントリはメタデータを含むデバイス（必要に応じて）、2番目のエントリはデータを含むデバイスです。ターゲットバージョン1.8.0までで最大64のメタデータ/データデバイスエントリをサポートします。1.9.0では最大253までサポートされ、これは使用するMDカーネルランタイムによって強制されます。

ドライブが失敗しているか、作成時から欠損している場合、該当する位置のメタデータとデータドライブには「-」を指定できます。

例の表¶

# RAID4 - 4 data drives, 1 parity (no metadata devices)
# No metadata devices specified to hold superblock/bitmap info
# Chunk size of 1MiB
# (Lines separated for easy reading)

0 1960893648 raid \
        raid4 1 2048 \
        5 - 8:17 - 8:33 - 8:49 - 8:65 - 8:81

# RAID4 - 4 data drives, 1 parity (with metadata devices)
# Chunk size of 1MiB, force RAID initialization,
#       min recovery rate at 20 kiB/sec/disk

0 1960893648 raid \
        raid4 4 2048 sync min_recovery_rate 20 \
        5 8:17 8:18 8:33 8:34 8:49 8:50 8:65 8:66 8:81 8:82

ステータス出力¶

‘dmsetup table’はマッピングを構築するために使用されるテーブルを表示します。オプションパラメータは常に上記の順序で出力され、「sync」または「nosync」は他の引数の前に常に表示されます。繰り返し可能な引数は値の順序で並べられます。

‘dmsetup status’はアレイの状態と健康状態に関する情報を提供します。出力は以下の通りです（通常は1行ですが、明確にするために展開しています）:

1: <s> <l> raid \
2:      <raid_type> <#devices> <health_chars> \
3:      <sync_ratio> <sync_action> <mismatch_cnt>

1行目はdevice-mapperによって生成される標準出力です。

2行目と3行目はraidターゲットによって生成され、例を挙げて説明するのが最も適切です:

0 1960893648 raid raid4 5 AAAAA 2/490221568 init 0

ここではRAIDタイプがraid4で、5つのデバイスがありすべてが「A」（アクティブ）、アレイが初期の復元で2/490221568の完了度を示しています。個々のフィールドの詳細な説明:

<raid_type>

アレイを生成する際に使用した<raid_type>と同じです。

<health_chars>

各デバイスごとに1文字で示します:

  • ‘A’ = アクティブで同期中

  • ‘a’ = アクティブだが同期していない

  • ‘D’ = デッド/失敗

<sync_ratio>

sync_actionで説明されるプロセスがアレイのどの部分に適用されたかを示す比率です。sync_actionが「check」または「repair」の場合、resyncまたはrecoverプロセスが完了しているとみなされます。

<sync_action>

以下の可能な状態のうちの1つ:

アイドル

  • 同期操作が実行されていません。

frozen

  • 現在の操作が中断されています。

resync

  • 配列が初期同期中または不完全なシャットダウン後に再同期中（ビットマップによって補助される可能性あり）です。

recover

  • 配列内のデバイスが再構築または交換中です。

check

  • ユーザーが実行した配列全体のチェックが進行中です。すべてのブロックが読み込まれて整合性が確認され、<mismatch_cnt>に検出された不一致の数が記録されます。この操作により配列には変更が加えられません。

repair

  • 「check」と同じですが、不一致は修正されます。

reshape

  • 配列が再形成（reshape）中です。

<mismatch_cnt>

RAID1/10のミラー複製間の不一致またはRAID4/5/6の誤ったパリティ値の数です。この値は「check」操作後にのみ有効です。健全な配列では<mismatch_cnt>は0です。

<data_offset>

RAIDセットの各コンポーネントデバイスのユーザーデータの開始位置からの現在のデータオフセット（オフプレース再形成をサポートするためのそれぞれのRAIDパラメータを参照してください）。

<journal_char>

  • ‘A’ - アクティブなライトスルージャーナルデバイス。

  • ‘a’ - アクティブなライトバックジャーナルデバイス。

  • ‘D’ - デッドジャーナルデバイス。

  • ‘-’ - ジャーナルデバイスなし。

メッセージインターフェース¶

dm-raidターゲットは「メッセージ」インターフェースを通じて特定の操作を受け付けます。（man dmsetup でメッセージインターフェースに関する詳細情報を確認してください。）これらの操作には以下のものがあります:

“idle”

現在の同期操作を停止します。

“frozen”

現在の同期操作を凍結します。

“resync”

再同期を開始または継続します。

“recover”

修復プロセスを開始または継続します。

“check”

配列のチェック（すなわち「スクラビング」）を開始します。

“repair”

配列の修復を開始します。

破棄サポート¶

ハードウェアベンダー間でのdiscardサポートの実装は異なります。ブロックがdiscardされた場合、一部のストレージデバイスはそのブロックを読み込む際にゼロを返します。このようなデバイスは「discard_zeroes_data」属性を設定します。他のデバイスはランダムなデータを返します。混乱を招くのは、一部のデバイスが「discard_zeroes_data」を宣伝しているにもかかわらず、discardされたブロックを読み込む際にゼロを reliably 返さないことです。RAID 4/5/6はパリティブロックを複数のデバイスのブロックから計算し、パフォーマンスのため「discard_zeroes_data」が信頼できることが前提となっています。したがって、デバイスが一貫していることが重要です。RAID 4/5/6のストライプ中にブロックがdiscardされ、その後の読み込み結果が一貫しない場合、パリティブロックがいつでも異なる計算結果になる可能性があり、冗長性を失います。RAID 4/5/6でdiscardを有効にする場合、ハードウェアがdiscardをどのように処理するかを理解することが重要です。

ストレージデバイスのこの点での動作は信頼性が低いため、even when reporting ‘discard_zeroes_data’を報告している場合でも、デフォルトではRAID 4/5/6のdiscardサポートは無効にされています。これによりデータの整合性が保証されますが、パフォーマンスが若干低下します。

「discard_zeroes_data」を正しくサポートするストレージデバイスは、カーネル内で徐々にホワイトリストに追加されており、信頼できるとされています。

信頼できるデバイスの場合、以下のdm-raidモジュールパラメータを設定してRAID 4/5/6のdiscardサポートを安全に有効化できます。

‘devices_handle_discards_safely’

キャッシュ¶

はじめに¶

dm-cache は、Joe Thornber、Heinz Mauelshagen、Mike Snitzer によって書かれたデバイス・マッピングのターゲットです。

このターゲットは、ブロックデバイス（例：スパインド）のパフォーマンスを向上させるために、その一部のデータをより高速でより小さなデバイス（例：SSD）に動的に移すことを目的としています。

このデバイス・マッピングのソリューションにより、dm スタックのさまざまなレベルにキャッシュを挿入することが可能になります。例えば、スリムプロビジョニングプールのデータデバイスの上に配置することもできます。仮想メモリシステムとより密接に統合されたキャッシュソリューションは、パフォーマンスがより向上します。

このターゲットは、スリムプロビジョニングライブラリで使用されているメタデータライブラリを再利用しています。

どのデータをいつ移すかは、プラグインポリシーモジュールに委ねられています。我々は実験を通じていくつかのポリシーを実装しており、特定のI/Oシナリオ（例：仮想マシンイメージサーバー）用に他のポリシーを提供してくれる他者も期待しています。

用語集¶

移動

論理ブロックの主なコピーを一つのデバイスから別のデバイスへ移す行為。

促進

遅いデバイスから高速デバイスへの移動。

降格

高速デバイスから遅いデバイスへの移動。

元のデバイスは常に論理ブロックのコピーを保持しており、これは古いデータである可能性がありますが、ポリシーに応じてキャッシュデバイス上のコピーと同期されている場合もあります。

設計¶

サブデバイス¶

このターゲットは、後に詳しく説明する他のパラメータとともに3つのデバイスを渡して構築されます：

  1. 元のデバイス - 大きく遅いデバイス。

  2. キャッシュデバイス - 小さく速いデバイス。

  3. 小さなメタデータデバイス - キャッシュに含まれるブロック、汚染されたブロック、およびポリシーオブジェクトに使用する追加ヒントを記録します。この情報はキャッシュデバイスに置くこともできますが、分離することでボリュームマネージャーが異なる方法で構成できるようになります（例：追加の堅牢性のためにミラーリング）。このメタデータデバイスは単一のキャッシュデバイスのみに使用できます。

固定ブロックサイズ¶

元のデバイスは固定サイズのブロックに分割されます。このブロックサイズはキャッシュを作成する際の設定で指定できます。通常は256KB - 1024KBのブロックサイズを使用しています。ブロックサイズは64セクタ（32KB）から2097152セクタ（1GB）までで、64セクタ（32KB）の倍数である必要があります。

固定ブロックサイズはターゲットを大幅に簡略化しますが、ある程度の妥協点です。例えば、ブロックの一部が頻繁にアクセスされるにもかかわらず、全体がキャッシュに促進されることがあります。そのため、大きなブロックサイズはキャッシュスペースを浪費します。一方、小さなブロックサイズはメタデータ（コアとディスクの両方）の量を増やすため悪影響です。

キャッシュ運用モード¶

キャッシュは3つの運用モードを持っています: writeback、writethrough、および passthrough。

writebackが選択された場合、キャッシュされているブロックへの書き込みはキャッシュのみに送られ、メタデータでブロックがdirtyとマークされます。

writethroughが選択された場合、キャッシュされているブロックへの書き込みは、元のデバイスとキャッシュデバイスの両方に到達するまで完了しません。クリーンなブロックはクリーンのまま維持されるべきです。

passthroughが選択された場合、キャッシュの内容が元のデバイスと整合性があるとは限らない状況で役立ちます。この場合、すべての読み込みは元のデバイスから行われ（キャッシュはヒットしません）、すべての書き込みは元のデバイスに転送されます。さらに、書き込みヒットはキャッシュブロックの無効化を引き起こします。passthroughモードを有効にするには、キャッシュがクリーンである必要があります。passthroughモードは、整合性の心配をせずにキャッシュデバイスをアクティブ化できるようにします。既存の整合性は維持されますが、書き込みによりキャッシュは徐々に冷えていきます。後述の「invalidate_cblocks」メッセージを用いてキャッシュの整合性を確認または確立できる場合、キャッシュデバイスはまだ温かい状態でwritethroughまたはwritebackモードに移行できます。そうでない場合は、移行前のキャッシュ内容は破棄する必要があります。

キャッシュのデコミッションやサイズ変更時に役立つシンプルなクリーンポリシーが提供されています。すべてのdirtyブロックをクリーン（書き戻し）します。キャッシュのサイズを縮小時、削除する領域にあるすべてのキャッシュブロックがクリーンである必要があります。削除領域にdirtyブロックが残っていると、サイズ変更は失敗します。キャッシュのfastデバイスに使用されるボリュームを縮小する際は、キャッシュがクリーンであることを確認する必要があります。これは特にwritebackモードを使用する場合に重要です。writethroughおよびpassthroughモードはすでにクリーンなキャッシュを維持しています。今後、指定されたしきい値以上の部分的なクリーン処理がサポートされることで、サイズ変更中にキャッシュを温かく保ちながらwritebackモードで運用できるようになります。

マイグレーションスロットリング¶

元のデバイスとキャッシュデバイス間でのデータマイグレーションには帯域幅が必要です。ユーザーはスロットリングを設定して、特定の時間に発生するマイグレーション量を制限できます。現在は通常のI/Oトラフィックを考慮していません。ピーク時のI/O期間にマイグレーションを避けるためには、この点の改善が求められています。

一時的に、「migration_threshold <#セクタ>」というメッセージを使用して、マイグレーションされる最大セクタ数を設定できます（デフォルトは2048セクタ（1MB）です）

ディスク上のメタデータの更新中¶

FLUSHまたはFUA bioが書き込まれるたびにディスク上のメタデータがコミットされます。このようなリクエストがなければ、1秒ごとにコミットされます。これにより、キャッシュは揮発性の書き込みキャッシュを持つ物理ディスクのように動作します。電源が切れた場合、最近の書き込みが失われる可能性があります。ただし、どんなクラッシュでもメタデータは常に一貫性を保たなければなりません。

キャッシュブロックの「dirty」状態は頻繁に変化するため、飛ばしで更新することはできません。そのため、ヒントとして扱います。通常の動作では、dmデバイスが停止されるときに書き込まれます。システムがクラッシュした場合、再起動時にすべてのキャッシュブロックがdirtyとみなされます。

ブロックごとのポリシーのヒント¶

ポリシープラグインはキャッシュブロックごとにデータを保存できます。ポリシーによってこのチャンクのサイズは決まりますが、小さく保つ必要があります。dirtyフラグと同様に、クラッシュ時にこのデータは失われますので、安全なフォールバック値が常に可能であるべきです。

ポリシーのヒントはパフォーマンスに影響を与えるが、正しさには影響しません。

ポリシーのメッセージング¶

ポリシーにはそれぞれに特有のチューニングパラメータがあり、これらを取得・設定する汎用的な方法が必要です。デバイスマッパーのメッセージを使用します。cache-policies.txtを参照してください。

Discardビットセットの解像度¶

データのコピーを避けるため、ブロックがdiscardされているかを知ることが重要です。mkfsがブロックデバイス全体をdiscardする例がこれに該当します。ブロックのdiscard状態を追跡するビットセットを保存します。ただし、このビットセットのブロックサイズはキャッシュブロックとは異なる場合があります。これは、元のデバイス全体のdiscard状態を追跡する必要があるためです（dirtyビットセットはキャッシュデバイスの小さな領域のみを対象としています）。

オプション機能引数は以下の通りです:

writethrough

キャッシュブロックの内容がオリジンブロックの内容と異なることを禁止するライトスルーキャッシング。この引数がない場合、パフォーマンスのためキャッシュブロックの内容を後で書き戻すデフォルトの動作が行われ、これにより対応するオリジンブロックと異なる可能性があります。

passthrough

さまざまなキャッシュコヒーレンシー状況（例：下位ストレージのスナップショットのロールバックなど）に有用なデグレードモード。読み込みと書き込みは常にオリジンに行います。書き込みがキャッシュされたオリジンブロックに行うと、キャッシュブロックは無効化されます。パステラーモードを有効にするにはキャッシュがクリーンである必要があります。

metadata2

メタデータバージョン2を使用します。これはディリィビットを別のbtreeに格納し、キャッシュのシャットダウン速度を向上させます。

no_discard_passdown

キャッシュからオリジンのデータデバイスへのディスカードの伝達を無効にします。

「デフォルト」と呼ばれるポリシーは常に登録されます。これは現在考えられる全体的なパフォーマンスを提供するポリシーの別名です。

デフォルトポリシーはカーネルによって異なり得るため、特定のポリシーの特性に依存している場合は常に名前で要求してください。

メッセージ¶

ポリシーにはそれぞれ異なる調整パラメータがあり、これらを取得・設定するための汎用的な方法が必要です。デバイスマッパーのメッセージが使用されます。（sysfsインターフェースも可能です。）

メッセージの形式は:

<key> <value>

E.g.:

dmsetup message my_cache 0 sequential_threshold 1024

無効化はキャッシュからエントリを削除することを指し、バックアップせずに実行されます。キャッシュブロックはinvalidate_cblocksメッセージを通じて無効化でき、このメッセージは任意の数のcblock範囲を受け取ります。各cblock範囲の終端値は「終端を越えた」値であり、5-10は5から9までの範囲を表します。今後、より大規模なキャッシュの効率的な無効化をサポートするため、16進数で表現されたcblock範囲を受取る変種メッセージが必要になる可能性があります。invalidate_cblocksを使用する際には、キャッシュがpassthroughモードでなければなりません。

invalidate_cblocks [<cblock>|<cblock begin>-<cblock end>]*

E.g.:

dmsetup message my_cache 0 invalidate_cblocks 2345 3456-4567 5678-6789

例¶

テストスイートは以下にあります:

https://github.com/jthornber/device-mapper-test-suite

dmsetup create my_cache --table '0 41943040 cache /dev/mapper/metadata \
        /dev/mapper/ssd /dev/mapper/origin 512 1 writeback default 0'

        /dev/mapper/ssd /dev/mapper/origin 1024 1 writeback \
        mq 4 sequential_threshold 1024 random_threshold 8'

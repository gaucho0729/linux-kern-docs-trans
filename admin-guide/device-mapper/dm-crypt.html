dm-crypt¶

Device-Mapperの「crypt」ターゲットは、カーネルの暗号APIを使用してブロックデバイスの透明な暗号化を提供します。

サポートされているパラメータの詳細な説明については以下を参照してください: https://gitlab.com/cryptsetup/cryptsetup/wikis/DMCrypt

パラメータ:

<cipher> <key> <iv_offset> <device path> \
<offset> [<#opt_params> <opt_params>]
<cipher>

暗号化暗号、暗号化モードおよび初期ベクトル（IV）ジェネレータ。

暗号化暗号の仕様書形式は:

cipher[:keycount]-chainmode-ivmode[:ivopts]

例:

aes-cbc-essiv:sha256
aes-xts-plain64
serpent-xts-plain64

暗号化暗号の仕様書形式は、カーネル暗号API形式（capi:プレフィックスで選択）でも直接指定可能です。IVの仕様は最初の形式タイプと同じです。この形式は認証モードの指定に主に使用されます。

カーネル暗号API暗号化暗号の仕様書形式は:

capi:cipher_api_spec-ivmode[:ivopts]

例:

capi:cbc(aes)-essiv:sha256
capi:xts(aes)-plain64

認証モードの例:

capi:gcm(aes)-random
capi:authenc(hmac(sha256),xts(aes))-random
capi:rfc7539(chacha20,poly1305)-random

/proc/cryptoには現在ロードされている暗号モードの一覧が含まれています。

<key>

暗号化に使用される鍵。16進数としてエンコードするか、カーネルキーリングサービスに存在する鍵についてはコロン（:）で始まる<key_string>として渡すことができます。選択された暗号と選択されたIVモードで有効な鍵サイズのみを使用可能です。一部のIVモードでは、鍵文字列に追加の鍵（例：IVシード）が含まれるため、鍵は複数の部分が1つの文字列に連結されています。

<key_string>

カーネルキーリングの鍵は、次の形式の文字列で識別されます：<key_size>:<key_type>:<key_description>。

<key_size>

暗号化鍵のバイト数。カーネルキーペイロードサイズは<key_size>で指定された値と一致する必要があります。

<key_type>

「logon」、「user」、「encrypted」のいずれかのカーネルキーティプです。

<key_description>

カーネルキーリングの鍵の説明として、<key_type>の鍵をロードする際にcryptターゲットが検索する文字列です。

<keycount>

マルチキーパッケージモード。<keycount>個の鍵を定義し、セクタがオフセットに応じて暗号化されます（セクタ0はkey0、セクタ1はkey1など）。<keycount>は2の累乗でなければなりません。

<iv_offset>

IVオフセットは、セクタ番号にセクタ数を加算してIVを生成する際のオフセットです。

<device path>

このデバイスはバックエンドとして使用され、暗号化されたデータを含みます。/dev/xxxのようなパスや<major>:<minor>のデバイス番号として指定できます。

<offset>

暗号化データが開始するデバイス内の開始セクタ。

<#opt_params>

オプションパラメータの数。オプションパラメータがない場合は、オプションパラメータセクションを省略するか#opt_paramsをゼロにできます。それ以外の場合、#opt_paramsは次の引数の数です。

オプションパラメータセクションの例:

3 allow_discards same_cpu_crypt submit_from_crypt_cpus

allow_discards

ブロックディスカードリクエスト（a.k.a. TRIM）は暗号化デバイスを通じて処理されます。デフォルトではディスカードリクエストを無視します。

警告: このオプションを有効にする前に、特定のセキュリティリスクを慎重に評価してください。例えば、暗号化デバイスでディスカードを許可すると、後でデバイス上でディスカードされたブロックが簡単に特定される場合、暗号化されたデバイス（ファイルシステムタイプ、使用領域など）に関する情報漏洩のリスクがあります。

same_cpu_crypt

IOが送信された同じCPUを使用して暗号化を行います。デフォルトでは非バインドのワーキューを使用し、暗号化作業を利用可能なCPU間で自動的にバランスを取るよう設定されています。

submit_from_crypt_cpus

暗号化スレッドから書き込みBIOSを別スレッドにオフローディングを無効にします。一部の状況では、暗号化スレッドから書き込みBIOSを単一スレッドにオフローディングするとパフォーマンスが大幅に低下することがあります。デフォルトでは同じスレッドに書き込みBIOSをオフローディングし、CFQが同じコンテキストで書き込みを送信できるようにするためです。

no_read_workqueue

dm-cryptの内部ワーキューをバイパスし、読み取りリクエストを同期的に処理します。

no_write_workqueue

dm-cryptの内部ワーキューをバイパスし、書き込みリクエストを同期的に処理します。このオプションはホスト管理型ゾーンブロックデバイス（例: ホスト管理型SMRハードディスク）では自動的に有効になります。

integrity:<bytes>:<type>

デバイスはセクタごとに<bytes>メタデータをper-bioインテグラティ構造に保存する必要があります。このメタデータは下位のdm-integrityターゲットによって提供される必要があります。

<type>はメタデータが永続的なIVのみに使用される場合、「none」に設定できます。

認証付き暗号化（AEAD）の場合、<type>は「aead」に設定されます。AEADモードでは暗号化されたデバイスの整合性を計算および検証します。追加の領域は認証タグ（必要に応じて永続的なIV）を保存するために使用されます。

sector_size:<bytes>

<bytes>を暗号化単位として使用します。このオプションは512バイト〜4096バイトの範囲で、2の累乗である必要があります。仮想デバイスはこのサイズを最小IOおよび論理セクタとして宣言します。

iv_large_sectors

IVジェネレータは<sector_size>単位のセクタ番号を使用します。デフォルトでは512バイトセクタを使用します。

例えば、<sector_size>が4096バイトの場合、plain64 IVの2番目のセクタはフラグなしで8（フラグありで1）になります。<iv_offset>はこのフラグが指定されている場合、<sector_size>（512バイト単位）の倍数でなければなりません。

例のスクリプト¶

LUKS（Linux Unified Key Setup）は、cryptsetupユーティリティを使用してdm-cryptによるディスク暗号化を設定するための現在の推奨方法です。詳しくは https://gitlab.com/cryptsetup/cryptsetup

#!/bin/sh
# Create a crypt device using dmsetup
dmsetup create crypt1 --table "0 `blockdev --getsz $1` crypt aes-cbc-essiv:sha256 babebabebabebabebabebabebabebabe 0 $1 0"

#!/bin/sh
# Create a crypt device using dmsetup when encryption key is stored in keyring service
dmsetup create crypt2 --table "0 `blockdev --getsize $1` crypt aes-cbc-essiv:sha256 :32:logon:my_prefix:my_key 0 $1 0"

#!/bin/sh
# Create a crypt device using cryptsetup and LUKS header with default cipher
cryptsetup luksFormat $1
cryptsetup luksOpen $1 crypt1

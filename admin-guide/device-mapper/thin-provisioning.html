スリムプロビジョニング (薄プロビジョニング)¶

はじめに¶

このドキュメントでは、スリムプロビジョニングとスナップショットを実装するためのデバイス・マッパーのターゲットの一覧について説明しています。

以前のスナップショット実装と比較して、この実装の主な特徴は、複数の仮想デバイスを同じデータボリュームに格納できる点です。これにより管理が簡素化され、ボリューム間でのデータ共有が可能となり、ディスク使用量を削減できます。

もう一つの重要な機能は、再帰的なスナップショット（スナップショットのスナップショット…など）の任意の深さへのサポートです。以前のスナップショット実装では、検索テーブルをチェインで接続することでこの機能を実現していましたが、パフォーマンスは深さに比例してO(depth)となりました。この新しい実装では単一のデータ構造を使用して、深さによるパフォーマンス低下を回避しています。ただし、一部のシナリオではフラグメンテーションが問題となる可能性があります。

メタデータはデータとは別のデバイスに保存され、管理者にはいくつかの柔軟性が与えられます。例えば以下のような用途で:

  • メタデータの耐障害性を向上させるため、メタデータをミラーリングされたボリュームに保存し、データをミラーリングされていないボリュームに保存する。

  • パフォーマンスを向上させるため、メタデータをSSDに保存する。

Status¶

これらのターゲットは本番環境での使用が安全とされています。ただし、異なる使用ケースではデータボリュームのフラグメンテーションなどによりパフォーマンス特性が異なります。

このソフトウェアが予期しないパフォーマンスを示している場合は、 dm-devel@redhat.com に詳細を添えてメールを送信してください。私たちはできるだけ問題を改善いたします。

メタデータの確認と修復に使用するユーティリティツールは完全に開発され、'thin_check' および 'thin_repair' として利用可能です。パッケージ名はディストリビューションによって異なります（Red Hatディストリビューションでは 'device-mapper-persistent-data' と呼ばれます）。

クックブック¶

このセクションでは、スリムプロビジョニングの簡単な使用例をいくつか紹介します。これらは dmsetup プログラムを使用してデバイス・マッパードライバーを直接制御する方法です。最終ユーザーは、サポートが追加された後は LVM2 などの上位レベルのボリュームマネージャーを使用することを推奨します。

プールデバイス¶

プールデバイスはメタデータボリュームとデータボリュームを統合します。I/Oはデータボリュームに線形にマッピングされ、メタデータは以下の2つのメカニズムを通じて更新されます:

  • スリムターゲットからの関数呼び出し

  • ユーザー空間からのデバイス・マッパーの「メッセージ」で、新しい仮想デバイスの作成など制御を行います。

新規のプールデバイスの設定¶

プールデバイスの設定には有効なメタデータデバイスとデータデバイスが必要です。既存のメタデータデバイスがない場合、最初の4KBをゼロにすることで空のメタデータを示すメタデータデバイスを作成できます。

dd if=/dev/zero of=$metadata_dev bs=4096 count=1

必要なメタデータの量は、スリムデバイス間で共有されるブロック数（つまりスナップショットを通じて）によって異なります。平均以下の共有が少ない場合は、メタデータデバイスのサイズを平均より大きくする必要があります。

参考として、メタデータデバイスに使用するバイト数を計算する際には、$data_dev_size / $data_block_size * 48 の値を算出し、その結果が2MB未満の場合は2MBに切り上げることを推奨します。多数のスナップショットを生成し、大量の変更を記録している場合は、この値を増やす必要があるかもしれません。

サポートされる最大サイズは16GBです。デバイスがこれより大きい場合、警告が表示されますが、余分な領域は使用されません。

プールテーブルの再読み込み¶

プールのテーブルを再読み込みできます。実際には、プールが容量不足で拡張される際にもこの方法が用いられます。(注: 現在、再読み込み時に異なるメタデータデバイスを指定することは禁止されていませんが、以前のディスク上の場所に正確にI/Oをルーティングしない場合、問題が発生します。)

既存のプールデバイスを使用する¶

dmsetup create pool \
    --table "0 20971520 thin-pool $metadata_dev $data_dev \
             $data_block_size $low_water_mark"

$data_block_size は、512バイトセクタ単位で割り当てられるディスク領域の最小単位を表し、128（64KB）から2097152（1GB）までの間で、128（64KB）の倍数である必要があります。スリムプールが作成された後は $data_block_size を変更することはできません。スリムプロビジョニングに特に興味がある場合は、1024（512KB）などの値を使用することを推奨します。多数のスナップショットを生成する場合は、128（64KB）などの小さな値を使用することを推奨します。新規に割り当てたデータをゼロに初期化しない場合、256000（128MB）程度の $data_block_size を使用することを推奨します。

$low_water_mark は $data_block_size ブロック単位で表されます。データデバイスの空き領域がこのレベルを下回ると、dmイベントがトリガーされ、ユーザー空間のデーモンがこれをキャッチしてプールデバイスを拡張する必要があります。このようなイベントは1回だけ送信されます。

再開されたデバイスの空き領域が low water mark を下回っても、特別なイベントはトリガーされません。ただし、デバイスの再開は常にイベントをトリガーします。ユーザー空間のデーモンはこのイベントを処理する際、空き領域が low water mark を上回っていることを確認する必要があります。

メタデータデバイスの low water mark はカーネル内で維持され、メタデータデバイスの空き領域がこの値を下回ると dmイベントがトリガーされます。

ディスク上のメタデータの更新中¶

ディスク上のメタデータは、FLUSHまたはFUA bioが書かれるたびにコミットされます。このようなリクエストがなければ、1秒ごとにコミットされます。これにより、スリムプロビジョニングターゲットは、揮発性のライトキャッシュを持つ物理ディスクのように動作します。電源が切れた場合、最近の書き込みデータが失われる可能性があります。メタデータは、どんなクラッシュでも常に一貫性を保つ必要があります。

データ領域が満杯になると、プールは設定に応じてエラーを返すかIOをキューに並べます（参照: error_if_no_space）。メタデータ領域が満杯になったり、メタデータ操作が失敗した場合、プールはIOエラーを返します。プールをオフラインにして修復を行うまで、IOエラーが続きます。修復により1) 一貫性の問題を修正し、2) 修復を強制するフラグをクリアします。プールのメタデータデバイスが修復されると、サイズ変更が可能となり、プールは通常動作に戻ります。注意点として、プールが修復が必要なフラグが立っている場合、データおよびメタデータデバイスのサイズ変更は修復完了までできません。また、プールのメタデータ領域が満杯になると、現在のメタデータトランザクションは中止されます。プールが上位IOレイヤー（例: ファイルシステム）に完了を通知したIOをキャッシュしているため、プールの修復が必要な場合、一貫性チェック（例: fsck）を実施することをお勧めします。

スリムプロビジョニング (薄プロビジョニング)¶

  1. 新しいスリムプロビジョニングボリュームの作成。

新しいスリムプロビジョニングボリュームを作成するには、アクティブなプールデバイスにメッセージを送信する必要があります。この例では/dev/mapper/poolです：

dmsetup message /dev/mapper/pool 0 "create_thin 0"

ここで「0」はボリュームの識別子で、24ビットの数値です。「caller」が識別子を割り当てて管理する必要があります。識別子がすでに使用されている場合、メッセージは-EEXISTで失敗します。

  1. スリムプロビジョニングボリュームの使用。

スリムプロビジョネットボリュームは「thin」ターゲットを使用してアクティベートされます：

dmsetup create thin --table "0 2097152 thin /dev/mapper/pool 0"

最後のパラメータはスリムプデバイスの識別子です。

内部スナップショット¶

  1. 内部スナップショットの作成。

スナップショットはプールに別のメッセージを送ることで作成されます。

注意: スナップショットする元のデバイスがアクティブな場合、スナップショット作成前にそのデバイスを一時停止する必要があります。これは現在は強制されていないため、ご注意ください！

dmsetup suspend /dev/mapper/thin
dmsetup message /dev/mapper/pool 0 "create_snap 1 0"
dmsetup resume /dev/mapper/thin

ここで「1」はボリュームの識別子で、24ビットの数値です。「0」は元のデバイスの識別子です。

  1. 内部スナップショットの使用。

作成後、ユーザーは元のデバイスとスナップショットの間の接続を気にする必要はありません。実際、スナップショットは他のスリムプロビジョニングされたデバイスと変わりません。同じ方法でスナップショットを取得することも可能です。どちらか一方のみをアクティブにしても完全に合法です。また、どちらもアクティブ化または削除する際の順序は特に必要ありません。(これは従来のデバイスマッパーのスナップショットとは異なります。)

他のスリムプロビジョニングされたボリュームと同様に、同じ方法でアクティブ化してください：

dmsetup create snap --table "0 2097152 thin /dev/mapper/pool 1"

外部スナップショット¶

外部 読み取り専用 デバイスをスリムプロビジョニングされたボリュームのソースとして使用できます。スリムデバイスの未プロビジョニング領域への読み取りは、ソースデバイスに転送され、書き込みは通常通り新しいブロックの割当が行われます。

このような用途の一つは、仮想マシンホストがスリムプロビジョニングされたボリューム上でゲストを実行したいが、ベースイメージを他のデバイス（複数の仮想マシン間で共有される可能性がある）に配置したい場合です。

この技術を使用する際は、ソースデバイスに書き込みを行ってはいけません！もちろん、スリムデバイスに書き込みを行い、スリムボリュームの内部スナップショットを取得することも可能です。

  1. 外部デバイスのスナップショットの作成

これはスリムデバイスの作成と同様です。この段階ではソースデバイスを指定する必要はありません。

dmsetup message /dev/mapper/pool 0 "create_thin 0"

  1. 外部デバイスのスナップショットの使用。

スリムターゲットに追加のパラメータを指定して、ソースデバイスを指定してください：

dmsetup create snap --table "0 2097152 thin /dev/mapper/pool 0 /dev/image"

N.B. このスナップショットのすべての子スナップショット（内部スナップショット）にも同じ追加のソースパラメータが必要です。

非アクティブ化¶

プールを使用しているすべてのデバイスが非アクティブ化されるまで、プールそのものも非アクティブ化できません。

dmsetup remove thin
dmsetup remove snap
dmsetup remove pool

参照¶

‘thin-pool’ターゲット¶

  1. コンストラクタ

    thin-pool <metadata dev> <data dev> <data block size (sectors)> \
          <low water mark (blocks)> [<number of feature args> [<arg>]*]

    オプションの機能引数：

    skip_block_zeroing:

    新規プロビジョニングブロックのゼロイニングをスキップ。

    ignore_discard:

    discardサポートを無効化。

    no_discard_passdown:

    discardを下位データデバイスに伝播しないが、マッピングのみを削除する。

    read_only:

    プールメタデータへの変更を許可しない。このモードは、thin-poolが作成され、最初にフル読み取り/書き込みモードで使用された後からのみ利用可能です。初期のthin-pool作成時に指定することはできません。

    error_if_no_space:

    空き容量がない場合、エラーIOを発生させる。

    データブロックサイズは64KB（128セクタ）から1GB（2097152セクタ）までの間でなければなりません。

  2. Status

    <transaction id> <used metadata blocks>/<total metadata blocks>
<used data blocks>/<total data blocks> <held metadata root>
ro|rw|out_of_data_space [no_]discard_passdown [error|queue]_if_no_space
needs_check|- metadata_low_watermark
    transaction id:

    ユーザー空間がボリュームマネージャーからのメタデータと同期を取るために使用する64ビットの数値。

    使用データブロック / 総データブロック

    空きブロック数がプールの低水位マーカーを下回ると、ユーザー空間にdmイベントが送信されます。このイベントはエッジトリガーで、再起動ごとに一度だけ発生します。ボリュームマネージャーのライタはこのイベントを登録し、その後ターゲットの状態を確認する必要があります。

    保持されたメタデータルート:

    ユーザー空間からの読み込みアクセスのために保持されているメタデータルートの位置。'-'は保持されたルートがないことを示します。

    discard_passdown|no_discard_passdown

    discardが実際に下位デバイスに渡されているかどうか。テーブルをロードする際この機能が有効になっていても、下位デバイスがこれをサポートしない場合、無効になる可能性があります。

    ro|rw|out_of_data_space

    プールが特定のデバイス障害に遭遇すると、読み取り専用メタデータモードに移行します。このモードではプールメタデータ（新しいブロックの割当など）への変更が許可されません。

    読み取り専用モードでも安全でないと判断される深刻な状況では、さらにI/Oが許可されず、ステータスは'Fail'という文字列のみを含みます。この場合、ユーザー空間の回復ツールを使用する必要があります。

    error_if_no_space|queue_if_no_space

    プールがデータまたはメタデータ空間を枯渇した場合、データデバイスに宛てられたIOをキューに並べたりエラーを返したりします。デフォルトでは、より多くの空間が追加されるか、「no_space_timeout」が期限切れになるまでIOをキューに並べます。「no_space_timeout」dm-thin-poolモジュールパラメータを使用してこのタイムアウトを変更できます。デフォルトは60秒ですが、0を設定することで無効にできます。

    needs_check（設定されている場合）'-'（設定されていない場合）

    メタデータ操作が失敗し、メタデータのスーパーブロックにneeds_checkフラグが設定されました。メタデータデバイスを非アクティブ化し、チェックまたは修復する必要があります。'-'はneeds_checkフラグが設定されていないことを示します。

    メタデータ低水位マーカー:

    メタデータ低水位マーカーのブロック数値。カーネルが内部でこの値を設定しますが、ユーザー空間がこの値を知る必要があります、イベントがこのしきい値を越えたことによるものかどうかを判断するためです。

  3. メッセージ

create_thin <dev id>

新しいスリムプロビジョニングデバイスを作成します。<dev id>は呼び出し元が選ぶ任意の24ビットの一意な識別子です。

create_snap <dev id> <origin id>

他のスリムプロビジョニングデバイスの新しいスナップショットを作成します。<dev id>は呼び出し元が選ぶ任意の24ビットの一意な識別子です。<origin id>は新しいデバイスがスナップショットとなるスリムプロビジョニングデバイスの識別子です。

delete <dev id>

スリムデバイスを削除します。これは取り消せません。

set_transaction_id <current id> <new id>

Userland volume managers, such as LVM, need a way to synchronise their external metadata with the internal metadata of the pool target. The thin-pool target offers to store an arbitrary 64-bit transaction id and return it on the target’s status line. To avoid races you must provide what you think the current transaction id is when you change it with this compare-and-swap message.

reserve_metadata_snap

Reserve a copy of the data mapping btree for use by userland. This allows userland to inspect the mappings as they were when this message was executed. Use the pool’s status command to get the root block associated with the metadata snapshot.

release_metadata_snap

Release a previously reserved copy of the data mapping btree.

‘thin’ target¶

  1. コンストラクタ

    thin <pool dev> <dev id> [<external origin dev>]
    pool dev:

    the thin-pool device, e.g. /dev/mapper/my_pool or 253:0

    dev id:

    the internal device identifier of the device to be activated.

    external origin dev:

    an optional block device outside the pool to be treated as a read-only snapshot origin: reads to unprovisioned areas of the thin target will be mapped to this device.

The pool doesn’t store any size against the thin devices. If you load a thin target that is smaller than you’ve been using previously, then you’ll have no access to blocks mapped beyond the end. If you load a target that is bigger than before, then extra blocks will be provisioned as and when needed.

  1. Status

    <nr mapped sectors> <highest mapped sector>

    If the pool has encountered device errors and failed, the status will just contain the string ‘Fail’. The userspace recovery tools should then be used.

    In the case where <nr mapped sectors> is 0, there is no highest mapped sector and the value of <highest mapped sector> is unspecified.

dm-log-writes (書き込みをログに記録するデバイスマッパーターゲット)¶

このターゲットは2つのデバイスを必要とし、通常はIOを処理するデバイスと、すべてのライト操作をログに記録するデバイスを指定します。これはファイルシステム開発者向けに、ファイルシステムが書き込まれる際のメタデータやデータの整合性を検証するためのものです。すべてのWRITEリクエストに対してlog_write_entryが記録され、ターゲットはユーザー空間から任意のデータを取得してログに挿入できます。WRITEリクエスト内のデータはログにコピーされるため、再現時に元の順序通りに動作します。

ログの順序¶

書き込みがキャッシュから外れたことを確認した後、完了の順序でログを記録します。これにより、通常のWRITEリクエストはREQ_PREFLUSHリクエストが次に来るまで実際にログに記録されません。これにより、ユーザー空間がディスク上の状態と一致する再現を容易にし、キャッシュ内の状態ではなく、不適切な待機/フラッシュを検出するのを助けます。

これは、書き込みが完了した時点ですべてのWRITEリクエストをリストにアタッチします。REQ_PREFLUSHリクエストを検知するとこのリストをリクエストに接続し、FLUSHリクエストが完了した時点ですべてのWRITEとFLUSHをログに記録します。REQ_PREFLUSHが発行された時点での完了したWRITEのみが順序通りに追加され、電源障害時の最悪シナリオをシミュレートします。以下の例を考慮してください（Wは書き込み、Cは完了を表します）：

W1,W2,W3,C3,C2,Wflush,C1,Cflush

ログには以下のようになります：

W3,W2,flush,W1….

これは実際にディスク上の状態をシミュレートするためであり、特定のタイミングでの電源障害が不整合なファイルシステムを生成するケースを検出できます。

REQ_FUAリクエストはこのフラッシュメカニズムをバイパスし、完了した時点で即座にログに記録されます。これらのリクエストは明らかにデバイスキャッシュをバイパスするためです。

REQ_OP_DISCARDリクエストはWRITEリクエストと同じように扱われます。そうでなければ、DISCARDリクエストがすべて終わってからWRITEリクエスト、そしてFLUSHリクエストの順で処理されてしまいます。以下の例を考慮してください：

WRITE block 1, DISCARD block 1, FLUSH

DISCARDが完了した時点でログに記録すると、再現時の順序は以下のようになります：

DISCARD 1, WRITE 1, FLUSH

これは実際に起きた順序とは異なり、ログ再現時に検出されません。

ターゲットインターフェース¶

  1. コンストラクタ

    log-writes <dev_path> <log_dev_path>

    dev_path

    通常はすべてのIOが送られるデバイス。

    log_dev_path

    ログエントリが書き込まれるデバイス。

  2. Status

    <#logged entries> <highest allocated sector>

    #logged entries

    ログエントリの数

    highest allocated sector

    最高に割り当てられたセクタ

  3. メッセージ

mark <description>

dmsetupメッセージを使用して、ログに任意のマーカーを設定できます。たとえば、毎回の書き込み後にファイルシステムをfsckする場合、まずmkfsまでのログを再現して、fsck対象が適切であることを確認する必要があります。このような場合、以下のようにします：

mkfs.btrfs -f /dev/mapper/log
dmsetup message log 0 mark mkfs
<run test>

これにより、mkfsのマーカーまでログを再現し、その後指定した間隔でfsckチェックを実行しながらログを再現できます。

すべてのログには、終端に「dm-log-writes-end」とラベルが付けられたマーカーがあります。

ユーザースペースコンポーネント¶

ログをさまざまな方法で再現するユーザースペースツールがあります。以下から確認できます： https://github.com/josefbacik/log-writes

使用例¶

ファイルシステムでfsyncをテストしたい場合、以下のようにします：

TABLE="0 $(blockdev --getsz /dev/sdb) log-writes /dev/sdb /dev/sdc"
dmsetup create log --table "$TABLE"
mkfs.btrfs -f /dev/mapper/log
dmsetup message log 0 mark mkfs

mount /dev/mapper/log /mnt/btrfs-test
<some test that does fsync at the end>
dmsetup message log 0 mark fsync
md5sum /mnt/btrfs-test/foo
umount /mnt/btrfs-test

dmsetup remove log
replay-log --log /dev/sdc --replay /dev/sdb --end-mark fsync
mount /dev/sdb /mnt/btrfs-test
md5sum /mnt/btrfs-test/foo
<verify md5sum's are correct>

Another option is to do a complicated file system operation and verify the file
system is consistent during the entire operation.  You could do this with:

TABLE="0 $(blockdev --getsz /dev/sdb) log-writes /dev/sdb /dev/sdc"
dmsetup create log --table "$TABLE"
mkfs.btrfs -f /dev/mapper/log
dmsetup message log 0 mark mkfs

mount /dev/mapper/log /mnt/btrfs-test
<fsstress to dirty the fs>
btrfs filesystem balance /mnt/btrfs-test
umount /mnt/btrfs-test
dmsetup remove log

replay-log --log /dev/sdc --replay /dev/sdb --end-mark mkfs
btrfsck /dev/sdb
replay-log --log /dev/sdc --replay /dev/sdb --start-mark mkfs \
      --fsck "btrfsck /dev/sdb" --check fua

これにより、FUAリクエストを検出するまでログを再現し、fsckコマンドを実行します。fsckが正常に終了した場合、次のFUAまで再現を続け、完了するか、fsckコマンドが異常終了するまで繰り返します。

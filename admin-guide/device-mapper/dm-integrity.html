dm-integrity¶

dm-integrity テンプレートは、セクタごとのタグを備えたブロックデバイスをエミュレートし、整合性情報の保存に利用できるようにします。

セクタごとの整合性タグを保存する一般的な問題は、セクタと整合性タグの書き込みが原子的でなければならないことです。つまり、クラッシュ発生時にセクタと整合性タグのどちらも書き込まれるか、どちらも書き込まれないことが保証される必要があります。

書き込みの原子性を保証するため、dm-integrity テンプレートはジャーナルを使用します。セクタデータと整合性タグをジャーナルに書き込み、ジャーナルをコミットした後、データと整合性タグをそれぞれの場所にコピーします。

dm-integrity テンプレートは dm-crypt テンプレートと併用可能です。この場合、dm-crypt テンプレートが整合性データを生成し、bio_integrity_payload が bio に添付されて dm-integrity テンプレートに渡します。このモードでは、dm-crypt と dm-integrity が認証されたディスク暗号化を提供し、攻撃者が暗号化デバイスを改変した場合、ランダムデータではなく I/O エラーが返されます。

dm-integrity テンプレートはスタンドアロンモードでも使用可能です。このモードでは、テンプレートが内部で整合性タグを計算および検証します。このモードでは、ディスクまたは I/O パスにおける静かなデータ破壊を検出できます。

dm-integrity はジャーナルではなくビットマップを使用する代替モードもあります。ビットマップのビットが 1 の場合、対応する領域のデータと整合性タグは同期されていません。マシンがクラッシュした場合、同期されていない領域は再計算されます。ビットマップモードはジャーナルモードより高速ですが、信頼性が低く、クラッシュ時にデータ破壊が発生した場合、検出されない可能性があります。

テンプレートを初めてロードする際、カーネルドライバーがデバイスをフォーマットします。ただし、スーパーブロックにゼロが含まれている場合にのみフォーマットします。スーパーブロックが有効でない場合もしくはゼロでない場合、dm-integrity テンプレートはロードできません。

テンプレートを初めて使用するには:

  1. スーパーブロックをゼロで上書きする

  2. 1セクタサイズで dm-integrity テンプレートをロードし、カーネルドライバーがデバイスをフォーマットします

  3. dm-integrity テンプレートをアンロードする

  4. スーパーブロックから「provided_data_sectors」値を読み取る

  5. 「provided_data_sectors」サイズで dm-integrity テンプレートをロードする

  6. dm-integrity と dm-crypt を併用する場合は、dm-crypt テンプレートを「provided_data_sectors」サイズでロードする

ターゲット引数:

  1. 下位ブロックデバイス

  2. デバイスの開始位置にある予約セクタの数 - dm-integrityはこれらのセクタを読み書きしません

  3. 整合性タグのサイズ（"-"が使用されている場合は、内部ハッシュアルゴリズムからサイズを取得します）

  4. mode:

    D - 直接書き込み（ジャーナルなし）

    このモードではジャーナリングが使用されず、データセクタと整合性タグが別々に書き込まれます。クラッシュした場合、データと整合性タグが一致しない可能性があります

    J - ジャーナル付き書き込み

    データと整合性タグがジャーナルに書き込まれ、原子性が保証されます。クラッシュした場合、データとタグの両方が書き込まれるか、どちらも書き込まれません。ジャーナルモードは書き込みスループットが2倍低下します

    B - ビットマップモード - データとメタデータが何も同期せずに書き込まれます

    ドライバーはデータとメタデータが不一致な不整合領域のビットマップを維持します。このモードは内部ハッシュのみで使用可能です

    R - リカバリーモード - このモードではジャーナルが再現されません

    チェックサムの検証も行われず、デバイスへの書き込みが許可されません。このモードはデバイスが他の標準モードで起動できない場合のデータ復旧に有用です

  5. 追加引数の数

追加引数:

journal_sectors:数値

ジャーナルのサイズ、この引数はデバイスのフォーマット時にのみ使用されます。すでにフォーマット済みのデバイスではスーパーブロックから値が使用されます

interleave_sectors:数値

インターリーブセクタ数。この値は2の累乗に丸められます。すでにフォーマット済みのデバイスではスーパーブロックから値が使用されます

meta_device:デバイス

デバイス上でデータとメタデータをインターリーブしないでください。メタデータ専用の別デバイスを使用します

buffer_sectors:数値

1つのバッファ内のセクタ数。この値は2の累乗に丸められます

タグ領域はバッファを使用してアクセスされ、バッファサイズは設定可能です。大きなバッファサイズはI/Oサイズを大きくしますが、I/O操作の回数は少なくなります

journal_watermark:数値

ジャーナルのウォーターマーク（％）。ジャーナルサイズがこのウォーターマークを超えると、ジャーナルをフラッシュするスレッドが起動されます

commit_time:数値

コミット時間（ミリ秒）。この時間経過後にジャーナルが書き込まれます。FLUSHリクエストが受信された場合も即座にジャーナルが書き込まれます

internal_hash:アルゴリズム(:キー)（キーはオプション）

内部ハッシュまたはCRCを使用します。この引数が使用されている場合、dm-integrityターゲットは上位ターゲットからの整合性タグを受け付けませんが、自動的に生成・検証を行います

crcアルゴリズム（例：crc32）を使用することで、データの誤った破損を防ぐことができます。また、hmacアルゴリズム（例：「hmac(sha256):0123456789abcdef」）を使用することも可能です。このモードでは暗号化せずにデータの暗号化認証が行われます。

この引数を使用しない場合、上位レイヤーのターゲット（例：dm-crypt）から整合性タグが受け取られます。上位レイヤーのターゲットは整合性タグの有効性を確認する必要があります。

再計算

内部ハッシュを使用する場合にのみ有効で、整合性タグを自動的に再計算します。

journal_crypt:algorithm(:key)（keyはオプション）

指定されたアルゴリズムでジャーナルを暗号化し、攻撃者がジャーナルを読むことができないようにします。ブロック暗号（例：「cbc(aes)」）やストリーム暗号（例：「chacha20」、「salsa20」、「ctr(aes)」）を使用できます。

ジャーナルにはブロックデバイスへの最後の書き込み履歴が含まれており、攻撃者がジャーナルを読むと最後に書き込まれたセクタ番号が確認できます。セクタ番号から攻撃者は書き込まれたファイルのサイズを推測できるため、この状況を防ぐためにジャーナルを暗号化できます。

journal_mac:algorithm(:key)（keyはオプション）

ジャーナル内のセクタ番号を誤ってまたは悪意を持って変更されることを防ぎます。誤った変更を防ぐにはcrcアルゴリズムを使用し、悪意のある変更を防ぐにはkey付きのhmacアルゴリズムを使用してください。

内部ハッシュを使用している場合、このオプションは必要ありません。このモードではジャーナルを再現する際、ジャーナルエントリの整合性がチェックされるため、変更されたセクタ番号がこの段階で検出されます。

block_size:number

データブロックのサイズ（バイト単位）。ブロックサイズが大きいほど、各ブロックの整合性メタデータのオーバーヘッドが小さくなります。サポートされる値は512、1024、2048、4096バイトです。指定しない場合、デフォルトのブロックサイズは512バイトです。

sectors_per_bit:number

ビットマップモードでは、このパラメータは1ビットマップに対応する512バイトセクタ数を指定します。

bitmap_flush_interval:number

ビットマップのフラッシュ間隔（ミリ秒単位）。この間隔が経過するとメタデータバッファが同期されます。

allow_discards

整合性デバイスに対してブロック削除リクエスト（TRIM）を許可します。削除は内部ハッシュを使用するデバイスにのみ許可されます。

fix_padding

タグ領域のより小さなパディングを使用し、空間効率を高めます。このオプションが存在しない場合、古いカーネルとの互換性のために大きなパディングが使用されます。

legacy_recalculate

HMACキーを使用してボリュームの再計算を許可します。セキュリティ上の理由によりデフォルトでは無効になっています - 攻撃者がボリュームを変更し、recalc_sectorをゼロに設定すると、カーネルが変更を検出しない可能性があります。

ジャーナルモード(D/J)、buffer_sectors、journal_watermark、commit_time、allow_discardsは、ターゲットを再ロードする際に変更可能です（非アクティブなテーブルをロードし、スワップしてsuspendとresumeで再起動）。他の引数はターゲットを再ロードする際には変更すべきではありません。ディスクデータのレイアウトがこれらに依存しており、再ロード後のターゲットが機能しなくなる可能性があります。

ステータスライン:

  1. 整合性の不一致の数

  2. 提供されたデータセクタ数 - つまりユーザーが使用可能なセクタ数

  3. 現在の再計算位置（再計算が行われていない場合は'-'）

フォーマットされたブロックデバイスのレイアウト:

  • 予約セクタ

    (このターゲットでは使用されませんが、LUKSメタデータや他の用途に使用可能)、予約領域のサイズはターゲット引数で指定されます

  • スーパーブロック(4kiB)

    • マジック文字列 - デバイスがフォーマットされたことを示します

    • version

    • interleaveセクタのlog2値

    • 整合性タグのサイズ

    • ジャーナルセクションの数

    • 提供されたデータセクタ数 - このターゲットが提供するセクタ数（つまりデバイスサイズからすべてのメタデータとパディングのサイズを引いた値）。このターゲットを使用するユーザーは、'provided data sectors'の制限を超えるデータへのアクセスを行うBIOSを送信すべきではありません。

    • フラグ
      SB_FLAG_HAVE_JOURNAL_MAC

      • journal_macが使用されている場合にフラグが設定されます

      SB_FLAG_RECALCULATING

      • 再計算が進行中です

      SB_FLAG_DIRTY_BITMAP

      • ジャーナル領域には汚染ブロックのビットマップが含まれています

    • log2(セクタあたりのブロック数)

    • 再計算が終了した位置

  • ジャーナル

    ジャーナルはセクションに分割され、各セクションには以下の内容が含まれます

    • メタデータ領域(4kiB)、ジャーナルエントリを含みます

      • すべてのジャーナルエントリには以下の内容が含まれます

        • 論理セクタ（データとタグが書き込まれるべき場所を指定します）

        • データの最後の8バイト

        • 整合性タグ（サイズはスーパーブロックで指定されます）

      • すべてのメタデータセクタは最後に以下の内容を含みます

        • mac（8バイト）、8つのメタデータセクタ内のすべてのmacは64バイトの値を形成します。これはジャーナルセクション内のセクタ番号のHMACを保存するために使用され、ジャーナル内のセクタ番号が改ざんされる可能性を防ぎます。

        • コミットID

    • データ領域（サイズは可変で、メタデータ領域に収まるジャーナルエントリの数に依存します）

      • データ領域内のすべてのセクタには以下の内容が含まれます

        • データ（504バイトのデータ、最後の8バイトはジャーナルエントリに保存されます）

        • コミットID

    ジャーナルセクション全体が正しく記録されているかをテストするため、ジャーナルの各512バイトセクタ末尾には8バイトのコミットIDが付与されます。ジャーナルセクション内のすべてのセクタでコミットIDが一致する場合、そのセクションが正しく記録されているとみなされます。コミットIDが一致しない場合は、セクションが部分的に記録されており、再実行すべきではありません。

  • タグとデータが混在した1つ以上のラン

    各ランには以下が含まれます:

    • タグ領域 - セクタごとに整合性タグを含みます

    • データ領域 - データセクタを含みます。1つのランに含まれるデータセクタ数は2の累乗でなければなりません。この値のlog2はスーパーブロックに記録されています。

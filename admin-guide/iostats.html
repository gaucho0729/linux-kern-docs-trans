I/O 統計項目¶

2.4.20以降（一部の以前のバージョンではパッチで導入）、および2.5.45以降では、ディスク活動を測定するためのより詳細なディスク統計情報が導入されました。このようなツールは、 sar および iostat 通常はこれらを解釈し、作業を自動で行います。ただし、自作のツールを作成したい場合、ここにフィールドの説明があります。

2.4では、情報は追加のフィールドとして /proc/partitionsファイルに含まれています。2.6以降では、情報は2つの場所に存在します：1つは /proc/diskstatsファイルに、もう1つはsysfsファイルシステムにあります。sysfsファイルシステムは情報を取得するためにはマウントされている必要があります。このドキュメントでは、sysfsが /sysにマウントされていると仮定しますが、もちろんどこにマウントされている可能性もあります。両方の情報源は同じ情報から取得しており、差異がありません。 /proc/diskstats とsysfsは同じ情報源を使用するため、一致するはずです。

これらの異なるフォーマットの例は以下の通りです：

2.4:
   3     0   39082680 hda 446216 784926 9550688 4382310 424847 312726 5922052 19310380 0 3376340 23705160
   3     1    9221278 hda1 35486 0 35496 38030 0 0 0 0 0 38030 38030

2.6+ sysfs:
   446216 784926 9550688 4382310 424847 312726 5922052 19310380 0 3376340 23705160
   35486    38030    38030    38030

2.6+ diskstats:
   3    0   hda 446216 784926 9550688 4382310 424847 312726 5922052 19310380 0 3376340 23705160
   3    1   hda1 35486 38030 38030 38030

4.18+ diskstats:
   3    0   hda 446216 784926 9550688 4382310 424847 312726 5922052 19310380 0 3376340 23705160 0 0 0 0

2.4では、実行できます grep 'hda ' /proc/partitions。2.6以降では、選択肢があります cat /sys/block/hda/stat または grep 'hda ' /proc/diskstats.

sysfsの選択は、特定の少数のディスクを監視する場合に適しています。 /proc/diskstats ディスクが多数ある場合、この選択肢がより適しています。なぜなら、ディスク統計のスナップショットごとに50、100、500以上ものオープン/クローズオーバーヘッドを回避できるからです。

2.4では、統計項目はデバイス名の後にあります。上記の例では、最初の統計項目は446216です。対照的に、2.6以降では、 /sys/block/hda/statを確認すると、446216から始まる15項目が表示されます。また、 /proc/diskstatsを確認すると、15項目の前にメジャーデバイス番号とマイナーデバイス番号、デバイス名が表示されます。これらのフォーマットはいずれも15項目の統計情報を提供し、それぞれの項目の意味は完全に同じです。すべての項目は起動後累積しており、項目9はI/O完了時にゼロに戻ります。他の項目は増加します（オーバーフローしてラップする場合を除く）。非常に忙しいシステムや長寿命のシステムではラップが発生する可能性があります。そのため、アプリケーションはラップを扱う準備が必要です。ラップに関する情報は、各項目ごとにunsigned int（32ビット）またはunsigned long（マシンによって32ビットまたは64ビット）の型として記載されています。観測時間が非常に広範囲でない限り、これらの項目は気づく前に2回ラップしないはずです。

各統計項目は指定されたデバイスにのみ適用されます。システム全体の統計を取得したい場合は、すべてのデバイスを検索し、合計を計算する必要があります。

項目1 – 読み込み完了数（unsigned long）

これは成功した読み込みの総数です。

項目2 – 読み込みマージ数、項目6 – 書き込みマージ数（unsigned long）

連続する読み込みと書き込みは効率化のために統合されることがあります。そのため、2つの4K読み込みが最終的にディスクに渡る前に1つの8K読み込みになる可能性があり、その結果として1つのI/Oとしてカウント（およびキューイング）されます。このフィールドは、このような統合がどれだけ行われたかを示します。

フィールド3 – 読み込んだセクタ数（符号なし長整数）

成功した読み込みセクタの総数です。

フィールド4 – 読み込みに費やしたミリ秒数（符号なし整数）

すべての読み込みに費やしたミリ秒数（__make_request()からend_that_request_last()までの時間）の合計です。

フィールド5 – 成功した書き込み数（符号なし長整数）

成功した書き込みの総数です。

フィールド6 – 統合された書き込み数（符号なし長整数）

フィールド2の説明を参照してください。

フィールド7 – 書き込んだセクタ数（符号なし長整数）

成功した書き込みセクタの総数です。

フィールド8 – 書き込みに費やしたミリ秒数（符号なし整数）

すべての書き込みに費やしたミリ秒数（__make_request()からend_that_request_last()までの時間）の合計です。

フィールド9 – 進行中のI/O数（符号なし整数）

ゼロになるはずの唯一のフィールドです。要求が適切なstruct request_queueに渡るたびにインクリメントされ、完了するたびにデクリメントされます。

フィールド10 – I/O処理に費やしたミリ秒数（符号なし整数）

フィールド9がゼロでない限りこのフィールドは増加します。

5.0以降、少なくとも1つの要求が開始または完了したときにjiffiesがカウントされます。要求が2jiffies以上かかる場合、並行処理中の要求のため一部のI/O時間は計測されません。

フィールド11 – 重み付きI/O処理に費やしたミリ秒数（符号なし整数）

このフィールドは、I/O開始、完了、統合、またはこれらの統計の読み込みごとにインクリメントされます。進行中のI/O数（フィールド9）を最後の更新時からのI/O処理に費やしたミリ秒数（このフィールドの更新時からの時間）で乗算した値を加算します。これにより、I/O完了時間と溜まっているバックログを簡単に測定できます。

フィールド12 – 成功したディスカード数（符号なし長整数）

成功したディスカードの総数です。

フィールド13 – 統合されたディスカード数（符号なし長整数）

フィールド2の説明を参照してください。

フィールド14 – ディスカードされたセクタ数（符号なし長整数）

成功したディスカードセクタの総数です。

フィールド15 – ディスカードに費やしたミリ秒数（符号なし整数）

すべてのディスカードに費やしたミリ秒数（__make_request()からend_that_request_last()までの時間）の合計です。

フィールド16 – 完了したフラッシュリクエスト数

成功したフラッシュリクエストの総数です。

ブロックレイヤーはフラッシュリクエストを統合し、一度に最大1つのリクエストを実行します。これはディスクによって実行されたフラッシュリクエストをカウントします。パーティションには追跡されません。

フィールド17 – フラッシュに費やしたミリ秒数

これはすべてのフラッシュリクエストが費やしたミリ秒数の合計です。

パフォーマンスボトルネックを導入することを避けるため、これらのカウンタを変更する際にはロックは保持されません。これにより、変更が衝突した場合、わずかな不正確さが生じる可能性があります。たとえば、各パーティションごとの読み取りI/Oの合計がディスクに実行されたものと一致するはずですが、ロックがないため、実際には非常に近似値になる可能性があります。

2.6以降では、各CPUごとにカウンタが存在し、ロックの不足がほぼ問題にならなくなりました。統計を読み取る際には、各CPUごとのカウンタを合計し（unsigned long変数のオーバーフローが発生する可能性あり）、その結果をユーザーに提供します。ただし、各CPUごとのカウンタ自体にアクセスするためのユーザーファーストインターフェースは存在しません。

4.19以降では、リクエスト時間はナノ秒精度で測定され、このインターフェースに表示される際にはミリ秒に切り捨てられます。

ディスクとパーティションの違い¶

2.4と2.6以降ではI/Oサブシステムで大きな変更がありました。その結果、一部の統計情報が消失しました。ディスクアドレスがパーティション相対的なものからホストディスク相対的なものに変換されるタイミングが大幅に早まりました。すべてのマージとタイミングは今ではディスクレベルで行われるようになり、2.4ではディスクとパーティションの両方で行われていました。このため、2.6以降ではパーティションの統計出力がディスクとは異なります。2.6以降のマシンではパーティションにはのみ4つのフィールドが利用可能です。これは上記の例に反映されています。 four これは上記の例に反映されています。

フィールド1 – 送信された読み取り数

これはこのパーティションに送信された読み取り数の合計です。

フィールド2 – 読み取られたセクター数

これはこのパーティションから読み取る必要があるセクター数の合計です。

フィールド3 – 送信された書き込み数

これはこのパーティションに送信された書き込み数の合計です。

フィールド4 – 書き込まれたセクター数

これはこのパーティションに書き込む必要があるセクター数の合計です。

ディスクアドレスがディスク相対的なものに変換されるため、パーティション相対的なアドレスの記録は残っていません。これにより、後の読み取りの成功または失敗をパーティションに帰属させることはできません。言い換えれば、パーティションの読み取り数はパーティションのキューイングよりもわずかに前でカウントされ、ディスク全体の完了時にカウントされます。これは微妙な違いであり、ほとんどの場合では興味がないでしょう。

より重要なのは、パーティションのマージ前の読み込み/書き込み数とディスクのマージ後の読み込み/書き込み数を数えることによって引き起こされる誤差です。典型的なワークロードでは、連続的で隣接したリクエストが多数含まれるため、発行された読み込み/書き込み数は完了した読み込み/書き込み数の何倍にもなり得ます。

2.6.25では、パーティションおよびディスクの統計情報が再び完全に利用可能となり、パーティションとディスクの統計情報が再び整合性を保つようになりました。しかし、パーティション関連のアドレスを記録していないため、マージ後のリクエストの最初のセクタを含むパーティションに操作が割り当てられます。リクエストがパーティションをまたいでマージされる可能性があるため、このためにはじめてわずかな（おそらく無視できる）誤差が生じる可能性があります。

追加の注意点¶

2.6以降では、sysfsがデフォルトでマウントされません。Linuxのディストリビューションがまだこれを追加していない場合、以下のような行を追加してください： /etc/fstab:

none /sys sysfs defaults 0 0

2.6以降では、すべてのディスク統計情報が /proc/statから削除されました。2.4では、これらがどちらにも表示されます /proc/partitions および /proc/stat、ただし、 /proc/stat にあるものは、 /proc/partitions にあるものとは非常に異なる形式を取っています。（proc(5)を参照してください。システムに存在する場合）

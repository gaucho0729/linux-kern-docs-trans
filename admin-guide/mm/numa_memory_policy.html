NUMA Memory Policy¶

NUMAメモリポリシーとは何ですか？¶

Linuxカーネルでは、「memory policy（メモリポリシー）」とは、NUMAシステムまたはエミュレートされたNUMAシステムにおいて、カーネルがメモリを割り当てるノードを決定する仕組みです。Linuxは、非均一メモリアクセス（Non-Uniform Memory Access: NUMA）アーキテクチャをサポートするプラットフォームを2.4.?からサポートしており、現在のメモリポリシーサポートは2004年5月頃にリリースされたLinux 2.6に追加されました。このドキュメントでは、2.6におけるメモリポリシーサポートの概念とAPIについて説明します。

メモリポリシーは、cpusets（Documentation/admin-guide/cgroup-v1/cpusets.rst)という管理メカニズムと混同しないでください。cpusetsは、複数のプロセスがメモリを割り当てられるノードを制限するための仕組みです。メモリポリシーは、NUMAを意識したアプリケーションが利用できるプログラミングインターフェースです。タスクにcpusetsとポリシーが同時に適用されている場合、cpusetsの制限が優先されます。詳しくは メモリポリシーとcpusets をご参照ください。

メモリポリシーの概念¶

メモリポリシースコープ¶

Linuxカーネルは、メモリポリシーのスコープをサポートしており、ここでは最も一般的な順に最も特定の順に説明します：

システムデフォルトポリシー

このポリシーはカーネルにハードコードされています。これは、以下のより特定のポリシースコープによって制御されていないすべてのページ割り当てを制御します。システムが「起動状態」になった際、システムデフォルトポリシーは下記で説明するローカル割り当てを使用します。ただし、起動時にシステムデフォルトポリシーは、十分なメモリを持つすべてのノードに割り当てを分散し、初期起動ノードを起動時の割り当てで過負荷から守るための設定になります。

タスク/プロセスポリシー

これはオプションの、タスクごとのポリシーです。特定のタスクに定義された場合、このポリシーは、より特定のスコープによって制御されていないタスクまたはその代行によるページ割り当てをすべて制御します。タスクがタスクポリシーを定義していない場合、タスクポリシーによって制御されるすべてのページ割り当てはシステムデフォルトポリシーにフォールバックします。

タスクポリシーはタスクのアドレス空間全体に適用されるため、継承可能です。実際には、fork() [clone()でCLONE_VMフラグを指定しない場合]とexec*()で継承されます。これにより、親タスクが子タスクのタスクポリシーを設定できるようになります。子タスクがメモリポリシーを意識していない実行可能ファイルからexec()される場合でも、親タスクがポリシーを設定できます。詳しくは メモリポリシーAPI セクションで、タスクがタスク/プロセスポリシーを設定・変更するために使用できるシステムコールの概要をご参照ください。

マルチスレッドタスクにおいて、タスクポリシーは、ポリシーをインストールした[Linuxカーネルタスク]と、そのスレッドによって後続で作成されたスレッドにのみ適用されます。新しいタスクポリシーがインストールされる時点に存在する、他のスレッドは現在のポリシーを保持します。

タスクポリシーは、ポリシーがインストールされた後で割り当てられたページにのみ適用されます。タスクがタスクポリシーを変更する際、すでにタスクによってフォールトイン（ページイン）されたページは、割り当てられた時点でのポリシーに基づいて保持されます。

VMAポリシー

「VMA（仮想メモリ領域）」とは、タスクの仮想アドレス空間の範囲を指します。タスクは、自身の仮想アドレス空間の特定の範囲に対して特定のポリシーを定義できます。詳しくは、以下の「mbind()システムコール」セクションをご参照ください。 メモリポリシーAPI mbind()システムコールを使用してVMAポリシーを設定する方法についての概要は、以下のセクションをご参照ください。

VMAポリシーは、このアドレス空間の領域をバックするページの割り当てを制御します。タスクのアドレス空間のどの領域にも明示的なVMAポリシーが設定されていない場合、タスクポリシーにフォールバックし、タスクポリシー自体もシステムデフォルトポリシーにフォールバックすることがあります。

VMAポリシーにはいくつかの複雑な点があります：

  • VMAポリシーは、みなしページ（匿名ページ）にのみ適用されます。これは、匿名セグメント（タスクスタックやヒープなど）に割り当てられたページ、またはMAP_ANONYMOUSフラグでmmap()されたアドレス空間の領域を含みます。ファイルマッピングにVMAポリシーを適用した場合、MAP_SHAREDフラグが使用されている場合は無視されます。MAP_PRIVATEフラグが使用されている場合は、マッピングへの書き込み試行時に匿名ページが割り当てられた際にのみポリシーが適用されます（つまり、Copy-On-Writeのタイミング）。

  • VMAポリシーは、仮想アドレス空間を共有するすべてのタスク（いわゆるスレッド）に共有され、ポリシーのインストールタイミングに関係なく継承されます。fork()によっても継承されます。ただし、VMAポリシーはアドレス空間がexec*()によって破棄され再作成されるため、exec()を介して継承することはできません。したがって、NUMAを意識したアプリケーションのみがVMAポリシーを使用できます。

  • タスクは、以前にmmap()で割り当てられた領域のサブ範囲に新しいVMAポリシーをインストールできます。このような場合、Linuxは既存の仮想メモリ領域を2つまたは3つのVMAに分割し、それぞれに独自のポリシーを割り当てます。

  • デフォルトでは、VMAポリシーはポリシーがインストールされた後で割り当てられたページにのみ適用されます。既にVMA範囲にフォールトインしたページは、割り当てられた時点でのポリシーに基づいて保持されます。しかし、2.6.16以降、Linuxはmbind()システムコールを通じてページの移動をサポートしており、新しいポリシーがインストールされた後でもページの内容を移動させることができます。

共有ポリシー

概念的には、共有ポリシーは「メモリオブジェクト」に適用され、そのオブジェクトが1つ以上のタスクの異なるアドレス空間に共有マッピングされています。アプリケーションはVMAポリシーと同じように、mbind()システムコールを使用して共有オブジェクトをマッピングする仮想アドレス範囲を指定することで共有ポリシーをインストールします。ただし、VMAポリシーはタスクのアドレス空間の範囲の属性とみなされるのに対し、共有ポリシーは直接共有オブジェクトに適用されるため、オブジェクトにアタッチするすべてのタスクが同じポリシーを共有し、どのタスクからも割り当てられた共有オブジェクトのページは共有ポリシーに従います。

2.6.22以降、共有メモリセグメント（shmget()またはmmap(MAP_ANONYMOUS|MAP_SHARED)で作成されたもの）のみが共有ポリシーをサポートします。Linuxに共有ポリシーのサポートが追加された際、関連するデータ構造はhugetlbfs shmemセグメントに追加されました。その時点ではhuget,lbfsはフォールト時に割り当てを行う「ラズィー割り当て」をサポートしていませんでしたため、hugetlbfs shmemセグメントは共有ポリシーのサポートと「接続」されていませんでした。現在ではhugetlbfsセグメントがラズィー割り当てをサポートしていますが、共有ポリシーのサポートはまだ完全ではありません。

上記の VMAポリシー セクションで述べたように、通常のファイルをMAP_SHAREDでmmap()した場合のページキャッシュページの割り当ては、共有ファイルマッピングでサポートされる仮想アドレス範囲にインストールされたVMAポリシーを無視します。代わりに、共有ページキャッシュページ（タスクによってまだ書き込まれていないプライベートマッピングをバックするページを含む）は、タスクポリシーが存在する場合はそれに従い、それがない場合はシステムデフォルトポリシーに従います。

共有ポリシーインフラストラクチャは、共有オブジェクトのサブセット範囲に異なるポリシーをサポートしています。しかし、Linuxは、ポリシーをインストールしたタスクのVMAを、各ポリシー範囲ごとに別々に分割します。そのため、共有メモリセグメントにアタッチする異なるタスクは、その1つの共有オブジェクトをマッピングするための異なるVMA構成を持つことができます。これは、共有メモリ領域を共有するタスクの/proc/<pid>/numa_mapsを確認することで確認できます。そのうちの1つのタスクが領域の1つ以上の範囲に共有ポリシーをインストールした場合です。

メモリポリシーのコンポーネント¶

NUMAメモリポリシーは、「モード」、オプションのモードフラグ、およびオプションのノードセットから構成されます。モードはポリシーの動作を決定し、オプションのモードフラグはモードの動作を決定し、オプションのノードセットはポリシー動作の引数として扱われます。

メモリポリシーは、参照カウントされた構造体struct mempolicyによって内部的に実装されます。この構造体の詳細は、以下で説明する必要に応じて文脈とともに説明します。

NUMAメモリポリシーは以下の4つの動作モードをサポートしています：

デフォルトモード–MPOL_DEFAULT

このモードはメモリポリシーAPIでのみ使用されます。内部的にはMPOL_DEFAULTはすべてのポリシースコープでNULLメモリポリシーに変換されます。既存の非デフォルトポリシーはMPOL_DEFAULTが指定されたときに単純に削除されます。その結果、MPOL_DEFAULTは「次の最も具体的なポリシースコープにフォールバックする」という意味を持ちます。

たとえば、NULLまたはデフォルトタスクポリシーはシステムデフォルトポリシーにフォールバックし、NULLまたはデフォルトVMAポリシーはタスクポリシーにフォールバックします。

メモリポリシーAPIのいずれかで指定されたデフォルトモードは、オプションのノードセットを使用しません。

このポリシーで指定されたノードセットが空でない場合、エラーです。

MPOL_BIND

このモードは、メモリがポリシーで指定されたノードセットから取得される必要があります。メモリは、割り当てが行われるノードに最も近いノード（十分な空きメモリを持つ）から割り当てられます。

MPOL_PREFERRED

このモードは、ポリシーで指定された単一のノードから割り当てを試みます。その割り当てが失敗した場合、カーネルはプラットフォームファームウェアから提供される情報に基づき、好ましいノードからの距離の増加順で他のノードを検索します。

Preferredポリシーは内部的に単一のノードを使用します（struct mempolicyのpreferred_nodeメンバ）。内部モードフラグMPOL_F_LOCALが設定されている場合、preferred_nodeは無視され、ポリシーはローカル割り当てとして解釈されます。「ローカル」割り当てポリシーは、割り当てが行われるCPUを含むノードから開始するPreferredポリシーと見なせます。

ユーザーがこのモードで空のnodemaskを指定することで、常にローカル割り当てが優先されるように指定できます。空のnodemaskを渡した場合、このポリシーは後述のMPOL_F_STATIC_NODESまたはMPOL_F_RELATIVE_NODESフラグを使用できません。

MPOL_INTERLEAVED

このモードでは、ポリシーで指定されたノード間でページ単位にページ割当を分散します。このモードは、使用されている文脈によって若干異なる挙動をします:

匿名ページおよび共有メモリページの割当において、Interleaveモードはポリシーで指定されたノード集合を、フォルトアドレスのページオフセットをセグメント[VMA]内のアドレス modulo ポリシーで指定されたノード数でインデックス付けします。その後、選択されたノードからページを割当てる試みを行い、そのノードがPreferredポリシーで指定されたか、またはローカル割当によって選択されたかのように動作します。つまり、割当は各ノードのzonelistに従って行われます。

ページキャッシュページの割当において、Interleaveモードはタスクごとのノードカウンタを維持してポリシーで指定されたノード集合をインデックス付けします。このカウンタは、指定されたノードの最大値に達した後、最小値に戻ります。これにより、アドレス範囲やファイル内のページオフセットではなく、割当順序によって指定されたノードにページを均等に分散させます。システム起動時に一時的なインターリーブシステムデフォルトポリシーはこのモードで動作します。

NUMAメモリポリシーは以下のオプションモードフラグをサポートしています:

MPOL_F_STATIC_NODES

このフラグは、タスクやVMAの許可ノード集合が変更された後でも、ユーザーが指定したnodemaskが再マッピングされないように指定します。

このフラグがない場合、メモリポリシーが再バインディングされるたびに（許可ノード集合の変更により）、ノード（Preferred）またはnodemask（Bind、Interleave）が新しい許可ノード集合に再マッピングされます。これにより、以前は望ましくなかったノードが使用される可能性があります。

このフラグがある場合、ユーザー指定のノードがタスクのcpusetの許可ノードと交差する場合、その交差する部分にメモリポリシーが適用されます。交差しない場合、デフォルトポリシーが使用されます。

たとえば、cpusetにmems 1-3が設定されたタスクが同じセットに対してInterleaveポリシーを設定している場合を考えてみます。cpusetのmemsが3-5に変更された場合、Interleaveはノード3、4、5で行われます。このフラグがある場合、ユーザーのnodemaskから許可されるのはノード3のみなので、インターリーブはそのノードのみで行われます。ユーザーのnodemaskから許可されるノードがなくなった場合、デフォルトの動作が使用されます。

MPOL_F_STATIC_NODESはMPOL_F_RELATIVE_NODESフラグと併用できません。また、空のnodemask（ローカル割当）で作成されたMPOL_PREFERREDポリシーにも使用できません。

MPOL_F_RELATIVE_NODES

このフラグは、ユーザーが渡したnodemaskがタスクまたはVMAの許可ノードセットに対する相対的なマッピングになることを指定します。カーネルはユーザーが渡したnodemaskを保持し、許可ノードセットが変更された場合、その元のnodemaskを新しい許可ノードセットに基づいて再マッピングします。

このフラグがない場合（MPOL_F_STATIC_NODESもない場合）、許可ノードセットが変更されると、メモリポリシーが再バインドされるたびに、ノード（Preferred）またはnodemask（Bind、Interleave）が新しい許可ノードセットに再マッピングされます。この再マッピングは、ユーザーが渡したnodemaskの許可ノードセットに対する相対性を保持しない可能性があります。たとえば、nodemaskが1,3,5の場合、許可ノードセットが元の状態に戻るまでに7-9に再マッピングされ、その後1-3に再マッピングされる可能性があります。

このフラグを使用すると、ユーザーが渡したnodemaskのノード番号が許可ノードセットに対する相対的な位置として再マッピングされます。つまり、ユーザーのnodemaskにノード0、2、4が設定されている場合、ポリシーは許可ノードセット内の最初のノード（BindまたはInterleaveの場合、3番目と5番目のノード）に適用されます。ユーザーが渡したnodemaskはタスクまたはVMAの許可ノードセットに対する相対的なノードを表します。

ユーザーのnodemaskに許可ノードセットの範囲外のノードが含まれている場合（たとえば、許可ノードセットが0-3の場合にノード5が設定されている）、再マッピングはnodemaskの先頭に戻り、すでに設定されていないノードはmempolicyのnodemaskに設定されます。

たとえば、cpusetにアタッチされたタスクがmems 2-5のセットでMPOL_F_RELATIVE_NODESを使用したInterleaveポリシーを設定している場合、cpusetのmemsが3-7に変更されると、interleaveはノード3、5-7で行われます。その後、cpusetのmemsが0、2-3、5に変更されると、interleaveはノード0、2-3、5で行われます。

一貫した再マッピングにより、このフラグを使用してメモリポリシーを指定するノードマスクを準備するアプリケーションは、現在の実際のcpusetによって課せられたメモリ配置を無視し、常にメモリノード0からN-1に配置されているかのようにノードマスクを準備すべきです。ここでNはポリシーが管理するメモリノードの数です。その後、カーネルがタスクのcpusetによって許可されるメモリノードのセットに再マッピングするようにさせましょう。これは時間とともに変化する可能性があるためです。

MPOL_F_RELATIVE_NODESはMPOL_F_STATIC_NODESフラグと併用できません。また、空のノードマスク（ローカル割当）で作成されたMPOL_PREFERREDポリシーにも使用できません。

メモリポリシー参照カウント¶

使用/解放競合を解消するため、struct mempolicyにはアトミックな参照カウントフィールドが含まれています。内部インターフェースであるmpol_get()/mpol_put()はそれぞれこの参照カウントを増減します。mpol_put()は参照カウントがゼロになるまで構造体をmempolicy kmemキャッシュに戻すことはありません。

新しいメモリポリシーが割り当てられると、参照カウントは「1」に初期化され、これは新しいポリシーをインストールしているタスクが保持する参照を表します。メモリポリシー構造体へのポインタが他の構造体に保存される場合、ポリシーインストール完了時にタスクの参照が解放されるため、もう一つの参照が追加されます。

ポリシーの実行時「使用」中には、参照カウントへのアトミック操作を最小限に抑えます。これはキャッシュラインがCPUとNUMAノード間で跳ねる可能性があるためです。「使用」は以下のいずれかを指します：

  1. タスク自身がget_mempolicy() API（以下で説明）を使用して、または他のタスクが/proc/<pid>/numa_mapsインターフェースを使用してポリシーを照会する場合。

  2. ページ割当時にポリシーのモードと関連するノードまたはノードリスト（存在する場合）を確認するためのポリシーの検査。これは「ホットパス」として扱われます。注意点として、MPOL_BINDの場合、「使用」はページ回収中にスリープする可能性のある全体の割当プロセスにわたるため、BINDポリシーノードマスクは参照によって不適切なノードをフィルタリングするために使用されます。

上記の使用において追加の参照を取得する必要はありません：

  1. システムデフォルトポリシーを取得/解放する必要はありません。これはシステムが起動後は変更されたり解放されたりしませんからです。

  2. ポリシーを照会する際には、タスクのタスクポリシーもしくはVMAポリシーに関する追加の参照を取る必要はありません。なぜなら、照会中にタスクのMMのmmap_lockを読み取り専用で取得しているからです。set_mempolicy()およびmbind() API [以下参照] は、タスクまたはVMAポリシーをインストールまたは置き換える際にはmmap_lockを書き込み専用で取得するため、他のタスクまたはスレッドがポリシーを照会している間にも、タスクまたはスレッドがポリシーを解放する可能性はありません。

  3. タスクまたはVMAポリシーのページ割当使用は、mmap_lockを読み取り専用で保持しながら行われるフォールト処理パスで発生します。再代入を行う際にはmmap_lockを書き込み専で保持する必要があるため、ページ割当中にポリシーが下から解放される可能性はありません。

  4. 共有ポリシーには特別な考慮が必要です。あるタスクが共有メモリポリシーを置き換えている間、別のタスクがそのポリシーに基づいてページを割当てるか、照会している可能性があります。この競合状態を解消するため、共有ポリシーインフラストラクチャは共有ポリシー管理構造のスピンロックを保持しながら、共有ポリシーの検索時に追加の参照を取得します。これにより、ポリシーを使用が終了した後でこの追加参照を解放する必要があります。非共有ポリシーと同じ検索/割当パスで共有ポリシーの追加参照を解放しなければなりません。このため、共有ポリシーは明示的に「共有」とマークされ、追加参照は「条件付きで」解放される必要があります。

    この追加参照カウントのため、共有ポリシーはスピンロックを保持しながらツリー構造で検索する必要があるため、ページ割当パスでの使用コストが高くなります。特に、異なるNUMAノードで実行されるタスク間で共有される共有メモリ領域の共有ポリシーでは顕著です。この追加オーバーヘッドは、常にタスクまたはシステムのデフォルトポリシーにフォールバックするか、全体をメモリに予備的にページを読み込んでロックダウンすることで回避可能です。ただし、すべてのアプリケーションに適切なわけではありません。

メモリポリシーAPI¶

Linuxはメモリポリシーを制御するための3つのシステムコールをサポートしています。これらのAPIは常に呼び出しタスク、呼び出しタスクのアドレス空間、または呼び出しタスクのアドレス空間にマップされている共有オブジェクトにのみ影響します。

注意

これらのAPIを定義するヘッダーや、ユーザー空間アプリケーションにおけるパラメータデータ型は、Linuxカーネルの一部ではないパッケージに存在します。カーネルのシステムコールインターフェース（'sys_'で始まる）は<linux/syscalls.h>に定義され、モードおよびフラグの定義は<linux/mempolicy.h>にあります。

タスクのメモリポリシーを設定:

long set_mempolicy(int mode, const unsigned long *nmask,
                                unsigned long maxnode);

呼び出し元タスクの「タスク/プロセスメモリポリシー」を、'mode'引数で指定されたモードと'nmask'で定義されたノードの集合に設定します。'nmask'は、少なくとも'maxnode'個のノードIDを含むビットマスクを指します。オプションのモードフラグは、'mode'引数にフラグを組み合わせて渡すことで指定できます（例: MPOL_INTERLEAVE | MPOL_F_STATIC_NODES）。

set_mempolicy(2)のmanページを参照してください。

タスクのメモリポリシーまたは関連情報の取得:

long get_mempolicy(int *mode,
                   const unsigned long *nmask, unsigned long maxnode,
                   void *addr, int flags);

'flags'引数に応じて、呼び出し元タスクの「タスク/プロセスメモリポリシー」を取得するか、指定された仮想アドレスのポリシーまたは位置を取得します。

get_mempolicy(2)のmanページを参照してください。

タスクのアドレス空間範囲のVMA/共有ポリシーをインストール:

long mbind(void *start, unsigned long len, int mode,
           const unsigned long *nmask, unsigned long maxnode,
           unsigned flags);

mbind()は、'start'と'len'引数で指定された呼び出し元タスクのアドレス空間範囲に、(mode, nmask, maxnodes)で指定されたポリシーをVMAポリシーとしてインストールします。追加の操作は'flags'引数で指定できます。

mbind(2)のmanページを参照してください。

メモリポリシー コマンドラインインターフェース¶

Linuxのメモリポリシー実装の一部とは厳密には関係ありませんが、numactl(8)というコマンドラインツールが存在し、以下のような操作が可能です:

  • set_mempolicy(2)、fork(2)、exec(2)を用いて指定されたプログラムのタスクポリシーを設定

  • mbind(2)を用いて共有メモリセグメントの共有ポリシーを設定

numactl(8)ツールは、メモリポリシーコールラップを含むランタイムバージョンのライブラリに同梱されています。一部のディストリビューションでは、ヘッダーやコンパイル時のライブラリが別個の開発パッケージとして提供されています。

メモリポリシーとcpusets¶

メモリポリシーは、上記のようにcpusets内で動作します。メモリポリシーがノードまたはノードのセットを必要とする場合、ノードはcpuset制約によって許可されたノードのセットに制限されます。ポリシーで指定されたnodemaskに含まれるノードがcpusetによって許可されていない場合、MPOL_F_RELATIVE_NODESが使用されていない場合、ポリシーで指定されたノードのセットとメモリを持つノードのセットの交差が使用されます。結果が空集合である場合、ポリシーは無効とみなされ、インストールできません。MPOL_F_RELATIVE_NODESが使用されている場合、ポリシーのノードは以前に説明したようにタスクの許可されたノードのセットにマッピングされ、折り込まれます。

タスクが2つのcpusetsに属し、共有メモリ領域（shmget()またはmmap()でMAP_ANONYMOUSとMAP_SHAREDフラグを使用して作成された共有メモリセグメントなど）にアクセスしている場合、メモリポリシーとcpusetsの相互作用は問題となることがあります。このような場合、タスクが領域に共有ポリシーをインストールした場合、2つのcpusetsが許可するメモリを持つノードのみがポリシーで使用できます。この情報を取得するには、メモリポリシーAPIの外側にステップを踏む必要があります。また、他のタスクが共有領域に接続しているcpusetsの許可メモリセットが互いに交差しない場合、「ローカル」割り当てが唯一有効なポリシーです。

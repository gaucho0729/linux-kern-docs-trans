Userfaultfd¶

目的¶

Userfaults は、ユーザー領域からオンデマンドページングを実装する機能を提供し、より一般的にはユーザー領域がさまざまなメモリページフォールトを制御できるようにします。これは通常、カーネルコードだけが行える操作です。

たとえば、userfaults は、 PROT_NONE+SIGSEGV トリックの適切でより最適な実装を可能にします。

設計¶

Userfaults は、 userfaultfd システムコールを通じて配信され、解決されます。

以下の userfaultfd （仮想メモリ範囲の登録と解除を除き）主に2つの主要な機能を提供します：

  1. read/POLLIN ユーザー領域スレッドに発生しているフォールトを通知するプロトコル

  2. さまざまな UFFDIO_* ioctl で仮想メモリ領域を管理できるようになります。これは、ユーザー領域が1)を通じて受信した userfaults を効率的に解決するか、またはバックグラウンドで仮想メモリを管理するための機能です。 userfaultfd userfaults と通常の仮想メモリ管理（mremap/mprotect）との真の利点は、userfaults のすべての操作で重い構造（vmas）を一切使用しないことです（実際には、

ランタイムロードでは mmap_lock を書き込みモードで取得しません）。 userfaultfd TB規模にわたる仮想アドレス空間を扱う際、vmas はページ（またはヒューゲページ）粒度のフォールト追跡に不適切です。そのような場合、必要な vmas は非常に多くなります。

システムコールで開かれた後、UNIX ドメインソケットを通じてマネージャープロセスに渡すこともできます。これにより、マネージャープロセスが複数の異なるプロセスの userfaults を処理できるようになり、それらのプロセスは処理内容を知らない場合でも（もちろん、後で同じ領域をマネージャーがすでに追跡している場合を除く）

以下の userfaultfd API 自身を userfaultfd 同じ領域をマネージャーがすでに追跡している場合、現在は -EBUSY).

API¶

最初に開かれた userfaultfd は、 UFFDIO_API ioctl を呼び出して有効化する必要があります。 uffdio_api.api 値が UFFD_API （または後の API バージョン）に設定されている必要があります。これにより、 read/POLLIN プロトコルでユーザー領域が使用するプロトコルが指定されます。 UFFD 2.5開発シリーズで導入された形式です。 uffdio_api.features ユーザー領域が使用するプロトコルは、 UFFDIO_API ioctl が成功した場合（つまり、リクエストされた uffdio_api.api が実行中のカーネルによってもサポートされ、リクエストされた機能が有効化される場合）、 uffdio_api.features および uffdio_api.ioctls read(2) プロトコルのすべての利用可能な機能と一般的な ioctl の 2 つの 64 ビットビットマスクが返されます。

以下の uffdio_api.features ioctl によって返された UFFDIO_API ビットマスクは、 userfaultfd がサポートするメモリタイプと、ページフォールト通知以外で生成されるイベントを示します：

  • 以下の UFFD_FEATURE_EVENT_* フラグは、ページフォールト以外のイベントがサポートされることを示します。これらのイベントについては、以下の Non-cooperative userfaultfd セクションでより詳細に説明します。

  • UFFD_FEATURE_MISSING_HUGETLBFS および UFFD_FEATURE_MISSING_SHMEM がサポートされていることを示します。 UFFDIO_REGISTER_MODE_MISSING hugetlbfs と共有メモリの登録をサポートしており、すべての shmem API（つまり tmpfs、 IPCSHM, /dev/zero, MAP_SHARED, memfd_createなど、仮想メモリ領域それぞれに対応します。

  • UFFD_FEATURE_MINOR_HUGETLBFS カーネルがサポートしていることを示します。 UFFDIO_REGISTER_MODE_MINOR hugetlbfs仮想メモリ領域の登録をサポートしています。 UFFD_FEATURE_MINOR_SHMEM shmem仮想メモリ領域のサポートを示す類似の機能です。

ユーザー・ランドアプリケーションは、ioctlを呼び出す際に使用する機能フラグを設定する必要があります。 UFFDIO_API その機能がサポートされている場合に有効にするよう要求します。

一旦 userfaultfd APIが有効化されている場合、 UFFDIO_REGISTER ioctlを呼び出す必要があります（返されたbitmaskに存在する場合）。 uffdio_api.ioctls bitmaskを用いて、メモリ範囲を登録します。 userfaultfd uffdio_register構造体を適切に設定することで、その範囲に対してカーネルが追跡するべきエラー種類を指定します。 uffdio_register.mode bitmaskはカーネルに、範囲に対して追跡するべきエラー種類を指定します。 UFFDIO_REGISTER ioctlは、範囲に登録されたユーザー・フォールトを解決するために適切なioctlのbitmaskを返します。 uffdio_register.ioctls 範囲に登録されたユーザー・フォールトを解決するために適切なioctlのbitmaskを返します。ただし、すべてのメモリタイプ（例: アノニマスメモリ vs. shmem vs. hugetlbfs）や、すべてのインターセプトされたエラー種類に対して、すべてのioctlがサポートされるとは限りません。

ユーザー・ランドは以下の方法でユーザー・フォールトを解決できます。 uffdio_register.ioctls バックグラウンドで仮想アドレス空間を管理する（メモリを追加したり、潜在的に削除したりするため）。 userfaultfd ユーザー・フォールトが発生する可能性があります。これは、ユーザー・ランドがバックグラウンドでユーザー・フォールトされたページをマップする直前に発生する可能性があるためです。

ユーザー・フォールトの解決¶

ユーザー・フォールトを解決する基本的な方法は3通りあります：

  • UFFDIO_COPY 原子的にユーザー空間から既存のページの内容をコピーします。

  • UFFDIO_ZEROPAGE 原子的に新しいページをゼロにします。

  • UFFDIO_CONTINUE 既に初期化されたページをマップします。

これらの操作は、操作が完了するまで、半分に初期化されたページを誰も見ることができないことを保証する点で原子的です。読み取り者は操作が完了するまでユーザー・フォールトを引き続き発生させます。

デフォルトでは、これらの操作は、該当範囲でブロックされているユーザー・フォールトを起こします。また、 UFFDIO_*_MODE_DONTWAKE mode フラグをサポートしており、これは、後で別途に起こすことを示します。

どのioctlを選びますか？ページフォールトの種類と、それを解決するために行いたい操作に依存します：

  • For UFFDIO_REGISTER_MODE_MISSING フォールトの場合、新しいページを提供するか（UFFDIO_COPY）、またはゼロページをマップするか（UFFDIO_ZEROPAGE）。デフォルトでは、カーネルは欠損フォールトに対してゼロページをマップします。userfaultfdを使用すると、フォールトを引き起こしたスレッドが再開する前に、ユーザー空間が提供するコンテンツを決定できます。

  • For UFFDIO_REGISTER_MODE_MINOR フォールトの場合、既存のページ（ページキャッシュ内）があります。ユーザー空間は、フォールトを解決する前にページの内容を変更するオプションがあります。内容が正しい（変更してもよいし、しなくてもよい）と確認したら、ユーザー空間はカーネルにページをマップさせ、フォールトを引き起こしたスレッドが再開するように求めます。 UFFDIO_CONTINUE.

注意：

  • 発生したフォールトの種類を確認するには、 pagefault.flags 内での uffd_msgを確認します。 UFFD_PAGEFAULT_FLAG_* フラグを確認します。

  • ページを配布するioctlsは、登録した範囲にデフォルトで設定されません。適切なioctl構造体のすべてのフィールドを埋めることを忘れないでください（範囲を含む）。

  • uffd_msg構造体から、uffdからスレッドで読み取ったアクセスがトリガーした欠損ページイベントのアドレスを取得できます。これらのIOCTLで必要なページ数を自由に指定できます。DONTWAKEを使用していない場合、これらのIOCTLの最初のものはエラー発生スレッドを起動します。

  • すべてのエラーをテストしてください（pollfd[0].revents & POLLERR）。これは、例えば範囲が正しく指定されていない場合などに発生します。

書き込み保護通知¶

これは（mprotectとSIGSEGVシグナルハンドラを使用するよりも）高速ですが同等の機能です。

まず、 UFFDIO_REGISTER_MODE_WPで範囲を登録する必要があります。mprotect(2)ではなく、 ioctl(uffd, UFFDIO_WRITEPROTECT, struct *uffdio_writeprotect) を使用します。構造体に渡された mode = UFFDIO_WRITEPROTECT_MODE_WP の範囲はデフォルトで設定されず、登録した範囲と一致する必要もありません。登録範囲内に好きなだけ範囲を設定できます。その後、uffdから読み取るスレッドで構造体が msg.arg.pagefault.flags & UFFD_PAGEFAULT_FLAG_WP が設定されています。ここで再び ioctl(uffd, UFFDIO_WRITEPROTECT, struct *uffdio_writeprotect) を送信します。このとき pagefault.mode が設定されていない場合、スレッドが起動します。これにより、書き込みが継続し、uffd読み取りスレッドで書き込みの記録を取ることができます。 UFFDIO_WRITEPROTECT_MODE_WP 両方の

で登録した場合、ページの供給と書き込み保護の解除の順序を考慮する必要があります。書き込み保護（WP）領域と未保護（!WP）領域への書き込みには違いがあります。前者は UFFDIO_REGISTER_MODE_MISSING および UFFDIO_REGISTER_MODE_WP が設定され、後者は UFFD_PAGEFAULT_FLAG_WP が設定されます。後者は保護で失敗しなかったにもかかわらず、 UFFD_PAGEFAULT_FLAG_WRITEが使用されたときにページを供給する必要があります。 UFFDIO_REGISTER_MODE_MISSING が使用されたときにページを供給する必要があります。

QEMU/KVM¶

QEMU/KVMは、 userfaultfd システムコールを使用してポストコピーのライブマイグレーションを実装しています。ポストコピーのライブマイグレーションは、クラウドの別のノードにメモリが配置されている仮想マシンを実行する形態のメモリ外部化の一種です。 userfaultfd 抽象化はKVMカーネルコードを1行も変更することなく、QEMUにポストコピーのライブマイグレーションを追加するのに十分汎用的です。

ゲストの非同期ページフォールト、 FOLL_NOWAIT および他のすべての GUP* 機能は、ユーザーフォールトと併用しても問題ありません。ユーザーフォールトはゲストスケジューラで非同期ページフォールトをトリガーするため、ユーザーフォールトを待っていることのないゲストプロセス（ネットワークに依存しているものなど）はゲストvcpuで継続して実行できます。

通常、ポストコピーのライブマイグレーションを開始する前にプレコピーのライブマイグレーションを1回実行することが有益です。これにより、読み取り専用ゲスト領域のユーザーフォールトを生成しないようにできます。

ポストコピーのライブマиграーションの実装は現在、単一の双方向ソケットを使用していますが、今後は2つの異なるソケットが使用される予定です（ユーザーフォールトの遅延を最小限に抑えるため、ソケットの数を減らす必要なく） /proc/sys/net/ipv4/tcp_wmem).

ソースノードのQEMUは、宛先ノードに存在しないページをすべてソケットに書き込み、宛先ノードで実行されているQEMUのマиграーションスレッドが動作します UFFDIO_COPY|ZEROPAGE ioctls on the userfaultfd in order to map the received pages into the guest (UFFDIO_ZEROCOPY is used if the source page was a zero page).

宛先ノードで別のポストコピースレッドがpoll()を用いてソケットを監視し、 userfaultfd 並行して動作します。ユーザーフォールトが発生した後、イベントが生成されると、ポストコピースレッドがソケットからread()を行い、 POLLIN を受信してフォールトアドレス（または userfaultfd がすでに解決されウェイクアップされた場合の -EAGAIN が実行されている並行QEMUマиграーションスレッドによって処理されます). UFFDIO_COPY|ZEROPAGE QEMUポストコピースレッド（宛先ノードで実行）がユーザーフォールトアドレスを取得すると、その欠損ページに関する情報をソケットに書き込みます。QEMUソースノードが情報を受信し、そのページアドレスに「シーク」して、その新しいページオフセットから残りの欠損ページを送信します。その後すぐに（TCP_WMEMキューをネットワーク経由でフラッシュする時間だけ）宛先ノードで実行されているQEMUのマиграーションスレッドがフォールトを引き起こしたページを受信し、通常通りマップします。

この際、ソースノードのQEMUはユーザーフォールトの発生に伴い、ライブマиграーションに関連する各ページの状態ビットマップを保持する必要がなくなり、ソースノードで実行されているQEMUが宛先ノードにまだ欠損しているページを把握するための単一のビットマップを維持します。ソースノードのビットマップを確認して、ラウンドロビン方式で送信すべき欠損ページを特定し、受信したユーザーフォールトに応じてビットマップをスキャンします。各ページを送信した後は、ビットマップを適切に更新します。また、同じページを2回送信しないようにするのも重要です（ユーザーフォールトがポストコピースレッドによって読み込まれる直前に UFFDIO_COPY|ZEROPAGE がマиграーションスレッドで実行される場合）。

ユーザーフォールトが開始する頃には、宛先ノードのQEMUはライブマиграーションに関連する各ページの状態ビットマップを保持する必要がなくなり、ソースノードで実行されているQEMUが宛先ノードにまだ欠損しているページを把握するための単一のビットマップを維持します。ソースノードのビットマップを確認して、ラウンドロビン方式で送信すべき欠損ページを特定し、受信したユーザーフォールトに応じてビットマップをスキャンします。各ページを送信した後は、ビットマップを適切に更新します。また、同じページを2回送信しないようにするのも重要です（ユーザーフォールトがポストコピースレッドによって読み込まれる直前に UFFDIO_COPY|ZEROPAGE がマиграーションスレッドで実行される場合）。

Non-cooperative userfaultfd¶

When the userfaultfd 外部のマネージャーによって監視される場合、マネージャーはプロセスの仮想メモリレイアウトの変化を追跡できる必要があります。Userfaultfdは、ページフォールト通知と同じread(2)プロトコルを使用して、このような変化をマネージャーに通知します。マネージャーは、適切なビットを設定することでこれらのイベントを明示的に有効にする必要があります。 uffdio_api.features passed to UFFDIO_API ioctl:

UFFD_FEATURE_EVENT_FORK

enable userfaultfd fork()のハンドラ。この機能が有効になると、親プロセスのコンテキストが新たに作成されたプロセスに複製されます。マネージャーは userfaultfd 新しいプロセスのファイル記述子でコンテキストを受け取ります。マネージャーは UFFD_EVENT_FORK new userfaultfd context in the uffd_msg.fork.

UFFD_FEATURE_EVENT_REMAP

mremap()呼び出しに関する通知を有効にします。非協力的なプロセスが仮想メモリ領域を別の場所に移動する場合、マネージャーは UFFD_EVENT_REMAPの部分で、 uffd_msg.remap 古いアドレスと新しいアドレス、およびその元の長さを含む通知を受け取ります。

UFFD_FEATURE_EVENT_REMOVE

madvise(MADV_REMOVE)およびmadvise(MADV_DONTNEED)呼び出しに関する通知を有効にします。これらのmadvise呼び出しでイベント UFFD_EVENT_REMOVE が生成されます。イベント uffd_msg.remove 削除された領域の開始アドレスと終了アドレスを含みます。

UFFD_FEATURE_EVENT_UNMAP

メモリのアンマッピングに関する通知を有効にします。マネージャーは UFFD_EVENT_UNMAP with uffd_msg.remove アンマッピングされた領域の開始アドレスと終了アドレスを含む情報を取得します。

Although the UFFD_FEATURE_EVENT_REMOVE および UFFD_FEATURE_EVENT_UNMAP are pretty similar, they quite differ in the action expected from the userfaultfd manager. In the former case, the virtual memory is removed, but the area is not, the area remains monitored by the userfaultfd, and if a page fault occurs in that area it will be delivered to the manager. The proper resolution for such page fault is to zeromap the faulting address. However, in the latter case, when an area is unmapped, either explicitly (with munmap() system call), or implicitly (e.g. during mremap()), the area is removed and in turn the userfaultfd context for such area disappears too and the manager will not get further userland page faults from the removed area. Still, the notification is required in order to prevent manager from using UFFDIO_COPY on the unmapped area.

Unlike userland page faults which have to be synchronous and require explicit or implicit wakeup, all the events are delivered asynchronously and the non-cooperative process resumes execution as soon as manager executes read(). The userfaultfd manager should carefully synchronize calls to UFFDIO_COPY with the events processing. To aid the synchronization, the UFFDIO_COPY ioctl will return -ENOSPC when the monitored process exits at the time of UFFDIO_COPY, and -ENOENT, when the non-cooperative process has changed its virtual memory layout simultaneously with outstanding UFFDIO_COPY operation.

The current asynchronous model of the event delivery is optimal for single threaded non-cooperative userfaultfd マネージャーの実装。後で新たな機能として同期型イベント配信モデルを追加することが可能です。 userfaultfd 非協力型マネージャーのマルチスレッド拡張を支援するための機能で、例えばイベント受信と並行してIOCTLSを実行可能にするなど、 UFFDIO_COPY シングルスレッドの実装は現在の非同期イベント配信モデルを引き続き使用する必要があります。

HugeTLB Pages¶

概要¶

このファイルの目的は、Linux カーネルにおける huge page（大容量ページ）のサポートについての簡単な概要を提供することです。このサポートは、ほとんどの現代的なアーキテクチャが提供する複数のページサイズのサポートに基づいています。たとえば、x86 CPU は通常 4K と 2M（アーキテクチャ的にサポートされている場合は 1G）のページサイズをサポートし、ia64 アーキテクチャは 4K、8K、64K、256K、1M、4M、16M、256M の複数のページサイズをサポートし、ppc64 は 4K と 16M のページサイズをサポートします。TLB（Translation Lookaside Buffer）は、仮想アドレスから物理アドレスへの変換をキャッシュするメカニズムです。通常、これはプロセッサにおいて非常に希少なリソースです。オペレーティングシステムは、限られた TLB リソースを最大限に活用しようとします。この最適化は、より大きな物理メモリ（複数ギガバイト）が簡単に利用可能になった現在、より重要となっています。

ユーザーは、Linux カーネルの huge page サポートを mmap システムコールまたは標準の SYSV シェアードメモリシステムコール（shmget、shmat）を使用して利用できます。

まず、Linux カーネルは CONFIG_HUGETLBFS（「ファイルシステム」の下にあります）と CONFIG_HUGETLB_PAGE（CONFIG_HUGETLBFS が選択されたときに自動的に選択される）のコンフィギュレーションオプションでビルドする必要があります。

以下の /proc/meminfo このファイルは、カーネルの huge page プール内の永続的な huge tlbpage の総数についての情報を提供します。また、デフォルトの huge page サイズや、デフォルトサイズの huge page プール内の空き、予約済み、余剰の huge page の数についての情報を表示します。huge page サイズは、huge page レギオンをマッピングするシステムコールの引数の適切なアライメントとサイズを生成するために必要です。

の出力には、次のようないくつかの行が含まれます: cat /proc/meminfo では、

HugePages_Total: uuu
HugePages_Free:  vvv
HugePages_Rsvd:  www
HugePages_Surp:  xxx
Hugepagesize:    yyy kB
Hugetlb:         zzz kB

where:

HugePages_Total

は huge page プールのサイズを示します。

HugePages_Free

はプール内でまだ割り当てられていない huge page の数を示します。

HugePages_Rsvd

は「予約済み」の略で、プールから割り当てることを約束しているがまだ割り当てられていない huge page の数を示します。予約済み huge page は、アプリケーションがフォールト時に huge page をプールから割り当てられるように保証します。

HugePages_Surp

は「余剰」の略で、の値を超える huge page の数を示します。最大の余剰 huge page の数は、 /proc/sys/vm/nr_hugepagesによって制御されます。 /proc/sys/vm/nr_overcommit_hugepages.

Hugepagesize

はデフォルトの hugepage サイズ（Kb 単位）を示します。

Hugetlb

はすべてのサイズの huge page によって消費されるメモリ（kB 単位）を示します。異なるサイズの huge page が使用されている場合、この数値は HugePages_Total * Hugepagesize を超えます。より詳細な情報を得るには、 /sys/kernel/mm/hugepages （以下に記載）を参照してください。

/proc/filesystems カーネルで構成された「hugetlbfs」というファイルシステムも表示されるべきです。

/proc/sys/vm/nr_hugepages これはカーネルのヒューゲページプールに現在存在する「永続的」なヒューゲページの数を示します。「永続的」なヒューゲページはタスクによって解放されるとヒューゲページプールに戻されます。root権限を持つユーザーは、値を増減することで、永続的なヒューゲページを動的に追加または解放できます。 nr_hugepages.

ヒューゲページとして使用されるページはカーネル内で予約され、他の用途には使用できません。ヒューゲページはメモリ圧力下でもスワップアウトされません。

ヒューゲページがカーネルのヒューゲページプールに事前に割り当てられると、適切な権限を持つユーザーはmmapシステムコールや共有メモリシステムコールを使用してヒューゲページを利用できます。以下の「ヒューゲページの使用」のセクションを参照してください。 ヒューゲページの使用以下の説明を参照してください。

管理者は、カーネルのブートコマンドラインで「hugepages=N」パラメータを指定することで永続的なヒューゲページを割り当てられます。ここで「N」は要求されたヒューゲページ数です。これはメモリがまだフラグメント化されていないため、ヒューゲページを割り当てる最も信頼性の高い方法です。

一部のプラットフォームでは複数のヒューゲページサイズがサポートされています。特定のサイズのヒューゲページを割り当てるには、hugepagesブートコマンドパラメータの前に「hugepagesz=<size>」というヒューゲページサイズ選択パラメータを指定する必要があります。<size>はバイト単位で指定し、[kKmMgG]などのオプションスケールサフィックスを指定できます。デフォルトのヒューゲページサイズは「default_hugepagesz=<size>」ブートパラメータで選択できます。

Hugetlbブートコマンドラインパラメータのセマンティクス

hugepagesz

ヒューゲページのサイズを指定します。hugepagesパラメータと併せて使用して、指定されたサイズのヒューゲページを事前に割り当てます。したがって、hugepageszとhugepagesは通常、ペアのように指定されます。例:「hugepagesz=2M hugepages=1024」

hugepagesz=2M hugepages=512

特定のヒューゲページサイズごとにコマンドラインでhugepageszを1回だけ指定できます。有効なヒューゲページサイズはアーキテクチャに依存します。

hugepages

事前に割り当てるヒューゲページの数を指定します。これは有効なhugepageszまたはdefault_hugepageszパラメータの後に通常指定されます。ただし、hugepagesが最初または唯一のhugetlbコマンドラインパラメータである場合、これはデフォルトサイズのヒューゲページ数を暗黙的に指定します。この場合、デフォルトサイズのhugepagesz,hugepagesパラメータペアで上書きすることはできません。

2Mのデフォルトヒューゲページサイズを持つアーキテクチャの場合:

hugepages=256 hugepagesz=2M hugepages=512

256 2M ハイパーキャッシュページが割り当てられ、hugepages=512 パラメータが無視されるという警告メッセージが表示されます。無効な hugepagesz パラメータが hugepages パラメータの前に指定されている場合、hugepages パラメータは無視されます。

default_hugepagesz

デフォルトのハイパーキャッシュページサイズを指定します。このパラメータはコマンドラインで一度だけ指定可能です。default_hugepagesz は、デフォルトサイズのハイパーキャッシュページを事前に指定された数だけ割り当てるための hugepages パラメータと組み合わせてオプションで指定可能です。また、上記の hugepages セクションで説明したように、デフォルトサイズのハイパーキャッシュページの事前割り当て数を暗黙的に指定することも可能です。したがって、2M がデフォルトのハイパーキャッシュページサイズのアーキテクチャでは、

hugepages=256
default_hugepagesz=2M hugepages=256
hugepages=256 default_hugepagesz=2M

すべて256 2M ハイパーキャッシュページが割り当てられます。有効なデフォルトのハイパーキャッシュページサイズはアーキテクチャに依存します。

複数のハイパーキャッシュページサイズがサポートされている場合、 /proc/sys/vm/nr_hugepages デフォルトサイズの事前割り当てられたハイパーキャッシュページの現在の数を示します。したがって、以下のようにコマンドを使用して、デフォルトサイズの永続的なハイパーキャッシュページを動的に割り当てたり解放したりできます。

echo 20 > /proc/sys/vm/nr_hugepages

このコマンドは、ハイパーキャッシュページプール内のデフォルトサイズのハイパーキャッシュページ数を20に調整しようとし、必要に応じてハイパーキャッシュページを割り当てたり解放したりします。

NUMA プラットフォームでは、カーネルはタスクが変更する際の NUMA メモリポリシーで指定された許可されたノードのセット全体にハイパーキャッシュページプールを分散しようとします。 nr_hugepages許可されたノードのデフォルトは、タスクがデフォルトのメモリポリシーを使用している場合、すべてのメモリを持つオンラインノードです。許可されたノードでハイパーキャッシュページに必要な連続するメモリが不足している場合、永続的なハイパーキャッシュページを割り当てる際には静かにスキップされます。詳しくは、 以下に記載の議論 を参照してください。タスクメモリポリシー、cpusets およびノードごとの属性が永続的なハイパーキャッシュページの割り当ておよび解放とどのように相互作用するかについての議論です。

ハイパーキャッシュページの割り当て成功または失敗は、割り当て試行時のシステムに存在する物理的に連続したメモリの量に依存します。カーネルが NUMA システムの一部ノードからハイパーキャッシュページを割り当てられなかった場合、十分な連続メモリを持つ他のノードから追加のページを割り当てることを試みます。

システム管理者は、このコマンドをローカルのrc初期化ファイルのいずれかに配置することを検討すべきです。これにより、カーネルが起動プロセスの初期段階で、物理的に連続するページを取得する可能性が非常に高い状態でヒープページを早期に割り当てることができます。管理者は、sysctlまたはmeminfoを確認することで、実際に割り当てられたヒープページの数を検証できます。NUMAシステムにおいてヒープページのノードごとの分布を確認するには、以下のコマンドを使用してください。

cat /sys/devices/system/node/node*/meminfo | fgrep Huge

/proc/sys/vm/nr_overcommit_hugepages が、アプリケーションが要求するヒープページよりも多い場合、ヒープページプールがどの程度拡張できるかを指定します。 /proc/sys/vm/nr_hugepages を設定することで、ヒープページプールがその数の「余剰」ヒープページを取得できるようになります。これらの余剰ヒープページが使用されなくなった場合、それらはカーネルの通常のページプールに戻されます。

を介してヒープページプールのサイズを増やす場合、既存の余剰ページはまず永続的なヒープページに昇格します。その後、必要かつ可能であれば、新しい永続的なヒープページプールサイズを満たすために追加のヒープページが割り当てられます。 nr_hugepagesを設定することで、デフォルトのヒープページサイズの永続的なヒープページプールを縮小できます。カーネルは、タスクが変更するメモリポリシーのメモリノード全体でヒープページの解放をバランスを取ろうとします。

をより小さな値に設定することで、管理者はデフォルトのヒープページサイズの永続的なヒープページプールを縮小できます。カーネルは、タスクが変更するメモリポリシーのメモリノード全体でヒープページの解放をバランスを取ろうとします。 nr_hugepages 選択されたノード上のすべての解放可能なヒープページが、カーネルの通常のページプールに戻されます。 nr_hugepages注意：を介して永続的なヒープページプールを縮小すると、使用中のヒープページのバランスが余剰ヒープページに変換されます。これは、余剰ページの数がオーバーコミット値を超過しても発生します。この条件が成立している間、つまりが十分に増加するまで、または余剰ヒープページが使用されなくなって解放されるまで、新たな余剰ヒープページの割り当ては許可されません。

タスクメモリポリシーとヒープページの割り当て・解放の相互作用¶

huge pages are allocated and freed via the /proc interface or the /sysfs interface using the nr_hugepages_mempolicy attribute, the NUMA nodes from which huge pages are allocated or freed are controlled by the NUMA memory policy of the task that modifies the nr_hugepages_mempolicy sysctl or attribute. When the nr_hugepages attribute is used, mempolicy is ignored.

The recommended method to allocate or free huge pages to/from the kernel huge page pool, using the nr_hugepages example above, is:

numactl --interleave <node-list> echo 20 \
                            >/proc/sys/vm/nr_hugepages_mempolicy

or, more succinctly:

numactl -m <node-list> echo 20 >/proc/sys/vm/nr_hugepages_mempolicy

This will allocate or free abs(20 - nr_hugepages) to or from the nodes specified in <node-list>, depending on whether number of persistent huge pages is initially less than or greater than 20, respectively. No huge pages will be allocated nor freed on any node not included in the specified <node-list>.

When adjusting the persistent hugepage count via nr_hugepages_mempolicy, any memory policy mode–bind, preferred, local or interleave–may be used. The resulting effect on persistent huge page allocation is as follows:

  1. Regardless of mempolicy mode [see NUMA Memory Policy], persistent huge pages will be distributed across the node or nodes specified in the mempolicy as if “interleave” had been specified. However, if a node in the policy does not contain sufficient contiguous memory for a huge page, the allocation will not “fallback” to the nearest neighbor node with sufficient contiguous memory. To do this would cause undesirable imbalance in the distribution of the huge page pool, or possibly, allocation of persistent huge pages on nodes not allowed by the task’s memory policy.

  2. One or more nodes may be specified with the bind or interleave policy. If more than one node is specified with the preferred policy, only the lowest numeric id will be used. Local policy will select the node where the task is running at the time the nodes_allowed mask is constructed. For local policy to be deterministic, the task must be bound to a cpu or cpus in a single node. Otherwise, the task could be migrated to some other node at any time after launch and the resulting node will be indeterminate. Thus, local policy is not very useful for this purpose. Any of the other mempolicy modes may be used to specify a single node.

  3. 許可されるノードマスクは、タスクのメモリポリシー（mempolicy）から導出されます。このポリシーは、タスク自体またはその先祖（例えばnumactl）によって明示的に設定されたものであってもかまいません。これは、タスクが非デフォルトのポリシーでシェルから呼び出された場合、そのポリシーが使用されることを意味します。システム内のすべてのノードまたはcpuset全体にインターリーブを実行するには、numactl –interleaveまたは–membind [-m]でノードリストを「all」に指定します。

  4. numactlなどを使って指定されたタスクメモリポリシーは、タスクが実行されるcpusetのリソース制限に制約されます。したがって、cpuset内のノードがシステムノードのサブセットであるタスクが、cpuset外でヒューゲページを割り当てることはできず、まずすべての希望ノードを含むcpusetに移動する必要があります。

  5. ブート時のヒューゲページ割り当ては、オンラインのメモリを持つすべてのノードに要求されたヒューゲページ数を分散します。

各NUMAノードのヒューゲページ属性¶

sysfsで説明したルートヒューゲページ制御ディレクトリの一部のコンテンツは、メモリを持つ各NUMAノードのシステムデバイスごとに以下のように複製されます：

/sys/devices/system/node/node[0-9]*/hugepages/

このディレクトリ内では、サポートされている各ヒューゲページサイズごとのサブディレクトリが含まれており、以下の属性ファイルがあります：

nr_hugepages
free_hugepages
surplus_hugepages

free_’とsurplus_’属性ファイルは読み取り専用です。これらは、親ノードのフリーや過剰割り当て（overcommitted）されたヒューゲページの数をそれぞれ返します。

以下の nr_hugepages attributeは指定されたノードのヒューゲページ総数を返します。この属性に書き込むと、十分なリソースがある場合、タスクのmempolicyやcpuset制約に関係なく、親ノードの永続的なヒューゲページ数を指定値に調整します。

過剰割り当ておよび予約ページの数はグローバルな量です。これは、フォールト発生時にタスクのmempolicyが適用され、どのノードからヒューゲページ割り当てが試行されるかが判明するまで、事前に判明しないためです。

ヒューゲページの使用¶

ユーザーのアプリケーションがmmapシステムコールを使ってヒューゲページを要求する場合、システム管理者がhugetlbfsタイプのファイルシステムをマウントする必要があります：

mount -t hugetlbfs \
      -o uid=<value>,gid=<value>,mode=<value>,pagesize=<value>,size=<value>,\
      min_size=<value>,nr_inodes=<value> none /mnt/huge

このコマンドは、ディレクトリにhugetlbfs（擬似）ファイルシステムをマウントします /mnt/huge。このディレクトリに作成されるすべてのファイルは /mnt/huge ヒューゲページを使用します。

以下の uid および gid optionsはファイルシステムのルートの所有者とグループを設定します。デフォルトでは、 uid および gid 現在のプロセスの所有者とグループが使用されます。

以下の mode optionはファイルシステムのルートのモードを値& 01777に設定します。この値はoctal（8進数）で指定されます。デフォルトでは0755が選択されます。

プラットフォームが複数のヒューゲページサイズをサポートする場合、 pagesize オプションは、ヒューゲページのサイズと関連するプールを指定するために使用できます。 pagesize 指定値はバイト単位で指定されます。もし pagesize 指定されない場合、プラットフォームのデフォルトのヒューゲページサイズと関連するプールが使用されます。

以下の size オプションは、そのファイルシステムに許可されるメモリ（ヒューゲページ）の最大値を設定します（/mnt/huge）。この size オプションは、バイト単位で指定するか、指定されたヒューゲページプールの百分率として指定できます（nr_hugepages）。サイズはHPAGE_SIZE境界に四捨五入されます。

以下の min_size オプションは、ファイルシステムに許可されるメモリ（ヒューゲページ）の最小値を設定します。 min_size は、同様に sizeと同じ方法で指定できます（バイト単位またはヒューゲページプールの百分率）。マウント時に、 min_size で指定されたヒューゲページ数はファイルシステムによって予約されます。十分な空きヒューゲページがなければマウントは失敗します。ヒューゲページがファイルシステムに割り当てられたり解放されたりするたびに、予約数は調整され、割り当てられたヒューゲページと予約されたヒューゲページの合計が常に少なくとも min_size.

の値を保つようにします。 nr_inodes オプションは、 /mnt/huge が使用できるインODEの最大数を設定します。

もし size, min_size または nr_inodes オプションがコマンドラインに指定されていない場合、制限は設定されません。

For pagesize, size, min_size および nr_inodes オプションでは、[G|g]/[M|m]/[K|k]を使用してギガ/メガ/キロを表すことができます。たとえば、size=2Kはsize=2048と同じ意味を持ちます。

hugetlbファイルシステムに配置されたファイルに対して読み取りシステムコールはサポートされていますが、書き込みシステムコールはサポートされていません。

通常のchown、chgrp、chmodコマンド（適切な権限を持つ場合）は、hugetlbfsのファイル属性を変更するために使用できます。

また、アプリケーションがshmat/shmgetシステムコールまたはmmapとMAP_HUGETLBを使用する場合、マウントコマンドは必要ありません。mmapとMAP_HUGETLBを使用する方法の例については map_hugetlb も参照してください。

を参照してください。hugetlbメモリを共有メモリセグメント経由で使用するユーザーは補助グループに所属する必要があります。システム管理者はそのgidを /proc/sys/vm/hugetlb_shm_groupに設定する必要があります。同じまたは異なるアプリケーションがmmapとshm*コールの組み合わせを使用する場合もありますが、MAP_HUGETLBを指定せずにmmapコールを使用するにはファイルシステムのマウントが必要です。

ヒューゲページでバックアップされたメモリを操作するシステムコールは、プロセッサのネイティブページサイズに合わせて長さが調整されます。通常、EINVALエラーが設定されたり、長さがヒューゲページに合わせていない場合、ヒューゲページが無視されます。たとえば、munmap(2)は、ヒューゲページでバックアップされたメモリで長さがヒューゲページサイズより小さい場合に失敗します。

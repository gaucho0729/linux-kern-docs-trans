Spectre サイドチャネル¶

Spectre は、現代のCPUにおけるブランチ予測とスペクティブ実行を悪用してメモリを読み出し、アクセス制御を迂回する可能性のあるサイドチャネル攻撃の一種です。スペクティブ実行のサイドチャネル攻撃はメモリを変更しませんが、メモリ内の特権データを推測する試みを行います。

このドキュメントでは Spectre バリアント1 と Spectre バリアント2 を取り扱います。

影響を受けるプロセッサ¶

スペクティブ実行のサイドチャネル手法は、ほとんどの現代の高性能プロセッサに影響を及ぼします。これは、現代の高速プロセッサがブランチ予測とスペクティブ実行を採用しているためです。

以下のCPUは脆弱性があります：

  • Intel Core、Atom、Pentium、および Xeon プロセッサ

  • AMD Phenom、EPYC、および Zen プロセッサ

  • IBM POWER および zSeries プロセッサ

  • 高機能 ARM プロセッサ

  • Apple CPU

  • 高機能 MIPS CPU

  • おそらく他のほとんどの高性能CPUも影響を受けます。詳細についてはCPUベンダーにご確認ください。

プロセッサが影響を受けるかどうかは、sysfs にある Spectre ベリケーションファイルから確認できます。参照： Spectre システム情報.

問題¶

プロセッサはスペクティブ操作を用いてパフォーマンスを向上させます。これにより、プロセッサのキャッシュ、バッファ、ブランチ予測器にメモリアクセスや計算の痕跡が残ることがあります。悪意のあるソフトウェアはスペクティブ実行パスを操作し、その後、CPUのキャッシュやバッファにおけるスペクティブ実行の副作用を活用して特権データを推測する可能性があります。

Spectre バリアント1は条件分岐のスペクティブ実行を悪用し、Spectre バリアント2は間接分岐のスペクティブ実行を悪用して特権メモリを漏らします。参照： [1] [5] [6] [7] [10] [11].

Spectre バリアント1 (境界チェックバイパス)¶

境界チェックバイパス攻撃 [2] メモリアクセスの境界チェック（例：配列のインデックスが有効な範囲内かを確認する）に使用される条件分岐命令を迂回するスペクティブ実行を悪用します。これにより、検証チェックが解決する前に無効なメモリ（オーバーフローインデックス）へのアクセスがスペクティブで行われ、このようなスペクティブメモリアクセスは副作用を残し、サイドチャネルを形成して攻撃者に情報漏洩を引き起こします。

Spectre バリアント1の攻撃にはネットワーク経由でのデータ読み出しの拡張もあります。参照： [12]しかし、このような攻撃は困難で、低帯域幅、脆弱性があり、低リスクとみなされています。

注意してください。"Bounds Check Bypass"という名前にもかかわらず、Spectre バリアント1はユーザー制御の配列境界チェックに限定されません。任意の条件チェックにも影響を及ぼす可能性があります。カーネルエントリーコードの割り込み、例外、NMIハンドラはすべて条件付きswapgsチェックを含んでおり、Spectre v1の文脈では問題になる可能性があります。なぜなら、カーネルコードがユーザーGSとして推測的に実行される可能性があるからです。

Spectre バリアント2（ブランチターゲットインジェクション）¶

ブランチターゲットインジェクション攻撃は、間接ブランチの推測実行を悪用します。 [3]間接ブランチ予測子は、プロセッサ内で間接ブランチのターゲットを推測するために使用され、攻撃者によって影響を受ける可能性があります。これにより、ゲッジコードが推測的に実行され、被害者のメモリに触れた機密データが漏洩する可能性があります。推測実行中にCPUのキャッシュに残る副作用は、データ値を推測するために測定できます。

Spectre バリアント2の攻撃では、攻撃者は、CPUのブランチターゲットバッファを毒化して、被害者のブランチターゲットをゲッジコードに誘導できます。この毒化は、攻撃者が間接ブランチのアドレスオフセットを制御できるようにして、既存のコードに間接ブランチを実行することで実現できます。影響を受けたハードウェアのブランチ予測は、アドレスとオフセットを完全に区別せず、オフセットを予測に使用するため、特権コードの間接ブランチが同じオフセットを持つゲッジコードにジャンプする可能性があります。

最も有用なゲッジコードは、攻撃者が制御可能な入力パラメータ（レジスタ値など）を受け取るよう設計されており、メモリ読み込みを制御できます。入力パラメータを持たないゲッジコードも可能ですが、攻撃者は読み込むメモリの制御が極めて限られ、攻撃が有用なデータを漏らすリスクが低下します。

バリアント2の他の攻撃ベクトルとして、攻撃者がリターンスタックバッファ（RSB）を毒化する方法があります。 [13] リターンスタックバッファを毒化して、推測的なサブルーチンリターン命令実行をゲッジコードに誘導します。攻撃者の不均衡なサブルーチン呼び出し命令は、リターンスタックバッファのエントリを「毒化」し、後に被害者のサブルーチンリターン命令によって消費されます。この攻撃は、コンテキストスイッチまたは仮想マシン（VM）のエクスイット時にリターンスタックバッファをフラッシュすることで緩和できます。

同時多重スレッド（SMT）を搭載したシステムでは、ハードウェアスレッド間でレベル1キャッシュとブランチターゲットバッファ（BTB）が共有されるため、スレッドの兄弟スレッドから攻撃が可能である。兄弟スレッド上で実行されている悪意のあるプログラムは、ペアのBTBを操作して間接ブランチの推測実行をジェッタコードに誘導し、レベル1キャッシュに残る推測実行の副作用を測定して被害者のデータを推測することができる。

また、ブランチヒストリバッファ（BHB）を毒化して、間接ブランチを特定のブランチターゲットバッファ（BTB）エントリに推測的に誘導するという別の攻撃ベクトルも存在する。この場合、エントリが間接ブランチのソースアドレスと関連付けられていないとしても、BHBは強化されたIBRSの存在下でも権限レベルを超えて共有される可能性がある。

現時点で確認されている唯一の現実的なBHB攻撃ベクトルは、非特権eBPFを介したものである。したがって、非特権eBPFを有効にしないことを強く推奨する（特にeIBRSを使用する場合、リトポリーンを用いない場合）。BHB攻撃に対する完全な対策として、リトポリーン（またはeIBRSとリトポリーンの組み合わせ）を使用することを推奨する。

攻撃シナリオ¶

以下の攻撃シナリオは想定されているが、すべての可能な攻撃ベクトルを網羅しているとは限りません。

1. ユーザープロセスがカーネルを攻撃する¶

Spectre バリアント1¶

攻撃者は、システムコール中にレジスタまたはメモリ内の特定アドレスを介してカーネルにパラメータを渡す。このパラメータは、後でカーネルが配列のインデックスとして使用するか、スペクターベリアント1攻撃のためにポインタを生成するために使用される可能性がある。インデックスまたはポインタは無効だが、推測実行のためのコードブランチではバウンドチェックが回避される。これにより、特権メモリへのアクセスと漏洩が発生する可能性がある。

スペクターベリアント1攻撃でデータポインタが影響を受ける可能性のあるカーネルコードでは、新しい「nospec」アクセッサマクロが使用され、推測的なデータの読み込みを防ぐ。

Spectre バリアント1 (swapgs)¶

攻撃者は、割り込みまたは例外のswapgsパスを推測的にスキップさせるようにブランチ予測器をトレーニングすることができる。攻撃者がGSレジスタをユーザー空間の値に初期化した場合、swapgsが推測的にスキップされると、推測実行ウィンドウ内のGS関連のpercpuアクセスは攻撃者が制御するGS値で行われる。これにより、特権メモリへのアクセスと漏洩が発生する可能性がある。

例:

if (coming from user space)
    swapgs
mov %gs:<percpu_offset>, %reg
mov (%reg), %reg1

ユーザー空間から来た場合、CPUは推測的にswapgsをスキップし、ユーザーGS値を使用して推測的なpercpu読み込みを行うことができます。これにより、ユーザーは推測的に任意のカーネル値の読み出しを強制できます。もし、percpu値を別のロード/ストア命令のアドレスとして使用するようなガジェットが存在する場合、カーネル値の内容はL1サイドチャネル攻撃を通じて見えてしまう可能性があります。

カーネル空間から来た場合でも同様の攻撃が可能です。CPUは推測的にswapgsを行い、その結果、ユーザーGSが推測的なウィンドウの残りの期間にわたって使用されるようになります。

Spectre バリアント2¶

Spectre バリアント2の攻撃者は poison システムコールを発行する前にブランチターゲットバッファ(BTB)を毒化して攻撃を開始します。カーネルに移行した後、カーネルは間接ジャンプ時に毒化されたブランチターゲットバッファを使用し、スペキュラティブ実行中にジェッタコードにジャンプします。

攻撃者がスペキュラティブ実行中にリークされたメモリアドレスを制御しようとする場合、レジスタやメモリ内の既知のアドレスを通じてジェッタにパラメータを渡す必要があります。ジェッタが実行された後、副作用を測定できます。

カーネルはリターントランポリン（retpoline）を使用して、毒化されたブランチターゲットバッファエントリを消費されることを防ぐことができます。 [3] [9] すべての間接ブランチに対して適用されます。リターントランポリンは、推測実行中にジャンプしてガジェットコードに到達するのを防ぐため、推測実行パスをトラップします。x86 CPUでハードウェアにEnhanced Indirect Branch Restricted Speculation（Enhanced IBRS）が搭載されている場合、Spectre バリアント2の緩和にEnhanced IBRSを使用すべきです。retpolineよりも効率的です。

ファームウェアにガジェットコードが存在する可能性があり、rogueユーザー・プロセスによってSpectre バリアント2攻撃で悪用される可能性があります。x86でのこのような攻撃を緩和するため、カーネルがファームウェアコードを呼び出す前に、Indirect Branch Restricted Speculation（IBRS）機能を有効化します。

2. ユーザー・プロセスが別のユーザー・プロセスを攻撃する場合¶

悪意のあるユーザー・プロセスは、同じハードウェアスレッド上のコンテキストスイッチを通じて、または同時多線程（SMT）システムで物理プロセッサコアを共有するスレッド（シblings）から、別のユーザー・プロセスを攻撃する試みを行うことができます。

Spectre バリアント1の攻撃は、プロセス間でパラメータを渡す必要があり、データのやり取り関係が必要です（例：リモートプロシージャ呼び出し（RPC））。これらのパラメータは、ガジェットコードによって攻撃対象プロセスのプライベートメモリにアクセスする無効なデータポインタを導出するために使用されます。

Spectre バリアント2の攻撃は、rogueプロセスから以下の方法で実行できます poisoning ブランチターゲットバッファ。これは、後述の被害プロセスが同じハードウェアスレッドで後続して実行されるか、同じ物理コアを共有するサブスレッドで並行して実行される場合、間接ブランチターゲットに影響を与える。

ユーザープロセスは、prctl()システムコールを使用して自身の間接ブランチ推測を無効化することで、Spectre変異種2の攻撃から自己を保護できます。管理者は、不安全なプロセスがブランチターゲットバッファを汚染するのを防ぐために、プロセスの間接ブランチ推測を無効化することもできます。ただし、間接ブランチ推測を使用しないことで生じるパフォーマンスのコストと、ブランチターゲットバッファのクリアに伴うコストが発生します。x86でSMTが有効になっている場合、間接ブランチ推測が無効なプロセスでは、シングルスレッドの間接ブランチ予測子（STIBP）が有効化され、サブスレッドがブランチターゲットバッファを制御するのを防ぎます。 [4] さらに、コンテキストスイッチ時にそのプロセスへの移行時にインデックスブランチ予測バリア（IBPB）が発行され、ブランチターゲットバッファがクリアされます。

x8,6ではコンテキストスイッチ時にリターンスタックバッファが埋め込まれます。これにより、リターンスタックバッファが不足しているときにブランチターゲットバッファがブランチ予測に使用されなくなります。以前のプロセスが残したリターンスタックバッファ内の汚染されたエントリも同時にクリアされます。

ユーザーのプログラムはアドレス空間ランダム化を使用して攻撃を困難にすべきです（/proc/sys/kernel/randomize_va_space = 1または2に設定）。

3. バーチャライズされたゲストがホストを攻撃する場合¶

攻撃メカニズムはユーザープロセスがカーネルを攻撃する方法と同様です。カーネルはハイパーコールやその他のバーチャライゼーションエクスポート経路を通じて進入します。

Spectre変異種1の攻撃では、rogueゲストはハイパーコールを通じてレジスタなどにパラメータを渡して、カーネルに入った後に特権メモリを speculate するための無効なポインタを取得できます。このようなカーネルコードが特定された場合、nospecアクセッサマクロが使用され、スペキュレートされたメモリアクセスを停止します。

Spectre変異種2の攻撃では、rogueゲストは poison ブランチターゲットバッファまたはリターンスタックバッファに影響を与え、カーネルがスペキュレート実行パス内の gadget コードにジャンプするようにします。

変異種2を緩和するため、ホストカーネルは間接ブランチ用のリターントランポリンを使用して汚染されたブランチターゲットバッファを回避し、VMエクスポート時にリターンスタックバッファをフラッシュします。これにより、rogueゲストがホストカーネル内の間接ブランチを影響を与えるのを防ぎます。

不正なゲストからのホストプロセスの保護のために、ホストプロセスはprctl()を介して間接ブランチ推測を無効化できます。このようなプロセスへのコンテキストスイッチ時には、ブランチターゲットバッファがクリアされます。

4. 虚擬化されたゲストが他のゲストを攻撃するケース¶

不正なゲストは、他のゲストがアクセス可能なデータを取得するために別のゲストを攻撃することがあります。

ゲスト間でパラメータがやり取り可能であれば、Spectreの変異種1型攻撃が可能です。これは共有メモリやメッセージ送信などのメカニズムを通じて行われる可能性があります。このようなパラメータは、ゲスト内の特権データへのデータポインタを導出するために使用され、被害者の推測経路に存在するゲートウェイコードによって特権データがアクセスされる可能性があります。

Spectreの変異種2型攻撃は、不正なゲストから以下の手段を介して実行できます。 poisoning ブランチターゲットバッファまたはリターンスタックバッファを介して。このような毒入りエントリは、被害ゲストの推測実行経路を操作するために利用される可能性があります。

Linuxカーネルは、同じCPUハードウェアスレッド上で実行されている他のゲストへの攻撃を緩和するために、仮想マシンの終了時にリターンスタックバッファをフラッシュし、新しいゲストに切り替える前にブランチターゲットバッファをクリアします。

SMTが使用されている場合、スレッドの兄弟ホストで実行されている信頼できないゲストからのSpectre変異種2型攻撃は、管理者がprctl()を介して不安全なゲストの間接ブランチ推測を無効化することで緩和できます。ゲスト自身も、マイクロコードベースの緩和策（例: x86におけるIBPBまたはSTIBP）をゲスト内で有効化することで保護できます。

Spectre システム情報¶

Linuxカーネルは、Spectreに対する現在の緩和状態をシステム全体で確認するためのsysfsインターフェースを提供しています。システムが脆弱かどうか、およびどの緩和策が有効かを表示します。

Spectre変異種1型の緩和状態を示すsysfsファイルは:

/sys/devices/system/cpu/vulnerabilities/spectre_v1

このファイルの可能な値は次の通りです。

「影響を受けない」

プロセッサは脆弱ではありません。

「脆弱: __userポインタの衛生処理とユーザーコピーバリアンスのみ；swapgsバリアンスなし」

swapgsの保護は無効化されています。それ以外の場合は、ケースバイケースでカーネルが保護を実施しており、明示的なポインタの衛生処理とユーザーコピーLFENCEバリアンスで保護されています。

「緩和: ユーザーコピー/swapgsバリアンスと__userポインタの衛生処理」

ケースバイケースでカーネルが保護を実施しており、明示的なポインタの衛生処理、ユーザーコピーLFENCEバリアンス、swapgs LFENCEバリアンスで保護されています。

ただし、保護はケースバイケースで実施されており、Spectre変異種1型のすべての可能な攻撃ベクトルがカバーされる保証はありません。

spectre_v2 カーネルファイルは、カーネルが retpoline の緩和策でコンパイルされているか、CPU がハードウェアでの緩和策をサポートしているかを報告します。また、CPU が追加のプロセス固有の緩和策をサポートしているかどうかも報告します。

このファイルは、マイクロコードによって有効化された CPU の機能を報告します。この機能はユーザープロセス間の攻撃を緩和するために使用されます：

  1. 間接ブランチ予測バリアンス (IBPB) は、異なるユーザーのプロセス間の隔離を追加します。

  2. 単一スレッド間接ブランチ予測子 (STIBP) は、同じコア上で実行される CPU スレッド間の隔離を追加します。

これらの CPU 機能は使用時にパフォーマンスに影響を与える可能性があり、個別にプロセスごとに有効化できます。

Spectre バリアント 2 の緩和策状態を表示する sysfs ファイルは以下の通りです：

/sys/devices/system/cpu/vulnerabilities/spectre_v2

このファイルの可能な値は次の通りです。

  • カーネル状態：

「影響を受けない」

プロセッサは脆弱性がありません

「緩和策：なし」

脆弱、緩和策なし

「緩和策：Retpoline」

Retpoline チューンを使用

「緩和策：LFENCE」

LFENCE 指令を使用

「緩和策：強化 IBRS」

ハードウェアに焦点を当てた緩和策

「緩和策：強化 IBRS + Retpoline」

ハードウェアに焦点を当てた + Retpoline

「緩和策：強化 IBRS + LFENCE」

ハードウェアに焦点を当てた + LFENCE

  • ファームウェア状態：x86 でのみ、ファームウェア呼び出し時に間接ブランチ制限スペキュレーション (IBRS) を使用して Spectre バリアント 2 攻撃を保護するかどうかを表示します。

「IBRS_FW」

ファームウェア呼び出し時のユーザープログラム攻撃に対する保護

  • 異なるユーザーのプロセス間の保護における間接ブランチ予測バリアンス (IBPB) 状態。この機能は prctl() でプロセスごとに制御可能で、カーネルコマンドラインオプションでも制御可能です。これは x86 でのみ使用可能な機能です。詳細については下記を参照してください。

「IBPB: 無効」

IBPB は使用されません

「IBPB: 常時有効」

すべてのタスクで IBPB を使用

「IBPB: 条件付き」

SECCOMP または間接ブランチ制限タスクで IBPB を使用

  • 異なるハイパースレッド間の保護における単一スレッド間接ブランチ予測 (STIBP) 状態。この機能は prctl でプロセスごとに制御可能で、カーネルコマンドラインオプションでも制御可能です。これは x86 でのみ使用可能な機能です。詳細については下記を参照してください。

「STIBP: 無効」

STIBP は使用されません

「STIBP: 強制」

すべてのタスクで STIBP を使用

「STIBP: 条件付き」

SECCOMP または間接ブランチ制限タスクで STIBP を使用

  • リターンスタックバッファ (RSB) 保護状態：

「RSB 塗りつぶし」

コンテキストスイッチ時に RSB の保護が有効化されています

完全な緩和にはCPUベンダーからのマイクロコードの更新が必要かもしれません。必要なマイクロコードが利用できない場合、カーネルは脆弱性を報告します。

Spectreバリアント1およびバリアント2の緩和措置を有効にする¶

1. カーネルの緩和措置¶

Spectre バリアント1¶

Spectreバリアント1では、脆弱なカーネルコード（コードの監査やスキャンツールによって判定）は、個別にケースごとにnospecアクセッサマクロを使用して境界のクリッピングを行うように注釈付けされます。 [2] これにより、利用可能なディスクロージャーのギアを回避します。ただし、Spectreバリアント1のすべての攻撃ベクトルをカバーするとは限りません。

コピーからユーザーのコードはLFENCEバリアーを使用して、 access_ok() チェックが誤って推測されるのを防ぎます。このバリアーはbarrier_nospec()マクロによって実行されます。

Spectreバリアント1のswapgsバリアントでは、割り込み、例外、NMIエントリで必要な場所にLFENCEバリアーが追加されます。これらのバリアーはFENCE_SWAPGS_KERNEL_ENTRYおよびFENCE_SWAPGS_USER_ENTRYマクロによって実行されます。

Spectre バリアント2¶

Spectreバリアント2の緩和措置では、コンパイラがカーネル内の間接ジャンプやコールを同等のリタポリーン（retpoline）に変換します。 [3] [9] ターゲットアドレスに移動します。リタポリーンの下でのスペキュラティブ実行パスは無限ループにトラップされ、スペキュラティブ実行がギアにジャンプするのを防ぎます。

脆弱なCPUでリタポリーンの緩和措置を有効にするには、カーネルをgccコンパイラでコンパイルし、-mindirect-branch=thunk-externおよび-mindirect-branch-registerオプションをサポートする必要があります。カーネルがClangコンパイラでコンパイルされている場合、コンパイラが-mretpoline-external-thunkオプションをサポートする必要があります。カーネル構成(CONFIG_RETPOLINE)を有効にし、CPUが最新のマイクロコードで実行されている必要があります。

Intel Skylake世代のシステムでは、緩和措置はほとんどのケースをカバーしますが、すべてではありません。参照 [3] 詳細についてはこちら。

Spectreバリアント2のハードウェア緩和を備えたCPU（例：x86のEnhanced IBRS）では、リタポリーンは実行時に自動的に無効になります。

リタポリーンの緩和措置は脆弱なCPUではデフォルトで有効です。管理者はカーネルコマンドラインおよびsysfs制御ファイルを通じて強制的に有効または無効にできます。参照 カーネルコマンドラインでの緩和制御.

x86では、ファームウェアコードを呼び出す前に間接ブランチ制限推測をデフォルトで有効にし、ファームウェアを用いたSpectreバリアント2の侵害を防ぎます。

カーネルアドレス空間ランダム化（カーネル構成のCONFIG_RANDOMIZE_BASE=yおよびCONFIG_SLAB_FREELIST_RANDOM=y）は、カーネルへの攻撃を一般的に困難にします。

2. ユーザープログラムの緩和措置¶

ユーザープログラムはLFENCEまたは「境界のクリッピング」を使用してSpectreバリアント1を緩和できます。詳細は参照 [2].

Spectreバリアント2の緩和策として、個々のユーザーのプログラムは間接ブランチ用のリターントランポリンでコンパイルできます。これにより、悪意のあるソフトウェアがブランチターゲットバッファに残した毒エントリを消費するのを防ぐことができます。代替案として、プログラムはprctl()を用いて間接ブランチのスペキュレーションを無効化することもできます（参照 Speculation Control）。x86では、ユーザーのプログラムが実行中にスレッドの兄弟スレッドからの攻撃を防ぐためにSTIBPを有効にし、プログラムの切り替え時にIBPBでブランチターゲットバッファをクリアします。

ユーザーのプログラムにおける間接ブランチのスペキュレーションを制限することで、x86においてプログラムがバリアント2の攻撃を実行することも防げます。すべてのサンドボックス化されたSECCOMPプログラムはデフォルトで間接ブランチのスペキュレーションを制限しています。管理者はカーネルコマンドラインおよびsysfs制御ファイルを介してこの挙動を変更できます。参照 カーネルコマンドラインでの緩和制御.

間接ブランチのスペキュレーションを無効にしたプログラムは、より多くのオーバーヘッドが発生し、実行速度が遅くなります。

ユーザーのプログラムはアドレス空間ランダム化（/proc/sys/kernel/randomize_va_space = 1または2）を有効にして、攻撃を困難にする必要があります。

3. VMの緩和策¶

カーネル内で、rogueゲストからのSpectreバリアント1の攻撃は、VMエクスイットパスごとに個別に緩和されます。脆弱なコードは「境界クリッピング」に「nospecアクセッサマクロ」を使用し、情報漏洩のツールを回避します。ただし、これはすべてのバリアント1の攻撃ベクトルをカバーするとは限りません。

rogueゲストからのSpectreバリアント2の攻撃に対して、LinuxカーネルはretpolineまたはEnhanced IBRSを使用して、rogueゲストが残した毒エントリをブランチターゲットバッファに消費させないようにします。また、すべてのVMエクスイット時にリターンスタックバッファをクリアして、リターンスタックバッファのアンダーフローを防ぎ、毒されたブランチターゲットバッファが使用されるのを防ぎます。

同じCPUハードウェアスレッド内のゲスト間の攻撃を緩和するため、CPUに新しいゲストに切り替える前にブランチターゲットバッファをクリアしてクリーン化します。

上記の緩和策は、脆弱なCPUではデフォルトで有効になっています。

SMTを使用する場合、スレッドの兄弟スレッドからのゲスト間攻撃を緩和するため、管理者が兄弟スレッドで実行中の信頼されていないゲストの間接ブランチスペキュレーションをprctl()で無効化できます。

カーネルは、ゲストが選択したマイクロコードベースの緩和策（例:x86におけるIBPBまたはSTIBP）を用いて自身を保護できるようにします。

カーネルコマンドラインでの緩和制御¶

Spectreバリアント2の緩和策はカーネルコマンドラインで無効化したり、強制的に有効にしたりできます。

nospectre_v1

[X86,PPC] Spectre Variant 1 (bounds check bypass)の緩和策を無効にする。このオプションでシステム内でのデータ漏洩が発生する可能性があります。

nospectre_v2

[X86] Spectre variant 2 (indirect branch prediction)の脆弱性に対するすべての緩和策を無効にする。このオプションでシステムがデータ漏洩を許す可能性があり、spectre_v2=offと同等です。

spectre_v2=

[X86] Spectre variant 2 (indirect branch speculation)の脆弱性に対する緩和策を制御します。デフォルトではカーネルがユーザー空間からの攻撃を防ぎます。

on

無条件で有効にする、spectre_v2_user=onを強制します

off

無条件で無効にする、spectre_v2_user=offを強制します

auto

カーネルがCPUモデルが脆弱かどうかを検出します

「on」を選択すると、CPU、利用可能なマイクロコード、CONFIG_RETPOLINE設定オプション、カーネルが構築されたコンパイラに基づいて実行時に緩和策を選択します。「auto」を選択すると、ユーザー空間からユーザー空間タスクへの攻撃に対する緩和策も選択される可能性があります。

「on」を選択すると、ユーザー空間からユーザー空間タスクへの攻撃に対する緩和策も有効になります。

「off」を選択すると、カーネルとユーザー空間の保護をすべて無効にします。

特定の緩和策を手動で選択することもできます:

retpoline ジェネリック、lfence retpoline、ジェネリック Retpolines retpoline,lfence LFENCE; 間接ブランチ retpoline,amd retpoline,lfence eibrs 増強IBRS eibrs,retpoline 増強IBRS + Retpolines eibrs,lfence 増強IBRS + LFENCE

このオプションを指定しない場合は、spectre_v2=autoと同等です。

ユーザー空間の緩和策:

spectre_v2_user=

[X86] ユーザー空間タスク間でのSpectre variant 2 (indirect branch speculation)の脆弱性に対する緩和策を制御します

on

無条件で緩和策を有効にする。spectre_v2=onによって強制されます

off

無条件で緩和策を無効にする。spectre_v2=offによって強制されます

prctl

間接ブランチ予測は有効ですが、スレッドごとにprctlで緩和策を有効にすることができます。緩和策の制御状態はフォーク時に継承されます。

prctl,ibpb

上記の「prctl」と同様ですが、スレッドごとにのみSTIBPを制御します。異なるユーザー空間プロセス間で切り替える際には常にIBPBを実行します。

seccomp

上記の「prctl」と同様ですが、すべてのseccompスレッドが緩和策を有効にします（明示的に除外しない限り）。

seccomp,ibpb

上記の「seccomp」と同様ですが、スレッドごとにのみSTIBPを制御します。異なるユーザー空間プロセス間で切り替える際には常にIBPBを実行します。

auto

カーネルは利用可能なCPU機能と脆弱性に基づいて緩和策を選択します。

デフォルトの緩和策: CONFIG_SECCOMP=yの場合は「seccomp」、それ以外は「prctl」

このオプションを指定しない場合は、spectre_v2_user=autoと同等です。

一般的には、カーネルは現在のCPUに対して適切な緩和策をデフォルトで選択します。Spectre variant 2の緩和策を無効にするには、spectre_v2=offで起動します。Spectre variant 1の緩和策は無効にできません。

緩和策選択ガイド¶

1. 信頼できるユーザースペース¶

すべてのユーザースペースアプリケーションが信頼できるソースから来ており、外部から提供された信頼できないコードを実行しない場合、緩和策を無効にできます。

2. 感度の高いプログラムの保護¶

セキュリティに敏感なプログラム（例: 暗号キーを持つプログラム）には、プログラムが実行されている間、間接ブランチの推測を無効にすることで、Spectre variant 2に対する保護を実施できます（参照 Speculation Control).

3. 信頼できないプログラムをサンドボックス化する¶

攻撃の源となる可能性のある信頼できないプログラムは、実行時に間接ブランチの推測を無効にして隔離できます（参照 Speculation Control). この方法により、信頼できないプログラムがブランチターゲットバッファを汚染するのを防ぎます。SECCOMPサンドボックスで実行されているすべてのプログラムは、デフォルトで間接ブランチの推測が制限されます。この挙動はカーネルのコマンドラインやsysfs制御ファイルを通じて変更可能です。参照 カーネルコマンドラインでの緩和制御.

3. 高度なセキュリティモード¶

すべてのプログラムに対してSpectre variant 2の緩和策を起動時に強制的に有効にするには、起動時に「on」オプションを指定します（参照 カーネルコマンドラインでの緩和制御). これにより、すべてのプログラムの間接ブランチの推測が制限されるため、オーバーヘッドが発生します。

x86では、新しいプログラムに切り替える際にIBPBでブランチターゲットバッファがクリアされます。STIBPは常に有効にされ、スレッドの兄弟プロセスから発生するSpectre variant 2攻撃を防ぎます。

代替案として、間接ブランチの推測が明示的に無効になっているプログラムを実行する際のみSTIBPを使用し、新しいプログラムに切り替える際には常にIBPBを使用してブランチターゲットバッファをクリアします（参照「ibpb」オプション カーネルコマンドラインでの緩和制御). この「ibpb」オプションは「on」オプションよりパフォーマンスコストが低く、STIBPを常に有効にしている「on」オプションよりも効率的です。

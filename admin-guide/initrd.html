初期 RAM ディスク (initrd) の使用¶

1996年、2000年に Werner Almesberger <werner.almesberger@epfl.ch> および Hans Lermen <lermen@fgan.de>

initrd は、ブートローダーによって RAM ディスクをロードする機能を提供します。この RAM ディスクはその後、ルートファイルシステムとしてマウントされ、プログラムをその上から実行できます。その後、別のデバイスから新しいルートファイルシステムをマウントし、以前のルート（initrd からのもの）はディレクトリに移動され、その後アンマウントできます。

initrd は、システム起動を2段階に分けるように設計されています。1段階ではカーネルが最小限のコンパイル済みドライバを含んで起動し、2段階では initrd から追加のモジュールをロードします。

このドキュメントでは initrd の使用方法について簡単な概要を説明します。より詳細なブートプロセスについては、 1.

操作¶

initrd を使用する場合、システムは通常以下の手順で起動します：

  1. ブートローダーがカーネルと初期RAMディスクをロードします

  2. カーネルが initrd を「通常の」RAMディスクに変換し、initrd に使用されていたメモリを解放します

  3. ルートデバイスが /dev/ram0でない場合、古い（非推奨）change_root プロシージャーが実行されます。下記の「非推奨のルート変更メカニズム」セクションを参照してください。

  4. ルートデバイスがマウントされます。もし /dev/ram0の場合、initrd イメージがルートとしてマウントされます

  5. /sbin/init が実行されます（これは有効な実行可能なファイル（シェルスクリプトを含む）であり、uid 0 で実行され、init が行えるほぼすべての操作が可能です）。

  6. init が「実際の」ルートファイルシステムをマウントします

  7. init が pivot_root システムコールを使用してルートディレクトリにルートファイルシステムを配置します

  8. init が /sbin/init 新しいルートファイルシステム上で実行され、通常のブートシーケンスが行われます

  9. initrd ファイルシステムが削除されます

ルートディレクトリの変更にはアンマウントは含まれません。そのため、この手順中に initrd 上で実行中のプロセスを残すことが可能です。また、initrd にマウントされたファイルシステムは引き続きアクセス可能です。

ブートコマンドラインオプション¶

initrd は以下の新しいオプションを追加します：

initrd=<path>    (e.g. LOADLIN)

  Loads the specified file as the initial RAM disk. When using LILO, you
  have to specify the RAM disk image file in /etc/lilo.conf, using the
  INITRD configuration variable.

noinitrd

  initrd data is preserved but it is not converted to a RAM disk and
  the "normal" root file system is mounted. initrd data can be read
  from /dev/initrd. Note that the data in initrd can have any structure
  in this case and doesn't necessarily have to be a file system image.
  This option is used mainly for debugging.

  Note: /dev/initrd is read-only and it can only be used once. As soon
  as the last process has closed it, all data is freed and /dev/initrd
  can't be opened anymore.

root=/dev/ram0

  initrd is mounted as root, and the normal boot procedure is followed,
  with the RAM disk mounted as root.

圧縮された cpio アーカイブ¶

最近のカーネルでは、圧縮された cpio アーカイブから RAM ディスクを構築する機能があります。このようなシステムでは、RAM ディスクイメージの作成に特別なブロックデバイスやループバックは必要なく、ディスク上のディレクトリを作成し、そのディレクトリに移動して、以下の例のように実行できます：

find . | cpio --quiet -H newc -o | gzip -9 -n > /boot/imagefile.img

既存のイメージファイルの内容を確認するのも同様に簡単です：

mkdir /tmp/imagefile
cd /tmp/imagefile
gzip -cd /boot/imagefile.img | cpio -imd --quiet

インストール¶

まず、「通常の」ルートファイルシステム上に initrd ファイルシステム用のディレクトリを作成する必要があります。例えば：

# mkdir /initrd

ディレクトリ名は特に重要ではありません。詳細については、 pivot_root(2) man page.

ブートプロセス中にルートファイルシステムが作成される場合（つまりインストール用フロッピーディスクを作成している場合）、ルートファイルシステムの作成プロセスは以下のファイルシステムを作成する必要があります。 /initrd directory.

initrdが一部のケースでマウントされない場合でも、以下のデバイスが作成されれば、その内容は依然としてアクセス可能です:

# mknod /dev/initrd b 1 250
# chmod 400 /dev/initrd

第二に、カーネルはRAMディスクサポートと初期RAMディスクのサポートが有効になっている状態でコンパイルされる必要があります。また、initrdからプログラムを実行するために必要なすべてのコンポーネント（例: 実行可能形式とファイルシステム）もカーネルにコンパイルされる必要があります。

第三に、RAMディスクイメージを作成する必要があります。これはブロックデバイスにファイルシステムを作成し、必要なファイルをコピーしてから、ブロックデバイスの内容をinitrdファイルにコピーする作業です。最近のカーネルでは、少なくとも以下の3種類のデバイスが適しています:

  • フロッピーディスク（どこでも動作しますが、非常に遅い）

  • RAMディスク（高速ですが物理メモリを割り当てます）

  • ループバックデバイス（最も洗練された解決策）

ループバックデバイスの方法について説明します:

  1. ループバックブロックデバイスがカーネルに組み込まれていることを確認してください

  2. 適切なサイズの空のファイルシステムを作成します、例:

    # dd if=/dev/zero of=initrd bs=300k count=1
# mke2fs -F -m0 initrd

    (スペースが限られている場合は、Minix FSをExt2よりも使用することを検討してください)

  3. ファイルシステムをマウントします、例:

    # mount -t ext2 -o loop initrd /mnt

  4. コンソールデバイスを作成します:

    # mkdir /mnt/dev
# mknod /mnt/dev/console c 5 1

  5. initrd環境を正しく使用するために必要なすべてのファイルをコピーします。最も重要なファイル /sbin/init

    注意

    /sbin/init 権限には「x」（実行）を含める必要があります。

  6. initrd環境の正しい動作は、再起動せずに以下のコマンドで頻繁にテストできます:

    # chroot /mnt /sbin/init

    これは、一般的なシステム状態を変更しないinitrd（例: ネットワークインターフェースの再構成、マウントされたデバイスの上書き、すでに実行中のデーモンの起動など）に限られます。ただし、通常、このようなchrootされたinitrd環境でpivot_rootを使用することが可能です。

  7. ファイルシステムをアンマウントします:

    # umount /mnt

  8. initrdは現在「initrd」ファイルにあります。オプションでこれを行います:

    # gzip -9 initrd

initrdの実験を行う場合は、レスキュー用フロッピーディスクを作成し、以下のシンボリックリンクを追加することもできます /sbin/init に（木の下から葉に向かって） /bin/sh. あるいは、実験用のnewlib環境を試すこともできます 2 小さなinitrdを作成するためです。

最後に、カーネルを起動しinitrdをロードする必要があります。ほぼすべてのLinuxブートローダーがinitrdをサポートしています。ブートプロセスは依然として古いメカニズムと互換性があるため、以下のブートコマンドラインパラメータを指定する必要があります:

root=/dev/ram0 rw

(rwはinitrdファイルシステムに書き込む必要がある場合にのみ必要です。)

LOADLINを使用する場合は、単に実行します:

LOADLIN <kernel> initrd=<disk_image>

e.g.:

LOADLIN C:\LINUX\BZIMAGE initrd=C:\LINUX\INITRD.GZ root=/dev/ram0 rw

LILOを使用する場合は、オプションを追加します INITRD=<path> グローバルセクションまたは対応するカーネルのセクションに /etc/lilo.conf、APPENDを使用してオプションを渡します。例:

image = /bzImage
  initrd = /boot/initrd.gz
  append = "root=/dev/ram0 rw"

そして実行します /sbin/lilo

他のブートローダーについては、それぞれのドキュメンテーションを参照してください。

これでinitrdを使用して起動し、楽しめます。

ルートデバイスの変更¶

その役割を終えたら、initは通常、ルートデバイスを変更し、Linuxシステムを「実際の」ルートデバイス上で起動する作業を進めます。

この手順には以下のステップがあります:

  • 新しいルートファイルシステムのマウント

  • それをルートファイルシステムに変換する

  • 古い（initrd）ルートファイルシステムへのすべてのアクセスを削除する

  • initrdファイルシステムのアンマウントとRAMディスクのメモリの解放

新しいルートファイルシステムのマウントは簡単です。現在のルート以下のディレクトリにマウントするだけでよいです。例:

# mkdir /new-root
# mount -o ro /dev/hda1 /new-root

ルートの変更はpivot_rootシステムコールで実行され、また以下で利用可能です: pivot_root ユーティリティ（参照: pivot_root(8) manページ; pivot_root util-linuxバージョン2.10h以上に同梱されています 3). pivot_root 現在のルートを新しいルート以下のディレクトリに移動し、新しいルートをその場所に配置します。古いルートのディレクトリはpivot_rootを呼び出す前に存在する必要があります。 pivot_root. 例:

# cd /new-root
# mkdir initrd
# pivot_root . initrd

現在、initプロセスは実行可能ファイル、共有ライブラリ、標準入出力/エラー、および現在のルートディレクトリを通じて古いルートにアクセスする可能性があります。これらすべての参照は次のコマンドで解除されます:

# exec chroot . what-follows <dev/console >dev/console 2>&1

what-followsが新しいルート以下のプログラムである場合、例えば: /sbin/init 新しいルートファイルシステムがudevとともに使用され、有効な /dev ディレクトリがない場合、chrootを呼び出す前にudevを初期化する必要があります。 /dev/console.

注意: pivot_rootの実装詳細は時間とともに変更される可能性があります。互換性を確保するため、以下の点に注意してください:

  • pivot_rootを呼び出す前に、呼び出しプロセスの現在ディレクトリが新しいルートディレクトリを指している必要があります

  • 最初の引数として.を使用し、古いルートのディレクトリの相対パスを第二引数として使用する

  • 古いルートと新しいルートの両方でchrootプログラムが利用可能である必要があります

  • その後、新しいルートにchrootする

  • execコマンドでdev/consoleに相対パスを使用する

これでinitrdをアンマウントし、RAMディスクによって割り当てられたメモリを解放できます:

# umount /initrd
# blockdev --flushbufs /dev/ram0

NFSマウントされたルートを使用してinitrdを使用することも可能です。参照: pivot_root(8) manページの詳細。

使用シナリオ¶

initrdを実装する主な動機は、システムインストール時にモジュール化されたカーネル構成を可能にするためです。手順は以下の通りです:

  1. システムはフロッピーディスクや他のメディアから最小限のカーネル（例: RAMディスク、initrd、a.out、Ext2 FSのサポート）を起動し、initrdをロードします

  2. /sbin/init 「実際の」ルートFS（つまり、デバイスタイプ、デバイスドライバ、ファイルシステム）をマウントするための必要な情報と、配布メディア（例：CD-ROM、ネットワーク、テープなど）を決定します。これはユーザーに尋ねる、自動プローブによる、またはハイブリッドアプローチを用いることで実現できます。

  3. /sbin/init 必要なカーネルモジュールをロードします。

  4. /sbin/init ルートファイルシステムを作成し、初期化します（これはまだ使いやすいシステムである必要はありません）。

  5. /sbin/init が呼び出されます。 pivot_root ルートファイルシステムを変更し、chroot経由でインストールを継続するプログラムを実行します。

  6. ブートローダーがインストールされます。

  7. ブートローダーが、システム起動に使用したモジュールセットを含むinitrdをロードするように設定されます（例： /initrd 変更可能で、その後アンマウントされ、最終的に画像がこの /dev/ram0 または /dev/rd/0 ファイルに書き込まれます）。

  8. これでシステムは起動可能となり、追加のインストールタスクが実行できます。

initrdの主な役割は、通常のシステム運用時に構成データを再利用することを可能にし、膨大な「汎用」カーネルやカーネルの再コンパイル・再リンクを必要としないことです。

二つ目のシナリオは、単一の管理ドメイン内で異なるハードウェア構成を持つシステムでLinuxが動作するインストールです。このような場合、小さなセットのカーネル（理想的には1つだけ）を生成し、システム固有の構成情報のサイズを最小限に保つことが望ましいです。この場合、必要なモジュールすべてを含む共通のinitrdが生成され、その後、 /sbin/init またはその読み込みに必要なファイルが異なるだけでよいです。

三つ目のシナリオは、より使いやすい復旧ディスクです。ルートFSパーティションの場所などの情報は起動時に提供する必要がなく、initrdからシステムをロードする際にはユーザー向けのダイアログが呼び出され、またいくつかの整合性チェック（あるいは自動検出の形）を行うこともできます。

最後に、CD-ROMディストリビューターはinitrdを用いてCDからのインストールをより効率化する場合があります。例えば、ブートフロッピーやinitrd経由でCDから大きなRAMディスクをブートストラップする、または LOADLIN またはCD-ROM自体からブートし、フロッピーよりもRAMディスクをCDからロードします。

非推奨のルート変更メカニズム¶

このメカニズムはpivot_rootの導入以前に使用されていました。現在のカーネルでもサポートされていますが、これに依存すべきではありません。

このメカニズムは、linuxrcが終了するときに「実際の」ルートデバイス（つまり、カーネルイメージでrdevで設定したか、ブートコマンドラインでroot=…で指定したデバイス）をルートファイルシステムとしてマウントします。その後、initrdファイルシステムがアンマウントされ、もしそれがまだbusyであれば、ディレクトリに移動されます。 /initrd新しいルートファイルシステム上にこのようなディレクトリが存在する場合があります。

このメカニズムを使用するには、ブートコマンドオプションのroot、init、またはrwを指定する必要はありません。(指定された場合、これらは実際のルートファイルシステムに影響を与えるだけで、initrd環境には影響しません。)

/procがマウントされている場合、linuxrc内から「実際の」ルートデバイスを変更できます。新しいルートFSデバイスの番号を特殊ファイル/proc/sys/kernel/real-root-devに書き込むことで、例えば:

# echo 0x301 >/proc/sys/kernel/real-root-dev

このメカニズムはNFSや類似のファイルシステムと互換性がありません。

この古い非推奨メカニズムは一般的に change_rootと呼ばれます、一方で新しいサポートされているメカニズムは pivot_root.

change_rootとpivot_rootの混合メカニズム¶

change_rootとpivot_rootメカニズムを使用したくない場合、 root=/dev/ram0 pivot_rootメカニズムをトリガーするため、initrdイメージ内に両方の /linuxrc および /sbin/init を作成できます。

/linuxrc は以下のみを含みます:

#! /bin/sh
mount -n -t proc proc /proc
echo 0x0100 >/proc/sys/kernel/real-root-dev
umount -n /proc

linuxrcが終了した後、カーネルはinitrdを再びルートとしてマウントし、このとき /sbin/initを実行します。再度、この初期化プロセスの役割は、最終的な実行前の正しい環境を構築すること（コマンドラインで渡された root= device を使用して）です。 /sbin/init.

General Information¶

intel_pstate intel_idle ドライバーは、 CPU performance scaling subsystem in the Linux kernel (CPUFreq). It is a scaling driver for the Sandy Bridge and later generations of Intel processors. Note, however, that some of those processors may not be supported. [To understand intel_pstate it is necessary to know how CPUFreq works in general, so this is the time to read CPUパフォーマンススケーリング if you have not done that yet.]

For the processors supported by intel_pstate, the P-state concept is broader than just an operating frequency or an operating performance point (see the LinuxCon Europe 2015 presentation by Kristen Accardi 1 for more information about that). For this reason, the representation of P-states used by intel_pstate internally follows the hardware specification (for details refer to Intel Software Developer’s Manual 2). However, the CPUFreq core uses frequencies for identifying operating performance points of CPUs and frequencies are involved in the user space interface exposed by it, so intel_pstate maps its internal representation of P-states to frequencies too (fortunately, that mapping is unambiguous). At the same time, it would not be practical for intel_pstate to supply the CPUFreq core with a table of available frequencies due to the possible size of it, so the driver does not do that. Some functionality of the core is limited by that.

Since the hardware P-state selection interface used by intel_pstate is available at the logical CPU level, the driver always works with individual CPUs. Consequently, if intel_pstate is in use, every CPUFreq policy object corresponds to one logical CPU and CPUFreq policies are effectively equivalent to CPUs. In particular, this means that they become “inactive” every time the corresponding CPU is taken offline and need to be re-initialized when it goes back online.

intel_pstate is not modular, so it cannot be unloaded, which means that the only way to pass early-configuration-time parameters to it is via the kernel command line. However, its configuration can be adjusted via sysfs to a great extent. In some configurations it even is possible to unregister it via sysfs which allows another CPUFreq scaling driver to be loaded and registered (see に記載されています。).

Operation Modes¶

intel_pstate can operate in two different modes, active or passive. In the active mode, it uses its own internal performance scaling governor algorithm or allows the hardware to do preformance scaling by itself, while in the passive mode it responds to requests made by a generic CPUFreq governor implementing a certain performance scaling algorithm. Which of them will be in effect depends on what kernel command line options are used and on the capabilities of the processor.

This is the default operation mode of intel_pstate ハードウェア管理P状態（HWP）をサポートするプロセッサ向けに。 scaling_driver ポリシーアトリビュートを使用していつでも変更できます。 sysfs すべての CPUFreq ポリシーに文字列 "intel_pstate" が含まれる。

このモードでは、ドライバーがスケーリングガバナーレイヤーをバイパスし、 CPUFreq 独自のスケーリングアルゴリズムを提供します。 CPUFreq これらのアルゴリズムは、一般的なスケーリングガバナーと同じようにポリシーに適用できます（つまり、 scaling_governor ポリシーアトリビュートを使用していつでも変更できます。 sysfs）。[注意：異なるポリシーに対して異なるP状態選択アルゴリズムを選択する場合もありますが、それは推奨されません。]

これらは一般的なスケーリングガバナーではありませんが、一部のガバナーと同じ名前を持っています。さらに混乱するのが、これらは一般的なガバナーと同じように動作しないことが一般的です。たとえば、 powersave 提供されるP状態選択アルゴリズム intel_pstate は一般的な powersave ガバナー（概ね、 schedutil および ondemand ガバナーに該当します）。

トーボP-statesサポート¶

ほとんどの場合、利用可能なP-statesの全体範囲は intel_pstate 、異なるタイプのプロセッサ動作に対応する2つのサブ範囲に分けることができます。この境界は後述の「トーボしきい値」と呼ばれます。

トーボしきい値を超えるP-statesは「トーボP-states」と呼ばれ、それらが属するサブ範囲全体は「トーボ範囲」と呼ばれます。これらの名称は、マルチコアプロセッサが十分な電力がある場合に、熱的制限を超えない限り、1つ以上のコアのP-stateを機械的に増加させるTurbo Boost技術に関連しています。

具体的には、ソフトウェアがCPUコアのP-statesをトルボ範囲（つまり、トルボしきい値を超えた範囲）内で設定した場合、プロセッサはそのコアのパフォーマンススケーリング制御を引き受けて、今後自身が選ぶトルボP-statesに移行することが許可されます。ただし、この許可の解釈はプロセッサの世代によって異なります。つまり、サンドイッチブリッジ世代のプロセッサは、ソフトウェアが設定した最後のP-stateを超えたものを使わず、トルボ範囲内であっても、決して使用しません。一方、それ以降の世代のプロセッサは、この設定をトルボ範囲内のすべてのP-stateを自由に使用する許可と解釈し、ソフトウェアが設定したP-stateを上回るものも含めて利用できます。言い換えれば、これらのプロセッサでは、トルボ範囲内のどのP-stateを設定しても、そのコアを最大サポート可能なトルボP-stateにまで引き上げるようプロセッサが自由に処理します。

トルボP-statesの重要な特性の一つは、持続不可能なことです。より正確には、どのCPUもこれらの状態に indefinitely とどまることを保証されていません。これは、プロセッサパッケージ内の電力配分が時間とともに変化する可能性があるため、あるいはトルボP-stateを長時間使用した結果、設計された熱的制限を超える可能性があるためです。

逆に、トルボしきい値以下のP-statesは一般的に持続可能です。実際、ソフトウェアがそのうちのどれかを設定した場合、プロセッサは熱的ストレスや電力制限違反の状況以外では、それをより低いP-stateに変更しないと期待されます（同一パッケージ内の他のCPUが同時に同じP-stateを設定している場合など、より高いP-stateを引き続き使用する可能性もあります）。

一部のプロセッサでは、複数のコアが同時にトルボP-statesにいることが可能ですが、それらの最大P-stateは同時に実行中のコア数に依存します。通常、3コアが同時に実行されている場合の最大トルボP-stateは、2コアの場合より低く、2コアの場合の最大値は1コアの場合より低くなります。したがって、1コアの最大トルボP-stateは全体で最も高い値です。

サポートされる最大のトルボPステート、トルボしきい値（サポートされる最大の非トルボPステート）およびサポートされる最小のPステートは、プロセッサモデル固有の値であり、プロセッサのモデル固有レジスタ（MSR）を読み取ることで決定できます。さらに、一部のプロセッサは設定可能なTDP（熱設計電力）機能をサポートしており、この機能が有効になっている場合、トルボしきい値はプラットフォームファームウェアによって設定可能な値になります。

ACPIテーブル内のオブジェクトとは異なり、 _PSS 常にすべての利用可能なPステート（トルボ範囲を含む）を intel_pstate コアおよび（パッシブモードでは）ジェネリックなスケーリングガバナに公開します。これにより、ACPIベースのCPUパフォーマンススケーリングに比べて、トルボPステートがより頻繁に設定される傾向があります（詳しくは CPUFreq を参照してください）。 intel_pstate が使用される際には、 に記載されています。 の属性はすべてのケースで期待通り動作する必要があります（つまり、トルボPステートを無効に設定した場合でも常にそれらの使用を防ぐ必要があります）。

さらに、 intel_pstate が実際のトルボしきい値を常に把握しているため（プロセッサでConfigurable TDP機能が有効になっていても）、その no_turbo 属性は sysfs （説明は に記載されています。）で正しく動作する必要があります。 intel_pstate を参照してください）。

Pステート制限の調整¶

intel_pstate Pステート制限を2つの方法で設定できます： max_perf_pct および min_perf_pct グローバル属性 を介して、または scaling_max_freq および scaling_min_freq CPUFreq ポリシー属性を介して。これらの制限間の調整は、ドライバの現在の運用モードに関係なく以下のルールに基づいて行われます。

  1. すべてのCPUはグローバル制限に影響されます（つまり、どのCPUもグローバル最大値より速く動作させられず、グローバル最小値より遅く動作させられません）。

  2. 各CPUは自身のポリシーごとの制限に影響されます（つまり、自身のポリシー最大値より速く動作させられず、ポリシー最小値より遅く動作させられません）。有効なパフォーマンスは、プラットフォームがコアごとのPステートをサポートしているか、ハイパースレッディングが有効になっているか、および他のCPUからのパフォーマンス要求によって異なります。プラットフォームがコアごとのPステートをサポートしていない場合、他のCPUがその時点で高いパフォーマンスを要求している場合、そのCPUのポリシーで設定された制限を超える有効なパフォーマンスが発生する可能性があります。コアごとのPステートをサポートしていても、ハイパースレッディングが有効な場合、シblings CPUが高いパフォーマンスを要求していると、他のシblings CPUは自身のポリシー制限を超えるパフォーマンスを得る可能性があります。

  3. グローバル制限とポリシーごとの制限は独立して設定できます。

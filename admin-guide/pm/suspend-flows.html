システムスリープコードフロー¶

著者

システムが作業状態からサポートされているいずれかのスリープ状態へ移行するには、少なくとも1つのグローバルなシステム全体の移行が必要です スリープ状態. ハイبرネーションにはこの目的で複数の移行が必要ですが、他のスリープ状態は一般的に システム全体のスリープ (または単に システムスリープ)状態と呼ばれるもので、これには1つの移行で十分です。

これらのスリープ状態では、システムの作業状態からターゲットスリープ状態への移行は システムスリープ （ほとんどの場合、この表現が移行を意味するかスリープ状態を意味するかは文脈によって明確になります）と呼ばれ、スリープ状態から作業状態への戻りは システム再起動.

システムのさまざまなスリープ状態に関連するスリープと再起動の移行に伴うカーネルコードフローは非常に類似していますが、 スリープ（S2IまたはS2Idle） コードフローと関連する suspend-to-RAM および standby スリープ状態のコードフローにはいくつかの重要な違いがあります。

以下の suspend-to-RAM および standby スリープ状態はプラットフォームサポートなしでは実装できません。それらの違いは、スリープと再起動のフックでプラットフォームドライバが提供する必要のあるプラットフォーム固有のアクションに帰着します。それ以外の点では、これらのスリープ状態のスリープと再起動コードフローはほぼ同一なので、これらを合わせて プラットフォーム依存スリープ 状態と呼ぶことにします。

スリープへの待機状態移行コードフロー¶

システムが作業状態から スリープ（S2IまたはS2Idle） スリープ状態へ移行する際の手順は以下の通りです：

  1. システム全体のスリープ通知を呼び出す。

    カーネルサブシステムは、スリープ移行が開始される直前に呼び出されるコールバックと、再起動移行が完了した後に呼び出されるコールバックを登録できます。

    これにより、システム状態の変更に備えることができ、再起動後に作業状態に戻った後にクリーンアップを行うことができます。

  2. タスクの凍結。

    タスクは主にユーザー空間からMMIO領域や直接アクセス可能なI/Oレジスタを通じた不正なハードウェアアクセスを防ぐために凍結されます。また、次の移行ステップが進行中にユーザー空間がカーネルに進入しないようにします（これはさまざまな理由で問題になる可能性があります）。

    すべてのユーザー空間タスクは、シグナルが送られたかのようにインターセプトされ、次のシステム再起動移行が終了するまで非中断スリープ状態に置かれます。

    システムの停止中に特定の理由で凍結されるカーネルスレッドはその後凍結されますが、インターセプトされません。代わりに、それらは定期的に凍結が必要かどうかを確認し、必要と判断された場合は非中断スリープ状態に移行する必要があります。[ただし、カーネルスレッドはカーネル空間で利用可能なロックや他の並行制御を用いてシステムの停止と再開と同期化でき、これにより凍結よりもはるかに正確な制御が可能となるため、後者の方法はカーネルスレッドには推奨されません。]

  3. デバイスの停止とIRQの再構成。

    デバイスは4つのフェーズで停止され、それらは 準備, 停止, 後続の停止 および IRQなし停止 (参照： デバイス電源管理の基礎 各フェーズで実際に何が起こるかについては詳細を参照してください。

    すべてのデバイスが各フェーズで処理されますが、通常はそれらのうち2つ以上で物理的にアクセスされることがありません。

    ランタイムPM APIはすべてのデバイスで、期間中は無効にされます 遅延 スリープフェーズと高レベルの（「アクション」）割込みハンドラは、noirqスリープフェーズが始まる前には呼び出されません。 noirq スリープフェーズ。

    その後も割込みは処理されますが、割込みコントローラーにのみ通知され、システムの通常動作状態で発生するデバイス固有のアクションは実行されません（これらのアクションは、後続のシステム復帰遷移で実行されます。参照 に記載されています。).

    システム復帰デバイスに関連するIRQは「アーム」され、それらのいずれかがイベントを送信するとシステム復帰遷移が開始されます。

  4. スケジューラ・ティックの凍結と時刻保持の停止。

    すべてのデバイスがスリープ状態になった後、CPUはアイドルループに移行し、最も深いアイドル状態に移されます。この際、各CPUは自身のスケジューラ・ティックを「凍結」し、ティックに関連するタイマーイベントは、別の割込みソースによってCPUが再起動されるまで発生しません。

    最後にアイドル状態に入ったCPUは時刻保持を停止します（その他の機能も含む）。これにより、高解像度タイマーが将来の動作をトリガーするのを防ぎ、最初に起動されたCPUが時刻保持を再開するまで、CPUは一括りで比較的長時間の深いアイドル状態を維持できます。

    この時点で、CPUは非タイマーハードウェア割込みのみで起動されます。その場合、CPUはアイドル状態に戻りますが、起動したCPUに割込みが発生した場合、システム復帰遷移が開始されます（その割込みがシステム復帰用IRQから来た場合）。

スリープからの復帰コードフロー¶

システムがスリープ状態から作業状態に移行するための以下の手順が実行されます: スリープ（S2IまたはS2Idle） スリープ状態から作業状態への移行には以下の手順が実行されます:

  1. タイマーカウントを再開し、スケジューラのティックを凍結解除します。

    1つ以上のCPUが非タイマーハードウェア割込みによって起動されると、前段階のスリープ移行で最後に進入したアイドル状態から抜け、タイマーカウントを再開し（他のCPUがすでに起動して再開している場合は除く）、そのCPUのスケジューラティックを凍結解除します。

    CPUを起動した割込みがシステム再起動用に設定されていた場合、システム再起動の移行が開始されます。

  2. デバイスの再起動と作業状態のIRQ設定の復元を行います。

    デバイスは以下の4つのフェーズで再起動されます: noirq再起動, early再起動, 再起動 および complete (参照： デバイス電源管理の基礎 各フェーズで実際に何が起こるかについては詳細を参照してください。

    すべてのデバイスが各フェーズで処理されますが、通常はそれらのうち2つ以上で物理的にアクセスされることがありません。

    IRQの作業状態設定は、再起動フェーズの後で復元され、ドライバがサポートするすべてのデバイスにおいて、earlyフェーズ中にランタイムPM APIが再有効化されます。 noirq 再起動フェーズの後で、ランタイムPM APIが再有効化されます。 early 再開フェーズ。

  3. タスクの復活。

    前の遷移のステップ2で凍結されたタスクは「解凍」され、 停止 それらがその時点での中断不能なスリープから目覚めさせられ、ユーザー空間のタスクがカーネルから抜け出すことが許可される。

  4. システム全体の再開通知を呼び出す。

    これは前の遷移のステップ1に類似しており、 停止 この時点で同じセットのコールバックが呼び出されるが、異なる「通知タイプ」パラメータ値が渡される。

プラットフォーム依存スリープコードフロー¶

システムが作業状態からプラットフォーム依存スリープ状態へ遷移する際の手順は以下の通り：

  1. システム全体のスリープ通知を呼び出す。

    このステップは、suspend-to-idleスリープ遷移で説明したステップ1と同じです。 上記.

  2. タスクの凍結。

    このステップは、suspend-to-idleスリープ遷移で説明したステップ2と同じです。 上記.

  3. デバイスの停止とIRQの再構成。

    このステップは、suspend-to-idleスリープ遷移で説明したステップ3に類似していますが、 上記システム wakeup 用の IRQ のアーム処理は、プラットフォームに影響を与えることが一般的ではありません。

    すべてのCPUが十分な深さのアイドル状態にあり、すべてのI/Oデバイスが低電力状態にされている場合、一部のプラットフォームでは非常に深い低電力状態に移行できます。このようなプラットフォームでは、suspend-to-idleによりシステムの消費電力が大幅に削減されます。

    しかし、他のプラットフォームでは、低レベルのコンポーネント（例：割込み制御器）をプラットフォーム固有の方法でオフにする必要があります（プラットフォームドライバが提供するハックで実装されます）才能同等の電力削減を達成できます。

    通常、インバンドハードウェア割り込みはシステムを起動させることを防ぎ、これは特別なプラットフォーム依存の方法で行われる必要があります。その後、システムのウェイクアップソースの設定は、システムウェイクアップデバイスがスリープ状態になったときに開始され、プラットフォームスリープホックによって最終的に完了します。

  4. 非ブートCPUの無効化。

    一部のプラットフォームでは、上記のスリープホックはシステムの1CPU構成で実行される必要があります（特に、ハードウェアはプラットフォームスリープホックと並行して実行されるコードによってアクセスできない必要があります。プラットフォームファームウェアにトラップしてスリープ遷移を完了させることが一般的です）。

    このため、CPUオフライン/オンライン（CPUホットプラグ）フレームワークが使用され、システム内のすべてのCPU（ブートCPUを除く）がオフラインにされ（通常、オフラインにされたCPUはディープアイドル状態になります）。

    これにより、すべてのタスクがこれらのCPUから移動し、すべての割り込み（IRQ）が唯一オンラインのCPUに再ルーティングされます。

  5. コアシステムコンポーネントのスリープ。

    コアシステムコンポーネントが（電力喪失を含む）将来の動作準備を行い、時刻管理を停止します。

  6. プラットフォーム固有の電源除去。

    これは、メモリコントローラーとRAM（後者の内容を保持するため）および一部のシステムウェイクアップデバイスを除いて、すべてのシステムコンポーネントから電源を除去する予定です。

    多くの場合、制御はプラットフォームファームウェアに渡され、必要な場合はスリープ遷移を完了する必要があります。

プラットフォーム依存の再開コードフロー¶

システムがプラットフォーム依存のスリープ状態から作業状態に戻るための以下のステップが実行されます：

  1. プラットフォーム固有のシステムウェイクアップ。

    プラットフォームは、指定されたシステムウェイクアップデバイスからの信号によって起動され（インバンドハードウェア割り込みでなくてもよい）、制御はカーネルに戻されます（カーネルが制御を再取得する前に、プラットフォームファームウェアがプラットフォームの作業構成を復元する必要があります）。

  2. コアシステムコンポーネントの再開。

    スリープ時のコアシステムコンポーネントの設定が復元され、時刻管理が再開されます。

  3. 非ブートCPUの再有効化。

    前のスリープ遷移でステップ4で無効化されたCPUが再びオンラインにされ、そのスリープ時の設定が復元されます。

  4. デバイスの再起動と作業状態のIRQ設定の復元を行います。

    このステップは、suspend-to-idleスリープ遷移で説明したステップ2と同じです。 上記.

  5. タスクの復活。

    このステップは、スリープトアイドルのスリープ遷移で説明したステップ3と同じです 上記.

  6. システム全体の再開通知を呼び出す。

    このステップは、スリープトアイドルのスリープ遷移で説明したステップ4と同じです 上記.

バグの報告¶

背景¶

上流のLinuxカーネルメンテナは特定のカーネルバージョンのみを対象に不具合を修正します。対象バージョンには現在の「リリース候補」（-rc）カーネル、すべての「安定版」カーネル、およびすべての「長期サポート」カーネルが含まれます。

詳しくは以下をご参照ください。 https://www.kernel.org/ サポート対象のカーネル一覧についてはこちら。サポート終了（[EOL]）が記載されているカーネルは、修正がバックポートされません。

kernel.orgに記載されていないバージョンのカーネルで不具合を見つけた場合、Linuxディストリビューションや埋め込みベンダーにサポートを依頼してください。 alternatively、サポートされている安定版または-rcカーネルを実行し、そのバージョンで不具合が再現するか確認してください。不具合を最新の-rcカーネルで再現するのが望ましいです。

Linux Kernel の不具合を報告する方法¶

問題の原因となるサブシステムを特定する¶

Linuxカーネルのどの部分が問題の原因になっているかを特定することで、不具合の修正が受けやすくなります。単に汎用のlinux-kernelメーリングリスト（LKML）に投稿しても、1日1000件以上のメールを扱うメーリングリストの中で不具合報告が埋もれてしまう可能性があります。

代わりに、問題の原因と考えられるカーネルサブシステムを特定し、そのサブシステムのメンテナおよびメーリングリストにメールを送ってください。サブシステムメンテナから返信がない場合は、LKMLなどのメーリングリストの範囲を広げてください。

通知すべき人物を特定する¶

問題の原因と考えられるサブシステムが特定できた場合、不具合報告を送信してください。一部のメンテナはバグトラッカー（https://bugzilla.kernel.org）を介して不具合報告を好む場合があります。一方で、他のメンテナはサブシステムメーリングリストを介して不具合報告を好む場合があります。

メールで不具合報告を送る際の宛先を確認するには、MAINTAINERSファイルで該当するサブシステムまたはデバイスドライバーを検索してください。関連するエントリをファイル内で検索し、「M:」行に記載された人物にメールを送信し、「L:」行に記載されたメーリングリストにCCしてください。メンテナが返信する際は、「全員に返信」を選択して、メールスレッドに公開メーリングリストを保持してください。

問題の原因となるドライバーがわかっている場合、get_maintainer.plスクリプトにそのドライバーファイルを渡してください：

perl scripts/get_maintainer.pl -f <filename>

セキュリティ不具合の場合は、MAINTAINERSファイルに記載されているセキュリティ担当者にコピーしてください。彼らは不具合修正と情報公開の調整をサポートします。参照： セキュリティ関連のバグ 詳しくは

どのサブシステムが原因か特定できない場合は、kernel.orgのバグトラッカーに不具合を報告し、 linux-kernel@vger.kernel.orgにメールを送信してください。バグトラッカーのURLを参照してください。（Linuxカーネルメーリングリストについての詳細情報は、 http://vger.kernel.org/lkml/).

不具合報告のヒント¶

不具合報告が初めての場合、以下のガイドを読みましょう：

https://www.chiark.greenend.org.uk/~sgtatham/bugs.html

http://www.catb.org/esr/faqs/smart-questions.html

関連性のない不具合を別々のメールスレッドまたは別々のbugzillaエントリとして報告することが本当に重要です。複数の関連性のない不具合を一度に報告すると、メンテナが関連するデータを分離するのが困難になります。

情報を集める¶

不具合報告で最も重要な情報は、不具合を再現する方法です。これにはシステム情報、および（最も重要に）ユーザーが不具合をトリガーするためのステップバイステップの手順が含まれます。

失敗が「OOPS:」を含む場合、画面を撮影するか、netconsoleトレースをキャプチャするか、またはスクリーンに表示されたメッセージを直接不具合報告に記載してください。不具合報告を投稿する前に、以下のドキュメントを読みましょう。バグ狩り”を読みましょう。これは「Oops」情報の処理方法を説明しています。

メールまたはbugzilla経由で送信する不具合報告の推奨フォーマットです。標準化された不具合報告フォームを使用することで、あなたが何かを忘れずに済むようになり、開発者にとって必要な情報を見つけるのが容易になります。あなたの不具合と関係のない情報は自由に省略してください。

まず、scripts/ver_linuxに含まれるver_linuxスクリプトを実行し、いくつかの重要なサブシステムのバージョンを報告します。このスクリプトを実行するには以下のコマンドを用います awk -f scripts/ver_linux.

この情報をもとに不具合報告フォームのすべての項目を埋め、開発者による容易な識別のためにメールリストに投稿する際には、件名を「PROBLEM: <1.からの1行の要約>」とします:

[1.] One line summary of the problem:
[2.] Full description of the problem/report:
[3.] Keywords (i.e., modules, networking, kernel):
[4.] Kernel information
[4.1.] Kernel version (from /proc/version):
[4.2.] Kernel .config file:
[5.] Most recent kernel version which did not have the bug:
[6.] Output of Oops.. message (if applicable) with symbolic information
     resolved (see Documentation/admin-guide/bug-hunting.rst)
[7.] A small shell script or example program which triggers the
     problem (if possible)
[8.] Environment
[8.1.] Software (add the output of the ver_linux script here)
[8.2.] Processor information (from /proc/cpuinfo):
[8.3.] Module information (from /proc/modules):
[8.4.] Loaded driver and hardware information (/proc/ioports, /proc/iomem)
[8.5.] PCI information ('lspci -vvv' as root)
[8.6.] SCSI information (from /proc/scsi/scsi)
[8.7.] Other information that might be relevant to the problem
       (please look in /proc and include all information that you
       think to be relevant):
[X.] Other notes, patches, fixes, workarounds:

フォローアップ¶

不具合報告者の期待¶

Linuxカーネルメンテナは不具合報告者が報告した不具合についてフォローアップできるように期待しています。これは新しいテストを実行する、パッチを適用する、カーネルを再コンパイルする、または不具合を再トリガーするなど、さまざまな行動を含みます。メンテナにとって最もストレスになるのは、不具合を報告した後で、修正を試すよう求めても返信がないことです。

ただし、あなたがサポートされているカーネルで不具合が発生していることをメンテナが知っているだけでも有用です。フォローアップができない場合でも。例えば、「最新のカーネルを試してみたが不具合が再現しなくなった」というメールでのフォローアップも有用です。メンテナは沈黙を意味するものがまだ不具合が起きていることを前提にしています。

カーネルメンテナの期待¶

Linuxカーネルメンテナは忙しく、過労している人間です。場合によっては、あなたの不具合を1日、1週間、2週間以内に処理できないことがあります。メールに返信がない場合は、休暇中やLinuxカンファレンス出席中かもしれません。カンファレンススケジュールは https://LWN.net で確認してください:

https://lwn.net/Calendar/

一般的に、カーネルメンテナはバグ報告に対して1〜5営業日程度で返信します。ほとんどのメンテナはカーネルの開発に専念しており、土日は作業していない可能性があります。メンテナたちは世界中で分散しており、あなたのタイムゾーンで作業しているとは限りません。高優先度のバグでない限り、最初のバグ報告から少なくとも1週間待ってからメンテナにリマインダーのメールを送信してください。

このルールの例外は、リグレッション、カーネルクラッシュ、セキュリティの脆弱性、または新しいカーネル動作によって引き起こされるユーザースペースの破壊などです。これらのバグはメンテナがすぐに処理すべきです。メンテナがこれらの種類のバグに対して適切なタイミングで返信していないと感じた場合（特にマージウィンドウ中は特に）、LKMLおよびLinus Torvaldsにバグを報告してください。

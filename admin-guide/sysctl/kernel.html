bootloader_type (x86 限定)¶

これは、ブートローダーが示すタイプ番号を4ビット左にシフトし、ブートローダーのバージョンの下位4ビットをORで結合した値です。このエンコーディングの理由は、かつてカーネルヘッダーの type_of_loader フィールドと一致していたため、後方互換性のためこのエンコーディングを維持しています。つまり、ブートローダーのタイプ番号が0x15で、バージョン番号が0x234の場合、このファイルには340（0x154）が含まれます。

を参照してください。 type_of_loader および ext_loader_type の Linux/x86 ブートプロトコル フィールドを参照してください。

core_pipe_limit¶

このsysctlは、 core_pattern コアファイルをユーザー空間のヘルパープロセスにパイプするように設定されている場合（パターンの最初の文字が「|」の場合、上記を参照）にのみ適用されます。 core_pattern パイプでアプリケーションにコアを収集する際、収集アプリケーションがクラッシュしたプロセスの /proc/pid ディレクトリからデータを収集することがあります。これを安全に実行するため、カーネルは収集プロセスが終了するのを待つ必要があります。これにより、不適切なユーザー空間の収集プロセスがクラッシュしたプロセスの再収集をブロックする可能性があります。このsysctlはその対策として、同時にパイプされるクラッシュしたプロセスの最大数を定義します。この値を超える場合、その値を超えたプロセスはカーネルログに記録され、コアはスキップされます。0は特殊な値で、並行して無制限のプロセスを収集できるが、待機は行われない（つまり、収集プロセスが確実にアクセスできるとは限らない）ことを示します。 /proc/<crashing pid>/この値のデフォルトは0です。

core_uses_pid¶

デフォルトのコアダンプファイル名は「core」です。これを core_uses_pid 1に設定すると、コアダンプファイル名がcore.PIDになります。もし core_pattern 「%p」は含まない（デフォルトでは含まない）こと core_uses_pid 設定されている場合、ファイル名に.PIDが追加されます。

ctrl-alt-del¶

このファイルの値が0の場合、Ctrl-Alt-Delは捕捉され、 init(1) プログラムに graceful restart の処理を委譲されます。ただし、値が0より大きい場合、LinuxはVulcan Nerve Pinch（tm）に対する反応として即座に再起動します。ディスカーディングバッファの同期すら行わずにです。

注意:

プログラム（例：dosemu）がキーボードを「raw」モードで使用している場合、Ctrl-Alt-Del はカーネル tty レイヤーに到達する前にそのプログラムによってキャプチャされ、その処理はプログラムが決定する。

dmesg_restrict¶

このトグルは、権限のないユーザーが dmesg(8) カーネルのログバッファからのメッセージを表示するのを制限するかどうかを示します。When dmesg_restrict が 0 に設定されている場合、制限はありません。When dmesg_restrict が 1 に設定されている場合、ユーザーは CAP_SYSLOG を使用する必要があります。 dmesg(8).

カーネルの設定オプション CONFIG_SECURITY_DMESG_RESTRICT を設定するデフォルト値として dmesg_restrict.

ドメイン名とホスト名¶

これらのファイルは、domainname と hostname コマンドと同じ方法で、NIS/YP ドメイン名と、あなたのボックスのホスト名を設定するために使用できます。つまり：

# echo "darkstar" > /proc/sys/kernel/hostname
# echo "mydomain" > /proc/sys/kernel/domainname

は以下のとおり同じ効果を持ちます：

# hostname "darkstar"
# domainname "mydomain"

ただし、注意点として、クラシックな darkstar.frop.org はホスト名が "darkstar" で、DNS（インターネットドメインネームサーバー）ドメイン名が "frop.org" であり、NIS（ネットワーク情報サービス）または YP（イエローページ）ドメイン名とは混同しないでください。これら2つのドメイン名は一般的に異なります。詳細な議論については、 hostname(1) man page.

kptr_restrict¶

このトグルは、以下を通じてカーネルアドレスを公開する際の制限が設けられているかどうかを示します /proc その他のインターフェース。

が呼ばれるとき、modprobeは kptr_restrict 0（デフォルト）に設定されている場合、アドレスは印刷前にハッシュ化されます。（これは%pと同等です。）

が呼ばれるとき、modprobeは kptr_restrict 1に設定されている場合、%pKフォーマット指定子で印刷されるカーネルポインタは0に置き換えられます（ユーザーが CAP_SYSLOG 有効なユーザーおよびグループIDは、実際のIDと等しくなります。これは、%pKのチェックがread()のタイミングで行われるためであり、open()のタイミングではなく、open()とread()の間に権限が昇格した場合（例：setuidバイナリを通じて）%pKが非権限ユーザーにカーネルポインタを漏らすことはありません。注意：これは一時的な解決策です。正しい長期的な解決策は、%pKのチェックをopen()のタイミングで行うことです。%pKを使用するファイルからworld read権限を削除し、 dmesg_restrict を保護するために使用する dmesg(8) 非権限ユーザーにカーネルポインタ値を漏らすことが懸念される場合

が呼ばれるとき、modprobeは kptr_restrict 値が2に設定されている場合、%pKを使用して表示されるカーネルポインタは、権限に関係なく0に置き換えられます。

modprobe¶

カーネルモジュールを自動ロードするためのユーザーモードヘルパーのフルパス。デフォルトは「/sbin/modprobe」です。このバイナリは、カーネルがモジュールを要求するときに実行されます。たとえば、ユーザースペースがmount()に未知のファイルシステムタイプを渡した場合、カーネルはこのユーザーモードヘルパーを実行して、対応するファイルシステムモジュールを自動的にロードします。このユーザーモードヘルパーは、必要なモジュールをカーネルに挿入する必要があります。

このsysctlはモジュール自動ロードにのみ影響します。明示的にモジュールを挿入する能力には影響しません。

このsysctlはモジュールロードリクエストのデバッグに使用できます：

echo '#! /bin/sh' > /tmp/modprobe
echo 'echo "$@" >> /tmp/modprobe.log' >> /tmp/modprobe
echo 'exec /sbin/modprobe "$@"' >> /tmp/modprobe
chmod a+x /tmp/modprobe
echo /tmp/modprobe > /proc/sys/kernel/modprobe

代替として、このsysctlを空文字列に設定すると、モジュール自動ロードが完全に無効になります。カーネルはユーザーモードヘルパーを実行しようとせず、kernel_module_request LSM hookも呼びません。

カーネル構成にCONFIG_STATIC_USERMODEHELPER=yが設定されている場合、設定された静的ユーザーモードヘルパーオプションがこのsysctlを上書きします。ただし、空文字列は上記のようにモジュール自動ロードを完全に無効にするために依然として受け入れられます。

numa_balancing¶

自動ページフォールトベースのNUMAメモリバランスを有効/無効にします。メモリは、アクセス頻度が高いノードに自動的に移動します。

自動NUMAメモリバランスを有効/無効にします。NUMAマシンでは、CPUがリモートメモリをアクセスするとパフォーマンス低下が発生します。この機能を有効にすると、カーネルは定期的にページをアンマップして、どのタスクスレッドがメモリをアクセスしているかをサンプリングします。ページフォールト発生時に、アクセスしているデータがローカルメモリノードに移動すべきかどうかを判定します。

ページのアンマップとフォールトのトラップは追加のオーバーヘッドを生じますが、理想的にはメモリローカル性の向上によって補償されます。ただし、万全の保証はありません。ターゲットワークロードがすでにNUMAノードにバインドされている場合はこの機能を無効化すべきです。逆に、機能のシステムオーバーヘッドが高すぎる場合は、カーネルがNUMAヒントフォールトをサンプリングする頻度を制御する numa_balancing_scan_period_min_ms, numa_balancing_scan_delay_ms, numa_balancing_scan_period_max_ms, numa_balancing_scan_size_mb、およびnuma_balancing_settle_count sysctlsで調整できます。

numa_balancing_scan_period_min_ms, numa_balancing_scan_delay_ms, numa_balancing_scan_period_max_ms, numa_balancing_scan_size_mb¶

自動NUMAバランスは、タスクのアドレス空間をスキャンしてページをアンマップし、ページが適切に配置されているか、またはタスクが実行されているローカルメモリノードに移動すべきかを検出します。毎回「スキャン遅延」ごとに、タスクはアドレス空間内の次の「スキャンサイズ」数のページをスキャンします。アドレス空間の終わりに達した場合は、スキャナが再び最初から開始します。

「スキャン遅延」と「スキャンサイズ」の組み合わせによってスキャンレートが決まります。スキャン遅延が減少するとスキャンレートは増加します。スキャン遅延およびスキャンレートはすべてのタスクにおいて適応的であり、過去の挙動に依存します。ページが適切に配置されている場合、スキャン遅延は増加し、そうでない場合はスキャン遅延は減少します。「スキャンサイズ」は適応的ではありませんが、「スキャンサイズ」が高いほどスキャンレートも高くなります。

スキャンレートが高いとシステムオーバーヘッドが増加します。ページフォルトは捕捉され、データの移動が必要となる可能性があります。ただし、スキャンレートが高いほど、ワークロードのパターンが変化した場合にタスクのメモリがローカルノードに迅速に移動し、リモートメモリアクセスによるパフォーマンスへの影響を最小限に抑えます。これらのsysctlはスキャン遅延のしきい値とスキャンするページ数を制御します。

numa_balancing_scan_period_min_ms タスクの仮想メモリをスキャンするための最小時間（ミリ秒単位）です。これにより、各タスクの最大スキャンレートを制御します。

numa_balancing_scan_delay_ms タスクが初期化時にフォークする際の初期の「スキャン遅延」です。

numa_balancing_scan_period_max_ms タスクの仮想メモのスキャンにかかる最大時間（ミリ秒単位）です。これにより、各タスクの最小スキャンレートを制御します。

numa_balancing_scan_size_mb 1回のスキャンでスキャンするページ数（メガバイト単位）です。

sched_util_clamp_min_rt_default:¶

デフォルトではLinuxはパフォーマンスチューニングされています。これは、リアルタイムタスクが常に最高周波数で動作し、最も能力のある（最大容量を持つ）CPU（異質なシステムでは）で実行されるということを意味します。

Uclampは、すべてのリアルタイムタスクのリクエストされたuclamp.minをデフォルトで1024に設定することでこれを実現します。これにより、タスクが最高周波数で動作し、大きなCPUに偏って実行されるようにします。

このコントロールは、uclampを使用する際のデフォルト動作を管理者が変更できるようにします。特にバッテリー駆動デバイスでは、最大容量と周波数で動作するとエネルギー消費が増加し、バッテリー寿命が短くなる可能性があります。

このコントロールは、ユーザーがsched_setattr()システムコールでリクエストされたuclamp.min値を変更していないリアルタイムタスクに対してのみ有効です。

このコントロールは、上記で定義されたsched_util_clamp_minの範囲制約に逃げることはできません。

例えばもし

sched_util_clamp_min_rt_default = 800 sched_util_clamp_min = 600

その後、ブーストは600に制限されます。なぜなら、800は許容範囲[0:600]外だからです。これは例えば、省電力モードがsched_util_clamp_minを変更してすべてのブーストを一時的に制限する場合に発生します。この制限が解除されると、設定されたsched_util_clamp_min_rt_defaultが有効になります。

信頼性、可用性、サービス性¶

RASの概念¶

信頼性、可用性および保守性（RAS）は、サーバーの信頼性を測るための概念として用いられます。

信頼性

システムが正しい出力を生成する確率です。

  • 一般的には Mean Time Between Failures（MTBF）で測定されます

  • ハードウェアの障害を回避、検出、修理する機能によって向上しています

可用性

システムが特定の時間に稼働している確率です

  • 一般的には特定の期間におけるダウンタイムの割合で測定されます

  • 実行時においてハードウェアの障害を検出・修正するメカニズムを用います;

保守性（またはメンテナビリティ）

システムを修理または保守する際の簡易性と速さです

  • 一般的には Mean Time Between Repair（MTBR）で測定されます

RASの改善¶

システムのダウンタイムを減らすためには、ハードウェアのエラーを検出し、可能な限り実行時に修正する機能が必要です。また、ハードウェアの劣化を検出し、システム管理者がデータ損失やシステムダウンタイムを引き起こす前に部品の交換を行うように警告するメカニズムも提供する必要があります。

監視の対象となるメカニズムの中で、一般的なものは以下の通り:

  • CPU – 実行中の命令や L1/L2/L3 キャッシュでのエラーを検出;

  • メモリ – エラー訂正論理（ECC）を追加してエラーを検出・修正;

  • I/O – 送信データに CRC チェックサムを追加;

  • ストレージ – RAID、ジャーナルファイルシステム、チェックサム、自己監視・分析・報告技術（SMART）。

エラー検出の発生回数を監視することで、ハードウェアのエラー確率が増加しているかを特定でき、その場合、修正可能なエラーのうちに劣化したコンポーネントを交換する予防保守を行うことができます。

エラーの種類¶

現代のシステムで使用される大多数のメカニズムは、ビットパケットのエラー数がしきい値以下である場合にエラー訂正を可能にする技術（例: ハミングコード）を使用しています。エラー数がしきい値を超える場合、これらのメカニズムはエラーが発生したことを高い確率で示すことができますが、訂正することはできません。

また、使用されていないコンポーネントでエラーが発生することもあります。例えば、現在割り当てられていないメモリの一部です。

これにより、いくつかのエラーのカテゴリが定義されます:

  • 訂正可能なエラー（CE） - エラー検出メカニズムがエラーを検出し、修正しました。このようなエラーは通常致命的ではありませんが、一部のカーネルメカニズムにより、システム管理者が致命的とみなすこともできます。

  • 訂正不能なエラー（UE） - エラー訂正閾値を超えるエラーが発生し、システムが自動的に訂正できなかった場合。

  • 致命的エラー - システムの重要なコンポーネント（例：カーネルの一部がUEエラーによって破損した場合）でUEエラーが発生した場合、データ破損を防ぐ唯一確実な方法はマシンを停止または再起動することです。

  • 非致命的エラー - 使用されていないコンポーネント（例：電源オフ状態のCPUや未使用のメモリバンク）でUEエラーが発生した場合、システムは依然として動作し、ホットスペアが利用可能であれば影響を受けたハードウェアを置き換える可能性があります。

    また、ユーザー空間プロセスでエラーが発生した場合、そのプロセスを終了させてユーザー空間で再起動するのも可能です。

非致命的エラーの処理メカニズムは通常複雑で、システム管理者が望むポリシーを適用するためにはユーザー空間アプリケーションの支援が必要な場合があります。

不良ハードウェアコンポーネントの特定¶

ハードウェアの欠陥を検出するだけでは不十分で、システムは再び信頼性を確保するための最小限の交換可能な単位（MRU）を特定する必要があります。

そのためにはエラーロギング機能だけでなく、エラーメッセージをMRUのシルクスクリーンやコンポーネントラベルに変換するメカニズムも必要です。

ECCメモリ¶

前節で述べたように、ECCメモリにはエラー訂正に使用する追加のビットが含まれています。上記の例では、メモリモジュールが データ幅ビットを有し、 トータル幅ビットを有しています。エラー検出および訂正メカニズムに使用される追加の8ビットは、 syndrome12.

したがって、CPUがメモリコントローラーに データ幅ビットのワードを書き込む要求を出すと、メモリコントローラーはハミング符号や他のエラー訂正コード（例：SECDED+）を用いてリアルタイムで syndrome を計算し、 トータル幅 サイズのコードを生成します。このコードはメモリモジュールに書き込まれます。

読み込み時に、 トータル幅 ビットのコードは、書き込み時に使用した同じECCコードを用いて再び変換され、 データ幅 ビットのワードと syndromeビットのコードが生成されます。 データ幅 ビットのワードは、エラーが発生してもCPUに送信されます。

メモリコントローラーはさらに、 syndrome を確認し、エラーが発生したか、およびECCコードがそのエラーを修正できたかをチェックします。エラーが修正された場合、Corrected Error（CE）が発生し、修正できなかった場合はUncorrected Error（UE）が発生します。

CE/UEに関する情報は、メモリコントローラー内の特別なレジスタに保存され、BIOS、特定のCPU、またはLinux EDACドライバーによって読み取ることができます。x86 64ビットCPUでは、Machine Check Architecture（MCA）を介してこれらのエラーも取得可能です。3.

目的¶

以下の edac カーネルモジュールの目的は、Linuxで動作するコンピュータシステム内で発生するハードウェアエラーを検出・報告することです。

メモリ¶

メモリの補正可能なエラー（CE）と補正不能なエラー（UE）が主な収集対象のエラーです。これらタイプのエラーは、 edac_mc device.

CEイベントを検出すること、それらのイベントを収集し報告すること、 更新処理が完了した後でも新しい読者が即座に開始する可能性があるため、以下のコードは読者がいないと信頼してはならない。 ただし、将来のUEイベントの予測とは必ずしも関係ありません。CEイベントだけでも、データがまだ破損していないため、システムは継続して動作します。

ただし、CEを示すメモリモジュールの予防的なメンテナンスや、積極的な部品交換を行うことで、恐ろしいUEイベントやシステムのパニックの発生確率を減らすことができます。

他のハードウェア要素¶

EDACの新機能として、 edac_device デバイスのクラスは、カーネルの2.6.23バージョンで追加されました。

この新しいデバイスタイプにより、メモリ以外のECCハードウェア検出器の状態を収集し、sysfsインターフェースを通じてユーザー空間に提示することが可能になります。

一部のアーキテクチャでは、L1、L2、L3キャッシュ、DMAエンジン、ファブリックスイッチ、メインデータパススイッチ、インターコネクション、およびさまざまなハードウェアデータパスにECC検出器が搭載されています。ハードウェアが報告する場合、edac_deviceデバイスを構築してその状態をユーザー空間に提示することが可能です。

バージョン管理¶

EDACは、「コア」モジュール（edac_core.ko）といくつかのメモリコントローラー（MC）ドライバモジュールから構成されています。あるシステムでは、コアがロードされ、1つのMCドライバがロードされます。コアとMCドライバ（または edac_device ドライバ）には、それぞれのモジュールの現在のリリースレベルを反映する個別のバージョンがあります。

したがって、システムがどのバージョンを実行しているかを「報告」するには、COREのバージョンとMCドライバのバージョンの両方を報告する必要があります。

読み込み中¶

もし edac カーネルに静的リンクされていた場合、ロードは必要ありません。もし edac モジュールとして構築されていた場合、必要なモジュールをmodprobeでロードしてください。 edac 必要なモジュールをmodprobeでロードできます。依存関係によって必要なコアモジュールがロードされるはずです。

例:

$ modprobe amd76x_edac

両方の amd76x_edac.ko メモリ制御モジュールと edac_mc.ko コアモジュールをロードします。

  • dimm_mem_type - メモリタイプ属性ファイル

    この属性ファイルは、このcsrowに現在搭載されているメモリのタイプを表示します。通常はバッファードメモリまたはアンバッファードメモリのいずれかです。例:

    • Registered-DDR

    • Unbuffered-DDR

Sysfs設定¶

以下 /sys/devices/system/edac/pci 次の制御ファイルおよび属性ファイルがあります:

モジュールパラメータ¶

  • edac_mc_panic_on_ue - UEによるパニック制御ファイル

    修正不能なエラーはマシンのパニックを引き起こします。これは通常望ましいです。修正不能なエラーが発生した際に継続することは良くありません。修正できなかった内容が不明であり、オペレーティングシステムのコンテキストが破損している可能性があるため、継続するとさらなる破壊が発生する可能性があります。カーネルにMCEが設定されている場合、EDACはUEを常に検出しません。

    ロード時間:

    module/kernel parameter: edac_mc_panic_on_ue=[0|1]

    実行時間:

    echo "1" > /sys/module/edac_core/parameters/edac_mc_panic_on_ue

  • edac_mc_log_ue - UE制御ファイルのログ記録

    訂正不能なエラーを記述するカーネルメッセージを生成します。これらのエラーはシステムメッセージログシステムを通じて報告されます。UEログ記録が無効になってもUE統計情報は蓄積されます。

    ロード時間:

    module/kernel parameter: edac_mc_log_ue=[0|1]

    実行時間:

    echo "1" > /sys/module/edac_core/parameters/edac_mc_log_ue

  • edac_mc_log_ce - CE制御ファイルのログ記録

    訂正可能なエラーを記述するカーネルメッセージを生成します。これらのエラーはシステムメッセージログシステムを通じて報告されます。CEログ記録が無効になってもCE統計情報は蓄積されます。

    ロード時間:

    module/kernel parameter: edac_mc_log_ce=[0|1]

    実行時間:

    echo "1" > /sys/module/edac_core/parameters/edac_mc_log_ce

  • edac_mc_poll_msec - ポーリング周期制御ファイル

    エラー情報のポーリングにかかる時間（ミリ秒単位）。値が小さすぎるとリソースが無駄にされ、値が大きすぎると必要なエラー処理が遅れ、エラーの特定に必要な情報が失われる可能性があります。現在のデフォルトは1000ミリ秒（1秒ごと）です。すべての帯域を確保する必要があるシステムではこの値を増やすことができます。

    ロード時間:

    module/kernel parameter: edac_mc_poll_msec=[0|1]

    実行時間:

    echo "1000" > /sys/module/edac_core/parameters/edac_mc_poll_msec

  • panic_on_pci_parity - PCIパリティエラー時のパニック動作

    パリティエラーが検出された際のパニック動作を有効にするか無効にするかを設定します。

    モジュール/カーネルパラメータ:

    edac_panic_on_pci_pe=[0|1]

    有効:

    echo "1" > /sys/module/edac_core/parameters/edac_panic_on_pci_pe

    無効:

    echo "0" > /sys/module/edac_core/parameters/edac_panic_on_pci_pe

Nehalemおよび新しいIntel CPUでのEDAC APIの使用¶

古いIntelアーキテクチャでは、メモリコントローラーはNorth Bridgeチップセットの一部でした。Nehalem、Sandy Bridge、Ivy Bridge、Haswell、Sky Lakeおよび新しいIntelアーキテクチャでは、メモリコントローラー（MC）の強化版をCPU内に統合しました

この章では、新しいIntel CPUに搭載された強化されたメモリコントローラーの違いについて説明します。例えば i7core_edac, sb_edac および sbx_edac ドライバー

注意

Xeon E7プロセッサファミリでは、メモリコントローラー用に別個のチップ、Intel Scalable Memory Bufferを使用します。このようなファミリにはこのセクションは適用されません

  1. 1つのQuick Patch Interconnect（QPI）に対して1つのメモリコントローラーがあります。ドライバーでは、「ソケット」という用語は1つのQPIを指します。これは物理的なCPUソケットに関連しています

    各MCには3つの物理的な読み込みチャネル、3つの物理的な書き込みチャネル、3つの論理チャネルがあります。ドライバーでは現在、これらを単に3つのチャネルと見なしています。各チャネルには最大で3つのDIMMを搭載できます

    最小の単位はDIMMです。csrowに関する情報はありません。EDAC APIでは最小の単位をcsrowと見なすため、ドライバーはチャネル/DIMMを順番に異なるcsrowにマッピングします

    例えば、以下のレイアウトを想定します:

    Ch0 phy rd0, wr0 (0x063f4031): 2 ranks, UDIMMs
  dimm 0 1024 Mb offset: 0, bank: 8, rank: 1, row: 0x4000, col: 0x400
  dimm 1 1024 Mb offset: 4, bank: 8, rank: 1, row: 0x4000, col: 0x400
Ch1 phy rd1, wr1 (0x063f4031): 2 ranks, UDIMMs
  dimm 0 1024 Mb offset: 0, bank: 8, rank: 1, row: 0x4000, col: 0x400
Ch2 phy rd3, wr3 (0x063f4031): 2 ranks, UDIMMs
  dimm 0 1024 Mb offset: 0, bank: 8, rank: 1, row: 0x4000, col: 0x400

    ドライバーはこれを以下のようにマッピングします:

    csrow0: channel 0, dimm0
csrow1: channel 0, dimm1
csrow2: channel 1, dimm0
csrow3: channel 2, dimm0

    csrowごとに1つのDIMMをエクスポートします

    各QPIは異なるメモリコントローラーとしてエクスポートされます

  2. MCはテストドライバーにエラーを注入する機能を持っています。ドライバーはいくつかのエラー注入ノードを通じてこの機能を実装します:

    メモリエラーを注入するには、以下にあります。 /sys/devices/system/edac/mc/mc?/:

    • inject_addrmatch/*:

      エラー注入マスクレジスタを制御します。エラーコードに一致するアドレスの複数の特性を指定することが可能です：

      dimm = the affected dimm. Numbers are relative to a channel;
rank = the memory rank;
channel = the channel that will generate an error;
bank = the affected bank;
page = the page address;
column (or col) = the address column.

      上記の各値を「any」に設定することで、任意の有効な値に一致させることができます。

      ドライバの初期化時に、すべての値が「any」に設定されます。

      例えば、チャンネル、バンク、ページ、カラムをすべて任意に指定し、DIMM 2のランク1でエラーを生成するには：

              echo 2 >/sys/devices/system/edac/mc/mc0/inject_addrmatch/dimm
        echo 1 >/sys/devices/system/edac/mc/mc0/inject_addrmatch/rank

To return to the default behaviour of matching any, you can do::

        echo any >/sys/devices/system/edac/mc/mc0/inject_addrmatch/dimm
        echo any >/sys/devices/system/edac/mc/mc0/inject_addrmatch/rank
    • inject_eccmask:

      何ビットが問題を起こすかを指定します。

    • inject_section:

      どのECCキャッシュセクションにエラーが発生するかを指定します。

      3 for both
2 for the highest
1 for the lowest
    • inject_type:

      エラーの種類を指定します。これは以下のビットの組み合わせです：

      bit 0 - repeat
bit 1 - ecc
bit 2 - parity
    • inject_enable:

      0以外の値が書き込まれたときにエラー生成を開始します。

    すべてのinject変数は読み取れます。書き込みにはroot権限が必要です。

    データシートでは、inject_addrmatchに一致するアドレスへの書き込み後にエラーが生成されるものとされています。しかし、読み込みでもエラーが発生することがあります。

    例えば、以下のコードは、チャネル2上の任意のDIMM/アドレスでソケット0の書き込みアクセス時にエラーを生成します：

    echo 2 >/sys/devices/system/edac/mc/mc0/inject_addrmatch/channel
echo 2 >/sys/devices/system/edac/mc/mc0/inject_type
echo 64 >/sys/devices/system/edac/mc/mc0/inject_eccmask
echo 3 >/sys/devices/system/edac/mc/mc0/inject_section
echo 1 >/sys/devices/system/edac/mc/mc0/inject_enable
dd if=/dev/mem of=/dev/null seek=16k bs=4k count=1 >& /dev/null

    ソケット1の場合、上記のコマンドで「mc0」を「mc1」に置き換える必要があります。

    生成されたエラー メッセージは以下のようになります：

    EDAC MC0: UE row 0, channel-a= 0 channel-b= 0 labels "-": NON_FATAL (addr = 0x0075b980, socket=0, Dimm=0, Channel=2, syndrome=0x00000040, count=1, Err=8c0000400001009f:4000080482 (read error: read ECC error))

  3. 訂正済みエラー メモリレジスタカウンタ

    新しいMCには、メモリエラーをカウントするレジスタがあります。ドライバは、Registered DIMMを持つデバイスで訂正済みエラーを報告するためにこれらのレジスタを使用します。

    ただし、これらのカウンタはUnregistered DIMMでは動作しません。チップセットがUDIMMにも対応するカウンタを提供しているため（ただし、デフォルトのものより粒度が粗い）、ドライバはUDIMMメモリに対してこれらのレジスタを公開します。

    これらは、以下の内容を確認することで読み取れます： all_channel_counts/:

    $ for i in /sys/devices/system/edac/mc/mc0/all_channel_counts/*; do echo $i; cat $i; done
   /sys/devices/system/edac/mc/mc0/all_channel_counts/udimm0
   0
   /sys/devices/system/edac/mc/mc0/all_channel_counts/udimm1
   0
   /sys/devices/system/edac/mc/mc0/all_channel_counts/udimm2
   0

    ここでの動作は、同じDIMM番号で異なるcsrowでのエラーが同じカウンタをインクリメントすることです。したがって、このメモリマッピングでは：

    csrow0: channel 0, dimm0
csrow1: channel 0, dimm1
csrow2: channel 1, dimm0
csrow3: channel 2, dimm0

    ハードウェアは、csrow0、csrow2、csrow3のいずれかで最初のDIMMでのエラー時にudimm0をインクリメントします；

    ハードウェアは、csrow0、csrow2、csrow3のいずれかで2番目のDIMMでのエラー時にudimm1をインクリメントします；

    ハードウェアは、csrow0、csrow2、csrow3のいずれかで3番目のDIMMでのエラー時にudimm2をインクリメントします；

  4. 標準エラー カウンタ

    標準エラー カウンタは、ドライバがmcelogエラーを受信したときに生成されます。UDIMMではソフトウェアでカウントされるため、一部のエラーが失われる可能性があります。RDIMMでは、レジスタの内容を表示します。

ダイナミックデバッグ¶

はじめに¶

このドキュメントでは、動的デバッグ(dyndbg)機能の使い方について説明します。

動的デバッグは、カーネルコードを動的に有効/無効にして追加のカーネル情報を取得できるようにするための機能として設計されています。現在、もし CONFIG_DYNAMIC_DEBUG 設定されている場合、すべての pr_debug()/dev_dbg() および print_hex_dump_debug()/print_hex_dump_bytes() コールサイトごとに動的に有効にすることができます。

動的デバッグをグローバルに有効にしたくない場合（つまり、ある埋め込みシステムなどでは）、 CONFIG_DYNAMIC_DEBUG_CORE 動的デバッグの基本的なサポートとして設定し、 ccflags := -DDYNAMIC_DEBUG_MODULE 後で動的デバッグを行うモジュールのMakefileに追加します。

もし CONFIG_DYNAMIC_DEBUG 設定されていない場合、 print_hex_dump_debug() は単に print_hex_dump(KERN_DEBUG).

For print_hex_dump_debug()/print_hex_dump_bytes()、フォーマット文字列はその prefix_str 引数であり、それが定数文字列である場合；または hexdump 、動的に構築される場合 prefix_str は動的に構築されます。

動的デバッグにはさらに有用な機能があります：

  • シンプルなクエリ言語により、ソースファイル名、関数名、行番号（行番号の範囲を含む）、モジュール名、フォーマット文字列のいずれか0または1つ以上の組み合わせに一致させることで、デバッグステートメントをオン/オフできます：

    • ソースファイル名

    • 関数名

    • 行番号（行番号の範囲を含む）

    • モジュール名

    • フォーマット文字列

  • debugfs制御ファイルを提供します： <debugfs>/dynamic_debug/control を読み込むことで、すべての既知のデバッグステートメントの一覧を表示し、ガイドとして役立てることができます

動的デバッグの動作の制御¶

の動作は pr_debug()/dev_dbg() debugfsファイルシステム内の制御ファイルに書き込むことで制御されます。したがって、この機能を使用するには、まずdebugfsファイルシステムをマウントする必要があります。その後、制御ファイルは <debugfs>/dynamic_debug/controlとして参照します。たとえば、ソースファイル svcsock.c、行1603から出力する場合は、単に

nullarbor:~ # echo 'file svcsock.c line 1603 +p' >
                              <debugfs>/dynamic_debug/control

構文に誤りがある場合、書き込みが失敗します：

nullarbor:~ # echo 'file svcsock.c wtf 1 +p' >
                              <debugfs>/dynamic_debug/control
-bash: echo: write error: Invalid argument

注意：debugfsが有効になっていないシステムでは、制御ファイルは /proc/dynamic_debug/control.

動的デバッグの動作の表示¶

すべてのデバッグステートメントの現在の設定された動作を表示するには、

nullarbor:~ # cat <debugfs>/dynamic_debug/control
# filename:lineno [module]function flags format
net/sunrpc/svc_rdma.c:323 [svcxprt_rdma]svc_rdma_cleanup =_ "SVCRDMA Module Removed, deregister RPC RDMA transport\012"
net/sunrpc/svc_rdma.c:341 [svcxprt_rdma]svc_rdma_init =_ "\011max_inline       : %d\012"
net/sunrpc/svc_rdma.c:340 [svcxprt_rdma]svc_rdma_init =_ "\011sq_depth         : %d\012"
net/sunrpc/svc_rdma.c:338 [svcxprt_rdma]svc_rdma_init =_ "\011max_requests     : %d\012"
...

このデータに標準のUnixテキスト操作フィルタを適用することもできます。たとえば：

nullarbor:~ # grep -i rdma <debugfs>/dynamic_debug/control  | wc -l
62

nullarbor:~ # grep -i tcp <debugfs>/dynamic_debug/control | wc -l
42

3列目は、各デバッグステートメントコールサイトの現在有効なフラグを表示しています（フラグの定義については下記を参照してください）。フラグがすべて無効な場合のデフォルト値は =_です。したがって、任意の非デフォルトフラグを持つすべてのデバッグステートメントコールサイトを表示できます：

nullarbor:~ # awk '$3 != "=_"' <debugfs>/dynamic_debug/control
# filename:lineno [module]function flags format
net/sunrpc/svcsock.c:1603 [sunrpc]svc_send p "svc_process: st_sendto returned %d\012"

コマンド言語リファレンス¶

語彙レベルでは、コマンドはスペースまたはタブで区切られた単語のシーケンスからなります。したがって、これらはすべて同等です：

nullarbor:~ # echo -n 'file svcsock.c line 1603 +p' >
                              <debugfs>/dynamic_debug/control
nullarbor:~ # echo -n '  file   svcsock.c     line  1603 +p  ' >
                              <debugfs>/dynamic_debug/control
nullarbor:~ # echo -n 'file svcsock.c line 1603 +p' >
                              <debugfs>/dynamic_debug/control

コマンドの送信はwrite()システムコールによって境界付けられます。複数のコマンドは、セパレータで区切って一緒に書くことができます ; または \n:

~# echo "func pnpacpi_get_resources +p; func pnp_assign_mem +p" \
   > <debugfs>/dynamic_debug/control

クエリセットが大きい場合、バッチ処理も可能です：

~# cat query-batch-file > <debugfs>/dynamic_debug/control

もう一つの方法はワイルドカードを使用することです。マッチルールは、 * (ゼロまたは複数の文字に一致) および ? (ちょうど1つの文字に一致) をサポートしています。例えば、すべてのusbドライバをマッチさせることができます:

~# echo "file drivers/usb/* +p" > <debugfs>/dynamic_debug/control

構文レベルでは、コマンドはマッチ仕様のシーケンスに続いて、フラグ変更仕様を含みます:

command ::= match-spec* flags-spec

マッチ仕様は、既知の pr_debug() callsitesからフラグ仕様を適用するサブセットを選択するために使用されます。これらをクエリと考え、各ペア間には暗黙のANDが適用されます。注意点として、マッチ仕様の空リストはすべてのデバッグステートメントcallsitesを選択します。

マッチ仕様は、比較するcallsiteの属性を制御するキーワードと、比較対象の値を含みます。可能なキーワードは以下の通りです:

match-spec ::= 'func' string |
               'file' string |
               'module' string |
               'format' string |
               'line' line-range

line-range ::= lineno |
               '-'lineno |
               lineno'-' |
               lineno'-'lineno

lineno ::= unsigned-int

注意

line-range スペースを含めることはできません。例えば、「1-30」は有効な範囲ですが、「1 - 30」は有効ではありません。

各キーワードの意味は以下の通りです:

func

与えられた文字列は、各callsiteの関数名と比較されます。例:

func svc_tcp_accept
func *recv*             # in rfcomm, bluetooth, ping, tcp
ファイル

与えられた文字列は、各callsiteのsrc-root相対パス名、またはソースファイルのbasenameと比較されます。例:

file svcsock.c
file kernel/freezer.c   # ie column 1 of control file
file drivers/usb/*      # all callsites under it
file inode.c:start_*    # parse :tail as a func (above)
file inode.c:1-100      # parse :tail as a line-range (above)
module

与えられた文字列は、各callsiteのモジュール名と比較されます。モジュール名は、 lsmodで見られる文字列であり、ディレクトリや .ko サフィックスを除き、 - が変更されて _に置き換えられます。例:

module sunrpc
module nfsd
module drm*     # both drm, drm_kms_helper
format

与えられた文字列は、動的デバッグフォーマット文字列内で検索されます。注意点として、文字列は全体に一致する必要はなく、一部でもよいです。ホワイトスペースやその他の特殊文字は、Cのオクタル文字エスケープ記法を使用してエスケープできます。例えば、スペース文字は \ooo で表されます。 \040代わりに、文字列はダブルクォーテーション（"）またはシングルクォーテーション（'）で囲むこともできます。例:

format svcrdma:         // many of the NFS/RDMA server pr_debugs
format readahead        // some pr_debugs in the readahead cache
format nfsd:\040SETATTR // one way to match a format with whitespace
format "nfsd: SETATTR"  // a neater way to match a format with whitespace
format 'nfsd: SETATTR'  // yet another way to match a format with whitespace
line

与えられた行番号または行番号の範囲は、各 pr_debug() callsiteの行番号と比較されます。単一行番号はcallsiteの行番号と完全に一致します。行番号の範囲は、最初の行番号と最後の行番号の間の任意のcallsiteに一致します。最初の番号が空の場合、ファイルの最初の行を、最後の番号が空の場合、ファイルの最後の行を指します。例:

line 1603           // exactly line 1603
line 1600-1605      // the six lines from line 1600 to line 1605
line -1605          // the 1605 lines from line 1 to line 1605
line 1600-          // all lines from line 1600 to the end of the file

フラグ仕様は、変更操作に続いて1つ以上のフラグ文字を含みます。変更操作は以下のいずれかです:

-    remove the given flags
+    add the given flags
=    set the flags to the given flags

フラグは以下の通りです:

p    enables the pr_debug() callsite.
f    Include the function name in the printed message
l    Include line number in the printed message
m    Include module name in the printed message
t    Include thread ID in messages not generated from interrupt context
_    No flags are set. (Or'd with others on input)

For print_hex_dump_debug() および print_hex_dump_bytes()、のみ p フラグに意味があり、他のフラグは無視されます。

表示では、フラグの前に = (mnemonic: フラグが現在等しい値) が付きます。

正規表現 ^[-+=][flmpt_]+$ フラグ仕様に一致します。一度にすべてのフラグをクリアするには、 =_ または -flmpt.

ブートプロセス中のデバッグメッセージ¶

ブートプロセス中に、ユーザー空間やdebugfsが存在する前からコアコードおよび組み込みモジュールのデバッグメッセージを有効にするには、 dyndbg="QUERY", module.dyndbg="QUERY"（sleepable RCU）が導入されました。 ddebug_query="QUERY" (ddebug_query は廃止されています。 dyndbg、および非推奨です)。QUERYは上記の構文に従いますが、1023文字を超えてはなりません。ブートロー�ーダーによってはより厳しい制限が課される可能性があります。

これら dyndbg のパラメータは、ddebugテーブルが処理された後すぐに、early_initcallの一部として処理されます。これにより、このearly_initcall以降に実行されるすべてのコードにおけるデバッグメッセージを有効化できます。

x86システムでは例えばACPIの有効化はsubsys_initcallであり、

dyndbg="file ec.c +p"

が有効な場合、ACPIの設定中に早期の埋め込まれたコントローラーのトランザクションを表示します（通常はノートPCなど）。PCI（または他のデバイス）の初期化も、デバッグ目的でこのブートパラメータを使用する重要な候補です。

もし foo モジュールが内蔵されていない場合、 foo.dyndbg はブート時に処理されますが、効果はなく、後にモジュールがロードされるときに再処理されます。 ddebug_query= および裸 dyndbg= はブート時にのみ処理されます。

モジュール初期化時のデバッグメッセージ¶

が呼ばれるとき、modprobeは modprobe foo をスキャンし、 /proc/cmdline のために、 foo.paramsを削除し、 foo.をカーネルに渡します。modprobeの引数で指定されたパラメータや /etc/modprob.d/*.conf ファイル、以下の順序で処理されます：

  1. を介して指定されたパラメータ、 /etc/modprobe.d/*.conf:

    options foo dyndbg=+pt
options foo dyndbg # defaults to +p

  2. foo.dyndbg で指定されたものと、 foo. は削除され、渡されます：

    foo.dyndbg=" func bar +p; func buz +mp"

  3. modprobeの引数：

    modprobe foo dyndbg==pmf # override previous settings

これら dyndbg クエリは順番に適用され、最後のものが最終的なものです。これにより、ブート引数が～からのものを上書きまたは変更できます。 /etc/modprobe.d （合理的な理由で、1はシステム全体に適用され、2はカーネルまたはブートに特有です)、modprobeの引数でこれらを上書きできます。

～において、クエリは foo.dyndbg="QUERY" 形式では、クエリは module foo. foo はパラメータ名から抽出され、各クエリに適用され、各タイプごとに1つのマッチスペックのみが許可されます。 QUERYオプションは「偽」のモジュールパラメータであり、これは以下の意味を持ちます：

以下の dyndbg モジュールはこれを明示的に定義する必要がありません

  • すべてのモジュールは、pr_debugを使用するかどうかに関わらず、暗黙的に取得します

  • これは

  • には表示されません /sys/module/$module/parameters/ 確認するには、コントロールファイルをgrepして、または /proc/cmdline.

For CONFIG_DYNAMIC_DEBUG カーネルでは、ブート時に指定された設定（またはコンパイル時に～で有効化されたもの）は -DDEBUG flagで有効化されたもの）は、デバッグメッセージが不要になった場合、後でdebugfsインターフェースを通じて無効化できます：

echo "module module_name -p" > <debugfs>/dynamic_debug/control

例¶

// enable the message at line 1603 of file svcsock.c
nullarbor:~ # echo -n 'file svcsock.c line 1603 +p' >
                              <debugfs>/dynamic_debug/control

// enable all the messages in file svcsock.c
nullarbor:~ # echo -n 'file svcsock.c +p' >
                              <debugfs>/dynamic_debug/control

// enable all the messages in the NFS server module
nullarbor:~ # echo -n 'module nfsd +p' >
                              <debugfs>/dynamic_debug/control

// enable all 12 messages in the function svc_process()
nullarbor:~ # echo -n 'func svc_process +p' >
                              <debugfs>/dynamic_debug/control

// disable all 12 messages in the function svc_process()
nullarbor:~ # echo -n 'func svc_process -p' >
                              <debugfs>/dynamic_debug/control

// enable messages for NFS calls READ, READLINK, READDIR and READDIR+.
nullarbor:~ # echo -n 'format "nfsd: READ" +p' >
                              <debugfs>/dynamic_debug/control

// enable messages in files of which the paths include string "usb"
nullarbor:~ # echo -n '*usb* +p' > <debugfs>/dynamic_debug/control

// enable all messages
nullarbor:~ # echo -n '+p' > <debugfs>/dynamic_debug/control

// add module, function to all enabled messages
nullarbor:~ # echo -n '+mf' > <debugfs>/dynamic_debug/control

// boot-args example, with newlines and comments for readability
Kernel command line: ...
  // see whats going on in dyndbg=value processing
  dynamic_debug.verbose=1
  // enable pr_debugs in 2 builtins, #cmt is stripped
  dyndbg="module params +p #cmt ; module sys +p"
  // enable pr_debugs in 2 functions in a module loaded later
  pc87360.dyndbg="func pc87360_init_device +p; func pc87360_find +p"

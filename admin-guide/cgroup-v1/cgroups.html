1. 制御グループ¶

1.1 cgroupsとは？¶

Control Groupsは、タスクの集合とその将来の子タスクを、専用の動作を持つ階層グループに集約/分割するためのメカニズムを提供します。

定義:

A cgroup は、1つ以上のサブシステムのパラメータセットとタスクのセットを関連付けるものです。

A subsystem は、cgroupsが提供するタスクグループの機能を活用して、タスクのグループを特定の方法で処理するモジュールです。サブシステムは通常、「リソース制御器」として、リソースをスケジュールしたり、cgroupごとの制限を適用したりするものですが、プロセスのグループに対して何か処理を行いたい場合に使用することもできます（例：仮想化サブシステム）。

A hierarchy は、タスクの集合が階層内のcgroupのいずれかに必ず属するように配置されたcgroupの集合です。各cgroupにはサブシステムが関連付けられ、それぞれのサブシステムに階層内のcgroupごとにシステム固有の状態が付属します。各階層にはcgroup仮想ファイルシステムのインスタンスが関連付けられます。

いつでも複数のアクティブなタスクcgroup階層が存在する可能性があります。各階層はシステム内のすべてのタスクを分割します。

ユーザー側のコードは、cgroup仮想ファイルシステムのインスタンス内でcgroupを名前で作成・削除し、タスクがどのcgroupに属するかを指定・照会し、cgroupに割り当てられたタスクのPID一覧を取得できます。これらの作成や割り当ては、そのcgroupファイルシステムのインスタンスに関連付けられた階層にのみ影響します。

単独では、cgroupの用途は単純なジョブの追跡に限られます。意図は、他のサブシステムが汎用cgroupサポートを介してcgroupに新たな属性を提供することです（例：プロセスがcgroup内からアクセスできるリソースを記録・制限するなど）。cpusets（参照： CPUSETS)は、各cgroup内のタスクにCPUの集合とメモリノードの集合を関連付けることができます。

1.2 cgroupsが必要な理由¶

Linuxカーネル内でプロセスの集約を提供するための複数の取り組みがあり、主にリソースの追跡目的で行われています。このような取り組みにはcpusets、CKRM/ResGroups、UserBeanCounters、仮想サーバー名前空間などが含まれます。これらはすべて、プロセスをグループ化/パーティショニングする基本的な概念を必要とし、新たにフォークされたプロセスは親プロセスと同じグループ（cgroup）に属する必要があります。

カーネルのcgroupパッチは、このようなグループを効率的に実装するために必要な最小限のカーネルメカニズムを提供します。システムの高速パスへの影響は最小限であり、cpusetsなどの特定のサブシステムが追加の動作を提供するためのハックポイントも提供しています。

複数階層のサポートが提供されており、タスクをcgroupに分ける際の区分けが異なるサブシステムがある場合に役立ちます。並列階層を持つことで、各階層がタスクの自然な区分けとなるため、複数の無関係なサブシステムを同じcgroupツリーに強制的に組み込む必要がありません。

一方の極端では、各リソース制御またはサブシステムが個別の階層に配置され、もう一方の極端ではすべてのサブシステムが同じ階層に接続されます。

複数階層が役立つシナリオの例（元々vatsaによって提案されたものです）として、さまざまなユーザー（学生、教授、システムタスクなど）を持つ大規模な大学サーバーを考えてみましょう。 vatsa@の.ibm.comこのサーバーのリソース計画は以下のようになるかもしれません：

CPU :          "Top cpuset"
                /       \
        CPUSet1         CPUSet2
           |               |
        (Professors)    (Students)

        In addition (system tasks) are attached to topcpuset (so
        that they can run anywhere) with a limit of 20%

Memory : Professors (50%), Students (30%), system (20%)

Disk : Professors (50%), Students (30%), system (20%)

Network : WWW browsing (20%), Network File System (60%), others (20%)
                        / \
        Professors (15%)  students (5%)

Firefox/LynxなどのブラウザはWWWネットワーククラスに、(k)nfsdはNFSネットワーククラスに配置されます。

同時にFirefox/Lynxは、起動したユーザー（教授/学生）に応じて適切なCPU/Memoryクラスを共有します。

異なるリソースごとにタスクを異なるクラスに分類できる（リソースサブシステムを異なる階層に配置することで）ことで、管理者は実行通知を受け取るスクリプトを簡単に設定でき、ブラウザを起動したユーザーに応じて以下のような操作が可能になります：

# echo browser_pid > /sys/fs/cgroup/<restype>/<userclass>/tasks

単一の階層のみで、起動されたすべてのブラウザに別個のcgroupを作成し、適切なネットワークや他のリソースクラスと関連付ける必要があり、これによりこのようなcgroupの増殖が起こる可能性があります。

また、管理者が学生のブラウザに一時的にネットワークアクセスを強化する（夜でユーザーがオンラインゲームをするため）OR学生のシミュレーションアプリにCPU性能を強化するといったことも考えられます。

PIDをリソースクラスに直接書き込む機能があるため、単に以下を実行するだけで済みます:

# echo pid > /sys/fs/cgroup/network/<new_class>/tasks
(after some time)
# echo pid > /sys/fs/cgroup/network/<orig_class>/tasks

この機能がなければ、管理者はcgroupを複数の別個のものに分割し、その後で新しいcgroupを新しいリソースクラスに関連付ける必要がありました。

1.3 cgroupはどのように実装されていますか？¶

コントロールグループはカーネルを以下のように拡張します:

  • システム内の各タスクは、css_setへの参照カウントされたポインタを持っています。

  • css_setは、システムに登録されている各cgroupサブシステムに対応する参照カウントされたポインタを持つcgroup_subsys_stateオブジェクトのセットを含みます。タスクが所属するcgroupのヒエラルキーごとの直接的なリンクはありませんが、cgroup_subsys_stateオブジェクトを経由して確認できます。これは、サブシステム状態へのアクセスが頻繁に行われるため、パフォーマンスに影響を与えるコードで重要な処理であるためです。一方で、タスクの実際のcgroup割当（特にcgroup間の移動）はそれほど頻繁ではありません。タスク構造体のcg_listフィールドを経由してcss_setにリンクされた連想リストが存在します。

  • cgroupヒエラルキーのファイルシステムは、ユーザー空間から閲覧および操作するためにマウントできます。

  • 任意のcgroupにアタッチされているタスク（PIDで表示）の一覧を取得できます。

cgroupの実装には、カーネルの他の部分とのいくつかのシンプルな接続ポイントが必要で、パフォーマンスに影響を与えるパスには一切ありません:

  • init/main.cで、システム起動時にルートcgroupと初期css_setを初期化します。

  • forkおよびexit処理で、タスクをcss_setにアタッチまたはデタッチします。

さらに、タイプ「cgroup」の新しいファイルシステムをマウントすることで、カーネルに既知のcgroupを閲覧および編集できます。cgroupヒエラルキーをマウントする際には、ファイルシステムマウントオプションとしてコンマ区切りのサブシステムリストを指定できます。デフォルトでは、cgroupファイルシステムのマウントはすべての登録済みサブシステムを含むヒエラルキーをマウントしようとします。

すでに同じサブシステムセットを持つアクティブなヒエラルキーが存在する場合、新しいマウントに再利用されます。既存のヒエラルキーにマッチしない場合、かつリクエストされたサブシステムのうち少なくとも1つが既存のヒエラルキーで使用されている場合は、-EBUSYでマウントが失敗します。それ以外の場合は、リクエストされたサブシステムと関連付けて新しいヒエラルリーがアクティブになります。

現在、アクティブなcgroupヒエラルキーに新しいサブシステムをバインドするか、既存のサブシステムをアクティブなヒエラルキーからアンバインドすることはできません。今後は可能かもしれませんが、エラー回復に多くの問題が伴います。

cgroupファイルシステムがマウント解除された場合、トップレベルのcgroupの下に子cgroupが作成されている場合は、その階層はマウント解除されても依然としてアクティブのままになります。子cgroupが存在しない場合は、その階層は非アクティブになります。

cgroup用に新たなシステムコールは追加されません。すべてのクエリおよび設定機能は、このcgroupファイルシステムを通じて提供されます。

/proc以下の各タスクには、「cgroup」という名前のファイルが追加され、アクティブな各階層に対してサブシステム名と、cgroupファイルシステムのルートに対する相対パスとしてのcgroup名を表示します。

各cgroupは、cgroupファイルシステム内のディレクトリとして表され、以下のファイルでそのcgroupを記述します：

  • tasks: そのcgroupにアタッチされているタスク（PIDで表される）の一覧です。このリストは並び替えられず、このファイルにスレッドIDを書き込むことでスレッドをこのcgroupに移動させます。

  • cgroup.procs: そのcgroup内のスレッドグループIDの一覧です。このリストは並び替えられず、重複するTGIDを含む可能性があります。ユーザースペースでは、このプロパティが必要な場合はリストを並び替え、重複を除去する必要があります。このファイルにスレッドグループIDを書き込むことで、そのグループ内のすべてのスレッドをこのcgroupに移動させます。

  • notify_on_releaseフラグ: エクスイット時にリリースエージェントを実行するか？

  • release_agent: リリース通知に使用するパス（このファイルはトップcgroupのみに存在します）

cpusetsなどの他のサブシステムは、各cgroupディレクトリに追加のファイルを追加する可能性があります。

新しいcgroupはmkdirシステムコールまたはシェルコマンドで作成されます。cgroupのプロパティ（フラグなど）は、上記のリストに示す該当ファイルに書き込むことで変更されます。

ネストされたcgroupの名前付き階層構造により、大規模なシステムをネストされた、動的に変更可能な「ソフトパーティション」に分割できます。

各タスクのcgroupへのアタッチメント（そのタスクの子プロセスがフォーク時に自動的に継承）により、システム内のワークロードを関連するタスクのセットに整理できます。タスクは、必要なcgroupファイルシステムディレクトリのアクセス権が許可されている場合に、他の任意のcgroupに再アタッチ可能です。

タスクが一つのcgroupから別のcgroupに移動する際、新しいcss_setポインタが割り当てられます。既存のcss_setが目的のcgroupコレクションを含んでいる場合は再利用され、そうでない場合は新しいcss_setが割り当てられます。適切なcss_setはハッシュテーブルを参照して検索されます。

cgroupがcss_sets（およびその構成要素となるタスク）へのアクセスを許可するためには、cg_cgroup_linkオブジェクトの集合がラティスを形成します。各cg_cgroup_linkは、cgrp_link_listフィールドに所属する特定のcgroupに関するcg_cgroup_linksリストにリンクされ、cg_link_listフィールドに所属する特定のcss_setに関するcg_cgroup_linksリストにリンクされます。

したがって、cgroup内のタスク一覧を表示するには、そのcgroupを参照しているcss_setを順に走査し、各css_setのタスクセットをサブ走査することで実現できます。

Linux仮想ファイルシステム（vfs）をcgroupの階層構造として使用することで、cgroupに親しみやすいパーミッションと名前空間が提供され、追加のカーネルコードは最小限に抑えられます。

1.4 notify_on_releaseとは何ですか？¶

cgroupのnotify_on_releaseフラグが有効（1）になっている場合、そのcgroup内の最後のタスクが（終了したり、他のcgroupにアタッチしたり）離れ、そのcgroupの最後の子cgroupが削除されたとき、カーネルはその階層のルートディレクトリにある「release_agent」ファイルの内容を実行します。この実行には、cgroupファイルシステムのマウントポイントからの相対パスを指定します。これにより、無視されたcgroupの自動削除が可能になります。システム起動時のルートcgroupのnotify_on_releaseの初期値は無効（0）です。他のcgroupの初期値は、親のnotify_onの_release設定の現在値になります。cgroup階層のrelease_agentパスの初期値は空文字列です。

1.5 clone_childrenとは何ですか？¶

このフラグはcpusetコントローラーにのみ影響します。cgroupのclone_childrenフラグが有効（1）になっている場合、新しいcpuset cgroupは初期化時に親から構成情報をコピーします。

1.6 cgroupはどのように使用しますか？¶

cpusetコントローラーを使用して新しいジョブをcgroup内に含めるには、以下の手順が考えられます。

1) mount -t tmpfs cgroup_root /sys/fs/cgroup
2) mkdir /sys/fs/cgroup/cpuset
3) mount -t cgroup -ocpuset cpuset /sys/fs/cgroup/cpuset
4) Create the new cgroup by doing mkdir's and write's (or echo's) in
   the /sys/fs/cgroup/cpuset virtual file system.
5) Start a task that will be the "founding father" of the new job.
6) Attach that task to the new cgroup by writing its PID to the
   /sys/fs/cgroup/cpuset tasks file for that cgroup.
7) fork, exec or clone the job tasks from this founding father task.

例えば、以下のコマンドシーケンスは、CPU 2と3、メモリノード1を含む名前「Charlie」のcgroupを設定し、そのcgroup内でサブシェル「sh」を起動します。

mount -t tmpfs cgroup_root /sys/fs/cgroup
mkdir /sys/fs/cgroup/cpuset
mount -t cgroup cpuset -ocpuset /sys/fs/cgroup/cpuset
cd /sys/fs/cgroup/cpuset
mkdir Charlie
cd Charlie
/bin/echo 2-3 > cpuset.cpus
/bin/echo 1 > cpuset.mems
/bin/echo $$ > tasks
sh
# The subshell 'sh' is now running in cgroup Charlie
# The next line should display '/Charlie'
cat /proc/self/cgroup

2. 使用例と構文¶

2.1 基本的な使用方法¶

cgroupの作成、編集、使用はcgroup仮想ファイルシステムを通じて行えます。

すべてのサブシステムを含むcgroup階層をマウントするには、以下のように入力します。

# mount -t cgroup xxx /sys/fs/cgroup

「xxx」はcgroupコードによって解釈されませんが、/proc/mountsに表示されるため、好きな識別文字列として使用できます。

注意: 一部のサブシステムは、ユーザーからの入力がないと動作しません。例えば、cpusetsが有効になっている場合、ユーザーは各新規に作成されるcgroupが使用可能になる前に、cpusとmemsファイルを埋め込む必要があります。

セクション 1.2 cgroupsが必要な理由 あなたが制御したい単一のリソースまたはリソースグループごとに、異なるcgroupsの階層を作成する必要があります。そのためには、/sys/fs/cgroupにtmpfsをマウントし、各cgroupsリソースまたはリソースグループ用のディレクトリを作成してください:

# mount -t tmpfs cgroup_root /sys/fs/cgroup
# mkdir /sys/fs/cgroup/rg1

cpusetとmemoryサブシステムのみでcgroups階層をマウントするには、以下のように入力してください:

# mount -t cgroup -o cpuset,memory hier1 /sys/fs/cgroup/rg1

cgroupsの再マウントは現在サポートされていますが、推奨されません。再マウントはバインドされたサブシステムやrelease_agentを変更できるため、実用性は低いです。今後、再マウントのサポートは削除される予定です。

階層のrelease_agentを指定するには:

# mount -t cgroup -o cpuset,release_agent="/sbin/cpuset_release_agent" \
  xxx /sys/fs/cgroup/rg1

release_agentを複数回指定すると失敗します。

サブシステムのセットの変更は、現在は単一の（ルート）cgroupを含む階層にのみサポートされています。任意のサブシステムを既存のcgroup階層からバインド/アンバインドできる機能は今後実装される予定です。

/sys/fs/cgroup/rg1配下で、システム内のcgroupsの木に対応する木が確認できます。例えば、/sys/fs/cgroup/rg1は全体を保持するcgroupです。

release_agentの値を変更したい場合:

# echo "/sbin/new_release_agent" > /sys/fs/cgroup/rg1/release_agent

再マウントを通じて変更することも可能です。

/sys/fs/cgroup/rg1配下に新しいcgroupを作成したい場合:

# cd /sys/fs/cgroup/rg1
# mkdir my_cgroup

このcgroupに対して何か操作を行いたい場合:

# cd my_cgroup

このディレクトリにはいくつかのファイルがあります:

# ls
cgroup.procs notify_on_release tasks
(plus whatever files added by the attached subsystems)

このcgroupにシェルをアタッチします:

# /bin/echo $$ > tasks

このディレクトリ内でmkdirを使用して、cgroup内に別のcgroupを作成することも可能です:

# mkdir my_sub_cs

cgroupを削除するにはrmdirを使用してください:

# rmdir my_sub_cs

このcgroupが使用中（内部にcgroupが存在する、またはプロセスがアタッチされている、または他のサブシステム固有の参照で保持されている）場合、削除に失敗します。

2.2 プロセスのアタッチ¶

# /bin/echo PID > tasks

PID、ではなくPIDsです。一度に1つのタスクのみアタッチ可能です。複数のタスクをアタッチする場合は、順番に実行してください:

# /bin/echo PID1 > tasks
# /bin/echo PID2 > tasks
        ...
# /bin/echo PIDn > tasks

現在のシェルタスクをアタッチするには、0をエコーバックしてください:

# echo 0 > tasks

threadgroup内のすべてのスレッドを一度に移動するには、tasksファイルではなくcgroup.procsファイルを使用できます。threadgroup内の任意のタスクのPIDをcgroup.procsにエコーバックすると、そのthreadgroup内のすべてのタスクがcgroupにアタッチされます。cgroup.procsに0を書き込むと、書き込みタスクのthreadgroup内のすべてのタスクが移動します。

注意: すべてのタスクは常に各マウントされた階層に所属する正確に1つのcgroupにあります。現在のcgroupからタスクを削除するには、新しいcgroup（ルートcgroupを含む）に移動させる必要があります。そのためには、新しいcgroupのtasksファイルに書き込みます。

注意: 一部のcgroupサブシステムで強制される制限により、プロセスを別のcgroupに移動させる操作が失敗する場合があります。

2.3 階層の名前によるマウント¶

cgroups階層をマウントする際、name=<x>オプションを指定すると、指定した名前がその階層と関連付けられます。事前に存在する階層をマウントする際、アクティブなサブシステムのセットではなく名前で参照する際にこのオプションを使用できます。各階層は名前がありませんか、または一意の名前を持ちます。

名前は[w.-]+に一致する必要があります。

新しい階層にname=<x>オプションを指定する際には、サブシステムを手動で指定する必要があります。以前の動作として、明示的に指定されていない場合にすべてのサブシステムをマウントする動作は、サブシステムに名前を指定した場合にサポートされません。

サブシステムの名前は、/proc/mountsおよび/proc/<pid>/cgroups内の階層記述の一部として表示されます。

3. カーネルAPI¶

3.1 概要¶

カーネルのサブシステムが一般的なcgroupシステムに接続するには、cgroup_subsysオブジェクトを作成する必要があります。これは、cgroupシステムからのコールバックメソッドを含むとともに、cgroupシステムによって割り当てられるサブシステムIDを含みます。

cgroup_subsysオブジェクトの他のフィールドには以下のものがあります:

  • subsys_id: サブシステムの一意な配列インデックスで、cgroup->subsys[]配列のどのエントリを管理するかを示します。

  • name: 一意なサブシステム名に初期化する必要があります。MAX_CGROUP_TYPE_NAMELENを超えないようにしてください。

  • early_init: サブシステムがシステム起動時に早期初期化が必要かどうかを示します。

システムによって作成されるすべてのcgroupオブジェクトには、サブシステムIDでインデックスされるポインタの配列があります。このポインタはサブシステムによって完全に管理され、一般的なcgroupコードはこのポインタに触れることがありません。

3.2 同期¶

cgroupシステムでグローバルミューテックスcgroup_mutexが使用されます。cgroupを変更したい場合、このミューテックスを取得する必要があります。また、cgroupの変更を防ぐためにもこのミューテックスを取得できますが、その状況ではより特定的なロックがより適切である可能性があります。

詳細は kernel/cgroup.c を参照してください。

サブシステムは、cgroup_lock() および cgroup_unlock() 関数を通じて cgroup_mutex を取得/解放できます。

タスクの cgroup ポインタにアクセスする方法は次の通りです: - cgroup_mutex を保持している間 - タスクの alloc_lock を保持している間（task_lock() を通じて） - 以下のセクションを通じて rcu_read_lock() セクションを通じて rcu_dereference()

3.3 サブシステムAPI¶

各サブシステムは以下を行う必要があります:

  • linux/cgroup_subsys.h にエントリを追加する

  • cgroup_subsys オブジェクト <name>_cgrp_subsys を定義する

各サブシステムは以下のメソッドをエクスポートできます。必須メソッドは css_alloc/free です。他のメソッドで NULL の場合は、成功した無操作（no-op）とみなされます。

struct cgroup_subsys_state *css_alloc(struct cgroup *cgrp) (呼び出し元が保持している cgroup_mutex)

cgroup にサブシステム状態オブジェクトを割当てるための関数です。サブシステムは、渡された cgroup に対して自身のサブシステム状態オブジェクトを割当てる必要があります。成功時は新しいオブジェクトへのポインタを返し、失敗時は ERR_PTR() 値を返します。成功時は、cgroup_subsys_state 型（通常はより大きなサブシステム固有のオブジェクトに埋め込まれた）の構造体へのポインタをサブシステムポインタに設定します。このオブジェクトは cgroup システムによって初期化されます。注意: この関数は初期化時に呼び出され、このサブシステムのルートサブシステム状態を生成します。この場合、渡された cgroup オブジェクトの親が NULL であるため（階層のルートであるため）、初期化コードを実行する適切な場所です。

int css_online(struct cgroup *cgrp) (呼び出し元が保持している cgroup_mutex)

@cgrp がすべての割当を完了し、cgroup_for_each_child/descendant_*() イテレータに表示される後、呼び出されます。サブシステムは、-errno を返して作成を失敗させることが可能です。このコールバックは、階層における信頼性のある状態共有と伝播を実装するために使用できます。cgroup_for_each_descendant_pre() のコメントを参照してください。

void css_offline(struct cgroup *cgrp); (呼び出し元が保持している cgroup_mutex)

css_online() の対応処理であり、css_online() が @cgrp で成功した場合にのみ呼び出されます。これは @cgrp の終わりの始まりを示します。@cgrp が削除され始め、サブシステムは @cgrp に保持しているすべての参照を開始して解放する必要があります。すべての参照が解放されると、cgroup 削除は次のステップ - css_free() に進みます。このコールバック後は、@cgrp はサブシステムにとって死んだとみなされます。

void css_free(struct cgroup *cgrp) (呼び出し元が保持している cgroup_mutex)

cgroup システムが @cgrp を解放する直前です。サブシステムは自身のサブシステム状態オブジェクトを解放する必要があります。このメソッドが呼び出される時点で、@cgrp は完全に使用されておらず、@cgrp->parent はまだ有効です。（注意 - このサブシステムの create() メソッドが新しい cgroup に対して呼び出された後でエラーが発生した場合にも、新しい cgroup に対して呼び出される可能性があります。）

int can_attach(struct cgroup *cgrp, struct cgroup_taskset *tset) (呼び出し元が保持している cgroup_mutex)

1つ以上のタスクをcgroupに移動する前に呼び出されます。サブシステムがエラーを返す場合、このアタッチ操作は中止されます。@tsetにはアタッチするタスクが含まれており、少なくとも1つのタスクを含むことが保証されています。

タスクセットに複数のタスクがある場合、以下のことが保証されています。

  • すべてが同じスレッドグループから来ていることが保証されています。

  • @tsetには、cgroupを切り替えるかどうかに関わらず、そのスレッドグループからすべてのタスクが含まれています。

  • 最初のタスクがリーダーです。

各@tsetエントリにはタスクの古いcgroupも含まれており、cgroup_taskset_for_each()イテレータを使用することで、cgroupを切り替えていないタスクは簡単にスキップできます。注意点として、これはフォーク操作では呼び出されません。このメソッドが0（成功）を返す場合、呼び出し元がcgroup_mutexを保持している間は有効であり、今後attach()またはcancel_attach()が呼び出されることが保証されています。

void css_reset(struct cgroup_subsys_state *css) (呼び出し元が保持している cgroup_mutex)

この操作は@cgroupの設定を初期状態に戻すオプションです。現在は統合階層において、"cgroup.subtree_control"を通じてサブシステムが無効化された場合にのみ使用されますが、他のサブシステムに依存しているため有効なままにされるべきです。cgroupコアはこのようなcssを非表示にし、関連するインターフェースファイルを削除することで、このコールバックを呼び出して隠されたサブシステムが初期中立状態に戻るようします。これにより、隠されたcssからの予期せぬリソース制御を防ぎ、再度表示されるときに設定が初期状態になっていることを保証します。

void cancel_attach(struct cgroup *cgrp, struct cgroup_taskset *tset) (呼び出し元が保持している cgroup_mutex)

can_attach()が成功した後、タスクアタッチ操作が失敗したときに呼び出されます。can_attach()に副作用があるサブシステムは、この関数を提供してロールバックを実装する必要があります。提供しない場合は不要です。この関数は、can_attach()操作が成功したサブシステムについてのみ呼び出されます。パラメータはcan_attach()と同一です。

void attach(struct cgroup *cgrp, struct cgroup_taskset *tset) (呼び出し元が保持している cgroup_mutex)

タスクがcgroupにアタッチされた後、メモリ割当やブロッキングが必要なポストアタッチアクティビティを許可するために呼び出されます。パラメータはcan_attach()と同一です。

void fork(struct task_struct *task)

タスクがcgroupにフォークされたときに呼び出されます。

void exit(struct task_struct *task)

タスクの終了処理中に呼び出されます。

void free(struct task_struct *task)

タスク構造体が解放されたときに呼び出されます。

void bind(struct cgroup *root) (呼び出し元が保持している cgroup_mutex)

cgroupサブシステムが別の階層とルートcgroupに再バインドされたときに呼び出されます。現在は、デフォルト階層（サブ階層を持たない）と作成/破壊されている階層（サブ階層を持たない）の間での移動にのみ関与します。

4. 拡張属性の使用¶

cgroupファイルシステムは、ディレクトリおよびファイルに特定の種類の拡張属性をサポートしています。現在サポートされている種類は以下の通りです:

  • 信頼 (XATTR_TRUSTED)

  • セキュリティ (XATTR_SECURITY)

どちらも、設定にはCAP_SYS_ADMINの権限が必要です。

tmpfsと同様に、cgroupファイルシステムの拡張属性はカーネルメモリに保存され、使用量を最小限に保つことが推奨されます。これはユーザー定義の拡張属性がサポートされていない理由で、任意のユーザーが設定できる可能性があり、値のサイズに制限がないためです。

この機能を現在利用している主なユーザーは、コンテナ内のcgroup使用を制限するSELinuxと、cgroup内の主なPIDなどのメタデータを扱うsystemd（systemdはサービスごとにcgroupを作成します）です。

5. 質問¶

Q: what's up with this '/bin/echo' ?
A: bash's builtin 'echo' command does not check calls to write() against
   errors. If you use it in the cgroup file system, you won't be
   able to tell whether a command succeeded or failed.

Q: When I attach processes, only the first of the line gets really attached !
A: We can only return one error code per call to write(). So you should also
   put only ONE PID.

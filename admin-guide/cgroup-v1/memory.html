メモリリソースコンテラー¶

ノート:

このドキュメントは完全に古くなりすぎていて、完全な再構築が必要です。ただし、まだ有用な情報が含まれているためここに残していますが、より深い理解が必要な場合は現在のコードを確認してください。

ノート:

このドキュメントでは、メモリリソースコントローラーは一般的に「メモリコントローラー」と呼ばれていました。ここで使用するメモリコントローラーはハードウェアで使用されるメモリコントローラーとは区別してください。

(編集者向け) このドキュメントでは:

メモリコントローラーを使用するcgroup（cgroupfsのディレクトリ）を「メモリcgroup」と呼びます。git-logやソースコードで見かけると、パッチのタイトルや関数名は「memcg」をよく使用します。このドキュメントではその表現を避けています。

メモリコントローラーの利点と目的¶

メモリコントローラーは、タスクグループのメモリの挙動をシステムの他の部分から分離します。LWNの記事[12]ではメモリコントローラーの可能な用途がいくつか示されています。メモリコントローラーは以下の用途で使用できます。

  1. アプリケーションやアプリケーショングループを分離する メモリを多く消費するアプリケーションは、より少ないメモリに制限して分離できます。

  2. メモリ制限付きのcgroupを作成する；これはmem=XXXXで起動するよりも良い代替手段です。

  3. 仮想化ソリューションは、仮想マシンインスタンスに割り当てるメモリ量を制御できます。

  4. CD/DVDレーザーレコーダーは、焼録がメモリ不足で失敗しないように、システムの他の部分が使用するメモリ量を制御できます。

  5. 他の用途もいくつかあります；一つ見つけて使用するか、VMサブシステムを学習・ハッキングするための遊びとして利用してください。

現在の状態: linux-2.6.34-mmotm（2010年4月の開発版）

機能:

  • 匿名ページ、ファイルキャッシュ、スワップキャッシュの使用量を記録し、制限します。

  • ページは、各memcgごとのLRUにのみリンクされ、グローバルなLRUはありません。

  • オプションで、メモリ＋スワップの使用量を記録し、制限します。

  • 階層的な記録

  • ソフト制限

  • タスクを移動（再充電）する際のアカウント移動は選択可能です。

  • 使用量閾値通知

  • メモリ圧力通知

  • OOMキラーの無効化スイッチとOOM通知

  • ルートcgroupには制限設定はありません。

カーネルメモリサポートは進行中であり、現在のバージョンは基本的に機能を提供しています。（セクション2.7を参照）

1. 歴史¶

メモリ制御機能には長い歴史があります。Balbir Singh氏がメモリ制御機能に関する要望（RFC）を投稿したのがその始まりです[1]。RFC投稿当時、メモリ制御の実装はいくつか存在していました。RFCの目的は、メモリ制御に必要な最小限の機能について合意を形成することでした。最初のRSS制御機能は、Balbir Singh氏が2007年2月に投稿しました[2]。その後、Pavel Emelianov氏が3回にわたってRSS制御機能の実装を投稿しました[3][4][5]。OLSでのリソース管理に関するボフォートでは、ページキャッシュとRSSを一緒に扱うべきだという意見が示されました。また、ユーザー空間でのOOM処理を可能にする要望も出されました。現在のメモリ制御機能はバージョン6で、マップ済み（RSS）とマップ未済みページキャッシュの制御を統合しています[11]

2. メモリ制御¶

メモリは、他のリソースと異なり限定された量しか存在しません。タスクが大量のCPU処理を必要とする場合、その処理は数時間から数年単位で分散されることが可能ですが、メモリでは同じ物理メモリを再利用しなければなりません。

メモリ制御機能の実装はフェーズごとに分かれています。以下がそのフェーズです。

  1. メモリ制御

  2. mlock(2)制御

  3. カーネルユーザーメモリの会計およびスラブ制御

  4. ユーザーマッピング長制御

メモリ制御は最初に開発された制御機能です。

2.1. 設計¶

設計の中心は、page_counterと呼ばれるカウンターです。page_counterは、制御に関連するプロセスグループの現在のメモリ使用量と制限を追跡します。各cgroupにはメモリ制御機能専用のデータ構造（mem_cgroup）が関連付けられています。

2.2. 会計¶

     |  mem_cgroup        |
     |  (page_counter)    |

      /            ^      \
     /             |       \
+---------------+  |        +---------------+
| mm_struct     |  |....    | mm_struct     |
|               |  |        |               |
+---------------+  |        +---------------+
                   |
                   + --------------+
                                   |
+---------------+           +------+--------+
| page          +---------->  page_cgroup|
|               |           |               |
+---------------+           +---------------+

  (Figure 1: Hierarchy of Accounting)

図1は制御の重要な側面を示しています

  1. 会計はcgroupごとに実行されます

  2. 各mm_structは所属するcgroupを把握しています

  3. 各ページはpage_cgroupへのポインタを持ち、それにより所属するcgroupを把握します

会計は以下の通り行われます: mem_cgroup_charge_common()が呼び出され、必要なデータ構造が設定され、課金対象のcgroupが制限を超えていないかを確認します。制限を超えていた場合、reclaimがcgroupに対して呼び出されます。詳細についてはこのドキュメントのreclaimセクションをご参照ください。すべてが順調に進んだ場合、page_cgroupというページメタデータ構造が更新されます。page_cgroupにはcgroupごとのLRUが存在します。(*) page_cgroup構造体は起動時またはメモリホットプラグ時に割り当てられます。

2.2.1 会計の詳細¶

すべてのマップされた匿名ページ(RSS)とキャッシュページ(Page Cache)が会計されます。再利用不可能なページやLRUに含まれないページは会計されません。我々の目的は通常のVM管理下でのページの会計です。

RSSページはページフォールト時に会計されます（すでに以前に会計済みの場合は除きます）。ファイルページはinode（radix-tree）に挿入される際にPage Cacheとして会計されます。プロセスのページテーブルにマップされている間、重複した会計は慎重に回避されます。

RSSページは完全にアンマップされたときに会計が解除されます。PageCacheページはradix-treeから削除されたときに会計が解除されます。RSSページがkswapdによって完全にアンマップされても、システム内にSwapCacheとして存在し続けることがあります。このようなSwapCacheも会計されます。スワップインされたページはSwapCacheに追加された後に会計されます。

注意: カーネルはスワップインリードアヘッドを行い、複数のスワップを一度に読み込みます。memswが有効になっている場合、ページのmemcgはスワップに記録されるため、スワップイン後にページが会計されます。

ページの移動時に会計情報は保持されます。

注意: 我々の目的は使用中のページ数の制御であるため、LRUに含まれないページはVMの観点から制御が難しい傾向があります。

2.3 共有ページの会計¶

共有ページは最初の接触アプローチに基づいて会計されます。ページに最初に接触したcgroupがそのページを会計します。このアプローチの原則は、積極的に共有ページを使用するcgroupが最終的にそのページを課金されることです（これはメモリ圧力が発生した際に、そのページをもたらしたcgroupから課金が解除されるため）。

ただし、セクション8.2をご参照ください: タスクを別のcgroupに移動する際、move_charge_at_immigrateが選択された場合、そのページが新しいcgroupに再課金される可能性があります。

2.4 スワップ拡張¶

スワップの使用量はすべてのcgroupに対して記録されます。スワップ拡張により、使用量を読み取ったり制限したりできます。

CONFIG_SWAPが有効な場合、以下のファイルが追加されます。

  • memory.memsw.usage_in_bytes

  • memory.memsw.limit_in_bytes

memswはメモリ＋スワップを意味します。メモリ＋スワップの使用量はmemsw.limit_in_bytesで制限されます。

例: 4Gのスワップを持つシステムにおいて、2Gメモリ制限下で誤って6Gメモリを割り当てたタスクがスワップをすべて使用します。この場合、memsw.limit_in_bytes=3Gと設定することでスワップの悪用を防ぎ、スワップ不足によって引き起こされるシステムのOOMを回避できます。

なぜ「メモリ＋スワップ」なのか

グローバルLRU(kswapd)は任意のページをスワップアウトできます。スワップアウトとはメモリからスワップへアカウントを移動すること…メモリ＋スワップの使用量には変化がありません。言い換えれば、スワップの使用量を制限する際にグローバルLRUの影響を出さない場合、OSの観点から「メモリ＋スワップ」制限の方がスワップだけを制限するよりも優れています。

cgroupがmemory.memsw.limit_in_bytesに達した場合の挙動

cgroupがmemory.memsw.limit_in_bytesに達した場合、このcgroup内でスワップアウトを行うことは無駄です。そのため、cgroupのルーチンではスワップアウトが行われず、ファイルキャッシュが削除されます。ただし、上記のようにグローバルLRUはシステムのメモリ管理状態の健全性を保つためにスワップアウトを行うことができます。cgroupではこれを禁止することはできません。

2.5 回収¶

各cgroupは、グローバルVMと同じ構造を持つper cgroup LRUを保持しています。cgroupが制限を超えた場合、まずそのcgroupからメモリを回収し、新しいページを確保するためのスペースを作ります。回収が失敗した場合は、OOMルーチンが呼び出され、cgroup内の最もメモリを消費しているタスクが選ばれて終了します。(10. OOM制御を参照)

cgroup向けの回収アルゴリズムは変更されていません。ただし、回収対象のページはper-cgroup LRUリストから選ばれます。

ノート:

root cgroupでは回収が機能しません。root cgroupには制限を設定できませんからです。

注意2:

panic_on_oomが「2」に設定されている場合、システム全体がpanicします。

oomイベント通知レジスタが登録されている場合、イベントが通知されます。(oom_controlセクションを参照)

2.6 ロッキング¶

lock_page_cgroup()/unlock_page_cgroup()はi_pagesロック下で呼び出すべきではありません。

他のロック順序は以下の通り:

PG_locked.
mm->page_table_lock
pgdat->lru_lock

lock_page_cgroup.

多くの場合、lock_page_cgroup()のみが呼び出されます。

per-zone-per-cgroup LRU（cgroupのプライベートLRU）はpgdat->lru_lockで保護され、独自のロックは持ちません。

2.7 カーネルメモリ拡張（CONFIG_MEMCG_KMEM）¶

カーネルメモリ拡張機能により、メモリ制御装置はシステムが使用するカーネルメモリの量を制限することが可能になります。カーネルメモリはユーザーメモリとは根本的に異なり、スワップされないため、この貴重なリソースを過剰に消費することでシステムをDoS攻撃することが可能になります。

カーネルメモリの会計機能は、すべてのメモリcgroupでデフォルトで有効になっています。ただし、起動時にカーネルにcgroup.memory=nokmemを渡すことで、システム全体で無効にすることが可能です。この場合、カーネルメモリは一切会計されません。

ルートcgroupにはカーネルメモリの制限が課されません。ルートcgroupの使用量は会計されるかどうかは不定です。使用メモリはmemory.kmem.usage_in_bytesに累積されるか、必要に応じて別個のカウンターに記録されます（現在はTCPのみ対応）。

主な「kmem」カウンターは主なカウンターにフィードされるため、kmemの使用量はユーザーのカウンターからも確認可能です。

現在、カーネルメモリにはソフト制限が実装されていません。今後の作業として、これらの制限に達したときにslabの回収をトリガーする予定です。

2.7.1 現在のカーネルメモリリソースの会計¶

スタックページ:

すべてのプロセスは一部のスタックページを消費します。カーネルメモリの会計を行うことで、カーネルメモリの使用量が過剰な場合、新しいプロセスの作成を防ぐことができます。

slabページ:

SLABまたはSLUBアロケータによって割り当てられたページは追跡されます。memcg内でキャッシュが初めて触れたときに、各kmem_cacheのコピーが作成されます。この作成はラズリーに実行されるため、キャッシュ作成中には一部のオブジェクトはスキップされる可能性があります。slabページ内のすべてのオブジェクトは同じmemcgに属する必要があります。ただし、タスクがページ割り当て中に別のmemcgに移動した場合、この条件は満たされません。

ソケットメモリ圧力:

一部のソケットプロトコルにはメモリ圧力閾値があります。メモリ制御装置は、cgroupごとに個別に制御可能にし、グローバルに制御するのではなくします。

TCPメモリ圧力:

TCPプロトコルにおけるソケットメモリ圧力。

2.7.2 一般的な使用ケース¶

「kmem」カウンターが主なユーザーカウンターにフィードされるため、カーネルメモリはユーザーメモリとは完全に独立して制限することはできません。Uをユーザー制限、Kをカーネル制限とすると、制限の設定には以下の3つの可能性があります:

U ≠ 0、K = 無制限:

これはkmem会計が導入される前から存在する標準のmemcg制限メカニズムです。カーネルメモリは完全に無視されます。

U != 0, K < U:

カーネルメモリはユーザーメモリのサブセットです。この設定は、各cgroupあたりのメモリ総量が過剰割当されているデプロイメントで役立ちます。カーネルメモリの過剰割当は強く推奨されません。なぜなら、ボックスが非回収可能なメモリ不足になる可能性があるからです。このような場合、管理者はKを設定して、すべてのグループの合計が総メモリを超えないようにし、QoSを犠牲にしながらUを自由に設定できます。

警告:

現在の実装では、cgroupがKに達してもUを下回っている間はメモリ回収がトリガーされません。このため、この設定は現実的ではありません。

U != 0, K >= U:

kmemのチャージはユーザーカウンターにも反映されるため、cgroupに対して両種類のメモリの回収がトリガーされます。この設定により管理者はメモリの統一的なビューを得られ、また単にカーネルメモリ使用量を追跡したい人にとっても有用です。

3. ユーザーインターフェース¶

3.0. 設定¶

  1. CONFIG_CGROUPSを有効化

  2. CONFIG_MEMCGを有効化

  3. CONFIG_MEMCG_SWAPを有効化（swap拡張を使用する場合）

  4. CONFIG_MEMCG_KMEMを有効化（kmem拡張を使用する場合）

3.1. cgroupの準備（cgroups.txtを参照、なぜcgroupが必要なのか？）¶

# mount -t tmpfs none /sys/fs/cgroup
# mkdir /sys/fs/cgroup/memory
# mount -t cgroup none /sys/fs/cgroup/memory -o memory

3.2. 新しいグループを作成し、bashをその中に移動する:

# mkdir /sys/fs/cgroup/memory/0
# echo $$ > /sys/fs/cgroup/memory/0/tasks

現在0 cgroup内にいるため、メモリ制限を変更できます:

# echo 4M > /sys/fs/cgroup/memory/0/memory.limit_in_bytes
ノート:

「k, K, m, M, g, G」といったサフィックスを使用して、キロ、メガ、ギガバイトの値を示せます。（ここでのキロ、メガ、ギガはキビバイト、メビバイト、ギビバイトを指します。）

ノート:

「-1」と書くことで、 *.limit_in_bytes(unlimited).

ノート:

ルートcgroupにはもう制限を設定できません。

# cat /sys/fs/cgroup/memory/0/memory.limit_in_bytes
4194304

使用状況を確認できます:

# cat /sys/fs/cgroup/memory/0/memory.usage_in_bytes
1216512

このファイルへの成功した書き込みは、このファイルに書かれた値で制限を設定したことを保証しません。これはページ境界への四捨五入やシステム全体のメモリの利用可能性などの複数の要因によるものです。ユーザーは書き込み後にこのファイルを再読み込みして、カーネルが実際に適用した値を確認する必要があります:

# echo 1 > memory.limit_in_bytes
# cat memory.limit_in_bytes
4096

memory.failcntフィールドは、cgroup制限を超過した回数を示します。

memory.statファイルはアカウント情報です。現在、キャッシュ、RSS、アクティブページ/非アクティブページの数が表示されます。

4. テスト¶

機能や実装のテストについてはmemcg_test.txtを参照してください。

パフォーマンステストも重要です。純粋なメモリコントローラーのオーバーヘッドを確認するには、tmpfsでのテストが良い結果をもたらします。例: tmpfs上でカーネルのmakeを実行します。

ページフォールトのスケーラビリティも重要です。並列ページフォールトテストを測定する際、マルチプロセステストの方がマルチスレッドテストよりノイズが少なく良い結果が得られます。

しかし、上記の2つは極端な状況のテストです。メモリコントローラー下での通常のテストは常に役立ちます。

4.1 トラブルシューティング¶

ユーザーがcgroup内のアプリケーションがOOMキラーによって終了することを発見する場合があります。その原因はいくつかあります：

  1. cgroupの制限が低すぎる（実用的な動作ができないほど低すぎる）

  2. ユーザーが匿名メモリを使用しており、スワップがオフになっているか、または容量が十分でない

syncコマンドを実行し、echo 1 > /proc/sys/vm/drop_cachesを実行することで、cgroup内のキャッシュされたページ（ページキャッシュページ）をいくつか削除できます。

発生した原因を把握するには、「10. OOM制御」（下記）に従ってOOM_Killを無効にして、その後の挙動を確認すると役立ちます。

4.2 タスクの移動¶

タスクが1つのcgroupから別のcgroupに移動する場合、デフォルトではそのタスクの負担（charge）は引き継がれません。元のcgroupから割り当てられたページは依然としてそのタスクに負担として残り、ページが解放されたり回収されたりすると負担は解除されます。

タスクの負担をタスクの移動と同時に移動させることができます。8.「タスク移動時の負担移動」を参照してください。

4.3 cgroupの削除¶

rmdirコマンドでcgroupを削除できますが、4.1および4.2節で説明したように、すべてのタスクがそのcgroupから移動した後でも、ページに対して負担を課すため、そのcgroupに負担が残っている可能性があります。（タスクではなくページに対して負担を課すためです。）

統計情報をルート（use_hierarchy==0の場合）または親（use_hierarchy==1の場合）に移動し、子からの負担解除以外には負担の変更はありません。

swap情報に記録された負担はcgroupの削除時に更新されません。記録された情報は破棄され、swapを使用するcgroup（swapcache）はその新しい所有者として負担が課されます。

use_hierarchyについての詳細は、セクション6を参照してください。

5. その他のインターフェース¶

5.1 force_empty¶

memory.force_emptyインターフェースは、cgroupのメモリ使用量を空にするために提供されています。このインターフェースに何かを書き込むと：

# echo 0 > memory.force_empty

cgroupが回収され、可能な限り多くのページが回収されます。

このインターフェースの典型的な使用ケースはrmdir()を呼び出す前です。rmdir()はmemcgをオフラインにしますが、ファイルキャッシュの負担によりmemcgがまだ存在する可能性があります。一部の非使用中のページキャッシュはメモリ圧力が発生するまで負担を保持する場合があります。その回避を目的とする場合はforce_emptyが役立ちます。

また、memory.kmem.limit_in_bytesが設定されている場合でも、カーネルページの負担は依然として表示されます。これは失敗とは見なされず、書き込みは成功します。この場合、memory.kmem.usage_in_bytes == memory.usage_in_bytesが期待されます。

use_hierarchyについての詳細は、セクション6を参照してください。

5.3 swappiness¶

特定のグループに対して/proc/sys/vm/swappinessを上書きします。ルートcgroupのtunableはグローバルなswappiness設定に対応します。

グローバルなreclaimとは異なり、limit reclaimでは0のswappinessがスワップストレージが利用可能であっても、一切のスワップを防ぐため、メモリcgroupのOOM killerが発生する可能性があります。これはファイルページが存在しない場合に特に起こります。

5.4 failcnt¶

メモリcgroupはmemory.failcntとmemory.memsw.failcntというファイルを提供します。failcnt(==失敗回数)は使用量カウンターが制限に達した回数を示します。メモリcgroupが制限に達した場合、failcntが増加し、その下位にあるメモリが回収されます。

failcntをリセットするにはfailcntファイルに0を書き込みます:

# echo 0 > .../memory.failcnt

5.5 usage_in_bytes¶

効率化のため、他のカーネルコンポーネント同様に、メモリcgroupは不要なキャッシュラインの偽共有を避けるための最適化を行います。usage_in_bytesはその方法に影響を受け、正確なメモリ(およびスワップ)使用量を示すわけではありません。これは効率的なアクセスのために用いられる「近似値」です。(もちろん、必要に応じて同期されます。)正確なメモリ使用量を知りたい場合は、memory.stat(5.2を参照)のRSS+CACHE(+SWAP)値を使用してください。

5.6 numa_stat¶

これはnuma_mapsと似ていますが、メモリcgroupごとに動作します。メモリcgroup内でのNUMAローカル性情報を可視化するために有用です。ページは任意の物理ノードから割り当てられるためです。一つの用途例は、この情報とアプリケーションのCPU割当を組み合わせてアプリケーションのパフォーマンスを評価することです。

各memcgのnuma_statファイルには、「total」「file」「anon」「unevictable」それぞれのノードごとのページ数が含まれ、「hierarchical_<counter>」はメモリcgroup自身の値に加えて、すべての階層子の値を合計したものです。

memory.numa_statの出力形式は:

total=<total pages> N0=<node 0 pages> N1=<node 1 pages> ...
file=<total file pages> N0=<node 0 pages> N1=<node 1 pages> ...
anon=<total anon pages> N0=<node 0 pages> N1=<node 1 pages> ...
unevictable=<total anon pages> N0=<node 0 pages> N1=<node 1 pages> ...
hierarchical_<counter>=<counter pages> N0=<node 0 pages> N1=<node 1 pages> ...

「total」カウントはfile + anon + unevictableの合計です。

6. ハイエラルサポート¶

メモリコントローラーは深い階層と階層別会計をサポートします。階層はcgroupファイルシステムで適切なcgroupを作成することで構築されます。例えば、以下のcgroupファイルシステム階層を考慮してください:

    root
  /  |   \
 /   |    \
a    b     c
           | \
           |  \
           d   e

上記の図では、階層的なアカウントが有効になっている場合、eのすべてのメモリ使用量はその祖先（つまりcとルート）にまでアカウントされ、memory.use_hierarchyが有効になっているルート（cとルート）にアカウントされます。もし一つの祖先がその制限を超えた場合、回収アルゴリズムはその祖先および祖先の子タスクからメモリを回収します。

6.1 階層的なアカウントと回収の有効化¶

メモリcgroupはデフォルトで階層機能を無効化しています。サポートを有効化するには、ルートcgroupのmemory.use_hierarchyファイルに1を書き込みます：

# echo 1 > memory.use_hierarchy

この機能は以下のように無効化できます：

# echo 0 > memory.use_hierarchy
注意1：

cgroupに既に他のcgroupが作成されている場合、または親cgroupがuse_hierarchyを有効にしている場合、有効化／無効化が失敗します。

注意2：

panic_on_oomが「2」に設定されている場合、任意のcgroup内でOOMイベントが発生すると、全体システムがpanicします。

7. ソフト制限¶

ソフト制限はメモリの共有をより多く可能にします。ソフト制限の考え方は、制御グループが必要な分だけメモリを使用できるようにすることを目的とし、

  1. メモリの競合が発生していないこと

  2. ハード制限を超えないこと

システムがメモリの競合や低メモリを検出すると、制御グループはソフト制限に戻されます。各制御グループのソフト制限が非常に高い場合、他の制御グループがメモリを奪われることを防ぐために最大限に制限されます。

ソフト制限はベストエフォート機能であり、保証はありませんが、メモリが強く競合している場合、ソフト制限のヒント／設定に基づいてメモリが割り当てられることを目的としています。現在、ソフト制限ベースの回収はbalance_pgdat（kswapd）から呼び出されます。

7.1 インターフェース¶

ソフト制限は以下のコマンドを使用して設定できます（この例ではソフト制限を256 MiBと仮定します）：

# echo 256M > memory.soft_limit_in_bytes

この値を1Gに変更したい場合は、いつでも以下のコマンドを使用できます：

# echo 1G > memory.soft_limit_in_bytes
注意1：

ソフト制限はメモリcgroup間のバランスを取るためにメモリを回収するため、長期間にわたって効果を発揮します。

注意2：

ソフト制限はハード制限よりも常に下に設定することをお勧めします。そうでない場合、ハード制限が優先されます。

8. タスク移動時のチャージ移動¶

ユーザーはタスクの移動とともにそのタスクに関連するチャージを移動させることができます。つまり、古いcgroupからタスクのページをアンチャージし、新しいcgroupにチャージします。この機能は!CONFIG_MMU環境ではページテーブルの欠如のためサポートされていません。

8.1 インターフェース¶

この機能はデフォルトで無効です。有効化（および再無効化）には、宛先cgroupのmemory.move_charge_at_immigrateに書き込みます。

これを有効にする場合は:

# echo (some positive value) > memory.move_charge_at_immigrate
注意:

move_charge_at_immigrateの各ビットは、何種類かのチャージが移動すべきタイプについての意味を持っています。詳しくは8.2節をご参照ください。

注意:

チャージは、mm->ownerを移動するときだけ移動されます。言い換えれば、スレッドグループのリーダーです。

注意:

タスクを目的のcgroupに移動する際、十分なスペースが確保できない場合、メモリを回収してスペースを確保しようとします。十分なスペースが確保できない場合、タスクの移動が失敗する可能性があります。

注意:

多くのチャージを移動する場合、数秒かかることがあります。

再度無効にする場合は:

# echo 0 > memory.move_charge_at_immigrate

8.2 移動可能なチャージの種類¶

move_charge_at_immigrateの各ビットは、何種類かのチャージが移動すべきタイプについての意味を持っています。ただし、いずれにせよ、ページまたはスワップのアカウントを移動するには、そのチャージがタスクの現在（旧）メモリcgroupに課されている必要があります。

ビット

何種類のチャージが移動するか？

0

ターゲットタスクが使用する匿名ページ（またはそのスワップ）のチャージ。Swap拡張（2.4節を参照）を有効にする必要があります。

1

ターゲットタスクがmmappedしたファイルページ（通常ファイル、tmpfsファイル（例: ipc共有メモリ）、tmpfsファイルのスワップ）のチャージ。匿名ページの場合とは異なり、タスクがページフォールトを行わなくても、タスクがマップしている範囲のファイルページ（およびスワップ）が移動される可能性があります。つまり、タスクの「RSS」でない他のタスクの「RSS」でも移動される可能性があります。また、ページのmapcountは無視されます（page_mapcount(page) > 1であってもページを移動できます）。Swap拡張（2.4節を参照）を有効にする必要があります。

9. メモリ閾値¶

メモリcgroupは、cgroups通知API（cgroups.txtを参照）を使用してメモリ閾値を実装しています。これにより、複数のメモリおよびmemsw閾値を登録し、閾値を越えたときに通知を受け取ることができます。

閾値を登録するには、アプリケーションは以下の手順を実行する必要があります：

  • eventfd(2)を使用してイベントfdを作成します。

  • memory.usage_in_bytesまたはmemory.memsw.usage_in_bytesを開きます。

  • cgroup.event_controlに「<event_fd> <memory.usage_in_bytesのfd> <閾値>」という文字列を書き込みます。

アプリケーションは、メモリ使用量が閾値を越えたときにeventfdを通じて通知されます。

rootおよび非rootのcgroupに適用可能です。

10. OOM制御¶

memory.oom_controlファイルはOOM通知およびその他の制御に使用されます。

メモリcgroupは、cgroup通知API（cgroups.txtを参照）を使用してOOM通知を実装しています。これにより、複数のOOM通知配信を登録し、OOMが発生したときに通知を受け取ることができます。

通知を登録するには、アプリケーションは以下が必要です:

  • eventfd(2)を使用してeventfdを作成する

  • memory.oom_controlファイルを開く

  • 「<event_fd> <memory.oom_controlのfd>」という文字列をcgroup.event_controlに書き込む

OOMが発生した場合、アプリケーションはeventfdを通じて通知されます。root cgroupではOOM通知は動作しません。

memory.oom_controlファイルに「1」を書き込むことでOOM-killerを無効化できます。以下のように:

#echo 1 > memory.oom_control

OOM-killerが無効化されている場合、cgroup内のタスクは、accountable memoryを要求した際にmemory cgroupのOOM-waitqueueで待機/スリープします。

それらを実行するには、memory cgroupのOOM状態を緩和する必要があります

  • 制限を拡大するか、使用量を減らすか。

使用量を減らすには、

  • いくつかのタスクを終了する。

  • アカウントの移行を伴って他のグループにいくつかのタスクを移動する。

  • いくつかのファイルを削除する (tmpfs上？)

その後、停止したタスクは再び動作します。

読み込み時に、現在のOOM状態が表示されます。

  • oom_kill_disable 0または1 (1の場合はOOM-killerが無効化されています)

  • under_oom 0または1 (1の場合はmemory cgroupがOOM状態で、タスクが停止される可能性があります)

11. メモリ圧力¶

圧力レベルの通知は、メモリの割当コストを監視するために使用できます。圧力に基づいて、アプリケーションはメモリリソースの管理戦略を異なる方法で実装できます。圧力レベルは以下の通り定義されています:

「low」レベルは、システムが新しい割当のためにメモリを回収していることを意味します。この回収活動を監視することは、キャッシュレベルの維持に役立つ可能性があります。通知を受けた場合、プログラム（通常は「Activity Manager」）はvmstatを分析し、早めに不必要なサービスを停止するなどの行動を取るかもしれません。

「medium」レベルは、システムが中程度のメモリ圧力を経験していることを意味します。システムはスワップを行い、アクティブなファイルキャッシュをページアウトするなどする可能性があります。このようなイベントが発生した場合、アプリケーションはvmstat/zoneinfo/memcgや内部メモリ使用統計をさらに分析し、簡単に再構築またはディスクから再読み込み可能なリソースを解放するかどうかを決定するかもしれません。

「critical」レベルは、システムが積極的にスラッシングしており、メモリ不足（OOM）に近づいているか、あるいはカーネル内でのOOMキラーがトリガーされるところまで来ていることを意味します。アプリケーションはシステムを助けるためにできる限りの行動を取るべきです。vmstatや他の統計情報に相談する時間はすでに過ぎている可能性があるため、即座の行動を取ることが推奨されます。

デフォルトでは、イベントは上位に伝播し続け、イベントが処理されるまでです。つまり、イベントは透過しません。例えば、3つのcgroups（A→B→C）があるとします。このとき、cgroups A、B、Cにイベントリスナーを設定し、グループCでメモリ圧力が発生した場合、通知を受けるのはグループCのみで、グループAとBは通知を受けません。これは、メッセージの過剰なブロードキャストを防ぐためで、特にメモリが不足している場合やスワップが頻繁に行われる状態ではシステムに悪影響を及ぼすためです。グループBが通知を受けるのは、グループCにイベントリスナーが存在しない場合に限ります。

3つのオプションモードがあり、それぞれ異なる伝播動作を指定します:

  • 「default」: 上記のデフォルト動作です。このモードはオプションモードパラメータを省略した場合と同じ動作であり、後方互換性を保持しています。

  • 「hierarchy」: イベントは常にルートにまで伝播します。これはデフォルト動作と似ていますが、各レベルにイベントリスナーが存在するかどうかに関係なく伝播が続く点が異なります。上記の例では、グループA、B、Cすべてにメモリ圧力の通知が届きます。

  • 「local」: イベントは透過します。つまり、通知が登録されたmemcgでメモリ圧力が発生したときにのみ通知を受けます。上記の例では、グループCに「local」通知が登録されていればグループCが通知を受けますが、グループBが「local」通知を登録していても、グループBは決して通知を受けません。

レベルとイベント通知モード（「hierarchy」または「local」）はカンマで区切られた文字列で指定します。つまり、「low,hierarchy」は階層的な透過通知をすべての先祖memcgに指定します。デフォルトの非透過動作はモードを指定しません。「medium,local」はmediumレベルでの透過通知を指定します。

memory.pressure_levelファイルはイベントfdの設定にのみ使用されます。通知を登録するにはアプリケーションは:

  • eventfd(2)を使用してイベントfdを作成します。

  • memory.pressure_levelを開く;

  • cgroup.event_controlに「<event_fd> <memory.pressure_levelのfd> <level[,mode]>」という文字列を書き込む;

アプリケーションは特定のレベル（またはそれ以上のレベル）でメモリ圧力が発生したときにeventfdを通じて通知されます。memory.pressure_levelへの読み書き操作は実装されていません。

テスト:

新しいcgroupを作成し、メモリ制限を設定し、cgroup内の通知を設定し、その後子cgroupがcritical pressureを経験する小さなスクリプトの例:

# cd /sys/fs/cgroup/memory/
# mkdir foo
# cd foo
# cgroup_event_listener memory.pressure_level low,hierarchy &
# echo 8000000 > memory.limit_in_bytes
# echo 8000000 > memory.memsw.limit_in_bytes
# echo $$ > tasks
# dd if=/dev/zero | read x

(多数の通知が予想され、最終的にoom-killerがトリガーされます。)

  3. 制限がまだ達成されていないが使用量が近づいている場合でも、バックグラウンドで回収を開始する

Summary¶

全体的に、メモリコントローラーは安定したコントローラーであり、コミュニティ内で幅広くコメントされ議論されてきました。

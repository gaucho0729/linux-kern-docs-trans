1. Cpusets¶

1.1 Cpusetsとは何ですか？¶

Cpusetsは、タスクにCPUとメモリノードのセットを割り当てるメカニズムを提供します。このドキュメントでは「メモリノード」とは、メモリを含むオンラインのノードを指します。

Cpusetsは、タスクのCPUおよびメモリの配置を、タスクの現在のcpuset内に限定します。これらは仮想ファイルシステムでネストされた階層構造を形成しており、大規模システムにおける動的ジョブ配置を管理するために必要な、既存の機能を超えた基本的なハックです。

Cpusetsは、一般的なcgroupサブシステムを使用しており、 制御グループ（Control Groups）.

タスクがsched_setaffinity(2)システムコールを使用してCPUをCPUアフィニティマスクに含めたり、mbind(2)およびset_mempolicy(2)システムコールを使用してメモリノードをメモリポリシーに含める場合、これらのリクエストはタスクのcpusetを通じてフィルタリングされます。cpusetに含まれないCPUやメモリノードは除外され、スケジューラはタスクのcpus_allowedベクターに許可されていないCPU上でタスクをスケジュールしません。カーネルのページアロケータは、タスクのmems_allowedベクターに許可されていないノード上でページを割り当てません。

ユーザー空間のコードは、cgroup仮想ファイルシステム内でcpusetsを名前で作成および削除し、これらのcpusetsの属性と権限、割り当てられるCPUおよびメモリノードを管理し、タスクがどのcpusetに割り当てられているかを指定および照会し、cpusetに割り当てられたタスクのpid一覧を表示できます。

1.2 Cpusetsが必要なのはなぜですか？¶

多くのプロセッサ（CPU）、複雑なメモリキャッシュ階層、複数の非均一アクセス時間を持つメモリノード（NUMA）を持つ大規模なコンピュータシステムの管理は、プロセスの効率的なスケジューリングとメモリ配置に追加の課題をもたらします。

通常、より小さなシステムでは、オペレーティングシステムが自動的に利用可能なCPUとメモリリソースをリクエストタスク間で共有することで十分な効率で運用できます。

しかし、メモリアクセス時間や競合を減らすために慎重なプロセッサとメモリ配置がより効果的な大規模システムでは、顧客にとって大きな投資となるため、明示的にジョブを適切にサイズのされたシステムのサブセットに配置することで恩恵を受けることができます。

これは特に以下の環境で特に価値があります：

  • 同じWebアプリケーションの複数インスタンスを実行しているWebサーバー、

  • さまざまなアプリケーションを実行しているサーバー（例えば、ウェブサーバーとデータベース）、または

  • 大規模なHPCアプリケーションを実行しているNUMAシステムで、高要求なパフォーマンス特性を持つもの。

これらのサブセット、または「ソフトパーティション」は、ジョブの混合が変化するたびに動的に調整可能で、他の同時実行中のジョブに影響を与えない必要があります。また、メモリの場所も、メモリの場所が変更されるたびに移動することが可能です。

カーネルcpusetパッチは、このようなサブセットを効率的に実装するために必要な最小限のカーネルメカニズムを提供します。既存のCPUとメモリ配置機能をLinuxカーネルで活用し、重要なスケジューラーやメモリ割当コードに影響を与えることなく、実装を可能にしています。

1.3 cpusetsはどのように実装されていますか？¶

cpusetsは、プロセスまたはプロセスのセットが使用できるCPUとメモリノードを制限するためのLinuxカーネルのメカニズムです。

Linuxカーネルには、タスクがスケジュールされるCPUを指定するためのsched_setaffinityと、メモリを取得できるメモリノードを指定するためのmbind、set_mempolicyという2つのメカニズムがあります。

cpusetsはこれらの2つのメカニズムを以下のように拡張します：

  • cpusetsは、カーネルが認識している許可されたCPUとメモリノードのセットです。

  • システム内のすべてのタスクは、タスク構造体内のポインタを介して、参照カウントされたcgroup構造体にアタッチされてcpusetに属します。

  • sched_setaffinityへの呼び出しは、タスクのcpusetで許可されているCPUにのみフィルタリングされます。

  • mbindおよびset_mempolicyへの呼び出しは、タスクのcpusetで許可されているメモリノードにのみフィルタリングされます。

  • ルートcpusetは、システム内のすべてのCPUとメモリノードを含みます。

  • 任意のcpusetでは、親のCPUおよびメモリノードリソースのサブセットを含む子cpusetを定義できます。

  • cpusetsの階層は、/dev/cpusetにマウントされ、ユーザー空間から閲覧および操作が可能です。

  • cpusetは排他モードでマークされると、他のcpuset（直接の祖先および子孫を除く）が重複するCPUまたはメモリノードを含むことはできません。

  • 任意のcpusetにアタッチされているタスク（pidで表示）を一覧表示できます。

cpusetsの実装には、カーネルの他の部分とのいくつかのシンプルなインターフェースが必要で、パフォーマンスに影響するコードは一切ありません：

  • init/main.cで、システム起動時にルートcpusetを初期化します。

  • forkおよびexit処理で、タスクをcpusetにアタッチおよびデタッチします。

  • sched_setaffinityで、タスクのcpusetで許可されているCPUにのみリクエストされたCPUをマスクします。

  • sched.cのmigrate_live_tasks()で、cpusetで許可されているCPU内でタスクを移動させます。

  • mbind および set_mempolicy のシステムコールにおいて、タスクの cpuset で許可されている Memory Nodes に応じて、要求された Memory Nodes をマスクします。

  • page_alloc.c において、メモリの使用を許可されたノードに制限します。

  • vmscan.c において、ページ回復を現在の cpuset に制限します。

cpusets をカーネルが認識している現在の状態を閲覧・編集するためには、「cgroup」ファイルシステムタイプをマウントする必要があります。cpusets には新たなシステムコールが追加されず、すべてのクエリおよび編集機能はこの cpuset ファイルシステムを通じて行われます。

各タスクの /proc/<pid>/status ファイルには、以下の例に示す形式の2つのフォーマットで、タスクの cpus_allowed（スケジューリング可能なCPU）および mems_allowed（メモリを取得可能なMemory Nodes）が表示される4行が追加されます。

Cpus_allowed:   ffffffff,ffffffff,ffffffff,ffffffff
Cpus_allowed_list:      0-127
Mems_allowed:   ffffffff,ffffffff
Mems_allowed_list:      0-63

各 cpuset は、標準の cgroup ファイルに加えて以下のファイルを含む cgroup ファイルシステム内のディレクトリとして表されます。

  • cpuset.cpus: その cpuset に含まれるCPUの一覧

  • cpuset.mems: その cpuset に含まれるMemory Nodesの一覧

  • cpuset.memory_migrate フラグ: 設定されている場合、ページを cpuset のノードに移動します

  • cpuset.cpu_exclusive フラグ: CPUの割り当てが排他か？

  • cpuset.mem_exclusive フラグ: メモリの割り当てが排他か？

  • cpuset.mem_hardwall フラグ: メモリ割り当てがハードウェルドか？

  • cpuset.memory_pressure: cpuset 内のページング圧力を示す指標

  • cpuset.memory_spread_page フラグ: 設定されている場合、許可されたノード上でページキャッシュを均等に分散します

  • cpuset.memory_spread_slab フラグ: 設定されている場合、許可されたノード上でスラブキャッシュを均等に分散します

  • cpuset.sched_load_balance フラグ: 設定されている場合、その cpuset 内のCPU間で負荷をバランス取ります

  • cpuset.sched_relax_domain_level フラグ: タスクの移動時の検索範囲

さらに、ルート cpuset にのみ以下のファイルがあります:

  • cpuset.memory_pressure_enabled フラグ: メモリ_pressure を計算しますか？

新しい cpuset は mkdir システムコールまたはシェルコマンドで作成されます。cpuset のプロパティ（フラグ、許可されたCPUとMemory Nodes、アタッチされたタスクなど）は、上記のファイルに書き込むことで変更できます。

ネストされた cpusets の名前付き階層構造により、大規模なシステムをネストされた、動的に変更可能な「ソフトパーティション」に分割できます。

各タスクがフォーク時にそのタスクの子孫に自動的に継承され、cpusetにアタッチされることで、システム内の作業負荷を関連するタスクのセットに整理し、各セットが特定のcpusetのCPUとメモリノードのみを使用するように制限できます。タスクは、必要なcpusetファイルシステムディレクトリの権限が許可されている場合、他のcpusetに再アタッチすることが可能です。

システム全体の管理（"in the large"）は、sched_setaffinity、mbind、set_mempolicyシステムコールを使用して個々のタスクとメモリ領域に詳細に配置されることがスムーズに統合されます。

以下のルールは各cpusetに適用されます。

  • そのCPUとメモリノードは、親のサブセットでなければなりません。

  • 親が排他設定されていない限り、このcpusetは排他設定できません。

  • CPUまたはメモリが排他設定されている場合、それらは兄弟のcpusetと重複してはなりません。

これらのルールとcpusetsの自然な階層構造により、cpusetの排他保証を効率的に実施でき、すべてのcpusetを毎回スキャンする必要がありません。また、Linux仮想ファイルシステム（vfs）を使用してcpuset階層を表現することで、cpusetsに親しみやすい権限と名前空間が提供され、追加のカーネルコードを最小限に抑えています。

ルート（top_cpuset）cpuset内のcpusとmemsファイルは読み取り専用です。cpusファイルはCPUホットプラグ通知を用いてcpu_online_maskの値を自動的に追跡し、memsファイルはcpuset_track_online_nodes()フックを使用してnode_states[N_MEMORY]（つまりメモリを持つノード）の値を自動的に追跡します。

cpuset.effective_cpusとcpuset.effective_memsファイルは通常、cpuset.cpusとcpuset.memsファイルの読み取り専用コピーです。cpuset cgroupファイルシステムが"cpuset_v2_mode"オプションでマウントされている場合、これらのファイルの挙動はcpuset v2の対応するファイルと同様になります。つまり、ホットプラグイベントはcpuset.cpusとcpuset.mnadの値を変更しなくなり、それらのイベントはcpuset.effective_cpusとcpuset.effective_memsにのみ影響し、このcpusetが現在使用しているCPUとメモリノードを表示します。詳しくは Control Group v2 を参照してください。

1.4 排他cpusetとは何ですか？¶

cpusetがCPUまたはメモリ排他設定されている場合、そのCPUまたはメモリノードを共有する他のcpusetは、直接の祖先または後継者以外には存在できません。

cpuset.mem_exclusiveのcpuset または cpuset.mem_hardwall は「ハードウェールド（hardwalled）」状態であり、これはカーネルがページ、バッファ、その他の複数のユーザー間で共有されるデータを割り当てる際の制限を課します。ハードウェールドか否かに関わらず、すべての cpuset はユーザー空間のメモリ割り当てを制限します。これにより、複数の独立したジョブが共通のカーネルデータ（ファイルシステムページなど）を共有しながら、各ジョブのユーザー割り当てを個別 cpuset ごとに隔離できるシステム構成が可能になります。このため、すべてのジョブを含む大きな mem_exclusive cpuset を構築し、各個別ジョブごとに子 cpuset（非 mem_exclusive）を構築します。これにより、すらすらとメモリを取得できるのは、中断ハンドラからのリクエストなど、典型的なカーネルメモリのわずかな量に限られます。

1.5 メモリ圧力とは何ですか？¶

cpuset の memory_pressure は、その cpuset 内のタスクが、cpuset のノード上で使用中のメモリを解放しようと試みる速度を表す、cpuset ごとの単純なメトリックです。

これにより、専用 cpuset で実行されているジョブを監視するバッチマネージャーが、そのジョブが引き起こすメモリ圧力を効率的に検出できます。

これは、さまざまなジョブが混在する厳密に管理されたシステムで、メモリ使用量が許容範囲を超えたジョブを終了または優先順位を変更する場合に役立ちます。また、緊密に結合された長時間実行される大規模並列科学計算ジョブにおいても、許容範囲を超えてメモリを使用し始めるとパフォーマンス目標を大幅に達成できなくなるため、非常に有用です。

このメカニズムは、バッチマネージャーが cpuset のメモリ圧力を監視するための非常に効率的な方法を提供します。ただし、バッチマネージャーやその他のユーザー コードがこの状況に対処する方法を決定し、行動を起こす必要があります。

==>

この機能を有効にするには、特別なファイル /dev/cpuset/memory_pressure_enabled に「1」を書き込む必要があります。このメトリックの __alloc_pages() の再バランスコードにおけるハックは、この機能が無効になっている場合（cpuset_memory_pressure_enabled フラグがゼロの場合）は、単にフラグがゼロであることを認識するだけになります。したがって、この機能を有効にしないシステムでは、このメトリックは計算されません。

なぜ cpuset ごとの実行平均なのか？

このメーターが cpuset ごとにではなくタスクまたは mm ごとにであるため、バッチスケジューラがこのメトリックを監視する際のシステム負荷は、大規模なシステムでは大幅に軽減されます。なぜなら、各クエリごとにタスクリストをスキャンする必要がないからです。

このメーターはランニングアベレージであり、累積カウンターではなく、バッチスケジューラが単一の読み取りでメモリ圧力を検出できるため、一定期間の読み取りと結果の累積を必要としなくなります。

このメーターはタスクやmmごとのものではなく、CPUセットごとのため、バッチスケジューラがCPUセット内の動的に変化するタスクの集合全体をクエリし、結果を累積するのではなく、単一の読み取りでCPUセット内のメモリ圧力を取得できます。

CPUセットごとのシンプルなデジタルフィルタ（スピンロックとCPUセットごとの3ワードのデータを必要とします）が保持され、そのCPUセットにアタッチされたタスクが同期（直接）ページリカレートコードに入った場合に更新されます。

CPUセットごとのファイルは、CPUセット内のタスクによって引き起こされた直接ページリカレートの最近の（10秒の半減期）レートを表す整数を提供します。単位は秒あたりの再取得試行回数で、1000倍されます。

1.6 メモリスプレッドとは何ですか？¶

各CPUセットには、カーネルがファイルシステムバッファや関連するカーネルデータ構造にページを割り当てる場所を制御する2つのブールフラグファイルがあります。これらは「cpuset.memory_spread_page」と「cpuset.memory_spread_slab」と呼ばれます。

「cpuset.memory_spread_page」のブールフラグファイルが設定されている場合、カーネルは故障タスクが使用可能とされるノード全体にファイルシステムバッファ（ページキャッシュ）を均等に配分します。タスクが実行されているノードにページを優先的に配置するのではなく、均等に配分します。

「cpuset.memory_spread_slab」のブールフラグファイルが設定されている場合、カーネルはインノードやデントリなどのファイルシステム関連のスラブキャッシュを、故障タスクが使用可能とされるノード全体に均等に配分します。タスクが実行されているノードにページを優先的に配置するのではなく、均等に配分します。

これらのフラグの設定はタスクの匿名データセグメントまたはスタックセグメントページには影響を与えません。

デフォルトでは、両方のメモリスプレッド機能はオフになっており、タスクが実行されているノードのローカルでメモリページが割り当てられます。ただし、タスクのNUMAメモリポリシーやCPUセット設定によって変更されている場合を除き、十分な空きメモリページが利用可能であればそのようにします。

新しいCPUセットが作成される際、それらは親のメモリスプレッド設定を継承します。

メモリの分散設定により、影響を受けるページまたはスラブキャッシュの割当は、タスクのNUMAメモリポリシーを無視し、代わりに分散されます。mbind()またはset_mempolicy()呼び出しでNUMAメモリポリシーを設定しているタスクは、その包含タスクのメモリ分散設定の変更によってこれらの呼び出しに変化は感じません。メモリ分散がオフになっている場合、現在指定されているNUMAメモリポリシーが再びメモリページ割当に適用されます。

「cpuset.memory_spread_page」と「cpuset.memory_spread_slab」はどちらもブールフラグファイルです。デフォルトでは「0」を含み、そのcpusetにおいて機能がオフになっています。このファイルに「1」を書き込むと、指定された機能が有効になります。

実装はシンプルです。

フラグ「cpuset.memory_spread_page」を設定すると、そのcpuset内にいるタスクまたはその後にそのcpusetに参加するタスクそれぞれにプロセスごとのフラグPFA_SPREAD_PAGEが有効になります。ページキャッシュのページ割当呼び出しは、このPFA_SPREAD_PAGEタスクフラグをチェックし、設定されている場合、新しい関数cpuset_mem_spread_node()が呼び出され、割当に優先するノードが返されます。

同様に、「cpuset.memory_spread_slab」を設定すると、フラグPFA_SPREAD_SLABが有効になり、適切にマークされたスラブキャッシュは、cpuset_mem_spread_node()が返すノードからページを割り当てます。

cpuset_mem_spread_node()関数もシンプルです。この関数は、タスクごとのローター変数cpuset_mem_spread_rotorの値を用いて、現在のタスクのmems_allowed内の次のノードを選択し、割当に優先します。

このメモリ配置ポリシーは、他の文脈ではラウンドロビンまたはインターレーブと呼ばれます。

このポリシーは、スレッドローカルデータを対応するノードに配置する必要があるが、大規模なファイルシステムデータセットをジョブのcpuset内の複数ノードに分散して収容する必要があるジョブにおいて、大幅な改善をもたらします。このポリシーがない場合、特に1つのスレッドでデータセットを読み込むジョブでは、ジョブのcpuset内のノード間でのメモリ割当が非常に不均等になる可能性があります。

1.7 何ですかsched_load_balance？¶

カーネルスケジューラ（kernel/sched/core.c）は自動的にタスクをロードバランシングします。1つのCPUが過剰に利用されていない場合、そのCPU上で実行されているカーネルコードは、他の過負荷のCPUにあるタスクを探し出し、そのタスクを自身に移動します。ただし、cpusetsやsched_setaffinityなどの配置メカニズムの制約に従います。

負荷分散のアルゴリズム的コストと、タスクリストなどの主要な共有カーネルデータ構造への影響は、バランスを取るCPUの数が増えるにつれて線形以上に増加します。そのため、スケジューラはシステムのCPUを複数のスケジュールドメインに分割する機能をサポートしており、各スケジュールドメイン内でのみ負荷分散を行います。各スケジュールドメインはシステム内の一部のCPUをカバーし、2つのスケジュールドメインは重複しません。一部のCPUはどのスケジュールドメインにも属さず、負荷分散の対象外となる場合があります。

簡単に説明すると、2つの小さなスケジュールドメイン間で負荷分散を行うよりも、1つの大きなドメイン内で行う方がコストは低くなります。ただし、その場合、2つのドメイン内の過負荷が他方のドメインに分散されることはありません。

デフォルトでは、すべてのCPUをカバーする1つのスケジュールドメインが存在します。これは、カーネル起動時の「isolcpus=」引数で隔離されたCPUも含みます。ただし、隔離されたCPUは負荷分散に参加せず、明示的に割り当てられていない限りタスクを実行しません。

上記の2つの状況では、すべてのCPUを対象としたデフォルトの負荷分散は適していません。

  1. 大規模なシステムでは、多くのCPU間での負荷分散はコストが高くなります。システムがcpusetsを使用して独立したジョブを別々のCPUセットに配置されている場合、完全な負荷分散は必要ありません。

  2. 一部のCPUでリアルタイム処理をサポートするシステムでは、そのCPUでのシステムオーバーヘッドを最小限に抑え、必要なければタスクの負荷分散を避ける必要があります。

cpuset.sched_load_balanceフラグが有効（デフォルト設定）の場合、そのcpusetの許可CPU（cpuset.cpus）が1つのスケジュールドメインに含まれるように要求します。これにより、タスク（sched_setaffinityでピンされた場合を除く）がそのcpuset内のどのCPUからも他のどのCPUにでも移動可能になります。

cpuset.sched_load_balanceフラグが無効の場合、スケジューラはそのcpuset内のCPU間での負荷分散を避けることになります。ただし、他のcpusetがsched_load_balanceを有効にしている場合を除き、必要に応じて例外的に負荷分散を行います。

たとえば、トップcpusetでcpuset.sched_load_balanceフラグが有効の場合、スケジューラはすべてのCPUをカバーする1つのスケジュールドメインを設定します。その他のcpusetのフラグ設定は影響しません。すでに完全な負荷分散を行っているからです。

そのため、上記の2つの状況では、トップcpusetのcpuset.sched_load_balanceフラグを無効にし、一部の小さな子cpusetのみにこのフラグを有効にすることが適切です。

このような操作を行う際、通常はトップのcpusetに未固定のタスクを残さないことが望ましいです。なぜなら、このようなタスクは、このフラグ設定の下位cpusetの詳細に応じて、特定のCPUサブセットに人工的に制限される可能性があるからです。たとえそのタスクが他のCPUで空きCPUサイクルを活用できるとしても、カーネルのスケジューラは、そのタスクを未使用のCPUに負荷バランスを考慮しない可能性があります。

もちろん、特定のCPUに固定されたタスクは、「cpuset.sched_load_balance」を無効にしたcpusetに残しても問題ありません。なぜなら、これらのタスクは他の場所に移動しないからです。

cpusetとスケジューラドメインの間には、整合性の不一致があります。cpusetは階層構造を持ち、ネストするのに対し、スケジューラドメインはフラットで、重複せず、各CPUは最大1つのスケジューラドメインに属します。

スケジューラドメインがフラットであることが必要は、部分的に重なったCPUセット間での負荷バランスが不安定な動的を引き起こす可能性があるためです。したがって、2つの部分的に重なったcpusetが「cpuset.sched_load_balance」フラグを有効にしている場合、それらを含む単一のスケジューラドメインが形成されます。タスクは自身のcpuset外のCPUに移動しないものの、スケジューラの負荷バランスコードは、その可能性を検討する際に計算リソースを無駄にすることがあります。

この整合性の不一致により、「cpuset.sched_load,load_balance」フラグが有効なcpusetとスケジューラドメインの構成には1対1の関係がありません。cpusetがフラグを有効にすると、そのすべてのCPU間で負荷バランスが行われますが、フラグを無効にすると、他の重なったcpusetがフラグを有効にしない限り、負荷バランスが行われないことを保証されます。

2つのcpusetが部分的に重なった「cpuset.cpus」を許可しており、そのうち1つだけがこのフラグを有効にしている場合、もう一方のcpusetは重なったCPUでのみ負荷バランスが行われる可能性があります。これは先述のトップcpusetの例の一般的なケースです。同様に、トップcpusetの場合と同様に、非自明なCPU使用量を持つタスクをこのような部分的に負荷バランスされたcpusetに残さないことが望ましいです。なぜなら、負荷バランスが行われないため、タスクが許可されたCPUの一部に人工的に制限される可能性があるからです。

「cpuset.isolcpus」に含まれるCPUは、isolcpus=カーネル起動オプションにより負荷バランスから除外されており、どのcpusetの「cpuset.sched_load_balance」の値がどうであれ、負荷バランスが行われません。

1.7.1 スケジューラの負荷バランス実装の詳細¶

各cpusetごとのフラグ「cpuset.sched_load_balance」はデフォルトで有効になっています（これは他のcpusetフラグとは異なります）。このフラグが有効なcpusetでは、カーネルがそのcpuset内のすべてのCPUでロードバランシングを実行することを保証します（そのcpusetのcpus_allowedに含まれるすべてのCPUが同じスケジューリングドメインに含まれることを確認します）。

2つの重なったcpusetsがどちらも「cpuset.sched_load_balance」を有効にしている場合、それらは（必須ですが）同じスケジューリングドメインに含まれなければなりません。

デフォルトではトップcpusetが「cpuset.sched_load_balance」を有効にしている場合、上記によりシステム全体をカバーする単一のスケジューリングドメインが存在することになります。他のcpusetの設定とは関係ありません。

カーネルはユーザー空間に対して、可能な限りロードバランシングを避けることを約束します。cpusetの「cpuset.sched_load_balance」が有効な場合、そのcpusetに許可されたCPUのセットに対してロードバランシングを提供しつつ、可能な限り細かい粒度のスケジューリングドメインのパーティションを選択します。

内部のカーネルcpusetとスケジューラーのインターフェースでは、cpusetコードがスケジューラーコードに、システム内のロードバランシング対象のCPUをパーティション化した結果を渡します。このパーティションは、CPUをペアワイズで互いに重複しないサブセット（struct cpumaskの配列として表現）に分類し、すべてのロードバランシング対象のCPUをカバーします。

cpusetコードは、以下のいずれかの条件が満たされるたびに、このような新しいパーティションを生成してスケジューラーのスケジューリングドメイン設定コードに渡します。

  • cpusetの「cpuset.sched_load_balance」フラグが空でないCPUを持つcpusetで変更された場合、

  • このフラグが有効なcpusetにCPUが追加または削除された場合、

  • cpusetの「cpuset.sched_relax_domain_level」値が変更された場合（空でないCPUを持つcpusetでこのフラグが有効な場合）、

  • このフラグが有効な空でないCPUを持つcpusetが削除された場合、

  • CPUがオフラインまたはオンラインになった場合、

このパーティションは、スケジューラーが設定すべきスケジューリングドメインを正確に定義します。パーティション内の各要素（struct cpumask）に対応する1つのスケジューリングドメインが存在します。

スケジューラーは現在アクティブなスケジューリングドメインのパーティションを記憶しています。cpusetコードからpartition_sched_domains()関数が呼び出され、これらのスケジューリングドメインを更新する際には、新しいパーティションと現在のパーティションを比較し、変更ごとに古いものを削除し新しいものを追加します。

1.8 何ですか「sched_relax_domain_level」？¶

スケジューリングドメインでは、スケジューラーがタスクを2つの方法で移動させます。1つはタイクの定期的なロードバランシング、もう1つはスケジュールイベント発生時のものです。

タスクが目覚めたとき、スケジューラはそのタスクをアイドル状態のCPUに移動しようとします。たとえば、タスクAがCPU Xで実行中で、同じCPU X上でタスクBがアクティブ化された場合、CPU YがXの親CPUでありアイドル状態であれば、スケジューラはタスクBをCPU Yに移動させ、タスクAがCPU Xで実行されるのを待つことなくCPU Yで実行できるようにします。

また、CPUがランキューにタスクがなくなった場合、そのCPUはアイドル状態になる前に、他の忙しいCPUから追加のタスクを引き寄せることで助けを提供しようとします。

もちろん、移動可能なタスクやアイドルCPUを検索するにはコストがかかり、スケジューラは毎回ドメイン内のすべてのCPUを検索するわけではありません。実際には、一部のアーキテクチャでは、CPUが配置されているソケットやノード内でのみ検索範囲が制限されており、ロードバランシングではすべてのCPUを検索します。

たとえば、CPU ZがCPU Xよりも遠く離れているとします。CPU Xとその親CPUが忙しい状態であっても、CPU Zがアイドル状態である場合でも、スケジューラは検索範囲外のため、タスクBをXからZに移動させることはできません。その結果、タスクBはCPU X上でタスクAを待つことや、次のティックでのロードバランシングを待つことになります。特殊な状況におけるアプリケーションでは、1ティックの待機時間が長すぎる可能性があります。

「cpuset.sched_relax_domain_level」ファイルは、検索範囲を自由に指定できます。このファイルは整数値をとるため、理想的な検索範囲のサイズを以下のように指定できます。指定しない場合は初期値-1となり、cpusetに特別な要求はありません。

-1

要求なし。システムのデフォルト値を使用するか、他の要求に従います。

0

検索を行いません。

1

スレッド（コア内のハイパースレッド）を検索します。

2

パッケージ内のコアを検索します。

3

ノード内のCPUを検索します（ノンNUMAシステムではシステム全体を検索します）

4

ノードのチャンク内のノードを検索します（NUMAシステムでは）

5

システム全体を検索します（NUMAシステムでは）

システムのデフォルト値はアーキテクチャに依存します。relax_domain_level=パラメータを使用してシステムのデフォルト値を変更できます。

このファイルはcpusetごとに設定され、cpusetが所属するスケジューリングドメインに影響を与えます。したがって、cpuset.sched_load_balanceフラグが無効になっているcpusetでは、cpuset.sched_relax_domain_levelの設定は無効になります。

複数のcpusetが重なって1つのスケジューリングドメインを形成している場合、その中で最大の値が使用されます。注意点として、1つが0を指定し、他のものが-1を指定している場合、0が使用されます。

このファイルの編集は良い影響と悪い影響をもたらすため、編集が許容されるかどうかは状況次第です。状況が不明確な場合は編集しないでください。

あなたの状況は:

  • 各CPU間の移動コストは、あなたの特別なアプリケーションの挙動やCPUキャッシュなどの特別なハードウェアサポートにより、あなたのためにはかなり小さく考えられます。

  • 検索コストはあなたのためには影響を与えません。(for you) または、cpusetをコンパクトに管理することで検索コストを十分に小さくすることができます。

  • キャッシュヒット率を犠牲にしても遅延が必要な場合、'sched_relax_domain_level'を上げることで、あなたのためにはメリットがあります。

1.9 cpusetsの使用方法¶

重要なカーネルコード（例：スケジューラ）へのcpusetsの影響を最小限に抑えるため、またカーネルがタスク間のメモリ配置の直接的な変更をサポートしていないため、タスクのcpuset CPUやメモリノード配置の変更、またはタスクがどのcpusetに属するかの変更による影響は微妙です。

cpusetのメモリノードが変更された場合、そのcpusetに属する各タスクに対して、カーネルがそのタスクのメモリページを割り当てる際、変更を検知し、新しいcpusetのメモリ配置に合わせてタスクごとのメモリ配置を更新します。タスクがMPOL_BINDメモリポリシーを使用しており、そのタスクが束縛されていたノードが新しいcpusetと重なっている場合、タスクは新しいcpuset内でMPOL_BINDのノードのサブセットを引き続き使用します。タスクがMPOL_BINDを使用しており、新しいcpuset内でMPOL_BINDのノードが許可されなくなった場合、タスクは新しいcpusetにMPOL_BINDで束縛されているかのように扱われます（get_mempolicy()で取得するNUMA配置は変更されません）。タスクがcpusetから別のcpusetに移動した場合、カーネルはそのタスクのメモリ配置を、タスクのメモリページ割り当ての次の試行時に調整します。

cpusetの'cpuset.cpus'が変更された場合、そのcpuset内の各タスクの許可されたCPU配置が即座に変更されます。同様に、タスクのpidを別のcpusetの'tasks'ファイルに書き込むと、そのタスクの許可されたCPU配置が即座に変更されます。このようなタスクがsched_setaffinity()呼び出しによりcpusetの一部に束縛されていた場合、タスクは新しいcpuset内で許可されたすべてのCPUで実行可能となり、以前のsched_setaffinity()呼び出しの効果が無効になります。

要約すると、cpusetが変更されたタスクのメモリ配置は、タスクのメモリページ割り当ての次の試行時にカーネルが更新し、プロセッサ配置は即座に更新されます。

通常、ページが割り当てられると（主記憶領域の物理ページが割り当てられると）、そのページは割り当てられたノードにとどまり、そのページが割り当てられている限り、cpusetのメモリ配置ポリシー（cpuset.mems）が後で変更されても、そのノードにとどまります。cpusetフラグファイル「cpuset.memory_migrate」がtrueに設定されている場合、タスクがそのcpusetにアタッチされるとき、タスクが以前のcpusetで割り当てられたノード上のページは、タスクの新しいcpusetに移動されます。これらの移動操作では、cpuset内でのページの相対的な配置は可能な限り保持されます。例えば、ページが以前のcpusetの有効なノードの2番目に配置されていた場合、新しいcpusetの有効なノードの2番目に配置されます。

また、「cpuset.memory_migrate」がtrueに設定されている場合、そのcpusetの「cpuset.mems」ファイルが変更されたとき、そのcpusetに割り当てられたタスクのページが、以前の「cpuset.mems」設定のノードに配置されていた場合、新しい「mems」設定のノードに移動されます。タスクの以前のcpusetに含まれていなかったページ、またはcpusetの以前の「cp,uset.mems」設定に含まれていなかったページは移動されません。

上記には例外があります。ホットプラグ機能を使用して、cpusetに現在割り当てられているすべてのCPUを削除した場合、そのcpuset内のすべてのタスクが、最も近い非空のcpusを持つ先祖cpusetに移動します。ただし、cpusetが他のcgroupサブシステムと結合されている場合、タスクのアタッチに制限があるため、一部（またはすべて）のタスクの移動が失敗する可能性があります。このような失敗の場合、そのタスクは元のcpusetにとどまり、カーネルが自動的にそのタスクのcpus_allowedをすべてオンラインのCPUを許可するように更新します。メモリホットプラグ機能でメモリノードを削除する機能が利用可能な場合、同様の例外が適用されることが予期されます。一般的に、カーネルはタスクのすべての許可されたCPUまたはメモリノードがオフラインになった場合にタスクを飢えさせるよりも、cpusetの配置を破る方が好ましいです。

上記にはもう一つの例外があります。GFP_ATOMICリクエストは、カーネル内部で即座に満たされる必要がある割り当てです。GFP_ATOMICの割り当てが失敗した場合、カーネルは一部のリクエストを無視するか、まれにパニックを起こすことがあります。リクエストが現在のタスクのcpuset内で満たされない場合、cpusetを緩和し、どこでもメモリを検索します。カーネルを過負荷にしないよりも、cpusetを破る方が良いです。

cpuset内で含める新しいジョブを開始するには、以下の手順を行います：

  1. mkdir /sys/fs/cgroup/cpuset

  2. mount -t cgroup -ocpuset cpuset /sys/fs/cgroup/cpuset

  3. 新しいcpusetを作成するには、/sys/fs/cgroup/cpusetという仮想ファイルシステム内でmkdirやwrite（またはecho）コマンドを使用します。

  4. 新しいジョブの「創設者」となるタスクを起動します。

  5. この創設者タスクを新しいcpusetにアタッチするには、そのpidをcpusetのtasksファイルに書き込みます。

  6. この創設者タスクからジョブタスクをfork、exec、またはcloneします。

例えば、以下のコマンドシーケンスは、CPUs 2と3、Memory Node 1を含む名前が「Charlie」のcpusetを作成し、そのcpuset内でサブシェル「sh」を起動します：

mount -t cgroup -ocpuset cpuset /sys/fs/cgroup/cpuset
cd /sys/fs/cgroup/cpuset
mkdir Charlie
cd Charlie
/bin/echo 2-3 > cpuset.cpus
/bin/echo 1 > cpuset.mems
/bin/echo $$ > tasks
sh
# The subshell 'sh' is now running in cpuset Charlie
# The next line should display '/Charlie'
cat /proc/self/cpuset

cpusetをクエリまたは変更する方法はいくつかあります：

  • シェルからcd、mkdir、echo、cat、rmdirコマンド、またはC言語での同等コマンドを用いてcpusetファイルシステムを直接操作できます。

  • Cライブラリlibcpusetを介して。

  • Cライブラリlibcgroupを介して。(http://sourceforge.net/projects/libcg/)

  • Pythonアプリケーションcsetを介して。(http://code.google.com/p/cpuset/)

sched_setaffinityコールは、SGIのrunonやRobert Loveのtasksetを使用してシェルプロンプトから実行できます。mbindおよびset_mempolicyコールは、numactlコマンド（Andi Kleenのnumaパッケージに含まれる）を使用してシェルプロンプトから実行できます。

2. 使用例と構文¶

2.1 基本的な使用方法¶

cpusetの作成、変更、使用はcpuset仮想ファイルシステムを通じて行えます。

マウントするには、以下を入力します：# mount -t cgroup -o cpuset cpuset /sys/fs/cgroup/cpuset

その後、/sys/fs/cgroup/cpuset配下で、システム内のcpusetツリーに対応するツリーが確認できます。例えば、/sys/fs/cgroup/cpusetは全体のシステムを保持するcpusetです。

cpusetを/sys/fs/cgroup/cpuset配下に新規作成するには：

# cd /sys/fs/cgroup/cpuset
# mkdir my_cpuset

このcpusetに対して何か操作を行います：

# cd my_cpuset

このディレクトリにはいくつかのファイルがあります:

# ls
cgroup.clone_children  cpuset.memory_pressure
cgroup.event_control   cpuset.memory_spread_page
cgroup.procs           cpuset.memory_spread_slab
cpuset.cpu_exclusive   cpuset.mems
cpuset.cpus            cpuset.sched_load_balance
cpuset.mem_exclusive   cpuset.sched_relax_domain_level
cpuset.mem_hardwall    notify_on_release
cpuset.memory_migrate  tasks

これらファイルの読み込みにより、cpusetの状態（使用可能なCPUとメモリノード、使用中のプロセス、プロパティなど）を確認できます。これらのファイルに書き込むことでcpusetを操作できます。

いくつかのフラグを設定します：

# /bin/echo 1 > cpuset.cpu_exclusive

いくつかのCPUを追加します：

# /bin/echo 0-7 > cpuset.cpus

いくつかのメモリノードを追加します：

# /bin/echo 0-7 > cpuset.mems

このシェルをこのcpusetにアタッチします：

# /bin/echo $$ > tasks

このディレクトリ内でmkdirを使用することで、cpuset内にcpusetを作成できます：

# mkdir my_sub_cs

cpusetを削除するにはrmdirを使用します：

# rmdir my_sub_cs

cpusetが使用中（内部にcpusetが存在するか、プロセスがアタッチされているか）の場合、この操作は失敗します。

伝統的な理由により、「cpuset」ファイルシステムはcgroupファイルシステムをラッパーとして存在します。

以下のコマンド：

mount -t cpuset X /sys/fs/cgroup/cpuset

は以下のコマンドと同等です：

mount -t cgroup -ocpuset,noprefix X /sys/fs/cgroup/cpuset
echo "/sbin/cpuset_release_agent" > /sys/fs/cgroup/cpuset/release_agent

2.2 CPUの追加/削除¶

cpusetディレクトリ内のcpusまたはmemsファイルに書き込む際の構文は以下の通りです：

# /bin/echo 1-4 > cpuset.cpus         -> set cpus list to cpus 1,2,3,4
# /bin/echo 1,2,3,4 > cpuset.cpus     -> set cpus list to cpus 1,2,3,4

CPUsをcpusetに追加するには、追加するCPUを含む新しいCPUsリストを書き込みます。例えば、上記のcpusetにCPU 6を追加するには：

# /bin/echo 1-4,6 > cpuset.cpus       -> set cpus list to cpus 1,2,3,4,6

CPUsをcpusetから削除するには、削除するCPUを除いた新しいCPUsリストを書き込みます。

すべてのCPUを削除するには：

# /bin/echo "" > cpuset.cpus          -> clear cpus list

2.3 フラグの設定¶

構文は非常にシンプルです:

# /bin/echo 1 > cpuset.cpu_exclusive  -> set flag 'cpuset.cpu_exclusive'
# /bin/echo 0 > cpuset.cpu_exclusive  -> unset flag 'cpuset.cpu_exclusive'

2.4 プロセスのアタッチ¶

# /bin/echo PID > tasks

PID、ではなくPIDsです。一度に1つのタスクのみアタッチ可能です。複数のタスクをアタッチする場合は、順番に実行してください:

# /bin/echo PID1 > tasks
# /bin/echo PID2 > tasks
      ...
# /bin/echo PIDn > tasks

3. 質問¶

Q:

この‘/bin/echo’の件は？

A:

bashの組み込みコマンド‘echo’はwrite()への呼び出しをエラーと比較してチェックしません。cpusetファイルシステムでこれを使用すると、コマンドが成功したか失敗したかを判断できません。

Q:

プロセスをアタッチする際、行の最初のプロセスだけが本当にアタッチされます！

A:

write()への呼び出しごとに1つのエラーコードのみを返すことができます。したがって、1つのPIDのみを指定する必要があります。

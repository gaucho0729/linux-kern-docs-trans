6.1.2. bttvをあなたのカードと互換性させるには¶

bttvがコンパイル・インストールされている場合、カーネルを起動するだけでデバイスを検出試験するよう自動で試みます。ただし、モデルによってはハードウェアに関する追加情報が必要となる場合があります。デバイスがカーネルに直接その情報を提供できないためです。

検出されなかった場合、bttvはおそらく自動検出できず、insmodオプションが必要です。bttvで最も重要なinsmodオプションは「card=n」で正しいカードタイプを選択します。動画は表示されるが音声が聞こえない場合は、おそらく正しい（または何も指定していない）カードタイプを指定した可能性が高いです。サポートされているカードの一覧は BTTVカード一覧.

bttvがロードに非常に時間がかかる場合（特に tuner がない安価なカードではよく起きます）、modules構成ファイル（通常は /etc/modules.conf または以下のようなファイル /etc/modules-load.d/ですが、実際の場所はディストリビューションによって異なります）:

options i2c-algo-bit bit_test=1

一部のカードは追加のファームウェアファイルが必要です。たとえば、WinTV/PVRではそのドライバCDから呼ばれるファームウェアファイル hcwamc.rbfが必要です。これは自己解凍型ZIPファイル pvr45xxx.exe内に含まれています。このファイルを /etc/firmware ディレクトリに配置するだけで、ドライバの検出モード（カーネル起動時や、manuallyロード時など）で自動ロードされるようになります。 modprobe コマンド)でロードされるようになります。

6.1.3. 自動検出¶

bttvはPCIサブシステムIDを使ってカードタイプを自動検出します。lspciはサブシステムIDを2行目に表示します。以下のような形式です:

00:0a.0 Multimedia video controller: Brooktree Corporation Bt878 (rev 02)
        Subsystem: Hauppauge computer works Inc. WinTV/GO
        Flags: bus master, medium devsel, latency 32, IRQ 5
        Memory at e2000000 (32-bit, prefetchable) [size=4K]

サブシステムIDはbt878ベースのカードにのみ存在します（すべてのカードが必ず持つとは限りません）。bt848ベースのカードはサブシステムIDを持たず、自動検出が不可能です。IDの一覧は BTTVカード一覧 （ご関心がある場合や、アップデートのパッチをメールで送る場合にご参照ください）。

6.1.6. bttvでボックスがハードにフリーズした場合¶

これはbttvドライバのバグである可能性があります。また、不良なハードウェアである可能性もあります。あるいは何か他の原因かもしれません…

6.1.6.1. bttvのバグ¶

あるバージョンでは動作し、別のバージョンでは動作しなくなった場合、それはおそらくドライバのバグです。正確にどこで壊れたか（つまり、最後に動作したバージョンと最初に壊れたバージョン）を教えてくれると非常に役立ちます。

ハードなフリーズではログファイルに何もない可能性が高いです。カーネルメッセージをキャプチャする唯一の方法は、シリアルコンソールを接続し、ターミナルアプリケーションでメッセージをログに記録することです。/meはscreenを使用しています。詳細については Linux シリアルコンソール シリアルコンソールの設定方法を参照してください。

を読み、カーネルがプロテクションフォールト（いわゆる「カーネルオプス」）でレジスタ＋スタックダンプを出力するときに、有用な情報をどのように抽出できるか学びましょう。 バグ狩り 保護フォールトでカーネルがレジスタ＋スタックダンプを出力するときに、有用な情報をどのように抽出できるか学びましょう。

デッドロックに遭遇した場合は、sysrq-t（参照： Linux Magic System Request Key Hacks）を使用して各プロセスのスタックトレースをダンプすることで、どこで 正確に 「D」状態のプロセスが停止しているかを特定できます。

bttv 0.7.xがクラッシュするという報告を目にしたが、0.8.xは一部の人にとっては安定して動作する。おそらくbttv 0.7.xにはどこかに小さなバグが残っているのだろう。正確な場所は分からないが、私自身や多くの他のユーザーにとっては安定して動作する。0.7.x版で問題が起きた場合は、0.8.xを試してみることを検討してほしい…

6.1.6.2. ハードウェアの不具合¶

一部のハードウェアはPCI-PCI転送（例：キャプチャーデバイス→VGA）を処理できず、場合によってはbttvの問題がPCIバスの高負荷によって引き起こされることがある。bt848/878チップには、既知の互換性問題に対するいくつかの回避策が用意されており、README.quirksを参照のこと。

一部のユーザーはPCIレイテンシーを増やすことで問題が改善すると報告しているが、この方法が本当に問題を解決するのか、あるいは発生確率を減らすだけなのかは確証がない。bttvとbtaudioの両方には、デバイスのPCIレイテンシーを設定するinsmodオプションが用意されている。

一部のマザーボードは、複数のデバイスが同時にDMAを実行する際の処理に問題を生じることがあり、bttv + IDEの組み合わせでこの問題が起きることがある。このような場合、ビデオとハードディスクアクセスが同時に起きた際にフリーズが発生する可能性がある。IDEドライバを最新版に更新し、ハードウェアの不具合に対する最新の回避策を導入することで、これらの問題を解決できるかもしれない。

6.1.6.3. その他¶

バイナリのみのドライバ（例：nvidiaモジュール）を使用している場合は、問題を再現する際にはそのドライバを使用しないで試してみること。

IRQ共有は一部のケースで問題を引き起こす可能性がある。理論上は多くの設定で問題ないが、PCIカードの配置を変更してbttvに別のIRQを割り当てたり、他のデバイスとIRQを共有させたりする試みは価値があるかもしれない。VGAカードとのIRQ共有は特にトラブルを引き起こすことがある。また、bttvがACPIブリッジ（およびapci有効のカーネル）とIRQを共有する場合、不思議な現象が起きることも確認している。

6.1.7.1. 通常のPCIモード¶

PCI REQ信号は、入力された関数リクエストの論理ORです。内部のGNT[0:1]信号は、GNTと非同期的にゲートされ、オーディオリクエスト信号によってデマルチプレックスされます。したがって、電源投入時にアービトラータはビデオ関数にデフォルトし、バスアクセスのリクエストがない間はその位置にとどまります。これは望ましい状態です。なぜなら、ビデオがバスをより頻繁にリクエストするからです。しかし、オーディオが最高のバスアクセス優先度を持ちます。そのため、ビデオリクエストの後にオーディオリクエストが発生した場合でも、PCI外部アービトラータがBt879にアクセスを許可するまでは、オーディオがバスへのアクセスを優先します。どちらの関数も、バス上に進入した後は他方を強制的に中断することはできません。ビデオPCI FIFOをすべてPCIバスに空けるのにかかる時間は、オーディオPCI FIFOが許容できるバスアクセス遅延と比べて非常に短いです。

6.1.7.2. 430FX互換モード¶

430FX PCIを使用する場合、以下のルールを守ることで互換性を確保できます。

  1. REQを解除する際はFRAMEをアサートするタイミングと同時に実行してください。

  2. 前のトランザクションが完了するまでは、REQを再アサートして別のバストランザクションをリクエストしないでください。

個々のバスマスターがREQを直接制御できないため、ビデオとオーディオのリクエストを単純に論理ORするだけで規則を違反します。そのため、アービトラータとイニシエータの両方に430FX互換モード論理が含まれています。430FXモードを有効にするには、ページ104のデバイス制御レジスタでEN_TBFXビットを設定してください。

EN_TBFXが有効になると、アービトラータが2つの互換性ルールを満たすことを保証します。PCIアービトラータがGNTをアサートする前には、この内部アービトラータは依然として2つのリクエストを論理ORできます。しかし、GNTが発行された後は、このアービトラータは決定をロックし、今後はのみ承認されたリクエストのみをREQピンにルーティングします。決定ロックはFRAMEの状態に関係なく発生します。なぜなら、アービトラータはFRAMEがアサートされるタイミングを知らず、通常はGNTのサイクルの次のサイクルで各イニシエータがFRAMEをアサートするからです。FRAMEがアサートされた場合、それはイニシエータの責任でそのリクエストを同時に解除することです。アービトラータはこのリクエストをREQに流し、他のリクエストがREQをアサートしているのを許可しない責任があります。決定ロックはトランザクション終了時に解除できます。例えば、バスがアイドル状態にある場合（FRAMEおよびIRDY）。この後、アービトラータの決定は再びGNTがアサートされるまで非同期的に継続します。

6.1.7.3. PCI 2.1準拠でないコアロジックとのインターフェース¶

GNTが解除されたサイクル中にコア論理デバイスの一部がバストランザクションを開始する可能性があります。これはPCI 2.1準拠ではありません。これらのPCIコントローラーを使用するPCとの互換性を確保するためには、EN_VSFXビットを有効にする必要があります（ページ104のデバイス制御レジスタを参照）。このモードでは、REQがアサートされるまでアービトラータがGNTを内部機能に渡しません。これにより、GNTが解除されたサイクルと同時にバストランザクションが開始されることを防ぎます。また、バスパーキングを活用できなくなる副作用があり、アービトラーション性能が低下します。Bt879ドライバはこれらの非準拠デバイスを検出する必要があります。必要に応じてのみEN_VSFXビットを設定する必要があります。

新しいカードを動作させる場合、tvcards配列の他の要素がどのような用途かを知ることで役立つかもしれません:

no_tda9875      - "1" disables loading of tda9875.o module

6.1.8.16.1. Leadtek WinView 601 TV/FMのサポート¶

このセクションの著者: Jon Tombs <jon@gte.esi.us.es>

このカードは他のすべてのカードと基本的に同じ（Bt484A、Philipsチューナー）で、主な違いは3つのGPIOラインにプログラマブルなアタenuエータを接続していることで、音量制御を提供していることです。また、ボード上にインフラレッドリモコンのデコード回路を搭載しています。時間があるときにサポートを追加します（キーを押すたびに割込みを生成し、キーコードをGPIOポートに設定します）。

ラジオサポートのアプリケーションはまだありません。チューナーの周波数設定は動作するかもしれませんが、オーディオ多重器が正しくない可能性があります。動作しない場合はメールでご連絡ください。

  • Leadtekに感謝しますが、彼らはハードウェアについての質問に答えないため、ドライバはカードの視覚的な検査によって書かれました。このドライバを使用する場合は、彼らに怒りのメールを送り、Linuxをサポートしない限り彼らのハードウェアを購入しないと伝えてください。

  • Princeton Technology Corp（http://www.princeton.com.tw)が製造するオーディオアタenuエータに少しだけ感謝します。彼らのウェブサイトに公開されているデータシートにはチップのプログラミング情報が含まれていません！サーバーに隠されている完全なデータシートがありますが、私はどのように見つけたかは聞かないでください。

ドライバを使用するには以下のオプションを使用します。チューナーおよびPLLの設定はあなたの国によって異なります。modprobeパラメータを通じて強制的に設定できます。例えば：

modprobe bttv  tuner=1 pll=28 radio=1 card=17

チューナー型番1（Philips PAL_I）、28 MHzのクリスタルを搭載したPLL、FMラジオを有効化し、bttvカードID 17（Leadtek WinView 601）を選択します。

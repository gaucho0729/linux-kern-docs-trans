使い方¶

このモジュールはSMB3ファミリの高度なネットワークプロトコルをサポートしています（古いバージョンのダイアレクトもサポートしており、元々は「CIFS」と呼ばれていました）。

Linux用のCIFS VFSモジュールは、階層的なDFSネームスペース、ハードリンク、ロック機能など多くの高度なネットワークファイルシステム機能をサポートしています。これはSNIA CIFS技術リファレンス（1992年のX/Open SMB標準を上書きした）に準拠しており、Windows 2000、Windows XP、Sambaおよび同等サーバーとの最良の実践的相互運用性を実現するように設計されています。このコードはProtocol Freedom Information Foundationとの協力で開発されました。CIFSおよび現在のSMB3は、マックとWindows、主要なNASアプライアンス間での相互運用性の事実上の標準となっています。

MS-SMB2（SMB2/SMB3/SMB3.1.1プロトコル仕様の詳細については） https://samba.org/samba/PFIF/ 詳細についてはこちら。

ビルド手順¶

Linuxの場合：

  1. カーネルをダウンロード（例： https://www.kernel.org）し、カーネルディレクトリツリーのトップに移動してください（例：/usr/src/linux-2.5.73）

  2. make menuconfig（または make xconfig）

  3. ネットワークファイルシステムの選択肢内でcifsを選択

  4. 保存して終了

  5. make

CIFS VFSをカーネル自体に組み込んだ場合、ディストリビューションのインストール手順に従ってください（通常は単に make install).

推奨事項¶

セキュリティ向上のため、SMB2.1 ディアレクトリ言語またはそれ以降（通常は SMB3 が使用されます）が新しいデフォルトとなりました。古いディアレクトリ言語（例: Windows XP でのマウント）を使用する場合は、マウント時に "vers=1.0"（または Windows Vista 用の "vers=2.0"）を指定してください。注意点として、CIFS（vers=1.0）は非常に古く、セキュリティが低く、デフォルトの SMB3 に比べてダウングレード攻撃検出や暗号化共有、より強力なサインインと認証アルゴリズムなどの高度なセキュリティ機能がありません。SMB3 で POSIX の動作を改善するための追加のマウントオプションもあります（NB: SMB3 にのみ使用するには "vers=3.0" を指定してください）:

mfsymlinks および cifsacl および idsfromsid

ユーザーによるマウントの許可¶

ユーザーが所有するディレクトリでマウントおよびアンマウントを行うことは、cifs vfs で可能です。このようなマウントを有効にするには、mount.cifs ユーティリティを suid としてマークする必要があります（例: chmod +s /sbin/mount.cifs). ユーザーがマウントした共有をアンマウントするには、

  1. mount.cifs バージョン 1.4 以降

  2. /etc/fstab に共有をアンマウントできるユーザーがいることを示すエントリを追加します（例:

    //server/usersharename  /mnt/username cifs user 0 0

mount.cifs ユーティリティを suid として実行（ユーザーによるマウントを許可）する場合、リスクを減らすために、 nosuid マウント時に mount フラグを渡して、リモートターゲットで suid プログラムの実行を禁止します。root で mount を実行する場合、デフォルトでは nosuid フラグが渡されず、リモートターゲットでの suid プログラムの実行が有効になります。これは nfs や他のファイルシステムと同様に、mount オプションに指定することで変更できます。 nosuid ユーザーによるマウントが suid フラグを mount に渡すために、mount.cifs を再構築する際には次のフラグを指定する必要があります: CIFS_ALLOW_USR_SUID

Samba 3.0 以降のソースツリーには、cifs マウントに関するマニュアルページが docs/manpages/mount.cifs.8 にあります。

ユーザーによるアンマウントの許可¶

ユーザーがユーザーでマウントしたディレクトリをアンマウントできるようにするには（上記参照）、umount.cifs ユーティリティを使用します。直接呼び出したり、umount.cifs を /sbin に配置すれば、umount が cifs アンマウントヘルパー（ほとんどの umount ユーティリティのバージョンで有効）を呼び出すことができます（ただし、umount に -i オプションを指定すると、アンマウントヘルパーが呼び出されません）。mount.cifs と同様に、ユーザーによるアンマウントを有効にするには、umount.cifs を suid としてマークする必要があります（例: chmod +s /sbin/umount.cifs) または同等の設定（一部のディストリビューションでは、/etc/permissions ファイルにエントリを追加することで、同等の suid 効果を達成できます）。このユーティリティが成功するためには、ターゲットのパスが cifs マウントである必要があります。また、現在のユーザーの uid が、リソースをマウントしたユーザーの uid と一致している必要があります。

さらに注意すべきは、ユーザーがマウントおよびアンマウントを行うための一般的な方法は、mount.cifs と unmount.cifs を suid として使用するのではなく、マウントしたい //server/share ごとに /etc/fstab ファイルに1行を追加することです。ただし、潜在的なマウントターゲットに多くのまたは予測不可能な UNC 名が含まれる場合、この方法は管理が複雑になることがあります。

Sambaに関する考慮点¶

現在のほとんどのサーバーは SMB2.1 と SMB3 をサポートしており、これらはより安全ですが、古い less secure CIFS ディアレクトリには有用なプロトコル拡張機能があります。したがって、古いディアレクトリ（CIFS/SMB1）を使用してマウントする場合、最大のメリットを得るために、SNIA CIFS Unix Extensions 標準（例: ほぼすべてのバージョンの Samba、つまり 2.2.5 以降）をサポートするサーバーを使用することをお勧めします。ただし、CIFS vfs は幅広い CIFS サーバーと互換性があります。注意点として、Unix 拡張機能をサポートしないサーバーを使用すると、uid、gid およびファイルのパーミッションはデフォルト値を表示します。Unix CIFS 拡張機能を Samba サーバーで有効にするには、以下の行を smb.conf ファイルに追加してください。

unix extensions = yes

サーバーの smb.conf ファイルに追加してください。注意点として、Samba サーバーにおいて、ほとんどのクライアントが Unix または Linux である場合、以下の smb.conf の設定も役立ちます。

case sensitive = yes
delete readonly = yes
ea support = yes

Linux cifs クライアントから xattrs をサポートするには、server ea のサポートが必要です。EA サポートは、Samba の後続バージョン（例: 3.0.6 以降）で利用可能で、すべての Windows バージョンでも NTFS ファイルシステムの共有に対して EA サポートが動作します。拡張属性（xattr）サポートは、ほとんどの Linux ファイルシステムのオプション機能であり、make menuconfig を通じて有効にする必要があります。クライアント側で拡張属性（user xattr）のサポートを個別に無効化するには、マウント時に以下を指定してください。 nouser_xattr マウント時に指定してください。

CIFS クライアントは、Samba サーバーのバージョン 3.10 以降に対して POSIX ACL（getfacl、setfacl）を取得および設定できます。POSIX ACL を設定するには、cifs モジュールをビルドする際の CIFS 設定オプションで XATTR と POSIX サポートを有効にする必要があります。POSIX ACL サポートは、マウントごとに無効化するには以下を指定してください。 noacl マウント時に指定してください。

一部の管理者は Samba の smb.conf を変更したいかもしれません map archive および create mask デフォルト値からパラメータを変更しない場合、新たに作成されたファイルは無駄に制限的なデフォルトモードを持つ可能性があり、これは望ましくない場合もあります。ただし、サーバーおよびクライアントでCIFS Unix拡張機能が有効になっている場合、後続のsetattrコール（例：chmod）でモードを修正できます。注意点として、リモートで特殊デバイス（mknod）を作成する場合、Samba 3.0.6以降を使用していない場合は、Sambaにmkdev関数を指定する必要があります。これらの詳細については、Sambaサーバーのマニュアルページ（man smb.conf)を参照してください。また、cifs vfsはsmbfs vfsとは異なり、クライアントシステムのsmb.confを読み込まないため、マウント時に-oパラメータでオプション設定を渡します。Samba 2.2.7以降には、CIFS VFSがオープンしているファイルを削除できる修正が含まれており、これは厳格なPOSIX準拠のため必要です。Windowsサーバーはすでにこの機能をサポートしています。Sambaサーバーは、共有外のファイルを参照するシンボリックリンクを許可しないので、Samba 3.0.6以前のバージョンでは、絶対パス（スラッシュで始まる）を持つファイルへのシンボリックリンクは:

ln -s /mnt/foo bar

が禁止されます。Samba 3.0.6サーバーまたはそれ以降のバージョンでは、サーバー上で不安全なシンボリックリンク（共有外のサーバーのファイルを参照するリンク）をSamba固有の形式に変換し、ローカルのサーバーアプリケーションや非CIFSクライアントには無視されるようにして、Sambaサーバーがトラバースしないようにします。これはLinuxクライアントアプリケーションがcifs vfsを使用する場合に透明です。絶対パスのシンボリックリンクはSamba 3.0.5以降で動作しますが、リモートクライアントでCIFS Unix拡張機能を使用する場合に限られ、Windowsクライアントには見えず、通常は同じサーバー上で動作するローカルアプリケーションには影響を与えません。

使用手順¶

CIFS VFSのサポートがカーネルに組み込まれているか、モジュール（cifs.ko）としてインストールされている場合、以下のマウント構文を使用してSambaやMac、Windowsサーバーにアクセスできます：

mount -t cifs //9.53.216.11/e$ /mnt -o username=myname,password=mypassword

マウント時に-oオプションの前に-vを指定すると、mount.cifsマウントヘルパーがマウントステップをより詳細に表示します。-oの後にサポートされる一般的なcifs vfs固有のオプションは以下の通りです：

username=<username>
password=<password>
domain=<domain name>

他のcifsマウントオプションについては下記に説明します。mount.cifsマウントヘルパーがインストールされている場合、TCP名（IPアドレスに加えて）を使用できます。信頼できないサーバーにマウントする場合、またはcifs署名が有効でない（物理的なネットワークが不安全な場合）場合は、標準のマウントオプションを使用することを検討してください。 noexec および nosuid ローカルシステムで変更されたバイナリを実行するリスクを減らすため（敵対的なサーバーからダウンロードされたものや、敵対的なルーターによって変更されたもの）。

mount.cifsではCIFS URL仕様に準拠したマウントがまだ可能ではありませんが、サーバーと共有名の代替フォーマット（NFSスタイルのマウント構文にやや似た形式）を使用することで、より一般的なUNC形式（例: \servershare）ではなく、代わりに使用できます。

mount -t cifs tcp_name_of_server:share_name /mnt -o user=myname,pass=mypasswd

mount.cifsを使用する場合、パスワードはコマンドラインで-oオプションで指定する通常の構文ではなく、代替メカニズムで指定できます。 pass= パスワードを資格情報ファイルに含めることで指定できます。マウントオプションとしてcredentials=ファイル名を指定してください。資格情報ファイルには2行が含まれます：

username=someuser
password=your_password

  1. PASSWD環境変数でパスワードを指定します（ユーザー名はUSER環境変数から取得できます）。

  2. PASSWD_FILEを通じて名前付きファイルでパスワードを指定します

  3. PASSWD_FDを通じてファイル記述子でパスワードを指定します

パスワードが指定されていない場合、mount.cifsはパスワード入力を求めます

制限事項¶

サーバーは「pure-TCP」（ポート445のTCP/IP CIFS接続）またはRFC 1001/1002の「Netbios-Over-TCP/IP」サポートをサポートする必要があります。これはほとんどのサーバーがサポートしているため、問題になる可能性は低いです。

有効なファイル名はWindowsとLinuxで異なります。Windowsでは特定の予約文字（例: ストリーム名の開始を区切るための':'文字）を含むファイル名を制限していますが、Linuxではやや広範な有効文字が許容されます。Windowsサーバーは、サーバーのレジストリで明示的なマッピングが指定されている場合に、このような文字を再マッピングできます。Samba 3.10以降は、サーバーがUnix拡張機能で構成されており（クライアントが/proc/fs/cifs/LinuxExtensionsEnabledを無効にしていない場合）、Windows/CIFS semanticsで禁止される文字を含むファイル名（つまり有効なLinux文字を含むファイル名）を許可します。さらに、CIFS（vers=1.0）でマウントオプション mapposix を指定することで、不正なWindows/NTFS/SMB文字を再マッピング範囲にマッピングできます（このマウントパラメータはSMB3のデフォルトです）。この再マッピング（mapposix)範囲はまた、Mac（および一部の古いWindowsでの「Services for Mac」）にも互換性があります。

CIFS VFSマウントオプション¶

サポートされているマウントオプションの一覧は以下の通りです：

username

CIFSセッションを確立する際に使用するユーザー名。

password

ユーザーのパスワード。mount helperがインストールされている場合、パスワードが指定されていない場合はユーザーにパスワード入力を求めます。

ip

ターゲットサーバーのIPアドレス

unc

マウントするためのターゲットサーバーのユニバーサルネットワーク名（エクスポート）

ドメイン

CIFSセッション確立時にユーザー名の前に追加されるSMB/CIFSワークグループ名を設定

forceuid

マウント時に渡されたuidをinodeのデフォルトuidとして設定します。CIFS Unix拡張機能をサポートしているサーバー（適切に設定されたSambaサーバーなど）へのマウントでは、サーバーがuid、gid、モードを提供するため、このパラメータはサーバーとクライアントのuid/gid番号が異なっている場合にのみ指定する必要があります。サーバーとクライアントが同じドメイン（例: winbindやnss_ldapを実行中）にあり、サーバーがUnix拡張機能をサポートしている場合、uidとgidはサーバーから取得できます（マウント時にuidとgidを指定する必要はありません）。CIFS Unix拡張機能をサポートしていないサーバーでは、既存ファイルの検索時に返されるデフォルトuid（gid）は、マウントを実行したユーザー（root、mount.cifsがユーザーマウント用にsetuidで構成されていない場合を除く）のuid（gid）になります。ただし、(gid) マウントオプションを指定した場合を除き、 uid= (gid) マウントオプションを指定した場合を除き、ファイルへのアクセス時の権限チェック（認証チェック）はサーバー側で行われますが、管理者がクライアント側でも制限を望む場合があります。Windowsなどのuid/gid所有者を報告しないサーバーでは、クライアント側でも権限チェックを行い、file_modeとdir_modeをクライアント側で指定することで、粗いクライアント側の権限チェックを有効化できます（デフォルト）。

forcegid

(uidではなくgidについての上記と同じ)（デフォルト）

noforceuid

サーバーからuid情報を取得可能であれば、ファイルオーナー情報を埋め込む。このオプションを指定すると、uid=オプション（マウント時）で指定した値は、サーバーがinodeのuidを返すことができない場合にのみ使用されます。

noforcegid

(uidではなくgidについての上記と同じ)

uid

inodeのデフォルトuidを設定し、cifsカーネルドライバーにローカルユーザーがマウントしたことを示します。サーバーがUnix拡張機能をサポートしている場合、inode（ファイル）のオーナー情報は、このパラメータが指定されていない限り使用されません。 forceuid パラメータを指定した場合。

gid

inodeのデフォルトgidを設定します（上記と同様）。

file_mode

サーバーがCIFS Unix拡張機能をサポートしない場合、ファイルinodeのデフォルトモードを上書きします。

fsc

FS-Cacheを使用してローカルディスクキャッシュを有効にする（デフォルトでは無効）。このオプションは、遅い接続や負荷の高いサーバーおよび/またはネットワーク環境で、ディスクから読み込むのがサーバーから読み込むより速い場合に、パフォーマンス向上に役立つ可能性があります。サーバーへの呼び出し回数が減少するため、スケーラビリティにもポジティブな影響を与える可能性があります。ただし、ローカルキャッシュはすべてのワークロードに適しているわけではありません。たとえば、一度しか読み込まないタイプのワークロードでは不適切です。そのため、このオプションを使用する前に、ワークロードやシナリオを慎重に検討する必要があります。現在、ローカルディスクキャッシュは読み取り専用で開かれたCIFSファイルに対して機能します。

dir_mode

サーバーがCIFS Unix拡張機能をサポートしない場合、ディレクトリinodeのデフォルトモードを上書きします。

port

通常のポート（ポート445、その後はポート139）を試す前に、このTCPポートでサーバーに接続を試みます。

iocharset

ローカルのパス名をUnicodeに変換するためのコードページ。サーバーがUnicodeをサポートする場合、ネットワークパス名にはデフォルトでUnicodeが使用されます。iocharsetを指定しない場合、ローカルクライアントカーネルビルド時に指定されたnls_defaultが使用されます。サーバーがUnicodeをサポートしない場合、このパラメータは無視されます。

rsize

デフォルトの読み取りサイズ（通常16K）。クライアントは現在、CIFSMaxBufSizeより大きいrsizeを使用できません。CIFSMaxBufSizeはデフォルトで16Kであり、cifs.koモジュールのインストール時に（8Kからカーネルが許可する最大kmallocサイズまで）変更可能です。CIFSMaxBufSizeを非常に大きな値に設定すると、cifsがより多くのメモリを使用し、一部のケースではパフォーマンスが低下する可能性があります。rsizeを127K（元のCIFSプロトコルの最大値）を超えて使用するには、サーバーが新しいUnix Capabilityフラグ（非常に大きな読み取りをサポート）をサポートしている必要があります。一部の新しいサーバー（例：Samba 3.0.26以降）はこの機能をサポートしています。rsizeは最小2048から最大130048（127KまたはCIFSMaxBufSize、どちらか小さい方）まで設定可能です。

wsize

デフォルトの書き込みサイズ（デフォルト57344）。現在CIFSが許可する最大のwsizeは57344（14の4096バイトページ）です。

actimeo=n

属性キャッシュのタイムアウト（秒単位、デフォルト1秒）。このタイムアウト経過後に、cifsクライアントがサーバーから最新の属性情報を取得します。このオプションを使用して、ワークロードに応じた属性キャッシュタイムアウトを調整できます。短いタイムアウトはキャッシュ整合性をより保つが、サーバーへの呼び出し回数が増加します。長いタイムアウトはサーバーへの呼び出し回数を減らしますが、キャッシュ整合性のチェックが厳しくなくなるため、短時間の間で属性キャッシュが不正確になる可能性があります。

rw

ネットワーク共有を読み書き可能にマウント (サーバーが共有を読み取り専用としている可能性があることに注意)

ro

ネットワーク共有を読み取り専用でマウント

version

マウントヘルパーユーティリティの異なるバージョンを区別するためのオプション (通常は必要ありません)

sep

最初のマウントオプション (オプションの -o 以降) でコンマをセパレータとして使用し、マウントパラメータを区切ります。例:

-o user=myname,password=mypassword,domain=mydom

セパレータとしてドットを使用する場合は:

-o sep=.user=myname.password=mypassword.domain=mydom

ユーザー名やパスワードやドメインにコンマが含まれる場合に役立ちます。cifs.mount (バージョン 1.1 以降) が使用されている場合はこのオプションは重要ではありません。

nosuid

リモートサーバー (例: Samba) が CIFS Unix Extensions をサポートしている場合に、SUID ビットを持つ実行可能なプログラムの実行を許可しません。ネットワーク内のサーバー (マウントターゲット) を信頼できない場合は、セキュリティを高めるためにこのオプションを指定することをお勧めします。

exec

マウント先のバイナリの実行を許可します。

noexec

マウント先のバイナリの実行を許可しません。

dev

リモートマウント先のブロックデバイスを認識します。

nodev

リモートマウント先のデバイスを認識しません。

suid

このマウントポイントで SUID ビットが有効なリモートファイルの実行を許可します (root で実行する場合のデフォルト、ユーザーがマウントする場合のデフォルトは nosuid)

credentials

cifs カーネルコンポーネントでは無視されますが、mount.cifs ヘルパーアプリケーションが使用します。mount.cifs がインストールされている場合、指定された資格情報ファイルを開き読み込み、cifs vfs に渡すユーザーIDとパスワードを取得します。

guest

カーネルコンポーネントでは無視されますが、mount.cifs ヘルパーアプリケーションがマウントオプションに guest を指定された場合、ユーザーにパスワードを入力するよう促しません。パスワードが指定されていない場合は空のパスワードが使用されます。

perm

クライアントがパーミッションチェックを行います (ファイルの uid と gid がモードと希望する操作と一致するかを確認)。注意: これはターゲットマシンでサーバーソフトウェアが行う通常の ACL チェックとは別途行われます。クライアントのパーミッションチェックはデフォルトで有効です。

noperm

クライアントは権限チェックを行いません。これにより、このマウントポイントのファイルがローカルクライアントシステム上の他のユーザーによってアクセスされる可能性があります。これは通常、サーバーがCIFS Unix拡張機能をサポートしているが、クライアントとサーバーのシステム上のUID/GIDが十分に一致していない場合に必要ですが、非CIFS Unix拡張機能のマウントでは、マウント時に指定されたデフォルトモードがクライアントで強制されない場合に役立つことがあります（例：MultiUserMountが有効になっている場合）。注意点として、これはターゲットマシンでの通常のACLチェック（サーバーのACLとマウント時のユーザー名の比較）には影響を与えません。

serverino（サーバーのインノード番号を使用する）

クライアントではなく、サーバーのインノード番号を使用します。これによりハードリンクファイルの特定が容易になります（同じインノード番号を持つため）またインノード番号が永続的になる可能性がありますが、複数のサーバー側マウントが単一の共有にエクスポートされている場合、サーバーのインノード番号が一意でない可能性があるため、サーバーは一意性を保証しません（複数のファイルシステムが同じ共有上位ディレクトリにマウントされている場合）。注意点として、一部の古いシステム（例：Windows 2000以前）はUniqueIDsやCIFS Unix拡張機能の同等機能をサポートしていないため、このようなマウントオプションは効果を持たない場合があります。NFSドーマントの下でCIFSマウントをエクスポートするにはこのマウントオプションが必要です。現在では、サーバーが必要なネットワーク操作をサポートしている場合、これがデフォルトになります。

noserverino（クライアントがインノード番号を生成する）

クライアントがインノード番号を生成します（サーバーからの実際のインノード番号を使用しません）。このインノード番号はアンマウントや再起動後に変化するため、一部のアプリケーションに混乱を招く可能性がありますが、すべてのサーバーのファイルシステムが一意のインノード番号をサポートしているわけではありません。

setuids（有効UIDとGIDを設定する）

CIFS Unix拡張機能がサーバーとネゴシエーションされた場合、クライアントは新規に作成されたファイル、ディレクトリ、デバイス（create、mkdir、mknod）のローカルプロセスの有効UIDとGIDを設定しようとします。CIFS Unix拡張機能がネゴシエーションされない場合、新規に作成されたファイルとディレクトリでは、マウント時に指定されたデフォルトUIDとGIDを使用せず、ローカルに新しいファイルのUIDとGIDをキャッシュします。これにより、インノードが再ロードされるか、ユーザーが共有を再マウントした際にファイルのUIDが変化する可能性があります。

nosetuids（有効UIDとGIDを設定しない）

クライアントは、新規に作成されたファイル、ディレクトリ、およびデバイス（create、mkdir、mknod）に対してuidとgidを設定しようとしません。これにより、サーバーがデフォルト（通常は共有をマウントしたユーザーのサーバーuid）をuidとgidとして設定します。サーバー（クライアントではなく）がuidとgidを設定する設定はデフォルトです。CIFS Unix拡張機能がネゴシエーションされない場合、新規ファイルのuidとgidはマウントしたユーザーのuid（gid）またはマウント時に指定したuid（gid）パラメータとして表示されます。

netbiosname

ポート139経由でサーバーにマウントする際、RFC1001ネットBIOSセッション初期化時にクライアントのネットBIOSマシン名を表すRFC1001ソース名を指定します。

direct

このマウントで開かれたファイルのinodeデータキャッシュを行いません。これにより、このマウントでのmmapping（メモリマップ）が不可能になります。高速なネットワーク環境でクライアント側のキャッシュ効果がほとんどない場合（例：アプリケーションがページサイズより大きいデータの連続読み込みを行い、同じデータを再読み込みしない場合）、oplock（キャッシュトークン）が許可され保持されている場合、デフォルトの読み取り（readahead）と書き込み（writebehind）のローカルLinuxクライアントpagecache経由のキャッシュよりもパフォーマンスが向上する可能性があります。注意：directモードでは、ページサイズより大きい書き込み操作をサーバーに送信できます。

strictcache

厳格なキャッシュモードを有効にします。このモードでは、クライアントがOplock Level IIを持っている間は常にキャッシュから読み込み、それ以外はサーバーから読み込みます。すべての書き込みデータはキャッシュに保存されますが、クライアントが排他的Oplockを持っていない場合、データをサーバーに書き込みます。

rwpidforward

ファイルを開いたプロセスのpidをそのファイルの読み込みまたは書き込み操作に向けたすべての操作に転送します。これにより、WINEなどのアプリケーションがMandatory brlockスタイルを使用する際に読み込み・書き込みで失敗するのを防ぎます。

acl

サーバーがサポートする場合、setfaclおよびgetfaclを用いてPOSIX ACLを管理できます。（デフォルト）

noacl

このマウントでsetfaclおよびgetfaclコールを許可しません。

user_xattr

ユーザーのxattrs（名前が"で始まる属性）をOS/2の拡張属性（EAs）としてサーバーに送信できます。これにより、setfattrおよびgetfattrユーティリティのサポートが可能になります。（デフォルト） user. または os2.)

nouser_xattr

getfattr/setfattrを用いてxattrsを取得・設定・一覧表示できません。

mapchars

7つの予約文字のうち6つの文字（バックスラッシュを除く）を変換します：

*?<>|:

リマップ範囲（0xF000以上）に設定することで、CIFSクライアントがWindowsのPOSIXエミュレーションで作成されたファイルを認識できるようになります。これは、Sambaのほとんどのバージョンにマウントする際にも役立ちます（Sambaもこれらの7つの文字を含むファイルの作成や開けを禁止しています）。サーバーがワイヤー上でのUnicodeをサポートしていない場合、このオプションは効果を持ちません。

nomapchars

これらの7つの文字をすべて翻訳しない（デフォルト）。

nocase

パス名のケースを区別しないマッチングを要求（サーバーがサポートする場合、ケースを区別するがデフォルト）。（マウントオプション ignorecase は次のマウントオプションと同一です nocase)

posixpaths

CIFS Unix拡張機能がサポートされている場合、リマップせずに通常のCIFSファイル名で禁止されている特定の文字を許可するPOSIXパス名サポートを交渉を試みる。（デフォルト）

noposixpaths

CIFS Unix拡張機能がサポートされている場合、POSIXパス名サポートの要求を行わない（これにより、サーバーが特定の予約文字を含むファイルの作成を拒否する可能性があります）。

nounix

このマウント（ツリー接続）でCIFS Unix拡張機能を無効にする。これはほとんど必要ありませんが、複数の設定を一度に無効にする（posix acls、posix locks、posix paths、シンボリックリンクサポート、サーバーからUID/GID/モードの取得）ために、またはUnix拡張機能を実装したサーバーのバグを回避するために役立つ場合があります。

nobrl

サーバーにバイトレンジロック要求を送信しない。これは、cifsスタイルの強制バイトレンジロックで動作を破損する特定のアプリケーションのために必要です（ほとんどのcifsサーバーはまだアドバイザリーバイトレンジロックの要求をサポートしていません）。

forcemandatorylock

サーバーがPOSIX（アドバイザリー）バイトレンジロックをサポートしていても、強制ロック要求のみを送信する。一部の（おそらくレアな）アプリケーション、DOS/Windows用に最初にコードされたもので、Windowsスタイルの強制バイトレンジロックを必要とする場合、このオプションにより、cifsクライアントがPOSIXアドバイザリーロックをサポートするcifsサーバーであっても強制ロックのみを送信するよう強制的にできます。 forcemand これはこのマウントオプションの短い形式として受け入れられます。

nostrictsync

このマウントオプションが設定されている場合、アプリケーションがfsyncコールを実行すると、cifsクライアントはサーバーにSMB Flushを送信しない（これにより、サーバーがこのファイルのすべての汚れたデータを即座にディスクに書き出すように強制する）。ただし、cifsは依然としてすべての汚れた（キャッシュされた）ファイルデータをサーバーに送信し、サーバーからの応答を待つ。SMB Flushは非常に遅く、一部のサーバーはデータをディスクに書き出すのを少し遅らせることを許容できる場合があるため、このオプションを有効にすると、fsyncを過剰に使用するアプリケーションのパフォーマンス向上に役立つ可能性があるが、サーバークラッシュのリスクがわずかにある。

nodfs

DFS（グローバルネームスペースサポート）を無効化します（サーバーがこれをサポートしていると主張していても）。これは、Sambaサーバーのバージョン3.0.24および3.0.25でDFSパスの解析に問題がある場合に、回避策として役立ちます。

remount

共有を再マウントする（通常、読み取り専用から読み取り/書き込みへの変更やその逆を行うために使用されます）

cifsacl

ファイルのWindows ACLに基づいてモードビット（例：statで）を報告します。（実験的）

servern

セッションを確立する際に使用するサーバーのNetBIOS名（RFC1001名）を指定します。これは、OS/2やWindows 98、Windows MEなどの古いサーバーにマウントする際に必要です（それらはデフォルトのサーバー名をサポートしていないため）。サーバー名は最大15文字までで、通常大文字で表示されます。

sfu

CIFS Unix拡張機能がネゴシエーションされない場合、Services for Unix（SFU）と互換性のある形式でデバイスファイルやfifoを生成しようとします。また、SETFILEBITS拡張属性（SFUが行うように）を介してモードのビット10〜12を取得します。今後は、セキュリティドキュメント（ACL）のクエリを使用して、モードの下位9ビットもエミュレートされる予定です。

mfsymlinks

Minshall+Frenchシンボリックリンクのサポートを有効にします（参照 http://wiki.samba.org/index.php/UNIX_Extensions#Minshall.2BFrench_symlinks）。このオプションは'sfu'オプションとともに指定された場合無視されます。Minshall+Frenchシンボリックリンクは、サーバーがCIFS Unix拡張機能をサポートしている場合でも使用されます。

sign

パケット署名を必須とします（ルート上の中間システムによる不正データ変更を防ぐのに役立ちます）。注意：署名はlanmanまたは平文認証と併用できません。

seal

このマウントされた共有のすべてのデータをネットワーク送信前に暗号化（エンクリプション）します。Unix拡張機能のサポートが必要です。注意：これは'sign'マウントオプションとは異なり、このマウントされた共有を介して送信されるデータの暗号化を引き起こしますが、同じサーバーにマウントされた他の共有には影響を与えません。

locallease

このオプションはほとんど必要ありません。Fcntl F_SETLEASEは、SambaやNFSv4サーバーなどのアプリケーションでファイルがキャッシュ可能かどうかを確認するために使用されます。CIFSは明示的なリースのリクエストを行う方法がありませんが、ファイルがキャッシュ可能かどうか（oplocked）を確認できます。残念ながら、ファイルがoplockedでない場合でも、キャッシュ可能である可能性があります（つまり、cifsクライアントが他のローカルプロセスがファイルを使用していない場合にfcntlリースを許可する可能性があります）。たとえば、サーバーがoplocksをサポートしていない場合や、ユーザーがこのクライアントからのみファイルの更新を行うことを確信している場合などです。このマウントオプションを指定すると、cifsクライアントはoplockedでないファイルに対してローカルでリースを確認できるようになります（この場合、リースを拒否するのではなく）。(EXPERIMENTAL)

sec

セキュリティモード。許可される値は以下の通りです：

none

nullユーザーとして接続を試みる（名前なし）

krb5

Kerberos v5認証を使用する

krb5i

Kerberos認証とパケット署名を使用する

ntlm

NTLMパスワードハッシュを使用する（デフォルト）

ntlmi

NTLMパスワードハッシュと署名を使用する（/proc/fs/cifs/PacketSigningEnabledが有効になっているか、サーバーが署名を要求している場合にもデフォルト値となる可能性あり）

ntlmv2

NTLMv2パスワードハッシュを使用する

ntlmv2i

NTLMv2パスワードハッシュとパケット署名を使用する

lanman

(カーネル設定で有効にされている場合) 旧版のlanmanハッシュを使用する

hard

サーバーが応答しない場合でもファイル操作を再試行する

soft

応答しないサーバーに対してリトライを制限する（通常は1回のリトライのみ）後、エラーを返す。（デフォルト）

その他の /proc/fs/cifs フラグとデバッグ情報¶

情報表示用の擬似ファイル：

DebugData

アクティブなCIFSセッションと共有、有効な機能、cifs.koバージョンに関する情報を表示します。

Stats

リソース使用状況のサマリ情報と各共有ごとの統計情報を表示します。

設定用の擬似ファイル：

SecurityFlags

セキュリティ交渉を制御するフラグおよびパケット署名を制御するフラグです。認証（必須/可能）フラグ（例：NTLMおよび/またはNTLMv2の場合）は署名フラグと組み合わせて使用できます。一方、2つの異なるパスワードハッシュメカニズム（「必須」で指定）を同時に指定すると意味がありません。デフォルトフラグは以下の通りです：

0x07007

(NTLM, NTLMv2およびパケット署名が許可されます)。弱いパスワードハッシュを使用してサーバーへのマウントを許可したい場合の最大許可フラグは0x37037（lanman、plaintext、ntlm、ntlmv2、署名が許可されます）です。一部のセキュリティフラグは、対応するメニュー構成オプションが有効になっている必要があります（例：lanmanおよびplaintextはCONFIG_CIFS_WEAK_PW_HASHを必要とします）。PLAINTEXT認証を有効にするには、セキュリティフラグでlanman認証も同時に有効にする必要があります。なぜなら、cifsモジュールは古いlanmanダイクレット形式のセッションセットアップSMBを使用してみみみみテキストパスワードを送信するみみみみのみサポートするからです。（例：PLAINTEXTパスワードで認証する場合、セキュリティフラグを0x30030に設定します）

must use packet signing                       0x01001
may use NTLM (most common password hash)      0x00002
must use NTLM                                 0x02002
may use NTLMv2                                0x00004

cifsFYI

非ゼロ値に設定すると、システムエラー日志に追加のデバッグ情報がログ出力されます。このフィールドには、異なるデバッグエントリのクラスを制御する3つのフラグが含まれています。最大値は7で、これによりすべてのデバッグポイントが有効になります（デフォルトは0）。一部のデバッグステートメントは、カーネル構成でCONFIG_CIFS_DEBUG2が有効になっていない限りcifsカーネルにコンパイルされません。cifsFYIは次のフラグの1つまたは複数に設定可能で（7に設定するとすべて有効になります）：

+-----------------------------------------------+------+
| log cifs informational messages               | 0x01 |
+-----------------------------------------------+------+
| log return codes from cifs entry points       | 0x02 |
+-----------------------------------------------+------+
| log slow responses                            | 0x04 |
| (ie which take longer than 1 second)          |      |
|                                               |      |
| CONFIG_CIFS_STATS2 must be enabled in .config |      |
+-----------------------------------------------+------+

traceSMB

1に設定すると、SMBリクエストとレスポンスの開始時にシステムエラー日志にデバッグ情報がログ出力されます（デフォルトは0）

LookupCacheEnable

1に設定すると、inode情報が1秒キャッシュされ、検索のパフォーマンスが向上します（デフォルトは1）

LinuxExtensionsEnabled

1に設定すると、クライアントがCIFS「UNIX」拡張機能を使用しようとします。これはオプションのプロトコル拡張機能で、CIFSサーバーが正確なUID/GID情報を返し、シンボリックリンクをサポートするためのものです。SambaなどのCIFS Unix拡張機能をサポートするサーバーを使用するが、シンボリックリンクサポートを使いたくない場合、uidとgidフィールドをマウント時に指定された値にマッピングしたい場合は、この値をゼロに設定してください（デフォルトは1）

これらの実験的機能およびトレーシングは、/proc/fs/cifs内のフラグを変更することで有効になります（cifsモジュールがインストールまたはカーネルに組み込まれた後、例：insmod cifs）。機能を有効にするには1に設定します。例として、カーネルメッセージログへのトレーシングを有効にするには：

echo 7 > /proc/fs/cifs/cifsFYI

cifsFYIはビットマスクとして機能します。1に設定すると、さまざまな情報メッセージの追加的なカーネルログ出力が有効になります。2に設定すると、ゼロでないSMB戻りコードのログ出力が有効になり、4に設定すると、1秒以上かかるリクエスト（バイト範囲ロックリクエストを除く）のログ出力が有効になります。4に設定するには、カーネル構成（.config）にCONFIG_CIFS_STATS2が設定されている必要があります。7に設定すると、すべての機能が有効になります。最後に、SMBリクエストおよび応答の開始をトレースするには以下の方法があります。

echo 1 > /proc/fs/cifs/traceSMB

/proc/fs/cifs/Statsに、共有ごとの（クライアントマウントごとの）統計情報があります。カーネル構成（.config）にCONFIG_CIFS_STATS2が有効になっている場合、さらに詳しい情報が得られます。返却される統計情報には、リクエストタイプ（読み取り、書き込み、クローズなど）ごとに、試行されたおよび失敗した（つまりサーバーからのゼロでない戻りコードを持つ）SMB3（またはcifs）リクエストのカウンターが含まれます。また、その共有に対してサーバーに読み込まれたバイト数および書き込まれたバイト数の合計も記録されます。注意点として、クライアントのキャッシュ効果により、アプリケーションがクライアントで読み書きしたバイト数より少ない場合があります。統計情報は以下のコマンドでゼロに戻すことができます。 echo 0 > /proc/fs/cifs/Stats これは、2つの異なるシナリオのパフォーマンスを比較する際に役立つかもしれません。

また、以下の点に注意してください。 cat /proc/fs/cifs/DebugData は、アクティブなセッションとマウントされた共有に関する情報を表示します。

ケルベロス（拡張セキュリティ）の有効化は可能ですが、ヘルパープログラムcifs.upcallのバージョン1.2以降が必要であり、/etc/request-key.confファイルに設定されている必要があります。cifs.upcallヘルパーはSambaプロジェクトから提供されています（https://www.samba.org）。NTLMおよびNTLMv2、LANMANのサポートはこのヘルパーを必要としません。注意点として、NTLMv2セキュリティ（cifs.upcallヘルパーを必要としない）は、ケルベロスを使用せずとも、一部のユースケースには十分です。

DFSサポートにより、MS-DFSネームスペース内の共有への透明なリダイレクトが可能になります。さらに、UNC名で指定されたターゲット共有がホスト名（IPアドレスではなく）で始まる場合、ホスト名をIPアドレスに変換するためのユーザー空間のヘルパー（cifs.upcallなど）が必要であり、このユーザー空間のヘルパーは/etc/request-key.confファイルにも設定する必要があります。Samba、Windowsサーバー、多くのNASアプライアンスは、ネットワーク構成を簡素化し信頼性を向上させるためにDFSをグローバルネームスペースの構築方法としてサポートしています。

cifs KerberosおよびDFSのサポートを使用するには、Linuxのkeyutilsパッケージをインストールし、以下の行を/etc/request-key.confファイルに追加する必要があります：

create cifs.spnego * * /usr/local/sbin/cifs.upcall %k
create dns_resolver * * /usr/local/sbin/cifs.upcall %k

CIFSカーネルモジュールパラメータ¶

これらのモジュールパラメータは、モジュールのロード時にまたはランタイム中にインターフェースを使用して指定または変更できます：

/proc/module/cifs/parameters/<param>

i.e.:

echo "value" > /sys/module/cifs/parameters/<param>

  1. enable_oplocks

oplocksを有効にするか無効にするか。デフォルトでは有効になっています。[Y/y/1]。無効にするには、[N/n/0]のいずれかを使用してください。

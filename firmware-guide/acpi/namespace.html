要約¶

Linux ACPIサブシステムは、ACPIネームスペースのオブジェクトをLinuxデバイスツリーに変換し、/sys/devices/LNXSYSTEM:00以下の下に配置します。この階層の各デバイスオブジェクトには、/sys/bus/acpi/devicesに該当するシンボリックリンクが存在します。

このドキュメントでは、ACPIデバイスツリーの構造を説明しています。

ACPI定義ブロック¶

ACPIファームウェアは、システムメモリアドレス空間にRSDP（Root System Description Pointer）を設定し、XSDT（Extended System Description Table）へのポインタを指します。XSDTは常にその最初のエントリとしてFADT（Fixed ACPI Description Table）へのポインタを指します。FADT内のデータは、ハードウェアの固定長のエントリを含み、固定されたACPI機能を記述します。FADTはDSDT（Differentiated System Description Table）へのポインタを含みます。XSDTは複数のSSDT（Secondary System Description Table）へのポインタを含むエントリも持つことがあります。

DSDTおよびSSDTのデータは、定義ブロックと呼ばれるデータ構造に整理されており、ACPI制御メソッドなどのさまざまなオブジェクトの定義を含み、AML（ACPI Machine Language）で符号化されています。DSDTのデータブロックとSSDTの内容は、ACPIネームスペースと呼ばれる階層的なデータ構造を形成し、そのトポロジーは基盤となるハードウェアプラットフォームの構造を反映しています。

上記のACPIシステム定義テーブル間の関係は、以下の図に示されています：

+---------+    +-------+    +--------+    +------------------------+
|  RSDP   | +->| XSDT  | +->|  FADT  |    |  +-------------------+ |
+---------+ |  +-------+ |  +--------+  +-|->|       DSDT        | |
| Pointer | |  | Entry |-+  | ...... |  | |  +-------------------+ |
+---------+ |  +-------+    | X_DSDT |--+ |  | Definition Blocks | |
| Pointer |-+  | ..... |    | ...... |    |  +-------------------+ |
+---------+    +-------+    +--------+    |  +-------------------+ |
               | Entry |------------------|->|       SSDT        | |
               +- - - -+                  |  +-------------------| |
               | Entry | - - - - - - - -+ |  | Definition Blocks | |
               +- - - -+                | |  +-------------------+ |
                                        | |  +- - - - - - - - - -+ |
                                        +-|->|       SSDT        | |
                                          |  +-------------------+ |
                                          |  | Definition Blocks | |
                                          |  +- - - - - - - - - -+ |
                                          +------------------------+
                                                       |
                                          OSPM Loading |
                                                      \|/
                                                +----------------+
                                                | ACPI Namespace |
                                                +----------------+

               Figure 1. ACPI Definition Blocks

注意

RSDPは、RSDT（Root System Description Table）へのポインタも含むことがあります。プラットフォームはACPI 1.0のオペレーティングシステムとの互換性を確保するためにRSDTを提供します。OSはXSDTが存在する場合、それを使用することが期待されます。

例: ACPIネームスペース¶

すべての定義ブロックは単一のネームスペースにロードされます。ネームスペースは、名前とパスで識別されるオブジェクトの階層です。ACPIネームスペースのオブジェクト名には次の命名規則が適用されます：

  1. すべての名前は32ビット長です。

  2. 名前の最初のバイトは'A'-'Z'、'_'のいずれかでなければなりません。

  3. 名前の残りのバイトは'A'-'Z'、'0'-'9'、'_'のいずれかでなければなりません。

  4. '_'で始まる名前はACPI仕様によって予約されています。

  5. ' '記号はネームスペースのルートを表します（つまり、' 'で始まる名前はネームスペースルートに対して相対です）。

  6. ‘^’記号は、現在の名前空間ノードの親を表します（つまり、‘^’で始まる名前は、現在の名前空間ノードの親に基づいています）。

Linux ACPIデバイスオブジェクト¶

LinuxカーネルのコアACPIサブシステムは、ACPI名前空間オブジェクトで表されるデバイス、電源リソースプロセッサ、熱帯域を表すstruct acpi_deviceオブジェクトを作成します。これらのオブジェクトは、sysfsを介してユーザー空間にエクスポートされ、/sys/devices/LNXSYSTM:00以下のサブツリーにディレクトリとして表示されます。名前の形式は<バスID:インスタンス>で、‘バスID’は指定されたオブジェクトのACPI名前空間表現を指し、‘インスタンス’は同じ‘バスID’を持つ異なるオブジェクトを区別するために使用されます（これは無符号整数の2桁の十進数表現です）。

‘バスID’の値は、以下の表に示すように、オブジェクトの種類によって異なります。

+---+-----------------+-------+----------+
|   | Object/Feature  | Table | bus_id   |
+---+-----------------+-------+----------+
| N | Root            | xSDT  | LNXSYSTM |
+---+-----------------+-------+----------+
| N | Device          | xSDT  | _HID     |
+---+-----------------+-------+----------+
| N | Processor       | xSDT  | LNXCPU   |
+---+-----------------+-------+----------+
| N | ThermalZone     | xSDT  | LNXTHERM |
+---+-----------------+-------+----------+
| N | PowerResource   | xSDT  | LNXPOWER |
+---+-----------------+-------+----------+
| N | Other Devices   | xSDT  | device   |
+---+-----------------+-------+----------+
| F | PWR_BUTTON      | FADT  | LNXPWRBN |
+---+-----------------+-------+----------+
| F | SLP_BUTTON      | FADT  | LNXSLPBN |
+---+-----------------+-------+----------+
| M | Video Extension | xSDT  | LNXVIDEO |
+---+-----------------+-------+----------+
| M | ATA Controller  | xSDT  | LNXIOBAY |
+---+-----------------+-------+----------+
| M | Docking Station | xSDT  | LNXDOCK  |
+---+-----------------+-------+----------+

 Table 1. ACPI Namespace Objects Mapping

ACPIシステム記述テーブルの内容に基づいてstruct acpi_deviceオブジェクトを作成する際には、以下のルールが適用されます。

N:

オブジェクトのソースはACPI名前空間ノード（以下の表の2列目に示すオブジェクトの種類）です。その場合、sysfsのオブジェクトディレクトリには‘path’属性が含まれ、その値は名前空間ルートからのノードのフルパスを示します。

F:

struct acpi_deviceオブジェクトは固定ハードウェア機能（以下の表の2列目に示す固定機能フラグの名前）に対応するため、sysfsディレクトリには‘path’属性が含まれません。

M:

struct acpi_deviceオブジェクトは、特定の制御メソッドを持つACPI名前空間ノード（以下の表の2列目に示すACPI定義デバイスの種類）に対応します。その名前空間パスを含む‘path’属性がsysfsディレクトリに存在します。たとえば、ACPI名前空間ノードに_BCLメソッドが存在する場合、そのノードに対応するLNXVIDEO ‘バスID’を持つstruct acpi_deviceオブジェクトが作成されます。

上記の表の3列は、struct acpi_deviceオブジェクトを生成するために使用されるACPIシステム記述テーブルを示します（xSDTはDSDTまたはSSDTを指します）。

上記の表の4列は、struct acpi_deviceオブジェクトの‘バスID’生成ルールを示します：

_HID:

テーブルの最後の列に表示される_HIDは、対応するACPI Namespaceノード下にある_HID/_CID識別オブジェクトからオブジェクトのbus_idが導出されることを示します。この場合、オブジェクトのsysfsディレクトリには_HIDおよび_modalias属性が含まれており、それらを用いてオブジェクトの_HIDおよび_CIDを取得できます。

LNXxxxxx:

「modalias」属性は、「LNXxxxxx」形式のbus_idを持つstruct acpi_deviceオブジェクト（擬似デバイス）にも存在します。この場合、属性はbus_id文字列そのものを含みます。

デバイス:

テーブルの最後の列に表示される「device」は、対応するACPI Namespaceノードの_HID/_CIDからオブジェクトのbus_idを特定できないものの、そのオブジェクトがデバイスを表していることを示します（例: _ADRが定義されており_HIDや_CIDが定義されていないPCIデバイス）。このような場合、オブジェクトのbus_idとして「device」文字列が使用されます。

Linux ACPI物理デバイス接続¶

ACPIデバイス（つまりstruct acpi_device）オブジェクトは、Linuxのデバイス階層内の「物理デバイス」を表す他のオブジェクト（例: PCIバス上のデバイス）とリンクされることがあります。このような場合、ACPIデバイスオブジェクトは別の方法で表されるデバイスの「同伴デバイス」として機能し、以下の2つの役割を果たします：(1) 他の方法では取得できないデバイスの構成情報の提供、(2) ACPI制御メソッドを活用したデバイスに対する特定の操作。1つのACPIデバイスオブジェクトは複数の「物理デバイス」にリンクされることがあります。

ACPIデバイスオブジェクトが「物理デバイス」にリンクされている場合、そのsysfsディレクトリにはターゲットデバイスオブジェクトのsysfsディレクトリへの「physical_node」シンボリックリンクが含まれます。逆に、ターゲットデバイスのsysfsディレクトリには、同伴ACPIデバイスオブジェクトのsysfsディレクトリへの「firmware_node」シンボリックリンクが含まれます。このリンクメカニズムはACPI Namespaceによるデバイス識別に依存しています。例えば、PCIブリッジのACPI Namespaceオブジェクト下にあるPCIデバイス（つまり、_ADRが0x00020000を返し、親PCIブリッジのバス番号が0であるデバイス）が存在する場合、そのACPI Namespaceオブジェクトに対応するstruct acpi_deviceオブジェクトのsysfsディレクトリには、対応するPCIデバイスの/sys/devices/pci0000:00/0000:00:02:0/ sysfsディレクトリへの「physical_node」シンボリックリンクが含まれます。

リンクメカニズムは一般的にバス固有です。その実装のコアはdrivers/acpi/glue.cファイルに位置していますが、バスタイプに応じた補完部分は他の場所にも存在します。たとえば、PCI固有の部分はdrivers/pci/pci-acpi.cにあります。

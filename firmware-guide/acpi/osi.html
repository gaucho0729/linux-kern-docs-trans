ACPI _OSI および _REV メソッド¶

ACPI BIOS は、「Operating System Interfaces」(_OSI) メソッドを使用して、オペレーティングシステムがサポートする機能を確認できます。例として、BIOS の AML コードに _OSI("XYZ") が含まれている場合、カーネルの AML インタプリタがそのメソッドを評価し、"XYZ" をサポートしているかどうかを確認して YES または NO と BIOS に応答します。

ACPI _REV メソッドは、"OSPM がサポートする ACPI 仕様のバージョン" を返します。

このドキュメントでは、BIOS と Linux がこれらのメソッドを使用する方法と理由を説明しています。また、これらが広く誤用されている理由も説明しています。

_OSI の使用方法¶

Linux は、OEM が Linux との互換性を確認した機種と、Linux を元の OS（Windows や OSX）に代わりにインストールした機種の 2 群に分類されます。

より多くの機種は Windows での動作をテストしたものです。さらに、多くの機種は特定の Windows バージョンでの動作をテストしたため、BIOS が _OSI を使って現在動作している Windows バージョンを確認しても、実際にテストされたのは BIOS の 1 つの経路のみです。経験上、未検証の BIOS 経路を通すと Linux は BIOS バグのカテゴリ全体に曝されてしまうため、Linux の _OSのデフォルトはすべての Windows バージョンとの互換性を主張し続けなければなりません。

しかし、Linux は実際には Windows と互換性を持ちません。また、Linux が最新の Windows バージョンを _OSI 文字列リストに追加した際にリグレッションが発生するため、Linux コミュニティも被害を受けました。そのため、今後は追加の文字列がアップストリームへの導入前に十分に検証される可能性がありますが、最終的にはすべてが追加される可能性が高いです。

OEM が同じ BIOS イメージで Linux と Windows のサポートを実現したい場合、通常は Linux に特有の挙動を扱うために何か特別な処理が必要です。このような場合、BIOS は正確に必要な情報を尋ねるべきです：

_OSI("Linux-OEM-my_interface_name") で、'OEM' は OEM 特有のハックである場合に必要で、'my_interface_name' はハックの説明で、特殊な挙動、バグ、またはバグ修正を表します。

さらに、OEM は以下のプロジェクトを通じてアップストリームの Linux にパッチを送信する必要があります： linux-acpi@vger.kernel.org メールリスト。そのパッチがLinuxに導入されると、OSはOEMのシステムのBIOSが_OS_を介してインターフェースがOSによってサポートされているか尋ねるときに「YES」と応じます。Linuxディストリビューションは、そのパッチをLinuxの事前インストール用にバージョンアップして導入でき、すべてのアップストリームにリベースするディストリビューションで含まれます。カーネルバイナリを更新できないディストリビューションは、必要な場合にブートロー�ーダーにacpi_osi=Linux-OEM-my_interface_nameというコマンドラインパラメータを追加することもできます。

その文字列が、アップストリームのカーネルが最終的にサポートを拡張する機能を指している場合、カーネルにそのサポートが追加されたときにその文字列を削除するパッチを送信すべきです。

それはずいぶん簡単だった。続きを読み、間違った方法で行う方法を学ぼう。

_OSI以前には、_OSがあった¶

ACPI 1.0では、「_OS」を「オペレーティングシステムを識別する文字列を評価するオブジェクト」と定義していました。

ACPI BIOSフローでは、_OSの評価が含まれ、カーネル内のAMLインタプリタはOSを識別する文字列を返します:

Windows 98, SE: 「Microsoft Windows」Windows ME: 「Microsoft WindowsME:Millenium Edition」Windows NT: 「Microsoft Windows NT」

その考え方は、複数のOSを実行するプラットフォームで、BIOSが_OSを介してOSがサポートするデバイスを有効化したり、その既存のOSとの互換性を確保するためのクイックやバグ修正を有効化したりするためのものでした。

しかし、_OSには根本的な問題がありました。まず、BIOSはそのBIOSが実行する可能性のあるすべてのOSのバージョン名を知る必要があり、それらのOSのすべてのクイックを把握する必要がありました。もちろん、BIOSがOSに特定のインターフェースをサポートしているか尋ねる方がより論理的です。 特定の ことについてOSに尋ねる方がより論理的です。そのため、ACPI 3.0では、_OSIが生まれて_OSを置き換えました。

_OSは廃止されましたが、今日でも多くのBIOSが「Microsoft Windows NT」という_OSを検索します。しかし、機械に同梱されたOSよりも古いOSをインストールするという考えは、それほど現実的とは思えないでしょう。

LinuxはBIOSの習慣に合わせて「Microsoft Windows NT」と応じます。これは、 のみ 現行のWindowsと同様の戦略を採用しているため、そうしないとBIOSが未検証の経路に進む可能性があります。

_OSIが生まれ、すぐに誤って使われ始めました¶

_OSIでは、 BIOS がインターフェースを説明する文字列を提供し、OSに「YES/NO、このインターフェースをサポートしていますか？」と尋ねます。

例: _OSI(「3.0 Thermal Model」)は、OSがACPI 3.0仕様の熱拡張に対応している場合にTRUEを返します。古いOSはその拡張を知らないためFALSEを返し、新しいOSはTRUEを返す可能性があります。

OS固有のインターフェースについては、ACPI仕様ではBIOSとOSが「Windows-interface_name」のような形式の文字列で合意する必要があると規定していました。

しかし、2つの問題が発生しました。まず、Windowsエコシステムでは設計された用途とは異なり、_OSIを_OSの直接の代替として使用しており、OSのバージョンを識別するのではなく、サポートされるOSのインターフェースを示していました。実際、ACPI 3.0仕様自体も最初からこの誤用を例としてコードに組み込み、_OSI("Windows 2001")を使用する例を示していました。

この誤用は採用され、現在も続いています。

Linuxはこの誤用を採用せざるを得ませんでした。_OSI("Windows 2001")やその後継にTRUEを返さなかった場合、テストされたBIOSが動作しなくなる可能性がほぼ100%ありました。

この戦略は問題があります。Linuxは最新版のWindowsとは完全に互換性がなく、不具合を解消するのに1年以上かかる場合もあります。

Linuxコミュニティも悪化を招く行動を取りました。_OSI("Linux")にTRUEを返すことで、Windowsの誤用よりもさらに悪影響を及ぼしました。なぜなら"Linux"にはバージョン情報が含まれていないからです。_OSI("Linux")は未検証のBIOSフローで使用されたため、一部のBIOSが不具合を起こす原因となりました。しかし一部のOEMは検証済みのフローで_ OSI("Linux")を使用し、実際のLinux機能をサポートしていました。2009年にはLinuxが_ OSI("Linux")を削除し、legacyシステムのためにcmdlineパラメータで再実装しました。さらにBIOS_BUG警告をすべての_ OSI("Linux")を呼び出すBIOSに表示するようになりました。

BIOSは_ OSI("Linux")を使用すべきではありません。

結果として、LinuxはWindowsマシンでテストされたACPI BIOSとの互換性を最大化する戦略を取っています。ただし、この互換性を過度に過信するリスクがありますが、代替案はしばしばBIOSが未検証のパスを取って破綻するという深刻な結果を招くことがありました。 any OS。

_REVを使用しないでください¶

_ OSI("Linux")が廃止された後、一部のBIOS開発者は_ REVを使用してLinuxとWindowsの違いを同じBIOSでサポートするようになりました。

_ REVはACPI 1.0で定義され、OSがサポートするACPIバージョンとOS AMLインタプリタのバージョンを返すものでした。

現代のWindowsは_ REV = 2を返し、LinuxはACPI_CA_SUPPORT_LEVELを使用して、サポートする仕様バージョンに基づいてインクリメントしていました。

不幸なことに、_ REVも誤用されました。例えば、一部のBIOSは_ REV = 3をチェックし、Linux用に処理を行っていましたが、Linuxが_ REV = 4を返したことでそのサポートは破綻しました。

この問題に対応するため、Linuxは2015年中頃から_ REV = 2を常に返すようにしました。ACPI仕様も_ REVが非推奨となり、常に2を返すことが明記される予定です。

Apple Mac と _OSI(「Darwin」)¶

Apple の Mac プラットフォームでは、ACPI BIOS が _OSI(「Darwin」) を呼び出して、マシンが Apple OSX を実行しているかどうかを判定します。

Linux の _OSI(「Windows」戦略と同様に、Linux では _OSI(「Darwin」) に YES を返すのがデフォルトで、ハードウェアへの完全なアクセスと OSX で見られる検証済み BIOS パスを有効にします。Windows でテストされたプラットフォームと同様に、この戦略にはリスクがあります。

Linux-3.18 からは、マックの Thunderbolt サポートを有効化する目的で、_OSI(「Darwin」) に YES を返すようになりました。さらに、カーネルが _OSI(「Darwin」) を呼び出していると検知すると、すべての _OSI(「Windows」を無効にし、不完全に書かれた Mac BIOS が未テストのパスの組み合わせに落ちることを防ぎます。

Linux-3.18 の変更により、Mac ノートパソコンでの電力性能が低下し、3.18 の実装では cmdline 「acpi_osi=!Darwin」でデフォルトを変更できませんでした。Linux-4.7 で acpi_osi=!Darwin をワークアラウンドとして使用できるように修正され、Mac Thunderbolt の電力管理サポートが Linux-4.11 で実装されることを期待しています。

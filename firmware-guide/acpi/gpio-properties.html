_DSD デバイスプロパティ（GPIO関連）¶

ACPI 5.1のリリースにより、_DSD構成オブジェクトがついにGPIO（および他の項目も）を名前で指定できるようになりました。以前は、_CRSで返されるGPIOを特定するには整数インデックスのみを使用していましたが、これは非常にエラーが起こりやすいです（_CRS出力順序に依存するなど）。

_DSDを導入することで、GPIOを整数インデックスではなく名前でクエリできるようになりました。以下にASLの例を示します：

// Bluetooth device with reset and shutdown GPIOs
Device (BTH)
{
    Name (_HID, ...)

    Name (_CRS, ResourceTemplate ()
    {
        GpioIo (Exclusive, PullUp, 0, 0, IoRestrictionOutputOnly,
                "\\_SB.GPO0", 0, ResourceConsumer) {15}
        GpioIo (Exclusive, PullUp, 0, 0, IoRestrictionOutputOnly,
                "\\_SB.GPO0", 0, ResourceConsumer) {27, 31}
    })

    Name (_DSD, Package ()
    {
        ToUUID("daffd814-6eba-4d8c-8a91-bc9bbf4aa301"),
        Package ()
        {
            Package () {"reset-gpios", Package() {^BTH, 1, 1, 0 }},
            Package () {"shutdown-gpios", Package() {^BTH, 0, 0, 0 }},
        }
    })
}

サポートされているGPIOプロパティの形式は以下の通りです：

Package () { "name", Package () { ref, index, pin, active_low }}
ref

_CRSにGpioIo()/GpioInt()リソースを含むデバイス。通常これはデバイス自身（例：BTH）です。

index

_CRS内のGpioIo()/GpioInt()リソースのインデックス（0から始まります）。

GpioIo()/GpioInt()リソース内のピン。通常これは0です。

active_low

1の場合はGPIOがアクティブローとしてマークされます。

ACPI GpioIo()リソースにはアクティブローかハイかを示すフィールドがありませんので、ここでは"active_low"引数を使用します。1に設定するとGPIOがアクティブローとして認識されます。

注意：_DSDにおける"active_low"はGpioInt()リソースには意味がなく、0でなければなりません。GpioInt()リソースには独自の定義方法があります。

Bluetooth例では"reset-gpios"は2番目のGpioIo()リソース、そのリソース内の2番目のピンでGPIO番号が31のものです。

GpioIo()リソースには、ドライバが初期化時に使用すべき出力ピンの初期状態が明示的に提供されていません。

Linuxは常識を働かせて、バイアスと極性設定から状態を推定します。以下の表に期待される動作を示します：

上記のように、私たちの例では両方のGPIOがバイアス設定が明示的で_DSDが存在するため、アクティブでハイ極性として扱われ、Linuxはドライバが異なる設定で再プログラミングするまでこの状態でピンを構成します。

GPIO配列に穴を空けることも可能です。SPIホストコントローラーのように、一部のチップセレクトがGPIOで実装され、一部がネイティブ信号で実装される場合などに役立ちます。例えばSPIホストコントローラーはチップセレクト0と2をGPIOで、1をネイティブ信号で実装する場合があります：

Package () {
    "cs-gpios",
    Package () {
        ^GPIO, 19, 0, 0, // chip select 0: GPIO
        0,               // chip select 1: native signal
        ^GPIO, 20, 0, 0, // chip select 2: GPIO
    }
}

その他のサポートされているプロパティ¶

以下のDevice Tree互換のデバイスプロパティは、GPIOコントローラー用の_DSDデバイスプロパティでもサポートされています:

  • gpio-hog

  • output-high

  • output-low

  • 入力

  • line-name

例:

Name (_DSD, Package () {
    // _DSD Hierarchical Properties Extension UUID
    ToUUID("dbb8e3e6-5886-4ba6-8795-1319f52a966b"),
    Package () {
        Package () {"hog-gpio8", "G8PU"}
    }
})

Name (G8PU, Package () {
    ToUUID("daffd814-6eba-4d8c-8a91-bc9bbf4aa301"),
    Package () {
        Package () {"gpio-hog", 1},
        Package () {"gpios", Package () {8, 0}},
        Package () {"output-high", 1},
        Package () {"line-name", "gpio8-pullup"},
    }
})

  • gpio-line-names

例:

Package () {
    "gpio-line-names",
    Package () {
        "SPI0_CS_N", "EXP2_INT", "MUX6_IO", "UART0_RXD",
        "MUX7_IO", "LVL_C_A1", "MUX0_IO", "SPI1_MISO",
    }
}

これらのプロパティについての詳細は、Documentation/devicetree/bindings/gpio/gpio.txtを参照してください。

ドライバが提供するACPI GPIOマッピング¶

ACPIテーブルに_DSDが含まれていないが、_CRSでGpioIo()/GpioInt()リソースを提供し、デバイスドライバがこれらと依然として対話する必要があるシステムがあります。

そのような場合、ドライバが利用可能なACPIデバイス識別オブジェクト(_HID、_CID、_CLS、_SUB、_HRV)を用いてデバイスを特定し、GpioIo()/GpioInt()リソースによってリストされたすべてのGPIOラインの意味と目的を決定するための十分な情報が得られると考えられます。言い換えれば、ドライバはデバイスを特定した後、GpioIo()/GpioInt()リソースの用途を把握する必要があります。その作業が完了すれば、ドライバは使用するGPIOラインに名前を付けて、それらの名前と対応するACPI GPIOリソース間のマッピングをGPIOサブシステムに提供するだけで十分です。

これを実現するため、ドライバはNULL終端のstruct acpi_gpio_mappingオブジェクトの配列としてマッピングテーブルを定義する必要があります。各オブジェクトは名前、lineデータ（struct acpi_gpio_paramsオブジェクト）の配列へのポインタ、およびその配列のサイズを含みます。struct acpi_gpio_paramsオブジェクトは、crs_entry_index（_CRS内のターゲットGpioIo()/GpioInt()リソースのインデックス）、line_index（そのリソース内のターゲットラインのインデックス）、active_low（そのラインのアクティブローフラグ）の3つのフィールドで構成され、上記の_DSD GPIOプロパティフォーマットと同様に動作します。

以前に議論した例のBluetoothデバイスでは、関係するデータ構造は以下のようになります:

static const struct acpi_gpio_params reset_gpio = { 1, 1, false };
static const struct acpi_gpio_params shutdown_gpio = { 0, 0, false };

static const struct acpi_gpio_mapping bluetooth_acpi_gpios[] = {
  { "reset-gpios", &reset_gpio, 1 },
  { "shutdown-gpios", &shutdown_gpio, 1 },
  { }
};

次に、マッピングテーブルはacpi_dev_add_driver_gpios()またはそのマネージドアナログを第二引数として渡す必要があります。これは、第一引数で指定されたACPIデバイスオブジェクトにテーブルを登録します。これはドライバの.probe()ルーチン内で実行する必要があります。除去処理では、ドライバは以前に登録されたGPIOマッピングテーブルをacpi_dev_remove_driver_gpios()を呼び出してACPIデバイスオブジェクトから解除する必要があります。

_CRSフォールバックの使用¶

デバイスが_DSDを持っていない、またはドライバーがACPI GPIOマッピングを生成していない場合、LinuxのGPIOフレームワークはGPIOを返却しません。これはドライバーが実際に取得できるGPIOを把握していないためです。例えば、以下のようなデバイスがある場合:

Device (BTH)
{
    Name (_HID, ...)

    Name (_CRS, ResourceTemplate () {
        GpioIo (Exclusive, PullNone, 0, 0, IoRestrictionNone,
                "\\_SB.GPO0", 0, ResourceConsumer) {15}
        GpioIo (Exclusive, PullNone, 0, 0, IoRestrictionNone,
                "\\_SB.GPO0", 0, ResourceConsumer) {27}
    })
}

ドライバーは以下の通り正しいGPIOを取得できると期待します:

desc = gpiod_get(dev, "reset", GPIOD_OUT_LOW);

しかし、「reset」とGpioIo()のマッピングが確認できないため、_CRSの記述でERR_PTR(-ENOENT)を返します。

ドライバー開発者は、マッピングを明示的に渡すことでこの問題を解決できます（これは推奨される方法であり、上記の章で詳細に説明されています）。

ACPI GPIOマッピングテーブルは、ドライバーがサービス対象の正確なデバイスを把握していない場合でも、ドライバーに影響を与えてはなりません。これは、ACPI GPIOマッピングテーブルが、上記の章で説明したACPI IDや特定のオブジェクトとほとんど関連付けられていないことを意味します。

GPIO記述子の取得¶

ACPIからGPIOリソースを取得するための主なアプローチは2つあります:

desc = gpiod_get(dev, connection_id, flags);
desc = gpiod_get_index(dev, connection_id, index, flags);

ここでは、接続IDが提供されている場合とそうでない場合の2つのケースを考慮します。

ケース1:

desc = gpiod_get(dev, "non-null-connection-id", flags);
desc = gpiod_get_index(dev, "non-null-connection-id", index, flags);

ケース2:

desc = gpiod_get(dev, NULL, flags);
desc = gpiod_get_index(dev, NULL, index, flags);

ケース1は、対応するACPIデバイス記述がデバイスプロパティを定義していることを前提とし、それ以外の場合はGPIOリソースを取得できません。

ケース2はGPIOコアに明示的にリソースを_CRSから検索するように指示します。

注意してください gpiod_get_index() ケース1およびケース2では、2つのバージョンのACPIデバイス記述が提供され、ドライバーにマッピングが存在しない場合、異なるリソースが返されます。そのため、前章で説明したように、ドライバーは慎重に処理する必要があります。

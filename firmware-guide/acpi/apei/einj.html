APEI エラーインジェクション¶

EINJ はハードウェアエラーインジェクションメカニズムを提供します。これは、APEI および RAS の一般的な機能をデバッグおよびテストするための非常に有用なツールです。

まず、BIOS が EINJ をサポートしているか確認する必要があります。そのために、以下のようないらっしょメッセージを確認してください：

ACPI: EINJ 0x000000007370A000 000150 (v01 INTEL           00000001 INTL 00000001)

これは、BIOS が EINJ テーブルを公開していることを示しており、インジェクションが行われる仕組みです。

代替案として、/sys/firmware/acpi/tables に「EINJ」ファイルがあるか確認してください。これは同じ情報の別の表現形です。

上記のファイルが存在しない場合でも、必ずしも EINJ がサポートされていないとは限りません。諦める前に、BIOS セットアップ画面でエラーインジェクションを有効にするオプションがあるか確認してください。WHEA と呼ばれるオプションを探してください。多くの場合、APEI、EINJ などの機能をBIOS メニューでサポートされているか確認するためには、事前に ACPI5 サポートオプションを有効にする必要があります。

EINJ を使用するには、カーネル構成で以下のオプションが有効になっていることを確認してください：

CONFIG_DEBUG_FS
CONFIG_ACPI_APEI
CONFIG_ACPI_APEI_EINJ

EINJ ユーザーインターフェースは <debugfs マウントポイント>/apei/einj にあります。

以下のファイルはこれに関連します：

  • available_error_type

    このファイルはサポートされているエラー種類を示します：

    エラー種類値

    エラー説明

    0x00000001

    プロセッサ訂正可能

    0x00000002

    プロセッサ訂正不能非致命的

    0x00000004

    プロセッサ訂正不能致命的

    0x00000008

    メモリ訂正可能

    0x00000010

    メモリ訂正不能非致命的

    0x00000020

    メモリ訂正不能致命的

    0x00000040

    PCI Express 訂正可能

    0x00000080

    PCI Express 訂正不能致命的

    0x00000100

    PCI Express 訂正不能非致命的

    0x00000200

    プラットフォーム訂正可能

    0x00000400

    プラットフォーム訂正不能非致命的

    0x00000800

    プラットフォーム訂正不能致命的

    ファイルの内容形式は上記と同様ですが、表示されるのは利用可能なエラー種類のみです。

  • error_type

    インジェクションするエラー種類の値を設定します。可能なエラー種類は、上記の available_error_type ファイルに定義されています。

  • error_inject

    このファイルに任意の整数を書き込むことでエラーインジェクションをトリガーします。必要なすべてのエラーパラメータを指定した後、この書き込みを最後のステップとして行う必要があります。

  • フラグ

    カーネルバージョン 3.13 以降で利用可能です。これは、param{1..4} のうちどれが有効で、ファームウェアがインジェクション時に使用するかを指定します。値は ACPI5.0 データ構造の SET_ERROR_TYPE_WITH_ADDRESS で定義されるビットマスクです：

    ビット0

    プロセッサ APIC フィールドが有効（param3 を参照）

    ビット1

    メモリアドレスとマスクが有効（param1 および param2）

    ビット2

    PCIe (seg,bus,dev,fn) が有効（param4 を参照）

    ゼロに設定すると、従来の動作が模倣され、インジェクションの種類が1ビットのみを設定し、param1 が多重化されます。

  • param1

    このファイルは、最初のエラーパラメータ値を設定するために使用されます。その効果は、error_typeで指定されたエラータイプに依存します。たとえば、エラータイプがメモリ関連のタイプである場合、param1は有効な物理メモリアドレスでなければなりません。[「flag」が設定されていない場合を除く]

  • param2

    上記のparam1と同じ用途を使用します。たとえば、エラータイプがメモリ関連のタイプである場合、param2は物理メモリアドレスマスクでなければなりません。Linuxではページ単位またはより細かい粒度（例：0xfffffffffffff000）が必要です。

  • param3

    「flags」の0x1ビットが設定されているときに、APIC IDを指定するために使用します

  • param4 「flags」の0x4ビットが設定されているときに、ターゲットとなるPCIeデバイスを指定するために使用します

  • notrigger

    エラーインジェクションメカニズムは2段階のプロセスです。まずエラーをインジェクトし、その後、そのエラーをトリガーするためのアクションを行います。「notrigger」を1に設定すると、トリガー段階をスキップします。 可能かもしれません。 これにより、ユーザーはCPU、メモリ位置、またはエラーインジェクションのターゲットとなるデバイスへの単純なアクセスによって、別のコンテキストでエラーを引き起こすことができます。この方法が実際に機能するかどうかは、BIOSがトリガー段階に実際に含める操作に依存します。

ACPI 4.0仕様に基づくBIOSバージョンでは、エラーをインジェクトする場所を制御するオプションが限定されています。あなたのBIOSが拡張機能（param_extension=1モジュールパラメータ、またはブートコマンドライン einj.param_extension=1で有効）をサポートしている場合、param1とparam2ファイルでメモリインジェクションのアドレスとマスクを指定できます。

ACPI 5.0仕様に基づくBIOSバージョンでは、インジェクションのターゲットに対する制御がより広がっています。プロセッサ関連のエラー（タイプ0x1、0x2および0x4）の場合、フラグを0x3に設定（bit 0はparam3、bit 1はparam1およびparam2）することで、インジェクションされるエラーサインチャレジに追加情報を含めることができます。実際に渡されるデータは次の通りです：

memory_address = param1;
memory_address_range = param2;
apicid = param3;
pcie_sbdf = param4;

メモリエラー（タイプ0x8、0x10および0x20）の場合、param1でアドレスを設定し、param2でマスクを指定します（0x0はすべて1に等価）。PCIeエラー（タイプ0x40、0x80および0x100）の場合、param1でセグメント、バス、デバイス、ファンクションを指定します：

 31     24 23    16 15    11 10      8  7        0
+-------------------------------------------------+
| segment |   bus  | device | function | reserved |
+-------------------------------------------------+

とにかく、その意図は伝わるはずです。疑問があれば、drivers/acpi/apei/einj.cのコードを見てください。

ACPI 5.0のBIOSは、ベンダー固有のエラーをインジェクションする機能も提供する場合があります。この場合、ファイル名がvendorのファイルには、BIOSから取得した識別情報が含まれており、ベンダー固有拡張機能を希望するアプリケーションが、この拡張機能をサポートするBIOS上で実行していることを確認できるようになります。すべてのベンダー拡張機能ではerror_typeに0x80000000ビットが設定されています。ファイルvendor_flagsはparam1とparam2の解釈を制御します（1 = PROCESSOR、2 = MEMORY、4 = PCI）。詳細については、BIOSベンダーのドキュメンテーションを参照してください（ベンダーがこの機能を私たちの予想を超えて活用する可能性があるため、このAPIの変更が予想されます）。

エラーインジェクションの例:

# cd /sys/kernel/debug/apei/einj
# cat available_error_type            # See which errors can be injected
0x00000002    Processor Uncorrectable non-fatal
0x00000008    Memory Correctable
0x00000010    Memory Uncorrectable non-fatal
# echo 0x12345000 > param1            # Set memory address for injection
# echo $((-1 << 12)) > param2         # Mask 0xfffffffffffff000 - anywhere in this page
# echo 0x8 > error_type                       # Choose correctable memory error
# echo 1 > error_inject                       # Inject now

dmesgに以下のような出力が表示されるはずです:

[22715.830801] EDAC sbridge MC3: HANDLING MCE MEMORY ERROR
[22715.834759] EDAC sbridge MC3: CPU 0: Machine Check Event: 0 Bank 7: 8c00004000010090
[22715.834759] EDAC sbridge MC3: TSC 0
[22715.834759] EDAC sbridge MC3: ADDR 12345000 EDAC sbridge MC3: MISC 144780c86
[22715.834759] EDAC sbridge MC3: PROCESSOR 0:306e7 TIME 1422553404 SOCKET 0 APIC 0
[22716.616173] EDAC MC3: 1 CE memory read error on CPU_SrcID#0_Channel#0_DIMM#0 (channel:0 slot:0 page:0x12345 offset:0x0 grain:32 syndrome:0x0 -  area:DRAM err_code:0001:0090 socket:0 channel_mask:1 rank:0)

EINJについての詳細情報が必要な場合は、ACPI仕様バージョン4.0のセクション17.5およびACPI 5.0のセクション18.6を参照してください。

ACPIベースのデバイス列挙¶

ACPI 5は、シリアルバス制御機器の背後にあるスレーブデバイスを列挙するために使用できる新しいリソース（UartTSerialBus、I2cSerialBus、SpiSerialBus、GpioIoおよびGpioInt）を導入しました。

さらに、SoC/チップセットに統合された周辺機器がACPI名前空間にのみ出現するケースも増えてきています。これらは通常、メモリマップレジスタを通じてアクセスされるデバイスです。

このサポートを実現し、既存ドライバーをできるだけ再利用するため、以下の取り組みを行いました：

  • バスコネクタリソースを持たないデバイスはプラットフォームデバイスとして表現されます。

  • 実際のバス背後に存在するデバイスで、コネクタリソースがある場合は、 struct spi_device struct i2c_device（標準UARTはバスではないため、struct uart_deviceは存在しません）として表現されます。

ACPIとDevice Treeはどちらもデバイス（およびリソース）の木構造を表現するため、この実装はDevice Treeの方法をできるだけ採用しています。

ACPIの実装は、バス（プラットフォーム、SPI、I2C）背後のデバイスを列挙し、物理デバイスを作成して、ACPI名前空間内のACPIハンドルにバインドします。

これは、ACPI_HANDLE(dev)がNULLでない場合、デバイスがACPI名前空間から列挙されたことを意味します。このハンドルは、他のデバイス固有の設定情報を抽出するために使用できます。以下にその例を示します。

プラットフォームバスサポート¶

プラットフォームデバイスでデバイスを表現するため、デバイスにプラットフォームドライバーを実装し、サポートするACPI IDを追加するだけで十分です。同じIPブロックが他の非ACPIプラットフォームで使用される場合、ドライバーはオフボードで動作するか、最小限の変更で動作する可能性があります。

既存ドライバーにACPIサポートを追加するのは比較的簡単です。以下に最もシンプルな例を示します：

#ifdef CONFIG_ACPI
static const struct acpi_device_id mydrv_acpi_match[] = {
        /* ACPI IDs here */
        { }
};
MODULE_DEVICE_TABLE(acpi, mydrv_acpi_match);
#endif

static struct platform_driver my_driver = {
        ...
        .driver = {
                .acpi_match_table = ACPI_PTR(mydrv_acpi_match),
        },
};

ドライバーがGPIOの取得や設定など複雑な初期化を行う必要がある場合、ACPIハンドルを取得して、ACPIテーブルからこの情報を抽出できます。

DMAサポート¶

ACPI経由で列挙されたDMAコントローラーは、システムに登録してリソースへの汎用的なアクセスを提供する必要があります。たとえば、slaveデバイスに汎用API（dma_request_chan()）でアクセスしたいドライバーは、プローブ関数の最後に以下のように自身を登録する必要があります：

err = devm_acpi_dma_controller_register(dev, xlate_func, dw);
/* Handle the error if it's not a case of !CONFIG_ACPI */

必要に応じてカスタムのxlate関数（通常はacpi_dma_simple_xlate()で十分）を実装して、struct acpi_dma_specのFixedDMAリソースを対応するDMAチャネルに変換します。その場合のコード例は以下のようになります：

#ifdef CONFIG_ACPI
struct filter_args {
        /* Provide necessary information for the filter_func */
        ...
};

static bool filter_func(struct dma_chan *chan, void *param)
{
        /* Choose the proper channel */
        ...
}

static struct dma_chan *xlate_func(struct acpi_dma_spec *dma_spec,
                struct acpi_dma *adma)
{
        dma_cap_mask_t cap;
        struct filter_args args;

        /* Prepare arguments for filter_func */
        ...
        return dma_request_channel(cap, filter_func, &args);
}
#else
static struct dma_chan *xlate_func(struct acpi_dma_spec *dma_spec,
                struct acpi_dma *adma)
{
        return NULL;
}
#endif

dma_request_chan()は、登録されたDMAコントローラーごとにxlate_func()を呼び出します。xlate関数では、struct acpi_dma_spec内の情報と、struct acpi_dmaで提供されるコントローラーのプロパティに基づいて適切なチャネルを選択する必要があります。

クライアントは、特定のFixedDMAリソースに対応する文字列パラメータでdma_request_chan()を呼び出す必要があります。デフォルトでは、「tx」はFixedDMAリソース配列の最初のエントリ、「rx」は2番目のエントリを意味します。以下にレイアウトを示します。

Device (I2C0)
{
        ...
        Method (_CRS, 0, NotSerialized)
        {
                Name (DBUF, ResourceTemplate ()
                {
                        FixedDMA (0x0018, 0x0004, Width32bit, _Y48)
                        FixedDMA (0x0019, 0x0005, Width32bit, )
                })
        ...
        }
}

したがって、この例では、リクエストライン0x0018のFixedDMAは「tx」、次のリクエストラインは「rx」となります。

信頼性の高いケースでは、クライアントは残念ながらacpi_dma_request_slave_chan_by_index()を直接呼び出し、特定のFixedDMAリソースをインデックスで選ぶ必要があります。

SPIシリアルバスサポート¶

SPIバスの背後にあるスレーブデバイスにはSpiSerialBusリソースがアタッチされています。これはSPIコアが自動的に抽出し、バスドライバがspi_register_master()を呼び出すことでスレーブデバイスが一括して列挙されます。

SPIスレーブデバイスのACPI名前空間の例は以下のようになります：

Device (EEP0)
{
        Name (_ADR, 1)
        Name (_CID, Package() {
                "ATML0025",
                "AT25",
        })
        ...
        Method (_CRS, 0, NotSerialized)
        {
                SPISerialBus(1, PolarityLow, FourWireMode, 8,
                        ControllerInitiated, 1000000, ClockPolarityLow,
                        ClockPhaseFirst, "\\_SB.PCI0.SPI1",)
        }
        ...

SPIデバイスドライバは、プラットフォームデバイスドライバと同様にACPI IDを追加するだけで十分です。以下は、at25 SPI EEPROMドライバにACPIサポートを追加する例（上記のACPIスニペットに対応）です：

#ifdef CONFIG_ACPI
static const struct acpi_device_id at25_acpi_match[] = {
        { "AT25", 0 },
        { },
};
MODULE_DEVICE_TABLE(acpi, at25_acpi_match);
#endif

static struct spi_driver at25_driver = {
        .driver = {
                ...
                .acpi_match_table = ACPI_PTR(at25_acpi_match),
        },
};

このドライバは、EEPROMのページサイズなどの情報が必要ですが、現在では標準的な方法がありません。一つのアイデアは、_DSMメソッドでこれらの情報を返すことです：

Device (EEP0)
{
        ...
        Method (_DSM, 4, NotSerialized)
        {
                Store (Package (6)
                {
                        "byte-len", 1024,
                        "addr-mode", 2,
                        "page-size, 32
                }, Local0)

                // Check UUIDs etc.

                Return (Local0)
        }

その後、at25 SPIドライバは、ACPIハンドルに対して_DSMを呼び出してこの構成情報を取得できます：

struct acpi_buffer output = { ACPI_ALLOCATE_BUFFER, NULL };
struct acpi_object_list input;
acpi_status status;

/* Fill in the input buffer */

status = acpi_evaluate_object(ACPI_HANDLE(&spi->dev), "_DSM",
                              &input, &output);
if (ACPI_FAILURE(status))
        /* Handle the error */

/* Extract the data here */

kfree(output.pointer);

I2Cシリアルバスサポート¶

I2Cバスコントローラーの背後にあるスレーブデバイスは、プラットフォームやSPIドライバと同様にACPI IDを追加するだけで十分です。I2Cコアは、アダプターが登録されたら自動的にコントローラー背後のスレーブデバイスを列挙します。

既存のmpu3050入力ドライバにACPIサポートを追加する例は以下の通りです：

#ifdef CONFIG_ACPI
static const struct acpi_device_id mpu3050_acpi_match[] = {
        { "MPU3050", 0 },
        { },
};
MODULE_DEVICE_TABLE(acpi, mpu3050_acpi_match);
#endif

static struct i2c_driver mpu3050_i2c_driver = {
        .driver = {
                .name   = "mpu3050",
                .owner  = THIS_MODULE,
                .pm     = &mpu3050_pm,
                .of_match_table = mpu3050_of_match,
                .acpi_match_table = ACPI_PTR(mpu3050_acpi_match),
        },
        .probe          = mpu3050_probe,
        .remove         = mpu3050_remove,
        .id_table       = mpu3050_ids,
};

GPIOサポート¶

ACPI 5はGPIO接続を記述するための2つの新しいリソース、GpioIoとGpioIntを導入しました。これらのリソースは、デバイスが使用するGPIO番号をドライバに渡すために使用できます。ACPI 5.1では_DSD（デバイス固有データ）が追加され、GPIOの名前付けなどが可能になりました。

例:

Device (DEV)
{
        Method (_CRS, 0, NotSerialized)
        {
                Name (SBUF, ResourceTemplate()
                {
                        ...
                        // Used to power on/off the device
                        GpioIo (Exclusive, PullDefault, 0x0000, 0x0000,
                                IoRestrictionOutputOnly, "\\_SB.PCI0.GPI0",
                                0x00, ResourceConsumer,,)
                        {
                                // Pin List
                                0x0055
                        }

                        // Interrupt for the device
                        GpioInt (Edge, ActiveHigh, ExclusiveAndWake, PullNone,
                                0x0000, "\\_SB.PCI0.GPI0", 0x00, ResourceConsumer,,)
                        {
                                // Pin list
                                0x0058
                        }

                        ...

                }

                Return (SBUF)
        }

        // ACPI 5.1 _DSD used for naming the GPIOs
        Name (_DSD, Package ()
        {
                ToUUID("daffd814-6eba-4d8c-8a91-bc9bbf4aa301"),
                Package ()
                {
                        Package () {"power-gpios", Package() {^DEV, 0, 0, 0 }},
                        Package () {"irq-gpios", Package() {^DEV, 1, 0, 0 }},
                }
        })
        ...

これらのGPIO番号はコントローラー相対であり、パス「\_SB.PCI0.GPI0」はコントローラーへのパスを指定します。LinuxでこれらのGPIOを使用するには、それらを対応するLinux GPIO記述子に変換する必要があります。

これには標準的なGPIO APIがあり、Documentation/admin-guide/gpio/に詳しい説明があります。

上記の例では、このようなコードを使用して、対応する2つのGPIOデスクリプタを取得できます。

#include <linux/gpio/consumer.h>
...

struct gpio_desc *irq_desc, *power_desc;

irq_desc = gpiod_get(dev, "irq");
if (IS_ERR(irq_desc))
        /* handle error */

power_desc = gpiod_get(dev, "power");
if (IS_ERR(power_desc))
        /* handle error */

/* Now we can use the GPIO descriptors */

これらの関数には、デバイスが解放されるときにデスクリプタを解放するdevm_*バージョンのものもあります。

MFDデバイス¶

MFDデバイスは、子デバイスをプラットフォームデバイスとして登録します。子デバイスには、ACPI名前空間内のそれらに関連する部分を参照するために使用できるACPIハンドルが必要です。LinuxのMFDサブシステムでは、2つの方法を提供しています:

  • 子デバイスは親のACPIハンドルを共有します。

  • MFDセルは、デバイスのACPI IDを指定できます。

最初のケースでは、MFDドライバは何も処理する必要がありません。結果として生成される子プラットフォームデバイスは、親デバイスを指すACPI_COMPANION()が設定されます。

ACPI名前空間に、ACPI IDまたはACPI adrを使用してマッチできるデバイスがある場合、セルは以下のように設定する必要があります:

static struct mfd_cell_acpi_match my_subdevice_cell_acpi_match = {
        .pnpid = "XYZ0001",
        .adr = 0,
};

static struct mfd_cell my_subdevice_cell = {
        .name = "my_subdevice",
        /* set the resources relative to the parent */
        .acpi_match = &my_subdevice_cell_acpi_match,
};

ACPI ID「XYZ0001」は、MFDデバイス直下のACPIデバイスを直接検索し、見つかった場合、そのACPIコンパニオンデバイスが結果として生成される子プラットフォームデバイスにバインドされます。

デバイスツリー名前空間リンクデバイスID¶

デバイスツリープロトコルでは、ドライバやドライバコアが認識する文字列または文字列配列を値として持つ「compatible」プロパティを基にデバイスを識別します。これらの文字列の集合は、ACPI/PNPデバイスID名前空間に類似したデバイス識別名前空間とみなせます。したがって、デバイスツリー（DT）名前空間に既存の識別文字列を持つデバイスに対して、新たに（おそらく冗長な）ACPI/PNPデバイスIDを割り当てる必要は原則としてありません。特に、そのIDは他のデバイスとの互換性を示すためにのみ必要である場合です。

ACPIでは、デバイスの互換性を示すための識別オブジェクトとして_CID（Compatible ID）が使用されますが、そのIDはACPI仕様で規定された名前空間のいずれかに属する必要があります（詳細はACPI 6.0の第6.1.2節を参照）。DT名前空間はその一つではありません。さらに、仕様では、すべてのACPIオブジェクトがデバイスを表す場合、_HIDまたは_ADR識別オブジェクトのいずれかが存在することを義務付けています（詳細はACPI 6.0の第6.1節を参照）。非列挙バスタイプの場合は、このオブジェクトは_HIDでなければならず、その値は仕様で規定された名前空間のいずれかからデバイスIDを取得しなければなりません。

特別なDT名前空間リンクデバイスIDであるPRP0001は、ACPIにおいて既存のDT互換デバイス識別情報を使用し、ACPI仕様に基づく上記の要件を同時に満たす手段を提供します。つまり、_HIDがPRP0001を返す場合、ACPIサブシステムはデバイスオブジェクトの_DSD内の「compatible」プロパティを検索し、その値をもとに元のDTデバイス識別アルゴリズムと同様に該当デバイスを識別します。もし「compatible」プロパティが存在しないか、値が無効な場合、デバイスはACPIサブシステムによって列挙されません。それ以外の場合、デバイスは自動的にプラットフォームデバイスとして列挙されます（ただし、デバイスから親へのI2CまたはSPIリンクが存在する場合は、ACPIコアが親ドライバに列挙を委譲します）。また、_CIDでリストされたデバイスIDとともに、「compatible」プロパティ値から得られる識別文字列が使用され、デバイスに適したドライバが検索されます。

同様に、_CIDで返されるデバイスIDリストにPRP0001が含まれる場合、_HIDと_CIDでリストされた他のデバイスIDと比較して、PRP0001の位置によって「compatible」プロパティ値でリストされた識別文字列の優先順位が決まります。具体的には、_CIDの返却パッケージ内でPRP0001の前に返されるデバイスIDが優先的に検査されます。この場合、デバイスが列挙されるバスタイプは、_HIDで返されるデバイスIDによって決まります。

例えば、以下のACPIサンプルがlm75型I2C温度センサーを列挙し、Device Tree名前空間リンクを用いてドライバにマッチさせるために使用されることがあります：

Device (TMP0)
{
        Name (_HID, "PRP0001")
        Name (_DSD, Package() {
                ToUUID("daffd814-6eba-4d8c-8a91-bc9bbf4aa301"),
                Package () {
                        Package (2) { "compatible", "ti,tmp75" },
                }
        })
        Method (_CRS, 0, Serialized)
        {
                Name (SBUF, ResourceTemplate ()
                {
                        I2cSerialBusV2 (0x48, ControllerInitiated,
                                400000, AddressingMode7Bit,
                                "\\_SB.PCI0.I2C1", 0x00,
                                ResourceConsumer, , Exclusive,)
                })
                Return (SBUF)
        }
}

_HIDがPRP0001を返すとともに_DSDまたは_CIDに「compatible」プロパティが存在しないデバイスオブジェクトを定義しても、その祖先のいずれかが_DSDに有効な「compatible」プロパティを持つ_DSDを提供する限り有効です。このようなデバイスオブジェクトは、複合的な親デバイスのドライバに階層的な構成情報を提供する追加の「ブロック」として単純に扱われます。

ただし、PRP0001は、デバイスオブジェクトの_HIDまたは_CIDからのみ返却可能であり、そのデバイスオブジェクト自身の_DSDまたはその上位階層の「composite device」のケースにおける_DSDから返却されるすべてのプロパティがACPI環境で使用可能である場合に限られます。そうでない場合、_DSD自体は無効とみなされ、「compatible」プロパティは意味を失います。

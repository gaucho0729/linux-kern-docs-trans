遅延IO¶

Deferred IO は IO を遅延させ再利用する方法です。ホストメモリをバッファとして使用し、MMU ページフォールトをデバイス IO を実行するタイミングのプレトリガーとして利用します。以下の例は、このような設定がどのように動作するかを説明するのに役立つかもしれません:

  • Xfbdev などのユーザー空間アプリケーションがフレームバッファを mmap します

  • Deferred IO とドライバがフォールトハンドラと page_mkwrite ハンドラを設定します

  • ユーザー空間アプリケーションが mmap された仮想アドレスに書き込みを試みます

  • ページフォールトが発生し、フォールトハンドラに到達します

  • フォールトハンドラが物理ページを検索し、それを返します

  • page_mkwrite でこのページをリストに追加します

  • 遅延後にワークキュータスクをスケジュールします

  • アプリケーションはそのページに書き続けて追加のコストが発生しません。これは主な利点です。

  • ワークキュータスクがリストのページを mkclean し、フレームバッファの更新作業を完了します。これは実際にデバイスと通信する作業です。

  • アプリケーションがこのアドレス（mkclean された状態）に書き込みを試みます

  • ページフォールトが発生し、上述のシーケンスが再び発生します

上記のように、一つの利点は爆発的なフレームバッファ書き込みを最小コストで実行できるようにすることです。その後、静かな状態になったタイミングでフレームバッファを実際に更新します。これは相対的にコストのかかる作業です。

非揮発性の高遅延ディスプレイの一部では、最終的な画像が望ましいため、各書き込みごとに更新する必要はありません。

他のシナリオでもこの技術が役立つ可能性があります。Paul Mundt は、ページカウントをもとに SG DMA を実行するかメモリバーストを行うかを決定するケースでこの技術が有益であると述べています。

また、デバイスのフレームバッファが通常の形式（例：対角にシフトした RGB）でない場合、アプリケーションが通常のフレームバッファを装うようにし、vsync タイミングでタッチされたページリストに基づいてデバイスのフレームバッファにリスワイズするメカニズムを提供する場合もあります。

使い方: (アプリケーション向け)¶

変更は必要ありません。通常通りフレームバッファを mmap して使用してください。

使い方: (fbdev ドライバ向け)¶

以下の例は参考になります。

  1. 構造体を設定してください。例:

    static struct fb_deferred_io hecubafb_defio = {
        .delay          = HZ,
        .deferred_io    = hecubafb_dpy_deferred_io,
};

遅延は page_mkwrite トリガーが発生したタイミングから deferred_io コールバックが呼ばれるまでの最小遅延です。deferred_io コールバックの説明は以下にあります。

  1. deferred IO コールバックを設定してください。例:

    static void hecubafb_dpy_deferred_io(struct fb_info *info,
                                     struct list_head *pagelist)

deferred_ioコールバックは、ディスプレイデバイスへのすべてのIO操作を行う場所です。pagelistというリストを受取り、これは遅延中に書き込まれたページの一覧です。このリストを変更してはいけません。このコールバックはワークキューから呼び出されます。

  1. 初期化を呼び出してください:

    info->fbdefio = &hecubafb_defio;
fb_deferred_io_init(info);

  2. クリーンアップを呼び出してください:

    fb_deferred_io_cleanup(info);

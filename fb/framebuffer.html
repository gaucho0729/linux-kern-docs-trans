フレームバッファデバイス¶

最終更新日: 2001年5月10日

0. はじめに¶

フレームバッファデバイスはグラフィックハードウェアの抽象化を提供します。これは特定のビデオハードウェアのフレームバッファを表し、アプリケーションソフトウェアがハードウェアにアクセスするための明確なインターフェースを提供します。これにより、ソフトウェアは低レベルのハードウェアレジスタに関する知識を必要としません。

このデバイスは通常/devディレクトリに配置されている特別なデバイスノードを通じてアクセスされます。つまり、/dev/fb*です。

1. /dev/fb* のユーザー視点¶

ユーザーの視点では、フレームバッファデバイスは/dev内の他のデバイスと同様に見えます。これは主に29番のキャラクターデバイスで、マイナーデバイス番号がフレームバッファの番号を指定します。

慣例として、以下のデバイスノードが使用されます（数字はデバイスのマイナーデバイス番号を示します）：

 0 = /dev/fb0      First frame buffer
 1 = /dev/fb1      Second frame buffer
     ...
31 = /dev/fb31     32nd frame buffer

後方互換性のために、以下のシンボリックリンクを作成することも考えられます：

/dev/fb0current -> fb0
/dev/fb1current -> fb1

など…

フレームバッファデバイスはまた normal メモリデバイスであり、これはコンテンツを読み書きできるということを意味します。例えば、スクリーンのスナップショットを撮るには：

cp /dev/fb0 myfile

同時に複数のフレームバッファが存在することもあります。例えば、組み込みハードウェアに加えてグラフィックカードを搭載している場合です。対応するフレームバッファデバイス（/dev/fb0 と /dev/fb1 など）はそれぞれ独立して動作します。

フレームバッファデバイスを使用するアプリケーションソフトウェア（例：Xサーバー）はデフォルトで /dev/fb0 を使用します（古いソフトウェアは /dev/fb0current を使用します）。代替のフレームバッファデバイスを指定するには、$FRAMEBUFFER 環境変数をフレームバッファデバイスのパス名に設定します。例えば（sh/bash ユーザーの場合）：

export FRAMEBUFFER=/dev/fb1

または（csh ユーザーの場合）：

setenv FRAMEBUFFER /dev/fb1

これにより、Xサーバーは2番目のフレームバッファを使用します。

2. /dev/fb* のプログラマ視点¶

すでにご存知の通り、フレームバッファデバイスは /dev/mem と同様のメモリデバイスであり、同じ機能を持っています。読み込み、書き込み、特定の場所へのシーク、mmap()（主な用途）が可能です。違いは、特殊なファイルに現れるメモリが全体のメモリではなく、特定のビデオハードウェアのフレームバッファである点です。

/dev/fb* はまた、ハードウェアに関する多くの情報を照会・設定するための複数のioctlを許可します。カラーマップの処理もioctlを通じて行われます。詳細については <linux/fb.h> を参照してください。ここでは簡単な概要を示します：

  • ハードウェアに関する変更不可能な情報を要求できます。例えば、名前、スクリーンメモリの構造（平面、パッケージドピクセルなど）、およびスクリーンメモリのアドレスと長さなどです。

  • ハードウェアに関する可変情報を取得・変更できます。例えば、可視および仮想幾何学、深度、カラーマップ形式、タイミングなどです。その情報を変更しようとすると、ドライバーがハードウェアの能力に合わせて値を四捨五入するか、変更が不可能な場合はEINVALを返す可能性があります。

  • カラーマップの一部を取得・設定できます。赤、緑、青、透過性などの色ごとに16ビットで通信を行い、すべての既存ハードウェアをサポートします。ドライバーは、ハードウェアに適用するための必要な計算処理を行います（ビット数を減らすか、透過性を無視するなど）。

このようなハードウェアの抽象化により、アプリケーションの実装がより簡単で移植性が向上します。例えば、Xサーバーは/dev/fb*のみで動作するため、具体的なハードウェアのカラーレジスタの構造などは知る必要がありません。XF68_FBDevはビットマップ形式の非加速ビデオハードウェア用の汎用Xサーバーです。アプリケーションプログラムに組み込む必要があるのはスクリーンの構造（ビットプレーンやチャンキーピクセルなど）のみで、フレームバッファ画像データを直接処理します。

今後、グラフィックカードなどのフレームバッファドライバーは、ランタイムにロードされるカーネルモジュールとして実装される予定です。このようなドライバーは単に register_framebuffer() を呼び出し、いくつかの関数を提供するだけで十分です。カーネルとは独立してこのようなドライバーを書く・配布することで、多くの手間を省けます…

3. フレームバッファ解像度の維持¶

フレームバッファの解像度はユーティリティ fbsetで維持されます。これにより、フレームバッファデバイスのビデオモードプロパティを変更できます。主な用途は現在のビデオモードを変更することです（たとえば、起動時にあなたの /etc/rc.* または /etc/init.d/* ファイルのいずれかで）。

fbsetはビデオモードのデータベースを設定ファイルに保存しているため、独自のモードを簡単に追加し、簡単な識別子で参照できます。

4. Xサーバー¶

Xサーバー（XF68_FBDev）はフレームバッファデバイス用の最も注目すべきアプリケーションです。XFree86リリース3.2以降、XサーバーはXFree86に組み込まれ、2つのモードを持っています:

  • もし 表示 のサブセクションで fbdev ドライバーに関する記述には以下が含まれます:

    Modes "default"

    ライン、Xサーバーは上記のスキームを使用します。つまり、/dev/fb0（または設定されている場合の$FRAMEBUFFER）で決定された解像度で起動します。ただし、色深度（Depthキーワードを使用）と仮想解像度（Virtualキーワードを使用）は依然として指定する必要があります。これはXFree86に同梱された設定ファイルのデフォルトです。最もシンプルな設定ですが、いくつかの制限があります。

  • したがって、/etc/XF86Configファイルで解像度を指定することも可能です。これにより、仮想デスクトップサイズを維持しながらリアルタイムで解像度の切り替えが可能です。使用するフレームバッファデバイスは依然として/dev/fb0current（または$FRAMEBUFFER）ですが、利用可能な解像度は今や/etc/XF86Configで定義されます。デメリットは、タイミングを異なる形式で指定する必要があることです（ただし fbset -x が役立つかもしれません）。

ビデオモードを調整するにはfbsetまたはxvidtuneを使用できます。注意点として、xvidtuneはXF68_FBDevと100%互換性がありません。報告されるクロック値は常に正しくありません。

5. ビデオモードタイミング¶

モニターは電子ビーム（カラーモデルでは3本の電子ビーム、モノクロでは1本の電子ビーム）を使用して画面に画像を描画します。画面の前部にはカラーリングされたリンガ（ピクセル）のパターンが配置されています。リンガが電子ビームで衝突すると光子を放出し、それが可視になります。

電子ビームは画面の左から右へ、上から下へ水平なスキャンライン（スキャンライン）を描画します。電子ビームの強度を変更することで、さまざまな色と明るさを持つピクセルを表示できます。

各スキャンラインの後、電子ビームは画面の左端に戻り、次のラインへ移動します。これは水平リトレースと呼ばれます。画面全体（フレーム）を描画した後、ビームは上左隅に戻ります。これは垂直リトレースと呼ばれます。水平リトレースと垂直リトレースの間、電子ビームはオフにされ（ブラインドされます）。

電子ビームがピクセルを描画する速度はグラフィックボードのドットクロックで決まります。例えば、28.37516 MHz（毎秒のサイクル数）のドットクロックでは、各ピクセルは35242 ps（ピコ秒）の長さになります：

1/(28.37516E6 Hz) = 35.242E-9 s

画面解像度が640x480の場合、1スキャンラインで640（xres）ピクセルを描画するのにかかる時間は：

640*35.242E-9 s = 22.555E-6 s

ですが、水平リトレースも時間がかかるため（例：272 ピクセル）、1スキャンライン全体には：

(640+272)*35.242E-9 s = 32.141E-6 s

水平スキャンレートは約31 kHzとします：

1/(32.141E-6 s) = 31.113E3 Hz

画面全体は480（yres）ラインで構成されていますが、垂直リトレースも考慮する必要があります（例：49 ライン）。したがって、画面全体には：

(480+49)*32.141E-6 s = 17.002E-3 s

垂直スキャンレートは約59Hzです：

1/(17.002E-3 s) = 58.815 Hz

これは、画面データが1秒間に約59回リフレッシュされることを意味します。ちらみが目立たない安定した画像を得るために、VESAは垂直スキャンレートが72Hz以上であることを推奨しています。しかし、ちらみの感じ方は非常に人間依存です：一部の人にとっては50Hzでも問題ありませんが、私は80Hz未満になるとすぐに感じてしまいます。

モニタが新しいスキャンラインの開始時刻を知らないため、グラフィックボードは各スキャンラインに対して水平同期パルス（水平同期またはhsync）を、各新しいフレームに対して垂直同期パルス（垂直同期またはvsync）を供給します。画像の位置は、同期パルスが発生するタイミングに影響されます。

以下の図はすべてのタイミングを要約しています。水平リトレース時間は左マージン、右マージン、hsync長の合計であり、垂直リトレース時間は上マージン、下マージン、vsync長の合計です：

+----------+---------------------------------------------+----------+-------+
|          |                ↑                            |          |       |
|          |                |upper_margin                |          |       |
|          |                ↓                            |          |       |
+----------###############################################----------+-------+
|          #                ↑                            #          |       |
|          #                |                            #          |       |
|          #                |                            #          |       |
|          #                |                            #          |       |
|   left   #                |                            #  right   | hsync |
|  margin  #                |       xres                 #  margin  |  len  |
|<-------->#<---------------+--------------------------->#<-------->|<----->|
|          #                |                            #          |       |
|          #                |                            #          |       |
|          #                |                            #          |       |
|          #                |yres                        #          |       |
|          #                |                            #          |       |
|          #                |                            #          |       |
|          #                |                            #          |       |
|          #                |                            #          |       |
|          #                |                            #          |       |
|          #                |                            #          |       |
|          #                |                            #          |       |
|          #                |                            #          |       |
|          #                ↓                            #          |       |
+----------###############################################----------+-------+
|          |                ↑                            |          |       |
|          |                |lower_margin                |          |       |
|          |                ↓                            |          |       |
+----------+---------------------------------------------+----------+-------+
|          |                ↑                            |          |       |
|          |                |vsync_len                   |          |       |
|          |                ↓                            |          |       |
+----------+---------------------------------------------+----------+-------+

フレームバッファデバイスは、水平タイミングをドットクロック数（ピコ秒、1E-12秒）で、垂直タイミングをスキャンライン数で期待しています。

6. XFree86タイミング値をフレームバッファデバイスタイミングに変換¶

XFree86モードラインは以下のフィールドから構成されます：

"800x600"     50      800  856  976 1040    600  637  643  666
< name >     DCF       HR  SH1  SH2  HFL     VR  SV1  SV2  VFL

フレームバッファデバイスは以下のフィールドを使用します：

  • pixclock: ピクセルクロック（ピコ秒）

  • left_margin: 同期から画像までの時間

  • right_margin: 画像から同期までの時間

  • upper_margin: 同期から画像までの時間

  • lower_margin: 画像から同期までの時間

  • hsync_len: 水平同期の長さ

  • vsync_len: 垂直同期の長さ

  1. ピクセルクロック：

    xfree: MHz単位

    fb: ピコ秒（ps）単位

    pixclock = 1000000 / DCF

  2. 水平タイミング：

    left_margin = HFL - SH2

    right_margin = SH1 - HR

    hsync_len = SH2 - SH1

  3. 垂直タイミング：

    upper_margin = VFL - SV2

    lower_margin = SV1 - VR

    vsync_len = SV2 - SV1

VESAタイミングの良い例は、XFree86ソースツリーの「xc/programs/Xserver/hw/xfree86/doc/modeDB.txt」にあります。

フレームバッファデバイスAPI¶

最終更新日: 2011年6月21日

0. はじめに¶

このドキュメントは、アプリケーションがフレームバッファデバイスとやり取りするためのフレームバッファAPIについて説明しています。デバイスドライバとフレームバッファコア間のカーネル内APIについては記述していません。

元のフレームバッファAPIにおけるドキュメンテーションの不足により、ドライバの動作が微妙（あるいはそれほど微妙ではない）な違いで異なっています。このドキュメントでは推奨されるAPI実装を説明していますが、アプリケーションは異なる動作に対応する準備をすべきです。

1. キャパビリティ¶

デバイスおよびドライバのキャパビリティは、固定スクリーン情報キャパビリティフィールドで報告されます:

struct fb_fix_screeninfo {
      ...
      __u16 capabilities;             /* see FB_CAP_*                 */
      ...
};

アプリケーションはこれらのキャパビリティを使用して、デバイスおよびドライバから期待できる機能を把握する必要があります。

  • FB_CAP_FOURCC

ドライバがfour character code (FOURCC)ベースの形式設定APIをサポートしています。サポートされている場合、形式はFOURCCを使用して設定され、色成分レイアウトを手動で指定するのではなく、フォーマットが設定されます。

2. タイプとビジュアル¶

ピクセルはハードウェア依存の形式でメモリに保存されます。アプリケーションは、フレームバッファメモリにハードウェアが期待する形式で画像データを書き込むために、ピクセルの保存形式を把握する必要があります。

フォーマットはフレームバッファタイプとビジュアルによって記述されます。一部のビジュアルには追加情報が必要であり、これは可変スクリーン情報のbits_per_pixel、グレースケール、赤、緑、青およびトランスポーのフィールドに保存されます。

ビジュアルは色情報をどのように符号化し、マクロピクセルを作成するかを説明します。タイプはマクロピクセルがメモリにどのように保存されるかを説明します。以下のタイプとビジュアルがサポートされています。

  • FB_TYPE_PACKED_PIXELS

マクロピクセルは単一の平面内で連続して保存されます。マクロピクセルあたりのビット数が8の倍数でない場合、マクロピクセルが次の8の倍数ビットにパディングされるか、ビジュアルによって決定されるようにバイト単位で詰め合わせられます。

行末のパディングが存在する場合、それは固定スクリーン情報のline_lengthフィールドを通じて報告されます。

  • FB_TYPE_PLANES

マクロピクセルは複数の平面に分割されます。平面数はマクロピクセルあたりのビット数に等しく、平面i番目はすべてのマクロピクセルのi番目のビットを保存します。

平面はメモリ内で連続して配置されます。

  • FB_TYPE_INTERLEAVED_PLANES

マクロピクセルは複数の平面に分割されます。平面数はマクロピクセルあたりのビット数に等しく、平面i番目はすべてのマクロピクセルのi番目のビットを保存します。

平面はメモリ内でインターリーブされています。インターリーブ係数は、異なる平面に属する2つの連続するインターリーブブロックの開始位置間のバイト距離を表し、固定スクリーン情報のtype_auxフィールドに保存されます。

  • FB_TYPE_FOURCC

マクロピクセルは、変数screen informationのグレースケールフィールドに保存されているフォーマットFOURCC識別子に記述される方法でメモリに保存されます。

  • FB_VISUAL_MONO01

ピクセルは黒または白であり、変数screen informationのbppフィールドで指定されたビット数（通常は1ビット）で保存されます。

黒いピクセルはすべてのビットが1に設定され、白いピクセルはすべてのビットが0に設定されています。1ピクセルあたりのビット数が8未満の場合、複数のピクセルが1バイトにパックされます。

FB_VISUAL_MONO01は現在、FB_TYPE_PACKED_PIXELSのみで使用されています。

  • FB_VISUAL_MONO10

ピクセルは黒または白であり、変数screen informationのbppフィールドで指定されたビット数（通常は1ビット）で保存されます。

黒いピクセルはすべてのビットが0に設定され、白いピクセルはすべてのビットが1に設定されています。1ピクセルあたりのビット数が8未満の場合、複数のピクセルが1バイトにパックされます。

FB_VISUAL_MONO01は現在、FB_TYPE_PACKED_PIXELSのみで使用されています。

  • FB_VISUAL_TRUECOLOR

ピクセルは赤、緑、青のコンポーネントに分解され、それぞれのコンポーネントは対応する値の読み取り専用ルックアップテーブルにインデックス付けされます。ルックアップテーブルはデバイス依存であり、線形または非線形のランプを提供します。

各コンポーネントは変数screen informationの赤、緑、青、およびトランスポーザーフィールドに記述される方法でマクロピクセルに保存されます。

  • FB_VISUAL_PSEUDOCOLORおよびFB_VISUAL_STATIC_PSEUDOCOLOR

ピクセル値はカラーマップ内のインデックスとしてエンコードされ、カラーマップは赤、緑、青のコンポーネントを保存します。カラーマップはFB_VISUAL_STATIC_PSEUDOCOLORでは読み取り専用で、FB_VISUAL_PSEUDOCOLORでは読み取り書き込み可能です。

各ピクセル値は変数screen informationのbits_per_pixelフィールドで報告されるビット数で保存されます。

  • FB_VISUAL_DIRECTCOLOR

ピクセルは赤、緑、青のコンポーネントに分解され、それぞれのコンポーネントは対応する値のプログラマブルなルックアップテーブルにインデックス付けされます。

各コンポーネントは変数screen informationの赤、緑、青、およびトランスポーザーフィールドに記述される方法でマクロピクセルに保存されます。

  • FB_VISUAL_FOURCC

ピクセルは変数screen informationのグレースケールフィールドに保存されているフォーマットFOURCC識別子に記述される方法でエンコードおよび解釈されます。

3. スクリーン情報¶

アプリケーションはFBIOGET_FSCREENINFOおよびFBIOGET_VSCREENINFO ioctlsを使用してスクリーン情報を照会します。これらのioctlsはそれぞれfb_fix_screeninfo構造体とfb_var_screeninfo構造体へのポインタを取ります。

struct fb_fix_screeninfoはフレームバッファデバイスおよび現在のフォーマットに関するデバイスに依存しない変更不可能な情報を保存します。これらの情報はアプリケーションが直接変更することはできませんが、ドライバがフォーマットを変更する際に変更可能です：

struct fb_fix_screeninfo {
      char id[16];                    /* identification string eg "TT Builtin" */
      unsigned long smem_start;       /* Start of frame buffer mem */
                                      /* (physical address) */
      __u32 smem_len;                 /* Length of frame buffer mem */
      __u32 type;                     /* see FB_TYPE_*                */
      __u32 type_aux;                 /* Interleave for interleaved Planes */
      __u32 visual;                   /* see FB_VISUAL_*              */
      __u16 xpanstep;                 /* zero if no hardware panning  */
      __u16 ypanstep;                 /* zero if no hardware panning  */
      __u16 ywrapstep;                /* zero if no hardware ywrap    */
      __u32 line_length;              /* length of a line in bytes    */
      unsigned long mmio_start;       /* Start of Memory Mapped I/O   */
                                      /* (physical address) */
      __u32 mmio_len;                 /* Length of Memory Mapped I/O  */
      __u32 accel;                    /* Indicate to driver which     */
                                      /*  specific chip/card we have  */
      __u16 capabilities;             /* see FB_CAP_*                 */
      __u16 reserved[2];              /* Reserved for future compatibility */
};

struct fb_var_screeninfoはフレームバッファデバイス、現在のフォーマット、ビデオモード、およびその他の miscellaneous パラメータに関するデバイスに依存しない変更可能な情報を保存します：

struct fb_var_screeninfo {
      __u32 xres;                     /* visible resolution           */
      __u32 yres;
      __u32 xres_virtual;             /* virtual resolution           */
      __u32 yres_virtual;
      __u32 xoffset;                  /* offset from virtual to visible */
      __u32 yoffset;                  /* resolution                   */

      __u32 bits_per_pixel;           /* guess what                   */
      __u32 grayscale;                /* 0 = color, 1 = grayscale,    */
                                      /* >1 = FOURCC                  */
      struct fb_bitfield red;         /* bitfield in fb mem if true color, */
      struct fb_bitfield green;       /* else only length is significant */
      struct fb_bitfield blue;
      struct fb_bitfield transp;      /* transparency                 */

      __u32 nonstd;                   /* != 0 Non standard pixel format */

      __u32 activate;                 /* see FB_ACTIVATE_*            */

      __u32 height;                   /* height of picture in mm    */
      __u32 width;                    /* width of picture in mm     */

      __u32 accel_flags;              /* (OBSOLETE) see fb_info.flags */

      /* Timing: All values in pixclocks, except pixclock (of course) */
      __u32 pixclock;                 /* pixel clock in ps (pico seconds) */
      __u32 left_margin;              /* time from sync to picture    */
      __u32 right_margin;             /* time from picture to sync    */
      __u32 upper_margin;             /* time from sync to picture    */
      __u32 lower_margin;
      __u32 hsync_len;                /* length of horizontal sync    */
      __u32 vsync_len;                /* length of vertical sync      */
      __u32 sync;                     /* see FB_SYNC_*                */
      __u32 vmode;                    /* see FB_VMODE_*               */
      __u32 rotate;                   /* angle we rotate counter clockwise */
      __u32 colorspace;               /* colorspace for FOURCC-based modes */
      __u32 reserved[4];              /* Reserved for future compatibility */
};

変数情報を変更するには、アプリケーションはfb_var_screeninfo構造体へのポインタを渡してFBIOPUT_VSCREENINFO ioctlを呼び出します。呼び出しが成功した場合、ドライバは選択された固定スクリーン情報に応じて更新を行います。

fb_var_screeninfo構造体を手動で完全に埋めるのではなく、アプリケーションはFBIOGET_VSCREENINFO ioctlを呼び出し、関心のあるフィールドのみを変更するべきです。

4. フォーマット設定¶

フレームバッファデバイスは、フレームバッファフォーマットの設定に2つの方法を提供しています：レガシーAPIとFOURCCベースのAPI。

レガシーAPIは長期間にわたりフレームバッファフォーマット設定の唯一のAPIであり、アプリケーションでは広く使用されています。RGBおよびグレースケールフォーマット、およびレガシーの非標準フォーマットを使用する場合の推奨APIです。

フォーマットを選択するには、アプリケーションはfb_var_screeninfo構造体のbits_per_pixelフィールドを、望むフレームバッファの深度に設定します。値が8以下の場合は通常モノクロ、グレースケール、または擬似カラーのビジュアルにマッピングしますが、これは必須ではありません。

  • グレースケールフォーマットの場合、アプリケーションはグレースケールフィールドを1に設定します。赤、青、緑、トランスポフィールドはアプリケーションが0に設定し、ドライバは無視します。ドライバは赤、青、緑のオフセットを0にし、長さをbits_per_pixelの値に設定する必要があります。

  • 擬似カラーフォーマットの場合、アプリケーションはグレースケールフィールドを0に設定します。赤、青、緑、トランスポフィールドはアプリケーションが0に設定し、ドライバは無視します。ドライバは赤、青、緑のオフセットを0にし、長さをbits_per_pixelの値に設定する必要があります。

  • 真彩色およびディレクトカラーフォーマットの場合、アプリケーションはグレースケールフィールドを0に設定し、赤、青、緑、トランスポフィールドをメモリ内のカラーコンポーネントのレイアウトを記述するように設定します：

    struct fb_bitfield {
    __u32 offset;                   /* beginning of bitfield        */
    __u32 length;                   /* length of bitfield           */
    __u32 msb_right;                /* != 0 : Most significant bit is */
                                    /* right */
};

    ピクセル値はbits_per_pixel幅であり、重ならない赤、緑、青、アルファ（透明度）コンポーネントに分割されます。ピクセル値内の各コンポーネントの位置とサイズはfb_bitfieldオフセットと長さフィールドで記述されます。オフセットは右から計算されます。

    ピクセルは常に整数倍のバイトで保存されます。1ピクセルあたりのビット数が8の倍数でない場合、ピクセル値は次の8の倍数のビットにパディングされます。

フォーマット設定が成功した場合、ドライバは選択されたフォーマットに応じてfb_fix_screeninfo型、ビジュアル、およびライン長フィールドを更新します。

FOURCCベースのAPIは、4文字コード（FOURCC）で形式記述を置き換えます。FOURCCは、形式を明示的に記述することなく一意に定義する抽象的な識別子です。これはYUV形式をサポートする唯一のAPIです。ドライバはRGBおよびグレースケール形式にもFOURCCベースのAPIを実装することを推奨します。

FOURCCベースのAPIをサポートするドライバは、fb_fix_screeninfoのcapabilitiesフィールドにFB_CAP_FOURCCビットを設定してこの機能を報告します。

FOURCCの定義はlinux/videodev2.hヘッダーファイルにあります。ただし、V4L2_PIX_FMT_プレフィックスで始まっているにもかかわらず、V4L2に限定されず、V4L2サブシステムの使用を必要としません。FOURCCのドキュメンテーションは 画像形式.

形式を選択するには、アプリケーションがグレースケールフィールドを望ましいFOURCCに設定します。YUV形式の場合、colorspaceフィールドをlinux/videodev2.hに記載されているcolorspacesのいずれかに設定して適切なカラースペースを選択する必要があります。 カラースペース.

赤、緑、青、トランスポフィールドはFOURCCベースのAPIでは使用されません。将来の拡張機能でこれらのフィールドに意味が与えられる可能性があるため、アプリケーションはこれらのフィールドをゼロにし、ドライバは無視する必要があります。

形式設定が成功した場合、ドライバは選択された形式に応じてfb_fix_screeninfoのtype、visual、line_lengthフィールドを更新します。typeフィールドはFB_TYPE_FOURCCに、visualフィールドはFB_VISUAL_FOURCCに設定されます。

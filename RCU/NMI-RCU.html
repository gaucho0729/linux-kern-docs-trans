RCUを用いて動的NMIハンドラを保護する¶

RCUは通常、読み取り専用データ構造を保護するために使用されるが、動的でマスク不可な割り込みハンドラや動的IRQハンドラを提供することも可能である。このドキュメントでは、Zwane MwaikamboのNMIタイマーワークを参考に、arch/x86/oprofile/nmi_timer_int.cおよびarch/x86/kernel/traps.cからどのように実装するかを説明する。

関連するコードの一部は以下にリストアップされており、それぞれに簡単な説明が付いています：

static int dummy_nmi_callback(struct pt_regs *regs, int cpu)
{
        return 0;
}

dummy_nmi_callback()関数は、何も実行せずゼロを返す「ダミー」NMIハンドラであり、これによりNMIハンドラがデフォルトのマシン固有の動作を実行できるようにする。

static nmi_callback_t nmi_callback = dummy_nmi_callback;

nmi_callback変数は、現在のNMIハンドラへのグローバルな関数ポインタである。

void do_nmi(struct pt_regs * regs, long error_code)
{
        int cpu;

        nmi_enter();

        cpu = smp_processor_id();
        ++nmi_count(cpu);

        if (!rcu_dereference_sched(nmi_callback)(regs, cpu))
                default_do_nmi(regs);

        nmi_exit();
}

do_nmi()関数は各NMIを処理する。まずハードウェア割り込みと同じようにプリエンプションを無効化し、各CPUごとのNMIカウントをインクリメントする。次にnmi_callback関数ポインタに保存されたNMIハンドラを呼び出す。このハンドラがゼロを返す場合、do_nmi()関数はデフォルトのmachine-specific NMIを処理するdefault_do_nmi()関数を呼び出す。最後にプリエンプションを復元する。

理論上、 rcu_dereference_sched() は必要ありません。このコードはi386のみで実行されるため、理論上は必要ありません。 rcu_dereference_sched() しかし、実際にはAlphaや、積極的な最適化コンパイラを持つシステムで同様の処理を行う人にとって、ドキュメンテーションの補助として役立ちます。

クイズ：

なぜ...が必要なのでしょうか？ rcu_dereference_sched() ポインタで参照されるコードが読み取り専用であるにもかかわらず、Alphaで必要なのでしょうか？

クイズへの答え

NMIとRCUに関する議論に戻ります：

void set_nmi_callback(nmi_callback_t callback)
{
        rcu_assign_pointer(nmi_callback, callback);
}

set_nmi_callback()関数はNMIハンドラを登録します。注意点として、コールバックで使用するデータはset_nmi_callback()関数の呼び出しの前には初期化しておく必要があります。書き込みの順序を保証しないアーキテクチャでは、 rcu_assign_pointer() が、NMIハンドラが初期化された値を確認するための保証を提供します：

void unset_nmi_callback(void)
{
        rcu_assign_pointer(nmi_callback, dummy_nmi_callback);
}

この関数はNMIハンドラをアンレジストします。ただし、他のCPUで現在実行中のNMIハンドラがある可能性があるため、その実行がすべてのCPUで完了するまで、古いNMIハンドラで使用されるデータ構造を解放することはできません。

これを実現する方法の一つは synchronize_rcu()、以下のようになります：

unset_nmi_callback();
synchronize_rcu();
kfree(my_nmi_data);

これはv4.20以降、 synchronize_rcu() が、すべてのCPUがプリエンプションを無効化したコードセグメントを実行完了するのをブロックするためです。NMIハンドラはプリエンプションを無効化するため、 synchronize_rcu() は、すべての進行中のNMIハンドラが終了するまで戻らないことが保証されています。したがって、ハンドラのデータをすぐに解放しても安全です。 synchronize_rcu() 戻ります。

重要な注意点: この機能を動作させるには、対象のアーキテクチャがNMIのエントリとエクスイットそれぞれでnmi_enter()とnmi_exit()を呼び出す必要があります。

クイッククイズの答え:

なぜ...が必要なのでしょうか？ rcu_dereference_sched() ポインタで参照されるコードが読み取り専用であるにもかかわらず、Alphaで必要なのでしょうか？

set_nmi_callback()を呼び出した呼び出し元は、新しいNMIハンドラで使用されるデータを初期化している可能性があります。その場合、 rcu_dereference_sched() would be needed, because otherwise a CPU that received an NMI just after the new handler was set might see the pointer to the new NMI handler, but the old pre-initialized version of the handler’s data.

この同じ悲しい話は、アグレッシブなポインタ値の推測最適化を持つコンパイラを使用している他のCPUでも発生する可能性があります。

さらに重要なのは、 rcu_dereference_sched() makes it clear to someone reading the code that the pointer is being protected by RCU-sched.

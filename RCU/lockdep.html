RCUとlockdepチェック¶

すべてのRCUの種類にlockdepの検査が利用可能で、lockdepが各タスクがどのRCUの読み取り側クリティカルセクションに進入し、退出するタイミングを把握できるようにします。各RCUの種類は別々に追跡されます（ただし、これは2.6.32以前のバージョンでは当てはまりません）。これにより、lockdepの追跡にRCUの状態を含めることができ、デッドロックなどのデバッグ時に有効な場合があります。

さらに、RCUはlockdepの状態を検査する以下のプリミティブを提供しています:

rcu_read_lock_held() for normal RCU.
rcu_read_lock_bh_held() for RCU-bh.
rcu_read_lock_sched_held() for RCU-sched.
srcu_read_lock_held() for SRCU.

これらの関数は保守的であり、確信が持てない場合（たとえば、CONFIG_DEBUG_LOCK_ALLOCが設定されていない場合）には1を返します。これにより、lockdepが無効になっているときにWARN_ON(!rcu_read_lock_held())から偽陽性が発生しないようにします。

さらに、別個のカーネルのコンフィギュレーションパラメータCONFIG_PROVE_RCUは、 rcu_dereference() プリミティブの検査を有効にします:

rcu_dereference(p):

RCU読み取り側クリティカルセクションを確認します。

rcu_dereference_bh(p):

RCU-bh読み取り側クリティカルセクションを確認します。

rcu_dereference_sched(p):

RCU-sched読み取り側クリティカルセクションを確認します。

srcu_dereference(p, sp):

SRCU読み取り側クリティカルセクションを確認します。

rcu_dereference_check(p, c):

明示的なチェック式「c」を用いて、 rcu_read_lock_held()を検査します。これはRCUの読み取り者とアップデータの両方から呼び出されるコードで役立ちます。

rcu_dereference_bh_check(p, c):

明示的なチェック式「c」を用いて、 rcu_read_lock_bh_held()を検査します。これはRCU-bhの読み取り者とアップデータの両方から呼び出されるコードで役立ちます。

rcu_dereference_sched_check(p, c):

明示的なチェック式「c」を用いて、rcu_read_lock_sched_held()を検査します。これはRCU-schedの読み取り者とアップデータの両方から呼び出されるコードで役立ちます。

srcu_dereference_check(p, c):

明示的なチェック式「c」を用いて、 srcu_read_lock_held()を検査します。これはSRCUの読み取り者とアップデータの両方から呼び出されるコードで役立ちます。

rcu_dereference_raw(p):

検査を行いません。（極めて控えめに使用してください。）

rcu_dereference_protected(p, c):

明示的なチェック式「c」を用い、すべてのバリアとコンパイラ制約を省略します。これはデータ構造が変更されない場合（たとえば、アップデータのみによって呼び出されるコードで）役立ちます。

rcu_access_pointer(p):

ポインタの値を返し、すべてのバリアを省略しますが、複製や結合を防ぐコンパイラ制約は保持します。これはポインタ自体の値をテストする場合（たとえばNULLと比較する場合）に役立ちます。

以下の rcu_dereference_check() チェック式は任意の論理式であり、通常はlockdepの式を含みます。ただし、任意の論理式を使用できます。比較的複雑な例として、以下のコードを考えてみましょう:

file = rcu_dereference_check(fdt->fd[fd],
                             lockdep_is_held(&files->file_lock) ||
                             atomic_read(&files->count) == 1);

この式は、RCU安全な方法でポインタ「fdt->fd[fd]」を取得し、CONFIG_PROVE_RCUが設定されている場合、この式が以下のいずれかで使用されていることを検証します:

  1. RCU読み込み側クリティカルセクション（暗黙の）の場合、または

  2. files->file_lockを保持している場合、または

  3. 共有されていないfiles_structの場合。

ケース（1）では、vanilla RCU読み込み側クリティカルセクションでRCU安全な方法でポインタが取得され、ケース（2）では->file_lockが変更を防ぎ、ケース（3）では現在のタスクが唯一のファイル構造体へのアクセスを持つため、変更が防がれます。上記のステートメントがアップデートコードからのみ呼び出される場合、以下のように記述できます:

file = rcu_dereference_protected(fdt->fd[fd],
                                 lockdep_is_held(&files->file_lock) ||
                                 atomic_read(&files->count) == 1);

これにより、上記のケース#2および#3が検証され、さらにこのコードがRCU読み込み側クリティカルセクションで使用される場合、lockdepが警告を発するようになります（ケース#2または#3のいずれかが成立している場合を除くと）。 rcu_dereference_protected() バリアーおよびコンパイラ制約をすべて省略しているため、他のバージョンよりもより良いコードを生成します。 rcu_dereference()RCU保護されたポインタまたはそのポインタが指すRCU保護されたデータが同時に変更される可能性がある場合、このコードを使用することは違法です。 rcu_dereference_protected() RCU保護されたポインタまたはそのポインタが指すRCU保護されたデータが同時に変更される可能性がある場合、このコードを使用することは違法です。

例え rcu_dereference()、lockdepが有効になっている場合、RCUリストおよびhlistのトラバーサルプリミティブは、RCU読み込み側クリティカルセクション内から呼び出されているかを確認します。ただし、これらにlockdep式を追加のオプション引数として渡すことができます。このlockdep式により、これらのトラバーサルプリミティブは、lockdep式が偽であり、かつRCU読み込み側クリティカルセクション外から呼び出された場合のみ警告を出します。

たとえば、workqueue for_each_pwq() マクロは、RCU読み込み側クリティカルセクション内で使用するか、wq->mutexを保持した状態で使用することを意図しています。したがって、以下のように実装されています：

#define for_each_pwq(pwq, wq)
        list_for_each_entry_rcu((pwq), &(wq)->pwqs, pwqs_node,
                                lock_is_held(&(wq->mutex).dep_map))

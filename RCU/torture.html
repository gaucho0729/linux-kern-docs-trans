RCUのストレステスト実行¶

CONFIG_RCU_TORTURE_TEST (設定オプション)¶

CONFIG_RCU_TORTURE_TEST構成オプションはすべてのRCU実装で利用可能です。これはrcutortureカーネルモジュールを生成し、そのモジュールをロードして拷問テストを実行できます。テストは定期的にステータスメッセージを printk()経由して出力し、dmesgコマンドで確認できます（「torture」でgrepするかもしれません）。テストはモジュールをロードしたときに開始し、モジュールをアンロードしたときに停止します。

モジュールパラメータは「rcutorture.」で前接します カーネルのコマンドラインパラメータ.

出力¶

統計出力は以下の通りです：

rcu-torture:--- Start of test: nreaders=16 nfakewriters=4 stat_interval=30 verbose=0 test_no_idle_hz=1 shuffle_interval=3 stutter=5 irqreader=1 fqs_duration=0 fqs_holdoff=0 fqs_stutter=3 test_boost=1/0 test_boost_interval=7 test_boost_duration=4
rcu-torture: rtc:           (null) ver: 155441 tfle: 0 rta: 155441 rtaf: 8884 rtf: 155440 rtmbe: 0 rtbe: 0 rtbke: 0 rtbre: 0 rtbf: 0 rtb: 0 nt: 3055767
rcu-torture: Reader Pipe:  727860534 34213 0 0 0 0 0 0 0 0 0
rcu-torture: Reader Batch:  727877838 17003 0 0 0 0 0 0 0 0 0
rcu-torture: Free-Block Circulation:  155440 155440 155440 155440 155440 155440 155440 155440 155440 155440 0
rcu-torture:--- End of test: SUCCESS: nreaders=16 nfakewriters=4 stat_interval=30 verbose=0 test_no_idle_hz=1 shuffle_interval=3 stutter=5 irqreader=1 fqs_duration=0 fqs_holdoff=0 fqs_stutter=3 test_boost=1/0 test_boost_interval=7 test_boost_duration=4

「dmesg | grep torture:」コマンドでほとんどのシステムでこの情報が抽出できます。より特殊な構成では、他のコマンドを使用して printk()が使用する出力をアクセスする必要があります。使用する printk()はKERN_ALERTを使用するため、目立つはずです。 ;-)

最初と最後の行はrcutortureモジュールパラメータを示し、最後の行はRCUが正しく動作したかどうかを自動判定した結果として「SUCCESS」または「FAILURE」を表示します。

項目は以下の通りです：

  • 「rtc」：現在読み取り可能な構造体の16進アドレス

  • 「ver」：起動以来、読み取り可能な構造体を変更したRCUライタータスクの回数

  • 「tfle」：非ゼロの場合は、「torture freelist」（「rtc」領域に配置する構造体を含む）が空であることを示します。この状態はRCUが正常に動作していないにもかかわらず、誤って動作していると勘違いさせるため重要です。 :-/

  • 「rta」：拷問freelistから割り当てられた構造体の数

  • 「rtaf」：freelistが空だったため失敗した割り当ての回数。この値がゼロでないことは珍しくありませんが、rtaの値に対する割合が大きいと問題です。

  • 「rtf」：拷問freelistへの解放回数

  • 「rtmbe」：ゼロでない値は、 rcu_assign_pointer() および rcu_dereference() が正しく動作していないことを示します。この値はゼロでなければなりません。

  • 「rtbe」：ゼロでない値は、 rcu_barrier() ファミリの関数のうちの1つが正しく動作していないことを示します。

  • 「rtbke」：rcutortureはRCUの優先度逆転を強制するためのリアルタイムkスレッドの生成に失敗しました。この値はゼロでなければなりません。

  • 「rtbre」：rcutortureはリアルタイムkスレッドを生成しましたが、優先度レベル1のリアルタイム優先度に設定できませんでした。この値はゼロでなければなりません。

  • 「rtbf」：RCU優先度昇格でRCU優先度逆転を解決できなかった回数

  • 「rtb」: rcutortureがRCUのプライオリティインバージョン条件を強制しようとした回数です。RCUのプライオリティブースティングを「test_boost」モジュールパラメータでテストしている場合、この値はゼロでない必要があります。

  • 「nt」: rcutortureがタイマーハンドラ内からRCUのリーダーサイドコードを実行した回数です。この値がゼロでないのは「irqreader」モジュールパラメータを指定した場合のみです。

  • 「リーダーパイプ」: リーダーが確認した構造体の「年齢」のヒストグラムです。最初の2項目以外の項目がゼロでない場合、RCUは破損しています。rcutortureはエラーフラグ文字列「!!!」を出力して、ご注意を促します。新規に割り当てられた構造体の年齢はゼロで、リーダーの可視性から削除されると1になります。その後はグラスパリッドごとに1ずつ増加し、(RCU_TORTURE_PIPE_LEN-2)回のグラスパリッドを通過後に解放されます。

    上記の出力は正しく動作するRCUから取得したものです。破損した状態での出力を確認したい場合は、自分で破損させましょう。 ;-)

  • 「リーダーバッチ」: リーダーが確認した構造体の「年齢」のヒストグラムですが、グラスパリッドではなくカウンターフリップ（またはバッチ）の観点から表示しています。非ゼロの項目数は依然として2項目です。この別な視点が必要な理由は、場合によっては「リーダーパイプ」リストよりも「リーダーバッチ」リストに3項目が表示されやすいためです。

  • 「フリーブロック循環」: パイプライン内の特定のポイントに到達したトーチャー構造体の数を示します。最初の項目は割り当てられた構造体の数と密接に関連し、2番目の項目はリーダーの可視性から削除された構造体の数、そして最後の項目を除く他の項目はグラスパリッドを通過した構造体の数と対応します。最後の項目はゼロでなければなりません。なぜなら、トーチャー構造体のカウンターが本来以上にインクリメントされた場合にのみ増加するからです。

RCUの異なる実装は実装固有の追加情報を提供できます。たとえば、Tree SRCUは以下の追加行を提供します：

srcud-torture: Tree SRCU per-CPU(idx=0): 0(35,-21) 1(-4,24) 2(1,1) 3(-26,20) 4(28,-47) 5(-9,4) 6(-10,14) 7(-14,11) T(1,6)

この行は、各CPUごとのカウンターレコードの状態を示しており、この場合はTree SRCUで動的に割り当てられたsrcu_structを使用しているため「srcud-」（「srcu-」ではなく）となっています。括弧内の数字は、対応するCPUの「old（旧）」と「current（現在）」カウンターの値を表します。「idx」値は「old」および「current」値を基盤となる配列にマッピングし、デバッグに有用です。最後の「T」項目はカウンターの合計を示します。

特定のカーネルビルドでの使用方法¶

特定のカーネルビルドにおいてRCUを負荷テストすることが有効な場合があります。たとえば、そのカーネルビルドを本番環境に導入する準備をしている場合です。その際、カーネルはCONFIG_RCU_TORTURE_TEST=mでビルドされるべきであり、テストはmodprobeを使用して開始し、rmmodを使用して終了させる必要があります。

たとえば、以下のスクリプトを使用してRCUを負荷テストできます：

#!/bin/sh

modprobe rcutorture
sleep 3600
rmmod rcutorture
dmesg | grep torture:

出力結果は手動で「!!!」というエラーフラグを確認できます。もちろん、より複雑なスクリプトを作成してこのようなエラーを自動的に検出することも可能です。「rmmod」コマンドは「SUCCESS」「FAILURE」、または「RCU_HOTPLUG」のいずれかを強制的に表示します。 printk()最初の2つは自明ですが、最後の「RCU_HOTPLUG」はRCUの失敗はなかったものの、CPUホットプラグの問題が検出されたことを示します。

メインラインカーネルでの使用方法¶

rcutortureを使用してRCU自体の変更をテストする際には、関連するKconfigオプションやカーネル起動パラメータの幅広い組み合わせをテストするため、複数のカーネルをビルドする必要があります。この状況ではmodprobeとrmmodの使用は時間がかかりやすく、エラーが発生しやすいです。

そのため、tools/testing/selftests/rcutorture/bin/kvm.shスクリプトがx86、arm64、powerpcのマインラインテストに利用可能です。デフォルトでは、tools/testing/selftests/rcutorture/configs/rcu/CFLISTに指定されたテストシリーズを実行します。各テストは、自動生成されたinitrdで提供される最小限のユーザースペースを使用してゲストOS内で30分間実行されます。テストが完了後、生成されたビルド製品とコンソール出力を分析し、テスト結果を要約します。

大規模なシステムでは、kvm.shに–cpus引数を渡すことでrcutortureテストを高速化できます。たとえば、64-CPUのシステムでは「–cpus 43」を指定すると、最大43つのCPUを並列でテスト実行します。v5.4以降では、すべてのシナリオを2回のバッチ処理で完了でき、テスト時間は約8時間から約1時間に短縮されます（16つのカーネルをビルドする時間は除きます）。–dryrun sched引数はテストを実行せず、テストがバッチ処理にどのようにスケジュールされるかを示します。これは–cpus引数で指定するCPU数を決定する際の参考になります。

すべての変更がすべてのシナリオを実行する必要があるわけではありません。たとえば、Tree SRCUの変更は、「–configs ‘SRCU-N SRCU-P’」という引数をkvm.shに指定して、SRCU-NとSRCU-Pのシナリオのみを実行できます。大規模なシステムでは、複数のフルセットのシナリオを同時に実行できます。たとえば、448つのハードウェアスレッドを持つシステムでは、5つのフルセットのインスタンスを同時に実行できます。このような実行を実現するには:

kvm.sh --cpus 448 --configs '5*CFLIST'

あるいは、このようなシステムでは、単一の8コアCPUシナリオの同時実行インスタンスを56個実行できます:

kvm.sh --cpus 448 --configs '56*TREE04'

もしくは、2つの8コアCPUシナリヨのそれぞれについて28個の同時実行インスタンスを実行できます:

kvm.sh --cpus 448 --configs '28*TREE03 28*TREE04'

もちろん、各同時実行インスタンスはメモリを使用します。メモリ使用量を制限するには、–memory引数を使用します（デフォルトは512M）。メモリの値が小さい場合、以下の–bootargsパラメータでコールバック洪水テストを無効化する必要があります。

場合によっては追加のデバッグが役立ちます。そのような場合は、kvm.shの–kconfigパラメータを使用できます。たとえば、 --kconfig 'CONFIG_KASAN=y'.

カーネルのブート引数を指定することもできます。たとえば、rcutortureのモジュールパラメータを制御するために使用します。たとえば、RCUのCPUストール警告コードの変更をテストするには、「–bootargs ‘rcutorture.stall_cpu=30’」を使用します。これにより、スクリプトが失敗を報告します（結果として発生するRCU CPUストール警告）。上記のように、メモリを減らす場合、rcutortureのコールバック洪水テストを無効化する必要があります:

kvm.sh --cpus 448 --configs '56*TREE04' --memory 128M \
        --bootargs 'rcutorture.fwd_progress=0'

場合によっては、カーネルのフルセットのビルドのみが必要です。これは–buildonly引数の役割です。

最後に、–trust-make引数は、各カーネルビルドが前のビルドから可能な限り再利用できるようにします。

kvm.shスクリプトのソースコードに記載されている、さらに複雑な引数もあります。

実行中に失敗が発生した場合、kvm.shの出力末尾にビルド時間と実行時間の失敗数が表示されます。これをファイルにリダイレクトする必要があります。各実行のビルド製品とコンソール出力は、tools/testing/selftests/rcutorture/resディレクトリ内のタイムスタンプ付きディレクトリに保存されます。特定のディレクトリをkvm-find-errors.shに指定すると、エラーのサマリーと完全なエラーログを巡回できます。たとえば:

tools/testing/selftests/rcutorture/bin/kvm-find-errors.sh \
        tools/testing/selftests/rcutorture/res/2020.01.20-15.54.23

ただし、ファイルを直接アクセスする方がしばしば便利です。実行中のすべてのシナリオに関連するファイルは、トップレベルのディレクトリ（上の例では2020.01.20-15.54.23）に配置され、各シナリオごとのファイルはシナリオ名で命名されたサブディレクトリ（例: 「TREE04」）に保存されます。あるシナリオが複数回実行された場合（上の例では「–configs ‘56*TREE04’」のように）、そのシナリオの2回目以降の実行に対応するディレクトリにはシーケンス番号が付与されます（例: 「TREE04.2」、「TREE,04.3」など）。

トップレベルのディレクトリで最もよく使用されるファイルはtestid.txtです。テストがgitリポジトリ内で実行された場合、このファイルにはテストされたコミットと、未コミットの変更点（diff形式）が含まれます。

各シナリオ実行ディレクトリで最もよく使用されるファイルは以下の通りです:

.config:

このファイルにはKconfigオプションが含まれます。

Make.out:

これは特定のシナリオに対するビルド出力です。

console.log:

これは特定のシナリオに対するコンソール出力です。このファイルはカーネルが起動した後に確認できますが、ビルドが失敗した場合には存在しない可能性があります。

vmlinux:

これはカーネルを含み、objdumpやgdbなどのツールと併用するのに役立ちます。

いくつかの追加ファイルは利用可能です。ただし、頻繁には使用されません。多くはrcutorture自身やそのスクリプトのデバッグ目的に設計されています。

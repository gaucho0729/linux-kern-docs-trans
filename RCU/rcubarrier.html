RCUとアンロード可能なモジュール¶

[LWN に最初に掲載されました。2007年1月14日、 http://lwn.net/Articles/217484/]

RCU (read-copy update) は、読み込み専用ロック（その他の用途にも利用される）などの代替として考えられる同期メカニズムであり、デッドロック、優先度逆転、無限の遅延に免疫のある非常に低負荷の読み込み処理を提供します。RCU の読み込み側クリティカルセクションは、 rcu_read_lock() および rcu_read_unlock()、非 CONFIG_PREEMPT カーネルではコードを生成しません。

これは、RCU ライタが並行して読み込む読者を認識していないことを意味します。したがって、共有データへの RCU 更新は非常に慎重に行う必要があります。すべての既存の読者が完了するまで、データ構造の古いバージョンを保持しておきます。このような読者がこれらの古いバージョンに参照を保持している可能性があるためです。RCU 更新はそのため、コストが高く、RCU は読み込みが主な状況に最も適しています。

RCU ライタが読者がすべて完了したことをどうやって判断できるでしょうか。読者がまったく痕跡を残さない可能性があるからです。ある synchronize_rcu() プリミティブは、すべての既存の読者が完了するまでブロックします。リンクリストから要素 p を削除したいアップデータは、適切なロックを保持しながら次の手順を行います。

list_del_rcu(p);
synchronize_rcu();
kfree(p);

しかし、上記のコードは IRQ コンテキストでは使用できません – その call_rcu() プリミティブを使用する必要があります。このプリミティブは、RCU 保護されたデータ構造内に配置された rcu_head 構造体へのポインタと、後でその構造体を解放するための関数へのポインタを取ります。IRQ コンテキストからリンクリストの要素 p を削除するコードは次のようになります：

list_del_rcu(p);
call_rcu(&p->rcu, p_callback);

なぜなら call_rcu() ブロックしない限り、このコードは IRQ コンテキスト内で安全に使用できます。関数 p_callback() は次のようになります：

static void p_callback(struct rcu_head *rp)
{
        struct pstruct *p = container_of(rp, struct pstruct, rcu);

        kfree(p);
}

call_rcu()を使用するモジュールのアンロード¶

しかし、p_callback がロード不可モジュールで定義されている場合怎么办？

いくつかの RCU コールバックが待機している間にモジュールをアンロードすると、これらのコールバックを実行している CPU は、後で呼び出されるときに深刻な失望を覚えるでしょう。これは、 http://lwn.net/images/ns/kernel/rcu-drop.jpg.

我々は、 synchronize_rcu() モジュール終了コードパスに配置するかもしれませんが、これは十分ではありません。たとえ synchronize_rcu() グレースペリオドが経過するのを待つことはありますが、コールバックが完了するのを待つことはありません。

複数の連続した synchronize_rcu() 呼び出しを試みるかもしれませんが、それでも確実に動作するとは限りません。非常に重い RCU コールバック負荷がある場合、一部のコールバックが他の処理を進めるための遅延としてdeferredされる可能性があります。リアルタイムカーネルでは、過剰なスケジューリング遅延を避けるためにこのような遅延が必要です。

rcu_barrier()の実装¶

Dipankar Sarmaの rcu_barrier() の実装は、RCUコールバックが1つのCPUごとのキューに登録された後で再順序付けされないという特性を利用しています。彼の実装では、RCUコールバックを各CPUごとのコールバックキューに登録し、それらがすべて実行開始するのを待機してから、すべての以前のRCUコールバックが完了していることを保証しています。

以下のコードは元のコードです rcu_barrier() 次の通りでした:

1  void rcu_barrier(void)
2  {
3    BUG_ON(in_interrupt());
4    /* Take cpucontrol mutex to protect against CPU hotplug */
5    mutex_lock(&rcu_barrier_mutex);
6    init_completion(&rcu_barrier_completion);
7    atomic_set(&rcu_barrier_cpu_count, 0);
8    on_each_cpu(rcu_barrier_func, NULL, 0, 1);
9    wait_for_completion(&rcu_barrier_completion);
10   mutex_unlock(&rcu_barrier_mutex);
11 }

行3では呼び出し元がプロセスコンテキストにあることを確認し、行5と行10ではrcu_barrier_mutexを使用して、同時に1つのプロセスのみがグローバルな完了フラグとカウンタを使用できるようにしています。これらの変数は行6と行7で初期化されています。行8では各CPUがrcu_barrier_func()を呼び出すよう指定しており、以下に示します。on_each_cpu()の引数リストにある最終的な「1」は、すべてのrcu_barrier_func()呼び出しが完了するのを待つためのものです。行9では完了を待機します。 rcu_barrier() このコードは2008年に再実装され、その後何度も改訂されていますが、依然として一般的なアイデアを示しています。

1  static void rcu_barrier_func(void *notused)
2  {

rcu_barrier()のまとめ¶

以下の rcu_barrier() プリミティブは、RCUを使用しているコードがコアカーネルに集中しているため、比較的使用されていません。ただし、アンロード可能なモジュールからRCUを使用している場合、 rcu_barrier() モジュールが安全にアンロードされるようにする必要があります。

クイズ #2:

CPU 0のrcu_barrier_func()が即座に実行され（これによりrcu_barrier_cpu_countが1にインクリメントされる）、他のCPUのrcu_barrier_func()呼び出しがフルグレース期間分遅延した場合、これによりどのような結果になるでしょうか？ rcu_barrier() 早期に戻るの？

回答: これは起こりません。理由は、on_each_cpu()の最後の引数であるwaitフラグが「1」に設定されているためです。このフラグはsmp_call_function()に渡され、さらにsmp_call_function_on_cpu()に渡され、これにより後者はrcu_barrier_func()のクロスCPU呼び出しが完了するまでスピンします。これにより、非CONFIG_PREEMPTカーネルではグレース期間が完了しないことが防がれます。なぜなら、各CPUがグレース期間が完了する前にコンテキストスイッチ（またはその他のクイエント状態）を経る必要がありますからです。しかし、これはCONFIG_PREEMPTカーネルでは役立ちません。

したがって、on_each_cpu()はsmp_call_function()呼び出し中にプリエンプションを無効化し、さらにローカルでのrcu_barrier_func()呼び出しにもプリエンプションを無効化します。これによりローカルCPUがコンテキストスイッチできず、再びグレース期間が完了しないことになります。つまり、すべてのCPUがrcu_barrier_func()を実行した後で初めてrcu_barrier_callback()が実行される可能性があり、これによりrcu_barrier_cpu_countが早すぎるゼロになるのを防ぎます。

現在、-rt実装のRCUはRCUコールバック用に単一のグローバルキューを保持しており、この問題にはなりません。しかし、-rt RCUが最終的に各CPUごとのコールバックキューを持つようになると、状況は変わります。簡単な変更としては、以下を追加するというものです。

Currently, -rt implementations of RCU keep but a single global queue for RCU callbacks, and thus do not suffer from this problem. However, when the -rt RCU eventually does have per-CPU callback queues, things will have to change. One simple change is to add an rcu_read_lock() 8行目の前 rcu_barrier() そして rcu_read_unlock() この同じ関数の8行目の後。より良い変更案があれば、教えてください！

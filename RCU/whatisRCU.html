1. RCU概要¶

RCUの基本的な考え方は、更新を「除去フェーズ」と「回収フェーズ」に分けることです。除去フェーズでは、データ構造内のデータ項目への参照を削除（必要に応じて、これらのデータ項目の新しいバージョンへの参照に置き換える）し、リーダー（読み取り側）と同時に実行可能です。除去フェーズをリーダーと同時に実行しても安全なのは、現代のCPUのセマンティクスが、リーダーがデータ構造の古いバージョンまたは新しいバージョンのいずれかを参照することを保証するからです。回収フェーズでは、除去フェーズで削除されたデータ項目の回収（例: メモリの解放）を行います。データ項目の回収は、それらを参照しているリーダーを妨害する可能性があるため、回収フェーズは、それらのデータ項目への参照を保持していないリーダーがすべて完了した後で開始する必要があります。

更新を除去フェーズと回収フェーズに分けることで、アップデータは除去フェーズをすぐに実行し、回収フェーズは除去フェーズ中にアクティブなすべてのリーダーが完了するまで延期できます（リーダーが完了するまでブロッキングするか、完了後に実行されるコールバックを登録する）。除去フェーズ中にアクティブなリーダーのみを考慮する必要があります。なぜなら、除去フェーズ後に開始するリーダーは、削除されたデータ項目への参照を取得できず、回収フェーズによって妨害されることはないからです。

したがって、典型的なRCU更新シーケンスは以下のようになります：

  1. データ構造へのポインタを削除し、その後のリーダーが参照を取得できなくします。

  2. 除去フェーズ中にアクティブだったすべてのリーダーが、RCU読み取り側クリティカルセクションを完了するのを待ちます。

  3. この時点で、データ構造への参照を保持しているリーダーはいないため、これより安全に回収（例: kfree()d).

上記のステップ(b)は、RCUの遅延破壊の背後にある主要なアイデアです。すべてのリーダーが完了するまで待機できるという能力により、RCUリーダーは、場合によってはまったく同期を行わずに、非常に軽量な同期を実現できます。これに対比して、より伝統的なロックベースのスキーマでは、アップデーターがデータ構造をリーダーの下から削除しないようにするため、リーダーは重い同期を必要とします。これは、ロックベースのアップデーターが通常データ項目を場所を変えて更新し、そのためリーダーを排他する必要があるからです。これに対比して、RCUベースのアップデーターは、現代のCPUでは単一のアラインメントされたポインタへの書き込みがアトミックであるという特性を活用し、リンク構造内のデータ項目のアトミックな挿入、削除、置換を可能にします。これにより、リーダーの動作を妨げることなく、並行してRCUリーダーは古いバージョンにアクセスし続けることができ、アトミック操作、メモリバリア、通信キャッシュミスといった現代のSMPコンピュータシステムで非常にコストのかかる操作を省略できます。

上記の3段階の手順では、アップデーターが削除と回収のステップを実行していますが、別のスレッドが回収を行うことがしばしば有益です。これは実際にLinuxカーネルのディレクトリエントリキャッシュ（dcache）で行われています。同じスレッドが更新ステップ（上記のステップ(a)）と回収ステップ（上記のステップ(c)）を実行する場合でも、これらを分けて考えるのが有益です。たとえば、RCUリーダーとアップデーターはまったく通信する必要がありませんが、RCUはリーダーと回収者間の暗黙の低コストな通信を提供しており、それが上記のステップ(b)で行われます。

では、リーダーが完了したかどうかを回収者がどのように判断できるのでしょうか？リーダーがどんな同期操作も行わないという前提で考えると、どうやってこの問題を解決するのか、RCUのAPIがどのようにこれを簡単にするかを読み進めてください。

2. RCUのコアAPIとは何か¶

RCUのコアAPIは非常に小さく、

  1. rcu_read_lock()

  2. rcu_read_unlock()

  3. synchronize_rcu() / call_rcu()

  4. rcu_assign_pointer()

  5. rcu_dereference()

RCU APIには多くの他のメンバーがありますが、これらはすべて5つのコアAPIを基盤として表現されます。ただし、ほとんどの実装では、 synchronize_rcu() の call_rcu() コールバックAPIを基盤として表現されます。

以下の5つのコアRCU APIについて説明します。他の18つのAPIについては後述します。詳細はカーネルdocbookドキュメンテーションを参照してください。または関数ヘッダコメントを直接確認してください。

rcu_read_lock()¶

void rcu_read_lock(void);

読み手がRCUの読み込み側クリティカルセクションに入ったことを回収者に通知するために使用されます。RCUの読み込み側クリティカルセクション内ではブロック操作は禁止されていますが、CONFIG_PREEMPT_RCUで構築されたカーネルでは、このセクションをプリエンプションすることが可能です。RCU保護されたデータ構造がRCU読み込み側クリティカルセクション内にアクセスされる場合、そのセクションの全期間を通じて回収されることは保証されています。参照カウントはRCUと併用して、データ構造への長期的な参照を維持するために使用できます。

rcu_read_unlock()¶

void rcu_read_unlock(void);

読み手がRCUの読み込み側クリティカルセクションを終了したことを回収者に通知するために使用されます。RCUの読み込み側クリティカルセクションはネストしたり、重なったりする場合があります。

synchronize_rcu()¶

void synchronize_rcu(void);

アップデータコードの終わりと回収者コードの始まりを示します。これは、すべてのCPUで既存のRCU読み込み側クリティカルセクションが完了するのをブロックして実現します。注意として、 synchronize_rcu() will ではありません その後に始まるRCU読み込み側クリティカルセクションの完了を必ず待つわけではありません。例えば、以下のイベントの順序を考えてみましょう：

        CPU 0                  CPU 1                 CPU 2
    ----------------- ------------------------- ---------------
1.  rcu_read_lock()
2.                    enters synchronize_rcu()
3.                                               rcu_read_lock()
4.  rcu_read_unlock()
5.                     exits synchronize_rcu()
6.                                              rcu_read_unlock()

繰り返しますが、 synchronize_rcu() は進行中のRCU読み込み側クリティカルセクションの完了を待つだけで、その後に開始されるものについては必ずしも待つ必要はありません。 synchronize_rcu() が呼び出された後です。

もちろん、 synchronize_rcu() 必ずしも戻りません 即時 最後の既存のRCU read-side critical sectionが完了した後です。一つの理由はスケジューリングの遅延が生じる可能性があるからです。また、多くのRCU実装では効率向上のためリクエストをバッチ処理するため、これによりさらに遅延が生じる可能性があります synchronize_rcu().

なぜなら synchronize_rcu() 読者が必要なタイミングを判断するAPIであり、その実装はRCUにとって極めて重要です。RCUがほぼすべての読み込み集中状況で有用であるためには、 synchronize_rcu()APIのオーバーヘッドも非常に小さくなければなりません

以下の call_rcu() APIはコールバック形式の synchronize_rcu()であり、後述のセクションで詳しく説明します。ブロッキングではなく、すべての進行中のRCU read-side critical sectionが完了した後に呼び出される関数と引数を登録します。このコールバック形式は、ブロッキングが禁止されている状況や、更新側のパフォーマンスが極めて重要である状況で特に有用です

しかし、 call_rcu() APIは軽率に使用すべきではありません。なぜなら、 synchronize_rcu() APIは一般的に簡潔なコードを生成します。さらに、 synchronize_rcu() APIは、グレースペリオドが遅延した場合でも更新レートを自動的に制限するという良い特性を持っています。この特性により、サービス拒否攻撃に対してシステムの耐性が高まります。コードで call_rcu() 更新率を制限することで、このようにした耐性を得ることができます。更新率を制限する方法については、checklist.txtを参照してください。

rcu_assign_pointer()¶

void rcu_assign_pointer(p, typeof(p) v);

はい、 rcu_assign_pointer() 通常のRCU読み込み側クリティカルセクションは、条件付きでスリープロックを取得することが許容されます（例として マクロとして実装されていますが、このように関数を宣言できるとより良いでしょう。(コンパイラの専門家はおそらく異論を唱えるでしょう。)

アップデータは、RCUで保護されたポインタに新しい値を割り当てるためにこの関数を使用します。これにより、アップデータから読者への値の変更を安全に通信できます。このマクロは rval 値にはなりませんが、特定のCPUアーキテクチャに必要なメモリバリア指令を実行します。

おそらく同様に重要なのは、(1) 哪些のポインタがRCUで保護されているか、(2) ある構造体が他のCPUにアクセス可能になるタイミングをドキュメント化することです。ただし、 rcu_assign_pointer() は、_rcu リスト操作プリミティブなど間接的に使用されることが最も一般的です、例えば list_add_rcu().

rcu_dereference()¶

typeof(p) rcu_dereference(p);

例え rcu_assign_pointer(), rcu_dereference() はマクロとして実装しなければなりません。

読み手は rcu_dereference() を使用してRCUで保護されたポインタを取得し、その後参照可能な値を返します。注意点として、 rcu_dereference() は実際にポインタを参照しません。代わりに、後で参照するためにポインタを保護します。また、特定のCPUアーキテクチャに必要なメモリバリア指令も実行します。現在、Alphaのみが rcu_dereference() 内でメモリバリアを必要とします – 他のCPUでは、何も生成されません。すらコンパイラのディレクティブすらありません。

一般的なコーディング慣習では、 rcu_dereference() を使用してRCUで保護されたポインタをローカル変数にコピーし、その後このローカル変数を参照します。例えば以下の通りです:

p = rcu_dereference(head.next);
return p->data;

ただし、この場合、これらを1つのステートメントに統合してもかまいません:

return rcu_dereference(head.next)->data;

RCUで保護された構造体から複数のフィールドを取得する場合は、ローカル変数を使用するのが当然です。繰り返しの rcu_dereference() 呼び出しは見た目が悪いですし、クリティカルセクション内で更新が発生した場合に同じポインタが返される保証もありませんし、Alpha CPUでは不要なオーバーヘッドを引き起こします。

注意点として、 rcu_dereference() で返される値は、外側のRCU読み取り側クリティカルセクション内でのみ有効です 1。例えば、以下は ではありません 合法です:

rcu_read_lock();
p = rcu_dereference(head.next);
rcu_read_unlock();
x = p->address; /* BUG!!! */
rcu_read_lock();
y = p->data;    /* BUG!!! */
rcu_read_unlock();

1つのRCU読み取り側クリティカルセクションから別のクリティカルセクションへの参照を持つことは、ロックベースのクリティカルセクション間での参照を持つことと同じく違法です！同様に、クリティカルセクション内で取得した参照をその外で使用するのも、通常のロックを使用する場合と同じく違法です。

RCUの rcu_assign_pointer()と同様に、 rcu_dereference() RCUで保護されているポインタを記録することです。特に、いつでも変更される可能性のあるポインタを、たとえば直後に rcu_dereference()。また、同様に rcu_assign_pointer(), rcu_dereference() は通常、_rcuリスト操作プリミティブを介して間接的に使用されます。たとえば list_for_each_entry_rcu() 2.

1

変体 rcu_dereference_protected() はRCU読み取り側クリティカルセクションの外でも使用できますが、更新側コードで取得したロックによって保護されている限りです。この変体は、たとみを使用した場合に発生するlockdep警告を回避します。 rcu_dereference() は、よりもさらにシンプルなコードを生み出すため、のミリ秒単位のレイテンシーを回避できます。よって、ご活用ください。 rcu_read_lock() 保護。使用する rcu_dereference_protected() また、コンパイラ最適化を許可するという利点もあります。 rcu_dereference() 禁止しなければならない。この rcu_dereference_protected() 変体は呼び出し元が取得しなければならないロックを示すlockdep式を取る。指定された保護が提供されていない場合、lockdep splatが発生します。参照 A Tour Through RCU’s Requirements APIのコードコメントを参照してください。

2

もし list_for_each_entry_rcu() インスタンスが更新側コードおよびRCUリーダーによって使用される場合、追加のlockdep式を引数リストに追加できます。たとえば、追加の「lock_is_held(&mylock)」引数が与えられた場合、このインスタンスがRCU読み取り側クリティカルセクションの外でmylockの保護なしに呼び出された場合のみ、RCU lockdepコードが警告を発します。

Linuxカーネルでは少なくとも3種類のRCU使用方法があります。上記の図は最も一般的なものを示しています。アップデーター側では、すべての3種類の使用方法で使用されるプリミティブは同じです。 rcu_assign_pointer(), synchronize_rcu() および call_rcu() ただし、読者側での保護には、使用されるプリミティブは使用方法によって異なります:

  1. rcu_read_lock() / rcu_read_unlock() rcu_dereference()

  2. rcu_read_lock_bh() / rcu_read_unlock_bh() local_bh_disable() / local_bh_enable() rcu_dereference_bh()

  3. rcu_read_lock_sched() / rcu_read_unlock_sched() preempt_disable() / preempt_enable() local_irq_save() / local_irq_restore() hardirq enter / hardirq exit NMI enter / NMI exit rcu_dereference_sched()

これら3つのタイプは以下のようになります:

  1. 通常のデータ構造にRCUが適用されます。

  2. リモートからのサービス停止攻撃にさらされる可能性のあるネットワーク関連のデータ構造にRCUが適用されます。

  3. スケジューラおよび割込み/NMIハンドラタスクにRCUが適用されます。

また、ほとんどの用途は(a)です。(b)と(c)のケースは専用用途において重要ですが、比較的まれです。

3. コアRCU APIの使用例¶

このセクションでは、動的に割り当てられた構造体へのグローバルポインタを保護するためのコアRCU APIの簡単な使用例を示します。より一般的なRCUの使用例は、 listRCU.rst, arrayRCU.rst, and NMI-RCU.rst.

struct foo {
        int a;
        char b;
        long c;
};
DEFINE_SPINLOCK(foo_mutex);

struct foo __rcu *gbl_foo;

/*
 * Create a new struct foo that is the same as the one currently
 * pointed to by gbl_foo, except that field "a" is replaced
 * with "new_a".  Points gbl_foo to the new structure, and
 * frees up the old structure after a grace period.
 *
 * Uses rcu_assign_pointer() to ensure that concurrent readers
 * see the initialized version of the new structure.
 *
 * Uses synchronize_rcu() to ensure that any readers that might
 * have references to the old structure complete before freeing
 * the old structure.
 */
void foo_update_a(int new_a)
{
        struct foo *new_fp;
        struct foo *old_fp;

        new_fp = kmalloc(sizeof(*new_fp), GFP_KERNEL);
        spin_lock(&foo_mutex);
        old_fp = rcu_dereference_protected(gbl_foo, lockdep_is_held(&foo_mutex));
        *new_fp = *old_fp;
        new_fp->a = new_a;
        rcu_assign_pointer(gbl_foo, new_fp);
        spin_unlock(&foo_mutex);
        synchronize_rcu();
        kfree(old_fp);
}

/*
 * Return the value of field "a" of the current gbl_foo
 * structure.  Use rcu_read_lock() and rcu_read_unlock()
 * to ensure that the structure does not get deleted out
 * from under us, and use rcu_dereference() to ensure that
 * we see the initialized version of the structure (important
 * for DEC Alpha and for people reading the code).
 */
int foo_get_a(void)
{
        int retval;

        rcu_read_lock();
        retval = rcu_dereference(gbl_foo)->a;
        rcu_read_unlock();
        return retval;
}

まとめると、以下のような点があります:

  • Use rcu_read_lock() および rcu_read_unlock() でRCU読み込み側クリティカルセクションを保護します。

  • RCU読み込み側クリティカルセクション内では、 rcu_dereference() でRCU保護ポインタを間接参照します。

  • コンカレンシーな更新がお互いに干渉しないようにするためには、ロックやセマフォなどの堅実なスキームを使用する必要があります。

  • Use rcu_assign_pointer() でRCU保護ポインタを更新します。このプリミティブは、更新者をコンカレンシーな読者から保護し、 ではありません コンカレンシーな更新がお互いに干渉しないようにする必要があります！そのため、更新者と再取得者の区別を明確にするため、依然としてロック（または類似のもの）を使用する必要があります。 rcu_assign_pointer() after

  • Use synchronize_rcu() RCU保護データ構造からデータ要素を削除した後、 データ要素を再取得/解放する前に、すべてのRCU読み込み側クリティカルセクションがそのデータ項目を参照する可能性があることを待機するために使用します。 before reclaiming/freeing the data element, in order to wait for the completion of all RCU read-side critical sections that might be referencing that data item.

See checklist.txt for additional rules to follow when using RCU. And again, more-typical uses of RCU may be found in listRCU.rst, arrayRCU.rst, and NMI-RCU.rst.

4. 更新スレッドがブロックできない場合¶

上記の例では、foo_update_a()はグレースペリオドが終了するまでブロックします。これは非常に単純ですが、ある場合ではこの程度の待機は許容されません – 他の高優先度の作業が待っている可能性があります。

このような場合では、 call_rcu() rather than synchronize_rcu()の部分で、 call_rcu() APIは以下の通りです:

void call_rcu(struct rcu_head * head,
              void (*func)(struct rcu_head *head));

この関数は、グレースペリオドが経過した後にfunc(head)を呼び出します。この呼び出しはsoftirqまたはプロセスコンテキストから行われる可能性があるため、関数はブロックしてはなりません。foo構造体にはrcu_head構造体を追加する必要があります（例として以下のように）:

struct foo {
        int a;
        char b;
        long c;
        struct rcu_head rcu;
};

foo_update_a()関数は以下のように記述できます:

/*
 * Create a new struct foo that is the same as the one currently
 * pointed to by gbl_foo, except that field "a" is replaced
 * with "new_a".  Points gbl_foo to the new structure, and
 * frees up the old structure after a grace period.
 *
 * Uses rcu_assign_pointer() to ensure that concurrent readers
 * see the initialized version of the new structure.
 *
 * Uses call_rcu() to ensure that any readers that might have
 * references to the old structure complete before freeing the
 * old structure.
 */
void foo_update_a(int new_a)
{
        struct foo *new_fp;
        struct foo *old_fp;

        new_fp = kmalloc(sizeof(*new_fp), GFP_KERNEL);
        spin_lock(&foo_mutex);
        old_fp = rcu_dereference_protected(gbl_foo, lockdep_is_held(&foo_mutex));
        *new_fp = *old_fp;
        new_fp->a = new_a;
        rcu_assign_pointer(gbl_foo, new_fp);
        spin_unlock(&foo_mutex);
        call_rcu(&old_fp->rcu, foo_reclaim);
}

foo_reclaim()関数は以下のように記述できます:

void foo_reclaim(struct rcu_head *rp)
{
        struct foo *fp = container_of(rp, struct foo, rcu);

        foo_cleanup(fp->a);

        kfree(fp);
}

以下の container_of() primitiveは、構造体のポインタ、構造体の型、構造体内のポインテッドフィールドを指定して、構造体の先頭へのポインタを返すマクロです。

The use of call_rcu() は、foo_update_a()の呼び出し元が新しい要素の古いバージョンを気にすることなく即座に制御を再取得できるようにします。また、更新者（foo_update_a()）と再取得者（foo_reclaim()）の区別を明確に示しています。

アドバイスのまとめは前セクションと同じですが、今回は call_rcu() rather than synchronize_rcu():

  • Use call_rcu() RCU保護データ構造からデータ要素を削除した後、 RCU保護データ構造からデータ要素を削除して、そのデータ項目を参照する可能性のあるすべてのRCU読み込み側クリティカルセクションが完了後に呼び出されるコールバック関数を登録します。

  1. 読者がブロックする必要がありますか？そうであれば、SRCUが必要です。

  2. また、-rtパッチセットについてどうですか？非-rtカーネルで読者がブロックする必要がある場合、SRCUが必要です。非-rtカーネルではブロックしないが、-rtカーネルではブロックする場合、SRCUは必要ありません。（-rtパッチセットはスピンロックをスリープロックに変換するため、この区別があります。）

  3. NMIハンドラ、ハードIRQハンドラ、プリエンプションが無効になっているコードセグメント（preempt_disable()、local_irq_save()、local_bh_disable()、または他のメカニズムによる）を明示的なRCU読者として扱う必要がありますか？そうであれば、RCU-schedが唯一の選択肢です。

  4. ソフトIRQが1つ以上のCPUを占領してもRCUグレース期間が完了する必要がありますか？たとえば、ネットワークベースのDoS攻撃にあなたのコードが影響されるでしょうか？そうであれば、読者でソフトIRQを無効にする必要があります。たとえば、 rcu_read_lock_bh().

  5. 通常のRCUの使用よりも更新が過剰で、他の同期メカニズムには不適切なワークロードですか？そうであれば、SLAB_TYPESAFE_BY_RCU（元々はSLAB_DESTROY_BY_RCUと呼ばれていました）を検討してください。ただし、注意が必要です！

  6. アイドルループの真ん中、ユーザーモード実行中、またはオフラインCPUでの読取り側クリティカルセクションが必要ですか？そうであれば、SRCUが唯一の選択肢です。

  7. それ以外の場合は、RCUを使用してください。

もちろん、これはすべて以下の前提に基づいています：RCUが実際にあなたの作業に適切なツールであると判断していること。

クイッククイズ #1:

なぜこの議論は無知なのでしょうか？このアルゴリズムを現実世界のLinuxカーネルで使用する際に、デッドロックが発生する可能性があるのでしょうか？[ロックベースの「トイ」RCUアルゴリズムを指しています。]

回答：

以下のイベントのシーケンスを考慮してください：

  1. CPU 0は、関係のないロックを取得します。これを「problematic_lock」と呼び、spin_lock_irqsave()を通じてIRQを無効化します。

  2. CPU 1は進入します synchronize_rcu()、rcu_gp_mutexを書き込み取得します。

  3. CPU 0は進入します rcu_read_lock()、ただし、CPU 1がrcu_gp_mutexを保持しているため待機する必要があります。

  4. CPU 1が中断され、IRQハンドラがproblematic_lockを取得しようとします。

システムは現在デッドロックしています。

このデッドロックを回避する方法の一つは、CONFIG_PREEMPT_RTのアプローチを採用することです。ここで、すべての通常のスピンロックがブロッキングロックに、すべてのIRQハンドラが特殊なタスクのコンテキストで実行されます。この場合、上記のステップ4では、IRQハンドラがブロックされ、CPU 1がrcu_gp_mutexを解放できるようになり、デッドロックを回避できます。

デッドロックが発生しなくても、このRCU実装は、読者から他の読者への遅延が「漏れ」るようにします。 synchronize_rcu()これを確認するには、タスクAがRCU読み取り側クリティカルセクション（したがってrcu_gp_mutexを読み取り保持）にあり、タスクBがrcu_gp_mutexを書き込み取得しようとブロックされ、タスクCが rcu_read_lock() rcu_gp_mutexを読み取り取得しようとブロックされているタスクCがあります。タスクAのRCU読み取り側遅延がタスクCを妨げていますが、間接的にタスクBを通じてです。

リアルタイムRCU実装では、RCU読み取り側クリティカルセクション内のタスクが実行中のタスクによってブロックされないカウンタベースのアプローチを使用します。 synchronize_rcu().

クイズ #2:

負である例を挙げてください negative.

回答：

単一CPUのシステムを想像してください。そのシステムでは、プロセスコンテキストコードがルーティングテーブルを使用しますが、IRQコンテキストコード（たとえば、「ICMP REDIRECT」パケットを通じて）によって更新されることがあります。通常の処理方法は、プロセスコンテキストコードがルーティングテーブルを検索する際、割り込みを無効化することです。RCUの使用により、このような割り込み無効化は不要になります。したがって、RCUなしでは割り込み無効化のコストを支払いますが、RCUを使用すればそのコストは発生しません。

一部の人々は、この場合のRCUのオーバーヘッドが、単一CPUの割り込み無効化アプローチに対して負のオーバーヘッドであると主張します。一方で、他の人々はRCUのオーバーヘッドが単にゼロであり、正のオーバーヘッドを持つ割り込み無効化スキームをゼロオーバーヘッドのRCUスキームに置き換えることによって負のオーバーヘッドを生じるとは考えないかもしれません。

現実では、当然のことながら状況は複雑です。しかし、同期プリミティブの負荷が負になるという理論的な可能性さえも、ちょっと意外ですね。 ;-)

クイズ #3:

RCU読み込み側のクリティカルセクション内でブロックすることは禁止されていますが、PREEMPT_RTでは通常のスピンロックがブロック可能なので、どうやって処理するのでしょうか？？？

回答：

PREEMPT_RTはスピンロックのクリティカルセクションをプリエンプション可能に許可するように、RCU読み込み側のクリティカルセクションのプリエンプションも許可します。また、RCU読み込み側のクリティカルセクション内でのブロッキングスピンロックも許可します。

なぜこのような不一致が見られるのでしょうか？それは、必要に応じて優先度の上げ下げによってRCUのグレース期間を短縮できるからです（例えばメモリが不足している場合など）。一方で、ネットワーク受信などにブロッキングして待っている場合、どのプロセスを優先すべきかを判断する方法はありません。特に、優先すべきプロセスが人間である可能性があり、その人がピザを買いに出ていったという場合です。コンピュータで人間を刺激するようなことは、大変な関心を引くかもしれませんが、反対意見を引き起こす可能性もあります。それに、コンピュータが人間がどのピザ店に行ったかを知るなんてことはできませんよね？

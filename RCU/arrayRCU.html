RCUで読み込み優先配列を保護する¶

RCUはより一般的にリンクリストを保護するために使用されるが、配列を保護するにも利用できる。以下の3つの状況がある：

  1. ハッシュテーブル

  2. 静的配列

  3. リサイズ可能な配列

これらの3つの状況は、それぞれ配列のRCU保護ポインタを用いており、配列のインデックスをRCUで保護するという考えは tempting かもしれないが、この用途は ではありません サポートされていない。配列のRCU保護インデックスの問題点は、コンパイラが整数に対して過度な最適化を行う可能性があり、その扱いに関するルールが非常に複雑でコストがかかるためである。もし配列のRCU保護インデックスが特に有用であることが確認されたら（これまでのところそうではない）、コンパイラの明示的な協力を得て安全に使用できるようにする必要がある。

それ以外に、以下のセクションで3つのRCU保護ポインタの状況について説明する。

状況1: ハッシュテーブル¶

ハッシュテーブルは通常配列として実装され、各配列要素がリンクリストのハッシュチェーンを持つ。各ハッシュチェーンはlistRCU.txtドキュメントで説明されているようにRCUで保護できる。このアプローチは、radix treesなどの他の配列のリスト状態にも適用される。

状況2: 静的配列¶

データ自体（ポインタではなく）が各配列要素に配置され、配列のサイズが決して変更されない静的配列は、RCUで利用されていない。Rik van Rielはこの状況でseqlockを使用することを推奨しており、更新がまれであれば読み込み側のオーバーヘッドは最小限に抑えられる。

状況3: リサイズ可能な配列¶

リサイズ可能な配列のRCUの使用例として、System V IPCコードで以前使用されていたgrow_ary()関数がある。この配列はセマフォ、メッセージキュー、共有メモリIDを対応するIPC構造体のデータ構造にマッピングする。grow_ary()関数はロックを取得せず、代わりに呼び出し元がids->semセマフォを保持する必要がある。

以下のgrow_ary()関数は、いくつかの制限チェックを行い、新しいipc_id_aryを割り当て、古い内容を新しい配列にコピーし、新しい部分を初期化し、ids->entriesポインタを新しい配列に更新し、ipc_rcu_putref()を呼び出して古い配列を解放する。注意して rcu_assign_pointer() ids->entriesポインタの更新に使用され、どのアーキテクチャでもメモリバリアが含まれています:

static int grow_ary(struct ipc_ids* ids, int newsize)
{
        struct ipc_id_ary* new;
        struct ipc_id_ary* old;
        int i;
        int size = ids->entries->size;

        if(newsize > IPCMNI)
                newsize = IPCMNI;
        if(newsize <= size)
                return newsize;

        new = ipc_rcu_alloc(sizeof(struct kern_ipc_perm *)*newsize +
                            sizeof(struct ipc_id_ary));
        if(new == NULL)
                return size;
        new->size = newsize;
        memcpy(new->p, ids->entries->p,
               sizeof(struct kern_ipc_perm *)*size +
               sizeof(struct ipc_id_ary));
        for(i=size;i<newsize;i++) {
                new->p[i] = NULL;
        }
        old = ids->entries;

        /*
         * Use rcu_assign_pointer() to make sure the memcpyed
         * contents of the new array are visible before the new
         * array becomes visible.
         */
        rcu_assign_pointer(ids->entries, new);

        ipc_rcu_putref(old);
        return newsize;
}

ipc_rcu_putref()関数は配列の参照カウントを減算し、その後、参照カウントがゼロになった場合、 call_rcu() グレース期間が経過後に配列を解放します。

ipc_lock()関数が配列をトラバースします。この関数は、 rcu_read_lock()配列へのポインタを取得し、後で安全にデリファレンスできるようにするため、 rcu_dereference() メモリバリアが必要なAlpha CPUで動作します。配列のサイズが配列自体に格納されているため、配列サイズの不一致が起こらないため、単純なチェックで十分です。望ましいIPCオブジェクトに対応する構造体のポインタが「out」に配置され、NULLは存在しないエントリを示します。'out->lock'を取得した後、'out->deleted'フラグがIPCオブジェクトが削除中であるかどうかを示し、それ以外の場合はポインタが返されます:

struct kern_ipc_perm* ipc_lock(struct ipc_ids* ids, int id)
{
        struct kern_ipc_perm* out;
        int lid = id % SEQ_MULTIPLIER;
        struct ipc_id_ary* entries;

        rcu_read_lock();
        entries = rcu_dereference(ids->entries);
        if(lid >= entries->size) {
                rcu_read_unlock();
                return NULL;
        }
        out = entries->p[lid];
        if(out == NULL) {
                rcu_read_unlock();
                return NULL;
        }
        spin_lock(&out->lock);

        /* ipc_rmid() may have already freed the ID while ipc_lock
         * was spinning: here verify that the structure is still valid
         */
        if (out->deleted) {
                spin_unlock(&out->lock);
                rcu_read_unlock();
                return NULL;
        }
        return out;
}
クイッククイズの答え:

seqlockを使用する際、更新がまれであることがなぜ重要なのか？

seqlockを使用する際、更新がまれであることが重要であるのは、頻繁な更新がリーダーをライブロックする可能性があるからです。この問題を回避する方法の一つは、配列ごとにseqlockを割り当てるのではなく、配列全体に割り当てることです。

RCUを用いた読み込みが主なリンクリストの保護¶

RCU の最も効果的な応用の一つは、読み取りが主なリンクリストを保護することです（struct list_head list.h に記載されています）。このアプローチの大きな利点は、リストマクロに必要なメモリバリアがすべて含まれていることです。このドキュメントでは、RCU のいくつかの応用例を紹介します。特に重要な応用例から順に説明します。

例1: 読み込み中心リスト: 延期された破壊¶

カーネル内の RCU リストの一般的な用途の一つは、システム内のすべてのプロセスをロックなしで反復処理することです。 task_struct::tasks これはすべてのプロセスをリンクするリストノードを表します。リストは、リストの追加や削除と並行してトラバースできます。

リストのトラバースは、以下の 2 つのマクロによって行われます。 for_each_process() 以下の 2 つのマクロによって定義されています：

#define next_task(p) \
        list_entry_rcu((p)->tasks.next, struct task_struct, tasks)

#define for_each_process(p) \
        for (p = &init_task ; (p = next_task(p)) != &init_task ; )

すべてのプロセスのリストをトラバースするコードは通常、以下のように見えます：

rcu_read_lock();
for_each_process(p) {
        /* Do something with p */
}
rcu_read_unlock();

タスクリストからプロセスを削除する簡略化されたコードは以下です：

void release_task(struct task_struct *p)
{
        write_lock(&tasklist_lock);
        list_del_rcu(&p->tasks);
        write_unlock(&tasklist_lock);
        call_rcu(&p->rcu, delayed_put_task_struct);
}

プロセスが終了するとき、 release_task() 呼び出します list_del_rcu(&p->tasks) の下で tasklist_lock ライターロック保護の下で、すべてのタスクリストからタスクを削除します。この tasklist_lock リストの同時追加/削除によるリストの破壊を防ぎます。読者で for_each_process() は、以下の tasklist_lock。リストポインタの変更を読者に認識させないために、 task_struct オブジェクトは、1つ以上のグレース期間が経過した後でしか解放されません（ call_rcu()）。この遅延された破壊により、リストをトラバースしている読者は常に有効な p->tasks.next ポインタを参照でき、リストのトラバースと同時に削除/解放が行われます。このパターンはまた、 存在ロックと呼ばれます。RCU は、すべての既存の読者が終了するまでオブジェクトをメモリにピンします。

例2: ロック外での読み込み側アクション: 場所内更新なし¶

最も効果的な応用例は、読者-ライターロックを使用した場合、検索結果に基づいて行動を取る前に読み取り側のロックを解除するケースです。最も有名な例はルーティングテーブルです。ルーティングテーブルはコンピュータ外の機器の状態を追跡しているため、時折古いデータを含むことがあります。したがって、ルートが計算された後は、パケットの送信中にルーティングテーブルを静的保持する必要はありません。畢竟、ルーティングテーブルを静的保持しても、外部インターネットの変化は防げません。実際には外部インターネットの状態が重要です。さらに、ルーティングエントリは通常、追加または削除されることが多いですが、場所を変更するのではなく、直接編集されることが多いです。

この RCU の使用例は、システムコールの監査サポートに見られます。例えば、読者-ライターロックを使用した実装は以下のようにされます： audit_filter_task() 以下のようにされます：

static enum audit_state audit_filter_task(struct task_struct *tsk)
{
        struct audit_entry *e;
        enum audit_state   state;

        read_lock(&auditsc_lock);
        /* Note: audit_filter_mutex held by caller. */
        list_for_each_entry(e, &audit_tsklist, list) {
                if (audit_filter_rules(tsk, &e->rule, NULL, &state)) {
                        read_unlock(&auditsc_lock);
                        return state;
                }
        }
        read_unlock(&auditsc_lock);
        return AUDIT_BUILD_CONTEXT;
}

ここでリストはロックの下で検索されますが、対応する値が返される前にロックは解除されます。この値が処理されるまでに、リストはすでに変更されている可能性があります。これは、監査をオフにしている場合、いくつかの追加のシステムコールを監査しても問題ないため、理にかなっています。

これは、読み取り側にRCUを簡単に適用できる理由です。以下のようにします：

static enum audit_state audit_filter_task(struct task_struct *tsk)
{
        struct audit_entry *e;
        enum audit_state   state;

        rcu_read_lock();
        /* Note: audit_filter_mutex held by caller. */
        list_for_each_entry_rcu(e, &audit_tsklist, list) {
                if (audit_filter_rules(tsk, &e->rule, NULL, &state)) {
                        rcu_read_unlock();
                        return state;
                }
        }
        rcu_read_unlock();
        return AUDIT_BUILD_CONTEXT;
}

以下の read_lock() および read_unlock() 呼び出しはそれぞれ、そして rcu_read_lock() および rcu_read_unlock()の部分で、 list_for_each_entry() はそれぞれ、そして list_for_each_entry_rcu()の部分で、 _rcu() リストトラバーサルプリミティブは、DEC Alpha CPUで必要となる読み取り側のメモリバリアを挿入します。

更新側の変更も簡単です。削除や挿入の処理にはリーダーライターロックを以下のように使用できます：

static inline int audit_del_rule(struct audit_rule *rule,
                                 struct list_head *list)
{
        struct audit_entry *e;

        write_lock(&auditsc_lock);
        list_for_each_entry(e, list, list) {
                if (!audit_compare_rule(rule, &e->rule)) {
                        list_del(&e->list);
                        write_unlock(&auditsc_lock);
                        return 0;
                }
        }
        write_unlock(&auditsc_lock);
        return -EFAULT;         /* No matching rule */
}

static inline int audit_add_rule(struct audit_entry *entry,
                                 struct list_head *list)
{
        write_lock(&auditsc_lock);
        if (entry->rule.flags & AUDIT_PREPEND) {
                entry->rule.flags &= ~AUDIT_PREPEND;
                list_add(&entry->list, list);
        } else {
                list_add_tail(&entry->list, list);
        }
        write_unlock(&auditsc_lock);
        return 0;
}

これらの2つの関数のRCUの同等物は以下の通りです：

static inline int audit_del_rule(struct audit_rule *rule,
                                 struct list_head *list)
{
        struct audit_entry *e;

        /* No need to use the _rcu iterator here, since this is the only
         * deletion routine. */
        list_for_each_entry(e, list, list) {
                if (!audit_compare_rule(rule, &e->rule)) {
                        list_del_rcu(&e->list);
                        call_rcu(&e->rcu, audit_free_rule);
                        return 0;
                }
        }
        return -EFAULT;         /* No matching rule */
}

static inline int audit_add_rule(struct audit_entry *entry,
                                 struct list_head *list)
{
        if (entry->rule.flags & AUDIT_PREPEND) {
                entry->rule.flags &= ~AUDIT_PREPEND;
                list_add_rcu(&entry->list, list);
        } else {
                list_add_tail_rcu(&entry->list, list);
        }
        return 0;
}

通常、 write_lock() および write_unlock() はspin_lock()とspin_unlock()に置き換えられますが、この場合、すべての呼び出し元が audit_filter_mutexを保持しているため、追加のロックは必要ありません。したがって、 auditsc_lock は不要となり、RCUの使用によりライターサイドがリーダーを排他する必要がなくなるためです。

以下の list_del(), list_add(), and list_add_tail() プリミティブは list_del_rcu(), list_add_rcu(), and list_add_tail_rcu()の部分で、 _rcu() リスト操作プリミティブは、弱い順序性を持つCPU（ほとんどのCPU）で必要なメモリバリアを追加します。また、 list_del_rcu() プリミティブは、それ以外にコンカレンテッドリーダーが劇的に失敗する可能性があるポインタ毒化デバッグ支援コードを省略しています。

したがって、リーダーが古データを許容できる場合、またエントリが場所を変えていない場合に追加または削除される場合、RCUは非常に簡単に使用できます！

例3: 場所内更新の処理¶

システムコール監査コードは、監査ルールを場所を変えて更新しません。しかし、もし更新する場合、その処理を行うリーダーライターロックコードは以下のようになるかもしれません（のみが更新されるものと仮定）： field_count が更新される場合、それ以外の追加フィールドは埋め込まれる必要があります）：

static inline int audit_upd_rule(struct audit_rule *rule,
                                 struct list_head *list,
                                 __u32 newaction,
                                 __u32 newfield_count)
{
        struct audit_entry *e;
        struct audit_entry *ne;

        write_lock(&auditsc_lock);
        /* Note: audit_filter_mutex held by caller. */
        list_for_each_entry(e, list, list) {
                if (!audit_compare_rule(rule, &e->rule)) {
                        e->rule.action = newaction;
                        e->rule.field_count = newfield_count;
                        write_unlock(&auditsc_lock);
                        return 0;
                }
        }
        write_unlock(&auditsc_lock);
        return -EFAULT;         /* No matching rule */
}

RCUバージョンはコピーを作成し、コピーを更新し、古いエントリを新しい更新されたエントリで置き換えます。この操作は、コピーを作成して更新を行う間に並行して読み取りを許容するため、RCU（read-copy update）という名前が付けられています。RCUコードは以下の通りです：

static inline int audit_upd_rule(struct audit_rule *rule,
                                 struct list_head *list,
                                 __u32 newaction,
                                 __u32 newfield_count)
{
        struct audit_entry *e;
        struct audit_entry *ne;

        list_for_each_entry(e, list, list) {
                if (!audit_compare_rule(rule, &e->rule)) {
                        ne = kmalloc(sizeof(*entry), GFP_ATOMIC);
                        if (ne == NULL)
                                return -ENOMEM;
                        audit_copy_rule(&ne->rule, &e->rule);
                        ne->rule.action = newaction;
                        ne->rule.field_count = newfield_count;
                        list_replace_rcu(&e->list, &ne->list);
                        call_rcu(&e->rcu, audit_free_rule);
                        return 0;
                }
        }
        return -EFAULT;         /* No matching rule */
}

また、このコードは呼び出し元が audit_filter_mutexを保持していることを前提としています。通常、ライターロックはこの種のコードではスピンロックになります。

このパターンの他の用途は、openswitchドライバの 接続トラッキングテーブル コードの ct_limit_set()です。このテーブルは接続トラッキングエントリを保持し、最大エントリ数の制限があります。ゾーンごとにこのようなテーブルがあり、したがって各ゾーンごとに 制限 があります。ゾーンはハッシュチェーン用のRCU管理ハッシュリストを使用してハッシュテーブルを通してその制限にマッピングされます。新しい制限が設定されるとき、新しい制限オブジェクトが割り当てられ、 ct_limit_set() が呼ばれて古い制限オブジェクトが新しいオブジェクトで置き換えられます。 list_replace_rcu()古い制限オブジェクトは、クレーム期間の後に使用してから解放されます。 kfree_rcu().

例4: 古いデータの除去¶

監査の例では古データを許容していますが、外部状態を追跡するほとんどのアルゴリズムも同様です。Linuxが外部状態の変化を認識するまでに遅延があるため、RCUによって引き起こされる追加の古データは一般的に問題ではありません。

ただし、古データを許容できない例は多くあります。Linuxカーネルの例としてSystem V IPC（ipc/shm.cのshm_lock関数を参照）があります。このコードは、各エントリのスピンロックの下にある 削除 フラグを確認し、 削除 フラグが設定されている場合、エントリが存在しないかのように装います。この処理が有効なのは、検索関数が各エントリのスピンロックを保持しながら戻る必要があるからです。

クイズへの答え

システムコール監査モジュールが古データを拒否する必要が生じた場合、一つの方法はaudit_entry構造体に deleted フラグと lock スピンロックを追加し、 audit_filter_task() 以下のようになります:

static enum audit_state audit_filter_task(struct task_struct *tsk)
{
        struct audit_entry *e;
        enum audit_state   state;

        rcu_read_lock();
        list_for_each_entry_rcu(e, &audit_tsklist, list) {
                if (audit_filter_rules(tsk, &e->rule, NULL, &state)) {
                        spin_lock(&e->lock);
                        if (e->deleted) {
                                spin_unlock(&e->lock);
                                rcu_read_unlock();
                                return AUDIT_BUILD_CONTEXT;
                        }
                        rcu_read_unlock();
                        return state;
                }
        }
        rcu_read_unlock();
        return AUDIT_BUILD_CONTEXT;
}

audit_entry構造体を修正することです。注意点として、この例はエントリが追加または削除されるものと仮定しており、場所を更新する操作を処理するためには追加のメカニズムが必要です。 audit_upd_rule()一つの点として、 audit_upd_rule() には追加のメモリバリアが必要で、 list_add_rcu() が本当に実行される前に list_del_rcu().

以下の audit_del_rule() 関数はスピンロックの下でフラグを設定する必要があります。以下のように: deleted flag under the spinlock as follows:

static inline int audit_del_rule(struct audit_rule *rule,
                                 struct list_head *list)
{
        struct audit_entry *e;

        /* No need to use the _rcu iterator here, since this
         * is the only deletion routine. */
        list_for_each_entry(e, list, list) {
                if (!audit_compare_rule(rule, &e->rule)) {
                        spin_lock(&e->lock);
                        list_del_rcu(&e->list);
                        e->deleted = 1;
                        spin_unlock(&e->lock);
                        call_rcu(&e->rcu, audit_free_rule);
                        return 0;
                }
        }
        return -EFAULT;         /* No matching rule */
}

This too assumes that the caller holds audit_filter_mutex.

例5: 古いオブジェクトのスキップ¶

This too assumes that the caller holds CLOCK_REALTIME For some usecases, reader performance can be improved by skipping stale objects during read-side list traversal if the object in concern is pending destruction after one or more grace periods. One such example can be found in the timerfd subsystem. When a cancel_list clock is reprogrammed - for example due to setting of the system time, then all programmed timerfds that depend on this clock get triggered and processes waiting on them to expire are woken up in advance of their scheduled expiry. To facilitate this, all such timers are added to an RCU-managed timerfd_setup_cancel():

static void timerfd_setup_cancel(struct timerfd_ctx *ctx, int flags)
{
        spin_lock(&ctx->cancel_lock);
        if ((ctx->clockid == CLOCK_REALTIME &&
            (flags & TFD_TIMER_ABSTIME) && (flags & TFD_TIMER_CANCEL_ON_SET)) {
                if (!ctx->might_cancel) {
                        ctx->might_cancel = true;
                        spin_lock(&cancel_lock);
                        list_add_rcu(&ctx->clist, &cancel_list);
                        spin_unlock(&cancel_lock);
                }
        }
        spin_unlock(&ctx->cancel_lock);
}

when they are setup in might_cancel When a timerfd is freed (fd is closed), then the cancel_list flag of the timerfd object is cleared, the object removed from the

int timerfd_release(struct inode *inode, struct file *file)
{
        struct timerfd_ctx *ctx = file->private_data;

        spin_lock(&ctx->cancel_lock);
        if (ctx->might_cancel) {
                ctx->might_cancel = false;
                spin_lock(&cancel_lock);
                list_del_rcu(&ctx->clist);
                spin_unlock(&cancel_lock);
        }
        spin_unlock(&ctx->cancel_lock);

        hrtimer_cancel(&ctx->t.tmr);
        kfree_rcu(ctx, rcu);
        return 0;
}

もし CLOCK_REALTIME and destroyed: timerfd_clock_was_set() clock is set, for example by a time server, the hrtimer framework calls cancel_list which walks the cancel_listand wakes up processes waiting on the timerfd. While iterating the might_cancel flag is consulted to skip stale objects:

void timerfd_clock_was_set(void)
{
        struct timerfd_ctx *ctx;
        unsigned long flags;

        rcu_read_lock();
        list_for_each_entry_rcu(ctx, &cancel_list, clist) {
                if (!ctx->might_cancel)
                        continue;
                spin_lock_irqsave(&ctx->wqh.lock, flags);
                if (ctx->moffs != ktime_mono_to_real(0)) {
                        ctx->moffs = KTIME_MAX;
                        ctx->ticks++;
                        wake_up_locked_poll(&ctx->wqh, EPOLLIN);
                }
                spin_unlock_irqrestore(&ctx->wqh.lock, flags);
        }
        rcu_read_unlock();
}

The key point here is, because RCU-traversal of the cancel_list リストにオブジェクトが追加または削除されている間、トラバーサル中にリストから削除されたオブジェクトにアクセスしてしまうことがあります。この例では、このようなオブジェクトはフラグを使用してスキップする方が良いことが示されています。

Summary¶

古くなったデータを許容できる読み取りが主なリストベースのデータ構造はRCUの使用に最も適しています。最も単純なケースは、データ構造にエントリが追加または削除される（または場所を変えて原子的に行われる修正される）場合ですが、非原子的な場所の修正はコピーを作成して修正し、その後オリジナルをコピーに置き換えることで処理できます。古くなったデータを許容できない場合、 削除 フラグを各エントリごとのスピンロックと併用することで、検索関数が新たに削除されたデータを拒否できるようにします。

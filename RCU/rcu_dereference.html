rcu_dereference()の戻り値の適切な扱い¶

ほとんどの場合、以下の rcu_dereference() または類似のプリミティブのいずれかを使用して心配することなく、ポインタの間接参照（「*」プレフィックス）、フィールド選択（「->」）、代入（「=」）、アドレス取得（「&」）、定数の加算・減算、キャストなどはすべて自然で安全に動作します。

他の操作では問題が発生する可能性があります。RCUコードの正常な動作を保つためには、以下のルールを守ってください：

  • RCU保護ポインタを読み込むには、いずれかの rcu_dereference() プリミティブファミリを使用しなければなりません。そうでない場合、CONFIG_PROVE_RCUは警告を発します。さらに深刻なのは、コンパイラやDEC Alphaの最適化によってランダムなメモリ破壊バグが発生する可能性があることです。いずれかの rcu_dereference() プリミティブを使用しないと、コンパイラが値を再読み込みし、単一のポインタに対して2つの異なる値が存在するという不具合が発生します。また、 rcu_dereference()DEC Alphaでは、ポインタを読み込み、そのポインタを間接参照し、そのポインタの格納前の初期化前のデータを返す可能性があります。

    さらに、volatileキャストにおいて rcu_dereference() コンパイラが結果のポインタ値を推論できないようにします。コンパイラが実際にポインタの正確な値を推論できる例（「コンパイラが知りすぎている」セクションを参照）があるため、そのような場合では不適切な順序付けを引き起こす可能性があります。

  • rcu_dereferenceはポインタ値に対してのみ使用できます。コンパイラが整数値について過度に知っているため、整数演算を通じて依存関係を保持する信頼性がありません。例外は極めて限られており、ポインタを一時的にuintptr_tにキャストして以下の操作を行うことができます：

    • そのポインタの必須ゼロの低順位ビットにビットを設定またはクリアします。これは明確にポインタがアライメント制約を持つ必要があることを意味します。たとえば、char*ポインタでは一般的に動作しません。

    • ポインタをXORビットで変換する方法（一部の古典的なbuddy-allocatorアルゴリズムで使用される手法）。

    他の操作を行う前に、その値をポインタに戻すキャストを行うことが重要です。

  • 「+」および「-」のインフィックス算術演算子を使用する際、キャンセルを避けてください。たとえば、変数「x」に対して「(x-(uintptr_t)x)」のような式をchar*ポインタで使用するのは避けてください。コンパイラがこのような式をゼロに置き換える権利があり、その後のアクセスがもはやその値に依存しなくなる可能性があります。 rcu_dereference()これにより、不適切な順序付けによるバグが再び発生する可能性があります。

    もちろん、「p」が rcu_dereference()から取得されたポインタであり、「a」と「b」が偶然等しい整数である場合、式「p+a-b」はその値が依然として依存するため安全です。 rcu_dereference()これにより、適切な順序が維持されます。

  • RCUをJITed関数の保護に使用している場合、'()'という関数呼び出し演算子が、直接または間接的に取得された値に適用される rcu_dereference()この問題は、新しいJITed関数が以前のJITed関数と同じメモリを使用しているシステムで発生します。この場合、ハードウェアと直接やりとりしてインストラクションキャッシュをフラッシュする必要があります。

  • 比較演算子（「==」、「!=」、「>」、「>=」、「<」、「<=」）の結果をデリファレンシングに使用しないでください。例えば、以下の（非常に奇妙な）コードはバグがあります：

    int *p;
int *q;

...

p = rcu_dereference(gp)
q = &global_q;
q += p > &oom_p;
r1 = *q;  /* BUGGY!!! */

    以前と同様、このコードがバグっている理由は、比較演算子が通常ブランチを使用してコンパイルされるためです。また、ARMやPowerPCなどの弱いメモリマシンでは、このようなブランチの後にストアを順序付けることができますが、ロードを推測できるため、再び順序の誤りを引き起こすバグが発生する可能性があります。

  • 取得されたポインタを比較する際は、非常に注意が必要です。 rcu_dereference() NULLポインタ以外の値と比較する際は注意が必要です。リンス・トーラルズが説明したように、2つのポインタが等しい場合、コンパイラが比較しているポインタを取得したポインタに置き換える可能性があります。 rcu_dereference()。

    p = rcu_dereference(gp);
if (p == &default_struct)
        do_default(p->a);

    コンパイラが「p」の値が変数「default_struct」のアドレスであることを知っているため、このコードを以下のようになります：

    p = rcu_dereference(gp);
if (p == &default_struct)
        do_default(default_struct.a);

    ARMおよびPowerハードウェアでは、「default_struct.a」からのロードが推測されるようになり、これにより、それが「」の前に発生する可能性があります。 rcu_dereference()。これにより、順序の誤りによってバグが発生する可能性があります。

    ただし、以下のケースでは比較は問題ありません：

    • 比較がNULLポインタに対して行われた場合、コンパイラがポインタがNULLであることを知っている場合、デリファレンシングはしないべきです。比較が不等しい場合、コンパイラはそれ以上知りません。したがって、取得したポインタをNULLポインタと比較するのは安全です。 rcu_dereference() NULLポインタに対して行われた場合。

    • 比較後、ポインタがデリファレンシングされることはないため、コンパイラは比較から得た情報を使用して、存在しない後続のデリファレンシングを再配置できません。このような比較は、RCU保護された環状連結リストをスキャンする際に頻繁に発生します。

      RCU読み込み側クリティカルセクション内であるかのチェックが不要で、ポインタが決してデリファレンシングされない場合に注意してください、 rcu_access_pointer() は、の代わりに使用すべきです。 rcu_dereference().

    • 比較対象のポインタは、長時間前に初期化されたメモリを参照しています。この比較が安全な理由は、誤った実行順序が発生しても、その比較の後ろにあるアクセスには影響を与えないからです。では、『長時間前』とは具体的にどれくらい前のことなのでしょうか？以下がいくつかの可能性です。

      • コンパイル時。

      • ブート時。

      • モジュールコードのモジュール初期化時。

      • kthreadコードのkthread生成以前。

      • 現在保持しているロックの取得時。

      • 以前 mod_timer() タイマーハンドラの実行時。

      Linuxカーネルの幅広いプリミティブにより、コードが後続で実行されるようにする他の多くの可能性があります。

    • 比較対象のポインタも参照元 rcu_dereference()．この場合、両方のポインタはどちらか一方に依存するため、どちらの方法でも正しい順序が得られます。 rcu_dereference() どちらか一方に依存するため、どちらの方法でも正しい順序が得られます。

      ただし、この状況は特定のRCU使用に関するバグが発生しやすくなる可能性があります。テスト中に発生した場合であれば、これは良いことです。このようなRCU使用に関するバグの例は、「EXAMPLE OF AMPLIFIED RCU-USAGE BUG」セクションに示されています。

    • 比較後のすべてのアクセスはストア操作であり、制御依存関係が必要な順序を保持します。ただし、制御依存関係を誤って扱うのは簡単です。詳しくは、Documentation/memory-barriers.txtの「CONTROL DEPENDENCIES」セクションをご参照ください。

    • ポインタは等しくありませんかつ、コンパイラがポインタの値を推論するための十分な情報を持っていません。注意してください、以下のvolatileキャストでは rcu_dereference() 通常、コンパイラが過度に知るのを防ぎます。

      ただし、コンパイラがポインタが2つの値のうちの1つのみを取ることを知っている場合、等しくない比較はコンパイラがポインタの値を推論するために必要な正確な情報を提供します。

  • コンパイラが提供するすべての値推測最適化を無効にしてください。特に、過去の実行から収集したデータを使用するフィードバックベースの最適化を利用している場合。このような値推測最適化は設計上、操作の順序を再配置します。

RCUの使用ミスの例¶

アップデータがRCUリーダーと同時に実行されるため、RCUリーダーは古い値や不整合な値を確認することがあります。RCUリーダーが最新または整合的な値を必要とする場合（それが時折起きます）、適切な注意を払う必要があります。この現象を理解するため、以下のコード断片を考えてみましょう。

struct foo {
        int a;
        int b;
        int c;
};
struct foo *gp1;
struct foo *gp2;

void updater(void)
{
        struct foo *p;

        p = kmalloc(...);
        if (p == NULL)
                deal_with_it();
        p->a = 42;  /* Each field in its own cache line. */
        p->b = 43;
        p->c = 44;
        rcu_assign_pointer(gp1, p);
        p->b = 143;
        p->c = 144;
        rcu_assign_pointer(gp2, p);
}

void reader(void)
{
        struct foo *p;
        struct foo *q;
        int r1, r2;

        p = rcu_dereference(gp2);
        if (p == NULL)
                return;
        r1 = p->b;  /* Guaranteed to get 143. */
        q = rcu_dereference(gp1);  /* Guaranteed non-NULL. */
        if (p == q) {
                /* The compiler decides that q->c is same as p->c. */
                r2 = p->c; /* Could get 44 on weakly order system. */
        }
        do_something_with(r1, r2);
}

reader()が「r1」に読み込まれる時間と「r2」に読み込まれる時間の間にアップデータが2回呼び出された可能性があるにもかかわらず、結果（r1 == 143 && r2 == 44）が可能であることに驚くかもしれません。しかし、驚く必要はありません。なぜなら、アップデータが2回呼び出された可能性があるにもかかわらず、コンパイラやCPUの再配置によって同じ結果が発生する可能性があるからです。

しかし、リーダーが整合的なビューを必要とする場合を想定しましょう？

その場合、ロックを使用するというアプローチが考えられます。例えば、以下のようになります：

struct foo {
        int a;
        int b;
        int c;
        spinlock_t lock;
};
struct foo *gp1;
struct foo *gp2;

void updater(void)
{
        struct foo *p;

        p = kmalloc(...);
        if (p == NULL)
                deal_with_it();
        spin_lock(&p->lock);
        p->a = 42;  /* Each field in its own cache line. */
        p->b = 43;
        p->c = 44;
        spin_unlock(&p->lock);
        rcu_assign_pointer(gp1, p);
        spin_lock(&p->lock);
        p->b = 143;
        p->c = 144;
        spin_unlock(&p->lock);
        rcu_assign_pointer(gp2, p);
}

void reader(void)
{
        struct foo *p;
        struct foo *q;
        int r1, r2;

        p = rcu_dereference(gp2);
        if (p == NULL)
                return;
        spin_lock(&p->lock);
        r1 = p->b;  /* Guaranteed to get 143. */
        q = rcu_dereference(gp1);  /* Guaranteed non-NULL. */
        if (p == q) {
                /* The compiler decides that q->c is same as p->c. */
                r2 = p->c; /* Locking guarantees r2 == 144. */
        }
        spin_unlock(&p->lock);
        do_something_with(r1, r2);
}

いつも通り、正しいツールを選びましょう！

コンパイラが知りすぎている例¶

から取得したポインタが rcu_dereference() 他のポインタと比較して不等である場合、コンパイラはそのポインタの値について何の知識も持ちません。この知識の欠如により、コンパイラが最適化を行い、RCUに依存する順序保証を破壊する可能性があります。また、 rcu_dereference() におけるボラタイルキャストは、コンパイラが値を推測することを防ぐべきです。

しかし、 rcu_dereference()がない場合、コンパイラは予想以上に多くの情報を把握しています。以下のコード断片を考えてみましょう：

struct foo {
        int a;
        int b;
};
static struct foo variable1;
static struct foo variable2;
static struct foo *gp = &variable1;

void updater(void)
{
        initialize_foo(&variable2);
        rcu_assign_pointer(gp, &variable2);
        /*
         * The above is the only store to gp in this translation unit,
         * and the address of gp is not exported in any way.
         */
}

int reader(void)
{
        struct foo *p;

        p = gp;
        barrier();
        if (p == &variable1)
                return p->a; /* Must be variable1.a. */
        else
                return p->b; /* Must be variable2.b. */
}

コンパイラが「gp」へのすべてのストアを確認できるため、「gp」の可能な値は「variable1」か「variable2」のいずれかです。したがって、reader()内の比較によって、「p」の正確な値をコンパイラが把握できます。この結果、コンパイラが「gp」からのロードとは独立した戻り値を生成でき、その結果、ロードと戻り値のロード間の順序保証が破壊されます。これにより、「p->b」が初期化前のゴミ値を返す可能性があります。

要するに、 rcu_dereference() が結果のポインタをデリファレンスする際には必須です。

rcu_dereference()ファミリーのどのメンバを使用すべきか¶

まず、rcu_dereference_raw()の使用を避けてください。また、第二引数に定数値1（またはtrue）を指定して使用するのも避けてください。この注意点を踏まえた上で、以下のガイドラインを参考にしてください。 rcu_dereference_check() および rcu_dereference_protected() のどのメンバをさまざまな状況で使用するか： rcu_dereference() RCU読み込み側クリティカルセクション内でアクセスが必要な場合は、

  1. を使用してください。新しい統合されたRCUの味噌では、RCU読み込み側クリティカルセクションは rcu_dereference()で開始され、ボトムハーフを無効にするもの、割込みを無効にするもの、プリエマプションを無効にするもの、またはそれらのすべてを無効にするものです。 rcu_read_lock()で開始され、ボトムハーフを無効にするもの、割込みを無効にするもの、プリエマプションを無効にするもの、またはそれらのすべてを無効にするものです。

  2. アクセスが一方ではRCUの読み取り側クリティカルセクション内である可能性があり、他方では（例えれば）my_lockで保護されている場合、使用してください rcu_dereference_check()たとえば:

    p1 = rcu_dereference_check(p->rcu_protected_pointer,
                           lockdep_is_held(&my_lock));

  3. アクセスが一方ではRCUの読み取り側クリティカルセクション内である可能性があり、他方ではmy_lockまたはyour_lockのいずれかで保護されている場合でも、再度使用してください rcu_dereference_check()たとえば:

    p1 = rcu_dereference_check(p->rcu_protected_pointer,
                           lockdep_is_held(&my_lock) ||
                           lockdep_is_held(&your_lock));

  4. アクセスが更新側であるため、常にmy_lockで保護されている場合、使用してください rcu_dereference_protected():

    p1 = rcu_dereference_protected(p->rcu_protected_pointer,
                               lockdep_is_held(&my_lock));

    これは#3の通り複数のロックを処理するように拡張でき、両方とも他の条件をチェックするための拡張も可能です

  5. 保護が呼び出し元によって提供され、このコードには未知である場合、rcu_dereference_raw()が適切です。さらに、ロックデップの式が過度に複雑になる場合にもrcu_dereference_raw()が適切かもしれませんが、その場合のより良いアプローチは、同期設計を見直すことかもしれません。それでも、ポインタを保護するのに何百ものロックや参照カウンタのうちのどれでも十分なデータロックのケースがあり、rcu_dereference_raw()はその場所があります

    ただし、現在のカーネルでの使用例の数を考えれば、その場所はおそらく想像以上に小さく、同義語であるrcu_dereference_check(…, 1)や近い関係にあるrcu_dereference_protected(…, 1)も同様です

RCU保護ポインタのスパースチェック¶

sparse静的解析ツールは、RCU保護ポインタへの直接アクセスをチェックし、コンパイラ最適化による仮想ロードやロードテアリングなどの原因で「興味深い」バグを引き起こす可能性があります。例えば、誰かが間違ってこのようなコードを書いたとします:

p = q->rcu_protected_pointer;
do_something_with(p->a);
do_something_else_with(p->b);

レジスタ圧力が高ければ、コンパイラが「p」を存在しないものとして最適化し、コードを以下のように変換する可能性があります:

do_something_with(q->rcu_protected_pointer->a);
do_something_else_with(q->rcu_protected_pointer->b);

q->rcu_protected_pointerがその間変更された場合、あなたのコードが致命的に失敗する可能性があります。これは理論的な問題ではありません：ちょうどこのようなバグが、Paul E. McKenney（および彼の無辜な同僚たち）に1990年代前半に3日間の週末を奪いました

ロードテアリングは、ポインタのペアのマッシュアップを参照してしまう可能性があり、これもあなたのコードを致命的に失敗させるかもしれません

これらの問題は、コードを以下のように書けば簡単に回避できただけです

p = rcu_dereference(q->rcu_protected_pointer);
do_something_with(p->a);
do_something_else_with(p->b);

残念ながら、このようなバグはレビュー中に非常に見逃しやすいです。このような場合、sparseツールと「__rcu」マーカーが役立ちます。ポインタの宣言（構造体内であれ形式パラメータであれ）に「__rcu」を付けることで、sparseにこのポインタが直接アクセスされている場合を警告させることができます。また、「__rcu」でマークされていないポインタが特定の方法でアクセスされている場合にもsparseが警告を出します。 rcu_dereference() たとえば、->rcu_protected_pointerは以下のようになります：

struct foo __rcu *rcu_protected_pointer;

「__rcu」の使用はオプトインです。使用しない場合は、sparseの警告は無視してください。

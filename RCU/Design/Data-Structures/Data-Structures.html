はじめに¶

このドキュメントでは、RCUの主要なデータ構造とそれらの関係について説明します。

データ構造の関係¶

RCUは実質的に大規模な状態機械であり、そのデータ構造はRCUリーダーが非常に高速に実行できるように、そしてアップデータが要求するRCUグレース期間を効率的かつ極めてスケーラブルな方法で処理できるように、状態を保持しています。RCUアップデータの効率とスケーラビリティは、以下の図に示すように、主に結合木（combining tree）によって提供されます。

この図は、包含する rcu_state 構造体で、木構造を含みます rcu_node この木構造の各葉ノードは rcu_node 木構造には最大で16 rcu_data 構造体が関連付けられており、これにより NR_CPUS 構造体の数は rcu_data 構造体があり、それぞれの可能なCPUに対応しています。この構造体は、必要に応じて起動時に調整され、 nr_cpu_ids ははるかに少ない NR_CPUsです。たとえば、いくつかのLinuxディストリビューションは NR_CPUs=4096、これは3段階の木構造をもたらします rcu_node tree. If the actual hardware has only 16 CPUs, RCU will adjust itself at boot time, resulting in an rcu_node tree with only a single node.

この結合木の目的は、クイエスcent状態、dyntick-idle遷移、CPUホットプラグ操作などのCPUごとのイベントを効率的かつスケーラブルに処理することです。クイエスcent状態はCPUごとの rcu_data 構造で記録され、他のイベントは葉レベルの rcu_node 構造で記録されます。これらのすべてのイベントは、木の各レベルで結合され、最終的に木のルート rcu_node 構造でグレースペリオドが完了します。グレースペリオドは、すべてのCPU（または、タスクの場合は CONFIG_PREEMPT_RCU、タスク）がクイエスcent状態を通過した後、ルートで完了できます。グレースペリオドが完了すると、その事実が木の根から下へと逆に伝播されます。

図に示すように、64ビットシステムでは、64の葉を持つ2段階の木構造は1,024のCPUを収容でき、ルートでは64のファンアウト、葉では16のファンアウトで構成されます。

RCUアップデータは、通常のグレースペリオドを待つためにRCUコールバックを登録することにより、直接的に call_rcu() または間接的に synchronize_rcu() などにより実行されます。RCUコールバックは rcu_head structures, which are queued on rcu_data structures while they are waiting for a grace period to elapse, as shown in the following figure:

This figure shows how TREE_RCU’s and PREEMPT_RCU’s major data structures are related. Lesser data structures will be introduced with the algorithms that make use of them.

Note that each of the data structures in the above figure has its own synchronization:

  1. Each rcu_state structures has a lock and a mutex, and some fields are protected by the corresponding root rcu_node structure’s lock.

  2. Each rcu_node structure has a spinlock.

  3. The fields in rcu_data are private to the corresponding CPU, although a few can be read and written by other CPUs.

It is important to note that different data structures can have very different ideas about the state of RCU at any given time. For but one example, awareness of the start or end of a given RCU grace period propagates slowly through the data structures. This slow propagation is absolutely necessary for RCU to have good read-side performance. If this balkanized implementation seems foreign to you, one useful trick is to consider each instance of these data structures to be a different person, each having the usual slightly different view of reality.

The general role of each of these data structures is as follows:

  1. rcu_state: This structure forms the interconnection between the rcu_node および rcu_data structures, tracks grace periods, serves as short-term repository for callbacks orphaned by CPU-hotplug events, maintains rcu_barrier() state, tracks expedited grace-period state, and maintains state used to force quiescent states when grace periods extend too long,

  2. rcu_node: This structure forms the combining tree that propagates quiescent-state information from the leaves to the root, and also propagates grace-period information from the root to the leaves. It provides local copies of the grace-period state in order to allow this information to be accessed in a synchronized manner without suffering the scalability limitations that would otherwise be imposed by global locking. In CONFIG_PREEMPT_RCU kernels, it manages the lists of tasks that have blocked while in their current RCU read-side critical section. In CONFIG_PREEMPT_RCU with CONFIG_RCU_BOOST, it manages the per-rcu_node priority-boosting kernel threads (kthreads) and state. Finally, it records CPU-hotplug state in order to determine which CPUs should be ignored during a given grace period.

  3. rcu_data: This per-CPU structure is the focus of quiescent-state detection and RCU callback queuing. It also tracks its relationship to the corresponding leaf rcu_node structure to allow more-efficient propagation of quiescent states up the rcu_node combining tree. Like the rcu_node この構造体は、ローカルのgrace-period情報をコピーして、対応するCPUからこの情報を無料で同期してアクセスできるようにします。最後に、この構造体は対応するCPUの過去のdyntick-idle状態を記録し、統計情報を追跡します。

  4. rcu_headこの構造体はRCUコールバックを表し、RCUユーザーによって割り当てられ管理される唯一の構造体です。この rcu_head 構造体は通常、RCU保護されたデータ構造内に埋め込まれています。

クイッククイズ:

Suppose that this rcu_node structure doesn’t see a request for a very long time. Won’t wrapping of the ->gp_seq field cause problems?

答え:

No, because if the ->gp_seq_needed field lags behind the ->gp_seq field, the ->gp_seq_needed field will be updated at the end of the grace period. Modulo-arithmetic comparisons therefore will always get the correct answer, even with wrapping.

Quiescent-State Tracking¶

These fields manage the propagation of quiescent states up the combining tree.

この rcu_node structure has fields as follows:

1   unsigned long qsmask;
2   unsigned long expmask;
3   unsigned long qsmaskinit;
4   unsigned long expmaskinit;

以下の ->qsmask field tracks which of this rcu_node structure’s children still need to report quiescent states for the current normal grace period. Such children will have a value of 1 in their corresponding bit. Note that the leaf rcu_node structures should be thought of as having rcu_data structures as their children. Similarly, the ->expmask field tracks which of this rcu_node structure’s children still need to report quiescent states for the current expedited grace period. An expedited grace period has the same conceptual properties as a normal grace period, but the expedited implementation accepts extreme CPU overhead to obtain much lower grace-period latency, for example, consuming a few tens of microseconds worth of CPU time to reduce grace-period duration from milliseconds to tens of microseconds. The ->qsmaskinit field tracks which of this rcu_node structure’s children cover for at least one online CPU. This mask is used to initialize ->qsmask, and ->expmaskinit is used to initialize ->expmask 通常のおよび緊急の優先期間の開始です。

クイッククイズ:

なぜこれらのビットマスクはロックで保護されているのでしょうか？冗談です、原子操作の概念を聞いたことないのですか？？

答え:

ロックレスの優先期間計算！なんて魅力的な可能性でしょう！しかし、以下のイベントのシーケンスを考慮してください：

  1. CPU 0は、相当長い間dyntick-idleモードに入っていた。起動時に、現在のRCU優先期間が報告を求めており、スケジューリングクロック割り込みが見つけるフラグを設定する。

  2. 一方、CPU 1は実行中である。 force_quiescent_state()、CPU 0がdyntick idleモードに入っていたことに気づく。これは拡張された静的状態に該当する。

  3. CPU 0のスケジューリングクロック割り込みがRCU読み取り側クリティカルセクションの真ん中で発生し、RCUコアが必要なことが判明したため、RCU softirq処理を開始する。

  4. CPU 0のsoftirqハンドラが実行され、静的状態を上位に報告するところまで来たところです。 rcu_node 木の葉では16のファンアウトがうまく機能することが確認されています。

  5. しかし、CPU 1が先に行動し、現在の優先期間を終了し、新しい優先期間を開始する。

  6. CPU 0は現在の優先期間ではなく、誤った優先期間の静的状態を報告します。その優先期間がRCU読み取り側クリティカルセクションよりも早く終了する可能性があります。その場合、大変な事態になります。

したがって、ビットのクリアとグレースペリオドのシーケンス番号の更新を調整するためにロックは絶対に必要であり、 ->gp_seq.

For 32-bit systems, this allows 16*32*32*32=524,288 CPUs, which should be sufficient for the next few years at least. For 64-bit systems, 16*64*64*64=4,194,304 CPUs is allowed, which should see us through the next decade or so. This four-level tree also allows kernels built with CONFIG_RCU_FANOUT=8 to support up to 4096 CPUs, which might be useful in very large systems having eight CPUs per socket (but please note that no one has yet shown any measurable performance degradation due to misaligned socket and rcu_node boundaries). 2   unsigned long dynticks_fqs;

以下の ->dynticks_snap フィールドは、クイエスcent状態を強制する際に対応するCPUのdyntick-idle状態のスナップショットを取得するために使用され、他のCPUからアクセスされます。最後に、 ->dynticks_fqs フィールドは、このCPUがdyntick-idle状態にあると判定される回数をカウントし、トレースおよびデバッグの目的で使用されます。

このrcu_data構造体の一部は以下の通り宣言されています：

1   long dynticks_nesting;
2   long dynticks_nmi_nesting;
3   atomic_t dynticks;
4   bool rcu_need_heavy_qs;
5   bool rcu_urgent_qs;

Summary¶

So the state of RCU is represented by an rcu_state structure, which contains a combining tree of rcu_node および rcu_data structures. Finally, in CONFIG_NO_HZ_IDLE kernels, each CPU’s dyntick-idle state is tracked by dynticks-related fields in the rcu_data structure. If you made it this far, you are well prepared to read the code walkthroughs in the other articles in this series.

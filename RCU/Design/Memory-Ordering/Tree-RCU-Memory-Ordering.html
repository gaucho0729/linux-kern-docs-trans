はじめに¶

このドキュメントでは、Tree RCUのグレースペリオドメモリ順序保証がどのように提供されるかの視覚的な概要を示します。

Tree RCUのグレースペリオドメモリ順序保証とは何ですか？¶

RCUのグレースペリオドは、非アイドル非オフラインコードに対して非常に強いメモリ順序保証を提供します。あるRCUグレースペリオドの終了後に実行されるコードは、そのグレースペリオドの開始前のすべてのアクセス（RCU読み込み側クリティカルセクション内）の効果を必ず見ます。同様に、あるRCUグレースペリッドの開始前に行われるコードは、そのグレースペリオドの終了後のすべてのアクセス（RCU読み込み側クリティカルセクション内）の効果を必ず見ます。

RCU-sched読み込み側クリティカルセクションは、プリエンプションが無効なコードの任意の領域を含みます。個々のマシン指令は非常に小さなプリエンプション無効コードの領域とみなせるため、 synchronize_rcu() as smp_mb() 強化版。

RCUアップデーターは、この保証を2つのフェーズに分けて実行することで利用します。1つ目のフェーズはグレースペリオドの前、2つ目のフェーズはグレースペリオドの後です。最も一般的な使用例では、1つ目のフェーズでリンクされたRCU保護データ構造から要素を削除し、2つ目のフェーズでその要素を解放します。これには、1つ目のフェーズの更新（一般的には削除）前に状態を観測したリーダーが、2つ目のフェーズの更新（一般的には解放）後の状態を観測しない必要があります。

RCUの実装は、次のセクションで説明するように、ロックベースのクリティカルセクション、メモリバリア、パーセパーセット処理を用いてこの保証を提供します。

Tree RCU グレースペリオドメモリ順序構築ブロック¶

RCUのグレースペリオドメモリ順序の主役は、 rcu_node 構造体の ->lockのクリティカルセクションです。これらのクリティカルセクションは、ロック取得用のアシスタント関数を含む、 raw_spin_lock_rcu_node(), raw_spin_lock_irq_rcu_node(), and raw_spin_lock_irqsave_rcu_node()を用います。そのロック解放対応はそれぞれ raw_spin_unlock_rcu_node(), raw_spin_unlock_irq_rcu_node(), and raw_spin_unlock_irqrestore_rcu_node()です。完全性を保つため、 raw_spin_trylock_rcu_node() も提供されています。重要な点は、ロック取得関数（ raw_spin_trylock_rcu_node()を含む）が、ロックの取得成功後に必ず smp_mb__after_unlock_lock() を呼び出します。

したがって、任意の rcu_node 構造、任意のアクセスが上記のロック解放関数のいずれかの前に発生した場合、すべてのCPUは、その後の上記のロック取得関数のいずれかの後のアクセスをその前に発生したものとして扱います。さらに、任意のCPUにおいて上記のロック解放関数のいずれかの前のアクセスは、すべてのCPUにおいて、そのCPUで実行された上記のロック取得関数のいずれかの後のアクセスをその前に発生したものとして扱われます。このロック解放関数とロック取得関数は異なる構造を操作している場合でも、そのように扱われます。 rcu_node Tree RCUは、これらの2つの順序保証を用いて、グレースペリオドに関与したすべてのCPU間で順序ネットワークを形成します。これは、グレースペリオド中にオンラインになったりオフラインになったりしたCPUも含みます。

答え:

コールバック実行¶

あるCPUの葉 rcu_node 構造体の ->gp_seq フィールドが更新されると、そのCPUはこのグレースペリオドの終了を待っていたRCUコールバックを呼び出すことができる。これらのコールバックは rcu_advance_cbs()によって識別され、これは通常 __note_gp_changes()によって呼び出される。以下の図に示すように、この呼び出しはスケジューリングクロック割り込み（rcu_sched_clock_irq() の左）またはアイドルエントリ（rcu_cleanup_after_idle() の右、ただし CONFIG_RCU_FAST_NO_HZ=yでビルドされたカーネルのみ）によってトリガーされる。いずれにしても、 RCU_SOFTIRQ が発生し、これにより rcu_do_batch() がコールバックを呼び出し、これにより各更新の必要な第2段階の処理（直接的にも間接的にもウェイクアップを通じて）が実行される。

注意点として、コールバックの呼び出しは、CPUがコールバックキューに蓄積された数が過剰であると認識した場合など、さまざまな特殊なコードパスによってもトリガーされる可能性がある。いずれの場合も、CPUはコールバック呼び出し前にその葉 rcu_node 構造体の ->lock を取得し、これにより新規に完了したグレースペリオドに対する必要な順序が保持される。

ただし、コールバック関数が他のCPUと通信する場合（例：ウェイクアップを行う場合）、その関数の責任で順序を維持する必要がある。例えば、コールバック関数が他のCPUで実行されるタスクをウェイクアップする場合、コールバック関数とウェイクアップされるタスクの両方で適切な順序が確保される必要がある。なぜこれが重要かを理解するため、以下の グレースペリオドクリーンアップ 図の上半分を見てほしい。コールバックは左端の葉 rcu_node 構造に対応するCPUで実行され、右端の葉 rcu_node 構造に対応するCPUで実行されるタスクをウェイクアップする可能性がある。この場合、グレースペリオドのカーネルスレッドはまだ右端の葉に到達していないかもしれない。このため、グレースペリオドのメモリ順序がまだそのCPUに到達していない可能性がある。このような場合でも、コールバック関数とウェイクアップされたタスクは適切な順序を提供しなければならない。

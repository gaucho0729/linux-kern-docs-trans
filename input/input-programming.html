1. 入力デバイスドライバの作成¶

1.1. 最も簡単な例¶

ここにインプットデバイスドライバの非常に簡単な例が出てきます。このデバイスにはただ1つのボタンがあり、そのボタンはI/OポートBUTTON_PORTでアクセス可能です。押下または解放時にBUTTON_IRQが発生します。ドライバは以下のように見えるかもしれません：

#include <linux/input.h>
#include <linux/module.h>
#include <linux/init.h>

#include <asm/irq.h>
#include <asm/io.h>

static struct input_dev *button_dev;

static irqreturn_t button_interrupt(int irq, void *dummy)
{
        input_report_key(button_dev, BTN_0, inb(BUTTON_PORT) & 1);
        input_sync(button_dev);
        return IRQ_HANDLED;
}

static int __init button_init(void)
{
        int error;

        if (request_irq(BUTTON_IRQ, button_interrupt, 0, "button", NULL)) {
                printk(KERN_ERR "button.c: Can't allocate irq %d\n", button_irq);
                return -EBUSY;
        }

        button_dev = input_allocate_device();
        if (!button_dev) {
                printk(KERN_ERR "button.c: Not enough memory\n");
                error = -ENOMEM;
                goto err_free_irq;
        }

        button_dev->evbit[0] = BIT_MASK(EV_KEY);
        button_dev->keybit[BIT_WORD(BTN_0)] = BIT_MASK(BTN_0);

        error = input_register_device(button_dev);
        if (error) {
                printk(KERN_ERR "button.c: Failed to register device\n");
                goto err_free_dev;
        }

        return 0;

err_free_dev:
        input_free_device(button_dev);
err_free_irq:
        free_irq(BUTTON_IRQ, button_interrupt);
        return error;
}

static void __exit button_exit(void)
{
        input_unregister_device(button_dev);
        free_irq(BUTTON_IRQ, button_interrupt);
}

module_init(button_init);
module_exit(button_exit);

1.2. この例が行っていること¶

まず、<linux/input.h>ファイルをインクルードする必要があります。これは入力サブシステムにインターフェースを提供し、必要なすべての定義を提供します。

_init関数は、モジュールのロードまたはカーネルの起動時に呼ばれます。ここでは必要なリソースを取得し（デバイスの存在を確認する必要があります）、

次に、新しい入力デバイス構造体を割り当てます input_allocate_device() そして入力ビットフィールドを設定します。これにより、デバイスドライバーが入力システムの他の部分にこのデバイスの種類（この入力デバイスが生成または受け入れ可能なイベント）を伝えます。私たちの例では、EV_KEYタイプのイベントのみを生成でき、そのうちBTN_0イベントコードのみです。したがって、これらの2つのビットのみを設定します。代わりに以下のようにすることもできました：

set_bit(EV_KEY, button_dev.evbit);
set_bit(BTN_0, button_dev.keybit);

というのも、複数のビットを使用する場合、最初のアプローチの方が短くなる傾向があります。

次に、例のドライバーは以下の呼び出しにより入力デバイス構造体を登録します：

input_register_device(&button_dev);

これにより、button_dev構造体が入力ドライバーのリンクリストに追加され、デバイスハンドラモジュールの_connect関数が新しい入力デバイスが出現したことを通知します。 input_register_device() スリープする可能性があるため、割り込みまたはスピンロックを保持している状態で呼び出すことはできません。

使用中、ドライバーで使用される関数は次の通りです：

button_interrupt()

ボタンからの割り込みごとにその状態を確認し、以下の呼び出しを通じて報告します：

input_report_key()

入力システムへの呼び出しです。割り込みルーチンが入力システムに同じ値のイベント（例えば、押下、押下）を報告しているかどうかを確認する必要はありません。input_report_*関数がそれらを自動的にチェックします。

次に、以下の呼び出しがあります：

input_sync()

イベントを受信する側に、完全なレポートを送信したことを通知する呼び出しです。これは1つのボタンのケースでは重要に見えませんが、例えばマウスの移動のようにXとYの値を個別に解釈したくない場合、非常に重要です。なぜなら、それによって移動の結果が変わるからです。

1.3. dev->open() と dev->close()¶

ドライバーがデバイスから割込みが来ないためポーリングを繰り返す必要がある場合、またはポーリングが常に実行されるほどコストが高いため、デバイスが貴重なリソース（例：割込み）を使用している場合、openとcloseコールバックを使用して、ポーリングを停止するか割込みを解放するタイミング、または再開するか割込みを再取得するタイミングを知ることができます。これを実現するには、例のドライバーに以下を追加します：

static int button_open(struct input_dev *dev)
{
        if (request_irq(BUTTON_IRQ, button_interrupt, 0, "button", NULL)) {
                printk(KERN_ERR "button.c: Can't allocate irq %d\n", button_irq);
                return -EBUSY;
        }

        return 0;
}

static void button_close(struct input_dev *dev)
{
        free_irq(IRQ_AMIGA_VERTB, button_interrupt);
}

static int __init button_init(void)
{
        ...
        button_dev->open = button_open;
        button_dev->close = button_close;
        ...
}

入力コアはデバイスのユーザー数を追跡し、dev->open()は最初のユーザーがデバイスに接続したときにのみ呼び出され、dev->close()は最後のユーザーが切断したときに呼び出されます。両方のコールバック呼び出しはシリアル化されます。

open()コールバックは成功した場合は0を、失敗した場合はゼロ以外の値を返す必要があります。close()コールバック（void型）は常に成功する必要があります。

1.4. 基本的なイベントタイプ¶

最もシンプルなイベントタイプはEV_KEYで、これはキーやボタンに使用されます。これは入力システムに以下のように報告されます：

input_report_key(struct input_dev *dev, int code, int value)

codeの許容値（0からKEY_MAX）についてはuapi/linux/input-event-codes.hを参照してください。値は真偽値として解釈され、ゼロ以外の値はキーが押されたことを、ゼロはキーが解放されたことを意味します。入力コードは、値が以前と異なる場合にのみイベントを生成します。

EV_KEYに加えて、EV_RELとEV_ABSという2つの基本的なイベントタイプがあります。これらはデバイスが提供する相対値と絶対値に使用されます。相対値の例は、マウスのX軸の移動です。マウスは最後の位置からの相対的な差を報告するため、絶対座標系を持たないためです。絶対イベントはジョイストickやデジタイザ（絶対座標系で動作するデバイス）に使用されます。

デバイスがEV_RELボタンを報告するのもEV_KEYと同様に簡単で、対応するビットを設定し、以下のように関数を呼び出します：

input_report_rel(struct input_dev *dev, int code, int value)

関数。ゼロ以外の値に対してのみイベントが生成されます。

しかしEV_ABSには特別な注意が必要です。input_register_deviceを呼び出す前に、デバイスが持つ各絶対軸に対応するinput_dev構造体の追加フィールドを埋め込む必要があります。もしボタンデバイスがABS_X軸も持っていたとしたら：

button_dev.absmin[ABS_X] = 0;
button_dev.absmax[ABS_X] = 255;
button_dev.absfuzz[ABS_X] = 4;
button_dev.absflat[ABS_X] = 8;

あるいは、単純に以下のように指定できます：

input_set_abs_params(button_dev, ABS_X, 0, 255, 4, 8);

この設定は、最小値が0、最大値が255（ジョイストickが到達可能で、たとえ時々より大きな値を報告しても問題ないが、常に最小値と最大値を到達可能でなければならない）で、データに+-4のノイズがあり、中心のフラットな位置のサイズが8のジョイストickのX軸に適しています。 grace periodsを尊重しなければなりませんし、 ジョイストickのX軸の設定で、最小値が0、最大値が255（ジョイストickが到達可能で、たとえ時々より大きな値を報告しても問題ないが、常に最小値と最大値を到達可能でなければならない）で、データに+-4のノイズがあり、中心のフラットな位置のサイズが8です。

absfuzz と absflat が不要な場合は、ゼロに設定することで、精度が高く常に正確な中心位置（存在する場合）に戻るようになります。

1.5. BITS_TO_LONGS(), BIT_WORD(), BIT_MASK()¶

bitops.h にあるこれらの3つのマクロは、いくつかのビットフィールド計算を支援します：

BITS_TO_LONGS(x) - returns the length of a bitfield array in longs for
                   x bits
BIT_WORD(x)      - returns the index in the array in longs for bit x
BIT_MASK(x)      - returns the index in a long for bit x

1.6. id* および name フィールド¶

dev->name は、入力デバイスドライバーが入力デバイスを登録する前に設定する必要があります。これは「Generic button device」のようなユーザー向けのデバイス名を含む文字列です。

id* フィールドには、バスID（PCI、USB、…）、ベンダーID、デバイスIDが含まれます。バスIDは input.h で定義されており、ベンダーおよびデバイスIDは pci_ids.h、usb_ids.h などのインクルードファイルで定義されています。これらのフィールドは、入力デバイスドライバーがデバイスを登録する前に設定する必要があります。

idtype フィールドは、入力デバイスドライバーに特有の情報として使用できます。

id および name フィールドは、evdev インターフェースを介してユーザー空間に渡せます。

1.7. keycode、keycodemax、keycodesize フィールド¶

これらの3つのフィールドは、密集したキーマップを持つ入力デバイスで使用する必要があります。keycode はスキャンコードを入力システムのキーボードコードにマッピングする配列であり、keycode max には配列のサイズ、keycodesize には各エントリのサイズ（バイト単位）を指定します。

ユーザー空間は、evdev インターフェースの EVIOCGKEYCODE および EVIOCSKEYCODE ioctls を使って現在のスキャンコードからキーボードコードへのマッピングを照会および変更できます。デバイスが上記の3つのフィールドをすべて埋めると、ドライバーはキーボードコードマッピングの設定および照会をカーネルのデフォルト実装に依存できます。

1.8. dev->getkeycode() および dev->setkeycode()¶

getkeycode() および setkeycode() コールバックは、ドライバーが input core が提供するキーボードコード/keycodesize/keycodemax マッピングメカニズムをオーバーライドし、スパースなキーボードコードマップを実装できます。

1.9. キーロックの自動繰り返し¶

…は簡単です。input.c モジュールで処理されます。ハードウェアの自動繰り返しは、多くのデバイスに存在せず、存在する場合でも（キーボード：トヨタノートブックなど）時折破損しているため使用されません。デバイスの自動繰り返しを有効にするには、dev->evbit に EV_REP を設定するだけで、すべてを input システムが処理します。

1.10. その他のイベントタイプ、出力イベントの処理¶

これまでの他のイベントタイプは以下の通りです：

  • EV_LED - キーボードのLEDに使用されます。

  • EV_SND - キーボードの蜂鳴に使用されます。

これらはキーボードイベントなどと非常に似ていますが、方向が逆です。システムから入力デバイスドライバーへ送信されます。入力デバイスドライバーがこれらのイベントを処理できる場合、evbit にそれぞれのビットを設定する必要があります。 および また、コールバックルーチンも設定してください：

button_dev->event = button_event;

int button_event(struct input_dev *dev, unsigned int type,
                 unsigned int code, int value)
{
        if (type == EV_SND && code == SND_BELL) {
                outb(value, BUTTON_BELL);
                return 0;
        }
        return -1;
}

このコールバックルーチンは割込みまたはBH（ただし、これはルールではありません）から呼び出されることがあり、したがってスリープしてはならず、処理が長時間かかることがないようにしなければなりません。

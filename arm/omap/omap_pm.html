OMAP PMインターフェース¶

このドキュメントでは、一時的な OMAP PM インターフェースについて説明します。ドライバ開発者は、この関数を使用して、カーネルの電源管理コードに最小レイテンシーまたはスループットの制約を伝達します。時間とともに、OMAP PM インターフェースの機能は Linux PM QoS コードに統合される予定です。

ドライバは以下の PM パラメータを表現する必要があります:

  • TI SRF に存在する電源管理パラメータの範囲をサポートする;

  • TI SRF または Linux PM QoS または Linux レイテンシーフレームワークなど、下位の PM パラメータ実装とドライバを分離する;

  • レイテンシーおよびスループットなどの基本単位に基づいて PM パラメータを指定し、OMAP または特定の OMAP バリアントに特有の単位を使用しない;

  • DaVinci などの他のアーキテクチャと共有されるドライバが、非 OMAP システムに影響を与えない方法でこれらの制約を追加できるようにする;

  • 他のアーキテクチャへの影響を最小限に抑えながらすぐに実装可能である。

このドキュメントでは、ドライバコード用の OMAP PM インターフェースを提案し、以下の5つの電源管理関数を含みます:

  1. 最大 MPU ウォーキングレイテンシーを設定:

    (*pdata->set_max_mpu_wakeup_lat)(struct device *dev, unsigned long t)

  2. 最大デバイスウォーキングレイテンシーを設定:

    (*pdata->set_max_dev_wakeup_lat)(struct device *dev, unsigned long t)

  3. 最大システムDMA転送開始レイテンシー（CORE pwrdm）を設定:

    (*pdata->set_max_sdma_lat)(struct device *dev, long t)

  4. デバイスが必要とする最小のバススループットを設定:

    (*pdata->set_min_bus_tput)(struct device *dev, u8 agent_id, unsigned long r)

  5. デバイスがコンテキストを失った回数を返す:

    (*pdata->get_dev_context_loss_count)(struct device *dev)

すべての OMAP PM インターフェース関数に関するさらに詳しいドキュメンテーションは、arch/arm/plat-omap/include/mach/omap-pm.h にあります。

OMAP PM レイヤーは一時的なものです¶

最終的には、Linux PM QoS レイヤーが OMAP3 に存在する電源管理機能の範囲をサポートする予定です。このプロセスが進行するにつれ、既存の OMAP PM インターフェースを使用しているドライバは Linux PM QoS コードに変更され、OMAP PM インターフェースは消えていく予定です。

OMAP PM 関数のドライバ使用方法¶

上記の例で示されているように、これらの関数はドライバに pdata を通じて、ドライバ .platform_data 構造体内の関数ポインタを通じて公開されます。関数ポインタは board-*.c ファイルによって、対応する OMAP PM 関数にポインタを指すように初期化されます:

  • set_max_dev_wakeup_lat は omap_pm_set_max_dev_wakeup_lat() にポインタを指し、などです。これらの関数をサポートしない他のアーキテクチャでは、これらの関数ポインタを NULL に設定しておきます。ドライバは以下の idiom を使用する必要があります:

    if (pdata->set_max_dev_wakeup_lat)
    (*pdata->set_max_dev_wakeup_lat)(dev, t);

これらの関数の最も一般的な用途は、割り込みが発生した時点からデバイスが使用可能になるまでの最大時間を指定することでしょう。これを実現するため、ドライバ開発者は、MPUの wakeup latency を制限するため set_max_mpu_wakeup_lat() 関数を使用し、デバイスの wakeup latency（使用可能になるまでの時間）を制限するため set_max_dev_wakeup_lat() 関数を使用すべきです（ clk_enable() 使用可能になるまでの時間）例えば：

/* Limit MPU wakeup latency */
if (pdata->set_max_mpu_wakeup_lat)
    (*pdata->set_max_mpu_wakeup_lat)(dev, tc);

/* Limit device powerdomain wakeup latency */
if (pdata->set_max_dev_wakeup_lat)
    (*pdata->set_max_dev_wakeup_lat)(dev, td);

/* total wakeup latency in this example: (tc + td) */

PM パラメータは、新しい値で関数を再度呼び出すことで上書きできます。設定を削除するには、t 引数を -1 として関数を呼び出します（set_max_bus_tput() の場合を除く）。

上記の5番目の関数 omap_pm_get_dev_context_loss_count() は、ドライバがデバイスが内部コンテキストを失ったかどうかを判定するための最適化として意図されています。コンテキストが失われた場合、ドライバはその内部コンテキストを復元した後で処理を続行する必要があります。

その他の専用インターフェース関数¶

上記の5つの関数は、すべてのデバイスドライバが使用できるように意図されています。DSPBridge と CPUFreq にはいくつか特殊な要件があります。DSPBridge は OPP ID を使ってターゲット DSP のパフォーマンスレベルを表現し、CPUFreq は MPU 周波数を使ってターゲット MPU のパフォーマンスレベルを表現します。OMAP PM インターフェースには、これらの専用ケースで OPP/MPU 周波数などの入力情報を、基盤となる電源管理実装が必要な形式に変換するための関数が含まれています：

  1. (*pdata->dsp_get_opp_table)(void)

  2. (*pdata->dsp_set_min_opp)(u8 opp_id)

  3. (*pdata->dsp_get_opp)(void)

  4. (*pdata->cpu_get_freq_table)(void)

  5. (*pdata->cpu_set_freq)(unsigned long f)

  6. (*pdata->cpu_get_freq)(void)

プラットフォーム向け OPP のカスタマイズ¶

CONFIG_PM を定義することで、シリコン向けの OPP レイヤーが有効になり、OPP テーブルの登録は自動的に実行されます。ただし、特殊なケースでは、デフォルトの OPP テーブルを調整する必要があります。例えば：

  • デフォルトで無効になっている OPP を有効にする（プラットフォームによって有効にする可能性がある）

  • プラットフォームでサポートされていない OPP を無効にする

  • このような場合、ボードファイルは以下の追加の手順を実行する必要があります：

arch/arm/mach-omapx/board-xyz.c:

#include "pm.h"
....
static void __init omap_xyz_init_irq(void)
{
        ....
        /* Initialize the default table */
        omapx_opp_init();
        /* Do customization to the defaults */
        ....
}
ノート:

omapx_opp_init は omap3_opp_init または omap ファミリに応じて必要なものになります。

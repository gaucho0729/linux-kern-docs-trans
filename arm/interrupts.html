割込み¶

2.5.2-rmk5:

これは、いくつかの主要なアーキテクチャ固有のサブシステムに大幅な変更を加えた最初のカーネルです。

まず、MMU TLBの処理方法にかなりの変更が加えられています。各MMU TLBの変体は完全に別々に処理されるようになりました - TLB v3、TLB v4（ライトバッファなし）、TLB v4（ライトバッファあり）、そして最終的にTLB v4（ライトバッファあり、I TLB無効化エントリあり）が含まれます。これらの関数内にはより多くのアセンブリコードが含まれており、今後の柔軟なTLB処理を可能にするためです。

次に、IRQサブシステム。

2.5カーネルでは、IRQの処理方法に大幅な変更が行われます。残念ながら、この変更により、irq_desc[]配列にアクセスする機種（基本的にすべての機種）が破損し、現在存在するすべての機種に影響が出ます。

例を挙げると、AssabetとNeponsetを使用した場合、以下のようになります：

          GPIO25                 IRR:2
SA1100 ------------> Neponset -----------> SA1111
                                 IIR:1
                              -----------> USAR
                                 IIR:0
                              -----------> SMC9196

現在の仕様では、すべてのSA1111割込みはお互いに排他的です。SA1111から割込みを処理している間、他のSA1111やSMC9196の割込みは処理を待つ必要があります。たとえば、SA1111のIDE PIOベースの割込みは、複数セクタのデータ転送が完了するまで、他のSA1111やSMC9196の割込みをブロックします。これは時間がかかる場合があります。また、SA1111の割込みハンドラでループしているため、SMC9196の割込みを無限にブロックすることも可能です。

新しいアプローチではいくつかの新しいアイデアが導入されています…

「親」と「子」の概念を導入します。たとえば、Neponsetハンドラでは、「親」はGPIO25で、「子」はSA1111、SMC9196、USARです。

また、「IRQチップ」の概念を導入します（主にirqdesc配列のサイズを減らすため）。これは実際の「IC」である必要はありません。実際、SA11x0のIRQは、GPIO0-10用とその他のすべてのIRQ用の2つの「チップ」構造で処理されます。これはさまざまな操作を含むコンテナです（この構造体の名前は今後改善される可能性があります）。この構造体には以下の操作があります：

struct irqchip {
        /*
         * Acknowledge the IRQ.
         * If this is a level-based IRQ, then it is expected to mask the IRQ
         * as well.
         */
        void (*ack)(unsigned int irq);
        /*
         * Mask the IRQ in hardware.
         */
        void (*mask)(unsigned int irq);
        /*
         * Unmask the IRQ in hardware.
         */
        void (*unmask)(unsigned int irq);
        /*
         * Re-run the IRQ
         */
        void (*rerun)(unsigned int irq);
        /*
         * Set the type of the IRQ.
         */
        int (*type)(unsigned int irq, unsigned int, type);
};
ack

  • 必須。do_level_IRQで処理されるIRQの場合、maskと同じ関数を使用する場合があります。

mask

  • 必須。

unmask

  • 必須。

rerun

  • 任意。do_level_IRQですべてのIRQを処理する場合、不要です。可能な限りハードウェアIRQを再トリガーする必要があります。再トリガーができない場合は、ハンドラを直接呼び出すこともできます。

type

  • 任意。IRQのタイプを変更できない場合はnullに設定し、ユーザーがタイプを設定できないことを検出できるようにします。

各IRQに対して、以下の情報を保持しています:

  • 「disable」深度（ disable_irq()s without enable_irq()s)

  • このIRQに対して行える操作を示すフラグ（有効、プローブ、noautounmask）は以前と同様です

  • IRQの状態（プローブ中、有効、など）

  • チップ

  • 各IRQハンドラ

  • irqaction構造体リスト

ハンドラは、レベル、エッジ、シンプルの3つの標準ハンドラのいずれか、または特別な処理が必要な場合は独自のハンドのラを使用できます。

「レベル」ハンドラは現在の実装で使用されており、非常にシンプルです。「エッジ」ハンドラは、このようなIRQ実装の欠陥を把握しており、ハードウェアIRQを処理中に有効に保つ必要があります。処理中にIRQが再度発生した場合、キューイングする必要があります。「シンプル」ハンドラは非常に基本的で、ハードウェア操作や状態追跡を行いません。これはSMC9196や上記のUSARなどの用途に適しています。

では、変更点は何か？¶

  1. マシン実装はirqdesc配列に書き込みを行ってはいけません。

  2. irqdesc配列を操作する新しい関数。最初の4つはマシン固有のコードにのみ有用とされています。最後の関数はマシン固有のコードにのみ推奨されますが、絶対に必要であればドライバでも使用可能です。

    set_irq_chip(irq,chip)

    このIRQのマスク/アンマスク処理方法を設定します

    set_irq_handler(irq,handler)

    このIRQのハンドラ（レベル、エッジ、シンプル）を設定します

    set_irq_chained_handler(irq,handler)

    このIRQの「チェイン」ハンドラを設定します - 自動的にこのIRQを有効にします（例：NeponsetおよびSA1111ハンドラ）。

    set_irq_flags(irq,flags)

    有効/プローブ/noautoenableフラグを設定します。

    set_irq_type(irq,type)

    IRQのエッジ（レベル）を有効にします。これはSA1111 INTPOL操作およびset_GPIO_IRQ_edge()関数の代替です。typeは<linux/irq.h>で定義されたIRQ_TYPE_xxxのいずれかです。

  3. set_GPIO_IRQ_edge()は非推奨となり、set_irq_typeで置き換えられます。

  4. SA1111 INTPOLへの直接アクセスは非推奨です。set_irq_typeを使用してください。

  5. ハンドラは、SA1110 GPIOに直接接続されている場合など、SA1111 IRQステータスを再読み込むたびにSA1110 IRQをアサートする必要があります。

  6. 自身のIRQ有効/無効制御を持たない子デバイス（例：SMC9196）に対しては、子ハンドラが呼ばれる間、親IRQをマスクまたは確認する必要があります。この場合、子ハンドラは「シンプル」ハンドラ（エッジもしくはレベルタイプではない）でなければなりません。ハンドラが完了した後、親IRQを再有効化し、すべての子デバイスの状態を再確認して保留中のイベントを検出する必要があります。（詳細はNeponset IRQハンドラを参照）

  7. fixup_irq()は削除されました arch/arm/mach-*/include/mach/irq.h

注意点として、この方法ではすべての問題を解決できない可能性があります。一部の問題はハードウェアに依存しています。同一の親信号でレベルベースとエッジベースのIRQを混在させること（例：neponset）は、ソフトウェアベースの解決策でも低IRQラテンシへの完全な対応は難しい領域です。

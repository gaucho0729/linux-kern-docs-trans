Bare-Metal相互排他用のvlocks¶

投票ロック（vlocks）は、メモリシステムに合理的かつ最小限の要件を課すことで、単純な低レベルの相互排他メカニズムを提供します。

これらは、ハードウェアが他のメカニズムを提供せず、通常のスピンロックが使用できない状況において、非連携なCPU間で臨時活動を調整するために使用することを意図しています。

vlocksは、単一のメモリ場所への書き込みにメモリシステムが提供するアトミック性を活用します。選挙を実行する際には、すべてのCPUが自身を「投票」する形で、共通のメモリ場所に一意の番号を保存します。すべての投票が終了した後、そのメモリ場所で確認される最終的な値が勝者を示します。

選挙が有限時間内で明確な結果をもたらすことを保証するため、CPUは勝者が選ばれていないかつ選挙がまだ開始されていない場合にのみ選挙に参加します。

アルゴリズム¶

vlocksアルゴリズムを説明する最も簡単な方法は、擬似コードを使用することです：

int currently_voting[NR_CPUS] = { 0, };
int last_vote = -1; /* no votes yet */

bool vlock_trylock(int this_cpu)
{
        /* signal our desire to vote */
        currently_voting[this_cpu] = 1;
        if (last_vote != -1) {
                /* someone already volunteered himself */
                currently_voting[this_cpu] = 0;
                return false; /* not ourself */
        }

        /* let's suggest ourself */
        last_vote = this_cpu;
        currently_voting[this_cpu] = 0;

        /* then wait until everyone else is done voting */
        for_each_cpu(i) {
                while (currently_voting[i] != 0)
                        /* wait */;
        }

        /* result */
        if (last_vote == this_cpu)
                return true; /* we won */
        return false;
}

bool vlock_unlock(void)
{
        last_vote = -1;
}

currently_voting[]配列は、CPUが選挙中であるかどうかを判定する方法を提供し、ラムポートのバーキーアルゴリズム[1]における「entering」配列に相当する役割を果たします。

しかし、選挙が開始されると、その下にあるメモリシステムのアトミック性が勝者を決定します。これにより、静的優先度ルールによる同順位解消や、オーバーフローするカウンターを必要としなくなります。

last_vote変数がすべてのCPUにグローバルに可視である限り、すべてのCPUがcurrently_votingフラグをクリアした後には、その変数に含まれる値は変化しません。

特徴と制限¶

  • vlocksは公平性を意図していません。競合状態においては、最後にロックを取得しようとしたCPUが最も勝ちやすいです。

    そのため、一意の勝者を選び出す必要があるが、どのCPUが勝つかは問題でない状況に最も適しています。

  • 他の類似メカニズムと同様に、vlocksは大量のCPUに対してスケーラブル性が低いです。

    必要に応じて、vlocksは投票階層を階層的に接続することでスケーラビリティを向上させることができます。以下は4096CPUの仮想例です：

    /* first level: local election */
my_town = towns[(this_cpu >> 4) & 0xf];
I_won = vlock_trylock(my_town, this_cpu & 0xf);
if (I_won) {
        /* we won the town election, let's go for the state */
        my_state = states[(this_cpu >> 8) & 0xf];
        I_won = vlock_lock(my_state, this_cpu & 0xf));
        if (I_won) {
                /* and so on */
                I_won = vlock_lock(the_whole_country, this_cpu & 0xf];
                if (I_won) {
                        /* ... */
                }
                vlock_unlock(the_whole_country);
        }
        vlock_unlock(my_state);
}
vlock_unlock(my_town);

ARM実装¶

現在のARM実装[2]には、基本アルゴリズムを超えたいくつかの最適化が含まれています：

  • currently_voting配列のメンバを近くに詰めることで、1つのトランザクションで配列全体を読み込むことが可能になります（ロックを競合するCPUの数が十分に少ないことを前提とします）。これにより、外部メモリへのラウンドトリップ回数を減らすことができます。

    ARM実装では、これにより単一のロードと比較操作を使用できます：

    LDR     Rt, [Rn]
CMP     Rt, #0

    …以下のコードに代わって

    LDRB    Rt, [Rn]
CMP     Rt, #0
LDRBEQ  Rt, [Rn, #1]
CMPEQ   Rt, #0
LDRBEQ  Rt, [Rn, #2]
CMPEQ   Rt, #0
LDRBEQ  Rt, [Rn, #3]
CMPEQ   Rt, #0

    これにより高速パスのレイテンシーが削減され、競合状態でバス競合が潜在的に減少します。

    この最適化は、ARMメモリシステムが重なったメモリアクセスの整合性を保証することに依存しています（これは多くの他のアーキテクチャでも同様です）。注意点として、currently_voting配列のどの要素がRtのどのビットに出現するかは気にせず、この最適化ではエンドイアンネスを考慮する必要がありません。

    ロックを競合するCPUが多すぎる場合、1つのトランザクションで配列を読み込むことはできず、複数のトランザクションが必要になります。実装ではこのケースのためにワードサイズのロードを繰り返すシンプルなループを使用しています。バイト単位でロードする場合と比べてトランザクション回数は依然として少ないです。

    原則として、LDRDやLDMを使用してさらに集約することも可能ですが、コードを簡潔に保つため、初期実装では試みられませんでした。

  • vlocksは現在、キャッシュを有効にできなかったCPU間での同期にのみ使用されています。これにより、キャッシュメモリでアルゴリズムを実行する際の多くのバリアーが不要になります。

    currently_voting配列の詰め込みは、すべてのロックを競合するCPUがキャッシュ整合性を有する場合を除き、キャッシュメモリでは機能しません。これは、1つのCPUからのキャッシュライトバックが他のCPUが書いた値を上書きしてしまうためです。（ただし、すべてのCPUがキャッシュ整合性を有する場合、おそらく適切なスピンロックを使用すべきです）。

  • last_vote変数に使用される「投票がまだない」値は0（擬似コードでは-1ですが）です。これにより、静的割当のvlockは.bssセクションに配置するだけで自動的にアンロックされた状態に初期化されます。

    各CPUのIDに対してオフセットを加えてこの変数を設定するため、どのCPUもIDとして0を使用することはありません。

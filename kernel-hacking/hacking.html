参加者¶

システム内のCPUはいつでも以下の状態のいずれかです:

  • プロセスと関連付けられず、ハードウェア割込みを処理中;

  • プロセスと関連付けられず、ソフトIRQまたはタスクレットを処理中;

  • プロセス（ユーザーコンテキスト）と関連付けられ、カーネル空間で実行中;

  • ユーザー空間でプロセスを実行中。

これらには順序があります。下位の2つの状態はお互いにプリエンプション可能ですが、それ以上では厳格な階層構造があり、それぞれの状態は上位の状態のみによってプリエンプションされます。例えば、CPU上でソフトIRQが実行中であるとき、他のソフトIRQはその実行を中断できませんが、ハードウェア割込みは可能です。ただし、システム内の他のCPUは独立して実行されます。

ユーザーコンテキストでは、割込みをブロックする方法がいくつかあり、本当に非プリエンプションになることが確認されます。

ユーザーコンテキスト¶

ユーザーコンテキストはシステムコールやその他のトラップから入る状態です。ユーザー空間と同様に、より重要なタスクや割込みによってプリエンプションされる可能性があります。sleep状態になるには、 schedule().

プリエンプションまたはソフトIRQが無効になっている場合（以下参照） in_interrupt() は偽陽性を返します。

ハードウェア割込み（Hard IRQs）¶

タイマータイク、ネットワークカード、キーボードはいつでも割込みを発生させる実際のハードウェアの例です。カーネルは割込みハンドラを実行し、ハードウェアを処理します。カーネルはこのハンドラが再入されないことを保証しており、同じ割込みが到来した場合、キューイング（または破棄）されます。このハンドラは割込みを無効化しているため、高速でなければなりません。頻繁に、このハンドラは割込みを確認し、ソフトウェア割込みの実行を示すフラグを設定して終了します。

ハードウェア割込み中であることを知るには、 in_irq() が真を返します。

警告

割り込みが無効になっている場合（以下参照）では偽陽性を返す可能性があるため注意してください。

ソフトウェア割り込みコンテキスト: Softirqとタスクレット¶

システムコールがユーザー空間に戻る直前、またはハードウェア割り込みハンドラが終了するとき、待機中の「ソフトウェア割り込み」（通常はハードウェア割り込みによってマークされる）が実行されます（kernel/softirq.c).

実際の割り込み処理の多くはここです。SMPへの移行初期には「ボトムハーフ」（BH）のみがあり、マルチCPUを活用していませんでした。風車式コンピュータ（マッチ棒と鼻水で作られた）から切り替えた直後に、この制限を廃止し「Softirq」に移行しました。

include/linux/interrupt.h ソフトウェア割り込みの種類をリストアップしています。非常に重要なソフトウェア割り込みはタイマーソフトウェア割り込み（include/linux/timer.h）です：指定された時間間隔で関数を呼び出すように登録できます。

ソフトウェア割り込みは複数のCPUで同時に実行されるため扱いにくいです。そのためタスクレット（include/linux/interrupt.h）がより多く使われます：動的に登録可能（任意の数を登録できます）であり、タスクレットは常に1つのCPUのみで実行されるように保証されていますが、異なるタスクレットは同時に実行可能です。

警告

タスクレットという名前は誤解を招くかもしれません：タスクとは関係なく、当時アレクセイ・クズネツォフが飲んだ悪いボドカと関係があるのかもしれません。

ソフトウェア割り込み（またはタスクレット）内であることを確認するには、 in_softirq() マクロ（include/linux/preempt.h).

警告

割り込みが無効になっている場合（以下参照）では偽陽性を返す可能性があるため注意してください。 ボトムハーフロック が保持されている場合。

基本的なルール¶

メモリ保護はありません

メモリを破壊すると、ユーザー空間でも割り込み空間でも、全体がクラッシュします。ユーザー空間でやりたいことが出来ないことを確認していますか？

浮動小数点やMMXは使用できません

FPUコンテキストは保存されません。ユーザー空間でもFPU状態は現在のプロセスと一致しない可能性があります：ユーザープロセスのFPU状態を操作してしまいます。本当にこれを行いたい場合は、FPU状態を明示的に保存/復元する必要があります（コンテキストスイッチを避けることも）。これは一般的に悪いアイデアです；まず固定小数点算術を使用してください。

厳格なスタック制限

コンフィギュレーションオプションに応じて、32ビットアーキテクチャでは3Kから6K、64ビットアーキテクチャでは14K程度のサイズです。割り込みと共有されるため、すべての領域を確保できません。スタック上の深すぎる再帰や大きなローカル配列は避けてください（動的に割り当ててください）。

Linuxカーネルは移植性があります

このように維持してください。コードは64ビット対応で、エンドイアンの依存性を持たない必要があります。CPU固有の処理を最小限に抑え、インラインアセンブリはきれいにカプセル化し、移植性を高めるように簡潔に実装してください。基本的にアーキテクチャに依存するカーネルツリーの部分に限定してください。

ioctls: 新しいシステムコールの作成は避ける¶

システムコールは一般的に以下のように見えます:

asmlinkage long sys_mycall(int arg)
{
        return 0;
}

まず、ほとんどの場合、新しいシステムコールを作成する必要はありません。キャラクタデバイスを作成し、それに適切なioctlを実装してください。これはシステムコールよりも柔軟で、各アーキテクチャのファイルに記述する必要はなく、Linusに受け入れられやすいです。 include/asm/unistd.h および arch/kernel/entry.S ファイルに記述する必要はなく、Linus に受け入れられやすいです。

すべての処理がパラメータの読み書きだけであれば、インターフェースの実装を検討してください。 sysfs() ioctl 内ではユーザー コンテキストでプロセスを処理します。エラーが発生した場合は、否定された errno を返します（参照

sleep した後は、シグナルが発生していないか確認する必要があります。Unix/Linux では、シグナルを処理するため、システムコールを一時的に終了してエラーを返します。 -ERESTARTSYS システムコールのエントリーコードがユーザー コンテキストに戻り、シグナルハンドラを処理した後、システムコールが再開されます（ユーザーが無効にしなければ）。そのため、データ構造を操作している途中などで再開を処理する準備が必要です。

一般的なルーチン¶

printk()¶

定義は include/linux/printk.h

printk() コンソール、dmesg、syslog デーモンにカーネルのメッセージを転送します。デバッグやエラー報告に有用で、割込みコンテキストでも使用可能です。ただし注意が必要です：コンソールに printk メッセージが大量に表示されるとマシンは使用不能になります。ANSI C の printf とほぼ互換性のあるフォーマット文字列を使用し、C の文字列連結によって最初の「優先度」引数を提供します。

printk(KERN_INFO "i = %u\n", i);

参照 include/linux/kern_levels.h; 他の KERN_ 値も同様に扱われ、syslog によってレベルとして解釈されます。特殊なケースとして、IP アドレスを出力する場合は以下の形式を使用します：

__be32 ipaddress;
printk(KERN_INFO "my ip: %pI4\n", &ipaddress);

printk() 内部では 1KB のバッファを使用し、オーバーフローは捕捉しません。十分なサイズであることを確認してください。

注意

ユーザーのプログラムで printf を打つ代わりに printk を打つようになるとき、あなたは本物のカーネルハッカーです :)

注意

別の補足：元の Unix Version 6 のソースコードには printf 関数の上にコメントがあり、「Printf はチャットには使わない」とありました。そのアドバイスに従うべきです。

copy_to_user() / copy_from_user() / get_user() / put_user()¶

定義は include/linux/uaccess.h / asm/uaccess.h

[SLEEPS]

put_user() および get_user() ユーザー空間と単一の値（int、char、long など）を取得・設定するために使用されます。ユーザー空間へのポインタは単純にデリファレンスすべきではありません：データはこれらのルーチンを使用してコピーする必要があります。どちらも -EFAULT を返します。

copy_to_user() および copy_from_user() はより一般的で、ユーザー空間と任意の量のデータをコピーします。

kmalloc()/kfree()¶

定義は include/linux/slab.h

[スリープ可能：下記を参照]

これらのルーチンは、malloc と free がユーザー空間で行うように、動的にポインタアライメントされたメモリのチャンクを動的に要求しますが、 kmalloc() は追加のフラグワードを取る点が異なります。重要な値：

GFP_KERNEL

スリープ可能で、メモリを解放するためにスワップする可能性があります。ユーザー コンテキストでのみ許可されますが、メモリを割り当てる最も信頼性の高い方法です。

GFP_ATOMIC

スリープしない。より信頼性が低いですが、割込みコンテキストから呼び出すことができます。エラー処理戦略をしっかり持つべきです。 GFP_KERNELのほうが信頼性が高いので、 本当に はメモリ不足のエラー処理戦略をしっかり持つべきです。

GFP_DMA

ISA DMA を 16MB 未満で割り当てます。ISA DMA が何であるか分からない場合は必要ありません。非常に信頼性が低いです。

スリープする関数が無効なコンテキストから呼ばれた警告メッセージが表示された場合は、割込みコンテキストから GFP_ATOMICを呼び出した可能性があります。その問題を修正すべきです。走るのではなく、走りなさい。

少なくとも PAGE_SIZE (asm/page.h または asm/page_types.h) バイトを割り当てている場合、以下の関数を使用することを検討してください： __get_free_pages() (include/linux/gfp.h)。これはオーダー引数（0 はページサイズ、1 は2ページ、2 は4ページなど）と上記と同じメモリ優先度フラグワードを取ります。

1 ページ以上を割り当てている場合は、 vmalloc()これはカーネルマップ内で仮想メモリを割り当てます。このブロックは物理メモリで連続していませんが、MMUはこれをあなたにとって連続しているように見えさせます（CPUには連続しているように見えるが、外部デバイスドライバーにはそう見えません）。もし本当に一部の特殊なデバイスのために物理的に連続したメモリが必要な場合、問題があります：Linuxではサポートが不十分で、時間が経つにつれて実行中のカーネルでのメモリのフラグメンテーションにより困難になります。最善の方法は、起動プロセスの初期段階でこのブロックを割り当てることです。 alloc_bootmem() ルーチン。

よく使われるオブジェクトのキャッシュを自作する前に、Linuxのslabキャッシュを使用することを検討してください。 include/linux/slab.h

current()¶

定義は include/asm/current.h

このグローバル変数（実際にはマクロ）は現在のタスク構造へのポインタを保持しており、ユーザーコンテキストでのみ有効です。たとえば、プロセスがシステムコールを実行するとき、このポインタは呼び出し元のプロセスのタスク構造を指します。これは NULLではありません 割込みコンテキストでは有効ではありません。

mdelay()/udelay()¶

定義は include/asm/delay.h / include/linux/delay.h

以下の udelay() および ndelay() 関数は小さな一時停止に使用できます。これらに大きな値を渡すとオーバーフローのリスクがありますので、ヘルパーファンクション mdelay() を使用するか、考慮してください。 msleep().

cpu_to_be32()/be32_to_cpu()/cpu_to_le32()/le32_to_cpu()¶

定義は include/asm/byteorder.h

以下の cpu_to_be32() 「32」は64や16に、「be」は「le」に置き換えることができる「イン・スイットファミリ」は、カーネルでのエンディアン変換を行う一般的な方法です：これらは変換後の値を返します。すべての変種は逆の変換も提供します： be32_to_cpu()などの数値かもしれません。

これらの関数には2つの主要な変種があります：ポインタを引数として受け取るポインタ変種、たとえば cpu_to_be32p()、および値を変換してvoidを返す「イン・スイットファミリ」、たとえば cpu_to_be32s()です。

local_irq_save()/local_irq_restore()¶

定義は include/linux/irqflags.h

これらのルーチンはローカルCPUのハードウェア割込みを無効にし、復元します。これらは再入可能で、前の状態を1つの引数で保存します。割込みが有効であることを知っている場合は、単に unsigned long flags を使用してください。 local_irq_disable() および local_irq_enable().

local_bh_disable()/local_bh_enable()¶

定義は include/linux/bottom_half.h

これらのルーチンはローカルCPUのソフトウェア割込みを無効にし、復元します。これらは再入可能で、ソフトウェア割込みが事前に無効になっていた場合でも、この関数ペアが呼ばれた後でも無効のままです。これらは現在のCPU上でソフトirqとタスクレットの実行を防ぎます。

smp_processor_id()¶

定義は include/linux/smp.h

get_cpu() プリエンプションを無効にし（他のCPUに突然移動されることを防ぎ）、現在のプロセッサ番号を0〜 NR_CPUSの間で返します。注意点として、プロセッサ番号は連続しない可能性があります。完了したら再び put_cpu() で返します。

他のタスクによってプリエンプションされないことを知っている場合（つまり割込みコンテキスト内かプリエンプションが無効になっている場合）、smp_processor_id()を使用できます。

__init/__exit/__initdata¶

定義は include/linux/init.h

起動後、カーネルは特別セクションを解放します。関数が __init でマークされ、データ構造が __initdata システム起動が完了した後、メモリが解放されます：同様に、モジュールは初期化後にこのメモリを破棄します。 __exit これは、ファイルがモジュールとしてコンパイルされない場合にのみ必要な関数を宣言するために使用されます：このファイルがモジュールとしてコンパイルされない場合、関数は破棄されます。ヘッダーファイルの使用方法を参照してください。注意として、この属性でマークされた関数が意味を持つことはありません。 __init モジュールにエクスポートされる必要があります EXPORT_SYMBOL() または EXPORT_SYMBOL_GPL()- これにより、システムが破損します。

__initcall()/module_init()¶

定義は include/linux/init.h / include/linux/module.h

カーネルの多くの部分は、モジュール（動的にロード可能なカーネルの部分）として十分に機能します。使用する module_init() および module_exit() マクロにより、#ifdefを使用せずに、モジュールとして動作するかカーネルに組み込まれるかに関わらず動作するコードを簡単に記述できます。

以下の module_init() マクロにより、モジュール挿入時（ファイルがモジュールとしてコンパイルされている場合）または起動時（ファイルがモジュールとしてコンパイルされていない場合）に呼び出す関数を定義します：ファイルがモジュールとしてコンパイルされていない場合、 module_init() マクロは __initcall()に等しくなり、リンカのマジックにより起動時に関数が呼び出されます。

関数は負のエラーナンバーを返してモジュールのロードを失敗させることができます（残念ながら、このモジュールがカーネルに組み込まれている場合、この機能は効果を持ちません）。この関数は割込みが有効なユーザーコンテキストで呼び出されるため、スリープすることが可能です。

module_exit()¶

定義は include/linux/module.h

このマクロにより、モジュールの除去時（またはカーネルに組み込まれたファイルの場合は決して呼ばれない）に呼び出す関数を定義します。モジュールの使用カウントがゼロに達した場合にのみ呼び出されます。この関数もスリープ可能ですただし、失敗は起こりません：関数が返るまでにすべてのクリーンアップが完了しなければなりません。

このマクロはオプションです：存在しない場合、モジュールは除去できません（'rmmod -f'を除く）。

try_module_get()/module_put()¶

定義は include/linux/module.h

これらはモジュールの使用カウントを操作し、除去を防ぐために使用されます（別のモジュールがエクスポートされたシンボルを使用している場合、モジュールは除去できません：以下を参照）。モジュールコードを呼び出す前に、 try_module_get() マクロを呼び出してください：失敗した場合、モジュールが除去されているため、存在しないかのように振る舞う必要があります。それ以外の場合、モジュールに安全にアクセスし、完了時に module_put() を呼び出してください。

ほとんどの登録可能な構造体には所有者フィールドがあります、例えば struct file_operations 構造体にあります。このフィールドを THIS_MODULE.

ウェイトキューは、特定の条件が真であるときに誰かが自分を起こすのを待つために使用されます。これらは競合状態を防ぐために慎重に使用する必要があります。あなたは wait_queue_head_tを宣言し、その条件を待つプロセスは自分自身を参照する wait_queue_entry_t を宣言し、それをキューに追加します。

ウェイトキューの宣言¶

あなたは wait_queue_head_t にキャストできるかどうかを確認する DECLARE_WAIT_QUEUE_HEAD() マクロを宣言するか、または初期化コード内で init_waitqueue_head() ルーチンを使用します。

キューへの登録¶

waitqueueに自身を登録する操作は比較的複雑です。これは、条件を確認する前にキューに自身を登録する必要があるためです。この操作を行うマクロは以下の通りです: wait_event_interruptible() (include/linux/wait.h) 第1引数はwait queueヘッドで、第2引数は評価される式です。この式が真である場合、またはシグナルが受信された場合、マクロは0を返します。 -ERESTARTSYS シグナルが受信された場合。The wait_event() バージョンはシグナルを無視します。

キューに待機中のタスクを起こす¶

を呼び出して、MMIOまたはIOポート範囲を利用可能にします。これを実施しないと、ドライバの再ロードができない状態になります。 wake_up() (include/linux/wait.h)、これはキュー内のすべてのプロセスを起こします。ただし、あるプロセスが設定されている場合、キューの残りの部分は起こされません。 TASK_EXCLUSIVE この基本的な関数の他の変種は、同じヘッダーにあります。

アトミック操作¶

特定の操作はすべてのプラットフォームでアトミックに保証されています。第1クラスの操作は atomic_t (include/asm/atomic.h)、これは符号付き整数（少なくとも32ビット長）を含み、これら関数を使用して操作または読み取りを行う必要があります。 atomic_t 変数。 atomic_read() および atomic_set() カウンタを取得および設定する atomic_add(), atomic_sub(), atomic_inc(), atomic_dec(), and atomic_dec_and_test() （カウンタがゼロに減算された場合にtrueを返します）。

はい。アトミック変数がゼロである場合、trueを返します（つまり、!= 0）。

これらの関数は通常の算術よりも遅いため、不要に使用すべきではありません。

第2クラスのアトミック操作は、ある unsigned longで初期化されます。定義されています include/linux/bitops.h。これらは一般的にビットパターンへのポインタとビット番号を取ります：0は最下位ビットです。 set_bit(), clear_bit() および change_bit() 指定されたビットを設定、クリア、および反転させます。 test_and_set_bit(), test_and_clear_bit() および test_and_change_bit() 同じ動作を行います。ただし、ビットが以前に設定されていた場合、trueを返します。これらは、アトミックにフラグを設定するのに特に有用です。

これらの操作は、ビットインデックスが...より大きい場合でも呼び出すことが可能です。 BITS_PER_LONGただし、ビッグエンディアンプラットフォームではこの結果の挙動が不思議なので、このような操作は行わないのが良いでしょう。

シンボル¶

カーネル本体では、通常のリンクルールが適用されます（つまり、シンボルがファイルスコープに宣言されていない限り、カーネルのどこでも使用可能です）。ただし、モジュールの場合、カーネル本体へのエントリポイントを制限する特別なエクスポートされたシンボルテーブルが保持されます。モジュールはまた、シンボルをエクスポートすることもできます。 static これはシンボルをエクスポートする古典的な方法です：動的にロードされるモジュールは、シンボルを通常通り使用できます。

EXPORT_SYMBOL()¶

定義は include/linux/export.h

これはシンボルをエクスポートする古典的な方法です：動的にロードされるモジュールは、シンボルを通常通り使用できます。

EXPORT_SYMBOL_GPL()¶

定義は include/linux/export.h

同様ですが EXPORT_SYMBOL() ただし、エクスポートされるシンボルは EXPORT_SYMBOL_GPL() のみ、特定のライセンスを指定したモジュールによってみることができる MODULE_LICENSE() GPL互換のライセンスを指定した場合、関数は内部実装の問題とみなされ、インターフェースとはみなされない。一部のメンテナや開発者は、新しいAPIや機能を追加する際にEXPORT_SYMBOL_GPL()を要求する場合があります

EXPORT_SYMBOL_NS()¶

定義は include/linux/export.h

これは EXPORT_SYMBOL() シンボルネームスペースを指定可能にする シンボルネームスペース

EXPORT_SYMBOL_NS_GPL()¶

定義は include/linux/export.h

これは シンボルネームスペースについては、 シンボルネームスペースを指定可能にする シンボルネームスペース

ルーチンとコンベンション¶

ダブルリンクリスト include/linux/list.h¶

かつてカーネルヘッダに存在していたリンクリストのルーチンは3セットありましたが、これは最強の選択肢です。単一のリストが必要な特別な理由がなければ、この選択肢は優れています。

特に list_for_each_entry() これは役立ちます。

戻り値の仕様¶

ユーザーコンテキストで呼ばれるコードでは、Cの規約を無視してよく0を成功として返し、負のエラー番号（例： -EFAULT)を失敗として返します。最初は直感的でないかもしれませんが、カーネルでは広く採用されています。

Using ERR_PTR() (include/linux/err.h)で負のエラー番号をポインタにエンコードし、 IS_ERR() および PTR_ERR() でそれを再取得する：エラー番号に別途ポインタパラメータを用意する必要がありません。不快ですが、良い意味でのものです。

コンパイルの破壊¶

リンスと他の開発者たちは開発カーネルで関数や構造体の名前を変更することがあります。これは単に皆を気を引き締めさせるためではなく、根本的な変更（例：割込みが有効な状態で呼ばれることはできず、追加のチェックを行う、または以前に検出されていたチェックを行わないなど）を反映しています。通常、これはlinux-kernelメーリングリストに詳細な説明を添えて投稿され、アーカイブを検索してください。ファイル全体を置き換えるだけでは問題が 悪化.

構造体メンバの初期化¶

構造体の初期化には、ISO C99で定義された指定初期化子を使用するのが望ましいです。例：

static struct block_device_operations opt_fops = {
        .open               = opt_open,
        .release            = opt_release,
        .ioctl              = opt_ioctl,
        .check_media_change = opt_media_change,
};

これにより、grepで検索しやすく、どの構造体フィールドが設定されているかが明確になります。これを実施するのは、見た目がカッコイイからです。

GNU拡張¶

GNU拡張はLinuxカーネル内で明示的に許可されています。一部の複雑な拡張は一般的な使用が少ないのでサポートが不十分ですが、以下のものは標準とされています（詳細はGCCのinfoページの「C拡張」セクションを参照 - はい、本当にinfoページです、manページはその内容の要約です）。

  • インライン関数

  • ステートメント式（つまり、({ と })構文）。

  • 関数／変数／型の属性（__attribute__）の宣言

  • typeof

  • ゼロ長さ配列

  • マクロ変数引数

  • voidポインタの算術演算

  • 非定数初期化子

  • アセンブリ命令（arch/ および include/asm/ の外側では使用不可）

  • 関数名を文字列として（__func__）。

  • __builtin_constant_p()

カーネル内でlong longを使用する際は注意が必要です。gccが生成するコードは悪質で、i386では割り算や乗算が動作しません（なぜなら、カーネル環境にGCCのランタイム関数が存在しないからです）。

C++¶

カーネルでC++を使用するのは通常悪い考えです。カーネルは必要なランタイム環境を提供せず、インクルードファイルもそのためにテストされていないからです。それでも可能ですが、推奨されません。本当にこれをやりたい場合は、少なくとも例外処理については無視してください。

#if¶

ヘッダーファイル（または.cファイルの先頭）でマクロを使用して関数を抽象化する方が、ソースコード全体に`#if`プリプロセッサステートメントを使用するよりも一般的に綺麗とされています。

カーネルにあなたのコードを配置する¶

公式の採用に向けたあなたのコードを整えるため、または丁寧なパッチを作成するためには、行政的な作業が必要です：

  • どの池に尿をかけているかを確認してください。ソースファイルの先頭、 MAINTAINERS ファイル内、そして最後に CREDITS ファイルを確認してください。この人物と連携し、労力を重複させたり、すでに却下された試みを繰り返さないよう確認してください。

    作成または大幅に変更したファイルの先頭にあなたの名前とEMailアドレスを記載してください。これはバグを見つけたとき、または 彼らが 変更を加えるときに最初に確認される場所です。

  • 通常、あなたのカーネルのハックに設定オプションを用意したいです。適切なディレクトリの Kconfig を編集してください。Config言語は切り貼りで簡単に使用でき、 Documentation/kbuild/kconfig-language.rst.

    に完全なドキュメンテーションがあります。オプションの説明では、専門家ユーザーとあなたの機能について何も知らないユーザーの両方を対象にし、不相容性や問題点をここで記載してください。 絶対に 説明の終わりには「疑問がある場合はN」と記載してください（または、まれに`Y`）。これは、あなたが何を話しているか分からない人々のために用意されています。

  • を編集してください。CONFIG変数はここでエクスポートされるため、通常は「obj-$(CONFIG_xxx) += xxx.o」の行を追加するだけで済みます。構文は Makefileにドキュメンテーションされています。 Documentation/kbuild/makefiles.rst.

  • を意識してください CREDITS 何か重要なことをした場合（単一ファイルを超える場合）、ソースファイルの先頭にあなたの名前が記載されているべきです。 MAINTAINERS これは、サブシステムの変更に相談を求めたり、バグについて知らされたりする意欲を示し、コードの一部に対するより深いコミットメントを意味します。

  • 最後に、以下のドキュメントを読むのを忘れないでください Documentation/process/submitting-patches.rst およびおそらく Documentation/process/submitting-drivers.rst.

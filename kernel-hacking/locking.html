レースコンディションとクリティカルリージョン¶

この重なり、結果が複数のタスクの相対的なタイミングに依存する状況はレースコンディションと呼ばれます。並行処理の問題を含むコードの部分はクリティカルリージョンと呼ばれます。特にLinuxがSMPマシンで動作し始めた後、これらはカーネル設計と実装における主要な問題の一つとなっています。

プリエンプションでも同様の効果が生じます。CPUが1台しかなければ、クリティカルリージョン中にタスクをプリエンプションすることで、同じレースコンディションが発生します。この場合、プリエンプションしたスレッドがクリティカルリージョン自体を実行する可能性があります。

解決策は、これらの同時アクセスが発生するタイミングを認識し、ロックを使用して一度に1つのインスタンスしかクリティカルリージョンに進入させないことです。Linuxカーネルにはこのようなロックの導入を支援する多くのフレンドリーなプリミティブがあります。そして、フレンドリーでないプリミティブもありますが、私はそれらの存在を無視します。

カーネルロックの2つの主なタイプ: スピンロックとミューテックス¶

カーネルロックの主な2つのタイプがあります。基本的なタイプはスピンロック（include/asm/spinlock.h）で、これは非常に単純な1つの保持者を持つロックです：スピンロックを取得できない場合は、常に試行し続ける（スピンする）まで待ちます。スピンロックは非常に小さく高速で、どこでも使用できます。

2番目のタイプはミューテックス（include/linux/mutex.h): これはスピンロックに似ていますが、ミューテックスを保持しながらブロックする可能性があります。ミューテックスをロックできない場合、タスクは自身を一時停止し、ミューテックスが解放されるまで待機します。これにより、待機している間にもCPUは他の処理を行えるようになります。あなたが待機している間にスリープできないケースは多くあります（参照 割込みから安全に呼び出せる関数はどれ？）、そのためスピンロックを使用する必要があります。

どちらのロックも再入可能ではありません：参照 デッドロック: 簡単で高度な.

タスクレット/タイマ間のロック¶

たまにタスクレットまたはタイマが別のタスクレットまたはタイマとデータを共有したい場合があります。

同じタスクレット/タイマ¶

タスクレットは一度に2つのCPUで実行されることはないため、SMPでもタスクレットが再入可能（同時に2回実行される）になる心配は必要ありません。

異なるタスクレット/タイマ¶

別のタスクレット/タイマがあなたのタスクレットまたはタイマとデータを共有したい場合、双方がspin_lock()とspin_unlock()を呼び出す必要があります。spin_lock_bh()は必要ありません。なぜなら、すでにタスクレット内にあり、同じCPU上で他のタスクレットが実行されることはないからです。

ソフトIRQ間のロック¶

しばしばソフトIRQは自身またはタスクレット/タイマとデータを共有したい場合があります。

同じソフトIRQ¶

同じソフトIRQは他のCPUでも実行できます。パーセルCPU配列（参照 パーセルCPUデータ）でより高いパフォーマンスを実現できます。ソフトIRQを使用するほど進んでいるなら、スケーラブルなパフォーマンスを重視するため、追加の複雑さを正当化するほどです。

共有データにはspin_lock()とspin_unlock()を使用する必要があります。

異なるソフトIRQ¶

共有データにはspin_lock()とspin_unlock()を使用する必要があります。それがタイマ、タスクレット、異なるソフトIRQ、同じか別のソフトIRQであっても、どれもが別のCPUで実行されている可能性があるためです。

ハードIRQコンテキスト¶

ハードウェア割込みは通常、タスクレットまたはソフトIRQと通信します。これは、作業をキューに格納する頻繁な作業で、ソフトIRQがそれを取り出します。

ハードIRQとソフトIRQ/タスクレット間のロック¶

ハードウェアIRQハンドラがソフトIRQとデータを共有する場合、2つの懸念があります。まず、ソフトIRQの処理はハードウェア割込みによって中断される可能性があり、次に、別のCPUのハードウェア割込みがクリティカルな領域に進入する可能性があります。これはspin_lock_irq()が使用される場面です。これは、そのCPUの割込みを無効にしてからロックを取得するように定義されています。spin_unlock_irq()はこれを逆を行います。

IRQハンドラはspin_lock_irq()を使用する必要がありません。なぜなら、softirqはIRQハンドラが実行されている間は実行されないからです。代わりにspin_lock()を使用できます。これはやや高速です。ただし、別のハードウェアIRQハンドラが同じロックを使用している場合を除いては、spin_lock_irq()はそのハンドラが私たちを妨害しないようにします。

これはUPでも完全に機能します。スピンロックは消失し、このマクロは単にlocal_irq_disable()（include/asm/smp.h）になります。これによりsoftirq/tasklet/BHが実行されることを防ぎます。

spin_lock_irqsave（include/linux/spinlock.h）は、割り込みが有効か無効かをフラグワードに保存する変体です。これはspin_unlock_irqrestore()に渡されます。これにより、同じコードをハードウェアIRQハンドラ（割り込みがすでに無効になっている状態）とsoftirq（割り込み無効が必要な状態）の両方で使用できます。

注意してください。softirq（およびタスクレットとタイマも含む）はハードウェア割り込みからの戻り時に実行されるため、spin_lock_irq()もこれらを停止します。この意味では、spin_lock_irqsave()が最も一般的で強力なロック関数です。

2つのハードIRQハンドラ間でのロック¶

2つのIRQハンドラ間でデータを共有する必要は滅多にありませんが、必要であればspin_lock_irqsave()を使用すべきです。IRQハンドラ自体内ですべての割り込みを無効にするかどうかはアーキテクチャに依存します。

trylock関数¶

ロックを一度だけ取得しようと試み、その結果を成功または失敗として即座に値で返す関数があります。他のスレッドがロックを保持している間でもデータにアクセスする必要がない場合に使用できます。その後データにアクセスが必要な場合は、後でロックを取得する必要があります。

spin_trylock()はスピンせずに、最初の試行でスピンロックを取得できた場合は非ゼロ値を、取得できなかった場合はゼロを返します。この関数はspin_lock()と同様にすべてのコンテキストで使用できますが、中断する可能性のあるコンテキストを無効にしてからスピンロックを取得する必要があります。

mutex_trylock() タスクの待機をせず、最初の試行でミューテックスを取得できた場合は非ゼロ値を、取得できなかった場合はゼロを返します。ハードウェアまたはソフトウェア割込みコンテキストでは安全に使用できません（待機しないにもかかわらず）。

一般的な例¶

簡単な例をステップごとに見てみましょう：数値から名前のマッピングを保持するキャッシュ。このキャッシュは各オブジェクトの使用頻度をカウントし、満杯になると最も使用頻度の低いオブジェクトを削除します。

すべてユーザーコンテキスト内¶

最初の例ではすべての操作がユーザーコンテキスト（つまりシステムコールから）で行われると仮定します（つまり待機が可能）。これにより、キャッシュとその内のすべてのオブジェクトを保護するミューテックスを使用できます。以下がコードです：

#include <linux/list.h>
#include <linux/slab.h>
#include <linux/string.h>
#include <linux/mutex.h>
#include <asm/errno.h>

struct object
{
        struct list_head list;
        int id;
        char name[32];
        int popularity;
};

/* Protects the cache, cache_num, and the objects within it */
static DEFINE_MUTEX(cache_lock);
static LIST_HEAD(cache);
static unsigned int cache_num = 0;
#define MAX_CACHE_SIZE 10

/* Must be holding cache_lock */
static struct object *__cache_find(int id)
{
        struct object *i;

        list_for_each_entry(i, &cache, list)
                if (i->id == id) {
                        i->popularity++;
                        return i;
                }
        return NULL;
}

/* Must be holding cache_lock */
static void __cache_delete(struct object *obj)
{
        BUG_ON(!obj);
        list_del(&obj->list);
        kfree(obj);
        cache_num--;
}

/* Must be holding cache_lock */
static void __cache_add(struct object *obj)
{
        list_add(&obj->list, &cache);
        if (++cache_num > MAX_CACHE_SIZE) {
                struct object *i, *outcast = NULL;
                list_for_each_entry(i, &cache, list) {
                        if (!outcast || i->popularity < outcast->popularity)
                                outcast = i;
                }
                __cache_delete(outcast);
        }
}

int cache_add(int id, const char *name)
{
        struct object *obj;

        if ((obj = kmalloc(sizeof(*obj), GFP_KERNEL)) == NULL)
                return -ENOMEM;

        strscpy(obj->name, name, sizeof(obj->name));
        obj->id = id;
        obj->popularity = 0;

        mutex_lock(&cache_lock);
        __cache_add(obj);
        mutex_unlock(&cache_lock);
        return 0;
}

void cache_delete(int id)
{
        mutex_lock(&cache_lock);
        __cache_delete(__cache_find(id));
        mutex_unlock(&cache_lock);
}

int cache_find(int id, char *name)
{
        struct object *obj;
        int ret = -ENOENT;

        mutex_lock(&cache_lock);
        obj = __cache_find(id);
        if (obj) {
                ret = 0;
                strcpy(name, obj->name);
        }
        mutex_unlock(&cache_lock);
        return ret;
}

追加、削除、またはキャッシュの検索を行う際には常にキャッシュ_lockを取得していることを確認しています。キャッシュインフラストラクチャ自体とオブジェクトの内容もロックで保護されています。この場合、ユーザーにデータをコピーして直接オブジェクトにアクセスさせないため、簡単に実装できます。

キャッシュ_add()ではロックを取得する前にオブジェクトのフィールドを設定するという軽量な最適化があります。これは、ロックを取得する前にオブジェクトをキャッシュに追加するため、誰もアクセスできないため安全です。

このファイルの外にオブジェクトを公開する¶

もしオブジェクトに含まれる情報がより多くなれば、情報をコピーするだけでは不十分になる可能性がある: 他のコードの一部がこれらのオブジェクトへのポインタを保持したい場合があり、毎回idを検索するのではなく。これにより2つの問題が生じる。

最初の問題は、我々が cache_lock オブジェクトを保護するために使用している: 他のコードが使用できるようにするには、これを静的でないものにしなければならない。これにより、ロックの管理が複雑になる。ロックがすべて1ヶ所に集中しているため、

2番目の問題は寿命の問題である: 他の構造体がオブジェクトへのポインタを保持している場合、そのポインタが有効であることを期待している。しかし、これはロックを保持している間だけ保証される。ロックを解放した後、誰かがcache_delete()を呼び出したり、さらに悪いことに同じアドレスを再利用して別のオブジェクトを追加したりする可能性がある。

オブジェクト自体の保護¶

これらの例では、オブジェクト（参照カウントを除く）が作成後で変更されることはないものと仮定しています。もし名前を変更できるようにしたい場合、以下の3つの可能性があります:

  • You can make cache_lock 静的でないため、オブジェクトの名前を変更する前にそのロックを取得してほしい。

  • callerに名前を変更するためのロックを取得し、名前を変更するcache_obj_rename()関数を提供し、誰もがその関数を使用するように伝えることができます。

  • キャッシュを cache_lock キャッシュ自体のみを保護し、名前を保護するための別のロックを使用してください。

一般的な問題¶

デッドロック: 簡単で高度な¶

コードがスピンロックを2回取得しようとするバグがあります。これにより、ロックが解放されるのを待つため、永遠にスピンします（Linuxではスピンロック、rwロック、ミューテックスは再入不可です）。これは簡単に診断できます：5晩徹夜してフワフワしたコードのうさぎと話すような問題ではありません。

やや複雑なケースを想像してください。ソフトIRQとユーザーコンテキストが共有する領域があり、spin_lock()呼び出しで保護する場合、ユーザーコンテキストがロックを保持している間にソフトIRQが割り込み、ソフトIRQが同じロックを取得しようと永遠にスピンする可能性があります。

これらはどちらもデッドロックと呼ばれます。上記のように、単一のCPUでも発生することがあります（ただし、UPコンパイルではスピンロックがカーネルコンパイルで消失するため、発生しません）。 CONFIG_SMP=n。2番目の例ではデータ腐敗が発生します。

この完全なロックアップは簡単に診断できます: SMPマシンではウォッチドッグタイマーやコンパイル時に DEBUG_SPINLOCK set (include/linux/spinlock.h) が発生したときにすぐにこの現象を示します。

より複雑な問題は「デッドリーエンブレース」と呼ばれるものです。これは2つ以上のロックを関与する問題で、ハッシュテーブルがあるとします。テーブルの各エントリがスピンロックで、ハッシュされたオブジェクトのチェーンがあります。ソフトIRQハンドラ内で、ハッシュ内の1か所から別の場所にオブジェクトを変更したい場合があります。このとき、古いハッシュチェーンのスピンロックと新しいハッシュチェーンのスピンロックを取得し、古いチェーンからオブジェクトを削除して新しいチェーンに挿入します。

ここには2つの問題があります。まず、コードがオブジェクトを同じチェーンに移動しようとした場合、自身のロックを2回取得しようとしてデッドロックします。次に、別のCPUで同じソフトIRQが逆方向にオブジェクトを移動しようとしている場合、以下のことが起こり得ます:

2つのCPUは永遠にスピンし続け、相手のロックを放棄するのを待つことになります。これはクラッシュのように見え、匂い、感じられます。

デッドロックの防止¶

教科書はロックの順序を常に統一すればこのようなデッドロックを防げると教えます。しかし実際にはこのアプローチはスケーラビリティが低く、新しいロックを追加する際、カーネルの理解が不十分で5000個のロック階層のどこに配置されるか分からないため、実用性がありません。

最良のロックはカプセル化されており、ヘッダーに露出せず、同じファイル外の非自明な関数呼び出しの間に保持されません。このコードを読むと、他のロックを取得しながらこのロックを保持しないので決してデッドロックしないことが分かります。あなたのコードを使う人々はロックを使っていることすら知らなくても良いです。

ここでの典型的な問題はコールバックやハックを提供することです。ロックを保持しながらこれらの関数を呼び出すと、単純なデッドロックやデッドリーエンブレース（コールバックが何をするか分からない）のリスクがあります。他のプログラマが狙っているのを忘れないで、このようなことはしないでください。

過剰なデッドロック防止¶

デッドロックは問題ですが、データ腐敗ほど深刻ではありません。読み込みロックを取得し、リストを検索して目的のオブジェクトが見つからなかった場合、読み込みロックを解放して書き込みロックを取得してオブジェクトを挿入するコードはレースコンディションがあります。

なぜか理解できないなら、私のコードから遠ざけてくれ。

タイマーレース: カーネルの趣味¶

タイマーはレース条件を引き起こす独自の問題を生じることがあります。リスト、ハッシュなど、各オブジェクトが自身を破壊する予定のタイマーを持つコレクションを考慮してください。

モジュールの削除など、コレクション全体を破壊したい場合、以下の手順を取るかもしれません：

/* THIS CODE BAD BAD BAD BAD: IF IT WAS ANY WORSE IT WOULD USE
   HUNGARIAN NOTATION */
spin_lock_bh(&list_lock);

while (list) {
        struct foo *next = list->next;
        del_timer(&list->timer);
        kfree(list);
        list = next;
}

spin_unlock_bh(&list_lock);

SMP（対称マルチプロセッサ）ではいつかクラッシュします。タイマーがspin_lock_bh()の前に起動してしまい、spin_unlock_bh()後にロックを取得した後、すでに破壊された要素を解放しようとするからです。

これを回避するには、以下の結果を確認する必要があります。 del_timer()返り値が1であればタイマーは削除済みです。0であれば（この場合）タイマーが現在実行中であることを意味し、以下のように処理できます：

retry:
        spin_lock_bh(&list_lock);

        while (list) {
                struct foo *next = list->next;
                if (!del_timer(&list->timer)) {
                        /* Give timer a chance to delete this */
                        spin_unlock_bh(&list_lock);
                        goto retry;
                }
                kfree(list);
                list = next;
        }

        spin_unlock_bh(&list_lock);

もう一つの一般的な問題は、タイマー関数の終わりで自分自身を再起動するタイマーを削除することです（callする）。このケースはレース条件に陥りやすく、頻繁に発生するため、 add_timer() del_timer_sync()を使用すべきです。これはタイマーが自分自身を再び追加するのを止められるまで、タイマーを削除する回数を返します。 del_timer_sync() (include/linux/timer.h)を用いることでこのケースを処理できます。これはタイマーが自分自身を再び追加するのを止められるまで、タイマーを削除する回数を返します。

ロックの速度¶

ロックの使用に関するコードの速度を考慮する際、主に3つの点に注意する必要があります。1つ目はコンカレンシー（複数のプロセスがロックを保持している間、待機するプロセスの数）。2つ目は、競合が起きないロックの取得と解放にかかる時間。3つ目は、より少ない数のロックや賢いロックの使用です。私はロックが頻繁に使用されるものと仮定しています。そうでなければ、効率を気にする必要はありません。

コンカレンシーはロックを保持する時間に依存します。必要なだけ保持し、それ以上は保持しないようにしてください。キャッシュの例では、ロックを保持せずにオブジェクトを作成し、リストに挿入する準備ができたらロックを取得します。

取得時間は、ロック操作がパイプラインに与える影響（パイプラインストール）や、このCPUが最後にロックを取得した可能性（つまり、このCPUにとってロックがキャッシュヒットしているか）に依存します。CPUが多ければ多いほど、この可能性は急速に低下します。700MHzのIntel Pentium IIIでは、1命令は約0.7ナノ秒、アトミックインクリメントは約58ナノ秒、このCPUでキャッシュヒットしているロックは160ナノ秒、他のCPUからキャッシュラインを取得するにはさらに170〜360ナノ秒かかります。（これらの数値はPaul McKenneyの Linux Journal RCU記事から抜粋).

これらの2つの目標は衝突しています: ロックを短時間保持するには、ロックを部分に分けて（例えば最終的なオブジェクトごとのロックの例のように）実現できますが、これによりロック取得の回数が増加し、結果として単一のロックを使用するよりもしばしば遅くなります。これはもう一つのロックの簡潔さを推奨する理由です。

3番目の懸念については以下で説明します: 一部の方法で行うロックの量を減らすことが可能です。

読み込み/書き込みロックの変種¶

スピンロックとミューテックスの両方には読み込み/書き込み用の変種があります: rwlock_t および struct rw_semaphoreこれらはユーザーを読者とライターの2つのクラスに分けることで、データを読み込むだけであれば読み込みロックを取得できますが、データを書き込むには書き込みロックが必要です。多くのユーザーが読み込みロックを保持できますが、ライターは唯一の保持者でなければなりません。

コードが読者/ライターの線で明確に分かれている場合（例えばキャッシュコードのように）かつロックが読者によって長時間保持されている場合、これらのロックを使用することで効果が得られます。ただし、通常のロックに比べてやや遅いため、実際には rwlock_t 通常は得がありません。

ロックを避ける: レッドコピー更新¶

読み込み/書き込みロックの特別な方法として「レッドコピー更新（RCU）」があります。RCUを使用することで、読者はロックをまったく取得することなく動作できます: キャッシュが更新よりも読み込みされることが期待されるため（そうでなければキャッシュは時間の無駄です）、この最適化の候補になります。

読み込みロックをどのように排除するのでしょうか？読み込みロックを排除することで、ライターは読者以下のリストを変更できるようになります。これは実際には非常に簡単です: 書き手が要素を慎重に追加する場合、読者がリンクされたリストを読み込むことができます。例えば、 new を単一のリンクされたリスト list:

new->next = list->next;
wmb();
list->next = new;

に追加する場合、wmb()は書き込みメモリバリアです。これは、新しい要素の next ポインタを設定する最初の操作が完了し、すべてのCPUに見えること、その後の操作（新しい要素をリストに追加する）が行われる前に保証します。これは重要です、なぜなら現代のコンパイラと現代のCPUは、指示を再配置する場合がありますが、それ以外の指示は再配置されません: 読み込み者が新しい要素をまったく見ないか、またはリストの残り部分を正しく指す next ポインタとともに見るようにしたいからです。

幸いなことに、標準の struct list_head リストに対してこの処理を行う関数があります: list_add_rcu() (include/linux/list.h).

リストから要素を削除するのはさらに簡単です: 旧要素へのポインタをその次の要素へのポインタに置き換え、読者はそれを見たり、スキップしたりします。

list->next = old->next;

あります list_del_rcu() (include/linux/list.h) はこの処理を行います（通常のバージョンは古いオブジェクトを毒として処理しますが、これは望んでいません）。

読者も注意が必要です: 一部のCPUは next 次の要素の内容を早期に読み始めるポインタですが、ポインタが下にある要素の内容が間違っていることに気づかない。再び、ある next ポインタが変更されると、リーダーはゴミ領域にジャンプしてクラッシュします。我々は、この要素を削除したときにリストを走査していたすべてのリーダーが完了するのを待つ必要があります。我々は list_for_each_entry_rcu() (include/linux/list.h）でご支援いたします。もちろん、ライターは単に list_for_each_entry()、同時に2つのライターが存在できないためです。

最終的な問題は、実際に削除された要素をいつ破壊できるかということです。思い出してください、現在リスト内でこの要素を走査しているリーダーがいるかもしれません：もしこの要素を解放し、 next ポインタが変更されると、リーダーはゴミ領域にジャンプしてクラッシュします。我々は、この要素を削除したときにリストを走査していたすべてのリーダーが完了するのを待つ必要があります。我々は call_rcu() すべての既存のリーダーが完了したときに実際にオブジェクトを破壊するコールバックを登録します。代替案として、 synchronize_rcu() を用いて、すべての既存のリーダーが完了するのをブロックするのも可能です。

では、Read Copy Updateはリーダーが完了したタイミングをどのように知るのでしょうか？その方法は以下の通りです：まず、リーダーは常にリストを rcu_read_lock()/rcu_read_unlock() ペア：これらは単にプリエンプションを無効化し、リーダーがリストを読みながら眠らないようにします。

RCUは、他のすべてのCPUが少なくとも一度は眠ったのを待つ：リーダーは眠ることができないため、削除中にリストを走査していたすべてのリーダーが完了したとわかることになります。コールバックがトリガーされます。実際のRead Copy Updateコードはこれより少し最適化されていますが、これは基本的なアイデアです。

パーセルCPUデータ¶

ロックを回避するためのもう一つの技術として、各CPUごとに情報を複製する方法があり、これは広く利用されています。たとえば、共通な状態のカウントを維持したい場合、スピンロックと単一のカウンターを使用する方法がシンプルで効率的です。

その方法が遅すぎる場合（通常はそうではありませんが、非常に大きなマシンでテストし、それが実際に起きていたと示せる場合）、代わりに各CPUごとにカウンターを使用することで、どのCPUも排他ロックを必要としなくなります。詳しくはDEFINE_PER_CPU()、get_cpu_var()、put_cpu_var()を参照してください（include/linux/percpu.h).

シンプルなper-CPUカウンタには特に有用な local_t 型、およびcpu_local_inc()などの関連する関数があり、一部のアーキテクチャではシンプルなコードより効率的です（include/asm/local.h).

このようなカウンターの正確な値を取得するためには、より多くのロックを導入することなく簡単で信頼性の高い方法は存在しません。これは一部の用途では問題ではありません。

IRQハンドラで主に使用されるデータ¶

データが常に同じIRQハンドラ内でアクセスされる場合、ロックは一切必要ありません。カーネルはIRQハンドラが複数のCPUで同時に実行されないことを保証しています。

Manfred Spraulは、データがユーザコンテキストやsoftirqs/taskletsで非常にまれにアクセスされる場合でも、この方法は依然として有効であると指摘しています。IRQハンドラはロックを使用せず、他のアクセスは以下の通り行われます：

spin_lock(&lock);
disable_irq(irq);
...
enable_irq(irq);
spin_unlock(&lock);

以下の disable_irq() IRQハンドラの実行を防ぎ（他のCPUで実行中であれば終了を待つ）、スピンロックは同時に他のアクセスを防ぎます。これは単なるspin_lock_irq()呼び出しより遅いため、この種のアクセスが極めてまれにしか起きていない場合にのみ意味があります。

割込みから安全に呼び出せる関数はどれ？¶

カーネル内の多くの関数はスリープします（つまりschedule()を直接または間接的に呼び出します）。スピンロックを保持している間やプリエンプションが無効になっている状態では、これらを呼び出すことはできません。また、これらを呼び出すにはユーザコンテキストでなければならないため、割り込みから呼び出すことは違法です。

スリープする関数¶

最も一般的な関数は以下に示されていますが、他の呼び出しも安全かどうかはコードを読む必要があります。他のすべての呼び出しでスリープが可能であれば、あなたもスリープが可能である必要があります。特に、登録および解除関数は通常ユーザコンテキストから呼び出され、スリープ可能です。

  • ユーザースペースへのアクセス：

    • copy_from_user()

    • copy_to_user()

    • get_user()

    • put_user()

  • kmalloc(GP_KERNEL) <kmalloc>`

  • mutex_lock_interruptible() および mutex_lock()

    There is a mutex_trylock() 睡眠しない。それでも、割り込みコンテキスト内での使用は安全でないため、使用を避けてください。 mutex_unlock() 睡眠することもありません。割り込みコンテキストでの使用もできません。ミュートックスは取得したタスクによってのみ解放しなければなりません。

睡眠しない関数の一覧¶

ほぼすべてのロックを保持している状態でも安全に呼び出せる関数もあります。

  • printk()

  • kfree()

  • add_timer() および del_timer()

用語集¶

プリエミュプション

2.5以前、または CONFIG_PREEMPT が未設定の場合、ユーザー コンテキスト内でカーネル内にいるプロセスはお互いにプリエミュプションを行いません（つまり、CPUを手放すまで占有し、割り込みを除く）。2.5.4で CONFIG_PREEMPT が追加され、この挙動が変更されました：ユーザー コンテキスト内では、優先度が高いタスクが「割り込む」ことができます。スピンロックはUPでもプリエミュプションを無効にするようになりました。

bh

ボトムハーフ：歴史的経緯により、'bh'を含む関数は現在、ソフトウェア割り込みを指すことが多く、例えばspin_lock_bh()は現在のCPUで任意のソフトウェア割り込みをブロックします。ボトムハーフは非推奨となり、最終的にはタスクレットで置き換えられます。同時に1つのボトムハーフのみが実行されます。

ハードウェア割り込み / ハードウェアIRQ

ハードウェア割り込みリクエスト。in_irq()はハードウェア割り込みハンドラ内ではtrueを返します。

割り込みコンテキスト

ユーザー コンテキストではありません：ハードウェアIRQまたはソフトウェアIRQの処理中です。in_interrupt()マクロがtrueを返します。

SMP

対称マルチプロセッサ：複数CPUマシン用にコンパイルされたカーネル。（CONFIG_SMP=y).

ソフトウェア割り込み / ソフティーリクエスト

ソフトウェア割り込みハンドラ。in_irq()はfalseを返し、in_softirq()はtrueを返します。タスクレットとソフトウェア割り込みはどちらも「ソフトウェア割り込み」のカテゴリに属します。

厳密には、ソフトウェア割り込みとは、複数のCPUで同時に実行可能な最大32のソフトウェア割り込みのうちの1つです。有時、タスクレット全体を指す場合もあります（つまりすべてのソフトウェア割り込みを指します）。

tasklet

動的に登録可能なソフトウェア割込みで、一度に1つのCPUのみで実行されることが保証されています。

タイマ

指定された時間（またはそれに近い時間）に実行される動的に登録可能なソフトウェア割込みです。実行中はtaskletとほぼ同じ挙動を示します（実際にはtaskletから呼び出されます）。 TIMER_SOFTIRQ).

UP

ユニプロセッサ: SMPでない。（CONFIG_SMP=n).

ユーザーコンテキスト

特定のプロセス（システムコールやトラップなど）やカーネルスレッドの代行として実行されるカーネルです。実行中のプロセスは「マクロ」で確認できます。 current ユーザースペースとは混同しないでください。ソフトウェアまたはハードウェア割込みによって中断されることがあります。

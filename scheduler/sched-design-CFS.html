CFSスケジューラ¶

1. 概要¶

CFS は「完全な公平スケジューラ（Completely Fair Scheduler）」の略で、インゴ・モルナールによって実装され、Linux 2.6.23 にマージされた新しい「デスクトップ」プロセススケジューラです。これは、以前の vanilla スケジューラの SCHED_OTHER に関するインタラクティブコードの置き換えです。

CFS の設計の 80% は単一の文でまとめられます：CFS は、現実のハードウェア上で「理想的で正確なマルチタスクCPU」をモデル化しています。

「理想的なマルチタスクCPU」は（存在しない :-))、100% の物理的なパワーや、各タスクを正確に均等な速度で並列実行できるCPUです。たとえば、2つのタスクが実行されている場合、それぞれが50%の物理的なパワーや、実際に並列で実行されます。

現実のハードウェアでは一度に1つのタスクしか実行できませんので、「仮想実行時間（virtual runtime）」という概念を導入します。タスクの仮想実行時間は、上記の理想的なマルチタスクCPU上で次のタイムスライスが開始されるタイミングを指定します。実際には、タスクの仮想実行時間は、実際の実行時間を実行中のタスクの総数で正規化したものです。

2. 実装の詳細な情報¶

CFSでは、仮想実行時間はタスクごとのp->se.vruntime（ナノ秒単位）値を通じて表現され、追跡されます。この方法により、「期待されるCPU時間」を正確にタイムスタンプを刻み、測定することが可能です。

[補足：理想的なハードウェアでは、常にすべてのタスクが同じp->se.vruntime値を持ち、

タスクが同時に実行され、どのタスクもCPU時間の「理想的な配分」からバランスを崩すことは決してありません。]

CFSのタスク選択ロジックはこのp->se.vruntime値に基づいており、非常に単純です：常に最小のp->se.vruntime値を持つタスク（つまりこれまでに実行時間が最も少ないタスク）を実行しようとします。CFSは、実行可能なタスク間でCPU時間を「理想的なマルチタスクハードウェア」に近づけるように分割しようとします。

CFSの設計の大部分はこの非常に単純な概念から導き出され、niceレベルやマルチプロセッシング、さまざまなアルゴリズムの変種といった追加機能で補完されています。これらはスリープ中のタスクを認識するためのものです。

3. レッドブラックツリー¶

CFSの設計は非常に革新しており、実行キュー用の古いデータ構造を使わず、時間順に並べたレッドブラックツリーを用いて将来のタスク実行の「タイムライン」を構築します。これにより、配列スイッチのアーティファクト（以前のバニラスケジューラーおよびRSDL/SDにも影響を与えるもの）がありません。

CFSは、rq->cfs.min_vruntime値も保持しており、これは実行待ちキュー内のすべてのタスクの中で最小のvruntimeを単調に増加する値として追跡します。システムが実行した作業の総量はmin_vruntimeによって追跡され、この値は新たにアクティブ化されたエンティティを木の左側にできるだけ配置するために使用されます。

実行待ちキュー内の実行中のタスクの総数は、rq->cfs.load値を通じて記録されます。これは実行待ちキューにキューイングされているタスクの重みの合計です。

CFSは時間順に並べられた赤黒木を維持しており、すべての実行可能なタスクはp->se.vruntimeキーによってソートされます。CFSはこの木から「左端」のタスクを選び、それにこだわります。システムが進むにつれて、実行されたタスクは徐々に木の右側に配置されるため、すべてのタスクが「左端のタスク」となる機会が与えられ、決定的な時間内にCPUに実行されるようになります。

まとめると、CFSはタスクを少し実行し、タスクがスケジューリングされる（またはスケジューラのティックが発生する）と、そのCPU使用量が「記録される」ことで、タスクが物理CPUを実際に使用した時間（小さな時間）がp->se.vruntimeに加算されます。p->se.vruntimeが十分に高くなり、時間順に並べられた赤黒木で他のタスクが「左端のタスク」になるようになる（左端のタスクに対する小さな「粒度」距離を加えて過剰にスケジューリングを防ぎ、キャッシュを破壊しないようにする）と、新しい左端のタスクが選ばれ、現在のタスクがプリエンプションされます。

4. CFSの特徴¶

CFSはナノ秒単位のアカウント管理を使用し、ジーフィーズや他のHZの詳細に依存しません。したがって、CFSスケジューラは以前のスケジューラが持っていた「タイムスライス」の概念を持ちませんし、まったくのヒューリスティクスもありません。唯一の中心的な調整可能なパラメータ（CONFIG_SCHED_DEBUGを有効にする必要があります）は、

/proc/sys/kernel/sched_min_granularity_ns

で、スケジューラを「デスクトップ」（つまり、低遅延）から「サーバー」（つまり、良いバッチ処理）のワークロードに調整できます。デフォルトではデスクトップワークロードに適した設定になっています。SCHED_BATCHはCFSスケジューラモジュールでも処理されます。

設計上、CFSスケジューラは現在のストックスケジューラのヒューリスティクスに対する「攻撃」に対して脆弱ではありません。fiftyp.c、thud.c、chew.c、ring-test.c、massive_intr.cなどすべてのファイルは正常に動作し、インタラクティブ性に影響を与えず、予期される動作をします。

CFSスケジューラは、以前のvanillaスケジューラよりもniceレベルやSCHED_BATCHの処理が大幅に強化されており、両方のワークロードがより積極的に隔離される。

SMPロードバランシングは再設計・整理されており、ロードバランシングコードにはrunqueue-walkingの仮定がなくなった。スケジューリングモジュールのイテレータが使用され、バランスコードは大幅に簡潔になった。

5. スケジューリングポリシー¶

CFSは3つのスケジューリングポリシーを実装している:

  • SCHED_NORMAL (従来はSCHED_OTHERと呼ばれていた): 通常のタスクに使用されるスケジューリングポリシー。

  • SCHED_BATCH: 通常タスクほど頻繁にプリエンプションを起こさないため、タスクがより長く実行されキャッシュの利用効率が向上するが、インタラクティブ性を犠牲にする。これはバッチジョブに非常に適している。

  • SCHED_IDLE: nice 19よりもさらに弱いが、優先度逆転問題によるデッドロックを避けるため、真のアイドルタイマースケジューラではない。

SCHED_FIFO/_RRはsched/rt.cで実装されており、POSIX仕様に準拠している。

util-linux-ng 2.13.1.1のchrtコマンドは、SCHED_IDLEを除いてすべてのポリシーを設定できる。

6. スケジューリングクラス¶

新しいCFSスケジューラは、拡張可能なスケジューリングモジュールの階層構造である「スケジューリングクラス」を導入するように設計されている。これらのモジュールはスケジューリングポリシーの詳細をカプセル化しており、コアコードはそれらについてあまり仮定をしないで処理する。

sched/fair.cは上記のCFSスケジューラを実装している。

sched/rt.cはSCHED_FIFOとSCHED_RRのセマンティクスを、以前のvanillaスケジューラよりシンプルな方法で実装している。100のランキュー（すべての100のRT優先度レベルに対応）を使用し、以前のスケジューラの140に代わっており、expired配列は必要ない。

スケジューリングクラスはsched_class構造体を通じて実装されており、興味深いイベントが発生するたびに呼び出す必要のある関数のハンドラを含んでいる。

これは（一部を除く）ハンドラの一覧:

  • enqueue_task(…)

    タスクが実行可能状態に移るときに呼ばれる。スケジューリングエンティティ（タスク）を赤黒木に挿入し、nr_running変数をインクリメントする。

  • dequeue_task(…)

    タスクが実行不可能になったときに呼ばれる。対応するスケジューリングエンティティを赤黒木から削除し、nr_running変数をデクリメントする。

  • yield_task(…)

    この関数は基本的にdequeueの後にenqueueを行うだけだが、compat_yield sysctlが有効になっている場合は、赤黒木の右端にスケジューリングエンティティを配置する。

  • check_preempt_curr(…)

    この関数は、実行可能状態に入ったタスクが現在実行中のタスクを優先実行すべきかどうかを確認します。

  • pick_next_task(…)

    この関数は、次の実行に適したタスクを選びます。

  • set_curr_task(…)

    タスクがスケジューリングクラスを変更するか、タスクグループを変更するときにこの関数が呼ばれます。

  • task_tick(…)

    この関数は主にタイマーティック関数から呼び出されます。プロセスの切り替えを引き起こす可能性があります。これは実行中のタスクの優先実行を促進します。

7. CFSへのグループスケジューラ拡張¶

通常、スケジューラは個々のタスクを対象とし、各タスクに公平なCPU時間を提供しようとします。時には、タスクをグループ化し、各グループに公平なCPU時間を提供することが望まれることがあります。たとえば、システム内の各ユーザーに公平なCPU時間を提供した後、各ユーザーに属するタスクに公平なCPU時間を提供することが望まれることがあります。

CONFIG_CGROUP_SCHEDはまさにその目的を達成しようとします。タスクをグループ化し、そのようなグループ間でCPU時間を公平に分配します。

CONFIG_RT_GROUP_SCHEDは、リアルタイム（つまり、SCHED_FIFOおよびSCHED_RR）タスクをグループ化することを許可します。

CONFIG_FAIR_GROUP_SCHEDは、CFS（つまり、SCHED_NORMALおよびSCHED_BATCH）タスクをグループ化することを許可します。

これらのオプションはCONFIG_CGROUPSが定義されている必要があります。管理者は、「cgroup」擬似ファイルシステムを使用して、任意のタスクグループを作成できます。詳しくは、 制御グループ（Control Groups） この擬似ファイルシステムについての詳細情報はこちらをご覧ください。

CONFIG_FAIR_GROUP_SCHEDが定義されている場合、擬似ファイルシステムを使用して作成された各グループに対して「cpu.shares」ファイルが作成されます。以下の例の手順を参照して、「cgroups」擬似ファイルシステムを使用してタスクグループを作成し、そのCPUシェアを変更してください：

# mount -t tmpfs cgroup_root /sys/fs/cgroup
# mkdir /sys/fs/cgroup/cpu
# mount -t cgroup -ocpu none /sys/fs/cgroup/cpu
# cd /sys/fs/cgroup/cpu

# mkdir multimedia      # create "multimedia" group of tasks
# mkdir browser         # create "browser" group of tasks

# #Configure the multimedia group to receive twice the CPU bandwidth
# #that of browser group

# echo 2048 > multimedia/cpu.shares
# echo 1024 > browser/cpu.shares

# firefox &     # Launch firefox and move it to "browser" group
# echo <firefox_pid> > browser/tasks

# #Launch gmplayer (or your favourite movie player)
# echo <movie_player_pid> > multimedia/tasks

容量感知スケジューリング¶

1. CPU容量¶

1.1 はじめに¶

従来の同質なSMPプラットフォームは、完全に同一のCPUで構成されています。一方、異質なプラットフォームは、性能特性が異なるCPUで構成されており、このようなプラットフォームでは、すべてのCPUを同一視できません。

CPU容量は、システム内の最もパフォーマンスの高いCPUに対して正規化された値で、CPUが達成可能な性能を示します。異質なシステムは、異なる容量を持つCPUを含むため、非対称CPU容量システムと呼ばれます。

最大達成可能な性能（つまり最大CPU容量）の差異は、以下の2つの要因に起因します：

  • すべてのCPUが同じマイクロアーキテクチャ（µarch）を持つとは限りません。

  • 動的電圧周波数スケーリング（DVFS）により、すべてのCPUが物理的に高い作業パフォーマンスポイント（OPP）を達成できるとは限りません。

ARM big.LITTLEシステムは、この2つの例です。big CPUはLITTLE CPUよりもパフォーマンス志向であり（より多くのパイプラインステージ、より大きなキャッシュ、よりスマートな予測など）、通常LITTLE CPUよりも高いOPPを達成できます。

CPUのパフォーマンスは、通常、毎秒百万命令（MIPS）で表現され、Hzごとの達成可能な命令数として表現することもできます。これにより以下の式が得られます：

capacity(cpu) = work_per_hz(cpu) * max_freq(cpu)

1.2 スケジューラの用語¶

スケジューラ内で2つの異なる容量値が使用されます。CPUの capacity_orig は、そのCPUの最大達成可能な容量、つまり最大達成可能なパフォーマンスレベルを示します。CPUの capacity は、そのCPUの capacity_orig に、利用可能なパフォーマンスの一部（例：IRQの処理に費やす時間）が引かれた値を示します。

注意：CPUの capacity は、CFSクラス専用に使用されるのに対し、 capacity_orig はクラスに依存しません。このドキュメントの残りの部分では、 capacity と capacity_orig を簡潔さのため使い分けずに使用します。

1.3 プラットフォームの例¶

1.3.1 同じOPP¶

仮想的な2コア非対称CPU容量システムを想定し、

  • work_per_hz(CPU0) = W

  • work_per_hz(CPU1) = W/2

  • すべてのCPUが同じ固定周波数で動作している場合、

上記の容量の定義に基づき：

  • capacity(CPU0) = C

  • capacity(CPU1) = C/2

ARM big.LITTLEと対応すると、CPU0はbig、CPU1はLITTLEと対応します。

固定量の作業を定期的に実行するワークロードでは、実行トレースは以下のようになります：

CPU0 work ^
          |     ____                ____                ____
          |    |    |              |    |              |    |
          +----+----+----+----+----+----+----+----+----+----+-> time

CPU1 work ^
          |     _________           _________           ____
          |    |         |         |         |         |
          +----+----+----+----+----+----+----+----+----+----+-> time

CPU0はシステム内の最大容量（C）を持ち、固定量の作業WをT単位の時間で完了します。一方、CPU1はCPU0の半分の容量を持ち、そのためT単位の時間でW/2しか完了しません。

1.3.2 異なる最大OPP¶

通常、容量値が異なるCPUは最大OPPも異なります。上記と同じCPU（つまり同じwork_per_hz()を持つ）を以下のように考慮します：

  • max_freq(CPU0) = F

  • max_freq(CPU1) = 2/3 * F

これにより、

  • capacity(CPU0) = C

  • capacity(CPU1) = C/3

1.3.1節で説明した同じワークロードを、各CPUが最大周波数で実行する場合、以下のように結果します：

CPU0 work ^
          |     ____                ____                ____
          |    |    |              |    |              |    |
          +----+----+----+----+----+----+----+----+----+----+-> time

                           workload on CPU1
CPU1 work ^
          |     ______________      ______________      ____
          |    |              |    |              |    |
          +----+----+----+----+----+----+----+----+----+----+-> time

1.4 表現に関する注意点¶

注意すべきは、ある 単一の 値でCPU性能の違いを表すことが、ある程度の議論の的です。2つの異なるマイクロアーキテクチャ間の相対的なパフォーマンス差は、整数演算ではX%、浮動小数点演算ではY%、ブランチではZ%など異なります。それでも、この単純なアプローチで得られた結果はこれまで十分でした。

2. タスク利用率¶

2.1 はじめに¶

容量を考慮したスケジューリングでは、タスクのCPU容量に関する要件を表現する必要があります。各スケジューラークラスはこれを異なる方法で表現でき、タスク利用率はCFSに特有ですが、より一般的な概念を紹介するためにここに記述するのは便利です。

タスク利用率は、タスクのスループット要件を表すパーセンテージです。これはタスクのディューティーサイクルで簡易に近似できます。つまり：

task_util(p) = duty_cycle(p)

固定周波数のSMPシステムでは、100%の利用率はタスクが忙しいループであることを示します。逆に、10%の利用率は、実行よりも睡眠時間が長い小さな周期タスクであることを示唆します。変動するCPU周波数や非対称なCPU容量はこれの複雑さを多少増しますが、次のセクションで詳しく説明します。

2.2 周波数不変性¶

考慮すべき問題は、ワークロードのディューティーサイクルが現在のCPUが実行しているOPPに直接影響されることです。特定の周波数Fで周期的なワークロードを実行する場合を考えてみましょう：

CPU work ^
         |     ____                ____                ____
         |    |    |              |    |              |    |
         +----+----+----+----+----+----+----+----+----+----+-> time

これにより、duty_cycle(p) == 25%になります。

次に、以下のようなワークロードを実行する場合を考えてみましょう： 同じ 周波数F/2で実行する場合：

CPU work ^
         |     _________           _________           ____
         |    |         |         |         |         |
         +----+----+----+----+----+----+----+----+----+----+-> time

これにより、duty_cycle(p) == 50%になります。タスクの動作はどちらの実行でも完全に同じ（つまり同じ量の作業を実行）であるにもかかわらずです。

次の式を用いることで、タスク利用率信号は周波数不変性を持つことができます：

task_util_freq_inv(p) = duty_cycle(p) * (curr_frequency(cpu) / max_frequency(cpu))

上記の2つの例にこの式を適用すると、周波数不変性を持つタスク利用率は25%になります。

2.3 CPU不変性¶

CPU容量はタスク利用率に類似した影響を与えます。容量値が異なるCPUで同一のワークロードを実行すると、異なるディューティーサイクルが生じます。

1.3.2節で説明したシステムを考えてみましょう、つまり：

- capacity(CPU0) = C
- capacity(CPU1) = C/3

各CPUが最大周波数で実行する場合、特定の周期ワークロードを実行すると以下のように結果します：

CPU0 work ^
          |     ____                ____                ____
          |    |    |              |    |              |    |
          +----+----+----+----+----+----+----+----+----+----+-> time

CPU1 work ^
          |     ______________      ______________      ____
          |    |              |    |              |    |
          +----+----+----+----+----+----+----+----+----+----+-> time

つまり、

  • duty_cycle(p) == 25% となるのは、p が CPU0 で最大周波数で実行される場合

  • duty_cycle(p) == 75% となるのは、p が CPU1 で最大周波数で実行される場合

タスク利用率は以下の式により CPU 不変性を実現できます

task_util_cpu_inv(p) = duty_cycle(p) * (capacity(cpu) / max_capacity)

with max_capacity システム内の最高 CPU 容量値を表します。この式を先ほどの例に適用すると、CPU 不変性を持つタスク利用率は 25% となります

2.4 不変タスク利用率¶

周波数および CPU の不変性を両方適用する必要があります。タスク利用率が CPU および周波数不変性を持つ場合の擬似式は、タスク p に対して以下のようになります

                                   curr_frequency(cpu)   capacity(cpu)
task_util_inv(p) = duty_cycle(p) * ------------------- * -------------
                                   max_frequency(cpu)    max_capacity

言い換えれば、不変タスク利用率とは、タスクがシステム内の最高容量 CPU で最大周波数で実行されているかのように振る舞うことを表します

以下のセクションで言及するタスク利用率はすべてその不変形式を指します

2.5 利用率推定¶

クリスタルボールを持たない限り、タスクの挙動（したがってタスク利用率）はタスクが最初に実行可能になる瞬間には正確に予測できません。CFS クラスは、Per-Entity Load Tracking (PELT) メカニズムに基づいて少数の CPU およびタスク信号を保持しており、そのうちの一つが 平均 利用率（瞬時とは異なります）を提供します

これは、容量を考慮したスケジューリング基準が「真の」タスク利用率（クリスタルボールを用いて）を考慮して記述されるものの、実装では常にその推定値しか使用できないことを意味します

3. 容量を考慮したスケジューリング要件¶

3.1 CPU 容量¶

Linux は現在 CPU 容量を自動で判別することはできず、この情報は外部から提供する必要があります。アーキテクチャは arch_scale_cpu_capacity() を定義する必要があります

ARM および ARM64 アーキテクチャは、この機能を arch_topology ドライバの CPU スケーリングデータに直接マッピングしており、これは capacity-dmips-mhz CPU バインディングから導出されます。詳細は Documentation/devicetree/bindings/arm/cpu-capacity.txt を参照してください

3.2 周波数不変性¶

2.2 で述べたように、容量を考慮したスケジューリングには周波数不変なタスク利用率が必要です。アーキテクチャは arch_scale_freq_capacity(cpu) を定義する必要があります

この関数を実装するには、各 CPU がどの周波数で実行されているかを判別する必要があります。実装方法の一つは、CPU の現在の周波数に比例してインクリメントするハードウェアカウンタ（x86 では APERF/MPERF、ARM64 では AMU）を活用することです。もう一つの方法は、カーネルが切り替わった周波数を認識しているときに cpufreq の周波数遷移に直接ハックする方法です（ARM/ARM64 でもこの方法が使用されています）

4. スケジューラトポロジー¶

スケジューラドメインの構築中に、スケジューラがシステムが非対称CPU容量を示しているかどうかを判断します。その場合、

  • sched_asym_cpucapacity静的キーフラグが有効になります。

  • SD_ASYM_CPUCAPACITYフラグが、すべてのユニークなCPU容量値をカバーする最低限のsched_domainレベルで設定されます。

sched_asym_cpucapacity静的キーフラグは、非対称CPU容量システム向けのコードセクションを保護するためのものです。ただし、このキーフラグは システム全体で。cpusetsを用いた以下の設定を想像してください：

capacity    C/2          C
          ________    ________
         /        \  /        \
CPUs     0  1  2  3  4  5  6  7
         \__/  \______________/
cpusets   cs0         cs1

これは以下の方法で作成できます：

mkdir /sys/fs/cgroup/cpuset/cs0
echo 0-1 > /sys/fs/cgroup/cpuset/cs0/cpuset.cpus
echo 0 > /sys/fs/cgroup/cpuset/cs0/cpuset.mems

mkdir /sys/fs/cgroup/cpuset/cs1
echo 2-7 > /sys/fs/cgroup/cpuset/cs1/cpuset.cpus
echo 0 > /sys/fs/cgroup/cpuset/cs1/cpuset.mems

echo 0 > /sys/fs/cgroup/cpuset/cpuset.sched_load_balance

システムにCPU容量の非対称性があるため、 通常のRCU読み込み側クリティカルセクションは、条件付きでスリープロックを取得することが許容されます（例として sched_asym_cpucapacity静的キーフラグが有効になります。ただし、CPU 0-1のsched_domain階層は単一の容量値をカバーしており、SD_ASYM_CPUCAPACITYフラグはその階層に設定されていません。これはSMP島を表しており、それとして扱う必要があります。

したがって、非対称CPU容量を対象としたコードパスを保護するための「標準的な」パターンは以下の通りです：

  • sched_asym_cpucapacity静的キーフラグを確認する

  • 有効な場合、sched_domain階層にSD_ASYM_CPUCAPACITYフラグが存在するかを確認する必要があります（必要に応じて、コードパスが特定のCPUまたはグループを対象としている場合）

5. 容量を意識したスケジューリングの実装¶

5.1 CFS¶

5.1.1 容量フィットネス¶

CFSの主な容量スケジューリング基準は以下の通りです：

task_util(p) < capacity(task_cpu(p))

これは一般的に「容量フィットネス基準」と呼ばれます。つまり、CFSはタスクが自身のCPUに「フィット」することを保証しなければなりません。これが破られると、タスクはCPUが提供できる以上の作業を実行する必要があります。その結果、CPUバインドになります。

さらに、uclampはユーザー空間がタスクに対して最小および最大の利用率値を指定できるようにします。これはsched_setattr()経由で、またはcgroupインターフェース経由で指定できます（参照 Control Group v2）。この名前の通り、この機能は前の基準におけるtask_util()を制限するために使用できます。

5.1.2 ワークアップCPU選択¶

CFSタスクのワークアップCPU選択は、上記の容量フィットネス基準に従います。さらに、uclampはタスクの利用率値を制限するために使用され、ユーザー空間がCFSタスクのCPU選択により多くの影響力を与えることができます。つまり、CFSのワークアップCPU選択は以下の条件を満たすCPUを探します：

clamp(task_util(p), task_uclamp_min(p), task_uclamp_max(p)) < capacity(cpu)

uclampを使用することで、ユーザー空間は例えば、低uclamp.max値を指定して忙しいループ（100%利用率）をどのCPUでも実行可能にしたり、高uclamp.min値を指定して小さな周期タスク（例：10%利用率）を最高性能のCPUで実行させることができます。

注意

CFSのワークアップCPU選択は、エネルギー意識スケジューリング（EAS）によって上書きされることがあります。これは以下の通り説明されています： エネルギー感知スケジューリング.

5.1.3 ロードバランシング¶

ウェイクアップCPU選択において、タスクがほとんど眠らない場合（場合によってはまったく眠らない場合）に発生する病理的なケースがあります。その結果、タスクがほとんど起動しない（場合によってはまったく起動しない）ため、以下のように考えます：

w == wakeup event

capacity(CPU0) = C
capacity(CPU1) = C / 3

                         workload on CPU0
CPU work ^
         |     _________           _________           ____
         |    |         |         |         |         |
         +----+----+----+----+----+----+----+----+----+----+-> time
              w                   w                   w

                         workload on CPU1
CPU work ^
         |     ____________________________________________
         |    |
         +----+----+----+----+----+----+----+----+----+----+->
              w

このワークロードはCPU0で実行すべきですが、タスクが以下のいずれかの場合、

  • 開始時点で不適切にスケジュールが設定された（初期利用効率の推定が不正確だった）

  • 開始時点で適切にスケジュールが設定されたが、急に処理能力が必要になった

場合、タスクはCPUに依存する状態（CPUバウンド）になる可能性があります。つまり、 task_util(p) > capacity(task_cpu(p))CPU容量スケジューリング基準が破られているため、ウェイクアップイベントがなくなると、ウェイクアップCPU選択によってこの問題を修正できなくなる可能性があります。

このような状況にあるタスクは「misfit（不適合）タスク」と呼ばれ、これを処理するメカニズムも同名です。misfitタスクの移動はCFSロードバランサーを活用しており、特にアクティブなロードバランス部分（現在実行中のタスクの移動を担当）を用います。ロードバランスが発生した際、misfitタスクが現在のCPUよりも容量の大きいCPUに移動可能であれば、misfitアクティブロードバランスがトリガーされます。

5.2 RT¶

5.2.1 ウェイクアップCPU選択¶

RTタスクのウェイクアップCPU選択では、以下の条件を満たすCPUを探します：

task_uclamp_min(p) <= capacity(task_cpu(cpu))

通常の優先度制約を依然として遵守しながら。候補となるCPUがこの容量基準を満たさない場合、厳格な優先度に基づくスケジューリングが実行され、CPU容量は無視されます。

5.3 DL¶

5.3.1 ウェイクアップCPU選択¶

DLタスクのウェイクアップCPU選択では、以下の条件を満たすCPUを探します：

task_bandwidth(p) < capacity(task_cpu(p))

通常の帯域幅および期限制約を依然として尊重しながら。候補となるCPUがこの容量基準を満たさない場合、タスクは現在のCPUに留まります。

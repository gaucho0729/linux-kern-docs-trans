リアルタイムグループスケジューリング¶

0. 警告¶

これらの設定をいじるとシステムが不安定になる可能性があります。設定はrootのみが操作可能で、rootが何をしているかを理解していると仮定しています。

特に重要な点:

  • sched_rt_period_usの非常に小さな値は、期間が利用可能なhrtimerの解像度や、予算更新自体にかかる時間よりも小さい場合、システムが不安定になる可能性があります。

  • sched_rt_runtime_usの非常に小さな値は、実行時間があまりにも短いためシステムが進展を困難にされる場合、システムが不安定になる可能性があります（注意: マイグレーションスレッドとkstopmachineの両方、リアルタイムプロセスです）。

1. 概要¶

1.1 問題¶

リアルタイムスケジューリングの核心は決定性です。グループはCPU時間などの帯域幅が常に一定であることを信頼する必要があります。複数のリアルタイムタスクグループをスケジュールするには、各グループにCPU時間の固定割合を割り当てなければなりません。最小保障がなければリアルタイムグループが不足する可能性があります。曖昧な上限は信頼できません。したがって、単一の固定割合が唯一の選択肢です。

1.2 解決策¶

CPU時間は、特定の期間内でどれだけ実行時間を費やすかを指定することで分割されます。各リアルタイムグループにこの「実行時間」を割り当て、他のリアルタイムグループが使用することは許可されません。

リアルタイムグループに割り当てられていない時間は、通常優先度のタスク（SCHED_OTHER）に使用されます。割り当てられた実行時間を使わなかった場合も、SCHED_OTHERが利用します。

例を挙げると、フレーム固定リアルタイムレンダラーは1秒間に25フレームを提供しなければならないため、フレームあたりの期間は0.04秒になります。音楽を再生したり入力に応じたりする必要があるため、グラフィックスに割り当てられるCPU時間は約80%です。このグループには0.8 * 0.04秒 = 0.032秒の実行時間を割り当てることができます。

このようにグラフィックスグループは0.04秒の期間で0.032秒の実行時間制限を持ちます。音声スレッドがDMAバッファを0.005秒ごとに再充填する必要がある場合、その処理には約3%のCPU時間が必要です。このグループには0.03 * 0.005秒 = 0.00015秒の実行時間でスケジュールできます。

残りのCPU時間はユーザー入力や他のタスクに使用されます。リアルタイムタスクが明示的に必要なCPU時間を割り当てられているため、グラフィックスやオーディオのバッファアンダーランを防ぐことができます。

注意: 上記の例は完全に実装されていません。非均一な期間を有効にするためのEDFスケジューラがまだ実装されていないためです。

2. インターフェース¶

2.1 システム全体の設定¶

システム全体の設定は /proc 虚擬ファイルシステムの下で構成されています:

/proc/sys/kernel/sched_rt_period_us:

100% CPU帯域幅に相当するスケジューリング期間

/proc/sys/kernel/sched_rt_runtime_us:

リアルタイムスケジューリングが使用できる時間のグローバルな制限です。CONFIG_RT_GROUP_SCHED が有効になっていなくても、リアルタイムプロセスに確保される時間の制限になります。CONFIG_RT_GROUP_SCHED が有効な場合、これはすべてのリアルタイムグループに利用可能な総帯域幅を表します。

  • 時間はマイクロ秒（us）で指定されます。これはインターフェースが s3,2 のためです。これにより、1us から約35分までの運用範囲が得られます。

  • sched_rt_period_us は 1 から INT_MAX までの値を取ります。

  • sched_rt_runtime_us は -1 から (INT_MAX - 1) までの値を取ります。

  • ランタイムが -1 の場合は、ランタイム == 期間、つまり制限がありません。

2.2 デフォルトの挙動¶

sched_rt_period_us のデフォルト値（1000000 または 1s）と sched_rt_runtime_us のデフォルト値（950000 または 0.95s）。これにより、SCHED_OTHER（非リアルタイムタスク）に 0.05s が割り当てられます。これらのデフォルト値は、ランアウトしたリアルタイムタスクがマシンをロックアップさせることを防ぎ、復旧に少しの時間残すように選ばれました。ランタイムを -1 に設定すると、古い挙動に戻ります。

デフォルトではすべての帯域幅がルートグループに割り当てられ、新しいグループは /proc/sys/kernel/sched_rt_period_us から期間を取得し、ランタイムは 0 になります。他のグループに帯域幅を割り当てたい場合は、ルートグループの帯域幅を減らし、その差分を他のグループに割り当てます。

リアルタイムグループスケジューリングは、グループにリアルタイムタスクを受けるためには、まずそのグループに総CPU帯域幅の一部を割り当てなければなりません。そのため、グループの設定を完了するまで、ルート以外のユーザーでもリアルタイムタスクを実行することはできません。ユーザーがリアルタイム優先度でプロセスを実行する権限があるとしてもです！

2.3 タスクのグループ化の基準¶

CONFIG_RT_GROUP_SCHED を有効にすると、タスクグループにリアルタイムCPU帯域幅を明示的に割り当てることができます。

これは cgroup 虚擬ファイルシステムを使用し、"<cgroup>/cpu.rt_runtime_us" を使って各制御グループに確保されるCPU時間の制御を行います。

制御グループの操作についての詳細情報が必要な場合は、 制御グループ（Control Groups） 同様に適用されます。

グループ設定は以下の制限に従ってチェックされ、構成がスケジューリング可能であることを保証します:

Sum_{i} runtime_{i} / global_period <= global_runtime / global_period

現時点では、以下のようになります（ただし今後の計画を参照してください）:

Sum_{i} runtime_{i} <= global_runtime

3. 今後の計画¶

各グループのスケジューリング期間（"<cgroup>/cpu.rt_period_us"）をカスタマイズ可能にする作業が進行中です。

期間に関する制約は、サブグループが親グループの期間よりも小さくてもしくれは等しい期間を保つ必要があります。しかし現実的には、期限ベースのスケジューリングが導入されていないと、まだ実用的ではありません。これは、リソースの競合に陥りやすいからです。

2つの兄弟グループAとBを考えてみましょう。両方とも帯域幅が50%ですが、Aの期間はBの期間の2倍です。

  • group A: period=100000us, runtime=50000us

    • 0.1秒ごとに0.05秒間実行されます

  • group B: period= 50000us, runtime=25000us

    • 0.1秒ごとに0.025秒間実行されます（または0.05秒ごとに1回実行されます）。

これは、現在Aのwhile (1)ループがBの期間全体を実行し、Bのタスク（低い優先度のタスクを仮定）が1つの期間の間リソースを奪われることを意味します。

次のプロジェクトはSCHED_EDF（Earliest Deadline Firstスケジューリング）の実装で、Linuxカーネルに完全な期限ベースのスケジューリングを導入します。上述のグループを期限ベースでスケジューリングし、期間の終了を期限として扱うことで、両方のグループが割り当てられた時間を受け取ることを保証します。

SCHED_EDFの実装には時間がかかるかもしれません。優先度継承（Priority Inheritance）は最大の課題です。現在のLinuxのPIインフラストラクチャは、静的な優先度レベル0-99に特化しています。期限ベースのスケジューリングでは、優先度が期限の残差（期限 - 現在時刻）に逆比例するため、期限継承が必要です。

これは、PIの仕組み全体を再設計しなければならないことを意味し、それが我々が持つ最も複雑なコードの一部の一つです。

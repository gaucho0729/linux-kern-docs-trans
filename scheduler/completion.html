完了 - 「完了を待つ」バリアAPI¶

はじめに:¶

複数のスレッドがカーネルのアクティビティが特定のポイントや状態に到達することを待っている場合、コンプリーションは競合条件を回避した解決策を提供できます。セマンティック的にはpthread_barrier()に似ており、類似の使用ケースを持っています。

コンプリーションはコードの同期メカニズムであり、ロックやセマフォの誤使用やビジーロープロセスよりも優れています。何かを待つために yield() またはユニークなmsleep(1)ループを使用する場合、wait_for_completion*()関数やcomplete()を使用することを検討すべきです。

コンプリーションを使用する利点は、明確で焦点を当てた目的を持ち、コードの意図が非常に読みやすくなることです。ただし、すべてのスレッドが結果が必要になるまで実行を継続できるため、コード効率が高まり、待機と信号送信は低レベルスケジューラのスリープ/ウェイクアップ機能を用いて非常に効率的です。

コンプリーションはLinuxスケジューラのwaitqueueとウェイクアップインフラストラクチャーベースで構築されています。waitqueue上のスレッドが待っているイベントは、「struct completion」内の単純なフラグに還元され、適切に「done」と呼ばれます。

コンプリーションはスケジューリングに関連するため、コードはkernel/sched/completion.cにあります。

使用方法:¶

コンプリーションを使用する際の3つの主要な部分は以下の通りです：

  • 「struct completion」同期オブジェクトの初期化

  • wait_for_completion()の変体のいずれかを呼び出すことで待機部分

  • complete()またはcomplete_all()を呼び出すことで信号送信側

また、コンプリーションの状態を確認するための補助関数もあります。初期化は最初に行わなければなりませんが、待機と信号送信の部分は順序を問いません。つまり、あるスレッドが別のスレッドが待機する必要があるかどうかを確認する前に、コンプリーションを「done」状態にマークしていることは完全に正常です。

コンプリーションを使用するには、#include <linux/completion.h>を必要とし、staticまたはdynamic変数をstruct completion型で作成します。

struct completion {
        unsigned int done;
        wait_queue_head_t wait;
};

これにより、待機タスクを配置する->wait waitqueueと、完了状態を示す->doneコンプリーションフラグが提供されます。

コンプリーションは同期されているイベントを参照する名前で命名すべきです。良い例は以下の通りです：

wait_for_completion(&early_console_added);

complete(&early_console_added);

良い、直感的な名前（いつも通り）はコードの可読性を助けます。コンプリーションを「complete」と名付けるのは、目的が非常に明確でない限り役立ちません…

コンプリーションの初期化:¶

動的に割り当てられた完了オブジェクトは、関数/ドライバの寿命にわたって生き続けることが保証されたデータ構造に埋め込むことが望ましく、非同期のcomplete()呼び出しとの競合を防ぐ必要があります。

wait_for_completion()の_timeout()や_killable()/_interruptible()の変体を使用する際には特に注意が必要です。これらの待機関数がタイムアウトやシグナルによって早期に返る場合でも、関連する活動（complete()や）がすべて完了するまでメモリの解放が保証される必要があります。 reinit_completion()関連する活動（complete()や）がすべて完了するまでメモリの解放が保証される必要があります。

動的に割り当てられた完了オブジェクトの初期化はinit_completion()の呼び出しによって行われます：

init_completion(&dynamic_object->done);

この呼び出しでは、待機キューを初期化し、->doneを0に設定します（つまり「未完了」または「未実行」状態）。

再初期化関数 reinit_completion()は、待機キューを触らずに->doneフィールドを0にリセットします（「未実行」状態）。この関数を呼び出す側は、並行して行われる可能性のあるracyなwait_for_completion()呼び出しの存在を確認する必要があります。

同じ完了オブジェクトに対してinit_completion()を2回呼び出すことは、キューを空に再初期化し、キューに登録されたタスクが「失われる」可能性があるため、一般的にはバグです。その場合、を使用してくださいが、他の競合条件にも注意してください。 reinit_completion() in

静的宣言と初期化にはマクロが利用可能です。

ファイルスコープでの静的（またはグローバル）宣言には、 DECLARE_COMPLETION():

static DECLARE_COMPLETION(setup_done);
DECLARE_COMPLETION(setup_done);

この場合、完了オブジェクトは起動時（またはモジュールロード時）に「未実行」状態で初期化され、init_completion()呼び出しは必要ありません。

関数内でのローカル変数として完了オブジェクトが宣言されている場合、初期化には常に DECLARE_COMPLETION_ONSTACK() 明示的に使用する必要があります。ロックデップの確認を目的としているだけでなく、限定されたスコープが意図的であることを明確にするためです：

DECLARE_COMPLETION_ONSTACK(setup_done)

ローカル変数として完了オブジェクトを使用する際には、関数スタックの短い寿命に注意する必要があります。関数が呼び出し元のコンテキストに戻る前に、すべての活動（待機スレッドなど）が終了し、完了オブジェクトが完全に使用されないことを確認する必要があります。

この点をもう一度強調します: 特にタイムアウトやシグナル(_timeout(), _killable() および _interruptible())などのより複雑な結果を持つ待機 API バリアントを使用する場合、オブジェクトが他のスレッドによってまだ使用されているにもかかわらず、待機が早すぎるタイミングで完了する可能性があり、wait_on_completion*() の呼び出し元関数から戻ると関数スタックが解放され、他のスレッドで complete() が実行された場合に微妙なデータ破壊を引き起こす可能性があります。単純なテストではこのような競合状態は発生しません。

不明確な場合は、動的に割り当てられたコンプリーションオブジェクトを使用してください。できれば、他の長寿命オブジェクトに埋め込まれ、その寿命がヘルパースレッドの寿命を上回るようなオブジェクトを使用し、またはロックや他の同期メカニズムを用いて complete() が解放されたオブジェクトに対して呼び出されないようにする必要があります。

ナイーブな DECLARE_COMPLETION() スタック上での実行はロックデップ警告を引き起こします。

コンプリーションの待機:¶

スレッドが並行処理の完了を待機する場合、初期化されたコンプリーション構造体に対して wait_for_completion() を呼び出します:

void wait_for_completion(struct completion *done)

典型的な使用例は以下の通りです:

CPU#1                                   CPU#2

struct completion setup_done;

init_completion(&setup_done);
initialize_work(...,&setup_done,...);

/* run non-dependent code */            /* do setup */

wait_for_completion(&setup_done);       complete(setup_done);

wait_for_completion() と complete() の呼び出し順序に特定の制限はありません。complete() の呼び出しが wait_for_completion() よりも先に実行された場合、待機側はすべての依存関係が満たされているため即座に続行します。逆に complete() の呼び出しが後である場合、完了がシグナルされるまでブロックします。

wait_for_completion() は spin_lock_irq()/spin_unlock_irq() を呼び出しているため、割り込みが有効であることを確認した上でのみ安全に呼び出す必要があります。割り込みが無効なアトミックコンテキストから呼び出すと、検出が難しい偽の割り込み有効化が発生します。

デフォルトではタイムアウトなしで待機し、タスクを不可中断状態にします。wait_for_completion() およびその変種はスリープ可能なプロセスコンテキストでのみ安全に呼び出せます（アトミックコンテキスト、割り込みコンテキスト、無効なIRQ、プリエンプション無効の状況では使用できません）。以下の try_wait_for_completion() を参照してください。アトミック/割り込みコンテキストでのコンプリーション処理の方法についても説明しています。

すべての wait_for_completion() 変種は、待機しているアクティビティの性質により長時間ブロックする可能性があるため、ほとんどの場合、ミューテックスを保持しながらこの関数を呼び出すことは推奨されません。

利用可能な wait_for_completion*() 変種:¶

以下の変異体はすべてステータスを返却し、このステータスはほとんどの（またはすべての）ケースで確認する必要があります。ステータスを意図的に確認しないケースでは、その理由を説明するコメントを追加することをお勧めします（例: arch/arm/kernel/smp.c:__cpu_up()を参照）。

よく発生する問題の一つは、返却型の割り当てが不正確であることです。返却値を適切な型の変数に割り当てるよう注意してください。

返却値の特定の意味を確認する行為も、精度が低くなることが確認されています。例えば、以下の構文のように：

if (!wait_for_completion_interruptible_timeout(...))

…成功した場合と中断された場合のどちらでも同じコードパスを実行するため、おそらく意図しない動作になる可能性があります：

int wait_for_completion_interruptible(struct completion *done)

この関数は、待機中にタスクをTASK_INTERRUPTIBLEにマークします。待機中にシグナルが受信された場合、-ERESTARTSYSを返却し、それ以外は0を返却します：

unsigned long wait_for_completion_timeout(struct completion *done, unsigned long timeout)

タスクはTASK_UNINTERRUPTIBLEにマークされ、最大で「timeout」jiffiesの間待機します。タイムアウトが発生した場合は0を、それ以外はjiffies単位の残り時間を返却します（ただし、少なくとも1は保証されます）。

タイムアウトはmsecs_to_jiffies()またはusecs_to_jiffies()で計算することが望ましく、これによりコードがHZ依存性を持たないようになります。

返却されたタイムアウト値を意図的に無視する場合、その理由を説明するコメントを追加するべきです（例: drivers/mfd/wm8350-core.c wm8350_read_auxadc()を参照）：

long wait_for_completion_interruptible_timeout(struct completion *done, unsigned long timeout)

この関数はjiffies単位のタイムアウトを渡し、タスクをTASK_INTERRUPTIBLEにマークします。シグナルが受信された場合、-ERESTARTSYSを返却し、それ以外はタイムアウトした場合は0、完了した場合はjiffies単位の残り時間を返却します。

さらに、_killable変異体はTASK_KILLABLEをタスクの状態として使用し、中断された場合は-ERESTARTSYSを返却し、完了した場合は0を返却します。_timeout変異体もあります：

long wait_for_completion_killable(struct completion *done)
long wait_for_completion_killable_timeout(struct completion *done, unsigned long timeout)

_io変異体（wait_for_completion_io()）は非_io変異体と同様の動作をしますが、待機時間を「IOの待機」として計測するため、スケジューリング/IO統計でのタスクの計測に影響を与えます：

void wait_for_completion_io(struct completion *done)
unsigned long wait_for_completion_io_timeout(struct completion *done, unsigned long timeout)

完了を通知する：¶

継続の条件が満たされたことを通知したいスレッドは、waitersのうち1つを継続可能にするためにcomplete()を呼び出します：

void complete(struct completion *done)

…または、すべての現在および将来のwaitersを通知するためにcomplete_all()を呼び出します：

void complete_all(struct completion *done)

完了を通知する際、スレッドが待機を開始する前に通知が行われても正常に動作します。これはwaiterが「doneフィールド（struct completion）を消費（デクリメント）する」ことで実現され、待機スレッドの起動順序はエンキューされた順（FIFO順序）で行われます。

complete()が複数回呼ばれた場合、その数だけwaiterが継続できるようになります。complete()の各呼び出しはdoneフィールドを単純にインクリメントします。complete_all()を複数回呼び出すことはバグです。complete()とcomplete_all()はIRQ/アトミックコンテキストで安全に呼び出すことができます。

特定の「struct completion」に対して、complete()またはcomplete_all()を呼び出すのは常に1つのスレッドだけです。これはwait queueスピンロックでシリアル化されています。complete()またはcomplete_all()への並行呼び出しは設計上のバグである可能性があります。

IRQコンテキストから完了を通知しても問題ありません。spin_lock_irqsave()/spin_unlock_irqrestore()で適切にロックされ、かつスリープすることはありません。

try_wait_for_completion()/completion_done():¶

try_wait_for_completion()関数はスレッドをwait queueに追加せず、スレッドをブロックする必要がある場合にfalseを返します。それ以外の場合は1つのposted completionを消費してtrueを返します：

bool try_wait_for_completion(struct completion *done)

最後に、waiterに影響を与えることなくcompletionの状態を確認するにはcompletion_done()を呼び出します。posted completionがまだwaiterによって消費されていない場合（waiterが存在することを示す）にはfalseを返し、それ以外はtrueを返します：

bool completion_done(struct completion *done)

try_wait_for_completion()とcompletion_done()はIRQまたはアトミックコンテキストで安全に呼び出すことができます。
